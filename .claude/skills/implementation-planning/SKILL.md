# 从架构到可信交付

把架构承诺连接到有依据的实现选择，以及能够逐步兑现承诺的计划。核心问题是：
哪些现有成果能承担我们的语义，哪些责任仍由我们承担，以及怎样尽早知道这条
实施路径确实走得通。

本 skill 提供研究和规划的判断方法。按当前能力的风险与未知展开，不要求固定
阶段、候选数量、计划模板或工具链，也不把每次局部修改升级为完整选型研究。

## 以架构承诺为锚，以实现证据校准路径

从本次能力的需求、架构结论及其接受状态出发，辨认必须保持的可观察行为和仍可
选择的实现机制。已有正式规格时引用精确版本；尚未形成规格时，以可识别的设计稿
为研究依据，显式保留未决项。不要要求先有完整 spec 才能研究如何实现它。

在依赖技术选择的规格映射和实施计划定稿前，完成针对性的行业研究与可行性评估。
语义规格可以与研究相互校准：规格使候选比较有依据，研究暴露隐藏假设；不能让
某个库的对象模型、默认行为或 API 反向成为未经选择的领域承诺。

语言无关的设计仍需遵守项目已确认的技术约束。具体前提从
[系统要求](../../../docs/requirements/system/constraints.md)和当前决定读取。
发现实现限制时，区分某个候选不适用、已有证据不足与架构假设被反例否定；不能
从“这个库做不到”直接推导“降低系统保证”。需要改变语义时回到
[architecture-design](../architecture-design/SKILL.md)及其权威入口处理。

## 调研的价值在于减少会改变决策的不确定性

把调研问题写成与本能力有关的判断：候选能否兑现哪项承诺，差异在哪里，什么
观察会使我们改变选择。调查成熟产品、开源实现、标准和理论时，先找相同问题
与相同前提，避免只找相似名称、熟悉框架或能快速跑通的 API。

比较候选时先看必要语义能否成立，再比较适配、验证、维护和运行的总成本。
成熟度应由相关使用经验、维护状况和边界行为支持，不能用流行程度代替契约适配。
只展开会影响选择的因素；例如需要动态卸载时，资源所有权与停止行为通常比接口
是否简洁更有决定性。性能取舍应对应实际负载和瓶颈证据，沿用
[研发品味](../engineering-taste/SKILL.md)的复杂度判断。

外部技术事实核对官方文档、论文、采用版本的源码及测试，保留具体页面、版本或
提交，以及它支持的结论和局限。社区材料可用于发现候选和反例，关键主张回到
原始来源验证。已有研究在版本、假设和采用范围仍有效时可以复用；不能把模型记忆
或陈旧比较当作当前选型证据。无法核实时保留未知，不包装成已验证的推荐。

理论、算法和现成设计也可以复用，但要解释其前提如何映射到本系统。理论结论、
上游测试、源码实验、实际采用的包或 fork 的行为，是不同范围的证据；它们之间
需要可解释的映射。核对 Cordis/DSH 原语时使用
[cordis-authoritative-docs](../cordis-authoritative-docs/SKILL.md)。

优先验证一旦失败就会使大量后续工作作废的假设。文档不足以判断关键行为时，
用能区分候选的最小实验或真实组合探针取得证据；实验应针对争议的失败、并发或
生命周期边界，只有 happy path 的演示不能回答这些问题。并非每个依赖都需要实验。
当必要保证已有足够依据、剩余未知不会改变当前选择且有明确处置时，停止扩展
搜索；候选目录的长度不代表调研质量。

结论应给出有证据支持的推荐、影响取舍的关键差异，以及尚待验证的部分对推进的
影响。证据不足以选定路径时，指出能区分选项的下一项观察；不要以资料汇总代替
判断，也不要为了给出确定答案而隐藏未知。

## 复用是在承接成果的同时分配责任

按[复杂度与复用](../../../docs/architecture-guide/assurance/judgment.md#复杂度与复用)
优先复用符合要求的成熟成果。衡量的是本项目最终需要拥有多少语义、代码和维护
责任，而非本次少写多少行。复用可以止于一个算法或可靠组件，不必接受整个上游
应用的架构与策略。

| 路径 | 判断它是否合适的关键 |
|---|---|
| 直接采用 | 候选在实际采用范围内兑现契约，我们能够控制所需配置、资源与失败边界 |
| 通过适配组合 | 差异属于表示或真实边界映射，适配能闭合责任，不依靠包装掩盖行为不符 |
| fork 后二次开发 | 有价值的成熟内核值得保留，必要行为差异能在明确的维护边界内直接修改 |
| 自建必要部分 | 相关成熟方案经评估仍无法满足必要契约，或适配、fork 的总体负担更高 |

这些路径可组合，不是必须逐级尝试的流程。选择应说明为什么它比相关替代方案更
适合本能力；自建的依据是具体缺口，fork 的依据是可承担的差异和保留下来的价值。
源码可改不等于应该重写，也不必为等待上游接受补丁而放弃项目已拥有的维护权。

评估 fork 时把后续责任算入选择：采用和保留的源基线、我们修改的语义及其验证、
需要吸收的上游修复，以及持续合并或主动分化的代价。按实际使用核对许可和维护
条件；不把 fork 当作一次复制后免费的资产。项目既定的 Cordis 与 DSH 维护边界
沿系统要求执行，不将所有依赖统一改为 fork，也不为自有 fork 无理由保留兼容层。

## spec 固定承诺，计划解释如何兑现承诺

研究结果应进入它所支持的材料：事实与局限归研究，选择与取舍归相应提案或决定，
精确语义归 spec，实现版本、映射与推进依据归相关实现材料。具体归属和接受规则
沿[组织规范](../../../docs/maintenance/organization.md)及其导航，不在计划中
建立第二份会独立演化的契约。

具体提供者与应用装配进入[当前实现设计正文](../../../docs/maintenance/organization.md#当前实现设计的归属)，
计划引用采用快照并安排交付。服务键、注入、运行资源和跨能力交接不能只留在
一次性施工稿；已实现的精确签名引用公共源码。维护规格及其映射时使用
[spec-maintenance](../spec-maintenance/SKILL.md)。

定稿时应能看出每项关键保证由谁负责：哪些由采用的实现承担，哪些需要本项目
补足，哪些仍缺证据。数据形状不能代替行为，底层提供一个原语也不能自动证明
跨能力组合已满足产品要求。库版本或调用细节通常属于实现映射；只有已明确成为
外部承诺的内容才进入相应契约。

若新的技术证据确实要求调整设计，说明受影响的假设、语义和证据，按既有治理
处理后再更新依赖项。研究结论不自动接受设计，计划也不批准修改已发布规格。
未决选择只阻止依赖它的定稿或实施；独立研究、候选建模和不依赖该选择的工作
仍可继续。

按[设计就绪](../../../docs/maintenance/spec-maintenance.md#设计就绪与实施入口)
判断本次依赖是否齐备。延后映射记录负责产物、维护归属、受影响消费者和闭合
时点；不能从语义已接受推断插件消费者已经具备实施输入。

## 把计划写成可检验的交付论证

计划应让执行者和审阅者理解：从当前状态到目标能力，需要建立哪些事实，工作
之间为何依赖，什么结果足以支持继续推进或宣布完成。文件清单、工期和完成百分比
可以帮助安排工作，但不能代替这条论证。

**以可观察增量衡量推进。** 优先围绕完整行为组织可验收的小增量，让真实调用、
状态和结果尽早贯通。确有共享基础工作时，说明哪个消费者需要它、何时接入验证；
避免各技术层分别“完成”而系统长期没有可运行行为。最终交付必须回到完整目标，
不能把早期薄增量悄悄当作全部范围。

**按不确定性和依赖排序。** 区分实现上的先后关系与尚未验证的共同假设。优先处理
会改变后续路径的高影响未知；并行工作应建立在足够稳定的契约和可独立判断的
结果上。多人依赖同一未验证机制时，先贯通代表性组合通常比同时复制假设更有效。
效率以得到可信交付的总时间和返工成本衡量，不以同时启动多少任务衡量。

**让验收独立于实现叙述。** 从需求和契约推导可观察结果及重要反例，说明由什么
测量支持判断。根据风险覆盖失败、并发、恢复及跨能力组合，并为真实装配留下
明确的验证工作。mock、组件通过或文档检查不能代替产品边界的证据；性能目标也
需要可复现的负载与比较依据。验证应能推翻错误实现，而不是重复实现的内部结构。

**让任务可以可靠接续。** 工作边界应足以让执行者找到采用版本、允许改变的范围、
依赖输入、预期产物和完成依据，无须猜测原设计者的隐含意图。契约缺口、技术未知
和环境缺失需要不同处置，不能混成笼统的“阻塞”。按任务需要在现有计划或记录中
保留已确认、待验证和实际测得的状态，不另造平行台账或重新抄写规格。

**让计划能够被证据修正。** 明确什么观察会使路径失效、哪些工作因此需要调整。
实验推翻假设、组合验证失败或依赖变化时，修正受影响的选择与证据，保留仍有效
的进展；不要为维持进度表而弱化验收，也不要每次失败都重开整个架构。只有依赖
已稳定、风险可解释的部分才适合细化承诺；更远的工作可保留方向和依赖，不制造
精确工期与充分验证的假象。

例如，若架构要求任务重启后可恢复、同一任务只有一个有效执行者，采用成熟任务库
后仍需解释持久状态、执行权和恢复交接由谁承担。一个有价值的早期增量能观察到
真实持久化、重启和执行权竞争的结果，并显式限定外部副作用的保证范围；“库已
接入、调度模块已完成、mock 测试通过”尚不足以支持这些承诺。

## 完成判断与使用边界

一个计划准备就绪，应有足够证据支持实施选择，并使执行者知道下一项可验收的
增量、所依赖的事实及失败后的调整方向。这不等于能力已经交付。能力完成还需要
在实际集成状态下兑现本次范围内的契约，并保留可核对的证据和覆盖局限；沿
[验证规范](../../../docs/maintenance/verification.md)与
[贡献指南](../../../CONTRIBUTING.md)说明结果，不能从计划获批或检查变绿推断。

所需行为、技术依据、责任归属与交付判断已清楚时，停止增加规划细节。具体命令、
工作树操作、角色配置和正式接受分别使用其既有入口。本 skill 不规定编排框架，
不增加发布、合并或外部动作的授权，也不要求为使用指导而创建额外治理材料。
