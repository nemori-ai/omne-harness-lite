## 1. 这条线管什么

一句话：让「系统有多快、多省、撑得住多大」随时答得出来，并且不随着演进悄悄变差。

### 1.1 三个维度，两端

性能工程不只是速度。它管三个并列的维度：

| 维度 | 问的是 | 例子 |
| --- | --- | --- |
| 时间 | 一件事要等多久，能同时做多少 | 一轮的用时、首字之前的等待、打开一个会话、界面掉不掉帧 |
| 空间 | 占多少内存、多少磁盘，随使用怎样涨 | 服务进程的内存、数据目录的字节、每类记录有没有终点、页面的 DOM 与堆、安装包的大小 |
| 经济性 | 每一轮花多少 token，前缀缓存命中不命中 | 发给模型的请求是不是只追加、有没有多带 |

经济性是 agent harness 特有的一头：每一轮都把历史重发给模型，装法差一点，费用与首字等待就差几倍。

两端：服务端（核心领域与发行装配）与桌面界面。人直接等的几个时刻跨两端，分段量。

### 1.2 四种手段，次序是先后

1. **算。** 每条热路径写出代价怎样随负载变：现在的实现是多少，任何实现至少要多少，设计上许它多少。差距就是优化的空间，方向也在里面。这一步不用跑。
2. **数。** 用确定的计数（提交数、读数、字节、请求数、重渲次数）验证实现符合算出来的式子。任何机器上都判得了。
3. **量。** 有噪声的时间与内存，只在标定过的机器上量。量的目的是读出式子里的常数，和守住人感觉得到的那几个时刻。
4. **看趋势，然后优化。** 结果留下来；按差距从大到小改，改前改后各有读数。

软件工程上这叫性能工程。第 2 到 4 件是其中的持续基准测试与性能回归测试；第 1 件是设计期的性能建模。业界大多只做后面三件，结构性的问题要等量出来才发现。我们把「算」放在最前面。

### 1.3 不管的

线上真实运行时发生了什么（可观测性，归产品自己）；模型答得好不好、供应商快不快；准入与测试跑得快不快（运维线）；功能对不对（修复线）。

### 2.4 别家怎样做，我们取什么

细节在调研笔记第三、四节。

- 多数 agent harness 没有成体系的性能工程：手写基准、不进门禁、靠人看。
- 取 VS Code 聊天性能回归的三样：假模型驱动场景；首字用绝对阈值、其余用相对阈值；回到初始状态之后看堆还剩多少。
- 取 opencode 的一样：把「不该发生的事」写成精确的计数，例如切回已缓存的会话请求数必须是 0。
- 取 gemini-cli 与 pi-mono 的两样：基线文件进仓库；每条性能修复带改前改后的数字与复现命令。
- 取 Codex 的存储做法作对照：老会话压缩、工具输出落盘时截断、日志分区限额。
- 取 Claude Code 的一条：前缀缓存的命中率是事故级的指标。
- 取 TigerBeetle 的两条：设计时就写资源的估算；所有循环与队列有固定的上界。

## 3. 先算：代价模型

### 3.1 什么算得出来，什么只能量

| | 算得出来 | 只能量 |
| --- | --- | --- |
| 是什么 | 次数与字节：提交、读、请求、帧、重渲、DOM 节点、token。它们随负载怎样增长。任何实现的下界。队列稳不稳、会不会积压 | 常数与分布：一次落盘多久、一次渲染多久、垃圾回收与调度的抖动、尾部的延迟、真实模型的缓存命中 |
| 由什么决定 | 结构。与机器无关 | 机器、运行时、当时的负载 |
| 用来做什么 | 定设计、定门的期望值、指优化的方向 | 填式子里的常数，守住人感觉得到的时刻 |

所以量是用来验证实现符合模型、读出常数的，不是用来发现结构的。结构性的问题在设计时就该算出来。

### 3.2 代价模型

每条热路径一份代价模型。它是仓库里的一页文档，放在这条路径的套件目录里，不是 GitHub 上的卡。它是这条线最基本的一样东西，套件、门、优化都从它出来。一份写六栏：

1. **路径**：用户的哪个动作，经过哪些领域。
2. **负载的参数**：决定代价的那几个量。
3. **现在的代价**：读源码写出的式子。每一项注明是读到的还是推出的。
4. **下界**：任何实现都要付的。例如要显示一屏就至少要读一屏。
5. **设计预算**：我们许它多少，介于下界与现在之间，写明取舍的理由。
6. **怎样守**：规格里的哪一句、哪个静态检查、哪份形式化模型、哪道计数门。

「现在」与「下界」差多少倍、差在阶上还是常数上，就是这条路径的优化空间。差在阶上的先做。

### 3.3 现在就算得出来的

参数：N 是会话到现在的轮数，k 是一轮里的步数，d 是每轮新增的上下文，S 是系统提示加工具声明；L 是一条正在生成的内容的长度，b 是每帧新增的长度；H 是会话历史的字节数，P 是一页的大小（64 KiB），M 是会话的条目数，V 是视口放得下的条目数；c 是一次调用的提交数，t 是一次落盘提交的耗时。

| 路径 | 现在的代价 | 下界 | 差在哪 |
| --- | --- | --- | --- |
| 流式一条内容（两端） | 每帧带全文：总字节约 L²/(2b)，在客户端过四遍；每帧 Markdown 全文重渲；服务端每个事件全值比较一次。都与 L² 成正比 | 总字节与 L 成正比；每帧只处理新增的与最后一个没闭合的块 | 阶。例：模型用工具参数写一个 100 KB 的文件，每秒 200 字节，现在累计处理约 250 MB，下界 100 KB |
| 流式的每一帧重渲多少组件 | 订阅整份工作区的全部组件 | 1 个：正在生成的那一块 | 常数，但每帧都付 |
| 打开一个会话 | ⌈H/P⌉ 次串行请求；每页全量排序与重算；DOM 节点与 M 成正比 | 1 次请求；DOM 节点与 V 成正比 | 阶 |
| 切回打开过的会话 | 同「打开」 | 0 次历史请求，只取离开之后新增的 | 阶 |
| 启动的首屏 | 全部模块的脚本，加用到的字体片 | 外壳加当前页 | 常数。没有构建产物，字节数没有量 |
| 一轮的读 | 约 240 次，与 N 无关（实地） | 与 k 成正比：每步按键读一次当前状态 | 常数。240 次里谁在读还没分清 |
| 一轮的提交 | 约 133 + 0.27·N（实地，取自第 15 轮与第 110 轮两个点） | 与 k 成正比，与 N 无关 | 阶：随 N 涨的那一项应当是 0。原因没查 |
| 一次工具调用的用时 | 提交串行，落盘设置是每次提交都同步（读到），所以不少于 c·t。旧数 151 次、每次约 6 毫秒，算出 0.9 秒，与旧的实测一致 | 个位数次提交 | 常数，大：式子说明用时由提交数决定，减提交数是唯一的路 |
| 日志的字节 | 旧数 200 轮 134 MiB | 新增内容的总和，与 N·d 成正比 | 可能在阶上。现有的界是 64 KiB 加每步 12 KiB |
| 发给模型的输入 | 每轮重发历史：N 轮合计 N·S + d·N(N+1)/2 | 接口决定的，同左。前缀缓存命中时读取的单价约为十分之一 | 我们管的是三件：前缀逐字稳定、不多带、压缩的触发点。发行装配上稳不稳没有核 |
| 服务端的内存 | 约每轮多 20 MB（实地，方向） | 常数加有界的缓存 | 阶 |
| 每类持久记录的条数 | 回执只增不减（读到） | 在途的加保留期内的 | 阶 |
| 载入一个会话的状态 | 没有核 | 带快照时与快照之后的条目数 s 成正比。要载入不超过 R，就要 s ≤ R/f，f 是折叠一条的代价 | 没有核 |
| 多个会话同时写 | 每个事务域一个写者（读到）。到达的提交率乘每组的落盘耗时小于 1 才不积压 | 同左 | 这是稳定条件，不是差距。旧数里 40 个会话同发只完成 22 到 24 个，现在还是不是这样没有核 |

这张表是「推出」为主的第一稿。7.2 的第 0 步把它逐条核实，写成正式的代价模型。

### 3.4 模型怎样进到约束里

约束后来的 agent 的只有四样：架构与领域的边界、规格、静态检查、形式化证明。代价模型经这四样起作用，不另立一套。

- **规格里的成本句子。** 规格里已经有这样的话：会话的正常推进不全量扫描历史；派生物在变化时维护，热路径只读取；请求的变化只追加在尾部；工具的热路径按键读。代价模型把每一句翻成一个式子，再翻成一道计数门。缺的句子补进规格：例如「一帧的处理代价与已生成的长度无关」「打开会话的请求数与历史长度无关」。
- **门的期望值从式子来。** 确定的门（计数与字节）的期望是代价模型上的设计预算，不是「上次量到的数乘余量」。这样已有的退化不会被固化。只有有噪声的门才从标定来。
- **形式化模型核计数的界。** 「一次调用至多提交几次」「队列不超过多少」「重试有界」是状态不变式，TLC 能核，仓库里已有工具链。pqw 的 `formal-guard` 把「较高的性能要求」列为触发条件之一，照它走。限定：TLC 的结论只对模型里取的有限参数成立。
- **所有循环与队列有上界。** 规格里已经大量写了「有界」。代价模型把每条路径上的界列出来。按已有的规矩，合法使用碰得到的上限要有去处（分页、排队、引用），不是判失败。
- **动热路径的设计要带代价模型的差分。** 定约时写明这次改动让哪一项变了、变成什么。新能力（压缩、循环拓展件、后台调用、Skill 与 MCP）第一次落地时带自己的代价模型。

### 3.5 模型自己的限度

- 模型给的是次数与阶。常数靠量。阶对、常数小的地方不值得动：5 KB 的消息全文重解析不到 5 毫秒。所以每份代价模型除了式子还要代入一组真实的参数，看差距到底多少倍。
- 模型要被证。计数门就是模型的检验：实测的次数与式子不符，先查量法，再查实现，最后才改模型；改模型要记下来。
- 不外推。式子只在核过的参数范围内算数；范围之外的结论只当假设。
- 排队的式子要分清开环与闭环：会话是闭环的（等上一步结束才发下一步），照开环算会高估积压。

## 4. 第一版要回答的十五个问题

每个写成一句能判真假的话。「模型的期望」来自第 3 节。「怎样判」里的三种门见 5.2。

### 4.1 服务端的时间

| # | 要成立的 | 模型的期望 | 量什么 | 怎样判 |
| --- | --- | --- | --- | --- |
| 1 | **一轮的代价与会话有多长无关** | 每轮的提交数、读数、写入字节只是步数的函数，对轮数的斜率是 0 | 每轮的提交数、读数、写入字节；harness 自己的用时；请求组装的用时 | 规模门。先判计数，再判时间 |
| 2 | **一次工具调用、一次模型调用，harness 加的是小的常数** | 提交数不超过设计值；用时约等于提交数乘单次落盘 | 每次调用的提交数、读数、harness 一侧的用时；首字之前 harness 花的时间 | 结构门（提交数）；用时先只报告 |
| 3 | **冷启动、打开长会话、重启后接手，各在预算之内** | 载入与快照之后的条目数成正比，不与全部历史成正比 | 进程起来到开始受理；新进程到长会话的首页历史；重启到被打断的那一轮有结局 | 结构门（读到的行数）；绝对门（标定之后） |
| 4 | **多个会话同时推进，都做得完，互相不拖慢** | 稳定条件成立时每个会话的用时与单跑之比接近 1 | 完成的个数；每个会话的轮用时相对单跑的比值；存储的排队等待 | 「全部完成」是硬判；其余先只报告 |

### 4.2 空间

## 5. 基本机制

### 5.1 六条原则

1. **先算后量。** 每个套件从一份代价模型出来；没有代价模型的不立套件。
2. **能确定地判的就确定地判。** 计数与字节在任何机器上都一样，做硬门。时间与内存有噪声，只在标定过的机器上判，或者只看同一次运行里的前后比值。
3. **评测只读产品本来就该有的读数。** 计时段、诊断、存储的计数、页面里的计时标记，是运维和排障也要用的。读数缺了是产品的可观测性缺口，补在产品里；评测不给被测的代码打补丁。
4. **测的是生产路径。** 跑构建产物，经公开的入口，在发行装配上；界面跑打包后的页面。替身只用在不被测的边界上：模型的上游、外部网络。
5. **评测自己也要被证。** 负载先过「确实达到了目标规模」的断言；每道门有一个必须通过的样本和一个必须失败的样本；判不了就是「阻塞」，不算过。
6. **每个结果都可比、都留底。** 结果带着负载的标识、机器配置的标识、被测的提交。

### 5.2 指标的两条轴，三种门

| | 结构门：量与规模的关系对不对 | 规模门：两档或逐轮的增长 | 绝对门：不超过预算 |
| --- | --- | --- | --- |
| **确定的**（提交数、读数、行数、字节、请求数、帧数、重渲次数、DOM 节点数、token） | 任何机器上判。期望值取代价模型的设计预算 | 任何机器上判 | 任何机器上判 |
| **有噪声的**（墙钟、处理器时间、保留堆、常驻内存、长的动画帧、输入延迟） | 不适用 | 同一次运行里两档的比值，基本不受机器快慢影响 | 只在有本配置基线的机器上判；没有基线判「阻塞」 |

确定的那一行不需要专用的机器，也不会误报，第一版先让它全部生效。十五个问题里每一个都至少有一道确定的门。

### 5.3 七样共用的设施

| 设施 | 做什么 | 现在有什么可以接 |
| --- | --- | --- |
| **代价模型** | 第 3.2 节的六栏。放在被测路径的套件目录里；成本句子落到规格 | 规格里已有的成本句子；现有的形式化工具链 |
| **读数** | 服务端：计时段、每次调用的账目、存储的计数（提交、读、写入字节、落盘、排队等待）、各表的大小。界面：关键时刻的计时标记（外壳挂上、登录门出现、会话首屏、第一帧上屏）、每帧的字节、请求的计数 | 会话与 Agent 的计时段已在发；请求组装的段没接线；存储没有读数；模型与工具的用时是未知；界面一个都没有 |
| **负载定义** | 确定地生成一份负载：固定的种子、固定的形状、几档规模，带标识与有效性断言。三类：长会话的轮形；流式的回复（定总长、每帧新增多少、帧的间隔）；大的工具输出与长的历史 | 长会话的轮形；日志字节用例的两种消息大小。假模型要补上能流式吐多帧的脚本 |
| **运行器** | 服务端：每个样本一个新进程、一个私有的状态目录，只跑构建产物。界面：起真的服务端与页面宿主，经 DevTools 协议驱动无头的浏览器；启动与窗口的场景起真的 Electron。改前改后交替跑；开头结尾各跑一次噪声探针 | 长会话量法已经起真实的服务；`page-walk` 已经是 DevTools 协议；`window-walk` 已经起真的 Electron |
| **判定** | 三种门的公式；增长判定；「通过、失败、阻塞」三种结果；失败复核一次才算 | `tools/e9/metrics.mjs` 的增长判定与窗口比值。合成一份，另一份退出 |
| **基线与留存** | 基线按机器配置的标识分文件，进仓库；每次运行的摘要追加到历史 | 没有 |
| **报告** | 改前改后的比较表；每个端点写清量的是什么、对着哪张代价模型；趋势页 | 长会话量法的摘要；`loop:health` 的趋势页可以照它的样子 |

### 5.4 一个套件要交什么

一个套件对着一条用户路径。交五样，缺一样不算接进来：

1. **代价模型。**
2. **负载生成器**，带标识与有效性断言。
3. **场景**：经公开的入口驱动被测的路径，不复制产品的算法。
4. **门与对照**：每道门写明种类、期望值与它的出处（代价模型的哪一栏，或哪次标定）；每道门一个正样本一个负样本。
5. **登记**：套件清单里一行，写明改了哪些路径要重跑它。

领域照旧自己带东西：读数由领域自己发出，套件由这条线写。领域不认识评测。

### 5.5 界面怎样量

界面与服务端共用上面的设施，多出来的是这几条：

- **确定的量优先。** 请求数、帧数与每帧的字节、每帧重渲的组件数、DOM 节点数、首屏的脚本字节、取的字体片数，都是确定的，任何机器上判。界面的结构性问题（第 2.2 节）全部能用它们判。
- **有噪声的量**：启动各段、长的动画帧、流式时打字到上屏的延迟、滚动时掉的帧、堆。固定视口、窗口可见、不并发、每个场景几个新进程取中位数。
- **降速档。** 处理器降速 4 倍再跑一次，代表慢的机器，也把差异放大到噪声之上。
- **泄漏检查。** 做一遍场景，回到初始状态，强制垃圾回收，看堆比开始多出多少。
- **不量的**：观感与动效好不好看。那归负责人上手看。

### 5.6 运行与噪声

- 只在 Linux 上判时间。参照配置取这台机器（8 核、32 GB、Linux x86）。别的平台只跑确定的门。
- 判时间的运行要机器空着。向运维线的整机令牌池要全部令牌；令牌池没做完之前，用运行名额加开跑前核负载。
- 每次运行开头和结尾各跑一次固定的噪声探针。两次差得多，这次运行标「有噪声」：门失败改判「阻塞」，要重跑；门通过照常算。
- 计时的门失败时只重跑那个场景一次，两次都失败才算。
- 量法不轮询被测的系统。要知道一轮结束，订阅观察流。
- 并发的场景按闭环驱动（会话等上一步结束才发下一步），与真实的用法一致；另报开环下的到达率上限。

### 5.7 判定

```
确定的门的期望 = 代价模型上的设计预算
绝对预算       = ceil( 参照配置上的实测中位数 × 余量 )
规模预算       = 模型给的期望比值 × 余量
```

- 余量的初值 1.25。标定时三次全量运行之间的中位数差不超过一成就用它；超过就按端点放大，并把离散度写进标定记录。
- 逐轮的增长用现有的增长判定，不另造。
- 预算是源码里的常量，旁边注明出处。不能用环境变量放宽。
- 三种结果：通过、失败、阻塞。阻塞包括有噪声、没有本配置的基线、缺读数。阻塞不能写成通过。
- 现有的判据沿用：窗口比值 1.5；日志自有字节不超过 64 KiB 加每步 12 KiB。

### 5.8 基线、留存与趋势

- **基线**进仓库：一个机器配置一份，文件名是配置的标识。标识由配置算出来（处理器型号、核数、内存、系统与内核、Node 与 SQLite 的版本、文件系统；界面的再加浏览器与 Electron 的版本），不用机器名。
- **每次运行的归档**留在跑它的机器上，不进仓库。
- **历史**：每次全量运行的摘要追加成一行。建议放在仓库的一条单独的数据分支上，不进主干、不走 gate：它不是约束，只是数据。这一条是我定的，可以改。
- **趋势**：从历史生成一页，每个端点一条曲线。第一版只画，不自动判。

### 5.9 什么时候跑

| 时机 | 跑什么 | 结果怎样用 |
| --- | --- | --- |
| 成员的慢层 | 小规模的确定的门 | 红了就是红了 |
| 改了热路径的 PR，合入之前 | 登记表里对应的套件，改前改后交替 | 两份摘要附在交付声明里。失败就不合；阻塞要重跑 |
| 每次提升 `main` 之前 | 全量一次 | 追加一个历史点 |
| 0.1.0 发布之前 | 全量，在参照配置上 | 性能验收报告 |

不进准入。这是 2026-11-03 定的：准入要快；评测在自己的运行里生效。

### 5.10 预算谁批，退化怎样处置

- 处置只有三种：修代码；这是获批的架构代价，带着新的代价模型与对照改预算；是门自己的毛病，带着对照修门。
- 预算由这条线批。放宽超过 25%，或任何规模门的放宽，归负责人批（2026-11-05 定的）。
- 代价模型的设计预算在阶上放宽（例如从「与历史无关」改成「与历史成正比」），归负责人批。
- 没有新的对照数据不能放宽。不挑运气好的那一次。

### 5.11 放在哪

- 设施是一个工具成员：`tools/perf-harness/`，带规格。运行器、判定、配置标识、基线的读写、报告、自测在这里。
- 套件放在顶层 `benchmarks/<被测的路径>/`，按用户路径分目录，不照搬包的结构。每个目录里是代价模型、负载、场景、门。基线在 `benchmarks/baselines/`。
- 成本句子落在所在包组或应用的规格里。形式化模型放在成员的 `verification/` 下，照现有的做法。
- 现有的东西怎样归：`tools/e9` 的增长判定并进设施，成为唯一的一份，`tools/e9` 与 `tools/joint-b` 的适配器退出；长会话量法与历史开销迁成两个套件；两个走查脚本留在原处，界面的套件复用它们的驱动；成员里的小规模门与微基准留在原处。
- 新建成员用包模板生成。位置与名字是我定的，可以改。

### 7.4 现下要紧的

1. **第 0 步。** 不占机器，现在就能做。它做完，后面每一步都有了依据，也能提前看出哪些改动要动契约。
2. **流式的帧改成增量，早做。** 负责人已定要改。它动两份契约，越晚改消费者越多，所以排在别的界面优化之前。
3. **第 2 步里和修复线重合的那一半**（模型与工具的用时进账目、诊断读得到工具的记账）。两条线对齐由谁做，别做两遍。
4. **第 1 步等机器空。** 另一个会话在做准入与差分变异的提效，这一边重的活先不做。

## 9. 和别的线的关系

- **问题修复线**管对不对。重合的三处各说清归谁：读数的补齐是同一批代码，一个会话做完；卡 #1296（读的运行时限）是修复，改完跑这条线的套件；「打开会话读到耗尽」像缺陷，先对一下归谁。
- **产品从一到 n 线**拥有桌面界面的功能与观感。这条线拥有界面的读数、套件与预算，并做不改变行为的性能改动。看得见的变化（例如切会话时先显示缓存的内容）由两条线一起定。
- **运维线**提供机器的独占窗口。这条线的设施也给运维线量制品的大小与启动用时。
- **两条产品线**：动热路径的能力，定约时带代价模型的差分；合入之前跑对应的套件。
- 原来挂在线卡 #1220 上的事分开：性能的差异归这条线；「出了问题查得到」留在修复线；「干净的机器上装得起来」归运维线。
