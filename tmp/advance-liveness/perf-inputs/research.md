## 一、dsh 怎样做

路径相对 dsh 仓库根。

**组织**

- 顶层 `benchmarks/` 按被测的用户路径分目录，不照搬包的结构：`session-open`（大会话首次打开、升级后重开、Agent 恢复）、`session-corpus`（多会话的列表、搜索、分叉）、`agent-continuation`（长历史上的续接、工具密集的续跑）、`conversation-fold`、`active-stream-reconnect`、`terminal-io`、`user-text`、`long-session-browser`。
- 共用的支撑层 `benchmarks/support/` 只有四个文件：`built-worker.ts`（子进程隔离）、`calibration.ts`（校准与预算判定）、`machine-profiles.ts`（机型表）、`scaling-report.ts`（报告）。夹具生成留在各自目录。规矩是「至少两个目录都要用才上提」。
- 加一个评测的约定写在 `benchmarks/AGENTS.md`：一个测量路径一个目录；登记编译入口；目录里的说明写「怎样跑、量什么、开发备注」；另写一份记录，记负载、计时边界、内存终点、校准参照、备选方案、已知排除。
- 包里的 `.perf.ts` 只作诊断，不进门禁。

**防评测失效**

- 只量构建产物。计时的子进程必须是纯 Node 的 `.js`，启动时断言三样：路径在构建目录里、没有 TypeScript 加载器、包入口解析到产物。
- 每个样本一个新子进程，私有的临时目录，超时就杀，失败也清理。
- 不复制产品算法，不为测量新增生产导出。替身只用在不被测的边界上（模型适配器、工具体、传输）。
- 负载有效性断言：列表要求每一行都带投影（存储布局一变评测就失败）；语料各分位不低于实测；写出的事件数与字节数不少于要求。
- 每个预算常量自带正负对照的单测：记录下来的样本必须通过；旧的限值必须失败；合成的回归值（预算加一、期望乘 1.26）必须失败。
- 预算不能用环境变量放宽。放宽要新的多次实测加正负对照。

**负载与数据**

- 全部合成，确定性：固定种子的随机数、固定的形状常量。数据运行时生成（约 1.5 GB），不进仓库。明令不用录制的会话与用户材料。
- 分布取自真实数据的聚合：22 个分位锚点取自 1,650 个本地会话，只提取计数与字节，不含内容；合成时向上取整并断言不低于实测。
- 没有负载的版本号，靠源码常量加 Git 历史。

**度量与判定**

- 墙钟（端点级，另分阶段）、同一区间的进程 CPU 时间、整进程峰值常驻内存、两次 GC 之后的保留堆增量、受限堆下能不能跑完。磁盘字节没有预算。计数类只作诊断。
- 判中位数。次数按用例定（1 到 5 个子进程）。没有离群剔除。
- 预算 = ceil(期望 × 机型系数 2 × 余量 1.25)；在参照机上直接标定的只乘 1.25；内存与比值只乘 1.25。
- 规模类判定用两档比值，不拟合曲线。

**持续运行与结果**

- 每个 PR 必过，单独一个作业，要求机器别的不跑；合入主干之后不跑，没有定时跑。
- 结果只在单次运行里：一份 JSONL 加一份自包含的 HTML，作为制品留 7 天。没有历史趋势。它的说明明说自己「不是持续趋势系统」。
- 没有噪声探测与自动重试；跨机器的换算只是建议，不作门禁。

**起因与教训**

- 起因：一次格式升级让首次打开从约 35 毫秒退化到约 5 秒，真实日志从 0.3 秒到 26 秒、峰值 2.7 GB，合入时没人发现。
- 同机并发的检查互相污染墙钟，所以评测独占作业，敏感的用例串行。
- 变快不等于赢，要同时看保留内存。
- 明确不做：每次检出历史提交做对比；用真实录制的语料；在生产代码里加探针；用环境变量调预算。

**它没有而我们要有的**

历史趋势与留存；合入之后与定时的运行；噪声探测；磁盘字节与写入次数的预算；负载的显式版本；每轮开销不随历史增长的判定（它没有单次追加的微基准、逐轮增长曲线、fsync 计数、日志尺寸预算）。

## 二、业界做法

**指标分两类**

- 确定性的，任何机器上都能判：磁盘字节与页数、写放大、fsync 次数、系统调用数、分配字节、指令数。SQLite 用 cachegrind 数指令，称计数可重复到 7 位有效数字以上，墙钟连 1 位都难复现（sqlite.org/cpu.html）。Go 的 benchstat 对这类指标有 `assume=exact`。
- 有噪声的，必须在标定过的机器上判或只看比值：延迟分位数、吞吐、CPU 时间、常驻内存、GC 暂停。云上实测相对标准差从 0.03% 到超过 100%（Laaber 等）；链接顺序、环境变量大小这类无关细节也会改变结果（Mytkowicz 等，ASPLOS 2009）；JIT 预热不一定收敛（Barrett 等）。

**降噪的办法与代价**

| 办法 | 代价 | 适用 |
| --- | --- | --- |
| 专用机器，关频率调节，绑核 | 要有机器和运维 | 墙钟与延迟 |
| 多次取样加统计检验 | 运行时间 | 通用 |
| 同机交替跑改前与改后 | 要同时备好两个构建 | 共享机器上最便宜 |
| 数指令或模拟缓存 | 是代理指标，不含 I/O 与并行的收益，跑得慢 | CPU 密集的小函数 |
| 相对比值加校准探针 | 要有可靠的参照 | 跨机器（ClickHouse 的做法） |
| 变点检测代替固定阈值 | 要有历史，要调参 | 长期趋势（MongoDB 的做法） |

**统计**

- 报中位数与分位数，不报均值。置信区间用自助法。比较用 Mann-Whitney U，样本至少 10 次，最好 20 次（benchstat）。
- 报效应量的置信区间，不只报显著不显著（Kalibera 与 Jones，ISMM 2013）。
- 控制误报：不重跑到出现差异为止；评测一多总有偶然显著的；设噪声带；要求持续或重复确认才算。

**几个项目的节奏**

- Rust：每个合入提交跑一次，默认指标是指令数；PR 上按需跑；周报只报明确相关的变化。
- Go：面板按提交画历史并带置信区间；benchstat 做改前改后的比较。
- ClickHouse：同一批查询分别跑基线构建与待测构建；PR 跑按影响选出的子集，夜间跑全量；用校准测试当每台机器的尺子；越跑越慢的测试判为不可复现；夜间的变化要次日重复才确认。
- MongoDB：在历史序列上用变点检测找退化，替换了人工看图和固定阈值；出来的变点清单由人复核。
- Node.js 自己：`benchmark/` 按领域分组，每个参数组合一个单独的进程，`compare.js` 默认 30 次。
- Chromium、Firefox：每个测试有登记的负责人；报警有人轮值分诊；Firefox 要求重跑确认回归持续存在才立案，有分诊时限。

**常见的失效方式**

被优化掉；预热不足；测到了缓存；没达到目标规模；协调遗漏（负载生成器等慢请求回来才发下一个，慢请求被漏掉，延迟分位数失真；要按计划发送时刻算延迟）。

**防门禁太吵被关掉**

确定性的指标硬拦，有噪声的只提示；设最小样本数与噪声带；不稳的评测单独隔离；要持续或重复确认才报警；报警要有人认领、有分诊时限。

**Node 与 SQLite 一侧现成的工具**

- 微基准：tinybench（vitest bench 基于它）、mitata（带防优化、GC 控制、分配统计）。
- 进程级的改前改后：hyperfine。
- HTTP 负载：autocannon（设了速率才修正协调遗漏）、k6（负载、浸泡）。
- 诊断：`--cpu-prof`、`--heap-prof`。只用来定位，不进门禁。
- SQLite：`dbstat` 虚拟表与 `PRAGMA page_count`、`freelist_count` 量页数与空闲页；数 fsync 可以在提供者里包装计数，或用 `strace`。
- 托管的服务：CodSpeed、Bencher。小团队先不用。

## 三、别的 agent harness 与同类工具怎样做

2026-11-16。一路子代理浅克隆各家的公开仓库只读源码（没有运行），闭源的只看官方公开写过的。没查到的不代表没有。

**一句话的结论**：多数家是手写的基准脚本，不进 PR 门禁，结果靠人看。做得成体系的有四家，各在一头。

| 谁 | 成体系在哪 | 可以学的 |
| --- | --- | --- |
| VS Code 的聊天性能回归（`.github/workflows/chat-perf.yml`、`scripts/chat-simulation/`） | 固定一个版本当基线；本机的假模型服务器驱动场景（纯文字、大代码块、快速流 1000 个 token 每 2 毫秒一个、读文件、终端）；每场景 7 次；23 项指标（首 token、完成用时、堆增量、GC、布局次数、强制回流、长任务）；首 token 用绝对阈值 100 毫秒，其余用相对阈值 20%。另有泄漏检查：打开、跑完全部场景、回到初始状态，残余堆增长超过 10 MB 就失败 | 和我们最像的一套。假模型驱动的场景化回归；按指标分绝对与相对阈值；「回到初始状态之后还剩多少」的泄漏检查 |
| gemini-cli（`perf-tests/`、`memory-tests/`） | 基线文件 `baselines.json` 进仓库；每晚在专用机器上跑，不进 PR；超过基线 15%（内存 10%）失败；丢预热、多次取样、四分位过滤、取中位数。场景里有「恢复一个 60 MB 的会话」「长会话里打字的延迟」「一百万行的命令输出」 | 基线进仓库加每晚跑；把「恢复大会话」当成一条用例 |
| opencode 的 strobe（`packages/app/perf/`、`packages/desktop/perf/`、`packages/core/perf/`） | 改前改后两个构建成对交替跑，主指标给区间；机器不合格（窗口隐藏、软件渲染、限频、忙）就拒绝出数；用同一个构建比自己来自检方法。负载贴近 agent：120 轮的滚动、每秒 40 个增量的流、500 到一万个会话的首页。**把「不该发生的事」写成精确的计数**：切回已缓存的标签，请求数必须是 0 | 精确计数的断言比时间阈值稳得多；机器不合格拒绝出数 |
| pi-mono（`packages/chord/docs/benchmarks.md`、`packages/durable/test/`） | 手动跑，但每一个切片留一节读数：机器、版本、每个数字包含什么、结果表；后一个切片拿来对比。存储当成基准的一部分：同一套读写在内存、SQLite、JSONL 几种后端上比；工具输出做 1 GiB 的压测并量落盘大小与重放用时。变更记录里每条性能修复都带数字与复现命令（数组追加 32000 次从 11.3 秒到 1.4 秒） | 每条性能修复带改前改后的数字与命令；存储大小与重放用时进基准 |

**存储一侧各家怎样管**

| 谁 | 怎样落盘 | 怎样控制变大 | 量不量 |
| --- | --- | --- | --- |
| Codex | 每个会话一份 JSONL，加一个 SQLite 状态库 | 超过 7 天的用 zstd 压缩；落盘时截断，命令输出与 MCP 结果各 64 KiB；日志表每线程 10 MiB 且 1000 行；增量回收空间；读侧能倒着读、能分页 | 量。线上按 1% 采样，记每条与每轮落盘的字节、压缩比与耗时 |
| Claude Code | 转录文件 | 按天数清理；本地回收转录（收益不到一成不重写）；大的工具结果另存到会话的目录；空闲时压缩 | 遥测里有工具结果的字节数。没查到预算 |
| gemini-cli | 从整份 JSON 迁到追加写的 JSONL | 默认留 30 天，可设条数；工具输出 40000 字符截断 | 60 MB 的夹具量恢复用时 |
| opencode | SQLite | 工具输出 2000 行或 50 KiB，超出的落到文件，留 7 天 | 没查到库大小的度量 |
| goose | SQLite，WAL | 到 225000 token 自动压缩；大的工具返回另行处理 | 没查到 |
| Zed | SQLite，每个线程是 zstd 压缩的 JSON | | 没查到 |
| pi-mono | 多种后端 | 文档缓存按使用有界；JSONL 后端明说内存随历史增长 | 量，进基准 |

**运行时各家量什么**

- 线上遥测（不是 CI 读数）：Codex 记首 token 用时、请求用时、MCP 调用用时；Claude Code 记请求用时、首 token、缓存读与缓存写的 token、工具结果的字节数。
- **Claude Code 把前缀缓存的命中率当成事故级的指标**：官方博客说整个 harness 围绕前缀缓存设计，命中率过低就按事故处理；会话中途不增删工具；分叉与压缩要共用父会话的前缀。曾因为系统提示里放时间戳、工具次序不确定而破坏过缓存。
- 流式渲染是各家量得最充分的一类：VS Code、opencode、pi-mono 的终端界面（帧时间与每帧分配）、Zed（帧时间直方图）。

**带出处的规矩只有两条**：Zed 的贡献说明要求「非视觉的改进附 benchmark」；Claude Code 把缓存命中率当事故指标。

**agent harness 特有的性能问题**：每轮重发历史与前缀缓存；上下文随轮数增长与压缩；会话日志只追加越来越大；长会话的恢复与加载；工具输出很大；流式输出的渲染；子进程与沙箱的启动；多个 agent 的内存。专门为「压缩本身的耗时与收益」「沙箱启动」做公开度量的，没有查到一家。

**几乎没有一家把全部基准做成 PR 门禁。** 通行的做法是先报告，基线稳了之后只对确定性强的指标（存储大小、请求计数）设门。

## 四、桌面与前端的性能工程

2026-11-16。一路子代理读一手资料（web.dev、W3C、Electron 与 React 的官方文档、项目自己的文章）。标「推」的是它的推断。

**指标，哪些适用于本机的桌面应用**

- 直接适用：输入到下一次绘制的延迟（INP，好的线是 200 毫秒以内）、事件计时、长动画帧（LoAF，一帧被拖过 50 毫秒）、长任务、自己打的计时点（`performance.mark`、`measure`）、帧时间（60 赫兹下一帧 16.7 毫秒，留给应用约 10 毫秒）。聊天界面的核心问题是流式期间还响不响应，这几样正好回答它。
- 只当相对量用，不套绝对阈值：最大内容绘制、首次内容绘制、首字节。那些阈值是给真实网络加载定的，本机没有网络（推）。
- 要自己打点：「会话内容可见」「第一个增量上屏」。单页应用里标准的加载指标量不到切换会话（推）。

**Electron 的启动**

- 分段：进程创建、主进程模块加载到就绪、创建窗口、渲染进程加载页面与脚本、首帧、可交互。VS Code 用成对的计时点框出每一步。
- 官方的清单：审查依赖的加载成本；推迟昂贵的加载与初始化；不阻塞主进程；打成单文件；字体打进包里。
- `show: false` 加 `ready-to-show` 避免白闪，但官方说它可能太晚，所以同时设 `backgroundColor`。
- 代码在本地磁盘，没有下载的成本，包体的成本变成解析、编译、执行。分块的目的是首屏少执行，不是少下载（推）。

**流式内容的渲染**

- 每个增量都更新状态会重渲整条消息。通行的做法：流的所有权放在 React 之外的存储里，React 只订阅；按帧或按 16 到 50 毫秒合并一次；每一行按编号只订阅自己那条消息，流式期间只有正在流的那一行重渲。
- React 的并发特性帮不上这一处：外部存储的变化不能标成非阻塞的过渡（React 文档）。所以靠合并，不靠 `startTransition`（推）。
- Markdown：streamdown 按块拆分、每块单独缓存，只重渲变了的块；它每个增量是否对全文重新分词，文档没说。另有只追加 DOM 的增量解析器（`streaming-markdown`），代价是早先猜错了改不回来。
- 长列表：高度不定、还在长、要贴底，是虚拟滚动最难的情形。TanStack Virtual 在 2026 年加了为聊天设计的末端锚定。不用虚拟化的轻办法是 `content-visibility: auto` 加占位尺寸。Devin 重写聊天渲染：先用骨架占位、可见区周围按需加载、以最顶上可见的一项为锚。
- dsh 的浏览器评测：240 轮的会话，120 个增量、每 16 毫秒一个；按动画帧采样；计时止于两帧之后；用 DevTools 协议读主线程任务时间与堆；3 个全新的浏览器取中位数。

**内存**

- 实验室里：DevTools 协议的 `Performance.getMetrics`（含 DOM 节点数、堆），先强制回收再读。桌面上另有 `app.getAppMetrics()` 读每个进程的内存。
- 泄漏：同一个场景重复几次，看强制回收之后还涨不涨。现成的工具有 MemLab、fuite。

**客户端的缓存**

- 通行的模型：先显示缓存，后台校对；只取可见的一段；从新往旧翻页；保留的页数有上限。
- Notion 把 SQLite 放进浏览器：导航快约两成，但慢盘上读盘比网络还慢，改成让两者竞速；多个标签同时写曾造成数据损坏。教训：中位数会掩盖尾部的退化；缓存不一定比重取快。
- 本机的服务就在回环上，重取本来就快，所以客户端缓存的收益主要在少算、少渲，不在少传（推）。

**事件流**

- HTTP/1.1 下一个源最多六条连接，几条 SSE 会占掉大半。对策是一条流上多路复用。
- `EventSource` 没有背压的接口。慢的消费者怎样处理（丢、合并）要协议自己定。

**怎样在实验室里可重复地量**

- 驱动：DevTools 协议（`Performance.getMetrics`、`Tracing`、CPU 降速）。Playwright 对 Electron 的支持标着实验性。
- 降噪：窗口必须可见（隐藏时计时器与动画被节流）；固定视口；不并发跑；每个场景几个全新的进程取中位数。
- 确定的量：DOM 节点数、请求数与连接数、打包字节、重渲的次数、状态提交的次数。有噪声的量：输入延迟、长帧、帧时间、主线程任务时间、启动用时、堆。

**门禁**

- 包体的检查是确定的，可以硬拦（size-limit 一类）。
- 有噪声的先标警告，连续多次变差再升级成拦。

## 五、不跑也能算的：数理与形式化建模

2026-11-16 07:17 UTC，一路只读子代理调研。每条标了证据：**已读**是抓到并读了那一页；**摘要**是只见到搜索结果的概述；**推导**是自己推的，不是文献结论。标「推导」的式子用之前要在我们的体系里再核一遍。

### 1. 谁在这样做

- **TigerBeetle** 是最直接的例子（[TIGER_STYLE](https://raw.githubusercontent.com/tigerbeetle/tigerbeetle/main/docs/TIGER_STYLE.md)，已读）。两条规则：设计时对网络、磁盘、内存、处理器四类资源各写一份带宽与延迟的估算，「最好的一千倍收益在设计阶段拿」；所有循环和队列都有固定的上界。
- **存储引擎的代价模型**是成熟的一支。
  - RUM 猜想（Athanassoulis 等，EDBT 2016）：读、更新、内存三种开销不能同时最小。是猜想，没有证明。
  - LSM 的 Monkey 与 Dostoevsky（SIGMOD 2017、2018）用闭式公式写出更新、点查、范围查的代价，再据此调参（摘要）。
  - Sprite LFS 的清理写代价是 2/(1−u)，u 是被清理段的利用率（公式取自讲义，没核原文）。
  - SQLite 的 WAL 有可算的规律（[官方页](https://www.sqlite.org/wal.html)，已读）：写只追加、只写一次；缺省 1000 页自动检查点；读的代价随 WAL 变大而变差；`synchronous=NORMAL` 时只有检查点才 fsync；有读者长期在读时检查点完不成，WAL 无界增长。
- **排队与可伸缩性。** Gunther 的 USL（[arXiv 1105.4301](https://ar5iv.arxiv.org/html/1105.4301)，已读）：C(N) = N / (1 + α(N−1) + βN(N−1))，α 是争用，β 是一致性代价，峰值在 √((1−α)/β)，过了峰值吞吐倒退。作者建议至少六个负载点来拟合。M/M/1、Little 定律、Amdahl 定律是教科书结论。
- **用模型检查器核计数的界。** 「一次调用至多提交 k 次」「队列不超过 B」「重试有界」写成状态不变式是 TLC 的本职。限定：只对模型里取的有限参数成立。TLC 的 `-generate` 模式能做粗略的统计（Vanlightly 2024，已读），但 TLA+ 没有浮点、只有均匀分布；只要统计、不要正确性时，写一段模拟更简单。
- **性能契约。** Bolt（NSDI 2019）：契约写出性能怎样依赖几个关键变量，预测的指令数与访存数比实测多不超过 7%（摘要）。Smith 与 Williams 的软件性能工程（2001）：设计时用简单模型预测，随开发细化。
- **静态推代价。** Infer Cost（[官方文档](https://fbinfer.com/docs/checker-cost)，已读）估最坏执行代价的上界，有新旧版本的差分报告。**不支持 JavaScript 与 TypeScript。** RAML 面向 OCaml 一类语言。对我们只能借思想。
- **经验复杂度。** trend-prof（ESEC/FSE 2007）与 Google Benchmark 的 `Complexity()`：在几个量级的规模上跑，用最小二乘拟合出阶（摘要）。这是「量」的一种，但量的是阶，不是时间。

工业上没找到的：前端渲染代价的成文模型；流式协议增量与全量的成文分析；事件溯源快照间隔的成文推导。AWS 用 TLA+ 的公开文章讲的是「有了模型检查才敢做激进的优化」，管的是正确性，没有「算出性能界」的内容。

### 2. 算和量怎样配合

- Gunther：模型设定预期，迫使你解释每一个偏差；下一轮测量是最终的裁判。
- 处置的次序（综合推导）：模型给期望；测量检验实现落不落在界内，并读出常数；实测出界时先查测量本身，再查实现，最后才改模型；测量稳定地出界、测量问题已排除，才修模型并记下来。

### 3. 局限

- **外推会错。** USL 论文里的一个案例：头一批数据外推出峰值约一万二千用户，实测约两千，原因是头一批数据里看不到后来才出现的限制。超出取样范围的结论只能当假设。
- **理想化会错。** 开环与闭环的负载行为差得很远（Schroeder 等，NSDI 2006，摘要）；闭环的压测器会漏掉最慢的样本（协调遗漏）。
- **常数会压过阶。** LangChain 的文档说 5 KB 的消息解析不到 5 毫秒，通常先限流渲染就够。阶说明会不会退化，常数决定要不要处理。
- **划线**（推导）：能算的是计数与阶，由结构决定，与机器无关。要量的是常数与分布：单次操作多久、尾部延迟、垃圾回收与调度、真实设备的 fsync、缓存的实际命中。模型的输入可以是量出来的常数，输出是计数的界与阶。

### 4. 现成可用的公式

都是推导，除非另注。

- **快照间隔。** 事件到达率 λ，一条事件的折叠代价 f，写一次快照的代价 C，每单位时间的载入次数 ρ，每 s 条事件一个快照。单位时间的代价是 λC/s + ρ·(s/2)·f，最优 s* = √(2λC/(ρf))。形式与 Young（1974）、Daly（2006）的最优检查点间隔同构，只是「故障」换成了「载入」。比最优更好检验的是硬界：要求载入用时不超过 R，则 s ≤ R/f。
- **整理的摊还。** 每次全量重写的代价是存活数据 L，两次整理之间新增 G，摊还的写放大是 1 + L/G。
- **流式界面。** 每帧重渲整条消息，第 k 帧的代价与 k 成正比，总计与长度的平方成正比；增量的总字节与长度成正比。虚拟滚动把 DOM 节点从与消息数成正比降到与视口成正比。Markdown 的解析器大多不能续喂，缓解的办法是只重解析最后一个没闭合的块。
- **上下文的费用。** 每轮重发全部历史，第 k 轮的输入是 S + k·d，N 轮合计 N·S + d·N(N+1)/2。前缀缓存不改变这个阶，只把读取那一项的常数从 1 降到约 0.1；真正省下的是预填的计算量。
- **前缀缓存的条件**（[Anthropic 文档](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)，已读；OpenAI 的类似）：前缀按工具、系统提示、消息的次序逐字相同，上游任何一处改动使其后全部失效；有最短可缓存长度；缺省存活 5 分钟，命中续期，另有 1 小时的选项；写入约 1.25 倍，读取约 0.1 倍。由此实现必须守：上下文只追加；工具与系统提示不半路变；序列化确定；两次请求的间隔不超过存活期（一个工具跑过 5 分钟就过期）；压缩会使前缀失效。
- **压缩的触发点。** 一个压缩周期 k 轮，每轮读取的单价 r，每轮增量 d，压缩一次的代价 C：平均每轮的代价里随 k 变的是 r·d·k/2 + C/k，最优 k* = √(2C/(r·d))。实际上质量的上限先于成本：上下文越长召回越差（[Anthropic 的文章](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)，已读）。触发点由质量上限、成本最优、缓存失效的代价三者一起定。
