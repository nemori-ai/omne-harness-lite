##### E.5.2 目标

为 Session 日志子系统建一套可复跑、能比较前后、能看出是否随规模增长、并且能阻断退化的评测：

- 给波 3 的快照拆分、增量折叠、常驻缓存提供改前与改后证据；
- 此后作为热路径 PR 的门禁。

两条用户定的不变式，评测要守住：

1. 活跃会话常驻内存，读路径用日志头核对再增量折叠。
2. 日志只追加，落盘后不可变。

按这两条，每次提交和每次读的代价只应与新增条目有关。

##### E.5.3 dsh 做了什么，我们借鉴什么

**dsh 的事实**（路径相对 `8bd073392`）：

- 没有单独叫「session log benchmark」的套件。性能评测在顶层 `benchmarks/`，按被测用户路径分目录。和 Session 存储相关的有三个：`session-open`（打开一个 127,400 事件的大会话）、`session-corpus`（3,000 个会话的列表，1,000 个会话的搜索和 fork）、`agent-continuation`（800 轮历史上的续接）。
- 是 PR 的必过门禁：Linux 独占托管 runner 上的必需 job，判毫秒和内存预算的中位数（`.github/workflows/ci.yml`），另出自包含 HTML 报告。
- 数据全部合成。语料长度分布只取了本机 1,650 个会话的聚合分位数（`benchmarks/session-corpus/corpus-shape.ts`）。
- 基线就是源码常量。预算 = 实测中位数 × 机型系数 × 余量（`benchmarks/support/calibration.ts`：机型系数 `CI_TIME_SCALE`=2，余量 `PERFORMANCE_BUDGET_HEADROOM`=1.25）。不能用环境变量覆盖；放宽预算必须带新的对照数据。
- 防止评测本身失效：每个样本一个全新子进程；被测代码必须是构建产物；负载先过「达到目标规模」的断言；存储布局一变评测就失败；判定常量自带正负对照单测。
- 起因：格式升级让首次打开从约 35 ms 退化到约 5 s，合入时没人发现。
- dsh 的日志记录流式 delta，我们的日志不记 Model 的流片段（`packages/session/session-contract/docs/object-model/session-log-events.md`），所以对应时按轮数与内容字节对齐，不按事件数对齐。

**dsh 没有而我们要守的**：每轮开销不随历史增长。dsh 没有单次 append 的微基准、逐轮增长曲线、fsync 计数、多写者并发、日志尺寸预算。所以我们的门分三类：结构门、规模门、绝对时间门。

**借鉴 / 不借鉴**：

| 借鉴 | 不借鉴 |
| --- | --- |
| 计时门禁：预算 = 实测中位数 × 机型系数 × 余量，每道门有正负对照（R2-D138 Q1） | 多机型换算报告（PassMark 单核分、磁盘延迟模型）：基线按配置标识分文件，换算模型本身是估计 |
| dsh 的规模方案（127,400 事件、200 轮、22 个分位锚点、3,000 个会话、800 轮历史等）逐项对应到 S1～S10（Q6） | cgroup 内存上限重跑：改用受限 V8 堆的「能跑完」检查 |
| 重新实现 dsh 的语料定义，并读取它的会话快照夹具（Q7） | 浏览器场景 |
| 确定性合成负载带 `definitionId`；全新子进程；跑构建产物；负载有效性断言；两次 GC 后取内存；两规模配对比值；按长度分层取样；离线 HTML | E9 的 1.5 中位数比：只沿用 R2-D17 的增长判定（Q8） |

##### E.5.6 三类门与门清单

| 类别 | 判什么 | 是否随环境变 | 运行要求 |
| --- | --- | --- | --- |
| 结构门 | 计数、行数、字节与档位的关系（例如每次提交写入字节与 N 无关） | 不变，确定性 | 任何 Linux 环境，名额按轻活 |
| 规模门 | 两档耗时的配对比值；S8 的 R2-D17 增长判定 | 基本不受机器快慢影响，受噪声影响 | 计时运行 |
| 绝对时间门 | 某端点的中位数 ≤ 预算 | 依赖配置 | 计时运行，必须有本配置的基线 |

内存门（保留堆、峰值 RSS、受限堆能否跑完）和绝对时间门一起运行，不乘机型系数。

选门原则：直接决定用户每轮等待的端点设门；冷打开设门（dsh 的退化正是在冷打开上漏过去的）；并发和尺寸只报告。门清单（候选，B0 冻结）：

| 门 | 场景与端点 | 类别 | 期望值来源 |
| --- | --- | --- | --- |
| T1 | S1 单次提交墙钟，P99 档与 MAX 档 | 绝对 | 标定实测 |
| T2 | S1 配对比值：MAX 档 ÷ P50 档 | 规模 | 理论 O(1)，期望 1.0 |
| T3 | S2 `readWork` 墙钟，MAX 档 | 绝对 | 标定实测 |
| T4 | S2 配对比值：MAX ÷ P50 | 规模 | 理论 O(1)，期望 1.0 |
| T5 | S3 每个样本最慢一页的中位数，240 轮全翻 | 绝对 | 标定实测 |
| T6 | S3 配对比值：L-E ÷ P90 | 规模 | 理论 O(log N + K + B)，期望 `log(N_LE)/log(N_P90)` |
| T7 | S4 两窗口比值 | 规模 | 与页内字节成正比，按实测字节比给期望 |
| T8 | S5 首页历史端到端：十层中位、p99、MAX | 绝对 | 标定实测（冷打开允许线性，所以不设规模门） |
| T9 | S6 外部追加 k 条后的读取：P99 档 ÷ P90 档 | 规模 | 与 N 无关，期望 1.0 |
| T10 | S8 每轮 Session 段墙钟的 R2-D17 增长判定 | 规模 | 判定规则本身，无期望值 |
| T11 | S8 后窗（第 781～800 轮）每轮中位数 | 绝对 | 标定实测 |
| T12 | S8「800 轮历史冷启动再续 20 轮」总时长 | 绝对 | 标定实测 |
| M1 | S7 保留堆增量，L 与 MAX | 内存 | 标定实测 × 余量 |
| M2 | S5、S7 在 128 MB old space 下能跑完 | 内存 | 不需标定 |

只报告不设门：S9 的各项等待、S10 的库与 WAL 字节、CPU 占墙钟比例、p95/p99（门只判中位数）。

结构门（G 系列）在每个场景各自定义，例如：S1 每次提交写入字节与档位无关；S6 外部追加 k 条后从日志读的行数等于 k 加常数；S10 每次提交的 fsync 次数不超过组提交设计值。

S8 的增长判定直接调用 `tools/e9/metrics.mjs` 的 DP2 B，方法标识沿用。S8 用 800 轮：第 41～800 轮分 19 块，每块 40 轮（R2-D17 原为第 11～200 轮每 10 轮一块，块数不变，块长按轮数放大）。

##### E.5.7 门槛公式与标定

```
绝对预算 = ceil( 实测中位数(参照配置) × 机型系数 M × 余量 H )
规模预算 = 期望比值 × H_scale
内存预算 = ceil( 实测值 × H )            （不乘 M）
```

- 实测中位数：参照配置上、标定提交上，3 次独立全量运行。每次运行内 5 个子进程取中位数，再取 3 次里较大的那个中位数。
- 机型系数 M：在本配置的基线上判门时 M = 1。换到没有基线的新配置时，用固定校准探针在两边实测，取墙钟比；这样得出的预算标为「临时」，只能用到本配置的基线入库为止。
- 余量 H：初值 1.25（沿 dsh）。标定时核三次运行之间的中位数差：不超过 10% 用 1.25；超过 10% 按端点放大 H，并把实测离散度写进标定记录。H_scale 初值同样 1.25，按同一规则标定。
- 常量位置：预算写成源码常量，旁边注明实测样本、配置标识、提交 SHA、运行归档名。**不提供环境变量覆盖。**
- 标定记录：套件目录下 `CALIBRATION.md`，每次标定追加一节，写明日期、配置标识、标定提交；每个端点的 3 次中位数与全部样本；得出的预算和 H 的取值理由；正负对照结果。原始归档留在 WSL，`CALIBRATION.md` 只放数值摘要。
- 标定时机：规模门的期望值来自复杂度要求，不依赖实测，可以先上；**绝对门要在快照拆分合入之后的提交上标定**，在拆分前标定会把已知的退化固化成基线。

##### E.5.8 基线文件与配置标识

基线文件 `baselines/<配置标识>.json`，存各端点的中位数、样本离散度、预算、标定提交、`definitionId`，以及完整的配置字段。配置标识由机器配置算出，不用机器名（Q4）。

进入摘要的字段（任一项变了，摘要就变，判为不可比）：

| 字段 | 取法（在 WSL 内） | 规范化 |
| --- | --- | --- |
| `cpu.model` | `/proc/cpuinfo` 第一个 `model name` | 去掉 `(R)`、`(TM)`、`CPU @ …GHz` 后缀；连续空白合为一个；小写 |
| `cpu.logical` | `os.availableParallelism()` | 整数 |
| `mem.totalGiB` | `/proc/meminfo` 的 `MemTotal` | 向下取整到 GiB |
| `mem.swapGiB` | `/proc/meminfo` 的 `SwapTotal` | 向下取整到 GiB |
| `os.id`、`os.version` | `/etc/os-release` 的 `ID`、`VERSION_ID` | 原样 |
| `kernel.release` | `uname -r` | 原样，小写 |
| `virt` | 内核串含 `microsoft-standard-WSL2` 时为 `wsl2`，否则 `none` | 枚举 |
| `node.version` | `process.version` | 原样 |
| `sqlite.version` | 经 `node:sqlite` 执行 `select sqlite_version()` | 原样 |
| `fs.type` | `findmnt -no FSTYPE -T <评测根>` | 小写 |
| `fs.options` | `findmnt -no OPTIONS -T <评测根>` 中与持久化相关的项（`data=`、`barrier`、`commit=`、`sync`） | 只保留这几项，排序 |
| `storage.class` | WSL 内只看得到虚拟盘（`lsblk` 显示 `Virtual Disk`、`ROTA=1`，不可信），所以从 Windows 侧取发行版所在盘的物理盘 `BusType` 与 `MediaType` | 例如 `vhdx/nvme-ssd`；裸机 Linux 为 `<bus>-<media>` |
| `bench.harness` | 设施的主版本号 | 原样 |

摘要算法：

1. 把字段按键名排序，组成规范 JSON：只含字符串和整数，无空白。
2. 取 SHA-256 的前 12 位十六进制，前缀 `cfg-`，例如 `cfg-3f9a0c1d2e4b`。
3. 文件名即 `baselines/cfg-3f9a0c1d2e4b.json`。

只记录、不进摘要的字段：主机名、Windows 版本号、物理盘型号、CPU 微码；WSL 版本串、`.wslconfig` 原文；开跑与结束时的负载、电源计划、Defender 状态（Q9：不改本机设置，只记录）。这些变了仍然可比，报告里列出差异。

不可比的情形：配置摘要不同；`definitionId` 不同；设施主版本不同；被测会话格式的迁移版本不同。不可比时绝对门判 `blocked: no-baseline`，不判通过；规模门和结构门照常判。

波 2 设计时的原机器配置是 24 逻辑核的混合核心 CPU、约 47 GiB 内存、Ubuntu 24.04、WSL2、Node 26、ext4 根。**接手机器的配置很可能不同，需要重建基线。** 升级 Node 也要重新标定（`node.version` 进摘要，这是有意的）。

##### E.5.9 正负对照与误报控制

**每道门三层对照**（第一层每次都跑，后两层在标定时跑，结果写进 `CALIBRATION.md`）：

| 层 | 做法 |
| --- | --- |
| 判定单测（快层） | 已记录的标定样本必须判通过；把中位数乘 1.26 的合成样本必须判失败；规模门用「平稳」和「线性增长」两组合成序列，分别判通过和失败 |
| 实测负控（标定时） | 规模门 T2、T4、T9、T10：在快照拆分前的提交上运行必须判失败，拆分后必须判通过；另用场景里的替身读者（每次整份重读）复现一次失败，不改产品代码。绝对门 T1、T3、T5、T8、T11、T12：在被测端点外面套一层固定延迟（例如每次调用多读一次整份快照），中位数超出预算必须判失败 |
| 实测正控（标定时） | 同一标定提交连续 3 次全量运行都判通过 |

内存门 M1 的负控：场景替身额外保留一份整份历史，保留堆必须超预算。M2 的负控：把受限堆降到明显不够的值，必须报告「堆耗尽」而不是超时。

**噪声控制**：

1. 只判中位数：冷场景 5 个子进程；热场景每进程预热 20 次、计时 200 次，取每进程 p50，再取 5 个进程的中位数。
2. 配对交替：热路径 PR 的「合入前」与「合入后」两个提交按 ABABAB 交替起子进程。除绝对门外，再加相对门：`后 ÷ 前` 的配对比值 ≤ H。
3. 噪声探针：每次运行开头和结尾各跑一次固定校准探针（固定次数地对临时库做「提交一条 + fsync」，再做固定次数的 JSON 编解码）。两次探针的中位数差超过 10%，或探针中位数偏离基线探针超过 15%，本次运行标为 `noisy`。
4. 不对称判定：`noisy` 运行里的门失败改判为 `blocked: noisy`，必须在独占窗口重跑，不能算失败也不能算通过；`noisy` 运行里的门通过照常算通过（噪声只会让结果变慢）。
5. 失败复核：非 `noisy` 运行里某道计时门失败时，自动只重跑该场景一次，两次都失败才判失败，两次数值都记录。
6. 结构门不受以上规则影响。

**门禁失败后的流程**（R2-D138 Q2：不进准入，在套件自己的运行里生效）：

1. 触发：改到 Session 日志热路径的 PR，在合入前后各跑一次（合入前 = PR 的基点，合入后 = PR 的头，按交替方式运行），两份 `summary.json` 附在交付说明里。热路径默认指 `packages/session/session-storage-sql`、`packages/session/session`、`packages/session/session-adapters` 的 Journal 读写、`packages/storage/sqlite-provider`、`packages/storage/sql-contract`。
2. 判定：任一门判 `fail` 就阻断这个 PR；判 `blocked`（包括 `noisy`、`no-baseline`、缺测）也不能合入，要在独占窗口重跑，或者先为本配置建基线；不能把 `blocked` 写成通过。
3. 定位：在 WSL 里单独重跑失败的场景，看分段数值和 CPU 占比，必要时做剖析。
4. 处置，三种结果：(a) 修代码，重跑到通过；(b) 这是已获批的架构代价：由预算的审批人批准新预算，PR 附新的标定数据和正负对照，写进 `CALIBRATION.md`，没有新对照数据不能放宽预算；(c) 是门本身的缺陷（误报或测错了）：修门，同样附对照数据。
5. 波末：Reduce 在独占窗口跑一次全量，结果进状态页。规模门失败要开问题处理；绝对门失败按第 4 步走。

**预算审批人**：这一点设计稿仍待用户确认。默认做法：Reduce 凭新的标定数据和正负对照批准；绝对预算放宽超过 25%、或任何规模门的放宽，交 qiwei.pan 批准。

##### E.5.10 在 WSL 上跑、systemd 托管、名额规则

**只在 Linux 测**（Q5）：计时和 fsync 都在 WSL 2 的 `Ubuntu-24.04` 上测。Windows 原生（NTFS、Defender、Windows 上的 `node:sqlite`）完全不测，报告里要写明「Windows 原生未测」（风险 R2）。

**执行环境**：

- 经 `wsl.exe -d Ubuntu-24.04 --exec bash -l` 调用。
- 在 WSL 自己的文件系统里从 GitHub 克隆，不加 `--reference`，不经 `/mnt/` 做 git、安装或构建。被测提交先推到远端再 fetch。
- 每个被测提交用 WSL 内的 `git worktree` 放在 `~/bench/trees/<sha>/`，由 WSL 的 Git 创建和移除；每棵树单独 `pnpm install --frozen-lockfile` 并构建，`node_modules` 只属于 Linux。依赖执行位时先跑 `git fix-modes`（NTFS 上写过的文件在 WSL 里显示为 744）。
- Node 版本要满足 `engines.node >= 24`。
- 需要先在 WSL 安装 `strace`（原机器上没装；`sudo apt install strace`，属于 B0）。

**长跑托管**：

- 全量运行用 WSL 的 systemd 托管：`sudo systemd-run --unit=slb-<时间戳> --uid=<WSL 用户> --gid=<WSL 用户> --collect /bin/bash -l <脚本>`。原因：`wsl.exe` 调用结束时，WSL 会杀掉它启动的后台进程，`nohup … & disown` 也保不住；只有 systemd 单元在调用它的会话结束后仍然继续运行。
- 结果写进 `~/bench/runs/<时间戳>/`：原始样本 JSONL、`summary.json`、`report.html`、`processes.json`、环境与配置字段。运行结束写一个完成标记文件。会话里只挂读这个本地文件的检查，不轮询模型。用 `systemctl status slb-<时间戳>` 查状态。
- 全量运行控制在 60 分钟内（风险 R4）。后台任务上限 2 小时。

**Windows 侧启动器**（Git Bash）：

1. 用 `scripts/with-test-slot.mjs` 取独占名额 `OMNE_TEST_SLOTS=1`。名额目录用同一组共同目录，这样才能和其他写者排队（R2-D19）。
2. 记录 Windows 主机的 CPU 负载。WSL 和主机共用 CPU，主机上别的负载在 WSL 内看不见。
3. 启动 systemd 单元，等完成标记出现。
4. 把 `summary.json` 和 `report.html` 复制出来供状态页展示。
5. 释放名额。

**名额规则**：

- 计时运行期间全机独占（R2-D116、R2-D118 补充），其他写者连轻活也停。
- 只跑结构门的运行可以按轻活设 `OMNE_TEST_SLOTS=2`。
- 主机侧：启动器开跑时主机 CPU 占用超过阈值（初值 10%），整次运行标为 `noisy`。
- WSL 内：开跑前确认没有别的 `slb-*` 单元在运行；记录 `/proc/loadavg`；计时场景一次一个进程，串行。

**fsync 计数**（S10）：用 `strace -f -e trace=fsync,fdatasync,sync_file_range -o <文件>` 附在被测 worker 进程上。每次提交前后各写一个标记：worker 向一个专用描述符写一字节，strace 会记下这次 `write`，按标记切分得到每次提交的 fsync 次数。strace 会扰动计时，所以 fsync 场景单独运行，不和计时样本混在一起。fsync 计数是确定性的，作结构门。产物同时满足 E9 `fsync-count` 事件的 `source: 'strace'`，可供联调 B 复用。

**冷与热**：冷场景是新进程冷，不清文件系统缓存（同 dsh）；可选变体经 `sudo` 写 `/proc/sys/vm/drop_caches` 清 WSL 内缓存，只报告不设门。混合核心 CPU 上 WSL 的虚拟 CPU 由 Windows 调度到哪种核，WSL 内无法固定，靠中位数、配对交替和噪声探针吸收（风险 R1）。
