# 桌面界面的现状：盘点

2026-11-16，只读盘点，读的是集成轨道头 `7bdc40352`。由一路只读子代理读源码；标「统筹核过」的几条我自己又在源码里对了一遍。**没有跑过任何东西，没有读数。** 最后一节的「风险」都是读代码推出来的。路径相对仓库根。

## 1. 架构

- 三个角色。Electron 主进程（`apps/desktop/src/electron-host/main.ts`）里跑宿主核心（`main-core/login-session.ts`），独占登录证明，只在内存。渲染进程是沙箱页面，里面是一棵 Cordis 客户端树。本机宿主是同一个核心的 HTTP 版（`web-host/server.ts`）。
- 页面装树：`main.tsx` 依次连接宿主的桥、起客户端树、装外壳、装四个界面模块（身份、会话、人工介入、资产），最后渲染。协议客户端在可用性观察答出该协议之后才出现。
- 一次调用经过：页面的协议客户端 → 连接性的看守 → 桥 → `ipcRenderer.invoke` → 主进程的 `ipc-host` → 宿主核心（按契约核对目标、带上凭据）→ HTTP 传输 `POST /api/<协议>/v<版本>/<名>` → 服务端入口。
- 一条观察流经过：服务端 SSE → 主进程解析 → 主进程逐帧 `page.send` → 预加载脚本按编号分发 → 页面的事件队列（无界数组）→ 解码 → 会话界面的驱动器。
- **每一帧在 Electron 路径上：字符串化两次、解析两次。** 服务端写成 SSE；主进程解析；主进程再字符串化发给页面；页面再解析、过编解码校验、再转成普通对象。解析器是手写的 JavaScript 扫描器（`packages/common/json-text/src/read.ts`），不是 `JSON.parse`。

## 2. 启动

- 主进程：开沙箱、打开登录会话、等 `app.whenReady()`、注册自定义协议、开窗口并加载页面。**没有 `show: false`、`ready-to-show`、`backgroundColor`**（统筹核过：`apps/desktop/src` 里搜不到）。窗口一创建就显示。
- 页面：一个模块入口。首次渲染之前要等桥拿到第一个登录状态、树装完。
- 登录门要等身份协议的客户端出现，也就是等可用性观察的第一帧；之前显示「正在连接服务……」。
- 登录之后外壳把所有页面同时挂载、用 `hidden` 藏起来（`shell.tsx`）。对话页、「待你决定」页、设置页同时发请求：查当前租户、列会话（50 条）、列卡（上限 100）、观察卡（常驻）、读设置列表。
- **没有延迟加载，没有代码分割**（统筹核过：源码里搜不到动态导入、`lazy`、`manualChunks`）。`assembly.tsx` 静态导入全部模块；共用界面件的 `code-highlight.ts` 静态导入代码高亮、中日韩、数学、流程图四个插件。

## 3. 打包

- `apps/desktop/vite.config.ts` 共 15 行：没有手动分块、没有目标、没有压缩与源码映射的配置，用缺省。
- 检出里没有构建产物，产物多大没有量。
- 依赖里体积大的（只读到版本，没有量体积）：react 19.3、streamdown 2.7（带 marked、remark、rehype 一家）、代码高亮（shiki 3.23）、流程图（mermaid 11.17）、数学（katex 0.16）、radix-ui、tailwindcss 4.3。
- 字体：`packages/frontend/ui-kit/resources/fonts/` 共 9.7 MB（统筹核过）。霞鹜文楷切成 194 片（97 个字符范围乘常规与粗体），共约 9.25 MB，单片约 64 KB；Inter 350 KB；JetBrains Mono 72 KB。`wenkai.css` 有 194 条 `@font-face`，都是 `font-display: block`（统筹核过）。按用到的字符范围懒取。

## 4. 流式渲染

**服务端的粒度**

- 模型输出在服务端合并过：本机的缺省是每 100 毫秒或每 16 KiB 一批（`apps/harness-server/src/local/operator-defaults.ts:102-103`，统筹核过）。所以大约每 100 毫秒一帧。
- 观察这一层不再合并：每个流事件产出一个内容帧（有时前面带一个状态帧），SSE 一帧一次写。
- 慢的消费者：观察者的队列到 256 帧或 8 MiB 时发一个「缺口」帧，客户端要整段重新观察。

**帧里带的是什么**

- 内容帧带的是「变了的块」的完整块。还在增长的块，它的值是**到目前为止的全文**，不是增量（`model-contract` 的 `changedStreamBlocks`；客户端 `applyDelta` 按下标整块替换）。
- 所以一条长的回复，每帧的字节数随回复的长度线性增长。

**客户端收到一帧之后**

- 驱动器每帧派发一次，状态机产出新的整份状态（不可变，对象展开），同步通知全部监听者。
- **没有按动画帧合并，没有节流**（统筹核过：`session-ui` 里搜不到 `requestAnimationFrame`、`startTransition`、`useDeferredValue`）。
- 组件订阅的是整份工作区：`useSyncExternalStore(driver.subscribe, driver.getState)`（`conversation-page.tsx:57`，统筹核过；会话列表面板订的是同一个）。一帧让页面、正文、会话、对话、输入框都重渲。
- 已提交的消息有 `memo` 而且一帧里条目不变，所以它们不重渲。正在生成的那条消息每帧用全文重渲。
- 状态帧的修订号超过已读到的位置时，还会触发一次历史重读。

**正文怎样渲染**

- Markdown 用 streamdown（`ui-kit/src/prose/prose.tsx`），流式模式，代码高亮、数学、流程图、中日韩四个插件常开。每帧把整条文本交给它。它内部按不按块缓存解析，没读到（依赖没装）。
- 工具参数、推理、工具结果都走同一条路径。

**贴底**

- `useFollowBottom`：靠滚动事件判断离底部是否在 32 像素之内；每次变化之后在布局阶段把 `scrollTop` 设成 `scrollHeight`，每帧一次强制布局。`ResizeObserver` 只观察滚动容器自己，内容自己长高（字体换上、折叠展开、图表渲染出来）不触发。

## 5. 长会话

- 会话列表：游标分页，服务端缺省与上限都是 50，「更多」按钮追加。每次一轮结束或输入被受理都重取第一页，第一页会覆盖已经追加的页。
- 历史：第一次从新往旧读，每页 64 KiB，之后用游标。**打开会话时内容是空的，判断「读到了已知的条目」的函数在空内容上恒为假，所以会一页一页串行读到历史耗尽**（`session-machine.ts` 的 `historyPage`、`content.ts` 的 `reachesKnown`，统筹核过）。
- 每来一页：合并（建表、全量排序、每条转成普通对象）、全量重算对话的条目、全部渲染。
- **没有虚拟滚动，没有 `content-visibility`**（统筹核过）。DOM 节点数随消息数线性增长。
- 服务端每次打开观察要回扫历史来定位当前的一轮：每页 64 KiB，最多 4 页。

## 6. 缓存

- 没有任何持久的缓存。`localStorage` 只存主题。没有 IndexedDB。HTTP 全部 `no-store`，页面的静态文件也是 `no-store`，Electron 每次整文件读进内存。
- 内存里：一个驱动器同时只持有一个会话。**切走再切回，内容清空，重新观察并重读全部历史**（`session-machine.ts` 的 `opened`，统筹核过）；会话组件以会话编号为 `key`，整棵重挂。没有每会话的缓存，没有失效规则，没有上限。
- 设置、待决的卡、租户：各自的驱动器随页面挂载建立；页面只是藏起来不卸载，所以切页面不重取。
- 产品正文只有一句：应用可以缓存显示用的内容，但不把缓存当成结果。

## 7. 工具输出与大内容

- 工具卡的折叠只用样式（行高为零、透明、`inert`），折叠着的内容始终挂载。
- 工具参数递归渲染成嵌套的列表，没有深度与数量的上限。生成中的原始参数是一整个 `<pre>`，不截断。工具结果的文字走 Markdown（带代码高亮）。
- 没有截断，没有「折叠时不渲染」，没有「显示更多」。

## 8. 内存

- 观察的订阅在切换与卸载时会退，没看到泄漏的路径。
- 随时间增长的：会话的全部条目（每次重读一页都重新分配这一页的全部对象）；页面的事件队列与主进程到渲染进程的 IPC 都没有背压；服务端观察的收件箱无界。

## 9. 现有的性能相关的东西

- **没有任何计时点**：搜不到 `performance.mark`、`PerformanceObserver`。没有性能用例。没有包体的检查。
- 规格与产品正文里没有性能数字。未决清单的 `JR-012` 里提到「首屏预算」，没有数。
- 架构正文的通则（`docs/architecture/assurance.md`）：没有阈值时只报实测与趋势，不能据此宣布达标；性能结论要带基线、条件、重复次数、噪声；阈值由目标的拥有者定。

## 11. 从代码上看最可能的性能风险

读代码推出来的，没有量过。按轻重排。

1. **每帧全文，每帧过四遍整文本处理。** 帧带着增长中的块的全文；主进程解析再字符串化，页面再解析、校验、转对象；解析器是手写的。长回复要处理的总字节随长度平方增长，而且在主线程上。
2. **每帧全量重渲。** 订阅的是整份工作区，输入框、页面、对话都跟着重渲；正在生成的消息每帧把全文交给 Markdown（带高亮、数学、流程图）；没有按帧合并。
3. **打开长会话的代价与历史的长度成正比。** 读到历史耗尽；每页全量排序、全量重算；全部渲染；没有虚拟化。
4. **切会话没有缓存。** 清空、重读全部历史、整棵重挂。
5. **状态帧触发的历史重读**把那几页的旧条目全部换成新对象，已提交消息的 `memo` 失效，对话条目整体重算。
6. **包体与首屏。** 全部静态导入，带着高亮、流程图、数学、radix，不分块；中文字体 `font-display: block`，字体取回之前文字不显示；窗口一创建就显示，没有背景色，空白期看得见。
7. **贴底每帧强制布局**；内容自己长高不会重新贴底。
8. **折叠着的内容也挂载，工具输出不截断。** 大的工具输出拖慢整页，并且参与每帧的重算。
9. **登录后三个页面同时挂载、同时发请求**，观察卡常驻。走本机宿主（HTTP/1.1）时，登录态、可用性、待决的卡、会话共四条长连接，占掉浏览器同源六条连接的大半。Electron 的 IPC 路径没有这个问题。
10. **队列无界、没有背压。** 渲染慢时帧在页面的队列、IPC、服务端的收件箱里积压；服务端只在 256 帧或 8 MiB 时发「缺口」让客户端整段重取。
