## 表 1　义务 = f(日志)：`check(ref)` 读到的快照 → 这一次做哪一步

义务只是日志的函数（I-2）。进程内的 `known`（交过哪些输入）只能让推进器少做一次幂等的重交，丢了也不少做一步：重启后按原操作身份重交，Agent 认回原受理。

| 快照 | 今天 | 应然 | 差异 |
| --- | --- | --- | --- |
| 已归档 | `judgeRunStart` 答 archived，什么都不做 | 同今天：没有义务 | 无 |
| 冻结、无活跃 Run | 返回 | 同今天：冻结的处置归冻结流程 | 无 |
| 活跃 Run，execution 还没创建，或首批既不在 `known` 也没被取走（`grantedNotInvoked`） | `replay`：同一身份重放 `start` 再 `invoke` | 同今天 | 无 |
| 活跃 Run，有没交过的待处理输入（`waitingInputs`） | `handIn` 逐条 `submit` | 同今天 | 无 |
| 活跃 Run，首批已交或已取走，无待交输入 | 交恢复：问挂接（表 3） | 同今天 | 无 |
| 无活跃 Run，有可叫醒的待处理输入，可开 | `openRun` 只带首条输入（R6）；其余在 `invoke` 之后逐条 `submit`，下一步才被取走 | `openRun` 带当时全部可叫醒的普通输入作为一批（I-4，F1）；批由开始 Run 的提交写进日志，重放读日志里的那一批 | **未做**（F1） |

| Run 已是取消终态，Agent 一侧的 execution 没终结 | Session 不管；第 1 程起它不再占执行槽，新一轮照常受理 | execution 以取消收束为终结（Agent 的事，表 4） | **未做**：execution 在执行记录里一直开着，没有已知的用户可见后果 |
| 两个未终结 Run | 不可达 | 不可达：I-5，`judgeRunStart` 在活跃时答 run-active | 无 |

## 表 2　一次出站的结局 → 处置

今天每一步各写一套：`invoke`、`submit`、`openRun` 对可重试失败按 `retryDelaysMs = [1s, 5s, 30s]` 重试，用完 `report('retries-exhausted')` 后返回，这次叫醒用掉，义务由周期扫描（约 30 秒）重新现算。`handOver` 在发行装配里每次都答 `unavailable`（E1），只报一条诊断；它不挡任何一步，因为待处理资格在取走时解除，收尾不看交入事实。

应然只有一张表，四步共用。处置只有五种：

- **成**：义务这一步完成，接着现算下一步。
- **定**：有确定答复（拒绝、被取代、终态），按答复收场或交恢复，记诊断。
- **认回**：结局未知，按原操作身份查询（`settled` / `resolution.watch`），不重发新的。
- **延后**：一时做不成。叫醒保留，按退避等一档后**重新从日志现算**（回到表 1），次数不设上限；等待间隔有下限、逐档加长、有上限（I-8）。每一次延后记一条「暂停」诊断（SE-8 改为暂停语义），同一原因按指数节流。
- **退出**：日志说这一步已不再需要（`stillAdvancing` / `stillRunning` 为假），或进程关闭。

| 结局 ＼ 步 | openRun（startRun 提交） | invoke | submit | handOver（receive 事实） |
| --- | --- | --- | --- | --- |
| ok | 成 → invoke | 成 → 记 `known`，handOver(首批) | 成 → 记 `known`，handOver | 成（发行装配里不可达：没有证据来源） |
| invalid（准入拒收，带证据） | 不可达：提交不经准入 | 定：有界收束为失败（closeRefused） | 定：记 rejected 事实（handOver） | 不可达：事实提交不经准入 |
| refused（驱动拒绝） | 不可达 | 定：有界收束为失败 | 定：今天落进「非可重试 → 报诊断返回」；应然同 invalid 的处理，记 rejected 事实 | 不可达 |
| denied（授权） | 定：报诊断 | 定：报诊断（advance.ts:493-507）；授权改变后由扫描再现算 | 定：同 invoke | 定：报诊断 |
| terminal | 不可达：开新轮前判过 | 退出（这一轮已终结） | 退出 | 退出：认回已终态 |
| stale-advance / advance-withdrawn | 定：交恢复 | 定：交恢复（`recover(ref)`） | 退出：执行已不是当前的 | 退出 |
| conflict（来源核对不成立） | 定：交恢复 | 定：交恢复 | 定：交恢复 | 定：交恢复 |
| busy | 不可达 | **延后**（推进位还被占：表 4 的让位是它终会结束的依据） | **延后** | 不可达 |
| unavailable（依赖一时不可用，含「解释还没跟上」） | **延后** | **延后** | **延后** | **定**：发行装配里这是确定的答复，不重试，记一条诊断即止。证据来源接上之后（#1195、#1197 的 G8）才区分一时与确定 |
| changed（修订已变） | **延后**：再读、再判、再提交 | 不可达：drive 不比修订 | 不可达 | 延后：再读再提交 |
| commit-unknown | 认回（`unknownTo`） | 认回（`settled`），认不回则延后 | 认回，认不回则延后 | 认回（`resolution.watch`） |
| frozen | 定：冻结流程（`freeze`） | 不可达 | 不可达 | 不可达 |
| unsupported | 定：报诊断 | 定：报诊断 | 定：报诊断 | 定：报诊断 |
| 驱动口不在（`drive()` 为空，agent-absent） | 不可达 | **延后**：今天直接 return（advance.ts:451） | **延后**：今天 return false | 不可达 |
| 进程关闭 | 退出 | 退出 | 退出 | 退出：`known` 随进程丢；重启后按原操作身份重交，Agent 认回原受理 |

「延后」的寿命：它只活在进程里。进程重启，延后丢失，启动恢复与周期扫描按表 1 现算出同一个义务（模型的 `Restart` 动作覆盖这一点）。所以延后可以是内存里的计时器，但**每一种「延后」都必须保证有下一次叫醒**：要么计时器，要么扫描。今天的实然是「有界重试用完，交给扫描」，模型 `bad-no-scan` 显示去掉扫描就卡死。把有界重试改成不设上限的延后是可选的改进，不是正确性的必需：扫描已经兜住。要守的是间隔有下限（I-8）。

## 表 3　挂接状态 × Session 恢复的处置

`recover.ts` 的 `check`：对活跃、首批已交或已取走的一轮，`inspect` 得到 `ExecutionStatus`，`handsBack` 为真才 detach 并接手。`inspect` 先读执行记录，再问宿主的 `contact`；第 1 程起 `contact` 按运行时自己的报告答（`agent-host-local/src/contact.ts`）。

| Agent 一侧的真实状态 | 第 1 程之前 contact 答 | 今天 contact 答 | Session 处置 | 差异 |
| --- | --- | --- | --- | --- |
| 宿主运行着这个实例，槽被这个 execution 占着 | live | live | 等：Agent 在推 | 无 |
| 宿主运行着这个实例，槽已预留或在排空 | live | live | 等 | 无 |
| 宿主运行着这个实例，槽空着或被别的 execution 占着（驱动停下之后） | live（R4 的后果） | **lost**，证据是宿主自己的（`runtime-released`） | detach → claim → resume | 已做（第 1 程）。整条接手路只读过码，没在发行组合上跑过 |
| 宿主没有运行这个实例，装配有失联证据 | lost | lost | 接手 | 无 |
| 宿主没有运行这个实例，装配没有证据 | unknown | unknown | 不接手，等下一次扫描 | 未做。现场两次重启后都接手成功（`claim` 答 ok），说明发行装配给得出证据；没有逐行核实 |
| 槽被这个 execution 占着，但没有任何在途的推进（修订 1 的 R3「丢了一次叫醒」） | live | live | 等 | **候选，没有现场证据**。当初拿它解释第 2 次卡死，那次归因是错的。不做，除非先复现 |
| execution 已 ended / suspended | 不问 contact | 同左 | ended：叫醒解释；suspended：接手 | 无 |
| 读执行记录失败 | inspect 失败 | 同左 | 这次不做，扫描再来 | 无 |

一处已知的窗口：`inspect` 先读记录、后问 contact，execution 恰好在两者之间正常结束时会答失联。随后的 `detach` 对已结束的 execution 答不可用，`claim` 因修订已变而不成，不改任何状态（读码，没有单独跑）。

## 表 4　执行槽 × 事件

`agent-host-local` 按 `sessionSlotReference(session, adoption)` 给每个会话一个实例；一个实例一个执行槽（`provider.ts` 的 `Slot`：`free`、`reserved`、`running`）。`expire` 只回收报 idle 的实例。

| 槽的状态 ＼ 事件 | 新一轮 invoke | 这一轮被取消 | 驱动在一个节点上确定不能继续 | idle 计时到 | 进程停 |
| --- | --- | --- | --- | --- | --- |
| `free` | 预留、受理、开始推 | 不可达 | 不可达 | 回收实例 | 无事 |
| `reserved` | 答忙 | 受理没完成：按受理的结局走 | 不可达 | 不回收 | 有序停止 |
| `running`，推着当前轮 | 答忙（Session 一时只开一轮，新一轮只会在取消之后来） | 驱动读到取消，以取消收束，execution 终结，槽让出 | **第 1 程起**：报告一次，槽让出，execution 仍未终结。之前：槽一直占着，直到重启 | 不回收 | 有序停止 |

应然里还差的一格：驱动停下之后 execution 在执行记录里一直开着。

- 这一轮在 Session 一侧还活跃时：恢复按表 3 接手。停下的原因会过去的，接手后推完；原因是确定的（现场：收尾提交超过存储的命令上限 `command_limit`），每次接手都再停下一次，这一轮永不收场，人只能取消。模型 `gap-deterministic-halt.cfg` 就是这一格。应然：同一个节点连续停下若干次之后，这一轮以失败终结。由谁数、数在哪、几次，**没有定**。
- 这一轮已被取消时：Session 不再关心它，execution 留在执行记录里不终结。没有已知的用户可见后果；`packages/agent/SPEC.md` 写的是「新挂接读原取消意图以取消授权收束」，没有兑现。

取消的时序竞争（#1404）：取消已提交、取消控制还没写进 Agent 执行记录的窗口里，`E2` 之外的节点撞上 `stale-advance` 会直接停下而不是等取消原因。第 1 程没有改这条路，只是让停下不再占槽。

## 表 5　日志解释一次的结局 → 处置

`journal-interpretation.ts:375-405`：瞬时失败第一次 0 ms 重排，随后 `initialMs` 起按倍数到 `maxMs`，次数不设上限（SPEC 允许）。

| 结局 | 今天 | 应然 |
| --- | --- | --- |
| ok，没有待决事件 | 结束 | 同今天 |
| ok，有事件没有决定后果 | 记一条警告 | 同今天 |
| unavailable：存储或依赖一时不可用 | 重试，次数无上限 | 同今天，但首次也有退避下限，不 0 ms 紧贴（I-8） |
| changed：日志在解释时被并发改动 | 0 ms 重排 | 重排有下限间隔；并发改动本身会发布叫醒，不需要紧贴重试 |
| unavailable：原始材料缺失（`required original material is missing`，R5） | 当瞬时失败，每 5 s 重试，永不收场 | 永久性失败：停止重试，把这一轮按「解释隔离」处理（SPEC：「日志有缺口按隔离处理」），记具名诊断，交人或交恢复 |
| 其余确定失败 | 结束并记警告 | 同今天 |
| 进程停 | 停 | 同今天 |

永久与瞬时的分界由失败的产生者给出，不由解释器猜：存储或 Session 的读答 unavailable 时带上「会不会过去」的分类。这条分类要回到失败产生处去定（第 5 步）。

1. 批的形状（F1）：开始 Run 的提交怎样写下这一批，`invoke` 怎样带它，Agent 的受理怎样一次接走一批，批里有一条被准入拒收时怎样处置。涉及 `AgentDrivePort.invoke` 与 Agent 契约的 `InputEntry`（今天 `initial` 只带一条）。已读到的代码事实与候选做法在 `handoff-card.md`。
2. 停下的 execution 怎样在有界次数内终结（表 4 的缺口）。
3. 永久性失败的分类落在哪个产生者上（表 5）。
4. 取消在 Agent 一侧的收束（#1404）。
