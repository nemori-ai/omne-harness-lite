## 接手 1　这条线是什么

负责人 2026-11-25 在本机的桌面端一天里四次卡死（会话不再往前走，重启服务端才解）。由此立了这条线：把「会话受理、消息消费、推进」做对做好，用偏函数全化、形式化建模与证明、property test 把极端场景盖住，一程一个 PR 进 `integration/mainline`；并把性能设施（`tools/perf-harness`、`benchmarks/`）系统地建起来，根治「会话日志越长每步越慢」。

- 目标与完成判据：`goal.md`（负责人认可的原文）。
- 分程：本卡上面的「各程」表。
- 这条线的交付入口挂在两张修复主题卡下：#1611（会话推进与恢复）、#1612（取消、归档与审批等待）。每程做完，在这两张卡的待修清单上逐项写处置与证据。

## 接手 6　推进链路今天是怎样工作的

这是原会话读码加复现得到的，`formal-handoff.md` 的环境假设表给了每条的证据级别。

- 受理：输入进会话日志，同一次提交里取得待处理资格，提交叫醒推进。
- 推进每次被叫醒都从日志现算做哪一步（`advance.ts` 的 `check`）。没有活跃 Run 且有可叫醒的待处理输入：`openRun`。
- 开轮分两次提交：先提交开始 Run 与首个 attempt（不扣任何输入的待处理资格），再向 Agent `invoke`，**只带首条输入**。其余待处理输入在 `invoke` 成功之后由 `handIn` 逐条 `submit`。
- Agent 每一步开始时按输入水位线取走当时已受理的输入，这一步的开始提交里带上送达，待处理资格在这里解除。
- 交入回执在发行装配里写不上（没有证据来源）。日志里的「已交入」永远是空的，Session 靠进程内的 `known` 不重复 `submit`；重启后重交，Agent 按操作身份认回。
- 收尾：Agent 向 Session 提条件终结。结论是完成或取消时，只要还有待处理、没被推迟的输入就挡回，Agent 回去再走一步取走它。结论是失败时不挡（第 1 程）。
- 一轮最多 50 步（`maxRunSteps`）。到上限以守卫失败收尾。
- 失败的一轮结束后会话停着等人，没取走的输入留在待处理；人的下一句开下一轮。
- 驱动在一个节点上确定不能继续时停下：报告一次，execution 在执行记录里不终结。第 1 程起让出执行槽。
- 周期扫描（约 30 秒，会话有退避）对有待处理输入或活跃 Run 的会话叫醒推进与恢复。恢复问挂接，得到失联就 `detach`、`claim`、`resume`。

量设计的尺子：每一条推进义务都要能从日志现算出来，进程内的状态只许让推进器多做一次幂等的认回，不许让它少做一步；并且有扫描兜底。这和架构里发件箱的道理是同一个（`docs/architecture/data-and-state.md`「正式消息队列」）：欠别人的事和事实同一次提交落盘，对方持久承接了才销账，没销账的定期扫描。输入的交付已经是这个形状，待处理资格就是那条发件箱记录。

## 接手 7　已知的缺口与候选做法

每条都写了证据级别。「候选」是读码推出来的，动手之前先证实。

### 7.1 开轮只带首条输入（F1，R6）：下一程

- 现象（真部署证实）：甲成功，乙因密钥无效失败，恢复密钥后发丙。丙那一轮 2 次模型调用，第一步只回乙，第二步回丙。
- 产品的应然：CAP-SW05「每轮开始时把当时已收到的普通消息一并接走，不漏不拆」。
- 现行规格写的是今天的做法，要改：`packages/session/SPEC.md`「开轮时待处理里有几条输入的，Agent 先取走首条，其余由 Session 随后交入，在下一步被取走并送达」「新 Run 分两次提交……带首条输入」「首条输入被拒收时 Run 以失败收束，其余输入留给下一个 Run」。
- 代码事实：
  - `judgeRunStart`（`session-contract/src/judgments.ts`）取 `wakingInputs(snapshot)[0]` 作 `first`；开始事实里记的是 `first`。
  - `advance.ts` 的 `invoke` 用 `deriveDriveOperation({ kind: 'invoke', execution, first, started })` 作操作身份，只把 `first` 交给 `AgentDrivePort.invoke`。
  - Agent 契约的 `InputEntry`（`agent-contract/src/passages.ts`）里，`invoke` 一支是 `initial: AcceptedInput`，单条。消息准入（`session-adapters/src/cordis/message-handoff.ts` 的 `bindInvoke`）按一条输入做一次裁定。
- 候选做法（没有建模，没有定）：
  1. `invoke` 带一批。开始 Run 的提交把这一批写进开始事实，`invoke` 的操作身份由这一批算出，Agent 的 `initial` 变成非空的一批，第一步全部取走。批界由日志定，重放确定。代价：改 Agent 契约的公开面，可能是破坏性改动，要负责人拍板；准入对一批里的每一条各判一次，「首条被拒收则 Run 失败收束」这条规则要重定（候选：被拒的各自失去资格，全部被拒才失败收束）。
  2. 不改契约，让第一步等其余输入交完再定水位线。原会话不取这条：它让 Agent 知道 Session 还欠它几条，是一方等另一方，违反「调用是远程调用，寿命分开」。
- 要守的性质：模型的 `BatchNotSplit`；每条输入恰好被回答一次；`invoke` 重放不新建 execution、不改批。

### 7.2 撤销归档后新一轮卡死（F11，R9）：下一程

- 根因（现场只读核实，`f11/report.md`）：撤销归档铸造第 2 代作用域，会话自有的三块注册（`session.modes`、`session.working-directory`、`session.workspace-guidance`）只在创建时写进第 1 代。coding 定义里有带条件的工具，准备请求时读 `session.modes` 被拒；`apps/harness-server/src/rows/agent-context/tools.ts` 把确定的拒绝译成可重试的 `unavailable`，Agent 在 I1 每约 15 秒重查，永不收场。重启救不回。
- 没证实的一点：后台调用与此无关、任何 coding 会话归档再撤销都会卡。区分实验：另起实例，开 coding 会话，不起后台调用，归档、撤销、发一句，预期出现诊断 `tool-conditions: read: refused`。先做这个实验。
- 代码事实：
  - 撤销归档的决策（`session-contract/src/decide-management.ts`）只写 `session.unarchived`（带新一代的作用域绑定）与空闲证据。
  - 注册的决策（`decide-initialization.ts`）要求注册属于「活着的原始创建作用域」，否则抛 `registration does not belong to the live original creation scope`。
  - 适配层已经有「之后的注册变化」的编码（`session-adapters/src/cordis/context-input.ts` 的 `encodeContextRegistrationChange`，带作用域与提交），没读到谁在用。
  - 规格 `packages/session/SPEC.md`：「撤销归档铸造新代次的作用域，新代次不迁移旧作用域的注册」，没说会话自有块由谁、什么时候重新注册。这一句要由 Session 的拥有者改清楚。
- 两处差异，都要关：
  1. 新一代作用域在第一轮开始之前有会话自有块的注册。候选：撤销归档的那次提交里为新一代重新声明（同一次提交，不留窗口）。
  2. 消费者读一个当前作用域确定没有的块时得到确定的答复，这一轮有界地失败，不无限等。这是 #1195 的 U5「永久缺失不冒充暂时」。
- 波及（候选，没核）：撤销归档后的请求可能还缺工作目录与工作区指导两块提醒；执行期带条件命令的放行判断也读不到。

### 7.3 界面的「在跑、能停」与日志不一致（R8，I-7）：下一程

- 现象（截图为证）：日志里有未终结的 Run 时，桌面端显示空闲、没有停止按钮，同时显示「还有 2 句话排着没处理」。人无从自救。
- 没读过代码。要读会话观察的投影（`session-observation`）与界面模块（`session-ui`）怎样得出「在跑」。应然：日志里有未终结的 Run，客户端就显示在跑并能发出停止；停止最终使这一轮收场。
- 改界面观感先加载技能 `visual-standard`；动协议加载 `domain-access-plugin`。

### 7.4 停下的 execution 不终结

- 模型 `gap-deterministic-halt.cfg`：收尾提交确定地失败时，恢复每次接手都再停下一次，这一轮永不收场，人只能取消。
- 这条接手路（`inspect` 得到失联、`detach`、`claim`、`resume`）只读过码，没有在发行组合上跑过。先跑一次：让一轮在收尾节点确定地失败，看恢复是不是每个扫描周期接手一次、又停一次。
- 应然：同一个节点连续停下若干次之后，这一轮以失败终结。由谁数、数在哪、几次，没有定。
- 被取消的一轮的 execution 停下后在执行记录里一直开着：`packages/agent/SPEC.md` 写「新挂接读原取消意图以取消授权收束」，没有兑现。没有已知的用户可见后果。

### 7.5 取消的时序竞争（#1404）

取消已提交、取消控制还没写进 Agent 执行记录的窗口里，`E2` 之外的节点撞上 `stale-advance` 直接停下（`coordinator.ts` 的 `failedNode`；只有 `E2` 有 `waitForRevocationCause`）。原会话用探针的 `cancel-model`、`cancel-tool` 各试一次没有触发。第 1 程之后它不再使会话卡死，只是那一轮以「停下」而不是「取消收束」结束。

### 7.7 每步读写量（R10，I-10）

第一份基线（独立装配，同一会话 4 轮、每轮 45 步）：每步约 1250 次存储读、约 95 次提交。一半是身份的 `read-standing`（每次访问裁定读一次存储），其次是每次 `readWork` 之前的版本读（约 220 次）。这份小负载下读数不随轮数涨，但常数极大；每步提交数随轮数缓涨（93.6 到 102.2）。调用方没有归因到（异步边界丢了栈），要在领域的读面上打标。

真部署上的读数：同一会话每步约 80 次 `readWork`、60 到 170 页 `history.next`，一步从 0.5 秒涨到 2.5 到 3.7 秒；快照只有约 40 KB，慢在排队（每个域 2 个读线程）。

验收组用例在准入里并行时偶发超时（#1573，跟踪在 #1612），很可能是同一件事的另一面：八个发行树服务端同时跑，每步上千次读挤在少量读线程上，等待过了 120 秒的上限。没有证实。

## 接手 8　工具与用法

**探针**（临时文件，不提交）。复制到 `apps/harness-server/tests/long-session/` 下运行，跑完删掉；先构建。

```sh
cd apps/harness-server
cp <材料>/probe/probe-steps.ts <材料>/probe/probe-midrun-input.ts tests/long-session/
# 每步读写量：同一会话 4 轮、每轮 45 步
node --experimental-strip-types tests/long-session/probe-steps.ts --steps 45 --rounds 4 --out /tmp/probe-steps
# 步数上限时排着输入（第 1 程的复现）：第二句恰在第 50 步到达，模型继续要工具
node --experimental-strip-types tests/long-session/probe-midrun-input.ts --when tool --steps 60 --secondAt 50 --keepGoing --waitMs 240000 --out /tmp/pm
rm tests/long-session/probe-*.ts
```

- `probe-steps.ts` 一轮不要超过 45 步：50 步是上限，撞上就是失败的一轮。
- `probe-midrun-input.ts` 的 `--when`：`tool`（第 `--secondAt` 次模型请求到达时发第二句）、`finish`、`cancel-model`、`cancel-tool`、`none`。旧行为下它会一直等到 `--waitMs`。
- 旧行为下的成员用例会 100% 占着一个核空转。可能不结束的命令用 `perl -e 'alarm 120; exec @ARGV' <命令>` 包住。

**形式工具**：`source ~/.config/omne/environment.sh` 之后有 `$JAVA_BIN` 与 `$TLA2TOOLS_JAR`（1.7.4）。跑法见 `formal-handoff.md`。仓库里已有的模型：`packages/agent/agent/verification/run-lifecycle/`（一轮在 Agent 内部的节点；第 1 程改了它的 P3）。

**fast-check**：4.10.2，已进 catalog；`packages/agent/agent` 与 `packages/session/session-contract` 已有 devDependency。别的成员要用时照样加。

## 接手 9　踩过的坑

- 成员用例与发行进程从 `dist` 加载。改了源码不重建，测的是旧产物：红是假的，绿也是假的。验证「先红」时，去掉修复之后也要重建。
- 整洁基线 `tools/product-checks/hygiene-baseline.json` 只手改、只收紧。它的命令行连 `--help` 都会按当前值重写基线，不要跑。文件或函数变长超过基线会被 `lint:rules` 拦：把逻辑挪到新文件，或零增长地改。连续三行以上的注释块也会被拦。
- `lint:rules` 只扫已跟踪的文件，新文件先 `git add`。
- 改了 `session-contract` 的源码要重算发行摘要：在 `packages/session/session-contract` 下 `node scripts/recompute-release.mjs --write`（不带 `--write` 不落盘）。最后一次改源码之后再算一次。摘要变了之后，之前建的会话在新构建上可能接不上（#1461），部署时要告诉负责人。
- 改了契约成员的公开面：`pnpm run contract:api -- --write`，快照一起提交。契约工具对「函数加可选参数」报 `review`，要在卡评论里写判断。
- 改了 `pnpm-workspace.yaml` 的 catalog 之后要 `pnpm install`，否则 `pnpm exec` 拒绝运行。
- 预检报缺 agent 投影：`uv run --locked python .meta_harness/tooling/src/initialize_agents.py --project-root .`。
- 提交信息与 PR：作者是人，trailer 只有 `Harness:` 与 `Agent-Role:` 两行；不加 `Co-Authored-By`，PR 正文不加工具署名页脚，宿主自动附加的也删掉。
- zsh 不拆分变量：文件清单传给命令用 `xargs`。
- 准入：
  - 接续（`--resume-from`）只接受「修复之后的新头」。同一个头不让接续，要么整跑，要么照 `omne-card` 的准入证据参考页手工组合（`cli.ts step <步> --plan tmp/check-plan/plan.json`，带 `OMNE_ADMISSION=1`）。
  - `apps/harness-server/acceptance/PD-tool-execution.*`（后台命令一组）在验收与用例两步并行时偶发超时，单独跑稳定通过（#1573）。红的用例每次不同。
  - 准入会吃满整机的核。机器内存吃紧时宿主会回收后台任务；回收之后可能留下令牌包装的孤儿进程，按进程组停（`kill -- -<进程组>`）。
- 停自己的进程只按 PID 或本仓库路径匹配，不按名字。
- 定时唤醒稀疏地挂；闲着的后台任务及时关。
