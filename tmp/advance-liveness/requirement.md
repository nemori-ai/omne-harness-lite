# 会话受理、消费、推进：任何时序下不卡死、不丢、不重、不拆

## 代理的复述

负责人在用 omne 时，会话会在没有任何报错的情况下卡住：界面上没有「停止」，消息一直排着；服务端日志里这一轮开着，却没有任何一方还会推它，只有重启服务端才能解开（2026-11-25 一天三次，#1649）。同一条链路上还有：失败一轮的输入被下一轮拆成两步重答（F1）、撤销归档后会话永久卡死（F11）、存储拥塞时重试风暴把别的租户也拖住（F36、#1640）。

目标：把「受理 → 消费（批次承接）→ 推进（交给 Agent、交回事实、收场）」这条链路做成在任何交错与故障下都满足安全性与活性。做法是偏函数定义与全化、TLA+ 建模与证明守关键性质，再用 property test 把模型里的极端交错落到代码上。一程一个 PR，进联调轨道。

## 值不值得做

不问：修复。

## 需求的三问

### 给用户什么能力

发出去的话一定会被处理：要么得到回应，要么明确告诉人为什么不能处理、能怎么办。会话不会无声卡住，也不需要重启服务端才能接着用。卡住时人总能自己停下这一轮，接着往下做。

### 系统实现前后有什么区别

| 场景 | 以前（实测） | 以后 | 谁看得见 |
| --- | --- | --- | --- |
| 交给 Agent 时依赖一时不可用（存储队列满、关闭中） | 推进器有限重试，用完只报诊断就放弃，这一轮永久悬置（#1649 反例） | 依赖恢复后推进器从日志重新接到这一步，这一轮接着走 | 人：会话自己恢复；运维：诊断里看得到「等依赖」而非「放弃」 |
| Agent 交回事实时 Session 答 unavailable | 事实丢掉，没人再推 | 按原操作认回，或由日志现算的义务补交 | 同上 |
| 推进时日志被并发改动（answered changed） | 重试一次后再未被调度 | 变化本身成为一次叫醒；日志里缺的那步总会被补 | 同上 |
| 取消一轮后马上开新一轮 | 旧推进者占着推进位，新一轮 invoke 重试用完后悬置 | 旧推进者的推进位随取消失效，新一轮有界时间内交到 Agent | 人：取消后再发一句就能继续 |
| 服务端有没收场的一轮 | 界面可能显示空闲、没有停止按钮，人无从自救 | 界面「有没有在跑的一轮」与日志一致，总能发出停止 | 人 |
| 一轮失败后的新输入（F1） | 新一轮先单独回答失败轮的旧输入，再用第二次模型调用回答新输入 | 每轮开始时把当时全部待处理的普通输入一并接走 | 人：一次回答；账单：少一次调用 |
| 归档时有后台调用，撤销归档后发消息（F11） | 新一轮 0 次模型调用、永久悬置，取消后再发仍卡 | 撤销归档后的新一轮与普通一轮一样推进 | 人 |
| 依赖失败后的重试 | 0 毫秒紧贴重试，readWork 每秒上百次 | 重试有退避下限，有上限地占用共用资源 | 运维、同机其他租户 |
| 进程重启 | 是解开卡死的唯一办法 | 只是一次普通的恢复，不再是解药 | 运维 |

### 谁受益，谁可能受损

- 受益：桌面端与 CLI 的使用者（会话不卡）；同机的其他租户（不被重试风暴拖住）；运维（不用靠重启救火）；做到点作业与子代理的 agent（它们的会话同样走这条推进链路）。
- 可能受损或行为被改变：
  - SE-8「每次放弃都留下具名诊断」的语义改为「每次暂停都留下具名诊断，义务不随之结束」；依赖这条诊断判定「已放弃」的地方要同步（会话诊断协议的消费方、桌面端的失败展示）。
  - 推进器从「内存循环」改为「从日志现算义务」，恢复扫描与运行中补救走同一条路径；`session-adapters`、`agent-host-local` 的驱动口语义可能收紧（推进位随取消失效）。
  - 一轮的批界语义（F1）改变后，回答的轮次数与调用次数会变少，依赖旧行为的测试要同步。

## 不变式清单

| 编号 | 性质 | 违反时的后果 | 谁守 | 验证方式 |
| --- | --- | --- | --- | --- |
| I-1 | **开着的一轮最终收场**：只要依赖最终可用、被取消轮次的推进位最终失效，日志里每一轮未终结的 Run 最终会完成、失败或被取消；不存在「开着、缺一步、无人负责」的可达稳态 | 会话无声卡死，只能重启（#1649） | Session（推进），Agent（推进位） | TLA+ 活性 `OpenRunSettles` 在强公平下成立；property test：随机注入依赖失败与并发改动后，开着的 Run 在有界步数内推进 |
| I-2 | **推进义务从日志现算**：推进器欠的每一步（交给 Agent、交回事实、收场、交入后续输入）都是日志的函数；进程内对象丢失、重试用完、报诊断后返回，都不使义务消失 | 义务只活在内存，一次失败即永久丢失 | Session | 全化表：每个（日志状态 × 推进器事件）都有确定的下一步；TLA+ 不变式「义务 = f(日志)」；重启前后义务集合相同的 property test |
| I-3 | **依赖一时不可用不变成错误结局，也不变成悬置**：答 unavailable 或 changed 的读写，要么按原操作认回，要么在依赖恢复或日志变化时重试；永不静默丢弃 | 事实丢失或误判失败（#1649 第 1、2 次，#1195） | Session（适配与推进） | 偏函数全化表（每种失败种类一个确定处置）；故障注入 property test |
| I-4 | **一条输入至多一次有效承接，批界确定**：每轮开始时把当时已受理、待处理的普通输入一并接走；失败轮的承接作废后，输入与后来的输入在下一轮同批承接 | 同一句话处理两次，或拆成两步多付一次调用（F1） | Session（受理与批次） | TLA+ 不变式；property test：任意受理与失败交错下，每条输入恰好被回答一次，同一批内不拆 |
| I-5 | **单活跃且推进位可让渡**：一个会话同一时刻至多一个未终结 Run、一个有效推进者；被取消或失效的推进者在有界时间内让出推进位，不阻塞新一轮的交接 | 新一轮交不进去（#1649 第 3 次） | Session 与 Agent 的交接边界 | TLA+ 安全性加活性；property test：取消后立刻开新轮的交错 |
| I-6 | **终态不可反转，后继有因**：终态至多成立一次；失败后没有人的输入或重试不开新轮；撤销归档不复活已取消的工作，但恢复接新工作的完整资格 | 工作复活，或撤销归档后永久不可用（F11） | Session | TLA+ 不变式；property test 覆盖归档、撤销归档与后台调用的交错 |
| I-7 | **人总有出路**：日志里有未终结的 Run 时，客户端看得到它在跑，并能发出停止；停止最终使这一轮收场 | 人无从自救（今天的实况） | Session（会话观察投影）、桌面端 | 会话观察的投影与日志一致的 property test；桌面端走查 |
| I-9 | **租户之间互不饿死**：存储的共用队列按租户公平排队并有配额；一个租户的读写压力不使别的租户的受理、推进读写在有界时间内得不到服务 | 一个租户把别的租户拖到卡死（F36、#1640） | 存储（排队与配额），Session（只当消费者） | 排队模型的公平性质（TLA+ 或证明）；两租户负载 property test（另起实例）。负责人定：纳入，放最后一程 |
| I-10 | **一步推进的读写量只取决于新增的条目**：Agent 走一步、Session 推进一次、客户端跟上一次，读写的量与会话日志总长、已走步数无关，只与这一步新增的条目和这一步的请求本身有关 | 会话越长越慢，存储读队列被同一会话占满（2026-11-25 实测：每步 pass.run 0.5 s → 3.7 s，每步约 80 次 readWork、60–170 页历史读） | Session（读取与观察）、Agent（每步取上下文）、客户端 | 定位后按读者给出复杂度论证；property test：日志长度翻倍，每步读量不变；另起实例的长会话基准。负责人 2026-11-25 追加：「要根治的」 |
| I-8 | **重试有界、有退避**：任何重试有下限间隔与总速率上限；一个会话的推进重试不耗尽存储的共用队列 | 重试风暴拖垮同机其他租户（F36） | Session（策略对象） | 策略对象的类型与配置门禁；负载 property test（另起实例） |

## 不算不变式、归别处的

- 性能目标：首轮在依赖恢复后多久被补上、重试间隔与上限的具体数值，归需求本身与 spec 的验收标准。
- 选型：TLA+（TLC）建模，fast-check 写 property test，归技术调研与复用。
- 品味：推进器去掉内存里的长生命周期循环，归 ub-mode 与收口。
