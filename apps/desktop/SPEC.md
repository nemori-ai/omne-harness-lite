# @omne-harness/desktop

## 总体架构

桌面应用回答一个问题：一个人怎样在窗口里使用系统，而页面的代码读不到登录证明。它由两半组成。页面是客户端的 Cordis 树，树上有界面外壳与各领域的界面模块。页面之外的那一半替页面做三件事：把登录证明放进页面读不到的 cookie，把页面的请求带上凭据转给服务端入口，把构建好的页面发给浏览器。

这三件事的全部逻辑在转发层里。转发层把页面的请求适配成服务端入口的调用，带上凭据转发。它是一个 Hono 应用，只认 `Request` 与 `Response`，不认识承载它的进程。它有两种承载，页面不变。桌面应用里它跑在 utility 进程，由主进程把请求送进去，不开任何端口。另一种是独立转发进程：人在命令行启动的一个 Node 进程，在回环地址上监听，让普通浏览器打开页面。独立转发进程只用于开发与走查。

本规格给每一部分一个名字，不用「宿主」统称页面之外的那一半：

| 部分         | 回答的问题                                                                                           |
| ------------ | ---------------------------------------------------------------------------------------------------- |
| 共享类型     | 页面与转发层之间的路径与字节；两边读同一份协议清单                                                   |
| 转发层       | 登录怎样变成一枚 cookie；一个页面请求能不能转发、带什么凭据；一页的多条观察怎样合成一条流            |
| 独立转发进程 | 开发与走查时，一个单独的 Node 进程怎样在回环地址上把转发层交给浏览器；它不是 utility 进程            |
| 主进程       | 怎样把应用协议的请求送进 utility 进程里的转发层，怎样保管 cookie，窗口怎样加固与恢复；本机设备的路由 |
| utility 进程 | 桌面应用里承载转发层的子进程，属于整个应用，不属于哪个窗口；它怎样启动、就绪、停止与重启             |
| 进程间传输   | 主进程与 utility 进程之间怎样在一个消息端口上传 `Request` 与 `Response` 的流，怎样限速与取消         |
| 页面         | 页面这一侧的传输怎样接到客户端的树；界面外壳怎样画出插入位置里的东西；装配文件列出哪些协议与界面模块 |

下文的「外壳」是界面外壳的简称。本规格不用「宿主」指应用的任何一部分。

一次调用这样走：界面模块调协议客户端，协议客户端经页面的传输发一个同源的 `POST`。浏览器自己带上 cookie。转发层读出 cookie 里的登录证明，按协议契约核对目标并决定带什么凭据，再发往服务端入口。桌面应用里多两跳：应用协议的请求先到主进程，主进程注入 cookie，经进程间传输送到 utility 进程。

## 领域边界

本应用拥有：登录 cookie 的内容与它什么时候签发、什么时候清除；转发层的转发规则；页面与转发层之间的路径与字节；一页一条事件流的合流规则；界面外壳（服务 `shell` 的实现、版式、当前页面、露着哪一面与翻面的入口、租户的存放、主题与字号档的偏好、Agent 形的座位与报告的合并、告知笺）；页面的装配；窗口。

本应用不拥有：身份、会话、设置项与人工介入的规则与协议，它们归各自的包组与协议契约；连接、客户端的树与协议客户端怎样随可用性长出与收回，归接入的客户端核心与客户端装配；对话界面、待你决定的界面与设置界面归各自领域的界面模块。界面外壳与转发层都不认识任何领域：转发层只读协议契约里每个操作的身份要求。

本应用需要别人做的：

| 需要                 | 对方                                                          | 本应用需要它做什么                                                                                                                                                                      |
| -------------------- | ------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 客户端核心与连接     | 接入（SDK 与客户端装配）                                      | 给出传输接口与连接插件；客户端的树随服务端入口挂着的协议长出与收回协议客户端；给出登录状态源的接口                                                                                      |

| 外壳契约与共用界面件 | 前端（`shell-contract`、`ui-kit`）                            | 插入位置、每个位置的规矩、服务 `shell` 的抽象类；控件、样式 token 与主题控制器                                                                                              |

## 心智模型

把转发层想成一个只认识几份协议契约的看门人，把页面想成一个拿不到钥匙的访客。钥匙是登录证明，放在一枚页面的脚本读不到的 cookie 里。页面每发一个请求，浏览器替它把这枚 cookie 交给转发层。转发层对每个调用与观察只问三件事：这个目标是不是我认识的契约里声明过的；它是不是一个携带凭据的操作；按契约它该带什么凭据。

转发层不记任何登录的事。它知道的全部来自这一个请求带来的 cookie。所以承载它的进程重启不丢登录，两个进程里的转发层可以服务同一个浏览器。

最容易想错的四处：

- 退出总会清掉 cookie，哪怕服务端是否注销不确定。
- 一次 `denied` 不等于登录失效。页面收到 `denied` 之后问一次登录状态，转发层用同一个证明查一次当前租户。它也答 `denied` 才算失效。
- 页面发往转发层的请求失败时，页面证明不了字节没有发出，除非转发层在转发前就拒绝了它。
- 页面读不到 cookie，不等于页面里的代码做不了事。页面里的任何代码都能以这个人的身份发起契约里声明过的操作。cookie 只保证证明带不走。谁的代码能进页面，由装配决定。

界面模块只依赖界面外壳，外壳在它就加载。它要的协议与别的界面模块提供的东西写成引用，外壳按此刻的登记表给每个界面模块算一次采用（规则见[前端规格的「界面模块」](../../packages/frontend/SPEC.md#界面模块)）。服务端少一份协议时，引用它的界面模块的页面还在导航里，页面的位置写着缺的是哪一份、为什么；别的页面不受影响；协议回来，页面自己恢复。切换页面只是藏起别的页面，不是卸下，所以看一眼设置不会打断对话里正在进行的一轮。翻面也一样：正面与反面都挂着，翻过去只是换哪一面露着。

## 应然设计

### 登录 cookie

- 登录证明只在一枚 cookie 里，名字是 `omne_login`。它的值是一段 JSON 的 base64url：登录证明、行事租户、登录标识。行事租户取签发成功体里的租户。
- 属性：`HttpOnly`，`SameSite=Strict`，`Path=/bridge/`，`Max-Age` 是一年（31536000 秒）。应用关了再开，登录还在。
- `Max-Age` 不是登录的有效期。登录有效不有效由服务端定：每份登录在签发时冻结了最长截止时刻与空闲截止时刻，到期、被撤销或换了凭据之后服务端答 `denied`。cookie 只保证证明不先于服务端的截止时刻丢掉。
- 页面启动时问一次登录状态。服务端认这份登录，页面直接进「已登录」；不认，转发层清除 cookie，页面回登录门并显示原因。
- 证明因此落在本机，存在应用的用户数据目录里。打包的应用（测试档与发行档）打开了 Electron 的 cookie 加密，落盘的值用系统保管的密钥加密：macOS 是钥匙串，Windows 是当前用户的 DPAPI，Linux 是 Secret Service 或 KWallet。没打包的应用（`pnpm run start:test`、`pnpm run dev`）没有这个开关，证明以明文落盘，保护它的只有这个目录的权限。
- 测试启动不碰系统保管的密钥：macOS 用假钥匙串，Linux 用 Chromium 自带的固定密钥。它们只给测试与验证用，应用自己从不加这两个开关。
- Windows 上 Chromium 只把 cookie 密钥写在用户数据的 `Local State` 里，而这个文件要在新的用户数据启动约 10 秒后或干净退出时才写。首次启动后这段时间里应用崩溃或被杀，已经落盘的 cookie 就再也解不开。所以测试档与发行档在 Windows 上拿到单实例锁之后，`Local State` 里没有密钥就先起一份带 `--omne-cookie-key-writer` 的应用：同一个用户数据目录、不用 GPU，就绪时用 safeStorage 加密一句探针打出来，干净退出写下密钥。启动最多等它 5 秒。主窗口开出来之后解探针，解得回原文记一行「用的是存下的密钥」，解不回记一条错误。写入者跑完仍没有密钥，就留一份带版本的失败记录，同一版本一天之内不再跑并说明；找到密钥就删掉记录。Electron 在生成密钥时就写盘之后，这一段与它的代码一起删掉。
- 转发层是唯一写这枚 cookie 的地方，写的时机只有三个：登录成功时签发；退出时清除；确认登录已失效时清除。
- cookie 读不出（不是 base64url、不是 JSON、缺字段、超过长度上限）当作没有 cookie，并在这次答复里清除它。

对一个请求，转发层只看它有没有带来读得出的 cookie：

| 事件                         | 请求没有 cookie                              | 请求带着 cookie                                               |
| ---------------------------- | -------------------------------------------- | ------------------------------------------------------------- |
| 页面请求登录                 | 发出登录操作                                 | 拒绝：已经登录                                                |
| 登录的答复是成功             | 签发 cookie。只告诉页面「登录成功」          | 不可达                                                        |
| 登录的答复是其他结果，或未知 | 不签发。把结果如实告诉页面，未知就说未知     | 不可达                                                        |
| 页面请求退出                 | 直接答「已经退出」                           | 发出注销操作，目标是 cookie 里的登录标识                      |
| 注销的答复是成功或无变化     | 不可达                                       | 清除 cookie，答「已经退出」                                   |
| 注销的答复是其他结果，或未知 | 不可达                                       | 仍然清除 cookie。告诉页面：本机已退出，服务端是否已注销不确定 |
| 页面问登录状态               | 答「未登录」                                 | 用 cookie 里的证明查一次当前租户，按下一张表答                |
| 页面请求一次普通调用或观察   | 不带登录证明发出。需要登录的操作由服务端拒绝 | 按契约带上凭据发出                                            |

页面问登录状态时，转发层查当前租户得到的结果：

| 查询的结果           | 转发层怎样答                                      |
| -------------------- | ------------------------------------------------- |
| 成功                 | 「已登录」                                        |
| `denied`             | 清除 cookie，答「未登录」，并说明原因是登录已失效 |
| 其他结果，或结果未知 | 「已登录」，并说明这一次没有核实                  |

- 登录的结果对页面只有四种：登录成功；统一认证失败答认证失败；`unknown` 与本地的结果不确定答未知；其余（字节没发出、依据不可用、本部署不提供、协议拒绝、契约读不出的消息体、已经登录）答不可用。退出的结果只有两种：已经退出，未知。答复的正文只有结果字段，登录证明只出现在 `Set-Cookie` 头里。
- 登录操作是身份协议的签发登录，注销是撤销登录。
- 登录或注销的调用抛出异常时：登录不签发 cookie；注销仍然清除 cookie。异常不原样交给页面，答复是「未知」。
- 同一个证明同一时刻至多一次查询在途：同一个进程里的转发层，带着同一个证明来的并发询问共用一次查询的结果。结果不缓存。
- 登录状态里一并说出转发层认识的协议（名字与主版本）。页面拿自己的协议清单比对，页面要用而转发层不认识的，或者转发层根本没说，页面顶上写一句「应用的版本旧了，需要重启。」并列出少的那几样，不像这项能力不存在那样静默。
- 页面的调用与观察经桥的消息到转发层，转发层自己是一个协议客户端，用它自己的传输重新发给服务端，所以页面的头到不了服务端。页面一侧契约的修订号写在桥的消息里（`revision`，正整数），转发层原样带进请求，由传输写成头。没带修订号的消息照旧读得出；修订号不是正整数的消息读不出，不当成没带。

登录中与退出中不再是转发层的状态。它们是页面自己的状态，见「页面」一节。

### 转发规则

- 转发层只转发它认识的契约里声明的操作与观察。认识的契约是 `access/v1` 加页面的树带着的那一份协议清单，页面与转发层读同一份。目标按协议名、主版本与名字三样精确比对。不认识的协议、认识的协议里没有声明的名字、标了携带凭据的操作，一律答「字节没发出」，不带任何东西发往服务端。
- 转发层读契约有两个不能省的理由。第一，每个操作带什么凭据写在契约里：不要身份的什么都不带；要登录的只带登录证明；要行事租户的带登录证明与行事租户。第二，签发登录这一类操作的答复正文里有登录证明，页面经普通调用拿到它，cookie 就白藏了。
- 凭据只从这个请求的 cookie 里取。页面在正文或头里自带的凭据被丢弃。

### 页面与转发层之间的路径

- 路径都在 `/bridge/` 之下：调用、开观察、停观察、事件流、登录、退出、登录状态、取 plugin 的文件。其余 `GET` 是构建好的页面静态文件。
- 调用的答复是传输的三种结果之一：答复了（结果与体）、没发出、不确定。登录与退出的答复只有结果字段。问登录状态是一个 `POST`，一问一答，不是一条流：它会向服务端发一次查询，还可能清除 cookie，所以不用 `GET`。
- 一个页面的全部观察走同一条事件流（`GET` 带页面自取的标识）。开一条观察与停一条观察是两个普通 `POST`，带页面给这条观察取的标识，事件按标识分发。原因：服务端入口是 HTTP/1.1，一个观察一条流；浏览器对一个地址只保持几条连接，每条观察各占一条长连接时，开着的观察一多，调用就排不上。
- 事件流的请求一到就返回响应头，不等上游。开观察的 `POST` 登记之后立刻答复，上游的观察在答复之后才开。
- 这一页还没有事件流时开观察答 `409`，什么都不转发。事件流断了，转发层取消挂在上面的全部观察，页面把它们都读作不确定，下一条观察重新开一条事件流。
- 事件流按页面读的速度写。转发层为一条事件流攒下的还没被读走的字节有上限，上限是转发层里的一个常数（1 MiB）。一帧放得下才放进去，放不下就等页面读走，这期间不从这条流上各个上游的观察取下一帧。单独一帧比上限大时，它等到流里空了独自放进去。
- 页面一直不读时，积压留在服务端入口。服务端入口的规则是积压碰到它的字节上限就结束这条观察。转发层把上游给的结束原因原样交给页面，页面照常把它当作一条结束了的观察重新开。转发层不替上游编一个结束原因。
- 一页的观察共用一条流，所以它们互相排队：一条观察的帧很多时，别的观察的事件排在它后面。这是合流的代价，换来的是调用不被长连接挤占。
- `POST` 只收 JSON，并且必须带同源的 `Origin`，不带的被拒绝。挡住别的来源的是这条检查，不是 cookie 的 `SameSite`：`SameSite` 不看端口，本机另一个端口上的页面算同站，它发来的请求照样带着 cookie。所以每一个有效果的路径都是 `POST`。
- 用一份登录证明开的观察不留到这份登录之后。退出时，以及确认登录已失效时，转发层结束每一页上用这份证明开的观察，结束原因是 `denied`。不要身份的观察不受影响。
- 登录证明与密码不进日志，不进错误信息。日志一事一行：被拒的请求只写方法、路径与 `Host`、`Origin` 两个头；失败的请求只写方法、路径与失败的种类，不写错误的原文，因为原文可能引用消息体。日志从不写消息体、cookie、证明或密码。
- 页面发往转发层的请求失败时，只有转发层在转发前答出的拒绝能证明字节没有发出；其余失败，调用答不确定。

### 取 plugin 的文件

页面装一份 plugin 的代码与样式、画它带的图时，从同源的一条路取它的文件：`GET /bridge/plugins/<名字>/<版本>/<包里的路径>`。

- 这条路在 `/bridge/` 之下，因为登录的 cookie 只在这个路径下带；放在别处，页面的导入请求不带登录。
- 转发层带着这个请求的登录，经 `plugin/v1` 的 `read-file` 一段一段地读，读到一段就交给页面一段，目标租户是登录证明里的那一个。它是一个读，没有效果，所以是 `GET`：页面的 `import()` 与样式表只会发 `GET`。
- 一个文件多大都取得到，没有段数或字节数的上限：第一段的答复带着整个文件的字节数，答复头里的长度就是它；每一段都要比上一段往前，所以它一定读得完。转发层不把整个文件攒在内存里，同时在手的只有一段，页面读得慢时不去取下一段。
- 只认包里许带的后缀：`.js`、`.css`、`.json` 与五种图 `.png`、`.jpg`、`.webp`、`.avif`、`.svg`。类型只取决于后缀，答复带 `nosniff`。名字、版本与路径先照 plugin 清单的规矩核，路径不解码：不合规矩的、后缀不在这几种里的，答 `404`，不问服务端。
- 取到的文件答复带 `cache-control: private, max-age=31536000, immutable`：地址带版本，内容不会变；`private` 是因为它要登录才取得到。不是文件的答复（没登录、不在、被拒、取不到）仍是 `no-store`。
- 矢量图的答复另带 `content-security-policy: default-src 'none'; style-src 'unsafe-inline'; sandbox`：有人把这个地址当页面直接打开时，里面的脚本不跑、什么都不加载。它被当图片用时浏览器本来就不执行脚本，这一条是第二道。
- 没登录答 `401`，不问服务端。第一段就知道有没有：服务端答不在答 `404`，答拒绝答 `403`，答依据取不到答 `503`，都不带服务端给的正文。第一段之后出的事只能断在半路：后面的一段读不到、不在了、文件的字节数变了、下一段没有往前或越过了末尾、读完时比说好的短，转发层就让这个答复断掉，页面的这次导入失败；不把残缺的一份当整份交出去。
- 版本是内容的摘要，同一个地址的内容不会变；页面按地址缓存模块，换了版本就是另一个地址。
- 这条路不改内容安全策略：脚本与样式仍然只许同源，页面里没有内联脚本，也不许 `eval`。
- 页面给装载器三样：怎样取一份 plugin 的代码（从上面那条路动态导入），交给代码的 `React` 和共用界面件，与一份 plugin 的文件在哪（`/bridge/plugins/<名字>/<版本>/`）。plugin 的代码因此和应用用同一个 React，文件里不写任何包名；它的数据成员用 `file(路径)`、代码成员用 `files.url(路径)` 指到自己包里的图。
- 图不在装的时候取：装一份 plugin 只取它的模块，图在第一次被画到时由浏览器去取，取过的走缓存。启用着但没穿的皮肤，样式不进页面，它的图不会被请求。

外壳的实现另声明两个按键选画法的点，把共用件的[换画口](../../packages/frontend/SPEC.md#换画口)接到登记表上：

| 点 | 键 | 自带的画法 |
| --- | --- | --- |
| `shell.icon` | 图标的名字（规矩的键表列出全部） | 图标集里那一个 |
| `shell.piece` | `loading`、`empty-state`、`inline-notice`、`figure` | 共用件自带的那一件 |

- 一个键上有算数的画法就画它，没有就画自带的，不多一层元素；画法抛出时这一处落回自带的，别处不受影响；换样子时与令牌同一刻换。这些都是按键选画法的点本来的规矩。
- 页面根上只放一个口，外壳起来之前、走了之后，共用件画自带的。
- 装载器常驻一条要登录的观察。页面常驻的这类观察现在是四条，服务端入口每登录的名额要盖得住它们再加同时看着的会话，见[服务端应用的规格](../harness-server/SPEC.md#接入)。
- 页面给装载器一个底，存在本机（`localStorage` 的 `omne.floor:<租户>`），每个租户一份。它从一次启动里第一次去装起记成「正在起」，到这一次起来了才改回；下一次启动读到「正在起」，就是上一次装的时候页面没了，连倒的次数加一。「起来了」有三个条件：读到了要装的表，表里每一份都有了结局，这之后页面再活过两秒并且已经把自带的界面画出来（启动时那行「正在连接」换掉了）。两秒是给一装上就让页面重新加载的那一种留的。
- 连倒的次数到 2，底拦下上一次要装的那几份：第三次启动不装它们，页面照常画自带的。只启动、还没读到要装什么就关掉的那一次不算倒下；只卸不装的那一次也不算。存的东西读不懂时从头算；本机存不了时这一次照常，只是不跨启动。
- 没起来的写在主区最上面的一条提示里，登录前后都在同一处：启动时出错的界面模块写名字并说别的照常；被底停掉的写是哪一份哪一版、为什么停、怎样放开（换一版，或者不再装它）。没有就不画这一条。
- 装配里有 plugin 的装载器（`plugin-ui`），协议清单里有 `plugin/v1`。装什么、怎样装归[包组规格](../../packages/plugin/SPEC.md#客户端的装载器)。

### 独立转发进程

- 它只用于开发与走查：在浏览器里调页面，以及走查脚本驱动无界面的浏览器。它不是给人日常使用的交付面，不随发行的应用提供。它和 utility 进程没有关系，桌面应用不启动它。
- 一个 Node 进程在回环地址上监听，把收到的请求交给转发层。它只监听回环地址。
- `Host` 头必须是回环名字（`127.0.0.1`、`localhost`、`[::1]`），端口不核：挡住重绑定页面的是名字，经端口转发打开时浏览器看到的是另一个端口。
- 页面断开连接时，还没答复的调用被取消，开着的事件流被取消。
- 已知的限制，启动时打印在第一行：登录 cookie 在浏览器自己的 cookie 库里。cookie 不按端口隔离，浏览器把它带给 `127.0.0.1` 上任何端口的 `/bridge/` 路径，所以这台机器上别的本机网页服务能收到登录证明。不要用它登录一个要紧的账号，不要在不信任的机器上用它。桌面应用没有这条限制，它不开端口，cookie 不进浏览器。

### 主进程与 utility 进程

- 页面在应用自己的协议下（`omne-app://app`）。主进程登记这个协议，把每个请求映射到一个内部的 HTTP 源，经进程间传输送进 utility 进程。utility 进程里跑转发层。这条路径上不开任何 TCP 监听，别的程序与别的网页够不着转发层。
- utility 进程由主进程在应用启动时拉起，一个应用一个。它属于应用，不属于窗口：窗口关了再开、页面重新加载、渲染进程崩了，它都照常；应用退出时主进程停掉它。有多个窗口时它们共用同一个 utility 进程与同一个 cookie 罐，各自的事件流按页面自取的标识分开。
- 窗口用应用专用的一个持久会话，cookie 罐建在这个会话上，应用协议也登记在它上面。
- Chromium 不替应用协议下的页面保存 cookie，也不给它的请求发 `Origin`。所以主进程做三件事：
  - 保管 cookie。转发层答复里的 `Set-Cookie` 存进主进程的 cookie 罐，存好并写到磁盘之后才把答复交给页面，下一个请求就看得到。应用退出前再写一次，等它有时限。主进程给每个请求注入 `Cookie` 头。页面自带的 `Cookie` 头被剥掉。页面的脚本没有 `document.cookie`。
  - 补上来源。请求到达协议处理函数，说明它来自应用自己的页面，因为窗口不离开应用协议。主进程给非 `GET` 的请求补上内部源的 `Origin`。页面自带的 `Origin` 不被采信。
  - 关联取消。处理函数收到的请求自带的取消信号不触发。主进程在请求发出前给它盖一个头，值是本次启动的随机前缀加网络请求的编号，页面自带的同名头被换掉。页面在响应头之前放弃请求时，主进程从网络请求的错误事件得知，按这个头找到这次请求并取消它。响应头之后，取消经响应正文那条流传到。
- 本机设备的路由：`/device/` 下的请求不送进 utility 进程，由主进程自己答（`src/main/device-screen.ts`）。`GET /device/screen` 答 `{ available }`，这台机器有没有屏幕后端；`POST /device/screen` 截一张，等人选定才答；`GET /device/screen/frame`、`POST /device/screen/active` 与 `POST /device/screen/choice` 只给截图时的遮罩页用，都带着屏与截图号（`?screen=<屏>&capture=<号>`）；`POST /device/screen/settings` 打开系统设置的屏幕录制那一页（只有 macOS 有，别处答 404）；`/device/` 下别的路径答 404。屏幕后端就是 agent 截图用的那一个：`@omne-harness/screen` 的 `screenBackendFor(process.platform)`，库的二进制由主进程按档加载（打包的应用从 `resources/native/node-screenshots.node`，没打包的从安装的包），第一次用时加载一次，加载不了答没有后端。截图在 omne 自己的进程里，macOS 的屏幕录制许可因此记在 omne 名下。
- 截一张的次序：后端答没有许可时，先请系统要一次许可（macOS 弹一次窗，并把 omne 列进系统设置），答 403 `not-authorized`，窗口不动。否则让开（macOS 隐藏整个应用，别处隐藏窗口，等窗口看不见了再等一会儿），截图号加一，把后端列的每块屏此刻的整块画面截下冻住，再在每块屏上开一个遮罩窗口（`src/main/screen-overlay.ts`）：无边框、透明、置顶到屏保那一层、盖住菜单栏与程序坞，载应用自己的一页 `shot.html?screen=<屏>&capture=<号>`（`src/page/shot/`，构建的第二个入口，同一份内容安全策略）。鼠标所在那块屏的遮罩拿焦点。
- 遮罩页的界面是 react-screenshots（钉 0.5.22）的组件：给它冻住的画面，人在上面框选，可以拖边调整，带放大镜；标注矩形、椭圆、箭头、画笔、文字、马赛克，撤销与重做；双击选区或点「确定」取定，没框选时双击取整张；右键或点「取消」算取消。组件交出的 PNG 是选区乘设备像素比，从冻住画面的物理像素裁出并合上标注。「保存」钮藏起来，图只进附件区。不接 Esc：omne 让开之后遮罩拿不到键盘（真机上按 Esc 没有反应）。工具栏的图标是组件自带的，不取自界面件，这是对视觉规范的一处偏离。
- 组件的样式在构建时经 `scripts/screenshots-css.ts` 改两处：收进 `omne-builtin` 层，去掉它内联成 `data:` 的图标字体（`font-src 'self'` 不收 `data:`）；同一份字体由遮罩页作为自己的文件提供（`src/page/shot/screenshots-icon.woff2`，从这一版组件的样式里原样取出）。样式里找不到那条字体声明时构建失败，换版本时不会静默丢掉图标。
- 一次截图只认一块屏：遮罩页上第一次按下时报告 `active`，主进程记下在用的屏，别的遮罩不再接指针；之后只收在用的那块屏交的结果，别的屏交的答 409。遮罩页把组件的「确定」交成 PNG、把「取消」交成空内容，都交给 `choice`，一页只交一次。主进程先读完请求体，再核「在截、截图号对、在用的屏为无或就是它」并结算。在用的屏的遮罩被关掉、页面没加载出来、它的渲染进程没了，算取消；别的屏的遮罩出这些事，不结算。截图号对不上的请求一律答 409，上一次截图迟到的请求不会成为这一次的答复。这些次序由 `verification/models/screen-choice/` 的模型检查（见那里的 `formal-mapping.md`）。
- 主进程拿到结果就关掉全部遮罩并回来。取定答 `image/png` 与冻住画面的时刻（头 `x-omne-taken-at`），取消答 204。同一时刻只截一次，截着时再截答 409 `busy`；不在截或截图号不对时，取画面答 404，报告在用与交结果答 409；交的不是 PNG 答 400。冻住时某块屏不见了答 409，后端出错答 500，都带一句原因，都先回来，不开遮罩。页面一侧是 `src/page/screen-source.ts`，装配把它交给媒体的界面模块作截图的来源；独立转发进程没有这些路由，浏览器里没有截图钮。
- utility 进程有明确的状态：空闲、启动中、运行中、停止中、已停止。并发的启动共用同一次就绪。启动到就绪有时限，停止有宽限期。utility 进程意外结束时主进程重启它，开着的请求以失败结束，页面读作不确定。因为转发层不记登录，重启之后人不用重新登录。
- 停掉或退役一个还没生出来的 utility 进程时，Electron 杀不了它；主进程在它生出来的那一刻杀掉它，不让它跑到宽限期满或一直跑下去。
- utility 进程不在的时候，页面自己的文档请求算一次加载失败，由窗口的恢复重新加载。别的请求照常得到一个表示失败的状态，页面读作不确定。文档请求要是也答一个状态，窗口会把那一行失败的文字当成加载好的页面留在那里。
- 进程间传输在一个消息端口上按请求编号复用，传 `Request` 与 `Response` 的头、状态与双向的正文。每条正文有字节窗口：发出而没被确认的字节到了上限，发的一方等着。取消、端口关闭都在两端各清理一次。
- 进程间传输不给请求加时限，等响应头、两帧之间、整个请求三样都不设。一次调用要等服务端答完才有响应头，接入层与客户端核心都没有给调用规定时限，结果丢了按「不确定」认回。传输自己掐断一个慢而合法的调用，是把一个会有答复的调用变成不确定。停不下来的请求由另外三条路收：页面放弃时主进程取消它；utility 进程结束时端口关闭，开着的请求以失败结束；应用退出。

### 页面

- 客户端的 Cordis 树装着连接插件与清单里每份协议的协议客户端。连接插件的传输是页面到转发层的同源 HTTP。读到「暂时没有可读的」时按可配置的再问策略等待，次数与总时长都有上界。
- 登录状态归页面。它有四个取值：未登录、登录中、已登录、退出中。页面请求登录时进「登录中」，请求退出时进「退出中」。登录中与退出中，页面不发新的登录与退出。
- 页面启动时问一次转发层的登录状态，得到未登录或已登录，然后才画登录门或工作区。问不到时按退避重问，这期间页面只说正在连接，不进登录门：页面可能比转发层先就绪，这时把人放到登录门前是错的。
- 登录的答复是「登录成功」，页面进「已登录」。答复是「认证失败」，页面回「未登录」。答复是其余任何一种（未知、不可用），页面不自己下结论，问一次登录状态，按它答的进「已登录」或「未登录」：这次登录可能已经签发了 cookie 而答复丢了，这时再登录一次只会被答「已经登录」。
- 退出的答复到了，页面进「未登录」。
- 页面在三种时候再问一次转发层的登录状态：一次调用答 `denied`；一条观察以 `denied` 被拒或结束；页面的事件流断了又连上。转发层答「未登录」时页面进「未登录」，并显示转发层给的原因。同一时刻至多一次询问在途。问不到时页面的登录状态不变。
- 树上另装拓展点的机制的服务 `dynamis`、外壳的服务 `shell` 与装配文件列出的界面模块，`dynamis` 在外壳之前装。外壳继承外壳契约的 `ShellService`：放进去、读位置与订阅由抽象类照登记表给出，外壳不另写存放规则。页面在树起来之前就建好的状态经一个转接的读口读位置，外壳的服务加载后接上它，卸载后断开。
- 两个界面模块撞在同一处时，这一处两份都不画。撞的是登录门或反面时，那一面上显示一行说明，写明是哪几家。外壳每发现一处冲突，往树的日志里记一条错误，写明位置、标识与各家的名字。一个点读不出时外壳在它那里什么都不画，和「没有东西」看起来一样，所以树的问题一栏每出现一个问题（没有声明的点上放了东西，一个点被声明了两次，键的来历成环或取自没声明的点），外壳也记一条错误，写明是哪个点、哪一种问题；同一个点的同一种问题只记一次，消失之后再出现再记。
- 客户端这棵树问得出来：`tree(登记表, 整个部署)` 给出全部的点、点下的键、每一项是谁放的、生没生效。桌面装配出的整棵树钉在 `tests/client-tree.txt` 里；谁加了一个点而宿主没有声明，这条用例会红。
- 装配文件 `page/assembly.tsx` 只列两样：协议契约的清单（与转发层读同一份 `shared/protocols.ts`）和界面模块插件的清单（身份、会话、会话的读法、人工介入、通知、日程、日历、资产、MCP、工具、模型、用量、工作区、媒体、画布，共十五个，`boundaries` 用例核这份清单）。它是页面里唯一导入领域成员的文件；去掉一个界面模块只改这一处，外壳照常编译和运行。
- 两个领域的界面要碰在一起时，也在装配文件里接，界面模块之间不互相导入。有十一处。第一处：会话的界面模块从 `./cordis` 入口导出带类型的拓展点 `sessionDock`（对话页里转写区与输入框之间的位置），装配把它作为选项 `sessionDock` - 装配不交资产类别的名字：资产页上类别的名字由资产的界面模块经 `assets/v1` 的 `list-categories` 向服务端取，装配文件里没有类别的名字。
- 登录的端口：页面把自己的登录状态、登录与退出组成外壳契约的 `ShellLogin` 交给外壳。两边的形状由类型对上：客户端装配的登录状态多一个取值，这里就编译不过。外壳把退出包一层：退出的结果是 `unknown` 时记下「本机已经退出。服务端是否已注销这次登录，没有得到确认。」，回到登录门时由门上的形用浓墨的墨框写出，下一次退出开始时清掉。转发层答「未登录」并给了原因时（例如登录失效），回到登录门时同样由门上的形写出这个原因。
- 租户：外壳存放当前租户的文本，身份的界面模块设它；登录状态离开「已登录」时外壳把它清空。页面、侧栏区、反面与附着位置的每一项渲染时收到它，页面项的标记也收到它。
- 附着位置：外壳实现服务的 `attached(位置的名字, 对象)`，返回一个组件元素。它订阅 `attached` 位置与租户，只渲染 `anchor` 与给定名字相同的项，逐项以项的标识为 `key`，每一项收到 `{ scope, subject }`；没有匹配的项时什么都不渲染，外面不包多余的容器。位置的项放进来或撤下、租户变了，这个元素自己重渲染，不靠所在的页面重渲染。
- 展示方自己排版：外壳实现服务的 `arranged(位置的名字, 对象, 排版函数)`，同样返回一个组件元素，取的项、次序、订阅都和 `attached` 相同。它不把各项拼在一起，而是把每一项的标识、标签与渲染结果交给排版函数，画排版函数的返回值。位置的项放进来或撤下、租户变了，它用新的表再调一次排版函数。
- 界面模块缺着必需的需要时，外壳这样画它放的东西。页面：导航里的那一行照旧，页面的位置画一条行内通知（注意的语气），一句话写出缺的是哪一条与原因。登录门：同一种通知，开头写「登录现在用不了」。反面不画通知：放它的模块缺着必需的需要时外壳不放反面，应用只有一面。原因有六种，每种一句：服务端没有提供这份协议；服务端提供的是别的主版本（写出是哪几个；两边一高一低时说出哪一边的版本旧了）；这份协议在服务端有两份，都没有生效；这个应用里装了两份不同的客户端；这个应用没有装它的客户端；它要的那个点没有人提供。连接还没有说开着什么时不画通知，画「正在连接服务……」。缺没缺由外壳契约的采用给出；原因由外壳向连接的可用性问，外壳契约不认识连接。页面从缺回到齐时重新挂载，只在打开时读一次的页面会重读。
- 显示在前面的那一页在同一拍里被收回又放上（界面模块换了一份采用）时，它仍然显示在前面；一拍之后页面还不在，外壳才回到第一页。
- 一项坏了只坏这一项：外壳画的每一项（登录门、页面、页面项的标记、侧栏区的一项与它的窄条样子、反面、附着位置的一项）都包在一层错误边界里，项的渲染函数在边界里面的一个组件里调，所以渲染函数自己抛出、或它返回的组件在渲染当中抛出，都只落在这一项上。坏了的一项的位置上显示一句「这一块读不出」，不带错误的文本；页面项的标记坏了什么都不画。边界不加任何 DOM 元素。这一项收到的租户或对象变了，边界重试一次；都没变的重渲染不重试。页面里没有写诊断的去处，外壳不另记。
- 页面项的标记：页面项带 `badge` 时，导航里标题之后多一个 `.shell-nav-badge` 元素，内容是 `badge` 收到当前租户后的返回；返回空值时元素仍在、内容为空，由样式隐藏。导航收起、只剩图标时，标记缩成图标右上角的小点。
- 当前页面：没有人选过时显示次序最前的一页；人在导航里选了一页或界面模块调 `navigate`，显示那一页；标识不在时什么都不做。显示着的一页被撤掉，回到次序最前的一页，撤掉的那页再回来也不抢回前面；一页都没有时主区空着。
- 家：次序最前的一页由家代表，它在导航里没有自己的一行。<!-- OD-6 --> 侧栏里任何时候恰好一处被选中：家、导航的一行或底部的一格。侧栏区里一个界面模块自己的「当前的那一项」（例如当前会话）只在它所属的页面显示着时画选中的底；外壳经服务的 `page` 告诉界面模块现在显示的是哪一页。家被选中时不画选中的底，形坐在那里就是标记。选中的底在行间滑动；跨段时旧的淡出、新的淡入。
- 外壳的样子，按登录状态：
  - 未登录与登录中：只有主区。上面是门的座位，下面是登录门里的那一项，宽度取决定宽度，标题左对齐，不居中摆成落地页。登录门空着时，连接还在「正在连接」就说正在连接服务，否则说「这个部署没有开放登录」。「正在连接」晚一个 `enter` 的时长才显示，快的启动看不到它；同一时刻至多一个加载状态。
  - 退出中：主区只说「正在退出……」。
  - 已登录：左边是可以折叠的侧栏，右边是主区。侧栏从上到下：家（形的座位与折叠按钮，不写应用名；家的可访问名称与提示是应用名）<!-- OD-3 -->；`primary` 段页面的导航（每页一行：图标、标题与可选的标记）；侧栏区里 `primary` 段的各项，这一段自己滚；底部只有一种排法，两行：上一行是 `utility` 段的页面，每页一个图标加名字的安静项，排成一行（照来源：一行排得下就是一行，排不下才换行，不截字）；下一行左边是侧栏区里 `utility` 段的各项（身份的账号块在这里），右边是翻面的墨记号与「外观」的图标钮；应用只有一面时没有墨记号。<!-- OD-22 --> 主区放每一页，别的页隐藏而不卸下，每一页在自己里面滚。
  - 连接正常时，外壳不画任何连接状态。连接断开时出现一行字，写原因，并说正在重连：已登录时在家的下面，未登录时在登录门的上方。重连中是一行中性的字加活动标记。这时只有这一处说话：别的界面（例如账号块）留着上一次知道的样子，不另说断开。<!-- OD-21 -->
  - 侧栏折成窄条时，每个控件是一个圆，名字成为右侧的提示；侧栏区里给了 `rail` 的项画 `rail`，没给的不画。账号的窄条样子让人在窄条里也能退出登录。
  - 宽度小于 768 时，导航变成从右边进来的抽屉，带遮罩与浮层的影子；换页或宽度越过 768 时抽屉自己关上。形不会没有座位：抽屉关着时，家站在页面上抽屉的开关旁边；抽屉开着时，家是抽屉里的那一个。<!-- OD-19 -->
- 地标：全页恰好一个主区 `<main>`，归外壳；登录之后侧栏是补充区，页面导航在它里面。界面模块放进来的内容不带 `<main>`。
- 形：外壳在页面里放共用界面件的形一次，并放两个座位：门（未登录与登录中）与家（已登录），优先级都是 1。对话头的座位由会话的界面模块用共用界面件的座位放，优先级 2。家是一个可按的控件：按它去次序最前的一页；待答数大于零时，去形口报告里的 `waitingPage`。外壳按外壳契约「形口」合并报告，把前台的活动、一次性的事实与待答数交给形，并把前台的活动写成一句隐藏的状态文字。
- 浮层：登录之后，外壳把 `float` 位置的各项各画在一个框里，框都在同一层：这一层固定铺满窗口，在两面之上（正面的页面与宽窗口的侧栏，或反面），在告知笺、窄窗口的导航、形、确认面板与菜单之下；这一层不接指针，框接。一项都没有时没有这一层。窄窗口里导航盖住主区时，这一层和主区一样不可操作。每个框的位置是「靠哪个角、离那两条边各多少像素」：缺省靠右下角，各 24；画的时候把距离夹到这一项整个在窗口里，窗口或这一项的大小变了就重新夹。人按住这一项标了可以拖的元素（只认主键、第一个指针），移动过 4 个像素才算拖：拖着时框跟着指针、带 `data-dragging`；松手时把落点换算成靠最近的那个角并记下，随后的那一下点吃掉；取消时回到拖之前的位置；没过 4 个像素就松手，照常是一下点。位置按项的标识存在本机的 `localStorage`（键 `omne.float.` 加标识），读不到、读不懂或存不进时用缺省。一项渲染时抛出，只有这一项不画。
- 两面：登录之后，外壳把正面（上面「已登录」的样子）与 `back` 位置的那一项（反面）都挂上，窗口的一生里都不卸下；翻面只换哪一面露着。收起的那一面带 `inert`，所以不接指针与键盘，它里面的座位不算看得见；它不用页面的 `hidden`，因为翻过去的那一刻，底下那一面要已经画好。没有人放反面时应用只有一面，下面的入口都不出现，按键也不翻。露着反面时那一项被撤下，外壳直接露出正面，不播翻面；记着的那一面不变，那一项回来时入口回来，外壳不自己翻过去。
  - 入口有四个：⌘⇧P（别的平台 Ctrl+Shift+P），两面上都听；正面侧栏底部的墨记号；反面那一项用 `turn()` 画在角上的记号；在反面对形按右键。应用菜单里不放翻面：主进程不向页面发消息（见「窗口」）。反面那一项坏了时，⌘⇧P 与对形按右键照常，所以总能翻回正面。
  - 停在哪一面是这台设备的偏好，存在本机的 `localStorage`（键 `omne.face`），只记正面或反面。`theme-boot.js` 在首帧之前读它，页面第一帧就停在那一面（DT-50）。第一次打开、读不到或读不懂时是正面；存不进时这一次照常，只是不跨启动。没登录时只有登录门，记着的那一面不动，登录之后照它停。记着反面、而连接还没有说开着什么时，外壳露着一张空的纸等着：反面那一项放上了就画它；定下来没有反面，就露出正面，记着的那一面不变。
  - 翻面的样子用共用界面件的翻面（见[共用界面的规格](../../packages/frontend/SPEC.md#纸的面)）。不给离开的那一面拍照，翻面层直接把活着的那一面朝对边压窄。翻完，外壳在隐藏的状态文字里说现在露着哪一面。
  - 在反面调 `navigate`（纸上点开一个会话、随身入口的「去对话页」都是），外壳先翻回正面，再切到那一页。
- 皮肤：人在用哪一套皮肤的选择按租户记在本机（键 `omne.look.<租户>`），是一段文字。应用只按租户存取这段文字（`storedTenantTexts`），把存取交给 plugin 的装载模块，自己不读它的含义；怎样读、读不懂怎样办归那个模块。本机存不了时这一次照常、只是不跨启动。外壳的「样子」由装载模块照它算出来之后告诉外壳（规则在 [Plugin 的规格](../../packages/plugin/SPEC.md#客户端的装载器)）。
- 告知笺：外壳把瞬时提示画成[告知笺](../../.meta_harness/design/ubiquitous_language/terms/interaction-and-dispatch.md#ul-told-note--告知笺--told-note)。<!-- OD-4 --> 形坐在家、侧栏展开时才写；同时只写最新的一条，后来的替换前面的。不写的时候提示直接丢掉，不排队，也不算进待答数。点告知笺等于调 `navigate` 去提示的动作指的页面；人去了那一页或点掉它，墨卷回口里。告知笺没有计时器。没有动作的提示，点它只收起。告知笺不盖住任何一行的字：外壳按家下面、第一行导航上面的空地给它定行数的上限，不少于两行，写不下的用省略号收住。<!-- OD-20 -->
- 外观：侧栏底部的「外观」打开应用的平样式菜单：主题三选一（浅色、深色、跟随系统），字号档四选一（小楷、中楷、大楷、老花）。每个选项自己就是回执。⌘= 大一档、⌘- 小一档、⌘0 回到中楷；别的平台用 Ctrl。不用 Electron 的缩放。主题切换时全局颜色不做动画。
- 字号档：外壳用共用界面件的字号档控制器，偏好存在本机的 `localStorage`（键 `omne.size`），读不到或存不进时当作中楷。`theme-boot.js` 在首帧之前按同一条规则写下 `data-size`（DT-40）。
- 键盘：页面开头有跳到正文的链接；F6 在侧栏、正文与侧边区之间走，只走露着的那一面；⌘⇧P 翻面；Escape 关上当前的浮层或墨框，焦点回到触发它的控件；鼠标打开的东西上不留焦点环。
- 主题：外壳用共用界面件的主题控制器，偏好存在本机的 `localStorage`（键 `omne.theme`），读不到或存不进时当作跟随系统。页面在入口脚本之前装入一个同源的小脚本 `theme-boot.js`，它在首帧之前按同一条规则定下明暗，页面不先以另一种主题闪一下。内容安全策略不为它放宽。
- 界面的令牌：一个令牌是 `--omne-` 开头、页面根上有值的自定义属性，或页面的样式表在选择器含 `:root` 的规则里给了值的这样一个名字。外壳把名字表报给 `shell.tokens`（`dataKeysOf('shell.tokens')`）：名字从页面的样式表里读，不另抄一份；按名字排，各带根上此刻的值，取不到值的给 `null`。读不到的样式表（跨源）略过；一张都读不到时答空表，不抛。认一个令牌名与这张表一致：表里有的都认。外壳整个应用这个部位（`shell.app`）的说明写成「窗口里的一切。换主题、换品牌色，就是给它放令牌。」，让找「主题」的人找得到它。
- 改过的颜色：整个应用上算数的令牌（`shell.app` 上胜出的那一项）存在本机的 `localStorage`（键 `omne.tokens`）。`theme-boot.js` 在首帧之前把它们写到根上，并在根的 `data-boot-tokens` 里记下写了哪几个：名字必须是 `--omne-` 开头，值必须过得了外壳核令牌值的那条规矩，过不了的不写。所以换过颜色的应用再起来，第一帧就是换过的颜色（DT-45）。
- 存与去的时机：这些令牌是运行中装上的 plugin 放的，页面起来时它们还没装上。所以页面在「要装的每一份都有了结局」之前不动本机存的，也不动首帧写在根上的；有了结局，把首帧写的去掉（从这里起由改动的样式表说），并把当时算数的存进去，之后每次变了都跟着存。没有算数的令牌时把这个键去掉。没登录、或登录的人退出了，去掉这个键与首帧写的：下一个人的第一帧不带上一个人的颜色。
- 样式：入口样式先引入共用界面件的汇总样式，再写外壳自己的版式；各界面模块的样式由装配文件引入。侧栏的版式与折叠动效取自参考项目，来历见 `src/page/shell/UPSTREAM.md`。外壳与界面模块的样式里，断点只有 768、1100 与对话区的 1160。
- 走查：`node apps/desktop/demo/page-walk.mjs [--shots <目录>]` 在全新的状态目录与空闲端口上起真的服务端、独立转发进程（与走查脚本同一个进程）与无界面的 Chromium，走注册、登录、侧栏与账号块、会话、停止一轮、资产页（切到资产，页签的字取自服务端，一份资产在列表里、点开有详情，同一个登录在页面之外新建一份技能时页面不用人动就列出它，在页面里选一个目录新建一份技能，列表里看它的简介，在详情里禁用、启用、移除，再选同一个目录同名新建，按页签打开各份资产的详情改一项再清除、设一个秘密项再清除、被锁定的一项没有控件，MCP 的页签与它的说明，页签里没有独立设置）、设置页（「日历与时区」一组，改一项并读回，再清除）、明暗切换、「待你决定」页读得出、退出、再登录，在页面里搜登录证明、密码与设过的秘密串，再走一轮失败后按「重试」接着做与工具卡参数的呈现；然后让一轮停在并行的两次 Ask 上（一次两题、一次一题）：对话页一张纸上有三张卡、一次摆一张、纸顶三个圆点与导航上的张数，「待你决定」页按会话分组是同一组卡；在对话页点圆点、按「下一题」与方向键翻题，翻题前后纸高与「下一题」钮的位置不变，再照「还差 n 题」翻到没答的逐张答齐、一次提交，三张卡都收起、两次 Ask 各自走完、这一轮接着走完；最后另一轮在「待你决定」页里答，对话页的卡随之收起，会话自己走完。页面走完之后，它用同一个登录直接调资产协议的「列出类别」。走查失败时打印服务端错误输出的末尾。它不进测试分层。
- 观感走查：`node apps/desktop/demo/visual-walk.mjs [--shots <目录>] [--scenes …] [--themes …] [--widths …] [--sizes …] [--series …] [--reduced]` 与页面走查同样起真的服务端（脚本化的模型）、独立转发进程与无界面的 Chromium，先种下验收数据（会话、一轮回复、工具调用、失败的一轮、一批问询卡、一个停在完成的回复上的会话、一次几十行输出的工具调用；在做的一轮与后台调用由各自的场景现开，在做的一轮由脚本化的模型把回复扣住一半；第一次登录的场景在种数据之前用另一个从没建过会话的账号注册、截图、再退出），再把每个场景按主题、窗口与字号截一张图，文件名是「场景号-主题-宽度[-字号]」；`--series` 改为录一段帧序列（带每帧的时刻），给动效逐帧量时长；`--reduced` 仿真减弱动效。共用的起法在 `demo/walk-support.mjs`。它不进测试分层。

### 窗口

- 窗口的网页偏好：`sandbox`、`contextIsolation` 开，`nodeIntegration` 关，`webSecurity` 开，没有预加载脚本。应用启动时开启沙箱。页面里没有 `require` 与 `process`，全局对象上没有应用另外放上去的东西。
- 页面不从 `file://` 加载。应用协议登记为标准、安全、支持 `fetch` 与流。静态文件由转发层发，路径逃不出构建好的页面目录；HTML 带内容安全策略，`connect-src` 只有应用自己，页面不直接连服务端。图片的来源除了应用自己与 `data:`，只多放行 `blob:`：媒体的界面模块经协议读回图片的字节，在页面里造成一个本页的地址来显示；别的指令不为它放宽。
- 导航到应用协议之外、新窗口与 `<webview>` 一律拒绝。权限只放行麦克风：请求的是媒体、而且只有音频时放行，供附件区按住录音；带视频的媒体与别的权限一律拒绝。打包的 macOS 应用在 Info.plist 写明麦克风的用途。被拒的导航与新窗口，地址是 `http`、`https` 或 `mailto` 时交给系统浏览器打开，别的地址不打开。
- 发行档的窗口关掉 DevTools。
- 窗口先不显示，页面画出第一帧时才显示。一秒之内没有第一帧也显示，窗口不会一直不出现。
- 主窗口持有一份答 2xx 的文档、加载完、并且显示出来时，主进程打一行 `main window loaded and shown`，每个进程一次。答错误状态的文档、加载失败后 Chromium 自己的错误页、隐藏的窗口都不算。macOS 锁屏时不发 `show` 事件，应用刚显示的窗口自报可见也算显示。
- 页面的文档加载失败或渲染进程意外结束时，应用自动重新加载一次。这次自动重新加载之后三十秒内再失败，应用不再自动重试，改为问人：重新加载，或关闭。页面没有响应时问人：继续等待、重新加载，或关闭。同一时刻只问一次。
- 问着「没有响应」的时候页面自己恢复了，或者页面崩了、加载失败了，这个问题收起，人选什么都不再动它；失败照上一条处理。
- 重新加载，不论自动的还是人选的，都等 utility 进程就绪再做：它在启动或在重启的退避里时，现在加载只会再失败一次。自动重新加载的额度在真的重新加载时才算用掉。等着的时候 utility 进程启动失败，不再等，改为问人。页面好好的时候 utility 进程换代，不动页面。
- 窗口关闭途中渲染进程没了，它既完不成关闭也否决不了，主进程直接销毁这个窗口，不交给恢复；页面否决了关闭的照旧。窗口没有响应与恢复响应各记一行日志。
- 窗口关闭时把位置、大小与是否最大化存进用户数据目录的 `window-state.json`。下次打开时，存的位置在某块屏幕上露出足够多才沿用，否则用缺省大小。文件读不出当作没存过，写不进就不存。
- macOS 上窗口隐藏标题栏：工作区顶上一条可拖的条，侧栏给窗口按钮留出 `--omne-window-inset`。别的平台用系统的标题栏，这个量是零；页面在浏览器里打开时也是零。
- 应用只开一个实例，再起一次时把已有的窗口提到前面；窗口全部关掉时应用退出。
- 应用退出带走 utility 进程。窗口关闭本身不停它。

### 构建档

构建档在构建时编进包里，运行时不选。`dev` 只由 `pnpm run dev` 以监视方式构建；`test` 是 `pnpm run start:test` 与 e2e 跑的；`release` 是唯一发出去的，也是慢层用例与独立转发进程用的。每档一个目录 `dist/<档>`，放页面、主进程与 utility 进程各一个自带依赖的包、一份 package.json，每个包旁记下模块清单与哈希；启动器拿不到别的档的包。一个档带什么由构建定：本档不带的模块在解析时换成同一契约的空实现，不靠运行时判断，也不靠摇树。

| 性质 | dev | test | release |
| --- | --- | --- | --- |
| 构建；打包 | `pnpm run dev`；不打包 | `pnpm run build:test`；`pnpm run package:test` | `pnpm run build`；`pnpm run package`、`pnpm run dist` |
| 启动 | `pnpm run dev` | `pnpm run start:test` | `pnpm run start` |
| 包；打包 | `dist/dev`；不打包 | `dist/test`；`out/test`，只解开 | `dist/release`；`out/release`，解开或安装包 |
| 压缩、`NODE_ENV=production` | 否 | 是 | 是 |
| 开发宿主（页面重建后重载、`<userData>-dev`） | 有 | 无 | 无 |
| 全局对象上的 `desktopBuildProfile` | 有 | 有 | 无 |
| Node 调试参数（`EnableNodeCliInspectArguments`） | 开（不翻 fuses） | 开 | 关 |
| 别的 fuses | 不翻 | 打包后与发行档相同；没打包不翻 | 翻 |
| Chromium 远程调试（`--remote-debugging-port`、`--remote-debugging-pipe`） | 允许 | 允许 | 拒绝：入口第一句就记一行 `remote debugging refused` 并以 97 退出，端点打开之前 |
| DevTools | 有 | 有 | 每个窗口都关 |
| Windows 上预写 cookie 密钥 | 否 | 是 | 是 |
| 签名与公证 | 否 | 否 | 还没配 |

每次启动主进程的第一行日志是 `{"buildProfile":…,"msg":"build profile"}`，自己起应用的启动器读它，Playwright 读全局对象上的档名，档不对就拒绝。主进程的未捕获异常与未处理的拒绝只记日志，不弹 Electron 阻塞的错误框。test 与 release 是同一份源码出的两份 JS：测试档上得到的结论，只在这张表说两档相同的地方算到发行档头上，其余由 `verify:build` 与 `verify:release` 守。

### 起法

- 命令的名字照一条规则：不带后缀的是发行档，测试档一律带 `:test`，开发是 `dev`。`build` 只出 JS，不碰 Electron；`package` 用 electron-builder 把 `dist/<档>` 组装成解开的应用并翻 fuses，不再构建；`dist` 在此之上出安装包，只有发行档有；`start` 起已经打好的包。构建、打包与验证都是 `apps/desktop` 的包脚本：仓库根只有跨成员的命令，不另设桌面应用的转发。

  | 动作 | 发行档 | 测试档 |
  | --- | --- | --- |
  | 构建 | `pnpm run build`：tsc 出独立转发进程一侧，再出 `dist/release` | `pnpm run build:test`：`dist/test` |
  | 打包 | `pnpm run package`：`out/release`，解开 | `pnpm run package:test`：`out/test`，解开 |
  | 安装包 | `pnpm run dist` | 无 |
  | 启动 | `pnpm run start` | `pnpm run start:test` |

- 仓库的构建与测试跑的是 `pnpm run build`，慢层用例因此测发行档的包。e2e、`start:test` 与 `package:test` 要先跑 `pnpm run build:test`；缺哪一样，命令说要先跑哪一条。分步走一遍的次序：`build`、`build:test`、`verify:build --no-build`、`package:test`、`package`，最后 `verify:release --no-build`，两档各构建一次，打包的就是验过的那份。
- `pnpm run start [Electron 参数]` 起 `out/release` 里打好的应用，像人双击那样：不加任何测试开关，不另给用户数据目录，用安装的应用的用户数据目录与系统的钥匙串或密钥库，受单实例锁约束，同名的应用已在跑就只是把它叫到前面。参数照原样传给应用。没打包就说先跑 `pnpm run package`，不退回没打包的 Electron。Linux 上沙箱起不来就说原因并以 1 退出，带了 `--no-sandbox` 也不起。应用的退出码原样传出，被信号结束时返回 128 加信号号；终端的 Ctrl+C 同时到应用与启动器，启动器等应用自己退出，单独发给启动器的 SIGTERM 与 SIGHUP 转给应用。只想看一眼又不碰自己的数据，就自己给 `--user-data-dir=<空目录>`，macOS 上再给 `--use-mock-keychain`。
- `pnpm run start:test [--packaged | --app <可执行文件>] [--user-data-dir=<目录>]` 起测试档，缺省没打包；缺省用一个一次性的用户数据目录，应用与它的辅助进程都确认退出后删掉，确认不了就留下并以 1 退出；要留登录就给 `--user-data-dir=`。应用以 0 退出却没在用户数据目录里写下任何东西，判失败。主进程退出后，辅助进程还占着输出，3 秒后不再等，收掉它们并以 1 退出。服务端地址取环境变量 `OMNE_SERVER`，缺省是 `http://127.0.0.1:8787`。
- `pnpm run dev` 以监视方式构建 dev 档。页面重新构建后，应用里的开发宿主重载窗口；主进程或 utility 进程的包重新构建后应用重启。两种情形登录都还在，因为它在 cookie 里。关掉窗口，监视随之结束；应用崩溃或被信号结束时，`pnpm run dev` 以非零的状态退出。
- dev 档的用户数据目录是应用数据目录下的 `<应用名>-dev`，不和安装的应用共用，也不顺带建出安装的应用的目录。测试启动每次都用自己的 `--user-data-dir`。
- 所有启动经 `scripts/launch.ts`：它定可执行文件、参数、工作目录与环境，从继承的环境里去掉 `ELECTRON_RUN_AS_NODE`、`ELECTRON_NO_ATTACH_CONSOLE` 与 `NODE_OPTIONS`。测试启动另加隔离开关：假钥匙串或固定密钥（见登录 cookie），macOS 上 `-ApplePersistenceIgnoreState YES`，免得应用启动途中崩过之后，下一次停在「要重新打开窗口吗」的系统询问上。打包的应用先读回 fuses，不是测试档那一列就不起。
- Linux 上先真的试建一个无特权的用户命名空间，判断 Chromium 的沙箱起不起得来：以 root 运行、建不出用户命名空间、AppArmor 限制，并且 `chrome-sandbox` 不是 root 所有的 4755，就起不来。起不来时测试与开发启动加 `--no-sandbox` 并在 stderr 说一次原因；`pnpm run start` 与 `verify:release` 不加，见各自一节。
- `pnpm run start:test` 与 `pnpm run dev` 把应用放进它自己的进程组。`start:test` 在终端按 Ctrl+C 时信号只到启动器，启动器只把它转给应用的主进程，应用自己退出：同时杀掉辅助进程会让 GPU 进程在主进程还没退完时死掉；第二次再转一次，第三次杀掉应用的进程组，主进程已退出而辅助进程还占着输出时，第二次就杀。Windows 上没有这些信号，每一次都结束应用的整棵进程树。`pnpm run dev` 收到 Ctrl+C 或 SIGTERM，或构建档不对时，只给应用的主进程发 SIGTERM，让它先把 cookie 写盘再收掉辅助进程；3 秒内不退就杀掉它的进程组（Windows 上直接结束整棵进程树）。重启进行到一半时也一样，等新旧应用都退出之后才退出。因重新构建重启应用时，旧应用照这样结束，新进程在它退出之后才起。
- `electron` 包没有安装脚本，装依赖时不下载二进制。第一次 `pnpm run start:test` 或第一次跑 `electron-window` 用例时，包自己把二进制下载到 `node_modules/electron/dist`，本机缓存里有同版本的压缩包就不联网。要提前备好，在 `apps/desktop` 下跑 `pnpm exec install-electron`。
- 主进程入口不在顶层等 `app` 就绪：Electron 在入口模块的顶层 `await` 完成之前不发就绪事件。
- 独立转发进程：`omne-desktop-host [--server <origin>] [--port <port>]`，地址与端口也可以取环境变量 `OMNE_SERVER` 与 `OMNE_DESKTOP_PORT`。它发 `pnpm run build` 出的页面；页面不分档，各档的页面是同一份。
- `src/` 下每一部分一个目录：

  | 目录             | 部分                              |
  | ---------------- | --------------------------------- |
  | `src/shared`     | 共享类型                          |
  | `src/forwarding` | 转发层                            |
  | `src/standalone` | 独立转发进程                      |
  | `src/main`       | 主进程                            |
  | `src/utility`    | utility 进程的入口                |
  | `src/port-fetch` | 进程间传输                        |
  | `src/page`       | 页面；界面外壳在 `src/page/shell`，截图的遮罩页在 `src/page/shot` |

  构建、启动、打包与验证的脚本在 `scripts/`，主进程与脚本共用的启动信号在 `src/startup-signals.ts`。

### 打包

- `pnpm run package` 把 `dist/release` 打成解开的应用到 `out/release`；`pnpm run package:test` 把 `dist/test` 打到 `out/test`；`pnpm run dist` 把 `dist/release` 打成安装包：macOS 是 dmg 与 zip，Windows 是可以选安装目录与安装范围的 NSIS，Linux 是 deb 与 rpm（rpm 要本机有 `rpmbuild`）。安装包只出发行档。三者都不构建，打的就是 `dist/<档>` 里现有的包，没有就说先跑哪一条构建。只打一个平台，给 `dist` 加 `--mac`、`--win` 或 `--linux`。Windows 安装包要在 Windows 上打：electron-builder 26 在 macOS 上交叉打出的安装包能装、应用能跑，但没配应用图标时卸载程序过不了 NSIS 的完整性检查（electron-userland/electron-builder 的 issue 10258，27 版修复）。
- electron-builder 的配置分 `electron-builder.base.mjs` 与两份各自写全应用目录与输出目录的 `electron-builder.test.mjs`、`electron-builder.release.mjs`。它打的就是 `dist/<档>`，去掉源码映射与模块清单；应用里不装 `node_modules`。唯一的原生二进制是截图库在构建平台上的那一个（`scripts/native-binaries.ts` 照 napi-rs 的平台包名找到它），放在 asar 之外的 `resources/native/node-screenshots.node`；找不到时打包失败，不打出一个截不了屏的应用。打包器把 `node-screenshots` 当外部模块，不打进主进程的包。
- 应用名、包名与 `appId` 在 `product.json` 里只写一次，都是可移植的文件名：electron-builder 不改写它们，可执行文件的路径照它的缺省名字算。应用名决定用户数据目录。
- fuses 一张表两列，在 `scripts/fuses.ts`：不能以 Node 运行，不认 `NODE_OPTIONS`，只从自己的 asar 加载且核对它的完整性，cookie 加密打开。测试档只多开 Node 调试参数，Playwright 的 Electron 驱动要靠它接上应用。两档都在打包后翻上并逐个读回，没翻上打包失败。
- Windows 安装包（`nsis/installer.nsh`）不碰不是它装的文件。首次安装只接受空目录或不存在的目录，读不了的目录也拒绝；升级只接受注册过、且卸载程序按文件删除的那一份安装。卸载与升级只删打包时列下的文件（`scripts/nsis-files.ts` 在打包后写出 `out/nsis/<架构>.nsh`，编进卸载程序），目录空了才删，用户自己放进去的文件留下。安装路径或已装目录里有目录链接就拒绝。删不掉的文件报出 Windows 错误码并停下，卸载程序与注册都留着，可以重试。没有这份记录的旧安装不替用户调用它的递归卸载程序，而是拒绝并请人先备份、处理旧安装。登记的安装目录在一块本机固定盘上、盘读得到而目录整个不在了，这份登记算过期：新的安装目录验过之后，删掉过期的登记、不调用它的卸载程序，按首次安装继续；登记的路径为空、盘不可用（可移动盘或网络盘上的目录不在也算）、读不了，或目录还在而没有按文件删除的卸载程序，都拒绝。这些检查在 electron-builder 选定装给当前用户还是所有用户、做完需要的提权之后才跑，并且在卸载旧版本、解开任何文件之前；靠 `patches/app-builder-lib-nsis-destination.patch` 给 `app-builder-lib` 加的入口调用，同一个补丁让安装包初始化时不在安装目录里建东西，静默安装的 `/D` 因此不会在检查之前把不在的目录建出来。旧的安装包可能已经建出了一个空目录：确认它是空的、挪开之后再用新的安装包重试。
- 打出 Windows 安装包之后，`scripts/installer-receipt.ts` 在它旁边写一份按架构的 SHA-256 回执，把安装包与这次打包的可执行文件、`app.asar` 绑在一起；`verify:release --no-build` 拿它核对要发出去的就是验过的那一份。
- 三个平台都不签名。macOS 上翻 fuses 之后重做临时签名，arm64 的应用没有签名起不来；打 universal 包时 electron-builder 先为每个架构各打一份临时切片，切片上不重做签名，否则合不成一份。正式签名、公证、发行渠道与自动更新不在本应用里。Linux 的 deb 要维护者的邮箱，`product.json` 还没有，`pnpm run dist --linux` 现在会报错。

### 端到端用例

- `pnpm run test:e2e` 经 Playwright 的 Electron 驱动起测试档，对一个真的服务端与替身模型网关走一遍：注册、发一条消息、看到回复、页面读不到登录 cookie 与 Node；退出再打开，凭 cookie 直接进工作区，并读落盘的 cookie 库：打包的应用的值只在加密的一列，没打包的是明文。
- 两个目标：`unpackaged` 起 `dist/test`，要先 `pnpm run build:test`；`packaged` 起 `out/test` 的应用，还要先 `pnpm run package:test`，开跑前先单独读回它的 fuses，不对就一个打包的用例都不跑。每次启动核对应用报的档是 test、用的是给它的用户数据目录，Linux 上核对用的是固定密钥。
- 每个用例用一个新建的用户数据目录，用完删掉；它起的应用在用例结束时退出。同一时刻只起一个应用。开跑时这个检出的应用已经在跑，或 macOS 在前台的会话锁着屏，拒绝开跑。每个用例只关自己起的应用：关不掉时杀掉它与 Playwright 为它建的进程组，等它们退出；确认不了退出就留下它的用户数据目录。跑完按路径还看得到这个检出的应用，只判失败不杀，那可能是另外手动起的。它不进测试分层。

### 发布前验证

- `pnpm run verify:build [--no-build]` 构建 test 与 release 两档，对每个包核对两样。模块清单：每个包旁边记着它的档、包名、文件哈希、完整的依赖图（被摇掉的模块也在内）与实际产出代码的模块，记录的档、包或哈希对不上就要求重新构建；本档排除的模块不在任何一个包的依赖图里，导入它的包换成了空实现；本档该有的，导入它的包实际产出了它的代码，并且没有空实现。文本：别的档的标记不在本档任何一个包里，本档的标记至少在一个包里，按整词找——发行档有拒绝远程调试的那句与关掉 DevTools，没有 `desktopBuildProfile` 与开发宿主，测试档反过来；两档都没有没替换的档名与运行时的 `NODE_ENV` 分支；发行档里出现的 `OMNE_*` 名字只许是发行档读的那几个（`RELEASE_OMNE_ENV`），新加的调试变量因此进不了发行档。测试档是文本标记的阳性对照，另在临时目录构建一份 dev 档作模块清单的阳性对照。加一项调试能力，就把它放进 `PROFILE_ENTRIES` 或加一个标记。
- `pnpm run verify:release [--no-build] [--distribution] [--allow-no-sandbox]` 是唯一自动起发行档的地方，缺省先依次跑 `build`、`build:test`、`package:test` 与 `package`（Windows 上带 `--distribution` 时是 `dist`），两档各构建一次、打的就是第 2 项核对的那份，再从外面做五项，每项一行 pass、fail 或 skipped 带理由：
  1. fuses：从二进制读回，是发行档那一列。
  2. 包内容：最终的 app.asar 恰好是 `dist/release` 的文件，逐字节相同、包内记的完整性对得上；package.json 从主进程包进；旁边没有解开的目录；macOS 上 Info.plist 记的 asar 完整性是它的头；`dist/release` 与作对照的 `dist/test` 过 verify:build，包里实际发出去的包的文字也过发行档的文本核对。
  3. 拒绝远程调试：带两种开关各起一次，都以 97 退出、主进程只打一行拒绝、端口不接受连接、管道不答、不留进程；测试档同样起一次作阳性对照，它必须答，否则这一项失败。
  4. 启动冒烟：在新的用户数据目录上起，30 秒内报 release 档并打出主窗口就绪行；从外面请它退出（SIGTERM，Windows 上不带 `/F` 的 taskkill）要以 0 退出、它建出的进程全部离开、看得到主进程、渲染进程与它自己的 utility 进程；只写进给它的目录，安装的应用的用户数据目录前后不变；Windows 上新目录要有一次存下密钥与一次核对，别处一行都不能有。macOS 锁屏时跳过。
  5. 签名与公证：本地未签名的包跳过；`--distribution` 时 macOS 要 Developer ID 签名、公证并装订、Gatekeeper 接受，Windows 要应用与 `out/release` 里的 NSIS 安装包两者的 Authenticode 都有效，安装包还要与它的回执对得上。Linux 没有这一项。
- Linux 上沙箱起不来时跳过 3 与 4 并说怎样打开，`--allow-no-sandbox` 让它们不带沙箱跑并在结果里写明。只数启动自己建出的进程：起之前先列一次进程，再看开始时间、父进程与进程组；不在父子关系与进程组里的，可执行文件的路径对、并且命令行带着这次启动自己建的用户数据目录才算，同一个 Electron 上别的启动器起的应用不算（`start:test` 收尾同样这样认）；Windows 上杀一个进程之前先按创建时间认准它，不碰复用了 PID 的别的进程。起不来时报出原因。辅助进程确认都退出了才删它们用的临时目录，确认不了就留下目录并判这一项失败；被打断时同样先杀、再确认、再删。退出码：0 验过；1 有失败；2 不完整，1 到 4 有跳过，或要发行时 5 跳过。

## 原则与约束

- 页面的代码读不到登录证明。新增任何路径、答复字段、头、日志或错误文本，先确认它不带登录证明与密码。
- 转发层不记登录。它需要的关于登录的一切都从这个请求的 cookie 里读。
- 转发层只认 `Request` 与 `Response`：不导入 `electron`，不导入 Node 的 HTTP 模块，不认识自己跑在哪种承载上。
- 主进程不做业务：它映射地址、保管 cookie、补来源、关联取消、管 utility 进程与窗口。它不读协议契约，不读正文。
- 转发层是看门人，不是代理：只转发声明过的目标，拿不准就答「没发出」，不猜着放行。
- 页面与共享类型不导入转发层、主进程与 utility 进程的代码，也不导入 Node 内置与 `electron`；这三处不导入页面；界面外壳不导入任何领域。
- 结果不知道就是不知道：页面证明不了没发出的，答不确定；注销结果不确定时如实告诉页面。
- 界面模块随协议客户端「挂没挂着」加载与卸载；能不能用由服务端在每次调用时判断。
- 新增一个领域的界面只改装配文件与协议清单，界面外壳与转发层不变。
