# @omne-harness/desktop

## 总体架构

桌面应用回答一个问题：一个人怎样在窗口里使用系统，而页面的代码读不到登录证明。它由两半组成。页面是客户端的 Cordis 树，树上有界面外壳与各领域的界面模块。页面之外的那一半替页面做三件事：把登录证明放进页面读不到的 cookie，把页面的请求带上凭据转给服务端入口，把构建好的页面发给浏览器。

这三件事的全部逻辑在转发层里。转发层把页面的请求适配成服务端入口的调用，带上凭据转发。它是一个 Hono 应用，只认 `Request` 与 `Response`，不认识承载它的进程。它有两种承载，页面不变。桌面应用里它跑在 utility 进程，由主进程把请求送进去，不开任何端口。另一种是独立转发进程：人在命令行启动的一个 Node 进程，在回环地址上监听，让普通浏览器打开页面。独立转发进程只用于开发与走查。

本规格给每一部分一个名字，不用「宿主」统称页面之外的那一半：

| 部分         | 回答的问题                                                                                           |
| ------------ | ---------------------------------------------------------------------------------------------------- |
| 共享类型     | 页面与转发层之间的路径与字节；两边读同一份协议清单                                                   |
| 转发层       | 登录怎样变成一枚 cookie；一个页面请求能不能转发、带什么凭据；一页的多条观察怎样合成一条流            |
| 独立转发进程 | 开发与走查时，一个单独的 Node 进程怎样在回环地址上把转发层交给浏览器；它不是 utility 进程            |
| 主进程       | 怎样把应用协议的请求送进 utility 进程里的转发层，怎样保管 cookie，窗口怎样加固与恢复                 |
| utility 进程 | 桌面应用里承载转发层的子进程，属于整个应用，不属于哪个窗口；它怎样启动、就绪、停止与重启             |
| 进程间传输   | 主进程与 utility 进程之间怎样在一个消息端口上传 `Request` 与 `Response` 的流，怎样限速与取消         |
| 页面         | 页面这一侧的传输怎样接到客户端的树；界面外壳怎样画出插入位置里的东西；装配文件列出哪些协议与界面模块 |

下文的「外壳」是界面外壳的简称。本规格不用「宿主」指应用的任何一部分。

一次调用这样走：界面模块调协议客户端，协议客户端经页面的传输发一个同源的 `POST`。浏览器自己带上 cookie。转发层读出 cookie 里的登录证明，按协议契约核对目标并决定带什么凭据，再发往服务端入口。桌面应用里多两跳：应用协议的请求先到主进程，主进程注入 cookie，经进程间传输送到 utility 进程。

## 领域边界

本应用拥有：登录 cookie 的内容与它什么时候签发、什么时候清除；转发层的转发规则；页面与转发层之间的路径与字节；一页一条事件流的合流规则；界面外壳（服务 `shell` 的实现、版式、当前页面、租户的存放、主题偏好）；页面的装配；窗口。

本应用不拥有：身份、会话、设置项与人工介入的规则与协议，它们归各自的包组与协议契约；连接、客户端的树与协议客户端怎样随可用性长出与收回，归接入的客户端核心与客户端装配；对话界面、待你决定的界面与设置界面归各自领域的界面模块。界面外壳与转发层都不认识任何领域：转发层只读协议契约里每个操作的身份要求。

本应用需要别人做的：

| 需要                 | 对方                                                          | 本应用需要它做什么                                                                                                                                                                      |
| -------------------- | ------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 客户端核心与连接     | 接入（SDK 与客户端装配）                                      | 给出传输接口与连接插件；客户端的树随服务端入口挂着的协议长出与收回协议客户端；给出登录状态源的接口                                                                                      |
| 协议契约             | 身份、会话、人工介入、资产、工具、日程、日历、通知、模型      | 声明每个操作与观察的身份要求，以及哪些操作携带凭据；转发层与页面读同一份清单                                                                                                            |
| 外壳契约与共用界面件 | 前端（`shell-contract`、`ui-kit`）                            | 插入位置、服务 `shell` 的抽象类与存放规则 `createSlotStore`；控件、样式 token 与主题控制器                                                                                              |
| 界面模块             | 身份、会话、人工介入、资产、MCP、通知、日程、日历、工具、模型、工作区 | 各自是客户端树上的插件，自己注入协议客户端或别的界面模块提供的口，往插入位置里放东西：登录门与账号块、会话列表与对话页、待你决定页、资产页与设置页、资产页上 MCP 的页签、日程页、日历页、工作区页 |
| 服务端入口           | 接入（服务端）                                                | 按协议名、主版本与名字承载调用与观察；在身份协议上答复登录、注销与当前租户                                                                                                              |

本应用不为别的包组实现端口。

## 心智模型

把转发层想成一个只认识几份协议契约的看门人，把页面想成一个拿不到钥匙的访客。钥匙是登录证明，放在一枚页面的脚本读不到的 cookie 里。页面每发一个请求，浏览器替它把这枚 cookie 交给转发层。转发层对每个调用与观察只问三件事：这个目标是不是我认识的契约里声明过的；它是不是一个携带凭据的操作；按契约它该带什么凭据。

转发层不记任何登录的事。它知道的全部来自这一个请求带来的 cookie。所以承载它的进程重启不丢登录，两个进程里的转发层可以服务同一个浏览器。

最容易想错的四处：

- 退出总会清掉 cookie，哪怕服务端是否注销不确定。
- 一次 `denied` 不等于登录失效。页面收到 `denied` 之后问一次登录状态，转发层用同一个证明查一次当前租户。它也答 `denied` 才算失效。
- 页面发往转发层的请求失败时，页面证明不了字节没有发出，除非转发层在转发前就拒绝了它。
- 页面读不到 cookie，不等于页面里的代码做不了事。页面里的任何代码都能以这个人的身份发起契约里声明过的操作。cookie 只保证证明带不走。谁的代码能进页面，由装配决定。

界面外壳与界面模块之间的关系是「挂没挂着」：一个界面模块要的协议客户端在树上，它才加载，往插入位置里放东西；协议撤了，它卸载，放的东西随作用域撤掉。这是 Cordis 的依赖注入本来就做的，界面外壳不判断哪个协议开着。切换页面只是藏起别的页面，不是卸下，所以看一眼设置不会打断对话里正在进行的一轮。

## 应然设计

### 登录 cookie

- 登录证明只在一枚 cookie 里，名字是 `omne_login`。它的值是一段 JSON 的 base64url：登录证明、行事租户、登录标识。行事租户取签发成功体里的租户。
- 属性：`HttpOnly`，`SameSite=Strict`，`Path=/bridge/`，`Max-Age` 是一年（31536000 秒）。应用关了再开，登录还在。
- `Max-Age` 不是登录的有效期。登录有效不有效由服务端定：每份登录在签发时冻结了最长截止时刻与空闲截止时刻，到期、被撤销或换了凭据之后服务端答 `denied`。cookie 只保证证明不先于服务端的截止时刻丢掉。
- 页面启动时问一次登录状态。服务端认这份登录，页面直接进「已登录」；不认，转发层清除 cookie，页面回登录门并显示原因。
- 证明因此落在本机，以明文存在应用的用户数据目录里，保护它的只有这个目录的权限。现在没有加密：加密要靠打包时打开 Electron 的 cookie 加密开关，本应用还没有打包这一步。做打包时要一并打开它。
- 转发层是唯一写这枚 cookie 的地方，写的时机只有三个：登录成功时签发；退出时清除；确认登录已失效时清除。
- cookie 读不出（不是 base64url、不是 JSON、缺字段、超过长度上限）当作没有 cookie，并在这次答复里清除它。

对一个请求，转发层只看它有没有带来读得出的 cookie：

| 事件                         | 请求没有 cookie                              | 请求带着 cookie                                               |
| ---------------------------- | -------------------------------------------- | ------------------------------------------------------------- |
| 页面请求登录                 | 发出登录操作                                 | 拒绝：已经登录                                                |
| 登录的答复是成功             | 签发 cookie。只告诉页面「登录成功」          | 不可达                                                        |
| 登录的答复是其他结果，或未知 | 不签发。把结果如实告诉页面，未知就说未知     | 不可达                                                        |
| 页面请求退出                 | 直接答「已经退出」                           | 发出注销操作，目标是 cookie 里的登录标识                      |
| 注销的答复是成功或无变化     | 不可达                                       | 清除 cookie，答「已经退出」                                   |
| 注销的答复是其他结果，或未知 | 不可达                                       | 仍然清除 cookie。告诉页面：本机已退出，服务端是否已注销不确定 |
| 页面问登录状态               | 答「未登录」                                 | 用 cookie 里的证明查一次当前租户，按下一张表答                |
| 页面请求一次普通调用或观察   | 不带登录证明发出。需要登录的操作由服务端拒绝 | 按契约带上凭据发出                                            |

页面问登录状态时，转发层查当前租户得到的结果：

| 查询的结果           | 转发层怎样答                                      |
| -------------------- | ------------------------------------------------- |
| 成功                 | 「已登录」                                        |
| `denied`             | 清除 cookie，答「未登录」，并说明原因是登录已失效 |
| 其他结果，或结果未知 | 「已登录」，并说明这一次没有核实                  |

- 登录的结果对页面只有四种：登录成功；统一认证失败答认证失败；`unknown` 与本地的结果不确定答未知；其余（字节没发出、依据不可用、本部署不提供、协议拒绝、契约读不出的消息体、已经登录）答不可用。退出的结果只有两种：已经退出，未知。答复的正文只有结果字段，登录证明只出现在 `Set-Cookie` 头里。
- 登录操作是身份协议的签发登录，注销是撤销登录。
- 登录或注销的调用抛出异常时：登录不签发 cookie；注销仍然清除 cookie。异常不原样交给页面，答复是「未知」。
- 同一个证明同一时刻至多一次查询在途：同一个进程里的转发层，带着同一个证明来的并发询问共用一次查询的结果。结果不缓存。
- 登录状态里一并说出转发层认识的协议（名字与主版本）。页面拿自己的协议清单比对，页面要用而转发层不认识的，或者转发层根本没说，页面顶上写一句「应用的版本旧了，需要重启。」并列出少的那几样，不像这项能力不存在那样静默。

登录中与退出中不再是转发层的状态。它们是页面自己的状态，见「页面」一节。

### 转发规则

- 转发层只转发它认识的契约里声明的操作与观察。认识的契约是 `access/v1` 加页面的树带着的那一份协议清单，页面与转发层读同一份。目标按协议名、主版本与名字三样精确比对。不认识的协议、认识的协议里没有声明的名字、标了携带凭据的操作，一律答「字节没发出」，不带任何东西发往服务端。
- 转发层读契约有两个不能省的理由。第一，每个操作带什么凭据写在契约里：不要身份的什么都不带；要登录的只带登录证明；要行事租户的带登录证明与行事租户。第二，签发登录这一类操作的答复正文里有登录证明，页面经普通调用拿到它，cookie 就白藏了。
- 凭据只从这个请求的 cookie 里取。页面在正文或头里自带的凭据被丢弃。

### 页面与转发层之间的路径

- 路径都在 `/bridge/` 之下：调用、开观察、停观察、事件流、登录、退出、登录状态。其余 `GET` 是构建好的页面静态文件。
- 调用的答复是传输的三种结果之一：答复了（结果与体）、没发出、不确定。登录与退出的答复只有结果字段。问登录状态是一个 `POST`，一问一答，不是一条流：它会向服务端发一次查询，还可能清除 cookie，所以不用 `GET`。
- 一个页面的全部观察走同一条事件流（`GET` 带页面自取的标识）。开一条观察与停一条观察是两个普通 `POST`，带页面给这条观察取的标识，事件按标识分发。原因：服务端入口是 HTTP/1.1，一个观察一条流；浏览器对一个地址只保持几条连接，每条观察各占一条长连接时，开着的观察一多，调用就排不上。
- 事件流的请求一到就返回响应头，不等上游。开观察的 `POST` 登记之后立刻答复，上游的观察在答复之后才开。
- 这一页还没有事件流时开观察答 `409`，什么都不转发。事件流断了，转发层取消挂在上面的全部观察，页面把它们都读作不确定，下一条观察重新开一条事件流。
- 事件流按页面读的速度写。转发层为一条事件流攒下的还没被读走的字节有上限，上限是转发层里的一个常数（1 MiB）。一帧放得下才放进去，放不下就等页面读走，这期间不从这条流上各个上游的观察取下一帧。单独一帧比上限大时，它等到流里空了独自放进去。
- 页面一直不读时，积压留在服务端入口。服务端入口的规则是积压碰到它的字节上限就结束这条观察。转发层把上游给的结束原因原样交给页面，页面照常把它当作一条结束了的观察重新开。转发层不替上游编一个结束原因。
- 一页的观察共用一条流，所以它们互相排队：一条观察的帧很多时，别的观察的事件排在它后面。这是合流的代价，换来的是调用不被长连接挤占。
- `POST` 只收 JSON，并且必须带同源的 `Origin`，不带的被拒绝。挡住别的来源的是这条检查，不是 cookie 的 `SameSite`：`SameSite` 不看端口，本机另一个端口上的页面算同站，它发来的请求照样带着 cookie。所以每一个有效果的路径都是 `POST`。
- 用一份登录证明开的观察不留到这份登录之后。退出时，以及确认登录已失效时，转发层结束每一页上用这份证明开的观察，结束原因是 `denied`。不要身份的观察不受影响。
- 登录证明与密码不进日志，不进错误信息。日志一事一行：被拒的请求只写方法、路径与 `Host`、`Origin` 两个头；失败的请求只写方法、路径与失败的种类，不写错误的原文，因为原文可能引用消息体。日志从不写消息体、cookie、证明或密码。
- 页面发往转发层的请求失败时，只有转发层在转发前答出的拒绝能证明字节没有发出；其余失败，调用答不确定。

### 独立转发进程

- 它只用于开发与走查：在浏览器里调页面，以及走查脚本驱动无界面的浏览器。它不是给人日常使用的交付面，不随发行的应用提供。它和 utility 进程没有关系，桌面应用不启动它。
- 一个 Node 进程在回环地址上监听，把收到的请求交给转发层。它只监听回环地址。
- `Host` 头必须是回环名字（`127.0.0.1`、`localhost`、`[::1]`），端口不核：挡住重绑定页面的是名字，经端口转发打开时浏览器看到的是另一个端口。
- 页面断开连接时，还没答复的调用被取消，开着的事件流被取消。
- 已知的限制，启动时打印在第一行：登录 cookie 在浏览器自己的 cookie 库里。cookie 不按端口隔离，浏览器把它带给 `127.0.0.1` 上任何端口的 `/bridge/` 路径，所以这台机器上别的本机网页服务能收到登录证明。不要用它登录一个要紧的账号，不要在不信任的机器上用它。桌面应用没有这条限制，它不开端口，cookie 不进浏览器。

### 主进程与 utility 进程

- 页面在应用自己的协议下（`omne-app://app`）。主进程登记这个协议，把每个请求映射到一个内部的 HTTP 源，经进程间传输送进 utility 进程。utility 进程里跑转发层。这条路径上不开任何 TCP 监听，别的程序与别的网页够不着转发层。
- utility 进程由主进程在应用启动时拉起，一个应用一个。它属于应用，不属于窗口：窗口关了再开、页面重新加载、渲染进程崩了，它都照常；应用退出时主进程停掉它。有多个窗口时它们共用同一个 utility 进程与同一个 cookie 罐，各自的事件流按页面自取的标识分开。
- 窗口用应用专用的一个持久会话，cookie 罐建在这个会话上，应用协议也登记在它上面。
- Chromium 不替应用协议下的页面保存 cookie，也不给它的请求发 `Origin`。所以主进程做三件事：
  - 保管 cookie。转发层答复里的 `Set-Cookie` 存进主进程的 cookie 罐，存好并写到磁盘之后才把答复交给页面，下一个请求就看得到。应用退出前再写一次，等它有时限。主进程给每个请求注入 `Cookie` 头。页面自带的 `Cookie` 头被剥掉。页面的脚本没有 `document.cookie`。
  - 补上来源。请求到达协议处理函数，说明它来自应用自己的页面，因为窗口不离开应用协议。主进程给非 `GET` 的请求补上内部源的 `Origin`。页面自带的 `Origin` 不被采信。
  - 关联取消。处理函数收到的请求自带的取消信号不触发。主进程在请求发出前给它盖一个头，值是本次启动的随机前缀加网络请求的编号，页面自带的同名头被换掉。页面在响应头之前放弃请求时，主进程从网络请求的错误事件得知，按这个头找到这次请求并取消它。响应头之后，取消经响应正文那条流传到。
- utility 进程有明确的状态：空闲、启动中、运行中、停止中、已停止。并发的启动共用同一次就绪。启动到就绪有时限，停止有宽限期。utility 进程意外结束时主进程重启它，开着的请求以失败结束，页面读作不确定。因为转发层不记登录，重启之后人不用重新登录。
- utility 进程不在的时候，页面自己的文档请求算一次加载失败，由窗口的恢复重新加载。别的请求照常得到一个表示失败的状态，页面读作不确定。文档请求要是也答一个状态，窗口会把那一行失败的文字当成加载好的页面留在那里。
- 进程间传输在一个消息端口上按请求编号复用，传 `Request` 与 `Response` 的头、状态与双向的正文。每条正文有字节窗口：发出而没被确认的字节到了上限，发的一方等着。取消、端口关闭都在两端各清理一次。
- 进程间传输不给请求加时限，等响应头、两帧之间、整个请求三样都不设。一次调用要等服务端答完才有响应头，接入层与客户端核心都没有给调用规定时限，结果丢了按「不确定」认回。传输自己掐断一个慢而合法的调用，是把一个会有答复的调用变成不确定。停不下来的请求由另外三条路收：页面放弃时主进程取消它；utility 进程结束时端口关闭，开着的请求以失败结束；应用退出。

### 页面

- 客户端的 Cordis 树装着连接插件与清单里每份协议的协议客户端。连接插件的传输是页面到转发层的同源 HTTP。读到「暂时没有可读的」时按可配置的再问策略等待，次数与总时长都有上界。
- 登录状态归页面。它有四个取值：未登录、登录中、已登录、退出中。页面请求登录时进「登录中」，请求退出时进「退出中」。登录中与退出中，页面不发新的登录与退出。
- 页面启动时问一次转发层的登录状态，得到未登录或已登录，然后才画登录门或工作区。问不到时按退避重问，这期间页面只说正在连接，不进登录门：页面可能比转发层先就绪，这时把人放到登录门前是错的。
- 登录的答复是「登录成功」，页面进「已登录」。答复是「认证失败」，页面回「未登录」。答复是其余任何一种（未知、不可用），页面不自己下结论，问一次登录状态，按它答的进「已登录」或「未登录」：这次登录可能已经签发了 cookie 而答复丢了，这时再登录一次只会被答「已经登录」。
- 退出的答复到了，页面进「未登录」。
- 页面在三种时候再问一次转发层的登录状态：一次调用答 `denied`；一条观察以 `denied` 被拒或结束；页面的事件流断了又连上。转发层答「未登录」时页面进「未登录」，并显示转发层给的原因。同一时刻至多一次询问在途。问不到时页面的登录状态不变。
- 树上另装外壳的服务 `shell` 与装配文件列出的界面模块。外壳实现外壳契约的 `ShellService` 与 `ShellSlots`：受保护的 `place` 交给契约的 `createSlotStore`，读位置用它的 `items` 与 `subscribe`，外壳不另写存放规则。
- 装配文件 `page/assembly.tsx` 只列两样：协议契约的清单（与转发层读同一份 `shared/protocols.ts`）和界面模块插件的清单（身份、会话、人工介入、通知、日程、日历、资产、MCP、工具、模型、工作区，共十一个，`boundaries` 用例核这份清单）。它是页面里唯一导入领域成员的文件；去掉一个界面模块只改这一处，外壳照常编译和运行。
- 两个领域的界面要碰在一起时，也在装配文件里接，界面模块之间不互相导入。有六处。第一处：会话的界面模块从 `./cordis` 入口导出带类型的拓展点 `sessionDock`（对话页里转写区与输入框之间的位置），装配把它作为选项 `sessionDock` 交给人工介入的界面模块，这个会话正在等人决定的卡于是出现在对话页的输入框上方；去掉这一处，卡仍然在「待你决定」页里。第二处：会话的界面模块导出 `sessionCallDetail`（「后台」页签里每项调用下面的位置），装配把它交给工具的界面模块（`createToolUiModule({ callDetail })`），每项后台调用的输出正文于是出现在它下面；工具的界面模块按调用引用经工具协议读输出，会话的界面模块不读。第三处：装配把资产的界面模块导出的拓展点 `assetsCategoryPage`（资产页上类别的页面）与资产治理口的键 `assetGovernanceKey` 交给 MCP 的界面模块（`createMcpUiModule({ page, governance })`），资产页的「MCP」页签于是画 MCP 自己的页面。MCP 的界面模块自己写它要的口的形状，资产给的形状赋不过去时这个文件编译不过（`tests/assembly.spec-d.ts` 另核一个形状不对的键编译不过）；去掉这一行，资产页上 MCP 这一类回到通用的页面。第四处：装配把人工介入的界面模块导出的按键的拓展点 `releaseDetail` 交给日程的界面模块，日程按种类 `schedule.activation@1` 登记一个画法，「让安排生效」这一类调用的放行卡于是用日程自己的画法画接下来几次；去掉这一行，卡上照样逐条显示条目。第五处：模型的界面模块不往外壳放东西，只在树上提供「这个租户有哪些模型可选」的服务（键 `modelChoicesKey`）；会话的界面模块提供一个交列表的口（键 `sessionModelChoicesKey`）。装配用 `handOver(口, 服务)` 把两者接上：两边都在树上时把服务交进口里，任何一边撤下就收回。新建会话旁的模型选择与对话页抬头上换模型的下拉于是出现；去掉这一行或模型协议没挂着，会话的界面照常，抬头上只写当前的模型，新建会话不带模型。第六处和第五处同形：工作区的界面模块在树上提供「这个租户有哪些工作区可选」的服务（键 `workspaceChoicesKey`），会话的界面模块提供一个交列表的口（键 `sessionWorkspaceChoicesKey`），装配用 `handOver` 接上。新建会话旁的工作区选择与对话页抬头上换工作区的下拉于是出现；去掉这一行或工作区协议没挂着，会话的界面照常，抬头上只写当前的工作目录，新建会话不带工作区。`handOver` 是应用自己的（`page/hand-over.ts`），不认识领域。交过去的都是带类型的拓展点或键，不是一段名字：两边要的对象形状对不上时，这个文件编译不过。
- 装配不交资产类别的名字：资产页上类别的名字由资产的界面模块经 `assets/v1` 的 `list-categories` 向服务端取，装配文件里没有类别的名字。
- 登录的端口：页面把自己的登录状态、登录与退出组成外壳契约的 `ShellLogin` 交给外壳。两边的形状由类型对上：客户端装配的登录状态多一个取值，这里就编译不过。外壳把退出包一层：退出的结果是 `unknown` 时记下「本机已经退出。服务端是否已注销这次登录，没有得到确认。」，回到登录门时显示，下一次退出开始时清掉。
- 租户：外壳存放当前租户的文本，身份的界面模块设它；登录状态离开「已登录」时外壳把它清空。页面、侧栏区与附着位置的每一项渲染时收到它，页面项的标记也收到它。
- 附着位置：外壳实现服务的 `attached(位置的名字, 对象)`，返回一个组件元素。它订阅 `attached` 位置与租户，只渲染 `anchor` 与给定名字相同的项，逐项以项的标识为 `key`，每一项收到 `{ scope, subject }`；没有匹配的项时什么都不渲染，外面不包多余的容器。位置的项放进来或撤下、租户变了，这个元素自己重渲染，不靠所在的页面重渲染。
- 展示方自己排版：外壳实现服务的 `arranged(位置的名字, 对象, 排版函数)`，同样返回一个组件元素，取的项、次序、订阅都和 `attached` 相同。它不把各项拼在一起，而是把每一项的标识、标签与渲染结果交给排版函数，画排版函数的返回值。位置的项放进来或撤下、租户变了，它用新的表再调一次排版函数。
- 一项坏了只坏这一项：外壳画的每一项（登录门、页面、页面项的标记、侧栏区的一项、附着位置的一项）都包在一层错误边界里，项的渲染函数在边界里面的一个组件里调，所以渲染函数自己抛出、或它返回的组件在渲染当中抛出，都只落在这一项上。坏了的一项的位置上显示一句「这一块读不出」，不带错误的文本；页面项的标记坏了什么都不画。边界不加任何 DOM 元素。这一项收到的租户或对象变了，边界重试一次；都没变的重渲染不重试。页面里没有写诊断的去处，外壳不另记。
- 页面项的标记：页面项带 `badge` 时，导航里标题之后多一个 `.shell-nav-badge` 元素，内容是 `badge` 收到当前租户后的返回；返回空值时元素仍在、内容为空，由样式隐藏。导航收起、只剩图标时，标记缩成图标右上角的小点。
- 当前页面：没有人选过时显示次序最前的一页；人在导航里选了一页或界面模块调 `navigate`，显示那一页；标识不在时什么都不做。显示着的一页被撤掉，回到次序最前的一页，撤掉的那页再回来也不抢回前面；一页都没有时主区空着。
- 外壳的样子，按登录状态：
  - 未登录与登录中：只有主区，里面是登录门里的那一项。登录门空着时，连接还在「正在连接」就说正在连接服务，否则说「这个部署没有开放登录」。
  - 退出中：主区只说「正在退出……」。
  - 已登录：左边是可以折叠的侧栏，右边是主区。侧栏从上到下：应用名与折叠按钮；连接状态；页面的导航（每页一项，标题、图标与可选的标记）；侧栏区的各项按次序；底部明暗切换。主区放每一页，别的页隐藏而不卸下。
  - 连接断开时，不论哪种登录状态，主区上方都有一条提示「连不上服务。正在按间隔重新连接……」。
- 地标：全页恰好一个主区 `<main>`，归外壳；登录之后侧栏是补充区，页面导航在它里面。界面模块放进来的内容不带 `<main>`。
- 主题：外壳用共用界面件的主题控制器，偏好存在本机的 `localStorage`（键 `omne.theme`），读不到或存不进时当作跟随系统。页面在入口脚本之前装入一个同源的小脚本 `theme-boot.js`，它在首帧之前按同一条规则定下明暗，页面不先以另一种主题闪一下。内容安全策略不为它放宽。
- 样式：入口样式先引入共用界面件的汇总样式，再写外壳自己的版式；各界面模块的样式由装配文件引入。侧栏的版式与折叠动效取自参考项目，来历见 `src/page/shell/UPSTREAM.md`。
- 走查：`node apps/desktop/demo/page-walk.mjs [--shots <目录>]` 在全新的状态目录与空闲端口上起真的服务端、独立转发进程（与走查脚本同一个进程）与无界面的 Chromium，走注册、登录、侧栏与账号块、会话、停止一轮、资产页（切到资产，页签的字取自服务端，一份资产在列表里、点开有详情，同一个登录在页面之外新建一份技能时页面不用人动就列出它，在页面里选一个目录新建一份技能，列表里看它的简介，在详情里禁用、启用、移除，再选同一个目录同名新建，按页签打开各份资产的详情改一项再清除、设一个秘密项再清除、被锁定的一项没有控件，MCP 的页签与它的说明，页签里没有独立设置）、设置页（「日历与时区」一组，改一项并读回，再清除）、明暗切换、「待你决定」页读得出、退出、再登录，在页面里搜登录证明、密码与设过的秘密串，再走一轮失败后按「重试」接着做与工具卡参数的呈现；然后让一轮停在并行的两次 Ask 上（一次两题、一次一题）：对话页出现三张卡、题号、等待提示与导航上的张数，「待你决定」页按会话分组是同一组卡，在对话页左右切换、答齐之后一次提交，三张卡都收起、两次 Ask 各自走完、这一轮接着走完；最后另一轮在「待你决定」页里答，对话页的卡随之收起，会话自己走完。页面走完之后，它用同一个登录直接调资产协议的「列出类别」。走查失败时打印服务端错误输出的末尾。它不进测试分层。
- 图表走查：`node apps/desktop/demo/charts-walk.mjs [--page charts|usage] [--shots <目录>]` 用 vite 打一个页（`charts` 只含界面工具包的图表控件；`usage` 是用量页，装上示例模块、布局选中它带来的卡片与画法，读数来自假的客户端），带本应用的内容安全策略送出，在 Electron 里载入；浅色与深色各核一次图表是否画出、颜色是否只取自图表色变量、页里有没有样式表，策略违规与控制台错误要是零，并各截一张图。它读界面工具包的构建产物，不进测试分层。

### 窗口

- 窗口的网页偏好：`sandbox`、`contextIsolation` 开，`nodeIntegration` 关，`webSecurity` 开，没有预加载脚本。应用启动时开启沙箱。页面里没有 `require` 与 `process`，全局对象上没有应用另外放上去的东西。
- 页面不从 `file://` 加载。应用协议登记为标准、安全、支持 `fetch` 与流。静态文件由转发层发，路径逃不出构建好的页面目录；HTML 带内容安全策略，`connect-src` 只有应用自己，页面不直接连服务端。
- 导航到应用协议之外、新窗口、`<webview>` 与全部权限请求一律拒绝。被拒的导航与新窗口，地址是 `http`、`https` 或 `mailto` 时交给系统浏览器打开，别的地址不打开。
- 窗口先不显示，页面画出第一帧时才显示。一秒之内没有第一帧也显示，窗口不会一直不出现。
- 页面的文档加载失败或渲染进程意外结束时，应用自动重新加载一次。这次自动重新加载之后三十秒内再失败，应用不再自动重试，改为问人：重新加载，或关闭。页面没有响应时问人：继续等待、重新加载，或关闭。同一时刻只问一次。
- 问着「没有响应」的时候页面自己恢复了，或者页面崩了、加载失败了，这个问题收起，人选什么都不再动它；失败照上一条处理。
- 重新加载，不论自动的还是人选的，都等 utility 进程就绪再做：它在启动或在重启的退避里时，现在加载只会再失败一次。自动重新加载的额度在真的重新加载时才算用掉。等着的时候 utility 进程启动失败，不再等，改为问人。页面好好的时候 utility 进程换代，不动页面。
- 窗口关闭时把位置、大小与是否最大化存进用户数据目录的 `window-state.json`。下次打开时，存的位置在某块屏幕上露出足够多才沿用，否则用缺省大小。文件读不出当作没存过，写不进就不存。
- 窗口用系统的标题栏，三个平台相同。
- 应用只开一个实例，再起一次时把已有的窗口提到前面；窗口全部关掉时应用退出。
- 应用退出带走 utility 进程。窗口关闭本身不停它。

### 起法

- `pnpm run build` 先出主进程、utility 进程的入口与页面，再 `pnpm run window` 起窗口。服务端地址取环境变量 `OMNE_SERVER`，缺省是 `http://127.0.0.1:8787`。
- `pnpm run dev` 是开发时的起法：先完整构建一次，再监视源码。页面重新构建后窗口重新加载。主进程或 utility 进程一侧重新构建后应用重启。两种情形登录都还在，因为它在 cookie 里。关掉窗口，监视随之结束；应用崩溃或被信号结束时，`pnpm run dev` 以非零的状态退出。
- 开发时起的应用用单独的用户数据目录（原目录名加 `-dev`），不和安装的应用共用。两边的登录 cookie 与窗口位置互不相见。`electron-window` 用例每次用一个新建的临时目录。
- 两种起法都经同一个启动脚本起 Electron。它从继承的环境里去掉 `ELECTRON_RUN_AS_NODE`、`ELECTRON_NO_ATTACH_CONSOLE` 与 `NODE_OPTIONS`：带着它们，Electron 的二进制会当成 Node 或带着调试参数启动，不是这个应用。
- `electron` 包没有安装脚本，装依赖时不下载二进制。第一次 `pnpm run window` 或第一次跑`electron-window` 用例时，包自己把二进制下载到 `node_modules/electron/dist`，本机缓存里有同版本的压缩包就不联网。要提前备好，在 `apps/desktop` 下跑 `pnpm exec install-electron`。
- 主进程入口不在顶层等 `app` 就绪：Electron 在入口模块的顶层 `await` 完成之前不发就绪事件。
- 独立转发进程：`omne-desktop-host [--server <origin>] [--port <port>]`，地址与端口也可以取环境变量 `OMNE_SERVER` 与 `OMNE_DESKTOP_PORT`。
- `src/` 下每一部分一个目录：

  | 目录             | 部分                              |
  | ---------------- | --------------------------------- |
  | `src/shared`     | 共享类型                          |
  | `src/forwarding` | 转发层                            |
  | `src/standalone` | 独立转发进程                      |
  | `src/main`       | 主进程                            |
  | `src/utility`    | utility 进程的入口                |
  | `src/port-fetch` | 进程间传输                        |
  | `src/page`       | 页面；界面外壳在 `src/page/shell` |

## 原则与约束

- 页面的代码读不到登录证明。新增任何路径、答复字段、头、日志或错误文本，先确认它不带登录证明与密码。
- 转发层不记登录。它需要的关于登录的一切都从这个请求的 cookie 里读。
- 转发层只认 `Request` 与 `Response`：不导入 `electron`，不导入 Node 的 HTTP 模块，不认识自己跑在哪种承载上。
- 主进程不做业务：它映射地址、保管 cookie、补来源、关联取消、管 utility 进程与窗口。它不读协议契约，不读正文。
- 转发层是看门人，不是代理：只转发声明过的目标，拿不准就答「没发出」，不猜着放行。
- 页面与共享类型不导入转发层、主进程与 utility 进程的代码，也不导入 Node 内置与 `electron`；这三处不导入页面；界面外壳不导入任何领域。
- 结果不知道就是不知道：页面证明不了没发出的，答不确定；注销结果不确定时如实告诉页面。
- 界面模块随协议客户端「挂没挂着」加载与卸载；能不能用由服务端在每次调用时判断。
- 新增一个领域的界面只改装配文件与协议清单，界面外壳与转发层不变。
