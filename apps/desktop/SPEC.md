# @omne-harness/desktop

## 总体架构

桌面应用回答一个问题：一个人怎样在窗口里使用系统，而页面从不持有登录证明。它由两半组成：页面是客户端的 Cordis 树，树上有界面外壳与各领域的界面模块；宿主替页面持有登录，经一座窄桥把页面的请求转给服务端入口，并把构建好的页面发给浏览器。宿主可以是本机的 Node 进程，也可以是桌面外壳的主进程；两者实现同一座桥，页面不变。

| 部分          | 回答的问题                                                                                     |
| ------------- | ---------------------------------------------------------------------------------------------- |
| 共享类型      | 桥长什么样：页面能向宿主要什么，宿主怎样答；页面与宿主之间的字节                               |
| 宿主核心      | 登录会话怎样持有登录证明、怎样决定一个页面请求能不能发出、带什么凭据；与桌面外壳无关           |
| 本机宿主      | 本机进程怎样把桥经同源 HTTP 交给页面，怎样发出页面的静态文件                                   |
| Electron 宿主 | 主进程怎样把桥经进程间通信交给沙箱里的页面，怎样发出页面的静态文件，窗口怎样加固               |
| 页面          | 桥在页面这一侧怎样接到客户端的树；外壳怎样画出插入位置里的东西；装配文件列出哪些协议与界面模块 |

页面经桥的「调用」与「观察」通道发出请求；宿主核心按自己认识的协议契约核对目标，按登录会话的状态带上凭据，再经连接发往服务端入口。登录与退出不走普通调用：页面把凭据交给桥，宿主核心发出登录操作并保存证明，页面只得到结果。

## 领域边界

本应用拥有：登录会话（状态与登录证明）、桥的通道与字节、宿主的转发规则、界面外壳（服务 `shell` 的实现、版式、当前页面、租户的存放、主题偏好）、页面的装配。

本应用不拥有：身份、会话、设置项与人工介入的规则与协议，它们归各自的包组与协议契约；连接、客户端的树与协议客户端怎样随可用性长出与收回，归接入的客户端核心与客户端装配；对话界面、待你决定的界面与设置界面归各自领域的界面模块。外壳不认识任何领域；装配文件是页面里唯一点名领域的地方。

本应用需要别人做的：

| 需要                 | 对方                               | 本应用需要它做什么                                                                                                                                                      |
| -------------------- | ---------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 客户端核心与连接     | 接入（SDK 与客户端装配）           | 给出传输接口与连接插件；客户端的树随服务端入口挂着的协议长出与收回协议客户端；给出登录状态源的接口                                                                      |
| 协议契约             | 身份、会话、人工介入、资产、日程、日历 | 声明每个操作与观察的身份要求，以及哪些操作携带凭据；宿主与页面读同一份清单                                                                                              |
| 外壳契约与共用界面件 | 前端（`shell-contract`、`ui-kit`） | 插入位置、服务 `shell` 的抽象类与存放规则 `createSlotStore`；控件、样式 token 与主题控制器                                                                              |
| 界面模块             | 身份、会话、人工介入、资产、MCP、日程、日历 | 各自是客户端树上的插件，自己注入协议客户端或别的界面模块提供的口，往插入位置里放东西：登录门与账号块、会话列表与对话页、待你决定页、资产页与设置页、资产页上 MCP 的页签、日程页、日历页 |
| 服务端入口           | 接入（服务端）                     | 按协议名、主版本与名字承载调用与观察；在身份协议上答复登录、注销与当前租户                                                                                              |

本应用不为别的包组实现端口。

## 心智模型

把宿主想成一个只认识几份协议契约的看门人，把页面想成一个拿不到钥匙的访客。钥匙是登录证明，只在宿主的登录会话里。页面能做的只有五件事：发一次调用，开一个观察，交出凭据要求登录，要求退出，看登录状态。宿主对每个调用与观察只问三件事：这个目标是不是我认识的契约里声明过的；它是不是一个携带凭据的操作；按现在的登录状态它该带什么凭据。

登录会话是一个有四个状态的聚合，事件与状态的每一格都有确定的答复。最容易想错的三处。退出总会删掉本机的证明，哪怕服务端是否注销不确定。一次 `denied` 不等于登录失效：它只触发一次探测，探测也答 `denied` 才算。页面发往宿主的请求失败时，页面证明不了字节没有发出，除非宿主在转发前就拒绝了它。

外壳与界面模块之间的关系是「挂没挂着」：一个界面模块要的协议客户端在树上，它才加载，往插入位置里放东西；协议撤了，它卸载，放的东西随作用域撤掉。这是 Cordis 的依赖注入本来就做的，外壳不判断哪个协议开着。切换页面只是藏起别的页面，不是卸下，所以看一眼设置不会打断对话里正在进行的一轮。

## 应然设计

### 登录会话

登录会话在宿主进程里，独占登录证明。状态四个：未登录、登录中、已登录、退出中，用四个互不相交的类型表示；登录证明只是「已登录」「退出中」两个类型的字段。

| 事件                             | 未登录                                       | 登录中                                             | 已登录                               | 退出中                                                                             |
| -------------------------------- | -------------------------------------------- | -------------------------------------------------- | ------------------------------------ | ---------------------------------------------------------------------------------- |
| 应用启动，读本机保存的登录证明   | 读到就进「已登录」，读不到留在「未登录」     | 不可达                                             | 不可达                               | 不可达                                                                             |
| 页面请求登录                     | 进「登录中」，发出登录操作                   | 拒绝：正在登录                                     | 拒绝：已经登录                       | 拒绝：正在退出                                                                     |
| 登录的答复是成功                 | 不可达                                       | 保存登录证明，进「已登录」。只告诉页面「登录成功」 | 不可达                               | 不可达                                                                             |
| 登录的答复是其他结果，或结果未知 | 不可达                                       | 回「未登录」。把结果如实告诉页面，未知就说未知     | 不可达                               | 不可达                                                                             |
| 页面请求退出                     | 直接答「已经退出」                           | 拒绝：正在登录                                     | 进「退出中」，发出注销操作           | 拒绝：正在退出                                                                     |
| 注销的答复是成功或无变化         | 不可达                                       | 不可达                                             | 不可达                               | 删掉登录证明，进「未登录」                                                         |
| 注销的答复是其他结果，或结果未知 | 不可达                                       | 不可达                                             | 不可达                               | 仍然删掉本机的登录证明，进「未登录」。告诉页面：本机已退出，服务端是否已注销不确定 |
| 身份协议明确答复登录已失效       | 不变                                         | 不可达                                             | 删掉登录证明，进「未登录」，通知页面 | 删掉登录证明，进「未登录」                                                         |
| 页面请求一次普通调用             | 不带登录证明发出。需要登录的操作由服务端拒绝 | 同左                                               | 带上登录证明发出                     | 拒绝：正在退出                                                                     |

- 登录操作是身份协议的签发登录，注销是撤销登录，目标是这次登录自己的登录标识。行事租户取签发成功体里的租户。
- 登录的结果对页面只有四种：登录成功；统一认证失败答认证失败；`unknown` 与本地的结果不确定答未知；其余（字节没发出、依据不可用、本部署不提供、协议拒绝、契约读不出的消息体）答不可用。
- 「拒绝」在桥的结果类型里没有自己的值：登录被拒答不可用，退出被拒答未知。页面只在未登录时给登录、已登录时给退出，正常使用碰不到。
- 登录或注销的调用抛出异常而不是给出答复时，登录会话不停在中间状态：登录回「未登录」；注销仍然删掉本机的证明，进「未登录」。异常原样抛给调用方。
- 「身份协议明确答复登录已失效」的判定：一次带登录证明的调用答 `denied`，或带登录证明的观察以 `denied` 被拒或结束之后，登录会话用同一个证明查一次当前租户；它也答 `denied`，才是这个事件。同一时刻至多一次探测在途；结果不缓存，下一次 `denied` 再探。探测答复到达时登录会话已不再持有这个证明，事件不作用。注销在途时探测先把状态带回「未登录」，注销的答复到达时不再改变状态，结果仍按上表告诉页面。
- 一个宿主进程服务一个用的人：登录会话在进程里只有一个。保存登录证明的地方是一个可替换的凭据仓库。

### 转发规则

- 宿主只转发它认识的契约里声明的操作与观察。认识的契约是 `access/v1` 加页面的树带着的那一份协议清单，页面与宿主读同一份。目标按协议名、主版本与名字三样精确比对，带路径的名字到不了别的操作。不认识的协议、认识的协议里没有声明的名字、标了携带凭据的操作，一律答「字节没发出」，不带任何东西发往服务端。
- 宿主认识的协议表在宿主启动时编进去，换了部署而没有重启宿主，宿主就比页面旧。所以宿主在登录状态的每一条消息里一并说出它认识的协议（名字与主版本）。页面拿自己的协议清单比对：页面要用而宿主不认识的，或者宿主根本没说（比这一版旧的宿主），页面顶上写「页面宿主的版本旧了，需要重启。」并列出少的那几样，不像这项能力不存在那样静默。
- 「带上登录证明发出」按契约里这个操作或观察的身份要求带：不要身份的什么都不带；要登录的只带登录证明；要行事租户的带登录证明与行事租户。
- 「拒绝：正在退出」的普通调用与观察答「字节没发出」，客户端核心读作不可用。

### 宿主给页面的通道

- 桥有五条通道：调用、观察、登录、退出、登录状态。调用的答复是传输的三种结果之一：答复了（结果与体）、没发出、不确定。观察的答复是一条事件流，一帧一个事件，最后一个事件写观察怎样结束；页面断开，宿主取消这个观察。登录与退出的答复只有结果字段。登录状态先给当前状态，变了再给。其余 `GET` 是构建好的页面静态文件。
- 宿主只监听回环地址。`POST` 只收 JSON；`Host` 头必须是回环名字（`127.0.0.1`、`localhost`、`[::1]`），端口不核，因为挡住重绑定页面的是名字，经端口转发打开时浏览器看到的是另一个端口；有 `Origin` 头时必须同源。页面的 HTML 带内容安全策略：只许自己的脚本与样式，只许连同源。
- 桌面外壳是第二种承载：主进程里跑宿主核心，页面跑在开了沙箱的窗口里，五条通道经进程间通信走同一座桥。页面这一侧只认一个通道接口：同源 HTTP 与进程间两种实现实现同一个接口，页面里只有选通道的那一处知道有两种承载。
  - 进程间通信只有六个调用名（调用、观察、关闭观察、登录、退出、登录状态）与两个事件名（观察的事件、登录状态的事件），登记处理函数的集合恰是这个集合。预加载脚本只向页面暴露一个对象 `omneHost`，键恰是五条通道，不暴露 `ipcRenderer` 与别的东西。
  - 每个处理函数先核发消息的框架的地址在应用自己的协议之下，不是就答「没发出」，不转发。正文经与 HTTP 相同的读写函数读，读不出的答「没发出」。
  - 一个页面开的观察，每个有主进程给的编号，一个页面只能关自己开的。页面关了某个观察，取消上游，不再发这个观察的任何事件；上游结束只发一次结束事件。页面关闭、重新加载或崩了，它开着的观察与调用全部取消，登录状态的订阅退订。
  - 登录状态的订阅先给当前状态，变了再给；同一个页面重复订阅不重复发送。
  - 页面一侧：处理函数抛出读作不确定，被拒读作没发出，与 HTTP 通道一致。
- 登录证明与密码不进日志，不进错误信息。宿主的日志一事一行：被拒的请求只写方法、路径与 `Host`、`Origin` 两个头；失败的请求只写方法、路径与失败的种类，不写错误的原文，因为原文可能引用消息体。日志从不写消息体、证明或密码。
- 页面发往宿主的请求失败时，只有宿主在转发前答出的拒绝能证明字节没有发出；其余失败，调用答不确定。

### 页面

- 客户端的 Cordis 树装着连接插件（传输与登录状态都是桥）与清单里每份协议的协议客户端。登录状态流断开后，页面按退避重新跟上；读到「暂时没有可读的」时按可配置的再问策略等待，次数与总时长都有上界。
- 树上另装外壳的服务 `shell` 与装配文件列出的界面模块。外壳实现外壳契约的 `ShellService` 与 `ShellSlots`：受保护的 `place` 交给契约的 `createSlotStore`，读位置用它的 `items` 与 `subscribe`，外壳不另写存放规则。
- 装配文件 `page/assembly.tsx` 只列两样：协议契约的清单（与宿主读同一份 `shared/protocols.ts`）和界面模块插件的清单（身份、会话、人工介入、资产、MCP、日程、日历、工具，共八个，`boundaries` 用例核这份清单）。它是页面里唯一导入领域成员的文件；去掉一个界面模块只改这一处，外壳照常编译和运行。
- 两个领域的界面要碰在一起时，也在装配文件里接，界面模块之间不互相导入。现在有三处。第一处：会话的界面模块从 `./cordis` 入口导出带类型的拓展点 `sessionDock`（对话页里转写区与输入框之间的位置），装配把它作为选项 `sessionDock` 交给人工介入的界面模块，这个会话正在等人决定的卡于是出现在对话页的输入框上方；去掉这一处，卡仍然在「待你决定」页里。第二处：会话的界面模块导出 `sessionCallDetail`（「后台」页签里每项调用下面的位置），装配把它交给工具的界面模块（`createToolUiModule({ callDetail })`），每项后台调用的输出正文于是出现在它下面；工具的界面模块按调用引用经工具协议读输出，会话的界面模块不读。第三处：装配把资产的界面模块导出的拓展点 `assetsCategoryPage`（资产页上类别的页面）与资产治理口的键 `assetGovernanceKey` 交给 MCP 的界面模块（`createMcpUiModule({ page, governance })`），资产页的「MCP」页签于是画 MCP 自己的页面。MCP 的界面模块自己写它要的口的形状，资产给的形状赋不过去时这个文件编译不过（`tests/assembly.spec-d.ts` 另核一个形状不对的键编译不过）；去掉这一行，资产页上 MCP 这一类回到通用的页面。交过去的都是拓展点，不是一段名字：两边要的对象形状对不上时，这个文件编译不过。
- 装配不交资产类别的名字：资产页上类别的名字由资产的界面模块经 `assets/v1` 的 `list-categories` 向服务端取，装配文件里没有类别的名字。
- 登录的端口：页面把桥的登录状态源、登录与退出组成外壳契约的 `ShellLogin` 交给外壳。两边的形状由类型对上：客户端装配的登录状态多一个取值，这里就编译不过。外壳把退出包一层：退出的结果是 `unknown` 时记下「本机已经退出。服务端是否已注销这次登录，没有得到确认。」，回到登录门时显示，下一次退出开始时清掉。
- 租户：外壳存放当前租户的文本，身份的界面模块设它；登录状态离开「已登录」时外壳把它清空。页面、侧栏区与附着位置的每一项渲染时收到它，页面项的标记也收到它。
- 附着位置：外壳实现服务的 `attached(位置的名字, 对象)`，返回一个组件元素。它订阅 `attached` 位置与租户，只渲染 `anchor` 与给定名字相同的项，逐项以项的标识为 `key`，每一项收到 `{ scope, subject }`；没有匹配的项时什么都不渲染，外面不包多余的容器。位置的项放进来或撤下、租户变了，这个元素自己重渲染，不靠宿主页面重渲染。
- 宿主自己排版：外壳实现服务的 `arranged(位置的名字, 对象, 排版函数)`，同样返回一个组件元素，取的项、次序、订阅都和 `attached` 相同。它不把各项拼在一起，而是把每一项的标识、标签与渲染结果交给排版函数，画排版函数的返回值。位置的项放进来或撤下、租户变了，它用新的表再调一次排版函数。
- 一项坏了只坏这一项：外壳画的每一项（登录门、页面、页面项的标记、侧栏区的一项、附着位置的一项）都包在一层错误边界里，项的渲染函数在边界里面的一个组件里调，所以渲染函数自己抛出、或它返回的组件在渲染当中抛出，都只落在这一项上。坏了的一项的位置上显示一句「这一块读不出」，不带错误的文本；页面项的标记坏了什么都不画。边界不加任何 DOM 元素。这一项收到的租户或对象变了，边界重试一次；都没变的重渲染不重试。页面里没有写诊断的去处，外壳不另记。
- 页面项的标记：页面项带 `badge` 时，导航里标题之后多一个 `.shell-nav-badge` 元素，内容是 `badge` 收到当前租户后的返回；返回空值时元素仍在、内容为空，由样式隐藏。导航收起、只剩图标时，标记缩成图标右上角的小点。
- 当前页面：没有人选过时显示次序最前的一页；人在导航里选了一页或界面模块调 `navigate`，显示那一页；标识不在时什么都不做。显示着的一页被撤掉，回到次序最前的一页，撤掉的那页再回来也不抢回前面；一页都没有时主区空着。
- 外壳的样子，按登录状态：
  - 未登录与登录中：只有主区，里面是登录门里的那一项。登录门空着时，连接还在「正在连接」就说正在连接服务，否则说「这个部署没有开放登录」。
  - 退出中：主区只说「正在退出……」。
  - 已登录：左边是可以折叠的侧栏，右边是主区。侧栏从上到下：应用名与折叠按钮；连接状态；页面的导航（每页一项，标题、图标与可选的标记）；侧栏区的各项按次序；底部明暗切换。主区放每一页，别的页隐藏而不卸下。
  - 连接断开时，不论哪种登录状态，主区上方都有一条提示「连不上服务。正在按间隔重新连接……」。
- 地标：全页恰好一个主区 `<main>`，归外壳；登录之后侧栏是补充区，页面导航在它里面。界面模块放进来的内容不带 `<main>`。
- 主题：外壳用共用界面件的主题控制器，偏好存在本机的 `localStorage`（键 `omne.theme`），读不到或存不进时当作跟随系统。
- 样式：入口样式先引入共用界面件的汇总样式，再写外壳自己的版式；各界面模块的样式由装配文件引入。侧栏的版式与折叠动效取自参考项目，来历见 `src/page/shell/UPSTREAM.md`。
- 走查：`node apps/desktop/demo/page-walk.mjs [--shots <目录>]` 在全新的状态目录与空闲端口上起真的服务端、进程内的本机宿主与无界面的 Chromium，走注册、登录、侧栏与账号块、会话、停止一轮、资产页（切到资产，页签的字取自服务端，按页签改一项再清除、设一个秘密项再清除、被锁定的一项没有控件，MCP 的页签与它的说明）、设置页的说明、明暗切换、「待你决定」页读得出、退出、再登录，在页面里搜登录证明、密码与设过的秘密串，再走一轮失败后按「重试」接着做与工具卡参数的呈现；然后让一轮停在并行的两次 Ask 上（一次两题、一次请示）：对话页出现三张卡、题号、等待提示与导航上的张数，「待你决定」页按会话分组是同一组卡，在对话页左右切换、答齐之后一次提交，三张卡都收起、两次 Ask 各自走完、这一轮接着走完；最后另一轮在「待你决定」页里答，对话页的卡随之收起，会话自己走完。页面走完之后，它用同一个登录直接调资产协议的「列出类别」。走查失败时打印服务端错误输出的末尾。它不进测试分层。

### 窗口

- 窗口的网页偏好：`sandbox`、`contextIsolation` 开，`nodeIntegration` 关，`webSecurity` 开，预加载脚本只有一份，是自足的 CommonJS 文件。应用启动时开启沙箱。页面里没有 `require` 与 `process`。
- 页面不从 `file://` 加载：应用登记自己的协议（标准、安全、支持 `fetch`），只从构建好的页面目录发文件，路径逃不出这个目录；HTML 带与本机宿主同一份内容安全策略，`connect-src` 只有应用自己，页面不直接连服务端，所有请求经主进程。
- 导航到应用协议之外、新窗口、`<webview>` 与全部权限请求一律拒绝。
- 应用只开一个实例，再起一次时把已有的窗口提到前面；窗口全部关掉时应用退出。
- 登录证明只在主进程里，和本机宿主一样只在内存里，进程退出就没有。

### 起法

- `pnpm run build` 先出主进程、页面与预加载脚本，再 `pnpm run window` 起窗口。服务端地址取环境变量 `OMNE_SERVER`，缺省与本机宿主相同。
- `electron` 包没有安装脚本，装依赖时不下载二进制。第一次 `pnpm run window` 或第一次跑真窗口的用例时，包自己把二进制下载到 `node_modules/electron/dist`，本机缓存里有同版本的压缩包就不联网。要提前备好，在 `apps/desktop` 下跑 `pnpm exec install-electron`。
- 主进程入口不在顶层等 `app` 就绪：Electron 在入口模块的顶层 `await` 完成之前不发就绪事件。

## 原则与约束

- 登录证明不进页面。新增任何通道、答复字段、日志或错误文本，先确认它不带登录证明与密码。
- 页面与共享类型不导入宿主一侧，也不导入 Node 内置与 `electron`；宿主一侧不导入页面；外壳不导入任何领域。预加载脚本只导入 `electron` 与共享类型；主进程一侧的桥不导入 `electron`，用替身就能测。
- 宿主是看门人，不是代理：只转发声明过的目标，拿不准就答「没发出」，不猜着放行。
- 宿主核心与桌面外壳无关；换宿主只换承载桥的那一层，页面与宿主核心不变。
- 结果不知道就是不知道：页面证明不了没发出的，答不确定；注销结果不确定时如实告诉页面。
- 界面模块随协议客户端「挂没挂着」加载与卸载；能不能用由服务端在每次调用时判断。
- 新增一个领域的界面只改装配文件与协议清单，外壳不变。外壳不加契约没有的插入位置。
