# @omne-harness/repo-toolchain

## 总体架构

`@omne-harness/repo-toolchain` 是本仓库的检查器包，发布在 npm。仓库在 `pnpm-workspace.yaml` 的 catalog 里钉它的精确版本。根目录的检查与三个工具成员运行 npm 上的那个版本，不运行本目录的源码。

| 部分 | 源码 | 入口命令 |
| --- | --- | --- |
| 规则引擎与源码收集 | `src/core` | 无，经 `.` 导出 |
| 提交署名 | `src/commits.ts` | 无，由 product-checks 的 `lint:rules` 调用 |
| 依赖图、依赖方向与环 | `src/deps` | `omne-deps` |
| 声明兼容 | `src/declarations` | `omne-declarations` |
| 契约 API 快照 | `src/declarations` | `omne-contract-api` |
| 验收锁 | `src/acceptance` | `omne-acceptance-lock` |
| 实际架构、全局符合性与架构视图 | `src/arch` | `omne-architecture` |
| 结构度量与审讯页 | `src/metrics`、`src/report` | `omne-metrics` |
| 回路状态、收工钩子与体检页 | `src/loop` | `omne-loop-status`、`omne-loop-health`、`src/loop/stop-hook.ts` |
| 长期产品与场景发现 | `src/product` | 无，供 product-checks 与回路读取 |

包内下层不依赖上层，次序是：`src/core`；检查与度量（`acceptance`、`arch`、`archive`、`declarations`、`deps`、`metrics`、`product`、`commits.ts`）；`src/report`；`src/loop`。`metrics` 不依赖 `arch`。命令入口负责组装，不受这几条约束。

每个命令的参数、环境变量与退出码见它的 `--help`。

## 领域边界

本包拥有：

- 每项检查判什么算违例，每个传感器量什么、怎样落带。
- 它写出的数据的形状：依赖图缓存、契约 API 快照与基线区块、`metrics.json` 等度量产物、`status.json`、`trend.jsonl`、`hook-readings.json`、体检页数据。
- 所有入口共用的缺省基线规则。

本包不拥有：

- 依赖规则的正文：规则写在 [repo-config](../repo-config/dependency-cruiser.cjs) 的 dependency-cruiser 预设里，含义与出处归[系统分层](../../docs/architecture/layers-and-dependencies.md)。
- 全局架构预期：归 `docs/architecture/constraints.json`。本包读它，不反写。
- 可加改动的规则：归 `omne-card` 技能的 `references/contract-change.md`。契约成员表归 `docs/engineering/delivery-lines.json`。
- 本仓库的产品规则、署名历史审计基线与验收覆盖声明：归 product-checks。
- 测试计划与测试、验收耗时账本：由 test-runner 写出，本包只读。
- 收工钩子的宿主配置：由 `.meta_harness/agents/hooks/hooks.yaml` 生成。

消费者：

- 三个不发布的工具成员 dev-flow、product-checks、test-runner 经本包的子路径导入它。本包不导入它们。
- `exports` 的子路径对应 `src` 下的模块。`.` 导出规则类型、`collectSources`、`runRules(files, rules)` 与实际架构 API。`./architecture` 导出实际架构 API 与视图投影。`loop/run`、`loop/hook-measure` 与 `loop/sensors/*` 只供本仓库其他工具成员的测试使用，不作公开承诺。发布时去掉指向 `src` 的 `source` 条件。
- 根脚本 `lint:deps`、`check:declarations`、`acceptance:lock`、`metrics`、`loop:status`、`loop:health` 与宿主的收工钩子。
- pqw-adapter 读 `repo-toolchain.config.json` 的 `metrics.thresholds` 与断言写法。

## 心智模型

- 传感器只说事实：位置、数值、带位。它不写该怎么改。能让检查失败的只有硬线，其余都只报告。
- 不知道就是不知道。读不到、没数据、判不了都写明原因，不拿零、空集或「没有发现」冒充量过了。
- 规则从运行检查器的仓库读，事实从被检查的仓库读。被检查的检出改不了判它的规则。

## 应然设计

### 仓库根与配置

- 被检查的仓库取 `OMNE_SUBJECT_ROOT`，未设置时取当前目录所在 Git 仓库的根。
- 运行检查器的仓库取 `OMNE_RUNNER_ROOT`，未设置时与被检查的仓库相同。依赖规则（`.dependency-cruiser.cjs`、`tsconfig.base.json`）、`constraints.json` 的方向行与配置只从这个仓库读。
- 配置在仓库根的 `repo-toolchain.config.json`，可有 `loop`、`metrics`、`acceptanceLock`、`contractApi` 四节。每个命令只读自己的那一节。缺文件、缺所读的节、有认不出的节、缺项、类型不对、线的次序不对时报错退出，不使用默认值。阈值、窗口与开关都在配置里，代码里不写死数值。
- dependency-cruiser 要靠 TypeScript 解析 `.ts`。找不到 TypeScript 时依赖图检查报错退出，不在漏掉 `.ts` 的情况下通过。

### 缺省基线

`core/task-context` 的 `resolveBaseline(root, explicitBase?, env?)` 是所有入口共用的缺省基线规则，按顺序取第一个存在的：

1. 显式基线：`--base`，没有就取环境变量 `BASELINE`。空串视为没给。
2. 任务上下文固定的 `targetBase`。工作树绑定了任务上下文时，显式基线只有等于 `targetBase` 才被接受，否则抛 `stale`。
3. `origin/main`，本地没有这个引用时取 `main`。

结果带 `source`：`explicit`、`task`、`origin/main` 或 `main`。`baselines` 不补缺省：没有任务上下文也没有显式基线时 `targetBase` 为 `undefined`。

### Git 子进程

对显式仓库起的 Git 子进程隔离八项仓库定位变量，认证、Git 配置与 OMNE 的两个根照常继承。外部的 `GIT_DIR` 一类变量不能让检查读写另一个仓库。

### 依赖图

- 仓库只有一张依赖图，由 dependency-cruiser 按运行检查器的仓库的规则与解析选项生成。`lint:deps`、回路状态、结构度量与实际架构报告都读它，本包不另写导入解析或层位表。
- 成员边是产品源码（不含测试）解析到另一个成员的依赖，类型导入也算。成员之间成环即失败。只在组的层面成环、成员之间不成环的不算。图另保留成员里走到的模块清单（`modules`）与跨成员的文件级依赖事实（`dependencies`），方向判定只从这两项判断。
- 工作树的图不含被 Git 忽略且未跟踪的目录里的模块与违规。不在 Git 仓库里的目录照常出图。
- 基线图与工作树的图都有缓存。缓存键覆盖一切能改变图的输入，含出图代码本身的摘要。命中时读到的图与重算的逐字节相同。缓存读不到、坏了、键对不上、写不进都按未命中，既不让检查失败也不让它放行。算图期间输入变了不写缓存。
- 缓存不能声称的：原来解析不到的导入，之后在被忽略的目录里出现了文件，缓存可能仍报旧的失败，但不会放行。

### 依赖方向

`omne-deps` 按运行检查器的仓库的 `constraints.json`（schema 3 的 `directions`）检查依赖方向。`--root` 只改变被检查的树。

- 命中：一处已解析的导入，所在文件落在某条方向行某个 `from` 角色的 `paths` 里，解析后的目标文件所在成员等于某个 `to` 角色的成员。类型导入、`export … from`、动态 `import()`、包名与公开子路径、tsconfig 别名与跨成员相对路径都按解析后的目标判断。目标在 `src/`、`dist/` 或声明文件里都算同一成员。解析失败的导入不是方向命中，由 `no-unresolvable` 报出。
- 每处命中一条 `direction-rule`，写方向行、源文件、目标文件、两端角色与出处。一处导入命中几条方向行就报几条。
- 方向行的某个源角色或目标角色在被检树里匹配不到任何文件时，报一条 `direction-unknown`。成员改名或迁走后，方向检查不以「命中 0 处」通过。
- 运行检查器的仓库没有 `constraints.json` 时不检查方向，并写明未检查。文件没有方向行时写明没有方向行。
- 退出码：有依赖违规、环、`direction-rule` 或 `direction-unknown` 时退出 1。`constraints.json` 解析失败、校验失败、来源核对失败，或新旧两个位置的 `constraints.json` 并存时退出 2，这时不出依赖图。
- 回路的硬线是依赖违规与环。方向命中只让 `lint:deps` 退出 1，在回路里只报告。

### 提交署名

`commit-attribution` 查当前提交可达的全部历史，不查源码。规则正文归根 `AGENTS.md` 的「署名与分支」。

| 报出 | 放行 |
| --- | --- |
| `Co-Authored-By:` 行里是 coding agent 或其厂商 | 人与人的共同署名 |
| `Generated with`、`Generated by` 一类把 agent 列为产出者的行 | `Harness:`、`Agent-Role:` 两条来源 trailer |
| author 或 committer 的名字、邮箱是 agent | 提交标题与正文里提到 agent 的名字 |

报告写成 `commit <短号>:<提交信息里的行号>`。认的是 `src/commits.ts` 里列出的名字。它不核对来源 trailer 写没写、写得对不对。浅克隆时只查克隆下来的提交。本包不读历史审计基线，`attributionViolations` 报告全部违反。

### 验收锁

可执行验收放在成员的 `acceptance/` 目录，归负责的人、主会话与独立验收角色。实施的 agent 只运行、不修改。`omne-acceptance-lock` 核对这一条：

- 基线提交就是清单。工具拿基线与 HEAD 的合并点同当前工作树比，列出验收文件的净变化（含未提交与未跟踪）、每一个碰过验收文件的提交（短号、作者、`Agent-Role`、碰了哪些文件）、原始违规、已批准的历史例外与未解决违规。
- 判锁被破：碰过验收文件的提交，`Agent-Role` 不在拥有者角色里且没有精确历史批准；工作树里有未提交或未跟踪的验收改动。放行：`Agent-Role` 是拥有者角色的提交；没有来源 trailer 的提交按人写的算。
- 受管的根、验收目录名与拥有者角色只在配置的 `acceptanceLock` 一节定一次。
- 模板生成的验收入口不算验收内容：`acceptance/` 下名为 `README.md` 或 `index.md`、变化前后仍有独立一行文档占位标记的文件，增删改都不计入。
- `LockReport.violations` 保留原始发现，`commits[].allowed` 表示原角色判断，`approvedExceptions` 单列已批准的历史例外，`unresolvedViolations` 是剩余违规，命令据它返回 0 或 1。回路的 `auditRanges[].acceptance` 保留完整报告，`hardLines.acceptanceLock.violations` 只列未解决项。
- 历史批准只来自编进 `src/acceptance/historical-approvals.data.ts` 的只读列表。每条对应一个提交里的一个受保护路径，并带完整提交、所写父提交、旧新 blob 与完整二进制 diff 的 SHA-256。工具读真实 Git 对象核对每一项。一个提交列出的受保护路径必须恰好等于为它登记的路径，否则这个提交一条都不批准。路径集合相等而一条指纹不符时，只有那一条不批准。仓库配置、环境变量、参数与外部地址都不能新增批准，运行时不访问 GitHub。
- 没有任务上下文时，合并提交与每个父提交分别比较。有任务上下文时只列与所有父提交都不同的路径，干净合并因此不列路径。
- 先改后改回的提交照样列出、照样判破。角色取自提交人自己写的 trailer，所以碰过验收的提交一律列出，由接受的人过目。工具不看验收的内容、有没有运行、过没过。

### 声明兼容

`omne-declarations` 把全部有 `build` 脚本的成员 `dist/` 下的 `.d.ts` 作为根文件交给 TypeScript 6 建一个程序，选项取仓库根 `tsconfig.base.json` 并打开库检查。全部解析去掉 `customConditions`，按消费者视角读：成员之间的导入解析到对方的 `dist` 声明，`src` 不进程序。成员声明里有诊断即退出 1，第三方声明里的诊断只计数。没有 `dist/` 的成员列为未构建，自己不判失败。已构建的成员导入未构建的成员时，导入方报 TS2307 并判失败。本包调用 TypeScript 旧编程接口的模块都从 `@typescript/typescript6` 导入。

### 契约 API 快照

`omne-contract-api` 给每个契约成员一份入库的 API 快照，并把两份快照之间的差异粗分为 `none`、`additive`、`review`。它只报告，不拦截。公开形状归 `src/declarations` 的 `api-format.ts`、`contract-api.ts`、`api-baseline.ts`、`api-classify.ts`。

输入：

- 配置是 `contractApi` 一节，只有 `members`（契约成员表的路径，不能为空）与 `snapshot`（快照路径模板，以 `.md` 结尾，至少含 `{member}` 或 `{package}`）两个键。别的键、缺键、值不合条件，或两个成员算出同一个快照路径时，命令出错退出。
- 契约成员是成员表各组 `contracts` 的并集。成员的 `package.json` 要有 `name`，`exports` 是按子路径的对象，每个子路径有 `types` 条件，否则单列为声明不全。
- 读法与声明兼容相同，全部契约成员另建一个程序。成员 dist 有编译诊断时不生成它的快照，报告前三条诊断。

快照：

- 格式版本写在快照第 3 行。读到别的版本、认不出的行或重复项时读取失败。改格式时提高版本号，全部快照重新生成。
- 快照有两部分：每个入口导出的名字（写明声明在哪个文件或哪个外部包、是否仅类型），以及成员 dist 里经 TypeScript 打印器规范化的全部声明文件。声明文件保留导入、导出与模块扩充，快照能还原成一组能编译的声明。别的成员写进来的扩充不进本成员的快照。
- 同一份 dist 生成的快照字节相同，与一起生成的其他成员无关。快照摘要是快照文件字节的 SHA-256，十六进制小写。

动作：

- `--write` 写快照，内容不变的文件不重写。没有 dist、声明不全或有编译诊断的成员不写，原文件不变。
- `--check` 拿 dist 现场生成的快照与快照文件比，每个成员一种状态：`match`、`differs`（附差异与分类）、`unreadable`、`missing`、`unbuilt`、`invalid`。
- `--diff <基线>` 只比快照文件，不读 dist。成员取基线与当前两份成员表的并集，每侧的快照路径按那一侧的包名算。只在当前的成员整份算新增，只在基线的整份算删除。包名变了、两侧都没有快照文件都是 `review`。一侧读不出时这个成员按 `review` 计。基线不是提交时出错退出。
- `--baseline-write <提交>` 生成里程碑基线登记的 `json omne-contract-baseline:v1` 围栏区块。区块的对象只有 `milestone`（字符串或 null，必有）、`members`（每项只有 `path`、`commit`、`sha256`、`apiTree`，`path` 不重复）与可选的 `breakingCards` 三个键。`--member` 只写指定成员。成员不合条件时出错退出。
- `--baseline <文件>` 读一个区块（整段 JSON，或恰好含一个围栏的文本），每个成员从它自己的 `commit` 比到工作树的快照，规则同 `--diff`。基线点是全部登记提交的共同祖先。登记的成员在它的 `commit` 上不是契约成员或没有快照、在基线点上已是契约成员却没有登记的成员，都判不了，结果为拒绝，`breakingCards` 不能放行。其余情况分类为 `review` 而没有 `breakingCards` 时也拒绝。登记的 `sha256` 或 `apiTree` 与提交对不上时只报告。本工具不读 GitHub。

分类是白名单门，只有正证据成立才是 `additive`，整份取最强的一项：

- `none`：两份快照规范化后的文本相同。规范化只抹掉注释、布局、顶层语句的顺序与普通参数的名字。
- 全局作用域有差异时整份 `review`，不跑检查器：`declare global` 与对外部模块的 `declare module` 块增删改；脚本文件增删改或与模块之间切换；三斜线指令的变化；导入或 `export … from` 的模块边增删；`export as namespace` 增删改。消费者程序里全局作用域只有一份，检查器证明不了这类改动不影响已有导出。
- `additive` 要两条正证据。第一，每一处差异都在白名单里，白名单只有两类：新增一个旧侧不知道的名字（与已有同名声明合并、与入口已有导出名重名、或在文件作用域里遮住已有符号的不算）；在模块作用域的接口或类型字面量里新增属性写法的可选属性（对本成员模块的扩充块内的改动不算）。第二，TypeScript 检查器对涉及的每个导出证明两个方向都可赋值：新到旧表示读方不破坏，旧到新表示写方（提供者、替身、实现者）不破坏。
- 其余一律 `review`，附注写明命中哪一条：`global-scope-change`、`outside-whitelist`、`uncovered`、`direction`、`incomplete`、`truncated`（实例组合超过 16 组）、`diagnostics`。
- `review` 的含义是需要人判断，不是 PR「契约变化」一节的级别。那一节的级别由人按可加改动的规则判定。

退出码：`--check`、`--diff`、`--baseline-write` 完成退出 0。`--write` 有成员没写成退出 1。`--baseline` 有判不了的成员，或分类为 `review` 而没有 `breakingCards` 时退出 1。用法、配置、Git、区块格式与工具错误退出 2。

### 实际架构

`readActualArchitecture({ root, revision?, base? })` 从实际源码抽取架构事实，不读意图声明。`omne-architecture` 的标准输出只有这份 JSON。

- 传入的 revision 与 BASE 各自先解析成不可变提交，之后只读该提交的 Git 树。BASE 不取合并点，不从当前工作树补文件。完整 BASE 包含已删除或移动的文件。
- 不传 revision 时读当前文件系统。`source` 记录 Git 的 `dirty`，`inputDirty` 另标记已读输入中没有进入提交的文件（含被 Git 忽略的源码或配置），路径在 `unversionedInputs`。被 Git 忽略且未跟踪的目录是本地产物，不算成员。
- 成员来自该版本的 workspace 与 manifest，名称取 `manifest.name`，不由目录猜包名。`packages/`、`apps/` 下的成员属于产品范围，其余单列为开发成员。按包名写的 `extends` 不应用，记进 `configuration.installedExtends`。
- `unknown` 保留无法还原的表达式、原因与所有出处。空集合不能证明不存在。`candidateProviders` 保留全部候选，`runtimeSelection` 为 `not-observed`，不选择未经运行观察的提供者。
- 关系身份不含源码路径与行号，名称用 JSON 元组编码。文件搬迁或行号变化不成为语义新增。差分分别列成员、事实、导入、未知的新增与删除。
- 覆盖率为 `no-data`，不执行测试。进程、外部资源、运行选择与隔离等未观察项写在 `scope.limitations`。

### 全局架构符合性

符合性报告是消费实际事实的附加文档。`actual.json` 与默认的实际 JSON 不读也不含意图。

- 输入：当前唯一输入是 `docs/architecture/constraints.json`。HEAD 与 BASE 各按本版坐标发现输入，历史版本仍可读旧位置。同一版本存在两份输入时拒绝。规则身份只取公开的 `RULE_IDS`。`source` 是仓库根相对的 Markdown 路径，可带锚点，文件与锚点从同一版本读，坏引用拒绝。未知规则、坏 JSON、越界路径与重复身份都失败。缺输入以 `INPUT` unknown 保留坐标与原因，不能声称整体符合。
- `rules` 认四个 H1 身份：`H1-SESSION-FACTS`、`H1-AGENT-REASSEMBLY`、`H1-MODEL-LIFETIME`、`H1-OBSERVATION-CONTINUITY`。报告把它们列为 `behavior`，标明本报告未执行，不为它们生成符合性行。
- 方向行：schema 3 的 `directions` 每行只有 `id`、`from`、`to`、`source`。`id` 匹配 `^DIR-[A-Z0-9]+(-[A-Z0-9]+)*$` 且唯一。`from`、`to` 引用已声明的角色，源角色与目标角色不在同一个成员，同一角色不在两边。方向行引用的角色，`paths` 都落在同一个成员目录里，且不与别的角色相同或互相包含。违反的都拒绝。方向行与角色只从运行检查器的仓库读，依赖事实读各版本自己的依赖图。方向行引用的角色在某版本里都匹配不到文件时不取这个版本的图，每一行都是 unknown。取了图而图不可得时这些行是 unknown。报告行按方向行、源角色、目标角色展开，`rule` 为 `DIRECTION`。`DIRECTION` 不是 `RuleId`，不能写进 `rules`，也关不掉。
- 机械子集：`LAYER-ENTRY`、`LAYER-DIP`、`IC-1` 到 `IC-5` 与 `DIRECTION` 是有限的静态检查。单条 converged 只表示该条没有发现违规，不表示成员或系统整体符合。责任没有采用时是 unknown。目录名不授予许可。已接受的 IC-5 例外与分层要求冲突时，该分层结果为 unknown 并指出例外出处。其余 IC、LSP 与 SOLID 各条保留为行为义务或人工判断，这些状态在 JSON、页面与体检页中保留。
- 包扫描把符合性行投影到 `PackageScan.dependencies`，另加 `undeclared-dependency`（源码引用了另一个成员而导入方的三类依赖都没有声明它，类型导入也要声明）与 `member-cycle`。这两个名字不是 `RuleId`。
- 比较：给 BASE 时，当前实现对 BASE 的规则与精确例外比较，BASE 上已有的违规为存量，其余为新增。BASE 输入缺失时依赖它的结果是 unknown 或 no-data，不用 HEAD 或空规则替代。没给 BASE 时新旧分类为 unjudged。方向偏离行对基线版本的图判新旧，基线的图不可得时不判，每行写明原因。
- 预期变化：HEAD 与 BASE 的全局预期及原节点预期变化单列。JSON 格式、行号与集合排序不造成预期变更。路径、角色状态、依据、规则或例外变化是语义变化。依据文件的字节变化在 `sourceChanges` 另报，不计入语义变化。
- 只在 BASE 比较中，来源位于 `packages.0.0.1.legacy/` 或 `apps.0.0.1.legacy/`、路径在该版本源码里全部零命中的角色可以退休。退休角色不参与判定，原始值仍参与预期差分。
- 命令：`--conformance` 让标准输出与 `--out` 换成符合性 JSON。`--member` 只筛选这份输出的行，只能与 `--conformance` 同用。未出现在当前或 BASE 清单里的成员返回空行与 `matched=false`。
- 报告退出 0 不表示符合：偏离与未知都只报告，硬线归 `omne-deps`。

### 架构视图

`--report <目录>` 另生成 `report.html`、`graph.json`、`actual.json`、`conformance.json` 与 `summary.md`，报告路径写到标准错误。`--out` 不得覆盖报告文件。公开投影是 `buildArchitectureView(document, bands)` 与 `selectArchitectureView(graph, selection)`，形状归 `src/arch/view.ts`。

- 视图只消费实际事实与附加的符合性文档。目录组不表示运行、部署、事务或租户边界。服务与事件同名不表示实际绑定，提供者全部列为候选。规划与架构预期没有输入时显示「未提供」，配置选择与运行绑定显示「未观测」。
- 总览只汇总跨组的直接成员导入与装配声明，组内关系留到展开。依赖矩阵的数字是输入事实身份数，不是调用次数，不从矩阵形状判层级、循环或符合性。
- 稳定的控件名称是：`系统总览`、`架构视图`、`复杂度与风险`、`目录组或应用`、`聚焦组件`、`显示邻接`、`变化范围`、`叠加圈复杂度`、`叠加耦合`、`导出 SVG`、`导出 JSON`；导航路径 `当前架构路径`；侧栏 `架构导航`、`架构详情`；画布 region `架构画布`。关系种类的复选框名称取中文图例文字。
- 画布的 `aria-busy` 表示布局正在执行，`data-layout-state` 取 `loading`、`ready`、`failed`。选择改变时清除旧图并禁用导出，只有本次选择绘制成功后才允许导出。旧的布局结果不能覆盖新选择。布局、解压或解析失败时显示原因，不显示空白视图冒充成功。
- 导出的 JSON 有 `kind: architecture-selection`、`schemaVersion: 1`、`selection`、`source`、可选 `baseline`、`nodes` 与 `edges`。边的 `evidence` 保留输入身份、`version`（current 或 baseline）与 `occurrences`。导出的 SVG 包含完整当前子图与图例，不因视口裁剪丢失节点或关系，节点与边保留 `data-node-id`、`data-edge-id`。几何缺失时导出失败，不生成部分图。
- 页面只用内联的数据、脚本与样式，`file://` 打开不需要服务端或网络。名称与表达式按文本显示。布局只能调用官方 `ELK` 构造器的 `layout`。故障验证可以在页面脚本之前包装它，不得替换事实输入、投影函数或渲染函数。
- 参数、读取、投影与写入失败使命令非零退出。

### 结构度量

`omne-metrics` 只报告，不判失败。

- 计划文件由 test-runner 的 `plan --json` 写出。本工具只读它的四栏：`head`、`base.ref`、`base.mergeBase` 与 `plan.test`（成员目录的数组）。这四栏是本包的输入约定。
- 给 `--plan` 时，基线与合并点取自计划。计划算的不是当前提交时报错。工作树绑定了任务上下文时，计划的基线要与上下文固定的基线一致。算完计划后工作树又改了计划外的成员时，带覆盖率的运行报错，要求重算计划。
- 覆盖率只对计划里要跑测试、且在 `metrics` 配置的 `coverage.roots` 下的成员跑。没跑覆盖率的成员按圈复杂度评级，跑了却没有数据的成员单独标出。跨成员并行时，结果按成员原来的顺序合并，各成员的日志、报告目录与退出码与串行时相同，顺序只影响墙钟，不影响读数。一个成员起不来时不再开新成员，等已开始的结束后报错。
- 产物：`summary.md`（不超过 12 行，同时打印）、`metrics.json`（每个成员与函数的圈复杂度、覆盖率、CRAP、是否变更，`meta` 里有各成员覆盖率的耗时与退出码）、`graph.json`、`review.html`（自包含的审讯页）、`actual.json`、`architecture.json`、`conformance.json`、给 `--plan` 时的 `plan.json`、开了覆盖率时的 `coverage/`。
- 计分单元是有名字的函数：函数声明、类与对象字面量的方法、赋给名字的箭头函数与函数表达式。匿名回调并入所在单元。
- 圈复杂度等于 1 加上 `if`、各类循环、`catch`、`?:`、`case`、`default`、`&&`、`||` 的个数。`??`、`?.` 与逻辑赋值不计。阈值是按这套计数校出来的。
- 覆盖率取函数行范围内、不落在更内层有名函数里的语句行的命中比例。`dist/**/*.js` 一并收集，经 sourcemap 映射回 `src/`。子进程里执行的代码不计入。
- CRAP 等于圈复杂度的平方乘以（1 减覆盖率）的三次方，再加圈复杂度。成员风险值是成员内函数评级分的均值加一个总体标准差，按色带换成 1 到 10 的评分。组取组内最差的成员。
- 函数是否变更比对函数自身文本的摘要，不看 diff 行号。架构变化用精确 BASE，函数变化用合并点，页面分别显示两个坐标。
- 扇入、扇出是依赖它的成员数与它依赖的成员数，不稳定度是出除以入加出。
- 阈值与色带在 `metrics` 配置：`thresholds`、`bands`、`page.changedEdgeLimit`。

### 回路状态

`omne-loop-status` 回答：整洁的各项指标现在各在哪条带上，这次变更里有哪些红项要解释，哪些成员超了预算。

- 硬线：依赖违规或环；给了 `--base` 时验收锁被破；严格模式下开着的传感器没数据。硬线被破退出 1，工具出错退出 2，其余报告项再多也是 0。无法解析的导入归 `lint:deps`，不算硬线。
- 严格模式要求给 `--base` 与 `--out`，不写趋势快照，草稿写进 `--out` 下的 `proposals/`，回路目录一个字节都不动。范围 `engineering` 只与严格模式同用：当前与全部基线都没有产品源码与测试时，`duplication`、`assertions` 没数据列入 `hardLines.sensors.notApplicable`，原因码 `engineering-without-product-inputs`，证据存在 `scope.evidence`。工程范围不证明产品质量。
- 回路目录是 `$OMNE_METRICS_HOME`，没设时是主检出的 `tmp/clean-loop/`。产物：`status/<提交短号>[-dirty]/status.md` 与 `status.json`；超预算成员的草稿 `proposals/<成员路径>.md`，六个固定章节取常量 `CLEANUP_SECTIONS`；`trend.jsonl`；收工钩子的 `hook-readings.json` 与 `hook.log`。
- 三条带：每个指标与每项成员预算都有提醒线、处置线、解除线，数值越大越差，`release ≤ warn ≤ act`。值到处置线进入处置，回落到解除线及以下才解除。上一次的带位取趋势里最近一条是当前提交祖先的快照。配置为与基线比的指标另与基线快照比，比基线差至少是提醒，没有基线快照标未判。基线快照是 `BASE` 合并点的快照，没有就取合并点之前最近的一条。不给 `BASE` 时用与 `primaryBranch` 的合并点。
- 趋势快照只在工作树干净时写：给了 `--snapshot`，或 HEAD 正是 `primaryBranch` 的头。同一提交已有一条就不再写。坏行跳过并报出行号。
- 指标：红色成员数与超 alert 的函数数（取结构度量，不跑覆盖率）；稳定依赖不稳定的边数（`I(to) − I(from) > margin`）；一起改却分属两组的成员对数；新增跨成员依赖数（给了 `BASE` 才有）；静态装配事实的新增、移除与元数据变化数与全局架构预期改动数（中性计数，无线、不与趋势比）；未解析服务标识符数；没有断言的测试数（按语法树判，`assertionPattern`、`helperPattern`、`typeTestPattern` 可配）；全仓重复行占比；单个产品 topic 窗口内 `revision:` 翻动次数；并行工作树数与被多棵工作树同时改的成员数；验收总耗时与最慢一份验收的耗时。
- 成员预算：每个成员四项（超 alert 的函数数、风险值、重复行占比、没有断言的测试数），任一项处于处置即超预算。`memberBudget.excludeGroups` 里的组不判预算、不生成草稿，全仓指标照样计入它们。解除之后又进入处置达到 `relapseLimit` 次的成员标结构问题，上报，不生成草稿。`memberBudget.baseline` 为真时，存量成员只在比基线快照变差时进提醒，绝对线只管新成员与处置。
- 要解释的函数：先取这次变更碰过、带位不是 ok 的函数，再与基线提交上同一路径、同一限定名的函数比圈复杂度。基线上没有的写「新出现」，变大的写「原 N → 现 M」，拿不准的照列并写原因，没变大的从名单里拿掉并在 `explain.functionsNotWorse` 列出。改名的文件按改名前的路径取。
- 对照表条数：读 `docs/clean-loop.md`。表头有「归类」一栏的表，这一格须是 `传感器`、`评审问法`、`归人`、`不适用`、`不采` 之一。对照表的条目名按出现次数逐字对回条目全表，缺的、多的分别列出。文件不存在报没数据。
- 验收耗时：传感器不跑验收，只读 test-runner 以 `--script acceptance` 写下的账本。账本根是主检出的 `tmp/acceptance-ledger/`，`OMNE_ACCEPTANCE_LEDGER_HOME` 可改。取当前提交那一格（工作树不干净时是 `-dirty` 那一格）里最新的一次交代了每个有 `acceptance` 脚本的成员的运行。真跑过的记录优先于只有跳过的记录。没有成员有验收脚本时读数是 0 份，算有数据。只有影响面显式跳过的账本时算有数据，两项耗时如实写没数据与跳过原因。有验收却找不到这样一次运行时没数据。
- 重复代码：用 `@jscpd/core` 与 `@jscpd/tokenizer`，范围是各成员 `src/` 下的非测试、非声明 TypeScript 源。库给的后一端止行早于起行，或跨度超过前一端两倍加两行时，按前一端的行数推算，清单里标 `plausibleEnd`。重复行占比因此是近似值。
- 实际装配：回路经 `sensors.architecture` 读实际架构与符合性。关掉时明确报 no-data。`sensors.assemblyDelta` 缺 BASE 时为 no-data，不用零冒充已比较。当前或 BASE 的全局预期缺失时 architecture 为 no-data，严格模式点名失败。有效预期与完整源码都读到时，空事实集是真实的空结果。

### 收工钩子

`src/loop/stop-hook.ts` 由宿主在 agent 收工时调用（`Stop` 与 `SubagentStop`），把这次变更里比上一次新出现或变差的红项作为事实反馈给 agent。

- 输出协议：要反馈时向标准输出写恰好一个 `{"decision":"block","reason":"…"}`。量读数时自己出了错，写恰好一个 `{"systemMessage":"…"}`，给用户看，不交给 agent，不拦收工。其余情形不写任何字节。所有路径都退出 0。
- 不反馈的情形：`OMNE_LOOP_HOOK=off`；输入不是 JSON 对象；`stop_hook_active` 为真（每次收工至多拦一次）；工作目录（输入的 `cwd`，没有就用进程当前目录）不在 Git 仓库里；`loop` 配置的 `hook.enabled` 为假；这次变更没碰产品源码、全局 `constraints.json` 或它引用的 Markdown 源。
- 量不了的情形：脚本不在被量的仓库里且没给 `OMNE_RUNNER_ROOT`，或本检出没装依赖。这时只给用户一句「量不了」。
- 基线：有任务上下文时取 `taskBase`，没有 ownerTask 时取 `targetBase`。没有任务上下文时，在 `primaryBranch` 与 `integration-policy.json` 里 `status` 为 `active` 的轨道分支之间取离 HEAD 最近的合并点，并列时取 `primaryBranch`。一个候选也求不出时基线是 `HEAD`。每次调用重新计算，不沿用上一次。
- 读数：变更函数里超 alert 且比基线涨了或新出现的（判法同回路状态的要解释的函数）、新增的跨成员依赖与其中稳定依赖不稳定的、改动过的测试文件里没有断言的用例、依赖违规与环两条硬线、相对 BASE 预期的新增架构偏离与预期的语义改动。不跑重复代码、覆盖率、工作树与 topic 几项。
- 依赖项只换改动文件的边：取基线合并点上按提交缓存的依赖图，只对改过且还在的源文件跑一层 dependency-cruiser，再把基线图里这些文件发出的依赖与违规换成现算的。解析配置变了（根上的 `.dependency-cruiser.cjs` 或 `tsconfig*.json`，或成员 `package.json` 里影响解析的字段）时依赖项不量，只写一句改看 `pnpm run lint:deps`。同一成员里的文件环与没改的文件指向已删文件的旧边留给 `lint:deps`。
- 架构读数的 BASE 一侧按提交算一次，存进回路目录的 `hook-baseline/`。键是 BASE 提交、`sensors.architecture` 配置、检查器代码的摘要与存储格式版本，键对不上或文件坏了就重算覆盖，不给旧数。BASE 一侧最先算，超时时也已存下。
- 量读数在子进程里跑，超过 `hook.timeoutSeconds` 就连同它起的进程整组结束。
- 只反馈比上一次新出现或变差的：每条按类别与位置（不含行号）比，函数另比圈复杂度。上一次是这棵工作树、这条分支最近一次的读数，存在 `hook-readings.json`，至多 `hook.stateLimit` 条。反馈列前 `hook.maxItems` 条，整段不超过 `hook.maxChars` 个字符，硬线排最前。
- 找到仓库之后任何一步抛错或超时：不反馈给 agent，往 `hook.log` 追加一行原因，用 `systemMessage` 给用户一句警告，含原因的前 300 个字符与日志位置。

### 流程体检页

`omne-loop-health` 把趋势快照、测试耗时账本与 Git 历史汇成一张页面，写进回路目录的 `health/`：`health.html`（自包含，不带脚本，不引外部地址）、`health.json`（每块是有数据或没数据及原因）、`summary.md`（不超过 15 行，末行是页面路径）。

- 块：`primaryBranch` 沿第一父链最近 `health.commits` 个提交各改了几个文件；最近 `health.runs` 次全量测试运行的墙钟，每层一条线，带基线的运行与含缓存命中的运行不计入；每个指标的走向；对照表条数；每个指标最近一次有数据的快照；一行符合性摘要。
- 任何一块没有数据，都在那一块里写明没有数据与原因。
- 中位数在偶数个时取中间两个里较小的那个。提交大小只数文件个数。

### 长期产品与场景发现

- `readProductTopics(productRoot)` 读当前 slug 目录的 README front matter，取 PD 身份、正整数 `revision` 与 `status`。模板目录不参与。PD 身份必须与 slug 目录一致且全根唯一，产品正文必须存在，实际路径都在产品根内。
- 非法根、缺失或无效的元数据、重复身份、目录不符、缺产品正文与越界都是输入错误，不转成零输入的成功。合法的空根单列为未覆盖。读取不依赖 Issue 配置或历史任务。
- 编号场景的解析归 `src/product/scenarios.ts`。缺场景正文或没有编号场景的 PD 单列未覆盖，不从能力表猜场景。

## 原则与约束

- 改了本目录要先发新版本，再改仓库的钉子。源码测试通过不代表消费者已装上修复。
- 页面内联的第三方代码在构建时写进 `dist`，发布的包不依赖这些界面库。
- 失败要关闭：缓存、历史批准与契约分类拿不准时都朝拒绝或 `review` 走，不朝放行走。
- 不复用已有的覆盖报告：成员的 `dist/`、测试、配置与安装状态不在提交里，判定不了输入相同。
- 度量算法按 Robert C. Martin 工具的做法用 TypeScript 重写，不搬原文。不移植抽象度与主序列距离：那套判法会把稳定而没有抽象的纯数据契约包判进痛苦区。
- 超阈值看职责不看数字。回答同一个问题的单个分派可以留在阈值之上。把函数拆碎只换来数字，换不来设计。
- 每个传感器都由回路金丝雀种一处已知违规守着：哪个传感器读错目录或算法坏了，金丝雀就指名变红。它只证明种下的那几处查得出，不证明查得全。
- 静态读数不证明运行时的隔离、授权、事务、生命周期或运行绑定。这些由实际公开服务、成员规格与行为验证负责。
- 耗时读数受机器负载影响，几次之间的差不能直接归因于代码。
- 架构视图的布局只用 ELK 算位置与路由。屏幕上的关系图与导出的 SVG 用同一份几何。

## 不变式

- 被检查的树不能改变判它的规则、方向行、配置或历史批准。
- 未知、没数据与判不了从不被报告成通过或零。
- 只有硬线能让 `omne-loop-status` 失败，硬线之外的读数只报告。
- 同一份输入生成的契约 API 快照与依赖图逐字节相同。
- 收工钩子所有路径都退出 0，每次收工至多拦一次。
- 依赖图缓存不会让一个重算会失败的检查通过。
