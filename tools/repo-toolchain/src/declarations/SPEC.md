# 契约 API 快照

本规格是 `omne-contract-api` 的行为契约。公开形状归类型：快照模型与文件格式在 [api-format.ts](api-format.ts)，三个动作的结果在 [contract-api.ts](contract-api.ts)，基线区块与两个基线动作的结果在 [api-baseline.ts](api-baseline.ts)，差异、附注与分类在 [api-classify.ts](api-classify.ts)，白名单的语法判断在 [api-whitelist.ts](api-whitelist.ts)，检查器比较在 [api-compare.ts](api-compare.ts)。用法归 [README_ZH](../../README_ZH.md#契约-api-快照)。可加改动的规则归 [integration.md「可加改动」](../../../../docs/engineering/integration.md#可加改动)，本工具只给粗分类，不改变那里的规则。

## 输入

- 配置：运行检查器的仓库根 `repo-toolchain.config.json` 的 `contractApi` 一节。这一节只有两个键。
  - `members`：线归属表的仓库相对路径，不能为空。
  - `snapshot`：快照路径模板，以 `.md` 结尾，至少含 `{member}` 或 `{package}` 之一。`{member}` 换成成员目录，`{package}` 换成去掉 scope 的包名。
  - 这一节不是对象、有别的键、缺键或值不合上面的条件时，命令出错退出。两个成员算出同一个快照路径时，命令也出错退出。
- 契约成员：线归属表各线 `contracts` 的并集，按路径排序。表的完整校验归 dev-flow 的 `check:lines`。本工具只要求 `lines` 是数组，每条线的 `contracts` 是非空字符串的数组。
- 成员声明：`package.json` 要有 `name`，`exports` 是按子路径的对象，每个子路径要有 `types` 条件。不满足的成员单列为声明不全，不生成快照。
- dist：成员 dist 里的全部 `.d.ts`。读法与声明兼容检查相同：TypeScript 6，选项取仓库根 `tsconfig.base.json` 并去掉 `customConditions`，成员之间的导入解析到对方的 dist。全部契约成员共用一个程序，这个程序与声明兼容检查的程序分开建立。
- 编译诊断：成员 dist 文件里有语法或语义诊断时（例如转导出的包没有构建，TS2307），不生成这个成员的快照，报告前三条诊断。缺项的快照比没有快照更糟。

## 快照

- 格式由 `SNAPSHOT_FORMAT` 标明，写在快照第 3 行。读到别的版本、认不出的行、重复的入口、重复的声明文件或同一入口里重复的导出名时，读取失败，不按旧规则猜。改格式时提高版本号，全部快照要重新生成。
- 快照有两部分。
  - 入口：每个 `exports` 子路径一节，标出入口的声明文件，列出导出的每个名字。每个名字写明声明在哪里：本成员的哪个声明文件、哪个外部包，或本成员哪个文件的命名空间导出。改名导出标出原名。值经 `export type`、`import type` 或 `export type * from` 导出时标「仅类型」，隔几层 `export *` 也算。`export * as ns` 写一行 `ns`，再把它的成员写成 `ns.<名字>`。只由别的成员的模块扩充加进来的名字不算本成员的导出。
  - 声明文件：成员 dist 里的每个 `.d.ts`，键是 dist 内相对路径。文件经 TypeScript 打印器规范化：注释与原有空白去掉，导入、导出与 `declare module`／`declare global` 块保留。所以一个成员的全部声明（含未导出的内部声明与模块扩充）按「文件路径＋名字」定位，快照可以原样还原成一组能编译的 `.d.ts`。
- 别的成员写进来的扩充在那个成员的声明文件里，不进本成员的快照。
- 确定性：同一份 dist 生成的快照字节相同。入口按子路径、导出按名字、文件按路径，以 UTF-16 码元排序。快照只取决于成员自己的文件，与一起生成的其他成员、成员的顺序无关。
- 快照摘要：快照文件字节的 SHA-256，十六进制小写。`--check --json` 对每个有快照文件的成员给出 `sha256`。

## 三个动作

- `--write`：从 dist 生成快照并写到配置的路径。内容不变的文件不重写。没有 dist、声明不全或有编译诊断的成员不写，原来的快照文件保持不变。
- `--check`：拿 dist 现场生成的快照与快照文件比。每个成员的状态是下面之一：
  - 一致（match）；
  - 不一致（differs），附快照到 dist 的差异与分类，规则同 `--diff`；
  - 快照读不回（unreadable），例如格式版本不对；
  - 没有快照文件（missing）；
  - 没有 dist（unbuilt）；
  - 声明不全（invalid），含编译诊断。
- `--diff <基线>`：基线提交上的快照文件对工作树的快照文件，逐成员分类。它只比快照文件，不读 dist。所以先用 `--check` 确认工作树的快照与 dist 一致。
  - 基线先解析成提交。不是提交时出错退出。其他 Git 失败带着原因出错退出，不当作没有文件。
  - 成员取基线与当前两份线归属表的并集。每侧的快照路径按那一侧的包名算。基线上没有线归属表时，基线一侧没有契约成员。
  - 只在当前是契约成员：基线一侧没有快照，整份算新增。只在基线是：整份算删除。包名变了是 review。两侧都没有快照文件是 review，不当作没变。
  - 一侧的 `package.json` 读不出或快照读不回时，这个成员标为读不出，总的分类按 review 计。

## 里程碑基线

里程碑的契约基线登记在评论里，形式是一个 `json omne-contract-baseline:v1` 围栏区块。基线文件不入库。本工具不读 GitHub：读评论、按时间合并几条登记归 dev-flow。

区块的 JSON 是一个对象，只有下面三个键：

- `milestone`：里程碑名，字符串或 null。必须有这个键。
- `members`：非空数组，每项只有四个键：`path`（成员目录，仓库相对）、`commit`（这个成员的基线提交，40 位小写十六进制）、`sha256`（该提交上快照文件字节的 SHA-256，64 位小写十六进制，口径与 `--check --json` 相同）、`apiTree`（`git rev-parse <commit>:<path>/api` 的树号）。`path` 不重复。不同成员可以有不同的 `commit`。
- `breakingCards`：可选，不重复的非空字符串数组，写承接破坏性改动的 `integration` 卡。调度者在破坏性裁定读回后补登记。

区块里没有版本字段，版本在围栏标记里。不记几个成员拼接的摘要。

- `--baseline-write <提交> [--milestone <名>] [--member <成员目录>]...`：从这个提交生成区块。成员取那个提交的线归属表，`--member` 给出时只写这些成员（补登记用）。标准输出是整个围栏区块，加 `--json` 时是 JSON 对象。没给 `--milestone` 时 `milestone` 为 null。提交解析不了、`--member` 不是那个提交上的契约成员、成员声明不全、那个提交上没有快照文件或没有 `api` 目录时，出错退出。
- `--baseline <文件>`：读区块并逐成员核对。文件内容整段是 JSON 对象时按 JSON 读，否则须恰好含一个 `json omne-contract-baseline:v1` 围栏，例如登记评论的正文。键、格式或围栏个数不对时出错退出。
  - 成员取登记与工作树线归属表的并集。登记的成员从它自己的 `commit` 上的快照比到工作树的快照，分类规则与 `--diff` 相同。只在登记里的成员整份算删除。
  - 基线点是全部登记提交的共同祖先（`git merge-base --octopus`，只有一个提交时就是它）。没有登记、只在工作树线归属表里的成员：在基线点上已是契约成员的是漏登记；不是的是基线之后加入的，基线一侧没有快照，整份算新增。
  - 下列成员判不了，列在 `undetermined`，成员状态为 `invalid`：登记的成员在它的 `commit` 上不是契约成员、声明读不出或没有快照文件；漏登记的成员。登记一侧读不出时不能当作没有快照，否则一份写错提交的登记会让整个成员按新增放行。
  - 总的分类取各成员中最强的一项，读不出与判不了的成员按 review 计。有判不了的成员时结果为拒绝（`refused`），退出 1，`breakingCards` 不能放行。否则分类为 `review` 而没有 `breakingCards` 时拒绝，退出 1；有 `breakingCards` 时放行。放行只说明登记了承接卡；每个 review 成员由哪张卡承接，由集成节点核对。
  - 登记与它的提交对不上时，在 `registration` 里逐项报告：`sha256-mismatch`（那个提交上快照文件的 SHA-256 与登记不同）、`api-tree-mismatch`（`api` 树号与登记不同）、`not-a-contract-member`（那个提交上这个成员不是契约成员，这个成员同时判不了）。前两项不改变分类与退出码。
  - 登记的提交没有共同祖先时出错退出。
  - 它只比快照文件，不读 dist。先用 `--check` 确认工作树的快照与 dist 一致。

## 分类

结果是 `none`、`additive` 或 `review`，整份取最强的一项。分类是白名单门：只有正证据成立才是 `additive`，其余一律 `review`。分类只报告，不拦截。

差异分两桶。消费者的程序里全局作用域只有一份：模块作用域能靠改名把两侧隔开，全局作用域不能，检查器证明不了「这处改动没有影响已有导出」，检查器算出的类型也不带来源（`keyof ErrorOptions` 到检查器手里已经是 `"cause"`）。所以全局作用域的差异不进 `additive`。

### none

两份快照规范化后的文本相同时是 `none`。规范化只抹掉不改变类型的差异：注释、布局、顶层语句的顺序、普通参数的名字。`this` 参数不改名。同名语句（重载）保持先后。三斜线指令（`path`、`types`、`lib`）是规范化文本的一部分，保持原顺序。两份快照的字节相同（包名之外）时直接是 `none`，不再比较。

### review：全局作用域有差异

下面任何一处差异，整份 `review`，附注 `global-scope-change`，不跑检查器找 `additive`。

- `declare global` 块与对外部模块的 `declare module '…'` 块（模块名不以 `.` 开头）：增、删、改。
- 脚本文件（没有导入导出的 `.d.ts`，顶层声明都是全局的）：新增、删除、任何语句变化；文件在脚本与模块之间切换。
- 三斜线指令：任何差异。
- 入口可达的文件集合：导入或 `export … from` 的模块边增删。带绑定的导入、`import type`、空的 `import {}`、无绑定的 `import './x.js'`／`import 'pkg'`、`import x = require()`、`import('…')` 类型都算边。同一文件里再加一条已有模块的导入不算新边。
- `export as namespace X`：它声明 UMD 全局名。增、删、改名都算。

### additive

`additive` 同时要求两条正证据，都只看模块作用域。

1. 每一处差异都在白名单里。白名单只有两类。(b) 对应[可加改动](../../../../docs/engineering/integration.md#可加改动)表的「加可选字段」一行。(a) 在该表中没有对应的行：新增一个此前不存在的名字不改变已有声明，本工具据此把它列入白名单。
   - (a) 新增顶层语句，引入旧侧不知道的名字：新导出、新入口、新内部声明。名字要同时满足三条，任一不满足就在白名单外，附注写明与谁重名。
     - 不是本文件已有的声明。与已有同名声明合并的不算：新增重载、第二个同名接口或命名空间、命名空间合并到类或函数上，都改 `typeof` 与已有导出的形状。
     - 不是任何入口在旧侧已有的导出名（`export *` 与 `export { x as y }` 展开后的名字）。例如入口 `export * from './a.js'` 已经导出 `Foo`，入口文件里再声明一个 `Foo` 就遮住它。
     - 在该文件的作用域里，旧侧程序解析不到这个名字的符号。解析含经导入可见的名字、lib 与外部包的全局名，值、类型与命名空间三种含义都算。例如一个未导出的 `interface Error` 遮住 lib 的 `Error`，文件里 `f<T = Error>()` 的默认实参就指向它。解析用旧侧还原的程序；建不起程序或解析失败时按白名单外处理。
     - 对本成员自己模块的 `declare module './x.ts'` 块新增或删除也不算：它合并进别的文件里的声明。删掉一条空的 `export {}` 而文件仍是模块时，不算改动。
   - (b) 在模块作用域的接口或类型字面量里新增可选属性。只认属性写法（`b?: T`）。方法签名（`b?(): T`）与索引签名不算。扩充块里的接口不在这一类：对外部模块与 `global` 的扩充见上一节；对本成员模块的 `declare module './x.ts'` 块内的任何改动都在白名单外。
2. 检查器对涉及的每个导出证明两个方向都可赋值：新 → 旧成立，表示按旧形状写的读方仍接受新值（readers）。旧 → 新成立，表示旧写方（提供者、替身、实现者）产出的值仍被接受（writers）。两个方向用同一种写法证明。「涉及」指它自己的声明文本变了，或它经本成员的内部声明能到达一条按白名单改了的语句。

白名单的判断看语法，只有 (a) 的名字解析借旧侧程序的检查器。对每条改了的顶层语句，工具把新侧判定为新增的可选属性去掉，再与旧侧比规范化文本。对不上的差异都算白名单外。

### review：其余

其余一律 `review`。每项差异附注命中哪一条，附注是判别联合：

| 附注 | 含义 |
| --- | --- |
| `global-scope-change` | 全局作用域有差异，见上面的一节。附注写明是扩充块、脚本文件、三斜线指令、模块边还是 UMD 全局名 |
| `outside-whitelist` | 改动不在白名单里。含删除导出、删除入口、删除整份快照、两侧都没有快照、导出标注变了（改名、「仅类型」、声明来源）、包名变了、任何不是新增可选属性的语句改动、与已有同名声明合并的新增声明、与入口已有导出或文件作用域里已有符号重名的新增声明、对本成员模块的扩充块增删改 |
| `uncovered` | 涉及的导出没有任何可赋值比较。例如命名空间导出 |
| `direction` | 检查器的某条比较有一个方向不成立。附注保留两个方向与原因，供人判断。含义变了（类型与值）、类型参数个数变了、新增 `any`、重载换序，也记在这里 |
| `incomplete` | 检查器没有给出结论。例如比较行报错、还原后找不到导出 |
| `truncated` | 类型参数的实例组合超过上限 16 组，没有全部比较 |
| `diagnostics` | 还原的声明有编译诊断。例如快照记录的依赖在当前检出里没有构建 |

### 检查器怎样比较

1. 把两份快照的声明文件还原到成员目录下的虚拟目录（旧、新各一份），与一个比较文件放进同一个程序。外部包从当前检出的 `node_modules` 解析，两侧解析到同一份。
2. 每侧先做归一化：对别的模块与 `global` 的扩充改写成本侧的命名空间，两侧才能同时存在；对本成员模块的扩充保留。走到这里时扩充两侧相同（有差异已经整份 `review`），所以扩充本身不比较。脚本文件只还原新侧一份，否则同一份全局声明在程序里出现两次。方法签名改成函数类型的属性，避开方法参数的双变。本成员的 `unique symbol` 改成按文件与名字定位的字面量，两侧的品牌才能互相比较。类的 private 与 `#` 成员删除、protected 去掉，避开名义性。
3. 对两侧都有、标注相同、声明在本成员里的每个导出写两个方向的可赋值性。类型参数按约束实例化，取两侧约束的并集，字面量联合逐个展开，其余用不透明的品牌类型。新侧放宽了约束时，新的实参在旧侧不成立，这条比较记为 `incomplete`。另比一次不实例化的泛型整体，写法是泛型函数的返回值。值另比 `typeof`，并核对两侧能否当值用。
4. 「到达」只沿本成员还原的声明里出现的名字走，不进 lib 与外部包：用来判断哪些导出被改动涉及。
5. 每个比较都成立、声明文本却变了、又没有任何差异落到导出上时（例如没被引用的内部类型加了可选成员），整份记一项 `additive`。

`review` 的含义是「需要人判断」。它包括两方都破坏的改动、只破坏写方或读方的改动，也包括按「可加改动」表不破坏、但不在白名单里的改动，例如契约声明开放的联合加成员、给类型参数加默认值、放宽类型参数约束、给扩充接口加可选属性。`review` 不是 PR「契约变化」一节的级别。那一节的 none、additive 或 breaking 由人按「可加改动」表判定。

## 已知限制

- 白名单门失败关闭：只有正证据成立才是 `additive`。误报 `review` 的次数比只用检查器时多。这是 P1 只报告阶段的有意取舍：漏判 `additive` 会让人跳过本该细看的差异，误报 `review` 只多一次人工判断。
- 白名单只有两类。表里不破坏任何一方、但不在白名单里的改动一律 `review`。例如给类型参数加默认值、放宽约束、把必填的联合成员声明为开放。
- 可赋值不等于每种消费写法都能编译。`any` 会吞掉差异（新增 `any` 另判 `review`，已有的 `any` 不再细看）。名义类与品牌靠归一化处理。重载的选取、`this` 类型与泛型方差的极端形式可能双向可赋值却仍破坏某种写法。白名单门把这些改动挡在 `review`，检查器的方向只是附注。
- 泛型整体只用一种写法比较。检查器在两份相同、又互相嵌套的别名实例上有递归深度的启发式，可能把相同的类型判成不可赋值。已知的例子是 tool-contract 的 `ToolBindings` 一类：它的可加改动会落到 `review`，由人判断。另一侧的限制是：没有推断依据的类型参数会被实例化成 `unknown`，所以一侧不是泛型形状时，这种写法可能只证明一个方向。这只影响附注里的方向，不影响分类。
- 命名空间导出没有可赋值比较。它一有改动就是 `uncovered`。
- 没有约束的类型参数只用一个不透明的品牌类型实例化。只对某个具体实参（例如 `number`）生效的条件分支，实例比较看不到。白名单门把这类改动挡在 `review`，检查器的方向附注可能仍写两个方向都成立。
- 只比较本成员的声明。别的成员对本成员类型的 `keyof` 等派生在单成员比较里看不到。转导出的别的包的声明变化归那个包的快照。
- 外部包按当前检出解析，基线一侧用的也是当前的外部包。外部包本身的变化不归本成员。
- `/// <reference no-default-lib="true" />` 不进快照：TypeScript 6 只在 lib 文件里认它，打印器不输出它。对 TypeScript 6 的消费者它没有作用。
- 只看声明的形状。行为、文档、运行时校验与默认值不在快照里。
- 快照与 dist 一致只说明快照是最新的，不说明改动可加。
