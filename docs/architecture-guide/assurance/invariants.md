## 规则描述什么

状态不变量描述在规定观察点必须成立的关系，例如一个资源至多有一个当前写入拥有者。跨事件安全约束描述不能发生的序列，例如结果不能被归给另一调用。进展性质描述在明确前提下某事最终发生，例如已接纳的取消最终结算。[基础术语](../foundations/concepts.md)区分这些含义。

不应把所有正确性要求都写成静态 schema 或都称为状态不变量。两个字段各自合法，不代表其组合合法；每一帧格式正确，也不代表开始与结束顺序正确。

## 一条规则的完整含义

下表是描述要点，不是要求新建通用规则对象或引擎。

| 要点 | 应当明确的内容 |
|---|---|
| 标识与归属 | 稳定可引用的规则名，以及拥有语义和变更责任的能力 |
| 适用范围 | 适用契约版本、租户、实例、操作或数据集合 |
| 前提 | 环境假设、有效身份、外部能力或公平调度等条件 |
| 要求 | 状态关系、允许的事件序列，或必须最终达到的结果 |
| 成立边界 | 每个外部可观察状态、提交点、一次使用结束，或其他明确时点 |
| 强制位置 | 哪个操作阻止违规，或者什么协议使违规无法提交 |
| 验证与响应 | 可取得的独立证据，以及失败时拒绝、停止、报告或恢复的责任 |

内部多步操作可以经过外部不可见的中间状态，但必须说明可见性和提交边界。只说“最终一致”不能解释期间哪些读者可能看到什么，也不能替代进展前提。

## 执行与观察

规则是语义承诺。操作边界的强制约束负责保护承诺；运行时检查负责发现可观察的偏离；测试和形式模型在各自范围内探索行为。关闭一个诊断检查，不解除原本的授权、唯一性或状态转移约束。

独立检查应核对可能由不同路径产生的证据，例如事件与权威状态、多方组装的结果、开始与结束配对，或日志重建结果与实际请求。检查器先调用被测方法写入，再用同一方法读回，通常没有增加独立观察价值。

方法存在性、固定纯函数样例和自己的注册表变更，往往在类型、入口校验或测试中更直接。没有独立关系可检查时，可以不安装运行时检查；出现新的可独立偏离关系后再重新判断。

检查失败发生在哪里也很重要。发请求前的检查可能阻止外部效果；提交后的观察只能报告已经发生的偏离，不能让已提交事实变成未提交。失败响应必须与[交互阶段](../runtime/interaction.md)一致。

## 规则和检查器的演化

检查器可以作为有依赖、作用域和清理归属的能力动态装配，但检查器的生命周期不同于规则的有效期。检查注册应明确归属，安装失败撤除部分监听，退出后不能继续影响新代际。

重新装载的检查器需要说明观察基线从哪里恢复。仅监听现场事件时，无法声称覆盖了它装载之前的工作；若从历史重建，需要核对历史完整性和解释版本。

修改规则本身时，应说明现有状态如何满足新规则、在途操作归哪版规则、切换时是否存在未保护窗口。若不能满足新规则，应明确拒绝激活、先转换状态或显式退出受影响工作。不能把修改检查代码当成已完成全部语义迁移。
