## 抽象的价值

判断一个抽象，先看它隔离了什么真实变化、拥有哪项契约、保护什么不变量。名字听起来通用或未来可能有多个实现，不足以单独成立；明确的外部边界即使当前只有一个提供者，也可能值得抽象。

好的边界减少其他部分需要理解的内容。消费者若仍必须了解提供者内部状态、特殊错误和清理顺序，表面上的接口隔离尚未兑现，需要回到[能力契约](../modeling/capabilities.md)检查责任分配。

## 识别偏差

| 现象 | 应进一步判断什么 |
|---|---|
| 每条持久记录都变成插件实例 | 是否存在独立运行行为和资源生命期，还是只是服务管理的数据？ |
| 所有职责都进入一个通用管理器 | 是否有多项独立状态权威和不变量被混在一起？ |
| 相同结构在多个上下文重复定义 | 语义是否真的不同；如果只是边界投影，映射在哪里？ |
| 依赖依靠固定初始化顺序成立 | 能否明确说明实际需求和失效响应？ |
| 通过 Context 获得所有服务 | 可达范围是否超出当前职责和授权？ |
| 卸载返回后后台工作仍可改状态 | 静止条件、所有权登记或异步等待是否缺失？ |
| 超时一律转为失败再重试 | 是否遗失部分结果、未知外部效果和幂等条件？ |
| 每个包都安装自检插件 | 是否有独立证据可核对，还是重复自身实现？ |
| 热替换声称完全回滚 | 恢复范围是否包括外部效果、旧句柄和持久状态？ |
| 为未来分布式预建大量框架 | 当前缺少的是契约，还是确有运行需求的基础设施？ |

这些现象是调查入口，不是仅凭外观就判错的规则。判断应回到具体需求、状态和证据。

## 复杂度与复用

满足规格、边界和可验证性的成熟实现优先。复用时比较实际契约、生命周期控制和维护成本，不能只比较 API 是否相似；自建时需要说明现有实现具体缺少哪项必要能力。

选择改实现还是增加适配边界前，先明确依赖的维护权和目标契约的归属。按
[SYS-KERNEL](../../requirements/system/constraints.md#sys-kernel)，Cordis 消费官方发布包，
其余选定的 DSH 复用组件由本项目 fork 维护。fork 的上游实现是可追溯的设计起点；
其 API、包划分和调用限制不自动成为本项目必须保留的契约。需要改变行为时，先由
需求和目标契约明确差异，再在拥有相应职责的实现中直接表达，不因沿袭上游而额外
增加兼容包装。

维护权也不构成重构理由：符合要求的不变量和成熟实现继续复用；承载授权、生命周期
或部署责任的边界仍有价值，不能因源码可改而删除。保留源基线、变更依据与验证映射，
区分上游源码测试和实际采用的发布包或 fork 实现验证。

缓存、池化、并行、批处理或自定义协议会引入一致性和失败成本。优化性复杂度需要可重复的瓶颈证据。正确性或明确边界所需的机制，则说明它保护的规则，不把它伪装成尚无测量的性能收益。

更多高阶判断见 [工程判断 skill](../../../.meta_harness/agents/skills/harness-design-handbook/canonical/references/architecture/assurance/judgment.md)，具体风险类别见[防御性研发模式](../../defensive-patterns.md)。

## 判断的停止点

一个设计已经能直接解释所需行为、关键状态和失败边界，且合适的验证支持这些承诺时，可以停止扩展。不会因为其他专题存在，就要求当前能力也增加同类机制。

局部修正沿权威契约完成；边界变化则更新所属定义与证据。发现文档或实现冲突，先解决归属和决策状态；不能增加兼容包装，让相互矛盾的含义同时长期存在。
