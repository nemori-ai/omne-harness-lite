## 语言无关的表达

先描述集合、记录、关系、操作、事件和状态转移，再映射到实现语言。概念的意义不能依赖某个语言的对象地址、隐式异步上下文、装饰器或模块加载次序。

例如“消费者依赖提供者”应展开为需求、解析范围、有效绑定、失效条件及响应；具体使用依赖注入 API 是实现映射。一个 JSON 对象形状也不足以单独表达其生命周期和授权约束。

描述某项操作时，需要能辨认前置条件、输入、状态变化、结果与失败。声明某种保证时，需要能指向适用的观察范围和[规则](invariants.md)，避免用“安全”“原子”“可恢复”等词代替定义。

## 规格的分工

沿用[spec/ 的工具与组织约定](../../../spec/README.md)：

| 表达 | 主要用途 | 不能单独说明的内容 |
|---|---|---|
| 概念与契约文档 | 统一词汇、身份、边界、操作含义和决策理由 | 所有并发执行都满足性质 |
| JSON Schema | 约束交换和保存的数据形状，引用共享定义 | 跨请求权限、运行生命周期和最终进展 |
| Alloy | 描述结构关系，在给定范围内查找违反约束的结构 | 任意规模都成立，或真实运行必然终止 |
| TLA+ | 作为行为权威规格，描述状态变化、并发与时序性质 | 未建模的环境和实现细节自然正确 |
| 验收场景 | 说明消费者可观察结果，并约束不同实现 | 对全部状态空间的穷尽证明 |

不是每个概念都必须同时拥有所有表示。根据需要保护的性质选择合适工具，让不同表示引用同一语义定义；不要为了填满目录制造平行模型。

## 证据与追溯

一项性质应能追溯到规则、模型假设、实现边界和相关验证。数据投影或代码生成需要说明映射保留哪些含义；自动生成减少重复，不自动证明行为等价。

优先验证实际边界：贡献者卸载后资源是否消失，变更失败后实际处于什么状态，租户访问是否被拒绝，外部写入是否发生。只检查 mock 调用次数或 Agent 的成功文字，可能错过真正结果。

替换实现应使用共同契约场景。并发和恢复场景应覆盖关键交错或失败点，而不是机械复制实现分支。运行时检查、测试、有限模型检查与证明分别说明其覆盖范围，证据不能跨范围借用。

## 变更与验证范围

仅改变局部表达、且不影响已有契约时，采用与变更相称的检查；改变所有权、状态、事件顺序或跨边界行为时，需要验证相关性质。通过后无需为了增加数量重复无关验证。

契约或假设改变后，应识别旧证据中哪些已经失效。规格版本遵循所属目录约定；保持新旧版本与实现、场景的映射，不能引用旧版本通过的结果来声称新行为已经验证。

形式化结论要说明假设和范围：有限模型没有找到反例，意味着在已建模范围内没有发现该类违反；运行时检查没有报错，只覆盖它实际观察到的关系。需要更强保证时，再增加相应的模型或证明工作。
