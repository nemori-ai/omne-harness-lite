## 使用方式

本文帮助检查设计能否被其他 agent 理解、实现和验证。它是语义要点，不是固定表单、JSON Schema 或要求每项都单独落文件的模板。只展开对当前能力有实际影响的内容。

一个简单的纯计算能力可能只需要输入输出、失败和共享类型；管理长生命周期任务的能力则必须说明所有权、取消和恢复。需要多少描述，由行为决定。

## 沿完整动作链核对组合

从真实触发走到契约要求的结果，检查每次跨边界交接前后：谁拥有工作和权威状态，
交出什么身份、资格或结果，谁负责下一步，以及接收被拒绝或失败时责任留在哪里。
方法和状态各自合法，不足以证明整个操作有合法终点。

针对当前能力展开正常、拒绝、失败、撤除或恢复中会改变责任的分支；不要求机械
穷举所有类别。例如，执行者已交还工作资格后，授权直接拒绝时仍需有人结算或
接续原工作；仅为允许和待批准建立后续路径，会遗留无人负责的工作。这里是
检查方法，不选择某个能力应终止、重试还是等待的产品政策。

每个必要交接都应落到所属能力或组合契约，再对应到提供者和应用设计。共享类型、
包布局和依赖注入图分别只能说明部分关系；尚未完成的最后一段不能被“接口齐全”
掩盖。只有整体性质无法归属单一能力时才另建组合契约，不为一次联调重复各方承诺。

## 引用与完成标准

引用已有概念和契约时，指向其权威位置及所需版本；只有语义不同或边界投影确有必要时才建立新表示，并明确映射。基础词汇不应在每份设计中重新解释一遍。

读者应能够从契约判断正常使用、依赖缺失、并发、撤除和失败时的可观察行为。尚未决定的政策应明确标出，不能用一个看似完整的数据结构掩盖行为空缺。

描述完整意味着对所需行为有足够解释和验证依据，不意味着覆盖所有想象中的部署形态或引入全部机制。发现需要新增框架时，回到[架构判断](../assurance/judgment.md)检验其价值。

结论标明语义、提供者映射、应用装配和验证分别覆盖到哪里；实施入口按
[设计就绪](../../maintenance/spec-maintenance.md#设计就绪与实施入口)判断，
不能把一次限定范围的语义审阅扩大为全部实现设计已完成。
