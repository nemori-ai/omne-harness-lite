## 边界的依据

一个能力边界需要有可以独立解释的责任：它保护哪些关系，向谁承诺哪些行为，哪些实现变化应被隔离在内部。优先围绕这些责任组织服务，具体包和插件数量随后确定。[术语定义](../foundations/concepts.md)区分了这些单位。

定义、提供和消费是角色。服务可以直接实现一个契约，也可以通过注册表接纳多个提供者；仅为给同一个操作改名而增加中间服务，没有形成新的边界。普通计算不需要资源所有权或动态装配时，可以直接作为函数表达。

存储需求本身不要求聚合、Repository 或插件实例。需要发布管理的内容定义可以由服务保存为记录；需要独立启动和结束的行为才需要对应运行实例。数据结构复用其权威定义，不能在每个消费者处复制一份。

## 区分组合关系

| 关系 | 需要说明的含义 |
|---|---|
| 代码依赖 | 哪些公共定义和实现被引入，代码从哪里分发？ |
| 运行依赖 | 哪项能力可用时消费者才可以执行？ |
| 所有权 | 谁负责释放实例、注册和任务？ |
| 作用域 | 名称如何解析，贡献和活动对谁可见？ |
| 业务关系 | 哪些身份、事实和操作在业务上关联？ |
| 部署拓扑 | 哪些部分共同部署，哪些通信跨越故障边界？ |

一棵父子树可以承载其中一种关系。需要把两种关系绑定时，必须说明绑定的理由和变化后果。例如创建了一个子 Agent，不足以自动证明它继承父 Agent 的所有权限。

## 依赖与解析

依赖至少需要明确目标契约、解析范围、必需性和有效期。必需依赖缺失时不得继续按“已就绪”执行；等待、拒绝接纳或结束实例，是需要选择的不同政策。可选依赖缺失时也应有解释得通的行为，不应靠吞掉异常形成默认值。

同名提供者冲突应被拒绝或由明确的选择规则处理。依赖环涉及的是能否激活和取得进展：应说明如何打破循环、延迟哪段行为，或拒绝该组合；不能只验证每个服务名最终都出现在配置中。

依赖声明还包括撤除语义。消费者能否继续持有旧绑定、旧提供者何时可以释放、新请求何时选择新提供者，见[动态演化](../runtime/evolution.md)。有多个相互依赖的字段时，不能在一次操作中分别读取可能来自不同代际的配置。

## 注册条目与替换

依赖注册表和依赖其中某个条目不是同一个条件。例如渲染器需要某个变量，注册表仍存活并不能证明该变量的提供者仍可用。条目级依赖可以通过受管绑定、订阅或独立的生命周期能力表达，选择应与撤除和使用边界相匹配。

替换是否成立，要从消费者可以观察的行为判断。相同方法名和数据形状不足以证明相同含义；错误、持久性、取消和授权保证也是契约的一部分。对多个提供者，用共同的契约场景验证它们兑现相同承诺，详见[规格与证据](../assurance/specification.md)。

例如，本地执行和远程执行可以共享命令执行契约，但远端超时后操作是否仍在运行必须有明确表示。若现有契约只接受“成功／失败”，就需要先修正边界表达，而不是让远程实现伪造确定的失败。
