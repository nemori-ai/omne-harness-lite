## 确定权威来源

每类状态都应说明谁拥有其含义、谁能修改，以及观察者怎样取得可信结果。区分[运行状态、事实、投影与缓存](../foundations/concepts.md)，避免多个存储副本各自成为独立真相。

需要多个视图时，明确导出或复制关系。边界投影可以采用不同形状，但必须说明身份、遗漏字段、时间点和失败含义的映射；表达相同语义的结构应复用权威定义。

例如，发布记录决定某个内容版本是否可引用；运行时索引帮助快速找到它。索引重建不能擅自把未发布内容变成已发布内容，缓存命中也不能绕过当前授权。

## 选择保存方式

保存当前状态、记录事件或保留快照，应由恢复、查询和审计需求决定。事件记录只有在顺序、词汇、版本和折叠语义明确时，才能支持可靠重放；普通调试日志不能直接承担这个角色。

投影说明输入来源、折叠规则和有效位置；缓存说明失效与重建条件。派生结果与权威来源不一致时，应能定位哪条映射出了问题，不通过反向覆盖事实来隐藏差异。

保存历史不要求运行时对象永久存活。需要重建的是被契约承诺保留的状态及关系；已卸载实例的内部对象布局不必成为持久格式。

## 存储操作的承诺

存储是可替换的能力，但其契约必须足以支持消费者的不变量。需要按实际操作说明：

| 问题 | 必须区分的含义 |
|---|---|
| 写入结果 | 已接纳、对当前读者可见、已提交、可抗约定故障 |
| 并发 | 谁拥有写入权，冲突如何处理，顺序由哪层建立 |
| 原子性 | 保证覆盖单条写入、一批写入还是多个资源 |
| 读取 | 返回哪个观察点，是否允许陈旧或部分结果 |
| 关闭 | 是否排空写入，何时释放所有权，失败如何观察 |
| 格式 | 哪些版本可以解释，无法解释的数据怎样拒绝或转换 |

单次后端调用原子，不意味着上层多次调用组成事务。跨写入规则需要由拥有该规则的能力建立提交、恢复或补偿机制。

已持久提交后，通知失败不能被报告成“写入没有发生”。提交事实与通知结果应分别表达，避免调用者盲目重试造成重复效果；详见[交互协议](../runtime/interaction.md)。

## 生命周期与恢复

定义撤除、运行实例停止、句柄关闭、缓存失效和持久数据删除是不同操作。只要业务事实需要保留，插件卸载就不能隐式删除它。旧句柄是否能在后端替换后继续使用，应在契约中明确。

恢复还要区分物理数据完整性与业务完成状态。存储能够返回完整记录，不足以判断远端工具是否已完成外部操作；未知结果需要核实、幂等重试或由上层政策处理。

对每种恢复设计，说明从哪里恢复、恢复到哪个合法状态，以及恢复本身中断后能否再次执行。进一步的替换例子见[存储提供者替换](../examples/storage-replacement.md)。
