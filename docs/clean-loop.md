# 整洁回路

这一页讲两件事：**这个仓库靠什么让敏捷流程、架构设计和代码编写持续待在整洁的范围里**，以及
**[整洁之道的条目全表](../.meta_harness/research/clean-code-doctrine-current/doctrine-catalogue.md)里每一条在这里由谁来管**。
它是开发文档：只讲这个仓库怎么开发，不规定被设计的系统该是什么样。

## 三句话

- **约束结果，不约束做法。**不规定 agent 先写测试还是后写、函数怎么拆；只看交回来的东西量出来是什么样。
- **反馈事实，不下指令。**工具说的是「这个函数圈复杂度 14，没有测试覆盖」，不说「你应该把它拆开」。
- **阈值管边界，不管路径。**只有四条线破了不许合并，其余都只报告；怎么回到线内由干活的一方自己定。

所以 agent 的固定提示里只有「跑哪条命令、把输出贴进交付说明、对红项逐条交代」这一类句子。
规矩不写成提示词里的条条框框：能量的做成传感器，量不了但问得出后果的做成评审问法，剩下的归人。

## 回路怎么转

```text
改动 ──→ 传感器（make metrics／make loop-status）──→ 带位
                                                      │
              ┌───────────────────────────────────────┤
              │ 正常      什么都不用做                │
              │ 提醒      交付说明里逐条交代          │  ← 实施的 agent
              │ 处置      生成清理草稿，等人批准      │  ← 负责人批准后才派
              │ 反复变红  标为结构问题，上报          │  ← 负责人：方向与拆分
              │ 硬线被破  不许合并                    │
              └───────────────────────────────────────┘
```

| 带位 | 意思 | 谁动 |
|---|---|---|
| 正常 | 在提醒线以下 | 没人需要动 |
| 提醒 | 过了提醒线，或比基线差了 | 实施的 agent 在交付说明里逐条写「已处理」或「保留，理由是……」；没有交代的退回 |
| 处置 | 到了处置线；之后要回落到**解除线**及以下才算恢复，在两条线之间来回不算好了 | `make loop-status` 给超预算的成员各生成一份清理草稿；负责人批准、驳回或写明何时再看 |
| 结构问题 | 同一个成员清理之后又反复进入处置 | 不再派清理。这是拆分或方向的问题，归负责人，agent 只提反驳 |

**四条硬线**（破了不许合并，其余一律只报告）：

1. 依赖方向与环——`pnpm run lint:rules` 的方向规则，`make loop-status` 也会标出。
2. 验收没有被实施者改动——`make acceptance-lock BASE=<任务基线>`。
3. 主线保持绿——合并前在待合并的提交上跑完整的 `make check`。
4. 传感器有数据——一项指标量不出来不等于它是好的。严格模式（`make loop-status STRICT=1 BASE=… OUT=…`）下，
   配置里开着的传感器有哪个没数据就判失败并指名；传感器自己会不会悄悄失灵，由一份种了已知违规的小夹具每次跟着测试跑来守。

**第一、二、四条都接在 `make check` 的最后一步**（严格模式的回路状态），所以第三条那一轮完整检查通过，就同时说明这三条没破。
远程 CI 关着的时候，这一轮本地检查就是合并前唯一的门。

**收工时的反馈**：agent 收工的那一刻，若这次变更碰了产品源码、且有要解释的红项，宿主的收工钩子会把那几条读数作为事实交还给它——
只说位置与数值，不说该怎么改；同一分支上同一组读数只说一次，钩子自己出错从不拦人。它是提醒，不是门：
没被提醒不等于没有红项，交代了没有仍由交付说明与接受的人核对。怎么生效、怎么关，见[宿主钩子的源](../.meta_harness/agents/hooks/README.md)。

阈值、窗口与开关都在 [`tools/ts-checks/loop.config.json`](../tools/ts-checks/loop.config.json) 与
[`metrics.config.json`](../tools/ts-checks/metrics.config.json) 里。它们是负责人的判断，可以改，**改的理由写进那次提交**；
不为了让某次交付变绿而放宽。现在的数是起步值，没有用真实交付校准过。

## 入口

| 想知道 | 跑什么 |
|---|---|
| 这次改动的结构与度量 | `make metrics BASE=<任务基线>`，摘要原样贴进交付说明 |
| 各项指标的带位、这次变更里要解释的红项、哪些成员超了预算 | `make loop-status BASE=<任务基线>` |
| 验收有没有被动过 | `make acceptance-lock BASE=<任务基线>` |
| 合并前三条硬线（方向与环、验收锁、传感器有数据）破没破 | `make check` 的最后一步；单独跑是 `make loop-status STRICT=1 BASE=<基线> OUT=<目录>` |
| 在主线上留一条趋势 | 干净的主线提交上跑 `make loop-status`，它自己追加一条快照；别的提交上要留就加 `SNAPSHOT=1` |
| 给一张故事卡记时间点（提出、第一次能跑、接受） | `make loop-card CARD=<卡号> EVENT=proposed\|runnable\|accepted` |
| 流程走得怎么样：卡的前置时间、每周接受数、剩余卡数、提交大小、测试耗时与债的走向 | `make loop-health`，出一张离线可开的页面 |

每个入口覆盖什么、**不能声称什么**，在[验证与证据](verification.md#检查入口)；传感器各自的算法、出处与查不出的东西，在
[tools/ts-checks](../tools/ts-checks/README_ZH.md)。这里不抄第二份。

## 清理任务

超预算的成员由 `make loop-status` 生成清理草稿，落在主检出的 `tmp/clean-loop/proposals/`。草稿只列事实与边界：
要清理的条目（带位置）、行为锁（现有测试只读）、解除条件（回落到解除线及以下）、不许动的东西。
`examples/` 下的成员不判预算、不出草稿——它们是阶段性的演示，不长期维护。

**草稿不是派发。**主会话把草稿报给负责人，负责人批准之后才按[清理任务的派发模板](../.meta_harness/agents/roles/cleanup-task.md)派出去；
实施的 agent 平时只在它正在改的文件里顺手清理，范围之外的列为清理候选，不自己动手。

## 条目对照表

[条目全表](../.meta_harness/research/clean-code-doctrine-current/doctrine-catalogue.md)的每一条，在这里归到五类之一：

| 类别 | 意思 |
|---|---|
| 传感器 | 有确定性的检查或度量在量它。落点写入口；还没建的写明排在哪 |
| 评审问法 | 量不了，但评审时有一问对着它，且那一问要落到工具输出或具体反例。问法的正文在各自的评审判据里，这里只指路 |
| 归人 | 由负责人判断或抽查，不交给工具，也不交给 agent |
| 不适用 | 不是一条可以照做的要求（定义、立场、理由、总目），或它针对的情形这个仓库没有 |
| 不采 | 这个仓库明确不照它做，落点写我们取的是什么 |

一条只归一类，按**主要靠什么兜住**归；同时沾着别的，写在落点里。条目名与全表逐字一致，方便对回去。
「现状」一栏只有两个值：**已有**——落点今天就在；**待建**——落点还没建成，写明排在哪。
各类条数由 `make loop-status` 数出来，不在这里手写。

评审问法指到的三份判据：设计评审的[「选择」判据](../.meta_harness/agents/skills/harness-design-handbook/canonical/references/review/choice.md)
（下面简称「选择」）、[实现评审检查表](../.meta_harness/agents/roles/implementation-review-checklist.md)（简称「检查表」，后面的数字是第几问）、
手册的[判断](../.meta_harness/agents/skills/harness-design-handbook/canonical/references/architecture/assurance/judgment.md)。
「研发品味」指[这一份](../.meta_harness/agents/roles/engineering-taste.md)。

## 这张表说明不了什么

- **归到「传感器」不等于那一条被守住了。**传感器量的是代理指标：圈复杂度低不等于函数只做一件事，没有词法重复不等于没有重复的判断。
- **归到「评审问法」的，只有派了评审才有人问。**实现评审默认不派，L2／L3 或有没交代的红项才派。
- **归到「归人」的没有任何自动的东西兜着。**负责人不抽查，它就没人管。
- 条目全表里标着「目录层」「仅转述」的条目，原文没有读过；它们的归类是按小节标题的字面意思做的。
