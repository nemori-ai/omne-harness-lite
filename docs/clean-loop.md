# 整洁回路

这一页讲两件事：**这个仓库靠什么让敏捷流程、架构设计和代码编写持续待在整洁的范围里**，以及
**[整洁回路的条目集合](../tools/repo-toolchain/resources/clean-loop-entries.md)里每一条在这里由谁来管**。
它是开发文档：只讲这个仓库怎么开发，不规定被设计的系统该是什么样。

## 三句话

- **约束结果，不约束做法。**回路不规定函数怎么拆，只看交回来的东西量出来是什么样。测试先设计、实施可按 TDD 顺序，这些做法归[方法层](engineering/skills.md#ub-mode-研发品味)，与回路互补。
- **反馈事实，不下指令。**工具说的是「这个函数圈复杂度 14，没有测试覆盖」，不说「你应该把它拆开」。
- **阈值管边界，不管路径。**只有四条线破了不许合并，其余都只报告；怎么回到线内由干活的一方自己定。

所以回路给 agent 的固定提示里只有「跑哪条命令、把输出贴进交付说明、对红项逐条交代」这一类句子。
规矩不写成提示词里的条条框框：能量的做成传感器，量不了但问得出后果的做成评审问法，剩下的归人。

## 回路怎么转

```text
改动 ──→ 传感器（pnpm run metrics／pnpm run loop:status）──→ 带位
                                                      │
              ┌───────────────────────────────────────┤
              │ 正常      什么都不用做                │
              │ 提醒      交付说明里逐条交代          │  ← 实施的 agent
              │ 处置      生成清理草稿，等人批准      │  ← 负责人批准后才派
              │ 反复变红  标为结构问题，上报          │  ← 负责人：方向与拆分
              │ 硬线被破  不许合并                    │
              └───────────────────────────────────────┘
```

| 带位 | 意思 | 谁动 |
|---|---|---|
| 正常 | 在提醒线以下 | 没人需要动 |
| 提醒 | 过了提醒线，或比基线差了；成员预算里基线快照有的成员只看「比基线差了」，绝对的提醒线只管新成员 | 实施的 agent 在交付说明里逐条写「已处理」或「保留，理由是……」；没有交代的退回 |
| 处置 | 到了处置线；之后要回落到**解除线**及以下才算恢复，在两条线之间来回不算好了 | `pnpm run loop:status` 给超预算的成员各生成一份清理草稿；负责人批准、驳回或写明何时再看 |
| 结构问题 | 同一个成员清理之后又反复进入处置 | 不再派清理。这是拆分或方向的问题，归负责人，agent 只提反驳 |

**四条硬线**（破了不许合并，其余一律只报告）：

1. 依赖方向与环——`pnpm run lint:rules` 的方向规则，`pnpm run loop:status` 也会标出。
2. 验收没有被实施者改动——`pnpm run acceptance:lock --base <任务基线>`。
3. 主线保持绿——合并前，在待合并的提交上计算好影响面，再运行受影响、因此需要执行的检查。检查范围包括所需的构建、类型检查、测试和可执行验收，以及共同硬线检查。交付说明记录基线、提交、范围、依据与结果。`pnpm run check` 按影响面打印计划并执行这些检查；未选中的检查没有运行，交付说明应如实列出。
4. 传感器有数据——一项指标量不出来不等于它是好的。严格模式（`pnpm run loop:status --strict --base … --out …`）下，
   配置里开着的传感器有哪个没数据就判失败并指名；传感器自己会不会悄悄失灵，由一份种了已知违规的小夹具每次跟着测试跑来守。

`--strict --scope engineering` 是 `omne-loop-status` 的工程范围严格模式，需要时显式传入；`pnpm run check` 的严格一步不传 `--scope`。只有当前树、固定 targetBase、实际 merge-base 和每个 taskBase 均无受维护产品源码与测试时，duplication 与 assertions 的无数据读数才标为工程范围不适用。
原始 no-data 保留，报告给出精确提交与计数。任何一处仍有输入、基线未知、读取失败或其他启用传感器无数据，均不能用此范围放行。
关闭的传感器单列 off。普通本地检查与默认 strict 继续要求所有启用传感器有数据；方向、环与验收锁在两种范围中都生效。

**第一、二、四条都接在严格模式的回路状态中**，`pnpm run check` 把它放在最后一步。手动执行受影响范围时，也要完成这三条共同硬线检查。
远程 CI 关着的时候，本地检查证据就是合并前的门。通过受影响范围的检查，不表示未执行的检查也通过。

**要解释的不替历史交代**：「这次变更里要解释的红项」里的函数，只列碰过、超线、且比基线涨了或新出现的；
原来就在线外、这次没有变差的只数个数。agent 改一行存量的大函数不必替它的历史交代，让它更糟才要。

**收工时的反馈**：agent 收工的那一刻，若这次变更碰了产品源码或架构预期、且有要报告的读数，宿主的收工钩子会把那几条读数作为事实交还给它——
只说位置与数值，不说该怎么改；同一分支上同一组读数只说一次，钩子自己出错从不拦人。它是提醒，不是门：
没被提醒不等于没有红项，交代了没有仍由交付说明与接受的人核对。没有 task context 时，钩子的基线是主线与活跃集成轨道里离 HEAD 最近的合并点，细则见[收工钩子](../tools/repo-toolchain/README_ZH.md#收工钩子)。怎么生效、怎么关，见[宿主钩子的源](../.meta_harness/agents/hooks/README.md)。

**长期验证跟着场景走。**验收场景和声明覆盖它们的可执行验收随产品持续维护，不按任务数量复制。`pnpm run acceptance:scenarios`分别报告当前产品的覆盖声明、执行与接受；缺编号场景的topic单列未覆盖。覆盖声明不证明验收已执行、通过或交付已接受。实际运行和接受分别核对。合并前按影响面选择必要验收，验收耗时由传感器报告。放置和维护规则归[源码布局](workspace.md#目录与内容归属)。

阈值、窗口与开关都在仓库根 [`repo-toolchain.config.json`](../repo-toolchain.config.json) 的 `loop` 与
`metrics` 两节里。它们是负责人的判断，可以改，**改的理由写进那次提交**；
不为了让某次交付变绿而放宽。负责人 2026-10-02 照试点时量到的分布定过一轮（成员预算的两组线、红色成员数只与基线比、
topic 翻动的线、验收耗时的预算）；其余的数仍是起步值，都还没有用多轮真实交付校准过。

## 入口

| 想知道 | 跑什么 |
|---|---|
| 这次改动的结构与度量 | `pnpm run metrics --base <任务基线>`，摘要原样贴进交付说明 |
| 改动碰到的代码，测试守不守得住 | `pnpm run mutation --base <任务基线>`，**只报告、不画线**：改动行上存活与无覆盖的变异体原样贴进交付说明，读数攒在主检出的 `tmp/mutation-ledger/` |
| 各项指标的带位、这次变更里要解释的红项、哪些成员超了预算 | `pnpm run loop:status --base <任务基线>` |
| 验收有没有被动过 | `pnpm run acceptance:lock --base <任务基线>` |
| 场景的验收覆盖声明及工具状态标签 | `pnpm run acceptance:scenarios` |
| 只跑可执行验收 | `pnpm run acceptance`（缺省先构建；`pnpm run check` 里它排在构建之后） |
| 合并前三条硬线（方向与环、验收锁、传感器有数据）破没破 | `pnpm run check` 的最后一步；单独跑是 `pnpm run loop:status --strict --base <基线> --out <目录>`，之前要有对应候选的验收运行或影响面显式跳过账本；跳过不表示验收通过，候选绑定的限制见[工具说明](../tools/repo-toolchain/README_ZH.md#验收耗时) |
| 在主线上留一条趋势 | 干净的主线提交上跑 `pnpm run loop:status`，它自己追加一条快照；别的提交上要留就加 `--snapshot` |
| 提交大小、测试耗时与结构指标的走向 | `pnpm run loop:health`，出一张离线可开的页面 |

每个入口覆盖什么、**不能声称什么**，在[验证与证据](verification.md#检查入口)；传感器各自的算法、出处与查不出的东西，在
[tools/repo-toolchain](../tools/repo-toolchain/README_ZH.md)。这里不抄第二份。

## 清理任务

超预算的成员由 `pnpm run loop:status` 生成清理草稿，落在主检出的 `tmp/clean-loop/proposals/`。草稿只列事实与边界：
要清理的条目（带位置）、行为锁（现有测试只读）、解除条件（回落到解除线及以下）、不许动的东西。

**草稿不是派发。**主会话把草稿报给负责人，负责人批准之后才按[清理任务的派发模板](../.meta_harness/agents/roles/cleanup-task.md)派出去；
实施的 agent 平时只在它正在改的文件里顺手清理，范围之外的列为清理候选，不自己动手。

## 条目对照表

[条目集合](../tools/repo-toolchain/resources/clean-loop-entries.md)的每一条，在这里归到五类之一：

| 类别 | 意思 |
|---|---|
| 传感器 | 有确定性的检查或度量在量它。落点写入口；还没建的写明排在哪 |
| 评审问法 | 量不了，但评审时有一问对着它，且那一问要落到工具输出或具体反例。问法的正文在各自的评审判据里，这里只指路 |
| 归人 | 由负责人判断或抽查，不交给工具，也不交给 agent |
| 不适用 | 不是一条可以照做的要求（定义、立场、理由、总目），或它针对的情形这个仓库没有 |
| 不采 | 这个仓库明确不照它做，落点写我们取的是什么 |

一条只归一类，按**主要靠什么兜住**归；同时沾着别的，写在落点里。条目名与工具维护的集合逐字一致，方便对回去。
「现状」一栏只有两个值：**已有**——落点今天就在；**待建**——落点还没建成，写明排在哪。
各类条数由 `pnpm run loop:status` 数出来，不在这里手写。

评审问法指到的三份判据：设计评审的[「选择」判据](../.meta_harness/agents/skills/harness-design-handbook/canonical/references/review/choice.md)
（下面简称「选择」）、[实现评审检查表](../.meta_harness/agents/roles/implementation-review-checklist.md)（简称「检查表」，后面的数字是第几问）、
手册的[判断](defensive-patterns.md#dp-10-规格实现与证据对齐)。
「研发品味」指[这一份](../.meta_harness/agents/roles/engineering-taste.md)。

## 这张表说明不了什么

- **归到「传感器」不等于那一条被守住了。**传感器量的是代理指标：圈复杂度低不等于函数只做一件事，没有词法重复不等于没有重复的判断。
- **归到「评审问法」的，只有派了评审才有人问。**实现评审默认不派，L2／L3 或有没交代的红项才派。
- **归到「归人」的没有任何自动的东西兜着。**负责人不抽查，它就没人管。
- 条目全表里标着「目录层」「仅转述」的条目，原文没有读过；它们的归类是按小节标题的字面意思做的。
