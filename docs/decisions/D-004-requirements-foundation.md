# D-004：系统目标与产品要求作为设计基础

## 决定与依据

采用独立的 `docs/requirements/` 维护系统目标、产品特性和用户指定的全局要求。
产品按环境、用户、智能体三维组织，一项一个主正文，副维度引用；稳定身份独立
于路径和分类。确认按具体正文范围记录，用户明确要求直接成立，来源补充和未决
部分分别标明。

已确认要求是系统建模、能力定义、架构、决定与产品化的前提。继续使用
proposals → decisions，决定在有效需求前提和适用范围内记录已接受选择，不能
通过设计接受削弱要求。新要求改变旧前提时，标出冲突范围并停止将该部分作为新
工作的默认依据，形成必要的修订和取代；旧接受记录与已发布规格保留。

接受设计时记录需求身份、确认条款、Git commit 与当时路径；消费基线由随交付
保存的不可改指保留引用保护，并验证独立恢复。当前需求页与 Git 历史共同维护
演进；不新增逐次 vN 目录、全局需求 JSON 注册表或人工双向关系库。

需求依据为[提案中的用户输入及接受记录](../proposals/requirements-foundation/README.md)。
本决定处理文档治理，不是消费某项产品要求的实现设计，因此不附加无关 PF 身份。

## 与既有决定的关系

本决定补充 D-001 的 docs 归属，在其单义定义与规格分类基础上增加需求层；补充
D-002 已承认的用户新要求输入变化，明确决定权威的有效需求前提及冲突处置。
没有撤销两者原有选择，故 `supersedes` 为空；D-001、D-002 原文与未受影响范围
保留。D-003 的防御评估职责保持适用。后续实质取代仍须按 D-002 记录强理由。

## 理由与边界

单页会随逐项叙述持续膨胀；只有架构投影和候选材料不足以维持独立的需求前提。
按主题拆分并由下游记录采用范围，既支持持续增长，也避免复制定义和伪造历史依据。
Git 基线需要额外保留与恢复验证，换取 squash 或分支清理后的可复查性。

接受范围包括组织、权威、确认、追溯、迁移及相称检查。omne-next 的具体继承截止
范围、未来承诺是否持续继承、动态定义量词及产品精确达成判断仍归各需求未决项；
本决定不接受租户、模型或 Agent 核心候选，不发布业务规格。

规则归[需求维护](../maintenance/requirements.md)，实施与证据归
[迁移记录](../maintenance/migrations/2026-09-12-requirements-foundation.md)。
