# RFC-0011：主干准入与多层轨道

规则与维护责任见[RFC入口](README.md)。本提案是四条主干准入规则的完整正文，并增加多层轨道。

- **取代 RFC-0004。** 本提案整篇取代 [RFC-0004](RFC-0004-trunk-pr-admission.md) revision 1 中仍然有效的范围，即扣除 [RFC-0008](RFC-0008-repo-toolchain-trust.md)「决定范围」第 1 至 8 项与 [RFC-0009](RFC-0009-adoption-and-local-tool-retirement.md)「决定范围」第 1 至 12 项之后的全部条款。本提案接受后，RFC-0004 的状态改为 superseded。
- **复述 RFC-0008 与 RFC-0009。** 这两篇提案取代 RFC-0004 的那部分内容，本提案在第 16 至 18 节复述原文，并在每节末尾注明出处。复述只为让读者不必拼读多篇提案。这些条款仍由 RFC-0008 与 RFC-0009 拥有，以原文为准。
- **部分取代 RFC-0009。** 本提案修改 RFC-0009 的三处条款：policy registry 的轨道字段、轨道退役由 admin 操作 registry 与分支的规则，以及“`gate-track` 读取轨道登记”的陈述。精确范围见「决定范围」。
- **部分取代 RFC-0002。** 本提案决定 [RFC-0002](RFC-0002-engineering-toolchain.md) 留给准入规则一起决定的准入缓存策略：进入任何一条主干之前的检查不读 turbo 任务缓存，只写本地缓存；是否写远程缓存仍归 RFC-0002 的未决项。精确范围见「决定范围」。
- **多层轨道。** 轨道的上游可以是 main，也可以是另一条轨道。来源是 [#420](https://github.com/nemori-ai/omne-harness-lite/issues/420) 的提案与 [PanQiWei 的决定](https://github.com/nemori-ai/omne-harness-lite/issues/420#issuecomment-6268204990)。

提案采用、规范写回、实现和交付接受分别判断。

## 问题与有效输入

### 需求

一项较大的工作可能需要自己的集成层。它下面有多张卡，这些卡要先互相集成，形成完整的结果后再进入上一级轨道。现在的规则只有一层轨道，这样的工作只能直接在一条责任轨道上进行。它的半成品与该轨道上的其他工作混在一起，不能单独提升，也不能单独暂停。

另一个问题是准入规则分散在三篇提案中。RFC-0004 的一部分被 RFC-0008 取代，另一部分被 RFC-0009 取代，第二阶段的设计已接受但没有写回。读者要拼读三篇提案，才能知道哪些条款仍然有效。

### 已观察的事实

所核输入为 main `dab083a6d28cb8d5159f9556020238efe63498b9` 与 `github-gate` `f3783d4dab9f24c415d4cb85f7b1992ff6d39ad1`，读取日期为 2026-10-19。

准入规则：

- [现行准入](../engineering/integration.md#现行准入)规定：轨道接受个人分支或 main 的 PR；main 只接受 `integration/*` 的 PR；stable 只接受 main 的 PR；main 向轨道的同步是唯一的反向流动。

`gate-publish.yml`：

- head 与 base 都是 `integration/*` 时拒绝。head 为 `stable`、`release`、`github-gate` 时拒绝。
- 只在目标为 main 时，核对来源轨道的 first-parent 提交都有目标为该轨道的 unit。目标为 stable 时，对 main 做同样的核对。核对的范围下限先取 `gate/cutover.json` 中该分支的切换点，没有时再取 `omne/gate/track/<名>` 标签指向的提交，两者都没有就拒绝。
- 工具链审批在下列任一情形下不适用：模式不是合并（即进入 stable）；base 不是 `integration/*`；head 是 `main`。
- 并发组按 PR 号划分（`gate-publish-pr-<PR号>`），不取消进行中的运行。
- 确认后核对 PR head 与 base 在派发后没有变化，构造合并，推送时以派发时读到的目标为 lease。
- 发布决定评论发在 PR 上，内容为目标、PR head、结果、记录标签、平台记录的确认者、运行链接、确认说明原文，命中工具链路径时还有工具链确认的确认者与说明。推送后流程在 PR 上补记结果。
- 记录标签的正文是 `omne-gate-record:v1` JSON，字段为 `schema`、`target`、`base`、`head`、`result`、`pr`、`mode`、`confirmedBy`、`run`、`gate`，进入 stable 时另有 `checkpoint`。

`gate-track.yml`：

- 要求新轨道的起点在 main 的 first-parent 历史上。
- 只在分支与 `omne/gate/track/<名>` 都不存在时创建。
- 起点标签的 JSON 正文有 `schema`、`target`、`mode`、`result`、`issue`、`confirmedBy`、`run`、`gate`，没有上游字段。

轨道与 registry：

- 远端现在没有任何 `omne/gate/track/*` 标签。`gate/cutover.json` 登记了 main、`integration/legacy-refactor` 与 `integration/engineering-toolchain` 的切换点。
- 切换点与 registry 的 `initialMain` 不是同一个提交。例如 legacy-refactor 的切换点是 `3522ffe7`，`initialMain` 是 `3aee8019`。
- 远端的 `integration/` 分支只有 legacy-refactor 与 engineering-toolchain 两条。`integration/development` 仍在 registry 中登记为 retiring，分支已经不在远端。
- [policy registry](../engineering/integration-policy.json) 的轨道条目只有 `id`、`branch`、`owner`、`source`、`status`、`initialMain`。`tools/dev-flow/src/integration/policy.ts` 拒绝其他字段。registry 只由本地集成工具（`start`、`status`、`task-sync`）读取。`github-gate` 上的流程都不读 registry。
- 任务 binding 的 route 有 `track`、`global`、`cross-track` 三种（`tools/dev-flow/src/delivery/binding.ts`）。后两种的目标分支是 main（`sync.ts` 的 `routeTarget`）。但 `gate-publish` 拒绝个人分支直接进入 main，所以这两种 route 现在没有可用的准入路径。

不需要修改的部分：

- 双基线与 `task-sync` 只认任务的目标分支。轨道名保持扁平时，它们不受层级影响。
- 收工钩子有 task context 时用 taskBase 与 targetBase，没有时与主线求合并点，与轨道无关。
- `gate-release` 要求提交在 main 或某条轨道的 first-parent 历史上，并有 unit 记录，与层级无关。

第二阶段：

- RFC-0004 的第二阶段设计已经接受，但没有写回，也没有实施。现行正文只在 [integration.md「第二阶段目标」](../engineering/integration.md#第二阶段目标)记录了方向。

### RFC-0004 的依据

RFC-0004 的方案依据下列事实。这些事实读取于 2026-10-14，本提案沿用。逐条实测记录留在当时的任务 tmp。

来自官方文档：

- Free 计划可以给公开仓库配置 environment。environment 可以设置必需的确认者。确认者确认后，引用它的 job 才继续。管理员绕过的选项可以关闭。
- 规则集的“要求指定工作流通过”只在 organization 或 enterprise 级提供，只属于 Enterprise 计划。
- 规则集的“要求状态检查通过”只按检查名称和来源 App 判断，不区分产生检查的工作流文件。
- `pull_request` 事件使用 PR 合并引用上的工作流文件。`pull_request_target` 事件使用默认分支上的工作流文件。官方提醒这类工作流不要带着密钥或写权限执行 PR 的代码，并点名缓存投毒。
- 合并队列在目标分支的最新状态上组合 PR，在组合结果上运行必需检查，通过后把目标分支更新到这个组合结果。它触发 `merge_group` 事件。organization 拥有的公开仓库可以使用。合并队列有自己的合并方式设置。
- 标准规格的 GitHub 托管 runner 对公开仓库免费。官方不建议公开仓库使用自托管 runner。
- 规则集的 bypass 名单可以包含 GitHub App。标签规则集可以限制创建。
- 公开仓库的 Actions 日志最多保留 90 天。

在测试仓库实测（Free 计划 organization 中的公开仓库）：

- 有写权限的人可以在 PR 中增加一个与必需检查同名的 job，或者用自带的令牌写一个同名的提交状态。规则集为必需检查指定来源 App 后，这两种冒充都不被认可，冒充的 PR 也进不了合并队列。
- 规则集要求的检查对推送同样生效。admin 在更新限制的例外名单内，推送没有检查的提交仍被拒。`--admin` 合并和合并接口因缺少必需检查被拒。
- environment 的分支限制按运行的引用判断。只接受 `github-gate` 时，main、PR、合并队列临时分支和轨道上发起的运行都被拒绝。
- 用 `workflow_dispatch` 在 `github-gate` 上派发时，平台使用 `github-gate` 上的工作流文件。默认分支上必须存在同名文件，否则派发返回 404。
- 门铃可以在 `pull_request` 和 `merge_group` 事件中用自带的令牌派发运行。
- 合并队列把目标分支直接移到它检查过的提交。只用 merge commit 时，这个提交的第一父是原目标，第二父是 PR 的提交。合并队列的规则集不接受通配符分支名。
- GitHub App 列入例外名单后，可以在一次原子推送中更新受保护的分支并创建受限的标签。推送包含 PR 提交时，平台把 PR 标为已合并，合并者显示为该 App。
- environment 的确认说明可以从运行的确认记录读回。重跑需要重新确认。
- 网页上的 organization 审计日志在 Free 计划可用，记录了被拒的引用更新、App 使用规则例外和间接合并。审计日志接口在 Free 计划不可用。
- PR 自带的工作流可以为自带的令牌申请写权限。仓库默认权限设为只读时，PR 里的工作流声明写权限后仍新建了一个分支。

## 建议与改变范围

### 1. 目标

本节复述 RFC-0004 提案人对目标的说明，全部规则按它设计。

- 要的是留痕和权限集中，不是把人隔离在外。
- admin 必须先确认，代码才能进入 main、stable 和 release。admin 可以确认自己的 PR。admin 以后可能增加。
- 确认由人作出。机器身份只在人确认之后执行动作，或者只报告结果。
- main、stable 和 release 严格把关。轨道是最频繁的一层，把关可以轻一些。
- 轨道是按责任划分的共享汇集点，不是直接开发的分支。
- 绕过要能被发现并留下记录，不要求能被阻止。阻止需要取消 admin 修改规则集等管理权限，这也取消了流程失效时的恢复手段，人就不能再操作主干。

### 2. 名称

- **主干**：`integration/<名>`、`main`、`stable`、`release` 四种分支。
- **轨道**：`integration/<名>` 分支。
- **上游**：轨道的上一级，是 main 或另一条轨道。
- **子轨道**：上游为某条轨道的轨道。上游为 main 的轨道称为顶层轨道。
- **同步（FI）**：从上游进入轨道，包括 main 进入顶层轨道。
- **提升（RI）**：从轨道进入上游，包括顶层轨道进入 main。本提案中“提升”只取这一含义。
- **起点**：轨道创建时所在的提交。用 `gate-track` 创建的轨道，起点是 `omne/gate/track/<名>` 标签指向的提交。
- **切换点**：`github-gate` 的 `gate/cutover.json` 为一条分支登记的提交。切换点之后的提交都要有记录。它原本登记早于 `gate-track` 的主干；admin 处置缺口时，也可以为任一分支登记或移动切换点（第 8 节）。切换点不是起点。
- **核对下限**：覆盖核对从哪个提交之后开始。先取切换点，没有切换点时取起点。
- **自动检查**：准入流程自动运行的检查。第二阶段才有。
- **确认**：一位 admin 在 Actions 的 environment 中同意一次具体的发布，即一个 PR 进入一条主干。
- **确认检查**：第二阶段确认之后才写入的那一项检查结果。
- **发布身份**：GitHub App `omne-harness-lite-publish`。它更新主干并创建记录标签，在确认后执行发布。第二阶段它还写入确认检查。
- **报告身份**：第二阶段的专用 GitHub App。它只写检查结果，报告自动检查的结果。
- **记录身份**：第二阶段的专用 GitHub App。它为合并队列合入轨道的提交创建 unit。GitHub App 的写权限不区分引用，限制来自规则集：在受保护的分支和标签上，它只能创建 unit。它仍能推送不受保护的分支，例如个人工作分支和 `candidate/<名字>`。
- **发布流程**：使用发布身份的流程，即 `github-gate` 上的 `gate-publish`、`gate-track` 与第二阶段的发布 job。

### 3. 主干

| 主干 | 代表什么 | 接受的来源 | 记录 |
| --- | --- | --- | --- |
| `integration/<名>` | 一类工作的汇集 | 个人工作分支、它的上游、它的直接子轨道 | unit 标签 |
| `main` | 各轨道汇合后的完整结果 | 顶层轨道 | unit 标签 |
| `stable` | 代码到达一个稳定节点 | main 的 first-parent 历史上的一个提交 | stable 与 checkpoint 标签 |
| `release` | 对外发布的版本，与 npm 上的版本对应（对应方式留给后续提案，见第 15 节） | stable 历史上带 checkpoint 的一个提交 | 版本标签 |

代码沿轨道树向上提升，经 main 进入 stable，再进入 release。上游向轨道的同步是唯一的反向流动。

另有三类分支不是主干：

- **个人工作分支**：任务在这里开发，不受限制。
- **`candidate/<名字>`**：第二阶段使用。它从来源主干上选定的一个提交创建，用来向上一级或向子轨道提 PR。来源主干前进时它不变，所以不需要重复确认。发布完成后删除。它的创建不另加限制。它不受保护，可能在确认后被改动，所以流程不按它的名称或当前提交作判断，见第 9 节。
- **`github-gate`**：保存准入流程本身，不保存产品代码。只有 admin 能更新。

`release` 还没有创建。第 15 节规定它的位置与准入方式。

### 4. 轨道树

1. 每条轨道只有一个上游。全部轨道组成一棵以 main 为根的树。
2. 轨道只与它的上游和它的直接子轨道交换提交。
3. 不允许跨层流动：main 不直接同步给子轨道，子轨道不直接进入 main。
4. 不允许兄弟轨道之间流动。兄弟轨道之间要共享成果，先提升到共同的上游，再从上游同步。
5. main 的变化逐层同步。要到达第二层的轨道，先同步进它的上游，再从上游同步进它。
6. 层数不设上限。

例：A 的上游是 main，A1 与 A2 的上游是 A。

| 流动 | 是否允许 | 含义 |
| --- | --- | --- |
| main 进 A | 允许 | A 的同步 |
| A 进 main | 允许 | A 的提升 |
| A 进 A1、A 进 A2 | 允许 | 子轨道的同步 |
| A1 进 A、A2 进 A | 允许 | 子轨道的提升 |
| 个人分支进 A、A1 或 A2 | 允许 | 任务交付 |
| main 进 A1、A1 进 main | 拒绝 | 跨层 |
| A1 进 A2、A2 进 A1 | 拒绝 | 兄弟轨道之间 |

只允许相邻层之间流动，每条轨道就只有一条主干来源路径。unit 覆盖的核对与冲突的归属因此和单层轨道时相同。代价是 main 的变化要逐层同步，才能到达深层的轨道。

这条规则约束的是主干之间的 PR。个人分支的内容不受约束：从 main 顶端开出的个人分支可以进入子轨道，把 A 还没有的 main 提交带进 A1。gate 不能识别这种情形。轨道的 owner 按约定拒绝这样的 PR，要求先逐层同步。

跨轨道或全局的完整单元，也先进入一条顶层轨道，再随它进入 main。任务 binding 中 `global` 与 `cross-track` 两种 route 的目标分支改为一条具名的顶层轨道，仍须具名受影响的责任。具体字段由实施卡在集成工具的 SPEC 中定义。

### 5. 轨道的身份与上游关系

#### 上游从哪里读

`gate-publish`、`gate-track` 与 `gate-reconcile` 按下列顺序确定一条轨道的上游，三者使用同一个顺序：

1. 该轨道有 `omne/gate/track/<名>` 起点标签：读标签正文的 `parent`。标签没有 `parent` 字段时，上游为 main。
2. 否则，该轨道在 `gate/cutover.json` 中登记了切换点：上游为 main。现有的 `integration/legacy-refactor` 与 `integration/engineering-toolchain` 属于这种情况。
3. 两者都没有：拒绝。

起点标签先于切换点。原因是 `gate/cutover.json` 还承担另一个用途：admin 可以移动一条分支的核对下限来处置缺口（第 8 节「定时核对与缺口」），这条分支可能是子轨道。如果切换点先于起点标签，为子轨道登记下限会把它的上游变成 main，违反“上游关系不能修改”。

切换点与起点标签都只能由 admin 或发布身份写入，PR 不能修改它们，所以它们是上游关系的可信来源。`gate/cutover.json` 在 `github-gate` 上，只有 admin 能更新。起点标签由发布身份在 admin 确认后写入，之后不能修改或删除。

#### 核对下限从哪里读

核对下限与上游无关，沿用现行顺序：先取 `gate/cutover.json` 中该分支的切换点，没有时取起点标签指向的提交，两者都没有就拒绝。所以同一条子轨道可以同时有起点标签和切换点：上游按标签读，核对下限按切换点读。

#### 起点标签的格式

起点标签的正文仍是 `omne-gate-record:v1`，增加一个字段 `parent`。`parent` 取 `main`，或上游轨道的名称（不含 `integration/` 前缀）。读取方遇到没有 `parent` 的旧标签，按 main 处理。

#### 名称

- 子轨道也命名为 `integration/<名>`，不用 `integration/<上游>/<名>`。Git 中 `integration/a` 与 `integration/a/b` 两个分支不能同时存在。层级关系由记录表示，不由名称表示。
- 轨道名仍须符合 `^[a-z0-9][a-z0-9-]{1,40}$`。另外不能是 `main`、`stable`、`release` 或 `github-gate`，否则 `parent` 的取值会有两种读法。
- 已在 `gate/cutover.json` 中登记的名称不能再用 `gate-track` 创建。否则新轨道会继承旧名称的切换点作为核对下限，并且现有轨道会因新标签改变上游的读法。

#### 上游关系不能修改

轨道创建后不能更换上游。需要不同的上游时，退役原轨道，再创建一条名称不同的新轨道。原轨道的成果经个人分支重新进入新轨道，按个人分支的规则准入。

#### registry 是投影

policy registry 的轨道条目修改如下：

- 增加 `parent`，每个轨道条目必填。取值与起点标签相同：`main`，或上游轨道的名称（即分支名去掉 `integration/` 前缀）。现有三个条目都填 `main`。增加 `parent` 的那次改动可以同时删除 retiring 的 `development` 条目，保留时填 `main`。
- `initialMain` 改名为 `initialBase`，含义是轨道在上游上的起点提交。现有轨道的值不变。

`gate-publish` 与 `gate-track` 不读 registry。registry 的改动要先进入某条轨道再提升到 main，有时间差，而且 PR 能修改它。

本地集成工具 `start` 在给一条轨道开工时核对下列各项，任一不满足就拒绝开工。核对只针对本次 route 的轨道及其上游链，不使整份 registry 失效：

- 该轨道及其上游链上的每一条轨道都已登记，分支都存在于远端。
- 上游链上的每一条轨道都处于 active 或 paused 状态。上游 paused 时，已有子轨道上的工作可以继续；新建子轨道则要求上游为 active（第 6 节）。这是有意的区分。paused 只表示不派发新任务，paused 的轨道仍可同步与提升，`gate-publish` 不读 registry，也不按状态拦截。
- registry 的 `parent` 与可信来源一致，查找顺序与 gate 相同：有起点标签时与标签的 `parent` 一致（缺字段为 `main`）；否则有切换点时为 `main`。远端读不到时拒绝。

### 6. 创建轨道

`gate-track` 按下列规则创建轨道：

1. 派发时传入轨道名、`parent`、起点提交和接收决定评论的 Issue 号。流程把全部参数当作数据，先校验格式。不合格就停止。参数只经环境变量传给命令，不直接拼进命令文本。
2. `parent` 为 `main` 时，起点必须在 main 的 first-parent 历史上。
3. `parent` 为某条轨道时，按第 5 节能确定这条轨道的身份，它的分支存在，起点在它的 first-parent 历史上，并且是它的核对下限本身或核对下限之后的提交。
4. 轨道名符合第 5 节的名称规则，分支与起点标签都不存在。
5. 一位 admin 在 `publish` environment 中确认，必须填写说明。`gate-track` 不读 registry，所以上游必须处于 active 状态这一条由确认者核对，并写在说明中。
6. 发布身份在一次原子推送中创建分支与起点标签，并在指定 Issue 上写建轨道决定评论。

轨道创建后，仍须在 registry 中登记 owner、责任与 `parent`，然后才能派发任务。registry 能接受 `parent` 之前，不创建子轨道。

建轨道时上游必须已经存在，而上游关系之后不能修改，所以轨道树中不会出现环。

### 8. 第一阶段准入（现行）

#### 允许的 PR

`gate-publish` 按第 5 节确定 head 与 base 的上游，再判定组合：

| base | 允许的 head |
| --- | --- |
| 轨道 T | 个人工作分支；T 的上游；T 的直接子轨道 |
| `main` | 顶层轨道 |
| `stable` | `main` |
| `release` | 无。`release` 创建之前一律拒绝 |

- head 为 `stable`、`release` 或 `github-gate` 时，一律拒绝。
- base 为轨道 T 时，T 的上游链必须能按第 5 节逐级确定到 main，并且链上每一条轨道的分支都存在。任一上游分支已被删除时拒绝，见第 13 节。
- 其他组合一律拒绝。

#### 派发与确认

1. 派发 `github-gate` 上的 `gate-publish`，传入 PR 号与 PR head 的完整提交号。进入 stable 时还要传 checkpoint 名称。命令见 `github-gate` 分支的 `gate/README.md`。派发参数按数据处理，先校验格式，只经环境变量传给命令。
2. 一位 admin 在 `publish` environment 中确认，必须填写说明，空说明被拒绝。admin 可以确认自己的 PR。agent 可以用 admin 的凭据代为确认，说明中注明代为确认的人。确认者以平台的确认记录为准，评论中的名字只是抄录。
3. 流程不运行测试，确认暂代轨道的自动检查。说明中写明本地运行了哪些检查及结果。流程不自动读取集成条件，确认者在确认前核对卡上的条件，并在说明中引用。
4. 确认不是交付接受。进入轨道、main、stable、交付接受与关闭分别记录。流程不修改 Stage、接受或关闭。

#### 仓库工具链变更闸门

个人分支进入任何一层轨道的 PR，合并结果改动了 `gate/toolchain-paths.txt` 所列的路径时，先由 `repo-toolchain-review` environment 的确认者确认，再进入 `publish` 的确认。

- 命中按合并结果计算：`git merge-tree` 得出的结果与目标比较，变化的文件再与清单比对。
- 工具链确认也必须填写说明，说明原文写进发布决定评论。
- 同步（包括 main 进顶层轨道）、提升（包括顶层轨道进 main）与 main 进 stable 都不经这道审批。它们搬运的提交都已经以个人分支的形式进入过某条轨道。
- 第二阶段闸门仍然存在。同步与提升的豁免改按第 9 节「轨道：合并队列」的判别口径判定，与任务绑定的豁免使用同一个判别，不按 head 的分支名判定。闸门在合并队列上的具体形态（由哪个身份登记、合并队列怎样等待确认），由第二阶段的实施卡确定，经 admin 确认。

闸门的其余规则见第 16 节。

#### 构造、核对与推送

1. 确认后，流程核对 PR 的 head 与 base 在派发后没有变化，任一变化就停止。
2. 发布身份构造合并提交：第一父为目标，第二父为 PR head。有冲突就停止，冲突先在来源分支解决。
3. 这次发布是提升时，即 head 是 base 的直接子轨道，或 base 为 main，流程核对 head 轨道在核对下限之后的每个 first-parent 提交，都有目标为该轨道的 unit。同步不做这项核对：上游的记录由上游自己的提升负责。进入 stable 前，对 main 在切换点之后的 first-parent 历史做同样的核对。有缺口就停止。
4. 发布身份在一次原子推送中更新目标并创建记录标签。推送以派发时读到的目标为 lease。目标在派发后变化，推送失败，须重新派发。
   - 合并写 `omne/gate/unit/<结果提交号>`。unit 的名称由提交决定。
   - 进入 stable 时不产生合并，只快进到 main 的 first-parent 历史上的已有提交，旧 stable 必须是它的祖先。记录为 `omne/gate/stable/<提交号>` 与 `omne/gate/checkpoint/<名称>`。同一提交只能进入 stable 一次：另一次发布已把 stable 推进到同一提交时，记录已存在，整次推送失败。
   - 标签正文是 `omne-gate-record:v1` JSON。
5. 推送前，发布身份在 PR 上发出发布决定评论。评论包含目标、PR head、结果、记录标签、平台记录的确认者、运行链接与确认说明原文。推送失败时，评论记载的决定没有生效，以真实引用与记录标签为准。
6. 推送完成后，平台把 PR 标为已合并，流程在 PR 上补记结果。

评论长期保存在 PR 中，不受 Actions 日志保留期的影响。

#### 提升 PR 的说明

轨道的提升 PR（子轨道进上游、顶层轨道进 main）由该轨道的 owner 提出。PR 说明列出自上一次提升以来进入该轨道的卡，以及这些卡在下一层或 main 上要满足的条件。上一层的确认者据此核对条件。树越深，经子轨道运输进来的卡越不容易看到，所以这份清单由离这些卡最近的 owner 给出。清单每张卡写 Issue 编号、revision 与 attempt。第二阶段由流程读取这份清单（第 9 节），精确格式由实施卡在 `gate/README.md` 中定义。

#### 定时核对与缺口

- `gate-reconcile` 每小时从 main 触发一次。它为核对下限之后没有记录的主干提交开缺口 Issue，不创建标签。stable 的尖端没有对应的 stable 记录时，同样开缺口 Issue。
- `gate-reconcile` 增加一项核对：一条轨道的分支存在，而按第 5 节确定的上游链上有分支不存在时，开缺口 Issue。
- 缺口不设处理时限。缺口存在时，相应主干的提升被拦住。
- 缺口有三类，闭合方式不同：
  - **没有 unit 的主干提交。** 第一阶段没有补建 unit 的流程，这类缺口分两步处置：
    1. 该轨道的 owner 或任一 admin 在缺口 Issue 中写具名决定，说明缺口提交的来源和处置，并列出该提交带来的卡（Issue 编号、revision 与 attempt）。
    2. admin 在 `github-gate` 的 `gate/cutover.json` 中，把该分支的切换点改为缺口中最后一个没有 unit 的 first-parent 提交，并在缺口 Issue 中注明这次修改的提交。核对范围是下限之后的提交，所以缺口提交不再被核对，之后的提交仍须有 unit。

    两步都完成后，缺口 Issue 才闭合，提升随之恢复。只有第 1 步时，缺口仍未闭合。移动下限只改变核对范围，不改变上游关系（第 5 节）。
  - **stable 的尖端没有对应的 stable 记录。** admin 在缺口 Issue 中写具名决定。stable 下一次经流程发布后，新的尖端有了记录，缺口 Issue 闭合。
  - **上游链上有分支不存在。** 上游关系不能修改，被删除的名称已被占用，不能重建，所以上游链断开的轨道只能删除，包括被删轨道下面各层的全部轨道。这些轨道的成果由删除的人处理，例如经个人分支进入其他轨道。它们按第 13 节自下而上删除，全部删除后，缺口 Issue 闭合。
- 2026-10-15 登记的原切换点之前的历史，按 #208 的决定整体认可，不补记录。下限移动后，原核对下限（切换点或起点）与新下限之间没有 unit 的提交，以缺口 Issue 中的具名决定为依据，不属于 #208 的认可范围。

#### 平台配置

- main、轨道和 stable 的创建与更新只允许发布身份。
- `integration/**/*` 只有仓库管理员可删除，所有人禁止非快进更新。
- main 与 stable 禁止删除和非快进更新。
- `github-gate` 只有 admin 能创建和更新，禁止删除和非快进。RFC-0004 原写“admin 和发布身份”，发布身份只为更新受信版本文件而列入；RFC-0008 取消了这个文件，改为只有 admin。
- main 上为 `github-gate` 的每个流程保留一个同名的空壳文件，修改准入流程由 admin 直接更新 `github-gate`。这两条在第一阶段已经生效，规则见第 9 节「门铃与 `github-gate` 上的运行」。
- `omne/gate/*` 标签只有发布身份能创建，任何人不能修改或删除。采用标签（`omne/integration/adoption/*`）与旧 unit 标签作为历史保留，任何工具不再读取，同样禁止修改和删除，没有 bypass。采用标签只允许发布身份创建，现在不再创建新的采用标签。
- 仓库只允许 merge commit。
- `publish` environment 的确认者为 admin，关闭管理员跳过，只接受 `github-gate` 上的运行。`repo-toolchain-review` 与 `npm-release` 两个 environment 的确认者与 `publish` 相同，同样关闭管理员跳过、只接受 `github-gate` 上的运行，不存放密钥。调整 `publish` 的确认者时同步调整它们。
- 切换点记在 `github-gate` 的 `gate/cutover.json`。
- 平台保护不验证任务接受。admin 修改规则集本身属于管理权限。

#### 身份、密钥与运行

- 发布身份的 App 归组织所有。密钥只放在 `publish` environment 的 secrets 中，不放仓库级 secrets。管理者按安全情况决定是否轮换，不定期更换。发布身份的密钥按与 admin 权限同等的级别保管。
- 流程使用 GitHub 托管 runner。
- 使用密钥的 job 不执行 PR 或仓库的内容，不恢复缓存，引用的第三方 action 用完整提交号固定。
- 公开仓库的运行日志对所有人可见。使用密钥的 job 不在日志中打印 Issue 的非公开信息或任何凭据，只打印判断结果和提交号。
- GitHub Actions 自带的身份不进入任何规则集的例外名单。受保护的分支和标签只靠规则集保护。留痕以评论和标签为准，不依赖运行日志。
- 审计日志由组织和项目的管理者按需要查看，不设固定周期。
- `github-gate` 的改动由组织和项目的管理者按需要审阅，不设固定周期。

#### 检查责任

- 提交 PR 的人在有 task context 的任务工作树中运行检查，确认者在说明中写明实际命令和结果。
- 没有 task context 的检出，基线退回 `origin/main`。不伪造 Issue 绑定，也不手写 context。
- 没有任务 context 的 main 本身，例如进入 stable 的 PR，第一阶段没有正式检查入口。确认者写明实际运行的命令及其限制，不写成正式检查结论。
- 进入任何一条主干（轨道、main、stable、release）之前的检查都是准入检查，不读 turbo 任务缓存（本地与远程），只写本地缓存。准入检查是否写远程缓存，随远程缓存是否启用一起，仍归 RFC-0002 的未决项。缓存命中时任务不会真正运行，检查会显示通过而实际没有运行。这一条决定 [RFC-0002](RFC-0002-engineering-toolchain.md)「建议与改变范围」中「影响面选择」约束 3 留给本规则一起决定的准入缓存策略。其他缓存（例如 pnpm 按锁文件完整性校验取包的 store）不在这条规则内。远程缓存是否启用不在本提案内。
- 第一阶段由提交 PR 的人进入准入模式：合并前的检查带 `OMNE_ADMISSION=1` 运行，例如 `OMNE_ADMISSION=1 BASELINE="$TASK_BASE" pnpm run check`。进入 stable 的 PR 没有 task context，确认者运行的命令同样带这个变量。确认说明写明实际命令；命令没有带这个变量时，这次运行不作为准入检查结论。
- 本地缓存（`.turbo/`）不进入 Git，由 `.gitignore` 排除。
- 检查通过不代替语义或行为接受。

#### 范围

- 来自 fork 的 PR 不在本阶段范围内。
- 不采用“由本地工具在合并之外单独盖 unit”作为准入。
- 不另加 CODEOWNERS。
- 当前 admin 获得确认权，本提案不另改 admin 名单。
- 远程检查恢复后，pstack 的 `fix-ci`、`babysit` 等方法才有输入。是否采用它们由[技能入口](../engineering/skills.md)的拥有者另行决定，不属于本提案。

### 9. 第二阶段（已采用，待实施）

本节复述 RFC-0004 已接受的第二阶段设计，并按多层轨道推广。RFC-0008 与 RFC-0009 已取代的部分不在本节，见第 16 至 18 节。

#### 目标

- 轨道改为自动检查通过后经合并队列自动合并，取消轨道的 `publish` 确认。仓库工具链变更闸门的确认保留（第 8 节）。
- 增加报告身份和按改动范围的必需检查。
- 受信检查器的版本由仓库的钉子承载，不在 `github-gate` 上另存版本文件，见第 16 节。
- 集成条件评论只规定必要信息，见本节「main：确认后由发布流程推送」。

第 8 节中本节没有改变的条款，在第二阶段继续有效，包括「身份、密钥与运行」「范围」与「提升 PR 的说明」。

这些机制写于 turbo 与多层轨道之前，部分前提已经改变。例如，准入时的影响面已改由 turbo 选择。第二阶段开工时，实施者先按当时的平台能力与仓库状态核对这些机制。需要改变本节的设计时，另开提案。

#### 轨道：合并队列

每条轨道（包括子轨道）启用合并队列，只允许 merge commit 这一种合并方式。合并队列的规则集不接受通配符分支名，所以每条轨道单独一个规则集。新增轨道时同时新增它的规则集。仓库还须开启自动合并，否则 PR 无法加入队列。

1. 个人分支向轨道提 PR。门铃派发准入流程，由报告身份把自动检查的结果登记在 PR 的提交上。PR 的提交通过该轨道的必需检查之后，才能加入合并队列。
2. 有写权限的人把 PR 加入合并队列。合并队列规则本身拒绝直接推送，admin 也不例外，所以进入轨道只有经由队列这一条路。平台规则不能限制谁加入队列：给轨道加上“只有 admin 能更新”的规则后，合并队列连 admin 加入的 PR 也合不进去，例外名单换成“只在经由 PR 时放行”的模式也一样。所以轨道 owner 认可 PR 是约定，不由平台强制：registry 中每条轨道的 owner 按约定负责把该轨道的 PR 加入合并队列。本仓库只有 admin 有写权限，其余协作者只有读权限，所以目前能加入队列的只有 admin。
3. 合并队列在轨道的最新状态上组合 PR，触发 `merge_group` 事件。门铃派发 `github-gate` 上的准入流程，由它对组合结果运行自动检查，并用报告身份登记结果。
4. 检查通过后，合并队列把轨道直接移到这个组合结果，不另外生成提交。
5. 记录流程为这个提交创建 unit。unit 的 `verification` 指向报告身份在这个提交上登记的检查结果。

多个 PR 同时进入队列时，合并队列逐个组合、逐个检查。目标前进后，后续 PR 在新的状态上重新组合和检查，不需要人重新操作。

上游向轨道的同步也走这条路径，来源是从上游选定提交创建的 `candidate/<名字>`。子轨道向上游的提升也走上游的合并队列。

轨道不要求集成条件的决定，流程不读取条件。集成条件在进入 main 时由 main 的发布流程核对。卡上限定为某一层轨道的条件，由该轨道的 owner 在把 PR 加入合并队列前核对，这是约定，不由平台强制。

多层轨道下的检查：

- 个人分支进轨道：检查按 PR 声明的 Issue 与派发记录做 taskBase 与 writeScope 审计，拒绝认领写范围不符的卡。
- 同步与提升：PR 不对应单张卡，不做任务绑定审计，按改动范围检查。流程不按 head 的分支名判别同步与提升，因为 `candidate/<名字>` 的创建不受限制。判别口径是：PR 的 head 提交在 base 的上游的 first-parent 历史上（同步），或者在 base 的某条直接子轨道的 first-parent 历史上（提升）。两者都不满足的 PR，按个人分支处理，要求任务绑定。
- 子轨道进上游：另有一项必需检查，核对子轨道在核对下限之后的每个 first-parent 提交都有 unit。这与第一阶段第 8 节的覆盖核对相同，缺口在每一层都被拦住。

#### main：确认后由发布流程推送

1. 顶层轨道向 main 提 PR。PR 上的检查只供参考，不是 main 的必需检查。
2. 准备好发布时，admin 手动派发 main 的发布流程，传入 PR 编号。PR 打开或更新不自动派发它：main 的发布流程共用一个并发组，等待确认的运行会占住这个组，自动派发会让其他运行被平台取消。被取消的运行由 admin 重新派发。
3. 检查 job 在 main 的当前状态上构造候选并验证。构造候选的 job 用自带的令牌把候选推到不受保护的 `candidate/main-pr-<编号>`，以便报告身份能在它上面登记结果。候选与 PR 有冲突时流程停止，冲突先在来源轨道上把 main 合进来解决，再重新发布。
4. 报告身份把 main 级的自动检查登记到候选上。
5. 流程暂停，运行页面列出候选、main 和 PR 的提交号，等待一位 admin 在 Actions 中确认。确认的对象就是这一个候选。确认者必须填写说明。
6. 推送 job 读取这次确认的确认者、时间和说明，说明为空时停止。然后核对：main 仍是预期的提交，PR 的提交没有变，候选的两个父提交正好是 main 和 PR 的提交，候选的树等于这两者合并的结果，候选上有报告身份登记的 main 级检查。推送 job 还在推送前重读所引用的集成条件决定与相关卡的授权，与检查 job 读到的不一致就停止。任何一项不符，流程停止，不发出发布决定。
7. 流程合成发布决定评论，由发布身份发在 PR 上，并在每张涉及的卡的 Issue 里留一条带链接的评论。评论包含确认者写的说明、平台记录的确认者和时间、候选、main 和 PR 的提交号、要更新的分支和标签名，以及所引用的集成条件决定。
8. 发布身份把确认检查写到候选上，然后用一次原子推送更新 main 并创建 unit。
9. 平台把 PR 标为已合并。推送完成或失败后，流程在 PR 上补记结果。

- 集成条件的决定仍由 owner 写，不由流程代写。owner 在卡的 Issue 中写一条单独的条件决定评论，检查 job 读取它，流程合成的发布决定评论引用它。条件决定评论必须含整体工作流需要的信息：卡的 Issue 编号、revision 与 attempt，目标主干，满足了哪些条件，以及决定人。其余内容不限定格式。流程怎样找到并读取这条评论，由第二阶段的实施卡在 `gate/README.md` 中定义，经 admin 确认。
- 检查 job 从 unit 收集本次进入 main 的任务集合：
  1. 每一层的收集区间由一次提升确定。顶层这一次提升是本次进入 main 的 PR，区间上界是 PR 的 head；下一层的一次提升是范围内一条记为提升的 unit，区间上界是这条 unit 记录的 head。区间下界是该分支在上界之前最近一次进入上游的提交与核对下限两者中较晚的一个。“最近一次进入上游的提交”按提交结构识别：上游 first-parent 历史上、第二父落在该分支 first-parent 历史上的最近一个合并提交，取它的第二父；不按 unit 的类别识别，因为第一阶段写的 unit 没有类别。收集区间内、下界之后、上界及之前的 first-parent 提交。同一子轨道在上游的范围内提升过多次时，每次提升各自确定一段区间，区间首尾相接，不重叠。没有前一次进入上游的提交时，下界取核对下限。“最近”按上游 first-parent 历史的顺序计。
  2. 对区间内每个提交的 unit：记有任务绑定的，取其绑定。记为提升的，以这条 unit 为这一次提升，对来源子轨道按第 1 步收集，逐层向下。记为同步的，不贡献任务，它搬运的提交已由上游自己的提升负责。第一阶段 `gate-publish` 写的 unit 没有任务绑定也没有类别，记为缺口的 unit 只引用缺口 Issue，两者都不贡献任务。
  3. 收集结果与顶层轨道提升 PR 说明中的卡清单（第 8 节「提升 PR 的说明」）比较。收集结果中有、清单中没有的卡，流程停止。清单中有、收集结果中没有的卡，检查 job 在运行页面逐张列出。

  清单多出的卡只允许来自三处：第一阶段写的 unit 对应的提交；记为缺口的 unit，其缺口 Issue 的具名决定列出了该卡；核对下限之前的提交。确认者在确认说明中逐张写明来源，写不出来源就不确认。
- 检查 job 与推送 job 之间只经平台传递数据。推送 job 使用的提交号只来自校验过的派发参数和平台查询，不来自检查 job 的输出，因为检查 job 执行候选的代码，可以改写自己的输出。这一条原写在 RFC-0004「现行集成工具的改造」中，该节已被 RFC-0009 取代；本提案把它作为第二阶段检查 job 与推送 job 的新条款保留，见「决定范围」。
- 评论长期保存在 PR 和 Issue 里，不受 Actions 日志保留期的影响。
- 发布决定评论记载候选与 unit 名称，用于核对与审计，不作为恢复依据。发布运行中断后重跑时，流程先读真实引用：
  - 目标已等于候选并且记录标签存在：按已发布处理，只补记 PR 上的结果。main 的候选在重跑时会被重新计算，所以“目标等于候选”按 main 尖端 unit 的 `pr` 与 `head` 和本次一致判定。stable 按 `omne/gate/stable/<提交号>` 是否存在判定，release 按版本标签是否存在判定。候选本来就带有的 main 上的 unit 与 checkpoint 标签不算。
  - 目标仍是预期的旧提交：重新构造候选、验证并确认。
  - 其余情形，包括目标等于候选而记录标签不存在、目标是其他提交：停止并交 admin 处理。目标等于候选而记录标签不存在，说明有人绕过了流程，按缺口处理，发布身份不补建记录。

  stable 与 release 的重跑用同一规则，“候选”指派发时传入的提交。第 17 节“运行结果未知时”是这一规则的第一条，适用于两个阶段；本条是第二阶段的完整规则。
- 发布决定评论的作者是发布身份，评论中记载的确认者是 admin，并与平台的确认记录一致。任何 admin 都能作出发布决定。
- 平台无法区分确认是 admin 本人作出的，还是 admin 的 agent 用 admin 的凭据作出的。确认记录表示该 admin 行使了确认权，责任由该 admin 承担。
- 发布决定评论在推送之前发出。推送失败时，评论记载的决定没有生效，以结果记录为准。
- main 的发布流程串行运行。确认之后 main 发生变化时，发布流程停止。重新构造的候选须重新验证和确认。
- main 级的必需检查只写在发布流程构造的候选上，名称与 PR 上的检查不同。admin 点合并按钮生成的合并提交没有 main 级的必需检查，平台拒绝它。

#### stable 与 release：确认后由发布流程快进

1. admin 在来源主干上选定一个提交，创建 `candidate/<名字>`，向目标主干提 PR，并派发发布流程，传入这个提交号。
2. 检查 job 在这个提交上运行 stable 级或 release 级的检查，报告身份登记结果。
3. 一位 admin 在 Actions 中确认，并填写说明。运行页面列出要推送的提交号。
4. 推送 job 核对：目标主干仍是预期的提交，这次更新是快进，派发时传入的提交上有报告身份登记的该级检查。推送的提交固定为派发时传入、运行页面列出的那一个，不在推送时重读 PR 的提交，因为 `candidate/<名字>` 不受保护，可能在确认后被改动。
5. 流程合成发布决定评论发在 PR 上，然后用一次原子推送把目标主干快进到这个提交，同时创建 checkpoint 标签或版本标签。两者要么都成功，要么都不成功。
6. 平台把 PR 标为已合并。这一点在 main 上实测过，在 stable 上是推断。

stable 和 release 仍直接指向来源主干上已有的提交，不产生新提交。stable 的条件决定和历史复核与 main 相同，由 owner 写在卡的 Issue 中，检查 job 读取。

#### 每一级的自动检查

| 主干 | 自动检查的内容 |
| --- | --- |
| 轨道 | 按改动范围的检查。个人分支的 PR 声明它对应的 Issue 和派发记录，检查按派发记录做 taskBase 和 writeScope 审计。子轨道的提升另核覆盖 |
| main | 轨道一档的全部内容。来源轨道上每个提交都有 unit。集成条件的决定 |
| stable | PR 的提交在 main 的 first-parent 历史上，旧 stable 是它的祖先。从切换点到这个提交，main 上每个提交都有 unit。完整检查，见第 18 节 |
| release | PR 的提交在 stable 的历史上，并且有 checkpoint 标签。旧 release 是它的祖先。发布前检查留给后续提案 |

- 自动检查按改动范围选择，不在每次准入时运行全量检查。这是硬性要求，原因是轨道是最频繁的一层，每次都跑全量会让准入的耗时随仓库增长而失控。
- 轨道和 main 按实际改动、声明依赖和读者规则选出成员，只运行这些成员的检查。选择依据与[开发指南](../development.md#迭代中的受影响测试)相同，不能凭“没修改那个包”省略消费者验证。
- PR 不能通过修改选择规则缩小自己的检查范围。检查器取自目标分支钉住的版本，选择规则文件受仓库工具链变更闸门保护（第 16 节）。PR 改动根目录的 `package.json`、`pnpm-workspace.yaml` 等全局文件时，计划选中全部成员。
- 自动检查与合并队列的检查同样不读 turbo 任务缓存，写入范围同第 8 节「检查责任」。持有密钥的 job 不恢复任何缓存。
- 比较基线从平台查询，不取自门铃传入的参数。PR 阶段以 PR 与目标分支的共同祖先为基线，合并队列阶段以队列组合的目标提交为基线。
- 必需检查按轨道和级别分别命名，确认检查也按级别分别命名。检查名中的轨道由流程向平台查询 PR 的目标分支或合并队列临时分支的名称得出，不取自门铃参数。被检查的提交不是任何一个到该轨道的 PR 的提交，也不是该轨道合并队列的组合提交时，流程停止。否则通过进入一条轨道的检查的提交，可以被推到另一条轨道；通过进入 stable 的确认的提交，也可以被当作已确认进入 release。

#### 必需检查由专用身份报告

如果检查由普通的 job 报告，PR 分支可以新增一个工作流，放一个与必需检查同名、直接成功的 job，平台无法区分。所以全部必需检查都由专用身份报告。规则集为自动检查指定来源为报告身份，为确认检查指定来源为发布身份。其他来源报告的同名检查不被认可。

三个身份的密钥分别保存在三个 environment 里。三者都只接受 `github-gate` 引用上的运行，都关闭管理员跳过。

- 报告环境：不设确认者，只保存报告身份的密钥。报告身份还能读取 organization 的 Project。准入流程用它在不执行 PR 内容的 job 中读取任务看板，只把检查需要的字段交给检查 job，例如卡的派发记录、taskBase 和写范围。检查 job 执行 PR 的代码，交给它的数据等于公开。自带的令牌读取同一看板返回空列表而不报错，所以流程把空看板当作错误。
- 记录环境：不设确认者，只保存记录身份的密钥。
- 发布环境：设置必需的确认者，即 admin，允许发起人自己确认。它只保存发布身份的密钥。

三个专用身份的 App 都归组织所有，密钥只放在对应 environment 的 secrets 中，不放仓库级 secrets，管理者按安全情况决定是否轮换，不定期更换。发布身份已按此办理（第 8 节「身份、密钥与运行」）。报告身份与记录身份在第二阶段切换第 1 步创建时同样办理。

执行 PR 内容的检查 job 不引用任何 environment，没有密钥，令牌只读。使用密钥的 job 不执行 PR 内容，不恢复缓存，不执行检查 job 产生的任何文件，引用的第三方 action 用完整提交号固定，安装依赖时不执行包的生命周期脚本。使用密钥的 job 不在日志中打印看板内容、Issue 的非公开信息或任何凭据。

检查结果的可信度以检查 job 为上限。检查 job 执行 PR 的代码，它不是沙箱，PR 的代码可以影响同一 job 的结果。

各身份的密钥单独外泄时：

- 报告身份：持有者能伪造自动检查，未通过检查的内容可以进入轨道。main、stable 和 release 还需要确认检查和发布身份。
- 记录身份：持有者能为任意提交创建 unit。伪造的 unit 让缺口不被发现，但内容进入 main 时仍要通过检查和确认。
- 发布身份：持有者能写入确认检查，并能更新 main、stable 和 release。它不能伪造自动检查，但报告身份在确认之前就把自动检查登记到候选上。所以对任何已经通过检查、正在等待确认的候选，持有者都能自己写入确认检查并推送，不经任何人确认。stable 和 release 同理：来源主干上已有的提交通过检查后，持有者可以直接更新这两级。发布身份的密钥按与 admin 权限同等的级别保管和轮换。

#### 记录流程与缺口

记录流程为合并队列合入轨道的提交创建 unit。

- 触发：只有两个入口。一是 PR 被合并队列合入轨道时，`pull_request` 关闭事件触发门铃，门铃派发记录流程。这个门铃使用的是轨道上合入之后的那份工作流文件，所以每条轨道都要有门铃文件。二是有人在 `github-gate` 上手动派发记录流程。
- 串行：两个入口使用同一个按轨道命名的并发组，同一条轨道同时只有一次记录流程在运行。同一提交上出现两个 unit 会使核对永久拒绝该轨道，而标签不能删除，所以必须串行。
- 每次扫整条轨道：平台的并发组最多保留一个等待中的运行，更新的运行会取消它。所以记录流程每次都为整条轨道上所有没有 unit 的提交补建，而不只处理触发它的那一个提交。被取消的运行留下的提交，由后面任何一次运行补上。
- 创建前核对四件事，少了任何一件都不创建：
  1. 这个提交上有报告身份登记的、该轨道名称的通过检查。按报告身份对应用户的编号识别，不按显示名识别。
  2. 这个提交是合并队列合入的，即存在一个已合并的 PR，其合并提交就是它。
  3. 它的第一父是轨道的上一个提交，第二父是这个 PR 的提交。
  4. 个人分支的 PR 声明了任务绑定。同步与提升的 PR 不要求任务绑定，判别口径见本节「轨道：合并队列」。这类 PR 的 unit 不记任务绑定，改记类别（同步或提升）与来源分支。

  admin 停用规则集后把一个单提交 PR 的提交直接快进推到轨道上时，平台把这个 PR 标为已合并，合并提交就是它本身。它能通过除第二父以外的全部核对，只有第二父的核对能识别它。核对不通过时，流程不创建 unit，并开一张缺口 Issue。创建前再查一次该提交是否已有 unit，已有则跳过。
- 定时核对只报告：`gate-reconcile` 跳过合入后尚不足一个记录周期的提交，以免在记录流程运行之前开出缺口 Issue。
- 门铃副本：合入事件的门铃使用轨道上的文件，所以门铃的改动要经各轨道自己的准入进入每条轨道。某条轨道的门铃失效时，该轨道的 unit 要等到下一次手动派发的记录流程才补上，期间该轨道的提升会因缺 unit 而失败。
- 标签创建：unit 只允许记录身份和发布身份创建。checkpoint、stable、版本、起点与采用标签只允许发布身份创建。
- 缺口闭合：绕过造成的、没有 unit 的提交（四项创建前核对不通过），由该轨道的 owner 或任一 admin 在缺口 Issue 中写下具名决定，说明该提交的来源和处置，并列出该提交带来的卡，再由记录身份创建 unit。这个 unit 记类别为缺口，并引用缺口 Issue。记录流程失败或门铃失效造成的缺口按第 14 节由普通路径补建 unit。另外两类缺口按第 8 节「定时核对与缺口」闭合。

#### 门铃与 `github-gate` 上的运行

- 全部使用密钥的工作都在 `github-gate` 上派发的运行中完成。PR 分支、合并队列的临时分支和 main 上的工作流都拿不到密钥。
- PR 打开或更新、PR 进入合并队列、PR 被合入、定时核对的时间到达，都由一个很薄的门铃流程响应。门铃只用自带的令牌派发 `github-gate` 上的相应流程，并传入 PR 编号或提交号。确认不需要门铃，它发生在同一次运行中。
- `github-gate` 上的流程自己向平台查询这个 PR 或提交的真实信息，不采信门铃传来的其他内容。门铃传入的参数一律当作数据：先校验格式，例如提交号必须是 40 位十六进制，事件名必须在允许的列表中，校验不通过就停止；参数只经环境变量传给命令。
- 门铃流程不受信任，可以被 PR 修改。被修改后的后果：不按门铃，就没有检查结果，PR 进不了主干；让准入流程检查别的提交，准入流程照实检查，结果登记在那个提交上；反复按门铃，多出的运行按提交号排入并发组。所以密钥的安全不依赖 main 上 `.github/workflows/` 的内容。
- main 上为 `github-gate` 的每个流程保留一个同名的空壳文件。平台只允许派发默认分支上存在的工作流。空壳文件的内容不影响安全，因为派发到 `github-gate` 的运行使用 `github-gate` 上的定义。新增流程时，空壳文件须先经 main 的准入进入 main。
- 修改准入流程由 admin 直接更新 `github-gate`，不需要旧流程先放行新流程。

#### 平台配置的改变

- 每条轨道一个合并队列规则集，仓库开启自动合并。
- 撤除第一阶段对轨道“更新只允许发布身份”的限制，否则合并队列无法合入。轨道的创建仍只允许发布身份，由 `gate-track` 执行。
- 按级新增要求自动检查和确认检查的规则集，不设例外。
- main、stable 和 release 的更新只允许发布身份。release 在第一次对外发布之前创建，创建时直接采用确认一档。
- 标签的创建限制改为：unit 只允许记录身份和发布身份创建；checkpoint、stable、版本、起点与采用标签仍只允许发布身份创建。这一改动在切换第 3 步执行，否则记录流程写 unit 会被规则集拒绝。
- 禁止非快进和禁止改删标签的规则集不变。

#### 切换步骤

第二阶段分四步切换：

1. 试运行。创建报告身份、记录身份与对应的 environment，门铃流程进入 main。规则集不动。准入、记录和发布流程只计算和比较，不写检查结果，不创建标签，不推送。第一阶段的流程照常发布。
2. 观察若干次真实的发布，核对新流程的计算结果与第一阶段的实际结果一致。
3. 轨道切换。仓库和合并队列都只允许 merge commit，轨道启用合并队列，新增轨道的必需检查规则集，放开记录身份创建 unit，记录流程开始写 unit。从这一步起，第一阶段的流程不再用于轨道。
4. main 和 stable 切换。新增 main 和 stable 的必需检查规则集，发布流程开始按第二阶段推送。从这一步起，第一阶段的流程不再用于 main 和 stable。

第 3 步和第 4 步是平台设置操作，由 admin 执行，完成后读回全部规则集并执行第二阶段的验收。每一步开始前，停止用第一阶段的流程发布相应主干，避免两条路径为同一提交各写一个 unit。退回时停用新增的规则集，恢复原来的更新权限，第一阶段的流程恢复使用。已经创建的标签不能删除，所以退回不撤销已有的记录。

第二阶段的设计在第 1 步开始前写回 integration.md「第二阶段目标」，不随多层轨道的实施卡写回。

### 10. 记录与上一级核对

- 每个进入主干的提交最终都有记录，或者有一张公开的缺口 Issue。
- 上一级的准入核对下一级的记录是否完整：子轨道上缺 unit 的提交进不了上游，轨道上缺 unit 的提交进不了 main，main 上缺 unit 的提交进不了 stable。
- 缺口出现后，相应主干的提升被拦住。对绕过造成的、没有 unit 的提交（四项创建前核对不通过）：第二阶段，具名决定写下后由记录身份补建 unit，缺口闭合，提升随之恢复；记录流程失败或门铃失效造成的缺口按第 14 节闭合；第一阶段没有补建流程，具名决定写下后由 admin 移动核对下限，缺口闭合，提升随之恢复。另外两类缺口的闭合见第 8 节「定时核对与缺口」。

### 11. 稳定点

stable 选择 main first-parent 历史上的已有提交，只要求旧 stable 是其祖先。main 后续前进不改变选定的 checkpoint。stable 的完整检查见第 18 节。

### 12. 任务与交付

- 任务从真实 Issue 的 revision 和当前 attempt 开始。指定调度者记录并读回人的责任、分支、route、不可变 taskBase、写范围与条件定位。目录不能自动决定路线。
- 任务的 route 选择它要进入的那条轨道，子轨道上的卡，route 就是该子轨道。不设隐含默认轨道。
- completionTarget 为 `track` 时，指 route 中的那条轨道。之后随该轨道进入上游、进入 main，都属于运输，与 `track` 卡之后随轨道进入 main 的做法相同。
- 集成条件可限定目标层或实际 ref，未声明为 all。限定为 track 层的条件，只在进入 route 中的那条轨道时适用。要在上一层轨道或 main 之前满足的条件，写明实际 ref。
- 双基线与 `task-sync` 见第 18 节，不论目标分支处于第几层都适用。
- Issue 仍是任务的唯一来源。确认不代替集成条件的决定，也不代替交付接受。
- 运输层改变不自动新建卡或提高交付修订。

### 13. 退役与删除

删除轨道就是退役轨道。由 admin 删除轨道分支。

- 唯一的硬条件：没有其他轨道以它为上游时，才能删除。删除前以起点标签为准确认：所有现存 `integration/*` 分支的起点标签 `parent` 都不指向它。registry 只作参考。子轨道先删除，退役沿子树自下而上进行。
- 删除不丢失历史。轨道上合入的提交都有 `omne/gate/unit` 记录标签，标签不能修改或删除，分支删除后这些提交仍可经标签找到。
- 尚未提升的成果，由删除的人负责处理：例如先提升、经个人分支转入其他轨道，或确认放弃。不要求固定格式的记录。
- registry 条目事后整理：删除条目或修改状态，按普通改动经任意轨道进入，没有先后顺序要求。retiring 状态保留为可选，owner 想在删除前停止派发时可以标记。标记要随同步到达目标轨道后才对该轨道的开工生效，不是即时的。
- owner 更换先交接未提升的成果与活动任务。
- 删除 ref、工作树或唯一临时材料，仍按[工作约定](../engineering/workflow.md#责任与协作交接)和[发布边界](../engineering/publication.md)取得明确授权。Git revert 不撤销外部副作用。

平台不能按上游关系阻止删除。误删仍有子轨道的轨道时，由下面三层发现并拦住：

1. 本地：`start` 核对目标轨道与整条上游链的分支都存在于远端，任一已删除就拒绝开工（第 5 节）。分支一删，不需要先改 registry，开工即被拒绝。
2. 准入：`gate-publish` 拒绝进入上游链上有分支已不存在的轨道（第 8 节）。所以上游被删除后，它下面各层的子轨道都不会继续积累工作。
3. 事后：`gate-reconcile` 为上游链上有分支不存在的轨道开缺口 Issue（第 8 节）。上游关系不能修改，被删除的名称也不能重建，所以这些轨道只能删除，全部删除后缺口 Issue 闭合。

不新增退役流程。

### 14. 保证与已知限制

本提案给出两个保证，强度不同。

- **正常使用时**：进入主干的提交都经过 PR，并带有记录标签。第一阶段由发布流程合入；第二阶段轨道由合并队列合入，其余由发布流程合入。第一阶段，进入每一层主干都经过 admin 确认。第二阶段，进入主干的提交就是通过了该级必需检查的那个提交本身，进入 main、stable 和 release 的还经过确认。平台对 admin 同样强制。
- **有人绕过时**：绕过会被发现并留下记录，但不能被阻止。定时核对与记录流程负责尽早发现，上一级的准入负责最迟在下一次提升时拦住。

已知的绕过：

- admin 修改或停用规则集和 environment 后直接推送主干。定时核对发现没有记录的提交。第二阶段，admin 停用规则集后经 PR 合入或快进推送时，记录流程的创建前核对会拒绝创建并开出缺口 Issue。admin 若同时伪造了 unit，只能靠组织审计日志发现。规则集修改事件是否进入审计日志尚未核对。
- admin 在流程最后一次读取目标与推送之间，把 stable 直接推到本次要发布的同一提交。流程无法区分，仍会写入记录。
- admin 修改 `github-gate`。这等于修改持有密钥的流程，可以让流程不经确认写入确认检查，或把密钥打印到公开日志。`github-gate` 的提交历史不能改写，所以修改会留下记录。
- admin 删除仍有子轨道的轨道。`gate-reconcile` 事后报告。
- 个人分支把 main 的提交跨层带进子轨道。只靠轨道 owner 的约定，见第 4 节。
- 专用身份的密钥外泄，影响见第 9 节。记录身份的密钥外泄时，持有者还能为已经绕过进入 main 的提交补建 unit，使它通过进入 stable 的覆盖核对，只剩 stable 级的检查与确认。
- admin 不写具名决定，直接移动 `gate/cutover.json` 中的核对下限。流程只读这个文件的当前值，察觉不到。修改留在 `github-gate` 的提交历史中，靠管理者审阅 `github-gate` 的改动发现。
- admin 删除起点标签。标签禁止删除，只有修改规则集后才能做到。该子轨道没有切换点时，上游按第 5 节无法确定，轨道冻结。若它因合法的缺口处置有切换点，上游会被读为 main，它可以直接进入 main，跨层禁令对它失效。
- admin 把 stable 推到 main first-parent 历史以外的提交。之后的 stable 发布要求旧 stable 是新提交的祖先。只要那个提交不是之后任何 main first-parent 提交的祖先，这个条件就不满足，stable 无法再经流程发布，只能按第 17 节恢复。

已知限制：

- 第一阶段的 unit 没有任务绑定，确认者无法核对提升 PR 的卡清单是否完整。owner 漏列的卡会随提升进入 main，其集成条件没有被核对。第二阶段写的 unit 带任务绑定，收集规则能发现这种情形；第一阶段写的 unit 仍不能。
- 第二阶段，检查 job 只为收集到的卡读取条件决定。记录流程写的 unit 保留 `target` 字段，见下一条。清单中多出、来自三类来源（第 9 节）的卡，集成条件仍只由确认者人工核对。
- 第二阶段切换第 3 步到第 4 步之间，main 仍由第一阶段的 `gate-publish` 发布，它的覆盖核对要求 unit 的 `target` 字段指向该轨道。记录流程写的 unit 必须保留 `target` 字段，否则这一段时间内所有轨道都无法进入 main。

第一阶段，正常路径不产生缺口：每次经 `gate-publish` 合入，都在同一次原子推送中为结果提交创建 unit，多层轨道的每一层都是这样。第一阶段的缺口只来自 admin 的绕过或第 17 节的恢复，这与单层时相同。第二阶段，记录流程失败或门铃失效也会产生缺口（第 9 节「记录流程与缺口」）。

缺口在闭合前会拦住提升。一条轨道上的一个缺口，会让这条轨道及它下面全部子轨道的成果都暂时无法经它提升。第一阶段没有补建 unit 的流程，缺口按第 8 节「定时核对与缺口」移动核对下限闭合。第二阶段，记录流程失败或门铃失效造成的缺口，由下一次运行按普通路径补建 unit；补建后该提交有了 unit，缺口 Issue 由补建的运行或 owner 注明后闭合。绕过造成的缺口，四项创建前核对必然不通过，补建的入口与核对由第二阶段的实施卡确定，经 admin 确认。移动下限会让下限之前的提交不再被核对，所以它只在具名决定说明了缺口提交的来源之后执行。

### 15. release 与对外发布

- release 只规定位置与准入方式。版本号规则、变更说明、向 npm 发布的步骤和凭据，以及多个包共用版本号还是各自编号，留给后续提案。
- release 在第一次对外发布之前创建，创建时直接采用确认一档。
- release 不在 policy registry 中登记。registry 只登记轨道，gate 按分支名识别 release。
- `@omne-harness/repo-toolchain` 与 `@omne-harness/repo-config` 经 `gate-release` 发到 npm，不经 release 主干，见第 16 节。

> 3. 确认必须填写说明，空说明被拒绝。说明原文写进发布决定评论。
> 4. 只有个人分支进入轨道的 PR 经这道确认。轨道进 main、main 进轨道和 main 进 stable 不经这道确认，它们搬运的提交都已经从个人分支进入过轨道。
> 5. 路径清单只在 `github-gate` 上维护，改它是对 `github-gate` 的 admin 改动。
> 6. policy registry（`integration-policy.json`）中检查命令、轨道检查或采用条件的改动，同样经这道闸门确认。现行的 `policy-check` 与 `policy-adopt` 在退役前继续有效。
>
> 第二阶段有 PR 自动检查之后，同样的判断改为 PR 上的一个必需检查，确认机制不变。
>
> **检查器与配置预设的发布**
>
> - 两个包的源码留在本仓库：`tools/repo-toolchain` 与 `tools/repo-config`，发布在 npm 的 `@omne-harness` 作用域下。根配置文件只保留按包名引用预设的入口（`tsconfig.base.json`、`.dependency-cruiser.cjs`、`.oxlintrc.json`）。其余工具成员（`tools/product-checks`、`tools/dev-flow`、`tools/test-runner`）不发布，由闸门保护。
> - 发包流程 `gate-release` 只在 `github-gate` 上运行，由派发者传入要发布的包、源提交与接收决定评论的 Issue。源提交必须已有 `omne/gate/unit` 记录，并在 main 或某条轨道的 first-parent 历史上；版本号取自该提交的 `package.json`；npm 上已有的版本不再发布，计划与发布前各查一次。同一个包的两次发布按并发组串行。
> - 确认走 `npm-release` environment，确认者与 `publish` 相同，必须填写说明。发布使用 npm 可信发布（GitHub OIDC，不存长期 token），附来源证明。流程把结果写进指定 Issue 的决定评论。
> - 发布成功但决定评论写入失败时，流程以失败结束；重跑会因版本已存在而停止。此时由派发者在该 Issue 上手动补记决定评论，引用运行链接。
> - 首个版本 0.0.1 由 AIEPhoenix 手动发布，因为 npm 的可信发布只能为已存在的包配置。
>
> **受信版本的载体与升级**
>
> - 受信版本是 `pnpm-workspace.yaml` 的 catalog 中两个包的精确版本，以及锁文件中它们的 resolution 与 integrity。根目录与不发布的工具成员用 `catalog:` 引用。`linkWorkspacePackages: false` 让普通版本号只从 registry 解析，安装的是 npm 上的包，不是工作区源码。
> - 仓库的检查（本地 `make check`、`scripts/integration-check.sh`、根命令 `check:declarations`、`lint:deps`、`lint:rules` 等）运行钉住的版本。改工作区 `tools/repo-toolchain` 或 `tools/repo-config` 的源码不改变这些检查的结果，只影响这两个成员自己的构建、类型检查与测试。收工钩子仍运行工作区源码，见「已知限制」。
> - 自动检查接入后（RFC-0004 第二阶段），检查器取自目标分支钉住的版本，不取自 PR 钉住的版本；PR 改钉子由闸门确认。
>
> 升级按下面的顺序：
>
> 1. 在一个 PR 里改检查器或预设，并提高版本号。这个 PR 改到工具链路径，经闸门确认；它仍由当前钉住的版本检查。
> 2. PR 进入轨道或 main 后，经 `gate-release` 发布新版本。
> 3. 再开一个只改 catalog 钉子与锁文件的 PR。确认者核对它的改动确实只有这两处；只有这样，用旧版本检查目标分支才等价于用旧版本检查候选。
> 4. 用旧版本在目标分支上、用新版本在组合候选上各跑一遍完整检查。PR 说明写两次的结果、差别，以及新版本删除或放宽的每一项检查；PR 作者列出这些项，确认者核对。确认说明引用 PR 说明。
> 5. 新版本在组合候选上的结果不得比旧版本在目标分支上的结果多出失败；两边都有的既有失败如实列出。不满足时不确认。
> 6. 新版本有问题时，再开一个 PR 把钉子改回旧版本，同样按第 3 至 5 步运行与确认。npm 上已经发布的版本不再修改。
>
> 第一阶段平台不跑检查，第 4 步的两次检查由提交者在本地运行，结果由确认者核对。第二阶段改为 PR 上的必需检查。
>
> 与 RFC-0004 及 #217 的升级保证相比：
>
> - **保持**：新旧都跑；旧版本的失败如实保留；删除或放宽的检查须逐项写明；确认后才换；待升级的版本不能批准自己（改钉子须经闸门确认，发布新版本须经 `npm-release` 确认）。
> - **改变**：受信版本从 `github-gate` 上的记录改为仓库里受闸门保护的钉子与锁文件；“新检查器必须通过”改为“新版本不得多出失败”，因为仓库目前有既有失败；删除或放宽的清单由 PR 作者列出、确认者核对，不由流程计算；旧版本检查目标分支，而不是候选，前提是第 3 步的核对；升级不再与 main、stable、release 的发布共用并发组，钉子改变后，在途 PR 须在包含新钉子的组合候选上重新检查（现行准入的组合候选规则）。
>
> **已知限制**
>
> - 第一阶段平台不跑检查。本地检查运行钉住的包，但结果由提交者写进说明，最终靠确认者把关。
> - agent 仍可以在包内用行内禁用注释或删除测试。这属于包内自治，仓库工具链只报告，不拦截。
> - 收工钩子仍运行执行检出里的 `tools/repo-toolchain` 源码。它给 agent 读数，不是准入检查。
> - Python 工具（`tools/spec-tools`、`.meta_harness/tooling`）不发布，不钉版本，由闸门保护。
> - 来源证明中的 `gitCommit` 是 `github-gate` 上的工作流提交，不是源提交。追溯源提交要经由“来源证明 → 运行 → 发布决定评论”。
> - npm 为两个包自动生成了占位版本 `0.0.0-stage`，它不是经本流程发布的版本，仓库不钉它。
>
> #217 的验收情形与本提案的对应：
>
> | #217 情形 | 本提案中的对应 | 状态 |
> | --- | --- | --- |
> | 成功升级 | 改钉子 PR 新旧都跑，新版本不多出失败，确认后合入 | 未演练。#351 是从运行工作区源码切到钉住版本的首次钉版，不是两个已发布版本之间的升级 |

> | 并发发布 | 同一个包的发布串行；钉子改变后在途 PR 须重新检查 | 前者已实施；后者依赖确认者执行现行准入的组合候选规则 |
> | 执行中断 | `gate-release` 只在 npm 上没有该版本时发布，重跑不覆盖；评论失败时手动补记 | 已实施；补记为人工步骤 |
> | 新克隆读取受信版本 | 新克隆按锁文件安装钉住的版本 | 已实施 |
>

- 第 6 项：轨道冻结时，经 RFC-0008 的升级顺序更新检查器。

### 17. 流程失效时的恢复（复述 RFC-0009）

> 本机工具删除之后，恢复路径如下：
>
> - `github-gate` 上的流程出错：admin 修正 `github-gate` 后重新启动流程。流程会重新核对目标与 PR，重复启动不会重复发布。
> - Actions 或发布身份不可用：admin 在一张 Issue 中写明原因，临时把自己加入相应规则集的例外，用普通的 Git 命令完成合并并推送，再恢复规则集并读回。推送产生的提交没有 unit 记录，定时核对（`gate-reconcile`）会把它报告为缺口 Issue。admin 在缺口 Issue 中写具名决定，说明该提交的来源与处置。RFC-0004「记录流程与缺口」规定闭合后由记录身份补建 unit；第一阶段的 `github-gate` 还没有补建 unit 的流程，`gate-reconcile` 只报告、不创建标签。补建入口实施之前，缺口 Issue 中的具名决定是这次恢复的处置记录。
>
> 这替代 RFC-0004「流程失效时的恢复」中“用本机工具完成发布”一句。admin 修改规则集仍属于 RFC-0004 所说的“admin 修改规则集”，定时核对与记录核对照常适用。

以上复述自 [RFC-0009](RFC-0009-adoption-and-local-tool-retirement.md) revision 1「流程失效时的恢复」，精确条款以原文为准。复述中的“RFC-0004「记录流程与缺口」”即本提案第 9 节「记录流程与缺口」。本提案在具名决定之后增加一步：admin 移动该分支的核对下限，使缺口闭合、提升恢复，见第 8 节「定时核对与缺口」。这一步由本提案第 8 节拥有，补充 RFC-0009 的恢复规则，RFC-0009 原文不变。

RFC-0004「流程失效时的恢复」中未被 RFC-0009 取代的部分，复述如下：

- main 以上的确认检查只有发布身份能写，规则集要求的检查对 admin 的手动推送同样生效。所以发布流程失效时，admin 也无法用手动推送发布。
- 恢复时，admin 在一张 Issue 中写明原因，临时调整相应规则集，再恢复规则集并读回。这一操作属于“admin 修改规则集”，定时核对与记录核对照常适用。

本提案对上面两条的推广：第一条只在第二阶段成立，因为第一阶段没有必需检查。临时调整在第一阶段是把自己加入更新限制的例外；第二阶段还要临时停用相应的必需检查规则集，因为这些规则集不设例外。

下列两条是本提案新增的条款，内容取自现行 [integration.md「权限、候选与恢复」](../engineering/integration.md#权限候选与恢复)，RFC-0004 原文没有：

- 运行结果未知时，先读运行页面、目标分支和 `omne/gate/*` 标签，不盲目重新派发。目标已等于本次的结果提交并且记录标签存在，就按已发布处理。
- Git 已发布而 Issue 投影失败时，由原正文单写者修复技术记录，不重放 Git。

### 18. 本机集成工具、task-sync 与 registry（复述 RFC-0009）

> | 受影响拥有者 | 现行保证或机制 | 拟改变内容 | 必须保持的条件与例外 |
> | --- | --- | --- | --- |
> | 集成规则，[多层分支规则](../engineering/integration.md) | 采用状态、首次接入、清理与政策接续、本机恢复手段 | 删除采用机制与本机发布路径的描述；写入新的 task-sync 与恢复方式 | 四条主干、两档准入、闸门与记录流程不变；采用、unit、checkpoint 标签仍不可修改和删除 |
> | 集成工具（`tools/dev-flow/src/integration`）及其契约 | 17 个命令，契约 I01 至 I11 | 保留 `register`、`start`、`status`、`baselines`，新增 `task-sync`；其余删除 | 开工准入的核对内容不变；task context 的读格式不变 |
> | policy registry（`integration-policy.json`） | 命令清单、profiles、owners、采用条件 | 只保留仓库、交付配置位置、轨道登记、远端与超时 | 轨道登记及其 owner 字段保留，`gate-track` 继续使用 |
> | `github-gate` | 路径清单列出将删除的文件 | admin 删去失效的路径 | 只有 admin 能改 `github-gate` |
>
> **退役的命令与文件**
>
> 删除下列命令及只为它们存在的实现、测试与文档：
>
> | 类别 | 命令或文件 |
> | --- | --- |
> | 采用机制 | `policy-handoff`、`policy-check`、`policy-adopt`、`bootstrap`、`activation-check`、`activate`；采用入口文件 `docs/engineering/integration-bootstrap.json` |
> | 本机发布 | `prepare`（含 `task-sync` 模式）、`seal`、`verify`、`publish`、`resume` |
> | 旧建轨道 | `track-register`、`track-bootstrap-plan`、`track-bootstrap`、`track-retire` |
> | 受信检出运行器 | `scripts/integration-check.sh` 及 `scripts/check.sh` 中转入它的分支 |
>
> - 建轨道由 `gate-track` 承担。`track-retire` 依赖采用锚点与旧的 `omne/integration/unit` 前缀，在现状下不能运行；轨道退役改由 admin 在 policy registry 中把轨道标为 retiring 或 retired，并删除轨道分支；轨道上的记录标签保留，不删除。具体流程跟随轨道退役另定，不再由本机工具执行。
> - `scripts/integration-check.sh` 只在设置受信检出时由 `scripts/check.sh` 转入，它服务于 `verify` 的受信运行器。`verify` 删除后它没有调用者。仓库的检查运行钉住的检查器版本（RFC-0008），不需要另一个受信检出。
> - 现有的采用标签（`omne/integration/adoption/*`）与旧 unit 标签不删除，作为历史保留，任何工具不再读取。标签不可修改和删除的规则不变。
>
> **保留的命令**
>
> - `register`、`start`：开工准入的核对内容不变：卡的修订、attempt、分支、taskBase、写范围与开工条件，拒绝已关闭的卡，一个工作树只绑定一个任务，派发权核对 `publish` environment 的 reviewer。`start` 不再读 `integration-bootstrap.json`，policy 固定读 `docs/engineering/integration-policy.json`；context 不再写 `anchor`。
> - `baselines`：不变。
> - `status`：改为报告本工作树的 task context 与远端目标分支：是否已绑定任务、绑定的卡与修订、`taskBase`、`targetBase`、远端目标分支当前提交，以及 `targetBase` 是否落后于远端目标。删除 pending、unknown、legacy、adopted 四种采用状态。
> - task context 的读格式不变：`schemaVersion` 仍为 1，`operation` 字段保留并写 `null`。因此这些改动只在不发布的 `tools/dev-flow` 中进行，不需要给 `@omne-harness/repo-toolchain` 发新版本。
>
> **task-sync 与两条基线**
>
> 任务执行期间同步目标分支，改为两步：
>
> 1. 执行者在自己的工作分支上用普通的 `git merge` 合并远端目标分支的某个提交 T，自己解决冲突并提交。
> 2. 执行者运行新命令 `task-sync --target T`。命令核对后，把本工作树 context 的 `targetBase` 原子更新为 T。
>
> `task-sync` 只在下列条件全部满足时更新，任一不满足就拒绝并不改 context：
>
> - 本工作树已绑定任务，context 可读。
> - T 是远端目标分支当前提交或其祖先。远端读不到时拒绝。
> - T 是当前 HEAD 的祖先，即确实已合并进工作分支。
> - 当前 `targetBase` 是 T 的祖先，`targetBase` 只能前进，不能后退或改到另一条历史。
> - 工作树没有未提交的改动。
>
> 两条基线的含义变为：
>
> - `targetBase`（目标基线）：最近一次同步进来的目标提交。影响面计算与组合检查以它为准。开工时等于派发时的目标 HEAD。
> - `taskBase`（任务起点）：开工时固定，任何同步都不改变。逐提交审计、验收锁与先改后改回的核对都从它开始，并照常检查合并进来的提交的全部父提交。
>
> 集成规则「两条基线」中“候选固定目标 B 和源 S、C 第一父为 B”只描述 `gate-publish` 构造的合并结果，不描述工作分支上的同步合并。工作分支上的同步合并，第一父是工作分支自己。
>
> **policy registry 瘦身**
>
> `integration-policy.json` 只保留：`schemaVersion`、`revision`、`repository`、`deliveryConfig`、`tracks`（轨道登记，含 owner、状态与 `initialMain`）、`transport`、`timeouts`。删除 `owners`、`commands`、`profiles`、`checkpointCoverage`、`requiredFiles`，以及轨道条目中的 `checks`。`parsePolicy` 同步改为只校验保留的字段。
>
> #290 方案把删除命令清单放在 turbo 接替之后。这一前提已经满足：影响面的成员选择与构建已交给 turbo（`tools/test-runner` 的 `turbo.ts`），类型检查与测试仍由测试运行器逐成员运行；`make check` 不读命令清单，它的读者只有将要删除的 `verify` 与采用命令。所以命令清单与退役命令同时删除。集成规则中“受影响检查今天仍由 `make check-plan` 与 `make test-affected` 执行……这些条件还没有在 turbo 上落地”一句已经过时，随本提案写回改正。
>
> policy registry 仍属于仓库工具链路径，改动经仓库工具链变更闸门确认（RFC-0008）。
>
> **第二阶段不再改造本机工具**
>
> RFC-0004 设想第二阶段把现行本机工具拆成“检查一半”与“推送一半”在 Actions 上运行，并相应修改工具契约 I07、I08、I09、I11。第一阶段的 `gate-publish` 已经不运行本机工具，这些工具在本提案中删除，所以这一改造不再进行。第二阶段的自动检查与发布在 `github-gate` 的流程中实现；RFC-0004 对第二阶段的其他要求（必需检查由专用身份报告、检查选择、记录核对）不变。stable 的完整检查即全量 `make check`（`FULL=1`），由目标分支钉住的检查器版本运行，不再从 policy 的 profiles 读取。
>
> “发布身份加入 `integration-policy.json` 的 owners，需要一次 policy 升级”的条款随之失去对象：流程不读 policy 的 owners，policy 也不再有 owners 字段。

以上复述自 [RFC-0009](RFC-0009-adoption-and-local-tool-retirement.md) revision 1「建议与改变范围」的受影响拥有者表，以及「退役的命令与文件」「保留的命令」「task-sync 与两条基线」「policy registry 瘦身」「第二阶段不再改造本机工具」各小节，精确条款以原文为准。下列各处由本提案部分取代，精确范围见「决定范围」：

- 「退役的命令与文件」中轨道退役“由 admin 在 policy registry 中把轨道标为 retiring 或 retired，并删除轨道分支”，以及 RFC-0009「决定范围」未决事项中“在此之前轨道退役由 admin 直接操作 policy registry 与分支”：改为删除分支即退役，有子轨道的轨道不能删除，registry 条目事后整理（第 13 节）。
- 「policy registry 瘦身」中轨道条目“含 owner、状态与 `initialMain`”：增加 `parent`，`initialMain` 改名为 `initialBase`，见第 5 节。
- 受影响拥有者表 policy registry 一行中“`gate-track` 继续使用”：`gate-track` 实际不读 registry，本提案也不让它读，见第 5、6 节。

复述中的 `make check`（`FULL=1`）现在是 `FULL=1 pnpm run check`。

### 第二阶段的验收

必须被平台拒绝：

1. 任何人推送一个没有通过该级必需检查的提交到任何主干，包括 admin。
2. 用合并按钮在 main、stable 或 release 上生成合并提交。
3. 用 squash 或 rebase 合入轨道。
4. 合并队列以外的方式更新轨道，包括 admin 推送一个已带有报告身份检查结果的提交。
5. 确认之后 main 发生变化，发布流程仍按旧候选推送。
6. 确认之后 Issue 的条件或授权发生变化，发布流程仍然推送。
7. stable 快进到 main 的 first-parent 历史以外的提交，或 release 快进到 stable 历史以外的提交。
8. 通过进入一条轨道的检查的提交被推到另一条轨道。通过进入 stable 的确认的提交进入 release。
9. 未经确认的运行读取发布环境中的密钥。`github-gate` 以外的引用上的运行读取任何一个环境中的密钥，包括 main。
10. 报告身份写入确认检查或创建标签。记录身份写检查结果，或者更新受保护的分支。
11. PR 分支里增加同名 job 冒充必需检查后进入任何主干。
12. 确认时不填写说明，发布流程仍然发布。
13. 专用身份以外的身份创建 unit、checkpoint 或版本标签。
14. admin 以外的身份更新 `github-gate`。任何人删除 `github-gate`，或对它做非快进更新。
15. 合并队列以 squash 或 rebase 合入轨道。
16. 子轨道有 first-parent 缺口时，经合并队列进入上游。
17. 个人工作分支改名为 `candidate/<名字>` 后，不带任务绑定进入轨道。

必须成功：

18. main 进轨道的同步 PR、子轨道进上游的提升 PR 经合并队列合入。记录流程不要求任务绑定，unit 记下类别与来源分支。

必须由流程停止：

19. 顶层轨道进 main 时，检查 job 经提升 unit 逐层收集到子轨道中各卡的绑定。收集结果中有一张卡不在提升 PR 说明的卡清单中时，流程停止。

必须被发现并报告：

20. admin 临时停用规则集后直接推送到轨道或 main。定时核对开出缺口 Issue。
21. admin 临时停用规则集后经 PR 合入轨道。记录流程拒绝创建 unit 并开出缺口 Issue。
22. 记录流程失败或被停用期间有提交进入轨道。定时核对开出缺口 Issue，下一次提升的自动检查失败。
23. 记录流程的自动触发与手动重跑同时发生。同一提交上不出现第二个 unit。

### 多层轨道的验证

`github-gate` 的流程没有自动测试。多层轨道的情形在一个测试仓库中运行，做法与 RFC-0004 的实测相同。测试仓库复制本仓库的规则集、environment 与 `github-gate` 流程，并在 `gate/cutover.json` 中登记一条模拟现有轨道 L。

不在本仓库建临时轨道：`omne/gate/*` 标签不能修改或删除，`gate-track` 又拒绝起点标签已存在的名称，临时轨道的名称会被永久占用；有的情形还要故意删除一条有子轨道的分支。

必须成功：

1. `gate-track` 从 main 创建 A，标签记录 `parent: main`。
2. `gate-track` 从 A 的 first-parent 提交创建 A1 与 A2，标签记录 `parent: A`。
3. `gate-track` 以 L 为上游创建 L1。
4. 个人分支进 A1。改动命中工具链路径时，经过 `repo-toolchain-review`。
5. A 进 A1，A1 进 A，不经过工具链审批。
6. A 进 main，L 进 main。
7. 三层：从 A1 创建 A1a；A1 进 A1a，A1a 进 A1。

必须被拒绝：

8. main 进 A1，A1 进 main，A 进 A1a，A1a 进 A。
9. A1 进 A2。
10. 个人分支进 main。
11. A1 有一个 first-parent 缺口时，A1 进 A。
12. `gate-track` 的 `parent` 为不存在的轨道；起点不在 parent 的 first-parent 历史上，或早于 parent 的核对下限；轨道名为 `main` 等保留名；轨道名已在 `gate/cutover.json` 中登记；参数格式不合格。
13. A 的分支被删除后，个人分支进 A1，个人分支进 A1a。

必须被报告：

14. A1 仍存在时删除 A 的分支，`gate-reconcile` 开缺口 Issue。

缺口处置：

15. 情形 11 之后，admin 在 `gate/cutover.json` 中为 A1 登记切换点，取缺口中最后一个没有 unit 的 first-parent 提交。A1 进 A 成功；`gate-publish` 与 `gate-reconcile` 读到的 A1 上游仍为 A；A 进 A1 仍被允许，main 进 A1 仍被拒绝。

本地工具（单元测试）：

16. registry 接受 `parent` 与 `initialBase`，拒绝未知字段。
17. `start` 在目标轨道或上游链上有未登记、retiring、retired 或分支不存在的轨道时拒绝；registry 仍登记为 active 而分支已删除时同样拒绝；有起点标签时，registry 的 `parent` 与标签不一致就拒绝；没有起点标签而有切换点时，`parent` 必须为 `main`；远端读不到时拒绝。其他轨道的开工不受影响。
18. `global` 与 `cross-track` route 指向顶层轨道。

本仓库只验证：现有轨道 legacy-refactor 与 engineering-toolchain 照常同步与提升。

  3. RFC-0009 revision 1「policy registry 瘦身」中轨道条目的字段：增加 `parent`，`initialMain` 改名为 `initialBase`。

  5. RFC-0002 revision 2「决定范围」中“准入缓存只读受信运行，还是完全关闭读取，仍要和 RFC-0004 一起定具体策略”，以及「建议与改变范围」中「影响面选择」约束 3 的“具体策略还要和 RFC-0004 一起决定”：定为进入任何一条主干之前的检查不读 turbo 任务缓存、只写本地缓存；是否写远程缓存仍归 RFC-0002 的未决项（第 8、9 节）。RFC-0002 的其他条款不变。
- 不采用范围及理由（RFC-0004 中不承接的条款）。下列各项也在 RFC-0004 被取代的范围内，只是本提案不重述它们：
  1. 「验证与消费者切换」中“`integration-policy.json` 登记 release 主干”。registry 只登记轨道，没有工具按 registry 识别 release，gate 按分支名识别。

  3. 「问题与有效输入」的有效输入表中“main、stable 和 release 的发布流程沿用 I04、I09 的候选与比较语义”。I04 与 I09 所属的本机工具已由 RFC-0009 删除。候选、目标比较与事务前重读的要求由第 9 节直接陈述，不再引用工具契约。
  4. 第二阶段探路表中以本机工具或工具契约为退路的后果，例如“恢复按工具契约 I11 读取真实引用”。理由同第 3 项。本提案的探路表已把这些后果改写为对 `github-gate` 流程的后果，例如“分支与标签分两次推送”。
  5. 起草过程的记录：「实质备选」中的草稿文件名（例如 `RFC-draft-merge-gate.r7-button-main.md`），以及散在正文与验收中的“实测中……”旁白。它们是 RFC-0004 起草时的过程记录，按[文档治理](../engineering/documentation.md#四类长期成果与普通任务)留在 RFC-0004 原文与 Git 历史中。实测结论本身已并入探路表的“当前依据”。
  6. 受影响拥有者表中“发布身份对应的用户加入 owners，需要一次 policy 升级”。RFC-0009 删除了 registry 的 owners 字段，这一条失去对象。
  7. 「发布决定评论」中“发布决定评论同时承担恢复依据……下一次运行据此判断上一次是否已经发布”，以及探路表“发布流程的操作意图保存在哪里”一行。RFC-0009「决定范围」第 8 项已整节取代 RFC-0004「恢复语义的改变」，替代句是“流程会重新核对目标与 PR，重复启动不会重复发布”。本提案第 9 节写明第二阶段重跑时先读真实引用，评论只用于核对与审计。
- 起草时的处理（随本提案一起接受）：
  1. 禁止兄弟轨道之间流动（第 4 节）。#420 D2 只决定了跨层流动。
  2. RFC-0004 所说 admin 的“确认和手动更新的权限”，指 admin 确认进入主干的 PR，主干的更新都由发布身份执行，与现行平台配置一致。按这一解释改写的位置：第 7 节；第 1 节「目标」中“阻止需要取消什么”（RFC-0004 原写“取消 admin 的更新权限”）；第 9 节「平台配置的改变」中 main、stable 与 release 的更新只允许发布身份（RFC-0004 原写“admin 和发布身份”）；第 9 节切换第 4 步删去“把更新权限改为 admin 和发布身份”；「实质备选」中“取消 admin 修改规则集等管理权限”一行（RFC-0004 原写“取消 admin 的更新权限”）。
  3. 跨轨道或全局的完整单元先进入一条顶层轨道，再随它进入 main（第 4 节）。这与现行 gate 规则一致。
  4. 现有轨道按 `gate/cutover.json` 的登记确定身份，可以作为子轨道的上游（第 5 节）。
  5. 同步与提升 PR 不要求任务绑定。第一阶段的 `gate-publish` 不机器核对任务绑定，卡上的条件由确认者按 PR 说明核对，所以第一阶段不受影响。RFC-0004 第二阶段的记录流程要求进入轨道的每个 PR 都声明任务绑定，没有为同步 PR 留出路：main 进轨道的同步 PR 拿不到 unit，轨道会因缺口无法再进 main。这在单层时已经存在，多层时子轨道的提升也遇到同样的问题。本提案在第二阶段免除同步与提升 PR 的任务绑定：判别按提交，head 提交在 base 的上游或某条直接子轨道的 first-parent 历史上；这类 unit 记类别与来源分支；进入 main 时逐层向下收集任务集合（第 9 节）。
  6. 第二阶段的检查 job 与推送 job 只经平台传递数据（第 9 节）。RFC-0004 把这一要求写在本机工具的拆分上；工具删除后，本提案把它改为对 `github-gate` 流程的要求。
  7. 第一阶段的缺口由 admin 移动 `gate/cutover.json` 中的核对下限闭合（第 8 节）。RFC-0004 与 RFC-0009 只规定了补建 unit，第一阶段没有补建流程；现行 `gate-publish` 与 `gate-reconcile` 已经先读这个文件，所以这一处置不需要新流程。为使移动下限不改变上游关系，上游的查找改为起点标签先于切换点（第 5 节）。
  8. 不采用 RFC-0004 留作第二阶段备选的“轨道不打 unit”（「实质备选」）。
  9. 提升 PR 由该轨道的 owner 提出，PR 说明列出所含的卡、条件以及每张卡的 Issue 编号、revision 与 attempt（第 8 节「提升 PR 的说明」）。现有顶层轨道进 main 时即适用。
  10. 卡上限定为某一层轨道的条件，由该轨道的 owner 在把 PR 加入合并队列前核对（第 9 节「轨道：合并队列」）。
  11. 轨道的 owner 拒绝把上游还没有的 main 提交跨层带进子轨道的个人分支 PR（第 4 节）。
  12. 第二阶段发布运行中断后重跑，先读真实引用，发布决定评论不作为恢复依据；目标等于候选而记录标签不存在时停止，发布身份不补建记录（第 9 节）。
  13. 进入 main 的任务集合按第 9 节的三步收集：每一层的区间按第 9 节第 1 步由一次提升确定，按提交结构识别上一次进入上游的提交；收集结果中多出的卡使流程停止；清单中多出的卡由流程列出、确认者逐张写明来源。RFC-0004 没有规定任务集合怎样跨层收集。
  14. 缺口分三类，各有闭合方式；没有 unit 的提交，具名决定须列出该提交带来的卡；第二阶段为绕过造成的缺口补建的 unit 记类别为缺口并引用缺口 Issue，记录流程失败或门铃失效造成的缺口按普通路径补建（第 8、9、14 节）。“上游链上有分支不存在”的缺口只能以删除上游链断开的各轨道闭合。
  15. 标签创建限制在第二阶段切换第 3 步放开，允许记录身份创建 unit（第 9 节）。RFC-0004 在第 4 步加标签创建限制，理由是本机工具发布 main 时要在同一次推送中创建 unit；第一阶段已把标签创建限制为只允许发布身份，所以本提案在第 3 步为记录身份放开 unit。
  16. 删除分支即退役，由 admin 执行；唯一的硬条件是没有其他轨道以它为上游；未提升的成果由删除的人处理；registry 条目事后经任意轨道整理，retiring 为可选标记。不设退役标记的顺序、专门的任务卡或固定格式的记录。现有 `development` 条目（retiring，分支已删除）可在增加 `parent` 的改动中删除，或在下次整理 registry 时清理（第 5、13 节）。
  17. paused 的轨道仍可同步与提升，paused 只表示不派发新任务（第 5 节）。
  18. 准入检查覆盖进入任何一条主干之前的检查，不读的是 turbo 任务缓存；只写本地缓存；第一阶段由提交者以 `OMNE_ADMISSION=1` 进入准入模式，进入 stable 时由确认者带这个变量运行，确认说明写明命令；本地缓存不进入 Git（第 8 节）。
  19. 第二阶段仓库工具链变更闸门保留，豁免与免绑定使用同一判别口径；闸门在合并队列上的形态、缺口 unit 的补建入口由第二阶段实施卡确定（第 8、9、14 节）。
  20. 已知绕过与已知限制增加：不写具名决定移动核对下限、删除起点标签、stable 被推到 main first-parent 历史以外、记录身份密钥外泄的扩展影响；第一阶段卡清单无法核对完整、三类来源卡的条件只由人工核对、记录流程的 unit 须保留 `target`（第 14 节）。
- 未决与依赖停止点：
  - 无。原列的四项已决定：
    1. 编号定为 RFC-0011。2026-10-20 核对远端全部分支，已用的最大编号是 RFC-0010（`integration/legacy-refactor` 等分支），RFC-0011 未被占用，PR 与 Issue 中也没有其他使用。
    2. 轨道退役简化为删除分支即退役，写入第 13 节。
    3. 集成条件评论只规定整体工作流需要的信息，其余不限定格式；流程读取方式由第二阶段实施卡在 `gate/README.md` 中定义（第 9 节）。RFC-0004 原计划在工具契约 I08 中定义，I08 已随本机工具删除。
    4. 规则集的“合并前必须完成部署”不作为前提，第二阶段保持由发布身份写确认检查；开工时实测，成立时另开提案（「实质备选」）。
