# RFC-0005：源码包的测试责任

规则与维护责任见[RFC入口](README.md)。本提案记录 [Issue #241 的补充评论](https://github.com/nemori-ai/omne-harness-lite/issues/241#issuecomment-6165378893)，标识是 `package-testing-boundaries-20261014-241`。它后继 [RFC-0003](RFC-0003-source-packages.md) revision 1 里「测试」那一行。RFC-0003 的 status 保持 accepted。PanQiWei 于 2026-10-14 接受本提案 revision 1，记录见[接受评论](https://github.com/nemori-ai/omne-harness-lite/issues/241#issuecomment-6165681764)。现行说明在[验证](../verification.md#包级测试责任与边界)。

## 问题与有效输入

RFC-0003 revision 1 要求成员测试在源码可直接执行时读源码，并且禁止用旧 `dist` 让缺少产物的测试通过。它没有规定单元、契约、集成和端到端分别由谁承担，也没有规定例外怎样写明。

这些分工目前散落在任务卡里。agent 交付操作和任务模板已经限制「单元只覆盖本包、集成与关键旅程按拥有者安排」。默认的契约测试、隔离边界、不适用理由、成员文档和模板消费还没有一处正文。

## 建议与改变范围

测试责任由包的公开承诺和实际职责决定。目录名、测试数量、是否起子进程、使用什么框架，都不决定责任。

`fast` 和 `slow` 记录执行成本。单元、契约、集成、端到端记录责任和组合范围。两套记录分开。`slow` 不等于端到端。`fast` 不能代替集成证据。

| 测试责任 | 默认承担者 | 应当证明什么 | 范围停在哪里 |
| --- | --- | --- | --- |
| 单元测试 | 原则上每个包 | 本包自身的规则、分支、状态变化、失败和适用边界 | 不为测本包逻辑启动无关系统。不反复验证下游包的内部实现 |
| 契约测试 | 原则上每个包 | 从公开入口观察输入、输出、拒绝、错误，以及本包承诺的所有权、生命周期和隔离。公开类型与运行时责任分别验证 | 以本包对消费者的承诺为边界。不依赖兄弟包的私有实现来证明契约 |
| 集成测试 | 实现具体存储或应用服务的包 | 本包与兑现承诺所必需的真实数据库、Worker、传输或其他依赖组合之后，事务、持久化、恢复、资源释放和失败传播是否成立 | 只组合该责任所需的参与者。纯定义和值包不因被服务消费而取得整套集成测试责任 |
| 端到端测试 | 明确拥有关键用户旅程的业务实现包 | 从该旅程的公开入口到可观察的业务结果，验证必要的关键协作和失败路径 | 只覆盖该拥有者负责的旅程和必要参与者。其他被调用的包不复制同一旅程 |

单元和契约是不同关注点。一次从公开入口运行的测试可以同时覆盖本包逻辑和契约。该测试必须能说明它验证了哪些承诺。

只发布类型、纯重导出，或其他确实没有某类行为的包，可以说明某项不适用。成员拥有者写明理由、替代证据和接受范围。没有运行时行为时，可以用类型消费测试验证公开类型。类型检查不能替代真实的运行时校验。

空目录、空脚本、恒真断言或整套 skip 不能充当「都有测试」。也不为了填表制造没有断言对象的测试。

隔离要求：

1. 单元和契约测试使用包的公开入口和受控依赖。夹具由本包或明确的测试设施拥有。依赖替身保持公开契约。测试不穿透兄弟包的私有源码，不读取旧实现，也不共享旧产物。
2. 测试需要文件、数据库、端口、进程或时钟时，写明谁创建、谁释放、怎样隔离，以及失败后怎样清理。测试不依赖开发者已有的登录、真实 `OMNE_HOME`、工作目录里的偶然状态，或其他用例留下的数据。
3. 必须由真实组合才能证明的性质，在该集成或旅程的拥有者处验证。模拟数据库不证明事务或持久性。模拟容器不证明 Cordis 行为。普通进程退出不证明物理断电耐久。替身的通过范围写清楚。
4. 源码导入测试，与实际安装、exports、声明、bin 和构建产物的消费验证，分别承担责任。独立消费测试证明包能被单独消费。它不是业务端到端测试。CLI 的 help 或 version 子进程测试不是整套用户旅程。
5. 跨包改动仍验证受影响的消费者。按影响面选择测试，表示本次运行哪些已经存在的责任。契约共用的符合性用例由契约拥有者维护。各提供者运行适用的部分。
6. 本提案不改变已接受的安全、租户隔离、事务或生命周期保证，也不取消适用的故障注入和独立验证。缩小组合范围是在标明责任。

模板默认引导单元和契约验证。实现具体存储或应用服务的包再增加集成入口。拥有关键用户旅程的包再增加旅程入口。模板不为每个包生成一套集成目录、端到端目录和全系统启动脚本。具体目录和 runner 由实施时的模板方案决定。本提案不预设那套目录名。

工具链负责发现和运行成员声明的测试。工具链不代替成员定义业务测试。通用运行器的后续重构仍归 `integration/engineering-toolchain`。本提案的规范落地不等待那次重构。

#242、#243、#244 的默认责任是自身单元、公开契约和独立消费。它们不启动治理服务、Session、数据库或完整 CLI。#245 验证自身状态、公开结果、受控时钟和必要进程边界。#246 在自身进程入口验证命令、输出、退出码和文件系统行为。该批的 help 和 version 不是完整业务旅程。#247 要写明未来提供者的真实数据库和 Worker 集成测试。当前探针不是生产提供者的符合性接受。#248 要写明公开契约和 Cordis 集成证据的责任。内核探针不扩展成每个业务包都运行的全系统旅程。这些卡消费写回后的规则。不在七张卡里复制本提案全文。

C8 的证据是正式源、精确条款、文档检查，以及本提案与现行规范的写回关系。C9 的证据是隔离临时样例，覆盖纯值或契约包、具体存储或应用服务实现包、关键旅程拥有者。样例不注册为产品成员。样例中的替身不能用来宣称真实数据库或完整用户旅程已经验证。选择机制尚未实现时，交回当前可用方法、未覆盖范围和具名后续责任。
