# 技术提案（RFC）

本目录规则已采用。正式提案从下方条目进入；提案登记、技术采用、规范切换和功能实现分别判断。交付卡日常启用范围仍由[交付配置](../engineering/github-delivery.json)拥有。

这里保存进入正式审议的技术提案及其决定范围，不从旧PF补造提案历史。

## 当前规范从哪里读

项目要求归[项目要求](../requirements.md)，全系统设计归[技术架构](../architecture/README.md)，领域关系归[领域设计](../domains/README.md)。精确规格与机制设计由实际成员维护。实施者先读当前拥有者，只有需要理解变化缘由时展开提案。

## 准入、编号与状态

真实技术变化需要审议时使用[RFC模板](.templates/rfc.md)；草稿先留任务tmp，拥有者、有效输入、实质方案和影响范围足以审议后分号。已有承诺足够的修复不强制提案。

身份为 `RFC-` 加四位递增序号，正式文件为 `RFC-编号-短名.md`。集成写者核对所有现存号后分配，编号不复用。并行作者写独立草稿，不争写编号或当前规范。

单篇front-matter唯一维护review、accepted、rejected或withdrawn状态。accepted注明精确revision与范围，不代表规范已切换或实现完成。决定状态不重开；新技术决定另开提案。部分或全部被后继取代是独立范围关系，不覆盖原决定。

## 现行源与维护

提案写回表定位已采用范围的真实承诺拥有者及切换修订。未写回提案不能作为新正式实施依据。写回定位分待写回、已写回和免除写回。后继决定获有权者接受后，由受影响规范拥有者确认仅被取消或替代且尚未写回的范围可免除；记录后继决定revision、范围、确认者及日期，部分免除须拆分，余项继续待写回。原接受决定固定，已执行写回不改为免除。未采用范围不产生写回义务。当前规格独立表达当前决定，不要求消费者拼读提案历史。

决定后的方案与决定范围固定，必要导航、更正标注和后继关系可维护。单篇状态和关系是唯一源，入口仅导航；未来列表可派生，不手填第二套状态。

## 保存与访问边界

技术提案及最小决定关系适用专门保留例外；访谈、逐轮评审、调度记录、执行日志及原始运行输出仍留tmp。输入是否可公开先由拥有者判断，不能因目录公开私有产品材料。
