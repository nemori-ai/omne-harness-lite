# RFC-0004：四条主干的 PR 准入与确认

规则与维护责任见[RFC入口](README.md)。PanQiWei 于 2026-10-14 接受本提案 revision 1，决定见[接受评论](https://github.com/nemori-ai/omne-harness-lite/issues/249#issuecomment-6164587010)。本文是该决定的正式文本。它不是实施许可，规范写回尚未发生。

## 问题与有效输入

现行规则要求每次共享发布同时创建一个不可变的 unit 标签。这个要求由本地的集成工具执行，GitHub 不知道它。在 GitHub 上合并 PR 不需要 unit 标签，所以合并可以绕过记录。

所核输入为 main `6d0e6ee03a57c34d4f4c399151bd28557f0fc019`。平台状态于 2026-10-14 用 `gh api` 读回。下列陈述分三类标注。

已观察的事实：

- 首次采用 `02c0fc82` 之后，main 的 first-parent 历史有 11 个提交。其中 8 个没有 unit 标签，7 个是 squash 合并。清单见 [#208 的调查报告](https://github.com/nemori-ai/omne-harness-lite/issues/208#issuecomment-6145636814)。
- 这 8 个缺口使 stable 的首次 checkpoint 被拒。`prepare` 返回 `Unregistered direct track commit`，退出码为 2。
- 规则集 24987710、24989192 和 24987717 分别限制 main、`integration/**` 和 stable 的创建与更新。三者的 bypass 名单都只有一个用户。规则集 24987710 创建于 2026-10-13。
- 规则集 24987709 和 24989191 禁止 main、stable 和轨道的非快进更新，bypass 名单为空。它们与上一条的三个规则集相互独立。
- 规则集 24926783 禁止更新和删除 adoption、unit 与 checkpoint 标签，bypass 名单为空。它不限制创建。
- 仓库有 4 个 admin。仓库允许 merge commit、squash 和 rebase 三种合并方式。
- 仓库属于 Free 计划的 organization，可见性为公开。仓库没有注册自托管 runner，也没有 environment。
- `.github/workflows/check.yml` 只保留手动触发。文件注明自 2026-10-01 起以本地 `make check` 为准。
- 集成工具的发布步骤读取具名 owner 的 Issue 评论决定。它把决定与操作、候选、目标、来源、任务集合和回执逐项绑定，并在事务前重读 Issue 输入和授权。依据是工具契约 I08 与 `publish.ts`。
- 现行规则不要求代码经 PR 进入轨道或 main。owner 在本机运行集成工具，由工具构造合并提交并推送。PR 只用于查看和讨论改动。`integration.md` 只在首次接入的准备步骤中提到 PR。
- 现行规则没有 release 分支。远端也还没有 stable 分支。
- 集成工具从已采用提交取检查器，不从候选取。依据是工具契约 I07。检查器升级要求旧检查器先放行新 main。[#217](https://github.com/nemori-ai/omne-harness-lite/issues/217) 记录了旧检查器拒绝自身迁移的情况。

来自官方文档的陈述：

- Free 计划可以给公开仓库配置 environment。environment 可以设置必需的确认者（required reviewers）。确认者确认后，引用它的 job 才继续。管理员绕过的选项可以关闭。
- 规则集的“要求指定工作流通过”只在 organization 或 enterprise 级提供。2023 年的更新日志写明它只属于 Enterprise 计划。
- 规则集的“要求状态检查通过”只按检查名称和来源 App 判断，不区分产生检查的工作流文件。
- `pull_request` 事件使用 PR 合并引用上的工作流文件。
- `pull_request_target` 事件使用默认分支上的工作流文件，PR 不能修改它。官方事件参考写明它的运行引用是默认分支。官方提醒这类工作流不要带着密钥或写权限执行 PR 的代码，并点名缓存投毒。
- 合并队列（merge queue）在目标分支的最新状态上组合 PR，在组合结果上运行必需检查，通过后把目标分支更新到这个组合结果。它触发 `merge_group` 事件。[官方文档](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-a-merge-queue)写明 organization 拥有的公开仓库可以使用。合并队列有自己的合并方式设置，与仓库的合并方式设置分开。
- 标准规格的 GitHub 托管 runner 对公开仓库免费。官方不建议公开仓库使用自托管 runner。
- 规则集的 bypass 名单可以包含 GitHub App。标签规则集可以限制创建，只允许 bypass 名单内的身份创建。
- 公开仓库的 Actions 日志最多保留 90 天。

在测试仓库实测的事实（2026-10-14，Free 计划 organization 中的公开仓库，逐条记录留在任务 tmp）：

- 有写权限的人可以在 PR 中增加一个与必需检查同名的 job，或者用自带的令牌写一个同名的提交状态。两者的来源都显示为 GitHub Actions。规则集为必需检查指定来源 App 后，这两种冒充都不被认可，冒充的 PR 也进不了合并队列。
- 规则集要求的检查对推送同样生效。在 stable 上，admin 在更新限制的例外名单内，推送没有检查的提交仍被拒。在 main 上，`--admin` 合并和合并接口因缺少必需检查被拒。
- environment 的分支限制按运行的引用判断。只接受 `github-gate` 时，main、PR、合并队列临时分支和轨道上发起的运行都被拒绝。
- 用 `workflow_dispatch` 在 `github-gate` 上派发时，平台使用 `github-gate` 上的工作流文件。默认分支上必须存在同名文件，否则派发返回 404。
- 门铃可以在 `pull_request` 和 `merge_group` 事件中用自带的令牌派发运行。
- 合并队列把目标分支直接移到它检查过的提交。只用 merge commit 时，这个提交的第一父是原目标，第二父是 PR 的提交。合并队列的规则集不接受通配符分支名。
- GitHub App 列入例外名单后，可以在一次原子推送中更新受保护的分支并创建受限的标签。推送包含 PR 提交时，平台把 PR 标为已合并，合并者显示为该 App。
- environment 的确认说明可以从运行的确认记录读回。重跑需要重新确认。
- 网页上的 organization 审计日志在 Free 计划可用，记录了被拒的引用更新、App 使用规则例外和间接合并。审计日志接口在 Free 计划不可用。

推断：

- 规则集 24987710 生效后，合并按钮只对 bypass 名单内的用户有效。缺口的剩余来源是该用户不经集成工具直接合并。
- 同一目标分支上有多个并行的 PR 时，合并按钮生成的合并提交是一个没有被检查过的组合。现行工具在目标变化时拒绝发布，要求重建候选并复验。

### 与 #208 和 #217 的关系

#208 和 #217 暴露的是同一个缺口的两面：决定和执行没有被平台绑在一起，检查器的版本也没有一条正当的更换路径。

- #208 负责核定 8 个历史缺口，并决定怎样恢复记录。本提案只防止新的缺口，不处理已有的缺口。缺口核定之前，第一次进入 stable 的 PR 不会通过。
- #217 要求一个可重复使用的检查器升级流程。本提案让 `github-gate` 规定检查器的受信版本，并把升级做成准入流程的一种，由 admin 确认、发布身份执行。本提案一并解决 #217：它的适用条件、证据、批准人、失败行为和测试要求都在“检查器的受信版本与升级”一节给出。#217 的设计阶段成果即本提案，实施随本提案一起派发。

## 建议与改变范围

提案人对目标的说明如下，本节按它设计。

- 要的是留痕和权限集中，不是把人隔离在外。
- admin 目前是 PanQiWei，以后可能增加。admin 也必须先确认才能让代码进入 main、stable 和 release，可以自己确认。
- 确认由人作出。机器身份只在人确认之后执行动作，或者只报告结果。
- main、stable 和 release 要严格把关。轨道是最频繁的一层，把关可以轻一些。
- 轨道保持现行定位。它是按责任划分的共享汇集点，不是直接开发的分支。

### 四条主干

| 主干 | 代表什么 | 接受的来源 | 记录 |
| --- | --- | --- | --- |
| `integration/<track>` | 一类工作的汇集 | 工作分支，以及 main 的同步 | unit 标签 |
| `main` | 各轨道汇合后的完整结果 | 轨道，以及跨轨道或全局的完整单元 | unit 标签 |
| `stable` | 代码到达一个稳定节点 | main 上的一个提交 | checkpoint 标签 |
| `release` | 对外发布的版本，与 npm 上的版本对应 | stable 上的一个提交 | 版本标签 |

代码只沿一个方向提升：工作分支进轨道，轨道进 main，main 进 stable，stable 进 release。main 向轨道的同步是唯一的反向流动。

另有三类分支不是主干：

- 工作分支。任务在这里开发，不受限制。
- `candidate/<名字>`。它是从 main 或 stable 上选定的一个提交创建的临时分支，用来向上一级提 PR。来源主干前进时它不变，所以不需要重复确认。提升完成后删除。
- `github-gate`。它保存准入流程本身，不保存产品代码。

### 名称

- 自动检查：准入流程自动运行的检查。
- 确认：一位 admin 在 Actions 中同意一次具体的提升。它对应现行规则里的“盖章”。
- 确认检查：确认之后才写入的那一项检查结果。
- 报告身份：一个专用的 GitHub App。它只能写检查结果。它报告自动检查的结果。
- 记录身份：一个专用的 GitHub App。它为进入轨道的提交创建 unit。GitHub App 的写权限不区分引用，限制来自规则集：在受保护的分支和标签上，它只能创建 unit 标签。它仍能推送不受保护的分支，例如工作分支和 `candidate/<名字>`。
- 发布身份：一个专用的 GitHub App。它能写检查结果，能更新 main、stable 和 release，能创建这三级的记录标签。它写入确认检查，并执行这三级的发布。
- 发布流程：使用发布身份的流程。它运行现行集成工具的候选、验证和发布步骤。

### 两档准入

| 主干 | 自动检查 | 确认 | 更新由谁执行 | 记录何时创建 |
| --- | --- | --- | --- | --- |
| 轨道 | 必须通过 | 不需要 | 有写权限的人把 PR 加入合并队列，由合并队列更新 | 进入轨道后由记录流程创建 |
| main | 必须通过 | 需要一位 admin 确认 | 确认后由发布流程推送 | 与分支在同一次推送中创建 |
| stable、release | 必须通过 | 需要一位 admin 确认 | 确认后由发布流程快进 | 与分支在同一次推送中创建 |

进入主干的每个提交，都必须是通过了该级必需检查的那个提交本身。规则集要求的检查对 admin 的手动推送同样生效，不设例外。

### 轨道：合并队列

轨道启用合并队列，只允许 merge commit 这一种合并方式。合并队列的规则集不接受通配符分支名，所以每条轨道单独一个规则集。新增轨道时同时新增它的规则集。仓库还须开启自动合并，否则 PR 无法加入队列。

1. 工作分支向轨道提 PR。门铃派发准入流程，由报告身份把自动检查的结果登记在 PR 的提交上。PR 的提交通过该轨道的必需检查之后，才能加入合并队列。
2. 有写权限的人把 PR 加入合并队列。合并队列规则本身拒绝直接推送，admin 也不例外，所以进入轨道只有经由队列这一条路。但平台规则不能限制谁加入队列：实测中，给轨道加上“只有 admin 能更新”的规则后，合并队列连 admin 加入的 PR 也合不进去，例外名单换成“只在经由 PR 时放行”的模式也一样。所以轨道 owner 认可 PR 是约定，不由平台强制。本仓库只有 admin 有写权限，其余协作者只有读权限，所以目前能加入队列的只有 admin。
3. 合并队列在轨道的最新状态上组合 PR，触发 `merge_group` 事件。门铃流程派发 `github-gate` 上的准入流程，由它对组合结果运行自动检查，并用报告身份登记结果。
4. 检查通过后，合并队列把轨道更新到这个组合结果。实测表明合并队列直接把轨道移到被检查的提交，不另外生成提交。
5. 记录流程为这个提交创建 unit 标签。unit 的 `verification` 指向报告身份在这个提交上登记的检查结果。

多个 PR 同时进入队列时，合并队列逐个组合、逐个检查。目标前进后，后续 PR 在新的状态上重新组合和检查，不需要人重新操作。

main 向轨道的同步也走这条路径。同步的来源是 `candidate/<名字>`。

轨道不要求集成条件的决定。集成条件在进入 main 时核对，与现行规则相同。

### 现行集成工具的改造

现行工具的发布步骤读取检查阶段在同一台机器上留下的回执、日志、检查器工作目录和候选工作目录。在 Actions 上，检查和发布必须是两个 job：确认发生在 job 开始时，而确认者须先看到检查结果。所以现行工具不能原样运行，须拆成两半，这是本提案的实施内容。

- 检查一半：在没有密钥的 job 中运行。它构造候选、用受信版本的检查器验证候选、核对来源轨道的记录和集成条件的决定，并把结论交给报告身份登记到候选上。
- 推送一半：在持有密钥的 job 中运行，不执行任何内容，也不读取检查 job 留下的任何文件。它只向平台查询并核对三件事：候选上有报告身份登记的、该级名称的通过检查，目标仍是预期的提交，候选的父提交和树与重新计算的结果一致。核对通过后才推送。

这一改造使现行的检查回执（工具契约 I07）在四条主干的路径上由“报告身份在候选上登记的结果加推送前的重新计算”替代，远端前提（I09）、发布决定（I08）和恢复语义（I11）也随之修改，见“受影响的拥有者”。实测中跑通的是这种拆分后的形态，不是现行工具本身。

两半之间只经平台传递数据。推送一半使用的提交号只来自校验过的派发参数和平台查询，不来自检查 job 的输出，因为检查 job 执行候选的代码，可以改写自己的输出。

### main：确认后由发布流程推送

1. 轨道或跨轨道的完整单元向 main 提 PR。PR 上的检查只供参考，不是 main 的必需检查。
2. 准备好发布时，admin 手动派发 main 的发布流程，传入 PR 编号。PR 打开或更新不自动派发它：main 的发布流程共用一个并发组，等待确认的运行会占住这个组，自动派发会让其他运行被平台取消。被取消的运行由 admin 重新派发。
3. 检查一半在 main 的当前状态上构造候选并验证。构造候选的 job 用自带的令牌把候选推到不受保护的 `candidate/main-pr-<编号>`，以便报告身份能在它上面登记结果。候选与 PR 有冲突时流程停止。冲突须先在来源轨道上把 main 合进来解决，再重新发布。
4. 报告身份把 main 级的自动检查登记到候选上。
5. 流程暂停，运行页面列出候选、main 和 PR 的提交号，等待一位 admin 在 Actions 中确认。确认的对象就是这一个候选。确认者必须填写说明。
6. 推送一半读取这次确认的确认者、时间和说明，说明为空时停止。然后它核对：main 仍是预期的提交，PR 的提交没有变，候选的两个父提交正好是 main 和 PR 的提交，候选的树等于这两者合并的结果，候选上有报告身份登记的 main 级检查。任何一项不符，流程停止，不发出发布决定。
7. 流程合成发布决定评论，由发布身份发在 PR 上，并在每张涉及的卡的 Issue 里留一条带链接的评论。评论包含确认者写的说明、平台记录的确认者和时间、候选、main 和 PR 的提交号、要更新的分支和标签名，以及所引用的集成条件决定。
8. 发布身份把确认检查写到候选上，然后用一次原子推送更新 main 并创建 unit 标签。
9. 平台发现 PR 的提交已经进入 main，把 PR 标为已合并。推送完成或失败后，流程在 PR 上补记结果。

集成条件的决定仍由 owner 写，不由流程代写。现行工具里，条件确认和历史复核写在 owner 的发布决定评论中。改造后，owner 在卡的 Issue 中写一条单独的条件决定评论，检查一半读取它，流程合成的发布决定评论引用它。这是工具契约 I08 新增的一种评论格式。

发布决定评论的作者是发布身份，不是确认者。现行工具契约 I08 要求评论作者是 policy owner，这一条改为：评论作者是发布身份，评论中记载的确认者是 admin，并且与平台的确认记录一致。确认者以平台记录为准，评论中的名字只是抄录。这一改变使任何 admin 都能作出发布决定，而现行 policy owner 只有 PanQiWei。发布身份对应的用户须加入 `integration-policy.json` 的 owners，这需要一次 policy 升级。

评论长期保存在 PR 和 Issue 里，不受 Actions 记录保留期的影响。发布决定评论同时承担恢复依据：它记载了候选和 unit 标签名，下一次运行据此判断上一次是否已经发布，见“恢复语义的改变”。

平台无法区分确认是 admin 本人作出的，还是 admin 的 agent 用 admin 的凭据作出的。提案人认为这不构成问题：agent 归属于人，确认记录表示该 admin 行使了确认权，责任由该 admin 承担，与[贡献交付](../../CONTRIBUTING.md#形成可审阅的交付)中“负责的人承担最终内容”一致。实测中，agent 用 admin 的 gh 凭据通过接口完成过确认，平台记录的确认者就是该 admin。

发布决定评论在推送之前发出，所以推送失败时，评论记载的决定没有生效，须以结果记录为准。实测中出现过推送失败而决定评论已发出的情况。

main 的发布流程串行运行。确认之后 main 发生变化时，发布流程停止。重新构造的候选须重新验证和确认，与现行“目标变化要求重建候选和复验”相同。

main 级的必需检查只写在发布流程构造的候选上，名称与 PR 上的检查不同。所以 admin 点合并按钮生成的合并提交没有 main 级的必需检查，平台拒绝它。实测中，合并按钮、合并接口和 `--admin` 合并都被拒绝。

### stable 与 release：确认后由发布流程快进

1. admin 在来源主干上选定一个提交，创建 `candidate/<名字>`，向目标主干提 PR，并派发发布流程，传入这个提交号。
2. 检查一半在这个提交上运行 stable 级或 release 级的检查，报告身份登记结果。
3. 一位 admin 在 Actions 中确认，并填写说明。运行页面列出要推送的提交号。
4. 推送一半核对：目标主干仍是预期的提交，这次更新是快进，派发时传入的提交上有报告身份登记的该级检查。推送的提交固定为派发时传入、运行页面列出的那一个，不在推送时重读 PR 的提交。`candidate/<名字>` 不受保护，可能在确认后被改动。
5. 流程合成发布决定评论发在 PR 上，然后用一次原子推送把目标主干快进到这个提交，同时创建 checkpoint 标签或版本标签。两者要么都成功，要么都不成功。
6. 平台把 PR 标为已合并。这一点在 main 上实测过，在 stable 上是推断：stable 的两次实测没有使用 PR。

stable 和 release 仍直接指向来源主干上已有的提交，不产生新提交。stable 的条件决定和历史复核与 main 相同，由 owner 写在卡的 Issue 中，检查一半读取。

### 每一级的自动检查

| 主干 | 自动检查的内容 |
| --- | --- |
| 轨道 | 针对改动范围的检查，见下文。PR 声明它对应的 Issue 和派发记录，检查按这份派发记录做 taskBase 和 writeScope 审计，并拒绝认领写范围不符的卡 |
| main | 轨道一档的全部内容。来源轨道上每个提交都有 unit 标签。集成条件的决定 |
| stable | PR 的提交在 main 的 first-parent 历史上，并且旧 stable 是它的祖先。从起点到这个提交，main 上每个提交都有 unit 标签。采用的 policy 规定的启动、安装和迁移检查 |
| release | PR 的提交在 stable 的历史上，并且有 checkpoint 标签。旧 release 是它的祖先。发布前检查留给后续提案 |

检查器取自受信版本，不取自 PR，也不取自 main 的最新提交。受信版本的来源见下文“检查器的受信版本”。

自动检查按改动范围选择，不在每次准入时运行全量检查。这是本提案的硬性要求，原因是轨道是最频繁的一层，每次都跑全量会让准入的耗时随仓库增长而失控。

- 轨道和 main：用现行的受影响检查工具（`make check-plan` 和 `make test-affected`）按实际改动、声明依赖和读者规则选出成员，只运行这些成员的检查。选择依据与[开发指南](../development.md#迭代中的受影响测试)相同，不能凭“没修改那个包”省略消费者验证。
- stable：运行采用的 policy 规定的完整检查。stable 的频率低，并且它是共同的稳定基准。
- 受影响范围的计算由检查器完成，检查器取自受信版本，选择规则文件也从检查器一侧读取。PR 不能通过修改选择规则缩小自己的检查范围。PR 改动根目录的 `package.json`、`pnpm-workspace.yaml` 等全局文件时，现行规则会选中全部成员。
- 比较基线从平台查询，不取自门铃传入的参数。PR 阶段以 PR 与目标分支的共同祖先为基线，合并队列阶段以队列组合的目标提交为基线。

完整检查在托管 runner 上的耗时没有实测。按改动范围检查之后，准入的耗时取决于改动大小，而不是仓库大小。

平台按名称和来源判断必需检查。必需检查按轨道和级别分别命名，确认检查也按级别分别命名。准入流程登记的检查名中的轨道，由流程向平台查询 PR 的目标分支或合并队列临时分支的名称得出，不取自门铃参数。被检查的提交不是任何一个到该轨道的 PR 的提交，也不是该轨道合并队列的组合提交时，流程停止。否则通过进入一条轨道的检查的提交，可以被推到另一条轨道。通过进入 stable 的确认的提交，也可以被当作已确认进入 release。

### 必需检查由专用身份报告

平台按名称和来源应用判断必需检查。如果检查由普通的 job 报告，PR 分支可以新增一个工作流，放一个与必需检查同名、直接成功的 job。它的来源同样是 GitHub Actions，平台无法区分。

为此，全部必需检查都由专用身份报告。规则集为自动检查指定来源为报告身份，为确认检查指定来源为发布身份。其他来源报告的同名检查不被认可。

三个身份的密钥分别保存在三个 environment 里。三者都只接受 `github-gate` 引用上的运行，都关闭管理员跳过。见下文“门铃与 `github-gate` 上的运行”。

- 报告环境：不设确认者，只保存报告身份的密钥。报告身份还能读取 organization 的 Project。准入流程用它在不执行 PR 内容的 job 中读取任务看板，只把检查需要的字段交给检查 job，例如卡的派发记录、taskBase 和写范围。检查 job 执行 PR 的代码，交给它的数据等于公开。实测中，自带的令牌读取同一看板返回空列表而不报错，所以流程把空看板当作错误。
- 记录环境：不设确认者，只保存记录身份的密钥。
- 发布环境：设置必需的确认者，即 admin，允许发起人自己确认。它只保存发布身份的密钥。

执行 PR 内容的检查 job 不引用任何 environment，没有密钥，令牌只读。

PR 自带的工作流可以为自带的令牌申请写权限。实测中，仓库默认权限设为只读，PR 里的工作流声明写权限后仍新建了一个分支。所以本提案以下列前提为准：

- GitHub Actions 自带的身份不进入任何规则集的例外名单，也不进入 policy 的 owners。
- 受保护的分支和标签只靠规则集保护。
- 留痕以评论和标签为准，不依赖运行日志。

使用密钥的 job 不执行 PR 内容，不恢复缓存，不执行检查 job 产生的任何文件，引用的第三方 action 用完整提交号固定，安装依赖时不执行包的生命周期脚本。

仓库是公开的，Actions 的运行日志对所有人可见。使用密钥的 job 不在日志中打印看板内容、Issue 的非公开信息或任何凭据，只打印判断结果和提交号。

检查结果的可信度以检查 job 为上限。检查 job 执行 PR 的代码，它不是沙箱，PR 的代码可以影响同一 job 的结果。这一点与现行的本机验证相同。

各身份的密钥单独外泄时，影响如下：

- 报告身份：持有者能伪造自动检查。未通过检查的内容可以进入轨道。main、stable 和 release 还需要确认检查和发布身份。
- 记录身份：持有者能为任意提交创建 unit 标签。伪造的 unit 让缺口不被发现，但内容进入 main 时仍要通过检查和确认。
- 发布身份：持有者能写入确认检查，并能更新 main、stable 和 release。它不能伪造自动检查，但报告身份在确认之前就把自动检查登记到候选上。所以对任何已经通过检查、正在等待确认的候选，持有者都能自己写入确认检查并推送，不经任何人确认。stable 和 release 同理：来源主干上已有的提交通过检查后，持有者可以直接更新这两级。发布身份的密钥须按与 admin 权限同等的级别保管和轮换。

### 记录流程与缺口

记录流程为进入轨道的提交创建 unit。

- 触发：只有两个入口。一是 PR 被合并队列合入轨道时，`pull_request` 关闭事件触发门铃，门铃派发记录流程。这个门铃使用的是轨道上合入之后的那份工作流文件，所以每条轨道都要有门铃文件。二是有人在 `github-gate` 上手动派发记录流程。
- 串行：两个入口使用同一个按轨道命名的并发组，同一条轨道同时只有一次记录流程在运行。同一提交上出现两个 unit 会使现行工具永久拒绝该轨道，而标签不能删除，所以必须串行。
- 每次扫整条轨道：平台的并发组最多保留一个等待中的运行，更新的运行会取消它。为此，记录流程每次都为整条轨道上所有没有 unit 的提交补建，而不只处理触发它的那一个提交。被取消的运行留下的提交，由后面任何一次运行补上。
- 创建前核对：记录流程为一个提交创建 unit 之前，核对四件事：
  1. 这个提交上有报告身份登记的、该轨道名称的通过检查。按报告身份对应用户的编号识别，不按显示名识别。
  2. 这个提交是合并队列合入的，即存在一个已合并的 PR，其合并提交就是它。
  3. 它的第一父是轨道的上一个提交，第二父是这个 PR 的提交。
  4. 对应的 PR 声明了任务绑定。

  少了任何一件都不够。实测中，admin 停用规则集后把一个单提交 PR 的提交直接快进推到轨道上，平台把这个 PR 标为已合并，合并提交就是它本身。它能通过除第二父以外的全部核对，只有第二父的核对能识别它。核对不通过时，它不创建 unit，并开一张缺口 Issue。创建前再查一次该提交是否已有 unit，已有则跳过。
- 定时核对只报告：一个定时运行的流程逐条核对轨道和 main 的 first-parent 历史，为没有 unit 的提交开一张缺口 Issue。它不创建标签，所以不会与记录流程冲突。直接推送没有 PR 事件，它能比下一次进入 main 更早发现。它跳过合入后尚不足一个记录周期的提交，以免在记录流程运行之前开出缺口 Issue。
- 门铃副本：合入事件的门铃使用轨道上的文件，所以门铃的改动要经各轨道自己的准入进入每条轨道。某条轨道的门铃失效时，该轨道的 unit 要等到下一次手动派发的记录流程才补上，期间进入 main 的检查会因缺 unit 而失败。
- 标签创建：unit 标签只允许记录身份和发布身份创建。checkpoint、版本和采用标签只允许发布身份创建。

上一级的自动检查会核对下一级的记录是否完整。轨道上缺 unit 的提交进不了 main。main 上缺 unit 的提交进不了 stable。

缺口出现后，相应主干的提升被拦住，直到缺口闭合。闭合须由 admin 在缺口 Issue 中写下具名决定，说明该提交的来源和处置，再由记录身份创建 unit。启用之前的 8 个缺口按 #208 的决定处理。

### 准入流程保存在 `github-gate` 分支

- `github-gate` 分支保存准入、记录、定时核对、发布和升级流程的定义，以及受信版本文件。只有 admin 和发布身份能更新它，发布身份只在升级流程中更新受信版本文件。任何人不能删除它，也不能对它做非快进更新，所以更新历史留在这个分支上。
- 修改准入流程由 admin 直接更新 `github-gate`，不需要旧流程先放行新流程。
- main 上为 `github-gate` 的每个流程保留一个同名的空壳文件。平台只允许派发默认分支上存在的工作流。空壳文件的内容不影响安全，因为派发到 `github-gate` 的运行使用 `github-gate` 上的定义。新增流程时，空壳文件须先经 main 的准入进入 main。

### 门铃与 `github-gate` 上的运行

GitHub 的手动派发（`workflow_dispatch`）可以指定在哪个分支上运行一个工作流，平台使用该分支上的工作流文件。所以在 `github-gate` 上派发的运行，执行的一定是 `github-gate` 上的流程定义。

全部使用密钥的工作都在 `github-gate` 上派发的运行中完成。三个 environment 只接受 `github-gate` 引用上的运行。PR 分支、合并队列的临时分支和 main 上的工作流都拿不到密钥。

各种事件只负责按门铃：

- PR 打开或更新、PR 进入合并队列、PR 被合入、定时核对的时间到达，都由一个很薄的门铃流程响应。确认不需要门铃，它发生在同一次运行中。
- 门铃流程只做一件事：用自带的令牌派发 `github-gate` 上的相应流程，并传入 PR 编号或提交号。
- `github-gate` 上的流程自己向平台查询这个 PR 或提交的真实信息，不采信门铃传来的其他内容。
- 门铃传入的参数一律当作数据。`github-gate` 上的流程先校验格式，例如提交号必须是 40 位十六进制，事件名必须在允许的列表中，校验不通过就停止。参数只经环境变量传给命令，不直接拼进命令文本，否则门铃可以借参数在持有密钥的运行中执行任意命令。

门铃流程不受信任，可以被 PR 修改。它被修改后的后果如下：

- 不按门铃：没有检查结果，PR 进不了主干。
- 让准入流程检查别的提交：准入流程照实检查，结果登记在那个提交上。
- 反复按门铃：多出的运行按提交号排入并发组。

所以密钥的安全不再依赖 main 上 `.github/workflows/` 的内容。

### 检查器的受信版本与升级

本节一并解决 [#217](https://github.com/nemori-ai/omne-harness-lite/issues/217)。

#### 受信版本记在哪里

`github-gate` 上保存一个文件，写明受信检查器的提交号。准入流程和发布流程每次运行开始时读取它，按它取出检查器，并把读到的值写在运行页面上。

采用标签保留为记录。每次升级，升级流程在同一次原子推送中更新这个文件并创建对应的采用标签，两者始终一致。本机工具和新克隆照旧从采用标签读取检查器版本。流程每次运行都核对文件与最新采用标签一致，不一致时停止。

#### 适用条件

下列改动须经升级流程，不能经普通的 main 准入生效：

- 改变受信检查器的提交，即集成工具及其锁文件的版本。
- 改变 policy registry 中登记的检查命令、轨道检查或采用条件。

普通的 main 准入用当前的受信检查器检查候选。候选包含新检查规则，而旧检查器不认识它时，普通准入会失败。这正是 #217 记录的情况，此时改走升级流程。

#### 升级流程

1. admin 在 `github-gate` 上派发升级流程，传入包含新检查器的 PR 编号。
2. 检查一半在没有密钥的 job 中构造候选，分别用当前的受信检查器和候选中的新检查器，按各自登记的命令检查候选。两次检查的命令、退出码和日志摘要都写在运行页面上。旧检查器的失败如实保留，不改写成通过。
3. 检查一半比较新旧两份检查命令清单，列出新检查器删除或放宽的每一项检查。
4. 新检查器检查不通过时，流程停止。
5. 流程暂停，等待一位 admin 确认。确认说明必须逐项说明第 3 步列出的删除或放宽。列出了删除或放宽而说明为空时，流程停止。这一条防止待升级的版本取消检查后批准自己。
6. 推送一半核对 main、PR 的提交和受信版本文件在确认后都没有变化，然后用一次原子推送完成三件事：更新 main、更新 `github-gate` 上的受信版本文件、创建新的采用标签。
7. 流程发出升级决定评论，记载旧版本、新版本、候选、两次检查的结果摘要、删除或放宽的检查及确认者的说明。

推送一半要更新 `github-gate`，所以发布身份须列入 `github-gate` 和采用标签的更新例外名单。admin 直接修改 `github-gate` 上的受信版本文件仍然可行，但不经过上述证据和确认，属于“admin 修改 `github-gate`”这条绕过路径。

#### 并发与中断

- 升级流程与 main、stable、release 的发布流程使用同一个并发组。升级进行时不发布，发布进行时不升级。
- 每次准入或发布运行在开始时记下受信版本。推送之前再读一次，与开始时不一致就停止。升级之前开始、尚未完成的运行因此全部失效，须在新版本下重新运行。这对应 #217 要求的“旧工作上下文何时失效”。
- 升级流程中断后，下一次运行先读取受信版本文件、最新采用标签和 main。三者都已指向新版本时，报告已升级并结束。三者都未变时，按未升级处理，重新检查和确认。其他情形停止并交 PanQiWei 处理。

#### 验收

#217 要求的测试情形都纳入本提案的验收，用隔离的测试仓库、固定的版本和实际的流程完成：

- 成功升级：旧检查器拒绝、新检查器通过，确认后 main、受信版本文件和采用标签一起更新。
- 未经授权：没有确认、确认说明为空，或者列出了删除或放宽却没有逐项说明，流程都不更新任何引用。
- 版本或证据变化：确认后 PR 的提交、main 或受信版本文件发生变化，流程停止。
- 并发发布：升级期间派发的发布排队等待，升级之前开始的运行在推送前停止。
- 执行中断：推送前后中断，下一次运行能正确判断已升级或未升级。
- 新克隆读取采用记录：升级后新克隆的本机工具从采用标签读到新版本，与 `github-gate` 上的文件一致。

#217 中由一次维护授权完成的那次迁移不重做，它的记录继续有效。

### 保证

本提案给出两个保证，强度不同。

- 正常使用时，进入主干的提交就是通过了该级必需检查的提交。进入 main、stable 和 release 的提交还经过了确认。平台强制这两点，对 admin 也一样。
- 有人绕过时，绕过会被发现并留下记录。定时核对和记录流程负责尽早发现，上一级的自动检查负责最迟在下一次提升时拦住。

第二个保证针对下列绕过方式。本提案不阻止它们，只保证能发现。

- admin 修改或停用规则集和 environment 后直接推送。定时核对发现没有 unit 的提交。admin 停用规则集后经 PR 合入或快进推送时，记录流程的创建前核对会拒绝创建并开出缺口 Issue。admin 若同时伪造了 unit，只能靠 organization 的审计日志发现。审计日志在 Free 计划的网页上可用，实测记录了被拒的引用更新、专用身份使用规则例外和间接合并。规则集修改事件是否记录尚未核对。审计日志由谁查看、多久查看一次，由 PanQiWei 决定。
- admin 修改 `github-gate`。这等于修改持有密钥的流程，可以让流程不经确认写入确认检查，或把密钥打印到公开日志。`github-gate` 的提交历史不能改写，所以修改会留下记录。由谁审阅 `github-gate` 的改动、多久审阅一次，由 PanQiWei 决定。
- 专用身份的密钥外泄。影响见上文。

选择“发现”而不选择“阻止”是提案人的要求。阻止需要取消 admin 的更新权限，人不再能直接操作主干。

### 流程失效时的恢复

main 以上的确认检查只有发布身份能写，规则集要求的检查对 admin 的手动推送同样生效。所以发布流程失效时，admin 也无法用手动推送发布。恢复办法是：admin 在一张 Issue 中写明原因，临时调整相应规则集，用本机工具完成发布，再恢复规则集并读回。这一操作属于上文的“admin 修改规则集”，定时核对和记录核对照常适用。

### 恢复语义的改变

现行工具在推送前把操作意图写入本机的操作目录，失败或超时后由下一次运行读取意图并观察真实引用，判断已发布、未发布或分裂。这是工具契约 I11。发布流程在一次性的 runner 上运行，下一次运行读不到上一次的操作目录。本提案把四条主干上的恢复改为：以发布决定评论为意图记录，依据真实引用判断。新的运行先读取该 PR 上最近一条发布决定评论中的候选和标签名，再观察真实引用。目标已指向该候选并且标签匹配时，流程报告已发布并结束。目标未变并且标签不存在时，流程按未发布处理，重新验证并重新确认。其他情形，包括分支与标签不一致，流程停止并交 owner 处理。这是对 I11 的修改，须写回工具契约。

实施后的验收至少包含下列情形。

必须被平台拒绝：

1. 任何人推送一个没有通过该级必需检查的提交到任何主干，包括 admin。
2. 用合并按钮在 main、stable 或 release 上生成合并提交。
3. 用 squash 或 rebase 合入轨道。
4. 合并队列以外的方式更新轨道，包括 admin 推送一个已带有报告身份检查结果的提交。实测中合并队列规则以“改动必须经由合并队列”拒绝了这种推送。
5. 确认之后 main 发生变化，发布流程仍按旧候选推送。
6. 确认之后 Issue 的条件或授权发生变化，发布流程仍然推送。
7. stable 快进到 main 的 first-parent 历史以外的提交，或 release 快进到 stable 历史以外的提交。
8. 通过进入一条轨道的检查的提交被推到另一条轨道。通过进入 stable 的确认的提交进入 release。
9. 未经确认的运行读取发布环境中的密钥。`github-gate` 以外的引用上的运行读取任何一个环境中的密钥，包括 main。
10. 报告身份写入确认检查或创建标签。记录身份写检查结果，或者更新受保护的分支。
11. PR 分支里增加同名 job 冒充必需检查后进入任何主干。
12. 确认时不填写说明，发布流程仍然发布。
13. 专用身份以外的身份创建 unit、checkpoint 或版本标签。
14. admin 和发布身份以外的身份更新 `github-gate`。任何人删除 `github-gate`，或对它做非快进更新。
15. 合并队列以 squash 或 rebase 合入轨道。

必须被发现并报告：

16. admin 临时停用规则集后直接推送到轨道或 main。定时核对开出缺口 Issue。
17. admin 临时停用规则集后经 PR 合入轨道。记录流程拒绝创建 unit 并开出缺口 Issue。
18. 记录流程失败或被停用期间有提交进入轨道。定时核对开出缺口 Issue，下一次进入 main 的自动检查失败。
19. 记录流程的自动触发与手动重跑同时发生，或在试运行期间与本机工具并存。同一提交上不出现第二个 unit。

消费者切换的责任如下：

- 集成工具的 `SPEC.md` 和 `README.md` 写明本机发布步骤不再用于四条主干，写明新入口的契约，以及在一次性 runner 上运行时的恢复依据。
- `integration-policy.json` 登记 release 主干。registry 中每条轨道的 owner 按约定负责把该轨道的 PR 加入合并队列。
- `branch-integration` 技能、`docs/development.md` 和 [agent-delivery.md](../engineering/agent-delivery.md) 中的发布步骤随之更新。
- [发布边界](../engineering/publication.md)核对 release 主干与它现有内容的关系。
- `check.yml` 的文件说明随远程检查的恢复更新。
- 远程检查恢复后，pstack 的 `fix-ci`、`babysit` 等方法才有输入。是否采用它们由[技能入口](../engineering/skills.md)的拥有者另行决定，不属于本提案。

切换分四步交付。

1. 试运行。创建 `github-gate` 分支、三个专用身份和三个 environment，门铃流程进入 main。规则集不动。准入、记录和发布流程只计算和比较，不写检查结果，不创建标签，不推送。本机工具照常发布。
2. 观察若干次真实的发布，核对流程的计算结果与本机工具的实际结果一致。
3. 轨道切换。仓库和合并队列都只允许 merge commit，轨道启用合并队列，新增轨道的必需检查规则集，记录流程开始写 unit。从这一步起，本机工具不再用于轨道。
4. main 和 stable 切换。新增 main 和 stable 的必需检查规则集，把更新权限改为 admin 和发布身份，限制标签的创建，发布流程开始推送。标签创建的限制放在这一步，因为本机工具发布 main 时要在同一次推送中创建 unit，提前限制会使第 3 步与第 4 步之间无法发布 main。从这一步起，本机工具不再用于 main 和 stable。release 主干在第一次对外发布之前创建，创建时直接采用确认一档。

第 3 步和第 4 步是平台设置操作，由 admin 执行，完成后读回全部规则集并执行上面的验收。每一步开始前，owner 停止在本机对相应主干运行发布步骤，避免两条路径为同一提交各写一个 unit。退回时停用新增的规则集，恢复原来的更新权限，本机工具恢复使用。已经创建的标签不能删除，所以退回不撤销已有的记录。
