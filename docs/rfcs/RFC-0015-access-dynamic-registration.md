# RFC-0015：接入层动态注册与最小桌面应用

规则与维护责任见[RFC入口](README.md)。本页记录设计与决定范围。现行行为以文末[写回现行正文](#写回现行正文)所列的拥有者正文为准。提案采用、规范写回、实现和交付接受分别判断。

本提案回答一个问题：各领域怎样把自己的对外接口和事件流交给接入层，使得加一个领域不用改接入层，桌面、网页、命令行各种应用共用同一层，并且应用自己也是动态系统的一部分。它同时给出第一种应用形态，一个最小而完整的桌面应用的设计。

## 问题与有效输入

### 要解决的问题

入口只认三个固定的位置。每加一个对外操作，要同时改三个成员。人工介入刚按这个做法加了第三个位置。日历、通知、工作区都等着对外开放。各种应用形态都要先有一层共用的接入层。用的人还没有图形界面，不能在一个应用里登录、找回以前的会话、改设置、和 agent 对话。

不处理的后果：

- 每个新领域对外开放，都要改入口。
- 每种应用形态各写各的客户端。
- 运行中装上或卸下一个领域做不到，要改代码重新发行。
- 用的人只能用命令行一条一条发命令，自己读返回的数据。

普通设置项的细节：

| 环节 | 现在 |
| --- | --- |
| 声明 | 部署里声明的普通项只有一类：六个工具（Shell、Files、Tools、TodoItems、Ask、Web）各一项「调用权限」。它是权限项，值是「挑选」加「允许集合」，挑选在拒绝、询问、自动三档里取一档，默认是询问。秘密项是模型供应商密钥这一类 |
| 读 | 设置领域的目录读取已有，每行带声明、求值结果、来源、被谁锁定、可操作的授权、修订号。服务端应用实例化了目录，只在写会话这一层的权限时用，没有对外的入口。目录对权限项给出的是「默认加租户」两层的结果，不是权限的生效值：组织层在另一个域里，生效值由权限另行求出 |
| 写 | 设置领域有变更命令（设置、清除、锁定、解锁，带预期修订号）和两步的写入协议（准备、提交，另有取消、认回、读变更）。本机实现有按租户主体核资格的写入服务。它要的输入里，计划、提交时重读当前事实的参与者、三个阶段的存储登记、封口的路由，在正式装配里都没有提供者，测试装配里用的是夹具。租户层的写入不过权限的写入判断 |
| 生效 | 每次工具调用有三个检查点：Agent 动作准入、工具调用准入、工具启动。每个检查点都现读租户层、组织层、会话层的配值并交给权限求值，不缓存。「拒绝」不启动，「自动」启动。「询问」按会话的权限模式处理：跳过询问的模式下直接放行，要人批准的模式下答「不可用」，两种都不出卡。发行配置里两个 Agent 的权限模式都是跳过询问 |

三处现行正文禁止的都是 SDK 依赖服务端的东西。客户端自己有一棵装配树，原文没有禁止，也没有提到：

- [系统分层](../architecture/layers-and-dependencies.md#依赖关系与禁止方向)：「SDK 依赖公开契约及其平台适配，不依赖服务端的存储、运行时实例或 Cordis 装配树。」
- [接入组说明](../../packages/access/README.md)：「SDK 不依赖服务端私有实现、存储或 Cordis 装配树。」
- [公开契约规格](../../packages/access/public-contract/SPEC.md)：「它不依赖 server-entry。它不依赖服务器存储包。」

### 推断与未知

- 写入服务要的装配输入在正式装配里都没有提供者，已经核过，见上表「写」一行。所以租户层的写入这一段是新写，不是接线。
- 现在唯一的普通设置项是工具的调用权限。普通项可写，在界面上的意思就是使用者能改每个工具是拒绝、询问还是自动。这是权限边界上的改动，按风险级别从严验收。
- 日历与日程已经合入集成轨道。它没有改接入组、入口行和命令行，所以没有新增固定位置。它对外开放时按本提案挂一个协议。
- Skill 与 MCP 那条还没进轨道的分支，有没有碰入口，没有核。

### 受影响的消费者

现有线上形状的消费者：命令行、服务端应用、契约骨架验证应用，以及接入组三个成员的测试与验收。完整清单见[验证与消费者切换](#验证与消费者切换)。项目在 0.0.0 到 0.1.0 阶段，历史字节不是兼容承诺，消费者同一批改完，不留旧形状。

## 建议与改变范围

接入层自己不拥有任何领域的操作。它只提供每个领域都要用的那部分，并让领域把自己的对外协议挂上来。本提案做四件事：

1. 把「一个领域的对外协议」定义成显式的对象：一份协议契约，加一份贡献。
2. 让贡献随 Cordis 插件挂上和撤下。
3. 让「现在开放着哪些协议」这件事本身可以被客户端订阅。这是动态性穿过网络的那一环。
4. 让客户端也是一棵 Cordis 装配树。服务端挂上一个协议，客户端对应的那一支跟着长出来。服务端撤下，客户端那一支跟着收掉。

在这个结构之上，本提案交付一个最小而完整的桌面应用：登录、会话管理、设置、对话四部分。

### 1. 概念

每个词只有一个意思。其中八个进了统一语言，正式名与定义以词条为准：[公开协议](../../.meta_harness/design/ubiquitous_language/terms/architecture-core-and-extension.md#ul-public-protocol--公开协议--public-protocol)、[接入贡献](../../.meta_harness/design/ubiquitous_language/terms/architecture-core-and-extension.md#ul-access-contribution--接入贡献--access-contribution)、[公开观察](../../.meta_harness/design/ubiquitous_language/terms/interaction-and-dispatch.md#ul-public-observation--公开观察--public-observation)、[协议可用性](../../.meta_harness/design/ubiquitous_language/terms/reach-and-availability.md#ul-protocol-availability--协议可用性--protocol-availability)、[会话观察](../../.meta_harness/design/ubiquitous_language/terms/record-and-context.md#ul-session-observation--会话观察--session-observation)、[界面外壳](../../.meta_harness/design/ubiquitous_language/terms/interaction-and-dispatch.md#ul-app-shell--界面外壳--app-shell)、[界面模块](../../.meta_harness/design/ubiquitous_language/terms/interaction-and-dispatch.md#ul-ui-module--界面模块--ui-module)、[界面插入位置](../../.meta_harness/design/ubiquitous_language/terms/interaction-and-dispatch.md#ul-ui-slot--界面插入位置--ui-slot)。本页在没有歧义的地方用简称：协议、贡献、观察、可用性、外壳、插入位置。其余的词是本提案内的名字。

| 概念 | 意思 | 例子 |
| --- | --- | --- |
| 公开协议 | 一个领域对外的一整套操作与观察，有名字和主版本 | `session/v1` |
| 操作 | 一问一答。客户端发一条消息，服务端答一条消息 | `session/v1` 的 `list-sessions` |
| 观察 | 客户端订阅一条事件流，服务端按顺序一帧一帧推 | `session/v1` 的 `observe-session` |
| 协议契约 | 公开协议的纯数据定义：每个操作叫什么、身份要求是什么、消息体怎么读写、可能出现哪几种结果。它里面没有服务端的任何对象 | 会话组里定义 `session/v1` 的那份纯数据 |
| 身份要求 | 操作契约里的一栏，取「不需要」「登录」「行事租户」之一。它决定管道走到身份的哪一步 | 「列出会话」的身份要求是「登录」 |
| 登录证明 | 登录签发得到的凭据。客户端每次调用把它放在 `Authorization` 头里 | 桌面应用主进程的凭据库里保存的那一份 |
| 行事租户 | 请求头里带的租户。管道按它为调用者签发代租户行事的主体 | 「建会话」用行事租户 |
| 目标租户 | 消息体里带的租户。由领域的处理函数核对 | 「列出会话」消息体里的 `tenant` |
| 贡献 | 一份协议契约，加每个操作的处理函数与每个观察的帧来源。它是一个领域交给接入层的全部东西 | 会话的接入插件挂上去的那一包 |
| 接入插件 | 领域包组里单独的一个服务端 Cordis 插件。它把本领域的贡献挂上登记表 | 会话的接入插件挂上 `session/v1` |
| 帧来源 | 一个观察在服务端的承接者。先决定建不建立，建立之后吐帧，走完时给出结束原因 | 会话观察是 `observe-session` 的帧来源 |
| 登记表 | 记着现在挂着哪些贡献 | 挂上会话的贡献后多一行 `session/v1` |
| 在途调用 | 已经进了登记表、还没答复的一次调用 | 一次正在等处理函数答复的「发输入」 |
| 管道 | 每次调用都走的固定步骤：认登录、核租户、签主体、读消息体、交给领域判断、把结果写回 | 每个操作自动走完公共的几步 |
| 承载绑定 | 把一种线路上的字节变成逻辑消息，再把答复变回字节 | HTTP 加 SSE 的承载绑定 |
| 观察中枢 | 管理所有在途观察：预算、队列、心跳、结束 | 登录被撤销时，由它结束这个登录的观察 |
| 可用性 | 登记表对外的投影：现在挂着哪些协议。它和调用者是谁无关 | 装上会话的接入插件后，可用性里多出 `session/v1` |
| 内置协议 | 入口自己挂的协议 `access/v1`。可用性是它里面的一个观察 | 客户端一接上就订阅 `access/v1` 的可用性 |
| 传输 | 客户端一侧发一次调用、开一个观察的能力。它负责带上身份 | 桌面应用页面里的进程间传输 |
| 客户端核心 | 纯函数。给它一份协议契约和一个传输，得到一组带类型的方法 | `createClient(sessionProtocol, transport)` |
| 协议客户端 | 一个协议在客户端的一组方法。服务端宣告这个协议开放期间，它是客户端树上的一个服务 | 树上的服务 `protocol:session/v1` |
| 连接 | 客户端树上的服务：持有传输，记着可用性，报告登录状态 | 桌面应用页面里树上的 `connection` |
| 客户端装配 | 应用进程里的一棵 Cordis 树。协议客户端是树上的服务，界面模块是依赖这些服务的插件 | 桌面应用页面里的那棵树 |
| 外壳 | 一种应用形态自己的那部分：怎么画、有哪些插入位置。它不认识任何领域 | 桌面应用的窗口与导航 |
| 插入位置 | 外壳声明的、界面模块可以往里放东西的地方。种类是「只放一个」或「放一列」 | 「侧栏区」 |
| 界面模块 | 一个客户端 Cordis 插件。它声明依赖哪些协议客户端，往插入位置里放东西 | 会话的界面模块往侧栏区放会话列表 |
| 共用界面件 | 各领域界面共用的基础组件、主题、多语言的装配、流式 Markdown 的包装 | 各界面模块共用的按钮与主题 |
| 主进程 | Electron 的主进程。它是连接里可信的那一半 | 保管登录证明、替页面发 HTTP 请求的那个进程 |
| 页面 | Electron 的渲染进程。外壳、客户端的树、各领域的界面模块都在里面 | 显示对话的那个窗口里的内容 |
| 通用通道 | 页面和主进程之间的进程间通信。它不认识任何领域 | 页面经「调用」通道发一次 `list-sessions` |
| 登录会话 | 主进程里的状态机：未登录、登录中、已登录、退出中 | 打开应用时读到登录证明，登录会话进「已登录」 |
| 凭据库 | 主进程里保存登录证明的地方 | 用操作系统提供的加密保存的那一份 |
| 会话列表项 | 每个会话为了列出而多出的四个属性：创建时刻、最近活动时刻、生命周期、标题 | 一行：今天上午建、刚刚活动、`active`、「帮我整理下周的日程」 |
| 会话观察 | 一个会话的进行中视图，以观察的形式送给获准的观察者。它由会话一侧的一个集成成员产出，这个成员认识会话契约和模型契约，是 `observe-session` 的帧来源 | 对话界面里正在生成的那一段回复 |
| 通道 | 客户端和服务端之间一条双向、连续、不重放的媒体流。本提案只定位置和规则 | 一次语音通话里的声音 |

**同一个结构，在每个尺度上。** 每一层都是同样的三样东西：一份契约、一个承接者、一段寿命。

服务端：

| 尺度 | 契约 | 承接者 | 寿命跟着谁 |
| --- | --- | --- | --- |
| 整个 Harness 的公开面 | 协议的集合 | 入口 | 应用装配 |
| 一个协议 | 操作与观察的集合 | 一份贡献 | 领域接入插件的作用域 |
| 一个操作 | 身份要求、消息体、结果集 | 处理函数 | 一次调用 |
| 一个观察 | 建立点、帧、结束原因 | 帧来源 | 一次订阅 |

客户端是它的镜像：

| 尺度 | 契约 | 承接者 | 寿命跟着谁 |
| --- | --- | --- | --- |
| 整个应用 | 可用的协议的集合 | 连接 | 应用的一次运行 |
| 一个协议 | 同一份协议契约 | 协议客户端 | 服务端宣告它开放的那段时间 |
| 一个操作 | 同一份操作契约 | 方法 | 一次调用 |
| 一个观察 | 同一份观察契约 | 订阅句柄 | 一次订阅 |

四个推论：

- **大的由小的组成，没有别的东西。** 入口自己不拥有任何操作。客户端核心自己不认识任何协议。
- **上一层收了，下一层跟着收。** 这条链从服务端的应用装配一直通到客户端的一个界面模块。
- **可用性也是这个结构的一个实例。** 它是内置协议 `access/v1` 里的一个观察。登记表的变化，用登记表管理的机制对外说。
- **界面要用的视图不是另一个尺度。** 例如会话诊断要同时读会话、Agent、模型、工具四处。它是一份普通的贡献，只是它的处理函数依赖四个领域的读口。

**完全动态的系统要守的七条。** 「动态」的意思是：系统有哪些能力，是一个随时间变化的量。应用也在这个系统之内。

| # | 要守的 | 对设计的要求 |
| --- | --- | --- |
| 一 | 谁都不能把「有什么」当成常量 | 登记表每次调用现查。客户端不在构建期写死有哪些协议 |
| 二 | 「有什么」变了，要让依赖它的人知道。只能靠推 | 可用性本身是一个观察。它有快照，有变化帧，断了能续 |
| 三 | 依赖要声明出来。代码里不散落「如果某领域在就怎样」的判断 | 客户端有和服务端一样的依赖声明与生灭机制，由 Cordis 提供 |
| 四 | 寿命一层套一层，两边成对 | 网络边界不切断这条链。线两边是同一棵逻辑树的两段 |
| 五 | 撤下的时候，正在做的事都有确定的结局 | 两边各有一张全化表，见[状态与操作](#13-状态与操作) |
| 六 | 线上的契约是唯一不变的东西。对得上靠协议的名字和主版本 | 对不上不是错误。客户端有某个领域的界面模块而服务端没开放这个协议，这个模块只是不激活 |
| 七 | 短暂够不着不等于撤下 | 「暂时不可达」由调用结果表达，「已经撤下」才触发生灭 |

另有两条和动态无关，同样要守：服务端是事实的权威，客户端只有投影和缓存。身份与租户每次调用显式带上。

### 2. 每件事归谁

| 事实或决定 | 拥有者 |
| --- | --- |
| 一个操作的业务含义、允许与拒绝 | 该操作所属的领域 |
| 一个操作在线上的字段与结果 | 该领域的协议契约成员 |
| 逻辑消息的共同部分、对外结果表、判断次序、可用性 | 接入 |
| 登录识别、行事租户、主体签发 | 身份与授权。管道只调用，不改写 |
| 字节怎么走、地址、头、状态码、SSE 格式、上限 | 接入的承载绑定 |
| 这个部署开放哪些协议 | 服务端的应用装配。有贡献不等于自动开放 |
| 协议什么时候挂上、撤下 | Cordis 作用域，两边各一棵树 |
| 怎样发一次调用、读一次答复 | 接入的客户端核心。纯函数，不依赖 Cordis |
| 协议客户端什么时候在、界面模块什么时候在 | 接入的客户端装配 |
| 登录证明放在哪、由谁带到每次调用上 | 接入的客户端装配里的连接。桌面应用里由主进程持有 |
| 会话观察的帧从哪来 | 会话观察。它认识会话与模型两份契约，两个领域互不认识 |
| 会话诊断：一次读会话、Agent、模型、工具四处 | 会话一侧的一个集成成员，做成一份单独的贡献。装不装由应用装配定 |
| 插入位置的契约、各领域界面共用的基础组件与主题 | 界面外壳契约与共用界面件，能力组 `frontend` |
| 窗口、导航、插入位置的布局 | 各应用的外壳。本提案是桌面应用 |
| 一个领域在界面上长什么样 | 该领域的界面模块 |
| 一块消息内容给不给人看 | 产出这一块的一方，写在这一块的标注上 |
| 服务端给了的内容在界面上怎样显示 | 界面 |
| 设置项的含义、类型与合法值、默认、清除后果、生效时点 | 拥有这一项的资产 |

### 3. 共同契约

共同契约是一个纯成员，两端共用。下面的类型是设计形状，不是代码。

```ts
// 对外结果。封闭集合，由接入拥有。
type Outcome =
  | 'succeeded' | 'no-change' | 'not-committed' | 'need-decision'
  | 'protocol-rejected' | 'invalid' | 'uniform-auth-failure' | 'denied' | 'not-loginable'
  | 'not-visible' | 'not-found' | 'conflict' | 'archived' | 'frozen' | 'limited'
  | 'unsupported' | 'not-writable' | 'stage-not-provided' | 'basis-unavailable' | 'unknown'

// 这些结果的响应体永远是空对象，领域不能给它们加字段。
// 前四种管道自己会替领域答；后两种为了拒绝一致也固定为空。
type FixedOutcome = 'denied' | 'protocol-rejected' | 'basis-unavailable' | 'unknown' | 'uniform-auth-failure' | 'stage-not-provided'

// 两个函数都带调用方给的结构上限；契约里只写上限的名字。读写都返回结果，不合规时给 ok: false，不抛出。
// 现行形状归公开契约规格「共同契约」。
type Codec<T> = {
  readonly read: (value: JsonValue, limits: JsonLimits) => { readonly ok: true; readonly value: T } | { readonly ok: false }
  readonly write: (value: T, limits: JsonLimits) => { readonly ok: true; readonly value: JsonValue } | { readonly ok: false }
}

type OperationContract<Body, Results extends OutcomeBodies> = {
  readonly identity: 'none' | 'login' | 'acting-tenant'
  readonly effect: 'read' | 'commit'
  readonly limit: 'small' | 'input'            // 消息体上限的名字，数值是部署配置
  readonly body: Codec<Body>
  readonly outcomes: Results                   // 每种可能的结果，对应它的响应体怎样读写
  readonly carriesCredential?: true            // 结果里带登录证明。通用通道不转发这种操作
  readonly countsAsAccess?: true               // 答成功时算一次成功的业务访问。管道在写出答复之后向身份报告
}

type OutcomeBodies = { readonly succeeded: Codec<unknown> } & { readonly [K in Exclude<Outcome, 'succeeded'>]?: K extends FixedOutcome ? true : Codec<unknown> }

type ObservationContract<Open, Frame, End extends string> = {
  readonly identity: 'none' | 'login' | 'acting-tenant'
  readonly open: Codec<Open>
  readonly frame: Codec<Frame>
  readonly ends: readonly End[]                // 这个观察自己的结束原因。中枢的五种不用列
  readonly countsAsAccess?: true               // 建立成功时算一次成功的业务访问
}

type ProtocolContract = {
  readonly name: string
  readonly major: number
  readonly operations: Readonly<Record<string, OperationContract<any, any>>>
  readonly observations: Readonly<Record<string, ObservationContract<any, any, any>>>
}

declare function defineProtocol<const P extends ProtocolContract>(protocol: P): P
```

要点：

- **贡献必须完整。** 类型要求契约里的每个操作都有处理函数。这个部署不提供的操作，由处理函数明确答 `stage-not-provided`，不靠缺省。
- **`identity` 决定管道走到哪一步。** 处理函数拿到的是已经签发好的主体。
- **`effect` 决定失败时怎么答。** 规则见[服务端](#5-服务端)判断次序的第 13 步。这条规则由操作契约的两栏推出，不用逐个操作手写。
- **管道会替领域答的结果，每个操作都有，不用逐个列。** `protocol-rejected` 与 `basis-unavailable` 每个操作都有。身份要求不是「不需要」的操作有 `denied`。提交类操作有 `unknown`。`defineProtocol` 的类型把它们加进结果集。现有的提交类操作里结果集没有 `unknown` 的有 17 个，搬进新契约时就有了。
- **编解码建在现有的规则引擎上。** 公开契约已有一套用普通数据写的字段规则和一个读写共用的通用引擎。`Codec` 由规则得到，类型也从规则推出。所以现有操作的规则表原样搬进各领域的协议契约，不重写字段规则，线上的消息体不变。
- **`countsAsAccess` 由协议的拥有者标。** 「什么算一次业务访问」是身份的规则，哪些操作算由每个协议定，接入只负责报告。搬的时候只有会话的 7 个操作和会话观察标上，和现在一样。
- **客户端的类型靠推导，不靠生成。** 契约是显式的 TypeScript 数据，`ClientOf<P>` 用类型运算得到每个操作的方法签名。不需要构建期生成代码。
- **观察的结束原因分两层。** 中枢的五种对每个观察都一样：观察者取消、被同一个编号的新观察替换、登录失效或被撤权、暂时不可得、帧队列超了上界。观察自己的那些写在契约的 `ends` 里。

### 4. 线上的形状

原则：契约定义一条逻辑消息，每种承载把它放进自己原生的外层。逻辑消息有六部分：协议名与主版本、操作名或观察名、消息编号、登录证明、行事租户、消息体。HTTP 自己有外层，就是路径和头。所以前五部分放进路径和头，请求体里只有消息体。

这样服务端在读内容之前，先知道调的是什么、调用者是谁。未知的操作、没有登录的调用，不用读完消息体就能答复。消息体的上限可以按操作定。日志、指标、限流、代理不用解析 JSON 就知道在调什么。

| 部分 | 位置 |
| --- | --- |
| 协议、主版本、操作或观察的名字 | 路径：`/api/<协议名>/v<主版本>/<名字>` |
| 登录证明 | 请求头 `Authorization: Bearer <登录证明>` |
| 行事租户 | 请求头 `Omne-Acting-Tenant` |
| 消息编号 | 请求头 `Omne-Message-Id`。响应头回写同一个值 |
| 消息体 | 请求体。就是操作的消息体本身，没有外层 |
| 答复 | 响应体：`{"outcome": "<结果>", "body": {…}}` |

状态码沿用[现有的对应表](../../packages/access/public-contract/docs/http-binding.md#状态码映射)，一种结果一个状态码。

地址的三处写法和业界通行的做法一致：

- 以 `/api` 开头。它把接口和页面、静态文件分开。协议是运行中挂上来的，不留这个前缀，任何一个顶层路径都可能和将来的协议撞名。
- 版本写成 `v1`，放在协议名后面。每个协议有自己的版本。
- 协议名取领域的能力组名，不加后缀。挂在入口上的协议都是公开协议，后缀不带信息。跨几个领域的集成视图不属于任何一个领域，用它自己的名字，例如 `session-diagnostics`。

规则：

- 协议没挂着，或协议里没有这个名字，答 404，空正文，不读消息体。
- 所有操作和观察都用 POST。
- 业务结果只认响应体里的 `outcome`。同一种 `outcome` 总是同一个状态码、同样的头、同样形状的响应体。调用者不用状态码判断业务含义。
- 拒绝的响应一致。不论原因是登录无效、租户不符还是对象不存在，`denied` 的响应体逐字节相同，调用者推不出对象存不存在。
- 严格读取。多余的字段、重复的键一律拒绝。
- 读取类失败答 `basis-unavailable`，提交类失败答 `unknown`。结果未知不写成成功或失败。
- 不用 Cookie。浏览器不会自动带上登录证明。
- 所有响应不许缓存。

三条对每个协议都成立的规则：

- 管道只解释路径和请求头。消息体里的字段，包括目标租户，由领域的处理函数解释。
- 管道、传输和通用通道从不把消息体或响应体写进日志与诊断。所以契约里不需要「这个字段是秘密」的标记。
- `carriesCredential` 只标一个操作：登录的签发。只有它的响应里有登录证明。

**按操作写，不按资源和动词写。** 各领域对外的东西是命令和查询，例如「取消这一轮」「切换当前租户」「接受邀请」。它们不是对一种资源的增删改查。按资源和动词写的主要好处是中间节点可以缓存读取，而这里的读取都带身份、按租户隔离，一律不许缓存，这个好处用不上。

**流式的内容走观察。** 提交和观看是两件事。界面用一个操作提交输入，服务端立刻答复「收到了」。界面另外开着一个观察，服务端把状态变化和回复的增量一帧一帧推过来。观察也是一次 POST，响应是 SSE。观察有自己的地址，服务端从路径就知道这是一个观察。客户端发给服务端的一切都走操作，所以不需要双向的连接。

**观察的两种送法。** 契约里，一个观察是一条逻辑流。线路上有两种送法，用同一个地址，走同一条管道。

| 送法 | 怎么走 | 谁用 |
| --- | --- | --- |
| 独占 | 一次 POST 建立观察，这次请求的响应就是 SSE | 脚本、命令行、第三方。桌面应用由主进程代连。走 HTTP/2 的浏览器也直接用它 |
| 共用 | 客户端先开一条共用的事件流。之后建立观察时，在请求头里写明把帧送到那条流上。这次 POST 的响应是普通的确认，帧带着观察的编号从共用流出来 | 网页外壳。它一律用这一种，不看连接是哪个版本的 HTTP |

要有共用这一种的理由：浏览器只在 TLS 上用 HTTP/2。本机的入口不提供 TLS 时，浏览器只能用 HTTP/1.1，同一来源一般只允许六条连接，所有标签页合起来算。本机的网页不以 TLS 为前提，因为公共的证书机构不给本机地址发证书，自己签的证书要装进每台设备的信任库。

送法的规则：

- 每个观察的建立都走完整的管道，带自己的登录和租户。共用流不替任何观察做身份判断。
- 共用流只属于开它的那个登录。别的登录不能往它上面挂观察。
- 共用流断了，上面的每个观察都算连接断开，各自按重附着规则续上。
- 领域的帧来源和界面模块都不知道帧走的是哪种送法。服务端由观察中枢决定从哪条连接写出，客户端由连接的传输决定。

本提案只做独占的送法。共用的送法在网页外壳之前做，不在本提案。

### 5. 服务端

#### 服务端的树

读图的三条约定：

- 每个节点是一个 Cordis 插件。服务端的插件叫「行」。
- 「提供」是插件放到树上的服务。「依赖」是插件声明要用的服务：依赖的服务都在，插件才存在；有一个不在了，插件连同它下面的一切一起收掉。
- 「每次调用现取」不是依赖。服务暂时不在时插件不收掉，只是这一次调用答 `basis-unavailable`。

```text
根
├─ 基础设施的各行（存储、遥测……）
│
├─ 身份与授权的各行
│     提供：主体签发
│
├─ 入口行
│     不含任何领域的代码
│     依赖：主体签发、遥测
│     提供：登记表
│     内部：承载绑定（HTTP、SSE）→ 管道 → 观察中枢
│     自己挂一份：内置协议 access/v1，里面有「可用性」这个观察
│
├─ 会话领域
│   ├─ 会话核心的各行
│   │     不知道有接入层
│   │     提供：会话服务
│   └─ 会话接入插件
│         依赖：登记表
│         挂上：会话的贡献，协议 session/v1
│         每次调用现取：会话服务
│
└─ 其余每个领域各一枝，形状相同
```

- 「挂上」绑定在接入插件自己的作用域上。接入插件卸载，它挂的协议自动撤下，不需要另写撤下的代码。
- 接入插件对领域服务是「每次调用现取」，不是「依赖」。所以领域服务重装配时协议不撤，只是那段时间的调用答 `basis-unavailable`。
- 装不装某个领域的接入插件，由应用装配决定。这就是「开不开放这个协议」的开关。
- 一次调用、一次订阅不是树上的节点。它们是入口里的运行时对象，寿命比任何插件都短。

#### 模块

| 模块 | 公开类型与签名 | 深度 | 变化的理由 |
| --- | --- | --- | --- |
| 登记表 | `mount(contribution)`；`enter(key, name)`；`subscribe(listener)` | 三个方法后面是表项、在途集合、修订号、撤下时的排空 | 挂上与撤下的规则变了 |
| 管道 | `handle(request): Promise<response>` | 一个方法后面是全部判断次序 | 判断次序变了 |
| 观察中枢 | `open(entered, principal, open, sink)` | 一个方法后面是预算、队列、心跳、结束 | 观察的资源规则变了 |
| HTTP 承载绑定 | `start()`、`stop()` | 路径、头、状态码、SSE 的全部细节 | 线路的形状变了 |
| 内置协议 | 一份普通的贡献 | 入口自己挂的 `access/v1` | 可用性的帧变了 |

聚合：

| 聚合 | 拥有的状态 | 谁发起变化 | 原子范围 |
| --- | --- | --- | --- |
| 登记表 | 表项、每个表项的在途调用集合、修订号 | 接入插件挂上与撤下；管道登记与注销在途调用 | 「查表项并登记成在途」是一步。「移除表项、给在途调用发中止、修订号加一、给订阅者排帧」是一步 |
| 观察中枢 | 每个在途观察的帧队列、心跳计时、结束标记 | 管道建立观察；帧来源推帧；登记表通知撤下；连接断开 | 「读可用性快照并登记订阅者」是一步 |

跨聚合一致性：登记表变化时同步通知观察中枢和可用性的帧来源，不经过异步的事件总线。这一步不能让出执行权，见[形式化](#15-形式化)的硬要求。

对领域暴露：协议契约的类型、贡献的类型、登记表的 `mount`。不暴露：管道的步骤、观察中枢的队列、承载的细节。

#### 登记表与贡献

```ts
// 领域的接入插件看到的全部。
interface AccessRegistry {
  // 绑定在调用者的 Cordis 作用域上，是这个作用域的一个效应。
  // 作用域卸载时，收回函数先同步撤下，再返回一个 Promise，它在这份贡献的在途工作都结束时完成。
  mount<P extends ProtocolContract>(contribution: AccessContribution<P>): void
}

type AccessContribution<P extends ProtocolContract> = {
  readonly protocol: P
  readonly operations: { readonly [K in keyof P['operations']]: OperationHandler<P['operations'][K]> }
  readonly observations: { readonly [K in keyof P['observations']]: FrameSource<P['observations'][K]> }
}

type OperationHandler<O> = (call: CallContext<O>, body: BodyOf<O>) => Promise<AnswerOf<O>>

type CallContext<O> = {
  readonly principal: PrincipalFor<O>   // 按 identity 一栏：none 时没有，login 时是登录身份，acting-tenant 时是代租户行事的主体
  readonly messageId: string
  readonly signal: AbortSignal
}

// 管道用的两个方法。领域看不到。
interface RegistryForPipeline {
  // 同步。查表项并把这次调用登记成在途，是一步。没挂着就返回 undefined。
  enter(key: ProtocolKey, name: string): Entered | undefined
  // 同步。读快照并登记订阅者，是一步。
  subscribe(listener: (change: AvailabilityChange) => void): { readonly revision: number; readonly protocols: readonly ProtocolKey[]; readonly unsubscribe: () => void }
}

type Entered = {
  readonly member: { readonly kind: 'operation'; readonly contract: OperationContract<any, any>; readonly handler: OperationHandler<any> }
                 | { readonly kind: 'observation'; readonly contract: ObservationContract<any, any>; readonly source: FrameSource<any> }
  readonly signal: AbortSignal
  readonly leave: () => void            // 答复写出之后调用。撤下靠它知道在途的结束了
}
```

帧来源的形状：

```ts
// 帧来源。先决定建不建立，建立之后吐帧，走完时给出结束原因。
// 原因是这个观察自己的那些，或中枢五种里帧来源自己也会碰到的两种：denied、unavailable。
// 观察的契约见「共同契约」一节。
type FrameSource<O> = (context: ObservationContext<O>, open: OpenOf<O>) => Promise<
  | { readonly outcome: 'succeeded'; readonly frames: AsyncGenerator<FrameOf<O>, EndOf<O>> }
  | { readonly outcome: 'denied' | 'invalid' | 'basis-unavailable' }
>
```

接入向身份与授权要的端口。接口归接入，实现归身份的适配：

```ts
interface AccessIdentity {
  identifyLogin(proof: string): Promise<LoginIdentity | IdentityFailure>
  actFor(login: LoginIdentity, tenant: string): Promise<Principal | IdentityFailure>
  // 一次成功的业务访问。管道不等它结束；它失败只记诊断，不改答复。
  reportAccess(login: LoginIdentity): Promise<void>
}
```

**撤下怎样做。** 撤下分两段：

- 同步的一段：移除表项，给这份贡献的在途调用发中止，把它的观察标成要结束，可用性推一帧。这一段在收回函数里一次做完，中间不让出执行权。
- 之后：在途的调用各自答复并调 `leave`，观察各自写出结束帧。最后一个结束时，这份贡献才算撤下完成，收回函数返回的 Promise 随之完成。

「撤下完成」是登记表自己的状态，由最后一个 `leave` 触发，不由谁来等。Cordis 会等收回函数返回的 Promise，所以同一个作用域在撤下完成之前不会重新挂上。设计的性质不以 Cordis 的这个行为为前提。现有的 `registerInCallerFiber` 要求撤销同步完成，不用它。

停机时先关入口、等在途的结束、再撤插件，这个次序归服务端应用的关闭流程，不靠卸载的次序。入口的停止沿用现有做法，等在途的请求结束。

**领域的接入插件怎么写。** 接入提供一个小函数，把「依赖登记表、挂上贡献、每次调用现取领域服务」这三件事包好：

```ts
declare function defineAccessPlugin<P extends ProtocolContract>(definition: {
  readonly name: string
  readonly protocol: P
  // 每次调用现取。取不到时返回 undefined，处理函数答 basis-unavailable。
  readonly handlers: (provide: <S>(key: ServiceKey<S>) => S | undefined) => Omit<AccessContribution<P>, 'protocol'>
}): Plugin
```

#### 管道与判断次序

一次调用的判断次序。前五步只看路径和头，是同步的。第 5 步登记成在途之后，才开始任何要等待的事。

1. 路径不是 `/api/<协议名>/v<主版本>/<名字>`，或带查询串：404，空正文。
2. 方法不是 POST：405。
3. `Host` 头不合规：421。
4. `Content-Type` 头不合规：415。
5. 调 `enter`。返回空就是协议没挂着，或协议里没有这个名字：404，空正文。返回了就已经登记成在途。第 1 到 5 步之间不让出执行权。
6. 在途请求的预算超了：429，空正文。
7. 读 `Omne-Message-Id`。没有或格式不对：`protocol-rejected`。
8. 按 `identity` 一栏识别登录、核对行事租户、签发主体。失败按身份规则答。
9. 按这个操作的上限读消息体，严格解析，用契约的编解码读成类型。不合规：`protocol-rejected`。
10. 第 6 到 9 步之间收到了中止：答 `basis-unavailable`。处理函数还没开始，没有任何效果。
11. 把主体和消息体交给处理函数。
12. 处理函数返回了答复：核对结果在契约的结果集里，用契约的编解码写回。
13. 处理函数抛出，或在中止之后失败，或在中止之后过了宽限还没返回：读取类答 `basis-unavailable`，提交类答 `unknown`。
14. 写出答复之后调 `leave`。答复是成功、契约标了 `countsAsAccess` 的，随后向身份报告一次成功的业务访问，不等它结束。

处理函数自己知道「什么都没提交」的时候，直接返回 `basis-unavailable`，不要抛出。抛出的失败按第 13 步处理，因为管道不知道效果有没有发生。

第 13 步的宽限是部署配置。中止之后管道给处理函数这么长的时间收场，过了就不再等它，按同一条规则答。这样「每个在途调用都有确定的结局」由管道自己守住，不靠每个领域的处理函数都理会中止。

和现有三个位置相比，次序有两处是有意改的，都因为登录证明从消息体挪到了请求头：

- 现在先读消息体、再识别登录。新的次序先识别登录、再读消息体。同一个请求既没有登录、消息体又不合规时，现在答 `protocol-rejected`，以后按身份规则答。
- 现在部署不提供的操作在识别登录之前就答 `stage-not-provided`。新的次序里它由处理函数答，在识别登录之后。没有登录的人调一个不提供的操作，以后按身份规则答。

第 1 到 9 步与第 12 到 14 步归接入，所有协议共用。只有第 11 步归领域。

#### 观察中枢

观察中枢对每个协议的观察都一样。它管：

- 每个登录和整个实例的观察数上限。
- 帧队列的字节上限，超了就结束，由客户端重新建立。可用性是唯一的例外：它的帧来源由入口自己提供，看得到自己的队列，积压超了就丢掉积压、改发一帧快照，所以它走不到「超了就结束」这一步。
- 心跳。
- 每一轮复核登录还有效；登录被撤销时结束。
- 同一个编号重新建立时替换旧的。
- 协议撤下、停机、连接断开时结束。
- 写结束帧。原因是中枢的五种加上这个观察自己的那些。
- 建立成功、契约标了 `countsAsAccess` 的，向身份报告一次成功的业务访问。

入口里现有的两段代码是中枢的起点：登记观察的那一段（先占名额后附着、两个上限、同编号替换、每轮复核登录、按登录结束）和写流的那一段（串行的写队列与心跳）。它们不认识任何领域，搬过来不重写。要加的是三样：挂帧来源的入口、帧队列的字节上限、协议撤下时结束。现有的「取消观察」操作和它的保留时间删掉，理由见下一段。

**取消一个观察归观察中枢，不是任何协议的操作。** 独占的送法下，客户端中止这次请求就是取消。中枢随即结束这个观察，原因是 `observer-cancelled`，并让帧来源收场：帧来源在收场时退掉它的订阅、停掉计时。共用的送法做出来时，连接是几个观察共用的，不能靠断开来取消其中一个，那时在 `access/v1` 里加一个「结束观察」的操作，它触发的是同一条路径。

#### 内置协议与可用性

可用性回答一个问题：这个部署现在挂着哪些协议。它是登记表的投影，和调用者是谁无关。

- **状态：** 一个集合，每一项是协议名加主版本；再加一个只增不减的修订号。所有订阅者看到的是同一个集合。
- **帧有两种：** 快照带修订号和整个集合。变化带修订号、新增的项和移除的项。
- 事件与结果的全化表见[状态与操作](#13-状态与操作)。

**不需要登录就能订阅。** 两个理由：

- 登录本身是某个协议里的操作。客户端要先知道这个协议开着，才能登录。
- 协议挂没挂着不是秘密。调一个没挂着的协议得到 404，任何人都能试出来。

`access/v1` 是起点。它随入口一直在，客户端可以把它当作固定的。

**它不回答「允不允许」。** 「这个租户能不能用某个领域」是许可，不是存在。许可归领域和授权，在每次调用时回答。界面要按许可显示或隐藏，由领域的界面模块读领域自己的读口。分开的理由：

- 它们是两个事实，有两个拥有者。存在归服务端装配，许可归领域和授权。
- 按登录和租户给不同的可用性，每个订阅者要有一份自己的视图，变化的来源从一个变成两个，接入层还要去订阅治理的变化。分开之后，可用性只是一个集合加一次广播。

以后要让界面模块能声明自己依赖某项许可，许可可以做成授权领域的一个观察，客户端同样把它映射成树上的服务。那是另一个协议的事，用的是同一套机制。

**性能。** 查登记表与广播可用性不加全局锁、不串行化无关调用：登记表的读不加锁，广播按订阅者各自排队。

### 6. 客户端

#### 客户端核心

客户端核心是纯成员，只依赖共同契约。脚本、测试、第三方集成直接用它，自己处理「协议不在」的情况。

```ts
// 传输负责带上身份。客户端核心看不到登录证明。
interface Transport {
  call(request: {
    readonly protocol: ProtocolKey; readonly operation: string
    readonly messageId: string; readonly body: JsonValue; readonly signal?: AbortSignal
  }): Promise<
    | { readonly kind: 'answered'; readonly outcome: string; readonly body: JsonValue }
    | { readonly kind: 'not-sent' }          // 字节没有发出
    | { readonly kind: 'uncertain' }         // 字节可能已经发出，没有可信的答复
  >
  observe(request: {
    readonly protocol: ProtocolKey; readonly observation: string
    readonly messageId: string; readonly open: JsonValue; readonly signal: AbortSignal
  }): AsyncIterable<JsonValue>
}

declare function createClient<P extends ProtocolContract>(protocol: P, transport: Transport): ClientOf<P>

type ClientOf<P extends ProtocolContract> = {
  readonly [K in keyof P['operations']]: (body: BodyOf<P['operations'][K]>, options?: { readonly signal?: AbortSignal })
    => Promise<AnswerOf<P['operations'][K]> | { readonly outcome: 'unavailable' } | { readonly outcome: 'uncertain' }>
} & {
  readonly observe: { readonly [K in keyof P['observations']]: (open: OpenOf<P['observations'][K]>, options: { readonly signal: AbortSignal })
    => AsyncIterable<FrameOf<P['observations'][K]>> }
}
```

本地多出的两种结果：

| 结果 | 什么时候 |
| --- | --- |
| `unavailable` | 字节没有发出：协议客户端已经收回，或连接没有接上 |
| `uncertain` | 字节可能已经发出，没有可信的答复；或答复读不懂。客户端核心不自动重发 |

传输有三种实现：

| 实现 | 用在哪 | 身份从哪来 |
| --- | --- | --- |
| HTTP 传输 | 命令行；桌面应用的主进程；以后的网页 | 构造时给一个凭据来源 |
| 进程间传输 | 桌面应用的页面 | 不带。主进程替它带 |
| 进程内传输 | 测试 | 测试给 |

#### 客户端装配

客户端装配是 Cordis 成员，只比客户端核心多依赖 Cordis。应用用这一层。

```ts
// 连接。树上的服务名是 connection。
interface Connection {
  readonly transport: Transport
  readonly availability: {
    current(): ReadonlySet<ProtocolKey>
    subscribe(listener: (open: ReadonlySet<ProtocolKey>) => void): () => void
  }
  readonly login: {
    state(): 'signed-out' | 'signing-in' | 'signed-in' | 'signing-out'
    subscribe(listener: (state: LoginState) => void): () => void
  }
}

declare function connectionPlugin(options: { readonly transport: Transport; readonly login: LoginStateSource }): Plugin
declare function defineProtocolClient<P extends ProtocolContract>(protocol: P): Plugin
// 协议开放期间，树上有服务 `protocol:<名字>/v<主版本>`，值是 ClientOf<P>。
```

对客户端暴露：协议契约的类型、`createClient`、传输的接口、连接与协议客户端两个 Cordis 服务。

连接是一个聚合。它拥有可用性的修订号与集合、登录状态的只读视图。可用性的帧与登录状态的通知发起变化。应用一帧是一步。

连接订阅可用性的规则：

- 一接上就订阅 `access/v1` 的可用性观察，拿到快照。
- 收到变化帧时核对修订号。基础对不上就不应用，重新订阅拿快照。
- 观察断了就按退避重连。重连期间协议客户端不收回，调用得到 `unavailable`。
- 重连拿到新快照，按差异提供或收回协议客户端。

协议客户端收回时，先把它标成已收回，再调 Cordis 的收回函数。标记之后它的方法一律答 `unavailable`。Cordis 收回服务的次序是：

1. 收回服务的那一刻，服务立刻不可见。
2. 依赖它的插件随后卸载，是异步的。
3. 收回函数返回一个可以等待的对象。等它完成时，依赖的插件都已经卸载。

中间有一小段时间，界面模块还在，服务已经没了。「标记之后方法答 `unavailable`」这条规则盖住这一段。

#### 客户端的树

桌面、网页、终端界面、命令行各有一棵，结构相同，只有外壳不同。

```text
根
├─ 外壳
│     提供：插入位置
│     不认识任何领域
│
├─ 连接
│     提供：连接（传输、登录状态）
│     一连上就订阅服务端的「可用性」观察，记着现在开放着哪些协议
│
├─ 会话
│   ├─ 会话的协议客户端
│   │     依赖：连接
│   │     提供：服务 protocol:session/v1。只在可用性里有 session/v1 的时候提供
│   └─ 会话的界面模块（会话列表、对话页）
│         依赖：protocol:session/v1、插入位置
│
└─ 其余每个领域的协议客户端与界面模块各一枝，形状相同

树外：客户端核心（纯函数）
      给它一份协议契约和一个传输，得到一组方法。
      协议客户端内部用的就是它。
```

- 协议客户端与界面模块在应用装配时就装在树上，但不一定激活。服务端没开放某个协议，对应的服务不出现，依赖它的界面模块就不存在。代码里没有「如果有某领域就怎样」的判断。
- 换登录，树上的协议客户端不变，因为可用性和调用者无关。变的是数据：界面模块按新的身份重新读。

**两棵树怎么接上。** 两棵树不共用任何 Cordis 对象。它们之间只有线上的契约，两边导入的是同一份协议契约成员。

```text
装上一个领域
  [服务端] 接入插件装上 → 登记表多一行 → 「可用性」推一帧
     ══ 线 ══
  [客户端] 连接收到 → 协议客户端的服务出现 → 界面模块加载

一次调用
  [客户端] 界面模块 → 协议客户端的方法 → 连接的传输
     ══ 线 ══  POST /api/session/v1/list-sessions
  [服务端] 承载绑定 → 管道（查登记表）→ 处理函数 → 现取领域服务 → 答复原路写回

卸下一个领域
  [服务端] 接入插件卸载 → 登记表少一行 → 「可用性」推一帧
     ══ 线 ══
  [客户端] 连接收到 → 协议客户端的服务立刻不可见 → 界面模块随后卸载
```

客户端没装某个协议的协议客户端时，可用性里出现这个协议什么都不发生，只记一条诊断。

#### 外壳与界面模块

插入位置的契约归能力组 `frontend`。最小的插入位置只有三个：

| 插入位置 | 种类 | 谁往里放 |
| --- | --- | --- |
| 登录门 | 只放一个 | 身份的界面模块。未登录时外壳只显示它 |
| 页面 | 一列。每项有标识、路径、标题、组件，可选的导航项 | 会话的对话页、资产的设置页 |
| 侧栏区 | 一列。每项有标识、次序、组件 | 会话的会话列表 |

往插入位置里放东西绑定在界面模块的作用域上。模块卸载，它放的东西自动撤掉。

共用界面件：各领域界面共用的基础组件、主题、多语言的装配、流式 Markdown 的包装。它先做到四部分用得到的插入位置和组件，不做完整的插入位置框架。

### 7. 协议怎样划分

#### 协议与拥有者

| 协议 | 拥有者 | 操作 |
| --- | --- | --- |
| `access/v1` | 接入（内置） | 可用性这个观察 |
| `identity/v1` | 身份与授权 | 注册、登录的签发与撤销、更换凭据、本人的登录与成员资格的查询、租户的读取与切换、组织、邀请、隶属、准入、授权表达。共 34 个 |
| `assets/v1` | 资产与规则 | 设置的四个：列出、查看、设置、清除 |
| `session/v1` | 会话与工作 | 建会话与认回、发输入与认回、读历史、取消一轮、停一次调用、列出会话；一个观察 |
| `session-diagnostics/v1` | 会话一侧的集成成员。它读会话、Agent、模型、工具四个领域的读口 | 读会话诊断 |
| `human-intervention/v1` | 人工介入 | 列出卡片、读一张卡、提交答复、认回一次提交。没有观察 |

协议名取领域的能力组名，集成视图用它自己的名字。「治理」这个协议不再存在。每个操作的消息体、结果集、业务规则原样带过来，不重新设计。按[共同契约](#3-共同契约)的规则，提交类操作的结果集补上 `unknown`。

#### 操作怎样分进去

契约里每个操作的三栏，从现有规定机械地得到：

| 栏 | 怎样得到 |
| --- | --- |
| 身份要求 | 现在禁止带登录证明的是「不需要」。现在要登录证明、禁止带行事租户的是「登录」。两样都要的是「行事租户」 |
| 只读或提交 | 名字以「查询」「读」「列出」开头的，以及准入判断，是只读。其余是提交 |
| 消息体上限 | 「发输入」和人工介入的「提交答复」用大的那一档。其余用小的那一档 |
| 算不算业务访问 | 会话位置现在报告的 7 个操作和会话观察标上。其余不标 |

#### 和现有操作的几处不同

- **不进新契约的操作。** 有四个操作对任何调用都答「本阶段不提供」：停用主体、恢复主体、终结主体、介质丢失后重开。它们没有任何实现，不进 `identity/v1`。以后要做时在同一个主版本里加操作，不破坏已有的客户端。
- **不要健康检查。** 它的用途是「服务在不在、是哪个版本」。`access/v1` 的可用性已经回答了这两件事。
- **取消观察不是会话的操作。** 它归观察中枢，对每个协议的观察都一样，见[服务端](#观察中枢)。
- **登录的签发一定返回登录的编号。** 退出时要用它撤销自己这份登录。
- **17 个提交类的身份操作多了 `unknown` 这个结果。** 它们现在出错时答一个没有内容的 500。命令行要认这个新结果。
- **识别登录先于读消息体。** 两处可见的次序变化见[管道与判断次序](#管道与判断次序)。
- **派生标识用的文本不改。** 会话标识、输入标识、人工介入的提交身份是哈希派生的，哈希的输入里有 `session-public/1`、`hitl-public/1` 开头的文本；会话契约里操作身份族的名字也是这种文本，并且存进了日志。它们是标识族的名字，不是线上的协议名，只是当初取了同一个字面量。搬代码时原样保留，并用测试钉住派生的结果。改了它们，同一个消息编号重送会得到另一个会话，已有会话的认回查不到原来的操作。
- **会话的定义名映射搬到会话一侧。** 它的服务定义现在放在入口成员里，随会话的接入插件搬走。
- **消息体上限从按路径改成按操作。** 会话与人工介入里用小的那一档的操作，上限比现在低。搬的时候逐个核它们的消息体够不够。

部署不提供的操作照旧答「本阶段不提供」，例如更换凭据。协议挂着，个别操作不提供，这两件事不矛盾：可用性的粒度是协议。

#### 目标租户放在消息体里

会话的操作里，只有「建会话」用行事租户。其余的操作在消息体里带一个目标租户，规则是「目标租户的账号必须等于登录的账号」。这是会话与身份两个领域的规定，本提案不改它。

管道只管请求头里的东西：登录和行事租户。消息体里的目标租户由领域的接入插件核对，它向身份要「为这个登录、这个目标租户签发主体」的服务。所以身份要求只有三种，不为它加第四种。人工介入的四个操作同样带目标租户，身份要求是「登录」。

#### 带目标租户的操作，主体由谁签发

主体只由应用装配登记的具名持有者签发，签发与关系核对的规则归身份。主体有两种，领域的接入插件按「自己在什么时刻核对资格」选一种。接入不替领域选。

| 主体 | 特点 | 谁用 |
| --- | --- | --- |
| 随登录的主体 | 每次登录都不同 | 每次调用都重核资格的领域，例如会话 |
| 稳定的入口主体 | 同一个租户每次登录都得到同一个主体引用 | 在对象创建时固定受众的领域，例如人工介入的读者与答复者 |

人工介入的接入插件另带两样，都从现在的入口搬过来，规则不变：

- 提交身份由目标租户和答复编号确定性地派生。换一份登录原样再送，认回的是同一次提交。
- 人工介入查询卡片时要用的卡片池所在处的引用是部署配置，客户端不填。

#### 架构页原有七条规则的去留

[系统分层](../architecture/layers-and-dependencies.md#领域能力的公开位置)原有七条「领域能力怎样对外」的规则。四条保留，三条改，另加三条。

| 原规则 | 去留 | 本提案里是什么 |
| --- | --- | --- |
| 一个领域协议一个位置 | 含义保留，名字和地址改 | 一个领域一个协议。名字是 `<协议名>/v<主版本>` |
| 含义与形状分开 | 改 | 领域拥有操作的含义，也拥有自己协议的契约。共同部分归接入。入口不认识任何领域，不再是组合承担者 |
| 先识别登录，再由具名持有者签发行事主体 | 保留 | 管道识别登录。主体的两种来源由领域的接入插件选 |
| 拒绝一致 | 保留 | 不变式 I-13 |
| 跨位置只传引用 | 保留 | 一个协议不承载另一个领域的语义 |
| 列表与读取是领域的查询投影 | 保留 | 结果带来源、快照与完整度 |
| 每个位置一个 SDK 客户端 | 改 | 客户端核心从契约得到客户端，不为每个协议手写一个 |
| 新增 | | 挂上与撤下随插件（I-4、I-5） |
| 新增 | | 有贡献不等于开放（I-15） |
| 新增 | | 可用性只说协议挂没挂着（I-6） |

### 8. 会话新增的三样

会话与工作的业务规则不变。变的只有三件：列出会话、会话观察真的发帧、读历史按标注给出内容。

另有一处小改：「建会话」的定义名可以不给。不给时用部署配置里标为默认的那个定义。部署没有标默认的，答 `invalid`。界面不让用户填定义名。现在定义名是必填的，部署配置里也没有「默认」这个标记。这处改的是 `session/v1` 的消息体和定义名的解析，随「接入插件」那一程做，不在「列出会话」那一程。

#### 列出会话

```ts
// session/v1 的操作 list-sessions。身份要求：登录。只读。小的那一档。
type ListSessionsBody = {
  readonly tenant: string                    // 目标租户
  readonly cursor: string | null             // 上一页的 next 原文。第一页给 null
  readonly limit?: number                    // 不给就用部署的默认值。超过部署的上界答 invalid
  readonly includeArchived?: boolean         // 不给就是不含已归档的
}
type ListSessionsSucceeded = {
  readonly sessions: readonly {
    readonly session: string
    readonly createdAt: string | null        // UTC 时刻。null：这个会话建在系统开始记提交时刻之前
    readonly lastActivityAt: string | null   // 同上
    readonly lifecycle: 'initializing' | 'dormant' | 'active' | 'frozen' | 'archived'
    readonly title: string | null            // 最早一条带文字的用户消息的开头。还没有时是 null
  }[]
  readonly next: string | null               // null 表示读完了
  readonly completeness: 'complete' | 'partial'  // partial：这一页读到了行数的上界，可能还有没扫到的
}
// 结果集：succeeded、denied、invalid、basis-unavailable。
```

- 次序是最近活动的在前。「活动」只算三种提交：建会话、受理一条输入、一轮结束。没有时刻的会话排在有时刻的后面，它们之间按会话标识排。
- 标题取最早一条带文字的用户消息里第一段文字的开头，至多 80 个字符，空白压成一个空格。第一条输入的第一块可能是图片或文件，所以规则说的是「带文字的」。它只写一次，之后不变。改标题是以后的产品功能，不在本提案。
- 列表是查询投影，不是全部事实。结果带完整度。
- 读的资格：登录的人按租户成员放行，不看租户角色；工作主体拒绝。会话契约的访问操作表加「列出会话」一项，服务端应用的授权政策表加一行。

**先要有的事实：提交的时刻。** 现在系统里没有。会话日志的条目、提交的回执、存储的每张表都不带时刻。所以创建时刻和最近活动时刻不是「缺一份投影」，是缺一个事实。

会话契约的事件目录已经规定「提交时间记在批次上」，只是没有实现。本提案照这条规定做最小的一份：

- 每次提交记一行：提交序号与时刻。这一行是事实，归提交。列表项的两个时刻从它派生。
- 时刻取自会话自己的时钟端口。时钟在系统分层里是一项横向能力，但没有公共的时钟成员：会话、Agent、模型、工具、身份、日历各在自己的契约里声明时钟端口。提交是会话的事实，所以用会话的时钟。存储里现有的那个时钟只给游标算过期用，不是业务时间的来源，不用它。
- 时钟答「不可用」时，提交照常成立，这一行的时刻为空。提交不因为读不到时间而失败，也不改用本机墙钟顶替。
- 存储在提交时取一次读数，随提交的事实交给在事务里运行的参加者。参加者自己仍然不用时间函数。时钟怎样交到存储手里，由存储成员的规格定。
- 这一程之前的提交没有这一行，以后也补不出来。那些会话的两个时刻是空的。

这一条让「列出会话」这一程碰每一次提交都走的路径，比原先估的大。每次提交多一次时钟读数和一行写入，这一程的第一个切片先量它的代价。

**会话列表项的仓储设计。** 列表项是每个会话一行的派生数据：创建时刻、最近活动时刻、生命周期、标题。它不是新的概念。它不是对会话内容的概括，不调用模型。接入层没有自己的存储。

列表项是一份投影，按会话契约对投影的要求声明五样：

| 要声明的 | 列表项的答案 |
| --- | --- |
| 来源 | 这个会话的日志，加上每次提交的时刻 |
| 计算规则 | 创建时刻取建会话那次提交的时刻；最近活动时刻取最近一次「活动」的提交的时刻；标题取最早一条带文字的用户消息；生命周期取每次提交归约出的值 |
| 覆盖到的提交位置 | 它和引起变化的那一批条目在同一个事务里写，所以总是覆盖到最新的修订号 |
| 计算版本 | 一个整数，写在列表项上。计算规则变了就加一 |
| 失效条件 | 列表项不存在，或它的计算版本不是当前版本 |

生命周期不是单独写入的事实。它是会话契约规定的、由事实归约得出的值，每次提交末尾算一次，存在会话的快照里。列表项取的就是这个值。

接口归会话契约，实现归会话的 SQL 存储：

```ts
// 会话契约里的读取面。资格：目标租户的主体。
interface SessionDirectory<P> {
  list(input: Readonly<{
    principal: P
    tenant: TenantId
    after: string | null
    limit: number
    includeArchived: boolean
  }>): Reply<Readonly<{ items: readonly SessionListItem[]; next: string | null; completeness: 'complete' | 'partial' }>>
}
```

| 问 | 答 |
| --- | --- |
| 写入路径 | 列表项和引起它变化的那一批条目在同一个提交事务里写，不多一次往返。会话的参加者写一批条目时本来就顺带写十来张派生表，材料是前一份快照、新的快照和这一批条目；列表项照这个做法加一张。创建时刻只在建会话时写。标题在那一行的标题还空着、这一批里有带文字的用户消息时写。最近活动时刻在建会话、受理输入、一轮结束时写。生命周期每次提交按新快照里的值写。写入是幂等的：同一批重放得到同一个值 |
| 查询路径 | 一种查询：按租户，最近活动倒序，会话标识作第二排序键。按键集分页，游标是上一页最后一行的两个键，不用偏移量。需要一个索引：租户、最近活动时刻、会话标识。每页的行数有部署的上界，初值 50。没有全表扫描 |
| I/O 形态 | 读是一次带上界的索引范围扫描，整块返回，不流式。和提交之间不需要额外的隔离：读到稍旧的一页是可以接受的，列表本来就是投影 |
| 容量假设 | 单机部署，一个租户一年在一万个会话的量级。索引范围扫描的代价只和每页的行数有关，和会话总数无关。超过假设时先变慢的是「含已归档」的翻页，那时再给生命周期加进索引 |

三条约束：

- 列表项是一张新的派生表，带上面那个索引。现有每次提交都改的两处都放不下它：一处是严格模式的表，不能加列；另一处是一段 JSON 文本，排不了序。
- 这一程之前建的会话在迁移里同步回填：标题从日志取，生命周期从快照取，两个时刻留空。会话存储已有一次这样的回填，照它做。回填在迁移的事务里做完，期间这个租户的写要等；单机单用户的量级下可以接受，写进已知限制。回填之后列表总是全的。按标识打开一个会话不依赖列表项。
- 改会话的参加者会改变它的清单摘要，所以要换组合的版本号，并更新发行配置里对应的两行。任何两个同时改会话存储的分支，合入时都在这几处相撞。所以排程时不让两程同时改会话的存储。

#### 会话观察

会话观察由一个新的集成成员产出，它是 `observe-session` 的帧来源。这个成员认识会话契约和模型契约，两个领域互不认识。它用两头的读取面：

- 会话这头：读者的日志读取面。反向读「调用登记」得到最近一次主模型调用的引用，反向读「一轮开始、一轮结束」得到当前这一轮。提交之后有一个只含标识、修订号和条目种类的通知。读工作快照的那个面只给协调者和维护者，观察者不用它。
- 模型这头：按引用取当前的流，先给快照再给增量。

这些读取面的形状不变。但有四处现状和上面的用法对不上，由「会话观察」那一程补齐：

| 要成立的 | 现在 | 怎样补 |
| --- | --- | --- |
| 模型的公共流在正式装配里可用 | 没有安装 | 服务端应用的模型宿主行打开观察，发布两个读取面。它们的消费者从「入口」改成「会话观察」 |
| 登录的人能取当前的流、能订阅 | 服务端应用的模型授权表只放行工作主体与宿主主体 | 授权表给登录的主体放行这两个动作。理由见下 |
| 每一次提交都发通知 | 只有经会话命令入口的提交发。一轮当中的调用登记、助手消息、工具消息不发 | 经存储事务端口的提交在完成之后也发同一个事件 |
| 从一条调用登记读出种类、引用、用途 | 日志里有两种存法，规格只写了一种 | 会话契约给一个读取函数，会话观察和会话诊断共用。规格补上两种存法 |

**为什么带着登录的人的主体去读模型的流。** 观察会话的是登录的人，「谁在做」的答案就是他。会话观察不拿自己的身份替他读：那样模型不知道真正在读的是谁，也违反「身份每次调用显式带上」。允不允许归模型的授权表。登录的人已经能读自己会话的历史，也已经能查一次模型调用的状态；看正在生成的那段回复是同一类读取。跨租户仍由模型的读取面在第一步挡住。

**为什么要补通知。** 工具执行期间没有模型流，会话观察按退避刷新，间隔最长 30 秒。工具的结果和下一次模型调用的登记都是一轮当中的提交。它们不发通知，界面就要等到下一次刷新才知道。通知的本意是「这个会话有新的提交」，对每条提交路径都成立；会话契约只规定通知可以丢，没有规定某些提交不发。现状是少了发出点。

```ts
// session/v1 的观察 observe-session。身份要求：登录。
type ObserveSessionOpen = { readonly tenant: string; readonly session: string }
type ObserveSessionFrame =
  | { readonly kind: 'state'
      readonly run: string | null            // 新增。当前这一轮的编号，没有进行中的一轮时是 null
      readonly revision: string              // 新增。会话日志到这一刻的修订号
      readonly phase: string | null          // 模型调用的阶段
      readonly target: { readonly projection: 'model-output-v1' } | null }
  | { readonly kind: 'snapshot'; readonly projection: 'model-output-v1'; readonly value: JsonValue }
  | { readonly kind: 'delta'; readonly projection: 'model-output-v1'; readonly value: JsonValue }
  | { readonly kind: 'gap'; readonly reason: 'buffer' | 'source-history' }
  | { readonly kind: 'refreshing' }
// 这个观察自己的结束原因只有一个：refresh-exhausted。
```

职责怎样分：

| 归观察中枢（接入，对每个协议的观察都一样） | 归会话观察（只认识会话与模型） |
| --- | --- |
| 每个登录和整个实例的观察数上限 | 建立时以观察者的身份读一次日志，核对资格 |
| 帧队列的字节上限，超了就结束 | 定位、取当前的流、观察、翻译成帧 |
| 心跳 | 没有新内容时按退避刷新，到上界时结束 |
| 每一轮复核登录还有效；登录被撤销时结束 | 状态帧里的四个字段 |
| 同一个编号重新建立时替换旧的 | |
| 协议撤下、停机、连接断开时结束 | |
| 写结束帧。原因是中枢的五种加上这个观察自己的那些 | |

刷新的策略、退避与上界沿用[服务端接入规格的刷新策略](../../packages/access/server-entry/SPEC.md#刷新策略)，随成员搬到会话观察的规格里。它加一个事件和三条规则：

- **事件「这个会话有新的提交」。** 通知里的条目种类和「读历史给出的八种、调用登记」有交集时，重新定位，四个字段有变化就发一帧状态。没有交集的通知不理会。
- **通知只是叫醒，不是事实的来源。** 漏掉的通知由原有的按间隔刷新补上。
- **通知不能被吞掉。** 定位正在进行时来的通知要记下，这次定位结束之后立刻再定位一次。正在进行的那次定位读到的可能是通知之前的日志。
- **重新定位只读新条目。** 第一次定位反向读。之后的重新定位从上一次读到的位置往后读，不重读整段日志。会话的读取面已有这个读法。

加进通知之后每个状态怎样答，见[会话观察的定位与流](#会话观察的定位与流)的两张全化表。

「现在有没有一轮在进行」的判法写进会话契约的规格：最近一条「一轮开始」之后没有同编号的「一轮结束」，就是在进行。

快照帧与增量帧的值是一棵 JSON 值。模型契约的投影函数现在给出的是 JSON 文本，它另给出「得到值」的一步。

帧来源收场时退掉它对提交通知和模型流的订阅、停掉计时。

**会话观察只管自己的订阅。** 会话与 Agent 对模型和工具的调用，本质上是一次远程调用：发起的一方只管自己这边的生命周期，被调用的一方管它自己的。会话观察按同一个道理做：

- 它是两个服务的客户端：会话的日志读取面，模型的公共流。它手里只有自己的读取和订阅。
- 观察者断开、观察结束、换目标时，它收掉的只是自己的订阅。模型的那次调用继续还是停止，是模型的事，会话观察不管，也不替谁去取消。
- 模型的流保留多久、什么时候退役，是模型的事。会话观察不要求模型为它多留。取不到流就按刷新的规则处理，已提交的内容由读历史给。
- 它不从会话或 Agent 的运行实例里拿流。会话日志里记的是那次调用的引用，凭引用向模型要流。发起调用的一方就算不在了，流照样看得到。

**会话观察的领域面与对象。** 下面是设计形状，不是代码；名字在写成员规格时按统一语言核一遍。

```ts
// 会话观察对外的全部。只用会话与模型的词，不导入接入组的任何成员。
// 接入插件把它接成 observe-session 的帧来源：open 的三种结果对应建立的三种结果，帧一对一。
interface SessionObservation<P> {
  open(input: Readonly<{
    access: SessionAccess<P>            // 观察者自己的主体、租户、会话。读日志和读模型的流都用它
    signal: AbortSignal                 // 观察者不再持有这次观察。中止之后会话观察收掉自己的一切
  }>): Promise<
    | Readonly<{ kind: 'opened'; frames: AsyncGenerator<SessionObservationFrame, SessionObservationEnd> }>
    | Readonly<{ kind: 'denied' }>      // 读日志被拒。和「会话不存在」看不出区别
    | Readonly<{ kind: 'unavailable' }>>
}

type SessionObservationFrame =
  | Readonly<{ kind: 'state'; run: RunId | null; revision: SessionRevision; phase: string | null
               target: Readonly<{ projection: 'model-output-v1' }> | null }>
  | Readonly<{ kind: 'snapshot'; projection: 'model-output-v1'; value: JsonValue }>
  | Readonly<{ kind: 'delta'; projection: 'model-output-v1'; value: JsonValue }>
  | Readonly<{ kind: 'gap'; reason: 'buffer' | 'source-history' }>
  | Readonly<{ kind: 'refreshing' }>

// 帧序列走完时的原因。被中止时序列直接结束，不给原因：那是观察者自己的事。
type SessionObservationEnd = 'refresh-exhausted' | 'denied' | 'unavailable'

// 会话观察向外要的东西。接口归会话观察，实现是会话与模型已有读取面的薄适配。
type SessionObservationPorts<P> = Readonly<{
  history: Pick<SessionHistory<P>, 'begin' | 'next' | 'since'>     // 会话的日志读取面，「读者」这一类
  streams: ModelStreamReferences<P>                                // 按调用的引用取当前的流
  observer: ModelStreamObservation<P>                              // 订阅一条流
  // 订阅「这个会话有新的提交」。返回退订的函数。只带条目种类，不带内容。
  notices: (target: Readonly<{ tenant: TenantId; session: SessionId }>, onCommit: (kinds: readonly string[]) => void) => () => void
  wait: (milliseconds: number, signal: AbortSignal) => Promise<'elapsed' | 'cancelled'>   // 计时。测试给假的
  policy: ObservationRefreshPolicy                                 // 间隔、退避、次数、总时长、取流的等待上界
  locatePages: number
}>
```

它里面有五个对象，各有一个变化的理由：

| 对象 | 它独占的 | 为什么单独 |
| --- | --- | --- |
| 一次观察 | 帧的出口与次序；「第一帧是状态」；中止时收场 | 只有它发帧，所以帧的次序只有一处要守 |
| 定位 | 日志读到哪了；当前这一轮；最近一次主调用的引用；日志的修订号。纯读 | 「看哪一次调用」只由日志决定，和流无关 |
| 流的订阅 | 对一个目标的订阅和它的中止信号；换目标之后丢掉迟到的旧帧 | 「那次调用的流现在怎样」只由模型决定，和日志无关 |
| 刷新的预算 | 间隔、退避、连续没有新内容的次数、累计的等待时长 | 它是策略，换部署就换值，不该散在状态机里 |
| 帧的翻译 | 模型的帧到会话观察的帧；状态帧只在四个字段有变化时发 | 对外表示的那张对应表只有一处实现 |

会话与模型各补的三个小东西，都是纯函数或已有事件，形状如下：

```ts
// 会话契约。从一条调用登记的载荷读出种类、引用、用途，两种存法都认。不是调用登记时返回 null。
type CallRegistrationView = Readonly<{
  kind: 'model' | 'tool'
  reference: string | null                                          // 还没关联上的工具登记没有引用
  purpose: 'main' | 'compaction' | 'extension' | 'action'
}>
declare function readCallRegistration(payload: JsonValue): CallRegistrationView | null

// 模型契约。现有的编码函数给出 JSON 文本；这一个给出值，文本是它之后的一步。
declare function projectModelOutputV1(input: ModelOutputV1Input): Outcome<JsonValue, ModelOutputV1Failure>

// 提交通知沿用现有的事件，名字与参数不变：租户、会话、修订号、出处、条目种类。
// 变的只有一条：经存储事务端口的提交完成之后也派发它。
```

| 界面要知道的 | 从哪来 |
| --- | --- |
| 正在生成的那一段回复 | 快照和增量 |
| 这一轮开始了、结束了；取消这一轮要用的编号 | 状态帧的 `run` |
| 日志里有新的已提交内容，例如工具的结果、压缩记录、最终的回复 | 状态帧的 `revision` 变大了。界面拿它和自己读到的位置比，落后就读历史 |
| 已提交的内容本身 | 读历史。历史是权威，流只是进行中的投影 |

#### 读历史给出什么

「给不给」和「画不画」是两件事，各有一个拥有者。

- **给不给，由内容自己的标记定。** 消息的每一块都带一个标注，写明这一块给不给人、给不给模型。标注由产出这一块的一方写。读历史按「给人」这一位过滤，和组装模型请求时按「给模型」那一位过滤是同一个做法。服务端没有别的过滤：没有按种类的清单，也没有部署配置。
- **画不画，由界面定。** 服务端给了的内容，界面默认显示、折叠还是收起来，是界面的事。

读历史给出的种类写死在 `session/v1` 的契约里，共八种：

| 种类 | 界面上是什么 |
| --- | --- |
| 用户消息、助手消息 | 对话正文 |
| 工具消息 | 工具调用的结果 |
| 内部工具消息、系统提醒 | 系统放进对话里的内容。产出方把它们标成了给人 |
| 压缩记录 | 「前面的对话已压缩」的标记 |
| 一轮开始、一轮结束 | 一轮的边界，以及它是完成、失败还是被取消 |

规则：

- 标成不给人的块不出现在历史页里。这样标的有三种：供应商交回的加密推理状态、没生成完的工具调用、给模型看的结果卸载提示。去掉块之后，消息上的推理回放描述按消息规格的投影规则重写。
- 一条消息滤完一块不剩时，它不出现在历史页里。
- 日志里其余的事实不属于对话，归 `session-diagnostics/v1`。例如尝试的开始与释放、调用的执行事实、输入的路由。
- 部署或组织以后要对人隐藏某类内容，做法是让产出方把它标成不给人，不在接入层加清单。

### 9. 设置

租户在自己这一层为持有的资产配置声明允许的设置项，这是资产与规则的产品规则。设置项的含义、类型与合法值、默认、清除后果和生效时点由拥有它的资产声明。设置领域的目录在声明之上补四样：当前生效的值、它来自哪一层、有没有被上层锁定、不能操作时的原因。`assets/v1` 的四个操作把这份目录按行事租户这一层公开出来。

| | 能看到的 | 设置 | 清除 |
| --- | --- | --- | --- |
| 普通项 | 声明、生效的值与它的来源层、本层配的值、锁定 | 写本层的值 | 本层不再提供这个值，重新按层序求值。它不等于关闭，也不等于恢复默认 |
| 秘密项 | 声明、本层与部署层的状态：未配置、可用、已撤销、读不出。值永远读不回来 | 写本层的秘密 | 清掉本层的秘密 |

规则：

- 普通项的值不合声明时答 `invalid`。被上层锁定时答 `not-writable`，响应体里的原因是「被上层锁定」。两种都不写入。
- 目录说这一层不能配某一项时，答「不可配」并带目录给的原因。界面把这一行显示成只读并写出原因。只读是逐项的事实，由领域给出，不是对普通项的一律规定。
- 普通项的新值在声明的生效时点起作用。界面在这一行写明它什么时候生效。
- 写入可能已经提交但没有认回时答 `unknown`，调用者先查看这一项再决定是否重试。这一条对两类项相同。

普通项的写入带预期的修订号：

- 「列出」和「查看」给出每一项的修订号。「设置」和「清除」把它原样带回。修订号对不上时答 `conflict`，不写入，界面重新读这一项。
- 公开的一次「设置」在领域里是准备加提交两步。两步对调用者是一个操作，一个消息编号。
- 锁定和解锁不公开。

普通项那一行的字段取自设置领域的目录条目：声明（类型与约束、默认、展示信息）、求值结果（生效的值、来源、被谁锁定）、可操作的授权、修订号。

所以设置界面的每一行有：标题、现在的值或状态、来源、「设置」和「清除」两个动作。

现有的普通项都是权限项。权限项的求值规则归权限，和一般的普通项不同，所以对它另有五条：

- 「生效的值」是权限求出来的那一档，不是最具体的那个值。读的时候另外读组织层，给出共同的允许集合，以及有没有被上层主动禁止。它是租户这一层往上的结果，不含某个会话自己的挑选。
- 这一层只能写挑选，不能写允许集合。本层已有的允许集合原样保留。
- 要写的挑选是允许某个操作的值，而它不在共同的允许集合里，或上层已经主动禁止：答 `not-writable`，原因是越过上界。「拒绝」这一类确定的限制不依赖外层来源，外层暂时读不出也能写。
- 执行时每次工具调用都按当时各层的配值重新求值，这是安全边界。写入时的核对是为了不把不会生效的值写进去，并告诉使用者原因。
- 新值对之后的每一次工具调用生效。已经启动的调用不受影响。

只有登录的人能改设置。在会话里运行的 agent 用的是会话里的主体，它不能读写设置：能调用一个工具，不等于有权配置它。

资产一侧提供一个领域面，把列出、查看、设置、清除四个动作用领域的词做出来。服务端应用的正式装配里，租户层的写入要有真实的计划和在提交事务里重读当前事实的参与者，这一段是新写的，不是把现成的服务接上。

下面几小节是这个领域面的设计。它不碰线上的形状，也不碰界面。

#### 设置的概念

| 概念 | 意思 | 例子 |
| --- | --- | --- |
| 设置项 | 一份资产声明的、可以配值的一项。声明给出名称、用途、类型与合法值、默认、清除后果、何时生效 | Shell 工具的「调用权限」 |
| 持有 | 一个范围把一份资产加进自己的使用范围。有持有才能给它配值。部署提供的官方资产，每个合法租户都算已经持有 | 租户持有官方的 Shell 工具 |
| 层 | 配值的来源。普通设置按默认、组织、租户、工作区、会话的次序求值。权限的来源是默认、组织、租户、会话 | 租户这一层 |
| 本层的配值 | 这一层自己写的值。没写就是「未设置」，它和写了 `false` 不是一回事 | 租户把 Shell 的调用权限挑成「自动」 |
| 生效的值 | 各层的配值按规则求出来、实际会被用的那个值 | 组织只允许「拒绝」和「询问」时，租户挑了「自动」，生效的是「询问」 |
| 普通项、秘密项 | 普通项的值可以读回来。秘密项的值只能写，读不回来，只能看状态 | 调用权限；模型供应商的密钥 |
| 权限项 | 普通项里的一种。它控制一个具体操作允不允许做，值是分档的 | 调用权限：拒绝、询问、自动 |
| 挑选 | 一层给权限项写的、没有加锁的值。它是一个选择，不是边界 | 租户挑「自动」 |
| 允许集合 | 一层给权限项加的锁：只许这几档。各层的允许集合取交集，是下面各层的上界 | 组织锁成只许「拒绝」「询问」 |
| 主动禁止 | 一层把权限项配成「不允许做这个操作」。更具体的层不能把它改成允许 | 租户把 Shell 挑成「拒绝」，这个租户的会话里就不能再放开 |
| 修订号 | 一项配值当前的版本。写的时候带上读到的那个，对不上就不写 | 两个窗口同时改同一项，后提交的那个被拒绝 |
| 使用边界 | 一个值从什么时候起被用上。由声明这一项的功能定 | 调用权限在下一次工具调用时生效，正在进行的那一次不变 |

#### 设置里每件事归谁

| 事实或决定 | 拥有者 |
| --- | --- |
| 一项设置的名称、用途、类型与合法值、默认、清除后果、何时生效 | 声明它的资产或功能 |
| 一个租户持有哪些资产 | 资产 |
| 各层的配值存在哪、按什么次序求值、锁怎样生效、修订号 | 设置 |
| 权限项怎样求值：允许集合取交集、挑选向外取第一个界内的、都在界外取最近的一档、主动禁止不可覆盖 | 权限 |
| 一个要写的权限值合不合上界 | 权限的配值写入判断 |
| 谁是「本人」，有没有配值的资格 | 身份与授权 |
| 一次具体的工具调用最后允不允许 | 授权的动作准入。它消费权限给的依据 |
| 值从什么时候起被用上 | 声明这一项的功能给出使用边界；装配与会话在那个边界上取新值 |
| 这些事实在线上长什么样 | `assets/v1` 的协议契约 |
| 界面怎样显示 | 设置的界面模块 |

#### 设置的操作与答复

四个操作：列出、查看一项、设置一项、清除一项。秘密项沿现有的规则，下面是普通项的全化表。

「列出」「查看」：

| 情形 | 答复 |
| --- | --- |
| 主体是这个租户的本人，来源都读得到 | 成功 |
| 主体没有读的资格，或目标不是自己的租户 | 拒绝。和「不存在」看不出区别 |
| 「查看」的资产没有持有，或项不在声明里 | 不可见 |
| 资产引用对上了多份持有，或一份持有有多个在用的版本 | 冲突 |
| 来源、资格或存储有一样读不出 | 依据不可用。不给一份残缺的当完整的 |

「设置」：

| 情形 | 答复 | 写不写 |
| --- | --- | --- |
| 本人，持有，项存在，值合声明，修订号对得上，不越界，没被锁 | 成功，带新的修订号 | 写 |
| 值和现在本层的配值相同 | 无变化 | 不写 |
| 没有配值的资格 | 拒绝 | 不写 |
| 主体不是登录的人，例如会话里干活的主体 | 拒绝 | 不写 |
| 资产没有持有，或项不在声明里 | 不可见 | 不写 |
| 值不合声明的类型与合法值 | 无效 | 不写 |
| 权限项：要写的值里带了允许集合 | 无效。这一层只收挑选 | 不写 |
| 修订号对不上，或声明在读之后变过 | 冲突。界面重新读这一项 | 不写 |
| 被上层锁定 | 不可写，原因是被锁定 | 不写 |
| 权限项：要写的挑选是允许某个操作的值，而它不在共同的允许集合里，或上层已经主动禁止 | 不可写，原因是越过上界 | 不写 |
| 权限项：要写的是「不允许」这一类确定的限制，而某个外层来源暂时读不出 | 成功。限制不依赖外层来源来成立 | 写 |
| 其余的值，而某个适用的来源读不出 | 依据不可用 | 不写 |
| 写已经交出去，没有等到确认 | 未知。调用者按原操作认回，不重新发一次新的 | 可能已经写了 |

「清除」：

| 情形 | 答复 | 写不写 |
| --- | --- | --- |
| 本层有配值，资格与修订号都对 | 成功。本层不再提供这个值，重新按来源求值 | 写 |
| 本层本来就没有配值 | 无变化 | 不写 |
| 其余情形 | 同「设置」的对应行 | 同上 |

读不出来和没有是两回事：来源、资格或存储不可得时答「依据不可用」，不显示成「未设置」，不显示成默认值。读的是租户这一层的管理视图；一次运行实际选入的设置是另一个视图，本提案不做。

#### 一次写入要守的条件

一次写入成立，下面几样必须在同一个提交边界上同时成立。准备的时候成立、提交的时候不成立了，就不写。

1. 主体是这个租户的本人，是登录的人，现在仍然有配值的资格。
2. 这个租户现在仍然持有这份资产。
3. 项在现在的声明里，声明的版本没有变。
4. 值合声明。
5. 修订号是现在的。
6. 没有被上层锁定；权限项另外要在现在的上界之内。
7. 这次写入有一个原操作的身份。确认丢了，按这个身份认回，不产生第二次写入。

写的只是租户这一层。它不写组织层，不写官方层，不写会话层。写入确认之前要落到持久存储：确认成功的配值在进程崩溃、系统崩溃或断电之后读得回来。

生效：

- 写入成立之后，本层的配值立刻能查到，生效的值按新的配值重新求。
- 值在声明给出的使用边界上被用上，不追溯。已经发出去的调用不变，已经记下的调用输入不改写。
- 设置的值或锁变了，设置的维护方把这个范围的采用变更计数加一，并通知使用方。使用方在自己的使用边界上据此取新值。
- 「挑成自动」只表示这一档不需要人批准，不表示调用已经成功，也不解除执行环境自己的限制。「挑成拒绝」是主动禁止，会话模式、一次性的批准、人工介入的答复都不能把它放开。

#### 设置的不变式

| 编号 | 性质 | 违反时的后果 |
| --- | --- | --- |
| S-1 | 写入只落在主体本人的租户这一层 | 一个租户改了别人的、组织的或官方的配值 |
| S-2 | 越过上界的允许值写不进去；上层的主动禁止，下层放不开 | 组织的限制被租户绕过 |
| S-3 | 显示的生效值等于实际执行时用的值。权限项显示的是权限求出来的那一档 | 使用者以为放开了，其实没有；或以为拦着，其实放开了 |
| S-4 | 读不出来不显示成未设置或默认值；结果未知不显示成成功或失败 | 使用者照着错的状态做决定 |
| S-5 | 修订号对不上不写。过期的编辑盖不掉别人已经确认的内容 | 两个窗口互相覆盖 |
| S-6 | 同一次写入只成立一次。确认丢失之后按原操作认回 | 重复写入，或把「没收到答复」当成「没写」 |
| S-7 | 确认成功的配值崩溃之后读得回来 | 设置丢失，权限回到别的档位而没人知道 |
| S-8 | 新值只作用于使用边界之后的使用，不改写已经发生的 | 正在进行的调用半路换了权限 |
| S-9 | 清除只撤回本层的覆盖 | 清除被当成关闭或设成 `false` |
| S-10 | 读写面不返回别的租户的配值，不返回秘密项的值 | 泄露 |
| S-11 | 只有登录的人能读写设置。会话里的主体与系统主体被拒绝 | agent 给自己把工具权限改成自动 |
| S-12 | 这一层只写挑选，不写允许集合。本层已有的允许集合原样保留 | 租户给下层加了锁，而没有地方能看到和解开它 |

#### 设置读写面的契约

读写面在资产一侧，只用领域的词，不导入接入组的任何成员。接入插件把它映射成 `assets/v1` 的四个操作，一个操作对一个方法。下面是设计形状，不是代码；名字在写成员规格时按统一语言核一遍。

```ts
// P 是调用者的主体。读写面自己核它是不是这个租户的登录主体。
interface TenantSettings<P> {
  list(input: Readonly<{
    principal: P
    tenant: TenantId
    asset?: AssetRef                 // 给了就只列这一份资产的项
    after: string | null             // 上一页的 next 原文
    limit: number
  }>): Promise<
    | Readonly<{ kind: 'listed'; items: readonly SettingView[]; next: string | null; completeness: 'complete' | 'partial' }>
    | ReadRefusal>

  describe(input: Readonly<{ principal: P; tenant: TenantId; asset: AssetRef; item: string }>): Promise<
    | Readonly<{ kind: 'described'; item: SettingView }>
    | ReadRefusal>

  set(input: Readonly<{
    principal: P
    tenant: TenantId
    asset: AssetRef
    item: string
    operation: OperationId           // 调用者给的原操作身份。原样再送，认回的是同一次写入
    expectedRevision: string         // 从 list 或 describe 读到的修订号
    value: SettingInput
  }>): Promise<WriteOutcome>

  clear(input: Readonly<{
    principal: P; tenant: TenantId; asset: AssetRef; item: string
    operation: OperationId; expectedRevision: string
  }>): Promise<WriteOutcome>
}

type SettingInput =
  | Readonly<{ kind: 'ordinary'; value: JsonValue }>
  | Readonly<{ kind: 'permission'; pick: string }>          // 只有挑选。没有允许集合
  | Readonly<{ kind: 'secret'; secret: SecretText }>

type SettingView = Readonly<{
  asset: AssetRef
  item: string
  revision: string
  declaration: Readonly<{
    title: string
    purpose: string
    appliesAt: string                                        // 何时生效，给人读的
    clearEffect: string                                      // 清除的后果，给人读的
  }>
}> & (
  | Readonly<{
      kind: 'ordinary'
      valueSchema: JsonValue
      default: Presence
      own: Presence                                          // 本层的配值：未设置，或一个值
      effective: Readonly<{ value: Presence; source: 'default' | 'organization' | 'tenant' | null }>
      lockedBy: 'organization' | null
      editable: Editable
    }>
  | Readonly<{
      kind: 'permission'
      choices: readonly Readonly<{ value: string; label: string; description: string; permitsOperation: boolean }>[]
      default: string
      own: string | null                                     // 本层的挑选
      // 租户这一层往上求出来的结果。不含会话自己的挑选。
      effective:
        | Readonly<{ kind: 'value'; value: string; source: 'default' | 'organization' | 'tenant' }>
        | Readonly<{ kind: 'prohibited'; by: 'organization' | 'tenant' }>   // 被主动禁止
        | Readonly<{ kind: 'empty-bound' }>                                 // 共同的允许集合是空的
      bound: readonly string[] | null                        // 共同的允许集合。null 表示没有任何一层加锁
      editable: Editable
    }>
  | Readonly<{
      kind: 'secret'
      own: SecretState                                       // 未配置、可用、已撤销、读不出
      official: SecretState
      editable: Editable
    }>
)

type Presence = Readonly<{ kind: 'unset' }> | Readonly<{ kind: 'set'; value: JsonValue }>
type Editable =
  | Readonly<{ kind: 'yes' }>
  | Readonly<{ kind: 'no'; reason: 'locked' | 'not-a-source' | 'prohibited-above' }>

type ReadRefusal =
  | Readonly<{ kind: 'denied' }>           // 没有资格，或目标不是自己的租户。和「不存在」看不出区别
  | Readonly<{ kind: 'not-visible' }>      // 资产没有持有，或项不在声明里
  | Readonly<{ kind: 'conflict' }>         // 资产引用对上了多份持有或多个在用的版本
  | Readonly<{ kind: 'unavailable' }>      // 来源、资格或存储有一样读不出

type WriteOutcome =
  | Readonly<{ kind: 'written'; revision: string }>
  | Readonly<{ kind: 'no-change' }>
  | Readonly<{ kind: 'denied' }>
  | Readonly<{ kind: 'not-visible' }>
  | Readonly<{ kind: 'invalid' }>
  | Readonly<{ kind: 'conflict' }>         // 修订号对不上，或声明在读之后变过
  | Readonly<{ kind: 'not-writable'; reason: 'locked' | 'out-of-bound' | 'prohibited-above' | 'not-a-source' }>
  | Readonly<{ kind: 'unavailable' }>      // 确定没有写
  | Readonly<{ kind: 'unknown' }>          // 可能已经写了。用同一个 operation 原样再送来认回
```

契约上的八条规定：

1. 每个方法先核主体，再做别的。主体不是这个租户的登录主体，一律答 `denied`，不读任何东西。
2. `denied` 不带原因。别的拒绝可以带上面列出的原因，不带内部的标识和别的租户的任何信息。
3. `set` 和 `clear` 对同一个 `operation` 只成立一次。同一个 `operation` 加同样的输入再送，答原来的结果，这就是认回，不另设认回的方法。同一个 `operation` 加不同的输入，答 `conflict`。
4. `unavailable` 表示确定没有写。`unknown` 表示可能已经写了。两者不能混。
5. `list` 的一页来自同一份快照。来源不全时 `completeness` 是 `partial`，不把残缺的一页当完整的。
6. 权限项的 `effective` 由权限求出，材料是默认、组织、租户三层当时的配值。读写面自己不实现求值规则。
7. 秘密项的值只进不出。`SettingView` 里没有秘密的值，任何拒绝和诊断里也没有。
8. 读写面不缓存配值。每次读都读当时的。

对象怎样分：

| 对象 | 它独占的 | 为什么单独 |
| --- | --- | --- |
| 读写面 `TenantSettings` | 核主体、把四个动作编排成读与写 | 它是调用者看到的全部。接口小，后面的东西都藏在它里面 |
| 设置的目录读取 | 声明、各层的配值、修订号 | 设置领域已有。读写面用它，不重做 |
| 权限的求值与写入判断 | 权限项的生效值、要写的挑选合不合上界 | 规则归权限。读写面把三层的配值交给它，不自己算 |
| 租户层的写入计划与提交参与者 | 准备时算出要写什么；提交时在事务里重读「一次写入要守的条件」并决定写不写 | 条件必须在提交的那一刻成立，所以重读在事务里 |

读写面的结果和 `assets/v1` 的结果一一对应：

| 读写面的结果 | `assets/v1` 的结果 |
| --- | --- |
| `listed`、`described`、`written` | `succeeded` |
| `no-change` | `no-change` |
| `denied` | `denied` |
| `not-visible` | `not-visible` |
| `invalid` | `invalid` |
| `conflict` | `conflict` |
| `not-writable` | `not-writable`，响应体带原因 |
| `unavailable` | `basis-unavailable` |
| `unknown` | `unknown` |

### 10. 桌面应用

它是一个 Electron 桌面应用。页面经进程间通信找主进程，主进程连服务端。页面这一层按「拿出来就能当网页跑」来写，以后做网页版只换传输。

#### 进程怎样分

客户端的 Cordis 树放在页面里。一个领域的协议客户端与界面模块因此在同一个进程里。主进程只做连接里可信的那一半。

| 部分 | 职责 |
| --- | --- |
| 主进程 | 窗口与加固；凭据库；登录会话；HTTP 传输；通用通道的服务端一侧 |
| 预加载脚本 | 只暴露一个对象。页面拿不到原始的进程间通信接口 |
| 页面 | 外壳；客户端的树；装配文件里列出的各领域界面模块 |
| 共享 | 通用通道的类型。纯类型，不依赖 Electron |

页面里的装配文件是唯一列出领域的地方：它导入身份、会话、资产三个界面模块并装上树。外壳的其他代码不导入任何领域。去掉其中一个模块，外壳照常编译和运行。

窗口的加固：上下文隔离、关闭 Node 集成、沙箱、拒绝弹窗与外部导航、四个权限入口全拒。内容安全策略只许应用自己的脚本。

#### 登录会话

登录会话是主进程里的聚合。它独占登录证明。发起变化的是页面的登录与退出请求、身份协议的答复。状态有四个：未登录、登录中、已登录、退出中。登录证明只在「已登录」和「退出中」两个状态下存在。全化表见[状态与操作](#13-状态与操作)。

凭据库：登录证明用操作系统提供的加密保存。系统不提供时，存成只有当前用户可读的文件。

**客户端怎样知道登录已失效。** 登录失效时，任何带登录的调用都答 `denied`，和「没有权限」看不出区别。这是有意的。区分的办法不用新增操作：

- `identity/v1` 的「读当前租户」只要求登录。它答 `denied` 只有一个原因：登录无效。
- 主进程的登录会话在任何一次带登录的调用答 `denied` 之后调它一次。它也答 `denied`，就是登录会话全化表里「身份协议明确答复登录已失效」那个事件。
- 同一时刻至多一次这样的探测在途。探测的结果不缓存：下一次 `denied` 再探一次。

#### 页面与主进程之间的通道

页面拿到的只有「发一次调用、开一个观察、订阅可用性、登录、退出、读登录状态」。页面拿不到登录证明，也拿不到原始的进程间通信接口。

| 通道 | 方向 | 内容 |
| --- | --- | --- |
| 调用 | 页面到主进程 | 协议、操作、消息编号、消息体。答复是传输的三种结果之一 |
| 开观察 | 页面到主进程 | 协议、观察、消息编号、建立点。答复是观察的编号 |
| 关观察 | 页面到主进程 | 观察的编号 |
| 观察的帧 | 主进程到页面 | 观察的编号、一帧，或「结束」 |
| 登录 | 页面到主进程 | 凭据。答复只有结果，没有登录证明 |
| 退出 | 页面到主进程 | 无。答复只有结果 |
| 登录状态 | 主进程到页面 | 四个状态之一 |
| 外观偏好 | 双向 | 主题、语言 |

守住「登录证明不进页面」的三道：

1. 「调用」通道拒绝转发契约里标了 `carriesCredential` 的操作。这类操作只有登录会话自己调。
2. 「登录」和「退出」通道的答复类型里没有登录证明这个字段。
3. 页面与预加载脚本不许导入主进程里连服务端的代码，由 lint 规则守。

桌面应用在本机只存登录证明和外观偏好。

#### 四部分界面

**登录**

- 第一次使用时注册并登录。之后打开时已登录就直接进入，没登录就先登录。
- 可以退出登录。
- 登录证明只留在主进程里，不进页面。输入的密码不进日志，不进错误信息。「登录」通道的请求交出之后，页面的表单清空。

**会话管理**

- 列出自己的会话，新的在前。列表来自服务端的 `list-sessions`。
- 每个会话显示创建时间、最近活动时间、第一条输入的开头。
- 选一个进入，看到它已有的历史，接着聊。
- 新建一个会话。

**设置**

- 设置协议里的每一项，都能看到它的说明和当前值，能改，能清除。行的形状见[设置](#9-设置)。
- 改完之后，显示的是服务端答复的结果。

**对话**

1. 输入一条消息，发出去。
2. 回复流式出现。文字逐步变长。会话里的其他内容按种类渲染，例如推理、工具调用和它的结果、这一轮的状态。
3. 回复还在出的时候，可以接着打字，可以取消这一轮。
4. 来回多轮。

会话内容的种类与渲染。界面要渲染的东西来自三处，每处的种类是封闭的。不认识的种类显示一个看得见的占位，写明种类名。

| 来源 | 种类 | 渲染 |
| --- | --- | --- |
| 历史的条目 | 用户消息、助手消息、工具消息、内部工具消息、系统提醒、压缩记录、一轮开始、一轮结束 | 前三种按消息的部件画。内部工具消息和系统提醒画成一行收起的标记，点开看内容。后三种画成一行标记 |
| 消息的部件 | 文字等内容块、推理、工具调用、没生成完的工具调用、解析不了的工具调用、工具结果 | 文字走流式 Markdown。推理和工具调用画成可以展开的卡片。工具调用和它的结果按调用编号配成一对。Ask 工具的调用画成问题卡，见下面「对话里的卡片」 |
| 进行中的流 | 模型输出投影的快照与增量 | 按同一套部件画，标出「正在生成」。这条助手消息提交之后，用历史里的那一条替换它 |

「流畅」指下面四件看得见的事。数值线等有了第一个能跑的版本之后量出来再定。

- 回复流出来的同时，打字马上显示，不丢字。
- 长回复不整屏闪烁。
- 窗口大小变了，内容重新排好。
- 会话很长时，滚动和输入不变慢。

四部分之外不做：多面板、其他领域的面板、切换租户的界面。

**对话里的卡片。** agent 用 Ask 工具向人提问时，人工介入出一张卡，这一轮等人答。桌面应用的第一版把这张卡渲染出来，不提供答卡。理由是现在的装配里只有 Ask 工具会出卡：两个 Agent 的权限模式都是跳过询问，也没有登记会拦下工具调用问人授权的拓展件，所以权限的「询问」不出卡。

- 一次 Ask 工具调用在对话里画成问题卡：每个问题的原文、它的选项、每个选项的标签与后果说明。内容取自这次工具调用的参数。
- 卡片的状态取自对话自己的内容：这次调用还没有结果、这一轮还在进行，是「等待答复」；有了结果，显示答复；这一轮结束而没有结果，是「已失效」。它不经人工介入的协议，所以界面不用为它另外查卡片。
- 等待答复时，卡上写明这一轮在等人，以及两条出路：在命令行里答复，或在桌面应用里取消这一轮。
- 归 I-20：Ask 的问题卡是会话内容的一种，必须渲染。

在桌面应用里答卡不在本提案。做的时候才需要人工介入的界面模块，以及怎样及时知道有新卡：人工介入的协议没有观察，新卡的提示归通知能力，通知还没有设计。

#### 主场景走一遍

用的人打开应用，登录，选一个旧会话，发一句话，看回复流出来，中途取消。

| 步 | 调用谁 | 状态怎样变 | 失败落到哪 |
| --- | --- | --- | --- |
| 打开应用 | 主进程读凭据库 | 登录会话：未登录，或已登录 | 读不到就是未登录 |
| 页面起来 | 连接订阅 `access/v1` 的可用性 | 树上出现三个协议客户端，三个界面模块加载 | 接不上：外壳显示「连不上服务」，按退避重连 |
| 登录 | 页面经「登录」通道交出凭据。主进程调 `identity/v1` 的登录签发 | 登录中，再到已登录。页面只得到「成功」 | 凭据不对：`uniform-auth-failure`，回未登录。结果未知：回未登录，如实显示未知 |
| 列出会话 | `session/v1` 的 `list-sessions` | 无 | `denied` 之后主进程探测一次登录是否失效 |
| 打开一个会话 | 读历史，反向第一页；建立观察 | 观察中枢多一个在途观察 | 观察数到上限：`basis-unavailable`，界面仍能读历史 |
| 发一句话 | `send-input` | 会话受理输入，开始一轮。提交通知叫醒会话观察，发一帧状态，`run` 有值 | 结果未知：`uncertain`。界面显示未知，用同一个受理编号调认回，不重发 |
| 回复流出来 | 快照，再是增量 | 界面按部件画 | 流断了：`refreshing`，重新观察同一个目标，拿新快照 |
| 取消 | `cancel-run`，带状态帧里的 `run` | 一轮结束。状态帧的 `run` 变回空，`revision` 变大。界面读历史补上已提交的内容 | 那一轮已经结束：答复里就是它的结局 |

失败语义的三条另走：

| 情形 | 走到哪 |
| --- | --- |
| 协议在调用途中被撤下 | 处理函数没开始：`basis-unavailable`。已开始的读取：`basis-unavailable`。已开始的提交：`unknown`。客户端树上的协议客户端被收回，界面模块卸载 |
| 领域的提供者暂时不在 | 协议还挂着。处理函数取不到领域服务，答 `basis-unavailable`。界面不消失 |
| 登录在服务端被撤销 | 在途的观察被中枢以「登录失效」结束。下一次调用答 `denied`，探测确认，登录会话回未登录，外壳只显示登录门 |

### 11. 实时媒体的通道

本节回答「以后要做打电话怎么办」。它只定位置和规则。**通道契约的具体形状、媒体格式、编解码的协商不在本提案**，等有实时需求时再设计。

线上走的数据有两类，性质相反：

| | 事实类 | 媒体类 |
| --- | --- | --- |
| 例子 | 提交输入、取消一轮、回复的文字 | 通话里的声音 |
| 单独一条丢了 | 不行，每条都要有着落 | 不要紧 |
| 晚到 | 仍然有用 | 没用，不如丢掉 |
| 断了之后 | 从上次的位置续上 | 不重放，接着往下 |
| 要不要逐条答复 | 要 | 不要 |

操作和观察是为事实类设计的。媒体类用第三种东西：通道。

做法是把管事的和传媒体的分开：

1. 开通道是一个普通操作。它走完整的管道，认登录、核租户。答复里给出通道的地址和一张票。
2. 媒体在通道上走。通道凭票建立。
3. 通话中的状态、转写的文字是事实，仍然走观察。
4. 关闭通道是一个操作，有确定的答复。

规则：

- 通道上只传媒体。命令和事实不走通道。
- 没有绕过管道的通道。每条通道都由一个操作开出来。
- 票短时有效，只能用一次，只对这一条通道有效。浏览器的 WebSocket 设不了 `Authorization` 头，票解决这个问题。
- 通道的寿命挂在它所属的协议下。协议撤下，通道关闭。
- 通道用什么技术是承载的事，契约不规定。本机上 WebSocket 够用。隔着公网的浏览器用 WebRTC 更合适，它在网络丢包时不会卡住。

它装得进本提案的结构：

- 通道也是「契约、承接者、寿命」三样。契约是媒体格式和方向，承接者是领域提供的媒体端点，寿命是一次通话。
- 协议契约里有操作和观察两类成员，到时加第三类 `channels`。这是纯增加，不用通道的协议不改。
- 观察中枢管理在途的观察，到时同样管理在途的通道：预算、协议撤下时关闭。

### 12. 外来的代码在哪运行、能碰什么、谁来决定

本节只写原则。**部署者自带插件的实现不在本提案**，它单独一程。

同一个问题在三处出现：网页要装上一个外来领域的界面模块；工作区带来循环拓展件、脚本这类可执行的内容；用户自己带来一套服务端插件。三处问的都是：一段别处来的代码，凭什么可以在这里运行。这件事只设计一次。

两条原则：

1. 允许装载不等于放开权限。一段代码能碰到什么，由它运行的位置和显式给它的能力决定，每次动作还要重新核对授权。知道代码是谁发布的、有人批准过它，都不扩大它能碰到的范围。
2. 决定让一段代码运行的人，必须管得着这段代码在那个位置上能碰到的一切。位置的边界越小，有资格决定的人越多。

由这两条得到一张表。服务端和客户端是同一个结构。

| 运行位置 | 代码能碰到什么 | 谁有资格决定 | 例子 |
| --- | --- | --- | --- |
| 进程外，经公开协议接入 | 只有它的登录被允许做的事 | 不需要对代码做决定，只要给它一个身份 | 第三方应用、外部服务、MCP 服务 |
| 执行环境里的命令 | 环境档位声明的边界，以及当次授权 | 租户。为会话选用工作区就是决定 | 工作区带来的命令型拓展件、脚本 |
| 服务端的受限执行域 | 显式给的能力，每次动作按主体重新核对 | 租户或工作区一级就够 | 受限的 JS 代码 |
| 服务端进程内的原生插件 | 整个进程，包括所有租户的数据 | 只有官方发行，或这个部署的部署者 | 各领域的行；部署者自己带来的一套 Cordis 插件 |
| 浏览器页面内 | 当前登录的全部权限 | 只有官方发行，或这个部署的部署者 | 各领域的界面模块 |
| 浏览器里隔离的框 | 桥上显式给的能力 | 租户或用户一级就够 | 第三方的界面 |
| 桌面、终端应用的进程内 | 用户的整台机器 | 只有官方发行，或这台机器的主人 | 外壳 |

三个推论：

- **用户自己带来一套 Cordis 插件，可以。** 条件是他是这个部署的部署者。本机部署上一台机器属于一个人，用户就是部署者。多租户的部署上，租户不是部署者，不能往进程里放原生插件，要走上面三行。
- **工作区的内容永远不能让宿主装载原生代码。** 工作区一级管不着整个进程。
- **进程外是门槛最低的一条路。** 对外开放的协议越全，外部系统越不需要往进程里放代码。

共用的机制沿用资产已有的概念，不造新词：

| 要回答的事 | 用哪个概念 |
| --- | --- |
| 这段代码是哪一份 | 资产版本。一次发布定下的内容，发布后不可变，带内容摘要 |
| 它归谁 | 来源层：官方、组织、租户、工作区。原生插件另有部署者 |
| 谁决定用它 | 采用。做决定的人要符合原则二 |
| 当时用的到底是什么 | 采用依据。它记下来源和内容摘要 |
| 内容变了怎么办 | 那是另一个资产版本。它在下一个采用点才生效，运行中的东西不静默换版 |
| 读它的自述会不会运行它 | 不会。清单是纯数据。读取不执行，读取成功不等于采用 |

所以不另设一种「信任记录」。采用就是决定，采用依据就是记录。资产版本的读取、内容摘要的核对、采用与采用依据的存取，各处都用资产与采用的同一套机制。

界面模块的代码怎样到达客户端：

1. 官方发行的领域，界面模块和外壳一起构建、一起发行。运行中不下载代码。动态的是激活，不是下载：模块一直在树上，协议开放了它才激活。本提案只用这一条。
2. 部署者带来的领域，界面模块和它的服务端插件属于同一个资产版本，由同一次采用决定。入口按内容摘要托管界面那部分的文件。客户端按摘要取文件，核对摘要，再装上客户端的树。它和「部署者自带插件」是同一件事，一起做。
3. 桌面和终端应用不在自己的进程里运行服务端下发的代码。部署者管不着用户的机器。这类应用要显示外来领域的界面，放进隔离的框里。
4. 租户或用户一级带来的界面，只能在隔离的框里运行。隔离的框和它的桥不在本提案。

### 13. 状态与操作

#### 服务端：登记表里的一个协议

在途调用和在途观察是另外的对象，各有自己的寿命，不算登记表的状态。

| 事件 | 协议未挂上 | 协议已挂上 |
| --- | --- | --- |
| 挂上同名同版本的协议 | 成功。可用性推一帧 | 拒绝，报装配错误。已挂的那份不动，不覆盖 |
| 撤下 | 不可达。撤下只随成功挂上的那个作用域发生 | 表项移除。它的在途调用收到中止信号。它的观察以 `ended(unavailable)` 结束。可用性推一帧 |
| 调用到达 | 404，空正文，不读消息体 | 进管道 |
| 建立观察 | 404，空正文 | 进管道。通过后交给观察中枢 |
| 在途调用完成 | 照常写回。表项撤了也写回 | 照常写回 |
| 在途调用在中止后失败 | 读取类答 `basis-unavailable`。提交类按判断次序第 13 步的 `effect` 规则答 | 同左 |

领域的提供者暂时不在，不等于协议撤下。重装配期间协议一直挂着，处理函数每次调用现取提供者，取不到答 `basis-unavailable`。

#### 客户端：树上的一个协议客户端

| 事件 | 服务未提供 | 服务已提供 |
| --- | --- | --- |
| 可用性说这个协议开放了，树上装了它的协议客户端插件 | 提供服务。依赖它的界面模块加载 | 不变 |
| 可用性说这个协议开放了，树上没装它的协议客户端插件 | 不变。记一条诊断 | 不可达 |
| 可用性说这个协议撤下了 | 不变 | 服务立刻不可见。依赖它的界面模块随后卸载。收回要等这些模块卸载完才算完成。在途调用按下一行处理。订阅句柄结束 |
| 在途调用遇到服务收回或连接断开 | 不可达 | 字节没发出的，本地答「不可用」。字节可能已发出的，本地答 `uncertain`。不自动重发 |
| 连接闪断 | 不变 | 不变。服务不收回。调用按上一行。观察按重附着规则续上 |
| 连接恢复，可用性给出新快照 | 按快照与本地的差异走第一行 | 按差异走第三行，或不变 |
| 换登录或换租户 | 不变 | 不变。可用性和调用者无关。此后的调用带新的身份，界面模块重新读数据 |

协议客户端插件由 `defineProtocolClient` 得到，应用装配时装在树上。外部代码手里留着的旧方法句柄，在服务收回之后再调用，一律本地拒绝。

#### 桌面应用主进程里的登录会话

状态四个：未登录、登录中、已登录、退出中。登录证明只在「已登录」和「退出中」存在。

| 事件 | 未登录 | 登录中 | 已登录 | 退出中 |
| --- | --- | --- | --- | --- |
| 应用启动，读本机保存的登录证明 | 读到就进「已登录」，读不到留在「未登录」 | 不可达 | 不可达 | 不可达 |
| 页面请求登录 | 进「登录中」，发出登录操作 | 拒绝：正在登录 | 拒绝：已经登录 | 拒绝：正在退出 |
| 登录的答复是成功 | 不可达 | 保存登录证明，进「已登录」。只告诉页面「登录成功」 | 不可达 | 不可达 |
| 登录的答复是其他结果，或结果未知 | 不可达 | 回「未登录」。把结果如实告诉页面，未知就说未知 | 不可达 | 不可达 |
| 页面请求退出 | 直接答「已经退出」 | 拒绝：正在登录 | 进「退出中」，发出注销操作 | 拒绝：正在退出 |
| 注销的答复是成功或无变化 | 不可达 | 不可达 | 不可达 | 删掉登录证明，进「未登录」 |
| 注销的答复是其他结果，或结果未知 | 不可达 | 不可达 | 不可达 | 仍然删掉本机的登录证明，进「未登录」。告诉页面：本机已退出，服务端是否已注销不确定 |
| 身份协议明确答复登录已失效 | 不变 | 不可达 | 删掉登录证明，进「未登录」，通知页面 | 删掉登录证明，进「未登录」 |
| 页面请求一次普通调用 | 不带登录证明发出。需要登录的操作由服务端拒绝 | 同左 | 带上登录证明发出 | 拒绝：正在退出 |

#### 会话观察的定位与流

[服务端接入规格的刷新策略](../../packages/access/server-entry/SPEC.md#刷新策略)画了六个状态。它们其实是两条独立的轴交叉出来的：

| | 定位：空闲 | 定位：进行中 |
| --- | --- | --- |
| 流：没有目标 | 「等待下一轮」 | 「定位」「查询 current」 |
| 流：观察中 | 「观察中」 | 原图没有这一格 |
| 流：等着重新观察同一个目标 | 「重新观察同一目标」 | 原图没有这一格 |

没有通知的时候，定位只在没有目标时才做，所以右下两格不会出现。加进「这个会话有新的提交」之后，流还在的时候也要定位，这两格就要有答案。所以按两条轴各写一张表，每一格只写一次。

**定位这条轴。** 一次定位是串行的一步：读日志得到修订号、当前这一轮、最近一次主调用的引用；现在没有目标，或主调用换了，再向模型取那次调用当前的流。有目标而且主调用没换，不问模型。另有一个标记「有新提交待看」。

| 事件 | 空闲 | 进行中 |
| --- | --- | --- |
| 建立成功 | 开始定位，反向读 | 不可达 |
| 刷新的间隔到期 | 开始定位，只读新条目 | 不可达：间隔只在空闲而且没有目标时计 |
| 通知，条目种类有交集 | 开始定位，只读新条目。正在等的间隔取消。不发 `refreshing`，不计一次尝试 | 立起标记 |
| 通知，条目种类没有交集 | 不理会 | 不理会 |
| 这次定位有了结果 | 不可达 | 按下一张表处理结果，回到空闲。标记立着：放下标记，立刻再开始一次定位，这优先于等间隔 |

定位的结果怎样处理，看流那条轴现在在哪：

| 结果 | 流：没有目标 | 流：观察中，或等着重新观察 |
| --- | --- | --- |
| 主调用是新的一次，模型给了它的流 | 发 `state`，再订阅、发 `snapshot`。预算归零 | 收掉对旧目标的订阅，之后到的旧帧丢掉。发 `state`，再订阅、发 `snapshot`。预算归零 |
| 主调用是新的一次，模型没给流 | 四个字段有变化就发 `state`，再发 `refreshing`。计一次尝试，开始等间隔 | 收掉对旧目标的订阅：它已经不是最近的主调用。发 `state`、`refreshing`。计一次尝试，开始等间隔 |
| 主调用没换，模型给了一条新的流 | 发 `state`，再订阅、发 `snapshot`。预算归零 | 不可达：有目标而且主调用没换时不问模型 |
| 主调用没换，模型没给新的流；或日志里还没有主调用 | 四个字段有变化就发 `state`。这次定位是间隔到期引起的，就发 `refreshing`、计一次尝试、按退避开始等下一档间隔；是通知引起的，不发 `refreshing`、不计尝试，按现在这一档间隔重新等 | 流不动。四个字段有变化就发 `state` |
| 读日志暂时不可得，翻页读满了还没找到，取流超时 | 当作没有新内容，同上一行 | 流不动。记一条诊断 |
| 读日志被拒 | 结束，原因 `denied` | 同左 |
| 模型拒绝，或答复引用无效 | 结束，原因按公开契约的对应表 | 同左 |

「模型没给流」包括：没有可看的目标、暂时不可得、还没受理这次调用、给的是同一条已经关闭的流。

**流这条轴。**

| 事件 | 没有目标 | 观察中 | 等着重新观察同一个目标 |
| --- | --- | --- | --- |
| 定位给出新目标 | 订阅，进「观察中」 | 换目标，见上表 | 换目标，原来的等待取消 |
| 模型交来快照 | 是迟到的旧帧，丢掉 | 发 `snapshot`。预算归零 | 是迟到的旧帧，丢掉 |
| 模型交来增量 | 丢掉 | 阶段变了先发 `state`，再发 `delta`。预算归零 | 丢掉 |
| 目标的流结束了：来源关闭、流已过期、生产者结束、缓冲以外的缺口、没给结束帧就断了 | 不可达 | 按对应表发 `gap`，再发 `refreshing`。进「没有目标」，计一次尝试，开始等间隔 | 不可达 |
| 订阅中断但目标还在：容量、暂时不可得、缓冲的缺口 | 不可达 | 按对应表发 `gap`，再发 `refreshing`。进「等着重新观察」，计一次尝试 | 不可达 |
| 模型撤了观察者的资格 | 不可达 | 结束，原因 `denied` | 不可达 |
| 间隔到期 | 归定位那条轴 | 不可达：观察中不计时 | 重新订阅同一个目标，进「观察中」 |
| 次数或累计时长用完 | 结束，原因 `refresh-exhausted` | 不可达：观察中不计 | 结束，原因 `refresh-exhausted` |

流这条轴要「开始等间隔」而定位正在进行时，不另起间隔：等这次定位的结果，按结果那张表处理。标记立起之后接着做的那一次定位，算通知引起的。

任何一格遇到中止，会话观察收掉日志的读取、流的订阅、通知的订阅和计时，帧序列结束。取消、替换、撤销登录、连接断开、协议撤下、帧队列超了上界，都由观察中枢判断，对会话观察来说只是中止。

三条要守的性质：

- **不丢唤醒。** 一条种类有交集的通知到达之后，总有一次在它之后才开始的定位。空闲时通知直接引起定位；进行中时通知立起标记，这次结束后再定位一次。通知在提交之后才发，所以那次定位读得到这次提交。
- **旧目标的帧不出现在新目标之后。** 换目标时先收掉旧订阅，之后到的旧帧丢掉。
- **第一帧是状态。** 建立之后的第一次定位不论结果如何，先发 `state` 或直接结束。

前两条和「不停在旧的调用上」由模型三检查，见[形式化](#15-形式化)。

### 15. 形式化

命中形式化触发的有七处。三处做了有限模型检查，四处不做模型。

| 触发 | 位置 | 处理 |
| --- | --- | --- |
| 生命周期与状态机；并发 | 服务端登记表里的一个协议，和它的在途调用、在途观察 | 模型一 |
| 跨域边界上的性质；并发 | 登记表、可用性、连接、客户端树上的协议客户端 | 模型二 |
| 生命周期与状态机 | 主进程里的登录会话 | 不做模型。状态只有四个，没有并发的写者，全化表已经写出每一格。「不把登录证明交给页面」是结构上的性质，靠边界的 lint 和测试守 |
| 较高的性能要求 | 查登记表、广播可用性 | 不做模型。要守的是不加全局锁、不串行化无关调用，结构上直接看得出来。没有数值目标 |
| 生命周期与状态机；并发 | 会话观察的定位与流：通知、间隔、读日志、模型的流以任何顺序交错 | 模型三。这个状态机从来没有实现过 |
| 数据生命周期；并发 | 租户层设置的一次写入：两个窗口同时改、确认丢失后再送 | 不做模型。全化表已经写出每一格；并发由修订号与提交事务里的重读守，重复由原操作的身份守，两样都是存储事务里的单步判断 |
| 较高的性能要求 | 每次提交多一次时钟读数和一行写入 | 不做模型。要守的是不多一次往返，结构上看得出来。代价在「列出会话」那一程的第一个切片量 |

三个模型是 TLA+ 写的，用项目钉住的 TLC 1.7.4 检查。模型、负控配置与运行命令在[接入登记表与可用性的有限行为模型](../../packages/access/server-entry/verification/models/README.md)。**这是有限模型的结论。** 它说明设计在下面的规模内没有这一类缺陷。它不说明实现正确，也不说明更大的规模下成立。

#### 模型一：登记表与在途工作

规模：2 个协议名，2 个调用（一个读取类、一个提交类），1 个观察，贡献最多挂上 3 次。结果：64,350 个不同的状态，没有发现错误。

| 性质 | 说的是什么 | 守的不变式 |
| --- | --- | --- |
| `Unique` | 同名协议至多挂着一份 | I-3 |
| `AbortReachesInFlight` | 在途的调用如果属于一份已经不在表里的贡献，它一定已经收到中止 | I-4 |
| `HonestAnswer` | 处理函数已经开始的提交类调用，不会被答成「依据不可用」 | I-8 |
| `GoneMeansSettled` | 撤下完成时，这份贡献的在途调用都答复了，观察都结束了 | I-4 |
| `EveryCallSettles` | 到达的调用最终都有答复 | I-4 |
| `EveryObsEnds`、`DrainCompletes` | 要结束的观察最终结束；撤下最终完成 | I-4 |

故意改坏的七个变体，每个都在预期的性质上失败：

| 变体 | 改坏了什么 | 在哪条性质上失败 |
| --- | --- | --- |
| `noUniqueness` | 挂上时不查同名 | `Unique` |
| `noAbort` | 撤下时不给在途调用发中止 | `AbortReachesInFlight` |
| `nonAtomicLookup` | 查登记表和登记成在途分成两步 | `AbortReachesInFlight` |
| `wrongAnswer` | 提交类调用在中止后失败，答成「依据不可用」 | `HonestAnswer` |
| `earlyGone` | 不等在途的都结束就宣布撤下完成 | `GoneMeansSettled` |
| `noObsEnd` | 撤下时不让观察结束 | 进展性质 |
| `stuckAborted` | 收到中止的调用没人处理 | 进展性质 |

`EveryObsEnds` 没有单独的变体让它失败。它在模型里由公平性直接保证。

#### 模型二：可用性两端收敛

规模：2 个协议，2 个订阅者，登记表最多改 3 次，每个订阅者的积压上限 2，每个订阅者最多断线 1 次。结果：6,722 个不同的状态，没有发现错误。

| 性质 | 说的是什么 | 守的不变式 |
| --- | --- | --- |
| `ViewIsTruePast` | 订阅者的视图总是登记表在某个修订号上真实有过的样子 | I-6 |
| `DeltaBaseMatches` | 队头是变化帧时，它的基础正好是订阅者手里的那个修订号 | I-6 |
| `Converges` | 订阅着的订阅者最终看到的集合等于登记表，除非它又断开了 | I-6 |

故意改坏的三个变体：

| 变体 | 改坏了什么 | 结果 |
| --- | --- | --- |
| `nonAtomicSubscribe` | 读登记表和登记订阅者分成两步 | 三条性质各自单独检查时都失败 |
| `dropOldest` | 积压满了丢最旧的一帧，不改发快照 | `DeltaBaseMatches` 与 `ViewIsTruePast` 各自失败 |
| `staleOnReconnect` | 重连时不发快照 | `DeltaBaseMatches` 与 `ViewIsTruePast` 各自失败 |

#### 模型三：会话观察的定位与流

规模：最多 3 次提交，每次提交可以带来一次新的主调用；最多订阅 3 次。模型的发布与撤回随时可以发生，因为那是模型自己的事。结果：53,162 个不同的状态，没有发现错误。

| 性质 | 说的是什么 |
| --- | --- |
| `QuiescentIsCurrent` | 不丢唤醒。定位空闲、没有在途的通知、标记没立着时，观察者看到的修订号就是日志的修订号 |
| `TargetIsLatest` | 不停在旧的调用上。同样安静下来时，目标要么没有，要么是日志里最近的主调用 |
| `NoStaleFrame` | 旧目标或旧订阅的帧不发出去 |
| `AxesAgree` | 定位与流两条轴对得上 |
| `EventuallyCurrent` | 提交停下之后，观察者最终看到最新的修订号，并一直保持 |

故意改坏的三个变体：

| 变体 | 改坏了什么 | 在哪条性质上失败 |
| --- | --- | --- |
| `dropWhileBusy` | 定位进行中来的通知不记下 | `QuiescentIsCurrent` |
| `noDiscard` | 迟到的旧帧不丢掉 | `NoStaleFrame` |
| `keepOldTarget` | 主调用换了、模型没给新的流时，留着旧目标 | `TargetIsLatest` |

第一个变体就是本提案修订 3 之前的写法：那时的表写着定位进行中「不理会」通知。

这个模型的前提：通知不丢。通知丢了由按间隔的刷新补上；流还在的时候不按间隔刷新，所以丢了的那次提交要等到流结束后的那次定位才看到。这是设计接受的。次数与累计时长的上界、时钟、取消与撤权没有建模。

#### 环境假设

- 处理函数要么正常完成，要么在收到中止之后失败。实现里这一条由管道守：中止之后过了宽限还没返回的，管道当它失败。处理函数因为别的原因失败，模型里没有，它按操作契约的 `effect` 规则答，不涉及交错。
- 连接断开时，服务端一定丢掉这个订阅者和它的积压。
- 没有建模：时钟、心跳、请求预算、同一个调用被重发。

#### 两条硬要求

前两个模型里各有一处「必须是一步」，分成两步就出错：

1. **查登记表和把调用登记成在途，中间不能让出执行权。** 分成两步，撤下的中止就可能漏掉一个刚查完表的调用。
2. **读登记表得到快照和把订阅者登记上，中间不能让出执行权。** 分成两步，中间那次变化的帧就丢了。

在 JavaScript 里，这两处各自是一段没有 `await` 的同步代码。它们已经写进签名：`RegistryForPipeline.enter` 与 `RegistryForPipeline.subscribe` 都是同步方法。

#### 精化对照

| 形式化里的 | 守它的类型、方法或结果变体 | 契约测试 |
| --- | --- | --- |
| 模型一 `CallArrive`：查表与登记成在途是一步 | `RegistryForPipeline.enter` 是同步方法。判断次序第 1 到 5 步之间不让出执行权 | 调用登记成在途之后撤下协议，中止信号被触发 |
| 模型一 `Unmount`：移除表项、发中止、标观察要结束是一步 | 登记表撤下的那个同步段 | 同上 |
| 模型一 `UnmountComplete` 要等在途的都结束 | 撤下完成是登记表的状态，在每个 `Entered.leave` 都被调用、每个观察都写出结束帧时达到。`mount` 的收回函数返回的 Promise 在这时完成 | 撤下并等它完成，此时每个在途调用都已答复 |
| 模型一的进展性质：收到中止的调用最终有答复 | 判断次序第 13 步的宽限 | 处理函数不理会中止，过了宽限调用仍得到答复，撤下完成 |
| 模型一 `HandlerStart` 遇到已中止：答「依据不可用」 | 判断次序第 10 步 | 处理函数还没开始就收到中止，答 `basis-unavailable` |
| 模型一 `HandlerFinish` 中止后失败：提交类答「未知」 | 判断次序第 13 步，按契约的 `effect` 分 | 提交类操作的处理函数开始之后撤下并失败，答 `unknown` |
| 模型一 `Unique` | `mount` 遇到同名同主版本的表项时抛装配错误 | 挂上同名协议第二次报错，第一份照常答复 |
| 模型二 `Subscribe`：读快照与登记订阅者是一步 | `RegistryForPipeline.subscribe` 是同步方法，返回快照 | 订阅的同时挂上一个协议，订阅者最终的集合里有它 |
| 模型二 `Change`：改表、修订号加一、排帧是一步 | 登记表挂上与撤下的同步段里调用订阅者的回调 | 同上 |
| 模型二 积压满了改发快照 | 观察中枢对可用性这个观察的队列策略 | 订阅者不读、连续变化超过上限，恢复后得到一帧快照 |
| 模型二 `DeltaBaseMatches` | 连接应用变化帧之前核对修订号 | 收到基础对不上的变化帧时重新订阅 |
| 模型三 `Notice`：定位进行中立起标记；`LocateDone`：标记立着就再定位 | 会话观察里「定位」这个对象的一个标记，和定位结束时的一次判断 | 定位读完日志还没结束时提交并通知，不等间隔就发出带新修订号的状态帧 |
| 模型三 `Deliver`：不属于现在这份订阅的帧丢掉 | 「流的订阅」这个对象：每份订阅一个中止信号，帧到达时核对它属于现在这一份 | 换目标之后旧订阅再交来一帧，它不出现在帧序列里 |
| 模型三 `LocateDone`：主调用换了而模型没给流时放下旧目标 | 定位的结果那张表的第二行 | 观察中出现新的主调用登记而模型没给流，收掉旧目标，发状态帧与 `refreshing` |
| 登录会话的全化表 | 主进程里的登录会话，状态用四个互不相交的类型表示，登录证明只是「已登录」和「退出中」两个类型的字段 | 每一格一条用例 |

| 模型里的东西 | 含义 | 设计里的对应 |
| --- | --- | --- |
| `entries` | 登记表：一组「协议、第几次挂上」 | 登记表的表项。「第几次挂上」对应一份贡献的身份 |
| `genState`：`live`、`draining`、`gone` | 一份贡献的寿命：挂着、撤下中、撤下完成 | 贡献的生命周期。`draining` 到 `gone` 对应接入插件作用域的卸载完成 |
| `call[c].state`：`idle`、`registered`、`running`、`answered` | 一次调用：没到、已登记成在途、处理函数在跑、已答复 | 管道里的一次调用 |
| `call[c].aborted` | 中止信号已发给它 | `CallContext.signal` |
| `call[c].started` | 处理函数开始过 | 决定失败时答 `basis-unavailable` 还是 `unknown` |
| `obs[o].mustEnd` | 观察中枢已经决定结束它，结束帧还没写出 | 观察中枢里的待结束标记 |

| `view[s]` | 订阅者手里的修订号和集合 | 连接里记着的可用性 |

#### 证明转成的契约测试

| 性质 | 模型给出的结论 | 契约测试 | 变红的缺陷 |
| --- | --- | --- | --- |
| I-3 同名至多一份 | 在上面的规模内成立 | 挂上同名同版本的协议第二次，报装配错误，第一份照常答复 | 去掉挂上时的同名检查 |
| I-4 中止送达每个在途的 | 成立，前提是查表和登记是一步 | 调用登记成在途之后撤下协议，这个调用的中止信号被触发 | 撤下时不遍历在途集合；或查表与登记之间插入等待 |
| I-4 撤下完成时都已结束 | 成立 | 撤下协议并等它完成，此时它的每个在途调用都已答复，每个观察都收到了结束帧 | 撤下不等在途的结束 |
| I-4 进展 | 成立，前提是公平调度 | 调用收到中止之后，在有界的步数内得到答复 | 收到中止的调用不被处理 |
| I-8 提交类答「未知」 | 成立 | 提交类操作的处理函数开始之后撤下协议并让处理函数失败，答复是 `unknown` | 把这种情形答成 `basis-unavailable` |
| I-8 读取类与未开始的 | 成立 | 读取类操作在中止后失败，答复是 `basis-unavailable`。处理函数还没开始就收到中止，答复是 `basis-unavailable` | 交换这两种答复 |
| I-6 订阅不漏帧 | 成立，前提是读表和登记订阅者是一步 | 订阅的同时挂上一个协议，订阅者最终的集合里有它 | 读表与登记订阅者之间插入等待 |
| I-6 积压满了改发快照 | 成立 | 订阅者不读，登记表连续变化超过积压上限，订阅者恢复读取后得到一帧快照，集合等于登记表 | 积压满了丢最旧的一帧 |
| I-6 重连得到快照 | 成立 | 断线期间登记表变化，重连后第一帧是快照，集合等于登记表 | 重连后只发后续的变化帧 |
| I-6 帧不错位 | 成立 | 客户端收到基础对不上的变化帧时不应用，改为重新订阅 | 客户端不核对修订号就应用 |
| 会话观察不丢唤醒 | 成立，前提是通知不丢 | 一次定位读完日志、还没结束时，提交一次并送达通知。不等间隔，观察者发出带新修订号的状态帧 | 定位进行中来的通知不记下 |
| 会话观察不发旧帧 | 成立 | 换目标之后让旧订阅再交来一帧，这一帧不出现在帧序列里 | 换目标时不收掉旧订阅，或不核对帧属于哪份订阅 |
| 会话观察不停在旧的调用上 | 成立 | 观察中出现新的主调用登记而模型还没给它的流，观察者收掉旧目标 | 主调用换了仍留着旧目标 |

最后一行是模型之外加的一道防线：模型证明服务端不会发出错位的帧，客户端仍然核对一次。

依赖方向：

### 17. 交付怎样分

范围分成并行的两路，之后再串行两程。

| 段 | 范围 | 写哪里 |
| --- | --- | --- |
| 第一路「接入层」 | 公开契约的共同部分；贡献的类型与登记表的服务定义；入口里的登记表、管道、观察中枢、新地址的 HTTP 承载绑定、内置协议与可用性；客户端核心；客户端装配；守新边界的依赖方向门禁 | `packages/access/`；依赖方向门禁的配置与约束登记；`apps/harness-server` 里入口那一行 |
| 第二路「领域一侧」，一次一程 | 第一个产品要用、又不依赖接入层的三件领域能力：提交的时刻、会话列表项与列出会话的读取面；会话观察，连同它要补齐的四处；接通普通设置项的读写 | 列出会话：`packages/session/` 下的会话契约、会话实现、会话 SQL 存储；`apps/harness-server` 里会话的授权政策表、发行配置、材料目录与参加者清单。会话观察：新成员会话观察；会话契约；经事务端口提交之后发通知的那一处，落在会话组的哪个成员在定约时定；模型契约的投影函数；`apps/harness-server` 里的模型宿主行、模型授权表、会话观察的装配行与发行配置。设置：`packages/assets/`；`apps/harness-server` 里接设置领域的装配行 |
| 之后的第一程「接入插件」 | 身份、资产、会话、会话诊断、人工介入各一个协议契约成员和一个接入插件成员；服务端应用的装配换成入口行加各接入插件行；命令行换到客户端核心；删掉现有三个位置、公开契约里各领域的形状和三个手写的客户端；契约骨架验证应用退役 | 各领域的能力组；`packages/access/`；`apps/harness-server`；`apps/cli` |
| 之后的第二程「桌面应用」 | 界面外壳契约与共用界面件；各领域的界面模块；桌面应用 | `packages/frontend/`；各领域的能力组；`apps/desktop` |

规则：

- 两路的写范围不相交，互不导入。服务端应用里，第一路只改入口那一行，第二路改的是会话、模型、设置的行与发行配置。第二路的三件只用领域自己的词，不导入接入组的任何成员。会话观察对外给出的是领域面：一次建立的结果，加一个帧的异步序列。把它接成帧来源是接入插件那一程的事。
- 第二路的三件里，「列出会话」和「会话观察」都改会话存储与发行配置，所以不能同时做。第二路本来就是一次一程。
- 一程的大小按人在一个验收窗口里验得完多少定，大概 3 到 5 小时。两路各分成几程、每一程做哪个对象，在交接时定，记在这条线的路线图卡上。每一程做完一个完整的对象，并带一条能亲手跑的演示命令；守新边界的门禁与正文的写回随建了那条边界的那一程做。
- 第一路最先做的一程先回答「纯成员能不能在浏览器里编过、跑通」：建一个不带 Node 类型、带浏览器类型的消费者夹具，把共同契约编过去，在无界面的浏览器里跑一次。客户端核心在它自己那一程再过一次同样的夹具。仓库里还没有这样的成员。
- 「会话观察」最先做的两程不写会话观察的逻辑。第一程在正式装配上接通会话日志与模型的公共流，并量两个数：调用登记比模型调用晚多久出现、首帧要多久。第二程让每一次提交都发通知。这条链从来没有在真实的存储和真实的流上跑通过。
- 第一路交付期间，新地址和现有三个位置并存，现有位置不动。第一路用内置协议和测试里的贡献验证整条链。
- 接入插件那一程按领域互不相交，可以并行。相交的只有服务端应用里列出开放哪些协议的装配文件，以及命令行。
- 整件事完成的判据是替代的实现都删掉了：现有三个位置、公开契约里各领域的形状、三个手写的客户端、契约骨架验证应用。
- 每一程各自经 PR 进集成轨道。准入独占机器，所以合入是串行的，后合入的一方先同步轨道头。
- 每一程的验收标准写在那一程的卡和 spec 里，不在本提案。

## 验证与消费者切换

### 已验证的

| 说不准的点 | 怎么验的 | 结果 |
| --- | --- | --- |
| Cordis 4.0.4 能不能在浏览器里跑 | 探针：打包后在无界面的 Chromium 里跑；搜索包里只有 Node 才有的东西与 `eval` | 能。打包后 73 KB（没有压缩）。搜不到 `process`、`Buffer`、`node:` 开头的导入、`AsyncLocalStorage`、`eval`、`new Function` |
| 服务随可用性的帧出现与收回时，依赖它的插件跟着加载与卸载，再次出现时能重新加载 | 探针：生灭，Node 与浏览器各跑一遍 | 成立，两边结果相同 |
| 服务收回时依赖它的插件按什么次序卸载 | 探针：卸载次序 | 服务立刻不可见，依赖的插件随后异步卸载，收回函数返回的对象完成时都已卸载。设计已按这个次序写 |
| 方法签名能不能从契约推出来，类型检查慢不慢 | 探针：45 个操作加一个观察，另有 200 个操作的规模 | 能。消息体与结果类型都推得出来；读取类没有 `unknown`；六种错误用法与贡献少一个处理函数都编译不过。TypeScript 6.0.3 下 45 个操作 0.21 秒，200 个操作 0.34 秒 |
| 撤下与在途调用的交错 | 模型一 | 规模内通过，七个改坏的变体都失败 |
| 可用性两端收敛 | 模型二 | 规模内通过，三个改坏的变体都失败 |
| 会话观察的定位与流：通知、间隔、读日志、流的帧交错 | 模型三 | 规模内通过，三个改坏的变体都失败。其中一个变体是修订 3 之前的写法 |

### 没有验证的

下面各条没有验证过，不能当作已经成立：

- 开了沙箱的 Electron 页面里没有跑过 Cordis。只在同一个内核的无界面浏览器里跑过。
- 提交通知接上会话观察之后，从工具结果提交到界面看见它的延迟没有量过。它不依赖轮询间隔的前提是一轮当中的提交也发通知，现在不发。
- 「一轮当中的提交不发通知」和「登录的主体被模型的授权表拒绝」都是从代码结构推的，没有运行。
- 会话日志、模型的公共流、提交通知三样从来没有在真实的存储和真实的流上接在一起跑过。入口现有的观察测试全用替身。
- 一次模型调用开始之后，会话日志里它的登记晚多久出现：没有规格，没有量过。调用结束之后它的流保留多久是模型的事，会话观察不依赖它。
- 每次提交多一次会话时钟的读数和一行写入，代价没有量过。
- Cordis 等收回函数返回的 Promise，只读了源码，没有写测试。
- 共同契约和客户端核心能不能在不带 Node 类型的条件下编过、在浏览器里跑通，没有试。Cordis 试过，这两个成员没有。
- 现有 60 多个操作的规则表能不能原样接到新的编解码上，没有试。
- 严格模式的表不能加列，只有存储规格的记载，没有复现。
- streamdown 四个插件各自的许可没有核。streamdown 本身核过，是 Apache-2.0。
- 普通设置项从写入到下一次采用生效这条路，在正式装配里没有跑过。写入服务只在测试装配里实例化过。
- 内部工具消息的块实际标成什么，没有逐个产出方核。系统提醒核过一处，标的是给人也给模型。
- 三个模型只说明在给定规模内没有这一类缺陷，不说明实现正确，也不说明更大的规模下成立。模型三以通知不丢为前提。
- 桌面应用「流畅」的数值线没有定。
- 线上形状没有对照浏览器同源与跨源的限制逐条核。
- 「外来的代码」一节沿用的资产概念能不能原样覆盖原生插件和界面模块，没有读资产与采用的契约正文核。

### 沿用现有规定、没有重判的

- 身份的 34 个操作，消息体、结果集与业务规则原样带过来。它们是身份领域自己的规则，本提案只换挂法。逐个重判是身份领域的设计工作，不在本提案。
- 会话观察的刷新策略、退避与上界的数值，各来源结果的对外表示，沿用服务端接入规格与公开契约现有的规定。状态机按两条轴重新全化过，并做了模型三；数值与对应表没有重判。这个状态机此前没有实现过。
- 「目标租户的账号必须等于登录的账号」这条规则本身沿用。本提案只论证了它该由谁核对。
