# DSH、Cordis 与完全动态系统

本文记录对 DeepSeek Harness（DSH）及其底层 Cordis 运行时的机制性解读，并将这些机制放回 OMNE 的“完全动态系统”目标中理解。本文只讨论动态运行时、形式化模型和系统演化，不讨论具体 Agent 应用框架的选型。

## DSH 的基本思想

DSH 的核心主张是“一切皆插件”。模型、工具、技能、会话、存储、沙箱、循环、调度和界面都作为可替换组件接入运行时。组件之间通过服务、依赖声明和事件协作，而不是依赖一个不可替换的巨型核心。

这种设计把系统拆成三个层次：

1. **运行时内核**：维护上下文、服务、事件、组件和生命周期。
2. **组合与装载层**：根据 profile、bundle、patch 组成当前运行时，并处理配置变更。
3. **领域应用层**：把具体的 Agent 能力装配到运行时中。

DSH 的另一条核心原则是“每次运行都可追踪”。模型看到的系统提示、上下文注入、工具调用、工具结果、子任务调度和流式输出，都会进入追加式会话记录。恢复、分叉、重放和轨迹查看都从同一条记录派生。

这意味着运行记录不是事后生成的日志，而是模型可见历史的规范来源。任何进入模型请求的内容，都必须能够从记录中重新构造。

## Cordis 的运行时模型

### Context 是服务与事件的承载体

Cordis 的 Context 不是单纯的字典，而是一个带作用域和生命周期的运行时对象。它承载：

- 服务提供者及其唯一性约束；
- 组件对服务的依赖声明；
- typed event 的发布与订阅；
- 组件隔离、拦截和子上下文；
- 与当前组件 Fiber 绑定的注册记录。

组件通过 Context 注册服务或监听事件。注册记录归属于创建它的 Fiber；Fiber 卸载时，属于它的注册和副作用一并清理。

### Fiber 生命周期

组件不是一次性函数调用，而是有生命周期的 Fiber。典型状态包括：

```text
PENDING → LOADING → ACTIVE → UNLOADING → DISPOSED
                    ↘ FAILED
```

组件依赖的服务尚未出现时，可以停留在 `PENDING`。依赖满足后进入加载和激活。服务消失、配置变化或目标版本变化时，组件会被卸载、恢复或重新加载。

依赖方不能在 provider 已经失效后继续使用旧的服务视图。运行时需要先排空依赖方，再提交新的 provider 解析结果。这是结构性动态系统与普通回调机制之间的关键区别。

### 可逆 effect

Cordis 要求组件对 Context 的改变留下可执行的清理动作。一个 effect 可以抽象为：

```text
前向变换：Γ → Γ'
逆变换：Γ' → Γ
```

运行时累计这些逆变换，并在组件退出时按相反顺序执行。这样，组件卸载后，可以恢复它对受控上下文产生的贡献。

这里的“恢复”不是任意世界状态的时间倒流。只有被运行时独占、被 Context 建模并且拥有可靠逆操作的状态，才属于可恢复范围。已经发出的网络消息、已经提交的外部写入、单调递增的分配器和其他不可逆 emission，必须通过延迟提交或业务补偿处理。

### Reactive coeffect

组件不仅产生 effect，也声明自己依赖什么。运行时持续观察依赖表，并将变化分类为：

- 激活：依赖从不满足变为满足；
- 停用：依赖从满足变为不满足；
- 中性：依赖变化但不影响当前组件。

这使组件生命周期由上下文变化驱动，而不是由固定启动顺序驱动。组件可以在 provider 迟到时等待，在 provider 撤销时卸载，在 provider 替换时重新解析。

### 事件调度

Cordis 的事件系统区分不同调度语义：

- `emit`：广播事件；
- `parallel`：并行通知；
- `serial`：按顺序执行；
- `bail`：某个处理器给出结果后提前结束；
- `waterfall`：处理器逐步修改并传递上下文。

事件因此不只是观测工具，也是组件之间的正式扩展协议。

### 声明式组合与热替换

profile 由有序 bundle 组成，patch 可以替换或插入配置项。配置更新不是简单地重新启动整个应用，而是对组件树进行协调：

1. 识别新增、删除和变更的组件；
2. 按依赖关系安排卸载和激活；
3. 运行旧组件的清理动作；
4. 装载新版本并提交新的解析视图；
5. 失败时恢复到上一个可用版本。

这使系统结构本身成为可修改对象。

## Cordis 论文的形式化理解

相关论文是 2026 年的预印本：[A Programming Paradigm for Spatiotemporal Composability](https://arxiv.org/abs/2608.25512)。它提出“时空可组合性”这一统一视角。

### Temporal composability

Temporal composability 关注一个组件在时间上的加入和退出。每次状态变换都携带针对当前状态的逆操作，多个 effect 形成可累积、可逆的序列。组件退出时，逆操作按相反顺序执行，从而恢复该组件在受控状态上的贡献。

### Spatial composability

Spatial composability 关注组件在空间上的依赖关系。组件声明所需 key 和提供的 key，运行时根据依赖满足度激活、停用和重载组件。

### 统一 Context

论文把 effect context 与 coeffect context 统一为递归 Context。所有交互都必须通过 Context-mediated operation 进行，组件不能绕过 Context 直接修改受保护状态。

论文还引入 observational equivalence：两个状态不必在物理表示上完全相同，只要对允许的观察操作表现等价即可。这适合描述组件卸载后的“语义恢复”。

### 条件性定理

论文给出了 Preservation、Recovery、Ordering、Resolution coherence、Progress 和 Confluence 等结果，但这些结果都是有前提的：

- provider 之间不能冲突；
- 依赖关系必须无环；
- Fiber 数量和 iterator 长度需要有界；
- provision 必须满足 total 条件；
- effect 必须提供正确的 inverse；
- 相关操作需要满足交换性条件。

运行时本身不会自动证明插件作者提供的 inverse 或交换性 witness 正确。论文证明的是满足这些契约的组件系统，而不是任意动态代码都自动安全。

此外，论文仍是 v1 预印本。独立的 Idris2 研究复核项目 [DGamma](https://github.com/Termina1/dgamma) 表明，部分命题需要修正或加强前提，Confluence 的机械化证明尚未完成。因此应把这些结果理解为条件性语义基础，而不是已经完成的工业级验证。

## 对“完全动态系统”的理解

OMNE 的“完全动态”不是指每次运行产生不同的输出，而是指系统的结构和组织可以在运行期演化。

可以将系统状态写成：

```text
s_t       运行状态
θ(t)      策略与行为参数
A_t       可用动作集合
σ(t)      组织与编排拓扑
```

一个真正的完全动态系统允许以下量在运行过程中变化：

```text
动作：      a_t = π_θ(t)(s_t, o_t)
状态：      s_(t+1) = F(s_t, o_t, a_t, ξ_t)
动作空间：  A_(t+1) = Ψ(A_t, s_t, o_t, a_t)
拓扑：      σ(t+) = Φ(σ(t), s_t, o_t, a_t)
策略：      θ(t+1) = G(θ(t), s_t, o_t, a_t, r_t)
```

因此，“动态”至少有两个层次：

- **轨迹动态**：同一套结构在不同状态下走不同路径；
- **结构动态**：运行中的工具、组件、约束、知识形态和组织拓扑发生变化。

只有前者时，系统仍然是动态执行的静态架构。后者才进入完全动态系统。

## MVC-4 + 2 的解释

OMNE 文档提出四条硬性标准和两条加分项。

### MVC-1：Stateful Loop

系统有持续存在、可读写并参与决策的状态。状态不是一次调用的临时变量，而是影响后续行动的运行时事实。

### MVC-2：Adaptive Policy

策略可以在运行期更新。更新可以来自参数调整、检索增强、规则注入、提示结构改变或其他可验证的策略变化。

### MVC-3：Evolving Action Set

动作空间可以在运行期增加、替换和卸载。新增动作必须经过声明、权限和生命周期管理，不能只是把一个函数临时塞进调用上下文。

### MVC-4：Re-configurable Topology

组织拓扑可以在线重构。系统能够加入、删除或替换组件、阶段和子系统，同时处理正在运行的工作、依赖关系和旧版本清理。

### MVC-5：Knowledge Reorganization

知识结构本身可以被重组，而不只是向固定结构中添加数据。节点类型、关系形态、层级、版本和投影可以在受控条件下演化，并保留历史。

### MVC-6：Adaptive Governance

约束、权限、配额、审计规则和状态转换守卫可以成为可版本化、可评估和可更新的运行时对象，而不是全部固化在程序代码中。

MVC-1 到 MVC-4 定义了最小完全动态系统。MVC-5 和 MVC-6 则使系统具备持续自进化所需的知识和治理基础。

## DSH/Cordis 对 OMNE 的启发

### 结构演化必须是一等能力

如果动作集合和组织拓扑只能在部署前改变，系统就无法真正自我演化。结构变更必须拥有自己的声明、版本、依赖、激活和回滚语义。

### 自进化结果必须经过运行时承载

知识或策略系统可以提出新的候选结构，但候选不能直接改变生产运行时。候选需要经过：

```text
提出 → 评估 → 契约检查 → 隔离运行 → 观测 → 提交或撤销
```

这要求运行时能管理多个代次，并能在不破坏旧代次的情况下试运行新代次。

### 可逆性是受控范围内的工程契约

不能承诺整个世界可回滚。更准确的做法是划定受控 Context：

- Context 内的状态必须拥有明确逆操作；
- Context 外的 emission 必须延迟、幂等或提供补偿；
- 每个组件声明自己的副作用边界；
- 恢复验证使用语义等价，而非依赖物理字节相等。

### 动态性必须有治理

没有依赖约束、权限边界、版本隔离和失败恢复的动态加载，只会把系统变成不可预测的运行时修改器。完全动态系统需要同时具备变化能力和变化约束。

## 对实验方向的工作定义

基于以上理解，OMNE 的完全动态运行时可以暂时定义为：

> 一个能够在运行期安全地改变动作空间、组件依赖、组织拓扑、知识结构和治理规则，并且能够记录、评估、隔离、提交或撤销这些变化的系统。

其中“安全”不等于所有外部副作用都可逆，而是意味着每次变化都有明确的作用域、版本、所有者、生命周期、证据和失败处置。

DSH 展示了一个可运行的动态组件系统，Cordis 论文提供了描述这种系统的形式化语言，OMNE 的完全动态目标则要求把这种能力进一步连接到知识演化、治理演化和持续自进化闭环中。
