# 开发模型防御辅助评估协议

## 目的与单位

此协议比较一个开发 agent 在固定条件下使用一项防御辅助的 `retain`、
`simplify`、`remove` 三个 arm。一次报告只能覆盖一个明确的候选、基线、
任务集版本和环境快照。每项任务都运行基线模型的 `retain`，以及候选模型的
`retain`、`simplify`、`remove`，才可观察候选切换的回归。公开任务包可用于调
优；报告还必须携带一个未参与调优的冻结 `heldout` 任务包、其 hash 和防污染
声明，不能把公开样例称为留出检验。

这里的“开发 agent”是为本仓库产出设计、文档、代码或审阅结果的 agent。产品
runtime agent 的输入、授权、副作用和成功定义不同；不得把本协议的报告作为
其可靠性、安全性或发布依据。

## 最小可审阅证据

报告记录基线和候选的提供者、标识、可辨认版本或修订和实际配置文件；也记录
推理配置、harness、工具和 prompt 的版本及文件。每个 arm 以稳定的
`pattern_id` 指向同一防御模式，并保存实际辅助文本或配置文件。所有文件均以
相对路径和 SHA-256 回查。每种模型/arm 对每项任务以相同正整数重复运行。每次
运行需要：

- 任务、split、arm 和重复序号；
- 本地产物或轨迹文件及其 SHA-256；
- 每个关键约束的观察状态，而不是“agent 说它遵守了”；
- token、耗时、工具调用和人工干预的成本事实。

固定任务集中的关键约束有 `authority`、`approval_boundary`、
`decision_finality`、`causal_basis`、`proportional_process`、
`cross_boundary`、`cancellation_semantics` 和 `resource_quiescence`。报告
可增加其他约束；不得把未观察、违反或缺失轨迹说成通过。

离线 CLI 只检查结构、完整覆盖、hash 和证据文件。`violated` 是有效观察，
不会把完整失败结果降格为缺数据；`unobserved` 才表示不完整。含违反的报告可
以 `evidence-ready` 交人工审阅，但不能记录 `adopt`，适合记录 `do_not_adopt`。
它无法确认轨迹真实性，也不替代人工审阅产物、任务质量或因果归因。因此
`evidence-ready` 是待审阅状态，不是统计结论或采用授权。

## 解释与复核

比较时同时审阅失败类别、相邻任务回归、成本和人工干预。不得用汇总总分掩盖
关键约束退化，也不规定一个放之四海皆准的样本量或分数阈值。若证据缺失、任
一关键约束未观察、重复不完整或条件不可比，结论为 `inconclusive`，补齐或重
跑后再判断。关键约束违反是拒绝或缩小采用范围的证据，不是 inconclusive；
“尚未出错”也不能证明模型已经内化辅助。

人可以基于 evidence-ready 报告填写 `adoption_record`，记录在什么模型、版本、
环境和任务范围内保留、简化或停止某项辅助，以及替代机制和复核触发。模型、
推理、工具、prompt、任务分布变化，故障复发、边界变化或明显成本负担都会触
发复核。删除辅助不撤销系统保证；回调失败处理和旧运行态恢复只按各自契约作
出保证，不能据此协议作普遍承诺。
