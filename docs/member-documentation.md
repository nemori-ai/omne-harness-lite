# 能力组与成员包文档

本页维护`packages/<domain>/`能力组和`packages/<domain>/<package>/`成员包的文档要求。它供开发者、集成者及文档维护者选择正文位置、阅读路径和维护责任。成员的必选文件见[包组织](package-organization.md#成员的必选结构)。模板及检查的具体操作归[开发指南](development.md#创建和整改产品包)和[模板工具](../tools/repo-toolchain/templates/package/README_ZH.md)。

这里的domain指[产品包组织](package-organization.md)中的能力组，不自动对应DDD的domain或bounded context。能力组不是workspace成员，也不是运行时或部署边界。文档随其实际工程责任生长，不为目录对称创建空包。

## 三处各自拥有的知识

| 位置 | 唯一正文的责任 | 继续展开的位置 |
| --- | --- | --- |
| `docs/domains/` | 系统领域责任、事实拥有者、跨领域协作及组合保证的承担者 | 导航到真实能力组及契约拥有者 |
| `packages/<domain>/` | 本组工程分解、成员选择、允许依赖、组内关键协作、组合验证及共同维护 | 导航到参与包及实际协调者的协议 |
| `packages/<domain>/<package>/` | 本包公开使用、契约、内部设计、配置、运行限制、验证和维护 | 导航到公开定义、专题及持续验证资源 |

上层约束下层，下层说明如何兑现。当前源码和测试用于对照设计，不能反向降低承诺。能力组不得重写成员错误集合或状态机；成员不得复制组级依赖规则。跨组精确协议归实际协调者，领域页与组页解释参与关系并链接该源。

例如，系统领域页说明日程整体完成与通知送达各归谁。schedule组说明组内哪些包承担Job协调、存储映射和装配、依赖如何连接。通知包维护送达协议、去重、取消及恢复的精确条件。共同事务不能因成员相邻或处于同组就视为成立。

## 能力组文档要求

每个真实能力组提供`README.md`和`documentation.json`。README是组的阅读入口，可直接承载以下正文；内容有独立阅读任务或维护节奏时再拆到`docs/`。登记维护应有文件和章节，不手填完成状态。

| 必需信息 | 读者应能回答的问题 |
| --- | --- |
| 责任与范围 | 本组解决什么工程责任，服从哪些系统和领域约束，哪些责任另有拥有者？ |
| 成员与依赖 | 真实成员各做什么，公开消费从哪里开始，允许的依赖方向是什么？ |
| 关键协作 | 组内主流程怎样交接，协调者是谁，精确失败和生命周期协议在哪里？ |
| 组合验证 | 哪些性质必须在组合中检验，谁承担验证，前提、执行入口与未覆盖在哪里？ |
| 维护 | 新增包、提供者或适配怎样选择位置，哪些组内变化要求同步导航、契约或组合验证？ |

实际成员清单来自真实workspace成员。具名文档目标可以先维护设计与规格，但须单独标明尚非workspace成员；文档目录和登记不证明包、源码或运行实例存在。组页解释职责与关系，不维护另一套手填完成数量。允许单成员组；它仍说明与外部能力的边界及扩展规则。没有组内组合性质时明确适用范围与理由，不留空标题冒充完成。

组根不放`package.json`、产品源码或统一成员SPEC。共同业务契约必须由实际成员或协调者拥有。组级文档说明组合验证责任，可执行资源仍随实际成员、应用或验证工具维护；不能在文档组根建立另一套运行入口。

## 成员包文档要求

成员根README提供一次阅读即可确定用途和下一步的入口。沿现有包模板保留双语README；两种语言表达同一份承诺，修改时同步，不分别引入规则。

| 必需信息 | 读者应能回答的问题 |
| --- | --- |
| 职责与状态 | 本包拥有何种能力，适用范围及采用依据是什么，哪些部分仍未实现或未验证？ |
| 使用 | 如何消费公开入口，必要依赖和最小有效示例是什么，独立使用与Cordis集成有何前提？ |
| 契约 | 公开形状及必要校验在哪里，非类型行为由谁维护，错误、生命周期及资源责任如何定位？ |
| 设计 | 内部模块怎样协作、为什么这样组织，关键状态和依赖怎样兑现公开承诺？ |
| 配置与运行 | 哪些配置、运行环境和资源限制实际适用，调用者与包各承担什么？ |
| 验证 | 适用的测试种类、必要的真实依赖或替身、独立运行入口、未覆盖和不适用理由分别是什么？分类见[包级测试责任](verification.md#包级测试责任与边界) |
| 维护 | 常见修改从哪里进入，哪些消费者和资源必须同步，如何扩展或替换而保持承诺？ |

可以在README中完整回答，也可以用简短说明链接到唯一专题源。不适用的信息说明理由；未完成的信息登记为缺项或明确占位。模板生成的说明不能当作真实设计、采用状态或运行证据。

成员在自己的验证说明里写下公开承诺、适用测试种类、必要的真实依赖或替身、独立运行入口、未覆盖和不适用理由。测试种类的承担者和停止范围只维护在[包级测试责任与边界](verification.md#包级测试责任与边界)。不另造一份跨包测试台账。

### 行为契约与完整文档

成员契约属于持续维护的长期规格，单次实施输入引用它；两者的用途、生命周期及承接规则归[规格分类](engineering/documentation.md#单次交付规格与长期规格)。

公开类型和必要运行时校验拥有数据形状。`SPEC.md`拥有类型不能完整表达的行为，例如结果、失败、所有权、生命周期、并发、事务、取消和恢复。契约要求必须保留条件、例外和要求强度，实现与测试不能替代承诺。

“薄SPEC”不作为成员文档的厚度限制。SPEC避免重复类型表和无效叙述，但必须完整表达适用的行为。使用指导、内部架构、机制论证和维护步骤按各自阅读任务组织；不因它们不是行为条款而省略。

多提供者共同消费一个公共承诺。提供者的契约只补自己真实承担的配置、资源、失败等责任，不另写公共保证。内部设计引用行为源，不能用更方便的机制描述改写行为。旧技术材料须按[架构准入规则](engineering/documentation.md#位置与唯一源)筛选；不符合上层的旧设计不能成为成员规范。详细技术内容按实际组、成员或协调者的责任承接，其内容不能推翻现行系统架构。未接受的条款仍标明候选范围。

持续技术未决及后续设计义务就近由工程设计或规格拥有者维护，写明影响、责任及下一入口。产品页只引用技术问题及其产品后果，不成为第二份精确机制正文。成员尚未具名时保留承接缺项，不将组根改成统一成员SPEC。

### 按需专题与持续资源

| 位置 | 何时建立 | 拥有什么 |
| --- | --- | --- |
| `docs/architecture.md`或具名设计页 | 内部设计具有独立阅读任务 | 内部模块关系、机制和必要理由 |
| `docs/guides/<任务>.md` | 有真实使用、集成或维护流程 | 前提、步骤、结果与失败处置 |
| `docs/reference/<主题>.md` | API导航、配置或协议需要单独查询 | 精确参考或到公开定义的导航 |
| `SPEC.md` | 本包承担非类型行为义务 | 现行行为承诺及其条件 |
| `schema/` | 有对外Schema | 正式身份、发布及消费者 |
| `verification/` | 有持续模型、证明或组合验证 | 可复跑资源、性质、前提和范围 |
| `tests/fixtures/` | 测试需要独立输入 | 测试数据，不能替代规格 |
| `acceptance/` | 有独立用户入口验收 | 独立验收者拥有的场景 |
| `adr/` | 有必须持续消费的实现取舍 | 现行理由，不累积本次提案和评审过程 |
| `resources/` | 包运行需要非源码资产 | 运行资源及必要来源、许可 |

具体允许格式、必需伴随文件和版本以模板manifest为准。API参考可从导出及文档注释生成；生成物须注明输入与生成命令，不手工维护第二份签名。生成API不能替代行为、使用或内部设计说明。需要新格式时由工具拥有者更新规则，不能靠ignore隐藏受维护资源。

## 阅读与维护路径

维护者先从[任务地图](context-map.md)定位系统或领域责任，再进入组README。组内局部任务直接从所属包README展开到契约、源码或验证；责任足够明确后停止阅读。完整Harness接入沿access组定位公开契约、SDK及服务端接入，独立能力消费无需强制经过SDK。

新增能力组先确定稳定责任、系统约束及具名维护者，再用domain模板建立组入口和登记。新增包先核对已接受职责、消费者及公开边界，在所属组使用package模板。创建模板不表示接受技术设计；未完成草稿不贴采用标识。

修改唯一正文时同步受影响入口、章节锚点、登记及实际读取者。拆页后原位置保留摘要和导航，撤掉已迁正文。跨包契约或组合机制变化还须核对真实协调者、参与包及组合验证，不只修链接。

组与包的局部AGENTS只在确有局部判断、边界或触发时建立。遵循`write-agents-md`，不将完整手册、命令表或契约复制进常驻提示。未进入正式RFC的候选、单次计划、访谈、逐轮评审和原始输出留任务`tmp/`，规定保存例外沿[文档治理](engineering/documentation.md#四类长期成果与普通任务)。长期SPEC独立表达当前决定，RFC仅定位变化理由；交付Issue引用精确输入，不成为第二规格源。

## 检查与结论边界

模板检查观察目录、节点、必需文件、版本及结构；文档inventory观察登记、章节、占位和未知。登记须可被实际发现，依据沿本页对应要求章节，具体格式归[spec-tools](../tools/spec-tools/README.md#文档目标与缺项计量)。

缺文件、仅标题、占位、错误登记及无法判定分别报告。旧版和未标识不自动升级；历史版本使用精确历史规则。正文结构可观察不表示语义充分、设计接受或行为兑现。目录通过也不证明租户隔离、生命周期或恢复。

报告给出全量、可比增减、口径变化和未覆盖。新增要求或删减分母不能算作修复收益。具体检查选择沿[验证说明](verification.md)，本规则不新增全项目合并硬线，也不要求每次维护跑完整产品矩阵。
