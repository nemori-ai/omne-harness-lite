# 架构设计与规格维护衔接

## 任务依据与范围

用户要求结合前述能力建模讨论和指定交接文档，优化现有架构设计指导，建立规格
维护体系，并优化或补充必要 skills。讨论的主线是：从能力目的和消费者出发，
定义最小充分契约，区分服务与插件边界、动态依赖和生命周期，并考虑系统机制及
Agent 工具/技能的消费方式。[交接证据](../../research/design-spec-maintenance/README.md)
保留具体来源、主线与开发分支的差异及未复验范围。

本轮在 D-001 的三类规格与单一权威、D-002 的接受边界和 D-004 的需求基础上补充
维护衔接，不改写其既有选择，不新增 catalog 或规格身份。这里审阅的是治理与
方法改动，不接受核心能力分支的产品契约或具体 Cordis 映射。

## 问题与设计取舍

已有原则正确，但语义接受、具体映射、应用装配和真实验证缺少可持续的衔接；
施工稿可能被迫长期拥有公共接口和运行关系。局部合法的状态与方法也可能漏掉
跨能力最后一段。补更多空模型或插件表无法独自解决这些问题。

| 本轮选择 | 理由与边界 |
|---|---|
| 补强现有建模正文 | 以目的、消费者和最小充分契约为主线，分别推导服务、插件与消费面；不另创固定架构流程 |
| 当前实现设计随包和应用维护 | 采用成员 `design.md` 作为默认入口，简单情况允许已有 README 承载；语义仍归 spec，历史论证保留原身份 |
| 就绪判断按任务依赖限定 | 区分语义、提供者、装配和实证，延后项有负责产物与受影响消费者；不要求所有未来细节先定稿 |
| 沿契约与实际消费关系维护 | 语义、映射、公共接口、规范模型和证据变化分别处理，精确消费者不自动升级 |
| 覆盖与缺口从契约入口可发现 | 复用已有验证说明与证据，不用文档数量或一道检查代表整体完成 |
| skills 与角色只投影必要职责 | 新增 spec-maintenance，调整 architecture-design 和 implementation-planning，以及实施/评审交接；不新增编排框架或模型配置 |

主要正文由[总体范式](../../architecture-guide/foundations/paradigm.md)、
[能力边界](../../architecture-guide/modeling/capabilities.md)、
[组织规范](../../maintenance/organization.md#当前实现设计的归属)和
[规格维护](../../maintenance/spec-maintenance.md)分别拥有。
其它文件提供导航或既有职责的投影，不建立平行完成清单。

## 迁移与验收范围

已有包与应用在相关设计修订或下次依赖消费时核对并补齐必要映射；不批量创建空
design.md，不移动或改写冻结规格。交接分支仍拥有具体产品映射与实现的交付责任。

验收关注：概念和权威分工一致；冻结/版本规则保持；缺口不被总体完成状态吞掉；
实施输入能定位必要运行责任；普通局部修改保持轻量；跨能力路径可发现责任断点；
双端 skills 和角色源/生成物一致。验证记录见[本轮验证](verification.md)。

## 审阅与接受

状态为待审的治理变更。用户已授权完成这套优化工作；本页不把该授权或后续只读
评审写成对所有具体候选选择的自动接受。独立评审结果由本轮验证入口导航，正式
采用按既有知识流转记录，未改变业务规格、catalog 或冻结表。
