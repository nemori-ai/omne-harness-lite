# 工具内部过程帧：tool-execution 与 context-sessions 协调稿

日期：2026-09-13。修订：v1。状态：候选边界设计，供后续两个专题共同消费；不是已接受决定、正式规格或实现完成声明。

## 目的与结论

本稿回答工具内部过程帧由谁定义、谁产生、谁保存、谁消费，以及这些职责在 Cordis 下如何组合。文中的 `tool-execution`、`context-sessions`、日志／存储指职责，不预先要求同名包、插件、进程或数据库。

**候选结论：过程帧的执行语义与生产生命周期归 tool-execution；context-sessions 负责会话关联及模型上下文消费；记录与读取的存储保证由所选日志／存储能力兑现。** 用户按需观察是工具执行的产品能力，界面可以装配在会话中，其访问与回放协议不因此转归会话生命周期。

此前讨论中“session log 的设计需要考虑过程帧”，指双方必须协调记录、引用和读取保证，不表示所有帧都归会话定义、都必须进入模型上下文，或都必须写进同一个物理日志。

这是从 Cordis 的能力、提供者、依赖、作用域、所有权和生命周期组合出发，结合 OMNE 要求形成的设计推论。Cordis 本身不规定本项目的过程帧业务模型，也不自动提供耐久交付与恢复协议。

## Cordis 视角的推导

上游机制证据沿用 DSH 官方提交 `c291e7961a515f6d7af9304e7fd1d257929aef26`。它是研究版本，不是已选定的 Cordis 发布依赖；实际采用包前须核对其对应语义。

| 已核对的机制事实 | 对本设计的推论 |
|---|---|
| Cordis 通过服务表面、声明式依赖和类型化事件组合能力，注册与监听具有受管生命周期。[Primer](https://github.com/deepseek-ai/deepseek-harness/blob/c291e7961a515f6d7af9304e7fd1d257929aef26/docs/cordis-primer.md) | 先确定生产、记录和消费责任，再以服务／插件组合；不因都能从一个 Context 取得，就把它们当成一个状态 owner。 |
| Fiber 表达一次插件运行实例；事件监听注册随其 owner Fiber 卸载而移除。[Fiber API](https://github.com/deepseek-ai/deepseek-harness/blob/c291e7961a515f6d7af9304e7fd1d257929aef26/docs/cordis-api/fiber.md)、[事件源码](https://github.com/deepseek-ai/deepseek-harness/blob/c291e7961a515f6d7af9304e7fd1d257929aef26/vendor/cordis/src/events.ts) | 会话观察订阅可以随会话实例释放；PF-003 允许继续的后台工作须有独立于该实例的受管执行 owner。 |
| 原始 `emit` 不等待监听器返回的 Promise；`parallel` 会等待被派发的监听器，但调用完成本身没有业务持久化含义。[事件源码](https://github.com/deepseek-ai/deepseek-harness/blob/c291e7961a515f6d7af9304e7fd1d257929aef26/vendor/cordis/src/events.ts) | 必需记录要有明确的写入确认及失败契约，不能只依赖一次事件广播。即使用 awaited 事件，也须验证必需记录者存在并兑现约定保证。 |
| DSH scope 是额外的注册／路由机制，仅使用其协议的接口获得对应隔离；作用域可见性不证明租户权限。[Scope README](https://github.com/deepseek-ai/deepseek-harness/blob/c291e7961a515f6d7af9304e7fd1d257929aef26/packages/core/scope/README.md) | 不能靠在事件上附一个 Session 对象或 scope key 完成授权。生产准入、读取、订阅、导出与模型消费各自检查适用权限。 |

最直接的生命周期反例：工具已转后台，原会话实例被回收。若生产者或唯一记录者跟随该实例销毁，工具将被误停或失去必需记录，违反 PF-003.C4/C6。因而“源自此 Session”的业务因果关系，不能自动成为“由此 Session 的临时实例负责释放”的所有权关系。

执行 owner 独立不意味着不受治理，也不要求首版另起进程。普通 Run 中断／取消仍按 PF-013 传播到其自有后台工具；`interrupt_then_run` 对后台工具有不同处置。运行时回收与人类显式停止必须辨认原因，不能只走同一个 dispose 开关。

## 职责与事实的唯一归属

以下是后续设计的建议分工；共享含义最终只定义一次，由公开契约引用。

| 责任 | 主责 | 交付给其他能力的内容 |
|---|---|---|
| 工具特有的阶段、进度、文本或媒体内容 | 工具实现提供者 | 符合当前声明的内容；工具自报进度不自动成为执行成功事实 |
| 单次调用身份、执行尝试／运行代际、来源校验、帧顺序与终态边界 | tool-execution | 可关联、可判断时效的执行观察协议，及明确的失败／未知状态 |
| 观察订阅、回放接续、披露资格及缺口语义 | tool-execution，使用相应授权能力 | 用户、会话和诊断消费者都能按各自权限消费同一事实；执行权不自动授予原始内容读取权 |
| 写入确认、读取位置、物理完整性、存储版本和故障结果 | 日志／存储能力 | 按消费契约提供可替换实现；帧语义及调用状态仍由 tool-execution 解释 |
| 记录分类、必须保留的范围与裁剪后果 | tool-execution 与观测／数据治理设计共同明确；存储提供者执行 | 哪些事实不可缺失，哪些过程内容可临时传输、摘要或到期删除；具体策略尚未选定 |
| Session／Run／Step 与调用的因果关联、会话历史投影 | 执行编排与 context-sessions | 原调用的稳定引用、来源及观察位置；转后台或换运行实例不改写发起关系 |
| 哪些帧、摘要或结果进入模型，以及实际送入内容的依据 | context-sessions／请求装配 | 模型可见记录及来源引用；模型侧内容不反向改写工具执行事实 |
| 用户实时展示、按需展开和诊断导出 | 各消费端及其受治理读面 | 表现层与传输实现；不从缺少新帧推断工具完成，也不因存在进度条推断成功 |

业务关联中应能区分适用的租户、调用、发起 Session／Run／Step，以及同一调用的执行尝试或运行代际。它们是待精确建模的语义维度，不是在此创建一套字段清单。提供者不得仅凭自报身份为其他调用追加权威记录；由 tool-execution 的准入边界约束允许生产的对象和范围。

同一帧被历史、UI 和诊断读取，不产生三份同义事实定义。派生摘要、脱敏视图、模型输入可以有不同表示，但须说明来源位置、遗漏和转换，不能冒充原帧。

## 依赖、装配与生命周期

### 服务消费关系

| 消费者 | 依赖及作用 | 不可混淆的关系 |
|---|---|---|
| 执行编排 | 使用 tool-execution 发起、观察和控制调用 | 业务发起方不是后台资源必须跟随的临时 owner |
| tool-execution | 使用当前合格的工具提供者；按记录等级依赖日志／存储与授权能力 | 不以某个会话运行时活着、某个 UI 正在订阅为执行前提 |
| 会话的工具观察／关联部分 | 使用工具观察契约消费当前状态，或从持久记录形成历史投影 | 历史读取不能要求具体工具实现仍装载、原 worker 或会话实例仍活着 |
| 上下文装配 | 消费获准的帧／结果／摘要及来源 | 消费记录不重新执行工具，内容也不提升为系统指令或授权 |
| UI、观测和导出 | 按各自读取范围消费观察接口及记录 | 单个观察者的存续不拥有执行工作；实际故障传播规则需分级 |

不要求整个 context-sessions 服务在启动时硬依赖所有工具提供者。哪些操作需要当前执行观察服务，哪些仅需持久记录，应分别声明。若互相注入导致两个服务都不能激活，应回到具体操作拆解依赖，不能用隐藏启动顺序遮盖依赖环。

日志／存储实现不依赖会话模型渲染或工具执行调度来完成一次合格的记录操作。它可以服务多种记录；是否共享通用承载、使用同一存储或按调用保留子流，留给后续设计。本稿不要求新增通用事件总线、独立 FrameService 或一帧一个插件。

### 运行所有权与动态变化

- 具体工具能力通过声明、实现、绑定参与装配；调用的有效提供者及可用操作必须可辨。后台生产者由能兑现后台生命周期的受管 owner 持有，会话侧仅持有允许的观察／控制关系。
- 观察监听器可以通过 Cordis effect／事件注册管理；持久身份、读取位置和权限依据不能只放在闭包、Context 或 Fiber uid 中。
- 工具实现、记录提供者、观察消费者分别可演化。准备卸载或替换时，需要明确受影响的在途调用采用保留旧绑定、排空、拒绝变更或经过验证的接管等哪种政策；本稿不预选一种，也不承诺任意热迁移。
- 卸载观察者不撤销已经保存的记录，也不成为用户中断命令。必需记录者失效应让相应记录保证的不可用显现，不能因为服务名称还在就宣称已可靠保存。
- 帧类型可以随获准工具能力演化；定义来源、格式版本和解释能力必须可辨。采用注册表还是由工具声明携带格式信息后定。类型定义／解码器的演进须保留已承诺历史的读取路径；暂时无法解释时明确报告，不静默显示为空。
- 普通过程内容不能自行声明调用已成功、恢复执行权或扩大读取权限。执行状态与控制不变量由 tool-execution 的受控操作维持，不随一个自定义帧类型或观测插件卸载而消失。
- 首版允许同机组合。未来跨节点时须显式传递身份、来源、顺序及确认信息；Cordis 事件和对象引用不自动成为远程消息协议。

## 从产生到记录、展示和模型消费

下述步骤是协调流程，不是已发布 API。尤其不把“产生、记录、用户看见、送给模型、模型理解”合并为一个状态。

1. **关联调用。** 执行编排提供可信的工作关联，tool-execution 按当前授权、工具版本和执行条件建立调用及其生产资格。
2. **接纳过程内容。** 提供者在该调用允许的生产范围内上报内容；tool-execution 处理来源、类型版本、顺序和当前执行权。需要区分迟到消息与新的执行尝试，不能让旧执行者覆盖终态或新执行者结果。迟到诊断是否另作记录须显式决定。
3. **兑现记录等级。** 对必须耐久的记录，等待相应持久确认后才声称已保存；写入成立但回执丢失时，重试须辨认原事实。允许先流式展示的内容标识其临时性，不能承诺已经可回放。具体分类及故障政策是待定项。
4. **通知消费者。** 实时通知帮助在线观察者及时取得信息。将必需记录者与可选展示监听器的失败责任分开：UI 离线不丢失已经确认的记录；必需记录失败不被广播成功掩盖。
5. **形成会话／模型投影。** 会话历史可关联原调用及过程记录位置。实际采用的帧、摘要或结果形成模型可见内容的依据；是否逐帧进入上下文、何时摘要、何时只保留可查询引用，由装配策略明确。
6. **重新关联。** 会话运行时重建后，在当前权限下找回原调用及可用读取位置，接续观察其现状和结果。帧缺口、过期、尚未持久化、读取失败与调用结果未知分别表达；重新订阅不得重新派发调用。

若过程内容含图片、音频或文件，临时路径不足以兑现媒体保留。需要持久交付的内容由相应附件／制品能力提供有效引用，并明确内容保存与帧／回复受理之间的成立条件、失败清理和保留义务；不假定 JSONL 一行天然保存了被引用的媒体。

顺序也需区分：单次调用内的顺序、多个调用的因果关系、日志存储位置和界面到达时间分别表达。单个调用的帧序号不能直接当作整个 Session 的顺序；具体合并视图和读取游标留给双方协商。

## 双方设计交接

以下按设计责任协调，不是实施派单；尚未定案的内容可继续标为候选，但依赖其保证的实施不得先假定成功。

| 设计方 | 本轮后续须给出的输入 | 对方据此才能确定的内容 |
|---|---|---|
| tool-execution | 调用及生产者身份、帧与状态／结果的区别、内容版本、顺序／去重／终态、观察与控制权限 | 会话关联、重建订阅、历史解释，以及精确控制后的呈现 |
| tool-execution | 前后台转换、执行 owner、旧执行权撤销、迟到结果与后台宿主失联的含义 | 会话回收和恢复不误停、不复活、不重复派发 |
| context-sessions／执行编排 | Session／Run／Step 关联、模型输入的实际提交位置、消费及摘要规则 | 过程生产方提供足够来源信息，避免把模型上下文视图当原始执行状态 |
| 日志／存储设计 | 写入确认、顺序范围、读取位置、幂等及故障结果、格式与引用义务 | 必需记录在哪里形成保证，如何读取原事实、如何识别缺口 |
| 工具、会话与治理设计共同 | 记录分类、披露与脱敏、容量／背压、保留／裁剪、删除关联、记录故障时的工作处置 | 可实现且一致的观察、存储和恢复承诺 |

必须共同收敛的事项：

- **记录等级及确认点**：哪些过程帧必须保存、哪些允许暂态展示；不能削弱关键生命周期和审计事实的完备性。
- **接续与游标**：进程内重新订阅、跨运行时恢复、存储到期后的读取分别保证什么；游标的位置、授权与有效期如何解释。
- **并发与故障**：多生产者、重复上报、迟到帧、强停、写入结果未知、存储不可用、消费者过慢分别如何反馈和收口。
- **生命周期交叉**：Session 归档／删除、原 Run 结束、后台工具仍活跃时，观察、记录、控制和保留义务如何继续；不能由存储清理或会话目录操作隐式杀工具。
- **动态演化**：工具及帧格式更新、提供者卸载、读写后端替换时，哪些历史可读、哪些调用可继续，无法满足时怎样拒绝或等待。

上述缺口不阻止先按责任分别探索；它们阻止声称已经具备完整耐久回放、无损恢复或可实施的正式协议。

## 与前期 DSH 复用调研的关系

- [工具执行调研](dsh-reuse-assessment-20260913/sections/tools-hitl/tools.md)在固定版本未发现满足 PF-003 的通用内部帧订阅／回放协议。现有调用身份、取消信号、结算与清理机制可作为 fork 起点；不能把普通 tool/result 或局部 PTC 审计直接当成完整过程帧能力。
- [Session 调研](dsh-reuse-assessment-20260913/sections/context-sessions/05-session-lifecycle-persistence-resume.md)提供追加记录、flush、JSONL 故障处理和格式演进的候选价值；它们不决定过程帧的业务归属，也不自动提供媒体保存、后台工作接管或本项目的控制保证。

具体 fork 内容、包闭包和后端选择后定。Cordis 官方包与其他选定 DSH 组件自有 fork 的维护边界沿 SYS-KERNEL，本稿不接受整套 DSH Loop 或本地 jobs 的生命周期。
