## 0. 框架是什么（一段话）

一套让任何 agent 从"一条新的产品要求"走到"Cordis 上可运行的能力变更"的统一方法，三层：
**心智模型**（需求空间的正交轴；能力基——每根基向量是一个拥有者，有耐久状态、提交边界与
不借别人词汇就能陈述的不变量；Cordis 平面是基的投影；一条要求对每根基向量只可能是七种
关系之一：组合、投影、拓展、换提供者、细分、新增、取代）；**流程与工件**（需求归位 → 对能力
基拆解 → 提案：每个决定点 ≥3 真候选 + 基线、同一把尺比较 → 架构设计与独立评审 → 决定 →
投影到 Cordis → spec 发版 → 提供者设计 → 反投影核对覆盖）；**不漏环节的硬件**（独立 skill
被三个相关 skill 前置加载；每个文档家族一份模板 + 检查清单；docs/ 与 spec/ 按能力基组织；
能机器核对的字段进 docs-check）。现有已正式化的内容按新结构迁一遍，作为框架的第一次真实使用。

## 1. 设计原则（决定后面所有取舍）

1. **权威不动。** 需求正文、决定、契约的权威地位与 D-001/D-002/D-004 的规则不变；框架只改
   "怎样到达那里"和"落在哪个目录"。
2. **门比措辞管用。** 调研结论：备选方案的兑现率只与"有没有会失败的检查"相关。凡能机器
   核对的（字段齐全、候选数量、每候选有成本与失败模式、否决理由存在、关系类型已填、链接可达）
   进 docs-check；靠人读的只留在检查清单里，并明确由评审角色核对。
3. **一个概念一份权威。** 心智模型正文只在架构指南一处；skill 是导航与硬性清单，不复述正文；
   模板不复制规范，只列必填节与每节回答的问题。
4. **候选便宜、证据昂贵。** ≥3 候选是陈述义务，不是原型义务；证据只对前一两名做。
5. **谁为论证负责。** 上游对 AI 代写提案要么禁止要么要求披露；本项目由裁决分层承担：作者
   裁决（agent）与用户裁决分列，每份提案写明哪些是 agent 自定、依据什么筛法、用户可否决。
6. **不为将来预留。** 只为当前三条线（需求→提案→决定→spec→提供者设计）建模板与检查；
   没有消费者的家族（例如评估协议）不动。

### 2.4 机器核对（docs-check 扩展，tools/spec-tools）

只加能稳定判定的规则，每条对应模板里一个字段：
- 提案：front matter 有 `basis_decomposition: true` 且正文含"## 对能力基分解"节；每个 `### 决定点` 下候选标题 ≥3 且有一个标 `（基线）`；每个候选子节含"成本""失败模式"两个小标题；`status: accepted` 时接受记录节存在且链接可解析到决定。
- 决定：`sources` 里的提案每个决定点在决定"选择"节里被引用（按锚点）。
- spec：每个已登记版本目录的 README 有"在能力基里的位置"节；契约差异表存在且来源列不含链接（沿 spec-check 规则）。
- 架构：`docs/architecture/capability-basis.md` 的行集合与 catalog 的 `accepted` 身份集合一致。
调研已确认"没有任何来源尝试检查候选是不是真的"——这一项留给评审清单，不做机器判定。

## 4. 不做的事

- 不建第二套需求或规格登记表；能力基地图是 catalog 的投影，不是新权威。
- 不给每个既有提案补造三个候选来"达标"；只重排既有候选并如实标注。
- 不做通用模板引擎、生成脚本；模板是 Markdown 正文。
- 不在这一波改任何契约条款或发新版。

## 5. 需要用户确认的点

1. §0 的理解是否准确（尤其"能力基地图是当前架构的一页、catalog 的投影"）。
2. "≥3 真候选 + 基线"作为提案硬门（docs-check 拒绝）而不是软建议——调研表明软的兑现率约四分之一。
3. 既有提案迁移时候选不足的处理：如实标注而不补造（§2.6）。
