# 从一条产品要求到一个 Cordis 插件：正交拆解与投影的路

提案附件（2026-09-15 作者思考稿，随本提案作为候选方法正文；未进指南）。目标读者：将来在这个仓库上拆需求、建模、
做架构的 agents。现有指南把这条路分段讲过：[总体范式](../../architecture-guide/foundations/paradigm.md)
讲"从目的到可演化的实现"，[需求推导性质](../../architecture-guide/assurance/invariants.md)
讲性质，[完整动作链](../../architecture-guide/reference/contract-description.md)
讲交接，[能力边界](../../architecture-guide/modeling/capabilities.md)
讲服务与插件，[装载效应](../../architecture-guide/runtime/lifecycle.md)
讲装卸。这份稿子把它们串成一条从头走到尾的路，重点放在两件事：**正交拆解**（把一条
要求拆成互不纠缠的轴）和**投影**（把语言无关的契约投到 Cordis 的插件、服务、Fiber 上，
而不是反过来）。

## 0. 先说心智：五条道

1. **需求说的是世界应有的结果与约束，不是机制。** 一条产品要求从不提插件；它说的是
   "谁、在什么时候、能观察到什么、什么永远不会发生、什么最终会发生"。拿到要求的第一步
   是把它改写成这种句子。一旦要求里出现"用一个队列""加一个状态"，那是作者在替设计说话，
   要退回去。
2. **系统是事实与拥有者的集合，不是调用的集合。** 每个概念只有一个权威定义、一个能在提交
   边界兑现它不变量的拥有者；其他地方都是投影或消费。设计时问"这条事实由谁写、在哪次提交
   里、和什么同批"，不问"哪个函数调用哪个函数"。
3. **一切都会装卸。** 完全动态系统里没有常驻件。设计任何对象时先回答：它不在的时候什么
   仍然为真、它被撤掉时谁接手、它留下的事实归谁。答不出来的设计不是设计。
4. **契约先于语言，Cordis 是投影。** 身份、不变量、状态转移用语言无关的契约表达；插件、
   服务键、Fiber、注入是把契约投到运行时的形状。同一契约可以有另一种投影（另一种语言、
   另一个进程），投影变了语义不变。反过来，从 Cordis 的 API 形状倒推领域语义，是最常见的
   走偏。
5. **复杂度是为不变量与真实变化付的钱。** 一个抽象要么隔离一处已经存在的变化，要么承载
   一条契约；否则不建。待裁决的事项先筛"是不是过度设计"，再从顶层建模自己定，只有真正的
   产品取舍才上交。

## 1. 流程：八步，每步有产出、有判据、有常见错误

### S1 需求归位

- 做什么：找到要求在需求正文里的条款（PF-xxx.Cn、SYS-xxx），把它改写成可观察陈述：
  "在 X 情形下，Y 观察到 Z；永远不 A；最终 B"。同时标出：已确认的、来源继承的、
  作者假设的、未知的。
- 产出：一张"条款 → 可观察陈述 → 确认状态"表。
- 判据：每条陈述都能指向一个观察者（用户、Agent、运维、另一个能力）。
- 常见错误：把机制写进需求；把来源系统的实现细节当成已确认要求；漏掉"不会发生"那一半。

### S2 正交拆轴

- 做什么：把每条可观察陈述投到独立的变化轴上。本仓库反复出现的轴有八根：
  身份与租户（谁）、权威状态与所有权（什么是真的、谁说了算）、生命周期与耐久（何时
  开始结束、崩溃后什么还在）、准入与授权（允许谁做什么、门在哪）、效应与可逆性（改了
  外部什么、能不能撤）、等待与进展（谁在等谁、最终会怎样）、观测与披露（谁必须看到、
  谁不能看到）、预算与时间（花多少、多久）。
- 正交的判据：**能不用另一根轴的词汇陈述这根轴的不变量。** "Run 完成当且仅当登记簿
  为空"不需要提租户；"跨租户默认拒绝"不需要提 Run 状态。做不到时有两种可能：这是一个
  真实的组合（那就要一份组合契约，逐行声明同提交与级联），或者是建模错了（把两个概念
  揉成了一个）。
- 产出：每根轴一句不变量，加一张交叉表标出哪些格子是真实组合。
- 常见错误：把"等待关系"散在三根轴上各写一遍（我们在 Run 上就犯过，后来合成了一个
  登记簿）；把 UI 的呈现需要当成一根轴（呈现是投影，不是轴）。

### S3 对能力基分解

这一步是整条路的枢纽，值得把三个空间分清：

| 空间 | 里面是什么 | 一条要求在这里是什么 | 地图 |
|---|---|---|---|
| 要求空间 | S2 的八根变化轴 | 一个向量：每根轴上"变不变、怎么变" | 需求正文 |
| 能力基 | 系统已定义的核心能力，每个是一个拥有者：一份耐久状态、一个提交边界、一组不借别人词汇就能陈述的不变量 | 一张分解表：对每个基向量，这条要求是什么**关系** | `spec/catalog.json` + 架构 README |
| Cordis 平面 | 插件、服务键、Fiber、注入、类型化事件 | 基向量的投影，按固定规则 | `cordis.md`、包设计 |

要求空间告诉你"变的是哪一类东西"，能力基告诉你"落在谁身上"，Cordis 平面告诉你
"运行时长什么样"。设计的创造性工作全在第二步；第三步应该接近机械。**如果第三步
需要发挥创意（一个能力非得拆成两个插件而且要同提交写），那是第二步错了。**

一条要求对每个基向量只可能是七种关系之一，每种关系的工件足迹、受影响者、证据范围
和运行时形状都是确定的：

| 关系 | 判据 | 工件足迹 | 受影响者 | 证据 | Cordis 形状 | 代价 |
|---|---|---|---|---|---|---|
| 组合 | 只用现有能力的操作与事实就能陈述，不动任何不变量 | 组合契约或装配说明 | 无 | 组合场景，必要时组合模型 | 组合者住在提交拥有者插件里 | 最低 |
| 投影 | 只在现有事实上开一个新读面或视图 | 消费者提案 + 提供者读面义务 | 提供者多一条只读义务 | 投影单测、场景 | 只 inject 读面的插件 | 低 |
| 拓展 | 某能力新增值、操作或事实，原不变量原样成立 | 该能力下一版；旧版不动 | 旧消费者不受影响，可选择迁移 | 只重跑该能力的性质 | 同服务键，方法/事件增加 | 中 |
| 换提供者 | 契约不变，实现换 | 提供者设计 + 撤回/换代政策 | 当前消费者按依赖变化政策处理 | 提供者符合性 | 同服务键，新插件；drain / reacquire | 中 |
| 细分 | 发现一个基向量其实是两根（不变量互相借词） | 新能力 v1 + 旧能力下一版 + 决定取代 | 旧消费者迁移 | 两份性质重推 | 拆插件或拆提交拥有者 | 高 |
| 新增 | 不变量无法用现有词汇陈述，且有自己的耐久状态与提交边界 | 新能力 v1 + 架构 README 行 | 新消费关系 | 全套 | 新插件 + 新服务键 + 事实流 | 高 |
| 取代 | 某能力的不变量本身要改 | 新版本 + 决定取代旧决定 + 迁移说明 | 所有消费者 | 全部重验 | 服务键可能不变，语义换代 | 最高 |

多根基向量同时被"取代"就是换基，只在决定层面发生，极少，要有可复现的强理由。

- 做什么：把 S2 的每条不变量投到能力基上，填分解表；每格写关系与理由。先试最便宜
  的、仍能守住不变量的关系——这是双向筛子：看似要新增的，先问是不是组合或拓展
  （过度设计）；看似小拓展的，先问原不变量是不是真的原样成立（压缩的复杂度）。
- 拥有者判据：谁能在**一次提交边界**里兑现不变量，谁就是拥有者；兑现不了的只是转发层。
- 共用的协议与契约在设计阶段先定一版。
- **基的健康信号**（分解表顺带给出）：一条要求同时"拓展"三个基向量、且要求它们同提交
  → 基缺一根，或者提交边界放错了；两个基向量总是一起变 → 它们其实是一根（等待关系
  曾散在 run、session、driver 三处，合成登记簿就是这个信号的处理）；一个基向量的不变量
  能从别的基向量推出 → 它是组合，不是能力。
- 基本身是受维护的对象：每次接受都更新 catalog 与架构 README 的投影表；投影是有损的
  （不变量、性质、证据不住在 Cordis 里），所以反向核对永远回到契约，不回到代码形状。
- 产出：分解表（基向量 × 关系 × 理由）、概念 → 权威 → 版本/缺口 的映射。
- 常见错误：因为缺一张映射表就升级整份规格；因为"只是框架细节"就绕过授权、所有权、
  失败或状态演化的变化；给已有概念在新包里另造一份定义；从 Cordis 形状倒推关系类型。

### S4 推导性质与保护点

- 做什么：从 S1 的陈述推安全性质（永远不）与进展性质（最终会），每条写明保护点
  （哪次提交、哪个门、哪个守卫）和证据种类（有限模型、规范场景、投影单测、负载单测）。
- 过度设计的筛子就在这一步：一个机制若不保护任何性质、也不隔离任何已存在的变化，
  就不建。反过来，一个短函数若掩盖了所有权、把取消/超时/部分完成压成一个布尔，那不是
  简单，是压缩的复杂度。
- 产出：性质表（编号、陈述、来源、保护点、证据）。
- 常见错误：从现有接口或测试反推需求；把偏好的机制写成既定不变量；把"模型检查通过"
  说成无条件证明。

### S5 沿完整动作链核对

- 做什么：从入口走到下一个稳定点，五条分支都走：正常、拒绝、失败、撤除、恢复。每次
  交接写明拥有者；效应按三种形状归位——派生与守卫、同提交共写、提交后反应。跨协调域
  的交接只能是第三种。
- 产出：动作链表（步骤、拥有者、事实、候选政策）。
- 常见错误：方法与类型齐全就以为交接闭合；失败分支交给"以后再说"；把跨域交接写成
  同提交。

### S6 投影到 Cordis

到这一步才选运行时形状。投影规则：

| 契约里的东西 | 投到运行时的形状 | 为什么 |
|---|---|---|
| 一个能力，有自己的耐久状态与提交边界 | 一个插件提供一个服务（`omneX`），契约的操作 = 服务方法，契约的事实 = 该流上的类型化事件 | 拥有者与提交边界一一对应，效应寿命 = 插件 Fiber |
| 一个组合，要求同提交共写 | 组合者住在**提交拥有者**的插件里（准入、Session），不另起插件 | 同提交只能在一个写面里完成 |
| 只读、只投影的消费者（消息流、目录读面） | 插件只 required inject 读面，不 inject 写面；依赖方向单向 | 让"它不能改事实"从依赖图上就看得出 |
| 政策（模型选择、工具集合、提示词） | 贡献 / 配置，在各自契约规定的工作边界重新解析 | 不为每个值变化重建实例（AR-9） |
| 机制（驱动、准入、存储） | 插件；变化走关实例 / 排空 / 换代 | 机制变化改变效应寿命 |
| 效应的寿命 | 作用域与 Fiber：根 / 租户 / Session / Agent；disposal 之后不能再有观察者 | 一切都会装卸 |
| 装载效应 | 成对写：贡献了什么、撤除时清理或交接什么、保留什么事实 | 卸载不等于回滚外部效果 |
| 依赖变化 | 两种触发分开：required 提供者撤回 → 插件整体退出活动；操作返回不可用 → 局部降级 | 消费者承诺不能含糊 |
| 将来的分布式 | 插件边界要能变成进程边界而不改领域语义：提交边界留在一个协调域内，跨域只走提交后反应 | 第一版单机，边界要为异构部署留好 |

- 产出：`cordis.md`——消费方式、能力侧要求、插件与服务键、装载效应与撤除、依赖变化
  政策、fork 演化路径。
- 常见错误：从 Cordis API 倒推语义；给转发层起服务键；把上游应用的策略当项目约定；
  为想象中的分布式预埋远程栈。

### S7 证据与登记

- 做什么：提案（候选、取舍、证据义务）→ 独立评审 → 接受决定 → 发布新版契约（不原地
  覆盖，登记 catalog 与冻结）→ 架构页收敛为投影 → 提供者设计修订 → 应用装配。
- 四层状态分开报告：语义接受、提供者可实施、装配明确、实际验证。不能合并成一个"完成"。
- 常见错误：借验证附件在冻结外另立规范；把评审通过当接受；把接受当实现。

### S8 反投影核对

- 做什么：从插件集合回到 S1 的可观察陈述，逐条问"哪个契约条款、哪份证据兑现了它"。
  兑现不了的登记为缺口，写明受影响消费者与闭合时点；不静默丢。
- 产出：需求覆盖表（条款 → 契约 → 证据 → 缺口）。

## 2. 两个走过的例子

**等待期间的排队用户输入**（PF-013.C5 的 2026-09-15 补充）。S1：Run 在等工具或等人时
用户又发了话，产品期望被自动消费，不干等。S2：轴上只有两根动了——等待与进展（Run
的空闲点）、权威状态（队列项被谁取走）；租户、授权、效应都不变。S3：拥有者都已存在
（session 的队列与取批、run-driver 的等待出边、run 的 basis），只需下一版扩展。S4：
性质是"不注入正在进行的调用""命令与 trigger 仍等 Run 结束""前台结果最终仍被消费"；
保护点是取批的同提交与 Step 收束判定。S5：入队 → 空闲点 → 取入既有 Run → 开一步 →
结果作接续回来。S6：**没有新插件**——Session 插件的取批组合者多一种形态，驱动器的唤醒
集合多一项。S7：模型加一个动作，场景一条，缺口表三行。S8：需求条款 → SE/RD/RN 下一版
→ TS-23 与 `RunSteer`。

**消息流**（帧、游标、派生消息）。S1：客户端看到一致的历史与实时；断线不丢、不重、
可追平。S2：轴很多——观测与披露（读权、不流出的东西）、耐久（事实 vs 瞬态）、等待与
进展（补齐最终追平）、身份（一个 Session 一条流）。S3：事实与广播已由 D-014 拥有；
消息模型缺一个权威，落到 CD 下一版与 session 的派生表；游标与补齐是新能力。S4：十三条
安全、三条进展性质，保护点分别在信封、投递侧、投影读面。S5：订阅建立、投递前、撤权、
投影不可用、来源消失五条分支。S6：一个**纯消费者插件**，只 inject 读面；MC 提供者多一个
读面义务；传输归应用装配。S7：有限模型两版，评审一轮八项阻断全按作者裁决改入。S8：
覆盖表在提案的 requirements.md。

## 3. 给未来 agents 的十问

拆需求、建模前把这十个问题写下来再动手：

1. 这条要求的可观察陈述是什么？观察者是谁？"永远不"那一半写了吗？
2. 它动了哪几根轴？每根轴的不变量能不用别的轴的词说出来吗？
3. 交叉的格子是真实组合还是建模错误？
4. 对能力基的分解表填了吗？每个基向量上是组合、投影、拓展、换提供者、细分、新增还是取代？选的是能守住不变量的最便宜关系吗？分解表有没有暴露基的病（同提交跨三根、两根总一起变、一根可由别根推出）？
5. 哪些性质是安全的、哪些是进展的？各自的保护点和证据是什么？
6. 五条分支（正常、拒绝、失败、撤除、恢复）每次交接的拥有者是谁？哪些交接必须同提交、哪些只能是提交后反应？
7. 投到 Cordis 上是插件、服务、组合者、贡献还是配置？效应住在哪个 Fiber？撤除时清理什么、交接什么、保留什么？
8. 它不在的时候什么仍然为真？required 依赖撤回和操作不可用分别怎么办？
9. 这条边界将来能变成进程边界吗？跨域的交接是不是都走了提交后反应？
10. 哪些决定是机制层的（自己定）、哪些是产品取舍（上交）？每个自定的决定写了理由与被排除的形状吗？
