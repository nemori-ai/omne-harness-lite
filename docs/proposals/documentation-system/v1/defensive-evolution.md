## 区分保证与辅助措施

模型能力提高，首先改变的是它需要多少辅助，不能据此推断系统语义、外部世界或所有环境限制已经改变。

| 内容 | 示例 | 如何演化 |
|---|---|---|
| 系统必须兑现的保证 | 租户隔离、授权、已承诺的提交与取消语义 | 由项目要求和版本化契约管理；模型升级不是撤销保证的依据 |
| 对保证的提醒和设计指导 | 不把外部发送当成可回滚，检查释放是否真正结束 | 可压缩、降为按需资料或交给可靠工具反馈；底层保证仍在 |
| 针对模型弱点的辅助 | 固定步骤、重复检查提醒、编辑次数触发重新考虑 | 按模型、任务、工具和上下文评估收益，可缩小范围或移除 |
| 特定环境的临时绕行 | 某版本工具的缺陷、平台限制、依赖兼容问题 | 按环境适用性和修复证据退出，不因模型更强就认定问题消失 |

同一条文字可能混合多类内容，需要先拆清楚。可以取消“每次都写完整十步计划”的要求，同时保留“明确目标和验收依据”的结果要求；两者不是同一保证。

用户明确的偏好与工作约束也不等同于模型缺陷。评测可显示执行某种偏好有代价，却不能因此自动取消用户要求。

## 经验从哪里来又归哪里

来源包括设计反例、实际 review 纠正、实现缺陷、事故、模型行为轨迹和工具故障。当前项目没有生产部署，可以从真实设计与研发记录开始，不要求先收集生产事故才能建立经验。

首先辨明问题属于系统缺陷、工具表达不清、环境故障、知识缺失还是模型行为偏差。同一条失败轨迹可能有多种原因，单次观察不能直接泛化成永久流程。

按经验的实际用途选择归属：

- 可以在操作边界确定判断的正确性要求，进入相应契约、实现检查和有意义的测试。
- 工具参数、返回信息或错误反馈诱发误解，优先修正工具契约与呈现。
- 有条件适用的缺陷识别经验，进入防御模式或相关专题。
- 具有独立复用价值的判断方法，进入相应 skill；不为每个错误新建 skill。
- 非显然、系统性且值得保留的故障机制，进入按需建立的 `docs/postmortems/`，链接由它促成的改变。
- 只属于当前任务的临时信息，留在任务记录；没有持续价值时可以删除。

一次严重且机制清楚的失败也可支持增加约束，不强制等多次复发；但必须保留它实际说明了什么。反过来，频繁出现的模式也可能只反映坏工具或重复样本，不自动证明需要更强提示。

## 一条模式需要保留什么

无需为每一条都写长表。短条目可以用几行交代，复杂条目再单独成页。最少需要知道：

| 信息 | 目的 |
|---|---|
| 规则与所保护结果 | 防止只有步骤、没有收益目标 |
| 缺陷证据与机制 | 区分实际经验、推断和未经验证的建议 |
| 适用范围与反例 | 避免局部教训被泛化为全局强制流程 |
| 契约/工具/检查的归属 | 不让指导文档另建一份系统语义 |
| 当前使用方式 | 常驻简述、按需参考、条件注入或已退出 |
| 复核条件及已有验证 | 模型、工具、环境、任务分布变化后能重新判断 |

“当前使用方式”与“知识是否仍然有效”分别表达。一条知识可以仍然正确，但不值得占用常驻上下文。已退出的提示也可能在某个旧模型或特定失败条件下仍有用。

## 怎样减少对更强模型的束缚

可采取的变化包括：压缩表达、合并同义条目、从常驻改为按需读取、按适用范围注入、由工具提供即时反馈、删除已经无收益的辅助、将历史理由归档。不是只有“继续强制”或“彻底遗忘”两种选择。

尤其应检查：一条规则是在描述目标和边界，还是把某次成功的具体执行步骤永久化。对能够自行组织工作的模型，固定过程可能增加重复阅读、无用计划、过度确认和重复测试；应以实际效果比较，而不是以规则遵守率越高越好。

更强模型不一定在所有任务、长上下文、工具组合或降级路径上更可靠。适用范围应绑定实测条件，不能简单写成“新模型都不需要这条”。未覆盖的模型或环境明确标为未验证，不把它们默认归入已退休范围，也不因此向所有模型重新注入全部旧规则。

暂不设计一个自动修改根 AGENTS 或正式系统契约的自学习服务。开发 agent 可以提出有证据的精简，在当前任务授权范围内调整普通指导；改变用户约束或系统保证仍按对应权威处理。模型自评“我不会再犯”只能作为研究线索。

## 用什么证据决定退出

**已有防御下长期不出错，不足以证明防御已无用。** 它可能一直在发挥作用。针对模型辅助，优先比较同等条件下保留、简化和移除三种方案，而非只看模型版本名称或距离上次故障的时间。

有用的比较应记录模型与可辨认版本、推理配置、harness/skill/工具版本、实际加载的指导、任务类别和环境。在代表性任务中观察实际产物、错误与副作用，并按随机性进行适当重复。开发 agent 的架构任务需要自己的样本，产品运行 agent 的对话或编码基准不能直接替代。

评价至少覆盖所保护的失败类别、相邻任务的回归，以及 token、时间、无用工具调用和人为干预等成本。不能只追求总分增加而掩盖严重类别退化；也不能为减少 token 删除必要的边界信息。根据风险和验证成本选择样本规模，不预设全项目统一次数或分数阈值。

调优样本与独立检验样本分开，并保留人工可以判断的证据。检查最终行为和产物，不把“文档仍包含这句警告”“agent 声称遵循规则”作为效果指标。工具消费的字段、结构与链接仍可用确定性校验，语义提示的具体措辞不宜被无理由冻结。

退出时记录：在什么范围停止哪种辅助、依据什么证据、替代机制是什么、哪些情况需要恢复或重新评估。删除的是指定范围内的使用方式，历史原因按价值保留。

回归样本也可以合并、降频或淘汰，防止评测成本单调增加。但要区分已经无区分度的昂贵模型行为样本和仍在保护系统正确性的必要检查。相同样本连续通过不是任意删除权限/租户等边界验证的理由。

模型升级、工具边界变化、故障复发、规则之间冲突或明显的执行负担都可触发复核。定期回顾只作为发现遗漏的补充；不按年龄自动断言知识已经错误。

## 现有文档需要怎样调整

现有[防御性研发模式](../../docs/defensive-patterns.md)将全部条目描述成需要长期保持的原则。建议改为可持续维护的当前指导，并补充归属、范围和证据链接；不把每一段原文都固化为不可变约束。

两处值得在迁移中专门澄清：

1. **“回调故障不能摧毁调度器”。** 面向独立观察者的故障隔离，与校验、授权或命令操作应当失败，是不同语义。不能把“捕获后继续”推成所有回调的通用规则。需要链接各交互契约的失败处理。
2. **“失败必须阻止假状态提交”。** 保留旧实例继续可用、恢复旧配置、停止服务和报告降级是不同保证。旧资源已结束或外部输出已发生时，不一定能恢复旧运行态。应保护真实报告和已承诺的提交规则，具体恢复政策由契约定义，避免绝对化承诺。

这两点是本次对既有文字的范围分析，并非宣布已经确定新的回调或重载政策。迁移时先核对其接受依据和对应规格；缺少设计的部分保持待决。

## 阅读与存储的组织建议

保留 `docs/defensive-patterns.md` 的稳定入口，把它维护成当前有效的简短原则和按问题导航。有真实内容增长时再按主题增设 `docs/defensive-patterns/` 页面；不预先拆出空的模式卡目录。

具体系统保证回到所属规格；事故故事进入按需创建的 postmortems；规则增删实验进入 research 的对应专题；值得保留的取舍进入 decisions。模式页通过证据和决定链接串联这些内容，不复制长日志或完整实验报告。

默认阅读只到与当前工作相关的模式。已经退出的条目从常驻提示、skill 路由和有效索引一并撤除或指向替代项；历史仍可按需检索。根 AGENTS 不随每次事故追加一条永久命令。

本页正式落点建议为 `docs/maintenance/defensive-evolution.md`。它规定如何判断规则资产的价值与去向，不要求本阶段实现新的运行时记忆系统或自动评测平台。
