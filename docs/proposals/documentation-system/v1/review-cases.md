## 代表性场景

以下是对组织方案的纸面检验，不是已经实现的系统测试，也不发布新的领域模型。

| 场景 | 按本方案处理 | 用来识别的问题 |
|---|---|---|
| 新增提示词渲染能力 | 先在提案内定义行为、动态变量来源和撤除规则，引用已接受数据；接受后按能力/数据的实际归属发布 | 没有因为写了 Schema 就自动批准 Profile、渲染器和注册表 |
| 两个能力使用相同租户身份 | 都引用同一数据契约；各自定义授权检查点和失败结果 | 不为每个服务复制 Tenant，也不把数据字段存在当作授权已经执行 |
| 上下文提供者卸载 | 消费者能力说明单次使用的绑定与撤除政策；跨能力联合切换的性质归组合契约 | 静态 `$ref` 和类型目录不能冒充活跃注册表 |
| 模型档案在某次工作开始时被选中 | 数据契约说明档案含义；管理、选择和发送行为各有明确归属，必要时定义组合约束 | 不将 LLMProfile 的持久化身份误当成整个请求或会话的事务边界 |
| 存储能力增加远程提供者 | 若旧承诺可兑现，保持能力契约并补实现符合性证据；若出现新的超时不确定性，先处理契约变化 | 包路径改变不是版本依据，消费者可观察含义才是 |
| 路由数据发布新版本 | 数据新版本独立登记；依赖旧版本的能力仍精确引用原版本，采用新版本时评估消费者和组合 | 不靠修改全局 current 自动改变所有消费者 |
| 数据 Schema 不变，但撤除时行为改变 | 能力契约及相关模型升版；不凭 Schema 相同判断兼容 | 行为版本不会被数据版本掩盖 |
| 一份提案只接受了静态提示词部分 | 接受记录明确范围，动态绑定等候选继续留在提案 | 不出现整份提案状态替局部决定背书 |
| 只修复导航链接 | 修改可变索引和入口，检查链接；若问题在冻结原件则记录勘误或新修订 | 不要求无关能力升版，也不破坏已发布快照 |
| 替换不变量检查器 | 不变量定义保持原归属；证据记录新检查器的覆盖、版本和观察缺口 | 实现替换或诊断关闭不会撤销规范约束 |
| 已接受规格 v1 尚未形成 TLA+ | 明确未形式化范围和已接受的文字语义；后来增加规范行为模型形成新修订并核对等义性 | “已接受”和“已完成行为建模”不会混为一谈 |
| 一个测试覆盖多项能力的整体安全性质 | 在组合的验证映射中关联各参与版本；各能力入口能找到该组合 | 不复制测试说明，也不把整体性质无条件归给单一参与者 |
| 研究证明某上游能力行为不同于旧假设 | 更新事实认识并标明受影响决定，提出必要复议；不直接把上游政策作为本项目新规则 | 事实可信度和政策权威不会混同 |
| 一份大提案只批准两个独立选择 | 提炼对应决定，原提案逐项记录去向，其余部分继续 review | 不把整份提案搬进 decisions 后默认全部生效 |
| 新模型在现有提示下长期不犯某种错 | 比较有无该辅助的行为，再按模型/任务范围精简、降层或退出 | 现有规则下的成功不被误读为删除规则的证据 |
| 搜索找到一份已退休的防御经验 | 入口标明状态和替代项，按需要读取历史，不重新注入成常驻要求 | 历史仍可追溯，常驻上下文不会单调膨胀 |

## 取舍与维护代价

| 选择 | 收益 | 代价及控制方式 |
|---|---|---|
| 能力、数据、组合三种归属 | 表达静态数据、独立行为与协作性质；承载动态系统而不预设 DDD 分类 | 需要判断规则归谁；通过单一权威和明确引用解决，不另建第四种万能目录 |
| 形式工件随契约保存 | review 一项能力时能就近看到行为、场景和缺口 | 按工具批量运行需要发现机制；先用清单、文件模式和现有工具，不建平台 |
| 数据契约集中、独立版本化 | 同义定义全系统复用，消费者按需采用版本 | 小文件与引用数量可能增长；只提取有独立含义的命名结构，匿名辅助结构就地保存 |
| 提案与有效规格分开 | 候选可以充分展开，机器清单和未来实现有可靠的接受边界 | 接受时需要晋升并更新引用；保留提案结果映射，不留下两份同时有效的定义 |
| 单一目录清单 | 身份、版本、状态和位置可检查 | 清单可能成为编辑热点；只存最小元数据，暂不分片或引入数据库 |
| 已发布快照不可覆盖 | 可精确 review、复现和追踪历史依据 | 产生少量重复版本文件；先使用 Git 与目录，避免为消除重复发明差量规格系统 |
| 当前架构保持可变视图 | 读者能快速了解当前整体设计 | 容易与契约漂移；涉及边界和采用版本的变更同步检查相关视图 |
| 旧 DDD 原件集中归档 | 保护未提交历史和原始语义，对照拆分是否丢失约束 | 暂时保留旧分类；从有效目录清单排除，并由归档入口标明用途 |

未来增长主要是新增独立契约与局部引用，无需先规划完整子系统树。能力数量多到影响索引阅读时，可以增加主题索引；物理目录是否分组以实际检索成本决定，不提前把服务拓扑写进稳定 ID。

最大的治理风险是把 `compositions/` 当杂物目录，或者把 `data/` 变成一套脱离行为的庞大模型库。前者要求每项组合有明确参与者与整体保证，后者要求每个数据概念有含义、使用者和变更归属。没有这些信息的候选应继续留在提案中。

另一项风险是“所有工件都要齐全”使简单能力难以落盘。因此目录树是容量设计：文件按内容出现，未完成验证如实记录，正式接受不由文件数量决定。

## 本版建议确认的选择

本版明确建议：

1. 保留 `spec/` 名称；以 `capabilities/`、`data/`、`compositions/` 作为有效规格入口。
2. 正式规格按语义归属聚合工件，提案和研究分别放入 `docs/`。
3. 已发布契约逐修订冻结，精确引用；单一目录清单维护身份、状态和当前指针。
4. 现有 DDD 定义先保护原件，再按数据与行为拆分归属；模型是否接受逐项保留真实依据。

这些决定只确定今后在哪里、以什么身份和维护规则描述系统。租户管理、模型目录、提示词、工具、Session/Run/Step 的具体服务切分、操作语义和数据内容，仍由各自设计讨论决定。
