# 文档与规格体系重构方案 · 第一版

状态：**proposed，供用户 review**。日期：2026-09-12。

本方案回应用户已经确认的方向：项目采用面向 Cordis 的动态能力组合与显式不变量建模，不再用 DDD 战术分类作为系统建模和目录组织的前提。本文提出目录、权威边界和维护规则，尚未执行现有内容的迁移，也不批准任何具体能力、服务边界或模型。

## 核心建议

保留现有根目录名 `spec/`，避免仅因单复数改名带来的工具与链接变更。`specs/` 若作为最终偏好，可以统一替换；本方案不同时保留两套入口。

正式规格按三个语义归属组织：

| 入口 | 定义什么 | 不意味着什么 |
|---|---|---|
| `spec/capabilities/` | 某项能力对消费者承诺的行为、边界、依赖和生命周期 | 一份契约必然对应一个插件、进程或微服务 |
| `spec/data/` | 可命名、可引用的数据含义、身份、取值和结构约束 | 数据都需要独立存储，或者需要一个运行实例 |
| `spec/compositions/` | 多项能力共同参与时的约束、装配要求和演化规则 | 再建一个通用编排器，或者集中接管各能力的状态 |

TLA+、Alloy、Schema、验收场景与追踪关系跟随其语义归属保存。工具类型是查找视图，不作为阅读一项能力时必须跨越的顶层分区。

`docs/` 保存设计指南、当前架构视图、决策理由、提案、研究和维护约定。待评审的规格附件留在提案内；正式规格通过明确接受后进入 `spec/` 的有效目录。

提案保留讨论范围，从中提炼经接受的最终决定；研究提供可核对的依据，不代替项目选择。防御模式持续维护，区分系统保证与针对模型弱点的辅助，让后者能够根据实测收益缩减、降为按需资料或退出。两者的详细规则见上述新增专题。

## 这次调整保留什么

- 一个概念只有一个权威定义；其他能力通过引用复用。
- 语言无关的契约、显式身份、状态权威、租户边界和不变量。
- 第一版单机交付，以及未来独立分布式部署时保持语义的要求。
- TLA+ 行为权威、Alloy 结构检查、JSON Schema 数据约束的分工。
- 已发布版本不可覆盖、已有提案需要 review、历史材料可追溯。

调整的是以 `domain/aggregate/entity/value-object/enum` 分类来决定设计归属的做法。记录仍然可以有身份，词表仍然可以是枚举，操作仍然需要一致性边界；这些性质在具体契约中表达。某个局部设计若确实需要聚合式一致性约束，可以说明理由后采用，它不再是所有能力的统一入口。

## 目标与完成标准

| 目标 | 可检查的完成标准 |
|---|---|
| 能按问题找到答案 | 从根入口经分组索引和契约入口即可定位定义，通常不超过三次导航 |
| 不会把建议当约定 | 提案、研究、已接受版本和历史材料在入口及引用中可区分 |
| 能完整阅读一个能力 | 契约入口直接关联所用数据、组合约束、模型、场景与验证缺口 |
| 能局部演进 | 变更能通过明确引用定位受影响方；无关能力无需同步升版 |
| 能跨实现复现 | 行为不依赖某种语言对象、目录形状或进程内调用方式 |
| 维护成本与规模相称 | 不强制空目录、每能力一份 ADR、全工具覆盖或重复登记同一字段 |

“规格已接受”“已有可运行形式模型”“模型检查通过”“实现符合规格”分别记录，不能相互代替。

## 实施边界

本轮交付只有这份提案包。后续迁移以本方案确认的结构为依据，保留现有语义和评审状态；发现缺少能力边界或存在语义矛盾时，将问题明确保留在提案中，不利用目录重构顺带作出业务决定。

本方案建议维护少量 Markdown 约定和一个规格目录清单，使用现有工具完成校验。无需引入文档平台、架构数据库、自制建模语言或通用工作流引擎。
