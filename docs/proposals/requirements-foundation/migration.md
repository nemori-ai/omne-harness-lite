`docs/system-goals.md` 在迁移完成后可暂留仅含导航的迁移入口，原锚点指向新正文；
同步所有项目内引用后删除入口也可。它不能继续保留一份目标正文。是否需要暂留，
根据外部已分享链接及工作中引用决定，属于文档导航维护。

## 建议推进顺序

1. 用户讨论并确认组织形态、权威关系、需求确认方式与历史引用方案。
2. 记录本方案的接受范围和治理决定；建立 requirements 入口，迁移当前已知目标
   与两项产品特性。拆分前后逐项比对用户明确内容、来源补充与未决项。
3. 同步规则、导航与相称的检查；核对全部旧 ID 和链接的去向。
4. 为现有候选设计标明需求依据与缺口，不伪造历史 决定 当时已经引用了新建的 ID。
   现有有效决定先做适用性核对；有实质变化时再记录取代。
5. 提交需求基线并建立、交付保留引用，核对开发分支清理后仍可从独立检出恢复。
   后续接受设计时固定其采用范围。继续用户逐项介绍的流程。

## 用当前内容检验这套方案

| 场景 | 预期结果 |
|---|---|
| 用户再介绍十项特性 | 在主维度新增独立条目，副维度加引用；已有正文不持续膨胀 |
| PF-002 同时影响环境、用户、智能体 | 环境维度拥有唯一正文，另两维只解释关联；三个位置不独立接受或修订同一要求 |
| 主维度调整或一项拆成两项 | 分类变化保持原 ID；语义拆分有新身份及旧条目去向，链接可追踪 |
| 原始环境感知要求已明确，来源补充包含更多条件 | 分别标明确认与来源映射；无法确认的条件不被整页接受标签掩盖 |
| 某个设计只接收新信息，却声称已经实现全部环境响应 | 需求覆盖审阅指出缺少发起响应和行为的对应；链接存在不等于覆盖完成 |
| 用户新要求与某个旧 决定 的具体前提冲突 | 标出受影响范围并暂停依赖冲突选择的新工作；保留旧记录，形成取代候选 |
| 需求变了，但旧规格与测试仍可通过 | 只能说明旧基线的符合性，不声称满足新目标；新承诺发布新版本 |
| omne-next 在已选基线后接受新承诺 | 作为待处理的需求变更输入；不从检索权限推定用户已经扩大继承授权 |
| 决定引用开发分支上的需求提交，交付采用 squash | 通过交付的保留引用保存原 commit；清理开发分支后，独立检出仍能恢复引用的正文与确认范围 |
| 完全动态原文有判定量词歧义 | 原件与时间线保持不变；目标页保留问题，依赖该量词的精确验收不定稿 |
| 只是修复既有文档的错别字 | 沿所属条目和链接检查完成，无需新增需求、决定 或整套接受流程 |
| 某项技术支撑没有独立前台功能 | 关联其服务的系统目标或全局约束，解释必要性；不编造产品特性 |

上述是方案的情景检验，不是已经运行的自动化或行为证明。接受后，文档检查验证
路径、身份与分类；迁移比对和独立评审验证原有语义与确认边界是否保留。只有修改
检查器行为时才增加相应工具测试。
