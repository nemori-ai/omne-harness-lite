# D-006 接受时的设计阶段边界

本页保留 A–F 的来源到目标差异及消费者验收门槛，供 D-006 选择追溯；具体阶段
状态不在这里维护。后续设计接受见 [D-007](../../decisions/D-007-runtime-composition.md)
与 [D-008](../../decisions/D-008-core-capabilities.md)，当前覆盖归[核心架构](../../architecture/core-capabilities.md)。

本计划以[源码集合](selection.md)为输入。完成本次范围决定后，先完成接口相关的
设计，再分别导入和开发；**选中包、设计接受、源码导入、目标实现验收是不同状态**。
现有 live-agent v1 已接受，但它的 Session 附着、授权、构造驱动和释放协作还需
相邻能力的具体接口；此前 dsh-agent 源基线不等于 v1 实现。

## Cordis 视角的共同边界

各专题首先列出：提供什么能力；在哪个 Context 中发布和解析；谁拥有贡献和资源；
必要/可选依赖的失效影响什么；新工作绑定哪一代实现；在途工作与退出如何收口。
用受管 service/plugin、依赖注入、事件和 scope 组合，不创建统一的 runtime-state
大对象，也不把业务事实塞进 Context、ALS 或可见性过滤器。

数据规格拥有身份和结构，能力规格拥有行为与状态转移，组合规格拥有跨能力的
整体性质。模型消息、附件引用、工具调用关联等同义数据只有一个权威定义；
模型供应商形状只是边界投影。Cordis 注入关系不代替授权、就绪检查或耐久交接。

## 设计工作及验收清单

下面是必须交付的设计工作，不是已接受的新接口名或完整施工规格。各工作须包含
目标与不变量、方案/取舍、来源到目标差异、精确数据/行为/组合规格、验证范围、
独立只读评审及接受记录；TLA+、Alloy、JSON Schema 按项目规格规则用于对应性质。

| 工作 | 范围与必要输入 | 进入源码/实现前的验收重点 |
|---|---|---|
| A：共同契约与内核映射 | 已接受 identity/live-agent v1；明确 scope 与调用上下文；Session/Run/Step/调用/内容引用的语义拥有者 | 不复制身份；租户权限、业务因果与资源所有权分离；具体 Session 附着与 factory/释放接口可被两端实现；共享数据不反向依赖 LLM 服务；改动既有发布契约须发布新版本 |
| B：Session、状态与持久化 | A 的共享契约；session、projection、persistence、JSONL 来源 | Session 生命周期与目录、append-only 事实、可变状态权威/投影、版本/恢复；受理与落盘的确认点；独占写入及未知失败保留；日志损坏/截断尾部可辨；恢复历史与恢复执行分开；JSONL 具体支持平台和耐久保证经验证 |
| C：**新工具系统架构** | [现有工具候选](../tool-system/v1/README.md)、PF-024/PF-014 澄清、A/B 相关接口、D-005 | 多命令单槽位及命令级参数/权限；必需 skill 的激活、贡献与撤回；调用/attempt 的耐久接纳和幂等；精确绑定、过程帧、取消与后台所有者；HITL 的待答、唯一答复和重检；与 Session/Run/模型接口对齐 |
| D：**新模型系统架构** | [模型历史候选](../model-contracts/README.md)、A 的内容契约、OpenRouter 强制出口、多模态及模型切换要求 | Cordis 模型服务与可替换提供者；所有用途请求包括压缩/标题/后台统一走 OpenRouter；当前租户/模型资格与预算准入；精确请求/adapter 绑定；能力判定、流式文本/媒体/工具交互、错误/重试/取消及费用归因；模型切换不追溯改写历史或在途请求 |
| E：Loop、Run 控制与上下文装配 | A–D 的可消费契约，agent-loop/system-prompt 来源 | Run/Step 的精确身份、状态权威、输入取批与 durable queue；`queue`、`interrupt`、`interrupt_then_run`、`resume`、`cancel`、`force_stop` 的差异；工具前台/后台传播与新输入整体意图；上下文快照、必需 skill 与工具集合一致、窗口预算/压缩和恢复后消费 |
| F：真实组合与首个应用装配 | 各专题已接受规格、实际实现和受限提供者；应用装配由项目编写 | 授权输入→耐久接纳→合法 OpenRouter 请求→真实工具→历史/状态落盘→停止与恢复接续；验证动态撤回、租户拒绝、旧目标控制和失败收口；假的模型/工具只支持局部测试，不作为产品闭环证据 |

范围决定并不接受 C/D/E 的完整设计。C 沿用草案可复用部分，但需要重新对齐当前
需求基线、D-005 和本批来源边界；草案中的 jobs 或环境包建议不因保存快照而生效。
D 不能仅把 endpoint 改成 OpenRouter：请求授权、能力与多模态映射、金额归因、
动态切换和失败边界都必须明确；具体 API/SDK 在设计时核对当时官方资料。

对 HITL、定义/设置与权限、资产/媒体存储、预算、独立执行所有者等相邻责任，必须
标明已有可消费契约或补齐所需最小设计及提供者。不需要为了本批一次完成整个
管理 UI/商业化系统，但涉及真实操作的权威不能空缺，不能用任意许可或内存等待
替代需求保证。第一条产品闭环的具体交付范围由 F 的实施计划明确，不能从本表
推定已经交付所有 PF-*。

## 依赖与可并行工作

先由 A 固定共享边界；B/C/D 可以在其各自必需接口接受后并行，交叉接口未决的
部分先协作设计，不能各自造同义契约。E 的独立控制模型可以提前设计，依赖的组合
必须在 B/C/D 接受后定稿。F 消费真实已验收实现。

每个能力在自己的设计通过后，可以进入本能力的导入和开发，不必等待全部专题
完成；依赖尚未实现时可用契约替身验证局部行为，最终组合验收必须覆盖真实两端。
涉及跨能力原子意图或恢复的语义须先形成共同规格，不能以“后端稍后补”放行。

## 每次导入与二次开发的交付

1. 固定上游 commit、文件来源、许可、保留/删除/替换列表、普通第三方版本与构建入口。
   对该切片保存语言无关的源设计基线，明确哪些是源事实、哪些是已接受目标，不能
   把上游观察伪装成产品规格。
2. 先在本地拥有源码，保存可复查原件或哈希、差异和有价值的源测试；不暴露尚未
   兑现目标契约的生产入口。新来源不得从依赖安装或生成代码中隐式进入。
3. 按已接受目标规格修改真正的语义拥有者；对与产品要求冲突的源行为，记录有
   因果说明的测试改动，不为保留源测试而继承旧政策。
4. 验证最终源码/声明/构建配置与 lockfile 的依赖闭包、公开入口及独立消费者；验证
   相应租户、生命周期、取消、动态依赖和持久恢复场景，再给出有范围的接受证据。

本次源码集合决定不改变现有 `spec/catalog.json` 或冻结版本。当前采用范围从上述决定与成员拥有者核对。
Session/tools/model 的正式设计；源码导入与实现沿逐阶段授权、评审和验收推进。
