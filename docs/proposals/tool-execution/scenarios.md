# 场景：调用生命周期的验收路径

[提案索引](README.md) · [生命周期](lifecycle.md) · [不变式](invariants.md) · [证据模型](evidence/README.md)

每个场景给出触发、期望的事实序列（事件 kind 按[转移表](lifecycle.md#转移表)）、
[ToolCall.tla](evidence/model/ToolCall.tla) 里对应的动作与性质，以及模型不覆盖、要由提供者
验收兑现的部分。编号 TS-xx，与 run-driver v2 的 S-xx 场景互不重号；提案接受后进入 tools
下一版的 scenarios。

| 编号 | 场景 | 期望事实序列 | 模型动作与性质 | 模型外验收 |
|---|---|---|---|---|
| TS-01 | 前台调用正常结算并接续 | `tools.call.proposed` → `tools.call.admitted`（AU allow、BG 预留、AR pin 同批）→ `execution.attempt.accepted` → `execution.attempt.dispatch_intent` → `execution.attempt.terminal` + `tools.call.settled{succeeded}` + `inbound.arrival.accepted{call_settlement}` 同批 → Run waiting → `inbound.arrival.classified{continuation}` → 下一 Step 的 tool_result | Propose / GateAllow(foreground) / Start / Dispatch / Terminal / Adjudicate / Consume；SettledDelivered、ConsumedOnce | 结果按 `outputSchema` 校验、`content` 引用已耐久（[schema.md](schema.md#结果形状)）；费用随 attempt 记 |
| TS-02 | 门 = ask，人批准后执行 | `tools.call.waiting` + `hd.request.created{system_approval}` → 批准 → `run.approval.consumed` + `tools.call.admitted` 同批 → 同 TS-01 | GateAsk / Approve；HumanByAnswer 不适用（tool 类）；AnswerOnce | 决定只被这次准入消费、新 attempt 不能重用（[T-9](invariants.md#调用)）；HD 决策池与超时不解除 |
| TS-03 | 门 = deny 或人拒绝 | `tools.call.settled{denied_before_execution}` + arrival 同批；无 attempt | GateDeny / Reject；AttemptAfterAdmission | tool_result 载明拒绝原因；hooks `PreToolUse` deny 走同一路径且不改参数（T-6） |
| TS-04 | stop 先于 start（墓碑） | admitted 后用户 stopCall → `tools.control.requested` + `execution.stop.fenced` + `tools.call.settled{cancelled_before_execution}` 同批；owner 迟到的 start 被拒 | StopRequest 于 admitted；NoStartAfterFence、FenceConsistent；否定变体 lateStart 证明去掉 owner 短门的 fence 检查即违反 | owner 短门把 start 与 fence 排在同一账本（TL-08） |
| TS-05 | 执行中 stop，真实结果先到 | `tools.control.requested` → owner 报 `execution.stop.progressed{quiescent}` → `tools.call.settled{interrupted}`；若 terminal 先到则结果为真实结局、`tools.control.progressed` 随后 | StopRequest 于 executing / StopProgress / Terminal；StopsProgress、SettledStable | `forced_isolation` 后的 `possible_effect` 标记；清理失败 retained（[T-3](invariants.md#调用)） |
| TS-06 | 手动或自动转后台，Run 收束，后台结算开新 Run | `tools.relation.detach_requested` → `tools.relation.detached` → 驱动器在该 tool_use 的 tool_result 位置写 `deferred_receipt{detached_background}`（若需开 Step）→ Run completed → 后台 `tools.call.settled` → `inbound.arrival.classified{queue}` → trigger 开新 Run，其首个 Step 的输入含 `system_reminder{late_result, ref: call}` | Detach / DetachConfirm / RunWake / RunComplete / Adjudicate（C 列）/ RunStart；TerminalRunOnlyBackground | 占位与迟到结果恰各一次（[T-14](invariants.md#调用)）；前台上限计时归 tools 包，三值记录到调用（TL-10）；`background` 声明协议装载核实；按模型族投影为 user / developer message 的单测 |
| TS-07 | detach 失败保持前台 | `tools.relation.detach_requested` → owner 拒绝 → 关系回 foreground 并报告；owner 崩溃中的 detach 同样回退 | DetachFail / OwnerRecover 的 rel 回退 | 单次失败原因具名；interrupt_then_run 下失败改为 stop（[级联表](lifecycle.md#控制与级联表)） |
| TS-08 | 执行 owner 崩溃 | accepted 无 dispatch_intent → 同 attemptId 重发 start，不建第二个 attempt；dispatch_intent 而 terminal 不明 → `tools.call.settled{unknown}`，之后只追加 `tools.call.resolved` | OwnerCrash / OwnerRecover；UnknownAfterDispatch | 费用暴露、inspect 核实、`resolution` 追加不改写（TL-07）；墓碑先于新 start 恢复（TL-08） |
| TS-09 | Run interrupt | 前台、转换中、后台调用全部 stop（PF-013.C4）；`human` 请求保留；resume 后 pending continuation 被消费 | RunInterrupt / RunResume / Consume；InterruptKeepsHuman、NoStaleContinuation | 全 Run 阻塞的显式 resume；后台调用被停的用户提示 |
| TS-10 | Run cancel | 所有 open 调用 stop 或 cancelled；`human` 请求关闭并结算 `cancelled_before_execution`；未消费输入 closed；cancel 后到达的结算按 D1 列 closed | RunCancel / Adjudicate（D1）；NoStaleContinuation、FenceConsistent | force_stop 的 epoch 撤销与 `run.late_fact.recorded` |
| TS-11 | 归档后后台调用继续 | Archive 不动任何调用；后台 terminal → arrival 受理 → `closed(closed_by_archive)`；结果引用按数据治理保留 | Archive / Adjudicate（D2）；ArchiveKeepsWork、ArchivedNoPending | 删除后的结果处置；恢复归档后不重开已关闭结算（政策 b） |
| TS-12 | `human ask_user`：答复作为工具返回值 | `tools.call.proposed` → allow：`tools.call.admitted` + `hd.request.created{question}` 同批 → 视图 `waiting_human`，Step 收束，Run waiting → 用户答复：`hd.decision.recorded` + `tools.call.settled{succeeded}` + arrival 同批 → continuation → 下一 Step 该 tool_use 的 tool_result = 答复；若等人期间已因其它输入开过 Step（tool_result 位置已放 `deferred_receipt{waiting_human}`），答复改以 `system_reminder{human_answer}` 进入到达的 Step | GateAllow(human_wait) / RunWait / Answer / Adjudicate / Consume；HumanByAnswer、HumanRequestsResolve | 崩溃后请求与调用均耐久、答复照常路由（RD-16）；迟到第二次答复按 HD-02 返回现状不生成 arrival；两种呈现恰居其一（T-14） |
| TS-13 | `human ask_user` 期间 interrupt | 请求保留，Run interrupted；答复仍可记录并结算，continuation 等 resume 后消费 | Answer 于 interrupted / RunResume（Conts ≠ {} → waiting）/ Consume；InterruptKeepsHuman | 用户界面区分"Run 已中断"与"问题仍开放" |
| TS-14 | `human request_approval` 后的动作调用 | `request_approval{action 描述}` → 用户 approve / reject / comment → 答复作为 tool_result 耐久进历史（本质是用户提示词）→ 模型据此提议真正的动作调用 → 该调用照常过 TL-07 门：AU allow 则执行，需要人类确认则系统发起 system_approval；答复不被门消费、不建立持续授权 | 不建模（提示层语义） | PF-005.C10 的可追溯 = 答复在历史里可查；越界时重新请求是 Agent 的提示纪律（omne-next HT-6 同）；[T-9](invariants.md#调用)、U-44 |
| TS-15 | 并行批（`parallel_safe`） | 两个前台调用同批准入并 start；先结算的 continuation 唤醒驱动器，驱动器发现另一调用未结算再次等待；写回按模型发出顺序 | 两调用的 Terminal / Consume / RunWait 交错；SettledDelivered | 首版驱动器可串行；写回顺序与合成结果（`cancelled_before_execution`）的验收 |
| TS-16 | 前台上限到点；同批混合 | `onLimit: detach` → TS-06；`onLimit: stop` → TS-05；`keep_waiting` → 无事件，Run 等到工具结束或用户 stop；同一 Step 三个调用分别声明三种 `onLimit`，各走各的；Step 在提议登记后已收束，下一 Step 缺省等仍开放的前台登记注销后再开（合批规则，作者裁决 9） | Detach / StopRequest 作为无标签触发；两调用交错 | 计时用单调执行时长、HITL 等待不计；有效阈值 = min(声明, 系统上限)（[T-11](invariants.md#调用)，U-45） |
| TS-17 | hooks `PostToolUse` block | 结果照常结算与消费；投影选择器把该结果以 `blocked_by_hook{reason}` 占位，耐久结果不变 | 不建模 | `hooks.run.completed` 记录；参数与结果不可改（T-6；[cordis.md](cordis.md#hooks-兼容层在工具站点的落点)） |
| TS-18 | Run 不可恢复失败时有未答问题与在途前台调用 | RD-13 收口 → failed：未准入的调用 `cancelled_before_execution`；在途前台调用与未答问题都保留，等待位置释放；调用结束或用户答复 → `inbound.arrival.classified{queue}` → trigger 开新 Run，首个 Step 以 `system_reminder{late_result \| human_answer}` 接上 | RunFail；FailKeepsHuman、TerminalRunOnlyBackground、NoStaleContinuation、HumanByAnswer | U-43；失败原因对用户可见，未答问题仍在决策池 |
| TS-19 | 用户对等人中的调用单次 stopCall | `tools.control.requested` + `hd.request.closed{withdrawn}` + `tools.call.settled{cancelled_before_execution}` 同批 → 该 tool_use 的 tool_result 或 `system_reminder` 说明问题已撤回 | StopRequest 于 human 调用（Cascade 的 Now 分支）；FenceConsistent、AnswerOnce | 撤回后迟到答复按 HD-02 返回现状 |
| TS-20 | 用新输入打断：前台可转后台调用、不可转调用、已后台调用、未答问题各一 | `queue.item.enqueued` + 复合意图 + `run.control.requested{interrupt, supersededByInput}` 同批 → 可转者 `tools.relation.detached`、不可转者 `tools.control.requested` + `execution.stop.fenced`、已后台者不动、问题保留 → 每个停止请求有物理事实（含 unknown）即收口完成：`run.state.changed{→ superseded}` + `run.epoch.closed{superseded}` + `run.wait.released{*, superseded}` + 旧 Run 未消费 continuation 改判 context + `inbound.arrival.accepted{system_notice: 被保留的工作清单}` 同批 → `queue.items.taken` + `run.lifecycle.created` + `run.step.opened{cutpoint: 新输入 + system_reminder{system_notice}}` + `inbound.context.advanced` → 被停调用结算 `interrupted`、转后台调用结算、用户答复：各自 `inbound.arrival.classified{context}` → 新 Run 下一 Step 的 `system_reminder{late_result \| human_answer}` | RunInterruptThenRun（`D` 为转后台集合；全部已提议调用 `rel` 置 background）/ Adjudicate（B 列）/ Consume；SupersedeReleasesPositions、SupersedeKeepsWork | 清单作为 context 到达、恰被下一个有模型 Step 的 Run 消费一次（作者裁决 4、12）；停止未知计入收口、清单注明、单调用 `stopCall{force}` 作升级（作者裁决 10）；`superseded` 终态不可 resume（[动作链 B3/B8](lifecycle.md#interrupt-与-interrupt_then_run-的动作链)） |
| TS-21 | 普通中断时执行方停止未知 | `run.control.requested{interrupt}` → `tools.control.requested` + `execution.stop.fenced` → owner 有界等待到期：`execution.stop.progressed{physical: unknown, cleanup: retained, effect: possible}` → `tools.control.progressed{unknown}` + `tools.call.settled{unknown}` → 收口完成：`run.state.changed{→ interrupted}` + `run.epoch.closed{interrupt}`；调用 `possibleEffect` 长期可见 → 用户 resume：不重试该调用；或用户 force_stop：Run 进 `stopping`，对该调用 `stopCall{force}`，owner 报 `isolated` 后 `cancelled(force_stopped)`（RN-05，作者裁决 10） | StopRequest / StopProgressUnknown（派发意图之后）/ 收口按 RunInterrupt 原子化；StopsProgress、FenceConsistent、UnknownAfterDispatch | 界面"停止未确认"与强停入口；没有系统级超时（作者裁决 2）；三轴词表（作者裁决 5）；force_stop 的 stopping 路径不建模，按 run-driver 场景验收 |
| TS-22 | 生图工具的产物 | 工具经 CT `retainReference{producedBy: {call, attempt}}` 取得引用 → 可选 `tools.frame.<kind>{media: true, render: image}`（过程）→ `tools.call.settled{succeeded, content: [image{MediaRef, delivery}]}` → 派生 `tool_result` 消息；客户端按 `mediaId` 去重，以结果块为准 | 不建模 | 未耐久引用不进 terminal 结果（T-12）；同一引用不双份呈现（T-16）；按制品身份检索归 PF-015 能力设计（作者裁决 6） |
| TS-23 | Run 等前台调用时用户追加普通文本（`queue`） | attempt 结算、C1 提议并登记 → Step 收束（作者裁决 9）、C1 前台执行中 → `run.state.changed{waiting}` → 用户 `queue.item.enqueued{text}` → 同提交 `queue.items.taken{into: R}` + `run.step.opened{cutpoint: [用户文本, deferred_receipt{C1, reason: foreground_pending}]}` + `run.state.changed{running}` → 模型回复（可能不提议调用）→ Step 收束、C1 登记仍开放 → `run.state.changed{waiting}` → C1 结算：`inbound.arrival.classified{continuation}` + `run.wait.released{C1, settled}` 同批 → `run.step.opened{cutpoint: [system_reminder{late_result, ref: C1}]}`（已占位，T-14）；若用户在 C1 结算就绪后又发文本，同一 Step 先带 C1 的 reminder 再带文本 | RunSteer（waiting → running，C1 仍 foreground）→ RunWait → Terminal(C1) → Adjudicate(A 列) → Consume；TerminalRunOnlyBackground、NoStaleContinuation | 取入既有 Run 的取批形态（SE-06 下一版）；切点里的占位投影与"接续先于文本"的合批顺序（作者裁决 7、9；模型不建模队列与优先级，驱动器单测验收）；队首是 command / trigger 时不取 |
