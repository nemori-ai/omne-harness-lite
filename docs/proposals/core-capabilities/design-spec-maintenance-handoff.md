# 架构设计、规格与 Cordis 实现映射的维护交接

本页交接本轮关于能力规格、Cordis 提供者设计及其长期维护的讨论，供另一个会话
完善架构设计、spec 撰写维护的最小流程、规范和配套 skills。它记录事实、问题和
建议，**不是已经接受的新维护规范，也不表示相关实现映射已经完成**。

事实核对基于 `design/dsh-core-adoption` 的 `4e67db6`：已同步 main `12855d2`
新增的 implementation-planning 指导；Agent/Session 受审稿固定于 `cd16f1`。
实施验证的后续观察核对到 HUB `46770b9`，对应 diagnostics 受审源码 `66d92a9`。
本页所说的“当前”指这次交接的状态，后续交付从相应入口核对。

## 用户要求与接收任务

用户连续提出以下问题，并明确最终的工作分工：

1. `spec/capabilities/` 有些能力只有 `contract.md`，这些文件与模型、数据定义
   如何分工，缺少其它文件是否意味着设计不完整？
2. 从 Cordis 视角，能力由一个或多个插件提供效用；service、dependencies、
   Fiber、作用域和生命周期应在哪里定义，是否属于 spec 管理范围？
3. 这些定义会随需求增加和变化持续演进，不能只留在本次施工计划；以后应在
   设计阶段形成闭环，现在先明确系统性的长期维护位置。
4. 最小设计流程、规格规范和配套技能由另一个会话统一设计。本会话提供讨论、
   具体缺口及其成因，不并行发布另一套规则。

接收方需要判断并落实：语义规格与具体实现映射的唯一归属、设计达到何种程度
可以进入对应实施、变更如何沿依赖传播，以及这些判断怎样进入已有规范与 skills。
不需要重新定义 Cordis 内核，也不需要为所有能力预建相同文档或模型模板。

## 已经澄清的概念

`spec/` 承载语言无关的精确承诺；`packages/core/work-data` 是这些共享数据的
TS 类型、实际校验及规范化实现，不能成为另一份语义权威。对旧 OMNE 的类比是：
`omne_harness/contracts` 对应这里的 spec；旧共享运行库
`libs/omne_harness_contracts` 更接近 work-data 的位置。

能力、包、service、plugin、Fiber 不一一对应：能力表达消费者可依赖的保证，
service 提供访问面，plugin 提供实现或注册贡献，Fiber 是插件的一次应用实例。
同一能力可以有多个提供者，一个包可以提供多个插件；纯数据/编解码包没有必要
为了外形统一变成插件。Fiber uid 不是持久业务身份，Context 可见性也不是租户授权。
上游概念核对采用固定 DSH 源码
`c291e7961a515f6d7af9304e7fd1d257929aef26` 的
[Primer](https://github.com/deepseek-ai/deepseek-harness/blob/c291e7961a515f6d7af9304e7fd1d257929aef26/docs/cordis-primer.md)
和 [Fiber 文档](https://github.com/deepseek-ai/deepseek-harness/blob/c291e7961a515f6d7af9304e7fd1d257929aef26/docs/cordis-api/fiber.md)；
实际项目内核采用官方 `@deepseek-ai/cordis@4.0.2`，源码研究版本与发行物身份分别记录。

只有 `contract.md` **本身不是缺陷**。现行规则要求能力入口、版本化契约及 catalog
登记；共享数据沿 `spec/data/` 复用，跨能力性质沿 `spec/compositions/` 表达。
是否增加 Schema、TLA+、Alloy 或规范场景，应由需要保护的性质决定。但没有模型
的条款不能被称为已做形式验证，已有模型也不自动覆盖整份能力契约。

## 已发现的缺口

| 缺口 | 当前状态与影响 |
|---|---|
| 具体 Cordis 提供者映射未完整固定 | 缺少可逐项查到的插件入口、service key、注入条件、解析范围、Context/Fiber 所有权及真实清理关系；不能让后续插件消费者自行猜测 |
| 从语义到运行装配的对应不完整 | 已有“必须排空/交接”的承诺，但尚不能对全部第一批能力回答谁关闭准入、谁跟踪在途工作、依赖突然消失由谁结算；具体工作仍待设计和实际验证 |
| 实现设计长期正文的归属不明确 | 具体接口和映射分散在专题提案/实施稿，规则没有明确接受后迁往哪里、以后由谁维护，容易让一次性施工稿承担长期权威 |
| 设计接受的范围没有充分区分 | “语义已接受”“接口可实施”“装配已固定”“真实行为通过”需要各自证据；整体完成措辞可能掩盖仍未交付的映射 |
| 形式与实现覆盖的发现入口不足 | 有覆盖记录，但从能力入口并不总能直接辨认哪些性质未建模、哪些组合未运行；不能靠文件数量判断覆盖 |

还出现过具体的跨能力交接遗漏，已经通过本轮独立评审关闭设计缺口：

- Agent/Session 初稿缺少 driver 正常返回/失败后的受限结算入口，原 Step 的
  接续身份也不完整。
- Session 只保留 DefinitionVersion，无法区分同版本的不同 acquisition 或移除后重选。
- Session owner 的设置写资格与 emergency_control 的边界没有接通 AU。
- TG 移除/停用选用所需的真实 SR 引用清单提供者未固定。
- 第一轮修订后仍遗漏 TL proposed → driver 交还 claim → 当前门直接 deny 的
  接续路径：若 continuation 只在 allow/ask 建立，直接拒绝可能遗留无人接续的 Step。

`cd16f1` 的最终独立只读复核确认 S-R1–S-R4 闭合；相关过程见
[评审](implementation/review.md#p2-agentsession-施工稿评审)与
[接受证据](implementation/evidence/session-runtime-design/README.md)。
S18 等场景仍待真实产品 TDD，不能将设计闭合写成恢复/零效果已验证。
这些反例表明问题不限于缺一张插件表，跨能力的完整动作链也需要在设计中检查。
具体服务键尚未固定并不必然意味着语义规格缺条款：应先核对现有契约是否已经
拥有所需保证。只有发现依赖失效、身份、所有权或状态演化等承诺本身不足时，
才按所属契约处理新版本；不能用一份实现映射表代替缺失的语义，也不能反向把
全部实现细节追加为语言无关规范。

另有一类问题需要与设计缺项分开：**设计已经要求，但实现或测量没有兑现**。
diagnostics 的独立只读评审在 `66d92a9` 找到六项问题，详见
[D1 实现评审](implementation/review.md#diagnostics-d1-实现评审)。HUB `46770b9`
已经通过现有完整产品检查、17 包隔离消费，以及另行真实文件/span 消费；六项
反例仍未关闭，D1 未接受。评审者没有执行这些新反例，实际 RED/GREEN 已交原
infrastructure-developer 处理，不能把源码分析表述为已发生的实测故障。

其中三个例子特别适合接收方判断流程应解决什么：

| 已有设计保证 | 实现/测量遗漏 | 对设计与验收衔接的启示 |
|---|---|---|
| 目录容量包含旧来源和未确认写入 | 各实例只核算自身；同目录新旧代可能复用余额，原检查不足以验证共同预算 | 保证的作用范围与责任拥有者要一致，单实例测试不能代表跨实例不变量；若现有实施接口缺少共同 owner，应先固定该选择 |
| 准备/关闭失败后原资源责任可查、可重试 | 写失败与关闭失败分别测试，但组合路径可能失去重试；旧文件扫描的清理责任也可能遗漏 | 按实际资源取得和责任转移选反例，覆盖相关失败的组合，不能只按异常名称各测一次 |
| 已结束关联句柄只保留不可变身份 | 活动 span 计数归零，仍可能经公开 context 保留 SDK span 与 runtime | 验证目标应是保留/释放的真实对象关系，内部计数只是其中一项观察 |

这些问题不支持“继续增加 contract.md 就能解决”的结论，也不要求穷举所有故障
组合。它们支持从受承诺的范围、资源和交接关系选择可否定错误实现的场景，并把
新增反例回填到验收与实际证据中。是否需要变更 spec，仍由语义承诺是否缺失决定。

## 缺口为什么会产生

以下分析基于可见材料和实际评审反例；它不是对历史 agent 内部推理的猜测。
本会话的调度与接受也有责任：没有把尚未固定的实施映射持续作为独立缺口显著呈现。

| 成因 | 可核对依据与因果关系 | 应交给规范/技能解决的问题 |
|---|---|---|
| 总体映射被当作足够的设计结果，具体映射的交付义务后移 | [原计划](plan.md)要求明确 Cordis 服务、贡献、依赖及事件映射，并写阶段 1–7 完成；组合设计又把具体服务键/exports 交给实施计划。两者之间没有一份完整对应产物来界定“完成到哪一层” | 设计完成结论必须标明层次与范围；关键映射的延后应有明确产物、拥有者及受影响消费者，不能被总体完成状态吞掉 |
| 语言无关语义与框架细节的边界处理不完整 | 正确地没有把 ctx/Fiber 对象塞进数据契约，但具体映射主要留在指南或施工稿，没有稳定的当前正文归属 | 语言无关不等于省略实现设计；既要维持语义独立，也要明确实现如何兑现以及对应文档在哪里维护 |
| 包布局和公共类型提供了局部进展，无法替代运行关系 | 已有职责包、公开入口、依赖无环和共享数据/记录实现，但这些检查不回答运行时服务何时可用、依赖消失如何影响工作 | 分清包依赖、Cordis 注入依赖、业务工作依赖，并检验它们的实际衔接 |
| 按能力分工后，跨边界“最后一段”没有完整走通 | SR/TL 直接 deny 反例中，各自已有合法状态与接口，组合仍可能遗留已交还 claim、无人接续的 Step | 评审要从真实触发走到正常、拒绝、失败、撤除、恢复等结果，找到每一步的状态与责任拥有者；不能只检查名词和方法齐全 |
| 检查证明的范围与设计充分性不同 | docs-check 明示只检查结构；有限模型有显式范围。它们无法自动检出缺失 service/Fiber 映射或未建模路径 | 验收依据分别报告结构、语义审阅、有限模型、公开产物和真实组合，不把某一道绿灯扩大为整体完成 |
| 一次交付的材料没有明确转入长期维护正文 | 现行组织规范规定 spec、研究、提案、决定与架构视图，却没有明确当前包级映射的稳定位置及变更交接 | 规定当前设计的唯一正文与导航，施工计划只保留交付安排，历史论证仍保留当时身份 |

因此不能简单归因为“contract.md 太少”“缺少更多模板”或“没有做审阅”。现有指南
已经提出多项正确原则，独立审阅也确实发现并关闭了交接问题。需要加强的是这些
原则怎样落实为可检查的设计输入、接受范围和持续维护责任，而非再复制一套原则。
在明确限定的范围内接受概念与语义设计，本身可以正确；现有
[共同边界视图](../../architecture/runtime-composition.md)也明确提醒归属完成不等于
施工接口齐备。本次观察支持的是后续映射的衔接责任未被系统固定，不能据此断言
某位作者忽视 Cordis，或已有评审越过了它当时的审查范围。

## 长期维护归属建议：待接收方统一决定

本轮建议沿现有语义归属细化，不增加第四种 spec 身份，不建立平行 catalog。

| 内容 | 建议的长期正文 |
|---|---|
| 共享数据含义与结构 | `spec/data/<数据>/vN/` |
| 能力的逻辑服务、操作、依赖条件、所有权、生命周期及失败承诺 | `spec/capabilities/<能力>/vN/contract.md` |
| 不能归属单一能力的交互协议与整体性质 | `spec/compositions/<组合>/vN/contract.md` |
| 提供包的 Cordis 插件、service key、inject、Context/Fiber/effect 映射及实现选择 | `packages/<领域>/<包>/design.md` |
| 应用实际提供者选择、配置接入、挂载、就绪及退出顺序 | `apps/<应用>/design.md` |
| 全局视图与发现入口 | `docs/architecture/runtime-composition.md`，链接正文并标出覆盖/缺口 |
| 上述归属及演进规则 | `docs/maintenance/organization.md`；其它入口按职责引用 |

区分标准应以承诺为准：例如“依赖撤除后不得接纳新工作、已有工作如何交接”归
spec；“哪个插件通过什么注入声明和 effect 顺序兑现它”归提供包设计。若服务键、
事件或公开接口本身已成为消费者承诺，还需管理所属接口版本与消费者迁移，不能
因为业务 spec 未变就当作任意内部修改。

包 README 和可变能力入口应能相互找到语义与提供者设计；应用再引用提供包。
准确的已实现 TS 签名引用公开源码，不在文档复制第二份独立接口定义。实现前的
候选接口必须可辨认，不能指向尚不存在的已发布 API。一个包不必按插件逐份建文档，
不要求纯函数包描述不存在的 Fiber；设计文件本身也不等于建立 workspace 成员。

## 建议收敛的最小闭环

设计阶段至少应能让下一位实施者回答：本次语义由谁负责，采用哪个精确契约；
服务由谁提供，在何种作用域和条件下取得；谁拥有工作与资源；何时就绪；依赖
缺失、替换、撤除、失败和恢复时怎样收口；哪些真实场景足以否定错误实现。
回答应落在各自拥有的正文，不要求另造一份重复所有材料的总表。

建议接收方将以下要求融入已有流程，而非追加固定流水线：

1. 需求/范围先明确，区分语义问题、实现选择及仍需研究的事实；成熟机制的证据
   可以复用，不以“先有完整 spec”为由阻止必要可行性研究。
2. 在相关实施开始前，受依赖的契约、提供者映射与组合责任应足够明确；遗漏
   阻止它的消费者，不阻止独立研究或已经固定输入的其它工作。
3. 形成设计后安排独立只读审阅，包含关键跨能力路径；评审结论和接受决定分开，
   设计接受与真实实现验证分开。
4. 多个消费者依赖同一未知机制时，先完成代表性共享实现与真实组合验证，再
   并行展开消费者；声明可编译或 mock 通过不能替代它。
5. 需求变更沿“精确契约 → 提供包设计 → 应用装配 → 测试/模型 → 交付记录”
   判断影响。语义变化按现有版本规则发布新规格；仅实现映射变化更新实现设计
   与相关验证，不机械升级所有 spec，不为局部修改重审全部架构。
6. 每次交付同步受影响正文、版本引用、导航、实际证据和剩余义务。保留历史
   提案/施工稿的固定修订，当前设计通过稳定入口维护，避免两个正文独立演化。

需要特别判断的是：哪些映射在架构设计时必须确定，哪些可在实施研究后固定，
以及后者如何限制“设计完成”的范围。用户要求的是依赖工作开始前闭环，不是
让所有未来细节预先定稿，也不是把框架默认行为当作产品政策。
