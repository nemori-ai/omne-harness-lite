# 验证、工具与证据

本页定义检查的边界：每个入口覆盖什么、**不能**据此声称什么。
命令的准确目标由根 [Makefile](../Makefile) 与 [scripts/check.sh](../scripts/check.sh) 维护，
实际参数与退出语义以各 CLI 的 `--help` 为准。

## 检查入口

组合入口 `make check` 调用 [scripts/check.sh](../scripts/check.sh)，依次执行下表前五项，
任一步失败即停止。该脚本也支持从其他工作目录通过绝对路径调用，供本地与 CI 共用。
整套检查占一个[运行名额](../scripts/README.md#运行名额)：同一台机器上已有一套在跑时，后来的排队等候，
等过最长时限则以 75 退出且**什么都没有执行**——那不是检查失败，也不是通过。

| 入口 | 覆盖 | **不能**声称 |
|---|---|---|
| `make agents-check` | 从 canonical 源与角色源重新计算产物，核对文件内容、权限及三个根相对软链接 | 宿主已发现配置、原生权限已生效或模型行为符合预期 |
| `make docs-check` | 跨仓库 Markdown 本地链接与锚点、Codex/Claude 技能镜像一致 | 内容正确、设计成立或因果理由充分 |
| `make design-check` | 设计链的身份、资源、引用、冻结登记与形式任务登记（`.meta_harness/design/`）；统一语言、领域对象条目与产品 topic 三家的对账——形态与条目一一对应、出处与依据的 rev 等于 topic 当前 rev、词条索引与分卷一致、派生总表是最新的；实现映射节点的形状对账——kind 与目录名及 `bindings.yaml` 一致、assembly 才有 `architecture.md`、源码位置与节点同名、交付面 PF 的 rev、技术栈采用的状态与依据链、契约坐标在 catalog 里、交付面仍是 draft 时不得登记绑定；故事卡的对账——卡号唯一且与所在 topic 一致、六个字段齐全、引用的验收场景存在、一条场景至多属于一张卡、前置不成环、演示每步写着应当看到什么 | 登记等于执行；`--formal registered` 只确认任务存在。对账通过**不代表**任何条目或节点的内容正确，也查不出「产品正文里冒出一个新对象却没人立词条」；节点通过**不代表**某条绑定的证据真能支持那条条款，也查不出一条应用间的边只写了一侧；故事卡对账通过**不代表**卡切得合适、演示照着做得出来，没有编号的场景它看不见 |
| `make test` | 仓库检查器、Meta Harness 编译/链接工具与 `design-subagents` 生成器的离线测试 | 宿主加载与模型行为已验证 |
| `make product-check` | TS/JS 格式与格式化适配器自测；全部 TS 成员的构建与类型检查（含 `*.spec-d.ts` 类型测试）；`packages/`、`apps/` 与 `tools/` 成员的 vitest 运行时测试（`examples/` 是阶段性演示，只构建与类型检查，它的测试不在这里跑，需要时进该成员目录单独跑）；测试这一步由[测试运行器](../tools/ts-checks/README_ZH.md#测试运行)按配置的并行度逐成员跑完，一个成员失败不拦其余的，结束时列全失败并写耗时账本——契约纯模块对 spec `examples.md` 的机检、Cordis 4.0.4 的 8 条 probe、存储一致性套件在 **sqlite** 上的 15 组用例、租约时钟的回拨与重启用例；`tools/ts-checks` 的结构规则扫描 `packages/`（条数与清单以 [tools/ts-checks](../tools/ts-checks/README.md) 的规则表为准），并核对当前提交可达的全部历史里[没有把 agent 列为作者的署名](../tools/ts-checks/README_ZH.md#提交署名) | 示例的测试通过——它们不在检查范围内；来源 trailer 已如实填写——署名检查只拦作者式署名，看不出哪些提交有 agent 参与；产品能力已端到端验证——tenancy 插件的包内场景已是真实测试，但装配 `apps/tenancy-host` 未建、跨包真实组合只到注册组合那一层；pg 方言未运行（缺 `OMNE_TEST_PG_URL` 时 `describe.skip`，**跳过不是通过**）；跨进程重启的持久证据、真实外键存在性（归装配）与端到端流程都不在其中；结构规则只看文本，不做类型分析 |
| `make test-affected BASE=<基线>` | **不在 `make check` 里。**取基线合并点到当前工作树（含未提交与未跟踪）的全部改动文件，按各成员 `package.json` 声明的 workspace 依赖算出「变更成员＋直接或间接依赖它们的成员」，先构建这些成员及其依赖，再只跑它们的测试并写耗时账本；根清单、锁文件、共享 tsconfig、`.meta_harness/design/spec/**` 等全局文件有改动时判为全部受影响。`PLAN=1` 只列范围不运行。见 [tools/ts-checks](../tools/ts-checks/README_ZH.md#测试运行) | 全量测试通过——没被选中的成员没有跑；范围只按声明的依赖与配置里的全局路径算，测试经别的途径读到的文件（未列入全局路径的夹具、环境）变了不会被选中；类型检查、格式与结构规则不在其中。合并前的结论仍以 `make check` 为准 |
| `make test-triage RUN=<运行目录>` | **只报告。**把那次运行里失败的用例逐个单独重跑若干次并归类：隔离仍失败、隔离时过时不过、隔离稳定通过、未能单独重跑；对「隔离稳定通过」的另把所在文件整个单独跑一次 | 「隔离稳定通过」等于机器或并行的问题——它只说明这条用例单独跑能过，原失败可能来自并行负载，也可能来自用例之间的相互影响或执行顺序，工具不区分；也**不等于可以放行**：贴着时限的用例要么修快、要么给出有依据的显式时限。当前代码与那次运行不同时，重跑结果不可比 |
| `make acceptance-lock BASE=<任务基线>` | **不在 `make check` 里。**各成员 `acceptance/` 目录（故事卡的可执行验收）自任务基线以来的净变化，以及这段范围里每一个碰过它的提交与其来源 trailer；碰过验收的提交 `Agent-Role` 不在拥有者角色里，或工作树里有未提交、未跟踪的验收改动，就退出 1。基线提交就是清单，不另存哈希。见 [tools/ts-checks](../tools/ts-checks/README_ZH.md#验收锁) | 没人改弱过验收——角色取自提交的人自己写的来源 trailer，把实施提交写成拥有者角色的它认不出，所以碰过验收的提交一律列出、由接受的人过目；验收写得对、被运行过、通过了——它只看谁动过文件 |
| `make formal-tools` | Java 与 `TLA2TOOLS_JAR`、`ALLOY_ANALYZER_JAR` 指向的实际 JAR 可用 | 任何模型已经跑过 |
| `make metrics` | **只报告，不判失败，不在 `make check` 里。**全部成员产品源码的每函数圈复杂度、成员间依赖边与分层方向（与 `lint:rules` 的 `group-direction` 同一份策略）、环；给 `BASE` 时标出基线以来变更的成员、函数、导入与提交形状；`COVERAGE=1` 时对 `packages/` 与 `apps/` 下的变更成员逐个跑测试取语句行覆盖并合成 CRAP（`examples/` 不跑）。产出摘要、数据与离线可开的审讯页，见 [tools/ts-checks](../tools/ts-checks/README_ZH.md#结构度量) | 覆盖率高或 CRAP 低等于行为正确——没有变异测试，断言强度未知；未见方向违规等于架构合理——层位是人定的策略，工具只核对方向；超阈值等于失败——它是抽查线索。覆盖率只计成员自己测试经 `src/` 或自己 `dist/` 执行到的源码，别的成员的测试与子进程里的执行不计；dist 早于源码时行号可能对不上；工作树不干净的产物不是任何提交的度量 |
| `make design-review` | **只报告，不判失败，不在 `make check` 里。**对 catalog 里的契约做八项确定性的机械核对：正文里没带坐标、本契约又没有的 `S-n`；分析阶段编号 `INV-`/`SAF-`/`LIV-`；candidate 契约「产品依据」写的 PF rev 落后于 topic 当前 rev（`FROZEN=1` 时连已接受的一起看）；catalog 依赖与 covers 指向的条款或产品小节不存在；版本目录里有不在 resources 里的文件；「# \| 写什么」定义表要求的项在「# \| 内容」操作表里缺行或为空；失败集合以「其他」「等」「etc」收尾。另给依赖图的环、稳定依赖不稳定（阈值在 `design-review.config.json`）与扇入扇出前几名。`CONTRACT` 限定逐份核对的坐标，依赖图始终算全图。结果分「成立的问题」与「未能判定」两节，写法不规则的一律归后者。见 [tooling](../.meta_harness/tooling/README.md#设计评审报告) | 报出的问题等于契约有错——每条只说明机械判据成立，由评审者逐条判断；没报出等于没有这类问题——写法不规则的、简称后的条款号、带坐标引用指向的条款是否存在都不在判据内；任何语义判断：一句话有没有两种读法、同名不同义、用词是不是统一语言的词条、状态词有没有混用、业务选择对不对、Schema 与正文在语义上是否一致 |
| `make role-eval ARGS="…"` | **不在 `make check` 里；它的子命令都不调用模型。**在常设用例集上做研发角色的行为评估，模型只由主会话派 subagent 来跑，子命令成对围着那一次派发：`prepare` 从角色源现编译定义、建一次性的工作副本（待审材料，或装好依赖的整仓检出）、写简报；`record` 收录宿主留下的 subagent 记录，核对简报、实际模型、副本有没有被动过、有没有够到真值，整仓检出一类还核对是从仓库之外的会话派发的；developer、qa 的流在 `record` 时由程序在副本上跑测试或读验收报告来判定；评审类的流由 `judge-brief`／`judge-record` 让判官 subagent 把报告判定成逐条结果，判官引的原句与所属发现由程序对着报告核；`calibrate-*` 让判官判一组有人工判定的报告并逐处比对；`summary`、`report` 算每个指标的均值与区间。`prepare` 在用例集当前版本的两次签字不全、受保护路径有未提交改动或材料 `verify` 不过时拒绝。没以报告收尾、实际模型与流里钉的不符、够到真值的尝试另记，不进结果。运行器自身的离线测试在 `make test` 里。见[运行器](../.meta_harness/agents/evaluation/harness/README.md)与[常设用例集](../.meta_harness/agents/evaluation/suites/README.md) | 角色在真实工作上的表现——用例是有限的几份材料，种入的缺陷比真实的更显眼；比该流说明里写的噪声范围更小的变化；Codex 一端的行为（只有 Claude Code 一端）；判官判得对——它的一致率只在校准用的那些报告上量过；subagent 没越界——它与主会话共用检出，核对只认得出记录里留了痕迹的越界；程序判定的流里完成声明与验收报告引的输出是否属实——程序只读测试结果与报告字段 |

**检查结论以本地跑的 `make check` 为准；远程 CI 目前关闭。**合并前在待合并的那个提交、干净的工作树上
跑一轮完整的 `make check`，交付说明写明提交、用时与结果。仓库里保留着一份只能手动触发的工作流，
恢复条件与做法见[自动化入口](../scripts/README.md#ci)；恢复之后它在全新检出上跑同一个 `make check` 再跑 `make metrics`，
**通过的含义同样不超过上表**：不带付费模型凭据，也不跑 `FORMAL=run`，度量步骤的成败不计入检查结论。

`make design-check` 的三个形式模式含义不同：`FORMAL=registered`（默认）只确认任务与工件已登记，
`FORMAL=skip` 记录本次明确跳过，**`FORMAL=run` 才真正调用 runner** 并传播缺工具、超时和非零退出。
前两种**都不是**模型已通过的证据。`GATE=release` 作为切换/冻结门，对任一 blocked relation、
unknown consumer 或缺 release evidence 的关系失败。

对账那两支默认把「rev 落后」判为失败：某个产品 topic 升了 rev，引用它的词条出处、对象条目依据
与实现映射节点的交付面就要逐条复核后才能把 rev 改到当前值。本地迭代时可用 `STALE=report`
（节点检查里 `warn` 是它的同义词）只列出待复核队列而不失败；**它不是通过的证据**，交付前仍须以默认模式通过。

> **留档区不在检查范围内。**`design_legacy/`、`research/legacy_backup/` 与 `agents/research/`
> 保持原件搬来时的相对链接——改写它们就会篡改「当初那份材料实际写了什么」。
> 单独封存的 Node 24 worker API 原文也按精确路径和 SHA-256 保留上游相对链接；
> 检查器拒绝该原文字节变化，周围研究说明仍接受本地导航检查。
> 各区入口说明了这一点。

## 环境与实际执行

自动化入口需要 Git、Bash、Make，以及 [uv](https://docs.astral.sh/uv/getting-started/installation/)
与根 `package.json` 指定的 Node/pnpm。`uv sync --locked` 依据锁文件准备 Python 3.12+
及 JSON Schema、Markdown、YAML 验证依赖，并以 editable 方式安装 workspace 工具包。
`make test` 的临时目录为 `tmp/test-runs/`，只用于本仓库测试。
测试运行器的耗时账本与各成员日志落**主检出**的 `tmp/test-ledger/<提交短号>[-dirty]/<时间>/`
（环境变量 `OMNE_TEST_LEDGER_HOME` 可改根目录）；工作树不干净的账本不是任何提交的账本。

形式工具链**装在系统全局路径**，不依赖任何仓库内的临时目录：

```text
/opt/java/jdk-21.0.12.1+1-jre      JRE
/opt/tlaplus/tla2tools.jar         TLA+ / TLC
/opt/alloy/alloy-6.2.0.jar         Alloy Analyzer（alloy.jar 指向它）
/usr/local/bin/{java,tlc,tla2sany,alloy}
```

`JAVA_HOME`、`JAVA_BIN`、`TLA2TOOLS_JAR`、`ALLOY_ANALYZER_JAR` 在 `/etc/environment`
与 `/etc/profile.d/tlaplus.sh` 中声明，**登录后的 session 自动继承**；
非登录 shell（某些 CI 步骤、`bash -c`）读不到 `/etc/environment` 之外的文件，
需要时显式传入。JAR 来自
[TLA+ 官方发行页](https://github.com/tlaplus/tlaplus/releases)与
[Alloy 官方发行页](https://github.com/AlloyTools/org.alloytools.alloy/releases)。

**环境存在不等于已验证。**`make formal-tools` 只报告工具可用，报告应记录工具版本与文件
SHA-256；当前环境是否安装、仓库是否定义了模型，是两个问题。

形式任务的命令登记在设计链的 `registry/formal-tasks.json`：唯一任务 ID、`tla|alloy`、
输入 `artifacts` 与参数数组 `command`，可声明 `timeout_seconds`。参数支持环境变量展开，
**未设置的变量导致失败，不经过 shell**。工具若用退出码 0 表示「找到反例」，
任务必须通过专属验证适配器把期望性质的失败映射为非零，
**不能只运行 GUI 或随意命令充当模型检查**。

正式版本新增 `.tla` 或 `.als` 却没有任务覆盖时检查失败；没有任何任务时明确报告
`UNCOVERED`，**不能宣称 TLA+/Alloy 已跑过**。

## 证据能支持什么

选择工具根据所需性质，**不把多种证据排成可互相替代的分数等级**。

| 证据 | 能支持的结论与必要边界 |
|---|---|
| 正确性论证或人工审阅的证明 | 说明命题、定义域、前提和推导；只有完整证明才报告为证明，草图与未闭合义务分别标明 |
| 模型检查 | 说明模型、实际探索范围、配置、被检性质及结果；**有限实例未发现反例不能扩展为任意规模或真实实现正确** |
| 机器检查的演绎证明 | 固定命题、证明工件、工具及依赖，实际检查通过；列出公理、环境假设、信任边界及未消解义务 |
| 实现符合性证据 | 固定实际包/fork、源码、配置、装配和环境，观察契约要求的结果；契约测试、故障注入及实机结果分别说明范围 |

检查器未执行、占位证明、跳过目标，或把目标本身当成未验证假设，**都不能报告该目标已经证明**。
实际失败和工具不支持也分别记录。

形式模型与实现之间要能解释：哪些状态和事件对应，哪些实现步骤被抽象成一个动作，
哪些环境或提供者行为被假定。行为的权威是所采用的 TLA+ 规格；
采用其他表示时说明映射，**不建立另一套相冲突的行为**。
没有精化证明时如实说明符合性由哪些场景或轨迹核对支持，**不把模型证明自动延伸到代码**。

可复用证据至少记录：契约与模型版本、源码 commit、工具与版本、命令或配置、
输入边界/假设和结果。通过、失败、不确定和未覆盖均须如实保留。
**有限测试或模型检查不能表述为无条件证明。**

## 分别表述这六种状态

尚未形式化、模型未覆盖、已声明但未执行、执行失败、有限范围通过，
以及实现尚未存在或真实组合未验证——**它们是六件事，不能合并成一个百分比**。

某个模型通过不能扩展为整份契约已验证；结构检查、语义审阅、有限模型、
公共产物消费和真实组合属于不同证据范围。记录后两者时固定实际发行物、
所消费接口及应用装配；**上游源码测试不自动代表实际采用的包**，
单组件和替身通过不代表跨能力动作链闭合。

实现、契约、装配或假设变化后，旧证据保留原范围并标出当前失效部分，
**不让新入口把过往结果投影为当前通过**。

## 交付时说明什么

保留失败的实际输出与影响判断，修正后运行受影响检查。
交付说明检查针对哪个源码状态、配置和范围；已有证据仍覆盖同一状态时可引用，
变化使其失效时补跑。临时日志放在 `tmp/`，清理工作树前保留任务需要的证据。
