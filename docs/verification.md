# 验证、工具与证据

本页定义检查的边界：每个入口覆盖什么、**不能**据此声称什么。
命令的准确目标由根 [package.json](../package.json) 的 `scripts`、[scripts/check.sh](../scripts/check.sh) 与 `scripts/` 下的入口脚本维护，
实际参数与退出语义以各 CLI 的 `--help` 为准。

静态检查排除任意层级中以`.legacy`结尾的目录，包括格式、文档遍历、源码规则及实际架构抽取。`no-legacy-dependency` 另外拦住 package.json、pnpm workspace 和源码重新引入这些目录或 `@omne-harness-lite/` 包名。文档里的标明字面值不在这条规则的扫描范围内。`pnpm run check`的按影响面、未知路径回退及`FULL=1`均不选择其中的类型检查、测试和验收。当前工具所需的workspace依赖可单独构建准备；显式封存来源核对继续按其拥有者承诺读取。准备与来源核对不构成封存实现的质量接受。当前成员内部的归档测试也从Vitest发现和类型检查根文件中排除。Python两条执行路径在收集前排除`.legacy`目录及其conftest。覆盖率度量保留成员原有排除配置，另外排除归档测试、源码和新鲜度输入。源码中的generated、tmp、dist或coverage目录不因名称而豁免后缀核对。TypeScript仍检查当前代码的显式导入依赖；不能通过排除导入诊断把当前错误变成成功。带归档输入但不能识别的检查脚本明确报错，不能声称已排除。文档体系及其开发工具的交付不以封存实现的全量构建、测试为验收门槛，也不能将未验证的封存实现写成已通过。新目标目录缺少源码或证据时，保留缺项与无法判定状态。已有验证结论在其源码、输入和适用条件未变时直接引用，不为重复收集相同结果重跑。`omne-loop-status` 的 `--strict --scope engineering` 是工程范围的严格模式：当前树和所有有效审计基线均无产品源码与测试时，仅 duplication 和 assertions 的原始 no-data 标为不适用，并保存计数依据。其余无数据与方向、环、验收锁仍失败，精确规则见[整洁回路](clean-loop.md#回路怎么转)。`pnpm run check` 的严格一步不传 `--scope`，保持默认门槛。`pnpm run check` 默认按影响面执行，全量设置`FULL=1`。

## 检查入口

合并前，在待合并的提交上计算好影响面，再运行受影响、因此需要执行的检查。共同硬线仍须核对。
交付说明记录基线、提交、范围、依据、结果与未覆盖范围。下面列的是命令的实际覆盖，不表示每次交付都须调用全部入口。

组合入口 `pnpm run check` 调用 [scripts/check.sh](../scripts/check.sh)：先算基线（`BASELINE`，没给用 `origin/main` 或 `main`）以来改动的**影响面**并打印计划，
再跑每次都跑的常驻检查与计划里的各步（下表 `pnpm run check` 一行），最后以严格模式跑一次回路状态（下表 `pnpm run loop:status` 一行），
任一步失败即停止。该脚本也支持从其他工作目录通过绝对路径调用，供本地与 CI 共用。
整套检查占一个[运行名额](../scripts/README.md#运行名额)：同一台机器上已有一套在跑时，后来的排队等候，
等过最长时限则以 75 退出且**什么都没有执行**——那不是检查失败，也不是通过。

正式 `Check` 工作流当前停用，合并前的检查结论以实际执行的本地候选证据为准。合并前在待合并的那个提交、干净的工作树上

**通过的含义同样不超过上表**：不带付费模型凭据，也不跑 `FORMAL=run`，度量步骤的成败不计入检查结论。

产品topic升rev后，词条出处与对象依据须逐条复核。局部迭代可用`pnpm run check:design --stale report`列待复核队列，但不是通过；交付使用默认对账。模型执行独立于导航检查，不由`pnpm run check:design`隐式运行。

## 环境与实际执行

自动化入口需要 Git、Bash，以及 [uv](https://docs.astral.sh/uv/getting-started/installation/)
与根 `package.json` 指定的 Node/pnpm。`uv sync --locked` 依据锁文件准备 Python 3.12+
及 JSON Schema、Markdown、YAML 验证依赖，并以 editable 方式安装 workspace 工具包。
`pnpm run test:python` 的临时目录为 `tmp/test-runs/`，只用于本仓库测试。
两个 TypeScript 工具套件的 Vitest setup、两个 Python 工具测试根的 pytest conftest，以及格式自测入口在创建 fixture 前隔离外来 OMNE root 和八项 Git 仓库定位变量。具体 Git 集合与 staged 例外见 [脚本环境边界](../scripts/README.md)。测试场景需要敌对环境时在被测入口显式注入，不能用 setup 净化后的普通调用证明生产隔离。`roleeval`、文档检查及 Cursor 来源和声明命令分别在本部署单元的进程边界保护显式目录；真实 Git 与本地命令替身不代表宿主模型或 Cloud 接受。
测试运行器的耗时账本与各成员日志落**执行工作树**的 `tmp/test-ledger/<提交短号>[-dirty]/<时间>/`
（环境变量 `OMNE_TEST_LEDGER_HOME` 可改根目录）；工作树不干净的账本不是任何提交的账本。

形式工具链**装在系统全局路径**，不依赖任何仓库内的临时目录：

```text
/opt/java/jdk-21.0.12.1+1-jre      JRE
/opt/tlaplus/tla2tools.jar         TLA+ / TLC
/opt/alloy/alloy-6.2.0.jar         Alloy Analyzer（alloy.jar 指向它）
/usr/local/bin/{java,tlc,tla2sany,alloy}
```

`JAVA_HOME`、`JAVA_BIN`、`TLA2TOOLS_JAR`、`ALLOY_ANALYZER_JAR` 在 `/etc/environment`
与 `/etc/profile.d/tlaplus.sh` 中声明，**登录后的 session 自动继承**；
非登录 shell（某些 CI 步骤、`bash -c`）读不到 `/etc/environment` 之外的文件，
需要时显式传入。JAR 来自
[TLA+ 官方发行页](https://github.com/tlaplus/tlaplus/releases)与
[Alloy 官方发行页](https://github.com/AlloyTools/org.alloytools.alloy/releases)。

**环境存在不等于已验证。**`pnpm run check:formal-tools` 只报告工具可用，报告应记录工具版本与文件
SHA-256；当前环境是否安装、仓库是否定义了模型，是两个问题。

模型、精确配置、命令及成立前提由实际成员的`models/`与`verification/`维护；系统未实现机制归相应architecture拥有者。每次执行记录输入摘要、工具版本、参数、预算、输出和判读，放本工作树`tmp/`。不设中央冻结或形式任务登记。

正控须识别工具的完成结论；负控须命中指定性质或反例，非零退出本身不算通过。Alloy的SAT/UNSAT与TLC的安全/时序反例按原配置判读，缺工具、超时、解析失败或未执行如实保留。工具环境存在、Schema通过或GUI打开不表示模型已执行，也不代替真实组合验证。

## 证据能支持什么

选择工具根据所需性质，**不把多种证据排成可互相替代的分数等级**。

| 证据 | 能支持的结论与必要边界 |
|---|---|
| 正确性论证或人工审阅的证明 | 说明命题、定义域、前提和推导；只有完整证明才报告为证明，草图与未闭合义务分别标明 |
| 模型检查 | 说明模型、实际探索范围、配置、被检性质及结果；**有限实例未发现反例不能扩展为任意规模或真实实现正确** |
| 机器检查的演绎证明 | 固定命题、证明工件、工具及依赖，实际检查通过；列出公理、环境假设、信任边界及未消解义务 |
| 实现符合性证据 | 固定实际包/fork、源码、配置、装配和环境，观察契约要求的结果；契约测试、故障注入及实机结果分别说明范围 |

检查器未执行、占位证明、跳过目标，或把目标本身当成未验证假设，**都不能报告该目标已经证明**。
实际失败和工具不支持也分别记录。

形式模型与实现之间要能解释：哪些状态和事件对应，哪些实现步骤被抽象成一个动作，
哪些环境或提供者行为被假定。行为的权威是所采用的 TLA+ 规格；
采用其他表示时说明映射，**不建立另一套相冲突的行为**。
没有精化证明时如实说明符合性由哪些场景或轨迹核对支持，**不把模型证明自动延伸到代码**。

可复用证据至少记录：契约与模型版本、源码 commit、工具与版本、命令或配置、
输入边界/假设和结果。通过、失败、不确定和未覆盖均须如实保留。
**有限测试或模型检查不能表述为无条件证明。**

## 分别表述这六种状态

尚未形式化、模型未覆盖、已声明但未执行、执行失败、有限范围通过，
以及实现尚未存在或真实组合未验证——**它们是六件事，不能合并成一个百分比**。

某个模型通过不能扩展为整份契约已验证；结构检查、语义审阅、有限模型、
公共产物消费和真实组合属于不同证据范围。记录后两者时固定实际发行物、
所消费接口及应用装配；**上游源码测试不自动代表实际采用的包**，
单组件和替身通过不代表跨能力动作链闭合。

实现、契约、装配或假设变化后，旧证据保留原范围并标出当前失效部分，
**不让新入口把过往结果投影为当前通过**。

## 交付时说明什么

保留失败的实际输出与影响判断，修正后运行受影响检查。
交付说明检查针对哪个源码状态、配置和范围；已有证据仍覆盖同一状态时可引用，
变化使其失效时补跑。临时日志放在 `tmp/`，清理工作树前保留任务需要的证据。

## 集成的两条基线

有 task context 的检查由[共同 loader](../tools/repo-toolchain/src/core/task-context.ts)取得 targetBase 与本任务的 taskBase/taskSource。影响面按 targetBase，验收锁按原任务从 taskBase 逐提交审计，并补 targetBase 到 HEAD 的改动；合法运输父保留其来源。显式给出的基线与 targetBase 不同时拒绝。没有 context 的检出以显式基线或 `origin/main` 为基线。全局 main 趋势仍按 main。targetBase 只由 task-sync 前进，见[工具指南](../tools/dev-flow/src/integration/README.md#同步目标分支)。

## 包级测试责任与边界

PanQiWei 于 2026-10-14 接受 [RFC-0005 revision 1](rfcs/RFC-0005-package-testing.md#决定范围)。本页是该决定的现行说明。

测试责任由包的公开承诺和实际职责决定。目录名、测试数量、是否起子进程、使用什么框架，都不决定责任。`fast` 和 `slow` 记录执行成本。单元、契约、集成、端到端记录责任和组合范围。`slow` 不等于端到端。`fast` 不能代替集成证据。

| 测试责任 | 默认承担者 | 应当证明什么 | 范围停在哪里 |
| --- | --- | --- | --- |
| 单元测试 | 原则上每个包 | 本包自身的规则、分支、状态变化、失败和适用边界 | 不为测本包逻辑启动无关系统。不反复验证下游包的内部实现 |
| 契约测试 | 原则上每个包 | 从公开入口观察输入、输出、拒绝、错误，以及本包承诺的所有权、生命周期和隔离。公开类型与运行时责任分别验证 | 以本包对消费者的承诺为边界。不依赖兄弟包的私有实现来证明契约 |
| 集成测试 | 实现具体存储或应用服务的包 | 本包与兑现承诺所必需的真实数据库、Worker、传输或其他依赖组合之后，事务、持久化、恢复、资源释放和失败传播是否成立 | 只组合该责任所需的参与者。纯定义和值包不因被服务消费而取得整套集成测试责任 |
| 端到端测试 | 明确拥有关键用户旅程的业务实现包 | 从该旅程的公开入口到可观察的业务结果，验证必要的关键协作和失败路径 | 只覆盖该拥有者负责的旅程和必要参与者。其他被调用的包不复制同一旅程 |

单元和契约是不同关注点。一次从公开入口运行的测试可以同时覆盖本包逻辑和契约。该测试必须能说明它验证了哪些承诺。

只发布类型、纯重导出，或其他确实没有某类行为的包，可以说明某项不适用。成员拥有者写明理由、替代证据和接受范围。没有运行时行为时，可以用类型消费测试验证公开类型。类型检查不能替代真实的运行时校验。空目录、空脚本、恒真断言或整套 skip 不能充当「都有测试」。也不为了填表制造没有断言对象的测试。

单元和契约测试使用包的公开入口和受控依赖。夹具由本包或明确的测试设施拥有。依赖替身保持公开契约。测试不穿透兄弟包的私有源码，不读取旧实现，也不共享旧产物。测试需要文件、数据库、端口、进程或时钟时，写明谁创建、谁释放、怎样隔离，以及失败后怎样清理。测试不依赖开发者已有的登录、真实 `OMNE_HOME`、工作目录里的偶然状态，或其他用例留下的数据。

测试结果不依赖快慢层怎样拆分，也不依赖文件并行。同一组测试分层跑、两层一起跑（`turbo run test`），或开着文件并行跑，结果必须相同。测试需要写构建产物或其他共享文件时，在自己创建的临时目录里写，并自己清理。测试不删除、不改写成员的 `dist/` 或其他测试会读的共享位置。反例：打包测试如果先删除再重建 `apps/cli/dist`，同时并行运行、经包名读取 `dist` 的测试就会随机失败。所以 `apps/cli` 的打包测试构建到临时目录，不碰 `apps/cli/dist`。这一条是上面隔离要求在运行编排上的具体要求，不是新的测试责任。

必须由真实组合才能证明的性质，在该集成或旅程的拥有者处验证。模拟数据库不证明事务或持久性。模拟容器不证明 Cordis 行为。普通进程退出不证明物理断电耐久。替身的通过范围写清楚。源码导入测试，与实际安装、exports、声明、bin 和构建产物的消费验证，分别承担责任。独立消费测试证明包能被单独消费。它不是业务端到端测试。CLI 的 help 或 version 子进程测试不是整套用户旅程。

跨包改动仍验证受影响的消费者。按影响面选择测试，表示本次运行哪些已经存在的责任。契约共用的符合性用例由契约拥有者维护。各提供者运行适用的部分。本页不改变已接受的安全、租户隔离、事务或生命周期保证，也不取消适用的故障注入和独立验证。

工具链发现并运行成员声明的测试。它不代替成员定义业务测试。生成器为草稿写出 `tests/public-entry.spec.ts`，从包名导入公开入口，并核对当前导出。它不生成集成目录、端到端目录或全系统启动脚本。集成入口和旅程入口的目录名尚未决定。

## 组合性质与证明义务

以下义务约束本次实际声明和消费的保证。复用已适用的证据，不为目录完整性新造模型。

### 从承诺界定性质

先说明消费者依赖什么，再选择允许的操作和状态表示。Context、服务键或 disposer
的存在本身不证明行为。Cordis 的机制与条件性结论按[采用来源](../.meta_harness/agents/skills/harness-design-handbook/canonical/references/cordis.md)确认；
项目需要兑现的具体含义仍由能力及组合契约拥有。

| 性质 | 需要说明的含义 |
|---|---|
| 局部可逆 | 在给定有效状态及操作条件下，所附逆操作恢复约定的观察 |
| 撤除正确 | 撤除本实例贡献，保留其他合法贡献和明确保留的事实；依赖使用按契约收口 |
| 释放或交接完成 | 资源或工作到达规定终态，或由明确的新所有者承接 |
| 可交换或互不干扰 | 指定操作族在允许条件和交错下，状态、结果、后续合法操作及撤除满足声明的关系 |
| 授权撤销、工作取消、业务补偿 | 分别由所属契约定义生效点、在途政策及完成条件，不以局部逆操作代替 |

观察关系由契约允许的消费者观察确定，包括必要的返回值、失败、顺序、权限与
后续行为。可以隐藏无业务意义的内部布局，不能为了证明成立而忽略既定的观察。
受控范围按实际访问、所有权和恢复能力划定，不按“内存/磁盘”或“经 Context
取得”直接划分；外部输出与已成立的业务事实沿所属协议保留或处理。

### 证据要求何时触发

逐项按本次声明及其用途判断，可以引用已有适用的证明和模型。下表针对需要
建立的事实，不要求所有提案具有相同附件。完成时点由[就绪范围](engineering/quality.md#区分四层就绪状态)
与本次消费者需要确定。

| 设计情形 | 所需证据义务 |
|---|---|
| 复用既有受控操作，未改变语义、表示和适用前提 | 核对精确契约、已有证据范围及使用映射；验证实际使用符合契约，不重复证明上游 |
| 自定义局部效应和清理，影响范围明确 | 给出前后条件、所有权、保留范围和正确性论证；实现阶段覆盖相关部分失败、重入/并发及清理结果 |
| 新增共享操作，以其可逆、可交换或互不干扰性质支撑跨组件组合 | 必须给出覆盖所声明操作族和范围的形式化证明；复用定理时补足前提成立的论证 |
| 自定义并发装卸、共享资源交接、代际替换或恢复协议 | 需要相应行为模型及关键性质检查；复用已有完整契约和适用证据可引用。声称已建立检查边界外的结论，或机制选择依赖这种推广时，需相应证明 |
| 依赖上述性质省略或放宽顺序、隔离、排空或冲突检查等控制 | 必须证明所依赖性质及省略/放宽控制后仍保留目标保证；首次设计即省略与取消既有控制同样适用 |
| 外部输出或已经确认不可逆的效果 | 明确不可逆边界、结果不确定性及业务撤销/补偿/恢复协议；按实际协议验证，不构造虚假的逆操作 |

多项适用时分别履行相关义务，不用一项通过替代另一项。对顺序敏感的操作可
明确依赖、限制允许的交错或选用其他满足需求的机制；必须验证实际采用的政策，
串行执行本身不证明撤除能保留后续合法变化。

当需要待设计系统新建立的共享代数保证承载租户隔离、唯一写入权、安全撤除等系统
关键保证，且以其为依据省略或放宽控制约束时，所依赖的证明须经机器检查。
这包括首次设计即省略控制，以及复用原语后改变表示、操作语义或放宽证明前提。
已有证明可复用，但必须满足本次所需级别并补足适用性论证，不能通过改称“复用”
改变门槛。关键性根据所保护
的需求、不变量和失效后果说明，不由包名或角色名判断。其他必须证明的情形可
采用有明确形式命题、完整推导及独立审阅的证明；若声称机器检查通过，必须有
相应实际结果。此处不指定新证明工具或替换 TLA+ 的行为权威地位。

契约中的全称要求是规范目标，不自动是已证明结论，也不单独触发上述新增门槛。
可以接受要求或语义范围并保留未验证状态；依赖强制证明的具体机制选择另行
判断，不能借“接受语义”同时放行它。

不能通过省略性质名称逃避义务：只要方案的成立依赖该性质，就应说明并提供
证据。未触发强制证明仍需相称验证；工具未具备、时间不足或模型能力强都不
消解已触发义务。探索性候选可保留待完成项，不将它们当作可直接消费的保证。

### 命题与前提的责任

证明需要能辨认所量化的状态、参与者、操作和配置范围，操作的定义域、观察
关系、失败模型及进展所需的公平性或终止前提。先定义目标性质，不能将它本身
写成未受约束假设，再以模型检查通过宣称已经兑现。

局部逆关系可写作 `undo_e(apply_e(s)) ≈ s`，但该式只覆盖定义中的条件。允许
其他组件在建立与撤除之间活动时，还需论证其他合法贡献得到保留。交换性不能
只看最终容器相同：必要时包含前向及逆操作、返回结果、可执行条件，以及后续
操作或继续执行选择。停止请求与静止、逆序调用与异步完成顺序分别按实际契约
表达。重复清理的调用协议需明确，不一概要求数学逆操作本身幂等。

服务提供者拥有受控接口和表示方式所承诺的性质；消费者负责满足自身调用及
生命周期条件；装配负责实际依赖与作用域；无法由系统兑现的部分保留为环境
假设。一方的假设由另一方提供时，引用其精确保证和证据；循环地互相假定不能
代替证明，循环依赖的性质需要整体论证或先建立独立成立的前提。

区分前提由哪个操作强制、由协议保证、仅被检查器观察或仍未经验证。声明式
接口不能限制绕过它的任意代码；受控 API 的行为证据和宿主执行权限证据分别
取得，不把提示词、Context 可见性或测试环境隔离当作生产安全边界。

### 共享贡献的最小例子

假设一个注册能力的消费者只依赖每个实例各自的条目。A 建立 `a`，B 随后建立
`b`，撤除 A 应保留 `b`。若 A 的逆操作恢复整个旧表，B 的合法贡献会丢失。
按独立注册身份撤除自身条目，可以把关键正确性责任集中到注册能力提供者；
是否需要代际、唯一令牌等表示，由实际身份及旧引用契约决定。

这个例子适合验证“保留他方贡献”，不能自动证明所有注册接口可交换。若条目
顺序决定请求处理，或注册返回值使两个顺序可区分，就需进一步建模观察和顺序
政策。不能借例子接受产品的接口形状，也无需为纯计算组件建立空 effect。

### 把设计义务交给实现

如果模型将清理抽象为原子地移除全部所属资源，组合结论以该抽象成立为前提；
实际 disposer、后台任务和后端必须有对应证据。若所声称保证覆盖清理失败、
挂起或残留，就应在合适层次描述这些行为，不能用理想清理动作遮蔽它们。

按风险从契约导出测试：部分取得资源后失败；两个实例交错建立/撤除；旧清理
晚于新实例发布；清理异常或依赖消失；退出后的晚到结果；外部效果成功但回执
丢失。观察真实资源、权威状态或消费者行为，不能仅断言回调被调用。

共享验证设施应能识别代表性错误，例如空清理、恢复整个旧快照或误删他方贡献。
这可以用少量负例核对测量有效性，不要求所有组件运行统一突变测试。具体版本、
环境、实际结果及局限按[证明与实现证据](#证明与实现证据)记录；
改变表示、调用约束或环境时沿[证据适用范围](#证据能支持什么)重新判断证据适用性。

## 规格的分工

| 表达 | 主要用途 | 不能单独说明什么 |
|---|---|---|
| 概念与契约文档 | 统一词汇、身份、边界、操作含义，引用设计理由 | 全部并发执行都满足性质 |
| JSON Schema | 约束交换/保存的数据形状并引用共享定义 | 跨请求权限、生命周期与最终进展 |
| Alloy | 表达结构关系，在给定范围查找反例 | 任意规模成立或真实运行必然终止 |
| TLA+ | 行为权威规格：状态变化、并发与时序性质 | 被省略的环境与实现细节自然正确 |
| 规范验收场景 | 明确消费者可观察结果，约束不同实现 | 全部状态空间的穷尽证明 |

按需要保护的性质选表达，各工件指向同一语义；不为填满目录制造平行模型。
只有 contract.md 不自动是缺陷，有模型也不自动覆盖完整；达到什么形式化与证据门槛，
由实际承诺和[组合性质](#组合性质与证明义务)判断。

## 证据与追溯

性质从[性质核对](../.meta_harness/agents/skills/harness-design-handbook/canonical/references/properties.md)，证据须能追到规则、模型假设、
实现边界与消费者观察。全称要求表达规范目标，不自动表示已证明。
生成代码、共享测试和相同接口有各自价值，均不单独证明行为等价。

优先观察真实边界：撤除后资源是否消失、失败后状态是什么、受保护访问是否被拒绝、外部写入是否发生。
多个提供者使用共同契约场景，并覆盖影响保证的失败与交错；只检查 mock 次数或成功文字可能漏掉实际结果。
测试预期由契约导出，fixture 不能补造缺失行为。

## 证明与实现证据

| 需要对应 | 留下什么 |
|---|---|
| 采用对象 | 精确契约、实现/发行物修订，以及证明或模型输入 |
| 抽象状态 | 模型变量对应哪些权威状态与可观察事实 |
| 抽象动作 | 由哪些实现步骤兑现，提交/观察点在哪里 |
| 前提责任 | 谁强制、谁以契约保证、什么仅被诊断、什么仍是假设 |
| 省略部分 | 未建模的失败、并发与资源行为由哪项证据或待办承接 |
| 实际执行 | 工具、配置、环境、结果、覆盖范围与局限 |

模型把清理视为原子成功动作时，提供者仍需兑现这个抽象；
承诺覆盖清理失败、挂起或残留时，应在相应层次建模，不能把目标性质自身无约束地当作前提。
一方假设由另一方承担时引用精确保证，循环互相假定不能闭合整体证明。

## 变更与验证范围

有限模型未找到反例，只支持已建模且已执行的范围；运行时检查只支持实际观察的关系；
机器检查证明需有命题、前提与真实工具结果。各类证据不能跨范围互相冒充。

表示、调用方式、观察关系或环境改变时，重新判断哪些旧证据仍适用，方法见[变更与维护](maintenance.md#修改与迁移)。
出现反例时先区分实现违约、规格遗漏、模型抽象错误、环境前提变化和新要求，再修正对应拥有者；旧证据只保留其原有范围。
只改局部表达时做相称检查；相关检查通过且没有新疑点后停止，不用重复无关验证增加信心。
