# 验证、工具与证据

本页定义检查的边界：每个入口覆盖什么、**不能**据此声称什么。
命令的准确目标由根 [Makefile](../Makefile) 与 [scripts/check.sh](../scripts/check.sh) 维护，
实际参数与退出语义以各 CLI 的 `--help` 为准。

静态检查排除任意层级中以`.legacy`结尾的目录，包括格式、文档遍历、源码规则及实际架构抽取。`make check`的按影响面、未知路径回退及`FULL=1`均不选择其中的类型检查、测试和验收。当前工具所需的workspace依赖可单独构建准备；显式封存来源核对继续按其拥有者承诺读取。准备与来源核对不构成封存实现的质量接受。当前成员内部的归档测试也从Vitest发现和类型检查根文件中排除。Python两条执行路径在收集前排除`.legacy`目录及其conftest。覆盖率度量保留成员原有排除配置，另外排除归档测试、源码和新鲜度输入。源码中的generated、tmp、dist或coverage目录不因名称而豁免后缀核对。TypeScript仍检查当前代码的显式导入依赖；不能通过排除导入诊断把当前错误变成成功。带归档输入但不能识别的检查脚本明确报错，不能声称已排除。文档体系及其开发工具的交付不以封存实现的全量构建、测试为验收门槛，也不能将未验证的封存实现写成已通过。新目标目录缺少源码或证据时，保留缺项与无法判定状态。已有验证结论在其源码、输入和适用条件未变时直接引用，不为重复收集相同结果重跑。工程工具首次启用使用`scripts/check-engineering.sh`及采用policy明确列出的命令。该入口保留产品传感器的无数据报告，不将它标为严格产品检查通过；`make check`的严格产品门槛保持独立。

## 检查入口

合并前，在待合并的提交上计算好影响面，再运行受影响、因此需要执行的检查。共同硬线仍须核对。
交付说明记录基线、提交、范围、依据、结果与未覆盖范围。下面列的是命令的实际覆盖，不表示每次交付都须调用全部入口。

组合入口 `make check` 调用 [scripts/check.sh](../scripts/check.sh)：先算基线（`BASELINE`，没给用 `origin/main` 或 `main`）以来改动的**影响面**并打印计划，
再跑每次都跑的常驻检查与计划里的各步（下表 `make check` 一行），最后以严格模式跑一次回路状态（下表 `make loop-status` 一行），
任一步失败即停止。该脚本也支持从其他工作目录通过绝对路径调用，供本地与 CI 共用。
整套检查占一个[运行名额](../scripts/README.md#运行名额)：同一台机器上已有一套在跑时，后来的排队等候，
等过最长时限则以 75 退出且**什么都没有执行**——那不是检查失败，也不是通过。

| `make acceptance [NO_BUILD=1]` | **`make check` 不调它，而是按计划跑同一个运行器的验收一步（只跑被选中、带验收的成员，不再构建），任何一份不过即失败。**它跑每个带 `acceptance` 脚本的成员的可执行验收，与测试同一个[运行器](../tools/ts-checks/README_ZH.md#测试运行)、同一份并行度；缺省先构建这些成员及其依赖（验收驱动 `dist/`）。耗时账本写进主检出的 `tmp/acceptance-ledger/`，供回路状态的验收耗时传感器读；失败可交给 `make test-triage` | 产品已被接受——验收只覆盖它声明的那几条场景，接受归产品负责人；声明之外的场景成立；`NO_BUILD=1` 时 `dist/` 是新的——那由调用方先构建保证 |
| `make scenario-status` | **只报告，不在`make check`里。**读取实际当前产品README元数据、编号场景与覆盖声明。每个PD均进入结果，缺场景正文或编号单列未覆盖；执行与有效接受没有证据输入时保持`unknown`。非法产品根、身份、修订或越界明确失败。见[场景状态](../tools/ts-checks/README_ZH.md#场景状态) | 覆盖声明不证明执行、通过、支持或接受；无编号场景不代表无产品要求，合法空根单列未覆盖，不宣称全部覆盖；输入限于长期产品与覆盖声明 |
| `make test-affected BASE=<基线>` | **不在 `make check` 里。**取基线合并点到当前工作树（含未提交与未跟踪）的全部改动文件，用与 `make check` 同一份影响面计划选成员（变更成员、沿声明的 workspace 依赖反向传递到的、测试读到改动路径的；判全量时全部），先构建这些成员及其依赖，再只跑它们的测试并写耗时账本；缺省只跑**快层**，`TIER=slow` 或 `TIER=all` 换层。`PLAN=1` 只列范围与层，不运行。见 [tools/ts-checks](../tools/ts-checks/README_ZH.md#测试运行) | 全量测试通过——没被选中的成员没有跑，缺省也没跑慢层；范围的盲区与 `make check` 相同（没写进读者规则的读取会漏选，环境变化不在其中）；类型检查、格式与结构规则不在其中。合并前的结论仍以 `make check` 为准 |
| `make test-tier TIER=fast\|slow\|all` | **不在 `make check` 里。**先构建，再跑全部成员的那一层并写耗时账本。`TIER=slow` 跑全量慢层，`TIER=fast` 量快层全量的墙钟，`TIER=all` 与 `pnpm run test` 相同。见 [tools/ts-checks](../tools/ts-checks/README_ZH.md#测试运行) | 另一层也过了；归层是对的——层由测试文件自己声明，运行器照单跑 |
| `make mutation [BASE=<基线>\|MEMBERS=<成员目录,…>]` | **只报告，不在 `make check` 里。**把基线以来改动碰到的产品源码行（`packages/`、`apps/` 成员 `src/` 下，缺省基线 `main`；`MEMBERS=` 改为点名成员的全部产品源码）交给 Stryker 逐处变异，只跑快层，列出存活与无覆盖的变异体；读数写进主检出的 `tmp/mutation-ledger/`。Stryker 自身出错才退出非零。见 [tools/ts-checks](../tools/ts-checks/README_ZH.md#差分变异) | 测试守得住——只量了改动行与 Stryker 的变异算子；存活一定是测试缺口——判定会抖，要复跑确认；慢层守着的代码被量到了——只跑快层；别的成员的测试守着的代码被量到了——只跑本成员自己的测试，那部分显示为无覆盖 |

| `make metrics` | **只报告，不判失败，不在 `make check` 里。**全部成员产品源码的每函数圈复杂度、成员间依赖边与分层方向（与 `lint:rules` 的 `group-direction` 同一份策略）、环；给 `BASE` 时标出基线以来变更的成员、函数、导入与提交形状；`COVERAGE=1` 时对 `packages/` 与 `apps/` 下的变更成员逐个跑测试取语句行覆盖并合成 CRAP。产出摘要、数据与离线可开的审讯页，见 [tools/ts-checks](../tools/ts-checks/README_ZH.md#结构度量) | 覆盖率高或 CRAP 低等于行为正确——没有变异测试，断言强度未知；未见方向违规等于架构合理——层位是人定的策略，工具只核对方向；超阈值等于失败——它是抽查线索。覆盖率只计成员自己测试经 `src/` 或自己 `dist/` 执行到的源码，别的成员的测试与子进程里的执行不计；dist 早于源码时行号可能对不上；工作树不干净的产物不是任何提交的度量 |
| `make loop-status [BASE=<任务基线>] [SNAPSHOT=1] [STRICT=1 OUT=<目录>]` | **`STRICT=1` 那一档是 `make check` 的最后一步；除硬线外只报告。**严格模式另判开着的传感器都有数据（有一个没数据就退出 1），要求 `BASE` 与 `OUT`，草稿只写 `OUT`、不写快照，回路目录不动。整洁各项指标的带位（提醒／处置／解除三条线带滞回，部分另与基线快照比）：红色成员数、超 alert 的函数数、稳定依赖不稳定的边、一起改却分属两组的成员对、没有断言的测试、全仓重复行占比（jscpd 核心库）、产品 topic 的 rev 翻动、并行工作树与被它们同时改的成员、验收总耗时与最慢一份验收的耗时（读 `make acceptance` 或 `make check` 的验收一步在这个提交上留下的账本；没有成员有验收时是「0 份」；`make check` 的计划跳过了验收时认那份「跳过」的记录，两项耗时如实写没数据、写明跳过；有验收却没有任何记录才是传感器没数据）；给 `BASE` 时列这次变更里要解释的红项（变更函数超 warn 且比基线涨了或新出现的，原来就超线、这次没变差的只计数；新增跨成员依赖及其中稳定依赖不稳定的、改动过的测试里没有断言的用例、碰到改动文件的克隆）；各成员四项预算（基线快照里有的成员只在比基线差时提醒，处置照绝对线），超预算的生成清理草稿，反复变红的标结构问题，另列比基线变差的成员；对照表各类条数。方向违规或环、或给了 `BASE` 且验收锁被破才退出 1；干净的工作树上写趋势快照。传感器金丝雀（每个传感器种一处已知违规的夹具）随 `tools/ts-checks` 的测试每次都跑。见 [tools/ts-checks](../tools/ts-checks/README_ZH.md#回路状态) | 有数据等于量得对——金丝雀只证明种下的那几处查得出，不证明查得全；带位与草稿是抽查线索，不是质量结论或该拆的指令；没有断言的测试只看语法，断言藏在导入的辅助函数里会误报，有断言不等于断言有力，类型测试里编译得过的语句就算断言；重复只查词法相同的片段，改了名字的查不出；一起改的成员对只说明历史共变；没数据的传感器写明原因，没数据不等于没问题；阈值是起步值，未经校准（验收耗时的两条带是施工简报的提议，归负责人定）；验收耗时受机器负载影响；工作树不干净的读数不是任何提交的度量，也不写快照；没有基线快照时成员预算退回绝对线；要解释的函数按「同一路径、同一限定名」与基线比，函数或外层改了名、git 不认作改名的挪文件都按新出现算，只比圈复杂度 |
| `make loop-health [OUT=<dir>]` | **不在`make check`里，只报告。**把趋势快照、测试耗时账本与主线Git历史汇成自包含页面、`health.json`和`summary.md`；报告提交大小、全量测试墙钟、结构指标与成员预算走向、对照表条数及传感器最近有数据的时点。见[流程体检页](../tools/ts-checks/README_ZH.md#流程体检页) | 没数据的块保留原因；提交大小只数文件；测试耗时受负载影响；不同分支快照按提交时间排序，不能直接归因于代码；输入限于趋势快照、测试耗时账本和Git历史 |
| `make role-eval ARGS="…"` | **不在 `make check` 里；它的子命令都不调用模型。**在常设用例集上做研发角色的行为评估，模型只由主会话派 subagent 来跑，子命令成对围着那一次派发：`prepare` 从角色源现编译定义、建一次性的工作副本（待审材料，或装好依赖的整仓检出）、写简报；`record` 收录宿主留下的 subagent 记录，核对简报、实际模型、副本有没有被动过、有没有够到真值，整仓检出一类还核对是从仓库之外的会话派发的；developer（含 product、terminal、verification 三类实施）与 qa 的流在 `record` 时由程序在副本上跑测试、读验收报告或拿角色写的测试去跑预置的变异体来判定；评审类的流由 `judge-brief`／`judge-record` 让判官 subagent 把报告判定成逐条结果，判官引的原句与所属发现由程序对着报告核；`calibrate-*` 让判官判一组有人工判定的报告并逐处比对；`summary`、`report` 算每个指标的均值与区间。`prepare` 在用例集当前版本的两次签字不全、受保护路径有未提交改动或材料 `verify` 不过时拒绝。没以报告收尾、实际模型与流里钉的不符、够到真值的尝试另记，不进结果。运行器自身的离线测试在 `make test` 里。见[运行器](../.meta_harness/agents/evaluation/harness/README.md)与[常设用例集](../.meta_harness/agents/evaluation/suites/README.md) | 角色在真实工作上的表现——用例是有限的几份材料，种入的缺陷比真实的更显眼；比该流说明里写的噪声范围更小的变化；Codex 一端的行为（只有 Claude Code 一端）；判官判得对——它的一致率只在校准用的那些报告上量过；subagent 没越界——它与主会话共用检出，核对只认得出记录里留了痕迹的越界；程序判定的流里完成声明与验收报告引的输出是否属实——程序只读测试结果与报告字段 |

正式 `Check` 工作流当前停用，合并前的检查结论以实际执行的本地候选证据为准。合并前在待合并的那个提交、干净的工作树上
计算影响面并执行所需检查。交付说明写明基线、提交、范围、依据、用时与结果。仓库里的正式工作流文件只声明手动触发，
恢复条件与做法见[自动化入口](../scripts/README.md#ci)；恢复之后它在全新检出上跑同一个 `make check` 再跑 `make metrics`，
**通过的含义同样不超过上表**：不带付费模型凭据，也不跑 `FORMAL=run`，度量步骤的成败不计入检查结论。

产品topic升rev后，词条出处与对象依据须逐条复核。局部迭代可用`STALE=report`列待复核队列，但不是通过；交付使用默认对账。模型执行独立于导航检查，不由`make design-check`隐式运行。

## 环境与实际执行

自动化入口需要 Git、Bash、Make，以及 [uv](https://docs.astral.sh/uv/getting-started/installation/)
与根 `package.json` 指定的 Node/pnpm。`uv sync --locked` 依据锁文件准备 Python 3.12+
及 JSON Schema、Markdown、YAML 验证依赖，并以 editable 方式安装 workspace 工具包。
`make test` 的临时目录为 `tmp/test-runs/`，只用于本仓库测试。
测试运行器的耗时账本与各成员日志落**执行工作树**的 `tmp/test-ledger/<提交短号>[-dirty]/<时间>/`
（环境变量 `OMNE_TEST_LEDGER_HOME` 可改根目录）；工作树不干净的账本不是任何提交的账本。

形式工具链**装在系统全局路径**，不依赖任何仓库内的临时目录：

```text
/opt/java/jdk-21.0.12.1+1-jre      JRE
/opt/tlaplus/tla2tools.jar         TLA+ / TLC
/opt/alloy/alloy-6.2.0.jar         Alloy Analyzer（alloy.jar 指向它）
/usr/local/bin/{java,tlc,tla2sany,alloy}
```

`JAVA_HOME`、`JAVA_BIN`、`TLA2TOOLS_JAR`、`ALLOY_ANALYZER_JAR` 在 `/etc/environment`
与 `/etc/profile.d/tlaplus.sh` 中声明，**登录后的 session 自动继承**；
非登录 shell（某些 CI 步骤、`bash -c`）读不到 `/etc/environment` 之外的文件，
需要时显式传入。JAR 来自
[TLA+ 官方发行页](https://github.com/tlaplus/tlaplus/releases)与
[Alloy 官方发行页](https://github.com/AlloyTools/org.alloytools.alloy/releases)。

**环境存在不等于已验证。**`make formal-tools` 只报告工具可用，报告应记录工具版本与文件
SHA-256；当前环境是否安装、仓库是否定义了模型，是两个问题。

模型、精确配置、命令及成立前提由实际成员的`models/`与`verification/`维护；系统未实现机制归相应architecture拥有者。每次执行记录输入摘要、工具版本、参数、预算、输出和判读，放本工作树`tmp/`。不设中央冻结或形式任务登记。

正控须识别工具的完成结论；负控须命中指定性质或反例，非零退出本身不算通过。Alloy的SAT/UNSAT与TLC的安全/时序反例按原配置判读，缺工具、超时、解析失败或未执行如实保留。工具环境存在、Schema通过或GUI打开不表示模型已执行，也不代替真实组合验证。

## 证据能支持什么

选择工具根据所需性质，**不把多种证据排成可互相替代的分数等级**。

| 证据 | 能支持的结论与必要边界 |
|---|---|
| 正确性论证或人工审阅的证明 | 说明命题、定义域、前提和推导；只有完整证明才报告为证明，草图与未闭合义务分别标明 |
| 模型检查 | 说明模型、实际探索范围、配置、被检性质及结果；**有限实例未发现反例不能扩展为任意规模或真实实现正确** |
| 机器检查的演绎证明 | 固定命题、证明工件、工具及依赖，实际检查通过；列出公理、环境假设、信任边界及未消解义务 |
| 实现符合性证据 | 固定实际包/fork、源码、配置、装配和环境，观察契约要求的结果；契约测试、故障注入及实机结果分别说明范围 |

检查器未执行、占位证明、跳过目标，或把目标本身当成未验证假设，**都不能报告该目标已经证明**。
实际失败和工具不支持也分别记录。

形式模型与实现之间要能解释：哪些状态和事件对应，哪些实现步骤被抽象成一个动作，
哪些环境或提供者行为被假定。行为的权威是所采用的 TLA+ 规格；
采用其他表示时说明映射，**不建立另一套相冲突的行为**。
没有精化证明时如实说明符合性由哪些场景或轨迹核对支持，**不把模型证明自动延伸到代码**。

可复用证据至少记录：契约与模型版本、源码 commit、工具与版本、命令或配置、
输入边界/假设和结果。通过、失败、不确定和未覆盖均须如实保留。
**有限测试或模型检查不能表述为无条件证明。**

## 分别表述这六种状态

尚未形式化、模型未覆盖、已声明但未执行、执行失败、有限范围通过，
以及实现尚未存在或真实组合未验证——**它们是六件事，不能合并成一个百分比**。

某个模型通过不能扩展为整份契约已验证；结构检查、语义审阅、有限模型、
公共产物消费和真实组合属于不同证据范围。记录后两者时固定实际发行物、
所消费接口及应用装配；**上游源码测试不自动代表实际采用的包**，
单组件和替身通过不代表跨能力动作链闭合。

实现、契约、装配或假设变化后，旧证据保留原范围并标出当前失效部分，
**不让新入口把过往结果投影为当前通过**。

## 交付时说明什么

保留失败的实际输出与影响判断，修正后运行受影响检查。
交付说明检查针对哪个源码状态、配置和范围；已有证据仍覆盖同一状态时可引用，
变化使其失效时补跑。临时日志放在 `tmp/`，清理工作树前保留任务需要的证据。

## 集成的两条基线

采用后的检查由[共同 loader](../tools/ts-checks/src/integration/context.ts)取得固定 targetBase 与各卡 taskBase/taskSource。影响面按目标 B，验收锁按原任务逐提交审计并补 B..C；合法运输父保留其来源。显式 BASE 不能替代丢失 context。全局 main 趋势及未采用任务仍按原含义。候选执行证据和未来部署边界见[工具指南](../tools/ts-checks/src/integration/README.md)。

## 组合性质与证明义务

以下义务约束本次实际声明和消费的保证。复用已适用的证据，不为目录完整性新造模型。

### 从承诺界定性质

先说明消费者依赖什么，再选择允许的操作和状态表示。Context、服务键或 disposer
的存在本身不证明行为。Cordis 的机制与条件性结论按[采用来源](../.meta_harness/agents/skills/harness-design-handbook/canonical/references/cordis.md)确认；
项目需要兑现的具体含义仍由能力及组合契约拥有。

| 性质 | 需要说明的含义 |
|---|---|
| 局部可逆 | 在给定有效状态及操作条件下，所附逆操作恢复约定的观察 |
| 撤除正确 | 撤除本实例贡献，保留其他合法贡献和明确保留的事实；依赖使用按契约收口 |
| 释放或交接完成 | 资源或工作到达规定终态，或由明确的新所有者承接 |
| 可交换或互不干扰 | 指定操作族在允许条件和交错下，状态、结果、后续合法操作及撤除满足声明的关系 |
| 授权撤销、工作取消、业务补偿 | 分别由所属契约定义生效点、在途政策及完成条件，不以局部逆操作代替 |

观察关系由契约允许的消费者观察确定，包括必要的返回值、失败、顺序、权限与
后续行为。可以隐藏无业务意义的内部布局，不能为了证明成立而忽略既定的观察。
受控范围按实际访问、所有权和恢复能力划定，不按“内存/磁盘”或“经 Context
取得”直接划分；外部输出与已成立的业务事实沿所属协议保留或处理。

### 证据要求何时触发

逐项按本次声明及其用途判断，可以引用已有适用的证明和模型。下表针对需要
建立的事实，不要求所有提案具有相同附件。完成时点由[就绪范围](engineering/quality.md#区分四层就绪状态)
与本次消费者需要确定。

| 设计情形 | 所需证据义务 |
|---|---|
| 复用既有受控操作，未改变语义、表示和适用前提 | 核对精确契约、已有证据范围及使用映射；验证实际使用符合契约，不重复证明上游 |
| 自定义局部效应和清理，影响范围明确 | 给出前后条件、所有权、保留范围和正确性论证；实现阶段覆盖相关部分失败、重入/并发及清理结果 |
| 新增共享操作，以其可逆、可交换或互不干扰性质支撑跨组件组合 | 必须给出覆盖所声明操作族和范围的形式化证明；复用定理时补足前提成立的论证 |
| 自定义并发装卸、共享资源交接、代际替换或恢复协议 | 需要相应行为模型及关键性质检查；复用已有完整契约和适用证据可引用。声称已建立检查边界外的结论，或机制选择依赖这种推广时，需相应证明 |
| 依赖上述性质省略或放宽顺序、隔离、排空或冲突检查等控制 | 必须证明所依赖性质及省略/放宽控制后仍保留目标保证；首次设计即省略与取消既有控制同样适用 |
| 外部输出或已经确认不可逆的效果 | 明确不可逆边界、结果不确定性及业务撤销/补偿/恢复协议；按实际协议验证，不构造虚假的逆操作 |

多项适用时分别履行相关义务，不用一项通过替代另一项。对顺序敏感的操作可
明确依赖、限制允许的交错或选用其他满足需求的机制；必须验证实际采用的政策，
串行执行本身不证明撤除能保留后续合法变化。

当需要待设计系统新建立的共享代数保证承载租户隔离、唯一写入权、安全撤除等系统
关键保证，且以其为依据省略或放宽控制约束时，所依赖的证明须经机器检查。
这包括首次设计即省略控制，以及复用原语后改变表示、操作语义或放宽证明前提。
已有证明可复用，但必须满足本次所需级别并补足适用性论证，不能通过改称“复用”
改变门槛。关键性根据所保护
的需求、不变量和失效后果说明，不由包名或角色名判断。其他必须证明的情形可
采用有明确形式命题、完整推导及独立审阅的证明；若声称机器检查通过，必须有
相应实际结果。此处不指定新证明工具或替换 TLA+ 的行为权威地位。

契约中的全称要求是规范目标，不自动是已证明结论，也不单独触发上述新增门槛。
可以接受要求或语义范围并保留未验证状态；依赖强制证明的具体机制选择另行
判断，不能借“接受语义”同时放行它。

不能通过省略性质名称逃避义务：只要方案的成立依赖该性质，就应说明并提供
证据。未触发强制证明仍需相称验证；工具未具备、时间不足或模型能力强都不
消解已触发义务。探索性候选可保留待完成项，不将它们当作可直接消费的保证。

### 命题与前提的责任

证明需要能辨认所量化的状态、参与者、操作和配置范围，操作的定义域、观察
关系、失败模型及进展所需的公平性或终止前提。先定义目标性质，不能将它本身
写成未受约束假设，再以模型检查通过宣称已经兑现。

局部逆关系可写作 `undo_e(apply_e(s)) ≈ s`，但该式只覆盖定义中的条件。允许
其他组件在建立与撤除之间活动时，还需论证其他合法贡献得到保留。交换性不能
只看最终容器相同：必要时包含前向及逆操作、返回结果、可执行条件，以及后续
操作或继续执行选择。停止请求与静止、逆序调用与异步完成顺序分别按实际契约
表达。重复清理的调用协议需明确，不一概要求数学逆操作本身幂等。

服务提供者拥有受控接口和表示方式所承诺的性质；消费者负责满足自身调用及
生命周期条件；装配负责实际依赖与作用域；无法由系统兑现的部分保留为环境
假设。一方的假设由另一方提供时，引用其精确保证和证据；循环地互相假定不能
代替证明，循环依赖的性质需要整体论证或先建立独立成立的前提。

区分前提由哪个操作强制、由协议保证、仅被检查器观察或仍未经验证。声明式
接口不能限制绕过它的任意代码；受控 API 的行为证据和宿主执行权限证据分别
取得，不把提示词、Context 可见性或测试环境隔离当作生产安全边界。

### 共享贡献的最小例子

假设一个注册能力的消费者只依赖每个实例各自的条目。A 建立 `a`，B 随后建立
`b`，撤除 A 应保留 `b`。若 A 的逆操作恢复整个旧表，B 的合法贡献会丢失。
按独立注册身份撤除自身条目，可以把关键正确性责任集中到注册能力提供者；
是否需要代际、唯一令牌等表示，由实际身份及旧引用契约决定。

这个例子适合验证“保留他方贡献”，不能自动证明所有注册接口可交换。若条目
顺序决定请求处理，或注册返回值使两个顺序可区分，就需进一步建模观察和顺序
政策。不能借例子接受产品的接口形状，也无需为纯计算组件建立空 effect。

### 把设计义务交给实现

如果模型将清理抽象为原子地移除全部所属资源，组合结论以该抽象成立为前提；
实际 disposer、后台任务和后端必须有对应证据。若所声称保证覆盖清理失败、
挂起或残留，就应在合适层次描述这些行为，不能用理想清理动作遮蔽它们。

按风险从契约导出测试：部分取得资源后失败；两个实例交错建立/撤除；旧清理
晚于新实例发布；清理异常或依赖消失；退出后的晚到结果；外部效果成功但回执
丢失。观察真实资源、权威状态或消费者行为，不能仅断言回调被调用。

共享验证设施应能识别代表性错误，例如空清理、恢复整个旧快照或误删他方贡献。
这可以用少量负例核对测量有效性，不要求所有组件运行统一突变测试。具体版本、
环境、实际结果及局限按[证明与实现证据](#证明与实现证据)记录；
改变表示、调用约束或环境时沿[证据适用范围](#证据能支持什么)重新判断证据适用性。

## 规格的分工

| 表达 | 主要用途 | 不能单独说明什么 |
|---|---|---|
| 概念与契约文档 | 统一词汇、身份、边界、操作含义，引用设计理由 | 全部并发执行都满足性质 |
| JSON Schema | 约束交换/保存的数据形状并引用共享定义 | 跨请求权限、生命周期与最终进展 |
| Alloy | 表达结构关系，在给定范围查找反例 | 任意规模成立或真实运行必然终止 |
| TLA+ | 行为权威规格：状态变化、并发与时序性质 | 被省略的环境与实现细节自然正确 |
| 规范验收场景 | 明确消费者可观察结果，约束不同实现 | 全部状态空间的穷尽证明 |

按需要保护的性质选表达，各工件指向同一语义；不为填满目录制造平行模型。
只有 contract.md 不自动是缺陷，有模型也不自动覆盖完整；达到什么形式化与证据门槛，
由实际承诺和[组合性质](#组合性质与证明义务)判断。

## 证据与追溯

性质从[性质核对](../.meta_harness/agents/skills/harness-design-handbook/canonical/references/properties.md)，证据须能追到规则、模型假设、
实现边界与消费者观察。全称要求表达规范目标，不自动表示已证明。
生成代码、共享测试和相同接口有各自价值，均不单独证明行为等价。

优先观察真实边界：撤除后资源是否消失、失败后状态是什么、受保护访问是否被拒绝、外部写入是否发生。
多个提供者使用共同契约场景，并覆盖影响保证的失败与交错；只检查 mock 次数或成功文字可能漏掉实际结果。
测试预期由契约导出，fixture 不能补造缺失行为。

## 证明与实现证据

| 需要对应 | 留下什么 |
|---|---|
| 采用对象 | 精确契约、实现/发行物修订，以及证明或模型输入 |
| 抽象状态 | 模型变量对应哪些权威状态与可观察事实 |
| 抽象动作 | 由哪些实现步骤兑现，提交/观察点在哪里 |
| 前提责任 | 谁强制、谁以契约保证、什么仅被诊断、什么仍是假设 |
| 省略部分 | 未建模的失败、并发与资源行为由哪项证据或待办承接 |
| 实际执行 | 工具、配置、环境、结果、覆盖范围与局限 |

模型把清理视为原子成功动作时，提供者仍需兑现这个抽象；
承诺覆盖清理失败、挂起或残留时，应在相应层次建模，不能把目标性质自身无约束地当作前提。
一方假设由另一方承担时引用精确保证，循环互相假定不能闭合整体证明。

## 变更与验证范围

有限模型未找到反例，只支持已建模且已执行的范围；运行时检查只支持实际观察的关系；
机器检查证明需有命题、前提与真实工具结果。各类证据不能跨范围互相冒充。

表示、调用方式、观察关系或环境改变时，重新判断哪些旧证据仍适用，方法见[变更与维护](maintenance.md#修改与迁移)。
出现反例时先区分实现违约、规格遗漏、模型抽象错误、环境前提变化和新要求，再修正对应拥有者；旧证据只保留其原有范围。
只改局部表达时做相称检查；相关检查通过且没有新疑点后停止，不用重复无关验证增加信心。
