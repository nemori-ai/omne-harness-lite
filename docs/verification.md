# 验证、工具与证据

本页定义检查的边界：每个入口覆盖什么、**不能**据此声称什么。
命令的准确目标由根 [Makefile](../Makefile) 与 [scripts/check.sh](../scripts/check.sh) 维护，
实际参数与退出语义以各 CLI 的 `--help` 为准。

静态检查排除`packages.0.0.1.legacy/`和`apps.0.0.1.legacy/`两个封存目录，包括格式、文档遍历、源码规则及实际架构抽取。文档体系及其开发工具的交付不以封存实现的全量构建、测试为验收门槛，也不能将未验证的封存实现写成已通过。新目标目录缺少源码或证据时，保留缺项与无法判定状态。已有验证结论在其源码、输入和适用条件未变时直接引用，不为重复收集相同结果重跑。工程工具首次启用使用`scripts/check-engineering.sh`及采用policy明确列出的命令。该入口保留产品传感器的无数据报告，不将它标为严格产品检查通过；`make check`的严格产品门槛保持独立。

## 检查入口

合并前，在待合并的提交上计算好影响面，再运行受影响、因此需要执行的检查。共同硬线仍须核对。
交付说明记录基线、提交、范围、依据、结果与未覆盖范围。下面列的是命令的实际覆盖，不表示每次交付都须调用全部入口。

组合入口 `make check` 调用 [scripts/check.sh](../scripts/check.sh)：先算基线（`BASELINE`，没给用 `origin/main` 或 `main`）以来改动的**影响面**并打印计划，
再跑每次都跑的常驻检查与计划里的各步（下表 `make check` 一行），最后以严格模式跑一次回路状态（下表 `make loop-status` 一行），
任一步失败即停止。该脚本也支持从其他工作目录通过绝对路径调用，供本地与 CI 共用。
整套检查占一个[运行名额](../scripts/README.md#运行名额)：同一台机器上已有一套在跑时，后来的排队等候，
等过最长时限则以 75 退出且**什么都没有执行**——那不是检查失败，也不是通过。

| `make acceptance [NO_BUILD=1]` | **`make check` 不调它，而是按计划跑同一个运行器的验收一步（只跑被选中、带验收的成员，不再构建），任何一份不过即失败。**它跑每个带 `acceptance` 脚本的成员的可执行验收，与测试同一个[运行器](../tools/ts-checks/README_ZH.md#测试运行)、同一份并行度；缺省先构建这些成员及其依赖（验收驱动 `dist/`）。耗时账本写进主检出的 `tmp/acceptance-ledger/`，供回路状态的验收耗时传感器读；失败可交给 `make test-triage` | 产品已被接受——验收只覆盖它声明的那几条场景，接受归产品负责人；声明之外的场景成立；`NO_BUILD=1` 时 `dist/` 是新的——那由调用方先构建保证 |
| `make scenario-status` | **只报告，不在`make check`里。**读取实际当前产品README元数据、编号场景与覆盖声明。每个PD均进入结果，缺场景正文或编号单列未覆盖；执行与有效接受没有证据输入时保持`unknown`。非法产品根、身份、修订或越界明确失败。见[场景状态](../tools/ts-checks/README_ZH.md#场景状态) | 覆盖声明不证明执行、通过、支持或接受；无编号场景不代表无产品要求，合法空根单列未覆盖，不宣称全部覆盖；输入限于长期产品与覆盖声明 |

计算影响面并执行所需检查。交付说明写明基线、提交、范围、依据、用时与结果。仓库里的正式工作流文件只声明手动触发，
恢复条件与做法见[自动化入口](../scripts/README.md#ci)；恢复之后它在全新检出上跑同一个 `make check` 再跑 `make metrics`，
**通过的含义同样不超过上表**：不带付费模型凭据，也不跑 `FORMAL=run`，度量步骤的成败不计入检查结论。

产品topic升rev后，词条出处与对象依据须逐条复核。局部迭代可用`STALE=report`列待复核队列，但不是通过；交付使用默认对账。模型执行独立于导航检查，不由`make design-check`隐式运行。

## 环境与实际执行

自动化入口需要 Git、Bash、Make，以及 [uv](https://docs.astral.sh/uv/getting-started/installation/)
与根 `package.json` 指定的 Node/pnpm。`uv sync --locked` 依据锁文件准备 Python 3.12+
及 JSON Schema、Markdown、YAML 验证依赖，并以 editable 方式安装 workspace 工具包。
`make test` 的临时目录为 `tmp/test-runs/`，只用于本仓库测试。
测试运行器的耗时账本与各成员日志落**执行工作树**的 `tmp/test-ledger/<提交短号>[-dirty]/<时间>/`
（环境变量 `OMNE_TEST_LEDGER_HOME` 可改根目录）；工作树不干净的账本不是任何提交的账本。

形式工具链**装在系统全局路径**，不依赖任何仓库内的临时目录：

```text
/opt/java/jdk-21.0.12.1+1-jre      JRE
/opt/tlaplus/tla2tools.jar         TLA+ / TLC
/opt/alloy/alloy-6.2.0.jar         Alloy Analyzer（alloy.jar 指向它）
/usr/local/bin/{java,tlc,tla2sany,alloy}
```

`JAVA_HOME`、`JAVA_BIN`、`TLA2TOOLS_JAR`、`ALLOY_ANALYZER_JAR` 在 `/etc/environment`
与 `/etc/profile.d/tlaplus.sh` 中声明，**登录后的 session 自动继承**；
非登录 shell（某些 CI 步骤、`bash -c`）读不到 `/etc/environment` 之外的文件，
需要时显式传入。JAR 来自
[TLA+ 官方发行页](https://github.com/tlaplus/tlaplus/releases)与
[Alloy 官方发行页](https://github.com/AlloyTools/org.alloytools.alloy/releases)。

**环境存在不等于已验证。**`make formal-tools` 只报告工具可用，报告应记录工具版本与文件
SHA-256；当前环境是否安装、仓库是否定义了模型，是两个问题。

模型、精确配置、命令及成立前提由实际成员的`models/`与`verification/`维护；系统未实现机制归相应architecture拥有者。每次执行记录输入摘要、工具版本、参数、预算、输出和判读，放本工作树`tmp/`。不设中央冻结或形式任务登记。

正控须识别工具的完成结论；负控须命中指定性质或反例，非零退出本身不算通过。Alloy的SAT/UNSAT与TLC的安全/时序反例按原配置判读，缺工具、超时、解析失败或未执行如实保留。工具环境存在、Schema通过或GUI打开不表示模型已执行，也不代替真实组合验证。

## 证据能支持什么

选择工具根据所需性质，**不把多种证据排成可互相替代的分数等级**。

| 证据 | 能支持的结论与必要边界 |
|---|---|
| 正确性论证或人工审阅的证明 | 说明命题、定义域、前提和推导；只有完整证明才报告为证明，草图与未闭合义务分别标明 |
| 模型检查 | 说明模型、实际探索范围、配置、被检性质及结果；**有限实例未发现反例不能扩展为任意规模或真实实现正确** |
| 机器检查的演绎证明 | 固定命题、证明工件、工具及依赖，实际检查通过；列出公理、环境假设、信任边界及未消解义务 |
| 实现符合性证据 | 固定实际包/fork、源码、配置、装配和环境，观察契约要求的结果；契约测试、故障注入及实机结果分别说明范围 |

检查器未执行、占位证明、跳过目标，或把目标本身当成未验证假设，**都不能报告该目标已经证明**。
实际失败和工具不支持也分别记录。

形式模型与实现之间要能解释：哪些状态和事件对应，哪些实现步骤被抽象成一个动作，
哪些环境或提供者行为被假定。行为的权威是所采用的 TLA+ 规格；
采用其他表示时说明映射，**不建立另一套相冲突的行为**。
没有精化证明时如实说明符合性由哪些场景或轨迹核对支持，**不把模型证明自动延伸到代码**。

可复用证据至少记录：契约与模型版本、源码 commit、工具与版本、命令或配置、
输入边界/假设和结果。通过、失败、不确定和未覆盖均须如实保留。
**有限测试或模型检查不能表述为无条件证明。**

## 分别表述这六种状态

尚未形式化、模型未覆盖、已声明但未执行、执行失败、有限范围通过，
以及实现尚未存在或真实组合未验证——**它们是六件事，不能合并成一个百分比**。

某个模型通过不能扩展为整份契约已验证；结构检查、语义审阅、有限模型、
公共产物消费和真实组合属于不同证据范围。记录后两者时固定实际发行物、
所消费接口及应用装配；**上游源码测试不自动代表实际采用的包**，
单组件和替身通过不代表跨能力动作链闭合。

实现、契约、装配或假设变化后，旧证据保留原范围并标出当前失效部分，
**不让新入口把过往结果投影为当前通过**。

## 交付时说明什么

保留失败的实际输出与影响判断，修正后运行受影响检查。
交付说明检查针对哪个源码状态、配置和范围；已有证据仍覆盖同一状态时可引用，
变化使其失效时补跑。临时日志放在 `tmp/`，清理工作树前保留任务需要的证据。

## 集成的两条基线

采用后的检查由[共同 loader](../tools/ts-checks/src/integration/context.ts)取得固定 targetBase 与各卡 taskBase/taskSource。影响面按目标 B，验收锁按原任务逐提交审计并补 B..C；合法运输父保留其来源。显式 BASE 不能替代丢失 context。全局 main 趋势及未采用任务仍按原含义。候选执行证据和未来部署边界见[工具指南](../tools/ts-checks/src/integration/README.md)。
