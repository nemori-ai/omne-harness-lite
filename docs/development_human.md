# 给人看的开发指南

本页写给指导 agent 工作、并对交付结果负责的人。你主要负责定义问题、判断质量和决定是否接受。具体实现由 agent 完成，命令和操作步骤见[开发指南](development.md)。原生依赖的锁定安装、白名单构建和编译器前提也由该指南维护。

## 用机器学习训练理解研发分工

可以把正在建设的软件看作一个 model，把内部实现的每一行代码看作 model parameters。agent 根据任务、约束和反馈修改这些参数。人决定这个 model 要解决什么问题、怎样衡量质量，以及在什么结构和改进流程中寻找解。

这样理解后，你的日常工作就不再围绕逐行检查实现展开。你需要看软件在真实任务上的表现，核对评价方法是否可信，并判断架构和研发流程是否支持持续改进。

| 训练中的概念 | 软件研发中的对应 | 你负责什么 |
| --- | --- | --- |
| 问题定义 | 用户要完成的任务、输入、环境和不应发生的结果 | 明确需求与责任范围，判断问题是否值得解决 |
| 目标 | 可观察的成功判据、禁止结果和成本要求 | 确认怎样算做成，哪些保证不能用其他收益抵消 |
| metric | 行为验收、结构读数、性能与资源成本、交付趋势 | 设计评价方法，核对工具能测什么、漏了什么 |
| optimizer | 任务切分、探路、反馈、修复、独立评估和集成的迭代过程 | 确定反馈与取舍规则，判断何时继续实现、修正目标或重看结构 |
| model structure | 领域责任、公开契约、依赖方向、状态所有权和生命周期 | 接受架构边界，核对实际组合是否符合这些边界 |
| model parameters | 已接受约束内的算法、函数、数据结构和内部实现 | 将实现交给 agent，按风险检查结果和必要热点 |

负责这些工作不意味着你要亲手编写全部测试、度量工具或设计正文。你可以让 agent 提案和实现，再确认它们表达的是正确的问题与判断依据。具体编码方法仍由 agent 在现行契约和授权范围内选择。

这个类比描述的是分工和反馈。软件研发并没有因此变成对程序做梯度训练。验收规则、权限和架构承诺也不是实施者可以随意调整的参数。agent 可以建议修改，改变有效要求仍须由有权者决定。

### model 质量不能压成一个总分

行为正确、租户隔离、可维护性、运行成本和交付速度是不同问题。测试通过率、覆盖率或圈复杂度只能回答其中一部分。先核对必须成立的保证，再结合其余读数作取舍，不用较高的性能分数抵消数据泄露。

例如，一项任务要求查询只能返回当前租户自己的记录。主路径能查到记录、覆盖率很高，都不能证明没有泄露。你需要核对另一个租户的数据是否被拒绝，缺少身份时是否默认拒绝，以及错误、日志和真实组合是否仍守住边界。agent 可以实现这些检查，但不能为了通过而删去这些判据。

一般实现由 agent 完成，人的注意力放在目标和证据上。现行 L3 对身份、租户隔离、凭据、内核原语及要求同一提交的状态，仍要求人逐行核对热点并安排独立评审。这个范围见[接受级别](#接受级别)，不扩展为对全部代码逐行审查。

## 怎样判断这个 model 的质量

交付时先回答下面五个问题。答案对应后面的接受流程和工具读数。

### 解决的是正确的问题吗

看实际使用者要得到的结果，而不只看功能清单。明确适用输入、失败时应看到什么，以及本次不交付什么。主路径第一次能跑时，亲自按演示步骤试一次。偏离需求的实现，即使全部测试通过，也应先修正方向。

### 评价方法能发现错误吗

确认判据覆盖承诺和禁止结果。agent 声称通过时，要能定位实际运行及其结果。对高风险保证，按接受级别安排独立评估。可执行验收由其拥有者维护，实施者只能运行，不能自行修改。

留意测试是否只检查了 agent 已经实现的路径。边界输入、失败与恢复、真实消费者，以及不同租户的组合，需要按本次承诺选择。变异读数可以帮助发现某处代码被改坏后仍没有测试失败，但它不能证明测试已经充分。

### 在真实组合中也成立吗

各成员分别通过，不证明装配后正确。核对公开入口、实际依赖与配置、状态和资源生命周期，以及故障后如何恢复。按风险选择真实组合、故障注入或独立验收，不要求每个小改动重跑全部场景。

未执行、缺资源和无法验证都保留原状。它们不能记成通过，也不能由另一个环境中的成功代替。

### 结构和成本支持继续演进吗

model structure 在这里对应软件怎样分担责任。看新增依赖有没有越界，状态由谁拥有，哪些成员总要一起修改。结构图和度量能帮助你定位问题，不能替你决定拆分是否合理。

再看实际运行成本、测试耗时和返工趋势。如果一个成员清理后反复变复杂，或一个小需求总要改动多个责任组，先核对边界和契约。持续修改内部代码未必能解决结构问题。

### 证据对应眼前的候选吗

核对实际提交或未提交字节、工作树、基线、工具版本和运行环境。旧候选的绿测、旧 `dist` 或另一棵树的日志，不能支持当前交付。

有 task context 的任务工作树中，原始 `taskBase` 审计任务历史，目标基线用于本次组合和影响面检查。同步目标分支只让目标基线前进，不会替换原始任务基线。具体规则归[多层分支集成](engineering/integration.md)。

## 主动让 agent 做可视化讲解

理解顶层架构、陌生模块或复杂业务流程时，主动让 agent 为你做一次性的、定制化的可视化讲解。说明你想弄清哪个问题、已经知道什么，以及哪里还不理解。agent 可以根据这次需要生成可离线打开的 HTML、可交互的图，或能逐步播放的演示动画。

选择形式时，先看要理解什么。

| 要理解的问题 | 可以向 agent 要什么 |
| --- | --- |
| 顶层架构怎样协作 | 分层和责任图，可展开模块，查看依赖方向、状态所有者与系统边界 |
| 特定模块怎样工作 | 输入、输出、内部状态和生命周期的讲解，按步骤展示正常路径、失败与恢复 |
| 一次业务请求怎样完成 | 可暂停、回退的流程动画，跟随具体请求查看数据、控制和权限检查，切换异常分支 |

例如，你可以这样提出要求。

> 请基于当前已接受的架构和实际实现，为我做一份一次性的离线 HTML 讲解。我想理解一个业务请求经过哪些模块，每一步由谁负责、状态在哪里变化。
>
> 用一个具体例子逐步演示，让我能暂停、回退，并切换到失败和恢复路径。标明所依据的文档或实现版本，区分设计目标、已有实现和未验证部分。用到模拟数据或示意动画时直接说明。

看完后，检查自己能否说清关键责任、依赖、状态变化和失败处理。仍有疑问，就让 agent 改换例子、展开某个模块或补一条异常路径。以这些问题是否得到回答，判断讲解是否有效。

可视化帮助理解，真实运行证据仍按前面的质量问题核对。示意动画播放顺畅不证明系统已经实现或验证通过。一次性讲解材料放任务 `tmp`，需要长期保留的有效结论维护到原有设计或契约正文，不另建一份需要持续同步的架构权威。

## 一个需求从提出到接受，你在哪几个点出手

| 时点 | 你做什么 | 需要看到的依据 |
| --- | --- | --- |
| 提需求 | 定义可观察结果、禁止结果和本次范围 | 一个能单独接受的结果，必要时先做探路件 |
| 定顺序 | 按结果、风险和真实依赖安排任务 | 排序不是硬依赖，排进迭代不等于满足开工条件 |
| 定判据 | 确认成功条件和相称证据，选择接受级别 | 判据覆盖承诺，必要的可执行验收归有权者维护 |
| 派发 | 确定写范围、实际检出、任务基线和集成责任 | 任务带验收清单与停止条件，共享对象只有一个写者 |
| 第一次能跑 | 亲自按演示步骤使用 | 可观察结果符合需求，方向偏差尽早处理 |
| agent 交回 | 核对摘要、实际结果、未覆盖和结构读数 | 见[交回时看什么](#交回时看什么)，不以完成声明代替证据 |
| 接受 | 由具名有权者确认接受范围和剩余责任 | 产品结果归产品负责人，技术结果归其拥有者 |
| 集成 | 核对精确候选、影响面、必要检查与授权 | 接受、Git 集成、Issue 关闭和 Project 阶段分别判断 |
| 之后 | 判断清理、修复和下一次迭代的安排 | 有明确范围、责任和处理时点，不影响在途工作 |

合并、推送和发布沿[任务授权](engineering/publication.md#提交表达与权限)执行。已有授权无需重复询问。检查通过不扩大权限。正式成果和临时材料的保存分别沿[成果保存](engineering/publication.md#成果保存与跨会话接续)核对。

### 独立任务隔离并行，共享对象单写

独立任务可以由主会话协调多个隔离写者。每个写者有明确 worktree、分支和范围。共享接口、锁文件与集成拓扑由单一负责人维护，耦合任务按依赖串行。你核对写权和依赖，不用会话数量判断协作是否合规。

检查和 hooks 观察实际执行者的检出。另一棵树的环境、检查结果或钩子沉默不能代替本树证据。清理前核对活跃消费者、唯一 ignored 材料和保存授权，具体条件归[协作交接](engineering/workflow.md#责任与协作交接)。

### 接受一张卡之后

普通Issue保留精确交付修订、最小决定和结果定位。按[agent交付操作](engineering/agent-delivery.md)核对启用范围；关闭、Project阶段、有效接受与当前能力支持分别判断。未启用时形成获准任务草稿，每项任务独立明确本次范围与结果。

将获接受的持续规则写回其现行拥有者，保留持续行为验收，由验收拥有者移除仅在本次交付时刻成立的临时断言。`pnpm run acceptance:scenarios`只读取长期产品与覆盖声明，不能证明验收已执行、通过或产品已接受。

后续场景含义改变时，按产品规则处理旧编号、建立新场景和任务。新增结果另立相应任务。仅重构或搬迁实现时，不强造产品故事，但要验证保持的行为与真实消费者。

## 哪些只有你能定，哪些可以不看，哪些必须逐行看

有权负责人决定产品方向、优先顺序、架构边界、验收内容、阈值、写权和接受范围。agent 可以提案、代笔和提出反例。文件落盘、独立评审或工具通过都不授予采用。

普通交付无需逐行阅读全部实现。先看结果、公开契约、结构和验证证据，按接受级别抽查。你也不必逐步监督 agent 使用哪种编码方法。

安全与不变量热点按 L3 逐行核对。agent 对自己成果的评价不能代替这项要求。其余实现细节由 agent 负责，你保留对最终内容、来源和验证的责任。

## 接受级别

派发时按改动触及的最高风险定级，不按行数或文件数定级。拿不准就上调。完整定义归手册的[风险分级](engineering/quality.md#按风险选择接受实现的看法)。

| 级别 | 你主要看什么 | 独立评估 |
| --- | --- | --- |
| L0 局部修复 | 交付说明、变更摘要和受影响检查 | 默认不派 |
| L1 常规增量 | 加看成员结构与风险，抽查两三个热点函数 | 默认不派，未交代红项可派实现评审 |
| L2 跨成员与装配 | 加看依赖全图与真实组合运行证据 | 摘要仍说不清或有未交代红项时派实现评审。有可运行交付面和可观察验收标准时派 qa |
| L3 安全与不变量 | 人逐行读热点，核对适用故障注入及形式任务 | 同时派实现评审与独立 qa，绿测不免读 |

任何级别出现实施者未交代的红项，都可以派实现评审只核相关范围。评审发现须有工具输出或具体反例。qa 的判决提供证据，接受仍归有权者。

每次检查固定实际候选，按影响面运行必要用例。计划排除与未执行分别记录。缺少某种检查入口时明确报告，不用其他证据冒充它。可执行验收在所有级别都保持实施者只读。

## 交回时看什么

交付摘要应让你先看到实际结果、证据和缺口，再决定是否深入到源码。按下面顺序读。

1. 核对候选和范围。提交、实际检出、基线、影响面和 completionTarget 是否明确。未提交候选须说明实际字节及已有改动边界。
2. 看行为与组合证据。必要检查是否执行，是否通过，哪些跳过或无法验证。结果能否定位到实际入口和候选。
3. 看结构。`pnpm run metrics` 提供摘要与审讯页。核对方向、环、新增依赖和热点，变更超线项须逐条说明处理结果或保留理由。
4. 看失败归因。将红灯归为机器或并发问题时，须附 `pnpm run test:triage` 的实际输出。隔离重跑稳定通过仍不能证明原因。贴近时限的用例需要加快，或提出有依据的显式时限。
5. 看测试质量和成本。覆盖率、无断言测试、测试耗时和变异读数分别核对。`pnpm run mutation` 是单独的报告入口，不在 `pnpm run check` 中自动运行，也不因零存活就证明测试充分。
6. 核验收变更。有可执行验收时，按原任务基线检查 `pnpm run acceptance:lock` 输出。它列出碰过验收的提交与自报角色。即使标成 `main` 或 `qa`，仍须核对是否为批准的修改。
7. 看共同硬线与需解释读数。`pnpm run loop:status` 的红项应在交付中有处置或明确理由。没变差的历史超线数不要求实施者替历史逐条交代。
8. 核对提交与接受责任。提交应能按独立单元理解，人的署名及 `Harness:`、`Agent-Role:` 来源沿[贡献交付](../CONTRIBUTING.md#形成可审阅的交付)核对。

度量是定位和抽查依据。方向无违规不证明架构合理，覆盖率高不证明行为正确。各入口的能力与声明边界归[验证与证据](verification.md#检查入口)。

### 合并前按影响面检查，同时守住三条共同硬线

`pnpm run check` 打印影响面，再执行常驻检查和受影响成员的必要步骤。严格回路归并检查依赖方向与环、验收修改，以及启用传感器的数据。具体硬线以[整洁回路](clean-loop.md#回路怎么转)为准，不在本页另定阈值。

计划未选中的检查没有运行。共同硬线不能因检查范围收窄而省略。全量检查由负责人安排，或由实际全局影响决定，合并后没有自动补跑。

有 task context 时，从共同 loader 取得任务基线与目标基线，不手选 `main` 绕过 context。没有 context 时，基线取显式 `BASELINE`，缺省为 `origin/main`。原任务审计和本次影响检查分别核对。

传感器量不出数据时，先查原因。目录迁移、工具故障或配置关闭都可能导致缺数据。需要停用传感器时记录决定与理由，不为让这次检查变绿而悄悄关闭。

### 收工时的自动反馈

启用且实际运行的收工 hook 会将当前执行者检出的新增结构红项反馈给 agent。同一分支同组读数只反馈一次。它提供位置与数值，修复方法仍由执行者判断。

hook 是提醒，不是合并门禁。未碰适用源码、hook 未启用、重复读数、故障或超时都可能没有反馈。错误时的警告和日志用于定位 hook 故障，沉默不证明没有红项。

你需要核对每个实际宿主的加载、信任和真实执行。需要关闭时，区分本会话的 `OMNE_LOOP_HOOK=off` 与长期配置的 `hook.enabled=false`，长期改变记录理由。精确条件、日志位置和宿主状态归[hooks 说明](../.meta_harness/agents/hooks/README.md)。

## 三类整洁各看什么信号

| 方面 | 看什么 | 何时需要改变安排 |
| --- | --- | --- |
| 研发流程 | 提出到可运行的时间、等待裁决、在途任务、提交大小和写权重叠 | 任务长期等待，先查问题切分、依赖与人的裁决。多树争写同一对象时先恢复明确写权 |
| 架构设计 | 依赖方向、环、新跨成员依赖，以及总要一起修改的责任组 | 跨组依赖说不清或结构反复变坏时，由拥有者重看边界，agent 提供反例与提案 |
| 实现质量 | 复杂度、重复、断言、测试耗时与清理后的变化 | 局部问题交 agent 处理。反复出现的问题先判断是否来自契约或拆分，不反复派同样的清理 |

结构与复杂度从 metrics 看，回路状态和趋势从 loop 看，执行耗时从实际运行账本看。不同入口的读数不能混成一个质量结论。提醒、处置与解除阈值的含义归[整洁回路](clean-loop.md#回路怎么转)。阈值仍需按真实交付校准，调整须留理由，不为某个候选临时放宽。

## 怎样算尽责

人的署名意味着对最终内容、来源和验证负责，不能用 agent 编写作为免责理由。接受前核对证据，而不是转述完成声明。

清理候选及时决定批准、驳回或何时再看。规格冲突、验收不可达和授权不明交相应有权者裁定，只暂停依赖部分。agent 不能靠自己换一个方便解释继续实施。

检查提示排队时遵守运行器的资源协调，不另起同套检查争用资源。阈值、停用传感器、接受和权限变化都保留依据。

## 一天里要看的东西

- 在途任务有没有独立写权与明确交接，耦合工作是否按依赖推进。
- 今天的交付有没有实际候选、行为证据、未覆盖和所需独立评估。
- 红灯归因有没有实际输出，等待人的裁决是否已处理。
- 清理是否积压，结构问题是否仍被当作局部代码问题处理。
- 集成目标是否满足其必要检查，不能在未处理的红项上继续声称主线健康。

## 每周看一次体检页

`pnpm run loop:health`汇总趋势、测试耗时和提交历史。它用于观察变化，不能代替一次交付的验证。

体检页用于核对提交大小、测试与清理成本的走向。任务范围、等待条件及具名决定从真实Issue核对；需要调整范围时按普通任务协议修订。某个成员清理后反复超预算时，重新核对结构。

趋势没有数据时查采集范围与原因，不把空白当健康。缺少历史输入时保留相应未知。按 main 比较的趋势须在当前 main 留真实快照，不把轨道或工作分支读数当成主线状态。

## 开始前准备 coding agent 环境

在实际使用的 coding agent harness 中安装并启用项目[三层方法](engineering/skills.md#三层分工)的来源：pstack 与 Matt 两份插件，以及 ub-mode 技能。ub-mode 按来源表的固定提交取 `https://raw.githubusercontent.com/unclebob/ub-mode/<ub-mode-revision>/SKILL.md`，放到宿主的用户技能目录：Claude Code 为 `~/.claude/skills/ub-mode/SKILL.md`，Codex 为 `~/.codex/skills/ub-mode/SKILL.md`，Cursor 为 `~/.cursor/skills/ub-mode/SKILL.md`。精确版本归[技能来源表](engineering/skills.md#来源与项目采用)，操作归[开发初始化](development.md#初始化-coding-agent-插件)，本页只说明人要核对的责任。

新机器、cloud 环境或更换 harness 后，确认插件版本、会话发现（含 `ub-mode`）、所需技能和参考，以及实际可用的模型和工具。Matt 完整插件仍只按项目选定子集触发。插件出现在列表中不证明自动路由、hooks 或真实任务遵循已经发生。

agent 可完成获准且能够自行操作的安装与核对，需要人完成的宿主信任或账号操作由你处理。缺能力时只暂停依赖工作。更新版本后重新核对实际加载，版本与采用范围由技能拥有者维护。

## 对话与交付队列

提出任务时说清本次要起草、建卡、取任务还是实施。feature、修复、重构、性能、维护和调查按[工作类型](engineering/work-types.md)准备不同依据。agent 沿[交付操作](engineering/agent-delivery.md)定位真实任务、来源、条件和具名责任。

Issue 协议已采用，日常入口仍以[配置](engineering/github-delivery.json)为准，启用及具名采用事实查[工程启用任务](https://github.com/nemori-ai/omne-harness-lite/issues/195)；未获本任务授权时只形成获准草稿。Project 是派生视图，关闭或阶段变化不授接受。

工作分支通常进入已登记且 active 的 integration 轨道，完整 RI 进入 main，stable 选择已有 main checkpoint。FI 将 main 的变化同步到轨道。人的工作是确定路线、completionTarget、必要条件和集成责任，具体操作可委派给获授权的 agent。

任务绑定、任务同步与发布恢复归[集成规则](engineering/integration.md)和[工具指南](../tools/dev-flow/src/integration/README.md)。Git 已集成、任务接受、Issue 写回及关闭分别读回，运输成功不自动结束全部责任。

## 已有机制与待补齐的接入

下面说明已具备的能力和剩余责任。工具实现、数据覆盖、正式启用和交付接受分别核对。写进计划或生成适配文件不表示已经接通。

- 可执行验收、覆盖声明和验收锁已有工具入口。产品观察读取当前PD；缺场景正文或编号时单列未覆盖，覆盖声明保留其现行格式与来源核对。实际执行、支持和有效接受仍分别核验。接受时仍核对有效场景、本次候选和实际运行证据，覆盖声明与任务阶段不能代替它们。具体覆盖归[验证说明](verification.md)。
- 趋势已有历史快照，工具支持回退到可用的祖先记录。比较时核对当前 main 提交是否有对应快照，以及实际采用的历史范围；共享时间线可能包含不同分支的记录。没有可用数据时保持未判，不能补造主线历史。采集条件归[回路](clean-loop.md)。
- hooks 的源、配置和入口已有，本工作树的原生 Codex `Stop` 已观察到正常反馈。这只支持当次事件与受检工作树。其他宿主、`SubagentStop` 和每个隔离执行者仍须核对真实 cwd、加载、信任与反馈；命令重放不能代替原生事件验证。边界归[hooks 说明](../.meta_harness/agents/hooks/README.md)。
- Issue 协议和多层集成工具已有，日常入口的启用状态归交付配置。主干的进入由 `github-gate` 的流程执行，当前轨道以 policy registry 为准。开工前按实际任务明确本次身份、结果与条件。条件归[交付操作](engineering/agent-delivery.md)与[集成规则](engineering/integration.md)。
- 正式 `Check` 工作流当前停用，已有在线 runner 和试验工作流不构成 main 或 PR 的正式检查。共享分支与记录标签的保护按[集成规则](engineering/integration.md#轨道责任与保护)配置，执行前核对实际生效状态。合并前保留绑定候选的本地检查证据，平台接入与恢复沿[自动化入口](../scripts/README.md#ci)核对。
