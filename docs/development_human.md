# 给人看的开发指南

本页写给**指导 agent 干活、并对结果负责的那个人**。命令细节在[开发指南](development.md)，
每个检查能说明什么在[验证与证据](verification.md)；这里只讲人在这套做法里的位置：
哪几个点必须你出手，哪些可以不看，看什么信号，偏了由谁拉回。

本页跟着机制一起长：正文只写**已经建成**的入口，还没建成的在[末尾](#还没建成的)单列，建成后再并进来。

## 三句话

- **约束结果，不约束做法。**你定要什么、怎样算做成；怎么做由 agent 自己定。
- **反馈事实，不下指令。**度量、测试、归因给的是数与事实；怎么处置由看到它的人或 agent 判断。
- **阈值管边界，不管路径。**只有少数几条硬线会拦住合并，其余都是抽查线索。

写给模型的条条框框越多，它发挥得越差。所以约束放在工具和阈值上，不放在越写越长的角色说明里。
相应地，**你的注意力放在工具给出的事实上**，而不是逐条核对 agent 有没有「照做」。

## 一个需求从提出到接受，你在哪几个点出手

| 时点 | 你做什么 | 核对什么 |
|---|---|---|
| 提需求 | 说清要的可观察结果和不要什么；能切小就切小 | 一次只推进一个可以单独交付的单元 |
| 定卡的顺序 | 产品设计切成[故事卡](../.meta_harness/design/product/conventions.md)之后，看第一张卡的演示脚本，定先做哪张 | 每张卡是不是一个你能照着演示看到的结果；第一张是不是最薄的那条主路径；顺序是你定的，不是起草的 agent 替你定的 |
| 批准验收 | 实施开始之前，读这张卡的[可执行验收](workspace.md#目录与内容归属)（主会话或 qa 写的），你点头才算数 | 它验的是不是卡上演示脚本里你会看到的那几步；有没有哪一步被写成了永远会过的样子。批准之后它只读，实施的 agent 改不了 |
| 派发前 | 定写入范围、基线提交和[接受级别](#接受级别) | 任务说明里有验收清单，不是一句「按设计完成」；基线提交记下来，交回时验收锁要用 |
| 第一次能跑 | 主路径第一次跑通时（探路件或第一张卡），亲自照演示脚本走一遍 | 你看到的和卡上写的「应当看到」是不是一回事；对不上现在就说，这是改方向最便宜的时候 |
| agent 交回 | 读交付说明与度量摘要，开审讯页看结构，按级别抽查 | 见[交回时看什么](#交回时看什么) |
| 接受 | **你说接受才算接受**。接受了一张卡，它就从 `stories.md` 删掉，见下面[接受一张卡之后](#接受一张卡之后) | 提交确实落在它说的分支上；检查是在那个提交、干净的工作树上跑的 |
| 合并 | 一个单元做完就并入主线，再开始下一个 | 待合并的状态上 `make check` 全绿 |
| 之后 | 批准或驳回清理：agent 报上来的清理候选，和回路给超预算成员生成的[清理草稿](clean-loop.md#清理任务) | 位置、范围、会不会碰到正在做的东西；被标成「结构问题」的不派清理，那是你要重看拆分的信号 |

合并、推送、发布这些对外动作，agent 不会自己做，等你一句话。

**一张卡记三个时间点**：定下要做它时记 `proposed`，主路径第一次照演示脚本跑通时记 `runnable`，你接受时记 `accepted`——
各是一句 `make loop-card CARD=<卡号> EVENT=<事件>`（主会话替你敲也行，但 `accepted` 那一笔只在你说了接受之后记）。
「从提出到第一次能跑隔了多久」是这套做法最想压短的那个数，不记就量不出来。

### 接受一张卡之后

**卡是过客，接受那一刻就退场；留下来守着那几条场景的是可执行验收。**你说了接受，主会话做三件事，你核对三件事：

| 做什么 | 你核对什么 |
|---|---|
| 把卡从那个 topic 的 `stories.md` 删掉，提交带 `Accepted-Card: <卡号>`；以 squash 合入时合并说明里留着这一行 | `git log --format='%h %(trailers:key=Accepted-Card,valueonly)'` 在主线上查得到这张卡；这一行**只在你说了接受之后**才写 |
| 把验收里只在交付那一刻有意义的断言拿掉（比如「与做这张卡之前一字不差」的快照比对） | 留下的每一条都是这几条场景以后一直该成立的事 |
| 在那个 topic 的 `decisions.md` 记一笔你接受了 | 写的是你的原话，没有替你多认什么 |

之后想知道哪些场景已经交付：`make scenario-status`。它是从「有没有验收覆盖」推出来的，没有人手写。

**以后这几条场景变了**，找不到那张卡是正常的——它已经不在了：

- 场景的**含义要变**：那是改产品。旧编号作废、给新编号，为新编号立新卡；覆盖旧编号的验收会被检查点名。
- 在它上面**再多做一点**：多出来的是一条新场景，立新卡。
- **实现重构或搬了地方**：不用立卡，也不用动验收——验收只认用户入口。重构之后验收还绿，就是没把行为改坏。

## 哪些只有你能定，哪些可以不看，哪些必须逐行看

**只有你能定**

- 产品方向与先后顺序，包括故事卡先做哪张：agent 给建议和理由，拍板的是你，拍了板它才记成决定。
- 架构读数与能力怎么拆：这是你（或主会话）亲自写的东西，agent 只评审与反驳，不代写。
- 验收的内容：怎样算做成。实施的 agent 只能运行验收，不能改它。
- 阈值与硬线放在哪。
- 是否接受，是否合并。

**可以不看**

- 逐行的实现代码（下面那几类除外）。
- agent 的中间过程，以及它对自己成果的评价。

**必须逐行看**

- 身份与租户隔离、凭据、内核原语、要求同一提交的状态。这些地方**绿灯不免读**。

## 接受级别

派发时定一个级别，它决定机器先过什么、你看什么。四级的完整定义只有一份，在设计手册的
[按风险选择接受实现的看法](../.meta_harness/agents/skills/harness-design-handbook/canonical/references/handoff.md#按风险选择接受实现的看法)：

- **L0 局部修复**：看交付说明就够。
- **L1 常规增量**：看结构图上这个成员的边与着色，抽查两三个最热的函数，不逐行读。
- **L2 跨成员与装配**：再加依赖方向全图与真实组合的运行证据；不接受带跳过的套件。
- **L3 安全与不变量**：逐行读热点，并安排独立评审。

按改动触及的最高风险定，不按改动大小；拿不准就上调一级。

**什么时候另派一个 agent 来看实现。**默认不派——每个单元都派一遍会把迭代拖长。两种情形派：

- **级别到了 L2 或 L3**。L3 两个都派：实现评审逐行读热点，独立验收在干净检出上按验收标准跑。
  L2 在你读完摘要仍说不清某处时派实现评审，有可运行的交付面时派独立验收。
- **度量摘要里有实施者没交代的红项**。任何级别都可以派实现评审只看那几处，不必先上调级别。

实现评审先跑工具再按检查表问，它的每条发现要么带工具输出、要么带一个具体反例；只有品味、没有证据的不算发现，可以不理。
独立验收给的是判决和证据，**判决不是接受**。两者都替不了你：L3 的热点你仍然逐行读。
派发时不要转发实施者的完成声明，只给交付坐标、级别与验收标准。

## 交回时看什么

1. **度量摘要**（十来行，`make metrics BASE=<基线>` 打印的那段）。方向违规与环必须是 0。
   这次改动的函数里超过阈值的，每一条都要有「已处理」或「保留，理由是……」；没有交代的退回。
2. **审讯页**（摘要末行给路径，浏览器直接打开）。红边是方向违规，成员的颜色是风险，
   点一个成员能看到它连着谁、哪几个函数最热。看「这次改动把线连到了哪」比读代码快。
3. **测试摘要**（每次运行末尾打印）。是否全部通过；最慢的成员；超过时限一半的用例有没有因为这次改动变多。
4. **红灯的说法**。agent 说「是机器并发的问题」时，要它附 `make test-triage` 的输出——
   没有这份输出，这个说法不成立。输出写「隔离稳定通过」也不等于可以放行：
   贴着时限的用例要么改快，要么给一个有依据的显式时限。
5. **提交**。小步、每个都能单独说清楚；作者是你；信息末尾有 `Harness:` 与 `Agent-Role:` 两条来源。
6. **验收有没有被动过**。这次交付配了可执行验收的，跑 `make acceptance-lock BASE=<任务基线>`：
   它列出基线以来每一个碰过 `acceptance/` 的提交和它写的来源。实施角色的提交在里面就退回；
   列出来的即使写的是 `main` 或 `qa`，也看一眼是不是你批准过的那次改动——角色是提交的人自己写的。
7. **回路状态**（`make loop-status BASE=<任务基线>` 打印的那几段）。先看硬线一段：破了就不合并。
   再看「这次变更里要解释的红项」：每一条在交付说明里都要有交代。各项指标的带位是给你的，不是给实施者的——
   哪一项到了「处置」、哪个成员超了预算，由你决定现在清还是写明何时再看。

度量与绿灯是抽查线索，不是验收结论：覆盖率高不等于行为对，没有方向违规不等于架构合理。
各入口不能声称什么，写在[验证与证据](verification.md#检查入口)。

### 合并前的那一轮完整检查替你守住三条硬线

`make check` 的最后一步是严格模式的回路状态：依赖方向与环、验收有没有被实施者动过（连同删掉的卡有没有记录）、配置里开着的传感器是不是都有数据，
三条里破了任何一条，这一轮就不过。在它之前，`make check` 还会把全部可执行验收跑一遍——已经交付的场景被后来的改动弄坏，会在这里红。所以合并前你只需要确认一件事：**待合并的那个提交上，完整的 `make check` 过了。**
它拿来比的基线默认是 `origin/main`；`BASELINE=<提交>` 可以换（同一个变量也是规格冻结比对的基线，见[自动化入口](../scripts/README.md)）。

「传感器有数据」这一条的意思是：一项指标量不出数来，不等于它没问题。哪个传感器没数据，输出会指名并写原因——
多半是目录搬了、配置关了，或工具坏了。**不要为了让检查通过把那个传感器关掉**；关它是一个要写进提交说明的判断。

### 收工时的自动反馈

实施的 agent 收工的那一刻，如果它这次改了产品源码、而且留下了要解释的红项（变更函数超了线、多了跨成员依赖、
改过的测试里有不断言的用例、破了方向或成了环），宿主会把这几条读数作为事实交还给它，让它再走一轮。
**它只陈述位置与数值，不告诉 agent 该怎么改**；同一分支上同一组读数只说一次；钩子自己出错或超时从不拦人，
但会给你一句警告（「收工钩子没能量出这次变更的结构读数……」）——看到它，说明这一次的沉默不代表没有红项，原因在主检出 `tmp/clean-loop/hook.log`。

你需要知道的只有四件事：

- **它是提醒，不是门。**没被提醒不等于没有红项（没碰产品源码、钩子被关、出错时都不提醒；重复代码与覆盖率不在其中）。
  交回时照旧看交付说明里对红项的逐条交代。
- **它只量会话站着的那一棵检出。**会话留在主检出、按路径往工作树里写，它看不到。所以工作树纪律要求主 agent 建好工作树先 `cd` 进去再动手；
  你看到一个会话在主检出里直接往 `.worktrees/…` 写文件，那一次的沉默不作数。
- **它会让 agent 多跑一轮。**主会话每答完一轮都会触发一次判断；只有碰了产品源码又有新的红项时才真的拦。
- **嫌它打扰就关**：这一次会话设环境变量 `OMNE_LOOP_HOOK=off`；长期关把 `tools/ts-checks/loop.config.json` 里 `hook.enabled` 改成 `false`，理由写进提交。
- **它在你的宿主里生没生效要你看一眼**：Claude Code 新开一个会话后生效；Codex 要在 `/hooks` 里逐条信任，钩子定义一改就要重新信任。
  怎么核、还有哪些没查清，见[宿主钩子的源](../.meta_harness/agents/hooks/README.md)。

## 三类整洁各看什么信号

| | 看什么 | 什么算偏了 | 谁拉回 |
|---|---|---|---|
| **敏捷流程** | 一个单元从提出到并入主线隔了多久；并行工作树数与被几棵工作树同时改的成员数；一次提交改了多少文件；单个产品 topic 两周内 rev 翻了几次 | 分支长期不合并；几棵工作树同时改同一个成员；一次提交改几十个文件；同一个 topic 的含义反复改 | 你：先停下新的派发，把在途的并掉；rev 翻得勤说明需求没想清，回到产品设计 |
| **架构设计** | 方向违规与环；这次新增的跨成员依赖；稳定的成员依赖了不稳定的成员；总是一起改却分属两组的成员 | 新增的跨组依赖没人说得清为什么；被依赖最多的成员在变得不稳定；两个组的成员每次都得一起改 | 你：方向与拆分是你的判断，agent 只提反驳 |
| **代码编写** | 变更函数的圈复杂度与 CRAP；成员的颜色；重复代码占比；没有断言的测试；测试耗时 | 同一处超阈值连续几次交付都是「保留」；某个成员清理过又变红；测试越跑越慢 | agent 在它正在改的文件里顺手清理；超预算的成员由回路出清理草稿，你批准后专项清理；反复变红的不再清，归你重看边界 |

这些读数除了测试耗时都在 `make loop-status` 的输出里，各有三条线：过了**提醒线**要有交代，过了**处置线**出清理草稿，
回到**解除线**以下才算恢复——在两条线之间晃不算好了。带位怎么判、四条硬线是哪四条，见[整洁回路](clean-loop.md#回路怎么转)。
现在的线都是起步值，没有用真实交付校准过；觉得哪条线不对就改配置，理由写进那次提交。

## 怎样算尽责

- **作者是你。**提交记在你名下，agent 不署名；「是 AI 写的」不是理由。理由见[根 AGENTS.md](../AGENTS.md#署名与分支作者是人来源可追溯)。
- **不把 agent 的完成声明转手当验收。**它说做完了，是它的陈述；你核过提交、检查与证据，才是你的接受。
- **清理不拖。**清理候选报上来就定：批准、驳回，或写明什么时候再看。攒着不定，债只会涨。
- **改阈值留理由。**阈值是你的判断，可以改，但把理由写进那次提交；不为了让某次交付变绿而悄悄放宽。
- **排队不绕过。**`make check` 提示在排队，说明机器上已有一套在跑；等它，别手工再起一套——挤在一起只会让两边都超时。
- **agent 报停要回话。**它报出的规格冲突、验收不可达、授权不明，只有你能解；不回话它不会自己继续。

## 一天里要看的东西

- [ ] 在途的单元有几个？超过一个的话，是不是写的是互不相干的成员。
- [ ] 今天要接受的交付：摘要、审讯页、按级别的抽查做了没有。
- [ ] 有没有红灯被说成「机器问题」却没附归因输出。
- [ ] 清理候选与清理草稿有没有积压没定的；有没有成员被标成「结构问题」。
- [ ] 主线是不是绿的；不是的话，先修它，别在红的主线上继续叠。

## 每周看一次体检页

`make loop-health` 出一张离线可开的页面（末行给路径），看的是走向，不是某一次交付：

| 看哪一块 | 什么算偏了 | 你做什么 |
|---|---|---|
| 卡的前置时间：提出 → 第一次能跑 → 接受 | 「提出到能跑」越来越长；有卡停在「进行中」好几天 | 卡切得太大就再切；卡在等你裁决就先裁 |
| 每周接受了几张 | 连着两周是 0，而在途的卡不少 | 停下新的派发，把在途的收掉 |
| 各 topic 还剩几张、几张未就绪 | 未就绪的越积越多 | 它们各缺一个裁决或一份上游设计，逐个定 |
| 提交的大小 | 一次提交改几十个文件成了常态 | 要求按单元拆开提交 |
| 测试耗时的走向 | 全量一轮越跑越久 | 看耗时账本里最慢的那几个，定要不要处置 |
| 债的走向：各项指标与超预算成员的读数 | 清理过的成员又回到处置；某项指标一路往上 | 前者是结构问题，重看拆分；后者定一次专项清理或调线并写理由 |
| 传感器最近一次有数据是什么时候 | 某一项很久没有数据 | 传感器坏了或被关了——量不出来不等于没问题 |

页面上哪一块没有数据，它会写明原因，不画空图。趋势与卡的台账是从这两个入口建成之日才开始记的，头几周图上只有几个点。

## 还没建成的

下面这些已在计划里，建成后各自并进上面的正文；在那之前不要当它们存在。

- 可执行验收的放置约定与验收锁已经有了，**但还没有哪张卡真的配上验收走完整条路**：现有的产品 topic 没有回头切卡，
  第一份验收随第一张试点卡出现。
- 趋势还没有积累：「不比基线差」要靠主线提交上留的快照来比，快照是从回路状态入口建成那天才开始留的，
  在那之前的基线一律标「未判」。
- **收工钩子在宿主里只核实了一半**：Claude Code 一端 2026-10-02 在一次真实会话里见过它被调用（会话收工那个点；那一次它在刚建的工作树里
