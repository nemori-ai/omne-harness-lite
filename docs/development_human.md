# 给人看的开发指南

本页写给**指导 agent 干活、并对结果负责的那个人**。命令细节在[开发指南](development.md)，
每个检查能说明什么在[验证与证据](verification.md)；这里只讲人在这套做法里的位置：
哪几个点必须你出手，哪些可以不看，看什么信号，偏了由谁拉回。

本页跟着机制一起长：正文只写**已经建成**的入口，还没建成的在[末尾](#还没建成的)单列，建成后再并进来。

## 三句话

- **约束结果，不约束做法。**你定要什么、怎样算做成；怎么做由 agent 自己定。
- **反馈事实，不下指令。**度量、测试、归因给的是数与事实；怎么处置由看到它的人或 agent 判断。
- **阈值管边界，不管路径。**只有少数几条硬线会拦住合并，其余都是抽查线索。

写给模型的条条框框越多，它发挥得越差。所以约束放在工具和阈值上，不放在越写越长的角色说明里。
相应地，**你的注意力放在工具给出的事实上**，而不是逐条核对 agent 有没有「照做」。

## 一个需求从提出到接受，你在哪几个点出手

| 时点 | 你做什么 | 核对什么 |
|---|---|---|
| 提需求 | 说清要的可观察结果和不要什么；能切小就切小 | 一次只推进一个可以单独交付的单元 |
| 派发前 | 定写入范围、基线提交和[接受级别](#接受级别) | 任务说明里有验收清单，不是一句「按设计完成」 |
| agent 交回 | 读交付说明与度量摘要，开审讯页看结构，按级别抽查 | 见[交回时看什么](#交回时看什么) |
| 接受 | **你说接受才算接受** | 提交确实落在它说的分支上；检查是在那个提交、干净的工作树上跑的 |
| 合并 | 一个单元做完就并入主线，再开始下一个 | 待合并的状态上 `make check` 全绿 |
| 之后 | 批准或驳回 agent 报上来的清理候选 | 位置、范围、会不会碰到正在做的东西 |

合并、推送、发布这些对外动作，agent 不会自己做，等你一句话。

## 哪些只有你能定，哪些可以不看，哪些必须逐行看

**只有你能定**

- 产品方向与先后顺序。
- 架构读数与能力怎么拆：这是你（或主会话）亲自写的东西，agent 只评审与反驳，不代写。
- 验收的内容：怎样算做成。实施的 agent 只能运行验收，不能改它。
- 阈值与硬线放在哪。
- 是否接受，是否合并。

**可以不看**

- 逐行的实现代码（下面那几类除外）。
- agent 的中间过程，以及它对自己成果的评价。

**必须逐行看**

- 身份与租户隔离、凭据、内核原语、要求同一提交的状态。这些地方**绿灯不免读**。

## 接受级别

派发时定一个级别，它决定机器先过什么、你看什么。四级的完整定义只有一份，在设计手册的
[按风险选择接受实现的看法](../.meta_harness/agents/skills/harness-design-handbook/canonical/references/handoff.md#按风险选择接受实现的看法)：

- **L0 局部修复**：看交付说明就够。
- **L1 常规增量**：看结构图上这个成员的边与着色，抽查两三个最热的函数，不逐行读。
- **L2 跨成员与装配**：再加依赖方向全图与真实组合的运行证据；不接受带跳过的套件。
- **L3 安全与不变量**：逐行读热点，并安排独立评审。

按改动触及的最高风险定，不按改动大小；拿不准就上调一级。

## 交回时看什么

1. **度量摘要**（十来行，`make metrics BASE=<基线>` 打印的那段）。方向违规与环必须是 0。
   这次改动的函数里超过阈值的，每一条都要有「已处理」或「保留，理由是……」；没有交代的退回。
2. **审讯页**（摘要末行给路径，浏览器直接打开）。红边是方向违规，成员的颜色是风险，
   点一个成员能看到它连着谁、哪几个函数最热。看「这次改动把线连到了哪」比读代码快。
3. **测试摘要**（每次运行末尾打印）。是否全部通过；最慢的成员；超过时限一半的用例有没有因为这次改动变多。
4. **红灯的说法**。agent 说「是机器并发的问题」时，要它附 `make test-triage` 的输出——
   没有这份输出，这个说法不成立。输出写「隔离稳定通过」也不等于可以放行：
   贴着时限的用例要么改快，要么给一个有依据的显式时限。
5. **提交**。小步、每个都能单独说清楚；作者是你；信息末尾有 `Harness:` 与 `Agent-Role:` 两条来源。

度量与绿灯是抽查线索，不是验收结论：覆盖率高不等于行为对，没有方向违规不等于架构合理。
各入口不能声称什么，写在[验证与证据](verification.md#检查入口)。

## 三类整洁各看什么信号

| | 看什么 | 什么算偏了 | 谁拉回 |
|---|---|---|---|
| **敏捷流程** | 一个单元从提出到并入主线隔了多久；`git worktree list` 里同时在做的有几棵；一次提交改了多少文件 | 分支长期不合并；几棵工作树同时改同一个成员；一次提交改几十个文件 | 你：先停下新的派发，把在途的并掉 |
| **架构设计** | 方向违规与环；审讯页上新连出来的边；被依赖最多的成员是否简单、稳定 | 新增的跨组依赖没人说得清为什么；被依赖最多的成员复杂度在涨 | 你：方向与拆分是你的判断，agent 只提反驳 |
| **代码编写** | 变更函数的圈复杂度与 CRAP；成员的颜色；测试耗时 | 同一处超阈值连续几次交付都是「保留」；测试越跑越慢 | agent 在它正在改的文件里顺手清理；超出的列为清理候选，由你批准后专项清理 |

## 怎样算尽责

- **作者是你。**提交记在你名下，agent 不署名；「是 AI 写的」不是理由。理由见[根 AGENTS.md](../AGENTS.md#署名与分支作者是人来源可追溯)。
- **不把 agent 的完成声明转手当验收。**它说做完了，是它的陈述；你核过提交、检查与证据，才是你的接受。
- **清理不拖。**清理候选报上来就定：批准、驳回，或写明什么时候再看。攒着不定，债只会涨。
- **改阈值留理由。**阈值是你的判断，可以改，但把理由写进那次提交；不为了让某次交付变绿而悄悄放宽。
- **排队不绕过。**`make check` 提示在排队，说明机器上已有一套在跑；等它，别手工再起一套——挤在一起只会让两边都超时。
- **agent 报停要回话。**它报出的规格冲突、验收不可达、授权不明，只有你能解；不回话它不会自己继续。

## 一天里要看的东西

- [ ] 在途的单元有几个？超过一个的话，是不是写的是互不相干的成员。
- [ ] 今天要接受的交付：摘要、审讯页、按级别的抽查做了没有。
- [ ] 有没有红灯被说成「机器问题」却没附归因输出。
- [ ] 清理候选有没有积压没定的。
- [ ] 主线是不是绿的；不是的话，先修它，别在红的主线上继续叠。
