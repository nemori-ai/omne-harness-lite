# 项目要求

本页说明 omne-harness-lite 要实现什么、第一版完整交付的范围，以及全系统必须遵循的要求。它是项目级要求的唯一现行正文，供项目、产品和系统负责人，以及开发与评审人员共同阅读。

项目负责人已于2026-10-10接受本页当前正文，未决验收条件继续保留并计为缺项。2026-10-15，项目负责人接受 SYS-COMPOSITION 的装配触发、重建条件和未写版本时的选版规则。IA3的项目要求源切换以本页现行正文为准，旧foundation要求正文退出，不从旧文档补入新要求或解释。已接受架构、产品规则及实际成员承诺分别由其拥有者维护。本页不声明功能已实现，也不以目标代替交付证据。

## 系统定位与目标

### 项目定位（SYS-IDENTITY）

omne-harness-lite 是一个 agent harness，为服务组织或个人的智能体提供运行、能力调用和治理支持。Harness 负责组织模型、工具、状态和执行过程，使智能体能够在明确的权限与资源条件下工作。

本项目延续 omne-next/omne_harness 的核心设计理念和最佳实践，目标是形成更轻量化、更高性能的 OMNE harness。轻量化与性能是项目目标，具体衡量场景、基线和指标尚待确定。

### 长期运行与持续进化（SYS-LONG-RUNNING）

最终产品应能够超长期待机、稳定运行并持续进化。持久存在的定义与状态应能支撑工作延续，执行资源的生灭不应直接决定系统能否继续服务。

这一目标包括以下要求。

- 系统须支持单个会话超长程数据的持续累积，数据累积、加载与读取均有性能要求。性能评价须覆盖会话数据规模持续增长的情境。
- 智能体运行时、模型运行时和工具运行时各自须满足稳定性与故障可恢复性要求。各类运行时的具体故障范围与恢复保证由对应规格承接。

系统须针对承载会话的进程崩溃、单一模型不可用、存储暂时不可用，以及工具或某项能力暂时不可用，提供相应恢复与降级策略。单点故障的影响应当可控，不能扩散为系统性崩溃。具体影响范围、恢复条件及降级行为由相应架构和规格明确。

其他关键服务不可用时，系统应当提供兜底策略。兜底策略应当优先不产生副作用；确需产生副作用时，应将其控制在最低限度，并优先选择服务恢复后可撤回的策略。兜底仍须遵循授权、数据保护与结果真实性要求，具体副作用及撤回边界由相应契约明确。

本条描述最终产品要求，阶段交付须分别明确适用范围与验收条件。

### 服务对象与利益对齐（SYS-ALIGNMENT）

系统须在不违背组织公共利益的前提下，持续最大程度地与个人租户的利益对齐。对齐是最终产品要求，后续产品规则和技术设计均须承接这一要求。

系统须原生提供对用户的感知与观测能力，并支持这些能力持续自主演进，以支撑与服务对象的长期利益对齐。这是系统自身的能力要求，具体能力及其演进须遵循适用的租户与内容权限。

租户隔离与权限正确不能单独证明利益对齐。组织公共利益的判定、个人利益对齐的评价及这一前提下的多服务对象冲突规则，由相应产品要求承接。

## 交付阶段与功能范围

### 第一版完整交付（SYS-DEPLOY）

第一版完整交付是单机系统。设计阶段须为关键机制、模块和子系统建立清晰边界，使它们未来可以独立扩展到分布式、异构物理节点和微服务化部署，而不改变领域语义。

这一要求约束当前边界设计，不要求第一版提前交付全部分布式设施。具体功能清单与阶段验收仍需逐项明确；最终产品目标不自动等于第一版的全部交付承诺。

系统须能够通过发布时的装配设置，分别运行于用户个人设备和云端集群。两类运行环境使用同一套领域语义，由各自装配满足相应能力、资源及运行条件。环境支持目标与各阶段交付范围分别明确。

### 当前研发阶段（SYS-EXPERIMENT）

项目当前处于 `0.0.0 → 0.1.0` 的研发阶段，尚未正式上线或对外提供生产服务。本阶段鼓励一切能够带来正向收益的破坏性重构。

重构须有明确的目标与收益依据，遵循有效要求和已接受的承诺；需要改变承诺时先明确新的采用范围。同步迁移当前消费者并删除被替代实现，不为旧版保留未经要求的兼容层。验证按风险与影响选择，确认收益并核对受影响的行为。

历史材料的保留不构成兼容承诺。阶段政策在进入 `0.1.0` 时须重新评估，不自动延伸为后续版本政策。

## 内核与开放能力

### 内核能力（SYS-KERNEL）

系统使用 Cordis 提供装配、组合、依赖注入与生命周期管理能力。

### 独立使用与替换（SYS-OPEN）

各领域模块的职责、公开接口与实现独立于 Cordis。模块在满足自身声明的依赖与资源条件后，应能通过公开接口独立使用，无须启动 Cordis 运行环境。

系统集成时，各模块须遵循 Cordis 的装配、组合、依赖注入与生命周期契约。集成代码负责将模块接入这些机制，领域模块的实现不因系统采用 Cordis 而依赖其运行时。

模块及其可复用构件应通过明确的公开接口提供独立使用与替换能力。本系统是这些模块的一种使用方式，其他使用者可以在不同运行环境中组合它们。独立使用仍须满足模块自身的行为契约；由系统组合后才能成立的保证，由相应的集成与协调责任承担。

### 模型接入（SYS-LLM）

模型请求通道不设固定的全局约束。具体接入方式属于技术采用与实现事实，由相应拥有者维护；当前采用不构成必须持续遵循的项目要求。

## 多模态输入与输出

### 原生多模态支持（SYS-MULTIMODAL）

系统须原生支持多模态输入与输出。多模态内容须能按相应接口契约参与输入接入、上下文组织、能力调用与输出交付，不能仅依赖调用方将其转换为纯文本后接入系统。

当前明确需要支持文字、图片与语音。具体格式、组合方式及各阶段支持范围由相应产品与接口契约明确。本要求不表示每个模型或工具都必须支持全部模态。

## 动态演化与运行对象

### 完全动态目标（SYS-DYNAMIC）

系统以完全动态为最终目标。能力的定义、实现、绑定和组合关系应能动态演化；设计须表达能力依赖、生命周期、作用域和所有权，以及结构变化怎样影响运行。

系统须允许运行时可能发生的变化，不能因此中断运行。变化对象包括但不限于智能体定义、模型、运行时允许改变的资产（如工具、MCP、skills、loop extensions）、权限和运行模式。各类变化如何生效、如何处理在途工作及保持运行连续性，由相应架构和规格明确。

允许通过重新装配或重新实例化实现热加载，但不得因此造成系统性停机。这些机制须承接相应的状态、生命周期及在途工作处置责任。

激活能力时明确其产生的效用，卸载时明确需要撤回的逆效用、撤回条件和在途工作的处置。只登记依赖字段或做一次加载前检查，不能满足这些要求。撤回运行时资源与撤销已经发生的外部行动分别判断。

Tool 的运行时加载、卸载与替换实现已有验收判据。依据是 PanQiWei 于 2026-10-21 采用的 [RFC-0012 revision 1](rfcs/RFC-0012-tool-dynamics.md#决定范围)。常驻工具、同形、采用点、登记键与协调者的规则归 [Tool 契约](../packages/tool/tool-contract/SPEC.md#会话常驻规则r1r5)。下列判据须在真实 Cordis 4.0.4 `Context` 上可复跑：

1. 装载作者插件前后，`toolRuntime`、`toolCommands`、`toolReads`、`toolInstances` 提供者的 fiber uid 不变。
2. 同一登记键的重复登记按规则认回同一贡献，或返回 conflict。release 只撤除自己的贡献。晚到的旧 release 不删除后继贡献。
3. 贡献有会话引用且没有同形替代时，`unload` 返回 `retained`，贡献保持 live。
4. 贡献没有引用且没有在途调用时，`unload` 经 `draining` 到达 `released`。此后旧固定请求的 `resolve` 返回 unavailable，作者插件 fiber 为 DISPOSED。有在途调用时的排空依赖 Tool P09 的按执行器排空，不在本条覆盖。
5. 同一能力的新旧版本并存。已有会话解析到旧登记键，新会话解析到新登记键。
6. 同形的新版本只在采用点前进。Run 中的刷新不改变登记键。
7. 出现不同形的新版本时，会话留在旧实现，并保持可用。
8. 作者插件 fiber 被突然撤除时，会话看到带原定义的 `known-unavailable`，在途调用恢复为 unknown。重新装载后，下一个采用点判定该工具继续可用。
9. 旧实现包缺失且存在不同形的合法胜出者时，下一个采用点判定冻结。会话只进入一次冻结状态，重复判定不产生新动作。冻结后会话不再派发新 Run，在途 Run 自然收场。
10. 全过程中，无关能力的调用零失败。P16 规定的目录与 Catalog 缺席语义不变。

其他各类变化的精确连续性保证与完全动态的验收判据尚待明确。本节之后的组织要求已确定，但不能据此声称现有机制已经达成完全动态目标。

### 定义、装配与活体（SYS-COMPOSITION）

可运行对象必须区分定义、装配与活体，三者不可合并。

| 部分 | 含义与约束 |
|---|---|
| 定义 | 声明需要哪些能力的数据。可复制、迁移和长期保存，闲置不占用执行资源。定义只引用能力标识，不持有具体实现引用。工具资产 body 中的实现引用是该资产版本的声明，不是定义持有的实现引用。 |
| 装配 | 在确定时刻，把作用域内当时可用的实现绑定到一份定义的求值动作。相同定义在不同作用域可得到不同结果。 |
| 活体 | 装配产生的运行对象，持有已捕获的绑定与实际资源。活体可回收、可重建，其资源生灭与定义修订分别发生。 |

活体在执行中使用自身装配时捕获的结构性绑定，不在长时执行中途暗换这些绑定。捕获不递归冻结服务内部的数据、注册条目或下级能力。稳定能力入口内部更新实现选择，不等于入口提供者换代，也不因此要求所有消费者重建。

直接捕获的提供者发生增减与换代时，变化作用于后续装配。若要改变已存在活体的结构性绑定，须通过显式生命周期动作退役并重建，并保存业务连续性。框架卸载重跑不代替业务交接。

需要次序的撤除由本系统组织，需要被感知的撤除失败由本系统报告。不能假定内核自动提供所需次序和失败处理。装配发生在哪一层仍待具体设计。

系统只在两个入口采用新的组合。

- 新 Run 开始时，系统比较当前采用依据和这次求值。求值结果已变化时完成重装。未变化时保持当前组合。
- Run 执行中，租户通过系统 slash command 显式要求 reload。该命令沿用已有的系统工作流，不新增资产类别。

会话初始化形成会话的首份采用依据，不是重新采用新组合的入口。Tool 的采用点包括会话初始化和上述两个入口。

文件变化或 Git 同步本身不触发重装。下一次走到上述入口时，求值读取当时的来源。没有走到入口时，新的选择可以保存。保存的选择不是采用依据。正在运行的组合保持不变，并告知调用方新选择尚未采用。重装失败时保持旧的合法采用，并返回原因。

一次执行是一份采用依据从被采用到下一次成功采用之前。显式 reload 是一次新的求值。新的求值采用当时的合法胜出者。合法胜出者是同一求值作用域里、按来源层序和资格筛选后，每个能力身份的结果。能力身份是类别加 name。会话不固定任何能力的版本。会话已经采用的能力，由采用依据记下它的形状，例如会话开始时取得的 ToolDefinition 的形状。负责解析能力、选取或路由实现的一方按这个形状核对：当前装载在插件根上、同一能力身份的实现中有同形且可用的实现时，选用它，版本与记下的不同也可以；没有时，按该能力拥有者规定的不兼容后果处理，不暗换成形状不同的实现。同形判据归各能力类别的拥有者。会话常驻工具的 name 与参数形状在会话内不变，常驻工具只在采用点加入常驻集合，规则见 [Tool 契约](../packages/tool/tool-contract/SPEC.md#会话常驻规则r1r5)。同一次执行不改写已经记入采用依据的正文，也不改写已经发出的调用。尚未发出的 Tool 或 MCP 调用，仍可按合法刷新看到新的定义和可用性。这次刷新不改写采用依据里已记下的版本，也不构成新的采用。Skill 已记录的正文保持不变。尚未取用的 Skill 正文，后续取用读取当时的合法版本。同一 Run 的普通恢复保留原采用依据，不重新求值；接续所需的实现同样按形状核对选取。已经发出的调用保留原输入、实现、环境与工作区。版本变更在这条选版规则以外的治理仍待具体设计。

## 租户与身份隔离

### 从第一天支持隔离（SYS-TENANT）

受租户所有权约束的关键对象和跨边界操作须显式携带租户身份，跨租户访问默认拒绝。自然人的全局身份与租户成员关系分别表达，同一个人可以具有不同租户的成员关系，不强行归入单一租户。

隔离义务约束数据访问和跨边界操作，不能仅用服务实例可见性代替。具体账号、组织和租户的产品规则可以进一步细化，但不能削弱全局隔离要求。

## 权限管理与人在回路

### 权限管理（SYS-AUTHORIZATION）

系统须提供权限管理能力，对主体在适用租户与资源范围内的访问和操作进行授权控制。权限的授予、变更、撤销及运行时检查须有明确规则，权限管理操作本身也须受授权约束。

具体权限模型、策略、粒度及生效语义由相关产品规则维护，精确接口与验证由实际拥有者承接。

### 人在回路（SYS-HITL）

系统须提供人在回路（Human-in-the-loop，HITL）能力，使获准的人能够在规定的运行节点审阅信息、作出决定，并使系统据此继续、调整、拒绝或停止相关工作。

人介入的触发条件、可见信息、决策权限及对执行过程的影响须有明确契约。介入与等待的产品规则由相关产品正文维护，精确接口、恢复承诺及阶段支持由实际拥有者承接。本要求不表示所有动作都必须先经人工批准。

## 数据安全与隐私

### 数据保护（SYS-DATA-PROTECTION）

系统须保护用户、组织和租户的数据安全与隐私。保护范围覆盖数据的采集、处理、存储、传输、共享、保留与删除，包括用户感知与观测、模型和工具调用、持久状态、日志与遥测中的数据。

数据处理须遵循明确的目的、授权范围和适用的数据策略，仅处理完成该目的所需的数据。系统须防止未授权访问、使用、披露和篡改，并保护数据免于丢失。不同处理环节分别核对权限，已有读取权限不自动授予对外传送或其他用途的使用权限。

可观测、可遥测和自主演进不构成扩大数据使用范围的授权。向外部模型、工具或观测端发送数据时，须核对接收方、发送内容和处理目的是否在允许范围内，并按数据保护要求筛选或脱敏。凭据与其他秘密值不得作为普通日志或遥测内容发送。

## 持久状态与恢复

### 已确认业务事实的持久性（SYS-DURABILITY）

系统对业务事实作出持久保存确认后，须在普通进程崩溃、操作系统崩溃或断电后保留这些事实。范围包括已受理输入、已记录的运行进度、已承接结果、授权决定及账目。各事实拥有者须明确确认边界，并保证恢复后仍能读取和解释事实。

此要求不自动涵盖可重建缓存、未承诺持久保存的在途流片段，或存储介质及整机物理损毁。持久保存、灾难备份与业务恢复分别验收。确认响应丢失时，调用方须按原操作身份核实结果，不能将未收到确认等同于未保存。

这一要求约束系统保存业务数据的行为，不改变当前研发阶段允许破坏性重构的政策。接口与数据格式可以演进，具体迁移和验证按影响范围设计；明确可重建的开发数据与需要保护的业务数据分别处理。

### 运行时解耦与接续（SYS-RUNTIME-CONTINUITY）

Agent 的运行时应与 Agent 状态持久化解耦。系统应能依据持久状态，在同构资源下恢复 Agent 并接续运行；同时应能针对异构运行时采用相应装配策略或部署版本，适应不同物理环境与操作系统。

恢复的具体判据尚未确认。后续核对须区分重启运行时、恢复持久状态与接续既有工作，也须区分持久状态、可重建状态、临时对象和未完成的外部行动。创建空白实例不足以说明已经恢复持久状态，持久历史本身也不能证明中断时的外部行动已经完成。这些区分用于展开恢复目标，不额外规定已确定的状态清单或恢复协议。

解耦不预先要求运行时与存储位于不同进程、机器或数据库。同构恢复与异构适配分别成立，不能据此承诺任意异构环境之间都能直接恢复同一执行状态。自动故障接管、热迁移与调用恰好执行一次也尚未据此定案。

## 工程观测与结果真实性

### 全链路可观测、可遥测与日志完备（SYS-OBSERVABILITY）

所有能力及其组合须具备工程诊断所需的观测与日志。工程人员应能追踪一次工作从入口到实际结局，判断是否接受、到达哪个阶段、等待什么、失败在哪里，以及哪些结果仍未知。面向用户的状态界面不能替代工程观测。

观测范围包括适用的用户、外部信号和日程入口，身份与授权、配置与装配、会话与执行步骤、模型与工具、子代理、后台工作、人介入、外部连接、知识与认知服务、制品、持久化与恢复，以及回复与通知交付。没有会话的系统工作同样须可观测。这一覆盖义务适用于相关能力交付时，不据此增加第一版功能清单。

具体义务包括以下各项。

1. 跨异步消息、排队、派发、后台脱离、进程、节点与运行时重建，保留适用的租户、主体、工作身份与因果关系。区分同一逻辑工作、各次尝试和运行时实例，并关联实际模型、插件与配置版本及执行环境。时间戳先后、因果先后和同一工作归属分别表达。
2. 接受或拒绝、开始、等待、恢复、取消或中断请求及实际结果、完成或失败、重要配置与权限及插件变更，以及未知外部效果，均有可定位、可解释的记录。失败信息应能定位所属阶段和组件。错误不能静默吞掉，缺少终态不能冒充仍在运行，日志不能只依赖已销毁运行时的控制台。
3. 延迟、排队、吞吐、失败、资源压力、能力就绪、持久化与交付进度须有必要数据，并能与工作轨迹和日志关联。逐步骤金额及财务事实由账目拥有者维护，遥测估计和采样不能冒充完整账单。
4. 采集、传输、存储、导出与查询故障，以及延迟、采样、丢弃和保留期到期造成的缺口须可见。关键生命周期、失败与审计事实不能因普通诊断采样而无声丢失。缓存、资源占用与保留策略须有边界；缺必要记录时按明确策略阻止依赖动作、保留待补记录或报告未知，不能制造假成功。
5. 获准研发、评估和诊断主体应能查询、导出程序化记录，展示界面使用同一依据。采集、保留、查询和导出均遵循租户与内容权限，秘密值须脱敏或排除。日志完备不要求无限保存全部原始内容，也不要求获取模型未提供的内部推理过程。
6. 能力、插件和跨边界流程的设计与验证须明确正常、拒绝、异常、中断、重试和恢复路径的观测责任与缺口处理。验证应能凭记录判断发生的结果，不能只证明代码输出过日志；未覆盖范围与故障假设须如实说明。
7. 系统须支持遥测，按配置采集并向获准的观测端传送运行指标、日志与调用链等观测数据，支持远程监测与诊断。遥测的采集、传输与接收须遵循租户与内容权限，传输失败及数据缺失须可识别。

遥测须遵循本页的数据安全与隐私要求。启用遥测不自动授予采集或对外传送用户数据的权限。

观测读取不重新执行动作。业务持久事实、工程遥测和面向用户的披露权限分别判断。具体事件、指标、保留时限、故障策略与性能目标由相应承诺拥有者展开，本页不指定观测后端或部署拓扑。

## 承诺与验证的表达

### 接口、行为与验证责任（SYS-SPEC）

公开 TypeScript 类型与必要运行时校验表达模块的形状。类型无法表达的不变量、失败、副作用、并发、取消和恢复承诺，由公开接口拥有者在模块旁维护薄规格。实现不能代替承诺。

重要隔离、事务、恢复与进展问题须保留相称的模型、探针或故障测试。每份证据说明前提、覆盖范围和未覆盖项，类型检查或一次测试通过不构成无条件证明。

项目要求约束系统架构，架构承接到领域和实际成员，再由实现与验证兑现。具体产品场景、技术选择、成员行为和研发方法由各自拥有者维护，本页不代写这些正文。验证强度按风险与影响选择，不能因要求完整就对所有任务机械执行全量检查。
