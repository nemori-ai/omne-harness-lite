# Agent runtime 与 Agent Loop

Agent Loop 根据显式工作事实和当下条件求出下一步。会话路径由 Session 适配器提供这些事实。Agent runtime 执行这个决定，发起调用，并从工作日志取得模型结果及处理进度。工具结果继续按自身交接协议承接。Loop 规则没有实例寿命；Agent runtime 可以退出或替换，原 Run 和它调用的执行不因此结束。

状态：已接受的目标架构。契约类型与 Cordis 服务定义已在 [agent-contract](../../../packages/agent/agent-contract/src/index.ts) 与 [agent-cordis-contract](../../../packages/agent/agent-cordis-contract/src/cordis.ts) 实现。Loop、runtime 与提供者尚未实现。Session、Run 和 attempt 的身份及推进权归[会话治理](session-and-run.md)，扩展的详细规则归[Loop extensions](loop-extensions.md)。

## 可随时重装配的运行实例

Agent 是可随时重装配的运行实例，不持有第二份权威工作状态。会话场景从[会话日志](session-and-run.md#h1-session-facts)中的 Agent 执行记录重建事实与原消费位置，再接续原工作。实例内的视图、缓存和局部计算都可丢弃，不能成为恢复的唯一依据。

Agent 独立能力不依赖 Session 契约。独立调用者提供本域的日志、持久与准入依赖，会话装配则由 Session 日志承载 Journal。重装配不终结原模型调用，也不接管观察者的连接或模型 ACK。

## 启动与运行条件

系统协调者启动会话推进前取得已校验装配、Run 与 attempt、原消费位置、日志读取范围及当前条件。会话处于冻结状态时，系统协调者不派发新 Run，在途 Run 继续收场，见[生命周期与工作收束](session-and-run.md#生命周期与工作收束)。它将关联映射为 Agent execution、当前 execution attachment 和公开输入，Agent 核心不依赖 Session 的具体治理接口。协调所需条件包括推进要求、当前资格、能力可用性、模型与窗口、Runtime Context、执行环境及必要资源。Agent 使用各拥有者给出的消费事实，不解释权限模式或维护环境选择状态机；实际发起仍由受信准入及围栏核验。

这些输入各有来源与生效时刻。日志负责已经发生的事实，不独自提供全部当前输入。历史授权用于解释旧执行，不能授权未来动作。不能把权威推进状态只保存在停机后无法恢复的 Agent runtime 内部。

恢复实例先完成原工作对账。存在未完成的模型调用、工具调用或扩展等待时，先接续它们，再判断是否发起新工作。装配失败、无法取得必要输入和暂时等待分别报告。

## 实例、执行与执行挂接

Agent runtime 可在一次工作完成后保持空闲和注册，后续执行复用装配及可重建缓存。一次逻辑执行的输入、调用、经过、等待和输出按执行身份保存到工作日志。会话路径使用会话日志，不另存 Agent 权威记录。更换物理实例沿原执行恢复，取得新执行挂接资格。顺序新执行不得复用旧授权、取消状态或输出游标。

Session 拥有 Run 及 attempt，外部适配器保存 Run/execution 和 attempt/execution attachment/runtime 的关联。Agent 条件性结束本域执行。会话专用提供者把 Session 输入受理、当前输入/等待/控制核验及普通 Run 终结纳入同一提交边界；已受理而通知延迟的输入不能遗漏。事件流结束或 Agent 对象退出不代替 Run 终态。Run 已完成不强制注销空闲 Agent，也不自动取消独立 Model/Tool 工作。

具体 OOP、接口及状态归 [Agent 对象模型](../../../packages/agent/agent-contract/docs/object-model.md)。独立调用者提供合格的本域持久和准入依赖，不虚构 Session/Run，也无需返回完成批准；系统路径仍兑现 Session 的唯一推进和终态规则。

## 一轮推进

```mermaid
flowchart TD
    Intake[承接当前批次输入] --> Context[上下文组装<br/>模型前扩展与输入固定]
    Context --> Model[模型执行、收场<br/>与回复准入]
    Model --> Actions[逐动作扩展链<br/>与本批人工答复]
    Actions -->|有获准动作| Tools[执行获准动作<br/>可靠承接工具结果]
    Actions -->|无获准动作| Next{下一步}
    Tools --> Next
    Next -->|有输入或需继续| Intake
    Next -->|继续等待| Wait[保存等待位置<br/>条件满足后再求值]
    Wait --> Next
    Next -->|完成候选| End[终态前扩展<br/>与终态记录]
```

图展示正常循环。恢复时先回到原调用或等待位置，取消和失败按各自路径收束；不能直接跳到下一次求值，也不能用一次函数返回当作全部调用收场。具体推进顺序如下。

1. 优先处理已生效取消、既有终态及原调用，恢复原消费位置。
2. 承接当前批次输入，取得本步可使用的事实与条件。
3. 通过[请求上下文](request-context.md)取得可发送输入，不能装下时按既有失败规则收束。
4. 执行模型调用前扩展，必要时重新组装，再固定输入并登记调用。
5. 从日志取得原模型调用的结果与真实收场事实，执行模型后及消息入口扩展。
6. 对每个动作执行自己的有序扩展链。不同动作可并行判断，整批判断完成前不发出已经获准的部分。
7. 等待本批人工答复后继续原扩展位置。获准动作通过授权、环境及资源检查后执行。
8. 取得前台结果或合法后台占位，可靠承接结果，经过执行后扩展，再次求值。

step 用于标识一次 Loop 推进单元，不能替代实际调用身份。同一步允许多个工具动作。模型回复被入口否决后，原调用已收场，后续模型调用是新调用，不能伪装成原调用内部重试。step 的精确切分归成员机制设计；否决历史沿原工作保留，不因新 step 或实例变化清零。

## 回复准入与动作处理

模型返回的是候选回复，模型 runtime 不执行其中的工具建议。Agent runtime 对完整回复进行准入和动作解析。未完整到达的参数块不能发起工具执行。

消息入口否决按来源分别处理。外部输入拒收并记录原因。模型回复被否决时保留原调用结果，退避后可创建新调用。连续否决不设次数上限。否决历史保留，不因此使 Run 失败。工具结果被否决使 Run 失败，不能重跑工具来制造另一份结果。

模型已经展示的原文不能由后续扩展改写。模态转换可以按契约追加派生表示，不能伪造原始内容。动作参数改写保留原参数与生效参数，后续准入、人工确认和执行必须针对同一生效参数。

## 下一步与完成条件

没有动作不直接等于工作完成。Loop 仍须检查新输入、未完成等待、协作模式及终态前扩展。

前台工具必须交回本步所需的结果；符合工具声明的后台占位可以使本步继续。后台工具仍有真实执行和后续结果责任。所有动作被否决后也须重新求值，不能把“没有发出动作”当成完成目标。

### 完成条件与终态

Agent 执行满足候选条件时，执行终态前扩展。会话路径将该候选关联到原 Run，终结协议由 Agent SPEC 的[条件终结](../../../packages/agent/agent-contract/SPEC.md#条件终结)与[提交参加者协议](../../../packages/agent/agent-contract/SPEC.md#提交参加者协议)细化。扩展可要求继续、等待或否决完成候选或失败候选。取消候选不经过这些扩展，由系统的受信只读核对决定 Agent 能否结束这次执行，规则见 Agent SPEC 的[取消判断与路线](../../../packages/agent/agent-contract/SPEC.md#取消判断与路线)。只有实际记录的终态才生效，随后执行终态后扩展。后置扩展不能撤销已成立的终态。

失败和取消也经过适用的终态路径，不能由普通消息冒充。终态后禁止发起新的工作，迟到结果与费用仍可记录。真实收场、逻辑终态、结果消费及资源清理分别判断。

## 调用关联与可接续性

每次模型调用、工具调用和扩展调用都须有独立身份，关联本域执行、执行挂接、step、动作及原消费位置。会话适配器同时保留原 Run 与 attempt 的映射。跨 attempt 接续使用稳定工作关联，不能仅凭 Session、Run、step 三项区分同一步的多个效果。

| 原调用用途 | 结果必须返回的位置 |
|---|---|
| 主流程模型回复 | 原模型回复处理节点。 |
| 压缩内部模型调用 | 原压缩计算与摘要提交节点。 |
| 扩展中的模型判断 | 原扩展调用与判断位置。 |
| 工具执行 | 原动作及结果处理节点。 |

扩展中的模型结果不能直接当成主流程回复。新的推进者不得因失去旧实例内存而重复付费判断或重做工具效果。结果保管遵循[流式与消费](streaming-and-consumption.md#可靠承接与原消费位置)。

## 长期运行与验证义务

Loop 读取有类型的推进事实，不解码 Model/Tool 内部状态或读取 Session 治理对象。效果协调者关联原调用与控制，并从日志投影模型的真实收场和处理进度。Agent 对 Model 的实时调用只有 `admit` 与 `cancel`，其余模型事实经日志到达。Model 的观察与读取操作由 Agent 外侧的观察者使用，恢复时取回账目的 dispatches 由结果接收方使用。结果接收方是 Agent 外侧的角色，由 Agent 宿主装配并常驻，不是 Agent 实例，不随 Agent 实例重装配丢失状态。结果接收方保存模型结果后返回 saved，Model 以原 evidence 沿专用 ACK operation 自己取得 ACK。ACK 未知时 Model 沿原 query 认回。这些操作都不交给 Agent。工具的等待、后台占位与交付责任仍按工具契约处理。Loop 不要求每次扫描全部会话历史。派生投影和缓存须可重建，并标明其对应的事实范围。性能优化不能遗漏新输入、未完成等待或取消意图。

循环守卫根据原始事实计算，不能因压缩或更换 attempt 清零。预算、时限和轮数采用明确策略，不在架构中虚构统一上限。实现验证须覆盖重复触发、推进者竞争、等待后替换实例、迟到结果及终态后禁止新发起。
