# 时间

一个装配好的系统只有一个时间源。它拥有一条时间线：两个读数，两种等待。系统里读时间和等时间的每一处都经过它，所以整条时间线可以整体换成模拟的。本页说明时间在系统里起什么作用、怎样和各领域解耦、装配时怎样提供、哪些可以由人设置。成员的精确承诺归 [`packages/assembly/SPEC.md`](../../../packages/assembly/SPEC.md#时间源)。

## 时间起的五个作用

| 作用 | 读哪个读数，用哪种等待 | 例子 |
| --- | --- | --- |
| 给事实打时间戳 | 墙钟读数 | 会话日志里一条记录的时刻、遥测记录的时刻 |
| 期限与等待 | 单调读数；「过多久」的等待 | 排队时限、重试间隔、心跳、空闲关闭 |
| 计划与日程 | 墙钟读数；「到几点」的等待 | 定时任务到点触发、会话空闲到点归档 |
| 告诉 agent 现在是什么时候 | 墙钟读数 | 经 Runtime Context 供给的当前时刻 |
| 账目与遥测里的时长 | 单调读数 | 一次调用花了多久 |

时间戳不决定先后。先后由日志位置与因果关联表达，见[时间、顺序与版本](../cross-cutting-concepts.md#时间顺序与版本)。

## 时间源

时间源回答四件事。每个钟各有一个读、一个等。

| | 墙钟 | 单调钟 |
| --- | --- | --- |
| 读 | `now()`：UTC 历元毫秒 | `elapsed()`：毫秒，只在同一个时间源内相减与比较 |
| 等 | `at(时刻, 回调)`：墙钟到了这个时刻就调一次 | `after(毫秒, 回调)`：单调读数增长这么多就调一次 |

两种等待都返回取消。睡眠、超时、心跳、周期任务是这两种等待之上的组合，由成员给出。等待和读数在同一条时间线上：一次 `after(d)` 在单调读数恰好增长 `d` 时到点，不需要调用方把「睡了多久」和「钟走了多久」对齐。

墙钟可以被改，单调读数不回退。墙钟被改时，「到几点」的等待按新读数重新核对，「过多久」的等待不受影响。这与操作系统里两类定时器的行为相同。

一个时间源是一个普通对象。同一个进程里要同时跑几条互不相干的时间线，就建几个，各给各的系统。

## 和各领域的关系

各领域继续声明自己的时钟端口，继续决定到期边界与时间读不到时的行为。时间源在端口的下面：

- 只有系统时间源读宿主的时钟与定时器。别处的生产源码不直接取时，由规则 `no-wall-clock` 守。
- 应用的装配把同一个时间源适配成各领域的时钟端口。领域的契约不依赖时间源这个成员。
- 领域实现内部的等待（排队时限、观察时限这一类）接收装配交来的时间源。没有改到的地方仍直接起宿主定时器，列在本页的[差距](#差距)里。

## 四种推进方式

| 推进方式 | 时间怎样前进 | 用途 |
| --- | --- | --- |
| 真实 | 宿主的时钟与定时器 | 发行的系统 |
| 手动 | 只有驱动方推进才走。到点的等待按「到点时刻，登记次序」依次触发 | 单元测试、契约测试 |
| 空闲就跳 | 没有在途的活、只剩等待时，直接跳到最近的一个到点 | 集成测试、agentic 验证、实验、仿真 |
| 倍速 | 跟着另一个时间源走，流逝乘一个系数。缺省跟着系统时间源 | 给人看的演示与回放 |

手动与空闲就跳两种方式下，时间的前进与机器的快慢无关。同样的输入得到同样的触发次序，所以用它们跑出来的裁定只由输入决定。跟着系统时间源的倍速仍随宿主的时钟走，不用于判定。

空闲的判断靠登记，不靠静默的时长：一件不靠时间流逝也会有进展的活（一次发给 Worker 的请求、一次在途的模型调用）开始时登记，结束时放手。登记数为零并且还有等待者时才跳。

驱动方可以要一份时间线记录：每次登记、触发、取消与改钟各一行。两次运行的记录可以逐行比较。

## 读的一方和驱动的一方

被驱动的系统拿到的是时间源本身，只有两个读数和两种等待。推进、改钟、登记在途、读记录这些在控制面上，只有驱动方持有。持有时间源不能推出控制面。

## 装配

时间源是装配入口最先准备好的运行时对象。一次运行只建一个，入口提供的各个时钟对象都从它适配，见[运行时对象](application-assembly.md#运行时对象)。

用哪一种推进方式由装配决定，不由环境变量或插件配置决定：

- 发行的服务端装配只构造系统时间源。它的源码里不出现模拟时间源的构造。
- 测试装配与实验装配构造模拟时间源，并自己持有控制面。

一个用模拟时间的系统是一个独立的系统实例，有自己的状态目录。它打出来的时间戳只在这个实例里有意义，不和真实时间的实例共用存储。领域的时钟采样带着时钟协议的名字（例如 `SessionClock` 的 `ClockSample.protocol`），模拟时间源适配出的采样使用另一个协议名，两种事实可以分辨。

## 可以由人设置的三样

这三样是三件不同的事，各有拥有者。

| 设置 | 它是什么 | 拥有者 | 影响时间源吗 |
| --- | --- | --- | --- |
| 时区与显示格式 | 一个时刻怎样显示给某个人 | 展示这一侧：设置项与界面 | 不影响。时间源只给 UTC |
| 时间的来源与健康 | 这个系统实例用的是哪一个时间源；宿主的钟有没有跳 | 运维与装配 | 它就是装配的选择，运行中不可改 |
| 模拟时间的控制 | 暂停、步进、跳到某个时刻、倍速、看还有哪些等待 | 实验装配的驱动方 | 是控制面本身 |

模拟时间的控制是一项特权。要让客户端使用它，按接入层的规矩另开一个协议，只在实验装配里挂出，并且经治理许可。「挂没挂着」和「许不许用」仍是两件事。

## 出线程与出进程

时间源在一个线程里。Worker 线程与子进程里的时间目前不在它的管辖内。目标做法：

- 线程：时间源把当前读数与最近的到点放进一块共享内存。Worker 里的视图读同一块内存，同步的等待挂在上面，时间推进时被唤醒。
- 进程：父进程起子进程时交给它一个通道，子进程的时间源经它读数与登记等待。
- 执行环境里代工具起的进程读的是宿主的钟。模拟的系统实例要让这些进程看到同样的时间，由执行环境在起进程时注入。

## 借鉴

这套设计没有新东西，每一块都有先例。

| 这里的 | 先例 |
| --- | --- |
| 一个系统一个时间源，别处不碰宿主时钟 | 操作系统内核的计时核心 |
| 墙钟与单调钟各有读与等；改墙钟只重核绝对时刻的定时器 | POSIX 的 `CLOCK_REALTIME` 与 `CLOCK_MONOTONIC`，`clock_gettime` 与 `clock_nanosleep` |
| 空闲就跳 | 无滴答内核在空闲时直接编程到下一个定时器；离散事件仿真；Go 的 `testing/synctest`、Tokio 的 `time::pause`、Temporal 测试服务的跳时 |
| 同样的输入同样的触发次序，记录可比较 | 确定性仿真测试 |
| 线程读共享内存里的时间 | vDSO 的时间页 |
| 模拟的系统是独立的实例，带自己的时间状态 | 虚拟机的虚拟时钟 |
| 改钟是特权 | `CAP_SYS_TIME` |
| 时区是展示，不是时钟 | 系统设置里时区与时间分开 |

## 差距

下面几样是目标设计，还没有实现。实现之前，依赖它们的做法不成立。

| 差距 | 现状 | 影响 |
| --- | --- | --- |
| 出线程、出进程的共享 | 没有。Worker 与子进程读宿主的钟 | 存储写线程里的组提交收集窗与检查点间隔、发行树里起的真实服务端，不受模拟时间控制。仓库的令牌池脚本跑在自己的进程里，又只用 Node 标准库，它的心跳过期用例靠改登记文件的时刻与一个按文件偏移的钟来控时，用不上时间源 |
| 服务端应用里各行的读时改走装配给的时间源 | 入口的四个时钟对象（会话、Agent、Model、身份）已经从它适配。治理、设置、遥测、Tool 运行时四行，以及 `tool-host-local` 的本地时钟与日历的应用时钟，仍各自读宿主的钟 | 模拟的系统实例里这几处仍是宿主时间 |
| 领域实现内部的等待改走时间源 | 接入层入口已经做到：收场宽限、心跳与每轮复核登录都登记在入口收到的时钟上，服务端应用的入口行拿系统时间源适配出这个时钟。这一行自己建了一个系统时间源，拿不到装配的那一个。存储提供者等其余成员仍直接起宿主定时器 | 模拟的系统实例里，接入层入口的等待仍按宿主时间；其余成员的用例各自想办法不等墙钟 |
| 禁止生产源码直接起定时器的规则 | 没有。`no-wall-clock` 只管读 | 新写的代码仍可能绕过时间源 |
| 各在途调用登记，使整个服务端能在空闲就跳下运行 | 没有 | 空闲就跳目前只用于进程内、不含真实 I/O 的装配 |
| 实验装配的启动入口、时间状态随系统实例保存 | 没有 | 模拟的系统实例重启后时间从哪里接着走，没有答案 |
| 模拟时间的控制协议与界面 | 没有 | 只能在代码里驱动 |
| 时区与显示格式的设置 | 没有 | 界面按各自的缺省显示 |
| 各领域 `./testing` 里的手动时钟改成模拟时间源的适配 | 没有，各写各的 | 同一件事有多份实现 |
