# 架构目标与约束

本页说明决定架构方向的工作情境、质量目标及必须遵循的约束。它为后续结构、运行、数据和部署设计提供判断依据。

状态：已接受的目标架构。已接续负责人明确的代表情境、质量优先级、运行环境及相关要求，并从现有产品正文提炼权限与 HITL 的架构影响。具体未决项和旧源切换按[架构入口](README.md#采用状态与当前有效源)处理。

## 上游依据与适用范围

[项目要求](../requirements.md)拥有系统目标和全局要求，[系统边界](context-and-scope.md)说明系统责任及外部环境。本页承接这些要求，说明架构方案应在哪些情境下比较，以及取舍时优先保护什么。

代表工作情境是单个会话的超长期运行与多智能体并行。架构评价须同时考虑会话数据持续增长，以及多个智能体共享资源和能力时的影响。并行不预先规定每个智能体独占进程或节点。

文字、图片和语音是当前明确需要支持的输入与输出模态。具体格式、组合方式和阶段支持范围由相应产品与接口契约细化。

最终产品目标、第一版完整交付范围与当前研发阶段分别判断。第一版完整交付采用单机范围；当前处于 `0.0.0 → 0.1.0` 研发阶段。代表情境用于评价架构，不自动补成第一版的完整功能清单或验收阈值。

## 关键质量目标

### 取舍优先级

在满足有效要求和已接受承诺的方案之间，按以下顺序考虑质量目标。

| 优先级 | 目标 | 架构需要保护的性质 |
|---|---|---|
| 1 | 长期运行与恢复 | 超长期会话能够持续工作，状态与执行资源分别管理，故障影响可控并有相应恢复和降级策略。 |
| 2 | 速度与吞吐 | 关注首次输出、会话创建、数据加载及多智能体并行时的处理能力，能定位主要耗时和等待。 |
| 3 | 动态演化 | 允许运行时可能发生的变化，不能因此中断运行；各类变化的生效及在途工作处置有明确责任。 |
| 4 | 维护效率 | 职责、契约与依赖清晰，修改影响可识别，便于人和 agent 理解、维护及验证。 |
| 5 | 低资源占用 | 尤其关注待机时的资源占用，区分持久数据、可重建状态和需要活跃运行的资源。 |
| 6 | 模块独立使用 | 领域模块满足自身前提后可脱离 Cordis 使用，系统集成由明确代码和契约承担。 |

排序用于架构取舍，不取消低优先级目标，也不允许突破隔离、授权、数据保护和结果真实性要求。模块独立使用仍是有效要求，不能以排序靠后为由让领域实现依赖 Cordis 运行环境。

### 运行时变化与连续性

架构须识别运行时哪些对象可能变化，允许这些变化，并保持运行连续性。变化对象包括但不限于智能体定义、模型、工具、MCP、skills、loop extensions、权限和运行模式。

允许通过重新装配或重新实例化实现热加载，但不得因此造成系统性停机。各项变化如何生效、如何交接生命周期及处理在途工作，由相应运行、数据和安全设计说明。定义、装配与活体仍分别表达，重装配须承接相应的连续性责任。

### 持续的利益对齐

系统须在不违背组织公共利益的前提下，持续最大程度地与个人租户的利益对齐。原生的用户感知与观测能力为这一目标提供支持。架构须承接组织公共利益约束与个人利益对齐目标，以及持续理解用户所需的能力。感知能力的演进服务于对齐目标，不能用系统自主改变了多少东西来替代对齐判断。

本项是长期承诺。当前 `0.0.0 → 0.1.0` 阶段不开展持续利益对齐的专项设计与实现，也不要求在本阶段完成组织公共利益判定、个人利益评价、用户感知与观测范围及相关演进验收的细化。这些事项不阻塞当前系统分解和其他能力设计；进入该专项时，再由产品要求及相应架构专题明确范围与责任。

本阶段的暂缓不改变现行租户隔离、授权、数据保护、工程观测与结果真实性要求，也不将满足这些要求表述为已经实现持续利益对齐。

### 长期会话与并行工作

超长期会话的数据累积、加载与读取均有性能要求。评价应覆盖数据持续增长后的表现，不能仅观察新建或短会话。多智能体并行时，也须核对共享能力、存储和执行资源对各项工作的影响。

轻量化重点包括待机资源占用、首 token 到达时间（Time to First Token，TTFT）、会话创建及相关数据加载，以及模块化程度。资源消耗与延迟分别评价，模块化同时影响维护和独立使用。

TTFT 的计时起点及首 token 判据由具体测量场景明确。入口到首次输出的端到端时延与模型调用自身的首 token 时延分别报告，不能用后者代替前者。会话创建、数据加载、排队与模型调用的耗时应可区分。具体规模、基线和目标数值后续确定。

### 单点故障的影响控制

以下情境是当前明确需要承接的恢复与降级场景。

| 故障情境 | 需要控制的后果 |
|---|---|
| 承载会话的进程崩溃 | 区分执行资源丢失、持久状态及未确认的外部效果，按相应契约恢复或接续工作。 |
| 单一模型不可用 | 明确依赖该模型的工作如何等待、降级或恢复，控制影响范围。 |
| 存储暂时不可用 | 明确无法可靠读写时哪些动作可继续、哪些必须等待或停止，避免假报持久化成功。 |
| 工具或某项能力暂时不可用 | 明确受影响的工作与可用能力，提供相应降级及恢复策略。 |
| 其他关键服务不可用 | 提供兜底策略，尽量避免副作用；必要副作用控制在最低限度，优先选择服务恢复后可撤回的策略。 |

单点故障的影响应当可控，不能扩散为系统性崩溃。故障影响由依赖关系和共享资源决定，须说明受影响范围；共享存储不可用时，可能有多项工作需要共同等待或停止。

兜底策略应当优先不产生副作用。确需产生副作用时，应将其控制在最低限度，并优先选择服务恢复后可撤回的策略。具体副作用、撤回条件与不能撤回时的处置由相应契约明确，不据此承诺所有外部效果均可撤销。

恢复与降级仍须遵循授权、数据保护和结果真实性约束。替换模型、切换能力、重试或等待的具体策略由后续设计明确，不能默认自动切换到任何可用提供者，也不能将未确认的外部效果当作未发生。

### 权限管理的架构影响

权限管理承接现有产品规则。资产声明设置与权限项，具备相应资格的层配值，运行时按实际来源及作用域求值。设置覆盖、权限收窄和执行环境选择分别处理，不能合并成一个宽松程度开关。

| 产品规则 | 架构需要承接的责任 |
|---|---|
| 外层锁定的权限边界不能被内层突破；明确禁止不能被会话授权或运行模式覆盖 | 将配置、求值和动作准入的责任分开，保留依据和适用范围。资产替换、工作区内容及授权表达均不能成为提权通道。 |
| 工作区提供能力和偏好，不提供授权；子代理权限不得超出父方与自身请求的交集 | 区分能力来源与授权来源，沿委托关系携带必要身份和权限边界。 |
| 权限设置、会话授权表达与运行模式共同参与动作准入；授权与撤回均有记录 | 当前准入依据与既往采用值分别维护，不能把一次判断缓存成永久放行。会话运行模式只处理应当请求授权时的行为，不消除明确禁止。 |
| 放行判断不可用时拒绝需要判断的动作；动作许可与执行落点许可分别判断 | 安全能力不可用时不能跳过准入；要求隔离环境而该环境不可用时，不能回退到更宽松的宿主机执行。 |

完整求值与授权规则由产品拥有者维护，本页不另定义权限模型。已有放行结论、后续准入及权限变化对在途动作的生效边界，由相关运行契约承接。

### HITL 的架构影响

HITL 承接工具中的人介入、系统的动作放行判断，以及产品已定义的 loop 拓展等待。工具执行的等待与 Run 的等待是两个生命周期；当前版本要求人应答的工具执行只在前台等待。其他会话不应因某个会话等待而被整体阻塞。

| 产品规则 | 架构需要承接的责任 |
|---|---|
| 需要人输入的等待统一进入租户范围内的决策池 | 卡片携带足够的判断信息，关联所属会话、实际等待者与解除条件。访问和答复沿会话权限判断，不能混合不同租户的卡片。 |
| 人可以在会话或决策池回答；同一张卡片只能答一次，同批全部处理后才解除阻塞 | 两个入口使用同一份卡片状态。区分批准、拒绝、明确不回答及作废，不能把解除等待等同于获得授权。 |
| 等待没有超时默认答案，系统不替人作答 | 等待须有可保存、可恢复的记录，不能仅保存在活跃协程中。执行已终局的卡片按相应规则作废，不伪造人的答案。 |
| 等待期间会话照常收消息和后台通知，排队后由当前 Run 处理；中断是立即处理的控制动作 | 输入受理、工作推进、决策等待和控制通道分别管理，不因等待拒收消息，也不因新消息另起 Run 绕过等待。 |

权限与 HITL 的产品依据归[PF-002](../../.meta_harness/design/product/PF-002-assets-settings-and-permissions/README.md)、[PF-007](../../.meta_harness/design/product/PF-007-meta-capabilities/README.md)、[PF-008](../../.meta_harness/design/product/PF-008-human-in-the-loop/README.md)及[PF-015](../../.meta_harness/design/product/PF-015-session-lifecycle-and-ownership/README.md)，相关执行与恢复边界沿各 topic 的依赖定位。具体采用范围以这些拥有者的接受记录为准；PF-008 仍保留 rev 6 待确认范围，本页提炼不提升其采用状态。

### 验证承接

[质量与符合性](assurance.md)承接上述目标的验证场景与证据范围。结构专题明确责任和依赖；运行专题说明变化、故障与降级；数据专题明确状态、持久化及恢复条件；部署专题说明资源与故障域。精确接口和行为由实际拥有者维护。

评价须说明情境、前提、实际结果和未覆盖项。当前没有给出并发数、会话规模、性能阈值、恢复时间或数据损失边界；本页也不据此声明已有实现达标。

## 技术与组织约束

系统采用 Cordis 提供装配、组合、依赖注入与生命周期管理。领域模块独立于 Cordis 建模和实现，集成时遵循相应契约。定义、装配与活体分别表达，已捕获的结构性绑定按明确生命周期改变。

第一版完整交付采用单机范围，关键边界须支持未来独立扩展到分布式、异构节点和微服务部署，且不改变领域语义。当前阶段鼓励有正向收益的破坏性重构；同步迁移当前消费者、删除被替代实现，并按风险与影响验证。

### 个人设备与云端集群

系统须通过发布时的装配设置，支持运行于用户个人设备和云端集群。两类环境使用同一套领域语义，由相应装配提供运行能力、资源与集成方式。

部署差异应落实在装配与提供者责任中，不能将个人设备或集群假设写进领域模块。身份、权限、数据保护、等待与恢复的承诺在两种装配下都须明确落实。发布装配不等于运行中的热迁移，也不自动提供跨环境执行状态接续。

第一版单机交付范围与个人设备、云端集群支持的阶段交付分别说明。这里不选择操作系统、编排平台或跨节点协议，也不将环境支持目标描述为已完成交付。

### 后续精确化

各类运行时变化的生效与连续性契约、运行环境支持矩阵及阶段验收，由相关产品、架构及规格展开。性能数值、等待恢复和故障处置的验证前提同样须明确。持续利益对齐按上文的长期承诺与阶段边界处理。本页给出架构方向及责任，不代替这些精确承诺。
