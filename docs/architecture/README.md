[项目要求](../requirements.md)说明系统要实现什么、阶段范围和全局约束，本区说明架构如何承接。[边界与环境](context-and-scope.md)已据此整理系统责任、外部参与者与信任边界，正文已获项目负责人接受。具体验收条件随相关专题和规格细化，不要求先全部定案才继续架构设计。

本区的设计正文描述系统应当具备的职责、结构、行为和保证，不从当前源码反推设计。实现现状与偏离作为独立的符合性材料维护；撰写与修订遵循[顶层设计表达应然](../engineering/documentation.md#顶层设计表达应然)。

## 系统总览

omne-harness-lite 是服务组织或个人的 agent harness，组织模型、工具、上下文、状态与执行过程。客户端经 SDK 和公开契约使用系统，服务端由领域能力、工作治理、运行时和基础设施提供者组合而成。系统使用 Cordis 装配和管理生命周期，领域模块满足自身依赖后也可独立使用。总体协作图与职责划分见[结构与责任](structure.md)，客户端、接口和服务端的依赖约束见[分层与依赖](layers-and-dependencies.md)。

账号、组织、租户和工作区确定身份与资源范围，资产、设置和权限分别求值。Session 与 Run 承担工作逻辑治理，Agent、Model 和 Tool runtime 各自管理执行生命周期。Runtime Context、一次模型请求的上下文和执行环境分别承担运行数据、请求输入与执行设施的责任，不能相互替代。具体流程和概念沿[运行架构](runtime/README.md)展开。

系统以长期运行与恢复、速度与吞吐、动态演化为优先质量目标，同时守住授权、隔离、数据保护和结果真实性。个人设备上的常驻服务和云端集群共享领域语义，具体装配明确其资源与故障边界。[数据与状态](data-and-state.md)、[安全与隔离](security/README.md)、[部署拓扑](deployment/README.md)说明这些保证由谁承接，[质量与符合性](assurance.md)说明如何论证和验证。这里汇总目标设计，实际实现及其差距分别判断。

## 按问题阅读

- 初次理解系统，读系统总览、边界与环境，再读结构与责任。
- 修改一个部分，先定位结构中的责任和实际拥有者。只有涉及跨边界行为时，才展开运行、数据、安全及跨系统约定。
- 设计客户端、SDK 或服务端接口，先读[分层与依赖](layers-and-dependencies.md)，再展开所调用能力的公开契约。部署拓扑承接这些逻辑边界，不替它们决定职责。
- 判断部署或运行影响，读部署拓扑及相关运行过程。具体操作从[使用与部署指南入口](../guides/README.md)进入。
- 评审交付或识别偏离，读目标与约束、质量与符合性，再按问题追踪相关专题和实际验证资源。
- 讨论架构变化，读相关专题、选择与取舍、风险与演进。新方向由负责人明确，候选稿不能直接作为实施依据。
- 找下一项设计工作或判断缺口由谁处理，先读[未决事项与后续设计入口](#未决事项与后续设计入口)，再到原文核对当前边界。

责任、依据、适用范围和本次必要验证已经明确时，停止扩大阅读。缺少关键正文或存在含义冲突时，暂停依赖该结论的行动，交系统架构负责人裁定。

## 采用状态与当前有效源

项目负责人已接受边界与环境、目标与约束、结构与责任、分层与公开契约、数据与状态、跨系统技术约定、质量与符合性，以及运行专题十二页、安全专题七页、部署专题八页的目标架构正文。2026-10-09 按负责人的确认同步此状态。接受的是正文中已明确的设计，具体未决项继续保留，不能自动补成已接受决定。

跨系统技术约定的共同语义已获接受。公共 SDK 共用基础契约并保留领域结果；登录入口拒绝租户冲突。具体接口与消费者的迁移继续按各拥有者承接，不能以架构接受推断其完成。

关键选择与取舍、风险与演进边界的占位章节允许暂时留空，仍须由[目标登记](../documentation.json)和 `make docs-inventory` 报告缺项。工具的结构读数不授予接受状态。

本区已接受正文是全系统架构的唯一准据，约束领域、成员细化及后续实现。[旧技术材料](../../.meta_harness/design/architecture/README.md)供提取细化和识别消费者，不能凭旧接受记录成为并列架构权威。冲突旧设计不得迁入规范；已迁入的冲突条款须删除或依据本区重新设计。现有实现不符合目标时记录偏离，不能以成员SPEC或采用限制制造架构例外。尚未判定的细化保持未判定，不因迁移自动采用。具体处置归[架构准入规则](../engineering/documentation.md#位置与唯一源)。

共同集成保证归[IC约定](cordis-integration-conventions.md)，[constraints](constraints.json)是现行机读采用映射；其状态只声明检查定位，不等于实际行为符合。消费者是否已切换、成员是否满足目标及行为是否经过验证，分别核对。

[系统目标与全局约束](../requirements.md)提供上游依据。领域关系归[领域层](../domains/README.md)，符合上层要求的精确接口、行为及验证资源归[实际成员](../../packages/README.md)。信息整合核对唯一正文和必要消费者，不要求所有旧技术设计继续有效。

## 维护与展开

源码目标布局和包边界从[产品包组织](../package-organization.md)展开，领域页维护责任和协作，workspace维护开发环境。包组织规则已落正式位置，现有包迁移及模板、路径检查适配仍由各自任务承接，不由架构接受推断完成。

系统架构负责人主导正文与采用范围，维护者按专题代笔、核对来源和更新导航。设计正文明确已采用要求、目标设计、阶段范围与未决事项，并给出适用范围与依据。符合性材料另行报告实现事实和偏离，不反向决定设计正文。重要约定定位上游依据、承接者及验证责任，图与派生视图引用正文拥有者。

一个承诺只保留一份现行权威。专题引用产品、领域、成员规格和操作指南，不复制其正文。这里维护现行关键选择及持续有用的理由，提案、访谈和单次评审证据仍归工作树 tmp。

[结构与责任](structure.md)保持系统总览粒度，直接解释总体分解、职责与所有权、依赖方向和扩展边界。状态机、执行时序、数据规则、安全机制及部署细节由各专题拥有，领域内部结构与精确接口随实际拥有者维护。复杂部分按需要另立专题，并在总体结构中保留协作关系与入口。

边界、依赖、运行流程、数据所有权或部署方式变化时，复核有关专题、图、导航和检查。填成正文后才移除对应占位标记。增删专题或必要章节时同步目标登记，单列要求范围变化，不把登记调整计为内容完成。

专题新增、解决或转交未决事项与后续设计时，同批更新[集中入口](#未决事项与后续设计入口)的摘要、责任及原文链接。事项解决后从未决索引移除或转为下一项真实的设计责任，结论写回拥有者；不能只修改这里而让原文继续待定。原文与索引冲突时先核对决定及采用范围，不将索引当作第二份契约。文档检查只能核对结构与链接，索引是否完整、分类是否准确仍须在文档评审中核对。
