# Cordis 上层集成约定

本页拥有IC-1至IC-19的系统集成规则；各能力的形状和类型外行为由公开接口拥有者维护。目录及包边界按[承载项目的产品包组织入口](../package-organization.md)，Service定义不再固定集中core，跨包方向也不再由core/util路径许可决定。服务唯一性、独立根入口、依赖换代、提交及在途责任保持各自约束。Cordis约束集成，不决定领域语义。

系统使用Cordis提供装配、组合、依赖注入和生命周期能力。机制事实按已采用版本核对 [basis](../../.meta_harness/design/basis/README.md) 中的 Cordis 条目。模型、探针和测试均须声明成立前提，不把有限证据写成整体符合。

这些规则不新增合并硬线。静态读数区分有限静态符合、偏离和 unknown；行为及责任仍需真实消费者证据和独立判断。不得放宽预期、扩大装配例外或改写声明来消除红项。

本页约束新写或修订的提供者及装配，不据规则发布自动宣称存量代码合规。实现方案或上游版本改变时复核相应规则；Cordis 升版先运行 basis 的全部相关 probe，失败条目必须回到对应集成要求重新判断。

## IC-1

每个能力接缝恰有一个Cordis服务定义，随能力契约或协议形状的唯一拥有者就近维护。下文称其为定义拥有者。同一契约的接缝由该拥有者统一维护，不因拆提供者或消费者复制定义。能力组与成员边界按产品包组织，不能由契约ID机械推导物理包路径。

装配入口交给插件的运行时对象仍通过能力接缝交付。定义由拥有该形状的成员维护；装配入口通过 provide 提供对象，插件通过 inject 获取对象。责任沿 IC-16。提供者与消费者引用同一定义，不各自拥有一份。

## IC-2

服务键只写一次。抽象 `Service` 以 `static readonly provide = '键'` 声明键，构造函数 `super(ctx, <类>.provide)`，定义包导出的键常量取自它。提供者 `extends` 这个抽象类，不另写键，也不自己 `ctx.provide` 这个键。消费者引用定义包的键常量。一个插件提供几个键（同一份实现的几个服务面）时，在插件体里逐个 `new` 各键的子类，它们都登记在这条插件的fiber上。也可以把子类本身当插件装，每个键对应一条fiber。按提供者的撤除与在途承诺选择，并写明理由。

## IC-3

服务定义可以是无实现的抽象 `Service`，或包含登记逻辑、可作为提供者装载的具体注册表 `Service`。仅有类型的 `interface` 不能作为服务定义。抽象 `Service` `implements` 根入口里的操作类型，同一组签名不写两份。类上的JSDoc写 `@contract <契约 ID>`，只写ID、不写版本；接缝出自协议形状、没有契约的，改写 `@owner <实际定义拥有者的成员路径>`。contract与owner二者必有其一。路径须指向真实成员，不用目标目录冒充已迁移位置。

## IC-4

每个包的根入口与Cordis无关，提供词汇类型、操作类型、纯函数或不依赖Cordis的函数与工厂。Cordis服务键、`Service`类、`Context`与`Events`增补和插件由同包集成入口维护，默认使用 `./cordis`。

契约与提供者共置时，可以另设同包的服务定义公开子入口，承载服务键、`Service`类及类型增补；该入口须满足IC-5的消费隔离要求。具体绑定插件仍从 `./cordis` 发布，引用同一服务定义，不复制类或键。子入口路径由成员exports和README明确，这项入口分责不要求拆包。

根入口不import `@deepseek-ai/cordis`，也不导入本包任何Cordis集成入口。`apps/` 与封存成员 `core/kernel-basis` 不受本条约束。目标成员 `packages/assembly/kernel-basis` 的根入口遵守本条。

## IC-5

能力操作的消费者只依赖公开契约及服务定义，按服务键取用，不依赖被选择的提供者实现入口。提供者选择由构造或装配拥有者承担。别的成员为正确使用契约数据所需的编解码、校验和比较等纯函数是契约词汇，随定义拥有者的根入口维护。

契约、服务定义与提供者共置于同一成员时，消费者可以引用该成员的契约或服务定义公开入口。这些入口不得引入被选择的业务提供者实现，须分别核对源码值边、生成声明和实际产物。IC-3允许的服务定义自有登记逻辑仍由定义入口维护，不因此引入独立提供者实现。成员共置不改变操作消费与实现选择的分责，也不要求只为目录分责而拆包。

非装配成员的跨成员依赖按[承载项目的系统分层及包组织角色入口](../package-organization.md)判断，core/util目录名不构成许可。业务不得反向依赖客户端、协议运输或应用，不通过私有入口读写其他能力事实。

同提交事务读函数例外保持原精确范围，须在实际拥有者的行为规格中声明，并写明两个写入者共同触碰的存储对象。目录变化不扩大例外符号、提供者互引或装配豁免，实际同提交和资源责任仍需验证。

## IC-6

同一个 isolate 标签下，一个接缝只有一个提供者在场；要两份实现并存，分到不同的 isolate 标签下，并在装配拥有者的行为规格中写明谁看见哪一份。

## IC-7

定义拥有者及成员名表达稳定职责，包边界按IC-1及产品包组织，不强制一个契约ID对应一个包。独立提供者包用限定名表达实现方式或后端，如 `storage-sql`、`session-log-jsonl`、`credential-custodian-local`，只有一个提供者时也一样。服务键用camelCase名词表达能力，如 `storage`，不写成实现名 `sqlStorage`。

## IC-8

必需依赖写在 `inject`。使用数组字面量，元素是字符串字面量或从定义包 import 的键常量；不在运行时拼、不经变量转手。写进去就等于「它换代或不在，我就卸载重跑」。插件里只有一段工作需要某个依赖时，用 `ctx.inject([...], cb)` 把那段放进子 fiber，不把整个插件挂在它上面。

## IC-9

可选依赖不写进 `inject`。调用时用 `ctx.get(键)` 或 kernel-basis 的 `resolveOptional` 现取，接受 `undefined`，按契约的缺席默认答案收场；`ctx.<键>` 只留给 inject 过的键。只需类型增补时，使用 `import type {}` 从定义拥有者的服务定义公开入口取得，默认路径为 `<定义包>/cordis`；按IC-4分设入口时使用成员exports和README声明的定义子入口，不从具体插件入口取得。提供者写明换代时如何处置已持有的旧引用。

## IC-10

事件名 `<范围>/<事件>`，全小写 kebab。范围是声明它的那个包的名字（不带 `@omne-harness-lite/`）。跨成员事件的范围取它所属定义包的名字，迁移途中暂时声明在别处也不改。通知（`emit`、`parallel`）的事件部分用过去分词，可带对象前缀（`session-log/appended`、`organization-governance/membership-changed`）；控制（`serial`、`bail`、`waterfall`）的事件部分用动词原形，说明被问的动作，如 `tool-admission/admit`。

## IC-11

事件在声明它的成员的服务定义公开入口增补 `Events`，默认使用 `./cordis`。按IC-4分设入口时，增补由定义子入口唯一维护，具体插件引用该定义，消费者按IC-9取得。跨成员监听的事件由拥有它的服务定义成员声明，只在一个成员内部用的留在该成员。每个事件的JSDoc写 `@mode`及载荷的 `@param`，公开派发承诺与它一致。派发模式仍为原五种，不由入口拆分改变。

## IC-12

可否决的异步控制用 `serial`，不用 `bail`。`bail` 不等 Promise，Promise 本身被当成否决值；`bail` 只承载同步判定；`waterfall` 用于环绕改写。通知有两种。`emit` 的监听者同步执行，**不得返回 Promise**。监听者如需启动异步工作，须自行处理其失败。需要等待异步监听者的通知使用 `parallel`。两种通知都由发通知的一方处理监听者失败。`emit` 调用放在 `try` 中，`parallel` 的异常处理在 `await` 外。监听者失败只记录诊断，不改变已提交操作的结果。

## IC-13

登记即效应。注册表 `Service` 的 `register()` 在方法里用 `this.ctx.effect(...)` 登记并返回撤除函数。登记落在调用方的fiber上，调用方撤除即撤掉。监听一律经 `ctx.on`。注册表不自己记「谁登记了什么」再等人注销。提供者须验证贡献者卸载后其登记已撤除。

上述贡献者配对仅在插件内调用成立。根 Context 调 register 时效应属于根 fiber，不随某个贡献者撤除。只允许测试或装配入口这样使用。以 ctx.provide 发布的普通对象没有 Service 的调用方 ctx，不能据此取得相同自动归属。

## IC-14

插件配置用 Standard Schema 校验（函数插件经 kernel-basis 的 `definePlugin`，`Service` 子类写静态 `Config`；Cordis 4.0.4 对两种插件都按 Standard Schema 校验，`registry.ts:104`、`fiber.ts:50-53`）。重试、退避、超时、限流和阈值等可调参数写成配置字段，默认值只是初值。配置错误时，插件加载失败，fiber 进入 `FAILED`。不能静默跳过缺失的引用。

## IC-15

一个进程挂哪些 Cordis 插件、各带什么配置，写成数据：[Cordis 插件树](../../.meta_harness/design/ubiquitous_language/terms/architecture-core-and-extension.md#ul-cordis-plugin-tree--cordis-插件树--cordis-plugin-tree)由两格[插件树层](../../.meta_harness/design/ubiquitous_language/terms/architecture-core-and-extension.md#ul-plugin-tree-layer--插件树层--plugin-tree-layer)叠出。发行层在前，运维者层在后。组织、租户和会话不构成插件树层。

## IC-16

插件树每行包含行id、插件和配置。插件由包名及其 `./cordis` 入口的导出名标识。配置只放可序列化的数据；运行时对象（迁移提供者、信号、回调）不进树，由装配入口 provide 成服务、插件 inject（定义归属见 IC-1）。运维者层按行 id 整行替换配置、停用或插入新行；**指向不存在的行 id 即启动失败**；进程能打印最终的树，并标出每一行出自哪一层。发行层的行 id 因此是对运维者的稳定承诺。改名或删一行要写进装配拥有者的当前说明与发行说明。

## IC-17

运行中按会话为 agent 装上的 Cordis 插件**不进**插件树。这些插件落在会话这一级的作用域里。事件按作用域过滤，撤除按作用域整体撤，故障不出作用域，登记不漏到别的会话。机制与正式名由「按会话装插件的作用域」这份设计定（UL-D-7没有为它立词）。

## IC-18

跨边界操作显式携带租户身份。租户身份是操作的参数（或参数里的身份值），不从 `ctx`、isolate 标签、插件实例或「谁装了这个插件」推断；不把「不 inject 就够不着」当访问控制。

## IC-19

契约里靠同一进程、同一 Context 才成立的保证，实际拥有者在行为规格中写明此刻靠什么兑现；拆成多进程时，它们要由协议重新兑现。

## 审阅与验证责任

| 要判断的责任 | 对应规则与证据 |
|---|---|
| 定义拥有者、纯入口和跨包消费 | IC-1～IC-5、IC-7；源码、声明、装载及实际制品检查 |
| 可替换提供者、必需／可选依赖 | IC-6、IC-8、IC-9；换代、缺席及旧引用的真实组合测试 |
| 类型化事件及失败影响 | IC-10～IC-12；声明／派发对应，监听失败不得改变已提交结果 |
| 贡献登记、撤除和在途责任 | IC-13、IC-19；调用方 fiber 撤除、实际停止与责任释放证据 |
| 配置和两层插件树 | IC-14～IC-16；非法配置／悬空修改拒绝、来源打印和装配顺序 |
| Session 作用域及租户授权 | IC-17～IC-19；明确区分作用域可见性与数据授权，未采用机制不得声称符合 |

每个提供者自行说明装载、停止准入、取消、实际完成及撤除的配对责任；内核未提供的进展、事务和跨进程保证由实际协议拥有者兑现。公开类型同形不证明 LSP 或生命周期正确。

服务图和事件矩阵从实际源码派生；架构预期由系统级约束维护，不另建手写实现绑定或完整服务分类表。单次读数、评审与迁移过程归工作树 tmp。

非装配成员的事务内读函数例外只能按精确目标、符号及共同存储对象采用，不能扩成提供者互引豁免。当前无此类独立中央绑定清单；新增或修订例外须由承诺拥有者说明并同步实际检查输入。
