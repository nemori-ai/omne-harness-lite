# 完全动态系统

> "若要谈论动态性，就必须区分**运行轨迹的多样性**与**系统结构的可演化性**。"
>
> —— *基于诺伯特·维纳（Norbert Wiener）的控制论思想扩展*

本文力图回答三个递进式问题：

1. **ReAct 范式为何称不上"完全动态"**？
2. **LangGraph、PydanticAI Graph 之类的"图式 Agent 框架"又差在何处**？
3. **什么才是"完全动态系统"，它的最小判定标准是什么**？

我们将沿着"事实陈述 → 逻辑推导 → 概念升华"的论述路径展开，并在关键处给出可查证的文献与文档引用，确保论点"引经据典、有理有据"。

## ReAct 范式：动态的是轨迹，而非结构

ReAct（*Reasoning + Acting*）由 Yao et al.（2023）提出，核心闭环为 **think → act → observe → reflect**。该闭环赋予 Agent 在**运行时**根据环境反馈调整下一步行动的能力。然而，只要稍加留意，便能发现它仍受以下三条"静态锁链"束缚：

1. **固定策略** —— LLM 的权重与提示模板在运行中一般保持不变（除非人工热更新）。
2. **固定动作空间** —— 可调用的工具集合、调用签名与安全策略多在部署前写死。
3. **固定控制拓扑** —— 决策逻辑始终遵循线性闭环，无法在运行中插入/删除阶段，亦无法自发增设子代理。

**结论**：若一个系统的"动"仅体现在状态层面，而策略、动作集合、控制拓扑皆不可变，则该系统至多是"**动态执行的静态架构**"。

于是，ReAct 虽然能走出千变万化的执行轨迹，却依旧逃不出先验设计的"牢笼"。它离"完全动态"尚隔着一堵墙。

## 图式 Agent 框架：静态拓扑 + 动态控制流

近年来，工程社区借鉴工作流编排思想，将 Agent 逻辑建模为*有向图*。其中两位明星选手是 **LangGraph** 和 **PydanticAI Graph**。二者都声称支持所谓"动态图（Dynamic Graph）"，然而稍加深掘便可发现：

| 特性 | LangGraph | Pydantic-AI | 共同局限 |
|------|-----------|------------------|-----------|
| **拓扑定义时机** | 运行前调用 `add_node`, `add_edge`, `compile()` | 运行前通过类型化节点/边声明，随后 `Graph.run()` | *拓扑在运行前固定* |
| **"动态"之含义** | 运行时根据状态激活 **conditional edges**；支持循环并受 `recursion_limit` 保护 | 运行时根据状态机规则选择下一节点，亦支持循环与恢复 | *动态的是控制流，而非拓扑* |
| **运行时改拓扑** | ✗（需重新 `compile()`） | ✗（需重新实例化） | *均不支持* |

**结论（工程角度）**：这类框架将"可视化、验证友好的静态拓扑"与"执行时的路径分支"解耦，牺牲了结构演化能力来换取可控性。故而，它们只能构建**结构静态、轨迹动态**的系统。

## 完全动态系统：从"状态动态"到"结构动态"

控制论大师 W. Ross Ashby 在《Design for a Brain》（1952）中强调：

> "**Adaptivity is not a property of behavior, but of organization.**"
>
> （适应性不是行为的属性，而是组织的属性。）

顺着他的思路，我们给出如下工作定义：

**定义（完全动态系统）**：在离散时间 $t \in \mathbb{N}$ 上，系统不仅拥有随时间演化的运行状态 $s_t$，还允许其策略参数 $\theta(t)$、动作空间 $A_t$ 与组织拓扑 $\sigma(t)$ 在运行期根据交互在线更新。其行为可由下式刻画：

$$
\begin{aligned}
a_t &= \pi_{\theta(t)}\bigl(s_t,\; o_t\bigr) \\
s_{t+1} &= F\bigl(s_t, o_t, a_t, \xi_t\bigr) \\
A_{t+1} &= \Psi\bigl(A_t, s_t, o_t, a_t\bigr) \\
\sigma(t^{+}) &= \Phi\bigl(\sigma(t), s_t, o_t, a_t\bigr) \\
\theta(t+1) &= G\bigl(\theta(t), s_t, o_t, a_t, r_t\bigr)
\end{aligned}
$$

**符号说明**：

| 符号 | 含义 |
|------|------|
| $t \in \mathbb{N}$ | 离散时间步 |
| $s_t$ | Agent 内部可读写状态（工作记忆/长期记忆/信念等） |
| $o_t$ | 观测（来自环境或上一次行动的回执） |
| $a_t$ | 行动（包含工具调用与参数） |
| $\pi_{\theta(t)}$ | 基于参数 $\theta(t)$ 的策略/控制器 |
| $\theta(t)$ | 随时间可更新的策略参数 |
| $A_t$ | 可用动作/工具集合（动作空间） |
| $\sigma(t)$ | 系统的编排/组织拓扑 |
| $F$ | 状态更新（记忆/信念）函数 |
| $\Psi$ | 动作空间（工具/技能库）演化函数 |
| $\Phi$ | 拓扑/编排演化函数 |
| $G$ | 策略参数更新函数 |
| $\xi_t$ | 环境/模型不确定性与噪声 |
| $r_t$ | 外部或内部回报/反馈 |

**要害在于**：若 $A_t$、$\sigma(t)$、$\theta(t)$ 中任一维度可随运行自发演化，则系统的"形"与"魂"皆动，可称"完全动态"。

## 最小判定标准：四条硬杠杠 + 两条加分项

为了让"完全动态"可落地，我们提出 **Minimal Viable Criteria（MVC-4 + 2）**：

### 硬性要求（MVC-4）

1. **闭环与状态（Stateful Loop）** — 必须有可读写的状态 $s_t$ 参与决策。
2. **策略在线自适应（Adaptive Policy）** — $\theta(t)$ 必可运行时更新（梯度微调、检索增强、规则注入皆可）。
3. **动作空间可演化（Evolving Action Set）** — 运行期允许注册/卸载工具，更新立即生效。
4. **拓扑可重构（Re-configurable Topology）** — 允许在不中断主循环的情况下增删节点/边或替换子图。

### 加分项（Optional-2）

5. **知识结构可重组** — 长期记忆库可合并、蒸馏、压缩并影响策略。
6. **治理与约束自适应** — 安全策略、资源配额、审计流程可在线调整。

**判定准则**：若系统满足 MVC-4，即可称为"最小完全动态系统"；满足全部 MVC-6，则向"自治、自进化"更进一步。

## 与现有框架的互补关系

- **LangGraph / PydanticAI Graph** 可继续作为"静态拓扑层"——负责可视化、类型校验与局部幂等重试。
- **完全动态运行时**（可自研或选型）位于其外层，接管：
  - *拓扑热重编排*（增删节点、版本回滚）
  - *工具热插拔*（发现、沙箱、授权）
  - *策略在线更新*（检索增强、LoRA 微调热加载）

如此，二者并非对立，而是"内静外动"的分层协作。

## 结语

ReAct 与图式框架让我们踏出了"轨迹动态"的第一步，但唯有迈入**结构动态**的领域，Agent 系统方能具备真正的自我演化潜能。

静态设计易验证，动态进化获生命。
