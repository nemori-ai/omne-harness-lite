# 领域与能力责任

本区说明业务、治理与执行责任怎样分工，逻辑模块怎样协作，以及精确承诺由谁维护。先从任务找到责任，再展开成员接口、行为规格和验证。它面向开发者、集成者与设计维护者；系统使用者从[使用入口](../guides/README.md)开始。

状态：领域责任设计正文已获项目负责人接受，约束后续领域与成员设计。引用的[项目要求](../requirements.md)和[已接受架构](../architecture/README.md)保持各自采用范围。正文接受不表示包已建立、代码已实现或运行保证已验证，原技术源的承接与退役继续按后续阶段推进。

## 从任务开始

| 要确定什么 | 先读哪里 | 继续及停止点 |
| --- | --- | --- |
| 事实、规则或组合保证归谁 | [责任边界](boundaries.md) | 找到拥有者及相邻交接后转责任页，不用通读全部领域 |
| 怎样扩展业务或模块 | [扩展指导](extending-the-system.md) | 明确责任与契约后进入工程场景，未定语义只暂停相关实现 |
| 局部变更影响哪些模块 | 下表对应入口 | 读模块角色、协作及契约导航，公开承诺足够就停止 |
| 怎样接入或替换提供者 | 责任入口、实际契约及[分层架构](../architecture/layers-and-dependencies.md) | 依赖、资格、资源、失败及结果承接清楚后停止 |
| 怎样判断偏离 | [组合验证](verification.md) | 区分结构读数、语义评审和运行证据，无法观察保持未覆盖 |

## 向下阅读与唯一源

系统架构拥有全系统约束，本区细化到逻辑模块的角色、事实归属、允许依赖、公开协作、关键交接和组合验证责任。一个包内也可以有多个需解释的模块；是否跨包不能单独决定本区粒度。公开类型、精确失败、状态转移、事务、并发、取消和恢复协议随实际成员或协调者；跨包协议也随其拥有者。产品规则和统一语言保持原源。

产品需求、能力状态、阶段与有效未决从内部[产品入口](../../.meta_harness/design/product/README.md)进入。责任页的“正式产品与技术承接”导航到对应正文、组及成员；新细化设计的待审状态与原责任正文的接受范围分别维护。

能力组的工程分解、组内成员关系与共同维护归`packages/<domain>/`，单包公开使用、契约、内部设计和维护归实际成员。按[两层成员文档](../member-documentation.md)展开；本区不复制包群依赖图或包内机制。

责任页说明设计要承接的契约，不推测当前实现已满足。尚未确定成员时继续具名模块设计和交接，不造空包或中央SPEC。简单成员已能解释整项责任时直接导航过去，不强制拆领域architecture页。

## 维护与状态

位置及最低章节由[本区文档要求](boundaries.md#文档内容与登记)维护。项目负责人已于2026-10-10接受本区四份总正文和17项责任正文。接受范围为已明确的责任分解、模块角色、事实归属、协作与依赖、关键交接、扩展和组合验证责任。正文保留的未决及下层设计义务继续由相应拥有者承接，不因本次接受而自动定案。局部documentation.json登记结构预期，工具派生缺项，不存手填通过状态。

新增、修改、拆页、登记和检查的步骤见[文档维护指南](../maintenance.md)。同一阅读任务的内容就近保留在README；出现独立阅读任务、消费者或维护节奏时，再按需拆出architecture、具名专题、组合验证或真实任务指南。各目录可以长期只保留README。拆出后原入口保留摘要与导航，同步必要章节登记和消费者。

修改范围、交接或保证时核对邻接责任、成员及接受依据。冲突交语义拥有者，下层实现不能覆盖已接受架构。目标能力组及责任到目录的导航见[产品包组织](../package-organization.md#责任与能力组)，顶层归属和开发环境见[workspace](../workspace.md)。领域责任不直接决定包数量，现有成员位置与目标目录分别判断。

后续设计从各责任页及[组合验证](verification.md)定位，原未决继续从[架构集中入口](../architecture/README.md#未决事项与后续设计入口)展开。临时提案、评审和单次证据不进入正式正文。
