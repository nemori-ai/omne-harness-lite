# Plugin

## 范围与边界

一份 Plugin 是一份定义：一个目录，最上面一份清单 `plugin.json`，列出它的成员，每个成员是某个[拓展点](../extending-the-system.md)上的一项。成员可以是另一类资产，也可以是不单独持有的东西：界面的令牌、样式与画法，一份对客户端开放的协议。装一份 Plugin，它的成员一起出现；卸下它，成员一起退场。

本领域回答五个问题：一份 Plugin 写成什么样才算合法；它怎样从「要装」走到「装上」；它让系统倒下的时候系统还起不起得来；它的代码够得着什么、以谁的名义行事；它记下的事实存在哪、活多久。

一份 Plugin 带来的可以是一个完整的领域：它记得住自己的事实（[它的数据](../../../packages/plugin/SPEC.md#plugin-的数据)），让 agent 知道这些事实（Runtime Context 的块），声明自己的设置、权限、通知来源与送进会话的输入来源，还可以声明自己的拓展点让别的 Plugin 往上放（[Plugin 声明的点](../../../packages/plugin/SPEC.md#plugin-声明的点)）。这几样都走官方领域走的那几个点与口，只是放的人是它。

本领域不回答的：

- 一个拓展点收什么。成员放得上放不上，由那个点的规矩判；一个点收不收 Plugin 的代码，由那个点的拥有者定。
- 别的类别的正文合不合格。指向一个类别的点的成员，由那个类别的正文契约判。
- 谁持有一份 Plugin、几份同名的听谁的。那归[资产与规则](../assets-and-rules/README.md)。
- 经口做的一件事许不许。口以这次调用者的名义调出借它的领域，由那个领域照自己的规矩判。
- 界面怎样把放上去的东西画出来。那归外壳契约，见[前端包组规格](../../../packages/frontend/SPEC.md)。
- 代码在哪个执行域里运行、关不关得住。客户端运行中装上的代码只从应用自己的地址来，这条边界归各宿主应用的内容安全策略；服务端的受限执行域归[执行环境](../execution-environments/README.md)。

## 作为资产类别

Plugin 是资产的一个类别 `plugin`，它的定义放在点 `plugin.plugins` 上。一份 Plugin 从一个目录发布；发布之后和任何一份资产一样被持有、启用、禁用、移除。agent 经工具 `OmneExtensions` 做这些事，人经资产页，两个入口走同一个发布服务。

一个租户要装什么由它持有的推出：类别 `plugin` 在它各层的每个名字，取资产求值胜出的那一版。被禁用的、被盖过的不装。没有第二个地方记着装没装。

发布时，这个类别判整份包：

1. 包里有 `plugin.json`，并且读得懂。
2. 包对得上清单。
3. 每个指向一个类别的点的成员，交给那个类别的正文契约判。目录型的类别只收 `directory` 成员，判的时候只看得见那个子目录；数据型的类别只收 `data` 成员。装的时候两种都做成那个类别的一份在持项。一份 Plugin 里不放 Plugin。类别的点都在服务端的树上，所以写在客户端一侧的这种成员不合格。
4. 清单的原文放得进一份正文。

有一个成员不合格，或它的类别不可用，整份不发，原因指到那个成员。

这个类别也答一次改动会怎样、在持的一份此刻怎样。影响只读清单，不运行任何东西：它列得出这一份会往哪些点放什么、哪些放不上、会和同一个租户的另一份撞在哪个键上。生效情况取自两棵树的装载方报的状态。

### 皮肤：收窄的一类

资产只认「类别加名字」，一个类别是登记进来的一份契约：一份在持的东西落到登记表上是哪几项、合不合格。Plugin 是约束最少的那个类别，清单写什么就放什么。皮肤是 Plugin 领域登记的第二个类别 `skin`，契约是 Plugin 的契约再多两条：清单写明这一份是皮肤；它只有客户端一侧的成员。它的定义放在点 `plugin.skins` 上。

- 一份包是不是皮肤由清单自己写明，不由它被发布到哪一类决定。写明是皮肤的发不进 `plugin`，没写明的发不进 `skin`。所以没有持有的包（开发目录里的）也认得出是不是皮肤。
- 皮肤不带新的包格式、装载方或状态表。清单、包、版本、换代、一份的贡献一起出现一起退场，都与 Plugin 相同。
- 一个租户要装的是两类合起来的一组。同一个名字在两类里各持有一份时，这个名字一份都不装。
- 启用与在用分开。资产说一套皮肤启没启用，可以同时启用几套；界面此刻用哪一套不归资产，归客户端：装载方把一套皮肤的成员放在「租户之下、这一套」这一层作用域里，外壳发问时带上在用的那一套，所以各处同一刻一起换，没在用的那几套对发问者不可见。
- 资产的规则不因皮肤多出一条。「同一时刻至多用一套」是发问的作用域带来的，不是求值里的一条。

## 模块角色与事实归属

| 模块角色 | 拥有的知识 |
| --- | --- |
| 清单与包 | 清单的形状；一个成员写成数据、目录、代码三种之一；包里许带哪几种文件；包对不对得上清单 |
| 类别 | 一份包合不合格；一次改动会怎样；在持的一份此刻生没生效 |
| 要装的 | 来源给的一组里，哪几份是这一侧要装的；版本是内容的摘要 |
| 一侧的状态 | 一份 Plugin 在一侧的五种状态，与表变了、装载有了结局时的每一步 |
| 来源 | 一个主体现在要装哪几份；它们的文件；什么时候可能变了 |
| 装载方 | 照「要装的」把成员放到点上；记着每份装成了没有；把自己的样子报出去 |
| 底 | 装的时候连着倒下了几次；到了上限拦下哪几份 |
| 口与客人写法 | 口的形状；一次调用怎样打开、关上口；`plugin.ports` 与 `plugin.guest-forms` 两个点的规矩 |
| 数据 | 一份 Plugin 在一个租户里存的键与它们的值；什么时候删（只在人明说时） |
| 声明的点 | 一份 Plugin 声明的点叫什么、收什么；它的代码怎样读自己点上的答案 |

「放」这个动作只在装载方手里。一份 Plugin 的代码交出的是「这一项的内容」，放到哪个点、哪个键由清单定，由装载方放。所以不运行任何代码，从清单就算得出这一份装上之后会往哪里放什么。这是交给代码什么的约定，不是执行域的隔离：取来的代码和宿主在同一个进程里运行，见[没有守住的](#没有守住的)。

## 协作与依赖

两棵树各有一个装载方，照同一张状态表、同一个回路、同一个底装，各装清单里自己那一侧。客户端的装载方是一个界面模块，往外壳的点上放；它经协议 `plugin/v1` 问服务端「这个租户、这一侧要装什么」，文件由宿主应用从同源的地址取给它。服务端的装载方是服务端应用的一行，往服务端的登记表上放，见[服务端一侧](#服务端一侧)。

「要装什么」是带身份问的，不放进不登录就能订阅的公开观察：哪些协议挂着不是秘密，一个租户装了什么是。

成员的作用域由装载方打上，清单里写不出。客户端打上的是读这张表的那个租户的作用域，服务端打上的是持有这份 Plugin 的那个租户的范围。所以一个租户装的东西别的租户看不到，没登录时也看不到。

两份 Plugin 往同一个点的同一个键上放，是同一层的两项：那个点答冲突，两份在这个键上都不算数，原来的样子照旧。这是点的规矩，不是装失败。

## 主路径与交接

1. 来源给出一组：每份有版本、清单与文件表。清单读不懂或包对不上清单的，来源不给出，并说明是哪一份、为什么。
2. 装载方读到这一侧要装的表。读不到不等于表是空的：已经装着的不动。
3. 对表里的每一份，照它现在的状态走一步：没装的去装，换了版本的换代，不在表里的卸下。
4. 装一份：服务端先钉住清单 `needs` 写的口；再逐个核成员能不能放，有一个不能就整份不装；再取代码成员的文件；然后在这一份自己的作用域里一起放上去。放上去之后点的规矩不认其中一项，整份撤回。
5. 每一份有了结局，客户端的装载方把这个客户端现在的样子报给服务端：每份装上了没有、没装上是为什么，以及这棵树上有哪些点与部位。服务端的装载方记下每个租户每一份的状态。类别答生效情况时读这两样。

换代时旧的一代留到新的一代有了结局，一份 Plugin 的贡献不出现一段空白。装失败只影响那一份，原因记下并报出去；它不算系统倒下。

## 应用起不来的时候

一份 Plugin 的代码可以让页面一装上它就没了。系统的答法是分两层起：随应用构建的那一部分是底，总是先起来；Plugin 是之后补装的。每一次去装之前先记一笔「正在装」，这一次稳住之后才抹掉。下一次启动发现这一笔还在，就是上一次装的时候倒下了。连着倒下到了上限，这一次不再装那几份，应用照常打开自带的界面，并在界面上写明停掉了哪几份、怎样放开。

被停掉的一份在两种情况下放开：它换了一版；不再要它。

画的时候抛出不走这条路：那一处落回自带的画法，别处照常，这一份仍算装上。

服务端用同一个底，见[服务端一侧](#服务端一侧)。

## 服务端一侧

服务端装的是每个租户在持并启用的 Plugin 清单里 `server` 一段。规则归[包组规格](../../../packages/plugin/SPEC.md#服务端的装载方)：

- 每个租户各有一个回路与一份底的记录。为一个租户装什么、装没装成、停没停，不改别的租户的。读不到一个租户在持什么，它装着的不动。
- 一个租户的一份 Plugin 是服务端应用的一个 fiber，名字是 `plugin:<名字>@<版本>`。它放的条目都在这个 fiber 上，卸下就是撤掉这个 fiber。
- 数据成员放成一条条目。代码成员放在一项交函数的点上：点的拥有者写了专门的写法就用它，没写就用通用写法，见[隔离与鉴权](#隔离与鉴权)。关着的点什么成员都不收。
- 一个类别的点收目录成员。这一项是那个类别在持的一项：资产引用与版本是这份 Plugin 在持的那一版，`within` 是成员写的目录。读它的一方照读任何一份那一类的定义去读，分不出它来自单独持有还是来自一份 Plugin。
- 一份 Plugin 的数据存在它的租户的存储里，按它的名字分开。卸下、禁用、移除都不删；同名的一份再装上读得到原来的；删只由人明说，或由 agent 经询问之后做。
- 一份 Plugin 声明的点在它的租户的作用域里，名字以它的名字开头，官方的声明带锁、它盖不掉；它卸下时，别的 Plugin 放在上面的成员等着，不报错。
- 一份 Plugin 让服务在装的时候连着倒下到了上限，下一次起来不再装那几份，服务照常起来，诊断写明是哪个租户的哪几份。被停掉的一份换了一版或不再被要，就放开。有序的停止不算倒下。底的记录存在运维者给的目录里，每个租户一个文件，见[服务端应用规格](../../../apps/harness-server/SPEC.md#拓展件)。

## 隔离与鉴权

整份契约是一句话：Plugin 的代码从不出示身份。它代哪个租户、以谁的名义行事，由它所在的通道定，不由它说。它够得着的每一样东西都是别人交到它手里的，交来的时候已经绑好了租户。

四条规则：

1. **没有环境里现成的权限。** 代码接触世界只经三样：清单；交到它手里的口；它交出去的函数被调用时带进来的参数。它不导入任何包，不读全局的东西。服务端导出的函数被调时只拿到 `{ ports }`，它的 fiber 所在的上下文里取不到任何受信名。客户端的代码拿到宿主交的共用库与一个没有「放」的外壳。
2. **作用域是打上去的，不是自己报的。** 装载方给每一项打上持有这份 Plugin 的那一层的作用域，清单里没有这个字段。登记表上一个发问者只看得见作用域是它自己作用域前缀的条目，所以一个租户的 Plugin 放的东西只改变这个租户看到的系统。
3. **口是引用，装上时钉住。** Plugin 要用宿主的什么，写在清单的 `needs` 里，名字是点 `plugin.ports` 上的键。装上时在这份 Plugin 的作用域里解析并钉住：没写的拿不到，写了而不在的整份不装。口的每个方法只收一份数据、只答一份数据，没有放租户、主体或函数的地方。
4. **经口的每次调用照常过鉴权。** 口里带着这次调用者的主体，去调出借它的领域已有的入口，领域照自己的规矩在动手的地方判。装上不等于许可。

### 一次调用的绑定

Plugin 只在被调到的时候行事，没有自己的主体。一次调用进来时，用这次调用者的主体打开钉住的那几个口；处理函数返回或抛出时关上。由此直接成立：

- Plugin 的权限不比这次调用者大。
- 存下来的口过后用不了：关了之后每个方法答 `closed`，不调领域。
- 钉住的口的出借者走了或换了，那个口答 `unavailable`，不换成别的。
- 禁用一份 Plugin 就是卸下它：它放的条目撤走，别人调不到它。

### 口与客人写法是两个点

哪些领域把什么借给 Plugin，由各领域自己定。两棵树各有两个点归 Plugin，都在构建时定，规矩写明关，Plugin 自己放不上去：它们决定 Plugin 自己能做什么。

| 点 | 键 | 一项 | 谁放 |
| --- | --- | --- | --- |
| `plugin.ports` | 口的名字，就是 `needs` 里写的 | `make(调用者)` 交出一个口，里面调的是这个领域已有的入口 | 出借口的领域的适配 |
| `plugin.guest-forms` | 要自己包一层的那个点的名字 | `form(交回的东西, …)` 把代码交回的东西做成那个点原来的一项；另带一句「要交回什么」与一个照抄的成员 | 那个点的拥有者写，也由它那一侧放 |

一个点原来的一项，它的函数可能被直接交到主体手上，例如协议的处理函数。不受信的代码不能拿到主体。所以一个点的函数会拿到主体、或要让 Plugin 的函数用得上口时，它的拥有者写一份专门的写法：Plugin 交什么样的函数，这些函数被调用时拿到什么。别的点用通用写法：交回的东西照规矩核过字段就是一项，函数拿不到口。一个点收不收 Plugin 的条目是另一件事，写在它的规矩里，缺省是开，规则归[拓展点的共同契约](../../architecture/cross-cutting-concepts.md#开与关)。

协议的点 `access.protocols` 有客人写法：Plugin 交一份协议契约与处理函数，每个操作的身份都是「为行事的租户」，不收观察。处理函数拿到输入与这次调用的口，见不到主体。这份写法归接入层。工具条目来源的点 `tool.entry-sources` 的写法归 Tool：Plugin 交几个函数，各成为会话里的一个工具。Plugin 这个领域自己不写任何一份写法。

### 入口的第二次问

一个租户的 Plugin 挂的协议在这个租户的范围里，不在整个部署这一层。入口在整个部署这一层问不到它时，只对带着登录、为这个租户行事、身份签发得了主体的调用者，用这个租户的范围再问一次登记表。别的调用者得到的答复与这份协议根本不存在时逐字节相同，可用性里也不列它。规则归[接入层规格](../../../packages/access/SPEC.md#管道)。

### 要守住的六件事

| 要守的 | 违反了是什么样 | 靠什么 |
| --- | --- | --- |
| 数据 | 一个租户的 Plugin 读到、改了另一个租户的会话、资产、设置 | 规则一、三、四：主体的租户须等于访问的租户，领域在动手的地方判 |
| 行为 | 一个租户的 Plugin 盖过了另一个租户的界面或功能 | 规则二：登记表的读带发问者的作用域 |
| 身份 | 它以另一个租户或系统的名义行事 | 规则一、三：主体是对象，它手里没有；口里绑着的那一个它摸不到 |
| 观察 | 它看到别的租户装了什么、在调什么 | 规则一、二：代码拿不到登记表；它挂的协议只有它自己的租户调得到 |
| 秘密 | 凭据、签发主体的能力落到它手里 | 规则一：受信的名字不在它的上下文里 |
| 资源 | 它死循环、吃光内存，让所有租户的服务停掉 | 契约管不了，归放置，见下一节 |

## 没有守住的

四条规则管的是代码拿到什么，不管代码跑在哪。下面这些，这份设计不守：

- **存心越界的服务端代码。** 服务端的代码由 `import()` 装进服务的进程，带着 Node 的全部能力：读写文件、读环境变量、改写进程里共用的模块，看得见经过这个进程的每个请求。它可以绕开交给它的口，直接去碰这些。上面前五件事对老实的代码成立，对存心越界的代码不成立。
- **运行当中拖垮服务。** 一份 Plugin 在一次调用里死循环、吃光内存，会让所有租户的服务停住。底只管「装的时候连着倒下」：它在重启之后停掉那几份，管不了运行当中的。
- **页面里存心越界的代码。** 页面里的代码就是这个用户：它能做用户在页面里能做的一切，包括切换他的行事租户。这用的是这个用户自己的权限，不是越过另一个租户。要挡它，得把代码关进单独的框架。
- **计时这一类旁路。** 从响应的快慢猜别的租户在做什么，不在这份契约里。拓展树的修订号整个部署只有一个，一个租户看得出别的租户的登记表什么时候变了，也属于这一类。
- **入口第二次问之前的认身份。** 带着证明与租户头调一份整个部署没有的协议，入口会多认一次身份；这一次排在在途名额之前，不受在途上限管，调用方也中止不了它。
- **取回到工作区时的符号链接。** `OmneExtensions export` 先核目标在会话的工作目录里，再写；核与写之间，这个会话自己的 Shell 放进去的符号链接会被跟着走。

所以这套隔离只对老实的 Plugin 成立，租户的服务端代码只适合开给信得过的租户。要给不认识的租户开，先要有执行环境的受限执行域：它只开放明确的输入与获准的接口（INV-EE10），对时间、内存、并发、输出与宿主调用有可执行的限额，并能停止不合作的代码（INV-EE11），见[执行环境规格](../../../packages/execution/SPEC.md#不变式)。口上来往的都是数据，所以换到受限执行域只换装载方：契约、Plugin 的作者与各领域都不改。

精确的规则、状态表与不变式见[包组规格](../../../packages/plugin/SPEC.md)；跨领域的交接见[领域交接设计](architecture.md)；流程见[关键流程](key-flows.md)。
