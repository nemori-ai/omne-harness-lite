# 通知

## 范围与边界

通知让一个收件人知道一件已经发生的事，并管这个收件人的注意力。收件人有两种：人，和受托的 agent。来源只交出事件；给谁、多急由收件人的通知订阅决定；通知进收件人的收件箱，再推到它的投递去处。

通知是接在核心系统上的插件。核心域的成员不依赖它；去掉它，会话、agent、模型与工具原有的流程不变。

系统要够到一个主体，有五种事，各归一个领域。通知只管第四种：

| 要对方做什么 | 发起方等不等 | 归谁 |
| --- | --- | --- |
| 在一段对话里对它说话、交代 | 不等 | [会话与工作](../sessions-and-work/README.md) |
| 要它做一个决定 | 一直等到答 | [HITL](../human-intervention/README.md) |
| 交给它一份要验收的工作 | 不等，之后对账 | [日程与Job](../schedules-and-jobs/README.md) |
| 让它知道一件事 | 不等 | 通知 |
| 让它读得到一个状态现在的值 | 不等 | [Context](../runtime-context/README.md) |

通知不等于会话消息或遥测。成果提交、模型回复、界面上显示过一次，都不能证明收件人已经收到。

## 模块角色与事实归属

| 模块角色 | 责任 |
| --- | --- |
| 接下 | 一次发送的身份、认回，以及同一次提交里每个收件人的通知 |
| 通知订阅 | 一个收件人对一类事件、在一个范围里的取值、备注、期限与依据 |
| 收件箱 | 一个收件人的全部通知，和它对每条的处置 |
| 投递 | 收件人的去处、最小间隔与节拍；投递单元与每次投递的结果 |
| 来源与渠道的登记 | 现在有哪些通知来源、事件类型与投递渠道 |
| 通知来源 | 事件发没发生、内容是什么；一件持续事项开着没有 |

这是逻辑分工，不裁定成员的划分。

## 协作与依赖

来源不认识通知的内部，也不知道收件的是人还是 agent。它在自己的事实里记下事件，由它带来的一个贡献成员交给通知；持续事项由它发布到 Context，通知去读。核心域连贡献成员也没有：会话的事件由通知一侧的适配成员读会话公开的观察得到。

通知向[身份与授权](../identity-and-authorization/README.md)问资格，向存储提交事实，往入口、工具运行时、会话的输入来源里各登记一项。给受托 agent 的投递经会话的输入受理成为一条输入；通知的定义不认识会话，认识它的只有那个适配成员。

通知向来源返回的只有交付事实：接下了没有，给了谁。来源那边的结局由来源自己判，通知送到了不改它。

## 主路径与交接

1. 来源交出一个事件。通知核资格，按发送身份认回，取来源的声明。
2. 通知按当时的通知订阅算出收件人，在一次提交里写下发送与每个收件人的通知。这一刻送达成立。
3. 通知按强弱、最小间隔与节拍把通知组成投递单元，推到每个启用的去处，记下每次的结果。
4. 收件人看、了结、划掉或恢复。这些只改通知的标记。

交接的形在每一处相同：交的一方凭自己耐久的事实持有请求，接的一方用自己的一次提交接下，结果不知道就按原身份再交。恢复送达不重做来源的动作。
