# 组织、归属与权威

本规范落实 [D-001](../decisions/D-001-documentation-system.md) 与 [D-004](../decisions/D-004-requirements-foundation.md)。每个概念只能有一个权威定义；投影、示例和边界传输形状必须链接其定义并说明映射，不能静默复制语义。

| 内容 | 权威位置 | 其他材料的责任 |
|---|---|---|
| 系统目标、产品特性与用户全局要求 | [requirements](../requirements/README.md) 维护唯一正文及具体确认范围 | 建模、能力定义、决定、规格与产品化受其约束，入口只投影；确认与追溯归[需求维护](requirements.md) |
| 组织及治理规则 | 所属有效决定与本目录维护规范 | requirements 与架构只引用，不另立同义要求 |
| 贡献入口与交付信息要求 | 根 [CONTRIBUTING.md](../../CONTRIBUTING.md) | 关联需求、治理与验证依据；不另造接受权限 |
| 开发上手与排障导航 | [开发指南](../development.md) | 环境与命令引用包配置、脚本和验证规范 |
| 架构方法 | `docs/architecture-guide/` | skill 负责路由，提案不复制方法论 |
| 当前系统视图 | `docs/architecture/` | 投影上游要求、已接受选择、精确规格及其覆盖与缺口 |
| 架构选择及适用范围 | `docs/decisions/D-*.md` | 提案保留讨论，研究保留证据 |
| 候选方案与待决问题 | `docs/proposals/` | 不得作为正式规范依赖 |
| 观察、来源、推断与局限 | `docs/research/` | 不得授权项目政策 |
| 可复现的对象、操作和组合承诺 | `spec/**/vN/contract.md` | 模型、Schema、场景和证据就近关联 |
| 提供包的当前实现设计 | 所属 `packages/<成员>/design.md` | 引用精确规格，解释插件、服务、依赖和资源映射；不另定义业务语义 |
| 应用的当前装配设计 | 所属 `apps/<应用>/design.md` | 选择并组合提供者，说明配置、挂载、就绪及退出；引用包设计 |
| 当前防御指导 | `docs/defensive-patterns.md` | 保证回到所属契约，演化规则见本目录 |
| 事故机制 | 按需建立的 `docs/postmortems/` | 链接促成的规则、决定或测试 |

正式规格依语义分为 `spec/data/`、`spec/capabilities/` 和 `spec/compositions/`。目录不表示插件、进程、数据库表或部署拓扑。数据契约定义可复用的数据含义；能力契约定义可观察的行为、授权、所有权与生命周期；仅当整体性质不能归属一个能力时才使用组合契约。

每个正式契约至少有入口、版本化 `contract.md` 和 `spec/catalog.json` 中的登记。复杂度实际出现时才增加 Schema、形式模型、场景或验证映射。`spec/archive/` 是历史材料，`docs/proposals/` 是候选材料，均不进入有效目录清单。

正式内容的 metadata 与字段形状以[机器可检查的元数据](metadata.md)为准。维护者不得另建平行 registry、`current.json` 或运行时注册表来表达目录状态；`catalog.json` 只服务文档发现，不参与 Cordis 的动态解析。

产品源码、开发工具与自动化的目录归属由[源码布局与 workspace](workspace.md)维护。
契约的实现放在所属成员，检查算法放在工具包；文档与规格目录承载它们的依据和证据。

## 当前实现设计的归属

需要长期维护的提供者与运行装配设计随所属包或应用保存，默认正文为成员根的
`design.md`；成员可以位于领域子目录。内容足够复杂时由该入口导航专题，不按
插件数量机械拆页。纯数据、编解码或简单计算包只描述实际存在的映射；已有 README
足以承载的简短说明可直接维护，不为统一外观补造插件或空设计文件。

提供包拥有其插件公共入口、服务键、贡献与依赖、Context/Fiber 及受管资源映射、
生命周期实现选择和所采用的依赖来源。应用拥有实际提供者选择、配置接入、挂载、
就绪和退出关系。跨包的产品协议仍归能力/组合契约；全局架构视图链接这些正文并
说明覆盖缺口，不复制另一份包级装配清单。具体映射的描述方法见
[Cordis 映射指南](../architecture-guide/reference/cordis-mapping.md#核对本项目的具体提供者)。

包 README 链接实现设计与所采用的规格；契约的可变入口反向导航适用提供者及其
验证范围，应用设计引用所消费的包设计。当前设计标明采用的精确契约、候选或已
采用范围及其依据；实际实现状态由可追溯证据说明。公共签名的已实现定义归公开
源码，文档解释含义和映射，不抄写一份会独立演化的接口。

当前正文可随实现设计演进，历史采用通过 Git 修订和交付记录追溯；消费者交接
引用可识别的采用快照，不能只写一个不断变化的路径。公共接口的身份、兼容范围
和消费者迁移需明确；这与业务 spec 的冻结版本分别管理。设计文件不自动建立
workspace 成员，不证明实现存在，也不授予候选接受状态。

规格、映射与计划的就绪判断、变更传播和历史接续见
[规格维护](spec-maintenance.md)；来源讨论留在提案或研究，施工安排留在计划。

## 贡献与开发入口的维护

CONTRIBUTING.md 负责让贡献者知道怎样界定任务、形成可审阅结果；开发指南负责
帮助读者准备环境、找到成员和执行相称检查。详细的版本、知识流转和验证义务仍由
本目录维护，AGENTS.md 只提供常驻边界和任务导航。

环境或命令变化先改包配置、脚本及其所属说明，再同步开发指南的相关示例；治理
变化先更新对应规则，再同步贡献入口。路径变化同步索引与链接检查范围。
评审入口变更时同时检查 CONTRIBUTING、开发指南、README 和 AGENTS 的相关导航，
无变化的内容不重写。文档描述当前可执行内容，不能把尚未实现的 CI/CD 或启动方式
写成可用能力。引用检查确认路径有效，受影响的命令还需实际执行验证。

## 共享定义

SYS-REUSE：同一概念全系统共用一个权威定义，跨能力和实现语言通过引用复用；
只有语义确实不同或属于边界投影时才采用不同表示，并明确映射。本条承接原系统
约束索引中的同名规则，正文归组织规范，需求与架构入口仅引用。
