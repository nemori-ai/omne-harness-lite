# 规格与实现设计的持续维护

本页连接架构设计、精确规格、提供者设计和实施交付。它在既有
[组织规则](organization.md)、[版本规则](versioning.md)和
[验证规范](verification.md)之上说明如何维持这些材料的对应，不新增规格身份、
注册表或固定流水线。本轮补充的来源、取舍与审阅状态见
[维护提案](../proposals/design-spec-maintenance/README.md)。

## 承诺与兑现的分工

spec 拥有语言无关的精确承诺；提供者设计解释具体实现如何兑现；应用设计解释
实际选择和装配；计划安排交付；证据说明某一版本在什么范围被观察或检查过。
这些内容可以共同演进，但各自只有一个语义拥有者。具体落点归
[当前实现设计的归属](organization.md#当前实现设计的归属)。

区分内容时看消费者依赖的含义。例如，依赖失效后是否接纳新工作、旧工作怎样
交接，属于能力或组合契约；通过哪个插件、服务键和 effect 实现，属于提供者
设计。公共服务键、事件或接口发生变化也可能影响消费者，需管理接口身份与迁移，
不能因为业务 spec 未变就按任意内部细节处理。

从[提案义务](knowledge-flow.md#提案需要留下什么)进入后续正文时，保留性质的
需求依据、含义、适用范围、前提及责任方；规范承诺归精确契约，具体兑现归
提供者设计，实际结果归证据，尚需生产的产物归[交付计划](delivery-planning.md)。
引用已有条款或记录，不在每层重建一份同义表。提案保留历史取舍，不继续拥有
当前实现。相关需求尚未导出必要不变量或安全/进展约束时，不能用接口齐全代替
语义就绪；推导方法归[不变量指南](../architecture-guide/assurance/invariants.md#从目标与需求推导性质)。

依赖有不同含义：代码依赖表达公共类型和分发，运行依赖表达服务可用与绑定，
业务工作依赖表达谁接续、结算或释放工作。维护时核对它们的实际衔接；包图、注入图
或一组方法签名都不能独自说明完整动作链。建模方法见
[能力边界](../architecture-guide/modeling/capabilities.md)和
[组合核对](../architecture-guide/reference/contract-description.md#沿完整动作链核对组合)。

## 规格按性质生长

正式契约的最小组织仍是稳定入口、版本化 `contract.md` 与 catalog 中的有效登记。
只有 `contract.md` 本身不是缺陷；应判断所需语义是否充分、能否找到采用的数据与
组合定义，以及哪些保证尚无验证证据。候选沿既有提案或明确授权的草案位置发展，
不能用登记补造接受。

contract 明确职责、操作和必要行为；跨能力共享数据引用 `spec/data/` 的权威定义；
无法归属单一能力的整体性质才进入 `spec/compositions/`。某种工具适合验证性质时
再增加相应工件：Schema 表达数据结构，TLA+ 表达行为权威规格，Alloy 辅助检验
结构，规范场景表达可观察要求。各工具的边界由
[规格表达](../architecture-guide/assurance/specification.md)和验证规范维护。

文字、Schema、模型和场景应共同表达同一语义，引用稳定规则及其精确版本；实现
语言的类型、规范化或校验库是映射，不成为另一份契约。出现冲突时报告具体反例、
采用版本和受影响范围，修正拥有该含义的材料，不能挑选最容易通过的一种表示。

从每个契约的可变入口应能发现采用版本、接受范围，以及适用的提供者设计和验证
说明。简单契约可在入口直接说明；有独立验证记录时链接已有 `verification.md`，
不复制覆盖清单。没有提供者或模型时直说尚缺，不能通过建立空文件伪装交付。
覆盖表达与证据位置由[覆盖的发现入口](verification.md#覆盖的发现入口)统一规定。

一方的假设若由另一能力兑现，明确其精确保证与适用证据；外部公平性、独占访问
或后端终止等条件不能无主地变成系统保证。共享代数性质的适用前提改变时，重新
按[证明触发](../architecture-guide/assurance/composability.md#证据要求何时触发)判断，
不能因为 API 名称相同或旧模型通过就沿用结论。

## 设计就绪与实施入口

设计完成结论需要限定对象、版本和范围。以下是独立判断维度，不是 catalog 新状态，
也不要求每项设计顺序经过四道审批：

| 结论范围 | 需要支持的判断 | 不能据此推出 |
|---|---|---|
| 语义已接受 | 相关需求、行为与跨能力交接已明确，有可引用的接受依据和精确契约 | 具体提供者及应用接口均已固定 |
| 提供者设计可供本任务实施 | 任务所依赖的公开接口、提供方式、绑定和资源责任足够明确，有采用依据 | 真实包、清理和恢复行为已经验证 |
| 应用装配已明确 | 所需提供者选择、配置、就绪、挂载与退出责任可定位 | 组件各自通过就表示装配已通过 |
| 行为已有实证 | 绑定实际版本与环境的验证支持明确条款和场景 | 所有配置、全部条款或未建模性质均成立 |

架构设计时必须明确影响能力含义的身份、状态权威、授权、所有权、依赖变化政策和
跨边界交接。技术研究可以随后固定具体映射，但不能把未定的业务政策当作普通实现
细节交给消费者猜测。反过来，不影响契约、公开接口或共同装配的局部算法与内部组织，
可由实施者在授权范围内选择，无须为所有未来实现细节等待设计定稿。

实施门槛针对本次任务：消费某个服务、贡献或组合前，必须能够定位本任务依赖的
语义版本，以及所需提供者、解析条件、资源/工作所有者、就绪和失效响应。若这些
内容仍需设计，先完成相应设计任务；允许使用替身时明确采用的接口和待真实组合
验证的义务。不能把“语义已接受”作为必要映射全部齐备的替代证据。

延期确定的关键映射应在现有设计入口或计划中记录具体缺口、负责产物、维护归属、
受影响消费者和何时需要闭合。缺口只阻止依赖它的工作，不阻止独立研究或输入已
固定的实施；不得以“后续完善”让总体完成状态吞掉未完成义务。

形成可识别设计稿后按现有[评审入口](../../.meta_harness/agents/roles/README.md#按判断对象选择-reviewer)
进行独立只读审阅。评审范围包含本次声称的设计维度及关键完整动作链；语义评审
不必等待全部实现映射，但其结论不得越过受审范围。评审、接受和实际验证分别
记录，接受沿[知识流转](knowledge-flow.md#接受与交付怎样闭合)完成。

规格形成待审稿后，spec-reviewer 以给定设计为前提，检查表达完整性、明确性与维护
规范，不裁决业务正确性或合理性。施工计划形成待审稿后，plan-reviewer 检查兑现
路径、依赖、单一写入归属、并行条件与组合验收安排，不重复规格内容审计。上游
未决在计划评审中表现为受影响任务的前提，不成为 reviewer 代选业务政策的授权。
具体输入、边界和交接归[评审分工](../../.meta_harness/agents/roles/README.md#按判断对象选择-reviewer)；
按对象与变化选择，不增加所有局部修改必经的多轮关卡。

## 变更沿依赖传播

从变化的含义和来源判断影响，而非从文件扩展名决定工作。关联通常沿
“需求/决定 → 精确契约 → 提供者设计/公共接口 → 应用装配 → 验证与交付记录”
传播；实现或实验发现反例时也会反向挑战前提。这是影响关系，不要求依次改动每层。

| 变化 | 主要处置 |
|---|---|
| 需求、身份、状态转移、授权或失败保证改变 | 定位所属契约与接受依据，处理决定适用性；已发布规范按版本规则演进，再识别受影响消费者 |
| 提供方式、依赖版本、服务键、接口、作用域或清理映射改变 | 更新所属实现设计与适用接口身份，检查调用方、应用和实际行为；仅当承诺改变才演进语义规格 |
| 状态表示、观察关系、允许交错或环境前提改变 | 定位所依赖的证明/模型及其消费者，重新判断证明义务与证据适用性；不能仅凭签名未变继续消费旧结论 |
| 实现偏离既有契约 | 在契约内修复实现及相关映射，补足受影响证据；不能为使测试通过倒写规格 |
| 规范正文、Schema、模型或规范场景需要增加或修正 | 冻结版本内的工件按版本规则处理，包括只补模型而不改文字；不原地补文件后重算冻结哈希 |
| 验证结果、覆盖范围或实现状态更新 | 更新版本目录外的证据与可变入口，绑定实际对象；不能从新结果改变原规范含义 |
| 仅导航、错链或非规范说明修正 | 在拥有者处修复并做相称检查，不机械升级全部契约或重审全部架构 |

受影响消费者包括引用共享数据或组合契约的其它规格，以及实际提供者、调用方和
应用。检索精确 ID/版本、公共入口与已有映射，结合动作链判断影响；文本搜索只是
发现线索，不能证明动态装配或隐式依赖不存在。无需建立第二份总 catalog。

新规格不会自动升级旧消费者。明确本次哪些消费者采用新版本、哪些仍保持旧版，
以及它们在现有需求下的适用性和未完成迁移。共同装配跨版本使用时检查接口与语义
是否仍可组合，不以各自能编译作为兼容依据。过往证据保留其实际版本和假设，
只重做因变化失效的验证及本次新增义务。

正式发布时，接受依据、版本工件、精确依赖、catalog、冻结记录和发现入口应在
同一可审阅变更中一致；详细发布与基线检查仍归版本规范和验证规范。新增模型任务
按现有 formal-tasks 管理，不从文件存在或工具退出码推断覆盖完整。

## 交付与长期接续

计划引用稳定正文并安排实施，不能长期拥有另一份公共接口或插件设计。历史提案
和施工稿保留当时的修订与身份；选定内容进入当前正文后，旧入口指向新拥有者并
说明采用范围。已实现的精确签名引用公共源码；实施前的候选签名与其采用快照要
可辨认，不能指向尚不存在的已发布 API。

交付同步受影响的契约引用、提供者设计、应用装配、公共源码导航与验证说明，
明确仍未完成的映射和组合义务及其归属。临时工作树中的关键证据需要在退役前
按[工作树纪律](../../.meta_harness/agents/skills/worktree-discipline/canonical/SKILL.md)保留；永久入口
不能依赖临时检出继续存在。

已有材料按真实后续变更或依赖消费迁移：先识别当前正文及具体缺口，再转移必要
内容和导航，保留来源与覆盖范围。不批量生成空 `design.md`，不因新规则发布就
宣称历史能力均已补齐，也不因单一提供者映射缺失撤销其已接受的语义范围。
