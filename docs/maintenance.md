# 文档维护指南

本页面向人和agent，说明新增、修改、拆分和整合文档时怎样选择位置、控制粒度、同步消费者并检查结果。开始前确认本次任务范围和有效源；责任明确后只展开受影响材料。

[文档治理](engineering/documentation.md)拥有位置、唯一源、表达、登记和留空规则。本页提供维护步骤与落点选择，具体要求继续由各区或实际成员维护。写作方法沿[文档与技能场景](engineering/scenarios/docs-and-skills.md)加载，技能正文保持原源。

先整体理解各类知识的关系，人读[知识地图](knowledge-map.md)，agent读[体系上下文](knowledge-map-agent.md)。两者说明全局模型，本页提供实际维护步骤。位置、文种、约束或入口变化时同步这两份投影及SVG；仅业务细节变化且不影响地图时不重复改图。维护要求归[整体知识体系说明](engineering/documentation.md#整体知识体系说明)。

## 选择信息层级

先判断读者要解决什么问题，再确定含义拥有者。下表是选择落点的提示，具体位置沿[唯一源规则](engineering/documentation.md#位置与唯一源)。

| 位置与入口 | 读者应能得到什么 | 细节继续去哪里 |
| --- | --- | --- |
| 项目根、[读者入口](README.md)、[任务地图](context-map.md) | 项目定位、角色或任务路径、必要前提、下一步与停止点 | 相应正文；入口只维护导航与必要摘要 |
| [项目要求](requirements.md) | 项目要达成的目标、全局要求与阶段范围 | 产品规则及架构如何承接这些要求 |
| [系统架构](architecture/README.md) | 全系统分解、分层、依赖方向、跨责任生命周期及共同约束 | 领域模块的协作和实际成员契约 |
| [领域责任](domains/README.md) | 责任边界、逻辑模块角色、事实归属、允许协作和组合责任 | 精确接口、行为与机制的实际拥有者 |
| [工程规范](engineering/README.md) | 跨场景约束、工作流程、按任务选择的方法和交付要求 | 被引用技能、工具和成员的精确说明 |
| [任务指南](guides/README.md)及实际应用说明 | 已支持任务的前提、步骤、结果和失败处置 | 相关公开能力和运行限制 |
| `packages/<domain>/`能力组 | 组内工程分解、允许依赖、跨包协作、组合验证和共同维护 | 真实成员及协议拥有者；规则沿[两层成员文档](member-documentation.md) |
| 实际packages、apps、tools成员 | 公开类型、行为规格、内部机制、使用方法和可复跑验证资源 | 该成员的具体专题与资源 |
| [技术提案](rfcs/README.md) | 进入审议的方案、最小决定及写回关系 | 当前规范由实际拥有者独立维护；不从旧源补造历史 |
| 真实交付Issue | 本次结果、范围、条件与最小决定 | 按[操作指南](engineering/agent-delivery.md)读取启用范围；Project只作视图，逐轮过程仍留tmp |
| 内部[产品与设计源](../.meta_harness/README.md) | 产品规则、统一语言、领域对象及持续研究依据 | 相应语义拥有者；公共读者只要求读取允许的契约投影 |

顶层设计沿[应然原则](engineering/documentation.md#顶层设计表达应然)，描述系统必须满足的边界与保证。当前源码、装配观察和检查结果用于对照设计；它们不反向确定目标分解。

## 控制内容粒度

以读者能够确定本次责任和下一步为结束条件。上层保留关系与约束，下层维护精确承诺，导航把两者连接起来。

领域页应细化到逻辑模块的角色、事实拥有者、允许依赖、公开协作、关键交接和组合验证承担者。一个包内的多个模块也可能需要领域层解释；是否跨包不能单独决定信息归属。领域的初始责任入口不自动成为DDD上下文、代码包、插件或进程。

产品正文在同页末尾维护“未决问题与待定事项”。产品政策和阶段选择由产品拥有者承接，技术问题的精确正文归能力组、成员或协调者，产品页说明影响并链接该源。来源缺证保留核对责任，已回答问答及处理历史留任务tmp。具体结构沿[产品正文指导](../.meta_harness/agents/skills/product-design/canonical/references/product-document.md)。

能力组与成员包不是只各有一个导航README。两层分别拥有工程关系与成员知识；必需信息可以在README完整回答，独立任务再拆专题，按[两层成员文档](member-documentation.md)维护。SPEC避免与类型重复，但必须完整表达适用行为，不限制文档体系的必要篇幅。

类型与字段、方法签名、错误集合、状态转移、事务、并发、取消、恢复协议和验证资源随实际契约拥有者维护。跨包协议由实际协调者拥有，领域页解释参与者和组合责任并导航过去。成员尚未确定时保留具名义务、设计入口和缺口，避免虚构当前API或包名。

例如，日程领域解释Job执行结果与通知送达分别归谁、谁判断整体完成。通知确认、去重和恢复的精确协议继续由通知及相应协调者维护。领域层的粒度要求见[责任边界](domains/boundaries.md#文档内容与登记)。

## 新增正文与拆页

新正文先明确阅读任务、含义拥有者、必要内容、采用范围和消费者。若已有正文拥有同一含义，优先修订该源并同步导航。新增业务责任、类别或模块先沿[扩展指导](domains/extending-the-system.md)确定归属。

同一阅读任务的内容可以就近保留在README。出现独立阅读任务、不同消费者或独立维护节奏时再拆页；篇幅是复核线索，不设统一字数门槛。每个目录可以长期只保留README，按实际需要增加专题。

| 后续文件 | 何时拆出 | 维护什么 |
| --- | --- | --- |
| `architecture.md` | 入口已难以解释内部模块及跨成员协作 | 逻辑模块分工、允许依赖、协调责任和必要理由 |
| 具名设计专题 | 某项机制有独立阅读或维护任务 | 所属层的边界与设计；精确成员机制仍随成员 |
| `verification.md` | 多个局部保证需要组合成立 | 组合性质、承担者、验证入口、前提和未覆盖 |
| `guides/<任务>.md` | 已有真实可执行的使用、集成或维护任务 | 前提、步骤、观察和失败处置 |

这些文件是按需选择，不是每个领域的必建清单。拆出后原位置保留摘要和导航，正文只留一份。领域现有必要章节及局部登记要求继续沿责任边界维护，不能用拆页省略必要交接。

## 修改与迁移

1. 定位当前权威正文、适用范围和接受依据，读取本次受影响的局部约定。辨认文字修复、导航调整与承诺变化；承诺变化须沿原接受入口取得依据。
2. 搜索入向链接、标题锚点、登记、代码读取、生成输入及下游消费者。只读取闭合本次影响面所需的材料。
3. 修改唯一正文。整合旧材料先按[架构准入规则](engineering/documentation.md#位置与唯一源)核对项目要求、系统架构和领域责任，再组织有效信息。冲突旧设计不得作为规范迁入；实现限制进入符合性材料，未判定条款不授予采用。不能仅搬动文件改变公开身份或采用范围。
4. 同步角色和任务入口、局部导航、锚点、登记及必要消费者。存在旧源交接时，在对应语义已采用且必要消费者完成切换后退出旧权威。
5. 按下一节更新结构预期，再运行适用检查。必要含义或消费者未明确时，只暂停依赖的写入或切换，向实际拥有者说明缺口和影响。

顶层源码归属和开发环境按[workspace](workspace.md)，目标能力组及包边界按[产品包组织](package-organization.md)。新增领域目录不自动创建或迁移成员。生成或宿主适配的操作按原工具入口执行，不能直接编辑生成产物代替源。

## 登记目标与留空

应有文档和必要章节按[登记规则](engineering/documentation.md#最低内容与维护)维护。项目级目标归[docs/documentation.json](documentation.json)，领域及成员维护自己的局部目标，同一目标只登记一次。默认发现范围与格式见[spec-tools](../tools/spec-tools/README.md#文档目标与缺项计量)。

新增必要内容先在真实要求拥有者明确，再同步稳定目标身份、拥有者、路径、章节和依据。结构要求的adopted表示应有结构已获授权，不表示目标正文中的新技术设计已接受。纯文字修复无需新增目标或改动结构依据。

具名目标成员可以先登记并建立文档目录，同时标明尚非真实workspace成员。文档落位不创建package.json、源码或运行实例，也不授予设计接受或实施权限。真实成员仍按[workspace](workspace.md)核对。

未建必要文件仍可登记，工具报告缺文件。未完成整页或必要章节使用独立行的 `<!-- documentation:placeholder -->` 标记；完成相应内容后移除。允许留空仍是缺项，留空依据持续由原拥有者维护。自然语言TODO不保证被工具识别，不用一句未决说明冒充必要正文已完成。

登记不存手填完成状态。维护者也不在正文记录当前通过数量；单次库存、评审与执行输出留工作树tmp。

## 检查与偏离报告

普通文档维护先检查真实引用和登记，命令在仓库根运行。只需确定首轮角色路径时用[角色查询](../tools/spec-tools/README.md#按角色读取上下文)；它不递归展开依赖。随后沿实际任务读取必要拥有者，分别记录访问资格、输入版本、结果及停止点。

```sh
make docs-check
make docs-inventory OUT=tmp/documentation-maintenance-report
```

docs-check检查已有链接与镜像，inventory观察已登记文件、章节、占位和unknown。inspectable只说明工具支持观察的结构存在；语义充分、应然与实现一致、读者实际体验和产品运行保证分别需要相应评审或真实验证。没有运行证据时写明未验证。

比较增减时使用维护前保存的独立登记及依据源，具体操作沿spec-tools。新目标、范围、要求或依据变化可能报告measurement-change，不能将其算成历史偏离消除。删除登记或放宽要求也不能作为修复收益。

报告给出全量存量、本次增减、口径变化、未覆盖和无法判定，注明承诺拥有者及影响。按[验证说明](verification.md)和[clean-loop](clean-loop.md)选择相称检查；文档任务不强制完整产品测试，新增门禁须沿其采用范围明确。

## 交付与后续维护

交付说明改了哪些权威正文、为什么改、哪些消费者同步、实际检查结果和剩余责任。正文写完、技术内容接受、实现完成和运行验证是不同结论，分别按真实依据报告。

后续设计从区入口及实际拥有者展开。架构未决沿[集中入口](architecture/README.md#未决事项与后续设计入口)维护，领域后续义务就近保留拥有者和下一入口。完成任务在临时计划中划掉，除[正式保存例外](engineering/documentation.md#四类长期成果与普通任务)外，候选、访谈、过程决定及单次证据留tmp。

维护者接手时先定位本次修改的源和消费者，无需通读所有文档。发现相同内容在两处成为权威时，先核对含义、适用范围与采用依据，再由拥有者确定唯一源及切换范围。
