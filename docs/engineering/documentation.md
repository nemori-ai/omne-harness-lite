# 文档治理

本页维护文档位置、唯一源、阅读、表达与留空规则。此范围来自项目负责人确定的信息架构及工程文档要求。工程区以现行规范引用和技能方法组织共享／场景正文；技术政策、系统架构和领域的未决仍由其拥有者明确，本页不替它们制定政策。

## 分层与遵循方向

阅读层按定位、任务路径、操作解释、精确承诺逐层展开。读者身份与访问权限分别判断；十类读者共享正文，通过[读者入口](../README.md)和[任务地图](../context-map.md)选路径。

约束方向是目标与产品规则 → 系统技术约定 → 领域与成员承诺 → 实现与验证。工程约定横跨研发各层。下层不能靠实现现状改写上层承诺；测量只报告观察，不授予接受。不同拥有者的冲突须核对含义、范围与采用依据。

### 顶层设计表达应然

顶层要求、架构、领域设计和工程规范正文描述系统应当怎样工作，以及实现必须满足的职责、边界、约束和保证。本原则适用于后续所有顶层设计文档的起草与修订。

设计依据是已确认的目标、产品规则、有效契约及明确采用的取舍。撰写时不从当前源码反推系统分解、接口、生命周期或行为要求，也不为适应现有实现而缩减上层承诺。旧设计同样须核对适用范围及其与新要求的关系，不能仅因已有代码或文档就自动沿用。

实现现状、源码映射、迁移进度和验证结果作为独立的符合性材料维护，用于识别实现与设计之间的偏离。发现偏离时，记录受影响的承诺与实际证据；不能通过把应然正文改成实然描述来消除偏离。

顶层设计可以规定目标中的模块、接口、执行与部署关系，但这些关系不表示当前代码已经实现。尚未决定的设计明确保留为待定，阶段范围按已确认决定标明；正文完成或采用也不等于实现完成或验证通过。

## 位置与唯一源

| 位置 | 持续维护什么 |
|---|---|
| 项目根 | 项目介绍、贡献入口和 agent 的心智／导航投影 |
| docs | 项目级要求、工程规则、技术架构、领域关系、任务指南和文档治理 |
| docs/domains/<已确认领域> | 领域范围、域内关系、成员导航、必要指南和组合验证责任 |
| packages/<domain> | 能力组的工程分解、成员依赖、关键协作、组合验证责任与共同维护 |
| 实际 packages/apps/tools 成员 | 公开形状、完整必要行为契约、使用与机制说明、当前选择的必要理由及验证资源 |
| .meta_harness | 独立系统目标、产品规则、统一语言、领域对象、持续研究、可迁出 agent 方法与人类协作者指南 |

同一承诺一份当前权威正文。入口、解释、翻译和图引用其源；不复制成第二套约定。代码目录不自动等于领域、插件、服务或部署单元。

产品正文在同页维护有效未决，产品政策及阶段选择归产品拥有者。精确技术未决及后续设计义务归能力组、成员或协调者正文，产品页保留影响和链接。来源缺证显式保留核对责任，已回答问答及处理过程留任务tmp。

本项目的系统架构以[docs/architecture](../architecture/README.md#采用状态与当前有效源)已接受正文为唯一准据，领域与成员只能在其约束下细化。旧技术材料的接受记录、位置、现有消费者或测试通过，都不能使其成为并列架构权威，也不能授予违背现行架构的例外。

[旧技术材料入口](../../.meta_harness/design/architecture/README.md)定位尚未整合的专题、完整Session候选及其消费者。保留文件表示迁出尚未完成，不表示其中全部设计继续有效。整合时先按现行项目要求、系统架构及领域责任筛选，再决定落位：

- 与上层一致的有效细化，由实际领域或成员拥有者承接其条件、例外与验证责任。
- 违背上层的旧设计不得写入正式规范正文；已迁入的相应条款须删除或依据上层重新设计，不能为保全旧源降低架构目标。
- 当前实现确有相应限制时，在成员使用说明或符合性材料中记录事实、目标差距及修复责任。记录偏离不授权该旧设计继续约束后续实施。
- 尚不能判定符合的条款，不借迁移授予采用。记录未判定范围及拥有者，只暂停依赖该条款的设计或切换。

源切换仍须核对公开身份、资源及真实消费者，但不以保全所有旧条款为完成条件。正确的终态是符合现行架构的唯一正文，以及可发现的实现偏离和未判定项。

本项目要求以[docs/requirements.md](../requirements.md)已接受正文为准，未决验收条件继续计为缺项。旧要求用于核对引用和取代范围，不能据此补入新的目标、条款或限制。新增或修订要求由负责人明确，再更新唯一正文及实际消费者；不能把同一要求保留为两份现行权威。

系统集成规则由架构区的Cordis集成约定维护，机读采用映射由同区constraints维护，阶段后端选择归部署专题的采用页。它们分别拥有共同集成要求、检查输入和阶段技术选择，不重复项目要求或实际成员的精确规格。必要内容与检查入口由[架构地图](../architecture/README.md#内容地图)登记。

项目术语以[统一语言](../../.meta_harness/design/ubiquitous_language/README.md)为锚点，正式含义与英文名从相应词条读取。文档引用定义，不另立一套同义词或术语表。文字清理保留正式概念；发现定义冲突时交原拥有者裁定，不在润色时自行统一。

## 四类长期成果与普通任务

产品设计、RFC、长期规格和技术设计是四类长期成果，分别拥有持续产品规则、正式技术提案、当前必要行为及兑现机制。普通任务卡独立记录一次交付，不是产品 topic 的固定分解成果。实际位置与关系由[交付协议](delivery.md#长期正文与一次交付)维护；feature、bug、refactor、performance、maintenance和investigation共用[工作类型协议](work-types.md)，不要求先有PF或产品场景。

正式RFC进入[提案区](../rfcs/README.md)，保留进入审议的方案、最小决定范围及写回关系。当前规范仍由实际拥有者维护，不依赖读者拼读提案历史。正式交付卡在真实Issue保留本次范围、最小决定及恢复定位，Project是调度视图。这两类是明确的保存例外，不将全部访谈、逐轮评审、调度store、原始证据或session log变成永久记录。

普通任务协议已采用，日常使用以[单一配置](github-delivery.json)的启用范围为准。未启用时只形成获准任务草稿。每项任务按实际需要明确独立身份、范围和具名结果接受责任。封存产品与Git历史保留来源身份，不成为当前任务源。平台启用与实际宿主行为须另行验证。

## 单次交付规格与长期规格

先按用途区分规格，再选择正文位置。文件名为`spec`、由技能生成或用于本次验收，都不能单独决定它是否是长期权威。

| 类型 | 回答什么 | 维护与归属 |
| --- | --- | --- |
| 单次交付规格 | 本次解决什么问题、改变什么、哪些不做，以及实施依赖和验收范围是什么？ | 面向本次实施与评审，引用适用的长期承诺。任务草稿与交付输入留工作树`tmp/<task>/`；已有获准使用的任务记录可直接引用，不另建永久规格副本 |
| 长期规格 | 系统、领域或成员持续必须满足哪些要求、接口和行为，适用条件与例外是什么？ | 由实际承诺拥有者维护当前有效源。项目要求、系统架构和领域约束按各层归属维护；精确形状由公开类型及必要校验表达，类型不能完整表达的行为由成员或协调者的契约维护 |

已有长期承诺足以支持局部修改时，不要求另写单次交付规格。需要整理讨论结果时，按[调查与设计场景](scenarios/research-and-design.md)使用Matt `to-spec`等方法；技能模板组织任务输入，不建立第二份长期权威。

单次交付提出新的持续保证或修订已有保证时，明确对应拥有者、适用修订、改变范围与接受依据。获准的承诺先写回其长期拥有者，再推进依赖该承诺的实施；交付时同步必要消费者及验证资源。任务规格不能成为某项持续保证的唯一源，也不能在任务结束时连同过程材料丢掉该保证。未获接受的候选不能借写入正式目录变为现行契约。

验收既核对本次交付范围，也核对受影响的长期承诺。任务完成不表示所有系统保证已兑现，单次测试通过不替代持续验证义务。一次执行的结果留任务材料，可复跑测试、模型与必要夹具随实际消费者维护。

## 首批目标与暂时留空

首批固定目标包括项目／贡献／agent 入口、docs 读者入口与任务地图、开工定向、工程／系统架构／领域／指南入口，以及演进与发布、系统架构的内容地图及专题落点；TypeScript 方法进入技能引用，Node 项目义务随防御与真实运行拥有者，不另设自有教程。新增项目要求正文须涵盖定位与目标、阶段与功能范围、内核与开放能力、多模态输入与输出、动态演化、隔离、权限管理与人在回路、数据安全与隐私、恢复、工程观测、承诺与验证、未决验收条件及维护归属。现有开发、布局、验证、防御与整洁回路保持其拥有者；产品、统一语言、领域对象和研究保持 meta 入口。

本阶段允许[TypeScript 未定政策](skills.md#尚待明确的-typescript-政策)、[运行未定政策](scenarios/dependencies-and-runtime.md#尚待明确的运行政策)、[首次发布政策](publication.md#首次发布政策待定)，以及架构入口明确暂缓的专题留空。它们仍是必要缺项，TS 与 Node 旧页退出只改变位置与登记口径，不算缺项修复。架构具体要求、接受状态与留空依据由[架构入口](../architecture/README.md)维护；系统总览已形成正文，不再属于待写范围。可读引用不撤销旧保证，也不表示未定政策已采用。留空依据持续有效，直至对应必要内容正式采用并撤销该依据。

项目要求中的必要验收条件在负责人逐项明确前允许暂时未完成，使用占位标记报告缺项。写出未决问题清单不等于补齐条件，结构可检查也不等于正文接受。

使用、管理、部署和集成的专门指南登记为应有目标。负责人已要求先留空、按实际交付补写；当前建立来源和承接入口，完整操作指南允许继续占位，仍报告缺项。应用／能力拥有者与文档维护者在真实公开操作、前提及相称验证具备后补齐，不从目标架构推导操作支持。具名目标成员尚缺精确契约时的范围与承接归[成员文档要求](../member-documentation.md#行为契约与完整文档)。负责人已接受[领域责任正文](../domains/README.md)，其[最低内容](../domains/boundaries.md#文档内容与登记)作为应有结构登记。正文的接受范围由领域入口维护，不能从包分组推断领域或从结构采用推断技术接受。产品优化另行决定，不预建假topic。

## 最低内容与维护

入口写清范围、状态、当前有效源、未完成目标及维护责任。每条读者路径给前提／权限、必要源、下一步、实际能力与验证限制、展开条件、阅读停止与行动暂停条件、缺项拥有者。

正文分别说明目的、范围和适用条件，再表达相应规则／关系／操作及必要验证责任。具体章节随负责人重写确定，不用填模板冒充充分。未写整文件或章节使用 `<!-- documentation:placeholder -->` 明确标记；补成正文时才移除对应标记。模板为新成员创建的固定文件按[成员文档的固定骨架](../member-documentation.md#固定骨架)生成，创建时即带这一标记；创建义务归模板，补写正文仍归成员拥有者。

项目层目标由[documentation.json](../documentation.json)维护，领域及成员可在自己的documentation.json维护所属目标。同一目标只保留一份现行登记，工具按实际拥有者发现；不能在根与局部重复登记。登记存稳定身份、拥有者、文种、权限、路径、必要章节、要求依据和留空依据，不存手填完成状态或规范全文。具名文档目标及其目录不等于真实workspace成员，须明确尚缺的成员建立及采用责任；文档落位不授予实施权限或证明运行支持。修改要求先改本页或真实拥有者，再同步登记；登记变动不是修复收益。结构要求的adopted不表示目标正文的新技术设计已接受。

源修订后，维护者核对角色／任务入口、入向锚点、JSON／代码读取、生成输入和影响面消费者。同一承诺的正文及必要消费在一批中切换，旧源退出后不留第二份权威。存在关键语义歧义就暂停依赖的写入，由负责人裁定；未进入正式RFC的候选、访谈、逐轮评审和单次输出留工作树tmp；正式保存例外按[长期成果与任务的保存边界](#四类长期成果与普通任务)判断。

## 工程目标与必要结构

工程文档让人和 agent 确定有效输入、范围、适用规范、技能顺序、结果、验证和停止点。共享规范回答适用任务守住什么；场景指南回答本次怎样连接步骤；技能正文拥有具体方法，成员拥有精确语义。下列位置及必要内容为已授权结构，文章的新语义、技能加载和行为结果另行判断。

| 位置 | 必要内容 |
|---|---|
| engineering/README.md | 从任务开始、共享查询、现行源与未完成范围、检查维护 |
| workflow.md | 输入与范围、最小上下文、协作交接、停止继续、完成声明 |
| quality.md | 目标依据、成果风险、性能成本、失败未知 |
| skills.md | 固定来源、采用和加载、方法／候选、差异、证明层次、完整 port 与实际加载缺项、更新 |
| publication.md | 目的范围、演进与交付、验证局限、首次发布未定政策 |
| skills.md、scenarios/dependencies-and-runtime.md 的未定政策段 | 分别保留 TS 政策与例外、部署支持及容量背压和环境例外的具名责任与缺项 |
| documentation.md | 本页的分层、位置、目标、维护、表达与检查 |
| delivery.md | 四类长期成果与普通任务的关系、卡与Stage、条件和解锁、决定、单写、创建对账及访问失败 |
| work-types.md | 六种主类型、附加输入、证据、接受责任与长期成果交接 |
| agent-delivery.md | 对话判断、建卡修订、取任务派发、更新、决定记录及恢复回执 |
| scenarios/README.md | 任务选择、组合最小阅读、方法采用与维护 |
| scenarios/research-and-design.md、feature.md、bug-fix.md、refactoring.md、performance.md、dependencies-and-runtime.md、review-and-delivery.md、docs-and-skills.md | 何时使用、开始输入、最小上下文、共享引用、工作步骤、完成交付、停止恢复、示例参考 |

文件相对本区；精确路径与稳定章节身份只在[目标登记](../documentation.json)维护。共享规范只保留适用解释和权威指针，不复制品味、验证命令表或技能正文；场景只维护其交接顺序，不另存第二份技能来源表。

用户选定的 Matt 六项补充按场景触发，具体名单与采用边界归[技能入口](skills.md)。实际 port 来源、本机安装与宿主发现已核对；全树采用、实际调用、hook 执行与行为验证仍有未覆盖，继续标记相应必要章节；新增高风险门禁仍未具体采用。unknown、未采用、未执行和允许留空不能算符合。

两份开发指南须提供项目初始化的插件前提。[开发指南](../development.md#初始化-coding-agent-插件)拥有实际harness安装、版本核对与缺口处理的步骤；[给人的指南](../development_human.md#开始前准备-coding-agent-环境)说明负责人需要核对的环境、加载与更新责任。精确版本和revision继续归技能来源表，不在两份指南另存。

## 维护指南与局部入口

开发指南须提供环境与插件初始化、任务开始、源码落位与成员创建、修改验证、一次交付的验证与整洁回路、提交与PR、终态与过程材料的操作入口。它说明何时选择何种检查、怎样绑定候选和形成交付；工程规则、系统保证、完整工具语义继续由实际拥有者维护，不在开发指南另立同义规范。

[文档维护指南](../maintenance.md)提供各层粒度的选择提示，以及新增、拆页、修改、迁移、登记、检查和交付的连续操作路径。本页继续拥有位置、唯一源、表达、登记及留空规则；分区拥有局部必要内容和承诺，不在指南中复制各区完整规范。

维护指南是负责人要求的应有文档，必要内容包括选择信息层级、控制内容粒度、新增正文与拆页、修改与迁移、登记目标与留空、检查与偏离报告、交付与后续维护。局部README保留本区粒度、状态和维护摘要并引用指南；新增指南不改变原技术正文的采用与退役范围。

docs的[读者入口](../README.md)按十类角色组织起点与停止条件，[任务地图](../context-map.md)按任务定位必要上下文。本区[AGENTS](../AGENTS.md)是继承根提示后的区域agent入口，为阅读、设计、实施、集成、评审、运维和维护提供常驻的分层心智、责任地图与触发判断，不能只面向文档维护者。它须说明当前有效源与目标、按任务展开，以及维护时的进一步加载条件；角色不授予访问、修改或接受权限。

区域提示保留跨任务有用且难以从普通工程知识推断的心智、地图、品味、边界与触发。具体规则按需进入其拥有者，通用方法和操作外置到技能、指南与工具。十类角色的完整阅读路径仍由README维护，不在AGENTS重复；整个根与区域继承链须核对权威、重复和上下文成本，并用局部修改、边界变化、源与实现冲突、绕过公开边界等代表任务探针验证指引。

## 整体知识体系说明

[知识地图](../knowledge-map.md)供人一次整体理解项目知识和文档的归属、遵循关系、状态、阅读与维护，使用静态图、文字替代及例子。[体系上下文](../knowledge-map-agent.md)供agent按需一次加载相同模型，提供明确的分层、拥有者、状态判断及加载和停止条件，不要求解析图或先通读所有入口。[开工定向](../orientation.md)供做架构、领域、契约、装配、实现切片或设计评审的人和agent开工前读一次，用图给出领域地图、协作方向与顶层架构，各图带状态与出处。

这三份（知识地图、体系上下文、开工定向）都是现行源的解释投影，不成为第二规范或完整任务流程。图中的路径和关系随所在的Markdown一起维护；图不表示软件依赖、部署拓扑、产品支持或完成度。访问资格仍由实际入口与操作确认，内部材料不成为公共消费的必读。

知识位置、文种、约束、状态含义或加载入口改变时，拥有者与文档维护者同步三份说明中受影响的部分、静态图、真实入向及登记。三份分别必须承载：整体地图/知识归属/遵循与状态/阅读和维护；分层模型/知识归属/状态与判断/加载与维护；领域地图/协作方向/顶层架构，以及各图的状态与出处。仅局部业务细节变化且未改变体系关系时，不机械扩充地图。正文不手填全量完成数、插件版本或派生调度状态；这些事实由其唯一拥有者维护。

开工定向还随它所列的出处章节维护，步骤归该页的[维护](../orientation.md#维护)一节。开工定向是[首批目标](#首批目标与暂时留空)之一。

## 产品包组织文档

[产品包组织](../package-organization.md)拥有目标能力组、责任到组的导航、包边界及新增规则；workspace拥有顶层归属与开发环境，领域拥有模块责任与协作，成员拥有精确接口和行为。根与包入口引用这些拥有者，不复制完整包树。

该专题是本轮正式落位的应有正文，必要内容为组织原则、目标目录、责任与能力组、包边界与公开入口、SDK与系统接入、依赖方向与Cordis集成、新增与扩展、文档归属与维护路径、现有成员与工具适配。目录治理更新不表示旧成员、模板或检查器已迁移，不接受新的运行机制或精确接口。

能力组与成员包两层都维护完整必要文档，要求归[两层成员文档](../member-documentation.md)。该页须说明三处知识归属、能力组要求、成员包要求、阅读与维护路径及检查边界。公开类型拥有形状，SPEC 拥有必要行为，不重复类型定义；新成员的架构、流程、对象模型、公开接口导航、使用定位与Cordis说明在创建时有固定专题位置；固定骨架以外的指南、参考与专题按实际阅读任务另文维护。薄 SPEC 不是体系厚度上限。具体模板及采用条件沿[包创建入口](../development.md#创建和整改产品包)与模板拥有者核对，正文不虚构新模板版本或命令支持。

## 检查与结论边界

`pnpm run check:docs` 检查已有 Markdown 链接与镜像；`pnpm run docs:inventory` 检查已登记的应有文档和章节，包括尚未建的位置。入口首轮可导航不等于十类真实体验通过，真实任务和人类反馈仍需分别验证。

inventory 的 inspectable 只表示受支持正文结构可检查。缺项、批准留空、候选、采用未知、工具错误分别报告；缺项或未知不增加合并硬线。工具格式、profile、比较方法和命令细节由[spec-tools](../../tools/spec-tools/README.md#文档目标与缺项计量)维护。
