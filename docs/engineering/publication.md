# 演进与交付边界

## 目的与范围

本页供开发、集成与交付负责人判断当前演进政策、独立消费、提交和发布边界。具体表达由贡献指南拥有，准备方法从工程技能入口展开，制品操作由对应工具和应用拥有者维护。

## 正文

### 当前演进与消费者

当前0.0.0至0.1.0阶段鼓励有正向收益的破坏性重构。重构须有明确目标与收益依据；改变承诺先明确新采用范围，仍依赖的组件按精确版本消费，验证按风险与影响选择，不扩大无关重构。具体判断沿[研发品味](skills.md#ub-mode-研发品味)，阶段要求归[SYS-EXPERIMENT](../requirements.md#当前研发阶段sys-experiment)。重构遵循有效要求与已接受承诺，获准的新语义在同批同步当前消费者并删除被替代实现。没有明确要求时，不增加兼容双轨、过渡层、回填或降级路径；不能独立验证的切片合成一个交付单元。保留历史材料不构成兼容承诺。进入0.1.0时重新评估阶段政策，物理移动不能改变接口身份或采用状态。

契约成员破坏性改动的允许时机与申请口子归[里程碑内的规则](integration.md#里程碑内的规则)，卡上的申请方式见[契约变更与里程碑类型](delivery.md#契约变更与里程碑类型)。

公开包消费区分类型依赖与运行时依赖，编译选项按实际 Node 和 Cordis 依赖验证。源码、生成声明与独立包消费者分别核对，不能用断言或别名掩盖边界问题。消费归属按[源码布局](../workspace.md#使用与维护)和实际成员 README、公开类型及必要行为核对。对外可单独消费的能力须检验真实声明、入口、依赖及制品；仓库内构建通过不等于独立安装或打包成功。

### 提交表达与权限

准备提交或 PR 表达时，方法按[技能入口](skills.md#playbook-入口)选择 Opening a PR，结果按[贡献表达](../../CONTRIBUTING.md#提交与-pr-表达)组织，标题和描述对应最终 diff。作者、分支及来源 trailer 归[贡献交付](../../CONTRIBUTING.md#形成可审阅的交付)。

任务授权决定是否提交、推送、发 PR、合并或部署；技能末尾的动作不是额外授权。已有明确授权持续有效，无需重复询问。没有相应授权就交付可审阅成果和证据，停在外部动作前；角色或检查通过不能自行获得权限。

### 评审接受和制品

评审意见、检查结果和正式接受沿[贡献接受](../../CONTRIBUTING.md#评审与接受)分别判断。流程使用[评审与交付](scenarios/review-and-delivery.md)；pstack 的 Opening a PR、Babysit、Shipping 是 playbook，适用和采用边界在[技能入口](skills.md)。它们不能覆盖项目风险选择或本次任务终点。

制品、归档及部署按所属应用和[artifact-builder](../../tools/artifact-builder/README.md)的实际支持操作，核对产物消费者与最终字节。逐轮评审与单次日志按[终态规则](../development.md#终态与过程材料)留任务tmp。正式RFC及Issue最小决定适用[保存例外](documentation.md#四类长期成果与普通任务)，不搬成第二份现行工程规范。

### 成果保存与跨会话接续

按 cloud agent 的使用前提，session log 和本地机器状态可能丢失。代码、正式正文、测试及拥有者维护的必要资源，在相称的可验证单元或预期中断节点及时提交，并在任务已授权的远端分支成功保存。不能等整项任务结束才首次保存；本地 commit 不能支持机器丢失后成果仍可取得的声明。

具体节点沿所选[自驱流程](skills.md#playbook-入口)及本次任务规模确定。两个 Autopilot 的首次推送时间是专用默认，不新增全项目统一分钟数。Git 远端保存、合并、正式接受及行为验证分别声明；已有授权持续有效，技能不授予新的外部权限。

只选择可入库成果。正式RFC及真实Issue的最小决定和交接按各自拥有者保留；Issue记录成功与Git远端保存分别读回。临时计划、decision trail、调度store、缓存、原始执行证据和transcript不因恢复要求整目录提交。pstack 的 resume store 位于本地 Git common directory，可支持检出仍存续的跨 session 定位；它不随 commit 推送，删除或重 clone 后不自动保留。并行任务保留各自检查点定位，不能把共享 latest 指针当调度锁或所有任务的唯一恢复依据。

Pause safely 与 Session pickup 的具体步骤沿[流程及恢复参考](skills.md#playbook-入口)。交付说明区分本地已提交、远端已成功保存与临时状态仍只在本地三个事实；不能用 checkpoint 文件存在代替远端取回证据。若本次任务还要求保存不可重建的临时材料，仅沿该具体需求处理，不默认新建永久过程史或远端状态服务。

## 验证责任与局限

交付者记录实际提交或未提交输入、范围、验证、未知及下一责任。未推送不能声称远端 CI 通过，未执行 Shipping 不能声称已合并。跨平台或独立消费未验证时保留缺口，由对应制品拥有者闭合。

首版正式发布时需重新制定兼容、迁移和发布规则；目前未采用。由发布责任人定义版本、支持范围、准入和消费者安排，不能把实验阶段政策延伸为长期兼容承诺。

## 集成发布

共享分支发布遵守[现行准入](integration.md#现行准入)：经 PR、admin 确认，由发布身份在一次原子推送中更新分支并创建记录标签。已有授权在精确适用范围内沿用；缺失的实际权限不能由工具或绿测补出。超时先读 refs，Git 成功后的 Issue 投影由原单写者接续。

[RFC-0011 revision 1](../rfcs/RFC-0011-trunk-admission-and-track-tree.md#15-release-与对外发布) 第 15 节接受 `release` 作为对外发布的主干位置。npm 的版本、支持范围和消费者安排仍由[首次发布政策](#首次发布政策待定)另定。`release` 分支还没有创建，创建时直接采用与 main 相同的确认。
