# 性能诊断与优化

## 何时使用

用于已测慢、资源异常或明确指标改进。一次故障用 Perf issue；持续单指标提升可参考 Hillclimb；运行／trace forensics 以诊断结束。一般文档改动不要求基准。

## 开始需要什么

需要指标、目标拥有者、实际工作负载、环境、基线采集方法、功能承诺、写范围和资源限制。无性能预算可以诊断和比较，但不能自造达标阈值。

## 最小上下文

先读被测入口和相关成员运行承诺、已有 trace／基准；how 用于解释测量，不替代测量。涉及取消、缓冲或事件循环时展开[资源所有权](../../defensive-patterns.md#dp-06-所有权必须可追踪)及[释放终态](../../defensive-patterns.md#dp-04-释放以可观察终态为准)，新边界才补设计。

## 适用共享规范

[性能证据](../quality.md#性能与成本证据)、[异步资源验证](../quality.md#异步资源的验证责任)、[结果声明](../workflow.md#完成与交付声明)。

## 工作步骤

1. 按 [pstack 性能 playbook](../skills.md#playbook-入口)选诊断或优化终点，用 benchmark-checklist 核对基线是否测到目标工作。保留负载、环境、样本、噪声与原始产物。
2. 基于测量形成可检验假设，按需用 how 理解源码；已有 trace 分析可用 Trace forensics。不能只读源码就断言性能上限。
3. 在已接受行为内实施一个可解释改动；跨函数或公开边界需要设计时参考 architect，并服从本次语义接受及[隔离责任范围](../workflow.md#责任与协作交接)。
4. 在可比条件下重复测量，同时复验功能、失败、资源和消费者。改变负载／环境或测量方法时单列口径变化，不混为改善。
5. 比较指标、波动、瓶颈、资源代价和剩余未知。未测入口或结果不确定就报告 inconclusive，不能宣布达标；沿评审交付结束授权范围。

## 完成及交付

提供基线与候选数值、重复／样本、环境、负载、差值、功能验证和代价，能沿方法复跑。没有可比基线就不报告提升百分比；诊断未修复分别写清。

## 停止与恢复

缺环境或指标含义不清时暂停性能结论，继续独立准备测量或取证。发现语义退化先处理契约，不用速度收益抵消错误；目标与方法明确后恢复。

## 示例与精确参考

优化批量查询时保持租户隔离和失败语义，用实际负载比较延迟与内存。空缓存路径变快不能代表真实工作负载，SQLite 数值也不代表另一后端。
