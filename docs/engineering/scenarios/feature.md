# 新功能交付

## 何时使用

用于已明确的新行为或现有行为扩展。新产品语义未定先走[调查与设计](research-and-design.md)；只有修正既有承诺走[缺陷](bug-fix.md)。本场景可以复用已接受设计，不能强制重复设计。

## 开始需要什么

需要精确需求及采用范围、接口／行为拥有者、消费者、写范围和验收。核对本树、环境与实际支持的接口或操作。必要语义未定仍可盘点影响和取证，依赖它的实现暂停。

## 最小上下文

读需求拥有者与相关成员 README、公开类型、必要行为、局部 AGENTS 和已有验证。跨边界保证展开架构及协调责任，局部责任足够就停止扩展。不以产品正文或目录存在推断开包条件。

新增业务责任、类别或模块时，先从[领域地图](../../domains/boundaries.md)定位拥有者，按[扩展指导](../../domains/extending-the-system.md)区分内部模块、提供者、责任入口与实际包，再按[产品包组织](../../package-organization.md)选择目标组、包边界和SDK投影。精确契约随实际拥有者；实施前核对模板、规则适配及真实消费者，不从目录推出接口接受或迁移完成。

## 适用共享规范

[工作输入](../workflow.md#有效输入与范围)、[协作交接](../workflow.md#责任与协作交接)、[TS 方法](../skills.md#pstack-方法入口)、[公开边界](../../workspace.md#使用与维护)、[相称验证](../quality.md#按成果和风险验证)。

## 工作步骤

1. 按 [pstack poteto-mode 的 Feature playbook](../skills.md#playbook-入口)组织任务，先用 how 定位影响。路由与实际读取方式按该页的固定 port 来源。
2. 只有新边界或既有设计不足时用 architect；类型之外的承诺可按需用已选 Matt codebase-design。有效输入充分时直接从该阶段继续，不重复访谈或审批。
3. 明确可验证单元与消费者，按[任务跟踪](../workflow.md#任务跟踪与接续)保留原步骤、跳过理由及四项吞吐检查点。需要补充切片时使用 Matt to-tickets；已有已接受故事卡保持其验收身份，不重复切分。独立任务按隔离交接并行，共享对象单一负责人，耦合任务按依赖推进。
4. 实施实际公开类型、行为与必要验证，优先复用已有方法。相称且有价值的测试路径可用明确来源的 pstack:tdd；缺真实验证路线才参考 create-verification-skill，并由项目 canonical 源维护。
5. 验证真实产物及受影响消费者，必要时用 blast-radius 核对 diff 外行为。按风险选择接受看法及相称验证；长任务按[成果保存](../publication.md#成果保存与跨会话接续)及时保存真实成果。沿[评审与交付](review-and-delivery.md)汇总，无发布授权就停在可审阅交付。

## 完成及交付

交付需求到行为的对应、实际实现、公开消费者、检查及未覆盖。已接受设计、实现完成、行为验证和正式接受分开声明。未完成义务保留具体拥有者，不能用 mock、骨架或构建通过声称新能力已兑现。

## 停止与恢复

关键承诺、写范围或必要验证环境缺失时，只停相关实现／接受。能独立落实的已有要求继续；冲突向拥有者提供反例。输入补齐后按真实影响恢复，不能为完成数字删验收或绕过公开边界。

## 示例与精确参考

已有 SPEC 的新查询可直接改其成员并检验实际公开调用；无需重新跑全套架构。新增租户授权含义则先回语义拥有者，不能让 Feature 默认自主实施替代接受。
