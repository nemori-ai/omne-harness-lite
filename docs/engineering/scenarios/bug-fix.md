# 缺陷定位与修复

## 何时使用

用于实际行为偏离已接受承诺，包括回归和运行故障。慢而功能正确的任务以[性能](performance.md)为主；根因未知仍可调查，不把候选原因写成事实。

## 开始需要什么

需要实际／预期行为、精确版本、复现入口、环境、相关契约和可写范围。敏感输入以允许的最小证据提供。缺运行环境时仍可查代码和契约，但报告未复现，不能宣称真实根因已验证。

## 最小上下文

先读发生故障的成员公开接口与必要行为、相关源码及现有测试；新保证或源冲突才展开设计。已明确的局部契约足够就停止扩展产品与架构。

## 适用共享规范

[停止与继续](../workflow.md#停止与继续)、[失败未知](../quality.md#失败未知与完成范围)；涉及异步资源时补[异步资源验证](../quality.md#异步资源的验证责任)。

## 工作步骤

1. 按 [pstack Bug fix playbook](../skills.md#playbook-入口)在发生故障的实际入口复现，固定版本、输入、环境和预期。无复现证据时显式标明，不以替代测试当同一入口的复现。
2. 按 how／why 理解机制并排除假设。Matt diagnosing-bugs 仍是[按需入口](../skills.md#matt-写法入口)，未采用就不能列为必需步骤或声称已加载。
3. 在现行契约内修复根因。真实行为保护适用时参考 pstack:tdd；不用来源不明的 tdd，也不为低影响文字修改机械增加测试。新语义先走调查与设计。
4. 用同一入口、相同条件复验并核对相关消费者；跨边界影响按需用 blast-radius。功能修复不自动证明性能恢复，必要时补性能专项。
5. 报告机制证据、修复、保护、结果与仍未知部分。相称检查通过后沿[评审与交付](review-and-delivery.md)完成授权范围，不默认推送或合并。

## 完成及交付

给出可复跑的前后行为、支持根因的证据、修复范围与保护结果。只排除部分假设就称部分诊断；环境未运行则保留未知。一次复现和日志留 tmp，必要长期行为测试归实际成员。

## 停止与恢复

预期和现行承诺冲突时停依赖修复，交语义拥有者；缺环境时停运行结论但继续独立分析。补齐可复现输入或裁定后恢复，不静默改规格迎合实现。

## 示例与精确参考

定时器取消后仍触发回调：在实际公开入口复现，区分取消请求与实际停止，核对所有者并复验。只有源码猜测时不能声称泄漏已经解决。
