# 工作类型、证据与接受责任

协议已采用，日常入口未启用。[GitHub交付配置](github-delivery.json)保持`enabled:false`；未启用时按本协议形成任务草稿。每项任务按实际需要明确本次身份、结果和接受责任。平台、默认分支模板及实际宿主执行仍须独立验证，本页不授予发布或启用。

本页的工作分类不是平台原生类型。卡的共用身份、分解、状态、条件和决定归[交付协议](delivery.md)。本页拥有各工作类型的附加输入、证据及持续正文更新要求。

## 工作类型与分解

每卡在正文选一个主工作类型。交付层级delivery／subtask、责任范围、风险、优先级和迭代分别表达，不把“子任务”“高风险”或“P0”混入工作类型。标签从正文派生；标签与正文不一致须对账，不能选择方便的一方授予开始资格。

混合工作按主接受结果分类，明确附带变化及其额外要求。可以独立接受且不会割裂同一结果时再拆子任务；例如feature下的refactor子任务有自己的技术证据。不能用主类型免除bug的修复证据、性能数字的可信性或公开承诺变更的接受。新增工作类型先由工程协议拥有者明确准入、证据与接受责任，并同步模板和消费；不把无法分类写成无约束other。

## 首版类型

| 主类型 | 本次结果及必要输入 | 必要证据与结果接受 | 持续成果落位 |
| --- | --- | --- | --- |
| feature | 新增或改变用户／公开能力；明确用户或消费者结果、已接受规则／契约及范围 | 产品结果由产品负责人接受；公共技术能力由有权契约负责人接受。按承诺演示正常、失败及禁止结果 | 产品规则、公共规格、设计、指南和持续验证按实际变化更新 |
| bug | 恢复应有行为；给预期依据、实测现象、环境／输入及影响。缺少预期依据先裁定，不能从现状推定正确 | 有权承诺拥有者接受修复；提供复现或具体观测、修复后证据及相称回归保护。暂不能复现须列替代证据、限制和未判定范围 | 预期不变时不重写规则；保留持续验证和必要机制说明，不把事故流水写成长期规范 |
| refactor | 改善结构、边界或可维护性；说明现有问题、目标组织、保持的公开行为及消费者 | 技术／机制拥有者接受目标结构和相称行为验证。公开承诺改变须先取得相应语义接受，不能用refactor标签绕过 | 当前设计、依赖约束、消费者和验证随结构同步；不为了体现改动重复不变SPEC |
| performance | 改善明确的延迟、吞吐、资源或并发稳定性；绑定基线、工作负载、环境、测量范围和获准目标 | 技术／性能保证拥有者接受。比较可重复的前后结果、波动、错误及正确性，说明瓶颈与真实工作发生。无有效基线或目标未定仍是缺口 | 持续基准及条件就近维护；新的长期保证写回所属规格或要求，不在卡中形成第二规范 |
| maintenance | 维护依赖、工具、构建、文档、验证或运行配置；明确应有状态、受影响消费者及风险 | 对应工程／工具／文档／运维拥有者接受可核结果，执行受影响检查；迁移不冒称产品接受，安全风险按现行硬线处理 | 正确拥有者的当前规则、配置、指南和持续资源更新；原始输出不入正文 |
| investigation | 回答技术问题、定位不确定原因或比较方案；明确问题、假设、方法边界和约定成果 | 具名问题拥有者接受证据、结论、限制及剩余未知。假设被否定或结论不确定可以是有效结果，但不能据此声称能力实现或问题已修复 | 原始实验留tmp；有持续阅读价值的获准结论进入研究或设计源。新承诺继续走接受及必要RFC，不自动实施 |

类型表不是固定全量测试清单。方法按影响、风险及可执行输入选择；缺证据如实计量，不能一律绿灯，也不能为所有卡强制跑完整clean-loop的所有可选检查。任何适用的既有硬线保持。

## 卡与长期正文的关系

有产品语义的卡引用相应产品规则与持续场景。纯技术卡可只引用实际SPEC、架构约束、设计、工程规范或缺陷证据，不要求PF、用户故事句式或产品负责人逐卡接受。调查先绑定获准问题和适用上层约束，其候选假设明确标为未采用。

接受者不是工作类型自动生成的角色。建卡时指定主结果接受者及授权依据，另列受影响语义拥有者。产品变化归产品负责人，技术契约或架构变化归其有权者；这些采用决定在依赖阶段进入条件表，卡接受不能替代。可由同一人兼任，仍记录决定身份。跨责任卡在所有本次承诺及适用决定齐备后才接受。

当前0.0.0至0.1.0政策允许有正向收益的破坏性变化。重构或性能优化若改变公开承诺，须显式列出变更、取得接受、同批切换真实消费者并删除替代实现；不能声称“保持行为”，也不要求保留无意义兼容层。行为保持型重构沿现行承诺验证即可，不自动强制RFC。

调查可以先交付证据再触发后续bug／performance／feature卡。调查卡关闭不解锁“已修复”或“已提速”的结果条件。获得获准结论后，没有持续价值的过程材料仍可留tmp；若约定成果须跨cloud接续，明确最小成果定位及持久保存入口，不将全量日志上传Issue。

## 工程方法

pstack方法及精确采用版本继续由[技能入口](skills.md)拥有。feature、bug-fix、refactoring、perf-issue分别是poteto-mode的playbook，不伪称独立skill；性能数字按pstack:benchmark-checklist复核。maintenance按实际工作选文档、依赖或运维方法，investigation用how／why及调查流程，必要时做获准探路实验。

Matt 的 `to-spec` 组织已经明确的单次实施输入，`to-tickets` 按独立可验证结果切卡；它们不把所有工作变为产品故事、不另设长期规格源，也不授予tracker写入或接受权。产品规则起草才加载product-design，普通技术卡不用为了模板而重做产品设计。
