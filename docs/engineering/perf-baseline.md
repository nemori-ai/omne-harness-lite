# 性能基线：Journal 的写入量与长会话

本页记录 Agent Journal 每次提交的写入量，以及它与会话日志的比。它是测量读数和阈值，不是承诺。承诺在 [session-adapters 的 SPEC](../../packages/session/session-adapters/SPEC.md) 与 [session-storage-sql 的 SPEC](../../packages/session/session-storage-sql/SPEC.md)，不变式在 [session-and-run](../architecture/runtime/session-and-run.md)。读数只对表头写明的提交、负载和环境成立。

## 测量什么

每次存储提交，按参加者读出下列项目。

| 读数                           | 含义                                                                                                                        |
| ------------------------------ | --------------------------------------------------------------------------------------------------------------------------- |
| 字节数                         | 提交请求里每个 command 的 JSON 文本（UTF-8）字节数。参加者取 command 的 `participant`。                                     |
| `sl_state`                     | Session 参加者在事务里整行重写的快照。它不在请求里，所以每次提交后读这一行的大小。                                          |
| 页数                           | 这次提交写进 WAL 的帧数。一帧是一页，页长 4096 字节。                                                                       |
| fsync 次数                     | 带提交标记的 WAL 帧数。库以 `synchronous=FULL` 打开，每次事务提交同步一次 WAL。这是由配置推出的次数，不是操作系统层的计数。 |
| 每步提交次数                   | 一步（一次 Model 调用加它请求的那次 Tool 调用）里的存储提交次数。                                                           |
| 自有字节对 `sl_entry` 字节的比 | 全部 `execution-record` command 的字节和，除以 `sl_entry` 的字节和。                                                        |

一步以 Model 调用被受理为界。第 0 步是建会话与受理输入。最后一次受理（文本答复，不带 Tool）之后的提交记在收尾步。

不被存储接受的提交单列为「被拒」，不计入字节、页数和 fsync。

## 怎样跑

入口是 `apps/harness-server/tests/rows/storage/journal-bytes.spec.ts`。

```sh
cd apps/harness-server
OMNE_JOURNAL_BYTES=20-small-release,20-3k-relaxed \
  pnpm exec vitest run --mode slow --typecheck.enabled=false tests/rows/storage/journal-bytes.spec.ts
```

用例名是「步数-消息档-存储上限」。消息档 `small` 是脚本化小消息，`3k` 是 3 KiB 消息。存储上限 `release` 是发行配置的 1 MiB 单 command 上限，`relaxed` 放开这一上限。`OMNE_JOURNAL_BYTES=all` 跑全部。同一文件里的增长用例：20 步的每次慢层都跑；200 步的每次运行要几十分钟，默认跳过，设 `OMNE_JOURNAL_GROWTH_200=1` 时运行。改动触及 Journal 路径时运行它们。读数写到 `tmp/journal-bytes/`，库副本写到 `tmp/journal-facts/`。

测量设施的快层测试在 `journal-measure.spec.ts`。字节和 WAL 的读法在 `fixtures/journal-measure.ts`。

世界是 line-through 联合世界：真实的 session-adapters Journal 提供者、真实的 sqlite-provider、真实的 Agent 循环和接收方。Model 与 Tool 是脚本替身，不访问网络。

### 测量的局限

- 页号在运行结束后用 `dbstat` 对到表。运行中被回收再分配给别的表的页，按最终所有者记。
- 提交串行经过包装器。存储写者本来就是单写，所以可见次序不变，但提交之间的重叠时间不测。
- 世界里有些步有一次存储没有接受的提交（表中「被拒」列）。原因没有深查。它不写字节。
- 只测一次，没有重复。字节数由负载决定，重复间只差几百字节。时间不测。

### `sl_entry` 编码的影响

`sl_entry` 的载荷存为普通 JSON 后，`sl_entry` 的字节和比旧编码小 22% 到 26%。自有字节、Session command 字节、最大一次发布与 fsync 次数不变，页数的差在 0.5% 以内。比值因分母变小而变大（20 步，小消息从 9.5 变为 12.8），不表示 Journal 的写入量增加。

### 过渡桥删除之前的读数含义

- 最大一次发布不随步数增长：从第 1 步到第 49 步都约 42 KiB。只有收尾步的一次发布约 321 KiB。
- 每步约 460 KiB 自有字节（3 KiB 消息约 512 KiB），不随步数增长。累计自有字节因此是步数的线性函数，但斜率远大于守卫的 W。
- 每步约 38 次提交，其中 Journal 发布 32 次，fsync 38 次。终态设计的目标是每步 7 到 10 次提交。
- 每步约 1200 页。第 5 步的页主要落在 `er_fact`、`sl_blob`、`er_fact_execution` 与 `_sql_receipt`。
- `sl_state` 行约 2 KiB，不随步数增长。
- Session 自己的字节（`Session KiB`）每步约 30 KiB，不随步数增长。

## 长会话

本节量同一个会话聊很多轮之后，每轮的系统开销、内存和磁盘是不是随轮数增长。要求在[会话与 Run 的长会话一节](../architecture/runtime/session-and-run.md#h1-long-session)与上面的 Agent 事实族三条里；本节只放量法、读数与判法。读数只对表头写明的提交、负载和机器成立。

### 量什么

测量在发行组合上跑：发行分发配置、真实 SQLite 存储、发行的 Shell 工具、本机的脚本模型网关，服务、测量与脚本模型在同一个 Node 进程里。一个租户建一个会话，然后一轮接一轮发输入。一轮是一次用户输入：脚本模型先请求一次 Shell（打印一个 4 KiB 的文件，结果直接回给模型），再给出文字答复。所以一轮有两次模型调用、一次工具调用。

| 读数             | 定义                                                                                                                                                                                                                                                                                            |
| ---------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 每轮自身开销     | 从发出这一轮的输入，到读到这一轮的终态条目，墙钟毫秒数，减去脚本模型构造答复的毫秒数。真实 Shell 的执行时间算在里面，每轮相同。终态靠每 20 毫秒读一次最新的终态条目得知，所以终点是上界，偏差不随轮数增长。分段读数取服务的遥测段：按拥有者（`session`、`agent`）把这一轮里结束的段求区间并集。 |
| 日志累计自有字节 | 全部提交里参加者是 `execution-record` 的 command 的 JSON 文本 UTF-8 字节之和，与上面「测量什么」同一定义。含建会话与轮外的提交。                                                                                                                                                                |
| 进程内存         | 每轮结束时进程的常驻内存（`rss`）与已用堆（`heapUsed`）。每轮都采，用于判定；每 10 轮的值写进摘要。                                                                                                                                                                                             |
| 磁盘             | 每轮结束时数据目录全部文件的字节数；每 10 轮另记每个库文件（主文件加 WAL）的字节、每张表与索引的字节（`dbstat`）与行数，以及同一时刻可见历史的字节：`read-history` 回答的 `message.user`、`message.assistant` 条目的 JSON 字节。每轮新增磁盘 = 这一轮末的数据目录字节减上一轮末的。             |
| 每次工具调用     | 一轮恰好一次工具调用，所以按轮计：发给存储线程的提交消息数，并按参加者分开（一次提交含某参加者的命令就给它记一次）；读消息数（读往返），按处理模块分开；提交前查询消息数；每轮墙钟的中位数。                                                                                                    |
| 提交与读的走向   | 每轮的提交数与读往返数随轮数的变化：第 1、20、100、200 轮的值，以及下面的两道门。                                                                                                                                                                                                               |

计数在测量进程里取：在 `Worker.prototype.postMessage` 上数发给存储线程的每条消息，不改成员代码。一轮的计数从发出输入开始，到读到终态之后再静置 500 毫秒为止，终态之后的收尾工作仍算在这一轮。读终态的轮询本身也读存储：每 10 轮在静置之后专门轮询 20 次，量出每次轮询的读（现在是 4 次：`read-login-by-proof`、`read-standing`、`read-governance`、`read-history`），各轮按自己的轮询次数扣掉。

### 怎样跑

```sh
pnpm run build
node apps/harness-server/tests/long-session/run.ts --out <新目录> [--rounds 200]
node apps/harness-server/tests/long-session/judge.ts <运行目录>        # 重判一个运行目录
node apps/harness-server/tests/long-session/compare.ts <运行 a> <运行 b>  # 对照同一提交的两次运行
```

输出：`rounds.jsonl`（每轮一行）、每 10 轮的 `storage-<轮>.json`、`visible-<轮>.json` 与 `polling-<轮>.json`、`run.json`（机器、结局、轮外计数、遥测记录数）、`summary.json` 与 `summary.md`。运行完成就退出 0，门的结论只报告不拦；运行失败（某轮终态不是 `completed`、脚本模型报错、一轮超过 180 秒）退出 1。`--rounds 20` 是短版，每一程收口时跑它比改前改后。`--control growth` 是负控：每轮 Shell 多睡 2 毫秒，进程多留 1 MiB，数据目录多写一个比上一轮大 16 KiB 的文件。

完整的 200 轮不进准入，也不和准入或别的长测量同时跑。

### 一轮与步

上面 Journal 写入量的界按步算：一步是一次模型调用加它请求的那次工具调用，以模型调用被受理为界。长会话一轮有两次模型调用，所以一轮折合两步。日志累计自有字节的界是 J0 + W × 2 × 轮数，J0 与 W 不变（64 KiB 与 12 KiB）。

### 量法可信

- **负控判得出增长。** `--control growth` 的 200 轮（提交 `6e8df732d`）：自身开销窗口比值 4.50，判失败；常驻内存窗口比值 2.89、逐段增长 R² 0.97，判失败；每轮新增磁盘窗口比值 3.64、逐段增长 R² 1.00，判失败。三条序列都判成增长。自身开销的逐段增长门 R² 是 0.92，没有判失败，因为负控加上产品本身的增长不是一条直线；按 P1 的判法，两道门有一道失败就是判成增长。
- **同一提交两次运行的差在范围内。** 范围：每轮提交与提交前查询的中位数、日志累计自有字节相差不超过 2%；每轮读往返的中位数不超过 20%；自身开销的前窗与后窗中位数不超过 25%；第 200 轮常驻内存不超过 15%；第 200 轮数据目录不超过 5%；每条序列「判没判成增长」的结论相同（任一道门失败即判成增长）。对照脚本是 `compare.ts`，超范围退出 1。
- **范围修订过一次。** 第一对运行之前写的范围是：读往返 5%，并且每一道门的结论都相同。第一对（基线 1 对基线 2）在这两处超出：读往返中位数差 14.5%，自身开销的逐段增长门 R² 是 0.952 与 0.944，落在 0.95 两侧。读往返的差全在会话的四个订阅者读（`read-execution-batches`、`read-execution-session`、`read-model-selection`、`read-work-version`）与 `identity read-standing` 上：订阅者每次被叫醒读一遍工作状态，叫醒在忙的时候会合并，所以读的次数随机器负载变；这两次运行的负载中位数是 6.9 与 13.2。所以改成上面的范围。修订后的范围用没有参与定范围的基线 3 检验：基线 1 对 3、基线 2 对 3 都在范围内，`compare.ts` 退出 0。
- **测量自己的读与内存。** 读终态的轮询每次 4 次读，已按校准扣掉。测量进程只按轮写一行数据，遥测段每轮用完即丢，网关不留请求内容。

### 限制

- 只在 macOS 上量过，没有 Linux 读数。fsync 没有量：macOS 上没有 strace，e9 的 fsync 来源只认 strace、提供者观察或合成。
- 服务、测量与脚本模型在同一个进程里，进程内存含测量的少量开销。
- 读往返只数次数，不数每次读了多少行；读放大仍未覆盖。
- 内存占得最多的三处是按字符串内容推出的，没有沿保留路径核到成员。

## 没有覆盖的

- 过渡桥删除之后的完整分步表与每步页数。上面只记了 200 步的累计与每步范围。
- 真实 Model 与 Tool、真实编码轮的负载。脚本负载的比值不能推到真实负载。长会话一节用发行组合，但模型仍是脚本网关。
- 读放大（每次读读了多少行）。[长会话](#长会话)一节量了时间、内存与读往返的次数，Journal 写入量一节只测写入。
- Postgres。读数只对 SQLite 的 WAL 成立。
