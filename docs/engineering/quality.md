# 交付质量与证据

本页把工程目标连接到可审阅依据，供执行者、评审者和负责人选择相称验证。精确验收、工具算法和阈值继续由实际拥有者维护。本页不新增统一数值门槛或合并硬线。

## 目标与可观察依据

| 目标 | 本次交付应让读者检查什么 | 结论的限制 |
|---|---|---|
| 可信 | 精确输入、有效源、实际结果、覆盖与未知，声明能定位证据 | 绿测不能证明全局正确，加载记录不能证明全面遵循 |
| 可解释 | 目标、重要选择、适用条件、机制说明和剩余责任 | 需要可审阅理由，不要求模型内部思维或永久形成史 |
| 高质量 | 公开承诺、失败、生命周期、真实消费者与相称检查 | 文档数、测试数和抽象数量不能代替质量 |
| 高性能 | 工作负载、环境、基线、指标、重复测量及资源代价 | 无预算时不能虚构“高性能”阈值 |
| 保质保量 | 约定范围对应完成、部分完成、受阻、未完成与范围变化 | 代码行数、页数和勾选数不是有效交付量 |
| 稳定高效 | 复用适用资料、可复跑方法、必要验证和实际成本观察 | 速度不能代替必要验证，未测成本保持未知 |

这些目标来自工程文档的工作目的；具体交付内容和证据要求沿[贡献指南](../../CONTRIBUTING.md#形成可审阅的交付)、[验证说明](../verification.md#证据能支持什么)及研发品味适用。

## 按成果和风险验证

设计成果核对目标、责任、承诺、选择依据、条件、未决和可实施输入。出现新边界时用 [`harness-design-handbook`](../../.meta_harness/agents/skills/harness-design-handbook/canonical/SKILL.md)选择相应评审；表达、选择和计划的判断分别派发。设计完成不自动批准实施。

软件成果核对实际公开消费、行为、失败、资源、组合与相称验证。按本页[风险分级](#按风险选择接受实现的看法)选接受级别；普通局部修复不默认新增独立评审，L2／L3 或未交代红项才按规定展开。

文档与技能成果核对唯一源、正确触发、可用路径、来源、维护消费者与结果范围。链接、结构、宿主加载、实际遵循和行为结果分别验证。结构完整不能替代真实阅读或任务执行。

按实际成果、风险、影响面与真实输入选择验证，兼顾可靠可信和灵活高效。Autopilot 的每轮 swarm、Multi-phase plan 的固定 live lane 及性能检查是专用默认，不自动成为所有任务的完整清单。采用时列明必要证据、复用依据、跳过原因和未覆盖；有差异就称限定采用，不声称完整执行原 playbook。

这项选择保留适用的独立接受责任及现有硬线。冻结被验候选的实际修订与字节，输入变化后复跑受影响检查；旧修订通过不能支持新候选通过。必要资源缺失时保留无法验证，不把精简验证解释为降低保证或消除红项。

## 公开能力、策略与观测

重试、退避、超时、限流、节流、熔断和轮询间隔等横切策略须采用可配置的策略对象与可替换实现；默认值只是配置初值，不能成为永久政策。调度与时序优先复用成熟策略库，不自行编写已有适用机制的计时与退避。具体取值、失败和生效语义由策略拥有者明确，不在本页写第二份配置表。

工程检查里的通用逻辑也复用成熟工具。格式、正确性规则、依赖方向、无用依赖报告和任务缓存的采用范围见 [RFC-0002 revision 1](../rfcs/RFC-0002-engineering-toolchain.md#决定范围)。Cordis 服务关系和领域对象的检查继续由项目工具拥有。这一句不表示这些工具已经接入。包级测试由谁承担、停在哪里，见[包级测试责任与边界](../verification.md#包级测试责任与边界)。本页不复制那套分类。

按[独立使用与替换](../requirements.md#独立使用与替换sys-open)，调用模型、执行工具等核心能力提供可公开、独立的函数闭包，不依赖 runtime、Session、租户或存储即可单独使用。本项目 runtime 是一种消费者；能力明确区分公开函数接口与Cordis服务接口。提供服务接口不能取消独立函数的公开使用能力。仅在运行时层成立的不变量由运行时层承担，函数层不作此承诺。解析、装配、判定、投影、传输适配、执行者、转换件和重试件等内部构件同样可替换、可单独取用；实际资源条件与组合责任随能力契约核对。

观测属于运行行为，在真实边界让状态转换、失败与因果链可解释。生产、研发和debug共用结构化log与trace语义，通过配置调节细节。关联、内容裁剪和耐久记录按[项目观测要求](../requirements.md#全链路可观测可遥测与日志完备sys-observability)核对；工程观测不自动成为耐久审计。具体观测契约仍由相关拥有者细化，不能据日志存在扩大记录保证。

## 异步资源的验证责任

涉及异步资源时，按[防御指导](../defensive-patterns.md#dp-06-所有权必须可追踪)核对所有者、错误去向和清理路径，按[释放终态](../defensive-patterns.md#dp-04-释放以可观察终态为准)核对取消、重复结束、故障及在途工作。运行时校验不能由断言或类型检查替代，`readonly` 不证明深不可变。类型或静态规则通过也不证明资源已收场、租户隔离或所有权成立。

精确生命周期和实际装配继续读成员公开契约及[原 Cordis 技术源](../../.meta_harness/design/architecture/README.md)。成员验证范围、后端、进程边界和假设按[实际执行](../verification.md#环境与实际执行)分别报告；加载 TS 技能不能替代这些运行证据。

## 性能与成本证据

性能任务走[性能场景](scenarios/performance.md)，方法按条件参考 [pstack benchmark-checklist](skills.md#pstack-方法入口)。保留基线、运行条件、样本／重复、噪声和代价；基线不同或输入改变时单列口径变化。没有可比基线就报告增减不可用。

非性能任务只有影响性能承诺或观察到退化时才增加相关测量。上下文量、重复阅读、运行时间和验证成本可以观察；当前没有统一成本评分或发布预算。数值门槛需由相应目标拥有者明确，不从一次测量推成全局政策。

## 失败未知与完成范围

沿[六种验证状态](../verification.md#分别表述这六种状态)区分未运行、受阻、有限通过、失败等事实。环境缺失、后端跳过、方法不支持和范围未知不能算通过。发现反例时提供契约条款、精确输入和可复跑路径，而非静默改承诺。

现有带位、处置责任和硬线由[整洁回路](../clean-loop.md)拥有。当前文档计量只观察已登记结构；新增高风险阻断的方向已提出，具体规则未采用。未来完整语义偏离、技能遵循与体验计量仍需工具或独立判断，不能由 inspectable 推出。

交付从[共享完成声明](workflow.md#完成与交付声明)进入；低风险成果不必额外填大型表单。负责人结合实际验收、未覆盖和后续责任判断可接受范围。

## 集成候选证据

[分支集成](integration.md)把 targetBase 的影响检查与每卡 taskBase 的逐提交审计分别保存。组合检查须在实际合并结果上运行；旧耗时 ledger 和分支各自绿测不能替代它。现有四条硬线保留，不新增数值门槛。

## 区分四层就绪状态

| 层次 | 能支持的结论 | 不能由此推断 |
|---|---|---|
| 语义接受 | 有明确范围的要求/契约已被有权者接受 | 提供者已有全部实施输入，或必要证明已完成 |
| 提供者可实施 | 被依赖的机制选择、接口、资源/失败责任已明确 | 应用已正确装配 |
| 装配明确 | 实际提供者、配置、消费与跨能力交接可解释 | 真实组合已经运行通过 |
| 实际验证 | 特定版本/环境/范围取得了相应结果 | 未检查范围成立或模型检查等于无条件证明 |

这是报告维度，不是新增的登记状态或四轮审批。
每个缺口说明负责产物/拥有者、受影响消费者、所需决定或证据及闭合条件；
只暂停依赖它的实施，不把不影响公共契约的内部实现选择都当成缺失规格。
语义接受不能绕过具体机制所需的[证明门槛](../verification.md#组合性质与证明义务)。

## 按风险选择接受实现的看法

接受一份实现类交付之前，先定它属于哪一级。级别决定机器先过什么、人看什么；
派发时把级别写进任务，交回时按它备齐证据。

| 级 | 适用 | 机器先过 | 人看什么 | 不做什么 |
|---|---|---|---|---|
| L0 局部修复 | 沿已接受契约的局部修复，文档与工具的小改 | 受影响范围的测试与类型检查 | 交付说明与变更摘要 | 不派评审 |
| L1 常规增量 | 单个成员内的实现，单份契约的提供者 | L0，加结构度量摘要——变更函数里超阈值的逐条有交代 | 该成员在结构图上的边与着色，抽查两三个最热的函数 | 不逐行读 |
| L2 跨成员与装配 | 多个成员、装配节点、迁移 | L1，加待合并提交的影响面所需检查与真实组合的运行证据 | 依赖方向全图与运行证据 | 不得跳过受影响且必需的用例 |
| L3 安全与不变量 | 身份与租户隔离、凭据、内核原语、要求同一提交的状态 | L2，加已触发的形式任务实际运行与故障注入 | 逐行读热点，并安排独立评审 | 不因为绿灯免读 |

级别按改动触及的最高风险定，不按改动大小；拿不准就上调一级。执行仓库没有某项入口
（结构度量、形式任务）时如实写「无此入口」，不以别的证据顶替。绿灯与度量是抽查线索：
级别只规定最低限度的看法，不代替接受者的判断，也不改变接受权归谁。

检查范围归执行仓库。风险级别不把受影响的检查扩大为无条件全仓检查。
计划排除的步骤如实记未执行，不能写成通过。

交付配了可执行验收（本次真实拥有者维护的验收文件，放置约定见[角色定义](../../.meta_harness/agents/roles/README.md)）时，
任何级别都多核一件事：**验收自任务基线以来没有被实施提交改动**。执行仓库有验收锁入口就跑它并把输出留作证据；
没有就对着基线提交看那几个文件的差异。验收被实施者改过的交付不接受，无论改得有没有道理——有道理的改动由验收的主人来做。

**什么时候派独立的 agent 来看实现**（角色定义见[角色定义](../../.meta_harness/agents/roles/README.md)）：

| 级 | implementation-reviewer（读这次变更的代码与读数） | qa（在干净检出上按验收标准跑） |
|---|---|---|
| L0、L1 | 不派。例外：机器读数里有实施者**没有交代的红项**，可以派它只看那几处 | 不派 |
| L2 | 有未交代的红项，或接受者读完摘要仍说不清某处时派 | 有可运行的交付面、且有写得成「触发 → 可观察结果」的验收标准时派 |
| L3 | 派：它逐行读热点 | 派 |

实现评审的每条发现要么带工具输出、要么带具体反例，它不收品味意见；验收的判决不是接受。
两者的结论都是证据：L3 上人仍然逐行读热点，不因为派了评审就免读。每张卡都派一遍会把迭代拖长，
所以默认不派，按上表在风险高或读数说不清时才派。

## 三轮未收敛时升级结构诊断

按“同一交付对象 + 同一需求/接受基线”计算实质轮次：一份可识别 revision 经相应独立评审后，
仍留下或新出现会改变语义、能力/所有权边界、状态/失败/在途政策、证据义务、
provider/assembly 可实施性，或计划依赖/验收责任的阻断 finding，计一轮。
同一 revision 的 architecture/spec 并行评审合为一轮；diff 很小但改变授权门或终态等承诺，仍是实质变化。
针对阻断做过实质修订后，独立复评确认原阻断仍未闭合，也计一轮，不要求出现新的 finding。
子代理的一个闭包（一个写者、一份闭包规格）也是一个交付对象，它的接受基线是闭包规格加追加记录。
闭包合回卡分支之后，卡候选的评审另按卡计轮。
归规格的阻断不计入闭包轮：派发者先修规格，在追加记录里记一条，再继续计数。

只有未发生实质修订的重复核对、纯机械修改后的核对，或已经没有实质阻断的复查不计轮次。
“机械”服从语义影响判断：标为措辞、格式、链接、生成投影或同步的改动一旦改变承诺，仍按实质轮次计算。
不按改动行数计数，也不为凑轮次重复 review。每轮都固定 revision、阻断 finding、处置和验证，
使重复、转移和真正闭合的问题可以比较。

**修复方的能力也按轮次升级，而不是同一档位反复试。**前两轮修复用常规档位；
第二轮修完、复评仍有阻断，**先质疑 reviewer 的判定本身，再升级修复方**：对每条剩余阻断逐条问
它是否判得对、是否合理、是否当前阶段必须闭合——reviewer 也会误判，也会把不属于本阶段的完善当成阻断报出来；
站不住的 finding 记下处置理由，不计入「未收敛」。剩下站得住的，第三轮修复交给当前可用的
**最高能力档位**（更强的模型，或派发者亲自动手），作为**最后一次局部完善尝试**。
子代理闭包到达这一时点时，按起点档位选择接手或从基线重做，见 [`workflow.md` D6](workflow.md#d6-按策略选模型按起点档位升级)。从基线重做也计这一轮。
连续两轮同档位修不干净，可能是判定有误、能力不够或问题不在局部三者之一，按成本从低到高依次排除；
跳过第一步，会把 reviewer 的误判当成结构问题去解决。本页不绑定具体模型，档位由派发者按当时可用的选项定。

同一基线经过最多三轮实质迭代仍有阻断 finding 时，停止同形态的局部补丁与重审，
冻结当前 revision 及三轮记录，暂停接受和依赖该设计的实施；不依赖该缺口的工作可以继续。
从整体设计链诊断以下关系，而不是继续修表面症状：

- 需求与接受基线是否完整、彼此一致；
- 能力责任和语义 owner 是否唯一，跨 owner 的保证是否有明确拥有者；
- 动作链、失败与在途工作在哪里交接，是否存在无人拥有或循环依赖；
- 单一权威是否被 proposal、spec、provider 或 assembly 的副本分裂；
- spec、provider、assembly 的分层是否把政策放错层，消费者依赖和证据/评审边界是否闭合。

跨 owner、finding 互相牵制或根因不明时，若宿主支持，可委派独立、高能力、只读 advisor 提供结构诊断。
至少给它目标与接受基线、完整设计链和精确 revision、三轮 findings/deltas/验证、重复或转移的问题、
根因假设、不可变约束及明确问题。要求输出根因、影响范围、应保留内容、结构修复路径与所需证据；
advisor 不代写设计、不作接受决定、不修改需求，本页也不绑定具体模型或固定 advisor 角色。

只有根因、语义 owner、结构修复范围和受影响消费者已明确，需求基线保持不变或已由有权者更新，
并形成新的可识别快照且完成自检后，才恢复一次与变化相称的独立评审。
更换 reviewer、branch 或拆分 patch 不重置计数；真实的新接受基线或边界重构开启新链时，
须记录旧链如何收口以及开启新链的理由。
