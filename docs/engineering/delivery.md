# Issue、Projects与交付协议

协议已采用，日常入口以[GitHub交付配置](github-delivery.json)的实际发布状态为准。PanQiWei已授权启用，接入及首次采用记录归[工程启用任务](https://github.com/nemori-ai/omne-harness-lite/issues/195)；未发布或未获本任务授权时只形成获准草稿。每项任务按实际需要明确本次身份、结果和接受责任。平台、默认分支模板及实际宿主执行仍须独立验证，本页不授予发布或启用。

本页拥有 Issue、Project、条件、调度与交付决定的共同协议。协议不是 GitHub 原生保证；对话及操作顺序归[agent交付操作](agent-delivery.md)。

## 长期正文与一次交付

| 长期成果 | 唯一源与责任 | 与普通任务卡的关系 |
| --- | --- | --- |
| 产品设计 | `.meta_harness/design/product/<topic>/`拥有概念、规则、旅程与持续产品判据 | 卡引用具体条款与场景；不在卡中另立产品规则 |
| RFC | [技术提案](../rfcs/README.md)拥有正式审议的方案及精确决定范围 | 采用不表示已写回规范，也不表示本次交付接受 |
| 长期规格 | 实际接口或机制拥有者的 SPEC 拥有当前决定的完整必要行为 | 单次实施规格可以组织卡的实施输入，不替代长期规格 |
| 技术设计 | 实际系统、领域、能力组、成员或装配拥有者解释如何兑现规格与必要理由 | 卡交接到真正拥有者，不留下中央技术副本 |

普通任务卡在配置仓库的真实Issue维护本次结果、范围、条件与当前摘要，一个结果有一个编辑源，Project提供派生调度视图。六种工作类型共用信息和流转协议。任务不要求PF或产品场景，产品能力支持状态继续归产品正文。

正式卡使用[独立交付模板](../../.github/ISSUE_TEMPLATE/work-item.md)或[子任务模板](../../.github/ISSUE_TEMPLATE/task.md)。卡的决定记录保留在真实 Issue；RFC 按专门规则保留方案与最小决定。逐轮讨论、派发、评审和原始运行输出仍放任务 `tmp`。卡接受后，当前产品规则、规格、设计与持续验证继续可直接阅读；过去的卡不能替代当前能力证据。

两种模板按相同的七个模块组织信息。成卡保留顶部“接手本卡”提示。历史卡仍可按原有完整布局读取，修订布局时整套迁移，不混放新旧章节。

| 模块 | 集中维护的事实 |
| --- | --- |
| 身份与责任 | 层级、类型、交付修订、创建标识、范围拥有者、接受者、调度者和正文单写者；子卡另列真实父卡 |
| 目标与范围 | 当前问题、本次结果、包含、不含及工作类型所需事实 |
| 依据与实施输入 | 唯一源、精确修订、采用范围、消费者、约束及持续成果落点；验收按输入ID引用 |
| 验收与测试 | 结果判据、验证拥有者、测试类型、覆盖、不覆盖、真实依赖或替身及环境要求 |
| 交付条件 | 按阶段阻塞的前置事实；无前置时本节正文仅写“无” |
| 当前执行与交接 | 认卡、派发、当前attempt、Git绑定、context读回、当前进展及实际成果证据 |
| 决定与剩余责任 | 具名决定定位、精确修订和范围、剩余责任、关闭及Project对账 |

任务背景由目标、输入、验收和条件给出。已有依据足够时直接引用，不强制另建task-context文档。工具生成的task context归执行区，不能代替这些实施输入。模板的章节和字段只提供观察结构，不证明输入充分或结果已接受。

## 1. 平台能力与职责

| 对象／能力 | 原生支持 | 本项目需承担的部分 |
| --- | --- | --- |
| Issue及sub-issues | 独立卡、评论、人员指派和任务分解 | 工作类型、交付／子任务责任、精确范围和接受资格 |
| Issue dependencies | blocked by／blocking | 阶段前置、取消不解锁、接受证据和语义完整性 |
| Projects | 多视图、字段、迭代、工作流 | 单一主Project、合法状态变化、就绪复核 |
| API／CLI | 查询、修改及关系接口 | 凭证、分页、超时对账、并发单写和未知处理 |

事实依据：[Projects](https://docs.github.com/en/issues/planning-and-tracking-with-projects/learning-about-projects/about-projects)、[依赖](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/creating-issue-dependencies)、[子项](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/adding-sub-issues)。这些平台对象不提供本项目的产品接受或执行独占保证。

首版一个主Project，仓库Issue作为正式卡源，不依赖组织特有Issue type。正文明确工作类型和交付层级，分类标签只是派生筛选；主Project不另维护可独立修改的第二个工作类型。标签不能授予ready、规范或接受权。Issue assignee表示负责的人，执行attempt标识区分其名下的agent实例。

主Project使用的字段、各自的唯一源与写者见[字段总表](#字段总表)。阶段由指定调度者维护；阻塞从条件观察，不作为抹去真实进展的独立Stage。首版不强制自动化：人工调度按同一协议复核，之后加只读检查及获准投影；不是从第一天开发新调度服务。

## 2. 卡片与阶段

交付卡是一次独立可接受的结果，可以服务用户，也可以恢复契约、改善结构或性能、维护工程基础、回答调查问题。工作类型及相应输入、验证和写回规则由[work-types](work-types.md)定义。所有工作类型均可没有PF或产品场景，按本次实际结果建立任务。

工作类型和分解关系独立。卡在正文选择一个主工作类型；交付层级为delivery或subtask。Task只是从父交付卡分解的子任务，不是与feature、bug或performance并列的工作类型。子任务须链接真实父卡、限定自有结果和接受者，工作类型可按自己的结果选择。独立技术结果直接建delivery，不以无父Task兜底。父子关系不自动产生阻塞，全部子任务接受也不自动接受父卡。

用户结果引用实际适用的长期产品依据；各topic的语义变化分别取得其负责人接受。非产品结果由具名技术／机制／工程接受者判断。调查卡接受的是约定的证据或结论，不是被调查能力已交付。

Epic是后续可选聚合能力，首版不创建正式Epic或对它运行本页Stage／接受操作。首次启用前须另明确聚合目标、结束／取消责任、状态和子项结算；不能复用Accepted或子项关闭率证明目标兑现。

| Stage | 意义与退出条件 |
| --- | --- |
| Backlog | 还在切片或缺输入；不能因排进迭代就派发 |
| Ready | 本次范围、接受者及开始条件已核；开始前再读回，不是永久许可 |
| In progress | 当前attempt已获授权，独立工作可推进；可能仍等待集成条件 |
| In review | 候选与相称证据已形成，等待适用技术核验；不是每个任务强制独立全审 |
| Integrating | 候选已通过准入，正在经 gate 进入目标轨道。gate 成功后进入 Awaiting acceptance 或接受流程；gate 失败退回 In review |
| Awaiting acceptance | 适用证据和条件齐备，等待具名接受者判断 |
| Accepted | 对精确交付修订与范围作了有效接受，关闭并退出活动 |
| Cancelled | 有权者明确不再交付，记录残余影响及后继处置，关闭但不记接受 |

Issue正文拥有交付范围、所核依据、条件及当前执行摘要；接受／取消事实由具名决定记录拥有。Project只拥有调度Stage等字段，Closed只说明平台状态。若三者不一致，报告并由调度者对账，不依据最便利的一项解锁。

启用该协议的主Project须禁用Issue／PR关闭→Done、PR合并→Done和Stage→自动关闭；仓库禁用关联PR合并自动关闭，PR正文用普通引用。官方说明默认自动化：[Project工作流](https://docs.github.com/en/issues/planning-and-tracking-with-projects/automating-your-project/using-the-built-in-automations)、[仓库自动关闭](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/managing-repository-settings/managing-auto-closing-issues)。技术接受可以根据合并后的真实证据作出，但平台事件不代替决定。

### 卡属性与合法组合

本节先列主Project的字段与视图，再规定交付卡的三个属性及其合法组合。

#### 字段总表

下表列出主Project的调度字段。字段 ID 与选项 ID 只登记在[交付配置](github-delivery.json)。配置的 `iteration` 键登记 Wave 字段，它在 Project 中是迭代类型的字段。dev-flow 的写入命令见[交付观察说明](../../tools/dev-flow/src/delivery/README.md#看板字段写入)。标题、负责人、父卡与子项进度是 GitHub 从 Issue 直接显示的内容，不在表中。

| 字段 | 含义 | 唯一源 | 谁写 | 何时写 | 用在哪些视图 |
| --- | --- | --- | --- | --- | --- |
| Status | 卡的调度阶段，取 [§2](#2-卡片与阶段) 表中的值，含 Integrating | Project 字段本身。任务事实仍归 Issue 正文，接受与取消归决定记录 | 按事件写，见本表下方的列表 | 阶段变化时 | 各里程碑看板与当前波的列、Active work 与周期的过滤、Awaiting acceptance |
| Line | 卡的交付线 | 正文「交付线」。`line:` 标签与本字段都是投影。派发后取 binding 的 `line` | `start` 新建 context 后写入。失败时调度者用 `board-cli.ts dispatched` 补写 | 开工时 | 各里程碑看板与当前波的泳道、Active work 的排序、周期 |
| Kind | 卡的主工作类型 | 正文「主工作类型」。写入前核对唯一的 `kind:` 标签与正文一致 | 同 Line | 开工时 | 按 kind 分组 |
| Wave | 卡所属的波 | 调度者在 Project 中为本波建的迭代，起止日覆盖本波的派发时间。`start` 取包含开工日的那个迭代 | 同 Line | 卡第一次开工时。卡已有 Wave 时不覆盖，同一张卡的新 attempt 不改 Wave | 当前波、路线图 |
| Needs decision | `yes` 表示卡在等人拍板，`no` 或空表示不等 | Project 字段本身。要裁定的问题和决定写在卡的评论中 | 本卡调度者。工具不写 | 发现需要人裁定时置 `yes`，包括破坏性契约改动的申请。决定读回后置 `no` | 待裁 |
| Priority | 排序与建议，不是依赖 | Project 字段本身 | 本卡调度者 | 排期时 | Active work、Awaiting acceptance |
| Milestone | 卡所属的里程碑 | Issue 的 milestone 字段 | 调度者。建里程碑与流转用 `milestone-cli.ts` | 建卡时设置。改里程碑用 `carry` | 各里程碑看板的过滤、Active work 与顶层交付卡的分组、路线图、周期 |
| Dispatched at | 卡第一次开工的日期 | dev-flow 写入的日期。已有值时不覆盖 | 同 Line | 开工时 | 周期 |
| Delivered at | 执行者交回候选 PR 的日期 | dev-flow 写入的日期 | 调度者运行 `board-cli.ts delivered` | 交回候选时 | 现有视图不显示 |
| Accepted at | 接受决定读回的日期 | dev-flow 写入的日期 | 调度者运行 `board-cli.ts accepted` | 接受决定读回后 | 周期 |
| Cycle days | Accepted at 与 Dispatched at 相差的天数 | 由两个日期算出 | 同 Accepted at | 同 Accepted at | 周期 |

Status 按事件由下列角色写入，操作顺序见[推进和更新状态](agent-delivery.md#4-推进和更新状态)：

- Backlog、Ready、In progress、Cancelled：本卡调度者在 Project 中设置。云端会话用 `delivery-stage`。
- In review：调度者在执行者交回候选 PR 时运行 `board-cli.ts delivered`。
- Integrating：运行合入的人在派发 gate 时运行 `board-cli.ts integrating`。一波并行的卡由集成节点运行。
- Awaiting acceptance：调度者在 gate 成功、等待具名接受者判断时在 Project 中设置。直接进入接受流程时可跳过。
- Accepted：调度者在接受决定读回后运行 `board-cli.ts accepted`。

标签是正文的投影，不是第二个源。下表列出调度用的标签族：

| 标签族 | 含义 | 唯一源 | 谁写 | 何时写 | 用在哪里 |
| --- | --- | --- | --- | --- | --- |
| `kind:<主工作类型>` | 卡的主工作类型 | 正文「主工作类型」 | 调度者 | 建卡时；主工作类型改变时同步 | Kind 字段的来源。`start` 要求恰有一个 |
| `level:delivery`、`level:subtask` | 交付层级 | 正文「交付层级」 | 调度者 | 建卡时 | 顶层交付卡视图的过滤 |
| `line:<交付线>` | 交付线 | 正文「交付线」 | 调度者运行[标签同步命令](../../tools/dev-flow/src/delivery/README.md#标签同步) | 建卡后；交付线改变时 | `start` 要求恰有一个 |
| `nature:<性质>` | 性质 | 正文「性质」 | 同 `line:` | 建卡后；性质改变时 | 属性发现核对 |
| `contract:<契约变更>` | 契约变更为 `additive` 或 `breaking`；为 `none` 时不打 | 正文「契约变更」 | 同 `line:` | 建卡后；契约变更改变时 | 属性发现核对 |

建卡时，卡必须有唯一的 `kind:` 标签、唯一的 `line:` 标签与里程碑，`start` 缺任一项时拒绝开工。调度者在派发一波之前，在 Wave 字段中为本波建好迭代，起止日覆盖本波的派发时间。

#### 卡属性

交付卡在「身份与责任」中登记交付线、性质与契约变更三个属性。调度者在 Issue 的 milestone 字段设置卡所属的里程碑。属性与主工作类型、交付层级相互独立。交付线的划分与路线规则归[多层分支集成](integration.md#交付线)，里程碑、契约基线与可加改动归[多层分支集成的同名一节](integration.md#里程碑与契约基线)。

- 交付线：[线归属表](delivery-lines.json)中的线 ID，或 `integration`。`integration` 表示卡归联调轨道，用于系统级或跨线的工作。
- 性质，取下列之一：
  - `design`：只改设计与规格正文。
  - `contract`：改契约成员的公开面、一致性套件或替身。
  - `impl`：在既有契约下实现。
  - `integration`：跨线的真实装配、集成点、联合验收或破坏性契约改动。
  - `baseline`：登记里程碑的契约基线。
- 契约变更，取下列之一：
  - `none`：不改契约成员的公开面。
  - `additive`：对契约成员只做可加改动。
  - `breaking`：对契约成员做破坏性改动。

交付线的取值 `integration` 与性质的取值 `integration` 属于两个字段：前者表示卡归联调轨道，后者表示跨线集成工作。交付线不是 `integration` 的卡称为线内的卡。卡的契约变更是整张卡的级别；PR 的「契约变化」逐个契约成员列出，其中最高的一级不超过卡的契约变更。

下表规定合法组合：

| 性质 | 交付线 | 写范围 | 交付条件可引用 | 契约变更 |
| --- | --- | --- | --- | --- |
| `design` | 任意 | 线内的卡：本线拥有的路径中的正文；交付线为 `integration` 时：任意路径中的正文 | 线内的卡：本线与交付线为 `integration` 的卡；交付线为 `integration` 时：任意卡 | `none` |
| `contract` | 线内 | 本线的契约成员 | 本线与交付线为 `integration` 的卡 | `none`、`additive` |
| `impl` | 线内 | 本线拥有的路径 | 本线与交付线为 `integration` 的卡 | `none`、`additive` |
| `integration` | `integration` | 任意路径 | 任意卡 | 任意 |
| `baseline` | `integration` | 不写仓库，在卡上登记基线 | 无 | `none` |

表外另有三条规则：

1. 任何卡都可以写线归属表 `shared` 列出的共享路径，只写由本卡其他改动生成或登记的变化，例如锁文件与文档登记。
2. 线内的卡依赖其他线的契约时，不引用其他线的卡，而写一条 `capability` 条件，目标是本线的目标轨道上可读到的那个契约形状。
3. 交付线为 `integration` 的卡写入线内的路径时，route 用 `cross-track`，具名联调轨道与线归属表登记的受影响线的 owner；只写联调轨道拥有的路径时，route 用 `track`。

属性属于交付范围。卡首次登记属性时不升交付修订；登记后改变交付线、性质或契约变更时升交付修订。调度者改里程碑时不升交付修订。属性派生的标签与 Project 字段只作投影，规则见[建卡或修订卡](agent-delivery.md#2-建卡或修订卡)。

Project 字段的唯一源与写者见[字段总表](#字段总表)。

#### 契约变更与里程碑类型

里程碑的契约基线、可加改动的判断，以及破坏性改动的允许时机，归[多层分支集成](integration.md#里程碑与契约基线)。卡属性上的规则如下：

1. 线内的卡的契约变更只取 `none` 或 `additive`，见上面的合法组合表。
2. 线内的卡在开发中发现必须对契约成员做破坏性改动时，执行者停止依赖这项改动的工作，在交接报告中写明改动与受影响的契约成员。调度者把卡的 Needs decision 置为 `yes`，在卡的评论中写明要裁定的问题，由人拍板。
3. 人同意后，破坏性改动由性质为 `integration` 的卡完成，见[里程碑内的规则](integration.md#里程碑内的规则)。裁定同意后，原线内卡只按兼容形状继续开发，仍不申报 `breaking`；破坏性切换由承接的 `integration` 卡按里程碑规则完成。决定读回后，调度者把 Needs decision 置为 `no`。
4. 负责人建 Milestone 时，在描述中写明里程碑类型：普通或重构型。Milestone 描述是里程碑类型的唯一源。

调度者用 `milestone-cli.ts carry` 改卡的里程碑时，binding 中派发时的里程碑不变，属性发现随后报告 `attribute-binding-drift`。处置如下：

1. carry 在卡上发的流转评论说明原因。
2. 正文单写者在这张卡的下一次 revision 中，把 binding 的 `milestone` 改为当前里程碑。漂移随之消失。

## 3. 条件、关系与解锁

Issue条件表是依赖语义唯一源，每项有稳定条件ID、类型、目标、阻塞阶段、所需结果／满足判据、确认责任与证据入口。排序是Priority或建议，不是硬依赖；父子仅分解。阻塞阶段为start、integration、acceptance。各阶段启动前读取自己的条件；进行中的卡可被integration阻塞而继续不依赖它的部分。

条件类型采用有限集合：issue-result（明确前置结果）、adopted-source（现行规范已接受及切换）、decision（具名产品／架构决定）、capability（真实可用及已验证能力）。表格的结构、解析版本及接口归[实际工具拥有者](../../tools/repo-toolchain/README.md)；无法机械判断的条件由具名确认者核，不能让agent猜自然语言通过。

整项Issue结果是整个开始阶段的前置时，可将该行投影为原生blocked by；只阻塞集成／接受或外部决定的条件不作全卡阻塞投影。原生边是条件表派生，不单独授权维护。首版集成写者人工核对投影；以后自动化仍需获准。未解释的原生边、漏边或悬空目标报告冲突，不能静默删边或让Ready覆盖它。

全部硬条件禁止自指，不得形成无法解除的循环等待。调度者在新增／修改条件、派发及阶段推进前检查完整相关链，包括未投影原生边的integration和acceptance条件；不把排序或父子混入硬依赖。按卡及所需阶段／结果分析：正常从start到integration再到acceptance是流程顺序，不是非法自依赖；A的integration等B接受而B的acceptance等A接受形成必须解除的循环等待。外部决定或capability若依赖其他交付结果，须提供其相关前置定位；不能取齐链或无法判定是否成环时报告unknown，不承诺全图无环。

确认自依赖或循环时，调度者列出涉及条件、阶段和完整等待链，暂停依赖该链的阶段，独立工作继续；交相应卡／条件拥有者重切结果、明确替代证据或调整获接受的条件，卡交付revision同步。调度者核对新依据及剩余相关链后才恢复，不静默删边、不用Priority改变解锁。检查器未实现时人工仍按同一规则走查；有工具后由工具观察、拥有者裁定。

原生关系页面没有充分定义取消、关闭和重开的全部解锁语义，因此不依赖平台Blocked展示决定资格。issue-result须核指定交付修订与所需结果的有效接受／技术完成证据及当前撤销情况；closed或not-planned不够。adopted-source须核当前规范，RFC仅accepted未写回不够。capability核其实际证据和适用条件，不要求一定等父任务的产品接受；判据由条件拥有者明确。

例如日程提醒的保存契约已确定，可先实施；真实组合验收仍等保存能力证据。权限RFC接受但契约未写回时，涉及新承诺的实施仍不能开始。前置被取消后，依赖者须保留未满足条件、重切范围或接受明确替代，不能仅移除原生边。

接受后卡仍可作为结果证据定位，但当前能力依赖逐步接续到现行契约、实现和持续验证。前置卡或依据变化时复核尚活动的后继；同一个过去事件不证明能力永远可用。长久已经接受的成果按实际影响复核，不机械撤销全部历史。

## 4. 接受、取消与重开

采用本节的决定记录格式。记录kind、卡交付revision、范围、决定者与权限依据、日期、所核长期源／实际成果／证据、未包含及剩余责任。决定必须来自有权者，或有可核对授权输入的代笔；机器人留言、任意评论、权限可写和绿测都不授予接受。接受内容有歧义或无法核对归属时保持unknown。

决定评论采用以下字段。填写提示按实际替换；字段存在或评论写入成功不能授予决定权。

```text
- 操作标识：{{本次决定唯一标识，超时用于读回对账，不声称平台exactly-once}}
- 决定：{{accept／cancel／revoke；部分认可用partial，不能让卡进入Accepted}}
- 对象与交付修订：{{IssueURL及revision}}
- 决定者、身份及权限依据：{{该交付结果的有权接受者；涉及产品／架构／契约变义列相应已有决定；代笔附有权者明确输入}}
- 日期：{{实际日期}}
- 范围：{{精确接受、取消或撤销结果；完整接受不能遗漏本次承诺}}
- 所核依据：{{适用产品场景、技术／工程规范、问题或调查授权及其修订、Git输入}}
- 成果与证据：{{实际远端提交／PR、方法、条件及结果范围；未执行不冒通过}}
- 不含与剩余责任：{{具名缺口及下一责任}}
- 前项关系：{{此前决定URL、取代／撤销精确范围，或无}}
```

卡由具名结果接受者判断所有本次承诺结果。产品结果必须由产品负责人接受；技术结果由有权技术／工程接受者判断，任务标签不能赋予权限。跨产品与技术责任时，各受影响语义拥有者先接受自己的变化；卡须明确相应决定与本次结果的主接受责任，不能由主接受者替其他拥有者批准变义。部分认可只记录认可范围，卡不进入Accepted、不关闭为完成；剩余结果继续活动，或由拥有者明确拆卡／缩小范围并接受新的交付修订。不能以记录accepted但少几项隐式销卡。

接受记录先写入并读回，再关闭并修复Project视图；它们没有跨对象事务。关闭或视图更新失败不撤销真实接受、不补造第二次决定；读回后修复。若未取得有效决定却已关闭，调度者纠正为活动并保留误操作说明。取消由有权的卡负责人明确作出，记录后继影响，不满足其他卡的结果条件。

接受后不重写旧决定。发现原范围其实未兑现或接受依据被撤销，由有权者记录精确撤销范围及新交付revision，再重开同一Issue；新需求或回归通常另开Issue引用原结果。只有有权者的新记录能撤销原接受；普通重开仅触发冲突复核，不自动改变全部历史。下游活动条件根据精确范围重新判断。交付revision语义变化由卡拥有者递增，样式和无关评论不升；新决定指明此前决定的链接与取代／撤销范围，当前有效事实须从相关决定及撤销链读取，链不完整就是unknown。

卡历史只说明过去交付与决定。当前产品规则、现行规格、设计及持续验收仍直接可读。GitHub评论可编辑，协议不能防管理员篡改；发布验证要检查历史指向和内容冲突，不能声称不可篡改审计。

## 5. 调度、认领与cloud接续

调度者由 `publish` environment 的 reviewer 担任，与派发校验和 PR 确认使用同一份名单。每张卡只有一个调度写者发放执行权，在卡的“调度者”一栏写明；多个调度者可以各管不同的卡，多个 agent 执行独立交付或独立子任务，但不能有两个调度者竞争同一卡。人类assignee、Project拖动和API“读空→写入→读回”不构成原子锁；首版不承诺无人值守跨调度者独占。

调度者读回当前依据与条件，核对现存执行，写入唯一当前attempt摘要并确认成功，才派发。摘要含attempt、人的责任、独立分支、授权范围、输入修订和最后成功保存的Git提交。同一Issue整个正文只有一个集成写者，默认由调度写者兼任；卡owner授权范围／修订／条件变化后交该写者集成，worker只提供候选及交接建议。不能因各写不同小节就并发整段更新正文。决定者可独立发表决定评论，正文集成写者核对评论与精确修订，不替决定者授予接受。worker在自己的分支产出并提交交接建议，不争写共享摘要。切换调度者先交接、确认前任不再发放；无法确认则停止新派发，不用更新时间当租约。

恢复先核远端Git、当前attempt及存活执行者，核对输入再推进。失联不等于停止。无法确认旧执行者时可在新独立分支探索候选，但不得重复共享写入或外部副作用，也不得自行集成。集成拥有者核对当前attempt、精确候选和输入再接受；过时attempt只能提供候选。多调度者的原子认领、过期执行隔离及外部副作用去重属于另一次设计，不伪称GitHub提供。

按[交付保存约定](publication.md)在相称节点保存正式成果到获准远端，Issue仅保留简短交接：远端提交、已核范围、下一步和缺口。没有推送成功只能声明本地保存，不能承诺cloud回收后可恢复。Issue评论成功与Git成功保存分别读回，原始日志和tmp不因此上传或整目录提交。

## 6. 访问、失败与最小工具

Project权限不赋予私有仓库权限，参与者必须能合法读取必要产品源；公开Issue不能泄漏私有正文、标题或敏感路径。安全定位仍由拥有者确认；未获资格时使用获准的来源投影或保留阻塞，不复制第二套业务规则。[访问边界](https://docs.github.com/en/issues/planning-and-tracking-with-projects/managing-your-project/managing-access-to-your-projects)

读取接口完整分页每层关系，记录仓库、Project、时点、输入协议、缺失权限和完整性。GitHub跨对象无已证全局快照；条件复核绑定实际读取修订，派发和接受前重读关键输入，发现变化重判，不能承诺原子多源一致性。外部受控变化通过单写交接，不能阻止所有第三方修改。

首版观察工具的目标能力包括读取、校验、依赖观察、待复核及存量／差量输出；不自动发布、认领或接受。将来获准的写入命令与只读检查分开，必须明确目标及授权；agent可按已获准范围使用实际宿主工具操作，不以本项目检查器未实现为由冒称全自动支持。机读形状、接入配置和解析器由[实际工具拥有者](../../tools/repo-toolchain/README.md)维护，不预造产品包或默认后台agent服务。

分页不全、权限不足、来源失效、格式无法解析、限流或平台故障分别unknown／input-error，不能当空队列或全ready。只读观察不增门禁。平台不可用停止新认领、状态切换和接受写入；已获授权的隔离任务可沿已核依据继续不依赖变化的部分。输出标过期，缓存不允许编辑并回灌。远端也不可用时如实声明保存局限。

每次拟建卡在请求发出前，由发布单写者分配稳定创建操作标识，连同目标仓库及本次获准发布输入的定位，保留在一个已知且跨会话可读的委派／交付交接Issue评论中。只记录最小请求定位，不复制整卡形成第二队列。接入配置登记该交接入口，未具备此入口或未读回请求记录时暂停自动创建；首次接入由负责人手动自举并记录已知入口，不声称尚无入口时可自动恢复。请求载荷将同一标识写入新交付卡／子任务正文的“创建操作标识”，标识不随卡revision变化、不复用。跨会话先取回请求定位，不能依赖丢失的本地tmp。

创建超时后，发布者完整读取目标仓库的可见Issue，按正文标识精确匹配：一个匹配核对仓库、内容及发布输入，取得真实Issue身份并接续；零匹配不是立即证明失败，先核请求结果及完整性，只有确定未创建才用原标识补写，无法确认保持unknown；多个匹配停止补写并交发布负责人裁定唯一源，处理副本的关系与消费者后再继续。查询不完整或权限不足保持unknown，不凭标题匹配、不盲重试。请求定位遗失也不新发标识重建相同卡，先由负责人调查重复风险。完成请求可关闭其交接待办，但不删除真实卡的创建标识。

写超时先按操作标识读回对账再补写；单写者串行发起创建和决定操作，不把clientMutationId当服务端幂等。未能确认一次创建／决定的结果前不盲重试，查询不完整时保留未知；可能重复须对账，不承诺exactly-once。[REST最佳实践](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api)

Project保留活动与近期项，达到容量前移出已结束项，Issue历史独立保留。归档不等于无限容量。具体套餐、当前CLI、App/PAT权限、Actions接入及原生关闭展示在启用前实测。其他平台政策限制继续由工程维护者处理，不凭网页接口存在假称目标可运行。

## 多层集成的交接

[多层分支规则](integration.md)维护技术运输。Issue 当前 revision/attempt 仍唯一拥有任务、路线和本次集成终点，正文单写者维护工具可读 binding；精确格式由[工具指南](../../tools/dev-flow/src/integration/README.md)拥有。binding 的格式含属性字段时，正文单写者在派发时把交付线、性质、契约变更与当时的里程碑写进 binding。binding 中的里程碑只记录派发时的值，与 Issue 不一致时只作报告。binding 格式不含这些字段时，属性只登记在正文与 milestone 中。已派发的 attempt 在交付前不改 binding 格式；同一张卡的新 attempt 在格式含属性字段时使用它。任务同步不能改变原 taskBase 或虚构新 attempt。

原交付条件表可增加“适用目标”列；未声明为 all。integration 条件按本次实际 track/main/stable 或登记完整 ref 核对，start/acceptance 保持 all。最终包含结果的条件放 acceptance。现有阶段环观察未完整覆盖目标层细化，未知不得说成全图无环。

完成 track 后已接受的结果仍可能被后续完整 RI 携带。有权 owner 对每个历史 identity/revision/attempt 与当前输入分别重核，历史 tuple 和 taskBase 不被新修订覆盖。当前 attempt 仍唯一，不因历史集合变成多执行队列。

Project 可由原投影单写者维护可选 Integration target/progress，取自 Issue 声明和实际 Git unit/checkpoint。没有真实字段配置时不造 ID；视图不另增 Stage 或可编辑调度队列，Stage 只取 [§2](#2-卡片与阶段) 表中的值。declared/observed 不一致或不足为 inconsistent/unknown，不能升级为 Accepted 或 Closes。Git 已发布而 Issue 投影失败时，由原正文单写者修复技术记录，不重放 Git。dev-flow 对平台的写入范围见[多层分支规则](integration.md#issue-与-project-的配合)。

## Map-Reduce 交接与整波放行

常驻 Line 与唯一 reduce 的责任、两个协调边界、三问、等待监督及接受顺序归[集成清单](integration.md#集成节点的清单)，完整状态和恢复归[负责人状态](map-reduce-states.md)。本协议的具名接受权限保持；Project、单卡接受、PR 合入或 Issue closed 均不能单独放行下一波。

整波放行前，非终态必须读回下一波任务与收口卡，并为包括 idle 在内的全部存续线发布 delta；有权终态必须读回终态决定并为每条存续线发布 terminal delta，不建虚构后继。随后本波收口卡按自身交付条件接受并读回，然后关闭。关闭是放行动作。只观察到 closed 事件不等于放行。blocked 或 failed 的交回由 reduce 发 redo delta 或接管，发布 delta 不等于问题已解决。只有显式终态结束 Line；轮空逐收口续接。
