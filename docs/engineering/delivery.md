# 卡与交接信息包

本页拥有卡、交接信息包、卡属性、提交成果与接受的规则。研发流程的环节与做法归 pqw 各技能，入口是 `single-session-dev-flow`。发卡、开工、开 PR、请求 gate 确认与接受的命令归 [`omne-card`](../../.meta_harness/agents/skills/omne-card/canonical/SKILL.md)。轨道、gate 与准入归[轨道与 gate](integration.md)。

## 长期正文与一次交付

| 长期成果 | 唯一源与责任 | 与普通任务卡的关系 |
| --- | --- | --- |
| 产品设计 | `.meta_harness/design/product/<topic>/`拥有概念、规则、旅程与持续产品判据 | 卡引用具体条款与场景；不在卡中另立产品规则 |
| RFC | [技术提案](../rfcs/README.md)拥有正式审议的方案及精确决定范围 | 采用不表示已写回规范，也不表示本次交付接受 |
| 长期规格 | 实际接口或机制拥有者的 SPEC 拥有当前决定的完整必要行为 | 单次实施规格可以组织卡的实施输入，不替代长期规格 |
| 技术设计 | 实际系统、领域、能力组、成员或装配拥有者解释如何兑现规格与必要理由 | 卡交接到真正拥有者，不留下中央技术副本 |

普通任务卡在配置仓库的真实 Issue 维护本次结果、范围与当前摘要。一个结果只有一个编辑源。六种[工作类型](work-types.md)共用卡与接受的规则。任务不要求 PF 或产品场景，产品能力的支持状态继续归产品正文。

卡的决定记录保留在真实 Issue；RFC 按专门规则保留方案与最小决定。逐轮讨论、派发、评审和原始运行输出放任务 `tmp`。卡接受后，当前产品规则、规格、设计与持续验证继续可直接阅读；过去的卡不能替代当前能力证据。

## 卡就是交接信息包

一张卡由一个会话交付：从卡给定的起点开工，到成果进入 `integration/mainline`。设计段的长期知识先落盘进 `integration/mainline`，再发卡。交付会话只读卡与它链接的正式文档就开工。会话里讨论过而没写进卡的内容，交付会话读不到。

卡的正文就是 pqw 的交接信息包。新卡一律用[卡模板](../../.github/ISSUE_TEMPLATE/card.md)，九个二级标题照抄、顺序不变：目标、依据、不变式、验收标准、边界、起点与风险、已定事项、只有人能定的待决、四问。起点提交写在「起点与风险」，依据钉在提交上。卡没有执行记录（attempt）、绑定与看板阶段。做法与命令见 `omne-card`「卡就是交接信息包」。

### 从人的话判断本次动作

| 人的意图或说法 | Agent 应做的动作 | 不可混淆的边界 |
| --- | --- | --- |
| “我想增加能力”“这里有个bug”“想优化性能” | 整理问题、当前依据、结果和类型，查询是否已有同范围卡；按当前任务授权起草或发卡 | 提出方向不表示已有规格或获准实施 |
| “帮我建卡”“把刚讨论的任务记下来” | 按获准范围创建或更新唯一卡，读回真实身份、正文及关系 | 建卡授权不等于实施、接受或合并授权 |
| “看看下一步”“哪些任务可以做” | 只读卡，报告排序、已满足与 unknown 的条件，提出候选 | 读取或建议不构成开工 |
| “开始这张卡” | 在卡给定的授权内开工，命令见 `omne-card`「开工」 | 范围不扩大到其他卡 |
| “补充一条要求”“先做B”“A还得等一下” | 区分语义修订、排序调整、阻塞或明确暂停，按各拥有者更新 | 改顺序不删依赖；暂停按精确范围处理 |
| “方案接受”“这个结果接受”“先取消” | 定位对象、修订、范围和决定者权限，分别记录技术采用、交付接受或取消 | 接受设计不表示结果交付；部分接受不关闭整卡 |

对话中的已有授权持续有效，不逐次要求人重复许可。确实缺对象、范围、接受权、产品规则或工具资格时，只问影响下一步的必要问题，并继续不依赖它的工作。只有人能定的事写进交接信息包的「只有人能定的待决」，交付会话开工时一次问齐。语境不足以区分接受方案还是接受成果时，不能自行关卡。

### 整理需求并定位已有卡

先识别人的目标和本次操作范围。按实际承诺拥有者定位产品、技术或工程依据，不强造 PF。查询仓库内的相关卡及已结束结果，按范围和语义比较，不只按标题去重。已有同一活动结果时更新它的获准修订，不另建并行可编辑卡；新回归或新结果可独立建卡并引用旧结果。

选主工作类型及 delivery 或 subtask 层级，确认结果、边界、主接受者、所核输入及类型所需证据。缺决定时保留具名问题，不编造默认答案。技术类型不免除相关产品或架构变化的接受。

讨论尚未变成建卡任务时，在对话或任务 tmp 形成草稿。草稿不是正式 Issue 副本或第二队列；获准发布后，真实 Issue 成为唯一编辑源。后续对话改变范围时核对真实卡及规范，不只修改可能丢失的会话记录。

## 契约变更

契约成员是[线归属表](delivery-lines.json)各线 `contracts` 列出的成员。PR 的「契约变化」逐个列出改动过的契约成员与它的级别：

- `none`：不改契约成员的公开面。
- `additive`：对契约成员只做[可加改动](#可加改动)。
- `breaking`：对契约成员做破坏性改动，见[破坏性契约改动](#破坏性契约改动)。

### 可加改动

构造一个值的一方是写方，读取它的一方是读方。一个契约类型的写方包括它的每个提供者与替身。消费者传入的回调，参数由提供者写、消费者读，返回值由消费者写、提供者读。可加改动是不破坏任何已有写方或读方的改动。卡级按本卡起点到候选 head 的改动判断。

下表列出常见形状，不穷举。未列出的改动也按是否破坏任一既有写方或读方判断：

| 改动 | 对写方 | 对读方 |
| --- | --- | --- |
| 加可选字段 | 不破坏 | 不破坏 |
| 加必填字段 | 破坏 | 不破坏 |
| 必填改为可选 | 不破坏 | 破坏 |
| 可选改为必填 | 破坏 | 不破坏 |
| 删除字段 | 破坏 | 破坏 |
| 给联合加成员 | 不破坏 | 破坏；契约事先声明该联合开放时不破坏 |
| 从联合删成员 | 破坏 | 不破坏 |
| 给由别人实现的接口加必填方法 | 破坏 | 不破坏 |

[人类协作者指南](../../.meta_harness/human/stable-contracts.md)解释这张表的由来和设计方法。它是说明材料，规则以本节为准。

### 破坏性契约改动

1. 卡没有把破坏性改动写进验收标准时，执行者在开发中发现必须对契约成员做破坏性改动，就停止依赖这项改动的工作，在卡评论中写明改动与受影响的契约成员，由人拍板。
2. 人同意后，破坏性切换一次完成：切换提供者、同步全部真实消费者并删除旧形状。破坏性改动按[风险级别](quality.md#按风险选择接受实现的看法)的 L3 合入。

### 契约变更的语义复核

`omne-contract-api` 把无法证明可加的改动分为 `review`。`review` 不是契约级别。它需要人判断这个改动是否可加：`delivery-lines.json` 中拥有该成员的线的 owner 在卡评论中写结论，PR 的「契约变化」按结论申报 `additive` 或 `breaking`，并链接那条评论。

## 提交成果供接受

形成候选后，执行按类型和风险选择的验证，并说明实际输入、结果、限制和未覆盖。收口的做法归 pqw `slice-closeout`，风险级别与人审数归[按风险选择接受实现的看法](quality.md#按风险选择接受实现的看法)。相称检查完成后，把实际成果与证据交给具名结果接受者；需要人的决定时给足对象、范围及缺口，不把全部原始日志交给人逐条检查。

判据要求附上的证据贴在卡评论里，与交付声明一起交给接受者。这类证据包括命令输出尾部、测量摘要、验收结论和准入日志摘要。任务 tmp 只在本工作树可读；换会话、换机器或回收工作树后，接受者就读不到它。只放在任务 tmp 的证据，接受者不据它判断。原件太大时贴摘要和关键行，并写明原件位置与哈希。原件仍按[终态与过程材料](../development.md#终态与过程材料)留在任务 tmp，不入库。

同一对话内有多个对象时，明确本次等待的是方案采用、某个子任务、整张卡还是合并。agent 可以代笔人的明确决定，但须能核对授权人、身份、对象、修订和范围；不因自己的测试结论自授接受。人已经明确决定且有权限时，直接回到该对象的记录拥有者，不再反复请示。

RFC 采用按[提案及决定关系](../rfcs/README.md#现行源与维护)和[RFC模板](../rfcs/.templates/rfc.md)记录精确提案修订与范围，写回仍分别判断。产品、架构及成员规格的采用，按其现行接受约定更新获准终态、采用状态和修订；非 RFC 方案的本次接受记录留任务区，不为补史虚构 RFC。上述采用均不写成卡的 accept 决定，也不关闭关联卡。卡与子任务的结果才进入[接受、取消与重开](#接受取消与重开)，使用真实 Issue 及交付修订；合并或发布继续回其已有授权和制品入口。

卡的有效决定先读回，再关卡。只接受子任务或部分结果时，父卡继续活动。平台写入不可用时，区分“负责人已在对话作决定”和“远端决定尚未记录”；停止依赖其持久事实的状态切换，不声称 Issue 已接受。恢复后取回有权者的可核输入，不能凭模糊回忆补造决定。

## 接受、取消与重开

采用本节的决定记录格式。记录 kind、卡交付修订、范围、决定者与权限依据、日期、所核长期源、实际成果与证据、未包含及剩余责任。决定必须来自有权者，或有可核对授权输入的代笔；机器人留言、任意评论、权限可写和绿测都不授予接受。接受内容有歧义或无法核对归属时保持 unknown。

决定评论采用以下字段。填写提示按实际替换；字段存在或评论写入成功不能授予决定权。

```text
- 操作标识：{{本次决定唯一标识，超时用于读回对账，不声称平台exactly-once}}
- 决定：{{accept／cancel／revoke；部分认可用partial，不能让卡进入Accepted}}
- 对象与交付修订：{{IssueURL及revision}}
- 决定者、身份及权限依据：{{该交付结果的有权接受者；涉及产品／架构／契约变义列相应已有决定；代笔附有权者明确输入}}
- 日期：{{实际日期}}
- 范围：{{精确接受、取消或撤销结果；完整接受不能遗漏本次承诺}}
- 所核依据：{{适用产品场景、技术／工程规范、问题或调查授权及其修订、Git输入}}
- 成果与证据：{{实际远端提交／PR、方法、条件及结果范围；未执行不冒通过}}
- 不含与剩余责任：{{具名缺口及下一责任}}
- 前项关系：{{此前决定URL、取代／撤销精确范围，或无}}
```

交付决定以外的评论（例如范围裁定或接管说明）不写「决定」列表字段，以免读者把它当成交付决定。需要字段时换一个字段名，例如 `- 裁定：`。

卡由具名结果接受者判断所有本次承诺结果。产品结果必须由产品负责人接受；技术结果由有权技术或工程接受者判断，任务标签不能赋予权限。跨产品与技术责任时，各受影响语义拥有者先接受自己的变化；卡须明确相应决定与本次结果的主接受责任，不能由主接受者替其他拥有者批准变义。部分认可只记录认可范围，卡不进入 Accepted、不关闭为完成；剩余结果继续活动，或由拥有者明确拆卡、缩小范围并接受新的交付修订。不能以记录 accepted 但少几项的方式隐式关卡。

接受记录先写入并读回，再关卡；它们没有跨对象事务。关卡失败不撤销真实接受、不补造第二次决定；读回后修复。若未取得有效决定却已关卡，重新打开并保留误操作说明。取消由有权的卡负责人明确作出，记录后继影响，不满足其他卡的结果条件。

接受后不重写旧决定。发现原范围其实未兑现或接受依据被撤销，由有权者记录精确撤销范围及新交付修订，再重开同一 Issue；新需求或回归通常另开 Issue 引用原结果。只有有权者的新记录能撤销原接受；普通重开只触发冲突复核，不自动改变全部历史。下游活动条件根据精确范围重新判断。交付修订的语义变化由卡拥有者递增，样式和无关评论不升；新决定指明此前决定的链接与取代或撤销范围，当前有效事实须从相关决定及撤销链读取，链不完整就是 unknown。

卡历史只说明过去交付与决定。当前产品规则、现行规格、设计及持续验收仍直接可读。GitHub 评论可编辑，本规则不能防管理员篡改；发布验证要检查历史指向和内容冲突，不能声称不可篡改审计。

## 对人的操作回执

每次完成有意义的操作，简短说明真实卡身份、做了什么、实际已记录或尚缺的事实及下一步；受阻时指明条件、责任和需要人提供的具体决定。区别“草稿已写”“卡已创建”“已开工”“候选已验证”“决定已记录”和“卡已关闭”，不要只回答“已完成”。

无需向人重复字段清单、技能正文或所有检查过程。工具发生超时或部分失败时，准确报告已成功部分及读回结果。自动路由、原生调用或 cloud 恢复未验证时明说；文档存在不表示 agent 已经遵循。
