# verification/proofs

本目录保存超出有限模型范围的手写证明。每条写明命题、前提和推导。性质编号与模型见 [formal-mapping.md](../formal-mapping.md)，有限范围的机检见 [formal-runs.md](../formal-runs.md)。

手写证明没有机检。它只在所列前提下成立。

## P1 已应用是日志前缀

**命题。** 对任意长度的持有者日志、任意送达序列和任意崩溃次数，机制已应用的提交序列始终是持有者耐久日志的前缀，注册修订等于其中注册决定的个数。这与提交身份的个数无关。

**前提。**

1. 持有者的日志只追加，写入成功才把输入送给机制（先提交、后应用）。
2. 机制只在 `after` 等于链头时应用一笔提交（`applyCommit`）。注册决定还要求 `basedOn` 等于当前注册修订，并把修订加一（`prepareRegistrationCommit`）。日志第 k 条的 `after` 是第 k−1 条的身份，身份互不相同。
3. 恢复只安装持有者交回的整份日志，链头取日志末项；崩溃清空机制的进程内状态。
4. 假设 A1：同一身份第一次送达的输入就是已提交的那份。

**推导。** 归纳不变式 I：设已应用序列长 n，则它等于日志的前 n 项，链头是第 n 项的身份（n = 0 时为空）。初始时成立。应用一笔提交 d 时，由前提 2，d 的 `after` 是第 n 项的身份；由前提 1、A1 与身份互不相同，d 是日志第 n+1 项。所以追加后 I 仍成立，注册修订只在 d 是注册决定时加一。重送、改写的重试、乱序的送达都不改 `applied`。崩溃使 `applied` 为空，恢复安装整份日志，I 成立。日志只追加，所以已有的前缀不会失效。

## P3 成功去重表有界且已释放的提交被拒绝

**命题。** 对任意长度的持有者日志、任意送达序列和任意崩溃次数，一个作用域的成功去重表至多一项。本实例应用过、但已不在表里的提交再次送达时，只要围栏打开，答复是「顺序不符」，不被应用，也不被答「已应用」。改写过输入的这种提交也一样。

**前提。**

1. P1 的前提与结论：已应用序列是日志的前缀。
2. 日志里的提交身份互不相同。第 k 条记录的 `after` 是第 k−1 条的身份，第一条为空（持有者的 `chained`）。
3. 应用一笔提交时，链头取它的身份，成功去重表先清空再写入它（`remember`）。恢复安装时，链头取检查点，即日志最后一条，表里只留身份等于链头的条目（`install`）。崩溃清空一切。
4. 不在表里的提交，`after` 不等于链头时答「顺序不符」，不应用。

**推导。** 归纳不变式 J：链头是已应用序列最后一项的身份（序列为空时为空），表包含于 {最后一项}。初始时成立。应用 c：c 追加到序列末尾，链头是 c，表是 {c}，J 成立。恢复：序列成为整份日志，链头是日志末项，表被过滤到链头，J 成立。崩溃：全部清空，J 成立。由 J，表至多一项。

设 x 是已应用序列第 k 项的身份，且 x 不在表里。x 的 `after` 是第 k−1 项的身份，k = 1 时为空（前提 1、2）。如果 k 是最后一项，链头是 x，而 x 的 `after` 不是 x（身份互不相同）。如果 k 不是最后一项，链头是更后一项的身份，也不等于第 k−1 项的身份，也不为空。两种情况下 `after` 都不等于链头，由前提 4 答「顺序不符」。改写只改载荷，不改 `after`，结论相同。

**范围外。** 前提 2 归持有者。持有者送错 `after` 时，本成员只能保证不按错的顺序应用：错的 `after` 不等于链头时答「顺序不符」。围栏关闭时答「恢复未完成」，也不应用。

## P5 缓存不改变读取结果

**命题。** 对任意操作序列，带读取缓存的实例与不带缓存的实例给出相同的读取结果。

**前提。**

1. 缓存键含作用域、资格身份与投影版本。
2. 每个改变过滤后读取输出的写入都推进投影版本：发布、换代清值、注册变化、作用域结束、恢复。runtime-context SPEC「读取缓存」列出这些推进点，换代的推进点在 `replaceInScopes` 的 `world.touch`。
3. 命中仍核资格、权威端口与 `current()`。
4. 父链上的值不缓存：带父级的读取不进缓存（模型的 `Cacheable`）。

**推导。** 设某次读取命中缓存条目 e。e 的键与本次相同，所以作用域、资格与投影版本都相同。由前提 2，从 e 写入到本次读取之间没有改变过滤后输出的写入，所以不带缓存的实例此时算出的输出与 e 相同。前提 3 保证资格变化不经缓存绕过。守卫 M4 去掉换代的推进点时差分变红，说明前提 2 是必要的。

**范围外。** 前提 2 的推进点清单由人维护。新增写入路径时要核对它是否推进版本。

## 读取工作量有界

**命题。** 一次读取对每个块键至多走父链长度的跳数，与发布次数和历史长度无关。

**推导。** `readBlock` 与 `inheritedValue` 只读当前值，不读历史。父链每跳读一次当前注册与当前值，遇到本租户的值或链尾就停。所以工作量是块键数乘以链长。
