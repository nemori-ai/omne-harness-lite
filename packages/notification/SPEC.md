# Notification

## 总体架构

Notification 包组回答一个问题：系统、agent 或源业务要把给定的内容交给一个明确的目标租户时，怎样可靠地接下这份交付责任，确认它真的到了目标手里可以随时取回，并让有资格的人按一次请求查到真实的结果，而不改变源业务的任何事实。

| 成员           | 回答的问题                                                                                           |
| -------------- | ---------------------------------------------------------------------------------------------------- |
| `notification` | 通知的定义拥有者：发送与查询的公开契约、受理与交接、送达确认、未知核对与恢复、可替换提供者的共同接缝 |

一次发送带着业务归属、发起者、明确目标与给定内容进入；通知核对当前的发送与披露资格，可靠承接交付责任之后才对外确认受理。合格的提供者按原目标交付，只有正确目标持久可取回的证据才记为送达。源方在通知可靠承接之前保管待交付责任，之后由通知保管，中间没有无人负责的窗口。查询只读，按一次请求定位原内容、来源、目标与已知结果。

## 领域边界

本组拥有：一次发送请求的受理与交付责任；送达、尝试与未知的事实；一次请求的查询；可替换提供者共同遵守的承诺。

本组不拥有：通知的内容（由发送方给定，本组不生成）；源工作与它的整体结算（Schedule、Job 或其他源协调方）；源事件的选择（源拥有者在接受时固定）；发送与披露资格（身份与授权）；人工等待的答复（人工介入）；日历发布与健康（Calendar）；呈现与已读（交付面）。普通回复、成果上报、运行时唤醒、复制邀约与 Cordis 事件派发不是通知。

本组声明、由别人实现的端口：

| 端口                   | 对方                                        | 本组需要它做什么                                           |
| ---------------------- | ------------------------------------------- | ---------------------------------------------------------- |
| 发送、跨租户与披露资格 | Identity（身份与授权）                      | 在实际披露的边界给出当前的资格判断                         |
| 目标交付提供者         | 具体通道的提供者（经应用装配）              | 按原目标交付，给出持久可取回的证据、未知的范围与支持限制   |
| 源事件与待交付责任     | 源业务（Schedule、Job、人工介入、Calendar） | 给出接受时固定的事件、内容与目标；在通知可靠承接前保管责任 |

本组为别人实现的端口：

| 端口 | 对方                           | 本组提供什么                                   |
| ---- | ------------------------------ | ---------------------------------------------- |
| 发送 | 系统、agent、源业务协调方      | 可靠受理一次给定内容的交付                     |
| 查询 | 源业务、应用的读面、有资格的人 | 按一次请求读原内容、来源、目标与已知结果；只读 |

## 心智模型

把通知想成一个挂号信窗口。寄件人交来内容、写明收件人，窗口签收之后这封信就是窗口的责任，签收之前还是寄件人的；只有收件人那边能随时取到信，才算送达，投进邮筒、广播出去或屏幕上闪过一次都不算。同一封信重寄几次还是同一封信；内容一样的两封信是两封。窗口不替寄件人写信，不替他办事，也不因为信没送到就说他的事没办成。

最容易想错的地方：受理、尝试、送达、呈现、已读与源工作完成是分别成立的事实，不是一个单向推进的状态；结果未知不是失败，超时、重试耗尽或实例撤除都不能把它改成「从未发生」；取消只在发送之前有效，已经发出或未知的不承诺撤回；资格失效挡住之后的披露，不抹掉已经发生的历史。

## 应然设计

### 发送与身份

- 系统或 agent 在授权下可以发送给定内容，不需要 Schedule、Job 或会话存在。纯通知不启动 agent 生成文案，不发起分析，不借恢复重做源动作；普通回复与成果上报不替代通知，成果提交不隐含发送。
- 一次请求分别保持业务归属、实际发起者、明确的目标组织与账号、适用来源；同一账号的其他组织身份不是目的地，不自动改投。系统业务、租户业务与目的地互不改变原业务归属，不借系统身份读取或披露租户私有资料。
- 发送准入、跨租户传送、目标接纳、查询与字段披露各按实际边界所需的当前资格判断；装配了工具、持有服务引用或指定了目标都不构成授权；未获准的跨租户访问默认拒绝。实际披露之前复核会失效的资格；资格撤销与发送竞争不产生未获准的披露，已发生的效果如实记录。
- 内容、来源引用与诊断只披露获准字段。允许目标收到一条通知不授予完整源历史的读权，不允许枚举别的租户私有通知是否存在；无权的结果按安全边界拒绝或裁剪，不展示私有内容来解释拒绝。

### 受理、交接与送达

- 对外确认可靠受理时，原内容、目标、来源关联与未完责任已经一致可恢复；不先答成功再异步补保管。源方直到通知可靠承接之前保管待交付责任，之后通知保管。回执丢失时按原请求核对，不由调用失败推断未受理。已提交的源事件不因交接失败而回滚或重做。
- 只有已确认的通知在明确目标租户范围内持久可取回，才报告送达；内容、目标与送达证据对应原请求。发送、渠道受理、事件广播、一次显示或在线状态都不能单独代替这个依据。目标提交未确认时如实表达未完、失败或未知的范围，不先写送达再补目标事实。离线不使已送达的通知丢失。
- 读面、实时呈现、诊断与事件通知源于同一业务事实，不另造一套交付真相；读面滞后说明新鲜度；提交之后的监听或投影失败不把受理或目标提交改写成未发生。

### 一次请求与同一通知

- 消费者能按一次发送请求定位原内容、允许披露的来源、目标、已知结果与未确认的部分。查询只读，不创建通知或源工作；缺投影不当作未发生。
- 同一请求的重试、恢复、重复的源告知或提供者换代保持同一逻辑通知与原内容、目标、来源语义，不产生多份用户通知。另一次主动发送要有新的业务意图，不充当旧请求的恢复；内容相同的不同意图不合并。没有安全证明时不靠盲目重发求进展；外部通道不可撤回或无法确认时保管未知，不宣称恰好一次。
- 并发受理、重复告知、多个尝试、晚到回执、取消与资格变化在具名的提交或效果边界上核对；实际送达不被过时的失败或取消投影覆盖。

### 源事件与整体结算

- 源拥有者在接受时固定事件、内容与目标声明。开始、成功、失败、取消只有被选中且实际发生才触发，每个 Job 的一个已选事件对应一次逻辑通知；等待不当开始，未知不当失败。之后修改 Schedule 不改已接受的 Job。通知层不推断事件、不添加默认事件，不因通知发送失败递归生成执行失败通知。
- 通知只返回真实的交付事实；源工作与组合终态由源协调方决定。通知不把源失败或取消洗成成功，不把受理、尝试或已读当整体完成；agent 主动另发、成果提交或客户端呈现不冒充配置的通知义务完成。
- 人工等待要让有资格的人知道事项在等待；合格入口显式呈现本租户待办并持续保存也是有效方式，不要求额外的发送。实际形成提示时才走本组；提示失败或未知不生成答复、不解除等待、不授予写权。日历维护提示的受理、送达与发布、风险、健康分别观察，提示失败不清风险、不改已提交的发布、不重抓源数据。

### 取消、未知与恢复

- 源允许的纯通知，发送前取得有效资格且在发送前获胜的取消阻止发送。发送已发生或结果未知时不承诺撤回，不把未知改成取消成功，也不因取消重发。源执行取消仍按原声明判断取消通知，并保留此前已触发的交付责任；晚到回执保有原归属。停止等待、断开连接或 disposer 都不自动取得业务取消的效果。
- 超时、进程退出、回执丢失、读面缺失与重试耗尽都不单独证明未发生。恢复先核对通知的权威事实与目标的实际效果：已确认送达的恢复原结果；原责任方显式发起继续、获有效准入且能安全继续时，只续原未完的交付；只读查询不触发发送；不能确认安全时如实保持未知、说明限制与处置拥有者，不重做源动作。

### 提供者、配置与生命周期

- 定义拥有者维护一个能力接缝；根入口与 Cordis 无关，集成入口引用同一定义；消费者依赖公开契约，不引用选定的后端。业务通知与 Cordis 事件派发分开，监听者或广播成功不是租户持久送达。
- 每个被采用的提供者证明明确目标、披露资格、持久可取回、查询与回执、外部副作用的责任；弱回执不升级为送达；不支持或缺席如实报告。
- 重试、退避、超时、限流是合法配置的值，不写死；配置缺失或无效、依赖缺席明确拒绝或暴露限制，不静默选通道、参数或收件人。策略停止继续尝试不清除已发生的效果或原责任，不把未知变成无效果。
- 换代或依赖失效时：先停准入，在途的保管或可靠移交，然后撤除自己的登记、监听与资源；接续方先核对原请求再接续；旧引用与晚到结果有归属；没有承接方时不把未完责任当完成或删除。新配置不改写已接受的内容、目标与源事件声明。
- 通知历史按目标租户隔离保留并可查询，不因源终结、归档、失权或实例卸载自动删除；查询仍核当前权限。诊断输出遵守租户与内容的披露资格。

## 原则与约束

- 通知不制造源工作，也不改源事实：不生成内容，不重做源动作，不决定源的整体结算。
- 送达只认目标持久可取回的证据；受理、尝试、呈现、已读各自成立。
- 结果不知道就是不知道。按原请求核对，不盲目重发，不把未知改成失败或「什么都没做」。
- 同一意图只有一份通知；新意图才是新通知。
- 资格每次在实际边界现核，装配可见不是授权；跨租户默认拒绝。
- 策略类的值是配置，不写死；配置不能减弱这里的任何一条。
- 外部输出不因 disposer 而可逆；卸载停的是实例，不是业务。

## 不变式

| 编号     | 永远成立的性质                                                                 | 违反的后果                              | 由什么守 |
| -------- | ------------------------------------------------------------------------------ | --------------------------------------- | -------- |
| INV-NO01 | 发送不需要也不制造源工作；恢复不重做源动作                                     | 一次通知触发一次额外的 agent 工作或费用 | 只有文字 |
| INV-NO02 | 业务归属、发起者与目标分别保持，不自动改投                                     | 通知送到同一账号的另一个组织            | 只有文字 |
| INV-NO03 | 每项操作按实际边界的当前资格判断；装配可见不授权；跨租户默认拒绝               | 未获准的披露                            | 只有文字 |
| INV-NO04 | 通知不扩大对源信息的访问，不泄露其他租户私有通知是否存在                       | 借通知读到不该读的历史                  | 只有文字 |
| INV-NO05 | 对外确认受理时原内容、目标、来源与未完责任已一致可恢复；交接没有无人负责的窗口 | 答了受理的通知丢失                      | 只有文字 |
| INV-NO06 | 送达只在正确目标持久可取回时报告                                               | 只是广播或显示过就被当成送达            | 只有文字 |
| INV-NO07 | 一次请求可按原请求定位；查询只读                                               | 查询触发发送，或缺投影被当作未发生      | 只有文字 |
| INV-NO08 | 技术继续不产生新的独立通知；新意图不冒充恢复                                   | 用户收到重复通知                        | 只有文字 |
| INV-NO09 | 只有被选中且实际发生的源事件形成通知义务；通知失败不递归生成失败通知           | 凭空的通知，或通知风暴                  | 只有文字 |
| INV-NO10 | 源执行、交付与整体结算分别成立                                                 | 源失败被通知洗成成功                    | 只有文字 |
| INV-NO11 | 等待与维护提示不改源事实；提示失败不生成答复、不解除等待                       | 提示失败被当作人的答复                  | 只有文字 |
| INV-NO12 | 取消只在发送之前生效；已发生或未知的不承诺撤回                                 | 声称撤回了已经送出的通知                | 只有文字 |
| INV-NO13 | 未知先核对原工作，不能确认安全就保持未知                                       | 盲目重发产生第二份外部效果              | 只有文字 |
| INV-NO14 | 并发归并保持同一事实；实际送达不被过时投影覆盖                                 | 已送达被晚到的失败改写                  | 只有文字 |
| INV-NO15 | 换代与撤除只撤自己的贡献，不抹历史与在途责任；新配置不改写已接受的请求         | 换代丢失在途通知                        | 只有文字 |
| INV-NO16 | 通知历史按目标租户隔离保留，不随源终结、失权或卸载自动删除                     | 历史被静默删除                          | 只有文字 |
| INV-NO17 | 每个可替换提供者兑现同一组承诺；弱回执不升级为送达                             | 换一个通道就换了语义                    | 只有文字 |
| INV-NO18 | 配置缺失、无效或依赖缺席明确暴露；不静默选通道、参数或收件人                   | 通知被静默发往错误的地方                | 只有文字 |
