# Notification

## 总体架构

Notification 包组回答一个问题：一件已经发生的事，怎样可靠地到一个收件人手里，而给谁、多急由收件人自己定。收件人有两种：人，和受托的 agent。

它是接在核心系统上的一套插件。核心域（Session、Agent、Model、Tool、Runtime Context、Request Context）的成员都不依赖它；去掉它，核心原有的流程不变。它只用核心与地基已经公开的东西：存储的提交与认回、身份与授权的资格判定、入口的协议登记、Tool 的绑定登记、会话的输入来源登记、Runtime Context 的块。

| 成员 | 回答的问题 |
| --- | --- |
| `notification-contract` | 通知的纯契约：公开的值、声明的形状、服务面的类型，以及全部纯决定（收件人的选择、发送、顶替、处置、订阅、强单元与节拍、重投、裁剪）。只依赖 zod |
| `notification` | 通知的定义拥有者：接下与认回、收件箱与处置、通知订阅、投递去处、目录、投递的推进、来源与渠道两个登记面，以及仓储的端口与事务脚本。只依赖契约 |
| `notification-cordis-contract` | 服务定义：五个服务面与两个登记面在 Cordis 里叫什么 |
| `notification-local` | 本地提供者：SQL 仓储、配置、到期的唤醒与扫描、应用内渠道、本组自己的两个来源、变化的告知、生命周期 |
| `notification-tools` | 给 agent 的多命令工具 `Notifications` |
| `notification-protocol` | 协议 `notification/v1`：人以租户 owner 的身份能做的操作与一条观察。纯数据 |
| `notification-access` | 协议的接入插件：处理函数与观察的帧源 |
| `notification-ui` | 界面模块：通知面板页、未了结的条数、往面板里放栏的拓展点 |

一件事这样走：来源把一个事件交给通知；通知用一次提交接下它，同一次提交里按当时的通知订阅算出收件人，把一条通知写进每个收件人的收件箱；之后按强弱、最小间隔与节拍，把通知组成投递单元，推到收件人每个启用的投递去处。投递的结果另记，不改已经入箱这件事。

认识会话的适配成员、往 Runtime Context 供给块的成员、设置声明的成员在用到时再建，建的时候写进这张表。

## 领域边界

本组拥有：通知来源与事件类型的目录；一次发送的接下与认回；通知订阅；收件人、它的投递去处与节拍；收件箱里的通知与收件人对它的处置；投递单元与每次投递的结果；合并与节拍的规则。

本组不拥有：事件发没发生、内容是什么（来源）；一件持续事项开着还是了结了（来源，经 Runtime Context 供给）；发送、读、处置、订阅的资格（身份与授权）；owner 对 agent 订阅的确认（人工介入出卡，答复归人）；会话的输入与开不开一轮（Session）；到点的判断与作业的结算（Schedule）；连接外部系统的连接与凭据（接入外部的那个成员）。普通回复、成果上报、Runtime Context 的变化提醒、Cordis 的事件派发都不是通知。

本组声明、由别人实现的端口：

| 端口 | 对方 | 本组需要它做什么 |
| --- | --- | --- |
| 资格 | 身份与授权，经应用装配 | 答一个主体此刻许不许：以某来源发送、读一个收件箱、处置、为一个收件人设订阅、管投递去处、列目录、当收件人；并答一段内容往一个去处能披露到哪一步 |
| 具名命令与事务参加者 | 存储 | 一次提交里写下发送与全部通知；结果不知道时如实答。按原身份认回由本组的事务脚本在同一次提交里查，不用存储的回执：存储对回滚的提交也留回执，按它认回会让一次失败的接下占住这个发送身份 |
| 时钟提示 | 应用装配 | 最小间隔与节拍到点的唤醒 |
| 「一组持续事项」这个需要 | Runtime Context，由装配把各来源发布的块绑上来 | 按本组自己的形状读各来源此刻还开着的事项与它们的变化 |

本组为别人实现的端口：

| 端口 | 对方 | 本组提供什么 |
| --- | --- | --- |
| 发送与查询发送 | 来源的贡献成员、agent 的工具、日程的提醒承接 | 接下一个事件；按原请求答它的结果 |
| 收件、订阅、去处、目录四组操作 | 接入插件、agent 的工具 | 读与处置收件箱；设与撤通知订阅；管投递去处；列来源、事件类型与渠道 |
| 来源登记面、渠道登记面 | 各来源、各渠道的贡献成员 | 两个拓展点，见「拓展点」 |

本组往别的宿主里放的：一个协议；一个多命令工具；会话的一个输入来源；Runtime Context 的两个供给块；两项设置声明；日程执行承接里「发一条通知」这一种。每一样都由一个贡献成员带来，宿主不在时只有那个成员不启动。

## 心智模型

把通知想成一个邮局，加每个收件人门口的一个信箱。寄信的人把信交到柜台，柜台盖了章，这封信就已经在每个收件人的信箱里了：盖章和入箱是同一个动作。邮局再按收件人自己的嘱咐去敲门：要紧的立刻敲，不要紧的攒到约好的时刻一起说一声。敲门没人应，信还在信箱里。

最容易想错的五处：

- **入箱才算送达，敲门不算。** 推到界面、送进会话、发到外面，都只是投递；它成功、失败还是不知道，都不改「信在信箱里」。
- **给谁、多急，是收件人的事。** 来源只说发生了什么、属于哪一类。来源给的强弱只是缺省，不能强行打扰。
- **通知只让人知道，不替人做事。** 它不调模型，不生成内容，不重做来源的动作。agent 收到之后办不办，由 agent 在自己的会话里定，并照会话当前的权限。
- **状态不是事件。** 一件还开着的事是来源的一个当前值，经 Runtime Context 读；通知不复制它，只提醒。一次性的事件才入箱。
- **几样东西分别成立。** 已接下、已送达、已投递、看过、了结、来源那边的结局，各有各的依据。结果不知道就是不知道，按原请求去查。

## 应然设计

### 事件与发送身份

- 一个事件带：来源、事件标识、事件类型、对象（可空）、时刻、内容（标题、正文、定位）。对象是「这件事关于来源里的哪个东西」。事件标识由来源在自己的范围内保证唯一。
- 发送身份是（租户，来源，事件标识）。两次发送是不是同一次，只比它。同身份同内容再来是认回，答原结果，不写任何东西；同身份不同内容是冲突，拒收，不覆盖。
- 实际来调发送的主体另由资格核对：它许不许以这个来源发送。它不进发送身份。

### 接下一次发送

- 判定的次序固定，前一项不过就不往下：请求完整且不超上限；发送主体有资格；这个发送身份没有接下过；来源此刻登记着并声明了这个事件类型，且这个类型是一次性事件；点了名时，这个类型许点名、收件人在同一租户、种类是这个类型许的；带因果深度时不超过上限。
- 认回排在取来源声明之前：一次发送接下之后来源撤下了，再送照样认得回。资格排在认回之前：没有资格的主体问不到这个发送身份有没有接下过。
- 接下是一次提交，里面一起成立：发送记录；每个入选的收件人一条通知；被顶替的旧通知的标记；「命中一次就撤」的通知订阅的到期。答「已接下」时这些都已耐久。没有收件人入选也是已接下。
- 来源此刻没有登记或声明取不到，答依据不可用；这和「来源名从没登记过」对外不区分。提交写不进答依据不可用；不知道写没写进答未知。

### 收件人的选择

- 对租户里每个收件人，在这个来源、这个事件类型上，找范围匹配这个事件对象的通知订阅，取最具体的一条。范围有三种：全部；对象等于某个引用；对象以某一段开头。相等比开头具体，开头里长的比短的具体，全部最不具体。不按正文匹配。
- 没有匹配的订阅时，取事件类型对这种收件人声明的缺省。取值不是「不收」的入选。
- 被点名的收件人一定入选；它的取值是「不收」时按弱。发出事件的那个收件人自己不入选。
- 强弱、缘由（被点名、命中了哪条订阅、还是类型的缺省）、当时的备注，在接下那一刻写进通知。之后改订阅、来源撤下，都不改已入箱的通知。

### 收件箱与处置

- 一条通知有三个各自成立的标记，各带时刻：看过；了结（办完或划掉）；被顶替（被哪一条）。它们不是一条状态线。
- 标看过在任何时候都成立，重复是认回。了结与划掉只对没了结且没被顶替的成立；已是同一种是认回，已是另一种要先恢复。恢复把办完或划掉的放回没了结；被顶替的不能恢复。
- 系统不自己恢复一条通知。恢复只来自有资格的一次明确的操作。
- 带替换键的事件入箱时，这个收件人箱里同一来源、同一个键的旧通知都标成被它顶替，不论旧的了结了没有。顶替时缺省不投递；发送时打开「重新提醒」才照强弱投递。
- 读是只读的，不改标记。列箱按入箱先后分页。无权、不存在、属于别的租户，对外是同一个拒绝；读不到时答依据不可用，不答成空。
- 处置只改通知的标记，不改来源的任何事实。

### 通知订阅

- 一条通知订阅的键是（收件人，来源，事件类型，范围）。它带：取值（不收、弱、强）、备注、期限（一直、命中一次就撤、到某个时刻为止）、依据。
- 「设成不收」是明确关掉；「撤掉」是回到事件类型的缺省。两者不同。
- owner 可以为本租户任何收件人设订阅，依据是 owner 本人。agent 只能为自己所在的会话设。agent 新订或调高要 owner 的同意：owner 的方式是自动生效时，依据是全权同意的当前这一代；是逐条确认时，要带 owner 对同一份内容的确认，依据是那次答复。确认对不上（别的内容、别的调用、别的租户、不是同意）是拒绝。agent 调低、撤掉、缩短期限不要同意。
- 同意在做出那一刻成立。之后 owner 改方式，已经成立的订阅照常有效，记着的依据不变。
- 本组只答「要 owner 确认」并给出这次请求的内容摘要。出卡、等答复、带着答复重提，由工具成员照人工介入的等人契约做。
- 订阅只影响之后接下的发送。来源撤下时订阅保留，来源回来后接着命中。

### 投递去处、投递单元与合并

- 一个收件人有一组投递去处。一个去处有：渠道、渠道认得的地址、最低强度（只收强的，或强弱都收）、启用与否。人缺省有一个应用内的去处，不能删。受托 agent 的去处随收件人一起建。
- 投递的单位是投递单元。强通知的单元：一个去处上入箱在它上一个强单元之后的、没了结的强通知；去处记着强单元推进到的入箱序号。形成单元时已经了结的，之后恢复了也不再进强单元，只进节拍。节拍的单元：这个收件人在这一拍的时刻该提醒的全部通知。单元的成员与内容在形成那一刻定下并耐久，之后每次重投用同一个单元、同一个投递身份、同一份内容。
- 一个去处有最小间隔。离上一个强单元不到最小间隔时不形成新的强单元；到了间隔，这段时间里攒下的强通知形成一个单元。它们排队，不丢，也不因为攒得多而提前。
- 节拍到点时，箱里有该提醒的才形成单元：对人是没看过的，对受托 agent 是没了结的；它订的持续事项还有开着的也算。没有该提醒的，这一拍不形成单元，不产生提交与投递。节拍的单元带这一拍的时刻之前入箱的全部该提醒的，不只带上一拍之后新来的。唤醒晚到时补的是那一拍本该有的内容，这一拍的时刻之后入箱的留给下一拍。
- 摘要机械合成：条数，加最早若干条的来源、事件类型与标题。不调模型。
- 同一条通知推到每个启用的去处，各是一个单元的一次投递，各有结果。它仍是一条通知，只入箱一次。
- 渠道答成功、失败（带原因与可否重试）或未知。抛出与超时记未知。失败可重试的与未知的按退避用同一投递身份再投；到上限后不再自动投，通知留在箱里，这个去处成为本组自己的一件持续事项「投递受阻」。渠道答确定收不了时不重试，也不改投别的收件人。
- 往出系统的渠道投时，载荷是标题加定位，正文按资格端口答的披露范围裁剪。完整内容回到本系统后重新核资格。

### 持续事项

- 事件类型分两种：一次性事件由来源发过来；持续事项绑定到来源在 Runtime Context 发布的一个块。持续事项不经发送，不入箱。
- 本组用自己的形状声明一个需要：一组持续事项，每项有身份、标题、定位、从什么时候开始。装配把各来源的块绑到这个需要上。本组不认识任何具体的块键。
- 一件事项刚出现时，取值是强的收件人被提醒一次；本组耐久记下（收件人，事项身份）提醒过。节拍时还有开着的就并进节拍的单元。
- 读块得到拒绝、缺项或未知时，不当成「没有开着的事项」：这一次不提醒，不清掉提醒过的记录。进程重建后拿到全量时，按记录比对，只提醒新的。
- 本组没有了结一件持续事项的操作。提醒的任何结果都不算对它的答复。

### 给受托 agent 的投递

- 受托 agent 在本组是一个不透明的引用。只有认识会话的适配成员知道它是一个会话。本组的契约里不出现会话。
- 适配成员在会话的输入来源拓展点登记一个来源，并在本组的渠道登记面贡献「会话输入」这个渠道。提交标识取投递身份，所以一个单元在一个会话里至多一条输入。
- Intake 答已受理或已认回，这次投递记成功；答拒收记失败、不可重试；答依据不可用或未知记未知。
- 送进会话的内容写明来源、事件类型、发出者与缘由，备注与事件分开给。来自系统外面的内容做数据标记并注明是数据。一条通知不带任何授权。
- agent 发的事件带发出者与因果深度：它是在第几层被本组叫醒的一轮里发的。这两样由工具成员按那一轮的起因填，agent 自己填不了。

### 拓展点

两个都在服务端，登记即效应，贡献方撤下时自动撤回。同名登记失败并报出来，不覆盖。登记不分租户，也不给任何人资格。

| # | 问题 | `notification.sources` | `notification.channels` |
| --- | --- | --- | --- |
| 1 | 叫什么 | 通知来源 | 投递渠道 |
| 2 | 哪一棵树 | 服务端 | 服务端 |
| 3 | 能放几项 | 按键放，每个来源名至多一项 | 按键放，每个渠道名至多一项 |
| 4 | 键从哪来 | 声明自带的来源名，`<领域>.<名字>` | 声明自带的渠道名 |
| 5 | 宿主给它什么 | 判规则时给核验过的发送主体与这次发送的元数据；另给发送口 | 租户、收件人引用、去处上的地址、载荷、投递身份 |
| 6 | 它交什么 | 数据与纯函数：来源名、给人看的名字、一组事件类型 | 带副作用的函数：投递。另有数据：认哪种地址，出不出本系统，缺省的最小间隔 |
| 7 | 什么时候读，变化怎样传 | 每次接下与每次列目录时现取；目录变了由本组发一个事件，协议的观察说「可能变了」 | 每次投递现取 |
| 8 | 出错时 | 规则答不出：这次发送答依据不可用 | 抛出或超时：这次投递记未知 |
| 9 | 撤下 | 下一次就没有了。已入箱的照旧可查可处置，订阅保留 | 先不接新的，在途的投递各有结局，然后撤完。用它的去处标成渠道不在 |
| 10 | 形状怎样变 | 加可选项相容，改形状换主版本 | 同左 |

一个事件类型的声明写：名字、给人看的名字、给模型读的说明；一次性事件还是持续事项（后者写绑定的块）；对象怎样写；许哪种收件人订阅；能不能点名；对每种收件人的缺省取值；内容是不是来自系统外面。

渠道的投递函数必须满足：同一个投递身份再调一次，不产生第二份效果。

本组自己的来源与渠道也经这两个登记面，和别人的走同一个契约：来源「agent 写的」与「通知自己」（目录变了；投递受阻），渠道「应用内」与「会话输入」。

### 目录

- 来源、事件类型与渠道的清单按当下的登记现算，不另存。只列调用方有资格知道的。
- 一个来源的声明此刻读不出时，整次答依据不可用，不答成少一个来源的清单。

### 提供者与生命周期

- 定义拥有者的根入口与 Cordis 无关；集成入口引用同一定义。消费者依赖公开契约，不引用选定的后端。
- 重试、退避、最小间隔、节拍的缺省、摘要列几条、因果深度的上限都是配置。缺失或无效时拒绝加载，不静默取值。
- 时钟提示只是唤醒，可以早、晚、重复、丢失。哪一拍、哪个单元该不该做，按存储里的状态算；丢了的靠启动时与定期的扫描补上。
- 撤下时先停准入，在途的投递各有结局或保持未知，再撤自己的登记与监听。撤下不删通知、订阅与投递记录，不撤回已经发生的投递。
- 通知的历史按租户隔离保留，不因来源撤下、会话归档或实例卸载自动删除。
- 仓储一次读的行数有上限。一个租户要读的行超过它时，这次读答依据不可用，不答成少一些。

### 对客户端开放

- 协议 `notification/v1` 是人以租户 owner 的身份做的事：收件、订阅与节拍、去处、目录四组操作，查一次发送，一条观察。agent 不经它。
- 每个提交按它留下的状态幂等：结果未知后原样再送，已经成立的答「没有变化」，没成立的这次成立。所以提交不另设「查」的操作；只有发送有发送身份，另有「查一次发送」。
- 正文合协议的规则、值不合本组规则的（来源名的写法、引用的长度、不到毫秒的时刻），答无效并注明是请求的值，不答成依据不可用。
- 观察的帧只说收件箱或目录可能变了，不带内容；建立时各说一次，观察者收到就重读。每发一批帧之前重核这次登录还能不能为这个租户行事。提供者卸下时观察以不可用结束，观察者重连。
- 接入插件的处理函数先核登录能不能为租户行事，再取主体与本组的服务面，最后调本组并映射结果。无权看一条通知与它不存在对外是同一个答复。本组抛出时，读答依据不可用，提交答未知。
- 界面模块的标记只按服务端答的改，不先改再等。读不出时留着上一次读到的并写明，不显示成空的收件箱。
- 界面模块的拓展点 `notification.inbox-sections` 让别的领域往通知面板里放一栏，排在通知的下面。它不按键分，对象是「人的收件箱」，文本是 `person`。贡献的一栏随贡献方的作用域撤掉。

### 给 agent 的工具

- 工具 `Notifications` 对模型是一条声明：`help` 加十一个命令。菜单、签名与用法由参数规则派生。
- agent 只以自己的身份行事。来源、事件类型、发出者、对象、因果深度由这次调用的绑定给；参数里没有这些字段，多给一个字段整次调用无效，不悄悄丢掉。收件箱与订阅只能是它自己的。
- agent 发的一条点名 owner。别的 agent 只有订阅了这个发出者才收到。
- agent 给的标识与替换键在交给本组之前按发出者加前缀：两个 agent 取同一个名字互不相干。同一个标识再发是认回。
- 本组的拒绝、依据不可用、结果未知在工具里都是失败的结果，写明原因与该怎么办；不写成一行成功的文本。读抛出算依据不可用，写抛出算结果未知。
- 订阅遇到「要 owner 确认」时出一张卡并挂起，留存这次请求与卡的标识。同意后带着这次调用、这张卡的引用重提，订阅的依据就是它。不同意、文字答复、没答、答的是别的卡，都不写。留存的状态读不出、过大，或和重提的请求对不上，重提被拒。

## 原则与约束

- 入箱才算送达。投递的结果不改送达。
- 给谁、多急归收件人。来源的强弱只是缺省。
- 通知不制造工作：不调模型，不生成内容，不重做来源的动作。
- 状态经 Runtime Context 知道，事件经发送知道。读不到不是没有。
- 结果不知道就是不知道。按原请求核对，不换身份重发。
- 资格每次现核；登记了、装了工具都不等于获准；收件人只在本租户。
- 本组不认识任何具体的来源、事件类型、渠道与块，也不认识会话。
- 谁的事实谁写：通知、订阅、投递单元只有本组写；合并与节拍的规则是纯函数，不写它们。
- 策略类的值是配置，配置不能减弱上面任何一条。

## 不变式

| 编号 | 永远成立的性质 | 违反的后果 | 由什么守 |
| --- | --- | --- | --- |
| INV-NO01 | 送达只认收件人随时取得回：一次性事件在收件箱，持续事项在来源自己那里。投递的结果不改送达 | 只弹过一次提示就算送达 | 只有文字 |
| INV-NO02 | 答了已接下，每个收件人的通知已在箱里，是同一次提交 | 答了接下的通知丢失 | 模型 `NotificationHandoff` 的 `AcceptedIsBoxed` |
| INV-NO03 | 一个发送身份对一个收件人至多一条通知；同身份不同内容是冲突 | 重复的通知 | 模型的 `OneNotificationPerRecipient` |
| INV-NO04 | 结果不知道保持未知，按原请求认回 | 盲目重发出第二份 | 仓储契约用例；接入插件与工具里「结果未知后原样再送」的用例 |
| INV-NO05 | 给谁、强弱、缘由、备注在接下时定下，之后不回头改 | 改订阅之后历史通知的归属变了 | 只有文字 |
| INV-NO06 | 了结之后系统不自己恢复；被顶替的不能恢复；同一收件人、来源与替换键至多一条没了结的 | 办完的事又冒出来；一个键两条活的 | 模型的 `OneLivePerKey` |
| INV-NO07 | 通知只进目标租户里的收件箱，送不到不改投 | 通知到了同一账号的另一个组织 | 仓储契约用例里两个租户互相读不到的一组；接入插件里别的租户读不到、别的租户的变化不出帧的用例 |
| INV-NO08 | 处置与投递的失败不改来源的任何事实 | 划掉「作业失败」，作业变成没失败 | 只有文字 |
| INV-NO09 | 本组不调模型，摘要机械合成，恢复不重做来源的动作 | 一条通知多花一次模型调用 | 只有文字 |
| INV-NO10 | 每个操作按当前资格现核；登记与装配可见不授权 | 未获准的披露或发送 | 只有文字 |
| INV-NO11 | 只有来源交来的事件形成通知；本组的投递失败不产生通知，只成为一件持续事项 | 通知风暴 | 只有文字 |
| INV-NO12 | 持续事项只有一份，归来源；本组不保存它开着没有，没有了结它的操作；提醒不算答复 | 卡答了面板上还挂着；提醒失败被当成答复 | 只有文字 |
| INV-NO13 | 读块得到拒绝、缺项或未知时不当成没有 | 来源读不到时显示「没有要处理的」 | 只有文字 |
| INV-NO14 | 一个投递单元在一个会话里至多一条输入；一条强通知至多进一个强单元 | 同一件事叫醒 agent 两次 | 模型的 `OneInputPerUnit`、`OneUnitPerStrong` |
| INV-NO15 | agent 的每条订阅有 owner 的同意作依据；agent 不能给自己同意，不能替别的收件人订；同意不回头 | agent 自己订一堆事件 | `decideSubscription` 的用例；工具里同意卡的用例 |
| INV-NO16 | 通知不带授权；外部内容投给 agent 时做数据标记 | 外部内容被当成指令 | 只有文字 |
| INV-NO17 | 没有该提醒的，这一拍不形成单元，不产生提交与投递 | 空的节拍花模型调用 | 模型的 `NoEmptyBeat` |
| INV-NO18 | 节拍的单元带这一拍的时刻之前入箱的全部该提醒的；没了结的不会无声消失 | 要办的事没人办 | 模型的 `BeatCarriesAllLive` |
| INV-NO19 | 一个去处两个强单元之间不小于最小间隔；间隔内的强通知排队，不丢 | 吵闹的来源让 agent 不停地醒 | 模型的 `StrongPaced`。「最终被投」没有模型守 |
| INV-NO20 | 核心域的成员不依赖本组；去掉本组，核心与人工介入原有的流程不变 | 通知故障带坏对话 | 依赖方向 `DIR-CORE-NOTIFICATION`：Session、Agent、Model、Tool 四组里登记了的成员导入本组任何成员都变红。Runtime Context 与 Request Context 的成员没有登记成角色，这条规则盖不到 |
| INV-NO21 | 本组的定义成员里不出现任何具体来源、事件类型、渠道、块键的名字，也不依赖会话 | 每加一个来源都要改通知 | 依赖方向 `DIR-NOTIFICATION-OUTWARD` 与 `DIR-NOTIFICATION-PURE`；契约与定义两个成员各有一条用例，只许导入白名单里的包 |
| INV-NO22 | 来源或渠道撤下后：新的不接；已入箱的可查可处置；订阅保留；在途的投递有确定的结局 | 卸一个插件，历史读不出 | 只有文字 |
| INV-NO23 | 目录是按当下登记现算的视图 | 新装的来源看不到 | 只有文字 |
| INV-NO24 | 本组自己的来源、渠道与持续事项走和别人相同的登记与契约 | 内置的能做别人做不到的事 | 只有文字 |
| INV-NO25 | 发出事件的收件人收不到它；因果深度超过上限的事件被拒收 | agent 自己或互相叫醒，停不下 | 只有文字 |
| INV-NO26 | 期限到了的订阅不再命中；命中一次就撤的在命中的那次提交里到期 | 只等一次的订阅一直叫醒 | 只有文字 |
| INV-NO27 | 通知、订阅、投递单元只有本组写；合并与节拍的规则是纯函数 | 换一种投递的规则要连事实一起动 | 只有文字 |
| INV-NO28 | 一条通知推到几个去处仍是一条，只入箱一次；一个去处的结果不改别的去处 | 加一个去处，箱里变成两条 | 只有文字 |
| INV-NO29 | 出系统的载荷按披露资格裁剪；完整内容回来后重新核资格 | 私有内容随外部投递离开本机 | 只有文字 |
| INV-NO30 | 投递单元的成员与内容在形成时定下，重投不变 | 重投的内容和第一次不同，会话答冲突 | 模型的 `OneUnitPerStrong`（成员部分）；内容不变只有文字 |

模型 `NotificationHandoff` 在 `notification/verification/`。它是有限模型，只验安全性；范围与没有覆盖的东西写在 `models.json` 的 `scope` 里。
