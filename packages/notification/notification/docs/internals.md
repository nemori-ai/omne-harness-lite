# 通知内部机制候选

本页保存尚待技术采用的设计，不表示实现、产品接受或阶段承诺。完整必要行为见[notification/notification SPEC](../SPEC.md)，产品范围见[产品正文](../../../../.meta_harness/design/product/notifications/design.md)。

## 身份和状态维度

每次请求分别带业务归属、发起者、明确目标租户、允许披露的来源与给定内容。目的地不改源业务身份；查询授权与发送授权分开。来源可能无 Schedule/Job，也可能是其已选实际事件或等待/维护事项。原请求、源事件、通知、尝试及投递之间的精确关系、标识和存储布局未定；本稿不选择幂等键、数据表或公共枚举。

| 事实维度 | 能证明什么 | 不能代替什么 |
| --- | --- | --- |
| 拒绝或尚未受理 | 当前已知准入结果；超时仍可能未知 | 未获回执不能证明从未发生 |
| 已受理 | 通知方可靠保管本次交付责任并可定位 | 实际发送、送达、源工作成功 |
| 发送或尝试 | 该提供者实际已知动作及未确认部分 | 目标持久可取回 |
| 送达可确认 | 正确目标范围持久可取回的证据 | 呈现、已读、源整体完成 |
| 呈现/取回/已读 | 各自实际取得的事实 | 默认已读推断或新增源读权 |
| 源终态及整体结算 | 源拥有者的实际事件和规则 | 通知层擅自将失败洗成成功 |

这些是分别成立的逻辑事实，不是一个从左到右必然推进的单值状态机。失败、未完与未知按可确认范围表达；未知结果可能后来确认为已发生，不以超时、重试耗尽或实例撤除把它改为从未发生。


## 受理、持久事实与交接

入口先解析显式身份和内容，再取得当前准入/披露判断。在真正发生外部披露的边界复核会失效的资格，不把旧授权快照当永久许可。查询也取当前资格并裁剪可见字段，不能泄露另一租户是否存在私有通知。源已提交事件与通知承接属于不同结果；可靠承接之前源方保管待交付责任，之后通知方保管，同一交接不得有无人负责的窗口。

受理记录、内容、目标、源关联和未完责任必须在对外声称可靠受理时一致可恢复。确认送达又必须对应正确目标的持久可取回事实；不能先写“已送达”再盼目标提交成功。目标提交已发生而回执丢失时保管未知，按原请求核对。单机的提交及跨协调边界的承接需实际机制兑现；本稿不指定网络与数据库同事务，不强制 outbox 或已接受幂等键。Q-NO03 须以故障和并发反例补齐精确方案。

读面、实时呈现、诊断和事件通知源于同一业务事实，不另造一套交付真相。读面滞后说明新鲜度；提交后的监听/投影失败不把受理或目标提交改写为未发生。源业务完成与通知完成的组合不由事件派发顺序自动成立。


## 并发、取消和恢复

重复源告知与提供者技术重试必须对应原逻辑意图；不同的主动发送意图不能因为内容相同就合并。源事件取其拥有者已接受的实际声明，未选或未发生事件不适用。并发尝试、晚到回执、资格撤销和发送前取消在明确提交/效果边界归并，不能一边确认送达、一边因取消抹掉实际效果。若无法证明重试安全，保管未知并交技术处置，不制造独立新通知求进度。

仅对源允许的发送前取消承诺阻止发送。发送已发生或未知不能承诺外部撤回；取消源执行仍保留此前通知及声明命中的取消通知。停止等待和撤除实例不自动取消业务。恢复只核对原请求、目标事实和取消竞争，接续未完交付，不重做源动作、抓数、生成内容或递归触发执行失败通知。


## 可替换提供者与 Cordis 投影

定义拥有者在未来真实成员中就近维护一个能力接缝；根入口与 Cordis 无关，集成入口沿 IC-1–IC-5 引用同一定义。消费者依赖公开契约，不引用选定后端；IC-18 显式身份与领域授权仍分别核对。业务通知与 IC-10–IC-12 的事件派发分开；emit/parallel 的监听者或广播成功不能当成租户持久送达。已提交后的监听失败保留诊断和未完反应责任。

必要依赖按 IC-8 装配，局部依赖放局部 fiber；可选依赖按 IC-9 在调用时取得，缺席给出真实支持限制。配置按 IC-14 验证，错误拒绝加载；重试、退避、超时、限流等值由合法配置拥有者选定，不在本稿写死。具体通道是否能保证目标身份、披露、可取回和可确认性须独立证明；不能用弱回执把不支持状态升级为送达。

停止准入、处理在途、保管未知、可靠移交，再撤除实例贡献。清理只撤自己的登记/监听/资源；持久通知历史和在途责任不依赖单个 fiber 存活。旧引用处置与晚到结果沿原请求归属，能力换代不抹掉旧语义，也不能用新配置改写原内容/目标。采用点、跨实例竞争和资源释放由 Q-NO03/Q-NO04 的精确方案承接。第一版单机不宣称目标事务或进展由 Cordis 自动保证；以后跨进程仍由协议兑现同一语义。


## 后续技术采用

下列事项是技术采用义务，不要求产品负责人选择数据库、协议或 provider。行为目标沿 [SPEC](../SPEC.md) 保持。

<a id="q-no02"></a>

### Q-NO02 请求、通知、尝试与投递身份

一次send请求可查，重复源告知和恢复辨认同一意图，但精确对象关系待裁。 技术拥有者怎样接受身份关系、生灭、公开定位形状及安全关联？

一次请求及结果可定位；重试不产生独立用户通知。

归属/发起者/目标/来源分别表达，不从工具名定Schema。

- 先定消费者单位和关系。沿已定行为推导公开形状，更新对象及统一语言。
- 比较技术分解候选。用同内容独立意图、重复事件、多尝试和晚到回执反例筛选，再接受形状。

保持行为，技术拥有者裁定；本稿不选标识或幂等键。

公开类型和防重复实现不能凭此候选定案。

技术拥有者为通知公开定义与领域对象/统一语言维护拥有者。

<a id="q-no03"></a>

### Q-NO03 可靠承接、确认及未知恢复

源已提交、通知承接或目标提交回执丢失，同时存在重复、取消及撤权竞争。 精确方案怎样保护提交/交接并证明故障及并发下安全继续？

受理时原内容/目标及责任可恢复，承接前源方保管。

送达须正确目标持久可取回；查询只读，显式恢复不重做源动作。

网络与数据库不假定同事务，不承诺所有通道恰好一次外部效果。

- 具名一致提交保护局部事实。说明参与对象、故障切点和仍需跨边界交接。
- 可靠协议保护跨边界承接。证明原身份、责任保管、重复归并及未知核对，不能仅凭调用顺序。

沿实际协调域接受机制及故障/并发证据；不强制outbox、Schema或恢复API。

实现接受前补V-NO05/08/12–15，完整语义保持。

技术拥有者为通知协调者、源业务协调者、目标交付及实际存储拥有者。

<a id="q-no04"></a>

### Q-NO04 提供者、配置采用及生命周期

提供者换代、目标离线或依赖缺席，策略改变但旧请求未完；旧CLI/TUI不代选新通道。 怎样接受具体支持、回执/目标核对、配置生效及在途接续并持续验证？

提供者保持目标资格、可取回及真实查询。

停止/disposer不撤回效果、不删历史，旧引用/在途/未知有归属。

参数可配置，不擅定通道、阈值或时限。

- 依支持范围分批接受。每个提供者证实判据/生命周期，不支持如实返回。
- 先补可替换组合验证。明确共同接缝、旧引用和在途责任再验证后端。

技术及装配拥有者落实机制，阶段通道仍归Q-NO01；不钉死参数或宣布新通道已支持。

V-NO15–18须有实际提供者及组合证据。

技术拥有者为通知定义/提供者、合法配置与装配拥有者。
