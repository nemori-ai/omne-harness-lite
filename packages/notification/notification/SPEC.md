# notification/notification 长期行为候选

本文件维护具名文档目标的完整必要行为。文档目录不成立真实 workspace 成员、公开形状、发布版本或运行能力。整体产品及技术采用尚未接受；阶段清单未选，实现与行为验证未核实。产品范围见[产品正文](../../../.meta_harness/design/product/notifications/design.md)，精确协作、机制与技术缺项见[内部设计](docs/internals.md)。本文件不重复未来公开类型，也不以机制未定取消已明确的行为。

## 责任、消费者与前提

通知定义拥有者对系统、agent、源业务协调及应用读面承诺给定内容的交付、一次请求的真实查询和未完责任。发送与查询分别接受显式身份及资格。通知不要求 Schedule、Job 或 agent 会话存在，不生成内容、不执行源工作、不决定源整体结算。普通回复、成果上报、运行时唤醒、复制邀约及 Cordis 事件派发保留各自含义。

业务归属、发起者和目标租户分别明确。租户为组织/账号共同身份；源事件与发送意图可辨认。对外可靠受理时，原内容、来源、目标和责任必须可恢复并可继续查询。查询使用一次请求的定位信息，但具体类型、通知/尝试/投递身份、相关性及幂等表达未定。不能从术语或工具名推断数据表、公共枚举或通知就是会话消息。

提供者声明具体支持范围、当前配置、效果边界、送达证据、未知核对及资源责任。装配、源方和目标方要具备实际承接及持续运行条件；资格不足、目标不可用或支持缺失时给出明确事实，不能以目录或注入可见性授予操作。正常进展以前述条件及有效治理成立为前提，不承诺固定时限或跨所有故障的无条件成功。

## 可检验不变式

### INV-NO01 独立发送而不制造源工作

系统或 agent 可以在授权下发送给定内容，无须 Schedule/Job/会话。纯通知不启动 agent 生成文案、不发起分析、不借恢复重做源动作。普通回复和成果上报不能替代通知，成果提交不隐含额外 send。验证义务 V-NO01。

### INV-NO02 业务归属、发起者与目标不混同

一次请求分别保持业务归属、实际发起者、明确目标组织/账号及适用来源。相同账号的其他组织身份不是目的地；不得自动改投。系统业务、租户业务或通知目的地互不改变原业务归属，不能借系统身份读取或披露租户私有资料。验证义务 V-NO02。

### INV-NO03 当前操作资格与原授权分开

发送准入、跨租户传送、目标接纳、查询及字段披露各按实际边界所需的当前资格判断。装配工具、持有服务引用或指定目标不构成授权。默认拒绝未获准的跨租户访问；实际披露前复核会失效的资格，查询按当前权限。资格撤销与发送竞争不能产生未获准的披露；已发生效果仍如实记录，失权不抹历史。验证义务 V-NO03。

### INV-NO04 通知不扩大源信息访问

内容、来源引用和诊断只披露获准字段。允许目标收到某条通知不授予完整源历史读权，也不允许枚举其他租户私有通知的存在性。无权结果依正式安全边界拒绝或裁剪，不向无权者展示私有内容以解释拒绝。复制邀约、等待事项和维护风险的访问规则由原拥有者判定。验证义务 V-NO04。

### INV-NO05 可靠受理必须同时保管责任

成功受理的原内容、目标、来源关联及未完责任在对外确认时一致可恢复；不能只返回成功再异步补保管。源方直到通知可靠承接前保管待交付责任，通知可靠承接后继续保管，同一交接不能出现无人负责的窗口。回执丢失时依原请求核对，不能依据调用失败推断未受理。已提交源事件不因交接失败而回滚或重做。具体提交/交接机制由 Q-NO03 兑现。验证义务 V-NO05。

### INV-NO06 送达须有正确目标持久可取回的依据

只有已确认通知在明确目标租户范围内持久可取回才报告送达；内容、目标和送达证据必须对应原请求。发送、渠道受理、事件广播、一次显示或在线状态不能独自代替该依据。目标提交未确认时表达未完、失败或未知的实际范围，不先写送达再补目标事实。离线不使已送达通知丢失；呈现、取回和已读分别成立，无已读证据只说明未确认。验证义务 V-NO06。

### INV-NO07 一次请求的可查询单位已定

消费者能按一次发送请求定位原内容、允许披露的来源、目标、已知交付结果及未确认部分。查询只读，不创建通知或源工作；读面滞后说明新鲜度，不把缺投影当未发生。精确对象身份未定不取消这一单位或责任。不同意图不因为内容相同就合并。验证义务 V-NO07。

### INV-NO08 技术继续不成为独立新通知

同一请求的重试、恢复、重复源告知或提供者换代保持同一逻辑通知及原内容/目标/来源语义，不产生多份独立用户通知。另一次主动发送须有新的业务意图，不能充当旧请求恢复或配置义务完成。原意图的辨认和防重复机制未定，不能擅定幂等键；没有安全证明时不得通过盲目重发获得进展。对外通道不可撤回或无法确认时，保管未知而非宣称恰好一次外部效果。验证义务 V-NO08。

### INV-NO09 源实际已选事件才形成通知义务

Schedule/Job 拥有接受时固定的事件、内容和目标声明。开始、成功、失败、取消只有已选且实际发生才触发，每个 Job 的一个已选事件对应一次逻辑通知；等待不当开始，未知不当失败，未命中不适用。后改 Schedule 不改已接受 Job 的要求。通知层不推断事件、不添加默认事件，不因通知发送失败递归生成执行失败通知。验证义务 V-NO09。

### INV-NO10 源执行、交付与整体结算分别成立

通知只返回真实交付事实。源协调方决定工作及组合终态，通知不把源执行失败或取消洗成成功，不把已受理、尝试或已读当整体完成。源方的有效组合成功要求仍由其拥有；通知未送达不能由 agent 主动另发、成果提交或客户端呈现冒充完成。恢复交付不得重做源机械动作或 agent 工作。验证义务 V-NO10。

### INV-NO11 等待与维护提示不改源事实

人类介入的无限等待必须让有资格的人知道事项等待，不能只靠人自行寻找池子；合格入口显式呈现本租户待办并持续保存也是有效方式，不要求额外业务 send 或带外通道。实际形成合法提示通知时才沿本域交付。通知失败/未知不生成答复、不解除等待、不授予写权。日历维护提示只承接获准披露的来源和状态；提示受理、送达及已读与发布、风险、健康分别观察。提示失败不清风险、不改已提交发布、不重抓源数据或铸造版本。源完成后已发通知仍按实际事实查询，不承诺撤回。验证义务 V-NO11。

### INV-NO12 取消按实际效果边界结算

对源允许的纯通知发送前取消，取消取得有效资格且在发送前获胜时阻止发送。发送已发生或结果未知时不承诺撤回，不把未知改为取消成功，也不因取消重发。源执行取消仍按原声明判断取消通知，并保留此前已经触发的交付责任；源执行已终结不能借取消清除未完通知。晚到回执保有原归属。停止等待、断开连接或 disposer 均不自动取得业务取消效果。独立通知取消 API 不在本候选中选定。验证义务 V-NO12。

### INV-NO13 未知必须先核对原工作

超时、进程退出、回执丢失、查询读面缺失和重试耗尽均不单独证明未发生。恢复保管原身份及未知，优先核对通知权威事实及目标实际效果。已确认送达恢复原结果；原责任方显式发起继续并获有效准入、且可以安全继续时只续原未完交付；只读查询不能触发该发送分支；不能确认安全时如实保持未知、说明限制和处置拥有者，不宣称失败即无效果，不重做源动作。验证义务 V-NO13。

### INV-NO14 并发归并须保持同一事实

并发受理、重复源告知、多个技术尝试、晚到回执、取消和资格变更在具名提交/效果边界核对。一次逻辑意图不能被拆成独立通知，实际送达不能被过时的失败/取消投影覆盖；每个结论保留它确认的范围。内容、目标、来源和确认依据一致，投影/监听失败不倒写已提交结果。跨协调边界可靠承接与单机一致提交分别由实际机制证明，不能凭调用顺序、两个局部成功或广播通过推出。验证义务 V-NO14。

### INV-NO15 生命周期与采用点不抹业务

提供者明确装载、停止准入、在途处置、实际停止、撤除和资源释放。换代或依赖失效时原方在可靠承接前保管原身份/未知/责任，接续方核对原事实；无承接方不能伪装完成或删除。旧引用及晚到结果有归属。清理只撤自身登记/监听/资源，外部输出不可因 disposer 宣称可逆。配置或能力版本采用点须明确，不能用新配置重写已接受内容、目标和源事件声明；公共历史不依赖实例存活。验证义务 V-NO15。

### INV-NO16 历史、观察与诊断保持边界

通知业务历史按目标租户隔离保留并可查询，不因源终结、归档、失权或实例卸载自动删除；查询仍验当前权限。历史索引和物理归档优化不得缩短有效业务保留及可查询范围，具体存储机制由数据及业务拥有者维护，本稿不设置 TTL。呈现、实时推送和诊断源于原事实并保留可披露的因果/来源定位、结果新鲜度及未知，不形成第二权威。诊断输出自身遵守租户和内容披露资格。验证义务 V-NO16。

### INV-NO17 扩展提供者仍兑现同一承诺

框架允许可替换交付与呈现提供者，但具体通道/提供者的接受和支持范围需独立确定。不因旧 PF 的阶段通道限制代选新阶段，也不把解除排除当作新增产品支持。每个已采用提供者证明明确目标、披露资格、持久可取回、查询/回执与外部副作用责任；弱回执不能升级为送达。不支持或缺席明确报告。Cordis 只投影装配和生命周期：唯一接缝定义、纯根入口、依赖隔离、事件失败及显式身份按 IC-1–IC-19；数据授权与领域责任不能由内核可见性替代。验证义务 V-NO17。

### INV-NO18 进展及配置前提须可见

发送和恢复在有效资格、合格目标、持续提供者、保管责任和有效策略成立时取得相应进展。重试、退避、超时、限流等参数属于合法配置；配置缺失/无效及依赖缺席明确拒绝或暴露限制，不能静默选通道、参数或收件人。策略停止继续尝试不清除已发生效果或原责任，不把未知变成无效果失败。具体进展时限和重试机制尚未接受，不以固定数字或无限自动重试补空。验证义务 V-NO18。

## 失败、取消与资源责任

准入拒绝不给交付成功承诺，但已经发生或未知的效果仍须如实核对。目标不可用、授权失效、存储/提供者故障、回执丢失、读面滞后及配置缺席分别保留实际范围。失败不是统一的“什么都没做”。已受理责任由通知保管，源方在承接前保管；换代承接前旧方保管。安全取消不依靠资源释放证明，资源释放也不代表业务终态。

目标持久事实与发送方确认可能处于不同提交域。本候选要求一致可辨认和可靠接续，不承诺一个覆盖外部网络的事务。Q-NO03 补机制及故障证据，Q-NO02 补公开身份形状，Q-NO04 补提供者、配置采用及生命周期证明；实施须待具体方案和支持范围被接受。

## 持续验证义务

下表是必须保存的验证义务和责任，不是已经运行的结果。真实提供者、源消费者及应用组合须留精确版本、输入、前提和未覆盖；类型、图或 mock 不证明整体符合。

| --- | --- | --- |
| V-NO01 独立发送 | 系统/agent 无Schedule/Job/会话发送；纯通知不启动工作；成果提交不另发 | 定义、源、工具 |
| V-NO02 身份分离 | 同账号不同组织、系统来源发给租户、目标变化不改源归属 | 通知、身份 |
| V-NO03 资格边界 | 跨租户默认拒绝；发送/查询分权；准入后撤权与披露竞争；装配不给权 | 通知、授权、目标 |
| V-NO04 披露 | 获准提示不暴露源历史、诊断/引用裁剪及私有存在性负例 | 披露拥有者、应用 |
| V-NO05 受理保管 | 原方提交后通知拒绝；受理记录/责任/回执各处崩溃，任何切点无人保管的负例 | 源、协调、存储 |

| V-NO09 事件声明 | 各事件已选/未选/未发生，等待/未知，Schedule后改不回写Job，通知失败不递归 | Schedule/Job、通知 |

| V-NO13 未知恢复 | 目标已提交回执丢失、进程/OS退出恢复；核对原身份、禁止盲重发或源重跑 | 协调、目标、存储 |
| V-NO14 并发提交 | 多尝试、重复源告知、晚到失败覆盖送达、取消/撤权竞争、监听失败不改提交 | 协调、源、目标 |

| V-NO16 历史观察 | 源终结/失权/归档不自动删；当前资格读历史；读面滞后、因果定位、诊断披露 | 通知、存储、应用 |
