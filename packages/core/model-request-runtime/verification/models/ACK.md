# ACK行为模型与有效性

本模型只抽象模型请求ACK、日志确认与原账的跨提交关系。Calls两个、Consumers两个，Focus一个调用参与交错，另一调用作为独立内容保留对照；只AckConsumer可准备确认。模型从真实terminal+ready前提起步，不覆盖终态推导或真实权限来源。原call/key/digest字节未建模，不登记创建幂等/密码学覆盖。

AckLifecycle.cfg检查AdmissionClosed（关闭后无新read）、WriterDrained（删除前实际旧writer停）、AckBeforeDelete（ACK确认先于删除）、AtomicDeletion（内容与released同提交）、ReadProtected、OtherCallUnchanged、RetainedIntegrity、RecoverableBatch、OldRefVisible、OneAccount。validity-check/Ack-{admission,drain,ackFirst,atomic,tamper,temporaryBatch,missing,sum}.cfg分别松开一个相关守卫或投影，必须得到对应反例；不是无反例通过。ReadProtected/OtherCallUnchanged无独立负控，不扩大覆盖为所有外部资源安全。

存在ACK append未提交/提交但未知回执，停止ACKwriter后同源读回确认；没有日志commit则可重试。模型固定原批标识，不证明实际原批字节相等。原晚writer可先/后形成final，新的自持结果结算与旧模型副本清理独立。temp为本次完整原批耐久占位；新writer不停止则不可清，结束后自动丢弃；非法回送可在tamper变异落final，使完整性断言失败。原账仅一个抽象单位；优先选一次与误加反例可失败，但不证明原Cost数值相等或补账算术。

AckProgress.cfg使用FairSpec：一个可选crash后恢复公平，ACKwriter/原writer/实际reader最终停止、确认与删除公平；新writer/结算结束与临时清理公平。存储可用抽象为up，最多一次crash，恢复后可用。EventuallyReleased只承诺已durable ACK最终released，不能据此声称用户必然发ACK；EventuallyDropTemp不要求consumer/后续处分继续。不以无限公平假定掩盖真实永不结束的外部owner。

单次执行的输入、日志、失败与判读放工作树tmp。修改输入后须区分原结果与新结果；未执行配置不得记为本次通过。
