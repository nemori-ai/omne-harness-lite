# 会话装配与独立执行

目标选择：B2。每Session独立Cordis Context，共享服务使用显式桥。此迁移未新增技术接受。

## B：动态会话装配

| 候选 | 兑现Q3／Q4 | 成本、敏感点与风险 | 采用判断 |
|---|---|---|---|
| B1 进程Context内每Session派生Context＋显式isolate／事件过滤 | Cordis effect收贡献，退出会话父fiber撤孩子；模型工具放外层执行池 | 派生Context本身不自动隔数据／事件，所有键及事件桥都需覆盖；共享root故障域更难检查 | 可行，证据齐全后可替换；不能称“子Context天然隔离” |
| B2 每Session独立Cordis Context，共享服务经绑定桥 | 动态贡献与事件域独立；每个Session宿主fiber整撤；实际模型工具放进程执行池，桥句柄退出只交还 | 显式跨Context桥需处理换代／准入／租户绑定；多Context成本需实测，不能隐式共享根ctx.get | 推荐。最直接表达IC-17；不要求独立进程或新领域scope对象 |
| B3 单Context会话协调者登记每个插件／贡献／执行句柄 | 每项带Session身份，撤除按所属句柄，外部池保工作 | 手动账本可动态，但每次新增贡献易遗漏过滤／清理，重复框架effect；撤除与故障组合维护代价高 | 在框架不足时备选，现有Cordis足够承载登记，不先自建通用scope内核 |

B2对Q1／Q2：依赖相同Session持久协调接口，Context退出不等于删除历史。对Q5：恢复协调器在进程root，无Session Context时也能扫描。对Q6：投影缓存属于数据／纯计算侧，不绑定Agentfiber，撤除只释放该消费者句柄。


复核条件：实际桥撤除会取消原调用，或资源开销不可接受时，按同样隔离和连续性场景重评。不能以子Context名称推断隔离。
