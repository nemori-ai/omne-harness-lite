# Human Intervention

## 总体架构

Human Intervention（人工介入，HITL）包组回答一个问题：一件工作走到需要人决定的地方时，怎样把这个请求和原来的工作关联起来，交给有资格的人看见，确认一个有效的人的处理，再可靠地交回原来等着的位置，而人工介入自己既不成为决定的权威，也不替原工作继续执行。

| 成员                          | 回答的问题                                                                                                                                              |
| ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `human-intervention`          | 公共协议 `hitl/1`：请求、卡片、答复、操作身份与原等待引用的值；命令、查询、恢复与提交协调的接口；边界解码；卡片的纯决策函数。不依赖 SQL、Node 或 Cordis |
| `human-intervention-local`    | 单机 SQL 提供者：原操作终态与封口、请求与卡片的共同提交、独立原等待（WaitOwner）、Identity 资格协调、按资格的查询与池、恢复与交接的应用入口             |
| `human-intervention-protocol` | 公开协议 `human-intervention/v1` 的协议契约：卡的列出、读出、答复的提交与认回四个操作，与卡有变化的观察 `observe-cards`。纯数据                          |
| `human-intervention-access`   | `human-intervention/v1` 的接入插件：核对登录与租户、取入口主体、搬形状、映射结果                                                                        |
| `human-intervention-ui`       | 界面模块：决策池页、会话里的卡、导航上的张数，三处读同一份卡的存放；提交人的答复，结果未知时认回                                                       |
| `human-intervention-tool`     | 给 Tool 的端口适配：等人决定的请求契约包成 Tool 的等待契约。工具作者交一批卡、读回每张卡的答复都用它                                                   |

原工作（Tool 的调用、Agent 的放行或扩展轮次）先固定问题、动作与原等待位置，再以一次原操作登记请求；请求、卡片与原等待的有效关联在一次提交里同时成立。人从会话入口或待办池读到卡片，提交答复；协调者裁定唯一的有效处理，把决定与原等待的答复箱在同一次提交里写下。原等待当前代次的接收者从答复箱读决定、接手并记下消费回执；之后原拥有者自己判断能不能继续。提示的送达交给 Notification，与答复无关。

## 领域边界

本组拥有：请求与卡片；人的有效处理（决定）及其提交依据；请求的读者与答复者受众；待办池投影；决定交到原等待的交接状态。单机提供者另外拥有独立原等待的保管：准备记录、接收代次、终局、答复箱、消费回执与待接手集合。

本组不拥有：原等待的含义、批次屏障、继续位置与业务终局（原 Tool 或 Agent 的协调者；会话的业务控制归 Session）；批准的含义、许可与消费（Authorization）；租户持久权限设置（Settings 与权限规则的拥有者）；主体发行与成员资格（Identity）；提示的受理与送达（Notification）；会话入列与推进（Session、Agent）；实际执行与外部效果。卡片是查询与呈现的视图，不是新的主体，也不是第二个决定权威。

## 心智模型

把人工介入想成一个挂号窗口加一个寄存柜。原工作拿着自己的等待号来挂号：问题、动作、参数和「答复送回哪里」都在挂号时定死。人在窗口前只能交一次有效的答复；答复和「送回哪里」一起锁进原等待的寄存柜，之后谁来取、什么时候继续，是原工作自己的事。窗口不解释答复的意思：同意不同意、算不算授权，由接手的原拥有者按它自己的规则读。

等待是一件可以无限期存在的耐久事实，不是一个挂着的 Promise。进程退出、界面关闭、没人看都不改变它；运行时换了实例，等待号不变，只是领取人的代次变了，旧代次不能再领。等人的时候不占执行名额、写事务或跨调用的锁，别的工具调用与别的会话照常前进。

最容易想错的地方：保存了答复不等于原等待已经接手，接手不等于动作已经执行，执行也不等于授权已经生效，这几件事分别确认；结果不知道就按原操作身份查，查无记录不是未提交；没有人回答就没有答案，时间、通知或系统都不能替人回答；原工作终局之后卡片失效，但已经成立的历史决定保留。

## 应然设计

### 请求的身份与登记

- 一次请求固定可信租户、来源（Tool 调用、Agent 放行轮次、Agent 扩展轮次）、原工作与原等待（`WaitRef`：拥有者、等待身份、继续实现的代次、目的地）、消费位置与采用依据。动作类请求另固定原动作、生效参数摘要、实现与授权依据。恢复与界面换代不暗换这些关联；运行时对象与闭包不进入数据。
- 请求、卡片与原等待的有效关联在一次提交里共同成立；任一参加者失败全部回滚。准备材料只固定原登记调用、受众与相容实现，不是有效人工等待。对同一等待换操作身份重新登记被拒绝。
- 来源的组合是封闭的：Tool 来源必带调用引用；放行来源可带调用引用；扩展来源不带；带运行引用必带会话引用。
- 系统确定需要问人、却确定生成不出有效卡片时，相关动作被拒绝且不执行，原协调者把准入故障与真实原因交给原 agent，并以合法可见的方式告诉人；不伪造人的拒答，不建立等待一张不存在的卡的人工等待。保存结果未知不是生成失败，按原操作身份查询。

### 卡片与答复

- 要等人决定的工具按本组的等人决定契约交出请求、读回答复：请求是一批本组的问询卡片，答复按卡给出选项、原话或没有答案。这条契约只用来向人要信息或选择；工具不经它问许不许，答复不产生授权。卡的形状与答复的种类只在本组定义，工具作者与应用的桥都不另写一份；不合契约的请求在登记之前被拒绝。每张卡写什么、选项对出卡方意味着什么，由出卡的原拥有者决定。
- 每张卡都允许不选任何选项而独立提交原话，也允许跳过（decline）；界面总是给出这两项。选项可以带出卡方给的角色：准（`approve`）或驳（`reject`），没有就是不带；本组照存、照交，不解释，也不拿它判断任何事；界面只用它定钮的字形与语气。系统放行卡的出卡方给不放行的两档驳、放行的三档准。<!-- OD-35 -->
- 每张卡记下登记的时刻：本组登记这批请求时从注入的时钟读一次，同一批的卡是同一个时刻；随卡保存，读卡时原样交出，不重新计算。时钟读不到或读出的不是 UTC 时刻时照常登记，这批卡不带时刻，读出时与旧的卡一样缺这一项：时刻只帮人读，不挡人的决定。<!-- OD-37 -->问询的每个问题有描述与至少一个文本候选，图解可选且不替代文本。系统放行卡不要求先选授权档位。每张卡必须写明跳过的后果，由出卡的原拥有者填写。
- 卡按种类各有一套形状，种类只有三种：问询、系统放行卡、拓展件的卡；来源只有三种：工具、系统准入、拓展件。每一种在产品里都有产生者，没有产生者的种类不留在契约里。系统放行卡有自己的形状：动作的目标、调用的标签（工具名、命令、动作预览）、生效参数的全文或有界的截断加摘要、发起的会话与 Agent，动作所属关口给人看的名字，出卡方给的选项，以及两项可选的：放行详情；有持续效果的选项所管的关口与出卡时它的依据，本组照存、不解释、界面不显示。每个选项带一行作用范围的说明，并由出卡方标明它现在给不给得出、效果是不是只管这一次。给不出的选项照样画出，答不进来。选项的标识是出卡方的封闭集合，本组不解释它们的含义。
- 放行详情是出卡方交来的数据，本组只核外形与大小，不认识它的任何种类。它带一个状态（给出，或给不出）、一列条目，以及可选的带种类的值。条目是（标签，值），值是一段文字或一列文字；给出的详情必有条目。带种类的值是（种类，一段 JSON 文本），种类带主版本。没有这一栏表示出卡方没有可给的详情。详情随卡的登记保存，读卡时原样交出，不重新计算；提供它的能力撤下之后，卡照样读得出。
- 答复只有三种：选择一个选项、一段原话、跳过；没有超时或自动答复分支。拒绝动作是一个明确的选项，与跳过不同。
- 本组只保存原话与选择，不解释准驳。接手者用自己的结果词汇解释：问询的跳过是这一题「没有答案」，问询的任何答复都不是许可；放行卡的原话交原准入与授权拥有者解释，提交本身不批准动作，也不写持久授权；扩展卡的原话交原扩展件解释，扩展件只能收紧，不能放宽。
- 卡片状态只有待答、已决定、已失效。已决定的卡另有交接投影：待接手、已接手、已被取代。部分完成、提交未知与查询不可用另保留已知范围，不强行映射为待答或已关闭。

### 唯一的有效处理与共同提交

- 一张卡至多一个有效决定。两个入口、多个客户端、答复与失效的竞争由原等待协调者在同一排序边界裁定，不因两次独立的资格检查都通过而确认两份决定。
- 共同业务单元包括：卡片的有效决定、原等待收到它的耐久答复箱项、原操作终态与待交接责任。只有这个单元确认成立，原消费位置才拿到可消费的决定。保存明确失败答真实失败；保存未知沿原卡片与原提交身份查询，确认成立才进入消费，仍未知或查询不可用则保留原关联与下一次查询的责任。竞争入口的「已处理」或「冲突」同样以权威结果为准，前一提交未知时不先答已处理。
- 技术重传复用操作身份；人的新提交用新身份，即使文本相同。同一卡的另一提交答 `already-decided`，只有当前有读取资格的人能看到已有决定的投影。先核资格，再查去重回执，旧成功回执不泄露内容。
- 写操作的结果是封闭集合：成功、已决定、已失效、冲突、拒绝、非法输入、预算不足、不可用、未知。未知只表示提交可能成立，不返回新的操作身份。

### 原等待、终局与交接

- 原等待的有效状态与业务终局由原拥有者决定。原工作已终局、合法控制解除等待或会话归档生效之后，未答的卡失效并记下依据与原因，不再接收新的有效答复；已成立的决定保留，交接时结算为已被取代，不复活工作。运行时退出、交付面关闭或不可观察都不是终局依据。
- 带会话的来源，登记与答复必须在同一次提交里经 Session 的守卫核对原工作仍在进行；装配没有给出会话守卫时答不可用，空守卫清单不表示不适用。失效与交接确认不经守卫：失效正是原工作结束后要做的事。
- 守卫拒绝一次答复时，原工作已不在进行：卡片已有终态的，答复的人得到卡片的终态（已失效及原因，或已有的决定）；卡片仍待答的，答冲突（守卫拒绝）。守卫拒绝使整笔提交回滚；同一操作身份之后被封口，重试答「已封口」。
- 恢复按稳定目的地与等待身份进行。仍在等待的等待由原拥有者绑定新的接收者代次：比较预期代次，原子分配严格递增的新代次；客户端自报的代次不取得所有权。读答复箱与接手都要求当前代次，旧代次答 `stale-generation`。读取不确认接手，也不删除决定。
- 接手在一次提交里记下消费回执、增加回执计数、推进检查点并移出待接手集合；同一决定再次接手认回原回执。仍在等待的等待只在整批卡片都有耐久消费回执后才成为可继续。已终局且从未绑定接收者的等待，可由原拥有者按当前代次直接结算为已被取代，不建立接收者，不进入可继续。
- 交接确认（`acknowledgeDelivery`）只接受原拥有者保管的完整消费回执，不凭界面已读或新代次伪造。

### 资格、受众与披露

- 呈现、答复、查询、恢复读取与通知内容各自携带可信主体、租户、目标与用途，核对当前对应的资格；跨租户默认拒绝。共用账号、工作区、实例、缓存、名字或旧批准都不授新权。条件失效或不能确认时，依赖它的操作被拒，合法事实与未完成责任仍保管，不向无权方泄露内容。
- 受众在登记时由原工作拥有者固定。来源为 Tool 或 Agent 的卡：读者是出卡方自己与该租户入口主体，答复者只有该租户入口主体。于是这个租户的人用任何一次登录都能读卡与答卡，别的租户读不到也答不了，出卡方能读不能代答。当前成员资格在每次读取与答复时重核。
- 会话入口与待办池读同一张卡、走同一个提交，一卡一决、资格与守卫都相同；入口不改变机制，也不写进会话历史。会话历史只经原拥有者已有的路径写入一次。
- 每次写入与原操作查询先核验已签发主体、当前成员资格、所需资格与租户；原操作的 actor 必须等于该主体的稳定引用。写入只在提交期间短暂保留资格，等人期间不持有保留；已提交结果的重放也重核当前资格。目标端先封口时，迟到的原提交不能成立；提交先成立时，撤权保留历史结果，之后的披露仍重查资格。

### 查询与池

- 池列出有资格读者的待答卡，默认只列待人处理的；显式可查已答未接手与历史。池不另存决定权威。
- 一页在一个快照里读修订、目录键与卡片正文，按请求登记序号与请求内卡片顺序排列；游标签名绑定 actor、租户、位置、规范过滤条件与快照修订，修订变了答冲突，不把新旧内容混在一页。游标不是读取资格。
- 输出预算先耗尽答 `partial` 与有效续页；单项放不下答 `limited`，不截断原话；存储失败答不可用，不跳过故障宣称完整。
- 过滤带会话引用时是会话入口，只列来源带这个会话的卡；过滤来源种类只选该种类。待交接列表只向原消费者披露还没被它接手的决定。

### 等待与执行名额

- 一次 Ask 等人只挂起这一个调用；同会话其他已准入、无显式依赖的调用照常可运行；一个会话的 Agent 循环等人不阻塞别的会话。已有显式依赖、同一次 Ask 的全部问题、同轮扩展判断的屏障保持，作用域被记下，不扩成全局屏障。
- 等待时可靠保存继续状态，释放执行名额、共享写事务与跨调用锁；唤醒只是让人去重读。同一次 Ask 的全部问题都处理（跳过也算已处理）才解除这次 Ask；同轮扩展的全部判断齐备之前，任何获准动作都不执行。
- 整批答复被可靠接手之后，原调用进入可继续，保留原答复与继续位置，按原调度拥有者的公平策略重新取得名额才继续；取得名额与实际继续之前重核原终局、接收代次、当前权限与批次屏障。答复接手之前就没释放名额的调用保留原名额直接继续。人不需要重答。
- 等待期间普通输入、后台结果与控制照常受理；普通消息进原队列，不被猜成卡片答复。受理成功、控制生效与等待解除分别确认。
- 斜杠命令的提示词与 Skill 分支是普通消息，系统流程命令交实际拥有者；都不因为某张卡存在而成为它的答案。MCP 的静态凭据与 OAuth 凭据沿资产持有与配值资格取得，不经 Ask 或 Run 扩展代办。
- 成员资格失效限制之后的读取、答复与新准入，不销毁租户、不删会话、不等同归档；重新加入同一组织恢复同一租户的资格，不复活旧终局，不重建旧卡。自动归档由会话拥有者按配置与真实的连续空闲判断，隐藏卡片不证明空闲。

### 授权与提示的组合

- 系统准入先算结构化权限、授权表达与会话模式；明确禁止直接拒绝，不出请求放宽的卡。系统卡只给当前有权且写入后能生效的选项；能访问会话不推导出修改租户设置的资格。仅本次与本会话的范围沿原授权规则；租户持久选择写入租户权限设置，受真实写设置资格与组织上界约束，设置是否生效以设置拥有者的实际回执为准。
- 有效决定只适用于原动作、生效参数与匹配的实现和依据。参数、实现或授权依据变了，不自动复用旧批准，由原继续执行者重新核对。人的批准、准入与实际环境隔离条件分别成立。
- 每个阶段只登记它需要的保护：保存人的答复只需当前身份与读答资格、卡片状态、原等待未终局与这些资格依赖的外域事实，不要求原运行时在线；把答复解释成许可或写持久规则另需当前批准资格与提交参加者；恢复继续或执行动作另需原动作绑定、执行采用围栏、许可消费与执行容量。
- 提示在请求确认之后才产生，由来源业务给出获准目标与内容，交 Notification 承接；发送、送达、已读、有效答复与原工作完成分别确认。提示失败不删除卡、不代答、不重做产生卡的工作；通知内容按当前披露资格裁剪。

### 恢复、换代与撤除

- 已有结论不重判，已有答复不重出同一张卡，未完成的调用按原身份认回；版本或依赖不兼容时保管原进度并报告受阻，不替人给新答案，不把「扩展不在」当作人拒绝，更不默认批准。
- 运行时实例换代不改变同一会话的 Agent 定义身份、原 Run、原调用或卡片身份。提供者只撤自己的登记、订阅与临时使用权；旧代次的清理不删新实例或别的租户的数据。有序停服不是打断：等待与卡片原样保留，重启后由原拥有者接回。
- 应用服务关闭时先拒绝新调用，再排空已受理的读写，最后关闭内部适配器；关闭后的调用答不可用，不冒充可能已提交的未知。关闭不删请求、不终结业务等待、不关闭共享存储。
- 关系守护发现投影缺行、多行、错关联或计数不一致时，相应实例的查询结果不能再解释为「没有工作」：停止路由、关闭并排空，维护期间答不可用；恢复只消费原拥有者的可信事实，不重新执行登记、答复、消费或外部动作，重开前核对全部关系守护与原结果认回。

### 存储与表示

- 每张表只有一个写参加者；本组不读原等待、资格、配值或授权的私表，它们以事务事实进入。终态 `committed` 不是业务成功，完整业务结果从原 SQL 操作日志读回；日志暂不能确认答未知，结果损坏答不可用。封口只在认回耐久的中止之后才答 `not-committed`。
- 原操作身份是租户、actor 与 `operationId`；方法与规范命令进入输入摘要，摘要不同即冲突。恢复命令与普通命令各自认回自己一族的原操作，问错一族答冲突。
- 文本与标识是合法的 Unicode：孤立代理项在边界答非法输入；合法代理对、NUL、控制字符、空格与换行按原值保留。预算按原 UTF-8 计量，存储表示必须往返单射，不截断原话，不合并不同标识。修订与接收代次是任意精度的十进制文本，序号以十进制字符串传递。
- 一次答复只读这一题和这张卡；中间回执只保留原绑定与计划摘要，不复制整批历史答复，合法批次的累积不触发回执上限。

### 协议与接入

- `human-intervention/v1` 有列卡 `list-cards`、读卡 `read-card`、提交答复 `submit-reply`、认回提交 `query-submit-reply` 四个操作，都要登录、都在消息体里带目标租户，都不算业务访问、不带登录凭证。`submit-reply` 是提交，另外三个是读。同一主版本里只能加操作与观察，改已有形状要新的主版本。登录证明由管道认出，处理函数拿到的是登录。位置引用不在消息体里，由装配给接入插件作设置；客户端在消息体里写位置引用按协议拒绝。
- 结果只有各操作列出的那些。领域的失败按名字对应：拒绝对 `denied`，非法输入对 `invalid`，上限对 `limited`（带资源与上限），冲突对 `conflict`，不可用对 `basis-unavailable`；`read-card` 没有 `conflict`。提交的结果：已决定、已被决定、已失效都是成功，各带自己的响应体。读的抛出答 `basis-unavailable`，提交的抛出与未知答 `unknown`。`query-submit-reply` 认回已提交的原结果，没有成立的提交答 `not-committed`，原操作被别的命令占着答 `conflict`。
- 卡的视图只暴露来源的种类、会话、Run、工具调用四个引用与登记的时刻（ISO 8601 的 UTC 时刻，旧的卡没有这一项时不带）；来源的路由字段、等待位置与采用依据不出现在答复里。选项的视图带可选的角色。这两项都是同一主版本里加的可选字段。
- 接入插件替每一次调用取入口主体，顺序固定：核对登录可为目标租户行事，不行答 `denied`，不去取入口主体；向入口主体持有者取这个租户的入口主体；取回的必须是这个租户的入口主体（行事主体、系统行动者、组件 `server-entry`、工作 `harness.hitl/cards`、租户相等），否则、抛出、缺席都答 `basis-unavailable`；HITL 入口面每次调用现取，取不到答 `basis-unavailable`，协议不撤。卡的读者与答复者名单绑着入口主体，所以任何登录只能经这个租户的同一个入口主体读卡与答复；入口主体的这几段文字不改，改了已有的卡读不出来。
- 答复的提交身份由租户与答复编号派生，不含登录与消息号，派生用的文本 `hitl-public/1-reply` 不改，它写进了已有的提交：同一个答复再送，认回的是同一次提交。接入插件不持有状态，不缓存卡，不自己认回。
- `human-intervention/v1` 另有一个观察 `observe-cards`：要登录，建立值带目标租户，不算业务访问，没有自己的结束原因。帧只有 `{ kind: 'changed' }`，意思是这个租户的卡可能变了、客户端该重读；帧里没有卡的任何内容。观察建立之后立刻给第一帧，客户端据此读第一遍，所以建立之前的变化不会漏。之后卡的每一次写完成之后给一帧；上一帧还没被取走时，连着来的变化合成一帧。
- 建立观察的次序固定：先核对登录可为目标租户行事，不行答 `denied`，依据不可用或抛出答 `basis-unavailable`，这两种都不去取信号来源；再现取信号来源，取不到答 `basis-unavailable`，协议不撤；然后先订阅，再答成功，订阅抛出答 `basis-unavailable`。每一帧发出之前重核登录仍可为这个租户行事：不行以 `denied` 结束，依据不可用或抛出以 `unavailable` 结束；重核期间到来的变化记成下一帧。信号来源关了以 `unavailable` 结束，调用方中止时结束。观察无论怎样结束都退订，不设定时器，不轮询。
- 信号的端口是 `CardChanges`：按租户文本订阅一个监听者，返回退订函数，退订两次第二次什么都不做。监听者有两个方法：`changed()` 说这个租户的卡可能变了；`closed()` 说信号来源不再工作（托管它的那一处被撤下或换代），之后不会再有 `changed()`。信号不带事实，丢一帧的后果只是界面晚一步重读，所以信号只在内存里。信号由托管人工介入应用的那一处发出：应用的每一次写（登记、答复、失效、交接确认与恢复一侧的写）落定之后告诉这个租户的监听者，读不发信号。

### 界面模块

- `human-intervention-ui` 的 `./cordis` 入口导出工厂 `createHumanInterventionUiModule(options?)`、它的选项类型 `HumanInterventionUiOptions`，以及页面的标识 `PAGE_ID` 与次序 `PAGE_ORDER`。工厂造出的界面模块注入 `human-intervention/v1` 的协议客户端：协议没挂着时模块不加载；协议撤了模块卸载，放进外壳的项随之撤掉，这个模块的全部驱动随作用域的效应收回而停下。根入口与 Cordis 无关，只导出卡的存放 `CardsHub` 与三处视图 `DecisionsPage`、`SessionCards`、`PendingBadge`。
- 模块总是往外壳的页面位置放一页「待你决定」，标识 `decisions`，次序 10，在对话（0）与设置（20）之间，页面项带张数的标记位；不放侧栏项与登录门。选项给了 `sessionDock` 时，模块另往这个[拓展点](../../.meta_harness/design/ubiquitous_language/terms/architecture-core-and-extension.md#ul-extension-point--拓展点--extension-point)里放一项：标识 `decisions-in-session`，次序 0，收到的对象是 `{ session }`，`session` 是会话引用的文本。`sessionDock` 是外壳契约的 `PointSink<{ session: string }>`：只有贡献的一面，对象的形状由本成员自己写。拓展点由应用的装配给，本成员不认识哪个界面模块展示会话，也不导入它；装配交来的拓展点对象形状对不上时，在装配处编译不过。外壳还没给租户时，三处都什么都不画。
- 一个租户只有一份卡的存放：这个租户全部状态是 `pending` 的卡与每张卡的提交状态，人填的草稿，正在进行的提交，被关掉的题。`CardsHub` 按租户给出同一个驱动；视图挂上时持有它，卸下时放手。持有数从 0 变 1 时驱动开始工作：读一遍列表，建立观察；从 1 变 0 时停下：中止观察，取消等着的重连。三处是这一份存放的三个读法，不各建各的存放，不各发各的请求：

  | 显示 | 外壳里的位置 | 显示什么 |
  | --- | --- | --- |
  | 决策池页「待你决定」 | 页面 | 这个租户全部的卡，按来源的会话分组，每组一个卡片区 |
  | 导航上的张数 | 同一个页面项的标记位 | 待答的卡的张数 |
  | 会话里的卡 | `sessionDock`，对话页里转写的末尾 | 来源的会话引用等于这个会话的卡片区 |

  于是人填的东西在两处看到同一份；同一张卡在一处正在提交，另一处也显示正在提交；任何一处记下，两处的这张卡都收起。外壳给的租户读不懂时，决策池页说出来，另两处什么都不渲染，都不建驱动。
- 三处的观感照[视觉规范](../../.meta_harness/agents/skills/visual-standard/canonical/SKILL.md)：决策卡片是对话流里最重的东西，它的画法（决定宽度、浮层底、细线抬起、卡片圆角）见技能的[对话流](../../.meta_harness/agents/skills/visual-standard/canonical/references/conversation-stream.md)一页；颜色与语气的规则见[规则与 token 的索引](../../.meta_harness/agents/skills/visual-standard/canonical/references/rules-index.md)的 C3、C4。下面每一句通知都写明语气：失败是 `InlineNotice` 的 `danger`；注意是 `caution`，琥珀；中性是 `neutral`。正常的状态不画字、不画点。
- 决策池页是单列页：`PageColumn` 加 `PageHeader`，标题「待你决定」，说明「Agent 提的问题、要你批准的动作」；页上没有「刷新」：列表随观察自己更新，读不出时通知里带「重试」。页头下面依次是：观察的一行（见下面观察那一条）；列表的失败或不全；各组。组头是说明字号的强字，写「会话」与会话引用的前 12 个字符（更长时加「…」）；没有会话的组叫「不属于会话的问题」。卡的数据里只有会话的引用，本成员也不认识展示会话的页面，所以组头是文字，不是链接。组头下面是这一组的卡片区。
  - 加载：还没读出列表时是 `LoadingState`「正在读取……」。
  - 空：`EmptyState`，图标是「等你」的字形 `awaiting`，一句「待答的问题会在这里等你。」，左对齐，没有动作。
  - 读不出：一行 `InlineNotice` 写原因，带「重试」，语气见下面的结果表；之前读到的卡留着。
  - 部分：列表不全时一行「列表不全：有的来源暂时读不出，这里没有列全。」（注意）。
  - 外壳给的租户读不懂：页里只有一行「外壳给的租户读不懂，这一页不能工作。」（失败）。
- 导航上的张数用共用件 `CountPill` 的等你一种（琥珀、表格数字），超过 99 显示「99+」，0 张时什么都不渲染。模块另经外壳的[形口](../frontend/SPEC.md#形口)报同一个数作待答数，`waitingPage` 是 `decisions`；外壳把它用琥珀写在形的口外。外壳还没给租户或租户读不懂时报 0。
- 会话里的卡：卡片区放在 `sessionDock` 里，可访问的区块标签是「这个会话待答的问题」。卡在屏幕上就是在等，所以区块上面不另写「在等你」一类的话；「现在发的话会排队，不算回答」由会话的输入框说。读出来了且这个会话一张卡都没有时什么都不渲染。列表读不出时写「这个会话的问题读不出来：」加原因与「重试」，语气见结果表。
- 列表按协议的游标取完全部页，只取 `pending` 的卡，不带会话过滤；会话里的卡与决策池页的每一组都从这一份里按来源的会话引用筛。一组卡是一张纸（卡片区），次序取列表的次序，新来的卡接在最后；纸的形态不随卡来自一次提问还是几次提问、来自哪一个工具而变。纸的画法是从外部项目的决策卡（来历见本成员的 `UPSTREAM.md`）按[应然设计推一个新组件的七步](../../.meta_harness/agents/skills/visual-standard/canonical/SKILL.md)推出来的：

  | 步 | 答 | 为什么 |
  | --- | --- | --- |
  | 1 属于哪一族 | 对话流里的一块：在会话里排在转写的末尾、主列里，随转写滚动；在决策池页是一组 | 来源的卡在转写里；卡在屏幕上就是 Agent 正在等它，等的那一处在转写的末尾；钉住的区块会让长卡在框里滚动 |
  | 2 多重 | 最重的一档：决定宽度、浮层底、细线抬起、卡片圆角。几张卡是一张纸上的几节，一次摆一节，纸顶一排圆点；纸里没有第二张卡 | 要人决定的事最重；卡片里不再套卡片 |
  | 3 每个状态怎样说真话 | 每一节各说各的状态，写在这一节的种类行与这一节的末尾；不在看的那几节由它们的圆点说；没作答什么都不画；整张纸读不出写在纸的上方 | 一题的结果不挡别的题，也不被别的题盖住 |
  | 4 反馈归哪一种 | 一题的作答是选择行，自己就是回执，什么都不发；只有纸底定夺的钮发（行式的「提交」，钮式的选项钮）；结果落在出事的那一节 | 来源：选一行不发送，只有纸底的钮发 |
  | 5 怎样出现与离开 | 纸到达一次；决定了的一节直接切掉，全部决定纸就离开；被关掉的一节落定一次。一张纸一个主动作；选了不跳题；翻题只换摆哪一节，纸不变高，指针下的东西不动 | 来源：指针下的东西不动；一次操作一个主动作 |
  | 6 用哪些件 | `DotPager` 与 `omne-paged`、`ChoiceList` 与 `ChoiceRow`、`FactList`、`Disclosure`、`Textarea`、`Button`（带字形）、`ActionTooltip`、`Ago`、`StateWord`、`CodeSurface`、`Segmented`、`InlineNotice` | 选择行是一个角色：一组里选一行，整行是目标；来源里它只在决策卡里，这里进共用件 |
  | 7 字 | 种类行说该谁动、什么时候问的；谁在问、在哪儿写在说明下面一行弱墨里（放行卡没有这一行） | 来源的种类行「需要你授权」 |

  一次摆一题。纸顶一排圆点（`DotPager`），每题一个，次序同纸上的节：空心琥珀是还没答，实心浓墨是答好了、还没提交或正在提交，危险色是没有记上，淡墨是未确认或已关闭；正在看的那一个拉长。圆点的名字与提示是「第 n 题：」加还没答、答好了，还没提交、正在提交、没有记上、未确认、已关闭之一。点圆点翻到那一题；焦点在圆点上时 ← → 翻，Home、End 到头尾；圆点右边两个图标钮「上一题」「下一题」，到头时不能按，焦点留在钮上。只有一题时不画圆点与钮。几题叠在同一格里（`omne-paged`），不在看的题 `inert`：纸高取最高的一题，翻题不改纸高，所以贴底跟随的转写不滚，指针下的圆点与钮不动。看哪一题跟着卡走，不跟着位置走：纸挂上时看第一题没答的，都答了看第一题；新来的卡接在最后，正在看的不变；正在看的那一题被切掉（决定了，或按了「知道了」）时，换成站到它位置上的那一题，没有就看最后一题。选了不跳题。纸长了随转写滚动，不在自己里面滚动。来源的卡右下的「拒绝」「批准」在这里是钮式的选项钮：钮上写出卡方给的标签，字形照出卡方给的角色，本组不解释哪一项是准（见「卡片与答复」）。

  纸的一节自上而下：
  1. 种类行：字形加一个词，`question` 与 `extension` 写「需要你回答」，`release` 写「需要你授权」；等着人答时字形与词是琥珀。行尾是提问的相对时间（`Ago`，最弱的墨，精确的时刻在提示里），卡的视图没带时刻时不写；第几题由圆点说，种类行不写。说明字号、强字。<!-- OD-37 OD-39 -->
  2. 标题：问询与拓展件的问题用阅读字体、正文字号；放行卡的动作用界面字体、正文字号、强字。长了在原来的字号上换行，不缩小。
  3. 说明：弱墨、界面字号。下面一行说明字号的弱墨：谁在问（`question`「Agent 在问你」、`extension`「拓展件在问你」）与卡的显示上下文。放行卡不画说明与这一行：动作就是标题，种类行已经说了要谁做什么，下面的事实表说是哪一次调用。
  4. 放行卡的调用摘要与放行详情，见下面放行卡那一条。
  5. 作答：卡的选项按出卡方的次序画，样子由下面的定夺规则定。「用自己的话回答」与「不回答这一题」不与出卡方的选项并列：它们收在选项下面一个安静的 `Disclosure`「自己写，或不回答」里（来源「添加备注（选填）」的手），打开后是两行选择行，选中其中一行时折叠保持打开。选中「用自己的话回答」时它下面展开一个文本框，随内容长高；选别的行时文本框收起，写下的字留着，只发选中的那一行。选中「不回答这一题」时它下面一行弱墨写卡写明的跳过后果。卡没有选项时不画折叠，文本框直接在，「不回答这一题」是它下面的一个安静的链接钮：按下就是选中这一项（钮显示按下，它下面写跳过后果），再按一次取消；在文本框里写字也取消它。任何一行都没有默认的选中与焦点，方向键在一组里移动。

  定夺规则，只看卡的数据，不看工具名：<!-- OD-35 -->
  - 钮式：纸上只有一节，这一节露在外面的选项（放行卡是一次性的那几档）有一到三个，每个标签不超过 8 个字、说明不超过 16 个字；全角的字算一个字，半角的字母、数字与符号两个算一个字。选项就是定夺的钮，排在纸底右边，照出卡方的次序，最后一个是主钮，别的是描边钮；按下就交这一个选择，不再另按「提交」。选项的说明放进钮的提示。选项带角色时字形与语气照角色：准是对勾，驳是关掉的字形；没有角色就不画字形。钮是选项的标签，不改成「批准」「拒绝」。
  - 行式：别的情形。卡的选项是一组选择行（`ChoiceList`，标签与一句说明），纸底右边是唯一的主钮「提交」，带对勾字形。
  - 钮式下，人在折叠里选了一行（有持续效果的一档、用自己的话回答、不回答这一题），纸底的选项钮换成「取消」与「提交」：「取消」清掉这个选择、收起折叠、换回选项钮；「提交」交这个选择，选的是有持续效果的一档时照下面放行卡那一条武装。

  纸底一行：左边「还差 n 题」（见下面提交那一条，只在行式下有），右边是定夺的钮（钮式）或唯一的主钮「提交」（行式）；底下一行说明字号的弱墨写正在提交或武装的原因。作答的三种行分别对应答复的 `selection`、`text` 与 `decline`，人不必先选准驳或授权档位；答复的三种形状与命令行 `submit-reply` 相同。界面不按工具名分支，卡的样子只看卡的数据。
- 纸按卡的种类取组件：外壳（作答的状态机、提交与认回）各种卡共用，每一节的卡身由该种类的组件画。不认识的种类用通用的卡身画出标题、说明与选项，不丢卡。
- 放行卡的调用摘要是一张事实表（`FactList`，画法照来源的 `.decision-facts`：上面一条细线，说明字号，词条最弱的墨）：工具（工具名、命令与预览，等宽）与动作类别（「工具：关口的名字」）；动作由一段程序发起时多一行来源，写「由程序发起」。会话与 Agent 的引用不画：它们是标识，不是给人看的事实；纸本来就在这个会话里。表下面是放行详情，按下表画。参数收在「详情」后面（`Disclosure`）的 `CodeSurface` 里；参数被截短时写「参数太长，只显示开头。全文摘要」加摘要。工具带来的画法与条目之间用一个分段控件（`Segmented`：「工具的画法」「条目」）切换。选项照上面的作答与定夺规则画：一次性的两档露在外面（钮式下是纸底的两个钮）；有持续效果的三档收在一个安静的 `Disclosure`「这一类动作」里，是三行选择行，排在露在外面的选项后面、「自己写，或不回答」前面，选中其中一档时折叠保持打开。每档的说明写它的作用范围。发卡方此刻不给的一档照样画出，不能选。选中有持续效果的一档时，纸底的「提交」武装：危险色，底下一行用危险色写「选了有持续效果的一档：以后同一类动作照它处理。」；选一次性的一档不武装，别处都不红。调用摘要、关口的名字、来源、五档与提交始终由本成员画，任何贡献都改不了它们。

- 一张纸只有一个提交：行式下是纸底右边的主钮「提交」，钮式下是按下的那个选项钮（或折叠里选了一行之后的「提交」），下面说的「提交」两种都算。组里每张不在途的待答卡都选了、写了字或按了「不回答这一题」，提交才能按；纸上不止一节且没齐时，纸底左边是一个链接「还差 n 题」，点它翻到第一节没答的，滚进视野，焦点到它作答的第一行；只有一节时不画链接。放行卡例外：它可以留着不答，组里至少答了一张、别的种类都答齐了就能提交，这时链接写「另有 n 张放行卡没答，可以先提交已答的」，一张都没答时仍写「还差 n 题」；一张放行卡的答复可能让服务端撤掉同批的其余几张，被撤的卡在重读时从列表里消失。提交把这一组答了的每一题各交一次，依次发出，前一题有了结果才发下一题；每题带列卡答复里这张卡的修订号作 `expectedRevision` 与一个新的答复编号；一题的结果不挡后面的题。提交中「提交」钮自己显示等待（活动标记加「正在提交……」），正在发的那一节种类行的行尾是活动标记加「正在提交」；整张纸不能再改，也不能再提交；正在认回的那一题不进下一次提交。每一题的结果写在它那一节的种类行与这一节的末尾：
  - 决定了：这一节从纸上去掉，直接切掉，不做离开的动画。全组都记下时纸离开。本成员不留已决定的卡，所以不画回执；记录是转写里那一次调用的行。
  - 已在别处答了、提问已经关掉：这一节留在纸上，种类行的词换成状态词表里中性的「已关闭」，作答的行收起，人填的还在，不能再交；原因是一行说明字号的弱墨，不画框，行尾一个图标钮「知道了」（关掉的字形，名字在提示里），按下去掉这一节。已在别处答了写「已在别处答了，这次的答复没有采用。」；关掉的原因按协议的原因名翻译，不认识的原因显示通用的一句「这次提问已经关掉。」。这几句都是中性的：被关掉不是失败。
  - 冲突：卡在别处变了，写原因并重新取列表；卡留着，人填的还在，可以再提交。
  - 被拒（`denied`、`invalid`、`limited`、`basis-unavailable`、`protocol-rejected`）与没发出去：写原因，人填的还在，可以再提交。
  - 结果未知（`unknown`、`uncertain`）：种类行的词换成中性的「未确认」，写「结果未知，正在确认。」（中性），用这一题原来的那份正文发 `query-submit-reply` 认回一次，不重发。认回得出确定结果就照上面显示；认回答 `not-committed` 时写「确认过了：原来那次没有提交上。可以再提交。」（失败）；认回仍不知道或被拒时写「结果仍未知：这次确认没有说出原来那次提交了没有。」（中性）与「再确认一次」。认回之前这一题不能再提交。

  读列表与提交一题没有成功时，语气按结果定：

  | --- | --- | --- |
  | `denied` | 中性 | 中性 |
  | `invalid`、`protocol-rejected` | 失败 | 失败 |
  | `limited`、`conflict`、`basis-unavailable` | 注意 | 失败 |
  | 没发出去（`unavailable`） | 注意 | 失败 |
  | `uncertain` | 中性 | 按结果未知认回 |

- 反馈：作答的行自己就是回执，按下立刻显示新的选择；选了不跳到别的题，指针下的东西不动。提交的结果落在每一题那一节上；失败写在出事的那一题上，不弹瞬时提示。
- 驱动工作时经 `observe-cards` 观察这个租户的卡。一帧只说卡可能变了：没在读列表就读一遍；正在读就记下，读完再读一遍，读的过程中来几帧都只再读一遍。观察被拒（结束原因或拒绝结果是 `denied`）时不再重连，决策池页头下写一行「没有权限接收更新，或登录已失效。」（中性）；被中止的结束不算断开；别的结束都算断开，驱动按 `@omne-harness/client-assembly` 的 `defaultBackoff` 等一段，到点再读一遍列表并重新建立观察，等着的时候决策池页头下是一行中性的说明字「更新暂时连不上，列表可能不是最新的，正在重连。」。连着断开的次数一直累加，等的时间随之变长；重新建立的观察收到第一帧，次数才清零。每次建立的观察有自己的代次，旧代次的帧与结束不算数。
- 什么时候取列表：驱动开始工作时；收到一帧时；一题的提交有了确定的结果（决定了、已在别处答了、提问已经关掉、冲突）之后。不轮询；唯一的定时器是观察断开后的重连等待。重新取列表时，正在提交、结果未知或排在这一次提交里还没发的卡即使不在新列表里也留着：排着的照发，由服务端答出真实的结果。不在新列表里的卡，人填的草稿随卡去掉。
- 一张卡决没决定以服务端答的为准，界面不从提交历史推卡的状态；帧只触发重读，不改任何一张卡的状态，也没有任何一条事件替人产生答复。失败码到中文文案与语气的映射归本成员。
- 状态机是纯函数（`src/model/cards-machine.ts`），一组的作答（草稿、一次提交的进度、被关掉的题）也在里面，驱动只做收发；看哪一题是每处视图自己的，不进卡的存放，会话里与决策池页各看各的，跟随的规则是纯函数（`src/model/pager.ts`）；卡的种类与提交状态用数据属性 `data-kind`、`data-state` 表达，样式读属性。卡的版式取自外部项目，来历见本成员的 `UPSTREAM.md`。用到的共用件：`DotPager`、`PageColumn`、`PageHeader`、`EmptyState`、`LoadingState`、`LoadingIndicator`、`InlineNotice`、`CountPill`、`Button`、`ActionTooltip`、`Ago`、`IconButton`、`ChoiceList`、`ChoiceRow`、`Textarea`、`FactList`、`FactRow`、`Disclosure`、`CodeSurface`、`Segmented`、`StateWord`；不另造控件与样式变量。

## 原则与约束

- 卡片不是决定权威。人的答复由原拥有者解释，许可由 Authorization 发，设置由 Settings 写，执行由原执行者做。
- 没有人回答就没有答案。时间、通知、界面、脚本与扩展件都不能替人作答；导入钩子的「允许」只按无意见解释。
- 几件事分别确认：答复保存、原等待接手、继续执行、授权生效、提示送达。一件成立不推出另一件。
- 结果不知道就是不知道。按原操作身份查询与封口，不换身份重发，不写成成功或失败；查无记录不是未提交。
- 等待是耐久事实，不是占着的资源。等人不持执行名额、写事务或锁，不阻塞独立的工作。
- 只撤自己的那一份。换代、关闭、撤除只影响本代次、本提供者的贡献，不删历史，不复活终局。
- 交接与提交的协议有形式模型与关键性质检查，模型在 `human-intervention/verification/`，对照见同目录的 `formal-mapping.md`；有限检查通过不等于实现符合。
