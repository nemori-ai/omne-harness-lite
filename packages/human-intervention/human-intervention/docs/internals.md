# 人在回路内部机制候选

本页保存尚待技术采用的设计，不表示实现、产品接受或阶段承诺。完整必要行为见[human-intervention/human-intervention SPEC](../SPEC.md)，产品范围见[产品正文](../../../../.meta_harness/design/product/human-intervention/design.md)。

## 身份、采用依据与状态

每个可处理请求携带可信租户、适用主体、来源类别、请求/卡片身份、原工作身份及原消费位置。动作请求保留原参数、生效参数、实现及授权依据；拓展请求另保留拓展件身份、版本或等价适用依据、位置和已发生调用。Ask 每个问题保留描述、必需文本候选及系统保证的独立自由作答，图解可选且不能替代文本。请示、系统放行与拓展卡也保留不选选项而独立提交原话的路径；系统卡不要求先选择授权档位。具体公开类型、编码及身份产生方式交 Q-HI02，不以运行时对象序列化代替数据契约。

逻辑状态区分尚未确认请求、有效待答、已有效处理但尚待原位置消费、原位置已处理以及失效。失效须有原工作终局或明确控制的依据及原因。人的拒答是一类有效处理，系统故障不是人的拒绝；因原执行失联而失败的是原 Tool 事实，卡片只关联其失效原因。部分完成、提交未知和查询不可用另保留已知范围，不强行映射为“待答”或“已关闭”。这些是必须可辨的事实，尚未固定 API 枚举。

一批卡片是同次等待的关联视图。Ask 多问题批次阻塞原 Ask 工具；其他工具的人工等待沿自己的声明；Run 拓展一轮卡片阻塞该轮的原判断。原扩展链拥有动作判断屏障，不由池子统一阻塞所有工具。已判动作不越过同批未完判断执行。后继拓展出卡属于下一轮，保留同动作和新位置，不伪装成重复第一轮。

会话归属、Run、Tool 的逻辑执行和三种 runtime 各有生命周期。Q03 的逻辑 dummy 取得不可用结果而真实工具未执行，不以此伪造等待或真实资源；已有结果仍回原消费位置。Agent runtime 换实例不改变同一 Session 的 AgentDefinition ID，也不改变卡片、原 Run 或 Tool 身份。


## 创建、答复和继续的组合

1. 原请求方固定问题、动作及位置，协调者在确认前可靠保管卡片、原等待及其关联。系统确定需问但生成有效卡片确定失败时，相关动作不执行，原协调者记录准入故障造成的拒绝及原因，交回原 agent，并通过合法可见方式告知人；不伪造拒答或建立等待不存在卡片的有效人工等待。这条规则对拓展出的卡片同样适用。拓展自己执行报错是另一种情形，沿正式扩展错误策略及有效声明处置，记录真实失败和后续责任。生成失败不等于保存确认未知，后者保留原请求身份查询，不先确认有效人工等待。请求已确认后，即使通知丢失，仍能在所属范围发现。
2. 呈现按当前读取资格取得合法投影。答复接口核验可信身份、目标卡片、当前有效状态、答复/配置资格及允许值，明确区分用户新处理与技术重传。
3. 协调者裁定一个有效答复，将人的处理及原等待可恢复更新作为一个业务单元成立。需要形成授权或设置时，由原权限拥有者保管其效果及完成责任，租户持久选项写租户权限设置，由当前写设置资格及组织上界约束；不能先声称设置生效再等待未知写入。
4. 只有共同业务单元已确认成立，原消费位置才取得可消费的有效处理；保存结果未知须先沿原提交身份查询确认，明确失败和仍未知分别返回真实回执，竞争入口也不先获已处理确认。原请求拥有者解释答复原话，确认对应批次或本工具条件是否齐备。请示原话不能明确读成准驳时保留“人有话说但未给准驳”，不当作批准、拒绝或明确拒答；交原 agent 指导调整后再请示，不据此执行拟动作。系统放行卡的原话交原准入及授权拥有者按现行规则解释，文字提交本身不自动成立批准或权限设置。拓展答复由原拓展件解释，不增系统授权。继续执行者核验原工作未终局、实际执行权、匹配采用、授权与环境条件；答复信息本身不直接发工具。
5. 卡片/池投影与提示从权威结果更新。未完成交接有具名保管者，原方在后方可靠接手前不清除唯一答复或依据。

实际保存边界须说明介质与部署前提，覆盖普通进程、操作系统崩溃和断电后的读取解释。若跨后端不能同提交，Q-HI03 的协议要说明阶段确认、未知和保管责任，禁止出现“人已有效回答、原等待永远看不见”或“原工作已继续、另一入口还能有效答”的状态。通知成功或收到唤醒不算原等待消费确认。


## 并发、控制及资格变化

两个入口、多个客户端、答复与取消、归档、插队及原工作终局可能竞争。以卡片及原等待的权威结果裁定先后；有效答复只有一次，不能因两次独立资格检查都通过而确认两份决定。答复已生效但尚未发动作时，继续条件仍按原拥有者核验，控制先成立则不凭旧答复复活推进。已发动作的控制和迟到收场归原调用，不把卡片状态改成“已撤回效果”。

成员资格失效限制后续读取、答复及新准入，不抹去合法事实或冻结全部业务。重新加入恢复同一租户资格，不重新创建旧卡片。自动归档仍由会话拥有者按配置和真实工作判定，不以界面隐藏证明空闲。会话归档按 Q04 业务取消解除等待，原独立执行继续负责实际停止、效果、结果及费用。

MCP 静态/OAuth 凭据沿资产持有和配值资格，不借 Ask 等待或 Run 扩展发起配值。斜杠命令的提示词/Skill 分支仍是普通消息；系统流程直接交实际拥有者，摘要不代替受理/生效；都不能仅因某张卡存在而成为它的答案。正式环境约束独立成立，受限执行域终止后已准入宿主调用仍由原桥接承接。


## 恢复、撤除和资源责任

人工等待是可恢复事实，Agent runtime 可挂起或交还；独立模型/工具可能继续运行和计费，不声明整个会话等待期间零费用。恢复从原卡片、等待及调用身份查询，已生效答复不重收，已记录判断/模型结果/效果不重跑。原执行连续性确定丢失沿执行拥有者收场，查询失败不证明丢失。

拓展件撤除、版本更新和重装配须保留未完判断、已答内容及原消费位置。新绑定或不兼容依据不能接走旧许可；兼容协议未采用则依赖路径受阻并可查询，Q-HI04 细化暂停、接续或关闭责任。不把“扩展不在”直接当作人拒绝，更不能默认批准；准入组件不可用沿正式全拒承接。

HITL 提供者配对自己的登记、订阅、查询句柄和临时数据使用权，只撤自己的贡献，旧清理不删除新代际或其他租户数据。退出前可靠保存或交接请求与未完处置，不因引用为零或 dispose 声称原工作物理停止。依赖不可用时阻止依赖耐久或当前资格的新操作，已确认事实仍保管；恢复后重新核验，不无条件执行停机前计划。


## 后续技术采用

下列事项是技术采用义务，不要求产品负责人选择数据库、协议或 provider。行为目标沿 [SPEC](../SPEC.md) 保持。

<a id="q-hi02"></a>

### Q-HI02 采用公开请求、答复及原等待接口

原 Tool、Run 拓展、UI 与授权拥有者要交换稳定数据，不能把 runtime 对象或任意闭包当数据契约。 由哪些具名定义及消费者采用稳定请求、处理结果、资格与原等待关联接口？

可信租户、原工作/消费位置、卡片/提交身份及采用依据必须可恢复。

普通消息、问询/请示和配置凭据不混同；当前资格分别核验。

卡片没有独立批准权威，原拥有者解释答复及继续。

- 复用已有可满足接口。核对必要事实与失败语义，并只补本次真实缺口。
- 补齐所缺公开契约。明确定义拥有者与消费者迁移，不生成假中央服务或空包。

技术采用先核对实际定义，保持领域接口与 Cordis 装配分开。

影响数据形状和组合实施，不留空整份业务规格。

技术拥有者为HITL 请求定义拥有者与原 Tool、Run 拓展、交付面及授权消费者。

<a id="q-hi03"></a>

### Q-HI03 采用唯一答复与原等待一致交接协议

两个入口或答复/归档竞争，答复存储、原等待更新和授权设置可能跨后端，回执也可能丢失。 实际协调者怎样裁定竞争、确认保存阶段及交接责任，并在进程/OS 崩溃和断电后认回原事实？

仅一个有效人的处理，答复与原等待作为共同业务单元成立。

设置生效有原设置拥有者证据，租户持久选择写租户权限设置。

未知不改成未发生，前方可靠接手前仍保管；耐久边界声明介质与部署条件。

- 适用共同提交边界。说明原答复与等待覆盖范围及额外授权效果的确认。
- 采用分阶段交接协议。说明每阶段确认、未知、查询及下一保管者，并验证无责任空档。

选择能证明 INV-HI06、INV-HI07、INV-HI14、INV-HI18 的机制；本文不指定数据库或消息协议。

阻塞可靠提交实现与故障验证，业务义务已明确。

技术拥有者为原等待协调者、HITL 保管与原授权/设置拥有者。

<a id="q-hi04"></a>

### Q-HI04 采用拓展等待接续与撤除协议

非确定拓展已调模型或产生效果后出卡，重启、撤除或版本更新时仍有未消费答复。 稳定拓展调用身份、非确定记录、版本兼容及撤除后的合法接续或关闭分别由谁承担？

复用已记录判断、非确定输入和效果，不简单重跑函数。

原版本/位置保留，普通 runtime 换代不换 Session AgentDefinition ID。

不兼容只阻塞依赖路径，不伪造人的拒答、批准或原工作终局。

- 保留原兼容消费位置。在原绑定和适用依据保持时认回原等待并消费记录。
- 显式处理不兼容。保管原进度，按合法协议重新判断或关闭，不能移用旧批准。

技术采用明确两类分支及验证反例，不选择一次重跑作为恢复。

影响拓展重装配、在途恢复和维护；不重开授权产品规则。

技术拥有者为原 Run/Tool 拓展调用与等待协调者、HITL 保管及装配拥有者。

<a id="q-hi05"></a>

### Q-HI05 采用合资格等待投影与通知交接

有权人未打开原会话仍须发现待答卡片，通知失败/已读又不能改变答复事实。 池查询的新鲜度/权限及需要提示时的合资格来源交接，采用哪些实际公开入口和责任？

全部有效待答卡片在所属租户/位置可发现，投影不持第二决定权威。

内容按当前披露资格裁剪，通知与卡片答复及源工作完成分别确认。

正式通知域拥有对象分解和交付，不在 HITL 另造发送或耐久权威。

- 池和会话呈现。说明权威查询、合法投影滞后与待答完整性。
- 在呈现外组合通知。源业务提出获准目标/内容，交通知拥有者承接送达与未知。

按所选 CAP 与通知实际契约细化，不假定某渠道或补造通知对象。

影响 UI/通知组合和披露验证，渠道配置不削弱待答可发现规则。

技术拥有者为HITL 查询/呈现拥有者、交付面与正式通知拥有者。
