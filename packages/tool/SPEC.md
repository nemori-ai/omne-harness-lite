# Tool

## 总体架构

Tool 回答一件事：一次工具调用怎样被受理、执行、等待、控制和收场，它的结果、效果与费用怎样保管并交给原消费者。包组有九个成员：

| 成员                   | 回答的问题                                                                                                         |
| ---------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| `tool-contract`        | 一次调用有哪些事实、操作与端口，边界上怎样判。纯数据与纯函数，不依赖 Cordis、存储或任何 Tool 实现                  |
| `tool-cordis-contract` | 在这套系统里 Tool 以哪些服务键、事件和登记协议出现。不含实现                                                       |
| `tool`                 | 一次调用怎样一步步推进：独立执行、账本、推进协程、正文管线与清扫。不依赖 Cordis，离开这套系统也能单独用、单独测    |
| `tool-host-local`      | 在一台机器上把账本、启动排序域、时钟、绑定登记表、目录、作者装载与邻域端口接起来，并给出 Cordis 插件               |
| `tool-storage-sql`     | 在 SQL 存储契约上兑现耐久的记录仓、正文存储与到期索引                                                              |
| `tool-definitions`     | 发行自带的几个工具作者（Tools、Files、Shell、Screen、TodoItems、Ask、Web、Skills、BkgToolCalls、Code）：参数、操作映射与结果文本 |
| `tool-protocol`        | 一个登录的人按调用引用读一次调用时，有哪些操作与观察：协议契约 `tool/v1`，纯数据                                   |
| `tool-access`          | `tool/v1` 的接入插件：把三个读口接到 `ToolRuntime` 的查询、内容与观察上                                            |
| `tool-ui`              | 界面模块：一次调用写到哪了，放在装配指定的位置上给人看 |

依赖只朝内：`tool-host-local` 依赖 `tool` 与 `tool-cordis-contract`，它们依赖 `tool-contract`；`tool-storage-sql` 依赖 `tool`、`tool-contract` 与 SQL 存储契约。别的领域的生产代码只依赖 `tool-contract`，写 Cordis 插件时另加 `tool-cordis-contract`。`tool-protocol` 不依赖任何 Tool 成员以外的领域；`tool-access` 依赖 `tool-protocol`、`tool-contract` 与 `tool-cordis-contract`，按 `packages/access/SPEC.md` 的规则装配。

一次调用的事实都在账本里，按调用分域保存。推进协程每次读一个调用的全部事实，按阶段与待办做一步，这一步是一个拥有者域里的一笔条件提交，或一次按原身份的端口调用；然后重读。宿主持有活体：实例、作者执行、环境值、观察订阅。活体丢了，新的协程从账本接着走。

## 领域边界

Tool 拥有：原逻辑调用、真实执行、内部等待、控制意图与实际结果、真实收场、原结果及其版本、效果确定性、执行账、交付状态、卸载正文的保管与回收、调用状态的寿命。一段程序在它那次调用之下发起的子调用，它们的位置表、父子关联与关闭屏障也归 Tool。还拥有工具定义的派生、实现的登记与选择，以及常驻工具在采用点的纯判定。

Tool 不拥有：资产的持有、版本与治理；身份、授权与许可的授予；执行环境的设施与放置；人的决定；设置值与秘密；消费方的工作、工作终态与会话冻结；Runtime Context 的作用域注册。Tool 不为调用创建或推进任何外部工作对象，不替被调用领域写私有状态。

## 心智模型

工具的本体是函数，模型消息里的调用与结果是它的投影。准入、执行、效果和结果保管都在函数这一面，所以模型直接调用、程序调用和经 Tools 转发的调用走同一个东西。为了给模型看得舒服改的是投影，不是函数的参数或返回值。

一次调用是账本里的一组耐久事实，不是一个活着的对象。每一步有一个由受理身份派生的固定操作号，提交未知就按这个号去问，不换号重做。活体只是在推进它：调用方走了、观察断了、宿主换了，调用照样有它的结局。对调用方，Tool 是一个被远程调用的服务：调用方不等 Tool 收场，Tool 也不等调用方。调用方想知道一次调用还有没有人管，就问「你的活体还在推进它吗」。Tool 对这一问从不答「不在我手里了」：开始过的调用带着外部效果与资源，由 Tool 与执行环境收场，调用方等到的是一个按正常的路交回的结果。

最容易想错的地方：流结束不是完成，完成只认一份计划后的 final；拒绝或失败不说明没有效果，效果单独记已发生、未发生或未知；disposer、关闭连接、释放资源都不是停止证明；逻辑收场不释放名额，释放要一条物理依据；常驻声明在上下文里不等于许可，撤销立刻生效；转后台不是第二次执行；活体里没有一次调用不等于它失联，失联要装配给的证据。

## 应然设计

### 定义、采用与常驻

- 工具资产的正文只带身份、治理声明（`requiredCapabilities`、`programmable`、`composes.skills`）与实现引用。装载时由治理声明与实现事实派生定义：形状、说明、返回声明、后台许可与声明来自实现；采用、名字、必需能力与 `programmable` 来自资产。资产名、能力名与定义名不同时拒绝装载。
- 工具资产的正文有两种来历。发行的，实现引用指向发行清单里的模块。经通用入口新建的与工作区带来的，是一个目录：`tool.json` 写名字、一句说明、参数的规则、怎样运行（程序、脚本文件与参数）、是读还是写、可选的时限，脚本放在旁边。它的实现是发行自带的脚本执行体，租户与工作区的代码不进服务端进程。脚本执行体把参数作为一个 JSON 对象写进脚本的标准输入，标准输出是结果；退出码非零是失败；到时限时读的答失败、写的答不知道，都不重跑。这类工具一道关口 `invoke`，缺省询问，不许程序调用。它说自己的影响与生效情况：`scriptToolImpact` 与 `scriptToolPlace` 给事实出行，事实由应用读。
- 形状只看名字、种类、参数契约与命令表，说明、返回声明与采用不参与。两份定义同形当且仅当形状相等。
- 必需依赖是抽象能力名的合取。缺一个必需提供者，整个工具不可用。可选项实际使用时探测。
- `programmable` 只有布尔 `true` 许可程序调用；省略与 `false` 拒绝，非布尔值是无效声明。它是整个工具的许可：没有它，任何命令都不对程序开放；它不被设置、常驻、后台或调用方身份推导或覆盖，唯一的例外是工具条目来源的条目，见[条目来源](#条目来源)。后台许可同样是作者声明，缺省拒绝，阈值与批准都不能放宽它。命令工具按命令声明 `background`，可列出给了就不许可的参数（Shell 的 `execute` 列 `terminal`：终端里的执行不许可）；工具级 `backgroundAllowed` 由此推出，定义判定守两者一致：工具不许可时任何命令都不能声明，命令工具许可时至少一个命令声明。
- 声明 `programmable: true` 的工具，每个命令写明它对程序是哪一种：返回声明的程序数据；不返回值；不对程序开放。函数形态的工具写在工具上。三种都没写的定义被拒绝，至少要有一个命令对程序开放。命令可以列出给了就不对程序开放的参数（Shell 的 `execute` 列 `terminal`）。程序调用点名一个不对程序开放的命令或参数时答 `unsupported`，不创建已受理执行。程序数据是完整的值，不截断、不卸载；它有声明的字节上限，超过是 `cause: result` 的失败。一次结果给不出完整的值时（例如进程的输出没有全部留住），作者不给 `data`，不给截过的值。命令在返回声明里写明它的结果是不是外部数据。
- 命令可以声明 `readOnly: true`：这个命令不改变别的调用看得到的任何东西。只有布尔 `true` 算只读，省略按有效果处理，别的值是无效声明；函数形态的工具写在工具上。它不是许可，本组不凭它放行、排队或限流：它随[固定请求的描述](#受理与调用身份)交给调用方，由调用方决定同一批动作能不能同时进行。经 `Tools` 转调时取目标命令的声明；程序执行方与工具条目来源的条目不声明只读。
- 可编程工具的名字、命令名与参数名要能在程序里使用：工具名与命令名是 ASCII 标识符，不与程序里的保留名相同；违反的定义被拒绝。程序里的函数签名由参数契约与程序数据的 schema 机械派生，作者不手写。模型只从 `Tools` 读到它：`inspect` 对可编程的工具给这一段，带条件的 `search` 每条给这一段（TL-75）。
- 多命令工具对模型是一个工具，只占一个声明。调用在参数里点名命令，编码是 `wrapped` 或 `flat` 之一；`flat` 的命令不得有名为 `command` 的字段。`flat` 的声明把各命令的字段逐个列进调用的参数 schema（同名字段在两个命令里形状不同时不写形状）：只在说明里写字段而 schema 里没有时，有的型号不发出这些字段。解码失败给封闭的拒绝类别，不猜命令。声明里的命令清单与 guide 由定义机械派生，作者不拼出错文本。
- 调用的信封除命令与参数外可以带一句意图 `intent`：一行，有字节上限，说明为什么发起这次调用。声明了 `background` 的命令，意图必填，缺了答拒绝并带这条命令的用法；别的命令可以不带。`flat` 的命令不得有名为 `intent` 的字段。意图只用来辨认：准入、权限、审批与执行都不读它，作者的参数与执行上下文里没有它。
- 受理时固定这次调用的标签：意图、工具名、命令名与动作预览。动作预览从调用本身机械地取：命令第一个必填文本参数的第一行，截到上限。标签随占位交付与调用状态给出，之后不变。
- 采用点是会话初始化、新 Run 开始和显式 reload。常驻规则 R1 到 R5 见不变式。采用点的判定只由纯函数给出，结论是前进、保持、同形替换件或冻结；冻结的原因只有 `tool-shape-lost`，判定写明是哪一项常驻工具（它的名字），只在新 Run 开始或 reload 时判，证据只来自换代协调者答 `missing` 或 `rejected`：租户已不持有记下的那一版时，验证者答 `missing` 并带持有记录；同一进程里那一版的贡献还在登记表上、仍可用时，照 R5 保持。暂时缺席、未知与撤权一律给同形替换件，不冻结。
- 工具条目来源交出的条目可以常驻。常驻的来源条目由持有者的记录带着采用时的整条定义；它没有常驻登记键，不经采用点的判定，不冻结。目录对它永远答记下的那条定义：来源此刻对这个主体列出这个名字就可用，执行体是来源；没列出或来源不在，给记下定义的替换件。被点名的命令能不能发，由来源在发出前复核，不比整个工具的形状。
- 刷新点允许的变化不同：会话初始化与 Run 中的提供者变化不判冻结、不前进记下的键；Run 中只允许可用性与路由变化。路由是在记下的键不可用时把后续调用送到同形贡献，不改写记下的键，已经发出的调用保留原实现。
- 已知不可用的工具（dummy）对任何参数都正常返回带原因的不可用结果，不启动原工具，不解析参数，只记替换件真实的处理开销。从未合法取得定义的目标不构造 dummy。
- `Tools` 能搜到的是这个主体此刻合法可用的视图，按当下事实现算，不按采用点记下的集合，也不按 Agent 定义收窄。搜索在评分与分页之前排除常驻项：常驻工具已经在模型的工具列表里，直接调用。搜索可以带条件「只要程序能调的」：这时问的是程序此刻能调什么，不是模型能直接调什么，所以不排除常驻项，只留可编程、此刻对程序可用的工具，每条多给它的函数签名与是否常驻，排序与分页不变；`Tools.execute` 只接受非常驻目标，常驻工具必须直接调用。发现与执行不把目标加入模型工具列表。
- 目录按名字回答一个工具此刻是否可用（`inspect`），也按一组名字一起回答（`inspectEach`）。一组的回答只读一次视图与登记表，再逐个判定。每个名字的答案与在同一份视图上单独 `inspect`（不点命令）的答案相同；未知的名字答 `unknown-tool`，不影响别的名字。判定期间视图或登记表变了，整组答重试，不答一半。比较视图与登记表变没变，用修订与定义的采用引用，不对定义全文重新哈希。
- 一次调用的动作由本组回答：直接调一个工具，动作就是这次调用；经 `Tools` 转发，动作是被点名的目标与交给它的生效参数，`Tools` 这次调用是载体。这个回答在启动之前就能问到，答案里有目标的精确采用、命令、生效参数、调用的标签与动作所属的关口。目标不存在、命令不存在、参数形状不对时答参数错误。放行判断按动作判断，不自己解析 `Tools` 的参数。
- 关口由工具的定义声明，是数据，进定义的摘要。一个工具声明一道或几道关口，每道有标识、给人看的名字与缺省值（禁止、询问、自动之一）；不声明就是一道，全部命令归它。每个命令写明归哪一道，或写明不设关口。一个命令归哪道关口只由（工具的精确采用，命令）决定，不随参数与领域状态变。命令写的关口没有声明过时，登记被拒绝。函数形态的工具只有一道关口。
- 动作所属的关口有三种答案：归一道关口；不设关口；这次调用是载体，关口取被带来的那个动作的。放行判断只从这个回答取关口，不按工具名推。本组自己不读关口做任何判断：关口是工具作者对治理的声明。不设关口的声明认不认由应用的装配点名决定；没被点名的当作归工具的第一道关口。
- 工具的作者可以为一个命令提供放行详情：命令的声明里写带种类的值的种类与结构（只给条目的不用写），命令的登记槽里交一个只读的函数，从这一次调用解析后的参数算出条目与可选的带种类的值。它和执行的函数并列登记，执行不依赖它。
- 一个命令可以声明它的调用条件：一组名字，每个名字指一件「这次调用所在的地方此刻成立」的事实，例如另一头有人可以答复。条件是数据，随命令的声明进定义的摘要；函数形态的工具声明在工具上。本组不解释条件的含义，也不知道事实从哪来：消费者在提供工具与每次受理时交来此刻成立的条件名。提供时，条件不成立的命令不出现在给模型的命令表与用法里，一个工具的命令全不出现时这个工具不提供；受理时，条件不成立的命令答一段说明它为什么此刻不可用的收场文字，不运行。两处用同一份声明，所以条件在一轮当中变得不成立时立刻生效。消费者不认识的条件名按不成立处置。装配与准入都不按工具名或命令名判断这类事。
- 向作者要放行详情是本组的一条只读路径，在启动之前就能问到，答案恰好三种：详情；没有（这个命令没交函数）；给不出。本组按登记找到命令的槽，用这个命令自己的解析处理生效参数，带时限调作者的函数，再核结果：条目的条数与长度、带种类的值符合声明的结构且不超大小、声明了种类就必须给值、没声明就不能给。解析不过、抛出、超时、不合，都答给不出，原因只进诊断。大小是预算，不是截断点：内容多的由作者自己给摘要（例如写出前若干项与总数），本组不替作者截。这条路径不写任何东西，不出卡，不等人；交给作者的只有主体、租户与解析后的参数。时限与各项大小是可配的策略，初值见 `tool-host-local` 的策略对象。
- 作者算放行详情的函数不产生任何效果：同一份输入算任意多次，除了得到同一份内容，它所在领域的状态不变。

### 条目来源

- 本组声明一个[拓展点](../../.meta_harness/design/ubiquitous_language/terms/architecture-core-and-extension.md#ul-extension-point--拓展点--extension-point)，供别的领域把自己的[工具条目来源](../../.meta_harness/design/ubiquitous_language/terms/reach-and-availability.md#ul-tool-entry-source--工具条目来源--tool-entry-source)放进工具入口。十问的答案：

  | # | 问题 | 答 |
  | --- | ------------ | ------------------------------------------------------------------------------------------------ |
  | 1 | 叫什么 | `tool.entry-sources` |
  | 2 | 哪棵树 | 服务端 |
  | 3 | 能放几项 | 按键放，每个键至多一项。开着：租户的 plugin 放得上，官方的来源带锁 |
  | 4 | 键从哪来 | 来源自带的名字前缀，例如 `mcp__` |
  | 5 | 宿主给什么 | 发问的主体与租户；选定时给条目名；执行时给命令、参数、受理时固定的那条命令声明、调用号、这次是不是程序发起、中止信号；接续时另给检查点与等待的答复 |
  | 6 | 这一项交什么 | 带副作用的函数：列出、选定、执行；可选的一对：检查点的声明与接续 |
  | 7 | 什么时候读 | 每次搜索、检视、选定现取，按发问的主体所为之行事的租户的作用域问 |
  | 8 | 出错时 | 列出抛出、超时、交出前缀之外的名字：这个来源答依据不可用，别的来源与登记表照常 |
  | 9 | 撤下 | 先不接新的调用；在途的各有结局；然后才算撤完。用 Dynamis 的排空 |
  | 10 | 形状怎样变 | 带主版本与修订号，只加不改 |

- 来源可以是检查点来源：它另交检查点的声明与一个接续的函数，两样一起给。这样的来源，执行可以答「完成」或「暂停」；暂停带编码后的状态、一个等待请求与一段收场文字，形状与[检查点作者](#等待与检查点作者)的相同。暂停、停泊、答复、重新排队、恢复段与失效走检查点作者的同一条路径，没有为来源另开的分支：一个检查点只有一个后继，恢复段可能从同一个检查点再跑一次，所以来源的接续要对同一个检查点幂等。没交检查点声明的来源答「暂停」是来源违约，按失败收场，效果未知。
- 来源条目的等待用哪种契约由来源定：等人的用人工介入的那一种；别的契约由它的拥有者经自己的桥交答复，声明了后台可等的才许在后台等。条目许不许转后台仍由命令的声明给。plugin 的客人条目不许暂停。
- 来源独占一个名字前缀。交出前缀之外的名字是来源违约：这个来源答依据不可用，别的来源与登记表照常。
- 读这个点的一方按行事租户的作用域问：整个部署的来源每个租户都看得见，一个租户的 plugin 放的来源只有这个租户看得见。整个部署的来源带锁，所以租户放不出同一个前缀的一份来顶掉它。
- **专门的写法。** 这个点收 plugin 代码的写法归本组（`tool-host-local` 的 `guestEntrySource`），由应用放到点 `plugin.guest-forms` 上（规矩见 [plugin 的规格](../plugin/SPEC.md#一个成员怎样判)）。plugin 交 `{ tools }`：每个工具写一句说明、参数的规则、是读还是写、一个函数。函数拿到解析过的参数与这次调用的口，见不到主体。写法把它做成一个条目来源：键是这份来源独占的名字前缀，要以两个下划线结尾；条目名是前缀加工具名；执行时用这次调用的主体打开口，函数返回或抛出时关上。
- 这样的条目的能力身份是带来它的那份 plugin 资产；一道关口，由写法定，plugin 自己定不了；不许程序调用，不许转后台，不声明只读。函数抛出时读的答失败、写的答不知道，都不重跑。函数交回的值编成 JSON 文本作结果，超过结果上限是 `cause: result` 的失败。
- **借给 plugin 的口 `web`。** 应用把单机 Web 提供者作为一个口放到点 `plugin.ports` 上，键 `web`，一个方法 `fetch`：给一个地址，答最后的地址、媒体类型、正文的文字与是否截过；或拒绝并带 Web 的失败种类；或不可用。时限、跳转次数与大小的上限就是 `Web` 工具用的那一份，只发 `GET`。口的条目带着方法的说明（收什么、答什么），给 agent 看拓展树的工具照它答。
- 来源的一次调用就是一次工具调用。受理、账本、时限、结果保管与取消归本组，执行体取自来源。
- 选定是同步的，读来源上一次列出时留下的快照。
- 来源列出时可以连同原因交出拿不出合法定义的名字（`withheld`）。搜索结果在条目之后列它们，带原因，只在第一页；它们不能被检视或调用。
- 许不许不在本组判。条目带它背后那份资产的能力身份，调用方的放行判断按能力身份与关口找声明。
- 条目的 `programmable` 由来源交出：来源背后的资产没有本地作者，这项许可取自那份资产的一项设置，由来源的拥有者定义，缺省不许。本组只读条目上的结果，不读设置。对程序开放的条目照常声明每个命令给程序的数据；这个值由来源在程序发起的那次执行里交出，本组把它与展示内容一起保存，展示内容照旧受自己的上限约束。

### 受理与调用身份

- 普通调用方只给主体、租户与调用请求，不给调用或操作身份。来源按（租户，完整消费位置）原子地认回或分配调用身份并保存原请求与原主体。同键同请求认回原身份；同键异请求对有权者答 `conflict`；异主体、撤权或伪造租户一律拒绝，不经 `conflict` 泄露原记录。身份不复用，包括提供者重启之后。
- 调用请求只带定义的采用引用（采用与名字），不带定义本身。Tool 在收件时换回完整定义，次序固定：先认已受理的调用，用它受理时存下的那一版；再按采用找本租户存过的定义；最后按名字问当前目录。找到的定义的名字与采用必须与引用相同，三处都没有时答 `invalid`（`unknown-tool`），什么也不写。请求的摘要只按引用形式算，所以同一请求的摘要与定义大小无关，目录换代之后重发也认得回。
- 受理同提交固定请求、原消费位置、调用方式与来源、固定设置与限额、定义与实现的匹配、批判断依据与待办。受理之后固定的东西不再换：不换函数、不暗改参数、不迁到更宽松的环境、不自动重发。
- 参数没收全时不受理；收全但解析失败形成原调用的 `arguments` 失败终局，不执行原工具。原参数与生效参数都按原始 JSON 文本保存，不接受重复键。
- 调用方式由受信入口给出，脚本不能自报直接调用。程序调用的目标不是 `programmable === true` 时答 `unsupported`，不创建已受理执行。后台起步而定义不许后台时拒绝，这项检查先于 dummy 与参数检查。
- 未知分两种：`association-unknown` 没有引用，调用方保留完整意图并重复 invoke；`commit-unknown` 带原引用，沿原 invoke 接续。`rejected` 只说这一次尝试没受理；其中的 `unavailable` 是依赖暂时不可用，调用方等依赖恢复后以原意图重入。
- 调用引用与操作引用的文本不含租户。租户来自调用方的访问；另一个租户的引用在本租户里查不到，答复与不存在的调用逐字节相同。引用不授权、不证明调用存在。
- 每个命令与读取先核边界输入，再问资格，最后才读记录仓。拒绝不写记录，也不披露调用是否存在。守卫或记录仓抛出的异常只以依赖名报告，不带异常正文。

### 排队与名额

- 队列在租户内按并发范围（owner，key）划分。范围由其拥有者授予，受理时核授予；调用方不能换键绕过限额。名额与范围预算只管容量：同时有多少执行在跑。同一批动作谁先谁后不归本组，调用方在交出调用之前自己排好；调用方不能指望用预算等于 1 来排出先后。
- 同一范围内按耐久序号先到先得。取得名额同时要求同工具的持有数小于工具上限、范围的持有数小于范围预算；`null` 表示该项不限，先后次序照样适用。还在准备的较早调用不持有名额，但后来的调用不能越过它。
- 名额按队列条目的阶段计数，不看前台或后台。转后台、存活协程的等待、调用方退出与观察断线都不释放名额。检查点作者可靠暂停后条目停泊：不持有名额，仍计入队列容量；答复接受后以新序号重新排队。
- 条目只凭调用域里的释放依据删除：启动前拒绝的排除证据、已启动执行的可信原 final（物理结束）、暂停中收场的旧执行排除、记录仓确定拒绝后的最小失败终局，或失联收场带的连续性证据。仅逻辑收场不是依据。
- 调用域与队列域没有共同事务。推进先由调用域写 `queue` 待办，队列域再转换，调用域最后关闭待办。创建条目的提交断言它读到的调用域修订号，所以已释放的调用永远不会再得到条目。没有启动记录的 `held` 条目是待履行的义务，不是启动，只由同一操作身份的重做或拒绝了结。
- 队列容量满时，新的受理在提交之前被拒绝；已受理的超额调用按序等待，不是执行失败。等待者对账只删除有依据的条目、请求运行欠队列一步的调用，从不回退别的调用的条目阶段，也不向调用域写记录。

### 启动围栏

- 启动要进入一个启动排序域。它对一次启动签发许可，许可冻结所有适用守卫的当前修订号与请求的规范摘要；许可本身不授权执行。
- 受信执行边界先保存不可执行的待发胶囊，再 `consume`。`consume` 在同一排序内依次：认回已有受理或拒绝；核守卫修订号未变，变了就提交永久拒绝；核交来的请求就是签发许可时的那一份；核主体此刻仍能为这个租户行事；核目标此刻仍可用（由宿主装配的目标可用性端口回答，例如工具还在当前视图里、驻留与调用方式相符），答拒绝就提交永久拒绝，答不出就回 `unknown` 并保留原任务；最后写唯一受理记录。交给受信外发桥是启动的线性化点。
- 许不许做这个动作不在这里判：调用方在交出调用之前已经由放行判断判过，调用到了就按已放行受理。受理记录不记放行的结论、来由与授权引用，本组也不给按调用读放行的口；要知道一次放行凭什么，去那次放行判断的记录里找。
- 外层调用方经 `toolStartFence` 使它拥有的守卫失效。失效与操作记录共同提交之后才返回证据；拿到证据之前不能声称新的发起已被阻止。证据之后，带旧修订号的许可都被拒绝。围栏不停止已受理的启动，需要停止的逐个经公开 `control` 提交 stop。同一操作号配另一个守卫答 `conflict`，守卫只前进一次。
- 主体资格暂时读不到时不受理，答 `unknown` 并保留原任务，不读缓存的资格，也不写成永久拒绝。启动处不向人询问。
- `inspect` 在没有受理也没有拒绝时先提交排除标记并收回当前许可，再答 `not-started`；之前签发的许可从此不能被受理。`exclude` 排除整次调用的全部未受理启动；调用已受理时答 `conflict`，在途执行只能由控制停止。
- 权限与会话授权的撤回只影响之后的放行判断，不撤销受理，也不停止排队中或在途的执行；要停用控制。主体资格在 `consume` 之前失效时拒绝启动，之后失效不撤销受理；这个残余窗口从 `consume` 的再核开始到外部效果完成为止。拒绝启动是一个结局：启动的权威在发放许可时或 `consume` 时明确拒绝的调用以「没有启动」收场，不留在启动中等下一次推进；答不出来（依据不可用）的才保留并重试。
- 排序域里一个调用方等轮次的时间有上限，到点答 `unavailable`，不无限等：它没有进入轮次，什么也没决定；一个不收场的轮次挡不住同一租户后面的全部调用。已经进入轮次而超过上限的写不被取消，可能仍会提交；停止等待的调用方对自己的操作得到 `unknown`，不答 `unavailable`。
- 启动回执未知时查排序域与原绑定的 `inspectStart`，不再 start。`not-started` 只在原许可与全部延迟请求都被排除后成立，这时才允许同一启动身份首次执行。已经启动又失联的执行绝不经 start 重放。

### 执行事实、收场与结果

- 执行源按批次交事实，每批带来源、批号与游标。同来源同事件同值去重，异值整批拒绝。批次保存后才给保管回执，源收到回执才解除自己的责任；回执丢失时重送原回执，不回退游标。流结束或抛错只表示通道结束，不代替 final。
- 一次启动的原 final 只成立一次。事实流保存的是账本计划后的最终事实：首屏、各小通道与正文条目引用，从不保存原始返回值或正文字节。超过内联阈值 L、或某个模型可见文本块放不进一页结果的结果，在计划时写成系统正文并封存；缩不小的块放不进一页时计划答 `invalid`，不提交读不出来的结果。
- 收场在一次调用域提交里写唯一原结果版本、真实效果、交付待办、物理结束与全部后继责任，并把被引用的正文置为已关联、其余正文标为孤儿。重试认回原期限，不重新起算。
- 作者返回形态在装载时选定：普通返回经固定 codec 编码再解码、经 renderer 成文本；结构化返回直接给 `ToolResult`。不按对象有没有 `content` 字段猜。任何输出违反声明都形成 `cause: result` 的失败，不形成 `completed`，不重跑作者。缺省结果政策只收文本块与共享引用块，规则一变就是新修订。
- 作者在声明里写明结果带哪些模态。结果的内容区只收文字块与带内容引用的块，内联的媒体被拒。要模型直接感知的图片、语音或文件，作者经作者环境里「存产出」的口交出字节，拿回内容引用与媒体事实，放进内容区。
- 「存产出」是 Tool 声明的端口：给媒体类型与字节，交回内容引用与媒体事实。持有方是这次调用的引用，由宿主填，作者看不到，也指定不了别的持有方。命令在声明里写明它的结果除工具声明的模态之外另带哪些。端口没有提供者时，结果声明带非文字模态的命令不可用，原因是 `products-unstorable`，别的命令不受影响；执行中途提供者不在了，这个口答不可用。
- 工具的可用性按结果的模态核：确认的消费者原生收不下结果声明的模态，这种媒体又没有可用的转换时，工具在原位不可用并说明原因，不先执行再丢掉结果。
- `Files` 的 `open` 打开静态的 PNG、JPEG 与 WebP：字节先过图像预算，再交「存产出」的口；结果的内容区是一行文字说明加一个图片的引用块，文字里没有图片的字节。损坏、动画、超出预算或格式不支持的图片拒绝，不取动画的首帧。
- `Screen` 是只读的观察工具，两个命令：`screens` 列出屏幕；`capture` 截一块屏，可以指明屏幕，也可以只截屏上的一块矩形（`region`：`x`、`y`、`width`、`height`，按 `screens` 给的物理像素，越出这块屏答 `invalidInput` 并说怎样查屏的像素），用来把小的东西看大。它要一个带 `screen` 设施的落点。截到的一帧先过图像预算，长边超过配置的上限时缩小，再交「存产出」的口。结果的内容区是一个图片的引用块加一行文字：哪块屏，屏的像素尺寸与缩放，这张图盖住屏上哪块矩形（不给区域时是整块屏），这张图的像素尺寸，截取的时刻。模型凭这行文字把图上的位置换成屏上的位置。两个命令在同一个默认要问的门里。
- 程序数据只在程序发起的调用里算出并保存：直接调用的结果不带 `data`，与命令声明没有声明程序数据无关。程序数据 `data` 与展示内容来自同一原结果，同一次提交保存，不在事后替换。程序执行方只从 `data` 取业务值，不解析展示文本或过程帧。
- 旧实例排除之后到达的真实结果形成新的结果版本与它自己的交付，原逻辑终局与原版本不改。
- 失败不推出没有效果。系统终局（失败、不可用、中断）可以没有业务 `data`。已真实开始的后台执行最终只能是完成、失败或中断。账本自己形成的结果不编造用量与费用，没有测的时长记未知，不记零。
- 真实执行的调用同样有账目。执行收场的那次提交写第 1 修订；执行在逻辑终局之后才真实结束的，晚到版本的那次提交写下一修订并标明迟到。时长是执行开始到账本收到 final 的时间，任一时刻取不到记未知。没有计量来源的用量与费用留空，小计是未知。账目的主体是调用：转后台、读输出与重投都不多出一份。
- 执行收场的那次提交，同提交把这次调用写成一行用量事实：调用、受理时冻结的消费者引用、工具名、开始时刻、时长、结局与账目。晚到的修订替换这一行里的账目。用量事实不随到期清扫删除，它没有参数、输出或任何正文。
- 按范围列账的读口 `ToolAccounts` 读用量事实：按租户、可选的时间段（按开始时刻）与消费者范围分页，没有开始时刻的调用不落在任何时间段里，读取时报出有几笔。读取每次核账目读取资格，另一租户与不存在答复相同。这个读口不知道谁来读；跨调用的统计与展示归 Usage。

### 正文卸载与保管

契约面向分布式与异构部署，不假定账本与正文存储同事务，不假定读取有快照隔离，不假定时钟同步。

1. 账本是唯一权威。只有账本提交能使正文可达；期限只存在账本里，正文条目与正文存储都不存期限。
2. 正文字节不可变，只属于一个结果；身份不复用、不共享、不去重。正文存储没有业务状态，全部操作幂等；同序号异内容以条件写报告冲突。
3. 写入许可有时限，由存储校验。账本确认执行活跃、代次匹配且调用未结算后才提交正文条目并签发许可；许可绑定租户、调用、正文与执行代次，带截止时间，由装配的密钥签名。调用结算后不再续发；作者的写入许可在距截止不到 ε 时先续发，再交给存储。封存先由存储校验分块齐全与摘要，再回到账本提交；存储答封存即表示正文已耐久。
4. 按可达性回收。结果提交关联引用的正文并按期限排期；调用结算把未关联的正文标为孤儿，宽限期 G 之后排期。回收先删存储里的字节，再在账本记已回收；中途崩溃重跑终态相同，回收后存储不留行。
5. 读回先在账本核授权、结果版本与期限，再按范围读存储，读完再用本地时钟核一次期限，到期就答找不到。存储里没有字节时复查账本：已回收、已成孤儿或已进入到期窗口答找不到；只有已关联且明显未到期才报告完整性故障（诊断以 `integrity:` 开头）。读回不续期。
6. 按调用放置。每次调用的事实在它自己的调用域；租户级域只存跨调用状态。热路径按键读，不读整个域，所以每次调用的读写量与已结算调用数无关。
7. 条件提交可以断言同一租户分区里其他域的修订号。这一个机制取代各处的专用守卫提交。
8. 到期索引是账本原语，随提交原子生效，是回收唯一的调度来源。
9. 部署参数由装配给定，启动时校验，不满足就拒绝启动：时钟偏差 ε，许可时长 W，宽限期 G > W + 2ε，正文保留期限 > W + 2ε，预览除数 k；预览预算 P 取作者上限、系统上限与 ⌊L/k⌋ 的最小值，声明受理时核描述头上限加 P 不超过 L。

一次调用里键为 `output` 的正文是它的输出正文。未结算的调用，输出正文可以按调用读：只读到账本已确认保存的位置，按位置分页，同一位置两次读到的字节相同；没有输出正文、已回收与存储一时读不到各自可辨，读不到不答成空。读不写账本，不改变结果、终局、效果与账目。封存之后它是结果的卸载原文，照正文的规则保管与回收。读它的资格与读结果相同，每次按当前资格核。

作者经执行上下文的窄 writer 写正文：开始、追加、封存三步，序号连续，同号同内容认回；受信绑定一次保存完整正文也走这三步。正常返回时有开始了却没请求封存的正文，是未完成的作者输出，形成失败。系统兜底卸载只给机械预览，不编造摘要；全文取回是一次新的工具调用，只计取回本身的开销。

### 交付与调用状态的寿命

- Tool 把一个结果版本推给受理时冻结的消费位置；重投与恢复不重新选择去处。推送的认回键是（租户，生产者种类，调用，结果版本）；账目另按（调用，账目事件，修订）推送，每个调用先取得结果的 saved 再推账目。
- 转了后台的调用另有一份占位交付，推给同一个消费位置，认回键是（租户，生产者种类，调用，占位）。每次调用至多一份。占位不是结果版本：它没有终局，也没有效果，只带来源与调用身份。占位的 saved 先于原结果版本的推送；最终结果仍是原结果版本，关系是 `original`。占位与结果走同一套推送、退避、saved 与解除。
- 接收方只在同时证实四件事后答 saved：完整冻结载荷已独立可靠保存或有可恢复引用；原消费关联与责任已成立；原键、消费位置与内容一致且去重已成立；保留条件与待交付责任继续有效。未知答 `outcome-unknown`，不以普通失败盖过；`signal` 只停本次等待。接收入口按租户分额度与背压，一个租户占满不挡别的租户。宿主一侧的推送同样按租户排：容量按租户计，一个租户的排队不占别的租户的位置，没有位置的交付仍然待推。
- Tool 核对 saved 的键后，以宿主主体经受信的交付解除释放该版本；消费者自己解除走 retained 或 processed 两条路径之一。通知、展示、读到内容或开始处理都不是可靠交接。释放之前 Tool 保留原键与完整冻结载荷。
- 交付释放就是消费者的确认。确认之后调用状态至多再保存一段期限：删除时刻取确认时刻加 G 与各卸载正文期限中的较大者；到时还有未结责任或宿主还不能放手时推迟一个 G 再判；阻塞的 `clock` 待办只记执行结束时没有计时标记，不算未结责任。删除覆盖账本的调用域与宿主里属于该调用的记录，不留墓碑；删除之后的调用按从未受理答复。没有确认的调用不删除。
- Tool 自己守不住三条前提，它们是对消费者的要求：先保存后确认；保存后不用同一消费位置重发；确认之后超过 G 不再控制。违反前一条，结果可能在保存前被删；违反第二条，同一调用身份的函数会再执行一次。
- 转发的子调用的消费者是转发它的调用；子调用的记录不早于父调用的记录删除。
- 交付推送按接收方的回答退避。接收方答 `unavailable` 时，下一次推送等一个退避，连续每次翻倍，封顶 `maxMs`，等待未满不推；答别的就清退避，下一次从 `initialMs` 起。接收方答 `denied`、`invalid` 或抛出是确定失败：不退避，交付仍欠着，一个接收方抛出不停同一轮里的其他交付。两种情形每次推送都写一条具名警告，带租户、调用、交付与原因。退避表的条目只在交付仍欠着时存在。

### 前后台、计时与控制

- 前台与后台是等待与交付关系，不是两种执行。转后台保留同一执行、输入、环境、身份、效果与账目，不重启、不重跑、不通知作者，作者的执行上下文里没有前后台。关系只从前台到后台，至多一次，不回前台；仍在运行的名额不释放。占位的来源是发起即后台、控制、阈值或前台上限之一；最终结果仍交原消费位置。发起即后台有两种来由：请求要后台，或所选命令声明 `background.start: 'launch'`；后者不看请求，受理即在后台，`start` 只能与空的 `unless` 同时声明。
- 能转后台要三件事同时成立：定义对本次调用许可后台（函数工具看 `backgroundAllowed`，命令工具看所选命令的声明与这次给出的参数；受理时的发起即后台与之后的转后台问同一个判据）；调用此刻是前台；调用此刻没有在等待（运行中的外部等待与暂停中的 Ask 都算）。阈值、前台上限、用户操作、插队、设置与意图都不创造许可。在后台的执行只能开等待契约声明 `background: 'waits'` 的 Ask，别的等待答 `background-cannot-wait`；关系不因等待而变，在后台暂停的调用仍是后台，不占名额，收场时照常交原结果。
- 控制、阈值与前台上限三条路转后台，都是同一次条件提交：改关系、写占位、收口前台计时段、登记占位交付。它与执行收场在调用域修订号上排出先后：转后台先成立，原 final 之后作为原结果版本交回；收场先成立，转后台答 `already-ended`。所以一次调用的前台交还恰好一份：占位或原 final。
- 前台累计时间由耐久累计量与已提交的计时段决定。内部等待与后台期间不累计；重启不归零；时钟倒退或跨进程无法比较时报告未知，不增大剩余额度。阈值与前台上限由发起方在受理之前给出并在受理时固定，之后的设置变化不影响这次调用。两者不是 `null` 时，到点由账本的到期索引调度。
- 阈值到点，Tool 以自己的主体提交 `background`，转不了就 `rejected`；前台上限到点，提交 `background`，转不了就停止（原因 `foreground-limit`）。来源都指向自己的计时证据。
- 到期项在执行开始的同一次提交里按剩余的前台时间登记，转后台或收场的同一次提交里撤掉。宿主在每次推进调用之前提交本租户已到期的计时控制，并在下一项到期时唤醒那次调用；触发失败时到期项照留，下一次推进再触发。计时控制的控制者是 Tool 自己：主体是一份固定的 Tool 证据，派发停止时不向调用方的资格提供者核对。前台上限对转不了的调用先给前台 `interrupted` 逻辑终局（原因 `foreground-limit`），再请求停止，真实结果存成晚到版本，与撤回前台相同。
- 每次公开控制分配新的操作号。意图有三种：
  - `stop` 请求停止，原消费位置继续等真实收场。
  - `withdraw` 必须带 reach：`all` 撤回目标的前台与后台；`foreground-and-unadmitted` 只在目标于控制提交时是前台关系才撤回它。reach 不及目标当时的关系时，控制照样提交，回执进度为 `rejected`，原因 `out-of-reach`，调用不变。
  - `background` 必须带 `otherwise`，说明转不了时怎么办：`reject` 提交控制，进度 `rejected` 并带原因，调用不变；`withdraw` 按 `withdraw(foreground-and-unadmitted)` 撤回前台。公开调用方只能用这两种；`stop` 只给前台上限用。「能转就转，不能就撤回」由 Tool 在一次提交里判，因为要读的许可、关系与等待都是 Tool 的事实。
- reach、`otherwise` 的判断与提交原子完成。下表是控制意图对调用状态的全化表，每格是一次条件提交：

| 调用状态             | `background`，能转              | `background`，不能转 | `withdraw`                                                                       | `stop`                       |
| -------------------- | ------------------------------- | -------------------- | -------------------------------------------------------------------------------- | ---------------------------- |
| 未开始，前台         | 转后台，之后照常排队启动        | 按 `otherwise`       | 排除未受理的启动，以 `interrupted` 收场，效果 `not-occurred`                     | 同 `withdraw`                |
| 运行中，前台         | 转后台                          | 按 `otherwise`       | 前台先得 `interrupted` 逻辑终局与前台 final；停止待办照发                        | 停止待办，前台继续等真实收场 |
| 暂停，等 Ask，前台   | 不可达（暂停在等待）            | 按 `otherwise`       | 以 `closedResult` 收场                                                           | 同 `withdraw`                |
| 暂停，等 Ask，后台   | 进度 `relation-changed`，不再转 | 同左                 | `all`：以 `closedResult` 收场；`foreground-and-unadmitted`：`out-of-reach`       | 以 `closedResult` 收场       |
| 未开始或运行中，后台 | 进度 `relation-changed`，不再转 | 同左                 | `all`：停止待办，收场时照常交原结果；`foreground-and-unadmitted`：`out-of-reach` | 停止待办                     |
| 已收场               | `already-ended`                 | 同左                 | 同左                                                                             | 同左                         |

- 前台目标被撤回时可以先形成 `interrupted` 逻辑终局与前台 final；真实结果、效果与成本沿原调用另存为晚到版本，不恢复入队资格。执行还在跑时它照占名额，晚到版本收场时才释放。撤回之后执行失联时，只把执行记为失联并释放名额，逻辑终局不变，也不再有晚到版本。没开始就被停止或撤回的调用，同一次提交排除启动，之后释放它的排队位置。受理控制不等于物理停止；只有实际收场证据证明 `stopped`。
- 中断原因分三类，各自可辨：控制请求（带控制操作号与是否撤回）、前台上限、恢复被拒（带排除依据）。工具自身失联属于失败，不与有意中断混成一类。

### 程序调用与子调用

- 程序执行方是一个工具的作者。它在自己这次调用（父调用）之下，经宿主挂给这次调用的程序调用能力发起子调用。本组不认识程序的语言与引擎，只认位置、目标与参数。
- 每次发起带一个序号：由执行域按程序发起的次序给出，从 1 起，不复用；序号 0 留给宿主为装入程序而发起的调用。子调用的消费位置是（程序调用方，父调用，序号）。受理按消费位置认回，所以同一位置的重送、查询与恢复都认回原调用，不产生第二次执行；两个位置上参数相同的调用是两次动作。
- 发起一个位置的次序固定：核程序自己的上限（调用总数与同时在途数，由程序执行方给出）；按名字在此刻的视图里选定目标，核它可用、`programmable`、所选命令与参数对程序开放、参数符合契约；在父调用域登记这个位置；问嵌套动作准入；放行后在父调用域记「已交出」，再交出调用；等它的原结果版本；承接。登记之前不过的，程序收到具名的拒绝，不留位置；登记之后不过的，位置以排除收场。
- 程序不写意图。目标命令要意图时，由准备子请求的可信来源写一句固定的话，说明这次调用由程序发起；标签照常在受理时固定。
- 子调用的固定请求：调用方式是 `programmatic`，来源带父调用与位置；并发范围、请求方作用域、工作目录与文件范围取父调用钉住的那一份；等待方式是前台；时限按目标自己的设置算。经 `Tools` 再转一手时来源不变。程序执行方自己不许程序调用，所以直接与间接的递归在受理时答 `unsupported`。
- 嵌套动作准入是端口，本组不判许不许（TL-26 不变）。它答可以、不可以或此刻答不了：答不了时位置留在已登记，过后以同一位置再问；提供者缺席时程序调用答不可用。交给这个端口的是位置、目标的精确采用、命令与生效参数，和直接调用时交给放行判断的动作是同一份。
- 位置表在父调用域里。每个位置有序号、子调用引用与状态：已登记、已交出、已排除、已承接。登记、交出、排除、承接与关闭都是父调用域的条件提交；关闭之后的登记与交出被拒绝。父子两个域没有共同事务：交出记在父调用域，子调用的受理是之后的另一笔提交，可以晚于关闭。
- 程序正文正常返回时关闭登记，不立屏障：已登记的位置照常走完。父调用只在每个位置都已排除或已承接之后以完成收场；正文返回而子调用还在途时，父调用没有完成。
- 父调用以别的原因结束时立关闭屏障：同一次提交关闭登记，写下屏障的范围、原因与那一刻每个位置的关系（前台、后台、还没受理），并为每个没收场的位置写待办。范围取自原因：程序异常、资源超限、确认失去连续性与 `stop` 是全部；`withdraw` 取它的 reach。范围只扩大，原因不改写。屏障是启动排序域里的守卫：范围之内的子调用在屏障之后不首次启动，也不恢复；范围是前台与未受理时，屏障成立那一刻已在后台的子调用照自己的规则启动与收场。每个位置的守卫归 Tool 的宿主自己：处置时由宿主抬高它的修订，不向调用方的访问守卫再问一次（调用方已经过了父调用的写入核验）；别的拥有者作废自己的守卫仍走带资格核验的那个口。一遍处置里有位置没能往前走时，这一遍答那次失败，不答成功。
- 屏障成立之后逐位置处置，每一步可重入：已登记的排除；已交出而受理不明的先按原身份查，没有受理就先排除它的受理操作，再记排除；范围之内已受理的，经公开 `control` 逐个请求停止，每项的进度（受理、被拒、未知、已停）单独保存。无权控制、停止被拒与结果未知的位置继续保管与跟踪。父调用可以先收场；待办留在父调用域，由恢复扫描接着做，不依赖活着的程序。
- 承接：子调用结果交付的消费者是程序位置。「已保存」是父调用域里这个位置记下结果版本的那一次提交，不复制正文。转后台的占位只更新位置的关系，不是结果，不解开程序的等待。父调用收场之后到达的结果照常承接到原位置。子调用的记录不早于父调用的记录删除。
- 程序拿到的值：终局是 `completed` 并且命令声明了程序数据时，是 `data` 的值。命令声明了程序数据而这次完成的结果没有 `data` 时，作者这次只给了要读的文字（例如设施拒绝了这次读写）：程序收到种类为 `failed` 的失败，效果记不知道；缘由在展示文本里，程序读不到，它进父调用的子调用摘要。别的终局与拒绝是具名的失败，带种类与效果（没发生、发生了、不知道），不变成空值。程序读不到展示文本与过程帧；带内容引用的块，程序拿到的是引用。
- 计时：程序执行方按执行域报告的计算时间计，不计等子调用与等人的时间；它没有前台上限，不许后台。父调用在程序运行期间照常占着自己的名额，等子调用时也不让出；子调用各自计入目标工具的上限，在父调用的并发范围里按序号取得名额，不计入范围预算。
- 父调用的结果有两部分：程序选出的输出，与本组从位置表生成的子调用摘要（各种结局的数目，每个没有正常完成的位置一行，还没收场的责任）。摘要不由程序提供，程序改不了。失败的原因区分程序异常、资源超限与失去连续性；由控制结束的保留原控制的原因。父调用的账目只计程序执行的资源，子调用的账目各在自己的调用上。

### 等待与检查点作者

- Ask 等待决策方的决定，没有超时、没有默认答案；暂停在它上面的前台调用不能转后台。调用方句柄释放、断线或查询失败都不作废仍有效的等待。同一请求只有一次有效决定；`no-answer` 与 `declined` 是有效决定，不是许可，也不是失败。普通 Promise 与 I/O 不构成等待。
- 取消与答复在原调用的事务里排序：取消先成立，后到的决定不被当作答案；答复先成立，保留它，随后的取消阻止还没放行的后续动作。决策方答出三种决定之外的值是它的故障，报告出来，不当作人的答复。
- 等人的等待只有一种请求契约，归人工介入（`human-intervention-tool`）：Ask 与别的检查点作者都按它交出卡片、读回答复，本组的作者不另定义卡片或答复的形状。这种等待只用来向人要信息或选择。工具的作者不经它问「许不许」：许可只由准入对动作判断，要人决定时由准入出放行卡片；人在这种等待里的答复只交回原调用，不产生任何授权。
- 等另一个 agent 的报告是第二种等待，请求契约归派发（`dispatch-tool`）：只有工具 `Agents` 的派发命令用它。它的契约声明 `background: 'waits'`，发起即在后台的派发调用在后台挂着它，`BkgToolCalls terminate` 只关这个等待。它与等人的等待守同样的规矩：没有超时，没有默认答案，前台暂停在它上面时不能转后台，控制关闭等待时调用以 `interrupted` 收场并交出暂停时写下的那段收场文字。答复由契约的拥有者经它的桥交来，本组按契约的名字找桥，不认识答复的含义；桥对一次交付只答已交、等待已关或读不到，「等待已关」与调用收场在同一笔提交里成立，所以一份答复不会既被采用又被告知已关。本组的受理、暂停、恢复与失效对两种契约是同一条路径，没有按契约分的分支。
- 检查点作者按段执行，每段是一次 `initial` 或 `resume`。段的上下文只有过程输出与取消信号，没有 `wait`，所以作者只能以返回 `suspended` 的方式等人。装配给一次调用挂的能力，第一段与每个恢复段都挂：同一次调用、同一份请求，能力相同。暂停带编码后的状态、一个按人工介入等人契约写的等待请求与一段 `closedResult` 文字；控制在人作答前关闭等待时，调用以 `interrupted` 收场，结果就是这段文字，不再运行任何段。
- 暂停的提交同时写检查点、状态、等待 `opening`、登记待办与停泊待办。请求原文与状态由账本保存，摘要与证据核对后各存一份，调用收场时删除。决定接受后重新排队，取得名额后从同一检查点运行恢复段；一个检查点只有一个后继，恢复段不重跑已完成的段。恢复段在运行它的进程里重新准备环境，不接管旧进程的环境。
- 检查点状态、等待请求与等待答复各有上界（`CHECKPOINT_STATE_MAX_BYTES`、`WAIT_REQUEST_MAX_BYTES`、`WAIT_RESPONSE_MAX_BYTES`），使写入它们的每一笔提交都放得进记录仓的命令上限，整个调用域远小于整域读取上限。
- 暂停中被 stop 或 withdraw 时，同一笔提交让调用收场、关闭等待、写登记失效与释放待办；效果记为未知，因为已运行的段可能有过效果。Ask 等待中的前台调用不能转后台。
- 暂停的推进里，提交未知或修订陈旧不移动任何已知事实：按认回的或重读的状态在同一次运行里重做这一步，直到调用到达它的等待。端口暂时答不出的，再问；端口答「未暂停」或「拒绝」是裁决，没有哪次运行重复它；其余失败也是裁决，待办停止本次运行。
- 已收场调用的等待要登记失效。失效操作的身份由调用与等待派生；回包不确定时经原操作的 `inspectOperation` 认回，不换身份重发；`excluded` 证明原失效不会落地，同一身份可以再发；决策方明确拒绝时待办记为阻塞并保留原因，调用的终局不变。
- 恢复段的环境准备不按首次启动处理：被拒绝时调用保持暂停并带原因，只有 stop 收场，不按从未启动收场；环境随已不在的进程丢失时重新计划恢复段；恢复段的启动意图已经记下、启动还没被受理时丢失也一样，在原启动身份下重新准备环境，不退回暂停。首次启动被拒绝或丢失才按从未启动收场，启动意图已记下之后丢失的也算，原环境的清理仍归适配器。已被恢复段 `continued` 的等待在调用收场之前关闭。
- 恢复段的答复值是普通 JSON：`json-text` 的树在交给作者之前解码。

### 恢复与推进

- 调用有待推进的工作，指它有 `pending` 的待办，或暂停中且有处于 `opening`、`open` 或 `responding` 的等待。账本在每笔调用域提交里算出这个标记，与记录同一事务写下或删掉。`blocked` 的待办不算，它等外部处置。
- 恢复扫描只读标记，按租户再按调用分页，把调用交宿主调度。重复调度是同一个提示，推进按调用当前的阶段与待办走，已启动的执行不会重新启动。
- 推进协程只经账本命令写记录。提交未知、修订陈旧与被否定答案排除都不停止推进，重读后以同一身份重做，但都不算进展。每次运行步数有上限；无进展的重调度按重试延迟翻倍退避，有上限，有进展就清零。被宿主中止的运行不重调度。
- 记录仓对一笔提交答确定拒绝时，那笔提交永远写不进去。没有启动记录的调用改写一条最小的失败终局（`runtime-lost`，诊断带拒绝原因），照常交付与释放；已有启动记录的调用停在这一步，不收场。账本对这笔提交立刻答确定失败 `invalid`（`field: storage`，带存储给的原因），不重读重决，也不消耗提交的重试次数。
- 否定答案（`not-accepted`、`not-committed`）必须排除该操作全部在途提交：账本写一条排除记录推进域修订号，之后按旧修订号准备的提交都失败。认回先于排除：已有该操作记录时答原回执。
- 只等人答复的调用休眠：移出宿主的内存表，不占容量，不再按拍子问决策方。唤醒提示、按租户的兜底重扫或内存表腾出空位把它带回来。
- 启动扫描与周期重扫不能由调用方的那一问取代：已经交回结果而还欠别的域一步的调用、后台调用、经 Tools 转发的子调用与不经 Agent 发起的调用，都没有调用方会来问。
- 跨租户的待办扫描按租户文本的顺序逐个读已发布目录里的租户事务域，每个域各读一次，整个扫描不声称是同一时刻的快照。任一个域读不到时整页答 `unavailable`，不答更短的页，诊断写明是哪个租户。
- 重试延迟必须在 1 ms 到 2147483647 ms 之间：0 会让失败的调用紧循环重跑，更大的值会让计时器在 1 ms 后触发。

### 活体、失联与收场

- 调用方以调用引用经 `contact` 问「你的活体还在推进这次调用吗」。回答只有四种：`holding`（还拿着）、`settled`（有结果了，结果正在或将要按正常的路交回）、`not-accepted`（没受理过）、`unknown`（此刻答不了）。没有「不在我手里了」。
- 回答之前先过访问核对，再读这次调用的记录；没有查看资格的主体得到拒绝，不论调用在不在活体里。这一问不等执行环境，不写账本，不加新的落盘状态与扫描。
- 「活体里有」指此刻真的有东西在推进它：宿主的内存表里有它，它由重调度、驱动的退避或排着的结果交回叫醒。休眠的调用不在活体里。
- 记录在而活体里没有的调用，回答时接回活体，之后由活体照常推进：

| 调用记录                                       | 活体里有                                    | 活体里没有                                                           |
| ---------------------------------------------- | ------------------------------------------- | -------------------------------------------------------------------- |
| 没有这次调用                                   | 不可达                                      | `not-accepted`                                                       |
| 没收场：已受理没开始、暂停着等人、由本实例开始 | `holding`                                   | 接回；接进去答 `holding`，接不进（内存表满、宿主正在停）答 `unknown` |
| 没收场：由别的实例开始过                       | `holding`（活体正在给它收场）               | 判断来源给出证据就接回，答 `holding`；没有证据不接，答 `unknown`     |
| 已收场                                         | `settled`，结果还没确认的让结果交回重新排上 | 同左                                                                 |

- 当前段属于别的实例、执行阶段是 `starting`、`live` 或 `unknown` 的调用，原执行可能还在旧实例里运行。判断来源没有证据时，宿主从内存表放掉它，不写账本，不接上，不重启。
- 有证据时由新的活体收场，次序固定：先让执行环境按原资源身份停掉这次执行名下的受管资源并确认，确认之后把工具宿主资源账本里这些资源记成已确认停止；再记失联：一次账本提交把执行记成 `lost`（带连续性证据），调用以 `failed`、原因 `runtime-lost` 收场，效果记为未知，同一次提交把没了结的控制记成调用已经结束；最后结果按正常的路交回原消费位置。确认不了就不记失联，调用留在活体里按驱动的退避再试。没有受管资源的进程内函数，停掉这一步是空的。
- 已经存下原 final、只差保全的调用不记失联：停掉资源之后照那份 final 收场。
- 开始过的执行绝不重跑。收场每一步可重入：记失联的操作身份由调用与启动记录派生，重送认回原结果。
- 收场之后，账本里与这次执行有关的记录（资源、控制、队列位置、等待登记）与事实相符：资源记已停，控制记已结束，名额以失联为依据释放，开着的等待关闭并留登记失效的待办。

### 保留范围与接手

- 会话的保留范围长寿：开着，然后关闭，不再开，也不删除。关闭之后它保留自己的记录、条目与结束事实，存储重启后仍在；对已关闭范围的计划、许可与接手一律答 `closed`。
- 预留留在创建者自己的获取记录里：创建者记自己未被接手的预留的停止，范围接手之后的键归范围记录。接手是对范围记录的一笔提交，断言获取记录与原调用不变；获取记录的 `handedOver` 由范围的条目派生。
- 被接手进程的确认停止，把结束事实记在范围域里自己的键下，读一条结束事实只触一条记录。范围的记录不随调用数增长，结束事实随范围寿命增长。

### 独立执行域

- 被接受的 `emit` 按序到达接收方。收尾（`finish`）先等此前接受的全部输出到达接收方。
- 信号中止先于交接就答取消；等待中的屏障或等待，在答复到达后以取消收场。第一个接收方没收下的输出处，屏障不再等待并答该失败。
- 以失败收场不等卡住的输出，接收方保留已收下的。以返回收场而仍有等待打开是无效。首次收场的种类不被后来的收场替换。

### 观察

- 普通消费者经 `instances.current` 取当前发布代次的公共引用与当前权威状态，经 `observation.observe` 先取一致快照，再接从该观察者上一游标起的增量。没有 `after` 续读：断开或出现缺口后重新取引用与快照。
- 发布代次就是（实例，代次），每个代次一条新的过程流；旧引用不接到后继。已建立的观察在代次被替换时以 `producer-ended`/`stale-instance` 结束，执行收场且发布源关闭时以 `producer-ended`/`closed` 结束；对非当前代次的新观察请求结束于 `stale-stream`，不联系任何句柄。
- 运行时门面在交出每一帧之前按同一调用与同一访问再核资格。拒绝时先移除订阅并丢弃排队，再结束于 `denied`；资格来源不可读时同样结束于 `unavailable`。
- `current` 只读状态，不写任何记录：未受理的引用答 `invalid`，不排除在途的受理。要据「没有」重交的认回只经 `lookup` 与 `queryOperation`，否定答案的排除只在那里发生（见「恢复与推进」）。
- 实例目录缺席时 `current` 整次答不可用，不答 `current: null`；`current: null` 只表示核权后确无路由，不证明未执行、结束或丢失。持久查询、控制、读取与交付不依赖目录或 Catalog。
- 过程帧只给人观察，不进入消费方的请求内容或程序的数据通路。保存先于发布；节流只合并同块增量，裁剪要保留数量与原因。没有过程块不造过程消息，发送失败不使执行失败。
- 遥测只观察已确认的提交，不是回执，也不是提交的条件。

### 对客户端开放

- 一次调用的事实由 Tool 自己对客户端开放，不经发起它的那一方转述：第三方凭调用引用向被调用的一方要。
- `tool/v1` 只有读，五个读口都按调用引用：`list-call-children` 按页列出一次父调用的位置表，每项带序号、目标的工具名与命令、动作预览、位置的状态与子调用引用；`read-call` 读阶段、关系、终局、效果与每个控制的进度；`read-call-result` 按页读结果；`read-call-output` 按位置读输出正文；`observe-call` 先给一致快照，再给过程帧的增量，规则同上一节。
- 控制的进度原样给出：受理、停止已证实、已结束、被拒、未知各自可辨，受理不显示成停止。
- 每个读口每次都按同一套资格守卫核主体；别的租户的引用、没有资格的引用与不存在的调用，答复逐字节相同。
- 协议里没有控制。停不停一次会话里的调用是那个会话的业务决定，要同时改它自己的事实（见 `packages/session/SPEC.md`「终态、控制与取消」），由会话的协议开放。

### 界面模块

- `tool-ui` 是客户端的界面模块，回答一件事：一次调用写到哪了，放在装配指定的位置上给人看。`./cordis` 入口导出工厂 `createToolUiModule(options?)` 与选项类型 `ToolUiOptions`；根入口另导出输出的存放 `CallOutputStore`、视图 `CallOutput` 与上限 `KEPT_CHARS`。模块注入 `tool/v1` 的协议客户端：协议没挂着时不加载，撤了就卸载，放进去的项随作用域撤掉。它只依赖 `tool-protocol`、外壳契约、客户端装配、SDK 的客户端核心、公开契约与共用界面件，不依赖别的 Tool 成员与别的领域。
- 选项给了 `callDetail` 时，模块往这个[拓展点](../../.meta_harness/design/ubiquitous_language/terms/architecture-core-and-extension.md#ul-extension-point--拓展点--extension-point)里放一项：标识 `tool-call-output`，次序 0，收到的对象是 `{ session, call }`。桌面应用把会话的 `sessionCallDetail` 交给它，于是每项后台调用的输出出现在会话「后台」页签里那一项的下面。本成员只写自己要的对象形状，不导入会话的界面模块。外壳还没给租户时什么都不画。
- 输出按调用引用经 `read-call-output` 读：视图挂着时从上一次读到的位置接着读，每 2 秒一次；同一个调用的几处视图共用一份存放，最后一处卸下时停下。屏幕上至多留最新的 `KEPT_CHARS`（8000）个字符，更早的不显示。
- 观感照[视觉规范](../../.meta_harness/agents/skills/visual-standard/canonical/SKILL.md)；颜色与语气的规则见[规则与 token 的索引](../../.meta_harness/agents/skills/visual-standard/canonical/references/rules-index.md)的 C3、C4。输出是会话后台调用那一行原地展开的内容，不是单独的一块；那一行的其余部分（命令与预览、停止的三段进度、最后一行输出）归会话的界面模块，输出排在最后。下面每一句通知都写明语气：注意是 `InlineNotice` 的 `caution`，琥珀；中性是 `neutral`。正常的状态不画字。
  - 有输出：`CodeSurface`，等宽，自己滚；顶上一行写格式，它与正文之间一条细线，正文在细线下面滚。可访问名称是「调用的输出」。新读到的字接在后面，不逐字动。
  - 输出还在写：`CodeSurface` 下面一个中性的状态词「输出还在写」，不是动画。写完了不画字。
  - 还没读到第一次：活动标记（`LoadingIndicator`）加「正在读输出…」。
  - 空：一行弱墨的说明字「还没有可读的输出」（中性）。
  - 读不到：一行 `InlineNotice`「输出现在读不到。」，结果的原名收在「详情」里，不直接给人看。`denied` 与结果不知道（`uncertain`）是中性，别的结果是注意。视图挂着时照样接着读，读到了这一行就换成输出。
- 选项给了 `callDetail` 时，模块另放一项，标识 `tool-call-children`，次序排在输出之前：这次调用有位置表时，按序号列出每个位置，一行写序号、工具名与命令、动作预览与一个状态词（排队、运行、等人、在后台、完成、失败、被拒、已停、不知道）；没有位置表、还没读到或读不到时什么都不画；读到过之后某一次读不到，留着上一次读到的。状态词取共用件的状态词表：排队中、处理中、待确认、在后台、已完成、失败、被拒、已停止、未确认；还在准入里的位置与在等人答复的子调用都是待确认（等人的琥珀）。它与输出共用同一种读法：视图挂着时每 2 秒读一次，每次读完位置表的每一页，卸下时停下。可访问名称是「子调用」。
- 选项给了 `toolCall` 时，模块在这个按键选画法的点上给键 `Code` 放一份画法，收到的对象是 `{ session, call, name, arguments, state, result }`。桌面应用把会话的 `sessionToolCall` 交给它，于是对话里一次 Code 调用画成：会话自己的那一行过程行（名字、状态词、参数与结果照旧），下面一个收着的「程序」（`Disclosure`，展开是 `CodeSurface` 里的程序正文，格式名 TypeScript；程序是按路径给的或参数还没读出来时没有这一项），再下面是这次调用的子调用列表。列表只在 `call` 是工具调用引用时读；`call` 不是引用时不读也不画。外壳还没给租户时只画会话自己的那一行。
- 反馈：本成员只读，没有动作，也不弹提示。用到的共用件：`CodeSurface`、`StateWord`、`InlineNotice`、`LoadingIndicator`、`Disclosure`。

### 装载、登记与换代

- 登记键是（来源层，能力身份，资产版本）。来源层四选一：官方、组织、租户、工作区；它只取自核验后的来源，不取自登记者的租户。来源的核验按层分：官方的核发行清单；租户的核这个租户此刻在持的就是这一份资产、这一版，并且没有被禁用，准入要求主体为这个租户行事。工作区层的登记对任何主体都不可见，现在没有装配用它。同一 fiber 以同一装载摘要再登记认回原贡献，其他同键登记一律 `conflict`；原贡献释放后新登记才成为后继；晚到的旧释放比较 token，只撤自己。
- 工具这个资产类别的定义放在点 `tool.tools` 上，规矩由 `tool-cordis-contract` 的 `toolToolsPoint` 给出：键是工具名，键公开，随可用性的观察到客户端。发行清单里的每个工具是整个部署这一层的一项，每个租户安装进资产的那一份是这个租户范围的一项。它是定义的登记，与上面活体的登记是两件事：绑定的解析不读这个点；常驻规划对发行的工具不读它，对发行里没有的名字由装配读这个点上的持有，取这个租户此刻生效的那一份。
- `resolve` 在本租户可访问的同形贡献中选：记下的键仍 live（含 draining）时优先它，否则取 live、非 draining、登记序号最小的一份。回退不比较资产版本，不做层序选择；向胜出者前进只在采用点发生。
- 换代协调者是作者插件句柄的唯一持有者，三个动词都向目标态收敛、可以重复调用：`ensureLoaded` 先核来源与包摘要再 import，授权之前不运行不可信模块的初始化；`unload` 先关闭新采用，读完全部持有者引用，按 draining、等在途收场、交接、释放贡献、销毁 fiber 的次序走，任一步没完成就停在 `draining`；`sweep` 按持有者记下的键重装。
- 保留义务：有有效持有者引用且没有同形 serving 替代的贡献，协调者不销毁。持有者引用读不到时保留并重新开放该键，不能证明没有引用就不撤。工作区层的贡献不作为 serving 替代。
- 实现的替换就是对新版本 `ensureLoaded`，旧版本在引用归零后收走，不存在原地替换。突然失依赖时登记随 fiber 撤除，在途调用保持未知，不换最新实现继续原执行。
- 结果接收方按 consumer owner 登记，登记绑在调用方 fiber 的 effect 上；同一 owner 已有存活登记时第二个登记失败，旧 fiber 已撤除或正在撤除时新登记替换它。登记不授资格，只在同一进程内成立。

### 记录仓

- 每个账本域一个修订号。提交只在被写域的修订号等于期望值、且每条同租户断言的域修订号等于给定值时生效，否则答 `conflict`，什么也不写。断言另一个租户的域在提交之前就拒绝。生效的提交总推进修订号，没有空操作捷径。
- 读取对同一提供者经手的提交即时可见。答「没有」总是存储当时的内容。按旧内容做出的写入被修订号拒绝；至多一次的事由启动围栏守；待办的对象本来就接受重复执行。
- 固定请求只在受理那次提交里写一次；之后每次提交的大小与请求大小无关。请求大到一条命令放不下时，受理当场被确定拒绝，调用不开始。
- 记录里只存定义的摘要。Tool 按（租户，摘要）存它采用过的每一版定义，各存一次，另记哪条记录引用它。缺的才写：一条命令放得下时随受理的提交一起写；放不下时先分块写，在受理那次提交里拼起来核对摘要再存。引用它的最后一条记录删掉或被覆盖时，同一次提交删掉这版定义。读记录时把它引用的定义一起带回；引用的定义不在时答不可用。
- 整域删除带期望修订号，一次删掉该域的记录、到期项与修订号，不留墓碑；另一个租户的同名域不受影响。正文分块与清单不属于任何账本域，不推进修订号。
- 租户只经受信目录取得事务域；每条语句以租户为第一过滤条件。读取被拒绝或失败答不可用，不答空。
- SQL 记录仓把一笔提交的答复映射成端口答复：原因来自此刻的存储状态（同一笔提交以后可能被接受）答 `unavailable`；原因来自提交本身或装配（再发多少次都被拒绝）答 `rejected`。
- 整域读取超过行数上限时拒绝，不截断；读取器答超出输出上限同样拒绝。
- 读回记录的摘要只取决于规范 JSON，不依赖存储是否保留键序。

### 凭据

- 凭据引用依次从租户、该租户所属组织、官方来源选；只有上一层确定没有配置才查下一层。选定之后秘密保管答任何失败都终止解析，不换来源、不用缺省秘密。失败闭集是 `missing | denied | invalid | unavailable`。
- 能力只在一次使用期间有效：每次使用先重核资格与秘密绑定，动作结束后一律撤销，再返回结果或原样重抛。撤销失败不能报告成功；动作与撤销都失败时一起抛出。能力、秘密与解析器不进入固定请求、日志、目录、供给块或持久记录。提供者缺席时答不可用，不降级到环境变量或共享默认凭据。

### 元工具作者

- `execute` 受理目标之后，在这次尝试已有的时限之内等目标收场：等到了，直接带回结果；没等到，答进行中与读结果的下一步。它不为此另设时限，也不改变目标的前后台。
- 搜索结果里每条命令带一行参数签名，由命令的参数契约机械派生，与检视里的用法行同一个来源。带条件「只要程序能调的」时另给函数签名，两样互不替代。
- `read_result` 的引用是公开、无状态、可解码的规范文本，绑定固定结果版本；引用不授权，每次读取由运行时按当前资格核。正文页给可读文本、完整 JSON 值或明确标为片段的 JSON、完整的 JSON Lines 记录，不要求模型解码 base64，不把片段冒充合法 JSON。回应本身的预算不超过运行时的内联阈值，否则回应会被再次卸载，模型读不到任何一页。
- 发行作者的描述只写用途与固定事实，不含运维构造值，所以发行清单能固定定义摘要。返回文本受各自的字节上限约束，截断时如实标注；作者截断或设施丢弃的输出，运行时卸载补不回来。
- 需要执行环境的工具，固定请求带这次调用的工作目录，以及它所属的工作区与实例（会话没有附着工作区时只带目录）。它由请求来源在受理时给出，是固定请求的一部分：受理之后不换，重建之后的恢复仍用它。请求来源给不出工作目录时，这次调用答不可用，不改用别的目录。经元工具转发的目标调用继承父调用钉住的目录：目标的固定请求与父调用的这一项不同（一边有一边没有也算不同），转发关联不成立。
- 工作目录不是作者的构造值。作者从这次调用的环境里取它：Files 把相对路径按它解析成绝对路径，解析只换字符串，不授予访问；Shell 的一次性命令与新建的终端默认从它开始，调用可以另给目录。留着的终端之后在哪个目录，随终端里的命令变，不随会话更换工作区变。批量补丁先对全部目标做预检，全部通过才提交一次；未知不表示全批落盘，也不自动重发。
- 一次调用的文件范围和工作目录在同一次受理里钉进固定请求，之后不变：读可以到哪，写可以到哪。作者从调用的环境里取到它，也取到工作目录；两个是分开的值。取落点时文件范围原样交给执行环境，由围栏执行，本组不自己判文件请求。
- Shell 在启动之前做一次预检，用的是这次调用的文件范围。起始目录不在写范围之内，或者脚本里明着写出的路径、重定向的目标在范围之外时，不启动，答复里点名这个路径。预检只判字面的路径：含展开的词不判，拆不成词的脚本不判，命令位置上的词不判。可执行程序不是 POSIX 一族时只核起始目录。预检是尽力而为的，不是隔离：程序运行时自己去读写的地方它看不到。
- Files 不做预检，读写在不在范围之内由围栏决定。围栏拒了一次读或写（`notAuthorized`），而这次请求的路径照这次调用的文件范围在范围之外时，答复点名这个路径与它是读还是写，并说明是「工作区之外的文件」这项设置拦下的（`reason=outsideScope`）；判断用执行环境契约的同一个 `withinScope`。路径在范围之内、或者这次调用没有钉范围时，拒绝照原样答。
- Shell 的结局如实区分停止已确认、未确认与未知，未知的退出码不显示为成功；一次性执行留下的进程按执行环境的处置报告写明去向。
- Shell 的定义声明两项设置，都是偏好：转后台的阈值，默认 1 分钟；前台上限，默认没有。一次执行运行超过一个固定的短时长之后，Shell 把输出边跑边写进输出正文，结束或被中止时封存，结果以它为卸载原文；结果正文仍是有上限的头尾两段。输出正文写满单份正文的上限后不再写，丢掉的字节数如实给出。
- BkgToolCalls 让 agent 看和停本会话的后台调用：`list`、`output`、`terminate` 与 `help`。它不许可后台，自己不保存任何事实：三个命令都经应用装配给的端口，作者不认识会话、租户与调用引用。`output` 给一项的状态与输出正文的一段；`terminate` 带原因，答复是已请求，不是已停止。找不到的一项、别的会话的一项与不存在的一项，答复相同。
- Ask 只有提问一个命令，不设关口：装了它的 Agent 在任何权限设置与询问策略下都能提问。提问声明只读：它不改变别的调用看得到的任何东西，所以同一批里的几个提问各自出卡、一起等人，排在提问后面的有效果的动作等它答完。它的说明讲清两点：它存在是为了给人可以直接点的选项，让人答得快，给选项不能让人更省事时不必用它；不用它问「可不可以做某个动作」，那由系统判断并在需要时自己问人，人在这里答的话不是许可。发行里各个工具的关口与缺省值写在各自的定义里。缺省值的规则：只读的命令归缺省自动的关口；产生效果的归缺省询问的关口，除非拥有这个工具的领域在自己的规格里给这道关口定了别的缺省。Web 搜不到结果是成功的空列表；能截断的正文截断后成功并标明，只有截不了的才答 `too-large`。Web 的外部内容放在外部数据标记之间；fetch 只发 GET，不带凭据头，跳转目标同样过网址检查，key 只交给一次搜索请求。

- Code 是程序执行方：命令 `execute` 与 `help`，不声明后台，不许程序调用，一道关口缺省自动。它要一个带 `program` 设施、确认隔离断言 `restricted-js` 的落点；拿不到时调用答不可用，不换别的落点。
- `execute` 给 `code` 或 `path` 之一，另可给 `input`（一个 JSON 值）。两个都给或都不给是参数错误。给 `path` 时，宿主在位置 0 上以程序调用发起一次 `Files` 的 `read`：它照常过嵌套动作准入与这次调用的文件范围，读到的正文就是这次调用的程序，正文的摘要与路径记进父调用，之后文件的改动不影响这次调用。读不到、不是文本或超过程序的大小上限时，父调用以失败收场，不运行任何程序。
- 程序是 TypeScript 写法的异步函数正文：类型在运行前擦掉，不接受的写法在运行前答语法错并指出行。每个此刻可调用的工具是程序里以工具名命名的一个对象，命令是它的方法；函数形态的工具是一个函数；全部也挂在 `tools` 上。每个函数收一个对象，返回声明的程序数据。没有正常完成的调用抛出 `ToolError`，带种类、工具名、命令名、效果与一句说明；程序可以捕获它，不捕获则程序失败。
- 程序的返回值与控制台输出是给模型的结果，照常过结果管线与卸载；返回值必须是 JSON 表达得了的。没有返回值不是失败，结果写明没有返回值。这次执行里有子调用的结果是外部数据时，整段输出按外部数据标记。结果末尾是子调用摘要。失败的结果写明种类、程序里的位置，并说明已完成的调用效果仍在、程序不会重跑。
- 给模型的说明由定义派生：作者写的部分加命令菜单，没有别的。作者写的部分求少而准：它的作用是让模型在该写程序的时候想到写程序、在不该写的时候不写，不教模型怎样写程序。它写一条统一的判据（这件事是很多次调用，中间的结果模型不用读）和这条判据下的几类工作：对很多项做同一步；几个调用相互喂；结果很大只要一小部分；要分支与重试；会重复做的存成文件按路径再跑。它写明什么时候直接调用：一两个小调用就能答；要读了上一步的结果才能定下一步；要原文留在对话里。此外只写模型无从知道的事实：工具是程序里的全局对象、调用返回值而不是文本、必须等待、没有文件网络定时器与模块、每次都是新环境，以及能调哪些工具、函数与返回的字段去 `Tools` 读。作者写的部分连同命令菜单有字节上限，定义的用例钉住。
- 什么能在程序里调、每个函数怎样调、返回哪些字段，模型只从 `Tools` 读：带条件的搜索答程序此刻能调的全部工具，`inspect` 答一个工具的函数。别处都不说：工具声明（命令菜单与工具自己的 `help`）只写返回什么与正文是什么，不写程序数据；Code 的声明不带任何工具的函数签名，它不随会话里常驻哪些工具而变；Code 的 `help` 没有参数，只给完整规则、这个部署实际的限额与去 `Tools` 找，大小与目录里有多少工具无关。程序读不到字段而以类型错误失败时，结果指到 `Tools inspect`。
- 程序按名字调用非常驻的可编程工具，不用先装载。一次执行开跑之前，宿主只判定程序正文里写到的名字：正文里的标识符与视图里的名字求交，再按名字取定义，不翻目录。所以判定的定义个数不超过正文写到的工具个数，与目录的大小无关。正文没写到的名字不成为全局对象；`tools[名字]` 用算出来的名字时，只找得到正文写到过的工具。视图或目录读不到时，`execute` 与 `help` 答不可用，不当成没有工具。

## 原则与约束

- 失败如实是失败。不能因为出过一些内容、资源已释放或调用方不再需要，就写成完成。
- 结果不知道就是不知道。按原操作身份认回，不换号重发，不写成成功或失败。
- 外部效果不因 disposer、关闭连接或释放资源声称可逆；撤权不回滚已受理的外发。
- 预期失败用具名答复，异常只用于程序缺陷；依赖抛出的异常只以依赖名报告，不泄露异常正文。
- 规则落在函数这一面。只在模型调用路径上生效、程序调用绕得过去的规则是错的。
- 策略类的数值（重试延迟、退避上限、步数、容量、期限）由装配给定并在构造时校验，不写死生产默认。
- 改变定义、匹配、保管或控制协议时，同步全部消费方与相应一致性套件。替身声明非耐久，不能装配进生产，也不证明耐久提供者符合契约。
