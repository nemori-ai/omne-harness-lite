# Tool

## 总体架构

Tool 回答一件事：一次工具调用怎样被受理、执行、等待、控制和收场，它的结果、效果与费用怎样保管并交给原消费者。包组有六个成员：

| 成员                   | 回答的问题                                                                                                      |
| ---------------------- | --------------------------------------------------------------------------------------------------------------- |
| `tool-contract`        | 一次调用有哪些事实、操作与端口，边界上怎样判。纯数据与纯函数，不依赖 Cordis、存储或任何 Tool 实现               |
| `tool-cordis-contract` | 在这套系统里 Tool 以哪些服务键、事件和登记协议出现。不含实现                                                    |
| `tool`                 | 一次调用怎样一步步推进：独立执行、账本、推进协程、正文管线与清扫。不依赖 Cordis，离开这套系统也能单独用、单独测 |
| `tool-host-local`      | 在一台机器上把账本、启动排序域、时钟、绑定登记表、目录、作者装载与邻域端口接起来，并给出 Cordis 插件            |
| `tool-storage-sql`     | 在 SQL 存储契约上兑现耐久的记录仓、正文存储与到期索引                                                           |
| `tool-definitions`     | 发行自带的几个工具作者（Tools、Files、Shell、TodoItems、Ask、Web）：参数、操作映射与结果文本                    |

依赖只朝内：`tool-host-local` 依赖 `tool` 与 `tool-cordis-contract`，它们依赖 `tool-contract`；`tool-storage-sql` 依赖 `tool`、`tool-contract` 与 SQL 存储契约。别的领域的生产代码只依赖 `tool-contract`，写 Cordis 插件时另加 `tool-cordis-contract`。

一次调用的事实都在账本里，按调用分域保存。推进协程每次读一个调用的全部事实，按阶段与待办做一步，这一步是一个拥有者域里的一笔条件提交，或一次按原身份的端口调用；然后重读。宿主持有活体：实例、作者执行、环境值、观察订阅。活体丢了，新的协程从账本接着走。

## 领域边界

Tool 拥有：原逻辑调用、真实执行、内部等待、控制意图与实际结果、真实收场、原结果及其版本、效果确定性、执行账、交付状态、卸载正文的保管与回收、调用状态的寿命。还拥有工具定义的派生、实现的登记与选择，以及常驻工具在采用点的纯判定。

Tool 不拥有：资产的持有、版本与治理；身份、授权与许可的授予；执行环境的设施与放置；人的决定；设置值与秘密；消费方的工作、工作终态与会话冻结；Runtime Context 的作用域注册。Tool 不为调用创建或推进任何外部工作对象，不替被调用领域写私有状态。

## 心智模型

工具的本体是函数，模型消息里的调用与结果是它的投影。准入、执行、效果和结果保管都在函数这一面，所以模型直接调用、程序调用和经 Tools 转发的调用走同一个东西。为了给模型看得舒服改的是投影，不是函数的参数或返回值。

一次调用是账本里的一组耐久事实，不是一个活着的对象。每一步有一个由受理身份派生的固定操作号，提交未知就按这个号去问，不换号重做。活体只是在推进它：调用方走了、观察断了、宿主换了，调用照样有它的结局。对调用方，Tool 是一个被远程调用的服务：调用方不等 Tool 收场，Tool 也不等调用方。调用方想知道一次调用还有没有人管，就问「你的活体还在推进它吗」。Tool 对这一问从不答「不在我手里了」：开始过的调用带着外部效果与资源，由 Tool 与执行环境收场，调用方等到的是一个按正常的路交回的结果。

最容易想错的地方：流结束不是完成，完成只认一份计划后的 final；拒绝或失败不说明没有效果，效果单独记已发生、未发生或未知；disposer、关闭连接、释放资源都不是停止证明；逻辑收场不释放名额，释放要一条物理依据；常驻声明在上下文里不等于许可，撤销立刻生效；转后台不是第二次执行；活体里没有一次调用不等于它失联，失联要装配给的证据。

## 应然设计

### 定义、采用与常驻

- 工具资产的正文只带身份、治理声明（`requiredCapabilities`、`programmable`、`composes.skills`）与实现引用。装载时由治理声明与实现事实派生定义：形状、说明、返回声明、后台许可与声明来自实现；采用、名字、必需能力与 `programmable` 来自资产。资产名、能力名与定义名不同时拒绝装载。
- 形状只看名字、种类、参数契约与命令表，说明、返回声明与采用不参与。两份定义同形当且仅当形状相等。
- 必需依赖是抽象能力名的合取。缺一个必需提供者，整个工具不可用。可选项实际使用时探测。
- `programmable` 只有布尔 `true` 许可程序调用；省略与 `false` 拒绝，非布尔值是无效声明。它对整个工具和全部命令生效，不被设置、常驻、后台或调用方身份推导或覆盖。后台许可同样是作者声明，缺省拒绝，阈值与批准都不能放宽它。
- 多命令工具对模型是一个工具，只占一个声明。调用在参数里点名命令，编码是 `wrapped` 或 `flat` 之一；`flat` 的命令不得有名为 `command` 的字段。解码失败给封闭的拒绝类别，不猜命令。声明里的命令清单与 guide 由定义机械派生，作者不拼出错文本。
- 采用点是会话初始化、新 Run 开始和显式 reload。常驻规则 R1 到 R5 见不变式。采用点的判定只由纯函数给出，结论是前进、保持、同形替换件或冻结；冻结的原因只有 `tool-shape-lost`，只在新 Run 开始或 reload 时判，证据只来自换代协调者答 `missing` 或 `rejected`。暂时缺席、未知与撤权一律给同形替换件，不冻结。
- 刷新点允许的变化不同：会话初始化与 Run 中的提供者变化不判冻结、不前进记下的键；Run 中只允许可用性与路由变化。路由是在记下的键不可用时把后续调用送到同形贡献，不改写记下的键，已经发出的调用保留原实现。
- 已知不可用的工具（dummy）对任何参数都正常返回带原因的不可用结果，不启动原工具，不解析参数，只记替换件真实的处理开销。从未合法取得定义的目标不构造 dummy。
- `Tools` 能搜到的是这个主体此刻合法可用的视图，按当下事实现算，不按采用点记下的集合，也不按 Agent 定义收窄。搜索在评分与分页之前排除常驻项；`Tools.execute` 只接受非常驻目标，常驻工具必须直接调用。发现与执行不把目标加入模型工具列表。

### 受理与调用身份

- 普通调用方只给主体、租户与固定请求，不给调用或操作身份。来源按（租户，完整消费位置）原子地认回或分配调用身份并保存原请求与原主体。同键同请求认回原身份；同键异请求对有权者答 `conflict`；异主体、撤权或伪造租户一律拒绝，不经 `conflict` 泄露原记录。身份不复用，包括提供者重启之后。
- 受理同提交固定请求、原消费位置、调用方式与来源、固定设置与限额、定义与实现的匹配、批判断依据与待办。受理之后固定的东西不再换：不换函数、不暗改参数、不迁到更宽松的环境、不自动重发。
- 参数没收全时不受理；收全但解析失败形成原调用的 `arguments` 失败终局，不执行原工具。原参数与生效参数都按原始 JSON 文本保存，不接受重复键。
- 调用方式由受信入口给出，脚本不能自报直接调用。程序调用的目标不是 `programmable === true` 时答 `unsupported`，不创建已受理执行。后台起步而定义不许后台时拒绝，这项检查先于 dummy 与参数检查。
- 未知分两种：`association-unknown` 没有引用，调用方保留完整意图并重复 invoke；`commit-unknown` 带原引用，沿原 invoke 接续。`rejected` 只说这一次尝试没受理；其中的 `unavailable` 是依赖暂时不可用，调用方等依赖恢复后以原意图重入。
- 调用引用与操作引用的文本不含租户。租户来自调用方的访问；另一个租户的引用在本租户里查不到，答复与不存在的调用逐字节相同。引用不授权、不证明调用存在。
- 每个命令与读取先核边界输入，再问资格，最后才读记录仓。拒绝不写记录，也不披露调用是否存在。守卫或记录仓抛出的异常只以依赖名报告，不带异常正文。

### 排队与名额

- 队列在租户内按并发范围（owner，key）划分。范围由其拥有者授予，受理时核授予；调用方不能换键绕过限额。
- 同一范围内按耐久序号先到先得。取得名额同时要求同工具的持有数小于工具上限、范围的持有数小于范围预算；`null` 表示该项不限，先后次序照样适用。还在准备的较早调用不持有名额，但后来的调用不能越过它。
- 名额按队列条目的阶段计数，不看前台或后台。转后台、存活协程的等待、调用方退出与观察断线都不释放名额。检查点作者可靠暂停后条目停泊：不持有名额，仍计入队列容量；答复接受后以新序号重新排队。
- 条目只凭调用域里的释放依据删除：启动前拒绝的排除证据、已启动执行的可信原 final（物理结束）、暂停中收场的旧执行排除、记录仓确定拒绝后的最小失败终局，或失联收场带的连续性证据。仅逻辑收场不是依据。
- 调用域与队列域没有共同事务。推进先由调用域写 `queue` 待办，队列域再转换，调用域最后关闭待办。创建条目的提交断言它读到的调用域修订号，所以已释放的调用永远不会再得到条目。没有启动记录的 `held` 条目是待履行的义务，不是启动，只由同一操作身份的重做或拒绝了结。
- 队列容量满时，新的受理在提交之前被拒绝；已受理的超额调用按序等待，不是执行失败。等待者对账只删除有依据的条目、请求运行欠队列一步的调用，从不回退别的调用的条目阶段，也不向调用域写记录。

### 启动围栏

- 启动要进入一个启动排序域。它对一次启动签发许可，许可冻结所有适用守卫的当前修订号与请求的规范摘要；许可本身不授权执行。
- 受信执行边界先保存不可执行的待发胶囊，再 `consume`。`consume` 在同一排序内依次：认回已有受理或拒绝；核守卫修订号未变，变了就提交永久拒绝；核交来的请求就是签发许可时的那一份；重读授权拥有者对本次动作的当前裁定；按全部或全不的方式消费绑定的授权许可；最后写唯一受理记录。交给受信外发桥是启动的线性化点。
- 外层调用方经 `toolStartFence` 使它拥有的守卫失效。失效与操作记录共同提交之后才返回证据；拿到证据之前不能声称新的发起已被阻止。证据之后，带旧修订号的许可都被拒绝。围栏不停止已受理的启动，需要停止的逐个经公开 `control` 提交 stop。同一操作号配另一个守卫答 `conflict`，守卫只前进一次。
- 已消费的许可不复活：另一调用出示已消费的许可、许可台账答未知、许可租户与调用租户不同，都拒绝启动。台账或裁定暂时读不到时不受理，答 `unknown` 并保留原任务，不读缓存放行，也不写成永久拒绝。
- `inspect` 在没有受理也没有拒绝时先提交排除标记并收回当前许可，再答 `not-started`；之前签发的许可从此不能被受理。`exclude` 排除整次调用的全部未受理启动；调用已受理时答 `conflict`，在途执行只能由控制停止。
- 受理之后的撤权不撤销受理，也不停止在途执行。这个残余窗口从 `consume` 的再核开始到外部效果完成为止。
- 排序域里一个调用方等轮次的时间有上限，到点答 `unavailable`，不无限等：它没有进入轮次，什么也没决定；一个不收场的轮次挡不住同一租户后面的全部调用。已经进入轮次而超过上限的写不被取消，可能仍会提交；停止等待的调用方对自己的操作得到 `unknown`，不答 `unavailable`。
- 启动回执未知时查排序域与原绑定的 `inspectStart`，不再 start。`not-started` 只在原许可与全部延迟请求都被排除后成立，这时才允许同一启动身份首次执行。已经启动又失联的执行绝不经 start 重放。

### 执行事实、收场与结果

- 执行源按批次交事实，每批带来源、批号与游标。同来源同事件同值去重，异值整批拒绝。批次保存后才给保管回执，源收到回执才解除自己的责任；回执丢失时重送原回执，不回退游标。流结束或抛错只表示通道结束，不代替 final。
- 一次启动的原 final 只成立一次。事实流保存的是账本计划后的最终事实：首屏、各小通道与正文条目引用，从不保存原始返回值或正文字节。超过内联阈值 L、或某个模型可见文本块放不进一页结果的结果，在计划时写成系统正文并封存；缩不小的块放不进一页时计划答 `invalid`，不提交读不出来的结果。
- 收场在一次调用域提交里写唯一原结果版本、真实效果、交付待办、物理结束与全部后继责任，并把被引用的正文置为已关联、其余正文标为孤儿。重试认回原期限，不重新起算。
- 作者返回形态在装载时选定：普通返回经固定 codec 编码再解码、经 renderer 成文本；结构化返回直接给 `ToolResult`。不按对象有没有 `content` 字段猜。任何输出违反声明都形成 `cause: result` 的失败，不形成 `completed`，不重跑作者。缺省结果政策只收文本块与共享引用块，规则一变就是新修订。
- 程序数据 `data` 与展示内容来自同一原结果，同一次提交保存，不在事后替换。程序执行方只从 `data` 取业务值，不解析展示文本或过程帧。
- 旧实例排除之后到达的真实结果形成新的结果版本与它自己的交付，原逻辑终局与原版本不改。
- 失败不推出没有效果。系统终局（失败、不可用、中断）可以没有业务 `data`。已真实开始的后台执行最终只能是完成、失败或中断。账本自己形成的结果不编造用量与费用，没有测的时长记未知，不记零。

### 正文卸载与保管

契约面向分布式与异构部署，不假定账本与正文存储同事务，不假定读取有快照隔离，不假定时钟同步。

1. 账本是唯一权威。只有账本提交能使正文可达；期限只存在账本里，正文条目与正文存储都不存期限。
2. 正文字节不可变，只属于一个结果；身份不复用、不共享、不去重。正文存储没有业务状态，全部操作幂等；同序号异内容以条件写报告冲突。
3. 写入许可有时限，由存储校验。账本确认执行活跃、代次匹配且调用未结算后才提交正文条目并签发许可；许可绑定租户、调用、正文与执行代次，带截止时间，由装配的密钥签名。调用结算后不再续发；作者的写入许可在距截止不到 ε 时先续发，再交给存储。封存先由存储校验分块齐全与摘要，再回到账本提交；存储答封存即表示正文已耐久。
4. 按可达性回收。结果提交关联引用的正文并按期限排期；调用结算把未关联的正文标为孤儿，宽限期 G 之后排期。回收先删存储里的字节，再在账本记已回收；中途崩溃重跑终态相同，回收后存储不留行。
5. 读回先在账本核授权、结果版本与期限，再按范围读存储，读完再用本地时钟核一次期限，到期就答找不到。存储里没有字节时复查账本：已回收、已成孤儿或已进入到期窗口答找不到；只有已关联且明显未到期才报告完整性故障（诊断以 `integrity:` 开头）。读回不续期。
6. 按调用放置。每次调用的事实在它自己的调用域；租户级域只存跨调用状态。热路径按键读，不读整个域，所以每次调用的读写量与已结算调用数无关。
7. 条件提交可以断言同一租户分区里其他域的修订号。这一个机制取代各处的专用守卫提交。
8. 到期索引是账本原语，随提交原子生效，是回收唯一的调度来源。
9. 部署参数由装配给定，启动时校验，不满足就拒绝启动：时钟偏差 ε，许可时长 W，宽限期 G > W + 2ε，正文保留期限 > W + 2ε，预览除数 k；预览预算 P 取作者上限、系统上限与 ⌊L/k⌋ 的最小值，声明受理时核描述头上限加 P 不超过 L。

作者经执行上下文的窄 writer 写正文：开始、追加、封存三步，序号连续，同号同内容认回；受信绑定一次保存完整正文也走这三步。正常返回时有开始了却没请求封存的正文，是未完成的作者输出，形成失败。系统兜底卸载只给机械预览，不编造摘要；全文取回是一次新的工具调用，只计取回本身的开销。

### 交付与调用状态的寿命

- Tool 把一个结果版本推给受理时冻结的消费位置；重投与恢复不重新选择去处。推送的认回键是（租户，生产者种类，调用，结果版本）；账目另按（调用，账目事件，修订）推送，每个调用先取得结果的 saved 再推账目。
- 接收方只在同时证实四件事后答 saved：完整冻结载荷已独立可靠保存或有可恢复引用；原消费关联与责任已成立；原键、消费位置与内容一致且去重已成立；保留条件与待交付责任继续有效。未知答 `outcome-unknown`，不以普通失败盖过；`signal` 只停本次等待。接收入口按租户分额度与背压，一个租户占满不挡别的租户。宿主一侧的推送同样按租户排：容量按租户计，一个租户的排队不占别的租户的位置，没有位置的交付仍然待推。
- Tool 核对 saved 的键后，以宿主主体经受信的交付解除释放该版本；消费者自己解除走 retained 或 processed 两条路径之一。通知、展示、读到内容或开始处理都不是可靠交接。释放之前 Tool 保留原键与完整冻结载荷。
- 交付释放就是消费者的确认。确认之后调用状态至多再保存一段期限：删除时刻取确认时刻加 G 与各卸载正文期限中的较大者；到时还有未结责任或宿主还不能放手时推迟一个 G 再判；阻塞的 `clock` 待办只记执行结束时没有计时标记，不算未结责任。删除覆盖账本的调用域与宿主里属于该调用的记录，不留墓碑；删除之后的调用按从未受理答复。没有确认的调用不删除。
- Tool 自己守不住三条前提，它们是对消费者的要求：先保存后确认；保存后不用同一消费位置重发；确认之后超过 G 不再控制。违反前一条，结果可能在保存前被删；违反第二条，同一调用身份的函数会再执行一次。
- 转发的子调用的消费者是转发它的调用；子调用的记录不早于父调用的记录删除。
- 交付推送按接收方的回答退避。接收方答 `unavailable` 时，下一次推送等一个退避，连续每次翻倍，封顶 `maxMs`，等待未满不推；答别的就清退避，下一次从 `initialMs` 起。接收方答 `denied`、`invalid` 或抛出是确定失败：不退避，交付仍欠着，一个接收方抛出不停同一轮里的其他交付。两种情形每次推送都写一条具名警告，带租户、调用、交付与原因。退避表的条目只在交付仍欠着时存在。

### 前后台、计时与控制

- 前台与后台是等待与交付关系，不是两种执行。转后台保留同一执行、输入、效果与账目，只从前台到后台，不回前台，不释放仍在运行的名额。转后台得到的是前台占位，占位的来源是发起即后台、控制、阈值或前台上限之一；最终结果仍交原消费位置。
- 前台累计时间由耐久累计量与已提交的计时段决定。内部等待与后台期间不累计；重启不归零；时钟倒退或跨进程无法比较时报告未知，不增大剩余额度。
- 到达前台上限时，许可后台且没有 Ask 等待就转后台，否则提交停止意图（原因 `foreground-limit`）。Tool 自己的这类转换也经同一个控制命令提交，来源指向自己的计时证据。
- 每次公开控制分配新的操作号。`stop` 请求停止，原消费位置继续等真实收场。`withdraw` 必须带 reach：`all` 撤回目标的前台与后台；`foreground-and-unadmitted` 只在目标于控制提交时是前台关系才撤回它。reach 不及目标当时的关系时，控制照样提交，回执进度为 `rejected`，原因 `out-of-reach`，调用不变。reach 的判断与提交原子完成。
- 前台目标被撤回时可以先形成 `interrupted` 逻辑终局与前台 final；真实结果、效果与成本沿原调用另存为晚到版本，不恢复入队资格。受理控制不等于物理停止；只有实际收场证据证明 `stopped`。
- 中断原因分三类，各自可辨：控制请求（带控制操作号与是否撤回）、前台上限、恢复被拒（带排除依据）。工具自身失联属于失败，不与有意中断混成一类。

### 等待与检查点作者

- Ask 等待决策方的决定，没有超时、没有默认答案、不能转后台。调用方句柄释放、断线或查询失败都不作废仍有效的等待。同一请求只有一次有效决定；`no-answer` 与 `declined` 是有效决定，不是许可，也不是失败。普通 Promise 与 I/O 不构成等待。
- 取消与答复在原调用的事务里排序：取消先成立，后到的决定不被当作答案；答复先成立，保留它，随后的取消阻止还没放行的后续动作。决策方答出三种决定之外的值是它的故障，报告出来，不当作人的答复。
- 检查点作者按段执行，每段是一次 `initial` 或 `resume`。段的上下文只有过程输出与取消信号，没有 `wait`，所以作者只能以返回 `suspended` 的方式等人。暂停带编码后的状态、一个 Ask 请求与一段 `closedResult` 文字；控制在人作答前关闭等待时，调用以 `interrupted` 收场，结果就是这段文字，不再运行任何段。
- 暂停的提交同时写检查点、状态、等待 `opening`、登记待办与停泊待办。请求原文与状态由账本保存，摘要与证据核对后各存一份，调用收场时删除。决定接受后重新排队，取得名额后从同一检查点运行恢复段；一个检查点只有一个后继，恢复段不重跑已完成的段。恢复段在运行它的进程里重新准备环境，不接管旧进程的环境。
- 检查点状态、等待请求与等待答复各有上界（`CHECKPOINT_STATE_MAX_BYTES`、`WAIT_REQUEST_MAX_BYTES`、`WAIT_RESPONSE_MAX_BYTES`），使写入它们的每一笔提交都放得进记录仓的命令上限，整个调用域远小于整域读取上限。
- 暂停中被 stop 或 withdraw 时，同一笔提交让调用收场、关闭等待、写登记失效与释放待办；效果记为未知，因为已运行的段可能有过效果。Ask 等待中的调用不能转后台。
- 暂停的推进里，提交未知或修订陈旧不移动任何已知事实：按认回的或重读的状态在同一次运行里重做这一步，直到调用到达它的等待。端口暂时答不出的，再问；端口答「未暂停」或「拒绝」是裁决，没有哪次运行重复它；其余失败也是裁决，待办停止本次运行。
- 已收场调用的等待要登记失效。失效操作的身份由调用与等待派生；回包不确定时经原操作的 `inspectOperation` 认回，不换身份重发；`excluded` 证明原失效不会落地，同一身份可以再发；决策方明确拒绝时待办记为阻塞并保留原因，调用的终局不变。
- 恢复段的环境准备不按首次启动处理：被拒绝时调用保持暂停并带原因，只有 stop 收场，不按从未启动收场；环境随已不在的进程丢失时重新计划恢复段。首次启动被拒绝或丢失才按从未启动收场，原环境的清理仍归适配器。已被恢复段 `continued` 的等待在调用收场之前关闭。
- 恢复段的答复值是普通 JSON：`json-text` 的树在交给作者之前解码。

### 恢复与推进

- 调用有待推进的工作，指它有 `pending` 的待办，或暂停中且有处于 `opening`、`open` 或 `responding` 的等待。账本在每笔调用域提交里算出这个标记，与记录同一事务写下或删掉。`blocked` 的待办不算，它等外部处置。
- 恢复扫描只读标记，按租户再按调用分页，把调用交宿主调度。重复调度是同一个提示，推进按调用当前的阶段与待办走，已启动的执行不会重新启动。
- 推进协程只经账本命令写记录。提交未知、修订陈旧与被否定答案排除都不停止推进，重读后以同一身份重做，但都不算进展。每次运行步数有上限；无进展的重调度按重试延迟翻倍退避，有上限，有进展就清零。被宿主中止的运行不重调度。
- 记录仓对一笔提交答确定拒绝时，那笔提交永远写不进去。没有启动记录的调用改写一条最小的失败终局（`runtime-lost`，诊断带拒绝原因），照常交付与释放；已有启动记录的调用停在这一步，不收场。账本对这笔提交立刻答确定失败 `invalid`（`field: storage`，带存储给的原因），不重读重决，也不消耗提交的重试次数。
- 否定答案（`not-accepted`、`not-committed`）必须排除该操作全部在途提交：账本写一条排除记录推进域修订号，之后按旧修订号准备的提交都失败。认回先于排除：已有该操作记录时答原回执。
- 只等人答复的调用休眠：移出宿主的内存表，不占容量，不再按拍子问决策方。唤醒提示、按租户的兜底重扫或内存表腾出空位把它带回来。
- 启动扫描与周期重扫不能由调用方的那一问取代：已经交回结果而还欠别的域一步的调用、后台调用、经 Tools 转发的子调用与不经 Agent 发起的调用，都没有调用方会来问。
- 跨租户的待办扫描按租户文本的顺序逐个读已发布目录里的租户事务域，每个域各读一次，整个扫描不声称是同一时刻的快照。任一个域读不到时整页答 `unavailable`，不答更短的页，诊断写明是哪个租户。
- 重试延迟必须在 1 ms 到 2147483647 ms 之间：0 会让失败的调用紧循环重跑，更大的值会让计时器在 1 ms 后触发。

### 活体、失联与收场

- 调用方以调用引用经 `contact` 问「你的活体还在推进这次调用吗」。回答只有四种：`holding`（还拿着）、`settled`（有结果了，结果正在或将要按正常的路交回）、`not-accepted`（没受理过）、`unknown`（此刻答不了）。没有「不在我手里了」。
- 回答之前先过访问核对，再读这次调用的记录；没有查看资格的主体得到拒绝，不论调用在不在活体里。这一问不等执行环境，不写账本，不加新的落盘状态与扫描。
- 「活体里有」指此刻真的有东西在推进它：宿主的内存表里有它，它由重调度、驱动的退避或排着的结果交回叫醒。休眠的调用不在活体里。
- 记录在而活体里没有的调用，回答时接回活体，之后由活体照常推进：

| 调用记录                                       | 活体里有                                    | 活体里没有                                                           |
| ---------------------------------------------- | ------------------------------------------- | -------------------------------------------------------------------- |
| 没有这次调用                                   | 不可达                                      | `not-accepted`                                                       |
| 没收场：已受理没开始、暂停着等人、由本实例开始 | `holding`                                   | 接回；接进去答 `holding`，接不进（内存表满、宿主正在停）答 `unknown` |
| 没收场：由别的实例开始过                       | `holding`（活体正在给它收场）               | 判断来源给出证据就接回，答 `holding`；没有证据不接，答 `unknown`     |
| 已收场                                         | `settled`，结果还没确认的让结果交回重新排上 | 同左                                                                 |

- 当前段属于别的实例、执行阶段是 `starting`、`live` 或 `unknown` 的调用，原执行可能还在旧实例里运行。判断来源没有证据时，宿主从内存表放掉它，不写账本，不接上，不重启。
- 有证据时由新的活体收场，次序固定：先让执行环境按原资源身份停掉这次执行名下的受管资源并确认，确认之后把工具宿主资源账本里这些资源记成已确认停止；再记失联：一次账本提交把执行记成 `lost`（带连续性证据），调用以 `failed`、原因 `runtime-lost` 收场，效果记为未知，同一次提交把没了结的控制记成调用已经结束；最后结果按正常的路交回原消费位置。确认不了就不记失联，调用留在活体里按驱动的退避再试。没有受管资源的进程内函数，停掉这一步是空的。
- 已经存下原 final、只差保全的调用不记失联：停掉资源之后照那份 final 收场。
- 开始过的执行绝不重跑。收场每一步可重入：记失联的操作身份由调用与启动记录派生，重送认回原结果。
- 收场之后，账本里与这次执行有关的记录（资源、控制、队列位置、等待登记）与事实相符：资源记已停，控制记已结束，名额以失联为依据释放，开着的等待关闭并留登记失效的待办。

### 保留范围与接手

- 会话的保留范围长寿：开着，然后关闭，不再开，也不删除。关闭之后它保留自己的记录、条目与结束事实，存储重启后仍在；对已关闭范围的计划、许可与接手一律答 `closed`。
- 预留留在创建者自己的获取记录里：创建者记自己未被接手的预留的停止，范围接手之后的键归范围记录。接手是对范围记录的一笔提交，断言获取记录与原调用不变；获取记录的 `handedOver` 由范围的条目派生。
- 被接手进程的确认停止，把结束事实记在范围域里自己的键下，读一条结束事实只触一条记录。范围的记录不随调用数增长，结束事实随范围寿命增长。

### 独立执行域

- 被接受的 `emit` 按序到达接收方。收尾（`finish`）先等此前接受的全部输出到达接收方。
- 信号中止先于交接就答取消；等待中的屏障或等待，在答复到达后以取消收场。第一个接收方没收下的输出处，屏障不再等待并答该失败。
- 以失败收场不等卡住的输出，接收方保留已收下的。以返回收场而仍有等待打开是无效。首次收场的种类不被后来的收场替换。

### 观察

- 普通消费者经 `instances.current` 取当前发布代次的公共引用与当前权威状态，经 `observation.observe` 先取一致快照，再接从该观察者上一游标起的增量。没有 `after` 续读：断开或出现缺口后重新取引用与快照。
- 发布代次就是（实例，代次），每个代次一条新的过程流；旧引用不接到后继。已建立的观察在代次被替换时以 `producer-ended`/`stale-instance` 结束，执行收场且发布源关闭时以 `producer-ended`/`closed` 结束；对非当前代次的新观察请求结束于 `stale-stream`，不联系任何句柄。
- 运行时门面在交出每一帧之前按同一调用与同一访问再核资格。拒绝时先移除订阅并丢弃排队，再结束于 `denied`；资格来源不可读时同样结束于 `unavailable`。
- 实例目录缺席时 `current` 整次答不可用，不答 `current: null`；`current: null` 只表示核权后确无路由，不证明未执行、结束或丢失。持久查询、控制、读取与交付不依赖目录或 Catalog。
- 过程帧只给人观察，不进入消费方的请求内容或程序的数据通路。保存先于发布；节流只合并同块增量，裁剪要保留数量与原因。没有过程块不造过程消息，发送失败不使执行失败。
- 遥测只观察已确认的提交，不是回执，也不是提交的条件。

### 装载、登记与换代

- 登记键是（来源层，能力身份，资产版本）。来源层四选一：官方、组织、租户、工作区；它只取自核验后的来源，不取自登记者的租户。同一 fiber 以同一装载摘要再登记认回原贡献，其他同键登记一律 `conflict`；原贡献释放后新登记才成为后继；晚到的旧释放比较 token，只撤自己。
- `resolve` 在本租户可访问的同形贡献中选：记下的键仍 live（含 draining）时优先它，否则取 live、非 draining、登记序号最小的一份。回退不比较资产版本，不做层序选择；向胜出者前进只在采用点发生。
- 换代协调者是作者插件句柄的唯一持有者，三个动词都向目标态收敛、可以重复调用：`ensureLoaded` 先核来源与包摘要再 import，授权之前不运行不可信模块的初始化；`unload` 先关闭新采用，读完全部持有者引用，按 draining、等在途收场、交接、释放贡献、销毁 fiber 的次序走，任一步没完成就停在 `draining`；`sweep` 按持有者记下的键重装。
- 保留义务：有有效持有者引用且没有同形 serving 替代的贡献，协调者不销毁。持有者引用读不到时保留并重新开放该键，不能证明没有引用就不撤。工作区层的贡献不作为 serving 替代。
- 实现的替换就是对新版本 `ensureLoaded`，旧版本在引用归零后收走，不存在原地替换。突然失依赖时登记随 fiber 撤除，在途调用保持未知，不换最新实现继续原执行。
- 结果接收方按 consumer owner 登记，登记绑在调用方 fiber 的 effect 上；同一 owner 已有存活登记时第二个登记失败，旧 fiber 已撤除或正在撤除时新登记替换它。登记不授资格，只在同一进程内成立。

### 记录仓

- 每个账本域一个修订号。提交只在被写域的修订号等于期望值、且每条同租户断言的域修订号等于给定值时生效，否则答 `conflict`，什么也不写。断言另一个租户的域在提交之前就拒绝。生效的提交总推进修订号，没有空操作捷径。
- 读取对同一提供者经手的提交即时可见。答「没有」总是存储当时的内容。按旧内容做出的写入被修订号拒绝；至多一次的事由启动围栏守；待办的对象本来就接受重复执行。
- 固定请求只在受理那次提交里写一次；之后每次提交的大小与请求大小无关。请求大到一条命令放不下时，受理当场被确定拒绝，调用不开始。
- 整域删除带期望修订号，一次删掉该域的记录、到期项与修订号，不留墓碑；另一个租户的同名域不受影响。正文分块与清单不属于任何账本域，不推进修订号。
- 租户只经受信目录取得事务域；每条语句以租户为第一过滤条件。读取被拒绝或失败答不可用，不答空。
- SQL 记录仓把一笔提交的答复映射成端口答复：原因来自此刻的存储状态（同一笔提交以后可能被接受）答 `unavailable`；原因来自提交本身或装配（再发多少次都被拒绝）答 `rejected`。
- 整域读取超过行数上限时拒绝，不截断；读取器答超出输出上限同样拒绝。
- 读回记录的摘要只取决于规范 JSON，不依赖存储是否保留键序。

### 凭据

- 凭据引用依次从租户、该租户所属组织、官方来源选；只有上一层确定没有配置才查下一层。选定之后秘密保管答任何失败都终止解析，不换来源、不用缺省秘密。失败闭集是 `missing | denied | invalid | unavailable`。
- 能力只在一次使用期间有效：每次使用先重核资格与秘密绑定，动作结束后一律撤销，再返回结果或原样重抛。撤销失败不能报告成功；动作与撤销都失败时一起抛出。能力、秘密与解析器不进入固定请求、日志、目录、供给块或持久记录。提供者缺席时答不可用，不降级到环境变量或共享默认凭据。

### 元工具作者

- `read_result` 的引用是公开、无状态、可解码的规范文本，绑定固定结果版本；引用不授权，每次读取由运行时按当前资格核。正文页给可读文本、完整 JSON 值或明确标为片段的 JSON、完整的 JSON Lines 记录，不要求模型解码 base64，不把片段冒充合法 JSON。回应本身的预算不超过运行时的内联阈值，否则回应会被再次卸载，模型读不到任何一页。
- 发行作者的描述只写用途与固定事实，不含运维构造值，所以发行清单能固定定义摘要。返回文本受各自的字节上限约束，截断时如实标注；作者截断或设施丢弃的输出，运行时卸载补不回来。
- Files 在有工作区根时把相对路径解析成绝对路径；解析只换字符串，不授予访问。批量补丁先对全部目标做预检，全部通过才提交一次；未知不表示全批落盘，也不自动重发。
- Shell 的结局如实区分停止已确认、未确认与未知，未知的退出码不显示为成功；一次性执行留下的进程按执行环境的处置报告写明去向。
- Ask 只在被卡住且确属人决定时问；跳过不是许可，只有明确的同意才许可动作。Web 搜不到结果是成功的空列表；能截断的正文截断后成功并标明，只有截不了的才答 `too-large`。Web 的外部内容放在外部数据标记之间；fetch 只发 GET，不带凭据头，跳转目标同样过网址检查，key 只交给一次搜索请求。

## 原则与约束

- 失败如实是失败。不能因为出过一些内容、资源已释放或调用方不再需要，就写成完成。
- 结果不知道就是不知道。按原操作身份认回，不换号重发，不写成成功或失败。
- 外部效果不因 disposer、关闭连接或释放资源声称可逆；撤权不回滚已受理的外发。
- 预期失败用具名答复，异常只用于程序缺陷；依赖抛出的异常只以依赖名报告，不泄露异常正文。
- 规则落在函数这一面。只在模型调用路径上生效、程序调用绕得过去的规则是错的。
- 策略类的数值（重试延迟、退避上限、步数、容量、期限）由装配给定并在构造时校验，不写死生产默认。
- 改变定义、匹配、保管或控制协议时，同步全部消费方与相应一致性套件。替身声明非耐久，不能装配进生产，也不证明耐久提供者符合契约。
