# tool-host-local 论证与证明

本目录保存超出有限模型范围的手写证明。每条写明命题、前提和推导。性质编号与模型见 [formal-mapping.md](../formal-mapping.md)，有限范围的机检见 [formal-runs.md](../formal-runs.md)。

手写证明没有机检。它只在所列前提下成立；前提由源码结构和测试维护，不由证明本身保证。

## P2 失效围栏的推广

**命题。** 同一租户的 host 域内，若失效 I 的提交修订 r_I 小于受理 A 的提交修订 r_A，则 A 所用 permit 的签发修订 r_P 大于 r_I。这对任意个数的 permit、失效、consume 和守卫资源都成立。

**前提。**

1. 协调器的每个操作都在租户串行区内读快照，并以快照修订为条件提交（`transact`）。所以提交有全序，每次读到的快照包含此前全部提交。
2. permit 记录保存签发时每个守卫的修订。
3. 守卫修订只在失效提交里加一，从不减少。
4. consume 在受理前比较 permit 里的每个守卫修订与快照里的当前修订，有一个不同就不受理。

**推导。** 设 r_P < r_I。由前提 2，permit 里守卫 g 的修订是 g 在 r_P 时的值 v。由前提 3，I 提交后 g 的修订至少是 v+1，并且以后不会回到 v。A 的快照修订是 r_A−1 ≥ r_I（前提 1），所以快照里 g 的修订不等于 v。由前提 4，consume 不受理，与 A 存在矛盾。所以 r_P > r_I。

**范围外。** 前提 1 只在单进程、单个账本存储的串行区内成立。跨进程的协调器没有被证明。

## P1 与 P5 的推广

**命题。** 任意次数的 consume 至多产生一条受理记录。任意次数地重送同一失效操作，守卫只前进一次。

**前提。** 受理提交在同一提交里删除 permit；之后的 consume 先由 `progressOf` 认回已有决定。失效记录以操作号为键（`invalidationKey`），提交前先查这个键。

**推导。** 第一条受理提交后，permit 已不存在，并且快照里有受理记录。由串行与条件提交，之后每个 consume 都读到这个快照，走认回分支，不写新受理。失效同理：第一次提交后，键已存在，重送只读出首次证据，不改守卫。

## Q1 推送次数的上界

**命题。** 记 W(1)=D0，W(k)=min(2·W(k−1), Cap)，其中 D0=`initialMs`，Cap=`maxMs`。一条交付在一个连续 unavailable 段内，第 k 次推送的时刻 t_k 满足 t_k ≥ t_1 + W(1)+…+W(k−1)。所以长度为 H 的时间窗内，该段的推送次数 N(H) ≤ 1 + r + ⌊H/Cap⌋，其中 r=⌈log2(Cap/D0)⌉。这个上界与驱动的频率无关。

**前提。**

1. `now()` 不后退。
2. 段内 `paced` 表项不被删除。表项在答复不是 unavailable 时删除，这正是段的结束；交付离开待推（保存、撤权、放弃）时也删除，段随之结束，见 Q7。
3. 同一进程。表项只在内存里；进程重启后第一轮等待重新从 D0 开始。
4. 一个交付由一个 worker 推送。

**推导。** 对 k 归纳。k=1 显然。设第 k 次推送答 unavailable。`pace` 读出上一表项的等待 W(k−1)（k=1 时没有表项，取 D0），写入 delay=W(k)、until=t_k+W(k)。下一次驱动若 now < until，`pacedAway` 返回等待，不推送。所以 t_{k+1} ≥ t_k + W(k)。

上界：W(j) < Cap 的 j 至多 r 个，此后 W(j)=Cap。第 1 次推送之后，前 r 次推送消耗爬坡的等待；其余每次至少隔 Cap。所以 N(H) ≤ 1 + r + ⌊H/Cap⌋。

**范围外。** 进程重启次数为 R 时，上界加 R·(1+r)。多个交付各自独立，总推送数是各自上界之和。有限模型 `PushesPaced` 只覆盖 D0=1、Cap=4、Horizon=14。

## Q7 退避表项的生命期

**命题。** 任一时刻，`paced` 的表项数不超过仍待推的交付数。表项的键是（调用，交付摘要）；一个交付至多一个表项。

**前提。**

1. 表项只由 `pace` 写入，且只为一个仍待推的交付写入：`push` 在 `pacedAway` 之前不改表，`pace` 的调用点都在 `push` 里，该交付此时是冻结阶段的记录。
2. 一个调用在同一时刻至多一个 run（`active` 按调用键并入）。
3. 执行器放弃调用只经 `retire`、改由另一实例执行、`close` 三条路径，前两条调用 `release`，第三条随 worker 关闭清空表。
4. 执行器每个重试间隔重新驱动一次存活的调用。

**推导。** 交付离开待推只有五种方式，各有释放点：

- 推送成功：`push` 在 `state.save` 之前 `unpace`。
- 确定失败：交付仍待推，表项保留与否都不破坏命题；源码清除它（Q4）。
- 被另一个 worker 保存、释放或完成：本 worker 的下一次 run 把该交付读成非冻结阶段，不加入 `sweep.owed`；run 结束时 `retainPaced` 删去不在 `owed` 里的表项。run 被取消或读取不完整（`certain` 为假）时不删，因为此时不知道。
- 撤权：下一次 `drive` 入口的 `qualify` 或 run 内的 `current` 答 `denied`，`unpaceCall` 删去该调用的全部表项。
- 放弃：前提 3。

`Deliveries` 为两个交付的有限模型 `DeliveryBackoff-table` 检查 `TableFollowsDelivery`（表项属于仍待推的交付）与 `TableBounded`（表项数不超过在途数）。前者对每个交付独立，所以对任意个数都成立：交付之间没有共享的变量，`TableBounded` 是它的计数推论。

**范围外。** 释放发生在观察到离开的时刻，不是转移的瞬间：交付被撤权或被他者保存之后，表项最多多留到该调用的下一次驱动。前提 4 给出这个延迟的上界；若执行器不再驱动一个未退役的调用，表项会留到 `release` 或 `close`。表里每个调用的表项数不超过它的交付数，而一个调用的交付数由账本里的结果行决定，不由本表决定。进程重启时表清空。
