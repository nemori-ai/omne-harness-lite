# RequestBody：请求正文在有界事务上的保存

本目录的模型检查包组规格「[不变式](../../../../SPEC.md#不变式)」的 MD-18：请求没有大小上界，存储的一次提交有上界，所以请求正文分成块，用几次提交写入。模型只证明列出的有限状态，不证明实现。

## 1. 建模的对象

一个调用身份、两份可能的输入（摘要 `d1` 与 `d2`；同一身份的另一份输入在契约里是冲突）、一个写进程。进程可以退出再启动，提交的答复可以丢失。

| 变量                  | 含义                               |
| --------------------- | ---------------------------------- |
| `chunks`              | 存储里的块，每块是（摘要，序号）   |
| `call`                | 没有调用，或调用受理时的摘要       |
| `held`                | 调用是否仍持有请求材料             |
| `caller`              | 本进程在途的受理：阶段与摘要       |
| `started`             | 进程是否做完了启动后的清扫         |
| `crashes`、`unknowns` | 进程退出与答复丢失的次数，各有上界 |

## 2. 规则

1. 块按调用与请求摘要取键。
2. 受理是一次提交：只有该摘要的每一块都在，才写入调用。
3. 进程启动后，先删除没有调用持有的块，再受理。
4. 释放在把请求材料标为已释放的同一次提交里删除该调用的块。
5. 受理没有写入调用时（调用已存在），删除这次尝试写下、调用又不持有的块。

## 3. 性质

| 名称             | 种类 | 含义                                                                       |
| ---------------- | ---- | -------------------------------------------------------------------------- |
| `BodyComplete`   | 安全 | 持有请求材料的调用，有自己摘要的每一块                                     |
| `NoOrphanAtRest` | 安全 | 没有受理在途时，每一块都属于持有请求材料的那个调用。所以已释放的调用没有块 |
| `Decided`        | 活性 | 调用方一直重做的受理最终有结论                                             |

活性依赖公平假设：启动清扫、开始受理与受理的提交最终发生；每一块的写入只要一再可行就最终成立。

## 4. 配置

| 配置                 | 去掉的规则                           | 必须得到                 |
| -------------------- | ------------------------------------ | ------------------------ |
| `positive`           | 无                                   | 两条安全性质与活性都成立 |
| `admit-unchecked`    | 规则 2：受理不看块                   | `BodyComplete` 的反例    |
| `key-without-digest` | 规则 1：块只按调用取键               | `BodyComplete` 的反例    |
| `keep-on-replay`     | 规则 5：没有写入调用的受理留下它的块 | `NoOrphanAtRest` 的反例  |
| `sweep-live`         | 规则 3 的限定：受理在途时也清扫      | 活性反例                 |

## 5. 模型到代码

| 模型                                    | 代码                                                                                                                                                       | 用例                                                           |
| --------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------- |
| 块的键（`Key`）                         | `src/schema.ts` 的 `md_request`，主键（tenant，call，digest，seq）                                                                                         | `tests/schema.spec.ts`                                         |
| 写一块（`Put`）                         | `src/commit.ts` 的 `putBody` 与参加者的 `putChunk`：已存在的块不改                                                                                         | `tests/request-body.spec.ts`：块的提交未确认时重做只留一份正文 |
| 受理的提交（`Admit`，写入调用）         | 参加者的 `writeBody` 与 `bodyWhole`：块数等于 `total` 才成立，否则以 `body-incomplete` 停止                                                                | 同上：块缺失时受理不成立，重做成立                             |
| 受理没有写入调用（`Admit`，调用已存在） | 核心在暂存写入之前认回已有的调用，那时不写块。写了块而提交没有写入调用时，`src/commit.ts` 提交 `body-discard`；参加者的 `discardBody` 只删没有调用持有的块 | 同上：不成立的受理不留块；调用已存在或已释放时再受理不写块     |
| 启动清扫（`StartSweep`）                | 进程里某租户的第一次受理的第一次提交带 `sweep`；参加者的 `sweepBodies`                                                                                     | 同上：新进程的第一次受理删除无归属的块，保留有调用持有的块     |
| 释放（`Release`）                       | 参加者的 `writeBody`：行的 `request` 为 NULL 时删除该调用的块                                                                                              | `tests/commit.spec.ts` 的释放用例                              |

## 6. 模型不覆盖的

- 同一进程里同一租户的两次受理同时进行。清扫成立之前开始的另一次受理可能被清扫删掉已写的块，那次受理答 `unavailable`，重做后成立。安全性质仍由规则 2 保证。
- 多个写进程写同一个数据库。规则 3 依赖一个数据库只有一个写进程。
- 块的内容与切法。切块可拼回原文、不超过编码大小，由用例守。
- 读取。`readBody` 逐块读，块不齐时答 `unavailable`，由用例守。
