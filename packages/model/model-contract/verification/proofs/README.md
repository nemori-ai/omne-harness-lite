## P3 每次唤醒的推送次数

**命题。** 一次唤醒处理 N 个交付，`maxRedeliveries` 为 k。这次唤醒的推送总数不超过 N·(1+k)。这与接收方的答复序列无关。

**前提。** 一次唤醒对每个交付至多进入一次 `push`。`push` 的循环变量 `redeliveries` 从 0 开始，每轮加一。

**推导。** 对循环的轮次归纳。每轮恰好推一次。只有 `outcome-unknown` 且 `redeliveries < k` 时进入下一轮；其余答复（saved、外来回执、unavailable、backpressured、cancelled-before-accept、拒绝）都结束循环。所以一个交付至多 k+1 轮，N 个交付至多 N·(1+k) 次。没有接收方时不进入循环，推送数为 0。

**范围外。** 两次唤醒之间的间隔由唤醒来源决定，不在本命题里。守卫 `runtime-push-bounds.spec.ts` 检查 k=2 的一个交付。

## P4 待交付晚账有界

**命题。** 对任意晚账序列，任何时刻待交付的晚账数不超过 `maxPendingAccounts`，每个租户的不超过 `maxPendingAccountsPerTenant`。

**前提。** 接纳一个新的晚账操作之前，先核对当前名额数与租户名额数，超过就拒绝（`late-account-capacity`），通过才写入名额表。名额只在该晚账 saved 时删除。同一操作重交时，名额表里已有它，不再新增。

**推导。** 名额表的大小只在接纳新操作时加一，而加一之前已核对它小于上限，所以加一之后不超过上限。删除只会减少。同一操作重交不改变大小。所以不变式「名额表大小不超过上限」对每一步都保持。租户上限同理。待交付晚账与名额一一对应（`ReservationsMatch`），所以结论对待交付晚账成立。

**范围外。** 名额表只在进程内。进程重启之后的名额由重启补推的实现决定，不在本命题里。
