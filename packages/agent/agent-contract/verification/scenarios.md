# Agent 持续验证场景

本页维护 Agent 契约的持续验证义务：独立调用、对象生命周期、控制范围、租户与资格、交错与失败、反例、交付责任、定义与请求、扩展与整批动作、Loop 节点、崩溃后接续，以及装配与 Cordis 集成。场景是后继实现必须通过的可观察结果，不是已运行的证据。行为的唯一正文归 [SPEC](../SPEC.md)，对象与状态归[对象模型](../docs/object-model.md)，能力到场景的追踪归[覆盖矩阵](coverage.md)。

## 编号规则

场景编号写作 `SC-AG-nn`，`nn` 是两位或三位数字。编号按加入顺序分配，一经使用不重排、不复用。其他页面和覆盖矩阵只引用编号，不复制场景表。分组占用固定号段，号段内加入新场景时取该段下一个空号。100 以上的号段按主题分配，新主题取下一个空段。

| 号段 | 分组 |
| --- | --- |
| 01 至 09 | 独立调用与事件消费 |
| 10 至 19 | 对象与生命周期 |
| 20 至 29 | 控制范围 |
| 30 至 39 | 租户、身份与资格 |
| 40 至 59 | 交错与失败 |
| 60 至 71 | 反例 |
| 72 至 79 | 定义采用与请求 |
| 80 至 89 | 交付责任 |
| 90 至 99 | 保留不用 |
| 100 至 139 | 扩展、整批动作与消息准入 |
| 140 至 159 | Loop 节点与控制入口 |
| 160 至 199 | 流式失败、崩溃与控制竞争后接续 |
| 200 至 219 | 装配与 Cordis 集成 |

每个场景的“后继验证观察点”写实现测试必须读到的事实。读不到该事实的测试不算覆盖该场景。

## 独立调用与事件消费

调用方没有任何外部协调者，只使用公开契约的 invoke、事件订阅与读取、确认和终态。

| 编号 | 场景 | 必须结果 | 后继验证观察点 |
| --- | --- | --- | --- |
| SC-AG-01 | 独立调用者从 invoke 走到终态 | 调用方只提供租户、主体、操作身份、受理输入和空推进依据。受理输入带完整的消息内容，来源依据为 null。调用方取得原执行句柄，订阅事件，读取并确认，收到终态事件。调用方不创建、不填写任何外部协调者的对象，不另存输入内容，也不返回完成批准 | 全程请求与返回值中没有外部协调者字段；Journal 的 inputs 返回的消息与 invoke 交出的内容一致；终态由 Agent 的条件终结成立；确认前缀与终态事件一致 |
| SC-AG-02 | 事件订阅被调用方关闭后用原游标重连 | 重连从已处理序号之后继续，边界上的重复事件内容与原事件相同，调用方按事件身份去重。订阅结束不被当成终态 | 同一事件身份的内容不变；订阅关闭前后执行状态不变；迭代结束本身不触发任何业务判断 |
| SC-AG-03 | 读取起点早于保留起点 | 返回缺口和恢复入口，不返回空页，不跳过事件，不默认消费成功 | 缺口的保留起点与恢复依据存在；调用方沿恢复入口取得完整快照后才继续 |
| SC-AG-04 | 读取方落后很多，又远慢于执行推进 | 执行推进不被读取方阻塞，已提交事件不丢弃。落后超过保留窗口时读取返回缺口 | 推进速度不随读取速度变化；缓冲只受配置的字节上界约束；超出上界的订阅以不可用结束并可重连 |
| SC-AG-05 | 确认回执丢失后重试，以及用更小的序号确认 | 重试认回原确认。更小的序号不回退已确认前缀，超出已发出序号的确认被拒绝 | 已确认前缀单调不减；处理依据为 null 时确认照常成立；Agent 不因处理依据的内容拒绝确认 |
| SC-AG-06 | 读取方在终态事件到达前一直离线 | Agent 自行条件终结，已可靠交接的事件保留，读取方上线后从原游标读到终态事件 | 执行不等待读取方；runtime 回 idle；事件与结果责任仍可认回 |
| SC-AG-07 | 仓库外只安装打包后的 agent-contract 并写调用方 | 类型可编译，生产依赖闭包不含 Cordis、具体宿主、模型或工具的实现包；没有从内部文件导入类型 | 完整生产安装闭包；移除 monorepo 路径别名后仍通过；包清单声明了契约文档引用的类型依赖 |

## 对象与生命周期

| 编号 | 场景 | 必须结果 | 后继验证观察点 |
| --- | --- | --- | --- |
| SC-AG-10 | 一次执行结束后同一 runtime 承接下一次 invoke | runtime 回 idle 并保持登记，新执行取得新执行身份。新执行不沿用上一执行的主体、授权、取消状态、输入队列和事件游标，可以复用定义解析和可重建缓存 | 两次执行的身份、游标和取消状态互相独立；登记一直为 published；缓存失效重建后结果相同 |
| SC-AG-11 | 执行结束后目录解析与连接 | resolve 与 connect 仍然成功，登记不因执行结束而撤销 | 登记状态；resolve 返回同一 runtime 的 invoker；connect 返回观察句柄 |
| SC-AG-12 | 同一操作重复 invoke，以及并发的新 invoke。另一次 `open` 已提交初始 checkpoint，该位置的扩展调用提交之前推进实例崩溃，恢复者 resume | 同一操作认回原执行，不重复经过 `execution_started`。并发的新 invoke 返回 busy，不进入隐藏队列。崩溃的一次：E4 读到 `position` 为 E3 且该位置尚无扩展调用，回 E3 接续同一次经过，该位置的扩展调用建立一次 | 持久去重记录；执行开始位置只经过一次；没有无界第二队列；崩溃的一次中初始 checkpoint 的 `position` 为 E3，恢复后的节点序列含 E4、E3、E4，该位置的 Passage 恰一个 |
| SC-AG-13 | 接管：执行处于 advancing，旧 runtime 失联，另一个 runtime 以 resume 接手，主体持有 takeover 资格 | attach 走接管路径。旧挂接在同一次提交中转为 superseded，新挂接 active，执行回到 reconciling。旧 runtime 之后的提交返回 stale-advance，它交出本地资源后回 idle，不再推进该执行。旧挂接的晚到回执只归原操作，不修改新位置。接管不新建执行，也不再经过 `execution_started` | 挂接状态表：旧挂接 superseded，新挂接 active；执行身份不变；旧 runtime 的状态由 occupied 变为 idle；旧回执的归属记录 |
| SC-AG-14 | 恢复：detach 之后 runtime 回 idle，之后另一个 runtime 以 resume 接手 | detach 后执行进入 suspended，不是取消，旧挂接 detached。resume 走恢复路径：新挂接 active，执行回到 reconciling，旧挂接保持 detached。原调用、判断和卡片保持原身份 | suspended 的接续依据；旧挂接始终是 detached，从未变为 superseded；新挂接取得资格；原操作身份未变 |
| SC-AG-15 | 停用实例时存在在途执行 | 拒绝新 invoke，交接在途执行，交清后撤登记。交接未知时报告剩余执行，不宣称完成 | draining 状态；剩余执行列表；登记状态 withdrawing 与 withdrawn 的区别 |
| SC-AG-16 | 登记发布与撤除重试 | 同一操作同一参数认回原结果，同一操作不同参数冲突。旧登记身份不能撤掉后继登记 | 登记身份类型；后继登记存活；撤除重试返回原结果 |
| SC-AG-17 | 旧句柄访问新执行 | 句柄只指向原执行，不静默指向 runtime 后来的执行 | 句柄绑定的执行身份；越界访问被拒绝 |
| SC-AG-18 | 新装配准备失败时原工作 | 原执行仍可解释，旧挂接不因准备失败而丢失资格 | 旧挂接状态；失败原因与原事实一致 |
| SC-AG-19 | 目录撤除或无活体路由 | 目录撤除不等于业务完成。无活体时沿持久恢复读取原事实，不根据目录缺席决定终态 | no-live-route 与原事实读取分开；执行状态不因撤登记改变 |

## 控制范围

四种控制各自独立。六个阶段是受理、意图成立、推进资格撤销、生产者确认、物理停止、责任释放。每个场景都要读到该控制适用阶段的事实，并确认不适用的阶段没有记录。适用关系见 SPEC 的“[六个阶段](../SPEC.md#六个阶段)”。

| 编号 | 场景 | 必须结果 | 后继验证观察点 |
| --- | --- | --- | --- |
| SC-AG-20 | 中断一个模型调用 | 只有具名调用被请求中断，该响应尚未发出的工具建议不执行。执行继续，其他调用不受影响。已交付内容和费用保留 | 阶段事实中没有推进资格撤销；其他调用状态不变；执行不进入终态 |
| SC-AG-21 | 取消一次执行 | 本执行的新推进停止，仍在前台的调用被请求中断，执行形成 cancelled 终态候选。已转后台并确认占位的工具、同 runtime 的其他执行、其他租户的工作不受影响 | 六个阶段事实各自可读；受影响调用集合只含本执行的前台调用；取消不复活 |
| SC-AG-22 | 暂停一次执行 | 当前挂接的资格被撤销并保存接续，执行进入 suspended，不终结。模型和工具调用不被请求停止。合法接手者可以恢复 | 没有生产者确认阶段；挂接状态 detached；恢复后原身份不变 |
| SC-AG-23 | 停用一个 runtime | 控制只作用于该 runtime 的登记与在途执行交接，不取消模型和工具的独立执行，不终结执行 | 停用没有 ControlRecord：受理与意图成立读 runtime 进入 draining，推进资格撤销读各执行的 detach 交接依据，责任释放读 quiesce 返回的 drained 或 unresolved 与宿主的登记状态；没有生产者确认与物理停止；交接完成后才撤登记；停用期间新的 invoke 返回 unavailable；执行状态为 suspended 或原状态 |
| SC-AG-24 | 控制已受理但生产者确认和物理停止尚未成立 | 报告为已受理而不是已停止。确认未知时保留未收尾责任 | 阶段事实只含已成立的阶段；未知阶段单独标记；不把受理当作停止 |
| SC-AG-25 | 控制命令与普通完成竞争 | 先成立的有效取消优先，旧挂接不再发新效果。后成立的取消在执行已终态时只认回终态，不复活 | 条件终结与控制的排序记录；终态唯一；晚到的真实效果与费用仍归原调用 |
| SC-AG-26 | 对 suspended 的执行发出取消，之后 resume | 取消的受理与意图成立先记录，执行保持 suspended。resume 取得新挂接后，执行由 reconciling 进入 settling，以取消授权终结为 cancelled。没有挂接时不发生终结 | 取消记录早于新挂接；suspended 期间没有 ended；终态只经新挂接的条件终结成立 |
| SC-AG-27 | 模型调用进行中，一项 urgent 输入经 submit 到达 | 输入沿原执行受理，模型调用被请求中断，已到内容保存，该响应尚未发出的工具建议不执行。已呈现的人工卡片保持有效。执行不终结，挂接不变 | 只有一条针对该模型调用的中断记录；卡片状态不变；执行身份与挂接身份不变 |

## 租户、身份与资格

| 编号 | 场景 | 必须结果 | 后继验证观察点 |
| --- | --- | --- | --- |
| SC-AG-30 | 另一租户的主体访问 runtime、句柄、事件或目录 | 一律按拒绝处理，不区分对象是否存在，不泄露任何对象的内容或状态 | 拒绝结果不随对象存在与否变化；没有部分内容返回 |
| SC-AG-31 | 操作缺少租户 | 返回输入无效，不从 runtime 绑定、上下文、历史标识或全局当前状态推断租户 | 没有任何读取或写入发生；错误中没有推断出的租户 |
| SC-AG-32 | 持有历史执行身份或旧句柄 | 历史身份与句柄不是读取与控制资格，每次操作重新核对租户，并以 AgentAccessCheck 核验主体资格 | 撤权后的同一句柄被拒绝；旧挂接不能发新效果 |
| SC-AG-33 | 用租户 A 的 runtime 承接租户 B 的执行 | 拒绝。更换租户或安全范围必须换实例 | 绑定值只在创建时决定；配置不能覆盖绑定 |
| SC-AG-34 | 事件、日志与诊断输出 | 不含私有权限块、秘密或无权内容。无权读取方读取含无权内容的页面时被整体拒绝，不返回删减后的页面 | 逐字段扫描事件与失败诊断；没有以空内容冒充原内容的页面 |
| SC-AG-35 | invoke 之后主体被撤权，随后 submit；或资格核验不可用 | 撤权后的 submit 返回 denied。核验返回不可用时操作返回 unavailable，不放行。两种情况都不写入任何状态。已受理的输入与已发出的调用不回滚 | 每次操作各调用一次资格核验，没有沿用较早的 allowed；被拒的操作没有新的输入、事件或修订号 |
| SC-AG-36 | 工厂缺少主体资格核验依赖 | 创建失败，不返回半就绪实例 | 创建返回 unavailable；没有 runtime 对象，也没有登记 |
| SC-AG-37 | 主体只有 resume 资格，另一个 runtime 仍持有 active 挂接；宿主随恢复依据提交了失联判断 | runtime 读到快照中旧挂接仍 active，以 takeover 另核验资格。结论为 denied 时 resume 返回 denied，不进入 attach，旧挂接保持 active。结论为 unavailable 时返回 unavailable，同样不写入。宿主的失联判断只作为证据被记录，不能代替核验。同一主体在执行 suspended 时仍可只凭 resume 资格恢复。两个不同操作身份的 resume 先后到达时，先成立的挂接 active，后来者只有 takeover 资格才可能取代它 | 核验调用序列里有 takeover 的单独调用；被拒的 resume 没有新挂接、事件或修订号；旧挂接状态不变；失联判断出现在恢复依据中，而不在核验结论里；suspended 路径的核验序列里没有 takeover |

## 交错与失败

| 编号 | 场景 | 必须结果 | 后继验证观察点 |
| --- | --- | --- | --- |
| SC-AG-40 | 重复 invoke 或 resume 同一操作 | 认回原执行和原执行挂接，不新建执行，不再经过 `execution_started` | 持久去重和当前资格 |
| SC-AG-41 | 调用登记后、生产者受理前进程退出 | 按原登记和原受理身份恢复同一次受理 | 原调用、请求摘要和真实发起次数 |
| SC-AG-42 | 模型结果已确认后 Agent 退出 | 消费侧的原材料或完成依据接续 | 不向 Model 重新领取全文，不重发 |
| SC-AG-43 | 三个动作中有一个在等人 | 整批不启动，答复到达后还需原规则处理 | 屏障成立前 Tool 实际启动数为零 |
| SC-AG-44 | 后继扩展再次出卡 | 原动作批继续等待，旧问题不重问 | 卡片原身份、经过及轮次 |
| SC-AG-45 | 人工决定呈现成功但回执丢失 | lookup 按原轮次和完整请求集合认回卡片，未知时不再出卡 | 原需求和创建排除证明 |
| SC-AG-46 | 压缩共同提交的回执丢失 | 按原操作查询认回原来源后 resume，不重发压缩模型。以另一条消息配原 commitment 提交被拒绝 | 同一摘要、覆盖范围与保留名单，原准备记录；commitment 与消息的绑定被核对 |
| SC-AG-47 | 已退役：压缩后扩展把摘要 A 改成 B | 场景不再成立。压缩之后位置只面对已提交的事实，没有扩展位置能改写压缩候选。编号不复用 | 无 |
| SC-AG-48 | 只变无关配置，或当前授权收窄 | 前者不重问，后者使旧允许不能启动 | 执行点的当前守卫及参数采用 |
| SC-AG-49 | Tool 内部 Ask 的答复 | 交 Tool 的原等待与原决定，不是扩展卡片 | 同一执行与等待不重跑 |
| SC-AG-50 | 前台调用合法转后台 | 同调用、同名额、一个耐久占位，后续真实结果另交 | 原占位不被最终结果改写 |
| SC-AG-51 | 旧 Agent 退出或依赖换代 | 先交还执行挂接，Model 和 Tool 的寿命独立 | 各实例宿主及目录贡献 |
| SC-AG-52 | 换代与取消竞争 | 由推进资格的授予者唯一裁定，取消先成立则无新推进 | 终态、旧资格和实际启动围栏 |
| SC-AG-53 | 执行已终态或已被取消之后，迟到结果到达 | 保管、账目和版本对账继续，没有旧业务推进 | 多结果项、当前承接者和原终态 |
| SC-AG-54 | 当前请求缺少模态或预算资料 | 按 Context 或 Model 的原结果明确失败或保持未知，不发出假的完整请求。限额未知本身不是失败，不被写成通过 | 完整实际输入与失败来源；没有新增的失败原因类别 |
| SC-AG-55 | 外部输入被准入否决 | 返回发送方并标明拒收，不报告可靠受理 | 原受理操作，且消息不存在 |
| SC-AG-56 | 模型回复被消息准入否决 | 保存真实回复和费用，退避后发新调用，不归原重试 | 不设置连续否决次数上限 |
| SC-AG-57 | 执行仍有推进资格时，Tool 结果被准入否决 | 原结果保留，按指定的消费契约提出失败 | 不重执行 Tool，不伪造替身成功 |
| SC-AG-58 | 最终请求已记录且调用在途时，模型选择变化；或选择在准备之后、最终请求记录之前变化。随后同一 execution 准备下一次请求 | 在途调用沿原固定请求继续，实际收件模型、请求内容和费用归属都不变。选择变化不切换定义，不创建 execution 或执行挂接。记录之前的变化使该候选重新读取、重新准备，不拼出新旧模型混合的请求。这次重新准备返回 needs-compaction 时，本 step 尚未进入计划才进入一次计划。本 step 已进入计划时以 cannot-fit 失败，原因是 after-compaction，并附 Context 的原结果与计划身份。记录之后的变化不改写已记录的最终请求。下一次请求按新的实际收件模型重新选择、重新读取 Runtime Context、重新准备 | 两次请求的实际收件模型不同，且各自与 FinalRequest 中固定请求的档案一致；在途调用的请求不变；记录之前再次调用了选择端口；execution 与挂接身份不变；定义采用不变；计划已进入时的失败原因类别与 SC-AG-59 相同 |
| SC-AG-59 | 调模型之前的扩展改写了请求，或选了另一个路由，改写后的请求在新的实际收件模型下装不下 | Agent 先重新选择，实际收件模型变化时重新读取，再以 previous、改写依据和该位置的经过调用 prepare。同一次经过不重跑该扩展位置。本 step 尚未进入压缩计划时，进入一次计划，提交后由 RequestPreparation.resume 复核。本 step 已进入计划时不进入第二个，以 cannot-fit 失败，原因是 after-compaction，并附 Context 的原结果与计划身份。两种情形都不换模型。复核通过后才记录最终请求 | 该扩展位置的经过只有一次；prepare 带有 previous、改写依据与该位置的经过；检查点中只有一个压缩状态；最终请求的实际收件模型等于最后一次选择的结果；计划已进入时的失败原因类别为 after-compaction，与 SC-AG-58 相同；失败路径没有再次选择模型 |

| 情形 | Agent 传入的 adopted | 期望 Context 返回 | 观察点 |
| --- | --- | --- | --- |
| 新 execution，模型还没有在这份历史中读过 Runtime Context | 空 | full，覆盖读取时有权读的全部模型可读块 | adopted 为空；返回 full；最终请求记录之后，adoptedContext 等于这次读取的 coverage |
| 新挂接：AgentRuntime.resume 或接管同一个 execution | 恢复出的 checkpoint 中的 adoptedContext。原 execution 还没有记录过最终请求时为空 | 能从已采用的覆盖接续时返回 incremental，沿提醒链补上挂接中断期间的变化。不能接续时返回 full。adopted 为空时与新 execution 相同 | adopted 取自恢复出的 checkpoint，不清零；Agent 没有因为换挂接而改为要求 full；中断期间的变化出现在返回的覆盖中 |
| 闲置后恢复：同一 execution 长时间等待后继续推进，下一次主请求准备前读取 | checkpoint 中的 adoptedContext，已记录过最终请求时非空 | Context 沿提醒链返回 incremental，用读取时的当前值补上等待期间的变化；不能接续时返回 full。两种结果都覆盖等待期间改变的块 | adopted 取自同一 execution 的 checkpoint，不清零；Agent 没有因为等待时长而改为要求某一种；返回的覆盖含等待期间改变的块的当前值；没有用旧快照代替这次读取 |
| 历史空闲后的新 execution：这份历史空闲一段时间后开始新的 execution，模型此前已在这份历史中读过 | 空，因为这是新 execution | 由 Context 选择 incremental 或 full。incremental 用读取时的当前值补上空闲期间的变化，空闲期间被丢弃的推送不需要补回。两种结果都覆盖空闲期间改变的块 | 返回的覆盖含空闲期间改变的块的当前值；Agent 接受 Context 返回的种类，不改写它；没有用旧快照代替这次读取 |
| 模型切换之后：同一 execution 内重新选择得到不同的实际收件模型，最终请求记录之前重新读取 | 与切换前相同的 adoptedContext | 种类由 Context 决定；返回绑定新的实际收件模型的可读块与覆盖证据 | 读取传入的 recipient 是新模型；切换前的读取结果被丢弃；adoptedContext 在最终请求记录之前不变 |
| 压缩提交之后：转换消息提交后、RequestPreparation.resume 之前读取 | 当前 adoptedContext，另带压缩转换依据 | 按 RC-04 返回 full，覆盖读取时有权读的全部模型可读块 | 读取带压缩转换依据；返回 full；最终请求记录之后 adoptedContext 等于这次读取的 coverage |
