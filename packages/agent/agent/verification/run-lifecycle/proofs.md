# Run 驱动生命周期的手写证明

本页把 [RunLifecycle.tla](RunLifecycle.tla) 的三条性质推广到无界范围。性质与映射见 [README.md](README.md)。手写证明没有机检，只在所列前提下成立。

## P1 对外发起至多一次

**命题。** 对任意崩溃次数、任意答复丢失次数，一步里逻辑主 Model 调用至多一个，每个动作的逻辑 Tool 发起至多一次。

**前提。**

1. 意图先于发起：M0 的提交保存 Model 调用身份之后才 admit；A2 的意图提交之后才 invoke。
2. 身份由已保存的意图确定派生，崩溃后沿用。
3. Model 与 Tool 按同一身份认回同一调用（Model 受理表、Tool P04）。
4. unknown 时按原身份查询或重试，不换新身份。

**推导。** 对发起次数归纳。第一次发起前意图已保存（前提 1）。之后任何一次再发起，都在恢复或重试之后，而恢复读到的是已保存的意图，派生出同一身份（前提 2、4）。由前提 3，对方把它认作同一个调用，逻辑发起数不变。崩溃次数只增加重试次数，不增加身份数。所以逻辑发起至多一次。负控 `bad-dispatch-before-intent-p1` 与 `bad-retry-redispatch-p1` 分别去掉前提 1 与 4，各给出两次发起的反例。

## P2 步数上限

**命题。** 对任意 `maxRunSteps = n` 与任意回复序列（含拒收），一个 execution 打开的步数与逻辑主请求数都不超过 n。

**前提。** 每个逻辑主请求打开一个新步（拒收后的重试也打开新步，R2-D229）。I8 在想继续且步序号已达 n 时给出 guard 失败候选，不打开新步。

**推导。** 步序号从 1 开始，只在 I8 决定继续时加一，而加一的条件是当前序号小于 n。所以序号不超过 n。请求数只在新步里加一（P1 保证一步至多一个逻辑请求），所以请求数也不超过 n。守卫 P2 对 n ≤ 3 与工具步数 ≤ 3 的全部组合检查这一点。

## P6 每步提交次数

**命题。** 一步的 Journal 提交次数不超过 `10 + 5a + c + r`，其中 a 是本步动作数，c 是崩溃次数，r 是被拒提交次数。这与等待时长和唤醒次数无关。

**前提。** 节点各提交一次：I0、M0、M3 与 I3（两次）、I4、A0、I8、F1、F3，以及等待的第一次进入 W0。每个动作提交意图、关联、保管、消息与一次等待，共五次。无进展的唤醒不提交（W0 只在第一次进入时保存等待）。每次崩溃后 attach 提交一次。按应然，每次被拒的提交回到 F1 重做候选一次。

**推导。** 把前提里的次数相加：基础节点 10 次，动作 5a 次，崩溃 c 次，被拒 r 次。无进展的唤醒是唯一与时长有关的事件，而它不提交，所以界与等待时长无关。拒收路径与无动作路径的提交更少。负控 `bad-commit-on-idle-wake-p6` 让每次唤醒都提交，界被越过。
