# 执行环境

## 总体架构

执行环境回答四个问题：一个动作实际落在哪里，那里能用什么，留下的东西能活多久，它现在还在不在。包组有五个成员：

| 成员                                    | 回答的问题                                                                                                               |
| --------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| `execution-environment-contract`        | 落点、获取、租约、受管资源与设施协议长什么样，各方在边界上怎样判。纯数据、纯函数与可复用的契约套件，不依赖 Cordis 和存储 |
| `execution-environment`                 | 登记表怎样匹配落点、记获取、签发采用记录、开门放行设施操作、编排恢复。不依赖 Cordis，不碰机器资源，可以单独用、单独测    |
| `execution-environment-cordis-contract` | 在这套系统里执行环境以哪一个服务出现，三个端口以哪些服务出现                                                             |
| `execution-environment-host-local`      | 在宿主机上把登记表装进服务，并以一个宿主提供者提供 `files`、`command` 与 `terminal`                                      |
| `image`                                 | 一份图像字节在什么预算内可以打开、编码与关闭。与另外四个成员没有依赖                                                     |

集成方先按允许清单解析落点，再凭获取键获取一次，拿回只开放所需设施的租约。每次设施操作都经登记表的门：门核对租约、账本、声明、租户、原调用与绑定层，再问设施守卫，然后才交给提供者。提供者造出的受管资源先在集成方的耐久账本里计划、取得许可，之后才发出外部效果。维护者凭恢复授权按作用域收回资源与获取。

## 领域边界

执行环境拥有：三个核心设施（`files`、`command`、`terminal`）的协议；落点的匹配规则；获取、采用记录与租约的状态与答复；受管资源从计划到确认停止的生命周期规则；一次性命令留下的进程归谁、怎样移交与停止；工具环境声明的 schema 与采用身份；`execution.placement` 与 `execution.host-facts` 两条块的语义；图像预算与句柄。

执行环境不拥有：一个动作允不允许做（授权）；该落哪一层（策略，归集成方）；工具做了什么（工具）；租户之间谁先提交（公平，归集成方的协调者）；任何耐久事实（归集成方的账本）；作用域什么时候结束（归作用域持有者）。

执行环境只认通用角色：访问身份（主体加租户）、不透明的作用域引用、不透明的原调用引用、请求身份、集成方、提供者、设施拥有者、维护者、观察者。它不导入会话、工具或授权的类型。

它向外声明的端口（它需要别人做的）：

| 端口                              | 对方                                       | 对得上的一句话                                                             |
| --------------------------------- | ------------------------------------------ | -------------------------------------------------------------------------- |
| 资源账本 `ResourceLedger`         | 工具（宿主一侧）                           | 执行环境需要一份耐久账本记计划、许可、接续与停止；工具宿主为每次获取提供它 |
| 设施守卫 `FacilityGuard`          | 工具（宿主一侧）与应用装配                 | 执行环境需要逐操作的授权答复；集成方提供守卫，执行环境不知道它的依据       |
| 环境授权 `EnvironmentAuthority`   | 应用装配                                   | 执行环境需要对访问身份与一个封闭动作的授权判定；装配提供它                 |
| 可信绑定来源 `ScopeBindingSource` | Runtime Context 给类型，会话一侧的装配实现 | 执行环境需要知道一个作用域绑定到哪个租户；作用域持有者回答                 |
| 恢复授权 `RecoveryAuthority`      | 应用装配（维护者）                         | 执行环境需要核对每次恢复；维护拥有者签发并核对恢复授权                     |
| 保留账本与保留进程账本            | 会话一侧的受信装配                         | 保留终端与保留进程需要按保留范围记账的第二份账本；受信装配给出它与保留范围 |

它为别人实现的端口：

| 端口                                             | 对方                           | 对得上的一句话                                                         |
| ------------------------------------------------ | ------------------------------ | ---------------------------------------------------------------------- |
| 环境面：落点、获取、查询、描述、按保留范围观察   | 工具（宿主一侧）与独立调用者   | 执行环境提供落点、租约与设施；工具宿主需要它们运行需要环境的工具       |
| 登记面：设施声明与提供者登记                     | 设施拥有者与提供者             | 执行环境提供登记与撤除；提供者需要把自己放进同一个登记表               |
| 恢复面：`recoverOwned`、`releaseScope`、恢复查询 | 维护者                         | 执行环境提供按作用域收回；维护者在作用域结束后需要它                   |
| 工具环境声明的 schema 与采用身份                 | 工具契约                       | 执行环境提供声明的类型与 schema；工具定义需要按采用身份校验环境声明槽  |
| 两条块声明                                       | Runtime Context 与模型类读者   | 执行环境提供落点与宿主事实的语义；Runtime Context 需要块声明来供给它们 |
| 图像的预算、打开、编码与关闭                     | 准备模型输入与保存附件的调用方 | 图像成员提供有界的打开与编码；调用方需要在交给模型之前独立准入图像     |

## 心智模型

把执行环境想成一个出租柜台。集成方带着在别处求好的允许清单来，柜台按清单找第一个合格的提供者，这是落点；再凭获取键租一次，这是获取；交出一份只开放所需设施的租约。每次用设施都要过柜台的门。柜台不判断许不许，只核对身份、作用域、账本与守卫给出的答复。

登记表是进程内的副本，不存别处没有的事实。耐久事实在集成方的账本里，原获取记录在提供者的配额域里。登记表丢了，从账本、提供者的原记录与恢复枚举接着来，不重建租约，也不重放设施操作。拿这一条量一个设计：只存在登记表内存里的一个标记，重启之后就没了，所以它只能做局部保护，不能决定任何结局。

最容易想错的地方：

- 逻辑收口不是物理停止。取消、释放、作用域结束只改变资格与责任；进程停没停，只认域外监督者对原资源身份与代的读数。
- 完成只确认这次请求点名的那一项。读取完成不表示写入完成；启动被接纳不表示进程已启动；`completed` 只表示主进程已结束，不表示执行域已空。
- 空列表不是没有责任。完整的空资源枚举只说明没有受管资源，不说明没有获取、描述符或在途操作；读不全的列表不是空列表。
- 绑定层说寿命，请求方作用域说归属。宿主机与租户级沙箱的绑定层不带作用域，落在那里的获取仍属于请求方作用域。
- 每个活着的进程恰好有一个归属方：本次获取，或一个保留范围。

## 应然设计

### 落点与获取

- 环境要求只有三样：有序的允许绑定层清单、设施键集合、隔离断言集合。策略词不进本域，带别的字段的要求在边界上拒绝。
- 落点解析按清单顺序取第一个合格的层：有在场的提供者声明这一层，所需设施的声明已登记并由它提供，所需隔离断言都由它确认。同一层有两个提供者同时合格时拒绝为 `ambiguousEnvironment`，不取先登记者，也不看后面的层。落点不授设施，也不授资源。
- 请求方作用域由调用方显式给出，不从会话或别的上层标识拼出。绑定层带作用域时，它必须等于请求方作用域，否则 `invalidInput`，不写记录，不调用提供者。描述、落点块、作用域释放、恢复与租约失效都按获取记录里的请求方作用域过滤。
- 解析落点与获取不是一个原子动作。获取时重新核对：请求方作用域没有释放，绑定层仍在清单内，隔离断言仍由该提供者确认，提供者仍在场，配额域等于提供者声明的配额域。核对失败即拒绝，不换落点。
- 获取的槽是租户加获取键。同一租户、同一键、相同指纹的重复只读已有状态，至多一份占用：已获取返回同一租约，已拒绝返回同一原因，其余返回进行中或原采用失败。指纹不同，或重试换了已捕获的账本、守卫或保留进程账本，拒绝为 `acquisitionConflict`，不调用提供者，不触及原获取。跨租户的同一键互相独立，互不披露。
- 原获取描述是租户、获取键、原调用、请求方作用域、落点与可选的保留范围。它在调用提供者之前形成，集成方随原工作保存。
- 提供者回执是临时的。执行环境核验之后才签发采用记录并交付租约。核验六项：提供者在场、执行环境没有关闭、请求方作用域没有释放、回执的绑定层与落点一致、所需设施都能从租约取到、当前授权仍成立。提供者不能自签采用记录。
- 提供者获取抛出、超时或丢失答复是获取未知，保留名额，不写成零分配拒绝。获取未知之后调用方用原获取描述查询，不换键重发。
- 所有入口在第一次外部调用或第一次等待之前捕获本操作拥有的数据字段。账本、守卫与提供者回执里的运行时对象保留原身份。

### 访问核验

- 普通入口先核访问身份里的租户是 legal-identity 铸造的值，不是就答 `invalidInput`，不写记录，不调用端口与提供者。然后依次核：环境授权答已授权；可信绑定来源确认目标作用域绑定到同一租户；查询原获取时，原获取描述的租户等于访问租户。前一项不成立，后面的不再执行。
- 访问核验先于读获取槽。拒绝、未绑定与错租户对外一律是 `notAuthorized`，不披露外租户的存在。端口答不可用为 `unavailable`；端口抛出或答复不在闭合集合里为未知，带原因 `authority` 或 `scope-binding`。
- 授权判定带同步前提 `current()`。执行环境在写入获取的最后一步与采用之前各核一次，答假或抛出按拒绝处理。
- 租户只用 legal-identity 的 `tenantEquals` 比较。解码器接受租户文本与本进程已铸造的租户，拒绝形状相同的手造对象。

### 原获取的查询、结清与采用失败

- 提供者按配额域、租户与获取键持有原记录，并提供原获取查询、按作用域枚举获取与结清。配额域是共享容量与原记录的定位域，跨登记代际稳定。路由按配额域选原代，原代不在时用同一配额域的另一份登记；从不问另一配额域，没有路由时答不可用，不回退到当前提供者，也不再次获取。
- 「未分配」只在确认没有分配、而且不会有迟到成功时答。曾分配后结清的答已结清。暂时看不到记录不是未分配。没有域外的进程退出证据时，新进程对旧获取答未知，不答未分配。
- 查询对外部业务只读：不获取、不计划、不许可、不接续、不执行设施动作、不结清。查询从不认领旧租约。查询发现已获取之后，同键获取以原输入进入原采用阶段，不再调用提供者的获取。
- 旧的查询答复不覆盖较新的已获取、已失效或已结清。非法回执或相互矛盾的终局按查询未知处理，保留原事实并给出诊断。
- 采用核验失败之后，原获取永久转为采用失败，保留第一个确定的原因。执行环境在同一个同步步骤里封住这个键的采用，经原回执的释放驱动清理。清理状态是已结清、进行中或未知；后两种保留名额。清理状态变化不改原因。同键之后只能认回采用失败，已结清不是新的获取机会。
- 撤权之后，失败回执只带原获取键、原因与粗粒度的清理状态，不带资源、租约或别的租户的事实。

### 配额

- 配额的单位是一个未结清的获取。提供者按租户声明两个上界：按租户上界（0 表示拒绝新获取）与可选的全局上界。数值来自可替换的策略，本域不规定数值。
- 提供者在首个分配之前原子地核对两个上界并占一个名额，同一配额域的全部登记代际共用这次判定与键表。超出时拒绝为 `quotaExceeded` 或 `globalCapacityExceeded`，这是零分配的终局，同键重试返回原拒绝。执行环境在获取之前只问配额能不能读，不比较数值，不自己计数。
- 名额只在全部实际资源、关闭与必要账本责任确认结清时恰好返还一次。临时回执、获取未知、补偿未结清、释放进行中、停止未确认都仍占名额，即使资源清单为空。作用域释放、租约失效与退役只封准入，不返还。降低上界保留已有占用，只停止新接纳。
- 按租户的公平排队归集成方的协调者。

### 租约与逐操作门

- 租约只暴露要求里的设施键。一个键要同时在要求里、在声明表里、在提供者的租约原件里，才取得到设施。
- 每次设施操作按下列次序核对，第一项不成立即拒绝，不调用设施：请求形状（`invalidInput`）；租约仍接纳新操作（`closed`）；这次获取的账本没有关闭（`closed`）；这个键的声明仍在并列出这个操作（`unsupported`）；租户（`notAuthorized`）；原调用（`invalidInput`）；绑定层（`invalidInput`）；须授权的操作问守卫；守卫放行之后再核一次租约与账本（`closed`）。门每次都从声明表现取声明。主体原样交给守卫，执行环境不比较主体。
- 门是所有设施操作的唯一入口，账本关闭的核对只在门里做一次。提供者在门之外自己发起的效果，由提供者在发出前自己核账本的关闭信号。
- 释放一开始就关闭租约入口，之后不论结果是已释放、待处置还是进行中，新操作都答 `closed`。释放只作用于这一次获取，可以重试，并发的释放共用一次调用。待处置的资源清单可以为空，空清单不表示已释放。丢掉租约引用不是释放。
- 失效只发生一次。提供者报告的失效原因记为来源 `provider`，原因文本原样保留。失效之后，在途的输出、终局与停止仍由原提供者处理。

### 设施协议

- 设施是按名登记的开放协议。设施拥有者发布声明：键、操作名单、其中须授权的操作。全系统一个键只有一份声明，第二份被拒绝，原声明不变。撤除声明后新获取取不到这个键，旧租约上的操作答 `unsupported`。声明只提供词汇，不安装设施，也不授权。
- 每次设施操作带请求身份、访问身份、原调用与绑定层。结果只有四态：完成、未解析、拒绝（带原因）、未知。同一请求身份只有一种确认。请求身份是关联标识，不是幂等键：执行环境不按它去重，调用方不重用它。
- 普通终端与进程的操作只作用于本次获取创建的对象。指向别的获取所建对象的引用按无效引用明确失败。
- `files`：未解析只用于路径上没有对象的读取、查看、列表与替换写入。替换写入带 `expectedVersion` 而当前版本不同时为 `conflict`，对象不变；删除、移动与复制带 `expectedVersion` 时同样，比较的是源对象。新建写入带 `expectedVersion` 为 `invalidInput`。版本是提供者的观察条件，不是比较并交换。写入结果可以带 `writeEffect`，缺省时不推断效果。列表条目的名字是单个实际路径段，从实际目录项取，不从对象 token 解析；需要名字的消费者遇到缺名条目时整体失败。
- 编辑不是设施操作。调用方读取得到版本（分段读取的各段版本必须相同），在内存里修改，以替换写入带回这个版本；`conflict` 时重读，未知时先查看，不自动重放。
- 授予根是声称隔离断言 `filesystem-root` 的落点自身的属性，由提供者在建立落点时确定，请求与租约里都没有它。在这样的落点上相对路径从授予根起算；绝对路径为 `invalidInput`，越出授予根或确认不了对象仍在根内为 `notAuthorized`。
- `command`：`start` 的完成表示进程实际已启动，带进程身份。接纳了而映像没有启动为 `rejected(unavailable)`。启动与否不可确认为未知。结局 `failed` 只用于已启动之后失联或效果未知。停止有两态 `graceful` 与 `forced`。
- `terminal`：持久 shell 的创建、分段执行、关闭与列表。无效的终端引用由原设施明确失败，不默认改成一次性执行。

### 保留终端

- 保留终端是逐获取归属的明确例外，以可选扩展 `retention`（`attach`、`detach`）提供，终端原有的四项操作不变。消费者调用前检查扩展，缺扩展时不创建终端、不执行，答 `unavailable`。
- `retain: 'session'` 的创建要求获取带受信的保留范围与第二份账本，提供者支持保留。缺任一项答 `unsupported`。普通获取账本不能代替保留账本，Session 归属不从调用方给的字符串或 parent 链推导。
- 保留终端从创建前就归保留账本。创建在首个异步等待之前进入可枚举责任，然后计划、取得许可、启动，并自动附着创建它的获取。取得许可之前不发出首个外部效果。保留容量必须显式配置，启动未知或未结清的也占容量。
- 每段执行仍归当前获取的账本，逐次经过守卫；附着不缓存后续权限。同一终端一次只有一段，竞争答 `busy`，不排队。`detach` 永久封闭这个获取与终端的关系，只收尾自己的段。`close` 先拒新附着与执行，再停止整个终端，未确认不标成已关闭。`list` 只列当前获取创建或附着的终端。
- 资格失败先答 `notAuthorized`；范围内找不到与范围外的引用都答 `notFound`。创建结果未知时不重发创建。
- 保留范围封闭（`releaseScope` 授权通过之后同步发出的封闭信号，或保留账本关闭）之后，提供者停止该范围的全部保留终端。枚举包括零附着、启动未知与关闭未确认的终端。跨进程只接续枚举与停止，不恢复附着或 shell。

### 终端段

1. 段的完成只看控制通道上本段的结束帧，不看静默时长或屏幕内容。
2. 终端里的后台进程不使终端失效。终端只在 shell 死亡、控制帧格式错误、代不符或与控制通道失联时失效。
3. 段的输出是 PTY 字节流中本段首尾哨兵之间的字节。哨兵带只有提供者认得的随机数，不经 PTY 输入写入。收到结束帧之后要读到段尾哨兵才交出结果；读到暂时无数据不交出。
4. 不在任何一段之内的字节是段间字节，进有界缓冲，由下一段的结果单独带出，并带丢弃的字节数，不混入段内输出。
5. 段进行期间，同一终端里后台进程写出的字节属于这一段。
6. 关闭终端停止终端执行域里的全部进程，包括脱离了 shell 的进程，由监督者确认。要让进程活过终端，调用方用一次性命令的保留，或交给宿主自己的服务管理器；后者是命令自己的外部效果。

### 一次性命令留下的进程

主进程退出之后，执行域里还活着的进程叫留下的进程。任何时刻每个活着的进程恰好有一个归属方：本次获取，或一个保留范围。

处置：主进程退出、输出安静之后，提供者按监督者对执行域成员的读数处置一次，并在 `completed` 结局里带处置报告 `residue`。缺省的 `residue` 只表示提供者没有报告处置，消费者不能当作 `none`。`failed` 结局没有处置，执行域仍归本次获取。

| 条件                                 | 处置                   | `residue`                                    |
| ------------------------------------ | ---------------------- | -------------------------------------------- |
| 读数确定只剩提供者自己的监督进程     | 停止执行域             | `none`                                       |
| 有留下的进程或读数未知，而且可以保留 | 整个执行域移交保留范围 | `retained`，带保留进程引用与进程数或「未知」 |
| 有留下的进程或读数未知，但不能保留   | 停止执行域             | `stopping`，带原因；停止的确认不推迟结局     |
| 移交提交的结果未知                   | 按原移交身份再问       | `unknown`                                    |

可以保留要求五项同时成立，`stopping` 的原因写出不成立的那一项：策略允许（`policy`）；获取带受信的保留范围与保留进程账本（`unbound`）；保留范围没有封闭、获取没有在处置期间被释放（`closed`）；该范围的保留进程没有满额（`capacity`）；提供者满足封闭收纳（`uncontained`）。读数未知按有留下的进程处理。

移交：提供者先在自己的保留进程索引里同步占一个可枚举的预留（首个异步等待之前，占一个名额），再在保留进程账本里计划。提交之前复核保留范围仍未封闭、执行域仍待处置，复核与归属改变在执行域的共同顺序内一次完成。提交是保留进程账本的 `adopt`：`confirmed` 表示移交生效，`closed` 时作废预留并停止；结果读不到时用同一个键再 `adopt`，查清之前本次获取不结清，也不停止这个执行域，执行域不被重复移交。

集成方对保留进程账本的义务：`adopt` 与原调用终局在同一耐久顺序内核对原调用仍可写、范围未封闭、有这次的预留；`adopt` 生效的同一次提交里，本次获取的账本结束对这个键的责任；同一键重复 `adopt` 是幂等的，已生效答 `confirmed`，未生效而范围已封闭答 `closed`；已移交的键可由该范围任一视图记 `stopped`。

移交之后，本次获取的释放不停止这个执行域。它只在进程全部自行退出、保留范围封闭或被显式停止时结束。全部自行退出时提供者记 `stopped`，这就是它的收场事实。

保留进程扩展：命令设施的可选扩展 `retention` 提供 `list`，可选 `stop` 与 `output`，命令原有的操作名单不变。登记表只在获取带受信的保留范围与保留进程账本、提供者提供 `list` 时交出扩展，每次调用仍经原获取的门与当前守卫。保留进程的 `list`、`stop` 与 `output` 有意按整个保留范围找目标，条件是获取带受信的保留范围并且守卫放行这次操作。列表只来自提供者耐久索引的完整读取，读不全答 `unavailable`，不跨保留范围或租户。

`stop`：

- 先核载荷形状，不成立为 `invalidInput`，不查索引。资格三项同时成立：租户相同、引用在本次获取的保留范围内、守卫放行。先问守卫再查引用，所以拒绝不披露引用在不在范围内；不在范围内答 `notFound`；资格读不到答 `unavailable`，不发出停止。
- 停止整个执行域。监督者确认执行域已空才答 `confirmed`，否则答 `unconfirmed`，保留范围继续承担责任。重复的 `stop` 并入进行中的停止。
- 已停止或已自行结清的保留进程，在保留账本保存其收场事实期间，资格成立时答 `confirmed`，不答 `notFound`，不再发出停止。所以调用方可以用原请求身份安全地再问。知道引用、能列出、曾发起都不单独授予停止权。

`output`：移交之后，提供者为每条流保存一个有界的字节尾部，只在提供者进程的内存里。答复给出开始保存的偏移 `savedFrom`、丢弃的字节数与 `start`、`end`、原始字节 `data`，满足 `start + data 的长度 = end`；没有 `from` 或 `from` 早于保存的第一个字节时从保存的第一个字节给，调用方由此看出缺口。字节数从不以字符数代替，`text` 只是这次 `data` 的解码。提供者重启后加载回来的保留进程没有尾部，答 `unavailable`；已离开索引的答 `notFound`。读输出不改变状态，也不授予停止权。

按保留范围观察：观察者经 `observeRetained` 读一个保留范围的保留进程列表，不经过获取。入口核对与描述相同。执行环境向每个提供者读一次完整列表并按引用去重合并；任何一个读不全，整体答 `unavailable`，从不交出部分列表。观察不分配获取，不使用恢复授权，不授予执行、读输出或停止。

收纳：封闭收纳指进程在创建时进入执行域，子进程继承成员关系，`setsid`、双重 fork 或重新挂父都离不开它。只按进程组或进程会话收纳不满足封闭收纳。命令设施用 `containment` 声明收纳强度；声明 `none` 或不满足封闭收纳的提供者不交出保留进程扩展，处置一律走停止；缺这个字段不能当作 `sealed`。命令自己经宿主服务管理器起的进程不在执行域里。

容量：每个保留范围的保留进程数有上界，由运营方配置。预留与停止中的项都占名额。满额只让新的处置走停止，从不停止已保留的进程。

保留进程的恢复：提供者在 `adopt` 确认之后把执行域写入耐久索引，并只按耐久索引的完整读取列出、监督、封闭与恢复保留进程。保留进程账本只记归属，不提供枚举。提供者重启后保留进程仍能列出、封闭时照常停止，不恢复监督连接与输出读取。提供者退役不停止保留进程，使用同一耐久索引的后继接管它们。移交提交之前提供者崩溃时，执行域仍归本次获取，由获取的排空停止；`adopt` 确认之后、写入耐久索引之前崩溃时，执行域只经请求方作用域的恢复停止。

### 恢复

- 恢复授权由集成方的维护拥有者签发，独立于用户访问。它是不可序列化的原对象，每次使用由恢复授权端口核对。它只用于停止、认回与结算一个作用域的受管资源与获取，以及恢复查询，不用于获取或新执行。用户撤权或退出不阻断系统回收。恢复入口不带租户。
- `recoverOwned` 与 `releaseScope` 可以带维护者从原账本带回的已知原获取描述列表，补足枚举的缺口，不代替枚举的完整性，也不授予权限。列表不合形，或作用域与参数不同，先答 `invalidInput`，不问恢复授权。
- 恢复走两路，两路都要完成：资源路逐提供者枚举并停止该作用域的受管资源；获取路按配额域去重，枚举该作用域的获取并加上已知列表，逐项结清。缺少恢复方法的提供者记为不支持，枚举失败记为不可用，不当空集。前面已处理的部分不因后面的失败而丢失。
- 只有两路枚举都确认完整、资源没有待处置、不支持或不可用、获取全部已结清时，维护者才可以记已释放。
- `releaseScope` 授权通过之后，先同步记下该作用域已释放并发出保留范围封闭信号，再使该作用域的租约以作用域释放失效，然后做与 `recoverOwned` 相同的两路恢复。重复调用继续处理未完成的项。授权不通过时什么都不做，作用域照常可用。
- 已释放的作用域由集成方的账本耐久保存，登记表只在进程内记住。执行环境重启后，集成方在该作用域的第一次获取之前重新调用 `releaseScope`，或自己拒绝该作用域的新获取。
- 只有资源与在途责任都属于实际进程的提供者，才可以用进程内记录承担配额与原获取记录；它的责任域必须比提供者登记与登记表的重载活得更久，由进程宿主的单一拥有者保管。冷恢复对旧容量的结清判定需要域外可信的进程退出证据，执行环境不根据同名进程、空登记表、新的提供者代或宿主重启猜测清零。

### 提供者的登记、退役与关闭

- 提供者的身份是名、代与版本。代是一次登记化身，每次登记取一个新的代，同名的新登记不冒充旧登记。版本是提供者代码的版本。采用记录与提供者证据都带版本。
- 撤除一个提供者的登记就是开始退役：先拒新租约，再排空。排空指已接纳的操作都已结束，受管资源都已停或列为待处置，获取、关闭与账本的责任都已结清。退役结果是已排空，或待处置并列出未停的受管资源；清单可以为空。清理未完或责任无人承接时不报已排空。待处置之后可以再退役。
- 进展上界归提供者。提供者的 `acquire` 与 `retire` 在自己配置的上界内返回：`retire` 超界答待处置；`acquire` 超界时先释放已分配的部分再以 `providerUnavailable` 拒绝，释放未确认时答获取未知并保留名额。登记表不为提供者计时。
- 登记表关闭之后，新的落点解析、获取与描述答 `ownerStopped`，全部租约失效，仍在临时回执的记录转为采用失败，然后并发退役全部提供者。关闭不清空获取表，查询仍能答关闭前的状态。恢复两操作在关闭之后仍可调用。
- 撤除不撤回任何外部效果，也不丢弃旧工作的处置责任。

### 宿主提供者

- 宿主提供者只提供 `host_machine` 一层，连续性 `not_guaranteed`，不确认任何隔离断言。`files`、`command` 与 `terminal` 由同一个宿主提供者声明，一层由一个提供者提供全部设施。
- 责任域由进程宿主的单一拥有者创建并交给每一代宿主提供者，它比提供者与登记表的重载活得更久；共享同一宿主容量的登记共享同一个责任域。配额接纳在一个没有等待的同步段里完成。每份获取一个门面：门面封住之后新操作答 `closed`，不起进程，不碰文件系统。排空一份获取先封门面，在配置的上界内等在途操作，再重试失败的关闭；什么都不剩才结清，名额恰好返还一次。
- 宿主文件使用：调用方在使用前按当前授权点名对象，设施只核对打开到的对象与点名一致。完成只挂在这个对象与这次句柄代际上；不一致为拒绝，确认不了为未知，都不把请求改到别的对象。关闭是另一次请求，没有成功回执时关闭结果为未知。
- 宿主文件根限制这一代全部 `files` 请求，它不是授予根：宿主提供者还提供不受文件限制的 `command`，所以不声称 `filesystem-root`。有根时，路径解析在根外、任何一段是 `..`、中间段是符号链接、跨设备或内容操作打开的文件有别的硬链接，都答 `notAuthorized`，拒绝之前根内与根外都没有变化。根打不开或文件前提不满足时答 `unavailable`，不放宽成无根。创建只在已核对的目录描述符下发生。
- 已经产生部分外部效果之后的失败答未知，不写成拒绝，也不自动重做。批次的每一项单独发布，不是多路径原子提交；恢复批次只读，不发布、不回滚。
- 一次性命令的每次启动有自己的执行域。启动先在账本计划，用户代码的第一条指令只在账本许可确认之后执行；许可不成立时停止执行域并记入账本。子进程只得到请求给出的环境变量；请求经私有通道交给执行域，不放在别的进程能读到的命令行上。
- 平台的目标按次序定：平台能做到比 Linux 更强的保证时做到更强并不再降低；否则与 Linux 对齐；操作系统确实做不到时，如实声明差异并写出原因。平台差异只经声明的事实体现：`containment`、保留扩展的有无、宿主事实的前提三态、结局里 `exit.signal` 的有无。
- 平台前提的探测结果合并成宿主事实的三态：任一项不满足为不满足，否则任一项未知为未知，全部满足为满足。探测没有完成不报满足。缺前提不影响落点解析与获取，只让依赖它的操作答 `unavailable`。
- 宿主提供者在有权限的宿主机上运行，不承诺同一用户的恶意程序之间的隔离。

### Cordis 装配

- 服务 `executionEnvironment` 的键只由抽象服务类给出，Service 实现继承它，不另写键。一个 isolate 标签下只有一个 Service 实现与一个登记表。沙箱以新的提供者成员加入同一个登记表，不是新的 Service 实现。
- 调用方类（`integrator`、`maintainer`、`provider`）是装配声明的一致性检查，不是访问控制。环境面每次仍经环境授权与可信绑定核对，恢复面每次仍经恢复授权核对。
- 三个端口是装配入口装载的运行时对象。Service 实现从自己装载时的上下文每次现取，不从服务方法里调用方的上下文取，否则调用方能给自己授权。取不到时答不可用，不放行。
- 登记即效应：设施声明与提供者的登记落在调用方插件的 fiber 上，调用方卸载即撤除。fiber 卸载在退役待处置时照常完成，待处置经日志错误可见；调用方直接调用撤除函数时，待处置以抛出报告，可以重试。
- 设施声明插件与宿主提供者插件分开装卸。宿主提供者插件重载只退役这一代，新的一代加入同一个责任域，看到原占用与原记录。

### 图像

- 预算有六个维度：格式列表、最大宽、最大高、解码后最大字节、同时解码份数、在途字节。缺值、非正数、重复格式或 png、jpeg、webp 以外的格式在构造时拒绝，本域不填缺省数值。预算对象只由 `imageBudget` 造出，持有自己的预留表，只有打开与关闭改它。
- 打开在第一次检查之前复制输入字节。在光栅出现之前读容器，只接受单帧 png、jpeg、webp；方向标记按严格规则读，旋转方向把宽高对调后计入预算；解码后字节按定向宽乘定向高乘 4 估计，超出任一上限或放不下预留时拒绝且不占预留。检查通过之后在第一次等待之前占预留；解码失败先释放预留再拒绝。
- 调用方停止等待不关闭句柄，也不证明原生工作已停止，预留保持到这次打开自己结束。
- 编码只在打开的句柄上，输出不带方向标记与 EXIF，编码不改变预留。关闭要观察到光栅不再被编码占用才释放预留；同一资源的关闭句柄只有一个，再次关闭返回同一个对象，不再释放。
- 声明的信任值只有不可信，解码与编码不提高信任。

## 原则与约束

- 只认通用角色。谁要用执行环境，谁把自己的身份翻译成访问身份、作用域、原调用与请求身份。
- 本域不提交任何耐久事实。资源许可与执行终局的同一耐久顺序由集成方的账本兑现；登记表的副本可以丢。
- 先许可，后效果。可能跨进程存活的受管资源先计划、取得许可，许可确认之后才发出首个外部效果。
- 结果不知道就是不知道：按原获取、原请求、原移交身份查询，不换键重发，不写成成功或失败，不自动重放。
- 能力如实声明。提供者不以统一形状虚构做不到的设施、隔离或收纳；证明不了就不声明。
- 重试、上界、容量与配额这类策略数值都是配置，代码里只有初值。
- 新设施只改设施拥有者的包；新沙箱是新的提供者成员。本域不为某个提供者或某种上层工作流加特例。

## 不变式
