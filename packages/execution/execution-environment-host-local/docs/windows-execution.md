# Windows command and terminal execution

The internal entry is `createWindowsHostCommands` in `src/windows-execution/index.ts`. It returns the same command manager shape as `createHostCommands`. It accepts that manager's input without the Linux prerequisite probe and callback. Provider integration remains outside this module.

The module requires 64-bit Windows and the installed .NET Framework 4 compiler. It compiles the bundled C# source with `%SystemRoot%/Microsoft.NET/Framework64/v4.0.30319/csc.exe`. It installs no SDK or native package. Compiled binaries are cached under the system temporary directory, in `omne-windows-execution/<source SHA-256>/bridge.exe`. Temporary compiler inputs are removed after compilation. A missing compiler or failed compilation returns `unavailable` before a resource is planned.

Each command has a separate native bridge and a randomly named Job Object. The bridge starts detached from Node's child-process lifetime. A controller exit therefore leaves the original Job available for recovery. The bridge holds OS resources. The TypeScript manager owns ledger calls and output accounting.

The manager records a resource plan before native allocation. The bridge creates the requested process suspended with `PROC_THREAD_ATTRIBUTE_JOB_LIST`. Job membership therefore forms part of process creation. The bridge does not leave a separate assignment step after creation. The attribute requires Windows 10 or Windows Server 2016 or later, as specified by [Microsoft's process attribute reference](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-updateprocthreadattribute). The Job uses `KILL_ON_JOB_CLOSE` and does not allow breakaway. The manager sends `GO` only after a confirmed ledger permit. Executable arguments, the explicit environment and input travel through private pipes. They do not appear on the bridge command line. The private control frame has a 2 MiB limit. Larger requests return `capacity` before allocation.

Output bytes come directly from Windows pipe reads. The shared command buffer supplies offsets, discard counts and the single-reader rule. The configured chunk and buffer limits apply. A natural root-process exit also stops any remaining Job members. A successful outcome requires the original process exit code, zero active Job members and both output readers to reach EOF. A lost observation produces `effectUnknown`.

Forced stop calls `TerminateJobObject`. Confirmation requires zero active processes in the original Job and a signaled original process handle. A ledger recording failure keeps the resource in `unconfirmed()` even when native stop was confirmed. Windows has no general graceful termination operation for these non-console commands. A graceful request returns `unconfirmed` and retains responsibility.

Native stop, recovery, durable recording and bridge-close waits share one `stopBoundMs` deadline. A stalled recording returns `unconfirmed` at the deadline. The manager retains that recording Promise and the original resource. A later call can observe the record without launching another command. The bridge can release native handles after confirmed native termination even when durable recording remains pending.

`stopWindowsResource(resource, boundMs)` reopens the original named Job. It does not start the command again. It confirms zero active members before notifying the orphaned bridge to release its handles. A missing name returns `unconfirmed`. The caller must preserve that uncertainty if the confirmation is lost before durable recording.

## Persistent terminals

`createWindowsHostTerminals` in `src/windows-execution/terminal.ts` implements the ordinary per-acquisition terminal manager. `createWindowsRetainedTerminalFactory` returns the platform reservation factory consumed by the shared retained-terminal index. It synchronously reserves terminal identity, a managed resource and buffer capacity. Its `start()` then plans the resource and obtains a permit before `GO`. Per-leg permits for retained terminals belong to the shared index. Provider entry selection remains outside this module.

Both factories accept `provider`, `settings` and `capacity`. Ordinary terminals also require `ledger` and `scope`. The retained factory consumes `{ request, ledger, scope, closed }`. A provider domain shares one `createWindowsTerminalCapacity()` object between both factories. Its explicit initial limits are 64 terminals, 256 windows, 64 MiB of reserved output capacity and 65,536 queued chunks. A window reserves its configured maximum buffer size. The next window is reserved before an invocation starts. Insufficient capacity rejects the request before script execution. Sealed unread windows retain their bytes and immutable summaries.

The terminal executable uses the installed Windows PowerShell `System.Management.Automation` 3.0 assembly. It embeds one persistent Runspace inside a ConPTY child. It does not install PowerShell or an SDK. PowerShell state and the observed working directory persist across invocations. Single-invocation `cwd` and `env` overrides are saved and restored. A failed restoration invalidates the terminal. Scripts use PowerShell syntax. Interactive credential and nested prompts are unavailable. This provider does not claim a sandbox or isolation from hostile code running as the same Windows user.

ConPTY requires Windows 10 version 1809 or Windows Server 2019 or later, according to [Microsoft's ConPTY reference](https://learn.microsoft.com/en-us/windows/console/createpseudoconsole). Terminal dimensions use signed Win32 coordinates and must not exceed 32,767 columns or rows. The host sends PowerShell output and errors through `Out-Default`. Host, information, warning, verbose, debug and progress messages write to the actual console. Their ConPTY bytes follow the same observation-window rules.

The shell host sends invocation identities and control facts through a private named pipe restricted to the current Windows user. The native broker reads raw ConPTY bytes. One broker lock orders output records and control events. User output cannot complete an invocation. The handle's process identity names the persistent shell resource and generation. Each invocation also has an internal identity.

The shell explicitly opens `CONIN$` and `CONOUT$`, then binds its standard handles to those console handles. It does not use the broker's standard handles for script input or output. Native programs inherit the console handles. A broken broker transport bypasses the unavailable send path and uses the original Job recovery coordinate within the remaining stop budget.

`completed` confirms foreground invocation completion and its fixed observation window. It does not confirm shell or background-process termination. The returned `exit` is `unknown`: Runspace completion, `HadErrors` and an old `$LASTEXITCODE` do not establish a current invocation return code. Consumers must not present this result as known command success. Script errors remain actual terminal output. A lost control channel produces `effectUnknown` and invalidates the terminal. Output observation failure produces `unavailable` and preserves the bytes already observed.

The private `finished` frame uses version 2. A completed frame carries a nonnegative, safe-integer `elapsedMs` measured by the shell host's monotonic clock between Runspace running and terminal state transitions. The public `durationMs` uses that elapsed fact, including when Node cannot dispatch control events until after completion. Missing, unsupported-version or invalid elapsed data fails control validation. An incomplete frame carries `elapsedMs: null`. Failed outcomes keep Node's local `observedDurationMs`; the implementation does not subtract timestamps from different clocks.

Each terminal starts with an idle observation window. An invocation takes that window, including previously observed idle bytes. Its completion seals the window in broker read order and opens the next idle window. Chunk offsets are relative to each window's start. Observed counts increase before buffer admission. Overflow discards newly observed excess bytes and records the corresponding offset gaps. Reader abandonment does not stop execution. Abandonment before sealing contributes to discard counts. Abandonment after sealing releases bytes without changing the fixed summary.

The approved Windows mapping has three limits:

- Bytes already written to the OS pipe but not yet read can enter a later window. Windows are observations, not causal attribution to a script.
- An empty script can retrieve already observed idle output. It is not an output-drain barrier.
- Close can release undelivered idle output. It does not report those bytes as delivered. The internal closure record preserves observed bytes, overflow-discarded bytes and bytes released without delivery separately. The public close reply contains no output body.

Forced stop can destroy the persistent shell and its entire Job. Confirmation requires the native resource to stop and the terminal ledger to record the stop. The terminal cannot be reused afterward. Other terminals have separate Jobs. An ended invocation's old handle returns `unconfirmed` unless the original resource already has confirmed termination. It never kills a newer invocation. Graceful stop requests shell shutdown but does not claim termination from request acceptance. Cold recovery stops the original Job and does not reattach or rerun scripts.

The ordinary manager removes confirmed closed entries before a later create and after `stopAll`. Such old references return `notFound`. Unconfirmed resources remain in the manager and continue to occupy capacity. Completed control events carry ordered invocation identities, so repeated events do not start another invocation or invalidate a newer one.

The [Windows tests](../tests/windows-execution/) cover real executables, Jobs, ConPTY and the embedded shell. Their ledger ports are controlled test providers. These tests do not establish provider assembly, tenant authorization, durable storage or cross-service retention. The native crash test kills the broker immediately after process creation and waits on the original suspended child's process handle. Window tests distinguish real terminal observations from the in-memory buffer tests.

## Host provider integration

The host provider selects the Windows command and terminal factories on Windows. It does not start the Linux systemd or PTY probes there. Its installation check reads the Windows build, the .NET compiler and the PowerShell assembly, then obtains both native bridge executables. A known missing prerequisite is `unsatisfied`. An unreadable prerequisite or failed compilation is `unknown`. Successful compilation establishes installation facts only. The facilities still report actual startup failures. The files prerequisite remains independent. On Windows it uses the existing native file bridge in its own temporary directory. It checks creation, handle-relative reading, directory-entry identity, removal and cleanup. A missing PowerShell executable is `unsatisfied`; an inconclusive operation or failed cleanup is `unknown`. This probe supplies no business principal and grants no file permission. The provider combines both execution and file prerequisite readings before registry selection.

One process-local host domain owns one Windows terminal capacity object. Ordinary and retained terminals share it across acquisitions and provider generations. The retained quota remains a separate bound. A retained shell can survive acquisition release and accept a new attachment in the same Session and provider generation. The shared retained index checks the tenant and scope. This does not support attachment after process restart.

Windows has no complete cold resource index. `listRecoveryResources` returns `unavailable`, including when this process knows live resources. The registry therefore retains an unavailable recovery result. It must not interpret a partial live list as proof that no older resource exists. Current acquisition settlement and provider retirement still stop their ordinary resources. After Session scope closure, `domain.maintain()` stops retained shells, including shells with no attached acquisition. Provider retirement also stops them. Scope abort alone does not schedule maintenance. Pending settlement and retirement return resources whose stop or ledger recording remains unconfirmed.

`recover` first consults the retained index. Otherwise it extracts the original shell from a retained-leg reference and stops the original Windows Job. Only a confirmed backend stop becomes `confirmedStopped`. An invalid or unreadable Job reference remains pending. A different provider is unsupported. Recovery does not replay scripts or recreate shells.

The provider tests in [windows-provider.spec.ts](../tests/windows-provider.spec.ts), [windows-provider-retention.spec.ts](../tests/windows-provider-retention.spec.ts) and [windows-provider-recovery.spec.ts](../tests/windows-provider-recovery.spec.ts) exercise this integration with real native processes and controlled ledger ports. Command execution and the A-to-B retained attachment pass through the real environment registry. Its authorization and ledger ports remain controlled test providers. They do not establish durable authorization or restart attachment. [host-platform.spec.ts](../tests/host-platform.spec.ts) checks platform selection with controlled prerequisite responses. It does not establish Linux host execution.

The [Windows file prerequisite tests](../tests/windows-files/probe.spec.ts) exercise the native file probe, cleanup, a missing probe directory and a missing PowerShell installation. They do not replace the file facility suites.
