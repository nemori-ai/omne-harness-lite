# Windows command and terminal execution

The internal entry is `createWindowsHostCommands` in `src/windows-execution/index.ts`. It returns the same command manager shape as `createHostCommands`. It accepts that manager's input without the Linux prerequisite probe and callback. Provider integration remains outside this module.

The module requires 64-bit Windows and the installed .NET Framework 4 compiler. It compiles the bundled C# source with `%SystemRoot%/Microsoft.NET/Framework64/v4.0.30319/csc.exe`. It installs no SDK or native package. Compiled binaries are cached under the system temporary directory, in `omne-windows-execution/<source SHA-256>/bridge.exe`. Temporary compiler inputs are removed after compilation. A missing compiler or failed compilation returns `unavailable` before a resource is planned.

The [Windows section of the SPEC](../SPEC.md#windows-的兑现未接受) owns the command behavior: containment, disposition, retention and cold recovery. That section is not accepted yet, and neither is the mechanism on this page.

Each command has a separate native bridge and a randomly named Job Object. The bridge starts detached from Node's child-process lifetime. The TypeScript manager owns ledger calls, disposition and output accounting.

The first member of each Job is an anchor process. The bridge starts the same native executable in anchor mode, with `DETACHED_PROCESS` and with the Job handle as its only inherited handle. The anchor holds that handle and waits. It reads and writes no data. It has no console, so Windows starts no console host for it. The anchor keeps the Job and its name alive while the Job has members, so the death of the bridge or of the harness process does not end a retained Job. The Job keeps `KILL_ON_JOB_CLOSE` for its whole life. If the anchor and the bridge both end, the last handle closes and Windows stops every member.

The manager records a resource plan before native allocation. When a state directory is configured, the manager then writes and flushes the cold-index marker. Only after that does the bridge create the Job, start the anchor and create the requested process. The requested process starts suspended with `PROC_THREAD_ATTRIBUTE_JOB_LIST`. Job membership therefore forms part of process creation. The bridge does not leave a separate assignment step after creation. The attribute requires Windows 10 or Windows Server 2016 or later, as specified by [Microsoft's process attribute reference](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-updateprocthreadattribute). The Job uses `KILL_ON_JOB_CLOSE` and does not allow breakaway. The manager sends `GO` only after a confirmed ledger permit. Executable arguments, the explicit environment and input travel through private pipes. They do not appear on the bridge command line. The private control frame has a 2 MiB limit. Larger requests return `capacity` before allocation.

Output bytes come directly from Windows pipe reads. The shared command buffer supplies offsets, discard counts and the single-reader rule. The configured chunk and buffer limits apply. When the root process exits, the bridge does not end the Job. It waits until both output pipes end or stay quiet for 100 ms, as the Linux gate does, and reports the exit code and the number of members other than the anchor, and the manager decides the disposition. The count also leaves out the console hosts (`conhost.exe`) that Windows starts in the Job for console members. A console host ends with the last process it serves, so it is never what a command leaves behind. A count that cannot be read is reported as unknown, and the manager treats it as leftover processes. After a handover, the bridge keeps reading the output pipes for the retained-process tail. A lost observation produces `effectUnknown`. When the control pipe of a running command closes, the manager stops that Job by name.

Forced stop calls `TerminateJobObject`. Confirmation requires zero active processes in the original Job, anchor included, and a signaled original process handle. A ledger recording failure keeps the resource in `unconfirmed()` even when native stop was confirmed. The outcome of a forced stop of a running command is `failed(effectUnknown)`. The bridge records that it started the stop, so the exit code that `TerminateJobObject` sets is not reported as a natural exit.

Windows has no general request to end a process. The bridge creates each command in a new process group with a hidden console of its own. A graceful stop attaches the bridge to that console and sends `CTRL_BREAK_EVENT` to the root process's group. The bridge is not in that group, so the event does not reach the bridge. If the root process exits within `graceMs`, the forced stop sequence cleans the Job. Processes that the root process left are not handed over. Otherwise the stop returns `unconfirmed`. A root process that is not a console program gets `unconfirmed` at once.

Native stop, recovery, durable recording and bridge-close waits share one `stopBoundMs` deadline. A stalled recording returns `unconfirmed` at the deadline. The manager retains that recording Promise and the original resource. A later call can observe the record without launching another command. The bridge can release native handles after confirmed native termination even when durable recording remains pending.

`stopWindowsResource(resource, boundMs)` reopens the original named Job. It does not start the command again. It confirms zero active members. An orphaned command bridge then exits by itself, because the pipes it drains close with the stopped Job. A terminal bridge exits by itself once its shell has ended. The SPEC states when a missing name counts as a confirmed stop: the marker must record the same boot and the same login session as the current process. Named objects under `Local\` are per login session, so a missing name in another session is no evidence. The caller must preserve the uncertainty if the confirmation is lost before durable recording.

## Persistent terminals

The [Windows terminal section of the SPEC](../SPEC.md#windows-终端未接受) owns the terminal behavior. This section explains the mechanism.

`createWindowsHostTerminals` in `src/windows-execution/terminal.ts` implements the ordinary per-acquisition terminal manager. `createWindowsRetainedTerminalFactory` returns the platform reservation factory consumed by the shared retained-terminal index. It synchronously reserves terminal identity, a managed resource and buffer capacity. Its `start()` then plans the resource and obtains a permit before `GO`. Per-leg permits for retained terminals belong to the shared index. Provider entry selection remains outside this module.

Both factories accept `provider`, `settings` and `capacity`. Ordinary terminals also require `ledger` and `scope`. The retained factory consumes `{ request, ledger, scope, closed }`. A provider domain shares one `createWindowsTerminalCapacity()` object between both factories. Its limits are constants: 64 terminals, 256 windows, 64 MiB of reserved output capacity and 65,536 queued chunks. The `terminal` configuration does not set them. The SPEC records this as a known limitation. Each invocation writes its output into a window. A window reserves its configured maximum buffer size. The window of the next invocation is reserved before an invocation starts. Insufficient capacity rejects the request before script execution. Sealed unread windows retain their bytes and immutable summaries. The bytes kept between segments are bounded by `betweenSegmentBytes` and do not count against this capacity.

The terminal executable uses the installed Windows PowerShell `System.Management.Automation` 3.0 assembly. It embeds one persistent Runspace inside a ConPTY child. The pseudoconsole comes from node-pty's bundled `prebuilds/win32-<arch>/conpty/conpty.dll`, not from `kernel32`. The provider resolves that path from `node-pty/package.json`, checks that `conpty.dll` and the `OpenConsole.exe` beside it exist, and passes the path in the start request. The broker loads the library by its absolute path with `LoadLibraryExW` and calls its `CreatePseudoConsole` and `ClosePseudoConsole` exports. Their signatures are the same as those of `kernel32`. `conpty.dll` starts `OpenConsole.exe` from its own directory as the pseudoconsole host. That process is outside the terminal's Job and ends when the broker closes the pseudoconsole. It does not install PowerShell or an SDK. PowerShell state and the observed working directory persist across invocations. Single-invocation `cwd` and `env` overrides are saved and restored. A failed restoration invalidates the terminal. Scripts use PowerShell syntax. Interactive credential and nested prompts are unavailable. This provider does not claim a sandbox or isolation from hostile code running as the same Windows user.

ConPTY requires Windows 10 version 1809 or Windows Server 2019 or later, according to [Microsoft's ConPTY reference](https://learn.microsoft.com/en-us/windows/console/createpseudoconsole). Terminal dimensions use signed Win32 coordinates and must not exceed 32,767 columns or rows. The host sends PowerShell output and errors through `Out-Default`. Host, information, warning, verbose, debug and progress messages write to the actual console. Their ConPTY bytes follow the same segment rules.

The shell host sends invocation identities and control facts through a private named pipe restricted to the current Windows user. The native broker reads raw ConPTY bytes. One broker lock orders output records and control events. User output cannot complete an invocation. The handle's process identity names the persistent shell resource and generation. Each invocation also has an internal identity.

The shell explicitly opens `CONIN$` and `CONOUT$`, then binds its standard handles to those console handles. It does not use the broker's standard handles for script input or output. Native programs inherit the console handles. A broken broker transport bypasses the unavailable send path and uses the original Job recovery coordinate within the remaining stop budget.

`completed` confirms foreground invocation completion and its fixed segment output. It does not confirm shell or background-process termination. The returned `exit` is a known code. The SPEC gives the rule. The host applies the rule as follows:

1. Before each invocation, the host sets `$global:LASTEXITCODE` to `$null` in a separate pipeline. It records the newest record in `$Error`.
2. The host appends one trailer statement to the script, on a new line. The trailer copies `$?` into `$global:__omne_succeeded`.
3. After the invocation, the host reads that variable and removes it. It reads `$LASTEXITCODE` and the records that are newer than the record from step 1.
4. The host implements `PSHost.SetShouldExit`. It records the code, completes the invocation with that code and then ends the shell. It does not call `Environment.Exit`.

`OmneTerminalExit` in `src/windows-execution/terminal-native-source.ts` holds the rule as pure functions. `Code` applies rules 2 to 6. `Added` classifies the new records: none, only native standard error (`NativeCommandError`), or other. `$Error` keeps at most `$MaximumErrorCount` records. When the record from step 1 left the list, or when the list was empty and is now full, `Added` answers other, so rule 4 does not apply.

A terminating error, or a `return`, `break` or `continue` at the top level of the script, stops the script before the trailer runs. The host then applies the rule with `$?` false. Script errors remain actual terminal output. A lost control channel produces `effectUnknown` and invalidates the terminal. Output observation failure produces `unavailable` and preserves the bytes already observed.

The private `finished` frame uses version 3. A completed frame carries the exit `code` and a nonnegative, safe-integer `elapsedMs` measured by the shell host's monotonic clock between Runspace running and terminal state transitions. Every `finished` frame carries `ended`, which is true when `exit` ends the shell. The manager then marks the terminal invalid at once, so a later invocation is not sent to the ending shell. The public `durationMs` uses that elapsed fact, including when Node cannot dispatch control events until after completion. Missing, unsupported-version or invalid elapsed data fails control validation. An incomplete frame carries `elapsedMs: null` and `code: null`. Failed outcomes keep Node's local `observedDurationMs`. The implementation does not subtract timestamps from different clocks.

The broker holds the only handle to the terminal Job. It stops the Job and exits in two cases:

- The provider's control pipe ends after `GO`. Nobody can stop the terminal after that, so the broker stops it. This happens when the provider process dies.
- The shell process exits. The broker first forwards every control frame of the shell, then stops the Job. `exit N` and a graceful close end the shell this way.

After the shell exits, the broker reports its stop with an unsolicited `stopped` frame. The broker also reports `controlLost` when the shell's control pipe ends. That frame invalidates the terminal, but it does not answer a stop that is waiting: the broker is still there and answers the stop itself. A broken transport on the Node side is reported as a broker fault. The manager then keeps the control pipe open, so the stop by Job name finds the Job.

Bytes are attributed by the segment sentinels of the Linux terminal, with the shared scanner in `src/terminal-sentinels.ts`. Each invocation carries a fresh 128-bit nonce in its control message. The shell host writes `ESC ] 7770 ; omne-b ; <nonce> BEL` to the console before the script and `ESC ] 7770 ; omne-e ; <nonce> BEL` after the script and the restoration of `cwd` and `env`. Errors of the overrides and of the restoration are therefore inside the segment. The bundled ConPTY passes the private OSC sequence through in order with the text it renders. The manager scans the broker's data frames for the current nonce only, removes the sentinels and holds a stream tail that can start a sentinel.

Bytes between the two sentinels go to the invocation's window. Bytes outside any segment go to a buffer bounded by `betweenSegmentBytes`. At the next begin sentinel the buffer becomes that invocation's `between`, with its observed and discarded counts. Bytes after the bound only increase the discarded count. The first invocation's `between` holds the control sequences ConPTY writes when it starts. Chunk offsets are relative to each window's start. Overflow of a window discards newly observed excess bytes and records the corresponding offset gaps. Reader abandonment does not stop execution. Abandonment before sealing contributes to discard counts. Abandonment after sealing releases bytes without changing the fixed summary.

The `finished` frame comes over the shell's control pipe and the end sentinel over the ConPTY output, so either can come first. The manager answers an invocation when it has both. When the shell's control pipe ends first, for example after `exit N`, the manager keeps reading data frames until the end sentinel arrives or the broker's output ends. Output that ends without the end sentinel fails the invocation with `effectUnknown`. A duplicate begin sentinel or an end sentinel before the begin sentinel fails the invocation with `effectUnknown` and invalidates the terminal. A missing `conpty.dll` or `OpenConsole.exe` rejects `create` with `unavailable` before the ledger plan, and the `terminalUnavailable` diagnostic names the missing files.

Forced stop can destroy the persistent shell and its entire Job. Confirmation requires the native resource to stop and the terminal ledger to record the stop. The terminal cannot be reused afterward. Other terminals have separate Jobs. An ended invocation's old handle returns `unconfirmed` unless the original resource already has confirmed termination. It never kills a newer invocation. Graceful stop requests shell shutdown but does not claim termination from request acceptance. Cold recovery stops the original Job and does not reattach or rerun scripts.

The ordinary manager removes confirmed closed entries before a later create and after `stopAll`. Such old references return `notFound`. Unconfirmed resources remain in the manager and continue to occupy capacity. Completed control events carry ordered invocation identities, so repeated events do not start another invocation or invalidate a newer one.

The [Windows tests](../tests/windows-execution/) cover real executables, Jobs, ConPTY and the embedded shell. Their ledger ports are controlled test providers. These tests do not establish provider assembly, tenant authorization, durable storage or cross-service retention. The native crash test kills the broker immediately after process creation and waits on the original suspended child's process handle. The provider-gone test kills a provider process that holds the control pipe of a broker. It then checks that the broker, the shell and a background member of the Job end, and that the Job name is gone. The exit test runs each row of the F3 table in one real shell. The segment tests run 30 invocations in one real shell and check that each output holds only its own lines with an empty `between`. They also check bytes a background writer writes between invocations, and the bound of the between buffer. The attribution test drives the manager with a stand-in broker to deliver the frames in each order. The read-order test holds the broker's reader and checks that an invocation is answered only after its end sentinel is read.

## Host provider integration

The host provider selects the Windows command and terminal factories on Windows. It does not start the Linux systemd or PTY probes there. Its installation check reads the Windows build, the .NET compiler and the PowerShell assembly, obtains both native bridge executables and runs the Job round trip. The SPEC names these items `windows-version`, `dotnet-csc`, `powershell-assembly`, `job-round-trip`, `conpty.dll` and `OpenConsole.exe`. A known missing prerequisite is `unsatisfied`. An unreadable prerequisite or failed compilation is `unknown`. Successful compilation establishes installation facts only. The facilities still report actual startup failures. The files prerequisite remains independent. On Windows it starts the files helper and runs one handle-relative creation, read, listing and removal in the state directory, or in its own temporary directory when no state directory is configured. A missing compiler is `unsatisfied`; an inconclusive operation or failed cleanup is `unknown`. This probe supplies no business principal and grants no file permission. The provider combines both execution and file prerequisite readings before registry selection.

One process-local host domain owns one Windows terminal capacity object. Ordinary and retained terminals share it across acquisitions and provider generations. The retained quota remains a separate bound. A retained shell can survive acquisition release and accept a new attachment in the same Session and provider generation. The shared retained index checks the tenant and scope. This does not support attachment after process restart.

The cold resource index is the set of markers in the state directory. `listRecoveryResources` reads the markers of the requested scope. Without a state directory, or when a marker cannot be read, it returns `unavailable`. The registry then retains an unavailable recovery result and does not interpret a partial live list as proof that no older resource exists. Current acquisition settlement and provider retirement still stop their ordinary resources. After Session scope closure, `domain.maintain()` stops retained shells, including shells with no attached acquisition. Provider retirement also stops them. Scope abort alone does not schedule maintenance. Pending settlement and retirement return resources whose stop or ledger recording remains unconfirmed.

`recover` first consults the retained index. Otherwise it reads the marker of the reference and applies the decision in the SPEC: a different boot is `confirmedStopped`, a different login session is `pending`, and in the same boot and session the original Job is stopped by name. A different provider or an unsupported reference format returns `unsupported`. An unconfirmed stop remains `pending`. Recovery does not replay scripts or recreate shells.

The provider tests in [windows-provider.spec.ts](../tests/windows-provider.spec.ts), [windows-provider-retention.spec.ts](../tests/windows-provider-retention.spec.ts) and [windows-provider-recovery.spec.ts](../tests/windows-provider-recovery.spec.ts) exercise this integration with real native processes and controlled ledger ports. Command execution and the A-to-B retained attachment pass through the real environment registry. Its authorization and ledger ports remain controlled test providers. They do not establish durable authorization or restart attachment. [host-platform.spec.ts](../tests/host-platform.spec.ts) checks platform selection with controlled prerequisite responses. It does not establish Linux host execution.

The [Windows file prerequisite tests](../tests/windows-files/probe.spec.ts) exercise the native file probe, cleanup, a missing probe directory and a missing compiler. They do not replace the file facility suites.
