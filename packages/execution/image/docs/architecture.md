# 图像成员架构

状态：技术设计已接受，见 [技术设计接受](https://github.com/nemori-ai/omne-harness-lite/issues/277#issuecomment-6198093789)。行为条件在 [SPEC](../SPEC.md)。类型在 [模型](model.md)。步骤在 [关键流程](key-flow.md)。Cordis 装配在 [集成](cordis.md)。

## 责任

图像成员拥有预算、声明、打开句柄、编码和关闭。

执行环境拥有落点、隔离和设施就绪。content-block 拥有封闭块的形状，不解码像素。保存图像字节的调用方拥有保存。准备模型输入的调用方拥有模型请求。宿主上的文件使用对象核对留在 `execution-environment`。本成员不描述 `Files()` 或 `Shell()` 的落点。

本成员放在执行组，是因为它持有一份可关闭的原生资源。它不改写执行环境的规格。

## 模块

根入口导出 `imageBudget` 和 `open`。打开句柄导出 `encode` 和 `close`。解码库的类型只出现在适配器里。适配器由 [Cordis 集成](cordis.md) 交进根入口，调用方不导入它。

新增格式时改格式联合和适配器。`imageBudget`、`open` 和 `close` 的调用形状不变。替换解码库时，根入口和服务定义的签名不变。

本成员不用继承表达另一种解码器。根入口和 Cordis 服务返回同一种拒绝。预算不合法时两边都返回拒绝。

只保存原始字节的调用方使用 `imageBudget`、`open` 和 `close`。编码只挂在打开句柄上。

## 旧实现里沿用的行为

封存成员 `@omne-harness-lite/image-codec` 用调用方传入的 sharp 0.35.3 做检查、解码和编码。输入可以是 png、jpeg、webp 和 gif。输出是 png、jpeg、webp。检查可以不分配光栅。解码得到 8 位 RGBA。方向 6、5、7、8 在解码时对调宽高，原始字节不改。多页在元数据核对时拒绝。关闭之后再编码得到不可用。APNG 的页数由自己读取 `acTL` 并核对 CRC，不靠解码库报出的默认帧。

这些行为留在本成员的打开和编码里。页数规则只用于拒绝多帧。gif 不进入允许列表。模型准备里的质量阶梯、尺寸搜索和请求缓存不留在本成员。原始字节的保存由调用方完成。

## 旧实现里不沿用的问题

最大边长在光栅已经分配之后才比较，失败类别是内部错误。本成员在光栅出现之前拒绝。

检查把 `limitInputPixels` 设成最大安全整数。超限因此可以进入解码。本成员的宽、高和解码后字节估计先于解码。

错误类别靠解码库的消息文本匹配。本成员的拒绝原因来自容器检查和预算比较。解码库抛出时，句柄发布前的失败是解码失败，并释放刚占上的预留。

取消只在阶段之间查看。已经开始的原生调用不会因为 Promise 结束而停止。本成员不接收取消信号。停止等待不关闭句柄。原生停止只有未被证明。

编码规格把缩放和背景铺平放进同一次编码。本成员的编码只换格式，不搜索目标尺寸。

## 未选的公开入口

只导出一个准入函数、成功时返回原始字节并在函数结束时丢掉光栅。公开面更小。调用方停止等待时，类型里没有对象继续持有预留，编码也要再解码一次。这个形状没有成为公开入口。
