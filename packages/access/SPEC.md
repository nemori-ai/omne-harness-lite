# Access

## 总体架构

接入层回答一件事：客户端和服务端怎样接。两端各是一棵 Cordis 树，中间只有一条连接。

| 成员                     | 回答的问题                                                                             |
| ------------------------ | -------------------------------------------------------------------------------------- |
| `public-contract`        | 两端共用的纯数据：对外结果的词汇、一份协议契约长什么样、字段规则与编解码，只有共同部分 |
| `server-entry`           | 服务端的入口：管道、登记表、观察中枢、进程内调用                                       |
| `access-cordis-contract` | 领域的接入插件用什么服务把协议挂上登记表；管道向身份要的端口                           |
| `sdk`                    | 客户端怎样按一份协议契约发出调用与观察：协议客户端核心与两种传输                       |
| `client-assembly`        | 客户端的装配：连接、服务端现在挂着哪些协议、每个协议一个协议客户端                     |

一次调用这样走：界面模块调协议客户端的方法，协议客户端经连接把消息交给入口，入口的管道建立身份后在登记表里找到处理函数，处理函数在领域的接入插件里，它调领域的公开入口。调用是一问一答，观察是一条事件流。入口自己挂一个内置协议 `access/v1`：一个观察答现在挂着哪些协议，一个读操作答发问的租户自己挂着哪些协议。客户端的连接一直订阅它，协议客户端随它长出与收回。

## 领域边界

接入层拥有消息怎样在两端之间走：外层的形状，身份怎样随每次调用带上，结果用哪些词，判断按什么次序，一个协议现在挂没挂着，结果不知道时两端怎样对待它。

接入层不拥有任何领域的含义。入口与界面外壳不认识任何领域。对客户端开放的三样，协议契约、接入插件、协议客户端与界面模块，都是领域带来的；开不开放由应用的装配决定。登录、主体与资格归身份与授权；会话、Run 与日志归 Session；卡片与答复归人工介入；调用状态与内容流归 Model。接入只核「这个调用者是谁」，不判断他能做什么。

「挂没挂着」和「许不许用」是两件事。入口放行不等于允许。

本组声明、由别人实现的端口：

| 端口                                                                   | 对方                       | 本组需要它做什么                                               |
| ---------------------------------------------------------------------- | -------------------------- | -------------------------------------------------------------- |
| 身份端口 `AccessIdentity`（`identifyLogin`、`actFor`、`resumeLogin`、`reportAccess`） | 身份一侧的适配（应用装配） | 由登录证明认出登录；为登录与租户签发主体；按认出时记下的登录与行事租户重新签出登录身份；记一次成功的业务访问 |

本组为别人实现的端口：

| 端口                                                | 对方                               | 本组提供什么                                               |
| --------------------------------------------------- | ---------------------------------- | ---------------------------------------------------------- |
| `defineProtocol`、`ruleCodec`、对外结果表           | 每个开放给客户端的领域的协议契约   | 一份字段规则同时得到类型与读写；管道替领域答的结果自动补上 |
| `AccessRegistryService.mount`、`defineAccessPlugin` | 每个领域的接入插件                 | 把协议挂上登记表，卸载即撤下                               |
| [进程内调用](#进程内调用)                         | 服务端里要替一个人做别的协议操作的领域（经应用装配） | 用那个人的登录，走与管道相同的身份、校验、处理函数与结账 |
| 协议客户端核心 `createClient` 与两种传输            | 每个领域的协议客户端；脚本与第三方 | 由协议契约得到客户端，结果只有契约的结果加两种本地结果     |
| `connectionPlugin`、`defineProtocolClient`          | 客户端应用与每个领域的界面模块     | 跟随可用性；服务端开着而且这个客户端带着契约的每份协议，是点 `connection.protocols` 上的一项 |

## 心智模型

服务端是事实的权威，客户端只有投影和缓存。

协议客户端跟着协议走：服务端把一个协议挂上，客户端这边它的协议客户端就长出来；撤了就收回，收回之后它的每个方法都答不可用。

入口是一个只会查表的门卫。它认得每个调用者是谁，认得每个协议挂没挂着，认不得任何业务；认出来的主体原样交给领域，许不许由领域判断。门卫对所有「认不出来」给出一模一样的拒绝，所以调用者从拒绝里试不出对象在不在。

拿这几条量一个设计：客户端里一个离开服务端就没法重新得到的事实，是放错了地方；界面模块里一段处理连接、可用性或重发的代码，是做了协议客户端该做的事；入口里出现一个领域的名字，是把接入插件的事做进了门卫。最容易想错的三处：传输断了不等于没做，提交类的结果就是不知道；观察的取消只结束观察，不是业务控制；挂上不等于开放，开放由装配挑。

## 应然设计

### 一次问

一次问是一个消息号加一份字节。传输能证明一个字节也没发出时，同一份字节再送一次；仍没发出，答「不可用」。字节可能已经发出而没有可信的答复，答「不确定」，不再送。这两个答复只在本地产生，不写成成功，也不写成失败。

HTTP 传输把两类失败认作没发出：连接建立之前就失败的（连不上、解析不到、路由不到、连接超时），以及运行时的 `fetch` 因目标端口在它的禁用端口表里而拒绝连接的。后一类不带错误码，按 `fetch` 给的原因识别；识别不出的一律算「不确定」。服务端监听在这样的端口上时，用 `fetch` 的客户端都连不上它。

消息号只把答复对应到这一次发送，不是去重键，也不进入任何业务身份。只有带着同一消息号的答复才交给这次调用；没有消息号的协议拒绝不记到任何一次调用上。

### 读与写

每个操作在协议契约里标明是读还是写。

写可能在服务端留下效果。它的答复不论是什么，协议客户端都原样交给调用方，不替调用方再问。

读没有效果。读得到「不可用」「不确定」或「依据不可用」时，这只说明现在读不到。协议客户端按装配给它的策略等一会儿再问。再问是一次新的问，用新的消息号。

再问在这三种情形下停止，并把手里的答复交给调用方：策略答不再等；调用方中止了这次调用；这个协议被撤回。

等待在服务端的可用性视图来了新的一帧时提前结束：服务端回来了就立刻再读，不等到点。

策略由应用给。没有拿到策略的协议客户端，每个读只问一次。

### 判断次序

- 一次调用按固定次序处理，前一步给出终端结果就不做后面的步骤：管道依次判地址、方法、`Host`、`Content-Type`、协议挂没挂着、在途预算、消息号、契约修订号、身份与消息体（见[管道](#管道)）；处理函数在领域里接着判目标租户与主体、部署范围与领域规则；要登录的读，处理函数给出答复之后、写出之前，管道再核一次登录。协议拒绝先于一切身份核验与业务读取，没有任何业务效果。
- 严格读取不接受注释、尾逗号与重复键。服务端不协商版本，按地址里的协议名与主版本选契约，不按消息里的文本分派。
- 同一个主版本里两端可以不同步升级。调用方在头 `Omne-Contract-Revision` 里写明自己的契约修订号：十进制正整数，没带算 1。服务端取「自己的修订号与对方的修订号里较小的那个」，按它读消息体、写答复、写这次观察的每一帧：对方不认识的字段不写出去；消息体里有这个修订号之后才有的字段，或调的是这个修订号之后才有的操作，答 `protocol-rejected`，什么都不执行。没有来回的协商：服务端只是不向对方写它没声明认识的东西，读取仍然严格。领域的处理函数不知道有修订号。
- 发起者只取登录证明认出的账号；消息体里的账号、组织与租户都是目标。裸账号标识、地址、旧连接与调用者自报的授权结果都不是登录。代租户行事主体的签发判据归身份，见[主体的签发与核验](../identity/SPEC.md#主体的签发与核验)：入口管道给 `acting-tenant` 的操作签发时，只要租户属于这个登录的账号；业务领域的接入行为目标租户办业务之前，还要这个租户的成员资格当前有效。

### 对外结果

结果是一个封闭集合。调用者只能依赖结果名与该结果列出的正文；内部诊断可以更细，但不进 SDK 或错误文本。每个结果答一句「调用者能知道什么」，也写明「不能由它推出什么」：

| 结果                 | 调用者可以知道的                       | 不能从该结果推出的                             |
| -------------------- | -------------------------------------- | ---------------------------------------------- |
| `denied`             | 本次不获准                             | 是禁止、无权、登录失效、跨租户，还是对象不存在 |
| `not-visible`        | 与目标不存在同一表现                   | 目标是否存在、属于谁                           |
| `basis-unavailable`  | 现在不能得出允许                       | 已知无权或已知冲突                             |
| `unknown`            | 提交结果没有认回                       | 效果没有发生，或可以安全地自动再做一次         |
| `not-committed`      | 原操作确定没有提交，可以用原标识再发起 | 再发起一定成功                                 |
| `need-decision`      | 要等原决定请求的一次人的答复           | 等待已经批准、拒绝或将超时批准                 |
| `stage-not-provided` | 本阶段或本部署不提供该操作             | 主体是否存在、登录是否有效                     |
| `protocol-rejected`  | 消息不被接受                           | 任何业务事实                                   |

六种结果的正文永远是空对象：`denied`、`protocol-rejected`、`basis-unavailable`、`unknown`、`uniform-auth-failure`、`stage-not-provided`。领域在类型上给不了它们字段。

### 拒绝一致与不披露

- 凡是没能确立调用者是谁、行事租户不符、对象不存在或属于别的租户、主体没有资格，对外都是同一份 `denied`，响应除消息号外逐字节相同，头也相同。
- 状态码只由结果决定，与对象是否存在无关；不同结果可以共用一个状态码，调用者不由状态码推出结果，也不由状态码决定是否再送。
- 秘密只出现在请求里：登录证明、凭据与秘密设置值不进响应、诊断、日志或错误文本。诊断只带代码、路径、协议名与操作名，不带头的值与消息体。

### 未知、再送与认回

- 连接断开、超时与响应丢失使调用者本地保持未知。它不是成功，也不是没有发生。
- 调用者在首次发送前生成业务标识（创建、受理、控制、答复各一种），重试同一意图时保持不变；SDK 不替调用者换它们，客户端也不填写服务端派生的身份。
- 未知之后，调用者用同一组标识原样再送（同内容得到原结果）或用对应的查询认回。确认 `not-committed` 之前，不换新标识重做同一意图。同一标识对应不同内容是 `conflict`，响应不含原内容。
- 存储给不出排除证明时，查询答 `unknown`，不答 `not-committed`。只读操作没有 `unknown`，原样再送即可。
- 服务端派生的业务身份是确定性的：同一意图在崩溃前后、重连之后得到同一身份。创建与受理按租户与标识派生；中断另含登录，因为不同登录不共享中断回执；HITL 答复按租户与答复标识派生，不含登录，换一份登录原样再送仍认回同一次提交。派生的算法归各领域，接入调用它，不另写。
- 客户端不缓存准入允许、登录证明或凭据。清掉投影不把 `unknown` 变成成功或没有发生。

### 名单与分页

- 一份名单要么完整，要么整份不可用：成功时数组给出全部当前项并标明完整；任一项读取时判定不了，整份答 `basis-unavailable`。不丢项，不把不可用改成空名单。
- 分页读取的空页不表示读完；读完由显式的标记给出。游标原样交回，不是读取资格，每一页都重新核验当前资格；游标错域、失效或被篡改是 `invalid`。

### 会话观察

会话观察是 Session 的接入插件开放的观察，规则归 Session 的[会话观察](../session/SPEC.md#会话观察)。接入层只给它管道与观察中枢：名额、替换、心跳复核登录与结束帧，见[观察中枢](#观察中枢)。

### 登记表与撤下

- 入口不自己存「挂着哪些协议」：它是 [Dynamis](../dynamis/SPEC.md) 登记表上的一个点 `access.protocols`，由入口声明。一份协议是这个点上的一个条目：键是「协议名/v主版本」，内容是这份贡献（处理函数与帧来源只当函数调用）、它的契约修订号与一个中止的句柄。点的规矩：每键至多一项，交带副作用的函数，同键多份答冲突，运行中能变。入口不认识任何领域。
- 应用为整个部署挂上的协议条目带锁（`lock: true`）：租户那一层放不出同键的一份来顶掉它。锁的答法归 Dynamis 的[答案](../dynamis/SPEC.md#答案)。
- 条目的内容摘要带着放它的实例。所以两个接入插件挂同一份协议一定是两项，答冲突，不会因为契约相同被并成一项、由其中一份悄悄胜出。
- 挂上是接入插件作用域上的一个效应，经服务 `dynamis` 登记，写法照 [`dynamis-cordis`](../dynamis/SPEC.md#接到-cordis-上dynamis-cordis)。接入插件就绪时它挂的协议才出现；`apply` 抛错的接入插件挂的协议从不出现。接入插件不写撤下的代码。
- 接入的 Cordis 契约只留一句承诺：`AccessRegistryService.mount(贡献)` 把协议放成调用它的插件作用域上的效应，那个插件就绪时开始服务，离开时撤下；两个插件挂同一份协议是冲突，不是这里的错误。`defineAccessPlugin` 的写法不变，所以各接入成员的源码不用动。旧的受保护钩子 `attach` 与错误类型 `AccessAssemblyError` 退出：前者是「登记表自己存一张表」时的形，后者是「同名第二份抛错」时的形。入口自己的那份 `access/v1` 没有接入插件，由入口那一行经提供者的 `own` 放上去、自己取回。
- 同名同主版本的协议任一时刻至多一份在服务。挂了两份时两个接入插件都照常加载，这份协议两份都不服务，调用答「没有执行，原因是冲突」，诊断写明是哪两家；别的协议不受影响；撤掉一份，另一份立刻服务。答案与谁先挂无关。不带 Cordis 的场合（入口自己的用例与夹具）用 `createStandaloneRegistry`：同一张协议表，每次挂上是一个自己的实例，答法相同。
- 进入是一个同步段：按条目现取，取到唯一的一项才把这次调用记在账上，钉在放这一项的实例上；中间不让出执行权。账是 Dynamis 的撤下的账，只用「在跑」与「完成」两种状态；入口的进程没了，在途的 HTTP 请求也断了，没有东西可认回，所以不用「未知」。
- 撤下是一个过程。接入插件离开时，它的实例在登记表上正在撤下：条目还在，答案不再看它，新的调用进不来。入口给这份协议在途的工作发中止。这份协议名下最后一个在途的工作离开时排空完，实例才取走；插件的卸载等它。
- 同一个名字的接入插件在旧的一代还在排空时又装上：新的一代立刻服务，旧的一代照旧排空，各记各的账。因为依赖丢失而卸载的接入插件不是这种情形：Cordis 里依赖的提供者要等依赖它的卸完，排空期间依赖回不来。
- 领域服务暂时不在不等于撤下：处理函数每次调用现取领域服务，取不到答 `basis-unavailable`，协议仍挂着。

### 管道

- 新地址是 `/api/<协议名>/v<主版本>/<名字>`。管道依次判：路径合文法、方法、`Host`、`Content-Type`、协议挂着且名字在契约里、在途预算、消息号、契约修订号、身份、按契约的上限读消息体并按契约的编解码读成类型。前一步给出答复就停。
- 契约修订号的头多于一个、或不是不带前导零的十进制正整数（至多九位；规则里的 `since` 也不能超过这个数，超过的在定义协议时就被拒绝）时，答 `protocol-rejected` 并记 `access.revision-rejected`；调的操作或观察的 `since` 大于对方声明的修订号时同样。这一步在消息号之后，所以答复带着消息号；在身份之前，所以不为它问身份端口。
- 没有被提供的三种情形都答 404 加一份写明「什么都没有执行」的正文 `{"kind":"not-executed","reason":…}`，原因各不相同：协议没挂是 `not-mounted`（记 `access.not-mounted`），协议挂了两份是 `conflict`（记 `access.protocol-conflict`，诊断带两家的实例名），协议在服务而契约里没有这个名字是 `not-offered`（记 `access.not-offered`）。挂着哪些协议本来就对所有调用者公开，所以这不多说出什么。两端修订号不同的时候，新的一端调到旧的一端还没有的操作，得到的就是这个答复。
- 登记表上 `access.protocols` 这个点读不出（没有声明、被声明了两次、它的来源读不出）不是「没挂」：调用答 503 加同一种正文，原因是 `unavailable`（记 `access.registry-unavailable`），同样什么都没有执行；可用性保持上一次读到的样子，不把读不出说成全部撤下。SDK 把这四种原因都读成没有发出。
- 一个租户自己的协议（它持有的 plugin 挂的）在这个租户的范围里，不在整个部署这一层。整个部署这一层答「没挂」、调用带着登录证明与 `Omne-Acting-Tenant`、身份端口认得这个登录并为这个租户签发了主体时，管道用应用给的「租户的范围」再问一次登记表：挂着就照常往下走；挂了两份、名字不在契约里、读不出，照上面答。别的情形答第一次的 `not-mounted`：没登录的、为别的租户行事的、签发不了的，得到的字节与这份协议根本不存在时相同。问不问第二次只看调用者自己的证明，与别的租户挂了什么无关。应用不给租户的范围时只问整个部署这一层。可用性只列整个部署这一层，租户的协议不在里面。
- 未知的操作与没有身份的调用在读消息体之前就被答复；这类答复与每一个 `denied` 都关闭连接，没有身份的调用者不能让服务端读入任意多的数据。
- 身份按契约的身份一栏：不要身份的不读身份头，主体为空；要登录的核验 `Authorization` 头里的登录证明；要行事租户的再用 `Omne-Acting-Tenant` 头签发主体。身份结果不缓存，每次调用都重新识别。管道不读主体里的字段，也不看消息体里的租户，原样交给领域。
- 答复之前再核登录：身份一栏要登录、读写一栏是读的操作，处理函数给出结果集里的答复之后、写出之前，管道用调用建立时的同一份登录证明再问一次身份端口。认出的仍是逐值相同的那个登录，原答复写出；不认得了或认出的是别的登录，答 `denied`；端口答依据不可用或抛出，答 `basis-unavailable`。改掉的答复正文为空，不带处理函数读到的内容。处理函数抛出、返回集外的结果、过了宽限，或管道已经给出答复时不再核。写不再核：提交在处理函数里可能已经发生，这时答 `denied` 不真。不要登录的操作没有登录可核。这一道把答复改成 `denied` 时记 `access.login-revoked-before-answer`；端口答依据不可用记 `access.identity-unavailable`，抛出记 `access.identity-fault`。每个读多一次登录查询，结果不缓存，也不和建立时的那次合并。
- 在等身份端口与读消息体时，同时等撤下的中止与调用者断开：中止答 `basis-unavailable`，断开不答，都不调处理函数。处理函数开始之后调用者断开，不给处理函数发中止，它照常跑完。
- 新地址只在注册表、身份端口、宽限与两个积压上限全部给出时开启；全缺时每个地址都答 404。开启时入口在启动时把内置协议挂上注册表，停止时最后一个撤下。
- 管道的诊断只带代码、路径、协议名、主版本与操作名，不带头的值、消息体与身份。处理函数答 `basis-unavailable` 时记 `access.basis-unavailable`；请求处理抛出时记 `access.request-fault`：抛在处理函数里的按[收场](#收场)的规则答复，抛在管道自己的步骤里的写出空正文的 500 并关闭连接。

### 进程内调用

- 服务端里的一个领域要替一个人去做别的协议的一个操作时（例：会话替发 `/model` 的那个登录做 `select-model`），走入口的进程内调用 `accessCalls.call`，不直接调那个领域的公开入口。它做的事与[管道](#管道)相同，只去掉读网络请求的几步：进登记表，确立身份，校验字段，调处理函数，照契约答复，结账离开。只做操作；名字是观察时答没有被提供。
- 进登记表照同样的范围规则：先问整个部署这一层；那里答「没挂」，而调用方交来的这个人能为这个租户行事时，再问这个租户的范围。
- 身份：调用方交出它认出这个人时一并记下的登录与行事租户，身份端口的 `resumeLogin` 按这一对重新签出登录身份，操作要行事租户的再经 `actFor` 签主体。不再要登录证明，也不核这一对是否相配：这与排队的输入受理时签主体是同一个信任边界，所以调用方只能交它自己记下的那一对。签不出答 `denied`，身份端口读不出或抛出答依据不可用。答复之前不再核一次登录，也不记业务访问。
- 字段：调用方交的是操作契约里的值，入口按契约把它写成线上的样子，再按入口的契约修订号读回来交给处理函数；写不成或读不回答 `protocol-rejected`。
- 答复与网络调用同一套：协议没挂、挂了两份、名字不在契约里、登记表读不出，答「什么都没有执行」并写明哪一种；其余是那个操作的答复，处理函数抛出时提交类答未知、只读类答依据不可用。它不放宽也不收紧那个操作的访问裁定：许不许由处理函数照它自己的规则判。
- 调用方给一个标识，它就是处理函数看到的消息号。同一个控制标识再送，由那个操作照它自己的认回规则答原来的结果；入口不另存。
- 只有服务端里经装配拿到这个服务的领域能用它，它不对客户端开放。

### 收场

- 处理函数返回结果集里的结果且写得出，原样答复。返回集外的结果、写不出、抛出、或中止之后过了宽限还没返回时，答复只由操作的读写一栏决定：读答 `basis-unavailable`，写答 `unknown`，因为处理函数开始之后提交可能已经发生。收场开始时已中止则不调处理函数，答 `basis-unavailable`。
- 宽限只在中止之后计时，必填，由装配给出。宽限之后迟到的结果丢弃，不写第二次答复。每种情形都先答复，再离开在途集合恰好一次。
- 再核登录算在处理函数的那一段里：宽限照样计时，中止之后过了宽限还没核完，读答 `basis-unavailable`。
- 成功的业务访问在写出答复之后报告，不等报告结束；报告失败不改答复。只有最终写出的是 `succeeded` 才报告：被再核登录改掉的答复不报告。

### 观察中枢

- 先占名额再附着：每实例一个上限，要登录的观察另计入它那个登录的上限。名额满了答 `basis-unavailable`。同一键（登录证明、地址与消息号）已有观察时，旧的以 `observer-replaced` 结束。
- 占名额时「够不够」的判定与计数加一在同一个同步段里，两个一起通过读取资格的请求不会同时越过上限；被这一次替换的旧观察不占名额。不要登录的观察没有可认的观察者，它的键只属于自己，不会被替换。
- 帧来源先决定建不建立；它的拒绝、抛出、撤下与调用者断开都不建立观察并还回名额。帧来源拿到的是主体，不是「已允许」。
- 帧来源拿到的上下文带 `revision`：这一路的帧按哪个契约修订号写，取两端较小的那个。写帧时少写字段仍归入口；这个数只用来决定一件事：一帧如果只因为订阅者读不到的东西变了才要发，来源不发它，也不为它动这个订阅者排着的帧。
- 中枢只对入口自己的可用性来源按写出的节奏拉帧：上一帧离开写队列才拉下一帧，积压留在帧来源。领域的观察一有帧就被拉取，积压碰到字节上限即结束。
- 每个观察恰好离开一次：结束帧写出之后，或等了宽限还写不出去、断开连接之后。每一种结束都中止给帧来源的信号。帧来源给出契约之外的结束原因、抛出或给出不合契约的帧，以 `unavailable` 结束。
- 每个心跳间隔复核一次登录；登录无效以 `denied` 结束，依据不可用以 `unavailable` 结束。连续一个心跳间隔没有写出字节时写一行心跳注释。
- 收场宽限、心跳与每轮复核登录的等待都登记在入口收到的时钟上，中枢自己不起宿主的定时器。应用没有给时钟时入口用宿主的定时器。每轮复核登录的等待标为后台等待，它不单独让宿主进程活着。
- 帧不带内容、只说「变了」的观察共用一个帧来源：建立之后先给一帧，之后把连着的几次变化合成一帧，每次给帧之前重核准入。领域只交按租户订阅变化的端口。

### 可用性

- 内置协议 `access/v1` 的观察 `availability` 不要登录（它另有一个要行事租户的读操作，见[租户范围的协议](#租户范围的协议)）：哪些协议挂着不是秘密，登录本身也是某个协议的操作。它对所有调用者给出同样的字节，不计入每登录的名额。入口在监听的整段时间里都挂着它。
- 订阅的第一帧是快照；之后每次挂上或撤下排一帧变化，变化的基础是修订号减一。一个订阅者积压的变化超过上限时，丢掉它排着的全部变化，下一帧改发完整快照。断线后重新订阅从快照开始。
- 客户端收到基础对不上的变化帧时不应用，改为重新订阅。
- `access/v1` 在契约修订号 3；修订号 3 加的见[租户范围的协议](#租户范围的协议)。修订号 2 加的都是可选字段：快照与变化帧里每份在服务的协议带它的契约修订号 `revision` 与契约摘要 `digest`（摘要就是那份协议的快照里对应修订号记着的那一个；手写编解码的协议没有摘要）；两种帧各带 `conflicts`，列出这次变化之后被两个实例同时放着、因此都不服务的协议。修订号 1 的订阅者收到的帧与以前逐字节相同：写的一方按对方的修订号少写。帧外层的 `revision` 仍是登记表变化的计数，与契约修订号无关。
- 可用性读的是登记表上点 `access.protocols` 的答案：一份协议在服务才算可用。同名的第二份装上时，这份协议从可用的集合里去掉并出现在 `conflicts` 里；撤掉一份，它回到可用的集合。
- 修订号 2 的快照另带 `points`：这棵树上声明的拓展点，每个带名字、主版本、修订号与规矩的摘要；规矩写了「键对外公开」的点另带它现在在服务的键，排好序。点或公开的键变了，服务端在同一个修订号上重发一帧快照，不占登记表变化的计数，不加新的帧种类。修订号 1 的订阅者读不到点，所以点的变化不给它发帧，也不动它排着的变化帧：它收到的帧的序列与以前相同。一个键公开的点读不出时这个点不带键，不写成空；目录读不出时点保持上一次读到的样子。公开的只是键：一项的内容不出这棵树，要内容走那个领域自己的协议。`access.protocols` 自己不写键公开：它的键就是 `protocols` 那一列，已经在帧里了。
- 客户端装配把这些点记在视图里：连接的 `availability.points()` 给出对方声明的点，`availability.keys(点名)` 给出一个公开键的点现在的键，变化随 `availability.subscribe` 到达。对方不说点（修订号 1 的 `access/v1`）时一个点也不知道。

### 协议契约与编解码

- 一份协议契约写明名字、主版本、操作与观察。操作写明身份一栏、读写一栏、消息体上限的名字、消息体的编解码与每个结果的正文编解码；观察另写建立值、帧与它自己的结束原因。
- 契约是封闭的：结果集之外的结果、契约之外的栏、缺少成功、给固定结果写编解码，都编译失败。`defineProtocol` 按身份一栏与读写一栏给每个操作补上管道会替领域答的结果；写操作的类型上就有 `unknown`。
- 规则是编解码与类型的唯一来源。读取是严格的，不给出部分读到的值；读写都不因输入不合规而抛出。数值上限只写名字，数值归部署配置。规则的叶子里有一个字节叶子：本地是字节，线上是 base64 文本，只认一份字节唯一的那一种规范写法（带补齐、末位不带多余的位、不夹空白、不是 URL 的字母表）；编与解用平台自带的 base64，平台没有时用自己的写法，两条路认的与写出的逐字相同。大小仍由操作的消息体上限管；一段内容大于上限时由协议分几次送，不由入口放宽上限。
- 协议契约是纯数据与纯函数，不含 Cordis、存储或服务端的类型；两端用同一份契约。
- 同一个主版本里，契约只做可加的改动，每次改动数一个修订号。修订号不手写：规则数据上后加的东西写明它从哪个修订号开始有（`since`），能写的地方是对象的字段、操作、观察；没写的从 1 就有。一份协议的修订号是它里面最大的 `since`，由 `revisionOf(协议)` 算出。后加的字段必须可选：早一个修订号的写方写不出它。`since` 不是正整数、或必填字段的 `since` 大于 1，`ruleCodec` 与 `defineProtocol` 当场抛出。取值集合、结果、结束原因与联合的选项不能在同一个主版本里后加：读方对它们是封闭的。
- 编解码的读与写各多一个可选的修订号。按修订号 r 写：`since` 大于 r 的字段不写出去，但它的值仍照规则核，不合规的照旧拒绝。按 r 读：`since` 大于 r 的字段算不认识的字段，照严格读取拒绝。不给修订号时读写整份规则。`projectRule(规则, r)` 给出规则在修订号 r 时的样子；按 r 读写与「用投影后的规则读写」逐字相同，这一条由性质用例守。由 `ruleCodec` 造的编解码带着它的规则数据（只读的 `rule`）。
- 同一个（协议名，主版本，修订号）只有一种内容，由提交在仓库里的快照守。每份协议的每个主版本有一份快照：领域协议在它自己成员的 `contract/v<主版本>.json`，`access` 在 `public-contract/contract/access.v1.json`。快照记着现在的规则数据（操作与观察的每一栏，每个编解码的规则，带着 `since`）与每个修订号的摘要：摘要是「契约在那个修订号时的样子」规范化之后的 SHA-256。
- 每个协议成员有一条用例 `tests/contract-snapshot.spec.ts`，用 `@omne-harness/public-contract/snapshot` 的 `checkRecorded` 核：快照里每个修订号，把现在的契约投影到它，摘要要与记着的相等。不等就失败，指出协议、主版本与修订号：已经发布的修订号不能改，要改就加新的 `since`，破坏性的改动换主版本。快照自己记着它记到了第几个修订号：从 1 到那一个，哪一个的摘要不在了也失败，所以删掉一个摘要再改那个修订号的内容过不去。现在的修订号没有记录、或快照里的规则数据不是现在的，也失败，并提示更新。它不读 Git 历史，在任何检出上都能跑。
- 更新只追加：在成员目录下带环境变量 `OMNE_CONTRACT_SNAPSHOT=append` 跑这条用例，它补上新修订号的摘要、换上现在的规则数据；已经记着的摘要一个也不改，有一个对不上或不在了就拒绝更新。新建一份协议时用同一个办法写出第一份快照。
- 这条检查拦得住的：删字段、改字段的种类、必填与可选互换、给取值集合加值、加结果、加结束原因、加不带新 `since` 的字段或操作、把后加的东西改成早就有、删操作、改身份一栏、读写一栏与消息体上限的名字。它不替代类型层的 API 快照：那一份守的是导出的类型，这一份守的是线上的规则数据。
- 契约里没有叫 `observe` 的操作：客户端按操作名给成员，观察都放在 `observe` 之下，同名的操作会被盖住。`defineProtocol` 拒绝这个名字；不经它构造的契约在客户端核心处被拒。
- 联合规则的各选项互不相交：第一个转换成功的选项胜出，本地值不记录命中了哪个选项。

### 客户端

- 协议客户端核心的结果只有契约的结果，加上两种本地结果「不可用」与「不确定」。答复的结果不认识或正文不合契约是「不确定」。服务端答「挂着的协议里没有这个名字」时，传输报成没有发出，核心照没发出的路再问一次，仍然如此就答「不可用」：这次调用确定没有执行，没有可认回的东西。传输负责带上身份，核心看不到登录证明。核心在每次调用与观察的请求里带上自己这份契约的修订号，HTTP 传输把它写成头 `Omne-Contract-Revision`；请求里没有修订号时不写这个头。浏览器里的 `fetch` 给不出「一个字节没发出」的证明，所以在浏览器里失败一律是「不确定」。
- 核心可以被告知对方把这份协议放在第几个修订号（`peerRevision`，每次调用现问）。知道而且对方比自己旧时，一端只向对方发对方认识的：调的操作或观察是对方的修订号之后才有的，或请求里用到了对方的修订号之后才有的字段，核心在本地答「不可用」，不发出去。它不把那个字段去掉再发：那是把一次做不到的请求悄悄做成另一件事。不知道对方的修订号时照旧全发，由对方按严格读取拒绝。服务端答「协议没挂」「协议冲突」时，和「没有这个名字」一样报成没有发出。
- 客户端装配把那条观察里每份协议的契约修订号记在视图里，交给它建的协议客户端；连接的 `availability.peerRevision(协议)` 读得到。对方没说（修订号 1 的 `access/v1`）时是不知道。
- 观察以异步生成器给出帧，结束方式在返回值里：契约里的原因、建立被拒、没发出、不确定、调用方中止。
- 连接一直跟着可用性；观察断了按退避重新订阅，视图不动，协议客户端不收回。协议开放而树上没有它的协议客户端时记一条诊断。
- 协议撤下时，协议客户端先标记已收回再注销服务；之后的调用（含外部留着的旧句柄）在本地答不可用，观察立刻结束；在途调用没发出的答不可用，可能发出的答不确定。换登录或换租户不改变协议客户端。
- 已经建立的观察连接断开后，客户端不自动重连，也不自动发出任何公开操作。
- 客户端装配在客户端的树上声明两个点：
  - `connection.protocols`：每键一项，键是「协议名/v主版本」。一项是这一版的协议客户端与对方的修订号。一项在两个条件都成立时出现：可用性里这份协议开着，而且这个客户端构建时带着这一版的契约。协议撤了，这一项取走。协议开着而对方的修订号变了，这一项换成新的：客户端仍是同一个，记着的修订号是新的。在服务端冲突的协议没有项。同键而摘要不同的几项答冲突。
  - `connection.server-points`：一项，是一个读法：服务端各个点上公开的键（`keys(点名)`），与它们的变化（`subscribe`）。
- 一份协议此刻的状态是五种之一，`availability.standing(协议)` 给出：还没有可用性；开着；同名的别的主版本开着（带出是哪几个）；没有；冲突。
- 需要一份协议的一方把需要写成对 `connection.protocols` 的引用：要哪份协议，认哪几个主版本（想要的在前），是不是可选。点名的主版本没有就是没有，不拿别的主版本顶替。界面模块的声明与采用见[前端规格的「界面模块」](../frontend/SPEC.md#界面模块)。
- 一直在的协议客户端（`connection.client(协议)`，与界面模块拿到的那一个）：它不随协议来去。每次调用按此刻的登记表找这份协议的那一项，恰好一项才转过去；没有、冲突或还没有可用性时，调用当场答不可用，观察以不可用结束，传输一次都不被调。
- 命令行不带这棵树。它的一次调用答不可用之后，读一次可用性的第一帧就停，照同一张状态表在标准错误上写出原因（见[命令行的规格](../../apps/cli/SPEC.md)）。

### 租户范围的协议

一个租户可以有它自己的协议：它持有的 plugin 在服务端放到 `access.protocols` 上、作用域是这个租户的那几份。整个部署的协议经可用性的观察告诉每个客户端；租户的协议只告诉为这个租户行事的调用者。

- **契约数据。** 这样一份协议的契约写成数据，形状归 `public-contract`：`{ name, major, operations }`，每个操作写 `effect`（`read` 或 `commit`）、`limit`（`small` 或 `input`）、`body` 与 `result` 两条规则。`guestContract(数据)` 把它做成一份协议契约：每个操作的身份都是行事租户，结果只有成功与管道替领域答的那几种，没有观察。数据不合格时它答第一处原因，不抛出。两端用这同一个函数，所以一份契约只写一次。
- **专门的写法。** `access.protocols` 收 plugin 代码的写法归本组（`server-entry` 的 `guestProtocol`；`guestItem` 把它做成点上的一项，一项留着契约数据），由应用放到点 `plugin.guest-forms` 上（规矩见 [plugin 的规格](../plugin/SPEC.md#一个成员怎样判)）。plugin 交 `{ contract, handlers }`：`contract` 是上面的契约数据，键要等于「名字/v主版本」，每个操作恰有一个处理函数。处理函数拿到输入与这次调用的口，见不到主体；它答的不在结果里时，读答 `basis-unavailable`，提交答 `unknown`，抛出也是。入口把契约数据原样留在条目上。
- 这样的条目不带锁，作用域是持有它的租户。整个部署的协议带锁，所以租户放不出同键的一份。
- **不收观察。** 一条观察占每登录的名额与帧的预算，这两样的上限还没有为租户的代码定；要变化的页面用读操作轮询。
- **读。** `access/v1` 在契约修订号 3 加一个读操作 `scoped`：要行事租户，正文是空的，成功时答 `{ protocols }`，每份带名字、主版本与契约数据。它只列作用域比整个部署深、发问的租户看得见、此刻在服务的条目。登记表读不出时答 `basis-unavailable`，不答空表。
- **变了怎样知道。** 修订号 3 的可用性快照与变化帧多一个可选的数 `scoped`：更深作用域的协议条目每变一次加一。它对所有调用者相同：只说有租户的协议变过，不说是谁的、是什么。修订号 2 及以前的订阅者收到的帧与以前逐字节相同。
- **客户端跟着长。** 连接登录着并有行事租户时读一次 `scoped`；可用性里的 `scoped` 变了再读；读到的每一份用 `guestContract` 做成契约、建一个协议客户端，放成 `connection.protocols` 上这个租户范围的一项；表里没有了的取走。换了租户或退出，上一个租户的全部取走。读不出时已经放着的不动，隔一会儿再读，连着读不出时隔得越来越久。读的中途又变了，读完再读一次。
- 读 `connection.protocols` 的一方按当前租户的作用域问，所以官方的协议与这个租户的协议都看得见，别的租户的看不见。
- 需要这样一份协议的一方（一份 plugin 在客户端的代码）拿到的是一直在的协议客户端：这份协议此刻不在时，调用当场答不可用。
- 命令行不带这棵树。它有一条通用的调用：点名协议、操作与一份 JSON 正文，先读 `scoped` 取契约，再发这一次（见[命令行的规格](../../apps/cli/SPEC.md)）。
- 转发层给一次调用带什么凭据，照这同一份答复，规则归[桌面应用的规格](../../apps/desktop/SPEC.md#转发规则)。

### HTTP 承载

- 承载是本机回环上的 HTTP/1.1：监听地址只能是 `127.0.0.1`，配置给出其他地址时启动失败，不静默改写。`Host` 只接受 `127.0.0.1` 或 `localhost`，挡住借用本机服务的重绑定页面。不发 CORS 头，不跟随重定向。
- 在读消息体之前按路径选择消息体上限，按实际读到的字节计数，不信任 `Content-Length`；超限停止读取并关闭连接。路径、方法、头的失败在读消息之前给出，不调用任何领域。
- 在途请求有一个与管道共用的预算，在读消息体之前预留，用尽时答空正文的 429 并关闭连接；断连不撤销已受理的业务调用。
- 依赖抛出或不可达时，对外结果按调用的种类：读取类依赖答 `basis-unavailable`；提交类调用开始之后答 `unknown`；结果集里没有线上 `unknown` 的提交类操作写出空正文的 500 并关闭连接，表示没有可信答复。接入不把这些情况写成 `denied`、`succeeded` 或 `basis-unavailable`。

## 原则与约束

- 「现在读不到」是会变的状态，不是结局。对它的再问只在协议客户端这一层做，各个界面模块不各写一遍。
- 结果不知道就是不知道。写类操作的未知效果不能靠再发一次去重做。
- 协议客户端核心要能在浏览器里用：它只依赖共同契约与它自己，策略的判定从设置里交进来。
- 客户端一侧的成员只依赖共同契约、协议客户端核心与 Cordis。
- 领域不认识接入层；接入插件调领域的公开入口，不反过来。入口、管道、登记表与观察中枢不导入任何领域。
- 身份每次调用显式带上；入口的身份检查不替代领域的授权判断。
- 策略类的数值（宽限、刷新、名额、帧队列、积压、消息体上限）都是装配给的配置，成员里不写初值。
- 自定义的登记、撤下与可用性协议有形式模型（`server-entry/verification/models/`）；有限检查的通过不等于实现符合，实现由对应的契约测试核对。
