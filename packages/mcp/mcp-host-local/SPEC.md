# @omne-harness/mcp-host-local 行为规格

状态：候选规格，尚未取得技术接受。本包是 `@omne-harness/mcp-contract` 的 `McpTransportFactory` 与 `McpTransport` 的实现方：stdio 与 Streamable HTTP 两种真实传输，含旧 HTTP+SSE 的回退，以及授权发现的取回。行为条款归契约成员的 [SPEC](../mcp-contract/SPEC.md) T1–T9 与 R4；本页只写本包兑现哪些条款、契约没有定而由本包决定的事项、与官方 SDK 的复用关系，以及验证。本页不复制条款正文。公开形状归 `src/` 的公开定义，导航在 [docs/public-api.md](docs/public-api.md)。

<a id="decisions"></a>

### 本页的决定

契约没有写、由本包按设计与裁定定下的事项。每条只指向本页的条款；条款是唯一的规则。

1. 协议会话与线路分开：会话兑现 T1–T9 的全部结论，线路只搬字节、不分类。见 H1、H2。
2. `open` 不发请求、不调用凭据句柄；答复之前再核一次 `signal`。见 H3。
3. 读类请求在流断开后再发一次，写类与调用不再发；旧 HTTP+SSE 模式下都不再发。见 H5。
4. stdio 线路读出并丢弃标准错误；`close()` 不停止进程。见 H6。
5. 旧 Streamable HTTP 会话在 `close()` 时不发 `DELETE`。见 H7 与[与协议的偏离](#protocol-deviations)。
6. 一行与一个 HTTP 正文的字节上界都是 16 MiB；越界是流断开。见 H8。
7. 旧 HTTP+SSE 是 HTTP 线路内的一种模式，只在 `initialize` 被答「4xx+纯」后试一次。见 H9。
8. HTTP 线路不设自己的超时；请求离开之前的失败只有连接未建立的那几种。见 H10、H11。
9. `stdio-ended` 事件的组成按 `PROCESS_EXIT_WINDOW_MS` 的窗口。见 H12。
10. 凭据的值只进出站请求的头。见 H13。

## 结果与不变量

每条写本包怎样兑现、一个反例，以及让守住它的用例变红的变异。锚点给验证引用。

<a id="h1"></a>

- **H1 一张表一份实现**（契约 T1、T2、T8）：`Session`（`src/session.ts`）把线路报告的每一次交换与事件翻成契约的 `WireEvent`，交给契约根导出的 `classifyWireEvent` 归类，再按 T8 的行得出结论。请求的组成（`_meta`、MCP 头、`Mcp-Name` 编码）、页的剔除、授权发现的组装、各结果与错误对象的读法都调用契约根导出的函数，本包不另写一份。反例：线路自己判断一行是不是 JSON；会话用自己的正则读 `-32022` 的 `data.supported`。变异：`conclude` 不再把 `http:2xx` 当流断开 → `session.spec.ts` D15、I06、O05、O06 行变红；`answerWireOf` 对探测的「5xx+码」不答 `server-error` → D16 行变红。

<a id="h2"></a>

- **H2 线路不分类**（契约 T2）：`Line`（`src/line.ts`）只报告 `unsent`、`sent`、`status`（状态、头、整个正文）、`stream`（头、逐条消息、`abort`）、`aborted`，以及共用流的 `line`、`ended`、`broken` 事件。线路不看消息的内容，不看状态码的含义，不核 `id`。反例：HTTP 线路把 404 读成「会话结束」；stdio 线路丢掉一行「不是 JSON」的文本。变异：HTTP 线路丢掉 POST 错误状态的正文（`status` 交换的 `body` 为空） → `conformance.spec.ts` 两遍各 11 个用例变红（D04–D08、D12、I03、O01–O03、C02 等按正文分类的行）。stdio 线路丢掉非 JSON 行是等价变异：契约把这样的行归为 `other`，结局相同。

<a id="h3"></a>

- **H3 `open` 不发请求**（契约 T9）：`createLocalTransportFactory(options).open(material, signal)` 先核 `signal`，建线路（stdio：取 stdin 的 writer、起 stdout 与 stderr 的读取、把已经成立的退出与 stdout 结束落定；HTTP：不做 I/O），再核一次 `signal`：已中止就关闭线路、答 `not-sent`（`connection-unavailable`），不交出传输。`open` 不写任何字节、不调用凭据句柄的任何方法。于是调用方在时限到期后释放句柄时，没有一个它授权过的传输还会调用它。反例：`open` 发 `server/discover` 探测；`open` 先 `authorize` 再交出传输。变异：`factory.open` 去掉第二次 `signal` 核对 → `public-entry.spec.ts`「a signal that fires while a stdio line is being opened」变红。

<a id="h4"></a>

- **H4 凭据只在发请求时用**（契约 T4、T9）：每个出站请求与通知在写出之前经 `credential.authorize(headers)`；句柄 reject、抛出或答失败时请求不发出，答 `not-sent`（`connection-unavailable`）。授权之后、写出之前传输被关闭的请求同样不发出。对端答 401 或带 `insufficient_scope` 的 403 时，只对曾用这个句柄授权的请求调用 `reportRejection()` 恰好一次，然后取回授权发现；其他 403 不调用。旧 HTTP+SSE 回退的 GET 也经句柄授权。授权发现的 well-known 取回不经句柄：元数据是公开的。反例：`reportRejection()` 在每个 401 上都调用，包括没有句柄的材料；元数据取回带着 `Authorization`。变异：带 `insufficient_scope` 的 403 不再按 S05 处理 → `session.spec.ts` S05 行（16 格）变红。`reportRejection()` 只对授权过的请求调用：没有句柄的材料没有可调用的对象，`conformance.spec.ts` T4「401 on a request that no handle authorized」核对不调用。

<a id="h5"></a>

- **H5 不代调用方重发**（契约 T8 D15、O05、C04、O06、O07）：只在 Streamable HTTP 材料、不在旧 HTTP+SSE 模式、请求是 `server/discover`、`tools/list` 或 `tasks/get`、第一次的结论是流断开或「2xx 而没有应答」时，以新的请求号再发一次；再发的结论不再触发再发。`tools/call`、`tasks/update`、`tasks/cancel` 不再发；`5xx+纯` 不再发。反例：`tools/call` 的流断开后静默重试。变异：`request` 对写类请求也再发（`READ_METHODS` 条件改为恒真） → `http.spec.ts`「tools/call, tasks/update and tasks/cancel are not sent again」变红。`tools/call` 不经 `request()`，没有再发的代码路径；同一用例按对端收到的请求数核对它。

<a id="h6"></a>

- **H6 进程归落点**（契约 T5、PL）：`StdioLine` 跑在材料的 `ProcessHandle.stdin`/`stdout` 上，从 `open` 起读出并丢弃 `stderr`（不写日志，让进程不因 stderr 管道满而阻塞）。`close()` 的次序：关 stdin 写端 → 取消 stdout 读取 → 清计时 → 取消 stderr 读取；不调用 `stop()`。会话在 `close()` 时先把在途请求全部答 `no-answer`（`abandoned`）、拒绝新请求，再关线路。反例：`close()` 调 `stop()`；先取消 stdout 再关 stdin。变异：`StdioLine.close` 颠倒两步 → `conformance.spec.ts` T5「stdio: close() closes stdin, then cancels stdout」变红。

<a id="h7"></a>

- **H7 不发 DELETE**：旧 Streamable HTTP 会话在 `close()` 时不向对端发 `DELETE`。契约 T5 只说关闭传输；`DELETE` 是对端效果，契约没有写它，套件也不核它；对端在空闲后自己回收会话。反例：`close()` 发 `DELETE`。变异：无用例变红（契约不核）；本条是与协议 SHOULD 的偏离，见[与协议的偏离](#protocol-deviations)。

<a id="h8"></a>

- **H8 字节上界**（契约 T2）：`src/limits.ts` 的 `BYTE_LIMIT` 是 16 MiB，与契约 `classifyWireEvent` 的 JSON 上界同值。stdio 上一行超过它（含跨块到达的行，换行到达时对该行精确量字节）是流断开：线路取消 stdout、立即宣告 `ended`，不等退出窗口；之后的请求答 `not-sent`。HTTP 上一个正文超过它是该请求的流断开。反例：按块累计、换行所在的块不核，16 777 217 字节的行按 64 KiB 分块恰好漏过（第一次实现的缺陷）。变异：`readStdout` 去掉换行到达时的精确量 → `stdio.spec.ts`「a line above the 16 MiB byte bound」变红。

<a id="h9"></a>

- **H9 旧 HTTP+SSE 模式**（契约 T3、T8 I07、S07）：只在旧一路的 `initialize` POST 被答「4xx+纯」时，HTTP 线路 GET 连接目标（`Accept: text/event-stream`、`MCP-Protocol-Version` 等于提出的旧版本、经句柄授权的头；没有 `Mcp-Method`、`Mcp-Name`、`Mcp-Session-Id`）。200、`text/event-stream`、第一个事件是 `endpoint` 且 `data` 相对目标解析后同源，三者都成立才进入模式：之后每个请求与通知 POST 到 endpoint，不带 `Mcp-Session-Id`；POST 的 2xx 没有应答按 `waiting`（`WireContext.mode = 'sse'`）；应答与对端的消息经共用的流到达；流结束或断开是每个在途请求的流断开，不再发，传输不再可用；`initialize` 之后请求的 404 按 S07 `session-ended`，endpoint 上的 `initialize` 自己不带会话。GET 的 401 与带 `insufficient_scope` 的 403 按 S05（`reportRejection()` 一次），其他 403 按 S06；其余不成立的情形答 I07 的 `not-sent`（`connection-unavailable`）。`initialize` 的 401、403、5xx、「4xx+码」与离开前的失败都不触发回退。`cancelRequest` 在这个模式下发 `notifications/cancelled`。反例：回退后对流断开的 `tools/list` 再发一次；跨源的 endpoint 被接受。变异：`endpointOf` 去掉同源核对 → `http.spec.ts`「a cross-origin endpoint」变红；`request` 在 SSE 模式下仍再发 → 「the stream breaking … re-sends nothing」变红。

<a id="h10"></a>

- **H10 请求离开之前的失败**（契约 T8 X01）：`fetch` 在应答头之前 reject 时，`cause.code` 在 `ECONNREFUSED`、`ENOTFOUND`、`EAI_AGAIN`、`EHOSTUNREACH`、`ENETUNREACH`、`EADDRNOTAVAIL`、`UND_ERR_CONNECT_TIMEOUT` 与 TLS 握手码（`ERR_TLS_CERT_ALTNAME_INVALID`、`DEPTH_ZERO_SELF_SIGNED_CERT`、`SELF_SIGNED_CERT_IN_CHAIN`、`UNABLE_TO_VERIFY_LEAF_SIGNATURE`、`CERT_HAS_EXPIRED`、`ERR_SSL_*`）里是 `unsent`（X01）；其余（`UND_ERR_SOCKET`、`ECONNRESET`、undici 自带的头与体超时等）是流断开：请求已离开。stdio 上写请求时进程已退出、上一次写失败或线路已关闭是 `unsent`（X02）。反例：头前重置被当作没有离开。变异：`UNSENT_CODES` 加入 `UND_ERR_SOCKET` → `http.spec.ts`「a reset before the answer head is stream-broken」变红。

<a id="h11"></a>

- **H11 没有自己的超时**：HTTP 线路对 `fetch` 不设超时；等待应答由调用方的 `signal`、`cancelRequest` 与 `close()` 结束（T8 D14、I05、O04、C03「等到 `close()`」）。stdio 上只有探测时限（`probeTimeoutMs`），只在等待 `server/discover` 的应答时计时；到时后迟到的应答按无关的行丢弃。反例：会话 60 s 后自己发取消并报超时。变异：`PROBES` 加入 `tools/list`（它也起探测计时并按探测归类） → `session.spec.ts` O01、O03、O08 行变红。

<a id="h12"></a>

- **H12 退出窗口**（契约 T8 进程退出）：stdout 先结束时线路最多等 `PROCESS_EXIT_WINDOW_MS` 的退出再宣告 `ended`，之后的退出不改变已归类的结论；进程先退出时线路最多再读 `PROCESS_EXIT_WINDOW_MS` 的 stdout（期内读到的行照常投递），然后宣告并取消读取。两个时刻取同一时钟。退出的观察直接挂在句柄的 `exited` 上，先于任何在它之后 `await` 这个 promise 的调用方。反例：观察挂在派生 promise 的第二跳上，先等过 `exited` 的调用方还能写出一个请求（第一次实现的缺陷）。变异：`onExited` 直接挂在派生 promise 的第二跳上 → `stdio.spec.ts`「a process that answers and exits」变红（施工时的真实缺陷）。进程先退出后继续读窗口内 stdout 这一半没有能让它变红的用例：Linux 上子进程对管道的写是同步的，应答总在退出之前被读到；它按契约 T8 的窗口实现，列为未覆盖。

<a id="h13"></a>

- **H13 凭据不外泄**：凭据句柄写进的头只进出站请求（`fetch` 的 `headers`）与回退的 GET；`Exchange`、`WireEvent`、答复、失败、授权发现与本包抛出的错误都不含请求头。本包不写日志。反例：`not-sent` 的失败带着请求头。变异：无单独变异；`http.spec.ts`「the credential value appears in no answer, failure or discovery」对所有结局的 JSON 断言不含令牌。

| 协议要求                                                                           | 本包的做法                                                        | 理由                                                                                            |
| ---------------------------------------------------------------------------------- | ----------------------------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| 客户端不再需要旧修订的会话时 SHOULD 发 `DELETE`（2025-03-26 起的 Streamable HTTP） | `close()` 不发 `DELETE`（H7）                                     | 契约 T5 只说关闭传输；`DELETE` 是对端效果，契约没有写它，套件也不核它；对端在空闲后自己回收会话 |
| Streamable HTTP 应答流断开时用新的请求号重发（2026-07-28 changelog 第 9 项）       | 只对读类请求重发一次（H5）                                        | 契约[与协议的偏离](../mcp-contract/SPEC.md#protocol-deviations)                                 |

## 所有权、失败与生命周期

- **身份与状态。** 一个 `Session` 是一个 `McpTransport`，带材料的代际。它拥有：在途请求表（请求号、上下文、每请求的 `AbortController`、授权标记、应答流的 `abort`）、协商出的版本与是否旧一路、旧 Streamable HTTP 的会话号、是否在旧 HTTP+SSE 模式、`closed` 与 `dead`（流断开、进程退出、会话结束，不再可用）。线路拥有：stdio 的 writer、stdout/stderr 的 reader、两个时刻与退出窗口的计时；HTTP 的在途 `AbortController` 集合与 endpoint。
- **一个请求只结算一次。** 先到者定（T5）：应答、流断开、进程退出、探测时限、`cancelRequest`、`signal`、`close()` 中最先发生的那个给出结论，之后的事件对已结算的请求没有作用。`close()` 先把在途请求全部答 `abandoned`，再关线路；线路关闭引起的 `aborted` 交换因此不会被读成流断开。
- **取消。** stdio 与旧修订（含旧 HTTP+SSE 模式）发 `notifications/cancelled`，`answer` 继续等；现代 Streamable HTTP 中止该请求的 `fetch` 与应答流并答 `abandoned`。`call` 的 `signal` 在调用前已触发答 `not-sent`；发出后触发答 `abandoned`，在线路写出期间触发时等写出返回后结算（不宣称没有对端效果）。
- **对端的请求与通知。** 任何线路上带 `method` 与 `id` 的消息：`ping` 答空结果，其余答 `-32601`，答复经线路写出（HTTP 上是一次 POST，它的状态没有结局）。`notifications/progress` 的 `progressToken` 对上在途调用时交给它的 `observe`（抛出不改变结局）；其他通知丢弃。
- **资源释放。** `close()`：会话结算在途请求、中止一切 `fetch` 与回退的 GET 流、关线路；stdio 线路按 H6 的次序关闭；探测与退出窗口的计时在结算或关闭时清除。应答流在答复到达后继续在后台读到结束，释放连接；无人等待的交换（通知、答复的 POST）同样在后台读完。`close()` 可以重复调用。没有 disposer 让外部效果可撤回：已经写出的请求与通知就是写出了。
- **失败的处置。** 线路 reject 是线路的缺陷，会话把它当作 `aborted`（HTTP）或忽略（写出通知）；凭据句柄 reject 或抛出按 T9；`observe` 抛出按 S6。本包不吞错误成成功：读不懂的应答按 T7 的 `what` 报出，没有应答按 `no-answer` 的原因报出。
- **并发。** 一条线路上多个请求可以同时在途：stdio 上按行投递，每行与每个在途请求的上下文归类一次；HTTP 上每个请求各自的 `fetch`。旧 HTTP+SSE 模式下共用一条流。会话不排队、不限流。
