### 本包自定

契约没有写、由本包定下的事项。每条在指向的位置写明。

1. 会话与线路分开。线路只报告线上发生的事实，会话用契约的函数归类并得出结论。旧 HTTP+SSE 回退的 GET 也如此：线路交出 `GetOpened`，会话判定回退是否成立。见 H1、H2、H9。
2. 会话对外的效果只经五个注入点：线路、材料里的凭据句柄、`SessionOptions.fetchMetadata`、计时端口 `SessionOptions.schedule` 与缺陷出口 `SessionOptions.reportDefect`。见 H14。
3. stdio 线路读出并丢弃标准错误。见 H6。
4. HTTP 线路自写，直接用 `fetch`，不用 SDK 的传输类。契约要求的不跟随重定向与不设超时由它兑现，见 H10、H11 与[复用表](#sdk-reuse)。
5. 请求离开之前的失败按 `fetch` 失败的 `cause.code` 集合判定。见 H10。
6. HTTP 正文也按契约 T2 的 16 MiB 上界读：只有 2xx 正文越界是流断开，错误状态的正文越界读成空正文。见 H8。
7. 应答到达之后，应答流在后台读到结束。没有人等待的交换（通知、答复对端请求的 POST）同样在后台读完。见[所有权一节](#所有权失败与生命周期)的「资源释放」。
8. 凭据的值只进出站请求的头。见 H13。
9. 会话的调用方只等在途项的结算，不等工作流：授权、组成与写出、拒绝报告与元数据取回、答复对端、通知都是会话拥有的后台工作。`close()` 另外只等线路的 `close()`。`discover` 有两处例外：它在关闭之下等待回退 GET 的授权与 GET 本身，以及 `notifications/initialized` 的写出；这两处交换没有在途项，关闭时收场。见[所有权一节](#所有权失败与生命周期)。

## 结果与不变量

每条写本包怎样兑现、一个反例，以及让守住它的用例变红的变异。锚点给验证引用。

<a id="h1"></a>

- **H1 一份规则一份实现**（契约 T1、T2、T7、T8）：`Session`（`src/session.ts`）把线路报告的每一次交换与事件翻成契约的 `WireEvent`，交给 `classifyWireEvent` 归类，再交给契约的决策层：`concludeAnswer` 给出 T8 行的结论，`discoverWith` 走探测与旧一路，`listingPageOf`、`taskReportOf`、`taskAnswerOf`、`callAnswerOf`、`interpretAnswer` 读出各请求的结果，`discoverAuthorization` 取回授权发现，`requestTextOf`、`notificationTextOf`、`responseTextOf` 写出消息的文本。会话自己不读 `-32022` 的 `data.supported`，不判断修订，不把错误类压平后再判断。反例：会话自己判断 `data.supported` 里的一项是不是现代版本，于是一个不是日期的版本被当作现代版本接受。变异：会话把 `-32022` 的错误类自判为 `+legacy` → `session.spec.ts`「a -32022 whose supported list names a modern-looking text that is no date」变红。

<a id="h2"></a>

- **H2 线路不分类**（契约 T2）：`Line`（`src/line.ts`）只报告事实。`send` 答 `unsent`、`sent`、`status`（状态、头、整个正文）、`stream`（头、逐条消息、`abort`）或 `aborted`。共用的流报告 `line`、`ended`、`broken` 事件。`openGet` 答 `GetOpened`：2xx 的状态、头与第一个事件，或非 2xx 的状态、头与正文，或 `unsent`、`unavailable`。线路不看消息的内容，不看状态码的含义，不核 `id`，不判断回退是否成立。反例：HTTP 线路把 404 读成「会话结束」；HTTP 线路自己判断 `endpoint` 是否同源。变异：HTTP 线路丢掉 POST 错误状态的正文（`status` 交换的 `body` 为空）→ `conformance.spec.ts` 里按正文分类的 T8 行（D04–D08、D12、I03、O01–O03、C02 等）变红。stdio 线路丢掉解析不了的行是等价变异：契约把这样的行归为 `other`，结局相同。

<a id="h3"></a>

- **H3 `open` 不发请求**（契约 T9）：`createLocalTransportFactory(options).open(material, signal)` 先核 `signal`，再建线路。stdio：取 stdin 的 writer，起 stdout 与 stderr 的读取，把已经成立的退出与 stdout 结束落定。HTTP：不做 I/O。然后再核一次 `signal`：已中止就关闭线路，答 `not-sent`（`connection-unavailable`），不交出传输。`open` 不写任何字节，不调用凭据句柄的任何方法。反例：`open` 发 `server/discover` 探测；`open` 先 `authorize` 再交出传输。变异：`factory.open` 去掉第二次 `signal` 核对 → `public-entry.spec.ts`「a signal that fires while a stdio line is being opened」变红。

<a id="h4"></a>

- **H4 凭据只在发请求与处理应答时用**（契约 T4、T9）：每个出站 HTTP 请求在写出之前经 `credential.authorize(headers)`：请求、通知、答复对端请求的 POST 与旧 HTTP+SSE 回退的 GET。句柄 reject、抛出或答失败时，这个请求不发出，答 `not-sent`（`connection-unavailable`）。句柄的每次调用经会话的一处入口，它在调用之前同步核传输是否已关闭：已关闭就不调用，请求不发出；每个等待点返回之后，工作流再核这个请求是否已结算、传输是否可用。对端答 401 或带 `insufficient_scope` 的 403 时，只对曾用这个句柄授权的请求调用 `reportRejection()` 恰好一次，并取回授权发现；两者是请求的后台工作，`close()` 与 `signal` 不等它们（见所有权一节）。其他 403 不调用。授权元数据的取回不经句柄、不带凭据写入的头（契约 T9）。反例：回退的 GET 先到 401 头、正文未到时 `close()`，`close()` 返回之后仍调用 `reportRejection()`。变异：`enterSse` 去掉 `openGet` 返回之后的关闭核对 → `http.spec.ts`「the fallback GET answered 401 with its body still to come when close() runs」变红。

<a id="h5"></a>

- **H5 不代调用方重发**（契约 T8 D15、O05、C04、O06、O07）：`request()` 在第一次的结论带「再发」标记时，以新的请求号再发一次，再发的结论不再触发再发。标记由契约的 `concludeAnswer` 按 `RESENT_REQUESTS` 给出：只在 Streamable HTTP、不在 SSE 模式、请求是 `server/discover`、`tools/list` 或 `tasks/get`、结论是流断开或「2xx 而没有应答」时成立。再发经过完整的发送：重新登记、重新授权。`tools/call` 不经 `request()`，没有再发的代码路径。反例：`tools/call` 的流断开后静默重试。变异：`request()` 对任何 `no-answer` 都再发 → `http.spec.ts`「tools/call, tasks/update and tasks/cancel are not sent again」变红（它按对端收到的请求数核对）。

<a id="h6"></a>

- **H6 进程归落点与 stdin 写端**（契约 T5、PL）：`StdioLine`（`src/stdio-line.ts`）跑在材料的 `ProcessHandle.stdin`/`stdout` 上。它从 `open` 起读出并丢弃 `stderr`，不写日志，让进程不因 stderr 管道满而阻塞。`close()` 的次序：中止 stdin 写端（对端看到输入结束），再取消 stdout 读取，再取消 stderr 读取，然后等两个读循环结束；它不调用 `stop()`。关闭是放弃：会话在关闭线路之前已按相结算全部在途请求（见所有权一节），之后没有任何字节需要送达，所以线路的关闭没有优雅一支，从不等缓冲排空：web 写的完成只表示下层收下了字节，不表示对端读了，等排空就是等对端。`close()` 不等缓冲排空，但已交给 Node 的字节仍可能送达对端：有在途写时，写端的中止要等这次写结束才生效，所以对端在在途写结束之后才见到输入结束。线路的 `close()` 只依赖本地资源（写端、两个 reader、两个读循环），这是线路对会话的义务（线路端口 `Line.close` 的文档写明），也是 V4 中 `close()` 返回那一句的前提。第二次调用 `close()` 得到同一次关闭，在读循环结束之后才完成。仍在等满管道的 `send` 答 `aborted`。一次写在完成前被它的 `signal` 中止时，线路中止写端，不再可写，并报告 `broken`：在途的已发出请求答 `no-answer`（`stream-broken`），传输不再可用。反例：`close()` 调 `stop()`；`close()` 等一个不读 stdin 的对端（无在途写就关闭写端：已出发的小写还在 Node 的缓冲里，关闭写端要等它冲进没人读的管道）。变异：`StdioLine.close` 颠倒前两步 → `conformance.spec.ts` T5「stdio: close() closes stdin, then cancels stdout」变红（「closes」指结束写端，中止也算）；关闭时改回关闭写端（`tests/model/mutants.ts` 的 `mStdio-close-flushes`）→ `stdio.spec.ts`「small calls that departed sit in the buffer to a peer that does not read stdin」变红。不读 stdin 的对端另由 `stdio.spec.ts`「the pipe is full」核对（一个未完成的大写被 `signal` 中止）；两个重叠写后 `close()` 当即返回由 `lines.spec.ts`「two overlapping writes, the first completes, then close()」核对；第二次 `close()` 不早于第一次完成由 `lines.spec.ts`「a second close() is the first one」核对。

<a id="h7"></a>

- **H7 不发 DELETE**：契约 [T5](../mcp-contract/SPEC.md#port-transport) 不要求 `close()` 发 DELETE；本包不发。套件不核它，本包没有用例。这是对协议 SHOULD 的偏离，登记在[与协议的偏离](#protocol-deviations)。

<a id="h8"></a>

- **H8 字节上界**（契约 T2）：`src/limits.ts` 的 `BYTE_LIMIT` 取契约根导出 `WIRE_LIMITS.maxBytes`（16 MiB）；元数据文档也按 `WIRE_LIMITS` 解析。
  - stdio：每一行按字节量，不论它从块里的哪个位置开始，也不论它跨几个块。一行超过上界是流断开：线路取消 stdout，立即报告 `ended`，不等退出窗口。已交给线路的在途请求答 `no-answer`（`stream-broken`），其他在途请求按相结算（`lineGoneAnswerOf`，见所有权一节「线路断开」），之后的请求答 `not-sent`。
  - HTTP：只有 2xx 正文越界是流断开：JSON 正文或一个 SSE 事件超过上界，是这个请求的流断开。错误状态的正文超过上界时，线路交出空正文，契约把它归为「纯」，状态照常归类。
  - 授权元数据与旧 HTTP+SSE 回退的非 2xx 正文用同一个有界读法（`src/body.ts`）。元数据超过上界按没取到算。

  反例：只量块里第一行的字节，块里后面的长行漏过；一行跨块、还没有换行就超过上界时读缓冲无界增长。变异：`readStdout` 只量块里的第一行 → `lines.spec.ts`「a line above 16 MiB that is not the first of its chunk」变红；去掉未换行部分的上界核对（`mStdio-no-cross-chunk-bound`）→ `lines.spec.ts`「a line that spans many chunks and passes the byte bound before any newline」变红。EOF 处没有换行的尾行照样投递（`mStdio-drops-tail`）、写被拒绝答 `unsent`（`mStdio-failed-write-sent`）各有一条用例与负控，见 `tests/model/mutants.ts`。

<a id="h9"></a>

- **H9 旧 HTTP+SSE 模式**（契约 T3、T8 I07、S07 与 SSE 模式）：旧一路的 `initialize` 答 I07 的「4xx+纯」时，`legacyPath` 调用 `enterSse` 试回退。`enterSse` 在会话关闭之下等待：先经句柄授权 GET 的头（H4），写入 `MCP-Protocol-Version`（等于提出的旧版本），再调用线路的 `openGet`。线路交出 `GetOpened` 的事实（H2）。会话的 `heldEndpoint` 按 T3 的判据判定回退是否成立：成立时调用 `enter(endpoint)`，并把连接模式改为 `legacy-sse`；不成立时调用 `discard()`。GET 的非 2xx 状态经 `refusedGet` 按 `initialize` 归类：S05 走授权发现（H4），其余答 I07 的 `not-sent`（`connection-unavailable`）。SSE 模式下，请求与通知 POST 到 endpoint，`WireContext.mode` 是 `sse`，归类与结论按 T8；共用流结束或断开时，会话按[所有权一节](#所有权失败与生命周期)的「线路断开」结算在途请求。其余 `initialize` 失败不触发回退（T3）。反例：跨源的 endpoint 被接受。变异：`heldEndpoint` 去掉同源核对 → `http.spec.ts`「the fallback that does not hold reports connection-unavailable: no stream, a cross-origin endpoint」变红。

<a id="h10"></a>

- **H10 请求离开之前的失败**（契约 T8 X01、X02）：`fetch` 在应答头之前 reject 时，`cause.code` 在下面的集合里是 `unsent`（X01）：`ECONNREFUSED`、`ENOTFOUND`、`EAI_AGAIN`、`EHOSTUNREACH`、`ENETUNREACH`、`EADDRNOTAVAIL`、`UND_ERR_CONNECT_TIMEOUT`，以及 TLS 握手码（`ERR_TLS_CERT_ALTNAME_INVALID`、`DEPTH_ZERO_SELF_SIGNED_CERT`、`SELF_SIGNED_CERT_IN_CHAIN`、`UNABLE_TO_VERIFY_LEAF_SIGNATURE`、`CERT_HAS_EXPIRED`、`ERR_SSL_*`）。其余失败是流断开，因为请求已离开：`UND_ERR_SOCKET`、`ECONNRESET`，以及 `fetch` 自带的头超时与体超时（`UND_ERR_HEADERS_TIMEOUT`、`UND_ERR_BODY_TIMEOUT`）。集合的依据是探针 `p3`（[verification/proofs/sdk](verification/proofs/sdk/README.md)）。stdio 上，写请求时进程已退出、上一次写失败或线路已关闭是 `unsent`（X02）。反例：头前重置被当作没有离开。变异：`UNSENT_CODES` 加入 `UND_ERR_SOCKET` → `http.spec.ts`「a connection refused is not-sent; a reset before the answer head is stream-broken」变红。

<a id="h11"></a>

- **H11 没有自己的超时**（契约 T8 D14、I05、O04、C03）：HTTP 线路对 `fetch` 不设超时。等待应答只由调用方的 `signal`、`cancelRequest` 与 `close()` 结束。`fetch` 自带的头超时与体超时按 H10 是流断开。授权元数据的取回受三样约束：请求的 `signal`、传输的关闭（两者合成一个 `AbortSignal` 交给 `fetchMetadata`），以及正文的字节上界（H8）。stdio 上只有探测时限（`probeTimeoutMs`）：`server/discover` 写出之后，会话经 `SessionOptions.schedule` 起计时；应答先到时计时取消；时限到了按 D13 走旧一路；迟到的应答因为请求已不在途而丢弃。反例：会话 60 s 后自己发取消并报超时。变异：`dispatch` 不起探测计时 → `session.spec.ts`「falls back to initialize when the probe time runs out, and drops the late discover answer」变红。

<a id="h12"></a>

- **H12 退出窗口**（契约 T8 进程退出）：`StdioLine` 按 `PROCESS_EXIT_WINDOW_MS` 兑现契约的窗口：两个时刻（stdout 结束、进程退出）取同一时钟；进程先退出时，窗口内读到的 stdout 行照常投递，然后线路报告并取消读取。退出的观察直接挂在句柄的 `exited` 上，先于任何在它之后 `await` 这个 promise 的调用方。反例：观察挂在派生 promise 的第二跳上，先等过 `exited` 的调用方还能写出一个请求。变异：`onExited` 挂在派生 promise 的第二跳上 → `stdio.spec.ts`「a process that answers and exits」变红。变异（进程先退出的一半）：`onExited` 不等窗口，立即报告并取消读取 → `lines.spec.ts`「delivers the line that stdout still carries within the window, then reports the end with the exit alone」变红。

<a id="h13"></a>

- **H13 凭据不外泄**：凭据句柄写进的头只进出站请求（`fetch` 的 `headers`）：POST 与回退的 GET。`Exchange`、`GetOpened`、`WireEvent`、答复、失败、授权发现与本包抛出的错误都不含请求头。本包不写日志。反例：`not-sent` 的失败带着请求头。变异：会话把请求的 `authorization` 头值写进应答头的挑战参数（授权发现的 `scopes` 带着令牌）→ `http.spec.ts`「the credential value appears in no answer, failure or discovery」变红。该用例先断言 `discover` 成功、`authorization-required` 带着发现，再断言所有结局的 JSON 都不含令牌。

<a id="h14"></a>

- **H14 会话只经注入的端口产生效果**：`Session` 对外的效果只经五个入口：线路（`Line`）、材料里的凭据句柄、`SessionOptions.fetchMetadata`、计时端口 `SessionOptions.schedule`（`Scheduler`：起一次计时，返回取消函数）与缺陷出口 `SessionOptions.reportDefect`。会话不读全局时钟，不直接起全局计时器，不直接调用 `setImmediate`。工厂给缺省的 `schedule`，它用 `setTimeout` 与 `clearTimeout`。工厂也给缺省的 `reportDefect`，它在 Promise 之外抛出缺陷，让宿主的未捕获处理看到。线路自己的计时（stdio 的退出窗口）不经这个端口。于是测试可以驱动会话，并排定每一次线路答复、凭据调用与计时触发的次序。反例：会话直接调用 `setTimeout` 起探测计时，测试无法决定它何时触发。变异：会话直接用 `setTimeout` 起探测计时，不经 `schedule` → `session.spec.ts`「starts a probe timer for the probe only, and clears it when the probe is answered」变红（它用记录计时的 `schedule` 替身，核对计时只经它起、经它取消）。

### 与 SDK 的复用关系

协议层优先复用官方 SDK。下表每一处「不复用」标出三类理由之一：

- **硬承诺**：复用会违反三条硬承诺之一。三条是：结局如实分类（T1、T8）；进程归落点（T5、PL）；不代调用方重发（T8 C04、O06、D15、O05 的「不再发」）。

| ----------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- | -------------- |
| T8 X01：请求离开之前失败答 `not-sent`（`connection-unavailable`） | 连接目标的端口是 WHATWG 的「bad ports」（1719、4045、6665–6669、10080 等）时，`fetch` 在连接之前拒绝，`cause` 没有码。本包按 H10 把它归为流断开。受影响的行：X01 读成 D15、O05（读类再发一次后答 `no-answer`（`stream-broken`）），C04（`tools/call` 的 `answer` 是 `no-answer`（`stream-broken`）），I06（`initialize` 答 `no-answer`（`stream-broken`），不再发），O06（`tasks/update`、`tasks/cancel` 答 `no-answer`（`stream-broken`），不再发） | 保守一侧：请求没有离开，本包却答「效果未知」；读类多发一次请求，这一次同样不会离开。没有一个结局把「可能有效果」读成「没有效果」 | 本成员的维护者 |

本包不在发送之前另判端口：那是 `fetch` 的规则，再写一份就是第二份实现。本包的测试夹具只用 20000 以上的端口。

### Cordis 插件

`./cordis` 入口导出插件工厂 `createMcpPlugin(parts)`。插件在一条 fiber 上提供 MCP 的三个服务。键与抽象类归 [mcp-cordis-contract](../mcp-cordis-contract/SPEC.md#结果与不变量)，服务的行为归 [mcp 的 SPEC](../mcp/SPEC.md) 与 [mcp-contract 的 SPEC](../mcp-contract/SPEC.md#services)。本节是插件行为的唯一规范正文：配置、端口的现取与缺席、换代与撤除。[docs/cordis.md](docs/cordis.md) 写装配的用法、Cordis 机制读数与 IC 符合性映射，它引用本节。

- **工厂与配置的切分。** `createMcpPlugin(parts)` 经 `@omne-harness/kernel-basis/cordis` 的 `definePlugin` 返回插件，`name` 是 `mcp`。工厂参数 `McpPluginParts` 是函数与本地对象，不进配置：`principalKey`（取自 `McpConfig`）、`checkOutput` 与可选的 `clock`（取自 `McpPorts`）、可选的 `fetch`（取自 `LocalTransportOptions`）。可选项缺席时取 `createMcp` 与 `createLocalTransportFactory` 的缺省，插件不另设值。配置 `McpPluginConfig` 是可序列化的数据：`McpConfig` 的三个上界 `maxListingPages`、`maxActions`、`instructionsByteLimit`，与 `LocalTransportOptions` 的 `probeTimeoutMs`、`clientInfo`（`name`、`version`）。五个字段都必填，没有缺省值。
- **配置的 Schema 只查形状。** 它按下列次序判定，只答第一项：
  1. 值不是普通对象（原型是 `Object.prototype` 或 `null` 的对象）：`configuration must be an object`。数组、`Date` 与从原型继承字段的对象都不是普通对象。
  2. 有一个自有键不是五个字段之一，符号键也算：`configuration has no field <键>`。
  3. 缺一个自有字段：`configuration needs the field <字段>`。
  4. 四个上界按 `maxListingPages`、`maxActions`、`instructionsByteLimit`、`probeTimeoutMs` 的次序，第一个不是数的：`<字段> must be a number`。
  5. `clientInfo` 不是普通对象：`clientInfo must be an object`。有自有键不是 `name` 或 `version`：`clientInfo has no field <键>`。缺一个：`clientInfo needs the field <字段>`。`name` 不是文本：`clientInfo.name must be a text`。`version` 不是文本：`clientInfo.version must be a text`。

  合形状时 Schema 答 `{ value }`。`value` 与 `value.clientInfo` 都是新对象，之后改动输入不影响插件。不合形状时答 `{ issues: [{ message }] }`，Cordis 4.0.4 以 `ValidationError` 使加载失败，消息是 `invalid config:` 加一行 `  - <message>`。取值范围不在 Schema 里：`createLocalTransportFactory` 的选项检查与 `createMcp` 的配置检查（[S3](../mcp-contract/SPEC.md#services)）在 `apply` 里抛 `RangeError`，加载照样失败。范围规则只有这一处来源。加载失败时插件不提供服务，也不登记撤除函数。

- **`apply`。** 它按次序做五件事：造四个端口适配器；造 `createInMemoryCatalogStore()` 与 `createLocalTransportFactory({ clientInfo, probeTimeoutMs, fetch })`，`fetch` 只在工厂参数给了时传；调一次 `createMcp(ports, { principalKey, maxListingPages, maxActions, instructionsByteLimit })`；登记撤除函数；逐个 `new` 三个服务子类，登记在同一个 `ctx` 上，共一条 fiber。三个服务共用 `createMcp` 的一张连接表、一张在途表与一张任务表。子类把每个方法原样转给 `createMcp` 交出的 `discovery`、`invoker`、`status`。`inspection` 与 `connections` 不提供成服务。
- **端口的现取。** 四个端口适配器每次被调用时，从 `apply` 收到的 `ctx` 用 `ctx.get(<键常量>)` 取服务。取到就把调用与参数原样转过去，答复原样交回。适配器不缓存取到的引用，也不用服务方法里调用方的上下文。
- <a id="port-absent"></a>**端口缺席。** 取不到时，适配器答该端口的 `unknown`，不答「拒绝」或「没有」：
  - `mcpAdoptionView` 缺席：`endpoints` 与 `endpoint` 答 `{ failure: 'unknown' }`（[AV6](../mcp-contract/SPEC.md#port-adoption)）。
  - `mcpUseEligibility` 缺席：`check` 答 `{ kind: 'unknown' }`（[UE5](../mcp-contract/SPEC.md#port-eligibility)）。
  - `mcpCredentialUse` 缺席：`acquire` 对两个用途都答 `{ failure: 'unknown' }`（[CU6](../mcp-contract/SPEC.md#port-credentials)）。
  - `mcpProcessLanding` 缺席：`start` 答 `{ failure: 'unknown' }`（[PL4](../mcp-contract/SPEC.md#port-landing)）。

  实际调用了缺席端口的那一步得到 `unknown`，操作按 mcp-contract 的条款答复，不放行：
  - 采用或资格不可读时，按 [S1](../mcp-contract/SPEC.md#services) 核采用与资格的操作答 `unknown`。`cancel` 不问端口（S1）。
  - 四个任务操作按 [S2](../mcp-contract/SPEC.md#services) 的建连规则：复用现有连接时不问采用与资格，端口缺席不挡它们；要新建连接而采用不可读时答 `Refusal` 的 `unknown`；资格不是 `granted` 时不建连接，答 `effect-unknown`（`no-connection`）。
  - 凭据不可读时，要连接的操作答 `credential-unavailable`（`unknown`）；落点不可读时答 `landing-unavailable`（[R6](../mcp-contract/SPEC.md#refusals)）。连接不建立，进程不起。凭据端口只在接入点需要凭据时被调用（[mcp 的 MC-5](../mcp/SPEC.md#mc-5)）。
  - `closeAll` 之后，要连接的操作先判关停，不问端口（[S8](../mcp-contract/SPEC.md#services)）。

- **换代。** 每次端口调用都现取。已转给旧提供者的调用照用它的答复。同一操作里，换代之后发出的端口调用用新实例。插件不因换代重跑，连接表不重建。已建连接持有的凭据句柄与进程句柄是旧提供者交出的：连接存续期间照旧使用，连接关闭时按 [MC-10](../mcp/SPEC.md#mc-10) 释放。
- **撤除。** 插件登记一个撤除函数，标签 `mcp.closeAll`。它只有一步收口：`await connections.closeAll()`。`closeAll` 答复之后，对报告里 `process` 为 `root-only` 或 `unconfirmed` 的每一条，撤除函数经 `ctx.logger('mcp').warn` 写一条警告，参数是消息、端点引用与范围；`tree-confirmed` 与 `no-process` 不写。撤除函数不捕获：`closeAll` 只在 `mcp` 有编程错误时以 `AggregateError` 拒绝（MC-10），这个拒绝原样抛给 Cordis，Cordis 4.0.4 的卸载把它交 `ctx.logger.error`，卸载照常完成。fiber 卸载后三个键上 `ctx.get` 答 `undefined`。撤除之后到达的操作按 [S8](../mcp-contract/SPEC.md#services) 答复。撤除不撤回已经发出的调用：已发出、还没有应答的调用答 `sent`，结局 `unknown`（`abandoned`）（S8、[O6](../mcp-contract/SPEC.md#outcomes)）。`closeAll` 报告的是确认的范围，不声称进程已停。
- **已知限制。** 插件不设期限。落点交出的进程句柄的 `stop()` 或凭据句柄的 `release()` 不答复时，`closeAll` 不答复，撤除函数不结算，`fiber.dispose()` 不返回（[mcp 的已知限制「拆除的端口挂起」](../mcp/SPEC.md#所有权失败与生命周期)）。期限由卸载该 fiber 的宿主承担。停止范围的警告是 `warn` 级：Cordis 4.0.4 的日志导出器没有设级别时只导出 `error` 与 `info` 两级（级别 0 与 1）。宿主要看到这条警告，须把导出器对 `mcp` 的级别设为 2 或更高。

## 所有权、失败与生命周期

- **身份与状态。** 一个 `Session` 是一个 `McpTransport`，带材料的代际。它拥有：在途请求表、连接模式（一个判别联合：现代一路，带协商出的版本；旧修订，带版本与旧 Streamable HTTP 的可选会话号；旧 HTTP+SSE 模式）、`closed` 与那一次关闭的结果、`dead`（流断开、进程退出、会话结束，传输不再可用）。在途表的每一项有请求号、`WireContext`、自己的 `AbortController`、自己的结算与出发点（两者都只兑现一次；在途表里还有它才算在途）与相：契约的 `InFlightPhase`（T5），已登记尚未交给线路 `authorizing`、已交给线路 `sent`（带它的交换：尚无、应答流的 `abort`、或探测计时的取消）、授权发现中 `discovery`（带拒绝应答的头与发现的进度）。线路拥有：stdio 的 writer、stdout 与 stderr 的 reader、两个时刻与退出窗口的计时；HTTP 的在途 `AbortController` 集合、endpoint 与共用流的 reader。
- **一个请求只结算一次。** 先到者定（T5）：应答、流断开、进程退出、探测时限、`cancelRequest`、`signal`、`close()` 中最先发生的那个给出结论，之后的事件对已结算的请求没有作用。一个请求在授权与写出之前登记进在途表，`call` 的 `signal` 在登记时接到它。
- **调用方只等结算。** 读写类操作与 `discover` 的探测等在途项的结算；`call` 等「出发点」与结算的先到者：线路收下请求（stdio 写完、HTTP 2xx 应答流开始）就交出 `SentCall`，先结算为 `not-sent` 就交失败，先结算为其他就交 `SentCall` 与那个答复。授权、组成与写出、拒绝报告与元数据取回、答复对端请求、通知，都是会话拥有的后台工作，经一个入口启动：调用凭据句柄之前同步核传输是否已关闭；在途表是每个工作流唯一的再核点：在途项结算之后的结果丢弃，没有在途项的写出（答复对端、通知、回退 GET）在句柄答复之后再核传输是否可用；工作流意外 reject 时，原因先交给 `SessionOptions.reportDefect`（缺陷出口；工厂的缺省在 Promise 之外抛出，让宿主的未捕获处理看到），再按所处的相结算它的在途项（规则是契约的 `stopAnswerOf`，见「取消」）；结算时端口抛出的缺陷也交缺陷出口；没有在途项的工作没有结局。处理一个线路事件或一条应答正文消息时的缺陷同样走缺陷出口，不归入流断开，读循环继续。线路的事件迭代 reject 时，会话按流断开处理（`stream-broken`，见「线路断开」），原因交缺陷出口。于是凭据句柄、元数据取回与对端的应答挂起都不让调用方等：没有 `signal` 的操作（`discover`、`listActions`、任务操作）只由 `close()` 放开；没有 `close()` 时，挂起的句柄由它的持有者负责。`close()` 本身只等线路的 `close()`，不等句柄、元数据取回或对端（见「关闭」）。`discover` 另有两处在关闭之下等待、关闭时收场的交换：旧一路回退 GET 的授权与 GET 本身，以及 `notifications/initialized` 的写出。
- **取消。** 登记之后任何时刻触发的 `signal`，传输都不再等待：在途项当场按所处的相结算，规则是契约的 `stopAnswerOf`（结局见 [V6](#properties) 与契约 [T5](../mcp-contract/SPEC.md#port-transport)，本页不重复）；`call` 在触发后结算，不等凭据句柄或对端；交换随之释放。`call` 的 `signal` 在调用前已触发时答 `not-sent`。「已交给线路」是 T5 的「已交出」：对端可能收到请求的任何部分之后；本包里就是授权返回、请求交给线路的 `send` 之后，不论写是否已完成。本包按相这样兑现：
  - 已登记、尚未交给线路（授权中）：授权若稍后返回，请求不发出。
  - 已交给线路，现代 Streamable HTTP：中止这次 `fetch` 与应答流，包括应答头还没到的时候。
  - 已交给线路，旧修订的 Streamable HTTP 与 SSE 模式：同样中止这次 POST 的交换；旧修订不把断开读成取消。SSE 模式下，应答若稍后经共用的流到达，按无关的消息丢弃。
  - 已交给线路，stdio：写已完成时，对端看不到释放。写未完成时，线路中止写端，传输按流断开不再可用（H6）。
  - 授权发现中：`signal` 结束元数据的取回，发现按当时已取到的内容交出，没取到的地址按 R4 是 `unavailable`；信号之后不再发起新的取回（R4 的第二个候选地址不再取），已发起的那次与拒绝报告在后台继续到结束，结果丢弃；会话不依赖取回遵守信号。
  - `cancelRequest`：stdio 与旧修订（含 SSE 模式）上，它把 `notifications/cancelled` 交给后台工作后当即返回（它不证明对端已停止），`answer` 继续等。现代 Streamable HTTP 上，它中止这个请求的 `fetch` 与应答流，答 `abandoned`。
- **关闭。** `close()` 标记关闭，对每个在途请求调用与 `signal` 同一条 `stopAnswerOf`，当场按它所处的相结算（结局见 V6 与 T5）；它不等授权发现结束，也不再调用句柄。然后会话中止一切 `fetch`、回退的 GET 与元数据取回，关闭线路，只等线路的 `close()`。线路的 `close()` 只依赖本地资源，不等对端（stdio 按 H6 中止写端，HTTP 中止全部交换）：这是线路端口对会话的义务（`Line.close` 的文档写明），也是 V4 中 `close()` 返回那一句的前提。关闭之后会话不再调用凭据句柄，不再答复对端的请求，之后的请求答 `not-sent`（`connection-unavailable`）。`close()` 可以重复调用：每次调用拿到同一次关闭的结果，都在线路的 `close()` 答复之后返回。
- **线路断开。** 流断开、进程退出（线路的 `ended`、`broken` 事件）与会话结束（T8 S07）都让传输不再可用，并按契约的 `lineGoneAnswerOf` 结算在途请求（结局见 V6 与契约 [T8](../mcp-contract/SPEC.md#t8)）。只有命运取决于线路的两相被结算：授权中的请求授权返回后不发出，已交给线路的请求按原因结算；会话结束时只结算被告知的那次请求，其余已交给线路的请求由各自的应答决定。授权发现中的请求不被断开结算：它的结论已由先到的拒绝定下，发现不经线路，发现做完照常结束；调用方放弃（`signal`、`close()`）才当场结算它。断开之后的请求不登记，不调用句柄；读类的再发经同一处登记被拒。迟到的应答（含迟到的 404）落在已结算的请求上没有作用，也不让传输不可用。
- **对端的请求与通知。** 任何线路上带 `method` 与 `id` 的消息由契约的 `readPeerMessage` 读出：`ping` 答空结果，其余答 `-32601`（`peerRequestAnswerOf`）。答复经线路写出，回显的 id 按原词形写出；HTTP 上答复是一次 POST，它先经 `authorize`（H4），它的状态没有结局。`notifications/progress` 的 `progressToken` 对上在途调用时交给它的 `observe`（抛出不改变结局）。其他通知丢弃。
- **资源释放。** 探测计时在结算或关闭时取消。应答到达之后，应答流在后台读到结束，释放连接；读的过程中到达的对端请求与通知照常处理。没有人等待的交换（通知、答复对端请求的 POST）同样在后台读完。关闭时这些读取随交换的中止结束。没有 disposer 让外部效果可撤回：已经写出的请求与通知就是写出了。
- **失败的处置。** 线路 reject 是线路的缺陷：会话把发送请求时的 reject 当作 `aborted`，把写出通知与答复时的 reject 忽略，把事件迭代的 reject 当作流断开并交缺陷出口。会话在结算途中调用的两个释放函数不抛出：流式交换的 `abort()` 与 `schedule` 返回的取消函数只释放本地资源。它们抛出是端口违约，本包对这时的结算不作保证。凭据句柄 reject 或抛出按 T9。工作流里任何没有预期的 reject 都有去向：原因交给缺陷出口 `SessionOptions.reportDefect`，它的在途项按所处的相结算（`stopAnswerOf`）。`observe` 抛出按契约 S6。本包不把错误变成成功：读不懂的应答按 T7 的 `what` 报出，没有应答按 `no-answer` 的原因报出。
- **并发。** 一条线路上可以有多个请求同时在途。stdio 上按行投递，每行对每个在途请求各归类一次。HTTP 上每个请求各自一次 `fetch`。SSE 模式下共用一条流。会话不排队，不限流。

## 性质与证据

本节把会话的请求生命周期写成定理，并分别记录每条性质的证据与状态。定理是目标。状态只说明所列证据在其范围内得到的结果，不是证明。模型动作、探索器动作与实现代码的映射、运行命令、规模上限与运行记录见 [verification/README.md](verification/README.md)。模型是 [verification/models/TransportSession.tla](verification/models/TransportSession.tla)，对真实实现的有界穷举探索器在 [tests/model/](tests/model/session-model.spec.ts)。

对象与参与者：

- 一个 `Session`（`src/session.ts`），一个 `McpTransport`，跑在一条线路上（`stdio-line.ts` 或 `http-line.ts`）。
- 驱动它的调用：`discover`、`call`、`listActions`、`updateTask`、`cancelTask`、`cancelRequest`、`close()`，以及每个 `call` 带的 `signal`。线路也驱动它：流断开、进程退出、旧 HTTP+SSE 共用流的结束（线路断开），以及对端对带旧会话的请求答 404（会话结束，T8 S07）；两者合称断开。
- 会话的注入端口：线路（`send`、`openGet`、应答流、`close`）、凭据句柄（`authorize`、`reportRejection`）、元数据取回 `SessionOptions.fetchMetadata`、计时端口 `SessionOptions.schedule`、缺陷出口 `SessionOptions.reportDefect`。会话不读全局时钟、不直接起全局计时器，所以探索器排定每一个端口调用、每一次计时触发、`signal` 与 `close()` 的次序。
- 一个在途请求的三相（`Pending.phase`）：已登记、尚未交给线路 `authorizing`，已交给线路 `sent`，授权发现中 `discovery`。

端口失败模型：每次端口调用可以按契约答复、答复它的失败、reject、或永不答复（挂起）。线路的 `send`、`openGet` 与应答流受它们收到的 `signal` 管辖：`signal` 中止时按契约当即收场（契约 [T5](../mcp-contract/SPEC.md#port-transport)、线路端口 [`line.ts`](src/line.ts)）。凭据句柄的 `authorize`、`reportRejection` 不收 `signal`，可以一直挂着；元数据取回收到 `signal`，会话不依赖它遵守，也可以一直挂着。承诺：调用方能看到的每一个等待（操作的结果、`call` 的结果与 `answer`）在 `signal` 触发或 `close()` 之后结算，凭据句柄、元数据取回、线路或对端挂起都不改变这一点。`close()` 单列：它只等线路的 `close()`，不等句柄、元数据取回或对端；它的上界取决于线路的 `close()` 会答复，这是线路端口对会话的义务（V4 中 `close()` 返回那一句的前提；stdio 见 [H6](#h6)，HTTP 见所有权一节「关闭」），不是对对端的假设。没有 `signal` 的操作（`discover`、`listActions`、任务操作）只由 `close()` 放开；没有 `close()` 时，挂起的句柄由它的持有者负责。挂起的端口调用留在后台，由会话拥有，它之后的答复作废。

证据分两种，范围见 [verification/README.md](verification/README.md#两种证据与各自范围)：有界穷举探索器驱动真实的 `Session`，核对下列性质的可观察形式；TLA+ 模型 `TransportSession.tla` 在有限配置内核对同一组性质的抽象形式。两者都只在各自上限与抽象之内成立，不是证明。

定理（性质编号、TLC 负控名与变异名在本节、[verification/README.md](verification/README.md) 与 [verification/models/README.md](verification/models/README.md) 三处相同；探索器与用例的负控名在本节、`verification/README.md` 与 `tests/model/mutants.ts` 三处相同；不变式名在下面证据表的 TLA+ 列、`verification/README.md` 与 `verification/models/` 相同）：

- **V1 恰好结算一次**：每个请求的答复恰好兑现一次；结算之后到达的线上事件、迟到的端口答复都不改变它。可观察的形式：没有为一个已结算的请求再发请求、再调用凭据句柄、再发起元数据取回（应答流在后台读到结束不算，见[资源释放](#所有权失败与生命周期)）。
- **V2 关闭、断开之后不碰凭据与线路**：`close()` 返回之后，不再调用凭据句柄的 `authorize` 与 `reportRejection`；会话断开之后，不再调用 `authorize`，也不再把请求交给线路。断开不禁 `reportRejection`：会话结束之后仍在途的请求被拒绝时，按 T4 报告一次。
- **V3 拒绝至多一次**：带 401、或带 `insufficient_scope` 的 403 的应答，至多调用一次 `reportRejection`，且只对曾用这个句柄授权过的请求；其他 403 与没有句柄的材料不调用（契约 [T4](../mcp-contract/SPEC.md#port-transport)）。
- **V4 有界**：请求的 `signal` 触发，或 `close()` 被调用之后，在探索器的静止点，调用方能看到的等待都已结算：该请求的结果、`call` 的 `answer`，以及 `close()` 结算的每个在途请求。结算当场发生，不等线路、凭据句柄或元数据取回；这些端口可以一直挂着，挂起的调用由会话留在后台。没有 `signal` 的操作只由 `close()` 放开。`close()` 在线路的 `close` 答复之后返回，不在它之前。只有这一句有前提：线路的 `close()` 只依赖本地资源。它是线路对会话的义务，stdio 的兑现见 [H6](#h6)，HTTP 的兑现见所有权一节「关闭」（中止全部交换）。`signal` 与 `close()` 对在途请求的结算不依赖这个前提，只依赖上面的端口失败模型：会话在结算途中调用的两个释放函数不抛出（见「失败的处置」）。断开子句：断开之后没有授权中的请求；线路断开之后没有已交给线路的请求；会话结束之后，其余已交给线路的请求合法地等自己的应答。授权发现中的请求断开前后一样，由取回答复、`signal` 或 `close()` 放开。
- **V5 不代调用方重发**：写类请求（`tools/call`、`tasks/update`、`tasks/cancel`）在流断开或「2xx 而没有应答」后不再发；读类（`server/discover`、`tools/list`、`tasks/get`）至多再发一次，用新的请求号并重新授权；旧 HTTP+SSE 模式下都不再发（契约 [T8 D15、O05、O06、C04](../mcp-contract/SPEC.md#t8)）。
- **V6 三相的去向**：`signal` 触发或 `close()` 时，按请求所处的相当场结算，两者规则相同：已登记、尚未交给线路的答 `not-sent`（`connection-unavailable`）；已交给线路的答 `no-answer`（`abandoned`）；授权发现中的答 `not-sent`（`authorization-required`），发现按当时已取到的内容交出，没取到的地址按 R4 是 `unavailable`，`close()` 不等发现结束。`close()` 之后或 `signal` 已触发时开始的请求答 `not-sent`（`connection-unavailable`）（契约 [T5](../mcp-contract/SPEC.md#port-transport)）。断开按同一条「相 → 结局」规则，但只作用于依赖线路的两相：授权中的请求答 `not-sent`（`connection-unavailable`）；线路断开时，已交给线路的请求按原因答 `no-answer`（`stream-broken`、`process-exited`）；会话结束时只有触发它的请求答 `not-sent`（`session-ended`），其余已交给线路的请求不动，等各自的应答；授权发现中的请求不被断开结算，之后照常以 `authorization-required` 结束（断开不是调用方放弃）。断开之后开始的请求答 `not-sent`（`connection-unavailable`）（契约 [T8](../mcp-contract/SPEC.md#t8)）。
