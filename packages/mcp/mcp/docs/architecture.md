## 关键机制与理由

- **关口只有一份，令牌有两个。** S1 的次序与映射只在 `gate.ts`：`admit` 交出带裁决的 `GateDecision`，`admitForUse`、`stillAdmitted`、`status.inspect`、`status.list` 都在它上面组合。「先核采用再核资格」不靠纪律：需要连接的函数只收 `AdmittedEndpoint`，它只由 `judge` 在资格 `granted` 时授予；只过采用的 `AdoptedOnly` 是另一个品牌，赋不进去。两者都是带解析过正文的冻结副本，只在关口内从采用端口的答复铸出（铸造函数不导出），登记在模块私有的 `WeakSet` 里；`judge` 只认登记过的令牌，运行期 `assertAdmitted` 挡住伪造的对象，所以准入的连接只在端口交来的材料上建立。
- **聚合不做 I/O，只由连接表一方写。** `Connection` 只做状态转移；连接表与它发起的建连（`build.ts`）在每次端口调用之后告诉它结果，服务经 `table.settle`、`table.lose` 报告，`Ensured` 只交只读视图。非法转移抛 `TypeError`，因为它只能来自本包的编程错误。两种代际策略写成 `GenerationPolicy`：新增一种传输只加一个取值。
- **键的规范文本。** 连接表与内存存储的 `Map` 键是 `connectionKeyOf`、`catalogKeyOf` 的固定字段序 JSON 文本。租户文本来自 `tenantCodec.encode`，所以不是 `legal-identity` 造出的租户进不了表。
- **建连、拆除与关闭都单飞，代际延续。** 同一键的并发 `ensure` 共享条目上的一个 promise；条目的拆除只有一次在进行（`tearing`），`lose`、准备失败、重建前的再停与关闭共用它，`lose` 先同步转状态再拆除；同一键的关闭也只有一次在进行（`closing`），`ensure` 等关闭或拆除完成再建，至多等到自己的临界区时限；条目只在已关闭且什么也不持有时删除（`forgettable`，SPEC MC-14）。同一租户同一持有的 `ensure` 在一个临界区里重读采用、关闭其他修订的连接并建立条目（建连在临界区外；重读与等待都受这次 `ensure` 的临界区时限约束），所以哪个修订的条目存在由临界区决定，两个修订的令牌先后过重读只留一个。关闭后条目删除，但键的最后代际留在一张小表里，下一条连接从它继续，所以一次运行内一个键的代际不重复，W3 的 `cancel`、`continueWithInput` 可以用代际数值比较。迟到的结果（旧代际的页）经 `settle`/`lose` 的代际守卫被忽略。
- **时限由本包自己守，调用方的中止只属于调用方。** 建连的时限从 `attempt()` 起覆盖尝试前对遗留进程的再停、`acquire`、`landing.start`、`open`、`discover`，以及失败或关停之后的收场，取页另起同一上界；每一次等待经 `within`，端口不尊重信号时也在时限内答复，时限到期后建连不再等任何端口，还没做完的收场在连接表的任务作用域里继续（失败答复的 `catalog` 是 `pending`）；迟到交来的句柄释放、传输关闭，迟到交来的进程停止一次并把未确认的范围记进条目的 `lingering`，等待落点的条目不被删除。落点未答时凭据句柄随可能到来的进程走：进程交来则在它 `stop()` 之后释放，落点答失败则随答复释放（S9）。每个端口只经 `ask` 询问：同步抛出与 reject 读成该端口的违约答复，时限后的违约当作什么也没交来。调用方的 `signal` 不进共享的建连：等建连、取页与发布边界各自核对它，答 `kept(cancelled)`，不标记清单。
- **失败按阶段，带着清单标记的结果回来。** `ensure` 的失败是 `{ stage: 'settings', reason }` 或 `{ stage: 'connect', reason, catalog }`：S5 要求 `refresh` 对标记写入的冲突答 `kept(superseded)`、不可用答 `unknown`，而 W3 的 `invoke` 只要 `reason`。两种消费者各取所需，标记只做一次。
- **发布边界在服务里，紧挨写入。** `mergeListing` 只核清单修订（契约 C5）；`refresh` 先做异步的核对（`stillAdmitted`：资格与采用修订），再在写入前同步核对代际与取消，中间没有 await。两次并发刷新各自取页，谁先写谁发布，另一方由存储的 `revision-conflict` 得到 `superseded`。
- **关闭只报告确认范围。** `teardown` 的次序固定：关传输、停进程（自己的与上次未确认停止的，每个都问）、释放句柄；关闭前先拒新请求并等在途的建连结束。端口违约经 `ask` 吸收（SPEC MC-14、MC-15）：`close()` 当作已关闭，`stop()` 当作 `unconfirmed`，`release()` 当作已释放不重试；所以每一步都执行，拆除不因端口违约而 reject，本包自己的错误照常抛出。未确认停止的进程留在条目的 `lingering` 里（带它确认的范围），视图由同持有全部条目的 `lingering` 报告 `residual`，下一次关闭或重建前再问一次。落点仍在途时确认范围并入 `unconfirmed`。建连中的端口违约按建连失败收场（SPEC MC-5 的表），只有本包的编程错误在收场后原样抛出。
- **关停先放句柄，再关连接。** `closeAll` 先置已关停，同步发起全部在途落点句柄的释放（S9 的关停例外；已交来进程的落点不在途，它的句柄等那个进程停止），再并发关闭各条目，所以一条连接的关闭挂起不拖住别的条目的句柄；两者都结束后，把任务作用域记下的本包错误以 `AggregateError` 交出。途中的建连在取得凭据之后、进程交来之后与协商成立之后各核一次已关停，命中则按准备失败拆除，不标记清单，所以关停开始后不交出连接。关闭次序的端口挂起时 `closeAll` 也挂起，宿主以自己的期限包住它（SPEC「已知限制」）。
- **时钟。** 清单取得时刻来自 `McpPorts.clock`；不给时装配读本机时钟，并按仓库规则标注为观察时刻。它不参与本包的任何判断。
- **调用口把取消做成一个信号。** 每次占位在途表给一个取消信号，与调用方的 `signal` 合成一个停止信号：发出前核对它，发出后在它下面等应答，所以 `cancel` 与调用方的中止走同一条路，对端只被告知一次（MC-16）。`cancel` 不认识连接：在途表项记下发出时的连接视图，自己判当前代际。
- **任务按发起时的账户隔离。** 任务表项记下对端账号；复用与新建的连接都要在同一个（租户、持有、账号）上，采用修订不算（MC-17）。复用不问任何端口，新建经同一个关口。
- **作用域归连接表。** 表自己建任务作用域，对外只给能交工作的视图；加入别人工作的等待（`waitAtMost`）不把工作交给作用域，自己发起的等待（`within`）才交。

## 验证与维护

每条 SPEC 条款对应的测试、反例与变异见 SPEC「结果与不变量」「组合与验证」。L3 热点是 `internal/gate.ts`、`internal/table.ts`（键、临界区、关闭对建连、关停）、`internal/teardown.ts`（句柄释放、每一步与每个进程）、`internal/build.ts`（时限与关停的收场）、`discovery.ts` 的发布边界、`internal/in-flight.ts` 与 `internal/task-table.ts` 的键、`tasks.ts` 的账户比较；交错用例在 `tests/races.spec.ts`、`tests/shutdown.spec.ts` 与 `tests/cancel.spec.ts`。改契约的服务条款时改同名模块；改 `Connection` 的状态机时同步 `tests/connection.spec.ts` 的合法转移表。
