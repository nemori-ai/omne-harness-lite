## 结果与不变量

每条写本包怎样兑现、一个反例，以及让守住它的用例变红的变异。锚点给验证引用。

<a id="mc-1"></a>

- **MC-1 配置**（S3）：`createMcp(ports, config)` 用 `validateConfig` 核对 `McpConfig`。`principalKey` 不是函数，或三个上界不是正的安全整数时，抛出 `RangeError`，不建立任何服务，不问任何端口。配置不是对象时同样抛出。`createMcp` 交出契约的五个服务 `McpServices`，它们共享一张连接表、一个在途表与一个任务表，装配只在 `internal/assembly.ts` 一处，测试经同一处装配。清单取得时刻来自 `McpPorts.clock`，缺省读本机时钟（S3）；输出校验函数来自 `McpPorts.checkOutput`（S3、O1）。反例：`maxListingPages: 0`、`maxActions: 1.5`、`principalKey: 'alice'`；两个服务各建一张表，`invoke` 看不见 `refresh` 建起的连接。变异：`isPositiveSafeInteger` 放过 0 → `config.spec.ts` 变红；装配不读 `ports.clock` → `mcp.spec.ts`「clock of the ports」变红。

<a id="mc-2"></a>

- **MC-2 关口**（S1）：S1 只有一份实现，在 `internal/gate.ts`：`admit` 先问 `AdoptionView.endpoint`（`adopted`，并把正文解析一次），再问 `UseEligibility.check`（`judge`），交出一个带裁决的 `GateDecision`；`refusalOf` 把裁决映射为 R1 的拒绝。未采用答 `not-available-to-you` 且不问资格；采用不可读或正文不能解析答 `unknown`；资格 `not-eligible` 答 `not-available-to-you`；被设置挡下答 `blocked` 带原因；资格 `unknown` 答 `unknown`。生产入口是 `internal/guard.ts` 的 `admitForUse`（读口、`release`）与 `stillAdmitted`（发布边界），以及 `status.ts` 在 `admit`/`judge` 上的组合；它们不另写映射。两个令牌：`AdoptedOnly`（采用通过、正文已读、资格未判）与 `AdmittedEndpoint`（资格也通过），都是冻结副本，带模块私有品牌并登记在模块私有的 `WeakSet` 里；需要连接的函数只收后者，`assertAdmitted` 对其他对象（含 `AdoptedOnly`、副本）抛出 `TypeError`。令牌只在关口内从采用端口的答复铸出，铸造函数不导出；`judge` 只接受登记过的 `AdoptedOnly`，换了正文或定义的副本抛出 `TypeError`，所以被准入的连接只在端口交来的材料上建立。`list` 经 `admitScope` 在关口内逐项裁决。反例：未采用的接入点让资格替身被调用；换掉定义的令牌副本被 `judge` 准入并启动了不是采用的命令。变异：`admit` 先问资格再看采用 → `gate.spec.ts`「without asking eligibility」与 `races.spec.ts`「(D1)」变红；`judge` 不核令牌来源 → `gate.spec.ts`「only a token this gate handed out」变红。

<a id="mc-3"></a>

- **MC-3 连接键**（K2，不变式 1）：连接表的键是 `connectionKeyOf(tenant, endpoint, account)` 的规范文本，含租户、持有、采用修订与对端账号。两个租户、两个对端账号、两个采用修订各自得到不同的连接。对端账号只由 `peerAccountOf` 得出（K1）。反例：同一采用修订下两个凭据绑定共用一条连接。变异：`connectionKeyTextOf` 去掉对端账号 → `ensure.spec.ts`「two peer accounts」变红；去掉租户 → 「two tenants with the same holding and adoption revision」变红。

<a id="mc-4"></a>

- **MC-4 配值**（S4、K1）：要连接的操作按 target、credential、connect-timeout、env 的次序检查配值，只报第一项（`settings` 阶段的失败）。credential 缺失答 `credential-unavailable`（`missing`），不合法答 `config-invalid`（`credential`）。connect-timeout 缺失时用请求的 `connectBound`，不合法时不改用 `connectBound`。`current` 与 `peer` 只需要 credential，缺失答 `config-missing`（`credential`）。反例：target 与 credential 同时不合法时报 credential。变异：`prepareSettings` 先查 credential → `ensure.spec.ts`「reports the first defect only」变红。

<a id="mc-5"></a>

- **MC-5 建立连接**（S4 第 4 步、R6、S7、S9，不变式 3、5）：连接表对一个键只建一条连接。状态是 `ready` 或 `degraded` 时复用；`preparing` 在途时加入同一次建连（单飞）；`lost` 或 `closed` 时重建，代际延续；同键的关闭在途时先等关闭完成。加入在途建连的调用最多等自己的加入时限，时限从加入起计时：先到时答 `connect` 阶段的 `connection-unavailable`，`catalog` 是 `pending`，建连继续由开始它的调用收场（第 1 轮裁定 F1）。建立前重读 `AdoptionView.endpoint`：未采用答 `not-available-to-you`，不可读或 reject 答 `unknown`，修订与令牌不同答 `unknown`；三种都不建连、不关别的连接。这次 `ensure` 的临界区时限从入口起计时，覆盖排队等临界区、重读与临界区里的等待（已定事项 22，第 1 轮裁定 F1）：时限先到答 `connection-unavailable`，不标记清单，不再等着或占着临界区。轮到时时限已到的调用不读采用、不等、不建连。临界区里等其他修订的关闭、同键的关闭或拆除时时限先到，拆除继续由条目自己收口。`closeAll` 之后的 `ensure` 不读采用、不建连，直接答 `connection-unavailable`（已定事项 5）。建连途中表关停时，建连在取得凭据之后（进程启动之前）、进程交来之后（打开传输之前）与协商成立之后（`ready` 之前）各核一次：已关停则拒新请求、按准备失败拆除（句柄释放、已起的进程停止），答 `settings` 阶段的 `connection-unavailable`，不标记清单。关停开始之后建连的某一步失败也这样收场：不标记清单，答同样的拒绝（第 1 轮裁定 F3）。所以关停开始之后才失败、或在检查点核到关停的建连，与关停之后才开始的 `ensure` 答同样的拒绝，不交出一个随即被拆的连接，也不写清单（已定事项 23）。关停之前已经失败的建连照常标记清单、答原来的失败，答复晚于关停也一样；`closeAll` 等这次标记写完（MC-10）。同一租户同一持有的 `ensure` 在一个临界区里完成重读、关闭其他修订的连接与条目的建立（建连本身在临界区外），所以两个修订的令牌先后过重读只留一个条目：后过的那个关闭先建的。建立的次序：`Connection.attempt()` → 再停这个键上一条连接留下的未确认停止的进程 → `auth` 不是 `none` 时 `CredentialUse.acquire`（stdio 用 `process-env`，HTTP 用 `http-authorization` 带 target） → stdio 经 `ProcessLanding.start` 取进程 → `McpTransportFactory.open` → `transport.discover()` → `Connection.ready(peer)`。建连时限在 `attempt()` 之后起计时，由表的时限来源取得（缺省 `AbortSignal.timeout`），覆盖建连的每一次等待：`attempt()` 之后、取凭据之前的再停，取凭据、进程启动、打开传输、协商，以及失败或关停之后的收场（拆除与标记清单）。时限到期后建连不再等任何端口，立即答复（P8 T2）；还没做完的收场在表的任务作用域里继续，失败答复里的 `catalog` 是 `pending`。端口不尊重信号时连接表自己放弃等待：迟到交来的句柄释放、传输关闭；迟到交来的进程 `await stop()`，范围不是 `tree-confirmed` 时并入条目的 `lingering`，状态视图由它报告 `residual`，下一次关闭再停一次。落点从开始起就在途，进程凭据句柄随落点走；落点在时限内答复时，句柄回到条目。落点在时限内未答时句柄不立即释放：进程交来则在它 `stop()` 返回后释放，落点答失败或 reject 则随答复释放（S9）。`closeAll` 在落点答复之前到来（时限内或时限后都算）则立即释放（S9 的关停例外，MC-14，第 1 轮裁定 F2）。每个端口都经 MC-15 的 `ask` 询问，违约（同步抛出或 reject）是该端口的违约答复；时限之后的违约当作什么也没交来，所以收口不留下未处理拒绝。调用方的 `signal` 不进建连：单飞由所有调用方共享，只受建连时限约束。任一步失败（含端口违约）：连接先同步转 `lost` 带 S7 原因，再经条目唯一的拆除关传输、`stop()` 已起的进程、释放凭据句柄（S9：进程句柄在 `stop()` 返回之后，没有进程时立即），`residual` 由拆除的结果报告，清单经 `markUnavailable` 写入。只有本包自己的编程错误在收场后原样抛给调用方。失败的答复与原因：

  | 失败                                                                       | 答复                                | `lost` 原因                                                            | `markUnavailable` 原因   |
  | -------------------------------------------------------------------------- | ----------------------------------- | ---------------------------------------------------------------------- | ------------------------ |
  | 凭据 `missing`、`rejected`、`unknown`                                      | `credential-unavailable` 带子因     | `preparation-failed`                                                   | `credential-unavailable` |
  | 落点 `landing-invalid`、`facility-missing`、`unknown`                      | `landing-unavailable`               | `preparation-failed`                                                   | `landing-unavailable`    |
  | `open` 或 `discover` 答 `not-sent`（`authorization-required`）             | `authorization-required` 带授权发现 | `authorization-required`                                               | `authorization-required` |
  | `open` 或 `discover` 答 `not-sent`（`connection-unavailable`）、任一步超时 | `connection-unavailable`            | `preparation-failed`                                                   | `connection-unavailable` |
  | `discover` 答 `no-answer`                                                  | `effect-unknown` 带子因             | `stream-broken`、`process-exited`；`abandoned` 记 `preparation-failed` | `connection-unavailable` |
  | `discover` 答 `error-answer`、`answer-malformed`                           | `connection-unavailable`            | `discover-failed`                                                      | `connection-unavailable` |

  `ensure` 的失败分两个阶段：`settings`（S4 的拒绝、K1 的 `credential-unavailable(missing)`、重读采用的 `not-available-to-you` 与 `unknown`、临界区时限先到与关停（建连之前、途中，或关停开始之后的失败）的 `connection-unavailable`；没有标记）与 `connect`（上表的答复，带标记结果 `catalog`：`marked`、`revision-conflict`、`unavailable`、`not-acquired`，或 `pending`：这次调用没等到标记的结果。`pending` 有两种来源：开始建连的调用的建连时限先到时，标记在作用域里继续，结果不再报告给它；加入在途建连的调用的加入时限先到时，建连仍归开始它的调用，可能成功，也可能失败并把标记结果报告给开始它的调用，加入的调用不知道建连的结局）。凭据缺失时没有对端账号，所以不标记清单。与契约 S5 的差异：S5 写 `discover` 答 `no-answer` 时连接转 `degraded`（`discover-failed`）。本包只在建连中调用 `discover`，这时连接还不是 `ready`，所以按上表转 `lost`。这项差异登记在[偏离](#deviations)。反例：落点永不返回时 `ensure` 永不返回、`release` 被拖住；时限后才交来的进程答 `unconfirmed` 却不进 `residual`；一次不答复的重读，或旧修订一次不答复的 `close()`，让同持有之后的每个 `ensure` 一起等；排在一个占着临界区的调用后面的 `ensure`，或加入一次挂起的建连的 `ensure`，等过了自己的时限；`closeAll` 之后，取凭据途中的建连照样启动进程、打开传输；关停开始之后失败的建连照样标记清单；建连自己的拆除或标记清单挂起时，调用方在时限之后仍等待。变异：排队等临界区不经 `within` → `races.spec.ts`「a call queued behind one that holds the critical section」变红；轮到时不核时限 → 同一例变红；加入的调用不受自己的时限 → 「a call that joins the build of another」变红；关停开始之后的失败仍标记 → `shutdown.spec.ts`「a build that fails after the shutdown began」变红；`landing.start` 不经 `within` → `races.spec.ts`「(B5)」变红；失败后的收场不经 `within` → `ensure.spec.ts`「with the mark pending」变红；失败路径不释放句柄 → `ensure.spec.ts` 三条「released exactly once」变红；迟到的进程不并入 `lingering` → `races.spec.ts`「(R3-2, S9)」变红；时限到时立即释放句柄 → 「(S9)」变红；重读与建条目不在一个临界区 → 「(observation)」变红；重读不经 `within` → 「(decision 22)」超时变红；临界区等关闭或拆除不受时限 → 「a teardown that does not answer holds no ensure past its bound」两例超时变红；建连不核已关停 → `shutdown.spec.ts`「shut while the credential is asked」「shut while the process starts」或「shut while negotiating」变红；关停收场标记清单 → 「marks nothing」变红。

<a id="mc-6"></a>

- **MC-6 代际**（不变式 2）：stdio 的代际在每次 `attempt()` 加一，失败的尝试也加；HTTP 的代际在 `ready()` 加一。同一个键关闭后再建的连接延续上一条的代际，同一次运行内一个键的代际不重复。`Connection.isCurrent(g)` 只对当前代际且状态是 `ready` 或 `degraded` 时为真。聚合只由连接表写（含它发起的建连）：服务经 `table.settle`、`table.lose` 报告结果，`Ensured.connection` 只是 `generation` 与 `isCurrent` 的只读视图。反例：失败的 stdio 尝试不加代际，迟到结果与下一次尝试同代。变异：`on-attempt` 改在 `ready` 加代际 → `connection.spec.ts`「failed attempts included」变红。

<a id="mc-7"></a>

- **MC-7 刷新与发布**（S5、C1–C6、不变式 2、4、5）：`refresh` 的次序是关口 → `ensure`（调用方 `signal` 中止时答 `kept`（`cancelled`），建连留给其他调用方） → `CatalogStore.read` 取 `basedOn` → 取页 → `completeListing` → `mergeListing` → 发布边界 → `CatalogStore.write(key, record, basedOn)`。`ensure` 失败时：`settings` 阶段的失败原样答复；`connect` 阶段按 `catalog` 答复：`marked`、`not-acquired` 与 `pending` 答这次连接失败本身，`revision-conflict` 答 `kept`（`superseded`），`unavailable` 答 `unknown`。取页阶段另起同一上界的时限（来源同 MC-5），最多 `maxListingPages` 页：某页超时按该页 `no-answer`（`abandoned`）处理；调用方中止答 `kept`（`cancelled`），不标记清单，连接不变。页答 `no-answer`、`error-answer` 或 `answer-malformed` 时 `kept`（`listing-incomplete`，`page-failed`），连接由 `ready` 转 `degraded`（`list-failed`）；全部页成功时 `degraded` 回到 `ready`；两者都经 `table.settle` 并只对当前代际生效。页答 `not-sent` 时经 `table.lose` 按 MC-5 的表处理，但 `lost` 原因是 `stream-broken`（`connection-unavailable`）或 `authorization-required`；标记写入冲突答 `kept`（`superseded`），不可用答 `unknown`；产出该页的代际已不是当前时 `lose` 不动作，`refresh` 答 `kept`（`superseded`）。发布边界的次序：先 `stillAdmitted`（资格仍 `granted`，否则答对应 `Refusal` 不发布；采用修订仍等于清单所在连接的修订，否则 `kept`（`superseded`）），然后紧挨写入同步核对产出清单的连接仍是当前（`isCurrent`，否则 `kept`（`superseded`））与 `signal` 未中止（否则 `kept`（`cancelled`））。写入答 `revision-conflict` 时 `kept`（`superseded`），答 `unavailable` 时 `unknown`。读取答 `unavailable` 时 `unknown`，不取页。清单取得时刻来自 `McpPorts.clock`（MC-1）。反例：资格核对期间连接换代，旧代际的清单仍发布。变异：去掉写入前的同步核对 → `races.spec.ts`「(B1)」两条变红；`lose` 去掉代际守卫 → 「(B2)」变红；取页不经时限 → 「(B3)」两条变红；去掉发布边界的 `isCurrent` → `refresh.spec.ts`「invariant 2」变红。

- **MC-8 读口不连接**（S8、K3）：`current` 与 `peer` 只过关口、读配值、查存储与连接表。`current` 的 `basisCurrent`：没有连接 `no-connection`；协议版本相等且能力按规范化 JSON（成员按名字的 UTF-16 码元排序）相等 `matches`；否则 `differs`。`peer` 没有 `ready` 或 `degraded` 的连接时答 `not-connected`。反例：`current` 在未连接时打开传输。变异：`current` 在没有连接时调用 `ensure` → `refresh.spec.ts`「not-acquired before any refresh, with no transport opened」变红。

<a id="mc-9"></a>

- **MC-9 状态视图**（S1、S7）：`inspect` 在 `admit` 的裁决上组合：未采用答 `not-available-to-you`，不可读答 `unknown`，`not-eligible` 答 `not-available-to-you`，被挡下写进 `use: blocked` 不算失败。凭据按解析过的正文与配值报告 `not-required`、`absent`、`invalid`、`present`，不报告值。连接状态来自连接表：没有条目 `none`；关闭后进程未确认停止时 `lost`（`close-unconfirmed`）带 `residual`；`lost` 带准备失败或关闭留下的 `residual`。`list` 经 `AdoptionView.endpoints` 取列表，逐项经 `judge` 核资格，`not-eligible` 不列，被挡下列出并带 `use: blocked`，任一项 `unknown` 整次 `unknown`，采用不可读整次 `unknown`。无权主体对存在与不存在的接入点得到同一答复。反例：`list` 把 `not-eligible` 的接入点列出。变异：`list` 对 `not-eligible` 写 `blocked` → `status.spec.ts`「not the ones without eligibility」变红。

<a id="mc-10"></a>

- **MC-10 关闭**（S8、S9、组页 `close()` 次序，不变式 4）：`release` 过关口后关闭该租户该持有的连接，一个键同时只有一次关闭在进行（单飞），拆除也只有一次（条目的 `tearing`，MC-14）：`lose`、准备失败、重建前的再停与关闭共用它。次序：`Connection.close()`（或 `lose()`）先同步拒新请求 → 关闭等在途的建连结束 → `transport.close()` → stdio `process.stop()`（含上次未确认停止的与迟到交来的进程） → 释放凭据句柄。`lose` 在途时的 `release` 等这次拆除完成再报告；`lose` 在途时的 `ensure` 等它完成再建。报告 `released` 带拆除返回的确认范围（几个进程时取最窄的），没有进程带 `no-process`，落点仍在途时带 `unconfirmed`（进程可能还会来，已定事项 5），没有连接答 `no-connection`。关闭后条目按 MC-14 的谓词删除，状态回到 `none`；`stop()` 答 `root-only` 或 `unconfirmed`（或 reject）时进程句柄留在条目里，状态是 `lost`（`close-unconfirmed`）带 `residual`，再次 `release` 或重建前再次 `stop()`，报告它这次确认的范围。`closeAll` 不问采用与资格：它把表置为已关停（之后不再建连），先发起在途落点的句柄的释放，不等答复（MC-14），再并发关闭每条连接，等全部释放与拆除结束后报告。然后它取走任务作用域记下的本包错误并关闭作用域（作用域由连接表自己创建，表外只拿到只能交工作的视图，退出只在这里）。有本包错误时，`closeAll` 以一个 `AggregateError` 拒绝，不交出确认范围的报告；它装着放弃在途落点或关闭某条连接时抛出的本包错误（这时其余连接照样关完，P3），以及任务作用域记下的本包错误。再次调用 `closeAll` 不再报这些错误；作用域关闭之后才出现的本包错误交给作用域的事后出口（`TableRuntime.afterExit`），缺省作为未捕获的异常抛出（P7，第 1 轮裁定 F5）。关闭不声称进程已停。反例：关闭进行中建起的新连接被删掉，进程无人停；`lose` 拆除途中 `release` 先报告 `released`，进程先于传输停止；落点永不答复时 `release` 报 `no-process`。变异：`ensure` 不等在途的关闭 → `races.spec.ts`「(B4)」变红；先 `stop()` 再 `transport.close()` → `release.spec.ts`「closes the transport before it stops the process」变红；`lose` 在拆除之后才转状态 → `races.spec.ts`「(R3-1)」变红；在途落点不并入确认范围 → `teardown.spec.ts`「(decisions 5, 6)」变红。

<a id="mc-11"></a>

- **MC-11 自动关闭的粒度**（S1 末句，不变式 6）：被设置挡下（`disabled`、`local-command-not-enabled`）与撤采用是接入点级的事实：关口答未采用或被挡下时，`refresh`、`current`、`peer`、`release`、`inspect`、`invoke`、`continueWithInput`（MC-16 第 3 步）、发布边界，以及任务操作经关口新建连接的那一步（MC-17 第 3 步；复用连接不问关口）先关闭该接入点的连接。主体无资格（`not-eligible`）是主体级的事实，不关闭：接入点对租户仍然成立。资格或采用 `unknown` 不关闭。`list` 不关闭。每次 `ensure` 先关闭同租户同持有下采用修订不等于当前读到的修订的连接；旧修订的令牌不能关闭新修订的连接（MC-5）。反例：一个主体被判 `not-eligible` 关掉同租户其他主体的连接。变异：`withdraws` 对 `not-eligible` 答真 → `gate.spec.ts`「does not close for a principal without eligibility」与 `races.spec.ts`「(O1)」变红。

<a id="mc-12"></a>

- **MC-12 在途表**（S2 的表，调用口第 1 轮裁定 1、4）：`InFlightCalls` 的键是（租户、`principalKey` 文本、关联键）。`reserve(key, signal)` 查重与占位是一个同步步骤，交出这次调用的停止信号：调用方的 `signal` 与本表的 `cancel` 合成一个；已结束的键可以再次占位。`cancel` 对只占位的键触发它，答 `signalled`；对已发出且其连接视图仍以发出代际为当前的键触发它，答 `signalled`；代际已换答 `unknown`，不触发；不在表的键答 `unknown`；已结束答 `no-call-in-flight`。`markSent(key, connection, generation)` 记下连接视图与发出代际：`ensure` 交出的代际，不是视图在记录时刻的代际。`conclude(key, phase)` 是键的唯一收口（MC-16 第 13 步）：已发出 → 结束；未发出且停止信号已触发 → 结束（调用存在过并被取消，之后的 `cancel` 答 `no-call-in-flight`）；未发出且未触发 → 撤销占位（之后的 `cancel` 答 `unknown`）。表项在本次运行内不删除，撤销的占位除外。请求标识由调用口自己持有，表不记。反例：两个并发占位都答 `reserved`；另一主体的 `cancel` 触发了本主体调用的信号；`call` 返回之前连接换代，表记成新代际，`cancel` 对已关闭的旧传输发了 `cancelRequest`。变异：`reserve` 查后经 await 再占 → `in-flight.spec.ts`「exactly one of two concurrent callers」变红；键文本去掉主体 → `cancel.spec.ts`「another principal」变红；去掉租户 → 「another tenant」变红；`cancel` 对已发出的键不核当前代际 → `in-flight.spec.ts`「generation has changed」变红；`markSent` 记视图的实时代际 → `in-flight.spec.ts`「by the generation it was sent on」与 `invoke.spec.ts`「lost and rebuilt before call returns」变红；`conclude` 对停止信号已触发的未发出调用撤销占位 → `cancel.spec.ts`「a signal that fired before the call」等变红。

- **MC-13 内存存储**（CS1–CS7）：`createInMemoryCatalogStore` 按清单键的规范文本（租户文本、对端账号文本、持有）保存整份记录，只接受期望修订等于当前修订的写入。它没有不可用的路径，CS8 不适用。租户不是 `legal-identity` 造出的值时抛出 `TypeError`。反例：两个租户同一持有读到同一份记录。变异：`catalogKeyTextOf` 去掉租户 → `memory-store.spec.ts` CS7 与「differs in the tenant」变红。

<a id="mc-14"></a>

- **MC-14 拆除与遗忘**（S8、S9、W3 已定事项 4、5、6、20、21）：拆除是一条连接的资源的关闭次序：关传输、停进程、释放凭据句柄。本包承诺：
  - 每步都执行：前一步的端口违约不跳过后一步。
  - 每个进程都被要求停止：条目自己的进程与每个未确认停止的进程各被请求停止一次；某个 `stop()` 违约不跳过其余进程。
  - 端口违约（同步抛出或 reject，MC-15）的处置（已定事项 4）：`close()` 违约当作已关闭；`stop()` 违约当作 `unconfirmed`，进程留到下一次关闭或重建前再停；`release()` 违约当作已释放，不重试，也不再调用第二次。
  - 拆除不因端口违约而 reject。本包自己的编程错误不吞掉，照常抛给等这次拆除的调用方。
  - 一条连接同时只有一次拆除，后来的加入它。拆除返回确认范围：这次每个 `stop()` 的答复取最窄，再并入仍未确认停止的进程；落点仍在途时并入 `unconfirmed`（已定事项 5）。调用方不自己拼。
  - 删除条件（已定事项 20）：条目只在已关闭、且下面五项都不持有时从表里删除：传输、进程句柄、凭据句柄、未确认停止的进程、在途的落点。一项资源在它的端口答复之后才离开条目，所以拆除等端口时条目不被删除。
  - 关停例外（S9、已定事项 6）：`closeAll` 先发起全部在途落点的进程凭据句柄的释放，不等答复，再关闭各条连接；之后交来的进程照样停止一次，句柄不再释放第二次。落点从开始起就在途，时限之内的也算（第 1 轮裁定 F2）。表关停之后才超出时限的落点，句柄在超出时限时立即释放。一个在途落点的句柄只释放一次，先到的一方（迟到的进程停止之后，或关停）释放它。已经交来进程的落点不再在途：它的句柄等这个进程的 `stop()` 答复之后释放（S9），关停不提前释放它。

  反例：`close()` reject 后换采用修订，旧进程无人停、旧句柄无人释放，旧条目却被遗忘（W2 评审探针 x4b）；自己的进程 `stop()` reject 后，未确认停止的进程这一轮没被问到（W3 评审探针 c1、c3）；`closeAll` 等另一条连接的 `close()` 时，在途落点的句柄一直不释放（W3 评审探针 2）；`closeAll` 后落点交来进程时句柄被释放第二次。变异：遗忘谓词漏掉在途落点 → `entry.spec.ts`「a landing is still in flight」变红；删除条件不看「已关闭」 → 「still takes requests」变红；去掉某一步对端口 reject 的吸收 → `teardown.spec.ts` 含该步 reject 的组合变红（后续步不执行，`release` 抛出）；`stop()` 不吸收 reject，或停进程的循环在 reject 处中止 → 「every process is asked to stop」两例变红；新修订的条目接管早先修订的未确认进程时丢掉它们 → 「a process an earlier adoption revision left lingering」变红；先清进程或句柄字段再等端口 → 「the entry stays while its teardown waits on a port」对应一例变红；`closeAll` 先关闭再释放在途句柄 → `shutdown.spec.ts`「while the close of another entry waits」变红；关停不释放在途落点的句柄 → `teardown.spec.ts`「closeAll releases the process credential handle at once」变红；落点到时限才交给条目 → `shutdown.spec.ts`「for a landing still within its bound」变红；关停后超出时限的落点不释放句柄 → `shutdown.spec.ts`「outlives its bound after the shutdown began」变红；关停也释放已交来进程的落点的句柄 → `shutdown.spec.ts`「not for a landing that already handed over its process」变红，探索器报 P1（`P1-released-before-stop`）。

<a id="mc-15"></a>

- **MC-15 端口违约**（AV、UE、CU、PL、CS，契约 T9，W3 已定事项 4，接手裁定 K2）：端口应以 `Outcome` 答复。同步抛出与 reject 都是违约，同样处置：本包只经 `internal/port.ts` 的 `ask` 一处询问端口，`ask` 把违约读成该端口的违约答复，调用方像处理普通失败一样处理它。`ask` 的闭包只包端口调用：本包自己的计算在闭包外做，它的错误照常抛出，不读成端口违约（第 1 轮裁定 F4）。各端口的违约答复：
  - 采用、资格答 `unknown`：关口答 `unknown`（`inspect`、`refresh`、`release` 的拒绝，`list` 整次 `unknown`），`ensure` 重读采用答 `unknown` 且不建连。
  - 存储答 `unavailable`：标记清单的 `catalog` 是 `unavailable`，`refresh` 读写存储答 `unknown`。
  - 取凭据答 `unknown`（`credential-unavailable`），落点答 `unknown`（`landing-unavailable`），`open` 答 `not-sent`（`connection-unavailable`），`discover` 与 `listActions` 答 `no-answer`（`abandoned`）（契约 T9）。建连按 MC-5 的表收场。
  - 拆除的 `close()`、`stop()`、`release()` 按 MC-14。
  - 违约发生在时限之后时，当作什么也没交来。

  时限之后继续的工作（收场、迟到结果的收口）在连接表的任务作用域里运行，没有调用方等它。等待分两种：自己发起的工作经 `within`，到期交给作用域；别人拥有的工作（加入在途的建连、等同键在途的关闭或拆除）经 `waitAtMost`，到期只停止等待，结果与错误仍归它的拥有者。其中本包自己的编程错误由作用域记下，`closeAll` 关完全部条目之后以 `AggregateError` 交给调用方；`closeAll` 之后才出现的交给作用域的事后出口（MC-10、P7）。反例：采用端口 reject 使 `inspect` 抛出而不是答 `unknown`；拆除的一步同步抛出，后面的步骤不执行，句柄被重试的拆除释放第二次；迟到路径上的端口同步抛出，成为无人处理的拒绝；修订号用尽时标记清单的 `RangeError` 被读成存储不可用；`closeAll` 答复之后出现的本包错误无人知道。变异：`ask` 不吸收同步抛出 → `port.spec.ts`「throws when it is called」与 `port-breach.spec.ts`「a port that throws」变红，探索器 `throws` 场景报 P7；`adopted` 不经 `ask` → 「adoption rejecting at the gate」变红；`markUnavailable` 放回 `ask` 的闭包 → `ensure.spec.ts`「an error of this package while marking reaches the caller」变红；作用域关闭之后不交事后出口 → `port.spec.ts`「the task scope」与 `shutdown.spec.ts`「closeAll hands the errors of the background work」变红；作用域关闭时丢掉已记下的错误 → 同两处变红。

<a id="mc-16"></a>

- **MC-16 调用口**（S1、S2、S6、R2、R5、O1–O6、D1–D5，已定事项 28–30、32、33，调用口第 1 轮裁定 1–6）：`invoke` 与 `continueWithInput` 走同一个次序。从占位起，一次调用只有一个拥有者（`perform`）：发出之前的每次等待都在这次调用的停止信号下，键只在第 13 步收口一次。步号是本条自己的编号，用例标题与源码注释里的「step N」指它：
  1. 前提（R2）：`args` 不是 JSON 对象（`isActionArgs`），或 `ContinueRequest` 既没有 `requestState` 也没有 `inputResponses`（它什么也不能续，S2 只说各自可选），返回的 Promise 以 `TypeError` reject，不占位。
  2. 占位：在途表按（租户、主体文本、关联键）占位，查重与占位一步；重复答 `correlation-key-in-use`。占位交出停止信号：调用方的 `signal` 与 `cancel` 合成一个（MC-12）。从这里到发出，每次等待都在它下面：已触发的信号不起任何等待（不问端口、不建连）；等待中触发时等待结束，端口调用交给连接表的作用域；等待答复之后才发现它已触发也一样。三种情形都答「未发出：`cancelled`」；停止信号已触发时某一步的拒绝也答 `cancelled`，不答拒绝原因（S2：占位后、发出前收到的 `cancel` 使原调用答 `cancelled`）。
  3. 先判关停：`closeAll` 之后答「未发出：`connection-unavailable`」，不问端口，首次调用与续调用相同（S8）。再过关口 `admitForUse`（S1，MC-2）：拒绝原样作为原因；撤采用或被挡下时连接先关闭（MC-11）。
  4. 配值 `prepareSettings`（S4，MC-4）：拒绝或 `credential-unavailable`（`missing`）原样作为原因。
  5. 已知动作：读存储里的清单（不连接）。存储违约答 `unknown`（MC-15）；没有清单、动作不在清单里或不可用答 `action-unavailable`；`invoke` 的 `expectedDefinition` 与当前摘要不同答 `definition-changed`。次序是先存在与可用，再摘要。
  6. `continueWithInput` 另核代际：连接表里没有这个键的可用连接，或它的代际与 `issuedAt` 不同，答「未发出：`unknown`」，不建连、不发出（S2）：建连只会给出更晚的代际。
  7. 建连 `ensure`（MC-5），在停止信号下等待（`cancel` 与调用方的中止都立即结束这次等待，建连留给其他调用方，同 `refresh`）；失败按下表映射。`continueWithInput` 在 `ensure` 答复后再核一次代际，不同答「未发出：`unknown`」，新代际上 `call` 计数 0。
  8. 发出前最后核对停止信号：已触发答 `cancelled`，传输 `call` 计数 0。这是第 2 步规则在最后一次等待之后的实例。
  9. `transport.call(request, stop, observe)`：请求带 `continuation`（`requestState` 与 `inputResponses` 各自可选，只带 `requestState` 合法）；观察函数由本包包一层，它抛出时吞掉（S6）。`call` 违约（T9）当作已发出而效果未知：结局 `unknown`（`abandoned`），没有可取消的请求，键按已发出结束。`not-sent` 按下表映射；其中 `connection-unavailable` 而停止信号已触发时是传输对已触发信号的答复（T5），连接不转 `lost`；停止信号已触发时答复按第 2 步是 `cancelled`。转 `lost` 时连接当即拒绝请求，拆除与清单标记交给连接表的作用域，调用不等它们：调用的答复只取决于传输的答复，不报告拆除的结果（`loseInScope`）。反例：转 `lost` 时 `close()` 挂起，调用一直不答复。
  10. `markSent(key, connection, 发出代际)`（MC-12）：发出代际是 `ensure` 交出的代际，所以 `call` 返回之前连接换代重建时，之后的 `cancel` 答 `unknown`、不告知对端。
  11. 在停止信号下等应答（`waitAtMost`）。信号先触发（占位后到这里之间的 `cancel` 或调用方的中止，含落在发出与登记之间的）：`cancelRequest(requestId)` 一次，交给连接表的作用域，不等它答复，结局 `unknown`（`abandoned`）；迟到的应答没有人读。应答 reject（T9）当作 `no-answer`（`abandoned`）。
  12. `classifyOutcome(answer, { issuedAt: 发出代际, outputSchema: 已知动作的, checkOutput: ports.checkOutput })`（O1–O6），内容经契约的 `toContentBlocks`（D1–D5），本包不改写；`checkOutput` 抛出由契约吸收成 `violates`（`output-check-failed`，O3），调用照常答 `sent`。结局 `unknown` 的子因是 `stream-broken` 或 `process-exited` 时连接按 S7 转 `lost`（下表最后一行），拆除同第 9 步交给作用域；`abandoned` 是本方放弃，不转。`task` 结局登记进任务表（MC-17）。
  13. 收口（`conclude`，MC-12），在 `perform` 的一个 `finally` 里，本包的编程错误也经过它：已发出 → 键转为已结束；未发出且停止信号已触发 → 键转为已结束，之后的 `cancel` 答 `no-call-in-flight`；未发出且未触发 → 撤销占位，键立即可再用，之后的 `cancel` 答 `unknown`。

- **MC-17 任务操作**（S2、S8、R7、T6，已定事项 31 与闭包规格第 5、6 条，调用口第 1 轮裁定 5、7 与修复轮规格第 8 条）：四个操作走同一个次序：
  1. 先判发起者与任务本身：任务表按（租户、主体文本、持有、任务号）查，表里没有（非发起者、另一租户、不存在的任务、重启之后）答 `Refusal` 的 `unknown`，`toStrictEqual` 同一值，不问任何端口。表里有、但 `TaskRef.issuedAt` 与记下的发起代际不同时，也答 `unknown`：那不是这个任务，与表外任务相同，不问端口、不发请求。
  2. 再判关停：`closeAll` 之后答 `effect-unknown`（`no-connection`），不问端口、不复用连接（S8）。
  3. 连接：任务表记下发起时的对端账号；任务的连接身份是（租户、持有、对端账号），即连接键的三项投影，有意不含采用修订：采用修订变了而账户没变时，任务仍属于同一账户。同租户同持有下对端账号相同的可用连接直接复用，不核采用与资格，不问端口。没有时经关口新建（`decideForUse`，撤采用或被挡下时先关闭连接，MC-11）：采用不可读答 `unknown`；未采用、正文不能解析、资格不是 `granted`（含 `unknown` 与被挡下）、S4 的配值缺陷与 `credential-unavailable`（`missing`）都答 `effect-unknown`（`no-connection`），不建连；新连接的对端账号与记下的不同（账户变了）时答 `effect-unknown`（`no-connection`），不建连、不发请求。`ensure` 的失败：任务请求没有发出，所以 `effect-unknown` 只留给 S2 的「不能新建」，建连没有交出连接时答 `ConnectionFailure`。`settings` 阶段：重读采用 `unknown` 答 `unknown`；时限先到或建连途中关停的 `connection-unavailable` 原样；其余（重读采用的 `not-available-to-you`、配值缺陷、凭据缺失）答 `effect-unknown`（`no-connection`）。`connect` 阶段：`ConnectionFailure` 原样；`EffectUnknown`（`discover` 无应答）答 `connection-unavailable`，同 MC-16 的表。`cancelTask` 与其他三个相同（契约 S2，晚于已定事项 31）。
  4. 请求在连接时限下等待（时限种类 `task`，来源同 MC-5）：时限先到当作 `no-answer`（`abandoned`），迟到的应答交给作用域、没有人读；传输方法违约（T9）同样。`not-sent` 按 MC-16 的表转 `lost`，答对应的 `ConnectionFailure`（`connectionFailureOf`，与调用口同一处）；`no-answer` 答 `effect-unknown` 带同一子因，`stream-broken` 与 `process-exited` 转 `lost`；转 `lost` 的拆除同 MC-16 第 9 步交给作用域，操作不等它；`error-answer` 与 `answer-malformed` 原样交出。
  5. 答复：`queryTask` 交出 `TaskReport` 或 `expired`；`taskResult` 对 `finished` 用 `classifyOutcome`（代际是这次请求的连接代际，`outputSchema` 是登记时已知动作的），`not-finished`、`expired`、`cancelled` 原样；`provideTaskInput` 答 `accepted`；`cancelTask` 答 `requested`。分类在 `ask` 之外（MC-15）：`ask` 只包传输的方法，答复之后才读它；`checkOutput` 抛出由契约吸收成 `violates`（`output-check-failed`），不读成 `effect-unknown`。

  反例：账户 A 发起的任务经账户 B 的凭据查询；非发起者由「任务不存在」与「不是你的」两种答复区分出任务是否存在；复用连接时又问了一次资格；对端不答时 `queryTask` 永不返回；新建连接时 `discover` 无应答答 `effect-unknown`（`stream-broken`），而任务请求没有发出；`checkOutput` 抛出时答 `effect-unknown`（`abandoned`），而对端已答；`issuedAt` 对不上的引用照样发请求。变异：任务表键去掉主体 → `tasks.spec.ts`「another principal」变红；去掉租户 → 「another tenant」变红；去掉账户比较 → 「another peer account」变红；复用分支去掉 → 「reuses the existing connection」变红；采用不可读也答 `no-connection` → 「unreadable is unknown」变红；资格非 `granted` 也建连 → 「eligibility granted」变红；关停检查去掉 → 「after closeAll」变红；先复用再判关停 → 没有用例变红（C37，等价变异：`closeAll` 在让出事件循环之前同步关闭每个条目，关停之后没有可复用的连接，次序只由本条与源码的阅读保证）；`no-answer` 子因改成 `abandoned` → 「no answer is effect-unknown」变红；请求不受时限 → 「bound cuts off」变红；表外任务也发请求 → 「task not in the table」变红；不核 `issuedAt` → 「an issuedAt other than the recorded one」变红；建连阶段的 `EffectUnknown` 原样交出 → 「a discover without an answer」变红；`settings` 阶段的 `connection-unavailable` 答 `no-connection` → 「a shutdown under way」变红；分类放回 `ask` → 「a checkOutput that throws」（契约吸收之后由 C 序列的契约变异配合）变红。

## 所有权、失败与生命周期

- 连接表拥有每条连接的 `Connection` 聚合、MC-14 列出的五项资源与任务作用域。调用口拥有在途表与任务表：在途表项记占位、发出代际与连接视图、这次调用的停止信号，任务表项记发出代际、对端账号与输出 schema；两张表与连接表都由 `createMcp` 的一次装配共享。一次调用从占位到收口只有一个拥有者 `perform`（MC-16）：每次等待在它的停止信号下，键在它的一个 `finally` 里收口一次，所以任何路径（端口违约、`checkOutput` 抛出、`lose`、`closeAll`、建连失败、本包的编程错误）都不遗留占位；发出后告知对端的 `cancelRequest` 归连接表的作用域。
- `Connection` 聚合只做状态转移，不做 I/O；非法转移是 `TypeError`，表示本包的编程错误，不是对端或端口的失败。条目何时离开表见 MC-14。
- 凭据句柄每条连接恰好取得一次、释放一次，端口违约时也成立：进程句柄在携带它的进程的 `stop()` 答复之后释放（时限后才交来的进程也是），HTTP 句柄随传输关闭释放，没有进程的准备失败时立即释放。在途落点的句柄随落点记录走，先到的一方（迟到进程停止之后，或关停）释放它，另一方找不到它；落点交来进程之后，关停不再释放它（MC-14）。
- 进程由连接表收口，时限后才交来的进程也由它停止一次。`stop()` 的确认范围只记在视图的 `residual` 上；调用了 `stop()` 不证明进程已停。未确认停止的进程留在条目里，下一次关闭或重建前再次请求停止。等待迟到落点的条目在关闭后仍保留，直到落点答复（成功、失败或 reject）。
- 外部效果：进程启动与传输打开是外部效果。关闭不可逆；一次失败的准备可能留下进程，它作为 `residual` 报告给宿主。`closeAll` 是本实例的关停：之后不再建连，要连接的操作答复如下：`refresh` 答 `connection-unavailable`；`invoke` 与 `continueWithInput` 答「未发出：`connection-unavailable`」，不问端口（MC-16 第 3 步）；任务操作答 `effect-unknown`（`no-connection`，MC-17 第 2 步）。
- 端口违约：端口应以 `Outcome` 答复；同步抛出与 reject 是违反契约的提供者，经 `ask` 读成该端口的违约答复（MC-15）；关闭次序的三步按 MC-14；时限后的违约当作什么也没交来。时限之后继续的工作归连接表的任务作用域；其中本包的编程错误由 `closeAll` 交出，`closeAll` 之后才出现的交给作用域的事后出口。
- 并发：同一键的并发 `ensure` 加入同一次建连，各自只等到自己的时限；同一键的关闭也只有一次在进行，拆除只有一次（`lose`、准备失败、重建与关闭共用）；同一租户同一持有的 `ensure` 串行决定哪个修订的条目存在。排队等临界区、临界区里的采用重读、等其他修订的关闭、等同键的关闭或拆除，都受这次 `ensure` 的临界区时限约束，超时答 `connection-unavailable`，不再等着或占着临界区。并发 `refresh` 各自取页，发布边界与存储的条件写入保证只有一份发布，另一份 `kept`（`superseded`）。迟到的结果按产出它的代际识别，不改变新连接。连接表的操作在一个事件循环内串行化状态变化，没有锁。
- 取消：调用的取消有两个来源，调用方的 `signal` 与 `cancel`，从占位起合成一个停止信号，发出前的每次等待（关口、存储读取、建连）都在它下面：发出前触发答「未发出：`cancelled`」，键转为已结束；发出后触发告知对端一次（`cancelRequest` 交给连接表的作用域，不等它）、结局 `unknown`（`abandoned`），迟到的应答没有人读（MC-16）。任务操作没有调用方的信号，只受连接时限（MC-17）。刷新的取消：调用方的 `signal` 只属于这一次 `refresh`：等待建连、取页与发布边界各自核对它，答 `kept`（`cancelled`）；建连本身只受建连时限约束，由同键的调用方共享。取消已取得的页不撤销对端效果；取消只阻止发布。
- 时限：每个时限的上界都是这次请求的连接上界（MC-4）。`ensure` 入口起一个临界区时限，覆盖排队、重读与临界区里的等待。开始建连的调用另起一个建连时限，从 `attempt()` 之后起覆盖建连的每一次等待，含失败或关停之后的收场；加入在途建连的调用另起一个，从加入起计时。取页阶段再另起一个，每个任务请求也另起一个（MC-17）。调用的等应答不受时限，只受停止信号（MC-16）。时限由表的时限来源取得，缺省 `AbortSignal.timeout`；测试注入能逐个触发的时限。一个 `ensure` 自己的时限都到期之后，它不再等任何端口（P8 T2），时限之间的长短与到期次序不限。端口不尊重信号时连接表自己放弃等待，迟到的结果被收口（句柄释放、进程停止并记录未确认的范围、传输关闭）。
- 已知限制（本版本）：
  - 端口质量前提：采用端口对同一次读取给出旧答复时（AV5 要求正文或配值一变修订就变，端口若延迟兑现），旧修订的令牌会短暂建起旧连接，随即被新修订的 `ensure` 关闭。本包按端口的答复行事，不能识别答复本身是旧的；这项由端口实现方保证。
  - 拆除的端口挂起：`close()`、`stop()` 或 `release()` 不答复（不是 reject）时，等这次拆除结束的调用也不答复：`closeAll`、`release`、关口在撤采用或被设置挡下时的自动关闭（MC-11），以及等 `lose` 的 `refresh`（它报告清单标记）。原因：它们报告确认的停止范围或标记，所以要等这些端口（P8 A1）。调用与任务操作不等拆除（MC-16 第 9、12 步，MC-17 第 4 步）。宿主应以自己的期限包住 `closeAll`。`ensure` 不受影响：它只等到自己的时限（MC-5）。
  - 时限先到时的清单标记：失败答复里的 `catalog` 是 `pending` 时，答复的调用不知道标记的结果。建连时限先到时，标记在任务作用域里继续，它的结果（含存储不可用或修订冲突）不再报告给任何调用方；加入时限先到时，建连仍归开始它的调用，结果只报告给那个调用。之后读清单的调用看到的是存储里的实际记录。
  - 报告与状态视图不一致：落点仍在途时，`release` 与 `closeAll` 报该连接的进程范围为 `unconfirmed`，而关闭之后 `status.inspect` 报 `none`。原因：`Residual` 只有进程一种，进程还没交来时没有可报的项；`Residual` 归契约，本波不改。落点永不答复、又没有 `closeAll` 时，它带走的进程凭据句柄一直持有，直到关停。
  - 在途表、任务表、连接表不跨重启（S2 已知限制）：重启之后，旧的关联键 `cancel` 答 `unknown`，旧任务的四个操作答 `unknown`。
  - 调用方的 `signal` 在发出后触发时，`cancelRequest` 只告知对端，不证明对端已停止；对端效果未知。`cancelRequest` 本身在连接表的作用域里运行，没有上界：一个永不兑现的 `cancelRequest` 不拖住调用，但在作用域里一直存活到进程结束；它经 `ask` 询问，违约不成为本包错误。
  - `refresh` 的关口与存储读取不在调用方的 `signal` 下等待（`discovery.ts`）：只有建连、取页与发布边界核对它。关口或存储不答复时，中止的 `refresh` 在那一步不返回。调用口没有这项限制（MC-16 第 2 步）。

## 性质与证据

本节把连接表生命周期与调用口的关键性质写成定理，并分别记录每条性质的证据与状态。定理是目标。状态只说明所列证据在其范围内得到的结果，不是证明。模型动作、探索器动作与实现代码的映射、运行命令、规模上限与运行记录见 [verification/README.md](verification/README.md)。生命周期的模型是 [verification/models/ConnectionTable.tla](verification/models/ConnectionTable.tla)，调用口的模型是 [verification/models/Calls.tla](verification/models/Calls.tla)，对真实实现的有界穷举探索器在 [tests/model/](tests/model/lifecycle.spec.ts)（生命周期场景 `lifecycle.spec.ts`，调用口场景 `calls.spec.ts`）。

对象与参与者：

- 一个 `createConnectionTable` 实例（`createMcp` 的一张表），它的条目，以及条目持有的五项资源：传输、进程句柄、凭据句柄、未确认停止的进程、在途的落点。
- 驱动它的调用：`ensure`、`close`（`release` 与自动关闭用它）、`closeAll`、`lose`。
- 调用口（P9–P14）：同一张表上的 `createCalls` 与 `createTasks`，它们共享的在途表与任务表；驱动它们的调用：`invoke`、`continueWithInput`、`cancel`、调用方的 `signal`（中止）、四个任务操作。
- 端口调用：重读采用、取凭据、落点启动、打开传输、`discover`、`close()`、`stop()`、句柄 `release()`、标记清单时的存储读取。调用口另有：关口的采用读取与资格核对、清单读取、标记清单时的存储写入、传输的 `call`、对端对已发出请求的应答（`SentCall.answer`）、`cancelRequest`、四个任务方法。
- 范围是 stdio 端点带进程凭据。这时五项资源都会出现。

端口失败模型 F：每次端口调用可以 (1) 按契约答复，(2) 答复它类型里的失败，(3) reject，(4) 被调用时同步抛出，(5) 永不答复，(6) 在时限到期之后才答复。`stop()` 另可答 `unconfirmed`。(3) 与 (4) 是违约的提供者，MC-15 把两者读成同一种违约答复。对端的应答是传输交出的 promise，不是方法，所以它没有 (4)。下列定理在 F 下陈述。

两种证据共同的前提：

- 客户调用只在静止时到达：一次事件循环轮次只有一个外部动作（客户调用、端口答复或时限到期），之后内部步骤一直运行到没有可运行的。
- 生命周期场景里存储的读取总答 `absent`，所以标记清单不调用 `store.write`；写入的挂起、违约与修订冲突没有覆盖，由 `refresh.spec.ts` 与 `port-breach.spec.ts` 的用例承担。调用口场景里存储持有一份清单，含一个可用动作 `read`，没有输出 schema；标记清单时的写入是一次端口调用，可以挂起或违约。
- 调用口场景里每个主体的调用都用同一个关联键 `c`，对端答复一个空的完整结果，或任务 `t1`（由场景指定）。
- 一次事件循环轮次只有一个外部动作，所以「端口答复与停止信号落在同一轮」的交错（`under` 在答复之后再核一次停止信号，修复轮的变异 C50）两种证据都表达不了；它由实现的那一行守住，没有变红的用例。

时限的到期次序：TLA+ 模型里各时限的上界相同，先建立的先到期。探索器的 `bounds` 场景让任何一个时限都可以下一个到期，所以覆盖上界不同的情形；其余场景同模型。

公平性前提：

- WF1：每个时限最终到期。
- WF2：promise 的反应最终全部运行，事件循环不被饿死。
- WF3：每次端口调用最终答复。只有 P8 T1 用它。
- WF4：每次端口调用最终答复，停止信号已触发的请求的对端应答除外，对端可以不答它。只有 P14 T1 用它。
- WF5：传输的 `call` 在停止信号触发之后最终答复（契约 T5：以 `not-sent` 答已触发的信号，或已经发出）。P14 T2 用它。

定理（在 F、WF1、WF2 下，另写前提的除外）：

- **P1 句柄守恒**：任何可达状态下，每个凭据句柄的 `release()` 至多被调用一次，并且只在 `release()` 时已交来的、携带它的每个进程的 `stop()` 都答复之后调用（S9）。关停例外：在途落点的句柄在 `closeAll` 时释放，这时进程还没交来；之后交来的进程照样停止一次（MC-14）。WF3 成立且 `closeAll` 已答复之后，每个取得的句柄恰好被调用一次。
- **P2 遗忘安全**：条目离开表时不持有五项资源中的任何一项，之后也不再被写入资源。可观察的形式：状态视图对一个键报 `none`，且这个键没有在途的调用与端口调用时，这个键取得的句柄都已释放，传输都已关闭，进程都已确认停止。
- **P3 每个进程都被要求停止**：落点交出的每个进程（时限内或迟到）在它的条目离开表之前，并在 `closeAll` 答复之前，至少被调用一次 `stop()`。
- **P4 关停之后不建连**：`closeAll` 被调用之后，不再调用 `ProcessLanding.start` 与 `McpTransportFactory.open`，之后答复的 `ensure` 也不交出连接（已定事项 23）。
- **P5 键隔离**：为一个连接键发出的每次端口调用只涉及这个键。`ensure` 只答复这个键的传输。条目只持有它自己的键的资源。所以不同租户或对端账号永不共用一个条目。
- **P6 迟到不覆盖**：时限到期之后才到的端口答复，以及处理它时发起的端口调用的答复，不改变消费者可见的状态：`current`，与 `stateOf` 去掉 `residual` 之后的部分。迟到的答复指建连等待的五个端口：重读采用、取凭据、落点启动、打开传输与 `discover`。拆除与标记清单的端口调用在时限之后由条目继续，它们的答复是条目自己的收口，不算迟到。P6 的投影把关闭后只为报告 `residual` 而保留的条目算作 `none`（状态视图对它报 `lost`（`close-unconfirmed`），MC-9），所以迟到交来的进程未确认停止时，投影从 `none` 变成 `lost` 带 `residual` 是允许的。对不是当前代际的 `lose` 答 `not-current`，不改变状态。「迟到结果不发布」归 `refresh` 的发布边界（MC-7），本节的证据不覆盖它。
- **P7 错误不静默、不崩溃**：每个异步副作用的失败都有去向：交给等它的调用方，记在条目上可被观察，或在没有调用方等它时由任务作用域记下、经 `closeAll` 交出；`closeAll` 关闭作用域之后才出现的，交给作用域的事后出口。不存在未处理的拒绝。本包的非法转移（`TypeError`）不发生。「不崩溃」针对端口与对端的行为：端口的失败经 `ask` 成为类型化的结局，不会到事后出口。事后出口只收本包自己的错误，本性质断言这种错误不发生；缺省出口把它作为未捕获的异常抛出，让缺陷显形，不把它藏起来（MC-10）。
- **P8 等待有界**：
  - P8 T1（WF1、WF2、WF3 下）：每个 `ensure`、`close`、`closeAll`、`lose` 最终答复。
  - P8 T2（只要 WF1、WF2，端口可以挂起）：一个 `ensure` 自己的时限（临界区一份；开始建连时的建连时限一份，或加入在途建连时的加入时限一份）都到期之后，它不再等任何端口就答复。各时限的上界与到期次序不限。
  - P8 A1（反定理）：拆除的端口或在途建连的端口挂起时，`close`、`closeAll`、`lose` 与关口的自动关闭可以一直不答复。原因：它们报告确认的停止范围，所以要等这些端口。这是已知限制，见上文「已知限制」中「拆除的端口挂起」。

调用口的定理（MC-16、MC-17；在 F、WF1、WF2 下，另写前提的除外）。「调用」指一次 `invoke` 或 `continueWithInput`；「发出」指传输的 `call` 答 `ok`（交出 `SentCall`）；「停止信号」指 `cancel` 对这次调用答 `signalled`，或调用方的 `signal` 触发：

- **P9 发出前不发**：调用答「未发出」时，它的 `call` 没有被调用，或被调用并答了 `not-sent`。调用答「已发出」时，它恰好调用了一次 `call`。停止信号在这次调用还没有调用 `call` 时到达，则之后它的 `call` 计数仍为 0，或答 `not-sent`。
- **P10 取消至多一次**：`cancelRequest` 只对 `call` 答 `ok` 交出的请求号调用，每个请求号至多一次。调用了它的调用答「已发出」，结局 `unknown`（`abandoned`）。
- **P11 占位守恒**：每个占位恰好 `conclude` 一次（`perform` 唯一的 `finally`，MC-16 第 13 步）：已发出或停止信号已触发的占位结束，其余撤销。调用答复时它的占位已结束或已撤销。占位只由占用它的调用结束。`reserve` 答 `in-use` 时，同键有另一个还在等的调用持有占位。静止（没有待决端口调用、没有时限）时没有占位未结束，所以答「未发出」的调用的关联键立即可以再占；端口违约、`lose`、`closeAll` 与建连失败都不遗留占位。探索器核对 P11 时，键的身份由探索器按（租户、主体文本、关联键）给出，经在途表的计数视图看每次占用、撤销与结束；实现的键文本把两个键合并时，`in-use` 落在另一个键的持有者上，报 P12，不是 P11。
- **P12 隔离**：在途表按租户与主体隔离，任务表按租户、主体、持有与任务号隔离。另一主体或另一租户用同一关联键 `cancel`，答 `unknown`，不触发端口调用，不停止别人的调用。非发起者的任务操作答 `unknown`，不触发端口调用。任务操作只在与记录相同的键（租户、持有、对端账户）的连接上发请求；同租户同持有下另一账户的连接不被复用。
- **P13 关停之后不发**：`closeAll` 被调用之后不再调用传输的 `call`。`closeAll` 之后开始的调用答「未发出」。
- **P14 有界答复**：
  - P14 T1（WF1、WF2 与 WF4 下）：每个调用与任务操作最终答复。探索器的形式：静止时每个调用与任务操作都已答复。
  - P14 T2（只要 WF1、WF2 与 WF5，其余端口可以挂起；P8 T2 的全局形式）：停止信号已触发的调用，在全部时限到期之后已答复，不再等传输的 `call` 以外的任何端口。调用在传输报告「没有发出」之前不能答「未发出」，所以对 `call` 的等待是传输的前提（WF5），不是调用口的时限。任务操作自己的时限（任务请求的时限，与它建连的时限）都到期之后已答复。
  - 在修复轮（`w3-mcp-call-fix1` 与 `1a143a4d4`）之前的实现对调用一句有反例，见 [verification/README.md「发现」](verification/README.md#发现)；本页修订的实现没有。
