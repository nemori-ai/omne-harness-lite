# verification

本目录承载连接表生命周期与调用口的性质证据：TLA+ 模型、模型与实现之间的映射、运行命令、判读规则与负控。性质 P1–P16 的定理陈述与各自的证据状态归 [SPEC.md「性质与证据」](../SPEC.md#properties)，本页不重复定理。对真实实现的有界穷举探索器在 [tests/model/](../tests/model/lifecycle.spec.ts)（生命周期场景）与 [tests/model/calls.spec.ts](../tests/model/calls.spec.ts)（调用口场景），它是本页第二种证据。

## 两种证据与各自范围

| 证据            | 是什么                                                                                                                                                                             | 能支持的结论                                               | 不能支持的结论                                       |
| --------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------- | ---------------------------------------------------- |
| TLA+ 模型与 TLC | [models/ConnectionTable.tla](models/ConnectionTable.tla)：连接表的行为模型；[models/Calls.tla](models/Calls.tla)：调用口的行为模型，连接表只剩抽象。TLC 穷举每个配置的全部可达状态 | 在配置的上限内，模型满足或违反所列性质                     | 实现符合模型、上限之外的规模、模型省略的部分         |
| 有界穷举探索器  | `tests/model/`：驱动真实的 `createConnectionTable`，以及同一张表上真实的 `createCalls` 与 `createTasks`，端口是可编程替身。宽度优先枚举上限内的全部调度                            | 在场景的上限内，本包的源码在所列可观察投影上满足或违反性质 | 真实传输、进程与存储，上限之外的调度，投影之外的状态 |

两种证据之间没有精化证明。对应关系由下面的映射，以及两边对同一类缺陷的负控（[负控](#负控)）支持。

## 动作映射

一次事件循环的一轮是一个外部动作，之后的内部步一直运行到没有纤程可运行。模型把这叫 `Quiescent`。探索器在每次选择之后等一次 `setImmediate`，于是全部 promise 反应运行完，Node 也报告完未处理的拒绝。所以两个模型与探索器的外部动作都只在静止时发生，落不到两次内部步之间的微任务窗口；这些窗口由服务层的逐微任务扫描用例检查（[未覆盖](#未覆盖)）。

两边的端口失败模型一一对应：答复、失败、reject、`unconfirmed`、同步抛出、挂起（永不选择答复）、迟到（先选 `fire` 再选答复）。

模型的抽象：

- 一次内部步是一个异步函数在两个 `await` 之间的同步部分。同一个键的纤程的内部步以任意次序交错，是微任务先进先出次序的超集。不同键的纤程不共享条目、轮次与资源，所以它们的内部步按键的固定次序运行（偏序约简）。
- 一次受时限的等待，在工作已结束且时限已到期时两种结局都探索（实现在时限已到期时直接答 `expired`）。
- 时限的上界相同，先建先到期。模型里排队的调用在队里不看自己的时限，加入的调用不另起自己的时限。模型检查的 P8 T2 是全局形式：全部时限都到期之后，没有 `ensure` 还在等。这两处省略不影响全局形式，因为全部时限到期时，它们所等的调用也已答复。逐个 `ensure` 的形式（自己的时限都到期就答复；正在等而一个自己的时限都没起，也算违例）只由探索器检查：每个场景都检查，`bounds` 场景另让上界不同的时限以任意次序到期。
- 键是抽象的：模型不建键怎样从租户、修订与对端账号推导。两个键的配置不触发时限，迟到路径只在一个键的配置里检查。
- 只建 stdio 与进程凭据，一个采用修订，一个对端账号。不建 HTTP、`degraded` 与 `settle`、资格、清单与发布、存储写入、关闭报告的范围值。
- 建连的 `ready` 与 `ensure` 的答复（`joinedW`）之间没有外部动作，所以模型里关闭落不到两者之间，`P16_NoOkAfterClose` 成立不依赖代码在答复兑现时的再核（`settledAnswer`）。代码里两者之间有几个微任务，由 `ensure.spec.ts` 的逐微任务扫描检查。

`Calls.tla` 的抽象与范围上限：

- 连接表只剩每个键的「可用、代际」与关停。`ensure` 是一个端口：`ok` 使连接可用（建连给下一个代际，复用保持代际），`fail` 是任何拒绝或时限到期，关停之后只答 `fail`。它的内部步骤、时限与五项资源归生命周期模型；两个模型之间没有组合证明。
- 关口的采用读取、资格核对、配值与清单读取合为一个端口 `gate`。`lose` 立即生效，实现里拆除交作用域（`loseInScope`），两边都不让调用等它；`closeAll` 只置关停并清空连接。`cancelRequest` 在模型里是无人等的待决调用（`owner = 0`），对应 `scope.spawn`。
- 传输的 `call` 在停止信号触发之后最终答复是前提（WF5）：`P14_BoundedAfterStop` 不把等在 `callW` 的调用算作卡住；探索器同样不把只等自己 `transport.call` 的已停止调用算作违例。WF5 是对传输的前提，依据契约 [T5](../../mcp-contract/SPEC.md#port-transport)「`call` 在 `signal` 触发后结算」一句（成员 SPEC [WF5](../SPEC.md#properties) 同此）。
- 连接是否仍接受请求的读取点（MC-10、P16）：模型在 `AfterEnsure` 与 `Abandon` 读 `Takes(k, gen)`；代码在发出（第 8 步）、取每一页、任务请求与 `cancelRequest` 之前经 `Ensured.wire` 读它，与发出在同一段同步执行里。模型里 `ensure` 的答复与发出在同一步，关闭落不到两者之间；代码里两者之间有几个微任务，落在其中的关闭由 `invoke.spec.ts`「step 8: at whichever microtask the close of the connection begins」逐个微任务扫描。
- 关停的读取点：模型在 `gateW`、`tgateW` 的关口答复之后读 `shut`；代码在下一次等待之前（`under`）、任务操作的入口、`refresh` 的入口、读存储之前与发布边界之前读它（发出、取页与任务请求之前由 `wire` 接住，`closeAll` 关闭每条连接），并在三个出口各读一次来决定答复（[关停与停止的判定点](#关停与停止的判定点)）。两边对「关停之后不问端口」的可观察结果相同，对答复不相同：模型的 `Refused` 不带原因，只覆盖「不问端口」，答复一侧由探索器（P13 的 `P13-answer-after-closeAll`）与服务层用例守住。
- 任务键碰撞（同主体在同一持有的两个账户上得到同一个任务号）模型写不出来：四个键里没有两个同租户同主体的键。P12 的这一句由探索器的 `task-collision` 场景承担（模型未覆盖）。
- 键、租户、主体与账户是常量表，不建它们怎样推导。关联键只有一个 `c`，任务只有一个 `t1`，每个键的调用与任务操作的次数是常量。
- 所有键的纤程以任意次序交错，没有偏序约简。
- 对端对已发出请求的应答是一个端口调用；它不能同步抛出。

探索器的近似：

- 状态按投影去重：消费者可见的表、待决调用及其调用点（`src/` 的函数栈）与是否迟到、时限、账本与预算。投影不含 promise 的续体。用例「the projection」在 `throws` 场景上核对去重与不去重找到同一组违例及其最短深度。
- 每次重放都核对路径与上一状态的投影。重放离开记录的路径时，探索器抛出 `Nondeterminism` 并停止，所以一次通过的运行同时说明：在这些调度下实现是确定的。
- 每个键有自己的采用视图，所以几个键的采用修订相同：`two-keys` 的两个键只差租户，`two-accounts` 的两个键只差对端账号。只差对端账号时，两个键的 `stateOf` 是同一个（同租户同持有），所以 P2 的可观察形式在两个键都为 `none` 时才检查。
- 调用口场景里，在途表是真实的 `InFlightCalls`，经一个只计数的子类 `CountedInFlight` 观察（`reserve` 调用 `super` 后报告，并交出包了一层的占位句柄：句柄的 `recordSent` 与 `conclude` 各自调用原句柄后报告给运行）；任务表是真实的 `TaskTable`。P11 读这个计数视图，其余性质只读操作的答复与端口账本。
- 调用口场景的存储持有一份清单（一个动作 `read`，没有输出 schema），所以 `lose` 的标记清单会写存储：`store.write` 是一个端口。生命周期场景的存储照旧答 `absent`。
- `transport.answer` 是对端对已发出请求的应答，在探索器答复 `transport.call ok` 的那一步建立，归属于发出它的操作。任务请求的时限在请求发出之后才建立（MC-17 的参数次序），探索器把它附到那次请求上，所以任务端口的迟到答复也受 P6 检查。
- 「新建连接的账户变了」在探索器里不可达：每个键的凭据固定。它只由 `Calls.tla` 的负控 `calls-bad-task-any-account` 在复用一路覆盖，探索器的 `task-account` 场景覆盖同一路。
- 调用点 `site` 只用函数名与文件名。探索器每次脚本化端口调用都读 `new Error().stack`；取栈时它把格式临时换成 V8 自己的逐帧格式，取完换回。vitest 装的格式化器会对每一帧做 source map 映射，这一步的开销随调用次数增长，会让慢层逼近用例的时限；两种格式给出同一个 `site`。

## 关停与停止的判定点

关停（`closeAll` 已开始）与停止（调用方 `signal` 或 `cancel` 已触发）是同一种外部事件：它让一次操作结束。答复因此在出口一处，从当时的状态读出，不由「下一步碰巧是什么」决定。途中各点只负责「关停之后不开始下一步、不问端口」，不决定答复；它们交出哨兵（调用口的 `STOPPED` 与 `SHUT`，任务操作与 `refresh` 的 `SHUT`）。

为什么不在每次等待之后再核一次：等待的答复与停止信号或关停可以落在同一轮事件循环里，`under` 返回之后到发出之前还有几个微任务，再核一次关不上这个窗口。模型与探索器一次事件循环轮次只有一个外部动作，表达不了这种交错，所以下面的点由服务层用例守住。

三个出口各读一次，次序如下：

| 出口                                                                        | 次序                                                                                                                                                                    |
| --------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 调用口：`calls.ts` 的 `answerAtExit`，由 `perform` 调用（MC-16 第 2、3 步） | 已发出的结局不改；调用的停止信号（调用方 `signal` 与 `cancel` 合成）已触发，答「未发出：`cancelled`」；否则关停已开始，答「未发出：`connection-unavailable`」；其余原样 |
| `refresh`：`discovery.ts` 的 `answerAtExit`（MC-7）                         | 已发布的结果不改；调用方 `signal` 已中止，答 `kept`（`cancelled`）；否则关停已开始，答 `connection-unavailable`；其余原样                                               |
| 任务操作：`tasks.ts` 的 `outcomeOf`（MC-17）                                | 没有调用方信号。已发出的结局不改；没有发出而关停已开始，答 `effect-unknown`（`no-connection`）；其余原样                                                                |

逐微任务扫描的做法：`closeAll`（或 `cancel`、关闭）依次落在第 0 到第 k 个微任务，每次核对落下之后没有开始新的一步、答复符合出口的次序。一步从哪个端口调用开始，按端口出现的序次判定；已开始的一步做完。k 取到扫描在最后几个微任务上不再看到新的端口调用为止。

## 未覆盖

- 真实传输、真实进程、真实对端与耐久存储：真实组合未验证。
- HTTP 端点、`degraded` 与 `settle`、换采用修订（不变式 6）、资格、`refresh` 的发布：两种证据都不覆盖，由既有用例承担。
- 上限之外的调度：例如一个键 3 次 `ensure`，或两种偏离同时出现；调用口的场景每个主体一个关联键、一个任务。
- 调用口：HTTP 端点、输出 schema 与 `checkOutput`、`inputRequired` 结局与真实的继续、任务表与在途表跨重启、授权发现的 `not-sent`：两种证据都不覆盖，由既有用例承担。「新建连接的账户变了」只在模型里。
- `close` 与 `closeAll` 把关闭条目（`closeAll` 另有放弃落点）时的本包错误收进 `AggregateError` 的一路：端口经 `ask` 不会让这些步骤拒绝，只有本包自己的缺陷会走到这里，所以没有不往本包注入缺陷就能触发的用例。任务作用域记下的本包错误一路有用例（P7）。
- S8 的关停先判：探索器不区分「关停之后问没问端口」。P13 禁传输的 `call`，并断言答复一侧；关停之后 `ensure` 本来就拒绝，所以去掉等待前的那一判在探索器上没有新签名。各点由[关停与停止的判定点](#关停与停止的判定点)的用例守住。
- 任务键碰撞（P12 的一句）：模型未覆盖，由探索器的 `task-collision` 场景与 `tasks.spec.ts` 承担。
- P16 的几处（MC-10）：两个模型与探索器的外部动作都只在静止时到达，所以两个微任务窗口它们落不到。建连 `ready` 与 `ensure` 答复兑现之间的窗口由 `ensure.spec.ts` 的逐微任务扫描承担。`ensure` 的答复与发出之间的窗口（模型里两者在同一步）由 `invoke.spec.ts` 的逐微任务扫描承担。`listActions` 一侧探索器不驱动，由 `refresh.spec.ts` 承担。持有内多条连接同时关闭、建连在途时不遗忘，探索器不变红，由 `ensure.spec.ts`、`entry.spec.ts` 承担，后者另有模型的 `bad-forget-building`。
- P15（不带 `unusable` 的失败不让就绪连接转 `lost`）：模型未覆盖。`Calls.tla` 的 `call`、`answer`、`task` 只有一种 `fail`，它的每个转移都经 `Lose`，所以它对应带标记的失败。表达 P15 要给这三个端口加一种不转 `lost` 的答复，这改的是模型的抽象，不只是配置，本页因此没有 P15 的 TLC 配置与负控。探索器只驱动调用口与 `getTask`：`refresh` 的页请求由 `refresh.spec.ts` 承担，其余三个任务方法用同一个答复函数，`marks` 场景没有驱动它们。`not-sent`（`authorization-required`）在 stdio 的替身上不出现，由服务层用例承担。
- 模型与实现之间没有精化证明。

## 维护

修改连接表的源码、端口替身或性质时，同步更新 [ConnectionTable.tla](models/ConnectionTable.tla)、`tests/model/` 与本页的映射，再重跑两种证据与受影响的负控。修改调用口（`calls.ts`、`tasks.ts`、`in-flight.ts`、`task-table.ts`）时，同样对 [Calls.tla](models/Calls.tla) 与 `calls.spec.ts` 的场景做。改关停与停止的出口或途中各点（`calls.ts`、`tasks.ts`、`discovery.ts`）时，先改「关停与停止的判定点」一节，再对该点做负控。探索器经 `InFlightCalls` 的子类观察在途表，它的方法签名变了，先改 `explore.ts` 的 `CountedInFlight`。新加一条性质时，同时在模型里加一个负控配置，在「负控」表里加一行实现一侧的缺陷，并证明两边都能变红。

每次运行的读数、负控的结果与原始输出贴到任务卡的评论里，原件留任务 `tmp/`，不进本目录。
