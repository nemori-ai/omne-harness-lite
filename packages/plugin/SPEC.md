# plugin

一份 plugin 是一个目录：最上面一份清单 `plugin.json`，写明它有哪些成员、各放到哪个拓展点上；别的文件是成员的数据或代码。本组拥有清单的形状、一份 plugin 在一侧怎样从「要装」走到「装上」，以及两棵树之间送它的路。词的定义归[统一语言](../../.meta_harness/design/ubiquitous_language/terms/capabilities-and-composition.md)。

## 总体架构

```mermaid
flowchart LR
  source["来源<br/>给出一组 plugin：版本、清单、文件表"]
  contract["plugin-protocol<br/>两棵树共用：清单、包的判定、要装的、一侧的状态、plugin/v1"]
  loader["装载方<br/>照「要装的」把成员放到点上"]
  points["各个拓展点<br/>规矩归点的拥有者"]

  source -->|"一组"| contract
  contract -->|"这一侧要装的"| loader
  loader -->|"放一项，撤一项"| points
```

| 成员 | 做什么 |
| --- | --- |
| `plugin-protocol` | 两棵树共用的纯契约。清单的读法、包对不对得上清单、成员的摘要、一侧要装的、一份 plugin 在一侧的状态机；协议契约 `plugin/v1`：列出一侧要装的、分页读文件、回报装成了没有、观察要装的变了没有。不依赖 Cordis、存储与浏览器 |
| `plugin-host-local` | Plugin 作为资产的一个类别：它的正文契约、它的点 `plugin.plugins`，与向资产的类别服务登记的 Cordis 插件 |
| `plugin-access` | 接入插件：核登录可为目标租户行事，问来源，把答复映射成 `plugin/v1`；声明来源与回报去处两个端口，带一份进程内的回报去处 |
| `plugin-ui` | 客户端的装载器：跟着来源读这个租户要装的，把每一份的成员放到界面的点上，表变了跟着装、换代、卸下 |

## 领域边界

- 本组拥有：清单的 schema；一个成员写成哪三种之一；包里许带哪几种文件；「要装的」怎样从来源给的一组算出来；一份 plugin 在一侧的五种状态与它们之间的每一步。
- 本组不拥有：一个点收什么。成员放得上放不上由那个点的规矩判，本组不替它判。
- 本组不拥有：别的类别的正文合不合格。清单里指向一个类别的点的成员，交给那个类别的正文契约判；本组只把它交过去，并把它说的话带回来。
- 本组不拥有：谁持有一份 plugin、哪一层的胜出。那是来源的事，来源交来的一组里每个名字至多一份。
- 纯契约不认识装载方，也不认识来源：两边都只拿它的类型与纯函数。它放在协议成员里，因为客户端一侧的成员只经本组的协议契约认识这个领域，而清单、要装的与一侧的状态是两棵树都要照着做的。

## 心智模型

- **清单是数据。** 不运行一份 plugin 的任何代码，就算得出它装上之后往哪些点上放哪些项。
- **一个成员是某个点上的一项。** 它写三种之一：`data`（这一项就是这份数据）、`directory`（这一项是包里的一个子目录）、`module` 加 `export`（这一项是包里一个文件的一个导出）。
- **「放」不在 plugin 手里。** 成员只说放什么、放到哪；放的是装载方，只放清单里写过的。
- **版本是内容的摘要。** 内容变了版本就变，同一个版本的内容永远相同。
- **装着的向要装的收敛。** 状态机的每一格都有去处：表里有的装上，不在了的卸下，换了版本的换代。

## 应然设计

### 清单

- 文件名是 `plugin.json`（常量 `MANIFEST_FILE`）。形状：`{ schema, name, summary, client?, server? }`，`schema` 是 `1`（常量 `MANIFEST_SCHEMA`）。一侧是 `{ needs?, members }`。
- `name` 是小写字母、数字与连字符，字母开头，至多 64 个字符。它进文件的地址，也是装上之后那个 fiber 的名字的一部分。`summary` 不能空。
- 一个成员：`point`（点的名字）、`key`、可选的 `id` 与 `rank`，加三种写法之一。写了两种或一种都没写的不合格。`module` 必须是 `.js` 文件并写明 `export`。
- 清单里的路径都在包里面：用 `/` 分段，每段是字母、数字、点、下划线与连字符，没有 `.` 与 `..`，不以 `/` 开头。
- 清单里写不出作用域：一份 plugin 的成员在哪一层，由装载方照持有它的那一层打上。
- 读法 `readManifest(文本)` 答两种之一：读到的清单，或拒绝并写明第一处不对的地方，成员的不对写明是哪一侧的第几个。它不抛出。
- 不认识的字段读的时候略过，所以给清单加可选字段是相容的；改形状要换 `schema` 的数。别的数的清单这一版的读法拒绝。

### 包

- 一个包是一张文件表：每个文件一个路径与一个内容摘要。
- `judgePackage(清单, 文件表)`：每个 `module` 指的文件在表里；每个 `directory` 下至少有一个文件；表里的文件除了目录型成员自己目录下的，只许是 `.js`、`.css`、`.json`（常量 `FILE_SUFFIXES`）；路径都在包里面。不合的答第一处原因。
- 一个成员的摘要 `memberDigest(成员, 文件表)`：成员这一段的内容（字段的先后不算），带文件的并上那个文件的摘要，带目录的并上目录下每个文件的摘要（文件表的先后不算）。摘要相同的两个成员放的是同一项。

### 作为资产类别

- Plugin 是资产的一个类别 `plugin`：目录型，经通用入口新建，命名空间 `plugins`，点 `plugin.plugins`。一份包至多 400 个文件，单个文件至多 1 MiB，整包至多 16 MiB。
- 它的正文契约由 `pluginBodyContract(类别的只读面)` 造出。类别的只读面每次判的时候现问，不在登记时固化：后来才登记的类别，它的成员同样被判。
- `inspect` 依次判四样，第一处不合格就停，整份不发：
  1. 包里有 `plugin.json`，并且读得懂（「清单」一节）。
  2. 包对得上清单（「包」一节的 `judgePackage`）。
  3. 每个成员照下表判。判的时候问 `atPoint(成员的点)`。
  4. 清单的原文在正文许可的大小之内。

  | 这个点 | 成员的写法 | 答 |
  | --- | --- | --- |
  | 不是任何类别的点 | 任意 | 不在这里判：点在不在、合不合它的规矩是装的时候的事 |
  | 一个类别的点，这个类别不可用（冲突、登记表读不出） | 任意 | 依据不可用，整份不发 |
  | Plugin 自己的点 | 任意 | 拒：一份 plugin 里不放 plugin |
  | 一个类别的点，这一类不经通用入口新建 | 任意 | 拒 |
  | 一个类别的点，成员写在客户端一侧 | 任意 | 拒：类别的点都在服务端的树上 |
  | 目录型类别的点 | `directory` | 用 `withinDirectory` 给这一类只看得见那个子目录的读口，交给资产的 `judgePackageContent`，名字是成员的键 |
  | 目录型类别的点 | `data`、`module` | 拒：这一类收目录 |
  | 数据型类别的点 | `data` | 交给这一类的 `judge`，名字是成员的键 |
  | 数据型类别的点 | `directory`、`module` | 拒：这一类收数据 |

- 成员被拒的原因写成 `<位置> (<点>, <键>): <原因>`，位置是 `<哪一侧>.members[<第几个>]`。类别判为不合格时，原因是 `the category <类别> says <这一类说的话>`，这一类说的话原样带上。
- `inspect` 交出的正文是清单的原文。`judge` 判一份正文：它不是一份读得懂的清单的拒；发布用的名字与清单的 `name` 不同的拒。
- 这一类不声明设置项，不引用别的能力。

### 要装的

- 来源给一组：每份是 `{ version, manifest, files }`。
- `wantedOf(一组, 哪一侧)` 是纯函数：清单里有这一侧的每一份，给出名字、版本、这一侧的成员与 `needs`、文件表，按名字排。结果与一组的先后无关。
- 一组里同一个名字出现两次，这个名字一份都不装。

### 一份 plugin 在一侧

状态五种：不要（`unwanted`）、在装（`loading`）、装上（`loaded`）、装失败（`failed`，带原因）、被底停掉（`held`）。`stepSide(状态, 事)` 是纯函数，给出下一个状态与装载方要做的事（装某一版、卸某一版）。

表动了的时候：

| 状态 | 表里有它，同一版 | 表里没了它 | 表里是另一版 | 进程重启 |
| --- | --- | --- | --- | --- |
| 不要 | 去装 | 不变 | 去装 | 不变 |
| 在装 | 不变 | 装完即卸 | 装完即换代 | 重新装表里最后说的那一版；表里已经没了它就回到不要 |
| 装上 | 不变 | 卸下 | 换代：新的一代在装，旧的一代留到它装完 | 再装 |
| 装失败 | 不变 | 去掉这条记录 | 用新的一版再装 | 再装 |
| 被底停掉 | 不变 | 去掉这条记录 | 放开，用新的一版装 | 仍停着 |

在途的一次装载有了结局的时候：

| 这期间表说的 | 装成了 | 没装成 | 底不让装 |
| --- | --- | --- | --- |
| 留着 | 装上；旧的一代卸下 | 装失败，记原因；旧的一代卸下（它不在表里了） | 被底停掉；旧的一代卸下 |
| 没了它 | 刚装上的与旧的一代都卸下，回到不要 | 旧的一代卸下，回到不要 | 同左一格 |
| 另一版 | 最旧的一代卸下，去装那一版；刚装上的留到它装完 | 去装那一版；旧的一代留到它装完 | 同左一格 |

- 没有在途的装载时，这三种结局什么都不改。
- 换代时旧的一代留到新的一代有了结局：一份 plugin 的贡献不出现一段空白。
- 装失败不算进程倒了。

### 协议 plugin/v1

五样都要登录，正文都带目标租户。

| 名字 | 种类 | 正文 | 成功时 | 别的答复 |
| --- | --- | --- | --- | --- |
| `list-wanted` | 读 | `{ tenant, side }`，`side` 是 `client` 或 `server` | `{ plugins }`：每份 `{ name, version, manifest, files }`。`manifest` 是 `plugin.json` 的原文，客户端用 `readManifest` 读；`files` 每项 `{ path, digest, bytes }` | 共同契约的那一组 |
| `read-file` | 读 | `{ tenant, name, version, path, offset, limit }` | `{ part, next, bytes }`：`next` 是下一个偏移，读完是空；`bytes` 是整个文件的字节数 | `not-found`：`plugin`（这个名字与版本不在这个租户要装的里）或 `file`（路径不在那一份的文件表里）；`limited`（`limit` 是 0） |
| `report-loaded` | 提交，重发安全；正文走大的那一档 | `{ tenant, client, plugins, points, parts }`：`client` 是客户端实例自己起的标识；`plugins` 每份 `{ name, version, state, reason }`，`state` 是 `loaded`、`failed`、`held`；`points` 每项 `{ name, summary }`；`parts` 每项 `{ name, label, summary, depths, within }` | `{}` | 共同契约的那一组，加 `unknown` |
| `list-reports` | 读 | `{ tenant }` | `{ clients }`：这个租户现在连着的每个客户端最后报的那一份，带它的 `client` | 共同契约的那一组 |
| `observe-wanted` | 观察 | `{ tenant, side, client }`：`client` 与回报里的是同一个标识 | 帧 `{ kind: 'changed' }`：打开时一帧，之后每次要装的可能变了一帧；客户端每收到一帧读一次表 | 以 `denied` 或 `unavailable` 结束 |

- 一次读至多给 256 KiB；`limit` 更大时按这个数读。
- 同一个客户端再报，覆盖它上一次报的。回报是全量的一份：它说的是这个客户端现在的样子，不是一次变化。
- 一个客户端「在」的意思是它开着 `observe-wanted`。它的最后一条观察结束，它报的那一份就去掉；不在的客户端报的不记，`report-loaded` 对它答依据不可用（没开观察就来报的、观察结束之后才到的迟到回报都是这样）。`list-reports` 因此只答现在连着的客户端。
- 页面不直接调 `read-file` 取代码：它从宿主应用同源的一条路取文件，那条路带着登录替它读。路径的写法与那条路的答复归宿主应用的规格（桌面应用见 [`apps/desktop/SPEC.md`](../../apps/desktop/SPEC.md#取-plugin-的文件)）。

### 接入插件与来源

- 每个处理函数的次序：核这次登录可以为目标租户行事，拒绝答 `denied`，依据取不到答 `basis-unavailable`；取为这个租户行事的主体；再问来源。来源答取不到时答 `basis-unavailable`；来源抛出时读操作答 `basis-unavailable`，提交操作答 `unknown`。
- 来源是插件声明的端口：`list(主体)` 给一组（每份带清单原文与每个文件的字节数），`read(主体, 位置)` 给一段字节或答哪一样不在，`subscribe(监听)` 在给的一组可能变了时叫监听。给什么可以因主体而不同。
- `list-wanted` 把来源给的一组经 `wantedOf` 筛成这一侧的。`read-file` 只认同一组里某一侧要装的那几份：名字与版本对不上答 `not-found/plugin`，路径不在那一份的文件表里答 `not-found/file`，两种都不问来源要字节。路径以文件表为准，所以带 `..` 或以 `/` 开头的路径一律是 `not-found/file`。
- 回报的去处是插件声明的端口：`record(租户, 客户端, 回报)` 记下并答记了没有（客户端不在时不记），`present(租户, 客户端)` 说这个客户端从现在起在、答复被叫到时不在了，`reportsOf(租户)` 列出每个客户端最后报的。插件带一份进程内的实现：每个租户至多记那么多个客户端的（服务端应用的行配置 `reportsPerTenant`，缺省 32），多了去掉最久没报的；进程重启后为空，客户端下次读到表时再报。读出去的是副本。
- `list-reports` 与别的操作一样先核登录可为目标租户行事，只答那个租户的。它是给 agent 的工具读客户端那棵树用的。
- 服务端应用的 `plugin-access` 行给的来源是运维者配置的开发目录（配置项 `devDirectory`，绝对路径；缺省不开，不开时给空表，观察照常开着）：
  - 目录下每个子目录是一份。清单读不懂、清单的 `name` 不等于子目录名、或 `judgePackage` 不合格的那一份不给出，行的日志里写一行警告，写明哪一份与原因；同一个原因只写一次。
  - 名字以点开头的文件与目录不算（系统与工具留下的，例如 `.DS_Store`、`.git`）。配置的目录读不了时，来源答取不到，不答空表：已经装着的不因此被卸下。
  - 文件表是子目录下全部普通文件，路径用 `/` 分段，摘要是内容的 sha256。版本是「按路径排好序的每个文件的路径与摘要」的 sha256 的前 16 位。它对所有租户给同一组。
  - 目录里增、删、改一个文件之后 2 秒内叫监听；扫出的每份版本都没变时不叫。行卸下时停止看。
  - 读只认最近一次扫描的文件表里有的路径；解析出的真实路径不在那一份的子目录下面时答 `file` 不在；内容的摘要与文件表对不上时答 `plugin` 不在，因为那个版本已经不在了。

### 客户端的装载器

`plugin-ui` 是一个界面模块，要协议 `plugin/v1`。它做四件事，各自能单独测：

- **跟着来源读。** 开观察 `observe-wanted`；来源在观察开好时发一帧、每次可能变了再发一帧，每一帧读一次 `list-wanted`。读到的表交给收敛的那一步。读不到（取不到、被拒、依据不可用）不是表空：什么都不交，已经装着的不动；这一轮观察收掉，等一会儿重开，连着读不到时等得越来越久，读到一次就从头算。
- **表里每份读成什么。** 清单用 `readManifest` 读，取这一侧的成员。清单读不懂、或清单里的名字和表里的名字不同的那一份仍然在表里，带着原因：它装失败，不当成「不在了」。
- **收敛。** 每份的状态照上面两张表走（`stepSide`）：表里有的装上，不在了的卸下，换了版本的换代。一份装的过程中抛出算装失败，原因记下。各份互不影响。
- **放到点上。** 一份 plugin 在外壳上占一个自己的作用域，名字是 `plugin:<名字>@<版本>`，成员都经它放，所以登记表上看得出每一项是哪一份、哪一版放的，卸下一份只撤它的。放之前先逐个核成员；有一个不能放，这一份什么都不放。放上去之后外壳的规矩不认其中一项（例如部位没有声明），整份撤回，原因是外壳说的那一句。

这一侧收数据成员的点与数据的样子：

| 点 | 键 | `data` |
| --- | --- | --- |
| `shell.tokens` | 部位的名字 | 令牌名到值的一张表 |
| `shell.part-style` | 部位的名字 | 状态（`base` 与六种状态）到样式声明的一张表 |
| `shell.layout` | 布局的键 | 标识的列表 |

- 这三个点一个键只有一项，成员不写 `id` 与 `rank`。别的点不收数据成员；目录型成员这一侧不收。同一份里两个成员写同一个点同一个键，这一份装失败。
- 代码成员（`module` 加 `export`）只放在收画法的点上：部位的画法 `shell.part-render`，与声明了的按键选画法的点（外壳的 `takesDrawing` 答是）。同样一个键一项，不写 `id` 与 `rank`。
- 值合不合规矩由外壳判，装载器只看 `data` 是表还是列表。
- 一个租户的两份 plugin 往同一个点的同一个键上放，是同一层的两项：外壳答冲突，两份在这个键上都不算数，自带的样子照旧，别的键不受影响。两份都算装上；这不是装失败，谁先谁后也不改变结果。拿掉其中一份，另一份立刻算数。

装一个代码成员：

1. 每个成员都先核过能不能放，有一个不能，这一份什么文件都不取。
2. 向宿主应用要这个文件的模块。怎样取由宿主应用给（桌面应用从同源的那条路动态导入，地址带版本）；应用没有给，代码成员装失败。
3. 取 `export` 写的那个导出，它得是函数。
4. 在这一份自己的作用域里用宿主交的东西调它一次：宿主应用交的（桌面应用交 `React` 与共用界面件 `ui`），加一个 `shell`。它交回的得是函数，这就是这一项的画法。
5. 装载器把画法放到清单写的点与键上。

| 哪一步坏了 | 结果 |
| --- | --- |
| 文件取不到，或模块装载时抛出 | 这一份装失败，原因带文件名与错误的话 |
| 没有那个导出，或它不是函数 | 这一份装失败 |
| 调它时抛出 | 这一份装失败，已经放上的撤回 |
| 交回的不是函数 | 这一份装失败，已经放上的撤回 |
| 画的时候抛出 | 不算装失败：那一处落回自带的画法或宿主通用的画法，规矩归[外壳契约](../frontend/SPEC.md#外壳契约) |

- 交给代码的 `shell` 没有「放」：只有切页（`navigate`）、提示（`toast`）、读当前租户（`scope`）。提示记在这一份的作用域上，卸下时一起撤掉。放的是装载器，只放清单里写过的。这说的是交给代码什么，不是隔离：取来的代码和页面在同一个上下文里运行，这一条挡不住它自己去碰页面里的东西。
- 交给代码的那个对象是冻结的。代码文件不写任何包名：它要用的都从这个对象里取，所以和应用用的是同一个 React。文件之间可以用相对路径互相导入。
- 成员的作用域是读这张表的那个租户的。别的租户、没登录时看不到它们。租户换了或退出了，上一个租户的装载器停下，它装的全部撤掉；新的租户另起一个。
- 进程重启之后，客户端记着的只有底记的那几样；别的由重新读到的表带回来。所以重启之后：装上的再装，装失败的再试，被底停掉的同一版仍停着。
- 协议撤了，这个模块随之卸下，它装的一起撤掉。协议还挂着而来源答取不到时，已经装着的不动。

### 回报

装载器把这个客户端现在的样子报给服务端，agent 才问得到「装上了没有、没装上是为什么、界面上有哪些点与部位可以改」。

- 报什么：每份有了结局的 plugin 的状态与原因（还在装的不报）；这棵树上声明了的点与部位（外壳的 `shell.described()`）。一份装上了、但它放的某一项和别人放的撞在同一个键上，状态仍是 `loaded`，原因写明哪个点哪个键、和谁撞了、两份都不算数。
- 什么时候报：读到一次表之后；一份 plugin 的状态动了；树上的点或部位变了。要报的和服务端上一次收下的相同就不报。
- 没送到（服务端没有答收下）不算报过：下一次读表、或下一次有变化时再报全量。同一时刻至多一次回报在途，在途时又有变化，送完再报一次最新的。
- 客户端的标识是这个页面实例自己起的，观察 `observe-wanted` 与回报用同一个。页面重新加载就是另一个客户端。

### 底

底回答一个问题：一份 plugin 让应用起不来的时候，应用还打不打得开。答法是应用先起自带的，plugin 是之后补装的；补装连着让应用倒下，就不再补装，并说出停掉了哪几份。底怎样算归 [Dynamis](../dynamis/SPEC.md)（`Floor`），存在哪、怎样认出「倒了一次」归宿主应用，装载器只经一个端口用它：

| 端口的一样 | 什么时候 | 意思 |
| --- | --- | --- |
| `rise(租户)` | 开始为一个租户装的时候 | 答上一次要装的，与现在拦不拦 |
| `want(租户, 名字)` | 每一次去装之前 | 从这里到 `settle`，应用要是没了，就算装的时候倒了一次 |
| `unwant(租户, 名字)` | 一份卸下了、装失败了、被放开了 | 这一样不再算要装的 |
| `settle(租户)` | 读到了表，而且表里每一份都有了结局 | 这一次起来了 |

- 名字是 `plugin:<名字>@<版本>`，和它在登记表上的名字相同。
- 底拦着的时候，上一次要装的那几份（各在那一版）不装，状态是被底停掉；装载器让外壳把它们记成没起来的（原因 `held`）。表里别的照装。
- 被停掉的一份有两种放开：表里它换了一版，新的一版照常去装；表里不再有它。两种都对底说 `unwant`。全放开之后的那一次起来，连倒的次数清零。
- 没有读到表之前不说 `settle`：读不到不等于起来了。有一份还在装的时候也不说。
- 装失败不算倒下：那一份记原因，对底说 `unwant`，下一次起来照常再试。
- 一份的画法在画的时候抛出不经过底：那一处落回，这一份仍算装上。
- 租户换了或退出时，装载器把装着的立刻撤掉，不等还在装的：在装的那一份落地时再撤。然后同样对底说 `settle`：有序地停下不是倒下。
- 应用不给底的时候，装载器照常装，什么都不拦。

## 原则与约束

- 纯契约没有任何运行时的依赖：它在服务端与页面里是同一份代码。
- 清单的不合格、包的不合格都答出来，不抛出；原因写给人读，点名到成员。
- 一个成员装不上，这一份在这一侧整份算装失败：一份 plugin 的贡献一起可见。
