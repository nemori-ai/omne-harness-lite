# plugin

一份 plugin 是一个目录：最上面一份清单 `plugin.json`，写明它有哪些成员、各放到哪个拓展点上；别的文件是成员的数据或代码。本组拥有清单的形状、一份 plugin 在一侧怎样从「要装」走到「装上」，以及两棵树之间送它的路。词的定义归[统一语言](../../.meta_harness/design/ubiquitous_language/terms/capabilities-and-composition.md)。

## 总体架构

```mermaid
flowchart LR
  source["来源<br/>给出一组 plugin：版本、清单、文件表"]
  contract["plugin-protocol<br/>两棵树共用：清单、包的判定、要装的、一侧的状态、plugin/v1"]
  loader["装载方<br/>照「要装的」把成员放到点上"]
  points["各个拓展点<br/>规矩归点的拥有者"]

  source -->|"一组"| contract
  contract -->|"这一侧要装的"| loader
  loader -->|"放一项，撤一项"| points
```

| 成员                | 做什么                                                                                                                                                                                                                                                                                           |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `plugin-protocol`   | 两棵树共用的纯契约。清单的读法、包对不对得上清单、成员的摘要、一侧要装的、一份 plugin 在一侧的状态机，照这张状态机向要装的收敛的回路（`createLoader`）与底的口（`FloorPort`）；协议契约 `plugin/v1`：列出一侧要装的、分页读文件、回报装成了没有、观察要装的变了没有。不依赖 Cordis、存储与浏览器 |
| `plugin-host-local` | Plugin 作为资产的一个类别：它的正文契约、它的点 `plugin.plugins`，与向资产的类别服务登记的 Cordis 插件；一个租户持有的 plugin 怎样从资产读出来                                                                                                                                                   |
| `plugin-tools`      | 给 agent 的只读工具 `OmneExtensionPoints`：看两棵拓展树上有哪些点与部位、各收什么、现在放着什么、变了什么。它只认识登记表这个库与工具契约，要的东西写成端口                                                                                                                                      |
| `plugin-access`     | 接入插件：核登录可为目标租户行事，问来源，把答复映射成 `plugin/v1`；声明来源与回报去处两个端口，带一份进程内的回报去处                                                                                                                                                                           |
| `plugin-ui`         | 客户端的装载器：跟着来源读这个租户要装的，把每一份的成员放到界面的点上，表变了跟着装、换代、卸下                                                                                                                                                                                                 |

## 领域边界

- 本组拥有：清单的 schema；一个成员写成哪三种之一；包里许带哪几种文件；「要装的」怎样从来源给的一组算出来；一份 plugin 在一侧的五种状态与它们之间的每一步。
- 本组不拥有：一个点收什么。成员放得上放不上由那个点的规矩判，本组不替它判。
- 本组不拥有：别的类别的正文合不合格。清单里指向一个类别的点的成员，交给那个类别的正文契约判；本组只把它交过去，并把它说的话带回来。
- 本组不拥有：谁持有一份 plugin、哪一层的胜出。那是来源的事，来源交来的一组里每个名字至多一份。
- 纯契约不认识装载方，也不认识来源：两边都只拿它的类型与纯函数。它放在协议成员里，因为客户端一侧的成员只经本组的协议契约认识这个领域，而清单、要装的与一侧的状态是两棵树都要照着做的。

## 心智模型

- **清单是数据。** 不运行一份 plugin 的任何代码，就算得出它装上之后往哪些点上放哪些项。
- **一个成员是某个点上的一项。** 它写三种之一：`data`（这一项就是这份数据）、`directory`（这一项是包里的一个子目录）、`module` 加 `export`（这一项是包里一个文件的一个导出）。
- **「放」不在 plugin 手里。** 成员只说放什么、放到哪；放的是装载方，只放清单里写过的。
- **版本是内容的摘要。** 内容变了版本就变，同一个版本的内容永远相同。
- **装着的向要装的收敛。** 状态机的每一格都有去处：表里有的装上，不在了的卸下，换了版本的换代。

## 应然设计

### 清单

- 文件名是 `plugin.json`（常量 `MANIFEST_FILE`）。形状：`{ schema, name, summary, kind?, client?, server? }`，`schema` 是 `1`（常量 `MANIFEST_SCHEMA`）。一侧是 `{ needs?, members }`。
- `kind` 写明这一份是什么。没写是普通的一份；写了只认 `skin`（皮肤），别的值读的时候拒绝并写明这个值。
- `name` 是小写字母、数字与连字符，字母开头，至多 64 个字符。它进文件的地址，也是装上之后那个 fiber 的名字的一部分。`summary` 不能空。
- 一个成员：`point`（点的名字）、`key`、可选的 `id` 与 `rank`，加三种写法之一。写了两种或一种都没写的不合格。`module` 必须是 `.js` 文件并写明 `export`。
- 清单里的路径都在包里面：用 `/` 分段，每段是字母、数字、点、下划线与连字符，没有 `.` 与 `..`，不以 `/` 开头。
- 清单里写不出作用域：一份 plugin 的成员在哪一层，由装载方照持有它的那一层打上。
- 读法 `readManifest(文本)` 答两种之一：读到的清单，或拒绝并写明第一处不对的地方，成员的不对写明是哪一侧的第几个。它不抛出。
- 不认识的字段读的时候略过，读到的结果里列出略过了哪些顶层栏（`unread`，按名字排），所以给清单加可选字段是相容的；改形状要换 `schema` 的数。别的数的清单这一版的读法拒绝。

### 包

- 一个包是一张文件表：每个文件一个路径与一个内容摘要。
- `judgePackage(清单, 文件表)`：每个 `module` 指的文件在表里；每个 `directory` 下至少有一个文件；表里的文件除了目录型成员自己目录下的，只许是 `.js`、`.css`、`.json`（常量 `FILE_SUFFIXES`）与五种图 `.png`、`.jpg`、`.webp`、`.avif`、`.svg`（常量 `IMAGE_SUFFIXES`）；路径都在包里面；数据成员的值里用 `file(路径)` 指到的每个文件都在表里（`fileRefs(值)` 给出一个值指到的路径）。不合的答第一处原因。
- `imageFault(路径, 文件的开头)`：名字是图的文件，开头要像这种图（位图各看开头的几个字节，AVIF 看 `ftyp` 盒的主品牌与兼容品牌里有没有 `avif` 或 `avis`，矢量图越过声明、注释与文档类型之后以 `<svg` 起头）；不像的答原因并写明文件。名字不是图的不归它判。要读的字节数是常量 `IMAGE_HEAD_BYTES`。
- 一个成员的摘要 `memberDigest(成员, 文件表)`：成员这一段的内容（字段的先后不算），带文件的并上那个文件的摘要，带目录的并上目录下每个文件的摘要（文件表的先后不算）。摘要相同的两个成员放的是同一项。

### 作为资产类别

- Plugin 是资产的一个类别 `plugin`：目录型，经通用入口新建，命名空间 `plugins`，点 `plugin.plugins`。一份包不设上限：文件数、单个文件、整包的字节数都不拦。清单 `plugin.json` 自己要放得进一份正文（1 MiB）。
- 它的正文契约由 `pluginBodyContract(类别的只读面)` 造出。类别的只读面每次判的时候现问，不在登记时固化：后来才登记的类别，它的成员同样被判。
- `inspect` 依次判四样，第一处不合格就停，整份不发：
  1. 包里有 `plugin.json`，并且读得懂（「清单」一节）。
  2. 包对得上清单（「包」一节的 `judgePackage`），并且名字是图的文件确是这种图（`imageFault`）：每张图各打开一次读它的开头；这时读不到是来源失败，不是包被拒。
  3. 每个成员照下表判。判的时候问 `atPoint(成员的点)`。
  4. 清单的原文在正文许可的大小之内。

  | 这个点                                             | 成员的写法            | 答                                                                                                      |
  | -------------------------------------------------- | --------------------- | ------------------------------------------------------------------------------------------------------- |
  | 不是任何类别的点                                   | 任意                  | 不在这里判：点在不在、合不合它的规矩是装的时候的事                                                      |
  | 一个类别的点，这个类别不可用（冲突、登记表读不出） | 任意                  | 依据不可用，整份不发                                                                                    |
  | Plugin 自己的点                                    | 任意                  | 拒：一份 plugin 里不放 plugin                                                                           |
  | 一个类别的点，这一类不经通用入口新建               | 任意                  | 拒                                                                                                      |
  | 一个类别的点，成员写在客户端一侧                   | 任意                  | 拒：类别的点都在服务端的树上                                                                            |
  | 目录型类别的点                                     | `directory`           | 用 `withinDirectory` 给这一类只看得见那个子目录的读口，交给资产的 `judgePackageContent`，名字是成员的键 |
  | 目录型类别的点                                     | `data`、`module`      | 拒：这一类收目录                                                                                        |
  | 数据型类别的点                                     | `data`                | 交给这一类的 `judge`，名字是成员的键                                                                    |
  | 数据型类别的点                                     | `directory`、`module` | 拒：这一类收数据                                                                                        |

- 成员被拒的原因写成 `<位置> (<点>, <键>): <原因>`，位置是 `<哪一侧>.members[<第几个>]`。类别判为不合格时，原因是 `the category <类别> says <这一类说的话>`，这一类说的话原样带上。
- `inspect` 交出的正文是清单的原文。`judge` 判一份正文：它不是一份读得懂的清单的拒；发布用的名字与清单的 `name` 不同的拒。
- 这一类不声明设置项，不引用别的能力。
- 这个类别自己答影响与生效情况（`pluginEffect`，登记时作为类别的 `effect` 带上；要的三样写成端口：这个租户在持的 plugin、服务端树上此刻的点、这个租户连着的客户端报了什么）。影响只读清单，不运行任何东西：发布一个没发布过的目录时清单取自那个目录，别的改动取自在持的那一版。成员的点此刻不在、写法与点收的不合、点在构建时定死、同租户另一份启用的 plugin 写了同一个键，各写明；没有客户端连着时，客户端的点写明此刻不知道。生效情况取自在持那一版的清单与客户端的回报；客户端对别的版本报的不算。
- 影响在发布之前拦得住的都拦：一个点列出了一项的数据能用哪些名字时（客户端回报的 `dataKeys`，例如界面的令牌），成员的数据用了表外的名字就写明是哪个名字、最接近的是哪几个（至多三个：差一两个字母的，或表里以它结尾的），这一项不会生效。清单里写了一份清单不读的顶层栏时（`readManifest` 的 `unread`），建议里列出这些栏并说清单读哪五栏、成员放在哪。客户端对一个点报了规矩时，成员的写法与何时能变照它核；只报了名字的点不核写法。发布一个目录时，包里名字是图、超过 2 MiB 的文件，建议里逐个写出路径与大小（MiB，一位小数），并说界面每次载入一张图都要解码它，发布前先压小或缩到显示的尺寸；这一句只是建议，不拦发布，别的改动不读包、不写它。
- 类别登记的 `authoring` 给动手写的人：一份完整的最小清单、清单读哪几栏、成员的三种写法、成员放哪一侧、到哪看一个点收什么。里面那份清单必须是 `readManifest` 整份读得进的。

### 皮肤这一类

- 皮肤是资产的第二个类别 `skin`：目录型，经通用入口新建，命名空间 `skins`，点 `plugin.skins`。它由本组登记，影响与生效情况用 Plugin 的那一份。
- 它的正文契约是 `skinBodyContract(类别的只读面)`：先照 Plugin 的四样判，都过了再照下表。`pluginBodyContract` 照同一张表的左列多拒一种。

  | 清单写明的种类                         | 发布到 `plugin`                    | 发布到 `skin`                |
  | -------------------------------------- | ---------------------------------- | ---------------------------- |
  | 没写                                   | 通过                               | 拒：清单没有写明它是皮肤     |
  | 皮肤，服务端一侧没有成员也没有 `needs` | 拒：这是一套皮肤，发布到皮肤这一类 | 通过                         |
  | 皮肤，服务端一侧有成员或 `needs`       | 拒：同上，并写明皮肤只有客户端一侧 | 拒：皮肤只有客户端一侧的成员 |

- 皮肤不带能力：客户端一侧的成员只落在改样子的点与按键选画法的点上（「客户端的装载器」），指向一个类别的点的成员写在客户端一侧本来就被拒。
- 皮肤完整的写法是随发行带的官方技能 `skin-authoring`：包在本成员的 `skills/skin-authoring/`，`OFFICIAL_SKILLS` 给出它在哪个目录，由服务端装配放到技能的官方层。
- 登记的 `authoring` 给动手写的人一份核对单：一份完整的最小清单（`readManifest` 整份读得进，带着 `kind`）；皮肤能改的五层各是哪个点（令牌、样式、部位的画法、图标、共用件）；名字到哪找；明暗怎样写；图怎样带、值与代码怎样指到它；交出之前查什么。末尾指到技能 `skin-authoring`。它每次 `help publish skin` 都整段读进上下文，所以不超过八行、不空行。

### 要装的

- 来源给一组：每份是 `{ version, manifest, files }`。
- `wantedOf(一组, 哪一侧)` 是纯函数：清单里有这一侧的每一份，给出名字、版本、清单写明的种类、这一侧的成员与 `needs`、文件表，按名字排。结果与一组的先后无关。
- 一组里同一个名字出现两次，这个名字一份都不装。

### 取自资产的一组

- 一个租户要装的由它持有的推出，没有第二个地方记着装没装：`heldPlugins(端口, 租户)` 列出类别 `plugin` 与 `skin` 在这个租户各层的全部名字，对每个名字在它那一类里拿各层的候选做资产的求值，取胜出的那一版。被禁用的、被盖过的不在里面。同一个名字在两类里各有一份胜出时两份都给出，由 `wantedOf` 照「同一个名字出现两次一份都不装」处理。
- 每份给出名字、版本、清单的原文与读出的清单、文件表（路径、摘要、字节数），与它在资产里的引用和版本。清单与文件表读自这一版发布时存下的正文，不读包。
- 版本是这一版的包摘要去掉算法前缀之后的 64 位十六进制：它要写进取文件的地址里。包摘要不是这个样子的那一版不给出。
- 读不到不变成空：这个租户的层给不出、列表读不到或只读到一部分、有一层的候选读不到、胜出那一版的正文读不到，都答不可用，整组不给。正文不是一份读得懂的清单的那一版不给出，别的照给。
- 经包的读口读一个文件的各段只打开它一次：`readHeldPart` 可以带一份按摘要留着的内容（`createKeptContents(字节预算)`），第一段打开并核过的内容留着，后面各段从它切；比预算大的不留。读口交的是整个文件，所以这条路的内存随文件大小长；已发布的版本在本机有目录时不走它，见服务端应用的规格。
- `readHeldPart(读口, 文件, 起点, 长度)` 经那一版的包读一个文件的一段，答这一段、下一段从哪开始（读完了答没有）与整个文件的字节数；包里没有这个文件答文件不在，包读不了答不可用。

### 一份 plugin 在一侧

状态六种：不要（`unwanted`）、在装（`loading`）、装上（`loaded`）、装失败（`failed`，带原因）、等着（`waiting`，带缺的是哪几个口或点）、被底停掉（`held`）。`stepSide(状态, 事)` 是纯函数，给出下一个状态与装载方要做的事（装某一版、卸某一版）。

等着和装失败一样是没装成，差别在原因：等着的一份缺的是此刻不在的口或点，不是它自己坏了，所以等的那一样出现了就再装。装载方为等着的一份订阅登记表的变化。

表动了的时候，与等的那一样出现的时候：

| 状态     | 表里有它，同一版 | 表里没了它   | 表里是另一版                           | 进程重启                                           | 它等的口或点都出现了 |
| -------- | ---------------- | ------------ | -------------------------------------- | -------------------------------------------------- | -------------------- |
| 不要     | 去装             | 不变         | 去装                                   | 不变                                               | 不可达：它不在等     |
| 在装     | 不变             | 装完即卸     | 装完即换代                             | 重新装表里最后说的那一版；表里已经没了它就回到不要 | 不可达：它不在等     |
| 装上     | 不变             | 卸下         | 换代：新的一代在装，旧的一代留到它装完 | 再装                                               | 不可达：它不在等     |
| 装失败   | 不变             | 去掉这条记录 | 用新的一版再装                         | 再装                                               | 不可达：它不在等     |
| 等着     | 不变             | 去掉这条记录，不再订阅 | 用新的一版再装               | 再装                                               | 用同一版再装         |
| 被底停掉 | 不变             | 去掉这条记录 | 放开，用新的一版装                     | 仍停着                                             | 不可达：它不在等     |

在途的一次装载有了结局的时候：

| 这期间表说的 | 装成了                                         | 没装成                                       | 缺口或点                                         | 底不让装               |
| ------------ | ---------------------------------------------- | -------------------------------------------- | ------------------------------------------------ | ---------------------- |
| 留着         | 装上；旧的一代卸下                             | 装失败，记原因；旧的一代卸下（它不在表里了） | 等着，记缺的是哪几样；旧的一代卸下（它不在表里了） | 被底停掉；旧的一代卸下 |
| 没了它       | 刚装上的与旧的一代都卸下，回到不要             | 旧的一代卸下，回到不要                       | 同左一格                                         | 同左一格               |
| 另一版       | 最旧的一代卸下，去装那一版；刚装上的留到它装完 | 去装那一版；旧的一代留到它装完               | 同左一格                                         | 同左一格               |

- 没有在途的装载时，这四种结局什么都不改。
- 「缺口或点」由「怎样装一份」答出：它装不成，而且缺的全是此刻不在的口、点或需要的引用。还缺别的（例如包里没有那个文件），答没装成。两侧共用这两张表：服务端缺的是口或点，客户端缺的是点或需要的引用。
- 换代时旧的一代留到新的一代有了结局：一份 plugin 的贡献不出现一段空白。
- 装失败不算进程倒了，等着也不算。
- 向要装的收敛只有一个回路 `createLoader(怎样装一份)`，两棵树各给自己的「怎样装一份」：它不碰界面、不碰文件、不认识 Cordis。底的口 `FloorPort`（起来时问上一次要装什么与现在停不停、装之前记一笔、不要了去掉、安定了清掉）与一个 fiber 的名字 `plugin:<名字>@<版本>` 也只此一份。

### 协议 plugin/v1

五样都要登录，正文都带目标租户。

| 名字             | 种类                             | 正文                                                                                                                                                                                                                                                                  | 成功时                                                                                                                                                           | 别的答复                                                                                                                    |
| ---------------- | -------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| `list-wanted`    | 读                               | `{ tenant, side }`，`side` 是 `client` 或 `server`                                                                                                                                                                                                                    | `{ plugins }`：每份 `{ name, version, manifest, files }`。`manifest` 是 `plugin.json` 的原文，客户端用 `readManifest` 读；`files` 每项 `{ path, digest, bytes }` | 共同契约的那一组                                                                                                            |
| `read-file`      | 读                               | `{ tenant, name, version, path, offset, limit }`                                                                                                                                                                                                                      | `{ part, next, bytes }`：`next` 是下一个偏移，读完是空；`bytes` 是整个文件的字节数                                                                               | `not-found`：`plugin`（这个名字与版本不在这个租户要装的里）或 `file`（路径不在那一份的文件表里）；`limited`（`limit` 是 0） |
| `report-loaded`  | 提交，重发安全；正文走大的那一档 | `{ tenant, client, plugins, points, parts }`：`client` 是客户端实例自己起的标识；`plugins` 每份 `{ name, version, state, reason, waiting }`，`state` 是 `loaded`、`failed`、`held`；`waiting` 可选，从修订号 3 开始有：这一份等着时写它缺的口或点的名字，`state` 写 `failed`；`points` 每项 `{ name, summary }`；`parts` 每项 `{ name, label, summary, depths, within }` | `{}`                                                                                                                                                             | 共同契约的那一组，加 `unknown`                                                                                              |
| `list-reports`   | 读                               | `{ tenant }`                                                                                                                                                                                                                                                          | `{ clients }`：这个租户现在连着的每个客户端最后报的那一份，带它的 `client`                                                                                       | 共同契约的那一组                                                                                                            |
| `observe-wanted` | 观察                             | `{ tenant, side, client }`：`client` 与回报里的是同一个标识                                                                                                                                                                                                           | 帧 `{ kind: 'changed' }`：打开时一帧，之后每次要装的可能变了一帧；客户端每收到一帧读一次表                                                                       | 以 `denied` 或 `unavailable` 结束                                                                                           |

- 一次读至多给 256 KiB；`limit` 更大时按这个数读。
- 回报里的 `waiting` 在 `plugin/v1` 的契约修订号 3 加（修订号 2 加的是点的规矩与数据键）。取值集合在同一个主版本里不能后加（规矩见[接入层规格](../access/SPEC.md#协议契约与编解码)），所以「等着」不是 `state` 的新值，而是 `failed` 带上 `waiting`。对方的修订号不到 3 时，客户端不写 `waiting`，等着的一份照 `failed` 报，`reason` 写明等的是什么。读回报的一方见到 `waiting` 就把这一份读成等着：`OmneExtensionPoints` 与类别的生效情况因此报得出「等着」。
- 同一个客户端再报，覆盖它上一次报的。回报是全量的一份：它说的是这个客户端现在的样子，不是一次变化。
- 一个客户端「在」的意思是它开着 `observe-wanted`。它的最后一条观察结束，它报的那一份就去掉；不在的客户端报的不记，`report-loaded` 对它答依据不可用（没开观察就来报的、观察结束之后才到的迟到回报都是这样）。`list-reports` 因此只答现在连着的客户端。
- `read-file` 一次至多给 720 000 字节，要得更多时给这么多的一段：字节在线上是文本，这么多字节的文本放得进一个答复。
- 页面不直接调 `read-file` 取代码：它从宿主应用同源的一条路取文件，那条路带着登录替它读。路径的写法与那条路的答复归宿主应用的规格（桌面应用见 [`apps/desktop/SPEC.md`](../../apps/desktop/SPEC.md#取-plugin-的文件)）。

### 接入插件与来源

- 每个处理函数的次序：核这次登录可以为目标租户行事，拒绝答 `denied`，依据取不到答 `basis-unavailable`；取为这个租户行事的主体；再问来源。来源答取不到时答 `basis-unavailable`；来源抛出时读操作答 `basis-unavailable`，提交操作答 `unknown`。
- 来源是插件声明的端口。问的一方是 `{ 主体, 租户 }`：主体是核过可为这个租户行事之后签发的，租户是它为之行事的那一个。`list(问的一方)` 给一组（每份带清单原文与每个文件的字节数），`read(问的一方, 位置)` 给一段字节或答哪一样不在，`subscribe(租户, 监听)` 在给这个租户的一组可能变了时叫监听。给什么可以因问的一方而不同。
- 几个来源经 `combineSources` 合成一个：`list` 把各自给的并在一起，有一个答取不到或抛出就整个答取不到（它给的那几份装着的不因此被卸下）；`read` 依次问，第一个不答「这一份不在」的就是答案；`subscribe` 每个都听。两个来源给了同一个名字时，这个名字照「要装的」的规矩一份都不装。
- `list-wanted` 把来源给的一组经 `wantedOf` 筛成这一侧的。`read-file` 只认同一组里某一侧要装的那几份：名字与版本对不上答 `not-found/plugin`，路径不在那一份的文件表里答 `not-found/file`，两种都不问来源要字节。路径以文件表为准，所以带 `..` 或以 `/` 开头的路径一律是 `not-found/file`。
- 回报的去处是插件声明的端口：`record(租户, 客户端, 回报)` 记下并答记了没有（客户端不在时不记），`present(租户, 客户端)` 说这个客户端从现在起在、答复被叫到时不在了，`reportsOf(租户)` 列出每个客户端最后报的。插件带一份进程内的实现：每个租户至多记那么多个客户端的（服务端应用的行配置 `reportsPerTenant`，缺省 32），多了去掉最久没报的；进程重启后为空，客户端下次读到表时再报。读出去的是副本。
- `list-reports` 与别的操作一样先核登录可为目标租户行事，只答那个租户的。它是给 agent 的工具读客户端那棵树用的。
- 服务端应用的 `plugin-access` 行给的来源是运维者配置的开发目录（配置项 `devDirectory`，绝对路径；缺省不开，不开时给空表，观察照常开着）：
  - 目录下每个子目录是一份。清单读不懂、清单的 `name` 不等于子目录名、或 `judgePackage` 不合格的那一份不给出，行的日志里写一行警告，写明哪一份与原因；同一个原因只写一次。
  - 名字以点开头的文件与目录不算（系统与工具留下的，例如 `.DS_Store`、`.git`）。配置的目录读不了时，来源答取不到，不答空表：已经装着的不因此被卸下。
  - 文件表是子目录下全部普通文件，路径用 `/` 分段，摘要是内容的 sha256。版本是「按路径排好序的每个文件的路径与摘要」的 sha256 的前 16 位。它对所有租户给同一组。
  - 目录里增、删、改一个文件之后 2 秒内叫监听；扫出的每份版本都没变时不叫。行卸下时停止看。
  - 变化的发现不靠平台的文件监视：监视只是提示，它可以丢事件、晚到、一个都不送，或者根本开不了。不管它说没说，每一轮都扫一次；一轮是 1 秒，或上一次扫描用时的 20 倍，取长的。所以没人要的扫描至多占二十分之一的时间，「2 秒内」对一次扫描用时不到 50 毫秒的目录成立（约两千个文件）；更大的目录是一轮加一次扫描的时间。
  - 监视送来事件时提前扫：一串连着的文件事件当一次变化，安静 150 毫秒之后扫；有东西一直在往目录里写时不等它停，从这一串的第一个事件起至多 500 毫秒就扫。
  - 每个动作的开销只跟它碰到的东西成正比，跟包多大、文件多大无关：
    - 一个文件的摘要按它的大小与修改时刻记着，这两样没变就不重读它；要算时流式地读一遍，不把整个文件放进内存。
    - 这一轮里扫过、监视之后又没说变过时，`list` 答上一次扫描的结果，不重扫。目录读不到时不记：每次问都重扫。
    - 读一段只从盘上读这一段，不读整个文件。这一段是不是列出来的那一版的，凭文件的大小与修改时刻认：与算摘要时相同才给，读之前、读之后各核一次；变了就答 `plugin` 不在。
  - 读只认最近一次扫描的文件表里有的路径；解析出的真实路径不在那一份的子目录下面时答 `file` 不在；文件自列出之后变过时答 `plugin` 不在，因为那个版本已经不在了。

### 客户端的装载器

`plugin-ui` 是一个界面模块，要协议 `plugin/v1`。它做四件事，各自能单独测：

- **跟着来源读。** 开观察 `observe-wanted`；来源在观察开好时发一帧、每次可能变了再发一帧，每一帧读一次 `list-wanted`。读到的表交给收敛的那一步。读不到（取不到、被拒、依据不可用）不是表空：什么都不交，已经装着的不动；这一轮观察收掉，等一会儿重开，连着读不到时等得越来越久，读到一次就从头算。
- **表里每份读成什么。** 清单用 `readManifest` 读，取这一侧的成员。清单读不懂、或清单里的名字和表里的名字不同的那一份仍然在表里，带着原因：它装失败，不当成「不在了」。
- **收敛。** 每份的状态照上面两张表走（`stepSide`）：表里有的装上，不在了的卸下，换了版本的换代。一份装的过程中抛出算装失败，原因记下。各份互不影响。
- **放到点上。** 一份 plugin 在外壳上占一个自己的作用域，名字是 `plugin:<名字>@<版本>`，成员都经它放，所以登记表上看得出每一项是哪一份、哪一版放的，卸下一份只撤它的。放之前先逐个核成员；有一个不能放，这一份什么都不放。放上去之后外壳的规矩不认其中一项，整份撤回，原因是外壳说的那一句。不认的只是「点此刻不在」（例如部位没有声明）或「需要的引用此刻缺着」时，这一份不是装失败，是等着，记下缺的是哪几样；装载器订阅外壳登记表的变化，它等的那一样出现了就用同一版再装。还有别的不认，装失败。认不认按这一份所放的那一层问（`shell.changesFor(那一层)`）：一套没在用的皮肤，成员不合规矩时同样装失败，不等到它被用上才发现。

**皮肤放在哪一层，此刻用哪一套。**

- 普通的一份，成员放在这个租户这一层（`tenantScope(租户)`）。清单写明是皮肤的一份，成员放在这个租户之下、这一套自己的一层（`lookScope(租户, 这一份的名字)`）。来源是开发目录还是资产不改变这一条。
- 外壳发问时带上在用的那一套（见[共用界面的规格](../frontend/SPEC.md#外壳契约)的「样子」）。所以在用的那一套的成员盖过这个租户普通的一份放在同一个键上的；没在用的那几套对发问者不可见。
- 在用哪一套由 `wearStep(记着的选择, 要装的皮肤, 装上了的皮肤)` 算出，它是纯函数，同时给出记着的选择变成什么。记着的选择按租户存在本机，三种：没有、自带的样子、某一套的名字。要装的皮肤是最近一次读到的清单里写明是皮肤的那些名字，不管状态：清单里有而装载器还没来得及记状态的也算，装载器还留着状态而清单里已经没有的不算。装上了的是其中有一代活着的：状态为「装上」，或正在换代而旧的一代还在。本机存的是一段文字，应用不读它的含义；读不懂的文字当作没有。

  | 记着的选择 | 条件                                   | 用               | 之后记着         |
  | ---------- | -------------------------------------- | ---------------- | ---------------- |
  | 自带的样子 | 任何                                   | 不用             | 不变             |
  | 某一套     | 它装上了                               | 它               | 不变             |
  | 某一套     | 它在要装的里，还没装上                 | 不用             | 不变             |
  | 某一套     | 它不在要装的里                         | 照「没有」的三行 | 照「没有」的三行 |
  | 没有       | 要装的里没有皮肤                       | 不用             | 没有             |
  | 没有       | 要装的里恰好一套，它装上了             | 它               | 它               |
  | 没有       | 要装的里恰好一套，它没装上；或两套以上 | 不用             | 没有             |

- 装载器的状态变了、人定了一个选择、换了租户，各重算一次。来源读不到时装载器的状态不动，所以在用的不变。清单还没读到过时不算：记着的选择原样留着，界面先是自带的样子。没有登录时不用任何一套，也不读写记着的选择。
- 记着的那一套还没装上时不落到别的一套：进程起来时几套先后装上，先装上的不抢走选择。
- 本成员往资产页的点 `assets.category` 上按键 `skin` 放一块：列出要装的每套皮肤与它的状态、原因，标出在用的，另有「自带的样子」。点一套就是定一个选择；装失败的、等着的与被底停下的不能选。没有皮肤要装时这一块不画。这一块自己还没有声明成部位。

这一侧收数据成员的点与数据的样子：

| 点                 | 键         | `data`                                      |
| ------------------ | ---------- | ------------------------------------------- |
| `shell.tokens`     | 部位的名字 | 令牌名到值的一张表                          |
| `shell.part-style` | 部位的名字 | 状态（`base` 与六种状态）到样式声明的一张表 |
| `shell.layout`     | 布局的键   | 标识的列表                                  |

- 这三个点一个键只有一项，成员不写 `id` 与 `rank`。别的点不收数据成员；目录型成员这一侧不收。同一份里两个成员写同一个点同一个键，这一份装失败。
- 代码成员（`module` 加 `export`）只放在收画法的点上：部位的画法 `shell.part-render`，与声明了的按键选画法的点（外壳的 `takesDrawing` 答是）。同样一个键一项，不写 `id` 与 `rank`。
- 值合不合规矩由外壳判，装载器只看 `data` 是表还是列表。
- 一个租户的两份 plugin 往同一个点的同一个键上放，是同一层的两项：外壳答冲突，两份在这个键上都不算数，自带的样子照旧，别的键不受影响。两份都算装上；这不是装失败，谁先谁后也不改变结果。拿掉其中一份，另一份立刻算数。

装一个代码成员：

1. 每个成员都先核过能不能放，有一个不能，这一份什么文件都不取。
2. 向宿主应用要这个文件的模块。怎样取由宿主应用给（桌面应用从同源的那条路动态导入，地址带版本）；应用没有给，代码成员装失败。
3. 取 `export` 写的那个导出，它得是函数。
4. 在这一份自己的作用域里用宿主交的东西调它一次：宿主应用交的（桌面应用交 `React` 与共用界面件 `ui`），加一个 `shell`。它交回的得是函数，这就是这一项的画法。
5. 装载器把画法放到清单写的点与键上，并交出它的出处：模块的地址（应用给的「这一份的文件在哪」接上清单里的路径）、导出的名字、这一份的文件在哪。应用没给文件在哪时不交出处。

| 哪一步坏了                   | 结果                                                                                             |
| ---------------------------- | ------------------------------------------------------------------------------------------------ |
| 文件取不到，或模块装载时抛出 | 这一份装失败，原因带文件名与错误的话                                                             |
| 没有那个导出，或它不是函数   | 这一份装失败                                                                                     |
| 调它时抛出                   | 这一份装失败，已经放上的撤回                                                                     |
| 交回的不是函数               | 这一份装失败，已经放上的撤回                                                                     |
| 画的时候抛出                 | 不算装失败：那一处落回自带的画法或宿主通用的画法，规矩归[外壳契约](../frontend/SPEC.md#外壳契约) |

- 交给代码的 `shell` 没有「放」：只有切页（`navigate`）、提示（`toast`）、读当前租户（`scope`）。提示记在这一份的作用域上，卸下时一起撤掉。放的是装载器，只放清单里写过的。这说的是交给代码什么，不是隔离：取来的代码和页面在同一个上下文里运行，这一条挡不住它自己去碰页面里的东西。
- 应用给了「一份 plugin 的文件在哪」时（`Code` 的 `files(名字, 版本)`，答一段以 `/` 结尾的本应用路径），装载器把它一起交给外壳：这一份的令牌与样式里的 `file(路径)` 就写成那个位置下的地址（规矩见[外壳契约](../frontend/SPEC.md#改一个部位的样子)）。交给代码的对象也多一样 `files`：`files.url(路径)` 答这一版里这个路径的地址，路径不在包里面答没有。应用没给时，指到文件的数据成员装不上并说明原因，代码拿不到 `files`。
- 出处让外壳能把同一个画法交给应用的别的画面（见[共用界面的规格「改动的投影」](../frontend/SPEC.md#改动的投影)）：那块画面照出处取同一个文件、用同样的东西再调一次导出。所以导出有三条义务：它可能被调不止一次，每次都要交回画法，不能靠「只调一次」记状态；它只用交给它的东西与自己模块里的东西造画法，不靠这一份别的成员被调过；它的画法可能画在一块没有界面其余部分的画面里，找不到别的部位时要画得出东西，不抛出。装载器不知道应用有几块画面，它只交出处。
- 交给代码的那个对象是冻结的。代码文件不写任何包名：它要用的都从这个对象里取，所以和应用用的是同一个 React。文件之间可以用相对路径互相导入。
- 成员的作用域是读这张表的那个租户的。别的租户、没登录时看不到它们。租户换了或退出了，上一个租户的装载器停下，它装的全部撤掉；新的租户另起一个。
- 进程重启之后，客户端记着的只有底记的那几样；别的由重新读到的表带回来。所以重启之后：装上的再装，装失败的再试，被底停掉的同一版仍停着。
- 协议撤了，这个模块随之卸下，它装的一起撤掉。协议还挂着而来源答取不到时，已经装着的不动。

### 回报

装载器把这个客户端现在的样子报给服务端，agent 才问得到「装上了没有、没装上是为什么、界面上有哪些点与部位可以改」。

- 报什么：每份有了结局的 plugin 的状态与原因（还在装的不报）；这棵树上声明了的点与部位（外壳的 `shell.described()`）。一份装上了、但它放的某一项和别人放的撞在同一个键上，状态仍是 `loaded`，原因写明哪个点哪个键、和谁撞了、两份都不算数。
- 什么时候报：读到一次表之后；一份 plugin 的状态动了；树上的点或部位变了。要报的和服务端上一次收下的相同就不报。
- 没送到（服务端没有答收下）不算报过：下一次读表、或下一次有变化时再报全量。同一时刻至多一次回报在途，在途时又有变化，送完再报一次最新的。
- 客户端的标识是这个页面实例自己起的，观察 `observe-wanted` 与回报用同一个。页面重新加载就是另一个客户端。

### 服务端的装载方

服务端照「一份 plugin 在一侧」的两张表、同一个回路与同一个底装，装的是每个租户在持的 plugin 清单里 `server` 一段。与客户端不同的地方：

- 每个租户各有一个回路与一份底的记录（`createServerSide`）：为一个租户装什么、装没装成、停没停，不改别的租户的。读不到一个租户在持什么，它装着的不动。
- 一份怎样放（`serverInstall`）：先在这份的作用域里用 `adopt` 钉住 `needs` 写的每一个口，有一个不在整份不装，答缺口或点，写明缺哪几个；数据成员放成一条条目；代码成员只放在给了客人写法的点上，文件按清单里的摘要取，导出的函数被调时只拿到 `{ ports }`，拿不到上下文、服务或宿主的任何东西。条目的作用域由装载方打上，是持有它的那个租户的范围；清单里写不出作用域。
- 一个类别的点收目录成员：这一项由应用做，是那个类别的 `HeldItem`，资产引用与版本是这份 plugin 在持的那一版，`within` 是成员写的目录。读它的一方照读任何一份那一类的定义去读，只是读口只看得见那个子目录；它分不出这份定义来自单独持有还是来自一份 plugin。
- 点此刻不在、写法与点收的不合（类别的点只收目录）、点在构建时定死、包里没有那个文件、导入或调用抛出、点不收交回的东西、同一份两个成员在同一处、键被更浅一层带锁的条目锁住、登记表不收：各有原因，指到成员。键被锁住的那一个在装入它的代码之前就判，原因写明被哪一份锁住（锁的答法归 [Dynamis](../dynamis/SPEC.md#答案)）。有一个成员不成，这一份什么都不放。不成的只有「口或点此刻不在」时，这一份等着；还有别的不成，这一份装失败。
- 两个点归 plugin，都在构建时定，plugin 自己放不上去：`plugin.ports`，键是口的名字，一项是 `{ make }`，`make(调用者)` 交出一个口，由出借它的领域的适配放上去，里面调的是这个领域已有的入口；`plugin.guest-forms`，键是收 plugin 代码的点的名字，一项是 `{ form }`，`form(交回的东西, { key, bind })` 把它做成那个点原来的一项。没有客人写法的点不收 plugin 的代码。
- 口（`Port`）的每个方法只收一份数据、只答一份数据（`done`、`refused` 带领域的原因、`unavailable`、`unknown`、`closed`），类型上没有地方放租户、主体或函数；进出都先复制，不是数据的不过去。调用者是 `{ principal, tenant }`：这次调用的主体，与持有这份 plugin 的租户。
- 一次调用的绑定（`bindPorts`）：一次调用进来时用它的主体打开钉住的那几个口，处理函数返回或抛出时关上；关了之后每个方法答 `closed`，不调领域。钉住的口的出借者走了，那个口答 `unavailable`，绑定不变。出借者换了一代，钉着它的口重新钉到新的一代上，这一份的状态不变；已经打开的那次调用仍用它打开时的那一代。plugin 只在被调到的时候行事，没有自己的主体。
- `access.protocols` 的客人写法：plugin 交 `{ contract: { name, major, operations }, handlers }`，每个操作写 `effect`、`limit` 与 `body`、`result` 两条规则；键要等于 `名字/v主版本`；每个操作的身份都是 `acting-tenant`；不收观察。处理函数拿到输入与这次调用的口，见不到主体；它答的不在结果里时，读答 `basis-unavailable`，写答 `unknown`，抛出也是。
- plugin 的代码在服务端进程里由 `import()` 装入，带着 Node 的全部能力（读写文件、读环境变量、改写进程里共用的模块，看得见经过这个进程的每个请求）。交到它手里的只有口：这限定的是交给它什么，不是一道边界。存心越界的代码守不住，所以租户的服务端代码只适合开给信得过的租户；要给不认识的租户开，先要有受限的执行域。
- 服务端应用把一份放成它自己的一个 fiber，名字是 `plugin:<名字>@<版本>`；卸下就是撤掉这个 fiber，它放的条目一起撤下。
- 代码成员放的条目交的是带副作用的函数，所以一律带排空（`dynamis-cordis` 的 `put(条目, { drain })`）：一份卸下或换代时，它的条目先不接新的调用，在途的调用各有结局，然后才取走。只交数据的条目离开时立刻取走。
- 类别答生效情况时读服务端每份的状态：服务端那一侧的成员看服务端，客户端那一侧的成员看客户端；状态是别的版本的不算。这棵树不在服务端装 plugin 时，服务端那一侧的成员写明不装。

### 底

底回答一个问题：一份 plugin 让应用起不来的时候，应用还打不打得开。答法是应用先起自带的，plugin 是之后补装的；补装连着让应用倒下，就不再补装，并说出停掉了哪几份。底怎样算归 [Dynamis](../dynamis/SPEC.md)（`Floor`），存在哪、怎样认出「倒了一次」归宿主应用，装载器只经一个端口用它：

| 端口的一样           | 什么时候                           | 意思                                                  |
| -------------------- | ---------------------------------- | ----------------------------------------------------- |
| `rise(租户)`         | 开始为一个租户装的时候             | 答上一次要装的，与现在拦不拦                          |
| `want(租户, 名字)`   | 每一次去装之前                     | 从这里到 `settle`，应用要是没了，就算装的时候倒了一次 |
| `unwant(租户, 名字)` | 一份卸下了、装失败了、等着了、被放开了 | 这一样不再算要装的                                    |
| `settle(租户)`       | 读到了表，而且表里每一份都有了结局 | 这一次起来了                                          |
| 记一次倒下（租户, 名字；名字归交付） | 装载方起来时，从进程留下的倒下记录里读到这一份的归因 | 上一个进程是在执行这一份的调用时倒下的，算它的一次倒下；连着到上限，这一份被底停掉 |

- 名字是 `plugin:<名字>@<版本>`，和它在登记表上的名字相同。
- 底拦着的时候，上一次要装的那几份（各在那一版）不装，状态是被底停掉；装载器让外壳把它们记成没起来的（原因 `held`）。表里别的照装。
- 被停掉的一份有两种放开：表里它换了一版，新的一版照常去装；表里不再有它。两种都对底说 `unwant`。全放开之后的那一次起来，连倒的次数清零。
- 没有读到表之前不说 `settle`：读不到不等于起来了。有一份还在装的时候也不说。
- 装失败不算倒下：那一份记原因，对底说 `unwant`，下一次起来照常再试。等着也一样：它算有了结局，对底说 `unwant`。
- 一份的画法在画的时候抛出不经过底：那一处落回，这一份仍算装上。
- 服务端还认一种倒下：运行中，一份 plugin 的调用让进程倒下。进程级的未接住异常处理器在退出前记下这一刻正在执行哪一份 plugin 的调用；监督者拉起进程之后，装载方从倒下记录里读到归因，对底说「记一次倒下」，底把它算作这一份的一次倒下。连着到上限，底停掉这一份，和装的时候倒下一样。处理器与归因归[装配](../assembly/SPEC.md#两层与权限)，存在哪归服务端应用。
- 这个归因有界。归得准的：装入这一份的文件时、调它的导出时、一次调用期间抛出的，以及这些时候起的微任务、定时器与 Promise 链上抛出的（归因跟着异步上下文走）。归不准的：别人的调用里跑到的它的代码，例如它挂在共用对象上的回调；记成「不知道是谁」，不算在哪一份头上，照进程倒下处理。所以这一条只对老实的代码成立，挡不住存心越界的代码。
- 运行中的倒下按每一份各自数，数到上限就停掉这一份，别的照装。这个数不因为一次起来安定了就清零：装得上不说明它被调时不倒。放开的办法和被底停掉一样：换一版，或表里不再有它。底的口因此在 `rise` 的答复里多一样可选的 `stopped`：被逐份停掉的那几份的名字。
- 租户换了或退出时，装载器把装着的立刻撤掉，不等还在装的：在装的那一份落地时再撤。然后同样对底说 `settle`：有序地停下不是倒下。
- 应用不给底的时候，装载器照常装，什么都不拦。

### 给 agent 的工具：看拓展树

成员 `plugin-tools` 给 agent 一个只读的多命令工具 `OmneExtensionPoints`：服务端与客户端两棵拓展树上有哪些点与部位、各收什么、现在放着什么、从某个修订号之后变了什么。它不改任何东西；要改，agent 写好文件再用发布的工具。

- 一个工具一条声明，五个命令：`help`、`tree`、`find`、`show`、`changes`。菜单、签名、help 与出错回执都由工具契约的 `command-call` 从定义派生。声明里不出现任何点名、部位名或类别名：名字都是开的字符串，每次调用拿此刻的登记表与回报核。
- 成员只认识登记表的库 `dynamis` 与工具契约，自己声明它要的端口，由应用适配。端口给出三样：服务端那棵树此刻的登记表；这个租户此刻连着的客户端各自报上来的样子（点、部位、plugin 的状态）；登记表的修订。发问者的作用域由绑定按行事的租户给出，模型给不了；读一个点时只看这个作用域看得见的条目。
- 读不到不是空。端口答不可用或抛出，那一棵印一行「此刻读不到」；要读的两棵都读不到，整个调用是失败结果。没有客户端连着时明说，不印一棵空树。
- `show` 一个点时，两棵树用同一个版式：版本、说明、键、同键多项怎样答、一项交什么、宿主给什么、出错时怎样，有例子时再给一个照抄的成员。服务端的点从它的声明读，再列发问者看得见的条目和各自的回执。客户端的点从客户端报上来的规矩读；它带数据里可用的名字时，按名字排列出来，各带此刻的值，至多列 200 个。客户端不报放着什么，所以客户端的点没有条目一段。回报里没有的栏不印，不编。
- `show` 一个部位时，三种深度里它开了的每一种各写一行「一个成员该怎样写」。那个深度的点报了例子，就用例子的第一行，把键换成这个部位，照抄就对；例子读不成带键的对象时，用成员里写死的写法。`tokens` 那一行之后指到列出全部名字的那个点。这三种深度的点 `shell.tokens`、`shell.part-style`、`shell.part-render` 与写死的写法是[外壳契约](../frontend/SPEC.md#外壳契约)的事实，成员里只写在一处。
- `find` 搜点的名字、说明与规矩（键、宿主给什么、例子、数据里可用的名字），搜部位的名字、叫法与说明。查询里连着的汉字拆成相邻的两字，每两字算一个词；一个汉字单独算一个词。一个都没找到时，结果指到 `tree` 一层层往下看；找到的比上限多时，写明还有几个，以及它们在哪几个宿主下。
- `tree` 里服务端的点与客户端的点一样，每行带说明。因为 `depth` 没有展开的节点，写明它下面一共还有多少个节点。
- 作用域不印原文：行事的租户印 `this tenant`，整个部署印 `deployment`，别的作用域印 `another scope`。
- 名字两棵树上都没有，是失败结果，原因后面带此刻真有的、离它最近的几个名字。
- 修订号写成「进程的标识.计数」。登记表每变一次，应用记一张；成员只留最近若干张，缺省 64 张。`changes` 用登记表的影响比较两张表，列出多了或少了的点、多了或少了的条目、回执变了的条目，只列发问者看得见的。修订号不是这个进程的，或早于留着的最早一张，答认不得，不猜。每个结果的最后一行是当前的修订号。

## 原则与约束

- 纯契约没有任何运行时的依赖：它在服务端与页面里是同一份代码。
- 清单的不合格、包的不合格都答出来，不抛出；原因写给人读，点名到成员。
- 一个成员装不上，这一份在这一侧整份不装（装失败，或只缺口或点时等着）：一份 plugin 的贡献一起可见。
