# Dispatch

## 总体架构

Dispatch 包组回答一个问题：一个会话里的 agent 把一件事交给另一个 agent，这次交托怎样成立、怎样收场，它唯一的那份报告怎样恰好交回一次；以及一个 agent 怎样给另一个会话里的 agent 递一句话。

它是接在核心系统上的一套插件。核心域（Session、Agent、Model、Tool、Runtime Context、Request Context）的成员都不依赖它；去掉它，核心原有的流程不变，只是 agent 手里没有工具 `Agents`。它只用核心与地基已经公开的东西：存储的提交与认回、身份与授权的资格判定、Tool 的绑定登记与等待契约、会话的建会话、送输入、读输入去向、取消一轮与会话目录、会话的输入来源登记、Agent 定义的目录。

| 成员 | 回答的问题 |
| --- | --- |
| `dispatch-contract` | 派发的纯契约：公开的值、服务面的类型，以及全部纯决定（受理、资格、状态转移、报告的成立与交付位置、撤回、消息的资格）。只依赖 zod |
| `dispatch` | 派发的定义拥有者：派发登记、推进与对账、仓储的端口与事务脚本。只依赖契约 |
| `dispatch-cordis-contract` | 服务定义：派发的服务面在 Cordis 里叫什么 |
| `dispatch-local` | 本地提供者：SQL 仓储、配置、对账的扫描与唤醒、生命周期 |
| `dispatch-session` | 认识会话的适配成员：登记三个输入来源；以系统主体建会话、送输入、读输入的去向、取消一轮、读会话目录 |
| `dispatch-tool` | 认识 Tool 的适配成员：报告等待的请求契约，以及把一份报告交给一次还在等的调用的桥 |
| `dispatch-tools` | 给 agent 的多命令工具 `Agents` |

一次带报告的派发这样走：派发方的 agent 调 `Agents` 的 `dispatch`；派发用一次提交登记这次派发；适配成员以系统主体建一个子会话，起始输入就是交给它的工作；派发方的这次调用转入后台等报告，派发方的这一轮接着走；被派发方做完，交回报告；派发用一次提交让报告成立，再把它交给还在等的那次调用，调用带着报告收场，结局作为一条提醒回到派发方。调用已经不在等时，报告改作一条输入送进派发方的会话。

本组不对客户端开放协议。人从会话的列表与历史里看见子会话、它与别的会话的关系和它说过的话。

## 领域边界

本组拥有：派发登记（谁、以哪种方式、交给了哪个 Agent 定义、建出了哪个会话、现在怎样）；一次派发至多一份的报告，以及它交到了哪里；撤回的请求与结局；agent 之间一条消息的资格；派发的嵌套深度与同时开着的派发数这两个上限的判定。

本组不拥有：会话的身份、关系、值守、归档与级联（Session）；被派发的 agent 那一轮怎样推进（Agent）；派发方那次调用的等待、暂停、收场与前后台（Tool）；一个会话怎样从另一个会话分叉、分叉点怎样定、前缀怎样存与读（Session）；一次模型请求的输入怎样算（Request Context 与 Agent）；一个 agent 许不许派发、许不许发消息（身份与授权）；Agent 定义有哪些、哪些是 master（Agent 定义的拥有者）；模型与工具的费用归谁（各自的生产者按消费者引用记）。

本组声明、由别人实现的端口：

| 端口 | 对方 | 本组需要它做什么 |
| --- | --- | --- |
| 资格 | 身份与授权，经应用装配 | 答一个主体此刻许不许派发、撤回、发消息、读派发 |
| 具名命令与事务参加者 | 存储 | 一次提交里写下一次状态转移；结果不知道时如实答 |
| 会话 | Session，经 `dispatch-session` | 建带关系、值守与起始输入的会话；送一条输入；读一条输入的去向；取消一轮；按标识读会话在目录里的一行 |
| 报告的等待 | Tool，经 `dispatch-tool` | 把一份报告交给一次调用的等待，并答交到了没有：已交、等待已关、读不到 |
| 分叉点 | 会话的分叉点读口与带来源的创建，经应用装配 | 受理 `spawn` 时向会话要派发方的分叉点：写出这次调用的那条助手消息之前，由可信的调用上下文带上那条消息的标识（`CallContext.asking`），记进派发。不由模型调出的调用没有这条消息，`spawn` 答定不下来；建子会话时把它交给会话的创建。派发不读视图的行，不知道前缀有多长。定不下来时答原因 |

| --- | --- | --- |

本组往别的宿主里放的：一个多命令工具；会话的三个输入来源；Tool 的一种等待契约。每一样都由一个贡献成员带来，宿主不在时只有那个成员不启动。

## 心智模型

把派发想成一张托办单。托的人写下要办的事，交到柜台，柜台给这张单子编了号，这次交托就成立了。办的人在自己的屋里办，办完交回一张回执。柜台在单子上盖一次章，把回执交到托的人手里：他还在窗口等，就当面给；他已经走了，就送到他屋里。

最容易想错的六处：

- **派发不是函数调用。** 被派发的会话不住在派发方的调用里。调用被取消、被插队、进程重建，派发与那个会话都照旧。
- **报告终结的是派发，不是会话。** 交了报告，那个会话不归档，那一轮也不必已经结束，之后还能通消息。
- **报告与消息是两样东西。** 报告至多一份，终结派发；消息多少条都行，什么都不终结，也不顶替报告。
- **`spawn` 是 fork。** 子会话从派发方会话在派发那一刻的对话分叉出来：它的模型视图在分叉点之前就是派发方的那一段，按引用读，不复制，没有长度上限；之后各写各的，派发之后父这边发生的事子看不见。怎样分叉归 [Session 与 Run 的「会话分叉」](../../docs/architecture/runtime/session-and-run.md#会话分叉)，派发只定「哪一次调用」并把分叉点交过去。子会话的第一条输入只有交代。
- **`handoff` 交出去就不归我管。** 建成即了结，没有报告，撤不回；想知道它做得怎样，像读任何一个同租户的会话那样去读。
- **找人找的是会话。** 一个 agent 住在一个会话里。给谁发消息、谁和我是什么关系，答案都在会话的目录里；本组只添上「这次派发现在怎样」。

## 应然设计

### 三种方式

| | `spawn` | `delegate` | `handoff` |
| --- | --- | --- | --- |
| 建出的会话 | 派发方会话的子会话，无人值守 | 同左 | 独立主会话，有人值守 |
| 起始输入 | 一段交代；对话的前情不在输入里，在分叉来的前缀里 | 一段交代 | 一段交接说明 |
| 这次调用何时返回 | 等到报告、失败或撤回 | 同左 | 会话建成或建不成就返回 |
| 报告 | 至多一份 | 至多一份 | 没有 |
| 撤回 | 可以 | 可以 | 不可以 |
| 可选的 Agent 定义 | master 或 non-master | 同左 | 只能是 master |

子会话的权限处理模式取派发那一刻派发方会话的当前值，会话授权不带过去。所以子会话能做的事不超过派发方此刻能做的。

### 派发的状态

```text
accepted → started → reported
                   → failed
                   → withdrawn
accepted → failed
accepted → withdrawn
handoff： accepted → handed-off | failed
```

- `accepted`：登记已提交，派发身份已定，会话还没有建成。
- `started`：会话与起始输入已成立。
- `reported`：报告已成立。只此一次。
- `failed`：会话建不成，或被派发的那一轮以失败、被取消收场而没有报告。带原因。
- `withdrawn`：撤回先于报告成立。
- `handed-off`：独立主会话已建成。

受理时就不成立的请求不登记：资格不许、目标定义不存在或类型不符、深度或同时开着的派发数超过上限、`spawn` 的分叉点定不下来，都直接答拒绝并带原因。

`reported` 之后另有一条轴，报告的交付：`pending → delivered（调用的结果 | 一条输入）| undeliverable`。交付的结果不知道时保持 `pending`，按原身份再交。

### 全化表

| 操作 \ 状态 | accepted | started | reported | failed | withdrawn | handed-off |
| --- | --- | --- | --- | --- | --- | --- |
| 建成会话 | → started；`handoff` → handed-off | 认回 | 不可达 | 不建 | 不建 | 认回 |
| 会话建不成 | → failed | 不可达 | 不可达 | 认回 | 不变 | 不可达 |
| 交报告 | 拒：还没开始 | → reported，交付 pending | 同一份认回；另一份拒 | 拒 | 拒：已撤回 | 拒：这种方式没有报告 |
| 那一轮正常结束、会话安静下来而没有报告 | 不可达 | 以最近一轮的最终回复为报告，→ reported | 不变 | 不变 | 不变 | 不适用 |
| 那一轮失败或被取消而没有报告 | 不可达 | → failed | 不变 | 不变 | 不变 | 不适用 |
| 撤回 | → withdrawn | → withdrawn，请求停那一轮 | 答已有报告 | 答原结局 | 认回 | 拒：撤不回 |
| 读 | 答 | 答 | 答，带报告与交付 | 答，带原因 | 答，带停止的进度 | 答，带会话 |
| 派发方会话归档 | → withdrawn | → withdrawn | 不变；未交付的报告记 undeliverable | 不变 | 不变 | 不变 |

「那一轮」指起始输入引起的那一轮，按读这条输入的去向认定。它失败或被取消，派发随之失败。它正常结束时，工作不一定已经完：被派发的 agent 可能还有转了后台的调用（比如它又派了活），之后的结局会叫醒它接着干。所以要等会话安静下来：没有在跑的一轮、没有待处理的输入、没有还没结算的后台调用，才以最近一轮的结局为准：正常结束取它的最终回复为报告，失败或被取消则派发以失败收场。没安静就按还在进行，下一次对账再看。

### 报告交到哪

报告成立与它的交付是两次提交。交付的位置由交付那一刻派发方的调用还在不在等决定，问的是 Tool：

1. 调用还在等：报告成为这次调用等待的答复，调用带着它继续，报告就是调用的结果。
2. 等待已经关了（调用被停下、被撤回，或以结果不知道收场；派发方那一轮被取消或被插队不关它，调用在后台）：报告作为一条输入送进派发方的会话，来源 `dispatch.report`，叫醒它。
3. 派发方的会话已归档：记 `undeliverable`，报告留在登记里，读派发时读得到。

Tool 对「交给等待」的答复只有三种：已交、等待已关、读不到。只有答「等待已关」才改走第 2 条；读不到时不动，按原身份再问。送输入用由派发身份派生的提交标识，重送认回同一条。所以一份报告不会两处都交，也不会两处都不交。

失败、撤回与 `handoff` 的结局同样交给还在等的那次调用，成为它的答复；等待已关时登记里只记下「等待已关」，不送输入，这个结局读派发时读得到。

派发的调用发起即在后台：命令 `dispatch` 声明 `background: { unless: [], start: 'launch' }`，调用方不用传参数，派发方的这一轮当场接着走；按 Tool 的通用规则，这样声明的命令必须带意图，后台调用列表靠它说明这个 agent 在做什么。等报告的等待契约声明 `background: 'waits'`，所以这次调用在后台仍挂着它的等待，第 1 条照旧成立：报告成为等待的答复，调用以它收场，Session 把这个结局作为一条提醒交给派发方，提醒头写明调用的短号与意图。人或 agent 用 `BkgToolCalls terminate` 停下它，只关等待，不撤回派发：派发与子会话照旧，报告改走第 2 条。要把工作收回用撤回。等待被关时，调用按 Tool 的规则以 `interrupted` 收场，结果是一段文字：派发仍在进行，报告以后会作为一条提醒送到。

### 撤回

撤回只对 `spawn` 与 `delegate`，只由派发方做。撤回成立与报告成立按派发登记的提交顺序裁定，先到的成立。撤回成立之后请求取消被派发的那一轮；请求、证实停下、外部效果三样分别报告，不把请求说成已停。撤回不归档子会话，不撤它已经做出的效果。派发方的调用还在等时，撤回的结果成为等待的答复。

### 消息

一条消息从一个会话的 agent 到另一个会话的 agent。资格：两个会话同属一个租户；接收方没有归档；不是发给自己；发送方此刻许发。不要求派发关系，兄弟与隔代的子会话之间也通。

消息以来源 `dispatch.message` 送进接收方的会话，带发送方的会话标识、它的 Agent 定义的名字、它与接收方的关系。接收方有没结束的一轮时按会话的输入规则追加，否则开新的一轮。消息不出报告，不改任何一次派发的状态。

拒绝说得出是哪一条：对方不存在或不在本租户（两者答同一句）、对方已归档、发给了自己、此刻不许。拒绝里不带对方的任何内容。送达的结果不知道时按原身份再送，不换身份。

### 上限

嵌套深度至多 2：主会话是第 0 层，它的子会话是第 1 层，再下一层是第 2 层，第 2 层的会话不能再 `spawn` 或 `delegate`。`handoff` 建的是主会话，从第 0 层算起。深度是会话关系的事实，由 Session 给出；本组在受理时判。

一个会话同时处在 `accepted` 或 `started` 的派发数有上限，取自配置。超过任一上限答拒绝并带原因。

### 对账

每一种「结果不知道」都按原身份重做同一步，不换身份、不另起一次：会话的身份由租户、系统主体与派发身份派生，重建认回同一个；送输入用派生的提交标识；交给等待按派发身份认回。进程重建之后，对账从登记里找出没走完的派发接着走：`accepted` 的去建会话，`started` 的去读起始输入的去向，`reported` 而没交付的去交，`withdrawn` 而停止没证实的去问。

### 工具 `Agents`

| 命令 | 做什么 | 条件 |
| --- | --- | --- |
| `help` | 用法 | |
| `dispatch` | 派发一份工作。`mode` 取 `spawn`、`delegate`、`handoff`；`agent` 是定义的名字；`instruction`；可选的报告形状期望 | |
| `message` | 给一个会话里的 agent 发一条消息。`to` 是会话标识 | |
| `list` | 列出会话，带过滤，每行带它与本会话的关系与派发的状态 | |

| `withdraw` | 撤回一次派发 | |
| `targets` | 列出现在能派给哪些 Agent 定义，带类型与说明 | |

`list` 是会话目录的一页接上派发登记。过滤、排序、分页与每行里的关系都是 Session 的；本组只按这一页的会话标识一次批量读出各自的派发状态，不逐行查。按派发状态过滤时反过来：先按派发方与状态从登记里取，再按标识批量读目录。`list` 给出的会话标识与工具 `Sessions` 给出的是同一个。按内容找会话、读一个会话说过什么，归 `Sessions`。

报告形状的期望交给被派发方，并随报告回显，不作校验。参数不对的回执带用法。

### 提供者与生命周期

派发登记在租户的存储分区里，一个租户的派发只在它自己的分区。本地提供者卸下时先不接新的派发与消息，在途的提交各有结局，再停对账。卸下不取消任何派发，也不归档任何会话；重新装上之后对账接着走。提供者不在时，工具的每个命令答依据不可用。

## 原则与约束

- 一次派发至多一份报告；报告恰好交付一次，位置二选一。
- 派发、被派发的会话、派发方的调用，寿命各管各的。
- 结果不知道就是不知道。按原身份再做，不换身份重发。
- 资格每次现核；装了工具不等于获准；派发与消息只在本租户之内。
- 本组不写会话的日志，不读会话日志的内部；要会话做的事都经会话公开的操作。
- 本组不认识人工介入，不向人要任何决定。
- 上限与对账间隔是配置，配置不能减弱上面任何一条。

## 不变式

| 编号 | 永远成立的性质 | 违反的后果 | 由什么守 |
| --- | --- | --- | --- |
| DP-01 | 一次派发至多成立一份报告；成立之后内容不变 | 派发方拿到两份互相矛盾的交代 | 模型 `DispatchReport` 的 `AtMostOneReport` |
| DP-02 | 已成立的报告至多交付到一个位置：调用的结果，或一条输入 | 同一份报告让派发方做两遍 | 模型 `DispatchReport` 的 `DeliveredOnce` |
| DP-03 | 派发方的会话没有归档时，已成立的报告不会停在两处都没交而再无人推进 | 派发方永远等不到报告 | 模型 `DispatchReport` 的 `NoStrandedReport` |
| DP-04 | 撤回成立之后没有报告成立；报告成立之后撤回不成立 | 已撤回的工作又交回结果 | 模型 `DispatchReport` 的 `WithdrawExcludesReport` |
| DP-05 | 派发方的每一次 `dispatch` 调用都有一个结果：报告、失败、撤回，或等待已关的说明 | 调用永远不返回 | 模型 `DispatchReport` 的 `CallAlwaysSettles` |
| DP-06 | 一次受理至多建出一个会话；重做认回同一个 | 一份工作被两个子会话各做一遍 | 契约测试 |
