# 日历

## 总体架构

日历包组回答一个问题：一个调用方怎样按明确的日历与版本，得到可指认、可复核的日别与工作日计算；这些版本知识又怎样从权威来源发现、校验、一致地发布与保管，并让人看得见它是否健康。

| 成员                       | 回答的问题                                                                                                            |
| -------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| `calendar-contract`        | 日期值、不可变快照、查询与供应服务端口、请求与结果、错误长什么样。纯数据与 schema，不依赖 Cordis 与存储               |
| `calendar`                 | 纯日期计算、查询应用、供应的解析与政策、供应应用（种子、校验、刷新、健康、恢复）怎样工作。不依赖 Cordis，不选存储后端 |
| `calendar-cordis-contract` | 日历在这套系统里以哪三个服务出现：查询服务、计算服务与供应服务的定义与键                                              |
| `calendar-local`           | 本机的发布存储与供应存储、受限的来源获取、发行种子的读取、供应运行器、设置环境投影与设置声明、计算服务，以及 Cordis 提供者 |
| `calendar-tools`           | 给 agent 的只读工具 `Calendar`：多命令的参数与结果、按调用绑定计算服务并核对租户                                      |
| `calendar-protocol`        | 公开协议 `calendar/v1` 的协议契约：目录、生效环境、供应健康与一次日期计算。纯数据                                         |
| `calendar-access`          | `calendar/v1` 的接入插件：核对登录与租户、取主体、调日历的服务、映射结果                                              |
| `calendar-ui`              | 界面模块：桌面侧栏的「日历」页                                                                                        |
| `calendar-adapters`        | 邻域的端口由谁来适配：Runtime Context 的两个租户级块（生效环境、供应风险）的声明与读者；给通知的贡献（来源 `calendar.supply` 的声明；供应风险块直接以通知的事项形状发布）。日历里只有它认识邻域的契约；通知的贡献是单独的插件，不装它日历照常 |

依赖只朝契约：`calendar-local` → {`calendar`、`calendar-cordis-contract`、`calendar-contract`、`sql-contract`}；`calendar-tools` → {`calendar-contract`、Tool 的公开作者协议}，不依赖 `calendar` 与 `calendar-local`；`calendar` → `calendar-contract`；`calendar-access` → {`calendar-protocol`、`calendar-cordis-contract`、`calendar-contract`、接入的贡献类型}；`calendar-ui` → {`calendar-protocol`、客户端装配、SDK 的客户端核心、公开契约、`frontend` 这一组}，不依赖日历的任何别的成员。查询应用先核资格，再解析日历与版本，在一份不可变快照里完成计算并带回实际依据。供应应用把来源材料解析、校验之后，经存储的具名参加者把新版本与当前发布事实在一次提交里写入；提交之后的反应经 outbox 交出。查询与供应可以在不同实例里运行，但消费同一份公开契约，不共用进程或数据库作为前提。

## 领域边界

日历拥有：日历身份与适用范围；不可变的版本知识（覆盖、星期默认表、逐日例外、知识截至、出处）；当前发布指针与发布代际；日期分类与工作日算术；供应的来源政策、校验、待裁、发布、恢复与健康；发行种子与发行把关条件。

日历不拥有：消费者选了哪份日历与时区（设置）；谁能读、能配、能发布（身份与授权）；Schedule 的身份、规则、预览与 Job 的接受、冻结、去重和补跑（日程）；通知的受理与送达（通知）；工具调用的准入、结果保管与长结果的读回（Tool）；SQL 提交与耐久的实际保证（存储提供者）。日历只读既有设置，不保存第二份消费者环境。

本组只认通用角色：可信上下文里的主体与租户、调用方给出的查询范围与依据、原操作身份。

本组需要、由别人提供的：

| 需要                             | 对方                              | 本组需要它做什么                                        |
| -------------------------------- | --------------------------------- | ------------------------------------------------------- |
| 有效环境读取                     | Runtime Context 的租户级块 `calendar.environment`，值由装配从设置供 | 一次读取同时给出时区、日历与修订；缺值如实答缺失        |
| 读取、配置与发布资格             | 身份与授权                        | 每次操作现场答当前资格；拒绝与未知分开                  |
| 具名命令与事务参加者             | 存储（`sql-contract`）            | 在一个事务域里写入版本、出处、指针、代际、回执与 outbox |
| 反应的承接                       | 健康投影、唤醒与通知的拥有者      | 承接 outbox 里提交之后的反应；重复告知不产生新版本      |
| 工具作者协议、结果保管与 offload | Tool                              | 登记工具贡献，保管完整结果，按当前资格读回              |

本组为别人提供的：

| 提供                                             | 对方                             | 本组提供什么                                 |
| ------------------------------------------------ | -------------------------------- | -------------------------------------------- |
| 查询服务（目录、读取、解析、分类、算术）         | 日程、独立程序、接入插件         | 按明确依据计算并带回实际身份、版本与观察位置 |
| 计算服务（按调用方生效的日历回答一个日期问题）   | 日程、`calendar-tools`、接入插件 | 选择固定为调用方生效的日历与当前版本，带回实际依据 |
| 供应服务（种子导入、刷新、健康、恢复）           | 系统管理入口与装配               | 发布新版本、报告健康与未完责任               |
| 供应风险块 `calendar.supply-risk`                | Runtime Context 的租户级作用域；经 `calendar-adapters` 的通知贡献给通知 | 此刻开着的供应风险，每项身份稳定             |
| 发行把关函数 `inspectCalendarRelease`            | 发行应用的发行检查               | 按政策与日期判一份发行：通过、警告、阻止     |
| 服务键 `calendarQuery`、`calendarCalculator`、`calendarSupply` | Cordis 装配        | 唯一的服务定义；提供者继承它                 |
| 设置声明（时区、生效日历）                       | 设置与应用装配                   | 两项个人设置的定义与默认值                   |
| 工具 `Calendar`                                  | Tool 与 agent                    | 只读计算，能力只有 `calendar.read`           |
| 公开协议 `calendar/v1`                           | 接入入口、命令行与界面           | 目录、生效环境、供应健康与一次日期计算       |

## 心智模型

把一份日历想成一叠写好就不再改的版本，加上一根指向「当前发布」的指针。查询总是先选定一份版本，再在它上面算；指针移走不改旧版，旧版仍能按原样复核。供应是另一条独立的线：发现、取材料、校验、和当前版比较，通过了才在一次提交里铸出新版并挪动指针。查询从不触发供应，供应坏了也不抹掉已经能答的旧版。

计算是固定依据上的偏函数：日期在覆盖内才有分类，覆盖外不猜普通工作日。答不出有四种不同的原因，彼此不冒充：缺选择或版本、覆盖不足、合法地不存在（`null` 是有依据的成功）、预算用尽。日历只做日期计算；什么时候做什么事、Job 接不接受，都是日程的决定。

最容易想错的几处：国家名不是日历身份，美国联邦日历不是全国放假；下载成功不等于发布；超时不等于没发布，要按原操作查回；取消请求被受理不等于发布被阻止；安装时间不是知识截至；一个全局的固定天数代替不了每份日历自己的健康政策。

## 应然设计

### 身份、版本与时间

- 日历身份表达业务适用范围；版本身份表达不可变知识；发布代际表达当前指针的提交次序。内容摘要、供应操作、契约版本、来源版本与运行实例代际各自分开。
- 一份版本保存覆盖、恰好七项的星期默认表、按日期唯一的例外、知识截至、合成时点与出处。半日事实只作出处备注，不改变全天分类。
- 日期只用 ISO 本地日期；分类不依赖当前时间；时区运算显式进行，不靠运行环境的缺省。
- 已发布的版本不可变：修订用新版本表达，同一版本不重绑定数据，当前发布变化不改旧内容；没有下架、到期删除或自动清理。实例退出、缓存失效、存储换代都不删除版本。

### 依据解析与查询

- 目录查询只要合法范围与读取资格，不要求日历身份、生效选择、版本、日期或规则输入；合法空目录与查询失败可区分；它不触发刷新或配置。
- 单历的读取、解析与计算必须明确给出日历身份（或明确请求某个消费者上下文的生效选择），并明确给出指定版本或当前已发布版本。没有生效选择不代选，没有版本不藏缺省。
- `latest` 一次捕获发布代际与版本身份，`pinned` 只读那一版，不随当前发布变化。一次计算只用同一份版本的内容、覆盖与出处，并带回实际采用的依据；直接计算与「先解析再按返回的身份与版本计算」等价。两次查询之间设置或当前版变化时如实报告不同依据，不混用。
- 有效环境必须是同一修订里的时区与日历，不拼两次读取；显式的空日历不被缺省日历替代。
- 读请求取消只停这一次观察；分页与投影标出观察位置，不外推成跨请求的永久快照。

### 日别与工作日算术

- 覆盖内先取逐日例外，没有例外时取星期默认表；覆盖外分类无定义。实际补班、observed 与法定例外不被星期模板覆盖。
- 前后增减 N 个工作日从起始日之后或之前开始数；N 为零返回起始日，即使它不是工作日。区间计数包含两端。合法输入、方向、版本与覆盖不由库的缺省补全；必要路径跨过未知日期时不跳过、不猜。
- 正序找第 N 个工作日：找到目标时只要已检查的前缀有覆盖；答「不存在」或找最后一个时，需要整个区间的依据。
- 合法输入推进越过四位年份的日期域时答覆盖不足，日期为空，并标出越过的是下界还是上界；普通的覆盖缺口带回实际缺失的日期；搜索预算先用尽答搜索上限。

### 有界计算

- 有界求值是另一个函数：合法且有答案的输入可能因预算不足答「受限」，所以它不是原偏函数的精确全化。领域上无答案、没算完、提供者故障与权限拒绝分别表达。
- 每一步是终止、确定、没有隐藏 I/O 的全函数；活动状态每递归一步预算严格减一；已终止的结果在零预算下仍可返回；足够的预算一定取得已有的答案或确定的「不存在」。组合只允许有限层，失败短路，不允许无限重试或无界展开。
- 计算与预览只读：不猜自然语言意图，不改设置、日历或 Schedule，不接受 Job、不扣次数、不触发动作或通知。整体 Schedule 的规则与预览归日程。

### 供应：发现与校验

- 每份日历沿自己的权威发布节奏发现新材料，跟进未来年度与已发布年度的修订；不能只重取固定旧地址就报没有变化。来源分角色：真值、对照、例外来源、远期探测；来源适配只做探测与取得，解析与政策在 `calendar`，不写版本库。
- 下载与格式合法不代替业务校验。校验至少包含格式、日期唯一、覆盖连续、关键锚点、补班合理、来源血统、对照差异、与当前版重叠部分的变化、覆盖不收缩。
- 规范内容相同是无变化。覆盖累积与有新权威出处的合法修订可以发布；覆盖收缩与关键假日缺失不替换当前版；没有新出处的静默重叠修改保留原材料、摘要与差异待裁，不自动接受也不丢弃。
- 声明为两个独立来源时必须实际独立（采集与转录路径不同）；同源转写不满足。补充材料只用于既有检查，不算新的独立对照，不代替真值回链。
- 美国范围只是联邦日历；中国的半天与地方节日等限制留在语义边界里。知识截至只取来源自己的依据（完成的有界扫描、组件修订时点），不能用 HTTP 日期、下载或安装时间代替。

### 发布的一致性与恢复

- 新版本、出处、当前指针与代际、操作回执与发布后的 outbox 由供应拥有者在一次提交里写入；不能先答成功再补版本，不能确认一个指向缺内容、未校验或半份数据的当前版。
- I/O、解析与业务校验在事务之外；提交时复核期望的发布代际、原操作与当前资格；前提变了就重新校验或报冲突，不能用旧校验覆盖后来的发布。同一版本异内容拒绝。
- 发布的版本精确关联原来那份候选（校验过、等着发布的材料，由 `candidateRef` 指到）；读取当前版先固定版本身份，再读该版的原发布材料并核来源、血统、权威、原文摘要与两个时点。不能用后来「无变化」的回执替代原材料；关联或材料缺失明确失败，不降成空贡献。来源权威引用与本机的原材料引用分开，后者不成为种子的可移植身份。
- 超时、断连、回执丢失不证明发布没发生：保留原日历、候选、提交关联、已确认部分与未知范围，先按原操作查回，不重铸版本、不回退旧数据；已确认的发布只接续未完的反应，仍未知的继续保管。
- 提交之后的反应（健康投影、唤醒、维护提示、通知）失败只留下未完的反应责任，不把发布报告成未发生、不改旧版、不重做发布。确认意图的键在首次发出前保存；同键同内容认回旧结果，同键异内容拒绝；未知时不自动换键，重新获准的确认用新键。
- 维护取消在提交前确认成立时才阻止这次发布；已成立的发布不因取消、停止或退出撤回。取消与提交竞争或效果不可确认时按原操作查回。已经发生的抓取、存储与通知效果如实保留。

### 种子与发行把关

- 发行种子为声明的每份日历带受校验的版本，至少完整覆盖发版日所在的自然年，并含发版时权威已发布的更远覆盖；这不等于从安装日起滚动十二个月。
- 安装先同步校验并落地种子，种子损坏明确失败，不注册一个假就绪的服务；之后才尽力联网刷新。无网不阻止覆盖内的查询；刷新失败保留现有数据与失败事实。重复初始化不重铸同一版本，不用旧种子回退；新种子走同一校验与发布路径。
- 健康与查询能力分开：覆盖与知识截至分别显示，最近成功更新、连续失败、待裁的材料与覆盖余量可观察，按每份日历的政策在覆盖耗尽前告警。
- 发行时任一日历达到严重条件不得发行，警告必须显式声明；政策或状态未知不报通过。阈值由治理拥有者给出，技术提供者不偷填缺省。
- 判一份发行只有一个纯函数 `inspectCalendarRelease(发行, 政策, 日期)`：逐日历答通过、警告或阻止（严重或未知）。导入种子时以种子自己的发行日调它，发行检查以当天调它；判法不写第二份。
- 查询服务的健康读口答每份供应的日历的健康，次序同目录，资格同查询。查询不认识供应应用：健康经装配给的健康投影端口读，端口缺席时答不可用。供应应用仍只认系统归属。

### 供应风险与提醒

- 本组把此刻开着的供应风险发布成租户级块 `calendar.supply-risk`。每份日历至多三项：覆盖到警告线、覆盖到严重线、供应失败。身份是 `calendar.supply/<日历>/<种类>`，同一成因同一身份；警告升到严重是新的一项。分级未知不算开着的风险。任一日历的健康读不到时，整块答未知，不答空。
- 块的值归本组；谁被提醒、多急归通知的订阅。块直接以通知的事项形状发布，模式就是通知那个需要的形状：租户级持有者只把不经翻译的绑定交给读者。来源 `calendar.supply` 的声明（三种事件类型都是持续事项，绑定这个块）在 `calendar-adapters`，由发行装配登记。本组的其余成员不认识通知。

### 与日程的接缝

- 日历提供指定版本或当前版本的知识与真实失败；日程拥有最新版的校验与 Job 的接受、已接受要求的冻结、去重、等待、取消与补跑。
- 新版本发布不接受、取消、移动或改写已有 Job 的采用内容，也不生成重复的 Job。跟随用户环境的安排随同一环境修订重算还没接受的未来；显式安排不随用户选择改变日历身份；显式 `latest` 跟随同历发布，`pinned` 保持指定版本；没有用户环境的系统归属不能跟随用户环境。
- 供应恢复不证明漏过的工作已经做了；查询或预算不成为 Job。

### 缓存

- 缓存键含实际身份、不可变版本与影响结果的全部输入；租户的选择与受保护投影再含所有者与资格。缓存只有加速权：不发布版本、不改设置；当前选择或版本变化不造成新旧混合；陈旧的目录与健康投影标出观察位置，不能以投影消失证明版本删除，也不能以旧缓存掩盖查询故障。

### 生命周期与装配

- 提供者停止先拒新准入，再按原操作把候选、已提交的发布、未知结果与 outbox 认回、排空或可靠交接；不能删了注册就宣称业务完成。
- 每个实例只撤自己的注册、监听、计时器、取数观察与存储使用权；两代清理交错时只释放自己的令牌；晚到的结果回到原操作；共享资源只释放自己的使用权。dispose 不回滚发布、下载或通知。部分初始化失败也收口；清理失败报告实际残留。供应计时器只用于唤醒，到期与探测状态在存储里。
- 自己持有的供应应用或运行器由提供者停止；借入的不停止。关闭先拒新调用，再有界排空，报告未完调用与失败。
- 服务定义在 `./cordis`，查询与供应各一个键；定义不授执行资格；提供者继承定义并持有资源，不把资源建在调用方的上下文上。方法不经上下文注入身份，不把本机资源写进跨部署的值。

### 计算服务

- 计算服务回答一个日期问题：某天的日别、两天之间的工作日数、前后数 N 个工作日、某天之后的 N 个工作日、一段时间里的第 N 个工作日。选择固定为调用方生效的日历与当前发布版本，一次调用只解析一次；它是查询服务对「消费者生效的日历、当前版本」这一个明确选择的封装，不另复制计算。
- 调用方不传日历与版本。用哪份日历由消费者的设置决定；消费者没有生效的日历时答缺选择，不代选。答复与查询服务的解析结果相同：实际日历身份、版本、覆盖与结果。
- 计算服务与查询服务共用资格、环境与快照，资格按查询的 `resolve` 现场核。

### 工具

- 一个多命令工具 `Calendar`，命令只做日期计算，能力只有 `calendar.read`。工具注入计算服务，不注入查询服务；参数里没有日历与版本，agent 不选日历。目录、单历读取与生效环境给人看，经公开协议提供，不放进工具。供应、发布、种子导入与发行管理不暴露给 agent。
- 参数不接受可信身份、权限上下文、存储、种子或任意回调；可信上下文每次调用从宿主取得，宿主解析出的所有者必须属于调用方的租户，不属于就拒绝。日历应用仍现场核资格。调用与直接计算的错误与依据含义相同。
- 完整的判别结果交给 Tool 保管与 offload；编码超过上限（16 MiB）明确失败，不以裁剪冒充成功。

### 设置环境投影

- 本组声明两项个人设置：时区与生效日历，设置项的类别为偏好，不是秘密。本组经设置的贡献口「独立设置」带来这份声明，`calendar-local` 的 `./cordis` 入口导出贡献插件；它是独立设置，不挂在任何资产上。默认值写在声明里，随发行带，用户看得见值来自默认。生效日历的取值是已供应日历的身份，逐值带人读的名字。设置的值与写入归设置；本组只声明并读取。
- 生效环境经 Runtime Context 的租户级块 `calendar.environment` 读到：块与读者在 `calendar-adapters`，装配从租户的独立设置供值，查询以协调者的身份读。读到缺项或未知答不可用，不当成「没有生效的日历」。
- 供值一侧从原调用恢复受信主体与已采用的目标映射，一次读取取得时区、日历与修订。缺值保持缺失；部分、错配、非法值与依赖异常答不可用。设置的可读不等于日历的可用，日历的使用权另行判断；适配不发行主体、不改偏好，不为后续 Schedule 写入提供原子当前性。

### 协议、接入与界面

- `calendar/v1` 的操作都要代租户行事、都是读：列出目录、读生效环境、读供应健康、回答一个日期问题。回答可以点名日历与版本，都不点名时用生效的日历与当前版本；只点名版本答非法。日期用公开契约的日期叶子。答复是给客户端的投影，不转发领域对象；计算的答复带实际依据，生效环境的答复带读取时的设置修订，供应健康的答复带每个来源最近一次的观察，失败的带来源自己给的原因；值来自默认还是用户设置，看设置的读写面。
- 接入插件按调用现取查询服务与计算服务，取不到答依据不可用；领域抛出时答依据不可用。不存在、别的租户与无权对外是同一个拒绝。
- 界面模块往外壳的页面位置放一个只读的日历页：生效的日历、时区与版本，供应的日历与它们的健康，查一天（可以选日历与版本）。改生效的日历与时区在设置页。它只依赖客户端装配、SDK 的客户端核心、公开契约、`frontend` 这一组与 `calendar-protocol`；没有租户时不画、不发调用。样子见下一节。

### 日历页的样子

这一节写这一屏用哪一族、长什么样、每个状态说什么。族的画法、状态、反馈与语气的规则在[视觉规范](../../.meta_harness/agents/skills/visual-standard/canonical/SKILL.md)与它的[规则与 token 的索引](../../.meta_harness/agents/skills/visual-standard/canonical/references/rules-index.md)，共用件在[前端规格](../frontend/SPEC.md#共用界面件)，这里不重写。

日历页的页面标识是 `calendar`，导航「日历」，图标 `appointment`。

- 族与多重：单列页（`PageColumn` 加 `PageHeader`），分三段，每段是共用件的段（`Section`：上面一条细线、正文字号的强标题）。内容是正文的轻重，只有「查一天」有一个动作。
- 骨架：页头「日历」，说明「日期计算与日程用哪套日历、哪个时区。这一页只读，改在「设置」页。」。下面依次三段：
  1. 「生效的日历」：一张事实表：日历、时区、版本（没有时写「没有可用的版本」）。
  2. 「供应的日历」：一张表，一份日历一行，列是名字、时区、版本、覆盖到（覆盖的最后一天，表格数字；没有覆盖写「没有覆盖」）。生效的那一份在名字后面带一个中性的小胶囊「生效」。供应健康并进这张表，不另画一张列相同的表：正常的一行什么词都没有；不正常时行尾一个状态词，原因写在名字下面的弱墨一行里，不另起一个满宽的行。原因依次是失败的来源与它给的原因（「来源 X 失败：…」，来源没有给时写「没有给出原因」）、领域给的原因、「连续失败 N 次」。
  3. 「查一天」：一行里是日期字段（提示照现在的「年-月-日」加一个例子）、日历下拉（「生效的日历」与各份供应的日历）、版本字段（只在选了一份具体的日历时出现，提示「版本，不填用当前版本」）与「查」；回车也是「查」。结果在这一行下面原地到达：一张事实表，哪天是工作日、节假日还是休息日（调休的后面加「（调休）」），与依据（日历与版本）。
- 行尾的状态词：一行至多一个，取最要紧的那个，次序是「供应失败」（失败色）、「覆盖即将耗尽」「覆盖快用完了」（琥珀）、「有待处理的更新」（中性）、「供应状态未知」「覆盖情况未知」（中性）。供应正常、覆盖充足时不写。
- 加载：每段各自读，读的时候用一个加载状态，词是「读取中」。「供应的日历」一段先等清单：清单读到之前整段是加载状态；清单读到而健康还在读时，表照画，行尾不写词，表下面一个「读取中」的活动标记。
- 空：「供应的日历」没有一份时写「部署供应的日历会列在这里。」。
- 部分：清单读到而健康读不出时，表照画，行尾不写词，表下面一句读不出健康的通知，带「重试」。
- 读不出与被拒：写在出事的那一段里，用下面的句子与语气；读不出的都带「重试」，领域答的拒绝不带。外壳给的租户读不懂时，页头下面一句「读不懂当前的租户。」，不发调用。
- 禁用：选「生效的日历」时版本字段不出现，不画灰掉的字段。日期为空时「查」不可点。
- 内容过长：原因的弱墨一行换行，不截断；表的名字一列换行。
- 反馈：「查」的结果看得见，原地到达；在查的时候只有「查」显示等待。查不到时，一句行内通知写在这一行下面，表不出现。再查一次时上一次的结果让给新的。别的都是读，没有回执。
- 用的件：`PageColumn`、`PageHeader`、`Section`；`FactList`、`FactRow`；共用件的表（`Table`、`TableBody`、`TableRow`、`TableCell`）；`StatusPill`（「生效」）；`StateWord`（行尾的词）；`Input`、`Select`、`Button`；`LoadingState`、`LoadingIndicator`、`EmptyState`、`InlineNotice`。

## 原则与约束

- 一个事实一个拥有者：设置、资格、日程决定、通知与工具保管都经端口读结论，日历不存第二份。
- 版本不可变，事实只追加：修订、撤销、待裁都是新的事实，不改旧的。
- 失败如实分类：缺依据、覆盖不足、合法空、预算用尽、故障与未知各有含义，互不冒充。
- 未知按原操作查回，不重做；只声称实际已阻止或已确认的效果。
- 产品含义（来源优先级、覆盖与健康政策、日别规则）由本组实现，不交给通用库的缺省行为；不建设世界节假日引擎。
- 公共消费不要求同机、同进程或共享数据库；跨部署的值不含运行时对象。
- 改变定义域、空结果、覆盖或预算的语义时，先改形式模型与负控，再改实现；有限模型检查、抽象证明、源码符合性与真实集成是四层不同的证据。
