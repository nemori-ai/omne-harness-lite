# settings 内部设计

本页说明当前核心实现。精确公开类型归 src/index.ts，实际持久化及跨域组合归 settings-local。

## 设置的输入、求值与采用

settings 的机制以合法声明、配置目标依据、来源配值和锁定为输入，输出有效值及依据；资产策略另提供持有约束。公开形状由 schema.ts、ports.ts 与 application.ts 固定。设置声明、缺省和清除分别沿 [SPEC](../SPEC.md#assignment)，同层 shared 与 local 合成沿 [工作区行为](../SPEC.md#workspace)，不能复用权限上界算法。

实际托管写入由 settings 提供者承接当前资格、目标、项、允许来源和预期依据；资产路径还核验持有，与持有移除及项变化竞争的提交关系由 [ASSET-M01](../../assets/docs/internals.md#asset-m01-完成与来源协议)协调细化。Plugin 的提前启用求值通过 [组协作](../../docs/key-flows.md#组合内含成员与外部引用)交入 assembly，本成员不持其整体状态机。

## 后续设计与验证

应用操作、身份及版本含义沿下文与协议设计；公开 Schema 与普通项校验已有实现，秘密保管端口尚不支持。持久化映射归 settings-local。提供者须兑现 [失败与恢复](../SPEC.md#failure-and-recovery)，成员验证托管写入、清除及来源求值，组协调者验证完整清单和持有生命周期。应用入口已有源码；有限协议模型及其已检查范围独立沿 verification 说明，不代替运行实现。

## 独立核心与组合适配

[组模型](../../docs/settings-composition.md)拥有数理分解与跨成员责任。纯核心接收固定声明、合法来源配值、允许的规则和预算；不读取资产仓库、不猜租户或工作区。`SettingDefinitions` 是不可变值，`SettingAssignments` 在一个目标提交范围内维护配值、锁及 revision，求值结果是不可变投影。

资产适配器将固定定义与合法持有映射为目标策略；独立适配器将功能定义与真实配置目标映射为目标策略。应用服务依赖相同端口，不做按资产类别的 switch。独立设置没有 holdingRef 也能调用公开查询和命令；托管写入仍须有可信资格及目标守卫。

## 目录与应用服务分工

`readCatalog` 聚合当前部署范围内合法贡献，分别生成管理或运行视图。字段与组来自固定声明；当前值、来源、锁定、可操作性及安全解释由服务计算。目录返回快照标识、依据、分组、字段与分页/不完整状态。完整运行求值不得接受不完整目录。

`evaluate` 与 `previewChange` 只读，`setValue/clearValue/lockProperty/unlockProperty` 写入一个受支持的目标范围，`getOperation` 查询原操作结果。贡献登记与秘密使用是分离接口，不与普通设置查询共享全部权限。实际写入口为 change，以 set/clear/lock/unlock 判别动作；公开服务不提供四个独立方法别名。

目录读取先取得固定声明与一致目标依据，再解析语义元数据和当前可读字段。分页用不透明游标绑定快照/范围/筛选/排序；重读资格失败则拒绝后续页。缓存只复用仍满足相同依据及当前读取资格的材料，失效不是空目录。字段的名称、用途、约束、默认/清除含义和采用后果为发布验证必填；单位、枚举标签等按类型必填。没有人可读说明的字段不以内部 key 顶替成功发布。

## 提交与撤除

应用层先构造纯变更决定，再由条件提交端口在当前目标/资格/定义/锁/revision 成立时提交。先查后写不满足该契约。配值、来源计数、操作结果和 outbox 在同一受支持提交范围内保存；外域参与者保证竞争事实与 fence 的共同变化。本地映射见 settings-local 的参与者与终态协调；完整系统采用另行验证。

close 停止接收新写，使在途操作到达可查询结果，最后释放资源；超时保留未决操作供恢复。贡献撤除不能删除已保存值，不证明外部副作用回滚。依赖不可用时不继续授予新操作；旧快照是否还能使用按其原采用及授权条件判断。

实现验证映射随 [verification](../verification/README.md) 维护。独立使用与资产组合必须运行同一符合性套件，另测各目标策略自己的资格和来源；不能用“公共服务参数里强制有持有”让独立实现违反替换原则。

公共输入、目录语义元数据、命令信封及失败分类见[应用协议](protocol.md)。当前源码已导出纯核心与应用端口，SQL 和目标提供者的实际组合单独验收。

## 当前实现分解

`schema.ts` 拥有声明、语义元数据与来源形状。`definition.ts` 校验组关系和元数据，并复用 Ajv 校验值。`evaluation.ts` 只处理已经合法化的有序来源，不解释身份或持有。`commands.ts` 在固定事实下生成变更决定，保留 raw 配值变化与 no-op 的区别。

`application.ts` 把一致授权投影交给查询端口，把当前条件提交交给命令端口。每页重新读取资格和依据，基准变化拒绝续页；目录局部失败不能成为完整运行快照。`registry.ts` 只管理装配贡献的可用性，同版本不同内容冲突，撤除不删除配值。目录仍需实际目标提供者，不从注册表推断访问权。

纯变更决定不是当前资格证明。SQL 的先行拥有者参与者必须与设置提交在同一受支持事务里核验当前目标与资格。Identity 独立事务域通过公开资格预留、目标终态和治理待决门兑现协调；外部的一次资格读取不能代替这个协议。

## 定义和来源重新采用

rebase.ts 接收当前状态、拥有者选定的新定义与新来源布局，以及逐条 retain/discard 决定。所有旧配值和锁都必须有决定，额外或重复决定被拒绝。保留值须通过新项校验。显式放弃不等同于改名迁移，新增来源没有旧值可继承。状态实际变化才增加 revision。

纯决定不授予重新采用权。本地 createSettingsMaintenance 是部署拥有者持有的维护能力，普通租户命令端口不暴露它。定义不匹配期间普通读取和写入拒绝，维护操作以精确 from/to、expectedRevision 和当前目标事实完成重新采用。配值变化记录包含 value 与 rebase 两种判别，均不含秘密或原值。
