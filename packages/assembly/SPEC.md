# Assembly

## 总体架构

Assembly 包组回答装配与交接领域里与 Cordis 贴得最近的三个问题。第一，采用这一层：一次求值怎样从合法的来源、定义、实现与运行条件得到一份可采用的执行配置，换代时新旧推进者怎样交接。第二，关闭：一个资源拥有者计划退出时，它手里的一组租约怎样有确定结局地关掉。第三，进程这一层的装配：进程里的每个插件属于哪一层、谁能换它；一行怎样在服务不停时换实现，换之前怎样算出会动到哪些行；一行坏了怎样自恢复，或进程怎样在期限内带着原因退出并被拉起；进程启动哪一版，起不来怎样退回。另外，它为全系统提供少数几个 Cordis 集成辅助，并拥有时间源：一个装配好的系统里读时间与等时间的唯一来源。

| 成员           | 回答的问题                                                                                                                                                    |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `assembly`     | 一组租约的关闭协议（准入、排空、按序执行退出步骤、给出报告）；采用与重装的行为规则的位置；进程这一层四样纯的东西：行的声明与依赖图上的影响计算、行的一代的状态机、监督的状态机、版本指针与戳的状态机 |
| `assembly-cordis` | 把进程这一层的四样接到 Cordis 上：稳定的入口；行的装载方（装入、核来源、备着、换代、排空）；行的监督（依赖没了、回来、期限）。依赖 `assembly`、`dynamis`、`dynamis-cordis` 与 Cordis |
| `kernel-basis` | Cordis 集成辅助：带配置校验的插件定义 `definePlugin`、可选依赖读取 `resolveOptional`、调用方 fiber 登记 `registerInCallerFiber`、测试装配 `startTestAssembly` |
| `time-source` | 一条时间线由谁拥有：墙钟与单调钟各一个读数、各一种等待；时间按真实、手动、空闲就跳、倍速四种方式之一前进 |

关闭协议是一个纯进程内的对象：资源拥有者为自己的一代资源建一个实例，接纳租约，退出时停准入、等租约释放、按自己给的步骤列表关后端，拿到 `closed`、`failed` 或 `timed-out`。采用协调者在新 Run 开始或租户显式要求重新加载时求值，把整份结果写成本次执行的采用依据；换代时它编排「停新准入、交接在途、撤依赖、关后端」的次序，每一步由各资源拥有者对自己的关闭协议实例完成。`kernel-basis` 不声明服务键，只把各领域都要写的几段 Cordis 胶水写一次。采用协调的公开操作、失败分类与耐久性质归装配与交接领域的采用协调设计（`adoption-contract`）。

进程这一层的四样纯的东西全是值与值到值的函数，写法和 Dynamis 一样。`assembly-cordis` 持有活的状态：入口背后现在是哪一代、每一行在监督里是什么状态。期限都从时间源读。应用只留三样：发行里有哪些行（清单）、进程的入口（命令行与退出码）、把监督者接到进程上。依赖方向：`assembly` 不认识任何领域；`assembly-cordis` 只认识 `assembly`、Dynamis 与 Cordis；应用认识它们。

## 领域边界

本组拥有：一组租约的关闭协议与它的报告；求值、采用依据、发布与重装入口的行为规则；Cordis 插件定义、可选依赖读取、调用方 fiber 登记与测试装配这几个辅助的形状与失败边界；时间源的读数、等待、推进方式与控制面；进程这一层的装配规则：两层与换的权限、行的换代与影响、监督与期限、装载与来源、版本目录、指针与戳。

本组不拥有：来源与业务规则（治理，见 `packages/governance`）；推进资格（原工作，Session 与 Agent）；调用事实与结果（实际执行者与消费者）；各能力的 Service 定义与服务键（各能力的契约成员）；发行里有哪些行、进程的入口与退出码、把监督者接到进程上（应用）；登记表上锁的答法与座位的换代操作（Dynamis）；租户层 fiber 的装载回路与底（Plugin）；桌面页面包怎样装、怎样验、什么时候切（桌面应用）；签名密钥的保管与轮换（发行流程）；fiber 状态与依赖注入（Cordis）；被关闭的资源本身（资源拥有者）；结果（操作结果归 `packages/common` 的 `operation-result`）；业务期限与时间读不到时的行为（各领域的时钟端口）；时刻与时长的文本（`packages/common` 的 `utc-instant`）；时区与显示格式（展示一侧）；用哪一种推进方式（应用的装配）。

## 心智模型

关闭协议像一扇只关一次的门。门开着时，按名字发租约；关门那一刻先上锁（之后谁来都答「已停止准入」），再等屋里的人都出来，等不到就如实报「超时」并留下名单，等到了就按清单逐项关灯，哪盏灯坏了记下来。门只管这一代：换代就是另开一扇门，旧门关不着新门里的人。门不知道远端是否可达，远端暂时不通不是关门的理由。

采用是一次拍照，不是一根活线。求值把当时合法的胜出者连同版本、清单与请求输入一起写进采用依据，这次执行从依据里读，不再回头问提供方；只在新 Run 开始或租户明确要求重新加载时重新拍照。拍到一半来源变了，就重拍一次；还变，就不发布，旧照片留着。

时间源像一台机器里唯一的那块表。表上有两个读数：墙钟告诉你现在几点，可以被拨；单调钟告诉你过了多久，只往前走。每个读数配一种闹钟：到几点叫我，过多久叫我。闹钟和读数在同一块表上，所以闹钟响的时候，表上的读数一定已经走到了那里。换一块可以由人拨动的表，整台机器就进了模拟时间，机器里的程序看不出差别，也拿不到拨表的手。

进程里的每个插件属于两层之一。官方层是发行自带的行与界面模块，加运维者在自己的部署里装的行；租户层是租户的 Plugin 带来的 fiber。两层的区别只有两样：谁有权装、换、撤，交到它手里的是什么。官方层归两级官方（发行方、这份部署的运维者），拿到的是整棵树；租户层归持有它的租户，拿到的只有口。装入、备着、换代、排空、起不来时退回，两层用同一套。

一行是一块门牌加门牌背后的一代又一代实现。依赖方认的是门牌，也就是入口；进程活着它就不换。换实现是在门牌背后换一代：新的一代先备着，启动成了才一步换上；旧的一代从这一步起不接新的调用，把名下在途的做完才算撤完。新的一代起不来，旧的照常服务。门牌自己没有状态。

最容易想错的地方：fiber 处于 `ACTIVE` 不等于存储可写、远端可达或工作已恢复；`dispose()` 完成、卸载完成或改写当前指针都不是关闭，也不表示业务收场、结果交接或外部效果撤回；同级 Cordis effect 的完成顺序不是产品的关闭顺序。

进程这一层还有几处最容易想错：

- 换实现、重跑、换进程是三件事。只有换实现不动依赖方；重跑照 Cordis 的规矩，连着注入它的子树一起卸了再装。
- 行的换代不是采用这一层的换代。前者换一行背后的实现，后者换一次执行的推进者。
- 一行回来的前提是它依赖的行都在，回来的次序跟着依赖走。
- 站稳与起稳都不等于到了 `ACTIVE`。站稳问的是这一行自己的就绪判断；起稳是进程就绪之后又过了一段稳定的时间。
- 锁只对更深的作用域起作用。租户的条目永远打不成整个部署那一层，所以锁伪造不了。
- 装进进程的模块卸不掉。每换一版多占一份内存，到进程重启才还。
- 换的入口不在对客户端开放的协议上，也不是给 agent 的工具。

## 应然设计

### 关闭协议：一组租约

这三节的关闭协议就是行的「一代的排空」用的那一套：停准入、等租约放开、按次序关、给报告。入口为每一代建一个实例。进程里的关闭只留这一套；进程的停机次序不在这里：先停准入，再做排空步，然后其余的行按依赖图倒着停（见[监督与期限](#监督与期限)）。

- 一个实例关闭一个进程里的一组租约；资源拥有者换代时另建一个实例。协议不打开代际，不把租约迁到另一个提供者，不选择关哪个后端；调用方给出步骤列表、排空超时与时钟。排空超时小于零时构造失败，此时还没有租约。
- 远端不可用不是停止准入；本地代理仍在时，调用方不调用 `close`，也不把准入设为停止。撤除本地提供者才是对该实例调用 `close`。
- 进程在 `close` 完成之前死亡，这次调用没有报告，不算成功；崩溃后的恢复归进程外监督。步骤失败或超时不回滚已经发生的外部效果。

### 关闭协议：准入与释放

- `admit` 必须带租约名字，没有默认调用方、租户或账号。准入开放时：空名字抛错，不新增持有；未持有的名字得到新 id；已持有的名字返回同一个 id；当前 id 被释放后再借同名得到新 id。准入停止后，`admit`（包括空名字）一律抛 `admission stopped`，不新增持有。
- `release` 在任何状态下都可以调用。只有传入的 id 仍是该名字当前持有的租约时才移除；旧 id 不能拆掉同名的新租约；重复释放什么也不做。释放不让 `close` 的 promise 确定，报告确定之后也不改写报告。
- `held` 按进入持有集合的次序返回当前持有的名字。`held` 与 `detachObserver` 都不释放租约、不停止准入、不让 `close` 确定；观察者离开不取消已持有的租约。
- 这些操作都不发出事件。

### 关闭协议：关闭与报告

- 第一次 `close` 建立唯一的关闭 promise；之后的调用（包括另一个 `caller`、从步骤或时钟里同步再调）都返回同一个 promise。被排除的调用方由第一次调用固定：它当时已被持有，排空就不等它。
- `close` 在返回 promise 之前就把准入设为停止，先于排空与任何步骤。
- 排空等到每个被等待的租约都释放，或注入的时钟走完排空超时。开始时等待集合非空而超时为零，直接报超时，不调用时钟。时钟走完时集合仍非空，报 `timed-out` 并按准入次序列出仍在等待的名字，步骤不执行；之后的释放不改写这份报告。时钟拒绝时，关闭 promise 以该错误拒绝，准入保持停止。
- 步骤按列表次序执行，每步是 `always` 或 `if-no-failure`。前面有步骤抛错之后，`always` 仍执行，`if-no-failure` 跳过并记入 `skipped`。抛错记为步骤名与消息（`Error` 取其消息，否则取字符串形式）。有失败或有跳过报 `failed`，列出已完成的步骤、每一项失败与跳过的步骤；否则报 `closed`，只列已完成的步骤。
- 关闭不取消租约；超时时仍被持有的租约一直持有到释放。promise 只在本进程内有效，不是跨进程的决定。
- 旧实例的 `close` 只等自己持有的租约，不释放新实例的租约，也不停止新实例的准入；旧报告确定之后新实例仍可接纳。
- 资源拥有者把在途结果的交接放在关闭后端之前；交接失败后，`always` 的后端步骤仍执行，`if-no-failure` 的跳过。

### 采用记录与失败

- 一次求值被采用时，持久记录是本次执行的采用依据：资产与定义版本、装配清单、固定的请求输入、适用执行条件。装配清单保存这次求值的来源、锁定的依赖身份与版本、扩展顺序；它不是活体句柄。
- 求值输入里的能力身份是类别加名字，不带版本；带版本的输入在求值之前被拒绝（`malformed`）。版本由来源层的层值决定：资产的「持有固定版本」与「跟随当前版」是层值。新的求值采用当时的合法胜出者；固定版本不豁免合法性、资格、锁定或撤权。Agent 定义总是解析为该身份最新的合法发布版本。
- 同一次执行从采用依据读取已记下的正文，不改写它。还没发出的 Tool 或 MCP 调用仍可按合法刷新看到新的定义与可用性；已记录的 Skill 正文不变，还没取用的 Skill 正文在取用时读当时的合法版本。
- 候选失败不发布新的采用依据，调用方得到失败记录，旧的合法采用保持。失败记录有四项：种类、身份、原因、旧采用是否保持。种类只有五种，没有成功种类：

| 种类         | 结果                                                                                     | 旧采用                             |
| ------------ | ---------------------------------------------------------------------------------------- | ---------------------------------- |
| 缺合法定义   | 装配失败，不是已采用。必需能力从未取得合法定义，或运行时自身必要依赖无法建立，都归这一种 | 保持；从未有过合法采用时写不适用   |
| 实现暂不可用 | 合法定义与必要绑定已具备时形成采用依据，并在依据里标明该能力暂不可用；不是装配失败       | 已有旧采用时保持；首次装配写不适用 |
| 候选被拒绝   | 返回原因，不是已采用                                                                     | 保持；从未有过合法采用时写不适用   |
| 来源未知     | 不用猜测补齐定义，不是已采用                                                             | 保持；从未有过合法采用时写不适用   |
| 无类别拥有者 | 不解释、不采用；未知类别归这一种                                                         | 保持；从未有过合法采用时写不适用   |

- 资产发布、装配成功、运行使用、旧实例退出是四件分开的事。

### 发布

- 注册表在一次求值作用域内合并候选项，只校验公共字段，不解释正文。同一能力身份只留一个胜出者；不同类别下的相同名字是两个身份。只有一份注册表，不按类别再拆。
- 一次收集有一个修订号；收集中来源变了一次就重试一次，再变则这次结果不完整，不缓存，也不替换上一份完整目录。能力、设置、权限分路求值；一次请求不混合旧模型档案、新工具 schema 与旧实现；任一路不完整，整份不发布。
- 发布是整份替换或完全不发布。发布前核对胜出者身份与所选候选一致，不一致则这次目录失效。取消优先于迟到候选；较新的完整快照胜过较早的；不完整的快照不胜出。原子性不靠某种数据库事务或 Cordis 布局成立，那会把布局变成产品要求。

### 重装入口与换代

这一节的换代是采用这一层的：一次执行的推进者怎样换。它和行的换代不是一回事，后者是一行背后的实现怎样换，见[行的换代：三种换法](#行的换代三种换法)。

- 只有两个入口：新 Run 开始时比较当前采用依据与这次求值，变了才重装；Run 执行中租户经系统斜杠命令显式要求重新加载。文件变化或 Git 同步本身不触发重装。不走这两个入口时，新选择可以保存，但不是采用依据，正在运行的组合不变，并告诉调用方新选择要到下一个入口才生效。
- 候选通过校验之前不取得业务推进资格；新旧并存期间两者的服务可见范围分开。重装失败保持旧的合法采用并返回原因，不调用旧实例的 `close`。
- 有效切换撤销旧推进权并保存接续依据，原执行不因此销毁；新推进者取得原 Run、新的 attempt 与候选装配。新候选兑现必要条件之前不切换新准入，旧租约与必需依赖留在原提供者。有效切换也不调用旧实例的 `close`。
- 旧实例退出是另一步：先停相应的新准入，再交接或终结在途责任，再撤除依赖分支，最后关闭共享后端；各资源拥有者关闭自己那一代的协议实例，装配不因此拥有这些资源。
- 原调用归旧的执行拥有者，直到收场或可靠交接；迟到结果须已有仍有效的接收方或可靠记录；旧推进者不推进新工作。
- 运行时启动前取得已校验的装配依据；同一位置的扩展按装配声明的顺序执行。

### 两层与权限

|  | 官方层 | 租户层 |
| --- | --- | --- |
| 有哪些 | 发行自带的行与界面模块，加运维者在自己的部署里装的行 | 租户的 Plugin 带来的 fiber |
| 谁有权装、换、撤 | 官方的两级：发行方（制品带签名）、这份部署的运维者（部署的配置点了名）。租户与 agent 都不是官方 | 持有它的租户 |
| 交到它手里的是什么 | 整棵树：Cordis 的 `ctx`，能注入任何服务 | 只有口；口上只来往数据 |
| 挂在哪 | 根下 | Plugin 的装载行下面 |

- 装入、备着、换代、排空、起不来时退回，两层用 `assembly-cordis` 的同一套装载。
- 租户层伤不到官方层，靠下面五道墙：

  | 墙 | 做法 | 落在哪 |
  | --- | --- | --- |
  | 租户的条目不让官方要保护的条目失效 | 官方的行放的、要保护的条目带锁（`lock: true`）：一个键上看得见的条目里有带锁的，作用域更深的全部出局。哪些条目带锁由放它的行决定；不带锁的照旧可以被租户盖过，令牌、样式这类本来就是给人换的 | 放它的行；锁的答法归 Dynamis 的[答案](../dynamis/SPEC.md#答案) |
  | 客人 fiber 的来去不动官方的行 | 监督只认官方层的行；租户层的 fiber 在自己的作用域里来去。官方的成员不注入租户层提供的任何东西，由依赖规则守 | `assembly-cordis`；依赖规则 |
  | 客人撤下有结局 | Plugin 放的带副作用的条目一律带排空：先不接新的，在途的各有结局，然后才取走 | Plugin 的服务端装载方 |
  | 要的口或点后来出现了会重试 | 一份 Plugin 因为口或点不在而装失败，状态记成「等着」，并订阅登记表的变化；它等的那一样出现了就再装。出借方换了一代，钉着它的口重新钉 | Plugin 的状态表 |
  | 运行中让进程倒下的客人，重启后不再装 | 进程级的未接住异常处理器在退出前记下「这一刻正在执行哪一份 Plugin 的调用」；监督者拉起之后，底把它算作这一份的一次倒下。连着到上限就停掉它 | `assembly-cordis`（处理器与归因）；Plugin 的底 |

- 最后一道墙的归因跟着异步上下文走：装入、调用期间抛出的，与这期间起的微任务、定时器、Promise 链上抛出的，都归得准。别人的调用里跑到的客人代码归不准，记成「不知道是谁」，照进程倒下处理。`assembly-cordis` 给两样：`attributed(谁, 做什么)` 与 `watchFalls`（进程级的未接住异常记下原因与归因，以 1 退出）。墙都只对老实的代码成立；存心越界的客人代码归隔离，不归这里。
- 换官方的行的入口不挂在对客户端开放的协议上，也不做成给 agent 的工具。入口是本机的：监督者的 `swap` 命令，经状态目录里一个只有本机同一用户能写的控制口告诉运行着的进程。谁能写状态目录与安装目录，谁就是运维者；这和「谁能写配置文件谁就能改官方的行」是同一条边界，不引入新的信任。

### 行的换代：三种换法

这一节起的换代是进程这一层的：一行背后的实现怎样换。采用这一层的换代见[重装入口与换代](#重装入口与换代)。

依据是 Cordis 的规矩：提供者一换，注入它的 fiber 全部卸载重跑。

| 换法 | 做法 | 依赖它的行 | 一行什么时候能用它 |
| --- | --- | --- | --- |
| 换实现 | 入口不动，背后换一代 | 不动 | 这一行声明了入口；新旧实现的契约同形 |
| 重跑 | 照 Cordis 卸了再装，连着依赖它的子树 | 全部重跑 | 这一行与子树里的每一行都声明了「重跑是安全的」 |
| 换进程 | 进程有计划地退出，监督者拉起 | 全部重来 | 总是可以 |

- 每一行在自己的声明里写它支持到哪一档：`swap: 'implementation' | 'rerun' | 'restart'`。不写就是 `restart`。

### 行的换代：入口

- 一行用 `defineEntry` 声明自己的入口：服务的每个方法怎样转给现在的那一代。依赖方注入的是入口行提供的对象，进程活着它就是这一个；入口行不换，依赖方就不重跑。入口还答现在在服务的是哪一代，没有时答依据不可用。
- 入口的每个方法在受理的那一刻取现在在服务的一代，把这次调用钉在它上面，调用完了放开。这就是 Dynamis 撤下里的「钉」。在途的调用留在旧的一代做完。
- 没有在服务的一代时，方法答依据不可用，不是空，不是抛出。
- 入口行自己没有状态。
- 入口转的是一问一答。服务对象上的订阅由入口自己持有订阅者的名单，换代时把名单交给新的一代。这一条只在一问一答上验过，订阅没有验；做不成，有订阅的服务就归到 `rerun` 或 `restart`。

### 行的换代：一代的全化表

一代是一份实现的一次装上。同一份实现卸了再装是另一代。状态：不在、备着（装入并启动中）、在服务、正在撤下、撤完、起不来。

| 状态 \ 操作 | 备 | 启动成了，换 | 启动抛错 | 受理一次调用 | 一次调用做完 | 名下没有在途的了 | 这一代自己倒了 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 不在 | → 备着。同一行已有一代备着：拒绝 | 不可达 | 不可达 | 拒绝：这一代不在 | 不可达 | 不可达 | 不可达 |
| 备着 | 拒绝：已经在备 | → 在服务；原来在服务的那一代同一步 → 正在撤下 | → 起不来；在服务的那一代不动 | 拒绝：还没在服务 | 不可达 | 不可达 | → 起不来 |
| 在服务 | 拒绝：它已经在服务 | 不可达 | 不可达 | 钉在它上面 | 放开 | 不变 | 见[监督与期限](#监督与期限) |
| 正在撤下 | 拒绝 | 不可达 | 不可达 | 拒绝：不接新的。入口不会把新调用给它 | 放开 | → 撤完，实现的 fiber 卸载 | 名下在途的记成未知，→ 撤完 |
| 撤完 | 拒绝：代数不重用 | 不可达 | 不可达 | 拒绝 | 幂等：已经放开 | 不变 | 不变 |
| 起不来 | 拒绝：这一代废了，要再试就是新的一代 | 不可达 | 不变 | 拒绝 | 不可达 | 不可达 | 不变 |

- 「不可达」由状态机的构造排除：只有备着的一代能被换上去；只有在服务与正在撤下的一代名下有调用。
- 一步换代用 `dynamis-cordis` 座位的换代操作：一步里把旧的定为正在撤下、新的定为在位。算法是登记表已有的[换代](../dynamis/SPEC.md#换代)，本组不另写。新的一代的 fiber 在登记表上用被接替者的名字，代数取下一个，所以登记表的换代成立；全文见 Dynamis 的规格。
- 正在撤下的一代的排空用[关闭协议](#关闭协议一组租约)：入口为每一代建一个实例。
- 「站稳」不等于 fiber 到了 `ACTIVE`。一行可以给一个就绪的判断，装载方在换之前问它；不给就以 `apply` 返回为准。

### 影响

`assembly` 的纯函数 `planChange` 拿一张行的图与一次变更，答这次变更的换法 `way`、会重跑的行 `reruns`（按依赖次序）与为什么是这一档。一行的声明写着名字、层、提供的服务键 `provides`、注入的服务键 `injects`、换法 `swap`、每个提供的键的契约摘要。变更有三种：换掉一行，一行没了，一行回来了。

1. 换一行的实现，新旧 `provides` 相同、每个键的契约摘要相同、这一行 `swap` 是 `implementation`：`way` 是 `implementation`，`reruns` 为空。
2. 否则这一行要重跑。`reruns` 是它加上依赖闭包：注入了它提供的键的 fiber，连着它们的子树，再连着它们提供的键的注入方，到不动点。
3. `reruns` 里只要有一行的 `swap` 是 `restart`：`way` 是 `restart`。
4. 契约变了形（`provides` 不同或摘要不同）：`way` 至少是 `rerun`；每个注入了变形的键的行都在 `reruns` 里。
5. 图里有环：拒绝，写明环。

- 预演等于实际：`assembly-cordis` 真的换了之后，把实际重跑的行与 `reruns` 比；不等就记一条错，并让进程走换进程。
- 依赖图来自行的清单里声明的 `injects` 与 `provides`。清单可能漏掉子 fiber 的注入，所以装好之后从活的树上再读一遍，和清单比；不等以活树为准，并记一条诊断。
- 每次调用现取的依赖不在图里：读的一方在提供者不在时得到依据不可用，自己不被卸载。这是让级联变少的方向。

### 监督与期限

官方层的每一行都在监督之下，不管它有没有关闭阶段。

| 这一行的状态 \ 事件 | 它依赖的行没了 | 它依赖的行回来了 | 它自己 `apply` 抛错 | 期限到 | 官方要换它 |
| --- | --- | --- | --- | --- | --- |
| 在服务 | Cordis 把它卸载 → 等依赖。名下在途的照这一行自己的声明处置 | 不可达 | 不可达（已经启动了） | 不适用 | 照[影响](#影响)走 |
| 等依赖 | 不变 | 它的 `swap` 不是 `restart`：Cordis 重跑它，→ 启动中，是新的一代。是 `restart`：进程有计划地退出 | 不可达 | 进程带着原因以 4 退出 | 记下要换的那一版，回来时用它 |
| 启动中 | → 等依赖 | 不变 | → 起不来；进程带着原因以 3 退出 | 进程带着原因以 3 退出，原因写明卡在哪一行 | 拒绝：先等它有结局 |
| 起不来 | 不变 | 不变 | 不变 | 不适用 | 可以：是新的一代 |

- 一行回来的前提是它依赖的行都在；回来的次序跟着依赖走。Cordis 自己守这一条（注入的服务齐了才启动），影响的计算照这个次序。
- 进程的状态：启动中、在服务、停止中、已退出。每个阶段有期限，期限从时间源读，数值是运维者的配置：

  | 阶段 | 规则 |
  | --- | --- |
  | 装入口对象、准备目录 | 有期限；到了以 3 退出，原因写明哪一步 |
  | 各行启动 | 结局里把每一行的状态都写出；有 `FAILED` 就立刻收场，不等期限 |
  | 启动失败之后的关闭 | 撤根有期限；到了强制退出，退出码不变。已写出的报告不改；向 stderr 写一条记录，写明卡住的行 |
  | 运行中一行没了 | 进入「等依赖」，有期限 |
  | 停机每一步 | 有期限 |
  | 停止信号 | 进程一起来就理会：装载期间收到就转入关闭 |

- 进程的停机分三步，每一步有期限：先停准入（接入行）；再做排空步，声明了排空的行在它的调用方还活着时把名下在途的做完；然后其余的行按依赖图倒着停。
- 退出码不加新的，含义全文归应用规格的[进程输出与退出](../../apps/harness-server/SPEC.md#进程输出与退出)，只把会挂住的地方都接到期限上。这里只写监督怎样用它们：等依赖回来的期限到了以 4 退出；重跑抛错或到期以 3 退出；进程级的未接住异常记下原因与归因（见[两层与权限](#两层与权限)的最后一道墙），以 1 退出。

### 监督者

| 场合 | 监督者 | 做法 |
| --- | --- | --- |
| 单独跑服务端 | 服务端自带的监督子命令 `supervise` | 一个很小的父进程：拉起 `serve`；按退出码决定拉不拉；带退避；连着起不来到上限，按版本指针退回上一份起稳过的再拉；再不行就停下并写明 |
| 用系统的服务管理器 | systemd 或 launchd | 应用的规格给出配置的样子与每个退出码该怎样配。launchd 没有「连着失败就停」，这一条仍由底来守 |
| 桌面应用 | 主进程监督转发层与页面 | 有上限，到了告诉人 |

- 监督者连着倒下的上限要比 Plugin 的底的上限多一次：底在第三次起来时才停得掉连倒两次的那一份，监督者先放弃的话它没有这个机会。
- 三种场合用 `assembly` 里同一份纯的监督状态机。它对退出码的处置：2 不拉；0 与 5 拉起，不算一次倒下；1、3、4 拉起，并算一次倒下。人要停服务，就停监督者本身。
- 自带一个监督者而不只靠系统的，是因为退回上一版要读版本指针，这是装配自己的事。

### 装载与来源

- 一份实现在一个版本目录里。装入就是 `import()` 这个目录里的入口文件。地址带版本，所以换一版得到新的模块。装进来的模块卸不掉，每换一版多占一份内存，到进程重启才还。
- 版本目录里只带这一行自己的代码。Cordis、Dynamis 这些共用的机制包不在版本目录里另带一份，否则同一个服务键会变成两个。这一条是推出的，具体的打包配置没试过；最简单的一种是行的实现文件只 `import` 类型，运行时要的东西都从交给它的 `ctx` 拿。
- 装进进程的官方实现，来源都要核过：

  | 级 | 怎样核 |
  | --- | --- |
  | 发行方 | 制品带一份摘要清单，清单带 Ed25519 签名，公钥在发行里。装入之前核签名，再逐个文件核摘要 |
  | 运维者 | 这份部署的配置里点了名的版本目录；不要签名 |

- 核签名用 Node 自带的 `crypto`，不用在线的签名服务：本机的门不能依赖网络。本组只做「核」这一半；密钥怎样保管、怎样轮换归发行流程。

### 版本目录、指针与戳

服务端与客户端用同一套版本指针。客户端的页面包怎样装、怎样验、什么时候切，归[桌面应用的规格](../../apps/desktop/SPEC.md)。

一版的状态：没装、装到一半、装好、试用中、定下。

| 状态 \ 操作 | 开始装 | 装完 | 装的时候中断 | 切到它 | 起稳了 | 倒了 | 连着倒到上限 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 没装 | → 装到一半 | 不可达 | 不可达 | 拒绝：没装好 | 不可达 | 不可达 | 不可达 |
| 装到一半 | 接着装或清掉重来 | → 装好 | 停在装到一半；下次清掉重来 | 拒绝：没装好 | 不可达 | 不可达 | 不可达 |
| 装好 | 幂等 | 幂等 | 不可达 | → 试用中；指针指它 | 不可达 | 不可达 | 不可达 |
| 试用中 | 拒绝 | 幂等 | 不可达 | 幂等 | → 定下；它成为退路 | 记一次 | 指针退回上一份定下的 |
| 定下 | 拒绝 | 幂等 | 不可达 | 幂等（切回它） | 幂等 | 记一次，照常再拉 | 停下并写明：没有更早的退路时不再拉 |

- 「起稳」是进程就绪并且过了一段稳定的时间（运维者的配置），不是到了 `ACTIVE` 就算。
- 安装根下一版一个目录，目录名带版本与内容摘要。装的时候先装进一个临时名字，装完原子地改名。装好之后只读。
- 指针是一个小的 JSON 文件，三样：现在的、上一份定下的、现在的这一份定下了没有。写指针用「写临时文件再原子改名」。
- 状态目录里的戳写着最后写它的版本、它用到的每种格式的号。启动时在拿到独占锁之后、碰任何存储之前读它：
  - 戳里的格式都认得：照常。
  - 有比自己新的格式：以 2 退出，写明是哪一版写的，状态目录一字不动。
  - 有比自己旧、要迁的：迁完再改戳。迁到一半倒了，戳没改，下次从头迁；每一域的迁移标记归存储域自己。
- 进程起来的次序：读指针，拿锁，核戳，装行。

### Cordis 集成辅助

- 根入口为空，不导入 Cordis；`./cordis` 放插件辅助与调用方 fiber 登记，`./testing` 放测试装配。产品源码不导入 `./testing`。本组不声明服务键。
- `definePlugin` 的输入与返回是同一组字段，必须带一个 Standard Schema 形式的配置 schema，`apply` 的配置参数就是该 schema 的输出；返回值不带 `provide` 或 `intercept`。函数插件走这个辅助。配置在插件体运行之前由 Cordis 校验，失败则 fiber 失败、插件体不运行。
- 必需依赖写进 `inject`；可选依赖不写进 `inject`，在调用时用 `resolveOptional` 读，缺席答 `undefined`，插件保持装载。类型参数是调用方的断言。
- `registerInCallerFiber` 在调用方的 Context（服务方法里的 `this.ctx`）上建一个 effect，在其中同步执行准入恰一次（Cordis 拒绝建 effect 时零次）。准入答三态之一：新建（交回新回执，保留 effect，撤除时恰调用一次撤回）、认回（交回原回执）、拒绝（交回原失败）；后两者只移除本次新建的 effect，不调用撤回。准入里提前请求撤除时，在拿到移除函数后、返回前执行；重复与重入的撤除只撤一次；提前撤除与调用方卸载同时发生时，只请求本次移除，已开始的卸载持有撤回。准入与撤回都必须同步。函数不做领域资格决定，不重试，不把异常翻译成拒绝或成功，不提供事务回滚；返回「新建」不保证登记仍存活。
- `startTestAssembly` 先把全部插件提交给新 Context，再检查每个插件体是否都已运行；后面的提供者满足前面的依赖时，前面的插件体必须在返回前运行。全部提交后仍有插件体没运行，视为启动失败。启动失败时先按启动的相反次序撤除已启动的 fiber：撤除全部成功抛原错误，否则抛同时带原错误与全部撤除错误的失败。`dispose` 按相反次序撤除全部，第一次拒绝不停下，最后汇总全部拒绝。测试装配不关闭调用方传入的资源，不规定业务关闭次序。

### 时间源

时间在系统里的作用、装配与可设置的三样归架构正文[时间](../../docs/architecture/runtime/time.md)。这里是成员 `time-source` 的承诺。

- 根入口给出时间源 `TimeSource`、系统时间源 `systemTime()` 与三个组合 `sleep`、`waitUntil`、`every`。子入口 `./simulated` 给出模拟时间源 `simulatedTime()`。成员不依赖 Cordis，不依赖别的工作区成员。
- `TimeSource` 有四个方法。`now()` 答墙钟读数，UTC 历元毫秒。`elapsed()` 答单调读数，毫秒，只在同一个时间源内相减与比较。`after(毫秒, 回调)` 在单调读数增长这么多之后调用回调一次。`at(历元毫秒, 回调)` 在墙钟读数不小于这个时刻之后调用回调一次。两种等待都返回取消函数。
- 等待从不在登记它的那次调用里同步触发，已经到点的也一样。取消过的等待不触发。触发之后再取消、重复取消都是空操作。
- `after` 的毫秒数小于零按零算。毫秒数或时刻不是有限数时抛 `TypeError`，不登记。
- 登记等待时可以给 `background: true`：这次等待不单独让宿主进程活着，只剩这类等待时进程可以退出。它只对系统时间源有意义，模拟时间源不区分。
- 系统时间源读宿主的墙钟与单调钟，用宿主的定时器等待。超过宿主定时器上限的等待分段续等。`at` 每次醒来按当时的墙钟重新核对，没到就续等。它不保证宿主的钟被拨快时提前醒。
- 模拟时间源由驱动方创建，交回两样：`source` 是给被驱动的系统的时间源，其余是控制面。从 `source` 取不到控制面。
- 模拟时间源的墙钟读数等于一个偏移加单调读数。`setWall(历元毫秒)` 只改偏移。一次等待的到点位置是它在单调读数上的位置：`after` 是登记时的读数加毫秒数；`at` 是时刻减偏移，偏移改了它跟着变。
- `advance(毫秒)` 把单调读数推进这么多。途中到点的等待按「到点位置，登记次序」依次触发，触发前读数先走到它的到点位置；已经过点的不回退读数。回调里新登记的等待，到点位置不超过终点的在同一次推进里触发。`next()` 跳到最近的一个到点位置并触发全部到点的等待，没有等待时答 `false`。`setWall` 之后立即触发因此到点的等待。
- 回调抛出的异常从这次 `advance`、`next` 或 `setWall` 抛给驱动方。读数停在那次触发的位置，抛出的那个等待已经移除，其余到点的等待留着。
- 回调里调用 `advance`、`next`、`setWall` 或切换推进方式抛 `TypeError`，不改状态。一次推进里新登记的等待在同一个到点位置上连续触发超过一万次时抛 `Error`，说明被驱动的系统在零延迟地空转。
- 推进方式由 `run(方式)` 切换，初始是手动。空闲就跳：在途登记数为零并且有等待时，在宿主的下一轮事件循环里 `next()` 一次，直到没有等待或有了在途登记。`hold()` 登记一件在途的活并交回放手函数，放手是幂等的。倍速 `run({ speed, follow })`：跟着另一个时间源 `follow` 的单调读数走，流逝乘系数 `speed`；`follow` 缺省是系统时间源，系数必须是正的有限数，否则抛 `TypeError`。倍速只在 `follow` 上为最近的一个等待挂一次等待；最后一个等待取消后，`follow` 上不留等待。切回手动时读数算到切换的那一刻。空闲就跳由宿主的事件循环驱动：有等待时只向宿主要一轮，没有等待时不要。空闲就跳与跟着系统时间源的倍速里，回调抛出的异常成为宿主的未捕获异常。
- 创建时给 `record: true`，`timeline()` 交回记录：登记、触发、取消、改墙钟各一行，带当时的两个读数。缺省不记录。
- `sleep(时间源, 毫秒, 信号)` 与 `waitUntil(时间源, 历元毫秒, 信号)` 答 `elapsed` 或 `cancelled`。信号已中止时答 `cancelled`，不登记等待。`every(时间源, 毫秒, 回调)` 每隔这么多毫秒调用回调一次，间隔从上一次调用返回时算起，返回取消函数。

- 模拟时间源的状态可以取出与恢复：取出的是当时的墙钟读数；用一个墙钟读数创建的时间源从那个读数开始，单调读数从零开始。还在等的等待不属于状态，由被驱动的系统重启时自己重新登记。

下面几样没有实现，见架构正文的[差距](../../docs/architecture/runtime/time.md#差距)：Worker 线程与子进程里的时间、整个服务端在空闲就跳下运行、模拟时间的控制协议与界面。

## 原则与约束

- 关闭有确定结局：`closed`、`failed`、`timed-out` 三种之一，或者进程死亡而没有报告；超时不是成功收场。
- 只关自己那一代。换代另建实例，旧实例看不见新租约。
- 采用是整份的。整份替换或完全不发布；失败保留旧的合法采用。
- 采用依据是本次执行唯一的定义来源；运行中不回头问提供方，不半路换组合。
- Cordis 给机制不给语义：fiber 状态不是业务就绪，effect 的完成顺序不是关闭顺序，`dispose()` 不是关闭。关闭报告由调用方的步骤列表产生，不靠同级 effect 或一次 `emit` 收集。
- 辅助只写一次各领域都要的胶水，不收回别的能力的 Service 定义，不做领域决定。
- 一个系统一个时间源。读数与等待在同一条时间线上；只有系统时间源读宿主的钟。
- 用哪一种推进方式由装配决定，不由环境变量或配置决定。发行的装配不导入 `./simulated`。
- 手动与空闲就跳两种方式下，触发次序只由登记与推进的输入决定，与宿主的快慢无关。空闲靠在途登记判断，不靠静默的时长。
- 进程这一层四样纯的东西：每个导出是值，或值到值的函数；不读时钟，不取随机数。期限由 `assembly-cordis` 从时间源读。
- 这四样里拒绝是返回值，不抛出，并带原因。每个操作在每个状态下都有确定的答复。
- 机制不认识领域。`assembly` 不认识任何领域；`assembly-cordis` 只认识 `assembly`、Dynamis 与 Cordis。由依赖规则 `mechanism-knows-no-domain` 守。
- 一行不声明换法就是 `restart`。一行只有自己声明能换实现或能重跑，才换策略。
