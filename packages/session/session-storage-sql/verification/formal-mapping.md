# 形式模型与规格、代码的对照

本页对照 `session-storage-sql/verification` 下四个有限模型：同日志提交（`log-commit`）、授权到尝试的解析（`attempt-grant`）、受保护提交（`protected-basis`）、已发布计数（`models/published-count`）。条款在包组规格 [`packages/session/SPEC.md`](../../SPEC.md)。模型检查只说明有限范围内的设计性质。正控要求无反例，负控要求命中指定性质。

## log-commit

`LogCommit.tla` 检查 Agent 的原发布与 Session 的解释提交共用一个存储的同日志提交：原记录与同根索引分开存放以便检出半发布，解释提交把后果、进度与操作回执一次发布。规格见 SE-14、SE-15。

| 要求                    | 不变量                                                                                                          | 负控                                                                                                    |
| ----------------------- | --------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| P1 同一操作至多提交一次 | `AtMostOnce`：按提交封套计数，不依靠集合去重                                                                    | `negative-forget-operation`：同时去掉事务入口与未知查询的操作认回，相同操作再次发布                     |
| P2 同事务可见           | `AtomicVisibility`：原记录与同根索引、进度与后果、操作记录与提交封套同时可见                                    | `negative-split-agent` 只发布原记录；`negative-split-session` 只发布解释封套                            |
| P3 未知之后认回不重复   | `RecoveryStable`：曾未知的操作只有一个封套，成功答复引用原封套；`NoRepeatedEffects`：每个原事件至多产生一次后果 | `negative-unknown-recommit`；`negative-replay-sequence`                                                 |
| P4 禁止非法提交         | `LegalCommit`：从提交封套重新核对租户、入口、实际 head、实际根与序号                                            | `negative-skip-head`、`negative-skip-root`、`negative-skip-tenant`、`negative-skip-view` 各去掉一个保护 |

| 配置                  | 预期与用途                                                        |
| --------------------- | ----------------------------------------------------------------- |
| `positive-race`       | 无反例：两个解释者竞争，同身份与异身份重读，两个事件共享一个 head |
| `positive-head`       | 无反例：零事件发布与读取之后 head 变化                            |
| `positive-boundaries` | 无反例：所有者与外来者、受信与委派、错误 head 的全部组合          |
| `positive-executions` | 无反例：不同执行的进度隔离，同一操作异语义冲突                    |
| `positive-recovery`   | 无反例：在途未知、晚到提交、回滚后重试、提交后认回                |
| `negative-*`          | 各命中上表所列的不变量                                            |

| 模型                               | 实现                                                                                               |
| ---------------------------------- | -------------------------------------------------------------------------------------------------- |
| 观察与 `Judge`                     | 契约的公开观察与观察校验，事务端口                                                                 |
| `PublishAgent`、同根索引分量       | 存储的执行记录发布与索引写入：原事实与四张索引表同事务写入                                         |
| `Root`、`Refresh`                  | 日志根与历史索引：根与索引在同一写事务里读出，同源                                                 |
| `Judge`、`PublishSession`、`Abort` | 日志判定与参加者的同日志发布：后果行、进度行、模型视图、快照、派生行、操作行与尾部在一次发布里成立 |
| `LoseContact`、`Query`、`Deliver`  | 提交的尝试代次结算：应答丢失答提交未知，查询认回，原事务仍活着时保持未知                           |
| 执行路由                           | 执行索引；建立与唯一关联归 `session-adapters` 的 `generation-handoff` 模型                         |

## attempt-grant

`AttemptGrant.tla`：一个 Run，attempt 依次开始，每次提交发一张回执并在同一提交里记入索引。

| 性质              | 含义                                                                    | 负控                                                                     |
| ----------------- | ----------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| `GrantResolves`   | 每张回执解析到发出它时的 attempt，与之后开始的 attempt 个数无关         | `negative-started-only`：只记开始回执，查不到就回落到 Run 唯一的 attempt |
| `StaleStaysStale` | 更早 attempt 的授权不会解析成当前 attempt，消费者看到过期而不是假的当前 | 无                                                                       |
| `IndexAtCommit`   | 索引只在提交时写入、不改写，读时不推断                                  | 无                                                                       |

配置：`positive`（三个 attempt、六张回执，检查全部性质，预期无反例）；`negative-started-only`（预期命中 `GrantResolves`）。

| 模型                | 实现                                                                                                                   |
| ------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| `receipts`、`index` | 一次提交回执的来源位置；授权索引表（租户、会话、attempt、位置、授权），由参加者随批写入                                |
| `Resolve`           | 适配层按记下的授权查 attempt，查不到不指名任何 attempt，不回落；历史索引解析原受理行时先按行记下的 attempt，再按授权名 |
| `StartAttempt`      | 开始 Run 与接管：开始一个 attempt，它的开始回执也是一张授权                                                            |
| `Commit`            | 当前 attempt 下的任何 Agent 发布                                                                                       |

## protected-basis

`SessionPermissionWrite.tla`：受保护写入时登录资格、组织层的值与租户域依据事实分处不同事务域，写入要在同一事务里核对。规格见 SE-23。

| 性质                           | 含义                                                                                                       | 负控（去掉的前提）                         |
| ------------------------------ | ---------------------------------------------------------------------------------------------------------- | ------------------------------------------ |
| `AtMostOnce`                   | 一个原操作的效果至多发生一次                                                                               | `negative-blind`：提交不看回执             |
| `CommitUsesCurrentFact`        | 效果依据的租户域事实等于提交那一刻的事实                                                                   | `negative-unguarded`：提交不核对读到的事实 |
| `SourceIsFresh`                | 一次投递使用的组织层的值不早于这次投递开始                                                                 | `negative-held`：沿用上一次投递保管的值    |
| `ReplayIsRecognised`           | 原操作已生效之后，投递得到原结果；依据事实之后的变化不会把它答成拒绝或不可用，只有失去登录资格的调用方例外 | `negative-early`：解析失败就直接答复       |
| `FailedResolutionIsNotDurable` | 解析失败不留持久裁定，下一次投递按自己读到的事实裁定                                                       | `negative-durable`：把无法裁定记成回执     |
| `EveryAttemptEnds`             | 事实停止变化后，每次投递都会结束                                                                           | 无                                         |

另有 `negative-query` 一份负控。配置预期：`positive` 无反例；`negative-*` 命中对应性质。

| 模型                    | 实现                                                                                       |
| ----------------------- | ------------------------------------------------------------------------------------------ |
| `Admit`                 | 提交的准入步骤；应用的依据来源另外在每次调用时核对登录                                     |
| `ReadSrc`、`ReadF`      | 应用的受保护依据来源：每次被调用都读取，不保管                                             |
| `Commit` 先看回执       | `commitFacts`：先查原操作各代次的回执；来源答失败后再查一次                                |
| `Commit` 核对读到的事实 | 受保护组合里的依据参加者在事务里用同事务的事实重算裁定，它停下时这一代次回滚，投递答不可用 |
| 效果与回执同时成立      | Session 写者在同一事务写事件、权限修订与操作记录                                           |
| 失败不留裁定            | 来源失败不提交；参加者停下只占用一个代次                                                   |

## published-count

`PublishedCount.tla`：已发布计数由本进程保管。变量：存储里的计数、保管者知道的计数（或不知道）、在途发布所带的计数、最近一次取到的计数、最近一次成功发布所带的计数与当时存储的计数。别的进程的发布是环境故障，留在模型里证明此时发布仍只在存储当前的计数上生效。

| 性质                 | 含义                                                             |
| -------------------- | ---------------------------------------------------------------- |
| `KnownIsPast`        | 已知计数不超过存储的计数，所以按它决定的发布要么被接受，要么被拒 |
| `TakenIsPast`        | 调用取到的计数不超过存储的计数                                   |
| `PublishedOnCurrent` | 本进程提交成功的发布，所带的计数就是当时存储的计数               |

配置：`PublishedCount-positive`（三条不变式都成立）；`PublishedCount-assume-applied`（答复未知时把计数当作已前进，必须命中 `KnownIsPast`）。

| 模型                               | 源码                                           |
| ---------------------------------- | ---------------------------------------------- |
| `Take`、`ReadRoot` 的选择          | 已发布计数的规划函数（全函数）：答已知或需读根 |
| `ReadRoot`、`Committed` 之后的确认 | 计数保管者的确认                               |
| `Refused`、`Unknown` 之后的作废    | 计数保管者的存疑                               |
| `Send` 与三种结局                  | Journal 提供者的同步、结算与已提交结算         |

不覆盖：一次读根的答复晚于一次发布到达；实现让计数只增不减，低于已知值的答复不改已知值，由 `tests/published-count.spec.ts` 守。
