# Session

## 总体架构

Session 管一个会话的业务流程，拥有会话日志。它回答：一个会话里发生过什么，这些事实怎样在一次提交里成立，接下来该做什么，由谁来做。包组的成员按它们回答的问题分：

| 成员                                                         | 回答的问题                                                                                                  |
| ------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------- |
| `session-contract`                                           | 日志里有哪些条目，一条命令怎样判成条目，条目怎样归约成快照。纯数据与纯函数，不依赖邻域契约，不依赖 Cordis   |
| `session`                                                    | 命令怎样被受理，提交之后接着做什么：命令处理、协调器、调度器、缓存。不依赖 Cordis，用替身就能跑完整个状态机 |
| `session-storage-sql`                                        | 一次提交怎样在一个事务里落盘，快照与索引怎样读                                                              |
| `session-cordis-contract`、`session-cordis`                  | 在这套系统里它以什么服务出现，怎样绑到存储上，怎样撤除                                                      |
| `session-adapters`                                           | 邻域的端口由谁来适配。Session 是最外层，经这里认识 Agent、Model、Tool、Runtime Context、执行环境与身份      |
| `session-observation`                                        | 一个登录的人看一个会话时看到哪些帧                                                                          |
| `session-search`、`session-search-sqlite`                    | 搜历史的一次查询怎样变成候选与核对；历史索引这份投影放在哪、怎样追日志、怎样重建                            |
| `session-protocol`、`session-access`、`session-ui`           | 对客户端开放的三样：协议契约、接入插件、界面模块                                                            |
| `session-diagnostics-protocol`、`session-diagnostics-access` | 登录的人怎样读一个会话的诊断页：协议契约 `session-diagnostics/v1` 与它的接入插件                            |
| `session-tools`                                              | 给 agent 的工具 `Sessions`：列、搜、读同一租户的会话，读可以从一个位置之后读起，用的是人经协议用的同一批读取                          |

一次提交是这样走的：命令进来，判定函数对着当前快照把它判成一组条目，存储在一个事务里把这组条目追加进日志，归约函数把它们并进快照。每次提交之后要做的事挂在写入者上，不挂在各个提交方上：提交之后只发一条唤醒，协调器与调度器读权威状态再决定做什么。

依赖方向：`session-contract` 不依赖任何邻域契约，出站端口的接口在这里声明，本域只说自己要什么；`session` 只依赖 `session-contract`；`session-cordis` 依赖前三者，不依赖邻域契约与存储后端；`session-adapters` 是组内唯一导入邻域契约的成员（`session-observation` 只读 Model 的公共流，也导入 Model 契约），它与 `session-cordis` 没有编译期依赖，端口的服务键由装配接上；`session-storage-sql` 依赖契约、Cordis 定义的 `./cordis` 入口与存储契约。

新增一段代码时按下表选成员，同时满足几条取最靠下的一条：

| 这段代码需要什么                                  | 放在                  |
| ------------------------------------------------- | --------------------- |
| 只用类型、值、身份与纯判断，不调用任何东西        | `session-contract`    |
| 用替身就能跑完整个状态机                          | `session`             |
| 要从 Cordis 现取时钟、叫醒总线或装配端口          | `session-cordis`      |
| 读会话日志与 Model 的公共流，产出会话观察的帧     | `session-observation` |
| 要导入任何其他邻域契约                            | `session-adapters`    |
| 给 agent 的工具作者，只依赖契约与 Tool 的作者协议 | `session-tools`       |
| 与存储介质相关                                    | `session-storage-sql` |

## 领域边界

Session 拥有一个会话的日志，而且是它唯一的写入者。别的领域要留下事实，把一条会话命令交给它，由它在同一次提交里写。Session 拥有：会话身份与固定事实（租户、定义标识、执行类型、必需身份）；日志与由它归约出的当前状态；Run 与执行尝试（attempt）的治理事实；受理、等待、控制、终态、归档、冻结、关系、空闲；会话当前值（三轴模式、工作区选择、模型选择、Context 注册、权限配值）；判断「还有未结工作吗」的依据。

Session 不发模型请求，不运行工具。对一次调用的控制送到它当前的等待者：还在某一步等待里的调用经 Agent 送达，因为答复要回到那一步；转了后台的调用没有在等它的步，Session 凭调用引用直接交给 Tool。Run 是它和 Agent 的边界：Session 交出工作与推进的资格，一轮怎样往前推归 Agent。取消与归档只改变资格与责任。模型发没发出、工具停没停，由各自的拥有者报告，Session 只对账。

Session 不拥有：授权政策与登录（身份与授权）；卡片与答复（人工介入）；模型档案与凭据（Model）；工具的启动围栏与结果清理（Tool 与 Agent 的日志）；作用域资源本身（执行环境、Runtime Context）；共享设置与资产的内容；存储事务的提交协议与回执（存储契约）。

Session 认识全部邻域，邻域都不认识 Session。邻域契约只用通用角色：外部协调者、提交参加者、消费者拥有者、作用域持有者、历史持有者、维护者。名称与形状的翻译只在 `session-adapters` 里发生。

Session 向外声明的端口（它需要别人做的）：

| 端口                                                                   | 对方                        | 对得上的一句话                                                                    |
| ---------------------------------------------------------------------- | --------------------------- | --------------------------------------------------------------------------------- |

| 事务端口 `SessionTransactionPort`、委派入口                            | 存储                        | Session 需要一个事务把条目、操作认回、治理变更与参加者放进同一次提交；存储提供    |
| 身份桥、证据桥、Context 输入、空闲输入                                 | 身份、装配、Runtime Context | Session 需要提交时的可信身份、采用依据、注册材料与空闲覆盖；各拥有者经适配提供    |
| 时钟、叫醒者                                                           | 装配                        | Session 需要采样时间与提交后的唤醒；装配提供                                      |
| `AgentDrivePort`：发起、交入、接续、控制、交还、保管、查询、读执行记录 | Agent                       | Session 需要把一轮交给 Agent 并读回原记录；Agent 的公开入口经适配接上             |

## 心智模型

会话日志是一个会话的唯一事实源。快照是日志归约出来的：待处理的输入，活动的轮，一轮取走了哪些输入，会话是不是在等人，都是归约的结果，没有别的来源。运行着的对象不存别处没有的事实；它丢了，从日志接着来。协调器、调度器、适配插件、缓存都是可丢的活体。

拿这一条量一个设计：一个决定会话接下来做什么的事实，如果不在日志里，进程重启之后就没有了。所以每个这样的事实都要有一条条目，或者能从已有的条目归约出来。

另一幅图景是「两本账、两个写入者」：会话日志只有 Session 一个写入者；Agent 的执行记录有自己的提供者。两本账在同一个事务域里，一次提交可以同时写两本，各自的事实各自成立。Session 对 Agent 的事实只做两件事：在 Agent 的提交里作为参加者核对或共同保存；事后读同一日志里的 Agent 事实，把后果写成自己的条目。Session 从不保存 Agent 的工作状态。

最容易想错的地方：

- 受理、承接、交入、解除是四件事。受理是输入进了日志；交入是 Session 把它交给 Agent；承接是 Agent 取走它；一轮开头的那一批由开始 Run 的提交定，之后各步的批界由 Agent 的输入水位线定；待处理资格只在读到承接事实时才解除。
- 提交叫醒只是唤醒。丢了、重了、合并了都不改变事实，扫描补查。
- 提交未知不是失败也不是成功。按原操作身份认回；认回之前不发出依赖这次提交的外部效果。
- 逻辑终态先于物理收场。取消一生效就记被取消终态，传播与对账随后进行；「已请求停止」不显示成「已停止」。
- 一个 Run 的状态机和它某一次推进尝试的状态机是两层。等待不是 Run 的状态。
- 读取的空不是没有：读不到、扫不完、有缺口时，答不可用或隔离，不答空队列、无 Run 或无权限。

## 应然设计

### 压缩采用与有效历史

Session 实现 Agent 的日志写入与输入来源适配，负责压缩结果的采用，不执行压缩算法或内部模型调用。服务的成功结果以完整 CompactionMessage 交来，Session 验证原值，不能重写后假称采用了原结果。

采用在日志的一次事务内核对执行仍是当前 Run 的推进执行、原准备及结果的关联、来源证明、当前模型视图代际、覆盖范围、配对与未结工作。完整压缩消息、历史标注、模型视图代际与 Agent 消费事实共同成立；仅认回提交操作身份还不够，同一任务结果与准备不能由另一个操作再次采用。提交未知按原操作查询，不追加第二条摘要。

当前未结工作以提交点事实为准。有对应模型可见消息的工作在覆盖范围内时必须保留该消息；没有对应可见消息的未结事实作为覆盖屏障，不能放进保留名单，覆盖必须在该事实之前结束。新的保护要求使原结果不合法时拒绝；原冻结输入之后的普通尾部追加不自动作废结果，未覆盖的全部模型可见消息继续存在。其他压缩已改变模型视图代际时拒绝旧结果，不能复活已被摘要的旧原文。消息规则归 [Common](../common/SPEC.md#消息)，来源可信与资格不是形状解码可以代替的判断。

输入冻结仅保存可恢复的引用与摘要，不能把完整历史重复写入 Agent 事实族。一条事实有固定的字节上限，所以事实不带长度随用量增长的清单：一步取走的批只记批的标识与水位，成员按标识里的区间从已受理的输入还原；打开执行的事实不重复列初始输入，它们各有自己的受理事实。冻结时已投影的消息按当时的模型视图代际、原条目和内容摘要读取。这样即使原条目含有已撤回的指导块，也能恢复冻结时实际可见的字节。收到结果时的保管块与采用后的历史消息共用同一份内容字节，遵循 [H1](../../docs/architecture/runtime/session-and-run.md#h1-agent-fact-invariants)。确认结果已接管与决定采用分开：拒绝采用仍须留下原结果的可靠处置，不丢失迟到结果的归属。

历史源从当前模型视图、配对见证和未结工作索引读取冻结输入与提交判断窗口。解析当前作用域使用 `readCurrentScope` 窄读，返回最后绑定（包含结束依据）或尚无绑定的 null；资格、会话隔离与读取进度与其他 Session 读取一致，进度落后不能答 null。当前视图是上次保留项、上次压缩消息和覆盖边界之后的增量，并应用已经提交的[读取资格投影](../../docs/domains/sessions-and-work/architecture.md#模型视图的资格投影)；起点只作身份锚点。模型次序与日志次序分别保留，不能靠解析不透明引用比较位置。索引与权威提交的读取进度一致，失去依据答不可用或未知，不答空历史。

固定当前视图、配对与未结工作的规模，增加已压掉的旧历史时，压缩热路径的读取、扫描、传输和复制量不得线性增加。范围标注与人侧历史按需分页派生，不逐次物化整个已覆盖前缀。索引重建可以独立回放日志，不能藏在每次压缩请求里。当前材料仍须完整物化，数据库索引定位的成本不承诺与数据库大小无关。

消息采用性质由 [CompactionLog](../../docs/architecture/verification/compaction/CompactionLog.tla)描述；它抽象来源核验和授权，不证明密码学、真实存储符合性或性能。

### 日志与提交

日志只追加。可靠提交之后，条目的内容、身份、租户与会话归属、因果关联、提交顺序不可原地修改或删除；更正、撤销、控制、状态变化都追加新条目并关联原事实。压缩、卸载、归档、终态、确认、重建投影、格式演进都不构成覆写的例外。更换编码或存储提供者要保留原条目与它的可解释依据。

Session 治理是日志唯一的业务写入口。生产者提交获准的事实或操作，不能直接改日志与治理索引。条目只表示已发生的事实；待执行命令、工程日志、遥测、叫醒不能冒充已提交的会话事实。在途的流式内容由生产者保管，Session 不逐片落盘；收场后实际采用的内容作为历史条目提交，中断的内容不能伪装成完整回复。

每次操作按（租户、会话、可信来源、操作标识）认回。相同身份且相同操作取得原回执，相同身份不同操作拒绝；同文的新输入仍是新操作。认回先于检查尾部进度，不因后来追加或换代产生第二批原条目；查询仍检查当前资格。命令的身份摘要只覆盖语义参数。

条目批次、操作认回依据、共同的治理变更与它的权威读取进度，在一次不可分割的提交里成立。受理内容与待处理资格、完整批次承接与资格解除、attempt 换代与旧资格撤销、Run 终态与新发起资格撤销，各自同批。必要的外部内容先达到可恢复引用的保管条件，再确认依赖它的条目；准备失败不报受理成功。

一次提交的结果只有五种含义：已提交（返回原提交身份、条目范围、回执，已达声明的耐久边界）；本次尝试被拒或未提交（原操作若有未决尝试仍是未知）；原操作明确未提交（要有存储提供者给出的持久裁定，终止此前全部尝试，之后重试用同一操作身份与新的尝试代次）；并发条件已变（不拼接旧的预计算条目，重新核对原操作再按当前事实判断）；结果未知（保留原操作与处置责任，按原身份查询，不换身份重做）。「未找到」只说明该读取时刻未见已提交操作。日志里暂时没有条目不能推出未提交。

会话命令（含上下文提醒）、Agent 日志的写入（含只写内容块的那一种）与预准入，认回记录是自己的表：`sl_operation`、`er_operation`、`er_preadmission`，与提交同一个事务写下。它们的提交身份声明 `recall: 'never'`，存储不另留回执。只写内容块的压缩输入（`compaction-input:*`）没有能认出原操作的记录，照旧用存储回执。结果未知时先等存储对这个操作的每个尝试代次答「已落定」（`settled`），再读自己的表：有就是已提交，按原记录认回，受保护提交还比命令摘要，摘要不同答冲突；没有才是没提交，排除依据取「已落定」的证明。先读表再问存储是错的：在途的提交可能在两次读之间落地。对外的查询照旧：没提交仍答「未知」。回滚不留回执，自己的记录又随事务回滚，所以查询认不出「某次尝试被拒」，一次尝试回滚之后查询答「未知」，不答 `attempt-rejected`。

提交不把模型的真实发出、工具副作用、外部物理停止或生产侧确认放进数据库事务。持久的处置责任与对方的执行契约各自对账；「记录了发起意图」不报告成「调用确实执行」。叫醒发生在提交之后，同一条记录重复投递不产生新条目；丢失由权威状态补查，工作的可靠性不以订阅一直在线为前提。

只有会话日志的唯一写入者写条目，写条目的函数只有一处，它写完一批时给出这一批的租户、会话、修订、出处证据与条目种类集合；认回、回滚与没写条目的提交不发叫醒。叫醒失败不回滚提交，也不改变提交的答复。运行时上下文只经会话日志里的提醒到达模型。Session 作为作用域持有者，以模型类读者读 Runtime Context，把读到的写成 `SystemReminderMessage`，在一步开始之前单独提交（`commitDerived` 的 `context-reminder`），这一步随后在它产生的修订上写，所以提醒排在这一步的输入之前。一次 Agent 记录的写入只容一个 Session 命令，所以提醒不与输入同一次提交。提醒的操作号由作用域、所告知的视图修订与提交时的会话修订算出，答复未知时认回同一个操作。模型在当前 epoch 里还没有被告知时，写一条完整快照：当前允许模型读的全部块的值。之后只在块的值变了时写一条变化提醒，说明哪一块变成了什么，声明允许带前值的块带上前值。没有可读的块、没有变化时不写。读取被拒、缺项或未知时这一步的提交失败，不当成没有变化。「已经告知到哪里」只是持有者的活体状态，在提醒的提交成功之后才推进。它丢了、读取游标作废或读取资格重签时，下一步重写一条完整快照。压缩提交之后，压缩之后的请求在同一步里准备，所以在同一次写入的调用里接着写一条完整快照；这一条没写成时不让已经提交的压缩失败，下一步照常重写。多写一条是追加，不改已有的历史。收件模型变化与新的执行开始不触发重写。会话工作目录是会话在当前这一步里文件与命令类工具默认使用的目录，Session 把它连同这一步文件请求读能到哪、写能到哪（文件范围）发布成一个模型可读的块，值有三种：没有选工作区，带部署的默认目录与读写都不限的范围；已附着，带工作区、实例、根目录与范围；选了但用不了，带工作区、实例与原因。它声明带前值，所以变化提醒同时给出原值与新值。它是一个状态块：写者是协调者类，值在步边界由 Session 作为持有者提交进会话日志。它只在一步开始之前的这一个动作里换值：先按日志里当时的选择向工作区目标端口核验，端口答可附着时同时答这时的范围；得到的值和块里的不同时提交一条步提交，再读块、写提醒。Session 不认识范围从哪来，只照端口的答复写；没有选工作区时不问端口，范围读写都不限，因为没有可以限的根。更换的提交与范围的来源变化本身都不改它，所以两者都从下一步起生效，一步之内它的值不变。步前核验答依据不可用时这一步的提交失败。进程重建之后，恢复把日志里最近一次提交的值装回，不重新核验，也不取最新的选择；其间受理的调用照装回的值钉住。作用域没有登记这个块的会话没有这个值，读它的一方得到拒绝，不得到默认目录。块里不放装载依据。

### 会话的固定事实与采用

租户、定义标识、执行类型与必需身份集合随创建固定，不随账号切换。创建要求明确租户、定义标识与执行类型；工作区可选，指定时工作区标识与附着（实例、装载依据）成对出现，指定的工作区必须按附着合法装载，失败不降为无工作区。本域不从磁盘目录、外部消息正文或最近使用值猜身份与工作区。创建会话与更换工作区在受理之前都先向工作区目标端口核验所选的实例：答合法时，把对方给出的附着与确认依据一起提交，附着不由会话自己拼；答未获准或实例不可用时不提交，更换时原选择不变；答依据不可用时不提交，也不记成拒绝。更换可以在任何未归档的状态受理，有没有 Run 在跑都一样；它只写一条变更条目，不改租户，不改已经发出的调用，不使正在跑的 Run 换资产组合；目标与当前选择相同时不写条目。人和 Agent 的更换是同一条会话命令，受同样的核验。关系、层数与值守也随创建固定，之后不变。关系三种：主会话；子会话，带父会话与成立依据；独立交接出的主会话，带来源会话与成立依据。层数是它到所在那棵树的根隔了几层，主会话是第 0 层，子会话的层数是父的层数加一，至多 2，超过就拒绝创建。值守两种：有人值守，无人值守；它回答这个会话的另一头有没有人可以沟通、交互与接收通知。成员本人经入口建的会话是有人值守的主会话；别的领域建会话时写明关系与值守，子会话恒为无人值守。建子会话时父会话必须存在、同租户、没有归档也没有冻结；子会话成立与父会话的日志记下这个子会话是同一次存储提交，父会话由此知道自己的全部子会话。

新 Run 采用该定义标识当时最新的合法版本；同一 Run 的普通恢复保留原采用，不重新求值。会话不固定能力的版本，延续靠按记下的形状核对同形可用的实现。显式 reload 经候选校验与安全交接后，可在同一 Run 采用同标识的新版本并建立新 attempt，校验失败保留原合法状态；没有未终结的 Run 时只记采用，供下一个 Run 用，规则见[Run 与推进资格](#run-与推进资格)。实例重建本身不改定义标识，不重发原调用，不丢原等待、卡片与结果消费责任。

采用要有跨源可核验的有效裁定边界：此前已生效的新发布或撤权使旧候选重算或拒绝，Session 尾部没变不能证明外部依据仍有效；无法核验时不发布新采用，保留原合法状态或报告不可用。裁定之后的变化沿动态规则处理，后续实际动作仍核对当前资格，历史采用记录不永久授权。

创建事实进入第一批日志，携带固定身份、初始值与采用依据。初始化未完成的项保存明确状态与接续责任，会话保持 initializing，直到全部必要项完成；失败的项保留任务，不用空值伪装就绪。重建从创建事实开始，缺起点、解释版本或初始依据时报告不可恢复，不从当前默认补造过去。恢复保留会话当前值，不重新套新的租户默认。 分叉：一个会话可以从另一个会话分叉出来：它的模型视图在分叉点之前是来源会话的那一段，按引用读，不复制；之后是它自己写的。分叉点是来源的一次模型请求的输入边界，由视图的代际、序号上界与来源日志当时的最大条目位置三样确定；来源随创建成立，之后不变，这一版只有子会话可以带来源，来源就是它的父会话，两者同租户。分叉出的会话只继承模型看到的对话：它的状态只从它自己的条目归约，来源的条目不进它的历史、搜索索引与用量归属。它自己的条目从分叉点的条目位置之后编号；视图按段拼，段在建的时候摊平，读不递归；各压各的；被段引用的行不删；任何一段读不出时视图读答不可用。建分叉读写的行数是常数。规则、读写路径的代价、失败语义与不变式 SF-1 到 SF-6 归 [Session 与 Run 的「会话分叉」](../../docs/architecture/runtime/session-and-run.md#会话分叉)。

会话选择与注册变化只影响本会话；修改共享源要由该源的拥有者确认。当前权限、共享资产与 Context 数据不因历史引用变成会话自有的源。会话当前值与采用依据分开记，当前值不能凭历史日志推测。

### 访问裁定

`SessionAccessCheck` 是必需的构造依赖，缺席时服务不启动，不能沿用旧的允许。每次公开读写在实际执行处调用一次：包括重复变更、原操作查询、每一页历史、恢复读与目录页。先取得本次裁定，再返回已有答案或披露正文。允许不缓存，不写进游标当作以后的凭据；被拒返回同名失败；不可用或核验抛错返回不可用，不继续读写，不推进修订、游标或操作答案。主体、操作、目标与命令材料在第一次异步等待之前固定。

一次面操作在开头核一次权，随后以委派入口取得只服务本次面操作的事务视图；点查、权威读、重做与提交都经视图，视图不再裁定，不跨面操作保留，不写进任务、缓存或游标。公开的事务端口每个方法各自裁定。存储核心只核租户归属键与绑定本次操作和固定输入的裁定证据，不解释主体类别或授权政策。

租户内操作使用带租户的访问身份，单会话目标绑定租户与会话标识，变更还携带原命令；`pending` 与目录以显式租户为目标；系统作用域的读取（常驻引用、已释放作用域）使用系统主体与限定资格，不制造空租户或任意租户的访问身份。持有组织成本账目读取资格的主体不因此获得其他租户的正文或执行控制。

模式变更的资格由授权适配器按原 `change` 命令裁定；Session 不用调用方类、模式词或历史允许去推断。调用方类（受理方、协调方、维护方、读取方）是装配事实，不是资格授予；它按操作限制能调哪些操作，受理方调不了开始 Run，协调方调不了创建会话，读取方调不了任何变更。

会话归属读取只证明一个会话属于哪个租户，以及创建它的那批证据。它不询问访问检查，只由装配里受信的签发闭包读取。未知的会话与别的租户的会话都答 `not-bound`，读不到答不可用。归属与创建证据在创建之后不再变化，所以只缓存 `bound` 的答复；`not-bound`、不可用与未知都不缓存，因为会话或作用域可能随后才创建。停止之后一切读取答不可用，已缓存的也一样。

作用域属主查询在每个已注册租户的域里按租户次序查找，找到第一个拥有者就停。作用域文本是单向摘要，不能从中读出租户。某个域读不到时答不可用，不答未知。已结束的作用域仍有属主。

每会话的工作主体由装配入口在读过归属之后签发：`not-bound` 答被拒；`bound` 却属于别的租户或会话答隔离；读取失败原样转交，抛出按不可用；签发失败答不可用并指明身份是拥有者。任何失败都不签发主体。

### 受理与输入

受理成功意味着必要数据已达到进程崩溃、操作系统崩溃与断电之后的耐久边界。普通输入的内容或有效引用、来源、租户、会话、同次提交标识与待处理资格在同一次提交里成立；没有已提交事实不得报告受理成功；拒绝留痕不取得待处理资格。受理标识先于首次发送取得并保留，回执丢失后重试只认回原事实，不新增消息、承接或 Run。受理成功不等 Agent 的唤醒送达。

普通输入的准入预算是按租户的设置，经 Runtime Context 的 `session.intake-budget` 块读取：待交数量与单输入字节数都是正安全整数。读不到时，要判预算的输入不受理，答依据不可用，不按旧值或默认值收。这个块只在答案取决于它时才读：没有输入在待交时，租户能设的任何值都会收下这一条，这时不读它，字节数按部署的上限判。待交只计占预算的来源已受理而还没被 Agent 正式接手的输入；不占预算的来源、卡片答复、控制、查询、恢复不占容量。等于上限可以受理，超过返回受限并带资源名与上限。访问裁定与原操作认回先于容量判断：已受理的原操作在队列满时仍可认回。读计数、判预算与入列在同一修订的原子提交里成立；历史输入超过新预算时仍保管。

每条输入有一个来源。来源是登记的声明，见[输入来源](#输入来源)。一次受理把声明与这次裁定的主体种类算成值，和输入写在同一次提交里：作者角色、叫不叫醒、由它单独引起的 Run 走哪个入口、占不占待交预算、来源的名字与给人看的名字。之后的交入、开 Run 与显示只读这些值，不再回头看声明。请求方不能自报其中任何一样。

来源的事实本身就写在这份会话日志里时（例如后台工具执行的结局），Session 在解释这条事实的同一次提交里受理它引起的输入，重放按来源事实的身份认回原输入。这种输入不经对外入口，受理定下的值与经入口递交的完全相同。受理之后，排队与承接的规则不按来源分，不按来源另设优先级。

不叫醒的输入照常进待处理视图。有未终结的 Run 时它照常交入；没有时它留在待处理里，随下一个 Run 的第一批交入。它不能单独使会话开始一轮。它是已受理而没有承接的输入，计入未结工作：挡自动归档，归档时和别的待处理输入一样被取消。叫不叫醒是输入在受理时定下的值，随输入活着：输入在待处理里或括号开着时都保留，被取走与失败归还都不改。成员本人在一轮在跑时发的输入可以选「等这一轮结束再发」。它和叫不叫醒一样是受理时定下的值：受理时记下当时未终结的那一轮，没有就等同普通输入。被记下的那一轮终结之前，这条输入不交入任何一轮；那一轮完成或被取消之后，它取得交入资格并能叫醒，没有未终结的 Run 时由它开下一轮。被记下的那一轮失败而会话停着等人时，它留在待处理里，等那之后开出的一轮终结才取得资格。它计入未结工作，归档时和别的待处理输入一样被取消。它与普通输入、插队三者的全化表（发法 × 会话的状态 × 之后的事）：没有未终结的一轮时三种都可以开一轮，插队与等这一轮的都等同普通输入；一轮在跑或正在取消时，普通的交进这一轮，插队的交给这一轮的等待，等这一轮的不交入，这一轮也照常可以完成；这一轮完成或被取消，等着的取得资格，与别的待处理照受理的次序开下一轮；这一轮失败而会话等人，普通的与插队的照失败的规则，等着的仍不交入、不叫醒，等之后开出的一轮终结；已归档、已冻结时三种都拒收；归档时三种待处理一样被取消。请求里的可选项是 `afterRun`（会话协议修订 3），记在受理条目上（`after`），之后不变。由 `session` 的 `tests/after-run.spec.ts` 与服务端的 `tests/rows/session-access/after-run-release.spec.ts` 守。

分流：普通消息按受理顺序进待处理视图；卡片答复认回原卡片，扩展发的卡片回原扩展的等待，工具内部的 Ask 回该工具的原等待，互不交换接续位置；控制不进队列；系统业务输入交原流程。队列由受理的输入扣除可靠承接与取消资格的事实派生，不另存决定资格的源。

受理流水线的次序固定：核请求完整并问资格；按请求身份认回；取来源的声明并核主体的种类；来源声明要解析时解析这段话；看会话的状态；来源声明要过受理前处理时运行处理件；判容量；提交；提交之后叫醒。认回排在取来源声明之前：一条输入受理之后来源撤下了，再送照样认得回。资格排在认回之前。来源没有登记与来源暂时不在答复相同，都是依据不可用。处理件一个拦下，结局是拒收；处理件不可用，结局是依据不可用，不当成放行。同一原提交重复进入时处理件会再运行，所以它要么没有外部副作用，要么按原提交身份幂等。提交之后没有拓展点：要在受理之后做事的一方订阅观察，读已提交的事实。解析一步把成员本人打的字交给解析器，答三种之一：输入，带生效内容；操作请求（命令名、参数原文，与要做的：哪个协议的哪个操作、带哪些字段，或参数不对及原因），这一次受理不提交，把请求交回（`unsupported` 带上请求）：交付面先请 Session 记下命令名与参数（`recordCommand`，日志条目 `session.command-recorded`，对人可见、不进模型视图）；参数不对就以那个原因拒收，否则再经入口的[进程内调用](../access/SPEC.md#进程内调用)替发这句话的那个登录去做那个操作，过它原来的访问裁定，答复就是那个操作的答复；会话接入经接入层契约里的 `accessCalls` 服务去做，不认识入口的实现；它不产生给模型的消息、不进待处理，结果是那个操作自己写下的条目；拒收，带原因，不入队。请求可以带一个可选项「发送方所见」，交给解析器比对。解析器的生效内容是受理前处理的起点：第一个处理件读到的是它，脱敏这类处理件看到的是展开之后的内容。原内容、解析器的生效内容与它绑定的依据在同一次受理提交里成立。识别、比对与展开的规则归[命令的规格](../slash-command/SPEC.md#解析受理的解析一步)。装配声明本部署没有解析器或没有处理件时，流水线跳过那一步；没有这样的声明而取不到时，需要它的输入不受理，答依据不可用。失效的斜杠命令明确拒绝，不降为普通消息。用途提醒是给人看的，不属于受理：输入照常受理。

已受理的普通输入由 Session 按到达顺序交入本会话未终结的 Run，没有未终结 Run 时先开 Run；不按来源另设优先级。读取、收到唤醒、向模型发请求都不是承接。承接由 Agent 的输入水位线定出确定的批界，Session 读到承接事件后保存批次、顺序与所属 Run 并解除待处理资格，不重选批界；每个输入至多一次有效承接。开始 Run 的提交把当时待处理的输入记成这一轮的初始批：去掉推迟到轮结束再发的，按受理的先后，至少有一条能叫醒；Session 发起执行时把这一批整批交给 Agent，之后不变。提交之后才到的输入照到达顺序逐条补交。补交被 Agent 的消息准入拒收时，该输入失去待处理资格并向用户显示原因，Run 继续。初始批里有一条被拒收时发起整个被拒，Run 以失败收束，被拒的那一条失去待处理资格并向用户显示原因，其余输入留给下一个 Run。发起被驱动确定拒绝而没有点名输入时，Run 以失败收束，这次发起带去的整批各自失去待处理资格并写明原因。

### 输入来源

来源回答：这条输入是谁、凭什么送来的。它是输入的属性，不是输入的种类。别的领域要给会话送输入，向会话登记一份来源声明；Session 的核心成员（`session-contract`、`session`、`session-cordis`）里不出现任何来源的名字。一份来源声明只有数据，五项：名字（`<领域>.<名字>`，稳定）；给人看的名字；接受的主体（成员本人，或系统主体并写明是哪个组件）；叫不叫醒（总是、从不、按请求里的一个标记）；过不过受理前处理（只有接受系统主体的来源写这一项，成员本人的输入恒要过）。

另外四样不在声明里，由主体的种类算出。成员本人：作者角色是用户消息，文字要解析，占普通输入的待交预算，由它单独引起的 Run 走登录入口并要登录有效。系统主体：作者角色是系统提醒，文字不解析，不占预算，Run 走系统的可信入口。主体属于哪一种由访问裁定给出：裁定为允许时同时给出主体的种类，系统主体还带组件。Session 不拆主体，也不听声明的。裁定给出的种类与声明接受的不一致时拒收；受理的裁定没有带主体的种类时答不可用。所以一个系统组件登记的来源，不论声明怎样写，都产生不了用户消息。

来源登记面 `session.input-sources` 是一个[拓展点](../../docs/architecture/cross-cutting-concepts.md#拓展点的共同契约)：服务端；按键放，每个名字至多一项，键是声明自带的名字；宿主不给贡献任何东西；每次受理现取；取不到答依据不可用；撤下之后下一次受理就没有了，已受理的输入不受影响；加可选的项是相容的，改形状换主版本。登记是这次部署的事实，不分租户；一个主体许不许以某个来源往某个会话送，每次受理都问访问裁定。登记即效应，写在登记服务自己的方法里。Session 包组自己的三个来源也经这个登记面：成员本人经入口发的输入由 `session-access` 登记；后台工具执行的结局与人对后台调用的停止提醒由 `session-adapters` 里对 Tool 的适配登记，前者按请求里的标记决定叫不叫醒（被单独停止过的调用的结局不叫醒），后者从不叫醒。受理前处理的登记面 `session.before-intake` 放一列有次序的处理件：每一件读原内容、前一件的产出、来源与请求身份，答放行（可以带生效内容）或拦下；处理件不写日志，不改来源、请求身份与叫不叫醒。解析器的登记面 `session.utterance-resolver` 只放一个，把一段人打的字判成输入、操作请求或拒收：服务端；只放一项；宿主交给它原内容、发送方所见、租户、主体与会话；每次受理现取；取不到而装配声明应当有时答依据不可用；撤下之后下一次受理就没有它，已受理的输入不受影响；加可选的项是相容的，改形状换主版本。它给出的生效内容只在原内容之后追加带来路标记的文字块，原内容里的每一块原样不动，所以去掉这些块就复原出请求方送来的原内容；文字块的来路标记只能由它写，请求方带来的拒收。受理同时保存请求方送来的原内容与进模型历史的生效内容，二者相同时只存一份；同一个请求身份再送时比较的是原内容。

受理前处理的登记面 `session.before-intake` 也是一个拓展点：服务端；按键放，每个名字至多一项，键是处理件自带的名字（`<领域>.<名字>`）；宿主交给处理件这条输入的原内容、前面一步给出的生效内容（第一个处理件读到的是解析器的生效内容，没有解析器时是原内容）、已核定的来源、请求身份与访问身份；处理件答四者之一：放行，放行并给出生效内容，拦下（可以点名一个内容块并带原因），不可用；每次受理现取；登记着的处理件按名字的码元序运行，前一件的生效内容是后一件的输入；一个拦下就拒收，一个不可用就答依据不可用；撤下之后下一次受理就没有它，已受理的输入不受影响；加可选的项是相容的，改形状换主版本。登记是这次部署的事实，不分租户。Session 的核心成员里不出现任何处理件的名字。处理件的生效内容只能在它读到的内容上给带内容引用的块补属性：媒体事实，表示快照，行内的文字兜底。它不能增删块，不能改文字块，不能改一个块的身份、可见性与内容引用。Session 逐块核这一条，不合的生效内容按处理件不可用处置。写进日志的是生效内容；调用方在原内容里自带的这三样属性不被采用。会话日志不存媒体的字节。输入里带内联字节的语音、图片或文件块时拒收，原因是要先上传。输入里带内容引用的块，受理时必须带着处理件给出的媒体事实：没有任何处理件为它给出时，这条输入答依据不可用。纯文字的输入不受处理件在不在的影响。

### 别的领域调会话

别的领域建会话、送输入、认回结局，调的是人经协议调的同一批操作，差别只在主体与访问裁定；Session 的成员里没有按调用者是谁分的业务分支。建会话可以带一条起始输入：会话身份由租户、来源主体与提交标识确定地派生，会话与起始输入在同一次提交里成立，同一个请求身份再送认回同一个会话。送一条输入的落点恰好是一个会话；目标已归档或已冻结是拒收，不暗中排队，不替它恢复，不换成别的会话。结局未知时用同一个请求身份再送或查询；请求方靠自己的耐久事实持有这份请求，请求队列只服务成员本人的输入。一份输入的去向由「读一份输入的去向」回答（见[读取与投影](#读取与投影)），请求方不拿会话最新的回复当成这份输入的结果。只停这份输入所属的那一轮，用取消一轮并点名那一轮。

### 搜历史

搜历史回答：这个租户的会话历史里，哪些消息含这些字。一次搜索有三部分：范围（整个租户，或一组会话；可以再按归档没归档与时间范围收窄），类型（条目的种类、作者角色、模型可不可读，缺省只搜模型可读的），内容（一个或几个字面词，都出现才算；或一条正则；可以选不分大小写）。匹配的单位是一条消息里的一个内容块，不跨块。一条消息只算一个命中：输入被一步取走时写的送达条目不另算。缺省搜的种类是人的话、agent 的回复、工具结果与系统提醒；压缩摘要与工具内部消息要点名才搜。被压缩覆盖的消息照样搜得到；日志里只留了预览的大结果只搜得到预览。正则的语法没有反向引用与环视，任何正则的匹配时间对被匹配的文本都是线性的；正则的长度与编译后的大小有上界，超出拒绝。结果从新到旧，按提交的时刻。一个命中带会话、这条消息的位置、种类、作者角色、时刻与命中处前后的一小段；位置可以直接当读历史的起点。搜索不改变被搜的会话：不写它的日志，不叫醒它，不重置它的空闲计时。每一页重新核资格；无权的会话与不存在的会话都不出现在结果里。

日志是权威，历史索引只负责挑候选。每个候选都回日志取出这条消息逐块核对，索引不决定一条消息算不算命中。核对与取可搜文本都在读到条目的那个读线程里做，离开读线程的只有判定的结论与索引的行。一次搜索先读索引的每个会话覆盖到的位置，再读候选，再读日志的尾巴，并把覆盖位置之后的日志直接扫一遍；所以索引落后只让搜索变慢，不让它漏。命中分两段给出：覆盖位置之后扫到的在前，索引里的在后，两段各自从新到旧；索引只落后刚提交的那一点时这就是整体的从新到旧，落后很多（重建时用着旧的一代、停机之后在追）时，前一段里较旧的命中会排在别的会话较新的命中之前。覆盖位置与日志头都只增不减，各有一个说明它们变没变的戳：戳没变时用上一次读到的，不重读；追日志的一趟也先看戳。一次搜索只用它开始时绑定的那一代索引。搜索覆盖的性质由 [SearchCoverage](session-contract/verification/models/formal-mapping.md#search-coverage) 描述；它不建模候选回日志核对的那一步，不证明实现符合模型。

历史索引是投影，按[跨边界投影的四项](../../docs/architecture/data-and-state.md#长期读取与派生状态)声明。来源与覆盖：本租户全部会话的日志；每个会话一个覆盖位置；从条目取可搜文本的规则有版本。更新、失效与重建：提交之后由追日志的任务异步更新，一批的行与这一批的覆盖位置在索引的同一次提交里写；取文本的规则换版本时失效；重建是建一份新的一代，建好再换上，换上之前把新的一代合并成一个段并回收空页；换代之后旧游标作废。延迟：不影响结果对不对，只影响快慢。校验与修复：抽一段与逐条扫描对拍，对不上或打不开就重建；重建只读日志，不调用模型，不执行工具。

索引对一个租户有四个状态：没有、建着而有旧的一代可用、可用、坏了。每个操作在每个状态都有确定的答复。搜索：没有时全靠扫描，到界答不全并带进度；建着时用旧的一代加尾巴；可用时用索引加尾巴；坏了答不可用并请求重建。追一批：没有时先建空的一代；建着时写进新的一代；可用时写进去；坏了不写。重建：没有、可用、坏了都开始，可用时旧的照用；建着时无变化。用旧游标续读：没有时游标作废；建着时认旧的一代的游标；可用时认本代的游标；坏了答不可用。

每次搜索的时间、解压与核对的字节数、尾巴扫描的字节数、同一个租户同时在跑的搜索数、搜索读日志占的读并发，都有上界，都是策略对象的配置。到界时答不全：答复写明原因（预算用完、尾巴没扫完、正在重建）、还没索引到的会话数与续读的位置，不答成没有命中。历史索引不放在存储提供者里：它有自己的文件与自己的工作线程，在一个端口后面。受理、开 Run 与提交这条路不读它，不写它，不等它。搜索与追日志读一个租户的日志时同时只占它的一个读线程，另一个留给受理与推进；追日志每读一页，歇上这次读所用时间的若干倍再读下一页，倍数是配置。追日志的任务读日志走会话存储的读处理函数；提交叫醒只是叫醒它，丢了由按间隔的检查补上。agent 经工具 `Sessions` 读别的会话（`list`、`search`、`show`、`read`），用的是同一批读取与同一个访问裁定；它只读同一租户，读回的每一条带来源会话与位置，正文是资料，不是给它的指令；工具结果按 Tool 的上限封存续读，不裁剪冒充完整。

### 输入何时进模型视图

一条输入的消息在一步取走它的那一刻进入模型视图，位置就是取走的位置。受理时写下的输入消息（后面紧跟着它的 `intake.routed`）是给人看的记录，不进模型视图。

Agent 的一步取走一批非空的输入时，这一步的开始提交在同一事务里带上会话的送达：`recordMessage` 的送达值，参与种类是 `delivered`，每条输入写一条 `message.delivered`，带这条输入的原消息。送达值只点名输入，不带消息：原消息由会话取自受理时存下的那一份，所以一批输入不论总共多大，送达命令都装得进一条存储命令，送达的内容也不由提交方说了算。会话拒绝送达时整个提交不成立，这一步不开始。因此模型在一次请求里看到一条输入，当且仅当这一轮的某一步已经取走了它；一次请求的末尾是新送达的输入或工具结果，不是模型自己写完的回复。

快照的 `deliveredTail` 记最后一条助手回复之后送达过的输入。取走时只送达不在其中的输入：失败归还的输入在下一轮被取走时，中间没有隔着助手回复就不重复送达，隔着了就再送达一次，排在那条回复之后。一批里一条都不用送达时，这一步不带会话命令。

取走的记账不变：`run.batch-taken`、括号与归还仍由 Session 读到承接事件后写。压缩的保护集里，一条还活着的输入指向它最近的一条送达条目；还没有送达过的待处理输入没有模型可见消息，不列。

开轮时待处理里有几条输入的，它们是同一个初始批，Agent 的第一步一并取走并送达。这一轮向模型发请求的次数等于取走的批数。

### 输入的括号

一批输入被一轮取走，是开一个括号。括号在这一条成立时关上：取走之后，有一条完整的助手回复进了日志。取走是租出，不是消费。

| 这一轮怎样终结 | 括号还开着的输入                                     | 之后要不要自动开下一轮         |
| -------------- | ---------------------------------------------------- | ------------------------------ |
| 完成           | 不会有：有输入没回答就不能完成                       | 还有能叫醒的待处理输入就自动开 |
| 被取消         | 随取消一起了结，不回到待处理。人说了停，不替人再跑   | 还有能叫醒的待处理输入就自动开 |
| 失败           | 在终结的同一次提交里回到待处理的队头，保持原来的先后 | 不自动开。会话等人             |

### 等人

一轮失败之后会话进入「等人」。这时不论待处理里有什么，都不开新的一轮：失败之前重试的预算已经用完，再自动跑一次没有新的依据。「等人」只有两个出口，都是人的决定：人发来一条新的输入；人对失败的那一轮发「重试」。解除之后，下一轮照常由 Session 开，按先后把待处理的输入一起带上，归还的在前，新发的在后，不用重新输入。

「重试」只解除等待，不是一条输入，也不由系统自己发。它点名失败的那一轮：那一轮已经不是会话在等的那一轮时答找不到。待处理里没有能叫醒的输入时它不被受理：下一轮开不起来，受理了也不会开轮。这种情形出现在一轮先给出过完整的回复、之后才失败的时候，人要让它接着做就发一条新消息。

能不能开新的一轮只在一处判。提交之后的触发、启动时的扫描、显式的开轮命令，问的都是这同一个判定。

会话在不在等人、等的是哪一轮、还有几条待处理，也只在一处算，「重试」认失败的那一轮用的是同一个算法。会话的工作面为此有一个窄的读口，只答这三样与那一轮的 execution，先判主体能不能读这个会话，不把会话的状态交出去。客户端经协议的「读等人」读到它们，连同这一轮失败的成因。

### 请求队列

发消息的请求到了服务端，先落进它所在会话的队列，再由这个会话的排空者按先后交给会话受理。受理进了会话日志，调用才答成功。

- 每个会话一条队，键是（租户、会话）。会话之间互不相干：会话甲的库在忙，只有甲的请求在等。
- 队列里是「送到了、还没有结局」的请求。它们不是会话里的事实，会话日志不记它们。
- 一条请求有了结局就离开队列，队列不留它。结局是受理成功，或者一个确定的拒绝。之后问「这条消息怎样了」，答案在会话日志里。
- 队列落盘。进了队列的请求在进程重启之后还在，重启后接着受理。
- 队列不是调度器，不在会话之间排先后。队列不是存储，不替会话日志保存任何东西。

一条请求在队列里存这些：租户文本、会话、请求标识、输入标识、消息的 JSON 文本、登录的编号、它在本会话里的序号。入队之前先做两件不读存储的事：消息要解得出来，登录要换得出目标租户里的主体。有一件不过，请求就不入队，调用按原样作答。排空时用队列里存的租户与登录重新签发主体，再受理。一条请求还在排队时，发它的登录被注销了，这条请求照样受理。发消息与注销登录是同一个人先后表达的两个意图，各自成立，互不相干；注销只决定之后还能不能用这个登录再发，不追回已经发出的消息。

#### 全化表

一条请求只有两个状态：不在队列里，在队列里。

| 操作                     | 不在队列里                                                                         | 在队列里                                                                                               |
| ------------------------ | ---------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| 入队（同标识、内容相同） | 追加到本会话队尾，等它的结局。本会话的队列已满时答 `limited`，`limit` 是队列的上限 | 认回同一条：不再追加，等同一个结局                                                                     |
| 入队（同标识、内容不同） | 追加。它以前有没有被受理过，由会话按原来的规矩判                                   | 答 `conflict`，不追加                                                                                  |
| 取队头去受理             | 无事可做                                                                           | 受理有了结局：记下它离开队列，把答复交给等着的调用。受理要再取：留在队头，按退避再取。哪些算再取见表下 |
| 查询                     | 问会话日志                                                                         | 答 `unknown`                                                                                           |

「内容相同」比的是输入标识、消息的 JSON 文本与登录。留不留在队头按成因分，不按对外的答复分。再取的只有两类：

- 等一等会好的：会话答 `unavailable`；会话此刻不在树上；签发主体暂不可用。
- 结果不知道的：会话答 `commit-unknown`；调用开始之后抛出。

其余每一种都是结局，带着它对外的答复离开队列：成功，以及任何别的失败。这包括对外答 `basis-unavailable` 的失败，例如会话答 `quarantined`，或者答一个不在 `send-input` 结果集里的种类。它们不会自己好，留在队头只会挡住这个会话后面的消息。

受理仍旧按请求的标识恰好一次。同一条请求被再取一次时，会话按原来的那次操作认回，答成功并标明是认回的，不产生第二条消息。这种情形出现在上一次受理的提交成了、记「离开」之前进程没了的时候。这一条靠会话原有的规矩，队列不另做。队列永远守住的六条性质是「不变式」一节的 RQ-1 到 RQ-6。

#### 落在哪

队列在 `session-access` 里。排空一条请求要用登录在目标租户里的主体，这是接入插件的知识；入口与会话核心都不认识队列。

落盘用一份只追加的日志文件，在存储的线程池之外。全部会话共用这一份文件，内存里按会话分开。文件在一个端口（`RequestJournal`）后面，换成别的实现时别处不动。队列空了的时候文件截空，所以进程不重启文件也不会一直长。放在线程池之外的理由：系统范围的库没有自己的线程名额，和租户的库抢同一批。名额全被占着的时候，入队本身会失败，而这正是队列要治的情形。别的提交类操作（建会话、取消一轮、停一个调用、重试）不进队列。

### Run 与推进资格

Run 层是 `none → active → completed | failed | cancelled`，终态不可反转，每个 Run 至多一次有效终结。attempt 层只在 active 里：授予、推进、等待、交还或被取代，再授予。等待不是 Run 的状态。Run 与 Agent 的执行一一对应，attempt 与执行的挂接一一对应；换代与恢复沿同一个执行。attempt 的序号严格递增，来自持久的开始事实，不靠数历史条目。

同一会话至多一个未终结的 Run，同一 Run 至多一个有效的推进者。新 Run 要有至少一条能叫醒的待处理输入、没有未终结 Run、入口准入满足；只有不叫醒的输入时不开 Run，无输入不造空 Run，已有 Run 接续或等待时不另造。交互入口的新 Run 要确认登录有效，同一 Run 的恢复不重过登录门，也不因登录到期取消已经推进的工作；后台与系统触发按各自的身份契约，不扩大登录条件。

新 Run 分两次提交，顺序固定：先提交开始 Run 与首个 attempt，不扣任何输入的待处理资格；再向 Agent 发起执行，带开始 Run 的提交记下的初始批。两次提交不合并。开始 Run 的提交遇到会过去的失败（前一个执行还没解释完、历史读不到；修订已变）时，按推进的退避等一档，再读快照、再判能不能开、再提交；退避用完记诊断，待处理的输入留给恢复扫描。两次之间崩溃，按原操作身份重放发起，Agent 按操作身份认回原受理，不新建执行身份。核对失败（推进资格已被取代）就停下交恢复；Agent 忙就等它的终态事件后重试；不可用则退避。发起被确定地拒绝（准入拒收或驱动被拒）时，执行不创建，Session 以这次拒绝为耐久依据提交有界收束，终态为失败。

新 attempt 生效后，旧 attempt 不能追加输入承接、发起调用或提交推进事实。资格要在实际发起与提交的边界有效，不是创建时检查一次。旧执行迟到的结果与费用仍按原调用身份保存，不算旧推进者越权。晚到的参加提交被判冲突，晚到的保管与处理交接、结果接收照常提交，晚到的 Agent 事件照常按事件身份写入并保留实际关联，晚到的重装与接管因预期过期而被拒。

推进命令（接管、重装、交还、收束）的乐观并发只比 Run 层的修订，不比整份快照的修订，所以无关的提交不会让有界收束一直重试到放弃。每个推进命令的预期修订必填。

接管（claim）分两步：先提交，核对旧 attempt 已交还或可信排除，授予新 attempt，序号加一；再向 Agent 接续，Agent 的条件提交里 Session 作为参加者只读核对。接续失败不撤销接管的那次提交：新 attempt 已是当前资格，由同一恢复者或下一次扫描用同一推进资格依据重试，撤销会让序号回退。谁读到当前推进并能出示它的证据，谁就能继续，不必是发起接管的同一进程。同一候选重复的重装认回原回执，同标识不同候选答冲突，不同候选且预期过期答已变。

重装由人显式要求：会话协议的 `reload-session`，或会话带来的系统命令 `/reload`。资格是登录的人对自己有继续资格的会话；别的租户与没有资格的被拒，答复与会话不存在相同。重装的判定：会话已归档或已冻结时拒绝，已冻结的带冻结的判定；取消已成立时拒绝；有一轮在跑、取消还没成立时，指着这一轮的重装判候选与交接证明，通过就在一次提交里记采用、撤旧、开新，不指任何一轮的拒绝并带修订，调用方带上这一轮重来；这一轮刚好结束或没有在跑的一轮时，指着那一轮的拒绝，调用方改走不指任何一轮的；不指任何一轮的判候选，通过就只记采用，与现在一样不写；候选带冻结的判定时拒绝并带回判定，推进随后提交冻结。重装是一个采用点：采用来源按这次重装自己的键现读工作区，不沿用这一轮开始时读到的那一份。没有在跑的一轮时，推进向采用来源要一次不靠比对跳过的求值，照右边一列提交：候选成为会话当前的采用，不开 Run，不建 attempt，下一个 Run 用它；与现在一样答「已经是最新的」；候选不合法保留原来的，答原因。有一轮在跑时，受理时就记下这次重装，在下一个安全点生效，不占请求队列，不动排着的话。重装先在不写任何条目的情况下备好候选并向 Agent 要交接证明：Agent 睡在已保存的等待上时马上交出；在一步的中间时，这一步求值之后、下一次模型请求之前交出；正在收尾时拒绝，重装改走空闲的一支；Agent 的规则见[它的规格](../agent/SPEC.md#接手)。候选不合法、交接被拒或不可用时不写任何事实，原采用仍合法则继续，不合法则报告不可用，不换定义标识，不以空采用推进；Agent 已经交出而提交被拒时，恢复扫描照原来的采用把这一轮接回去。从要交接到接上，恢复扫描不接管这个会话。提交在会话的串行段里做：先核执行仍是已交出、没有人接上（同一份交接可能已被另一次重装接上），再按交接之前读到的 Run 层修订提交，其间有过接管就答已变。这些交错由模型 `reload-handover` 检查（[形式对照](session/verification/formal-mapping.md#reload-handover)）。原采用的旧推进能配合时先交还，不能配合时撤除并入接管。提交成立之后，新的一次接手照[接手与恢复](#接手与恢复)的路接上，带着新的装配。重装成立后新采用只影响还没开始的经过，原调用、等待、卡片保留，已经发出的工具调用不重做，它的结果由新的一次接手用上。候选等于当前采用时不写采用变化。

Session 不保存接续值、检查点或任何 Agent 的工作状态；恢复需要接续数据时读 Agent 的执行记录。

### 与 Agent 的同日志参加与解释

Agent 经它的日志提供者写执行记录，Session 拥有会话日志；两本账在同一个事务域，提供者之间不另建事件副本的传输协议。Session 参加 Agent 的提交：四种交接（消息、上下文转换、保管、处理）在同一次提交里由 Session 共同保存；打开执行、交入输入、挂接、条件终结做只读核对，核对与发布之间必须复核原修订，不能让提交期间新受理的输入漏出条件终结的守卫。

来源核对：发起执行的来源依据是 Run 开始的回执，必须指向本会话已提交的开始事实，执行等于当前 Run 的执行，每条初始输入都属于开始事实记下的初始批、与推进资格依据吻合，Run 未终态；交入输入的来源依据是该输入的受理回执，输入当前有待处理资格，去处是本 Run；发起与交入的核对都只带每条输入的消息摘要，与会话受理时存下的那一份比对，不带消息原文；挂接的来源依据是该 attempt 的授予回执，普通推进要求它等于当前推进，取消收束只允许该 Run 已被取消、该 attempt 是取消之前最后授予的那一个，这样的挂接只带取消授权，结论只能是已取消。核对不成立响应「冲突」，依据为输入当前去处或当前推进；Agent 把它译成被拒，恢复者停止并交恢复，不按已变重读重试。

条件终结只读核对待交输入：以完成或取消为结论、而已受理还没交入的输入非空时响应冲突，推进协调补交后 Agent 重新求值；以失败为结论时不因待交输入响应冲突，这一轮照常以失败终结，这些输入保留待处理资格，由下一个 Run 承接（失败的一轮不再取输入，为它们挡住终结会让这一轮永远开着）；Run 已是被取消终态时响应冲突，依据为取消，Agent 以已保存的取消依据再次终结，核对结论只能是已取消。取消终态由哪一条控制写下就认哪一条：终态的依据就是那条控制的出处，取消一轮、归档与自动归档都一样；Agent 带来的取消控制与它相符才放行，不看会话里别的控制有几条。输入已被 Agent 取走而解释还没跟上时，交入回执的提交先答不可用，等解释跟上；这是两次提交允许的交错，不是遗漏。

保管与处理两种交接、以及生产方回报的执行事实，都要求所涉调用的绑定已在会话里。Session 判这类提交时读所涉执行里还没解释的事实；绑定登记在那里，就先答不可用，等解释跟上，不答非法。还没解释的事实里也没有这个绑定，才答非法。

Agent 的事实先由 Agent 的提交保存；Session 随后读同一日志里的事件正文与快照，经纯函数决定另一次解释提交，把承接、调用登记、等待、结束等后果、解释进度与该次操作的认回答案同批保存。解释提交失败不撤销 Agent 已提交的事实，也不推进持久的解释进度；未知先认回该次 Session 操作。两次提交共用会话日志，不合成一个原子批次。每个派生后果按原执行与事实身份唯一认回；事件进度、真实 head、原来源分别保存；每次读取都核对当前资格、租户与执行，并核对历史上的执行与 Run 的对应，没有对应关系时拒绝推测；日志有缺口按隔离处理。终结条目的收尾摘要：执行记录结清之后就会删掉，所以一轮怎样收尾在写终态的那一次解释提交里写进会话日志。那时执行记录还全，会话适配读 Agent 结束意图里的结论与失败候选，映射成会话契约自己的 `RunEnd`，写进 `run.terminal` 条目的 `end` 字段。`RunEnd` 有 `conclusion`（`complete`、`fail`、`cancelled`）与 `failure`（没有失败候选时为空）。`failure` 按种类（`kind`）只带读者要的字段：`node-failed` 带 `node`、`category`、`failureKind`，失败的产生者交出了一句只含身份与状态的诊断时再带 `diagnostic`；`model-refused` 带 `failure`，是 Model 拒绝的种类名；`no-reply` 带 `cause`、`upstreamStatus`、`diagnostic`，取自模型故障，没有时为空，Model 说上游在限流时再带 `throttled`（只取 `true`）；`cannot-fit` 带 `reason`；其余种类只带 `kind`。这个形状不引用 Agent 契约的类型。会话自己决定的终结写它自己知道的收尾：控制取消的一轮写 `conclusion` 为 `cancelled`、`failure` 为空；受限终止的成因在终结条目的 `bounded` 里，`end` 为空。读一轮失败成因的两处（读等人的成因端口、诊断页的 Run 收尾）都按 Run 读会话日志里这一轮的终结条目，不读 Agent 的执行记录；投影不丢栏：终结条目里带着的类别、上游状态、限流的记号与诊断，读等人的成因里都读得到；没有完成的一轮 `end` 为空时，诊断页答未记录（`not-recorded`）的缺口，读等人答没有成因。

未解释的日志事实计入未结工作，延迟解释不得造成提前空闲或完成。取消结论的解释要核对原 Run：只有该 Run 已有 Session 提交的被取消终态才认回 Agent 的取消结论，否则拒绝，不写取消终态、解释进度或成功答案；Agent 的事实仍保持已提交。已取消的原 Run 收到迟到事实时，只认回或保留引用，不反转终态，不改后继 Run、推进或等待。解释提交遇到一时的失败（不可用、已变、重发之后仍未知）时按退避再做，第一次也等过下限（缺省 50 毫秒起、每次翻倍、5 秒封顶，三个数在同一个策略对象里），不设次数上限，直到提交成功、得到确定的答复或插件停止。失败是一时的还是确定的，由产生它的一方说：缺的东西只是这一次读没带上（解释还没跟上、索引还没读完、快照的整块可选部分缺席），答不可用；日志或快照点名的那条记录确定不在（调用的登记、原始等待、控制引用的调用），答隔离，等多久都不会有。确定解释不了（隔离、非法）就不再重试：这个执行属于在跑的一轮时，以「解释不了」（`uninterpretable`）有界收束这一轮，终态的依据写明失败种类与诊断，没答完的输入留在待处理；这一轮已有终态时只记一行。这样收束的执行，Session 不再读它余下的事件，也不再等这份读取：快照里这个执行带上 `uninterpretable` 标记，之后的开轮、收场与空闲判断不要求它的尾巴已解释，后继的一轮照常带上留下的输入。别的终态不带这个标记，尾巴照旧要等。确定解释不了的执行在这个进程里只说这一次：之后不论什么再叫醒它的解释，都不再读、不再记。其余确定的拒绝只记日志，不重试。推进的重试档位同样没有 0：配置里某一档写成 0 在构造时被拒。结果未知时用同一操作身份重发同一通道的提交来认回，按操作查询认不回解释提交。后果没有判出的事件在该处停下，不当成别的东西提交。解释插件启动时不扫存储：漏掉的事件由同一执行的下一个事件带动解释，还没解释完的部分由已保存的解释进度与执行事件之间的差距记着。

模型与工具两条已收条目通道的解读进度，除了通道里的序号，还保存本批最后一项在执行条目里的位置，与后果同批写下。每一轮只从这个位置往后读；一个结果是不是转过后台的调用的结局，按原消费点查它的已收条目，不扫整条通道。每轮的读取量只取决于新增的条目。

Agent 日志提供者按租户与执行读执行索引，把调用交给该执行所属会话的日志；点名一个执行的材料保管同样按该执行路由，写进该会话。没有 Run 启动过的执行与别的租户的执行得到同一个拒绝答复，且不写任何东西。执行索引读不到答不可用，不答拒绝。不带执行的材料保管没有可路由的会话，答不可用且不写。每次成功写入之后只发一条不带事实的唤醒事件。执行记录的存放：记录按项存放，项有族与原键；存储只守一条规则，一个项只开一次、只改开着的项、关闭之后不再变，内存核心单独充当存储时守同一条。每族的开放规则是开放视图上的纯函数，所以每一步的读入与常驻内存只取决于开着的工作与新事实，冷启动只读开着的项，收尾与结束之后读全。关闭的项按原键读回；迟到而合法的事实不重开已关闭的项，而是把身份细到这次事实自己（结束之后才到的结果占新条目位，持有按持有期成项，交接的保管登记按交接与登记操作成项）。一次操作的答复只存引用、不内嵌随工作量增长的列表，一个操作只写一批；执行的头取自推进了修订的那一批；事实的内容只取决于命令与日志，保留的材料归命令里的执行，读它要有这个执行的资格。事件流是对账本的读，不绑在某个内存副本上，账本每知道一次发布就唤醒等待的流；一次调用读回关闭项的轮次不设常数上限，只有输给别的写入者才计入重试。与 Agent 契约的一处偏离：契约说保管未提交的交接算开着，这个状态只在一次登记结果未知的在途期间成立、不在日志里，本实现由账本保着在途的登记并按原键读回交接，此时读执行快照不列这条已关闭的交接。

执行记录里材料内容的回收：保存材料的一方在存的时候声明持有结束之后还有没有读者，缺省是有读者。声明随材料的事实记进执行记录。有读者的材料，内容按摘要存进共用的块表，与别的记录共用一份。声明没有读者的材料，内容按自己的条目（租户、执行、条目）存，不进共用的块表，也不参加按内容复用，所以别的记录不会点名它。这份材料的持有结束时，提供者在那一次发布的同一个事务里按这个键删掉内容；执行已在收尾、条目不再关闭时也是这样。事实行与条目行不删，事实里留着摘要。之后读这份材料，答已回收（`reclaimed`），不答成功、空或不可用。冷启动、收尾时读全、读回关闭项与投影记录，都不取这份内容。持有期间内容缺失是故障，读取答不可用。这条规则只管 Agent 的执行记录，不改变「日志与提交」一节对会话日志只追加、内容不可删的规定。执行记录的确认与回收：会话收完一个执行的全部交付之后，向 Agent 日志确认一次。收完由会话自己的事实判断，两件同时成立：工作快照里这个执行已终结；工作快照里没有挂在它上面的调用（转了后台还没结算的调用也在其中）。挂没挂着只由会话契约的 `callOpen` 一处定：调用被控制引用、或还等着它的交付时挂着；被调用方的终局交付（Tool 与 Model 的结果，转了后台的 Tool 调用的最终结局也在其中）一经条目消费写进会话日志，调用就不再挂着，不要求 Agent 处理过。成立之后读一次 Agent 快照的输出位置，最新发出的事件正是会话的消费位置、而确认还没到这里时才发；`through` 取这个位置。读输出位置只为不在迟到事件消费之前确认、不重复确认，收没收完不由它定。这个判断只有一处，日志解释每次解释成功之后调它，工具日志消费与模型条目消费每次把交付写进会话之后也调它。两边互相叫醒：日志解释每次提交之后叫醒这个执行的两条条目消费，两条条目消费每次提交之后叫醒这个执行的日志解释。条目消费读条目期间执行的修订变了，这一轮不提交、不报故障也不告警：改了修订的那次 Agent 提交已经排了下一轮。Agent 处理一次交付的事件，Tool 与 Model 都一样，只在这个被调用方的条目消费已把它处理的那份交付写进会话日志之后才解释；同一调用之后才到的交付不等。两条消费各按各的次序走，处理要是等同一调用之后的交付，排在那份交付前面、属于一个还没有事件点名的调用的条目会让两边互相等（模型 `binding-order`）。日志解释遇到处理了会话还没收到的交付，就停在这个事件之前，不跳过，等条目消费跟上再接着解释。这个事件自己带着那次调用的绑定（登记与关联）时，先单独提交这个事件里还不在会话里的绑定后果，解释位置不前进；条目消费据此写下交付，日志解释再提交这个事件的其余后果。一个事件里先登记后处理，会话日志按同样的先后记，两条规则不互相等。Run 进行中不确认，执行修订不因确认而前进。确认在丢失或中断之后不另留待办：执行记录提供者每次由新的写者代际第一次打开租户域时，唤醒已终结、确认没有到最新事件的执行，由日志解释再判一次。服务就绪时，执行日志对每个已登记的租户各打开一次租户域，所以新代际的这一次打开不等这个租户的下一轮 Run。Agent 日志在每次提交里对这次提交触及的执行判结清：已终结，确认到最后发出的事件，终结责任清单每一项都已结清。结清的那一次提交在同一个事务里删掉这个执行的事实行、全部条目行、条目内容、预准入记录与这个执行自己的块，把 `er_execution` 留作墓碑并标上结清的发布号，`er_operation` 留着，本进程里结果未知的提交仍按它认回。执行记录自己的块（Agent 检查点里的动作批、经过链、交接、中断与准入意图这一类）按执行存，只在同一个执行里按内容合并，不进会话的共用块表；声明持有结束之后有读者的材料仍按内容存进共用块表，不随结清删除。准入索引（输入与它的准入的对应）供会话读历史，寿命跟着会话，不随结清删除。已采用的请求按用途分两样留：会话当前的固定采用（本会话最后一次采用的请求，下一次请求经会话的窄采用来源读它，算 `continues` 与前缀变化原因）在结清的那一次提交里从这个执行的块移到按会话一份的记录里，留到同一会话里一次更新的采用结清时取代它；读当前采用取活着的执行里最新的采用与这份记录里发布号大的一份。每次模型调用的表示选择（每块带内容引用的块读的是原件、派生还是转写）在采用它的那一次提交里按（租户、会话、调用引用）另记一行，只记选择，不记整份请求，寿命跟着会话，诊断页按调用引用读它，活着的与已结清的调用同一条路。结清之后对这个执行的读写答已终结（`terminal`），不重建；被调用方把结果或占位推到这个执行的消费位置，接收方答已保存（`saved`）：结清证明这个执行的每一份交付都已写进会话日志，答拒绝会让被调用方一直欠着这份交付；结清那一次操作的查询，按墓碑上的修订与回执答已提交。执行记录提供者在新的写者代际第一次打开租户域时，删掉已结清执行的墓碑与 `er_operation`；此后对它的写与没有 Run 启动过的执行得到同一个拒绝。结清的那一次提交同时记下结清它的写者代际，清扫带着当前写者代际，只删更早的写者代际结清的；这次清扫没做完时，本代际之后的一次打开再做，本代际结清的墓碑留到下一个写者代际。读者按墓碑处理：读开着的项与按键读项读到墓碑答已结清；按发布号读事实时，被回收的发布号由 `er_operation` 认出，并列出它的执行，落后的账本据此重读；「记录早于事实族」只在会话没有一条事实而还有没结清的执行时成立。

### 接手与恢复

Session 把一轮交给 Agent 之后，会话读到 Agent 的受理，就当这一轮已经交出，不再重发。这份「读到过」只在内存里，不是事实源，不能因为它没记上就重发：受理之后 Agent 可能已经取走输入，同日志解释还没有跟上。重启之后从日志出发，照原操作身份把开始事实记下的初始批再交出一次，由 Agent 按操作身份认回原来的受理。

重新交出被受理之后，立刻做一次接手检查：读执行记录，问受理它的活体是否还在。交出本身可能被打断，Agent 写下了受理而 Session 没读到回答，进程就没了；原来的受理把推进交给了当时的活体，换了活体之后这次工作只经接手检查与新的执行尝试继续。推进资格已归后一次尝试的一轮也交给接手检查，由它认回接管再接续，而不是只记诊断就停。会话接手时问到执行已经终结而这一轮仍开着，回答的一侧补发一次唤醒，使会话读到结束事实。

恢复协调对一个会话的权威读逐类先查后做，查不到不当作不存在：

| 读到                                             | 先查                       | 做                                                                                                         |
| ------------------------------------------------ | -------------------------- | ---------------------------------------------------------------------------------------------------------- |
| 有未决的操作                                     | 每项按操作身份认回         | 已提交交回原协调器继续；未提交由原发起者决定是否重试；未知保留并报告                                       |
| 已授予而 Agent 还没受理                          | 发起的出站操作身份         | Agent 尚无记录就以同一身份重放发起；已受理就接手检查，交入记录没记上也继续                                 |

| 挂接已交还或被取代                               | 交还的身份                 | 认回或提交交还，进入下一行                                                                                 |
| 没有推进者                                       | 读执行记录                 | 先接管再接续；挂接仍活着时只有持接管资格并有宿主的失联判断才接管，没有依据就等 Agent，不以失联判断代替资格。接续被 Agent 确定拒绝（同一步连续停下到上限）时有界收束为失败，终态的原因取拒绝的原因，执行在执行记录里不终结 |

| 控制在传播中                                     | 原控制操作、待核对的生产者 | 交控制传播协调，不重发原调用                                                                               |
| 各类任务（初始化、已分流输入、级联、作用域释放） | 各拥有者                   | 重新驱动负责方；拥有者不可用就保留任务，退避                                                               |

提交未知时双方都不把未知改写为失败或成功，不发出依赖这次提交的外部效果（交付责任解除、发起执行、控制传播、叫醒）；认回为已提交才继续，为未提交就用同一身份重试；Session 为提交方的操作认回超过策略上限仍未知时，保留在未决里并报告维护者，不清理任何提交。参加提交的未知由提交方认回，Session 不列入自己的未决。

受理之后、唤醒推进之前崩溃，没有输入因叫醒丢失而停留：恢复扫描读出有能叫醒的待处理输入的会话，开 Run、重放发起、补交输入都按原操作身份，重复触发被认回。会话读到有未终结的 Run 而没有活体、没有人接手时，不声称空闲或完成。

### 等待与结果交接

等待关联原工作、开始依据、目标调用或卡片、原消费位置与交付责任，不另建独立的等待对象。释放 Agent 的计算不解除这些关联，也不取消独立的 Model 或 Tool；查询不到句柄或执行状态时保持未知，不自动重发。恢复所见与处置：原调用仍在执行，重取合法访问关系，继续原等待；已收场未交接，从生产侧取回原结果回原消费位置；已可靠交接而处理未完成，从消费侧内容或有效引用继续，不向已确认的模型重新领全文；查询故障保持未知；原执行确实失去连续性，交 Model 或 Tool 自己的契约，仍回原用途；原 Run 已终态或原调用不再等待，只完成允许的历史、交付与结算。

转了后台的调用，结局按下面的路回到会话：

1. Tool 把占位与最终结果推给原消费位置，由 Agent 的结果接收方保管；Tool 不认识 Session。
2. Session 解释占位的保管记录，记下这次调用已转后台；解释最终结果的保管记录时，在同一次提交里记下它已结算，并按[后台结果投递资格](../../.meta_harness/design/ubiquitous_language/terms/interaction-and-dispatch.md#ul-background-result-eligibility--后台结果投递资格--background-result-eligibility)决定要不要把它受理成一条输入。
3. 资格在：受理一条系统来源的输入，消息是 `SystemReminderMessage`，来源标记是后台工具执行，正文是这次调用的短号与标签、终局、效果与结果的模型可见内容，卸载的正文只给引用与取回办法；短号与标签是 Session 按快照里的后台调用记录补在最前面的一块（`This is background call b<n> (<工具> <命令>: <意图>).`），工具送来的块原样跟在后面。输入身份由（调用，结果版本）派生，同一结果至多成为一条输入。这次调用被单独停止过时，这条输入不叫醒，正文写明谁停的。资格不在：只记结算，结果照存、照样查得到。

资格从快照派生，不另存：会话没有归档，资格就在。单独停止这次调用不撤销它，取消原 Run 也不撤销它。占位留在历史原位，不改写；结局只在承接时追加到历史末尾。转了后台而还没结算的调用计入未结工作，挡自动归档，不挡 Run 完成。

主流程、扩展、压缩与 Run 外的消费位置分开。Run 外的调用保留真实的调用身份与对应的会话消费者，不伪造 Run 或 attempt，不借用碰巧活跃的 Run，不因接续重新计费。不可用的替换件沿原动作、工具身份与消费位置承接。

内容或有效可恢复引用、原归属、原位置与后续责任可靠保存之后，或原消费的处理已完成并保存了必要的完成事实之后，生产侧的责任才解除。交接与解除要可恢复地一致，不能双方都认为对方负责；展示、观察、收到叫醒、开始处理都不等于可靠消费。解除的确认由生产者自己做，结果接收方只返回已保存；同一原调用、同一结果版本、同一消费位置的重复确认返回原确认。模型收场后由当前合法消费者按 Model 契约确认，确认、清理、费用各自可查；Tool 不自动采用这份确认。保管成功而生产者确认未知时，保管继续，按原操作查询，不重新领取已清理的全文。

人的答复等待可以释放 Agent 的计算。卡片原事实保留，服务超时、实例释放与时间流逝不制造答复，不结束等待。扩展同批的卡片全部处理后才解除批次阻塞并回原扩展位置；人明确不回答的卡片返回没有答案，且不授予依赖批准的动作；工具内部的 Ask 只回该工具的原等待。会话日志里不另造第二个有效的卡片决定，卡片记录只引用并承接原决定。单次授权只覆盖明确批准的动作，整批才覆盖整批；消费后或所属 Run 终态后不得再用；撤销归档不复活被取消的卡片或已消费的许可；全局租户授权写租户权限设置，由拥有者校验上界。

### 终态、控制与取消

Run 的终态只有完成、失败、被取消。完成要先过原工作的条件与适用的终态前扩展，后置扩展不得撤销；队列空、模型无动作、runtime 退出、非常态上交都不自动证明完成。写终态的那一笔提交先为该 Run 里每个未答的调用写一条工具消息，再写终态；这条消息陈述发起方知道的事实（调用的结果不在对话里、Run 因何结束、工具可能已经产生效果），不是工具的结果，来源标记与终态条目相同。归约遇到还有未答调用的终态判历史不合法，所以后继 Run 的请求读到的历史里每个调用都有工具消息。

终态之后不新增原 Run 的 attempt、输入承接、调用或外部动作。已发的调用与未结费用可迟到保存，迟到的结果不成为消息；仍具合法投递资格的后台结果在未归档的会话按输入规则交后继工作，其中不叫醒的不单独开后继 Run，原 Run 不复活。已因归档取消了业务资格的调用，其结果在撤销归档后也不自动入队或造后继 Run。

控制先保存目标、发起主体、原因、级别与意图，随后按持久关联撤资格并传播，不依赖旧 Agent 句柄转发；受理不冒充实际生效或物理停止。单调用控制的发起主体由调用方类别给出：受理方是用户，协调方是 agent，维护方是系统；调用方不能自报。原因由调用方给，可以没有。控制的最小对接：Run 取消用该 Run 的身份，单调用控制用原调用身份，这一次操作用提交身份；成功是意图已保存，Run 取消生效时同批记被取消终态并撤销新发起资格；与已生效的终态冲突时拒绝并带回已生效的终态；未知按原提交身份查询，同身份重试返回原结果，同身份带不同目标或种类则拒绝。格式不合法的控制命令先于任何查找被拒，答复不泄露已有什么，也不保存任何事实。取消或打断一轮时，控制的待确认只收这一轮前台在等、而且仍在外的调用：最终交付已经写进日志的调用不进，哪怕 Agent 对它的等待要到下一次取批才消。「在外」与之后核对这个控制时用的是同一个判断：快照里有这个调用的登记，并且开放规则成立；所以待确认里的调用在控制对上账之前一定有登记。

控制送到调用当前的等待者。停一个转了后台的调用，Session 凭调用引用直接向 Tool 提交 `stop`。用户提的停止，在同一次提交里受理一条停止提醒：消息是 `SystemReminderMessage`，正文是这次调用的短号与标签、谁停的、原因，并写明停止只是已请求；它是不叫醒的输入。一项后台调用至多受理一次停止：它已经有停止时，再来的停止不论谁提的，都答原来那一次，不另留提醒；提醒的输入身份由调用派生。agent 提的停止与归档的撤回不受理提醒；转后台只对还在等待里的前台调用有意义，经 Agent 送达，调用已在后台时答复带回已成立的关系；归档对每个转了后台而没有结算的调用直接提交 `withdraw(all)`。直接提交的端口由 Session 声明，接口只说「按调用引用控制一次调用」，`session-adapters` 用 Tool 的命令实现。

本会话的后台调用只有一个查询，命令行、界面与给 agent 的工具都用它。一项后台调用是日志里记了已转后台而没有记已结算的一次工具调用。它的短号、标签、来源、转后台的时刻、停止的发起主体与原因取自会话日志。它的执行状态与控制的进度在读的时候经 Session 声明的端口向 Tool 现问，接口只说「按调用引用读一次调用的状态」；Session 不保存也不推断它。问不到时这一项的状态是未知，不显示成在跑、已停或不存在。停止的进度只有已请求、已受理、已证实停下三种，各自可辨。短号在调用转后台的那次提交里定下：`b` 加它在本会话转后台的先后，从 1 起，不复用。标签随占位的保管记录进来，Session 照抄，不解释。按短号读一项时，不是本会话的、别的租户的与不存在的，答复相同。

传播范围：单次模型或工具，只指定原调用；Run 取消，当前推进资格、该 Run 的模型与前台工具，后台、子会话与无关的 Run 外调用不自动跟随；仅替换 Agent，撤旧推进、接续同一 Run，原 Model 与 Tool 不因旧句柄销毁而停止；会话归档，原业务推进与等待、未承接的任务、全部关联的在途调用以及子会话级联。取消一旦生效就记被取消终态，优雅或强制只影响停止有多急，不改变终态时点；治理方继续跟踪真实收场，没有 Agent 时也继续，未收尾的外部效果保持未知，成功、失败、未知如实保存。

取消与受理、取消与条件终结、取消与换代的竞争按权威的提交顺序裁定，不按时间：取消先成立，之后的接管与重装被拒，输入照常取得下一个 Run 的待处理资格，归档先成立则新输入被拒；受理先于取消，输入保留待处理资格，归档在同批撤销资格并记取消范围；条件终结先于取消且 Agent 执行已结束时，取消回答终态并带回既有终态，若 Session 还没解释结束事实则取消照常提交，之后读到的结束事实只认回；取消已提交而没有活体挂接时，控制仍送到 Agent 的长期控制入口，受理不依赖挂接，新挂接读原取消意图以取消授权收束。任何顺序下只有一个终态，取消之后没有新授予且存活的推进资格。

控制的对账进度只有在原控制的传播、生产者核对与原责任交接都已对账之后才算完成；Run 取消与归档的生产者核对认 Agent 为每个前台调用各自发的停止（撤回或中断这一次调用）：它点名这次调用、到了生产者确认或物理停止，或者这次调用在停止被受理之前已以结果收场，就算这个生产者核对过；转后台不是停止。传播或责任仍未知时保持待对账，按原身份重放，超过策略上限则停在传播中并报告，不假装完成。插队保存共同的加急消息、处置决定、占位与提醒，已到的响应与已发生的效果尽量保留，原 Run 不终结；加急消息作为紧急输入交给原 execution，释放前台等待的控制由 Agent 随这次交付发出，Session 不另发；插队选中的生产者在 Agent 证实释放，或这次调用已收场、已转后台时对账；人工等待按主动插队记为明确拒绝，不伪造用户的答案或授权；重复的同次控制不重复插消息，独立的多次插队各有原提交。插队到达时会话没有未终结的 Run，这条输入按普通输入受理，答复标明它没有插到任何一轮。工具转后台沿工具拥有者的许可与转换契约，控制受理不表示转换完成，转换不建立第二次执行、不释放并发名额，后台结果沿原消费契约交回。

### 归档与作用域释放

归档的确认依赖业务取消、队列资格取消与后续处置责任成立，不等独立执行的物理停止。归档的答复带这次收起的 Run 与后台调用的数目，不声称执行已经停下。同批终结仍未结束的原 Run 为被取消，归档条目只引用这个唯一终态；已成立的完成或失败保持；没有原 Run 时不补造 Run 或终态。新任务与归档竞争只能是先受理后因归档取消，或明确拒绝，不得无痕丢失，也不得归档后仍保持待执行资格。归档后拒绝新任务，迟到的结果与费用保存原归属但不入任务队列；归档不删除历史、会话授权、工作区或实际费用。

会话关系的两端属于同一个租户，按访问身份的租户查找，任一端不存在就答被拒；级联按父会话的日志记下的子会话逐个进行，逐层向下。级联由调度器按策略的间隔推进，不依赖归档那一刻谁在场；随父会话归档的子会话在已归档的目录里记为随父归档。子会话的级联与未完成的处置要可恢复，每个子方一个固定的子操作身份，重放幂等；独立交接的子会话不级联；子方被拒时任务与原因保留，不伪装级联完成；子方提交未知时以同一身份再驱动。

归档的同一次提交产生作用域释放任务，由维护者身份凭装配注入的恢复授权请求执行环境释放；读回事实是已释放作用域的耐久账本，执行环境不保存这份账本。读回按五类处置：已释放（两路枚举完整、全部资源已停、原获取责任已结清）才解除任务；待续、不可用、未获授权保留任务（未获授权要报告维护拥有者，不改用会话用户的身份重试）；不支持的部分记录并交人；枚举失败表示资源未知，不表示没有。释放结果未知时任务状态为未知，以同一操作身份重试。执行环境提供者换代时，释放插件按页重新释放已归档会话的作用域，每个作用域沿原任务身份，重复释放认回。逻辑归档在提交时已成立，不等物理全停；对人的时间线只记「已发起释放」与读回结果。

撤销归档回到休眠（冻结的会话回到冻结），从撤销时刻重新计空闲，不恢复被取消的任务、Run、调用或卡片，不顺带恢复子会话；撤销归档铸造新代次的作用域，新代次不迁移旧作用域的注册：同一次提交里，会话为新代次重新声明创建时记下的那几块注册，材料取自日志里创建时的记录，次序与修订从头起；创建之后在旧代次上做过的增删不带过来。没有「撤销成功而作用域是空的」这个状态；原取消调用迟到的结果仍不自动入队，需要继续就显式提交新任务。旧的迟到重装或原调用不能重新启动已取消的工作。

Runtime Context 持有者的恢复只认会话日志。作用域对应的会话与代次一经铸造不变，查得的答案可以在进程内保存；作用域是否已经结束会变，不保存，每次读绑定。只有绑定显示作用域未结束时，才按空材料恢复一个还没有记录的新作用域。已结束答已结束，不在绑定里或读不到答不可用；空材料不用于会话没有显示为开着的作用域。

### 模式、自动归档与冻结

三轴模式（权限处理、执行环境、协作模式）分别保存并可变化，不扩大结构化权限。本会话租户可以改模式，改的资格在提交边界核对；Agent 不能经直接入口、也不能经未获人授权的工具或委托改模式，要改必须走人工介入，由人显式授权；代办模型切换不授予改模式的资格。创建时的默认只初始化，当前值跨恢复保留，专用入口已有有效必填初值时不能用通用默认补缺。模型可读的模式变化按 Context 协议感知，已固定的请求不回写。值守不是模式，不能改。「此刻能不能向人要答复」是值守与协作模式合起来的结论：有人值守且协作模式是 `co-work` 才能。值守与这个结论都随模式的那一块经 Runtime Context 发布，消费者不自己推。无人值守的会话里，权限处理要人决定的动作按「拒绝」处置，不放行也不等待。

自动归档默认关闭，只在显式启用、未豁免、符合连续空闲条件与时限时执行；没有有效的显式启用依据就不得自动归档。启用开关与时限取自本租户的合法设置，没有时限时不以旧默认补值。常驻标记只允许主会话，由具会话管理资格的用户维护自己的会话，子会话设常驻必须拒绝，不静默清除标记或改变关系，也不能用非法组合阻止父方的归档级联。空闲判断覆盖本会话与级联相关子会话的未终结 Run、待处理任务、在途的 Model 与 Tool：任何等待、后台工具或 Run 外调用使条件不成立，查看历史不算开展工作；新工作与到期检查竞争时重新核对。时钟采样失败不用系统时间补默认，墙钟差本身不证明连续空闲；来源无法证明离线区间、时钟回拨或有未决工作时观察为未知，普通重启不重置已确认的起点，成员失效不暂停或清零计时。开启自动归档或解除常驻使用原来已确认的连续空闲，操作前提示可能立即归档，不重置起点，仍要重新核对全部条件。

常驻工具是 Agent 不经发现即可调用的工具。会话在采用点（初始化、新 Run 开始、显式重装）纳入常驻工具，每项在同一次提交里写一次，常驻集合只增不减；会话当前记下的登记键取自最近一条带键对的采用记录。新 Run 开始与显式重装这两个采用点，推进都问采用来源这一次怎样采用。采用来源把会话记下的常驻（常驻工具的项、登记键与形状，常驻段，来源条目）交给判定，定义没变也交，答三种之一：用这一套（候选与常驻的结论，结论里可以有冻结的判定）；照原来那套（新候选不合法或算不出、原来那套仍适用，带原因）；没有可用的采用（带原因）。用这一套而与会话站着的一样时不写采用；不一样时，开始这一轮（或重装）的同一次提交里记一条采用，带上判出的常驻变化。照原来那套时，这一轮照原来的开始，会话里记一条对人可见、不进模型视图的说明，写新版没用上的原因。没有可用的采用时不开始，输入留着，记一条说明写在等什么；来源的事实变了再试，人不用重发。采用来源此刻答不出时不开始，照推进的退避重试，用尽后记一条说明。没有提供者时沿用站着的那一版。冻结的判定只在新 Run 或显式重装的采用点由 Tool 的公开纯函数给出，作为待采用材料的一部分原样到达，写明是哪一项常驻工具、为什么；工具暂时缺席、状态未知或被撤权时按 Tool 契约用同形不可用件，不给冻结判定。开始 Run 或重装返回冻结且不提交之后，推进触发以同一判定提交冻结。冻结不可逆，每个会话至多一次；冻结的会话不开始新 Run、不采用新版本，进行中的 Run 不被取消，按原规则收场，接管照常；冻结的会话里每个已受理的输入都有去处：没有未终结 Run 时拒绝新输入，冻结与冻结后 Run 终态的提交同批解除余下的待处理资格；冻结独立于归档，冻结的会话可以手动归档、参加自动归档裁定，撤销归档后仍是冻结。引用查询只算未归档的会话（冻结而未归档的算引用），不返回定义正文，读不到时答不可用，不返回空页冒充没有引用。引用查询的索引每行只记形状的摘要；同一个租户里同一个形状只存一份，键是租户与形状的规范摘要。写一行时缺这份形状才写；删掉或改写一行的那次提交里，不再有行引用的形状一并删掉。一行的形状取不回时，引用查询答不可用，不当作没有这个能力。常驻段是系统提示词里的一段，例如常驻 Skill 的简介。会话在采用点记下它的名字、文字与来源，和常驻工具在同一次提交里写；同一段只在采用点出新修订，新修订的文字必须以上一版为开头，不然拒绝。常驻工具里来源条目的那几项（例如 MCP 接入点），记录带着采用时的整条定义，没有登记键；登记键只覆盖登记表里的常驻工具。会话不认识常驻能力的类别，只认段的文字与工具的定义。

### 模型选择

会话保存当前选中的模型路由名、可选的推理强度、初始采用依据与切换事实；模型档案、合法集合、凭据与实际请求归 Model。当前选择与每次实际调用分别可查，上一次调用的记录不因切换改写，不用最近的实际调用反推会话选择。用户切换要有对应的会话操作资格与当前合法的目标，Agent 只代表明确的合法用户指令代办，不能自主换名；缺凭据的合法目标仍可选并说明暂时无法调用，非法目标明确拒绝且原选择不变。选择变更条目、当前值与原操作回执共同提交；确认之后的后续请求采用新选择，下一次请求失败不撤销切换；切换本身不产生新 Run 或 attempt，不替换定义，不重发或打断在途调用。还没固定的请求按当前选择重新求有效模型；已固定或已发的请求保持原模型、参数与内容；单独中断要走明确的控制。经压缩仍无法满足输入条件时按原工作规则失败，选择与历史保留，不暗换其他模型。选模型对客户端开放为会话协议的一个操作。调用方给目标路由名、可选的推理强度与一个控制标识。同一次提交采用路由与强度，只调强度时也提交完整选择。强度取 `low`、`medium`、`high`、`xhigh`，省略时采用模型档案默认参数。前一发行会话日志中已按指纹验证的 `session-log` 条目可原样重放，保留原操作依据，原先没有强度的选择按相同缺省处理。接入层按 Model 给出的目标型号能力核对显式档位，不支持时答 `unsupported-effort` 并保留原选择。目标解析不到档案或档案不可选时拒绝并带原因，不提交；缺凭据的合法目标照常提交。会话操作标识由控制标识确定地推出：结果未知时用同一个控制标识再提交，不会选两次。切换不打断在途的调用，下一次请求用新的选择。目标合不合法由接入层先经 Model 的档案判断，证据桥不为选模型向采用源要材料，与权限配值相同。建会话可以带一个模型：先经同一个档案判断，不可选或解析不到答非法、不建，判不出答依据不可用，可选就以它作初始选择；没带时用部署映射给的。读模型选择只读，答会话当前选中的路由名、显式选择的推理强度（如有）与读到的修订；模型的列表不在会话协议里，归 Model 的协议。目标合不合法在文字之外还看这段历史：历史里有目标型号读不了、又没有别的表示与文字兜底的块时，以模态不符拒绝，答复点名这些块（消息与块的标识，至多十六个）；历史读不到时答依据不可用，不当成空历史放行。

### 权限配值与待办

会话逐权限配值是独立于模式、Agent 作者上界与人的持续许可的当前声明，保存在会话日志里，当前集合由归约得出，稳定键在会话内唯一，每次设值、替换、清除或权限模式变更推进权限修订，别的工作不推进。写入需要专属的写资格，普通变更的访问允许或非空的授权引用不能替代；受保护的写绑定原操作与完整命令，不能把已结束的权限读取当作后续写入的租约。设值必须匹配精确的定义与稳定键并落在值域内，定义已撤下时清除仍可做。权限修订是当前性的依据，不是可长期使用的许可：读取之后发生修改时，使用这次读取的提交必须在同一事务里核对当前修订；定义变化时不忽略旧配值，也不返回空，不能可靠匹配就答不可用。从完整原批次重建权限状态只复用原归约，不重新授权，不改写历史；缺少权限字段的旧快照只能经重建取得，不在普通读取里补空。

会话授权上下文是人在这个会话里表达的授权的流水，保存在会话日志里，只追加：给出是一笔，撤回也是一笔。一笔授权表达有作用域（这一次，绑定一个动作的操作、目标与参数摘要；本会话，绑定一个关口与给出时的权限依据）、方向与来源。Session 只保存与归约，不解释它算不算数：「此刻这个动作准不准」由授权按它实时算，不存结论。归约出的当前状态按动作交出单次授权、按关口交出本会话授权，各带修订；单次授权的当前行在所属的这一轮终结时退出当前状态，日志保留；至多用一次由消费方的记录保证：消费方是 Agent 的官方准入，用掉的那一笔与放行的结论在准入的同一次提交里写进会话日志。追加要专属的写资格并绑定原操作，同一来源重来认回原条目。归档不删除它；新会话与子会话不继承它。别的领域的提交可以断言权限处理模式的来源未变；断言只看这一项，授权表达追加进来不让它失败。

待办是会话日志上的三类事实（添加、完成、移除），跨 Run 与 Agent 保留，归档、压缩与认回不清除它；它不进未结工作与恢复任务，不启动或唤醒 Agent。添加保存非空白且有字节上限的原文本，不裁剪；移除留下墓碑，之后的完成与移除答找不到且不泄露文本；不提供修改、重开或批量替换。标识由租户、会话与原调用文本确定性地派生，另一个原调用即使同文也是另一条。写入按归档、冻结、初始化中的次序分别拒绝，休眠与活动都可写，不依赖 Run 状态。列表每页重新核权，过滤已移除的并保留添加顺序，游标只含租户、会话、修订与位置四个字段；读不到、缺依赖与会话不存在都不转成空列表。

### 读取与投影

每次读取、分页、导出与按原条目的查询都检查当前资格。游标绑定租户、会话、来源身份、过滤条件、固定的读取上界与续读位置，调用方不能改游标扩大范围；错域、失效或无法核验的游标明确拒绝；读取期间新追加的只在新一轮遍历里出现。分页按确定的提交位置续读并保存扫描进度，不用最后一个可见条目代替扫描位置，也不把权限过滤造成的空页误判成历史结束；权限撤回后不继续泄漏旧页。历史的读取带固定的会话修订号上界：同一轮的每一页上界相同，历史条目与状态帧用同一条修订轴，读者可据此判断手里的历史新不新。游标的签名只认当前的键，轮换后旧签名无效，键来源不可读或已卸载时答不可用，换代前在途的校验在完成时复核当前键。游标签名覆盖固定的协议域前缀，再加载荷：别的协议的签名、只签载荷的同钥签名，都不能验作会话游标。引用查询的游标还绑定租户目录的修订与常驻键，换了修订或换了键的游标无效，所以逐页续读时先注册的租户不会被跳过。

每份投影声明来源、确定性的计算规则、覆盖到的完整提交位置、计算版本与失效条件；应用同一提交一次或重复一次得到同一结果；缺批、来源不符、未知且不能证明无关的事件类型、计算版本不兼容时停止相应投影并报告缺项，不把未解释的事实当作无待办、无 Run 或完成消费。治理决策必须用与权威尾部一致的治理状态；展示投影可以落后并公开进度，但不能用落后数据授予推进、拒绝必要控制或报告确定的空队列。恢复先验证检查点的来源、输入范围与计算版本再重算尾段，无有效检查点时从日志起点重建；重建只解释事实，不重新调用模型、执行工具、回答卡片或发外部效果。检查点与索引损坏可从权威事实重建；权威日志出现缺口、损坏或未知的提交状态时隔离受影响的会话并保留处置责任，不清空会话、不静默丢弃已提交的尾部；临时、未提交材料的清理不能误删已提交而回执未到的批次。

当前状态、待处理输入与原等待位置有直接可定位的索引，正常推进不全量扫描历史；派生物在变化时维护，请求到达时只读取与采用，热路径上不出现随历史长度增长的读取。分页、检查点恢复、内容读取与导出按实际条目与字节控制资源，不承诺无限容量或固定延迟。一页装得下多少由读的一方按字节决定，一页至少一行，装不下的由调用方在同一个版本上接着读；写入不因单个条目或单个执行记录项的大小被拒，大小的真实边界只有存储提供者对整条命令的限制。时间线的投影合并已提交的历史与在途的增量：日志条目到达后替换同一调用键的在途内容，故障后只可能缺从未展示过的在途片段，恢复后的展示说明缺口，不补造。「未结工作」只有一个计算，供历史持有者交给 Request Context 的下界、条件终结的阻塞依据与空闲裁定共用，三处不会对「还有未结工作」给出不同答案。工作快照只留开着的调用。一次调用开着，当且仅当：它转了后台还没结算；一条没对账完的控制引用它；它还没有结果；或会话有活着的 Run 而它的结果还没有一条处理过。还没关联上生产者的意图只在有活着的 Run 时开着。被等待的调用总在其中，不另列一条。其余的调用在那一批提交时离开快照，原样留一行，之后不改。此后针对它的事实（重复的登记、迟到的结果与账目、保管、处理、释放）照常写日志，各自记成它名下的一格，每格只写一次，不把它放回快照。按键问到离开的调用时，读回那一行并叠上这些格，答案与它一直留在快照里时相同；按生产者问绑定用 `readCall`，资格同读工作快照。归约没有拿到读回的办法时没有调用离开。停一个已经离开的调用答没有这次在途调用：它没有等待者，物理上停没停归生产方报告。空闲裁定看快照里有没有调用，不看结果有没有释放。会话当前状态的内存缓存只是读缓存，存储仍是权威：每次读先读会话的版本（会话日志的尾部与 Agent 的发布计数），只有版本等于缓存条目读取时的版本才用它，否则整份重读。本进程的提交把批次折进已持有的快照，折入的结果带的是存储答过的版本，之后的读仍先核版本。缓存不做访问裁定，调用方各自先裁定。会话的两个目录读口每一行都带这个会话的关系（种类、父或来源、根、层数）、值守与定义标识，并可以按它们过滤：按种类、按父、按根、按值守、按定义、按生命周期、按标题。读的一方点名一个本租户的会话作参照时，每一行另带它与参照会话的关系，取值是：本身、它的父、它的子、同父、同一棵树里的上层、同一棵树里的下层、同一棵树的其余、由它交接出的、交接出它的、无关；也可以按这个取值过滤。这些都从目录行自己的列与参照会话的那一行算出，过滤落在索引上，不逐行回日志，不递归；层数有上限，所以「下层」至多是两次按父或按根的索引读。过滤条件进游标。目录是投影，丢了从日志的创建条目重建。工作快照带的历史索引只答三样：尝试记录、待处理输入的受理出处、在跑的执行对待处理输入的准入；它不沿输入去读别的执行的准入。这份索引分页读、读到哪记到哪，会话有过多少轮、失败过多少轮都读得完；一次读不完时读工作答不可用，不把没有索引的快照留在缓存里，下一次从上次的位置接着读。

读待处理答这个会话已受理而没有被承接的输入：来源的名字与给人看的名字、作者角色、叫不叫醒、时刻与开头的一段，按受理的先后分页。读等待中的调用答哪几次调用停着在等人答复，各等的是哪张卡。读一份输入的去向答这条输入现在在哪一格，恰好一格：待处理（失败归还的带上它上一次所属的那一轮）；已被一轮取走而括号开着；已回答，带那一轮与那一轮的终态；随取消或归档了结；被 Agent 的消息准入拒收，带原因。没有这条输入与无权的答复相同。三个读口都只从日志归约出的状态读，不问 Agent，不改变被读的会话。会话目录有两个读口：没归档的会话，与已归档的会话。任一时刻一个会话恰在其中之一。归档与撤销归档的提交在同一批里更新目录，并记下归档的时刻与方式（人、自动、随父会话）。已归档的读口按归档时刻从新到旧分页，可以按归档时刻的范围、归档方式与标题里的字筛选；读不全时答不全，不答空。

账目真实归因到原调用；有发起的 attempt 或 Run 时记录相应关联与汇总，Run 外按对应的会话消费者；未知的费用继续待结，不当零，观察者与接续不重复收费。日志与遥测能定位原身份与因果，诊断内容按权限、隐私与外传规则筛选，遥测不替代业务持久事实。必要保存不可用时，阻止依赖该保证的新动作并说明影响；局部服务故障按责任限定，兜底优先无副作用，不授权绕过租户边界。

### 会话观察

会话观察回答：登录的人看一个会话，现在正在发生什么。它给出一条帧序列，告诉界面这一轮开始了没有、日志里有没有新的已提交内容、正在生成的那段回复是什么；已提交的内容由读历史给，历史是权威，观察只是进行中的投影。观察只读会话与模型两个领域，不写任何东西，不做授权判断；读日志与问模型都用观察者自己的主体。

建立时先以观察者的主体读一次日志核对资格，会话不存在、标识不合法与被拒的答复逐字段相同，调用方分不出；日志暂时不可得答不可用。帧序列的第一帧是状态帧：日志读到了就先发状态帧，主调用的流选不上（模型拒绝、引用不合法）也是先发状态帧再按原因结束，只有打开时日志读不到或被拒才一帧不发；状态帧有五个字段（当前这一轮的编号或空、日志的修订号、模型调用的阶段、这次调用的发出进度或空、有没有流目标），只有字段有变化才发新的，第一帧一定发。发出进度原样转述模型的调用状态：允许的发出次数、已发出的次数、上一次的成因、下一次不早于何时；观察不另数。对外的协议帧里没有进度时不带这个字段，上一次的成因只带成因名与上游状态码。快照与增量帧的值取自模型公共流的投影；增量的基线对不上就不应用，等下一个快照。被观察者自己中止时结束且不给原因；这是观察者自己的事，不报成日志不可得。

「看哪一次调用」只由日志决定：最近一条 Run 开始之后没有同编号终态，这一轮就在进行；主调用是最近一次登记的主用途、模型类、带引用的调用。这一轮在不在进行，和它绑定过多少次调用、主调用找没找到、流选不选得上都无关：从末尾倒着读时，找主调用有页数预算，预算用完没找到，答的是「这一刻没有流可看」，状态帧照样带这一轮的编号；预算内没读到 Run 的边界时，另读一遍只含 Run 开始与 Run 终态的条目，读到最近一条开始为止，这一遍不设页数（一轮至多一条开始、一条终态，同一时刻至多一轮在进行，所以最近一条开始之前至多一条终态）。没读完不当成没有在跑。「那次调用的流现在怎样」只由模型决定。两条轴独立：定位读日志，流轴订阅模型的公共流。有目标且主调用没换时不问模型；换了目标就收掉旧订阅，之后到的旧帧丢掉并记诊断。目标的流结束、订阅中断、模型撤了观察者的资格、值投影失败，各有确定的去向（回到没有目标并开始刷新，或重新观察，或以被拒、不可用结束），不把读不了的值当成没有内容。

刷新是策略：第一档间隔、每次没有新内容时的退避倍数与上限、连续没有新内容的次数上界、累计等待时长上界，都是装配传入的配置，间隔有底线；用尽时以刷新耗尽结束。间隔到期引起的定位在字段有变化时先发状态帧，再发刷新帧并计一次尝试；叫醒引起的定位不发刷新帧、不计尝试；观察中的时间不计。叫醒只是叫醒，不是事实来源：叫醒的种类集合是定位读的种类、会话站位的种类（选模型、改模式、换工作区、归档、撤销归档，界面显示它们，读历史读不到它们）与读历史的种类，后者与读历史来自同一个来源；没有交集的不理会。站位的提交叫醒之后，状态帧带上新的修订号，界面凭它重读显示的站位；漏掉、重复、合并都不改变结果，漏掉的由按间隔的刷新补上；标记「有新提交待看」不丢。读日志暂时不可得当作没有新内容，自己的游标不合法就丢掉并从头反向读，别的不合法与被拒按确定的原因结束。有目标在等待再次观察时，提交叫醒只被处理，不重启正在跑的等待，所以不断到来的提交推不迟下一次订阅；没有目标时，叫醒本身就是一次定位，定位之后重新开始等待。

### 协议、接入与界面

会话协议 `session/v1` 是纯数据（发输入与插队另有两个可选项：发送方所见，与「等这一轮结束再发」）：二十七个操作（建会话、查建会话、发输入、插队、查发输入、读历史、读等人、读待处理、读等待中的调用、读一份输入的去向、搜历史、列会话、列已归档的会话、取消一轮、停一个调用、转后台一个调用、列后台调用、重试、归档、撤销归档、选模型、选工作区、读模型选择、读工作区选择、读权限处理模式、改权限处理模式、重装）与一个观察，每个操作声明身份要求、效果与体上限，提交类并入未知，所有操作都计一次业务访问；信封（版本、消息编号、操作名、登录证明、行事租户）归共同契约。查询类操作本身可能答不出那次提交的结局，所以结果里有未知。读历史的成功体带这一轮读取固定的会话修订号。列会话只读，按固定次序分页，答每页的完整性（读到行数上界时为部分）；资格被拒与会话不存在看不出区别。重试点名失败的那一轮，同一控制标识再发一次答已恢复。插队与发输入进同一条请求队列，用同一个查询认回。列后台调用答每一项的短号、标签、来源、状态与停止。停一个调用可以带原因。归档与撤销归档按控制标识认回。列会话只列没归档的。停一个调用与转后台一个调用的路由在服务端，客户端不分前台后台；回执分开给出受理、停止已证实与未知。列后台调用只读，从快照列出本会话转了后台而没有结算的调用与它们的引用；读一次调用的状态、结果与过程归 Tool 的协议。读待处理、读等待中的调用、读一份输入的去向与搜历史都只读，结果集同读历史；搜历史另有受限（同一个租户同时在跑的搜索到了上界）。搜历史的成功体带这一页的命中、续读的游标、答得全不全，答不全时带原因、还没索引到的会话数与重建的进度。读等人只读，结果集同读历史；成功体是 `waiting`：会话没有在等人时为空，否则是等的那一轮、待处理的条数（共同契约的计数，线上是 JSON 的非负整数）与成因，成因为空或是成因的种类名加一句可以给人看的诊断（可以为空），再加 Model 说的失败 `fault`（类别、上游状态、是不是限流；这一轮不是败在一次失败的模型调用上时为空；修订 5 加的可选栏）。节点失败的诊断是失败的产生者交出的那一句，没交就为空。观察的帧只有五种（状态、快照、增量、缺口、刷新），观察自己的结束原因只有刷新耗尽。把一条文字输入做成发输入的用户消息（`userTextMessage`，与它的消息编号 `userMessageId`）也在会话协议里：消息与文本块的标识由输入标识派生（`msg_`、`blk_` 加输入标识 UTF-8 字节的 SHA-256，base64url 不带填充），派生是会话的约定，所有客户端与测试支撑共用这一份，不放进不认识任何领域的共同契约；它用平台的 WebCrypto，所以是异步的。读工作区选择答这个会话站在哪个工作区实例（没有选为空），以及此刻开始一步时的工作目录与状态：默认、附着，或用不了与原因；目录与状态按步前动作的同一算法现算，读不到答依据不可用，带这一读取的会话修订号。读权限处理模式答这个会话当前生效的模式与权限修订，按授权判断读的同一算法现算（含租户缺省），读不到答依据不可用。改权限处理模式只改三轴里的这一轴，取值是 `never`、`auto_permission`、`bypass-permissions`；它是提交类操作，带期望的权限修订，修订在提交的同一事务里核对；答已改、没有变化（同值，不提交）、修订冲突、被拒、依据不可用或未知，已改与没有变化都带当前的模式与修订。同一登录对同一会话、同一期望修订、同一目标值的再发，派生同一个操作标识，按原操作认回。它是人的声明，不采用部署的材料；资格是本会话租户本人的登录，在提交边界核对；Agent 的主体不能经这个操作改模式。改了之后，之后的每一次判断读到新值，已经发出的请求不回写。重装（`reload-session`）是提交类操作，身份是登录，字段是租户、会话与控制标识；同一个控制标识再发认回原来的结果。答复是已交接（这一轮换了一次接手，用上新版）、已采用（空闲时记下了，下一轮用）、已经是最新的，或被拒并带原因（已归档、已冻结带判定、候选不合法及原因、没有资格；取消已成立、Agent 说它不是当前的推进者、会话在读与提交之间变了，这三种是冲突带的原因），依据不可用与未知照提交类的规矩。会话冻结时，读历史里有一条冻结的条目（`session.frozen`），写明是哪一项常驻工具、为什么，会话页照它显示；状态帧只标已冻结，`reload-session` 答已冻结时带上那一项。重装判出冻结时，冻结提交成立才答已冻结；没成立答那次提交的失败，会话不算冻结。会话带来五条系统命令，由 `session-adapters` 的 `createSessionCommandSource` 交出、应用的装配登记到命令领域的入口来源上并标为官方：`model <模型名>` 做 `select-model`，[参数候选](../../.meta_harness/design/ubiquitous_language/terms/capabilities-and-composition.md#ul-argument-candidate--参数候选--argument-candidate)是这个会话此刻能选的模型，在用的那个带标记；`permission <模式>` 做 `change-permission-mode`，参数候选是三个模式各带一句说明；`archive` 做 `archive-session`；`reload` 做 `reload-session`；`effort <档位>` 对在用的模型做 `select-model`，模型不变、只换推理档位，参数候选是在用的型号提供的那几档，在生效的那一档带标记（会话没选过时是这个型号的缺省档）；型号一档都不提供时，候选是全部四档，每档都标为不能选并写明这个型号不能调推理档位，所以发送前就拦下；不带参数、或不在型号提供的档里，答参数不对。它们在一轮在跑时：`reload` 在下一个安全点做，其余立刻做。取用把参数解析成那个操作的字段，答操作请求，或答参数不对；不在这里做那个操作。会话的核心成员与接入成员里不出现这五条命令的名字。

接入插件把协议挂上登记表，业务规则与结果映射沿会话的原有规矩：只有创建会话用管道给的行事主体，其余操作与观察在消息体里带目标租户，处理函数把登录与目标租户交给身份换主体，被拒或依据不可用就原样作答、不调会话，换主体抛出按依据不可用；会话标识、输入标识、操作身份与登录入口来源的派生文本与入口逐字节相同；创建会话没给定义名时用配置的默认，没配置或不在部署映射里答非法，映射里缺初始模型选择答依据不可用，三者都不调会话；会话失败按固定表映射，提交类调用开始之后抛出答未知，只读类抛出答依据不可用，映射出的结果不在该操作的结果集里时答依据不可用；会话服务、观察、部署映射、会话目录每次调用现取，取不到时需要它的调用答依据不可用、协议不撤下（发消息例外，请求在队列里等）。列会话经接入包自己声明的只读端口，不碰会话的四个面。读等人先经会话的读口得到等人、条数与那一轮的 execution，再经接入包声明的成因端口按会话与 Run 问这一轮的失败成因；成因端口没装、读不到、答没有或抛出时成因答空，读等人照样答，等人与条数读不到才按依据不可用作答。成因端口以请求者的主体倒读会话日志里的终结条目，找到这一轮的那一条，从它的 `end.failure` 取：种类取 `kind`，诊断只取 `no-reply` 的 `diagnostic`（模型规格写明它是安全的短文本），空串当作没有，别的字段一律不放；适配归服务端应用里会话接入的那一行。插件卸载时停排空、再关日志，不再取队头，退避计时全部取消，在途的那一次受理不取消，队列里的请求留在日志里等下次装上。

会话诊断协议 `session-diagnostics/v1` 回答：登录的人读一个会话在某一刻的诊断页。它只有一个操作 `read-session-diagnostics`：登录身份、只读、体上限小、计一次业务访问；没有观察。请求体是首页（租户、会话、游标为空、可选的 Run 过滤、页字节数）或续页（租户、会话、游标）两种形状，两种互斥，空游标不带过滤与页字节，非空游标不带它们。成功体是一页：若干 Run 的诊断（框架、尝试计数、控制、终态与原因、调用登记、Model 调用与逐次派发、Tool 调用、消息计数、事实计数）、续页游标、是否读尽、扫描到的位置、固定的读取上界与缺口表。结果集只有成功、非法、被拒与依据不可用。字段规则写在协议成员里，信封与登录证明归共同契约。诊断页是投影，不是事实源：历史条目来自 Session 的读历史，Run 的收尾来自这一轮终结条目的 `end`，调用与逐次派发来自 Model，Tool 调用来自 Tool；Tool 调用的状态经 Tool 只读的 `current` 读，不经会写排除记录的 `lookup`；会话日志里已登记、带引用的调用，Tool 答不认得这个引用时，记为 Tool 不再保存，不记成没受理过；诊断页逐项带来源，来源缺席、不支持、被拒或读失败都变成带原因的缺口，不改整页结果，也不被写成空。披露的条目种类、一页的 Run 数上限与一个 Run 的调用数上限是插件的设置，三项必须一起给，缺任一项答依据不可用且不调会话；一页字节数的上界同样来自设置，首页超过上界答非法且不调会话。游标由进程内的随机密钥签名，绑定租户与会话，第一页的读取上界在续页里不变，错域、被篡改或别的进程签的游标答非法，续页时再判一次资格。Model 调用的逐次派发带这次发出的各个时刻、三段时长、发出到响应头的时长与连接重试的次数和原因，都原样取自 Model 的诊断；逐次派发另带这次发出的档案（名字就是模型）与推理强度及来源，取自 Model 的发出事实，读不到就是未知；Model 调用另带发出进度（允许几次、已发几次、上一次失败的成因）。这些栏缺了就是未知，诊断页不自己算。每次 Model 调用还带这次固定请求里每一块带内容引用的块模型读的是哪一份：取这次调用采用时按调用引用记下的 Request Context 覆盖证据的选择，派生与转写照搬，选了原件的媒体块从会话历史里那条消息的那一块取引用，再看最后一次完成的派发（没有就看最后一次派发）的物化回执，实际编码的媒体类型或字节数与引用不同为缩小的版本，相同或回执里没有这一份为原件，历史里那一块没有引用就不列；选择读不到时这一栏为空并记 Agent 来源的缺口，历史里找不到那一块或读不到时为空并记 Session 来源的缺口，派发读不到而又有要比对的原件时也为空。`session-diagnostics-access` 把协议挂上登记表。四个读口（会话历史、Model 的调用与尝试、Tool 的调用、一次模型调用的已采用请求里的表示选择）由本成员声明成需求端口，类型取自各邻域的契约，应用一行来适配；代某个租户读用的主体经 `DiagnosticsPrincipals` 端口换出：被拒或依据不可用就原样作答，抛出按依据不可用，之后不调会话。会话取不到答依据不可用而协议不撤下；已采用请求（Agent 来源）、Model、Tool 的读口缺席是该来源的不支持缺口。表示选择按调用引用读执行记录里按会话寿命留的那一行，执行结清之后照样读得到；没有这一行（采用时选择解不出）答未记录的缺口。会话失败只映射成被拒与非法，其余答依据不可用。整页投影完成之后、答复之前再换一次主体：这一次被拒或依据不可用，整页不给。这一次复核到的是端口能判的事（目标租户的账号等于登录的账号），登录在途被吊销时端口照样发主体，所以整页不给只在端口自己拒绝时成立；登录的存活由管道在每次调用开头判。投影的代码和读口的失败到缺口原因的映射原样沿用，只读，不向 Session、Model、Tool 写任何东西。

请求队列的文件日志：记录两种，一行一条 JSON，入队与离开；写进文件的只有点名的字段；打开时重放成还在队列里的请求，丢掉不完整的最后一行，并以写临时文件、落盘、改名的方式重写；追加落盘之后才算成，同时到的合成一次落盘且先后不变；追加失败要把文件截回追加之前的长度，截不回时不再接受追加；队列数到零且没有等着落盘的记录就截空，截空前后任何时刻进程没了，重开得到的都是空队列。

界面模块是客户端树上的一个插件：`session-ui` 的 `./cordis` 入口导出 `sessionUiModule`，它用外壳契约的 `defineUiModule` 造出来，依赖外壳的服务 `shell` 与会话协议的客户端（服务名照客户端装配的取法，是 `protocol:session/v1`）。两样都在时，它往侧栏区放会话列表（标识 `session-list`，次序 0）与已归档的会话（标识 `archived-sessions`，次序 1），往页面放对话页（标识 `conversation`，标题「对话」，次序 0，图标名 `conversation`）与搜历史的页（标识 `history-search`，标题「搜索」，次序 1，图标名 `search`，在 utility 段）；协议客户端撤了，它们随作用域撤掉。在列表里选一个会话或新建会话时，它调 `shell.navigate` 把对话页切到前面。别的界面模块带着对象跳到对话页时，对象是一个会话，加可选的一轮：对话页打开那个会话；带了一轮就停在那一轮开始的地方，那一轮读不到时停在末尾，不报错。对象的写法由 `./cordis` 入口的一个函数给出，装配把它交给要跳过来的模块。这些视图共用一个按租户建的模型：同一个租户只有一个，都不用时收掉，租户变了换一个新的。外壳给的租户还没有时不发调用，读不懂时对话页如实说出来。根入口只导出模型与两个视图，不带 Cordis 绑定。`./cordis` 入口除模块与客户端服务名外，还导出位置与页面的标识常量 `CONVERSATION_PAGE`、`SESSION_LIST` 和 `SESSION_DOCK`。

第三个拓展点是 `sessionCallDetail`（名字 `session.call-detail`，常量 `SESSION_CALL_DETAIL`），在一项后台调用的下面。宿主给它当前租户与 `{ session, call }`：会话的标识与这次调用的引用。别的八问答案与 `sessionDock` 相同。它让拥有调用输出的领域在这里显示输出，会话的界面模块不认识调用的协议。第四个拓展点是 `sessionStatus`（名字 `session.status`，常量 `SESSION_STATUS`），在输入框字段下面那一行、动作钮的左边。它放一列，按 `order` 升序排成一行；宿主给它当前租户与 `{ session }`；别的八问答案与 `session.dock` 相同。它让别的领域在输入框旁边放一条短的读数，会话自己不往里放东西，也不认识放进来的是什么。第五个拓展点是 `sessionRunFailure`（名字 `session.run-failure`，常量 `SESSION_RUN_FAILURE`），在失败的那一轮的通知里、原因与剩下的消息之后。宿主给它当前租户与 `{ session, cause, detail, fault }`：会话的标识，与 Session 读出的失败原因（种类、细节与 Model 说的失败，后两样可能是空）；只在这一轮有原因时出现。放进来的项按 `fault` 的类别认是哪一种失败，不按细节的字面认。别的八问答案与 `sessionDock` 相同。它让知道这个原因怎样补救的领域写一句怎样补救、给去补救的入口，会话的界面模块不认识原因背后的领域（模型的界面模块认出缺密钥，见 [Model 包组规格](../model/SPEC.md)）。

会话的界面模块自己往 `sessionSide` 放一项（标识 `background-calls`，标签「后台」），列出本会话的后台调用。每个调用是一行过程行：等宽的短号、意图与状态词；展开后依次是动作、命令与预览（`CodeSurface`）、停止的进度、最后一行输出，最下面是 `sessionCallDetail`。停止的进度是一张三行的事实表：已请求、已受理、已证实停下，到了哪一步哪一行有字，谁停的写在表里，不合并成一个词，也不画成进度条。「停止」是行尾唯一的动作，一个图标钮（停止的字形，名字在提示里），按下后这个钮自己显示等待，结果写在这一行下面：被拒写原因，结果不知道照实写，都是中性。有未结算的后台调用时，它往 `sessionDock` 放一行回执重量的说明字「后台有 n 项在跑」，按它展开侧边区并选中「后台」；没有时不放。两处读的都是列后台调用这一个操作；会话状态帧的修订变了、自己发过停止之后，重读。转写区里一次还在运行的工具调用旁边有转后台。对话页的头部放对话头的[座位](../../.meta_harness/design/ubiquitous_language/terms/interaction-and-dispatch.md#ul-agent-figure--agent-形--agent-figure)：用共用界面件的座位件，名字 `header`，优先级 2，在头部的正中，Agent 的名字在它右边。座位与名字合起来是一个展开控件。对话页显示着且有会话时形坐在这里，离开对话页时形回家；没有会话（还没选会话、外壳还没给租户或读不懂）时头部不画，座位不在，形留在家；座位自己不画东西。会话的界面模块经外壳的形口报这个会话此刻在做什么：持续的活动取 `thinking`、`looking`、`writing`、`background` 或 `idle`，一次性的事实取 `received`、`landed`、`could-not`，序号随事实递增；它不报待答数。<!-- OD-14 -->侧边区（`sessionSide` 的页签）缺省收着，静止的对话是居中的一列（照来源：工作面板按需打开）；人按对话头的展开控件打开它，打开后随对话区的宽度换样子：对话区不小于 1160 时停靠在对话页右边，是版面的一部分；窄于 1160 时收在对话头的展开控件后面，按它展开成淡墨的墨框，盖在页面上，不推消息与输入框。墨框开在头部那条细线下面一格（8，与来源的 `BELOW_RULE` 相同），尾巴越过细线到形的口；在墨框、它打开的东西（菜单、下拉，渲染到页面别处的也算）与展开控件之外按下，或按 Escape，收起，Escape 把焦点还给展开控件。墨框里的标题与数照来源的面板标题。宽窄之间切换时，选中的页签不变。<!-- OD-14 -->

这些拓展点都只在会话处于打开状态时有，没有会话、正在建会话和会话不可用时都不出现；换会话时，项收到的对象跟着变成新会话的标识。对象编成文本时就是会话的标识，所以直接往同名的附着位置里放的项收到的仍是这段标识。会话的界面模块不认识放进来的是什么，也不导入任何别的领域的成员。另有两个拓展点给带来非文字内容的领域用，会话的界面模块不认识媒体的协议。`sessionComposerAttachments`（名字 `session.composer-attachments`）在输入框里：宿主给它当前租户与 `{ session }`，以及一个交回内容块的口；放进来的项负责选取、上传与显示进度，把备好的带内容引用的块交回，还没备好时告诉宿主「不能发送」。交回的口是会话的界面模块在客户端树上提供的服务（键 `session.composer-intake`，从 `./cordis` 入口导出），由应用的装配交给贡献方；宿主给项的对象另带这份草稿的标识，每个来源按它交回自己的全部附件与「备没备好」，消息发出或输入框收走时草稿换新，对着旧草稿的交回丢弃。发送时这些块跟在文字块后面进同一条用户消息；只有附件、没有文字也可以发送。`sessionBlockRender`（名字 `session.block-render`，常量 `SESSION_BLOCK_RENDER`）管消息里一块非文字内容怎样画。它是按键选画法的点（规则见[共用界面的规格](../frontend/SPEC.md#按键选画法的点)），键是块的种类：宿主给画法当前租户与 `{ session, message, block, content }`，知道读法时另带 `read`；这个种类没有画法、或画法抛出时，宿主画占位的文字（种类与行内的文字兜底）。会话的界面模块另有一个同样写法的点 `sessionToolCall`（名字 `session.tool-call`，常量 `SESSION_TOOL_CALL`），键是工具的名字，取自服务端 `tool.tools` 上公开的键（`sessionToolCall.keys(连接说的)`，读不到时答读不到）：宿主给画法当前租户与这一次调用 `{ session, call, name, arguments, state, result }`，`call` 是调用的引用，`arguments` 在参数生成完并解得出之后才有，`state` 是 `working`、`completed`、`no-result` 之一，`result` 是结果里的文字；这个工具没有画法、画法抛出、或名字还没生成出来时，宿主画自己的那一行过程行。画法可以包着宿主通用的那一份画。`sessionDock` 在转写的末尾、主列里，随转写一起滚动，不在自己里面滚动；没有项时不占地方。它变高或变矮时，人原先停在末尾的，转写区仍然停在末尾；人往上翻过的，留在他翻到的地方。只有人往上翻才算离开末尾：内容或转写区的高度变了，不算。`sessionSide` 是对话页右边的侧边区，在主列之后。没有项时它没有任何元素，主列的宽度与位置和没有侧边区时相同。只有一项时不出页签，顶上显示这一项的标签；两项以上时是页签，没选中的项藏起来、不卸下。侧边区可以收起，收起后内容藏起来、不卸下。对话区窄于 1160 `session.header` 给 `{ title }`；会话列表的一行 `session.list.item` 给 `{ title, selected }`（这一行的名字、是不是打开着的那一段）。侧栏里的会话列表和对话页一样经外壳画。会话的界面模块在对话页里还有四个开了画法的[部位](../frontend/SPEC.md#部位)，全部部位钉在 会话也能摆在画布上。服务端：应用的装配里有一行（`session-canvas`）往画布的 `canvas.kinds` 上声明种类 `session.session`（叫法、一句这一类是什么、一句「标识就是会话标识」），只声明，不带 `admit`：会话没有要先持有的东西，读不读得到由画法在画的时候问。客户端：应用的装配把画布的 `canvas.element` 与 `canvas.picker` 交给会话的界面模块，它不导入画布的成员，各在键 `session.session` 上放一份画法。纸上的画法写标题（没有标题时同列表的写法）、最近一次活动的相对时间与状态（生命周期的词只在不正常时写，同列表），取自会话目录里这个会话自己的那一行。目录只在界面起来时读一次，所以这一行不在目录里时先重读一次目录，在比这一页新的目录里也没有，才说读不到，不存在与无权读写同一句；点开就带着这个会话跳到对话页（用上面那个对象写法），外壳在反面时先翻回正面。挑法按查找的字在本租户没归档的会话的标题里找，挑中一个就把它的标识交给画布的 `pick`。没交这两个点时，纸上的会话画成画布通用的页，查找里挑不了会话。

界面模块以协议客户端为输入，状态拆成三条独立的轴：会话（还没有、建会话中、已打开、不可用，打开时再分这一轮的还不知道、就绪、进行、取消）、观察（连接中、在连、断开重连）、会话列表（未读、读首页、读下页、已读、读失败）。界面遵守：这一轮在不在进行只从状态帧来，没收到过状态帧是「还不知道」，不是就绪：这时没有停止钮（停止要这一轮的编号），停止的命令答「还不知道有没有在做的一轮」，收到第一帧就按帧显示，从还不知道到就绪不算一轮结束；一直收不到帧时观察在重连，那一行重连的字就是原因；结果不知道就用同一个调用编号认回，不重发，认回仍未知就停在「结果仍未知」由人再确认；已提交的内容只从读历史来，进行中的回复来自观察，历史读到哪里取最近读完的那一轮的上界，状态帧的修订更大就从末尾再读一轮；对不上基线的增量不应用，换一代重新观察；历史条目、消息部件、流的块三处种类都封闭，表外的种类画成占位并写明种类名；工具调用与结果只按调用编号配对；转写区不认识任何工具，工具调用画成什么只取自对话本身；能作答的卡不是转写的条目，由人工介入的界面模块经 `sessionDock` 放在转写的末尾；被拒、本地不可用、未知各有一句人话，显示在出事的那一处；会话列表是服务端的投影，界面不在本地增删列表项，只在建会话、受理一条输入、一轮结束三种「活动」之后重读第一页；打开已有会话与新建成功走同一条路；列表读失败不碰已打开的会话；换会话时原会话没有结论的输入的答复一律作废。

一轮失败之后，界面经读等人知道会话在不在等人、等的是哪一轮、还有几条没处理与成因，不从历史里推。读的时机：读历史读到一条新的失败终结；状态帧说没有进行中的一轮而最近的终结是失败；在等人时发送有了答复；重试答恢复、冲突或找不到。读着的时候又要读，就在答复回来后再读一次。提示是失败语气的行内通知（`InlineNotice` 的 `danger`），放在等的那一轮的失败那一行下面，只有说事实的那一句带失败色，后面的句子是正文的墨：人话的原因在前，成因按种类查一张表得到中文，表里没有的写通用的一句并带上种类名；没有回复（`no-reply`）按成因带不带 Model 的失败分两句，带着的说「模型调用没有成功，这一轮没有得到回复。」，不带的（调用完成而回复不能用）说「模型没有给出有效的回复。」，调用为什么失败由放进 `session.run-failure` 的项在下面说；有诊断就收进通知里的「详情」；没有成因只说这一轮失败了；条数为零时只提示发一条新消息，不出重试；条数不为零时写条数与「重试」。重试点名等的那一轮，带一个新的控制标识；答恢复、冲突或找不到就重新读等人，答没有变化就显示发新消息的那句提示，答未知就如实显示（中性）并让人再问一次，再问用同一个控制标识，连不上与被拒写明原因（中性）、可以再按。读等人答不了（依据不可用、这个操作不在、被拒、连不上）时退回只显示这一轮失败了。

观感照[视觉规范](../../.meta_harness/agents/skills/visual-standard/canonical/SKILL.md)，转写里各种条目共用的原则见[对话流](../../.meta_harness/agents/skills/visual-standard/canonical/references/conversation-stream.md)；语气照[规则与 token 的索引](../../.meta_harness/agents/skills/visual-standard/canonical/references/rules-index.md)的 C3、C4：已知的失败用失败语气（`InlineNotice` 的 `danger`，状态词的失败色），结果不知道与被拒是中性，琥珀只给已知事实的注意，正常的状态不画字、不画点。会话列表是侧栏区的一列。顶上是「新建会话」，与导航的行同一列：同样的左内边、图标列与行高，图标加字，不是突出在左边的描边框。侧栏里不选模型：新会话不带模型，用部署给的默认，建了之后在对话头里改。下面每个会话一行，是 `GlideMenu` 的行：标题一行，没有标题时写「未命名的会话」加标识的前八位；下面一行弱墨的说明字只写最近一次活动的相对时间（`Ago`，精确的时刻在提示里）；对话页显示着时，当前会话是选中的底；别的页显示着时没有一行被选中（按外壳服务的 `page` 判断），侧栏里仍只有一处被选中。生命周期的词只在不正常时写：正在初始化、已冻结各是一个中性的状态词；正常的会话什么都不写，也不标在回复，那是形的事。加载时是一行弱墨的「正在读会话列表……」；空时列表什么都不写：主区的那一句已经说了，顶上的「新建会话」就是入口；读不到是行内通知，能重试时带「重试」，语气是注意，被拒是中性的一句原因；没读全时列表末尾一行说明字「列表可能不全」；还能往下读时，列表的末尾进了视野就接着读下一页，不放「更多」。已归档的会话在列表下面，是一行可展开的「已归档」，原地展开，不是浮层：里面是按标题里的字找的字段与已归档的行。这些行不能打开，所以不显示指针、不随悬停变色；「撤销归档」是行尾唯一的动作，一个图标钮（撤销的字形，名字在提示里），结果是这一行下面出现一次的回执。读不到是「已归档的会话暂时读不到。」，空是「没有已归档的会话。」，都是中性。

对话页的头部高 84，底下一条细线，照来源分三栏：左边是标题，界面字号、常规字重、弱墨（来源的话题控件那样），不是大标题；正中是对话头的座位与 Agent 的名字，见上面写座位的那一段；右边的下拉显示当前模型、推理强度和权限处理。模型的下拉只列可选的模型，再加上当前选中；当前选中不可选时照样显示，并写明原因（例如「没有启用」）。推理强度可选「模型默认」或四个统一档位，「模型默认」后面写出这个型号此刻的缺省推理强度，没有时写「供应商默认」；型号不支持的档位显示为禁用并说明原因。选模型默认会清除显式强度。切换型号会保留仍受支持的档位；否则目标行写明切换后采用该型号默认值。模型选择与权限处理之间是会话的工作区：一行弱墨的工作目录或用不了的原因，写不下的用省略号收住、整句在提示里，有工作区可选时前面是同样安静的下拉。最右一个 `⋯`：会话标识（等宽，可复制，复制的结果是这一项自己的回执）与「归档」。头部放不下时，座位与名字留在正中，标题至少留 8 个字的宽度，写不下的用省略号收住；先把工作区、再把权限处理、最后把模型和推理强度一起收进 `⋯`，菜单里写它们当前的值（工作区另写工作目录那一句），照样能改。会话的界面模块在客户端树上提供一个服务（键 `session.model-choice`，从 `./cordis` 入口导出），别的模块经它要求打开某一段会话的型号选择：打开着的是这段会话时，型号在头部就打开那个下拉，收进了 `⋯` 就打开 `⋯` 并展开型号的那一栏；不是这段会话时什么都不做。归档不问，按下就发，结果是一句出现一次的回执；撤销在已归档的列表里。观察在连接中与在连时头部什么都不画；断开重连时头部下面才出现一行中性的说明字，写更新断开了、正在第几次重连。没有会话时没有头部，主区正中只有一行弱墨的说明字：点「新建会话」开始一段对话。不画成标题，别处不再另说。正在建会话时是「正在建会话……」，结果不知道时通知带恢复动作「再确认一次」（重试的字形加字），被拒写原因，都是中性。会话不可用（没有权限读、登录已失效）是页里一句中性的原因。外壳给的租户读不懂时页里只有一行「外壳给的租户读不懂，会话界面不能工作。」，失败语气。

转写是这一页唯一滚动的面。主列最宽 740，在对话区里居中，侧边区停靠时在剩下的宽度里居中；页的左右内边距、底边与转写滚动区的槽照来源的对话页，按字号档换算；主列与输入框同一个左起点、同一条右边，你的话的气泡收在主列的右边上；同一个说话人的块之间 `--omne-space-block`，换人或隔天 `--omne-space-section`。你的话是右边的气泡，阅读字体，最宽是列宽的 88%。Agent 的话是左边一张纸色的底，底色、圆角、内边距照来源，阅读字体、正文字号，字的量度与来源相同（来源字体的 70ch，即 `--omne-measure-reading`）；Markdown 在里面，代码、表格、图各是一条细线围着的平面，不再套卡。说话人的名字不画，留给读屏。推理是一行过程行（图标、「推理」、状态词），原地展开成弱墨的阅读字。工具调用是一行过程行（图标、等宽的工具名、状态词）；状态词只用共用件的进行中、已完成、失败、未知，没有结果而这一轮已经结束的写「没有结果」，中性。展开后参数是一张事实表：会话按通用办法编进条目的参数先转回普通的值，不是那棵树的原样当普通的值，再写成名与值，嵌套的值写成一行摘要；结果是 `CodeSurface`，宽不超过主列；参数还没生成完时是 `CodeSurface` 里的原文加一个中性的「还在生成」。提问的调用和别的工具调用画法相同，不能作答，也不像能作答的卡；它在等人答时状态词是「待回复」（等人的琥珀），不写「处理中」。系统提醒与内部工具消息是最轻的过程行，缺省收着；展开后是几行弱墨的「名：值」，不出给模型的原文。正常的一轮开始与完成不画；压缩、取消、失败各是一行居中的说明字，失败的那一行词用失败色。媒体与不认识的种类是一行弱墨的占位，写明种类名。回复进行中转写什么都不说：没有占位、没有三个点、没有光标；流出来的字按词淡入，只有新到的行淡入，历史与「更早的」不动。在途的内容丢了一段时，末尾一行中性的说明字说明缺口与正在重新取，不补造。你发出的话气泡立刻出现，就是发出了：发送中与已受理不画词；未知（正在确认、结果仍未知）时气泡下一行是中性的说明字，结果仍未知时带一个「再确认一次」的图标钮（重试的字形）；没有发出（被拒、已确认没有受理）时气泡下一行写原因，词用失败色。从搜索跳来的那一条落定一次，不画常驻的框。每条回复下面一行回执重量的说明字：这条回复的模型与推理强度（来源），取自诊断页里这次调用最后一次发出；取不到不写。

输入框上方是排着的与在等的。还排着没处理的话是一行回执重量的说明字「还有 n 句话排着没处理」，原地展开成这些话的列表，不是一块带边框的区；读到的条数到了上界时写「至少还有 n 句话排着没处理」，展开后只列前面的；读不到是一行中性的原因；没有排着的话时什么都不画。在等人答的调用不另写一行：卡在屏幕上，它的条数只决定输入框的占位符。会话已冻结时，输入框的位置是一句中性的说明：这个会话已冻结，不能再开新的一轮，写明是哪个常驻工具、为什么；不说「暂时」。冻结的原因读不到时只说已冻结。输入框是整页唯一一张抬起的纸：窗口圆角、一条细线、`--omne-surface-field` 的底，聚焦时线变深，不画环；最高 `min(46dvh, 400px)`，只有字段自己滚；输入法组字时回车不发送。占位符照来源的写法：平时是「发消息给」加 Agent 的名字；一轮在做时是来源忙时的那一句「写好下一句，现在即可排队」；有在等人答的调用时是「发消息给」加名字再接「，会排队，不算回答」。字段下面一行，照来源只有这些：左边是 `sessionComposerAttachments` 放进来的图标动作，没有就空着；右边是 `sessionStatus` 的状态位与唯一的动作钮。不知道的不画：状态位里没有写「未知」的行。发送、停止、正在停止与再确认停止是同一个图标钮换脸（发送、停止、活动标记、重试的字形），名字在提示与可访问名称里，停止的样子带一句说明「停止这一轮。还没答的问题会一起关掉。」。输入框可以有一个助手：选项 `composerAssistant` 是一个服务键（形状 `ComposerAssistant`，从 `./cordis` 入口导出），由应用的装配交给提供方，没有时输入框照上面的样子。宿主每打开一个会话的输入框，向助手要一个这个租户、这个会话的帮手，输入框收走时关掉它；宿主把文字、光标与组字的开始结束告诉帮手，上下、Tab、回车、Esc 先问帮手吃不吃。帮手交回通用的数据：几段标记（种类与说明）、菜单的项与选中、灰字、发不出去的原因、随输入交出的所见。宿主照这些画：标记画在字段下面叠着的一层，菜单是从输入框上方出来的浮层；有发不出去的原因时发送不可用，原因下面一个「按原样发送」；发送时所见随输入交出。服务端以无效拒收并给了原因时，原因写在那句话下面，并告诉帮手一次。会话的界面模块不认识任何一条命令。

搜历史的页是单列页，`PageColumn` 加 `PageHeader`，标题「搜索」；页头下面只有一列，宽是阅读量度（`--omne-measure-reading`），在页的正中，没有阅读面：一条命中的阅读面就是那个会话。这一列照列表加阅读的目录栏的手（规则索引 S6、L6）：顶上是 `DirectorySearch`，搜索字形在字段里，有字时右边一个清除的图标钮，占位符按方式是「一个或几个词，用空格分开」或「一条正则」，回车就搜；字段清空（按清除钮或删光）就回到还没搜的样子。字段下面一行安静的件：分段控件「词」「正则」，后面是说明字重量的两个勾选项「只看我说的」「区分大小写」；这一行不收进折叠，少按一下。结果是 `GlideMenu` 里的 `ListReadingRow`：记号是对话的字形，标题是会话名（列表不认得这个会话时写标识的前 8 位），事实是带高亮的片段，阅读字体，高亮是强调色的淡底，不用浏览器的黄色，时间那一行是谁说的 · 相对时间；按一行就打开那个会话并跳到这一条。正在搜是一行弱墨的「正在搜……」。搜完了一条也没有，照列表的没有匹配：搜索的字形，「没有匹配「…」的记录。」（引号里是要找的字），下面一个「清除搜索」的图标钮（关闭的字形），按下与清空字段相同。没搜完时结果末尾一行中性的说明字加一个「接着搜」的图标钮（重试的字形）：人话在前（为什么没完、还有几个会话没读完），索引建到哪里收进「详情」；没搜完不写成没有找到。搜完了而还能往下读时，结果的末尾进了视野就接着读。正则写得不对、词太长或太多、同时在跑的搜索太多、没有权限、历史暂时搜不了，都写在那一行件下面，中性。

动作照[规则与 token 的索引](../../.meta_harness/agents/skills/visual-standard/canonical/references/rules-index.md#a-动作)的 A 节：带字的动作钮只有「新建会话」，别的工具动作是图标钮。反馈：模型、权限处理与分段控件自己就是回执，改成了权限处理不另写「已改为……」，没改成或不知道改没改成时在下拉旁写一句中性的原因；复制会话标识是 `⋯` 里那一项自己的回执；归档与撤销归档各落一句回执；发出的话以气泡出现为回执；失败写在出事的那一处。界面的控件、通知、折叠、过程行与文字的渲染都用共用界面件（`Button`、`IconButton`、`DropdownMenu`、`Textarea`、`Input`、`Segmented`、`Checkbox`、`GlideMenu`、`Ago`、`StateWord`、`TraceRow`、`FactList`、`CodeSurface`、`InlineNotice`、`Disclosure`、`Prose`、`PageColumn`、`PageHeader`、`EmptyState`、`LoadingState`、`FigureSeat`），本成员的样式表只有版式，不带这一类基础样式。版式的来历记在成员的 `UPSTREAM.md`。

### 存储

一次提交只有一个存储事务，参加者模块不开始、提交或回滚事务；提交携带本命令需要的全部参加者，不信任调用方挑选材料，提交固定使用组合版本，材料缺席、协议版本不符、跨租户、来源无权或最新条件改变时被拒或答已变。租户是每一行的列，也是每条语句的条件，不从连接、事务域或装配树推断；同一事务域只服务一个租户。会话身份、位置、提交序与条目位置由存储分配，操作身份由 Session 按固定规则派生，存储不生成。同一会话的提交串行化，读在事务外读已提交的快照。命令到条目批次的编码只有一份（判定函数），解码也只有一份（归约函数），二者共用一个解释版本，每批记录它的解释版本。读路径的游标需要游标签名，缺席时带游标的读答不可用。

条目的存储文本是一个 JSON 对象，成员与历史条目同序，载荷以 `body` 存它原样的 JSON 文本。数字保留源字面量，对象保留键序，读回得到同一棵树。含重复键的文本被拒绝，没有 `body` 的文本不被读取。提交的时刻取自 Session 的时钟，在第一次尝试之前读取一次；没有时钟、读取失败或抛出时，提交照常进行，这次提交的事实不带时刻。存储提供者接受的 JSON 嵌套深度必须不小于创建会话那条提交命令的嵌套深度：更深的命令被拒为 `command_limit`，创建会话就失败。实际深度由 `session-adapters` 的 `create-depth.spec.ts` 量出并守着。

存储失败分类：暂时的拒绝答不可用，调用方等待后以同一身份重做；确定的拒绝答非法，日志适配把存储说的那一句（原因码、哪个上限、量到多少、上限多少，只含身份与状态）作为担保的诊断随失败交出，这一轮的失败原因里读得到它；身份冲突时已有回执为已提交就认回（输入摘要不同则答冲突），为已回滚则选下一个尝试代次重新提交；某个代次为未知则答提交未知、不开新代次；提交结果未知、写者不再是当前、锁等待超时都答提交未知；任何 SQL 异常不转成业务拒绝，写路径答失败、读路径答不可用；权威条目缺口、损坏或尾部不一致时隔离该会话，读取工作与恢复返回隔离，其余读写答不可用；派生索引重建中时依赖它的读答不可用并带进度。权威表的迁移只增列或增表、不改旧列含义、不改位置与身份，派生表可以整体重建；归约版本升级是一次全量重建，不是迁移。数据库方言的差异（位置的编码、JSON 用文本、写并发、耐久）在边界处理，不分叉业务语义；不宣称断电耐久，耐久边界只由提供者读回的配置给出。向基础来源要材料只发生在该操作还没有任何已提交的送达时。来源失败时先再查一次回执：期间已提交的送达被认回，不用这次失败作答；没有已提交的送达才答这次失败，下一次送达重新询问。

### 装配

服务定义只有一个服务键，四个面挂在同一个键上，同一组签名不写两份；服务键只由抽象类给出，提供者不再提供这个键。调用方插件以对象形式声明调用方类。构造依赖里访问检查、委派入口、内部主体、会话工作主体缺席或撤除时服务停在待启动，不沿用旧的允许；其他端口缺席时只有需要它的操作答不可用，端口抛出同样映射为不可用并带拥有者与诊断，代理不补默认值，不用系统时间代替时钟采样；可选的能力（事务端口的日志提交、采用来源的规划）缺席时按不可用处理。出站端口缺席时出站调用不发出，任务保留，由调度器重放。唯一的事件是提交叫醒，载荷是租户、会话、会话修订、原提交证据与条目种类的去重集合，不带消息正文、凭据或附件地址；它只是唤醒提示，丢失不影响正确性。一个隔离标签下一个提供者；租户与会话是每次操作的参数，不用隔离或 Cordis 上下文表达，不为会话建 fiber。每个租户一个恢复扫描者，由装配保证全部进程里只装一份提供者插件；扫描者只在租户有待办时留着。根入口与 Cordis 无关，定义入口不导入任何提供者。

撤除有序：标记撤除中（此后面对每个操作答不可用，不再把叫醒交给实例）；释放全部维护句柄（扫描者停止）；调用实例的关闭，最多等配置的上限（调度器停止接受新触发，在途命令跑完或返回未知，协调器在当前命令结束后停止，最后释放时钟等待与缓存）；等待超时记诊断后返回，超时不表示实例已停止，仍在途的命令以自己的结果结束，提交未确认的得到提交未知。每一步抛出都被捕获并继续后续步骤。撤除不回滚已提交的事实，不补发未发出的出站调用，不取消任何 Model、Tool、Agent 的执行，也不撤回外部效果。依赖换代时插件先卸载再重跑。适配插件共同的规则：每个插件只以一个调用方类调用会话；只经邻域的公开契约工作，不导入提供者实现；每次出站调用与每个会话命令都带确定性派生的身份，不用时间、随机数或连接参与编码；邻域返回结果未知时按原身份查询或原样交给会话，不改写成功或失败；插件不保存业务事实，只持有可丢的派生物，丢失后从权威读重建；卸载只结束订阅、登记与在途的等待，不撤回外部效果。

### 协调器与调度器

会话命令的处理流水线对每个变更命令相同：核权并认回原操作；在同一事务边界读权威快照，带预期的命令把它与快照比较，不等就答已变，不用读到的修订改写预期；事务外调用判定函数得到拒绝原因并决定收哪些材料；向身份桥、证据桥、Context 输入或空闲输入要材料；提交；确认耐久后，有测量观察者时读回本次提交的条目并发出轮完成事件。每个命令恰一次提交，跨命令的事只能由后一个用例读取前一个已提交的事实。事务内的判定以存储参加者读到的当前状态重新裁定，以事务内的结局为准。命令处理器、协调器与调度器只编排读取、裁定、提交与叫醒，允许与拒绝只由纯裁定给出。协调器没有自己的状态，输入只有权威读、出站回执与调度器交来的会话身份，同一会话同一时刻只有一个协调实例在动作（进程内每会话一个串行队列；跨进程靠每租户一个扫描者、操作幂等、预期核对与执行记录提供者的条件提交围栏，不用锁）。受理流水线、Agent 推进协调器（开 Run、续入、同日志解释、恢复、接管、重装、冻结判定到达）、控制传播协调器、归档与级联协调器、恢复协调器各自读到事实后决定发出哪些命令或出站调用。调度器只决定什么时候再检查哪个会话，不写日志：推进触发（提交叫醒含受理、终态、冻结或会话创建时读快照并按判定开 Run 或续入，每会话一个在途触发，新叫醒合并为一次重查）；空闲与自动归档（时钟或提交叫醒触发，空闲观察非未知时记录空闲再判定是否到期，到期则归档，计时随进程丢失、重启后按已确认的起点续算）；恢复扫描（启动与周期按租户分页读八类待办原因，游标不持久，重复交付由命令的操作身份认回）；待决认回；控制重放；级联推进；预求值与预热（只预求值并缓存已校验的采用候选，候选只在新 Run 入口或显式重装时才成为采用依据）。内部等待明确返回到点、取消或被拒；时钟被拒时调度器记诊断，不把等待当作已到期，也不改用系统时间。所有间隔、上限与退避都是策略对象的配置，默认值不散在代码里，实现可以替换策略对象。会话调用经内部主体与会话工作主体：协调器用协调方、维护者的会话主体，不由单个会话归属决定的系统维护（按租户读待办、作用域释放的收尾）用内部主体的维护者；签发主体被拒就不推进该会话、待办保留，不可用或隔离则保留任务下次再取。

## 原则与约束

- 一类事实只有一个写入者。会话日志的唯一写入者是 Session；别的领域要留下事实，交一条会话命令。
- 逻辑收口和物理收场分开。取消、归档、换代、释放只改变资格与责任。
- 结果不知道就是不知道。按原来的那次操作认回，不重新发一次，不写成成功或失败；认回之前不发出依赖它的外部效果。
- 服务端是事实的权威。客户端只有投影和缓存。
- 一个结局连同它带来的后果在同一次提交里写下。不靠提交之后的另一步去补。
- 每次提交之后要做的事挂在写入者上，不挂在各个提交方上；提交之后只发唤醒，唤醒不是事实源，丢了由扫描补查。
- 业务规则不进应用层：允许与拒绝只由纯裁定给出，命令处理器、协调器、调度器只编排。协调器与调度器不持有状态，内存里只有可丢的计时、计数与缓存。
- 幂等只靠操作身份。重放同一命令派生同一身份，每个命令的第一步是认回。
- 外部效果与日志分开：对 Agent、执行环境、子会话的调用在提交之后发出，回执作为新事实提交；提交成功而调用没发出时，调度器按同一身份重放。
- 请求到了不算，算在请求之前：派生物在变化时维护，热路径只读取。
- 读不到不变成空。读取故障不当作空队列、无 Run、无权限或执行失联。
- 领域不认识调用它的是谁，源码依赖只朝内：端口的接口由提出需要的一方声明，另一方适配；邻域契约不点名 Session。
- 租户是每次调用的参数，缺租户或跨租户默认拒绝；租户与会话不从连接、上下文、隔离标签或装配树推断。
- 每个策略类的量（重试、退避、超时、间隔、预算、上限）是可配置的策略对象，合法使用会碰到的上限必须有去处，不判失败。
- 本组不为旧数据写兼容代码；改承诺同步真实消费者，替代实现随改随删。
