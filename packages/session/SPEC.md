# Session

## 总体架构

Session 管一个会话的业务流程，拥有会话日志。包组的成员按它们回答的问题分：

| 成员                                               | 回答的问题                                                                 |
| -------------------------------------------------- | -------------------------------------------------------------------------- |
| `session-contract`                                 | 日志里有哪些条目，一条命令怎样判成条目，条目怎样归约成快照。纯数据与纯函数 |
| `session`                                          | 命令怎样被受理，提交之后接着做什么。不依赖 Cordis                          |
| `session-storage-sql`                              | 一次提交怎样在一个事务里落盘，快照与索引怎样读                             |
| `session-cordis-contract`、`session-cordis`        | 在这套系统里它以什么服务出现，怎样绑到存储上                               |
| `session-adapters`                                 | 邻域的端口由谁来适配。Session 是最外层，经这里认识 Agent、Model、Tool      |
| `session-observation`                              | 一个登录的人看一个会话时看到哪些帧                                         |
| `session-protocol`、`session-access`、`session-ui` | 对客户端开放的三样：协议契约、接入插件、界面模块                           |

一次提交是这样走的：命令进来，判定函数对着当前快照把它判成一组条目，存储在一个事务里把这组条目追加进日志，归约函数把它们并进快照。每次提交之后要做的事挂在写入者上，不挂在各个提交方上。

## 领域边界

Session 拥有一个会话的日志，而且是它唯一的写入者。别的领域要留下事实，把一条会话命令交给它，由它在同一次提交里写。

Session 不发模型请求，不运行工具，也不直接控制它们的调用。Run 是它和 Agent 的边界：Session 交出工作与推进的资格，一轮怎样往前推归 Agent。

取消与归档只改变资格与责任。模型发没发出、工具停没停，由各自的拥有者报告，Session 只对账。

## 心智模型

会话日志是一个会话的唯一事实源。快照是日志归约出来的：待处理的输入，活动的轮，一轮取走了哪些输入，会话是不是在等人，都是归约的结果，没有别的来源。

拿这一条量一个设计：一个决定会话接下来做什么的事实，如果不在日志里，进程重启之后就没有了。所以每个这样的事实都要有一条条目，或者能从已有的条目归约出来。

## 应然设计

### 输入的括号

一批输入被一轮取走，是开一个括号。括号在这一条成立时关上：取走之后，有一条完整的助手回复进了日志。取走是租出，不是消费。

| 这一轮怎样终结 | 括号还开着的输入                                     | 之后要不要自动开下一轮   |
| -------------- | ---------------------------------------------------- | ------------------------ |
| 完成           | 不会有：有输入没回答就不能完成                       | 还有待处理的输入就自动开 |
| 被取消         | 随取消一起了结，不回到待处理。人说了停，不替人再跑   | 还有待处理的输入就自动开 |
| 失败           | 在终结的同一次提交里回到待处理的队头，保持原来的先后 | 不自动开。会话等人       |

### 等人

一轮失败之后会话进入「等人」。这时不论待处理里有什么，都不开新的一轮：失败之前重试的预算已经用完，再自动跑一次没有新的依据。

「等人」只有两个出口，都是人的决定：人发来一条新的输入；人对失败的那一轮发「重试」。解除之后，下一轮照常由 Session 开，按先后把待处理的输入一起带上，归还的在前，新发的在后，不用重新输入。

「重试」只解除等待，不是一条输入，也不由系统自己发。它点名失败的那一轮：那一轮已经不是会话在等的那一轮时答找不到。待处理是空的时候它不被受理：下一轮带不上任何输入，受理了也不会开轮。这种情形出现在一轮先给出过完整的回复、之后才失败的时候，人要让它接着做就发一条新消息。

能不能开新的一轮只在一处判。提交之后的触发、启动时的扫描、显式的开轮命令，问的都是这同一个判定。

## 原则与约束

- 一类事实只有一个写入者。
- 逻辑收口和物理收场分开。
- 结果不知道就是不知道。按原来的那次操作认回，不重新发一次，不写成成功或失败。
- 服务端是事实的权威。客户端只有投影和缓存。
- 一个结局连同它带来的后果在同一次提交里写下。不靠提交之后的另一步去补。

## 不变式

| 编号 | 永远成立的性质                                                                                                                                                              | 违反的后果                                                 | 由什么守                                                                                                                                     |
| ---- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| SE-1 | 一条输入至多一次有效承接。在一个 Run 里它至多被取走一次；所属的 Run 失败而括号还开着时，这一次承接作废，输入回到待处理，可以被后面的 Run 再取走。同一条输入至多得到一次回答 | 同一句话被处理两次                                         | `session-contract` 的归约与成员用例；`session-contract/verification/models` 下三个模型的 `TakeOnce` 与 `OneOutcome` 守的是没有作废时的那一次 |
| SE-2 | 一轮终结之后，没有括号开着的输入：要么已回答，要么随取消了结，要么回到了待处理                                                                                              | 排着的消息既不在待处理里，也没有被回答，等于丢了           | `session-contract` 的成员用例；系统级模型 `docs/architecture/verification/recovery` 的 `TerminalSettlesInputs` 与 `TakenInputResolves`       |
| SE-3 | 一轮失败之后，没有人的输入或重试就不开新的一轮                                                                                                                                    | 失败的轮带着同一批输入自己反复再跑，没有上界               | `session-contract` 的成员用例；同一个模型的 `NoAutoReopenAfterFailure`                                                                       |
| SE-4 | 归还与终结在同一次提交里                                                                                                                                                    | 两次提交之间进程没了，输入停在既没被取走也不在待处理的状态 | `session-contract` 的归约：归还是终结条目的归约结果，不是另一条条目                                                                          |
