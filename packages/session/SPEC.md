# Session

## 总体架构

Session 管一个会话的业务流程，拥有会话日志。它回答：一个会话里发生过什么，这些事实怎样在一次提交里成立，接下来该做什么，由谁来做。包组的成员按它们回答的问题分：

| 成员                                                         | 回答的问题                                                                                                  |
| ------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------- |
| `session-contract`                                           | 日志里有哪些条目，一条命令怎样判成条目，条目怎样归约成快照。纯数据与纯函数，不依赖邻域契约，不依赖 Cordis   |
| `session`                                                    | 命令怎样被受理，提交之后接着做什么：命令处理、协调器、调度器、缓存。不依赖 Cordis，用替身就能跑完整个状态机 |
| `session-storage-sql`                                        | 一次提交怎样在一个事务里落盘，快照与索引怎样读                                                              |
| `session-cordis-contract`、`session-cordis`                  | 在这套系统里它以什么服务出现，怎样绑到存储上，怎样撤除                                                      |
| `session-adapters`                                           | 邻域的端口由谁来适配。Session 是最外层，经这里认识 Agent、Model、Tool、Runtime Context、执行环境与身份      |
| `session-observation`                                        | 一个登录的人看一个会话时看到哪些帧                                                                          |
| `session-protocol`、`session-access`、`session-ui`           | 对客户端开放的三样：协议契约、接入插件、界面模块                                                            |
| `session-diagnostics-protocol`、`session-diagnostics-access` | 登录的人怎样读一个会话的诊断页：协议契约 `session-diagnostics/v1` 与它的接入插件                            |

一次提交是这样走的：命令进来，判定函数对着当前快照把它判成一组条目，存储在一个事务里把这组条目追加进日志，归约函数把它们并进快照。每次提交之后要做的事挂在写入者上，不挂在各个提交方上：提交之后只发一条唤醒，协调器与调度器读权威状态再决定做什么。

依赖方向：`session-contract` 不依赖任何邻域契约，出站端口的接口在这里声明，本域只说自己要什么；`session` 只依赖 `session-contract`；`session-cordis` 依赖前三者，不依赖邻域契约与存储后端；`session-adapters` 是组内唯一导入邻域契约的成员（`session-observation` 只读 Model 的公共流，也导入 Model 契约），它与 `session-cordis` 没有编译期依赖，端口的服务键由装配接上；`session-storage-sql` 依赖契约、Cordis 定义的 `./cordis` 入口与存储契约。

新增一段代码时按下表选成员，同时满足几条取最靠下的一条：

| 这段代码需要什么                              | 放在                  |
| --------------------------------------------- | --------------------- |
| 只用类型、值、身份与纯判断，不调用任何东西    | `session-contract`    |
| 用替身就能跑完整个状态机                      | `session`             |
| 要从 Cordis 现取时钟、通知总线或装配端口      | `session-cordis`      |
| 读会话日志与 Model 的公共流，产出会话观察的帧 | `session-observation` |
| 要导入任何其他邻域契约                        | `session-adapters`    |
| 与存储介质相关                                | `session-storage-sql` |

## 领域边界

Session 拥有一个会话的日志，而且是它唯一的写入者。别的领域要留下事实，把一条会话命令交给它，由它在同一次提交里写。Session 拥有：会话身份与固定事实（租户、定义标识、执行类型、必需身份）；日志与由它归约出的当前状态；Run 与执行尝试（attempt）的治理事实；受理、等待、控制、终态、归档、冻结、关系、空闲；会话当前值（三轴模式、工作区选择、模型选择、Context 注册、权限配值）；判断「还有未结工作吗」的依据。

Session 不发模型请求，不运行工具。对一次调用的控制送到它当前的等待者：还在某一步等待里的调用经 Agent 送达，因为答复要回到那一步；转了后台的调用没有在等它的步，Session 凭调用引用直接交给 Tool。Run 是它和 Agent 的边界：Session 交出工作与推进的资格，一轮怎样往前推归 Agent。取消与归档只改变资格与责任。模型发没发出、工具停没停，由各自的拥有者报告，Session 只对账。

Session 不拥有：授权政策与登录（身份与授权）；卡片与答复（人工介入）；模型档案与凭据（Model）；工具的启动围栏与结果清理（Tool 与 Agent 的日志）；作用域资源本身（执行环境、Runtime Context）；共享设置与资产的内容；存储事务的提交协议与回执（存储契约）。

Session 认识全部邻域，邻域都不认识 Session。邻域契约只用通用角色：外部协调者、提交参加者、消费者拥有者、作用域持有者、历史持有者、维护者。名称与形状的翻译只在 `session-adapters` 里发生。

Session 向外声明的端口（它需要别人做的）：

| 端口                                                                   | 对方                        | 对得上的一句话                                                                    |
| ---------------------------------------------------------------------- | --------------------------- | --------------------------------------------------------------------------------- |
| 访问检查 `SessionAccessCheck`                                          | 身份与授权                  | Session 需要对每次公开读写给出当前资格裁定；授权适配器提供                        |
| 事务端口 `SessionTransactionPort`、委派入口                            | 存储                        | Session 需要一个事务把条目、操作认回、治理变更与参加者放进同一次提交；存储提供    |
| 身份桥、证据桥、Context 输入、空闲输入                                 | 身份、装配、Runtime Context | Session 需要提交时的可信身份、采用依据、注册材料与空闲覆盖；各拥有者经适配提供    |
| 时钟、通知者                                                           | 装配                        | Session 需要采样时间与提交后的唤醒；装配提供                                      |
| `AgentDrivePort`：发起、交入、接续、控制、交还、保管、查询、读执行记录 | Agent                       | Session 需要把一轮交给 Agent 并读回原记录；Agent 的公开入口经适配接上             |

| `SessionCallControl`、`SessionCallStates`                              | Tool                        | Session 需要按调用引用控制一次调用、读一次调用的状态；Tool 的命令与读口经适配接上 |

| -------------------------------------------------------------------------------------- | --------------- | -------------------------------------------------------------------------------------- |

## 心智模型

会话日志是一个会话的唯一事实源。快照是日志归约出来的：待处理的输入，活动的轮，一轮取走了哪些输入，会话是不是在等人，都是归约的结果，没有别的来源。运行着的对象不存别处没有的事实；它丢了，从日志接着来。协调器、调度器、适配插件、缓存都是可丢的活体。

拿这一条量一个设计：一个决定会话接下来做什么的事实，如果不在日志里，进程重启之后就没有了。所以每个这样的事实都要有一条条目，或者能从已有的条目归约出来。

另一幅图景是「两本账、两个写入者」：会话日志只有 Session 一个写入者；Agent 的执行记录有自己的提供者。两本账在同一个事务域里，一次提交可以同时写两本，各自的事实各自成立。Session 对 Agent 的事实只做两件事：在 Agent 的提交里作为参加者核对或共同保存；事后读同一日志里的 Agent 事实，把后果写成自己的条目。Session 从不保存 Agent 的工作状态。

最容易想错的地方：

- 受理、承接、交入、解除是四件事。受理是输入进了日志；交入是 Session 把它交给 Agent；承接是 Agent 取走它，批界由 Agent 的输入水位线定；待处理资格只在读到承接事实时才解除。
- 提交通知只是唤醒。丢了、重了、合并了都不改变事实，扫描补查。
- 提交未知不是失败也不是成功。按原操作身份认回；认回之前不发出依赖这次提交的外部效果。
- 逻辑终态先于物理收场。取消一生效就记被取消终态，传播与对账随后进行；「已请求停止」不显示成「已停止」。
- 一个 Run 的状态机和它某一次推进尝试的状态机是两层。等待不是 Run 的状态。
- 读取的空不是没有：读不到、扫不完、有缺口时，答不可用或隔离，不答空队列、无 Run 或无权限。

## 应然设计

### 压缩采用与有效历史

Session 实现 Agent 的日志写入与输入来源适配，负责压缩结果的采用，不执行压缩算法或内部模型调用。服务的成功结果以完整 CompactionMessage 交来，Session 验证原值，不能重写后假称采用了原结果。

采用在日志的一次事务内核对执行仍是当前 Run 的推进执行、原准备及结果的关联、来源证明、当前模型视图代际、覆盖范围、配对与未结工作。完整压缩消息、历史标注、模型视图代际与 Agent 消费事实共同成立；仅认回提交操作身份还不够，同一任务结果与准备不能由另一个操作再次采用。提交未知按原操作查询，不追加第二条摘要。

当前未结工作以提交点事实为准。有对应模型可见消息的工作在覆盖范围内时必须保留该消息；没有对应可见消息的未结事实作为覆盖屏障，不能放进保留名单，覆盖必须在该事实之前结束。新的保护要求使原结果不合法时拒绝；原冻结输入之后的普通尾部追加不自动作废结果，未覆盖的全部模型可见消息继续存在。其他压缩已改变模型视图代际时拒绝旧结果，不能复活已被摘要的旧原文。消息规则归 [Common](../common/SPEC.md#消息)，来源可信与资格不是形状解码可以代替的判断。

输入冻结仅保存可恢复的引用与摘要，不能把完整历史重复写入 Agent 事实族。收到结果时的保管块与采用后的历史消息共用同一份内容字节，遵循 [H1](../../docs/architecture/runtime/session-and-run.md#h1-agent-fact-invariants)。确认结果已接管与决定采用分开：拒绝采用仍须留下原结果的可靠处置，不丢失迟到结果的归属。

历史源从当前模型视图、配对见证和未结工作索引读取冻结输入与提交判断窗口。解析当前作用域使用 `readCurrentScope` 窄读，返回最后绑定（包含结束依据）或尚无绑定的 null；资格、会话隔离与读取进度与其他 Session 读取一致，进度落后不能答 null。当前视图是上次保留项、上次压缩消息和覆盖边界之后的增量；起点只作身份锚点。模型次序与日志次序分别保留，不能靠解析不透明引用比较位置。索引与权威提交的读取进度一致，失去依据答不可用或未知，不答空历史。

固定当前视图、配对与未结工作的规模，增加已压掉的旧历史时，压缩热路径的读取、扫描、传输和复制量不得线性增加。范围标注与人侧历史按需分页派生，不逐次物化整个已覆盖前缀。索引重建可以独立回放日志，不能藏在每次压缩请求里。当前材料仍须完整物化，数据库索引定位的成本不承诺与数据库大小无关。

消息采用性质由 [CompactionLog](../../docs/architecture/verification/compaction/CompactionLog.tla)描述；它抽象来源核验和授权，不证明密码学、真实存储符合性或性能。

### 日志与提交

日志只追加。可靠提交之后，条目的内容、身份、租户与会话归属、因果关联、提交顺序不可原地修改或删除；更正、撤销、控制、状态变化都追加新条目并关联原事实。压缩、卸载、归档、终态、确认、重建投影、格式演进都不构成覆写的例外。更换编码或存储提供者要保留原条目与它的可解释依据。

Session 治理是日志唯一的业务写入口。生产者提交获准的事实或操作，不能直接改日志与治理索引。条目只表示已发生的事实；待执行命令、工程日志、遥测、通知不能冒充已提交的会话事实。在途的流式内容由生产者保管，Session 不逐片落盘；收场后实际采用的内容作为历史条目提交，中断的内容不能伪装成完整回复。

每次操作按（租户、会话、可信来源、操作标识）认回。相同身份且相同操作取得原回执，相同身份不同操作拒绝；同文的新输入仍是新操作。认回先于检查尾部进度，不因后来追加或换代产生第二批原条目；查询仍检查当前资格。命令的身份摘要只覆盖语义参数。

条目批次、操作认回依据、共同的治理变更与它的权威读取进度，在一次不可分割的提交里成立。受理内容与待处理资格、完整批次承接与资格解除、attempt 换代与旧资格撤销、Run 终态与新发起资格撤销，各自同批。必要的外部内容先达到可恢复引用的保管条件，再确认依赖它的条目；准备失败不报受理成功。

一次提交的结果只有五种含义：已提交（返回原提交身份、条目范围、回执，已达声明的耐久边界）；本次尝试被拒或未提交（原操作若有未决尝试仍是未知）；原操作明确未提交（要有存储提供者给出的持久裁定，终止此前全部尝试，之后重试用同一操作身份与新的尝试代次）；并发条件已变（不拼接旧的预计算条目，重新核对原操作再按当前事实判断）；结果未知（保留原操作与处置责任，按原身份查询，不换身份重做）。「未找到」只说明该读取时刻未见已提交操作。日志里暂时没有条目不能推出未提交。

提交不把模型的真实发出、工具副作用、外部物理停止或生产侧确认放进数据库事务。持久的处置责任与对方的执行契约各自对账；「记录了发起意图」不报告成「调用确实执行」。通知发生在提交之后，同一条记录重复投递不产生新条目；丢失由权威状态补查，工作的可靠性不以订阅一直在线为前提。

只有会话日志的唯一写入者写条目，写条目的函数只有一处，它写完一批时给出这一批的租户、会话、修订、出处证据与条目种类集合；认回、回滚与没写条目的提交不发通知。通知失败不回滚提交，也不改变提交的答复。

### 会话的固定事实与采用

租户、定义标识、执行类型与必需身份集合随创建固定，不随账号切换。创建要求明确租户、定义标识与执行类型；工作区可选，指定时工作区标识与附着（实例、装载依据）成对出现，指定的工作区必须按附着合法装载，失败不降为无工作区。本域不从磁盘目录、外部消息正文或最近使用值猜身份与工作区。

新 Run 采用该定义标识当时最新的合法版本；同一 Run 的普通恢复保留原采用，不重新求值。会话不固定能力的版本，延续靠按记下的形状核对同形可用的实现。显式 reload 经候选校验与安全交接后，可在同一 Run 采用同标识的新版本并建立新 attempt，校验失败保留原合法状态。实例重建本身不改定义标识，不重发原调用，不丢原等待、卡片与结果消费责任。

采用要有跨源可核验的有效裁定边界：此前已生效的新发布或撤权使旧候选重算或拒绝，Session 尾部没变不能证明外部依据仍有效；无法核验时不发布新采用，保留原合法状态或报告不可用。裁定之后的变化沿动态规则处理，后续实际动作仍核对当前资格，历史采用记录不永久授权。

创建事实进入第一批日志，携带固定身份、初始值与采用依据。初始化未完成的项保存明确状态与接续责任，会话保持 initializing，直到全部必要项完成；失败的项保留任务，不用空值伪装就绪。重建从创建事实开始，缺起点、解释版本或初始依据时报告不可恢复，不从当前默认补造过去。恢复保留会话当前值，不重新套新的租户默认。

会话选择与注册变化只影响本会话；修改共享源要由该源的拥有者确认。当前权限、共享资产与 Context 数据不因历史引用变成会话自有的源。会话当前值与采用依据分开记，当前值不能凭历史日志推测。

### 访问裁定

`SessionAccessCheck` 是必需的构造依赖，缺席时服务不启动，不能沿用旧的允许。每次公开读写在实际执行处调用一次：包括重复变更、原操作查询、每一页历史、恢复读与目录页。先取得本次裁定，再返回已有答案或披露正文。允许不缓存，不写进游标当作以后的凭据；被拒返回同名失败；不可用或核验抛错返回不可用，不继续读写，不推进修订、游标或操作答案。主体、操作、目标与命令材料在第一次异步等待之前固定。

一次面操作在开头核一次权，随后以委派入口取得只服务本次面操作的事务视图；点查、权威读、重做与提交都经视图，视图不再裁定，不跨面操作保留，不写进任务、缓存或游标。公开的事务端口每个方法各自裁定。存储核心只核租户归属键与绑定本次操作和固定输入的裁定证据，不解释主体类别或授权政策。

租户内操作使用带租户的访问身份，单会话目标绑定租户与会话标识，变更还携带原命令；`pending` 与目录以显式租户为目标；系统作用域的读取（常驻引用、已释放作用域）使用系统主体与限定资格，不制造空租户或任意租户的访问身份。持有组织成本账目读取资格的主体不因此获得其他租户的正文或执行控制。

模式变更的资格由授权适配器按原 `change` 命令裁定；Session 不用调用方类、模式词或历史允许去推断。调用方类（受理方、协调方、维护方、读取方）是装配事实，不是资格授予；它按操作限制能调哪些操作，受理方调不了开始 Run，协调方调不了创建会话，读取方调不了任何变更。

会话归属读取只证明一个会话属于哪个租户，以及创建它的那批证据。它不询问访问检查，只由装配里受信的签发闭包读取。未知的会话与别的租户的会话都答 `not-bound`，读不到答不可用。归属与创建证据在创建之后不再变化，所以只缓存 `bound` 的答复；`not-bound`、不可用与未知都不缓存，因为会话或作用域可能随后才创建。停止之后一切读取答不可用，已缓存的也一样。

作用域属主查询在每个已注册租户的域里按租户次序查找，找到第一个拥有者就停。作用域文本是单向摘要，不能从中读出租户。某个域读不到时答不可用，不答未知。已结束的作用域仍有属主。

每会话的工作主体由装配入口在读过归属之后签发：`not-bound` 答被拒；`bound` 却属于别的租户或会话答隔离；读取失败原样转交，抛出按不可用；签发失败答不可用并指明身份是拥有者。任何失败都不签发主体。

### 受理与输入

受理成功意味着必要数据已达到进程崩溃、操作系统崩溃与断电之后的耐久边界。普通输入的内容或有效引用、来源、租户、会话、同次提交标识与待处理资格在同一次提交里成立；没有已提交事实不得报告受理成功；拒绝留痕不取得待处理资格。受理标识先于首次发送取得并保留，回执丢失后重试只认回原事实，不新增消息、承接或 Run。受理成功不等 Agent 的唤醒送达。

普通输入的准入预算由装配固定：待交数量与单输入字节数都是正安全整数。待交只计已受理而还没被 Agent 正式接手的普通输入，卡片答复、控制、查询、恢复不占容量。等于上限可以受理，超过返回受限并带资源名与上限。访问裁定与原操作认回先于容量判断：已受理的原操作在队列满时仍可认回。读计数、判预算与入列在同一修订的原子提交里成立；历史输入超过新预算时仍保管。

系统来源的输入（第一种是后台工具执行的结局）不经对外入口，由 Session 在一次解释提交里自己受理：它和引起它的那条事实写在同一次提交里，重放按来源事实的身份认回原输入。它跳过 before-admit 组，不占普通输入的待交预算；只由它触发的 Run 走系统的可信入口，不要求登录有效。受理之后，排队与承接的规则和普通输入完全相同，不按来源另设优先级。

系统来源的输入里有一类不叫醒：人对一项后台调用的停止提醒，与被单独停止过的调用的结局。它照常进待处理视图。有未终结的 Run 时它照常交入；没有时它留在待处理里，随下一个 Run 的第一批交入。它不能单独使会话开始一轮。它是已受理而没有承接的输入，计入未结工作：挡自动归档，归档时和别的待处理输入一样被取消。叫不叫醒、是不是后台结局，是输入在受理时定下的属性，随输入活着：输入在待处理里或括号开着时都保留，被取走与失败归还都不改。

分流：普通消息按受理顺序进待处理视图；卡片答复认回原卡片，扩展发的卡片回原扩展的等待，工具内部的 Ask 回该工具的原等待，互不交换接续位置；控制不进队列；系统业务输入交原流程。队列由受理的输入扣除可靠承接与取消资格的事实派生，不另存决定资格的源。

受理流水线在 `accept` 提交之前运行 before-admit 组（用途提醒、内容型斜杠命令展开、用户提示提交的 hook），之后运行 after-admit 组（分流回执、推进条件触发），后一组不改已提交的内容，也不是第二次提交。槽的列表取不到时，需要经 before-admit 的输入不受理，答不可用；只有装配声明本部署没有命令域与 hooks 时槽列表才为空。同一原提交重复进入时 before-admit 会再运行，所以各槽要么没有外部副作用，要么按原提交身份幂等。用途跑题提醒在受理前，不保存被拦的正文；确认后是新请求。失效的斜杠命令明确拒绝，不降为普通消息。

已受理的普通输入由 Session 按到达顺序交入本会话未终结的 Run，没有未终结 Run 时先开 Run；不按来源另设优先级。读取、收到唤醒、向模型发请求都不是承接。承接由 Agent 的输入水位线定出确定的批界，Session 读到承接事件后保存批次、顺序与所属 Run 并解除待处理资格，不重选批界；每个输入至多一次有效承接。交入被 Agent 的消息准入拒收时，该输入失去待处理资格并向用户显示原因，Run 继续；首条输入被拒收时 Run 以失败收束，其余输入留给下一个 Run。

### 输入何时进模型视图

一条输入的消息在一步取走它的那一刻进入模型视图，位置就是取走的位置。受理时写下的输入消息（后面紧跟着它的 `intake.routed`）是给人看的记录，不进模型视图。

Agent 的一步取走一批非空的输入时，这一步的开始提交在同一事务里带上会话的送达：`recordMessage` 的送达值，参与种类是 `delivered`，每条输入写一条 `message.delivered`，带这条输入的原消息。会话拒绝送达时整个提交不成立，这一步不开始。因此模型在一次请求里看到一条输入，当且仅当这一轮的某一步已经取走了它；一次请求的末尾是新送达的输入或工具结果，不是模型自己写完的回复。

快照的 `deliveredTail` 记最后一条助手回复之后送达过的输入。取走时只送达不在其中的输入：失败归还的输入在下一轮被取走时，中间没有隔着助手回复就不重复送达，隔着了就再送达一次，排在那条回复之后。一批里一条都不用送达时，这一步不带会话命令。

取走的记账不变：`run.batch-taken`、括号与归还仍由 Session 读到承接事件后写。压缩的保护集里，一条还活着的输入指向它最近的一条送达条目；还没有送达过的待处理输入没有模型可见消息，不列。

开轮时待处理里有几条输入的，Agent 先取走首条，其余由 Session 随后交入，在下一步被取走并送达。这一轮向模型发请求的次数等于取走的批数。

### 输入的括号

一批输入被一轮取走，是开一个括号。括号在这一条成立时关上：取走之后，有一条完整的助手回复进了日志。取走是租出，不是消费。

| 这一轮怎样终结 | 括号还开着的输入                                     | 之后要不要自动开下一轮         |
| -------------- | ---------------------------------------------------- | ------------------------------ |
| 完成           | 不会有：有输入没回答就不能完成                       | 还有能叫醒的待处理输入就自动开 |
| 被取消         | 随取消一起了结，不回到待处理。人说了停，不替人再跑   | 还有能叫醒的待处理输入就自动开 |
| 失败           | 在终结的同一次提交里回到待处理的队头，保持原来的先后 | 不自动开。会话等人             |

### 等人

一轮失败之后会话进入「等人」。这时不论待处理里有什么，都不开新的一轮：失败之前重试的预算已经用完，再自动跑一次没有新的依据。

「等人」只有两个出口，都是人的决定：人发来一条新的输入；人对失败的那一轮发「重试」。解除之后，下一轮照常由 Session 开，按先后把待处理的输入一起带上，归还的在前，新发的在后，不用重新输入。

「重试」只解除等待，不是一条输入，也不由系统自己发。它点名失败的那一轮：那一轮已经不是会话在等的那一轮时答找不到。待处理里没有能叫醒的输入时它不被受理：下一轮开不起来，受理了也不会开轮。这种情形出现在一轮先给出过完整的回复、之后才失败的时候，人要让它接着做就发一条新消息。

能不能开新的一轮只在一处判。提交之后的触发、启动时的扫描、显式的开轮命令，问的都是这同一个判定。

会话在不在等人、等的是哪一轮、还有几条待处理，也只在一处算，「重试」认失败的那一轮用的是同一个算法。会话的工作面为此有一个窄的读口，只答这三样与那一轮的 execution，先判主体能不能读这个会话，不把会话的状态交出去。客户端经协议的「读等人」读到它们，连同这一轮失败的成因。

### 请求队列

发消息的请求到了服务端，先落进它所在会话的队列，再由这个会话的排空者按先后交给会话受理。受理进了会话日志，调用才答成功。

- 每个会话一条队，键是（租户、会话）。会话之间互不相干：会话甲的库在忙，只有甲的请求在等。
- 队列里是「送到了、还没有结局」的请求。它们不是会话里的事实，会话日志不记它们。
- 一条请求有了结局就离开队列，队列不留它。结局是受理成功，或者一个确定的拒绝。之后问「这条消息怎样了」，答案在会话日志里。
- 队列落盘。进了队列的请求在进程重启之后还在，重启后接着受理。
- 队列不是调度器，不在会话之间排先后。队列不是存储，不替会话日志保存任何东西。

一条请求在队列里存这些：租户文本、会话、请求标识、输入标识、消息的 JSON 文本、登录的编号、它在本会话里的序号。入队之前先做两件不读存储的事：消息要解得出来，登录要换得出目标租户里的主体。有一件不过，请求就不入队，调用按原样作答。排空时用队列里存的租户与登录重新签发主体，再受理。一条请求还在排队时，发它的登录被注销了，这条请求照样受理。发消息与注销登录是同一个人先后表达的两个意图，各自成立，互不相干；注销只决定之后还能不能用这个登录再发，不追回已经发出的消息。

#### 全化表

一条请求只有两个状态：不在队列里，在队列里。

| 操作                     | 不在队列里                                                                         | 在队列里                                                                                               |
| ------------------------ | ---------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| 入队（同标识、内容相同） | 追加到本会话队尾，等它的结局。本会话的队列已满时答 `limited`，`limit` 是队列的上限 | 认回同一条：不再追加，等同一个结局                                                                     |
| 入队（同标识、内容不同） | 追加。它以前有没有被受理过，由会话按原来的规矩判                                   | 答 `conflict`，不追加                                                                                  |
| 取队头去受理             | 无事可做                                                                           | 受理有了结局：记下它离开队列，把答复交给等着的调用。受理要再取：留在队头，按退避再取。哪些算再取见表下 |
| 查询                     | 问会话日志                                                                         | 答 `unknown`                                                                                           |

「内容相同」比的是输入标识、消息的 JSON 文本与登录。

留不留在队头按成因分，不按对外的答复分。再取的只有两类：

- 等一等会好的：会话答 `unavailable`；会话此刻不在树上；签发主体暂不可用。
- 结果不知道的：会话答 `commit-unknown`；调用开始之后抛出。

其余每一种都是结局，带着它对外的答复离开队列：成功，以及任何别的失败。这包括对外答 `basis-unavailable` 的失败，例如会话答 `quarantined`，或者答一个不在 `send-input` 结果集里的种类。它们不会自己好，留在队头只会挡住这个会话后面的消息。

受理仍旧按请求的标识恰好一次。同一条请求被再取一次时，会话按原来的那次操作认回，答成功并标明是认回的，不产生第二条消息。这种情形出现在上一次受理的提交成了、记「离开」之前进程没了的时候。这一条靠会话原有的规矩，队列不另做。

队列永远守住的六条性质是「不变式」一节的 RQ-1 到 RQ-6。

#### 落在哪

队列在 `session-access` 里。排空一条请求要用登录在目标租户里的主体，这是接入插件的知识；入口与会话核心都不认识队列。

落盘用一份只追加的日志文件，在存储的线程池之外。全部会话共用这一份文件，内存里按会话分开。文件在一个端口（`RequestJournal`）后面，换成别的实现时别处不动。队列空了的时候文件截空，所以进程不重启文件也不会一直长。放在线程池之外的理由：系统范围的库没有自己的线程名额，和租户的库抢同一批。名额全被占着的时候，入队本身会失败，而这正是队列要治的情形。

别的提交类操作（建会话、取消一轮、停一个调用、重试）不进队列。

### Run 与推进资格

Run 层是 `none → active → completed | failed | cancelled`，终态不可反转，每个 Run 至多一次有效终结。attempt 层只在 active 里：授予、推进、等待、交还或被取代，再授予。等待不是 Run 的状态。Run 与 Agent 的执行一一对应，attempt 与执行的挂接一一对应；换代与恢复沿同一个执行。attempt 的序号严格递增，来自持久的开始事实，不靠数历史条目。

同一会话至多一个未终结的 Run，同一 Run 至多一个有效的推进者。新 Run 要有至少一条能叫醒的待处理输入、没有未终结 Run、入口准入满足；只有不叫醒的输入时不开 Run，无输入不造空 Run，已有 Run 接续或等待时不另造。交互入口的新 Run 要确认登录有效，同一 Run 的恢复不重过登录门，也不因登录到期取消已经推进的工作；后台与系统触发按各自的身份契约，不扩大登录条件。

新 Run 分两次提交，顺序固定：先提交开始 Run 与首个 attempt，不扣任何输入的待处理资格；再向 Agent 发起执行，带首条输入。两次提交不合并。开始 Run 的提交遇到会过去的失败（前一个执行还没解释完、历史读不到；修订已变）时，按推进的退避等一档，再读快照、再判能不能开、再提交；退避用完记诊断，待处理的输入留给恢复扫描。两次之间崩溃，按原操作身份重放发起，Agent 按操作身份认回原受理，不新建执行身份。核对失败（推进资格已被取代）就停下交恢复；Agent 忙就等它的终态事件后重试；不可用则退避。发起被确定地拒绝（准入拒收或驱动被拒）时，执行不创建，Session 以这次拒绝为耐久依据提交有界收束，终态为失败。

新 attempt 生效后，旧 attempt 不能追加输入承接、发起调用或提交推进事实。资格要在实际发起与提交的边界有效，不是创建时检查一次。旧执行迟到的结果与费用仍按原调用身份保存，不算旧推进者越权。晚到的参加提交被判冲突，晚到的保管与处理交接、结果接收照常提交，晚到的 Agent 事件照常按事件身份写入并保留实际关联，晚到的重装与接管因预期过期而被拒。

推进命令（接管、重装、交还、收束）的乐观并发只比 Run 层的修订，不比整份快照的修订，所以无关的提交不会让有界收束一直重试到放弃。每个推进命令的预期修订必填。

接管（claim）分两步：先提交，核对旧 attempt 已交还或可信排除，授予新 attempt，序号加一；再向 Agent 接续，Agent 的条件提交里 Session 作为参加者只读核对。接续失败不撤销接管的那次提交：新 attempt 已是当前资格，由同一恢复者或下一次扫描用同一推进资格依据重试，撤销会让序号回退。谁读到当前推进并能出示它的证据，谁就能继续，不必是发起接管的同一进程。同一候选重复的重装认回原回执，同标识不同候选答冲突，不同候选且预期过期答已变。

重装先在不写任何条目的情况下备好候选并取得 Agent 的交接证明；候选不合法、交接被拒或不可用时不写任何事实，原采用仍合法则继续，不合法则报告不可用，不换定义标识，不以空采用推进。原采用的旧推进能配合时先交还，不能配合时撤除并入接管。重装成立后新采用只影响还没开始的经过，原调用、等待、卡片保留。候选等于当前采用时不写采用变化。

Session 不保存接续值、检查点或任何 Agent 的工作状态；恢复需要接续数据时读 Agent 的执行记录。

### 与 Agent 的同日志参加与解释

Agent 经它的日志提供者写执行记录，Session 拥有会话日志；两本账在同一个事务域，提供者之间不另建事件副本的传输协议。Session 参加 Agent 的提交：四种交接（消息、上下文转换、保管、处理）在同一次提交里由 Session 共同保存；打开执行、交入输入、挂接、条件终结做只读核对，核对与发布之间必须复核原修订，不能让提交期间新受理的输入漏出条件终结的守卫。

来源核对：发起执行的来源依据是 Run 开始的回执，必须指向本会话已提交的开始事实，执行等于当前 Run 的执行，首条输入与推进资格依据吻合，Run 未终态；交入输入的来源依据是该输入的受理回执，输入当前有待处理资格，去处是本 Run；挂接的来源依据是该 attempt 的授予回执，普通推进要求它等于当前推进，取消收束只允许该 Run 已被取消、该 attempt 是取消之前最后授予的那一个，这样的挂接只带取消授权，结论只能是已取消。核对不成立响应「冲突」，依据为输入当前去处或当前推进；Agent 把它译成被拒，恢复者停止并交恢复，不按已变重读重试。

条件终结只读核对待交输入：已受理而还没交入的输入非空时响应冲突，推进协调补交后 Agent 重新求值；Run 已是被取消终态时响应冲突，依据为取消，Agent 以已保存的取消依据再次终结，核对结论只能是已取消。输入已被 Agent 取走而解释还没跟上时，交入回执的提交先答不可用，等解释跟上；这是两次提交允许的交错，不是遗漏。

保管与处理两种交接、以及生产方回报的执行事实，都要求所涉调用的绑定已在会话里。Session 判这类提交时读所涉执行里还没解释的事实；绑定登记在那里，就先答不可用，等解释跟上，不答非法。还没解释的事实里也没有这个绑定，才答非法。

Agent 的事实先由 Agent 的提交保存；Session 随后读同一日志里的事件正文与快照，经纯函数决定另一次解释提交，把承接、调用登记、等待、结束等后果、解释进度与该次操作的认回答案同批保存。解释提交失败不撤销 Agent 已提交的事实，也不推进持久的解释进度；未知先认回该次 Session 操作。两次提交共用会话日志，不合成一个原子批次。每个派生后果按原执行与事实身份唯一认回；事件进度、真实 head、原来源分别保存；每次读取都核对当前资格、租户与执行，并核对历史上的执行与 Run 的对应，没有对应关系时拒绝推测；日志有缺口按隔离处理。

未解释的日志事实计入未结工作，延迟解释不得造成提前空闲或完成。取消结论的解释要核对原 Run：只有该 Run 已有 Session 提交的被取消终态才认回 Agent 的取消结论，否则拒绝，不写取消终态、解释进度或成功答案；Agent 的事实仍保持已提交。已取消的原 Run 收到迟到事实时，只认回或保留引用，不反转终态，不改后继 Run、推进或等待。

解释提交遇到瞬时失败（不可用、已变、重发之后仍未知）时先立即再做，之后按退避再做，不设次数上限，直到提交成功、得到确定的答复或插件停止。确定的拒绝只记日志，不重试。结果未知时用同一操作身份重发同一通道的提交来认回，按操作查询认不回解释提交。后果没有判出的事件在该处停下，不当成别的东西提交。解释插件启动时不扫存储：漏掉的事件由同一执行的下一个事件带动解释，还没解释完的部分由已保存的解释进度与执行事件之间的差距记着。

模型与工具两条已收条目通道的解读进度，除了通道里的序号，还保存本批最后一项在执行条目里的位置，与后果同批写下。每一轮只从这个位置往后读；一个结果是不是转过后台的调用的结局，按原消费点查它的已收条目，不扫整条通道。每轮的读取量只取决于新增的条目。

Agent 日志提供者按租户与执行读执行索引，把调用交给该执行所属会话的日志；点名一个执行的材料保管同样按该执行路由，写进该会话。没有 Run 启动过的执行与别的租户的执行得到同一个拒绝答复，且不写任何东西。执行索引读不到答不可用，不答拒绝。不带执行的材料保管没有可路由的会话，答不可用且不写。每次成功写入之后只发一条不带事实的唤醒事件。

### 接手与恢复

Session 把一轮交给 Agent 之后，会话读到 Agent 的受理，就当这一轮已经交出，不再重发。这份「读到过」只在内存里，不是事实源，不能因为它没记上就重发：受理之后 Agent 可能已经取走输入，同日志解释还没有跟上。重启之后从日志出发，照原操作身份再交出一次，由 Agent 按操作身份认回原来的受理。

重新交出被受理之后，立刻做一次接手检查：读执行记录，问受理它的活体是否还在。交出本身可能被打断，Agent 写下了受理而 Session 没读到回答，进程就没了；原来的受理把推进交给了当时的活体，换了活体之后这次工作只经接手检查与新的执行尝试继续。推进资格已归后一次尝试的一轮也交给接手检查，由它认回接管再接续，而不是只记诊断就停。会话接手时问到执行已经终结而这一轮仍开着，回答的一侧补发一次唤醒，使会话读到结束事实。

恢复协调对一个会话的权威读逐类先查后做，查不到不当作不存在：

| 读到                                             | 先查                       | 做                                                                                                         |
| ------------------------------------------------ | -------------------------- | ---------------------------------------------------------------------------------------------------------- |
| 有未决的操作                                     | 每项按操作身份认回         | 已提交交回原协调器继续；未提交由原发起者决定是否重试；未知保留并报告                                       |
| 已授予而 Agent 还没受理                          | 发起的出站操作身份         | Agent 尚无记录就以同一身份重放发起；已受理就接手检查，交入记录没记上也继续                                 |
| 有待交的输入                                     | 每个输入的交入身份         | 按到达顺序以同一输入标识补交                                                                               |
| 推进者的挂接仍活着                               | 无                         | 等 Agent 推进，读事件，补交待交输入                                                                        |
| 挂接已交还或被取代                               | 交还的身份                 | 认回或提交交还，进入下一行                                                                                 |
| 没有推进者                                       | 读执行记录                 | 先接管再接续；挂接仍活着时只有持接管资格并有宿主的失联判断才接管，没有依据就等 Agent，不以失联判断代替资格 |
| 执行已结束                                       | 同日志的结束事实           | 经解释提交按 Agent 的结论写终态；Session 未提交取消时 Agent 的取消结论被拒                                 |
| 执行记录或精确采用持续读不到                     | 按策略重试                 | 超过上限后有界收束为失败，写明未收尾的效果；Agent 尚无该执行的记录不算不可解释                             |
| 结果已报告而保管与处理都空                       | 生产者原调用               | 合格保管者保管；Agent 记录已按保留策略删除时由 Session 单方保管；交付责任的解除由生产者自己做              |
| 控制在传播中                                     | 原控制操作、待核对的生产者 | 交控制传播协调，不重发原调用                                                                               |
| 各类任务（初始化、已分流输入、级联、作用域释放） | 各拥有者                   | 重新驱动负责方；拥有者不可用就保留任务，退避                                                               |

提交未知时双方都不把未知改写为失败或成功，不发出依赖这次提交的外部效果（交付责任解除、发起执行、控制传播、通知）；认回为已提交才继续，为未提交就用同一身份重试；Session 为提交方的操作认回超过策略上限仍未知时，保留在未决里并报告维护者，不清理任何提交。参加提交的未知由提交方认回，Session 不列入自己的未决。

受理之后、唤醒推进之前崩溃，没有输入因通知丢失而停留：恢复扫描读出有能叫醒的待处理输入的会话，开 Run、重放发起、补交输入都按原操作身份，重复触发被认回。会话读到有未终结的 Run 而没有活体、没有人接手时，不声称空闲或完成。

### 等待与结果交接

等待关联原工作、开始依据、目标调用或卡片、原消费位置与交付责任，不另建独立的等待对象。释放 Agent 的计算不解除这些关联，也不取消独立的 Model 或 Tool；查询不到句柄或执行状态时保持未知，不自动重发。恢复所见与处置：原调用仍在执行，重取合法访问关系，继续原等待；已收场未交接，从生产侧取回原结果回原消费位置；已可靠交接而处理未完成，从消费侧内容或有效引用继续，不向已确认的模型重新领全文；查询故障保持未知；原执行确实失去连续性，交 Model 或 Tool 自己的契约，仍回原用途；原 Run 已终态或原调用不再等待，只完成允许的历史、交付与结算。

转了后台的调用，结局按下面的路回到会话：

1. Tool 把占位与最终结果推给原消费位置，由 Agent 的结果接收方保管；Tool 不认识 Session。
2. Session 解释占位的保管记录，记下这次调用已转后台；解释最终结果的保管记录时，在同一次提交里记下它已结算，并按[后台结果投递资格](../../.meta_harness/design/ubiquitous_language/terms/interaction-and-dispatch.md#ul-background-result-eligibility--后台结果投递资格--background-result-eligibility)决定要不要把它受理成一条输入。
3. 资格在：受理一条系统来源的输入，消息是 `SystemReminderMessage`，来源标记是后台工具执行，正文是这次调用的短号与标签、终局、效果与结果的模型可见内容，卸载的正文只给引用与取回办法。输入身份由（调用，结果版本）派生，同一结果至多成为一条输入。这次调用被单独停止过时，这条输入不叫醒，正文写明谁停的。资格不在：只记结算，结果照存、照样查得到。

资格从快照派生，不另存：会话没有归档，资格就在。单独停止这次调用不撤销它，取消原 Run 也不撤销它。占位留在历史原位，不改写；结局只在承接时追加到历史末尾。转了后台而还没结算的调用计入未结工作，挡自动归档，不挡 Run 完成。

主流程、扩展、压缩与 Run 外的消费位置分开。Run 外的调用保留真实的调用身份与对应的会话消费者，不伪造 Run 或 attempt，不借用碰巧活跃的 Run，不因接续重新计费。不可用的替换件沿原动作、工具身份与消费位置承接。

内容或有效可恢复引用、原归属、原位置与后续责任可靠保存之后，或原消费的处理已完成并保存了必要的完成事实之后，生产侧的责任才解除。交接与解除要可恢复地一致，不能双方都认为对方负责；展示、观察、收到通知、开始处理都不等于可靠消费。解除的确认由生产者自己做，结果接收方只返回已保存；同一原调用、同一结果版本、同一消费位置的重复确认返回原确认。模型收场后由当前合法消费者按 Model 契约确认，确认、清理、费用各自可查；Tool 不自动采用这份确认。保管成功而生产者确认未知时，保管继续，按原操作查询，不重新领取已清理的全文。

人的答复等待可以释放 Agent 的计算。卡片原事实保留，服务超时、实例释放与时间流逝不制造答复，不结束等待。扩展同批的卡片全部处理后才解除批次阻塞并回原扩展位置；人明确不回答的卡片返回没有答案，且不授予依赖批准的动作；工具内部的 Ask 只回该工具的原等待。会话日志里不另造第二个有效的卡片决定，卡片记录只引用并承接原决定。单次授权只覆盖明确批准的动作，整批才覆盖整批；消费后或所属 Run 终态后不得再用；撤销归档不复活被取消的卡片或已消费的许可；全局租户授权写租户权限设置，由拥有者校验上界。

### 终态、控制与取消

Run 的终态只有完成、失败、被取消。完成要先过原工作的条件与适用的终态前扩展，后置扩展不得撤销；队列空、模型无动作、runtime 退出、非常态上交都不自动证明完成。写终态的那一笔提交先为该 Run 里每个未答的调用写一条工具消息，再写终态；这条消息陈述发起方知道的事实（调用的结果不在对话里、Run 因何结束、工具可能已经产生效果），不是工具的结果，来源标记与终态条目相同。归约遇到还有未答调用的终态判历史不合法，所以后继 Run 的请求读到的历史里每个调用都有工具消息。

终态之后不新增原 Run 的 attempt、输入承接、调用或外部动作。已发的调用与未结费用可迟到保存，迟到的结果不成为消息；仍具合法投递资格的后台结果在未归档的会话按输入规则交后继工作，其中不叫醒的不单独开后继 Run，原 Run 不复活。已因归档取消了业务资格的调用，其结果在撤销归档后也不自动入队或造后继 Run。

控制先保存目标、发起主体、原因、级别与意图，随后按持久关联撤资格并传播，不依赖旧 Agent 句柄转发；受理不冒充实际生效或物理停止。单调用控制的发起主体由调用方类别给出：受理方是用户，协调方是 agent，维护方是系统；调用方不能自报。原因由调用方给，可以没有。控制的最小对接：Run 取消用该 Run 的身份，单调用控制用原调用身份，这一次操作用提交身份；成功是意图已保存，Run 取消生效时同批记被取消终态并撤销新发起资格；与已生效的终态冲突时拒绝并带回已生效的终态；未知按原提交身份查询，同身份重试返回原结果，同身份带不同目标或种类则拒绝。格式不合法的控制命令先于任何查找被拒，答复不泄露已有什么，也不保存任何事实。

控制送到调用当前的等待者。停一个转了后台的调用，Session 凭调用引用直接向 Tool 提交 `stop`。用户提的停止，在同一次提交里受理一条停止提醒：消息是 `SystemReminderMessage`，正文是这次调用的短号与标签、谁停的、原因，并写明停止只是已请求；它是不叫醒的输入。一项后台调用至多受理一次停止：它已经有停止时，再来的停止不论谁提的，都答原来那一次，不另留提醒；提醒的输入身份由调用派生。agent 提的停止与归档的撤回不受理提醒；转后台只对还在等待里的前台调用有意义，经 Agent 送达，调用已在后台时答复带回已成立的关系；归档对每个转了后台而没有结算的调用直接提交 `withdraw(all)`。直接提交的端口由 Session 声明，接口只说「按调用引用控制一次调用」，`session-adapters` 用 Tool 的命令实现。

本会话的后台调用只有一个查询，命令行、界面与给 agent 的工具都用它。一项后台调用是日志里记了已转后台而没有记已结算的一次工具调用。它的短号、标签、来源、转后台的时刻、停止的发起主体与原因取自会话日志。它的执行状态与控制的进度在读的时候经 Session 声明的端口向 Tool 现问，接口只说「按调用引用读一次调用的状态」；Session 不保存也不推断它。问不到时这一项的状态是未知，不显示成在跑、已停或不存在。停止的进度只有已请求、已受理、已证实停下三种，各自可辨。短号在调用转后台的那次提交里定下：`b` 加它在本会话转后台的先后，从 1 起，不复用。标签随占位的保管记录进来，Session 照抄，不解释。按短号读一项时，不是本会话的、别的租户的与不存在的，答复相同。

传播范围：单次模型或工具，只指定原调用；Run 取消，当前推进资格、该 Run 的模型与前台工具，后台、子会话与无关的 Run 外调用不自动跟随；仅替换 Agent，撤旧推进、接续同一 Run，原 Model 与 Tool 不因旧句柄销毁而停止；会话归档，原业务推进与等待、未承接的任务、全部关联的在途调用以及子会话级联。取消一旦生效就记被取消终态，优雅或强制只影响停止有多急，不改变终态时点；治理方继续跟踪真实收场，没有 Agent 时也继续，未收尾的外部效果保持未知，成功、失败、未知如实保存。

取消与受理、取消与条件终结、取消与换代的竞争按权威的提交顺序裁定，不按时间：取消先成立，之后的接管与重装被拒，输入照常取得下一个 Run 的待处理资格，归档先成立则新输入被拒；受理先于取消，输入保留待处理资格，归档在同批撤销资格并记取消范围；条件终结先于取消且 Agent 执行已结束时，取消回答终态并带回既有终态，若 Session 还没解释结束事实则取消照常提交，之后读到的结束事实只认回；取消已提交而没有活体挂接时，控制仍送到 Agent 的长期控制入口，受理不依赖挂接，新挂接读原取消意图以取消授权收束。任何顺序下只有一个终态，取消之后没有新授予且存活的推进资格。

控制的对账进度只有在原控制的传播、生产者核对与原责任交接都已对账之后才算完成；传播或责任仍未知时保持待对账，按原身份重放，超过策略上限则停在传播中并报告，不假装完成。插队保存共同的加急消息、处置决定、占位与提醒，已到的响应与已发生的效果尽量保留，原 Run 不终结；加急消息作为紧急输入交给原 execution，释放前台等待的控制由 Agent 随这次交付发出，Session 不另发；插队选中的生产者在 Agent 证实释放，或这次调用已收场、已转后台时对账；人工等待按主动插队记为明确拒绝，不伪造用户的答案或授权；重复的同次控制不重复插消息，独立的多次插队各有原提交。插队到达时会话没有未终结的 Run，这条输入按普通输入受理，答复标明它没有插到任何一轮。工具转后台沿工具拥有者的许可与转换契约，控制受理不表示转换完成，转换不建立第二次执行、不释放并发名额，后台结果沿原消费契约交回。

### 归档与作用域释放

归档的确认依赖业务取消、队列资格取消与后续处置责任成立，不等独立执行的物理停止。归档的答复带这次收起的 Run 与后台调用的数目，不声称执行已经停下。同批终结仍未结束的原 Run 为被取消，归档条目只引用这个唯一终态；已成立的完成或失败保持；没有原 Run 时不补造 Run 或终态。新任务与归档竞争只能是先受理后因归档取消，或明确拒绝，不得无痕丢失，也不得归档后仍保持待执行资格。归档后拒绝新任务，迟到的结果与费用保存原归属但不入任务队列；归档不删除历史、会话授权、工作区或实际费用。

会话关系的两端属于同一个租户，按访问身份的租户查找，任一端不存在就答被拒；级联按父会话的租户找子会话。子会话的级联与未完成的处置要可恢复，每个子方一个固定的子操作身份，重放幂等；独立交接的子会话不级联；子方被拒时任务与原因保留，不伪装级联完成；子方提交未知时以同一身份再驱动。

归档的同一次提交产生作用域释放任务，由维护者身份凭装配注入的恢复授权请求执行环境释放；读回事实是已释放作用域的耐久账本，执行环境不保存这份账本。读回按五类处置：已释放（两路枚举完整、全部资源已停、原获取责任已结清）才解除任务；待续、不可用、未获授权保留任务（未获授权要报告维护拥有者，不改用会话用户的身份重试）；不支持的部分记录并交人；枚举失败表示资源未知，不表示没有。释放结果未知时任务状态为未知，以同一操作身份重试。执行环境提供者换代时，释放插件按页重新释放已归档会话的作用域，每个作用域沿原任务身份，重复释放认回。逻辑归档在提交时已成立，不等物理全停；对人的时间线只记「已发起释放」与读回结果。

撤销归档回到休眠（冻结的会话回到冻结），从撤销时刻重新计空闲，不恢复被取消的任务、Run、调用或卡片，不顺带恢复子会话；撤销归档铸造新代次的作用域，新代次不迁移旧作用域的注册；原取消调用迟到的结果仍不自动入队，需要继续就显式提交新任务。旧的迟到重装或原调用不能重新启动已取消的工作。

Runtime Context 持有者的恢复只认会话日志。作用域对应的会话与代次一经铸造不变，查得的答案可以在进程内保存；作用域是否已经结束会变，不保存，每次读绑定。只有绑定显示作用域未结束时，才按空材料恢复一个还没有记录的新作用域。已结束答已结束，不在绑定里或读不到答不可用；空材料不用于会话没有显示为开着的作用域。

### 模式、自动归档与冻结

三轴模式（权限处理、执行环境、协作模式）分别保存并可变化，不扩大结构化权限。本会话租户可以改模式，改的资格在提交边界核对；Agent 不能经直接入口、也不能经未获人授权的工具或委托改模式，要改必须走人工介入，由人显式授权；代办模型切换不授予改模式的资格。创建时的默认只初始化，当前值跨恢复保留，专用入口已有有效必填初值时不能用通用默认补缺。模型可读的模式变化按 Context 协议感知，已固定的请求不回写。

自动归档默认关闭，只在显式启用、未豁免、符合连续空闲条件与时限时执行；没有有效的显式启用依据就不得自动归档。启用开关与时限取自本租户的合法设置，没有时限时不以旧默认补值。常驻标记只允许主会话，由具会话管理资格的用户维护自己的会话，子会话设常驻必须拒绝，不静默清除标记或改变关系，也不能用非法组合阻止父方的归档级联。空闲判断覆盖本会话与级联相关子会话的未终结 Run、待处理任务、在途的 Model 与 Tool：任何等待、后台工具或 Run 外调用使条件不成立，查看历史不算开展工作；新工作与到期检查竞争时重新核对。时钟采样失败不用系统时间补默认，墙钟差本身不证明连续空闲；来源无法证明离线区间、时钟回拨或有未决工作时观察为未知，普通重启不重置已确认的起点，成员失效不暂停或清零计时。开启自动归档或解除常驻使用原来已确认的连续空闲，操作前提示可能立即归档，不重置起点，仍要重新核对全部条件。

常驻工具是 Agent 不经发现即可调用的工具。会话在采用点（初始化、新 Run 开始、显式重装）纳入常驻工具，每项在同一次提交里写一次，常驻集合只增不减；会话当前记下的登记键取自最近一条带键对的采用记录。冻结的判定只在新 Run 或显式重装的采用点由 Tool 的公开纯函数给出，作为待采用材料的一部分到达；工具暂时缺席、状态未知或被撤权时按 Tool 契约用同形不可用件，不给冻结判定。开始 Run 或重装返回冻结且不提交之后，推进触发以同一判定提交冻结。冻结不可逆，每个会话至多一次；冻结的会话不开始新 Run、不采用新版本，进行中的 Run 不被取消，按原规则收场，接管照常；冻结的会话里每个已受理的输入都有去处：没有未终结 Run 时拒绝新输入，冻结与冻结后 Run 终态的提交同批解除余下的待处理资格；冻结独立于归档，冻结的会话可以手动归档、参加自动归档裁定，撤销归档后仍是冻结。引用查询只算未归档的会话（冻结而未归档的算引用），不返回定义正文，读不到时答不可用，不返回空页冒充没有引用。

### 模型选择

会话保存当前选中的模型路由名、初始采用依据与切换事实；模型档案、合法集合、凭据与实际请求归 Model。当前选择与每次实际调用分别可查，上一次调用的记录不因切换改写，不用最近的实际调用反推会话选择。用户切换要有对应的会话操作资格与当前合法的目标，Agent 只代表明确的合法用户指令代办，不能自主换名；缺凭据的合法目标仍可选并说明暂时无法调用，非法目标明确拒绝且原选择不变。选择变更条目、当前值与原操作回执共同提交；确认之后的后续请求采用新选择，下一次请求失败不撤销切换；切换本身不产生新 Run 或 attempt，不替换定义，不重发或打断在途调用。还没固定的请求按当前选择重新求有效模型；已固定或已发的请求保持原模型、参数与内容；单独中断要走明确的控制。经压缩仍无法满足输入条件时按原工作规则失败，选择与历史保留，不暗换其他模型。

### 权限配值与待办

会话逐权限配值是独立于模式、Agent 作者上界与人的持续许可的当前声明，保存在会话日志里，当前集合由归约得出，稳定键在会话内唯一，每次设值、替换、清除或权限模式变更推进权限修订，别的工作不推进。写入需要专属的写资格，普通变更的访问允许或非空的授权引用不能替代；受保护的写绑定原操作与完整命令，不能把已结束的权限读取当作后续写入的租约。设值必须匹配精确的定义与稳定键并落在值域内，定义已撤下时清除仍可做。权限修订是当前性的依据，不是可长期使用的许可：读取之后发生修改时，使用这次读取的提交必须在同一事务里核对当前修订；定义变化时不忽略旧配值，也不返回空，不能可靠匹配就答不可用。从完整原批次重建权限状态只复用原归约，不重新授权，不改写历史；缺少权限字段的旧快照只能经重建取得，不在普通读取里补空。

待办是会话日志上的三类事实（添加、完成、移除），跨 Run 与 Agent 保留，归档、压缩与认回不清除它；它不进未结工作与恢复任务，不启动或唤醒 Agent。添加保存非空白且有字节上限的原文本，不裁剪；移除留下墓碑，之后的完成与移除答找不到且不泄露文本；不提供修改、重开或批量替换。标识由租户、会话与原调用文本确定性地派生，另一个原调用即使同文也是另一条。写入按归档、冻结、初始化中的次序分别拒绝，休眠与活动都可写，不依赖 Run 状态。列表每页重新核权，过滤已移除的并保留添加顺序，游标只含租户、会话、修订与位置四个字段；读不到、缺依赖与会话不存在都不转成空列表。

### 读取与投影

每次读取、分页、导出与按原条目的查询都检查当前资格。游标绑定租户、会话、来源身份、过滤条件、固定的读取上界与续读位置，调用方不能改游标扩大范围；错域、失效或无法核验的游标明确拒绝；读取期间新追加的只在新一轮遍历里出现。分页按确定的提交位置续读并保存扫描进度，不用最后一个可见条目代替扫描位置，也不把权限过滤造成的空页误判成历史结束；权限撤回后不继续泄漏旧页。历史的读取带固定的会话修订号上界：同一轮的每一页上界相同，历史条目与状态帧用同一条修订轴，读者可据此判断手里的历史新不新。游标的签名只认当前的键，轮换后旧签名无效，键来源不可读或已卸载时答不可用，换代前在途的校验在完成时复核当前键。游标签名覆盖固定的协议域前缀，再加载荷：别的协议的签名、只签载荷的同钥签名，都不能验作会话游标。引用查询的游标还绑定租户目录的修订与常驻键，换了修订或换了键的游标无效，所以逐页续读时先注册的租户不会被跳过。

每份投影声明来源、确定性的计算规则、覆盖到的完整提交位置、计算版本与失效条件；应用同一提交一次或重复一次得到同一结果；缺批、来源不符、未知且不能证明无关的事件类型、计算版本不兼容时停止相应投影并报告缺项，不把未解释的事实当作无待办、无 Run 或完成消费。治理决策必须用与权威尾部一致的治理状态；展示投影可以落后并公开进度，但不能用落后数据授予推进、拒绝必要控制或报告确定的空队列。恢复先验证检查点的来源、输入范围与计算版本再重算尾段，无有效检查点时从日志起点重建；重建只解释事实，不重新调用模型、执行工具、回答卡片或发外部效果。检查点与索引损坏可从权威事实重建；权威日志出现缺口、损坏或未知的提交状态时隔离受影响的会话并保留处置责任，不清空会话、不静默丢弃已提交的尾部；临时、未提交材料的清理不能误删已提交而回执未到的批次。

当前状态、待处理输入与原等待位置有直接可定位的索引，正常推进不全量扫描历史；派生物在变化时维护，请求到达时只读取与采用，热路径上不出现随历史长度增长的读取。分页、检查点恢复、内容读取与导出按实际条目与字节控制资源，不承诺无限容量或固定延迟。时间线的投影合并已提交的历史与在途的增量：日志条目到达后替换同一调用键的在途内容，故障后只可能缺从未展示过的在途片段，恢复后的展示说明缺口，不补造。「未结工作」只有一个计算，供历史持有者交给 Request Context 的下界、条件终结的阻塞依据与空闲裁定共用，三处不会对「还有未结工作」给出不同答案。会话当前状态的内存缓存只是读缓存，存储仍是权威：每次读先读会话的版本（会话日志的尾部与 Agent 的发布计数），只有版本等于缓存条目读取时的版本才用它，否则整份重读。本进程的提交把批次折进已持有的快照，折入的结果带的是存储答过的版本，之后的读仍先核版本。缓存不做访问裁定，调用方各自先裁定。

会话目录有两个读口：没归档的会话，与已归档的会话。任一时刻一个会话恰在其中之一。归档与撤销归档的提交在同一批里更新目录，并记下归档的时刻与方式（人、自动、随父会话）。已归档的读口按归档时刻从新到旧分页，可以按归档时刻的范围、归档方式与标题里的字筛选；读不全时答不全，不答空。

账目真实归因到原调用；有发起的 attempt 或 Run 时记录相应关联与汇总，Run 外按对应的会话消费者；未知的费用继续待结，不当零，观察者与接续不重复收费。日志与遥测能定位原身份与因果，诊断内容按权限、隐私与外传规则筛选，遥测不替代业务持久事实。必要保存不可用时，阻止依赖该保证的新动作并说明影响；局部服务故障按责任限定，兜底优先无副作用，不授权绕过租户边界。

### 会话观察

会话观察回答：登录的人看一个会话，现在正在发生什么。它给出一条帧序列，告诉界面这一轮开始了没有、日志里有没有新的已提交内容、正在生成的那段回复是什么；已提交的内容由读历史给，历史是权威，观察只是进行中的投影。观察只读会话与模型两个领域，不写任何东西，不做授权判断；读日志与问模型都用观察者自己的主体。

建立时先以观察者的主体读一次日志核对资格，会话不存在、标识不合法与被拒的答复逐字段相同，调用方分不出；日志暂时不可得答不可用。帧序列的第一帧是状态帧，或者一帧不发就结束；状态帧有五个字段（当前这一轮的编号或空、日志的修订号、模型调用的阶段、这次调用的发出进度或空、有没有流目标），只有字段有变化才发新的，第一帧一定发。发出进度原样转述模型的调用状态：允许的发出次数、已发出的次数、上一次的成因、下一次不早于何时；观察不另数。对外的协议帧里没有进度时不带这个字段，上一次的成因只带成因名与上游状态码。快照与增量帧的值取自模型公共流的投影；增量的基线对不上就不应用，等下一个快照。被观察者自己中止时结束且不给原因；这是观察者自己的事，不报成日志不可得。

「看哪一次调用」只由日志决定：最近一条 Run 开始之后没有同编号终态，这一轮就在进行；主调用是最近一次登记的主用途、模型类、带引用的调用。「那次调用的流现在怎样」只由模型决定。两条轴独立：定位读日志，流轴订阅模型的公共流。有目标且主调用没换时不问模型；换了目标就收掉旧订阅，之后到的旧帧丢掉并记诊断。目标的流结束、订阅中断、模型撤了观察者的资格、值投影失败，各有确定的去向（回到没有目标并开始刷新，或重新观察，或以被拒、不可用结束），不把读不了的值当成没有内容。

刷新是策略：第一档间隔、每次没有新内容时的退避倍数与上限、连续没有新内容的次数上界、累计等待时长上界，都是装配传入的配置，间隔有底线；用尽时以刷新耗尽结束。间隔到期引起的定位在字段有变化时先发状态帧，再发刷新帧并计一次尝试；通知引起的定位不发刷新帧、不计尝试；观察中的时间不计。通知只是叫醒，不是事实来源：通知的种类集合与读历史的种类来自同一个来源，没有交集的不理会；漏掉、重复、合并都不改变结果，漏掉的由按间隔的刷新补上；标记「有新提交待看」不丢。读日志暂时不可得当作没有新内容，自己的游标不合法就丢掉并从头反向读，别的不合法与被拒按确定的原因结束。有目标在等待再次观察时，提交通知只被处理，不重启正在跑的等待，所以不断到来的提交推不迟下一次订阅；没有目标时，通知本身就是一次定位，定位之后重新开始等待。

### 协议、接入与界面

会话协议 `session/v1` 是纯数据：十六个操作（建会话、查建会话、发输入、插队、查发输入、读历史、读等人、列会话、列已归档的会话、取消一轮、停一个调用、转后台一个调用、列后台调用、重试、归档、撤销归档）与一个观察，每个操作声明身份要求、效果与体上限，提交类并入未知，所有操作都计一次业务访问；信封（版本、消息编号、操作名、登录证明、行事租户）归共同契约。查询类操作本身可能答不出那次提交的结局，所以结果里有未知。读历史的成功体带这一轮读取固定的会话修订号。列会话只读，按固定次序分页，答每页的完整性（读到行数上界时为部分）；资格被拒与会话不存在看不出区别。重试点名失败的那一轮，同一控制标识再发一次答已恢复。插队与发输入进同一条请求队列，用同一个查询认回。列后台调用答每一项的短号、标签、来源、状态与停止。停一个调用可以带原因。归档与撤销归档按控制标识认回。列会话只列没归档的。停一个调用与转后台一个调用的路由在服务端，客户端不分前台后台；回执分开给出受理、停止已证实与未知。列后台调用只读，从快照列出本会话转了后台而没有结算的调用与它们的引用；读一次调用的状态、结果与过程归 Tool 的协议。读等人只读，结果集同读历史；成功体是 `waiting`：会话没有在等人时为空，否则是等的那一轮、待处理的条数（共同契约的计数，线上是 JSON 的非负整数）与成因，成因为空或是成因的种类名加一句可以给人看的诊断（可以为空）。观察的帧只有五种（状态、快照、增量、缺口、刷新），观察自己的结束原因只有刷新耗尽。把一条文字输入做成发输入的用户消息（`userTextMessage`，与它的消息编号 `userMessageId`）也在会话协议里：消息与文本块的标识由输入标识派生（`msg_`、`blk_` 加输入标识 UTF-8 字节的 SHA-256，base64url 不带填充），派生是会话的约定，所有客户端与测试支撑共用这一份，不放进不认识任何领域的共同契约；它用平台的 WebCrypto，所以是异步的。

接入插件把协议挂上登记表，业务规则与结果映射沿会话的原有规矩：只有创建会话用管道给的行事主体，其余操作与观察在消息体里带目标租户，处理函数把登录与目标租户交给身份换主体，被拒或依据不可用就原样作答、不调会话，换主体抛出按依据不可用；会话标识、输入标识、操作身份与登录入口来源的派生文本与入口逐字节相同；创建会话没给定义名时用配置的默认，没配置或不在部署映射里答非法，映射里缺初始模型选择答依据不可用，三者都不调会话；会话失败按固定表映射，提交类调用开始之后抛出答未知，只读类抛出答依据不可用，映射出的结果不在该操作的结果集里时答依据不可用；会话服务、观察、部署映射、会话目录每次调用现取，取不到时需要它的调用答依据不可用、协议不撤下（发消息例外，请求在队列里等）。列会话经接入包自己声明的只读端口，不碰会话的四个面。读等人先经会话的读口得到等人、条数与那一轮的 execution，再经接入包声明的成因端口按 execution 问这一轮的失败成因；成因端口没装、读不到、答没有或抛出时成因答空，读等人照样答，等人与条数读不到才按依据不可用作答。成因的种类取 Agent 失败候选的种类名，诊断只取模型故障的诊断（模型规格写明它是安全的短文本），别的字段一律不放；适配归服务端应用里会话接入的那一行。插件卸载时停排空、再关日志，不再取队头，退避计时全部取消，在途的那一次受理不取消，队列里的请求留在日志里等下次装上。

会话诊断协议 `session-diagnostics/v1` 回答：登录的人读一个会话在某一刻的诊断页。它只有一个操作 `read-session-diagnostics`：登录身份、只读、体上限小、计一次业务访问；没有观察。请求体是首页（租户、会话、游标为空、可选的 Run 过滤、页字节数）或续页（租户、会话、游标）两种形状，两种互斥，空游标不带过滤与页字节，非空游标不带它们。成功体是一页：若干 Run 的诊断（框架、尝试计数、控制、终态与原因、调用登记、Model 调用与逐次派发、Tool 调用、消息计数、事实计数）、续页游标、是否读尽、扫描到的位置、固定的读取上界与缺口表。结果集只有成功、非法、被拒与依据不可用。字段规则写在协议成员里，信封与登录证明归共同契约。

诊断页是投影，不是事实源：历史条目来自 Session 的读历史，Run 的收尾来自 Agent，调用与逐次派发来自 Model，Tool 调用来自 Tool；诊断页逐项带来源，来源缺席、不支持、被拒或读失败都变成带原因的缺口，不改整页结果，也不被写成空。披露的条目种类、一页的 Run 数上限与一个 Run 的调用数上限是插件的设置，三项必须一起给，缺任一项答依据不可用且不调会话；一页字节数的上界同样来自设置，首页超过上界答非法且不调会话。游标由进程内的随机密钥签名，绑定租户与会话，第一页的读取上界在续页里不变，错域、被篡改或别的进程签的游标答非法，续页时再判一次资格。

`session-diagnostics-access` 把协议挂上登记表。四个读口（会话历史、Agent 的收尾、Model 的调用与尝试、Tool 的调用）由本成员声明成需求端口，类型取自各邻域的契约，应用一行来适配；代某个租户读用的主体经 `DiagnosticsPrincipals` 端口换出：被拒或依据不可用就原样作答，抛出按依据不可用，之后不调会话。会话取不到答依据不可用而协议不撤下；Agent、Model、Tool 的读口缺席是该来源的不支持缺口。会话失败只映射成被拒与非法，其余答依据不可用。整页投影完成之后、答复之前再换一次主体：这一次被拒或依据不可用，整页不给。这一次复核到的是端口能判的事（目标租户的账号等于登录的账号），登录在途被吊销时端口照样发主体，所以整页不给只在端口自己拒绝时成立；登录的存活由管道在每次调用开头判。投影的代码和读口的失败到缺口原因的映射原样沿用，只读，不向 Session、Model、Tool 写任何东西。

请求队列的文件日志：记录两种，一行一条 JSON，入队与离开；写进文件的只有点名的字段；打开时重放成还在队列里的请求，丢掉不完整的最后一行，并以写临时文件、落盘、改名的方式重写；追加落盘之后才算成，同时到的合成一次落盘且先后不变；追加失败要把文件截回追加之前的长度，截不回时不再接受追加；队列数到零且没有等着落盘的记录就截空，截空前后任何时刻进程没了，重开得到的都是空队列。

界面模块是客户端树上的一个插件：`session-ui` 的 `./cordis` 入口导出 `sessionUiModule`，它用外壳契约的 `defineUiModule` 造出来，依赖外壳的服务 `shell` 与会话协议的客户端（服务名照客户端装配的取法，是 `protocol:session/v1`）。两样都在时，它往侧栏区放会话列表（标识 `session-list`，次序 0），往页面放对话页（标识 `conversation`，标题「对话」，次序 0，图标名 `conversation`）；协议客户端撤了，两样随作用域撤掉。在列表里选一个会话或新建会话时，它调 `shell.navigate` 把对话页切到前面。两个视图共用一个按租户建的模型：同一个租户只有一个，两个视图都不用时收掉，租户变了换一个新的。外壳给的租户还没有时不发调用，读不懂时对话页如实说出来。根入口只导出模型与两个视图，不带 Cordis 绑定。`./cordis` 入口除模块与客户端服务名外，还导出位置与页面的标识常量 `CONVERSATION_PAGE`、`SESSION_LIST` 和 `SESSION_DOCK`。

对话页开三个[拓展点](../../.meta_harness/design/ubiquitous_language/terms/architecture-core-and-extension.md#ul-extension-point--拓展点--extension-point)，让别的领域往当前会话旁边放自己的界面。都用外壳契约的 `definePoint` 声明，从 `session-ui` 的 `./cordis` 入口导出；共同的规则见[拓展点的共同契约](../../docs/architecture/cross-cutting-concepts.md#拓展点的共同契约)。

| 问题                     | `sessionDock`                                                                            | `sessionSide`                                          |
| ------------------------ | ---------------------------------------------------------------------------------------- | ------------------------------------------------------ |
| 1 叫什么                 | `session.dock`（常量 `SESSION_DOCK`）                                                    | `session.side`（常量 `SESSION_SIDE`）                  |
| 2 哪一棵树               | 客户端                                                                                   | 客户端                                                 |
| 3 能放几项               | 一列，按项上的次序自上而下摆                                                             | 一列，一项一个页签                                     |
| 4 键从哪来               | 没有键                                                                                   | 没有键                                                 |
| 5 宿主给什么             | 当前租户，与 `{ session }`：当前打开的会话的标识                                         | 同左                                                   |
| 6 这一项交什么           | 标识、次序、可选的标签、渲染函数                                                         | 同左。标签是页签上的字，没有标签时用标识               |
| 7 什么时候读，变化怎样传 | 渲染时现取；项放进来或撤下，位置自己重画。贡献方自己读自己的数据、自己同步，会话不替它存 | 同左                                                   |
| 8 出错时                 | 只有这一项显示读不出（外壳的 FE-I14）                                                    | 同左                                                   |
| 9 撤下                   | 贡献方的作用域卸载，下一次渲染就没有了                                                   | 同左。选中的页签被撤下时回到第一项；全撤下时侧边区消失 |
| 10 形状怎样变            | 给对象加字段是相容的；改名字或去掉字段要换拓展点的名字                                   | 同左                                                   |

第三个拓展点是 `sessionCallDetail`（名字 `session.call-detail`，常量 `SESSION_CALL_DETAIL`），在一项后台调用的下面。宿主给它当前租户与 `{ session, call }`：会话的标识与这次调用的引用。别的八问答案与 `sessionDock` 相同。它让拥有调用输出的领域在这里显示输出，会话的界面模块不认识调用的协议。

会话的界面模块自己往 `sessionSide` 放一项（标识 `background-calls`，标签「后台」），列出本会话的后台调用：短号、意图、动作、状态、谁停的与进度，每项有停止，下面是 `sessionCallDetail`。有未结算的后台调用时，它往 `sessionDock` 放一行提示，没有时不放。两处读的都是列后台调用这一个操作；会话状态帧的修订变了、自己发过停止之后，重读。转写区里一次还在运行的工具调用旁边有转后台。已请求、已受理与已证实停下三种进度分开写。

这些拓展点都只在会话处于打开状态时有，没有会话、正在建会话和会话不可用时都不出现；换会话时，项收到的对象跟着变成新会话的标识。对象编成文本时就是会话的标识，所以直接往同名的附着位置里放的项收到的仍是这段标识。会话的界面模块不认识放进来的是什么，也不导入任何别的领域的成员。

`sessionDock` 在转写区与输入框之间。没有项时位置不占地方，有项时它不被压缩，自己最多占主区高度的七成，超出的在自己里面滚动。转写区因此变矮或变高时，人原先停在末尾的，转写区仍然停在末尾；人往上翻过的，留在他翻到的地方。只有人往上翻才算离开末尾：内容或转写区的高度变了，不算。

`sessionSide` 是对话页右边的侧边区，在主列之后。没有项时它没有任何元素，主列的宽度与位置和没有侧边区时相同。只有一项时不出页签，顶上显示这一项的标签；两项以上时是页签，没选中的项藏起来、不卸下。侧边区可以收起，收起后内容藏起来、不卸下。窗口不到 768 像素宽时默认收起，这个宽度取桌面外壳样式里现有的那一个断点；人点过收起或展开之后，不再跟着窗口的宽度变。收起与选中的页签只是这一页当下的状态，不落盘。

界面模块以协议客户端为输入，状态拆成三条独立的轴：会话（还没有、建会话中、已打开、不可用，打开时再分这一轮的就绪、进行、取消）、观察（连接中、在连、断开重连）、会话列表（未读、读首页、读下页、已读、读失败）。界面遵守：结果不知道就用同一个调用编号认回，不重发，认回仍未知就停在「结果仍未知」由人再确认；已提交的内容只从读历史来，进行中的回复来自观察，历史读到哪里取最近读完的那一轮的上界，状态帧的修订更大就从末尾再读一轮；对不上基线的增量不应用，换一代重新观察；历史条目、消息部件、流的块三处种类都封闭，表外的种类画成占位并写明种类名；工具调用与结果只按调用编号配对；转写区不认识任何工具，提问的调用和别的工具调用画法相同（名字、参数、在等结果或结果），没有结果而这一轮已经结束的调用写「没有结果」，这些都取自对话本身；能作答的卡不在转写区，由人工介入的界面模块经 `sessionDock` 放在输入框上方；被拒、本地不可用、未知各有一句人话，显示在出事的那一处；会话列表是服务端的投影，界面不在本地增删列表项，只在建会话、受理一条输入、一轮结束三种「活动」之后重读第一页；打开已有会话与新建成功走同一条路；列表读失败不碰已打开的会话；换会话时原会话没有结论的输入的答复一律作废。

一轮失败之后，界面经读等人知道会话在不在等人、等的是哪一轮、还有几条没处理与成因，不从历史里推。读的时机：读历史读到一条新的失败终结；状态帧说没有进行中的一轮而最近的终结是失败；在等人时发送有了答复；重试答恢复、冲突或找不到。读着的时候又要读，就在答复回来后再读一次。提示放在等的那一轮的失败那一行下面：成因按种类查一张表得到中文，表里没有的写通用的一句并带上种类名，有诊断就接在后面，没有成因只说这一轮失败了；条数为零时只提示发一条新消息，不出重试；条数不为零时写条数与「重试」。重试点名等的那一轮，带一个新的控制标识；答恢复、冲突或找不到就重新读等人，答没有变化就显示发新消息的那句提示，答未知就如实显示并让人再问一次，再问用同一个控制标识，连不上与被拒写明原因、可以再按。读等人答不了（依据不可用、这个操作不在、被拒、连不上）时退回只显示这一轮失败了。

历史里工具调用的参数是会话按通用办法编进条目的内部树，界面先把它转回普通的值，再显示成参数名与值的列表，嵌套的值缩进一层；不是那棵树的原样当普通的值。

界面的按钮、输入框、提示、徽标、折叠与文字的渲染都用共用界面件（`Button`、`Textarea`、`InlineNotice`、`StatusPill`、`Disclosure`、`Prose`），本成员的样式表只有版式，不带这一类基础样式。发送、停止、正在停止是同一个按钮的三种样子；停止的样子带一句说明「停止这一轮。还没答的问题会一起关掉。」。转写区只有刚到的行淡入，历史不动。列表项显示第一条输入的开头、最近一次活动与创建的时间。版式的来历记在成员的 `UPSTREAM.md`。

### 存储

一次提交只有一个存储事务，参加者模块不开始、提交或回滚事务；提交携带本命令需要的全部参加者，不信任调用方挑选材料，提交固定使用组合版本，材料缺席、协议版本不符、跨租户、来源无权或最新条件改变时被拒或答已变。租户是每一行的列，也是每条语句的条件，不从连接、事务域或装配树推断；同一事务域只服务一个租户。会话身份、位置、提交序与条目位置由存储分配，操作身份由 Session 按固定规则派生，存储不生成。同一会话的提交串行化，读在事务外读已提交的快照。命令到条目批次的编码只有一份（判定函数），解码也只有一份（归约函数），二者共用一个解释版本，每批记录它的解释版本。读路径的游标需要游标签名，缺席时带游标的读答不可用。

条目的存储文本是一个 JSON 对象，成员与历史条目同序，载荷以 `body` 存它原样的 JSON 文本。数字保留源字面量，对象保留键序，读回得到同一棵树。含重复键的文本被拒绝，没有 `body` 的文本不被读取。提交的时刻取自 Session 的时钟，在第一次尝试之前读取一次；没有时钟、读取失败或抛出时，提交照常进行，这次提交的事实不带时刻。存储提供者接受的 JSON 嵌套深度必须不小于创建会话那条提交命令的嵌套深度：更深的命令被拒为 `command_limit`，创建会话就失败。实际深度由 `session-adapters` 的 `create-depth.spec.ts` 量出并守着。

存储失败分类：暂时的拒绝答不可用，调用方等待后以同一身份重做；确定的拒绝答非法；身份冲突时已有回执为已提交就认回（输入摘要不同则答冲突），为已回滚则选下一个尝试代次重新提交；某个代次为未知则答提交未知、不开新代次；提交结果未知、写者不再是当前、锁等待超时都答提交未知；任何 SQL 异常不转成业务拒绝，写路径答失败、读路径答不可用；权威条目缺口、损坏或尾部不一致时隔离该会话，读取工作与恢复返回隔离，其余读写答不可用；派生索引重建中时依赖它的读答不可用并带进度。权威表的迁移只增列或增表、不改旧列含义、不改位置与身份，派生表可以整体重建；归约版本升级是一次全量重建，不是迁移。数据库方言的差异（位置的编码、JSON 用文本、写并发、耐久）在边界处理，不分叉业务语义；不宣称断电耐久，耐久边界只由提供者读回的配置给出。向基础来源要材料只发生在该操作还没有任何已提交的送达时。来源失败时先再查一次回执：期间已提交的送达被认回，不用这次失败作答；没有已提交的送达才答这次失败，下一次送达重新询问。

### 装配

服务定义只有一个服务键，四个面挂在同一个键上，同一组签名不写两份；服务键只由抽象类给出，提供者不再提供这个键。调用方插件以对象形式声明调用方类。构造依赖里访问检查、委派入口、内部主体、会话工作主体缺席或撤除时服务停在待启动，不沿用旧的允许；其他端口缺席时只有需要它的操作答不可用，端口抛出同样映射为不可用并带拥有者与诊断，代理不补默认值，不用系统时间代替时钟采样；可选的能力（事务端口的日志提交、采用来源的规划）缺席时按不可用处理。出站端口缺席时出站调用不发出，任务保留，由调度器重放。

唯一的事件是提交通知，载荷是租户、会话、会话修订、原提交证据与条目种类的去重集合，不带消息正文、凭据或附件地址；它只是唤醒提示，丢失不影响正确性。一个隔离标签下一个提供者；租户与会话是每次操作的参数，不用隔离或 Cordis 上下文表达，不为会话建 fiber。每个租户一个恢复扫描者，由装配保证全部进程里只装一份提供者插件；扫描者只在租户有待办时留着。根入口与 Cordis 无关，定义入口不导入任何提供者。

撤除有序：标记撤除中（此后面对每个操作答不可用，不再把通知交给实例）；释放全部维护句柄（扫描者停止）；调用实例的关闭，最多等配置的上限（调度器停止接受新触发，在途命令跑完或返回未知，协调器在当前命令结束后停止，最后释放时钟等待与缓存）；等待超时记诊断后返回，超时不表示实例已停止，仍在途的命令以自己的结果结束，提交未确认的得到提交未知。每一步抛出都被捕获并继续后续步骤。撤除不回滚已提交的事实，不补发未发出的出站调用，不取消任何 Model、Tool、Agent 的执行，也不撤回外部效果。依赖换代时插件先卸载再重跑。适配插件共同的规则：每个插件只以一个调用方类调用会话；只经邻域的公开契约工作，不导入提供者实现；每次出站调用与每个会话命令都带确定性派生的身份，不用时间、随机数或连接参与编码；邻域返回结果未知时按原身份查询或原样交给会话，不改写成功或失败；插件不保存业务事实，只持有可丢的派生物，丢失后从权威读重建；卸载只结束订阅、登记与在途的等待，不撤回外部效果。

### 协调器与调度器

会话命令的处理流水线对每个变更命令相同：核权并认回原操作；在同一事务边界读权威快照，带预期的命令把它与快照比较，不等就答已变，不用读到的修订改写预期；事务外调用判定函数得到拒绝原因并决定收哪些材料；向身份桥、证据桥、Context 输入或空闲输入要材料；提交；确认耐久后，有测量观察者时读回本次提交的条目并发出轮完成事件。每个命令恰一次提交，跨命令的事只能由后一个用例读取前一个已提交的事实。事务内的判定以存储参加者读到的当前状态重新裁定，以事务内的结局为准。命令处理器、协调器与调度器只编排读取、裁定、提交与通知，允许与拒绝只由纯裁定给出。

协调器没有自己的状态，输入只有权威读、出站回执与调度器交来的会话身份，同一会话同一时刻只有一个协调实例在动作（进程内每会话一个串行队列；跨进程靠每租户一个扫描者、操作幂等、预期核对与执行记录提供者的条件提交围栏，不用锁）。受理流水线、Agent 推进协调器（开 Run、续入、同日志解释、恢复、接管、重装、冻结判定到达）、控制传播协调器、归档与级联协调器、恢复协调器各自读到事实后决定发出哪些命令或出站调用。调度器只决定什么时候再检查哪个会话，不写日志：推进触发（提交通知含受理、终态、冻结或会话创建时读快照并按判定开 Run 或续入，每会话一个在途触发，新通知合并为一次重查）；空闲与自动归档（时钟或提交通知触发，空闲观察非未知时记录空闲再判定是否到期，到期则归档，计时随进程丢失、重启后按已确认的起点续算）；恢复扫描（启动与周期按租户分页读八类待办原因，游标不持久，重复交付由命令的操作身份认回）；待决认回；控制重放；级联推进；预求值与预热（只预求值并缓存已校验的采用候选，候选只在新 Run 入口或显式重装时才成为采用依据）。内部等待明确返回到点、取消或被拒；时钟被拒时调度器记诊断，不把等待当作已到期，也不改用系统时间。所有间隔、上限与退避都是策略对象的配置，默认值不散在代码里，实现可以替换策略对象。会话调用经内部主体与会话工作主体：协调器用协调方、维护者的会话主体，不由单个会话归属决定的系统维护（按租户读待办、作用域释放的收尾）用内部主体的维护者；签发主体被拒就不推进该会话、待办保留，不可用或隔离则保留任务下次再取。

## 原则与约束

- 一类事实只有一个写入者。会话日志的唯一写入者是 Session；别的领域要留下事实，交一条会话命令。
- 逻辑收口和物理收场分开。取消、归档、换代、释放只改变资格与责任。
- 结果不知道就是不知道。按原来的那次操作认回，不重新发一次，不写成成功或失败；认回之前不发出依赖它的外部效果。
- 服务端是事实的权威。客户端只有投影和缓存。
- 一个结局连同它带来的后果在同一次提交里写下。不靠提交之后的另一步去补。
- 每次提交之后要做的事挂在写入者上，不挂在各个提交方上；提交之后只发唤醒，唤醒不是事实源，丢了由扫描补查。
- 业务规则不进应用层：允许与拒绝只由纯裁定给出，命令处理器、协调器、调度器只编排。协调器与调度器不持有状态，内存里只有可丢的计时、计数与缓存。
- 幂等只靠操作身份。重放同一命令派生同一身份，每个命令的第一步是认回。
- 外部效果与日志分开：对 Agent、执行环境、子会话的调用在提交之后发出，回执作为新事实提交；提交成功而调用没发出时，调度器按同一身份重放。
- 请求到了不算，算在请求之前：派生物在变化时维护，热路径只读取。
- 读不到不变成空。读取故障不当作空队列、无 Run、无权限或执行失联。
- 领域不认识调用它的是谁，源码依赖只朝内：端口的接口由提出需要的一方声明，另一方适配；邻域契约不点名 Session。
- 租户是每次调用的参数，缺租户或跨租户默认拒绝；租户与会话不从连接、上下文、隔离标签或装配树推断。
- 每个策略类的量（重试、退避、超时、间隔、预算、上限）是可配置的策略对象，合法使用会碰到的上限必须有去处，不判失败。
- 本组不为旧数据写兼容代码；改承诺同步真实消费者，替代实现随改随删。
