# 共同持久事实与原子协调

目标选择：A1。使用单个真实AtomicStorage和显式StorageUnit参与者。此迁移未新增技术接受。

## A：共同持久事实与工作状态

| 候选 | 兑现Q1／Q2／Q5 | 成本、敏感点与风险 | 采用判断 |
|---|---|---|---|
| A1 单共享AtomicStorage，日志及Session状态显式参加StorageUnit | 同事务写受理、资格、Run选择／栅栏；恢复索引同提交；提交后通知只是加速 | 改现有非正式JSONL提供者；参与者须同真实实例、事务中禁止外部IO；日志与投影可验证一致 | 推荐。已有storage抽象可复用，复杂性集中在真实事务与归属 |
| A2 单日志追加为提交点，其余状态重放／持久检查点 | 受理事实内包含资格；CAS日志头用于单Run／栅栏；重放导出队列；恢复扫描日志目录 | 需要重新实现可靠journal CAS／索引／恢复队列；JSONL与独立索引未同提交时额外恢复协议；若每步全重放则Q6成本差 | 可行替代；只有单journal存储证明确切CAS与扫描进展、且节省成本有证据时重考虑 |
| A3 独立可靠收件箱＋日志＋事务outbox／inbox交接 | 先持久收件箱再异步写日志，每跳用稳定提交身份、持久ACK和重试达成Q1；Run侧仍需原子栅栏 | 可以拆节点，但有中间未交接状态、重复投递和更多责任；受理点须重新明确属于哪个持久拥有者 | 未来分布式合理，第一版无跨节点需求；当前不能把两处普通write冒充同提交 |

A1对Q3：原调用的准备／消费位置同提交，执行后端不加入Session事务；不可把网络请求包在数据库锁中。A1对Q4仍需每入口授权，不由同库保证。A1对Q6仅提供一致固定前缀，不替代投影算法。


复核条件：实际提供者无法兑现同实例参与时，停止依赖它的写入，不以两次普通write替代。网络IO不在事务锁内。
