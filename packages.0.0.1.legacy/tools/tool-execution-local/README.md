# Local Tool Runtime

`createToolExecutionRecordReader` borrows the original same-unit source and keyed-read operations. It returns only the readOriginalIn part of ToolExecutionRecords for its fixed tenant. It does not read complete Session prefixes or confer execution or recovery authority. See [the reader behavior](SPEC.md#local-provider-constraints).

The root exports `createToolInvoker`, `createToolImplementationRegistry`, `createToolRuntimeRegistry`, `createOriginalIssueToolRuntime`, and `createToolEnvironmentPlacementSource`. Public operation and construction types belong to [core/tool-execution-runtime](../../core/tool-execution-runtime/src/index.ts). Root factories do not import Cordis.

`createOriginalIssueToolRuntime(config, dependencies)` uses the same native executor with the [Session original issue protocol](../../core/tool-execution-runtime/SPEC.md#session原工具发起参加协议). Supply `tenant`, `recoveryPageSize` and `originalIssue`. The factory receives no full-history, Session enumeration, backing-log or Runner-selection ports. It reads its own task index and waits for original resource cleanup before readiness. Prepared requests supply the selected tool and after-action chain. Compose `toolOriginalIssueMigrations` into the shared storage before construction. Borrowed resources remain with their owners. Legacy tasks outside the native index require separate migration; this factory does not claim to recover them.

This factory returns `ToolPoolInstance`. Its `submit` takes a `PreparedToolExecution` with the original source and selected `after_action` chain. Executable requests include the selected definition and arguments. A non-executable request carries the original adoption and an explicit `unparseable` or `no_such_entry` result; it cannot carry a selected implementation. The Session producer prepares these inputs. The native pool verifies the original admission token for executable requests and reuses its existing executor. Non-executable requests record a failure without invoking the author; Session verifies their original completed batch. Private legacy adapters and their unit tests still require the migration described in [SPEC.md](SPEC.md); the public factory no longer selects that path.

The native owner retains the complete job and selected implementation before it presents a participant. The participant stages the original intent and unique claim in the caller's transaction. The native owner enters the author only after confirmed consumption of that same claim. An unconfirmed admission retains the original job. An unconfirmed consumption that is later found committed ends the unstarted job as unavailable. It does not call the author. The participant's `stopped` promise observes actual job completion and returned borrows; it is not a result-delivery receipt. Current component tests use real SQLite and the native executor with controlled Session admission. Full Session composition, its result custody, and the dynamic Cordis driver remain separate verification obligations.

`./cordis` exports `runtimeRegistry`, `implementationRegistry`, `managedRuntimeRegistry`, `managedImplementationRegistry`, and `managedToolExecutionLocal`. The runtime registry forwards prepared requests. The managed execution binding calls `ToolRuntimeStartupService.start(config)` and registers the returned pool only after its original `ready` promise resolves. Its dependencies are the startup service, registry, and shared assembly lifetime. It does not inject Session logs, history, Runner selection, or concrete executors.

The trusted application root supplies the startup service and chooses the native factory with its live dependencies. JSON configuration contains only `resultStorage`, `frameQueueBytes`, and `tailRetry`. The binding retains the original close control before waiting for recovery. Withdrawal prevents publication and waits for original cleanup. Unconfirmed close stays pending until the application explicitly retries that same instance. See [LP-6](SPEC.md) and the definition package's TE-24/TE-25.

The current delivery runs pure tool functions and records successful context reads before exposing their values. Observation release does not stop execution. A result writer binds before author entry, so later business revocation does not discard an existing receipt. Business queries still require current authorization. Cold recovery ends queued, running, or waiting records without re-entering the author function. Adopted environment resources remain with the original environment maintenance owner. It retains unknown cost and frame evidence and refuses readiness while resource cleanup is unconfirmed.

Tools with a `targetEnvironment` declaration now use current asset inputs to resolve their requirement and permission. The environment registry selects one instance that supplies all required facilities. The runtime retains that original lease and confirms its data adoption in the shared log before author entry. The author receives only the required facility ports. A pure tool does not acquire an environment. See [TE-26–28](../../core/tool-execution-runtime/SPEC.md) and [LP-7–11](SPEC.md) for adoption, authority changes, and retained cleanup responsibilities.

`./cordis` also exports `toolEnvironmentPlacement` and `managedToolEnvironmentPlacement`. They inject the existing `currentEvaluationInputs`, `toolRuntimeRegistry`, and `executionEnvironments` services. Their data configuration requires a name, an explicit `factoryPermission`, and a `selection` policy (`unique` or `reference`). The managed binding uses the shared assembly lifetime. Trusted root callers can instead pass a selection function to `createToolEnvironmentPlacementSource`.

The host environment provider supplies actual command and file facilities through the public environment contract. This runtime does not implement an OS backend. External service resolution, other declared dependencies or settings, interactive wait, and accepted cost reports require later implementation increments. Their unavailable paths do not substitute declaration defaults or report successful reception. The application delivery owner continues the durable A/B/C protocol; this package does not declare a result delivered when the author function returns.


## Persistent acceptance

The formal CLI owns the cross-runtime PF-006 S24 and S69 acceptance scenario in [apps/cli/acceptance](../../../apps/cli/acceptance/README.md). It checks complete ordinary returns, actual Shell execution, durable results and the next model request through the production entry. The retired demo and its acceptance adapter are removed.

The main session and independent acceptance owner maintain the cross-runtime scenario. Provider tests remain in this member. Network acceptance requires an explicitly configured dedicated tenant and uses its OpenRouter credentials without displaying them. Missing configuration or failed model requests do not count as passing results.

受信根可从纯根入口调用 `createToolOriginalIssueVerifier(storage)`。其 `verifyIn` 只在调用者原 Unit 读取完整持久原身份，不发行 claim 或执行权。原 job 关闭后仍可供既有结果保管核验；共享 Storage 的存续由根负责。

`createToolExecutionObligations({ storage, tenant, maxPageSize })` reads the tenant's native original-task index in one committed snapshot. Its callback may commit independent work. The source returns task references, without recovering Sessions or granting execution. It covers native original rows only. Legacy jobs, actual records and resource cleanup remain cold-recovery migration obligations; this reader alone does not establish pool readiness.
