# SYS-COMPOSITION：定义、装配与活体

## 这条服务于什么

[SYS-DYNAMIC](../fully-dynamic-system/requirements.md) 是根目标：
**能力的定义、实现、绑定和组合关系应能动态演化。**

演化要有发生的位置。如果定义里写死了用哪一份实现，就没有任何时刻可供绑定改变；
如果活体一经产生就与产生它的那份定义再无关系，改定义也影响不到任何东西。
**本条规定系统必须怎样组织，那个位置才存在。**

它不与 SYS-DYNAMIC 并列，也不是它的一部分：SYS-DYNAMIC 说**要达成什么**，
本条说**据以达成它的结构**。

## 已确认要求

### SYS-COMPOSITION.C1（三段结构）

一切可运行的东西分三段，三段不可合并：

| 段 | 是什么 | 本质 |
|---|---|---|
| **定义** | 声明需要哪些能力 | **数据**。可复制、可迁移、可长期保存；闲置不消耗 |
| **装配** | 一次求值：把当时作用域内实际可用的实现，绑定到一份定义上 | **动作**。有确定的发生时刻 |
| **活体** | 装配的产物，持有已捕获的绑定与实际资源 | **计算资源**。占用即消耗，可回收，**可重建** |

三段各自的失效方式不同，这正是不能合并的理由：定义因作者修订而变，
装配因作用域内可用实现的变化而得出不同结果，活体因资源治理而生灭。

### SYS-COMPOSITION.C2（关系是注入，不是包含）

**定义不持有任何具体实现的引用**，只按能力标识声明需求。
**活体不是定义的副本。**三者的关系是：

```text
活体 = 装配(定义, 作用域)
```

同一份定义在不同作用域装配出不同的活体，而**定义本身一个字不变**。

### SYS-COMPOSITION.C3（绑定在装配时确定并被捕获）

绑定在装配那一刻确定，此后属于**这一个**活体。
活体在执行中使用**已捕获的自身结构性绑定**，不在长时执行中途暗换它们。

捕获的是该活体直接消费的服务或执行实现，不递归冻结服务内部管理的数据、注册条目和下级能力。稳定的会话能力入口可持续更新定义数据与实现选择；Agent runtime 通过它发起调用，每个 Model／Tool runtime 再捕获自己的单次输入。能力被声明为必需，不等于 Agent Loop 必须直接 inject 其具体提供者。

### SYS-COMPOSITION.C4（变化作用于下一次装配）

活体直接捕获的提供者发生增减与换代，改变其后续装配结果，不暗改正在执行的旧绑定。入口内部的数据或实现注册更新不等于入口提供者换代，不因此要求其所有消费者重建。

要让变化作用于某个已存在的活体，走**显式的生命周期动作**——退役并重建，
在 Cordis 的依赖与所有权生命周期下衔接，并显式保存业务连续性；框架卸载重跑本身不代替业务交接。

### SYS-COMPOSITION.C5（撤除的次序与可感知性由本系统负责）

装载产生效应、撤除须撤回逆效应，这一条
[SYS-DYNAMIC 已于 2026-09-13 澄清](../fully-dynamic-system/requirements.md#已确认要求)，本条不重复。

本条补充它没有覆盖的一半：**撤除的次序与失败的可感知性，不是内核免费提供的。**
需要次序的撤除必须自己组合，需要被感知的失败必须自己上报。依据见「机制边界」第二行。

## 为什么必须是注入而不是包含

三条，每条都能被一个反例否定：

1. **若定义持有实现引用**，它就带着对某个作用域的假设，无法被复制到另一个作用域使用。
   而「绑定能动态演化」首先要求**绑定不在定义里**。
2. **若活体是定义的副本**，改一次定义就要去改所有活体，演化变成批量改写；
   而且活体各自漂移之后，「这份定义现在是什么」不再有答案。
3. **若绑定实时解析**，活体会在长时工作**中途**换代，而它已经产生的外部效果不会回滚。

第三条不是推测，有机制依据，见下一节。

## 机制边界：内核给什么、不给什么

**「依赖注入」在 Cordis 里有精确语义，照字面实现会出事。**本节记录四处分叉。

| 想当然的理解 | 实际读数 | 本系统因此怎么做 |
|---|---|---|
| 活体的业务能力用 `ctx.inject` 获得 | `inject` 的真实含义是「提供者换代或不可用，**我就卸载重跑**」。判断该不该 inject，要问消费者「**能承受被重启吗**」 | 按实际消费者捕获其自身绑定，不把每项业务能力的实现都做成 Agent Loop 的必需注入。长时工作承受不起被重启——这正是 C3、C4 的由来 |
| 撤除时各 disposer 会按序完成，失败会被报告 | effect 之间由并发驱动，**逆序只约束取出**；异常**只写日志不上抛** | 需要次序与结算的撤除，**合并进一个撤除过程**；失败要被感知，就在该过程内部自行上报（C5） |
| 用 `isolate` 给作用域做隔离 | `isolate` 隔离的是**服务实例的可见性**，不隔离数据 | 作用域隔离不靠 `isolate`；身份校验属数据访问层，归 [SYS-TENANT](../cross-system-constraints/requirements.md#sys-tenant) |
| 用 `bail` 做准入判定 | `bail` 不 await，Promise 本身是 bail 值；同步派发在它处停止并原样返回，异步判定尚未取得 | 需要 I/O 的准入走顺序 await 的派发方式 |

四条读数分别登记在 [basis 的 cordis 条目](../../basis/README.md) 的对应条目：
[必需服务换提供者会使插件体重跑](../../basis/cordis/plugin-body-reruns-on-provider-change.md)、
[effect 之间的释放是并发的](../../basis/cordis/effect-disposal-concurrent-not-ordered.md)、
[`isolate` 隔离服务实例的可见性](../../basis/cordis/isolate-hides-instances-not-data.md)、
[`bail` 不能承载异步控制判定](../../basis/cordis/async-control-not-bail.md)。

机制读数与可复跑 probe 以相应 basis 条目的当前正文为准。probe 只验证明确条件下的内核行为，不代替本系统的领域语义或完整组合保证。

**本条与上表的关系要分清**：C1–C4 是**建模决定**，即使四条读数全被推翻，
「定义是数据、活体是装配产物」依然成立——它的理由在上一节的前两条，与内核无关。
被推翻会失效的是**第三条理由**与本节右列的具体做法。

## 这条约束了什么

任何「某个定义怎么跑起来」的设计都受本条约束。已经在消费它的：

| 消费者 | 消费的是哪一条 |
|---|---|
| [PF-002](../../product/PF-002-assets-settings-and-permissions/design.md#63-组合的引用指向能力标识)：组合的引用指向能力标识 | C2。引用指向标识而非具体资产，正是「定义不持有实现引用」在产品层的说法 |
| [PF-003](../../product/PF-003-asset-transfer-and-sharing/README.md)：资产的复制与分享 | C1、C2。定义能跨组织流动而不携带环境假设，**正因为它不含绑定** |
| [PF-004](../../product/PF-004-agent-definition-and-assembly/README.md)：Agent 运行时 | C1–C4 全部。**它是本条在 agent 这件事上的产品落点**：三段各自叫什么、三个时刻分别定什么、变化怎么传播 |
| agent 实例的生灭被定为「资源与装配的治理」 | C1、C4。活体可回收重建，所以能按资源需要起落 |

## 待澄清

- **basis 覆盖有边界。**超出相应 probe 的机制前提必须补足，不能按一次运行推广；
  补齐 owner 见各条目自身（两条已写明「kernel 侧首个集成包」）。
- **作用域怎样成为装配的输入。**产品侧已有四层作用域
  （[PF-001](../../product/PF-001-identity-scope-and-agent-constraints/design.md#61-层次)），
  它与装配时「当时可用的实现」之间的对应关系尚未确定。本条只要求绑定在装配时确定，
  **不规定装配发生在哪一层、多久一次、由谁触发**。
- **活体的可重建前提。**哪些状态必须持久、哪些可重建、恢复接续到哪个合法位置，
  归 [SYS-RUNTIME-CONTINUITY](../runtime-state-and-continuity/requirements.md)，本条不重复。
- **定义自身的演化。**定义出新版本时，已经装配出的活体如何处置，
  按 C4 走显式生命周期动作；但「何时该重建」是资源与治理政策，本条不选定。

缺口限制依赖这些细节的定稿，不削弱 C1–C5。

## 与已有要求的关系

| 要求 | 关系 |
|---|---|
| [SYS-DYNAMIC](../fully-dynamic-system/requirements.md) | **本条服务于它。**它是根目标（要达成什么），本条是据以达成的组织方式（系统必须怎样组织）。C5 引用它 2026-09-13 的效应/逆效应澄清，不重复定义 |
| [SYS-RUNTIME-CONTINUITY](../runtime-state-and-continuity/requirements.md) | C1「运行时与状态持久化解耦」与本条的三段结构一致：**活体之所以可回收，正因为定义与持久状态都不在它里面**。恢复接续的判据归它，本条不定义 |
| [SYS-LONG-RUNNING](../long-running-and-evolving/requirements.md) | 超长期待机的形态由本条支撑：**定义长期存在，活体按需起落** |
| [SYS-KERNEL](../cross-system-constraints/requirements.md#sys-kernel) | 内核采用与自建边界归它。本条陈述建模决定，**不选择具体的内核机制**，也不据「机制边界」一节扩大或缩小采用范围 |
| [SYS-TENANT](../cross-system-constraints/requirements.md#sys-tenant) | 装配的作用域受租户约束；隔离不靠内核的 `isolate`，见「机制边界」第三行 |
