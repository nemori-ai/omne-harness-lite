### S-3 本契约明确不承诺什么

- **EC 的任何语义**（[S-1](#s-1-本契约拥有什么)）。
- **客户端怎样信任中心的证书**（按公共或组织的 CA 链加主机名校验，还是钉住公钥指纹），以及确认失败时据点怎样呈现：据点一侧的选择，归 PF-016 与 `apps/cli`（[G-2](#十一已知缺口)）。中心一侧对两种都出示同一份东西（[S-4](#s-4-客户端一面的连接只有-tls服务端认证)）。
- **客户端与中心之间的网络设备**：在两者之间终结 TLS 的设备不在本传输之内（[S-24](#s-24-装配给-vs-协议给) 的前提）。
- **应用层协议协商（ALPN）**：本契约的答复只对按 HTTP/1.1 成帧的请求报文定义；握手里协商什么，不改变它们。
- **接收上界、接收时限、读尽上界与时限的取值**（[S-10](#s-10-只答完整收到能成帧的请求报文)、[S-5](#s-5-一条连接恰承载一个请求答复)）：归入口层的实现映射。本契约只冻结四项接收上界与接收时限的**下限**（S-10）；取值只能不低于它们。TLS 握手阶段的时长上界同样归入口层的实现映射：接收时限从握手完成起算，本契约不给握手阶段任何下限或上限。
- **送达、限流与背压、跨协议版本的兼容窗口、时序侧信道**：同 EC S-3。逐字相同只约束字节，不约束耗时。

## 二、连接

### S-4 客户端一面的连接：只有 TLS，服务端认证

| 项 | 性质 |
|---|---|
| 承载 | HTTP/1.1（RFC 9112）over TLS。**客户端一面只有 TLS**：没有明文的承载；向它发明文 HTTP 的请求握不了手，问不到 |
| TLS 版本 | **最低 TLS 1.3**（RFC 8446）。只提供更低版本的客户端握不了手，问不到 |
| 早期数据 | **不接受 TLS 早期数据**（0-RTT，RFC 8446 §2.3）：中心不许任何会话票据带早期数据，客户端在首轮送来的早期数据按 RFC 8446 §4.2.10 的忽略方式丢弃，**不算请求报文的任何一部分**；请求报文只从握手完成之后的应用数据读起。理由：早期数据没有防重放（RFC 8446 §8），旁人截下一份写路由的请求就能让它再办一次，而重发本应只由客户端决定（EC S-17 第 5 件事） |
| 服务端认证 | 中心在握手里出示**部署配置输入**给出的证书链，并以对应的私钥完成握手。客户端在握手里带什么服务器名，出示的都是这一份 |
| 材料 | 证书链与私钥是部署配置输入，**不是**[部署密钥](../../../../ubiquitous_language/terms/grounding-and-isolation.md#ul-deployment-key--部署密钥--deployment-key)（EC S-3）。**缺一样、或私钥与证书链不配 ⇒ 启动失败**：不以任何内置材料顶替，不退回明文 |
| 客户端认证 | 中心不要求、不看客户端证书——认人只看出示物（EC S-11） |
| 客户端信任什么 | 不由本契约定（[S-3](#s-3-本契约明确不承诺什么)、[G-2](#十一已知缺口)）；中心不区分客户端用哪一种，也不因此改变出示的东西 |
| 换证书 | 改部署配置、重启。与[治理中心标识](../../../../ubiquitous_language/terms/grounding-and-isolation.md#ul-governance-center-identifier--治理中心标识--governance-center-identifier)无关：标识不是秘密，只管「是不是同一个」，不证明「真的是它」（EC [S-27](../../governance-center-entry/v2/contract.md#s-27-governancecenterid-的形状与相等)） |

**这张表是 [PF-017 §8](../../../../product/PF-017-governance-center-as-deployable-application/design.md#八边界与依赖) 防冒充硬要求在中心一侧的全部**：客户端能据证书链确认对端持有那把私钥；
确认不了就不交出登录状态、不接答复——那一半在客户端（[G-2](#十一已知缺口)）。它同时闭合 EC G-11 的中心一侧：手段是服务端 TLS 认证，材料是部署配置输入，验证义务见[验证入口](../verification.md#证据义务) V-7。

### S-5 一条连接恰承载一个请求—答复

- 中心在一条连接上**只读一个请求报文**，只答它一次；写出答复、或决定不写（[S-16](#s-16-问不到不写任何答复字节)）之后关闭连接。
  同一连接上这个报文之后的字节（例如流水线里的下一个请求）**不当作请求**：不成帧、不判、不答，只在下面的读尽里丢弃。
- **答复之外不写任何字节**：不写 1xx 临时答复——请求带 `Expect: 100-continue` 也不写 `100 Continue`，照常等请求体收齐再答；不写第二份答复。
  这是对 RFC 9110 §10.1.1 的**有意偏离**（[S-33](#s-33-与-http-规范的有意偏离)）：那里要源服务器在头部收齐时要么立即给出终态答复、要么立即写 `100 Continue`，不得等请求体。
  理由：1xx 只在请求带某些头时出现，答复就随请求变了（EC S-6）；而只看请求体（[S-6](#s-6-只看请求体)），头部收齐时也给不出终态答复。
- **写出答复之后，按下面的次序关闭连接**：
  1. **关写方向**（半关）：TLS 上先发 `close_notify`（RFC 8446 §6.1），再关传输的写方向；
  2. **读尽**：在**读尽上界**（按 HTTP 报文层即 TLS 明文计的字节数，与 [S-10](#s-10-只答完整收到能成帧的请求报文) 的请求体上界同值、同一计量层）与**读尽时限**之内，继续读对端送来的字节并**全部丢弃**，直到对端关闭它的写方向；
  3. **全关**。

  读尽中对端送来的字节超出读尽上界、或到了读尽时限对端仍未关写，**立即全关**。这时对端可能收不全、甚至收不到已写出的答复（连接以重置收场时，对端尚未读走的数据会被丢掉，RFC 9112 §9.6），**对它就是问不到**（[S-17](#s-17-客户端怎样读答复) 第 1 步）。
  理由：先关写、再读尽、后全关，是 RFC 9112 §9.6 为免「重置吞掉最后一份答复」给出的关闭方式；读尽有界、接收有时限，一条连接自握手完成起占住中心的时长与读入量就有界（握手阶段的时长上界归实现映射，[S-3](#s-3-本契约明确不承诺什么)）。
- 决定不写答复时（S-16），不走上面的读尽：握手已完成的连接先发 `close_notify` 再关闭（S-16）。
- 重发就是在一条新连接上再发一个请求（EC S-17 第 5 件事）。

## 三、请求

### S-6 只看请求体

一个请求报文里**只有请求体参与判定**（[PF-017 §6.2](../../../../product/PF-017-governance-center-as-deployable-application/design.md#62-中心只认登录状态不认客户端)：中心只认登录状态，不认客户端）：

| 报文要素 | 参与什么 |
|---|---|
| **请求体**：按 `Content-Length` 成帧的内容字节（[S-10](#s-10-只答完整收到能成帧的请求报文)） | 全部判定（[S-7](#s-7-请求体怎样读成信封)～[S-9](#s-9-公开体检的请求在本传输上的形状)） |
| `Content-Length` | 只用于成帧（[S-10](#s-10-只答完整收到能成帧的请求报文)） |
| `Transfer-Encoding` | 出现就成帧不了（[S-10](#s-10-只答完整收到能成帧的请求报文)）；本传输不收分块的请求体 |
| 方法、请求目标（路径与查询） | 不参与：任何方法、任何路径得到同一份答复。**`HEAD` 也一样，答复照样带体**——对 RFC 9110 §9.3.2 的有意偏离（[S-33](#s-33-与-http-规范的有意偏离)） |
| 其余一切请求头，含 `Host`、`Content-Type`、`Content-Encoding`、`Connection`、`Expect`、`Upgrade`、`Authorization`、`Cookie` | 不参与：不因它们放行、拒绝或改变答复。`Host` 缺席、重复或不合法照样答——对 RFC 9112 §3.2 要求的 `400` 的有意偏离（[S-33](#s-33-与-http-规范的有意偏离)），`400` 会是四种入口答复之外的第五种答复（EC S-7）；`Content-Encoding` 不解码，请求体按原字节读；`Upgrade` 不切换协议 |
| 对端地址、TLS 会话的任何属性 | 不参与（EC S-16） |

**客户端发请求一律用 `POST`**，以 `Content-Length` 成帧，请求体恰为一份信封或一份公开体检请求（[S-9](#s-9-公开体检的请求在本传输上的形状)）；路径不参与判定，规范实例用 `/`。
中心一侧不因方法不是 `POST` 而改变答复（上表）；客户端一侧只用 `POST`，是因为 `GET`、`HEAD` 的请求内容在一般 HTTP 语义下没有定义（RFC 9110 §9.3.1、§9.3.2），客户端一侧的 HTTP 实现可能拒发或丢掉它。

**出示物只有一个承载位置：请求体里信封的 `presentedLoginState`**（EC S-4、S-5）。`Authorization` 头里的东西**不是出示物**：
一个只在 `Authorization` 头里带了登录状态的请求，在本传输上就是**没带出示物**，经第 ② 步的路由得 `login-state-rejected`。
理由：只有一个承载位置，「多个出示物」只在一个解析器里判，「版本先于出示物」也不跨头与体两处（提案「传输候选的采用」第一行）。

### S-7 请求体怎样读成信封

请求体按下表逐级读。**任何一级读不下去，就是 EC S-10 ①「信封不可解析」，答 `version-mismatch`**（超出 S-10 接收上界的除外，见表下）——中心不知道它是哪一版、要办哪件事，不试着猜（[PF-017 §6.4 ①](../../../../product/PF-017-governance-center-as-deployable-application/design.md#64-无效与答不出是两个不同的答复)）：

| 级 | 要求 | 不满足 |
|---|---|---|
| 1 字节 → 字符 | 按 UTF-8（RFC 3629）**严格**解码：非法字节序列、超长编码、代理码点的编码（`ED A0 80`～`ED BF BF`）、超过 U+10FFFF 的都算解不了；**不以 U+FFFD 顶替** | `version-mismatch` |
| 2 字节顺序标记 | 请求体以 `EF BB BF`（U+FEFF）开头算解不了，**不跳过**：RFC 8259 §8.1 不许发送方加它，跳过它会让同一个请求有两种字节形式 | `version-mismatch` |
| 3 字符 → JSON | 恰为一份 JSON text（RFC 8259 §2）：值的前后只允许 JSON 的空白（U+0020、U+0009、U+000A、U+000D）。空请求体、只有空白、语法错、值之后还有别的字符，都算解不了 | `version-mismatch` |
| 4 顶层 | 顶层值是对象。数组、字符串、数、`true`、`false`、`null` 都不是信封 | `version-mismatch` |

**各级的先后，以及接收上界在哪里插进来**（[S-10](#s-10-只答完整收到能成帧的请求报文)）：请求体按 `Content-Length` 读满之后才开始第 1 级；第 1、2 级对**整个**请求体判完，才进第 3 级。
第 3 级从左到右读，读的同时判 S-10 的**嵌套深度**与**对象成员数**两个上界：深度在读到那个使深度超过上界的 `{` 或 `[` 时判，成员数在读到某个对象里超过上界的那一个成员的名字的起始 `"` 时判——**超界 ⇒ 关闭连接，不写任何字节**（问不到），不是 `version-mismatch`。
**深度与成员数只数到「仍是某个 JSON text 前缀」的最长前缀为止**：从请求体开头起、能作为某个合法 JSON text 开头的最长码点序列；语法错的位置 = 那个前缀之后的第一个码点。**超界只由前缀里的码点触发**——语法错的那个码点不计入深度与成员数——所以两者不会落在同一个码点上：**前缀里有超界 ⇒ 关闭连接不写；前缀里没有超界 ⇒ 只按语法错判、`version-mismatch`（第 3 级不通过）**。非 JSON 的请求体同样：前缀里没有超界，只按语法错判。请求在 S-10 的**下限之内**时，这两个上界永远不会触发，本条的收场只有表里那一列。

读下来之后：合 [S-9](#s-9-公开体检的请求在本传输上的形状) 的形状 ⇒ 公开体检（EC S-10 第 0 步）；否则它就是一个信封，按 EC S-10 从 ① 起判。
**一个请求有多处不合格时，EC S-10 的次序决定答复**：最先那一步的出口就是答复。

**JSON 值的读法**——它们决定一份信封合不合 EC 的 Schema，所以也决定答复：

- **成员名与字符串按转义还原之后的码点序列比较**：`"protocolVersion"` 就是 `protocolVersion`，`"composition.governance-center-entry\/v1#S-18"` 就是那个路由标识。不做 Unicode 规范化，不折叠大小写。
- **转义写出的孤立代理码点（如 `\uD800`）照常读成字符串的一部分**，不让请求体变成解不了；它在那个值所属的那一步被判：在出示物里就是出示物表示层不合格（EC S-5，`login-state-rejected`）；在 `protocolVersion` 里按 ① 判，在 `operation` 里按 ①′ 判，在载荷里按载荷那一步的规则判。
  这样同一个值不会因解析器不同而得到两种答复。原始字节里的代理码点编码是第 1 级的事。
- **数按 JSON 文本所写的精确数值判**，不先舍入到任何有限精度的表示：`1.0`、`1e3` 是整数（1、1000），`1.5` 不是，`9007199254740992` 大于 2⁵³−1。
  EC S-17 注 3 对 `offerTtl` 的「是整数，且不大于 2⁵³−1」因此在任何实现上判出同一个结果。

### S-8 重复成员

EC S-4 的「同一成员在传输上出现不止一次」，在本传输上就是：**请求体里某一个 JSON 对象的两个成员，名字按 [S-7](#s-7-请求体怎样读成信封) 还原之后相同。**

- 读请求体的一方**必须报告每一处重复**（在哪个对象里、哪个名字），**不得取其一**：不取先出现的、不取后出现的、不合并。RFC 8259 §4 只说名字「应当」唯一、并承认各实现对重复名的行为不可预测；本契约把它定死为「报告」。
- 报告之后按 EC S-4 那张表逐成员收场，本契约不另定收场：

| 重复在哪 | 收场 | 依据 |
|---|---|---|
| 信封顶层的 `protocolVersion` | ① `version-mismatch` | EC S-4 |
| 信封顶层的 `operation` | ①′ `invalid-input` | EC S-4 |
| 信封顶层的 `payload` | 载荷那一步 `invalid-input`：经第 ② 步的路由在认出人之后，免认人的路由在 ①′ 之后 | EC S-4 |
| 信封顶层的 `presentedLoginState` | ②「多个出示物」`login-state-rejected`。免认人的路由不看出示物，这处重复也不看（EC S-10） | EC S-4、S-11 |
| 信封顶层的表外名字 | 它本来就是表外成员：①′ `invalid-input` | EC S-10 ①′ |
| **某个成员的值的里面**（任意深度） | 那个成员的值不能被唯一确定，按它所属的那一步当作表示层不合格收场：在 `payload` 里 ⇒ 载荷那一步 `invalid-input`，与 `payload` 重复同一步；在另三个成员里——它们的值本应是字符串，是对象就已经不合格——收场与该成员不合格相同 | 本契约推导，见下 |
| 公开体检请求里 `operation` 以外的成员，任意深度 | 不看（EC S-18：其余成员一律忽略） | [S-9](#s-9-公开体检的请求在本传输上的形状) |

**「某个成员的值的里面」一行是推导**：EC S-4 只列了四个顶层成员。载荷内部的重复若由实现挑一个，同一份请求体在两个实现上会交出两份不同的载荷，正是 EC S-4 要挡的；
收在载荷那一步而不是 ①，因为那时版本已经读出、信封也合格，不合格的是「那件事的输入」（EC S-10：输入指载荷）。

### S-9 公开体检的请求在本传输上的形状

**请求体按 [S-7](#s-7-请求体怎样读成信封) 读下来是一个对象，其中恰有一个名为 `operation` 的成员，它的值是字符串 `composition.governance-center-entry/v1#S-18`** ⇒ 这是公开体检的请求（EC S-10 第 0 步、[S-18](../../governance-center-entry/v2/contract.md#s-18-公开体检)）。

- **不要信封**：`protocolVersion`、`presentedLoginState`、`payload` 与任何其他成员，在不在、重复不重复，一概不看。
  它们只受 [S-10](#s-10-只答完整收到能成帧的请求报文) 接收上界的约束：请求在下限之内就不会被切；其余成员让请求超出下限的，照样可能被切（关连接不写）。
- **发出公开体检请求的办法**：在 [S-4](#s-4-客户端一面的连接只有-tls服务端认证) 的 TLS 连接上，以 `POST`、以 `Content-Length` 成帧（[S-6](#s-6-只看请求体)：客户端一律如此），发一个请求体为上面那个对象的 HTTP/1.1 请求；路径任意。
  规范实例用 `POST /` 与最短的请求体 `{"operation":"composition.governance-center-entry/v1#S-18"}`（[examples §2](examples.md#2-公开体检的请求与答复)）。
  中心一侧照 [S-6](#s-6-只看请求体) 不看方法、路径、请求头：别的方法、别的路径同样得到公开体检答复。
- `operation` 出现不止一次的对象**不是**公开体检请求——它的 `operation` 不能被唯一确定（[S-8](#s-8-重复成员)）——按信封从 ① 起判。请求体读不下来同样不是，答 `version-mismatch`。
- 这一步不受版本那一关挡——那是 EC S-10 第 0 步排在 ① 之前的结果（[PF-017 §6.4](../../../../product/PF-017-governance-center-as-deployable-application/design.md#64-无效与答不出是两个不同的答复)：体检的公开部分不受 ① 挡；[§6.17](../../../../product/PF-017-governance-center-as-deployable-application/design.md#617-体检只说部署不说里面有谁)）；它是否随 EC S-8 跨协议版本冻结归 [G-4](#十一已知缺口)。**本条冻结的是公开体检请求的形状与中心的认法（请求在下限之内时），跨协议版本不改**（[S-18](#s-18-跨协议版本不改的两样在本传输上)）。

### S-10 只答完整收到、能成帧的请求报文

**成帧**

- **中心只对完整收到、能无歧义成帧的请求报文作答；成帧只认 `Content-Length`。**下列任一情形都是**成帧不了**——**关闭连接，不写任何字节**（问不到）：
  - 不是 HTTP/1.x 请求报文；请求行或头部语法错（RFC 9112 §3、§5）；
  - 头部里有 `Transfer-Encoding`，不论取值（含 `chunked`；本传输因此也没有尾部字段）；
  - 某一行以单独的 LF 结尾而不是 CR LF（RFC 9112 §2.2 允许接收方认单独 LF，本传输不认）；
  - 头部里有 obs-fold 续行（RFC 9112 §5.2）；
  - 字段名与冒号之间有空白（RFC 9112 §5.1）；
  - `Content-Length` 不合法：每一处的值不是 RFC 9110 §8.6 ABNF 的 `1*DIGIT`（不许逗号列表——同值逗号列表 `42, 42` 那里允许接收方拒收，本传输拒收；值的内部不许空白、正负号；前导零按 ABNF 允许，按十进制取值），或多处出现时各处的值**不逐字节相同**（`5, 5`、`05` 与 `5` 都算不同）。「值」指去掉字段行两侧 OWS 之后的 field-value（RFC 9112 §5）：`Content-Length: 5 `（尾随 SP）的值是 `5`，能成帧；
  - 报文没收齐连接就断了，或到了接收时限还没收齐（RFC 9112 §6.3 第 6 条）。

  **报文层语法——起始行、字段行、字段值（RFC 9110 §5.5）与 `Content-Length` 的值——按 RFC 9112／9110 的 ABNF 严格判，规范给接收方的宽松或替换选项一律不采用**；各字段自己的值语法（`Host` 等）不判，那是 [S-6](#s-6-只看请求体) 的事：请求行之前的空行不忽略（是成帧不了；对 RFC 9112 §2.2 的「应当」有意偏离，[S-33](#s-33-与-http-规范的有意偏离)）；请求行只按单个 SP 分词（§3 的「可以按空白分词」不采用）；裸 CR 不替换为 SP（§2.2）；起始行与第一个头之间的空白不吞（§2.2）；字段值里的 CR、LF、NUL 不替换（RFC 9110 §5.5）——凡此都是成帧不了。头部块的字节数从请求行的第一个字节起算，因此「请求行之前的空行」本身就落在头部块之外、直接判成帧不了。

  没有 `Content-Length` 的请求，请求体长为 0（RFC 9112 §6.3 第 7 条）：它能成帧，按 [S-7](#s-7-请求体怎样读成信封) 第 3 级答 `version-mismatch`。
  没有请求报文，就没有信封可判，也就没有 EC S-7 意义上的答复。HTTP 规范在这几处要求写 `400`、`414`、`501` 之类的，本传输一律不写（[S-33](#s-33-与-http-规范的有意偏离)）。

**接收上界与它们的下限**

- **接收有四个上界与一个时限**。取值归入口层的实现映射（[S-3](#s-3-本契约明确不承诺什么)），但**不得低于下表的下限**；**下限跨本传输的一切版本不改**（[S-18](#s-18-跨协议版本不改的两样在本传输上)）：

| 上界 | 量的是什么 | 下限 | 在哪一刻判 |
|---|---|---|---|
| 请求头部块 | 从请求行的第一个字节到结束头部的空行（含它的 CR LF）为止的字节数 | **8 KiB**（8192 字节） | **成帧时**：头部块读到超过上界仍未结束，即判 |
| 请求体 | 请求体的字节数 | **64 KiB**（65536 字节） | **读体时，按 `Content-Length` 先判**：头部收齐时 `Content-Length` 已大于上界，即判，不读请求体 |
| 嵌套深度 | 请求体 JSON 里对象与数组的嵌套层数：顶层的对象或数组是第 1 层，第 d 层的对象或数组里直接含的对象或数组是第 d + 1 层 | **64** 层 | **S-7 第 3 级从左到右读时**（[S-7](#s-7-请求体怎样读成信封) 表下） |
| 对象成员数 | 请求体 JSON 里任何一个对象的成员个数；同名成员出现几次计几个 | **1024** 个 | 同上 |
| 接收时限 | **起点**：客户端一面是 TLS 握手完成的那一刻（握手本身不计入），运维面是连接被接受的那一刻；**终点**：中心读到请求报文的最后一个字节（头部块与请求体都收齐）。中心自身的读取延迟不算在客户端头上：到时限那一刻先把已到达的字节读尽，再判收没收齐 | **30 秒**：起点之后不到 30 秒，中心不因这个时限切断它 | **接收期间**：到了时限报文还没收齐，即判 |

- **超过任一上界、或到了接收时限报文还没收齐 ⇒ 关闭连接，不写任何字节**（问不到）。这与成帧不了同一收场：不答 `version-mismatch`（那会叫客户端去升级），也不写任何 `4xx`（EC S-7：没有第五种答复）。
- **先后**：头部里的成帧与头部块上界在读头部时判（两者收场相同，谁先谁后不影响答复）；请求体上界在头部收齐之后、读请求体之前判；请求体读满之后才有 S-7——深度与成员数在它的第 3 级里判，之后才是第 4 级、[S-9](#s-9-公开体检的请求在本传输上的形状) 的公开体检认法与 EC S-10 的判定次序。

**下限之内不被切**

- 一个请求报文**在下限之内**，指它的头部块、请求体、嵌套深度与每一个对象的成员数都不超过上表的下限，**且在接收时限的下限之内收齐**（起点之后 30 秒内，起点与终点按上表）。
  **在下限之内的请求，不被任何上界或时限切掉**：它的答复只由 [S-7](#s-7-请求体怎样读成信封)～[S-9](#s-9-公开体检的请求在本传输上的形状) 与 EC 定。
- 所以**合 EC Schema 的信封只要在下限之内，就不会被切**；公开体检请求同样——但 S-9 一概不看的其余成员让它超出下限时，它照样可能被切。
- 超出下限的请求，一个实现可能切、另一个上界取得更高的实现照常答，两者都合本契约。**合 EC Schema 却超出下限的信封是可能有的**：EC 的 Schema 对凭据材料、创建键与各不透明标识没有长度上限（[G-3](#十一已知缺口)）。

## 四、答复

### S-11 答复的外形

中心在客户端一面写出的**每一份答复**——四种入口答复、路由结果、公开体检答复——都恰为下面这串字节，没有别的形式（`\r\n` 是 CR LF 两个字节；排版上的换行不是字节）：

```text
HTTP/1.1 200 OK\r\n
Content-Type: application/json\r\n
Cache-Control: no-store\r\n
Content-Length: <体的字节数>\r\n
Connection: close\r\n
\r\n
<体>
```

- **状态一律 `200`，原因短语恰为 `OK`**。答复是哪一种只看体（[S-17](#s-17-客户端怎样读答复)）；本传输不借 HTTP 状态码表达任何判定。
- **头恰此四个、恰此次序**；名字的大小写、冒号后恰一个空格、值都如上。`Content-Length` 是体的字节数，十进制，无前导零。
- **不写** `Date`、`Server`、`ETag`、`Keep-Alive`、`Vary`、`Transfer-Encoding` 或任何别的头；不写请求编号、时间戳、原因。
- 体按 [S-12](#s-12-体的写出规则) 写出。写完按 [S-5](#s-5-一条连接恰承载一个请求答复) 的次序关闭连接。
- **本契约说的「逐字节」「固定字节」都在 HTTP 报文这一层**：约束的是上面这串报文字节，TLS 记录与传输分段怎样切不在内。
  **每一份答复作为一整串一次写出**——不先写头、再写体，也不分几次写，这样各种答复在写出的次数与先后上也没有差别。

理由：EC S-6 要同一个答复值的**整个线上答复**逐字相同。随时刻变化的头（`Date`）、随请求变化的头（跟随请求的 `Keep-Alive`）会让六种不认情形从头部被分辨出来（[PF-017 §6.5](../../../../product/PF-017-governance-center-as-deployable-application/design.md#65-拒绝的时候什么都不多说)）。

### S-12 体的写出规则

体是一份 JSON text，UTF-8 编码，按下表写出。**同一个值只有一种字节序列。**

| 值 | 写法 |
|---|---|
| 对象 | 成员按**管它的那个定义**的 `properties` **书写次序**写出（EC 的 Schema，及其所引的 IV、OE 的 Schema）。管它的定义这样定：答复的最外层是 `RouteSuccess`、`RouteFailure`、`PublicHealthReply` 或 `FullHealthReply`；**`result` 的值由这次请求的 `operation` 对应的那个 `Result_<路由>` 管**（EC Schema 的 `Exchange` 把两者配对；`RouteSuccess` 里 31 个形状的并只管外层，不决定次序）；再往里，每个成员的值、每个数组元素，由所属定义里描述它的那段子模式（或那段子模式的 `$ref` 所指的定义）管；`oneOf` 取它所合的那一支（IV 的 `MembershipStanding`、`ScopeLayerIdentity` 各支互斥）；`allOf` 里补充的约束不引入新成员，也不改次序。可选成员缺席就不写，不写 `null`（EC S-17） |
| 数组 | 按领域给出的次序写出；本传输不排序、不去重 |
| 空白 | 任何两个记号之间都没有空白：没有空格、换行、缩进 |
| 字符串 | RFC 8785 §3.2.2.2 的写法：`"` ⇒ `\"`，`\` ⇒ `\\`；U+0008、U+0009、U+000A、U+000C、U+000D ⇒ `\b`、`\t`、`\n`、`\f`、`\r`；其余 U+0000～U+001F ⇒ `\u00` 加两位**小写**十六进制；**其余一切码点原样写成 UTF-8，不转义**（含全部非 ASCII、`/`、U+007F、U+2028、U+2029）；孤立的代理码点（本不该出现）⇒ `\u` 加四位小写十六进制 |
| 整数 | 十进制数字串：无前导零、无正号、无小数点、无指数 |
| 布尔 | `true`、`false` |
| 时间点（OE 的 `Instant`：`issuedAt`、`lastActivityAt`、`absoluteExpiresAt`、`idleExpiresAt`、`startedAt`、`OfferTiming`的两个时刻） | UTC，`YYYY-MM-DDTHH:MM:SSZ`，`T` 与 `Z` 大写；秒的小数部分**只在非零时写**，写恰好表示这个时间点所需的最少位数（`08:00:00Z`、`08:00:00.25Z`、`08:00:00.123Z`）；不写 `+00:00` 一类偏移 |

- **非 ASCII 原样写 UTF-8、不转义**，理由：RFC 8259 §8.1 定的交换编码就是 UTF-8，原样写是唯一最短的形式，而且与 RFC 8785 的字符串写法逐字一致——任何语言都能照一份外部规范复现同一串字节。
- 时间点那一行是在 OE 的 `Instant` 允许的写法（带偏移的 RFC 3339，[OE S-22](../../../data/offer-expiry/v2/contract.md#s-22-schema-的范围)）里取定一种：OE S22定义允许的时间表示，本传输在其中选定唯一字节写法，而本传输要同一个值只有一种字节。

### S-13 四种入口答复的固定字节

四种入口答复的体就是那个值的 JSON 字符串（EC Schema `EntryAnswer`）；按 [S-11](#s-11-答复的外形)、[S-12](#s-12-体的写出规则)，**每一种的完整答复是一份固定字节**：

| 答复 | 体 | 体的字节数 | 完整答复的字节数 | 完整字节 |
|---|---|---|---|---|
| `version-mismatch` | `"version-mismatch"` | 18 | 133 | [examples §1](examples.md#1-version-mismatch) |
| `login-state-rejected` | `"login-state-rejected"` | 22 | 137 | [examples §3](examples.md#3-另三种入口答复) |
| `unavailable` | `"unavailable"` | 13 | 128 | [examples §3](examples.md#3-另三种入口答复) |
| `invalid-input` | `"invalid-input"` | 15 | 130 | [examples §3](examples.md#3-另三种入口答复) |

- **同一个答复值每一次都是这份字节**，与请求的方法、路径、头、连接、时刻、来者都无关（EC S-6）。EC S-11 的六种不认情形、EC S-33 那次落在认人与办事之间的撤销，在线上都是 `login-state-rejected` 这 137 个字节（[PF-017 §6.5](../../../../product/PF-017-governance-center-as-deployable-application/design.md#65-拒绝的时候什么都不多说)）。
- 这四份字节是 [examples.md](examples.md) 与入口层 T-2 固定字节快照的共同来源；任何一个字节不同，就是违反本条。

### S-14 路由结果答复

- 体是 `{"result":…}` 或 `{"failure":"<具名值>"}`（EC S-7；Schema `RouteSuccess`、`RouteFailure`）；`result` 的值按这次请求的 `operation` 对应的 `Result_<路由>` 写出（[S-12](#s-12-体的写出规则) 的「对象」一行）。
- 外形照 [S-11](#s-11-答复的外形)：状态行与另三个头逐字节不变，**`Content-Length` 随体变化**。
- 同一个路由结果值只有一种字节；同一个具名失败值每一次都是同一份字节。一份实例在 [examples §4](examples.md#4-一份路由结果答复)。

### S-15 公开体检答复

- 体是 EC 的 `PublicHealthReply`：`{"reachable":true,"centerId":"<治理中心标识>","version":"<版本>"}`——成员恰此三个、恰此次序（Schema 书写次序），按 [S-12](#s-12-体的写出规则) 写出；外形照 [S-11](#s-11-答复的外形)。
- 一次运行期间三样不变（EC S-18），**所以一次运行期间公开体检答复是一份固定字节**；它随中心的标识与所装版本而不同，形状不变（[PF-017 §4 中心体检](../../../../product/PF-017-governance-center-as-deployable-application/design.md#中心体检)、[§6.17](../../../../product/PF-017-governance-center-as-deployable-application/design.md#617-体检只说部署不说里面有谁)）。
- **形状跨协议版本不改**（[S-18](#s-18-跨协议版本不改的两样在本传输上)）：状态行、四个头及其次序、体的三个成员及其次序、它们的写法。实例在 [examples §2](examples.md#2-公开体检的请求与答复)。

### S-16 问不到：不写任何答复字节

下列情形，中心**关闭连接，不写任何答复字节**；来者看到的是问不到，**不是**四种入口答复之一：

| 情形 | 依据 |
|---|---|
| 客户端一面还没开始应答（启动中） | EC S-34：起来即整体 |
| 停止接受新请求的那一刻，这个请求**不在途**——报文还没完整收到 | EC S-34：停机先停收 |
| 停机时在途的请求没在排空上界之内答完 | EC S-34：来者可能收不到答复，提交结果可能未知；不从断线推导未提交 |
| 参与方提供者换代期间到达的新请求 | EC S-34 |
| 报文成帧不了、超过接收上界 | [S-10](#s-10-只答完整收到能成帧的请求报文) |
| TLS 握手不成（明文、版本低于 1.3） | [S-4](#s-4-客户端一面的连接只有-tls服务端认证) |

**EC S-34 的「在途」在本传输上的读法：请求报文已完整收到——头部与请求体都齐了。**停止接受新请求时，报文已完整收到的请求在途，在排空上界之内照常判、照常答；报文还没收齐的连接直接关闭、不写任何字节，此后也不再读它。运维面同一读法（[S-20](#s-20-运维面的承载)）。

「不写任何答复字节」指 HTTP 层一个字节都不写。**关闭方式**：TLS 握手已完成的连接，中心先发 `close_notify`（RFC 8446 §6.1；RFC 9112 §9.8）再关闭传输，不主动以重置结束；接收缓冲里还有没读的字节时（如 `Content-Length` 超上界、不读请求体就关），传输层仍可能以重置收场（RFC 9112 §9.6），对端看到的同样是问不到。握手没完成的连接怎样结束本契约不定。
写出了答复、却在 [S-5](#s-5-一条连接恰承载一个请求答复) 的读尽超界时被立即全关的，对端也可能收不全——对它同样是问不到。

EC2 S34/S49/S52要求完整业务工作由入口拥有，包含事务外凭据准备。运输停止等待、关闭连接或超出排空等待上界不证明这些工作静止；装配必须在其真实结束或明确失败收场后才释放依赖，不能凭运输drain完成关闭数据库。

### S-17 客户端怎样读答复

任何客户端（据点侧的客户端代理在内）按下面四步读本传输上的答复。这是EC S6/S7/S14的闭合答复与失败映射在客户端的读取规则：

1. 按 HTTP/1.1 读完一份答复：状态行、头，再按 `Content-Length` 读满体。**连接在此之前关闭、超时、TLS 失败、读到的不是一份 HTTP/1.1 答复** ⇒ **问不到**——不显示成「没有」「无效」或任何一种答复（[PF-016 flows §二](../../../../product/PF-016-cli-tui-delivery-surface/flows.md#二分支与异常)：治理中心不可达）。
2. **体逐字节等于 `"version-mismatch"` 这 18 个字节 ⇒ `version-mismatch`。**这一步只看体，不依赖状态行与头。
   **这就是客户端认出 `version-mismatch` 的办法，跨协议版本不改**（[S-18](#s-18-跨协议版本不改的两样在本传输上)；[PF-017 §6.16](../../../../product/PF-017-governance-center-as-deployable-application/design.md#616-版本对不上就明说)；PF-016 flows §二：明说是版本对不上）。
3. 否则把体按 JSON 读：对公开体检请求只接收`PublicHealthReply`；其余请求的入口字符串、`{"result":…}`及`{"failure":…}`都必须与本次operation一起满足EC2 Schema的Exchange配对。另三个入口字符串不是所有路由都可返回；集合外按第4步处理。
4. 状态不是 `200`、体读不成 JSON、读成的值不属于这次请求应得的那一类 ⇒ 按**问不到**处理，并作为对端异常记下；**不猜它是什么**。

- 客户端**不以** HTTP 状态码或头区分答复：状态行与头是固定的，区分只靠体。
- 带 `Expect: 100-continue` 的客户端不得等 `100 Continue` 才发请求体——中心不写它（[S-5](#s-5-一条连接恰承载一个请求答复)）。
- 客户端在一条连接上只发一个请求报文，发完不再写：中心对之后的字节只读尽丢弃，超出读尽上界就立即全关，已写出的答复可能因此收不全（[S-5](#s-5-一条连接恰承载一个请求答复)）。

### S-33 与 HTTP 规范的有意偏离

本传输在下列几处**有意不照** RFC 9110／9112 的要求办。每一处都出自同一个理由：EC S-6 要同一个答复值的整个线上答复逐字相同、EC S-7 要答复集合闭合——照办就会让答复随请求的方法或头而变，或多出四种入口答复之外的第五种答复。
**本表的范围**：已按下列各节逐条核过 RFC 9110 §5.4、§5.5、§6.6.1、§7.4、§7.8、§8.4、§8.6、§9.3.1、§9.3.2、§9.3.6、§10.1.1、§13.1、§13.2（含 §13.2.1）与 RFC 9112 §2.2、§3、§3.2、§5.1、§5.2、§6.1、§6.3、§7.1、§9.6、§9.8，以及 RFC 8446 §4.2.10、§6.1——这些节里凡「必须」（MUST／MUST NOT）与本契约相违的，都在下表有一行；「应当」（SHOULD）级只举例，不保证列全。**未逐条核过的节不在此声明之内。**

| RFC 的要求 | 本传输怎样做 | 条款 |
|---|---|---|
| RFC 9112 §3.2：请求缺 `Host`、`Host` 不止一个或值不合法，服务端必须答 `400` | 不看 `Host`，照常判、照常答 | [S-6](#s-6-只看请求体) |
| RFC 9110 §9.3.2：对 `HEAD` 请求，服务端必须不写内容 | 对任何方法都照答、带体；`HEAD` 得到与 `POST` 同一份字节。客户端一律用 `POST`，所以这一处只落在不守本契约的来者身上 | [S-6](#s-6-只看请求体) |
| RFC 9110 §10.1.1：头部收齐、带 `100-continue` 且有请求体要来时，源服务器必须立即给出终态答复或立即写 `100 Continue`，不得等请求体 | 不写 `100 Continue`，等请求体收齐再答 | [S-5](#s-5-一条连接恰承载一个请求答复) |
| RFC 9110 §6.6.1：有钟的源服务器必须在每份 2xx 答复里写 `Date` | 不写 `Date`：答复不得随时刻变（EC S-6） | [S-11](#s-11-答复的外形) |
| RFC 9110 §5.4：请求头部字段大过愿意处理的，服务端必须答对应的 `4xx` | 头部块超上界即关闭连接、不写任何字节 | [S-10](#s-10-只答完整收到能成帧的请求报文) |
| RFC 9110 §7.4：源服务器必须拒绝目标 URI 的方案要求未满足的请求——`https` 资源的请求须来自持有对该目标源有效的证书的连接，否则拒绝（`421`） | 不看请求目标与 `Host`，不核证书与目标源是否对应，照常判、照常答。中心只出示 config 里的那一份证书链（[S-4](#s-4-客户端一面的连接只有-tls服务端认证)）；它对不对得上客户端要找的中心，归客户端核（[S-3](#s-3-本契约明确不承诺什么)、[G-2](#十一已知缺口)） | [S-6](#s-6-只看请求体) |
| RFC 9110 §9.3.6：服务端必须拒绝端口为空或不合法的 `CONNECT` 请求（典型答 `400`）；对 `CONNECT` 的 2xx 答复表示隧道已建立、不得带 `Content-Length` | 不看方法与请求目标：`CONNECT host: HTTP/1.1` 这类请求只要能成帧（authority-form 的 port 是 `*DIGIT`，空端口合 ABNF），照答同一份带 `Content-Length` 的 `200`，不建隧道；客户端一律用 `POST` | [S-6](#s-6-只看请求体) |
| RFC 9110 §13.1、§13.2：源服务器必须评估收到的前置条件头（`If-Match` 等），为假时不得执行方法 | 不看任何请求头，前置条件一律不评估 | [S-6](#s-6-只看请求体) |
| RFC 9112 §6.1、§7.1：接收方必须能解析分块传输编码 | 头部有 `Transfer-Encoding` 就成帧不了，关闭连接、不写任何字节 | [S-10](#s-10-只答完整收到能成帧的请求报文) |
| 成帧不了或超界时写状态码：RFC 9112 §5.1（字段名与冒号间有空白，必须答 `400`）、§5.2（obs-fold，必须答 `400` 或把它换成空格）、§6.3 第 4、5 条（体长定不下来或 `Content-Length` 不合法，必须答 `400` 再关闭）、§3（请求目标长过愿意解析的，必须答 `414`）；以及「应当」级的 `501`（§3、§6.1） | 一律关闭连接，不写任何字节（问不到）。也不答 `version-mismatch`：那会叫客户端去升级 | [S-10](#s-10-只答完整收到能成帧的请求报文) |

**「应当」级的偏离（举例，不保证列全）**：请求行之前的空行不忽略、语法不合的请求不答 `400`（RFC 9112 §2.2、§3 的「应当」）；`TRACE` 不回显（RFC 9110 §9.3.8）；成帧不了时不答 `501`（§3、§6.1）。

**不是偏离的几处**（规范本就允许，列出来免得被当成偏离）：单独 LF 不认作行终止（RFC 9112 §2.2 只说接收方「可以」认）；`Upgrade` 不切换协议（RFC 9110 §7.8 允许忽略）；`Content-Encoding` 不解码（RFC 9110 §8.4 的 `415` 是「可以」）；不收 TLS 早期数据（RFC 8446 §4.2.10 给出的忽略方式之一）；写完答复即按 RFC 9112 §9.6 的次序关闭连接；握手完成后的每一次关闭都先发 `close_notify`（RFC 8446 §6.1、RFC 9112 §9.8 的「必须」，[S-16](#s-16-问不到不写任何答复字节)）。

## 五、跨协议版本

### S-18 跨协议版本不改的两样，在本传输上

EC [S-8](../../governance-center-entry/v2/contract.md#s-8-协议版本与跨版本不变的两样) 说跨所有协议版本不变的两样，在本传输上是下面这些字节与读法。**本传输承载任何协议版本时都照此，不改**：

| EC S-8 的一样 | 在本传输上不改的 |
|---|---|
| **`version-mismatch` 这个答复**的形状与字节 | [examples §1](examples.md#1-version-mismatch) 的 133 个字节，逐字节；客户端认出它的办法：体逐字节等于那 18 个字节（[S-17](#s-17-客户端怎样读答复) 第 2 步） |
| **公开体检**的请求形状与答复形状 | 请求：客户端以 `POST`、以 `Content-Length` 成帧，请求体是恰有一个 `operation` 成员、其值为 `composition.governance-center-entry/v1#S-18` 的 JSON 对象；中心只看请求体，其余成员一律不看（这是认法；它是否先于 ① 判归 [G-4](#十一已知缺口)），方法、路径、头一律不看（[S-6](#s-6-只看请求体)、[S-9](#s-9-公开体检的请求在本传输上的形状)；请求在下限之内时——超出仍可能被切，S-9、S-10）。答复：状态行、四个头及其次序、体的三个成员及其次序、[S-12](#s-12-体的写出规则) 的写法（[S-15](#s-15-公开体检答复)） |

为了让这两样在任何协议版本旁边都**够得着、认得出**，下面几条是本传输自己的事实，同样不改：

- **够得着**：客户端一面的承载是 HTTP/1.1 over TLS，**TLS 最低版本 1.3，服务端认证方式**是中心以部署配置给出的证书链与对应的私钥在握手里认证自己、不要求客户端证书（[S-4](#s-4-客户端一面的连接只有-tls服务端认证)）。
  理由：持旧版本的客户端得先握得上手，才看得见版本对不上；换证书不在此列（S-4：改部署配置、重启），改的是材料，不是方式。
- **下限**：[S-10](#s-10-只答完整收到能成帧的请求报文) 四项接收上界与接收时限的下限（头部块 8 KiB、请求体 64 KiB、嵌套深度 64、对象成员数 1024、接收时限 30 秒）。上界与时限的取值可以随实现不同，下限不降。
  本条以下说「请求在下限之内」的，含「在接收时限的下限之内收齐」（S-10）。
- **EC ① 的出口在本传输上一律是那 133 个字节**：任何协议版本下，凡 EC S-10 判到 ① 的请求，本传输写出的都是 examples §1 那份字节（请求在下限之内时）。
  **哪些请求落进 ①，照 EC S-10**——本版是：请求体按 [S-7](#s-7-请求体怎样读成信封) 读不下来、`protocolVersion` 缺席、重复或不被接受；这些触发条件是否跨协议版本不改归 [G-4](#十一已知缺口)，本条不冻结它们。
  [S-7](#s-7-请求体怎样读成信封) 的读法本身（字节怎样读成 JSON 值）是本传输的事实，跨协议版本不改。
- **任何协议版本的任何其他答复，体都不等于那 18 个字节**——否则 [S-17](#s-17-客户端怎样读答复) 第 2 步会把它认成版本对不上。

**判定次序是 EC 的，不是本条冻结的**：公开体检请求得公开体检答复、不经版本那一关，是 EC S-10 第 0 步排在 ① 之前的结果；本传输在本版承载的每个协议版本上都照这个次序（请求在下限之内时）。
本条冻结的只是那两样**在本传输上的形状与字节**；「第 0 步先于 ①」是否随 EC S-8 的那两样一起跨协议版本冻结，EC2仍未冻结这项跨未来版本的承诺，保留G4，由EC owner明确（[G-4](#十一已知缺口)）。

**只要还是本传输，上面这些就不改**：本契约的任何后续版本若仍是本传输，都照抄本条；要改它们只能换传输（[S-19](#s-19-随协议版本演化的部分换传输)）。
理由：版本对不上的客户端正要靠这两样看见「对不上的是哪一版」「连的还是不是原来那个中心」（[PF-017 §6.16](../../../../product/PF-017-governance-center-as-deployable-application/design.md#616-版本对不上就明说)）；只钉形状而让它们的字节、或够着它们的办法随版本变，版本对不上的客户端照样认不出（EC S-8 末段）。

### S-19 随协议版本演化的部分；换传输

- **其余三种入口答复的字节、路由结果的头与写出规则**：在同一个协议版本之内逐字节不变（[S-13](#s-13-四种入口答复的固定字节)、[S-14](#s-14-路由结果答复)）。
  本版给出的这一份，适用于本版承载的每一个协议版本（`accepted_protocol_versions` 取什么值都一样）；将来某个协议版本要改它们，随本契约的新版本发布，不在本版上改。
  **一个中心同时接受多个协议版本时，按请求的 `protocolVersion` 所属的那个版本的绑定写答复；`version-mismatch` 永远是本绑定冻结的那 133 个字节**（[S-18](#s-18-跨协议版本不改的两样在本传输上)）。本版承载的协议版本就是 `accepted_protocol_versions` 里的全部，都映射到本绑定；将来的绑定版本须声明它承载哪些协议版本，映射随构建定、不在运行期协商。
- **换传输**（HTTP/2、经网关、换请求体的编码……）= 发一份**新的传输绑定**，不改本版。两份绑定可以并存，各自的那两样（[S-18](#s-18-跨协议版本不改的两样在本传输上)）各自冻结。
  **按 EC S-8，客户端认出 `version-mismatch` 的办法与发出公开体检请求的办法必须跨协议版本不变**——所以中心改用或加用别的绑定之后，对按本绑定来的请求仍必须以 S-18 的字节与读法应答；停用本绑定不是换一个协议版本可以带来的变化。
- 运维面的承载（[S-20](#s-20-运维面的承载)）改了，是新版本的绑定。TLS 最低版本与服务端认证方式不在此列：它们在 S-18 的不变集里。

## 六、运维面

### S-20 运维面的承载

| 项 | 性质 |
|---|---|
| 通道 | 运维面承载在**一个 Unix 域套接字**上，套接字文件在部署配置给出的一个目录下，**文件名恰为 `governance-center-ops.sock`**——运维者连的就是「那个目录／`governance-center-ops.sock`」这一个路径。**与客户端一面不共用任何通道**：客户端一面的 TLS 端点上没有运维面，这个套接字上也没有客户端一面（EC [S-25](../../governance-center-entry/v2/contract.md#s-25-运维面只在中心所在的机器上且没有治理路由)；[PF-017 §5.1](../../../../product/PF-017-governance-center-as-deployable-application/design.md#51-中心有两张面没有第三张)） |
| 只在本机可达 | 由这台机器的操作系统的文件访问控制兑现：那个目录**只对中心的运行用户可访问**——所有者是运行用户，组与其他用户没有任何权限位。**不满足 ⇒ 启动失败**；中心不替运维者改权限，也不在别处另开 |
| 目录不存在 | 启动失败；中心不替运维者建这个目录 |
| 启动时那个位置上已有文件 | 是套接字、**有人在听** ⇒ 另一个中心实例在用它 ⇒ **启动失败**，不抢占；是套接字、**没人在听** ⇒ 上次留下的残留，替换它；**不是套接字** ⇒ 启动失败，不删它 |
| 承载 | 套接字上是明文的 HTTP/1.1；[S-5](#s-5-一条连接恰承载一个请求答复) 的一连接一请求与写完后的关闭次序（没有 TLS，关写方向就是关套接字的写方向）、[S-10](#s-10-只答完整收到能成帧的请求报文) 的成帧与接收时限（下限同样 30 秒）同样适用。**适用的接收上界只有头部块与请求体两项**，下限同 S-10；嵌套深度与对象成员数不适用——运维面不读请求体的内容（[S-21](#s-21-运维面的答复)）。没有 TLS：可达性由上面的文件访问控制给出，不经网络 |
| 什么时候应答 | **只在客户端一面应答的那段时间里应答**（EC [S-34](../../governance-center-entry/v2/contract.md#s-34-起来即整体停机时在途请求归谁) 同起同停）：客户端一面开始应答之前，运维面收到连接即关闭，不写任何字节（问不到）。停止接受新请求时，与客户端一面同一读法（[S-16](#s-16-问不到不写任何答复字节)）：报文已完整收到的在途，照答；还没收齐的连接直接关闭、不写任何字节；此后新到的连接即关闭 |

够得到这个套接字的，就是握着那台机器的人——[运维者](../../../../product/PF-017-governance-center-as-deployable-application/design.md#运维者)（EC S-25）。

### S-21 运维面的答复

- **不看请求内容**：一个能成帧的请求报文，不论方法、路径、头、体是什么，都答**完整体检**（EC [S-26](../../governance-center-entry/v2/contract.md#s-26-完整体检)）。没有路由，也就没有第二个操作可加（EC S-25：运维面恰有一个操作）。发到运维面的信封、公开体检请求，得到的也是完整体检。
- 答复外形照 [S-11](#s-11-答复的外形)：状态行与四个头的名字、次序逐字节相同，`Content-Length` 随体。体是 EC 的 `FullHealthReply`，按 [S-12](#s-12-体的写出规则) 写出：十个成员按 Schema 书写次序——
  `reachable`、`centerId`、`version`、`startedAt`、`storageReachable`、`deploymentKeyPresent`、`deploymentKeyComplete`、`clockSane`、`defectCount`、`deploymentParameters`；`deploymentParameters` 里的五项同样按书写次序。
- 完整体检随读取的时刻变化（`storageReachable`、`clockSane`、`defectCount` 每次现读，EC S-26），**不是一份固定字节**；固定的是它的形状（[PF-017 §4 中心体检](../../../../product/PF-017-governance-center-as-deployable-application/design.md#中心体检)、[§6.17](../../../../product/PF-017-governance-center-as-deployable-application/design.md#617-体检只说部署不说里面有谁)）。实例在 [examples §5](examples.md#5-运维面的完整体检答复)。

## 七、秘密

### S-22 经传输的秘密

- **TLS 私钥按秘密处理**：不进任何输出——客户端一面的答复、两种体检、工程记录、启动失败的说明（EC S-29 列出的输出范围）。证书链不是秘密。
- **请求目标（路径与查询）、请求头与请求体的值不原样进任何输出**：请求体可能带出示物（EC S-29），请求头与请求目标可能带客户端放错位置的出示物（[S-6](#s-6-只看请求体) 的 `Authorization`；查询串里的令牌）或指认来者用的是哪个程序的东西（EC S-16：不登记来者是哪台机器、哪个程序）。
  工程记录按 EC S-30 记入口层观察到的判定，不记报文本身。
- 出示物在途中的机密性由 TLS 兑现（[S-4](#s-4-客户端一面的连接只有-tls服务端认证)；[PF-017 §8](../../../../product/PF-017-governance-center-as-deployable-application/design.md#八边界与依赖)），前提见 [S-24](#s-24-装配给-vs-协议给)。

## 八、一次来往；装配给与协议给

### S-23 两张面上一次来往的九件事

本传输不新增任何操作；下表是 EC 的每个操作在本传输上共同的那九件事。两张面指 [PF-017 §5.1](../../../../product/PF-017-governance-center-as-deployable-application/design.md#51-中心有两张面没有第三张) 的那两张：

| 九件事 | 客户端一面 | 运维面 |
|---|---|---|
| **1 输入与授权** | 一条 TLS 连接上的一个 HTTP/1.1 请求报文，只看请求体（[S-6](#s-6-只看请求体)）。本传输不做任何授权：认人在 EC S-10 第 ② 步，只看体里的出示物 | 本机套接字上的一个请求报文，内容一概不看（[S-21](#s-21-运维面的答复)）；授权就是够得着那个套接字（[S-20](#s-20-运维面的承载)） |
| **2 前置** | TLS 1.3 握手成功（[S-4](#s-4-客户端一面的连接只有-tls服务端认证)）；报文只按 `Content-Length` 成帧、在接收时限内收齐、不超过接收上界（[S-10](#s-10-只答完整收到能成帧的请求报文)；在下限之内就一定不超过）；客户端一面在应答 | 客户端一面在应答（[S-20](#s-20-运维面的承载)）；报文能成帧、在接收时限内收齐、不超过头部块与请求体两个上界 |
| **3 提交点与原子性** | **本传输不提交任何东西**；写出答复不是提交。路由的提交点照 EC S-17 第 3 件事；答复写出之前或之中连接断了，事实照 EC：要么已提交、要么没发生 | 无：纯读 |
| **4 返回与失败集合** | 恰为下列之一：[S-13](#s-13-四种入口答复的固定字节) 的四份固定字节之一；[S-14](#s-14-路由结果答复) 的一份路由结果；[S-15](#s-15-公开体检答复) 的公开体检答复；**或不写任何字节**（[S-16](#s-16-问不到不写任何答复字节)）。没有第五种：没有 `4xx`、`5xx`、`1xx`、错误页、空答复 | 恰为一份完整体检答复（[S-21](#s-21-运维面的答复)），或不写任何字节（[S-20](#s-20-运维面的承载)「什么时候应答」、[S-10](#s-10-只答完整收到能成帧的请求报文)） |
| **5 幂等与重发** | 本传输没有请求编号、不去重；重发就是新连接上的新请求，得到它在那一刻的答复（EC S-3、S-17 第 5 件事） | 纯读，任意重复 |
| **6 事件** | 无 | 无 |
| **7 缺席时的默认答案** | 请求体缺席或为空 ⇒ `version-mismatch`（[S-7](#s-7-请求体怎样读成信封) 第 3 级；RFC 9112 §6.3 第 7 条：没有 `Content-Length` 的请求体长为 0）；出示物缺席照 EC（经第 ② 步的路由 `login-state-rejected`）；`Host` 等头缺席不影响（[S-6](#s-6-只看请求体)）；中心不在应答 ⇒ 不写答复。**没有任何一项缺席被补成默认值** | 请求内容缺什么都不影响答复 |
| **8 在途归属** | 本传输没有跨连接的状态；答复写完即按 [S-5](#s-5-一条连接恰承载一个请求答复) 的次序关闭。停机时在途的请求（报文已完整收到）在排空上界内答完，否则不答；报文还没收齐的连接直接关闭（[S-16](#s-16-问不到不写任何答复字节)）；那件事的事实归 EC S-34 | 同左（[S-20](#s-20-运维面的承载)「什么时候应答」） |
| **9 装配给／协议给** | [S-24](#s-24-装配给-vs-协议给) 除「运维面只在本机可达」外的各行 | [S-24](#s-24-装配给-vs-协议给)「运维面只在本机可达」「两张面不共用通道」两行 |

### S-24 装配给 vs 协议给

**本传输本身就是进程边界**：客户端与中心各在一个进程里，多半各在一台机器上。所以本契约的保证**几乎都是协议给的**——由本契约写死的字节与读法兑现，不依赖两端同在一处；
只有运维面的可达性靠同一台机器上的操作系统给。每一行写做不到会怎样：

| 保证（来源） | 装配给：部署与本机的前提 | 协议给：本契约的字节与读法 | 做不到会怎样 |
|---|---|---|---|
| **整个线上答复逐字相同**（EC S-6） | — | [S-11](#s-11-答复的外形)、[S-13](#s-13-四种入口答复的固定字节)：四份固定字节，每份一次写出；无 `Date`、无随请求变化的头、无 `1xx`；与 HTTP 规范相违处按 [S-33](#s-33-与-http-规范的有意偏离) 偏离 | 六种不认情形从头部、长度或时刻被分辨出来——[PF-017 §6.5](../../../../product/PF-017-governance-center-as-deployable-application/design.md#65-拒绝的时候什么都不多说)被破 |

## 九、规范表达与证据义务

### S-25 形式工件：不触发

本契约不新增任何跨连接的状态、并发或交错性质：判定次序与答复闭合归 EC（它的 TLA+ 模型已检查到「同一个答复值」为止）；本契约把那些值落成字节、把字节读成值，都是逐请求的纯映射；
[S-5](#s-5-一条连接恰承载一个请求答复) 的关闭次序与 [S-16](#s-16-问不到不写任何答复字节) 的「在途」读法都只涉及一条连接自己的先后，没有两条连接之间的交错。
「同一个值只有一种字节」「哪一类请求体归哪一步」「下限之内不被切」「写完怎样关闭」的证据是字节快照、逐例测试与真实组合（[验证入口](../verification.md#证据义务) V-1～V-9、V-11），模型检查给不出比它们更强的东西。
**不建 Schema**：形状全在 EC 的 Schema 里，本契约只引用它的 `$id` 与定义名（[S-2](#s-2-依赖与精确承诺)）。

### 规范场景

场景约束来者可观察的字节，检查真实组合；执行状态在[验证入口](../verification.md)，不写进本版本目录。
下列场景假定 `accepted_protocol_versions` 含 `"2"`、不含 `"0-obsolete"`（取值不归本契约）。

### S-26 规范场景：固定字节，只看请求体

对四种入口答复各造一个请求，完整答复与 [examples.md](examples.md) 逐字节相同。
取一个没带出示物、`operation` 为 `capability.organization-governance/v2#S-27` 的信封（得 `login-state-rejected`），改用 `GET`、`PUT`、`HEAD`，改路径，加上 `Connection: keep-alive`、`Expect: 100-continue`、`Authorization: Bearer <一个有效出示物>`，去掉 `Host`，各发一次：**每一次都是那 137 个字节，此外一个字节都没有**。
**前提**：客户端发完请求报文就不再写，或之后多写的字节不超过读尽上界（[S-5](#s-5-一条连接恰承载一个请求答复)）；超过时中心立即全关，客户端可能收不全这份答复，那是 S-5 允许的收场，不算违反本场景。
公开体检请求以 `GET /x` 与 `POST /` 各发一次：两份答复逐字节相同。
依据：[acceptance §三「拒绝逐字相同」「只认登录状态，不认客户端」](../../../../product/PF-017-governance-center-as-deployable-application/acceptance.md#三判据)。

### S-27 规范场景：跨协议版本

同一个请求体（`protocolVersion` 为 `"0-obsolete"`、带一个有效出示物）分别发给两个 `accepted_protocol_versions` 取值不同的中心构建：**两次都是 examples §1 那 133 个字节**。
同一份公开体检请求发给两者：两份答复的状态行、头及其次序、体的成员及其次序相同。
依据：[acceptance §三「答复的先后」「版本对不上就明说」](../../../../product/PF-017-governance-center-as-deployable-application/acceptance.md#三判据)。

### S-28 规范场景：请求体的读法与重复成员

[examples §6](examples.md#6-请求体的读法与重复成员) 表里的每一行，线上答复都等于表里写的那一种。其中必须真跑的三支：
BOM 开头的有效信封得 `version-mismatch`（不被跳过）；以 `"operation"` 写出的第二个 `operation` 得 `invalid-input`（名字还原后比较）；
两个出示物其一有效得 `login-state-rejected`（不被取其一）。
**恰在下限上的请求照常得答复**（[S-10](#s-10-只答完整收到能成帧的请求报文)）：头部块恰 8192 字节、请求体恰 65536 字节、嵌套恰 64 层、某个对象恰 1024 个成员，各造一例。
四例都以公开体检请求加填充构造——填充放在一个多余的请求头里，或放在 `operation` 之外的成员里（中心一概不看）——**都得公开体检答复，一个也不被切**。
另造一例：接收时限的起点（S-10：握手完成）之后慢慢发，直到接近 30 秒（接收时限的下限）才发完最后一个字节的公开体检请求，同样照常得到答复。
依据：[acceptance §三「答复的先后」](../../../../product/PF-017-governance-center-as-deployable-application/acceptance.md#三判据)。

### S-29 规范场景：问不到与运维面

开门之前、停机开始之后各发一个请求：**一个字节都收不到**。停机开始的那一刻，报文已完整收到的请求在排空上界内得到它的答复；只发了一半报文的连接被关闭，一个字节都收不到。
头部带 `Transfer-Encoding: chunked`、以单独 LF 结尾的头部行、obs-fold 续行、字段名与冒号之间有空白、两个不同的 `Content-Length`：各发一次，都**一个字节都收不到**，也收不到任何 `4xx`（[S-10](#s-10-只答完整收到能成帧的请求报文)、[S-33](#s-33-与-http-规范的有意偏离)）。
向运维面的套接字 `governance-center-ops.sock` 以任意方法、路径、体各发一次：都得完整体检，体的成员次序如 [S-21](#s-21-运维面的答复)，不含任何治理事实与秘密。
把目录权限改成组可读再启动：起不来；留一个有人在听的套接字文件再启动：起不来，那个文件还在；留一个没人听的：起得来。
依据：[acceptance §三「体检只说部署」「运维者没有门」](../../../../product/PF-017-governance-center-as-deployable-application/acceptance.md#三判据)。

### S-30 规范场景：只有 TLS，服务端认证

向客户端一面的端口发明文 HTTP 请求：一个 HTTP 字节都收不到。只提供 TLS 1.2 的客户端：握不了手。
握手里出示的证书链与部署配置给的那一份逐字节相同；拿掉证书链或私钥、或换一把不配的私钥再启动：起不来。
中心签发的会话票据都不许早期数据；客户端以早期数据送出一份写路由的请求：它不被当作请求，那件事没有发生（[S-4](#s-4-客户端一面的连接只有-tls服务端认证)）。
跑完其余场景后，在全部答复、两种体检、工程记录与启动失败说明里搜私钥、各请求的原始请求目标与原始请求头：一处都搜不到（[S-22](#s-22-经传输的秘密)）。
依据：[acceptance §二「冒牌货」一行](../../../../product/PF-017-governance-center-as-deployable-application/acceptance.md#二绝不能发生的事)（客户端把报出同一个中心标识的冒牌货当成中心——本场景只验中心一侧的那一半，客户端一侧归 [G-2](#十一已知缺口)）；[PF-017 §8](../../../../product/PF-017-governance-center-as-deployable-application/design.md#八边界与依赖)。

## 十、版本差异与规范工件

### S-31 版本差异

相对冻结HT1：精确依赖为EC2/OE2/IV1，路由配对消费EC2的31路由及AR2注册；新增有限登录时间字段的规范写法，入口字符串也按路由校验。TLS1.3、HTTP成帧、只看体、固定错误字节、公开体检v1路由/三字段、运维通道沿用。注册/改密的完整业务生命周期归EC2，运输关闭不代表已取消。binding短名https-json/2与线上protocolVersion不同；构建必须显式指定映射，不由版本号相同推断。规范样例假设测试构建明确将字符串"2"映射到本绑定；不要求所有消费者把任意协议版本自动视为兼容。

### S-32 本版的规范工件

本文件与 [`examples.md`](examples.md)；与 catalog 登记的 `resources` 一致。
**不建 Schema、不建形式工件**（[S-25](#s-25-形式工件不触发)）。接受状态、冻结记录与执行结果都在本版本目录之外维护，本文件不填进度、通过状态或哈希。
