## 变化的影响

- **`data.content-blocks` v1 尚未定型**（2026-09-23 起草时记）。本契约 `$ref` 它的 `ContentBlock`、`AttachmentRef`、`CapabilityId`、`Modality`、`MediaType`，
  正文引用它的 `ExecutionOutcome`、「工具结果块里不得含工具调用块」（`call_in_result`）与「块的模态由媒体类型决定」两条规则。
  **它定型时要做的事**：
  ① 核对这五个 `$defs` 名仍在、形状与本包实例的写法一致（`id`、`kind`、`visibility`、`text`；`storage`、`key`、`mediaType`、`bytes`、`name`；`category`、`name`）——
  不一致则改本包 `examples.md` 第 3、7、8 节与 Schema 的引用，**Schema 若要改就要重跑 V-1**；
  ② 把 catalog 里这条依赖的 `clauses` 从 `$defs` 名与规则名换成那份契约的 `S-n`，把契约正文里的纯文本指称换成带坐标的链接；
  ③ 核对它给语音、图块定的「内联字节」写法——本包 `Offload.raw` 的内联形式照它写了一份（成员名 `inline`、base64），**两处应收成一份定义**（已报主线）；
  ④ 核对它的 `TextBlock.text` 是否允许空串——裸字符串 `""` 按 [S-20](v1/contract.md#s-20-两种写法与等价规则) 等价于一个 `text` 为空的文本块。
  **在它定型并与本包对齐之前，本包的 V-1 无法运行**，设计检查器在本包所在的检出里也会把这些引用报成未解析。
- **`JsonSchema` 引用官方元 schema 与设计检查器的冲突**（2026-09-23 起草时记）：按施工简报账本，`$defs/JsonSchema` 以 `$ref` 指向
  `https://json-schema.org/draft/2020-12/schema`；设计检查器只解析登记在 catalog 里的 Schema 资源，**会把它报成 unresolved schema resource**，
  而且 `data.content-blocks` 合入之后这一条仍在。**已报主线裁定**（改检查器还是改表示）；裁定落地前本包的检查器结果不会全绿。
- **[G-3](v1/contract.md#十已知缺口) 改判**（生成规则）：[S-7](v1/contract.md#s-7-多命令-input-的生成规则) 与 `examples.md` 第 2、9 节整段重写，V-2 重做；**候选期内原地改**。
  V-9 不受影响——它断言的是「以所选命令自己的 input 判参数」，与生成规则怎么改无关。
- **任一已知缺口被裁决**而改变语义或表示：候选期内原地改并在此记一行；**接受之后出 v2**，本版证据只保留原范围。
- **跨进程演化启动**：[第七节](v1/contract.md#七装配给与协议给)标「须由协议兑现」的三行（同一份定义、`help` 读同一版本、每个边界重新校验）从装配给转为协议给；本版证据只保留其单机范围。

结果不改写规范。发现语义问题回到来源设计（PF-006／PF-002／PF-005），不在这里改契约。
