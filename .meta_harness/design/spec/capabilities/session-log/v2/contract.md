## 一、含义与使用范围

### S-1 本契约拥有什么

**一个会话的会话日志里，追加一批条目、按键读、从某个位置往后读——以及追加时的两道判定：判重与尝试栅栏。**

| # | 拥有的事实与判定 | 正文 |
|---|---|---|
| 1 | 一本会话日志里条目的**全序**与每条的**日志位置**；读到的尾就是读那一刻已提交的最后一条 | [S-5](#s-5-一个会话一本会话日志)、[S-7](#s-7-日志位置与尾位置) |
| 2 | 条目壳的最小成员：会话、租户身份、运行与执行尝试、载荷、判重键、读取键 | [S-6](#s-6-条目与它的壳) |
| 3 | **判重**：同一本日志里一个判重键至多一条条目，按日志的耐久内容判 | [S-8](#s-8-判重键) |
| 4 | **尝试栅栏**：一个运行已有序号更大的执行尝试的条目之后，带栅栏的旧尝试写不进 | [S-10](#s-10-尝试栅栏) |
| 5 | 一批条目一次提交、全成或全不成；成功即持久；判定与写入是同一步 | [S-13](#s-13-提交与持久)、[S-14](#s-14-同一会话的追加一条接一条判定与写入是同一步) |
| 6 | 一本日志只属于一个租户身份 | [S-12](#s-12-一本日志一个租户身份) |

### S-2 本契约不拥有什么

**窄口**：下表左列是真的会话日志要有、而**本版不收**的东西——不是「不存在」，是「不在这一版的承诺里」。

| 不拥有 | 归谁 |
|---|---|
| **载荷的形状与含义**：消息、运行时记录、响应体、拓展件结论、成本条目都是载荷 | 各自的 data 契约（`data.messages`、`data.model-response`、`data.loop-extension`、`data.call-accounts`）。本契约**原样存、原样交回，不解释**（[S-11](#s-11-只增不改载荷原样)） |
| **载荷之间的配对与唯一**（一次调用至多一条工具消息、一个 `ResponseId` 至多一条助手消息……） | 写入方在追加时守（`data.messages/v2#S-32`）；本契约只给判重键这个手段（[S-8](#s-8-判重键)） |
| **判重键与读取键怎样从业务标识拼出** | 写入方：工具执行运行时拼 `(会话, CallId, 段)`、`(会话, CallId, 段, seq)`；模型请求运行时拼 `ResponseId`、`(callId, 发出序号)`；派发器拼 `(经过, 件名)`、`MessageId`、锚。**本契约只把键当不透明串**（[S-8](#s-8-判重键)、[S-9](#s-9-读取键)） |
| **一次经过的锚怎样算** | **不在本契约**：锚由调用方随 `dispatch` 传入的不透明键给出（`capability.loop-extension-runner/v2#S-5`，D-063 R-12），怎样从日志与输入算出它归 loop 那一程（那份契约的 G-1）。派发器把它拼进判重键与读取键，本契约照样只当不透明串 |
| **尝试开始、运行终结、取消请求这些条目的形状与写入时机** | loop 那一程（PF-012 §6.16）。本契约只要求**每条属于某次执行尝试的条目在壳上带那次尝试**，栅栏据此判（[S-10](#s-10-尝试栅栏)） |
| **条目壳上 PF-000 §5.5 的其余字段**：寿命宿主、出处、因果先后、外部效果的确定性 | **本版不收**：loop 与会话那一程（`data.messages` 的 G-2 同一件事）；外部效果的确定性照旧在各自载荷里（如 `data.call-accounts` 的账） |
| **封存**：会话归档之后日志还收不收追加 | **本版不收**：会话那一程（PF-015）。本版没有封存这回事（[S-24](#s-24-会话归档之后)） |
| **会话日志投影**的协议（PF-015 §5.8「怎么从日志算出一个投影就得是一套协议」） | **本版不收**：会话那一程；模态投影由 `capability.modality-projection` 与它的读方自己追到尾（`capability.model-request-runtime/v2#S-13`） |
| **追加通知、订阅、推送** | **本版不收**：交付面与会话那一程；本版没有消费者要它（[S-20](#s-20-本版不发事件)） |
| **压缩、卸载、取回全文** | 它们本来就是追加（PF-012 §4），由各自的能力追加；本契约不多一种操作 |
| **会话存不存在、谁有权读写一个会话** | 会话那一程与装配（[S-21](#s-21-装配给的保证-vs-协议须给的保证)） |

### S-3 本契约明确不承诺什么

- **不加入任何别的 owner 的事务**：一次追加就是它自己的一次提交。要「消息与自己那一侧的记录同成同败」的写入方，用自己的出站项加判重键收口（工具执行运行时已这样选，D-060 §八 M44）——**本契约与它共同触碰的存储对象就是判重键**（[S-8](#s-8-判重键)）。
- **不解释载荷**，不校验载荷的形状（[S-11](#s-11-只增不改载荷原样)）。
- **不铸任何业务标识**：`MessageId`、`ResponseId`、`RunId`、键都由写入方给。
- **不承诺条目的写入时刻**：条目壳本版不带时刻（[G-4](#十已知缺口)）；次序只看日志位置（`data.messages/v2#S-4`：`createdAt` 不是次序）。
- **不承诺断电不丢**：成功之后进程崩溃、重启都不丢（[S-13](#s-13-提交与持久)）；操作系统崩溃与断电的边界见 [G-3](#十已知缺口)。
- **不附 Schema**。操作的输入与返回用散文写含义；线上形状归把这些操作送过进程边界的那份 composition（[规格容器的规矩](../../../README.md#准入门槛与停止条件)）。

## 二、概念、身份与必要状态

**身份值一律引用 `data.identity-values` v1，会话的指认是 `SessionRef`（`data.messages/v2#S-24`），运行与尝试是 `data.call-accounts/v2#S-37` 的 `RunId` 与 `AttemptId`，不复制定义。**

### S-5 一个会话一本会话日志

**每个会话恰有一本会话日志**（[PF-012 §4 会话日志](../../../../product/PF-012-agent-loop-and-run/design.md#会话日志)「归会话，不归 Run」）。本契约的每个操作都作用在**一本**日志上，由调用带来的会话指认。

1. **只增不改**：条目一经提交，内容、位置、壳都不再变；没有删除、没有改写（[S-11](#s-11-只增不改载荷原样)）。
2. **全序**：一本日志里的条目按提交的先后排成一列，这就是[「本条之前」](../../../../product/PF-012-agent-loop-and-run/design.md#52-会话日志是唯一的真相来源)唯一的答案。
3. **一本日志的条目不出现在另一本日志的读里**：没有任何操作能跨会话读或写。
4. **会话存在与否不在这里判**：第一次向一个会话追加，就是这本日志的第一条；会话是否真的存在、调用方是否有权写，归会话那一程与装配（[S-21](#s-21-装配给的保证-vs-协议须给的保证)）。读一个从未追加过的会话，得到的是一本空日志（尾位置 `0`，[S-7](#s-7-日志位置与尾位置)），**不是失败**——那是一个读得到的事实，不是缺席的默认。

### S-6 条目与它的壳

**一条条目 = 壳 ＋ 载荷。**壳是本契约认得的部分，载荷是写入方交来、本契约原样存的部分（[`data.messages/v2#S-33`](../../../data/messages/v2/contract.md#s-33-消息不携带租户身份)：归属在承载它的条目上，不在消息里）。

| 成员 | 含义 | 何时有 |
|---|---|---|
| `session` | 这本日志的会话（`SessionRef`） | 恒有；等于操作指认的那个会话 |
| `tenant` | 这个会话持有的租户身份（`TenantId`）——[PF-015 §6.12](../../../../product/PF-015-session-lifecycle-and-ownership/design.md#612-会话持有创建那一刻的租户身份) 创建那一刻捕获的那一个；[PF-000 §5.5](../../../../product/PF-000-occurrences-and-record-entries/design.md#55-挂在每条条目上的字段) 的无条件必填 | **恒有** |
| `run`、`attempt` | 这条条目属于哪次运行的哪次[执行尝试](../../../../ubiquitous_language/terms/agent-runtime-loop.md#ul-run-attempt--执行尝试--run-attempt) | **两者同在或同缺**：属于某次尝试的条目两者都带；会话级的条目（例如模型切换落下的那条、入站那一侧落的消息）两者都不带 |
| `payload` | 载荷：一个 JSON 值，形状归它自己的 data 契约 | 恒有 |
| `dedupeKey` | 判重键（[S-8](#s-8-判重键)） | 可缺：缺席即这条不参与判重 |
| `readKeys` | 读取键的集合（[S-9](#s-9-读取键)），可为空集 | 恒有（空集也是写出来的值） |
| `position` | 日志位置（[S-7](#s-7-日志位置与尾位置)） | 提交时由本能力给出；写入方不交 |

- **壳上的运行与尝试由写入方如实给**：本契约不从载荷推（不读尝试开始记录里的序号来补），也不核对它们与载荷是否一致——**写错了尝试，栅栏就按写错的那个判**（[S-10](#s-10-尝试栅栏)）；如实给是写入方的义务。
- **壳上的其余字段本版不收**（[S-2](#s-2-本契约不拥有什么)）。

### S-7 日志位置与尾位置

**日志位置是一条条目在它那本日志里的序号：从 `1` 起的整数，第 n 条提交的条目位置是 n。**

1. **同一本日志里可比、单调、稠密**：后提交的位置更大；一批条目按交来的次序取连续的位置；**位置不回收、不复用、不跳号**。
2. **尾位置**是读那一刻已提交的最后一条的位置；**`0` 表示此刻一条都没有**——这是一个写出来的值，不是缺席。
3. **只在同一本日志里可比**：两本日志的位置没有关系；不同会话的位置相等不说明任何事。
4. **位置不承载别的意思**：不从位置推时刻、推运行、推尝试。

### S-8 判重键

**判重键是写入方给一条条目的一个不透明串：一本日志里，一个判重键至多一条条目，永远如此。**

1. **表示与相等**：按 [`data.identity-values/v1#S-31`](../../../data/identity-values/v1/contract.md#s-31-不透明标识的交换表示)——非空、逐码点精确相等、**本契约不解析它**。键怎样从业务标识拼出归写入方（[S-2](#s-2-本契约不拥有什么)）；**不同写入方的键撞在一起，就是撞在一起**，本契约不替它们分名字空间（[G-5](#十已知缺口)）。
2. **按日志的耐久内容判**：「这个键已经有一条」看的是**已提交的条目本身**（或与它同成同败的持久索引），**不是任何只活在进程里的集合**——提供者自己重启之后仍认得（[S-13](#s-13-提交与持久)）。
3. **撞上即整批不写**：一批里任何一条的判重键已在日志里，这一批**一条都不写**，以 `alreadyRecorded` 收场并交回撞上的那些键（[S-17](#s-17-append追加一批条目) ⑥）。**「已在」与「不可用」分得开**：前者是判出来的结论，后者是判不出来。
4. **判重与写入是同一步**（[S-14](#s-14-同一会话的追加一条接一条判定与写入是同一步)）：两路并发追加同一个键，恰一路成、另一路得 `alreadyRecorded`，**不会两路各判一次「不在」再各写一条**。
5. **它是跨 owner 的共同存储对象**：工具执行运行时的出站项与日志之间、模型请求运行时的结算与 agent loop 的「回复 ＋ 响应体」之间、两副协程对同一次经过的写之间，次序都落在这里——**本条不成立，这些写入方的「恰一条」一条都不成立**。

### S-9 读取键

**读取键是写入方给一条条目的零个或多个不透明串，用来按键把一组条目读回来**（[S-18](#s-18-readbykey按读取键读)）：例如「这次模型调用的全部记录」「这一次经过已落的全部结论」「模型切换落下的那几条」。

1. **表示与相等**同 [S-8](#s-8-判重键) 第 1 条。
2. **不唯一**：任意多条条目可以带同一个读取键；一条条目的读取键两两不同。
3. **判重键不是读取键**：按键读只看读取键；要按判重键找回一条，写入方把同一个串也放进读取键。

### S-10 尝试栅栏

**一次追加可以带一个栅栏 `fenced{run, attempt}`。带栅栏的追加只在提交那一刻这本日志里没有任何一条「同一个运行、尝试序号更大」的条目时才写得进；否则一条都不写，收 `attemptSuperseded`。**

这就是 PF-012 [「只有序号最大的那次尝试的写入被接受」](../../../../product/PF-012-agent-loop-and-run/design.md#同一个-run-同一时刻只有一副协程在推它)在日志写入边界上的兑现：

1. **比较对象在日志里，不在任何进程里**：「序号最大的尝试」读的是已提交条目壳上的 `(run, attempt)`（[S-6](#s-6-条目与它的壳)）——**不另存一份尝试行**，[「用它不引入日志之外的第二份状态」](../../../../product/PF-012-agent-loop-and-run/design.md#同一个-run-同一时刻只有一副协程在推它)。
2. **与 PF-012 同义的前提**：每一次尝试在日志里的第一条条目就是它的尝试开始记录（[`data.messages/v2#S-20`](../../../data/messages/v2/contract.md#s-20-尝试开始)：序号显式写出；[PF-012 §6.16](../../../../product/PF-012-agent-loop-and-run/design.md#616-日志里至少要有这几种-run-相关的条目)「尝试开始」一行）。这一条是 **loop 的义务**：它先落尝试开始，才以新的尝试写别的。这个前提成立，「日志里出现过的最大序号」就是「最近开始的那次尝试」。
3. **栅栏由写入方选带不带**：写入方在一次尝试里推 loop 的那些写（拓展件结论、模型调用的两个锚点与中断意图、调用终结）带栅栏；**结算类的写**（响应体、账）不带，照写、由写入方在载荷上标 `late`（`capability.model-request-runtime/v2#S-17`、`data.call-accounts/v2#S-39`）。**哪些写必须带，归写入方的契约**（`capability.loop-extension-runner/v2#S-21` ②、`capability.model-request-runtime/v2#S-17`），本契约只判带了的。
4. **带栅栏的一批里每条条目的壳必须就是那个 `(run, attempt)`**；对不上是 `invalidInput`。
5. **栅栏不判「这次尝试开始了没有」**：带着一个还没开始的尝试序号（比日志里最大的还大）写进来，本契约照写——那次写入本身就让这个序号成了最大的。**不先落尝试开始就以新序号写别的，是 loop 违约**（第 2 条）。
6. **栅栏只关不开**：一个运行一旦有了序号更大的条目，更小序号的带栅栏写入**此后永远**写不进（位置只增、条目不删）。

## 三、贯穿全部操作的规矩

### S-11 只增不改，载荷原样

1. **只增不改没有例外**（[PF-012 §4](../../../../product/PF-012-agent-loop-and-run/design.md#只增不改怎么和压缩卸载共存)；[PF-015 §5.8](../../../../product/PF-015-session-lifecycle-and-ownership/design.md#58-存储要守住的两件事)「存储真的兑现它」）：本契约没有改、没有删的操作；压缩与卸载在日志里都是追加。
2. **载荷原样存、原样交回**：读回的载荷与交来的是同一个 JSON 值——按 RFC 8259 严格读，**任何一层有重复成员名即不收**，**数无损**（超出 ±2^53 的整数与金额保留原文，不折成二进制浮点）：与 [`data.messages/v2#S-37`](../../../data/messages/v2/contract.md#s-37-规范表示)、[`data.content-blocks/v2#S-24`](../../../data/content-blocks/v2/contract.md#s-24-规范表示) 同一口径（M36）。交来的载荷不是合法 JSON 值即 `invalidInput`。
3. **不解释、不校验载荷的形状**：一条不合 `data.messages` 形状的消息交到这里，本契约照样存——**载荷的表示层校验归写入方在落盘之前做、读方在接收边界再做**（`data.messages` 第五节「表示层校验在每个接收边界重做」）。本契约**不能**替它们兜住一条非法消息（[G-6](#十已知缺口)）。

### S-12 一本日志一个租户身份

**一本会话日志里的全部条目带同一个租户身份**：会话持有的那一个（[PF-015 §6.12](../../../../product/PF-015-session-lifecycle-and-ownership/design.md#612-会话持有创建那一刻的租户身份)，此后不变）。

1. **第一条定下它**：这本日志的第一次追加，它的条目壳上的租户身份就是这本日志的租户身份。
2. **此后的追加带别的租户身份即拒**：`tenantMismatch`，一条都不写（[S-17](#s-17-append追加一批条目) ⑥）；同一批里两条带不同的租户身份是 `invalidInput`。
3. **第一条填得对不对，本契约判不了**：它不读会话持有的租户——写入方从 [`capability.session-tenancy/v2#S-8`](../../session-tenancy/v2/contract.md#s-8-holdingtenant读会话持有的租户身份) 取、如实填，是装配给的保证（[S-21](#s-21-装配给的保证-vs-协议须给的保证)）。**本条保证的是「不混」**：一本日志不会一半条目归这个租户、一半归那个（[SYS-TENANT](../../../../foundation/cross-system-constraints/requirements.md#sys-tenant)）。

### S-13 提交与持久

1. **一次追加是一次提交**：一批条目**全成或全不成**；成的那一刻起它们一起可见，**没有「前一条读得到、后一条还读不到」的一刻**。
2. **成功返回即已持久**：返回之后，提供者重启、所在进程崩溃再起来，这批条目**一条不少、位置不变**（[PF-015 §6.11](../../../../product/PF-015-session-lifecycle-and-ownership/design.md#611-会话睡醒之后还是原来那个)「会话日志一条不少」）；「写下」指确认落盘，不是交给了一个缓冲区。
3. **停机留下的半截不可见**：提交没有完成就停机，重启之后那一批一条都读不到——不会出现半批。
4. **读自己写的**：追加成功返回之后开始的任何一次读，都读得到这批条目——写入方据此把「已落进日志」当作「此后谁读都看得见」，这是 [PF-012 §6.1 日志先于可见](../../../../product/PF-012-agent-loop-and-run/design.md#61-日志先于可见)在日志这一侧的前提。
5. **断电的边界**：操作系统崩溃或机器断电时，成功返回的最后一段是否仍在，本版没有承诺（[G-3](#十已知缺口)）。

### S-14 同一会话的追加一条接一条；判定与写入是同一步

1. **同一本日志上的追加串行**：每一次追加有一个提交点，同一本日志的提交点排成一列（[S-5](#s-5-一个会话一本会话日志) 第 2 条的全序就是它）。
2. **判重、栅栏、租户三道判定都在提交点上、对提交点之前已提交的全部条目判**：判定与写入之间**没有别的追加插进来**。两路并发追加，后提交的那一路看得见先提交的那一路。
3. **不同会话的日志互不排队**。
4. **不靠进程内锁、不靠时间谓词**：两副协程可能在两个进程实例里，旧实例的锁新实例看不见；「旧的超时就算死了」挡不住一个恰好醒来的旧协程——**次序只落在这本日志的提交点上**（[S-8](#s-8-判重键) 第 5 条、[S-10](#s-10-尝试栅栏)）。

### S-15 缺席时的默认答案

**一律拒绝或明确失败，不放行、不回退、不填初值。**三类分开：

| 情形 | 结果 | 为什么不合并 |
|---|---|---|
| 判定得出「不写」 | 具名值：`tenantMismatch`、`attemptSuperseded`、`alreadyRecorded{keys}` | 成立的结论，原样重试不会变 |
| 判定**做不出来**：这本日志此刻读不到、写不进 | **`unavailable`**；追加时它的意思是**「没有确认提交」**（[S-22](#s-22-回执丢失与结果未知)） | 没有结论；按当时状态重试可能不同（`data.identity-values/v1#S-19`） |
| 输入**根本不构成这个请求** | **`invalidInput`**，在任何判定之前 | 表示层校验不是判定（`data.identity-values/v1#S-33`） |

- **身份参数没有默认值**：会话、条目壳上的租户身份，带了运行就必带的尝试，缺席即 `invalidInput`；**不从进程上下文、当前租户身份或「上一条的那个」补**（`data.identity-values/v1#S-17`、`#S-18`）。
- **本契约没有带默认值的参数**：`append` 的 `fence` 与 `readSince` 的 `after` 都是**必填**——不带栅栏要写出 `unfenced`，从头读要写出 `after: 0`。缺哪个都是 `invalidInput`，不补成「不带栅栏」或「从头读」：补前者会让一副该被关掉的旧协程写进去，补后者会让一次追尾的读悄悄变成全量读。
- **「读不到」不等于「没有」**：读操作在日志读不到时收 `unavailable`，**不返回空序列**；空序列只在日志读得到、确实没有匹配的条目时出现。

## 四、操作

### S-16 九件事与失败值总表

每个操作写全九件事：①输入 · ②前置与授权 · ③结构性禁止（不适用写「无」）· ④提交点与原子性 · ⑤成功返回 · ⑥失败集合（**闭合枚举，没有「其他」；按判定次序排列**，同一输入同一答案）· ⑦幂等与重复 · ⑧缺席时的默认答案 · ⑨事件。

**失败值总表**（本契约的全部失败值，含义以这里为准）：

| 值 | 含义 | 类 |
|---|---|---|
| `invalidInput` | 输入不构成这个请求（[S-15](#s-15-缺席时的默认答案) 第三行）；各操作 ⑥ 列出具体情形 | 表示层 |
| `tenantMismatch` | 这一批的租户身份与这本日志已定下的租户身份不同（[S-12](#s-12-一本日志一个租户身份)） | 结论 |
| `attemptSuperseded` | 带栅栏的追加被尝试栅栏拒收：这个运行已有序号更大的尝试的条目（[S-10](#s-10-尝试栅栏)）。**与 `capability.loop-extension-runner` v2 的同名值同义** | 结论 |
| `alreadyRecorded{keys}` | 这一批里有条目的判重键已在日志里（[S-8](#s-8-判重键)）；`keys` 列出撞上的那些判重键。**这一批一条都没写** | 结论 |
| `unavailable` | 判定或写入做不出来（[S-15](#s-15-缺席时的默认答案) 第二行）。**与已接受的 `capability.organization-governance` v1 同名同义** | 失败 |

> **账本外的名字**：`tenantMismatch`、`alreadyRecorded` 是本契约起草时给的**候选名**（施工简报的账本没有它们），**主线已接受**（D-060 §八 N-37 ①）；`alreadyRecorded` 与同批 `capability.assembly-manifest` v2 的同名值说的是同一件事（「这个键已经有一条已提交的记录，这一次什么都没写」），所以同名。

**谁调用**（本契约的面是据点进程内的能力间面，**不直接暴露给人或 agent**；调用方身份怎么核实见 [S-21](#s-21-装配给的保证-vs-协议须给的保证)）：

| 操作 | 调用方 |
|---|---|
| `append` | 工具执行运行时（排空出站项）、模型请求运行时（锚点、结算、模型切换）、agent loop（带栅栏的尝试内写入、回复与它的响应体）、拓展点派发（结论与提醒）、入站受理方 |
| `readByKey`、`readSince` | 模型请求运行时（选中模型、投影追尾、对账、读发出记录）、拓展点派发（按锚读结论、日志只读句柄）、agent loop 与交付面 |

### S-17 append：追加一批条目

`append(session, entries, fence) → { positions, tail }`

| # | 内容 |
|---|---|
| ① | `session`（`SessionRef`）；`entries`：**一条以上**的条目，每条带 `tenant`、可选的 `run` 与 `attempt`（两者同在或同缺）、`payload`、可选的 `dedupeKey`、`readKeys`（可为空集）——不带 `position`；`fence`：**必填判别式**，`unfenced` 或 `fenced{run, attempt}`（[S-10](#s-10-尝试栅栏)） |
| ② | 调用方是这个会话的写入方之一（[S-16](#s-16-九件事与失败值总表) 表），身份由装配核实（[S-21](#s-21-装配给的保证-vs-协议须给的保证)）；条目壳上的租户身份取自会话持有的那一个（[S-12](#s-12-一本日志一个租户身份) 第 3 条）；带栅栏时，这一批属于那次尝试 |
| ③ | 无 |
| ④ | **一次提交**：在这本日志的下一个提交点上，依次判 ⑥ 的三道结论；全过，整批按交来的次序取连续的位置写下，**整批一起可见、一起持久**（[S-13](#s-13-提交与持久)）；任何一道不过，**一条都不写** |
| ⑤ | `positions`：这批条目各自的日志位置，与 `entries` 同序；`tail`：提交之后的尾位置（等于最后一条的位置） |
| ⑥ | `invalidInput` → `tenantMismatch` → `attemptSuperseded` → `alreadyRecorded{keys}`；日志读不到或写不进 ⇒ `unavailable`。`invalidInput` 含：`session` 缺席或不合 `SessionRef`；`entries` 为空；某条缺 `tenant` 或 `payload`、`run` 与 `attempt` 只带其一、`attempt` 不是 ≥ 1 的整数、`payload` 不是合法 JSON 值（[S-11](#s-11-只增不改载荷原样) 第 2 条）、键不合 `data.identity-values/v1#S-31`、一条的读取键有重复；同一批里两条的判重键相同、两条的租户身份不同；带了 `position`；`fence` 缺席或不合形状；`fenced` 时某条的 `(run, attempt)` 与栅栏不同 |
| ⑦ | **判重键是幂等的唯一手段**：同一批以同样的判重键重交，第一次成了的，第二次得 `alreadyRecorded{keys}`、不多写一条——写入方据此认回（「已在」即已送达）。**不带判重键的条目不幂等**：重交就是又一条。回执丢了的重交见 [S-22](#s-22-回执丢失与结果未知) |
| ⑧ | 日志读不到或写不进 ⇒ `unavailable`：**没有确认提交**——可能没写下，也可能已写下（[S-22](#s-22-回执丢失与结果未知)）。**不把「判重判不出」当成「不在」写进去，也不当成「已在」回答** |
| ⑨ | 不发（[S-20](#s-20-本版不发事件)） |

- **多条目原子追加的两种用法**，都靠 ④ 与 ⑥：工具执行运行时把同一段的 `ToolInternalMessage`、结果消息与记录条目一次交来（整体成败）；agent loop 把「回复消息 ＋ 它的响应体」一次交来，响应体带以 `ResponseId` 拼出的判重键——**模型请求运行时已经写下那条响应体时，这一批撞键、整批不写，回复不成为消息**（`capability.model-request-runtime/v2#S-17`、`#S-38` 第一、二行）。

### S-18 readByKey：按读取键读

`readByKey(session, key) → { entries, tail }`

| # | 内容 |
|---|---|
| ① | `session`；`key`：一个读取键（[S-9](#s-9-读取键)） |
| ② | 调用方有权读这个会话（装配给，[S-21](#s-21-装配给的保证-vs-协议须给的保证)） |
| ③ | 无 |
| ④ | 只读，无提交。读的是**读那一刻**已提交的这本日志 |
| ⑤ | `entries`：这本日志里读取键含 `key` 的**全部**条目，带壳与位置，**按位置升序**（即提交次序）；`tail`：读那一刻的尾位置。没有匹配的条目时 `entries` 是空序列——**「没有」是一个读得到的结论** |
| ⑥ | `invalidInput`（`session` 或 `key` 缺席、不合形状）；日志读不到 ⇒ `unavailable` |
| ⑦ | 只读，天然可重复；两次读之间有追加，后一次的结果是前一次的**扩展**（前一次读到的条目原样在、位置不变，后面可能多出几条） |
| ⑧ | 读不到 ⇒ `unavailable`，**不返回空序列** |
| ⑨ | 不发 |

### S-19 readSince：从某个位置往后读

`readSince(session, after) → { entries, tail }`

| # | 内容 |
|---|---|
| ① | `session`；`after`：**必填**，一个 ≥ 0 的整数位置——`0` 即从头读 |
| ② | 同 [S-18](#s-18-readbykey按读取键读) ② |
| ③ | 无 |
| ④ | 只读，无提交 |
| ⑤ | `entries`：位置大于 `after`、不大于读那一刻尾位置的**全部**条目，按位置升序、**不跳号**；`tail`：读那一刻的尾位置。`after` 等于尾位置时 `entries` 为空。**`after` 大于尾位置时 `entries` 为空、`tail` 照实给**：调用方凭 `tail < after` 就知道它手上的水位不属于这本日志——本契约不替它判那是谁的错 |
| ⑥ | `invalidInput`（`session` 缺席或不合形状；`after` 缺席、不是整数或小于 0）；日志读不到 ⇒ `unavailable` |
| ⑦ | 只读，天然可重复；同 [S-18](#s-18-readbykey按读取键读) ⑦ |
| ⑧ | 读不到 ⇒ `unavailable`，**不返回空序列、不返回读到一半的那一段** |
| ⑨ | 不发 |

- **追到日志尾**：读方要「覆盖到日志尾」的答案（`capability.model-request-runtime/v2#S-13`、`capability.modality-projection/v2#S-6`），就以它手上的水位 `readSince`，读到的 `tail` 即它这一次追到的位置。

## 七、装配给的保证 vs 协议须给的保证

### S-21 装配给的保证 vs 协议须给的保证

[SYS-DEPLOY](../../../../foundation/cross-system-constraints/requirements.md#sys-deploy)：第一版单机，语义不变地可扩展。**左列单机时由装配顺带给出，跨进程之后不会自动成立；右列是本契约已经记下的待兑现项（[G-7](#十已知缺口)），不是「以后再说」。**

| 保证 | 本版（单机）由谁给 | 跨进程之后谁重新兑现 | 做不到会怎样 |
|---|---|---|---|
| **判重与栅栏在提交点上判、与写入同一步**（[S-14](#s-14-同一会话的追加一条接一条判定与写入是同一步)） | **装配给**：据点进程里一份会话日志提供者；同一本日志的追加在它那里排成一列 | **协议给**：每本日志一个定序者（或等价的协议），判重与栅栏在定序点上判；至少一次的投递按判重键落一遍 | 两路各判一次「不在」、各写一条：两条工具消息、两条响应体、**两笔钱**；旧协程的结论与新协程的并存 |
| **单写者**：一份日志存储同一时刻只有一个据点进程在写（据点装配 L-f） | **装配给**：属主排他——存储随进程加锁，锁随进程释放（与 SQL 存储的属主排他同一做法） | **协议给**：定序者唯一；换定序者时旧的先被隔离，才接收新的 | 排空重启时新旧两个进程各写一段，判重与栅栏各判各的，**两个进程互不相知** |
| **条目壳上的租户身份就是会话持有的那一个**（[S-12](#s-12-一本日志一个租户身份)） | **装配给**：写入方在同一进程里从 `capability.session-tenancy` 取、如实填；本契约守「不混」 | **协议给**：条目壳与载荷**一起过边界**、在接收边界按调用方租户身份重新验证（`data.identity-values/v1#S-30`），不单独传载荷再在对端补归属 | 一本日志的第一条就挂错租户，此后全错；或跨进程时一条条目被挂到另一个会话、另一个租户名下 |
| **调用方身份已核实**（全部操作） | **装配给**：本契约的面是据点进程内的能力间面；够得着它的只有装配放进来的写入方与读方 | **协议给**：调用携带会话与租户身份，在接收边界重新验证 | 拿到一个会话指认就能读别人的日志、往别人的日志里写；**本契约的面因此不得直接暴露成终端 API** |
| **读到的就是读那一刻已提交的全部**（[S-18](#s-18-readbykey按读取键读)、[S-19](#s-19-readsince从某个位置往后读)） | **装配给**：读与追加在同一个提供者上 | **协议给**：副本上的读写明它读到哪个位置为止（`tail` 如实），不以一份落后的副本冒充尾 | 读方以为追到尾了，漏掉一张刚进来的图；对账漏掉一条「已出门」 |
| **提交即持久**（[S-13](#s-13-提交与持久)） | **装配给**：本机文件，确认落盘才返回 | **协议给**：确认条件写进协议（几个副本落盘才算） | 返回成功之后丢了：送达方以为送到了，日志里没有 |
| **载荷原样**（[S-11](#s-11-只增不改载荷原样)） | 同一进程里一处无损的读写 | 每一跳（副本、传输、回放）都严格读、数无损 | 回放出来的日志与写下的不是同一份 |

## 八、交接、缺席与恢复

### S-22 回执丢失与结果未知

**`append` 收 `unavailable`、或调用方根本没等到回答（提供者在提交途中没了）时，这一批的结果未知：可能一条都没写，也可能整批已写（不会是半批，[S-13](#s-13-提交与持久) 第 3 条）。**

1. **收口的办法是判重键**：以同样的判重键重交同一批——得 `alreadyRecorded` 即上次已写下，得成功即上次没写下；两种都只留一条。**写入方要「恰一条」，就必须给判重键**；不给判重键的条目，重交就可能多一条，那是写入方的选择。
2. **不以读代替**：先读一遍「有没有」再决定写不写，中间可能插进别的追加——**判定与写入只在同一步里做**（[S-14](#s-14-同一会话的追加一条接一条判定与写入是同一步)）。
3. **带栅栏的一批结果未知时**：重交时它若已被新的尝试取代，得 `attemptSuperseded`——**这不说明上次写没写下**；要分清，写入方按读取键读回（它的判重键同时放进读取键，[S-9](#s-9-读取键) 第 3 条）。
4. **写入方各自的读法**：工具执行运行时把「已在」读成已送达、把 `unavailable` 读成留在出站项里重试；模型请求运行时把锚点的 `unavailable` 读成「没确认写下」、这一次不出网——锚点可能已经落下而请求没发，那一种由它的对账当作失联处理（`capability.model-request-runtime/v2#S-33`）。**这些读法在各自契约里，本契约只保证「未知」只有这两种可能**。

### S-23 提供者撤除、换代与重启

- **本契约的一切事实都在日志里**，提供者实例里没有「只有它知道」的东西；判重与栅栏读的都是已提交的条目。**换一个提供者实例、重启，任何一次判定的答案不变。**
- **撤除时在途的追加**：要么在撤除之前提交（此后读得到），要么没有提交（此后读不到、不留半批）；调用方可能等不到回答——按 [S-22](#s-22-回执丢失与结果未知) 收口。**本契约不交接任何活状态。**
- **依赖它的一方随它换代时怎样**（例如必需它的插件被卸载重跑）归那一方的契约与提供者设计，不在这里。

### S-24 会话归档之后

**本版没有封存**：会话归档之后，日志照样接收追加、照样可读。[PF-015 §6.3](../../../../product/PF-015-session-lifecycle-and-ownership/design.md#63-归档先停活儿再落状态)「归档先停活儿再落状态」——归档那一次提交里交付的出站项，归档之后照样落得下（工具执行运行时节点 L-4 的第一种）。
归档之后「不再有新的送达」由送达方自己守（`capability.tool-execution-runtime/v2#S-29`）。**要不要封存、封存之前等谁排空**，归会话那一程（[G-1](#十已知缺口)）；那时出新版本。

## 九、规范表达与验证义务

### S-25 本版选用哪些形式工件

| 性质 | 表达 | 状态 |
|---|---|---|
| **判重键至多一条**（[S-8](#s-8-判重键)）、**带栅栏的条目之前没有更大序号**（[S-10](#s-10-尝试栅栏)），在两路并发、提供者停机重启下仍成立；前提是判定与写入同一步、判重读耐久内容（[S-14](#s-14-同一会话的追加一条接一条判定与写入是同一步)、[S-8](#s-8-判重键) 第 2 条） | **行为模型 [`formal/SessionLog.tla`](formal/SessionLog.tla)**：把一次追加拆成「判定」与「写下」两步、写入方与停机非确定地交错；两个开关 `Serialized`（判定与写下同一步）、`DurableDedupe`（判重读已提交的条目而不是进程内集合）。正配置两个都开（登记为 formal task `session-log-v2-appends`）；三个否定配置各关一个、两个可达性配置各断言一道判定「从不拒收」，五个都**预期出反例**，只作有效性核对、不登记为 formal task | 执行状态不写在本版本目录，见[验证入口](../verification.md#形式工件) |
| 全批成败、位置稠密、读自己写的、载荷原样 | **不建模**：模型里一次「写下」就是整批一次写进，这几条**被建模方式吸收**，没有一条会在条款被违反时失败的断言 | 证据是规范场景与故障注入（[S-26](#s-26-判重停机重排不多一条)～[S-31](#s-31-读不到不是没有)） |
| 租户不混（[S-12](#s-12-一本日志一个租户身份)） | 不建模：单一的比较，没有交错 | 场景 [S-29](#s-29-一本日志一个租户身份) |

执行状态在[验证入口](../verification.md)，**不写进本版本目录**。

### 规范场景

**每一条都要真跑**：它们断言的是行为，只读本文证明不了。操作层面的实例在 [`examples.md`](examples.md)。

#### S-26 判重：停机重排不多一条

工具执行运行时交一批（`ToolInternalMessage`、结果消息、一条记录条目，判重键各不相同），提供者写下之后、回执送达之前杀掉进程；重启后同一批重交。
**必须观察到**：第二次得 `alreadyRecorded`，`keys` 是那三个；日志里每个键恰一条、位置是第一次给的。
**另跑两支**：① 把判重换成只记在进程内的集合（故障注入）——重启之后第二次写进、同键两条：**这一支必须失败**，它是「按耐久内容判」唯一的反例；② 两路同时交同一批——恰一路成、另一路 `alreadyRecorded`。

#### S-27 栅栏：旧协程写不进

同一个运行，尝试 1 的协程停在两次写之间；loop 以尝试 2 落下尝试开始（`fenced{R, 2}`）。之后尝试 1 以 `fenced{R, 1}` 交一条结论。
**必须观察到**：`attemptSuperseded`，日志里没有这条；尝试 2 的写照常。**另跑一支**：尝试 1 以 `unfenced` 交一条带 `late` 的响应体——**写得进**（结算不受栅栏拒收）。**再跑一支**：两副协程各带自己的序号同时交——无论谁先提交，日志里都没有「尝试 2 的条目之后的一条带栅栏的尝试 1 条目」。

#### S-28 回复与响应体：撞键整批不写

模型请求运行时以 `ResponseId` 拼出的判重键写下一条响应体（撤除时的结算）；agent loop 随后交「回复消息 ＋ 同一个判重键的响应体」一批。
**必须观察到**：`alreadyRecorded`，**回复消息也没写**——日志里没有「有回复消息、响应体说没有回复」那种组合。

#### S-29 一本日志一个租户身份

会话 `s1` 的第一次追加带租户身份 `T1`；之后一批带 `T2`；另一批里两条分别带 `T1`、`T2`。
**必须观察到**：前者 `tenantMismatch`、后者 `invalidInput`，日志里都没有它们。

#### S-30 位置与读

连续交三批（一条、两条、一条）。**必须观察到**：位置 1、2—3、4；`readSince(s1, 0)` 读到四条、`tail = 4`；`readSince(s1, 2)` 读到位置 3、4；`readSince(s1, 9)` 得空序列、`tail = 4`；某个读取键只在第 2、4 条上，`readByKey` 读到这两条、按位置升序。**另跑一支**：在一批提交途中杀掉进程——重启之后那一批一条都读不到、`tail` 是上一批的。

#### S-31 读不到不是没有

让日志存储读不到（故障注入），调三个操作。**必须观察到**：一律 `unavailable`；**没有一次交回空序列或 `tail = 0`**；`append` 之后恢复存储，按判重键重交能分清上次写没写下。

## 十一、提供者映射

**本版的最小提供者**（候选；它的节点由主线另立，本契约不设计它）：**文件系统 JSONL 追加器**（D-026），据点根作用域一份，服务键候选 `sessionLog`。它要兑现本契约的全部条款；**本契约对它的每一条要求都写成性质**——判重读耐久内容（[S-8](#s-8-判重键) 第 2 条）、判定与写入同一步（[S-14](#s-14-同一会话的追加一条接一条判定与写入是同一步)）、确认落盘才返回、停机留下的半截不可见（[S-13](#s-13-提交与持久)）、单写者（[S-21](#s-21-装配给的保证-vs-协议须给的保证) 第二行）。**文件怎样分、索引放在哪、怎样丢弃半截的尾行**归那个节点。
它**取代**验收装配里的会话日志替身（据点装配 [验收装配](../../../../realization/apps/cli/design.md#验收装配)那张表的「会话日志」一行）；**真提供者**仍归 loop 与会话那一程（[G-1](#十已知缺口)）。
