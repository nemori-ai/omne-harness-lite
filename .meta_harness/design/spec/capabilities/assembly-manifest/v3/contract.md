## 一、含义与使用范围

### S-1 本契约拥有什么

### S-3 本契约明确不承诺什么

- **追加不解释记录内容**：不核对构成与求值是否一致、不判 `unresolved`、不判撞名——那些是写入方在追加之前判的。新增读面只校验 S-32 投影，不改变旧读写操作的答案。
- **不替写入方重试**：条件追加撞了就是撞了（`headMismatch`），重读、重算、再交由写入方做。
- **不加入任何别的 owner 的事务**：一次追加就是它自己的一次提交。
- **不承诺断电不丢**：见 [G-3](#十已知缺口)。
- **不附 Schema**。操作的输入与返回用散文写含义；线上形状归把这些操作送过进程边界的那份 composition（[规格容器的规矩](../../../README.md#准入门槛与停止条件)）。

## 二、概念、身份与必要状态

**身份值一律引用 `data.identity-values` v1，会话的指认是 `SessionRef`（`data.messages/v2#S-24`），不复制定义。**

### S-5 一个会话一列换表记录

**本契约里，一个会话的[装配清单](../../../../ubiquitous_language/terms/agent-runtime-loop.md#ul-assembly-manifest--装配清单--assembly-manifest)是一列只增的换表记录**：每一次装配（含完整重新装配）、每一次 reload、每一次 ③ 型失败之后的自动刷新、每一次权限收回之后的收窄，各落一条（`capability.asset-registry/v2#S-18` 第 1 条）。

1. **只可追加，不可改写**（[PF-004 §4 装配清单](../../../../product/PF-004-agent-definition-and-assembly/design.md#装配清单)）：没有改、没有删的操作。
2. **一列只属于一个会话**：任何操作都不跨会话读写；一个会话的记录不出现在另一个会话的读里。
3. **会话存在与否不在这里判**：第一次向一个会话追加，就是这一列的第一条。读一个从没追加过的会话，得到的是一列空的记录（头 `0`，[S-7](#s-7-序号与头)）——**那是一个读得到的事实，不是失败**；写入方据此答它自己的「没有装配记录」（`capability.asset-registry` 的 `sessionNotFound`）。
4. **「一份清单」怎样从这一列里切出来**（PF-004 的「失效 → 重新求值得到一份新清单」）本版不收（[G-1](#十已知缺口)）。

### S-6 记录与它的壳

**一条换表记录 = 本契约认得的壳 ＋ 写入方交来、本契约原样存的内容。**

| 成员 | 含义 | 谁给 |
|---|---|---|
| `session` | 这一列的会话（`SessionRef`） | 操作指认 |
| `seq` | 序号（[S-7](#s-7-序号与头)） | **本能力在提交时给**；写入方不交 |
| `evaluation` | 这条记录所依的那次求值怎样指认，**必填判别式**，恰三种：`given{ref}`——写入方带来的求值引用，这条记录就是它指认的那一条（装配那一次，[S-8](#s-8-求值引用-evaluationref) 第 2 条）；`mint`——这条记录记下一次新的求值，引用由本能力在提交时铸（reload 那一次）；`reuse{ref}`——不记新的求值，沿用这个会话里已有的一条记录的引用（③ 型失败之后与权限收回之后，只删不增） | 写入方选种类；`mint` 的引用由本能力给 |
| `evaluationRef` | 这条记录所依的求值引用：`given` 与 `reuse` 的那个，或 `mint` 铸出的那个 | 提交时确定 |
| `tables` | **非空**：类别（`data.asset-model/v3#S-1`）→ `{ filledAt, composition }`。`filledAt` 是这张表这一次成立的时刻（`Instant`，[S-9](#s-9-表时刻同一类别上严格递增)）；`composition` 是这张表的完整构成，一个 JSON 值 | 写入方 |
| `content` | 其余内容，一个 JSON 值（`filledBy`、这次求值……，形状归写入方） | 写入方 |

- **一条记录带齐它换掉的每一张表的完整构成**，所以任何一类的当前构成都能从这一类最后一条记录单独读出（[S-16](#s-16-readhead读头与每一类最后一条)）。这是写入方的义务（`capability.asset-registry/v2#S-18` 第 1 条），本契约不核对 `composition` 里有什么。
- **`tables` 里的类别**在一条记录里两两不同。

### S-7 序号与头

1. **序号**是一条记录在它那一列里的位次：从 `1` 起，第 n 条提交的记录序号是 n；**稠密、单调、不回收、不复用**；(会话, 序号) 唯一。
2. **头**是读那一刻已提交的最后一条的序号；**`0` 表示这一列此刻是空的**——一个写出来的值，不是缺席。
3. **序号只在同一个会话里可比**；不从序号推时刻。

### S-8 求值引用 EvaluationRef

**`EvaluationRef` 指认一条记下了一次求值的记录**：`evaluation` 为 `given` 或 `mint` 的那一条。不透明，交换表示与相等按 `data.identity-values/v1#S-31`；**本契约不解析它，消费者也不得解析它**。

1. **全局唯一、永不复用**：一个 `EvaluationRef` 至多指认一条记录，跨一切会话、永远如此。
2. **`given`**：写入方带来的引用（会话资产注册表把装配交来的那个带来，`capability.asset-registry/v2#S-13`、`#S-22` ②）。同一个会话里**再以同一个引用 `given` 追加**，得 `alreadyRecorded{record}` 并交回已有的那一条——回执丢了的重试认回同一次（[S-17](#s-17-append条件追加一条换表记录) ⑦）；这个引用已经指认了**别的**记录（别的会话的，或本能力铸的），得 `evaluationRefConflict`。
3. **`mint`**：本能力在提交时铸一个新的，与已有的任何一个都不相等。
4. **`reuse{ref}`**：`ref` 必须指认**这个会话里**一条 `given` 或 `mint` 记录；否则 `recordNotFound`。`reuse` 记录不指认任何求值——它们没有自己的求值，只沿用。
5. **`EvaluationRef` 的权威在本条**（主线裁定 [D-060 §八 N-37](../../../../record/decisions/mainline-self-rulings-2026-09/decision.md#八实现映射起草反推出的契约修订m31m442026-09-25-追加) ③；原 [G-6](#十已知缺口) 闭合）：`capability.asset-registry` v2 [S-13](../../asset-registry/v2/contract.md#s-13-evaluationref) 以坐标引用本条、不另下定义，catalog 登那一侧 → 本契约的依赖；本契约不以坐标依赖那份契约——它是消费者。

### S-9 表时刻：同一类别上严格递增

**同一个会话、同一个类别上，后提交的记录里这张表的 `filledAt` 严格大于前一条里这张表的**（按时间点比较，`data.offer-expiry/v1#S-22`）。

1. 因此 **(会话, 类别, `filledAt`) 至多指认一条记录**——[S-18](#s-18-readhistory按表时刻读回一条) 就按它读。
2. `filledAt` 由写入方给（会话资产注册表取它的时钟，`capability.asset-registry/v2#S-6`）；本契约**只判它不回退**，不判它离此刻多远。不递增即 `filledAtNotIncreasing`，一条都不写。

### S-10 在场事实

**在场事实是「对这个会话，这个依赖名此刻有 / 没有在场且可用的提供者」的一条答案**（[PF-006 §6.4](../../../../product/PF-006-tools-and-skills/design.md#64-依赖声明与解析)「逐项看有没有在场且可用的提供者」），按 `DependencyName`（`data.tool-definition/v2#S-9`、`#S-18`：逐码点相等）键控，取值 `present` 或 `absent`。

1. **两种答案都要有依据**：`present` 与 `absent` 都是**有人给出了的事实**；**一个名字没有事实，就是判不出**，不是 `absent`（[S-19](#s-19-dependencypresence依赖名此刻在不在场) ⑧）。
2. **事实从哪里来本版不收**（[S-2](#s-2-本契约不拥有什么)、[G-2](#十已知缺口)）：谁在场、是否可用、提供者的自报，归 PF-006 依赖解析与据点装配那一程。本版的最小提供者从装配给它的事实答（[十一](#十一提供者映射)）。
3. **它不是换表记录**：不进序号、不影响头、不随会话的换表而变；「提供者换了或没了 → 重算」（PF-006 §6.4）由事实的给出方负责。

## 三、贯穿全部操作的规矩

### S-11 只增不改；原样存、原样交回

1. **只增不改没有例外**：本契约没有改、没有删的操作（[S-5](#s-5-一个会话一列换表记录) 第 1 条）。
2. **`composition` 与 `content` 原样存、原样交回**：读回的与交来的是同一个 JSON 值——按 RFC 8259 严格读，任何一层有重复成员名即不收，**数无损**（`data.messages/v2#S-37` 同一口径，M36）。不是合法 JSON 值即 `invalidInput`。
3. **不解释、不校验内容的形状**：形状归写入方（[S-2](#s-2-本契约不拥有什么)）。

### S-12 条件追加：判定与写入是同一步

1. **每次追加带一个期望头**：只在提交那一刻这一列的头**恰等于**期望头时写；否则一条都不写，收 `headMismatch{head}` 并交回此刻的头。
2. **同一会话上的追加串行**：每一次追加有一个提交点，同一会话的提交点排成一列；**期望头、求值引用、表时刻三道判定都在提交点上、对提交点之前已提交的全部记录判**，判定与写入之间没有别的追加插进来。
3. **两路以同一个期望头并发追加**，恰一路成、另一路 `headMismatch`——**这就是写入方（同一实例的两次并发、旧实例与新实例）共同触碰的存储对象**（会话资产注册表节点关键选择三、R-M1）。
4. **不靠进程内锁、不靠时间谓词**：次序只落在这一列的提交点上。
5. **不同会话互不排队。**

### S-13 提交与持久

1. **一次追加是一次提交**：一条记录全成或全不成；成的那一刻起它可见，**不会读到一条半截的记录**（[PF-004 §6.1](../../../../product/PF-004-agent-definition-and-assembly/design.md#61-不变式) I-9 的同形：不产生残缺的清单）。
2. **成功返回即已持久**：提供者重启、进程崩溃再起来，这条记录**一条不少、序号不变**（[PF-015 §6.11](../../../../product/PF-015-session-lifecycle-and-ownership/design.md#611-会话睡醒之后还是原来那个)）。
3. **停机留下的半截不可见**：提交没有完成就停机，重启之后读不到它。
4. **读自己写的**：追加成功返回之后开始的任何一次读，都读得到这条记录，头不小于它的序号。
5. **断电的边界**本版没有承诺（[G-3](#十已知缺口)）。

### S-14 缺席时的默认答案

**一律拒绝或明确失败，不放行、不回退、不填初值。**三类分开：

| 情形 | 结果 | 为什么不合并 |
|---|---|---|
| 判定得出「不写」或「没有那一条」 | 具名值：`alreadyRecorded{record}`、`evaluationRefConflict`、`headMismatch{head}`、`filledAtNotIncreasing{categories}`、`recordNotFound` | 成立的结论，原样重试不会变 |
| 判定**做不出来**：这一列此刻读不到、写不进；某个依赖名没有在场事实 | **`unavailable`**；追加时它的意思是**「没有确认提交」**（[S-22](#s-22-回执丢失与结果未知)） | 没有结论（`data.identity-values/v1#S-19`） |
| 输入**根本不构成这个请求** | **`invalidInput`**，在任何判定之前 | 表示层校验不是判定（`data.identity-values/v1#S-33`） |

- **身份参数没有默认值**：会话缺席即 `invalidInput`，不从进程上下文或「上一个会话」补（`data.identity-values/v1#S-17`、`#S-18`）。
- **本契约没有带默认值的参数**：`append` 的 `expectedHead` 与记录的 `evaluation` 都是**必填**——追加第一条要写出 `expectedHead: 0`，不补成「不管头」：补了，两路并发各写一条，条件追加就没了。
- **「读不到」不等于「没有」**：读在这一列读不到时收 `unavailable`，**不返回空列、不返回头 `0`、不返回一份旧的**（R-M8）；空列只在读得到、确实没有记录时出现。
- **「判不出」不等于「不在场」**：没有在场事实的名字收 `unavailable`，**不答 `absent`**（[S-10](#s-10-在场事实) 第 1 条）。

### S-15 九件事与失败值总表

每个操作写全九件事：①输入 · ②前置与授权 · ③结构性禁止（不适用写「无」）· ④提交点与原子性 · ⑤成功返回 · ⑥失败集合（**闭合枚举，没有「其他」；按判定次序排列**，同一输入同一答案）· ⑦幂等与重复 · ⑧缺席时的默认答案 · ⑨事件。

**失败值总表**（本契约的全部失败值，含义以这里为准）：

| 值 | 含义 | 类 |
|---|---|---|
| `invalidInput` | 输入不构成这个请求（[S-14](#s-14-缺席时的默认答案) 第三行）；各操作 ⑥ 列出具体情形 | 表示层 |
| `alreadyRecorded{record}` | `given` 带来的求值引用在这个会话里已经指认了一条 `given` 记录；`record` 是那一条。**这一次什么都没写**。与 `capability.session-log` v2 的同名值说同一件事（这个键已有一条已提交的记录，这一次什么都没写） | 结论 |
| `evaluationRefConflict` | `given` 带来的求值引用已经指认了别的记录：别的会话的，或本能力铸的 | 结论 |
| `recordNotFound` | 指认的那条记录在这个会话里没有：`reuse{ref}` 的 `ref` 不指认这个会话的 `given`／`mint` 记录；或 S-18 的 (类别, `filledAt`) 没有记录；或 S-33 确认头为 0、上界内没有同会话新求值源或选定源记录确定缺失 | 定位 |
| `headMismatch{head}` | 期望头不等于提交那一刻的头；`head` 是那个头 | 结论 |
| `filledAtNotIncreasing{categories}` | 记录里这些类别的 `filledAt` 不大于这个会话这一类上一条的（[S-9](#s-9-表时刻同一类别上严格递增)） | 结论 |
| `unavailable` | 判定或写入做不出来（[S-14](#s-14-缺席时的默认答案) 第二行）。**与已接受的 `capability.organization-governance` v1 同名同义** | 失败 |
| `unavailable{reason: invalid_evaluation_content}` | 只用于 S-33：源记录可读，但 S-32 必需投影缺失或非法。`reason` 是本版新增的闭合诊断值，不等于「没有模型锁」或空求值 | 失败 |

> **账本外的名字**：除 `invalidInput`、`unavailable` 外，上表的值与操作名 `readHead`、`readHistory` 都是本契约起草时给的**候选名**（施工简报的账本只给了四个操作的描述与 `dependencyPresence` 一个名字），**主线已接受**（[D-060 §八 N-37](../../../../record/decisions/mainline-self-rulings-2026-09/decision.md#八实现映射起草反推出的契约修订m31m442026-09-25-追加) ①）；`headMismatch` 就是会话资产注册表节点 R-M1 说的「冲突」，`alreadyRecorded` 就是 R-M2 说的「已在」。

上述历史账本不包括本候选的新名。`readEvaluation` 与 `invalid_evaluation_content` 由本次主线 2026-09-27 施工账本明确给定；其状态仍随 v3 候选，不能引用旧 D-060 声称已经接受。

**谁调用**（本契约的面是据点进程内的能力间面，**不直接暴露给人或 agent**；调用方身份怎么核实见 [S-21](#s-21-装配给的保证-vs-协议须给的保证)）：

|---|---|
| `readHead` | 会话资产注册表：每一次换表之前取头、每一次读取头对齐缓存、重启之后重建 |

### S-16 readHead：读头与每一类最后一条

`readHead(session) → { head, latest }`

| # | 内容 |
|---|---|
| ① | `session`（`SessionRef`） |
| ② | 调用方有权读这个会话的清单（装配给，[S-21](#s-21-装配给的保证-vs-协议须给的保证)） |
| ③ | 无 |
| ④ | 只读，无提交。**`head` 与 `latest` 出自同一刻**：同一个一致的读（R-M4） |
| ⑤ | `head`：那一刻的头（空列为 `0`）；`latest`：类别 → 那一刻这一类的**最后一条**记录（`tables` 含这一类的记录里序号最大的那条），带壳与内容；空列时是空映射 |
| ⑥ | `invalidInput`（`session` 缺席或不合形状）；读不到 ⇒ `unavailable` |
| ⑦ | 只读，天然可重复；两次读之间有追加，后一次的头更大 |
| ⑧ | 读不到 ⇒ `unavailable`，**不交回头 `0`、空映射或上一次读到的** |
| ⑨ | 不发 |

- **「便宜」不是本契约的承诺**：会话资产注册表每次读都要取头（它的节点关键选择二），读得快慢是提供者设计的事；本契约只承诺头与各类最后一条出自同一刻。

### S-17 append：条件追加一条换表记录

`append(session, expectedHead, record) → { seq, evaluationRef, head }`

| # | 内容 |
|---|---|
| ① | `session`；`expectedHead`：**必填**，≥ 0 的整数；`record`：`evaluation`（必填判别式）、`tables`（非空）、`content`（[S-6](#s-6-记录与它的壳)）——不带 `seq` |
| ② | 调用方是这个会话清单的写入方（装配给，[S-21](#s-21-装配给的保证-vs-协议须给的保证)）；记录内容已由写入方判过（[S-3](#s-3-本契约明确不承诺什么)） |
| ③ | 无 |
| ④ | **一次提交**：在这一列的下一个提交点上依次判 ⑥ 的各道结论；全过，这条记录以 `seq = 头 + 1` 写下，`mint` 的引用此刻铸出，**记录一起可见、一起持久**（[S-13](#s-13-提交与持久)）；任何一道不过，**什么都不写** |
| ⑤ | `seq`：这条记录的序号；`evaluationRef`：它所依的求值引用（[S-6](#s-6-记录与它的壳)）；`head`：提交之后的头（等于 `seq`） |
| ⑥ | `invalidInput` → `alreadyRecorded{record}` → `evaluationRefConflict` → `recordNotFound` → `headMismatch{head}` → `filledAtNotIncreasing{categories}`；这一列读不到或写不进 ⇒ `unavailable`。`invalidInput` 含：`session` 缺席或不合形状；`expectedHead` 缺席、不是整数或小于 0；`evaluation` 缺席或不是三种之一；`given`／`reuse` 的引用不合 `data.identity-values/v1#S-31`；`tables` 为空、类别不合 `data.asset-model/v3#S-1`、`filledAt` 不是 `Instant`；`composition` 或 `content` 不是合法 JSON 值；带了 `seq` |
| ⑦ | **`given` 幂等**：同一个会话以同一个引用再交，得 `alreadyRecorded{record}`——**不看期望头**（回执丢了的那次重试，头已经被它自己推过了），写入方据交回的那条认回。**`mint` 与 `reuse` 不幂等**：重交就是又一次追加；回执丢了见 [S-22](#s-22-回执丢失与结果未知) |
| ⑧ | 读不到或写不进 ⇒ `unavailable`：**没有确认提交**——可能没写下，也可能已写下（[S-22](#s-22-回执丢失与结果未知)）；不当作 `headMismatch` 回答 |
| ⑨ | 不发（[S-20](#s-20-本版不发事件)） |

- **判定次序为什么让 `alreadyRecorded` 在 `headMismatch` 之前**：装配那一次的回执丢了、写入方以同一引用重交时，头已经是它自己那一条推上去的；若先判头，它只能得 `headMismatch`，认不回自己那一次（R-M2「已在」「冲突」「不可用」三者可区分）。

### S-19 dependencyPresence：依赖名此刻在不在场

`dependencyPresence(session, names) → { presence }`

### S-32 求值投影的两个内容槽位

本版只为 `readEvaluation` 定义记录 `content` 中的两个可读槽位，不改变 [S-17](#s-17-append条件追加一条换表记录) 对任意合法 JSON 内容原样存取的保证：

| 成员 | 含义与约束 |
|---|---|
| `content.evaluation` | `capability.asset-evaluation/v4#S-8` 的完整 `EffectiveAssembly`，其公共纯值读取统一采用该契约 [`#S-47`](../../asset-evaluation/v4/contract.md#s-47-成功结果的值读取) 的全部条件；不据 S-8 摘要表另行补写同义 DTO 或校验规则。缺项与判不出按该契约 `#S-12` 区分；不得填入一份空集合冒充成功求值 |
| `content.compositionOrder` | `CapabilityId` 序列，是同一 `evaluation.composition` 的精确排列：每个元素恰出现一次，无额外元素、无遗漏。身份与相等沿 `data.asset-model/v3#S-3`；顺序由写入方提供，本能力不从集合的偶然枚举次序推导 |

1. **谁产生**：写入方对源 `EvaluationInput` 真实调用 `evaluate`，成功后把原结果和有序组成记在同一条 `given` 或 `mint` 记录上。写入方的取得、校验和提交义务由其契约承接；本条不把一次原样 JSON 追加称为已执行求值。`EvaluationInput` 不复制到本投影，本能力不重新求值。两个槽位之外的 `content` 仍完全归写入方。
2. **已有记录不被重解释成成功**：`append` 可以原样保存不含上述槽位或槽位不合约束的合法 JSON；`readHead`、`readHistory` 照旧交回。S-33 选定的最新 `given`/`mint` 源记录存在，但投影缺失或畸形时，以 `unavailable{reason: invalid_evaluation_content}` 失败，不回退到更早的合法内容。必需成员缺席、`content` 不是对象、`evaluation` 不满足 `capability.asset-evaluation/v4#S-47` 的任一读取条件、排列缺失/重复/有额外项均属于此分支。共享纯值读取不执行 `evaluate`，也不引入它的 `invalidInput` 或新的失败枚举；S-47 的可读结果不因此被证明计算正确、来源真实、新鲜或有权访问。`reuse` 只保留被收窄表的原来源，不作为 S-33 的新求值源。
3. **无损与表示层**：沿 [S-11](#s-11-只增不改原样存原样交回) 严格 JSON、重复键拒绝、数无损。不能先用有损解析吞掉重复键或舍入数值，再声称符合投影。`append` 输入不合严格 JSON 仍走原 `invalidInput`；持久内容无法无损读回时读面 `unavailable`，不得悄悄修复或以空值替代。
4. **不替消费者选项**：本投影不另带模型锁、默认模型或两个时限字段。运行时按其精确采用的契约解释真实求值结果：求值成功且模型设置无项与求值取不到是不同事实。第一次选模本批由显式 `selectModel` 记入会话日志；本条不声称闭合自动初选。两个时限不在这里填数，也不从重试件配置借值。
5. **拓展件链的消费者边界**：`data.loop-extension` v3 拥有位置、维度、干预力、报错策略与不可用处置的含义；`capability.loop-extension-runner/v2#S-6` 拥有消费这些值构链、排序及固定链时点的行为。本能力只原样交回两个槽位，不据这些条款新增判定或派发行为；故这两项是拥有者导航，不登记为本契约的规范依赖。系统默认重试的窄验收不表示完整外部拓展链已验证。
6. **已提交与当下求值分开**：本读面回答截至所固定头的最后一次已提交求值，不读取此刻各层持有或配值，不保证提交后发生的变化已经反映其中。模型请求运行时每次发出所需的新鲜输入及重求，由其独立契约承接；不得仅凭本读面成功就声称当前层配值已核实。

### S-33 readEvaluation：读取已提交的求值

| # | 内容 |

| ① | `session`，表示与相等沿本契约原有 `SessionRef`；必填，无默认 |
| ② | 调用方有权读这个会话的清单，沿 [S-16](#s-16-readhead读头与每一类最后一条) ② 与 [S-21](#s-21-装配给的保证-vs-协议须给的保证)；持有会话指认不等于授权 |

## 七、装配给的保证 vs 协议须给的保证

### S-21 装配给的保证 vs 协议须给的保证

[SYS-DEPLOY](../../../../foundation/cross-system-constraints/requirements.md#sys-deploy)：**左列单机时由装配顺带给出，跨进程之后不会自动成立；右列是本契约已经记下的待兑现项（[G-5](#十已知缺口)），不是「以后再说」。**

| 保证 | 本版（单机）由谁给 | 跨进程之后谁重新兑现 | 做不到会怎样 |
|---|---|---|---|
| **条件追加在提交点上判、与写入同一步**（[S-12](#s-12-条件追加判定与写入是同一步)） | **装配给**：据点进程里一份装配清单提供者、一份存储；同一会话的追加在那里排成一列 | **协议给**：每个会话一个定序者（或等价的比较并追加），期望头在定序点上判 | 两次换表都成功：重启之后重建出来的构成取决于谁后落盘——命令集在人不知情时变了 |
| **单写者**：一份清单存储同一时刻只有一个据点进程在写 | **装配给**：存储属主排他（与 SQL 存储的属主排他同一做法） | **协议给**：定序者唯一；换定序者时旧的先被隔离 | 新旧两个进程各排各的序号，(会话, 序号) 在两处各有一条 |
| **求值引用全局唯一**（[S-8](#s-8-求值引用-evaluationref) 第 1 条） | **装配给**：一个提供者铸、一份存储判冲突 | **协议给**：铸法本身保证唯一（不靠单点查重），`given` 的冲突在定序点上判 | 两个会话的记录共用一个引用：一个会话的 `fill` 被当成另一个会话那一次的重试认回 |
| **读到的头与各类最后一条出自同一刻**（[S-16](#s-16-readhead读头与每一类最后一条) ④） | **装配给**：一个存储里的一次一致读 | **协议给**：副本上的读写明它读到哪个序号为止，不以落后的副本冒充头 | 会话资产注册表按半截清单重建（头新、记录旧） |
| **提交即持久**（[S-13](#s-13-提交与持久)） | **装配给**：本机存储，确认落盘才返回 | **协议给**：确认条件写进协议 | 调用方被告知成功，重启之后少一次换表 |
| **在场事实的来源可信**（[S-10](#s-10-在场事实)） | **装配给**：装配把事实交给同一进程里的提供者 | **协议给**：事实带新鲜度与来源，接收边界核对；读不到按判不出 | 一件依赖不在场的拓展件被当成在场去跑，起不来被误记成报错 |
| **调用方身份已核实**（全部操作） | **装配给**：据点进程内的能力间面 | **协议给**：调用携带会话与调用方身份，接收边界重新验证（`data.identity-values/v1#S-30`） | 拿到一个会话指认就能读别人的构成、往别人的清单里写——**本契约的面不得直接暴露成终端 API** |

## 八、交接、缺席与恢复

### S-22 回执丢失与结果未知

**`append` 收 `unavailable`、或调用方根本没等到回答时，这条记录的结果未知：没写下，或整条已写下（不会是半截，[S-13](#s-13-提交与持久) 第 3 条）。**

1. **`given`**：以同一个引用重交——得 `alreadyRecorded{record}` 即上次已写下，得成功即上次没写下（[S-17](#s-17-append条件追加一条换表记录) ⑦）。
2. **`mint` 与 `reuse`**：没有可认回的键。以原来的期望头重交：得 `headMismatch` 说明**有人**推过了头——可能是它自己上次那一条，也可能是别的写入者；写入方要分清，就 `readHead` 读回最后一条、按它自己知道的内容比对。**本版不给这两种追加一个认回键**（[G-7](#十已知缺口)）；单机时同一会话的写入方只有会话资产注册表一个实例（它的节点「进程内的换表队列」），比对得出。
3. **不以读代替判定**：先读头再决定写不写，中间可能插进别的追加——**判定与写入只在同一步里做**（[S-12](#s-12-条件追加判定与写入是同一步)）。

### S-23 提供者撤除、换代与重启

- **本契约的一切事实都在存储里**，提供者实例里没有「只有它知道」的东西；换一个实例、重启，**任何一次判定的答案不变**。
- **撤除时在途的追加**：要么撤除之前提交，要么没有提交；调用方可能等不到回答——按 [S-22](#s-22-回执丢失与结果未知) 收口。**本契约不交接任何活状态。**
- **在场事实**：它们由装配给出（[S-10](#s-10-在场事实) 第 2 条）；提供者重启之后在事实重新给到之前，对应的名字判不出 ⇒ `unavailable`，**不沿用重启之前的**，除非提供者设计写明它们随存储持久。

### S-24 留存：本版不删

**本版没有删除记录的操作，也不因会话归档、会话结束而删**：会话资产注册表按 (会话, 类别, `filledAt`) 读回被顶替的快照（R-M9），它要求「会话存续期内不删」；本版给的比它强——**不删**。
**要不要在会话终结之后清理、留多久**，[PF-004 §6.7](../../../../product/PF-004-agent-definition-and-assembly/design.md#67-装配清单的生与失效) 说是「记录那一侧的事」，本版不收（[G-1](#十已知缺口)）；那时出新版本，且不得删掉仍被一次进行中运行的报告依赖的记录。

## 九、规范表达与验证义务

### S-25 本版选用哪些形式工件

**不建形式模型。**两路写入者共同触碰的存储对象是 (会话, 序号) 与期望头（[S-12](#s-12-条件追加判定与写入是同一步)），这一点与 `capability.session-log` v2 的判重是同一种判定（「对提交点之前的全部记录判，与写入同一步」），那一份的模型以 `Serialized` 开关表达了这种判定的必要性（**该模型未运行，不作证据**）；本契约的比较是一个整数相等，**没有另一种交错会让它在串行前提下出错**。「半截不可见」「读不到不是没有」被任何建模方式吸收，没有能失败的断言。**证据是下面的规范场景与故障注入**，其中 S-26 必须是真并发。

本版不附 JSON Schema。执行状态在[验证入口](../verification.md)，**不写进本版本目录**。

### 规范场景

**每一条都要真跑**。操作层面的实例在 [`examples.md`](examples.md)。

#### S-26 条件追加：两路并发恰一路成

同一个会话，头为 3；两个写入者同时以 `expectedHead: 3` 各交一条 `mint` 记录。**必须观察到**：恰一路成功得 `seq: 4`，另一路 `headMismatch{head: 4}`；这一列里没有第二条序号 4 的记录。**另跑一支**（故障注入）：把判定换成「先读头、再写」两步——**这一支必须出现两条都成功**，它是「判定与写入同一步」唯一的反例。

#### S-27 装配那一次的回执丢了

以 `given{e1}`、`expectedHead: 0` 追加；写下之后、回执送达之前杀掉进程；重启后以同样的参数重交。**必须观察到**：第二次得 `alreadyRecorded{record}`，交回的是第一次那一条（序号 1）；这一列只有一条。另以 `given{e1}` 在另一个会话追加：`evaluationRefConflict`。

#### S-28 按表时刻读回历史

依次追加三条：`given` 填六张（`filledAt` t1）、`mint` 重填 `slash_command`（t2）、`reuse` 去掉一条命令（t3）。**必须观察到**：`readHistory(s, slash_command, t1)`、`(… t2)`、`(… t3)` 各读回对应那一条；`readHistory(s, tool, t2)` 得 `recordNotFound`；以 `filledAt` t2 再交一条改 `slash_command` 的记录得 `filledAtNotIncreasing`。

#### S-29 头与各类最后一条出自同一刻

一边持续追加、一边反复 `readHead`。**必须观察到**：每一次读，`latest` 里每一条的序号都不大于 `head`，且 `head` 那一条的每个类别在 `latest` 里指的都是它。

#### S-30 读不到不是没有

让清单存储读不到（故障注入），调 `readHead`、`readHistory`、`append`。**必须观察到**：一律 `unavailable`；**没有一次交回头 `0`、空映射或 `recordNotFound`**；恢复之后按 [S-22](#s-22-回执丢失与结果未知) 分清 `append` 上次写没写下。

#### S-31 在场判定三种答

装配给出事实：`svc-a` 在场、`svc-b` 不在场；`svc-c` 没有事实。**必须观察到**：`dependencyPresence(s, [svc-a, svc-b])` 得 `{svc-a: present, svc-b: absent}`；`dependencyPresence(s, [svc-a, svc-c])` 得 **`unavailable`**——**不是 `{svc-a: present, svc-c: absent}`**。

#### S-34 新求值不被旧表收窄回退

取得由真实 `evaluate` 成功产出的不同结果 `E1`、`E2`、`E3` 及其明确排列 `O1`、`O2`、`O3`，E2 与 E1 的根设置不同。在会话 A：① `given{ref: R1}` 填六表并记 E1/O1；② 局部 reload 只换一类表，以 `mint` 提交 E2/O2，返回 R2；③ 对仍以 E1 为基准的另一类旧表作收窄，追加 `reuse{ref: R1}`。各次期望头与每类 `filledAt` 合原规则。

**必须观察到**：步骤②之后 `readEvaluation` 为 R2/E2/O2；步骤③之后仍为 R2/E2/O2，根设置不得回退 E1。`readHead` 仍读回步骤③的 R1 引用，`readHistory` 对旧表仍能读回其 E1 基准与收窄事实；不改写这些记录以伪装成 E2。

随后提交 E3/O3 与读取并发，读取只能返回同一读视图内的完整 R2/E2/O2 或 R3/E3/O3，不能使用高于已固定头的记录，不能拼接两份来源。另取不同类别、各自 `filledAt` 递增但跨类别时刻与序号次序不同的两次 reload，必须仍按最大提交序号选源，不按时刻选源。

在会话 B 放序号更大的合法新求值；读取 A 不能取 B 的源。对 A 选定的最新新求值分别注入投影缺失/畸形、读取不可用和记录确定缺失：前两类按 S-33 为 `unavailable`，后一类 `recordNotFound`，全都不得退回 R1/E1/O1。记录确定缺失为损坏注入场景，不表示合规追加会删除源。改变各层配值但未提交新求值时，本读面仍回答已提交的 E2；消费者不得把这个答案称为已核实当下配值。

#### S-35 投影缺席与畸形不能成为成功求值

下列每支均经本能力真实读写边界演练；除注明故障注入外，不绕过原 `append`。写方求值路径与提供者读写路径都须观察到，单有手工 JSON 往返不构成实际生产证据。

| 前提/触发 | 必须观察到 |
|---|---|
| 可读的新会话，头为 0 | `readHead` 仍成功返回头 0；`readEvaluation` 为 `recordNotFound`，不是空的 `EffectiveAssembly` |
| 合法 JSON `content` 不含两个投影槽位、或为非对象 JSON 值 | 原追加成功、原读头原样返回；`readEvaluation` 为 `unavailable{reason: invalid_evaluation_content}` |
| 投影成员类型错误、`compositionOrder` 缺少一项、多一项或重复一项 | 同上；不取数组的可用部分，也不重新排序修复 |
| 给追加面重复键或会失真的数值表示 | 严格表示拒绝或无损读取；不得吞键、舍入后写入，再声称成功投影 |
| 求值成功且模型设置没有对应项，其他必需投影完整 | 读面成功原样交回；运行时依其契约辨认没有模型锁。求值失败或存储不可读时读面不能返回同一成功值 |
| 两个会话拥有不同结果/顺序，交错追加并各自读取 | 每个会话只取得自己的源；由装配/协议验证拒绝跨会话未授权读，不把 `SessionRef` 当授权凭证 |
| 修改源输入中的显式时限，再真实求值、写方成功提交新记录 | `readEvaluation` 交回新源内容。未提交新求值时不伪造已提交变化；运行时每次发出的新鲜输入与重求另按其契约验证，不能由本读面代证；缺时限时不补默认值 |
| 默认重试的内建分支 | 真实求值结果与 `compositionOrder` 经写方落到同一源记录，再由读面供消费者；声明、位置/维度/干预力、报错策略和最终运行时结果分别按其拥有契约验证，不宣称覆盖外部 `needs` 或执行环境 |

**证明范围**：S-34/S-35 是规范验收场景，须由真实提供者与消费者组合执行，未执行不称通过。新增读面没有写入、跨 owner 同提交或在途状态，不新增 TLA+/Alloy 模型；沿原 S-25 保留实际并发读与故障注入义务。有效性核对须能让「按头的 reuse 引用回退」「按时刻代替序号选源」「最新源非法后回退」「吞掉畸形变空结果」「跨会话取源」「拼接两个源」分别被断言否定。

## 十一、提供者映射

提供者与装配映射由版本外入口维护，本契约不选择存储介质或服务注册机制。它要兑现本契约的全部条款；**本契约对它的每一条要求都写成性质**——条件追加的判定与写入同一步（[S-12](#s-12-条件追加判定与写入是同一步)）、求值引用全局唯一（[S-8](#s-8-求值引用-evaluationref)）、表时刻不回退（[S-9](#s-9-表时刻同一类别上严格递增)）、确认落盘才返回且不留半截（[S-13](#s-13-提交与持久)）、头与各类最后一条一次一致读（[S-16](#s-16-readhead读头与每一类最后一条)）、单写者（[S-21](#s-21-装配给的保证-vs-协议须给的保证) 第二行）。**表怎样分、索引放在哪、怎样铸引用**归那个节点。
**在场事实**由装配交给它（验收装配：测试种子；产品装配尚未给出写方，[G-2](#十已知缺口)）。`dependencyPresence` 保持本契约的一个查询；语义归属存疑仍登 G-2。
它**取代**验收装配里「装配清单」那个替身（[据点装配验收替身表](../../../../realization/apps/cli/design.md#验收装配)）；**真提供者**归 PF-004 那一程（[G-1](#十已知缺口)）。
