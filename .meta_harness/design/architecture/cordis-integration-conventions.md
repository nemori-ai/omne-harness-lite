# Cordis 上层集成约定

本页是系统级集成规则的唯一拥有者。IC-1～IC-19 的已采用边界保持；各能力的形状和类型外行为由公开接口拥有者维护。Cordis 约束集成，不决定领域语义。

只采用 Cordis 内核，不采用 DSH 的 agent、工具、记忆或会话运行时。机制事实按已采用版本核对 [basis](../basis/README.md) 中的 Cordis 条目。模型、探针和测试均须声明成立前提，不把有限证据写成整体符合。

这些规则不新增合并硬线。静态读数区分有限静态符合、偏离和 unknown；行为及责任仍需真实消费者证据和独立判断。不得放宽预期、扩大装配例外或改写声明来消除红项。

本页约束新写或修订的提供者及装配，不据规则发布自动宣称存量代码合规。实现方案或上游版本改变时复核相应规则；Cordis 升版先运行 basis 的全部相关 probe，失败条目必须回到对应集成要求重新判断。

## IC-1

每个能力接缝恰有一个 Cordis 服务定义，放在 `packages/core/` 的一个包里（下称定义包）。接缝出自一份能力契约（`capability.*` 或 `composition.*`）的，这份契约的全部接缝放同一个定义包，包名取契约 ID 去掉种类前缀（`capability.session-log` → `core/session-log`）。接缝出自某个 `core` 包拥有的协议形状、没有自己的能力契约的，定义放进那个包（`storage` → `core/storage`，`clock` → `core/offer-expiry`）。装配入口要交给插件的运行时对象（迁移提供者、启动信号、维护回调）同样经接缝交：定义放在拥有那份形状的 `core` 包，装配入口 provide、插件 inject（IC-16）。提供者与消费者都不持有服务定义

## IC-2

服务键只写一次：抽象 `Service` 以 `static readonly provide = '键'` 声明键，构造函数 `super(ctx, <类>.provide)`，定义包导出的键常量取自它。提供者 `extends` 这个抽象类，不另写键，也不自己 `ctx.provide` 这个键；消费者引用定义包的键常量。一个插件提供几个键（同一份实现的几个服务面）时，在插件体里逐个 `new` 各键的子类，它们都登记在这一条插件的 fiber 上；也可以把子类本身当插件装、一个键一条 fiber——按提供者的撤除与在途承诺选，并写明理由

## IC-3

服务定义的形状：抽象 `Service`（不含实现），或具体的注册表 `Service`（含登记逻辑，本身可作提供者装上）；不是只有类型的 `interface`。抽象 `Service` `implements` 根入口里的操作类型，同一组签名不写两份。类上的 JSDoc 写 `@contract <契约 ID>`，只写 ID、不写版本；接缝出自协议形状、没有契约的，改写 `@owner <拥有它的 core 节点路径>`（如 `packages/core/storage`），二者必有其一

## IC-4

**包的两面**：每个包的根入口与 Cordis 无关——定义包的根入口放词汇类型、操作类型与纯函数；提供者包的根入口放不依赖 Cordis 的公开函数面（函数或工厂）。Cordis 绑定（键、`Service` 类、`Context` 与 `Events` 增补、插件）一律放同包的 `./cordis` 入口。根入口不 import `@deepseek-ai/cordis`，也不 import 本包的 `./cordis`。`core/kernel-basis` 与 `apps/` 不受此条约束

## IC-5

消费者只依赖服务定义：按服务键取用，不 import 提供者包。别的成员为正确使用一份契约的数据而要用的纯函数（编解码、校验、比较）是契约的词汇，放定义包的根入口；提供者包只留实现自己的东西。非装配成员的跨成员 import 只指向 `core` 与 `util`；例外只有一类——为同一提交导出的事务内读函数——在实际拥有者的行为规格中声明，并写出两个写入者共同触碰的存储对象

## IC-6

同一个 isolate 标签下，一个接缝只有一个提供者在场；要两份实现并存，分到不同的 isolate 标签下，并在装配拥有者的行为规格中写明谁看见哪一份

## IC-7

命名：定义包取契约名（IC-1）；提供者包取限定名，说出实现方式或后端（`storage-sql`、`session-log-jsonl`、`credential-custodian-local`），只有一个提供者时也一样。服务键用 camelCase 名词，说能力不说实现（`storage`，不是 `sqlStorage`）

## IC-8

必需依赖写在 `inject`：数组字面量，元素是字符串字面量或从定义包 import 的键常量；不在运行时拼、不经变量转手。写进去就等于「它换代或不在，我就卸载重跑」。插件里只有一段工作需要某个依赖时，用 `ctx.inject([...], cb)` 把那段放进子 fiber，不把整个插件挂在它上面

## IC-9

可选依赖不写进 `inject`：调用时用 `ctx.get(键)` 或 kernel-basis 的 `resolveOptional` 现取，接受 `undefined`，按契约的缺席默认答案收场；`ctx.<键>` 只留给 inject 过的键；只要类型增补时写 `import type {} from '<定义包>/cordis'`。提供者写明提供者换代时手上的旧引用怎么处置

## IC-10

事件名 `<范围>/<事件>`，全小写 kebab。范围是声明它的那个包的名字（不带 `@omne-harness-lite/`）；跨成员事件的范围取它所属定义包的名字，迁移途中暂时声明在别处也不改。通知（`emit`、`parallel`）的事件部分用过去分词，可带对象前缀（`session-log/appended`、`organization-governance/membership-changed`）；控制（`serial`、`bail`、`waterfall`）的事件部分用动词原形，说被问的那个动作（`tool-admission/admit`）

## IC-11

事件在声明它的包的 `./cordis` 入口增补 `Events`：跨成员监听的事件由拥有它的服务定义包声明，只在一个成员内部用的留在该成员。每个事件的 JSDoc 写 `@mode`（五种派发之一）与载荷的 `@param`；公开派发承诺与它一致

## IC-12

派发：**可否决的异步控制用 `serial`，不用 `bail`**——`bail` 不等 Promise，Promise 本身被当成否决值；`bail` 只承载同步判定；`waterfall` 用于环绕改写。通知有两种：`emit` 的监听者同步执行、**不得返回 Promise**（要做异步的事自己起、自己兜住失败）；要等异步监听者的通知用 `parallel`。两种都由发通知的一方包住（`emit` 包 `try`，`parallel` 在 `await` 外包）：监听者失败只记一条诊断，不改变已提交操作的结果

## IC-13

登记即效应：注册表 `Service` 的 `register()` 在方法里用 `this.ctx.effect(...)` 登记并返回撤除函数——登记落在**调用方**的 fiber 上，调用方撤除即撤掉；监听一律经 `ctx.on`。注册表不自己记「谁登记了什么」再等人注销。提供者的验证义务中要求：贡献者卸载后，它的登记不在了

上述贡献者配对仅在插件内调用成立。根 Context 调 register 时效应属于根 fiber，不随某个贡献者撤除；只允许测试或装配入口这样使用。以 ctx.provide 发布的普通对象没有 Service 的调用方 ctx，不能据此取得相同自动归属。

## IC-14

插件配置用 Standard Schema 校验（函数插件经 kernel-basis 的 `definePlugin`，`Service` 子类写静态 `Config`；Cordis 4.0.4 对两种插件都按 Standard Schema 校验，`registry.ts:104`、`fiber.ts:50-53`）；可调参数——重试、退避、超时、限流、阈值——写成配置字段，默认值只是初值；配错在加载时失败（fiber `FAILED`），不静默跳过缺失的引用

## IC-15

一个进程挂哪些 Cordis 插件、各带什么配置，写成数据：[Cordis 插件树](../ubiquitous_language/terms/architecture-core-and-extension.md#ul-cordis-plugin-tree--cordis-插件树--cordis-plugin-tree)由两格[插件树层](../ubiquitous_language/terms/architecture-core-and-extension.md#ul-plugin-tree-layer--插件树层--plugin-tree-layer)叠出——发行层在前、运维者层在后；没有组织、租户或会话这几格

## IC-16

插件树的一行 = 行 id ＋ 插件（包名与它 `./cordis` 入口里的导出名）＋ 配置。配置只放可序列化的数据；运行时对象（迁移提供者、信号、回调）不进树，由装配入口 provide 成服务、插件 inject（定义归属见 IC-1）。运维者层按行 id 整行替换配置、停用或插入新行；**指向不存在的行 id 即启动失败**；进程能打印最终的树，并标出每一行出自哪一层。发行层的行 id 因此是对运维者的稳定承诺：改名或删一行要写进装配拥有者的当前说明与发行说明

## IC-17

运行中按会话为 agent 装上的 Cordis 插件**不进**插件树。原则：它们落在会话这一级的作用域里——事件按作用域过滤，撤除按作用域整体撤，故障不出作用域，登记不漏到别的会话。机制与正式名由「按会话装插件的作用域」这份设计定（UL-D-7 没有为它立词）

## IC-18

租户身份显式：跨边界操作的租户身份是操作的参数（或参数里的身份值），不从 `ctx`、isolate 标签、插件实例或「谁装了这个插件」推断；不把「不 inject 就够不着」当访问控制

## IC-19

装配给与协议给：契约里靠同一进程、同一 Context 才成立的保证，实际拥有者在行为规格中写明此刻靠什么兑现；拆成多进程时，它们要由协议重新兑现

## 审阅与验证责任

| 要判断的责任 | 对应规则与证据 |
|---|---|
| 定义拥有者、纯入口和跨包消费 | IC-1～IC-5、IC-7；源码、声明、装载及实际制品检查 |
| 可替换提供者、必需／可选依赖 | IC-6、IC-8、IC-9；换代、缺席及旧引用的真实组合测试 |
| 类型化事件及失败影响 | IC-10～IC-12；声明／派发对应，监听失败不得改变已提交结果 |
| 贡献登记、撤除和在途责任 | IC-13、IC-19；调用方 fiber 撤除、实际停止与责任释放证据 |
| 配置和两层插件树 | IC-14～IC-16；非法配置／悬空修改拒绝、来源打印和装配顺序 |
| Session 作用域及租户授权 | IC-17～IC-19；明确区分作用域可见性与数据授权，未采用机制不得声称符合 |

每个提供者自行说明装载、停止准入、取消、实际完成及撤除的配对责任；内核未提供的进展、事务和跨进程保证由实际协议拥有者兑现。公开类型同形不证明 LSP 或生命周期正确。

服务图和事件矩阵从实际源码派生；架构预期由系统级约束维护，不另建手写实现绑定或完整服务分类表。单次读数、评审与迁移过程归工作树 tmp。

非装配成员的事务内读函数例外只能按精确目标、符号及共同存储对象采用，不能扩成提供者互引豁免。当前无此类独立中央绑定清单；新增或修订例外须由承诺拥有者说明并同步实际检查输入。
