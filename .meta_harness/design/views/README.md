# 派生视图

这里的每一份文件都由生成器产出。**没有人手写，也没有人手改。**

失效事件：上游任一处变动。因此这里不判断、不裁决、不保存任何别处没有的事实——
它只是把散在各处的坐标重新排列，让人和 agent 少跳几次。

## 三条纪律

1. **不得被引为依据。** 需要引用时引上游那份手写的家。视图用于找到入口和发现缺口，
   不用于证明任何状态。
2. **与上游不一致时以上游为准**，重新生成即可；不手改视图使它看起来一致——
   那会制造一份没有来源的事实，且下次生成就被冲掉。
3. **每份带 `derived-from` 与生成时间**。读者据此判断这份视图是否还新鲜，
   而不是凭它看起来完整就采信。

## 视图清单

| 视图 | 从哪里 join | 回答什么 |
|---|---|---|
| `object-index` | covers + catalog + bindings | 某个装配对象牵涉哪些条款与契约 |
| `subject-page` | covers + catalog + bindings + record | 某个契约「现在是什么样」的一页导航 |
| `system-map` | catalog + lineage + realization | 当前有哪些能力、怎样组合、谁实现 |
| `coverage-report` | covers + bindings + verification | 哪些需求条款没有承载者，哪些承诺没有证据 |

## 为什么这几样必须派生

**object-index**：装配对象是会被重新分解的那一层。以它为键手写一份索引，
每次重分解整份作废。派生的索引以契约条款为键做 join，契约拆分后按
[lineage](../registry/README.md#lineage) 的条款级 mapping 自动仍然正确。

**subject-page**：「某个对象现在是什么样」的内容**全部来自别处**——
条款在 product 与 foundation、承诺在 spec、绑定在 realization、证据在 record。
手写它就是造第二份权威，且每次重分解都要改。

这类页面手写出来通常只有 6 到 10 行：它想成为入口，却因为不拥有任何事实
而只能转发，于是既没省下跳转，又多了一处会过期的地方。
正解不是把它写厚，是让它被生成。

**coverage-report**：手工维护的汇总计数半衰期短于被汇总的内容。
读者无从判断某个数字是刚核对过还是三个月前的残留，于是整张表一起失去可信度。

## 入库与一致性

视图入库，因为被读取是它存在的唯一目的——不入库就等于没有。
入库带来的漂移风险由生成器的 `--check` 模式守：检查应生成的文件是否存在且一致，
不一致即失败。这与 agent 产物编译采用同一种做法。
