# 产品设计区的维护与导航

本文件说明这个目录**拥有什么、怎么维护、从哪读起**，对进来的所有人成立。

**产品设计怎么做**——岗位视角、产品语言、什么自己定什么上报——归 `product-design` skill。
那份会把你的视角切成 product manager，**只有真要在这里落字的人才加载**；
做技术设计、规格或实现的人不加载它，产品正文对你们是**输入**，读它不需要换视角。

## 你来这里做什么

| 情形 | 怎么做 |
|---|---|
| 起草新 topic、修订产品正文、把一次交流落成设计、判断某项取舍自己定还是上报 | **先加载 `product-design` skill**，再按下面的维护规矩落盘 |
| 评审一份产品设计稿 | 委派 [product-design-reviewer](../../agents/roles/README.md)；自己看也先加载同一份 skill——**评的判据要和写的判据是同一套** |
| 做技术设计、规格或实现，把产品正文当输入 | 按下面的阅读地图取你要的那几节，**不要加载那份 skill**。读它不等于可以改它 |
| 读出产品正文有错、有洞或与实现对不上 | 报给该 topic 的 owner 或产品负责人，**别顺手改**，也不要在技术材料里另写一份「修正版」——那会变成第二份产品权威 |
| **要改一个 PF，想知道波及多大** | **先看[架构内核 PF](architecture-core.md)**：在那份清单上的，**改的是别的 PF 赖以成立的前提**。代价、半径与动手前的三个自检问题都在那里 |
| 只是要某个词的准确含义 | 直接去[统一语言](../ubiquitous_language/index.md)，不必进 topic |

## 一个 topic 里，答案在哪一份

以下stories规则只用于未迁ST。新Issue操作从[交付入口](../../../docs/engineering/agent-delivery.md)核对启用范围；未来产品模板中的活动查询不替换当前PF，不能直接复制整包并沿用旧stories／projection义务。

查**这个概念是什么、规则怎么定的** → `design.md`；
查**它怎么动、这步失败了怎么办** → `flows.md`；
查**做成什么样算对** → `acceptance.md`；
查**还有哪几块没交付、先做哪块、交付了怎么演示** → `stories.md`（[故事卡](conventions.md)，可选；它是交付切片，**不是产品含义的来源**，交付了的卡不在里面）；
查**当前适用范围、必要理由和未决** → `design.md` 的对应章节；
变更与讨论过程只放执行工作树 `tmp/<task>/`；

完整包结构、关系声明的 front-matter 格式与建包准入条件，见 [README](README.md)。

## 怎么管理 topic

### 什么时候建新 topic

建新的，当这块内容有**独立的存在理由**：它解决一个可以单独陈述的问题，
有自己的使用者，且改动它的原因与现有 topic 不同。

不建新的，当它只是某个 topic 的一部分细节——那种情况扩展已有 topic。

**判据**：你能为它写出一段「背景与问题」，且这段话不是另一个 topic 的翻版吗？
四个准入问题见 [README](README.md#准入)；答不上来就先不建包。

**还要判断它落在[架构内核](architecture-core.md)内还是外**：
**你是在立规矩，还是在用规矩？**发现自己不得不新立一条别人必须遵守的协议，
**那说明这块内容要么属于某个已有的架构内核 PF，要么这条界线该重新划**——
后者是产品负责人的裁决，不是你能自己定的。

### 怎么建

从 `.templates/topic/` 复制整包，按实际情况裁剪。
`design.md`、`README.md` 必须保留；
其余按需要取舍。模板里的 `{{提示}}` 是填写指导，成稿时替换或删除，
**不要留着占位符冒充内容**。

### 三种关系怎么用

关系声明在 `README.md` 的 front-matter，那是唯一的机器可读处。

| 关系 | 用在什么时候 | 后果 |
|---|---|---|
| `supersedes` | 对方的**全部**内容被本 topic 吸收 | 对方退役进 [archive](archive/README.md)，且必须带条款级去向映射 |
| `depends-on` | 引用对方定义的概念，本 topic 直接用而不重复定义 | 对方改定义时本 topic 要复核 |
| `extends` | 在对方基础上扩展新范围 | **对方继续有效**，两者并存 |

最容易搞错的是 `supersedes` 与 `extends`：前者对方**死掉**，后者对方**活着**。
只吸收了对方一部分内容的，不是 supersedes——那种情况下对方修订自己的范围并继续存在。

### 改动怎么记

**改变含义就要递增 rev 并同步当前消费者。**变更过程放工作树 tmp。错别字、链接修复、换个位置不算。

判断标准：读者据 rev 判断自己手上的理解是否还成立。
一次没记的修订，等于让所有下游无从判断。


**改故事卡不升 rev。**重新切分、调换顺序、改演示步骤，动的是交付怎么分块，不是产品是什么；
给已有的验收场景补编号同理。**反过来，切卡时发现少一条场景或某条场景要改，那是改 `acceptance.md`，照上面的规矩记**——
新的产品要求不许只写在卡里。**接受或作废的卡从 `stories.md` 删掉，也不升 rev**；已交付的场景后来含义变了，旧编号作废、给新编号，那是改 `acceptance.md`，要升。
格式、编号规则与卡的一生归[故事卡的格式契约](conventions.md)。

### 取代怎么做

取代是一次**明确的动作**，不是「不再维护」的默认状态。
四个步骤与各自的道理见 [archive/README.md](archive/README.md)，那里是这条规矩的唯一正文。

**只吸收了对方一部分内容的，不是取代**——那种情况下对方修订自己的范围并继续存在。

## 红线

这几条约束**任何在这里落字的人**，与他扮演什么角色无关。

- **不把技术实现写进产品设计。**判据：这条内容产品负责人能看懂并判断对错吗？
  不能，就归技术设计（`spec/`、`realization/`）。反过来也一样：技术设计不改产品语义。
- **不发明没人拍板的东西。**可以推导，但推导过程放任务 tmp，确定后的必要理由与边界归 design 正文。
- **不为了文档完整而填默认值。**未决项以显式缺口存在，比填一个看起来合理的猜测安全得多——
  猜测会被下游当成已定事实实现出来。
- **不静默修掉发现的问题。**将仍影响当前规则的缺口写进 design 正文的未决项，让它可见；
  静默改掉会让后来者以为这里从没出过问题。
- **正文只写最终确定的设计。**`design.md`、`flows.md`、`acceptance.md`、`README.md`
  回答的只有「**现在是什么样、为什么是这个样、有什么后果**」。
  **「rev N 以前是那样」「这一版把 X 移交给了 Y」「这条是我推的、某日核对确认成立」
  一律不进正文**——讨论、修订和接受过程都归执行工作树 tmp。
  混进去，读者就得先分辨哪句还算数；而下一次修订之后，那些对比谁也不会去维护。
  **例外只有 `depends-on` 表里标别人的精确版本，那是契约引用；`README.md` 的「状态」段写本 topic 的 rev 同理。**
- **概念只定义一次**，且**用[统一语言](../ubiquitous_language/README.md)里的那个词**；
  **新概念先进[词表](../ubiquitous_language/index.md)，再进正文**，没有例外。

## 与技术设计的交接

产品设计完成之后，技术设计沿 `harness-design-handbook` skill 展开，
系统级预期归architecture；模块公开类型、薄SPEC、必要理由和验证资源归实际接口/提供者拥有者，不在产品topic保存技术快照。
产品设计是那条链的**输入**，不是它的一部分——两者的作者视角不同。
