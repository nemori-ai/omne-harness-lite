# PF-021：产品验收场景

这些场景检查已确定的产品边界，不表示产品已经实现或通过运行测试。
本轮产品选择已明确；完整交付仍需落实 [技术设计交接](design.md#十技术设计交接事项) 并进行运行验证，本表不以正向样例代替技术契约。

## 已确定场景

| 编号 | 情形 | 可观察判据 |
|---|---|---|
| A01 | 用户手动创建安排，agent 也创建安排 | 两者均创建包含 Routine 与时间的 Schedule，并查看到期 Job；不要求先建 Routine，不建立两套不相通的日程 |
| A02 | 同一内容分别安排明天一次及每周重复 | 每份 Schedule 持有自己的 Routine，内容与时间职责可区分；相同内容不产生可变共享对象，各次 Job 来源清楚 |
| A03 | 每周五执行与每月第一个周一执行 | 两类确定性规则均可表达并核对有界预览；不要求用户拆出每个日期 |
| A04 | 某月末最后一个工作日包含中国调休影响 | 使用所选日历数据计算，不能仅把周一至周五当工作日；数据不足明确可见 |
| A05 | 同一租户 Schedule 需要 agent 执行并到期两次 | 两个需要 agent 执行的 Job 各自关联为其新建的不同会话；不存在复用会话模式 |
| A06 | 分别选择两份可用的 AgentDefinition 来承接 Job | 两份都附加统一成果工具及目标完成检查；不会因其中一份定义没自带工具就漏装 |
| A07 | 普通 agent 回复“完成”或停止输出，但 Job 目标未完成 | 不能仅凭回复或 Run 结束认定 Job 完成；目标检查有可辨认的结果；对照本次目标和交付要求判断，机制由技术侧验证 |
| A08 | 作业会话提交成果 | 成果交回本会话关联的 Job，不用用户自行猜它属于哪次安排；进度上报与候选最终成果提交可区分，候选成果须经目标完成检查 |
| A09 | 明天下午三点发送固定通知 | 到点通过通知能力向目标租户交付通知，不启动 agent 工作会话；送入目标租户可持久取回的范围即算送达 |
| A10 | 执行并通知 Job 已产生成果，但通知失败 | 同一个 Job 分别呈现执行与通知结果；不能因通知失败倒写工作未执行，也不能把成果上报当成通知送达 |
| A11 | 日历应用与 harness 同地部署 | 日历仍有独立产品责任，不能因同地部署取消其供应、查询与健康可见性 |
| A12 | 无网络首次安装正式发布物 | 中日美三份数据在覆盖内都可用，至少覆盖发版自然年；无网络不使初始化失败 |
| A13 | 安装后联网刷新失败，随后重复初始化 | 保留已有可用数据及真实信息截至时点，不以安装时间冒充新鲜度，不退回旧种子 |
| A14 | 美国日历用于回答某日是否放假 | 明确是联邦假日范围，不能声称全国所有主体都放假 |
| A15 | 已发布年度出现带新权威出处的修订 | 校验后产生新不可变版本；旧版和原出处仍可追溯，覆盖允许跨年累积 |
| A16 | 数据下载成功，但关键假日缺失或覆盖收缩 | 候选不能替换当前版，拒绝原因可观察 |
| A17 | 重叠日期发生没有新权威出处的静默修改 | 保存差异并呈现待裁；不自动采用，也不静默丢弃 |
| A18 | 覆盖将耗尽且新数据迟迟未发布 | 在耗尽前按该历政策告警；覆盖外查询明确缺依据 |
| A19 | 发布物任一日历达到严重新鲜度告警条件 | 不能发行；警告级情形须显式声明，不能用统一固定天数代替各历政策 |
| A20 | 使用相同规则、时区与日历版本进行预览和到期计算 | 日期结果一致；查询或预览不会修改日历、Schedule 或 Job |
| A21 | 以 Schedule 引用预览，再按同一份实际定义显式预览 | 前若干次日期及各次裁定说明一致 |
| A22 | 显式查某个已发布版本，或查当前已发布版本 | 能说明本次使用的版本，保留相应版本后答案可复核；不把默认策略藏在入口里 |
| A23 | 已有当前生效日历选择，直接查询与先取身份再查询 | Calendars 计算命令直接使用生效日历选择，与先 get 解析身份再计算的结果一致；无生效日历时明确缺依据，不代选。配置沿既有租户设置，查询不改写已有安排 |
| A24 | 离线安装带有更新种子的发布物 | 更新种子按校验与发布规则成为可用版本；重复同一安装不重复铸造版本 |
| A25 | 中国数据的两个交叉核对来源实际出自同一上游 | 不能以两份转写满足双源独立核对要求，来源关系与不足可见 |
| A26 | 来源出现美国半天关闭或中国部分公民半日假 | 仍按全日法定状态分类，半日事实保留出处备注；不能把它误报成全天非工作日，也不能宣称已支持半日计算 |
| A27 | 为同一时间规则分别安排执行、通知、执行并通知 | 三种工作类型均可表达；前者承担执行，中者承担通知，后者由同一个 Job 承担两部分工作 |
| A28 | 租户的执行并通知安排需要 agent 执行并到期两次 | 每次 Job 均为执行部分新建专属会话，统一成果工具及目标检查不缺失；通知部分不另建 agent 会话 |
| A29 | 系统和 agent 分别发起无 Schedule／Job 来源的通知 | 两者均可在授权范围内发送，通知由通知能力送达到明确目标租户；不要求先建日程或作业会话 |
| A30 | 同一账号属于两个组织，通知指定其中一个租户 | 目的地保持该租户身份，不因账号相同自动送入另一租户；跨租户默认拒绝 |
| A31 | 获授权使用者配置、管理并切换计算所用日历 | 系统提供这些操作及更新维护能力，所用日历可辨；已有 Schedule 保持其日历身份；新 Job 调派前采用最新发布依据，已有 Job 不受改写 |
| A32 | 通知发起成功但交付尚无证据或已失败 | 真实状态可辨，不把已发起当送达；送达须能在目标租户范围取回，不以已读为条件 |
| A33 | 系统在安排到期时承担调度 | 产生对应 Job 并触发执行、通知或两者；仅保存安排不能算完成调度能力，按日程声明的补跑与重叠策略处理异常 |
| A34 | 系统为自身的机械操作建立日程 | Schedule 及其内部 Routine、到期 Job 可明确系统归属，不借用特定账号、组织或租户，不要求创建特殊系统租户 |
| A35 | 系统自动更新检查日程到期 | 触发预先定义的机械操作并记录实际结果，不创建 agent 会话，不通过模型完成检查；检查不代表授权自动安装更新 |
| A36 | 试图把需要 agent 推理的工作放进系统自用日程 | 不能以系统自用机械日程承接，不绕过租户会话身份；出厂提供的 agent 工作形成租户日程 |
| A37 | 租户采用系统出厂提供的 Routine | 来源可辨为系统提供，采用后的 Routine 由 Schedule 持有，Schedule 及 Job 归该租户，agent 执行仍用专属租户会话；不把具体 Routine 内容或默认启用视为已设计 |
| A38 | 曾管理系统日程的人切换组织或租户身份失效 | 系统日程的归属不随其改变，也不因其个人身份变化消失；管理资格仍独立判断 |
| A39 | 系统机械工作需要向租户发送通知 | 日程与 Job 保持系统归属，通知目标租户明确并受相应授权约束；送达不转移来源工作的所有权 |
| A40 | agent 从空白创建一份完整安排 | 一次 Schedules.create 提交 Routine 与时间，返回 Schedule 身份和真实生效情况；不要求或返回独立 Routine ID |
| A41 | 同时修改工作内容与执行时间，其中一部分无法保存 | 不出现内容或时间部分保存／部分生效的安排，失败或未知如实返回 |
| A42 | 两份日程内容相同，修改其中一份 Routine | 只影响被修改的 Schedule，不修改另一份，也不需要共享引用拆分或派生 Routine 对象 |
| A43 | 两个租户采用同一出厂预置，之后其中一个定制内容 | 本租户日程可改自己的工作描述，另一租户及出厂预置不变；不自动跟随预置更新 |
| A44 | Schedule 内容已经修改，查询过去的 Job | ScheduledJobs.get 返回该次实际采用内容及结果，不用日程当前内容替换历史；Job 进度和成果彼此分离 |
| A45 | 管理 agent 已装配日程工具，尝试上报任意 Job 成果 | 管理资格不代替作业会话绑定；普通管理会话不凭 Job ID 使用 CurrentJob 写入其他作业 |
| A46 | 作业会话需要交付结果但未获日程管理能力 | CurrentJob 必须可用于本次交付，Schedules 不因作业身份自动装配或授权 |
| A47 | report_progress、submit_result 或 report_problem 调用成功 | 分别只证明进度记录、成果提交或问题上报；不自行证明 Job 成功、失败、取消或通知送达 |
| A48 | agent 预览日期、查看预置或读取已有日程 | 均不保存、启用、生成 Job 或发送通知；日历版本与计算依据可核对 |
| A49 | 管理 agent pause 或 stop 日程时，已有 Job 正在执行 | 控制后续安排不自动取消已有 Job，不删除结果；漏跑和重叠按本日程声明，技术侧保证产生 Job 与状态变化结果确定 |
| A50 | 普通 agent 已有日历计算和日程管理权限 | 不因此得到供应更新发布、持久全局切换或系统日程管理权 |
| A51 | 检查工具清单与完整安排读取结果 | 五组普通多命令工具中没有 Routines 槽；Schedules.get 直接包含 Routine，不返回待二次查找的 Routine 对象引用 |
| A52 | Notifications.send 仅返回发送受理及交付查询定位信息 | 不宣布已送达，get_delivery 继续反映真实已知结果；具体记录身份归技术设计，送达判据沿 design §6.5 |
| A53 | agent 获准创建一个完整安排 | 创建成功即启用；不另有日程专用审批。后续 Job 的每项工具动作仍按自身授权判定 |
| A54 | 修改日程时已有一个未开始 Job | 该 Job 保持其产生时确定的工作要求；只有之后产生的 Job 采用修改 |
| A55 | 创建者仅给过本会话授权，之后 Job 新建会话 | 不复制授权流水，也不从创建成功推出未来全部动作获准；租户层授权沿既有规则生效 |
| A56 | 新 Job 未指定工作区或先前成果输入 | 不继承创建会话或上次 Job 的工作区、整段历史与进度；显式引用仍须判权 |
| A57 | 结束一份安排后调用 resume | 不能恢复已结束安排；既有 Job 与结果保留，新需求可另建 Schedule |
| A58 | 用户不在线时通知送入目标租户可取回范围 | 算送达但不算已读；用户重新进入该租户仍可获取通知 |
| A59 | 同一 Run 尝试重启，或已停止后收到迟到成果 | 前者沿 PF-012 保持原 Job／会话；后者只留证，不把被取消工作改成正常成功 |
| A60 | 两个完整日期端点统计工作日，或增减 N 个工作日 | 统计含两端；增减从起始日之后／之前数，N 为零返回起始日；仍须使用明确日历版本及覆盖 |
| A61 | 预算后日历发布修订，使下一次候选不再有效 | 接受 Job 前重算并修正候选，不按旧预算调派；预算本身不是 Job |
| A62 | 日历更新时已有等待中的 Job | 本次目标、来源时刻、采用依据与策略保持不变，仍可推进；不挪动、取消或再创建一份对应工作 |
| A63 | 本地时刻因夏令时不存在或重复，或多个原计划平移相撞 | 不存在跳过，重复取第一次；碰撞合并并保留来源；跳过不耗次数，创建一个 Job 计一次，平移不越截止 |
| A64 | 恢复时漏过十次，声明补最近三次 | 只选择最近最多三次，按原时刻从早到晚处理，更早明确不补；下一轮不能再补另外三次 |
| A65 | 恢复时已有两个等待 Job，另有三次未处理时刻 | 等待 Job 继续自己的工作，不当作漏跑重建、不占新的补跑名额；三次按补跑上限与最新依据判断 |
| A66 | 补最近三次同时声明跳过重叠，先前工作尚未结束 | 补跑不绕过重叠声明；被跳过候选有记录、不伪造 Job、不在下一轮继续补它 |
| A67 | 同一日程分别选择四种重叠类型 | 跳过、停止先前后执行、独立并行、按原时刻等待各有可辨结果；不同 Schedule 不互相套用这份策略 |
| A68 | 替换策略已发停止请求，但停止未确认或失败 | 新工作不开始并行，明确呈现替换受阻及原因；请求受理不能冒充实际停止 |
| A69 | 并行的一个 Job 失败、停止或发送通知 | 其他 Job 的会话、目标、进度、结果与通知不被合并或级联改写；外部共享资源不被伪称自动隔离 |
| A70 | 已排队 Job 遇到 Schedule 策略更新或结束 | 自己采用的配置不回写；结束 Schedule 不自动取消既有 Job。后续新工作按自己的新声明处理 |
| A71 | 只修改日程的补跑上限、重叠类型或通知事件集合 | 一次 update 完成并由 get 返回完整配置，日程身份不变；历史 Job 返回旧配置，没有独立策略对象或新工具槽 |
| A72 | 开始、成功、失败、取消事件选择不同组合 | 只有选中且实际发生的事件触发通知；等待不等于开始，未命中的明确不适用 |
| A73 | 同一个执行事件的通知发送失败后重试 | 保持同一逻辑通知，不递归生成执行失败通知；提交成果不再隐含另发一条 |
| A74 | 执行成功但应发的开始或成功通知未送达 | 执行成功事实保留，整体不能冒充全部完成；未选中的事件不被伪造为已送达 |
| A75 | 创建或更新缺少策略、补跑 N 非正整数、工作类型与通知声明不匹配 | 明确失败并说明缺失或不匹配，不隐含选择全局默认，不部分保存生效 |
| A76 | 截止 9 月 30 日的日程从 9 月 29 日停机到 10 月 1 日，声明补最近两次 | 恢复仍可补截止内 29／30 日的合法未处理时刻，处置后自然结束；若已手动 stop 则不再新建任何补跑 Job。补跑不超剩余次数 |
| A77 | 9:00 恢复，8:00 被选为补跑、9:00 正常到期，声明跳过重叠且每次执行一小时 | 统一先处理 8:00，再处理 9:00；9:00 因先前动作未结束而跳过且原因可查，不能由扫描顺序偶然反转结果 |
| A78 | 新日历将另一来源平移到本日程既有 Job 的有效时刻 | 新候选记录为因既有工作跳过，不创建第二份，不增补旧 Job 来源；原 Job 的目标、依据与来源不变 |
| A79 | 每月 1 日非工作日，分别选择保持、跳过、前移、后移 | 各自保持原时刻、不建 Job、到此前最近工作日、到此后最近工作日；工作日保持不动，中国补班按工作日处理 |
| A80 | 平移结果跨月、触及起止边界或显式排除日期 | 跨月本身允许；越过起止或首次启用边界、原日期或结果日期被排除则跳过，不再寻找另一天；日内时刻保持 |
| A81 | 平移途中日历缺覆盖，或保持原日但基础规则是最后工作日 | 均明确缺依据，不能猜日期；与日历无关且保持原日的安排不强求日历 |
| A82 | 同一日期配置通过 create/update/get/preview 使用 | 类型与参数可配置和核对，预览说明基础日期与平移／排除结果；缺少必需选择明确失败；已有 Job 不改写 |
| A83 | 每月 31 日遇二月，或第五个星期一当月不存在 | 该期无候选，不改成月末、不消耗次数；每月最后工作日仍依所选日历求解 |
| A84 | 一次性安排声明遇非工作日后移，接受前日历修订 | 同样按最新依据重算；保持原日的一次性绝对时刻不被日别改变；一次性明确跳过后自然结束 |
| A85 | 等待中的 Job 没有会话，用户取消，之后前序结束或系统重启 | 取消成功后永不启动本次工作；不依赖 Run，不退次数、不补跑，Schedule 及其他 Job 不变 |
| A86 | 管理 agent 查看权限有效但没有取消权限 | cancel 拒绝且不停止工作；获授权后可用同一入口取消，不授予跨租户或系统机械管理权 |
| A87 | 取消与开始、完成竞争，或同一请求重复 | 按实际先后分别不启动、走停止或返回已有结局；停止未确认不报已停止，重复不产生新工作或重复通知 |
| A88 | 执行并通知在开始前取消，配置了取消通知 | 只触发取消事件，不虚构开始事件；既有通知和成果保留，迟到成果不能复活 Job |
| A89 | 纯通知在发送前取消、发送结果未知，或组合执行已成功但通知待送达 | 前者不再发送；未知保持未知且不承诺撤回；组合执行成功不改成取消，原通知义务继续 |
| A90 | 等待前序停止的新 Job 被取消，前序停止尚未确认 | 新 Job 不启动，但已发出的前序停止事实不撤销；真实停止进展可查 |

## 绝不能用来冒充完成的结果

- 保存了一句自然语言就称 Schedule 已生效，却不能说明生效规则或未来时刻。
- 需要 agent 的 Job 已建但会话未建好，就显示 agent 已开始工作。
- 把系统自用日程挂在管理员租户下，或用系统机械操作名义启动无租户 agent 执行。
- 同一个会话承担两个不同定时执行 Job，或要求用户额外选择专用 AgentDefinition 才能得到统一成果工具。
- 工具调用成功、Run 结束或会话归档就自动宣布 Job 达成目标。
- 为了“必须完成目标”忽略用户停止，或把失败、未知结果写成成功。
- 用“已尝试通知”代替“用户收到”，或为纯通知启动 agent 生成内容。
- 从日历更新成功推出过去错过的工作已经补做。
