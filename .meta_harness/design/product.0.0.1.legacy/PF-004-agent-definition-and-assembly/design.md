# PF-004：Agent 定义与装配

- 修订：rev 20，2026-09-29 · [变更历史](design.md)
- 状态：能力绑定四条规则及 Skill、Tool、MCP 的统一适用范围由产品负责人直接裁定；其余接受范围及显式缺口见 [README](README.md#状态)，不据此扩大规格或实现状态。

> **本 topic 拥有的是数据，不是活物。**一次装配求值出来的那份构成叫[装配清单](#装配清单)，
> 它是数据；**照它跑起来的那个协程**叫
> [agent runtime](../PF-012-agent-loop-and-run/design.md#agent-runtime)，**归 PF-012**。
> 两者的分界见 [现行词义](../../ubiquitous_language/index.md)。

## 一、背景与问题

[PF-002](../PF-002-assets-settings-and-permissions/design.md) 把 Agent Definition
定成一类资产——**静态定义**，[PF-003](../PF-003-asset-transfer-and-sharing/design.md)
说清了它怎么跨组织流动。但**一份定义怎么变成一个真正在跑的 agent**，此前没有任何一处拥有。

缺的不是一个环节，是一个**对象**。看看这些问题今天为什么答不出来：

- **「这个 agent 现在能做什么」**——「现在」指的是哪个东西？定义是长期不变的，
  而能做什么每时每刻都可能不同。问题问的是**当下那份构成**，而那份构成没有名字。
- **改一项权限，要不要把 agent 重启一下？**改一个工具呢？换个模型呢？
  这三件事对一个正在干活的 agent 各自意味着什么，此前混作一谈。
- **「当时那个 agent 到底是什么样」**——装了哪些工具、用的哪份提示词、哪个模型？
  没有对象承载这个事实，事后就永远复现不出来。
- **成本算谁的？**照着一份构成跑出来的花销没有归属，账单明细就无从谈起。

场景是**一个 agent 在一个会话里连续多轮运行**。这个场景里有一件正在发生、
却无法解释的事：**中间推进它的那个东西可能被取消过、重起过很多次，而用户完全无感。**

这是对的行为——**定义是数据，构成是算出来的数据，而真正在跑的那个是计算资源，
闲着就该释放**。但产品上如果没有「那份构成」这个对象，
「重起一个照样接着干」这件事就既说不清、也管不住。

**本 topic 拥有那份构成**：它怎么被算出来、由什么组成、什么是外面注入的、
变化怎么影响它、它什么时候失效。

> **本 topic 不拥有「真正在跑的那个」。**那是
> [agent runtime](../PF-012-agent-loop-and-run/design.md#agent-runtime)，一个协程，
> 归 [PF-012](../PF-012-agent-loop-and-run/README.md)。
> **把它和清单当成同一个对象，那个对象就会一半是不可变的数据、
> 一半是「占用即消耗的计算资源」**——[现行词义](../../ubiquitous_language/index.md)。

会话怎么管、输入怎么进来、一次运行怎么被驱动，都不在这里（见 §2）。

## 二、目标与非目标

### 目标

1. **定义装配与装配清单**，以及围绕它们的全部对象：动作空间、注入、执行环境的类别。
2. **定死三个时刻**：装配时确定什么、注入变化时改什么、请求时才算什么。
3. **给出不变式**：不论中间发生过什么，关于**定义与装配**哪些事必须始终成立。
4. **说清变化怎么传播**：改了某样东西，对正在跑的那个和下一次各意味着什么。
5. **逐个组成部分**说清它们各自的定义与装配——模型、系统提示词、工具、
   技能、插件、Slash Command、执行环境、上下文。

### 非目标

**本 topic 只管「算出一份构成」，不管照它跑起来之后的事。**
下面几样是最容易被顺手拉进来的：

| 不做什么 | 为什么 |
|---|---|
| **[agent runtime](../PF-012-agent-loop-and-run/design.md#agent-runtime)** | **照清单起的那个协程怎么起、怎么被取消、取消怎么传播**——全归 [PF-012](../PF-012-agent-loop-and-run/README.md) |
| **会话** | 会话是什么、怎么建、怎么管、历史怎么存——那是一个长期物件的事。本 topic 只用到它的一件事：**一次装配为一个会话而做** |
| **输入怎么进来** | 消息怎么受理、怎么排队、怎么调序、什么时候取一批——都不在这里 |
| **一次运行怎么被驱动** | 谁决定现在该跑一轮、怎么推进、怎么收束。本 topic 只用到一件事：**Run 照一份装配清单跑** |
| 单次工具调用的观察、中断与后台接续 | 它有自己的生命周期，且[能跨 agent runtime 存活](../PF-006-tools-and-skills/design.md)。本 topic 只定它**怎么被装进来**、**算不算在动作空间里** |
| 子 agent 的委派、监督与关系 | 一个会话里出现多份装配清单是那件事的结果，不是本 topic 的对象 |
| 待决项的统一呈现与作答 | 那是跨会话的事。**「等人的时候那个协程怎么办」也归 PF-012** |
| 模型怎么供给、怎么路由 | 归 [SYS-LLM](../../../../docs/requirements.md#模型接入sys-llm)。本 topic 只定**模型在哪一刻被确定** |
| 崩溃后恢复到哪个合法位置 | 判据归 [SYS-RUNTIME-CONTINUITY](../../../../docs/requirements.md#运行时解耦与接续sys-runtime-continuity)。本 topic 定的是**正常的装配与失效**，不是故障恢复 |
| 具体有哪些上下文项、哪些执行环境 | 本 topic 定它们**以什么方式进入**——上下文靠注入，执行环境靠装配留下的那两样——**不枚举内容** |

## 三、用户与场景

| 使用者 | 什么情况下接触这块 | 他关心什么 |
|---|---|---|
| **在会话里连续协作的人** | 每天的正常使用 | 我接着上次说，它还是刚才那个它吗？ |
| **组织管理员** | 改权限、换掉某个组件、禁用某个工具 | 我这一改，正在干活的人会被打断吗？什么时候生效？ |
| **对成本负责的人** | 看账单 | 是什么在花钱？等我回话的那半天算不算钱？ |
| **排障的人** | 出了问题回溯 | 当时那个 agent 到底装的是什么、用的哪个模型？ |
| **agent 自己** | 每一轮运行 | 我现在能做什么？外面的情况变了我怎么知道？ |

**最后一行是这块设计的直接消费者，不是被管理的对象。**
本 topic 的多条规则是为了让 agent 能回答「我现在处在什么情形下」——
它答不上来，上面四种人的问题也就都答不上来。

本 topic 把 SYS-COMPOSITION 的三段结构，落到 agent 这件具体的事上，
并给每一段起一个产品上的名字。

### 三个只引用、不拥有的对象

本 topic 无法绕开这三样东西，但**只用到它们各自的一件事**。
它们的定义、管理与驱动都不在这里。

| 对象 | 本 topic 用到的唯一一件事 | 本 topic **不**说它 |
|---|---|---|
| **会话** | **一次装配为一个会话而做**，并从它取得定义版本与适用会话类型的必需能力要求 | 会话怎么建、怎么命名归档、历史怎么存、输入怎么进来 |
| **Run**（一次运行） | **Run 照着一份装配清单跑** | 谁决定现在该跑、怎么推进、怎么收束、怎么中断 |
| **[agent runtime](../PF-012-agent-loop-and-run/design.md#agent-runtime)** | **它照着装配清单起**，是**唯一会「跑」的那个东西** | 它怎么被起、怎么被取消、取消怎么传播——**全归 [PF-012](../PF-012-agent-loop-and-run/README.md)** |

**写下这三行是为了防一件事**：**把装配清单当成一个活物**。
四者层次分明——

> **会话是长期的数据，装配清单是求值出来的数据，一次运行是逻辑边界，
> 只有 agent runtime 是活的。**

**这一层没有任何东西会「停下来」**：装配是个动作，清单是个结果，
两者都不占用计算资源。**要停的东西在 PF-012。**

### agent 类型

**一份 [Agent Definition](../PF-002-assets-settings-and-permissions/design.md#八类资产) 具不具备 master agent 的那一整套机制。**

**只有两个取值，没有第三个：**

| agent 类型 | 它是什么 |
|---|---|
| **master** | **具备全套机制**。用户挑的就是它，[会话由它开起来](../PF-015-session-lifecycle-and-ownership/design.md#53-会话类型怎么算出来) |
| **non-master** | **不具备 master 的那一整套机制**的 agent |

**`non-master` 是由 `master` 反过来定义的**，这是有意的：
**这条线划的是「有没有那套机制」，不是「它在某次派发里扮演什么角色」。**

**这是定义自身的属性，不是它某次装配的结果。**
同一份定义，在哪个作用域下装配、装出什么清单，**都不改变它是哪一类**。

> 当前明确的差异是[用户以 master 开主会话](../PF-015-session-lifecycle-and-ownership/design.md#会话的生命周期)、
> [master 带类目](#master-类目)、[master 只能官方提供](#68-两类-agent谁能被谁自定义)。
> 其他差异须有具体产品条款；「全套机制」不授权推断 non-master 缺少任意能力，也不要求先穷举未来机制。`spawn`／`delegate` 可选择 master 或 non-master；`handoff` 选择 master。定义类型不决定父子关系：用 master 派出的仍是子会话，不自动成为独立主会话。定义可用范围、派发权限和 official 不可替换规则照常适用。

### master 类目

**一份 master agent 的定义，主要是用来干什么的。**

**它只挂在 master 上**——`non-master` 没有这项属性，因为它不开协作，
「这段协作是干什么的」对它无意义。

当前五类：`general-purpose` · `coding` · `office` · `research` · `personal-life`。

**这五类只能由产品出厂增补，租户不能自定义**，理由在 [§7](#七取舍)。
[会话类型由它算出来](../PF-015-session-lifecycle-and-ownership/design.md#53-会话类型怎么算出来)——
**算，不是拷贝**，那条映射归 PF-015。

### 装配

**按会话类型的能力要求、Agent Definition 与作用域输入，求值出一份[装配清单](#装配清单)的动作。**

装配要回答：这一次**装哪些工具、带哪些技能、需要哪几类执行环境、
装进来哪些[沙箱实现](../PF-005-execution-environments-and-sandboxes/design.md#沙箱实现)、
系统提示词按什么规则组合**。

装配**有确定的发生时刻**，不是一个持续的过程。输入包括**会话类型要求的能力**、
**依据的定义版本及其能力声明**，以及**当时该作用域的资产与配值求值输入**。
Agent Definition 是输入之一；作用域提供资产候选，不意味着所有候选都进入这个 agent。
资产资格与同标识实现的求值规则归 PF-002；三类资产如何被选入及哪些必须绑定，归 [§6.2](#62-装配)。

> **会话挂了[工作区](../PF-002-assets-settings-and-permissions/design.md#工作区)的，那一级也在这份求值结果里**：
> 承载它的目录下那些特定命名的文件，**在装配这一刻被自动解析**，读出来的资产与配值作为工作区那一级参与求值
> （[PF-002 §4](../PF-002-assets-settings-and-permissions/design.md#挂上之后它的内容在装配时自动进来)）；
> **权限项照旧被滤掉**。会话[创建时没指定工作区](../PF-002-assets-settings-and-permissions/design.md#它是会话选用的不指定就是空)的，
> 这一级为空，**装配不会去找任何目录**。哪些文件、什么格式，PF-002 列为本版非目标，本 topic 同样不定。

> **它对应 [SYS-COMPOSITION 三段结构](../../../../docs/requirements.md#定义装配与活体sys-composition)
> 的第二段「装配」，那一段明写它是「一次求值」。**
> **第三段「活体」不在本 topic**——它是 [agent runtime](../PF-012-agent-loop-and-run/design.md#agent-runtime)，
> 归 PF-012。**求值的结果是数据，不是活体**；
> [现行词义](../../ubiquitous_language/index.md)。

### 能力自动继承

沿 [Capability Auto-Inheritance](../../ubiquitous_language/terms/capabilities-and-composition.md#ul-capability-auto-inheritance--能力自动继承--capability-auto-inheritance)。
Agent Definition 可以声明是否自动继承额外的 **Skill、Tool、MCP**，开启时声明开放到哪一层，并可显式排除特定继承项。**开关默认值为 `false`**；未声明时不自动继承额外能力。

**继承声明跟着 Agent Definition 本身走**，不是组织、租户、工作区各自为同一份定义配值的设置。
允许更具体层以同能力标识的自定义 Agent Definition 替换可替换的上级自定义定义；装配采用生效定义自己的整份继承声明，不把被替换定义的开关、范围、排除项逐项合并。
替换定义未写继承声明时，仍按默认 `false`；上级曾开启不使新定义自动开启。定义替换受 [§6.8](#68-两类-agent谁能被谁自定义) 的类型限制、official 不可替换及 PF-002 的上级锁定约束。

| 声明 | 自动继承涉及的来源 |
|---|---|
| 关闭 | 不自动继承额外能力；会话类型与定义显式要求的能力仍必须绑定 |
| 开放到组织 | 组织 |
| 开放到租户 | 租户、组织 |
| 开放到工作区 | 工作区、租户、组织 |

**左侧层包含右侧层：工作区 → 租户 → 组织。**这个范围决定自动选入哪些能力标识，**不限制这些能力由哪一层提供具体实现**。
能力一旦被选入，其实现继续在当前完整作用域内按 PF-002 的资格过滤、同标识覆盖与锁定规则解析。
例如，只继承组织能力时，组织提供的某个能力可以绑定租户或工作区的同标识实现；
租户或工作区新增的另一个能力标识则不会因此被自动继承。
**允许解析同标识替换，不等于允许覆盖已经锁定的实现。**
[PF-002 §5.5](../PF-002-assets-settings-and-permissions/design.md#55-资产替换的层级)的规则仍成立：
meta 能力任何层都替换不了；组织或租户在自己的资产持有上标 `immutable`，更具体层就不能替换该份实现，持有的是 official 资产也一样。
工作区不能设置 `immutable`，也不能越过上层已锁定的替换边界；自动继承及 reload 都不解除这些约束。
会话未选用工作区时，工作区来源为空，不因此虚构工作区或跨到其他租户取资产。
组织来源沿既有组织资产求值规则，不由这项声明新增组织间继承。

**排除项仅从自动继承部分扣除**，按既有能力标识（类别 ＋ name）指认；同名的 Skill 与 Tool 不是同一项。
排除的是能力标识，不是某一份实现；换同标识实现不能绕过继承排除。
MCP 的选择与排除针对接入点资产，它带来的动作仍按 MCP 的既有规则处理。
本声明不改变资产的持有、共享与执行权限，也不自动扩展到其余五类资产。

### 装配清单

**一次装配求值出来的那份构成。**

它是一个**对象**，不是过程的副产品。理由只有一条：
**「当时那个 agent 是什么样」这个问题，答案只能在这里。**
没有它，出了问题谁也说不清、事后谁也复现不了。

**它是数据**：不占用计算资源，不会「停下来」，也**不必每次重新求值**——
同一份清单**可以跨多次[执行尝试](../PF-012-agent-loop-and-run/design.md#执行尝试)复用**。

| 属性 | 业务含义 | 取值与约束 | 何时确定 |
|---|---|---|---|
| 为哪个会话求的 | 它是为哪一段协作算出来的 | 恰好一个会话 | 装配时，此后不变 |
| 依据的定义版本 | 它是照哪一份图纸算的 | Agent Definition 的一个**已发布版本** | 装配时，此后不变 |
| 实际构成 | 当次采用的定义、Loop／extensions、提示词组合规则、能力访问关系与能力选入依据；能力的当前数据和实现另由会话记录 | 见[动作空间](#动作空间)与 [§6.2](#62-装配) | 装配时产生，**只可追加** |
| 成本归属 | 照它跑出来的花销算谁的 | 启动它的那个租户 | 装配时 |

装配清单**只可追加，不可改写**，保存采用历史。会话能力的当前数据、实现选择与可用性独立变化；每次请求另记实际输入。更新当前采用值不改写清单旧条目，也不意味着 Agent runtime 必须重建。

> 清单记“当时采用什么”；资产是否仍被持有归资产治理，会话是否曾合法见过该能力归会话已知记录。资产被移除不抹掉后两者。

### 动作空间

**本会话的 agent 能识别并尝试发起哪些动作的集合。**它由会话已合法纳入的能力投影得到，与“目前能成功执行哪些动作”分开。

**能力身份的可见性在同一 Session 内单调增加。**一旦合法纳入，后续每个 Agent runtime 都能识别该身份；定义排除、会话移除、资产禁用／卸载、使用资格撤销或依赖失效，将该条目转为不可用并呈现替换件，不删除已知身份。新 Run、重装配、休眠恢复不清空这份会话记录。

| 变化 | 已知身份 | 当前可用性 |
|---|---|---|
| 合法新增能力 | 增加 | 按当前条件求值 |
| 定义不再选入、会话移除可选项、资产禁用／卸载 | 保留 | 生效后不可用，说明原因 |
| 实现或依赖恢复 | 保留 | 当前选择、治理及依赖条件都成立才恢复 |
| 执行权限收紧 | 保留 | 每次动作仍遵守其准入，不能凭历史许可执行 |
| 同身份的数据或实现更新 | 保留 | 按合法采用结果与兼容性求值 |

移除／禁用某一份实现来源时，先沿 PF-002 解析同标识的其他合法候选；仍有合法实现则更新绑定，没有合法候选才转为替换件。定义排除或会话移除的是能力身份，不能借换来源绕过。以下“能力卸载／不可用”指这一步求值后的结果。

单调性限定为能力**身份**，不冻结 schema、说明、Skill 正文或实现；不要求每轮提示词列出全部已知能力。常驻／发现／按需读取仍沿 PF-006、PF-007。尚未合法纳入的能力继续受继承范围、排除、租户与资产资格限制；历史条目不泄露未获准的新定义内容或实现信息。人的 Slash Command 入口不适用这一单调性。

### 注入

**一样东西不是 agent runtime 自带的，而是外面给它的；给的内容变了，agent runtime 也不用重起。**

这是本 topic 的核心机制。**上下文与权限都是注入的。**

> **[执行环境](#执行环境)不在其列**——它不是一个被注入的取值，
> 而是**每扇门每次执行按权限与已装配的沙箱实现算出来的落点**。
> **它与注入共享同一条性质**（变了不必重新装配、不必重建 agent runtime），
> **但来路不同**：一个是外面给的值，一个是算出来的结果。

注入与构成的分界，判据是一句话：

> **这个变化改变的是「它是什么」，还是「它处在什么情况下」？**

前者须进一步区分是 runtime 自身捕获的组成，还是会话能力的数据与实现。只有前一类替换要求交接实例；会话固定的 agent 身份不变；
后者是注入，它还是它，只是周围不同了。

### 运行期上下文

[PF-001 定义了 Context](../PF-001-identity-scope-and-agent-constraints/design.md#contextagent-运行时可感知的上下文信息)——
agent 运行时可感知的上下文信息，并给出协作范围与个人两种。本 topic **不改写它**，
只补 PF-001 没有覆盖的一类：**运行期才产生的上下文**——外部环境变了、
权限被调整了。

**某样能力此刻用不了，不在此列。**那是[当下可用性](../../ubiquitous_language/terms/reach-and-availability.md#ul-current-availability--当下可用性--current-availability)，
[每一次执行尝试开始时重算，不另外告知 agent](../PF-012-agent-loop-and-run/design.md#每一次尝试开始都要做四件事)：
它调到一样已经用不了的能力，[替换件](../PF-006-tools-and-skills/design.md#替换件)会在原位给它「用不了 + 原因」。
再补一条提醒，同一件事就说了两遍。

它们与 PF-001 的两种同样是「agent 能感知到的、关于我现在处在什么情形下的信息」，
同样**通过注入到达**，因此归在一处，不另立概念。到达方式见 §6.4。

### 执行环境

**动作实际落到哪里。**宿主机、沙箱，或别的什么。

**装配时确定的只有两样**：这份构成**需要哪几类**环境（由装进来的工具声明决定），
以及**装配方要不要装配[沙箱实现](../PF-005-execution-environments-and-sandboxes/design.md#沙箱实现)、装哪一个**——
[沙箱实现是装配时可选装配的，宿主机则始终在场](../PF-005-execution-environments-and-sandboxes/design.md#61-宿主机始终在场沙箱实现装配时可选装配)。

**这次执行落在哪一个，不在装配时定，也不是一个被注入的取值**：

> **每扇门、每一次执行各算一个落点**——
> 按[那扇门的执行环境权限](../PF-005-execution-environments-and-sandboxes/design.md#执行环境权限)、这次要用的设施、
> 以及已装配的沙箱实现各自声明的（设施 × 可绑定层级）算出来。

这带来一条很实在的性质：

> 一条 shell 命令，执行在宿主机还是沙箱里，**agent 都能执行**。

工具定义说的是「执行一条命令」，从不说「在哪执行」。
正因如此，**落点变了不必重新装配、不必重建 agent runtime，动作空间也不变**——
[变的是算出来的那个值，不是这个 agent 由什么构成](#61-不变式)。

**它有哪几种、落点怎么算、各自的存活期与隔离性，归 [PF-005](../PF-005-execution-environments-and-sandboxes/design.md)。**
本 topic 只定**装配这一头给它留下什么**：需要哪几类，以及装配方装进来哪些沙箱实现。

有一点先说清，免得与 PF-005 读成冲突：

> **执行环境的存活与 agent runtime 无关。**它可能比 agent runtime 短得多（一次工具调用就结束），
> 也可能长得多（绑定在租户）。**本 topic 不对它的寿命作任何断言。**

## 五、模型

### 5.1 一张图，三个对象各在其位

```text
   Agent Definition ─────┐
     （数据，长期）       │
                          ├──装配──→ 装配清单 ──照它起──→ agent runtime
   作用域（当时可用的     │          （数据，求值结果，      （协程，PF-012）
    实现、设置、权限）────┘           可跨尝试复用）              ↑
                                          ↑                        │
   会话 ──────────────────────────────────┘                        │
    （长期数据，本 topic 不拥有）  为它求值 + 提供定义版本与类型要求│
                                                                    │
                                  注入：上下文 · 权限 ─────────────┘
                                （可变，清单不因此重算、协程不因此重起；
                                  执行环境的落点每次执行按它们现算）
```

**图里最右边那一格本 topic 不拥有**，会话怎么来也不拥有。
画它们，只为说清**装配清单的两个接口：为谁求值，以及照它起什么**。

三件事值得单独说：

- **装配清单不是一个活物。**它是一份算出来的构成，**不会「停下来」，也不占用计算资源**。
  会停的是右边那一格，归 [PF-012](../PF-012-agent-loop-and-run/README.md)。
- **一份清单可以被好几个协程先后照着起。**重试、恢复，各起一个新协程，
  **不必重新求值**——同一个会话的两轮运行用户无感，靠的是这个。
- **注入是从旁边进来的，不在装配链上。**这条线是本模型最要紧的部分，见 §5.3。

### 5.2 三段结构是递归的

三段不只作用于 agent 整体。**每个组成部分各有一份**，它们的装配合起来，
才构成 agent 那一次装配。

| 组成部分 | **定义**（数据） | **装配时确定** | **每次请求时产生** |
|---|---|---|---|
| **模型** | 模型标识与能力声明：窗口、模态、是否支持工具调用 | ——（例外，见下） | **这一次用哪个模型**，以及这一次的调用 |
| **系统提示词** | 作者写的正文，以及各来源可贡献的片段 | **组合规则与定义正文** | **当前能力描述及组装出的文本** |
| **工具** | 调用形状、参数、权限项、设置项 | 纳入会话能力记录；提供动态访问入口 | 以相互匹配的定义数据、实现、参数及环境发起一次工具调用 |
| **技能** | 指引正文 + 资源 | 纳入会话已知技能集，当前可用性另算；[常驻](../PF-006-tools-and-skills/design.md#常驻)时 name + 说明进系统提示词，否则经 `Skills()` 发现；正文按需取 | —— |
| **插件** | 打包在一起的若干资产 | **展开**为内含成员，各自参与装配 | —— |
| **Slash Command** | 命令名、参数、绑定的技能 | 进入可用命令集 | 一次命令执行 |
| **执行环境** | 工具声明它需要什么样的环境 | **需要哪几类环境**（由装进来的工具决定），以及**装配方可选装配哪些[沙箱实现](../PF-005-execution-environments-and-sandboxes/design.md#沙箱实现)** | ——（见表下说明） |
| **上下文** | ——（不是被装配的对象） | ——（注入） | 这一次的上下文视图 |
| **（整体）** | Agent Definition | **装配清单** | 一次模型请求 |

**执行环境那一行要与 [PF-005](../PF-005-execution-environments-and-sandboxes/design.md) 一起读。**装配时确定的是
**需要哪几类**环境（由装进来的工具决定）与**装配方装进来哪些沙箱实现**，两样都属于构成；
而**这次执行实际落到哪一个**[每扇门每次执行现算](../PF-005-execution-environments-and-sandboxes/design.md#61-宿主机始终在场沙箱实现装配时可选装配)，
**清单不必重算**。

它的第三列写「——」，**不是说执行环境没有实例**，而是这张表的第三列问的是
「每次**模型请求**时产生什么」，而执行环境的实例化粒度是**工具调用**——
一次模型请求可能带来多次工具调用。各类环境各自活多久，归 PF-005。

**模型选择与能力的逐次采用均不冻结整个 Agent runtime 存活期。**模型不在装配时绑定。
理由见 §6.6——同一个会话的不同轮允许换模型，若在装配时绑死，
换模型就得重新装配，而那本该是轻的。

### 5.3 三个时刻

| 时刻 | 确定什么 | 变化与留痕 |
|---|---|---|
| Agent runtime 装配 | 固定身份、采用的 AgentDefinition、Loop／extensions、提示词组合规则、会话服务访问关系 | 自身捕获组成改变时形成新清单；普通恢复不偷偷升级 |
| 会话采用动态输入 | 合法纳入能力身份、当前定义数据与实现选择、模式、context、可用性 | 按来源原有生效点更新会话值与采用事实，不要求重建 Agent runtime |
| 模型／工具调用或 Skill 读取 | 当前实际使用的数据、实现、模型、参数、授权、环境与上下文 | 固定当次输入；后续变化不改写已经发起的工作 |

“必需能力”表示必须保留该能力位置，不等于 Agent runtime 直接依赖每个具体实现的生命周期。哪个活体实际消费哪个服务，见 §6.12。

### 5.4 为什么系统提示词必须落在第三列

系统提示词在每次模型请求时组装。装配确定作者正文及组合规则；会话能力入口提供当前允许呈现的描述、schema、常驻标记和替换件说明。常驻能力的数据变化、Skill 说明变化乃至 argsSchema 变化，都可以使下一份提示词或 tools 声明不同，而不替换组合规则或 Agent runtime。

因此必须区分**组合规则／提供入口**与**入口给出的本次数据**。“提示词有变化”不是重建判据。某次请求已经发出，就保留原文本、工具声明及来源依据；不能用新数据改写历史请求。

## 六、产品规则

### 6.1 不变式

不论中间发生过什么，以下关于**定义与装配**的事必须始终成立。

| # | 不变式 | 不成立会怎样 |
|---|---|---|
| **I-3** | 会话的定义身份固定；普通恢复不偷换已采用版本。**显式 reload 可在同一 Run 的安全交接点采用同身份新版本，开启新尝试**，历史清单和调用输入不改写 | 恢复时静默升级，或无法解释每次执行采用了哪一版 |
| **I-4** | 同一 Session 已知能力身份单调增加；当前可执行集合可缩小。重装配、定义更新及撤权不能删除已经合法见过的身份（[§6.5](#65-权限变化动作空间不变)） | 收紧权限会让 agent 突然「不知道某件事存在」，无法解释也无法申诉 |
| **I-5** | 每一次模型请求都有**可追溯的实际组成** | 出了问题答不出当时装的是什么 |
| **I-8** | 照一份装配清单跑出来的成本，**归属到启动它的那个租户** | 成本没有归属，账单明细无从谈起 |
| **I-9** | 装配缺少必需的东西时**明确失败**，**不产生残缺的装配清单** | 一个缺零件的 agent 跑起来，它自己不知道缺什么，用户也不知道 |

**编号里缺的四条，主语是 [agent runtime](../PF-012-agent-loop-and-run/design.md#agent-runtime)，所以它们归
[PF-012](../PF-012-agent-loop-and-run/design.md#agent-runtime-的四条不变式)。**
**编号沿用这里的一套**，既有引用因此不会指错；**正文在那边，这里不留第二份**：

| # | 它现在说什么 | 正文在哪 |
|---|---|---|
| **I-1** | 一个会话在任一时刻至多有一个活跃的 **agent runtime** | [PF-012 §6.1](../PF-012-agent-loop-and-run/design.md#agent-runtime-的四条不变式) |
| **I-2** | **agent runtime 的起灭**对协作中的用户不可见 | 同上 |
| **I-6** | agent runtime 被取消，**不产生用户可感知的损失** | 同上 |
| **I-7** | **等人回话的时间不消耗计算资源** | 同上 |

**为什么它们不能留在这里**：这四条说的全是**一个活物的生灭**，
而[本 topic 这一层没有活物](#三个只引用不拥有的对象)——装配是动作，清单是数据。
**把关于协程的不变式挂在一份数据上，那份数据就会被当成活物。**

### 6.2 装配

会话创建时固定 AgentDefinition 的身份，不固定其内容版本。每个新 Run 开始前，按这个身份取得最新已发布且有效的内容；变化后重新装配，未变化且清单仍有效才可复用。同一 Run 的普通恢复使用当前已生效清单；显式 reload 可以在安全交接点采用同身份新版本并开启新尝试（I-3），交接归 PF-012。工作区来源仍须经实际装配或显式 reload 校验；“最新”不是未经装载的文件内容。工作区切换不能更换定义身份，同身份来源替换仍受 official 与上级不可覆盖规则约束。

定义热重载可修改其显式依赖、自动继承开关、范围与排除项，后续装配按新内容求值；会话执行类型要求的必需能力身份集合保持。Skill、Tool、MCP 的当前可用集合可以增删，同身份可更新数据或实现；会话已知身份保留。会话移除只使允许移除的可选项不可用，不能绕过当前必需要求或能力选择边界。

会话的创建输入、作用域与持久化矩阵归 [PF-015 §6.16–6.19](../PF-015-session-lifecycle-and-ownership/design.md#616-会话组成与创建输入)。装配清单须能指回当次采用的定义及求值依据；能力的当前定义与实现另有会话采用记录，每次执行保留实际输入，不由清单冻结整个运行期的能力实现。各次 runtime 装配所需的恢复输入由该矩阵收齐；Agent runtime 的完整输入与变化矩阵见 §6.9–6.10，具体接口归技术设计。

- **装配产出一份只可追加的装配清单**，它是一次求值的结果。
- 输入包括**会话类型的能力要求**、**依据的定义版本及其能力声明**、**当时该作用域的求值输入**。
  会话挂了工作区的，**工作区那一级的内容在这一步自动解析进来**；没挂的，这一级为空
  （[§4 装配](#装配)）。
- **装配失败就是失败**（I-9）：从未取得必需能力的有效定义、runtime 自身必需资源拿不到，
  明确失败并说明缺什么。
- **装配不等于起一个 agent runtime。**清单算出来之后，
  照它起协程是[另一个动作](../PF-012-agent-loop-and-run/design.md#agent-runtime)，
  **可以起很多次**（每次[执行尝试](../PF-012-agent-loop-and-run/design.md#执行尝试)一次），
  **也可以一次都不起**（算完了但这次运行被取消）。

#### Skill、Tool、MCP 的绑定规则

**三类资产统一适用以下四条规则，初始装配与重新装配都一样。**

| 顺序 | 来源 | 绑定规则 |
|---|---|---|
| 1 | **会话类型要求的能力** | **最高优先级、强制绑定，是必须依赖。**定义不能省掉，继承关闭或排除项也不能去掉 |
| 2 | **Agent Definition 显式声明需要的 Skill、Tool、MCP** | **必须依赖，装配时必须带着。**不受自动继承的开关、范围或排除项影响 |
| 3 | **能力自动继承** | 开启时，按定义声明的层级范围选择额外可用的 Skill、Tool、MCP 能力标识；所选能力的具体实现另按完整作用域解析 |
| 4 | **定义显式排除的继承项** | 只从第 3 项中排除；不能取消第 1、2 项的必须依赖 |

因此，当前允许选入的三类能力可以表达为；已知身份则取历次合法纳入结果的并集：

```text
选入的能力标识 = 会话类型要求 ∪ 定义显式要求 ∪（所声明范围内的自动继承项 − 继承排除项 − 本会话移除的可选项）
具体实现 = 对每个当前允许的能力标识，按完整作用域的既有资产规则解析
会话已知身份 = 历次合法纳入的能力身份之并集；当前不再允许的已知条目使用替换件
```

本会话对可选项的移除声明作为会话级设置持久保留，重新装配仍参与上述求值，不因重算自动装回来。重新添加一个仍在当前声明允许范围内的可选项，撤销本会话对应的移除；新增可用资产也必须先进入当前定义允许的来源范围。会话装卸不新增一条绕过定义声明的能力入口。

必需项不接受会话移除。若定义热重载把此前被本会话移除的可选项改为显式必需，必需绑定优先，本会话移除声明不能使它缺席；装配结果应说明其必需来源。继承关闭、范围缩小或上级撤权时，会话添加意图也不能保住不再允许的可选项。

关闭自动继承时，最后一项为空。相同能力标识由多条来路选中时不重复绑定；
其中任何一条是必需来路，该能力就按必需处理。**排除继承不会反向删除显式声明。**
定义引用的组合仍按 PF-002 展开；这四条不为 Plugin、Connector、Slash Command、Loop Extension 或其他 Agent Definition 增加自动继承规则。

**通用的会话要求包括 meta tools，特殊执行类型还可有自己的必须依赖。**
[PF-007 的 meta](../PF-007-meta-capabilities/design.md#meta) 始终在场；
[PF-021 的作业会话](../PF-021-schedule-and-calendar/design.md#作业会话) 无论选哪份定义，都必须带有向当前 Job 提交成果的工具。
这里的类型要求也包含作业会话这种执行子类型，不限于 PF-015 的用途分类。
各类型具体要求哪些能力由相应产品正文拥有，本节只拥有共同的绑定顺序。

**必须依赖约束的是装配能否成立，不是每次调用必定成功。**
从未取得必需能力的合法定义，或无法建立 runtime 自身的必需依赖时，沿 I-9 明确失败；已有合法定义而实际执行实现不可用时，能力位置由替换件保留，不因此拒绝启动 Loop；
绑定优先级不授予执行权限，不绕过租户隔离，也不保证 MCP 对端永远在线。
已绑定能力的运行期不可用与调用放行继续沿 PF-006、PF-007；常驻与按需呈现仍由 PF-006 管，必需 Skill 不因此自动全文注入提示词。

#### 热重载沿用相同的选择边界

对 Skill、Tool、MCP 的显式 reload 重新选择候选时，仍按上述来源范围与排除规则求值，
并保留会话类型与定义显式要求的必需绑定。关闭继承不会禁止更新已选中的能力，
开启继承也不意味着文件一变就自动装载；来源读取、校验后替换及运行捕获仍沿 §6.3。
重载候选缺少必需能力的合法定义或 runtime 自身必要条件时，校验失败，旧数据尚未替换。已有能力实际实现不可用则按替换件处理，不伪造从未见过的定义。
更新已经在定义中的能力，与从环境自动增加额外能力，是两件不同的事。

### 6.3 三类变化，三种传播

工作区文件修改、Git 同步不自行触发加载。只有实际装配或显式 reload 才读取该来源；先校验候选，通过后才采用，失败不替换原数据。来源读取规则和更新传播是两件事。

| 变化层次 | 示例 | 对 Agent runtime 的影响 |
|---|---|---|
| 自身捕获的组成 | 采用新 AgentDefinition 版本、替换 Loop 或已捕获 extension、替换自身必需服务提供者 | 沿 §6.10 核对，必要时新清单与实例交接 |
| 会话能力与动态输入 | Tool 实现版本、Skill 正文、MCP 动作列表、argsSchema、常驻描述、可用性、context、模式值 | 更新合法采用的数据／实现与访问结果；不由这些变化本身触发 Agent runtime 重建 |
| 单次使用输入 | 模型选择、工具参数、环境、请求工具声明、Skill 读取内容 | 逐次确定并留痕；已经发起的工作保留原输入 |

运行中新增能力沿现有声明范围合法纳入会话，追加记录即可。已知能力不再被定义选入、被禁用或卸载时保留替换件；重新可用须同时满足当前选择、治理和依赖条件。

AgentDefinition 的采用版本仍是每个 Agent runtime 的装配输入：新 Run 取同身份最新有效版本；显式 reload 可在当前 Run 安全交接后采用新版本并开启新尝试。这是 AgentDefinition 的既定采用边界，不推导为所有资产数据更新都要换实例。未变化的 AgentDefinition 仅引用了发生更新的 Tool／Skill／MCP，不算 AgentDefinition 版本变化。

#### 三类变化背后只有一条判据？系统提示词的「成分」会不会变

必须检查的是**变化落在谁自身捕获的组成上**。提示词文本、工具 schema、常驻列表等请求数据变化不能单独推出重建。提供这些数据的入口可以保持，入口内的数据和实现选择可以变化。

能力的定义数据、执行实现与承载它们的服务相互独立：换数据不一定换实现，换实现不一定换服务；服务真的替换时，只影响其实际消费者及依赖传播范围，不直接推出整个会话或 Agent runtime 都重装配。实际直接依赖与所有权须由技术设计表达并验证，不能把每个被调用的工具都当成 Loop 的生命周期依赖。

### 6.4 上下文变化怎样到达 agent

这里只处理注入给会话的上下文数据发生变化。工作区本地或 remote 的资源变化沿 [PF-020 的异步感知规则](../PF-020-workspace/design.md#会话视角下的本地与-remote)，可由用户告知或 agent 按需读取、同步，不承诺自动监测、即时推送或刷新装配。组织的工作区参与限制仅在实际装配时判定，不因运行期上下文变化而热同步重判。

**以事件驱动的方式，在下一次运行里作为一条提醒出现。**
（这里的「上下文变化」是 [§4 运行期上下文](#运行期上下文)那一类；能力可不可用不走这条路。）

这里面有三件事是定死的：

- **已注入的运行期上下文不要求 agent 自行轮询。**环境变了会告诉它，不需要它反复去问。
  **例外只有一处，而且它不是轮询**：[每一次执行尝试起来时取一次当前快照](../PF-012-agent-loop-and-run/design.md#每一次尝试开始都要做四件事)——
  **一次尝试一次，不是隔一会儿问一遍**。**它存在是因为[会话空闲时推来的变更一律被丢弃](../PF-014-inbound-intake-and-queueing/design.md#610-注入的上下文变了没有运行在跑时什么都不做)**。
- **变化不打断当前正在进行的运行。**它等下一轮才现身，与
  [PF-001 §6.6「撤销不等于强制停止」](../PF-001-identity-scope-and-agent-constraints/design.md#66-撤销不等于强制停止)同向。
- **它以上下文内容的形式到达**，而不是以「你的能力被改了」的形式。

最后一条是关键：agent 是**读到**变化，然后自己决定怎么调整，
而不是被系统在背后改写。**「agent 能动态感知外界变化、在运行中调整自己的行动轨迹」，
成立的根子就在这里。**

### 6.5 权限变化：动作空间不变

权限、资产资格和能力可见记录分别回答“准不准执行”“能否采用”“是否曾合法见过”。收紧权限不删除历史已知能力；保留身份也不授予执行权。

| 变化 | 从未合法纳入的能力 | 已知能力 |
|---|---|---|
| 资产移除、禁用、定义排除／范围缩小、会话移除可选项 | 不新增到会话 | 在相应变化生效后保留不可用替换件 |
| 「谁可以使用它」被收回 | 不能新增或读取未授权内容 | 保留已知身份及足以说明不能使用的原因，不提供被撤回的实现或新内容 |
| 执行权限收紧 | 不构成新增依据 | 每次动作遵守准入；已有放行的适用范围沿 PF-012，不自动取消已发调用 |
| 资产或实现重新装载 | 仍须符合当前选入和治理边界 | 只有当前仍允许且必要依赖成立才恢复可用 |

各变化沿原有生效时刻：治理来源默认下一 Run 采用，显式 reload 可提前采用；执行权限遵守下一道准入，真实依赖消失则按实际不可用处理。变化不因保留条目而延迟生效，也不因更新条目而必须重新启动 Agent runtime。人的斜杠命令入口仍按 PF-002 即时隐藏等既有规则，不把它当作模型的能力记忆。

### 6.6 模型在每次请求时确定

- 模型的**生效**在每次请求时解析；它不在装配时绑定。
- **换模型不重新装配**，也不改变动作空间。
- 每一条模型产出的内容，**记下实际生成它的模型**。事后回看不改成「当前选的那个」。

**模型的选择存在哪、怎么选、当前轮正在跑时提出切换怎么办**——
那是会话与驱动那一侧的事，不在本 topic。本 topic 只定一件事：
**模型是请求时才确定的，因此它的变化不触及 agent runtime。**

### 6.7 装配清单的生与失效

| 动作 | 什么时候 | 结果 |
|---|---|---|
| **装配** | 需要一份构成而当前没有有效的 | 求值，产出装配清单 |
| **复用** | 已核对定义等输入未变化，且已有一份仍然有效的清单 | **直接用，不重新求值**——照它起第几个协程都一样 |
| **追加** | [运行中增量装上一个可选能力](#63-三类变化三种传播) | 清单上**加一条**，既有条目不动 |
| **失效** | 它赖以成立的 runtime 自身组成变了：采用新 AgentDefinition、Loop／extensions 或直接必要服务绑定；不包含会话能力入口内部的数据、实现和可用性变化（见 [§6.3 的判据](#三类变化背后只有一条判据系统提示词的成分会不会变)） | 下一次需要时**重新求值**，得到一份新清单 |

**清单不会「被回收」，它只会失效。**它是数据，不占用计算资源，
**留着也不花钱**——[要不要留、留多久，是记录那一侧的事](../PF-000-occurrences-and-record-entries/README.md)。

> **「回收」「显式退役」这类动作不落在清单上**——那说的是**一个活物**怎么停，
> 归 [PF-012 §6.13](../PF-012-agent-loop-and-run/design.md#613-取消跟着宿主走)
> 与 [§6.14](../PF-012-agent-loop-and-run/design.md#614-停止有两级)。
> **「等人回话时可以被回收」（I-7）同理**——
> 那说的是协程可以被取消，而**清单本来就不必为等待付费**。

**谁来决定现在该装配**，是驱动那一侧的事；本 topic 只定
**这几个动作各自意味着什么、必须留下什么**。

### 6.8 两类 agent，谁能被谁自定义

| 规则 | 内容 |
|---|---|
| **R-1** | **[master](#agent-类型) 的定义，只能由产品官方提供**——它必定是 [official](../PF-001-identity-scope-and-agent-constraints/design.md#来源official-与-customized) |
| **R-2** | **组织、租户、工作区能自定义的，只有 [non-master](#agent-类型) 的定义** |
| **R-3** | **[master 类目](#master-类目)只能出厂增补**，组织、租户、工作区都加不了新的一类 |
| **R-4** | **official Agent Definition 是 `immutable` 的**，组织、租户、工作区都不能以同标识自定义定义替换它；不限于 official master |

**R-3 不是一条独立的限制，它是 R-1 的推论**：
类目是用来给 master 分类的，**既然 master 只能官方给，类目自然也只能官方加**。
**租户能不能自定义会话类型，等价于问租户能不能自定义 master**——而那个问题已经有答案了。

**自定义 non-master 定义之间可以按层级同标识替换，前提是上级未锁定替换。**继承声明随最终生效的定义；不以替换 non-master 为入口创建 master，也不以 non-master 的同名定义绕过 official 锁定。
定义不可替换不把其原有可配置设置一概改为不可配值；设置与权限仍按各自规则求值。定义引用的能力仍按自身的覆盖规则解析实现；定义的 `immutable` 不自动给这些能力的实现加锁。定义版本发布与已运行构成的传播继续沿既有生命周期。

> **这些约束规定定义的来源与替换边界，不直接规定装出来的 agent 能做什么。**
> 一个 `non-master` 照样可以装得很强；**能力由构成决定，与类型无关**（[I-4](#61-不变式)）。

### 6.9 Agent runtime 组成与装配输入矩阵

“必须输入”表示装配／启动必须取得，不等于人必须手填；“派生”也可能是启动的必要条件。可选输入省略后只能沿该部件已有规则求值，不增设隐式默认。运行期的“可变”区分同一 Agent runtime 实例原地变化与同一 Session／Run 内替换实例。

| 部件 | 输入来源与必需性 | 同一 Agent runtime 存活期 | 跨实例变化与影响范围 | 持久／恢复依据 |
|---|---|---|---|---|
| 租户、Session 身份 | 必需，来自 Session | 固定，不能切租户／借用别的会话 | 本会话归属始终不变 | 身份、访问归属 |
| Run 与尝试 | 启动时必需；Run 已有，尝试序号由系统生成 | 所推进的 Run 与本次尝试身份固定 | 重建可换尝试，不因重装配新建 Run；已终结 Run 不复活 | Run／尝试事实与当前推进资格 |
| AgentDefinition 身份 | 必需，取会话固定选择 | 固定 | 不能借 reload 更换身份；同身份版本按显式 reload 的安全交接边界更新 | 固定身份与各次采用版本 |
| 本次采用的定义内容 | 必需，合法已发布／已校验内容 | 已捕获版本固定 | 新内容通过新清单及新实例采用；不改写历史输入 | 实际版本及可取得内容／等效依据 |
| 会话执行类型及其必需能力、extensions | 必需，取会话创建时固定要求 | 类型与必需身份不可移除 | 必需项实现可按覆盖规则替换，不能少装 | 固定要求与各次绑定 |
| 定义显式依赖及能力继承声明 | 从本次定义派生；默认自动继承 false | 随采用定义固定 | 只在采用新定义时变；移除声明不能覆盖必需项 | 定义及选入／排除依据 |
| 组织、租户、工作区的候选资产与配值 | 必需的求值来源；工作区可为空 | 不实时偷偷替换已捕获构成 | 已受理变更、实际装配、显式 reload 各沿原生效规则；共享编辑影响共享消费者 | 实际读取来源与版本、层级、锁定及选择原因 |
| 会话对可选能力的装卸声明 | 可选，已有会话值须恢复 | 可变；移除意图使已知可选项不可用 | 仅本会话，不删除已知身份，不绕过类型／定义要求 | 当前声明、已知身份及变更事实 |
| Skill／Tool／MCP 数据与实现 | 必需身份须有合法定义；具体实现允许不可用 | 当前采用值可更新；数据与实现分别记录，不冻结整段实例 | 通过会话入口生效，不由自身变更强制重建 Loop | 已知身份、当前定义及实现依据、每次实际使用输入 |
| 系统提示词组成 | 必需，从采用定义与组合规则派生 | 组合规则捕获；能力描述、schema 等数据逐请求取当前值 | 只有自身捕获的组合规则更换才要求重装配 | 规则依据与每次请求的实际文本、声明 |
| Agent Loop 与装入的 extensions | 系统规则、会话类型、定义、协作模式等派生 | 已捕获实现、顺序和必需绑定固定 | 必须换实现／顺序／集合时切换构成；旧拓展判断的接续须单独核对 | 采用规则／实现与顺序，已开始判断、卡片与结论 |
| 权限模式与当前权限 | 必需，取会话已保存模式与当前授权 | 注入可变；重新准入按现行授权 | 本会话模式不回写租户默认；组织／租户授权按其真实范围生效 | 会话模式，授权事实及每次准入依据；历史许可不是永久许可 |
| 执行环境模式／逐工具策略 | 必需，取会话策略与当前条件 | 可变，后续工具调用求值 | 环境或沙箱实现变更影响其实际消费者，不自动影响 Loop | 会话策略、调用实际环境与资源引用 |
| 协作模式 | 必需，取会话当前值 | Ask 开关等注入取值可变；extension 集合变化按构成规则 | 切换不换会话和 Run，不卸除类型强制检查；需要换实例时走交接 | 当前模式与实际生效的开关／extension 关联 |
| 模型选择与请求参数 | 可选显式值或已有求值来源；每次请求必须得到有效输入 | 可变，不绑定整段 Agent runtime | 下一次模型请求使用；在途请求保持原模型及参数 | 会话选择、参数与每次实际请求 |
| Runtime context 注册与内容 | 必需集合＋可选注册；从 Session 取得 | 允许注册增删、内容更新；必需块不能删 | 入口内注册和数据更新不重建 Loop；其直接提供入口替换另判 | 注册来源、消费者、配置、会话自有数据与历史采用依据 |
| 工作区选择、地址与实例入口 | 可选，按会话租户校验 | 允许合法更换来源，不改变固定身份 | 重新求值受影响输入；仅直接捕获组成改变才交接实例 | 会话选择、来源、资源引用；在途调用保留原引用 |
| 执行资源、设施与服务访问引用 | 按实际消费者条件性必需 | 当前可用性可变 | 工具下游失效由该工具处理；Loop 自身必需入口失效才阻止 Loop 依赖其推进 | 归属与引用，不持久化内存句柄 |
| Session 日志、推进投影、队列与目标 | 推进时必需，已有事实恢复 | 随执行推进；不成为 runtime 私有权威 | 新实例接着原进度；不重新消费已承接输入 | 日志及有效投影、目标与会话设置 |
| Model／Tool runtime 访问入口及调用句柄 | 必须能按需发起／查找；启动时不必已有具体调用 | 句柄可取得／释放；在途执行不归 Agent runtime | 新实例按执行身份重新取得句柄，不能仅因失去句柄就重复执行 | 调用身份、原输入、原消费者、Run／原尝试、状态、结果与承接关系 |
| 人工决策卡片、外部事件与待完成拓展判断 | 有待续工作时条件性必需 | 按原业务规则推进 | 替换实例不丢卡、不替人回答、不把已出结果重复消费 | 判断位置、原采用依据、卡片／答复、未完成等待关系 |

Runtime 持有的是这些持久事实和服务的使用关系，不复制一份独立会话状态。组织／租户／工作区来源的编辑是共享修改；一次重装配选择采用它们只改变本会话，不改变其他会话的当前装配。

### 6.10 重装配触发与生效矩阵

| 变化／事件 | 求值与生效 | 是否替换 Agent runtime |
|---|---|---|
| 首次推进 Run，没有有效清单 | 全部必需输入成立后求清单 | 首次创建 |
| 原 runtime 释放／崩溃后恢复 | 核对并恢复当前已采用状态；不借恢复静默升级 | 需要新实例，但不一定重新求清单 |
| 新 Run 或显式 reload 采用同身份新 AgentDefinition | 新清单；当前 Run 的显式采用走安全交接及新尝试 | 是，沿定义既定采用边界 |
| reload 候选与当前采用值相同 | 报告无变化 | 否 |
| Tool／Skill／MCP 数据、argsSchema、正文、实现版本、常驻属性变化 | 来源校验后更新会话采用值；后续使用取新值 | 否；不把入口内部变化视为入口替换 |
| 合法新增能力；已知能力移除、禁用、排除或失去依赖 | 新身份追加；已知身份转替换件；恢复仍须满足当前规则 | 否 |
| 只换模型、参数、权限／环境策略或 context 注册、内容 | 沿各自下一次使用／准入点生效 | 否 |
| 协作模式切换、Loop／extension 更换 | 模式值可动态变化；如果替换已捕获 Loop／extension 集合或实现，须完整交接 | 只有自身捕获组成变更时需要；保留类型必需检查 |
| Loop 自身直接依赖的服务提供者撤除／替换 | 沿真实依赖范围停止、恢复或重建，不能使用失效依赖假推进 | 可能需要；由实际直接依赖与传播关系决定 |
| 某工具依赖的服务提供者撤除／替换 | 工具实现／调用按其自身依赖治理；会话入口反映可用性 | 不因此重建 Agent runtime |
| 附着、更换、解除工作区 | 校验来源，重新求值受影响输入；在途执行保留原引用 | 仅当改变 Loop 自身捕获组成时需要 |
| 工作区文件、Git、remote 内容变化；组织工作区参与策略变化 | 按 PF-020 等待实际装配／reload，不自行热刷新 | 不直接触发 |
| MCP 离线、一次模型／工具失败 | 各执行层处理，不制造重装配循环 | 否 |
| 停止 Run、归档 Session | 沿显式取消范围 | 属于停止，不是重装配 |
| 变更 Session／租户／AgentDefinition 身份或固定执行类型 | 拒绝；不包装成热重载 | 不是合法重装配 |

### 6.11 撤销、卸载与不可用的产品原则

- **会话保留已知能力身份。**资产目录仍有撤销、卸载和禁用操作；在会话内表现为该能力不可用及原因，不把已知记录删除。未见过的能力不得借替换件越过选入边界。
- **必需位置与可执行实现分开。**会话类型／定义要求的能力位置不能少；已有合法定义而实现不可用时可由替换件满足位置要求。未知必需能力不能凭空造 schema；Loop 自身必要条件失效也不能靠替换件假装继续推进。
- **处置跟随真实消费者和所有权。**工具内部服务失效处理工具自身，不扩大成 Loop 重建；Loop 实例卸载不取消 Session／Run 名下独立执行。实际执行资源消失时仍按该执行自己的失败规则处理。
- **卸载不撤销已经发生的事。**保留调用身份、数据与实现依据、输出、费用、外部效果、等待与卡片；不重发已有工作，不声称外部效果已回滚。
- **采用失败与实际状态可见。**候选未通过校验不替换当前数据；数据有效但实现不可用要如实呈现。恢复、初始化和交接未完成不能报告成功。具体装卸顺序、等待、回退和重试由 Cordis 范式下的技术设计落实。

### 6.12 消费关系与生命周期依赖

这里的“注入”明确表达谁取得谁提供的输入或访问入口，不指定 Cordis service 名称、plugin 切分或 inject 配置。**Session 是长期数据与归属，不是一个天然存在的 fiber。**“Session 注入什么”指管理该会话的组件取得什么；其供给矩阵归 [PF-015 §6.22](../PF-015-session-lifecycle-and-ownership/design.md#622-会话作用域的输入与供给)。

| 消费者 | 取得的输入／入口 | 是否捕获每项能力的具体实现 | 变化影响谁 |
|---|---|---|---|
| Agent runtime | Session／Run／尝试身份；采用定义、Loop／extensions；日志与推进状态；context、模式、能力发现／读取／调用、模型调用入口 | **否**。Tool／Skill／MCP 经会话入口访问，不能把每一项声明都转为 Loop 的生命周期硬依赖 | Loop 自身捕获的组成与直接必要入口；入口内能力数据／实现更新不使 Loop 重建 |
| Model runtime | 一次请求的实际模型、参数、提示词、tools/schema、上下文，以及 Session／Run／用途与结果归属 | 捕获本次请求输入，不依赖这些工具的实际执行实现 | 自己的调用依赖；请求发出后不追着新 schema 改写 |
| Tool runtime | 本次合法采用且相互匹配的工具定义、实现、参数、准入、环境、MCP 连接与资源访问，以及执行归属 | **是，本次执行固定**；与另一次调用可不同 | 该执行真实所需的资源与服务；不转移到 Agent runtime 名下 |
| Skill 读取与资源消费 | 会话当前允许读取的说明、正文、资源及其版本；脚本另经工具执行准入 | 读取内容固定为一次使用依据；Skill 数据不天然对应一个 fiber | 内容更新影响下次读取；不自动运行脚本或重建 Loop |

**数据、实现与承载服务分别变化。**可以在同一服务中更新工具注册条目、替换执行函数或采用新 schema，而不替换服务提供者。反过来，服务替换可以不改变任何工具定义。若技术方案确实更换服务或其所有者，须按真实依赖与所有权传播；产品不承诺把任意不可恢复资源无损迁移。

会话入口必须提供明确的采用结果，不能让一次调用混用不匹配的新定义和旧实现。每次模型请求／Skill 读取／工具执行记录实际使用的数据版本和实现依据；资产版本与实现版本不要求一一对应。旧模型结果提出尚未发起的动作时，即使 Agent runtime 从未重建，也按 [PF-012 §6.18](../PF-012-agent-loop-and-run/design.md#618-agent-runtime-的装配与重装配交接)核对当前状态；原定义调用约定或实现绑定已变，不自动改参、不暗换实现，把原因交回 agent。

## 七、取舍

| 面临的选择 | 选了 | 为什么 |
|---|---|---|
| agent runtime 对用户可见 ／ 不可见 | **不可见**（I-2） | 它的生灭是资源治理，不是协作事件。让用户看见，他就得为一件本该系统负责的事操心，而且会问「为什么我的 agent 重启了」——那个问题没有对他有意义的答案 |
| 系统提示词在装配时定成品 ／ 在请求时组装 | **请求时组装** | 不同模型的组装方式可能不同。在装配时定死，换模型就得重新装配，而换模型本该是轻的 |
| 权限进构成 ／ 权限是注入 | **注入** | 进构成的话，收紧权限会让 agent 突然不知道某件事存在，既无法解释也无法申诉。作为注入，它知道「这件事存在，我现在不被允许」 |
| 落点进构成 ／ **每次执行现算** | **现算** | 一条命令执行在宿主机还是沙箱，agent 都能执行。进构成的话，落点一变就要重新装配，毫无道理；**环境供给及其实现由实际消费者取得，不由沙箱变化自动推出 Agent runtime 重建** |
| 上下文变化立即打断当前运行 ／ 下一轮到达 | **下一轮** | 立即打断会让一个正在收尾的工作半途而废，而变化本身通常不紧急。紧急的那种走[控制指令](../PF-014-inbound-intake-and-queueing/design.md#控制指令)，那归 PF-014 |
| 变化以「能力被改了」通知 ／ 以上下文内容到达 | **上下文内容** | 前者是系统替 agent 做决定，后者让 agent 自己判断怎么调整。**「在运行中调整行动轨迹」只有后者能做到** |
| 一个会话可有多个 agent runtime ／ 至多一个 | **至多一个**（I-1） | 两个 agent runtime 同时以同一身份说话，历史就没有单一真相 |
| 装配清单只作内部记录 ／ 作为产品对象 | **产品对象** | 「当时装的是什么」是排障与审计的唯一答案来源。只当内部记录，这个问题就永远答不上来 |
| 清单可跨尝试复用 ／ 每次尝试重算 | **可复用** | 重算要重跑一遍作用域求值，而[普通恢复不能静默更换定义版本](#61-不变式)（I-3）。显式 reload 的新清单须有单独采用记录；恢复本身不成为偷偷升级的入口 |
| 装配缺东西时降级跑起来 ／ 明确失败 | **明确失败**（I-9） | 一个残缺的 agent 跑起来，它自己不知道缺什么，用户也不知道——问题会在很远的地方以莫名其妙的形式出现 |
| 类目挂在每一份定义上 ／ **只挂在 master 上** | **只挂 master** | `non-master` 不开协作，「这段协作是干什么的」对它没有意义。**给它一个填不出内容的字段，只会让人去猜该填什么** |
| 第二类叫 `subagent` ／ **叫 `non-master`** | **`non-master`** | 叫 `subagent` 会与[子 agent](../../ubiquitous_language/terms/interaction-and-dispatch.md#ul-subagent--子-agent--subagent)**同名不同义**——那个说的是**派发关系里的角色**，这个说的是**定义有没有那套机制**。**两个词撞在一起，每次用都要带限定** |
| 会话类型直接拷贝类目 ／ **算出来** | **算出来**（归 [PF-015](../PF-015-session-lifecycle-and-ownership/design.md#53-会话类型怎么算出来)） | 拷贝的话，定义后来改了类目，**一批早就收尾的会话会在列表里集体变脸**。那不是修正，是篡改 |
| 本 topic 连会话与驱动一起定 ／ 只定定义与装配 | **只定定义与装配** | 四者的改动原因不同：会话因协作形态变，驱动因调度策略变，**agent runtime 因资源治理变**，而装配因求值的输入变。合在一起，改任何一处都要动其余三处 |
