### 2026-09-29 · Agent runtime 装配与安全交接

**直接裁决**：[本轮交流](../PF-004-agent-definition-and-assembly/interviews/2026-09-29-agent-runtime-assembly.md)要求完整装配矩阵；显式 reload 可在同一 Run 的安全交接点采用同身份新定义并开启新尝试；旧模型回复中的未发起动作按新装配核对，已移除或绑定已变不自动执行，原因交回 agent。撤销、卸载与不可用只规定 Cordis 范式下合理的产品原则。

### 2026-09-29 续裁：默认关闭与定义替换

产品负责人 [INT-011](interviews/2026-09-27-assembly-and-tool-scope.md#int-011) 直接裁定：自动继承默认 `false`；继承声明跟着 Agent Definition；允许下级替换可替换的定义；official Agent Definition 为 `immutable`；组织、租户、工作区只能自定义 non-master。

**D-3 已闭合。**声明不是独立逐层配值的设置；采用生效定义自己的声明。无声明的新定义按 false，不继承被替换定义的 true、范围或排除项。这是「声明跟着定义」及默认 false 的推导，不另造字段合并机制。

定义的不可替换只约束该定义资产，不自动锁定其引用能力的实现：引用仍指能力标识，所引资产各自的覆盖规则未被本次裁决撤销。原有可配置设置同理，不因定义 immutable 就全部失去配值能力。

**核对发现与取代范围**：PF-004 rev 14 §6.8 只明写租户只能自定义 non-master；PF-002 rev 25 §5.5 只列 meta 与持有层 immutable 三种 official 例外，尚未列 official Agent Definition。本次按明确要求补齐，不声称过去已经完整表达。取代 D-3 未裁状态及这些不完整的覆盖表述；保留 master 只能官方、上级持有锁、可配置设置与版本生命周期。官方的 non-master 定义同样受保护，不能由同名自定义定义替换。

**影响核对**：PF-001 来源通则引用完整例外；PF-002 定义与替换规则、流程、验收对齐；PF-006/007 的能力呈现与 meta 规则不变；PF-012/015 的运行与会话生命周期不变，PF-020 的来源读取不改变。冻结规格、接受范围与实现状态不升级。词表同步能力自动继承、agent 类型、official 来源例外，其余出处和对象骨架逐节复核后仅更新依据版本。

## 二、PM 推导

### 2026-09-29 由四条绑定规则推出的边界

| 推导 | 可核对的理由 |
|---|---|
| 排除仅对继承部分生效，不能删除任一必须依赖；同标识去重但保留必需性质 | 裁决第 4 条的对象是「排除继承」，第 1、2 条明定必须依赖；若排除能删必需项，这两条即不成立 |
| reload 重新选入三类资产时沿用同一规则；缺必需项校验失败 | reload 是重新加载已声明范围的入口，不是改写定义或会话类型的入口；既有 §6.3 与 PF-020 要求先校验再替换，因此不能在重载后丢掉必须依赖 |
| 必需 Skill 不等于全文常驻，必需 MCP 不等于其对端永不离线 | 裁决规定绑定，PF-006 分开构成、呈现与当下可用性；不存在改写后两者的用户指令 |
| 缺必需绑定明确失败，不以强制绑定为理由越权 | 第 1、2 条要求必需，既有 I-9 不允许残缺构成；权限与隔离未被撤销，不能用新增绑定顺序绕过它们 |
| 能力自动继承范围外的同标识实现仍可被选中 | INT-008 直接区分两个维度；否则在只继承组织能力时强制绑定组织实现，正好违反用户澄清 |


从已拍板内容推出的判断，附可核对的推理链。

| 结论 | 从哪几条推出 | 推理 |
|---|---|---|
| **三个时刻是三个，不是两个** | 「上下文/执行环境可变而实例不变」+「提示词在请求时组装」 | 若只有「装配时」和「请求时」，可变注入无处安放——它既不在装配时定死（那就不可变了），也不是每次请求重算（权限不是算出来的，是被改的）。**必须有中间这一段**，否则任何环境变化都只能靠重建实例来生效 |
| **构成与注入的分界判据** | 「实例本身不变而上下文、执行环境变化」 | 判据只能是：**这个变化改变的是「它是什么」，还是「它处在什么情况下」**。前者变了就是另一个 agent，后者它还是它。用「变了要不要重建」当判据是循环论证——那是结论不是判据 |
| **模型落在「请求时」，不在装配时** | 「不同次 run 允许切换模型」 | 若在装配时绑定模型，换模型就必须重建实例。而裁决明确要求换模型是轻的（它正是提示词延后组装的理由），所以模型只能是请求时解析 |
| **动作空间只由构成决定** | 「安全权限改变，agent 依然正常工作（动作空间不变）」 | 这是裁决的直接改写。若权限参与决定动作空间，「动作空间不变」就不成立 |
| **「移除」与「禁用」落在同一段上：构成** | 上一条 + [PF-002 §6.4](../PF-002-assets-settings-and-permissions/design.md#64-移除与禁用是两个动作)（2026-09-22 裁决） | 两个动作改的都是**持有关系**——一个不再持有，一个仍然持有但装配时被滤掉——所以两个都让**动作空间变小**，agent 两次都不知道有这回事。**权限那一维单独成行**：取值改了是注入，动作空间不变、调用被拒、能解释。**反证**：若把禁用归进注入，agent 手上就会多出一个永远调不通的条目，那是[替换件](../PF-006-tools-and-skills/design.md#63-不可用时装的是同名替换件不是不装)在管的另一件事 |
| **成分是实例的属性，成品是那一次请求的属性** | 「实例化确定所有成分，请求时组装」 | 这是裁决的改写，同时给出了一条可检验的判据：换模型后提示词可以不同，而实例不重建 |
| **系统提示词不能被手工维护一份完整的** | 「综合多个模块组装出来」 | 它是「装了什么」的函数。手工维护一份完整的，装配一变它就对不上——与 [PF-002 设置页是长出来的](../PF-002-assets-settings-and-permissions/design.md#61-设置页是长出来的不是画出来的)是同一条道理 |
| **一个会话至多一个 agent runtime** | 「一个 agent 在一个会话里连续多轮运行」这个场景本身 | 两个实例同时以同一身份说话，历史就没有单一真相，也无法回答「它还是刚才那个它吗」。场景的单数形式不是措辞，是约束 |
| **agent runtime 对协作中的用户不可见** | 「定义是数据、运行时是计算资源」+ 连续多轮场景 | 它的生灭是资源治理。让用户看见，他就要为一件本该系统负责的事操心，而且会问「为什么我的 agent 重启了」——那个问题没有对他有意义的答案 |
| **实例重建时依据的定义版本不变** | 上一条 | 若重建可以换一份定义，用户就会在同一段协作里遇到 agent 变脸，而他什么也没做。这与「生灭不可见」直接冲突 |
| **装配清单是一个产品对象** | 「把定义和运行时区别开」的目的之一是可解释 | 「当时那个 agent 是什么样」只有这里能答。仅作内部记录，这个问题就永远答不上来。且它**只可追加**——改写它等于销毁历史 |
| **装配缺必需的东西要明确失败** | 「数据与运行时解耦」的前提是装配结果确定 | 降级跑起来的话，agent 自己不知道缺什么，用户也不知道；问题会在很远的地方以莫名其妙的形式出现，而根因追不回来 |
| ~~**回收是显式退役，不是「没人用就自己没了」**~~ | 「运行时是计算资源」+ 资源必须有归属 | **rev 5 随 agent runtime 一并移交 [PF-012 §6.14](../PF-012-agent-loop-and-run/design.md#614-停止有两级)**，在那里叫[优雅取消](../../ubiquitous_language/terms/agent-runtime-loop.md#ul-graceful-cancellation--优雅取消--graceful-cancellation)。推理不变：隐式回收没有「结束」这个时刻，未结算的工作与未释放的资源就没有地方交代 |
| **等人回话不消耗计算资源** | 「运行时本质上是计算资源」 | 等待是一个**持久的事实**，不是一个 agent runtime 的姿势。让一个 agent runtime 干等着，等于为一件与计算无关的事付计算的钱 |
| **成本归属到启动实例的租户** | [PF-001 成本按租户归属](../PF-001-identity-scope-and-agent-constraints/design.md) | 那条在 PF-001 已定；本 topic 只是给它一个运行侧的落点——**在此之前没有对象承载成本** |
| **增量装载不是「变化作用于下一次装配」的反例** | [SYS-COMPOSITION.C4](../../foundation/definition-and-runtime-composition/requirements.md#sys-compositionc4变化作用于下一次装配) | 往实例里**新增**一个可选能力，和把它正在用的**必需绑定换代**，是两回事。前者它照常活着，后者它赖以成立的前提变了。C4 约束的是后者 |
| **变化以上下文内容到达，不以「能力被改了」通知** | 「事件驱动地多了条 system reminder」+「agent 据此调整行动轨迹」 | 若以「你的能力被改了」的形式到达，是系统替 agent 做了决定；只有作为内容读到，agent 才能自己判断怎么调整。**裁决要的那个结果只有后者能兑现** |
| **上下文变化不打断当前运行** | 「在它**下一次** run 的时候多了条提醒」 | 裁决的措辞已经定了时机。这也与 [PF-001 §6.6 撤销不等于强制停止](../PF-001-identity-scope-and-agent-constraints/design.md#66-撤销不等于强制停止)同向 |

| **判据里说的是系统提示词的「成分」，不是「成品」** | 2026-09-20 的裁决 + [§5.4 成分与成品的分界](design.md#54-为什么系统提示词必须落在第三列) | **按「成品」读，这条判据当场不成立**：换一个模型，[组装出来的那份文本本来就可能不同](design.md#54-为什么系统提示词必须落在第三列)——而[换模型恰恰是那个明确不重建的例子](design.md#66-模型在每次请求时确定)。**产品负责人给的是归纳的方向，这个限定词是 PM 依 §5.4 补的。**按「成分」读，[五类变化逐条都对得上](design.md#三类变化背后只有一条判据系统提示词的成分会不会变)，其中最要紧的一条验证是：**增量装载的那个能力是非常驻的，它从来不进系统提示词**，所以判据说「不重建」，与 [rev 3 已立的规则完全一致** |

### rev 11 新推的

主线施工简报（产品修订批 4a，2026-09-24）在产品负责人当日裁决之下交来的一致性修正；简报给的读法是「**两者说的是不同的时间尺度**」，下表把它推到能落字的程度。

| 结论 | 从哪几条推出 | 推理 |
|---|---|---|
| **I-4 与 PF-002 D-2 不相冲：I-4 的时间尺度是一次运行** | 2026-09-17「权限对一个**运行时实例**来说，本质上是依赖注入」+ 2026-09-17「安全权限改变，agent 依然正常工作（动作空间不变）」+ [PF-002 D-2](../PF-002-assets-settings-and-permissions/decisions.md#2026-09-24--d-2d-3d-4-三条待裁转拍板)「不能用就不装」+ [PF-002 §5.2](../PF-002-assets-settings-and-permissions/design.md#谁可以使用它是各类资产共用的一项权限)「已经开始的运行不变，自下一次运行起不再装入」 | 两条 09-17 裁决的主语都是**一个跑着的实例**：它在跑的时候权限变了，它照常工作、能发起的一样不少。D-2 管的是**下一次装配装不装**，那时还没有那个实例。两边说的不是同一个时刻——**一次运行之内，任何权限都不改变动作空间；运行之间，装配的输入本来就是当时的权限** |
| **运行之间，执行权限这一类仍不改变动作空间；只有「谁可以使用它」会** | 上一条 + [PF-002 §5.2](../PF-002-assets-settings-and-permissions/design.md#谁可以使用它是各类资产共用的一项权限)「执行权限、干预力改的是发起之后得到什么，这一项改的是装不装进来——它落在组装之前，与禁用同一段」 | 简报原句「运行之间按当时权限重新装配」若按字面读成「每次运行都重算一遍清单」，就与 [§6.7 复用](design.md#67-装配清单的生与失效)、[acceptance「改一项执行权限，清单不重算」](acceptance.md)相冲。**只有一种读法两边都成立**：装配本来就拿当时的权限求值，但执行权限不进构成，求出来的构成不变；「谁可以使用它」进的是组装那一步，它变了，构成才变。所以正文写「下一次装配按当时的权限求值」，并点名只有这一项让构成变小 |
| **「谁可以使用它」被收回，在本 topic 落在构成那一段，与禁用并列** | 上一条 + [2026-09-22 禁用是构成性变化](#一拍板记录) | 它与禁用一样：持有还在，装配时被滤掉，agent 不知道有这回事（PF-002 选「不装」而不是「装上、调用被拒」，理由是一种失败比两种好认）。**放在注入那一行就会被实现成调用被拒**，正是 D-2 否掉的那一种 |
| **I-4 的「不成立会怎样」一格不改** | 上两条 | 那一格说的是「**突然**不知道某件事存在」——一次运行之内的事。运行之间不装，agent 从那一次运行开始就没见过它，与禁用同一种表现，**没有「突然」** |

### rev 12 的主线裁定（2026-09-24，待产品负责人确认）

主线施工简报（产品修订批 4b）对 rev 11 在[第四节](#四已知的来源问题)登记的那一条给的裁定：「§6.3 复用判据补『构成变小（移除、禁用、「谁可以使用它」被收回）也重新装配，下一次运行起生效』，与 D-2 一致」。**主线裁定不是产品负责人的拍板**，他可推翻。

| 结论 | 从哪几条推出 | 推理 |
|---|---|---|
| **构成变小，也重新装配，下一次运行起生效**——非常驻条目上的移除、禁用、收回「谁可以使用它」都在内 | 主线裁定 + [2026-09-22 禁用是构成性变化](#一拍板记录) + [PF-002 D-2](../PF-002-assets-settings-and-permissions/decisions.md#2026-09-24--d-2d-3d-4-三条待裁转拍板)「不能用就不装」+ [PF-007 `Tools()` 搜的是当前装配清单](../PF-007-meta-capabilities/design.md#61-tools通向任意非常驻工具) | 非常驻条目不进系统提示词，照判据字面清单继续复用，而 `Tools()` 搜的就是那份清单——**被禁用、被收回的条目下一次运行里照样搜得到、调得到**，禁用即不可见与「不能用就不装」同时落空。补上这一句，常驻与非常驻两种在用户那一侧的表现一致：正在跑的照常用得上，下一次运行起看不到 |
| **只补「变小」，不补「变了」** | 上一条 + [§6.3 增量装载不必重新装配](design.md#63-三类变化三种传播) | 构成变大（运行中增量装上一个可选能力）清单追加一条就够，**重新装配反而会打断正在做的事**。落空的只有变小那一侧，补的也只是那一侧 |
| **判据本身不改，表里多一行、表下另成一句** | [产品负责人 2026-09-20 的归纳](design.md#三类变化背后只有一条判据系统提示词的成分会不会变) | 判据对常驻那几种、对改定义、对增量装载、对注入、对换模型的回答一个都没变；它答不到的只有「成分不变而构成变小」这一种。**把这一种硬塞进「成分」会让「成分」失去它在 §5.4 的意思**，所以另写一句。**代价**：那一节标题说「只有一条判据」，而现在要重新装配的理由有两种——这一处与产品负责人那条归纳的字面有出入，照实交他裁 |

**本 topic 在[架构内核](../architecture-core.md)上，rev 12 动手前的三问：**

1. **谁依赖改的这一条？**顺 `depends-on` 反查有十个 topic；碰到清单失效条件的是这三个：[PF-007](../PF-007-meta-capabilities/README.md)（`Tools()` 搜的就是当前装配清单——这一句正是为它成立而补，那边不用改）、[PF-012](../PF-012-agent-loop-and-run/README.md)（agent runtime 照一份清单起；清单何时失效它不过问）、[PF-006](../PF-006-tools-and-skills/README.md)（常驻与非常驻的分法，未动）。
2. **哪些已接受的结论会松动？**2026-09-20 那条归纳「其他都是应当能够归纳到这一点的情形」的字面——见上表最后一行，交产品负责人；2026-09-22「禁用是构成性变化」与 PF-002 D-2 **因此才真正兑现**，不松动。
3. **是真要改，还是用错了地方？**是改：落空的是本 topic 自己的清单失效条件，别处补不上；**没有新动作、新状态、新时机**，时机仍是「下一次运行起」。

### 「类目只能出厂加」是推论，不是第三条独立限制

**推理**：产品负责人已经把因果说全了——「**关键是用来限定 master agent 的 category，
而如果租户只能自定义 sub agent，就意味着 master agent 只能是产品 officially 提供的**」。
**所以 R-3 不必单独立论**：类目是给 master agent 分类用的，master agent 只能官方给，
类目自然只能官方加。**正文按推论写，不按并列的三条写**——
并列会让人以为将来可以单独放开其中一条。

### `non-master` 不该有类目

**推理**：类目回答「**这段协作是干什么的**」，而 `non-master`
[不开协作](design.md#agent-类型)——它没有那套机制。
给它一个填不出内容的字段，**只会让人去猜该填什么**，而猜出来的值会被下游当真。
**留空比留一个没意义的字段安全。**

### 本轮 PM 推导：装配、实例和独立执行的边界

- 会话身份与定义身份固定，而 reload 允许同 Run 采用新内容，因此以新清单和新尝试表达变化；普通恢复必须找当前实际生效清单，不能回到 Run 最初版本或直接读最新来源。
- Model／Tool runtime 由 Session／Run 治理，故 Agent runtime 的退役只改变使用关系；其自身依赖真的失效时仍按各自失败规则处理，不能推导成所有资源永不卸载。
- 未发起动作须按新绑定核对，而已经发起的调用保留原输入，故“模型返回动作建议”与“工具实际执行”必须分清；旧许可不能自动覆盖新实现。
- 重装配可能在等待调用、卡片或拓展判断时发生，故未完成工作的身份、采用依据、结果及等待关系须能恢复；这不推出一律等待、一律拒绝、一律回退或一律取消。
- 重载意图、当前实际生效构成会影响后续求值，故不能只保存一条可丢的命令摘要。持久化布局及交接算法仍属技术设计。

**框架核对依据**：[Cordis 4.0.4 必需服务提供者变化读数](../../basis/cordis/plugin-body-reruns-on-provider-change.md)区分提供者换代／不可用与同实例状态变化，并要求跨重跑保留的事实不能只在消费者闭包内。这里只据此约束产品原则，不指定 inject、effect、插件层次或 API；也不把 DSH 的宿主实现当成本项目方案。

**出处对账**：本轮复核 127 个被引词条／对象／待裁条目、164 个来源链接。以修改前快照核对出处未变部分，逐项检查改变的装配、reload、传播与恢复说明；同步增量装载、动作空间、会话资产注册表、定义／构成及清单的表达。Run、Session 与三类 runtime 的身份和宿主不变，既有资产治理、日志、调用、队列、context、待裁对象不因矩阵汇总而重新定义。引用更新到当前 rev，未新增持久对象。

### 2026-09-29 · 能力消费与服务依赖的边界

**直接输入**：[本轮交流 INT-005～008](../PF-004-agent-definition-and-assembly/interviews/2026-09-29-agent-runtime-assembly.md)：会话能力身份见过后保留，失去当前选择或实现时呈现不可用替换件；资产定义数据与执行实现解耦；会话类型必需与 AgentDefinition 显式必需同样不意味着 Loop 直接依赖能力背后的服务。

**本 topic 落点**：明确会话与各 runtime 消费关系；能力身份单调保留，数据／实现更新不自动重建 Agent runtime；必需能力不等于 Loop 的直接服务依赖。

**PM 推导**：①“已知”与“当前允许执行”必须分别求值，否则单调性会变成绕过撤权；②实现更新可发生在稳定入口内部，故不从它推出提供者换代或 Loop 重建；③ schema 更新可能改变调用含义，故即使实例未换也须核对尚未发起的旧动作；已发工作继续沿原输入；④每次求值所需输入不同，故分别保存会话当前采用值、历史数据与实现依据和单次调用快照；⑤Session 是数据／归属，逻辑供给矩阵不推出它是 fiber；实际 inject 边与所有权仍需技术设计和验证。常驻呈现、Slash Command 人的入口及未合法纳入资产仍沿各自边界，不把单调性扩为无条件信息公开。

**已知来源问题与处置**：旧文把能力的选入、数据、实现与服务生命周期混作一种“绑定变化”，因此过度推导 Agent runtime 重建；PF-010 还把提示词成品与实例期固定混为一谈。按本次输入修订，差异记入 C-47。AgentDefinition 版本采用仍沿已拍板的新 Run 或显式 reload 安全交接，不以本次技术分析自行取消该产品边界。框架事实采用 Cordis 4.0.4，区分 provider fiber 换代与同 provider 的数据更新（[已验证 basis](../../basis/cordis/plugin-body-reruns-on-provider-change.md)）；本次额外检查发布包源码，不声称运行了新探针。项目只复用 Cordis，不采用 DSH agent 原语。

**本轮出处对账**：复核 173 个被引用条目。修改前快照逐章节对比；已变出处逐项核对能力可见性、提示词、数据／实现与实际消费者边界，未变出处保持原定义。Session、Run、Agent runtime、装配清单、工具执行的身份／宿主不变，会话已知记录作为现有会话属性，不新建对象。已同步词条含义及来源 rev；对账证据在本次 HUB 的 tmp/session-injection-design。
