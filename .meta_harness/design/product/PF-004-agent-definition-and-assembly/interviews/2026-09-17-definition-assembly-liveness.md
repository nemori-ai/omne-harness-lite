## INT-002

- 标题：要带着 Cordis 视角与 live-agent 的架构模型去分析
- actor：**产品负责人本人**
- 表达方式：`quote`
- 内容：「虽然我们在做产品设计，但是其实你设计的时候还是要带着 Cordis 视角，
  就是权限在对一个运行时实例来说，本质上是依赖注入，由此才能将「数据」和
  「运行时实例」给解耦。然后就是，我们的系统是直接复用了 dsh-agent（也就是我们的
  packages/core/live-agent），因此这块你在设计产品的时候，最好带着对 live-agent
  的架构模型的理解去思考分析顺不顺」
- 状态：当前有效。**作为分析方法生效，不作为正文内容**——技术判断不进产品设计
- 记录者注：实际路径是 `packages/core/agent`（`live-agent` 是它的能力契约名）。
  据此读到的两件事改变了记录者的判断：一是 D-014 已把 Session、Run、Agent 实例
  定为三台独立状态机，「实例生灭是资源与装配的治理，与 Run 生命周期解耦」；
  二是 `basis/cordis` 已登记「`inject` 的真实含义是提供者换代即卸载重跑」，
  因此长时活体不能把业务能力做成必需注入。**后者促成了 SYS-COMPOSITION 的「机制边界」一节。**

## INT-003

- 标题：系统提示词的组装发生在请求模型那一刻
- actor：**产品负责人本人**
- 表达方式：`quote`
- 内容：「系统提示词不是智能体定义里面的一段静态文本而是综合多个模块（工具、技能等）
  组装出来的，但（技术上）我们需要明确，系统提示词的组装不是发生在智能体完成实例化
  那一刻（智能体完成实例化那一刻确定的是最终组装出的系统提示词的所有成分），
  而是在请求模型的那一刻（因为我们的产品是一个会话的不同次 run，允许切换模型，
  而不同模型对系统提示词的组装逻辑可能会不同，虽然统一接口契约）」
- 上下文：记录者此前把系统提示词归为「没有执行实例」的一类
- 状态：当前有效。落在 design.md §5.3、§5.4、§6.6
- 记录者注：这条**推翻了记录者上一轮的两处说法**——「系统提示词没有第三段」错了，
  「模型在装配时绑定」也错了。两者是同一个错误的两面：都把「换模型」当成了重的操作。

## INT-004

- 标题：上下文与执行环境是依赖注入，实例可以不变
- actor：**产品负责人本人**
- 表达方式：`quote`
- 内容：「执行环境和上下文，与智能体实例运行时的关系，是「依赖注入」的，
  也就是允许一个智能体实例本身不变，但是它可感知的上下文（scope）发生了变化、
  执行环境发生了变化（但不影响它动作执行本身，比如一个 shell 命令，执行在宿主机
  还是沙盒，agent 都能执行），上下文发生变化对于 agent 来说就是事件驱动地在它的
  下一次run的时候多了条「system reminder」。这种「依赖注入」形式的解耦，
  可以解决很多问题，比如 agent 动态感知外界环境的变化进而可以在运行中调整自己的
  行动轨迹，比如一个会话的安全权限发生了改变，agent 依然正常工作（动作空间不变）」
- 状态：当前有效。落在 design.md §4「注入」「执行环境」、§5.3、§6.3、§6.4、§6.5
- 记录者注：末句给的是**这套模型要兑现的两个结果**，不只是理由。正文因此把
  「动作空间只由构成决定」立为不变式 I-4——它是那两个结果能成立的唯一条件。
  这条也顺带解释了 PF-002 里「移除」与「禁用」当初凭产品直觉分开的两个动作，
  各自落在哪一段上。
