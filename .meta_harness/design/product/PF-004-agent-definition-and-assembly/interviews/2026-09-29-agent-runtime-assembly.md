# 2026-09-29：Agent runtime 装配与重装配

本文记录产品负责人原始输入与两次明确选择，正文归 PF-004、PF-012；会话与命令的引用同步 PF-015、PF-002、PF-014。它不是第二份产品权威。

## INT-001：完整装配设计

> 那么接下来，我们要在产品层面完整地把 agent runtime 的装配给设计出来，和前面我们梳理 session 部件、创建 session、明确哪些运行时可变哪些运行时不可变 一样的范式，同时在 agent runtime 这里还需要叠加，定义哪些情况下要触发 agent runtime 的重装配，以及当进行重装配的时候，活跃的 model runtime 和 tool runtime 怎么处置（或者说如果我们以及在设计上将它们的归属从 agent runtime 层面剥离了，还需要处置吗）

## INT-002：同一 Run 内显式 reload

问题：现行 PF-004 规定“同一 Run 内 AgentDefinition 版本不变，新 Run 才取最新版”。显式 reload 是否允许当前 Run 采用同一身份的新定义？

产品负责人选择：

> 允许：显式 reload 在当前 Run 的安全交接点生效，保留 Run 身份并开启新执行尝试（推荐）

## INT-003：旧模型建议中的未发起动作

问题：重装配后，旧模型请求才返回工具调用建议，但对应工具已被移除或换了实现；这次工具执行尚未发起，如何处理？

产品负责人选择：

> 按新装配核对；已移除或绑定已变的动作不自动执行，把原因交回 agent 重新判断（推荐）

## INT-004：撤除与不可用只给产品原则

> 重装配如果发生了某个部件的撤销或者说卸载或者说出现了不可用，产品上的处置只给原则，并且应当是在 Cordis 范式或者说框架下合理的处置原则

据此不采用讨论稿里“有未完成判断且不能接续便一律拒绝切换”的统一政策；不统一规定停用、恢复、卸载和重建的技术安排。产品约束必需条件、真实所有权、已发生效果、未完成工作及失败可见性。

## INT-005：会话能力身份单调

> 那么我们其实可以不定义能力撤销/卸载，也就是，在状态上，对于一个会话（当然这就意味着对于这个会话的每一个 agent runtime），能力的可见性是单调的，只要见过一次，后面即使 definition 改变、能力本身卸载，都归为进入不可用的状态，切换成替换件，直到重新装载上，那么这对 agent runtime 需要重装载的情形是不是可以大幅度缩减

## INT-006：Cordis 的实际消费关系

> 而且，从 Cordis 的设计，一个 service、plugin 变更，只有 inject 了它的 fiber 需要重装配（你可以去读 Cordis 相关的文档资料确认是否确实如此），那么对 agent runtime 来说，一个 tool、skill 的实现发生了变更，它到底要重装配吗？

核对范围：官方文档及发布包 @deepseek-ai/cordis 4.0.4 的 reflect.notify、Fiber._checkImpl／_refresh、父 fiber effect 所有权。provider fiber 的 epoch 变化与同 provider 内数据／注册更新不同；影响可沿实际依赖链传播，父子所有权及显式 restart 也是生命周期原因，不能泛化为“只有写 inject 的 fiber 才可能受影响”。核对不把 DSH 的 agent 实现作为本项目采用对象。

## INT-007：数据、实现与服务解耦

> 所以从产品设计上你就要明确定义清楚，到底是谁注入了谁，session 注入了什么、agent runtime 注入了什么，以及对于资产（当然就自然包括 tool、skill、mcp），我们很明确的是 数据（比如 definition）和实现 是解耦的，这进一步意味着实质上数据（比如 tool definition）不变而只是实现变，都不一定构成提供能力的服务本身的变化，甚至即使数据变化（比如 argsschema 变化）都未必会有影响，当然需要你来分析确认

## INT-008：两种必须依赖具有相同边界

> agent definition 里面声明要求必须装配的能力，同样不意味着 agent loop 必须直接依赖该能力背后的服务，和上面相同的道理
