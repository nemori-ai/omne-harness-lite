## rev 11 — 2026-09-24

**I-4 的时间尺度写明：一次运行之内，权限怎么变都不改变动作空间；运行之间，下一次装配按当时的权限求值。**
起因：[PF-002 rev 19](../PF-002-assets-settings-and-permissions/changelog.md) 落了产品负责人 2026-09-24 对 D-2 的裁决「不能用就不装」——
[「谁可以使用它」会话进行中被收回，已经开始的运行不变，自下一次运行起不再装入](../PF-002-assets-settings-and-permissions/design.md#谁可以使用它是各类资产共用的一项权限)；
而本 topic I-4「权限变化不改变动作空间」与 §6.5 表按字面与之相冲（那边 [decisions 第四节](../PF-002-assets-settings-and-permissions/decisions.md#四已知的来源问题)登记了这一处）。
主线施工简报（产品修订批 4a，2026-09-24）给的读法：**两者说的是不同的时间尺度**；推理在 [decisions「rev 11 新推的」](decisions.md#rev-11-新推的)。

| 位置 | 现在怎么说 |
|---|---|
| [§6.1 I-4](design.md#61-不变式) | 「权限变化不改变动作空间」→「**一次运行之内**，权限怎么变都不改变动作空间。运行之间，下一次装配按当时的权限求值（§6.5）」；「不成立会怎样」一格不变 |
| [§6.5](design.md#65-权限变化动作空间不变) | 新增一段：**时间尺度是一次运行**——运行之内不变；运行之间执行权限这一类不进构成、动作空间照样不变，**只有「谁可以使用它」改的是装不装进来**，落在组装之前、与禁用同一段，自下一次运行起不再装入。表里新增「谁可以使用它」一行（构成、下一次运行起变小、不知道有这回事）；「权限取值改了」一行注明是执行权限这一类 |
| [§4 动作空间](design.md#动作空间)的对照表 | 「权限收紧或放宽」→「**执行权限**收紧或放宽」；新增「谁可以使用它」一行 |
| [§6.3](design.md#63-三类变化三种传播) 两张表 | 构成性变化的例子补「收回了某人对它的『谁可以使用它』」；判据表第一行补同一种（常驻工具的），「权限取值改了」一行改为「执行权限的取值改了」 |
| [flows §3.3](flows.md#33-三类变化对构成的影响) | 构成那一行注明「谁可以使用它」被收回也在这一行；注入那一行写「执行权限这一类」 |
| [acceptance](acceptance.md) | 「改一项权限」→「改一项执行权限」；新增一行场景（运行中收回「谁可以使用它」）；「绝不能」那一行限定为「一次运行之内」与「执行权限」；判据表「动作空间只由构成决定」「注入不触及构成」改为执行权限，新增一行「一次运行之内动作空间不因权限而变」 |
| [decisions](decisions.md) | §二新增「rev 11 新推的」；§四新增一条来源问题（§6.3 判据对非常驻条目的移除、禁用、收回没有覆盖） |
| README | revision、状态段 |

**含义变了什么**：此前 I-4 读作「权限不论何时都不改变动作空间」；现在写明**只在一次运行之内对任何权限成立**，运行之间有一项权限——「谁可以使用它」——会让下一次运行的构成变小，与禁用同一条路。执行权限这一类的行为一个字没变。

**不改的**：权限是注入（对一个跑着的 agent runtime 而言）；构成性变化不改写活着的 agent runtime；§6.3 那条判据。

**下游要复核什么**：
- 把「权限变化不改变动作空间」实现成跨运行恒成立、因而把「谁可以使用它」做成「装上、调用被拒」的；那正是 D-2 否掉的一种。
- 装配求值：「谁可以使用它」判下来不能用的，不进装配清单；会话进行中被收回，下一次运行起不装。**非常驻的条目怎么让下一次运行看不到它，本 topic 的判据还没覆盖**，见 [decisions 第四节](decisions.md#四已知的来源问题)新登记的一条。
- [PF-002 decisions 第四节](../PF-002-assets-settings-and-permissions/decisions.md#四已知的来源问题)那一行可由 PF-002 的 owner 闭合。
- 出处标 PF-004 rev 10 的词条与对象条目，归统一语言与领域对象的维护者逐条复核。

| 系统提示词 | **成分是实例的属性，成品是那一次请求的属性**。不同模型组装方式可能不同 |
| 模型 | 唯一不在装配时绑定的组成部分——**每次请求时解析** |
| 动作空间 | **只由构成决定**。权限变了，动作空间不变 |
| 装配清单 | 是**产品对象**，只可追加。「当时那个 agent 是什么样」只有这里能答 |
| 不变式 | 九条，见 design.md §6.1 |

### 三段结构是递归的

不只 agent 整体有「定义 → 装配 → 实例」。模型、系统提示词、工具、技能、插件、
Slash Command、执行环境**各有一份**，它们的装配合起来才构成 agent 那一次装配。
逐项见 [design.md §5.2](design.md#52-三段结构是递归的)。

### 下游要注意的六处

- **不要把运行实例和会话当成一回事**，也不要和「一次运行」当成一回事。
  三者都不同：会话长期、实例可回收、一次运行短暂。
- **权限不在构成里。**把它实现进构成，「收紧权限 agent 照常工作」当场落空，
  而且收紧权限会让 agent 突然不知道某件事存在——既无法解释也无法申诉。
- **系统提示词的成品不能提前到装配时定死。**定死了，换模型就必须重建实例。
- **构成性变化不改写活着的实例。**要作用于它，只有显式退役重建一条路。
- **回收必须是显式退役。**未结算的工作、未释放的资源、未交代的失败，
  都要在退役过程里有结果。
- **装配清单只可追加。**改写它等于销毁历史。

### 本版刻意不做的

**会话、输入的受理与排队、一次运行的驱动**——这三样是最容易被顺手拉进来的，
产品负责人明确把它们划在边界之外。另有单次工具调用的生命周期、子 agent 的关系、
待决项的呈现与作答。

理由是同一条：**三者的改动原因不同。**会话因协作形态变，驱动因调度策略变，
实例化因装配与资源治理变。合在一起，改任何一处都要动其余两处。

### 本版留下的缺口

- **未决项：无。**
- **待裁决：无。**
- **一处已报告、尚未裁决的来源问题**：SYS-COMPOSITION.C3 的措辞未区分
  构成性绑定与可变注入，见 [decisions.md 第四节](decisions.md#四已知的来源问题)。
  本 topic 按「构成捕获、注入可变」落稿；foundation 若采用另一种表述，本 topic 需复核。

被排除的内容在 [design.md §2 非目标](design.md#非目标)，那是**边界**——
发现它们缺失不算缺陷。下游遇到本文档没回答的问题，应当停下来问，
而不是挑一个看起来合理的实现。
