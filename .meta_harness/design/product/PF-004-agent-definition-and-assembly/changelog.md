# PF-004 变更历史

记录**产品设计本身**的演进：哪一版改了什么含义、为什么改、下游要复核什么。
错别字、链接修复、段落搬家不记这里。

技术投影用 `provenance.json` 引用具体 rev，所以这里的 rev 不准会直接传导到实现侧。

## rev 5 — 2026-09-20

**拆掉「运行实例」，把活体那一半整个移交给 PF-012。本 topic 改名为「Agent 定义与装配」。**

依据：[UL-D-3](../../ubiquitous_language/decisions.md#ul-d-3--runtime-与活体--2026-09-20)，
产品负责人当天先立下 [runtime 命名约定](../../ubiquitous_language/conventions.md#runtime-这个词本系统写死了)
（凡以 `runtime` 为中心词的对象都是一个协程），随即指出**「PF-004 就不能用 agent runtime」**。

**拆的是什么**：rev 4 的「运行实例」被定义成「一次装配的产物：一副真正在跑的身子」，
同时挂着两组互斥的描述——

| 它被说成 | 属于哪一侧 | rev 4 的实际情况 |
|---|---|---|
| 「持有这一次的构成」「装配时确定，此后不变」 | **数据** | 四项属性全部不可变 ✓ |
| 「计算资源」「占用即消耗」「闲置就该回收」 | **执行体** | **一份资源都没持有**——模型归 PF-013 现算、上下文归 PF-010 现算、执行环境落点归 PF-005、权限归 PF-002 |

**两半各归其位**：

| rev 4 | rev 5 |
|---|---|
| 运行实例（数据那一半） | 本 topic 的[装配清单](design.md#装配清单)，属性表并入 |
| 运行实例（活体那一半） | [PF-012 的 agent runtime](../PF-012-agent-loop-and-run/design.md#agent-runtime) |
| 实例退役 · 停止有两级 · I-1 / I-2 / I-6 / I-7 | [PF-012 §6.13](../PF-012-agent-loop-and-run/design.md#613-取消跟着宿主走) 与 [§6.14](../PF-012-agent-loop-and-run/design.md#614-停止有两级)。**四条不变式沿用原编号**，既有引用不会指错 |

**[SYS-COMPOSITION](../../foundation/definition-and-runtime-composition/requirements.md#sys-compositionc1三段结构) 没有被推翻。**
它描述的「活体」——计算资源、可回收可重建、因资源治理而生灭、使用已捕获的绑定不逐次重解析、
变化不改写正在活着的——**五条逐条说的都是协程**。**是 rev 4 把「活体」认在了求值结果上**。

**下游要复核什么：**

| 谁 | 复核什么 |
|---|---|
| PF-005 / PF-006 / PF-007 / PF-008 / PF-011 | 引用「运行实例」的地方是否该读作**装配清单**（构成）还是 **agent runtime**（活体）。本次已按语义逐处替换，**但 rev 5 之后新写的正文要自己判** |
| PF-002 | 「Agent Definition 不是会话也不是实例」这句里的「实例」现指 agent runtime |
| 任何依赖 I-1 / I-2 / I-6 / I-7 的 | 正文已移交 PF-012，**编号不变、链接要改** |

**本 topic 的目录随之改名**为 `PF-004-agent-definition-and-assembly`——
`agent-runtime` 留在目录名里，会让读者以为这个概念归它。

**没有改变的**：三个时刻、[系统提示词成分/成品的分界](design.md#54-为什么系统提示词必须落在第三列)、
[§6.3 的判据](design.md#三类变化背后只有一条判据系统提示词的成分会不会变)、动作空间只由构成决定、
I-3 / I-4 / I-5 / I-8 / I-9，**逐条原样有效**。

## rev 4 — 2026-09-20

**把 rev 3 那三条并列的规则收成一条判据。**产品负责人在统一建模四个域时给的归纳：

> **本质上其实就是构建出来的 system prompt 会发生变化的时候必需重建，
> 其他都是应当能够归纳到这一点的情形。**

**没有一条规则被推翻**，[§6.3 那张表一个字没改](design.md#63-三类变化三种传播)——
**新增的是它背后那句话**，以及一张逐条核对的表：

| 变化 | 系统提示词的成分 | 重不重建 |
|---|---|---|
| 移除一个**常驻**工具 | **变** | 重建 |
| 改了 Agent Definition | **变** | 下一次 run 重建 |
| 运行中增量装载（含 agent 自己造的） | **不变**——那是**非常驻**的，[从来不进系统提示词](../PF-007-meta-capabilities/design.md#61-tools通向任意非常驻工具) | 不重建 |
| 权限、执行环境、上下文变了 | **不变**（I-4） | 不重建 |
| 换了模型 | **不变** | 不重建 |

> **价值在于它把「要不要重建」从一张要记的表，变成一个可以现场回答的问题。**
> 将来多出一类变化，**问它一遍就知道**。

### 判据里说的是「成分」，不是「成品」——这一句是 PM 补的

[§5.4 早就把两者分开了](design.md#54-为什么系统提示词必须落在第三列)：
**成分是运行实例的属性，成品是那一次请求的属性。**

> **按「成品」读，这条判据当场不成立**：换一个模型，组装出来的那份文本本来就可能不同，
> **而换模型恰恰是那个明确不重建的例子**。

**产品负责人给的是归纳的方向**；「成分」这个限定词是 PM 依 §5.4 补的，
**记在 [decisions](decisions.md#二pm-推导)**，可核对、可推翻。

### 下游要复核

- **任何把「重建判据」实现成一张枚举表**的东西——**现在有一条可现场回答的判据**；
- 本轮同时修订的 [PF-012 rev 4](../PF-012-agent-loop-and-run/README.md)、
  [PF-013 rev 2](../PF-013-model-profiles-and-invocation/README.md)、
  [PF-014 rev 2](../PF-014-inbound-intake-and-queueing/README.md)——**同一次联合修订的四份产物**。

## rev 3 — 2026-09-17

**精化重建的触发点。**§5.3 那张「三个时刻」表里，装配时那一格原先只写
「运行实例重建」，读者只看表会以为**构成一变就重建**。

起因是 [PF-006](../PF-006-tools-and-skills/README.md) 与
[PF-007](../PF-007-meta-capabilities/README.md) 落下来之后出现了具体场景：
**agent 在运行中自己造出一个工具**。若照表字面理解，它每造一件家伙什
就要把自己重启一次——而重启会打断它正在做的那件事。

| | rev 2 | rev 3 |
|---|---|---|
| §5.3 表「变了会怎样」 | 一律**重建** | **分两条路径**：Agent Definition 变了 → 下一次 run 重建；**运行中增量装载 → 不重建** |
| §6.3「增量装载是个例外」 | 已有这条规则 | **点明 agent 自己造的工具走的就是这一条**，并写清另一条路径为什么无条件重建 |

### 这不是推翻，是把已有的规则搬到表上

§6.3 的判据一个字没改，**仍然是**：

> 往实例里新增一个可选能力，和把它正在用的必需绑定换掉，是两回事。

改的是 §5.3——那张表被称为「本 topic 最要紧的一张表」，
**只看表的人此前拿不到这个例外**。

### 为什么「改了 Definition」无条件重建，不去区分改的是什么

比对差异再判断值不值得重建，**代价大于收益**；而重建的时机是
**下一次 run**，本来就不打断当前工作。

### 下游要复核什么

- **不要把「构成变了」和「Definition 变了」当成同一件事。**前者含运行中增量装载。
- agent 创建工具的产品语义在
  [PF-006 §6.9](../PF-006-tools-and-skills/design.md#69-agent-创建与修改工具技能本版只定三条)，
  本 topic 只负责说明它为什么不触发重建。

## rev 2 — 2026-09-17

**只改表述，不改含义**：把「执行环境」那几处写严，避免与
[PF-005](../PF-005-execution-environments-and-sandboxes/README.md) 并排读时被当成冲突。

| | rev 1 | rev 2 |
|---|---|---|
| §5.2 表里执行环境的「装配时确定」 | 「**接入点**」——词不达意，易被读成「装配时绑定了一个具体环境，此后跟着实例走」 | **「需要哪几类环境」**（由装进来的工具决定，属于构成）；**每一类实际落到哪一个是注入的** |
| 同一行第三列的「——」 | 没有解释，与 PF-005「无状态沙箱一次工具调用就结束」像是打架 | 加说明：**不是执行环境没有实例**，而是该列问的是「每次**模型请求**产生什么」，而执行环境的实例化粒度是**工具调用** |
| 对执行环境寿命的表态 | 正文**未表态**，但也没排除误读 | **正面写死**：执行环境的存活与运行实例无关，可能短得多也可能长得多，**本 topic 不对它的寿命作任何断言** |

**正文从未出现过「执行环境生命周期长于运行实例」这条断言。**该说法只在设计交流中
由 PM 提出、并被产品负责人当场纠正，从未落进任何文件——本版是为**防止误读**而做的
表述精化，不是撤回某条已写下的内容。

### 下游要注意的

- **不要把「装配时确定执行环境」理解成「绑定一个具体环境」。**装配确定的是
  **需要哪几类**，具体哪一个是注入的、随时可换。
- **执行环境的存活期一律去 PF-005 查**，本 topic 不是权威。

## rev 1 — 2026-09-17

**首版。**回答 PF-002 与 PF-003 都没有回答的问题：
**一份定义怎么变成一个真正在跑的 agent。**

### 这一版确定了什么

| 方面 | 结论 |
|---|---|
| 缺的是什么 | 不是一个环节，是一个**对象**——跑起来的那副身子此前没有名字 |
| 本 topic 的主角 | **运行实例**。会话与 Run 只作为它的两个接口出现，**都不在本 topic 拥有** |
| 三个时刻 | **装配时**定构成、**注入变化时**改环境、**请求时**才算模型与提示词成品 |
| 构成 vs 注入 | 判据一句话：**变化改变的是「它是什么」，还是「它处在什么情况下」** |
| 谁是注入的 | **上下文、执行环境、权限**三者。它们变了，运行实例**不重建** |
| 系统提示词 | **成分是实例的属性，成品是那一次请求的属性**。不同模型组装方式可能不同 |
| 模型 | 唯一不在装配时绑定的组成部分——**每次请求时解析** |
| 动作空间 | **只由构成决定**。权限变了，动作空间不变 |
| 装配清单 | 是**产品对象**，只可追加。「当时那个 agent 是什么样」只有这里能答 |
| 不变式 | 九条，见 design.md §6.1 |

### 三段结构是递归的

不只 agent 整体有「定义 → 装配 → 实例」。模型、系统提示词、工具、技能、插件、
Slash Command、执行环境**各有一份**，它们的装配合起来才构成 agent 那一次装配。
逐项见 [design.md §5.2](design.md#52-三段结构是递归的)。

### 下游要注意的六处

- **不要把运行实例和会话当成一回事**，也不要和「一次运行」当成一回事。
  三者都不同：会话长期、实例可回收、一次运行短暂。
- **权限不在构成里。**把它实现进构成，「收紧权限 agent 照常工作」当场落空，
  而且收紧权限会让 agent 突然不知道某件事存在——既无法解释也无法申诉。
- **系统提示词的成品不能提前到装配时定死。**定死了，换模型就必须重建实例。
- **构成性变化不改写活着的实例。**要作用于它，只有显式退役重建一条路。
- **回收必须是显式退役。**未结算的工作、未释放的资源、未交代的失败，
  都要在退役过程里有结果。
- **装配清单只可追加。**改写它等于销毁历史。

### 本版刻意不做的

**会话、输入的受理与排队、一次运行的驱动**——这三样是最容易被顺手拉进来的，
产品负责人明确把它们划在边界之外。另有单次工具调用的生命周期、子 agent 的关系、
待决项的呈现与作答。

理由是同一条：**三者的改动原因不同。**会话因协作形态变，驱动因调度策略变，
实例化因装配与资源治理变。合在一起，改任何一处都要动其余两处。

### 本版留下的缺口

- **未决项：无。**
- **待裁决：无。**
- **一处已报告、尚未裁决的来源问题**：SYS-COMPOSITION.C3 的措辞未区分
  构成性绑定与可变注入，见 [decisions.md 第四节](decisions.md#四已知的来源问题)。
  本 topic 按「构成捕获、注入可变」落稿；foundation 若采用另一种表述，本 topic 需复核。

被排除的内容在 [design.md §2 非目标](design.md#非目标)，那是**边界**——
发现它们缺失不算缺陷。下游遇到本文档没回答的问题，应当停下来问，
而不是挑一个看起来合理的实现。

## 怎么记下一版

改变含义就递增 rev 并在这里加一节。判断标准：
**读者需要据 rev 判断自己手上的理解是否还成立吗？**需要，就记。

每节至少说清三件事：改了什么含义、为什么、下游要复核什么。
