## rev 9 — 2026-09-22

**装配的输入里，工作区那一级怎么来的说清了。**
依据：[PF-002 rev 10](../PF-002-assets-settings-and-permissions/changelog.md)——产品负责人 2026-09-22 六条补充
（原话在 [PF-002 decisions](../PF-002-assets-settings-and-permissions/decisions.md#2026-09-22--工作区是一级治理不是目录会话创建时-opt-in挂上就自动加载)），
其中第 4 条「装配时自动解析加载工作区下的特殊文件」落在本 topic。

| 变更 | [§4 装配](design.md#装配)加一段、[§6.2](design.md#62-装配) 第二条补一句：**会话挂了工作区的，承载目录下特定命名的文件在装配这一刻被自动解析**，作为工作区那一级参与求值；权限项照旧滤掉；**会话没指定工作区的，这一级为空，装配不去找任何目录**。哪些文件、什么格式，与 PF-002 一样不定 |
|---|---|
| 语义变化 | 「当时该作用域的求值结果」这一输入此前没说工作区那一级从哪来、什么时候来；现在定了**来自承载目录、装配时自动进来、opt-in**。**装配的两样输入没有变成三样**——工作区的内容属于求值结果 |
| 下游要复核什么 | 任何把「读工作区配置」做成独立步骤或做成运行中随时重读的实现：它是**装配这一刻**的求值输入，之后目录里的文件变了，要不要重新装配按 [§6.3 三类变化](design.md#63-三类变化三种传播)判 |

## rev 8 — 2026-09-22

**执行环境不再是「注入给 agent runtime 的三样之一」。**
依据：[PF-005 rev 4](../PF-005-execution-environments-and-sandboxes/changelog.md) 推翻了「装配时注入一个执行环境」，
改为**宿主机始终在场、沙箱实现装配时可选装配、落点每扇门每次执行现算**；
该 topic 已把本 topic 这处措辞[登记为待复核](../PF-005-execution-environments-and-sandboxes/decisions.md#四已知的来源问题)。

### 改了什么

| 位置 | 现在怎么说 |
|---|---|
| [§4 执行环境](design.md#执行环境) | **装配时只留下两样**：需要哪几类环境（工具声明决定）、**装配方可选装配哪些沙箱实现**；**这次执行落在哪一个每扇门每次现算**（权限 × 设施 × 已装配沙箱实现的声明），**归 PF-005** |
| [§4 注入](design.md#注入) | **注入的是上下文与权限两样**；执行环境**与注入共享同一条性质**（变了不必重新装配、不必重建协程）**但来路不同**——一个是外面给的值，一个是算出来的结果 |
| [§5.1 图](design.md#51-一张图三个对象各在其位) · [§5.2 表](design.md#52-三段结构是递归的) · [§5.3 三个时刻](design.md#53-三个时刻) | 注入那一格去掉执行环境；装配那一格补上「装进来哪些沙箱实现」；落点写成**按新值现算** |
| [§6.3](design.md#63-三类变化三种传播) · [§6.5](design.md#65-权限变化动作空间不变) · [§7 取舍](design.md#七取舍) · [flows §1.5](flows.md#15-这次执行的落点换了) · [flows §3.3](flows.md#33-三类变化对构成的影响) · [acceptance](acceptance.md) | 「换执行环境」一律改为「**落点换了**」；取舍那一行由「进构成 ／ 是注入」改为「**进构成 ／ 每次执行现算**」 |

### 同一版里的第二件：§6.4 的「agent 不轮询环境」补了一处例外

依据：[产品负责人 2026-09-22 关于推与拉的裁决](../PF-014-inbound-intake-and-queueing/decisions.md#2026-09-22--runtime-context-的变更推与拉按-run-开没开闭合分)
（[PF-014 rev 3](../PF-014-inbound-intake-and-queueing/changelog.md) · [PF-012 rev 7](../PF-012-agent-loop-and-run/changelog.md)）。

[§6.4](design.md#64-上下文变化怎样到达-agent) 现在写明：**每一次执行尝试起来时取一次当前快照**，
**一次尝试一次，不是隔一会儿问一遍**——**它不是轮询**，
它存在是因为**会话空闲时生产方推来的 runtime context 变更一律被丢弃**。
**「变化以内容的形式到达、不打断正在跑的那一轮」两条一个字没改。**

### 含义变了什么

**本 topic 的两条承诺一字未改**：[落点变了不必重新装配、不必重建 agent runtime](design.md#执行环境)，
[动作空间只由构成决定](design.md#61-不变式)。**变的是「执行环境怎么进来」**：

> **此前读者会建出「agent runtime 持有一个当前执行环境、可以整体换掉」那样的东西；
> 现在它是每扇门、每次执行各算一个值。**

**下游要复核的是**：按「执行环境是注入的一个取值」建模的人，以及把沙箱实现当成注入物而不是装配项的人。
词条 [UL-execution-environment](../../ubiquitous_language/terms/grounding-and-isolation.md#ul-execution-environment--执行环境--execution-environment)
与[领域对象条目](../../domain_objects/objects.md)上那条「待 PF-004 的 owner 复核」随之闭合。

## rev 6 — 2026-09-21

**补上 Agent Definition 的两项分类属性：[agent 类型](design.md#agent-类型)与 [master 类目](design.md#master-类目)。**

依据：产品负责人 2026-09-21 的裁决，原话逐字见
[PF-015 decisions](../PF-015-session-lifecycle-and-ownership/decisions.md#2026-09-21--生命周期会话类型与业务流程拓展点)（裁决 8、9）。
**那次裁决是在谈会话类型时给出的，而这两项属性的家在本 topic**——
[PF-015 当时明写「只消费不定义」](../PF-015-session-lifecycle-and-ownership/design.md#九未决项)，本 rev 把它接过来。

### 一、新增两个概念

| 概念 | 是什么 |
|---|---|
| [**agent 类型**](design.md#agent-类型) | 一份定义**具不具备 master 的那一整套机制**：**`master`** / **`non-master`**。**只有两个取值**，后者**由前者反向定义** |
| [**master 类目**](design.md#master-类目) | 一份 master 的定义主要用来干什么。当前五类。**只挂在 master 上**——`non-master` 没有这项 |

**两者都是定义自身的属性**，与它某次装配的结果无关。

### 二、新增 [§6.8](design.md#68-两类-agent谁能被谁自定义) 三条规则

**master 必定是 official**；**租户能自定义的只有 `non-master`**；
**master 类目只能出厂增补**——第三条是第一条的推论，不是独立限制。

> **这三条约束的是「定义从哪来」，不是「装出来的 agent 能做什么」。**
> 一个 `non-master` 照样可以装得很强，**能力由构成决定**（[I-4](design.md#61-不变式)）。

### 三、第二类取值为什么叫 `non-master`

**产品负责人定的名**（[原话见 decisions](decisions.md#2026-09-21--agent-definition-的两项分类属性)）：

> **可以用 non-master 哈，也就是不具备一个 master agent 的全套机制的 agent。**

**这一句同时给了名字和定义方式**——由 master 反向定义，
划的是「**有没有那套机制**」，不是「它在派发里扮演什么角色」。

**这避开了一处同名不同义**：若第二类也叫 `subagent`，它会与
[子 agent](../../ubiquitous_language/terms/interaction-and-dispatch.md#ul-subagent--子-agent--subagent) 撞——
那个说的是**派发关系里的角色**。**两个词撞在一起，每次用都得带限定。**
**[C-14 就此闭合](../../ubiquitous_language/conflicts.md)。**

### 四、[§9 从「无未决项」变成有两条](design.md#九未决项)

1. **「master 的那一整套机制」包含哪些**——目前只列得出三条（开会话、带类目、只能官方提供）。
   **`non-master` 由它反向定义，清单不全这条线就划不准。**
   正文明写**不要按「凡是 master 有的它都没有」去实现**。
2. **`spawn` / `delegate` 能不能派一份 master 定义**——两种都自洽，等裁决。

### 五、顺带修掉一处失效引用

[§7 取舍表](design.md#七取舍)里「紧急的那种有显式控制（§6.8）」——
**本 topic 从来没有过 §6.8**，那是个指向不存在小节的引用。
现改为指向[控制指令](../PF-014-inbound-intake-and-queueing/design.md#控制指令)（归 PF-014）。
**记在 [decisions 第四节](decisions.md#四已知的来源问题)。**

## rev 4 — 2026-09-20

**把 rev 3 那三条并列的规则收成一条判据。**产品负责人在统一建模四个域时给的归纳：

> **本质上其实就是构建出来的 system prompt 会发生变化的时候必需重建，
> 其他都是应当能够归纳到这一点的情形。**

**没有一条规则被推翻**，[§6.3 那张表一个字没改](design.md#63-三类变化三种传播)——
**新增的是它背后那句话**，以及一张逐条核对的表：

| 变化 | 系统提示词的成分 | 重不重建 |
|---|---|---|
| 移除一个**常驻**工具 | **变** | 重建 |
| 改了 Agent Definition | **变** | 下一次 run 重建 |
| 运行中增量装载（含 agent 自己造的） | **不变**——那是**非常驻**的，[从来不进系统提示词](../PF-007-meta-capabilities/design.md#61-tools通向任意非常驻工具) | 不重建 |
| 权限、执行环境、上下文变了 | **不变**（I-4） | 不重建 |
| 换了模型 | **不变** | 不重建 |

> **价值在于它把「要不要重建」从一张要记的表，变成一个可以现场回答的问题。**
> 将来多出一类变化，**问它一遍就知道**。

### 判据里说的是「成分」，不是「成品」——这一句是 PM 补的

[§5.4 早就把两者分开了](design.md#54-为什么系统提示词必须落在第三列)：
**成分是运行实例的属性，成品是那一次请求的属性。**

> **按「成品」读，这条判据当场不成立**：换一个模型，组装出来的那份文本本来就可能不同，
> **而换模型恰恰是那个明确不重建的例子**。

**产品负责人给的是归纳的方向**；「成分」这个限定词是 PM 依 §5.4 补的，
**记在 [decisions](decisions.md#二pm-推导)**，可核对、可推翻。

## rev 3 — 2026-09-17

**精化重建的触发点。**§5.3 那张「三个时刻」表里，装配时那一格原先只写
「运行实例重建」，读者只看表会以为**构成一变就重建**。

起因是 [PF-006](../PF-006-tools-and-skills/README.md) 与
[PF-007](../PF-007-meta-capabilities/README.md) 落下来之后出现了具体场景：
**agent 在运行中自己造出一个工具**。若照表字面理解，它每造一件家伙什
就要把自己重启一次——而重启会打断它正在做的那件事。

|---|---|---|
| §5.3 表「变了会怎样」 | 一律**重建** | **分两条路径**：Agent Definition 变了 → 下一次 run 重建；**运行中增量装载 → 不重建** |
| §6.3「增量装载是个例外」 | 已有这条规则 | **点明 agent 自己造的工具走的就是这一条**，并写清另一条路径为什么无条件重建 |

### 这不是推翻，是把已有的规则搬到表上

§6.3 的判据一个字没改，**仍然是**：

> 往实例里新增一个可选能力，和把它正在用的必需绑定换掉，是两回事。

改的是 §5.3——那张表被称为「本 topic 最要紧的一张表」，
**只看表的人此前拿不到这个例外**。

### 为什么「改了 Definition」无条件重建，不去区分改的是什么

比对差异再判断值不值得重建，**代价大于收益**；而重建的时机是
**下一次 run**，本来就不打断当前工作。

### 下游要复核什么

- **不要把「构成变了」和「Definition 变了」当成同一件事。**前者含运行中增量装载。
- agent 创建工具的产品语义在
  [PF-006 §6.9](../PF-006-tools-and-skills/design.md#69-agent-创建与修改工具技能本版只定三条)，
  本 topic 只负责说明它为什么不触发重建。

## rev 1 — 2026-09-17

**首版。**回答 PF-002 与 PF-003 都没有回答的问题：
**一份定义怎么变成一个真正在跑的 agent。**

### 这一版确定了什么

| 方面 | 结论 |
|---|---|
| 缺的是什么 | 不是一个环节，是一个**对象**——跑起来的那副身子此前没有名字 |
| 本 topic 的主角 | **运行实例**。会话与 Run 只作为它的两个接口出现，**都不在本 topic 拥有** |
| 三个时刻 | **装配时**定构成、**注入变化时**改环境、**请求时**才算模型与提示词成品 |
| 构成 vs 注入 | 判据一句话：**变化改变的是「它是什么」，还是「它处在什么情况下」** |
| 谁是注入的 | **上下文、执行环境、权限**三者。它们变了，运行实例**不重建** |
| 系统提示词 | **成分是实例的属性，成品是那一次请求的属性**。不同模型组装方式可能不同 |
| 模型 | 唯一不在装配时绑定的组成部分——**每次请求时解析** |
| 动作空间 | **只由构成决定**。权限变了，动作空间不变 |
| 装配清单 | 是**产品对象**，只可追加。「当时那个 agent 是什么样」只有这里能答 |
| 不变式 | 九条，见 design.md §6.1 |

### 三段结构是递归的

不只 agent 整体有「定义 → 装配 → 实例」。模型、系统提示词、工具、技能、插件、
Slash Command、执行环境**各有一份**，它们的装配合起来才构成 agent 那一次装配。
逐项见 [design.md §5.2](design.md#52-三段结构是递归的)。

### 下游要注意的六处

- **不要把运行实例和会话当成一回事**，也不要和「一次运行」当成一回事。
  三者都不同：会话长期、实例可回收、一次运行短暂。
- **权限不在构成里。**把它实现进构成，「收紧权限 agent 照常工作」当场落空，
  而且收紧权限会让 agent 突然不知道某件事存在——既无法解释也无法申诉。
- **系统提示词的成品不能提前到装配时定死。**定死了，换模型就必须重建实例。
- **构成性变化不改写活着的实例。**要作用于它，只有显式退役重建一条路。
- **回收必须是显式退役。**未结算的工作、未释放的资源、未交代的失败，
  都要在退役过程里有结果。
- **装配清单只可追加。**改写它等于销毁历史。

### 本版刻意不做的

**会话、输入的受理与排队、一次运行的驱动**——这三样是最容易被顺手拉进来的，
产品负责人明确把它们划在边界之外。另有单次工具调用的生命周期、子 agent 的关系、
待决项的呈现与作答。

理由是同一条：**三者的改动原因不同。**会话因协作形态变，驱动因调度策略变，
实例化因装配与资源治理变。合在一起，改任何一处都要动其余两处。

### 本版留下的缺口

- **未决项：无。**
- **待裁决：无。**
- **一处已报告、尚未裁决的来源问题**：SYS-COMPOSITION.C3 的措辞未区分
  构成性绑定与可变注入，见 [decisions.md 第四节](decisions.md#四已知的来源问题)。
  本 topic 按「构成捕获、注入可变」落稿；foundation 若采用另一种表述，本 topic 需复核。

被排除的内容在 [design.md §2 非目标](design.md#非目标)，那是**边界**——
发现它们缺失不算缺陷。下游遇到本文档没回答的问题，应当停下来问，
而不是挑一个看起来合理的实现。
