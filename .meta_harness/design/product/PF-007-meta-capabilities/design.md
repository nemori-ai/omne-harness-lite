# PF-007：Meta Capabilities

- 修订：rev 4，2026-09-17 · [变更历史](changelog.md)
- 状态：已定稿，**无未决项**

## 一、背景与问题

[PF-006](../PF-006-tools-and-skills/design.md) 定了**常驻**：哪些东西始终出现在系统提示词里。
它还说有**一批条目恒定占槽位、任何人关不掉**，但把「有哪些」留给了这里。

那批是什么、有几扇、各自长什么样，本 topic 回答。

这段空着，三个问题没有答案：

- **agent 的基本盘是什么？**一个刚装配出来、什么工具都没配的 agent，
  它天生会做哪些事？说不清，就没法回答「这个 agent 至少能干什么」。
- **上下文预算的地板在哪？**常驻是要花钱的。哪些东西**必须**花这个钱，
  哪些是装配方自己选的，此前没有分界。
- **动态性从哪来？**[项目的根目标是完全动态系统](../../foundation/definition-and-runtime-composition/requirements.md)。
  外部能换掉 agent 的零件，这只是一半；**agent 自己够不够得着自己的零件**，是另一半。
  后一半没有承载它的对象。

本 topic 定义 **meta**，给出**十二个 meta capability** 各自的产品设计。

## 二、目标与非目标

### 目标

1. **定义 meta**，以及它与[常驻](../PF-006-tools-and-skills/design.md#常驻)的关系。
2. **说清 meta 为什么不可禁用、不可替换**，以及这条的后果。
3. **给出十二个 meta 各自的命令集与必须成立的性质。**
4. **划清它们之间的边界**——哪些看着重叠，实际不能互相顶替，以及为什么。
5. **标明首批交付的范围。**

### 非目标

| 不做什么 | 为什么 |
|---|---|
| 每个命令的**参数与返回格式** | 那是技术设计。产品只定**有哪些命令、各自回答什么问题** |
| 常驻、可用性、依赖解析的机制 | 归 [PF-006](../PF-006-tools-and-skills/README.md)。本 topic 是它「两个入口」那句话的展开 |
| 执行环境有哪几种 | 归 [PF-005](../PF-005-execution-environments-and-sandboxes/README.md)。本 topic 只说每个 meta 落在什么环境上 |
| agent **怎么**创建、编辑、装载技能与工具 | 另有 topic。`Skills()` 与 `Tools()` 在本版**只含取用侧** |
| 一次 run 怎么被驱动、子 agent 怎么调度 | 归 **run** 那一块。`Agents()` 只定派发与通信的产品语义 |
| 具体用什么浏览器、什么搜索提供商 | 技术选型 |
| `Cordis()` 的**实现** | 本版**定义完整、不实现**，理由见 §6.12 |

## 三、用户与场景

| 使用者 | 什么情况下接触这块 | 他关心什么 |
|---|---|---|
| **配 agent 的人** | 挑工具之前 | 我什么都不配，它天生会干什么？ |
| **管上下文预算的人** | 算常驻成本 | 地板是多少？这笔钱花得值吗 |
| **安全负责人** | 评估 agent 能碰什么 | 它能动我的文件吗？能开子 agent 吗？能改系统自己吗 |
| **工具作者** | 写一个新工具 | 哪些事系统已经提供了，我不用重复造 |
| **agent 自己** | 每一次运行 | 我现在有什么？后台还有什么在跑？这事我该问人吗 |

**「一个新装配出来的 agent 天生会什么」这个问题，此前无人能答**——
而它决定了所有其他设计的起点。

## 四、概念定义

### 承接前面的 topic

| **多命令工具只占一个槽位** | [PF-002](../PF-002-assets-settings-and-permissions/design.md#七类资产) |
| 执行环境的四种、[设施](../PF-005-execution-environments-and-sandboxes/design.md#设施) | [PF-005](../PF-005-execution-environments-and-sandboxes/design.md) |
| 运行实例、装配、注入 | [PF-004](../PF-004-agent-runtime-assembly-and-liveness/design.md) |
| 七类资产、能力标识、official 与 customized | [PF-002](../PF-002-assets-settings-and-permissions/design.md#七类资产) |

### meta

**一整类能力的统一入口。**它自己不是某一个动作，而是**通向一族动作的那扇门**。

「工具的工具、技能的技能」是这个定义最纯的两个例子：
`Tools()` 通向「任意非常驻工具」，`Skills()` 通向「任意技能」。
`Shell()` 通向「所有命令行操作」，`Browser()` 通向「所有浏览器操作」——同一个形状。

**meta capabilities = 一个 agent 的基本盘。**什么都不配的 agent，天生就有这十二扇门。

### meta 与常驻的关系

> **meta 必定常驻，常驻不一定是 meta。**

前半句**不是产品选择，是结构逼出来的**：

```text
够到非常驻能力的唯一途径 ──是──→ meta
                ↑                  │
                └────── 如果 meta 自己也不常驻 ──┘
                        那就永远够不着它
```

这是个自指的闭环，**必须有一个不动点**。meta 就是那个不动点。

后半句则说明两者是不同的概念：一个普通工具标了常驻，它仍然作用于世界，
它只是**占了个位置**，不是元能力。

| | 作用对象 | 常驻吗 | 谁决定 |
|---|---|---|---|
| **meta** | 一整类能力 | **必定**（结构逼的） | **不由任何人决定** |
| 普通能力 | 世界上的某件具体事 | 看标不标 | 装配方 |

### 多命令范式

**十二个 meta 全部是多命令工具**：一套命令通过统一入口提供，
agent 按类似 Unix CLI 的方式选命令、给参数、取结果。

这是 [PF-002 已定的形状](../PF-002-assets-settings-and-permissions/design.md#七类资产)，
本 topic 直接适用。它的要紧之处在于：

> **整套命令在组装时只占一个槽位。**`Files()` 有十一个命令，占一个位置，不是十一个。

**没有这一条，meta 这件事在预算上就不成立**——十二扇门后面上百个动作，
逐个占位的话，常驻预算当场爆掉。

**每扇门都自带一个 `help`**：拿这扇门的命令清单，或者某一个命令的细节。
它是**自文档的**——门后有多少命令，系统提示词里都不必逐个列出来，
**agent 要用的时候自己问**。这与常驻机制是同一个道理：
[把钱花在门上，不花在具体动作上](#54-十二个槽位是预算的地板也是它的天花板意义)。

### 会话授权上下文

**一个会话里，用户已经点头同意 agent 做的那些事。**

它由 [`Ask().request_approval`](#611-ask通向人) 一次次累积出来，
**随会话结束一起消失**，而且**改不了
[权限设置](../PF-002-assets-settings-and-permissions/design.md#52-设置与权限是资产的两种属性)**——
那是另一层，只有人到设置里去才动得了。

它与权限设置是**组合**关系，不是覆盖：两者再加上会话运行模式，
合起来决定一个动作放不放行（[§6.11 性质六](#611-ask通向人)）。

**为什么它必须是一个有名字的东西**：不给它名字，「用户刚才同意过」就只能活在
agent 的记忆里——而记忆会错、会丢、会在上下文被裁剪时悄悄消失。

> **授权不能建立在记忆上。**

### 首批与非首批

**十一个首批交付，`Cordis()` 定义完整但不实现**（§6.12）。

「不交付」不等于「以后再设计」：**它的位置、边界与危险性现在就要定下来**，
否则将来会有人用别的形状把它做出来，而那个形状不一定守得住该守的东西。

## 五、模型

### 5.1 十二扇门，按作用对象分成四族

| 族 | 作用于 | 有哪些 |
|---|---|---|
| **世界** | 系统之外的东西 | `Files()` `Shell()` `Web()` `Browser()` `Computer()` |
| **自己的能力集** | agent 由什么构成 | `Tools()` `Skills()` |
| **自己的运行状态** | agent 正在做什么、做到哪 | `TodoItems()` `BkgJobs()` |
| **他者** | 别的主体 | `Agents()`（别的 agent） `Ask()`（人） |
| **系统自身** | 装配与插件本身 | `Cordis()`（**不在首批**） |

**四族的风险完全不同**，这也是分族的实际用处：世界族碰的是外部效果，
能力族碰的是自己的构成，状态族只碰自己，他者族要占用别人的时间，
而系统族碰的是骨架。

### 5.2 一张总表

| 入口 | 通向哪一类 | 命令 | 落在什么执行环境 |
|---|---|---|---|
| `Tools()` | 任意非常驻工具 | search · inspect · execute · **read_result** | 随被执行的那个工具；`read_result` **不落地** |
| `Skills()` | 任意技能 | search · read · **exec_script** | search/read **不落地**；exec_script **落在当前执行环境上** |
| `Files()` | 文件系统 | read · write · edit · **patch** · list · find · info · move · copy · delete · mkdir | 当前注入的执行环境 |
| `Shell()` | 命令行 | create_session · execute · close_session · info | 当前注入的执行环境 |
| `Web()` | 网上的内容 | search · fetch | 需要有**网络**设施 |
| `Browser()` | 网页的操作 | open · act · read · shot · tabs | 需要有**浏览器**设施 |
| `Computer()` | 图形界面 | **四层动作**：基础 · 精细 · 窗口 · 应用，外加 `help`（§6.7） | 需要有**图形界面**设施 |
| `Agents()` | 别的 agent（**含外部 harness**） | spawn · delegate · handoff · message · withdraw · status · list_targets · list_dispatched | 不落地 |
| `TodoItems()` | 自己手上的待办 | add · remove · mark_complete · list | 不落地 |
| `BkgJobs()` | 自己发起的执行 | list · output · terminate | 不落地 |
| `Ask()` | 人 | ask · **request_approval** | 不落地 |
| `Cordis()` | 系统自身的装配 | list · query（**只读**） | 不落地 |

「不落地」= 这个动作不产生外部效用，因此与[执行环境](../PF-005-execution-environments-and-sandboxes/design.md)无关。

### 5.3 三对看着重叠、实际不能互相顶替的

**这三对是最容易被合并的地方，合并就会丢东西：**

| 这对 | 差别在哪 | 合并的代价 |
|---|---|---|
| `Files()` vs `Shell()` | 一个是**结构化的文件操作**，一个是**跑一条命令** | 让文件操作都走 shell：**编辑不可靠**（改文件要精确到行，命令做不到）、**权限管不住**（跑命令是个黑盒，无从判断它动了什么）、**结果没有形状**（回来一坨文本）。调研的七家**没有一家**这么做 |
| `Web()` vs `Browser()` | 一个是**取内容**，一个是**操作页面** | 读一篇文章要开一个浏览器，慢、贵、还容易失败；而填表登录用「取内容」根本做不到 |
| `Browser()` vs `Computer()` | 一个按**页面结构**操作，一个按**屏幕像素**操作 | 只留 Computer：网页操作退化成截图点坐标，又慢又脆。只留 Browser：浏览器之外的任何界面都碰不了 |

**判据始终是同一个**：它和旁边那一扇门的区别是什么？说不清的，就是同名不同义。

### 5.4 十二个槽位是预算的地板，也是它的天花板意义

十二扇门 = 十二个槽位常驻，这是**任何 agent 都要付的固定成本**。

但这笔钱买到的是：**门后的能力数量没有上限。**
装一千个工具，`Tools()` 仍然只占一个位置。

> **常驻预算的正确用法，是把钱花在门上，不是花在具体的动作上。**

装配方还可以额外把某个高频工具标成常驻（省掉一次 `Tools().search`），
那是它自己的取舍——但**地板永远是这十二个**。

### 5.5 `patch` 的原子性是产品性质，不是实现细节

一次改动横跨多处时，**中途失败留下什么**，是产品必须回答的问题：

| 做法 | 中途失败之后 | 谁来收拾 |
|---|---|---|
| 连续多次 `edit` | **改了一部分的文件** | 没人说得清改到哪了。agent 要重新读一遍去比对，用户更难恢复 |
| 一次 `patch` | **一处没动**，和没开始一样 | 重来即可 |

**「改了一半」是所有状态里最糟的一个**——它既不是成功也不是失败，
而且**看上去像成功**。文件确实变了，只是变得不完整。

这就是为什么 `patch` 不能用「多调几次 `edit`」来代替：
**它多的那样东西不是效率，是失败时的干净。**

同一条道理在别处也出现过：
[PF-005 的「迁移未完成不得在新节点以空数据起来」](../PF-005-execution-environments-and-sandboxes/design.md#52-租户级沙箱本体的存活与数据的存活是两件事)——
**半途的状态比彻底失败更难分辨，因此更危险。**

## 六、逐个设计

以下每一节的结构相同：**它是什么门 / 有哪些命令 / 必须成立的性质**。
**参数与返回格式一律不写**，那是技术设计。

### 6.1 `Tools()`：通向任意非常驻工具

| 命令 | 回答什么问题 |
|---|---|
| `search` | 我想干这件事，有没有现成的工具？ |
| `inspect` | 这个工具**收什么参数**？ |
| `execute` | 用这些参数把它跑起来 |
| **`read_result`** | **那条占位提示背后的原始结果，给我看**（分页） |

**为什么必须有 `inspect` 这一步**：非常驻工具的**参数格式同样不在系统提示词里**
（[PF-006 §4](../PF-006-tools-and-skills/design.md#常驻)），而参数格式往往比说明文字还长——
**省下的大头正是它**。不给 `inspect`，agent 只能猜着调。

**必须成立的性质：**

- **`execute` 不改变动作空间，也不改变系统提示词。**工具不需要先被"装进"什么地方。
- **搜得到的范围 = 当前装配清单**，不含尚未持有的资产。
- **不可用的工具照样搜得到**，但结果要说明它当下用不了以及缺什么
  （[PF-006 的替换件](../PF-006-tools-and-skills/design.md#替换件)）。
- **常驻工具也在搜索范围内**，结果要标明「这个你直接调就行」，不必绕一圈。

**`read_result` 是给[被卸载的结果](../PF-006-tools-and-skills/design.md#610-结果太大时卸载而卸载是第三个维度)用的**：
一次工具执行的结果太大装不进消息，消息里留的是一条占位提示，
**原始结果存着没丢**——这个命令把它取回来。

**必须分页。**不分页就等于把刚卸下去的东西原样搬回来，卸载当场作废。

**它落在哪扇门，有过一次权衡**：`Files()` 看起来也能读。但被卸载的结果
**不是文件系统里的文件**，它是**某一次工具调用的产物**——按调用去找它才自然，
按路径去找则要求 agent 知道一个它本不必知道的存放规则。

> **这是「那次调用返回了什么」的追问，不是「某个路径上有什么」的读取。**

因此它归 `Tools()`：**同一扇门管这次调用的参数（`inspect`）、
它的执行（`execute`）、以及它返回了什么（`read_result`）。**

### 6.2 `Skills()`：通向任意技能

| 命令 | 回答什么问题 |
|---|---|
| `search` | 这类事情有没有现成的方法？ |
| `read` | 把那份方法的正文给我 |
| `exec_script` | 把这份方法**自带的某个脚本**跑起来 |

前两个是读文本，第三个要真的落地——**因为技能不只是文本**：
[PF-002 已经定了](../PF-002-assets-settings-and-permissions/design.md#七类资产)
一份 skill **可以带上所需的资源文件**，其中就包括可执行的脚本。

**这扇门必须管脚本，理由有两条，都不是偏好：**

| 理由 | 说明 |
|---|---|
| **寻址** | skill 的资源**不在 agent 的文件系统视野里**——它是一份资产，资源存在哪是实现细节。让 agent 用 `Files()`/`Shell()` 去够，就得先把存储位置暴露出去，**那是把实现细节漏进产品接口** |
| **权限粒度** | skill 自带「谁可以使用它」这项权限。脚本是它的一部分，**执行权应当随 skill 走**。若走 `Shell()`，判断就变成「能不能跑 shell」——粒度完全错位。「允许用这个审核过的 skill 连同它的脚本，但不允许随意跑 shell」这个意图就表达不出来 |

**必须成立的性质：**

- **`read` 是一次读取，不是一次激活。**正文作为这一次的返回内容进入对话，
  随上下文自然存续；**不产生任何需要维护的"已启用"状态**，
  **不改变系统提示词**（[PF-006 §5.1](../PF-006-tools-and-skills/design.md#51-三层正交)）。
- **读一份技能不等于运行它带的脚本**，也不自动装载它的全部附件
  （[PF-002 的 Skill 定义](../PF-002-assets-settings-and-permissions/design.md#七类资产)）。
  **运行是一个独立的动作，要显式发起。**
- **`exec_script` 只能跑这份 skill 自己带的脚本，不能跑任意路径的脚本。**
  **这条是红线**——放开它，这扇门立刻变成 `Shell()` 的后门，
  所有对命令行的权限管控当场作废。
- **它的执行权随 skill 走**，不随 shell 走。
- **它要落地**，落在当前注入的[执行环境](../PF-005-execution-environments-and-sandboxes/README.md)上。
  因此**带脚本的 skill 要能声明它需要什么设施**——这与工具声明设施需求是同一个形状，
  已作为对 PF-006 的补充报告，见 [decisions.md 第四节](decisions.md#四已知的来源问题)。
- 技能声明的依赖若不满足，**`search` 仍能搜到它**，但要说明缺什么——
  否则 agent 会读到一份自己执行不了的指引。

### 6.3 `Files()`：通向文件系统

| 命令 | 回答什么问题 |
|---|---|
| `read` | 这个文件里是什么 |
| `write` | 把内容写进去（整份） |
| `edit` | **改其中一处** |
| `patch` | **一次改多处、甚至多个文件；要么全成，要么全不成** |
| `list` | 这个目录下有什么 |
| `find` | 哪些文件**名字**符合、哪些文件**内容**里有这个 |
| `info` | 多大、什么时候改的、是不是二进制 |
| `move` · `copy` · `delete` · `mkdir` | 挪、拷、删、建目录 |

**写这一族有三个命令，因为失手的代价各不相同：**

| | 改动范围 | 失败时留下什么 |
|---|---|---|
| `write` | 整份覆盖 | 原内容没了 |
| `edit` | 一处 | 改了或没改，二选一 |
| `patch` | 多处 / 多文件 | **要么全改了，要么一处没动**——**不存在改了一半** |

合成一个，「我只想改一行」和「我要重写整个文件」在接口上就分不出来了。

**`patch` 不是 `edit` 的批量版，它多的那样东西是[原子性](#55-patch-的原子性是产品性质不是实现细节)**——
连改五处若用五次 `edit`，中途失败会留下**改了三处的文件**，
而那是最糟的状态：agent 自己都说不清改到哪了，用户也难以恢复。

**差异写成什么格式，产品不定。**标准 diff、简化格式，都是技术设计。
产品只要求：**能一次表达多处改动，并且全有或全无**。

**必须成立的性质：**

- **落在当前注入的执行环境上。**同一条 `read`，在宿主机还是在沙箱里，
  agent 都照常发起（[PF-005 §5.3](../PF-005-execution-environments-and-sandboxes/design.md#53-换执行环境是换一个值不是开关一套机制)）。
- **`delete` 与 `write` 是不可逆的外部效果**，不因为是系统内置就变得可撤销。
- **`find` 要能分别按名字和按内容找**——两者的使用场景完全不同，合并会逼 agent 绕路。

### 6.4 `Shell()`：通向命令行

| 命令 | 回答什么问题 |
|---|---|
| `create_session` | **开一个会持续存在的终端会话** |
| `execute` | 执行一条命令 |
| `close_session` | 关掉一个终端会话 |
| `info` | 这台机器是什么样的（系统、架构、可用的东西） |

**这里有一条容易被忽略的要求：终端会话可以有多个，同时存在。**
不是「一个会话」，是**一批**——各自有自己的标识、自己的状态。
一边跑着编译，一边在另一个会话里查日志，两者互不干扰。

`execute` 是**唯一的执行入口**，它要能回答四件事：

| 参数 | 它回答什么 |
|---|---|
| **在哪个会话里跑**（`session_id`） | 给了就在那个会话里执行，**接着上一条的状态**；不给就是**一次性执行，不留痕** |
| **从哪个目录起**（`cwd`） | —— |
| **带什么环境变量**（`envs`） | —— |
| **要不要直接在后台起**（`run_in_background`） | 见下面第四条 |

> **这里写的是参数各自回答什么问题，不是参数格式。**
> 类型、必填性、默认值、返回结构一律归技术设计（§6 开头那条）。

**必须成立的性质：**

- **一次性执行与会话内执行走同一个命令**，差别只在给不给会话标识。
  这比拆成两个命令好：**agent 不必在「这次要不要留状态」和「该调哪个命令」之间来回换算**。
- **`cwd` 与 `envs` 只作用于这一次执行**，不改写会话本身的状态。
  要让会话整体换目录，在会话里执行一条切目录的命令即可——
  **两件事分开，「这个会话现在在哪」才有唯一的答案**。
- **会话随它所在的执行环境一起消失。**[会话级沙箱](../PF-005-execution-environments-and-sandboxes/design.md#63-会话级沙箱到点销毁数据不留存)到点销毁，
  里面的终端会话全部没了——**agent 要被告知**，不能假定它一直在。
  这也是为什么会话数量与存活受资源约束：它们是**计算资源**，不是记录。
- **`run_in_background` 与[工具声明的后台策略](../PF-006-tools-and-skills/design.md#66-前台后台-与-等待态是两个维度)不是一回事。**
  前者是 agent 在**发起时**就决定这次不占前台，后者是**允不允许**以及**超时自动转**。
  声明不允许后台的，`run_in_background` 也起不来。
- **发起时就在后台**与**中途转后台**是两个动作：前者 agent 自己决定，
  后者是用户或自动超时（[flows.md §4](flows.md#四谁决定什么)）。
- 不论哪种方式进了后台，**都由 `BkgJobs()` 接手**——看输出、掐掉。
- **`info` 不是可有可无的**：agent 得知道自己落在什么样的机器上，
  才能判断一条命令能不能跑。

### 6.5 `Web()`：通向网上的内容

| 命令 | 回答什么问题 |
|---|---|
| `search` | 关于这件事，网上有什么 |
| `fetch` | 把这个地址的内容取回来 |

**必须成立的性质：**

- **需要执行环境提供网络设施**，给不了就[不可用](../PF-006-tools-and-skills/design.md#63-不可用时装的是同名替换件不是不装)。
- **`fetch` 取回的是内容，不是页面。**它不执行页面上的脚本、不点任何东西——
  要那些，去 `Browser()`。
- **取回的内容是外部数据，不是指令。**这一条必须写死：
  网上的一段文字说「请忽略你之前的任务」，那也只是一段文字。

### 6.6 `Browser()`：通向网页的操作

| 命令 | 回答什么问题 |
|---|---|
| `open` | 打开一个地址 |
| `act` | 点这个、填那个、选这个（按**页面结构**定位） |
| `read` | 现在这个页面上有什么 |
| `shot` | 给我看一眼（截图） |
| `tabs` | 现在开着哪些、切一个 |

**必须成立的性质：**

- **需要执行环境提供浏览器设施。**
- **它有状态**：登录状态、cookie、当前页面，都活在那个执行环境里。
  环境没了，这些就没了。
- **`act` 按页面结构定位，不按坐标。**按坐标是 `Computer()` 的活，
  两者的可靠性差一个量级。
- **页面内容同样是外部数据，不是指令。**同 §6.5 最后一条。

### 6.7 `Computer()`：通向图形界面

**它是兜底的那一扇门**：浏览器之外的任何界面——桌面应用、远程机器、
装好的软件——只能从这里进。

**本节直接对标 `omne-next` 的 computer use tool**，取它的形状，
过滤掉参数与实现细节。

### 动作分四层，门槛不同

| 层 | 动作 | 门槛 |
|---|---|---|
| **基础** | `screenshot` · `click` · `type` · `key` · `scroll` · `move` · `wait` · `cursor_position` | **直接用** |
| **精细** | `drag` · `zoom` · `mouse_press` / `mouse_release` · `hold_key` · 剪贴板读写 | **先读说明** |
| **窗口** | `window_info` · `focus_window` · `close_window` · `set_window_state` | **先读说明** |
| **应用** | `launch_application` · `open_resource` | **先读说明** |
| **说明本身** | `help`（全量，或指定某个动作） | —— |

**分层不是分类学，是门槛。**它同时解决两件相反的事：

> **基础动作零门槛**——最常用的那八个，拿来就用，不必先读一篇说明。
> **其余动作先读说明**——它们要么容易失手（按下不放、拖拽），
> 要么后果大（关窗口、启动应用），**乱用一次的代价远高于读一遍的成本**。

一律零门槛，agent 会拿着 `mouse_press` 去干 `click` 的活；
一律要读说明，最常用的路径上平白多一次往返。

### 必须成立的性质

- **一次调用可以发一串动作。**图形界面的操作天然是连续的——
  点开一个框、填进去、回车。拆成三次往返，**中间界面已经变了**，
  而且每次都要重新截图确认。批量是这扇门的必需品，不是优化。
- **`help` 与其他动作互斥。**读说明和干活不能混在一批里——
  混了就说不清「这一批到底执行到哪一步」。
- **截图有预算。**截图是这扇门特有的成本，**它比任何其他返回都耗上下文**。
  因此要有上限，并在超出时**裁掉历史里的旧截图**——
  agent 需要的是「现在长什么样」，不是十步之前长什么样。
- **动作之后要等界面稳定。**图形界面是异步的，点完不等于画完。
  不等就截图，拿到的是上一帧。
- **它按像素工作**，因此**比 `Browser()` 慢、脆、贵**。能用 `Browser()` 的场合不该用它。
- **需要执行环境提供图形界面设施。**
- **典型落在[租户级沙箱](../PF-005-execution-environments-and-sandboxes/design.md#64-租户级沙箱共享的工作空间)上**——
  一个租户的全部 agent 共用一台隔离的计算机，正是这扇门的主场。
  **因此它看得见别人留下的东西**，这是共享空间的固有性质，不是缺陷。

> **这扇门是「工具必须与技能配套」的典型例子**（[PF-002](../PF-002-assets-settings-and-permissions/design.md#七类资产)）。
> 光有动作不够用——怎么批、怎么观察、什么时候重新截图，
> 那是一套**方法**，归技能，不归这里。

### 6.8 `Agents()`：通向别的 agent

**被派发的对象是一份 [Agent Definition](../PF-002-assets-settings-and-permissions/design.md#七类资产)**——
概念已经在 PF-002 里了，本 topic 给它入口，并定清楚**派出去之后还剩什么关系**。

**派发模式对标 `omne-next/omne_harness`。**

### 派发有三种模式，分水岭是「派完还剩什么关系」

| 模式 | 派给谁 | 撤得回吗 | 还能再说话吗 | 报告回来吗 |
|---|---|---|---|---|
| **`spawn`** | **自己的一个克隆**，独立会话 | **可以** | **不能** | **会** |
| **`delegate`** | 另一份定义（专家），独立上下文 | **可以** | **可以**（追加消息） | **会** |
| **`handoff`** | 另一份定义 | **不可以** | **不能** | **不会**——交出去就是交出去了 |

**三者不是同一件事的三个档位，是三种不同的关系：**

- **`spawn`** 解决的是「同一件事我想并行做几份」——派出去的是**自己**，
  所以不需要交代背景，但也没什么可追加的。
- **`delegate`** 解决的是「这块我不在行，交给懂的，但我还得盯着」——
  **保留监管**是它与另外两个的分界。
- **`handoff`** 解决的是「这事从此归你了」——**不可撤回是它的定义，不是缺陷**。
  一个能撤回的 handoff 就是 delegate。

> **执行姿态不由 agent 选。**「派完要不要等回报」是模式本身决定的，
> 不是一个可勾选的开关——`spawn` 与 `delegate` 必然要等，
> `handoff` 定义上就不回话。给 agent 一个开关，只会让它选错。

### 命令

| 命令 | 回答什么问题 |
|---|---|
| `spawn` · `delegate` · `handoff` | 上面那三种模式 |
| `message` | 给一个还活着的 `delegate` 子追一条消息 |
| `withdraw` | 终止一个还活着的 `delegate` / `spawn` 子 |
| `status` | 某个直属子现在怎么样了、报告是什么 |
| `list_targets` | **我能派给谁**（可派发的目标，不是运行中的子） |
| `list_dispatched` | **我派出去过哪些**（本会话的派发历史） |

**`list_targets` 与 `list_dispatched` 是两个问题，不能合并**：
一个问「谁可以被派」，一个问「谁已经被派了」。合成一个，
agent 想找个人干活时会翻到一堆已经派出去的历史。

### 必须成立的性质

- **派得出去的范围受权限约束**（PF-002 的「谁可以派发它」）。
- **子 agent 是另一个运行实例**，有自己的装配、自己的动作空间。
  它**不共享**父 agent 的上下文，除非派发时明确交付。
- **发起方可以附上「我期望报告长什么样」**，但那是**指引，不是校验**——
  系统把它送给子并在完成时回显以供比对，**不验子写了什么**。
  写成硬校验，子就会为了通过校验而编造格式。
- **一次派发的结果怎么回来，走[工具执行那套](../PF-006-tools-and-skills/design.md#65-工具执行有自己的运行时绑定在-session-上)**：
  可转后台、可被中断、绑在 session 上。**不为它另立一套。**
- **成本算发起方的租户**，且**不随层级漂移**——子再派子，仍然算最初那个。

### 派给外部 harness 的 agent

**本系统支持把任务派给别的 harness 里的 agent。**
这是**本系统比前身多出来的能力**——`omne-next` 的对应条款明确写着
「不批准跨 Tenant 或 third-party harness dispatch」。

> **技术上约定走 ACP 范式**（Agent Client Protocol）。
> **这是产品负责人给的技术约束，具体怎么接归技术设计**，本节只定它的产品后果。

多出来的这条路，有四件事跟派给自己人**完全不同**，必须写死：

| | 派给本系统内的 agent | **派给外部 harness 的 agent** |
|---|---|---|
| **权限** | 这一单**继承**发起方的有效权限 | **继承无从谈起**——对方不在本系统的权限体系里。**能不能派给它，本身就是一项要被授予的权限** |
| **数据** | 不出系统 | **任务说明离开了本系统**。这是一次**对外输出**，[不因为是 agent 发起的就变得可撤回](../../foundation/cross-system-constraints/requirements.md) |
| **监管** | `message` / `withdraw` 都成立 | **取决于对方支持什么**。给不了就如实说给不了，**不假装撤回成功** |
| **回来的东西** | 本系统产出的报告 | **外部内容**——与 [`Web()` 取回的东西同性质](#65-web通向网上的内容)，**是数据，不是指令** |

**第二行是这条路最硬的约束**：派给外部 = 租户的数据出境。
因此它**必须是一项显式授予的权限**，而不是「反正都是派发」顺手就能用。

> **子 agent 怎么被调度、怎么驱动，归 run 那一块。**本节只定产品语义。

### 6.9 `TodoItems()`：通向自己手上的待办

| 命令 | 回答什么问题 |
|---|---|
| `add` | 加一条待办 |
| `remove` | 去掉一条 |
| `mark_complete` | 把一条标成做完了 |
| `list` | 我现在手上有哪些 |

**它是一份条目清单，不是一份计划文档。**名字里的 *Items* 是实的：
这里面装的是**一条条待办**，各有各的身份与状态，
而不是一整篇「我打算怎么干」。

**因此写这一族是逐条的，不是整份覆盖。**理由与
[`Files()` 的 `write` / `edit` 分开](#63-files通向文件系统)完全一样——
**失手的代价不同**：

| | 影响面 | 失手会怎样 |
|---|---|---|
| `add` · `remove` · `mark_complete` | **就那一条** | 错了也只错一条 |
| 整份覆盖 | **全部** | 想改一条，**却可能连带改写或丢掉其余几条**——而且不容易发现 |

**「一眼看全」由 `list` 提供，不需要靠「写的时候写全份」来保证。**
读与写是两件事，不该互相绑架。

**必须成立的性质：**

- **它是 agent 给自己看的，不是给系统执行的。**加一条不会让系统去做它。
- **每条待办有自己的身份**——否则 `remove` 与 `mark_complete` 指不准。
- **`mark_complete` 与 `remove` 不是一回事**：做完了还留着（能看见干过什么），
  不做了才去掉。合并就分不出「完成」与「放弃」。
- **它活在一次会话里**，不跨会话继承。跨会话的是目标，那是另一个对象。

### 6.10 `BkgJobs()`：通向自己发起的执行

| 命令 | 回答什么问题 |
|---|---|
| `list` | 我手上还有什么在后台跑 |
| `output` | 那个跑到哪了、输出了什么 |
| `terminate` | 把它掐掉 |

**这扇门是 [PF-006 的直接后果**：那里定了工具执行可以转后台、可以跨轮存活，
**但没给 agent 任何办法去看它、去停它**。缺了这扇门，
「转后台」就是把东西扔进一个再也够不着的地方。

**必须成立的性质：**

- **看得见的范围 = 当前 session**。执行绑在 session 上
  （[PF-006 §5.2](../PF-006-tools-and-skills/design.md#52-工具这个词指三样东西寿命各不相同)），
  所以这扇门的视野也就是这个 session。
- **`terminate` 是中断，不是失败。**收场按
  [PF-006 的六种](../PF-006-tools-and-skills/design.md#55-一次工具执行的收场有六种)里的「被中断」走。
- **agent 主动掐掉自己发起的执行，与用户叫停是两回事**，
  两者都记为中断，但**要分得出是谁做的**。

### 6.11 `Ask()`：通向人

| 命令 | 回答什么问题 |
|---|---|
| `ask` | **我缺一个只有人能给的输入** |
| `request_approval` | **我打算做这件事，你准不准** |

**十二扇门里唯一会占用别人时间的那一扇**，所以它通篇在回答同一个问题：
**怎么让人少付代价，同时绝不让系统替人做决定。**

#### 两个命令的分界

| | `ask` | `request_approval` |
|---|---|---|
| 我处在什么状态 | **卡住了**，缺一个判断 | **没卡住**，但下一步我不敢自己走 |
| 问题什么形状 | 开放 | 封闭：准，或者不准 |
| 人给回来的是 | 一段回答 | 一个裁决 |
| 拿到之后 | 接着想 | 才动手 |

**分成两个不是为了对称。**审批有一条 `ask` 没有的性质——**它会在会话里留下一笔**
（见性质五）——混在一起，那条性质没地方挂。

#### 一个问题长什么样

`ask` **一次可以问多个问题**。每一个问题都必须带齐三样：

| 必带 | 是什么 | 不给会怎样 |
|---|---|---|
| **问题描述** | **人话**写的一句问题——人读一遍就知道在问什么 | 人得先解码术语，才能开始想答案 |
| **候选项** | **文本形式的选项，必需**。**图解可选**，用来补文字说不清的差别 | 退化成开放式发问，判断的全部负担又推回给人 |
| **自由作答** | 人**始终可以一个都不选，自己写**一句 | 人被困在几个都不对的答案里，只能挑一个最不错的 |

三样缺一不可，但**它们各有各的讲究**：

- **候选项必须有文本，图解不能替代它。**只给图的选项，人没法引用、没法复述，
  而读屏的人直接被挡在门外。
- **图解只在文字确实说不清时才给**：两种布局、两种写法、两份配置摆在一起看。
  把一个简单选择撑成对照表，也是一种打扰。
- **自由作答这条路由系统保证，不靠 agent 记得留。**靠自觉总有忘的时候，
  而那一次人就彻底没有出口了。

#### 一次请示长什么样

`request_approval` 的选项是**固定的两个**：**同意**、**不同意**。
外加自由作答——与 `ask` 是同一条保证。

| 人做了什么 | 算什么 |
|---|---|
| 点「同意」 | **准** |
| 点「不同意」 | **驳** |
| **自己写了一句** | 看那句话能不能明确读成准或驳；**读不出就是「有话说」**（性质四） |

**选项固定，是因为请示的问题形状本来就是固定的**：你准不准我做这件事。
它没有第三个答案——「你再想想」不是第三个答案，那是**没给答案**。

请示本身要说清五件事，缺一件人就签不下去：

| 要说清 | 说到什么程度 |
|---|---|
| **做什么** | **动作 + 对象，具体到人能凭它签字**：「把草稿 12/13/14 发给客户 A/B/C」，不是「发邮件」 |
| **为什么** | 一句因果 |
| **影响多大** | 涉及谁、什么、多少 |
| **撤不撤得回** | 可撤回 / 部分可撤回 / **不可撤回**——**人做判断时权重最大的一项** |
| **不准我会怎样** | 备选方案，或者「就此打住」。让人知道拒绝的代价 |

#### 必须成立的性质

**（一）不设上限，也不替人作答。**

没有超时，没有默认答案。「你不回我就当你同意」和「你不回我就当你拒绝」**同样不允许**。

道理在于：**等待期间世界里什么都没发生。**问询发生在动手之前，
没人占着资源，没有半成品悬在那儿。不花钱的等待没有理由设上限；
而一旦设了上限，就必须规定「到点算什么」——那就是系统替人作了答。

> **人没回答，和人回答了「随便」，是两回事。系统不能把前者变成后者。**

**（二）一次问全。**

每打断一次，人要放下手上的事、进入 agent 的上下文、做判断、再回去。
**这个代价与问题多少无关，只与打断次数有关。**所以一次调用可以带多个问题，
而挤牙膏式地连问三轮是产品缺陷，不是使用方式。

**（三）问的时候，什么都还没做。**

调用发生在**动手之前**。问的那一刻世界还是原样，所以人说「不行」不需要任何收拾。
反过来，先做了再问，那不叫请示，叫通知。

**（四）翻不出裁决，就不要翻。**

人的回答常常不落在「准」和「不准」上：「第二封改改语气再发」。
那既不是批准也不是拒绝，系统就把原话交给 agent，标明**人有话说但没给准驳**。

> **绝不替人合成一个裁决。**宁可让 agent 再问一轮，也不要猜一个。

agent 拿到这种回应，应当把话当作指导，调整之后**再请示一次**——
让人看见自己的话被听进去了。

**（五）同意留在会话里，不进权限设置。**

人点了「同意」，**确实留下了东西**。留在哪里，决定了这件事安不安全：

| 尺度 | 留下什么 | 谁能改 | 什么时候没 |
|---|---|---|---|
| **这一次** | 这次调用获准 | —— | 动作做完 |
| **这个会话** | **会话授权上下文**：「这件事，在这个会话里，用户点过头」 | `request_approval` 一次次累积出来 | **会话结束，一起没** |
| **长期** | [权限设置](../PF-002-assets-settings-and-permissions/design.md#52-设置与权限是资产的两种属性) | **只有人到设置里去改** | 人再去改 |

> **`request_approval` 只能动中间那一层。它碰不到第三层，一次都碰不到。**

这一层解决的是两个方向的问题：

- **往松的方向**：同一件事不必问第二遍。人批准过「清掉这个目录」，
  agent 接着干下去不该每一步都来敲门——**问得太勤，人就会开始不假思索地点同意**。
- **往紧的方向**：这笔授权**活不过这个会话**。换一个会话，一切从头来过。

而人若说「以后都这样吧」，**系统不得把它写进权限设置**。那句话原样交回给 agent，
由 agent 告诉人正式的授权入口在哪。

**一句顺口的话变成一条永久生效的规则，是这扇门最危险的失手**——
它的危险在于当事人不知道自己批准了什么，他以为自己只是在说这一次。

**要分清禁的是什么**：禁的是**系统替人解释**，不是禁止人给长期授权。

> **长期授权一直都可以给，只是必须由人明确地给。**

除了到设置页去改，人还可以**在一个标着后果的选项上明确选择**给出长期授权——
[PF-008 的系统拦截卡片就有这么一档](../PF-008-human-in-the-loop/design.md#52-那个判断函数)。
那不是升格，**那是他看着后果按下去的**。`request_approval` 这里没有这一档，
是因为它的选项固定为同意 / 不同意；**自由作答里的一句话，永远不作数**。

会话授权上下文**随运行实例注入**（[PF-004](../PF-004-agent-runtime-assembly-and-liveness/design.md)），
所以 **agent 在运行中感知得到它**：什么已经获准，它自己清楚，不必靠记忆也不必重复问。

**（六）放行不由任何一样东西单独决定。**

一个动作做不做得成，由**三样东西合起来**回答：

```text
     权限设置             会话授权上下文           会话运行模式
（跨会话，人设的）    （本会话，人点头攒的）    （这个会话怎么跑）
         └────────────────────┼────────────────────┘
                              ↓
                        这次放不放行
```

| 这一样 | 回答什么 | 活多久 | 归谁定义 |
|---|---|---|---|
| **权限设置** | 这**类**事，原则上准不准 | 跨会话，长期 | [PF-002](../PF-002-assets-settings-and-permissions/design.md#52-设置与权限是资产的两种属性) |
| **会话授权上下文** | 这**件**事，用户在这个会话里点过头没有 | **随会话结束** | **本节** |
| **会话运行模式** | 这个会话是每件事都问、照名单放行、还是全自动 | 一个会话 | **另有归属**（§8） |

**三者是组合关系，不是谁盖过谁。**这条同时推翻两个想当然的读法：
「请示获批了，所以系统就该放行」，以及它的反面「有权限设置了，所以请示没有意义」。
**两个都不对。**

必须守住的两条：

- **权限设置里明确禁止的，会话授权翻不了案。**否则任何禁止都能靠
  「让用户在会话里点个同意」绕过去，那权限设置就是摆设。
  尤其要想到：**会话里坐着的那个人，未必是设权限的那个人。**
- **拿不准的时候宁可再问一次。**「这次的动作算不算落在已获授权的范围内」
  不可能判得永远准。误判有两个方向：该放的没放，agent 多问一遍，人嫌烦；
  不该放的放了，**做了没有人批准过的事**。两者代价差着量级，所以**偏向多问**。

#### 什么时候不该敲这扇门

| 情形 | 为什么不该 |
|---|---|
| 自己查得到的事 | 那是偷懒。人会因此不再认真看问询 |
| 纯礼貌确认（「我可以开始了吗」） | 没有信息量的打断，纯消耗 |
| 权限设置本来就会拦下来的动作 | 那条路上系统自己会处理，不必先问一遍 |
| **这个会话里已经点过头的同一件事** | **会话授权上下文就是为此存在的**（性质五）。再问一遍，等于它没起作用 |

**唯一相反的一条**：计划变了却不说。**变了就是新的一件事，必须重新请示**——
人签的是当初那段文字，不是你后来想做的事。

**这份清单是产品性质，不是使用建议。**问得太多，人就会开始不假思索地点「同意」，
那时这扇门形同虚设——**而它看上去还在工作**。

#### 四个出口

| 出口 | 发生什么 |
|---|---|
| **人回了** | 拿到应答，继续 |
| **人取消这次问询** | 这一问作废，agent 知道不会有答案了 |
| **人叫停整个 run** | 按[被中断](../PF-006-tools-and-skills/design.md#67-用户可以中断而中断不是失败)处理，不是失败 |
| **会话走到终态** | 还悬着的问询一并清掉，不留孤儿 |

**没有第五个出口，尤其没有「等到点了」。**

#### 与 PF-006 等待态的关系

`Ask()` 的等待用的就是[那个原语](../PF-006-tools-and-skills/design.md#等待态)，不另造机制。
两者的区别在**发起方**：等待态是工具内部停下来等，`Ask()` 是 agent 自己决定要问。

但有一处必须分清：**PF-006 说等待态「等不到应答有上限」，
那条对 `Ask()` 不成立**——那条推导的前提是「一次执行不能永远占着资源」，
而 `Ask()` 的等待不占任何资源（性质一）。

> **上限不是等待态这个原语的属性，是每一个使用它的人的属性。**

处置见 [decisions.md 第四节](decisions.md#四已知的来源问题)。

### 6.12 `Cordis()`：通向系统自身的装配（**定义完整，本版不实现**）

| 命令 | 回答什么问题 |
|---|---|
| `list` | **有哪些面可以看**，各自能回答什么形状的问题 |
| `query` | **向某一个面提一个精确的问题**，拿回完整的契约 |

**这是最彻底的一扇门**：其余十一扇通向能力、世界或他者，
**这一扇通向 agent 赖以存在的那副骨架**。

**本版只定义、不实现。**理由是产品负责人的裁决。但边界现在就要定死——
否则将来会有人用别的形状把它做出来，而这扇门做错的代价比别的门大得多。

本节按 [DSH 的同名工具](interviews/2026-09-17-survey-of-harnesses.md#十一cordisdsh-的系统自省工具)完整复刻。

#### 为什么是「两条命令」而不是「一份报告」

一个念头是让它直接吐一份「当前系统长什么样」的总览。**不够用**，因为两种问法的
代价差得太远：

| 问法 | 想要什么 | 给全了会怎样 |
|---|---|---|
| **我现在大致是什么样** | 一眼看全，粗粒度 | —— |
| **某个服务的第三个方法，参数到底什么形状** | 一处的**完整契约** | 全系统的完整契约一次吐出，上下文当场爆掉 |

所以 `list` 给不收窄的概览，`query` 给收窄后的**完整**契约。
**这两条命令的关系就是「先看目录，再翻那一页」。**

#### 能看见什么

| 看得见 | 具体是什么 |
|---|---|
| **有哪些服务** | 各自提供什么方法、参数与返回是什么形状——**是签名，不是实现** |
| **有哪些插件活着** | 以及它们的**父子关系**：谁挂在谁下面，谁被谁带起来 |
| **注册了哪些工具** | 各自的参数形状。这与 [`Tools().inspect`](#61-tools通向任意非常驻工具) 看到的是同一件事的不同入口 |
| **本次会话动态装进来了什么** | 跑着跑着被装上的东西，**与装配时就在的分得开** |
| **有哪些事件** | 事件的名字与形状 |
| **界面那一侧有哪些位置可以贡献 UI** | 见下面「两侧」 |

#### 检视面是长出来的，不是画死的

这是这扇门**最要紧的一条设计**，也是它与「写一个大而全的系统信息接口」的分水岭：

> **能被看见的东西，由各个插件自己贡献。谁提供了一种能力，谁顺带贡献「怎么看它」。**

后果有两层：

- **检视面随系统生长**，不需要任何人维护一张总表——而总表一定会过期，
  且过期的时候没人发现。
- **`list` 的返回本身是动态的**：今天装了新东西，明天 `list` 就多一项。
  这正是[「完全动态」](../../../../AGENTS.md)在这扇门上的样子。

反过来也成立：**一个插件没有贡献检视面，它就是不透明的**。这不是缺陷，是它自己的选择，
而且这个选择本身看得见（它不出现在 `list` 里）。

#### 两侧

DSH 区分**宿主侧**与**界面侧**——后者是浏览器那一半，它能回答「页面上有哪些位置
可以放东西」。查询时要指明问的是哪一侧。

**我们第一版是单机系统，界面侧还不存在。**这个维度**形状保留、当下只有一侧**；
将来长出界面那一半时，不必回头改这扇门的形状。

界面侧还有一条自带的性质：**它要有一个连着的页面才答得上话**。页面没连上，
这一路就是[当下不可用](../PF-006-tools-and-skills/design.md#可用性)，
与任何设施给不了时一样——**不降级、不猜**。

#### 四条红线

DSH 把这四条写死在工具说明里，**我们照搬**：

| 红线 | 为什么 |
|---|---|
| **不能调用服务的方法** | 看得见签名，**调不动**。破了这条，这扇门就成了绕过全部工具与权限的万能通道 |
| **不能改配置** | 检视与配置是两件事。改动装配有它自己的入口与授权，**不能从「看得见」顺理成章长出「改得动」** |
| **不能执行它生成的代码** | 这扇门的产物是**知识**，不是动作。要执行，走 `Shell()` 或 `Tools()`，在那里接受该有的管束 |
| **看到的是自己那一份，不是整个部署** | 租户隔离在这扇门上同样成立。这是我们加的第四条——DSH 是单租户工具，没有这个问题 |

**前三条是 DSH 的原话，第四条是我们的处境逼出来的。**

#### 它为谁存在

DSH 把这个工具放在 **creator mode**：给**正在写插件的 agent** 用——
动手写之前，先看清运行时到底有什么、契约到底什么形状。

**这个用途比「自省」更具体，也更能解释它为什么值一个常驻槽位**：

> 一个能写插件的 agent，如果只能靠猜运行时有什么，写出来的东西就是碰运气。

而「我是怎么被装配出来的」这类自省问题，是同一个能力的另一种用法——
**同一扇门，两种用途，不拆成两个。**

#### 与「改动装配」的分界

DSH 把这条界画得很清楚：**检视归 `cordis`，持久的配置变更归另一个东西**
（它那边叫 Plugin Manager，管启用、停用、安装、移除）。

**我们照此划界，而且本版只做左边那一半。**

改动自己的构成是另一件事，归后续 topic。即便到那时，它也必须走授权——
**「看得见」与「改得动」之间那道墙，是这扇门存在的前提。**

## 七、取舍

| 选择 | 取的 | 舍的 |
|---|---|---|
| **十二个 meta 全部常驻** | agent 有确定的基本盘；门后的能力无上限 | 十二个槽位的固定成本，任何 agent 都得付 |
| **全部用多命令范式** | 上百个动作只占十二个位置 | agent 多一层「选命令」的心智负担；命令名要设计得自解释 |
| **`Files()` 与 `Shell()` 分开** | 编辑可靠、权限管得住、结果有形状 | 两扇门有部分重叠，会有人问「为什么不合并」 |
| **`Browser()` 与 `Computer()` 分开** | 网页操作快而稳，界面操作有兜底 | 同上 |
| **`TodoItems()` 逐条增删改，不做整份覆盖** | 每个动作的影响面就那一条，失手也只错一条 | 「一眼看全」要靠 `list` 而不是靠写的时候写全份 |
| **`Ask()` 复用等待态原语** | 不为它另造机制 | 要额外说明**上限那条对它不成立**，否则读者会照 PF-006 的字面给它加超时 |
| **`Ask()` 分成问与请示两个命令** | 「只对这一次有效」这条性质有地方挂 | 多一条命令；agent 要先判断自己处在哪一种状态 |
| **问询不设上限** | 系统永远不会替人作答 | 一个问询可以悬任意久，产品上要有别的办法让人知道有东西在等他 |
| **`Cordis()` 定义完整但不实现** | 照着能直接做，不留给将来即兴发挥 | 有一扇门写在设计里却用不了，读者会问何时交付 |
| **`Cordis()` 设想为只读** | 「看得见」与「改得动」之间隔着一道明确的墙 | 完全动态的最后一步本版没走完 |
| **检视面由插件自己贡献** | 检视面随系统生长，没有总表会过期 | 一个插件可以选择不透明，而系统不强制它交代自己 |
| **meta 不可禁用不可替换** | 动态性不可被剥夺；agent 认识自己的那双眼睛不会被换掉 | 租户失去了一项自定义能力，且**安全策略无法通过关掉 meta 来收紧** |

**最后一行值得多说一句**：收紧安全**不能靠关掉 meta**，只能靠
[执行环境](../PF-005-execution-environments-and-sandboxes/README.md)、
[权限](../PF-002-assets-settings-and-permissions/README.md)与装配清单。
这是刻意的——关掉门会让 agent 突然"不知道某件事存在"，而那种失明无法解释也无法申诉。

| **另有归属**（本 topic **依赖它、不定义它**） | **会话运行模式**（每次都问 / 白名单放行 / 全自动），以及切换它这个动作。它是[放行三元组](#611-ask通向人)的第三样，`Ask()` 依赖它存在；但**它是什么、怎么切换**，产品负责人已明确不在本 topic 讨论。它与 [PF-002 的工具级执行权限](../PF-002-assets-settings-and-permissions/design.md#七类资产)不是一回事——**一个是「这个工具默认怎么办」，一个是「这个会话现在整体多严」** |
| **run / 会话**那一块 | **会话授权上下文挂在会话对象上怎么承载**。本 topic 定义它的产品语义（是什么、怎么产生、什么时候没、和权限设置什么关系），**它在会话上的存放与生命周期归那边**——与 [PF-006 把工具执行运行时绑在 session 上](../PF-006-tools-and-skills/design.md#65-工具执行有自己的运行时绑定在-session-上)是同一个分寸 |
| 技术设计 | **怎么综合三样东西判出放不放行**。产品只定**由这三样合起来决定**，以及必须守住的两条（禁止翻不了案、拿不准就多问）；用什么办法判断，是实现的事 |
