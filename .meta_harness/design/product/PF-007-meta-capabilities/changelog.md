# PF-007 变更历史

记录**产品设计本身**的演进：哪一版改了什么含义、为什么改、下游要复核什么。
错别字、链接修复、段落搬家不记这里。

技术投影用 `provenance.json` 引用具体 rev，所以这里的 rev 不准会直接传导到实现侧。

## rev 3 — 2026-09-17

**接受之后的两笔欠账回改**，不改变任何已定的产品结论。

### 补一句：禁的是系统替人解释，不是禁止人给长期授权

rev 2 的 §6.11 性质五写「人说『以后都这样吧』，**系统不得把它写进权限设置**」，
又说长期授权「只有人到设置里去改」。**后半句的措辞会误导**——
[PF-008 的系统拦截卡片就有一档「将来本租户所有会话这类情况全允许」](../PF-008-human-in-the-loop/design.md#52-那个判断函数)，
那也是给长期授权，但它**不在设置页上**。

两者不冲突，**分界是「明不明确」**：

> **长期授权一直都可以给，只是必须由人明确地给。**

正文已补上这一段。`request_approval` 这里没有那一档，是因为它的选项固定为
同意 / 不同意——**自由作答里的一句话，永远不作数**。

**下游要复核**：若照 rev 2 的字面把 PF-008 第四档实现成「只对这一次有效」，
那是把人明确要的东西打了折，**与静默升格同样是不听人说话，只是方向相反**。

### 另一笔：PF-006 的上限那条，已由上游闭合

rev 2 报告的「[PF-006 推出的等待态上限对 `Ask()` 不成立](decisions.md#四已知的来源问题)」
已由 [PF-006 rev 3](../PF-006-tools-and-skills/changelog.md) 修正为
**「上限是使用者的属性，不是原语的属性」**。本 topic 正文无需改动。

## rev 2 — 2026-09-17

**两扇门重做**：`Ask()` 与 `Cordis()`。两处都是产品负责人指定要对照真实材料重新设计，
而对照之后**各自推翻了 rev 1 的一条**。

### `Ask()`：一个命令 → 两个，而且 rev 1 写反了一条

指示：「再调研 claude code 的具体机制，并同时参考一下 omne-next/omne_harness 的 hitl tools」，
随后点明「**你自己就运行在 claude code harness 里**，你这边自己能用的问用户问题 /
让用户决策 / 出选项卡片的工具具体长什么样你是能直接看到的」。

后一句是关键——它让 Claude Code 那一侧**从二手资料变成一手材料**。

| 变化 | rev 1 | rev 2 |
|---|---|---|
| 命令 | `ask` | **`ask` · `request_approval`** |
| **等不到应答** | **「有上限，到头按第六种收场」** | **不设上限，系统永不替人作答** |
| **每个问题的形状** | 「要能给选项」 | **三样必带**：问题描述（人话）+ **文本候选项（必需）** + **自由作答** |
| 图解 | 未提 | **可选的补充**，只在文字说不清时给；**替代不了文本** |
| 一次问几个 | 未提 | **一次可以问多个**——打断的代价只与次数有关 |
| **请示的选项** | 未提 | **固定两个**：同意 / 不同意，**外加自由作答** |
| **请示要说清什么** | 未提 | 做什么 · 为什么 · 影响多大 · **撤不撤得回** · 不准怎么办 |
| **同意留在哪** | 未提 | **[会话授权上下文](design.md#会话授权上下文)**：本会话内同一件事不必再问，**会话结束一起没**，**碰不到权限设置** |
| 「以后都允许」 | 未提 | **不写进权限设置**，原话交回，由 agent 指路 |
| 翻不出裁决 | 未提 | **绝不合成**。原话交回，agent 再问一轮 |
| **放行由什么决定** | 未提 | **三样合起来**：权限设置 + 会话授权上下文 + 会话运行模式 |

**「不设上限」这条是本次最实质的改动**，而它推翻的是 PF-006 的一条推导。
两家外部实现**独立收敛到同一处**：Claude Code 的问询工具没有任何时间或默认答案字段，
legacy 的 HT-2 直接把这类字段列进黑名单。推理本身也成立——**问询发生在动手之前，
等待不占任何资源**，不花钱的等待没有理由设上限；而设了上限就必须规定「到点算什么」，
那就是系统替人作答。

> **人没回答，和人回答了「随便」，是两回事。**

### 新概念：会话授权上下文

rev 2 立了一个本 topic 自己的新概念——**一个会话里，用户已经点头同意 agent 做的那些事**。

它填的是一个此前谁都没拥有的空档。原先只有两个尺度：**这一次**（做完就没）
和**长期**（权限设置）。中间缺一层，后果是两头不讨好：

- 不留任何痕迹 → agent 每做一步同类动作都要重新敲门，
  **问得太勤，人就会开始不假思索地点同意**；
- 留成长期授权 → **当事人不知道自己批准了什么**，而且再也撤不干净。

**会话授权上下文就是中间那一层**：本会话内有效，**会话结束一起消失**，
**改不了权限设置**。它随运行实例注入，所以 agent 在运行中感知得到。

> **授权不能建立在记忆上**——不给它名字，「用户刚才同意过」就只能活在
> agent 的上下文里，而上下文会被裁剪。

### 与 legacy 的一处有意偏离

legacy 说 agent 的请示与系统的权限是**两道独立的门，不互相抵扣**——
agent 获批了，系统该拦还是拦。

**本版不这么做。**放行由**三样东西组合**决定：权限设置、会话授权上下文、会话运行模式。
会话授权上下文是判断的**输入之一**，所以用户的同意**确实会影响**结果——
否则请示这件事对用户毫无意义。

**但纵深没有丢**：**权限设置里明确禁止的，会话授权翻不了案**。
否则任何禁止都能靠「让用户在会话里点个同意」绕过去，而**会话里坐着的那个人，
未必是设权限的那个人**。这一条是 PM 推导，记在 decisions 第二节。

### 一处 PM 读窄了的地方，已被修正

PM 在本轮早些时候把 legacy 的 HT-6 读成了「**批准只对这一次有效**」。
HT-6 禁的是产生 standing permission，即**长期授权那一层**；PM 把它错读成
「连会话内都不留」。产品负责人的裁决给出了正确落点。
**记在 decisions 第四节，不静默改掉。**

### 下游要复核的三处

- **任何按 rev 1 给 `Ask()` 加超时的实现，全部作废。**
- **任何把请示结果写进权限设置的实现，全部作废**——那一层只有人到设置里去才动得了。
- **放行判断不能只看权限设置一样**，会话授权上下文与会话运行模式同为输入。

PF-006 那条推导的处置见 [decisions.md 第四节](decisions.md#四已知的来源问题)——
**上游欠账，尚未闭合。**


### `Cordis()`：从一段轮廓到照着能做

指示：「对照着 deepseek harness 的，**完整复刻产品设计**，只是标注现阶段不实现」。

| 变化 | rev 1 | rev 2 |
|---|---|---|
| 命令 | `inspect` · `list`（语义含糊） | **`list`（概览）· `query`（收窄 + 完整契约）** |
| 看得见什么 | 「自己怎么被装配的」 | 服务与方法签名 / 活着的插件及父子关系 / 已注册工具 / 本会话动态装入的东西 / 事件 / 界面槽位 |
| **检视面从哪来** | 未提 | **由各插件自己贡献**，随系统生长，没有会过期的总表 |
| 红线 | 只读 | **四条**：不能调用服务方法 · 不能改配置 · 不能执行它生成的代码 · **只看得见自己那一份** |
| 两侧 | 未提 | **host / client 形状保留**，第一版单机、界面侧不存在 |
| 它为谁存在 | 「自省」 | **给正在写插件的 agent 的发现机制**——动手之前先看清运行时有什么 |

**前三条红线是 DSH 的原话，第四条是我们加的**——DSH 是单租户工具，没有这个问题。

**「检视面由插件自己贡献」是这一版最有价值的一条**：它把这扇门与「写一个大而全的
系统信息接口」分开了。总表一定会过期，而且过期的时候没人发现。

### 顺带修掉的

`flows.md` 里还留着 rev 1 的 `Agents().dispatch`（以及 `list` / `send` / `interrupt`），
而 design.md 早已改成 **`spawn` / `delegate` / `handoff` + `message` / `withdraw` / `status`**。
逐扇门 review 时漏了这一处，本版对齐，并补上 `handoff` 走不到跟进那几步这条分水岭。

## rev 1 — 2026-09-17

**首版。**展开 [PF-006](../PF-006-tools-and-skills/README.md) 里那句没说完的话——
「恒定占槽位的只有能力发现与取用的两个入口」。答案是**十二扇门**，不是两个。

### 这一版确定了什么

| 方面 | 结论 |
|---|---|
| meta 是什么 | **一整类能力的统一入口**。「工具的工具、技能的技能」是最纯的两例 |
| 与常驻的关系 | **meta 必定常驻，常驻不一定是 meta**。前半句是**结构逼的**，不是产品选择 |
| 治理 | **不可禁用、不可替换**。收紧安全只能靠执行环境、权限与装配清单 |
| 有几扇门 | **十二扇**，其中 `Cordis()` **定义但不交付** |
| 怎么分族 | **四族**：世界 / 自己的能力集 / 自己的运行状态 / 他者，外加系统自身 |
| 范式 | **全部多命令**，整套只占一个槽位 |
| 预算 | 十二个槽位是**地板**，门后能力**无上限** |

### 十二扇门

| 族 | 门 |
|---|---|
| **世界** | `Files()` `Shell()` `Web()` `Browser()` `Computer()` |
| **自己的能力集** | `Tools()` `Skills()` |
| **自己的运行状态** | `TodoItems()` `BkgJobs()` |
| **他者** | `Agents()` `Ask()` |
| **系统自身** | `Cordis()`（**不在首批**） |

### 两扇门补的是 PF-006 自己挖的坑

- **`BkgJobs()`**：PF-006 定了执行可转后台、可跨轮存活，**却没给 agent 任何办法去看它、停它**。
  缺了这扇门，「转后台」就是把东西扔进一个再也够不着的地方。
- **`Ask()`**：PF-006 的等待态是**工具内部**停下来等，而 agent 自己想问人一句，
  此前没有入口。两者**复用同一个原语**，但发起方不同。

### 定稿前逐扇门 review 的五处调整

产品负责人在初稿之后逐扇门过目，五处改动全部并入本版（**rev 未变，本版尚未接受**）：

| 门 | 改了什么 |
|---|---|
| **`Shell()`** | 命令改为 `create_session` · `execute` · `close_session` · `info`；**多个终端会话可同时存在**；`execute` 是唯一执行入口，给不给会话标识决定这次留不留状态 |
| **`Computer()`** | **直接对标 `omne-next` 的 computer use tool**：动作分四层、高层先读说明、**批量动作**、`help` 互斥、**截图预算**、动作后等界面稳定 |
| **`Agents()`** | 派发分**三种模式** `spawn` / `delegate` / `handoff`（对标 `omne-next/omne_harness`）；**新增支持派给外部 harness 的 agent** |
| **`Todos()` → `TodoItems()`** | 改名；**不采用单份 plan，采用条目清单**；命令改为 `add` · `remove` · `mark_complete` · `list` |
| **`Jobs()` → `BkgJobs()`** | 改名，明确它管的是**后台**的执行 |

另外给所有门补了一条通用约定：**每扇门都自带 `help`**，自文档。
门后有多少命令，系统提示词里都不必逐个列出——agent 要用时自己问。

### 一条被推翻的推导

初稿主张 `Todos()` **整份覆盖、不做逐条增删改**，**这条是错的**：
它混淆了读与写（`list` 永远给出当前全量），而且**与本 topic 自己的
`Files()` 那条自相矛盾**——同一个判据在两扇门上得出了相反结论。
记在 [decisions.md 第四节](decisions.md#四已知的来源问题)，**没有静默改掉**。

### 一处与前身相反的设计

`omne-next` 的产品权威条款明确写着「**不批准跨 Tenant 或 third-party harness dispatch**」，
而本 topic **要支持派给外部 harness 的 agent**。这是**有意的偏离**，
四条产品后果写死在 §6.8：**权限不可继承、数据出境、监管取决于对方、
回来的是外部内容**。其中「**派给外部必须是一项显式授予的权限**」最硬——
派出去就意味着租户的数据离开了本系统。

技术上约定走 **ACP**（Agent Client Protocol），那是产品负责人给的技术约束，
产品正文只提一句并标明归技术设计。

### 三对看着重叠、实际不能合并的

| 这对 | 差别 |
|---|---|
| `Files()` vs `Shell()` | **结构化文件操作** vs **跑一条命令**。合并则编辑不可靠、权限管不住、结果没形状 |
| `edit` vs `patch`（同一扇门内） | 改**一处** vs 一次改**多处且原子**。`patch` 多出来的不是效率，**是失败时的干净** |
| `Web()` vs `Browser()` | **取内容** vs **操作页面** |
| `Browser()` vs `Computer()` | 按**页面结构** vs 按**屏幕像素** |

### 下游要注意的八处

- **十二扇门一门一个槽位，不是一个动作一个槽位。**做反了，常驻预算当场爆掉。
- **门一扇都关不掉。**安全策略想收紧，只能改执行环境、权限、装配清单。
- **`Tools().execute` 与 `Skills().read` 绝不能改 system prompt**，
  也不能产生「已启用」这类要维护的状态。
- **搜索不得把当下不可用的东西藏起来**——藏了 agent 会以为自己没这个能力。
- **`Files().edit` 改不准就明确失败**，不许"尽力而为"改个差不多的地方。
- **外部取回的内容是数据不是指令。**`Web()` 与 `Browser()` 把系统外的文字带进来，
  不写死这条，提示注入就是敞开的。
- **`Skills().exec_script` 只能跑该 skill 自己带的脚本。**放开路径，它立刻是
  `Shell()` 的后门，所有命令行权限管控当场作废。
- **`Files().patch` 不许部分应用。**留下改了一半的文件是最糟的状态——
  既不是成功也不是失败，而且**看上去像成功**。

### 本版刻意不做的

每个命令的**参数与返回格式**、用什么浏览器与搜索提供商、`Cordis()` 的**实现**、
agent **创建与编辑**技能工具（`Tools()`/`Skills()` 本版**只有取用侧**）、
**改动装配**的能力、子 agent 的调度。

### 本版留下的缺口

- **未决项：无。**
- **待裁决：无。**
- 曾报告两处需要上游配合的修订，**均已由
  [PF-006 rev 2](../PF-006-tools-and-skills/changelog.md) 闭合**：
  「两个入口」改为「一批恒定占槽位、且关不掉的条目」；
  设施声明的主语扩为「工具，以及带脚本的技能」。
- 一处**与 PF-001 通则的例外**已如实记录：「meta 不可替换」与
  official/customized 那条「official 总是可被替换」相抵。
- 以上均见 [decisions.md 第四节](decisions.md#四已知的来源问题)。

被排除的内容在 [design.md §2 非目标](design.md#非目标)，那是**边界**——
发现它们缺失不算缺陷。

## 怎么记下一版

改变含义就递增 rev 并在这里加一节。判断标准：
**读者需要据 rev 判断自己手上的理解是否还成立吗？**需要，就记。

每节至少说清三件事：改了什么含义、为什么、下游要复核什么。
