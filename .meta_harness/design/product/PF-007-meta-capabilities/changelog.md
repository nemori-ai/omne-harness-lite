# PF-007 变更历史

记录**产品设计本身**的演进：哪一版改了什么含义、为什么改、下游要复核什么。
错别字、链接修复、段落搬家不记这里。

技术投影用 `provenance.json` 引用具体 rev，所以这里的 rev 不准会直接传导到实现侧。

## rev 13 — 2026-09-21

**放行判断从「三样组合」展开成「四步有序」，并划清权限作用在门还是命令上。**
依据：[两条裁决](decisions.md#一拍板记录)。

### 一、[§5.6 新增](design.md#56-一次放行判断走四步)：一次放行判断走四步

rev 2 定的是**三样东西组合决定放行**，**但没说次序**。本版补上：
**① 结构化取交集（任一层明确禁止即终局）→ ② 要不要确认 → ③ 拿决策记录算 → ④ 看会话运行模式。**

**三处是刻意的**：语义化授权排在「明确禁止」之后，**所以它结构上就翻不了案**——
[那条已定的规则](design.md#611-ask通向人)在这个次序下**自动成立**；
`bypass-permissions` **只跳过第 ④ 步**，**跳不过第 ①步**；
`auto_permission` 那一支**闭环**——问人的答案落成新的决策记录，下次在第 ③ 步就算得出来。

### 二、[§5.7 新增](design.md#57-权限能关掉一条命令关不掉一扇门)：一条红线的精确化

rev 2 起写着「**meta 不可禁用、不可替换**」。**本版把它说准：**

> **不可禁用说的是那扇门，不是门后的每一条命令。**

**权限照常作用在命令这一级。**已定的例子：会话运行模式是
[`never`](../PF-015-session-lifecycle-and-ownership/design.md#会话运行模式) 时，
`Ask().request_approval` **不可用**，而 **`Ask()` 这扇门还在**、`ask` 照常能用。

**关掉之后 agent 看得见它存在、用不了、以及为什么**——走[当下可用性](../PF-006-tools-and-skills/design.md#可用性)那套，**不藏起来**。
**这不是放宽，是把「禁用」落到正确的粒度上**：门一扇都关不掉这条**一个字没改**。

### 三、[§5.8 新增](design.md#58-子不得宽于父)：子不得宽于父

`子实际拿到 = 父当前拥有 ∩ 子请求`。**会话运行模式同样往下传**——
父是 `never`，子的 `request_approval` 一并不可用；**但子的 `Ask()` 不禁**。

**取「交集」这一种是有前提的**，[记在 decisions](decisions.md#三家挡子超过父的办法不同为什么我们能取最宽的那种)：
另一家用「子恒为 never」是因为它没有「子卡住了说得出来」的通路，**而我们有**。

## rev 12 — 2026-09-21

**「只保守」定成授权的原则，[D-2](decisions.md#三待裁决) 闭合。**
依据：[产品负责人裁决](decisions.md#一拍板记录)——
「**表达不清按最窄（仅下一次动作允许的含义），这是授权的原则，只保守。**」

### 改了什么

| 位置 | 内容 |
|---|---|
| [§4「作用域」段](design.md#会话授权上下文) | 补一句：**他没说清的时候，按最窄的那一档算** |
| [§6.11 性质五结尾](design.md#611-ask通向人) | 原写「这是一条待裁决，本版不替它填默认值」，**现在填上了**：表达不清按「仅下一次动作允许」算。并写明**「只保守」比一条消歧规则大**——它是整个授权面的取向，**拿不准就往限制更多的那边落** |

### 为什么这条比看上去重要

**rev 11 把红线从「用嘴说的不作数」改成了「系统不替人解释」**，
但那句话只挡住了一半——**它没说「解释不出来的时候怎么办」**。
不给答案，实现者会各自填一个，而**填得宽的那一版不会报错**，只会在某天多做一件没人批准的事。

**rev 12 给的答案是不对称的，而这个不对称就是理由：**
**少给了，用户再说一句就补上；多给了，事已经做完了。**

## rev 11 — 2026-09-21

**授权模型重定：用嘴说的话算数，而且能说得出作用域。**
依据：[产品负责人裁决](decisions.md#一拍板记录)，原话逐字见
[PF-015 decisions](../PF-015-session-lifecycle-and-ownership/decisions.md#2026-09-21--授权的来源撤回与作用域)。

### 一、[§4 会话授权上下文](design.md#会话授权上下文)整节重写

**它的形状变了**：从「用户已经点头同意的那些事」——一个**结论集合**——
变成「用户关于授权表达过的全部意思，按先后顺序排着的那一份」——**一份只追加的流水**。
**「此刻准不准」不再存在任何地方，每次现算。**

| 位置 | 原先 | 现在 |
|---|---|---|
| 它是什么 | 同意过的事的集合 | **按序追加的表达流水**；撤回也是往后加一笔，不擦除 |
| **什么时候没** | **随会话结束一起消失** | **不会没。**[会话归档不丢](../PF-015-session-lifecycle-and-ownership/design.md#67-归档不动授权)，撤销归档后原样还在——**它是数据** |
| 来源 | 只有 `request_approval` 攒出来的 | **不挑来源**：点「同意」算、**自由作答里写的算、agent 没问而用户主动说的也算** |
| 撤回 | **本版不提供逐笔撤销**，要收回就结束会话 | **两种撤回**：界面上 revoke、**用嘴说撤回**。下一次求值立刻生效 |
| 作用域 | 固定就是「本会话」 | **三档**：这一次 / 本会话 / **全局（本租户下未来所有会话）**，**由用户自己表达** |

### 二、被推翻的那条红线

rev 9 写着「**自由作答里的一句话，永远不作数**」，理由是防止
**系统替人把一句顺口的话解释成永久授权**。

**产品负责人推翻了「不作数」这半句**，保留了另外半句。现在守的是：

> **系统不替人解释他的意思，只负责准确理解。**

差别在**谁作的主**：人说「以后都这样吧」，系统认成一笔全局授权，**是理解**；
人说「这次可以」，系统认成「这类事以后都可以」，**是替他作主，不允许**。

**这条不变量现在唯一的着力点变成了「表达不清时按哪一档算」**，
而那是一条[新开的待裁决 D-2](decisions.md#三待裁决)——**本版不替它填默认值**。

### 三、[§6.11 性质五](design.md#611-ask通向人)重写、性质六的表改两处

- 性质五标题从「同意留在会话里，不进权限设置」改为「**人说的话算数，作用域由他自己定**」；
  三层尺度表改为**三档作用域表**。
- 新增一条边界：**表达得出不等于生效**——一个作用域能不能落地，
  仍按[他自己的身份与权限](../PF-001-identity-scope-and-agent-constraints/design.md#62-三种合成语义)判。
  **会话里坐着的那个人，未必是设权限的那个人**，这条老告诫在新模型下更要紧。
- 性质六三元组表：「活多久」一列从「随会话结束」改为「**与会话同寿，归档不丢**」；
  新增一句**三样都不是结论，结论每次现算**。

## rev 10 — 2026-09-21

**规则一从单向改成双向：子 agent 可以向派出它的那个 agent 发消息。**
依据：[UL-D-4 裁决 7](../../ubiquitous_language/decisions.md#ul-d-4--主会话与子会话--2026-09-21)。

产品负责人放宽了这条约束，理由是子那一侧有它自己要说的话——**干到一半需要确认一件事实、
澄清一句需求**。不给这条通路，它只能靠猜，或者把半成品当成品交回来。

### 一、改了什么

| 位置 | 原先 | 现在 |
|---|---|---|
| [规则一](design.md#先说谁能给谁发消息这是两条独立的规则) | 「agent 可以给**任何它派发出去的** agent 发消息」，**只管一个方向** | 「agent **与**它派发出去的 agent 之间**可以互发消息**」，**两个方向都通** |
| 情形表 | **四**种，第二行「`spawn`/`delegate` 出去的 → 派发者」是**不能** | **五**种，那一行改为**能**；**新增一行写明兄弟之间不能**（彼此无派发关系、也都无独立主会话身份） |
| [三种派发模式五维表](design.md#派发有三种模式) | 一维叫「**能不能向派发者发消息**」，`spawn`/`delegate` 为「不能」 | 改为「**能跟谁通信**」。放宽后三者在这一维都是「能」，**它不再是分水岭**；真正的区别是**能跟谁通**——前两种只能跟派发者，`handoff` 还落在规则二里 |
| §6.8 那一小节 | 标题「**「不能发消息」不等于「不能说话」**」，靠「不能发消息」反衬报告的必要性 | 改名 [**「报告与消息是两样东西」**](design.md#报告与消息是两样东西)。**区分本身不变**，只是不再需要那个反衬 |
| 规则二的「**会话仍活跃**」 | 无定义 | **= 未被归档**。没有删除会话的概念，也就没有「会话结束」这回事；**归档的精确语义归 PF-015** |

### 二、[§9.2](design.md#92-报告之后派发者再发一条消息子拿什么回应) 闭合了一半

那一节原本记着一个「**现有正文无解**」的真缺口：子交完报告之后收到消息，
两条出路（发消息 / 再交报告）**都被封死**。**通路那一半就此打开。**

**剩下的一半仍在**：那条回应**算不算子会话里新的一次运行**，它与
[会话内单活跃](../../ubiquitous_language/terms/agent-runtime-loop.md#ul-single-active-execution--会话内单活跃--single-active-execution)
对不对得上——**同一个子会话上的两次派发能不能同时在跑**。那仍归 PF-015。

它原先列的三个依赖里，另外两个已经有了：**会话之间的父子关系**由
[UL-D-4](../../ubiquitous_language/decisions.md#ul-d-4--主会话与子会话--2026-09-21) 定义；
**「会话有哪几种终态」这个问题本身被取消了**——没有终态，只有归档。

### 三、为什么是改规则一，不是新立一条

**裁决只说「子 → 父可以发消息」，没说改哪条规则**，两种落法产品长相一样，所以由 PM 定。
推理链记在 [UL-D-4「一处 PM 自己定的」](../../ubiquitous_language/decisions.md#ul-d-4--主会话与子会话--2026-09-21)，
要点是：新立一条会引入第三个判据（父子会话关系），**而它在当前外延上与规则一完全重合**；
改规则一则不会让任何不该通的通了——**兄弟之间仍然不通**。
**⚠️ 若将来出现「有派发关系但不构成父子会话」的第四种派发模式，两种表述会分叉，届时须重新裁决。**

### 四、下游要复核什么

| 谁 | 复核什么 |
|---|---|
| **统一语言 [UL-inter-agent-communication](../../ubiquitous_language/terms/interaction-and-dispatch.md#ul-inter-agent-communication--agent-间通信--inter-agent-communication)** | 规则一的覆盖面、「活跃」的定义、新增的注意 ⑤（兄弟与隔代都不通）——**已同步** |
| **[UL-dispatch-report](../../ubiquitous_language/terms/interaction-and-dispatch.md#ul-dispatch-report--派发报告--dispatch-report)** | 它的「注意」原先靠「不能向派发者发消息」立论——**已改写为报告与消息的分工** |
| **[PF-008](../PF-008-human-in-the-loop/README.md)** | 判断函数的输入不受影响；但**子 agent 现在能主动向上发消息**，与「请示」是两条不同的路——**本版未改 PF-008，若两者在产品上会被混淆需另开** |
| **PF-015（讨论中）** | 归档语义、同一子会话上的并发派发、规则一在归档后还成不成立 |

## rev 9 — 2026-09-20

**填上「生命周期受派发者控制，控制的是哪一样」——它不必再等 PF-015 了。**
依据：[UL-D-3](../../ubiquitous_language/decisions.md#ul-d-3--runtime-与活体--2026-09-20)。

**rev 8 把这一格记成缺口并指给了还没开题的 PF-015**，
同时写明不定它的代价：「实现方会挑最省事的那一种——报告一到就把子会话收掉，
那样裁决要的『后续仍可发消息』当场作废，而且不会报错。」

**UL-D-3 把两件事分开之后，答案只剩一个**：
产品负责人重申**会话是纯数据、治理性质的概念**（不是活物），
并立下**凡以 `runtime` 为中心词的对象都是协程**。于是——

| 派发者控制的 | 派发者停了 |
|---|---|
| 子 agent 那个 [agent runtime](../PF-012-agent-loop-and-run/design.md#agent-runtime)（协程） | **跟着停** |
| 子会话本身（数据） | **还在**，它没有「被停」这回事 |

**[五维表](design.md#派发有三种模式)那一行的措辞不变**，只是「控制」二字从此有了确定的所指。
**新增一处限定**：会话被终止 / 归档 / 回收时
[会递归带走名下一切](../PF-012-agent-loop-and-run/design.md#613-取消跟着宿主走)，
而 **`handoff` 出去的不在递归范围内**——它有独立主会话身份（PM 推导，链在 UL-D-3）。

**[§9 的缺口清单少一条](design.md#九未决项)**，剩下两样仍归 PF-015。

## rev 8 — 2026-09-20

**补一句一直没说出口的话：`Ask()` 的等待不可转后台。**
**这是局部修订**：`Ask()` 的两个命令、五条性质、十三扇门**一格未动**。

**缺这一句的后果很具体**，是 [PF-014](../PF-014-inbound-intake-and-queueing/README.md) 起草时撞出来的：

> rev 7 写了 `Ask()` 的等待「[不占任何资源](design.md#611-ask通向人)」「上限那条对它不成立」，
> **但没写「不可转后台」**。读者照[普通工具等待态](../../ubiquitous_language/terms/execution-and-outcome.md#ul-tool-wait-state--工具等待态--tool-wait-state)去推，
> 会推出**相反的结论**——于是
> [用户插队时它会被转后台而不是被中断](../PF-014-inbound-intake-and-queueing/design.md#54-插队停在哪就怎么办)，
> **那个问题就永远悬在那儿，而没有任何人会再看它一眼**。

**理由本来就在性质一里**：「不占资源」的前提**就是它停在那儿**。
[转后台意味着这一次执行以占位算齐、loop 接着往下走](../PF-006-tools-and-skills/design.md#66-前台后台-与-等待态是两个维度)，
而那时 agent 得**在没有这个答案的情况下继续**——**而它刚刚说自己卡住了**。

**顺带写明它在插队时的处置**：按「**人拒绝回复**」，
与[运行等待态上那些卡片同一个语义](../PF-008-human-in-the-loop/design.md#61-永远等着系统不替人作答)。
**这不破性质一**——那一条禁的是**系统替人作答**，而插队是**人自己作了答**。

**下游要复核**：任何把 `Ask()` 的等待当成普通工具等待态、因而允许它转后台的实现。

## rev 7 — 2026-09-20

**一条裁决，落在 `Agents()` 上；外加一条登记给别人的需求。**
**这是局部修订**：三种模式的五维表**一格未动**，两条通信规则**一字未改**。

### 落的那条裁决：报告终结的是这次派发，不是那个会话

产品负责人 2026-09-20：**`spawn` / `delegate` 出去的那两种 subagent，
完成答复不意味着它的会话到达终结状态，后续 master agent 依然可以对它们发送消息。**

| | rev 6 的字面 | rev 7 点明的 |
|---|---|---|
| **报告终结什么** | 「**终结这次派发**」 | 同一句话，**照字面读**：终结的是**这一次派发**，**那个会话没有因此落进任何终态** |
| **报告之后还能不能发消息** | **没说** | **能**——而这**不是新立的一条规则**，是[规则一](design.md#先说谁能给谁发消息这是两条独立的规则)本来就蕴含的：**规则一不带时间限定**，它只问「是不是我派的」 |

> **第二行是本版唯一容易被误读的地方**：没有新规则，**只是点明旧规则在报告之后依然成立**。

**不点破的后果是具体的**：「报告终结这次派发」会被顺手做成
「**报告一到就把那个会话收掉**」——裁决要的追问当场发不出去，
**而且不报错**，只表现为「消息发了，再没有下文」。

### 顺带看得见的一道线：谁产生子会话

裁决给了 subagent 的精确界定，**它在 `spawn` / `delegate` / `handoff` 之间划了一道
rev 6 没画出来的线**：

> **subagent = 会话是当前会话之子会话的那些 agent 会话。**
> **`handoff` 出去的不算**（它有独立主会话身份），**第三方 harness 的会话不算。**

| | 它的会话是什么 |
|---|---|
| `spawn` / `delegate` | **当前会话的子会话** |
| `handoff` · 外部 harness | **不是** |

**这是同一条分水岭的另一个侧面**（`spawn`/`delegate` 与 `handoff` 只差「是不是独立主会话」），
**不是第二条分界**。正文只把线画出来，**「子会话」本身不在本 topic 展开**。

### 登记一条需求，指向 PF-015

同一条裁决**明确指定不在本 topic 设计**的那部分，记进
[§8 明确不拥有](design.md#八边界与依赖)：

> **会话之间的关联关系（session tree），以及 master agent 感知、管理自己全部 subagent 的能力。**

**这里只登记，不设计。**顺带写明一处容易被顶替的地方：
**`list_dispatched` 顶不上这条需求**——它回答「我派出去过哪些」这本历史账，
而需求要的是「我现在有哪些子会话、各自怎么样、我拿它们能怎么办」。

### 本版新开一项未决

**PF-007 的未决项从一项变成两项。**

> **[§9.2](design.md#92-报告之后派发者再发一条消息子拿什么回应)：报告之后，派发者再发一条消息，子拿什么回应？**

**这是裁决直接暴露出来的真缺口**：它**不能向派发者发消息**（没有独立主会话身份），
**而报告只有一次且已经用掉**。

**PM 的倾向已写进正文，并标明是倾向不是结论**——
**一次派发 ≈ 那个子会话里的一次运行**，会话跨多次派发存活。
它不动任何既有结论，**但坐实它要等 PF-015 定下会话之间的关系、会话的终态，
并与[会话内单活跃](../../ubiquitous_language/terms/agent-runtime-loop.md#ul-single-active-execution--会话内单活跃--single-active-execution)对齐**。

**同一处还记了两笔连带，本版都不填**：规则一没说对方会话结束之后还成不成立；
**五维表里「生命周期受派发者控制」控制的是哪一样**（**该格的既有结论不动**，说清归 PF-015）。

### 三处参照，不构成依据

查了三家怎么给「交付完成之后那个东西还在不在」划界。
**只作参照：本版的裁决来自产品负责人，[§9.2](design.md#92-报告之后派发者再发一条消息子拿什么回应) 的倾向来自本 topic 自己的约束，都不建立在它们之上。**

| 看到的（事实） | 与本版的关系 |
|---|---|
| **Claude Code**：内建的一次性 subagent **不返回 id、无法续谈**；其余 subagent **完成后返回 agent id**，父 agent **用它发消息就能让那个 subagent 接着干，历史全保留** | **裁决要的正是可续的那一种。**顺带说明一件事：**能续的前提是它有身份**——这与 PF-015 那条「master 要感知、管理自己全部 subagent」是同一件事的两面 |
| **A2A**：任务进终态后不可重启，**后续追问是在同一个 contextId 下新建一个任务** | **容器长存、交付分次**，与 PM 倾向形状相同 |
| **ACP**：一个会话跨多个 prompt turn 存活，**每个 turn 以 stop reason 收口** | 同上 |

**三家在「容器长存」上一致，在「下一次交互算新的一次还是接着上一次」上不一致**
（A2A 新建任务，Claude Code 续同一个）——**那恰好就是 §9.2 要 PF-015 回答的问题**，
**所以本版没有照抄任何一家**。

**来源、观察与推测的区分、以及「看过但没采纳的」，随本次交接报给产品负责人**；
按调研纪律**不进 `decisions.md` 的拍板记录**。

## rev 6 — 2026-09-18

**`Agents()` 的派发模式重新设计。**产品负责人先给了**两条通信规则**垫底，
再用**五个维度**逐一定死三种模式。**rev 1 写的三处含义被推翻。**

### 先有两条规则，三种模式才讲得清

| | 规则 |
|---|---|
| **一** | **agent 可以给任何它派发出去的 agent 发消息**——不论哪种模式 |
| **二** | **具备独立主会话身份的、会话仍活跃的、同属一个租户的 agents，相互之间可以通信** |

**两条的覆盖面不一样**：规则一**只管派发者往外发**，不问对方身份；
规则二**是双向的，而且不要求有派发关系**——**两个素不相识的 agent 也能通**。

### 三种模式，五个维度

| | **`spawn`** | **`delegate`** | **`handoff`** |
|---|---|---|---|
| **是不是独立主会话** | 否 | 否 | **是** |
| **上下文怎么组装** | **继承当前会话的** | **接受一段 instruction** | **接受一段 handoff 说明**（本质也是 instruction） |
| **生命周期受谁控制** | 派发者 | 派发者 | **不受派发者控制** |
| **派发动作什么时候结束** | **进等待态**直到报告或失败 | 同左 | **确认会话建没建起来即结束** |
| **能不能向派发者发消息** | 不能（只能提交报告） | 不能 | **能** |

### 推翻了 rev 1 的三处

| | **rev 1 写的** | **rev 6 定的** | 照旧版实现会怎样 |
|---|---|---|---|
| **`spawn`** | 「自己的一个克隆，**独立会话**」 | **不是独立主会话**；**上下文继承当前会话的** | 会被建成一个独立会话——**那其实是 `handoff`** |
| **`handoff`** | 「**不能**再向派发者说话，交出去就是交出去了」 | **能向派发者发消息** | 交接之后两边**断了联系**，而那正是协作最需要的一条线 |
| **`delegate`** | 「**保留监管**」是它与另外两个的分水岭 | **这条分界不存在**——规则一让派发者能给**任何**派出去的发消息 | `delegate` 被赋予一个别人没有的特权，**另外两种的可观测性被无端削掉** |

> **三处的共同根子**：PM 当时按「派完还剩什么关系」**这一个维度**去排三种模式，
> 把耦合强弱想象成一条从强到弱的直线，于是「独立」「失联」「监管」被顺手捆在了一起。
> **产品负责人给的是五个正交维度**，三种模式的取值组合根本不落在一条直线上——
> **`spawn` 在「独立与否」上最弱，在「带多少上下文」上却最强。**
> **维度没拆开之前排出来的顺序，看上去自洽，其实是编的。**记在
> [decisions 第四节](decisions.md#四已知的来源问题)，**没有静默改掉**。

### 本版点破的三处，都不是新规定，是把给定的推完整

- **两处分水岭各自只有一条。**`spawn` 与 `delegate` 只差「**它带着什么开始干活**」；
  `spawn`/`delegate` 与 `handoff` 只差「**是不是独立主会话**」，
  而**另外三个维度的差别全是这一条的后果**（生命周期不受控、用户能直接找它、能回头发消息）。
- **报告 ≠ 消息。**产品负责人在「不能向派发者发消息」后面加的那个括号
  （「**只能是提交报告**」）是关键：**报告终结这次派发，消息什么都不终结**；
  **报告只有一次，消息来回多少次都行**。不点破，那条规则会被读成「它干完了也没地方说」。
- **`spawn`/`delegate` 用的正是 [PF-006 的等待态原语](../PF-006-tools-and-skills/design.md#等待态)，`handoff` 没用。**
  由此掉出一条现成的组合：前两种的等待可能很久，
  [转后台那个维度](../PF-006-tools-and-skills/design.md#66-前台后台-与-等待态是两个维度)正好用在这里。

### 命令表跟着改了两处

| 命令 | 改了什么 |
|---|---|
| **`message`** | 从「给子发消息」改为「**给一个还活着的 agent 发消息，按那两条规则判定**」——**它不只对派出去的子成立**。且**发不出去时要说清是哪一条不满足**（不是我派的？没有主会话身份？会话已结束？不同租户？），**不能只回一句「发不出去」** |
| **`withdraw`** | 明写 **`handoff` 撤不回**。**这不是缺陷，是它的定义**——**一个能被撤回的 `handoff`，那是 `delegate`** |

### 本版新开一项待裁决

**PF-007 从「未决项：无」变成有一项。**

> **D-1：`spawn` 的「继承当前会话的上下文」，是共享同一份[会话日志](../PF-012-agent-loop-and-run/design.md#会话日志)，还是派发那一刻复制一份？**

**PM 没有倾向，两种都自洽**，而它们**对「消息机制在 `spawn` 下有没有用」给出相反答案**：
共享的话派发者后来说的话子自己就看得见，规则一那条通路几乎用不上；复制的话那条通路是必需的。
**实现方会自己挑一种，而挑错了不会报错**——只表现为「子 agent 有时像是知道后来的事，有时又不知道」。
见 [§9.1](design.md#91-spawn-的继承当前会话的上下文是共享还是复制)。

### 下游要复核

- **任何按 rev 1 把 `spawn` 实现成独立会话的，全部作废**——那个形状现在叫 `handoff`。
- **任何在 `handoff` 之后切断双向通路的实现，全部作废。**
- **任何只给 `delegate` 开监管、不给另外两种的实现，全部作废。**
- **任何允许 `withdraw` 作用于 `handoff` 的实现，全部作废。**
- **跨 agent 通信的判定不能只看「是不是我派的」**——规则二这条路与派发关系无关。
- **`spawn` 的上下文语义在 D-1 裁决之前不要定死**，定死了将来改动的是行为不是参数。

## rev 5 — 2026-09-18

**补第十三扇门：`Engram()`。**门数从十二变成十三，族数从四变成五。

> 产品负责人的定位：**如果说 `Cordis()` 提供了 agent 动自己「行动 / 拓扑结构」的元能力，
> `Engram()` 提供的是 agent 动自己「知识结构」的元能力。**

### 它的分量与 `Cordis()` 不一样，这一条最要紧

| | 本版做到哪 |
|---|---|
| **`Cordis()`** | **定义完整，只是不实现**——边界危险，形状现在就要定死 |
| **`Engram()`** | **只占位**——**连命令集都不定** |

产品负责人明确：**不作实现交付要求，只是占位声明未来系统的终局 meta capabilities 里会有它。**

> **所以 [§6.13](design.md#613-engram通向自己的知识结构占位声明不作实现交付要求) 刻意写得短。**
> **多写一个字，都是在替一件还没设计的事情做决定。**

**本版为它定死的只有三件事**：**它存在**、**它属于哪一族**、**它动的是知识结构而不是别的**。

### 族表改了：「系统自身」→「自己的底层结构」

**原来那一族只有 `Cordis()`，族名叫「系统自身」。**
`Engram()` 碰的不是系统骨架，是 agent 自己的知识——**那个族名容不下它**。

| 族 | 作用于 | 有哪些 |
|---|---|---|
| **自己的底层结构** | agent **赖以成立**的那两套结构 | `Cordis()`（行动 / 拓扑）· `Engram()`（知识） |

**两个都不在首批，这不是巧合：**

> **动自己赖以成立的东西，是最彻底的能力，也是最该缓的。**

### 顺带修掉一处旧的不一致

**§5.1 的标题与正文写「四族」，表里却列了五行**，正文也描述了五个族的风险——
**这是加 `Cordis()` 那一版留下的**：加了一行，数目没跟着改。**现已统一为五族。**

> **`acceptance.md` 里那句「装配方额外标一个常驻 → 槽位变成十二个」是对的，不要动它。**
> 那一节说的是**首批**（十一扇门），十一 + 一 = 十二。
> **PM 一度把它当成旧错误改成了十四，已改回**——
> **门数说的是终局，槽位数说的是首批，两个视角不能混。**

### 一条判据的第三次现身

参考 `omne-selfound/omne_engram` 时看到一条：**没人查过 ≠ 可以删**——
失效、归档、删除必须来自显式决定。

**这与 [PF-010 刚定的「不给模型看不等于可以删」](../PF-010-context-management-and-assembly/design.md#不给模型看不等于可以删)是同一条判据。**

> 同一条判据在**上下文压缩**与**知识治理**两个毫不相干的地方各自成立——
> **这通常说明它不是为某一处编出来的。**

**记在 §6.13 备用，但它不构成本版的设计**——本版只占位。

### 下游要复核

- 任何按「十二扇门 / 十二个槽位」算常驻预算的东西——**地板现在是十三**；
- 任何按「四族」组织风险评估的东西；
- **任何开始实现 `Engram()` 的东西**——**它现在没有可实施的定义**，
  动手前必须先回来做完那一节。

## rev 4 — 2026-09-18

**`Tools()` 加一个命令：`read_result`。**

[PF-006 rev 4](../PF-006-tools-and-skills/changelog.md) 定了结果太大时卸载——
消息里留一条占位提示，原始结果存着。**取回它的入口在这里**：

| 命令 | 回答什么问题 |
|---|---|
| **`read_result`** | **那条占位提示背后的原始结果，给我看**（分页） |

**必须分页**，否则等于把刚卸下去的东西原样搬回来，卸载当场作废。

**为什么归 `Tools()` 而不是 `Files()`**：被卸载的结果**不是文件系统里的文件**，
它是**某一次工具调用的产物**。按调用去找它才自然；按路径去找，则要求 agent
知道一个它本不必知道的存放规则。

> **这是「那次调用返回了什么」的追问，不是「某个路径上有什么」的读取。**

于是同一扇门管这次调用的**参数**（`inspect`）、**执行**（`execute`）、
以及**它返回了什么**（`read_result`）。

## rev 2 — 2026-09-17

**两扇门重做**：`Ask()` 与 `Cordis()`。两处都是产品负责人指定要对照真实材料重新设计，
而对照之后**各自推翻了 rev 1 的一条**。

### `Ask()`：一个命令 → 两个，而且 rev 1 写反了一条

指示：「再调研 claude code 的具体机制，并同时参考一下 omne-next/omne_harness 的 hitl tools」，
随后点明「**你自己就运行在 claude code harness 里**，你这边自己能用的问用户问题 /
让用户决策 / 出选项卡片的工具具体长什么样你是能直接看到的」。

后一句是关键——它让 Claude Code 那一侧**从二手资料变成一手材料**。

| 变化 | rev 1 | rev 2 |
|---|---|---|
| 命令 | `ask` | **`ask` · `request_approval`** |
| **等不到应答** | **「有上限，到头按第六种收场」** | **不设上限，系统永不替人作答** |
| **每个问题的形状** | 「要能给选项」 | **三样必带**：问题描述（人话）+ **文本候选项（必需）** + **自由作答** |
| 图解 | 未提 | **可选的补充**，只在文字说不清时给；**替代不了文本** |
| 一次问几个 | 未提 | **一次可以问多个**——打断的代价只与次数有关 |
| **请示的选项** | 未提 | **固定两个**：同意 / 不同意，**外加自由作答** |
| **请示要说清什么** | 未提 | 做什么 · 为什么 · 影响多大 · **撤不撤得回** · 不准怎么办 |
| **同意留在哪** | 未提 | **[会话授权上下文](design.md#会话授权上下文)**：本会话内同一件事不必再问，**会话结束一起没**，**碰不到权限设置** |
| 「以后都允许」 | 未提 | **不写进权限设置**，原话交回，由 agent 指路 |
| 翻不出裁决 | 未提 | **绝不合成**。原话交回，agent 再问一轮 |
| **放行由什么决定** | 未提 | **三样合起来**：权限设置 + 会话授权上下文 + 会话运行模式 |

**「不设上限」这条是本次最实质的改动**，而它推翻的是 PF-006 的一条推导。
两家外部实现**独立收敛到同一处**：Claude Code 的问询工具没有任何时间或默认答案字段，
legacy 的 HT-2 直接把这类字段列进黑名单。推理本身也成立——**问询发生在动手之前，
等待不占任何资源**，不花钱的等待没有理由设上限；而设了上限就必须规定「到点算什么」，
那就是系统替人作答。

> **人没回答，和人回答了「随便」，是两回事。**

### 新概念：会话授权上下文

rev 2 立了一个本 topic 自己的新概念——**一个会话里，用户已经点头同意 agent 做的那些事**。

它填的是一个此前谁都没拥有的空档。原先只有两个尺度：**这一次**（做完就没）
和**长期**（权限设置）。中间缺一层，后果是两头不讨好：

- 不留任何痕迹 → agent 每做一步同类动作都要重新敲门，
  **问得太勤，人就会开始不假思索地点同意**；
- 留成长期授权 → **当事人不知道自己批准了什么**，而且再也撤不干净。

**会话授权上下文就是中间那一层**：本会话内有效，**会话结束一起消失**，
**改不了权限设置**。它随运行实例注入，所以 agent 在运行中感知得到。

> **授权不能建立在记忆上**——不给它名字，「用户刚才同意过」就只能活在
> agent 的上下文里，而上下文会被裁剪。

### 与 legacy 的一处有意偏离

legacy 说 agent 的请示与系统的权限是**两道独立的门，不互相抵扣**——
agent 获批了，系统该拦还是拦。

**本版不这么做。**放行由**三样东西组合**决定：权限设置、会话授权上下文、会话运行模式。
会话授权上下文是判断的**输入之一**，所以用户的同意**确实会影响**结果——
否则请示这件事对用户毫无意义。

**但纵深没有丢**：**权限设置里明确禁止的，会话授权翻不了案**。
否则任何禁止都能靠「让用户在会话里点个同意」绕过去，而**会话里坐着的那个人，
未必是设权限的那个人**。这一条是 PM 推导，记在 decisions 第二节。

### 一处 PM 读窄了的地方，已被修正

PM 在本轮早些时候把 legacy 的 HT-6 读成了「**批准只对这一次有效**」。
HT-6 禁的是产生 standing permission，即**长期授权那一层**；PM 把它错读成
「连会话内都不留」。产品负责人的裁决给出了正确落点。
**记在 decisions 第四节，不静默改掉。**

### 下游要复核的三处

- **任何按 rev 1 给 `Ask()` 加超时的实现，全部作废。**
- **任何把请示结果写进权限设置的实现，全部作废**——那一层只有人到设置里去才动得了。
- **放行判断不能只看权限设置一样**，会话授权上下文与会话运行模式同为输入。

PF-006 那条推导的处置见 [decisions.md 第四节](decisions.md#四已知的来源问题)——
**上游欠账，尚未闭合。**


### `Cordis()`：从一段轮廓到照着能做

指示：「对照着 deepseek harness 的，**完整复刻产品设计**，只是标注现阶段不实现」。

| 变化 | rev 1 | rev 2 |
|---|---|---|
| 命令 | `inspect` · `list`（语义含糊） | **`list`（概览）· `query`（收窄 + 完整契约）** |
| 看得见什么 | 「自己怎么被装配的」 | 服务与方法签名 / 活着的插件及父子关系 / 已注册工具 / 本会话动态装入的东西 / 事件 / 界面槽位 |
| **检视面从哪来** | 未提 | **由各插件自己贡献**，随系统生长，没有会过期的总表 |
| 红线 | 只读 | **四条**：不能调用服务方法 · 不能改配置 · 不能执行它生成的代码 · **只看得见自己那一份** |
| 两侧 | 未提 | **host / client 形状保留**，第一版单机、界面侧不存在 |
| 它为谁存在 | 「自省」 | **给正在写插件的 agent 的发现机制**——动手之前先看清运行时有什么 |

**前三条红线是 DSH 的原话，第四条是我们加的**——DSH 是单租户工具，没有这个问题。

**「检视面由插件自己贡献」是这一版最有价值的一条**：它把这扇门与「写一个大而全的
系统信息接口」分开了。总表一定会过期，而且过期的时候没人发现。

### 顺带修掉的

`flows.md` 里还留着 rev 1 的 `Agents().dispatch`（以及 `list` / `send` / `interrupt`），
而 design.md 早已改成 **`spawn` / `delegate` / `handoff` + `message` / `withdraw` / `status`**。
逐扇门 review 时漏了这一处，本版对齐，并补上 `handoff` 走不到跟进那几步这条分水岭。

## rev 1 — 2026-09-17

**首版。**展开 [PF-006](../PF-006-tools-and-skills/README.md) 里那句没说完的话——
「恒定占槽位的只有能力发现与取用的两个入口」。答案是**十三扇门**，不是两个。

### 这一版确定了什么

| 方面 | 结论 |
|---|---|
| meta 是什么 | **一整类能力的统一入口**。「工具的工具、技能的技能」是最纯的两例 |
| 与常驻的关系 | **meta 必定常驻，常驻不一定是 meta**。前半句是**结构逼的**，不是产品选择 |
| 治理 | **不可禁用、不可替换**。收紧安全只能靠执行环境、权限与装配清单 |
| 有几扇门 | **十三扇**，其中 `Cordis()` **定义但不交付** |
| 怎么分族 | **四族**：世界 / 自己的能力集 / 自己的运行状态 / 他者，外加系统自身 |
| 范式 | **全部多命令**，整套只占一个槽位 |
| 预算 | 十三个槽位是**地板**，门后能力**无上限** |

### 十三扇门

| 族 | 门 |
|---|---|
| **世界** | `Files()` `Shell()` `Web()` `Browser()` `Computer()` |
| **自己的能力集** | `Tools()` `Skills()` |
| **自己的运行状态** | `TodoItems()` `BkgJobs()` |
| **他者** | `Agents()` `Ask()` |
| **系统自身** | `Cordis()`（**不在首批**） |

### 两扇门补的是 PF-006 自己挖的坑

- **`BkgJobs()`**：PF-006 定了执行可转后台、可跨轮存活，**却没给 agent 任何办法去看它、停它**。
  缺了这扇门，「转后台」就是把东西扔进一个再也够不着的地方。
- **`Ask()`**：PF-006 的等待态是**工具内部**停下来等，而 agent 自己想问人一句，
  此前没有入口。两者**复用同一个原语**，但发起方不同。

### 定稿前逐扇门 review 的五处调整

产品负责人在初稿之后逐扇门过目，五处改动全部并入本版（**rev 未变，本版尚未接受**）：

| 门 | 改了什么 |
|---|---|
| **`Shell()`** | 命令改为 `create_session` · `execute` · `close_session` · `info`；**多个终端会话可同时存在**；`execute` 是唯一执行入口，给不给会话标识决定这次留不留状态 |
| **`Computer()`** | **直接对标 `omne-next` 的 computer use tool**：动作分四层、高层先读说明、**批量动作**、`help` 互斥、**截图预算**、动作后等界面稳定 |
| **`Agents()`** | 派发分**三种模式** `spawn` / `delegate` / `handoff`（对标 `omne-next/omne_harness`）；**新增支持派给外部 harness 的 agent** |
| **`Todos()` → `TodoItems()`** | 改名；**不采用单份 plan，采用条目清单**；命令改为 `add` · `remove` · `mark_complete` · `list` |
| **`Jobs()` → `BkgJobs()`** | 改名，明确它管的是**后台**的执行 |

另外给所有门补了一条通用约定：**每扇门都自带 `help`**，自文档。
门后有多少命令，系统提示词里都不必逐个列出——agent 要用时自己问。

### 一条被推翻的推导

初稿主张 `Todos()` **整份覆盖、不做逐条增删改**，**这条是错的**：
它混淆了读与写（`list` 永远给出当前全量），而且**与本 topic 自己的
`Files()` 那条自相矛盾**——同一个判据在两扇门上得出了相反结论。
记在 [decisions.md 第四节](decisions.md#四已知的来源问题)，**没有静默改掉**。

### 一处与前身相反的设计

`omne-next` 的产品权威条款明确写着「**不批准跨 Tenant 或 third-party harness dispatch**」，
而本 topic **要支持派给外部 harness 的 agent**。这是**有意的偏离**，
四条产品后果写死在 §6.8：**权限不可继承、数据出境、监管取决于对方、
回来的是外部内容**。其中「**派给外部必须是一项显式授予的权限**」最硬——
派出去就意味着租户的数据离开了本系统。

技术上约定走 **ACP**（Agent Client Protocol），那是产品负责人给的技术约束，
产品正文只提一句并标明归技术设计。

### 三对看着重叠、实际不能合并的

| 这对 | 差别 |
|---|---|
| `Files()` vs `Shell()` | **结构化文件操作** vs **跑一条命令**。合并则编辑不可靠、权限管不住、结果没形状 |
| `edit` vs `patch`（同一扇门内） | 改**一处** vs 一次改**多处且原子**。`patch` 多出来的不是效率，**是失败时的干净** |
| `Web()` vs `Browser()` | **取内容** vs **操作页面** |
| `Browser()` vs `Computer()` | 按**页面结构** vs 按**屏幕像素** |

### 下游要注意的八处

- **十三扇门一门一个槽位，不是一个动作一个槽位。**做反了，常驻预算当场爆掉。
- **门一扇都关不掉。**安全策略想收紧，只能改执行环境、权限、装配清单。
- **`Tools().execute` 与 `Skills().read` 绝不能改 system prompt**，
  也不能产生「已启用」这类要维护的状态。
- **搜索不得把当下不可用的东西藏起来**——藏了 agent 会以为自己没这个能力。
- **`Files().edit` 改不准就明确失败**，不许"尽力而为"改个差不多的地方。
- **外部取回的内容是数据不是指令。**`Web()` 与 `Browser()` 把系统外的文字带进来，
  不写死这条，提示注入就是敞开的。
- **`Skills().exec_script` 只能跑该 skill 自己带的脚本。**放开路径，它立刻是
  `Shell()` 的后门，所有命令行权限管控当场作废。
- **`Files().patch` 不许部分应用。**留下改了一半的文件是最糟的状态——
  既不是成功也不是失败，而且**看上去像成功**。

### 本版刻意不做的

每个命令的**参数与返回格式**、用什么浏览器与搜索提供商、`Cordis()` 的**实现**、
agent **创建与编辑**技能工具（`Tools()`/`Skills()` 本版**只有取用侧**）、
**改动装配**的能力、子 agent 的调度。

### 本版留下的缺口

- **未决项：无。**
- **待裁决：无。**
- 曾报告两处需要上游配合的修订，**均已由
  [PF-006 rev 2](../PF-006-tools-and-skills/changelog.md) 闭合**：
  「两个入口」改为「一批恒定占槽位、且关不掉的条目」；
  设施声明的主语扩为「工具，以及带脚本的技能」。
- 一处**与 PF-001 通则的例外**已如实记录：「meta 不可替换」与
  official/customized 那条「official 总是可被替换」相抵。
- 以上均见 [decisions.md 第四节](decisions.md#四已知的来源问题)。

被排除的内容在 [design.md §2 非目标](design.md#非目标)，那是**边界**——
发现它们缺失不算缺陷。

## 怎么记下一版

改变含义就递增 rev 并在这里加一节。判断标准：
**读者需要据 rev 判断自己手上的理解是否还成立吗？**需要，就记。

每节至少说清三件事：改了什么含义、为什么、下游要复核什么。
