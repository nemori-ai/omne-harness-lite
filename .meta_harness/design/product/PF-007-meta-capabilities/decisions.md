## 二、PM 推导

从已拍板内容推出的判断，附可核对的推理链。

| 结论 | 从哪几条推出 | 推理 |
|---|---|---|
| **meta 的定义要写成「一整类能力的统一入口」** | 「工具的工具、技能的技能」+ 必需集里有 `Shell()` `Computer()` `Web()` `Browser()` | 后四个**作用于世界**，不作用于能力集，按字面的「工具的工具」套不进去。能同时容下 `Tools()` 与 `Shell()` 的读法只有一种：**它们都是一族动作的入口**。「工具的工具、技能的技能」是这个定义最纯的两个例子。**「全都是 multiple command tool 范式」这条裁决正好印证**——多命令工具的本质就是一族命令共用一个入口 |
| **「meta 必定常驻」是结构逼出来的，不是产品选择** | 「meta 必定常驻」+ [PF-006 的常驻机制](../PF-006-tools-and-skills/design.md#常驻) | 够到非常驻能力的**唯一途径就是 meta**。若 meta 自己也不常驻，就永远够不着它——自指的闭环必须有不动点。**裁决说的「必定」在这里得到了解释，而不只是被复述** |
| **「不可禁用不可替换」与「必定常驻」是同一件事的两面** | 两条裁决 | 常驻保证门开着，不可禁用保证没人能关上它。**关掉一扇门等于门后一整类能力凭空消失**——这与「被禁用的能力 agent 仍然知道它存在」（[PF-004 的禁用](../PF-004-agent-runtime-assembly-and-liveness/design.md#63-三类变化三种传播)）性质不同，后者可解释，前者是失明 |
| **收紧安全不能靠关掉 meta** | 上一条 | 既然门关不掉，安全只能落在执行环境、权限与装配清单上。**这是代价，必须写出口**，否则安全负责人会找不到抓手 |
| **十三扇门按作用对象分五族** | 十三个的构成本身 | 分族不是为了好看：**五族的风险完全不同**——世界族碰外部效果，能力族碰自己的构成，状态族只碰自己，他者族占用别人的时间，**底层结构族碰的是 agent 赖以成立的东西**。不分族，「哪些门危险」就无从谈起 |
| **`handoff` 能向派发者发消息，不是单独规定的一条** | 两条通信规则 + `handoff` 是独立主会话 | 它**落进了[规则二](design.md#先说谁能给谁发消息这是两条独立的规则)的适用范围**（独立主会话 + 活跃 + 同租户）。**产品负责人自己就是这么给的**——他在「生命周期不受控制」后面加了括号「**因为是独立主会话，因此这个会话可以接受用户的消息**」。**PM 把这条推完整**：`handoff` 与另外两种的三个差别（生命周期不受控、用户能直接找它、能回头发消息）**全都是「有没有独立主会话身份」这一条的后果**。**分水岭只有一条，不是三条** |
| **`spawn` 与 `delegate` 的分水岭只有一条：它带着什么开始干活** | 五个维度的对照 | 两者在**另外四个维度上完全相同**，只差「上下文怎么组装」。所以：**`spawn` 带着我知道的一切**（适合「同一件事分身去做」，来龙去脉交代不过来），**`delegate` 只带着我交代的那段话**（适合「另一件事交出去」）。**`delegate` 的上下文隔离是用处不是限制**——继承一份几万字的上下文要付钱，**而很多活根本用不着那些背景** |
| **「不能向派发者发消息」不等于「它干完了没人知道」，报告与消息是两样东西** | 「不能向派发者发消息（**只能是提交报告**）」这句的括号 | 产品负责人特意加了那个括号。**报告终结这次派发**（等待态结束、工具调用返回），**消息什么都不终结**；报告**只有一次**，消息来回多少次都行。**不点破这层，那条规则会被读成「它干完了也没地方说」**——而实际正相反 |
| **`spawn` / `delegate` 用了[等待态原语](../PF-006-tools-and-skills/design.md#等待态)，`handoff` 没用** | 「进入等待态直到返回报告或失败」vs「确认创建情况后即结束」 | 前两种正是 PF-006 那个原语的用法；`handoff` 是普通的同步返回。**由此还掉出一条可用的组合**：前两种的等待可能很久，而[前台/后台那个维度](../PF-006-tools-and-skills/design.md#66-前台后台-与-等待态是两个维度)正好用在这里——**派发者可以把这次执行转后台，自己先干别的**，报告回来时以提醒的形式到达 |
| **`withdraw` 对 `handoff` 不成立** | 「生命周期不受派发者控制」 | 撤回就是控制生命周期。**`handoff` 的不可撤回不是缺陷，是它的定义**——**一个能被撤回的 `handoff`，那是 `delegate`** |
| **`message` 发不出去时要说清是哪一条不满足** | 两条规则各有条件 | 不是我派的？没有主会话身份？会话已经结束了？不同租户？**四种原因的处理方式完全不同**——只回一句「发不出去」，agent 无从判断该换个人、该等一等，还是压根这条路不存在 |
| **`Cordis()` 与 `Engram()` 同属一族，而且族名不能再叫「系统自身」** | `Engram()` 那条裁决里的定位对仗 | 产品负责人把两者并列成了**同一个形状**——「动自己 X 结构」：一个是**行动 / 拓扑**，一个是**知识**。而 `Engram()` 碰的**不是系统骨架**，是 agent 自己的知识，所以原来那个族名容不下它。改称**「自己的底层结构」**，作用于**agent 赖以成立的那两套结构** |
| **这一族的两个都不在首批，不是巧合** | 两条裁决各自的「不交付」 | **动自己赖以成立的东西，是最彻底的能力，也是最该缓的。**其余四族碰的都是「拿来用的东西」，这一族碰的是「自己成立的前提」 |
| **`Engram()` 这一节要刻意写得短** | 「不作实现交付要求」「只是占位声明」 | 与 `Cordis()` 的「定义完整只是不实现」**程度不同**：那边边界危险、形状现在就要定死；**这边连命令集都不该定**——**多写一个字，都是在替一件还没设计的事情做决定**。本版只定死三件事：**它存在、它属于哪一族、它动的是知识结构而不是别的** |
| **`omne_engram` 的四条性质与本项目已有判据同调，值得记下备用** | 查阅参考系统 | ①**它不裁决 agent 该相信什么**——与 [`Cordis()` 四条红线](design.md#四条红线)同性质（这扇门的产物是知识的组织方式，不是结论）；②**不主动推送、不观察潜在需求**——十三扇门全都是这样，**它是门不是后台服务**；③**没人查过 ≠ 可以删**——**与 [PF-010「不给模型看不等于可以删」](../PF-010-context-management-and-assembly/design.md#不给模型看不等于可以删)是同一条判据的又一次现身**；④**可以给「结构怎么演化」立约束，违反时明确失败**——与 [`patch` 的原子性](design.md#55-patch-的原子性是产品性质不是实现细节)同调。**第三条的复用值得单说**：同一条判据在**上下文压缩**与**知识治理**两个毫不相干的地方各自成立，**这通常说明它不是为某一处编出来的** |
| **十三个槽位是预算的地板** | 「必定常驻」+ [多命令只占一个槽位](../PF-002-assets-settings-and-permissions/design.md#八类资产) | 十三扇门 = 十三个固定成本。但门后能力无上限，所以**常驻预算的正确用法是把钱花在门上**。这条是 [PF-006 常驻机制](../PF-006-tools-and-skills/design.md#常驻)在本 topic 的直接后果 |
| **`BkgJobs()` 是 PF-006 挖的坑，必须补** | [PF-006 §6.6](../PF-006-tools-and-skills/design.md#66-前台后台-与-等待态是两个维度) | 那里定了执行可以转后台、可跨轮存活，**却没给 agent 任何办法去看它、停它**。缺了这扇门，「转后台」就是把东西扔进一个再也够不着的地方。**调研的 DSH 有 jobs、Claude Code 有 BashOutput/KillShell，七家里没有一家把后台做成单向的** |
| **`Ask()` 与 PF-006 的等待态是同一原语、不同发起方** | [PF-006 的等待态](../PF-006-tools-and-skills/design.md#等待态) | 等待态是**工具内部**停下来等，`Ask()` 是 **agent 自己决定要问**。两者都是「停下等一个形状确定的应答」，因此**复用同一个原语，不另造机制**；但方向不同，不能互相顶替 |
| **`Ask()` 要能给选项** | 「问人」这件事本身 | 开放式发问把判断的全部负担推回给人。给出选项与各自的后果，人只需要做选择。这与 `product-design` skill 的「怎么说话」对 PM 提问的要求是同一条道理 |
| **`Ask()` 要有 `request_approval` 这第二个命令** | 调研：[legacy 的 HITL 契约](interviews/2026-09-17-survey-of-harnesses.md#十hitl问人与请示)是 `ask_user` + `request_approval` 两个工具 | 「我缺个输入」与「我要动手了，你准不准」**形状不同**：前者开放、拿到之后接着想，后者封闭、拿到之后才动手。更要紧的是**审批有一条问询没有的性质——它会在会话里留下一笔**；合成一个命令，那条性质没地方挂。Claude Code 只有前者，因为它把审批交给了权限系统弹窗；**我们的 agent 需要能主动就名单之外的事请示**，那是它没有而我们要有的 |
| **问询不设上限，系统永不替人作答** | legacy [HT-2](interviews/2026-09-17-survey-of-harnesses.md#十hitl问人与请示) 明文黑名单；Claude Code 的问询工具**同样没有任何时间或默认答案字段** | **两家独立收敛到同一条，这是强证据。**推理本身也成立：问询发生在动手之前，**等待期间没有任何东西被占着**——不占资源的等待没有理由设上限。而一旦设了上限就必须规定「到点算什么」，那就是系统替人作了答。「人没回答」与「人回答了随便」是两回事 |
| **一次问全** | legacy HT-4「一轮至多停驻一次」；Claude Code 一次调用可带 1–4 个问题 | 打断的代价**与问题多少无关，只与打断次数有关**——每次都要人放下手上的事、进入 agent 的上下文、再回去。所以工具要支持一次带多个问题，而挤牙膏式连问是产品缺陷 |
| **自由作答这条路由系统保证，不靠 agent 记得留** | Claude Code：`Other` 由系统自动提供，且**明文要求 agent 不要自己加**；产品负责人裁决亦明列「允许人自由输入自己的答复」 | legacy 侧同源——`suggested_replies`「只是提示，人可自由作答，不是枚举约束」。**关键在于由谁兑现**：靠 agent 自觉总有忘的时候，而那一次人就被困在几个都不对的答案里 |
| **候选项的文本必需、图解可选** | 产品负责人裁决；参考 Claude Code 的 `preview`（等宽渲染，有它时切换为左右并排） | 图解的产品价值真实：**有些差别文字说不清**（两种布局、两种写法、两份配置），描述再准也不如让人看一眼。但它**只能是补充**——只给图的选项，人没法引用、没法复述，**读屏的人直接被挡在门外**。同时**文字够用时不要给图**，把简单选择撑成对照表也是打扰 |
| **同意不得静默升格为长期授权** | legacy [HT-6](interviews/2026-09-17-survey-of-harnesses.md#十hitl问人与请示) + 产品负责人裁决 | 一句顺口的「以后都这样吧」如果变成长期授权，**当事人根本不知道自己批准了什么**，而且再也撤不干净。长期授权只能从[设置与权限](../PF-002-assets-settings-and-permissions/design.md#52-设置与权限是资产的两种属性)走，那里有人看得见、改得掉。**注意这条禁的是第三层，不是第二层**——同意留在会话里是被允许的，写进设置不行 |
| **会话授权上下文只增不减，本版不提供逐笔撤销** | 「随会话结束一起消失」+ 最小设计 | 要收回给出去的同意，**结束会话**即可——那是个人人都懂、且一定有效的动作。多一个「撤销某一笔」，就多一处**「以为撤了其实没撤」**的可能，而这种误解在授权这件事上代价极高 |
| **权限设置里明确禁止的，会话授权翻不了案** | 三者组合 + [PF-001 的租户与成员](../PF-001-identity-scope-and-agent-constraints/design.md) | 否则任何禁止都能靠「让用户在会话里点个同意」绕过去，权限设置就成了摆设。**更要紧的是：会话里坐着的那个人，未必是设权限的那个人**——让一个普通成员点一下就越过组织的禁止，是明显的越权。**这条是 PM 推导；产品负责人若认为分类模型应当有权翻案，需要另行裁决** |
| **拿不准就再问一次** | 「这件事算不算落在已获授权的范围内」不是精确匹配，是判断 | 判断必然有误差，而两个方向的代价不对称：该放的没放，agent 多问一遍，人嫌烦；不该放的放了，**做了没有人批准过的事**。所以**偏向多问** |
| **翻不出裁决就不要翻** | legacy [HT-7](interviews/2026-09-17-survey-of-harnesses.md#十hitl问人与请示)「绝不合成 verdict」 | 人的回答常常不落在准/驳上（「第二封改改语气再发」）。**替人合成一个裁决等于伪造签字。**宁可让 agent 带着这句话再请示一轮——那还顺带让人看见自己的话被听进去了 |
| **放行由三样东西组合决定，而不是「两道互不抵扣的门」** | 产品负责人裁决（**组合**关系）；legacy §3.1 是「两道独立的门，不互相抵扣」 | **这是与 legacy 的一处有意偏离。**legacy 那两道门互不影响——agent 获批了系统照样拦，那样**用户的同意其实不起作用**。产品负责人给的是**组合**：会话授权上下文是放行判断的**输入之一**，所以同意**确实会影响**结果。这更说得通——否则请示这件事对用户毫无意义。**但纵深并没有丢**：权限设置里明确禁止的仍然翻不了案（见下一条） |
| **要写出「什么时候不该敲这扇门」** | 两家都有这份负面清单 | 它不是使用建议而是**产品性质**：问得太多，人就会开始不假思索地点同意，**那时这扇门形同虚设，而它看上去还在工作**。这种失效比报错危险得多 |
| **`Files()` 与 `Shell()` 必须分开** | 调研：七家**没有一家**让文件操作都走 shell | 三条实打实的理由：**编辑不可靠**（改文件要精确到行，跑命令做不到）、**权限管不住**（命令是黑盒，无从判断它动了什么）、**结果没有形状**（回来一坨文本） |
| **`Files().write` 与 `edit` 必须是两个命令** | 上一条 | 整份覆盖与局部修改**失手的代价差一个量级**。合成一个，「只改一行」与「重写整个文件」在接口上分不出来 |
| **`Browser()` 与 `Computer()` 必须分开** | 两者都在必需集里 | 一个按**页面结构**定位，一个按**屏幕像素**。只留 Computer，网页操作退化成截图点坐标；只留 Browser，浏览器之外的界面全碰不了 |
| **`Web()` 与 `Browser()` 必须分开** | 同上 | 一个**取内容**，一个**操作页面**。读一篇文章要开浏览器则慢而脆；填表登录用「取内容」根本做不到 |
| **`Tools()` 必须有 `inspect` 这一步** | [PF-006 的常驻机制](../PF-006-tools-and-skills/design.md#常驻) + 调研（legacy 与 DSH 都是三步链） | 非常驻工具的**参数格式同样不在系统提示词里**，而那往往比说明文字还长——**省下的大头正是它**。不给 inspect，agent 只能猜着调 |
| **搜索不得把当下不可用的东西藏起来** | [PF-006 的替换件](../PF-006-tools-and-skills/design.md#替换件) | 藏起来 agent 会以为自己没这个能力，而实际只是暂时用不了。**「知道有、知道现在用不了」正是替换件那条规则的用意** |
| ~~**`Todos().write` 整份覆盖，不做逐条增删改**~~ **这条推导是错的，已被产品负责人推翻** | ~~调研：各家都是整份写~~ | **错在混淆了读与写**：逐条改**不会**让「当前是什么」有多个答案——`list` 永远给出当前全量。而「一眼看全」是**读**的能力，不必靠「写的时候写全份」来保证。更要命的是它**与本 topic 自己的另一条自相矛盾**：[`Files()` 的 `write`/`edit` 分开](../PF-007-meta-capabilities/design.md#63-files通向文件系统)论证的正是「整份覆盖与局部修改失手代价不同」。详见第四节 |
| **`TodoItems()` 不跨会话** | 它作用于「这次在做什么」 | 跨会话继承的是目标不是计划，那是另一个对象（调研中 DSH 的 goals 是分开的） |
| **`Agents()` 派出去的结果走工具执行那一套** | [PF-006 §6.5](../PF-006-tools-and-skills/design.md#65-工具执行有自己的运行时绑定在-session-上) | 子 agent 的一次派发在产品上就是一次长执行：可转后台、可中断、绑 session。**不为它另立一套生命周期** |
| **子 agent 的成本算发起方的租户，不随层级漂移** | [PF-001 的成本按租户归属](../PF-001-identity-scope-and-agent-constraints/design.md) | 否则派得越深账越算不清 |
| **`exec_script` 归 `Skills()`，不归 `Shell()` 或某个代码执行的门** | 裁决 +「skill 可以带资源文件」+「读取不等于运行它带的脚本」（[PF-002](../PF-002-assets-settings-and-permissions/design.md#八类资产)） | 两条硬理由。**寻址**：skill 的资源不在 agent 的文件系统视野里，走 `Files()`/`Shell()` 就得先暴露存储位置，**那是把实现细节漏进产品接口**。**权限粒度**：skill 自带「谁可以使用它」，脚本是它的一部分，执行权应随 skill 走；走 `Shell()` 则判断退化为「能不能跑 shell」，「允许用这个审核过的 skill 连同脚本、但不许随意跑命令」这个意图就表达不出来 |
| **`exec_script` 只能跑该 skill 自己带的脚本，是红线** | 上一条 | 放开路径，这扇门立刻是 `Shell()` 的后门，**所有命令行权限管控当场作废**。这不是收紧，是这扇门能够存在的前提 |
| **带脚本的 skill 要能声明它需要什么设施** | `exec_script` 要落地 | 脚本要落在执行环境上，就得知道它要什么样的环境。这与[工具声明设施需求](../PF-006-tools-and-skills/design.md#64-依赖声明与解析)是同一个形状，但 **PF-006 只写了工具，没写技能**——已作为上游补充报告，见第四节 |
| **`Files()` 保留 `edit` 并新增 `patch`，两个都要** | 用户的提问 + 调研分布 | 两者回答的**不是同一个问题**：`edit` 改一处，模型出错率低；`patch` 一次改多处且**原子**。调研印证了这个张力——Claude Code/DSH/opencode/omne-next 全走 `edit` 形态，**Codex 走 patch 但用的是自定义简化格式**，正因为标准 diff 太容易生成错。只留 `edit` 失去原子性，只留 `patch` 则改一处也要付格式出错的代价 |
| **`patch` 真正多出来的是原子性，不是效率** | 上一条 | 连改五处若用五次 `edit`，中途失败留下**改了三处的文件**——**「改了一半」是所有状态里最糟的一个**：既不是成功也不是失败，而且**看上去像成功**。这与 [PF-005「迁移未完成不得以空数据起来」](../PF-005-execution-environments-and-sandboxes/design.md#52-租户级沙箱本体的存活与数据的存活是两件事)是同一条道理 |
| **差异写成什么格式，产品不定** | [product/AGENTS.md 的红线](../AGENTS.md#红线) | 标准 diff 还是简化格式，产品负责人看不出对错，属技术设计。产品只要求：**能一次表达多处改动，并且全有或全无** |
| **不引入「agent 主动申请提权」** | 调研：Codex 的 shell 有 `with_escalated_permissions` + `justification` | 那个设计让 **agent 能影响自己落在什么环境上**，而本系统的执行环境是**注入**的，[flows.md §4](flows.md#四谁决定什么) 已写死「agent 不选落点」。引入它，[PF-005 的热替换模型](../PF-005-execution-environments-and-sandboxes/design.md#53-换执行环境是换一个值不是开关一套机制)当场被捅破。**同一个问题我们的答案是「不可用 + 说明原因，agent 绕路」**——两种都成立，我们已经选了 |
| **`Shell().session` 的持久状态是显式的，不做隐式持久** | 调研：Codex 的 `ShellSnapshot` 自动保留 alias/环境变量/函数跨命令，落盘存 3 天；Claude Code 则只保持工作目录 | 隐式持久会让「这条命令的状态活多久」说不清，而那正是 [PF-005](../PF-005-execution-environments-and-sandboxes/README.md) 花一整个 topic 定下来的东西（执行环境有明确的绑定层级）。**显式开会话，状态的寿命就等于那个执行环境的寿命**，不需要第二套解释 |
| **一次性执行与会话内执行走同一个 `execute`**，差别只在给不给会话标识 | 裁决给的命令集里**没有单独的一次性执行命令** | 拆成两个命令，agent 每次都要在「这次要不要留状态」和「该调哪个命令」之间换算。合成一个，**这个判断变成一个参数，心智负担少一层** |
| **`cwd` 与 `envs` 只作用于这一次执行，不改写会话本身** | 「多个 terminal sessions 同时存在」 | 若它们能改写会话状态，「这个会话现在在哪」就有了两个来源（会话自身的状态 + 上一次 execute 带的参数），**唯一答案没了**。要让会话整体换目录，在会话里执行一条切目录的命令即可 |
| **`execute` 给了一个不存在的会话标识，必须明确失败** | 上一条 | 悄悄降级成一次性执行，**agent 以为自己接着上一条，其实状态全丢了**——而且它不知道。这比直接失败糟得多 |
| **`run_in_background` 与工具声明的后台策略不是一回事** | 裁决把它列为 `execute` 的参数 + [PF-006 §6.6](../PF-006-tools-and-skills/design.md#66-前台后台-与-等待态是两个维度) | 前者是 agent **发起时**决定这次不占前台，后者是**允不允许**以及**超时自动转**。因此**声明不允许后台的，这个参数也起不来**——声明就是声明 |
| **「发起时就在后台」与「中途转后台」的决定权不同** | 上一条 | 前者 agent 自己定（它知道这活要跑多久），后者归用户或自动超时（那是打断当前节奏的事）。**flows.md 的决定权矩阵据此拆成两行** |
| **同一个执行环境里的终端会话会一起消失** | 「多个会话同时存在」+ [PF-005 会话级沙箱到点销毁](../PF-005-execution-environments-and-sandboxes/design.md#63-会话级沙箱到点销毁数据不留存) | 它们都活在那个环境里，**环境是它们的宿主**。因此会话的数量与存活受资源约束——它们是**计算资源**，不是记录 |
| **`Cordis()` 本版设想为只读** | 「不作为首批交付」+ 完全动态的根目标 | 「看得见」与「改得动」之间必须隔一道明确的墙。**先定只读，是为了不让将来的人从「已经能看」顺理成章推出「那就能改」**。**复刻 DSH 时这条被印证**：它同样把只读的检视与持久的配置变更分给两个不同的东西 |
| **`Cordis()` 是 `list` + `query` 两条命令，不是一份总览报告** | 复刻 [DSH 的形态](interviews/2026-09-17-survey-of-harnesses.md#十一cordisdsh-的系统自省工具) | 两种问法的代价差一个量级：「我大致什么样」要的是概览，「某个方法参数什么形状」要的是**一处的完整契约**。只给总览，精确契约拿不到；只给完整契约，一次吐出全系统的会把上下文撑爆。**先看目录，再翻那一页** |
| **检视面由各插件自己贡献，不是画死一张总表** | DSH 的 Inspect Provider 机制 | 这是这扇门与「写一个大而全的系统信息接口」的分水岭。**总表一定会过期，而且过期时没人发现**；由贡献能力的人顺带贡献「怎么看它」，检视面就随系统生长。这与本项目[完全动态系统](../../../../AGENTS.md)的根心智是同一件事 |
| **`Cordis()` 的第四条红线（只看得见自己那一份）是我们加的** | [PF-001 的租户隔离](../PF-001-identity-scope-and-agent-constraints/design.md) | DSH 前三条红线照搬，但它是**单租户工具**，没有这个问题。我们从第一天起支持租户隔离，**这扇门若能看见整个部署，隔离就在这里破掉** |
| **`Cordis()` 的 host / client 两侧形状保留、当下只有一侧** | DSH 分宿主侧与界面侧 | 我们第一版是单机、界面那一半还不存在。**现在就把维度留出来**，将来长出来时不必回头改这扇门的形状——这比事后加一个参数便宜 |
| **外部取回的内容是数据，不是指令** | `Web()` 与 `Browser()` 的存在 | 这两扇门把系统之外的文字带进来。不写死这一条，**提示注入就是敞开的** |
| **设施给不了时不降级、不绕道** | [PF-005 沙箱创建失败不得退回宿主机](../PF-005-execution-environments-and-sandboxes/design.md#62-宿主机不提供租户隔离因此必须被显式允许) | 同一条规则在本 topic 的适用。绕道等于绕过安全判断 |
| **取回被卸载的结果这件事归 `Tools()`，不归 `Files()`** | 「`Tools()` 还需要提供……的命令」这条裁决 | 判据与[三对不能互相顶替](design.md#53-三对看着重叠实际不能互相顶替的)同源：被卸载的结果**不是文件系统里的文件**，它是**某一次工具调用的产物**。按调用去找它才自然；按路径去找，则要求 agent 知道一个它本不必知道的存放规则。**这是「那次调用返回了什么」的追问，不是「某个路径上有什么」的读取**。因此同一扇门管这次调用的参数、执行、以及它返回了什么 |
| **`read_result` 必须分页** | 「分页访问」这条裁决 | 不分页就等于**把刚卸下去的东西原样搬回来**，卸载当场作废 |
| **`read_result` 不落地** | 它读的是系统存着的结果，不产生外部效用 | 与 `search` / `inspect` 同类，与 `execute` 不同 |
