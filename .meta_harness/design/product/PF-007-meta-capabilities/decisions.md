# PF-007 决策与来源

产品设计允许 product manager 做判断，但**不允许发明没人拍过板的东西**。
本页把两者分开：哪些是产品负责人裁决的，哪些是 PM 自己推导的，各自依据在哪。

## 2026-09-29 · Ask() 的协作模式开关

依据 [PF-015 INT-003](../PF-015-session-lifecycle-and-ownership/interviews/2026-09-29-collaboration-modes.md#int-003)，产品侧以 Ask() 的开关和目标完成检查区分 co-work 与 auto-drive。模式归 PF-015，本包只接 Ask() 的适用边界。

与现有 meta 不可禁用／替换、PF-004 必需绑定对账后，将「关闭」表达为运行期不能经 Ask() 发起人交互，不删除资产或换实现；这是保持已定规则同时成立的推导。never 对 request_approval 的限制独立，co-work 不恢复被禁命令，auto-drive 不授予原本不存在的权限。旧「never 时 ask 照常可用」缩明为 never 本身不禁它，仍受协作模式约束。

开关如何实现、模式切换时进行中的交互如何衔接归技术设计；不自行增加计划审批工作流，不把没有收到的回答当成同意。冻结规格及原整包接受范围不变。

## 二、PM 推导

从已拍板内容推出的判断，附可核对的推理链。

| 结论 | 从哪几条推出 | 推理 |
|---|---|---|
| **meta 的定义要写成「一整类能力的统一入口」** | 「工具的工具、技能的技能」+ 必需集里有 `Shell()` `Computer()` `Web()` `Browser()` | 后四个**作用于世界**，不作用于能力集，按字面的「工具的工具」套不进去。能同时容下 `Tools()` 与 `Shell()` 的读法只有一种：**它们都是一族动作的入口**。「工具的工具、技能的技能」是这个定义最纯的两个例子。**「全都是 multiple command tool 范式」这条裁决正好印证**——多命令工具的本质就是一族命令共用一个入口 |
| **「meta 必定常驻」是结构逼出来的，不是产品选择** | 「meta 必定常驻」+ [PF-006 的常驻机制](../PF-006-tools-and-skills/design.md#常驻) | 够到非常驻能力的**唯一途径就是 meta**。若 meta 自己也不常驻，就永远够不着它——自指的闭环必须有不动点。**裁决说的「必定」在这里得到了解释，而不只是被复述** |
| **「不可禁用不可替换」与「必定常驻」是同一件事的两面** | 两条裁决 | 常驻保证门开着，不可禁用保证没人能关上它。**关掉一扇门等于门后一整类能力凭空消失**——这与「被禁用的能力 agent 仍然知道它存在」（[PF-004 的禁用](../PF-004-agent-definition-and-assembly/design.md#63-三类变化三种传播)）性质不同，后者可解释，前者是失明 |
| **收紧安全不能靠关掉 meta** | 上一条 | 既然门关不掉，安全只能落在执行环境、权限与装配清单上。**这是代价，必须写出口**，否则安全负责人会找不到抓手 |
| **十三扇门按作用对象分五族** | 十三个的构成本身 | 分族不是为了好看：**五族的风险完全不同**——世界族碰外部效果，能力族碰自己的构成，状态族只碰自己，他者族占用别人的时间，**底层结构族碰的是 agent 赖以成立的东西**。不分族，「哪些门危险」就无从谈起 |
| **`handoff` 能向派发者发消息，不是单独规定的一条** | 两条通信规则 + `handoff` 是独立主会话 | 它**落进了[规则二](design.md#先说谁能给谁发消息这是两条独立的规则)的适用范围**（独立主会话 + 活跃 + 同租户）。**产品负责人自己就是这么给的**——他在「生命周期不受控制」后面加了括号「**因为是独立主会话，因此这个会话可以接受用户的消息**」。**PM 把这条推完整**：`handoff` 与另外两种的三个差别（生命周期不受控、用户能直接找它、能回头发消息）**全都是「有没有独立主会话身份」这一条的后果**。**分水岭只有一条，不是三条** |
| **`spawn` 与 `delegate` 的分水岭只有一条：它带着什么开始干活** | 五个维度的对照 | 两者在**另外四个维度上完全相同**，只差「上下文怎么组装」。所以：**`spawn` 带着我知道的一切**（适合「同一件事分身去做」，来龙去脉交代不过来），**`delegate` 只带着我交代的那段话**（适合「另一件事交出去」）。**`delegate` 的上下文隔离是用处不是限制**——继承一份几万字的上下文要付钱，**而很多活根本用不着那些背景** |
| **「不能向派发者发消息」不等于「它干完了没人知道」，报告与消息是两样东西** | 「不能向派发者发消息（**只能是提交报告**）」这句的括号 | 产品负责人特意加了那个括号。**报告终结这次派发**（等待态结束、工具调用返回），**消息什么都不终结**；报告**只有一次**，消息来回多少次都行。**不点破这层，那条规则会被读成「它干完了也没地方说」**——而实际正相反 |
| **`spawn` / `delegate` 用了[等待态原语](../PF-006-tools-and-skills/design.md#等待态)，`handoff` 没用** | 「进入等待态直到返回报告或失败」vs「确认创建情况后即结束」 | 前两种正是 PF-006 那个原语的用法；`handoff` 是普通的同步返回。**由此还掉出一条可用的组合**：前两种的等待可能很久，而[前台/后台那个维度](../PF-006-tools-and-skills/design.md#66-前台后台-与-等待态是两个维度)正好用在这里——**派发者可以把这次执行转后台，自己先干别的**，报告回来时以提醒的形式到达 |
| **`withdraw` 对 `handoff` 不成立** | 「生命周期不受派发者控制」 | 撤回就是控制生命周期。**`handoff` 的不可撤回不是缺陷，是它的定义**——**一个能被撤回的 `handoff`，那是 `delegate`** |
| **`message` 发不出去时要说清是哪一条不满足** | 两条规则各有条件 | 不是我派的？没有主会话身份？会话已经结束了？不同租户？**四种原因的处理方式完全不同**——只回一句「发不出去」，agent 无从判断该换个人、该等一等，还是压根这条路不存在 |
| **`Cordis()` 与 `Engram()` 同属一族，而且族名不能再叫「系统自身」** | `Engram()` 那条裁决里的定位对仗 | 产品负责人把两者并列成了**同一个形状**——「动自己 X 结构」：一个是**行动 / 拓扑**，一个是**知识**。而 `Engram()` 碰的**不是系统骨架**，是 agent 自己的知识，所以原来那个族名容不下它。改称**「自己的底层结构」**，作用于**agent 赖以成立的那两套结构** |
| **这一族的两个都不在首批，不是巧合** | 两条裁决各自的「不交付」 | **动自己赖以成立的东西，是最彻底的能力，也是最该缓的。**其余四族碰的都是「拿来用的东西」，这一族碰的是「自己成立的前提」 |
| **`Engram()` 这一节要刻意写得短** | 「不作实现交付要求」「只是占位声明」 | 与 `Cordis()` 的「定义完整只是不实现」**程度不同**：那边边界危险、形状现在就要定死；**这边连命令集都不该定**——**多写一个字，都是在替一件还没设计的事情做决定**。本版只定死三件事：**它存在、它属于哪一族、它动的是知识结构而不是别的** |
| **`omne_engram` 的四条性质与本项目已有判据同调，值得记下备用** | 查阅参考系统 | ①**它不裁决 agent 该相信什么**——与 [`Cordis()` 四条红线](design.md#四条红线)同性质（这扇门的产物是知识的组织方式，不是结论）；②**不主动推送、不观察潜在需求**——十三扇门全都是这样，**它是门不是后台服务**；③**没人查过 ≠ 可以删**——**与 [PF-010「不给模型看不等于可以删」](../PF-010-context-management-and-assembly/design.md#不给模型看不等于可以删)是同一条判据的又一次现身**；④**可以给「结构怎么演化」立约束，违反时明确失败**——与 [`patch` 的原子性](design.md#55-patch-的原子性是产品性质不是实现细节)同调。**第三条的复用值得单说**：同一条判据在**上下文压缩**与**知识治理**两个毫不相干的地方各自成立，**这通常说明它不是为某一处编出来的** |
| **十三个槽位是预算的地板** | 「必定常驻」+ [多命令只占一个槽位](../PF-002-assets-settings-and-permissions/design.md#八类资产) | 十三扇门 = 十三个固定成本。但门后能力无上限，所以**常驻预算的正确用法是把钱花在门上**。这条是 [PF-006 常驻机制](../PF-006-tools-and-skills/design.md#常驻)在本 topic 的直接后果 |
| **`BkgJobs()` 是 PF-006 挖的坑，必须补** | [PF-006 §6.6](../PF-006-tools-and-skills/design.md#66-前台后台-与-等待态是两个维度) | 那里定了执行可以转后台、可跨轮存活，**却没给 agent 任何办法去看它、停它**。缺了这扇门，「转后台」就是把东西扔进一个再也够不着的地方。**调研的 DSH 有 jobs、Claude Code 有 BashOutput/KillShell，七家里没有一家把后台做成单向的** |
| **`Ask()` 与 PF-006 的等待态是同一原语、不同发起方** | [PF-006 的等待态](../PF-006-tools-and-skills/design.md#等待态) | 等待态是**工具内部**停下来等，`Ask()` 是 **agent 自己决定要问**。两者都是「停下等一个形状确定的应答」，因此**复用同一个原语，不另造机制**；但方向不同，不能互相顶替 |
| **`Ask()` 要能给选项** | 「问人」这件事本身 | 开放式发问把判断的全部负担推回给人。给出选项与各自的后果，人只需要做选择。这与 `product-design` skill 的「怎么说话」对 PM 提问的要求是同一条道理 |
| **`Ask()` 要有 `request_approval` 这第二个命令** | 调研：[legacy 的 HITL 契约](interviews/2026-09-17-survey-of-harnesses.md#十hitl问人与请示)是 `ask_user` + `request_approval` 两个工具 | 「我缺个输入」与「我要动手了，你准不准」**形状不同**：前者开放、拿到之后接着想，后者封闭、拿到之后才动手。更要紧的是**审批有一条问询没有的性质——它会在会话里留下一笔**；合成一个命令，那条性质没地方挂。Claude Code 只有前者，因为它把审批交给了权限系统弹窗；**我们的 agent 需要能主动就名单之外的事请示**，那是它没有而我们要有的 |
| **问询不设上限，系统永不替人作答** | legacy [HT-2](interviews/2026-09-17-survey-of-harnesses.md#十hitl问人与请示) 明文黑名单；Claude Code 的问询工具**同样没有任何时间或默认答案字段** | **两家独立收敛到同一条，这是强证据。**推理本身也成立：问询发生在动手之前，**等待期间没有任何东西被占着**——不占资源的等待没有理由设上限。而一旦设了上限就必须规定「到点算什么」，那就是系统替人作了答。「人没回答」与「人回答了随便」是两回事 |
| **一次问全** | legacy HT-4「一轮至多停驻一次」；Claude Code 一次调用可带 1–4 个问题 | 打断的代价**与问题多少无关，只与打断次数有关**——每次都要人放下手上的事、进入 agent 的上下文、再回去。所以工具要支持一次带多个问题，而挤牙膏式连问是产品缺陷 |
| **自由作答这条路由系统保证，不靠 agent 记得留** | Claude Code：`Other` 由系统自动提供，且**明文要求 agent 不要自己加**；产品负责人裁决亦明列「允许人自由输入自己的答复」 | legacy 侧同源——`suggested_replies`「只是提示，人可自由作答，不是枚举约束」。**关键在于由谁兑现**：靠 agent 自觉总有忘的时候，而那一次人就被困在几个都不对的答案里 |

| **`list_dispatched` 顶不上 PF-015 那条需求** | 命令表 + 2026-09-20 裁决 | 它按**派发动作**编址、是**历史账**，里面还含着 `handoff`（按裁决不算 subagent），且**没有「现在还在不在」这一维**。需求要的是按**子会话**编址的**当下状态** → **那条需求确实不在现有命令表上**，不是「已经有了只是没写」 |

### 三家挡「子超过父」的办法不同，为什么我们能取最宽的那种

**推理**：[调研记了三种形态](../../../research/agent-harness-session-design/research.md)——
DSH 把子的审批策略**恒定为 `never`**，Claude Code 让子**强制沿用父的模式**，Codex **取交集**并把审批浮层做到非活跃线程上。

**DSH 那条最严，而它的理由是一个我们没有的约束**：
「后台子的 escalation 会变成**没有任何产品界面显示的挂起**，于是『权限卡住的子』与『正常干活的子』从外面看一模一样」。

**这个理由对我们不成立**：[子 → 父的消息通路是通的](design.md#先说谁能给谁发消息这是两条独立的规则)（rev 10 放开的），
**子卡住了它说得出来**。所以我们能走 Codex 那条，**而不是因为我们更宽松**。

> **记下这一条是为了挡住一种误读**：将来若那条通路被收窄，**这个选择的前提就没了**，
> §5.8 要跟着复核。

### 2026-09-29 · 能力消费与服务依赖的边界

**直接输入**：[本轮交流 INT-005～008](../PF-004-agent-definition-and-assembly/interviews/2026-09-29-agent-runtime-assembly.md)：会话能力身份见过后保留，失去当前选择或实现时呈现不可用替换件；资产定义数据与执行实现解耦；会话类型必需与 AgentDefinition 显式必需同样不意味着 Loop 直接依赖能力背后的服务。

**本 topic 落点**：发现与读取经会话当前采用入口，已知不可用能力保留，未授权新内容不泄露。

**PM 推导**：①“已知”与“当前允许执行”必须分别求值，否则单调性会变成绕过撤权；②实现更新可发生在稳定入口内部，故不从它推出提供者换代或 Loop 重建；③ schema 更新可能改变调用含义，故即使实例未换也须核对尚未发起的旧动作；已发工作继续沿原输入；④每次求值所需输入不同，故分别保存会话当前采用值、历史数据与实现依据和单次调用快照；⑤Session 是数据／归属，逻辑供给矩阵不推出它是 fiber；实际 inject 边与所有权仍需技术设计和验证。常驻呈现、Slash Command 人的入口及未合法纳入资产仍沿各自边界，不把单调性扩为无条件信息公开。

**已知来源问题与处置**：旧文把能力的选入、数据、实现与服务生命周期混作一种“绑定变化”，因此过度推导 Agent runtime 重建；PF-010 还把提示词成品与实例期固定混为一谈。按本次输入修订，差异记入 C-47。AgentDefinition 版本采用仍沿已拍板的新 Run 或显式 reload 安全交接，不以本次技术分析自行取消该产品边界。框架事实采用 Cordis 4.0.4，区分 provider fiber 换代与同 provider 的数据更新（[已验证 basis](../../basis/cordis/plugin-body-reruns-on-provider-change.md)）；本次额外检查发布包源码，不声称运行了新探针。项目只复用 Cordis，不采用 DSH agent 原语。
