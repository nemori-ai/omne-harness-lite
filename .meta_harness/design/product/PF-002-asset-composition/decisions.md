## 二、PM 推导

以下结论不是直接裁决的，是从已拍板内容推出来的。推理链写在这里供核对。

| 结论 | 从哪几条推出 | 推理 |
|---|---|---|
| **四类资产是同一张组合图上的节点**，组合只有一种关系 | 「资产之间是组合关系」+「资产到 agent 的组装本质上也是组合关系」 | 第二句话的"本质上也是"就是在说两者**不是两种机制**。若是两种，就会有两套规则、两处覆盖语义、两个出错的地方 |
| **组装 = 组合关系在一个 Agent Definition 上求值的结果** | 同上 | 既然组装也是组合，那它不需要独立定义——它是组合图从某个 Agent Definition 节点展开的结果 |
| **Agent Definition 既能组合别人，也能被组合** | 「sub-agent 的定义属于这一类」（PF-001 §4 资产种类） | 作为 sub-agent 被引用时，它是被组合方；被实例化时，它是组合树的根。两种用法不冲突 |
| **求值与组装是两步，不能合并** | PF-001 §6.2 的资产合成 + 本 topic 的组合 | 求值回答"这个租户有哪些资产可用"（按五层作用域），组装回答"这个 agent 实际由什么构成"（按组合声明）。合并的话，"组织禁用了某个 skill" 与 "这个 agent 没引用它" 会变成同一件事，而它们的产品含义完全不同 |

## 三、待裁决

### 1. 四类是穷尽的吗——原先那张表里的其它行怎么办

[PF-001 §4「资产的种类」](../PF-001-identity-scope-and-agent-constraints/design.md#资产的种类)
目前列了**八行**，本次确定的是**四类**。差额部分需要产品负责人明确去向：

| PF-001 表里的行 | 我的判断 | 需要确认什么 |
|---|---|---|
| Hooks、Rules 等成员 | 它们是 **Plugin 的组合成员**，不是第五类。组合关系一旦成立，"成员"和"独立资产"不再互斥 | 是否同意按组合成员处理 |
| Tool、Service、Middleware 等实现 | **Tool 已被提为四类之一**；Service、Middleware 是技术实现概念，不该出现在产品设计里 | Service/Middleware 是否直接从产品正文移除 |
| **SlashCommand** | **判断不了。**它在 PF-001 表里是独立顶层资产，本次四类里没有它 | 见下 |
| **模型档案** | **判断不了。**PF-001 已说它"不是独立顶层资产"，但它确实参与 agent 组装（用哪个模型） | 见下 |
| **知识、经验、报告、附件与文件** | 我认为**它们不是资产**，理由见下 | 见下 |

### 2. SlashCommand 去哪了

**为什么 PM 不能自己定**：它在 PF-001 里是已定稿的独立顶层资产，本次没有出现在四类中。
删一类已定稿的资产不是设计判断。

三种可能，产品后果不同：

| 可能 | 后果 |
|---|---|
| (a) 它是 **Plugin 的组合成员** | 与 hooks/rules 同类处理，不能被单独授权或覆盖 |
| (b) 它是 **Skill 的一种调用方式** | 那它根本不是资产，是交互入口 |
| (c) 它**被砍掉了** | 本阶段不做斜杠命令 |

### 3. 模型档案在四类里的位置

**为什么 PM 不能自己定**：它既不像 skill/tool（不是能力），又确实参与组装（agent 用哪个模型）。

| 可能 | 后果 |
|---|---|
| (a) 它是 **Agent Definition 静态定义的一部分** | 换模型 = 改 agent definition；不能单独被组织覆盖 |
| (b) 它是 **Tool 的一种** | 模型调用被看作一种工具调用 |
| (c) 它**不是资产**，是配置 | 归设置而不是资产，按覆盖而非组合处理 |

### 4. 知识、经验、报告、附件与文件是不是资产

**这是我在 PF-001 里发现的一处内部不一致，先报告再处置。**

- PF-001 §4 把资产定义为**「约束 agent 由什么组装而成」**；
- 但 PF-001 的资产种类表里列了「知识、经验、报告、附件与文件」，
  而这些东西**不参与组装**——它们是 agent 工作时**读写的对象**，不是构成 agent 的零件。

按 PF-001 自己的定义，它们不该在这张表里。

我倾向把它们从资产里拿出去，归一个单独的 topic（工作产物与信息的治理）。
但这会**缩小 PF-001 已定稿的范围**，须由产品负责人确认，PM 不能自己删。

### 5. 组合的引用指向什么

**为什么 PM 不能自己定**：两种做法都自洽，且产品长相相反。

[PF-001 §6.3](../PF-001-identity-scope-and-agent-constraints/design.md#63-依赖与组合) 已定：
**依赖指向能力标识，不指向具体某个资产**，因此覆盖发生后依赖自动指向当前生效的那个。

问题是**组合（包含）是否照此办理**：

| 做法 | 后果 |
|---|---|
| (a) 组合也指向**能力标识** | 组织定制了某个 skill，所有含它的 plugin 与 agent **自动用上新的**。一致性好，但 plugin 作者无法保证自己包里的东西不被换掉 |
| (b) 组合指向**具体资产版本** | plugin 的完整性有保障，但组织的定制进不去包内，要逐个改 |
| (c) 默认 (a)，允许 plugin 声明某成员**不可替换** | 两者兼得，代价是多一个机制——而多一个机制就多一处要解释的地方 |
