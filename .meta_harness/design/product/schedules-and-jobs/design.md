# 日程与作业产品设计

采用范围见[topic 入口](README.md)。本文维护已确认的完整产品规则；技术采用、运行支持与交付接受分别记录，不从产品正文推导实现完成。

## 产品需求描述

人和 harness agent 需要把短、中、长期目标安排到未来，而不必让创建安排的会话持续运行。系统也需要按部署政策安排预先定义的机械工作。用户应在一个入口表达要做什么、何时做、遇到特殊日期或已有工作时怎么办，以及需要怎样通知；保存的是一份完整 Schedule。它包含 Routine 工作描述，Routine 没有独立身份、共享可变对象或另一路生命周期。采用出厂预置只是将已展示内容填入安排，后续编辑及各次工作状态属于这份安排。

<a id="schedule-job-model"></a>

安排、单次工作及实际结果需要分别指认。预览或下一次预算只是候选；候选在最终校验后被接受才形成 Job，即使它随后等待执行或等待前序停止。一个 Job 固定本次工作要求、来源时刻、采用的日期依据及策略，后改 Schedule、出厂内容或日历不能回写它。实际受理、开始、执行目标完成、通知送达和人已阅读各有不同证据，不能用一次请求成功或 Run 结束宣告全部完成。

系统、租户、发起者及通知目的地分别表达。租户由组织和账号共同确定；创建者会话归档或成员资格变化不销毁 Schedule、Job 和历史；若安排明确依赖该会话或关系，是否继续接受按其权威状态判断。每个入口按当前资格操作，到期接受与真正开始仍检查各自所需权限和依赖。同租户的不同 owner 也默认隔离；未认证或越权请求不得泄漏安排、工作或目标是否存在及其内容、状态、时间。失权或不可用明确拒绝、失败或受阻，不改投另一租户，不复制过去授权，也不靠系统调度取得任意资源权。已经开始的调用继续沿其原控制及结果责任收场；成员资格变化不自动冻结全部业务。

框架支持明确的时间、日期、补跑、重叠和通知声明，合法治理配置与可替换提供者承接它们。规则支持范围不由某个 cron 库或部署参数决定；未声明的策略不能由技术默认补齐。具体提供者、公开形状、超时、退避及容量参数继续由技术/治理拥有者确定。本页不选择通道或数据库，提供者存在也不证明这些产品规则已经兑现。

<a id="schedule-lifecycle"></a>

### J-SJ01 一次保存完整安排，再控制后续

用户或获授权 agent 希望创建、起草、编辑或采用预置安排。前提是归属、作者、工作类型、内容、完整时间规则，以及适用的日期处理、恢复、重叠、执行和结果声明明确，当前操作资格成立。一次保存完整定义，成功后才返回身份。预置内容和来源可读，采用后由 Schedule 持有，不反向修改预置或其他安排。未知字段、歧义、非法规则、无权或必要依据缺失时明确拒绝，不能留下半份安排。

创建可以直接启用，也可以保存为草稿。启用从严格晚于启用时刻的首个合法时隙开始。草稿只保存意图，不能到期、接受 Job 或形成可被扫描的未来工作。原作者或 owner 可以修订完整草稿并保留修改记录，也可丢弃；丢弃是不可恢复终态。owner 转正时重新核验当前时间、资格、环境和依赖；没有未来时隙则保留草稿并说明原因。重试同一次转正认回原结果，另发操作不能再次转正已转正或已丢弃的安排。逐次同意与转正的关系见 J-SJ15。

活跃或暂停安排的名称、同一工作类型下的 agent 指令或提醒文本可原地修改，保留身份和原管理状态。工作种类、时间规则、执行程序及输入、agent 配置、会话模式、目标、环境绑定、补跑、重叠或结果政策变化必须形成新的 Schedule。替换同时让前任进入已被替换终态并建立后继，后继继承活跃或暂停状态。用户看到旧安排仍有效，或后继已有效及双向关联，不能看到两个都生效或失败后两者都不存在。已接受 Job、原修订和旧执行史保持。

暂停阻止新 Job；恢复只解除用户暂停，仍受依赖状态与恢复政策约束。永久停止不可再次启用，不自动取消已有 Job。有限候选处置完后安排自然耗尽，Job 仍可继续；权威终局失效见 J-SJ12。终态不得靠改文字、换依赖或恢复旧事实复活。重复控制认回真实状态；回执未知先查原操作。对应 CAP-SJ01、CAP-SJ11。

<a id="time-rules"></a>

### J-SJ02 核对时间意图与特殊日期

用户希望在确认前知道下一次及有界未来时刻、日期原因、采用环境和版本。规则表达一次性时刻、标准五字段 cron 或 RRULE；同一范围内人和 agent 使用相同表达能力。一次性安排独立于“只剩一次的周期安排”，相对日期在保存时固定。过去时刻、不可解析时刻或夏令时不存在的本地时刻不能创建为一次性安排。

cron 为分钟精度，日与星期同时限制时满足任一条件即可，星期 0 和 7 均表示周日。秒字段、宏、随机散列和提供者专有语法不在该入口范围。RRULE 支持频率、间隔、月份、月日、年日、年周、星期、集合位置、时分秒与周起始的合法组合；起点、截止及合格次数独立表达，不允许在规则正文另藏一套。秒精度不静默截成分钟，最短间隔仍服从资源政策。完整合法表达由[日程行为规格](../../../../packages/schedule/schedule/SPEC.md)逐项固定，不能因所选库不支持而删掉已承诺输入。

常规编排支持日、周、月、自然季度和年。默认周起点为周一，显式周起始声明按合法规则执行。同一规则可有多个月份、星期或日内时刻；不能强迫用户拆成多份 Schedule。位置规则支持月、自然季度或年内第 N 个或最后一个指定星期几或工作日。工作日必须按真实日历判定。不存在的月日或位置跳过，不改成临近日。

起始和截止包含边界，截止须晚于起始；次数和截止同时约束。排除日期按规则时区排除整日，最多 366 项。日历可筛选工作日、非工作日或法定假日；非工作日包含普通休息日和假日，补班周末属于工作日。谓词不满足时按明确声明跳过、前移或后移至工作日，没有筛选和平移时保持原日。位置型工作日规则仍需日历。

计算依次检查原日期边界与排除，处理日历筛选和平移，再检查结果日期边界与排除，最后解释夏令时并合并碰撞。平移保留本地时刻，可以跨周期但不能越起始、截止或首次启用边界。平移后落入排除日就跳过，不继续找下一工作日。周期规则的夏令时缺失时刻跳过，重复时刻只取第一次。同一安排多个来源落在同一实际时刻时合并为一份候选，保留全部来源。

相同定义、环境与日历版本的引用式和展开式预览一致，显示原日期、平移、排除、夏令时、来源及两类次数限制。缺覆盖、非法规则、无权、搜索预算耗尽和合法空结果分别说明。预算耗尽不能报“没有下一次”。预览不保存、不扣次数、不接受 Job、不预测实际执行时长或重叠胜负，也不授予后续写权。对应 CAP-SJ02。

<a id="admission-limits"></a>

### J-SJ03 到期时接受本次工作

调度方希望把合法候选可靠承接成一次 Job。前提是 Schedule 允许新工作、当前归属与资格成立、必要依据和依赖可用、两类剩余次数都允许。预览、预算和准备都不等于接受。最终接受按当前完整定义、有效环境和所选日历版本政策重新核验；依据在接受前改变时重新准备或拒绝过期依据，不能沿用旧预算。

成功接受固定工作要求、程序输入或 agent 指令、会话模式及目标、策略、原定时刻、合并来源、实际日历身份与版本。接受后即使等待执行也已有可查询的 Job 和未完责任。修改安排、切换环境、修订日历或撤销未来权限不能回写已接受历史；实际开始及每个受保护动作仍检查当前资格。

| 次数轴                     | 计入什么                                                                                                            | 不计入什么                           |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------- | ------------------------------------ |
| 合格时隙上限 eligibleLimit | 经过规则、日历处理、夏令时及同刻合并后的合格序列；其中后来因重叠跳过、错过或准入拒绝而未形成 Job 的时隙仍占序列名额 | 日期过滤、排除、夏令时缺失与越界候选 |
| 接受作业上限 jobLimit      | 实际接受的 Job，合并一次算一次；等待、失败和取消不退还                                                              | 未接受候选、排除和跳过               |

两种上限可同时设置，任一耗尽都阻止新接受，不能用含混的“次数”互相替换。纯提醒接受形成通知 Job，计入作业上限但不消耗 agent 执行预算。例如合格上限为 3、作业上限为 2，第一个合格时隙因重叠跳过，后两次被接受，其中一次随后取消，最终仍是 3 个合格时隙、2 个已接受 Job，不再补出第三个 Job。

同一到期时刻至多接受一次。新候选撞上本安排已有 Job 时记录跳过，不能新建或向旧 Job 回填来源。已处理来源后来被日历重算到另一日也不能重复产生工作。并发、重启、响应丢失或接管须认回原接受与计数，不能各自产生一份。准备、接受或通知交接不能留下无法归责的部分成功。对应 CAP-SJ03、CAP-SJ06。

<a id="recovery"></a>

### J-SJ04 从停机、暂停或缺依据中恢复

周期执行只选择不补跑 none，或补最近最多 N 次 latest N，N 为正整数。设备恢复、日历恢复及积压扫描在相同候选、时刻和政策下选择同一集合，保存了更早 pending 候选也不获得优先权。漏过仅含首次启用之后、原定截止内、尚未接受且尚无明确处置的合法时隙。

恢复处理固定当前时刻 T 和本次漏过区间。none 将严格早于 T 的候选记为不补；latest N 只选择最近 N 个，其余明确记不补，后续扫描不能分页补光。T 当刻正常候选不占 N，与选中补跑按原定时刻升序处理。每次接受前仍核验当前资格、重叠和双限额；被重叠跳过的候选不再从更早积压补位。原定截止内的漏过可在截止后接受，手动永久停止则不再接受新 Job。

例如 T 为 10:30，漏过 08:00、09:00、10:00。none 不补三者，latest 1 只选 10:00，latest 2 选 09:00、10:00；10:30 若有正常候选则另行参与。恢复后查询应同时看到选择和不补原因，而不是只见已执行的行。

以下工作各有恢复含义，不能套用周期补跑。

| 场景                           | 可观察结果                                                                                                     |
| ------------------------------ | -------------------------------------------------------------------------------------------------------------- |
| 一次性执行到期遇可恢复依赖故障 | 默认作废并说明原因；显式选择等待恢复时保留原时刻，没有隐含五分钟准入截止，同一关系恢复后重新核验并最多接受一次 |
| 一次性执行只是扫描迟到         | 不能仅因当前时间晚于原定时刻就作废；读取面区分已派发、运行中和真实成功、失败或取消                             |
| 暂停跨过一次性原定时刻后恢复   | 按一次性作废政策终结，不能转换成周期补跑                                                                       |
| 用户环境不相容或尚未对账       | 恢复后从当前时刻重新计算，不补停泊区间，见 J-SJ12                                                              |
| 提醒错过首次接受窗口           | 记录错过且不补发，见 J-SJ08                                                                                    |
| 已接受 Job 等待或执行中断      | 继续原工作，不占补跑名额，不重复计次数或新建 Job                                                               |

原定时刻与实际接受、开始分别保留。权限或依据未知时明确受阻，不称已经执行或从未发生。补跑计算无法在预算内完成时，明确显示降级与未补区间，按不补跑重新确定未来时刻，不能假装完成全部搜索。重算提前到 T 之前的未处理周期候选仍受同一补跑规则约束。对应 CAP-SJ04、CAP-SJ10、CAP-SJ12。

### J-SJ05 遇到前序尚未结束的动作

用户明确选择跳过本次、停掉先前后执行、独立并行或等待后执行。比较同一 Schedule 的实际前序集合：含执行的 Job 看执行部分，纯通知看发送/交付动作；组合通知尾部不单独阻止下一次执行，仍由原 Job 持责。其他 Schedule 及共享外部文件不自动归入此策略。

跳过不创建 Job且不再作为漏跑；并行建立独立 Job 和结果，是否新建会话按执行声明判断；等待接受固定 Job，按原定顺序排在实际前序之后。替换先接受新 Job，向仍在执行或等待的前序发出明确停止控制，所需停止得到确认才开始新工作。此前并行留下多个前序时，非并行声明对实际集合处理，不能只看最近一个。

已知机械动作不能满足停止策略时保存即拒绝；停止失败、未知或未确认时新工作受阻，不能偷偷并行。Session 归档业务取消完成、控制请求受理或客户端断开不证明需要停止的原执行已经停止。已有工作固定输入不变，停止控制不回滚外部效果；新替换 Job 后来被取消也不能撤销已发出的旧工作控制。依赖恢复时先查原控制和队列，不能重建已有 Job。对应 CAP-SJ05。

<a id="execution-modes"></a>

### J-SJ06 按明确执行意图完成工作

执行型 Job 必须从开始就明确以下三种互斥路径。谁创建安排不能替代执行路径选择，程序输入也不能被解释成隐藏的 agent 指令。

| 执行路径                | 固定的工作意图                        | 用户应看到的承接结果                                                     |
| ----------------------- | ------------------------------------- | ------------------------------------------------------------------------ |
| 程序执行 program        | 已注册程序及合法输入                  | 程序执行一次，不要求 Session、agent 或模型；任意脚本不是可登记的程序引用 |
| agent 新会话 new        | 明确指令、合法 agent 配置和新会话选择 | 为本 Job 新建专属作业会话；重试认回同一份会话，不重复创建                |
| agent 已有会话 existing | 明确指令、指定已有会话及运行位置选择  | 只交给该会话；目标受阻或失效时如实受阻或拒绝，不能偷偷新建会话           |

指令是 Job 的业务要求，接受后冻结。如何把指令接入、采用何种消息、排队或推进，归[会话与工作](../sessions-and-work/design.md)；本域不定义消息角色，也不据“入队成功”判定 Job 完成。已有会话执行须关联到本次实际执行结果，不能取该会话最新回复或空闲状态冒充。取消本次工作也不能取消该会话其他无关工作。

新会话前提是当前启动资格、合法已发布 AgentDefinition、显式运行模式、资料及必需能力成立。普通 new 路径不自动成为父子派发，也不复制创建者或上一 Job 的整段上下文与授权；显式定时交接另见 J-SJ14。需要历史成果或工作区时明确引用并按当前资格读取，未指定工作区即为空。无人值守不能跳过权限。

agent 执行须把进度、候选成果、问题上报和达成判定绑定当前 Job；模型不能换一个 Job 身份报给别处。新作业会话附加对应成果工具与目标完成检查，已有会话由外部承接者维持相同的本次目标与结果关联。成功须有候选成果和目标达成依据，普通回复、成果提交成功或 Run 结束均不足。agent 产出资产沿实际工作区和租户提交，不能直接产出组织资产或替用户手动提升。

装配失败不声称开始；目标未达不能报成功。无法继续应呈现等待、失败或停止原因，不能无限续跑或抵消用户停止。恢复认回原执行，不新建业务重跑。同一会话的 AgentDefinition 标识、执行类型及合法版本变化沿原拥有者规则，不能为适配 Job 改写。不可用工具只产生真实不可用结果，不能冒充目标完成。对应 CAP-SJ06、CAP-SJ07。

### J-SJ07 系统按部署条件做机械工作

系统希望周期执行已定义维护功能。系统 Schedule/Job 归系统，不能伪造特殊租户；机械执行不建立 agent 会话、不调用模型作完成判断。功能及部署管理入口明确允许操作、真实资源资格和实际成功/失败/未知依据，按同一时间、受理及历史规则承接本次工作。

普通租户、获装配日程工具的 agent 或组织管理员不因此取得任意系统机械操作/全租户查询权，也不能只改所有者把租户安排转换为系统安排。有意停止的服务不得由备份安排偷偷启动；只有已定义操作真实成功才报完成，触发成功不足。不能停止时明说；恢复先查原操作及效果，只续合法未完部分，不将未知重放为新机械业务。具体系统功能清单和部署政策由拥有者确定，本稿不选工厂内容或启用频率。对应 CAP-SJ06、CAP-SJ11。

<a id="reminder"></a>

### J-SJ08 到点通知或按执行事件通知

提醒用途与执行用途互斥，改变用途必须原子替换。提醒没有执行指令、设备目标或 agent 执行预算；可空标题和非空正文保持原文本，不隐式修剪或规范化。内容边界由[行为规格](../../../../packages/schedule/schedule/SPEC.md)明确。来源提醒采用不补跑和并行通知，各期责任独立；其他原生纯通知可显式选择重叠策略，仍须满足真实等待或停止条件。一次性提醒不带日历过滤或平移。

提醒窗口政策 reminder-window-v1 允许首次通知接受发生于原定时刻 W 到截止之前。截止是 W 加 300 秒与下一有效时隙两者的较早者；没有下一有效时隙时取 W 加 300 秒。下一有效时隙已应用边界、排除、日历、夏令时和合并，不能取基础候选代替。正好到截止即错过，不补发。长停机的多个错过窗口须可查，不制造无界逐窗负担。窗口内已可靠接受的通知可稍后送达，不能因传输迟到改成错过或新发一份。准备时看到的窗口与实际准入必须一致。

纯通知 Job 到期交付已定义内容，不创建 agent 会话。需调查、分析或生成成果则包含执行；执行并通知仍是同一个 Job。组合声明选择非空的开始、成功、失败、取消事件集合，并明确各事件内容和目标租户。实际开始不是排队；成功有目标依据，失败是已确认不能继续，未知不是失败。每个本次已选实际事件产生一次逻辑通知，未选/未发生显示不适用。

本域保管事件和未完通知义务，经通知能力可靠承接给定内容，再消费真实交付事实。正确目标租户持久可取回才算送达，在线、已读、受理回执和成果提交均不能代替；不改投同账号其他租户。纯执行不附送通知；submit_result 不隐含 send，agent 主动 send 是独立意图，不能替配置义务。

纯通知只有送达才成功；组合只有执行目标达成且实际触发的全部通知均送达才整体成功。失败/取消的执行不会因通知送达变成功；执行成功但通知未达保留真实部分完成。没有事件命中不制造通知。投递失败不递归产生执行失败事件，不重做源机械/agent工作，取消后既有通知义务仍保留。通知回执未知先查原通知，不能盲重发；精确交接机制与对象分解由双方技术设计落实。仅已形成的通知才能显示真实通知身份，待交接意图不能伪造该身份。对应 CAP-SJ08。

### J-SJ09 取消这一次已接受工作

合资格用户或管理 agent 希望取消指定 Job，读权不能代替取消权。尚未开始的 Job，包括排队、等停止确认或装配前受阻，可不依赖 Session/Run 取消；成立后不再启动，恢复也不复活。已开始 agent 执行记录停止意图，沿原优雅取消或显式强制停止规则推进；物理停止未确认时分别呈现实际进展，不把请求受理当停止。机械功能按自身可停止边界处理。

纯通知发送前取消获胜则阻止发送且不另发取消通知；已发送或效果未知不承诺撤回、不把未知改成取消成功或因此重发。执行已终结时保留原成功/失败，组合未送达通知继续持责。组合执行取消成立，包括开始前取消，只在原声明选中取消事件时触发通知；不伪造开始或成功，已有通知和迟到效果留归原 Job。

取消不改 Schedule、其他 Job、固定输入、次数或历史，不使它再进入补跑。开始/完成/取消竞争给出可追溯顺序；重复取消认回原控制，不重复执行或通知。回执未知查同一 Job；完成检查不能拉起新执行抵消取消。替换发出的原控制仍独立成立。对应 CAP-SJ09、CAP-SJ08。

<a id="queries"></a>

### J-SJ10 查看安排、工作与未完成责任

合资格者希望按 Schedule 或 Job 查询完整定义、管理状态、原定/实际时刻、采用来源、等待/执行进度、成果、通知结果和漏过/跳过原因。查询只读、按当前租户及字段资格呈现，不能从读权取得管理、取消或源材料权限。后台调度、系统归属和通知目的地也不授全局读权。

列表和详情来自同一事实，合法无数据返回空结果。支持按依赖状态、作者、设备、日历过滤、稳定分页和总数，时间窗过滤与取回后按相同原定时刻过滤一致。agenda 区分历史真实处置和未来预测，正常、日历压制、依赖受阻、用户暂停都可见；草稿和终态可按筛选查询。被去重的判定须有原拥有者真实回执，缺证时明确缺席，不能解析外域私有标识猜造。日程读面不额外生成健康好坏判词。

agenda 的请求时区只改变显示和区间边界，不重解释安排规则；请求应明确时区，未提供则明确拒绝，不能借机器本地时区猜测。历史沿原依据，未来沿当前预测依据。每次工作须能定位到其执行证据；new 路径各期为不同会话，existing 路径以同一会话中的本次执行关联区分。请求超过公开页大小、窗口或预览上限时拒绝；运行中达到搜索预算则显示结果不完整及边界，不能无声截断。

历史不因 stop、Session 归档、失权或实例退出自动删除，物理归档/索引优化不缩短承诺查询范围。当前 Schedule 不能覆盖 Job 历史；读面滞后、查询故障与业务未知明确区分。调用超时或找不到投影先核对原接受和责任，不由查询触发重跑、补送或新安排。客户端关屏/离线只改变观察，不使已受理工作或历史消失。对应 CAP-SJ10。

### J-SJ11 更换调度提供者并接续工作

装配/运维希望调整合法策略或更换运行实例。前提是能力支持、配置生效点、依赖和接续协议明确。停止新准入后，按实际阶段保管或可靠移交已接受 Job、未处理区间、停止控制、原执行/通知关联和未知；移交确认前原方持责。下一方认回原事实，继续未完部分，不重复受理或重做已发生动作。

缺依赖、无效配置、不能安全核对或没有承接方时明确受阻与责任归属，不删登记后宣称完成。撤除仅清理自有监听、计时器、注册和使用权；不恢复整个旧快照抹他方变化，也不使外部输出可逆。晚到结果仍回原工作，新实例不得借旧回执产生第二份 Job。进展依赖当前资格、依据、持续提供者和合法策略，不承诺所有故障下无条件完成或固定耗时。对应 CAP-SJ12。

<a id="environment"></a>

### J-SJ12 随用户环境变化，并理解依赖受阻

用户创建的安排默认跟随用户生效环境 followUserEnvironment，固定业务和系统安排采用显式绑定 explicit。跟随模式采用同一份环境修订中的时区与日历，不混用新时区和旧日历；用户不必逐条迁移安排。显式绑定保持指定时区和日历身份。日历身份与版本政策分别选择，显式身份也可跟随该历最新发布版本 latest，或固定某版 pinned；未知固定版本不回退最新版本。

环境归设置拥有者，日历知识归[日历产品](../calendars/design.md)。缺少生效日历或时区时明确拒绝并指出修复入口。跟随变化只重算未接受未来，显示旧新环境及下一时刻的变化；已准备但未接受的旧依据失效，已接受 Job 和历史保持。切换收敛前不能用旧环境准入，新环境对账必须完成；收敛窗口由技术拥有者明确并验证。日历或环境不相容时可见受阻，恢复自洽后从当前时刻重新确定未来，不补停泊期间工作。显式安排不跟随旅行偏好改变，但显示时区可以改变。

用户管理状态和依赖可用性分别呈现。依赖恢复不会解除用户暂停。设备离线、成员关系暂停、AgentDefinition 暂时无合法可用发布、依赖会话用户归档属于可恢复受阻，只有原拥有者恢复同一关系才可重新就绪。设备退役、租户关闭、成员关系移除、AgentDefinition 身份永久失效、原主会话永久失效则终局失效，保留原因和历史。网络超时、含混的未找到或离线时长不能推断永久失效。迟到恢复不能覆盖更新的撤权或终局事实，同名新对象也不能复活旧安排。继续工作须创建新意图并重新准入。

依赖变化只约束尚未接受未来；对已接受工作是否停止由原运行控制另行判断，不能篡改其身份和结果。受阻、恢复、终局失效各形成真实通知，同一成因反复扫描只保留一件持续事项，不形成通知风暴。不同成因可辨，未发生的变迁不能发通知。通知说明原因、自动恢复条件和用户可做动作；依赖恢复但用户仍暂停时明确说明，不能称已补做。投递失败不清除受阻；发出过期提示前核对更新状态，历史仍保留。对应 CAP-SJ04、CAP-SJ13。

<a id="subscriptions"></a>

### J-SJ13 订阅系统提供的定期工作

用户可以发现受自己影响的系统功能。功能定义说明版本、工作模板、时间规则、可控性、不可关闭原因、允许个性化的参数、默认值及适用人群。用户可控的功能必须显式订阅，安装应用不代表同意订阅。不可控功能仍须出现在受影响用户清单，说明权威适用依据，不能伪称用户已经同意。

每份订阅有独立身份、所采用的定义版本、参数、管理状态和接受历史。未覆盖参数采用功能默认值，调整只影响自己的未接受未来，不改功能或其他用户。每名订阅者的同一到期最多接受一次，两名订阅者同刻到期分别接受，不相互去重。实际工作与结果也独立，一方失败不影响另一方。

功能需要错峰时，在声明窗口内确定每份订阅的偏移，预览可显示，重启后不重新随机。原定时刻与实际到期分别可见。取消订阅阻止新接受，已有 Job 沿自己的控制继续。升级功能定义不改已接受工作，采用新定义按该功能声明迁移或确认，不能偷偷替换精确发布。平台机械维护仍是系统归属，不能假造用户订阅。对应 CAP-SJ14。

<a id="handoff"></a>

### J-SJ14 定时交给子 agent 并回传原主会话

获授权 master 可把任务、报告要求、同租户的明确 AgentDefinition 身份和结果政策保存成未来意图。它使用 J-SJ06 的 agent 新会话路径，经外部执行承接者形成与原 master 有归属关系的一份 child 工作。即使目标与 master 采用相同定义，也创建独立 child，不续跑或复制 master 当前会话。master 空闲时可直接执行已固定意图，无需先唤醒 master 重新选择目标。

源系统固定精确 Blueprint 发布；目标采用现有 Session 约定，冻结 AgentDefinition 身份和工作意图，不提供固定 agent 版本选项。到期启动新 Run 时采用同一定义最新合法发布，并记录实际采用版本；同一 Run 普通恢复沿用原采用。旧发布停用或删除不自动使定义身份终局失效，有无可用发布及定义失效分别由 Agent 拥有者判定。这是明确的源适配差异，不能宣称版本策略逐字复刻。

每次接受只形成一个 child，重复启动先认回原执行。到期和后续受保护动作重核当前资格，不沿用创建时凭据。该交接模式默认重叠跳过，未明确允许并行时，前次 child 未终结就记录跳过，不自动排队积压。

child 的成功、失败或取消和原始报告可靠保存后，结果再交回原 master。master 忙时保留有界待收结果，队列满应显示受阻并保管责任；休眠按原唤醒规则恢复，用户归档显示受阻，永久失效则停止自动回传并保留 owner 可治理查看的结果。不能改投另一个会话或相似 agent。回传不等于用户发布或归档，原报告不能被 master 改写，整理后的交付物另有来源关联。对应 CAP-SJ15。

<a id="consent"></a>

### J-SJ15 让 agent 起草，并由用户控制同意与撤权

agent 只在当前合法 owner 和作者范围管理自己形成的安排，owner 可以查看其全部安排并修改、暂停或终止。工具可见不代表有管理权，读权不代表写权。合法读取和预览无需写入确认，agent 能使用与 human owner 相同的完整时间表达范围。

同意分为逐条 granular 或全权 blanket，效力范围分为当前会话 session 或持续 standing。默认逐条模式中，agent 创建成功后落草稿，用户不在场也可起草，但未确认前零未来工作。原作者可自行修订或丢弃自己的草稿。owner 对同一草稿转正就是逐条确认，会话内确认与面板转正认回同一个事实。在逐条同意模式且没有适用的持续全权同意时，对已生效安排的修改、取消、替换仍按具体命令确认，批准只适用于对应主体、归属、对象、工作种类、内容及来源上下文，不能移给另一份内容。

持续全权同意在其合法范围内允许自主生效，跨会话和重启有效，没有隐含过期；权威明确设置的期限仍有效。撤销只阻塞依赖该全权同意的安排，不删除它们，也不使独立有效的逐条批准失效。重新授予全权不会自动恢复旧安排，用户须逐条重新确认。确认只更新该安排采用的同意，仍保留用户暂停，也不能复活终态。未来接受、真实执行和披露分别核验当前资格。

持续工作配额按每个 owner 与作者的非终态未来意图计算。草稿、活跃、暂停和受阻均占一份；转正不重复收费，原子替换转移原配额，丢弃、永久停止、耗尽或终局失效释放配额。不能按每次 Job 重复占该配额，也不能通过并发创建越额。超额明确失败，既有安排不被挤掉，不能部分保存。额度值归既有资源治理。

agent 调用已获授权的其他正式能力而间接形成未来工作时，沿该能力自己的授权，不另套作者工具的确认门。实际受保护动作仍遵守当前资格。对应 CAP-SJ16。

<a id="results"></a>

### J-SJ16 发布可理解的成果，并独立归档

执行、回传 master、发布和归档各有独立结果与未完责任，查询不能用一个成功标记覆盖四者。受众、打扰程度和归档分别声明。内部工作 masterInternal 默认只回 master，不生成普通用户结果、feed 或通知；owner 仍可从获准治理入口检查。用户交付 userDeliverable 要由 master 形成安全、完整、可理解的正式成果，再发布到授权站内入口；卡片、通知和完整报告引用同一成果及其版本。默认不升级为推送或短信。

两种受众都可显式选择有效归档目的地。内部成果归档不自动公开，分类、容器及存储含义归归档拥有者，日程只采用合法目标引用。重复工作使用稳定系列，每期有独立身份、原定时刻、版本和出处，不能覆盖前期；按时间及稳定次序回顾。

master 整理失败时保留已完成执行和真实回传，发布显示失败或待处理，不能拿原始内部报告冒充用户成果。发布成功而归档失败只恢复归档。目的地失效不改投其他主题、项目或租户，原成果耐久保留。回执未知先核对原请求，不能盲重发造成第二份发布或归档；无法确认时呈现未知和处置责任。通知失败不重新执行工作。对应 CAP-SJ17。

<a id="self-wake-boundary"></a>

### J-SJ17 区分当前工作续跑与新的定时工作

用户需要知道 agent 是继续当前工作，还是接受另一份未来工作。自唤醒属于[会话与工作](../sessions-and-work/design.md)的当前工作延续，独立于 Schedule/Job；agent 指定已有会话来执行一个新 Job，也不能被解释为同一 Run 的自唤醒。本页只保存完整用户路径的组合要求，不取得 Session 状态和推进权。

当前获准 agent 请求在未来时刻续跑当前 Session 时，须先可靠保存挂起点和续跑责任，再确认并释放执行资源。等待不消耗活跃执行超时；到点且资格、依赖与提供者持续满足继续条件时，必须完成一次逻辑续跑；重复通知、重启与接管不能产生第二次逻辑续跑，保留原因果链，不另建 Session、Job 或派发单。重启、重复唤醒和接管认回同一责任，已取消或终局工作不能被复活。过去时刻、无效输入或非当前获准 agent 的请求明确失败，不留半登记意图。

自唤醒不豁免原无进展检测或 Run 生存底线。持续只自唤醒而无推进应被原检测识别；有真实工具或推理进展不应仅因自唤醒被误判。自唤醒须遵守既有政策的最小间隔、次数、截止和活跃预算，短时有界探测、提前完成和调整唤醒时间仍属于原工作责任。计数不因重启清零，挂起不重置原 Run 以规避治理。仍在原授权范围的同一工作续跑无需逐次批准，新目标或增权沿原治理。对应 CAP-SJ18；具体实现与验证由 Session 和 Agent 拥有者承接。

<a id="notification-boundary"></a>

### J-SJ18 在通知中保留真实交付与当前资格

日程只形成合法通知意图并消费交付结果，[通知](../notifications/design.md)拥有实际通知及各渠道事实。用户离线、外部渠道故障或重启后，通知仍须在正确 owner 的站内入口可靠取回。受理、站内可取回、外部已送达、打开和用户确认分别记录，打开不自动确认。没有外部推送提供者时可交付站内通知，但必须显示外部送达未配置。

信息通知不自动暂停 Run 或建立人类请求。需要人回答的通知只引用既有唯一请求，多渠道共用它，投递失败不回答或关闭请求。外部送达按用户设置、紧急度、安静时段、频率、去重合并与当前渠道资格决定，agent 不能指定越权收件人。外部摘要默认裁剪敏感内容，完整内容回到认证入口重新鉴权。拒绝不能泄漏目标渠道是否存在，多次投递只属于同一个逻辑通知。对应 CAP-SJ08；通用通知行为由通知拥有者落实，不属于本域新增通道实现。

### 可观察场景与交接顺序

以下演示是产品判据，不表示已经执行。

1. agent 在逐条模式创建明日安排。用户应看到草稿、作者和理由；跨过时间仍没有 Job。owner 转正合法草稿后看到下一严格未来时隙，重复原操作不再转正。修改时间则看到一个后继身份、旧身份终态及双向关联。
2. 建立跟随环境和显式绑定各一份安排，并先接受一个 Job。切换上海与中国日历为东京与日本日历后，跟随安排未来采用新环境，显式安排身份保持，旧 Job 的时区、日历、指令保持原值。
3. 使用 3 个合格时隙、最多 2 个 Job，令首个时隙因重叠跳过、第二个 Job 取消。用户应看到两个计数各自变化且取消不退款；再次扫描不能多建 Job。
4. 在 10:30 恢复具有 08:00、09:00、10:00 漏过的周期执行。latest 1 只选择 10:00；下一轮不能补 08:00。再用一次性等待恢复和纯提醒重复场景，应分别看到原意图等待及过窗不补，不能套同一种超时。
5. 分别运行程序、新会话 agent、已有会话 agent。应看到无会话程序、一份新会话、指定已有会话中的本次关联执行。使已有会话不可用，应看到受阻且没有替代会话；入队时不能显示执行完成。
6. 让两名用户订阅同一系统功能。两者同刻均有自己的工作，重复扫描不多建；取消其中一份订阅后，另一份仍继续。撤销 agent 的持续全权同意时，仅依赖它的安排受阻；重授后仍等待逐条确认。
7. 让 child 完成但 master 忙，再使归档暂时不可用。应看到原执行结果、有界待收、独立发布和归档状态；恢复只处理未完责任。内部报告不能直接出现在普通结果中心。
8. 自唤醒后重启再恢复，应继续原 Session 的同一工作；取消后不得复活。持续只自唤醒应触发原无进展治理，有真实推进应不被误判。
9. 提醒在窗口截止前接受、截止后送达，应保持已接受而非错过；首次接受正好到截止则显示错过且零补发。断网后重新打开站内入口，应能取回既有通知，打开不等于确认。

交接建议先验证日历与时间计算，再验证管理、环境、双限额及接受恢复，随后验证三条执行路径、订阅、同意、回传和归档，最后核对人工入口、程序调用与 agent 工具结果一致。跨域资格和真实结果回执是接受与执行的前提，不能以模拟成功替代；此顺序不拆分完整终态的产品范围。

## 未决问题与待定事项

以下保留发布承诺及实际技术、来源承接缺项。已确认的产品选择不再列为待裁决；技术缺项不撤销完整业务义务。

<a id="q-sj01"></a>

### Q-SJ01 发布版本与产品交付接受

完整目标范围已确定。产品负责人尚须指定其发布版本、实际装配和交付接受条件。具体系统功能目录及各自参数由功能拥有者提供，不能从框架支持推导任意系统程序已获准。发布版本未定不成为缩减上述能力或重开环境绑定、次数、编辑及补跑选择的理由。

<a id="q-sj02"></a>

### Q-SJ02 精确身份、公开形状与只读查询

用户需要辨认完整安排、已接受的单次工作及原操作，查看该 Job 固定的要求、来源和真实进度，见 J-SJ01、J-SJ03、J-SJ10。公开身份、查询形状及目标实现未完成核验时，尚不能确认查询能够认回原工作，或成果上报始终绑定当前 Job。

技术拥有者为Schedule/Job 公开定义及当前 Job 绑定、读面拥有者。完整问题、约束、选项及承接义务见[技术采用 Q-SJ02](../../../../packages/schedule/schedule/docs/internals.md#q-sj02)。

<a id="q-sj03"></a>

### Q-SJ03 时间算法与最新依据校验到接受

用户核对未来时刻后，定义或日历修订仍可能改变尚未接受的候选；到期工作必须采用接受时的有效依据，见 J-SJ02、J-SJ03。算法与校验到接受机制未经目标验证时，尚不能确认预览可复核或旧预算不会被误接成过时工作。

技术拥有者为日程日期/接受协调者与日历公开计算/版本拥有者。完整问题、约束、选项及承接义务见[技术采用 Q-SJ03](../../../../packages/schedule/schedule/docs/internals.md#q-sj03)。

<a id="q-sj04"></a>

### Q-SJ04 耐久受理、补跑区间与控制竞争

用户在回执丢失或重启后需要认回原 Job、继续原等待，并只补声明区间内最近最多 N 次漏过工作，见 J-SJ03、J-SJ04、J-SJ09。受理与控制恢复机制未经目标验证时，尚不能确认不会重复建 Job、重复计次数、分页补光旧积压或复活已经取消的执行。

技术拥有者为Job 接受/控制协调者、调度及真实存储提供者。完整问题、约束、选项及承接义务见[技术采用 Q-SJ04](../../../../packages/schedule/schedule/docs/internals.md#q-sj04)。

<a id="q-sj05"></a>

### Q-SJ05 执行、目标证据、停止与通知结算接入

用户需要分清装配未成、目标未达、前序停止未确认以及执行成功但通知未达，见 J-SJ05、J-SJ06、J-SJ08、J-SJ09。执行与通知接入未经目标验证时，尚不能确认替换工作会等到所需停止证据，也不能用 Run 结束或通知回执代替整份 Job 的真实结算。

技术拥有者为Job 整体协调者、Session/执行/目标检查与正式通知拥有者。完整问题、约束、选项及承接义务见[技术采用 Q-SJ05](../../../../packages/schedule/schedule/docs/internals.md#q-sj05)。

<a id="q-sj06"></a>

### Q-SJ06 提供者、配置采用与生命周期符合性

提供者替换、依赖失效或部分启动失败时，用户需要知道已接受的工作、停止控制和未完通知仍由谁保管或接续，见 J-SJ11。配置与生命周期方案未经目标验证时，尚不能确认换代不会丢失原工作、重复受理或把撤除实例显示为业务完成。

技术拥有者为日程提供者、合法治理与装配拥有者。完整问题、约束、选项及承接义务见[技术采用 Q-SJ06](../../../../packages/schedule/schedule/docs/internals.md#q-sj06)。
