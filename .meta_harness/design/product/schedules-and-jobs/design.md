# 日程与作业产品候选

本稿依据正式责任、冻结旧产品原文及最新用户决定筛选细化，尚未接受。完整能力候选不表示阶段支持或实现；

## 产品需求描述

人和 harness agent 需要把短、中、长期目标安排到未来，而不必让创建安排的会话持续运行。系统也需要按部署政策安排预先定义的机械工作。用户应在一个入口表达要做什么、何时做、遇到特殊日期或已有工作时怎么办，以及需要怎样通知；保存的是一份完整 Schedule。它包含 Routine 工作描述，Routine 没有独立身份、共享可变对象或另一路生命周期。采用出厂预置只是将已展示内容填入安排，后续编辑及各次工作状态属于这份安排。

安排、单次工作及实际结果需要分别指认。预览或下一次预算只是候选；候选在最终校验后被接受才形成 Job，即使它随后等待执行或等待前序停止。一个 Job 固定本次工作要求、来源时刻、采用的日期依据及策略，后改 Schedule、出厂内容或日历不能回写它。实际受理、开始、执行目标完成、通知送达和人已阅读各有不同证据，不能用一次请求成功或 Run 结束宣告全部完成。

系统、租户、发起者及通知目的地分别表达。租户由组织和账号共同确定；创建者会话归档或成员资格变化不销毁独立 Schedule、Job 和历史。每个入口按当前资格操作，到期接受与真正开始仍检查各自所需权限和依赖。失权或不可用明确拒绝、失败或受阻，不改投另一租户，不复制过去授权，也不靠系统调度取得任意资源权。已经开始的调用继续沿其原控制及结果责任收场；成员资格变化不自动冻结全部业务。

框架支持明确的时间、日期、补跑、重叠和通知声明，合法治理配置与可替换提供者承接它们。规则支持范围不由某个 cron 库或部署参数决定；未声明的策略不能由技术默认补齐。具体提供者、公开形状、超时、退避及容量参数继续由技术/治理拥有者确定。本稿不代选通道、数据库或阶段清单，不借旧 PF 的阶段排除宣布某项新提供者已经支持。

### J-SJ01 一次保存完整安排，再控制后续

用户或获授权 agent 希望创建、编辑或采用预置安排。前提是归属、工作类型、内容、完整时间规则以及适用的日期处理、补跑、重叠、执行和通知声明明确，当前保存资格与计算依赖成立。成功创建一次保存完整定义并启用；编辑可只提交局部意图，但保存结果必须整体一致，保持原管理状态。预置内容和来源可读，采用后由 Schedule 持有，不反向修改预置或其他安排。

缺字段、歧义、不支持的规则/停止策略、缺日期依据或无权时拒绝，不能留半份已生效定义。可按需预览，不强制多一道人工批准。pause 阻止新 Job，resume 只恢复暂停安排并按声明处理漏过；stop 永久结束后续，不能 resume 复活。编辑不能启用已暂停或结束安排，停止不自动取消已有 Job。重复控制返回真实状态，回执未知先查原保存或控制事实。对应 CAP-SJ01、CAP-SJ11。

### J-SJ02 核对时间意图与特殊日期

用户希望看到下一次及有界未来时刻、日期原因与实际依据。时间规则明确计算时区、起算、包含边界的开始/可选截止、可选次数、排除日期和正整数重复间隔。相对一次性日期保存时解析为固定日期。

常规按日、周、月、自然季度、年重复，周从周一开始。同一规则内可明确列出多个月份、星期或日内时刻。系统不能要求用户拆成多份 Schedule 来代替同规则多值。位置型仅支持所选月、季度或年内第 N 个或最后一个指定星期几或工作日，N 为正整数。不支持事件条件、任意脚本和无限嵌套组合。

每份安排明确选择保持原日、跳过非工作日、前移或后移至最近工作日。后三者及位置型工作日规则需要明确业务日历；保持原日不免除规则自身依赖。原日期边界/排除先检查，日期处理后再检查结果日期边界/排除，最后解释夏令时和合并碰撞。平移保留本地日内时刻，可以跨周期，不能越开始/截止或首次启用；平移结果被排除就跳过，不继续找第二个工作日。月内不存在的日期/位置和夏令时不存在的本地时刻跳过，夏令时重复时刻取第一次；均不能偷偷改成别的日期。

相同实际定义、时区和日历版本的引用及展开预览一致，显示来源、平移、排除及次数限制。缺覆盖、非法规则、无权或查询故障分别说明，不能猜工作日或伪装成合法空结果。预览不保存、不扣次数、不接受 Job、不预测实际重叠和执行时长，也不授后续写权。取消查询只结束本次观察；再次查询可以采用新依据，并如实显示变化。对应 CAP-SJ02。

### J-SJ03 到期时接受本次工作

调度方希望把合法候选可靠承接成一次 Job。前提是 Schedule 尚允许新工作、当前归属与资格成立、必要依据/依赖可用、剩余次数允许。日常预算下一次候选 t+1；调派前按有效完整定义及最新已发布日期依据重新校验，并保护校验到接受之间的一致性。成功接受固定本次定义、策略、原定时刻、合并来源、日历身份/版本与解释，建立可查询的 Job 和未完责任；等待也是已接受事实。

定义、日历、控制或资格在接受前改变时重核或给出冲突/受阻，不能执行过时预算。未接受候选落到同一有效时刻时合并，保留来源；新候选撞上本日程已有 Job 时记跳过，不能再创建或向旧 Job 回填来源。已处理来源后来被日历重算到另一日也不能重复产生工作。实际创建一个 Job 计一次，合并计一次；跳过、排除不计，等待/失败/取消不退还次数。接受回执丢失先认回原工作，不盲目再建。对应 CAP-SJ03、CAP-SJ06。

### J-SJ04 从停机、暂停或缺依据中恢复

用户希望恢复后处理真正漏过的工作，并知道哪些没有补。以恢复处理当前时刻 T 为界，漏过仅含首次启用之后、原定截止内、尚未形成 Job 且未已有明确跳过处置的合法时刻。明确选择不补，或补最近最多 N 次，N 为正整数；它是这一漏过区间的业务上限，不能用下一轮分页继续补光更早积压。

按最新依据找有效候选，已选补跑与 T 当刻正常工作合并后按原定时刻从早到晚逐个处理，并在接受前重核和适用重叠声明。T 当刻不占 N，仍可能被正在执行的较早补跑按重叠声明跳过，原因必须可查。超过 N 的更早时刻记不补；已有等待 Job 继续原工作，不占补跑名额。原定截止内漏过可在截止后受理，直到区间处置完成才自然结束；手动 stop 则不再接受任何新 Job。次数上限不能被补跑突破。

权限、日期依据或停止确认不足时如实受阻，未知不假称已经做过或从未发生。恢复读原接受、跳过、取消及执行/交付事实，只续原未完责任。原定时刻与实际受理、开始时间分别保留；重算提前到 T 之前的未处理候选同样受补跑约束。对应 CAP-SJ04、CAP-SJ10、CAP-SJ12。

### J-SJ05 遇到前序尚未结束的动作

用户明确选择跳过本次、停掉先前后执行、独立并行或等待后执行。比较同一 Schedule 的实际前序集合：含执行的 Job 看执行部分，纯通知看发送/交付动作；组合通知尾部不单独阻止下一次执行，仍由原 Job 持责。其他 Schedule 及共享外部文件不自动归入此策略。

跳过不创建 Job且不再作为漏跑；并行建立独立 Job/专属会话和结果；等待接受固定 Job，按原定顺序排在实际前序之后。替换先接受新 Job，向仍在执行或等待的前序发出明确停止控制，所需停止得到确认才开始新工作。此前并行留下多个前序时，非并行声明对实际集合处理，不能只看最近一个。

已知机械动作不能满足停止策略时保存即拒绝；停止失败、未知或未确认时新工作受阻，不能偷偷并行。Session 归档业务取消完成、控制请求受理或客户端断开不证明需要停止的原执行已经停止。已有工作固定输入不变，停止控制不回滚外部效果；新替换 Job 后来被取消也不能撤销已发出的旧工作控制。依赖恢复时先查原控制和队列，不能重建已有 Job。对应 CAP-SJ05。

### J-SJ06 agent 在专属会话交付成果

租户 Job 希望由 agent 完成明确目标。前提是当前启动资格、所选已发布 AgentDefinition 的合法采用、显式运行模式、工作资料及必需装配成立。每个需要 agent 的 Job 新建专属作业会话；它不是自动父子派发，不复用创建者或上一 Job 的整段上下文/授权。需要历史成果或工作区时明确引用并按当前资格读，不指定工作区即为空；无人值守不能自动跳过权限。

任何 AgentDefinition 都附加绑定当前 Job 的成果工具与 Loop 目标完成检查。读取、进度、候选最终成果及问题上报分别记录；模型不能换一个 Job ID 报给别处。最终成功要求有候选成果及可说明的达成依据，完成检查对照固定目标和交付要求判定达成。普通回复、submit 成功或 Run 完成均不足。Agent 产出资产仍按实际工作区/租户提交；不能直接产出组织资产或替用户手动提升。

装配失败不声称已开始；目标未达不得正常报成功，无法继续沿原等待、失败或停止机制说明原因，不无限续跑或抵消用户停止权。恢复仍是原 Job/Session/Run/调用及结果消费位置，重建 attempt 不新建业务重跑。同 Session 的 AgentDefinition 标识及执行类型固定，合法版本/实现变化按原资产与装配拥有者记录，不另冻资产副本。不可用工具替换件是原逻辑调用的不可用结果，不冒充真实工具成功或目标完成。对应 CAP-SJ06、CAP-SJ07。

### J-SJ07 系统按部署条件做机械工作

系统希望周期执行已定义维护功能。系统 Schedule/Job 归系统，不能伪造特殊租户；机械执行不建立 agent 会话、不调用模型作完成判断。功能及部署管理入口明确允许操作、真实资源资格和实际成功/失败/未知依据，按同一时间、受理及历史规则承接本次工作。

普通租户、获装配日程工具的 agent 或组织管理员不因此取得任意系统机械操作/全租户查询权，也不能只改所有者把租户安排转换为系统安排。有意停止的服务不得由备份安排偷偷启动；只有已定义操作真实成功才报完成，触发成功不足。不能停止时明说；恢复先查原操作及效果，只续合法未完部分，不将未知重放为新机械业务。具体系统功能清单和部署政策由拥有者确定，本稿不选工厂内容或启用频率。对应 CAP-SJ06、CAP-SJ11。

### J-SJ08 到点通知或按执行事件通知

纯通知 Job 到期交付已定义内容，不创建 agent 会话。需调查、分析或生成成果则包含执行；执行并通知仍是同一个 Job。组合声明选择非空的开始、成功、失败、取消事件集合，并明确各事件内容和目标租户。实际开始不是排队；成功有目标依据，失败是已确认不能继续，未知不是失败。每个本次已选实际事件产生一次逻辑通知，未选/未发生显示不适用。

本域保管事件和未完通知义务，经通知能力可靠承接给定内容，再消费真实交付事实。正确目标租户持久可取回才算送达，在线、已读、受理回执和成果提交均不能代替；不改投同账号其他租户。纯执行不附送通知；submit_result 不隐含 send，agent 主动 send 是独立意图，不能替配置义务。

纯通知只有送达才成功；组合只有执行目标达成且实际触发的全部通知均送达才整体成功。失败/取消的执行不会因通知送达变成功；执行成功但通知未达保留真实部分完成。没有事件命中不制造通知。投递失败不递归产生执行失败事件，不重做源机械/agent工作，取消后既有通知义务仍保留。通知回执未知先查原通知，不能盲重发；精确交接机制与对象分解由双方技术设计落实。对应 CAP-SJ08。

### J-SJ09 取消这一次已接受工作

合资格用户或管理 agent 希望取消指定 Job，读权不能代替取消权。尚未开始的 Job，包括排队、等停止确认或装配前受阻，可不依赖 Session/Run 取消；成立后不再启动，恢复也不复活。已开始 agent 执行记录停止意图，沿原优雅取消或显式强制停止规则推进；物理停止未确认时分别呈现实际进展，不把请求受理当停止。机械功能按自身可停止边界处理。

纯通知发送前取消获胜则阻止发送且不另发取消通知；已发送或效果未知不承诺撤回、不把未知改成取消成功或因此重发。执行已终结时保留原成功/失败，组合未送达通知继续持责。组合执行取消成立，包括开始前取消，只在原声明选中取消事件时触发通知；不伪造开始或成功，已有通知和迟到效果留归原 Job。

取消不改 Schedule、其他 Job、固定输入、次数或历史，不使它再进入补跑。开始/完成/取消竞争给出可追溯顺序；重复取消认回原控制，不重复执行或通知。回执未知查同一 Job；完成检查不能拉起新执行抵消取消。替换发出的原控制仍独立成立。对应 CAP-SJ09、CAP-SJ08。

### J-SJ10 查看安排、工作与未完成责任

合资格者希望按 Schedule 或 Job 查询完整定义、管理状态、原定/实际时刻、采用来源、等待/执行进度、成果、通知结果和漏过/跳过原因。查询只读、按当前租户及字段资格呈现，不能从读权取得管理、取消或源材料权限。后台调度、系统归属和通知目的地也不授全局读权。

历史不因 stop、Session 归档、失权或实例退出自动删除，物理归档/索引优化不缩短承诺查询范围。当前 Schedule 不能覆盖 Job 历史；读面滞后、查询故障与业务未知明确区分。调用超时或找不到投影先核对原接受和责任，不由查询触发重跑、补送或新安排。客户端关屏/离线只改变观察，不使已受理工作或历史消失。对应 CAP-SJ10。

### J-SJ11 更换调度提供者并接续工作

装配/运维希望调整合法策略或更换运行实例。前提是能力支持、配置生效点、依赖和接续协议明确。停止新准入后，按实际阶段保管或可靠移交已接受 Job、未处理区间、停止控制、原执行/通知关联和未知；移交确认前原方持责。下一方认回原事实，继续未完部分，不重复受理或重做已发生动作。

缺依赖、无效配置、不能安全核对或没有承接方时明确受阻与责任归属，不删登记后宣称完成。撤除仅清理自有监听、计时器、注册和使用权；不恢复整个旧快照抹他方变化，也不使外部输出可逆。晚到结果仍回原工作，新实例不得借旧回执产生第二份 Job。进展依赖当前资格、依据、持续提供者和合法策略，不承诺所有故障下无条件完成或固定耗时。对应 CAP-SJ12。

## 阶段与版本支持承诺

### Q-SJ02 精确身份、公开形状与只读查询

限制公开接口及读面实施，不影响完整CAP选择。 技术拥有者为Schedule/Job 公开定义及当前 Job 绑定、读面拥有者。完整问题、约束、选项及承接义务见[技术采用 Q-SJ02](../../../../packages/schedule/schedule/docs/internals.md#q-sj02)。

### Q-SJ03 时间算法与最新依据校验到接受

### Q-SJ04 耐久受理、补跑区间与控制竞争

限制受理/控制/恢复实施，不把存储机制变成产品票。 技术拥有者为Job 接受/控制协调者、调度及真实存储提供者。完整问题、约束、选项及承接义务见[技术采用 Q-SJ04](../../../../packages/schedule/schedule/docs/internals.md#q-sj04)。
