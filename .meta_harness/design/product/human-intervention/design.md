# 人在回路产品设计

本稿定义供负责人选择的完整能力及适用条件，尚未接受。上层以项目要求、已接受架构和正式领域分工为准。实现状态与阶段采用分开记录。

## 产品需求描述

人在回路让原工作在需要人的信息、方案选择或授权决定时，提出明确问题，等合资格的人处理，再把有效答复交回原位置。人应能知道谁在问、为了哪项工作、自己要决定什么，以及处理后哪些等待会解除。人的回答不证明动作已经执行，也不证明外部效果可撤回。

有资格的人可以从原会话的卡片或所属租户决策池处理同一请求。所有仍需要人输入的卡片都进入相应池子，不因会话数量、会话未打开、Agent runtime 不在内存或交付面关闭而遗漏。池子说明所属租户及所在部署位置，列出在该范围内等人的卡片；它是陈列入口，不持有另一份决定或执行生命周期。跨位置展示不隐含跨节点汇总或新的数据读取权。呈现与答复均核验当前资格，无权内容不出现在池子、消息提示或诊断中。

卡片必须自包含地说明问题和可选后果，保留原请求来源、原会话、动作与参数、等待位置及适用依据，能够回到原工作。来源至少分得出 agent 主动提问、系统放行判断和哪一件拓展件。这些来源的卡片均须允许人不选任何选项，独立提交自由文字。人可以回看上下文，但不必翻阅完整历史才理解正在请求的决定。卡片说明解除哪一项工具等待或哪一轮 Run 等待，部分答复是否仍需等待，以及后继判断可能再产生卡片。

授权与信息不同。问询的答复补充信息或选择；请示和系统准入的答复交授权拥有者解释，不能仅因文本包含“同意”就改变权限。放行判断先执行现行结构化权限、授权表达和会话模式规则，明确禁止不出卡，不允许人的普通批准、额外拓展件或工作区内容越过禁止。获准动作仍须满足实际环境和隔离条件。卡片只关联原动作及生效参数，改变参数、实现或授权依据后不能自动复用旧批准；保持同一调用约定及绑定的 runtime 换代本身不等于新动作。原会话的 AgentDefinition 标识不随 Agent runtime 实例替换。

系统不能替人给答案。没有超时默认批准、默认拒绝或无人查看时的自动答案；拓展件和脚本也不能代答已出的卡片。明确拒绝回答是人的合法处理，必须与不同意动作、调用失败和系统故障分开。原等待已经确定终局时，卡片失效而非收到伪造答案；未知状态不能冒充终局。人的授权可以依既有规则影响后续相同请求，合法权限配值也可以减少以后询问，二者都不等于对已出的卡片代答。MCP 的静态凭据与 OAuth 取得是合资格人的配值操作，不由 Agent、Run 或 HITL 卡片代办。

### J-HI01 回答 agent 的问询

人的目标是一次看清 agent 还缺哪些信息。前提是原工具发起了问询，保留有效的工具执行和消费位置，答复者有当前访问资格。一次 Ask 问询可以提出多个问题，每个问题形成卡片。每个问题必须有问题描述、文本候选项及系统保证的自由作答路径；图解可选，但不能替代文本候选项。人可以不选任何候选，独立提交自己的文字答复。

人在卡片上答复或明确表示不答，答复交原工具解释；同次问询要求的卡片全部处理后才解除该工具的等待。Ask() 固定以前台阻塞原调用，不可转后台。其他工具内部的人工等待按其声明的前后台和等待合同关联；后台工具等待只影响该工具，不自动阻塞整个 Run 或其他工具。

提交被拒时说明资格、卡片状态或输入原因，不把未接收内容显示为已生效。工具原执行已终局则卡片作废并说明依据；单纯 Agent runtime 退出不据此关卡。恢复认回原请求和已答部分，不重问已生效问题。取消、插队及工具收场沿原工作规则处置，不把“不回答”记为系统失败。能力为 CAP-HI01、CAP-HI05、CAP-HI06、CAP-HI07、CAP-HI08。

### J-HI02 在动手之前处理 agent 的请示

人的目标是知道拟执行动作、影响及退路，再决定准不准。前提是 Ask 的请示命令在当前协作与权限条件下可用，而且尚未用本次请示作执行依据。卡片说明动作和对象、为什么要做、影响、可逆性及替代办法；提供批准与拒绝两项明确选择，以及系统保证的自由作答路径。人可以不选批准或拒绝，独立提交文字。提出请示时动作仍未因本次请求发生，人拒绝不需要为本次请示清理外部效果。

有效答复保留原话并回原请示位置，由原授权及工作规则解释。文字能明确读成准或驳时，沿原规则处理；读不出准驳时，标明“人有话说但未给准驳”，不合成批准、拒绝或明确拒答。原 agent 把原话作为指导，调整后再请示，不能据此执行拟请示动作。人明确选择“不回答”时原工具取得没有答案的含义，不能当作批准；自由文字不是无限授权。

请示获准不解除明确禁止或环境要求，执行前仍确认同一动作、参数、实现与有效前提。若输入、资格或原状态改变，返回明确不适用或拒绝，不隐瞒改参后执行。恢复不重复产生已经答过的请示。能力为 CAP-HI02、CAP-HI06、CAP-HI08。

### J-HI03 处理系统的放行卡片

人的目标是理解为什么这次动作需要判断，并选择自己有权给出的授权范围。前提是原动作通过明确禁止的检查，但现行授权规则仍要求问人。系统提供可理解的动作说明及合法选项；支持拒绝、仅本次、本会话后续同类，以及本租户相关会话的租户权限设置选择。选项是否可用取决于它将写入的值是否在当前允许范围、操作者是否有相应权限；能答会话卡不自动取得修改租户设置的资格。租户持久选项写入租户权限设置，由真实写设置资格和组织允许上界约束。不能展示一个按下去不生效的长期授权选项。

人也可以不选任何授权档位，在这张系统卡上独立提交自由文字，不必先作准驳或授权范围选择。原话须保留并交原准入及授权拥有者按现行规则解释。是否形成有效授权及其范围，仍由原规则决定；提交文字本身不自动批准动作或写入权限设置。

系统已确定需要询问，但生成有效卡片确定失败时，相关动作被拒、不执行。原 agent 得到准入故障造成的拒绝及真实原因，人也通过合法可见的方式得知故障。系统不把故障记成人的拒答，也不建立等待不存在卡片的有效人工等待。卡片保存确认未知属于另一种情况，须保留原请求身份查询，不能仅因未知就改判为生成失败或再出一张卡。

人作出的决定与适用授权记录回原拥有者，按原动作或原批次的等待条件，由原执行者推进。卡片显示、答复有效、权限或授权生效以及动作真实发起分别可确认。明确禁止、准入组件不可用或继续条件不满足时不拿 HITL 补出许可。回执未知按原卡查询，不能再制造一项独立授权。能力为 CAP-HI03、CAP-HI04、CAP-HI06、CAP-HI07。

### J-HI04 处理拓展件的一轮卡片

人的目标是处理某一拓展位置提出的额外判断，例如生产操作前的信息核对。前提是拓展件在获准位置具备相应干预力，原 Run 尚可推进。卡片标明拓展件及其问题，使用同一决策池、答复与不代答规则。选项由拓展件提供，人仍可不选任何选项，独立提交自由文字；原话交原拓展件解释，不因自由作答取得系统授权权威。拓展件可以收紧或再问，不能把系统要求询问的动作直接放行。导入 hook 的“允许”或代填答案不能成为本系统授权，导入方须明示其在这里没有代答或放宽的效果。

同一批动作的各条前置链分别判断；每个动作已有结论或停在等待后，相关卡片形成这一轮。所有判断齐备且卡片全处理后，原链才可执行获准动作，已通过动作也不能先做。同一动作后继拓展件可能再出下一轮，人在卡片上应能理解这一点。拓展出卡执行报错沿正式扩展错误策略及有效声明处置，保留真实失败和可见结果，不伪造人的答复或等待不存在的卡片。恢复复用已记录的判断、模型结果及效果，原答复回原拓展件和位置，不简单重跑非确定函数。依赖撤除或版本不兼容时保留原等待，报告合法接续受阻，由原拥有者处理，不伪造否决或新答案。能力为 CAP-HI04、CAP-HI05、CAP-HI07、CAP-HI08。

### J-HI05 从会话或决策池作答一次

人的目标是集中处理多个会话的等待，也可留在会话内处理。前提是当前租户、位置和读取资格明确。两个入口展示同一卡片，提供同一份来源、原状态及有效处理结果；所有仍需输入且操作者有权读取的卡片可发现。人在任何入口作出有效答复后，另一入口不再显示它仍待处理，允许投影短暂滞后但须说明状态并按权威查询纠正。

并发提交只允许一个有效答复。另一提交获得实际已处理结果或冲突说明，不能继续原工作第二次。技术重传查同次提交，人的新提交不能只因文字相同任意去重。撤权、租户切换或无权查询时不披露原内容，事实仍由原拥有者保管；成员重新有效不铸造新租户或自动恢复已终局等待。能力为 CAP-HI05、CAP-HI06、CAP-HI09。

### J-HI06 在等待期间补消息或改变工作意图

人的目标是补充交代，或明确现在先处理另一件事。前提是原会话可受理相应输入。普通消息仍走原受理和队列，不猜成卡片答案、不覆盖已有问题；等待期间仍接收合法消息和后台结果，到原工作能消费时处理。交付面给出正在等待及新消息排队的可理解提示，取消和控制入口仍可使用。

人明确插队时沿输入与工作控制规则处理受影响等待：Ask 取得人拒绝回复的含义，Run 上本轮悬置卡片作为明确拒答处置，需批准的动作不据此发生；卡片上的拒答只处理这一张，粒度与插队不同。插队是人发起的事件，不是超时系统代答，其消息仍是消息。控制受理失败或未知时不假称等待已解除；已成立处理按原身份恢复，不把插队当作整个 Run 已取消。能力为 CAP-HI06、CAP-HI07、CAP-HI08。

### J-HI07 在停止、归档或资格变化后处理旧卡片

人的目标是知道旧问题是否还值得回答。前提是原工作拥有者能说明等待和业务状态。原工具或 Run 已确定终局、相应等待被合法控制解除，或会话业务归档生效时，关联卡片停止接受新有效答复，保留原问题、已答事实及失效依据。仅 Agent runtime 被回收、界面关闭或部署暂时失联时，不推定原工作终局。

会话归档按业务取消解除等待和推进依赖，传播适用取消，不等所有模型与工具物理停止。独立执行继续负责效果、费用、迟到结果及资源，卡片失效不宣称外部效果已撤回；撤销归档也不自动恢复旧调用。成员资格失效限制新访问和作答，但不直接归档、销毁租户或冻结全部业务。自动归档按已启用、会话未标记常驻及原空闲规则判断，不把看不见卡片当作没有工作。答复与控制竞争按原权威结果收束，迟到答复不复活终局。能力为 CAP-HI06、CAP-HI08、CAP-HI09。

### J-HI08 在恢复或换代后接续原等待

人的目标是自己的回答被接上，不再重答、不重复做事。前提是原卡片、答复、等待位置、采用依据和未完成交接责任可靠保存。Agent runtime 不在时仍可答卡；有效原执行者尚在则接续，已交还则按原 Run 的合法推进条件换实例。工具实际连续性丢失按工具自己的规则收场，不由 HITL 把新工具伪装成原执行。

答复接收和原等待更新保持可恢复一致；通知或响应丢失不改已提交事实。恢复先查询原身份，复用已答内容和已完成判断，只接续未完成责任。必要存储或查询不可用时保留未知及下一责任，不新出同一张卡或盲目重发动作。绑定、参数或采用依据不兼容时暂停依赖路径，显式重判或由原拥有者关闭，不转移旧许可给新实现。能力为 CAP-HI06、CAP-HI08、CAP-HI09。

### J-HI09 知道有问题在等自己

人的目标是在未打开原会话时仍能发现等待。前提是卡片已由原请求确认且有获准接收范围。交付面在相应租户与位置呈现等待入口；需要发送等待提示时，来源业务提出允许披露的内容与目标，正式通知能力负责自己的受理、送达与查询。卡片产生、提示已发、持久送达、已读和人的处理分别表达，不把显示或已读当作答复。

提示失败不删除卡片、不代答、不重做产生卡片的原动作；送达未知保持原通知身份并交通知拥有者处置。没有人查看时卡片照常等待。跨租户内容和秘密不为方便提示而外泄。具体渠道、对象分解及保管条件按通知契约细化，不在 HITL 中另造通知发送权威。能力为 CAP-HI05、CAP-HI09。

## 阶段与版本支持承诺

0.0.0 → 0.1.0 的完整 CAP 清单、产品适用条件及能力依赖等待负责人选择，见 Q-HI01。不从旧 PF 的“本版”范围、其他领域全部支持或目录存在推导阶段采用。

CAP-HI01–CAP-HI04 的卡片路径依赖 CAP-HI05、CAP-HI06、CAP-HI08，以及现行身份/授权条件，不能选有问题却不可发现、答复却不可可靠交回的组合。Ask 多问题及 Run 拓展轮次还依赖 CAP-HI07，在各自原等待范围适用；选择 Run 扩展批次时须保留同批判断屏障。CAP-HI09 的等待呈现依赖合法卡片及当前披露资格，需要通知时再组合正式通知能力及其受理/送达条件。技术部署可配置合法策略及机制参数，但未确定数值不授权缩短有效人工等待、补默认答案或删去其他业务不变式。

## 未决问题与待定事项

阶段选择归产品负责人。技术采用归具名技术拥有者，技术缺项不撤销已经明确的业务义务。实现状态仍为未核实。

<a id="q-hi01"></a>

### Q-HI01 选择 0.0.0 至 0.1.0 的完整能力集合

负责人需要确定要交付哪些 HITL 能力及合法适用条件，旧 PF 的“本版”不构成本轮选择。 0.0.0 至 0.1.0 采用哪些 CAP，并适用于哪些场景、主体及依赖？

选择以 CAP-HI01–CAP-HI09 的完整定义、产品条件和能力依赖为单位。

采用任一能力都须保留相关唯一处理、当前资格、不代答及原工作恢复规则。

具体 provider、机制、版本、公开形状和验证方案不是先选 CAP 的前置。

- 声明采用集合。逐项选 CAP 及产品条件，实际公开承诺与验证范围随后据此收束。
- 暂不采用某能力。明确该能力未支持及受影响旅程，不用删减完整能力来声称支持。

不代选能力子集。负责人完成具名选择后，技术采用落实所选承诺。

影响阶段交付和消费者可用范围，不改变已定业务不变式。

<a id="q-hi02"></a>

### Q-HI02 采用公开请求、答复及原等待接口

人需要从卡片看清原工作及答复解除的等待，并把答复交回原工具或拓展位置，见 J-HI01 至 J-HI04。公开接口未采用时，这条跨入口答复路径仍缺少可核对的消费依据。

影响数据形状和组合实施，不留空整份业务规格。 技术拥有者为HITL 请求定义拥有者与原 Tool、Run 拓展、交付面及授权消费者。完整问题、约束、选项及承接义务见[技术采用 Q-HI02](../../../../packages/human-intervention/human-intervention/docs/internals.md#q-hi02)。

<a id="q-hi03"></a>

### Q-HI03 采用唯一答复与原等待一致交接协议

人在会话和决策池同时作答、作答与归档竞争或保存回执丢失时，需要查到唯一有效处理及原工作是否仍在等待，见 J-HI05、J-HI07、J-HI08。协议未采用时，尚不能确认答复不会丢失、重复推进原工作或把未确认的授权设置显示为已生效。

阻塞可靠提交实现与故障验证，业务义务已明确。 技术拥有者为原等待协调者、HITL 保管与原授权/设置拥有者。完整问题、约束、选项及承接义务见[技术采用 Q-HI03](../../../../packages/human-intervention/human-intervention/docs/internals.md#q-hi03)。

<a id="q-hi04"></a>

### Q-HI04 采用拓展等待接续与撤除协议

人已答的拓展卡片在重启或换代后仍应交回原位置，不应要求人重答或重复已经发生的动作，见 J-HI04、J-HI08。接续不兼容时，人需要知道原等待仍被保管且继续受阻，旧答复不能成为新动作的许可，这条接续路径仍待技术采用核实。

影响拓展重装配、在途恢复和维护；不重开授权产品规则。 技术拥有者为原 Run/Tool 拓展调用与等待协调者、HITL 保管及装配拥有者。完整问题、约束、选项及承接义务见[技术采用 Q-HI04](../../../../packages/human-intervention/human-intervention/docs/internals.md#q-hi04)。

<a id="q-hi05"></a>

### Q-HI05 采用合资格等待投影与通知交接

有权人未打开原会话时也需要发现所属租户与位置的待答卡片，失权后不能继续看到受限内容，见 J-HI05、J-HI09。投影与通知交接未采用时，尚不能确认待办不会遗漏，也不能把提示已读或发送失败当作人的答复。

影响 UI/通知组合和披露验证，渠道配置不削弱待答可发现规则。 技术拥有者为HITL 查询/呈现拥有者、交付面与正式通知拥有者。完整问题、约束、选项及承接义务见[技术采用 Q-HI05](../../../../packages/human-intervention/human-intervention/docs/internals.md#q-hi05)。
