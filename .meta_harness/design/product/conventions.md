# 故事卡的格式契约

**一张故事卡长什么样，每个字段是什么意思，场景怎么编号，对账器守哪几条。**
读卡的人靠它读懂，写卡的人靠它写对，对账器靠它解析——三方共用这一份。

**怎么切卡**——第一张卡切多薄、一张卡证明几件事、远处的卡没想清楚怎么办、顺序谁来定——不在这里：
那是落字的人才需要的判断，归 `product-design` skill 的「切故事卡」一节，只此一份。

## 故事卡是什么，不是什么

**一张卡是一个可以单独演示的用户可见结果**：它由若干条验收场景（`acceptance.md` 里「可观察场景」的行）组成，
小到一两天能从验收走到合入。卡回答的是**先交付哪一块、交付了怎么看得出来**。

**卡是交付切片，不是产品含义。**产品是什么样仍只由 `design.md`、`flows.md`、`acceptance.md` 说；
卡不增加、不改变、也不解释任何一条规则。所以：

- **改卡不升 topic 的 rev**——重新切分、调换顺序、改演示步骤，都不动产品含义，词条出处与对象依据不必复核。
- **切卡时发现少一条场景，或某条场景要改**，那是改 `acceptance.md`，按[改动怎么记](AGENTS.md#改动怎么记)的规矩办；
  不许把新的产品要求只写在卡里。
- **卡里不写技术任务。**「建表」「接入某个库」不是卡；判据与产品正文相同：产品负责人能照着演示脚本做一遍并判断对不对吗？
- **卡的交付状态与时间不写在这里。**这一份只回答切成了哪几块、先做哪块、每块怎么演示。

「故事卡」是这个工作区组织交付的办法，不是被设计的那个系统里的概念，所以它不进[统一语言](../ubiquitous_language/README.md)，
定义只在这一页。

## 放在哪

每个 topic 一份可选的 `stories.md`，与 `acceptance.md` 同级，从[模板](.templates/topic/stories.md)起步。
**没有卡的 topic 不建这份文件**——空文件会被当成「已经切过、一张都没有」。

一张卡的场景跨了几个 topic 时，卡归**承载用户入口的那个 topic**（用户从哪里开始做这件事），引用别的 topic 的场景。

**文件里卡的先后，就是建议的交付顺序。**顺序由产品负责人定；谁在哪天定的、依据什么，记进该 topic `decisions.md` 的拍板记录。
调换顺序就是挪动卡在文件里的位置，不改卡号。

## 一张卡长什么样

````markdown
### ST-000-01 · 一次请示与它的答复都留得下来

- **价值**：事后追问「当时是谁同意的」的人，查得到请示和答复各一条，不必去翻聊天记录
- **覆盖场景**：[S2](PF-000-occurrences-and-record-entries/acceptance.md#一可观察的场景)
- **演示**：
  1. 让 agent 就一次有风险的操作发出请示 → 记录里多出一条请示，标着「可否决」
  2. 人答复「同意」→ 记录里再多出一条答复，它是之后那次操作的依据
- **不含**：进程中途被回收之后的恢复（那是另一条场景）
- **前置**：无
- **就绪**：是
````

这张卡只是示例，[PF-000](PF-000-occurrences-and-record-entries/README.md) 并没有切过卡；链接写全了 topic 目录，只因为这一页不在 topic 目录里——
在 `stories.md` 里写 `acceptance.md#小节` 就行。

**标题**：`### ` + 卡号 + ` · ` + 一句话。一句话说的是**用户因此能做到什么**，不是要做的工作。

| 字段 | 它是什么 | 它不是什么 |
|---|---|---|
| **价值** | 对谁有用、有了它能做到什么原来做不到的事 | 实现上的好处（「为后面的卡铺路」不是价值） |
| **覆盖场景** | 这张卡交付之后应当成立的验收场景：每条一个链接，**链接文字是场景编号**，指向那份 `acceptance.md` 里场景所在的小节 | 场景内容的复述——场景只在 `acceptance.md` 里写一次 |
| **演示** | 产品负责人照着做的脚本：缩进的编号步骤，每步写成「做什么 → 应当看到什么」 | 测试用例或实现步骤；看不见结果的一步不算一步 |
| **不含** | 读到这张卡的人最容易以为包含、其实不包含的东西；没有就写「无」 | 整个 topic 的非目标——那在 `design.md` |
| **前置** | 必须先交付的卡（写卡号，可以是别的 topic 的卡），以及卡住它的待裁决（链接到 `decisions.md` 的那一项）；没有就写「无」 | 技术依赖 |
| **就绪** | 「是」，或「否——缺什么」。就绪指的是：覆盖的场景都已写定，没有卡住它的待裁决 | 交付进度 |

六个字段都要有。**未就绪的卡照实写缺什么**，不为了让卡看起来完整而替未决的事填一个默认答案。

## 卡号

`ST-<topic 的三位编号>-<两位序号>`，如 `ST-016-01`。这个编号族登记在
[id-namespaces](../registry/id-namespaces.json)。

- 序号在 topic 内按建卡的先后分配，**发出去的号不重排、不复用**；一张卡被拆开或作废，它的号跟着作废。
- 卡号在整个产品区唯一（中间三位就是 topic 的编号，自然不会撞）。
- 交付顺序看卡在文件里的位置，不看序号大小。

## 场景怎么编号

**被卡引用的场景行，第一格必须是编号**——卡要指到唯一的一行，靠的就是它。

- **沿用该 topic 已有的写法**：现有的有 `S1`、`S2b`（[PF-000](PF-000-occurrences-and-record-entries/acceptance.md) 等）与
  `A01`（[PF-021](PF-021-schedule-and-calendar/acceptance.md)）两种。
- **还没有编号的 topic**，第一次被卡引用时给那张场景表加一列 `#`，从 `S1` 起编。
  **给已有的场景补编号不改含义，不升 rev。**
- 写法是 1 到 3 个大写字母接数字，可以再带一个小写字母（`S2b`）；加粗或加反引号都可以。
  **不带连字符**——带连字符的 `S-` 是契约条款的编号族。
- 编号在一份 `acceptance.md` 之内唯一，发出去就不重排、不复用。
- 编号的作用域是这一个 topic；跨 topic 提到时带上 topic 编号（「PF-016 的 S3」）。

「绝不能发生的事」不是场景，不归任何一张卡：它们在每一张卡交付时都必须成立。

## 对账

对账器守着下面这些，**不过就失败**。命令在工作区的 `tooling/README.md`「故事卡对账」；执行仓库的 `make design-check` 把它一起跑。

| 查什么 | 为什么 |
|---|---|
| 卡号合乎写法、全区唯一、中间三位等于所在 topic 的编号 | 下游按卡号引用，撞号或指错 topic 就无从引用 |
| 六个字段齐全 | 缺「不含」「前置」的卡，读的人只能猜 |
| 「覆盖场景」至少一条；每条都链接到某个 topic 的 `acceptance.md`，且那里有一行带这个编号；被引用的编号在那份文件里不重复 | 卡指不到具体的一行，交付了也无从核对 |
| **一条场景至多属于一张卡**（跨 topic 也算） | 属于两张卡的场景，说不清哪张卡交付时它该成立 |
| 「前置」里的卡存在、不是自己、不成环 | 成环的卡没有一张能先做 |
| 演示至少一步，每步都有「→」隔开的两半 | 没写「应当看到什么」的一步无法验收 |
| 「就绪」是「是」或「否」；写「否」的写着缺什么 | 只写「否」等于把缺口藏起来 |

本 topic 里**还不属于任何卡的带编号场景**，对账器只列出来、不判失败：远处的场景可以还没有卡。
链接的锚点由设计树的链接检查统一查。

**对账器查不了的**：一张卡是不是真的只证明一件事、演示能不能照着做出来、顺序排得对不对、
一张卡是不是小到一两天能交付。这些归起草时的判断与评审。
