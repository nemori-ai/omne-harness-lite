# PF-014 验收标准

产品视角的验收：**谁，在什么情形下，应当看到什么**。
概念与规则引用 [design.md](design.md)，本页不重新定义。

---

## 一、可观察场景

### 追加消息的两种走法

| # | 场景 | 应有表现 |
|---|---|---|
| S1 | agent 正在干活，用户直接说了一句话 | **它排着，不打断正在干的活**；用户**看得出它还排着、还没被看到** |
| S2 | agent 正在干活，用户连着说了三句 | **三句作为一批被一起消费**，agent 看到的是三句，**不是分三次各答一遍** |
| S3 | agent 正在干活，用户明确发出**插队** | 正在进行的那一步按[几种停法](flows.md#旅程三用户插队)之一被处置，**那句话进队首**，loop 走到 T1 就取走它 |
| S4 | **插队之后**，用户去看那次运行 | **它还活着**，没有落终态；它带着用户那句新话接着走 |
| S5 | 用户发出**取消** | **那次运行落终态「被取消」**，loop 停了。**与插队的结果截然不同** |
| S6 | 取消之后，系统补了一条中断提醒告诉 agent「刚才被叫停了」 | **不因为这条提醒开新运行。**用户下一次开口时，新运行里 agent 读得到它 |
| S7 | 模型正在吐字，用户**单独中断这次回复**（没有插队、没有取消），队列里也没有别的 | 已吐的那半句留着、标明被中断，外加一条中断提醒；正在跑的后台执行不受影响；**这次运行就此「完成」，agent 不会马上又开口** |
| S8 | 同上，但队列里**还排着**用户早先说的一句 | 运行不结束，loop 回 T1 取走那一句，agent 带着那半句与中断提醒接着想 |
| S9 | 用户排了一句，还没被取走，他想收回 | **收不回，本版不提供撤回**（[理由](design.md#为什么没有撤回一个排队项)）。他能做的是**再说一句**，agent 两句都看得到 |

### 插队停在几个位置上

| # | 场景 | 应有表现 |
|---|---|---|
| S10 | 插队时模型正在吐字，已经吐了半句 | **那半句留着**，收成一条标明「被中断」的消息，**外加一条中断提醒**。agent 下一轮看得见那半句 |
| S11 | 插队时一个**允许转后台**的工具正在跑 | **它转后台继续跑**，位置上留一条占位，**原因写着「因插队转后台」** |
| S12 | 插队时一个**不允许转后台**的工具正在跑 | **它被中断**，占位原因写着「因插队被中断」 |
| S13 | 插队时一次模型回复带的三个工具调用**已经跑完两个** | **那两个的结果一条不少地留着**，只处置还在跑的那一个 |
| S14 | 插队时模型正在吐字，吐出的部分里**已经有一个参数收齐的工具调用** | **它不执行**：那份被中断的回复不交出动作。它照样留在那条被中断的消息里；agent 读完用户那句话，再决定要不要重新发起 |
| S15 | 插队时 agent 正用 `Ask()` 等人回答 | **那次执行被中断**，占位原因写着「**人拒绝回复**」。agent 拿到的是「**没有答案**」，不是失败 |
| S16 | 插队时[运行等待态](../../ubiquitous_language/terms/interaction-and-dispatch.md#ul-run-wait-state--运行等待态--run-wait-state)上悬着三张卡片 | **三张一起从[决策池](../PF-008-human-in-the-loop/design.md#决策池)消失**；**需要授权的那些，对应的动作不做**；loop 回到 T1 |
| S17 | 上一条之后，用户回头看那三个动作 | **它们没有发生**，且看得出是「没得到批准」，不是「执行失败了」 |
| S18 | 插队时 loop 恰好**正在取队列 / 正在组装** | **什么都不中断**，那句话进队首，**loop 马上就取到它**——[没有「现在不能插」的窗口](design.md#54-插队停在哪就怎么办) |
| S19 | 用户连着插队两次 | 第二次**只是进队首**，**不会再中断一次**已经在走向 T1 的 loop |
| S20 | 用户在池子里对一张卡片点了「[我不答这个](../PF-008-human-in-the-loop/design.md#65-不回答是合法答复)」 | **只解除那一张**，别的卡片照旧等着——**这与插队的粒度不同**，[两个入口都在](design.md#544-这没有推翻-pf-008它把一个词说全了) |

### 什么会让队列从空变成非空

| # | 场景 | 应有表现 |
|---|---|---|
| S21 | 没有运行在跑，用户说了一句话 | **开一个运行** |
| S22 | 没有运行在跑，用户敲了一个绑定提示词或 skill 的斜杠命令 | **开一个运行。**它是内容，[不是控制指令](design.md#看着像控制指令其实不是)；agent 看到的是**展开后的**那条消息 |
| S23 | 用户敲了一个绑定 skill 的斜杠命令，翻会话日志 | **原命令与展开后的全文都在**；那个 skill 的正文**一字不差**，是这条消息里的一个内容块 |
| S24 | 用户敲了一个绑定 skill 的斜杠命令，后面带了几句话 | 那几句**另成一个内容块**，不拼进 skill 正文 |
| S25 | 用户敲的命令名不在这个会话的命令集里（包括他没有权限用的），或参数与声明对不上 | 交付面**当场明说、不发送**；受理面**什么都没收到**，日志里没有新条目 |
| S26 | 交付面发出时认得出的命令，到受理时已经不在这个会话的命令集里（恰好在这之间换了） | **明说「没有这个命令」**：不进队列、不触发流程、**不当一句普通的话**；日志里留一条**具名拒绝** |
| S27 | 没有运行在跑，用户敲了一个绑定系统业务流程的斜杠命令 | **不开运行**，不进队列。流程被触发，会话日志里多一条**记它发生过的条目**（命令名、参数、结果摘要）；agent 看不到它 |
| S28 | 一个运行正在跑，用户敲了一个绑定系统业务流程的斜杠命令 | **队列不因此变化**，「完成」那一格不因它不成立。reload 之外的流程会不会影响正在跑的运行，[归那条流程自己，本版未述](design.md#95-斜杠命令受理时还有一处没说) |
| S29 | 一个运行正在跑，用户发 reload | 按所选命令刷新对应资产注册表；候选先校验，失败保留原数据；不原地改写旧清单和调用输入，实际切换沿 PF-004／PF-012 安全交接；保留 Run 并开启新尝试，实际生效事实可恢复，不因受理命令改变队列或完成判据 |
| S30 | 连接件送来一条以 `/` 开头、恰好是某个命令名的消息 | **当成一句普通的话进队列**，不触发任何命令——[只有交付面识别斜杠命令](design.md#510-斜杠命令在受理时分两路走) |
| S31 | 用户在一条输入的中间写了 `/xxx` | 那是正文的一部分，**不被认成命令** |
| S32 | 队列里排着「一个斜杠命令展开的消息 + 两句用户消息」，一个运行正走到 T1 | **三条一起取走**——[不按来源挑](design.md#69-取批一次取走此刻队列里的全部) |
| S33 | 一条外部消息经连接件送达，此刻没有运行在跑 | **开一个运行。**[送进来的就要被处理](design.md#62-送进来的就要被处理要不要送进来归连接件) |
| S34 | 一条外部消息经连接件送达，此刻**有**运行在跑 | **不开新运行**，那个运行在下一个 T1 取走它——**而它同时让「完成」那一格不成立** |
| S35 | **会话未归档，一个两小时的后台构建跑完了，而那次运行早就完成** | **开一个运行**，agent 看见结果，**回话给用户**。这正是用户说「好了告诉我」要的 |
| S36 | 同上，但**此刻有别的运行在跑** | **不开新运行**，那个运行取走它。**两种处境走的是同一条路** |
| S37 | 人答了一张**属于后台执行**的卡片 | **不进队列，也不开新运行**。它[落到卡片上](design.md#三个去处)；那次执行接着跑，[运行本来就没停](../PF-008-human-in-the-loop/design.md#53-一批卡片与答完是什么意思) |
| S38 | **组织超管改了一项注入的设置，而这个会话空闲** | **什么都不做。**[下一次运行开始时组装出来的本来就是新的那一份](design.md#610-注入的上下文变了没有运行在跑时什么都不做) |
| S39 | 同上，但这个会话**有运行在跑** | **落一条 `SystemReminderMessage` 进队列**——agent 脚下的地变了，它必须知道 |
| S40 | 一个依赖恢复了、一项权限变了 | **不开运行，也不进受理面**。[下一次尝试开始时重算可用性就看到了](../PF-012-agent-loop-and-run/design.md#每一次尝试开始都要做四件事) |
| S41 | agent 一直在干新活，没有打转，转了很久 | **系统不会自己停它。**[这是 PF-012 定的模型边界，不是本 topic 的缺口](../PF-012-agent-loop-and-run/design.md#方程不保证这个循环会停) |

### 受理、去重、拦截

| # | 场景 | 应有表现 |
|---|---|---|
| S42 | 一条外部消息送到一个不存在的会话 | **具名拒绝**，发的人知道原因。**不泄漏「这个会话存不存在」之外的任何东西** |
| S43 | 队列里已经排了很长 | **照常受理。**[本版不设容量上限](design.md#66-队列不设容量上限)；**但排得多长，用户看得见** |
| S44 | 一个外部来源因为重试把同一条消息投了三次 | **只有一条入站到达**；后两次拿到与第一次相同的结果 |
| S45 | **用户**把同一句话手动发了两遍 | **两条都在。**系统不替他猜哪一条是多余的 |
| S46 | 一件「脱敏」拓展件改写了用户那条消息 | **日志里是改写之后的那份**，原文没有进过日志 |
| S47 | 一件「脱敏」拓展件改写的是**模型吐出来**的那条 | **同样成立**——[那个位置不只管输入](../PF-012-agent-loop-and-run/design.md#消息落盘之前每条消息都经过它不只是输入)。**但那条不是入站到达**，本 topic 不管它怎么来的 |
| S48 | 一件「攻击检测」拓展件否决了**用户自己**那条 | **用户看得出它被拦了**，不会以为自己的话凭空消失 |
| S49 | 一件拓展件否决了一条外部来源的消息 | **日志里一定留得下「有一条被拦下了」**；要不要回告发送方，由那件拓展件定 |
| S50 | 一张图进来，挂着的**模态转换**件转好了 | 日志里**那张图原样还在**，**转出来的派生表示与 transcript 挂在它上面**；换一个收得下图的模型，**用的仍是原图** |
| S51 | 一张图进来，**模态转换件没转成**（它挂了、此刻不可用，或交不出 transcript） | **这一条不被受理**：日志正文里没有它，**队列里也没有**；发的人被告知没发进去，会话与可选模型都没变——**绝不是「照原样落盘、只是没有 transcript」** |
| S52 | 一条外部消息经连接件送进一个已有的会话（[① 那一路](../PF-002-assets-settings-and-permissions/design.md#两种投递方式动作主体不同)） | **进那份连接件配的投递目标那个会话**；投递目标指的是一个已有的会话，**不会按外部线程分到不同会话** |

### 停机与恢复

| # | 场景 | 应有表现 |
|---|---|---|
| S53b | 普通消息持久提交之前停机，发送方保留了原输入和同次提交标识 | 此时未受理；发送方恢复后查询／自动重试，重新通过当前准入及落盘前干预后，日志与待处理资格恰好形成一份，不要求人手重新输入。没有保存输入的系统不得宣称能自行恢复它 |
| S54b | 普通消息已经完整持久入队、尚未承接，然后停机 | 恢复后消息仍待处理，系统自动推进，不依赖发送方在线、重试或打开会话；消息内容与原顺序保留 |
| S55 | 停机期间那个会话的运行状态变了 | **不影响任何一条到达的去处**——[去处不由处境决定](design.md#52-三个去处为什么是穷尽的) |
| S56 | 一个**没有运行、没有 agent runtime 的空闲会话**里，队列非空 | **照样被拉起来处理**。不需要有人来看这个会话才发生 |
| S57 | 普通消息提交已生效，受理回执丢失；交付面沿同次提交标识查询或重试 | 返回原受理事实及当前排队／承接状态，不新增消息、承接或 Run；查询前显示结果未知，不把它判为未受理 |
| S58 | 读取待处理消息后、持久承接前停机 | 消息仍待处理，读取或开始执行不能提前清除待处理资格；恢复后可正常承接，原输入未丢 |
| S59 | 承接事实已持久成立，随后停机但 Run 尚未完成 | 消息不再排队；原消息和承接事实可查，恢复沿原 Run 接续，不给后继 Run 再承接一次 |
| S60 | 卡片答复或控制指令受理提交成功，处置完成前停机 | 原目标、答复／意图和处置责任仍可查；按原目标恢复处置或明确关闭并留痕，不进入普通消息队列，也不以受理成功宣称已生效 |

## 二、绝不能发生的事

| 绝不能发生 | 如果发生了意味着什么 |
|---|---|
| **一条被受理的入站到达，既没被消费也没被明确关掉，就再也没有下文** | 用户永远等不到他要的那个结果，**而系统看上去一切正常**——这是本 topic 的头号事故 |
| **队列非空，而这个会话长期没有运行被开起来** | 上一条的具体形态。[队列非空就该有运行](design.md#68-停机不会让一条入站到达永远悬着)——**没有，就是漏了** |
| **一条消息被取走两次**，同一件事做了两遍 | 外部效果发生两次。[崩溃恢复导致的重做是不得已的代价，这一种不是](../PF-012-agent-loop-and-run/design.md#64-每一次尝试开始agent-都要知道) |
| **一条外部消息被静默丢弃** | 发的人以为送到了，用户以为 agent 没理他，**而日志里什么都没有** |
| **用户插一句话，把自己跑了两小时的任务杀掉了** | [插队与取消的语义被搞混了](design.md#插队与取消差别必须写死) |
| **插队之后，已经跑完的工具调用的结果丢了** | 违反[「最大程度保留」](design.md#53-插队的核心原则)。那些外部效果已经发生，**记录却说没有** |
| **一份被中断的回复里的工具调用，在中断之后被执行了** | 用户刚说「先听我说」或「别说了」，**外面却多了一件他没来得及拦的事**。[被中断的回复不交出动作](design.md#54-插队停在哪就怎么办) |
| **用户取消之后，系统补的那条中断提醒把 agent 重新叫了起来** | 用户说「别做了」，agent 却马上又开了一次运行——[那条提醒不让队列非空](design.md#57-穷举一什么会让队列从空变成非空) |
| **插队之后，模型已经吐出来、用户已经看见的那半句不见了** | [用户刷新一下页面，那半句就凭空消失，而他会以为自己看错了](../PF-009-context-message-types/design.md#69-用户看见了的会话日志里必须有) |
| **占位消息不说原因，agent 把它读成「工具执行失败了」** | 它会去**重试一件用户刚刚叫停的事**，[而且觉得自己在尽职尽责](../PF-006-tools-and-skills/design.md#67-用户可以中断而中断不是失败) |
| **一个等待因为取消而被视作「批准」** | **产生了不可逆的外部效果，而没有任何人批准过它** |
| **一个等待因为到点了而被自动作答** | [系统替人签了字](../PF-008-human-in-the-loop/design.md#61-永远等着系统不替人作答)。**取消是人做的，超时不是** |
| **受理面提供一档「收下但不进队列」** | [队列是日志的投影](../PF-012-agent-loop-and-run/design.md#待处理消息队列)。多这一档，日志里就要多一个「这条不算待处理」的标记，**整个模型的干净正来自没有它** |
| **一条入站到达攒在内存里，等组装来取** | [一次重启就凭空消失](../PF-010-context-management-and-assembly/design.md#要求四先落盘再组装)；而且[组装要跑两次，第二次就拼不出同样的东西](../PF-012-agent-loop-and-run/design.md#它们必须先落进日志这是被方程逼出来的) |
| **一条被拦下的到达，内容进了日志正文** | [等于承认它曾经进过方程的定义域](../PF-012-agent-loop-and-run/design.md#消息落盘之前每条消息都经过它不只是输入) |
| **一条被拦下的到达，连「被拦下」这件事都没留痕** | [能干预的拓展件必须留下结论](../PF-012-agent-loop-and-run/design.md#610-能干预的拓展件必须留下结论)。留不下，排查的人分不出「没人拦」和「拦了没说」 |
| **一个会话同时有两个活跃运行** | 违反[会话内单活跃](../../ubiquitous_language/terms/agent-runtime-loop.md#ul-single-active-execution--会话内单活跃--single-active-execution)。**「这个会话现在在干什么」有了两个答案** |
| **一个外部来源打断了正在干活的 agent** | 外面的人可以随时抢走这个会话的注意力。**它能做的到此为止：把一条消息放进队尾** |
| **组织超管改一次设置，所有空闲会话各醒一次、各调一次模型** | [说状态的提醒在没有运行时没有任何新信息](design.md#610-注入的上下文变了没有运行在跑时什么都不做)。**那是一笔纯粹由设置变更产生的账** |

## 三、判据

| 设计点 | 做到了的判据 | 没做到时的表现 |
|---|---|---|
| [**插队是原子的**](design.md#65-插队是原子的) | **在中断与消息入队之间的任意一点切断**，恢复之后要么两件事都成立、要么都不成立 | agent 停了一下然后什么都没变；或者用户明明按了「现在就说」却等很久 |
| [**插队不终止运行**](design.md#插队) | 插队之后去查那次运行，**它没有终态条目**，且随后它消费了用户那句话 | 那次运行落了「被取消」——**用户的任务被他自己的一句话杀掉了** |
| [**最大程度保留**](design.md#53-插队的核心原则) | 插队前已经到达的响应内容、已经跑完的工具结果，**插队后一条不少地在日志里** | 记录与实际发生过的事对不上 |
| [**占位一律说原因**](design.md#541-占位消息一律要说清原因) | 每一条因插队产生的占位，**都能读出是哪一种**（转后台 / 被中断 / 人拒绝回复） | agent 重试一件用户刚叫停的事 |
| [**两种「等人答」语义统一**](design.md#542-两种等人答机制各归各产品语义是同一条) | 插队之后，`Ask()` 与运行等待态**两边都记成「人明确拒绝回复」**，且 loop 都走到了 T1 | 两者的语义永久分叉，读者得记两套规则 |
| [**取消一律视作拒绝**](design.md#543-取消视作拒绝为什么只能往这个方向倒) | 能举出的所有情形里，**没有一种取消会产生外部效果** | 一次取消让一封邮件发出去了 |
| [**零个新的状态转移**](design.md#58-穷举二什么会影响退出循环的判断) | 把插队的六条路逐一对到 [PF-012 的转移表](../PF-012-agent-loop-and-run/design.md#56-状态转移表)上，**每一条都落在已有的行上** | 实现里长出了一个只有插队才走的分支，**而它平时根本不跑** |
| [**只有一个提交点**](flows.md#落盘之后没有第二步定落点) | 在提交前后切断，受理事实与对应去处的责任要么一起成立，要么都未成立；回执未知时按原提交查询，不据此判定失败 | 出现事实已受理而待处理资格丢失，或因回执未知另发一条 |
| [**不漏**](design.md#67-不漏不重) | 构造「结果回来时运行恰好正在结束」这个时刻，**那条消息仍然有人来看** | 用户永远等不到那个结果 |
| [**不重**](design.md#67-不漏不重) | 同上那个时刻，**agent 只被叫起一次** | 同一件事做了两遍 |
| [**受理面统一**](design.md#51-一条入站到达从哪里来到哪里去) | 去重、留痕、租户隔离、拓展点，**逐条检查都只在一个地方成立** | 控制指令绕过了其中某一条，**而没人发现** |
| [**去处不由处境决定**](design.md#52-三个去处为什么是穷尽的) | 同一条到达，在「有运行在跑」和「没有运行」两种处境下**走的是同一条路** | 受理面要去问「现在有没有运行」，**而那个答案在它问完之后就可能变了** |
| [**排着的看得见**](design.md#64-排着的东西必须看得见) | 用户能分辨「排着」与「已经被看过了」 | 他以为被无视，**再发一遍，而我们不去重** |
| [**过滤在连接件那一侧**](design.md#62-送进来的就要被处理要不要送进来归连接件) | 受理面的代码里**找不到任何一处按来源决定「要不要处理」的判断** | 受理面长出一个一刀切的开关，**而它补不上连接件那边的缺口** |

## 派发与归档裁决验收

归档与新任务同时发生，只能是先受理后因归档取消，或明确拒绝；已发起调用的迟到结果及账目仍保存而不唤醒会话。连接件专属验收随该资产存在性讨论搁置。

受理与消费的通用保管和清除范围按 [PF-015 §6.26](../PF-015-session-lifecycle-and-ownership/design.md#626-待消费数据先持久保管再交接)；本页的“取走”均指持久承接，不表示 Run 已完成或历史已删除。

## 推进信号的丢失与重复

| # | 场景 | 应有表现 |
|---|---|---|
| S61 | 普通消息完整持久受理后，通知尚未送达就丢失或系统停机；恢复时队列已非空、没有未终结 Run | 已受理事实及输入保持，系统自动创建 Run 并处理，不等新的队列边沿、发送方重投或打开会话 |
| S62 | 同一份已受理输入引发重复或合并的推进通知；原 Run 及有效执行者已在 | 原输入只逻辑承接一次；继续原 Run／attempt，不新增受理事实、模型或工具调用 |
