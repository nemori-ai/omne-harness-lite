# PF-014 决策与来源

产品设计允许 product manager 做判断，但**不允许发明没人拍过板的东西**。
本页把两者分开：哪些是产品负责人裁决的，哪些是 PM 自己推导的，各自依据在哪。

## 一、拍板记录

### 2026-09-29 · Agent runtime 装配与安全交接

**直接裁决**：[本轮交流](../PF-004-agent-definition-and-assembly/interviews/2026-09-29-agent-runtime-assembly.md)要求完整装配矩阵；显式 reload 可在同一 Run 的安全交接点采用同身份新定义并开启新尝试；旧模型回复中的未发起动作按新装配核对，已移除或绑定已变不自动执行，原因交回 agent。撤销、卸载与不可用只规定 Cordis 范式下合理的产品原则。

**本 topic 的落点**：明确 reload 在当前 Run 内的交接与新尝试不改变命令受理的去处；命令留痕不代替实际生效与恢复事实。

**取代范围**：PF-004 I-3 的“同一 Run 内所有尝试永远同版”收窄为“普通恢复不静默升级”；PF-002 reload 的“永不重装配当前构成”改为按实际构成影响处理。历史记录保留当时语境；此处不扩张资产刷新范围或更换 AgentDefinition 身份。


### 2026-09-20 · 范围与全部首批裁决

**分四次给**，其中第四次纠正了第三次的一处。原话按次序录下。

#### 第一次：范围与两个穷举

> 「那现在我们可以提前继续讨论 PF-014 的，也就是**整个 inbound 的设计**，这块可以以
> **design_legacy 里面相关的作为起点**，主要是**发起一次 run 的情形需要穷举出来**，
> 以及**一次 run（agent-loop）运行中能够对它退出循环的判断带来影响的情形的穷举**」

#### 第二次：追加消息的两种走法，与两种中断

> 「run 在跑着的时候用户说了一句话（追加了一条消息），分两种情况：1）**排队**；
> 2）用户明确发了个『**插队**』的命令。前者就是自然排队等到下一次能够消费请求队列里面的
> 消息的时候来获取（**连续排队的用户消息一起消费**，omne-next/omne_harness 也是这么设计的，
> claude 和 codex 也是），后者在流程上应该**视作是中断当前的 llm response**
> （这点和 omne-next 那边的设计不太一样）**让 loop 能够到达下一次消费请求队列的那个点**。
> 也就是说，从建模上，我们的系统应该要支持能够**单独地**：1）**中断一次 tool execution**；
> 2）**中断一次 llm response**（但是**该落盘记录的持久化的依然要**，参见 PF-009 或 PF-010）」

#### 第三次：保留原则，与原子命令

> 「因为 loop 可能停在 llm response 或者 tool execution 两个状态，**核心的原则是在最大程度
> 保留已经到达的响应或执行的工具调用的前提下中断**，那么意味着：1）中断 llm response；
> 2）**能够转后台的 tool execution 切后台，不能的中断 tool execution**
> （**都是加 ToolMessage 占位告知 agent 原因，避免误以为是工具执行失败**）。
> 所以这里也意味着 **`insert_user_message` 是一个原子命令**，不再是像 omne-next/omne_harness
> 那里的 **interrupt then run 的复合命令**」

同次给出「等人答」的分情况：

> 「『等人答』这个现象有两种：1）**tool 内部发起的**（`Ask()` meta tool）；
> 2）**system 判断后发起的**。……后者是 run 的等待态，**应当取消等待以实现插队的更高优先级的
> 用户意图**。当然因为取消等待态，那对应的进入到**决策池**的那些卡片，**需要能够被移除**，
> 并且**如果是需要用户授权的情形，应当视为用户拒绝**（因为这样在用户没有明确答复的前提下，
> **取消视作拒绝是无副作用可逆的**，大不了用户在对话里面显式再说一句批准，agent 重新做就是了）」

#### 第四次：人的处理有两种，并纠正 `Ask()`

> 「人的处理有两种：1）**回复**；2）**明确拒绝回复**。『**插入消息**』应当视为后者。
> 噢这里**我对 `Ask()` 的情况说错了**，它是**永远在前台阻塞 run 不过期的**，
> 因此应当**也是视为「人拒绝回复」**」

> **第三次说 `Ask()`「因为能转后台，应当是继续等」，第四次改判。正文依据的是第四次。**
> 记下这处改判不是为了留痕好看——**它把两种「等人答」在产品语义上合成了同一条**
> （人做了第二种处理），而机制上仍各归各。第三次那版会让两者的语义永久分叉。

#### 裁决 8 与 14 为什么最要紧

**裁决 8 是一条原则，不是一条规则。**插队在四种位置上各该做什么，全部由它推出来——
正文因此不必列一张要人背的条款表，**读者记住那一句就能自己推**。

**裁决 14 保住了 [PF-008 §6.1](../PF-008-human-in-the-loop/design.md#61-永远等着系统不替人作答) 的穷举。**
那条写着「清掉一张卡片只有两条路——**人处理它**，或者会话终结」
（**那个说法的正式名字是[归档](../../ubiquitous_language/terms/agent-runtime-loop.md#ul-session-archival--会话归档--session-archival)**）。
插队**不是第三条路**，它是「人处理它」的第二种形式。
**不动结构，只把一个已有词的含义说全**——这比新增一条路便宜得多，
也让 §6.1 的理由继续成立：系统仍然没替人作答，**是人自己作了答**，答的是「我现在不回这个」。

### 2026-09-23 · 斜杠命令有三种绑定目标，其中一种不是内容

**产品负责人原话（一）**，块 B-1 的开头（其余六条落在 PF-002、PF-004、PF-006，原文见 [PF-002 decisions](../PF-002-assets-settings-and-permissions/decisions.md#2026-09-23--斜杠命令三种绑定目标mcp-的动作即工具条目连接件带身份鉴权工作区资产的权限取最严值)）：

## 二、PM 推导

**推理链可核对、可推翻。**

| # | 结论 | 从哪几条推出 | 推理 |
|---|---|---|---|
| **P1** | **插队不终止 Run** | 裁决 5、11 | 裁决 5 的目的是「让 loop **到达**下一个消费点」，**到达意味着它还在走**。legacy 的 `interrupt_then_run` 是当前 Run 被取消、新 Run 起——**那个 loop 没在走，它死了**。两者根本不同，**这是与 legacy 最大的一处差别** |
| **P2** | **一个 Run 内部会多次消费输入队列** | 裁决 5 + PF-012 | [PF-012 的 T1](../PF-012-agent-loop-and-run/design.md#56-状态转移表) 写的就是「一条待处理的输入（触发，**或队列里攒的**）」，而 T7 动作结果齐了要回 T1。所以 legacy 那条「一个 Run 恰有一个启动依据」**只管启动，管不了运行中的追加** |
| **P3** | **取消运行等待态走已有路径，零新分支** | 裁决 13 + PF-012 | 卡片全判为拒绝 → [T5「被否的写一条『人不同意』」](../PF-012-agent-loop-and-run/design.md#56-状态转移表) → T8「一批动作全被否」→ 回 T1，**正好就是消费输入队列那个点**。不需要为插队新增任何状态转移 |
| **P4** | **中断时已吐出的那半份，下一轮 agent 看得见** | 裁决 7 + PF-009 + PF-012 | PF-009 会把它[收成一条消息](../PF-009-context-message-types/README.md)落进会话日志，而 [PF-012 §6.3](../PF-012-agent-loop-and-run/design.md#63-喂给-agent-的是日志原样) 明写「喂给 agent 的是日志原样」。**既然落了盘就在日志里**，除非特意标了不给模型看 |
| **P5** | **原子的具体含义**：中断（或转后台）、落占位消息、用户消息进队列，**三件事在同一次提交里成立** | 裁决 11 | 不原子会漏出两种坏状态——**中断了但消息没进队列**（loop 空转一圈又停下），或**消息进了队列但没中断**（等很久才生效）。裁决 11 明确否掉复合命令，就是要堵这个缝 |
| **P6** | **连续插队是幂等的** | 裁决 8、11 | 第二条插进来时若已经在走向消费点，**没有东西可中断了**；此时再中断一次违反裁决 8 的「最大程度保留」 |
| **P7** | **控制指令归本 topic 受理，但不排队** | PF-012 | PF-012 明写取消「走**外面进来的事**那条路，往日志里落一条，然后方程读到终态就停」。**既然从外面进来，受理面就该统一**；只是落点是即时生效而非队列。**legacy 把 control 排除在到达事实之外，我们不沿用**——受理面统一、落点分叉，比两个受理面干净 |
| **P8** | **`insert_user_message` 与「取消/强停」的区别必须写死** | P1、P7 | 两者都会中断正在进行的东西，但前者 **Run 不落终态、loop 继续**，后者 **Run 落终态「被取消」**。**搞混了，用户插一句话就会把自己的 Run 杀掉** |
| **P9** | **`Ask()` 与运行等待态语义统一、机制不合并** | 裁决 12、13、14 | 两者在词表里[挂在不同的生命周期上](../../ubiquitous_language/terms/execution-and-outcome.md#ul-tool-wait-state--工具等待态--tool-wait-state)（一个挂在工具执行，一个挂在运行）。**裁决 14 统一的是产品语义，不是机制**——强行合并会抹掉一个已经立住的区分 |
| **P10** | **PF-008 §6.1 禁的是「没有事件也要给答案」，插队不在其列** | 裁决 13 + PF-008 | §6.1 的原话理由是「**等待期间世界里什么都没发生**，不花钱的等待没有理由到点；一旦设了上限，就必须规定『到点算什么』——那就是替人签了字」。**插队有明确事件**：用户主动发了指令。**时间流逝替人签字，和用户自己改变主意，是两回事** |
| **P11** | **默认只能倒向拒绝，不能倒向批准** | 裁决 13 的理由 | 产品负责人给的理由本身就是[那条研发品味](../../../agents/roles/engineering-taste.md)的落点：「外部输出不因被运行时调用就变得可逆；**恢复、补偿、幂等和撤销必须区分**」。**拒绝与批准在可逆性上根本不对称**——拒绝什么都没做，批准产生外部效果 |

### 本轮 PM 推导：装配、实例和独立执行的边界

- 会话身份与定义身份固定，而 reload 允许同 Run 采用新内容，因此以新清单和新尝试表达变化；普通恢复必须找当前实际生效清单，不能回到 Run 最初版本或直接读最新来源。
- Model／Tool runtime 由 Session／Run 治理，故 Agent runtime 的退役只改变使用关系；其自身依赖真的失效时仍按各自失败规则处理，不能推导成所有资源永不卸载。
- 未发起动作须按新绑定核对，而已经发起的调用保留原输入，故“模型返回动作建议”与“工具实际执行”必须分清；旧许可不能自动覆盖新实现。
- 重装配可能在等待调用、卡片或拓展判断时发生，故未完成工作的身份、采用依据、结果及等待关系须能恢复；这不推出一律等待、一律拒绝、一律回退或一律取消。
- 重载意图、当前实际生效构成会影响后续求值，故不能只保存一条可丢的命令摘要。持久化布局及交接算法仍属技术设计。

**框架核对依据**：[Cordis 4.0.4 必需服务提供者变化读数](../../basis/cordis/plugin-body-reruns-on-provider-change.md)区分提供者换代／不可用与同实例状态变化，并要求跨重跑保留的事实不能只在消费者闭包内。这里只据此约束产品原则，不指定 inject、effect、插件层次或 API；也不把 DSH 的宿主实现当成本项目方案。
