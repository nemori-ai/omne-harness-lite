# PF-014 变更历史

记录**产品设计本身**的演进：哪一版改了什么含义、为什么改、下游要复核什么。
错别字、链接修复、段落搬家不记这里。

技术投影用 `provenance.json` 引用具体 rev，所以这里的 rev 不准会直接传导到实现侧。

## rev 2 — 2026-09-20

**同日重做。**rev 1 刚落稿，产品负责人就在统一建模 run、agent-loop、inbound
与触发事件时给了一条主干裁决：

> **Run 只是一个逻辑概念……在待处理的消息队列不空且不被 interrupt 之前，
> agent-loop 不会退出，而是持续消费消息队列。**
> （**而且这个消息队列不只是 user message，还包含比如 bkg tool result、agent context changed 等，
> 这样建模就自然把 PF-012 和 PF-014 的冲突给解决了。**）

**本 topic 的产品承诺一条都没变，变的是「怎么兑现」。**
rev 1 要受理面**逐条判断此刻有没有运行在跑**；rev 2 **完全不必问这个问题**。

### 一、落点从四个变三个：「只记一笔」没有了

**rev 1 的第四档，是为了区分「有运行会来看它」与「没人会来看它」。**
[PF-012 rev 4](../PF-012-agent-loop-and-run/changelog.md#rev-4--2026-09-20) 之后这个区分不该由受理面承担：

| 一条后台结果回来 | rev 1 | rev 2 |
|---|---|---|
| **运行还在跑** | 落点「只记一笔」——有人会来看 | **进队列。**队列非空，**那个运行本来就还没退出** |
| **运行已经结束** | 落点「入队」——把人叫来 | **进队列。**队列从空变非空，**那就是一次触发** |

> **同一个动作，两种自然结果。**[三个去处](design.md#三个去处)因此收敛成
> **进队列 · 落到卡片上 · 就地处置**，判据从三问减成两问。

**顺带落定了一条更硬的性质**：
**[去处由它是什么决定，不由此刻处境决定](design.md#52-三个去处为什么是穷尽的)。**

### 二、它消掉了 rev 1 最难兑现的那个要求

**rev 1 的[不漏不重](design.md#67-不漏不重)最容易破在一个具体时刻**：
一条到达正在定落点，**而那个运行恰好在这一刻结束**——
定成「只记一笔」就漏，定成「入队」就可能重。

> **rev 2 里那个时刻不存在。**受理面根本不看有没有运行在跑。

**连带掉出三处简化：**

| 简化了什么 | 说明 |
|---|---|
| **受理面只剩一个提交点** | 从「受理 → 落盘 → 定落点」三步变成**落盘一步**。[流程图里的第 ⑤ 步没有了](flows.md#rev-1-有一步定落点rev-2-没有) |
| **[没有会跨越停机的中间态](design.md#68-停机不会让一条入站到达永远悬着)** | rev 1 的「已受理但落点未定」要被写下来、要在恢复时被主动扫描补齐。**rev 2 落盘是不可分割的一步** |
| **[不漏变成模型的推论，不是要被实现的规则](design.md#67-不漏不重)** | 落进日志就是进队列，而队列非空 loop 就不收束 |

### 三、穷举一换了形式：从「什么会发起运行」到「什么会进队列」

[PF-012 rev 4 把触发定死成「让队列从空变成非空的那件事」](../PF-012-agent-loop-and-run/design.md#run)，
于是 rev 1 那张按情形展开的表塌掉了：

| | rev 1 | rev 2 |
|---|---|---|
| 表的行 | **七行情形**，每行都要写「而此刻这个会话没有活跃的运行」 | **九行来源**，只回答「它落成哪一种消息」 |
| 判断在哪 | **受理面逐行判断** | **队列空不空，loop 自己看** |
| 落成几种消息 | 没有这一列 | **三种**（`UserMessage` / `ToolMessage` / `SystemReminderMessage`），**一种新类型都没多** |

> **同一句话，在运行跑着时是追加，在它收束之后是触发。差别不在那句话身上。**

### 四、四条规则被推翻或删掉

| rev 1 的 | rev 2 | 为什么 |
|---|---|---|
| **§6.2「叫不叫醒由来源那一侧配，默认不叫」** | **[送进来的就要被处理，过滤归连接件](design.md#62-送进来的就要被处理要不要送进来归连接件)** | 「收下但不进队列」正是被删掉的那一档。而**过滤该放在有知识的那一侧**——连接件知道有没有 @ 我，受理面只能按来源一刀切 |
| **§6.6「外部来源有界，内部事实不适用满时拒绝」** | **[队列不设容量上限](design.md#66-队列不设容量上限)** | **产品负责人裁决是过度设计**：「现在我们完全可以运行无限容量的队列（以后真出问题了再针对性做产品设计）」 |
| **§6.9「用户消息取一批，其余一项一个运行」** | **[一次取走此刻队列里的全部，不按来源挑](design.md#69-取批一次取走此刻队列里的全部)** | rev 1 的理由是「不相干的事掺进来账就混了」，**而 rev 4 之后运行已经不等于「一件事」**，它是一段连续的循环 |
| **§6.10「撤回只在被取走之前成立」** | **[删掉](design.md#rev-1-有过第六条撤回一个排队项rev-2-删了)** | 那条消息已经在只增不改的日志里。**为一个没人要过的功能给队列加一层间接**；用户改口再说一句就是了 |

**控制指令家族因此从六条变五条。**

### 五、三处补上、一处改名

| | |
|---|---|
| **[插队多了一种停法](design.md#54-插队停在哪就怎么办)** | loop 正在取队列 / 组装 / 正要调模型时，**什么都不中断**，只做后两件事。**rev 1 漏了这一种**，照它实现会在那个窗口里拒绝插队——**而用户按下去没反应且不知道为什么** |
| **[注入的上下文变了，没有运行在跑时什么都不做](design.md#610-注入的上下文变了没有运行在跑时什么都不做)** | 不加这条限定，**组织超管改一次设置，所有空闲会话各醒一次、各调一次模型** |
| **[「消息落盘之前」比本 topic 的受理面大](design.md#56-消息落盘之前那一刻看得到什么)** | [PF-012 rev 4 把那个位置从「输入落盘之前」扩成了「消息落盘之前」](../PF-012-agent-loop-and-run/changelog.md#rev-4--2026-09-20)。**模型吐的、工具交的也经过它，但它们不是入站到达** |
| **「输入队列」改叫[待处理消息队列](../PF-012-agent-loop-and-run/design.md#待处理消息队列)** | **改的是名，不是含义。**那个概念归 PF-012，[同一个概念只有一个说法](../../ubiquitous_language/README.md) |

### 六、四个概念落进了词表

**rev 1 用了五个词而词表里一个都没有**，违反了[这个区的硬规矩](../AGENTS.md)：
**新概念先进词表，再进正文。**rev 2 补齐并收敛：

| rev 1 的词 | rev 2 |
|---|---|
| 到达 | **[入站到达](../../ubiquitous_language/terms/interaction-and-dispatch.md#ul-inbound-arrival--入站到达--inbound-arrival)**——「到达」撞了[增量到达](../../ubiquitous_language/terms/record-and-context.md#ul-incremental-arrival--增量到达--incremental-arrival)，**两处都要带限定** |
| 落点 | **不收词条。**它只在本 topic 用，不满足「跨 topic」那条准入；正文改用「[三个去处](design.md#三个去处)」直接描述 |
| 输入队列 | **作废**，用 PF-012 的[待处理消息队列](../../ubiquitous_language/terms/agent-runtime-loop.md#ul-pending-message-queue--待处理消息队列--pending-message-queue) |
| 控制指令 | **[收](../../ubiquitous_language/terms/interaction-and-dispatch.md#ul-control-command--控制指令--control-command)** |
| 插队 | **[收](../../ubiquitous_language/terms/interaction-and-dispatch.md#ul-queue-jump--插队--queue-jump)** |

### 七、两条待裁决全部关闭，零条上报

| rev 1 的待裁决 | 去向 |
|---|---|
| **「明确拒绝回复」要不要在卡片上另给显式入口** | **问法的前提不成立。**[PF-008 §6.5 早就定了「不回答」是合法答复](../PF-008-human-in-the-loop/design.md#65-不回答是合法答复)——**那个入口一直都在**，rev 1 漏查了。而且 rev 1 写的「发一条消息就达到同样效果」**也是错的**：[插队解除的是全部，卡片上那个只跳一张](design.md#544-这没有推翻-pf-008它把一个词说全了) |
| **打满时要不要有「合并」这条路** | **随「队列不设上限」一起消失**——没有「打满」这个时刻 |

### 下游要复核

- **任何按「落点有四种」实现的分发**——[现在是三个去处](design.md#三个去处)；
- **任何在受理时去问「此刻有没有运行在跑」的代码**——[不必问了](design.md#52-三个去处为什么是穷尽的)；
- **任何按「默认不叫醒」实现的连接件接入**——[送进来的就要被处理](design.md#62-送进来的就要被处理要不要送进来归连接件)；
- **任何实现了「撤回一个排队项」的界面**；
- **任何按来源挑着取队列的取批逻辑**；
- **[PF-012 rev 4](../PF-012-agent-loop-and-run/README.md) 与 [PF-013](../PF-013-model-profiles-and-invocation/README.md) 是同一次联合修订的另两份产物**，三份要对齐后才谈接受。

## rev 1 · 草稿 — 2026-09-20

**首版。**它填的是一处从未有人拥有的空格——
[PF-012](../PF-012-agent-loop-and-run/README.md) 定了一次运行怎么往前走，
**但没有人回答东西是怎么进日志的**。

### 这一版立住了什么

| 方面 | 结论 |
|---|---|
| 受理面 | **统一一个**，**落点分叉**。留档提案把控制排在外面、有两个受理面，**不沿用** |
| 共同动作 | **先落进[会话日志](../PF-012-agent-loop-and-run/design.md#会话日志)，再谈落点**——攒在内存里一次重启就没了 |
| 插队 | **不终止运行**（留档提案是「打断，然后起一个新的」）；**`insert_user_message` 是原子命令**，不是 interrupt-then-run |
| 核心原则 | **在最大程度保留已经到达的响应、已经执行的工具调用的前提下中断** |
| 两种「等人答」 | **产品语义统一**（人的处理有两种：回复 / 明确拒绝回复），**机制不合并** |
| 取消一个等待 | **一律视作拒绝，绝不视作批准**——拒绝无副作用可逆，批准产生不可逆的外部效果 |
| 零个新转移 | 插队的每一条路都落在 [PF-012 已有的转移](../PF-012-agent-loop-and-run/design.md#56-状态转移表)上 |

### 它当时没做对的四处

**rev 2 同日全部改掉**，经过见[上一节](#rev-2--2026-09-20)：
第四档落点「只记一笔」、「叫不叫醒」的配置、按来源挑的取批规则、撤回一个排队项。
**外加一处纪律问题**：五个新概念一个词条都没建就进了正文。
