### ST-014-01 · 在原会话继续下一轮协作

- **价值**：用户得到上一轮答复后可以继续说话，原会话不因一个 Run 完成而结束。
- **覆盖场景**：[S21](acceptance.md#什么会让队列从空变成非空)、[S56](acceptance.md#停机与恢复)
- **演示**：
  1. 准备已完成上一轮、没有活跃 Run 或 Agent Runtime 的会话，再发送一个新问题 → 原会话受理它，创建新的 Run，而非重开旧 Run 或另建会话。
  2. 不再额外打开或刷新该会话，等待处理 → 队列中的新问题自动被承接，用户得到下一轮答复。
  3. 查看会话和两轮工作的归属 → 会话身份相同，两轮 Run 可区分，上一轮终态不变。
- **不含**：运行中追加、插队、后台完成、定时或跨会话投递。
- **前置**：ST-015-01
- **就绪**：是

### ST-014-02 · 普通追加消息排队后被同一轮工作看到

- **价值**：用户补充要求时不会无意中打断正在做的事，也能知道补充何时被看到。
- **覆盖场景**：[S1](acceptance.md#追加消息的两种走法)、[S2](acceptance.md#追加消息的两种走法)、[S34](../PF-012-agent-loop-and-run/acceptance.md#一可观察的场景)、[S84](../PF-012-agent-loop-and-run/acceptance.md#运行时归属与句柄)、[S99](../PF-012-agent-loop-and-run/acceptance.md#trigger-与执行尝试)
- **演示**：
  1. 发起一轮任务，在原模型请求仍在途时普通追加三条可辨认的消息 → 当前请求不被中断，三条消息可见为排队，尚未被原请求看到。
  2. 等原请求及原步骤收场，查看下一合法消费点 → 三条作为一批被同一 Run 承接，模型后续回复反映这批输入。
  3. 核对承接记录和请求归属 → 每条仅承接一次，没有为三条分别创建并发 Run，也没有重复发起原模型请求。
  4. 在原输入已承接、队列为空且模型仍在途时普通追加 → 仍是原 Run 和原 attempt，模型不中断，新输入下一合法 T1 承接。
- **不含**：插队、等待卡答复、控制命令及输入撤回。
- **前置**：ST-014-01
- **就绪**：是

### ST-014-03 · 叫停任务后不会被中断提醒再次唤醒

- **价值**：用户明确要求停止时，这轮工作会结束，不会因为系统自己补了一条提醒又继续做事。
- **覆盖场景**：[S5](acceptance.md#追加消息的两种走法)、[S6](acceptance.md#追加消息的两种走法)、[S39](../PF-012-agent-loop-and-run/acceptance.md#一可观察的场景)、[S66c](../PF-012-agent-loop-and-run/acceptance.md#一可观察的场景)
- **演示**：
  1. 发起含一次前台工具执行的任务，在工具尚未返回时请求优雅取消当前 Run → 先记录取消请求，不再发起本 Run 的新工作，按关联请求停止前台执行。
  2. 等收尾后查看结果 → Run 为 cancelled，工具收场标明被中断及叫停原因，不冒充执行失败或外部效果已撤销。
  3. 等系统补完中断提醒，保持不发送新任务 → 提醒可查，没有因此开出新 Run。
  4. 用户再发一个新问题 → 新 Run 能看到先前中断原因，旧 Run 仍为 cancelled。
- **不含**：强制停止、插队、单独中断模型、后台执行、子会话和等待卡组合。
- **前置**：ST-012-01、[ST-006-10](../PF-006-tools-and-skills/stories.md#st-006-10--停止一次工具执行后它不会自行重来)
- **就绪**：是

### ST-014-04 · 没有活跃执行者时也能强制停止原工作

- **价值**：用户的停止权不取决于当前是否存在 Agent Runtime，并且能分清逻辑停止与未收尾的真实效果。
- **覆盖场景**：[S48](../PF-012-agent-loop-and-run/acceptance.md#一可观察的场景)
- **演示**：
  1. 发起含在途模型或前台工具的工作，只移除 Agent Runtime，保留原执行 → 原执行及待承接关联仍可查，Run 未终结。
  2. 用户从控制入口强制停止该 Run → 持久取消意图存在，旧尝试失去推进资格，系统按关联通知本 Run 的模型和前台工具。
  3. 查看本轮结果 → 会话治理落 cancelled，并标明可能存在未收尾的外部效果；原调用真实收场和迟到账按原归属保留，不复活运行。
- **不含**：优雅等待收尾、会话归档、后台和 Run 外调用组合、撤销外部效果，以及取消中途再次停机的独立场景。
- **前置**：ST-014-03、ST-012-04、ST-012-05
- **就绪**：是

### ST-014-05 · 发送途中停机也不用猜是否需要重发

- **价值**：用户已经交给系统的消息不会因半途停机消失或被做两遍。
- **覆盖场景**：[S53b](acceptance.md#停机与恢复)、[S54b](acceptance.md#停机与恢复)、[S57](acceptance.md#停机与恢复)、[S58](acceptance.md#停机与恢复)、[S59](acceptance.md#停机与恢复)、[S55](acceptance.md#停机与恢复)、[S42b](../PF-012-agent-loop-and-run/acceptance.md#一可观察的场景)、[S44](../PF-012-agent-loop-and-run/acceptance.md#一可观察的场景)、[S61](acceptance.md#推进信号的丢失与重复)
- **演示**：
  1. 交付面保存一条可辨认的普通消息及同次提交标识，在持久提交前停机后恢复 → 先查明未受理，再沿原提交自动重试，通过当前准入后恰好入队一次，无需人手重新输入。
  2. 让另一条普通消息完整持久提交，但丢失受理回执，再沿同次提交查询或重试 → 查到原受理状态，没有第二条消息或第二次承接。
  3. 在当前 Run 尚未承接后续两条输入时停机，恢复后再读取但暂不持久承接并停机 → 两条仍待处理，系统自动恢复；按原顺序承接，每条只承接一次。
  4. 在上述承接已持久成立、Run 尚未完成时再次停机 → 原消息与承接记录可查，消息不重新排队；原 Run 恢复接续，不为它们另起一次工作。
  5. 分别构造停机前有活跃工作、恢复时已无活跃工作，以及相反的状态变化 → 普通消息到达的去处仍由消息性质决定，没有因运行状态改变而丢失或重投。
  6. 持久入队后丢弃推进通知并停机，在队列仍非空、没有 Run 的状态恢复 → 不等新边沿、发送方重投或查看，系统自动创建 Run 并处理；恢复可收到原重复通知。
- **不含**：外部来源事件去重、Connector、插队提交和会话归档竞争。
- **前置**：ST-014-02
- **就绪**：是

### ST-014-06 · 工作收尾时送来的新消息仍有人处理

- **价值**：用户恰好在上一轮结束时发送补充，也不会被漏掉或执行两遍。
- **覆盖场景**：[S35](../PF-012-agent-loop-and-run/acceptance.md#一可观察的场景)、[S62](acceptance.md#推进信号的丢失与重复)
- **演示**：
  1. 在模型已返回无动作、当前 Run 即将结束时，送入一条有独特标记的新消息 → 这条输入成功受理，排队或承接情况可查。
  2. 让输入先于终结生效，再查看处理结果 → 当前 Run 不结束，消费该消息后继续；消息只被承接一次。
  3. 再让终结先于输入生效 → 旧 Run 的 completed 保持不变，新输入沿普通受理启动下一 Run，并得到一次处理。
  4. 原 Run 和有效执行者已在时重复／合并推进通知 → 不重复承接或新建 Run／attempt，也不重复原外部调用。
- **不含**：后台结果、跨会话投递、归档和迟到费用；“两种顺序都不漏不重”仍须在适用约束下成立。
- **前置**：ST-014-01、ST-014-02、ST-014-05
- **就绪**：是

### ST-014-07 · 插队后在同一任务里改变方向

- **子期**：2A · 可控的人机协作
- **价值**：用户可以调整任务方向，已经形成的记录仍可查。
- **覆盖场景**：[S3](acceptance.md#追加消息的两种走法)、[S4](acceptance.md#追加消息的两种走法)、[S10](acceptance.md#插队停在几个位置上)、[S14](acceptance.md#插队停在几个位置上)、[S18](acceptance.md#插队停在几个位置上)、[S19](acceptance.md#插队停在几个位置上)、[S41](../PF-012-agent-loop-and-run/acceptance.md#一可观察的场景)
- **演示**：
  1. 模型生成途中插入优先消息，分别覆盖普通部分回复与参数已完整的工具建议 → 当前生成被中断，已有内容及原因保留，未发出的旧建议不执行；优先消息排最前。
  2. 在取批或组装阶段插队 → 不打断这一阶段；接着取批时优先消息先于普通待处理消息，同一 Run 继续。
  3. 在第一次插队后、loop 正在走向 T1 时再插第二条 → 第二条只放进队首，不重复中断；插队本身不把 Run 判为终态。
- **不含**：单独中断、工具后台转移和取消 Run。
- **前置**：ST-014-02
- **就绪**：是

### ST-014-08 · 插队时长工具按后台许可收场

- **子期**：2B · 稳定完成项目长任务
- **价值**：用户的新方向能优先处理，允许继续的原工具不会被无故杀掉。
- **覆盖场景**：[S11](acceptance.md#插队停在几个位置上)、[S12](acceptance.md#插队停在几个位置上)、[S13](acceptance.md#插队停在几个位置上)
- **演示**：
  1. 分别准备允许与不允许后台的长工具，在执行中插队 → 允许者转后台继续并记录插队原因；不允许者中断并记录插队原因。
  2. 在一批工具部分已完成时插队 → 已完成的结果保留，未完成者按各自后台许可处理，agent 接到优先输入。
- **不含**：工具自己的后台许可、自动到时转后台及后台结果通知；这些由前置或后续卡提供。
- **前置**：ST-014-07、ST-006-11、ST-006-12
- **就绪**：是

### ST-014-09 · 插队可以结束当前人工等待

- **子期**：2A · 可控的人机协作
- **价值**：用户可以在等待中改问另一件事，不被旧请示卡住。
- **覆盖场景**：[S15](acceptance.md#插队停在几个位置上)、[S16](acceptance.md#插队停在几个位置上)、[S17](acceptance.md#插队停在几个位置上)、[S20](acceptance.md#插队停在几个位置上)
- **演示**：
  1. 在 Ask 多问题等待中先跳过一张 → 其余未答问题仍等待；再插队 → Ask 取得“人拒绝回复”，不是执行失败，agent 处理优先输入。
  2. 在系统批准有三张待答卡时插队 → 整批从池移走，没有把未答项当批准，原动作取得“没批准”后处理优先输入。
- **不含**：后台等待、hook 卸载与取消整个 Run。
- **前置**：ST-008-05、ST-014-07
- **就绪**：是

### ST-014-10 · 单独中断后按队列决定是否继续

- **子期**：2A · 可控的人机协作
- **价值**：用户可以只停当前生成，而由已有待处理任务决定下一步。
- **覆盖场景**：[S7](acceptance.md#追加消息的两种走法)、[S8](acceptance.md#追加消息的两种走法)
- **演示**：
  1. 准备一个沿原规则继续的后台工具，再在当前模型生成中单独中断，队列为空 → 部分回复保留并标明中断、落中断提醒，后台工具不受影响；Run 完成，不为了再试一次立刻重调模型。
  2. 再起生成，先普通追加输入再单独中断 → 当前生成停下，已有部分回复保留并标明中断、落中断提醒，后台工具仍不受影响；Run 不因中断直接完成，随后承接队列中的输入。
- **不含**：优雅取消、强制取消以及工具和人工等待的单独中断变体。
- **前置**：ST-014-02、ST-006-12
- **就绪**：是

### ST-014-11 · 看见还有多少输入在排队

- **期次**：第三期 · 性能与体验
- **价值**：用户知道还有话尚未被接手，不会把排队误认为消息丢失。
- **覆盖场景**：[S43](acceptance.md#受理去重拦截)
- **演示**：
  1. 保持 Run 正在等待，连续提交多条普通输入使队列变长 → 输入仍被受理，没有因达到未声明的容量上限而拒收。
  2. 查看会话排队信息 → 用户能读出当前队列长度，与已被取走的输入分得清。
- **不含**：队列容量或限流新政策、排队项撤回、逐条排队位置、预计等待时长和插队控制。
- **前置**：ST-014-02、ST-012-07
- **就绪**：是
