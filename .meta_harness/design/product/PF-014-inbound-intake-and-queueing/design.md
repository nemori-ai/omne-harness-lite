- 状态：工作区显式资产重载的一致性增量已正式接受；原接受与未决范围见 [README](README.md#状态)。

**连接件范围说明**：连接件是否保留为资产尚未定论，相关输入路径仅为搁置的条件性设计，不构成当前交付承诺；通用受理、队列与归档规则继续成立。

## 一、背景与问题

[PF-012](../PF-012-agent-loop-and-run/design.md) 把一次运行的边界定死在一件事上：

> **进入 Agent Loop 的那一刻运行开始，退出的那一刻运行结束；
> 而退不退出，只看[待处理消息队列](../PF-012-agent-loop-and-run/design.md#待处理消息队列)空不空。**

**那条规则把整个「什么时候开始、什么时候结束」的问题，压到了队列身上。**
于是它留下的缺口也很集中：

**没有人回答的是：东西是怎么进到那个队列里去的。**

一个会话随时会被外面找上：用户说话、外部消息推进来、到点了、别的会话捎来一句、
后台的活干完了、人答了一张卡片、用户按了取消。
**这些事与一次运行的生命周期不对齐**——可能在运行中途到达、
在它[停着等人](../PF-008-human-in-the-loop/design.md#61-永远等着系统不替人作答)的时候到达、
也可能在它早就结束之后才到达。

四个问题因此悬着：

- **一条东西进来，先发生什么？**PF-012 说
  [外面进来的事必须先落进日志，组装只负责读](../PF-012-agent-loop-and-run/design.md#它们必须先落进日志这是被方程逼出来的)——
  **那么「落进日志」是不是它唯一的去处？**不是的话，还有哪几种，谁来定。
- **什么会让队列从空变成非空？**说不清，
  「[会话不要求有人说过话](../../ubiquitous_language/terms/agent-runtime-loop.md#ul-session--会话--session)」这条定义就只是一句话——
  **没有任何一条路能让「没人说话」的那几种真的发生**。
- **运行跑着的时候用户说了一句，会怎样？**PF-012 定了「队列非空就接着消费」，
  **但没定「用户等不及了怎么办」**。而这有两个都说得通的答案：等它做完，或者现在就打断它。
  **两个答案的产品长相完全不同。**
- **「打断」与「取消」是不是一回事？**不写死，用户插一句话就会把自己跑了两小时的任务杀掉。

> **本 topic 只回答「怎么进来」。**进来之后怎么转，
> [PF-012 已经定死了，本 topic 一个新分支都不加](#八边界与依赖)。

## 二、目标与非目标

### 目标

1. **定义[入站到达](#入站到达)，并定出它受理之后的[三个去处](#三个去处)**——
   外面进来的每一件事先成为什么，之后往哪走。
2. **穷举什么会进入[待处理消息队列](../PF-012-agent-loop-and-run/design.md#待处理消息队列)，什么不会**。受理形成可恢复的待处理资格；[Trigger](../../ubiquitous_language/terms/agent-runtime-loop.md#ul-trigger--触发--trigger)促使系统检查和推进，具体推进分支沿 PF-012，不以队列变化代替 Run 边界。
3. **穷举什么会影响「退出循环的判断」**，且**全部挂在
   [PF-012 已定的两层出口](../PF-012-agent-loop-and-run/design.md#这个循环从哪里出去)上**，不另起一套。
4. **定义[插队](#插队)**：它做什么、不做什么、与取消差在哪。
5. **定义[控制指令](#控制指令)这个家族**：判据是什么、今天有哪几条、谁拥有它们的语义。
6. **定受理面的共同规矩**：怎么去重、排着的东西怎么让人看得见、怎么保证不漏不重。

## 三、用户与场景

| 使用者 | 什么时候接触这块 | 他关心什么 |
|---|---|---|
| **用户** | agent 正在干活，他想补一句 | **这句话什么时候会被看到？**会不会把正在做的事搞砸 |
| **用户** | 他改主意了，想让它现在就停下来听他说 | **「停下来听我说」和「别做了」是不是一回事？**我会不会误杀自己的任务 |
| **用户** | 他让 agent 跑一个两小时的构建，然后去忙别的 | **好了会有人告诉我吗**，还是要我自己回来问 |
| **接了外部消息源的人** | 一个频道天天有消息 | **是不是每条都会把 agent 叫起来、都要花钱** |
| **对成本负责的人** | 看账单 | 这次运行的账里**有没有混进不属于它的东西** |
| **安全负责人** | 企业场景 | 敏感信息能不能**在进日志之前**就被拦下 |
| **运维** | 一个后台结果回来了，但看上去没人处理 | **它去哪了？为什么没人来看它** |
| **agent** | 每一轮 | 我上一步为什么断了？**那是一次失败，还是有人叫停** |

**第二行是本 topic 最要紧的一个场景。**用户按下一个键，可能得到两种完全不同的结果——
**一种是他的任务接着跑、只是先听他说话，另一种是他的任务当场死掉。**
这两件事分不开，产品就不能用。

### 入站到达

**外面要送进一个会话的一件事，被受理之后成为的那条事实。**

> **受理是一个动作，不是一个通道。**东西送到了不等于被受理；
> **完整持久提交的那一刻，它成为一条可以被指着说「就是它」的事实。**
> 普通消息同时取得待处理资格；卡片答复和控制指令保存各自目标与处置责任，不进普通消息队列。回执未知不是未受理的事实。

| 性质 | 说明 |
|---|---|
| **归属于恰好一个会话** | 没有「飘着的到达」。送不进任何会话的东西，在受理这一步就被具名拒绝 |
| **有一个来源** | [来源是一个属性，不是另一种类别](../PF-009-context-message-types/design.md#65-来源是一个属性不是另一种消息)——同一套受理规矩对所有来源成立，差别只在取值 |
| **有一个[去处](#三个去处)** | 受理之后它往哪走，**由它是什么决定，不由此刻处境决定**（[§5.2](#52-三个去处为什么是穷尽的)） |
| **受理了就不会凭空消失** | 它要么被消费，要么被明确关掉——**两种都留痕**。[静默丢弃是本 topic 的头号事故](acceptance.md) |

**差一点就是它、但不是它**：**「一条消息」**。
消息是[七种之一](../PF-009-context-message-types/design.md#七种消息按谁在说话分)，回答**谁在说话**；
入站到达回答**外面送进来了一件什么事**。
**大多数入站到达会成为一条消息**，但不是全部——
一张卡片的答复、一条取消指令，都不是消息。

> **「从哪个通道进来」是它的一个属性，不是它的种类。**
> 用户敲的、连接件送的、定时到点的、别的会话捎来的，**走同一个受理面**。
> [PF-009 已经把这条道理写死了](../PF-009-context-message-types/design.md#65-来源是一个属性不是另一种消息)，本 topic 沿用。

### 三个去处

**一条[入站到达](#入站到达)被受理、落进[会话日志](../PF-012-agent-loop-and-run/design.md#会话日志)之后，只可能往三个地方去。**

> **「落进日志」不是去处，它是每一条入站到达的共同动作**（[§6.1](#61-先落账再谈别的)）。
> **去处回答的是另一个问题：谁会来看它。**

| 去处 | 它成为什么 | 谁来看它 |
|---|---|---|
| **进[待处理消息队列](../PF-012-agent-loop-and-run/design.md#待处理消息队列)** | 一条[消息](../PF-009-context-message-types/design.md#七种消息按谁在说话分) | **loop**。[队列非空它就不退出](../PF-012-agent-loop-and-run/design.md#run)；已经退出了的，**它一来就开下一个运行** |
| **落到一张[决策卡片](../PF-008-human-in-the-loop/design.md#决策卡片)上** | 一条**答复** | **那张卡片背后等着的那个东西**。[一批全答完才解除](../PF-008-human-in-the-loop/design.md#53-一批卡片与答完是什么意思) |
| **就地处置** | 一条[控制指令](#控制指令)，或一次[系统业务流程的触发](#510-斜杠命令在受理时分两路走)（绑定目标为 ③ 的斜杠命令） | **没有人「看」它**——控制指令改的是执行权或队列本身，系统业务流程由那条流程自己去办；两者都[不进 agent 的上下文](#控制指令) |

**三个为什么是穷尽的**：问两遍。

```text
                  这条入站到达，是内容还是处置？
                        │
           处置 ────────┴──────── 内容
            │                       │
      【就地处置】        它是不是在答一个已经问出去的问题？
                                    │
                        是 ─────────┴───────── 不是
                        │                        │
                  【落到卡片上】            【进队列】
```

> **这两问是判据，不是分类法。**将来多出一种来源，问它两遍就知道它去哪，
> **不必往这张表上加第四行。**

#### 为什么没有「只记一笔」这一档

**很自然会想给它加第四档**：落进日志，但**不进队列**——
「有运行会来看它，不必为它专门起一次运行」。**不加，因为
[运行退不退出本来就只看队列空不空](../PF-012-agent-loop-and-run/design.md#run)：**

| 后台结果回来时 | 进队列之后会发生什么 |
|---|---|
| **运行还在跑** | 队列非空，**那个运行本来就还没退出**，它接着消费 |
| **运行已经结束** | 有仍具待处理资格的未承接输入且没有未终结 Run，**创建下一个 Run 及首个 attempt** |

> **两种处境，同一个去处，两种自然结果。**
> 差别不在那条到达身上，**在于队列此刻空不空**——而那是 loop 的事，不是受理面的事。

**收益是受理面不必知道「此刻有没有运行在跑」。**
有了第四档就得知道，而**知道这件事是做不准的**——
[定落点的那一刻与运行结束的那一刻之间总有缝](#67-不漏不重)。
**现在那条缝不存在**：落进日志就是进队列，**没有中间态可漏**。

### 控制指令

**用户对正在发生的事、或对[待处理消息队列](../PF-012-agent-loop-and-run/design.md#待处理消息队列)本身的一次直接处置。**

**三条性质合起来才是它，缺一条就不是：**

| | |
|---|---|
| **它不是内容** | 它不进入 agent 的上下文去被理解，**它改变的是执行权或队列本身** |
| **它不排队** | 排队的意义是「等一个合适的时候」，**而它要的恰恰是现在** |
| **它的语义归定义那个动作的 topic** | **本 topic 不发明控制指令**，只定义受理面与这三条共同性质（[§5.5](#55-控制指令家族)） |

> **「键盘控制」不是一类到达。**它是**发出一条控制指令的一种敲法**——
> 同一条指令可以敲键盘发、点按钮发、调接口发。
> 把敲法当成一类东西，[斜杠命令](../../ubiquitous_language/terms/capabilities-and-composition.md#ul-slash-command--斜杠命令--slash-command)与它的边界就永远划不清；
> 问「它是内容还是处置」，边界当场就清楚了。

### 插队

**用户发出的一条[控制指令](#控制指令)，意思是「这句话我要现在就被看到」。**

它做**三件事，而且这三件事要么一起成立、要么都不成立**（[§6.5](#65-插队是原子的)）：

| | |
|---|---|
| **一** | 按[「最大程度保留」这条原则](#53-插队的核心原则)处置 loop 正停着的那一步 |
| **二** | 把用户这句话**放到[待处理消息队列](../PF-012-agent-loop-and-run/design.md#待处理消息队列)的队首** |
| **三** | 落下相应的占位与提醒，**让 agent 知道刚才发生了什么、为什么** |

> **⚠️ 插队不终止[运行](../../ubiquitous_language/terms/agent-runtime-loop.md#ul-run--运行--run)。**
> 这是它与[取消](#55-控制指令家族)最要紧的差别，也是本 topic 与**那份留档提案**
> （**只作起点，不作依据**；出处见 [decisions.md](design.md)）分歧最大的一处：
> 那边是「打断，然后起一个新的运行」，**这边运行一直活着，只是走到下一个取消息的那一点**。

**「插队」这个名字容易误导，说明白**：它插的不是别人的位置，是**时间**——
[排队等 loop 自己走到取消息那一步，插队把那段间隔压到最短](../PF-012-agent-loop-and-run/design.md#什么时候到与-loop-走到哪一步无关)。
**队首那一项是它的落脚处，不是它的目的。**

> **它是系统唯一的加急通道。**[PF-012 定死了不设第二种优先级](../PF-012-agent-loop-and-run/design.md#先到先处理只有一个例外)——
> 「工具结果要不要天然比用户消息优先」这类分级一律不做，**一个机制，不是两个**。

## 五、模型

### 5.1 一条入站到达从哪里来，到哪里去

```text
  外部输入 → 校验目标、资格、同次提交与落盘前干预
                         │
                         ▼
       【完整持久提交：入站事实 + 对应去处的责任】
                         │
           ┌─────────────┼─────────────┐
           ▼             ▼             ▼
       普通消息       卡片答复        控制指令／业务触发
       待处理资格     指定卡片关联    指定目标与待处置责任
           │             │             │
       Loop 承接       原等待接续      按该动作规则处置
```

去处由输入性质决定；提交不得只保存入站事实而遗漏其待处理或待处置责任。实际执行、外部效果与命令生效另按各自规则完成，不以“指令已受理”冒充“动作已完成”。

**这张图最要紧的一条**：**受理面只有一个，去处有三个。**

**斜杠命令不是图左边的一条来源线。**它是人在[交付面](../../ubiquitous_language/terms/interaction-and-dispatch.md#ul-delivery-surface--交付面--delivery-surface)上敲下的「用户说话」那一路上的**标注**：
来源仍是用户，标注说的是「这条输入开头是一个命令」。它按绑定目标落进三个去处中的两个，见 [§5.10](#510-斜杠命令在受理时分两路走)。

**那份留档提案把控制排除在到达之外**，于是它有两个受理面。**我们不沿用**——
取消和插队同样是**从外面进来的**，
[PF-012 自己就把取消归到「外面进来的事」那条路上](../PF-012-agent-loop-and-run/design.md#被取消不在这张表里因为它不是一行)。
**受理面统一、去处分叉，比两个受理面干净**：
去重、留痕、租户隔离、[消息落盘之前那个位置](#56-消息落盘之前那一刻看得到什么)
**只需要在一个地方成立**。

### 5.2 三个去处，为什么是穷尽的

**判据在[§4](#三个去处)，这里只补一句它最要紧的性质：**

> **一条入站到达的去处，由它是什么决定，不由此刻的处境决定。**

**这一句挡掉的是「同一个来源，两次到达的去处可以不同」那种写法**——
典型例子是后台结果：运行还在跑就「只记一笔」，运行结束了就「入队」。
**那个分叉不需要**，因为
[运行退不退出本来就只看队列空不空](../PF-012-agent-loop-and-run/design.md#run)：

| | |
|---|---|
| 运行还在跑 | 那条消息进队列，**队列非空，它本来就还没退出**——接着消费 |
| 运行已经结束 | 那条消息持久入队且没有未终结 Run，**创建下一个 Run 及首个 attempt** |

> **同一个动作，两种自然结果。**而受理面**不必知道此刻有没有运行在跑**。

**这一条的份量在于它消掉了一个很难兑现的要求。**
「[不漏不重](#67-不漏不重)」最容易破在一个具体时刻：**一条到达正在定落点，
而那个运行恰好在这一刻结束**——定成「只记一笔」就漏，定成「入队」就可能重。
**照现在这样，那个时刻不存在**：落进日志就是进队列，**没有中间态**。

### 5.3 插队的核心原则

**全部规则都从这一句推出来，不必背条款：**

> **在最大程度保留已经到达的响应、已经执行的工具调用的前提下中断。**

**为什么是「保留」而不是「干净地回滚」**：那些东西**已经发生了**。
模型已经吐出来的半句话，[用户可能已经看见了](../PF-009-context-message-types/design.md#56-流断在半路)；
一个已经跑完的工具调用，**它的外部效果收不回来**。
把它们抹掉不叫干净，叫**记录与事实对不上**——而
[会话日志是唯一的真相来源](../PF-012-agent-loop-and-run/design.md#52-会话日志是唯一的真相来源)。

**这条原则同时解释了为什么系统必须能「单独地」中断**：
中断一次[模型调用](../../ubiquitous_language/terms/execution-and-outcome.md#ul-model-call--一次模型调用--model-call)、
中断一次[工具执行](../../ubiquitous_language/terms/execution-and-outcome.md#ul-tool-execution--工具执行--tool-execution)，
**是两个动作**。只有一个「全停」按钮的话，
**一次模型回复刚开始、而三个工具调用里有两个已经跑完了**——那两个的结果就一起没了。

### 5.4 插队：停在哪，就怎么办

**loop 只可能停在这几个地方，所以这张表是穷尽的：**

| loop 停在哪 | 动作 | 落下什么 |
|---|---|---|
| **等模型回复** | 中断这次模型调用，**保留已经到达的部分**；**这份被中断的回复不交出动作**——里面哪怕有参数已经收齐的工具调用，也不执行 | [那半份收成一条标明被中断的消息](../PF-009-context-message-types/design.md#56-流断在半路)，**外加一条中断提醒**——**怎么收归 PF-009** |
| **工具执行中，[声明了允许转后台](../PF-006-tools-and-skills/design.md#66-前台后台-与-等待态是两个维度)** | **转后台**（那次执行继续跑） | 占位的工具返回消息，原因「**因插队转后台**」 |
| **工具执行中，不允许转后台** | **中断这次执行** | 占位的工具返回消息，原因「**因插队被中断**」 |
| **[`Ask()`](../PF-007-meta-capabilities/design.md#611-ask通向人) 停在那儿等人** | **中断这次执行** | 占位的工具返回消息，原因「**人拒绝回复**」 |
| **[运行等待态](../../ubiquitous_language/terms/interaction-and-dispatch.md#ul-run-wait-state--运行等待态--run-wait-state)上悬着卡片** | **取消等待，卡片从[决策池](../PF-008-human-in-the-loop/design.md#决策池)移除** | 每张卡片记作「**人明确拒绝回复**」（[§5.4.2](#542-两种等人答机制各归各产品语义是同一条)） |
| **正在取队列 / 正在组装 / 正要调模型** | **什么都不中断** | 那句话进队首，**loop 马上就会取到它**（[§6.5](#65-插队是原子的)） |

**前三行是同一条原则的三个取值**：能保留的就保留（转后台保留得最多），
保不住的就中断，**但一定留下占位**。

**最后一行不能省**：它说明**插队在任何时刻都是合法的**，
**没有一个「现在不能插」的窗口**——否则用户按下去没反应，而他不知道为什么。

**第一行「被中断的回复不交出动作」，同样从[那条原则](#53-插队的核心原则)推出来。**
它要保留的是**已经到达的响应**与**已经执行的工具调用**；回复里一个参数收齐、还没执行的工具调用，
**属于前者，不属于后者**——它照样留在那条被中断的消息里，只是不去执行。
执行它，就是在用户刚说「先听我说」之后**凭空多出一个外部效果**，而他那句话 agent 还没读到。
agent 读完那句新话，要不要重新发起，由它自己决定：**不做的可以再做，做了的收不回来**——
与[取消只能往拒绝那边倒](#543-取消视作拒绝为什么只能往这个方向倒)是同一个方向。
**这一条不只对插队成立**：用户[单独中断一次模型调用](#55-控制指令家族)，被中断的那份回复同样不交出动作。

#### 5.4.1 占位消息一律要说清原因

**目的只有一个：避免 agent 把它读成「这个工具执行失败了」。**

[PF-006 已经把这条道理写死了](../PF-006-tools-and-skills/design.md#67-用户可以中断而中断不是失败)：
**失败是「这事没成」，中断是「这事不做了」。**把中断当成失败递给 agent，
**它会重试——而用户刚刚明确表示他要说别的。agent 越勤快，后果越糟。**

**「因插队转后台」那一条尤其不能省**：转后台是一个**正常的收场**，
不说原因的话，agent 会以为是它自己或工具作者的安排，**而实际上是用户按了一下**。

#### 5.4.2 两种「等人答」：机制各归各，产品语义是同一条

**`Ask()` 与[运行等待态](../../ubiquitous_language/terms/interaction-and-dispatch.md#ul-run-wait-state--运行等待态--run-wait-state)挂在不同的生命周期上**，
[词表已经把它们分开了](../../ubiquitous_language/terms/execution-and-outcome.md#ul-tool-wait-state--工具等待态--tool-wait-state)，
本 topic 不合并它们。

| | **`Ask()`** | **运行等待态** |
|---|---|---|
| 挂在 | 一次**工具执行**上 | 一个**运行**上 |
| 谁发起 | **agent 自己**决定要问 | **系统**在拿到模型响应之后[算出来](../PF-008-human-in-the-loop/design.md#52-那个判断函数) |
| 插队时怎么处置 | **中断那次工具执行**，占位原因「人拒绝回复」 | **取消等待**，卡片移出决策池 |
| 之后 loop 走到 | 工具结果齐了 → [T7 → T1](../PF-012-agent-loop-and-run/design.md#56-状态转移表) | 卡片全答完 → [T5 → T8 → T1](../PF-012-agent-loop-and-run/design.md#56-状态转移表) |

> **两条路，同一个终点：[T1，也就是取一批消息的那一点](../PF-012-agent-loop-and-run/design.md#56-状态转移表)。
> 零个新的状态转移。**

**产品语义上，这两行是同一条**：

> **人的处理有两种——回复，或者明确拒绝回复。插入消息属于后者。**

**`Ask()` 为什么不走「转后台」那条路**：[它的等待永远在前台阻塞运行、不过期，因而不可转后台](../PF-007-meta-capabilities/design.md#611-ask通向人)。
**这一句必须由 PF-007 明写**——读者照普通工具的等待态去推，会推出相反的结论。

#### 5.4.3 「取消视作拒绝」为什么只能往这个方向倒

**产品负责人给的理由原样录在这里：**

> 在用户没有明确答复的前提下，**取消视作拒绝是无副作用、可逆的**——
> 大不了用户在对话里显式再说一句批准，agent 重新做就是了。

**反过来倒是不对称的**：视作批准会**当场产生外部效果**，而那些效果收不回来。
[`Ask().request_approval` 的第三条性质说得更直白](../PF-007-meta-capabilities/design.md#611-ask通向人)——
**问的那一刻世界还是原样，所以人说「不行」不需要任何收拾。**

#### 5.4.4 这没有推翻 PF-008，它把一个词说全了

**[PF-008 §6.1](../PF-008-human-in-the-loop/design.md#61-永远等着系统不替人作答) 那个穷举，本 topic 一条都不动：**

> 清掉一张卡片只有两条路——**人处理它**，或者这个会话
> [被归档](../../ubiquitous_language/terms/agent-runtime-loop.md#ul-session-archival--会话归档--session-archival)。

> **第二条路的正式说法是[归档](../PF-015-session-lifecycle-and-ownership/design.md#会话归档)。**
> **[「会话结束」这回事不存在](../../ubiquitous_language/terms/agent-runtime-loop.md#ul-session--会话--session)**——
> **凡是挂在「这段协作到此为止」上的东西，锚点都是归档**，本 topic 用的是这个词。

**插队不是第三条路，它是「人处理它」的第二种形式。**
不动结构，只把一个已有的词说全——**这比新增一条路便宜得多**。

**而 PF-008 §6.1 禁的到底是什么，必须说清，否则读者会以为这里破了那条：**

| §6.1 禁的 | 本 topic 做的 |
|---|---|
| **没有事件也要给答案**——超时到点、默认答案 | **有明确事件：用户主动发了一条指令** |
| 系统**替人**作答 | **人自己作了答**，答的是「我现在不回这个」 |

> **时间流逝替人签字，和人自己改变主意，是两回事。**
> §6.1 的原话理由是「**等待期间世界里什么都没发生**」——
> 插队这一刻，世界里发生了一件事，而且是人做的。

**而「明确拒绝回复」这件事 PF-008 早就有了**：
[§6.5「不回答」是合法答复](../PF-008-human-in-the-loop/design.md#65-不回答是合法答复)——
人可以在卡片上直接表示「这个我不答」，**它解除那张卡片，也计入「答完」**。

> **所以插队不是这件事的唯一入口，是它的第二个入口。**
> **两个入口的粒度不同**：卡片上那个跳**一张**，插队解除的是**运行等待态上悬着的全部**。
> **不点破这一点，会以为它们二选一。**

**还有一个歧义 PF-008 已经替我们消解掉了**：
[答复只在卡片上做，消息永远是消息](../PF-008-human-in-the-loop/design.md#55-两条入口一件事)。
所以**插队带的那句话不会被误读成对某张卡片的答复**——它就是一条消息。

### 5.5 控制指令家族

**本 topic 不发明控制指令。**它定义[判据](#控制指令)与受理面；
**家族成员由别的 topic 的产品语义决定**。所以这张表的完备性判据是一句可核对的话：

> **把所有 topic 扫一遍，问「用户可以对正在进行的事做什么」。**

**今天扫下来是六条：**

| 控制指令 | 它处置什么 | 语义归谁 | 它动的是[哪个出口](../PF-012-agent-loop-and-run/design.md#这个循环从哪里出去) |
|---|---|---|---|
| **取消** | 这一次运行 | [PF-012](../PF-012-agent-loop-and-run/design.md#被取消不在这张表里因为它不是一行) | **运行的出口**——落终态「被取消」 |
| **[强制停止](../../ubiquitous_language/terms/agent-runtime-loop.md#ul-forced-stop--强制停止--forced-stop)** | 这一次运行，连同它的执行资格 | 统一语言 / [PF-004](../PF-004-agent-definition-and-assembly/README.md) | **运行的出口** |
| **[插队](#插队)** | loop 正停着的那一步 | **本 topic** | **一次尝试的出口**——**运行不落终态** |
| **把一次工具执行切到后台** | 那一次工具执行 | [PF-006 §6.6](../PF-006-tools-and-skills/design.md#66-前台后台-与-等待态是两个维度) | 可能**结束一次「停住等」** |
| **中断一次工具执行** | 那一次工具执行 | [PF-006 §6.7](../PF-006-tools-and-skills/design.md#67-用户可以中断而中断不是失败) | 同上 |
| **中断一次模型调用** | 正在吐字的那一次模型调用 | [PF-013 §5.13](../PF-013-model-profiles-and-invocation/design.md#513-模型请求的运行时可以被单独控制而它停了看首-token) | **不直接动哪个出口**：那次调用收场为「被中断」，[被中断的回复不交出动作](#54-插队停在哪就怎么办)，loop 照转移表往下走——**队列里有待处理的就回 T1，没有就是「完成」**（[§5.8](#58-穷举二什么会影响退出循环的判断)） |

**后三条单独处置一件正在进行的事，不碰整个运行。**它们的语义早就在别处：
PF-006 写了「用户也可以手动把它切到后台」「用户可以提前中断」，
PF-013 写了「中断这一次调用，不动别的」。**受理面接住的是它们共同缺的那一半**——
用户那个动作从哪进来、要不要排队、跟取消是不是一回事。**这正是统一受理面的价值。**

> **「中断一次模型调用」与插队的第一行长得一样，差在队列里有没有那句话。**
> 插队把用户的话放上队首，loop 必然回 T1、读到它；单独中断**不带话**，
> 于是被中断之后**队列里若没有别的待处理，这次运行就此完成**——
> 用户要的正是「别说了」，[那条中断提醒不会把 agent 重新叫起来](#57-穷举一什么会让队列从空变成非空)。
> 他下一次开口，agent 在新的运行里读得到那半句与那条提醒。

#### 插队与取消，差别必须写死

| | **插队** | **取消 / 强制停止** |
|---|---|---|
| 运行落不落[终态](../PF-012-agent-loop-and-run/design.md#运行终态) | **不落。**它继续往下走 | **落。**终态「被取消」 |
| loop 之后干什么 | 走到 T1，**读用户那句新话** | **停了**。方程读到终态就停 |
| 用户想要的是 | **先听我说** | **别做了** |
| 搞混的后果 | —— | **用户插一句话，就把自己跑了两小时的任务杀掉了** |

> **这两条指令在界面上可能只差一个键。**所以它们的产品语义差多少，
> **必须在这里写到没有解释余地。**

#### 看着像控制指令，其实不是

| | 它其实是什么 |
|---|---|
| **在一张卡片上作答**（含[「我不答这个」](../PF-008-human-in-the-loop/design.md#65-不回答是合法答复)） | 一条入站到达，去处是**落到卡片上**。它提供的是**内容**，不是处置 |
| **[斜杠命令](../../ubiquitous_language/terms/capabilities-and-composition.md#ul-slash-command--斜杠命令--slash-command)** | 一条入站到达。绑定目标是提示词或 skill 的，去处是**进队列**——它要 agent 去做一件事，那是**内容**。绑定目标是系统业务流程的，去处是**就地处置**，但它也**不是控制指令**：它处置的不是正在发生的事或队列，而是交给那条流程去办（[§5.10](#510-斜杠命令在受理时分两路走)） |
| **换一个模型** | 一条会话事实。[PF-013 已定：正在进行的那一次照常跑完，不打断](../PF-013-model-profiles-and-invocation/design.md#59-换模型一条事实一个生效点零个新分支) |
| **一个依赖恢复了、一项权限变了** | 什么都不是——**它根本不必进受理面**。[可用性在每一次尝试开始时重算](../PF-012-agent-loop-and-run/design.md#每一次尝试开始都要做四件事)（[PF-006 定的是「每次 run 开始前」，而每一次尝试也算一次开始](../PF-006-tools-and-skills/design.md#62-可用性在每次-run-开始前重算)），下一次算到它就是了 |

**最后一行值得多说一句，因为 legacy 在这里有一条我们没有的东西**：
那份提案里有「额度恢复 / 依赖恢复唤醒一个在等门的运行」。
**我们的模型里没有「等门」这个停住点**——
[PF-012 的两个停住点只有「等人」与「等动作结果」](../PF-012-agent-loop-and-run/design.md#56-状态转移表)。
**没有那个停住点，就不需要那条唤醒的路。**

#### 为什么没有「撤回一个排队项」

**「让用户撤回一条还没被取走的排队项」不做，两条理由：**

| 理由 | 说明 |
|---|---|
| **它与[队列是日志的投影](../PF-012-agent-loop-and-run/design.md#待处理消息队列)打架** | 那条消息**已经在只增不改的日志里了**。要「撤回」就得再追加一条撤回条目、并让投影把它排除——**为一个没人要过的功能，给队列这个概念加一层间接** |
| **没有产品需求撑着它** | 用户想改口，**说一句就是了**；agent 会看到两条，而[后一条本来就覆盖得了前一条的意思](#63-去重只认来源说得出的那个同一件事) |

> **不做它不是因为做不到，是因为它买不到什么。**
> 真出现要它的场景，再回来加——**那时它是一条规则，不是这份设计的骨架。**

### 5.6 「消息落盘之前」那一刻，看得到什么

[PF-012 把这个位置开了出来，并把一半划给本 topic](../PF-012-agent-loop-and-run/design.md#消息落盘之前每条消息都经过它不只是输入)：
**位置存在、挂的是[拓展件](../PF-012-agent-loop-and-run/design.md#拓展件)、走同一套[干预力](../PF-012-agent-loop-and-run/design.md#干预力三档直接用-pf-000-的)，归那边；
那一刻具体看得到什么，归这里。**

> **这个位置比本 topic 的受理面大。**它**每有一条消息要落盘就经过一次**——
> 不论那条消息是用户说的、模型吐的还是工具交回来的。
> **本 topic 只管其中「从外面进来」的那些**；模型吐的、工具交的那些同样经过它，
> 但它们不是入站到达。

| 看得到 | 看不到 |
|---|---|
| **那条还没落盘的消息的内容**（一串[内容块](../../ubiquitous_language/terms/record-and-context.md#ul-content-block--内容块--content-block)） | **此刻有没有运行在跑**——[去处不由处境决定](#52-三个去处为什么是穷尽的) |
| **它的来源、它要进哪个会话** | **它会不会开一个新运行** |
| **人敲了斜杠命令的，看到的是展开之后的那条消息，外加原命令的标注**（[§5.10](#510-斜杠命令在受理时分两路走)） | **展开之前的样子**——展开发生在受理时，比这个位置早 |

**三档干预力在这个位置各是什么：**

| 档 | 在这儿意味着 |
|---|---|
| **只观察** | 看一眼，照常受理 |
| **可改写** | **改内容**——脱敏在这一档；[模态转换](../PF-013-model-profiles-and-invocation/design.md#转换件)给块挂上派生表示与 transcript、原块不动，也在这一档 |
| **可否决** | **这条到达根本不被受理**，不进日志正文。**模态转换件转不成，也走这一档**：[转换失败就是落盘前的否决](../PF-012-agent-loop-and-run/design.md#模态转换为什么必须落在这里)，发的人被告知，会话里什么都没多 |

> **模态转换件站在这个位置上，但它的契约归 [PF-013](../PF-013-model-profiles-and-invocation/README.md)**——
> 「有哪些模态、哪个模型收得下哪些」是大语言模型域定的。
> **本 topic 只定它在受理面上看得到什么：一串内容块，外加来源。**

#### 否决了，也不许静默

**否决的后果有两层，别混成一层：**

| | |
|---|---|
| **那条到达的内容** | **不进日志正文。**[PF-012 给这个位置的理由就是这个](../PF-012-agent-loop-and-run/design.md#消息落盘之前每条消息都经过它不只是输入)：拦下来的东西落盘再删，等于承认它曾经进过方程的定义域 |
| **「有一条到达被拦下了」这件事** | **必须留一笔。**这不是本 topic 新定的——[PF-012 §6.10「能干预的拓展件必须留下结论」](../PF-012-agent-loop-and-run/design.md#610-能干预的拓展件必须留下结论)已经要求了，而[留痕这一档本来就不进方程的定义域](../PF-000-occurrences-and-record-entries/design.md#条目效力--entry-standing)，**两条不冲突** |

**还有一条只对用户成立**：

> **用户自己发的那一条被拦下时，必须让他看得出来。**

不然他的话凭空消失，**而他会再发一遍**——
[而用户自己发的东西我们不去重](#63-去重只认来源说得出的那个同一件事)，于是 agent 真的收到两条。
外部来源要不要回告发送方，是**那件拓展件的事**：
告诉一个正常的外部系统「你的消息没进来」，和告诉一个攻击者「你被识别了」，代价完全不同。

### 5.7 穷举一：什么会让队列从空变成非空

**本节穷举什么会进队列，不根据队列原本空不空决定新建 Run。**输入持久入队后，系统按 [PF-012 的开始与推进边界](../PF-012-agent-loop-and-run/design.md#边界什么让它开始什么让它结束)检查：没有未终结 Run 时创建 Run；已有 Run 时交给它，按有效执行者及等待条件决定继续原 attempt 或创建新 attempt。

**队列为空不证明 Run 已结束；队列非空不证明已有执行者。**原输入已承接而模型仍在途时，新消息可使队列空转非空，仍由原 Run 处理。恢复时队列已非空却没有 Run，系统照样创建 Run，不等待新的空转非空。

Trigger 只是推进通知，不能代替受理事实或承接责任。通知可以重复、合并或重建；已受理输入不因通知丢失永久悬空，受理完成不等待通知送达。重复或过时通知本身不提供新的工作依据；仍检查当前持久事实，按其合法分支推进，不额外新增入站事实、Run、attempt 或外部调用。具体机制归技术设计。

**会进队列的，是这些：**

| 进队列的 | 在队列里是哪一种消息 | 它凭什么成立 |
|---|---|---|
| **用户说的一句话** | `UserMessage` | —— |
| **用户敲的一个[斜杠命令](../../ubiquitous_language/terms/capabilities-and-composition.md#ul-slash-command--斜杠命令--slash-command)，绑定目标是提示词或 skill** | `UserMessage`，**展开之后的**那一条，带原命令的标注 | 它要 agent 去做一件事，**那是内容不是处置**。来源仍是用户，斜杠命令是这条消息上的标注（[§5.10](#510-斜杠命令在受理时分两路走)） |
| **一条外部消息经[连接件](../PF-002-assets-settings-and-permissions/design.md#connector)送进一个已有的会话** | `UserMessage` | 连接件是**唯一回答「agent 从哪里被触达」的资产**。[送进来的就要被处理](#62-送进来的就要被处理要不要送进来归连接件)。这是连接件[两种投递方式](../PF-002-assets-settings-and-permissions/design.md#两种投递方式动作主体不同)里的 ① 那一路：**进哪个会话，是那份连接件上配的[投递目标](../../ubiquitous_language/terms/interaction-and-dispatch.md#ul-inbound-target--投递目标--inbound-target)，指的是一个已有的会话**；按外部线程分进不同会话，本版没有 |
| **连接件送来的一件事，经受理开出一个新会话** | `UserMessage`，落在那个新会话里 | 连接件两种投递方式里的 [② 那一路](../PF-002-assets-settings-and-permissions/design.md#两种投递方式动作主体不同)：**由受理开一个新会话，这条消息落进去，那个会话形成待处理输入；没有未终结 Run 时开起它的第一次运行**；新会话起步时的运行模式取那份连接件上配的[触发会话的默认运行模式](../PF-002-assets-settings-and-permissions/design.md#触发会话的默认运行模式)。创建身份与定义沿 [PF-015 §6.23](../PF-015-session-lifecycle-and-ownership/design.md#623-连接件创建会话的输入)；来源可指认的同一事件重复到达沿 §6.3 去重，不重复建会话。同一事件的路由及多接收者资格由 PF-002 决定，不按外部线程自动合并会话 |
| **一次[工具执行](../../ubiquitous_language/terms/execution-and-outcome.md#ul-tool-execution--工具执行--tool-execution)交回结果** | `ToolMessage`，填在那次调用的位置上 | [PF-012 §5.11](../PF-012-agent-loop-and-run/design.md#511-外面进来的事怎么到-agent-眼前) |
| **一次工具执行转了后台** | 那次调用的位置先落一条**占位** `ToolMessage` | 同上 |
| **一次[后台执行](../../ubiquitous_language/terms/execution-and-outcome.md#ul-background-execution--后台执行--background-execution)完成回传** | **`SystemReminderMessage`**——那次调用的位置已被占位填掉，**结果回来时没有它的位置** | 同上；**这一条正是[「好了告诉我」那个用户故事](#三用户与场景)的落点** |
| **[runtime context](../PF-015-session-lifecycle-and-ownership/design.md#runtime-context) 的某一块被生产方推来了变更，而此刻有运行在跑** | `SystemReminderMessage`（**说状态的，[写清「从什么变成了什么」](../PF-009-context-message-types/design.md#64-说状态的写清变化说事的写清发生消息一律追加)**） | 同上 + [§6.10](#610-注入的上下文变了没有运行在跑时什么都不做)。**会话空闲时推来的不在这张表里——它根本不产生一条到达** |
| **到点了**（日程 / 定时） | `SystemReminderMessage` | 到期工作的输入与去处由日程能力决定，推进沿 PF-012。日程能力归 [PF-021](../PF-021-schedule-and-calendar/design.md#63-机械执行与每次-agent-执行的新会话)：agent 工作先建专属租户会话，再沿本处受理；纯通知不入 agent 队列 |
| **别的会话捎来一句**（含子 agent 派发回来的） | `SystemReminderMessage` | 同上——**能力尚无 topic**，本 topic 为它预留的是**去处，不是能力** |

> **日程来源的产品依据见 PF-021；跨会话消息来源的剩余缺口见 §9.1。**
> **列出来不等于它们已经存在**——[§9.1](#91-有几类来源的能力还没开题) 如实记着缺口的形状。
> **第四行的依据只到「有这一路」**：新会话怎么建，还等会话那一块给出定义。

**这张表落在 [PF-012 定的三种消息](../PF-012-agent-loop-and-run/design.md#511-外面进来的事怎么到-agent-眼前)上**，
**十行，三种消息**，一种新消息类型都没多——
**消息类型归 [PF-009](../PF-009-context-message-types/README.md)，本 topic 只说哪种来源落成哪一种。**

#### 同样要写「什么不会」

**只列上一张表，读者会以为剩下的都是漏掉的。**

| 不进队列 | 为什么 |
|---|---|
| **人答完了一批卡片**（含「[我不答这个](../PF-008-human-in-the-loop/design.md#65-不回答是合法答复)」） | 它的去处是**落到卡片上**。[答复只在卡片上做，消息永远是消息](../PF-008-human-in-the-loop/design.md#55-两条入口一件事) |
| **一条[控制指令](#控制指令)** | [它不是内容，不排队](#控制指令) |
| **用户敲的一个斜杠命令，绑定目标是系统业务流程** | 它**不是内容**：触发那条流程，会话日志里只留一条记它发生过的条目，[不成为消息](#510-斜杠命令在受理时分两路走) |
| **注入的上下文变了，而此刻没有运行在跑** | **什么都不用做**——[下一次组装自然就是新的](#610-注入的上下文变了没有运行在跑时什么都不做) |
| **一个依赖恢复了、一项权限变了** | [我们的模型里没有「等它」那个停住点](#看着像控制指令其实不是) |
| **换了一个模型** | [PF-013：一条会话事实，下一次请求时生效](../PF-013-model-profiles-and-invocation/design.md#59-换模型一条事实一个生效点零个新分支) |
| **系统为一次已经发生的中断追补的那条提醒**（比如用户取消之后，告诉 agent「刚才被叫停了」的那一条） | **它不是入站到达**——取消那条控制指令才是，这条提醒是系统处置它时自己落的。它照样落进日志、下一个运行照样读得到，[**但它自己不取得待处理资格**](../PF-012-agent-loop-and-run/design.md#run)：否则用户刚说「别做了」，那条替他转告的提醒就把 agent 重新叫了起来，**与他的意思正好相反** |
| **模型吐出来的话、loop 自己落的占位与终态** | **它们不从外面进来，不是入站到达。**[它们照样是日志里的条目](../PF-012-agent-loop-and-run/design.md#53-改日志的动作与纯派生的动作)，但那是 loop 自己的事 |

**最后一行要紧**：**队列里有模型吐的话吗？没有。**
[PF-012 的 T1 取的是「待处理的消息」](../PF-012-agent-loop-and-run/design.md#56-状态转移表)——
模型刚说完的那一句是**这一步的产物**，不是**下一步的输入**。

### 5.8 穷举二：什么会影响「退出循环的判断」

**这一节全部挂在 [PF-012 已经定死的两层出口](../PF-012-agent-loop-and-run/design.md#这个循环从哪里出去)上，不另起一套：**

| | 退出条件 | 出口几个 |
|---|---|---|
| **运行** | 落终态。**「完成」的判据是[队列空](../PF-012-agent-loop-and-run/design.md#待处理消息队列)** | **一个** |
| **一次[尝试](../PF-012-agent-loop-and-run/design.md#执行尝试)** | 落终态 · 停住等 · 被中断 | **三个** |

| 进来的是什么 | 动的是哪个判断 | 依据 |
|---|---|---|
| **任何一条进队列的消息** | **运行的出口**——**队列非空，「完成」这一格就不成立**（[T2′](../PF-012-agent-loop-and-run/design.md#56-状态转移表)） | **[§5.7](#57-穷举一什么会让队列从空变成非空) 那十行一视同仁**，不是只有用户消息才有这个效果 |
| **取消 · 强制停止** | **运行的出口**——落终态「被取消」 | [它不从日志尾巴推出来，所以它没有转移行](../PF-012-agent-loop-and-run/design.md#被取消不在这张表里因为它不是一行) |
| **[会话被归档](../PF-015-session-lifecycle-and-ownership/design.md#会话归档)** | **运行的出口**，级联终止 | **本 topic 只引用**——[待处理任务取消、历史保留](#92-会话被归档那一刻队列怎么办) |
| **人答完了一批卡片**（解除的是**运行**或**前台执行**那两种） | **一次尝试的出口**——「停住等」结束 | [PF-008 §5.3 定了解除的是谁的阻塞](../PF-008-human-in-the-loop/design.md#53-一批卡片与答完是什么意思)，[PF-012 T4 → T5](../PF-012-agent-loop-and-run/design.md#56-状态转移表) |
| **一批动作的结果齐了** | 同上 | [PF-012 T6 → T7](../PF-012-agent-loop-and-run/design.md#56-状态转移表) |
| **[插队](#插队)** | **一次尝试的出口**——中断 / 转后台 / 视为拒绝，让 loop 走到 T1。**运行不落终态** | [§5.4](#54-插队停在哪就怎么办) |
| **用户把一次前台工具执行切到后台，或中断它** | **一次尝试的出口**——那一条以占位算齐，可能凑齐了这一批 | [PF-006 §6.6 / §6.7](../PF-006-tools-and-skills/design.md#66-前台后台-与-等待态是两个维度) + [PF-012 T7](../PF-012-agent-loop-and-run/design.md#56-状态转移表) |
| **用户单独中断一次模型调用** | **运行的出口可能因此成立**——被中断的回复[不交出动作](#54-插队停在哪就怎么办)，那条中断提醒[不让队列非空](#57-穷举一什么会让队列从空变成非空)；队列里没有别的，就是「完成」（[T2′](../PF-012-agent-loop-and-run/design.md#56-状态转移表)），有就回 T1 | [PF-013 §5.13](../PF-013-model-profiles-and-invocation/design.md#513-模型请求的运行时可以被单独控制而它停了看首-token) + [§5.5](#55-控制指令家族) |
| **人答完了一批属于后台执行的卡片** | **都不动**——[那次执行继续，而运行本来就没停](../PF-008-human-in-the-loop/design.md#53-一批卡片与答完是什么意思) | PF-008 §5.3 |

> **第一行与第六行的差别，是本 topic 最要紧的一句话。**
> **一条普通的用户消息进队列，只是让「完成」那一格不成立**——
> loop 走到 T1 时自然会取到它，**但它不会把 loop 从半路拽过来**。
> **插队才会。**[它插的是时间，不是位置](#插队)。

#### 有一条边界必须写明，否则本 topic 会越界

**[PF-012 已经把话说死了](../PF-012-agent-loop-and-run/design.md#方程不保证这个循环会停)：**

> **一个不打转、一直在干新活的 agent，系统不会自己停它。**
> 「转到什么程度算不值得」是**价值判断，不是状态事实**——留给用户挂拓展件。

**所以「预算烧光了」「转了太多轮」不是本 topic 的事。**
它们不从外面进来，不是入站到达，**不在上面那两张表里的任何一行**。

### 5.9 一个运行内部会多次取队列

[PF-012 的 T1 每次都要看队列](../PF-012-agent-loop-and-run/design.md#56-状态转移表)，
而 T7「动作结果齐了」要回 T1、[模型没给动作而队列非空也要回 T1](../PF-012-agent-loop-and-run/design.md#56-状态转移表)。
**所以取队列的那一点，在一次运行里出现很多次。**

> **legacy 那条「一个运行恰有一个启动依据」只管启动，管不了运行中的追加。**
> **本 topic 明确不沿用它**：一个运行可以消费很多条，**而它们不必来自同一个来源**。

**取队列的时候不按来源挑**，[一次取走此刻队列里的全部](#69-取批一次取走此刻队列里的全部)。

**「只取用户消息那一批」那种写法挡的是「一件不相干的事掺进来，账就混了」**，
而它有一个前提：**运行等于「一件要做的事」**。
[那个前提不成立](../PF-012-agent-loop-and-run/design.md#run)——
运行的边界是**一段连续的循环**：一次运行里，用户可能连说三句、
两个后台结果可能先后回来，**这些本来就在同一段协作里**。

> **而[「这次失败的任务花了多少钱」那句检验](../PF-012-agent-loop-and-run/design.md#run-是三样东西的归属单位)照样答得上**：
> 它问的是**这一段连续工作**的账，**而那正是运行的边界**。
> **那条规则想保护的东西一样没丢**，省掉的是**逐项按来源判断**。

### 5.10 斜杠命令在受理时分两路走

[斜杠命令](../PF-002-assets-settings-and-permissions/design.md#slash-command)的绑定目标恰有三种：
**① 一段自定义提示词、② 装配里的一个 skill、③ 一条系统业务流程**——是什么、谁能用、名字怎么不撞，归 PF-002。
**本节只定受理时它们怎么走：① ② 是内容，③ 不是。**

**谁识别、识别什么：**

| | |
|---|---|
| **只有交付面识别** | 只有经[交付面](../../ubiquitous_language/terms/interaction-and-dispatch.md#ul-delivery-surface--交付面--delivery-surface)送进来的输入，才会被认成斜杠命令——人读、机读两种[呈现形式](../../ubiquitous_language/terms/interaction-and-dispatch.md#ul-presentation-form--呈现形式--presentation-form)一样。**连接件、定时到点、别的会话捎话这些不经交付面的来源送来的 `/xxx` 原样当内容**，照一句普通的话受理 |
| **只认输入开头的一条** | 命令只能出现在输入的开头，**一条输入至多一条命令**；中间出现的 `/xxx` 是正文的一部分 |
| **只认这个会话认得的名字** | 名字按这个会话的[会话斜杠命令集](../../ubiquitous_language/terms/capabilities-and-composition.md#ul-session-slash-command-set--会话斜杠命令集--session-slash-command-set)认——[它什么时候定、什么时候换](../PF-002-assets-settings-and-permissions/design.md#会话认得哪些命令什么时候变)归 PF-002。**不在里面的名字，包括他没有权限用的，交付面当场明说「没有这个命令」、不发送**；带参数声明的命令，**参数解析不通过同样当场明说、不发送**（[PF-016 §5.7](../PF-016-cli-tui-delivery-surface/design.md#57-人要做的事分三族)）。这两种**不成为入站到达**，受理面见不到它们 |
| **受理时以此刻为准** | 交付面发出之后、受理之前，命令集若恰好换了（一次重新装配，或那个人的权限被收回），**按受理那一刻的命令集认**：名字已经不在的，与不存在的名字同样回答——**明说「没有这个命令」，不进队列、不触发任何流程，也不当成一句普通的话**。它已经到了受理面，所以照 [§6.1](#61-先落账再谈别的) 落一条**具名拒绝**，效力是留痕 |

**认出来之后，按绑定目标分两路：**

| 绑定目标 | 去处 | 受理时做什么 | 会话日志里留什么 | agent 看不看得到 |
|---|---|---|---|---|
| **① 提示词 · ② skill** | **进队列** | **在受理时展开**：① 把命令自带的提示词正文（带上参数）作为这条消息的内容；② 把那个 skill 的正文**逐字**作为这条消息里的一个内容块，人附带的参数**另成一个内容块** | **原命令与展开后的全文都留**：审计要看人敲的是什么，模型要看展开的是什么 | **看得到展开后的**那条 `UserMessage` |
| **③ 系统业务流程** | **就地处置**——不进队列 | **触发那条流程** | **一条记它发生过的[记录条目](../PF-000-occurrences-and-record-entries/design.md#记录条目)**：命令名、参数、结果摘要；效力是[留痕](../PF-000-occurrences-and-record-entries/design.md#条目效力--entry-standing)——丢了下一步照常，只是说不清发生过什么 | **看不到**——它不成为消息 |

**展开发生在受理时，所以[「消息落盘之前」](#56-消息落盘之前那一刻看得到什么)看到的是展开后的那条消息，外加原命令的标注。**
挂在那里的拓展件照常工作：脱敏改的是展开后的内容，否决拦下的是整条——原命令与展开结果一起不落盘。

**③ 为什么落在「就地处置」却不是[控制指令](#控制指令)**：问[那两个问题](#三个去处)，它不是内容，所以落在处置那一侧；
但控制指令处置的是**正在发生的事或队列本身**，③ 处置的是**交给一条系统流程去办的一件事**——
压缩这个会话的上下文、列出后台在跑的执行、展示会话的待办。它**不在[控制指令家族](#55-控制指令家族)里**，那张表的完备性判据不因它改变。
③ 那条流程**会不会动到会话日志、会不会影响运行的出口**，归定义那条流程的那一侧。
**本版点名的是 PF-002 的 [reload 一族](../PF-002-assets-settings-and-permissions/design.md#会话认得哪些命令什么时候变)**，各自刷新对应资产注册表，不等于一律完整重新装配。工作区来源先校验候选，失败明确报告且原内存数据未替换，通过后才按 PF-004 的构成生命周期切换；显式 reload 需要替换已捕获构成时，按 PF-012 安全交接，保留当前 Run 并开启新尝试，不原地改写旧清单和调用输入。命令执行摘要属于留痕；重装配的实际生效结果及当前构成会影响恢复，须沿 PF-012／PF-015 留存，不能只当成可丢的命令摘要。**命令受理本身不进队列、不改变「完成」判据**；各类重载的切换时机及必需绑定处置沿 PF-004，不在这里统一规定即时替换或下一 run 生效。其余流程本版不枚举。

## 六、产品规则

### 6.1 先落账，再谈别的

**每一条被受理的入站到达，先落进[会话日志](../PF-012-agent-loop-and-run/design.md#会话日志)，再谈它的[去处](#三个去处)。**

这不是本 topic 的偏好，是被方程逼出来的——
[PF-012 已经从写这一头论证过一遍](../PF-012-agent-loop-and-run/design.md#它们必须先落进日志这是被方程逼出来的)，
[PF-010 从读那一头论证过另一遍](../PF-010-context-management-and-assembly/design.md#要求四先落盘再组装)。
**攒在内存队列里的东西，一次重启就凭空消失，而没人知道少了什么。**

**这条还有第二层份量**：
[队列本身就是日志的投影](../PF-012-agent-loop-and-run/design.md#待处理消息队列)——
**不落盘就不在队列里，不在队列里就没有人会来看它。**
「先落账」不再只是留痕的要求，**它是那条消息被处理的前提**。普通消息内容或可恢复引用、来源、租户与会话归属、同次提交标识、待处理资格须完整持久保存；受理事实和待处理资格在同一次不可分割提交中成立。持久队列是日志投影，不能成为第二份权威。其他去处须保存各自目标和可恢复处置责任，不要求进入普通消息队列。拒绝／拦截留痕不使内容取得受理或排队资格。

> **落进日志 ≠ 进方程的定义域。**[效力那一套归 PF-000](../PF-000-occurrences-and-record-entries/design.md#条目效力--entry-standing)，
> 本 topic 不重定：一次被拦下的到达、一条具名拒绝，都是**留痕**。

### 6.2 送进来的就要被处理，要不要送进来归连接件

**一条经[连接件](../PF-002-assets-settings-and-permissions/design.md#connector)送达的外部消息，
受理之后就进队列，和用户自己说的那一句一视同仁。**

> **受理面不提供「收下但不处理」这种半吊子状态。**

**受理面没有「叫不叫醒」这项配置**——那种配置会长成这样：

| | 加了这项配置会怎样 | 实际怎么办 |
|---|---|---|
| 一条刷屏频道的消息 | 受理、落盘、**不进队列**——等下次有人说话时被看到 | **根本不该送进来。**过滤在连接件那一侧 |
| 那项配置在哪 | 受理面的一项设置 | **连接件自己的事**——它本来就是「agent 从哪里被触达」的那个资产 |

**两条理由：**

| 理由 | 说明 |
|---|---|
| **过滤要放在有知识的那一侧** | 「这条 Slack 消息该不该惊动 agent」，**连接件知道**（有没有 @ 我、是不是我关心的频道），受理面不知道。放在受理面，它只能按来源一刀切 |
| **「收下但不进队列」会多出一类语义** | [队列是日志的投影](../PF-012-agent-loop-and-run/design.md#待处理消息队列)。要有这一档，日志里就得多一个「这条不算待处理」的标记，**而整个模型的干净正来自「落进日志就是待处理」** |

> **这不是把问题推给别人。**它把问题**放回了本来就该回答它的那个地方**——
> 连接件那一侧如果做不出这个过滤，那是**那边的缺口**，
> 在受理面加一个一刀切的开关也补不上它。

**代价要写明**：**接一个吵闹的来源，如果连接件那边没配过滤，就会真的开始起运行、真的花钱。**
[排着的东西必须看得见](#64-排着的东西必须看得见)与成本可见性在这里同时兜底。

### 6.3 去重只认来源说得出的那个「同一件事」

**同一件事重复到达，只算一条。**

**这不是可选的优化**：外部来源几乎都会重投——重试、重连、重扫。
不去重的后果是**同一件事被做两遍**，而
[PF-012 为「重做」定过产品态度：那是崩溃恢复不得已的代价，要让 agent 知道](../PF-012-agent-loop-and-run/design.md#64-每一次尝试开始agent-都要知道)。
**重复到达造成的重做是可以避免的，所以必须避免。**

**但边界要划清：**

> **说不出「这是同一件事」的来源，系统不替它猜。**

**用户主动再次发送同一句话，作为不同提交收下**——不能按文本相同猜测重复。交付面为同一次提交保留稳定标识；回执丢失后的查询或自动重试沿用它，只返回原受理事实及当前处理状态，不新增消息、承接或 Run。此标识在租户、会话及来源范围内识别提交，不能用另一租户的标识取得或覆盖事实。改变内容后重新发送属于新的提交，不借原标识覆盖已受理内容。

提交标识须由发送方在首次提交前取得并保留，不能依赖可能丢失的受理回执才获得。未受理重试仍须通过当下资格与落盘前干预；查询已受理事实也受当前访问权限约束。具体标识格式、查询入口与重试策略归技术设计，不按内容哈希做全局去重。

连接件创建新会话的入口也受这条约束：同一事件向同一接收目的的重投不能变成两个会话或两份执行。是否允许多个明确接收目的属于路由产品规则，不能用去重替它做决定；创建与受理怎样共同保证不重归技术设计。

### 6.4 排着的东西必须看得见

**用户要看得出：他那一条还排着，没有被看到。**

**这条有先例**：[PF-008 §6.2 对等人的时候进来的消息配了一个弱提示](../PF-008-human-in-the-loop/design.md#62-等待期间照常收排队等着解除时一起看到)，
理由是「**挡住人说话，和提醒人还有事没做，是两件完全不同的事**」。**这里同构**：
排队不是拒绝，**但用户必须分得出「它排着」与「它已经被看过了」**。

**分不出的后果是连锁的**：他以为 agent 在无视他 → 他再发一遍 →
[而用户自己发的东西我们不去重](#63-去重只认来源说得出的那个同一件事) → **agent 真的收到两条**。

> **这条还要兜住另一件事**：
> [队列不设上限](#66-队列不设容量上限)，所以**排得太长这件事不会被系统拦下来**——
> **它只会被用户看见。**看不见，就没有任何机制会让人察觉不对劲。

**通知怎么送达归技术设计，但产品要求它必须存在。**

### 6.5 插队是原子的

**[插队做的三件事](#插队)要么一起成立，要么都不成立。**

> **它是一个命令，不是「先中断，再发一条消息」这个组合。**
> **中断是它的手段，不是它的语义。**

**不原子会漏出两种坏状态，各自都是用户看得见的：**

| 漏出什么 | 用户看到 |
|---|---|
| **中断了，但那句话没进队列** | agent 莫名其妙停了一下，**然后什么都没变**——loop 空转一圈又停回去 |
| **那句话进了队列，但没中断** | 他明明按了「现在就说」，**却还要等很久** |

**连续插队是幂等的**：第二条插进来时，若 loop 已经在走向 T1，**没有东西可中断了**——
此时它只是进队首。**再中断一次会违反[「最大程度保留」](#53-插队的核心原则)。**

### 6.6 队列不设容量上限

**[待处理消息队列](../PF-012-agent-loop-and-run/design.md#待处理消息队列)本版不设容量上限，
不因为「满了」而拒绝任何一条已经受理的入站到达。**

**「外部来源有界、内部事实不适用满时拒绝」那套双档规则是过度设计**，
产品负责人 2026-09-20 裁决：

> **现在我们完全可以运行无限容量的队列（以后真出问题了再针对性做产品设计）。**

**这条裁决之所以成立，是因为「满了怎么办」在本版没有一个非答不可的场景：**

| 本来担心什么 | 现在靠什么兜住 |
|---|---|
| 一个吵闹的外部来源灌爆队列 | [过滤在连接件那一侧](#62-送进来的就要被处理要不要送进来归连接件)，**灌不进来** |
| 用户疯狂敲消息 | 那是他的意思，[本来就不去重](#63-去重只认来源说得出的那个同一件事) |
| 内部事实（工具结果、后台回传）堆积 | 它们的量**由别处的界承担**——已经发出去的调用有多少，本来就有上限 |

> **但有一条不因为「不设上限」而消失**：
> **一条被受理的入站到达，无论如何不许静默丢弃**（[§6.7](#67-不漏不重)）。
> 将来真要加界，加的是「**具名拒绝**」——说清是哪一条、为什么，且发的人看得到；
> **绝不是悄悄扔掉。**

### 6.7 不漏、不重

> **一条被受理的入站到达，要么有人会来看它，要么它把人叫来。**
> **而且只叫一次。**

**它不靠受理面逐条判断处境来兑现，靠的是一条更硬的性质：**

| | 怎么兑现 |
|---|---|
| **不漏** | [落进日志就是进队列](../PF-012-agent-loop-and-run/design.md#待处理消息队列)，而**队列非空 loop 就不会收束**。所以「有人来看」不是一条要被实现的规则，**是模型的推论** |
| **不重** | 一条消息**被取走一次之后就不在队列里了**——「取到哪了」[从日志派生，不另立权威](../PF-012-agent-loop-and-run/design.md#67-检测状态从日志派生不另存)，**不另立两套可独立推进的权威事实** |

**最容易破这条的那个时刻因此不存在**：
「一条到达正在定落点，而那个运行恰好在这一刻结束」——
**受理面根本不看有没有运行在跑**（[§5.2](#52-三个去处为什么是穷尽的)）。

**剩下真正要靠实现保证的只有一条**：

> **落进日志这个动作本身，不许半途而废。**
> 落了一半的到达，既不在日志里、也不在外面等着，**那才是真的漏**。

**产品要求的是结果，不是办法。**怎么保证归技术设计；
**产品只要求这两种坏结局都不许发生，并且它们各自是可观察的。**

### 6.8 停机不会让一条入站到达永远悬着

**普通消息的受理成功，就是受理事实和待处理资格完整持久提交成功。**提交前没有系统已受理事实；提交后系统承担恢复及推进责任，不以发送方在线或再次查看为前提。发送成功提示不得早于该边界。

| 实际事实 | 谁保留输入并负责下一步 | 发送方可据什么判断 |
|---|---|---|
| 尚未持久提交，或提交明确未生效 | 发送方保留同次提交标识及输入，故障解除后查询／自动重试；系统不能凭没有保存过的内容恢复 | 明确未受理；资格不足或被否决须按相应原因处理，不保证原输入重试后一定通过 |
| 已完整持久提交，尚未承接 | 系统保留并恢复待处理消息，自动推进；发送方不必再次提交 | 已受理、仍待处理 |
| 已承接 | 系统按原 Run 与承接事实接续，不重新排队给另一个 Run | 已承接，不等于 Run 已完成 |
| 回执丢失、超时或连接断开，发送方尚未查明 | 实际责任仍由提交事实决定；发送方保留原输入，按同次提交查询／重试以查明 | 结果未知，不能直接报告未受理或要求人重新输入 |

**未受理是“没有已受理的持久事实”，不是“系统已收下但还没处理”。**拒绝、拦截与尚未提交都未形成受理事实；拒绝留痕、内存中收到数据、发送按钮已按下，不是受理成功。发送方不知道结果，是认知不确定，不能当作系统事实。

同次提交重复到达沿 [§6.3](#63-去重只认来源说得出的那个同一件事)。恢复不得为已受理消息重走落盘前干预、重复落盘或另作一次受理。普通消息的入站事实与排队资格没有跨停机的半完成状态；投影滞后须恢复一致，不能让消息消失或重复承接。

**卡片答复与控制指令仍属于入站到达，但受理并非进入普通消息队列。**它们须持久保存目标、答复／意图及可恢复处置责任。受理回执与实际答复生效、命令生效分别判断；提交后的恢复按原目标推进或明确关掉并留痕，不重复创造外部效果。它们的具体完成及重复处置规则沿各自产品，不以普通消息的队列状态代替。

**空闲会话即使没有 Run 或 Agent runtime，已受理的待处理消息也必须被自动拉起处理。**队列非空且没有活跃运行的状态不许长期存在；具体调度和故障恢复机制归技术设计，不要求有人查看会话才推进。归档拒收与明确取消待处理资格沿 §9.2。

### 6.9 取批：一次取走此刻队列里的全部

**[PF-012 T1 的「取一批」，取的是此刻队列里的全部，不按来源挑。**](../PF-012-agent-loop-and-run/design.md#56-状态转移表)

| 为什么不挑 | 说明 |
|---|---|
| **挑就要有判据，而判据要逐来源维护** | 唯一像样的判据是「是不是对正在做的这件事的追加」，而它**要求受理面替用户判断两件事相不相干**——那正是 agent 该做的判断，不是队列该做的 |
| **用户连说三句是一件事的三个片段** | 拆开取，**前两句各被答一次**，而他要的是第三句说完之后的那个回答。**legacy 与 Claude Code、Codex 都是一起取**（[裁决 4](design.md)） |
| **不挑就没有「挑剩下的那些什么时候轮到」这个问题** | 挑了就有。而那个问题一旦存在，**就要再定一套「什么时候回头取」的规则** |

**“取走”以 PF-012 的持久承接事实为准**，不是读取、收到通知或开始调用模型。承接与退出待处理投影可恢复一致；原消息和承接历史不删除。普通消息在交给 Run 后不再排队，但 Run 的工作还可继续，失败和取消按 Run 规则处理。共同的保管、交接与清除范围沿 [PF-015 §6.26](../PF-015-session-lifecycle-and-ownership/design.md#626-待消费数据先持久保管再交接)。

**开一个新运行的前提**：**这个会话此刻[没有活跃的运行](../../ubiquitous_language/terms/agent-runtime-loop.md#ul-single-active-execution--会话内单活跃--single-active-execution)。**
有，就由那个运行在下一个 T1 取走——[那条约束是治理约束，不是性能约束](../../ubiquitous_language/terms/agent-runtime-loop.md#ul-single-active-execution--会话内单活跃--single-active-execution)。

### 6.10 注入的上下文变了，没有运行在跑时什么都不做

**组织的设置改了、账号的偏好改了、[runtime context](../PF-015-session-lifecycle-and-ownership/design.md#runtime-context) 的某一块被它的生产方改了——**

**会话感知这类变更有两条路，缺一条都不成立：**

| 路 | 谁发起 | 什么时候 |
|---|---|---|
| **推** | **那一块的生产者** | 它那一块变了的时候 |
| **拉** | [agent runtime](../PF-012-agent-loop-and-run/design.md#agent-runtime) 自己 | **每一次[执行尝试](../PF-012-agent-loop-and-run/design.md#执行尝试)成功起来时，取一次当前快照**（[那是 §5.7 四件事里的一件](../PF-012-agent-loop-and-run/design.md#每一次尝试开始都要做四件事)） |

**推来的那一路，按此刻[运行](../PF-012-agent-loop-and-run/design.md#run)闭没闭合分两种：**

| 此刻 | 怎么办 |
|---|---|
| **有运行在跑**（Run 未闭合，**含停着等人**） | 落一条 `SystemReminderMessage` 进队列，**说状态的，写清「从什么变成了什么」**（[PF-009](../PF-009-context-message-types/design.md#64-说状态的写清变化说事的写清发生消息一律追加)）。**agent 脚下的地变了，它必须知道** |
| **没有运行在跑**（Run 已闭合，会话空闲） | **一律丢弃**：**不进队列、不落日志、不成为[记录条目](../PF-000-occurrences-and-record-entries/design.md#记录条目)** |

> **⚠️ 这一条只管 runtime context 生产方推来的变更。**
> **后台执行完成回传、用户又说了一句、外面送进来的消息、到点了——不在此列**：
> 会话未归档时，它们[照本 topic 受理](#61-先落账再谈别的)，可入队并触发下一次运行。归档时按 §9.2 区分拒收新任务与保存迟到执行事实，后者不取得待处理资格，也不在撤销归档后自动入队。
> **判据是这两类东西答的不是同一个问题**：前者说「**现在什么样**」，**重算即得**；
> 后者说「**发生了一件事**」，**丢了就真没了**。

**「丢弃」不会让 agent 拿着过时的值干活**：
下一次尝试起来时它**自己拉一次**，拿到的就是当前那一份；
那条状态提醒的**前值取[会话日志](../PF-012-agent-loop-and-run/design.md#会话日志)里最后感知到的那一份，现值取这一次拉到的**。

> **因果链记的是这个会话感知到的变化，不是世界上发生过的每一步。**
> 空闲期间那一块改过三次还是三十次，**会话只感知到一次**——
> 从它上次看见的那个值，到现在这个值。**那三十次里没有任何一次有 agent 在场。**

**这不是[「先落账再谈别的」](#61-先落账再谈别的)的例外，而是它的边界**：

> **被丢弃的那一推，从来没有成为一条[入站到达](#入站到达)。**
> 受理面收的是「**发生了一件事**」；**一块 runtime context 现在是什么值，不是一件到达的事**——
> 它[按 PF-000 的两条判据都不必留](../PF-000-occurrences-and-record-entries/design.md#52-那个判断两条独立充分条件)：
> 丢了**下一步照样算得出**（下次拉一次就有），**也没有需要向谁解释的发生过程**——那段时间没有 agent 在场。

> **不写这一条会怎样**：组织超管改一次设置，**所有空闲会话各醒一次、各调一次模型**，
> 而每一次 agent 都会发现自己无事可做。**那是一笔纯粹由设置变更产生的账。**

**这一条也是「[三个去处由它是什么决定](#52-三个去处为什么是穷尽的)」那句话的唯一一处例外，
所以要说清它为什么不算破例**：

> **这里判断的不是「去处」，是「要不要产生这条到达」。**
> 产生了，它的去处照样是进队列，**一点例外都没有**。

## 七、取舍

| 选了什么 | 得到 | 付出 |
|---|---|---|
| **受理面统一，去处分叉**（legacy 把控制排在外面） | 去重、留痕、租户隔离、拓展点**只需要在一个地方成立** | 「就地处置」这一支与另两支的形状很不一样，**读者要接受一张不对称的表** |
| **落进日志是共同动作，不是一种去处** | 「东西会不会凭空消失」**不再是一个需要逐来源回答的问题** | 日志更长 |
| **斜杠命令在受理时展开**（不是等组装时再展开） | 日志里就是模型看到的那一份；[组装仍是纯派生](../PF-010-context-management-and-assembly/design.md#要求四先落盘再组装)——skill 正文后来改了，**重放出来的还是当时那一份**；「消息落盘之前」的拓展件拦得到、改得到 | 展开后的全文与原命令都要存，日志更长 |
| **只有交付面识别斜杠命令** | 外部来源送来的文字**不能替人触发系统流程**；人敲与脚本驱动交付面，**留下的记录条目仍是同一串** | 同一串 `/xxx` 从两个入口进来后果不同，**这正是要的** |
| **没有「只记一笔」那一档** | 受理面**不必知道此刻有没有运行在跑**；[最难兑现的那个时刻因此不存在](#67-不漏不重) | **任何一条进队列的消息都会让「完成」不成立**，包括那些本来无所谓早晚的 |
| **插队不终止运行**（legacy 是打断然后起一个新的） | 用户插一句话**不会杀掉自己跑了两小时的任务** | 插队与取消长得像而语义相反，**产品必须把这个差别做到界面上** |
| **`insert_user_message` 是原子命令，不是复合命令** | 两种坏中间状态**根本不可能出现** | 它做了三件事，**读者得一次记住三件** |
| **排队是默认，插队要用户明确发命令** | 默认不打断正在干的活；**要打断就得说出来** | 用户想打断时**要多做一个动作** |
| **「最大程度保留」立成原则，规则从它推** | 四种情形各该怎么办**读者自己能推出来**，不必背 | 原则比条款抽象，**边角情形要回头对着它判一次** |
| **两种「等人答」语义统一、机制不合并** | 产品上只有一条要记的话：**人的处理有两种** | 机制上仍是两条路，**实现要各做一遍** |
| **取消一个等待一律视作拒绝，绝不视作批准** | **不可逆的外部效果永远不会因为一次取消而发生** | 用户偶尔要**再说一遍「批准」**，agent 重做一次 |
| **过滤归连接件，受理面不提供「收下但不处理」** | 模型干净：**落进日志就是待处理**；过滤放在**有知识的那一侧** | **连接件那一侧没配过滤，就会真的开始烧钱**——而那个缺口在本 topic 补不上 |
| **队列不设容量上限**（产品负责人裁决） | 不必回答「满了算谁的」「合并还是拒绝」这一整串问题 | **排得太长不会被系统拦住**，只会被用户看见 |
| **一次取走队列里的全部，不按来源挑** | 不必维护「哪些算追加」的判据，**也没有「挑剩的什么时候轮到」这个问题** | 一条新输入**会掺进正在跑的那个运行**——而[运行本来就不等于「一件事」](#59-一个运行内部会多次取队列) |
| **用户自己发的东西不去重** | 不会吞掉用户的话 | 他手抖发两遍，**agent 真的会看到两条** |
| **没有「撤回一个排队项」** | 队列这个概念**不必为它加一层间接** | 用户改口只能**再说一句**，而前一句 agent 照样看得到 |
| **穷举来源并指明其产品拥有者或缺口** | 缺口的形状**看得见** | 读者可能把它们当成已有能力，**所以每一处都标了** |

### 9.1 有几类来源的能力还没开题

[§5.7 的穷举](#57-穷举一什么会让队列从空变成非空)中，跨会话消息与子 agent 派发的完整来源能力仍未由独立 topic 定义：

| 这一类来源 | 现在有什么 | 缺什么 |
|---|---|---|
| **别的会话捎来一句**（含子 agent 派发） | 词表里有 [agent 派发](../../ubiquitous_language/terms/interaction-and-dispatch.md#ul-agent-dispatch--agent-派发--agent-dispatch)与 [agent 间通信](../../ubiquitous_language/terms/interaction-and-dispatch.md#ul-inter-agent-communication--agent-间通信--inter-agent-communication) | **跨会话的消息怎么被授权、怎么投递、目标不存在怎么办**——没有 topic |

> **本 topic 为它们留的是去处，不是能力。**
> 去处这一层不必等它们：**它们真出现的那天，问[那两个问题](#三个去处)就知道落在哪。**
> **反过来，不要因为这里列了它们，就当成我们已经实现这些来源能力。**

### 9.2 会话被归档那一刻，队列怎么办

沿 [PF-015 §6.3](../PF-015-session-lifecycle-and-ownership/design.md#63-归档先停活儿再落状态)：尚未承接的任务取消待处理资格，保留原消息与取消原因；队列投影从已受理输入中排除已承接及已取消的任务，不通过删消息或伪造承接来清空队列。撤销归档不重新排入这些任务。

已归档会话拒绝新的任务输入，发送方得到明确拒绝；不排队、不自动恢复会话。归档前已发起执行的迟到结果和账目仍落原归属，不属于新任务、不取得待处理资格，也不在撤销归档后自动入队。归档与输入同时发生时，任务或者先被受理后因归档取消，或者被明确拒绝，不能有无记录的丢失或归档后仍等待执行的第三种结果；具体实现归技术设计。
