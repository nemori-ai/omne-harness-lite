# 会话组成、动态装配与持久化

本页保存产品负责人原话及推导边界；规则归本包正文与 PF-004、PF-012。

## INT-001

用户要求区分会话组成部件的创建必需／可选输入、运行期固定／可变。随后明确：

> 会话自身的执行类型对应的必需能力身份运行时不可变；三种模式在会话创建时的默认值依据租户的设置来得出，会话后变更产生的影响限制在该会话内

并要求明确其他部件变更作用于会话还是租户，保存事件、日志之外的投影和会话级使用值，以便直接取得当前结果。

## INT-002

对 AgentDefinition 的最终澄清，取代交流中一度把整个定义版本固定的解释：

> 我们约定：AgentDefinition 身份在运行时不可变，但同一身份的 AgentDefinition 内容变更是运行会话时重新获取使用最新的（也就是热重载同一个身份的 AgentDefinition）；其他几个比较重要的，模型、工具、技能、mcp、runtime contexts 在运行时都是可变，比如换一个模型、工具/技能/MCP 添加移除或者同一个身份但换实现，runtime contexts 除了你说的可变外，还可以比如多加一块 runtime context、移除一块本来注册在这个会话的 runtime context。同时对 session 需要持久化什么，还需要叠加考量对 agent runtime、model runtime、tool runtime 进行装配时候需要提供的输入

## INT-003

> 嗯，本质上持久化的目的就是，为了能够算出同样的结果，需要确定下来的函数输入说什么，一切从函数式的视角看就能统一起来了。产品设计这块，完整更新落盘好上面的讨论吧

## 推导与未扩大范围

- 固定会话执行类型与类型必需声明、允许创建时显式模式初值、默认初始化后不跟随租户漂移，是主会话建议并随本次整体落盘要求收录的产品表达；不是逐字原话。
- 新 Run 获取最新有效定义，同 Run 尝试仍用已采用版本，沿 PF-004 已有生效边界；用户没有要求在已发请求内混换版本。
- 共享修改按目标归属，覆盖组织、工作区、账号和外部对象，不能只分成会话与租户两格。
- 同输入同结果针对确定性求值；模型响应与外部效果记录真实结果，不由此推导安全自动重做。
- 三类 runtime 输入是产品需要能够取得的信息，不是函数签名、存储表或新生命周期机制；技术细节继续交技术设计。
