# Trigger 与会话推进：2026-10-06 交流

本页保存本会话来源和推导范围。现行规则由 PF-012、PF-014 拥有，准确术语由统一语言拥有。本页不选定调度器、事件 API 或存储机制。

## 用户输入与确认

用户在 P1.3 发现 C-52 后提出：

> 所以 trigger 就不是严格意义上我们标准的 run 的开始，而应该是「产生一次 attempt」的事件触发机制，对吧？

主会话说明，Trigger 可以促使系统检查和推进工作，但不能与产生一次 attempt 一一对应。已经有有效 Agent runtime 时，可继续同一 attempt；没有可推进工作时，也可不产生任何 Run 或 attempt。主会话据此提出“促使系统检查并推进一个会话工作的信号”的定义及四种分支。

用户随后确认并授权完整同步：

> 同意，更新完整来。另外就是 ，主分支前进了，对包构建提供了一套标准的模板并对大部分已经满足了 cordis 上层集成契约规范的现存包完成了规范化，你的 工作树 可以先同步好主分支的变更

本次确认采用上述推进信号含义及对应分支，并授权工作树同步。它不表示每个 Trigger 必须生成 attempt，也不接受任何尚未核定的技术 API、全部产品修订或实际故事卡交付。

## 已确认的分支

| 持久事实及当前条件 | 处理 |
|---|---|
| 没有未终结 Run，且有具备待处理资格的未承接输入 | 创建 Run 和首个 attempt |
| 已有未终结 Run，没有有效 Agent runtime，且满足合法推进条件 | 在原 Run 创建新 attempt；仍未满足等待条件时保持等待 |
| 已有未终结 Run 及有效 Agent runtime | 通知原执行者，或继续／恢复同一 attempt；普通追加不打断在途调用 |
| 检查后没有可推进工作 | 不因此创建 Run 或 attempt |

## 必要推导及取代范围

输入已承接时可退出待处理队列，而原 Run 仍未终结。因此队列从空变非空并不证明应新建 Run。恢复时队列已非空，也仍需推进，不能等待新的队列边沿。这两项是 C-52 的反例。

Trigger 是通知作用，不能取代业务事实或授予推进权。信号可重复、合并或由持久事实重建。受理完成不等待通知送达；已受理输入、原等待结果和未完成责任不能因通知丢失永久悬空。这由持久受理、恢复推进及不漏不重要求共同推出，不规定具体调度算法或时限。

已有执行者遇到普通追加时，可以只记录并排队，待下一合法 T1 承接。等待满足时，有效原执行者继续同一 attempt；执行者已交还时才按原 Run 的条件创建新 attempt。重复信号不等于重复提交或重复调用，不额外承接、创建卡片或产生外部效果。

统一语言的形态仍为“属性”：Trigger 表达输入到达、原等待满足或恢复检查等事件在会话推进中扮演的通知角色。它不是本次新设的独立身份对象。具体通知载体及诊断标识由技术设计决定，不因此新增领域对象或强制一张持久信号表。

本次取代 UL-trigger 及 PF-012／PF-014 中“Trigger 等于 Run 起点／队列空转非空”的现行定义。保留历史决定和冻结技术来源的原文；P3 核对消费者，P4 闭合共同提交与恢复，P5 核对装配。PF-015 的持久保管与原归属要求保持，模型 ACK 清理及工具结果保留继续归原能力。

## 表达复核

产品复核指出，“信号重复／过时”与“没有可推进工作”不能并列作为不创建执行的充分条件。首次通知处理前停机，恢复收到同一通知时，输入仍需推进。因此四分支以当前事实为判断依据：重复／过时信号不提供新增工作依据，但仍允许检查并推进尚未完成的持久工作；只有检查后没有可推进工作才不创建执行。这是已确认方向的必要表达修正，不新增产品政策。
