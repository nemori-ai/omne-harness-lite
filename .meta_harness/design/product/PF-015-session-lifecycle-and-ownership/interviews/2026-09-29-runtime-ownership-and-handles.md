# 三类 runtime 的归属与句柄

## INT-001

产品负责人：

> 接下来我们要重新设计三个runtime之间的关系，明确它们所绑定的归属。具体来说，我们应该要求 tool runtime 和 model runtime 所绑定的归属都是 session （或者 session 的 run 逻辑治理对象），而非 agent runtime

## INT-002

> 那么 agent runtime，实质上只是在它存活期间，持有 model runtime 和 tool runtime 的句柄，但它如果被销毁了，句柄释放，并不影响 model runtime 和 tool runtime 本身的运行和存活

## INT-003

> 那么产品设计上，最新的这个设计冲突的地方，调整 表述，并确保最新的这个设计完整落盘

## INT-004

随后要求技术评价：

> 因此进一步地，在一个 agent loop（也就是 agent runtime）中发起一次模型请求或者一次工具调用的执行，本质上只是 agent loop 对 run 做相关动作的一次代理行为，这点从技术角度评价一下表述是否正确

## 主会话解释与推导边界

- 采用 Session 作为三类 runtime 生命周期归属，Run 作为工作治理、归因与结果承接单位；已有 Run 外调用仍直接归会话。这使两种已有归属可以同时成立。
- Agent Loop 指规则，Agent runtime 指运行实例；“代表 Run 发起”说明职责，不规定 Proxy 模式、线程模型或把 Run 本身做成 runtime。
- 零句柄仍存活，结果必须在无人等待时保存，恢复须区分仍在途／已完成／自身失联；这些是“销毁等待者不影响执行”的直接后果。
- 保留既有业务取消范围、后台工具、首 token 分界和终态规则；区分显式取消与释放句柄，不把独立寿命解释成永远不能取消。
- 持久执行身份、归属和输入依据须足以重新取得结果；具体存储、提交、连接、进程部署与句柄 API 留给技术设计。本轮不改冻结规格或接受记录。
