### 2026-09-21 · 生命周期、会话类型与业务流程拓展点

**产品负责人原话（第一段）：**

> 然后是关于会话的生命周期，这个我想捎带着会话上下文感知域一起说明，同时再引入两个产品设计。
> 先说会话生命周期：这个其实前面覆盖过了，当然这里可能对一些特定的定义还是要有调整，
> 具体来说，会话分成这几个生命周期：创建/初始化 - 运行/活跃（sessionn log 层面根据最新的 run
> 是否完结判定） - 休眠 - 归档，其中 运行 - 休眠 是持续切换的，归档状态可被撤销。
> 然后是引入的两个产品设计：1）会话类型，也就是这个会话的主要目的是什么，产品上，
> 可以通过用户选择的 AgentDefinition 来确定创建的会话类型，目前暂定（不限定死，未来可拓展）
> general-purpose, coding, office, research, personal-life 这五类；2）会话话题监测与适用性提示：
> 算法上提供（利用 loop 拓展点）对用户的话题与当前会话类型的适配性的探测机制，
> 如果发现比如用户在 coding 会话里面聊个人生活，就应该提示用户（此时消息暂不进消息队列）
> 并且让用户确认是否还是要在当前会话里面聊（因为用户可能只是临时提一个分岔的小话题，
> 不想开新会话，聊完啦就继续回正轨了），用户确认后才真进消息队列（交互界面上看就是发送成功）
> —— 但这其实就引入了一个特殊的拓展点——对一类请求在未落盘（持久化）前进行处理，
> 而不是在持久化后才处理。先到这，上下文感知域后面再展开。

**产品负责人原话（第二段，回答 PM 的几个问题）：**

> PF-007 规则二调整为 会话仍未被归档。归档可撤销对授权这块，要分着看：
> 1）授权是分级的，组织-租户-会话（该授权仅当前这个会话生效）；
> 2）组织 - 租户 的授权和会话的生命周期无关且是完全可以随时变更；
> 3）用户在一个会话内（agent 通过使用 Ask() 请求的）提供的语义授权，也是一种上下文感知域
> （langchain 的角度理解就是 runtime.state），是一种数据，会话归档不会丢；
> 4）我们的系统里面，最终对一个会话内的agent的授权是实时算的，比如工具使用授权，
> 在模型响应后的拓展点算。至于其他的比如工作取消（会话被归档，子会话同样级联被归档、
> 未完成的工具执行被中断、模型响应被中断）明确写明是不可逆不可恢复的。
> 关于会话类型你的几个问题：1）已存在的会话类型不跟着变，AgentDefinition里的 agent type/category
> 和 会话的类型，之间的映射关系是算出来的，不是绑定的。2）租户可自定义的 agent 资产，
> 这里我们进一步明确，是 subagent（这也是前面为什么我说 agent type/category 的原因，
> 可能 agent type 要留给 master agent - subagent 这样的区分来使用），而目前说的这五类都是 master type；
> 然后关于谁能拓展——只能出厂加（因为关键是用来限定 master agent 的 category，
> 而如果租户只能自定义 sub agent，就意味着 master agent 只能是产品 officially 提供的）。
> 话题监测拦截引出的一类拓展点：我们现有的实质上都是 loop extension points，
> 而话题拦截我们应该引出另一类 业务流程拓展点，它们不产生持久化的影响（对 session log），
> 而是产生业务流程的增量价值。「它是纯前端的，还是系统要临时持有它？如果系统持有，
> 用户一直不确认会怎样」：系统不需要持有，因为有 业务流程拓展点，你能理解吗，
> 就是正常流程推进，到了这个拓展点，被拦截的话，前端请求自然得到反馈

### 2026-09-21 · 授权的来源、撤回与作用域

**产品负责人原话（第三段）：**

> 「一笔已经给出去的会话级授权，现在要怎么收回？」：授权有两种，结构化授权和语义化授权，
> 前者你就直接理解是用户界面上有可操作的页面对特定授权条目 revoke，后者就是用户用嘴说提供授权，
> 当然也可以用嘴说撤回授权，然后这些信息按照来的先后顺序进一个会话级别的 上下文感知域
> （类似 langchain 的 runtime.state），再在后面通过一个拓展点实时计算
> （怎么算你别管，反正能算，产品提出来的要求就是系统要能够算得出来）

**产品负责人原话（第四段）：**

> 自由作答算数，甚至用户主动给授权（agent 没 Ask()）的也算，而且这里甚至还能区分是
> 单次执行的授权（用户这句话发出去后 agent 下一次的 tool calls 的执行授权）、本会话授权、
> 全局授权（租户下未来所有会话），就是产品上要有这样的能力，但是怎么做到的，不需要产品关心。

### 2026-09-21 · runtime context 与十五项 meta runtime context

**产品负责人原话（一，粗定义）：**

> 会话上下文感知域，指的是一块一块的，在会话推进中，llm、tool 和 拓展点 进行工作时需要感知到的
> messages（session log 中那些 llm 也就是 agent 能看到的）之外的上下文。为什么这里有 tool 和
> 拓展点 的事呢。你如果结合 langchain 的 runtime.state 在 tool 和 middleware 中的使用，就好理解了。
> 而这些上下文感知域，本质上也是一份份的数据，但和 session log 是 append only 的不同，
> 它们是一个个数据模型（通俗易懂理解就是一张张表单），在上下文中 in-place 地被更新
> （所以才会有当变更发生时需要追加 SystemReminderMessage 让 agent 可感知，当然这是特指 llm
> 需要感知的那些上下文感知域发生变更的时候，tool 和 拓展点 需要的就不用发通知，
> 因为不是给 agent/llm 看的）

**原话（二，答 PM 三问）：**

> 「表单」不仅要有消费者，还要有生产者，在我们的产品里面，可以分成，这份表单的内容是由会话本身来维护，
> 和由会话外的一个什么东西（你先不要管具体是什么东西，不同表单都不一样）来维护。
> 然后是 llm 怎么看到：对于一份 表单，llm 看到的有两种形态，一种是完整的，比如会话刚开始、
> 上下文压缩后，一种是变更通知。对于你的第三个问题：广义上就是 runtime context。

**原话（三，纠正 PM 两处过度归纳）：**

> runtime context 是会话要用的，会话要维护的投影是会话提供给会话外的服务用的，两者会有重复的部分，
> 但不完全重叠。实时算的不进来这一点有点过度归纳了，判决是会话内的三种角色（模型、工具、拓展点）
> 消费不消费（依赖不依赖）。

> 你不要纠结实时算啊，归根结底是 runtime context 是明确在 agent-loop 内被三个角色之一消费的，
> 可用性没人消费（消费它的是 runtime 本身），能理解吗？

**原话（四，逐条给生产者、消费者与信息）**——十五项逐条内容见
[§5.6 那张表](design.md#56-十四项-meta-runtime-context)，**本页不复制**；
其中对 PM 提问的直接回答：

> 关于「单次授权」，你可以这么理解，就是授权相关的 runtime context，数据结构上，
> 应当能够表示出单次、会话内、全局（always on）的区别，那么对于单次的处理，agent-loop
> 就能够有专门的拓展点，一次 run 明确结束的时候，清空单次授权的。
> 「消费者不止三类」不就是三类，上下文压缩这个（都说了实时算了）你当我没说。……
> agent 身份标识恒等于会话身份标识——这条写进产品正文。

## 二、PM 推导

**以下结论由 PM 从已拍板内容推出，每条附推理链，可以被逐条核对与推翻。**

### 指向别的租户的工作区，会话建不起来，而不是那一级为空

**从哪几条推出**：[跨租户默认拒绝](../PF-001-identity-scope-and-agent-constraints/design.md#64-隔离)、
[会话持有创建那一刻的租户身份](design.md#612-会话持有创建那一刻的租户身份)、
产品负责人原话「当会话是这个租户的，系统在装配的时候……自动解析加载」。

**推理**：原话里「当会话是这个租户的」是加载的前提，反面只有两种收场——拒绝创建，或建起来但不加载。
后者让用户以为挂上了而其实是空的，**一个安静的空比一个明确的拒绝更危险**（他会在错误的配置下跑完一整段协作）；
而且「指定了一份自己无权的工作区」本来就是一次跨租户访问，[默认拒绝](../PF-001-identity-scope-and-agent-constraints/design.md#64-隔离)没有例外。
**只有拒绝创建成立。**落在 [§6.13](design.md#613-工作区在创建时显式指定不指定就是空)。

### 撤销归档之后落在休眠，不落在运行

**推理**：状态判定规则是裁决 2（最新的 run 是否完结）。裁决 5 说归档时未完成的工具执行与
模型响应都被中断——**中断之后那次 run 已经完结**。所以撤销归档的那一刻，
不存在「尚未完结的最新 run」，按同一条判定规则只能落在休眠。
**这不是另定一条规则，是既有规则的必然结果。**

### 撤销归档只恢复这一个会话，子会话不跟着回来

**推理**：裁决 5 把「子会话级联被归档」与另两项并列，一同标为**不可逆不可恢复**。
若撤销归档会连带恢复子会话，那一项就不是不可逆的，与裁决 5 直接矛盾。
**因此子会话保持归档**；而撤销归档本身是每个会话各自的动作，所以**要哪个子会话就单独撤销哪个**。

### 归档只往下传，不往上传

**推理**：裁决 5 只说「会话被归档，子会话同样级联被归档」，方向是单向的。
反向传导会造成一个荒谬的后果——**agent 派出去的一个小差事收尾，会把派它出去的整段协作一起收掉**。
与[主会话生命周期相互独立](../../ubiquitous_language/terms/agent-runtime-loop.md#ul-primary-session--主会话--primary-session)
也不相容。**只有单向成立。**

### 会话类型不参与放行判断

**推理**：[放行三元组](../PF-007-meta-capabilities/design.md#611-ask通向人)
已由 PF-007 §6.11 定死为权限设置 × 会话授权上下文 × 会话运行模式，**三者**，
且明写「三者是组合关系，不是谁盖过谁」。裁决 6 引入会话类型时说的是「主要目的是什么」，
用途是裁决 10 的跑题探测，**通篇没有提到放行**。
若类型参与放行，等于在三元组外偷加第四条腿，**那是改 PF-007 的架构承诺，不是本 topic 能定的**。
**所以它不参与，且正文要明写**——否则实现者会自己猜。

### 语义化的全局授权，仍然受说话人自身权限的约束

**推理**：裁决 24 让一句话可以产生「租户下未来所有会话」的授权。
但[会话里坐着的那个人，未必是设权限的那个人](../PF-007-meta-capabilities/design.md#611-ask通向人)——
这是 PF-007 §6.11 已经写下的一条告诫。若说话即生效而不看说话人是谁，
**任何成员都能靠一句话改掉整个租户的授权面**，这与
[PF-001 的作用域与身份模型](../PF-001-identity-scope-and-agent-constraints/design.md#62-三种合成语义)冲突。
**只有一个答案成立**：作用域是用户表达出来的**意图**，能不能真的生效仍按原有的权限判断。
**裁决 25「怎么做到不需要产品关心」管的是识别，不是越权。**

### 业务流程拓展点暂由本 topic 拥有

**推理**：裁决 11 是产品负责人在本次 PF-015 讨论中直接引出的，
它的**唯一实例**（裁决 10 的跑题提醒）是会话类型的配套能力，而会话类型归本 topic。
**但它作为一类机制的归属并不天然属于会话**——将来长出与会话无关的实例时要重判，
所以[§9 把它列为显式缺口](design.md#九未决项)，**不在正文里假装它已经有家**。

### 为什么「没有 uncertain 档」说得通

**推理**：裁决 31 说判定是二分类、不存在第三档。二分类器当然可能判错，
所以这句话的产品含义**不是「它永远判得对」**，而是**「系统不把拿不准这件事丢回给用户」**。

**它之所以成立，全靠裁决 10 那条「[只提醒不阻拦](design.md#66-跑题只提醒不阻拦)」**：
判成「对不上」的最坏后果是用户多点一下，判成「对得上」的最坏后果是这次没提醒，
**两个方向都没有不可挽回的代价**。若提醒是能拦死的，这一档就非有不可。
**所以正文把这两条写在一起**——拆开看，第二条会显得武断。

### 自动归档与手动归档的后果必须一样

**推理**：裁决 28、29 给了两条来路，**但没说后果有别**。
若自动归的档「轻一些」（比如不级联、不中断），就等于凭空多出一个第五种状态，
与[§5.1 只有四个状态](design.md#51-四个状态怎么走)冲突；
而[裁决 5 的三项连带](#一拍板记录)是挂在**归档**上的，不是挂在「谁发起的归档」上。
**只有「后果一样」自洽。**

### †：第 6、12、13、14 项的生产者与消费者

**这四格是推的，不是产品负责人给的。**他对这几项说的是「**容易推断**」「**比较好推断**」。

**推理（生产者）**：四项的名字里都带着「**会话当前**」——
[工具执行的运行时绑在 session 上](../PF-006-tools-and-skills/design.md#65-工具执行有自己的运行时绑定在-session-上)、
[子会话由这个会话的 agent 创建](../../ubiquitous_language/terms/agent-runtime-loop.md#ul-child-session--子会话--child-session)、
待办归这个会话、ModelProfile 是「**会话当前使用的**」。
**四样东西都在会话名下，维护它们的只能是会话本身。**

**推理（消费者）**：产品负责人对第 1–5、11 项**一律给的是「三个角色都要用到」**，
而对这四项说「容易推断」——**最直接的读法是与前面同构**。
**这是类比，不是独立论证**，所以标了 †。

> **第 7 项的消费者当时推不出来，[已由裁决 51 给定](#2026-09-21--第-7-项的消费者)**——
> **是模型**，理由是一个还没做的能力。**当初没代填是对的**：
> 按「压缩那个函数不是拓展点」硬推，会推出「没有消费者、不该进清单」这个错误结论。
> **它的生产者仍是 †**，与第 6、12、13、14 同理。

### 两个被当场纠正的归纳，留在这里

**都是 PM 的，都没进过正文，但记下来能挡住同样的误读：**

| PM 说过 | 错在哪 |
|---|---|
| 「[当下条件](../PF-012-agent-loop-and-run/design.md#当下条件)与 runtime context 定义重叠而性质相反，**这是冲突**」 | **不是冲突。**产品负责人：「冲突我理解是只能在一边，但是**两边都可以有**哇」。**当下条件是「算下一步要读什么」的视角，runtime context 是那些东西的存在形态**——同一个事实可以既被当下条件读到，又以 runtime context 的形态存在 |
| 「**实时算的不进来**」是第二条判据 | **过度归纳。**那是它**怎么来的**，不是它**进不进来**的理由。**判据只有消费这一条**——第 15 项就是实时算的，照样算数 |

### 「归档」与「授权失效」必须分开陈述

**推理**：这两件事在既有正文里曾经被写在同一句话上
（[会话结束授权随之消失](../PF-007-meta-capabilities/design.md#会话授权上下文)）。
裁决 15 把它们劈开了——**授权是数据，归档不丢**。
方法侧也要求同一件事：授权撤销、工作取消、业务补偿三者
**分别定义生效点、在途政策与完成条件，不以局部逆操作代替**。
**产品阶段不分开说，契约阶段就拆不开**，所以 [§5.4](design.md#54-会话内的授权与生命周期的交界)
用一张表把两者并排放着。

### 外部来源不替谁建会话——主线裁定 R-N2（2026-09-23，待产品负责人确认；指路，不升 rev）

**结论**：[§2 非目标](design.md#非目标)加一句：连接件送进来的消息本版只投递到一个已有的会话；按消息新建会话、按对面线程分会话，本版没有。

**推理**：共用契约起草前的对账发现，连接件的投递目标只有「一个已有的会话」一种取值，而新建会话、按线程投递两种**哪一处正文都没写规则**。
那两种都要先回答「连接件替谁建会话、建在哪个租户身份下」——会话[持有创建那一刻的租户身份](design.md#612-会话持有创建那一刻的租户身份)，
而一条外部消息进来时，没有一个人站在那里作为创建者。**本 topic 管会话怎么建，所以由这里写明这条路本版不开**；
投递目标本身归 [PF-002 §4 Connector](../PF-002-assets-settings-and-permissions/design.md#connector)，受理之后怎么走归 [PF-014](../PF-014-inbound-intake-and-queueing/README.md)，三处各写一句指路。
**没有改任何已有规则**，所以不升 rev。
