## 一、背景与问题

[会话](../../ubiquitous_language/terms/agent-runtime-loop.md#ul-session--会话--session)
是这个系统里活得最久的东西。它比
[agent runtime](../../ubiquitous_language/terms/agent-runtime-loop.md#ul-agent-runtime--agent-runtime--agent-runtime) 长寿，
比任何一次[运行](../../ubiquitous_language/terms/agent-runtime-loop.md#ul-run--运行--run)长寿，
比它落地过的每一个[沙箱](../../ubiquitous_language/terms/grounding-and-isolation.md#ul-session-sandbox--会话级沙箱--session-scoped-sandbox)长寿。
用户看到的每一段协作、agent 写下的每一条记录、花掉的每一分钱，**都归到某一个会话名下**。

**但在此之前，它只有一个名字，没有一条生命线。**这造成四个具体的空洞：

**第一，谁都知道一段协作会停下来，但没人说得出「停下来」是什么。**
别的 topic 已经写下了吊在这个事实上的规则——
[两个 agent 能不能互相说话，要看对方那一边是不是还在](../PF-007-meta-capabilities/design.md#先说谁能给谁发消息这是两条独立的规则)；
[还悬着的问询什么时候一并清掉](../PF-007-meta-capabilities/design.md#四个出口)。
**这两条都需要一个精确的锚点，而那个锚点一直不存在。**

**第二，一个会话不知道自己是干什么的。**用户在一个专门用来写代码的会话里聊起了周末的安排，
系统一无所知——它既不会提醒，也没有能力提醒，因为**「这个会话是干什么的」从来没被表达过**。

**第三，会话与会话之间的关系是隐的。**agent 派出去一个子 agent，那边也开了一个会话。
两个会话之间到底是什么关系、谁能看见谁、一个停了另一个怎么办——
[UL-D-4](../../ubiquitous_language/decisions.md#ul-d-4--主会话与子会话--2026-09-21) 定了名字与拓扑，
**但「一个归档了，另一个怎么办」仍然没有答案**。

**第四，agent 干活时要感知的那些东西，没人说得出一共有哪些。**
[PF-001 定了 Context](../PF-001-identity-scope-and-agent-constraints/design.md#contextagent-运行时可感知的上下文信息)、
[PF-012 定了当下条件](../PF-012-agent-loop-and-run/design.md#当下条件)、
[PF-002 定了权限怎么求值](../PF-002-assets-settings-and-permissions/design.md#52-设置与权限是资产的两种属性)——
**各自都对，但没有一处回答「一个会话最少得带着哪些，少一样就不成立」。**
于是每个实现者自己攒一套，**而攒漏了不会报错**：agent 只是偶尔显得不知道自己在哪、
不记得刚才批过什么、忘了后台还有活儿在跑。

**不做会怎样**：上面那两条已接受的规则永远无法落地——
它们引用的事实不存在，实现者只能自己编一个，而每个人编的不一样。
**而第四个空洞更隐蔽**：它不会让任何东西失败，**只会让 agent 一直显得有点糊涂**。

## 二、目标与非目标

### 目标

- **给会话一条完整的生命线**：有哪几个状态、怎么走、哪些转换可逆、哪些不可逆。
- **把「归档」定成那个锚点**，并说清它连带发生什么、什么不跟着回来、**由谁发起**。
- **让会话知道自己是干什么的**，并在用户跑题时有能力提醒——**但不替用户决定**。
- **定清会话之间的归档如何传导**。
- **说清会话的生命周期对授权做什么、不做什么。**
- **定义 [runtime context](#runtime-context)**，并**圈定哪些是每个会话必不可少的**（[meta runtime context](#meta-runtime-context)）。
- **定义[会话运行模式](#会话运行模式)**——放行三元组的第三条腿，此前两个 topic 都在依赖它而无人定义。

### 非目标

- **不定义会话内的数据具体怎么存、什么时候算落定。**本 rev 只给出
  [存储要守住的两件事](#58-存储要守住的两件事)——**那是对存储提的要求，不是一份存储方案**。
  日志的语义仍归 [PF-012 §4](../PF-012-agent-loop-and-run/design.md#会话日志)。
- **不定义工具权限。**那是[放行三元组](../PF-007-meta-capabilities/design.md#611-ask通向人)里另一条腿的事。
  **执行环境权限也不在这里**——它管的是「作用落在哪」，
  归 [PF-005 §4](../PF-005-execution-environments-and-sandboxes/design.md#执行环境权限)。
- **不定义 agent 的类型与类目。**那是 AgentDefinition 的属性，
  **归 [PF-004 §4](../PF-004-agent-definition-and-assembly/design.md#agent-类型)**；
  本 topic 只**消费**它算出会话类型。
- **不做会话的删除。**见[§7 取舍](#为什么没有删除)。
- **不定义外部来源替谁建会话。**[连接件](../PF-002-assets-settings-and-permissions/design.md#connector)送进来的消息，本版只投递到一个已有的会话；
  按一条消息新建会话、按对面的线程分进不同会话，要先有「连接件替谁建会话、建在哪个租户身份下」的规则——**本版没有这条路**。

## 三、用户与场景

| 谁 | 什么情况 | 他期待什么 |
|---|---|---|
| **用户** | 两周前那段协作早就收尾了，列表里还占着位置 | 收起来，眼不见为净——**但别弄丢，说不定还要翻** |
| **用户** | 收起来之后又需要它了 | **能拿回来接着聊**，不用从头讲一遍背景 |
| **用户** | 在一个写代码的会话里，顺口问了句跟代码无关的 | **提醒一下就行，别拦着**——可能只是个岔出去的小话题，聊完就回来 |
| **用户** | 对 agent 说「这类事以后都不用问我了」 | **说了就算数**，不用再去设置页里翻一遍 |
| **用户** | 对 agent 说「刚才那个授权收回」 | **同样说了就算数** |
| **agent** | 正要动一个需要授权的工具 | 准确知道**此刻**自己有没有这个授权——不靠记忆，不靠翻聊天记录 |
| **用户** | 一堆早就不动的会话堆在那儿，挨个收太烦 | **过一阵自己收起来**，不用他管 |
| **agent** | 派出去的子 agent 还在跑，父会话被归档了 | 那边**不该继续烧钱**，它的活儿要一起停 |

## 四、概念定义

### 会话的生命周期

**一个会话从建立到被收起来，会处在四个状态之一。**

| 状态 | 它意味着什么 |
|---|---|
| **创建 / 初始化** | 会话的身份已经确立，但它还没开始承载协作 |
| **运行 / 活跃** | **最新的那次[运行](../../ubiquitous_language/terms/agent-runtime-loop.md#ul-run--运行--run)还没完结** |
| **休眠** | 会话完好、随时可用，但此刻没有在跑的运行 |
| **归档** | 这段协作被明确收起来了 |

**「运行 / 活跃」的判定只看一件事：**
[会话日志](../../ubiquitous_language/terms/record-and-context.md#ul-session-log--会话日志--session-log)
里最新的那次运行有没有完结。

> **判定依据是日志上的事实，不是有没有活着的协程。**
> 会话[本来就不是活物](../../ubiquitous_language/terms/agent-runtime-loop.md#ul-session--会话--session)；
> 进程重启、runtime 被回收，都不改变「最新那次运行完没完」这个事实。

**运行与休眠之间来回切换，没有次数限制**，也不构成任何一种终结。

### 会话归档

**把一段协作明确收起来的那个动作，以及它之后所处的那个状态。**

**它是这个系统里唯一一个「这段协作到此为止」的锚点。**
凡是别处写着「会话结束之后如何如何」的规则，指的都是它——
[没有删除会话这回事，所以也没有「会话结束」这回事](../../ubiquitous_language/terms/agent-runtime-loop.md#ul-session--会话--session)。

**归档可以被撤销。**撤销之后会话重新可用，历史一条不少。

**但归档连带发生的三件事不可逆，也不可恢复：**

| 连带发生 | 撤销归档之后 |
|---|---|
| **子会话级联被归档** | **不跟着回来**——每个子会话各自单独撤销 |
| **未完成的工具执行被中断** | **不续**。中断按[被中断处理，不是失败](../PF-006-tools-and-skills/design.md#67-用户可以中断而中断不是失败) |
| **正在进行的模型响应被中断** | **不续** |

> **「会话能拿回来」和「它当时在干的活儿能拿回来」是两件事。**
> 前者是状态的回退，后者是工作的恢复——**本系统只提供前者。**

### 会话类型

**一个会话主要是用来干什么的。**

它由用户创建会话时选定的
[AgentDefinition](../PF-004-agent-definition-and-assembly/design.md) **算出来**，
而不是由用户另外挑一次。当前有五类：

| 会话类型 | 干什么的 |
|---|---|
| `general-purpose` | 通用 |
| `coding` | 写代码 |
| `office` | 办公事务 |
| `research` | 调查与研究 |
| `personal-life` | 个人生活 |

**这五类只能由产品出厂时增补，租户不能自定义。**理由在[§7](#为什么类型只能出厂加)。

**会话类型在会话建立时算定，此后不随它的来源变化。**
同一份 AgentDefinition 后来改了、下线了、换了类目，**已经存在的会话不跟着变**。

承接定时工作的 [Job Session](../PF-021-schedule-and-calendar/design.md#作业会话) 表达独立的执行约束，
不增加第六种用途，也不从 AgentDefinition 的用途推断。其新建、成果交付和单次取消要求由 PF-021 定义；会话身份、主子关系与生命周期仍沿本 topic。

### 业务流程拓展点

**业务流程上一个开放的位置，挂在那里的东西可以拦住一次请求，但不改变任何已经落定的事实。**

它与
[Loop 拓展点](../../ubiquitous_language/terms/agent-runtime-loop.md#ul-loop-extension-point--loop-拓展点--loop-extension-point)
是**两类**东西：

| | Loop 拓展点 | 业务流程拓展点 |
|---|---|---|
| **挂在哪** | [Agent Loop 的状态点](../PF-012-agent-loop-and-run/design.md#loop-拓展点)前后 | 业务流程推进的途中 |
| **靠什么起作用** | **只能靠改[会话日志](../../ubiquitous_language/terms/record-and-context.md#ul-session-log--会话日志--session-log)** | **不产生任何持久化影响** |
| **它产出什么** | 会话日志上的增量 | **业务流程上的增量价值** |
| **典型位置** | 模型响应之后、工具执行之前…… | [受理](../../ubiquitous_language/terms/interaction-and-dispatch.md#ul-inbound-arrival--入站到达--inbound-arrival)之前 |

**「不产生持久化影响」是它的定义性质，不是它的实现细节。**
一个业务流程拓展点拦下一次请求，**系统不持有被拦下来的那份东西**——
请求就地返回给发起方，到此为止。

### runtime context

**会话推进中，在 [agent loop](../PF-012-agent-loop-and-run/design.md#agent-loop) 内
被模型、工具、拓展点之一消费的，[消息](../../ubiquitous_language/terms/record-and-context.md#ul-message--消息--message)之外的那些上下文。**

**它是一块一块的，不是一个大袋子。**每一块是一份数据——多数是一张表单，
**在上下文中 in-place 地被更新**；也有实时算出来的。
**共同点不是形态，是消费：会话内的角色要感知它。**

**它与[会话日志](../../ubiquitous_language/terms/record-and-context.md#ul-session-log--会话日志--session-log)是两样东西：**

| | 会话日志 | runtime context |
|---|---|---|
| **怎么变** | **只追加**，写下的永不改变 | **就地更新**，拿到的是**当前值** |
| **历史** | **全都在** | **不保留**，它只回答「现在是什么」 |
| **agent 怎么知道它变了** | 日志自己会说话 | **要专门告诉它**（见 [§6.8](#68-变更了要不要告诉-agent看谁消费它)） |

**每一块都有两端，缺一不可：**

| 端 | 取值 |
|---|---|
| **生产者** | **会话本身**维护，或**会话外的某个东西**维护——**按块而异** |
| **消费者** | **模型 · 工具 · 拓展点**，三个角色的一个或多个 |

> **工具和拓展点也读它**，这不是附带的——**runtime context 从来不只是"给模型的上下文"**。

### meta runtime context

**每个会话都必需携带、并且必需持续更新的那些 [runtime context](#runtime-context)。**

**它与[会话运行模式](#会话运行模式)、与装配无关**：不论装的是哪一份定义、
配了什么工具、跑在什么模式下，**这一批一样都不能少**。

> **和 [meta capabilities](../PF-007-meta-capabilities/design.md) 是同一个道理**：
> 那边是**每个 agent 必不可少的能力**，这边是**每个会话必不可少的感知**。
> **两边都不可禁用、不可替换。**

**哪些够得上「meta」，只有一条判据**（见 [§5.5](#55-哪些算-meta-runtime-context)）。

### 会话运行模式

**这个会话里，「本该问人」的那一刻改怎么办。**

**恰好三档：**

| 取值 | 本该问人的那一刻 |
|---|---|
| **`never`** | **一律当作被拒**，**不问任何人** |
| **`auto_permission`** | **拿已经形成的[授权表达](../PF-007-meta-capabilities/design.md#一笔授权表达有三个维度)算**；算得出就照算出来的办，**算不出来就问人** |
| **`bypass-permissions`** | **直接放行** |

**三档管的是同一件很窄的事**：

> **它不决定哪些动作要问人，只决定「本该问人的那些，改怎么办」。**

「要不要问」由[权限设置](../PF-002-assets-settings-and-permissions/design.md#52-设置与权限是资产的两种属性)
与[会话授权上下文](../PF-007-meta-capabilities/design.md#会话授权上下文)算出来；
**模式接手的是问不成的那一刻**（[完整的四步见 PF-007](../PF-007-meta-capabilities/design.md#56-一次放行判断走四步)）。

**`auto_permission` 是有闭环的那一档**：问人的答案**落成新的授权表达**，
进[本会话那份语义授权](#56-十四项-meta-runtime-context)——**下一次同样的事就算得出来了**。
**「同一件事不必问第二遍」不是另一条规则，就是这个闭环。**

> **这一档特意不叫 `auto`。**
> [上游有一个同名档，语义是「不问人、改问模型」](../../../research/agent-harness-session-design/research.md)，
> **而我们这一档从不替人做判断**——它只算已有的记录，算不出来就把问题**交回给人**。
> 名字里带上 `permission`，是为了让它与**执行环境那一维的 `auto_place`** 分得开：
> **一个决定「准不准」，一个决定「落在哪」。**
> **`never` 与 `bypass-permissions` 两档则与上游同义。**

**`never` 有一个连带后果**：
[`Ask().request_approval` 在这个会话里不可用](../PF-007-meta-capabilities/design.md#57-权限能关掉一条命令关不掉一扇门)——
**这扇门还在**，但这条命令用不了，**而且 agent 看得见它为什么用不了**。

## 五、模型

### 5.1 四个状态怎么走

```text
                        ┌──────────────────┐
     建立 ─────────────→│  创建 / 初始化   │
                        └────────┬─────────┘
                                 │  按「最新的运行完结没有」落位
                     ┌───────────┴───────────┐
                     ↓                       ↓
              ┌─────────────┐         ┌─────────────┐
              │ 运行 / 活跃 │ ←─────→ │    休眠     │
              └──────┬──────┘         └──────┬──────┘
                     │                       │
                     └───────────┬───────────┘
                                 ↓  归档
                        ┌──────────────────┐
                        │      归档        │
                        └────────┬─────────┘
                                 │  撤销归档
                                 ↓
                              休眠
```

**三件事要读出来：**

- **运行与休眠之间的往返没有上限**，来回多少次都不构成终结。
- **归档是唯一的出口，而它有回头路**——但回来落在**休眠**，不落在运行。
  归档的时候在跑的东西已经被中断了，**不存在「还没完结的最新运行」把它顶到运行态**。
- **没有第五个状态。**没有删除，没有过期，没有回收。

### 5.2 会话与会话之间

会话有[主会话与子会话两种性质](../../ubiquitous_language/terms/agent-runtime-loop.md#ul-primary-session--主会话--primary-session)，
关系与通信拓扑由 [UL-D-4](../../ubiquitous_language/decisions.md#ul-d-4--主会话与子会话--2026-09-21) 定，
本节只定**生命周期在这层关系上怎么传导**：

```text
      主会话 A                          主会话 B
         │                                 │
    ┌────┴────┐                       （彼此独立，
    ↓         ↓                     谁归档都不影响对方）
  子会话 A1  子会话 A2
    │
    ↓
  子会话 A1a
```

| 发生什么 | 传导到哪 |
|---|---|
| **A 被归档** | **A1、A2、A1a 全部级联被归档**——沿子会话关系一路到底，不看层级深浅 |
| **A1 被归档** | **只到 A1a**。**A 不受影响**，它还在跑自己的 |
| **A 撤销归档** | **只有 A 回来。**A1、A2、A1a 保持归档 |
| **B 被归档** | **与 A 这一支毫无关系** |

> **归档只往下传，不往上传。**一个子会话收尾，不意味着派它出去的那段协作也收尾了。

### 5.3 会话类型怎么算出来

[属性的定义归 PF-004](../PF-004-agent-definition-and-assembly/design.md#agent-类型)，本节只定那条映射。

```text
 用户挑一个 AgentDefinition
            │
            ↓
   读它的 agent 类型与类目          ← 属性归 PF-004 §4
            │
            ↓
     算出这个会话的类型             ← 建立时算一次，此后不变
```

**关键是「算」这个字。**会话类型**不是**在 AgentDefinition 上绑死的一个字段的副本——
两者之间是一条**映射关系**，而映射关系可以改。改了之后：

- **新建的会话按新映射算**；
- **已经存在的会话保持原样**，一个都不跟着变。

### 5.4 会话内的授权，与生命周期的交界

**授权的完整模型归 [PF-007 §4](../PF-007-meta-capabilities/design.md#会话授权上下文)**，
本节只定生命周期在这件事上的边界：

> **授权是数据，不是活物。**一个会话里用户表达过的授权，
> **归档不会让它消失**，撤销归档之后它原样还在。

**这条与上面那三项「不可逆」是分开的两件事，不能互相代替：**

| | 归档对它做什么 |
|---|---|
| **在途的工作**（工具执行、模型响应、子会话） | 工具执行与模型响应**被中断**，子会话被级联归档；都不可逆 |
| **已经表达过的授权** | **什么都不做**。它是[会话日志](../../ubiquitous_language/terms/record-and-context.md#ul-session-log--会话日志--session-log)那一侧的事实 |

> **「在途的工作停了」推不出「授权也没了」。**两者的生效点、在途政策与完成条件各不相同，
> 写在同一句话里，到了定契约那一步就再也拆不开。

### 5.5 哪些算 meta runtime context

**只有一条判据：**

> **它在 [agent loop](../PF-012-agent-loop-and-run/design.md#agent-loop) 内，
> 被模型、工具、拓展点这三个角色之一消费——依赖它。**

**判的是消费，不是别的。**不看它是表单还是实时算出来的，
不看它归谁维护，也不看它有多重要。

**两个反例，各说明一件事：**

| 不是它 | 为什么 |
|---|---|
| [**模态投影**](../PF-013-model-profiles-and-invocation/design.md#模态投影) | 它**确实是会话要维护的一项状态**——但那是**会话提供给会话外的服务用的**，**会话内的三个角色都不消费它** |
| [**当下可用性**](../../ubiquitous_language/terms/reach-and-availability.md#ul-current-availability--当下可用性--current-availability) | **消费它的是 runtime 本身**。它在[组装](../PF-010-context-management-and-assembly/design.md)那一步被算出来，直接把用不了的工具与技能**替换成一句说明（标识不变）**——**三个角色看到的是那句说明，不是这份数据** |

> **「会话要维护的状态」与 runtime context 是两个圈，有交集但不重合。**
> 前者还包含**会话对外提供的投影**，那一部分不在这里。
> **不写死这一条，这份清单会一路膨胀成「会话身上所有的东西」。**

### 5.6 十四项 meta runtime context

**† 标记的那几格是 PM 推导**，推理链在 [decisions](decisions.md#二pm-推导)，**可以被逐条推翻**。

| # | 这一块 | 生产者 | 消费者 | 至少提供什么 |

| **1** | **会话的元信息** | 创建会话的那个东西 | 三个角色 | 会话的身份标识 · 创建时间 · [会话类型](#会话类型) · 会话日志版本号 · 会话运行模式。**包括但不限于这些** |

**这张表里有六件事要单独读出来：**

- **第 4 条：agent 的身份标识恒等于会话的身份标识。**
  会话与 agent 是**一对一**的，而[同一时刻至多一个活跃的 agent runtime](../../ubiquitous_language/terms/agent-runtime-loop.md#ul-single-active-execution--会话内单活跃--single-active-execution)——
  **所以换了一个 agent runtime，这个标识也不变**。
  **它是产品层的承诺**：agent 之间互相寻址靠的就是它。
- **第 8 条的消费者里没有模型。**授权怎么合成是[拓展点实时算](../PF-007-meta-capabilities/design.md#会话授权上下文)的事，
  **模型不需要看见原始的分层授权**——它只需要知道**结果**。
- **作用域为「全局」的那一档不另占一块。**用户说的「以后所有会话都这样」
  **落成[租户层的权限设置值](../PF-002-assets-settings-and-permissions/design.md#52-设置与权限是资产的两种属性)**，
  [落点由 PF-007 定](../PF-007-meta-capabilities/design.md#一笔授权表达有三个维度)，**因此它随第 8 条那份结构化授权一起进来**，
  在[放行判断的第 ③ 步与本会话那份流水一起算](../PF-007-meta-capabilities/design.md#56-一次放行判断走四步)。
  **系统里的授权流水只有一种：每个会话一份**——第 9 条就是它在这张表里的那一面。
- **第 8、第 9 条的主体是[租户](../PF-001-identity-scope-and-agent-constraints/design.md#租户)，不是自然人那个账号。**
  [授权的「全局」一档管的是「这个租户下未来所有会话」](../PF-007-meta-capabilities/design.md#会话授权上下文)——
  **同一个自然人在另一个组织下是另一个租户，他在这边说过的话不跟过去。**
  场景里写「用户」是在说**坐在会话里的那个人**；**这两块数据归属于他此刻所在的那个租户**。
- **第 10 条可以是空，也可以变。**空就是[这一级什么都不加载](../PF-002-assets-settings-and-permissions/design.md#它是会话选用的不指定就是空)；
  它不是会话建起来就钉死的一项，换了一份就是[装配输入变了](../PF-004-agent-definition-and-assembly/design.md#装配)。
- **第 7 与第 14 条是一对，缺一个另一个就没用。**
  模型同时看得见**当前占了多少**与**压缩会怎么压**，才谈得上
  **自己判断要不要主动发起一次[压缩](../PF-010-context-management-and-assembly/design.md)**。
  **只给占用比，它不知道压了会失去什么；只给压缩策略，它不知道该不该压。**

### 5.7 三个作用域在同一份数据里

[授权有三个作用域](../PF-007-meta-capabilities/design.md#会话授权上下文)——
**单次执行 · 本会话 · 全局**。**作用域是同一份数据上的一个维度，不是三套各自的存法**：

> **授权相关的 runtime context，其数据本身就要能表示出
> 「单次 / 本会话 / 全局（always on）」的区别。**

**分得出这三者，正是为了知道这一笔该落到哪里**：

| 作用域 | 落在哪 |
|---|---|
| **单次执行** · **本会话** | **[第 9 条那份本会话的授权流水](#56-十四项-meta-runtime-context)**——**「单次执行」不另起一块** |
| **全局** | **不落在这块数据里。**它[落成租户层的权限设置值](../PF-007-meta-capabilities/design.md#一笔授权表达有三个维度)，随[第 8 条那份结构化授权](#56-十四项-meta-runtime-context)进来 |

> **系统里的授权流水只有一种：每个会话一份。**
> 没有第二份「全局的流水」——**一句管到未来所有会话的话，
> 管的本来就不是这个会话**，把它留在会话里，别的会话读不到它。

**单次那一档因此有明确的清除时机**：
**一次[运行](../../ubiquitous_language/terms/agent-runtime-loop.md#ul-run--运行--run)明确结束的时候，把单次授权清空**——
落点是 [loop 上「落终态之后」那个位置](../PF-012-agent-loop-and-run/design.md#十一个位置是推出来的不是挑出来的)。

> **不给它一个清除时机，「单次」这个词就是假的**——
> 它会一直留在那儿，而没有人知道它本该在上一次运行结束时就没了。

### 5.8 存储要守住的两件事

**产品层面对存储只提两条**，其余归技术设计。

#### 第一件：会话睡一觉醒来，还得是原来那个

**三样东西各有各的守法：**

| 什么 | 怎么守 | 谁定的 |
|---|---|---|
| [**会话日志**](../../ubiquitous_language/terms/record-and-context.md#ul-session-log--会话日志--session-log) | **只增不改，没有例外** | [PF-012 §4](../PF-012-agent-loop-and-run/design.md#会话日志)**已经定死**，本 topic 只是要求**存储真的兑现它**，而不是把它当成一句约定 |
| [**runtime context**](#runtime-context) | **除了实时算的那些，每一块都要能恢复** | **本 topic** |
| [**会话日志投影**](../../ubiquitous_language/terms/record-and-context.md#ul-session-log-projection--会话日志投影--session-log-projection) | **从日志重算一遍，必得同一个答案** | **本 topic** |

**判据是两个具体动作**：**会话被重新加载**、**归档被撤销**。
这两件事之后，[三个角色](#55-哪些算-meta-runtime-context)感知到的东西**必须和之前一样**。

> **不然那就不是同一个会话了**，而[会话不会消失](#61-会话不会消失)这条承诺也就落了空——
> **会话还在、却记不得自己是谁，跟消失没有区别。**

**实时算的那些不在此列。**它们本来每次都现算——
[上下文占用比](#56-十四项-meta-runtime-context)、[当下可用性](../../ubiquitous_language/terms/reach-and-availability.md#ul-current-availability--当下可用性--current-availability)——
**对它们来说根本没有「恢复」这回事**。

**还有一层，是关于投影的。**目前**需要独立维护的投影只有一个**——
[模态投影](../PF-013-model-profiles-and-invocation/design.md#模态投影)，
它把「这个会话的历史里，出现过哪几种模态是只有原件、没有文本那一份的」答出来。
**但这类东西会长**：将来会有别的服务，要从同一份日志里看出别的东西。

> **所以从第一天起，「怎么从日志算出一个投影」就得是一套协议，
> 而不是为模态投影单独写的那一段。**

**判据很直白**：**加第二个、第三个投影的时候，已有的那个不用改。**

#### 第二件：今天是单机，但别把单机焊进语义

[SYS-DEPLOY](../../foundation/cross-system-constraints/requirements.md) 已经定了
第一版是单机，**而边界要清晰到将来能扩展成分布式、异构节点与微服务化，且不改变领域语义**。
**落到存储这件事上，产品侧只认一条：**

> **存储在产品语义上是什么，不取决于它实际存在哪里。**

「会话日志是一份只增不改的流水账」这句话，**在单机和分布式下含义必须完全相同**。
产品设计或契约里一旦出现「因为都在一台机器上，所以……」这种推理，
**那就是把部署形态写进了语义**。

**这条现在不要求做任何分布式设施**，它只约束一件事：

> **将来换一套存储实现的时候，不该回过头来推翻[架构内核](../architecture-core.md)。**

## 六、产品规则

### 6.1 会话不会消失

**系统不提供删除会话的能力，任何角色都不提供。**
一个会话一旦建立，它的身份与历史就一直在——**能做的只是把它收起来**。

**因此「会话结束」这个说法在本系统里不成立。**要表达「这段协作到此为止」，
**说的是归档**。

### 6.2 归档有两条来路：人手动，或到期自动

| 来路 | 谁 |
|---|---|
| **手动归档** | **租户**——会话归它，收不收起来由它说了算 |
| **自动归档** | **系统按一个时限自动收**，那个时限是**出厂配置**，**默认 30 天** |

**自动归档与手动归档的后果完全一样**：
[三件事照样连带发生](#63-归档先停活儿再落状态)，**也照样可以撤销**。
**没有「系统归的档比较轻」这回事。**

> **那条时限是出厂配置，不是每个会话各设一个。**
> 它是一条产品默认值，**改它是改产品的出厂设定**。

> **注意[会话级沙箱到点销毁是另一回事](../PF-005-execution-environments-and-sandboxes/design.md#63-会话级沙箱到点销毁数据不留存)。**
> 那挂的是**沙箱自己的最大连续存活时间**，**那一节同时明写「会话可以无限期存在」**——
> **沙箱没了，会话照活**；两条时限管的不是同一样东西，也不必一致。

### 6.3 归档先停活儿，再落状态

归档一个会话，**在它落成归档状态之前**，下面三件事全部发生：

1. 它的**子会话**依次被归档（递归到底）；
2. 它名下**未完成的工具执行**被中断；
3. 它名下**正在进行的模型响应**被中断。

**这三件事都是「停下」，不是「回滚」。**
工具执行的收场是 [PF-006 六种收场](../PF-006-tools-and-skills/design.md#55-一次工具执行的收场有六种)里的**被中断**——
不论它在前台还是已转后台，[都不算失败](../PF-006-tools-and-skills/design.md#65-工具执行有自己的运行时绑定在-session-上)。
工具已经在外面造成的效果不会被撤销——
[外部输出不因为被系统调用就变得可逆](../PF-006-tools-and-skills/design.md#67-用户可以中断而中断不是失败)。

### 6.4 撤销归档只还给你状态

**撤销归档之后，会话回到休眠，历史一条不少。**

**但它不重启任何东西**：被中断的工具执行不续、被中断的模型响应不续、
被级联归档的子会话不跟着回来。**要哪个子会话，就去撤销哪个子会话的归档。**

### 6.5 会话类型不改变任何放行判断

**会话类型是一个用途标识，不是一道闸门。**
它**不参与**[放行三元组](../PF-007-meta-capabilities/design.md#611-ask通向人)，
也不收窄任何[权限](../PF-002-assets-settings-and-permissions/design.md#52-设置与权限是资产的两种属性)。

> **一个 `coding` 会话不会因为类型就做不了别的事。**
> 类型只用来判断「用户此刻聊的，和这个会话本来是干什么的，对不对得上」。

### 6.6 跑题只提醒，不阻拦

用户往一个会话里发的话，**若与这个会话的类型明显对不上**，
系统在这次请求落定之前把它**拦住并提醒**，由用户确认是否仍然要在这里聊。

**必须守住的五条：**

- **提醒是提醒，不是拒绝。**用户确认之后照常进行，**一次都不会被真正拦掉**。
- **被拦住的这一次不落任何痕迹。**它没有进队列，
  [没有被受理](../../ubiquitous_language/terms/interaction-and-dispatch.md#ul-inbound-arrival--入站到达--inbound-arrival)，
  **会话日志上什么都没有发生**。
- **系统不持有它。**用户确认之后发生的是**全新的一次请求**，不是把刚才那份取出来接着走。
- **用户不确认也不会有任何后果。**没有待办、没有草稿、没有超时——**什么都没有留下**。
- **这个提醒可以关掉。**不想要就关了，**关掉之后一次都不拦**。

> **为什么要拦而不是事后提示**：用户可能只是岔出去问一句，聊完就回正轨，
> **这种情况下开新会话反而添乱**。把选择权交回给他，而且要在他改主意还来得及的时候交。

#### 判定是二分的，没有第三档

**探测只给两个答案：对得上，或者对不上。**
**系统不设「不确定」这一档**——它不会把「我拿不准」这件事丢回给用户，
**因为那等于用一次打断换一个它自己也没有的答案**。

**这一档之所以不需要，是因为[提醒从不拦死](#66-跑题只提醒不阻拦)：**
判成「对不上」的最坏后果，是用户多点一下确认；
判成「对得上」的最坏后果，是这次没提醒。**两个方向都没有不可挽回的代价**，
所以不必为拿不准的情形另开一条路。

### 6.7 归档不动授权

**一个会话被归档，它里面已经表达过的授权一条都不变。**
撤销归档之后，那些授权原样还在，**不需要用户重新说一遍**。

**要收回一笔授权，走的是撤回，不是归档。**两条路互不替代——
[撤回怎么做归 PF-007](../PF-007-meta-capabilities/design.md#会话授权上下文)。

### 6.8 变更了要不要告诉 agent，看谁消费它

[runtime context](#runtime-context) 是**就地更新**的——**它不像日志那样自己会说话**。
所以变更之后：

| 这一块的消费者里 | 变更时 |
|---|---|
| **有模型** | **追加一条[系统提醒](../PF-009-context-message-types/design.md)**，让它知道这块变了 |
| **只有工具和拓展点** | **什么都不发。**那本来就不是给 agent 看的 |

> **通知的依据是「谁消费它」，不是「它重不重要」。**
> 给模型发一条它用不上的提醒，是在花它的注意力买没有的东西——
> **而注意力是这个系统里最贵的东西**。

**会话感知这类变更有两条路，而这条规则只管其中一条：**

| 路 | 谁发起 | 什么时候 |
|---|---|---|
| **推** | **那一块的生产者** | 它变了的时候。**[只在这个会话还有运行没闭合的时候才进得来](../PF-014-inbound-intake-and-queueing/design.md#610-注入的上下文变了没有运行在跑时什么都不做)**；会话空闲时推来的**一律丢弃** |
| **拉** | [agent runtime](../PF-012-agent-loop-and-run/design.md#agent-runtime) 自己 | **每一次[执行尝试](../PF-012-agent-loop-and-run/design.md#执行尝试)起来时取一次当前快照**（[PF-012 §5.7 四件事之一](../PF-012-agent-loop-and-run/design.md#每一次尝试开始都要做四件事)） |

> **两条路合起来才兑现「持续更新」。**
> 只有推，会话空闲那一段的变化就永远到不了；只有拉，运行中变的东西要等到下一次尝试才被看见。
> **而空闲期间丢掉的那些不必补**：下一次拉到的就是当前值，
> **那条状态提醒的前值取会话日志里最后感知到的那一份**——
> **[因果链记的是这个会话感知到的变化，不是世界上发生过的每一步](../PF-014-inbound-intake-and-queueing/design.md#610-注入的上下文变了没有运行在跑时什么都不做)。**

这条通知规则针对已加载的 runtime context 数据发生变化，不要求远端文件或 Git 仓库一变就即时同步、通知。工作区内容可由用户告知或 agent 按需读取、同步；资产文件变更须经实际装配或显式 reload 才进入装配数据。组织工作区参与限制也只在实际装配时重判，不由这里的快照读取扩大为运行中热同步。

### 6.9 模型看见一块 runtime context，只有两种形态

| 形态 | 什么时候 |
|---|---|
| **完整的那一份** | **会话刚开始**，以及**[上下文被压缩之后](../PF-010-context-management-and-assembly/design.md)** |
| **一条变更通知** | 这一块变了（§6.8） |

**第二种依赖第一种。**只发变更通知、从不发全量，
**模型就只能靠消息历史把当前状态拼出来**——
而[消息会被压缩、会被裁剪](../PF-010-context-management-and-assembly/design.md)，
**拼出来的那一份迟早与真的对不上**。

> **所以「压缩之后要重新给一份完整的」不是补偿措施，是这套机制成立的前提。**
> 这一条对[压缩那一侧](../PF-010-context-management-and-assembly/design.md)是硬要求：
> **meta runtime context 不能只当消息处理。**

### 6.10 单次授权在一次运行结束时清空

**在一次运行明确结束的时候，把作用域为「单次执行」的那些授权清空。**

**落点是 [loop 上「落终态之后」那个位置](../PF-012-agent-loop-and-run/design.md#十一个位置是推出来的不是挑出来的)**——
**不必新开位置**：那一处本来就开着，[用途写的就是「归档、通知、结算」这一类收尾动作](../PF-012-agent-loop-and-run/design.md#十一个位置是推出来的不是挑出来的)。

**「明确结束」用的是[运行终态](../../ubiquitous_language/terms/agent-runtime-loop.md#ul-run-terminal-state--运行终态--run-terminal-state)那三个**——
完成、失败、被取消，**三种都清**。

> **被取消也要清。**一次运行没跑完，不代表用户当时给的那句「这次可以」还能留到下一次用。
> **留着比丢了危险得多。**

### 6.11 会话睡醒之后，还是原来那个

**会话被重新加载、归档被撤销之后，
[三个角色](#55-哪些算-meta-runtime-context)感知到的东西必须和之前一样。**

落到三样上：[会话日志](../../ubiquitous_language/terms/record-and-context.md#ul-session-log--会话日志--session-log)**一条不少**
（它本来就只增不改）、**每一块不是实时算的 [runtime context](#runtime-context) 都还在**、
[投影](../../ubiquitous_language/terms/record-and-context.md#ul-session-log-projection--会话日志投影--session-log-projection)**重算得到同一个答案**。

**实时算的那些不算数**——它们没有「恢复」这回事，[判据在 §5.8](#58-存储要守住的两件事)。

> **这一条是 [6.1 会话不会消失](#61-会话不会消失)的下半句。**
> **只保住那条记录、却让它醒来时认不得自己，等于没保住。**

### 6.12 会话持有创建那一刻的租户身份

**会话在创建时捕获并持有[创建那一刻的那个租户身份](../PF-001-identity-scope-and-agent-constraints/design.md#当前租户身份)，
此后一切以它计，不随这个账号切换到别的租户身份而变**（依据
[PF-001 §4 当前租户身份](../PF-001-identity-scope-and-agent-constraints/design.md#当前租户身份)）。
**那个租户身份失效时的收场按本 topic 自己的规则**——会话[不会消失](#61-会话不会消失)，
能发生的只有[归档](#会话归档)。

### 6.13 工作区在创建时显式指定，不指定就是空

**创建会话时，[工作区](../PF-020-workspace/README.md)是一项显式的、可以不给的输入。**

- **不给，会话就没有工作区**：[那一级为空，装配什么都不加载](../PF-002-assets-settings-and-permissions/design.md#它是会话选用的不指定就是空)。
  **系统不替会话猜一份**——不按 agent 所在的目录、不按上一个会话用过的那份。
- **给了，须按[本会话的租户身份](#612-会话持有创建那一刻的租户身份)具备有效租户—工作区关系及相应访问资格**。治理所有者与获准参与者都可选用；实例本身不固定绑定一个租户。请求附着却无资格或装载失败时明确失败，不静默建成工作区层为空的会话。
- 可附着已经存在的实例，也可指定本地路径，先装载目标工作区、再创建会话。已有但尚未登记的目录，须显式选择“作为工作区使用”后建立并向中心同步关系；这一步不自动上传资源。
- 同一实例可跨租户共用，各会话分别求值；同一会话可组织同一工作区的多个 Git worktree 供不同 subagent 并行工作。创建 Git worktree 本身不登记实例或新工作区，显式使用时才关联。
- 会话归档不删除工作区和实例。关系解除或中心销毁后的后续附着沿 [PF-020](../PF-020-workspace/design.md#治理关系解除与中心销毁)：未重新显式登记前按普通目录使用，残留命名空间不贡献装配。
- 挂上的工作区及实际选用的实例入口记在 [meta runtime context 第 10 条](#56-十四项-meta-runtime-context)；
  它的内容怎么在装配时进来归 [PF-004](../PF-004-agent-definition-and-assembly/design.md#装配)。

> **为什么是 opt-in**：那一级的内容可能来自工作区地址或实例上随代码提供的资源；
> 隐式挂上等于隐式吃进一份配置。**用户说了才有，不说就没有。**

### 6.14 AGENTS.md 的上下文加载

AGENTS.md 按社区通用规范作为 runtime context 支持；嵌套子目录的文件在所在目录首次被访问时加载。它不属于 `.omne`/`.omne.local` 的资产目录，不套用资产的嵌套路径登记、兼容来源开关或显式资产 reload 规则。具体采用的规范版本、首次访问判据及上下文处理协议由 runtime context 规格核实与细化，不另增加专属工作区说明文件。

可观察结果：未访问子目录时不因资产发现而预先载入其 AGENTS.md；首次访问时加载相应上下文。工作区文件更新本身不等于全部资源立即进入模型上下文。

## 七、取舍

### 为什么没有删除

**因为会话是归属边界。**成本算在它头上，记录挂在它名下，
[授权、设置、沙箱都以它为作用域](../../ubiquitous_language/terms/scope-and-resolution.md#ul-scope-layer--作用域层--scope-layer)。
**删掉它，等于让一批已经发生的事实失去归属。**

**代价是诚实的**：列表会越来越长，存储会一直涨。
**我们选择用归档解决「看不见」，而不是用删除解决「不存在」**——
因为前者可撤销，后者不可。

> **这不等于说永远不会有删除。**合规要求下的数据清除是另一件事，
> 它有自己的触发条件、审批与留痕，**不是用户在界面上点一下的那种删除**。本 rev 不做。

### 为什么归档可撤销，副作用却不可逆

**因为它们本来就是两件事。**

- **归档**改的是**这个会话的状态**——那是一个标记，回退它没有任何外部代价。
- **中断在途的工作**改的是**外面的世界**——模型已经算过的 token、
  工具已经写出去的文件、子会话已经花掉的钱。

**把它们捆成一个「可逆的归档」，等于承诺系统能把外面的世界也退回去，而那做不到。**
与其给一个做不到的承诺，不如把界线画明白：**状态可以回头，工作不能。**

### 为什么类型只能出厂加

**因为租户能自定义的是子 agent，不是主 agent。**
这五类是用来标识**主 agent 的类目**的——
既然主 agent 只能由产品官方提供，那么类目自然也只能由产品出厂时增补。

**租户能不能自定义会话类型，不是一个孤立的问题**：它等价于问
「租户能不能自定义主 agent」，而那个问题已经有答案了。

### 为什么会话类型是算出来的，不是绑上去的

**因为它们的失效事件不同。**
AgentDefinition 是一份**会演进的资产**——它会被改、被下线、被换类目。
会话是一段**已经发生的协作**，它的用途在建立那一刻就定了。

**把两者绑死，等于让历史跟着资产走**：某天有人把一份 coding 的定义改成 research，
一批早就收尾的会话会在列表里集体变脸。**那不是修正，那是篡改。**

### runtime context 为什么不并进会话日志

**因为它们回答的问题不同。**日志回答「**发生过什么**」，
runtime context 回答「**现在是什么**」。

**并进去会两头都坏**：日志只追加，要表达「现在是什么」就得每次改一条都写一条新的，
**读的人得自己把历史折叠成当前值**——而折叠规则一旦有歧义，两边算出来的当前值就不一样。
反过来，把日志做成可就地改的，[「一条消息都不能擦除」](../PF-012-agent-loop-and-run/design.md#会话日志)当场作废。

> **一个只追加，一个就地改，这不是实现差异，是两种事实的性质差异。**

### 变更通知为什么按「谁消费」发，而不是一律发

**因为模型的注意力是这个系统里最贵的东西。**
一块只有工具和拓展点在读的 runtime context 变了，给模型发一条提醒，
它得读、得判断与自己有没有关系、然后得出「没关系」——**这一整趟是纯损耗**。

**而且损耗是累积的**：提醒多了，模型对提醒本身就不再当真，
**那时真正要紧的那条变更通知也一起失效了**——[和问得太勤是同一种失效](../PF-007-meta-capabilities/design.md#什么时候不该敲这扇门)。

### 单次授权为什么必须有明确的清除时机

**因为「单次」是一句承诺，而承诺要有人兑现。**
不给它一个确定的清除点，它就会一直留在那份数据里——
**而没有任何人会发现这件事**，直到某次 agent 拿着上一轮的授权做了这一轮的事。

**所以清除不能靠约定，要落成 [loop 上一个明确的拓展点](../PF-012-agent-loop-and-run/design.md#loop-拓展点)**，
在[运行终态](../../ubiquitous_language/terms/agent-runtime-loop.md#ul-run-terminal-state--运行终态--run-terminal-state)那一刻动手。
**三种终态都清**——**被取消的那次尤其要清**。

### 为什么要另立一类拓展点

**因为 Loop 拓展点做不了这件事，而且不该让它做。**
[挂在 Loop 拓展点上的东西只能靠改会话日志起作用](../../ubiquitous_language/terms/agent-runtime-loop.md#ul-loop-extension-point--loop-拓展点--loop-extension-point)——
这是一条**刻意设下的限制**，它保证了「agent 的下一步为什么变了」永远查得到。

**跑题提醒要做的恰恰是不留痕迹地拦一下。**
如果硬塞给 Loop 拓展点，要么打破那条限制，要么在日志里留下一堆
「用户本来想说但没说成」的东西——**两条都不能接受**。

**所以它是新的一类：拦得住请求，碰不到已经落定的事实。**

### 为什么对存储只提两条

**因为再多说就越界了。**日志落在哪个引擎、什么时候刷盘、快照怎么做、投影用什么结构——
**这些产品负责人判断不了对错**，按红线就该归技术设计。

**但这两条少说一条都不行：**

- **不提第一条**，技术上完全可以选一个让会话醒来丢状态的方案。
  **它跑得飞快，而且平时看不出错**——直到有人撤销归档，发现 agent 认不得自己了。
- **不提第二条**，单机的便利会一点一点渗进契约里。
  **等到要扩展的那天，代价是推翻[架构内核](../architecture-core.md)**，而那时候已经晚了。

> **两条都属于「不说会出事，说多了会越界」的那种要求**——
> 所以它们只说**要守住什么**，一个字都不说**怎么守**。
