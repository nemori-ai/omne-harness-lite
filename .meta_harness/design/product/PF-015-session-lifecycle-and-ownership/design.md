# PF-015：会话的生命周期与归属

- 状态：active；规则范围与接受依据见 [README](README.md#状态)，未决项见第九节。

## 一、背景与问题

[会话](../../ubiquitous_language/terms/agent-runtime-loop.md#ul-session--会话--session)
是这个系统里活得最久的东西。它比
[agent runtime](../../ubiquitous_language/terms/agent-runtime-loop.md#ul-agent-runtime--agent-runtime--agent-runtime) 长寿，
比任何一次[运行](../../ubiquitous_language/terms/agent-runtime-loop.md#ul-run--运行--run)长寿，
比它落地过的每一个[沙箱](../../ubiquitous_language/terms/grounding-and-isolation.md#ul-session-sandbox--会话级沙箱--session-scoped-sandbox)长寿。
用户看到的每一段协作、agent 写下的每一条记录、花掉的每一分钱，**都归到某一个会话名下**。

**但在此之前，它只有一个名字，没有一条生命线。**这造成四个具体的空洞：

**第一，谁都知道一段协作会停下来，但没人说得出「停下来」是什么。**
别的 topic 已经写下了吊在这个事实上的规则——
[两个 agent 能不能互相说话，要看对方那一边是不是还在](../PF-007-meta-capabilities/design.md#先说谁能给谁发消息这是两条独立的规则)；
[还悬着的问询什么时候一并清掉](../PF-007-meta-capabilities/design.md#四个出口)。
**这两条都需要一个精确的锚点，而那个锚点一直不存在。**

**第二，一个会话不知道自己是干什么的。**用户在一个专门用来写代码的会话里聊起了周末的安排，
系统一无所知——它既不会提醒，也没有能力提醒，因为**「这个会话是干什么的」从来没被表达过**。

**第三，会话与会话之间的关系是隐的。**agent 派出去一个子 agent，那边也开了一个会话。
两个会话之间到底是什么关系、谁能看见谁、一个停了另一个怎么办——
[UL-D-4](../../ubiquitous_language/decisions.md#ul-d-4--主会话与子会话--2026-09-21) 定了名字与拓扑，
**但「一个归档了，另一个怎么办」仍然没有答案**。

**第四，agent 干活时要感知的那些东西，没人说得出一共有哪些。**
[PF-001 定了 Context](../PF-001-identity-scope-and-agent-constraints/design.md#contextagent-运行时可感知的上下文信息)、
[PF-012 定了当下条件](../PF-012-agent-loop-and-run/design.md#当下条件)、
[PF-002 定了权限怎么求值](../PF-002-assets-settings-and-permissions/design.md#52-设置与权限是资产的两种属性)——
**各自都对，但没有一处回答「一个会话最少得带着哪些，少一样就不成立」。**
于是每个实现者自己攒一套，**而攒漏了不会报错**：agent 只是偶尔显得不知道自己在哪、
不记得刚才批过什么、忘了后台还有活儿在跑。

**不做会怎样**：上面那两条已接受的规则永远无法落地——
它们引用的事实不存在，实现者只能自己编一个，而每个人编的不一样。
**而第四个空洞更隐蔽**：它不会让任何东西失败，**只会让 agent 一直显得有点糊涂**。

## 二、目标与非目标

### 目标

- **给会话一条完整的生命线**：有哪几个状态、怎么走、哪些转换可逆、哪些不可逆。
- **把「归档」定成那个锚点**，并说清它连带发生什么、什么不跟着回来、**由谁发起**。
- **让会话知道自己是干什么的**，并在用户跑题时有能力提醒——**但不替用户决定**。
- **定清会话之间的归档如何传导**。
- **说清会话的生命周期对授权做什么、不做什么。**
- **定义 [runtime context](#runtime-context)**，并**圈定哪些是每个会话必不可少的**（[meta runtime context](#meta-runtime-context)）。
- **定义可在运行时切换的[会话协作模式](#会话协作模式)**，与权限和执行环境两个维度分别表达。
- **定义[会话运行模式](#会话运行模式)**——放行三元组的第三条腿，此前两个 topic 都在依赖它而无人定义。

### 非目标

- **不定义会话内的数据具体怎么存、什么时候算落定。**本 rev 只给出
  [存储要守住的两件事](#58-存储要守住的两件事)——**那是对存储提的要求，不是一份存储方案**。
  日志的语义仍归 [PF-012 §4](../PF-012-agent-loop-and-run/design.md#会话日志)。
- **不定义工具权限。**那是[放行三元组](../PF-007-meta-capabilities/design.md#611-ask通向人)里另一条腿的事。
  **执行环境权限也不在这里**——它管的是「作用落在哪」，
  归 [PF-005 §4](../PF-005-execution-environments-and-sandboxes/design.md#执行环境权限)。
- **不定义 agent 的类型与类目。**那是 AgentDefinition 的属性，
  **归 [PF-004 §4](../PF-004-agent-definition-and-assembly/design.md#agent-类型)**；
  本 topic 只**消费**它算出会话类型。
- **不做会话的删除。**见[§7 取舍](#为什么没有删除)。
- **不按外部线程自动聚合或分拆会话。**连接件投递已有会话与触发新会话是随其存在性讨论一并搁置的条件性入口；创建输入沿 [§6.23](#623-连接件创建会话的输入)，两路的选择与接收范围见 [§9](#九未决项)。
- **不为尚无场景的扩展提前增加产品机制。**业务流程拓展点按具体需求定义，不先列未来完整清单；不新增尝试开始前的挂点，也不另造复用同一子会话的并发派发机制。

## 三、用户与场景

| 谁 | 什么情况 | 他期待什么 |
|---|---|---|
| **用户** | 两周前那段协作早就收尾了，列表里还占着位置 | 收起来，眼不见为净——**但别弄丢，说不定还要翻** |
| **用户** | 收起来之后又需要它了 | **能拿回来接着聊**，不用从头讲一遍背景 |
| **用户** | 在一个写代码的会话里，顺口问了句跟代码无关的 | **提醒一下就行，别拦着**——可能只是个岔出去的小话题，聊完就回来 |
| **用户** | 对 agent 说「这类事以后都不用问我了」 | **说了就算数**，不用再去设置页里翻一遍 |
| **用户** | 对 agent 说「刚才那个授权收回」 | **同样说了就算数** |
| **agent** | 正要动一个需要授权的工具 | 准确知道**此刻**自己有没有这个授权——不靠记忆，不靠翻聊天记录 |
| **用户** | 一堆早就不动的会话堆在那儿，挨个收太烦 | **过一阵自己收起来**，不用他管 |
| **agent** | 派出去的子 agent 还在跑，父会话被归档了 | 那边**不该继续烧钱**，它的活儿要一起停 |

## 四、概念定义

### 会话的生命周期

**一个会话从建立到被收起来，会处在四个状态之一。**

| 状态 | 它意味着什么 |
|---|---|
| **创建 / 初始化** | 会话的身份已经确立，但它还没开始承载协作 |
| **运行 / 活跃** | **最新的那次[运行](../../ubiquitous_language/terms/agent-runtime-loop.md#ul-run--运行--run)还没完结** |
| **休眠** | 会话完好、随时可用，但此刻没有在跑的运行 |
| **归档** | 这段协作被明确收起来了 |

**「运行 / 活跃」的判定只看一件事：**
[会话日志](../../ubiquitous_language/terms/record-and-context.md#ul-session-log--会话日志--session-log)
里最新的那次运行有没有完结。

> **判定依据是日志上的事实，不是有没有活着的协程。**
> 会话[本来就不是活物](../../ubiquitous_language/terms/agent-runtime-loop.md#ul-session--会话--session)；
> 进程重启、runtime 被回收，都不改变「最新那次运行完没完」这个事实。

**运行与休眠之间来回切换，没有次数限制**，也不构成任何一种终结。

### 会话归档

**把一段协作明确收起来的那个动作，以及它之后所处的那个状态。**

**它是这个系统里唯一一个「这段协作到此为止」的锚点。**
凡是别处写着「会话结束之后如何如何」的规则，指的都是它——
[没有删除会话这回事，所以也没有「会话结束」这回事](../../ubiquitous_language/terms/agent-runtime-loop.md#ul-session--会话--session)。

**归档可以被撤销。**撤销之后会话重新可用，历史一条不少。

**但归档连带发生的三件事不可逆，也不可恢复：**

| 连带发生 | 撤销归档之后 |
|---|---|
| **子会话级联被归档** | **不跟着回来**——每个子会话各自单独撤销 |
| **未完成的工具执行被中断** | **不续**。中断按[被中断处理，不是失败](../PF-006-tools-and-skills/design.md#67-用户可以中断而中断不是失败) |
| **正在进行的模型响应被中断** | **不续** |

> **「会话能拿回来」和「它当时在干的活儿能拿回来」是两件事。**
> 前者是状态的回退，后者是工作的恢复——**本系统只提供前者。**

### 会话执行类型

[会话执行类型](../../ubiquitous_language/terms/agent-runtime-loop.md#ul-session-execution-type--会话执行类型--session-execution-type)决定会话承担的执行职责，以及必须绑定的 Skill、Tool、MCP 和 loop extensions。创建入口必须明确这一项；类型与其必需能力身份集合随该会话固定，具体实现按资产规则演化。作业会话是一个执行子类型，其交付义务由 PF-021 定义。

它与下文的用途分类不同：用途分类用于跑题提醒，执行类型提供不可被定义更新或模式切换取消的执行约束。它也不是三种运行期模式。

### 会话类型

**一个会话主要是用来干什么的。**

它由用户创建会话时选定的
[AgentDefinition](../PF-004-agent-definition-and-assembly/design.md) **算出来**，
而不是由用户另外挑一次。当前有五类：

| 会话类型 | 干什么的 |
|---|---|
| `general-purpose` | 通用 |
| `coding` | 写代码 |
| `office` | 办公事务 |
| `research` | 调查与研究 |
| `personal-life` | 个人生活 |

**这五类只能由产品出厂时增补，租户不能自定义。**理由在[§7](#为什么类型只能出厂加)。

**会话类型在会话建立时算定，此后不随它的来源变化。**
同一份 AgentDefinition 后来改了、下线了、换了类目，**已经存在的会话不跟着变**。

承接定时工作的 [Job Session](../PF-021-schedule-and-calendar/design.md#作业会话) 表达独立的执行约束，
不增加第六种用途，也不从 AgentDefinition 的用途推断。其新建、成果交付和单次取消要求由 PF-021 定义；会话身份、主子关系与生命周期仍沿本 topic。

### 业务流程拓展点

**业务流程上一个开放的位置，挂在那里的东西可以拦住一次请求，但不改变任何已经落定的事实。**

它与
[Loop 拓展点](../../ubiquitous_language/terms/agent-runtime-loop.md#ul-loop-extension-point--loop-拓展点--loop-extension-point)
是**两类**东西：

| | Loop 拓展点 | 业务流程拓展点 |
|---|---|---|
| **挂在哪** | [Agent Loop 的状态点](../PF-012-agent-loop-and-run/design.md#loop-拓展点)前后 | 业务流程推进的途中 |
| **靠什么起作用** | **只能靠改[会话日志](../../ubiquitous_language/terms/record-and-context.md#ul-session-log--会话日志--session-log)** | **不产生任何持久化影响** |
| **它产出什么** | 会话日志上的增量 | **业务流程上的增量价值** |
| **典型位置** | 模型响应之后、工具执行之前…… | [受理](../../ubiquitous_language/terms/interaction-and-dispatch.md#ul-inbound-arrival--入站到达--inbound-arrival)之前 |

**「不产生持久化影响」是它的定义性质，不是它的实现细节。**
一个业务流程拓展点拦下一次请求，**系统不持有被拦下来的那份东西**——
请求就地返回给发起方，到此为止。

### runtime context

**会话推进中，在 [agent loop](../PF-012-agent-loop-and-run/design.md#agent-loop) 内
被模型、工具、拓展点之一消费的，[消息](../../ubiquitous_language/terms/record-and-context.md#ul-message--消息--message)之外的那些上下文。**

**它是一块一块的，不是一个大袋子。**每一块是一份数据——多数是一张表单，
**在上下文中 in-place 地被更新**；也有实时算出来的。
**共同点不是形态，是消费：会话内的角色要感知它。**

**它与[会话日志](../../ubiquitous_language/terms/record-and-context.md#ul-session-log--会话日志--session-log)是两样东西：**

| | 会话日志 | runtime context |
|---|---|---|
| **怎么变** | **只追加**，写下的永不改变 | **就地更新**，拿到的是**当前值** |
| **历史** | **全都在** | **不保留**，它只回答「现在是什么」 |
| **agent 怎么知道它变了** | 日志自己会说话 | **要专门告诉它**（见 [§6.8](#68-变更了要不要告诉-agent看谁消费它)） |

**每一块都有两端，缺一不可：**

| 端 | 取值 |
|---|---|
| **生产者** | **会话本身**维护，或**会话外的某个东西**维护——**按块而异** |
| **消费者** | **模型 · 工具 · 拓展点**，三个角色的一个或多个 |

> **工具和拓展点也读它**，这不是附带的——**runtime context 从来不只是"给模型的上下文"**。

### meta runtime context

**每个会话都必需携带、并且必需持续更新的那些 [runtime context](#runtime-context)。**

**它与[会话运行模式](#会话运行模式)、与装配无关**：不论装的是哪一份定义、
配了什么工具、跑在什么模式下，**这一批一样都不能少**。

> **和 [meta capabilities](../PF-007-meta-capabilities/design.md) 是同一个道理**：
> 那边是**每个 agent 必不可少的能力**，这边是**每个会话必不可少的感知**。
> **两边都不可禁用、不可替换。**

**哪些够得上「meta」，只有一条判据**（见 [§5.5](#55-哪些算-meta-runtime-context)）。

### 会话的三个模式维度

会话中的模式分三个正交维度，各自回答不同问题，**都允许在运行时改变**。

| 维度 | 回答什么 | 当前取值与归属 |
|---|---|---|
| **权限维度** | 到了本该请求授权的环节，怎样处置 | 本文的[会话运行模式](#会话运行模式)：`never`、`auto_permission`、`bypass-permissions` |
| **执行环境维度** | 工具的作用落在哪里 | [PF-005 执行环境权限](../PF-005-execution-environments-and-sandboxes/design.md#执行环境权限)：`always-allow`、`auto_place`、`never-allow`；仍按工具分别配值、每次执行求落点 |
| **协作维度** | 人与 agent 怎样推进工作 | [会话协作模式](#会话协作模式)：`co-work`、`auto-drive` |

切换其中一维，不自动改写另外两维。`auto-drive` 可以与需要询问授权的权限模式、隔离执行环境同时存在；`co-work` 也不自动改成禁止执行或只读。
执行环境维度仍沿 PF-005 的逐工具粒度，不因放在这张表里变成全会话只有一个落点。

### 会话运行模式

本词专指上表的**权限维度**，不是全部模式的统称；它是运行时可变的。

**这个会话里，「本该问人」的那一刻改怎么办。**

**恰好三档：**

| 取值 | 本该问人的那一刻 |
|---|---|
| **`never`** | **一律当作被拒**，**不问任何人** |
| **`auto_permission`** | **拿已经形成的[授权表达](../PF-007-meta-capabilities/design.md#一笔授权表达有三个维度)算**；算得出就照算出来的办，**算不出来就问人** |
| **`bypass-permissions`** | **直接放行** |

**三档管的是同一件很窄的事**：

> **它不决定哪些动作要问人，只决定「本该问人的那些，改怎么办」。**

「要不要问」由[权限设置](../PF-002-assets-settings-and-permissions/design.md#52-设置与权限是资产的两种属性)
与[会话授权上下文](../PF-007-meta-capabilities/design.md#会话授权上下文)算出来；
**模式接手的是问不成的那一刻**（[完整的四步见 PF-007](../PF-007-meta-capabilities/design.md#56-一次放行判断走四步)）。

**`auto_permission` 是有闭环的那一档**：问人的答案**落成新的授权表达**，
进[本会话那份语义授权](#56-十四项-meta-runtime-context)——**下一次同样的事就算得出来了**。
**「同一件事不必问第二遍」不是另一条规则，就是这个闭环。**

> **这一档特意不叫 `auto`。**
> [上游有一个同名档，语义是「不问人、改问模型」](../../../research/agent-harness-session-design/research.md)，
> **而我们这一档从不替人做判断**——它只算已有的记录，算不出来就把问题**交回给人**。
> 名字里带上 `permission`，是为了让它与**执行环境那一维的 `auto_place`** 分得开：
> **一个决定「准不准」，一个决定「落在哪」。**
> **`never` 与 `bypass-permissions` 两档则与上游同义。**

**`never` 有一个连带后果**：
[`Ask().request_approval` 在这个会话里不可用](../PF-007-meta-capabilities/design.md#57-权限能关掉一条命令关不掉一扇门)——
**这扇门还在**，但这条命令用不了，**而且 agent 看得见它为什么用不了**。

### 会话协作模式

沿[会话协作模式](../../ubiquitous_language/terms/agent-runtime-loop.md#ul-session-collaboration-mode--会话协作模式--session-collaboration-mode)。它是会话运行期的属性，用来明确工作以怎样的协作方式推进。

| 取值 | 产品含义 | Ask() | 该模式附加的目标完成检查 |
|---|---|---|---|
| **`co-work`** | 强调人与 agent 的协作共创，共同形成理解、方向与工作成果 | 开启，仍受权限模式对具体命令的限制 | 不启用 |
| **`auto-drive`** | 强调目标导向，由 agent 主动推进工作，围绕目标开展自驱执行 | 关闭 | 启用，防止目标尚未完成时 agent loop 正常收束 |

**协作模式可以在同一个会话运行期间切换**，不要求为另一种协作方式新建会话或另选 AgentDefinition，也不改变会话的用途类型、身份与历史。
当前模式须让 agent 感知；它进入[会话元信息](#56-十四项-meta-runtime-context)，变更感知沿 §6.8，恢复沿 §5.8。

协作模式本身不授予工具权限、不选择宿主机或沙箱，也不扩大装配出的能力名单；所选模式仍在既有能力与权限边界内工作。
`auto-drive` 不等于跳过人的授权，`co-work` 不因这个名称就被规定为只讨论、不执行。
产品侧以 **Ask() 的开关与目标完成检查是否启用** 表达两种模式的行为差别，不另定计划审批阶段或协作工作流。Ask() 的关闭是当前协作模式下的人交互能力关闭，**不删除、替换或解除必需的 meta 资产绑定**；开启也不能解除权限模式对其命令的限制。
目标完成检查通过拓展件承接；具体怎样检查、挂在哪个拓展位置、运行期如何装卸与切换，以及如何处理进行中的调用，交技术设计，不在产品侧规定算法或时序。

检查约束的是目标未完成时的**正常收束**；既有用户停止、取消、失败与权限边界继续成立，不能因此无限续跑或假报成功。
切到 co-work 取消的是协作模式附加的检查；[作业会话](../PF-021-schedule-and-calendar/design.md#作业会话)自身强制要求的目标完成检查仍须成立。技术侧可以复用检查实现，不能丢失任一产品要求。
初始协作模式在未显式指定时取租户设置的默认值；初始化之后成为本会话的值，见 [§6.17](#617-默认值会话值与共享修改)。

## 五、模型

### 5.1 四个状态怎么走

```text
                        ┌──────────────────┐
     建立 ─────────────→│  创建 / 初始化   │
                        └────────┬─────────┘
                                 │  按「最新的运行完结没有」落位
                     ┌───────────┴───────────┐
                     ↓                       ↓
              ┌─────────────┐         ┌─────────────┐
              │ 运行 / 活跃 │ ←─────→ │    休眠     │
              └──────┬──────┘         └──────┬──────┘
                     │                       │
                     └───────────┬───────────┘
                                 ↓  归档
                        ┌──────────────────┐
                        │      归档        │
                        └────────┬─────────┘
                                 │  撤销归档
                                 ↓
                              休眠
```

**三件事要读出来：**

- **运行与休眠之间的往返没有上限**，来回多少次都不构成终结。
- **归档是唯一的出口，而它有回头路**——但回来落在**休眠**，不落在运行。
  归档的时候在跑的东西已经被中断了，**不存在「还没完结的最新运行」把它顶到运行态**。
- **没有第五个状态。**没有删除，没有过期，没有回收。

### 5.2 会话与会话之间

会话有[主会话与子会话两种性质](../../ubiquitous_language/terms/agent-runtime-loop.md#ul-primary-session--主会话--primary-session)，
关系与通信拓扑由 [UL-D-4](../../ubiquitous_language/decisions.md#ul-d-4--主会话与子会话--2026-09-21) 定，
本节只定**生命周期在这层关系上怎么传导**：

```text
      主会话 A                          主会话 B
         │                                 │
    ┌────┴────┐                       （彼此独立，
    ↓         ↓                     谁归档都不影响对方）
  子会话 A1  子会话 A2
    │
    ↓
  子会话 A1a
```

| 发生什么 | 传导到哪 |
|---|---|
| **A 被归档** | **A1、A2、A1a 全部级联被归档**——沿子会话关系一路到底，不看层级深浅 |
| **A1 被归档** | **只到 A1a**。**A 不受影响**，它还在跑自己的 |
| **A 撤销归档** | **只有 A 回来。**A1、A2、A1a 保持归档 |
| **B 被归档** | **与 A 这一支毫无关系** |

> **归档只往下传，不往上传。**一个子会话收尾，不意味着派它出去的那段协作也收尾了。

### 5.3 会话类型怎么算出来

[属性的定义归 PF-004](../PF-004-agent-definition-and-assembly/design.md#agent-类型)，本节只定那条映射。

```text
 用户挑一个 AgentDefinition
            │
            ↓
   读它的 agent 类型与类目          ← 属性归 PF-004 §4
            │
            ↓
     算出这个会话的类型             ← 建立时算一次，此后不变
```

**关键是「算」这个字。**会话类型**不是**在 AgentDefinition 上绑死的一个字段的副本——
两者之间是一条**映射关系**，而映射关系可以改。改了之后：

- **新建的会话按新映射算**；
- **已经存在的会话保持原样**，一个都不跟着变。

### 5.4 会话内的授权，与生命周期的交界

**授权的完整模型归 [PF-007 §4](../PF-007-meta-capabilities/design.md#会话授权上下文)**，
本节只定生命周期在这件事上的边界：

> **授权是数据，不是活物。**一个会话里用户表达过的授权，
> **归档不会让它消失**，撤销归档之后它原样还在。

**这条与上面那三项「不可逆」是分开的两件事，不能互相代替：**

| | 归档对它做什么 |
|---|---|
| **在途的工作**（工具执行、模型响应、子会话） | 工具执行与模型响应**被中断**，子会话被级联归档；都不可逆 |
| **已经表达过的授权** | **什么都不做**。它是[会话日志](../../ubiquitous_language/terms/record-and-context.md#ul-session-log--会话日志--session-log)那一侧的事实 |

> **「在途的工作停了」推不出「授权也没了」。**两者的生效点、在途政策与完成条件各不相同，
> 写在同一句话里，到了定契约那一步就再也拆不开。

### 5.5 哪些算 meta runtime context

**只有一条判据：**

> **它在 [agent loop](../PF-012-agent-loop-and-run/design.md#agent-loop) 内，
> 被模型、工具、拓展点这三个角色之一消费——依赖它。**

**判的是消费，不是别的。**不看它是表单还是实时算出来的，
不看它归谁维护，也不看它有多重要。

**两个反例，各说明一件事：**

| 不是它 | 为什么 |
|---|---|
| [**模态投影**](../PF-013-model-profiles-and-invocation/design.md#模态投影) | 它**确实是会话要维护的一项状态**——但那是**会话提供给会话外的服务用的**，**会话内的三个角色都不消费它** |
| [**当下可用性**](../../ubiquitous_language/terms/reach-and-availability.md#ul-current-availability--当下可用性--current-availability) | **消费它的是 runtime 本身**。它在[组装](../PF-010-context-management-and-assembly/design.md)那一步被算出来，直接把用不了的工具与技能**替换成一句说明（标识不变）**——**三个角色看到的是那句说明，不是这份数据** |

> **「会话要维护的状态」与 runtime context 是两个圈，有交集但不重合。**
> 前者还包含**会话对外提供的投影**，那一部分不在这里。
> **不写死这一条，这份清单会一路膨胀成「会话身上所有的东西」。**

### 5.6 十四项 meta runtime context

**† 标记的那几格是 PM 推导**，推理链在 [decisions](decisions.md#二pm-推导)，**可以被逐条推翻**。

| # | 这一块 | 生产者 | 消费者 | 至少提供什么 |
|---|---|---|---|---|
| **1** | **会话的元信息** | 创建会话的那个东西 | 三个角色 | 会话的身份标识 · 创建时间 · [会话类型](#会话类型) · 会话日志版本号 · 会话运行模式（权限维度）· 会话协作模式。**包括但不限于这些** |
| **2** | **租户、及其所属组织的元信息** | 租户子系统或服务 | 三个角色 | 租户身份标识 · 名称（**用户名、昵称、别名都有可能**）· 组织内角色 · 所属组织的身份标识 · 租户创建时间 · 组织创建时间 |
| **3** | **账号级的界面偏好**——[个人 context](../PF-001-identity-scope-and-agent-constraints/design.md#contextagent-运行时可感知的上下文信息) 里被 agent 感知的那几项，由账号承载、换组织不变；会话通过它持有的租户身份找到背后那个账号取到 | 会话外的一个东西 | 三个角色 | 语言 · 时区 · 地区 · 明暗风格一类。**不会所有的都有** |

| **5** | **操作系统的元信息** | 能取到操作系统信息的那个东西 | 三个角色 | 操作系统类型与版本 · **当前日期**（**不精确到时、分**） |
| **6** | **会话当前使用的 ModelProfile** | **会话本身** † | 三个角色 † | 那一份 [ModelProfile](../PF-013-model-profiles-and-invocation/design.md) 的内容 |
| **7** | **会话当前使用的 ContextCompactionSettings** | **会话本身** † | **模型** | 那一份设置的内容 |
| **8** | **组织与租户各自的授权** | 租户子系统或服务 | **只有拓展点** | **完整的**——拿到哪些就包含哪些。**两级分开、结构化，不经解析合并计算**。**[作用域为「全局」的授权表达落成的租户层权限值，就在这一份里](../PF-007-meta-capabilities/design.md#一笔授权表达有三个维度)** |
| **9** | **这个租户的语义授权（本会话中识别到并记录的）** | **本会话里的一个判断拓展点**，往本会话的存储记录 | **模型** · **拓展点** | 授权或撤回表达、所针对的动作与范围、单次／本会话作用域、先后关系及来源；全局授权沿第 8 项取得。它是判断依据，不是缓存的最终放行结论；不把第 8 项仅供拓展点读取的完整结构化授权复制给模型 |
| **10** | **本会话选定的[工作区](../PF-020-workspace/README.md)** | 创建会话的那个服务 | 三个角色 | 选定的逻辑工作区及使用的地址或实例入口，**可以是空**，可表达同一工作区下多个 worktree 的分工（[创建时没指定就是空](#613-工作区在创建时显式指定不指定就是空)）。工作区资源由可访问实例提供；具体装载状态归 PF-020 |
| **11** | **会话当前后台未结束的工具执行** | **会话本身** † | 三个角色 † | 能指认是哪次执行、在做什么、当前状态，以及如何查询或控制该执行；若正在等应答，能辨认正在等什么。只展示该执行实际已知的信息，不虚构进度或完成时间 |
| **12** | **会话当前持有的、未被归档的子会话** | **会话本身** † | 三个角色 † | 能指认哪个子会话、与本会话的关系、受派任务及当前会话／运行状态；报告是否已交与会话是否仍可交互分别表达。进一步查询与操作沿既有会话关系和权限 |
| **13** | **会话当前未完成的待办** | **会话本身** † | 三个角色 † | 能指认是哪一项、要做什么及当前未完成状态，足以沿待办能力查询和更新它。期限、优先级、跨会话目标等未承诺属性不作为必需内容 |
| **14** | **当前上下文长度占模型窗口的百分比** | **实时算**，不由谁维护 | **模型** | 那个百分比 |

**这张表里有六件事要单独读出来：**

- **第 4 条：agent 的身份标识恒等于会话的身份标识。**
  会话与 agent 是**一对一**的，而[同一时刻至多一个活跃的 agent runtime](../../ubiquitous_language/terms/agent-runtime-loop.md#ul-single-active-execution--会话内单活跃--single-active-execution)——
  **所以换了一个 agent runtime，这个标识也不变**。
  **它是产品层的承诺**：agent 之间互相寻址靠的就是它。
- **第 8 条的消费者里没有模型。**授权怎么合成是[拓展点实时算](../PF-007-meta-capabilities/design.md#会话授权上下文)的事，
  **模型不需要看见原始的分层授权**——它只需要知道**结果**。
- **作用域为「全局」的那一档不另占一块。**用户说的「以后所有会话都这样」
  **落成[租户层的权限设置值](../PF-002-assets-settings-and-permissions/design.md#52-设置与权限是资产的两种属性)**，
  [落点由 PF-007 定](../PF-007-meta-capabilities/design.md#一笔授权表达有三个维度)，**因此它随第 8 条那份结构化授权一起进来**，
  在[放行判断的第 ③ 步与本会话那份流水一起算](../PF-007-meta-capabilities/design.md#56-一次放行判断走四步)。
  **系统里的授权流水只有一种：每个会话一份**——第 9 条就是它在这张表里的那一面。
- **第 8、第 9 条的主体是[租户](../PF-001-identity-scope-and-agent-constraints/design.md#租户)，不是自然人那个账号。**
  [授权的「全局」一档管的是「这个租户下未来所有会话」](../PF-007-meta-capabilities/design.md#会话授权上下文)——
  **同一个自然人在另一个组织下是另一个租户，他在这边说过的话不跟过去。**
  场景里写「用户」是在说**坐在会话里的那个人**；**这两块数据归属于他此刻所在的那个租户**。
- **第 10 条可以是空，也可以变。**空就是[这一级什么都不加载](../PF-002-assets-settings-and-permissions/design.md#它是会话选用的不指定就是空)；
  它不是会话建起来就钉死的一项，换了一份就是[装配输入变了](../PF-004-agent-definition-and-assembly/design.md#装配)。
- **第 7 与第 14 条是一对，缺一个另一个就没用。**
  模型同时看得见**当前占了多少**与**压缩会怎么压**，才谈得上
  **自己判断要不要主动发起一次[压缩](../PF-010-context-management-and-assembly/design.md)**。
  **只给占用比，它不知道压了会失去什么；只给压缩策略，它不知道该不该压。**

### 5.7 三个作用域在同一份数据里

[授权有三个作用域](../PF-007-meta-capabilities/design.md#会话授权上下文)——
**单次执行 · 本会话 · 全局**。**作用域是同一份数据上的一个维度，不是三套各自的存法**：

> **授权相关的 runtime context，其数据本身就要能表示出
> 「单次 / 本会话 / 全局（always on）」的区别。**

**分得出这三者，正是为了知道这一笔该落到哪里**：

| 作用域 | 落在哪 |
|---|---|
| **单次执行** · **本会话** | **[第 9 条那份本会话的授权流水](#56-十四项-meta-runtime-context)**——**「单次执行」不另起一块** |
| **全局** | **不落在这块数据里。**它[落成租户层的权限设置值](../PF-007-meta-capabilities/design.md#一笔授权表达有三个维度)，随[第 8 条那份结构化授权](#56-十四项-meta-runtime-context)进来 |

> **系统里的授权流水只有一种：每个会话一份。**
> 没有第二份「全局的流水」——**一句管到未来所有会话的话，
> 管的本来就不是这个会话**，把它留在会话里，别的会话读不到它。

**单次那一档因此有明确的清除时机**：
**一次[运行](../../ubiquitous_language/terms/agent-runtime-loop.md#ul-run--运行--run)明确结束的时候，把单次授权清空**——
落点是 [loop 上「落终态之后」那个位置](../PF-012-agent-loop-and-run/design.md#十一个位置是推出来的不是挑出来的)。

> **不给它一个清除时机，「单次」这个词就是假的**——
> 它会一直留在那儿，而没有人知道它本该在上一次运行结束时就没了。

### 5.8 存储要守住的两件事

**产品层面对存储只提两条**，其余归技术设计。

#### 第一件：会话睡一觉醒来，还得是原来那个

**三样东西各有各的守法：**

| 什么 | 怎么守 | 谁定的 |
|---|---|---|
| [**会话日志**](../../ubiquitous_language/terms/record-and-context.md#ul-session-log--会话日志--session-log) | **只增不改，没有例外** | [PF-012 §4](../PF-012-agent-loop-and-run/design.md#会话日志)**已经定死**，本 topic 只是要求**存储真的兑现它**，而不是把它当成一句约定 |
| [**runtime context**](#runtime-context) | **除了实时算的那些，每一块都要能恢复** | **本 topic** |
| [**会话日志投影**](../../ubiquitous_language/terms/record-and-context.md#ul-session-log-projection--会话日志投影--session-log-projection) | **从日志重算一遍，必得同一个答案** | **本 topic** |

**判据是两个具体动作**：**会话被重新加载**、**归档被撤销**。
这两件事之后，会话身份、会话自有取值、注册声明与已发生事实必须恢复；[三个角色](#55-哪些算-meta-runtime-context)在输入未变时得到同样结果。按规则热重载的定义内容、共享配置及实时条件可以变化，不把历史快照冒充当下状态。

> **不然那就不是同一个会话了**，而[会话不会消失](#61-会话不会消失)这条承诺也就落了空——
> **会话还在、却记不得自己是谁，跟消失没有区别。**

**实时算的那些不在此列。**它们本来每次都现算——
[上下文占用比](#56-十四项-meta-runtime-context)、[当下可用性](../../ubiquitous_language/terms/reach-and-availability.md#ul-current-availability--当下可用性--current-availability)——
**对它们来说根本没有「恢复」这回事**。

**投影需要持久化来支持直接读取当前状态。**除[模态投影](../PF-013-model-profiles-and-invocation/design.md#模态投影)，还有当前 Run、待处理输入、等待事项、待办、后台执行与成本等按需维护的投影。投影不拥有独立事实；由日志派生的投影须能从同一段日志重建出同一结果。结合外部来源取得的当前值须标明来源，不能冒充仅从日志派生的投影。

持久化的判据、查询要求与三类 runtime 输入归 [§6.19](#619-从函数输入确定持久化范围)。会话级设置及 context 注册也要恢复，不把会话日志当作唯一一种允许持久化的数据。

> **所以从第一天起，「怎么从日志算出一个投影」就得是一套协议，
> 而不是为模态投影单独写的那一段。**

**判据很直白**：**加第二个、第三个投影的时候，已有的那个不用改。**

#### 第二件：今天是单机，但别把单机焊进语义

[SYS-DEPLOY](../../foundation/cross-system-constraints/requirements.md) 已经定了
第一版是单机，**而边界要清晰到将来能扩展成分布式、异构节点与微服务化，且不改变领域语义**。
**落到存储这件事上，产品侧只认一条：**

> **存储在产品语义上是什么，不取决于它实际存在哪里。**

「会话日志是一份只增不改的流水账」这句话，**在单机和分布式下含义必须完全相同**。
产品设计或契约里一旦出现「因为都在一台机器上，所以……」这种推理，
**那就是把部署形态写进了语义**。

**这条现在不要求做任何分布式设施**，它只约束一件事：

> **将来换一套存储实现的时候，不该回过头来推翻[架构内核](../architecture-core.md)。**

## 六、产品规则

### 6.1 会话不会消失

**系统不提供删除会话的能力，任何角色都不提供。**
一个会话一旦建立，它的身份与历史就一直在——**能做的只是把它收起来**。

**因此「会话结束」这个说法在本系统里不成立。**要表达「这段协作到此为止」，
**说的是归档**。

### 6.2 归档有两条来路：人手动，或到期自动

| 来路 | 谁 |
|---|---|
| **手动归档** | **租户**——会话归它，收不收起来由它说了算 |
| **自动归档** | **系统按一个时限自动收**，那个时限是**出厂配置**，**默认 30 天** |

**时限按连续空闲计算，不按会话创建时间计龄。**会话及本次归档会级联影响的子会话均没有未结束 Run，也没有活跃的 Model runtime 或 Tool runtime，且无待处理任务时，才开始累计这段空闲时间；等待应答的 Run、后台工具执行和 Run 外模型调用都使它不满足空闲条件。新任务被受理或重新开展工作即结束这段计时，工作全部收束后重新计时；初始化完成且从未开展工作的会话，从满足空闲条件时开始计时。单纯查看历史或刷新投影不算开展工作。

到达时限时仍须满足空闲条件才自动归档，不能让计时与新工作同时发生时误中断新工作。撤销归档后从撤销时刻重新计时。计时依据须可持久恢复，重启、休眠或 Agent runtime 重装配不把已经累计的空闲时间清零；计时实现归技术设计。

**自动归档与手动归档的后果完全一样**：
[三件事照样连带发生](#63-归档先停活儿再落状态)，**也照样可以撤销**。
**没有「系统归的档比较轻」这回事。**

> **那条时限是出厂配置，不是每个会话各设一个。**
> 它是一条产品默认值，**改它是改产品的出厂设定**。

> **注意[会话级沙箱到点销毁是另一回事](../PF-005-execution-environments-and-sandboxes/design.md#63-会话级沙箱到点销毁数据不留存)。**
> 那挂的是**沙箱自己的最大连续存活时间**，**那一节同时明写「会话可以无限期存在」**——
> **沙箱没了，会话照活**；两条时限管的不是同一样东西，也不必一致。

### 6.3 归档先停活儿，再落状态

归档一个会话，**在它落成归档状态之前**，下面三件事全部发生：

1. 它的**子会话**依次被归档（递归到底）；
2. 它名下**未完成的工具执行**被中断；
3. 它名下**正在进行的模型响应**被中断。

**这三件事都是「停下」，不是「回滚」。**
工具执行的收场是 [PF-006 六种收场](../PF-006-tools-and-skills/design.md#55-一次工具执行的收场有六种)里的**被中断**——
不论它在前台还是已转后台，[都不算失败](../PF-006-tools-and-skills/design.md#65-工具执行有自己的运行时绑定在-session-上)。
工具已经在外面造成的效果不会被撤销——
[外部输出不因为被系统调用就变得可逆](../PF-006-tools-and-skills/design.md#67-用户可以中断而中断不是失败)。

**归档同时了结尚未处理的任务。**已受理、尚未被 Run 承接的任务取消待处理资格，保留原消息与“因归档取消”的记录；不把取消伪装成已经处理，也不删除历史。归档期间拒绝新的任务输入并明确告知发送方，父子会话通信同样适用；不能暗中排队或自动撤销归档。

已经发起的模型／工具执行所产生的迟到结果与账目仍按原归属保存，不属于新任务输入，不因拒收规则丢失，归档期间只作为历史与执行事实记录，不取得待处理资格；撤销归档也不将这些事实自动入队。取消事实须参与队列投影，恢复或撤销归档后不会把已取消的任务重新排回队列。

### 6.4 撤销归档只还给你状态

**撤销归档之后，会话回到休眠，历史一条不少，空闲归档计时重新开始。**已取消的待处理任务不恢复；用户若仍要做它，须明确重新发起新的任务输入。

**但它不重启任何东西**：被中断的工具执行不续、被中断的模型响应不续、
被级联归档的子会话不跟着回来。**要哪个子会话，就去撤销哪个子会话的归档。**

### 6.5 会话类型不改变任何放行判断

**会话类型是一个用途标识，不是一道闸门。**
它**不参与**[放行三元组](../PF-007-meta-capabilities/design.md#611-ask通向人)，
也不收窄任何[权限](../PF-002-assets-settings-and-permissions/design.md#52-设置与权限是资产的两种属性)。

> **一个 `coding` 会话不会因为类型就做不了别的事。**
> 类型只用来判断「用户此刻聊的，和这个会话本来是干什么的，对不对得上」。

### 6.6 跑题只提醒，不阻拦

用户往一个会话里发的话，**若与这个会话的类型明显对不上**，
系统在这次请求落定之前把它**拦住并提醒**，由用户确认是否仍然要在这里聊。

**必须守住的五条：**

- **提醒是提醒，不是拒绝。**用户确认之后照常进行，**一次都不会被真正拦掉**。
- **被拦住的这一次不落任何痕迹。**它没有进队列，
  [没有被受理](../../ubiquitous_language/terms/interaction-and-dispatch.md#ul-inbound-arrival--入站到达--inbound-arrival)，
  **会话日志上什么都没有发生**。
- **系统不持有它。**用户确认之后发生的是**全新的一次请求**，不是把刚才那份取出来接着走。
- **用户不确认也不会有任何后果。**没有待办、没有草稿、没有超时——**什么都没有留下**。
- **这个提醒可以关掉。**不想要就关了，**关掉之后一次都不拦**。

> **为什么要拦而不是事后提示**：用户可能只是岔出去问一句，聊完就回正轨，
> **这种情况下开新会话反而添乱**。把选择权交回给他，而且要在他改主意还来得及的时候交。

#### 判定是二分的，没有第三档

**探测只给两个答案：对得上，或者对不上。**
**系统不设「不确定」这一档**——它不会把「我拿不准」这件事丢回给用户，
**因为那等于用一次打断换一个它自己也没有的答案**。

**这一档之所以不需要，是因为[提醒从不拦死](#66-跑题只提醒不阻拦)：**
判成「对不上」的最坏后果，是用户多点一下确认；
判成「对得上」的最坏后果，是这次没提醒。**两个方向都没有不可挽回的代价**，
所以不必为拿不准的情形另开一条路。

### 6.7 归档不动授权

**一个会话被归档，它里面已经表达过的授权一条都不变。**
撤销归档之后，那些授权原样还在，**不需要用户重新说一遍**。

**要收回一笔授权，走的是撤回，不是归档。**两条路互不替代——
[撤回怎么做归 PF-007](../PF-007-meta-capabilities/design.md#会话授权上下文)。

### 6.8 变更了要不要告诉 agent，看谁消费它

[runtime context](#runtime-context) 是**就地更新**的——**它不像日志那样自己会说话**。
所以变更之后：

| 这一块的消费者里 | 变更时 |
|---|---|
| **有模型** | **追加一条[系统提醒](../PF-009-context-message-types/design.md)**，让它知道这块变了 |
| **只有工具和拓展点** | **什么都不发。**那本来就不是给 agent 看的 |

> **通知的依据是「谁消费它」，不是「它重不重要」。**
> 给模型发一条它用不上的提醒，是在花它的注意力买没有的东西——
> **而注意力是这个系统里最贵的东西**。

**会话感知这类变更有两条路，而这条规则只管其中一条：**

| 路 | 谁发起 | 什么时候 |
|---|---|---|
| **推** | **那一块的生产者** | 它变了的时候。**[只在这个会话还有运行没闭合的时候才进得来](../PF-014-inbound-intake-and-queueing/design.md#610-注入的上下文变了没有运行在跑时什么都不做)**；会话空闲时推来的**一律丢弃** |
| **拉** | [agent runtime](../PF-012-agent-loop-and-run/design.md#agent-runtime) 自己 | **每一次[执行尝试](../PF-012-agent-loop-and-run/design.md#执行尝试)起来时取一次当前快照**（[PF-012 §5.7 四件事之一](../PF-012-agent-loop-and-run/design.md#每一次尝试开始都要做四件事)） |

> **两条路合起来才兑现「持续更新」。**
> 只有推，会话空闲那一段的变化就永远到不了；只有拉，运行中变的东西要等到下一次尝试才被看见。
> **而空闲期间丢掉的那些不必补**：下一次拉到的就是当前值，
> **那条状态提醒的前值取会话日志里最后感知到的那一份**——
> **[因果链记的是这个会话感知到的变化，不是世界上发生过的每一步](../PF-014-inbound-intake-and-queueing/design.md#610-注入的上下文变了没有运行在跑时什么都不做)。**

这条通知规则针对已加载的 runtime context 数据发生变化，不要求远端文件或 Git 仓库一变就即时同步、通知。工作区内容可由用户告知或 agent 按需读取、同步；资产文件变更须经实际装配或显式 reload 才进入装配数据。组织工作区参与限制也只在实际装配时重判，不由这里的快照读取扩大为运行中热同步。

### 6.9 模型看见一块 runtime context，只有两种形态

| 形态 | 什么时候 |
|---|---|
| **完整的那一份** | **会话刚开始**，以及**[上下文被压缩之后](../PF-010-context-management-and-assembly/design.md)** |
| **一条变更通知** | 这一块变了（§6.8） |

**第二种依赖第一种。**只发变更通知、从不发全量，
**模型就只能靠消息历史把当前状态拼出来**——
而[消息会被压缩、会被裁剪](../PF-010-context-management-and-assembly/design.md)，
**拼出来的那一份迟早与真的对不上**。

> **所以「压缩之后要重新给一份完整的」不是补偿措施，是这套机制成立的前提。**
> 这一条对[压缩那一侧](../PF-010-context-management-and-assembly/design.md)是硬要求：
> **meta runtime context 不能只当消息处理。**

### 6.10 单次授权在一次运行结束时清空

**在一次运行明确结束的时候，把作用域为「单次执行」的那些授权清空。**

**落点是 [loop 上「落终态之后」那个位置](../PF-012-agent-loop-and-run/design.md#十一个位置是推出来的不是挑出来的)**——
**不必新开位置**：那一处本来就开着，[用途写的就是「归档、通知、结算」这一类收尾动作](../PF-012-agent-loop-and-run/design.md#十一个位置是推出来的不是挑出来的)。

**「明确结束」用的是[运行终态](../../ubiquitous_language/terms/agent-runtime-loop.md#ul-run-terminal-state--运行终态--run-terminal-state)那三个**——
完成、失败、被取消，**三种都清**。

> **被取消也要清。**一次运行没跑完，不代表用户当时给的那句「这次可以」还能留到下一次用。
> **留着比丢了危险得多。**

### 6.11 会话睡醒之后，还是原来那个

**会话被重新加载、归档被撤销之后，
在同样的确定输入下，[三个角色](#55-哪些算-meta-runtime-context)取得同样结果；会话自有设置和注册恢复，实时条件及允许热重载的输入按 [§6.19](#619-从函数输入确定持久化范围)重新取得。**

落到三样上：[会话日志](../../ubiquitous_language/terms/record-and-context.md#ul-session-log--会话日志--session-log)**一条不少**
（它本来就只增不改）、**每一块不是实时算的 [runtime context](#runtime-context) 都还在**、
[投影](../../ubiquitous_language/terms/record-and-context.md#ul-session-log-projection--会话日志投影--session-log-projection)**重算得到同一个答案**。

**实时算的那些不算数**——它们没有「恢复」这回事，[判据在 §5.8](#58-存储要守住的两件事)。

> **这一条是 [6.1 会话不会消失](#61-会话不会消失)的下半句。**
> **只保住那条记录、却让它醒来时认不得自己，等于没保住。**

### 6.12 会话持有创建那一刻的租户身份

**会话在创建时捕获并持有[创建那一刻的那个租户身份](../PF-001-identity-scope-and-agent-constraints/design.md#当前租户身份)，
此后一切以它计，不随这个账号切换到别的租户身份而变**（依据
[PF-001 §4 当前租户身份](../PF-001-identity-scope-and-agent-constraints/design.md#当前租户身份)）。
**那个租户身份失效时的收场按本 topic 自己的规则**——会话[不会消失](#61-会话不会消失)，
能发生的只有[归档](#会话归档)。

### 6.13 工作区在创建时显式指定，不指定就是空

**创建会话时，[工作区](../PF-020-workspace/README.md)是一项显式的、可以不给的输入。**

- **不给，会话就没有工作区**：[那一级为空，装配什么都不加载](../PF-002-assets-settings-and-permissions/design.md#它是会话选用的不指定就是空)。
  **系统不替会话猜一份**——不按 agent 所在的目录、不按上一个会话用过的那份。
- **给了，须按[本会话的租户身份](#612-会话持有创建那一刻的租户身份)具备有效租户—工作区关系及相应访问资格**。治理所有者与获准参与者都可选用；实例本身不固定绑定一个租户。请求附着却无资格或装载失败时明确失败，不静默建成工作区层为空的会话。
- 可附着已经存在的实例，也可指定本地路径，先装载目标工作区、再创建会话。已有但尚未登记的目录，须显式选择“作为工作区使用”后建立并向中心同步关系；这一步不自动上传资源。
- 同一实例可跨租户共用，各会话分别求值；同一会话可组织同一工作区的多个 Git worktree 供不同 subagent 并行工作。创建 Git worktree 本身不登记实例或新工作区，显式使用时才关联。
- 会话结束或归档不删除工作区和实例。关系解除或中心销毁后的后续附着沿 [PF-020](../PF-020-workspace/design.md#治理关系解除与中心销毁)：未重新显式登记前按普通目录使用，残留命名空间不贡献装配。
- 挂上的工作区及实际选用的实例入口记在 [meta runtime context 第 10 条](#56-十四项-meta-runtime-context)；
  它的内容怎么在装配时进来归 [PF-004](../PF-004-agent-definition-and-assembly/design.md#装配)。

> **为什么是 opt-in**：那一级的内容可能来自工作区地址或实例上随代码提供的资源；
> 隐式挂上等于隐式吃进一份配置。**用户说了才有，不说就没有。**

### 6.14 AGENTS.md 的上下文加载

AGENTS.md 按社区通用规范作为 runtime context 支持；嵌套子目录的文件在所在目录首次被访问时加载。它不属于 `.omne`/`.omne.local` 的资产目录，不套用资产的嵌套路径登记、兼容来源开关或显式资产 reload 规则。具体采用的规范版本、首次访问判据及上下文处理协议由 runtime context 规格核实与细化，不另增加专属工作区说明文件。

可观察结果：未访问子目录时不因资产发现而预先载入其 AGENTS.md；首次访问时加载相应上下文。工作区文件更新本身不等于全部资源立即进入模型上下文。

### 6.15 三个模式维度独立变化

- 三个维度允许运行时改变；某一维发生变化，不自动替用户改变其他维度的取值。
- 权限判断继续沿 PF-007；执行环境仍按 PF-005 逐工具、逐次求值；协作模式决定协作方式，不替代前两者。
- 切换协作模式保持会话身份、用途类型与已有记录；仅切换该属性不改变 AgentDefinition 的能力继承声明或必需绑定。
- 协作模式属于可恢复的会话元信息；运行中的变更应让模型感知，空闲期间的变更在下次尝试读取当前快照。切换必须落实上表对应的 Ask() 开关与模式附加检查；装卸、生效时序和在途衔接归技术设计，不能把上下文通知当作对已发动作的撤销。

本轮已确定边界的验收场景：

| 场景 | 应当看到什么 |
|---|---|
| 改变协作模式，权限和执行环境配置未改 | 后两者不随之切换；既有放行与落点规则继续成立 |
| auto-drive 中遇到既有权限规则要求询问的动作 | 仍按所选权限模式处置，不以自驱执行为由直接放行 |
| co-work 下某个动作原本被权限允许 | 不因 co-work 增加全局只读或禁止执行规则 |
| co-work 与 never 权限模式同时选中 | Ask() 的协作提问可用，request_approval 仍受 never 限制，不因 co-work 开启 Ask() 而恢复请示 |
| 进入 auto-drive | Ask() 关闭；目标未完成时不能按正常完成收束；权限与执行环境取值不变 |
| 返回 co-work | Ask() 重新开启并继续受权限模式限制；该协作模式附加的完成检查不再启用 |
| 作业会话切到 co-work | PF-021 要求的完成检查继续成立，不借模式切换取消作业的交付义务 |
| auto-drive 下用户明确停止工作 | 沿既有停止规则处置，不能以目标未完成为由拒绝停止 |
| 同一会话由 co-work 切到 auto-drive，或反向切换 | 会话身份、用途类型、历史及能力选择边界不因此改变 |
| 会话休眠后重新加载 | 恢复已选协作模式，不因重新起 runtime 静默回到某个默认值 |

### 6.16 会话组成与创建输入

创建输入、运行期可变性、变更作用域、持久化需要是不同维度。必须输入表示创建过程必须明确，不表示由人手填；派生或系统生成的部件不是调用方必填参数。首次执行可以晚于创建，创建会话不要求同时存在三类 runtime。

| 部件 | 创建时取得方式 | 运行期不变与可变 | 变更作用域 | 会话持久化内容 |
|---|---|---|---|---|
| 会话标识、创建时间、创建来源 | 系统生成或可信入口提供 | 固定 | 本会话 | 身份与创建事实 |
| 租户身份 | 必须，由有效身份上下文取得 | 所属租户固定；关联授权等可变 | 归属不随账号切换 | 身份引用 |
| AgentDefinition | 必须明确身份；装配取得最新有效内容 | 身份固定，同身份内容可热重载；生效时点归 PF-004 | 采用状态属会话；修改共享定义影响其消费者 | 固定身份、各次实际采用的版本依据 |
| 会话执行类型及必需能力、extensions | 入口明确类型，从类型派生依赖 | 类型与类型必需身份集合固定，实现按规则可变 | 本会话要求；共享实现另算 | 类型、固定要求、实际绑定 |
| 用途分类 | 从创建时定义推导 | 固定 | 本会话 | 分类值 |
| 工作区及地址／实例入口 | 可选，不给就是空 | 可附着、更换、解除；不得借此更换定义身份 | 选择属会话；编辑工作区内容按工作区归属 | 当前选择、入口及变更事实 |
| 权限、执行环境、协作模式 | 可选显式初值；未给取租户默认；专用入口显式要求保留 | 三维各自可变 | 本会话 | 初值、当前值、变更事实 |
| 模型选择及模型参数 | 可选指定，否则按已有设置求值 | 可切换模型及允许调整的设置；有效模型逐请求确定 | 会话选择属会话；共享档案编辑另算 | 选择、覆盖／继承声明、请求采用依据 |
| Skill、Tool、MCP 已知身份、当前数据与实现 | 从类型、当前定义及作用域求值 | 身份合法纳入后保留；可用集合、数据及实现可变；移除可选项改为不可用，不绕过必需要求 | 会话采用属会话；共享资产修改另算 | 已知身份、合法采用数据与实现依据、当前状态、移除意图及采用事实 |
| loop extensions 实际装载 | 从类型、模式及已有装配规则派生 | 模式附加项可装卸；类型强制项保持；实现可更新 | 会话装载属会话 | 实际装载、配置及来源 |
| Runtime context 注册集合 | 必需项与允许的初始注册 | 可新增、移除非必需注册 | 本会话；不删除共享来源 | 注册声明、来源、配置、消费者 |
| Runtime context 内容 | 会话自有数据、共享来源或实时计算 | 固定身份值保持，其他允许的内容可变 | 依内容真实归属 | 自有数据、不可重算的恢复输入；外部引用与必要采用依据 |
| 其他会话级设置 | 可选覆盖或按各项规则求值 | 可覆盖项可变，受上级锁定约束 | 本会话覆盖不外溢 | 覆盖值、继承声明、必要来源依据 |
| 初始消息、任务、目标 | 普通会话可选；派发、Job 等入口条件性必需 | 原始输入保留，修订形成新事实 | 本会话；业务对象修改另算 | 输入、目标调整、结果关联 |
| 父子会话、派发、Job 关联 | 特定入口提供或系统生成 | 创建来源保持，集合及关联状态可演进；遵守各业务关系规则 | 对应会话与业务对象 | 关系事实、当前关系投影 |
| 生命周期、Run、执行尝试 | 系统初始化或执行时生成 | 身份与既有事实固定，当前状态推进 | 本会话 | 状态事实、当前投影 |
| 装配清单 | 求值生成 | 当前清单可更替；既有条目不改写，增量加载按 PF-004 追加 | 对应会话与执行 | 当前及实际采用清单、输入依据 |
| Agent／Model／Tool runtime | 按需装配与实例化 | 启停、释放、重建；三者生命周期归会话，Run 治理关联工作 | 对应会话与执行 | 执行关联、状态和结果，不存内存实例本身 |
| 沙箱等执行资源 | 按需取得或分配 | 可分配、释放、替换 | 按资源真实归属，可为会话、租户或共享范围 | 资源引用、归属、对账依据 |
| 会话事件、日志 | 系统建立，可含初始输入 | 历史只追加 | 本会话，内容可记载共享或外部修改 | 历史事实 |
| 状态投影 | 系统派生 | 随事实更新，可重建 | 投影的消费范围不改变事实归属 | 当前结果及对应来源进度／版本 |

三类 runtime 的装配结果不是创建会话的必填对象。类型要求、定义声明及继承规则归 PF-004；ModelProfile、工具执行、执行资源仍由各自 topic 定义。矩阵只收齐会话取得和保留它们的责任。

### 6.17 默认值、会话值与共享修改

[会话级设置](../../ubiquitous_language/terms/scope-and-resolution.md#ul-session-settings--会话级设置--session-settings)持久化之后仍只作用于本会话。三种模式创建时未明确指定的值，由该租户的设置得出并成为会话初值；不自行写死某一种权限档位、执行环境或协作模式。连接件、作业等入口已有的显式初值要求仍须满足，不能因存在通用默认值而省掉其必要配置；外部消息内容不能替入口选择身份或模式。

- 租户后来改默认值，只改变此后按默认创建的会话；已有会话即使从未手动切换，也保持自己的值。重启、休眠恢复、撤销归档、重新装配均不重新套用租户默认值。
- 会话内修改模式、模型选择或可覆盖设置，只写本会话；明确修改租户设置才产生租户范围的持久影响。保存会话值不隐式“记为默认”。
- 默认值与当前治理约束不同。会话保存了某个模式或选择，不会冻结租户授权、绕过组织锁定、强制在失权之后继续执行。
- 执行环境继续按 PF-005 逐工具、逐调用求值；初始化的是本会话采用的执行环境策略值，不是给整个会话分配一个永不变化的执行位置。
- 创建时保存执行环境策略中已确定的逐工具值及适用于未列工具的缺省声明。创建后新增工具，先按本会话当前策略求值；已有具体项保持，会话已保存的通用规则适用时使用该规则。若没有可适用的具体值或缺省声明，明确指出缺项并要求补充，不能静默读取租户后来修改的默认值。实时授权仍独立重判。
- 其他设置沿自身已有规则，分别保留显式覆盖或继承状态；例如没有会话覆盖的模型设置仍沿 PF-013 分层求值。不能把三种模式的初始化规则套到全部共享配置上。

| 实际修改的目标 | 持久影响范围 |
|---|---|
| 本会话的值、装载或 context 注册 | 本会话；恢复后仍成立 |
| 租户设置或租户资产 | 该租户的适用消费者；按每项初始化、继承或 reload 规则采用 |
| 组织配置或组织资产 | 组织范围内的适用消费者 |
| 工作区文件、设置或资产 | 使用相应资源的消费者，可能跨会话及获准租户 |
| 账号偏好 | 账号范围，可能跨其租户身份 |
| 工具修改的外部对象 | 对应外部对象，不因调用来自会话而缩成会话内效果 |

### 6.18 Runtime context 注册与内容分别变化

[运行时 context 注册](../../ubiquitous_language/terms/scope-and-resolution.md#ul-runtime-context-registration--运行时-context-注册--runtime-context-registration)与该块当前内容分别保存、分别变化。会话可以增加一块 context、移除已注册的非必需块，也可以更新既有块内容。注册要说明来源或提供者、配置、消费者，以及该块如何取得恢复所需内容；不在产品层规定接口形状。

- 必需 meta runtime contexts 始终在场；不能以动态移除取消必需信息，不能通过内容更新改写固定身份。
- 注册变化沿 [§6.8](#68-变更了要不要告诉-agent看谁消费它)告知相应消费者。给模型消费的块新增或移除后，后续组装须反映变化；过去已经发出的请求与历史消息不回写。
- 移除声明须跨恢复成立：恢复只装当前应在的块，不把已移除的会话注册复活。若来源规则另有强制要求，则不能接受这次移除。
- 只保存最后一份数据不够：会话须能恢复注册来源和配置。会话自有、无法重算的数据须保存；实时值重算，共享来源按规则重取，不把数据源副本当作新的共享权威。
- 移除本会话的注册不删除共享来源，不修改其他会话的注册。注册本身作为会话属性处理，不新增独立对象生命周期。

### 6.19 从函数输入确定持久化范围

**持久化的目的，是确定在需要重算时必须相同的函数输入。**先说清要重算哪一次判断、装配或投影，再确定要保留的输入；不能从“内存里有哪些字段”反推产品存储。相同的求值规则与相同输入应给出相同结果；规则或输入按允许的热重载发生变化，是新的求值，不是假称对旧计算的还原。

| 输入性质 | 产品要求 |
|---|---|
| 身份、类型要求、已发生事实 | 必须保持，不能因恢复或 reload 改写 |
| 会话的选择、设置、注册及不可重算内容 | 必须持久化；明确初值、当前值及变更依据，包括空闲计时的起点／中断／重置事实及归档取消待处理任务的事实 |
| 定义、资产、配置等共享来源 | 保留可解析的身份；需要解释旧执行时保留当时采用版本的可取得内容或等效依据；新求值按热重载与继承规则取当前内容 |
| 当下授权、可用性、连接与实时 context | 使用时重新取得；历史采用值不能作为新的授权或当前可用性证明 |
| 可从确定事实派生的当前状态 | 持久化投影以便直接读取，保留对应来源进度；重建必须与相同输入一致，不独立写出第二套事实 |

日志记发生过什么；会话级设置与注册记会话当前选择什么；投影回答当前推进到哪里。会影响恢复或后续求值的会话变更必须留下可追溯事实，当前值与相应事实不能分叉。纯日志投影只依赖日志；需要会话设置、context 或共享版本的求值，必须明确额外输入，不能声称“仅从日志即可恢复”。不要求所有外部实时信息写入日志，也不改变 runtime context 与消息的区别。

**当前值查询不应随日志长度增长而重扫整份历史。**指定当前值的读取按相对日志长度 O(1) 的访问目标设计；返回列表的成本仍与结果规模有关。投影可重建不等于每次查询都必须重建。过期投影不能冒充已反映最新事实的执行依据；具体存储结构、更新提交和查询复杂度证明归技术设计。

#### 三类 runtime 需要取得的输入

| 消费者 | 装配或启动需要取得的业务输入 | 会话应保留的依据 |
|---|---|---|
| Agent runtime | 租户／会话身份、Run／尝试归属、类型必需要求、同身份定义本次采用的内容、能力访问入口及 extension 装配结果、模式与设置、context 注册和数据、日志及其投影、工作区与资源入口 | 固定身份与要求、会话当前选择与注册、恢复内容、推进状态、本次采用定义及装配依据 |
| Model runtime | Session／Run 归属、调用身份与发起来源、本次有效 ModelProfile 和参数、已组装的消息／提示词、可见工具声明与允许它消费的 contexts、模型访问及取消所需条件 | 本次实际模型、参数、请求输入或可准确还原的依据、响应进度、结果、成本与失败事实 |
| Tool runtime | 会话与调用归属、目标工具、本次定义数据及匹配实现、参数和设置、允许它消费的 contexts、权限及环境求值结果、工作区／资源入口、结果回送和取消关系 | 本次调用身份、实际实现与输入依据、执行落点、状态、结果、外部效果和恢复对账关联 |

模型调用与工具执行的生命周期都归会话，Run 治理其关联工作；Agent runtime 只持有句柄。释放或销毁 Agent runtime 不取消两类执行。恢复先按持久调用身份重新取得句柄或读取已完成结果，不重新发起仍存活的模型或工具调用；工具运行连续性已丢失时按 PF-006 对账，不许借“输入一样”声称外部效果可以无条件重做。模型响应与外部执行不是因保存输入就变成确定函数；确定性承诺针对给定事实与规则的求值，外部结果按真实返回记录。

某次执行采用的输入，与下一次应采用的配置分别记录。换模型、热替换工具、更新定义或 context，不能把旧请求和旧调用的采用依据改成新值。新 Run 取得最新有效定义；显式 reload 也可按 PF-004／PF-012 在同一 Run 的安全交接点采用同身份新版本并开启新尝试。普通恢复使用当前已生效清单，不静默刷新来源。完整装配输入、变化与触发矩阵归 PF-004 §6.9–6.11；交接与在途结果归 PF-012 §6.18。资源处置的具体顺序及装配接口由技术设计细化，不新增产品审批阶段。

持久化不要求复制整份组织、租户、工作区资产目录；系统设施、凭据取得及存储／模型／工具提供者由各自配置负责，会话保留正确解析这些输入所需的归属与引用。

### 6.20 创建、变化与恢复的验收


| 场景 | 必须观察到 |
|---|---|
| 缺租户、定义身份或执行类型 | 创建过程不能以猜测或借用另一租户补齐；明确缺失 |
| 普通会话未给工作区和第一条消息 | 可建立空工作区、尚未执行的会话；不要求先起 runtime |
| 租户默认 co-work 创建 A，之后改为 auto-drive 再创建 B | A 保持 co-work，B 采用 auto-drive；A 恢复仍不改成租户新默认 |
| 在 A 切换三种模式或模型 | A 当前值持久保留，B 与租户默认不被改写；上级授权和锁定继续成立 |
| 创建后新增工具，租户默认策略已修改 | 用本会话保存的适用具体值或缺省声明；无适用声明则明确缺项，不偷取新租户默认；当前授权继续重判 |
| Job／连接件入口缺其必需显式配置 | 不能用通用默认绕过该入口的必填要求 |
| 同身份定义发布新有效内容，新 Run 开始 | 采用最新内容并按新声明装配；历史采用记录不变；同 Run 的尝试不偷换定义版本 |
| 换工作区带来另一身份定义 | 本会话定义身份不变；同身份实现替换仍受 official／上级锁定保护 |
| 同身份定义删改依赖或继承声明 | 后续装配按新内容求值，但会话类型必需身份集合保持；从未取得必需能力定义时明确报错；已知必需能力实现不可用则保留替换件 |
| 增删 Tool／Skill／MCP 或换同身份实现 | 合法变化沿既有生效边界采用；已知身份不删除，移除使其不可用，数据／实现变化不自动重建 Loop；历史执行保留旧采用值 |
| 增加 context、移除非必需 context，再恢复会话 | 注册与来源配置恢复；新增块在场、被移除块不复活；共享源不被删除 |
| 删除 meta context 或通过更新改会话租户身份 | 拒绝破坏必需项或固定身份 |
| 删除投影后用同一段事实重建 | 当前结果相同；日常指定当前值查询不扫描不断增长的日志 |
| 定义、共享来源或实时条件确实变化 | 新求值可不同，能解释变化来自什么输入；不把旧值当当前授权 |
| runtime 重建，已有工具仍在后台执行 | 恢复关联与等待，不重复发起；丢失连续性按既有中断对账 |
| 在会话内明确修改租户默认或工作区资产 | 按实际目标归属产生共享影响；与只修改会话值区分 |

补充验收：

| 场景 | 必须观察到 |
|---|---|
| 子会话交过报告，再收到父会话消息 | 未归档时沿当前 Run 追加或新 Run 触发；不重开旧派发，不再交同次派发的第二份报告 |
| 连接件外部内容指定另一个租户或 AgentDefinition | 不能替代可信入口提供的创建输入；来源可指认的重投不重复创建 |
| 固定输入已经超出模型窗口 | Run 明确失败并上交，会话与历史保留；无新条件不循环重新开 Run，不能静默删历史或分叉 |
| 读取第 9 块授权 context | 能指认本会话授权和撤回的作用对象及先后；全局结构化授权仍只沿第 8 块取得 |

归档与派发补充验收：

| 场景 | 必须观察到 |
|---|---|
| 用 master 定义 spawn／delegate | 可以派发，产生子会话；不改变 official 定义不可替换规则 |
| 会话已创建超过 30 天，但自身或归档会级联影响的子会话仍有等待中的 Run、后台工具或 Run 外模型调用 | 不满足自动归档的空闲条件，不因创建年龄到期而中断 |
| 全部工作收束、无待处理任务，连续空闲满出厂时限 | 自动归档；新工作到来则终止原空闲计时，重启系统不重置累计时间 |
| 手动归档时还有排队任务，之后撤销归档 | 原消息及取消原因仍可查，任务不自动重排；会话休眠并从撤销时重新计时 |
| 向已归档会话发新任务，同时旧调用交回迟到结果 | 新任务明确被拒；迟到结果与账按原执行归属保存，不触发新 Run |

### 6.21 三类 runtime 的归属与执行关联

执行关联还须识别原消费位置：主流程、具体拓展位置、压缩计算或 Run 外会话消费者。恢复后结果及失联处置交回原位置，不把所有模型返回都当成主流程回复。成本沿原调用／发起尝试记，承接关联单独记录，不因换等待者重复计费或认定旧费用浪费。

三类 runtime 的生命周期统一归 Session；Run 是关联工作的逻辑治理对象，不是物理进程父级。Agent runtime 推进当前 Run，持有 Model／Tool runtime 句柄而不拥有其生命。模型或工具运行不以持有句柄的 Agent runtime 数量为前提；句柄不作为需要跨恢复保留的内存对象。

会话必须持久保留调用／执行身份、所属 Session、关联 Run（如有）、原发起尝试（如有）、本次输入采用依据、当前执行与取消状态、结果和承接关系。运行等待谁、是否已完成以及结果是否已承接，不能只藏在已销毁的 Agent runtime 里。新 Agent runtime 从这些事实重新取得访问引用或读取结果；接手者不改写原执行归属，不重复计费或重新发起。

无 Agent runtime 持有句柄时，模型输出、工具结果、费用与失败仍应由相应执行按归属记录。会话归档要能找到并取消这些在途执行，不能只遍历某个 Agent runtime 手里的句柄。会话级旁路模型调用及其成本直接归会话，不受无关 Run 的取消影响。

具体取消矩阵、尝试交接及结果接续统一沿 [PF-012 §6.13](../PF-012-agent-loop-and-run/design.md#613-取消跟着宿主走)，模型失联和工具失联各沿 PF-013／PF-006；不从“执行发起于某实例”推导“实例销毁时执行跟着死”。持久化可恢复关联，不承诺失联的网络流或进程本体必然可恢复。

| 场景 | 必须观察到 |
|---|---|
| Model／Tool runtime 正运行，销毁唯一持有句柄的 Agent runtime | 两类执行继续；零句柄期间仍有输出、结果与账目记录 |
| 原 Agent runtime 已销毁，模型先完成，新实例随后接手 | 读取原结果，一次调用不变成两次；待承接事实不丢失 |
| Run 取消时，另有一个无 Run 归属的旁路模型调用 | 取消目标 Run 的模型调用；旁路调用不被误伤 |
| 没有 Agent runtime，归档会话 | 仍能找到并取消会话内模型与工具执行，保留真实结果及成本 |
| 同一机器故障同时影响多个 runtime | 分别判断各执行连续性；不把 Agent runtime 消失本身当作其他执行失败证据 |

会话还须保存重装配的请求意图、来源范围、校验结果与实际生效结果，并能直接取得当前有效清单、当前尝试和待续工作的投影。尚未生效的候选与已采用值分开；同一 Run 可以关联先后采用的不同清单。已开始调用保留原输入、原消费者与原尝试；新尝试的承接关系单独记录。内存句柄不作为可持久恢复的数据。具体事实边界见 [PF-012 §6.18](../PF-012-agent-loop-and-run/design.md#618-agent-runtime-的装配与重装配交接)。

### 6.22 会话作用域的输入与供给

Session 是长期身份、数据及资源归属。产品上说“给 Session 注入”，指管理该会话的组件取得输入和服务，不意味着 Session 本身是一个 Cordis fiber。以下为必须满足的逻辑消费关系；一个入口不必对应一个独立服务，具体 inject 边、插件与作用域布局归技术设计。

| 管理会话的组件取得什么 | 创建／运行时要求 | 向谁供给什么 | 变化范围 |
|---|---|---|---|
| 租户身份、当前授权及治理入口 | 创建时身份必需且固定；授权运行期重判 | 各类消费者的归属与准入依据 | 身份限本会话；授权沿真实治理范围 |
| 工作区、资产来源及定义读取／求值入口 | 工作区可空；固定 AgentDefinition 身份，按规定时刻采用内容 | Agent runtime 的定义、Loop／extension 装配输入；会话能力当前采用值 | 共享来源修改与本会话采用分别记录 |
| 类型必需项、定义显式能力要求、继承声明 | 类型身份固定；定义按已定采用边界变化 | 会话能力记录、必须保留的位置、选择／排除约束 | 会话采用；两种必需来源都不直接转成 Loop 对具体工具服务的依赖 |
| 存储、日志、投影与执行治理入口 | 创建／推进／恢复所需服务必须可取得 | 三类 runtime 与交付面读取进度、等待、结果、费用和控制目标 | 事实归会话／Run，不归 Agent runtime 闭包 |
| 租户默认值、会话设置与三个模式 | 创建求初值，之后恢复会话当前值 | 各消费组件按规定边界取值 | 改会话值不回写租户默认 |
| Runtime context 来源与注册 | 必需块成立，可选注册可增删 | 仅向声明的消费者提供其可读内容 | 会话注册／会话自有值与共享源修改分开 |
| Model／Tool 执行入口及实际设施 | 启动调用时取得必要条件，不要求创建会话即启动执行 | Agent runtime、extensions 或其他授权消费者发起／查找调用 | 执行归 Session，关联 Run 治理；句柄不转移所有权 |

**会话供给的是能力的访问入口与当前采用值，不是把每个工具实现直接注入 Loop。**Tool runtime 在调用时取得具体执行实现及其服务；Model runtime 取得本次请求快照；Skill 消费者取得当前允许读取的内容。Agent runtime 持有调用句柄，释放它不取消这些执行。

持久化须补齐三种不同输入：①会话已知能力身份及最后合法可呈现的定义；②当前合法采用的数据、实现来源／版本、选择约束和不可用原因的求值依据；③每次请求、读取或执行的实际输入。当前可用性恢复时重算，历史原因不当作实时事实；当前值不能覆盖历史输入。会话被归档、休眠或 Agent runtime 重建不丢已知身份。被撤权后不继续下载新内容；保留已知身份不等于保留执行权限。

| 场景 | 必须观察到 |
|---|---|
| definition 不变，只更换某工具实现，服务入口不变 | 下一次合法调用采用新实现，Agent runtime 可保持；在途调用用旧输入 |
| argsSchema 更新，承载服务不变 | 新请求采用新声明；旧请求建议核对当前约定，不直接执行；Loop 不因 schema 变化重建 |
| 必需工具服务离线，来源分别是会话类型或 AgentDefinition | 两种来源都保留必需能力位置和替换件；不把工具服务失效传播为 Loop 必须停止 |
| Skill 正文更新或 MCP 已知动作消失后恢复 | 正文在后续合法读取采用；消失动作保留不可用身份；恢复仍检查当前选择／治理 |
| 会话 A 曾合法见过能力、B 从未见过，随后资产禁用 | A 保留不可用条目，B 不新增；两者都不能执行被禁用实现 |

### 6.23 连接件创建会话的输入

**搁置。**连接件是否继续作为资产存在尚未定论，本节仅保留条件性设计，不构成当前交付承诺，也不阻塞通用会话创建与装配。具体规则只有在连接件定位重新确定后才可恢复采用；不继续补齐路由或接收范围。

连接件触发新会话也要满足 [§6.16 的创建输入](#616-会话组成与创建输入)。有效租户身份与 AgentDefinition 身份必须由受信任且有权配置该入口的一方确定；无人交互的入口须能从其配置及有效身份上下文取得这两项，不能让外部事件正文代选，也不能缺项时随意找一个租户或定义。创建者的授权与资产可用范围仍须核对。

工作区未指定就是空；权限模式仍须满足 PF-002 对连接件入口的显式配置要求，其余模式沿租户默认和会话初值规则。配置变化只作用于以后创建的会话，不改已有会话的固定身份。

来源能够指认同一事件时，重投不得重复开会话或重复触发同一份处理；沿 PF-014 的去重规则。此要求不决定同一事件是否允许多个明确接收者，路由与接收范围仍见 [§9](#九未决项)。不从消息内容推断线程归并。配置形状、身份如何传递和去重如何实现归技术设计。

### 6.24 上下文装不下时会话仍保留

压缩后仍装不进目标模型窗口，按 PF-012 结束这次 Run 为失败，并按 PF-011 上交非常态。会话保留历史、设置与已有结果，不因此归档或删除，也不因同一条件不变而反复开新 Run 重做无用压缩。

用户须能查到失败原因，并区分固定部分超限与压缩后的会话上下文仍超限。接手层有现成处置手段就沿 PF-011 处理，用尽继续上交；这里不另设一套溢出处置机制，不把自动分叉、丢历史或静默换模型作为默认补救。用户仍可沿已有能力调整模型或会话输入，条件满足后由新的输入触发新 Run；失败的原 Run 不复活。

### 6.25 沿用既有规则的边界

自动归档沿 [§6.2](#62-归档有两条来路人手动或到期自动) 的出厂时限，默认 30 天；不新增租户或单会话覆写项。归档不是删除，时限也不是历史数据保留期。资产设置的分层规则不能单独推出每一种系统行为都必须新增租户设置。

子会话报告之后的消息沿 PF-014：未归档且已有未结束 Run 时追加输入，没有未结束 Run 时触发新的 Run。一次派发只交一次报告；后续交互不会把旧派发重新打开，也不能据此把一次派发等同一次 Run。接收方已归档时拒绝新的任务输入，沿 §6.3 告知发送方。

业务流程拓展点只按已成立的场景增加；已有尝试开始后的挂点能够承载的判断不再增加前置挂点。四块 context 的业务最小信息见 §5.6，字段、刷新协议与存储投影交给规格和技术设计。结果卸载的全文保留承诺归 PF-006；存储分层与回收实现不能自行缩短这项承诺。

## 七、取舍

### 为什么没有删除

**因为会话是归属边界。**成本算在它头上，记录挂在它名下，
[授权、设置、沙箱都以它为作用域](../../ubiquitous_language/terms/scope-and-resolution.md#ul-scope-layer--作用域层--scope-layer)。
**删掉它，等于让一批已经发生的事实失去归属。**

**代价是诚实的**：列表会越来越长，存储会一直涨。
**我们选择用归档解决「看不见」，而不是用删除解决「不存在」**——
因为前者可撤销，后者不可。

> **这不等于说永远不会有删除。**合规要求下的数据清除是另一件事，
> 它有自己的触发条件、审批与留痕，**不是用户在界面上点一下的那种删除**。本 rev 不做。

### 为什么归档可撤销，副作用却不可逆

**因为它们本来就是两件事。**

- **归档**改的是**这个会话的状态**——那是一个标记，回退它没有任何外部代价。
- **中断在途的工作**改的是**外面的世界**——模型已经算过的 token、
  工具已经写出去的文件、子会话已经花掉的钱。

**把它们捆成一个「可逆的归档」，等于承诺系统能把外面的世界也退回去，而那做不到。**
与其给一个做不到的承诺，不如把界线画明白：**状态可以回头，工作不能。**

### 为什么类型只能出厂加

**因为租户能自定义的是子 agent，不是主 agent。**
这五类是用来标识**主 agent 的类目**的——
既然主 agent 只能由产品官方提供，那么类目自然也只能由产品出厂时增补。

**租户能不能自定义会话类型，不是一个孤立的问题**：它等价于问
「租户能不能自定义主 agent」，而那个问题已经有答案了。

### 为什么会话类型是算出来的，不是绑上去的

**因为它们的失效事件不同。**
AgentDefinition 是一份**会演进的资产**——它会被改、被下线、被换类目。
会话是一段**已经发生的协作**，它的用途在建立那一刻就定了。

**把两者绑死，等于让历史跟着资产走**：某天有人把一份 coding 的定义改成 research，
一批早就收尾的会话会在列表里集体变脸。**那不是修正，那是篡改。**

### runtime context 为什么不并进会话日志

**因为它们回答的问题不同。**日志回答「**发生过什么**」，
runtime context 回答「**现在是什么**」。

**并进去会两头都坏**：日志只追加，要表达「现在是什么」就得每次改一条都写一条新的，
**读的人得自己把历史折叠成当前值**——而折叠规则一旦有歧义，两边算出来的当前值就不一样。
反过来，把日志做成可就地改的，[「一条消息都不能擦除」](../PF-012-agent-loop-and-run/design.md#会话日志)当场作废。

> **一个只追加，一个就地改，这不是实现差异，是两种事实的性质差异。**

### 变更通知为什么按「谁消费」发，而不是一律发

**因为模型的注意力是这个系统里最贵的东西。**
一块只有工具和拓展点在读的 runtime context 变了，给模型发一条提醒，
它得读、得判断与自己有没有关系、然后得出「没关系」——**这一整趟是纯损耗**。

**而且损耗是累积的**：提醒多了，模型对提醒本身就不再当真，
**那时真正要紧的那条变更通知也一起失效了**——[和问得太勤是同一种失效](../PF-007-meta-capabilities/design.md#什么时候不该敲这扇门)。

### 单次授权为什么必须有明确的清除时机

**因为「单次」是一句承诺，而承诺要有人兑现。**
不给它一个确定的清除点，它就会一直留在那份数据里——
**而没有任何人会发现这件事**，直到某次 agent 拿着上一轮的授权做了这一轮的事。

**所以清除不能靠约定，要落成 [loop 上一个明确的拓展点](../PF-012-agent-loop-and-run/design.md#loop-拓展点)**，
在[运行终态](../../ubiquitous_language/terms/agent-runtime-loop.md#ul-run-terminal-state--运行终态--run-terminal-state)那一刻动手。
**三种终态都清**——**被取消的那次尤其要清**。

### 为什么要另立一类拓展点

**因为 Loop 拓展点做不了这件事，而且不该让它做。**
[挂在 Loop 拓展点上的东西只能靠改会话日志起作用](../../ubiquitous_language/terms/agent-runtime-loop.md#ul-loop-extension-point--loop-拓展点--loop-extension-point)——
这是一条**刻意设下的限制**，它保证了「agent 的下一步为什么变了」永远查得到。

**跑题提醒要做的恰恰是不留痕迹地拦一下。**
如果硬塞给 Loop 拓展点，要么打破那条限制，要么在日志里留下一堆
「用户本来想说但没说成」的东西——**两条都不能接受**。

**所以它是新的一类：拦得住请求，碰不到已经落定的事实。**

### 为什么对存储只提两条

**因为再多说就越界了。**日志落在哪个引擎、什么时候刷盘、快照怎么做、投影用什么结构——
**这些产品负责人判断不了对错**，按红线就该归技术设计。

**但这两条少说一条都不行：**

- **不提第一条**，技术上完全可以选一个让会话醒来丢状态的方案。
  **它跑得飞快，而且平时看不出错**——直到有人撤销归档，发现 agent 认不得自己了。
- **不提第二条**，单机的便利会一点一点渗进契约里。
  **等到要扩展的那天，代价是推翻[架构内核](../architecture-core.md)**，而那时候已经晚了。

> **两条都属于「不说会出事，说多了会越界」的那种要求**——
> 所以它们只说**要守住什么**，一个字都不说**怎么守**。
