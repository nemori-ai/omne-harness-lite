# 执行环境产品设计

状态：产品设计草案，revision 1。尚无整体接受证据。设计落位不授予实现支持、阶段能力或技术采用。技术承接从[领域入口](../../../../docs/domains/execution-environments/README.md)与[能力组入口](../../../../packages/execution/README.md)展开。

## 产品需求描述

人和 agent 需要知道动作实际落在哪里、那里提供哪些设施、留下的状态能保存多久。执行环境提供计算、文件、命令行、浏览器或其他已声明设施。设施、隔离、资源可用性、绑定范围和数据保存是不同维度，不能从“沙箱”“本地”“云端”或工作区路径推定全部保证。

环境选择消费工具要求和当前合法策略，按工具、按实际调用求值，不为整个会话预先指定永不改变的机器。宿主机也须声明真实设施和可用条件；它不提供租户隔离，不能因 agent 位于同一设备而自动获准使用。动作权限、落点策略、工作区参与及资源访问分别成立；工作区文件或人工批准不能解除明确禁止及所需隔离。

框架允许部署选择环境提供者、设施、合法策略及资源配置，不在产品正文钉死数值限额、TTL、节点、备份介质或具体安全引擎。已接受的策略词汇中，always-allow 允许直接使用宿主，auto_place 按条件选择合适环境，never-allow 禁止直接落宿主。三者仍受组织约束、当前授权和真实设施限制，宿主许可不授予额外动作权；没有配置或无法取得允许依据时，不能猜测许可。未声明环境需求的工具使用自己明确声明的直接依赖，不能把这条边界当成绕过隔离的后门。

短寿命沙箱可服务单次调用或在会话工作期间复用，会话级沙箱有已声明的最大连续寿命。重要原创产出不能只留在不提供长期保存承诺的环境中。租户级沙箱提供同租户的共享工作空间：获准会话可以看到彼此产出，也可能发生写入冲突；这不承诺同租户各个 agent 的文件互相隔离。其数据须按与租户相应的生命周期保存，并可备份、迁移；计算寿命和技术参数不改变这一要求，具体边界见 J-EE03。跨租户私有材料仍默认拒绝，共享实例、标签和目录名称不授予访问权。

### J-EE01 按本次资格取得需要的落点

用户希望工具在允许且具备所需设施的地方执行。前提是可信调用身份、原工作引用、实际工具要求和适用策略均已明确；独立工具调用无须创建 Session，但须提供等价合法输入。

动作准入通过后，系统比较当前所需隔离、设施、绑定条件及可用提供者，取得资源并确认就绪，再把实际环境和资源入口交原工具调用。一个会话可以同时使用多组满足不同调用要求的环境；设施及落点改变不自动改变工具动作空间或重建 Agent runtime。

无匹配设施、明确禁止、隔离无法确认、资源建立失败或宿主设施不可用，均报告真实原因并拒绝依赖该条件的执行。不得静默退回宿主机、较弱隔离或另一目标。取消准备后，已经分配的资源仍须查清和释放；未收到准备答复不能当成没有分配。恢复先查询原准备或原调用，不重复发出有副作用的工具动作。

### J-EE02 在有明确寿命的环境里持续工作

用户希望前后步骤可以复用状态，同时知道状态何时会消失。前提是已选环境声明复用范围、设施状态、最大连续寿命及临时数据边界；终端会话是命令行设施内的状态，与业务 Session 分开。

有效寿命内，工具可沿合法关联复用资源。单次调用沙箱不承诺跨调用状态；会话级沙箱达到声明的寿命边界后停止接受依赖旧状态的新工作，并执行回收。原设施及终端状态是否已关闭按实际结果报告，清理失败保留责任。再需要资源时可以取得新环境，新身份及状态丢失须可见。

agent 必须能感知当前落点及上次痕迹是否仍在；环境过期、重建或释放的变化经 Context 的合法供给规则传达，不由环境自动重发原计算或原工具。用户可以在到期前把重要产出保存到有相应承诺的资源。结束、归档 Session 或销毁 Agent runtime 不自动证明环境已关闭；环境退出也不证明上层工作已收束或外部效果撤销。

### J-EE03 让租户数据跨计算实例继续存在

同租户的获准会话希望继续使用共同工作空间，运维希望释放空闲计算或更换节点。前提是租户与数据归属、与租户相应的数据寿命、备份迁移条件及计算资源关联均明确；共享租户数据不等于逻辑工作区。

租户级沙箱内数据的有效保存寿命与租户生命周期相应，并须可备份、可迁移。租户仍存续且数据未按合法规则删除时，计算停止、释放、重建、更换节点及空闲回收不能使数据提前失效或删除，技术 TTL 也不能自行缩短这一寿命。数据继续由明确托管方保存。备份、恢复或迁移报告具体数据及版本、目标和实际完成状态；新计算实例取得合法数据关联后才服务新调用。数据访问沿当前主体和用途核验，不能复制另一租户的数据来补齐失败。

保存、备份或迁移失败须可见；部分完成、数据可读、新环境就绪和原执行恢复分别表达。恢复先核对原数据与原动作，不能以“环境重建成功”宣称原工具已迁移、旧痕迹仍在或原效果未发生。数据兼容条件不满足时阻止依赖操作，保留原数据及恢复责任；不承诺异构节点间任意热迁移。

备份或副本的技术保留窗口不改变业务数据寿命，清理副本不能提前删除其唯一有效托管内容。保存与恢复须说明适用故障范围，不承诺存储介质物理损毁后无条件恢复。合法数据删除及租户生命周期结束后的处置按相应数据规则处理，不推出永久留存。

### J-EE04 改变后续选择并保留原执行依据

用户希望收紧落点策略、选择另一个工作区或使用新环境。前提是修改由合法拥有者作出，Session 选择、工作区关联和环境条件分别记录，当前资源及动作权限继续核验。

后续调用按新的有效条件选择，已发调用保留原租户、工作、工具实现、环境、工作区和资源入口。新的工作区或环境选择不是把原进程搬过去；候选来源读取和装配采用成功也不证明实际环境已切换。提供者替换须处理旧资源和在途调用，不能仅因注册项撤除丢弃它们。

选择失败或取消时保留原采用记录和实际资源事实，但不延续已经撤销的访问权。较新选择及取消不能被迟到准备结果覆盖；迟到资源仍有查询和处置责任。agent 得到真实落点及痕迹变化后判断下一步，系统不替它盲目重做有外部效果的动作。

### J-EE05 只把必要资源交给子进程及设施

用户希望工具、命令型 MCP 或 hook 可以使用所需文件、网络和变量，同时保护宿主秘密。前提是该组件已取得自己的合法运行准入，以及本次落点、目标、用途和资源条件。发现工作区文件或开启兼容来源不构成执行许可。

子进程只接收该消费者允许且宿主实际具有的环境变量；不同消费者可有各自名单，不自动继承宿主整份环境。另行配置的凭据按凭据规则取得，变量同名不授予读取权。文件、挂载、网络和可调用能力以实际资源及用途限制，工作目录只确定起点。

未授权目标、缺少变量或凭据、无法建立所需限制，按具体依赖契约报缺失或拒绝，不借通用服务权限代操作。停止或超时分别记录实际子进程及调用收场，仍保护原结果；诊断不输出秘密值。hook 的兼容转换、逐件启用及业务效果归原拥有者，本领域不统一改写这些规则。

### J-EE06 让不可信代码在受限执行域中使用获准能力

系统须支持不可信代码进入主进程，并按其可能蓄意窃取秘密、越权或耗尽资源设防。用户希望它只接触明确输入和获准接口，不要求任意 Node.js 插件兼容。前提是所采用执行域、受控宿主接口及监督安排有证据满足正式隔离边界。

代码不能直接取得原始 Cordis Context、全局服务容器、任意宿主对象、模块加载或未经授予的文件、网络、进程及原生扩展能力。跨界请求及返回值由宿主验证，身份不能由代码伪造；持有旧句柄仍受实际使用时的授权限制。时间、内存、并发、输出及宿主调用有可执行的限额，恶意代码不合作也能终止，不能让它阻塞负责终止的同一调度线程。

提供者不能满足这些条件时不得承接该运行方式。普通模块、Cordis 作用域、node:vm 或进程级权限配置不作为充分安全证明。同进程仍共享进程故障域，不能宣称任意引擎缺陷或原生崩溃只影响一个插件；故障按真实影响和已保存状态恢复。具体引擎、API、桥接及配额数值是技术义务，已定边界不再作为产品投票。

### J-EE07 控制资源而不遗失已经发生的工作

用户或监督者希望停止代码、取消工作或释放计算。前提是目标执行域、原调用、资源和数据责任可以定位，控制方有对应资格，提供者说明可阻止、可合作停止及可强制终止的范围。

系统分别呈现控制受理、代码已停止、原工具或宿主调用实际收场、资源关闭及数据处置。终止受限执行域只阻止其中代码继续运行；已经准入的宿主调用及迟到结果继续由桥接和原调用拥有者承接，结果不能只返回到已销毁的执行域。销毁 Agent runtime、Run 逻辑终态和取消信号也不代替这些确认。

停止失败、清理失败、结果未知及仍需保留的资源可查询，不假报回收。已经发生的外部写入不因 disposer 而声称撤销。恢复核对原控制及原调用，只接续未完成责任；既不能丢弃结果，也不能重新发起相同有副作用动作来制造一个“成功”结果。

### J-EE08 在故障后辨认真实状态并接续责任

用户希望知道准备、执行、恢复及释放到了哪一步。前提是观察与控制关联原主体、工作、工具调用、环境、资源、数据和实际版本，并满足信息访问资格。

提供者报告就绪、排队、准备失败、资源压力、到期、终止、清理及数据恢复的真实状态。查询失败是暂时无法确认；原计算确定丢失、数据可恢复、新实例就绪和原执行连续性分别表达。Context 按自己的供给规则让 agent 知道落点及痕迹，不以通知成功证明迁移、停机或数据保存完成。

重启、失联或答复丢失后围绕原身份查询、等待或对账，只有证据支持未发生或安全后续动作时才执行。旧授权和旧快照不能复活已撤权利；未知不降成不存在。必要记录失败或观察过期须可见，观测请求不重做业务动作，凭据及私有内容按目的裁剪。释放空闲计算保护数据和未完成调用责任，不能为了资源读数好看而丢弃结果。

## 阶段与版本支持承诺

0.0.0 → 0.1.0 的执行环境能力清单等待负责人选择。CAP-EE01 至 CAP-EE12 是选择对象，不能据此声称全支持；本候选不推荐基线，不沿旧 PF 的“首版”、具体部署默认或其他领域承诺替负责人选择。

负责人选择完整 CAP、必要能力依赖、用户可理解的设施或部署适用范围、产品条件和限制。具体提供者及机制版本、设施协议、技术采用和验证方案由具名技术拥有者补足，不作为产品阶段选择的前置。形成实际支持声明及交付接受时，须再绑定精确版本、适用条件和真实验证范围。所有实现状态仍为未核实。

已定的租户边界及数据寿命、未知不等于未发生、不降级、取消与物理停止分开及同进程恶意代码设防，在相应能力采用时继续成立，不能用阶段选择将其改成宽松默认。

框架保留多提供者及可配置治理条件，数值、TTL、设施命名、兼容协议和安全机制由具名技术设计与部署采用明确。任意原生插件兼容、任意外部副作用回滚、跨节点无条件热迁移、短寿命数据永久留存及工作区目录安全围栏没有因本稿成为承诺。阶段、技术及证据缺项见[问题记录](design.md#未决问题与待定事项)。

## 未决问题与待定事项

本章是当前产品问题入口。阶段与政策选择、技术义务、来源缺证及明确非目标分别维护；既定约束不重新请求选择。技术问题只限制依赖部分，不能减损已有不变量。

### Q-EE01 0.0.0 → 0.1.0 支持清单

决定责任：阶段负责人。

场景：负责人需要确定执行环境领域在阶段交付中实际支持什么。

待明确：负责人选择哪些完整 CAP、必要能力依赖、用户可理解的设施或部署适用范围、产品条件和限制？

既定约束：

- CAP-EE01 至 CAP-EE12 全部为候选能力，实现均未核实。
- 正式租户、隔离、控制、未知和原调用边界在相关采用范围继续有效。
- 旧 PF 首版/默认、邻域支持或文件存在不代选。
- 产品选择完整 CAP、产品条件及必要能力依赖；提供者或机制版本、协议和验证方案由技术拥有者补足，不作为阶段选择前置。

处理方向及后果：

- 选择具名完整能力及必要能力依赖，逐项记录产品适用条件和限制。
- 负责人尚未决定时保持阶段清单未定，候选能力继续供评审。

等待负责人选择；不推荐基线或自动勾选能力。

影响：决定产品阶段承诺及后续具名技术设计范围；实际支持声明和交付接受另须绑定精确版本、适用条件及真实验证范围。

### Q-EE02 选择、准备与实际发起的协调边界
