# 2026-09-27 Omne Host 工作区讨论

- 来源：产品负责人在本会话的直接输入；无稳定会话 URI。
- 状态：首版 Git 范围与创建时选型吸纳至 PF-020 rev 6；生命周期解耦、资源异步同步与 agent 自主工作原则吸纳至 rev 7；统一抽象与原生能力复用吸纳至 rev 8。各段保留当时语境，现行规则以正文为准。

## 讨论背景

用户要求讨论 Omne Host 的工作区设计，可参考 omne-next 历史设计与 ChatGPT、Claude 的相关产品。记录者提出中心托管、实例装载、工作保存与成果交付区分、多实例冲突可见等建议；这些建议不因用户随后确认 Git 路线而全部成为产品裁决。

## 首版范围的明确输入

用户原话：

> 中心托管和部署节点装载实例，我们第一版先明确好只提供 git 管理的那一套（我们可以叫做 git 类型的工作区，这样未来 omne-host 的依然可以拓展其他类型的工作区，让租户自行在创建工作区的时候选择）

吸纳结果：首版 Omne Host 只提供 Git 工作区，中心托管 Git 资源，部署节点装载相应工作副本；租户创建时选择管理类型，后续可以增加其他类型。为避免与既有分类混用，记录者将该属性称为“工作区管理类型”，区别于“工作区类别”和“地址提供者类型”。

边界：本轮不确认 Gitea、Git LFS、自动 commit／push 的时机、分支策略、冲突解决、离线恢复、成果发布或类型转换策略。之前的“自动保存、显式交付”等建议仍待讨论。

## 生命周期、同步与 agent 自主性的明确输入

产品负责人明确（转述）：

1. 工作区生命周期与会话解耦。部署机器可先存在实例，再由会话 attach；也可在创建会话时指定本地路径，先装载目标工作区再创建会话。
2. 从会话看实例是本地，中心是 remote。所有资源同步都可以异步；用户在本地或远程上传、修改文件，不要求会话及时感知。用户觉得需要时可告知 agent，由它完成同步；agent 也可以在连续工作中自行发现变化或同步需求。
3. 应始终把 agent 当作有完全行为能力、连续上下文感知的“人”，它能自行发现和解决冲突，运用 Git 分支、工作树管理资源并避免竞争。

吸纳至 rev 7。记录者此前关于自动同步、主动推送变更、冲突默认交给用户的建议，不作为已接受或必需策略。系统提供实际可操作的能力及如实的状态结果，agent 在既有授权范围内自主工作；不是假定它无需读取就已知道远程变化。

仍未裁定：精确实例身份与状态机、Git worktree 与实例的对应、上传下载入口及覆盖规则、离线保留与恢复、操作完成回执、成果交付与托管实现。

## 统一抽象与原生能力复用的明确输入

产品负责人原话：

> 就是我们应该是这样抽象的：Workspace - GitBasedWorkspace ，那很多东西其实不需要我们从头实现一遍，利用 git 原生的机制或特性即可，未来其他 XXBasedWorkspace 同理，需要定义的只有契约和接口协议（而且主要应该是方便产品层面的比如前端、给人用，而不是给 agent 用，因为 agent 本身世界知识里面对 git 的操作是很熟练的了，它不需要有专门的我们为它定制的东西）

吸纳至 rev 8：Git 工作区的类型记法为 `GitBasedWorkspace`，是统一 `Workspace` 的特化，沿用已有身份。资源管理直接复用 Git 原生能力，产品定义所需契约和接口，主要面向前端与人的使用；agent 通过已有工具使用 Git，不另要求专用包装命令。

PM 推导：未来具体类型沿用其原生能力，不应被迫模拟 Git 特性；人的界面与 agent 直接操作应反映同一实际资源状态。以上不决定代码继承结构、完整接口集合、Git 托管产品或实例映射，也不把“主要给人用”解释为禁止 agent 调用产品接口。

## 生命周期范围的纠正

产品负责人原话：

> 没这么复杂，本地的工作区实例不用，那用户创建会话永远不指定 attatch 它就行了，它在不在本地不影响，远程的删除了也不影响；产品上的设计真正只关心的是治理中心的关系解除，也就是 租户 - 工作区 的关系解除，以及中心存储的云端的那个工作区被销毁了之后对关系的连带影响

吸纳至 rev 9：本项产品范围只有治理关系解除与中心工作区销毁后的关系影响；不用本地实例时不再附着即可，远程删除不连带本地清理。撤回记录者此前关于本地卸载、归档、回收站、保留和恢复的一整套产品决策展开，不将其带入本项后续裁定。

未裁定：谁能解除何种关系、治理所有者关系的处理，以及中心销毁后关联关系直接解除还是保留特定展示状态。该纠正不授予已解除关系任何持续访问中心资源的权限。

## 解除关系与普通本地目录

产品负责人原话：

> 解除本质上那就是删除一条关系条目咯，然后删除了之后相当于标识就没有了，那自然在用的时候（session attatch）就只当作是本地的普通文件目录（也就是其下的 .omne 和 .omne.local 等及时存在也不影响 session 装配了）

吸纳至 rev 10：解除关系即删除条目；对相应租户的后续会话，原目录不再提供工作区装配身份，双目录即使存在也不进入装配。文件保留，不隐式重新登记。标识消失指该租户通过此关系对工作区的识别，不扩大为删除其他租户关系或全局工作区。

PM 推导：双目录里的兼容开关也不能继续触发该工作区的第三方资产发现；普通文件访问仍依照现有环境和工具权限。运行中会话的重装配时机及中心销毁后的关系级联不在本次输入中裁定。

## 已有目录的首次登记

产品负责人原话：

> 然后就是我们还需要有一个机制，这个机制要能够让一个会话首次 attatch 一个本身没有记录在租户上的目录成为他可用的一个工作区（比如租户参与一个开源项目的开发，他自己先克隆了这个项目到本地，然后进入项目根并开始一个 omne 新 会话）

吸纳至 rev 11：支持在首次会话使用中登记并附着用户已有的本地目录，不要求预先到治理中心单独建记录或重新 clone。登记成功后接续既有工作区装配。

记录者提出的交付面建议：用户显式选择“作为工作区使用”后登记，普通启动仍为目录使用，避免关系删除后自动重新登记。此触发选择尚待回复；能力本身已确认。登记不自动上传、迁移或授予外部项目权限。

## 创建矩阵与显式登记触发

产品负责人原话：

> 进一步地我们用矩阵分析法来正式化工作区的创建，就可以分成：1）中心先有，然后本地实例化；2）本地先实例化，然后首次 attatch 的时候关系建立并同步到中心（只是关系同步，因为一个开源项目就未必是 omne-host 的，而一个已经存在的 omne-host workspace 本来就已经在 omne 数据中心侧了）

随后对登记触发选项明确选择：

> 显式选择后登记（推荐）

吸纳至 rev 12：两条路径统一在工作区身份与租户关系模型下。本地先有的首次登记只同步关系及必要关联标识，不上传资源；已有 Omne Host 工作区沿原有身份关联，外部项目不因登记迁移托管。显式选择才登记并附着，普通启动保持目录使用；解除关系后的目录也不自动恢复登记。

矩阵第二轴使用资源提供者，以区分治理中心中的关系登记与资源实际托管位置。历史段落中“触发待裁”是当时状态，由本次选择解决。

## 中心销毁的关系级联与权限

记录者提出：中心托管工作区确认销毁后，删除指向它的全部租户关系，包括所有者和参与者；本地目录保留，后续会话按普通目录使用，双目录不参与工作区装配。暂时不可达不等于销毁。

产品负责人回复：

> 同意，并且仅工作区的所有者（创建者或创建者授予了工作区的超管级别权限的租户）才有权利销毁工作区。

吸纳至 rev 13：确认上述级联结果，销毁资格限定创建者或由创建者明确授予工作区超管权限的租户。

PM 表达：工作区超管是工作区范围内的授权角色，区别于组织超管。用户此处以“所有者”指有资格销毁的主体集合；既有唯一治理所有者仍承载组织归属，授予权限不自动转移治理归属。单独解除关系的权限、治理所有者退出、授权撤回与再授权未由此补全。

## 关系解除权限与本版所有权边界

记录者逐项提出：普通参与租户可以退出自身关系；工作区超管可退出并失去授权；创建者或工作区超管可移除参与租户；普通参与租户不能移除他人；工作区仍存在时不能单独删除唯一治理所有者关系。本版不额外提供所有权移交流程，治理所有者结束工作区走已定义的销毁流程。

产品负责人回复：

> 认可

吸纳至 rev 14，上述规则作为产品裁决。用户另明确要求后续每项确认落盘后，自动展开下一项讨论，无需再次催促；该要求不代表后续提议已获接受。

## 组织参与限制默认值与已知缺口

记录者建议提供不启用、仅本组织、仅同一组织树三个配置状态，默认不启用；不启用仍须满足工作区授权，限制不拦原有资格下的只读访问。

产品负责人回复：

> 同意，默认不启用限制。并且需要明确我们目前的设计的已知缺口，也就是即使限制了，但依然拦不住将一个开源项目当普通的目录来访问和使用

吸纳至 rev 15：默认不启用已确定；把普通目录绕行明确写进产品正文、流程与验收边界。当前规则不构成完整防“公器私用”保证，不因记录缺口就承诺普通目录拦截或自动登记等新机制。

## 首版不提供参与限制例外

记录者建议：首版不提供逐租户、逐工作区的例外豁免名单，仅保留不启用、仅本组织、仅同一组织树三种整体配置。代价是无法单独放行某个外部工作区，需要调整组织整体参与策略。

产品负责人回复：

> 认可

吸纳至 rev 16，例外豁免移出未决项并列为首版非目标。普通目录使用的已知覆盖缺口继续保留，不因没有正式豁免入口而声称所有路径都已受控。

## 2026-09-27 批次确认：装配判定与超管授权

产品负责人要求先讨论多项，再一并落盘，并纠正组织参与限制的生效时机：

> 我们接下来可以讨论多项后你一并更新哈。现在回答当前这一项：因为判定只发生在会话装配阶段，因此只等下一次装配等时候再判定，不在运行中热同步变更来判定

吸纳结果：装配时使用当时策略和组织树，运行中不热同步或逐次操作重判，等下一次实际装配再判断。记录者此前“新操作立即按新规则”的建议撤回；不因此改变其他权限或资产配置的生效机制。

随后记录者提出超管授权规则：仅创建者可授予和撤回工作区超管权限；超管不可转授；撤回权限保留参与关系与其他已有授权；超管自行退出则按既定规则删除关系并失去授权。产品负责人回复：

> 认可

上述结果与目录发现及配置失败处理一起吸纳至 PF-020 rev 17。

## 2026-09-27 批次确认：跨租户实例与 worktree

记录者曾建议实例仅由一个租户持有，产品负责人纠正：

> 实例也可以跨租户啊，这个关系是每个会话装配时候算的，又不是写死在工作区实例里面的

记录者据此澄清：实例可跨租户共用，按各会话租户身份判断关系与配置；共用同一物理目录时 `.omne.local` 是相同的本地来源，不能仅凭目录名承诺租户间私有，不改变租户级私有资源归属。

记录者随后建议：Git worktree 创建本身不登记 Omne 实例或新 Workspace；会话显式选择它作为工作区使用时再关联实例，继续指向原工作区。产品负责人回复：

> 认可，就是这样，而且这样才能真正做到一个会话里面同时有多个 worktrees 让不同的 subagents 并行地隔离工作

对路径已有内容的处理，记录者建议已有目录直接接入、不重新 clone；从中心实例化遇到目标路径冲突则沿 Git 原生结果报告，不自动删除、覆盖或合并，由用户或 agent 决定后续处理。产品负责人回复“认可”。

合并吸纳至 rev 20。记录者此前提出的实例单租户绑定未获接受；本地工作目录分工不等于宿主机安全隔离，也不重新规定 subagent 的会话生命周期。

## 2026-09-27 批次确认：首版收尾原则

记录者依次提出三项收尾建议，产品负责人均回复“认可”：

1. 资源本身就是成果，首版不另设成果发布、交付流程或工作区状态；版本与里程碑沿 Git 和具体任务表达，交付面可上传、下载与查看。
2. 资源不限代码；文件大小及仓库容量随所选 Git 托管服务与部署配置。触及限制须明确失败、保留本地原件，不静默截断、遗漏或假成功；不另建首版大文件产品，LFS 等归技术选型。
3. 多地址表达入口及用途，不建立通用 Workspace 权威地址、自动同步、合并或冲突系统；Git 沿 remote、分支与显式操作，Omne Host 地址指向中心仓库。

产品负责人补充：

> 认可，原则就是首版不要太复杂和钉死太多的条条框框，留好未来良好可拓展空间即可

吸纳至 rev 21；未来管理类型、提供者准入与类型转换不提前补默认规则，人的具体交互由交付面接续。这里是逐项确认的来源，不代表整包评审或正式接受。
