# PF-020：工作区

- 修订：**rev 21**，2026-09-27 · [变更历史](changelog.md)
- 状态：已正式接受（active），接受依据见 [D-074](../../record/decisions/session-workspace-product-acceptance/decision.md)；条款来源与推导见 [decisions](decisions.md)。

## 一、背景与问题

只把工作区理解成一次会话挂上的本地目录，会把三个不同问题混成一个词：

- 工作成果和资源的完整聚合包是什么；
- 这份聚合包在哪台部署节点上被装载并供 agent 工作；
- 系统通过什么地址找到或访问它。

混在一起会造成两个产品问题：同一份工作成果不能自然地跨会话、跨机器继续，
而地址或本地目录又容易被误当成身份和安全边界。PF-020 先确立产品概念边界，
把装载和访问留下可演进的空间。

## 二、目标与非目标

### 目标

1. 定义一个有身份、跨会话持续、具有治理归属的完整资源聚合包。
2. 把逻辑工作区与装载后的工作区实例、访问工作区的地址区分开。
3. 允许多个租户通过不同类型的租户—工作区关系参与同一工作区，并在授权范围内维护同一份共享资源。
4. 允许同一租户在多个物理部署上拥有同一工作区的可访问实例。
5. 允许工作区携带自定义资产，并沿用 PF-002 的资产、设置和权限规则。
6. 让不同类型的 agent 在不同会话中理解自己是在同一工作区边界内持续维护资源。

### 非目标

| 不做什么 | 为什么 |
|---|---|
| 首版提供组织参与限制的逐租户或逐工作区例外豁免 | 仅提供不启用、仅本组织、仅同一组织树三种整体策略 |
| 本版提供工作区所有权移交 | 治理归属保持唯一；参与退出与中心销毁使用已定义流程 |
| 给工作区绑定一个固定、必须预先登记的目标 | 工作区的内容可以让 agent 自行感知目标，或由单次会话指定；目标不是工作区身份的一部分 |
| 为 Omne Host 首版提供非 Git 管理类型或选定具体 Git 托管服务 | 首版仅提供 Git 工作区，后续类型可扩展；是否采用 Gitea、LFS 等仍须后续设计 |
| 重建 Git 的同步、分支、冲突解决和恢复机制 | 复用 Git 原生能力；产品操作的完成与失败表达由后续契约具体化 |
| 首版增加成果发布状态、通用跨地址同步系统或独立大文件产品 | 资源成果、版本与同步使用原生机制；限制随托管服务及部署配置明确呈现 |
| 为每种外部提供者预先规定完整的实现协议 | GitHub、Obsidian、Office 365 等先作为地址提供者类型；各自的 API、版本和同步机制归后续规格 |
| 规定所有资产包内部的完整格式、Schema 或 Cordis 装载实现 | 本 topic 规定共同目录布局、文件职责、共享边界与合并关系；各类包格式和加载实现沿对应设计与规格展开 |
| 把工作区变成执行环境或宿主机安全边界 | 执行环境与权限归 PF-005；工作区地址本身不授予访问权 |
| 重定义工作区资产的设置和权限求值 | 归 PF-002，本 topic 只规定工作区资源如何进入该层 |
| 定义 WebUI、Desktop 或日程和日历交付流程 | 交付面分别预留给 PF-018、PF-019，日程和日历为 PF-021 |

## 三、概念与模型

### 工作区（Workspace）

工作区是**一个带有自身身份、具有治理归属的完整资源聚合包**。它可以包含文件、代码、
数据、知识以及工作区自定义资产等异构资源；它跨会话持续存在，不依赖某一种 agent 类型，
也不要求一直驻留在一台物理机上。

工作区有一个治理所有者租户，也可以通过[租户—工作区关系](#租户工作区关系)授权其他租户参与。
参与租户的实例仍然指向同一个工作区；它们不是各自复制出的另一个工作区。工作区共享资源的
修改会落在同一个工作区状态上，租户自己的设置、偏好和覆盖资产是否共享，按关系与资源层次区分。

工作区不绑定一个固定目标。agent 可以从工作区内容感知当前工作的方向，或在一次会话中
接受临时任务；临时任务完成不会改变工作区的身份。工作区也不是会话、agent、本地目录
或执行环境边界。

### 工作区实例（Workspace Instance）

工作区实例是工作区在某个部署节点上被装载或物化后、可供会话和 agent 使用的一次具体实现。
agent 通过工作区实例读写和维护工作区资源；同一工作区可以在多个部署节点上有多个实例。**实例不绑定单一租户，可以跨租户共用。**每个会话装配时，按本会话的租户身份判断关系、组织参与限制与有效配置，不把这些结果写成实例固定持有的租户归属。

**工作区及工作区实例的生命周期与会话解耦。**部署节点可以先有实例，再由会话选择并附着；也可以在创建会话的请求中指定本地装载路径，先把目标工作区装载为可用实例，再创建会话并附着。会话结束不自动删除工作区或卸载其实例。
不用某个本地实例时，用户后续创建会话不再附着它即可；本地目录是否仍存在，不要求在治理中心增加卸载、清理、归档或恢复流程。中心存储中的工作区销毁，不连带删除或清理已有本地实例；访问已不存在的中心资源仍须如实报告失败。实例不是新的工作区，也不改变工作区的治理所有权；实例
代表哪个租户的参与关系，需要在装配中明确，并保留工作归因；这不要求每次写入重新判断组织参与限制。

### 工作区创建与接入矩阵

工作区创建与接入分为两条路径：中心先有登记，再在本地实例化；或本地先有实例，在首次显式附着时建立租户关系并同步到治理中心。这里比较的是当前租户的中心登记与本地实例的先后，不把“当前租户尚未登记”理解成资源提供者那里没有这个工作区。

| 路径 | Omne Host 托管资源 | 外部提供者资源，如开源 Git 仓库 |
|---|---|---|
| 中心先有，再本地实例化 | 中心已创建或登记工作区及租户关系；部署节点按需装载托管仓库并附着 | 治理中心先登记外部工作区及租户关系；部署节点再从外部来源装载并附着 |
| 本地先有，再首次登记附着 | 本地已有相应实例，用户显式选择登记；关联已有 Omne Host 工作区并向治理中心同步关系，中心已有内容不因登记重复上传 | 用户自行 clone 等获得本地内容，显式登记并附着时建立关系并同步到治理中心；资源继续由原提供者承载 |

**关系登记同步与资源内容同步是两件事。**本地先有这条路径同步的是租户—工作区关系及其必要的关联标识，不自动上传本地文件，不将外部资源托管到 Omne Host；已存在的 Omne Host 工作区也不需要为了建立关系再上传一份。文件提交、拉取和推送仍沿具体管理类型的原生机制按需进行。

### 已有本地目录的首次登记与附着

租户可以将尚未记录在自己名下的本地目录登记为可用工作区，并在首次会话中附着它。例如用户自行 clone 开源项目，进入项目根目录后启动 Omne 新会话，可以在这次使用中完成工作区登记与附着，无须先去治理中心单独建好记录，也不要求由 Omne 重新 clone。

登记使该目录对应的工作区、当前租户与工作区的关系，以及本地实例建立关联；登记并附着成功后，该工作区出现在租户的治理中心，其 `.omne`、`.omne.local` 才按既有规则进入工作区装配。接入已有内容不意味着替换用户文件，也不自动把外部仓库迁移或上传到 Omne Host。

本地路径和 Git remote 可帮助识别资源，但不能单凭地址授予外部写权限、推定租户拥有外部项目，或合并不同工作区身份。登记沿用既有治理与授权规则，既有工作区的识别及关系类型按相应规则确定。

**用户显式选择“作为工作区使用”后才登记并附着。**仅进入目录或普通启动新会话不自动建立关系；普通目录使用不加载工作区装配来源。关系已删除的目录同样可以通过再次显式登记恢复工作区使用，但目录残留配置本身不能触发登记。登记失败不得报告工作区已附着，也不能提前以工作区来源完成装配。

### 治理关系解除与中心销毁

产品生命周期关注治理中心的两件事：租户—工作区关系的解除，以及中心存储的云端工作区销毁后对关联租户关系的连带影响。本地实例保留或清理不作为这两项动作的联动要求；远程销毁也不要求本地实例随之消失。

**解除关系就是删除该租户—工作区关系条目。**条目删除后，治理中心不再以这条关系标识该租户拥有或参与此工作区。本地内容不被删除；在未重新显式登记前，该租户后续会话使用原目录时，只将其作为普通本地文件目录，不再将其识别为当前会话的工作区装配来源。

即使目录下仍有 `.omne`、`.omne.local`，其中资产、设置和规范也不进入 session 装配；其中的第三方兼容开关不能继续触发同目录下 Codex 或 Claude Code 的工作区资产发现。目录内容的存在不恢复已删除的关系，也不自动重新注册工作区。

删除的是指定租户与工作区的关系，不据此删除其他租户的关系或底层资源。普通目录的文件访问仍按现有执行环境和工具权限处理，不将“失去工作区装配身份”解释为本地文件不可访问，也不据此恢复已解除的中心访问授权。

**中心托管工作区确认销毁后，删除指向它的全部租户—工作区关系条目，包括治理所有者和所有参与租户的关系。**各租户的本地目录仍保留；此后使用这些目录的会话按普通目录处理，不加载工作区来源。关系删除不意味着清理文件，也不把本地副本自动登记为替代工作区。

**只有工作区创建者租户，或由创建者明确授予该工作区超管权限的租户，才有资格销毁工作区。**后者称为[工作区超级管理员](../../ubiquitous_language/terms/subjects-and-ownership.md#ul-workspace-super-administrator--工作区超级管理员--workspace-super-administrator)。销毁授权语境中的“所有者”包含上述两类；工作区治理归属仍沿已有唯一治理所有者确定，授予超管权限本身不转移组织归属。

普通参与者、仅有维护或一般管理能力的租户，不因这些能力自动获得销毁资格；组织超级管理员身份本身也不授予此权限。工作区级超管权限不绕过既有组织参与限制或底层资源授权，不扩大为对外部提供者资源的额外权限。

单独解除关系遵循下表：

| 发起租户与动作 | 规则 |
|---|---|
| 普通参与租户退出 | 可以删除自己的参与关系 |
| 工作区超管退出 | 可以删除自己的参与关系，同时失去该工作区的授权 |
| 创建者或工作区超管移除参与租户 | 可以删除对方的参与关系 |
| 普通参与租户移除其他租户 | 不允许 |
| 工作区仍存在时单独删除唯一治理所有者关系 | 不允许，避免留下没有治理归属的工作区 |

工作区超管权限**仅由创建者授予和撤回，工作区超管不能转授**。创建者撤回某租户的超管权限时，保留其参与关系，其他权限依已有授权；移除参与关系则连同该关系承载的授权一起解除，两种动作分别表达。

**本版不提供工作区所有权移交。**唯一治理所有者不能单独退出；要结束该工作区，使用已定义的销毁流程。创建者授予工作区超管权限不构成所有权移交，工作区超管退出不改变治理归属。

已运行会话是否以及何时重装配不由这条后续附着规则推定。中心资源确已销毁与地址暂时不可达应当区分，不能仅凭一次访问失败认定销毁。此处不改变既有授权规则，也不因本地文件仍在而推定已解除的治理授权仍有效。

### 工作区地址（Workspace Address）

工作区地址是找到或访问工作区或其工作区实例的一种地址。它可以是本地文件系统路径、
GitHub 仓库地址、Obsidian vault、Office 365 资源地址、云端存储地址或未来定义的其他地址；
同一工作区可以有多个地址。

地址不是工作区身份，也不是访问凭据。知道一个地址不能绕过租户授权；地址失效或改变，
不自动意味着工作区身份消失。地址有自己的**提供者类型**，例如 `omne-host`、`github`、
`obsidian`、`office365` 或未来提供者；提供者类型描述地址如何被访问，不直接决定工作区类别。
地址表达访问入口与用途，不在统一 Workspace 层另设权威地址、自动同步、跨地址合并或冲突裁决系统。Git 工作区沿 remote、分支与显式 fetch/push 等原生操作决定读写目标；Omne Host 地址指向其中心托管仓库。有多个地址不意味着一次写入自动传播到其他地址。

### 工作区类别（Workspace Category）

工作区类别描述资源与治理语义，而不是某一条地址的字符串格式。当前保留三个可扩展类别：

- **Omne 原生工作区**：资源由 Omne Host 管理，Omne 是主要治理和存储方；
- **外部资源工作区**：资源主要由外部系统提供，例如 GitHub、Obsidian 或 Office 365；
- **组合工作区**：多个资源源共同组成一个工作区，暂作为未来类别。

一个外部资源工作区可以有本地地址和远端地址；一个地址提供者也可以被多个工作区使用。
工作区类别不改变租户关系，也不自动赋予写权限。

### 工作区管理类型

[工作区管理类型](../../ubiquitous_language/terms/scope-and-resolution.md#ul-workspace-management-type--工作区管理类型--workspace-management-type)描述工作区采用的资源持久保存、版本管理与实例同步模型。租户在创建 Omne Host 工作区时选择类型；首版只有 **Git** 可选，未来可扩展其他类型。

这与已有的两项分类分别回答不同问题：

| 属性 | 回答的问题 | Omne Host 首版工作区的值 |
|---|---|---|
| 工作区类别 | 资源主要由谁提供和治理 | Omne 原生 |
| 地址提供者类型 | 某个地址由哪个系统或宿主提供 | 中心地址由 `omne-host` 提供 |
| 工作区管理类型 | 工作区的资源按什么模型保存、版本化和同步 | Git |

Git 不成为 Omne Host 的同义词，Omne Host 也不被固定为只允许 Git 的提供者；未来新增管理类型不改变工作区、实例、地址与租户关系的区分。
类型在创建时选择不表示已经承诺创建后的类型转换，迁移规则尚未定义。

### 统一抽象与原生能力复用

统一抽象为 `Workspace`，Git 管理类型对应的特化为 `GitBasedWorkspace`，即已有的“Git 工作区”。这表达产品类型关系，沿用同一个工作区身份，不预先决定编程语言中的继承或插件结构。未来的 `XXBasedWorkspace` 只是扩展方向的记法，具体类型须另行定义。

Git 工作区直接复用 Git 的提交、版本、分支、worktree、差异、合并与远程同步机制。Omne 定义工作区需要的契约和接口协议，将原生能力接入产品，不重新实现一套对应的资源管理机制。未来其他管理类型同样复用各自已有的能力。

| 职责 | 产品边界 |
|---|---|
| 统一工作区 | 身份、租户关系与组织治理、实例装载及会话附着、资源入口与操作结果的共同约定 |
| 具体管理类型 | 采用底层资源系统的原生管理方式；Git 类型沿用 Git 的版本、协作和同步语义 |
| 面向人的交付面 | 通过契约和接口表达可执行操作、状态与结果，让人能在前端管理和使用工作区 |
| agent 工作 | 通过已有通用工具直接使用熟悉的 Git 能力，自主安排具体工作，不要求先学习或经由 Omne 专门定制的 Git 命令体系 |

接口协议主要服务产品交互与人的使用，不要求为 agent 另造一套 Git 包装工具，也不禁止 agent 在需要时使用产品已有接口。两种操作路径都须遵守既有授权，并如实反映实际资源状态。

PM 推导：共同契约应表达共同需求，具体能力按管理类型提供；未来非 Git 类型不应被要求虚构分支、提交或 worktree 才能接入。具体操作集合、参数、结果协议及能力差异的界面表达，留到产品交互与后续规格设计中细化。

### Omne Host 的首版范围

**首版 Omne Host 只提供 [Git 工作区](../../ubiquitous_language/terms/scope-and-resolution.md#ul-git-workspace--git-工作区--git-workspace)**：中心以托管的 Git 仓库管理共享资源，在获准的部署节点装载相应 Git 工作副本，作为该工作区的实例供人和 agent 持续工作。
Git 仓库地址、分支与提交版本不替代工作区身份；同一个工作区可以有多个实例，实例卸载不等于删除中心托管的资源。

选择 Git 限定了首版的资源管理路线，不限定工作区必须是代码项目；文档、PPT、表格等文件仍可作为工作区资源。文件大小与仓库容量遵循所选 Git 托管服务及部署配置的限制；触及限制时明确报告失败、保留本地原件，不静默截断、遗漏或显示成功。首版不另建大文件预览、转换或传输产品；Git LFS 等方案归技术选型，不因 Git 类型而承诺自动合并任意文件。
`.omne` 的共享同步与 `.omne.local` 不进入共享同步的边界继续成立；具体如何落实到版本管理和同步流程由后续设计明确。

Git 操作由 agent 按下述工作模型自主运用；分支与实例的精确映射、离线恢复、交付版本和具体托管产品另行设计。Omne Host 首版只提供 Git，也不取消外部资源工作区及其他地址提供者的既有概念。

### 资源操作与成果

工作区资源本身承载持续产出；首版不另设成果发布或交付流程，也不增加草稿、已发布、已交付等工作区状态。版本与里程碑由 Git 原生能力和具体任务组织，人的交付面可提供上传、下载与查看入口。操作结果需明确落在本地实例还是某个远端；排队或开始传输不等于完成，写入一处不代表所有地址和实例都已同步。

首版保持简单：明确身份、治理与接入边界，其余尽量复用 Git。保留工作区管理类型及提供者的扩展空间，不预先为尚未支持的类型规定完整行为。

### 会话视角下的本地与 remote

**以会话使用的部署节点实例为本地，中心托管的 Git 资源为 remote。**这是工作视角，不以二者是否碰巧在同一物理机器上决定。工作区资源的双向同步允许异步，不要求本地、remote 和其他实例即时一致。

用户可以在本地或 remote 上传文件、完成变更。**会话不需要立即感知这些变化**，也不以实时推送、自动拉取、打断 agent 或强制刷新上下文作为工作区的必需行为。
用户需要 agent 处理新内容时可以直接告知；agent 随后按实际位置读取本地变更，或检查、获取并整合 remote 变更。agent 也可以在连续工作中自行检查、发现变化，判断是否需要同步。允许稍后感知不代表已自动知道远端变化，实际内容仍由读取与 Git 操作获得。

本地保存、向 remote 提交成功以及另一个实例已经取得该变更是不同结果。用户或 agent 查询、执行操作时，应能判断当前状态和实际成功或失败；不能因接受了异步请求便声称同步已完成。
这项异步约定针对工作区资源同步，不改变租户授权、组织参与限制或资产权限规则；资源到达也不等于自动重装会话资产。

### agent 自主协作与 Git 管理

**产品上将 agent 视作具备完整行动能力、能在连续工作上下文中承担判断与协作责任的工作者。**工作区为它提供可检查、可操作的资源与 Git 能力，而不是要求系统预先替它编排所有工作步骤。

在获准的范围内，agent 自行判断何时检查状态、commit、获取或推送变更；能够发现并处理冲突，选择分支、使用 Git worktree 组织并行工作、避免竞争。产品不要求所有会话挤在同一分支或同一工作树，也不把每次 Git 内容冲突都固定升级为用户裁决。
需要用户给出业务取舍、补充信息或额外授权时，agent 再发起协作；既有权限规则仍适用。自主处理不等于冲突永远可以自动消除，系统必须如实提供操作结果，不能吞掉冲突或伪报成功。

分支与 Git worktree 是 agent 管理同一工作区资源的手段。创建 worktree 只产生原生 Git 工作目录，不自动建立 Omne 实例关联或新的 Workspace 身份；会话显式选择它作为工作区使用时，再识别并关联为实例，仍指向原来的逻辑工作区。

**一个会话可以组织多个 worktree，交给不同 subagent 在各自目录中并行、隔离地工作。**这里的隔离是 Git 工作目录层面的分工，不据此承诺宿主机安全隔离；各会话的身份与装配规则继续成立，不另行决定 subagent 的会话生命周期。

### 本地目录接入与目标路径冲突

将已有目录作为工作区使用时，直接接入原有内容，不重新 clone，不替换用户文件。从中心实例化到指定路径时，沿 Git 原生行为执行；遇到目标路径冲突如实报告，不自动删除、覆盖或合并目录。由用户或 agent 决定复用原目录、换路径或自行整理，Omne 不另建一套目录冲突解决机制。
Git 文件内容冲突与资产发现阶段的同能力来源冲突是不同问题，后者继续遵循本 topic 已定的来源选择规则。

### 租户—工作区关系

租户—工作区关系是治理中心用来记录“这个租户当前有哪些工作区”的持久关系对象。关系至少
区分：

| 关系类型 | 含义 |
|---|---|
| `owner` | 租户拥有工作区治理权，可以管理关系和工作区级治理动作 |
| `participant` | 租户被授权参与同一个工作区；实际能力另由 `read`、`maintain`、`administer` 等授权决定；创建者可明确授予工作区超管权限，销毁资格按前述规则判断，不从一般管理能力自动推定 |

关系存在时记录来源（创建、邀请、导入或公开资源登记）与状态（如有效、暂停）；解除时删除关系条目，不以保留一条“已撤销”的有效对象代替删除。仅仅发现
一个公开地址，不自动建立租户—工作区关系；治理中心的“我的工作区”来自有效关系的投影。

### 组织对参与范围的限制

组织可以对本组织租户设置[工作区参与限制](../../ubiquitous_language/terms/scope-and-resolution.md#ul-workspace-participation-restriction--工作区参与限制--workspace-participation-restriction)，约束以工作区身份参与外部项目的开发、维护。该规则存在下述已知覆盖缺口，不构成完整的防“公器私用”保证。配置包括：

| 限制 | 允许参与的组织范围 |
|---|---|
| 不启用限制（默认） | 不额外限制工作区的所属组织，仍须满足资源与工作区授权 |
| 禁止参与本组织外的工作区工作 | 仅本组织 |
| 禁止参与非本组织同树的其他组织的工作区工作 | 本组织及同一组织隶属树中的其他组织 |

工作区的组织归属按其治理所有者租户所在组织判断；地址提供者不决定组织归属。GitHub 上的工作区可以属于本组织，Omne Host 上的工作区也可以属于其他组织。
“同树”沿用 PF-001 的组织隶属关系与[上级链](../../ubiquitous_language/terms/subjects-and-ownership.md#ul-ancestor-chain--上级链--ancestor-chain)，不另造一套组织关系，也不使不同组织的资产或配置自动继承。

**这两种限制针对开发、维护和写入，不拦只读访问。**只读仍须满足资源本身的访问资格；这条规则不把私有资源变成公开资源。
工作区一侧允许参与、地址公开或实例已经装载，都不能替代参与租户所属组织的许可；反过来，组织允许也不自动授予工作区写权限。
限制跟着会话使用的租户身份，不扩展为对同一自然人的其他租户身份的限制。

**组织策略来自组织治理，不从工作区目录读取。**工作区所有者不能通过修改 `.omne` 或 `.omne.local` 解除参与者所属组织的限制。
**默认不启用限制**，组织可以按需选择仅本组织或仅同一组织树。不启用只表示不增加这项组织范围限制，不自动建立租户关系或授予工作区写权限。**首版不提供逐租户、逐工作区的例外豁免**，同一组织按所选参与范围执行，不另设豁免名单。需要改变范围时调整组织的整体参与策略。**组织参与限制仅在会话装配阶段判定**，使用装配时的组织策略和组织树关系。运行中不热同步这些变化，不在每次维护或写入时重新判定；下一次实际发生装配时再按最新状态判断。策略或组织树变化本身不强制触发重装配，不自动结束会话或删除租户—工作区关系。

这一生效规则只约束本项组织参与限制，不据此改写其他权限或资产配置的生效机制。

### 已知覆盖缺口：普通目录使用

即使组织启用参与限制，当前设计仍不能阻止租户把开源项目 clone 到本地后当作普通文件目录访问、修改和使用。租户没有显式登记并以工作区身份附着时，该目录不进入工作区治理与装配路径；原工作区关系已解除后的目录同样可以按普通目录使用。

因此，这项限制能约束被识别的工作区参与，不能据此声称组织资源只能用于本组织或同树项目，也不能声称已经彻底防止“公器私用”。普通目录操作仍受已有执行环境、工具及资源权限约束，但这些权限不等于本项组织归属限制。

这是当前设计明确保留的覆盖缺口。本版不因此隐式增加自动登记、仓库来源追踪、普通目录禁止访问或宿主机隔离要求；是否扩展覆盖范围需另行产品裁定。


### 两个约定目录

工作区实例的目录下使用两个固定名称的子目录，作为资产、配置和规范的自动发现与加载入口：

```text
工作区实例目录/
├── .omne/        工作区共享目录
└── .omne.local/  工作区本地目录
```

| 目录 | 内容归属与用途 | 共享与同步 |
|---|---|---|
| [工作区共享目录](../../ubiquitous_language/terms/scope-and-resolution.md#ul-workspace-shared-directory--工作区共享目录--workspace-shared-directory) `.omne` | 工作区级共享的资产、配置与规范 | 每次变更应同步到云端，并与获准访问该工作区的其他租户共享；完成时机与失败处理待同步策略定义 |
| [工作区本地目录](../../ubiquitous_language/terms/scope-and-resolution.md#ul-workspace-local-directory--工作区本地目录--workspace-local-directory) `.omne.local` | 实例本地的定制来源，各会话按自身租户身份求值 | 不进入工作区共享上传与同步；共用同一物理实例不保证租户间内容私有 |

**两个目录的结构完全一致**，同一种资产或配置使用相同的组织方式与解析规则，内部布局见下节。AGENTS.md 的支持属于 runtime context 设计，不由这里另定工作区专属规范入口。
这项约定使用文件系统命名空间来组织内容，不要求引入虚拟文件系统或操作系统隔离机制；目录名本身不是工作区身份或权限来源。

多个租户共用同一物理实例时，可以读取同一份 `.omne.local` 来源，再按各会话租户的资格、组织配置、租户配值与权限分别求值。`local` 表示不进入工作区共享同步，不表示目录固定归某一租户，也不独立保证不同租户之间的物理文件隔离。

这不让工作区所有者的租户级私有资产、配置或凭据自动进入其他租户会话。实例本地文件与租户级私有资源是不同来源，实例可共用不改变后者的归属规则。
实例本地内容是否另有跨设备备份或迁移能力尚未定义，不将其混入工作区共享同步。

### 目录内部结构

两个根均采用以下结构；按需创建资产子目录，不要求为未使用的类别创建空目录：

```text
工作区实例目录/
├── .omne/
│   ├── workspace.json       # 扩展发现路径、设置配值、禁用与兼容来源配置
│   ├── skills/
│   │   └── <技能包>/
│   │       ├── SKILL.md
│   │       ├── .omne/skill.json  # 可选的技能定义记录
│   │       ├── scripts/         # 按需携带的资源
│   │       ├── references/
│   │       └── assets/
│   ├── tools/
│   ├── mcps/
│   ├── connectors/
│   ├── loop-extensions/
│   ├── commands/
│   ├── plugins/
│   └── agents/
└── .omne.local/
    └── 与 .omne 相同的结构，按需存放本地定制
```

| 子目录 | 所承载的资产类别 |
|---|---|
| `skills/` | Skill |
| `tools/` | Tool |
| `mcps/` | MCP 接入点 |
| `connectors/` | Connector |
| `loop-extensions/` | Loop Extension |
| `commands/` | Slash Command |
| `plugins/` | Plugin |
| `agents/` | Agent Definition |

**`workspace.json` 是两个根各自的集中配置入口**，承载扩展发现路径登记、允许的设置配值、禁用及 Codex／Claude Code 兼容来源开关；不另设表达相同事实的 `settings.json`。文件职责相同不意味着两份文件内容相同，合并按下节的 local 优先规则。
工作区不增加 `permissions.json` 授权入口；权限、鉴权绑定和凭据仍遵循 PF-002 的归属与过滤规则，不能因为配置位于 local 就改成租户治理配值。

目录名用于组织与携带资产，能力身份仍按类别与 name。技能采用 `SKILL.md` 与可选 `.omne/skill.json` 的已有包形式，资源子目录按需存在；其余类别的包内文件格式沿对应资产设计与规格展开，不统一假定为 Markdown 文件。
技能包内部的 `.omne/skill.json` 属于该技能，不作为另一个工作区自动装载；资源位于 `scripts/` 也不等于获得执行许可。local 替换共享资产时使用被选中的完整资产包，不逐文件拼接两个包。

本布局不赋予顶层 `rules/` 自动向会话注入全部文件的语义；Plugin 中的 Rules 声明式成员沿 PF-002。

**AGENTS.md 支持归 runtime context 设计承接，遵循社区通用规范，嵌套子目录的 AGENTS.md 在所在目录首次被访问时加载。**本 topic 不另设 `.omne/AGENTS.md`、`.omne.local/AGENTS.md` 专属入口，不决定这类上下文的合并、冲突或运行中更新机制。它也不套用下述原生资产目录发现与重载规则；社区规范的具体采用依据和上下文行为由相应设计明确。
### 自动发现范围与配置错误

**原生资产按约定目录自动发现，不要求逐项清单登记。**默认只在工作区实例根部 `.omne`、`.omne.local` 的约定资产位置，按相应资产包格式识别内容。例如 `skills/example/SKILL.md` 可直接发现，不要求在 `workspace.json` 重复列出这个技能。

不递归搜索工作区嵌套子目录里的资产或命名空间；需要额外发现时，在根部 `.omne/workspace.json` 或 `.omne.local/workspace.json` 登记相对路径，支持通配符。两个来源结构相同，沿已有合并优先级处理；不另增工作区顶层的 `workspace.json`。扩展路径的相对基准、匹配语法与重复匹配处理由后续规格明确，不把“支持通配符”视为任意递归搜索。

**软链接始终排除，不发现也不跟随，无论是否登记。**默认发现、显式路径及通配符匹配都遵循此规则；发现路径需要穿过软链接时同样排除。不能先解析链接再将目标当作普通路径加入发现。已识别资产包的正常目录结构和内部资源不属于这里禁止的嵌套工作区搜索。

第三方来源仍按各自开关及受支持的 Skill、MCP、hook 约定发现；同样遵守嵌套范围与软链接排除规则。发现只产生装配候选，不授予执行权限。

| 配置情况 | 装配行为 |
|---|---|
| `.omne` 或 `.omne.local` 不存在 | 正常，该来源为空 |
| 资产目录存在，但该根没有 `workspace.json` | 正常发现默认范围内的资产；未配置项沿各自既定默认规则，尚未裁定的默认值不在此补全 |
| `workspace.json` 存在但无法解析或不符合配置格式 | 明确报告文件和错误，阻止本次装配，不静默忽略 |
| local 配置错误而共享配置正常 | 同样明确失败，不跳过 local 或退回共享值 |

配置字段与 Schema、各类资产包的具体识别格式，由后续规格接续；local 单独为共享资产配值的产品规则见下节。


### 目录的合并与作用域

**两个目录的可用内容取并集；同能力标识的资产由 `.omne.local` 覆盖 `.omne`。**
能力标识沿用 PF-002 的“类别 ＋ name”，不按文件名或自然语言描述是否相似判断，也不把整份 `.omne` 隐藏掉。
例如共享目录有 skill `review` 与 tool `build`，本地目录有 skill `review` 与 skill `notes`：
在都可用且未被锁定的情况下，结果包含本地的 `review`、共享的 `build`、本地的 `notes`。
本地替换作用于各会话独立求值的结果，不改写共享目录中的原资产。

这两个来源共同构成 **PF-002 的工作区资产层**，不是组织、租户之外新增的两个身份层。
它们仍遵循 PF-002 的禁用与使用资格过滤、同标识替换和上层锁定规则；本地来源的优先级不能绕过这些规则。
本地候选被过滤后，不以其同名为由抹掉仍可用的共享候选，随后才按工作区、租户、组织和 official 的既有次序求值。
任一候选被替换或过滤的原因与来源应能被识别；生效资产应能区分来自组织、租户、`.omne` 还是当前租户的 `.omne.local`。

共享设置与本地设置都从工作区层进入求值：**不同设置项取并集，同一设置项以 local 显式配置的值为准；local 未配置该项时采用共享值。布尔设置同样遵循优先级，不取 OR。**
例如共享值为 `true`、local 值为 `false`，结果为 `false`；共享值为 `false`、local 值为 `true`，结果为 `true`。未配置与显式 `false` 不等价。
两处都未配置的项按该项已有默认规则处理；尚未定义默认值的项不因合并规则而获得一个默认值。
这条规则处理同一配置目标的同一设置项，不把被替换资产的设置或凭据迁移给替换它的另一实现，也不把结构化设置值自动拆成递归合并的字段；设置项边界沿其声明。AGENTS.md 等 runtime context 的规范文本不在这条设置合并规则中处理。
双方内容中的权限配值、落点与身份类覆盖、治理类例外仍按 PF-002 过滤；“是我本地写的”不自动把目录里的值变成租户治理配置。

### 仅覆盖共享资产的设置

租户可以只在 `.omne.local/workspace.json` 中，以资产“类别＋name”指定允许的设置覆盖，无须复制共享资产或创建同名本地资产包。继续使用共享资产时，同项 local 显式值优先，未配置项沿已有继承规则；设置覆盖本身不触发资产实现替换，也不放宽权限或上层锁定。

**若按候选过滤与优先级规则选用了同名 local 资产，完整 local 实现的优先级高于这份针对共享资产的设置覆盖。**此时不叠加该覆盖，无论其中设置是否与 local 实现冲突；不采用“冲突项听资产、其他项继续从共享覆盖补入”的逐项混合方式。

| 生效资产来源 | local 针对共享资产的设置覆盖 |
|---|---|
| 仍使用共享资产，没有选用同名 local 替换件 | 按允许的设置与既定优先级应用 |
| 已选用同名 local 资产 | 使用完整 local 实现，不应用这份针对共享实现的覆盖 |

具体配置字段由后续规格表达；这里不把共享实现的设置、凭据或包内文件迁移给另一份 local 实现。

### 同工作区的第三方资产

两个目录都能配置是否使用同工作区的第三方 harness 资产。**Codex 与 Claude Code 各有一个独立布尔开关**，按 harness 扩展；Codex 开关统一覆盖 `.agents` 与 `.codex`，不要求用户分别管理两个目录。
两个来源的开关位于各自的 `workspace.json`，按上述设置优先级合并：local 显式关闭可以覆盖共享启用，local 未配置则采用共享值。**两个兼容来源默认都关闭，必须显式开启。**两处均未配置时不发现对应来源；具体字段格式由后续规格明确。

兼容范围只包含 **Skill、MCP、hook**；hook 经已有兼容层成为 Loop Extension。开启后直接识别原位置的受支持资产，无须复制到 Omne 目录或逐项重新登记；文件位置由对应 harness 的工作区约定识别，不能仅限于三个目录名。例如 Claude Code 的项目 MCP 配置位于工作区根 `.mcp.json`。
读取范围限于同工作区，本项开关不授权读取用户家目录的配置；不因此导入第三方的整体权限政策、Agent Definition 或指令文件。外部来源中的本地内容不因兼容读取变为共享同步内容；共用物理实例时可读取的来源仍按会话身份分别求值，不把本地目录视为租户隐私保证。

兼容读取保留源文件，不自动改写原件。共同的 Skill 基础格式与 MCP 协议不意味着第三方专属字段或配置外壳全部相同；格式、hook 事件及输出按受支持的兼容范围转换，不支持的内容明确报告。
转换后的候选仍进入工作区资产层，遵循 PF-002 的过滤、锁定、禁用与干预力约束；开启来源不等于授权运行其中的命令。

**可用候选中，Omne 原生的同能力资产优先于兼容来源，原生内部 local 优先于共享。**Codex 与 Claude Code 提供同能力但不同内容时明确显示冲突，由用户选择，不静默指定一家优先；不涉及冲突的能力仍取并集。来源与被覆盖原因可见，不能因多个发现路径而重复装载同一来源、重复触发同一 hook。
子目录发现与软链接排除遵循前述统一发现规则，开关变更按下述装配与显式重载规则生效。具体版本支持矩阵与相同来源的识别方式，由后续规格明确。

### 装载、附着与装配

装载实例使工作区资源可访问；会话显式附着（attach）实例后，按**会话所属租户**的组织、租户配置，
以及所附着实例中的 `.omne` 与 `.omne.local` 进行求值。不能把工作区所有者租户的凭据、私有资产或有效配置直接交给参与租户。
同一工作区的共享内容可以相同，不同租户的有效装配结果可以不同。

自动发现两个目录中的内容，不等于自动运行目录中的程序。求值与初始化继续遵循 PF-002、PF-004：
先求出可用资产，再按 Agent Definition 组装、投影属性与计算有效值；只有实际装配且获准启动的组件才进入初始化。
工作区带来的本地命令型 MCP 与命令型 hook 仍默认不启用，由对应租户在自己的设置中逐件打开。
**工作区资产和配置在装配时读取，不因文件变化自动静默重载。**新增、修改、替换或删除资产，改变设置、禁用及兼容开关，都在下一次实际装配时重新发现与求值。Git 同步完成也不自动改写当前装配；agent 可以直接读取新文件内容，但这不等于会话装配已经改变。

**会话装配设计提供资产热重载命令。**已有会话需要应用资产更新时，由显式执行命令触发重新加载；不能靠目录监听或后台同步自动静默应用。重载先校验待加载的数据，**校验通过后才替换 agent runtime 内存中的相应数据**。校验失败时明确报告原因，原有内存数据尚未替换；不将失败表述为已更新，也不进入部分新、部分旧的校验失败结果。

命令的具体名称、参数、校验之后的运行中构成切换与外部组件生命周期，由会话装配与对应交付面设计接续；上述校验失败边界不被扩大为任意外部副作用都可回滚的保证。

与 PF-004 的装配清单和构成变化规则相衔接：命令是显式触发入口，增量装载还是重新装配按相应能力与生命周期约束确定。本 topic 不以热重载命令取消必需绑定的生命周期约束。

## 四、产品规则

1. **治理归属与参与**：每个工作区有一个治理所有者租户，也可以有多个被授权参与的租户。
   参与关系不转移所有权；跨租户访问默认拒绝，通过治理关系使用工作区须有有效的租户—工作区关系。关系删除后的本地目录使用与装配按[关系解除规则](#治理关系解除与中心销毁)处理。
2. **持续性**：工作区身份和资源聚合跨会话持续。一次会话结束、一个 agent 类型更换或一个
   实例卸载，不等于工作区被删除。
3. **无固定目标**：工作区不要求预先绑定一个明确目标。单次会话可以指定目标，agent 也
   可以从资源内容理解目标；这些目标不成为工作区的固定属性。
4. **先装载再工作**：会话以工作区身份使用资源时，必须使用一个已选择且可访问的工作区实例，或由后续装载流程得到
   实例，agent 才能持续读写工作区资源。未选择、未授权或装载失败时，系统必须显式报告，
   不能静默创建另一份工作区来假装成功。
5. **共享维护**：参与租户可以在授权范围内装载同一工作区；其对共享资源的写入落在同一个
   工作区状态上，并保留租户、账号、实例和会话的归因。租户专属的设置和覆盖资产不因共享
   维护自动变成工作区共享资源。
6. **多地访问**：同一工作区可以同时或先后在多个部署节点上有实例，具体并发与一致性策略
   另行决定；产品概念不把工作区绑定到某台机器。
7. **类别与地址提供者分离**：工作区类别描述资源与治理语义；地址提供者类型描述访问该地址
   的外部系统或宿主。一个工作区可以有多个不同提供者的地址，不因此自动变成多个工作区。
8. **地址与身份分离**：地址可增删、替换或暂时不可达，不直接改变工作区身份；访问地址
   必须经过租户授权和实例可用性检查。
9. **自定义资产**：工作区可以携带自定义资产。它们进入工作区资产层，并遵守 PF-002：
   工作区可提供能力和偏好，但权限、落点与身份类设置及治理类例外不能借工作区放宽；
   工作区资产的权限取最严值。
10. **本地边界**：工作区实例的本地路径不是宿主机访问边界。agent 能访问什么由 PF-005
   的执行环境和具体命令权限决定。
11. **显式选择**：核心语义不因 agent 恰好运行在某个当前目录就隐式选择工作区。交付面可以
   根据当前目录或最近使用记录提出默认值，但提交给会话的仍必须是一次明确选择。
12. **组织参与限制**：以工作区身份开发、维护和写入须同时满足所属组织允许的参与范围与工作区自身授权；默认不启用限制，启用后的两种范围限制均不拦只读访问。普通目录使用不在本项当前覆盖范围内。
13. **目录发现与合并**：`.omne` 和 `.omne.local` 位于实例目录下，结构相同；可用内容取并集，同能力资产 local 优先，仍受 PF-002 约束。
14. **共享与本地分离**：`.omne` 的变更纳入共享同步，`.omne.local` 是实例本地来源，不进入共享上传与同步；共用实例的租户可分别求值这份来源，不保证其物理内容彼此私有。
15. **设置合并**：不同项取并集，同一项 local 显式值优先；布尔值亦如此，未配置不等于 `false`，不以 OR 替代优先级。
16. **第三方复用**：Codex、Claude Code 分别开关，仅复用同工作区 Skill、MCP、hook；Omne 原生同能力资产优先，两个第三方来源的不同内容冲突须显式选择。
17. **Omne Host 首版类型**：租户创建时选择工作区管理类型，首版仅提供 Git；中心托管 Git 资源，部署节点装载 Git 工作副本为实例，类型可在未来扩展。
18. **生命周期解耦**：实例可以先于会话存在；也可指定本地路径先装载目标工作区、再创建会话。会话结束不自动卸载实例或删除工作区。
19. **异步资源同步**：会话视实例为本地、中心为 remote；本地与远端变更无需即时同步或即时进入 agent 上下文，由用户告知或 agent 自主发现后按需处理。
20. **agent 自主管理**：在授权范围内，agent 自主同步、处理 Git 冲突，并运用分支和 worktree 协调工作；不以强制即时感知或每次冲突必交用户处理作为产品前提。
21. **原生能力复用**：`Workspace` 的 Git 特化为 `GitBasedWorkspace`；资源管理复用 Git，Omne 定义接入产品所需的契约与接口，主要面向人的交付面，不要求 agent 使用专门定制的 Git 命令体系。

## 五、取舍

### 5.1 选择逻辑身份而不是目录身份

目录适合做一种本地地址，却不能表达 GitHub、云端或多台机器上的同一资源聚合。工作区拥有
独立身份后，地址可以变化，实例可以迁移，跨会话连续性也不依赖当前机器。

### 5.2 选择实例作为 agent 的工作入口

agent 需要一个可读写、可观测的具体装载结果；直接让 agent 面向抽象地址会把网络、凭据和
同步失败混进每次资源操作。工作区实例承接这一层，具体装载和同步机制留给后续设计。

### 5.3 选择不固定目标

把目标写死在工作区身份里会让同一资源聚合不能服务连续但不同的任务，也会把 agent 对内容的
理解降为一项静态配置。目标可以由内容感知或由单次会话指定，工作区仍保持稳定身份。

### 5.4 选择“类别”与“地址提供者”分轴

GitHub、Obsidian 和 Office 365 的资源形状、版本和写入语义不同，但它们都可以通过统一的
工作区抽象被治理和装载。把提供者直接当成工作区类型，会在一个工作区有多个地址时产生冲突；
把提供者作为地址属性、把类别作为资源与治理语义，则可以在统一核心之上暴露提供者特有能力。

### 后续规格与实现需要细化的内容

以下内容在已确定的产品边界内进入契约或实现设计，不单独作为新产品需求：
