# PF-020：工作区

## 一、背景与问题

只把工作区理解成一次会话挂上的本地目录，会把三个不同问题混成一个词：

- 工作成果和资源的完整聚合包是什么；
- 这份聚合包在哪台部署节点上被装载并供 agent 工作；
- 系统通过什么地址找到或访问它。

混在一起会造成两个产品问题：同一份工作成果不能自然地跨会话、跨机器继续，
而地址或本地目录又容易被误当成身份和安全边界。PF-020 先确立产品概念边界，
把装载和访问留下可演进的空间。

## 二、目标与非目标

### 目标

1. 定义一个有身份、跨会话持续、具有治理归属的完整资源聚合包。
2. 把逻辑工作区与装载后的工作区实例、访问工作区的地址区分开。
3. 允许多个租户通过不同类型的租户—工作区关系参与同一工作区，并在授权范围内维护同一份共享资源。
4. 允许同一租户在多个物理部署上拥有同一工作区的可访问实例。
5. 允许工作区携带自定义资产，并沿用 PF-002 的资产、设置和权限规则。
6. 让不同类型的 agent 在不同会话中理解自己是在同一工作区边界内持续维护资源。

### 非目标

| 不做什么 | 为什么 |
|---|---|
| 给工作区绑定一个固定、必须预先登记的目标 | 工作区的内容可以让 agent 自行感知目标，或由单次会话指定；目标不是工作区身份的一部分 |
| 决定中心存储、单一事实源或云端服务形态 | GitHub、对象存储、本地目录等只是可能的地址或承载方式，产品策略尚未完成 |
| 决定双向同步、冲突解决、并发写入和断线恢复 | 这些是后续策略与技术契约要共同回答的问题 |
| 为每种外部提供者预先规定完整的实现协议 | GitHub、Obsidian、Office 365 等先作为地址提供者类型；各自的 API、版本和同步机制归后续规格 |
| 规定工作区的具体文件格式、Schema 或 Cordis 装载实现 | 属于规格与实现投影 |
| 把工作区变成执行环境或宿主机安全边界 | 执行环境与权限归 PF-005；工作区地址本身不授予访问权 |
| 重定义工作区资产的设置和权限求值 | 归 PF-002，本 topic 只规定工作区资源如何进入该层 |
| 定义 WebUI、Desktop 或日程和日历交付流程 | 交付面分别预留给 PF-018、PF-019，日程和日历为 PF-021 |

## 三、概念与模型

### 工作区（Workspace）

工作区是**一个带有自身身份、具有治理归属的完整资源聚合包**。它可以包含文件、代码、
数据、知识以及工作区自定义资产等异构资源；它跨会话持续存在，不依赖某一种 agent 类型，
也不要求一直驻留在一台物理机上。

工作区有一个治理所有者租户，也可以通过[租户—工作区关系](#租户工作区关系)授权其他租户参与。
参与租户的实例仍然指向同一个工作区；它们不是各自复制出的另一个工作区。工作区共享资源的
修改会落在同一个工作区状态上，租户自己的设置、偏好和覆盖资产是否共享，按关系与资源层次区分。

工作区不绑定一个固定目标。agent 可以从工作区内容感知当前工作的方向，或在一次会话中
接受临时任务；临时任务完成不会改变工作区的身份。工作区也不是会话、agent、本地目录
或执行环境边界。

### 工作区实例（Workspace Instance）

工作区实例是工作区在某个部署节点上被装载或物化后、可供会话和 agent 使用的一次具体实现。
agent 通过工作区实例读写和维护工作区资源；同一工作区可以在多个部署节点上有多个实例。

本版先把“工作区实例”作为装载结果的产品对象名称，实例的精确身份、可用状态、并发写入、
失效、卸载和同步生命周期尚未定下。实例不是新的工作区，也不改变工作区的治理所有权；实例
代表哪个租户的参与关系，需要在装载和每次写入时可被识别。

### 工作区地址（Workspace Address）

工作区地址是找到或访问工作区或其工作区实例的一种地址。它可以是本地文件系统路径、
GitHub 仓库地址、Obsidian vault、Office 365 资源地址、云端存储地址或未来定义的其他地址；
同一工作区可以有多个地址。

地址不是工作区身份，也不是访问凭据。知道一个地址不能绕过租户授权；地址失效或改变，
不自动意味着工作区身份消失。地址有自己的**提供者类型**，例如 `omne-host`、`github`、
`obsidian`、`office365` 或未来提供者；提供者类型描述地址如何被访问，不直接决定工作区类别。
地址还可以标记为权威来源、镜像或导入/导出通道；这些作用的具体约束尚未定下。

### 工作区类别（Workspace Category）

工作区类别描述资源与治理语义，而不是某一条地址的字符串格式。当前保留三个可扩展类别：

- **Omne 原生工作区**：资源由 Omne Host 管理，Omne 是主要治理和存储方；
- **外部资源工作区**：资源主要由外部系统提供，例如 GitHub、Obsidian 或 Office 365；
- **组合工作区**：多个资源源共同组成一个工作区，暂作为未来类别。

一个外部资源工作区可以有本地地址和远端地址；一个地址提供者也可以被多个工作区使用。
工作区类别不改变租户关系，也不自动赋予写权限。

### 租户—工作区关系

租户—工作区关系是治理中心用来记录“这个租户当前有哪些工作区”的持久关系对象。关系至少
区分：

| 关系类型 | 含义 |
|---|---|
| `owner` | 租户拥有工作区治理权，可以管理关系和工作区级治理动作 |
| `participant` | 租户被授权参与同一个工作区；实际能力另由 `read`、`maintain`、`administer` 等授权决定 |

关系还要记录来源（创建、邀请、导入或公开资源登记）和状态（有效、暂停、撤销）。仅仅发现
一个公开地址，不自动建立租户—工作区关系；治理中心的“我的工作区”来自有效关系的投影。

### 关系

```text
租户 ──owner/participant 关系──> 工作区 ──聚合──> 文件、代码、数据、知识、自定义资产……
                                  │  ├─可有多个──> 工作区地址 ──提供者类型──> Omne Host / GitHub / Obsidian / Office 365 …
                                  │  └─可装载为多个──> 工作区实例 ──供会话/agent 工作──>
```

## 四、产品规则

1. **治理归属与参与**：每个工作区有一个治理所有者租户，也可以有多个被授权参与的租户。
   参与关系不转移所有权；跨租户访问默认拒绝，只有有效的租户—工作区关系才能访问。
2. **持续性**：工作区身份和资源聚合跨会话持续。一次会话结束、一个 agent 类型更换或一个
   实例卸载，不等于工作区被删除。
3. **无固定目标**：工作区不要求预先绑定一个明确目标。单次会话可以指定目标，agent 也
   可以从资源内容理解目标；这些目标不成为工作区的固定属性。
4. **先装载再工作**：会话必须使用一个已选择且可访问的工作区实例，或由后续装载流程得到
   实例，agent 才能持续读写工作区资源。未选择、未授权或装载失败时，系统必须显式报告，
   不能静默创建另一份工作区来假装成功。
5. **共享维护**：参与租户可以在授权范围内装载同一工作区；其对共享资源的写入落在同一个
   工作区状态上，并保留租户、账号、实例和会话的归因。租户专属的设置和覆盖资产不因共享
   维护自动变成工作区共享资源。
6. **多地访问**：同一工作区可以同时或先后在多个部署节点上有实例，具体并发与一致性策略
   另行决定；产品概念不把工作区绑定到某台机器。
7. **类别与地址提供者分离**：工作区类别描述资源与治理语义；地址提供者类型描述访问该地址
   的外部系统或宿主。一个工作区可以有多个不同提供者的地址，不因此自动变成多个工作区。
8. **地址与身份分离**：地址可增删、替换或暂时不可达，不直接改变工作区身份；访问地址
   必须经过租户授权和实例可用性检查。
9. **自定义资产**：工作区可以携带自定义资产。它们进入工作区资产层，并遵守 PF-002：
   工作区可提供能力和偏好，但权限、落点与身份类设置及治理类例外不能借工作区放宽；
   工作区资产的权限取最严值。
10. **本地边界**：工作区实例的本地路径不是宿主机访问边界。agent 能访问什么由 PF-005
   的执行环境和具体命令权限决定。
11. **显式选择**：核心语义不因 agent 恰好运行在某个当前目录就隐式选择工作区。交付面可以
   根据当前目录或最近使用记录提出默认值，但提交给会话的仍必须是一次明确选择。

## 五、取舍

### 5.1 选择逻辑身份而不是目录身份

目录适合做一种本地地址，却不能表达 GitHub、云端或多台机器上的同一资源聚合。工作区拥有
独立身份后，地址可以变化，实例可以迁移，跨会话连续性也不依赖当前机器。

### 5.2 选择实例作为 agent 的工作入口

agent 需要一个可读写、可观测的具体装载结果；直接让 agent 面向抽象地址会把网络、凭据和
同步失败混进每次资源操作。工作区实例承接这一层，具体装载和同步机制留给后续设计。

### 5.3 选择不固定目标

把目标写死在工作区身份里会让同一资源聚合不能服务连续但不同的任务，也会把 agent 对内容的
理解降为一项静态配置。目标可以由内容感知或由单次会话指定，工作区仍保持稳定身份。

### 5.4 选择“类别”与“地址提供者”分轴

GitHub、Obsidian 和 Office 365 的资源形状、版本和写入语义不同，但它们都可以通过统一的
工作区抽象被治理和装载。把提供者直接当成工作区类型，会在一个工作区有多个地址时产生冲突；
把提供者作为地址属性、把类别作为资源与治理语义，则可以在统一核心之上暴露提供者特有能力。

## 七、验收关注点

本版的可观察验收场景见 [acceptance.md](acceptance.md)。后续每次补充存储、同步或交付策略，
都要重新检查“身份、实例、地址”三者是否仍能区分。

## 九、未决项

1. 工作区身份的具体形式、可见名称、删除/归档及恢复生命周期。
2. 租户—工作区关系是否允许转授权、跨组织参与和治理权委托。
3. 工作区共享资源与租户专属设置/覆盖资产的精确分层。
4. 工作区实例的精确身份、状态转移、卸载与失效语义。
5. 多个实例同时写入时的并发、一致性和冲突处理。
6. 哪个地址或存储是权威来源，是否允许多个地址作为可写副本。
7. 地址提供者的能力矩阵、凭据引用、版本监听和不可达恢复策略。
8. 地址提供者类型如何扩展和发现，谁能注册新的提供者。
9. 公开地址是否只建立发现记录，还是可以自动建立只读租户关系。
10. 会话究竟选择逻辑工作区后再解析实例，还是直接选择一个已存在的实例；两者在交付面上
   如何表达。
