**本 topic 有意没有立的几个名字**，以及为什么：

| 没立 | 为什么 |
|---|---|
| 「客户端」 | 正文里它只是「向中心问事的那一端」的日常说法；**中心不认客户端，只认登录状态**（[§6.2](design.md#62-中心只认登录状态不认客户端)）——立了它就等于承认中心眼里有这个东西。本版它就是 PF-016 的交付面在某台机器上的那一份 |
| 「立中心」「搬家」「升级」 | 都是运维动作，是过程；产品要说的已经用治理中心的[状态流转](flows.md#三状态流转)说完了，不需要各给一个词 |
| 「不半开」 | 是一条规则（[§6.6](design.md#66-要么整个起来要么不起来)），正文里作为规则名足够；立成词条会变成第二份权威 |
| 「平台管理员」「部署管理员」 | **刻意不立**：这两个名字一旦存在，就会有人往里放东西。[运维者](design.md#运维者)不是它们 |
| 「交接凭证」 | [技术侧明说它没有产品出处、不立词条](../../spec/data/identity-values/v1/contract.md#s-35-为什么不立统一语言词条)；本 topic 给的是它背后那把密钥的产品含义，不给它本身 |
| 「版本」 | 日常义：中心装的是哪一版。正文只要求它在体检里读得到、对不上时明说；**哪些版本算对得上归技术设计**，立了词条就得替它定一个产品层的比较规则，而本版没有 |
| 「数据所在」 | 日常义：中心的数据放在哪儿。正文只关心它够不够得着；放在哪、是什么，归运维者与技术设计。立成词条会让人以为产品在它身上定了什么 |
| 「备份」「恢复」 | 日常义，而且[在产品之外做](design.md#非目标)；产品只定恢复的后果（[flows 1.6](flows.md#16-从备份恢复)）。立成词条等于承认它们是产品动作 |

**对象条目**：本 topic **不新立任何对象**。[治理中心那一条](../../domain_objects/objects.md#ul-governance-center--治理中心)的「生灭」与「未裁」栏由本 topic 补上依据（[§四](#四已知的来源问题)），条目本身由主线更新。

## 六、调研参照

**这一节里的东西全部是参照与反例，不是依据。**
被采纳的做法已经写进[§二 PM 推导](#二pm-推导)并说清了它为什么适用于本产品；
**没有任何一条因为「某个知名产品这么做」而进入正文。**
下表区分**观察到的事实**与**我对其理由的推测**。

| 看的是什么 | 观察到的事实（来源） | 我的推测（**标明是推测**） | 对本设计的用处 |
|---|---|---|---|
| **第一个管理员怎么产生** | Keycloak：临时引导管理员「只在服务器初次启动、master realm 尚不存在时创建」，界面与日志都标它是临时的，「之后需要手动删除」；全部管理员丢失时的恢复命令要求「所有节点先停下」（[bootstrap-admin-recovery](https://www.keycloak.org/server/bootstrap-admin-recovery)）。Gitea：第一个注册的用户自动成为管理员——**官方安装页没有这句话**，只在第三方安装指南里见到（[Scaleway](https://www.scaleway.com/en/docs/tutorials/self-hosted-repository-gitea/)、[Linuxize](https://linuxize.com/post/how-to-install-gitea-on-ubuntu-20-04/)），按未经官方核实的观察记。Mattermost：「新安装系统上加入的第一个用户被赋予 system admin 角色」（[roles](https://docs.mattermost.com/end-user-guide/collaborate/learn-about-roles.html)）。Grafana：默认 admin/admin，「Set once on first-run」（[configure-grafana](https://grafana.com/docs/grafana/latest/setup-grafana/configure-grafana/)） | 推测：三家都有一个**平台级**的管理员角色，所以「第一个」必须是一个特殊的人；Keycloak 把它做成临时账号，是因为一个常驻的引导账号就是一个众所周知的后门 | **全部没采纳**（[推导 1](#二pm-推导)）：本产品没有平台级角色，建组织的人就是超管，「第一个」不需要任何特殊待遇。**采纳的是 Keycloak 那个失败模式的教训**：引导账号是后门，所以本产品一个也不留。Keycloak「恢复要先停节点」印证了「运维者的杆子是对机器的控制，不是一个账号」（[推导 2](#二pm-推导)） |
| **运维那一层与业务管理那一层怎么分** | GitHub Enterprise Server：Management Console 管「初始设置、DNS、主机名、SSL、认证、监控、维护、升级、许可」，用**安装时设的 root site administrator 密码**登录，与 GitHub 用户账号分开；只有 root 能建删 Management Console 用户（[about](https://docs.github.com/en/enterprise-server@3.14/admin/administering-your-instance/administering-your-instance-from-the-web-ui/about-the-management-console)、[managing access](https://docs.github.com/en/enterprise-server@3.14/admin/administering-your-instance/administering-your-instance-from-the-web-ui/managing-access-to-the-management-console)）。Headscale：用户与预授权密钥都由「Headscale administrator」在服务器命令行上建，文档里没有任何「第一个管理员」的概念——谁有服务器就谁管（[registration](https://headscale.net/stable/ref/registration/)）。Vault：封存状态下「只能解封与查状态」，「没有 root key shares 谁也读不了数据」（[seal](https://developer.hashicorp.com/vault/docs/concepts/seal)） | 推测：GHES 之所以给运维者一套独立凭据，是因为它有网页、要远程管；Headscale 不给，是因为管理动作本来就只在那台机器上发生。Vault 把「能开机的人」与「能读秘密的人」拆开，是因为持有解封密钥的运维者不该顺手读到秘密 | **采纳 Headscale 那种「运维者 = 握着机器的人」**（[推导 2](#二pm-推导)）：本产品没有网页，运维动作只在中心所在的机器上发生，不需要第二套身份体系。**采纳 Vault 那条分界**：运维者读不到秘密的值（[§6.14](design.md#614-运维者读不到任何秘密的值)）。**没采纳** GHES 的独立凭据与 Vault 的封存仪式——后者要人守在机器旁解封，而本产品的据点依赖中心无人值守地起来 |
| **丢了那把密钥会怎样** | GitLab：「secrets 文件里有数据库加密密钥。丢了它，GitLab 就无法解密数据库里任何加密过的值」，两步验证与 CI 变量都在内，文档要求与备份分开存（[backup](https://docs.gitlab.com/administration/backup_restore/backup_gitlab/)）；论坛上「Lost gitlab-secrets.json」是反复出现的求助帖（[一例](https://forum.gitlab.com/t/lost-gitlab-secrets-json/26627)）；有 issue 指出丢了之后系统「不能优雅恢复」、报错难懂（[#23499](https://gitlab.com/gitlab-org/gitlab/-/issues/23499)）。Gitea：SECRET_KEY「非常重要，丢了它，用它加密的数据（比如 2FA 密钥）再也解不开」（[config cheat sheet](https://docs.gitea.com/administration/config-cheat-sheet/)）。Grafana：secret_key「不能更换，除非把数据源设置重新编码」（[configure-grafana](https://grafana.com/docs/grafana/latest/setup-grafana/configure-grafana/)） | 推测：三家都让一把密钥同时承担「加密数据」，于是丢了它就是丢数据；报错难懂是因为「缺密钥」在启动之后才被发现 | **这是本设计里最直接被反面案例塑造的一条**（[推导 12](#二pm-推导)）：部署密钥**什么都不加密**，丢了的代价止于「重新生成」；缺了在**启动时**就发现并点名（[§6.6](design.md#66-要么整个起来要么不起来)），不在跑起来之后才报一个看不懂的错。**生成时告诉运维者「唯一一份、丢了起不来」**也来自这里 |
| **部署身份与地址** | Headscale：`server_url` 注释是「客户端要连的 URL」；Noise 私钥「缺了会自动生成」（[config-example](https://github.com/juanfont/headscale/blob/main/config-example.yaml)）；社区教程称删掉那把私钥后「每个节点都要重新注册」（[PerLod](https://perlod.com/tutorials/how-to-fix-headscale-errors/)，非官方）。Grafana `root_url`「是浏览器访问 Grafana 的完整 URL，用 OAuth 时回调地址要靠它」；Mattermost 的 Site URL 没设对时服务器「failed to load configuration ... invalid config」起不来（[论坛](https://forum.mattermost.com/t/error-failed-to-load-configuration-failed-to-load-invalid-config-config-isvalid-model-config-is-valid-site-url-app-error/13193)）；GitLab 改 `external_url` 后要清缓存、链接才对（[forum](https://forum.gitlab.com/t/how-to-redirect-old-to-new-external-url-after-changing-the-external-url/19021)） | 推测：Headscale 把身份押在一把私钥上，所以丢钥即全员重注册——那正是本产品不想付的代价；Grafana/Mattermost/GitLab 要知道自己的地址，是因为它们生成链接与回调 | **两条都采纳为反例**：[中心标识不押在密钥上](design.md#中心标识)（[推导 13](#二pm-推导)），[中心不知道自己的地址](design.md#612-同一个中心换了地址还是它另一个中心必须被认出来)（[推导 14](#二pm-推导)）——本产品没有网页没有链接，「地址配错了起不来」这一整类失败直接不存在 |
| **重启之后登录还在不在** | Keycloak 26 起「持久化用户会话」默认开启：「用户在重启或升级全部 Keycloak 实例之后仍保持登录」（[官方博客](https://www.keycloak.org/2024/12/storing-sessions-in-kc26)）；此前的滚动重启丢会话是被记录的问题（[#37825](https://github.com/keycloak/keycloak/issues/37825)） | 推测：他们改成默认持久化，是因为「重启把大家都踢下线」在生产里是真实的抱怨 | 印证[推导 9](#二pm-推导) 的方向；但本产品那条是从 PF-001「失效跨重启成立」推出来的，不是抄来的 |
| **配置错了要不要起来** | Mattermost：Site URL 不合法时服务器拒绝加载配置、不启动（同上）。Keycloak：引导管理员命令要求所有节点先停 | 推测：起不来比起来一半好查——一个跑着但有一半功能坏掉的服务，报错会出现在离原因很远的地方 | 支持[§6.6 不半开](design.md#66-要么整个起来要么不起来)（[推导 8](#二pm-推导)）；本产品的理由更硬——中心拥有的事实彼此咬合 |
| **握着机器的人能不能被挡住** | Gitea 文档明说：能改数据库的人就能拿到管理员权限，并能以运行 Gitea 的系统用户身份做任何事（[config cheat sheet](https://docs.gitea.com/administration/config-cheat-sheet/)） | —— | 支持[§6.13 把边界说实话](design.md#613-运维者没有任何一扇门通向账号能做的事)：产品挡的是「产品自己开的门」，不是握着磁盘的人 |
