# PF-004 变更历史

记录**产品设计本身**的演进：哪一版改了什么含义、为什么改、下游要复核什么。
错别字、链接修复、段落搬家不记这里。

技术投影用 `provenance.json` 引用具体 rev，所以这里的 rev 不准会直接传导到实现侧。

## rev 3 — 2026-09-17

**精化重建的触发点。**§5.3 那张「三个时刻」表里，装配时那一格原先只写
「运行实例重建」，读者只看表会以为**构成一变就重建**。

起因是 [PF-006](../PF-006-tools-and-skills/README.md) 与
[PF-007](../PF-007-meta-capabilities/README.md) 落下来之后出现了具体场景：
**agent 在运行中自己造出一个工具**。若照表字面理解，它每造一件家伙什
就要把自己重启一次——而重启会打断它正在做的那件事。

| | rev 2 | rev 3 |
|---|---|---|
| §5.3 表「变了会怎样」 | 一律**重建** | **分两条路径**：Agent Definition 变了 → 下一次 run 重建；**运行中增量装载 → 不重建** |
| §6.3「增量装载是个例外」 | 已有这条规则 | **点明 agent 自己造的工具走的就是这一条**，并写清另一条路径为什么无条件重建 |

### 这不是推翻，是把已有的规则搬到表上

§6.3 的判据一个字没改，**仍然是**：

> 往实例里新增一个可选能力，和把它正在用的必需绑定换掉，是两回事。

改的是 §5.3——那张表被称为「本 topic 最要紧的一张表」，
**只看表的人此前拿不到这个例外**。

### 为什么「改了 Definition」无条件重建，不去区分改的是什么

比对差异再判断值不值得重建，**代价大于收益**；而重建的时机是
**下一次 run**，本来就不打断当前工作。

### 下游要复核什么

- **不要把「构成变了」和「Definition 变了」当成同一件事。**前者含运行中增量装载。
- agent 创建工具的产品语义在
  [PF-006 §6.9](../PF-006-tools-and-skills/design.md#69-agent-创建与修改工具技能本版只定三条)，
  本 topic 只负责说明它为什么不触发重建。

## rev 2 — 2026-09-17

**只改表述，不改含义**：把「执行环境」那几处写严，避免与
[PF-005](../PF-005-execution-environments-and-sandboxes/README.md) 并排读时被当成冲突。

| | rev 1 | rev 2 |
|---|---|---|
| §5.2 表里执行环境的「装配时确定」 | 「**接入点**」——词不达意，易被读成「装配时绑定了一个具体环境，此后跟着实例走」 | **「需要哪几类环境」**（由装进来的工具决定，属于构成）；**每一类实际落到哪一个是注入的** |
| 同一行第三列的「——」 | 没有解释，与 PF-005「无状态沙箱一次工具调用就结束」像是打架 | 加说明：**不是执行环境没有实例**，而是该列问的是「每次**模型请求**产生什么」，而执行环境的实例化粒度是**工具调用** |
| 对执行环境寿命的表态 | 正文**未表态**，但也没排除误读 | **正面写死**：执行环境的存活与运行实例无关，可能短得多也可能长得多，**本 topic 不对它的寿命作任何断言** |

**正文从未出现过「执行环境生命周期长于运行实例」这条断言。**该说法只在设计交流中
由 PM 提出、并被产品负责人当场纠正，从未落进任何文件——本版是为**防止误读**而做的
表述精化，不是撤回某条已写下的内容。

### 下游要注意的

- **不要把「装配时确定执行环境」理解成「绑定一个具体环境」。**装配确定的是
  **需要哪几类**，具体哪一个是注入的、随时可换。
- **执行环境的存活期一律去 PF-005 查**，本 topic 不是权威。

## rev 1 — 2026-09-17

**首版。**回答 PF-002 与 PF-003 都没有回答的问题：
**一份定义怎么变成一个真正在跑的 agent。**

### 这一版确定了什么

| 方面 | 结论 |
|---|---|
| 缺的是什么 | 不是一个环节，是一个**对象**——跑起来的那副身子此前没有名字 |
| 本 topic 的主角 | **运行实例**。会话与 Run 只作为它的两个接口出现，**都不在本 topic 拥有** |
| 三个时刻 | **装配时**定构成、**注入变化时**改环境、**请求时**才算模型与提示词成品 |
| 构成 vs 注入 | 判据一句话：**变化改变的是「它是什么」，还是「它处在什么情况下」** |
| 谁是注入的 | **上下文、执行环境、权限**三者。它们变了，运行实例**不重建** |
| 系统提示词 | **成分是实例的属性，成品是那一次请求的属性**。不同模型组装方式可能不同 |
| 模型 | 唯一不在装配时绑定的组成部分——**每次请求时解析** |
| 动作空间 | **只由构成决定**。权限变了，动作空间不变 |
| 装配清单 | 是**产品对象**，只可追加。「当时那个 agent 是什么样」只有这里能答 |
| 不变式 | 九条，见 design.md §6.1 |

### 三段结构是递归的

不只 agent 整体有「定义 → 装配 → 实例」。模型、系统提示词、工具、技能、插件、
Slash Command、执行环境**各有一份**，它们的装配合起来才构成 agent 那一次装配。
逐项见 [design.md §5.2](design.md#52-三段结构是递归的)。

### 下游要注意的六处

- **不要把运行实例和会话当成一回事**，也不要和「一次运行」当成一回事。
  三者都不同：会话长期、实例可回收、一次运行短暂。
- **权限不在构成里。**把它实现进构成，「收紧权限 agent 照常工作」当场落空，
  而且收紧权限会让 agent 突然不知道某件事存在——既无法解释也无法申诉。
- **系统提示词的成品不能提前到装配时定死。**定死了，换模型就必须重建实例。
- **构成性变化不改写活着的实例。**要作用于它，只有显式退役重建一条路。
- **回收必须是显式退役。**未结算的工作、未释放的资源、未交代的失败，
  都要在退役过程里有结果。
- **装配清单只可追加。**改写它等于销毁历史。

### 本版刻意不做的

**会话、输入的受理与排队、一次运行的驱动**——这三样是最容易被顺手拉进来的，
产品负责人明确把它们划在边界之外。另有单次工具调用的生命周期、子 agent 的关系、
待决项的呈现与作答。

理由是同一条：**三者的改动原因不同。**会话因协作形态变，驱动因调度策略变，
实例化因装配与资源治理变。合在一起，改任何一处都要动其余两处。

### 本版留下的缺口

- **未决项：无。**
- **待裁决：无。**
- **一处已报告、尚未裁决的来源问题**：SYS-COMPOSITION.C3 的措辞未区分
  构成性绑定与可变注入，见 [decisions.md 第四节](decisions.md#四已知的来源问题)。
  本 topic 按「构成捕获、注入可变」落稿；foundation 若采用另一种表述，本 topic 需复核。

被排除的内容在 [design.md §2 非目标](design.md#非目标)，那是**边界**——
发现它们缺失不算缺陷。下游遇到本文档没回答的问题，应当停下来问，
而不是挑一个看起来合理的实现。

## 怎么记下一版

改变含义就递增 rev 并在这里加一节。判断标准：
**读者需要据 rev 判断自己手上的理解是否还成立吗？**需要，就记。

每节至少说清三件事：改了什么含义、为什么、下游要复核什么。
