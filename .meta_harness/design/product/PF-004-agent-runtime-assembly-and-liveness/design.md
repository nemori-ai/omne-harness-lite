# PF-004：Agent 运行时——定义、装配与实例

- 修订：rev 3，2026-09-17 · [变更历史](changelog.md)
- 状态：已定稿，**无未决项**

## 一、背景与问题

[PF-002](../PF-002-assets-settings-and-permissions/design.md) 把 Agent Definition
定成一类资产——**静态定义**，[PF-003](../PF-003-asset-transfer-and-sharing/design.md)
说清了它怎么跨组织流动。但**一份定义怎么变成一个真正在跑的 agent**，此前没有任何一处拥有。

缺的不是一个环节，是一个**对象**。看看这些问题今天为什么答不出来：

- **「这个 agent 现在能做什么」**——「现在」指的是哪个东西？定义是长期不变的，
  而能做什么每时每刻都可能不同。问题问的是跑起来的那个，而那个没有名字。
- **改一项权限，要不要把 agent 重启一下？**改一个工具呢？换个模型呢？
  这三件事对一个正在干活的 agent 各自意味着什么，此前混作一谈。
- **「当时那个 agent 到底是什么样」**——装了哪些工具、用的哪份提示词、哪个模型？
  没有对象承载这个事实，事后就永远复现不出来。
- **成本算谁的？**消耗计算资源的那个东西没有身份，成本就没有归属。

场景是**一个 agent 在一个会话里连续多轮运行**。这个场景里有一件正在发生、
却无法解释的事：**中间那副跑着的身子可能被回收过、重建过很多次，而用户完全无感。**

这是对的行为——定义是数据，跑起来的那副身子是计算资源，闲着就该回收。
但产品上如果没有「那副身子」这个对象，这件事就既说不清、也管不住。

**本 topic 只拥有那副身子**：它怎么来、由什么构成、什么是外面给它的、
变化怎么影响它、它怎么消失。会话怎么管、输入怎么进来、一次运行怎么被驱动，
都不在这里（见 §2）。

## 二、目标与非目标

### 目标

1. **定义运行实例**，以及围绕它实例化的全部对象：装配、装配清单、动作空间、注入。
2. **定死三个时刻**：装配时确定什么、注入变化时改什么、请求时才算什么。
3. **给出不变式**：不论中间发生过什么，关于运行实例哪些事必须始终成立。
4. **说清变化怎么传播**：改了某样东西，对正在跑的那个和下一次各意味着什么。
5. **逐个组成部分**说清它们各自的定义、装配与实例——模型、系统提示词、工具、
   技能、插件、Slash Command、执行环境、上下文。

### 非目标

**本 topic 只管实例化，不管驱动。**下面三样是最容易被顺手拉进来的：

| 不做什么 | 为什么 |
|---|---|
| **会话** | 会话是什么、怎么建、怎么管、历史怎么存——那是一个长期物件的事。本 topic 只用到它的一件事：**运行实例附着在一个会话上** |
| **输入怎么进来** | 消息怎么受理、怎么排队、怎么调序、什么时候取一批——都不在这里 |
| **一次运行怎么被驱动** | 谁决定现在该跑一轮、怎么推进、怎么收束。本 topic 只用到一件事：**Run 在运行实例上执行** |
| 单次工具调用的观察、中断与后台接续 | 它有自己的生命周期，且能跨运行实例存活。本 topic 只定它**怎么被装进来**、**算不算在动作空间里** |
| 子 agent 的委派、监督与关系 | 一个会话里出现多个运行实例是那件事的结果，不是本 topic 的对象 |
| 待决项的统一呈现与作答 | 那是跨会话的事。本 topic 只定「等人的时候运行实例怎么办」 |
| 模型怎么供给、怎么路由 | 归 [SYS-LLM](../../foundation/cross-system-constraints/requirements.md#sys-llm)。本 topic 只定**模型在哪一刻被确定** |
| 崩溃后恢复到哪个合法位置 | 判据归 [SYS-RUNTIME-CONTINUITY](../../foundation/runtime-state-and-continuity/requirements.md)。本 topic 定的是**正常生灭**，不是故障恢复 |
| 具体有哪些上下文项、哪些执行环境 | 本 topic 定它们**以什么方式**进入运行实例，不枚举内容 |

## 三、用户与场景

| 使用者 | 什么情况下接触这块 | 他关心什么 |
|---|---|---|
| **在会话里连续协作的人** | 每天的正常使用 | 我接着上次说，它还是刚才那个它吗？ |
| **组织管理员** | 改权限、换掉某个组件、禁用某个工具 | 我这一改，正在干活的人会被打断吗？什么时候生效？ |
| **对成本负责的人** | 看账单 | 是什么在花钱？等我回话的那半天算不算钱？ |
| **排障的人** | 出了问题回溯 | 当时那个 agent 到底装的是什么、用的哪个模型？ |
| **agent 自己** | 每一轮运行 | 我现在能做什么？外面的情况变了我怎么知道？ |

**最后一行是这块设计的直接消费者，不是被管理的对象。**
本 topic 的多条规则是为了让 agent 能回答「我现在处在什么情形下」——
它答不上来，上面四种人的问题也就都答不上来。

| **Context：agent 运行时可感知的上下文信息**（协作范围 / 个人两种） | [PF-001 §4](../PF-001-identity-scope-and-agent-constraints/design.md#contextagent-运行时可感知的上下文信息) |

本 topic 把 SYS-COMPOSITION 的三段结构，落到 agent 这件具体的事上，
并给每一段起一个产品上的名字。

### 两个只引用、不拥有的对象

本 topic 无法绕开这两样东西，但**只用到它们各自的一件事**。
它们的定义、管理与驱动都不在这里。

| 对象 | 本 topic 用到的唯一一件事 | 本 topic **不**说它 |
|---|---|---|
| **会话** | **运行实例附着在一个会话上**，并从它取得「跟哪一份定义的哪个版本协作」 | 会话怎么建、怎么命名归档、历史怎么存、输入怎么进来 |
| **Run**（一次运行） | **Run 在运行实例上执行**，一次执行期间实例必须在 | 谁决定现在该跑、怎么推进、怎么收束、怎么中断 |

**写下这两行是为了防一件事**：把「运行实例」和「会话」当成一回事，
或者把「运行实例」和「一次运行」当成一回事。三者都不同——
**会话是长期的，运行实例是可回收的，一次运行是短暂的。**

### 运行实例

**一次装配的产物：一副真正在跑的身子。**它持有这一次的构成，并占用实际的计算资源。

对应 [SYS-COMPOSITION 的「活体」](../../foundation/definition-and-runtime-composition/requirements.md#sys-compositionc1三段结构)。

- 它是**计算资源**。占用即消耗，闲置就该回收。
- 它**可回收、可重建**。回收之后，会话还在、历史还在、认定的定义还在。
- 它**不是**定义，也不是会话。**同一个会话的两轮运行，可能跑在两个不同的运行实例上。**

| 属性 | 业务含义 | 取值与约束 | 何时确定 |
|---|---|---|---|
| 附着的会话 | 它在为哪一段协作干活 | 恰好一个会话 | 装配时，此后不变 |
| 依据的定义版本 | 它是照哪一份图纸装出来的 | Agent Definition 的一个**已发布版本** | 装配时，此后不变 |
| 装配清单 | 它实际由什么构成 | 见下 | 装配时产生，只可追加 |
| 成本归属 | 它花的钱算谁的 | 启动它的那个租户 | 装配时 |

### 装配

**把一份定义，在某个作用域下，变成一个运行实例的动作。**

装配要回答：这一次**装哪些工具、带哪些技能、落在什么执行环境上、
系统提示词由哪些成分构成**。

装配**有确定的发生时刻**，不是一个持续的过程。它的输入是两样：
**依据的定义版本**，加上**当时该作用域的求值结果**（持有哪些资产、各项设置与权限的值）。
求值规则归 PF-002，本 topic 不重复。

### 装配清单

**这一次装配实际用了什么的记录。**

它是一个**对象**，不是过程的副产品。理由只有一条：
**「当时那个 agent 是什么样」这个问题，答案只能在这里。**
没有它，出了问题谁也说不清、事后谁也复现不了。

装配清单**只可追加，不可改写**。运行实例在生命里增量装上了新东西，
是在清单上加一条，不是修改既有条目。

### 动作空间

**这个运行实例能发起哪些动作的集合。**

它**只由构成决定**（见 §5.3）。这一条看似平淡，实则是本 topic 最有用的一条：

> **权限变了，动作空间不变。**

agent 照样能发起那个调用，只是这次被拒绝——它因此知道
「这件事存在，只是我现在不被允许」，而不是「这件事不存在」。

**但这条说的是「谁说了算」，不是「永不改变」。**动作空间当然会变——
装上一个新工具它就变大，移除一个工具它就变小。这一条锁定的是**变化的唯一原因**：

| 发生了什么 | 构成 | 动作空间 |
|---|---|---|
| 运行中热装上一个新工具 | 变了 | **跟着变大** |
| 退役重建后少了一个工具 | 变了 | 跟着变小 |
| 权限收紧或放宽 | 没变 | **不变** |
| 换执行环境、换模型 | 没变 | **不变** |

所以**「系统支持热装载新工具」与这一条不冲突，热装载正是它的一个实例**——
改的就是构成，动作空间跟着变是应该的。

它也**不依赖热装载做不做得到**：某次装载若触及了必需绑定、热装不了，
退一步走退役重建即可，那是一次完整装配，动作空间照样由构成决定。
**两条路殊途同归。**

这一条真正排除掉的只有一件事：**拿构成之外的东西去改动作空间。**

### 注入

**一样东西不是运行实例自带的，而是外面给它的；给的内容变了，运行实例不用重建。**

这是本 topic 的核心机制。**上下文、执行环境、权限，三者都是注入的。**

注入与构成的分界，判据是一句话：

> **这个变化改变的是「它是什么」，还是「它处在什么情况下」？**

前者是构成，变了就是另一个 agent，得重新装配；
后者是注入，它还是它，只是周围不同了。

### 运行期上下文

[PF-001 定义了 Context](../PF-001-identity-scope-and-agent-constraints/design.md#contextagent-运行时可感知的上下文信息)——
agent 运行时可感知的上下文信息，并给出协作范围与个人两种。本 topic **不改写它**，
只补 PF-001 没有覆盖的一类：**运行期才产生的上下文**——外部环境变了、
权限被调整了、某个依赖不可用了。

它们与 PF-001 的两种同样是「agent 能感知到的、关于我现在处在什么情形下的信息」，
同样**通过注入到达**，因此归在一处，不另立概念。到达方式见 §6.4。

### 执行环境

**动作实际落到哪里。**宿主机、沙箱，或别的什么。

执行环境是**注入的**。这带来一条很实在的性质：

> 一条 shell 命令，执行在宿主机还是沙箱里，**agent 都能执行**。

工具定义说的是「执行一条命令」，从不说「在哪执行」。落到哪儿，是注入的事。
正因如此，换掉执行环境不需要重建运行实例，也不改变动作空间。

**它有哪几种、各自的存活期与隔离性，归 [PF-005](../PF-005-execution-environments-and-sandboxes/design.md)。**
本 topic 只定它**以注入的方式进入运行实例**这一件事。

有一点先说清，免得与 PF-005 读成冲突：

> **执行环境的存活与运行实例无关。**它可能比运行实例短得多（一次工具调用就结束），
> 也可能长得多（绑定在租户）。**本 topic 不对它的寿命作任何断言。**

## 五、模型

### 5.1 一张图，三个对象各在其位

```text
   Agent Definition ─────┐
     （数据，长期）       │
                          ├──装配──→ 运行实例 ──→ 一次运行在它上面执行
   作用域（当时可用的     │          （计算资源）      ↑
    实现、设置、权限）────┘          产出装配清单      │
                                          │            │
   会话 ──────────────────────────────────┘            │
    （长期，本 topic 不拥有）    附着 + 提供依据的定义版本
                                                       │
                              注入：上下文 · 执行环境 · 权限
                                （可变，实例不因此重建）
```

**虚线之外的两样本 topic 不拥有**：会话怎么来、一次运行怎么被驱动。
图里画它们，只为说清运行实例的两个接口。

三件事值得单独说：

- **运行实例是会话的执行载体，不是会话本身。**载体换了，协作没断。
- **同一个会话的两轮运行可能跑在两个运行实例上，用户无感。**
  这不是妥协，正是「定义是数据、运行时是计算资源」该有的样子。
- **注入是从旁边进来的，不在装配链上。**这条线是本模型最要紧的部分，见 §5.3。

### 5.2 三段结构是递归的

三段不只作用于 agent 整体。**每个组成部分各有一份**，它们的装配合起来，
才构成 agent 那一次装配。

| 组成部分 | **定义**（数据） | **装配时确定** | **每次请求时产生** |
|---|---|---|---|
| **模型** | 模型标识与能力声明：窗口、模态、是否支持工具调用 | ——（例外，见下） | **这一次用哪个模型**，以及这一次的调用 |
| **系统提示词** | 作者写的正文，以及各来源可贡献的片段 | **全部成分** | **组装出来的那一份文本** |
| **工具** | 调用形状、参数、权限项、设置项 | 绑定到一个**适配当前执行环境的实现** | 一次工具调用 |
| **技能** | 指引正文 + 资源 | 进入可用技能集；摘要常驻，正文按需取 | —— |
| **插件** | 打包在一起的若干资产 | **展开**为内含成员，各自参与装配 | —— |
| **Slash Command** | 命令名、参数、绑定的技能 | 进入可用命令集 | 一次命令执行 |
| **执行环境** | 工具声明它需要什么样的环境 | **需要哪几类环境**（由装进来的工具决定） | ——（见表下说明） |
| **上下文** | ——（不是被装配的对象） | ——（注入） | 这一次的上下文视图 |
| **（整体）** | Agent Definition | **装配清单** | 一次模型请求 |

**执行环境那一行要与 [PF-005](../PF-005-execution-environments-and-sandboxes/design.md) 一起读。**装配时确定的是
**需要哪几类**环境——那由装进来的工具决定，属于构成；而**每一类实际落到哪一个**
是注入的，随时可换而实例不重建。

它的第三列写「——」，**不是说执行环境没有实例**，而是这张表的第三列问的是
「每次**模型请求**时产生什么」，而执行环境的实例化粒度是**工具调用**——
一次模型请求可能带来多次工具调用。各类环境各自活多久，归 PF-005。

**模型那一行是唯一的例外，而且例外得有理由**：它不在装配时绑定。
理由见 §6.6——同一个会话的不同轮允许换模型，若在装配时绑死，
换模型就得重建运行实例，而那本该是轻的。

### 5.3 三个时刻

这是本 topic 最要紧的一张表。

| | **装配时** | **注入变化时** | **请求时** |
|---|---|---|---|
| 确定什么 | **构成**：动作空间、技能、**需要哪几类执行环境**、系统提示词的**全部成分** | 上下文、执行环境、权限取值 | 这一次的模型、**这一次组装出的系统提示词**、这一次的上下文视图 |
| 变了会怎样 | **[Agent Definition](../PF-002-assets-settings-and-permissions/design.md#七类资产) 变了 → 下一次装配时重建**；**运行中增量装载则不重建**（§6.3） | **运行实例不变** | 每次都重算，本来就该不同 |
| 留下什么 | 装配清单 | 下一次运行里的一条提醒（§6.4） | 一次可追溯的实际请求 |

**中间那一列是这套模型的关键。**没有它，任何环境或权限的变化都只能靠重建运行实例来生效，
而重建会打断正在进行的工作——那不是产品要的。

**第一列里那个「但是」很要紧，不能只看表。**构成变了**未必**重建——
两条路径的结局不同：

| 路径 | 例子 | 结局 |
|---|---|---|
| **改了 Agent Definition** | 有人编辑了这份定义 | **下一次 run 重建实例。**不去区分改的是什么——比对差异再判断值不值得重建，**代价大于收益**，而「下一次 run」这个时机本来就不打断当前工作 |
| **运行中增量装载** | 运行里发现并装上一个新的可选能力，**包括 agent 自己造出来的** | **不重建**，清单上追加一条 |

判据在 §6.3：**往实例里新增一个可选能力，和把它正在用的必需绑定换掉，是两回事。**

### 5.4 为什么系统提示词必须落在第三列

它是作者写的一段话，**加上装配结果的投影**：装了哪些工具，提示词里就得有它们；
装了哪些技能，就得有对应的摘要。所以**没有一份「完整的系统提示词」可以被手工维护**，
它必须随装配结果一起长出来——这与 PF-002
[「设置页是长出来的」](../PF-002-assets-settings-and-permissions/design.md#61-设置页是长出来的不是画出来的)
是同一条道理的又一次应用：**凡是「持有什么」的函数，就不该被独立维护。**

但**长出来的是成分，不是成品**。成品要等到知道这一轮跟谁说话才能定，
因为**不同模型对提示词的组装方式可能不同**（接口契约统一，组装逻辑不必相同）。

分界因此很干净：

> **成分是运行实例的属性，成品是那一次请求的属性。**

把成品提前到装配时定死，换模型就必须重建运行实例——而那恰恰是要避免的事。

## 六、产品规则

### 6.1 不变式

不论中间发生过什么，以下关于运行实例的事必须始终成立。

| # | 不变式 | 不成立会怎样 |
|---|---|---|
| **I-1** | 一个会话在任一时刻**至多有一个运行实例** | 两副身子同时以同一个身份说话，历史就没有单一真相 |
| **I-2** | **运行实例的生灭对协作中的用户不可见** | 用户会看到 agent「重启了」，而他什么也没做 |
| **I-3** | 运行实例重建，**它依据的定义版本不变** | 同一段协作里 agent 中途变脸 |
| **I-4** | **动作空间只由构成决定**；权限变化不改变动作空间 | 收紧权限会让 agent 突然「不知道某件事存在」，无法解释也无法申诉 |
| **I-5** | 每一次模型请求都有**可追溯的实际组成** | 出了问题答不出当时装的是什么 |
| **I-6** | 运行实例被回收，**不产生用户可感知的损失** | 回收变成一种故障 |
| **I-7** | **等人回话的时间不消耗计算资源** | 一个等了两天的确认，账单上是两天的运行费 |
| **I-8** | 运行实例消耗的成本，**归属到启动它的那个租户** | 成本没有归属，账单明细无从谈起 |
| **I-9** | 装配缺少必需的东西时**明确失败**，不产生残缺的运行实例 | 一个缺零件的 agent 跑起来，它自己不知道缺什么，用户也不知道 |

**I-6 的具体含义**：回收之前，未完成的事情要么已经持久、要么在重建后能接续、
要么**明确失败并让人知道**。三者之外没有第四种。

**I-1 是关于运行实例的，不是关于运行的。**同一时刻能不能跑两个 Run，
那是驱动那一侧的事，不在这里。

### 6.2 装配

- **装配在运行实例诞生时完成**，产出一份只可追加的装配清单。
- 输入两样：**依据的定义版本** + **当时该作用域的求值结果**。
- **装配失败就是失败**（I-9）：定义引用的能力标识无人提供、必需资源拿不到，
  明确失败并说明缺什么。

### 6.3 三类变化，三种传播

这是本 topic 最常被问到的部分，逐类说死。

| 变化 | 例子 | 对**正在跑的**运行实例 | 对**下一次装配** |
|---|---|---|---|
| **构成性变化** | 组织移除了一个工具、换掉了某个组件 | **不改写它**。它按已捕获的构成继续；除非它赖以成立的东西没了，那就**退役** | 生效 |
| **注入性变化** | 权限取值改了、换了执行环境、外部环境变了 | **运行实例不变**，变化以提醒的形式在下一轮到达（§6.4） | 生效 |
| **每次请求时确定的** | 换模型 | 不存在「改写」这回事——**下一次请求就用新的** | —— |

**构成性变化不改写活着的运行实例**，这条来自
[SYS-COMPOSITION.C4](../../foundation/definition-and-runtime-composition/requirements.md#sys-compositionc4变化作用于下一次装配)。
要让它作用于某个已经在跑的实例，走**显式退役并重建**，不靠别的机制悄悄生效。

**增量装载是个例外，但它不是反例**：运行中发现并装上一个新的可选能力，
运行实例**不重建**，清单上追加一条。分界是：

> **往实例里新增一个可选能力，和把它正在用的必需绑定换掉，是两回事。**
> 前者它照常活着；后者它赖以成立的前提变了，该退役重建。

**agent 自己造出来的工具或技能，走的就是这一条。**它在运行中给自己添了件家伙什，
动作空间当场变长，实例**不重建**——否则它每造一个东西就把自己重启一次，
而重启会打断它正在做的那件事，这是荒谬的。
（这一条的产品语义见 [PF-006 §6.9](../PF-006-tools-and-skills/design.md#69-agent-创建与修改工具技能本版只定三条)，
本 topic 只负责说明它为什么不触发重建。）

**但改动 Agent Definition 是另一条路径**：那是装配的输入变了，
**下一次 run 重建实例**。不去区分改的是不是"只是新增"——
比对差异再判断值不值得重建，代价大于收益；而「下一次 run」这个时机
本来就不打断当前工作。

### 6.4 上下文变化怎样到达 agent

**以事件驱动的方式，在下一次运行里作为一条提醒出现。**

这里面有三件事是定死的：

- **agent 不轮询环境。**环境变了会告诉它，不需要它反复去问。
- **变化不打断当前正在进行的运行。**它等下一轮才现身，与
  [PF-001 §6.6「撤销不等于强制停止」](../PF-001-identity-scope-and-agent-constraints/design.md#66-撤销不等于强制停止)同向。
- **它以上下文内容的形式到达**，而不是以「你的能力被改了」的形式。

最后一条是关键：agent 是**读到**变化，然后自己决定怎么调整，
而不是被系统在背后改写。**「agent 能动态感知外界变化、在运行中调整自己的行动轨迹」，
成立的根子就在这里。**

### 6.5 权限变化：动作空间不变

按 I-4 与 §4 的「动作空间」，权限变化**不改变 agent 能发起什么**，
只改变发起之后会得到什么。

这让 PF-002 里
[「移除」与「禁用」是两个动作](../PF-002-assets-settings-and-permissions/design.md#64-移除与禁用是两个动作)
落在了不同的段上：

| | 改的是哪一段 | 动作空间 | agent 的表现 |
|---|---|---|---|
| **移除** | **构成**（持有关系变了） | **变小** | 不知道有这回事 |
| **禁用** | **注入**（权限取值变了） | **不变** | 知道它存在、调用被拒、**能解释** |

于是「一个会话的安全权限被收紧了，agent 照常工作」不再是一句愿望，
而是模型的推论：**权限压根不在构成里。**

### 6.6 模型在每次请求时确定

- 模型的**生效**在每次请求时解析；它不在装配时绑定。
- **换模型不重建运行实例**，也不改变动作空间。
- 每一条模型产出的内容，**记下实际生成它的模型**。事后回看不改成「当前选的那个」。

**模型的选择存在哪、怎么选、当前轮正在跑时提出切换怎么办**——
那是会话与驱动那一侧的事，不在本 topic。本 topic 只定一件事：
**模型是请求时才确定的，因此它的变化不触及运行实例。**

### 6.7 运行实例的生与灭

| 动作 | 什么时候 | 结果 |
|---|---|---|
| **装配** | 需要一副身子而当前没有 | 产生运行实例与装配清单 |
| **复用** | 已有就绪的运行实例 | 直接用，**不重新装配** |
| **回收** | 它空闲下来 | **显式退役**：先不再接新工作，等手上的事真正停当，再释放资源 |
| **退役重建** | 它赖以成立的构成没了 | 同上，下一次需要时重新装配 |

**回收是显式动作，不是「没人用就自己没了」。**这一条要紧在：
未结算的工作、未释放的资源、未交代的失败，都必须在退役过程里有结果（I-6）。

**等人回话时，运行实例可以被回收**（I-7）——等待是一个持久的事实，
不是一副身子的姿势。人回话之后重新装配一副继续，用户看到的是他的问题被接上了。

**谁来决定现在该装配、该回收**，是驱动那一侧的事；本 topic 只定
**这几个动作各自意味着什么、必须留下什么**。

### 6.8 停止有两级

| | **退役** | **强制停止** |
|---|---|---|
| 做什么 | 先关新工作，等真正停当，再释放 | 立刻撤销继续执行的资格 |
| 代价 | 慢，但结果干净 | 快，但**已经发出去的外部效果收不回来** |
| 反馈 | 各项都有结局 | **逻辑停止、实际停止、外部效果未知，必须分别说** |

**不能把「已经停止」和「外部效果已经撤销」说成一回事**——
这与根约定「外部输出不因被运行时调用就变得可逆」一致。

**谁有资格发起、怎么发起**，归驱动与控制那一侧。本 topic 定的是
**这两级各自对运行实例意味着什么**。

## 七、取舍

| 面临的选择 | 选了 | 为什么 |
|---|---|---|
| 运行实例对用户可见 ／ 不可见 | **不可见**（I-2） | 它的生灭是资源治理，不是协作事件。让用户看见，他就得为一件本该系统负责的事操心，而且会问「为什么我的 agent 重启了」——那个问题没有对他有意义的答案 |
| 系统提示词在装配时定成品 ／ 在请求时组装 | **请求时组装** | 不同模型的组装方式可能不同。在装配时定死，换模型就得重建运行实例，而换模型本该是轻的 |
| 权限进构成 ／ 权限是注入 | **注入** | 进构成的话，收紧权限会让 agent 突然不知道某件事存在，既无法解释也无法申诉。作为注入，它知道「这件事存在，我现在不被允许」 |
| 执行环境进构成 ／ 是注入 | **注入** | 一条命令执行在宿主机还是沙箱，agent 都能执行。进构成的话，换个沙箱就要重建实例，毫无道理 |
| 上下文变化立即打断当前运行 ／ 下一轮到达 | **下一轮** | 立即打断会让一个正在收尾的工作半途而废，而变化本身通常不紧急。紧急的那种有显式控制（§6.8） |
| 变化以「能力被改了」通知 ／ 以上下文内容到达 | **上下文内容** | 前者是系统替 agent 做决定，后者让 agent 自己判断怎么调整。**「在运行中调整行动轨迹」只有后者能做到** |
| 一个会话可有多个运行实例 ／ 至多一个 | **至多一个**（I-1） | 两副身子同时以同一身份说话，历史就没有单一真相 |
| 装配清单只作内部记录 ／ 作为产品对象 | **产品对象** | 「当时装的是什么」是排障与审计的唯一答案来源。只当内部记录，这个问题就永远答不上来 |
| 回收是隐式的 ／ 显式退役 | **显式退役** | 隐式回收没有「结束」这个时刻，未结算的工作与未释放的资源就没有地方交代 |
| 装配缺东西时降级跑起来 ／ 明确失败 | **明确失败**（I-9） | 一个残缺的 agent 跑起来，它自己不知道缺什么，用户也不知道——问题会在很远的地方以莫名其妙的形式出现 |
| 本 topic 连会话与驱动一起定 ／ 只定实例化 | **只定实例化** | 三者的改动原因不同：会话因协作形态变，驱动因调度策略变，实例化因装配与资源治理变。合在一起，改任何一处都要动其余两处 |
