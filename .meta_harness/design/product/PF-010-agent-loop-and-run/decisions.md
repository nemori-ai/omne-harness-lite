## 二、PM 推导

从已拍板内容推出的判断，附可核对的推理链。

| 结论 | 从哪几条推出 | 推理 |
|---|---|---|
| **run 与 agent-loop 必须是两个概念** | 「run 是数据 / 治理，agent-loop 是执行逻辑」 | 合成一个，就会写出「run 对象自己知道怎么往下走」这种设计——**而那个「知道」活在进程里，停机就没了**。分开之后，一个负责**被写下来**，一个负责**被重新算出来** |
| **改记录的动作 vs 纯派生的动作，是这套模型里最要紧的一条分界** | 「记录是唯一真相来源」+ 三个动作的叠加 | **纯派生的动作重算一定得到同样结果**，所以不必给它建检查点、恢复时也不必知道「上次做到哪了」。由此得到一条实现判据：**要不要给一个动作建状态点，看它改不改记录** |
| **组装是这一圈里唯一纯派生的动作** | 上一条 + 三个动作各自的性质 | 压缩追加摘要、调模型追加回复、探测可能写干预、执行追加结果——**只有组装什么都不留**。这条性质在「压完要再组装一次」时兑现了价值：**第二次组装不产生任何状态** |
| **不组装就不知道超没超** | 产品负责人对压缩位置的纠正 + [PF-007 的常驻预算](../PF-007-meta-capabilities/design.md#54-十二个槽位是预算的地板也是它的天花板意义) | 占位置的不只是对话——系统提示词、工具定义、十二扇门都占。**「量一量」这个动作本身就要求先组装出来** |
| **摘要只生成一次，不再被二次压缩** | 「压缩的输入是上次压缩点到现在」这条裁决 | 该区间定义使压缩天然是**增量**的。允许二次压缩就会出现「摘要的摘要的摘要」——**每压一轮损失一轮，而且损失是静默的**，没人看得出第三手摘要已经和原文没什么关系 |
| **压完还超 → 终局失败，不循环压** | 常驻部分压不动 + [失败三档的「谁能解决」判据](design.md#58-失败处置三档判据是谁能解决) | 压缩只碰得到对话。**光是固定部分就超了预算，那是装配的问题**，压对话压到空也没用——按判据落在「谁也解决不了」。原因要写明是固定部分超限，**否则运维会一直盯着对话长度查**。而压第二次除了损失信息什么也换不来——**能压的上一次已经压完了** |
| **L3 落「失败」，不新增终态** | 「终态就是失败」这条裁决的推广 | 终态越少越好，所有消费方（读面、统计、告警、计费）都少一种情形要处理。**为什么失败，本来就有地方写** |
| **失败第一档与[六种收场](../PF-006-tools-and-skills/design.md#53-一次工具执行的收场有六种)是同一回事** | 两者都是「把错误作为一条正常返回交给 agent」 | 不另立一套说法。legacy 那边是两处表述，我们合并 |
| **被卸载的结果不是「缺了一半」的结果** | 「算齐」这条裁决的两个理由 | 有[取回全文的通道](../PF-007-meta-capabilities/design.md#61-tools通向任意非常驻工具)，**而且占位里带摘要、很多时候摘要就够用**。所以它是**一个完整的、可按需展开的结果**——与[转后台留的占位](../PF-006-tools-and-skills/design.md#66-前台后台-与-等待态是两个维度)同形。**若占位只留地址不带摘要，这条推理就不成立了**，那时它确实是缺了一半 |
| **「等一等再试」不产生状态转移** | 它不动记录 | 重试对方程是隐形的。恢复时不会看到「重试到第几次了」这种状态——**也不需要看到** |
| **未分类的失败归终局**（fail-closed） | legacy 的硬约束，本 topic 采纳 | **不认识却放过去，是最危险的那种宽容** |
| **唯一终局落账点，且先确保会话存在** | legacy 的机制，本 topic 采纳 | 没有这一条，**第一轮就死掉的会话会变成幽灵**：run 失败了，但没有任何地方看得到它 |
| **恢复也算一次「开始」，因此[可用性重算](../PF-006-tools-and-skills/design.md#62-可用性在每次-run-开始前重算)** | 「恢复时重算」这条裁决 + PF-006 的规则 | PF-006 定的是「每次 run 开始前重算」，**把恢复也算作一次开始**，两者就统一了，不必为恢复另立规则 |
| **不必额外告知 agent 动作空间的差异** | [替换件](../PF-006-tools-and-skills/design.md#替换件)已经铺好了这条路 | 它调一个已经没了的能力，会拿到「用不了 + 原因」，据此绕路。**这条路已经铺好，不用再铺一条** |
| **恢复不重置循环阶梯** | legacy 的 INV + 「检测状态从记录派生」 | 不守这条，**agent 只要崩得够勤就能无限打转，而每次崩溃看起来都像意外** |
| **喂给 agent 的是记录原样，零追加零注入** | legacy 的 INV-RD-3 | 多塞一句「你刚才中断了」看似贴心，实则**改变了检测窗口**——多出来的那条可能被当成新的工作输入，把阶梯洗白 |
| **agent 必须知道自己处在一次恢复之后** | 「哪怕重做也接受」这条裁决 | 重做的风险由 agent 判断，**不知道就没法判断，也不知道该去核实什么**——尤其是「合成被中断结果」那条路：**那个动作可能真的做了一半** |
| **恢复本身要能被人看见** | 同上 | 外部效果重复了，**人得能追溯到是哪一次恢复造成的** |
| **记录先于可见** | legacy 的 INV-LG-2，本 topic 升为通则 | 「图里看得见、记录里没痕迹」的东西**一次重启就凭空消失**，而 agent 的后续判断全建立在它上面。对干预消息尤其硬：落盘顺序颠倒，**重探时窗口就变了，结论可能和上次不一样**——而方程的确定性正是靠「结论必然相同」撑着的 |
| **L0 观测永不可关** | 它只观测、不干预 | 关掉它，**「agent 在打转」这件事就再也没人知道**，包括那些还没严重到触发干预的早期迹象 |

| # | 事项 | PM 倾向 | 不定会怎样 |
|---|---|---|---|
| **D-1** | **循环探测看压缩前还是压缩后的记录** | **看压缩前（原始）** | 若看压缩后：**agent 打转到触发压缩，反而把打转记录压没了**，阶梯归零，可以接着转。这是一条能被利用的路径 |
| **D-2** | **压缩能不能压掉「还悬着的东西」**（未答完的卡片、转后台没回来的执行的占位） | **不能**，只压已经了结的部分 | 占位被压进摘要，**agent 就不知道自己还有东西在外面跑**，而记录层面它们还好端端悬着——**两边静默对不上** |
| **D-3** | **一次回复里多个动作，只有一个要问人** | **一起等**（按 [PF-008](../PF-008-human-in-the-loop/design.md#53-一批卡片与答完是什么意思)） | 代价是一个本来无害的动作被一张不相干的卡片卡住 |
| **D-4** | **被否掉的动作要不要照样走一遍模型**（T8） | **要** | 不走，agent 不知道人否了它，**下一轮还会再发一次** |
| **D-5** | **怎么让 agent 知道自己在恢复之后** | 途径未定，但**不能动历史**（§6.3） | 不知道就无从判断重做的风险 |

## 四、已知的来源问题

| 问题 | 影响 | 处置 |
|---|---|---|
| **PM 曾判断「停机时正在跑的后台执行应算『状态不明』而非失败」，该判断建立在一个错误的想象上** | 会凭空多出第七种收场，agent 也多一种情形要处理——而那种情形并不存在 | **记下不改掉。**PM 把后台执行想象成了**跑在系统外面的独立进程**。实际上它[跑在这个系统里](../PF-006-tools-and-skills/design.md#65-工具执行有自己的运行时绑定在-session-上)，**系统没了它就没了**，不存在「可能成功了只是结果没回来」。产品负责人的原话：「系统都停机了，运行在系统里的后台工具执行是不是也是失败了呢其实」 |
| **PM 把压缩的位置写成了「组装之前」，顺序错了** | 照字面实现，就得在不知道上下文有多大的情况下决定要不要压 | **记下不改掉。**产品负责人指出压缩的输入是「上一次压缩后到这一次模型请求前的完整上下文」，并提出「**发生压缩则补一个追加组装**」。**不组装就不知道超没超**——占位置的不只是对话，还有系统提示词、工具定义与[十二扇门](../PF-007-meta-capabilities/design.md#54-十二个槽位是预算的地板也是它的天花板意义)。正确顺序是**组装 → 量 → 超了才压 → 再组装**。这个纠正顺带让「组装是纯派生」这条性质**第一次兑现了价值** |
| **产品负责人指示以 legacy design 为起点** | legacy 的形态可能被误当作本 topic 的依据 | **只作起点与印证，不作依据。**提炼与优化点见 [调研笔记](interviews/2026-09-18-legacy-agent-loop.md)；本 topic 的每一条都能在第一、二节找到裁决出处或独立推理链。**四处有意超出 legacy**：循环守卫 L4 实际交付（那边是关着的口子）、等人不是失败且已完整设计、失败第一档与六种收场合并表述、恢复时重算可用性 |
