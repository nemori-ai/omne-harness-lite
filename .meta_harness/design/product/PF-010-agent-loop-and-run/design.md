# PF-010：Agent Loop 与 Run

- 修订：rev 1 · **草稿**，2026-09-18 · [变更历史](changelog.md)
- 状态：**设计未完成**。骨架已立，未决项见 [§9](#九未决项)。**不要据此实施。**

## 一、背景与问题

前面几个 topic 各自回答了一部分：agent 能做什么（[PF-006](../PF-006-tools-and-skills/design.md)、
[PF-007](../PF-007-meta-capabilities/design.md)）、什么时候停下来等人（[PF-008](../PF-008-human-in-the-loop/design.md)）、
它由什么装配而成（[PF-004](../PF-004-agent-runtime-assembly-and-liveness/design.md)）。

**没有人回答的是：这些串起来，一次运行怎么往前走。**

四个问题因此悬着：

- **一次 run 有哪些步骤，从哪一步能到哪一步？**说不清，就没人能实现它，
  也没人能判断某个实现走岔了。
- **系统在一个 run 没走完的时候停机了，怎么办？**这是产品要求，不是可选项——
  一个跑了两小时的任务因为一次重启就从头再来，用户不会接受。
- **agent 原地打转怎么办？**它会转到什么时候？谁来叫停？
- **出错了算谁的？**一次异常，是让 agent 自己改道，还是等一等再试，还是就此结束？

## 二、目标与非目标

### 目标

1. **分清 run 与 agent-loop**，说明为什么必须是两个概念。
2. **给出状态转移方程**：状态是什么、有哪些转移、每一步之后落到哪。
3. **定义恢复语义**：停机之后怎么接着走，什么不许变。
4. **定义失败处置**：一次异常归谁处置。
5. **定义循环守卫**：agent 原地打转时，系统按什么阶梯介入。

### 非目标

| 不做什么 | 为什么 |
|---|---|
| **上下文的消息类型、压缩产出什么形状、摘要怎么组织** | 归 **PF-009**（编号已占，尚未开始）。本 topic 只说压缩**在方程里的位置**与**它改不改记录** |
| 停下来等人这件事本身 | 归 [PF-008](../PF-008-human-in-the-loop/design.md)。本 topic 只说它**停在方程的哪一步** |
| **会话怎么建、怎么收束、输入平时怎么进来** | 归后续 topic。本 topic 只引用，见 §4 |
| run 的**治理属性**（归谁、怎么计费、谁能看） | 本 topic 只定它的**状态与生命周期**——那是方程的定义域 |
| 循环检测的**具体算法与阈值** | 产品定阶梯与介入方式，**阈值是可调的政策** |
| 记录**落在哪、怎么存** | 技术设计。产品只要求**它必须完整到能算出下一步** |

## 三、用户与场景

| 使用者 | 什么时候接触这块 | 他关心什么 |
|---|---|---|
| **用户** | 任务跑了一半系统重启了 | 我那个任务还在吗？要不要重来？**会不会重复做一遍** |
| **运维** | 排查一个卡住的 run | 它现在在哪一步？为什么不动了？ |
| **安全负责人** | 评估自动化边界 | agent 能自己转多久？谁能叫停？ |
| **实现这套东西的人** | 每一天 | 这一步之后该干什么？**这个判断依据从哪来** |
| **agent 自己** | 每一轮 | 我上一步做到哪了？**我是不是刚从一次中断里回来** |

### 只引用、不拥有的对象

| 对象 | 本 topic 用到的 | 本 topic **不**说它 |
|---|---|---|
| **会话** | run 附着在一个会话上；历史**存在会话里**，run 引用而不另存一份 | 会话怎么建、怎么收束、输入平时怎么进来 |

### run

**一次运行，作为数据。**它记着这次运行是什么、归谁、现在到哪一步了。

**它的价值在于它能被写下来**——写不下来的东西，停机就没了。

### agent-loop

**一次 run 的执行逻辑，写成一个方程。**

```text
下一步  =  f ( 记录 , 环境 )
```

**`f` 是纯的**：同一份记录配同一个环境，算出来的下一步唯一。

### 记录

**方程的定义域。**它由三部分组成：

| 组成 | 内容 |
|---|---|
| **消息历史** | 人说的、模型回的、动作发出去的、结果回来的 |
| **run 的姿态** | 在跑 / 停着等 / 已经终态 |
| **悬着的东西** | 没答完的[决策卡片](../PF-008-human-in-the-loop/design.md#决策卡片)、转到后台还没回来的执行 |

**`f` 的定义域几乎完全落在消息历史的尾巴上**——这不是巧合：
**agent 的全部状态本来就活在对话里。**

### 环境

**当下的可用性**，加上[放行判断要的那三样](../PF-008-human-in-the-loop/design.md#52-那个判断函数)。

**环境会变，方程不变。**恢复时环境可能与停机前不同——那不是不确定性，**那是事实**。

## 五、模型

### 5.1 run 与 agent-loop 是一体两面

| | run | agent-loop |
|---|---|---|
| 是什么 | **数据 / 治理**的概念 | **执行逻辑**的描述 |
| 缺了它 | 停机后**不知道当时在哪** | 知道在哪也**算不出下一步** |

**为什么必须分成两个概念**：把它们合成一个，就会写出「run 对象自己知道怎么往下走」
这种设计——**而那个「知道」活在进程里，停机就没了**。

分开之后，一个负责**被写下来**，一个负责**被重新算出来**。

### 5.2 记录是唯一的真相来源

> **没有明确记载的，就当它没发生。**

三条直接推论：

- **恢复时从最后明确记载的状态重新算。**不猜、不推测、不去问别的地方。
- **任何只活在内存里的状态都是缺陷。**它在停机那一刻就没了，而**没人知道少了什么**。
- **哪怕因此重做一遍，也接受**——代价写在 §6.5。

### 5.3 改记录的动作，与纯派生的动作

**这条分界比任何一个具体动作都重要。**

| 动作 | 改记录吗 | 是状态点吗 |
|---|---|---|
| **上下文压缩** | **是**——追加一条摘要 | **是** |
| **上下文组装** | **否**——纯粹从记录算出来 | **否** |
| **调模型** | **是**——追加回复 | **是** |
| **循环探测** | **可能**——干预消息 / 检测事实 / 终态 / 卡片 | **是** |
| **放行判断** | **可能**——要问人就落卡片 | **是** |
| **执行动作** | **是**——追加结果 | **是** |

> **纯派生的动作不进状态空间。**重算一定得到同样的结果，
> 所以不必给它建检查点，恢复时也不必知道「上次做到哪了」。

**组装是这一圈里唯一纯派生的那个**，而这条性质在 §5.5 会兑现价值：
它可以在一圈里跑两次而不留任何痕迹。

**由此得到一条实现判据**：

> **要不要给一个动作建状态点——看它改不改记录。**

### 5.4 一圈的骨架

```text
【想】 压缩? ──→ 组装 ──→ 调模型
                (纯派生)      │
                             ↓
                         【探测】循环探测
                             │
                   ┌─────────┼────────┬───────┐
                 无事/L0    L1/L2     L3      L4
                   │         │        │       │
                   ↓         ↓        ↓       ↓
              有动作吗？   回【想】  失败  【等人】
               ├ 没有 ──→ 【收尾】完成
               └ 有  ──→ 【判断】 ├ 要问人 ──→ 【等人】
                                  └ 放行  ──→ 【做】──→ 回【想】
```

### 5.5 「想」这一步：先组装，量完才知道要不要压

**不组装就不知道超没超。**占位置的不只是对话——系统提示词、工具定义、
[十二扇门那些常驻的东西](../PF-007-meta-capabilities/design.md#54-十二个槽位是预算的地板也是它的天花板意义)
都占。所以「量一量」这个动作本身就要求先组装出来。

```text
【组装】(纯派生) ──→ 量一量
    ├─ 在预算内 ────────────────────────────→ 【调模型】
    └─ 超了 → 【压缩】(改记录) → 【再组装】(纯派生) → 量一量
                                               ├─ 在预算内 → 【调模型】
                                               └─ 还超 → 终局失败（见下）
```

**第二次组装之所以能随便补一次，正因为组装是纯派生的**——跑两次、跑十次都不留痕、
不产生状态、恢复时重算结果一样。**这一圈里真正的状态点只有压缩那一个。**

**压缩吃的是「上一次压缩点 → 现在」的记录**，因此它是**增量**的。由此推出：

> **摘要只生成一次，不再被二次压缩。**

否则会出现「摘要的摘要的摘要」——每压一轮损失一轮，**而且损失是静默的**，
没人看得出第三手摘要已经和原文没什么关系。

**压完还超怎么办**：常驻那部分**压不动**——压缩只碰得到对话。
如果光是固定部分就超了预算，那是**装配的问题，不是压缩能解决的**。
按[失败三档](#58-失败处置三档判据是谁能解决)的判据，它落在**谁也解决不了**那一档：
**终局失败，原因写明是固定部分超限**，否则运维会一直盯着对话长度查。

**不循环压。**压第二次除了损失信息什么也换不来——**能压的上一次已经压完了**。

> **压缩产出什么形状、摘要怎么组织，归 PF-009**（[§9](#九未决项)）。
> 本节只定它在方程里的位置，以及它**改记录**这一件事。

### 5.6 状态转移表

**看记录的尾巴，决定下一步。**

| # | 记录的尾巴长什么样 | 这意味着 | 下一步 | 落到 |
|---|---|---|---|---|
| **T1** | 一条**待处理的输入**（触发，或队列里攒的） | 该想了 | **组装 → 量** | T1a / T1b |
| **T1a** | 量下来在预算内 | 可以发了 | **调模型** | T2 |
| **T1b** | 量下来超了 | 得先瘦身 | **压缩 → 再组装 → 再量** | T1a / **失败** |
| **T2** | 模型刚给了回复，**尚未探测** | 先看它有没有原地打转 | **循环探测** | T2a–T2d |
| **T2a** | 探测无事（或只记了一笔） | 继续 | 看有没有动作 | T3 / **完成** |
| **T2b** | 探测写了**干预消息** | 提醒它一下 | 回去想 | T1 |
| **T2c** | 探测判定要结束 | 转不动了 | **收尾** | **失败**（原因：原地打转） |
| **T2d** | 探测判定要问人，**卡片已落盘** | 交给人 | 停住等 | T4 |
| **T3** | 模型回复**有动作**，尚未判断 | 该判断了 | **跑[放行判断](../PF-008-human-in-the-loop/design.md#52-那个判断函数)** | T4 / T5 |
| **T4** | 卡片已落盘、**未答完** | 该等了 | **停住**（什么都不做） | T4 / T5 |
| **T5** | 这一批卡片**全答完**（或判断直接放行） | 有结论了 | 放行的**去做**；被否的**写一条「人不同意」** | T6 / T8 |
| **T6** | 动作**发出去了，结果没齐** | 该等了 | **停住** | T6 / T7 |
| **T7** | 动作结果**齐了**（转后台的、[被卸载的](../PF-006-tools-and-skills/design.md#610-结果太大时卸载而卸载是第三个维度)，**都以占位算齐**） | 该想了 | 回 T1 | T1 |
| **T8** | 一批动作**全被否** | 也得让它知道 | 回 T1（带着「人不同意」） | T1 |

**终态三个**：**完成 / 失败 / 被取消**。**终态不可逆，且只从一个出口走**（§5.10）。

**T1b 到「失败」那条边，是这一圈里唯一一个不经过模型就结束 run 的地方。**

**被卸载的结果算「齐」**，两条理由：
[`Tools().read_result`](../PF-007-meta-capabilities/design.md#61-tools通向任意非常驻工具)
给了取回全文的通道；而且**卸载不是全卸载——占位里带摘要，很多时候摘要就够用**。
**所以它不是一个「缺了一半」的结果，而是一个完整的、可按需展开的结果。**

### 5.7 循环守卫：四级阶梯

挂在拿到模型回复之后、往下走之前。四级**都只通过改记录来起作用**：

| 级 | 做什么 | 对方程做了什么 |
|---|---|---|
| **L0** | 只记一笔（**永不可关的地板**） | 不转移 |
| **L1 / L2** | 往记录里**写一条干预消息** | 落到 T1，agent 带着它继续想 |
| **L3** | **优雅结束** | 落终态**失败**，原因写明是原地打转 |
| **L4** | **出一张卡片问人** | 落到 T4——**复用[等人](../PF-008-human-in-the-loop/design.md#决策卡片)那条路，不另造** |

**阶梯走到第几级，是从记录里数出来的**，不另存计数器。所以：

> **崩溃恢复会自动复现崩溃前的循环史。**
> 靠反复崩溃来洗白打转记录，这条路是堵死的。

**L3 落的是「失败」，不新增终态。**终态越少越好——为什么失败，本来就有地方写。

**L4 是我们比前身走得远的一处**：那边它是个关着的口子，
而我们[已经有决策池了](../PF-008-human-in-the-loop/design.md#决策池)，
直接复用——**比起直接掐掉一个跑了很久的任务，让人给个方向要友善得多**。

### 5.8 失败处置三档，判据是「谁能解决」

| 档 | 谁能解决 | 对方程做了什么 | run 的结局 |
|---|---|---|---|
| **交给 agent** | **agent 改变行为**就行 | 把错误**写成一条动作结果** → 落到 T7 | **不中断** |
| **等一等再试** | **时间** | **原地重来，不动记录** | 耗尽 → 转下一档 |
| **终局** | **谁也解决不了** | 落终态 | **失败** |

**「谁能解决」是这套分类的全部**——它不问错误长什么样，只问**出路在哪**。

两条硬约束：

- **凭据错永不重试。**密码不对，试一百次还是不对，只是把账号锁了。
- **认不出来的一律归终局**（fail-closed）。**不认识却放过去，是最危险的那种宽容。**

**「等一等再试」不产生状态转移**，这一条要紧：重试对方程是隐形的，
恢复时不会看到「重试到第几次了」这种状态——**也不需要看到**。

**第一档与[六种收场](../PF-006-tools-and-skills/design.md#53-一次工具执行的收场有六种)是同一回事**，
不另立一套说法。

### 5.9 恢复：重新算一遍 f，但尾巴要先对账

系统重启之后，记录的尾巴可能停在**正常运行时不会出现**的形状上：

| 崩在哪 | 尾巴的样子 | 怎么接 |
|---|---|---|
| **发出了动作，结果没落盘** | 有调用、无结果 | **合成一条「被中断」的结果**补上，照常走 T7 |
| **模型已给完整回复，终态没落** | 有回复、无终态 | **幂等收尾，绝不再调模型** |
| **后台执行没落完成** | 占位还在，工作没了 | 算**失败**——它跑在这个系统里，**系统没了它就没了** |

**对完账，记录就回到方程认得的形状，剩下的照常算。**

**恢复也算一次「开始」**，所以[可用性要重算](../PF-006-tools-and-skills/design.md#62-可用性在每次-run-开始前重算)。
重算之后动作空间可能与停机前不同——**那本来就是事实，早知道比撞上去才发现好**。
不必额外告知 agent 差异：它调一个已经没了的能力，
[替换件](../PF-006-tools-and-skills/design.md#替换件)会给它「用不了 + 原因」。

### 5.10 唯一终局落账点

**所有终态事实从同一个出口走。**三个终态、任何触发路径，都不例外。

附带一个很硬的细节：**漏斗先确保会话存在，再落终局**——

> **第一轮就死掉的会话，它的第一条事实就是自己的失败。**

没有这一条，那种会话会变成幽灵：run 失败了，但没有任何地方看得到它。

### 5.11 卸载：结果落成消息之前的那一关

[卸载这件事是什么](../PF-006-tools-and-skills/design.md#610-结果太大时卸载而卸载是第三个维度)
归 PF-006，**本节只定它在方程里站在哪一步**。

```text
【做】工具返回 ──→ 要落成一条消息了
         ├─ 工具自己声明了要卸载 ──→ 用它给的摘要做占位
         ├─ 没声明，但这一条超了限额 ──→ 首尾保留的机械截断
         └─ 都不是 ──────────────────→ 原样
                        ↓
                  落进记录（改记录）
                        ↓
【想】组装 ──→ 量整体 ──→ 超预算才压缩
```

**两个判据，两个时机，别混成一件事：**

| | 看的是什么 | 什么时候 | 碰谁 |
|---|---|---|---|
| **卸载** | **单条**消息有多大 | 工具结果**落成消息时** | 这一条新结果 |
| **压缩** | **整体**超没超预算 | 组装并**量完之后** | 前面的历史 |

**压缩救不了单条超限。**压缩干的是把前面的历史收成摘要，
而这条新结果是**当下正要用的东西**——把它压掉等于这次调用白跑。
所以它必须在落进消息的那一刻就处理完。

**卸载是改记录的动作**，进状态空间。这一条要紧：
恢复时从记录里读到的，是**已经卸载过的那条占位**，不是原始结果。

> **否则每恢复一次，就把那个大结果重新塞回去一次。**

它**不在「想」那一圈里**（§5.5），所以那句「这一圈真正的状态点只有压缩一个」仍然成立。

### 5.12 事件：loop 之外发生的事，怎么到 agent 眼前

**有些事不是 agent 做出来的，但它必须知道。**至少这三类：

| 事件 | 发生在什么时候 |
|---|---|
| **工具转后台** | 那次调用还没完，但 run 不等它了（[PF-006 §6.6](../PF-006-tools-and-skills/design.md#66-前台后台-与-等待态是两个维度)） |
| **后台执行完成回传** | 结果回来了，而 run 可能早走远了 |
| **注入的上下文变了** | 组织的、账号的，以及将来会有的其他[视角](../PF-007-meta-capabilities/design.md#612-cordis通向系统自身的装配定义完整本版不实现)——**agent 脚下的地变了** |

> **[卸载](#511-卸载结果落成消息之前的那一关)不在这张表里。**
> 那不是「外面发生了什么」，是 agent-loop 解析工具返回值之后自己做的一个动作。

**落点统一**：agent-loop 把它们收进记录，**下一次组装时做成消息**给 agent 看。
**做成哪一类消息、长什么样，归 PF-009**（[§9](#九未决项)）。

#### 事件必须先落进记录，这是被方程逼出来的

不能把事件攒在内存队列里等组装去取——**组装是纯派生的**（§5.3）。

> 一旦组装要「消费」队列，它就成了改状态的动作。

而 §5.5 那一圈**要组装两次**：第一次量出超了，压完再组装一次。
队列被第一次取空，第二次就拼不出同样的东西——**两次组装结果不同，方程当场失效**。

再加上 §6.1「记录先于可见」：攒在内存里的事件，**一次重启就凭空消失**。

所以：**收事件是改记录的动作，组装只负责把记录里已有的事件拼出来。**

#### 事件什么时候到，与 loop 走到哪一步无关

事件随时可能到达，但 agent **只在下一次组装时看见它**。中间这段间隔是机制的自然结果，
不是缺陷——**[run 在等人的时候也照收不误](../PF-008-human-in-the-loop/design.md#62-等待期间照常收排队等着解除时一起看到)**，
解除阻塞之后一起看到。

## 六、产品规则

### 6.1 记录先于可见

**任何要进入 agent 上下文的东西，先落盘，再进上下文。**

绝不允许「图里看得见、记录里没痕迹」——那种东西**一次重启就凭空消失**，
而 agent 的后续判断全建立在它上面。

这条对**循环守卫的干预消息**尤其硬：落盘顺序颠倒，重探时窗口就变了，
**结论可能和上次不一样**——而方程的确定性正是靠「结论必然相同」撑着的。

### 6.2 恢复不铸新身份

接着跑的那个 run，**还是原来那个 run**。身份在数据里，不在进程里。

反过来：**铸新身份是「新一次运行」的专属权利**。分不清这两者，
同一件事会在记录里留下两份，而且**没人看得出它们是同一件事**。

### 6.3 喂给 agent 的是记录原样

恢复时重建的历史，**零追加、零注入**，触发那条消息停在它原本的位置。

多塞一句「你刚才中断了」进上下文，看似贴心，实则**改变了窗口**——
循环检测会因此失准（多出来的那条可能被当成新的工作输入，把阶梯洗白）。

要让 agent 知道自己在恢复之后，**用别的途径，不要动历史**（[§9](#九未决项) 待定）。

### 6.4 恢复不重置循环阶梯

**技术恢复不是新工作。**只有新的、独立的权威工作输入才为新工作开启新阶梯。

不守这条，agent 只要崩得够勤就能无限打转，**而每次崩溃看起来都像意外**。

### 6.5 重做可以接受，但必须看得见

「从最后明确记载的状态重算」意味着**可能重做**——同一封邮件发两遍、同一笔操作做两次。

**这是用户会遇到的事，不是技术注记。**所以：

- **agent 必须知道自己处在一次恢复之后**——重做的风险由它判断，
  不知道就没法判断，也不知道该去核实什么。尤其是「合成被中断结果」那条路：
  **那个动作可能真的做了一半。**
- **恢复本身要能被人看见**——外部效果重复了，人得能追溯到是哪一次恢复造成的。

### 6.6 终态不可逆，且只有一个出口

三个终态：完成 / 失败 / 被取消。**到了就回不去**，也**不许从别的地方落账**。

### 6.7 检测状态从记录派生，不另存

循环检测的计数与阶梯，**一律从消息窗口算出来**。

不新建持久计数结构——多一份状态就多一处会和记录对不上的地方，
**而对不上的时候，没人说得清哪份是真的**。

### 6.8 L0 观测永不可关

最低那一级**只观测、不干预**，因此没有任何理由关掉它。

**关掉它，「agent 在打转」这件事就再也没人知道**——
包括那些还没严重到触发干预的早期迹象。

## 七、取舍

| 选择 | 取的 | 舍的 |
|---|---|---|
| **run 与 loop 分成两个概念** | 一个能被写下来，一个能被重新算出来 | 读者要先分清两个词 |
| **记录是唯一真相来源** | 转移完全确定，恢复不必猜 | **可能重做**，且代价由外部效果承担 |
| **组装纯派生、不建状态点** | 可以随便跑第二次；恢复时少一类状态要对 | 每圈多算一次组装的开销 |
| **摘要不二次压缩** | 不会出现「摘要的摘要」那种静默失真 | 摘要会累积，长会话终有装不下的一天 |
| **压完还超即终局失败** | 不做无用的循环压缩，且把问题指回装配 | 用户看到的是一次失败，而不是一次降级 |
| **L3 落「失败」不新增终态** | 终态只有三个，所有消费方都好处理 | 「被守卫结束」与别的失败要靠原因区分 |
| **L4 复用决策池** | 不另造机制；比直接掐掉友善得多 | 本 topic 因此依赖 PF-008 |
| **恢复重算可用性** | agent 面对的是当下的真实情况 | 恢复前后动作空间可能不同 |

### 9.2 待产品负责人裁决

| 事项 | PM 的倾向 | 为什么需要裁决 |
|---|---|---|
| **循环探测看压缩前还是压缩后的记录** | **看压缩前（原始）**。检测是系统的事，它有权看全量；压缩是为了省模型的上下文，不该影响系统自己的判断 | 若看压缩后：**agent 打转到触发压缩，反而把打转记录压没了**，阶梯归零，可以接着转 |
| **压缩能不能压掉「还悬着的东西」** | **不能**。压缩只压已经了结的部分 | 没答完的卡片、转后台没回来的执行各有一个占位。占位被压进摘要，**agent 就不知道自己还有东西在外面跑**，而记录层面它们还好端端悬着——**两边静默对不上** |

| **被否掉的动作要不要照样走一遍模型**（T8） | **要**。「人不同意」是 agent 必须知道的，否则它下一轮还会再发一次 | 代价是多一次模型调用 |
