# PF-009：上下文消息类型

**本 topic 只做消息类型**——上下文管理与组装归 **PF-010**，
异常的分层处理归 **PF-011**。

前面几个 topic 都在往上下文里放东西——工具的返回、卡片的答复、事件做成的提醒——
**却没有人说过上下文里一共有哪几种东西**。

一句话概括本版的结论：

> **七种消息，按「谁在说话」分；而每个内容块自己带着「给人看吗、给模型看吗」两个标注。**

## 七种消息

| 谁在说 | 这一种 | 它说的是什么 | agent | 用户 |
|---|---|---|---|---|
| **系统**，在开头 | `SystemMessage` | 你是谁、你该怎么做 | ✓ | **✗** |
| **人** | `UserMessage` | 我要你做什么 | ✓ | ✓ |
| **模型** | `AssistantMessage` | 我的回答，以及我要调哪些工具 | ✓ | ✓ |
| **工具**，说结果 | `ToolMessage` | 你让我跑的那个，跑完了 | ✓ | ✓ |
| **工具**，说过程 | **`ToolInternalMessage`** | **我正在干什么，干到哪儿了** | **✗** | ✓ |
| **系统**，在中途 | **`SystemReminderMessage`** | **外面有信息进来了** | ✓ | ✓ |
| **系统**，回头看 | **`CompactionMessage`** | **前面那一大段，概括起来是这样** | ✓ | ✓ |

**七种里只有两种是单边的，而且方向正好相反**——
`SystemMessage` 只给 agent，`ToolInternalMessage` 只给人。

**说话的只有四个，消息却有七种**——因为工具要说两种话（结论 / 进行中），
**系统要说三种**：长期的**设定**、外面刚来的**信息**、对前面那段的**概括**。
**这三种时间朝向各不相同**：朝前、朝当下、**朝后**。

### 出门的时候分三类

| | 哪几种 | 怎么办 |
|---|---|---|
| **各家都有的** | `SystemMessage` · `UserMessage` · `AssistantMessage` · `ToolMessage` | 直接对应 |
| **我们自己的** | `SystemReminderMessage` · `CompactionMessage` | **由 adapter 决定落成那一家的哪一种**，两种各自决定 |
| **根本不出门的** | `ToolInternalMessage` | **不进请求**——它到不了 adapter 那里 |

**头一种与末一种都是系统在说话，但说的不是一回事**：前者是长期成立的设定，
后者是刚刚发生的事。**把后者做成前者，等于把一件偶发的事写进了长期设定。**

**末一种的含义是「一次 run 中接收到了外部的信息」**——另一个会话的 agent、
自己的 subagent、一个后台执行、环境本身，**来源是它的一个属性，不是另一种消息**。

## `SystemReminderMessage` 为什么独立成一种

它在**任何一家供应商那里都不存在**，所以必须在发出去之前被翻译掉：

```text
          SystemReminderMessage
                    │
          ┌─────────┴─────────┐
          ↓                   ↓
      openai              anthropic
   DeveloperMessage      UserMessage
```

**把选择推迟到 adapter，是让每一家都能用它最合适的形状。**
在模型层就定死成用户消息，openai 那边就永远用不上更贴切的那个。

**而标识由系统加，不由产生提醒的那一处加**——
生产者交出来的是一条消息，不是一段带标签的文本，**它根本没有机会伪造**。

## 一份会话日志，两种组装

```text
            会话日志（到了我们这儿的，全都在）
                          │
            ┌─────────────┴─────────────┐
       按「给人看」                 按「给模型看」
            ↓                           ↓
     组装给人的那一份            组装给 agent 的那一份
```

**标注挂在块上，不挂在消息上**——一条被中断的回复，
**它的文本块两边都给，而那个没长完的工具调用块两边都不给**。

> **日志不是「模型该看什么」的裁剪结果，而是「实际发生了什么」的忠实留存。**
> **删减只发生在组装那一步。**

## 说状态的写清变化，说事的写清发生；消息一律追加

| 它说的是 | 这条提醒必须写出什么 |
|---|---|
| **现在是什么样** | **从什么变成了什么**——前值与现值都在这一条里 |
| **刚才发生了什么** | **发生了什么**——那件事本身 |

**判据：这条提醒讲的是一个状态，还是一件事。**
状态有「当前值」，事没有——**事只有发生过与没发生过**。
**这个分别决定提醒怎么写，不决定它在日志里的命运**——
**两类都追加，组装也不筛**；agent 看到的是整条链「之前是 A → 变成 B → 又变成 C」，
**当前值从链尾读出来**。**「取代」只发生在一个块内部**，那是到达过程，不是日志。

**同一条判据在块上还用一次，只是用判据的人不同**：提醒是系统产生的，系统判得出；
[执行帧](../PF-006-tools-and-skills/design.md#发帧)是工具产生的，
**判断发生在工具作者写代码的时候，而且是逐块判**——
**开一个块的时候它自己说明怎么填**（追加片段 / 整体替换），系统照办，
[不看工具定义](../PF-006-tools-and-skills/design.md#帧长什么样由一份协议约定不由工具定义声明)。

## 一条消息是分次到达的

**但分次到达的那些东西，不另立一种消息。**七种回答「谁在说话」，
流式回答「这一条正在怎样到达」——**两个问题，两套词表，正交**。

| | 哪些 | 怎么到 |
|---|---|---|
| **能一点点长** | 文本、思考、工具调用的参数、**语音** | 一段一段来 |
| **不能** | 图、文件、工具结果 | **开个口，然后整个交出来** |

> **半张图没有意义。半段语音有——它能播。**

**语音另有一串文本没有的麻烦**：**生成完 ≠ 用户听到了**，中间隔着播放缓冲。
**本版语音是普通的输入与输出，不是全双工**——「用户没听到的，不给模型看」是打电话那种实时双工才有的要求，
**本版不做，也不作为架构内核的约束**，记为一个设计缺口；会塌的那几条假设也记下了。

**工具执行中说的话走的是同一套**：一次工具执行对应**一条** `ToolInternalMessage`，
内容是一串块；[执行帧](../PF-006-tools-and-skills/design.md#发帧)就是**这条消息的到达增量**，
**不另立一份帧协议**。**「填」有两种模式**——说事的**追加片段**，说状态的**整体替换**，
**开块的时候说明是哪一种**。

**不造「半条消息」这个类型**——日志里要是能躺着半条消息，
读到它的人**分不出「还没说完」与「说到一半被掐了」**。

**流断在半路**：已经到了用户眼前的那部分**必须留下**——用户叫停的，落成一条标明被中断的消息；
出错断的，记在那次尝试的账里、不成为消息；
**没长完的工具调用照样记进日志**（数据完整性），**但组装时剔掉不给模型看**——
给了它，模型要么干等要么再发一次。**中断这件事本身补一条提醒告诉 agent**，
否则它会给自己编一个解释。
