# PF-009 决策与来源

产品设计允许 product manager 做判断，但**不允许发明没人拍过板的东西**。
本页把两者分开：哪些是产品负责人裁决的，哪些是 PM 自己推导的，各自依据在哪。

**rev 2 起为正式版本，待裁决与未决项均已全部闭合。**

## 二、PM 推导

从已拍板内容推出的判断，附可核对的推理链。

| 结论 | 从哪几条推出 | 推理 |
|---|---|---|
| **按「谁在说话」组织消息类型**，而不是照抄 DSH 的两轴模型 | 「参考 DSH 的消息类型」+ 产品文档面向产品负责人 | 那边是**一个 `Message` + 三值 role + 正交的 source/form 两轴**，`UserMessage` 这些名字是特化视图而非并列成员（[调研笔记](interviews/2026-09-18-dsh-message-types.md)）。两轴模型讲给产品负责人听要先解释两个维度才说得清一条消息是什么。**产品定「有哪几种、各自是谁在说话」，不定它在代码里由几个类型承载**——语义对得上即可 |
| **`SystemReminderMessage` 必须独立，不能是「带标记的用户消息」** | 「它不是 SystemMessage，是特殊的一种」这条裁决 | 三条：**①** [记录是唯一真相来源](../PF-012-agent-loop-and-run/design.md#52-会话日志是唯一的真相来源)，混进 `UserMessage` 就要靠解析内容才答得出「用户到底说了什么」——**而解析会错，标记会被伪造**；**②** 每家最合适的落点不一样，模型层定死就浪费了 openai 的 `DeveloperMessage`；**③** adapter 要认的是**类型**，不是内容里的字符串——后者谁都写得出来 |
| **每一家都必须有落点，不许落空也不许丢** | 「让每个 adapter 识别然后适配成标准的某一种」这条裁决 | 「适配成某一种」蕴含**必须有一种**。丢掉的后果是 agent 在那一家上永远看不见系统在说什么——**同一个 agent 换一家模型行为就变了，而没人查得出为什么** |
| **提醒的标识由系统加，生产者交的是一条消息** | 独立类型这条裁决 + 两家做法相反这个事实 | [DSH 让生产者自己把标签烘进内容](interviews/2026-09-18-dsh-message-types.md)，[legacy 让框架拥有转义](interviews/2026-09-18-legacy-system-reminder.md)——**两家相反，说明这是真的设计选择**。既然我们做成**类型**，生产者交出来的就是一条消息而非一段带标签的文本，**它根本没有机会写歪或伪造**。反过来，约定「自己包起来」，则**任何能左右那段文本的人都能冒充系统说话**——工具返回里带个闭合标签就够了 |
| **说状态的取代，说事的追加** | [DSH 的 `snapshot` / `notice` 两个值](interviews/2026-09-18-dsh-message-types.md) + [PF-012 的三类事件](../PF-012-agent-loop-and-run/design.md#511-外面进来的事怎么到-agent-眼前) | 判据唯一：**这条提醒讲的是一个状态，还是一件事**——状态有「当前值」，事只有发生过与没发生过。后果不对称：状态做成追加，记录里躺着三份互相矛盾的说法，**而 agent 不知道哪份是现在的**；事做成取代，**前一个后台任务跑完这件事被后一个覆盖了**，而 agent 还在等它 |
| **内容是一串块，不在进记录时压成文本** | DSH 的块结构 + [PF-006 的附件思路](../PF-006-tools-and-skills/design.md#工具的产出) | 图、思考、结构化参数压成文本就得靠解析捞回来，**而解析会错且错得静默**。要压的时候有的是——发给不支持图的模型时 adapter 自己压，**但那是出门那一刻的事，不是进记录那一刻的事**。这与 PF-006「记录里留引用、要用时才去取」是同一条 |
| **「一份记录，两种组装」是本 topic 的中枢** | 三个互不相干的需求 + 产品负责人给出的块标注机制 | 三条来路：①[工具帧给人不给模型](interviews/2026-09-18-legacy-tool-frames.md)；②半截的工具调用**留记录、组装时剔掉**；③[用户没听到的语音不能让模型以为说过了](interviews/2026-09-18-openai-realtime.md)。**三条指向同一个机制，这是它成立的最硬证据**。PM 起初只写成「记录 ⊇ 上下文」，**产品负责人给出了更准的形状**：两个标注 + 两侧对称的组装——**给人的那份与给模型的那份地位相同，不存在一份特殊的「上下文」**。由此得出：**记录不是「模型该看什么」的裁剪结果，而是「实际发生了什么」的忠实留存；删减只发生在组装那一步** |
| **`CompactionMessage` 单立一种，有两条换来的东西** | 「这个类型本身我们有用」+「未必同型」这两条裁决 | **①** 它有一层别的消息都没有的关系——**它顶替了哪一段**，而提醒是孤立的一条事实；**②** 两者**未必同型**，现在合成一种，将来分家时**所有认过它的地方都要改**。**这是一处有意的冗余，产品负责人已明说**。（PM 起初还推了第三条「系统得认出摘要才能不去二次压它」，**已被推翻**——见第四节）|
| **「概括」不是「外面来的信息」** | `SystemReminderMessage` 的含义（产品负责人定的）| 提醒说的是**外面**刚来的信息，概括说的是**里面**已经过去的那一段。做成提醒，等于说「外面有人捎话来，说你前面聊了这些」——**那不是实情**。**系统那三种消息时间朝向各不相同**：设定朝前、提醒朝当下、概括朝后 |
| **`ToolInternalMessage` 是唯一不出门的那一种** | 「adapter 决定落点」这条裁决 + 「帧不进模型上下文」 | 七种因此分三类：**各家都有的**（直接对应）、**我们自己的**（adapter 决定落成什么）、**根本不出门的**。**第三类唯一不需要 adapter 操心——它压根到不了 adapter 那里**。不点破，写 adapter 的人会为它找一个落点，**而那个落点永远不会被用到** |
| **两种自有类型各自决定落点，不必落到同一处** | 它们说的不是一回事 | 硬要求同落点，**是在假设一个不存在的共性**。某一家可能对「提醒」有更贴切的角色，而对「概括」另有一个——**捆在一起就两头都用不上** |
| **标注挂在块上，不挂在消息上** | 产品负责人给的机制 + 被中断的那条消息的形状 | **同一条消息里，各个块的去向可能不同**——一条被中断的回复，它的文本块两边都要给，而那个没长完的工具调用块两边都不给，**这两个块在同一条消息里**。挂在消息上就表达不了这种情形，只能被迫把一条消息拆成两条，**而那会伪造出一个从未发生的消息边界** |
| **[§4 那张消息级的表](design.md#七种消息各自谁感知得到)是常态，块上的标注才是实际生效的** | 上一条 | 两者会在极少数情形下不一致（比如被中断的那条消息）。**不说清楚哪个为准，两处就会打架**。表的价值在于让人一眼看清常态，**而遇到分歧以块上的标注为准** |
| **剔除动作仍然是纯派生的** | 「组装是纯派生」这条性质 + 剔除的判据 | 同一份记录，每次组装都剔掉同样的东西——**不改记录，所以不进状态空间**。这一条让 [PF-012 §5.3](../PF-012-agent-loop-and-run/design.md#53-改日志的动作与纯派生的动作) 不必因为本 topic 而修改 |
| **中断只要发生就补一条提醒，不分情形** | 「中断事件需要能被感知」这条裁决 | agent 读到一段没头没尾的东西**会去解释这个反常，而它手上没有正确的解释**——于是重说一遍、重调一次，或者在推理里给自己编个理由。哪怕什么内容都没留下也补：**「用户刚刚叫停过」本身就是它该知道的事实**，关系到用户还想不想让它继续 |
| **`ToolInternalMessage` 不进模型上下文** | 「让用户感知工具执行内部情况」这条裁决 + [legacy 四处独立文本](interviews/2026-09-18-legacy-tool-frames.md) | 一个跑五分钟的工具能产出几百条，**而模型拿这些做不出任何判断**，只会吃掉预算。legacy 的表述更直白：**结果的读者是 agent，进度的读者是人**。**两边独立到达同一结论** |
| **帧的增量语义由工具作者声明，而提醒的由系统判** | [§5.4 的判据](design.md#54-提醒说的是现在什么样还是刚才发生了什么) + 产生者不同 | **同一条判据（说状态的取代、说事的追加），但判断的人不同**：提醒是系统产生的，系统判得出；帧是工具产生的，**只有工具作者知道自己这个工具是日志型还是进度型**。声明与行为不符要**明确拒绝**，不能猜着办 |
| **被砍掉的部分必须看得出来** | [legacy 的核心纪律](interviews/2026-09-18-legacy-tool-frames.md) | **一块被悄悄截短的面板，和一块完整的面板，对看的人来说长得一模一样**——而那正是这套东西要防的事。所以合并相邻增量可以，**默默丢弃不行**；砍了要说砍了多少 |
| **发帧不会把工具搞失败** | 帧是额外的好处，不是执行的一部分 | 工具**不会因为「说不出话」而执行失败**。反过来设计，**一个本来能跑完的工具会因为面板拥堵而失败**——那是拿次要的东西去赌主要的 |
| **语音进「能增量」那一类，是判据自己分出来的** | [§5.5 的判据](design.md#能一点点长出来的与要么没有要么整个有的) | **半张图没意义，半段语音有——它能播**。语音是后来才加的，而判据**自己就把它分到了对的一边**——这说明那条判据不是为原来那三样编出来的 |
| **双工本版不解决，但要写下会塌哪几条** | 「**未来**支持实时双工」这个措辞 + [OpenAI 的迁移清单](interviews/2026-09-18-openai-realtime.md) | 现在预埋双工机制，**是在为一个还没成形的需求造框架**。但什么都不写，真做的时候会**发现整个模型都不对**。折中：**记下会塌的三条假设**（消息排成一串 / 「一轮」是实在的 / 没消息等于没人说话），**让后来者知道该回来推翻哪几条** |
| **分次到达的东西与消息类型正交，不另立一种** | 「按谁在说话分」这个模型 + 流式的本质 | 一条正在长的块，**说话的人仍然是模型**——它回答不了「谁在说话」这个问题，只回答「这一条正在怎样到达」。**两个问题，两套词表**。做成又一种消息，「按谁在说话分」那个模型当场就塌了 |
| **只给「能一点点长出来」的三样做增量，其余整个交出来** | [DSH 的形状](interviews/2026-09-18-dsh-streaming.md) + 内容的性质 | **半张图没有意义**，半个文件也没有。这条分界决定了流式词表能有多小——**将来多出新的内容块，它走「开口 + 整个交出来」这条路，流式那套一个字都不用改**。代价是新块拿不到增量能力，**而那正是它本来就不需要的** |
| **不造「半条消息」这个类型** | [记录是唯一真相来源](../PF-012-agent-loop-and-run/design.md#52-会话日志是唯一的真相来源) | [LangChain 是另一种做法](interviews/2026-09-18-dsh-streaming.md)——半条消息是完整消息的子类，两半能相加。**我们不走那条路**：记录里要是能躺着半条消息，**读到它的人分不出「还没说完」与「说到一半被掐了」**。没说完的东西只是一个正在长的块 |
| **组装出来的必须与一次性拿到的完全相同** | 可复现性 | 不成立，则「agent 看到了什么」**取决于当时网络怎么样**——而那不可复现，出了问题也没法查。**这是一条可验证的性质，不是愿望** |
| **被中断的工具调用不给模型看**（但**记录里留着**） | [DSH 的做法](interviews/2026-09-18-dsh-streaming.md) + [PF-012 尾部对账](../PF-012-agent-loop-and-run/design.md#57-一次尝试三条路通向重新算一遍) + [PF-006 中断不是失败](../PF-006-tools-and-skills/design.md#67-用户可以中断而中断不是失败) | **中断发生在动手之前**，那些调用还没派发。给了模型，它要么干等、要么再发一次。**三处独立到达「不给模型看」这个结论**——但**「不给看」不等于「不记下来」**：DSH 那边是直接丢弃，**我们留在记录里**（产品负责人裁决），**剔除发生在组装那一步**。PM 起初把这两件事混成了一件，见第四节 |
| **什么都没出来的那次，不许伪造成一条空消息** | 同上 | 一条空的 assistant 消息是在说「模型什么也没说」，**而事实是它没说完**——两者对 agent 的下一步判断完全不同 |
| **用户看见了的，记录里必须有** | 「记录是唯一真相来源」在流式下的样子 | 用户已经看见半句话，记录里没有——**他刷新一下页面那半句就凭空消失了**，而他会以为自己看错了。反过来同样是错的 |
| **没收齐的参数不解析、不执行** | [DSH 整条路上没有一处试图解析半截 JSON](interviews/2026-09-18-dsh-streaming.md) | 补一条那边没明说的理由：**残缺的参数解析出来的东西比解析失败更危险**——它**可能恰好是合法的，而少了一半字段**，于是拿着半份参数就去动手了 |
| **封口时交出完整的那一块，消费方不必自己拼** | 「组装结果必须相同」这条 | 两边各拼一次，**就有了两个可能不一致的答案**。消费方**可以**自己拼（比如为了边到边渲染），但**不必**——权威的那一份在封口时给出 |
| **一条流必须有结局** | 等待的一方需要一个终止条件 | 没有结局，等着的那一方**永远不知道该不该继续等**。这与 [PF-006 等待态「系统要知道它正在等」](../PF-006-tools-and-skills/design.md#等待态)是同一类要求 |
| **提醒要记得住是哪一处产生的** | §3 的排查场景 | 不记，排查时只剩一句「这条哪来的」。**它不必给 agent 看**——这是给排查的人看的。按[属性优先于新概念](../PF-004-agent-definition-and-assembly/design.md)的一贯做法，**这是提醒的一个属性，不是新的一种消息** |
