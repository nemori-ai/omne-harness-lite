>
> 产品负责人当天稍后更正：**我们真正要兼容的是 GPT-Live，不是 Realtime。**
> 原话与重新调研见 [GPT-Live 那一篇](2026-09-18-openai-gpt-live.md)。
>
> **本篇不作废，因为它记的事实没有错**，而且 Realtime 的那个
> [毫秒级截断动作](#一最有价值的一条生成完了--用户听到了)**是 GPT-Live 里没有的东西**——
> 两相对照才看得出那边放弃了什么。
>
> **但本篇里「新一套」那些描述只抓到了表层**：真正的差别不是「回合制 → 全双工」，
> 而是 **GPT-Live 把语音层和推理层拆成了两个模型**。**以那一篇为准。**

**这是原始材料，不是结论，更不是依据。**

**缘起**：产品负责人要给能增量的内容加一种语音：

> **quote**：「你当前的设计里面流式的内容类型只有三种，这里我们期望说增加一种：语音，
> 因为我们期望说未来我们的系统能够支持实时双工语音对话（打电话）。
> 你可以结合 openai realtime api 得到额外的参考信息，同时如果你理解了它的底层机制，
> 或许也可以帮助我们这边的产品设计」

调研时间 2026-09-18，读的是官方文档。

## 〇、一个要紧的前提：那边现在是两套，模型不一样

| | 形态 |
|---|---|
| **早一套** | **回合制 + 打断**：一次一个回复，被打断就取消；有显式的「把历史截到这里」动作 |
| **新一套** | **真全双工**：边听边说。**没有回合边界**，改成**时间轴上带起止时间的片段** |

**产品负责人说的「打电话」是后一种。**

> **而最有参考价值的，是他们从前一种走到后一种时列的那张迁移对照表**——
> 那等于免费给了一份「**回合制的假设在真双工下哪几条会塌**」的清单。

## 一、最有价值的一条：生成完了 ≠ 用户听到了

**文本流里这两件事几乎同时；语音流里差着一整个播放缓冲。**他们的原话大意：

> **服务端产生音频比实时快。**

> 服务端可能已经生成完，**而客户端手里还有一秒的音频没播**。

**由此引出一个文本世界里根本不存在的方向：**

> **进度信息要从消费端流回生产端**——客户端得告诉服务端「用户只听到了这里」。

早一套 API 专门为此设了一个动作，参数是**毫秒**（不是字符数、不是分片序号），
而且**超出实际时长会报错，不会悄悄夹到末尾**。它的官方说明里有一句很关键：

> 截断音频**会把服务端的文字转写一并删掉**，
> 以确保**上下文里不留下用户没听到过的文字**。

**这条直接支撑了本 topic 的 [§5.9](../design.md#59-语音生成了不等于听到了)**：
用户没听到的，**不能让模型以为它说过了**。

**他们自己承认的一处缺口**（值得记下）：模型没有足够信息把转写和音频精确对齐，
所以截断之后**转写究竟剩下什么，文档自己的两处说法并不一致**。

## 二、走向真双工时，他们放弃了什么

**新一套不再提供「把历史截到这里」这个动作。**取而代之的是**把播放状态完全交给客户端**，
并且直说：

> 被压下去的音频**会让模型的会话上下文领先于用户听到的内容**——请测试对话怎么接续。

> **纠正性的指示，收不回用户已经听见的话。**

**这说明「服务端历史与播放进度精确对齐」这个目标，在真双工下被他们放弃了。**
那个截断动作是**回合制模型下的补丁**，**在真双工里没有继任者**。

## 三、回合制的哪些假设会塌

他们的迁移对照表里，与本 topic 直接相关的：

| 塌掉的假设 | 新一套的实情 |
|---|---|
| 消息排成一串 | **时间轴上带起止时间的片段**，用户与助手的区间**可以重叠** |
| 「一轮」是协议层的东西 | **降级成显示层的分组**，而且必须**可以重新分组** |
| 没收到 = 没人说话 | 明确警告：**不要从「缺一个事件」推出静默**，也不要把一个片段当成完整的一轮 |
| 说话结束有个权威事件 | **没有**。要自己从播放状态推「还在说」 |
| 打断说话 = 取消工作 | **明确解耦**：「**打断说话不会自动取消后台的工作**」 |

还有一条对分组的硬约束，原话大意：

> **把片段分成组这件事本身，不得触发工具执行，也不得取消后台工作。**

**本 topic 把前三条记进了 [§5.9](../design.md#双工会动摇消息是一个接一个这个假设本版不解决)**，
**并明确本版不解决**——现在预埋是为一个还没成形的需求造框架。

## 四、转写不是语音的一个附属字段

**输入侧和输出侧的答案还不一样，这点很容易踩：**

| | 转写是什么 |
|---|---|
| **模型说的话** | 同一段内容的**另一面**，与音频并行产出 |
| **用户说的话** | **另一个模型跑出来的旁路产物**——独立计费、异步、**可能与模型实际听到的有出入**，**而且会失败** |

官方原话大意：用户侧的转写**应当被当作一份粗略的参考**。

**对本 topic 的意义**：**不能把「转写」设计成语音块上的一个必填字段**——
第一次识别失败就崩了。它更像一个**可选的、有自己状态的伴随产物**。

**本版没有把这一条写进正文**（本版只到「语音能增量」这一层），
**但真做语音时必须回来看**。

## 五、另外几条记下来备用

- **取消要带原因，不能是布尔**：他们区分了「被用户打断」「被应用取消」「写到上限」「被安全策略拦下」——
  **四种的下游处理完全不同**。
- **音频字节按需拉取**：历史项的事件里**不带音频**，要单独取。
  **这与 [PF-006 的附件](../../PF-006-tools-and-skills/design.md#工具的产出)是同一条思路**。
- **沉默本身会成为历史的一项**（超时触发时，一段空音频会被提交进对话）。
- **早一套没有断线续接机制**，会话有硬性时长上限；新一套才有基于存档的分叉恢复。
- 同一个词在那套 API 里有**两个完全不同的含义**（把音频截到用户听到的地方 / 上下文超预算裁剪）。
  **本 topic 刻意不复用这个词**。
