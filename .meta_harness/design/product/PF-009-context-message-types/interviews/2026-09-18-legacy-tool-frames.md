# 2026-09-18 · legacy 的「工具帧」

**这是原始材料，不是结论，更不是依据。**

**缘起**：产品负责人要加一种消息类型：

> **quote**：「消息类型还需要增加一种，ToolInternalMessage,这个是我们在
> omne-next/omne_harness 里面对应的 工具帧 相关的需求，具体来说就是需要有能力
> 让用户感知到一个工具执行时候的内部情况（而不是只看着界面上说调用了一个工具，
> 但是这个工具执行得如何，无从感知），同时它既然叫 帧，就意味着也是有流式增量
> 更新的需求。」

来源：`omne-next/omne_harness` 与 `omne_core_v1`，2026-09-18 读。

## 〇、一处术语澄清

**那边没有叫 `ToolFrame` 的东西。**「工具帧」是中文俗称，
正式名是 **tool-emitted progress**（工具主动流出的进度），由一条编号 ADR 裁决。

而且「帧」在那边其实是**两个层次**：

| 层次 | 是什么 | 谁看 |
|---|---|---|
| **工具 ↔ harness 之间** | 一个数据结构，三种动作：发文本增量 / 发一整块 / 改写某一块 | 内部 |
| **对外** | 六种事件：块开始 / 增量 / 块结算 / 块被改写 / 重来了 / 被截断了 | 前端 |

**本 topic 只取产品语义**，不取这两层的划分——那是技术设计的事。

## 一、最要紧的一条：帧不进模型上下文

**那边写了四处，三处带理由。**原文大意：

> **结果台账的读取面是 agent，进度表的读取面是 owner（人）。进度不进模型上下文。**

> 不把进度塞进那条工具结果消息，因为**会把过程日志灌进模型上下文**；
> agent 要拿结果，走取回工具那条路。

还有一条负面证据——他们否掉过「把进度直接写进权威历史」这个方案，理由是：

> 把可能永远没人读的大块塞进权威历史，**会污染其上的全部投影**——
> 上下文渲染、循环检测、压缩，**逐个被大载荷拖累**。

**本 topic 独立推到了同一条**（[§5.8](../design.md#58-toolinternalmessage工具说它正在干什么)），
而那边的表述比我们更直白：**结果的读者是 agent，进度的读者是人。**

**这条直接支撑了 [§5.7「会话日志 ⊇ 上下文」](../design.md#57-一份会话日志两种组装)。**

## 二、两种增量语义，由工具**类级声明**

| 那边的值 | 语义 | 像什么 |
|---|---|---|
| **追加** | 每一块各自成立，日志往下长 | shell 输出 |
| **改写** | 某个位置上的块被**整个新版本取代** | 生成式界面、进度条 |

**并且：声明是声明，动作是动作；不一致时以声明为准，并具名拒绝。**
一个声明了「我是追加型」的工具去调改写，**会被拒**。

他们还写明了为什么**不能**用追加来冒充改写：

> 追加与替换在**压实、快照与渲染**三处语义相反，
> 用追加冒充替换，**重入的人会看到拼接起来的历史版本**。

**本 topic 采纳了这个二分**（[§5.8](../design.md#两种增量语义每一块自己说)），
并指出它就是 [§5.4 那条判据](../design.md#54-提醒说的是现在什么样还是刚才发生了什么)的第二次现身——
**只是这一次判断的人从系统换成了工具作者**，因为产生者不同。

## 三、不发帧的工具是正常形态

他们的接口在工具没声明时**返回空而不是抛异常**，理由写在代码里，原文大意：

> **一支队伍里几乎每个工具都不声明进度**，
> 为一个工具的寻常形态抛异常，会让调用方每次调用都要接住一个异常。

而**声明了不发却还是发了**的情形：**明确的空操作 + 每个实例警告一次**，不静默丢。理由：

> 静默丢会让作者以为自己在说话、消费端以为工具没输出，**两边都不报错**。

**本 topic 采纳**（[§5.8](../design.md#大部分工具不发这个而那是正常形态)）。

## 四、「说了但被丢了」必须看得出来

那边有六层预算（单帧字符 / 帧率 / 单次执行总数 / 每块字节 / 每次执行字节 / 每轮字节）。
**越界的处理方式是关键**：

- 帧率超了 → **合并相邻的增量**，并**把合并掉多少条记下来**；
- 单帧太长 → 截断，**并发一条「被截断了」的帧**；
- 总量超了 → 停止实时推送，**但块照常持久化**。

**核心纪律的原文大意：**

> **一块被悄悄截短的面板，和一块完整的面板，对看的人来说无法分辨——
> 而这正是这整套词表要防的缺陷。**

**本 topic 采纳这条纪律**（[§6.16](../design.md#616-砍了要说不许默默丢)），
**但不采纳那六层预算的具体形态**——**那是政策，不是产品语义**。
（他们自己也记了一笔欠账：那几个数值是代码常量，**没有 ADR 依据**。）

## 五、发帧不会把工具搞失败

发帧的接口**永不抛异常**；调用方那一侧也把异常吸收掉。

**本 topic 采纳**：**工具不会因为「说不出话」而执行失败**。

## 六、另外两条值得记的

**渲染提示与内容类型刻意正交。**他们有九个渲染提示（纯文本 / markdown / 终端 / 日志 / 代码 / 控件 / 图 / 表 …），
与 MIME 类型**不是一一映射**。理由：同样是纯文本，可能要等宽带颜色地渲染，
也可能要逐行折叠地渲染；**只留 MIME，就是逼前端硬编码一张猜测表**。

**非法组合具名拒绝，不静默改写成默认值**，理由原文大意：

> **一个被悄悄降级成纯文本的提示，和一个从来没发过的提示，看上去一模一样。**

**本 topic 没有采纳渲染提示这一层**——**「这东西该怎么显示」是呈现的事**，
本 topic 只定「有这么一种消息、它给谁看、它怎么增量」。**要不要有渲染提示，留给后续。**

## 七、那边的实现状态：机制齐了，最后一公里没通

**如实转述，因为它影响「这条经验有多少被真实验证过」：**

| | 状态 |
|---|---|
| 机制、事件、公开接口、前端类型 | **都已落地** |
| **真实产出帧的工具** | **一个都没有**（全仓搜索零命中，他们自己的裁决文档也认下了） |
| **真实消费的界面** | **零消费** |
| 转后台之后的实时推送 | **接线缺口**，已被一条修订条款正名为缺口 |

> **所以「让用户感知工具内部」这件事在那边今天还看不见——缺的是产出者与前端，不是机制。**

**这对本 topic 的意义**：那套机制的**设计**经过了推敲（几处「为什么不那样做」写得很扎实），
但**没有经过真实使用的检验**。采纳它的判断可以，**不能把它当作已验证的经验**。
