# 2026-09-18 · DSH 的消息模型

**这是原始材料，不是结论，更不是依据。**
产品负责人的指示是「**参考** deepseek harness 现在支持的消息类型」——
**参考，不是照搬**。本 topic 的每一条都能在 [decisions.md](../decisions.md) 找到出处。

来源：`/tmp/deepseek-harness`，2026-09-18 读（只读调研）。

## 一、一处要紧的澄清：那边不是「一组平行的消息类型」

**DSH 没有 N 个并列的消息类。**它只有**一个** `Message`，带：

- 一个只有三个值的 role：`system` / `user` / `assistant`；
- 一条**正交的** `source` 轴，记「这条是谁产生的」；
- 再加一条 `form` 轴，记「这是个什么东西」。

`UserMessage` / `AssistantMessage` / `SystemMessage` / `ToolResultMessage`
**这几个名字那边确实都有**，但它们是同一个结构的**特化视图**，不是并列的成员。

**尤其：`ToolResultMessage` 的 role 是 `user`**——工具结果在那边复用用户角色，
靠内容块里的关联信息认回那次调用。

> **本 topic 按「谁在说话」组织消息类型，是产品表达上的选择。**
> 技术投影时怎么承载（几个类型、几条轴），归那一侧，**但语义必须对得上**。

## 二、`developer` 这个词的落点

**DSH 全仓库没有 `developer` role。**

产品负责人说的「openai 是 `DeveloperMessage`」**指的是 OpenAI API 那边的角色**，
不是 DSH 的类型——**这一点没有出入**，记在这里只是免得后来者去 DSH 里找它。

## 三、「同一内部类型落成不同角色」那边有现成的先例

这是本次调研对本 topic 最有用的一条：**我们要做的事，那边已经在做了。**

| 内部 | 一条路线上 | 另一条路线上 |
|---|---|---|
| **不在开头的 `SystemMessage`** | 仍是 `system` | **被折叠成 `user`**，理由是那条路线只有一个 system 槽位，折叠是为了**保住顺序** |
| **工具结果**（内部 role 是 `user`） | 拆成 `tool` | 拆成 `toolResult` |

**内部 role 与出门时的 role 本来就不一致，翻译是 adapter 的本职。**

那边还把这种能力差异**提升成了一条模型能力声明**，让上层据此决定怎么摆系统提示词——
**印证了「把映射推迟到 adapter」不是绕远路，是那一层本来就该管这件事。**

## 四、那边的 system reminder：生产者自己包，core 不管

`<system-reminder>` 这个标签在 DSH 里**确实存在**，但：

- **是生产者自己烘进内容文本里的**，core 只做原样透传；
- 有一条显式的架构注释说明这是**有意的**：framing 归调用方所有；
- 生产者自己负责把内容里的闭合标签转义掉，**免得仓库里的内容闭合掉插件的框架**。

**这与 [legacy 的做法正相反](2026-09-18-legacy-system-reminder.md)**——那边是框架拥有转义。

> **两家做法相反，恰好说明这是个真的设计选择，不是细节。**

本 topic 取**第三条路**：既然它是一种**类型**，生产者交出来的就是一条消息，
**标识由系统在出门前加**——生产者根本没有机会写歪或伪造。理由见
[design §5.3](../design.md#53-落到对面之后agent-还得分得出这不是人说的)。

## 五、那边的 `form` 轴：本 topic 吸收了其中一点

DSH 的第二条轴回答「这是个什么东西」，有六个值。与本 topic 相关的是这两个：

| 那边的值 | 语义 |
|---|---|
| `snapshot` | **当前状态**，同一生产者的新快照**取代**旧的 |
| `notice` | **刚刚发生的一次性事件**说明，**不取代**任何东西 |

**这一条被吸收进了 [design §5.4](../design.md#54-提醒说的是现在什么样还是刚才发生了什么)**，
表述改成产品语言：**这条提醒讲的是一个状态，还是一件事。**

另外四个值（`instructions` / `catalog` / `relay` / `recall`）**本版没有采纳**——
它们回答的是「这段内容属于哪一类材料」，**那是上下文管理那一块的问题**，
本版只做消息类型。

## 六、另外几条读到的事实

| 事实 | 对本 topic 的意义 |
|---|---|
| **内容是块数组，不是字符串**；块有文本 / 思考 / 图 / 文件 / 工具调用 / 工具结果 | 本 topic 采纳，见 [§4](../design.md#消息的内容是一串块不是一段文本) |
| **工具结果块的内容本身又是块数组** | 所以工具也能返回图 |
| **文件块永远不原生发给模型**：出门时投影成一段确定性的引用文本，持久记录里保留结构化引用 | **与 [PF-006 的附件](../../PF-006-tools-and-skills/design.md#工具的产出)是同一条思路**——记录里留引用，要用时才去取 |
| **没有「临时消息」这个概念**：注入的提醒是持久的，进日志、会重放、会被压缩处理 | 与 [PF-012「记录是唯一真相来源」](../../PF-012-agent-loop-and-run/design.md#52-会话日志是唯一的真相来源)一致，本 topic 采纳 |
| 一次性通知的摘要有**长度上限** | 产品上只说「要短」，**具体多少是政策，本版不定** |

## 七、调研者给的一条提示，记在这里

那份调研的结论里有一句：按 DSH 那个代码库的既有设计倾向，
**新增一种 role 或一个平行的消息接口是逆架构的**，它的扩展点是加一个 `source` 值或一个 `form` 值。

**这不改变本 topic 的产品设计**——产品定的是「有哪几种消息、各自是谁在说话」，
**不定它在代码里由几个类型承载**。但这条提示对技术投影有用：
真要复用那一层，`SystemReminderMessage` 多半会落成「一个新的 source 值」而不是一个新 role。

**语义必须对得上，承载方式归那一侧。**
