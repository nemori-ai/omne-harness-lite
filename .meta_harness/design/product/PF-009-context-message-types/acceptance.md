# PF-009 验收标准

**做成什么样算做对了。**每一条都要能被观察到，
不能观察的不写在这里——那种条款验收时只会变成各人一套解释。

## 一、可观察场景

### 七种消息，各自是谁在说话

| 场景 | 应当看到什么 |
|---|---|
| 问「一共有哪几种消息」 | **七种**，按[「谁在说话」分](design.md#七种消息按谁在说话分) |
| 问「说话的有几个」 | **四个**——系统、人、模型、工具。**工具说两种话，系统说三种** |
| 拿一条消息，问「这是谁说的」 | **答得出，且不靠读内容猜**（[§6.1](design.md#61-一条消息是谁说的永远查得到且不靠解析内容)） |
| 一条系统提醒 与 一条用户消息 摆在一起 | **分得开**——前者不是后者带了个标记 |
| 问「用户到底说了什么」 | **答得出**，因为系统插的话不在 `UserMessage` 里 |

### 谁感知得到

| 场景 | 应当看到什么 |
|---|---|
| 问「哪几种是单边的」 | **两种，方向正好相反**：`SystemMessage` 只给 agent，`ToolInternalMessage` 只给人 |
| 组装给 agent 的那一份 | **没有一条 `ToolInternalMessage`** |
| 组装给人的那一份 | **没有 `SystemMessage`**；**有** `SystemReminderMessage` 与 `CompactionMessage` |
| 一条被卸载的工具结果 | **两边都看得见，但看到的不一样**——agent 是占位，界面上可以整个展开 |
| 用户问「agent 怎么像是忘了前面说过的话」 | **看得到那条 `CompactionMessage`**，知道这里压缩过 |

### 出门的时候

| 场景 | 应当看到什么 |
|---|---|
| 一条 `SystemReminderMessage` 发给 openai | 落成 **`DeveloperMessage`** |
| 同一条发给 anthropic | 落成 **`UserMessage`** |
| 一条 `CompactionMessage` | **adapter 自己决定落成哪一种**，**不必与提醒同落点** |
| 接一家新的模型供应商 | 那两种**都有落点**；**落不出去要当场报错，不许默默丢**（[§6.2](design.md#62-我们自己那两种每一家都要有落点不许落空也不许丢)） |
| 一条 `ToolInternalMessage` | **压根到不了 adapter 那里** |
| 一个工具的返回里带了 `<system-reminder>` 这样的字样 | **模型不会把它当成系统在说话**——adapter 认的是类型，不是字符串 |

### 每个块带两个标注

| 场景 | 应当看到什么 |
|---|---|
| 拿任意一个内容块 | 它带着**两个标注**：给人看吗、给模型看吗 |
| 问「标注在消息上还是块上」 | **块上**（[§6.11](design.md#611-每个块都带给人看--给模型看两个标注)） |
| 一条被中断的模型回复 | **同一条消息里**，文本块两边都给，**没长完的工具调用块两边都不给** |
| 四种标注组合 | **都造得出来**，没有哪一种被禁 |
| 用户发来一段视频 | **它装在一个文件块里**——块清单里没有「视频块」；**这个块是「视频」模态，由它的媒体类型决定**（[§4](design.md#消息的内容是一串块不是一段文本)） |
| 用户发来一份文档 | 也是一个文件块，**但它的媒体类型不属于任何一种模态**——它就是一个引用 |

### 一份会话日志，两种组装

| 场景 | 应当看到什么 |
|---|---|
| 问「上下文有几份」 | **两份**，地位相同——**不存在一份特殊的「上下文」** |
| 两份的来路 | **同一份[会话日志](../PF-012-agent-loop-and-run/design.md#会话日志)**，只是筛选条件不同 |
| 日志里找 `SystemMessage` | **找不到**——它不落日志；给 agent 的那一份开头那条是**每次组装时现算的**（[§4 消息](design.md#消息)） |
| 记下一条消息的那一刻 | **一个字都没删**（[§6.12](design.md#612-日志完整删减只发生在组装那一步)） |
| 同一份日志组装两次 | **结果一样**——组装是纯派生的，不改日志 |
| 事后排查「当时到底发生了什么」 | **查得到**，包括那些从没给模型看过的东西 |

### 一条消息是分次到达的

| 场景 | 应当看到什么 |
|---|---|
| 问「分次到达的东西算第八种消息吗」 | **不算**——七种回答「谁在说话」，流式回答「这一条正在怎样到达」，**两套词表正交** |
| 问「哪些能一点点长出来」 | **四样**：文本、思考、工具调用的参数、**语音** |
| 问「哪些不能」 | 图、文件、工具结果——**开个口，然后整个交出来** |
| 一段语音到了一半 | **有意义**——它能播 |
| 一张图到了一半 | **没有意义**，所以图不走增量 |
| 把一次流式攒完 | **与一次性拿到的那条消息一模一样**（[§6.8](design.md#68-组装的结果与一次性拿到的必须相同)） |
| 日志里找「半条消息」 | **找不到**——没有这种类型 |
| 将来新增一种内容块 | **流式那一套一个字都不用改**——它走「开口 + 整个交出来」 |

### 流断在半路

| 场景 | 应当看到什么 |
|---|---|
| 文本流到一半被用户叫停 | **已经到用户眼前的那半段留下来**，并标明被中断（[§6.9](design.md#69-用户看见了的会话日志里必须有)） |
| 文本流到一半**出错断了** | **已经到用户眼前的那半段在那次模型调用的账里**，刷新之后照样查得到；**它不是一条消息，模型那份里没有它**，agent 从中断提醒知道刚才断了 |
| 工具调用的参数流到一半被叫停 | **那段照样记进日志**（数据完整性），**但组装给模型时被剔掉** |
| 那半截参数 | **不解析、不执行**（[§6.10](design.md#610-没收齐的工具调用参数不解析不执行)） |
| 中断发生之后 | **补一条 `SystemReminderMessage`**，让 agent 知道为什么它上一条回复只有一半 |
| 问「哪些情形补提醒」 | **只要发生了中断就补**，不分情形（[§6.13](design.md#613-只要发生了中断就补一条提醒)） |
| agent 读到那条被中断的回复 | **不会给自己编一个解释**，因为提醒告诉了它发生过什么 |

### 提醒：说状态的写清变化，说事的写清发生；消息一律追加

| 场景 | 应当看到什么 |
|---|---|
| 注入的上下文变了三次 | **三条都在**，**每一条都说得出「从什么变成了什么」**；agent 要当前值，**读链尾那一条**（[§6.4](design.md#64-说状态的写清变化说事的写清发生消息一律追加)） |
| 三个后台任务先后跑完 | **三条都在**——它们说的是**事** |
| 日志里找「被后来那条提醒取代掉的旧提醒」 | **找不到这种事**——消息之间没有取代 |
| 组装给 agent 的那一份 | **没有「同一处只取最新」这道筛子**，整条链都在 |
| 问「这条提醒是哪来的」 | **答得出**——来源是它的一个**属性**，不是另一种消息（[§6.5](design.md#65-来源是一个属性不是另一种消息)） |
| 另一个会话的 agent 捎话来 | 走 `SystemReminderMessage`，**不新增消息类型** |

### 工具帧

| 场景 | 应当看到什么 |
|---|---|
| 一个跑五分钟的工具 | 用户**看得到它干到哪儿了**，而不是只看见「正在调用某工具」 |
| 一次工具执行，日志里有几条 `ToolInternalMessage` | **一条**，内容是一串块（[§5.8](design.md#执行帧就是这条消息的到达增量)） |
| 问「帧是什么」 | **就是那条消息的到达增量**，走[与模型回复同一套到达语法](design.md#到达的过程有它自己的语法)，**没有第二份帧协议** |
| 那条消息 | **不进模型的上下文**（[§6.14](design.md#614-工具帧不进模型的上下文)） |
| 问「这一块是追加还是整体替换」 | **开块那一下它自己说**，系统照办（[§6.15](design.md#615-每一块自己说它是追加片段还是整体替换系统照办)） |
| 一个工具先吐日志、最后给一块汇总面板 | **成立**——前面那些块追加片段，最后开一个整体替换的块 |
| 一次执行跑到一半被中断 | **已经交付出去的那些块留在日志里**（[§6.9](design.md#69-用户看见了的会话日志里必须有)） |
| 一次执行发过几块帧之后**失败了** | 那条 `ToolInternalMessage` **照常收尾**，已交付的块都在；执行的收场另记为失败（[§5.8](design.md#执行帧就是这条消息的到达增量)） |
| 一次执行一块帧都没交付就收场了 | **没有这条 `ToolInternalMessage`**——不伪造一条空的 |
| 帧太多被节流 | **砍了多少、为什么砍，看得出来**；**合并相邻增量可以，默默丢弃不行**（[§6.16](design.md#616-砍了要说不许默默丢)） |
| 帧发不出去 | **这次工具执行照常跑完**（[§6.17](design.md#617-发帧发不出去不影响这次工具执行)） |
| 绝大多数工具 | **一帧都不发**，这是正常形态 |

### 语音

| 场景 | 应当看到什么 |
|---|---|
| 用户说了一段话、模型回了一段语音 | **两条都是普通的消息**，按两个标注进两侧的组装；**用户那条整条到达**，模型那条的语音块和文本块一样按到达语法一段一段到（[§5.9](design.md#本版的语音是普通的输入与输出不是全双工)） |
| 模型生成了十秒语音，用户只听到三秒 | **本版不区分**说出去多少与听到多少——那是全双工才要的，[记为设计缺口](design.md#94-设计缺口实时双工下没听到的不给模型看) |
| 用户插话打断了语音 | 停掉的是**说话**；**正在办的那件事不会因此被取消** |

### 日志里不留到达的过程

| 场景 | 应当看到什么 |
|---|---|
| 日志里找「这条消息当时分了几次到、每次到了什么」 | **找不到**，也不该有 |
| 日志里找「用户当时看到的那半段」 | **找得到**——那是内容，不是过程 |
| 模型正在往外吐字时用户刷新页面 | **看得到正在说的那句话已经到了的部分**——在途快照里有开着的追加片段块里已到的片段（[§9.2](design.md#收尾之前拼到一半的那份是在途状态不是日志不是消息)） |
| 一个发帧的工具跑到一半，用户中途重进 | 先看到已经到了的全部内容，再接着看新的；**看不到此前被节流砍过什么**——那份交代收尾时才有 |
| 日志里找「这次模型调用开口了没有、什么时候开的口」 | **找得到**——那是账；**找不到它开口之后说到了哪儿**——那是在途 |

## 二、绝不能发生的事

| 绝不能发生 | 如果发生了意味着什么 |
|---|---|
| **系统提醒被塞进 `UserMessage` 里，靠内容里的标记区分** | 「用户到底说了什么」这个事实**从此要靠解析猜**，而**标记谁都写得出来**——一个工具的返回就能冒充系统说话 |
| **产生提醒的那一处，自己把标签烘进文本** | 同上。**生产者交的必须是一条消息，不是一段带标签的文本** |
| **`SystemReminderMessage` 被做成 `SystemMessage`** | 把一件**偶发的事**写进了**长期设定** |
| **某一家供应商上，那两种自有类型悄悄被丢掉** | 同一个 agent 换一家模型**行为就变了，而没人查得出为什么** |
| **要求两种自有类型必须落到同一处** | 在假设一个**不存在的共性**——产品负责人已明说两者未必同型 |
| **给 `ToolInternalMessage` 找一个出门的落点** | 那个落点**永远不会被用到**，而写 adapter 的人会以为它该有 |
| **工具帧进了模型的上下文** | 一个话多的工具**能把整份上下文吃光**，而它说的每一条对模型都没有用 |
| **两个标注被挂在消息上而不是块上** | 一条被中断的回复就没法表达了——**它的文本块该给，工具调用块不该给，而它们在同一条消息里** |
| **记下来的那一刻就先删一道** | 出了问题**永远查不到当时到底发生了什么**——而那正是「日志是唯一真相来源」要防的事 |
| **半截的工具调用被丢掉不记** | 事后查不到模型当时**打算调什么工具**——而那是排查中断问题最要紧的线索 |
| **半截的工具调用被送给了模型** | 它要么**干等一个永远不来的结果**，要么**再发一次** |
| **没收齐的参数被解析出来执行了** | 比解析失败更危险——**它可能恰好合法，而少了一半字段** |
| **中断发生了却没补提醒** | agent 看见自己上一条回复只有一半，**会给自己编一个解释** |
| **造出「半条消息」这种类型** | 日志里躺着半条消息，读到的人**分不出「还没说完」与「说到一半被掐了」** |
| **攒完的消息与一次性拿到的不一样** | 同一次对话，**流式和非流式跑出两种结果** |
| **说状态的提醒只报当前值，不说它是从什么变过来的** | 链断在每一条上——agent 面前躺着**几份各说各话的当前值**，**它得自己猜哪条在前** |
| **任何一条提醒在日志里被后来的那条取代或覆盖** | **因果链断了**：那一步变化从此查不到，而**日志只增不改**本来就不允许这种事 |
| **组装时按「同一处只取最新」把旧的那几条筛掉** | agent 看不见地是什么时候动的、动了几次——**而那正是它该知道的事实** |
| **为「另一个 agent 发来的消息」新增一种消息类型** | 来源是**属性**，不是类型——这么走下去每多一个来源就多一种类型 |
| **帧的增量语义要工具在定义里先声明** | 多了一个**从头到尾不会被读一次**的字段，还堵死了「先日志、后面板」这条路 |
| **一次工具执行落成一串 `ToolInternalMessage`** | 日志里多出一批**没人指得住**的消息，而它们本来是同一条消息里的一串块 |
| **帧另走一份自己的到达协议** | 封口、记账、断流收场要在两处各定一遍，**两处定得不一样时没人知道该信哪份** |
| **系统先查工具定义，再决定怎么解析帧** | 解析策略不统一了——**同样一份数据，换个工具发出来就被当成别的东西** |
| **一次工具执行因为「帧没发出去」而失败** | 一个纯粹的旁白决定了正剧的结局 |
| **一块面板被悄悄截短** | **它和一块完整的面板，对看的人来说长得一模一样**——而那正是这整套东西要防的 |
| **为了「没听到的不给模型看」，本版就去拆语音块、改标注** | 那是全双工的要求，[本版不作为架构内核的约束](design.md#94-设计缺口实时双工下没听到的不给模型看)；提前做，**是在为一个还没成形的需求造框架** |
| **收不下图的模型，在出门那一刻由 adapter 把图压成文本** | 模型读到的是一份**谁都没登记过、日志里查不到**的文本；[该读什么，落盘之前就由转换件定好了](design.md#66-内容是块不在进日志时压成文本) |
| **出错断流时，把用户已经看见的那半段丢掉** | 他刷新一下，那半段就凭空消失了 |
| **打断语音顺带取消了正在办的事** | 用户只是插了句话，**他没说不办了** |
| **为了「能回放当时的样子」把每个增量单独存下来** | **那份数据没有消费者**（[D-2 已裁决](decisions.md#三待裁决)） |

## 三、判据

| 设计点 | 做到了的判据 | 没做到时的表现 |
|---|---|---|
| 消息类型分得清 | 任取一条消息，**答得出是谁说的，且不读内容** | 要靠解析内容或看标记才分得出 |
| 单边的只有两种 | 遍历两份组装，**只有 `SystemMessage` 与 `ToolInternalMessage` 各缺一边** | 有第三种消息在某一边看不见 |
| 落点不许落空 | 接一家新供应商时**故意不配那两种的落点**，**当场报错** | 悄悄丢掉，跑起来才发现 agent 什么都没看见 |
| 标注在块上 | 造一条「文本给两边、工具调用块两边都不给」的消息，**表达得出来** | 只能整条给或整条不给 |
| 两侧组装对称 | **同一份日志组装两次，各自结果稳定**，且**互不影响** | 一侧的筛选改了另一侧也变 |
| 日志完整 | 中断一次流式，**日志里半截工具调用还在**，而模型那份里没有 | 日志里也没了 |
| 攒出来的等于一次拿到的 | **同一次响应跑流式与非流式，产物逐字相同** | 两种跑法结果有出入 |
| 状态与事分得清 | 让上下文变三次、让三个后台任务先后完成，**六条全在**；且前三条**各自说得出前值与现值**，后三条只说发生了什么 | 状态那三条里有一条报的是光秃秃的当前值，或者有任何一条在日志里被覆盖掉 |
| 帧不进模型上下文 | 让一个工具发一千帧，**模型那份上下文长度纹丝不动** | 上下文被撑大 |
| 一次执行一条消息 | 让一个工具发一千帧，**日志里那次执行只有一条 `ToolInternalMessage`**，块有一千个 | 日志里躺着一千条消息 |
| 填法逐块决定 | 同一次执行里**前面的块追加片段、最后一块整体替换，两种都生效** | 要先声明，或后一种被拒 |
| 砍了看得出来 | 触发节流，**界面上说得出砍了多少** | 面板悄悄变短 |
| 不留到达过程 | 跑一次流式，**日志里只有最终那条**（外加中断时已交付的部分） | 日志里躺着一串增量 |

## 四、本版不验收的

| 不验收 | 为什么 |
|---|---|
| 两侧的组装**各自怎么做** | 归 **PF-010**。本 topic 只验**标注在不在、两侧对不对称** |
| 压缩**什么时候发生、收走哪一段、摘要里装什么** | 同上 |
| 卸载后的占位、卡片答复**各自落成哪一种消息** | 同上——那是「组装成消息那一步怎么做」 |
| 异常的**分层处理** | 归 **PF-011**。本 topic 只验**流断在半路时日志里留下什么** |
