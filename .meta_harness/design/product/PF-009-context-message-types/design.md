# PF-009：上下文消息类型

## 一、背景与问题

前面几个 topic 都在往上下文里放东西，**却没有人说过上下文里一共有哪几种东西**。

| 谁 | 往里放了什么 |
|---|---|
| [PF-004](../PF-004-agent-definition-and-assembly/design.md) | 系统提示词的成分，以及它在哪一刻定死 |
| [PF-006](../PF-006-tools-and-skills/design.md) | 工具的返回怎么进消息；[卸载](../PF-006-tools-and-skills/design.md#610-结果太大时卸载而卸载是第三个维度)后换成占位；转后台先放占位 |
| [PF-007](../PF-007-meta-capabilities/design.md) | [十三扇门](../PF-007-meta-capabilities/design.md#54-十三个槽位是预算的地板也是它的天花板意义)常驻占预算 |
| [PF-008](../PF-008-human-in-the-loop/design.md) | 卡片答完之后，结果回到那次 run |
| [PF-012](../PF-012-agent-loop-and-run/design.md) | [外面进来的事](../PF-012-agent-loop-and-run/design.md#511-外面进来的事怎么到-agent-眼前)**以消息的身份落进会话日志**——**做成哪一种，那边没说** |

**每一处都在说「变成一条消息」，而「消息有哪几种」从没定义过。**

四个问题因此悬着：

- **一条消息到底是谁说的？**系统插进来的提醒，与用户真的说的话，
  如果在日志里长得一样——**agent 会把系统的话当成人的话去回应**，
  而「用户到底说了什么」这个事实，从此要靠猜。
- **同一份上下文发给不同供应商，形状并不一样。**谁负责翻译？
  翻译规则写在哪？定不下来，换一家模型就要重写一遍上下文的组装逻辑。
- **压缩产出的那份摘要，是一条什么？**[PF-012 明确把这个问题留给了这里](../PF-012-agent-loop-and-run/changelog.md)。
- **卸载后的占位、转后台的占位，算哪一类？**它们既不是工具真的返回了什么，
  也不是系统在说话。

本 topic 把这些补上。**本版先做第一块：消息一共有哪几种。**

## 二、目标与非目标

### 目标

1. **定义消息类型清单**：一个会话的日志里，可能出现哪几种消息，各自是谁在说话。
2. **定义我们自己那两种**（`SystemReminderMessage`、`CompactionMessage`）：
   它们为什么各自独立，以及**怎么落到各家供应商**——那里都没有这两种。
3. **定义「一条消息分次到达」**：它与消息类型是什么关系、断在半路怎么收场。
4. **定义每个内容块的两个标注**（给人看吗、给模型看吗），**以及它们为什么必须在块上**。

> **本 topic 到此为止。**产品负责人 2026-09-18 划定：
> **「这个 topic 我们只讲消息类型的产品设计。」**
> 上下文管理与组装另起一个 topic（**PF-010**），异常的分层处理再另起一个（**PF-011**）。

### 非目标

| 不做什么 | 为什么 |
|---|---|
| **上下文管理与组装**：两侧的组装各自怎么做、压缩产出什么形状、摘要怎么组织 | 归 [**PF-010**](../PF-010-context-management-and-assembly/README.md)（**rev 5，已接受**）。本 topic 只定**它们要用的那两个标注**，不定**怎么用** |
| **异常的分层处理机制** | 归 [**PF-011 非常态的分层处置**](../PF-011-off-nominal-handling/README.md)。本 topic 只定**流断在半路时日志里留下什么**，不定它怎么分层处置 |
| 每种消息**具体有哪些字段、叫什么名字** | 产品定**有哪几种、各自是谁在说话**；字段与序列化是技术设计 |
| 各家供应商 API 的**具体调用形式** | 产品只定「同一条消息在不同家落成什么」，怎么发是技术设计 |

| 一次 run 怎么被驱动、外面进来的事怎么落进日志 | 归 [PF-012](../PF-012-agent-loop-and-run/README.md)。本 topic 只定**收进来之后做成什么** |
| 系统提示词的**成分与组装时刻** | 归 [PF-004](../PF-004-agent-definition-and-assembly/design.md#54-为什么系统提示词必须落在第三列)。本 topic 不重定 |
| **模态、以及收不下某种模态时模型读的是哪一份** | 归 [PF-013](../PF-013-model-profiles-and-invocation/design.md#模态)（rev 5）。本 topic 只定**块有哪几类**，块装的东西是哪种模态、怎么转，都在那边 |
| **全双工语音**，以及它要求的「**用户没听到的，不给模型看**」 | **本版不做**，产品负责人已明确它**不作为架构内核的约束**。本版语音是普通的输入与输出（[§5.9](#59-语音生成了不等于听到了)），缺口记在 [§9.4](#94-设计缺口实时双工下没听到的不给模型看) |

## 三、用户与场景

| 使用者 | 什么时候接触这块 | 他关心什么 |
|---|---|---|
| **agent 自己** | 每一轮读上下文 | **这条是谁说的？**是人要我做，还是系统告诉我发生了件事 |
| **写 adapter 的人** | 接一家新的模型供应商 | 我拿到一条内部消息，**该把它变成那边的什么** |
| **排查上下文问题的人** | agent 答非所问、或者对着系统提醒回话 | 这条消息**是哪来的**？它本来该长什么样 |
| **工具作者** | 工具返回很大、或者转了后台 | 我的返回**落成一条什么**，agent 看到的是什么 |
| **产品负责人** | 决定要不要换模型供应商 | 换一家，**agent 的行为会不会变** |

**第一行仍然是直接消费者。**它分不清「系统插的话」与「人说的话」，
就会把一条提醒当成指令去执行，或者对着一条通知回一句「好的」。

### 消息

**一条对话记录。**

它落在[会话日志](../PF-012-agent-loop-and-run/design.md#会话日志)里，
而**日志里不只有消息**：

> **会话日志是一份只增不改的流水账，消息只是它的一部分。**
> **其余是各种不是消息的事**——每次工具执行的账、一次尝试开始这个事实。

**本 topic 只管消息这一部分**：有哪几种、各自是谁在说话、内容长什么样。
**日志本身归 [PF-012](../PF-012-agent-loop-and-run/design.md#会话日志)，
那些事件具体有哪些，本版不展开。**

> **另一层关系也要分清：日志不等于「拿去用的那一份」——日志是一份，拿去用的有两份。**

**一份组装给人，一份组装给 agent**，各按[块上的标注](#每个块带两个标注给人看吗给模型看吗)
从同一份日志里筛（§5.7）。

```text
            会话日志（全都在）
                   │
        ┌──────────┴──────────┐
        ↓                     ↓
   组装给人的那份        组装给 agent 的那份
```

**两侧地位相同**——**不存在一份特殊的「上下文」凌驾于另一份之上**。

### 七种消息，按「谁在说话」分

| 谁在说 | 这一种 | 它说的是什么 |
|---|---|---|
| **系统**，在开头 | `SystemMessage` | 你是谁、你该怎么做 |
| **人** | `UserMessage` | 我要你做什么 |
| **模型** | `AssistantMessage` | 我的回答，以及我要调哪些工具 |
| **工具**，说**结果** | `ToolMessage` | 你让我跑的那个，**跑完了，结果是这样** |
| **工具**，说**过程** | **`ToolInternalMessage`** | **我正在干什么，干到哪儿了** |
| **系统**，在中途 | **`SystemReminderMessage`** | **外面有信息进来了，你得知道** |
| **系统**，回头看 | **`CompactionMessage`** | **前面那一大段，概括起来是这样** |

**前四种各家模型供应商都有，后三种是我们加的。**

#### 说话的有四个，消息却有七种

**因为有的说话者要说不止一类话：**

| 谁在说 | 说几种 | 分别是 |
|---|---|---|
| **人** | 一种 | — |
| **模型** | 一种 | — |
| **工具** | **两种** | 一次调用的**结论** / 一次调用**进行中**的情况 |
| **系统** | **三种** | 长期的**设定** / 外面刚来的**信息** / 对前面那段的**概括** |

> **所以「谁在说话」不足以唯一确定一条消息**，还得看它说的是哪一类话。

**系统那三种，时间朝向各不相同**：设定朝**前**（这次对话开始之前就定好了），
提醒朝**当下**（刚刚发生了一件事），**概括朝后**（回头看已经过去的那一段）。

`SystemMessage` 在[实例存续期内恒定](../PF-004-agent-definition-and-assembly/design.md#54-为什么系统提示词必须落在第三列)，
而 `SystemReminderMessage` 随时可能出现在对话中间——
**把后者做成前者，等于把一件偶发的事写进了长期设定**。

同理，**把工具的过程混进它的结果里，等于让「跑到哪儿了」冒充「跑出了什么」**。

### 七种消息，各自谁感知得到

**这张表是定义的一部分，不是补充说明。**不写死，后面每个人都得自己猜一遍。

> **这张表说的是常态，而真正起作用的是[块上的那两个标注](#每个块带两个标注给人看吗给模型看吗)。**
> 表让人一眼看清每种消息通常去向哪边；**遇到分歧，以块上的标注为准**。

先把两个「感知」说准：

| 说法 | 准确的意思 |
|---|---|
| **agent 感知得到** | 它**出现在组装给 agent 的那一份里** |
| **用户感知得到** | 它**出现在组装给人的那一份里** |

| 消息 | agent | 用户 |
|---|---|---|
| `SystemMessage` | **✓** | **✗** |
| `UserMessage` | ✓ | ✓ |
| `AssistantMessage` | ✓ | ✓ |
| `ToolMessage` | ✓ | ✓ |
| **`ToolInternalMessage`** | **✗** | **✓** |
| `SystemReminderMessage` | ✓ | ✓ |
| **`CompactionMessage`** | ✓ | ✓ |

**七种里只有两种是单边的，而且方向正好相反：**

> **`SystemMessage` 只给 agent——那是给它的设定，不是说给人听的话。**
> **`ToolInternalMessage` 只给人——那是工具干活的过程，模型拿它做不出任何判断。**

**其余五种两边都感知得到。**

**`CompactionMessage` 对用户也可见**，理由与提醒那条一样：
人那一侧本来就不受上下文预算的限制，**他看得到完整的历史**——
如果看不到「这里压缩过了」这个标记，
**他就会奇怪 agent 怎么突然像是忘了前面说过的细节**。

### 出门的时候，七种分三类

**这是给写 adapter 的人看的那张表。**

| | 哪几种 | 出门时怎么办 |
|---|---|---|
| **各家都有的** | `SystemMessage` · `UserMessage` · `AssistantMessage` · `ToolMessage` | **直接对应**过去 |
| **我们自己的** | **`SystemReminderMessage`** · **`CompactionMessage`** | **由 adapter 决定落成那一家的哪一种**（§5.2） |
| **根本不出门的** | **`ToolInternalMessage`** | **不进请求**——它不给模型看，自然也没有落点问题 |

> **中间那一类是需要翻译的**：它们在任何一家的接口里都不存在，
> **所以必须在发出去之前被译掉**。

**第三类是唯一不需要 adapter 操心的**——**它压根到不了 adapter 那里**。

#### 三件容易搞错的事

**一、「两边都看得见」不等于「两边看到的一样」。**
被[卸载](../PF-006-tools-and-skills/design.md#610-结果太大时卸载而卸载是第三个维度)的工具结果，
agent 看到的是占位，用户界面上可以整个展开；
一条提醒给 agent 的是正文，给用户的可以是一行简短的提示。
**呈现怎么做归呈现，本表只说「感知不感知得到」。**

**二、`SystemReminderMessage` 对用户也是可见的。**
它记的是会话里真实发生过的事——后台任务完成了、外面捎话来了、刚才被叫停了。
**藏起来，用户就会看不懂 agent 接下来为什么那么说。**

**三、这张表说的是消息，不是消息里的每一部分。**
有些东西整条消息在两边都可见，**但其中某一块单独被挡掉**——
[没长完的工具调用](#半截的工具调用记下来但不给模型看)就是这样。**那是 §5.7 的事。**

### 消息的内容是一串块，不是一段文本

一条消息里装的是**若干个块**，块有这么几类：

| 块 | 装什么 |
|---|---|
| **文本** | 给人和模型看的话 |
| **思考** | 模型的推理过程——**与它给人看的话分开** |
| **语音** | 说出来的话（§5.9） |
| **图** | 图片本身 |
| **文件** | 一个[附件](../PF-006-tools-and-skills/design.md#工具的产出)的引用，**不是文件内容** |
| **工具调用** | 模型要调哪个工具、传什么参数 |
| **工具结果** | 一次调用的结果，**它自己又是一串块**（所以工具也能返回图） |

**块的类型是载体，不是[模态](../PF-013-model-profiles-and-invocation/design.md#模态)。**
模态（文本 · 图 · 语音 · 视频）是内容的形态，归 [PF-013](../PF-013-model-profiles-and-invocation/design.md#模态)；
**一个块是哪种模态，由它的媒体类型决定**。**视频没有自己的块类型，它装在文件块里**——
媒体类型是一段视频，这个文件块就是「视频」；媒体类型不属于任何一种模态的（一份文档），它就只是一个引用。
**不为视频另立一类块**：块是按「这是什么东西、怎么到」分的，而一段视频与别的附件一样，**开个口、整个交出来**（§5.5）。

**为什么不能是一段文本**：一条消息里可能既有文字又有图；
模型的思考与它的回答是两回事，混在一起就再也分不开；
工具调用的参数是结构化的，压成文本就要靠解析捞回来——**而解析会错**。

**工具在执行过程中说的话，用的也是这些块**（§5.8）——
**它不另外多出一类块**：一段文本、一张图、一个文件的引用，与别人说的话是同一批东西。

### 每个块带两个标注：给人看吗、给模型看吗

**这是本 topic 的中枢机制。**每一个块上都有这两个标注：

| 标注 | 它管什么 |
|---|---|
| **给人看** | 组装**面向人的那一份**时，取不取它 |
| **给模型看** | 组装**面向 agent 的那一份**时，取不取它 |

**两个标注互不决定**，四种组合都成立：

| 给人 | 给模型 | 什么东西长这样 |
|---|---|---|
| ✓ | ✓ | **绝大多数**——人说的话、模型的回答、工具的结果 |
| ✓ | ✗ | [工具执行中的过程](#toolinternalmessage) |
| ✗ | ✓ | 给模型的设定、以及别的「对人没有意义但模型要用」的东西 |
| ✗ | ✗ | [没长完的工具调用](#半截的工具调用记下来但不给模型看)——**留在日志里备查，两边的视图都不取** |

> **标注在块上，不在消息上。**

**因为同一条消息里，各个块的去向可能不同**：一条被中断的回复，
**它的文本块两边都要给，而那个没长完的工具调用块两边都不给**——
**这两个块在同一条消息里。**

**标注只说「取不取」，不说「长什么样」。**怎么呈现、要不要折叠、
要不要换一种说法，**那是组装那一侧各自的事**。

> 这个标注还是后面谈**上下文压缩**的前提——
> **压缩要先知道哪些块是给谁的，才谈得上压谁、留谁。**具体归[后续](#九未决项)。

### SystemReminderMessage

**一次 run 中，接收到了来自外部的信息。**

**「外部」是相对这次 run 说的**——不是 agent 自己做出来的，也不是人直接对它说的：

| 外面是谁 | 什么样的信息 |
|---|---|
| **另一个会话里的 agent** | 它发来一条消息 |
| **自己派出去的 subagent** | 它干完了，回来报告 |
| **后台的工具执行** | 跑完了，结果回来了；**或[恢复时对账发现它异常中断了](../PF-012-agent-loop-and-run/design.md#先对账再进方程)（由系统代落）** |
| **环境** | 组织与账号的上下文变了，以及将来别的[视角](../PF-007-meta-capabilities/design.md#612-cordis通向系统自身的装配定义完整本版不实现) |

**来源是它的一个属性，不是另一种消息。**

> **这几样对这次 run 来说是同一件事：外面有信息进来了。**

为每一类来源另立一种消息，五种就会变成七种八种，**而 agent 的处理方式并没有因此不同**——
它照样是「读一读，然后接着干」。何况**消息的正文本身就说得清是什么事**，
agent 读得懂，**不必靠类型去认**。

它有三条性质：

- **它不是任何一家供应商的标准类型。**各家都没有这一种——
  所以它**必须在发出去之前被翻译掉**（§5.2）。
- **它由系统产生，不由人产生。**哪怕正文里转述的是另一个 agent 说的话，
  **说这句话的仍然是系统**——是系统在告诉这个 agent「外面有人捎了话来」。
- **它是[会话日志](../PF-012-agent-loop-and-run/design.md#会话日志)的一部分，不是临时的。**
  [外面进来的那件事就是以它的身份落进日志的](../PF-012-agent-loop-and-run/design.md#511-外面进来的事怎么到-agent-眼前)，
  参与压缩、恢复时读得回来——与别的消息一视同仁。

### ToolInternalMessage

**一次工具执行过程中，它自己说出来的情况。**

**一次工具执行对应一条**，内容是一串块——
**正如一次模型调用对应一条 `AssistantMessage`**。块可以很多，消息只有一条。

它补的是一个具体的窟窿：用户看着界面上写着「正在调用某个工具」，
**然后就没有下文了**——它是卡住了，还是在正常地跑一件慢活，**现在分不出来**。

三条性质：

- **它是给人看的，不进模型的上下文**（§5.7）。一个跑五分钟的工具能产出几百个块，
  **而模型拿这些做不出任何判断**。
- **发不发是工具作者的选择**，而**绝大多数工具不发**——那是正常形态，不是缺陷。
- **它和模型的回复一样是分次到达的**：[执行帧](../PF-006-tools-and-skills/design.md#发帧)
  就是这条消息的到达增量，走的是 [§5.5 那套到达语法](#到达的过程有它自己的语法)；
  **每个块在开的时候说明自己怎么填**——追加片段，还是整体替换（§5.8）。

> **它与 `ToolMessage` 是两条轨**：一条说**过程**，一条说**结论**。
> 混在一起，就是让「跑到哪儿了」冒充「跑出了什么」。

### CompactionMessage

**系统回头看，把前面那一大段概括成的一条。**

它与 `SystemReminderMessage` **有两点相同**：
**都不是任何一家供应商的标准类型**，**都由 adapter 决定落成那一家的哪一种**（§5.2）。

**但它们不是一回事：**

| | `SystemReminderMessage` | `CompactionMessage` |
|---|---|---|
| 说的是 | **外面**刚来的信息 | **里面**已经过去的那一段 |
| 时间朝向 | 当下 | **回头看** |
| 与别的消息的关系 | **没有**——它自己成立 | **有**：它**顶替**了某一段 |

> **「概括」不是「外面来的信息」**——它是系统对**已有内容**的再加工。
> 做成提醒，等于说「外面有人捎话来，说你前面聊了这些」——**那不是实情**。

#### `CompactionMessage` 凭什么单独成一种：两条

**一、它有一层别的消息都没有的关系：它顶替了哪一段。**
提醒是孤立的一条事实，**摘要不是**——**它一定对应着被它收走的那一批**。
这层关系挂在哪里，只有它自己有。

**二、它以后多半会长得更复杂，而提醒不会。**
**两者未必同型**，现在合成一种，将来分家的时候**所有认过它的地方都要改**。

> **这是一处有意的冗余**：理论上确实可以塞进提醒里（§7）。
> **单立一种，换的是上面这三条。**

#### 压缩本身怎么工作，本版不定

**本版只定「它是一种消息、它是谁说的、它给谁看、它怎么出门」。**

压缩**什么时候发生、收走哪一段、摘要里装什么**，
归 [**PF-010**](../PF-010-context-management-and-assembly/README.md)（**rev 5，已接受**）。

## 五、模型

### 5.1 `SystemReminderMessage` 凭什么独立，而不是「一条带标记的用户消息」

最省事的做法是：就发一条 `UserMessage`，内容里加个标记说「这是系统说的」。
**三条理由否掉它。**

#### 一、日志里要分得开

[会话日志是唯一的真相来源](../PF-012-agent-loop-and-run/design.md#52-会话日志是唯一的真相来源)。
提醒要是混在 `UserMessage` 里，**「用户到底说了什么」这个事实就得靠解析内容才能回答**。

> **而解析会错，标记会被伪造。**

#### 二、每一家最合适的落点不一样

openai 那边有 `DeveloperMessage` 这一种，语义上比 `UserMessage` 贴切得多；
anthropic 那边没有，只能落成 `UserMessage`。

**在我们的模型里就定死成用户消息，openai 那边就永远用不上更合适的那个。**

> **把选择推迟到 adapter，是让每一家都能用它最合适的形状。**

#### 三、正因为它是一种类型，adapter 才认得出它

这条听着像循环，其实是实打实的：adapter 要做映射，得先认得出「这是一条提醒」。
**认的是类型，不是内容里的字符串**——后者谁都写得出来。

### 5.2 我们自己那两种，在各家落成什么

**`SystemReminderMessage` 与 `CompactionMessage` 都是我们自己的类型**，
**各家接口里都没有**——所以两者都得在发出去之前被译掉，
**而译成什么，由那一家的 adapter 决定**。

```text
       SystemReminderMessage        CompactionMessage
                 │                          │
       ┌─────────┴────────┐        ┌────────┴────────┐
       ↓                  ↓        ↓                 ↓
   openai            anthropic   openai          anthropic
DeveloperMessage    UserMessage   （各自的 adapter 定）
```

**这不是我们发明的怪招。**同一个内部类型因供应商能力不同而落成不同角色，
[DSH 已经有现成的先例](interviews/2026-09-18-dsh-message-types.md)：
一条不在开头的 `SystemMessage`，在一条路线上仍是 system，在另一条路线上**被折叠成 user**。

**映射表归 adapter，不归本 topic。**本 topic 定的是：

> **每一家都必须为这两种各给出一个落点，而且必须落成那一家真的支持的类型。**

**不许落成「发不出去」的东西**，也**不许因为某家没有合适的就把它丢掉**——
丢掉意味着 agent 在那一家上永远看不到系统在说什么，
**而同一个 agent 换一家模型行为就变了**。

> **两种各自决定，不必落到同一处。**
> 它们说的本来就不是一回事（§4），**硬要求它们同落点，是在假设一个不存在的共性**。

### 5.3 落到对面之后，agent 还得分得出这不是人说的

**我们自己那两种，一旦落成了那一家的普通角色，就与人说的话长得一样了**——
`SystemReminderMessage` 在 anthropic 那边就是一条 `UserMessage`。
所以**内容上必须自带标识**。

**而这个标识由系统加，不由产生那条消息的那一处加。**

> **这正是「独立类型」比「约定一个文本封套」更安全的地方。**

产生它的那一处交出来的是**一条消息**，不是一段带标签的文本——
**它根本没有机会把标签写歪，也没有机会伪造一个**。
反过来，如果约定「自己把内容包进某个标签里」，那么**任何能左右那段文本的人都能冒充系统说话**——
一个工具的返回里带上一个闭合标签就够了，**而 agent 没有任何办法分辨**。

**这一条对工具返回、对外部来的内容尤其硬**，因为那些内容本来就不受我们控制。

### 5.4 提醒说的是「现在什么样」，还是「刚才发生了什么」

**这条判据决定这条提醒该怎么写**，
**不决定它在[会话日志](../PF-012-agent-loop-and-run/design.md#会话日志)里的命运**——
**那个命运只有一个：追加。**

| 它说的是 | 这条提醒必须写出什么 | 例子 |
|---|---|---|
| **现在是什么样** | **从什么变成了什么**——前值与现值都要在这条里说清 | 组织与账号的[上下文](../PF-007-meta-capabilities/design.md#612-cordis通向系统自身的装配定义完整本版不实现)变了 |
| **刚才发生了什么** | **发生了什么**——那件事本身 | 一个后台工具跑完了、一次执行转了后台 |

**两类在日志里一律追加，[组装](#57-一份会话日志两种组装)的时候也不按「同一处只取最新」再筛一道。**
agent 读到的是整条链：**之前是 A → 变成了 B → 又变成了 C**，
**当前值由它从链尾读出来。**

> **因果链不能断。**变过三次就是变过三次——**这三步本身就是 agent 该知道的事实**，
> 它据此判断脚下的地什么时候动的、动了几次、往哪个方向动。

**这条链读得明白，全靠第一列那个要求。**说状态的提醒自己交代「从什么变成什么」，
三条连起来才是一段能对齐的变化史；**只报当前值，链就断在每一条上**——
读的人得自己猜哪条在前，而**那正是「三份各说各话」的来源**：
问题从来不在旧的那几条还在，在于每一条都没说自己是从哪儿变过来的。

> **判据很简单：这条提醒讲的是一个状态，还是一件事。**

状态有「当前值」，事没有——**事只有发生过与没发生过**。
**这个分别在写法上有后果**（要不要交代前值），**在日志里没有**。

**[PF-012 的三类事件](../PF-012-agent-loop-and-run/design.md#511-外面进来的事怎么到-agent-眼前)由此各归其位**：
工具转后台、后台执行完成回传，写的是**事**；注入的上下文变动，写的是**状态**，
**所以那一条要带上「从什么变成了什么」**。

> **「取代」在本 topic 只有一个落点：[一个块内部的整体替换](#填有两种模式开块的时候说明是哪一种)。**
> 那说的是**一条消息正在到达**的过程，**与日志无关**——**消息之间没有取代。**

### 5.5 一条消息是分次到达的

**模型的回复不是一下子给的，是一段一段来的。**用户要看见字往外冒，
而不是盯着空白等三十秒。

> **但分次到达的那些东西，不是第八种消息。**

[七种消息](#七种消息按谁在说话分)回答**谁在说话**；这里回答的是**这一条正在怎样到达**。
两个问题，**所以是两套词表，正交**。

#### 能一点点长出来的，与要么没有要么整个有的

| | 哪些 | 怎么到 |
|---|---|---|
| **能一点点长** | 文本、模型的思考、**工具调用的参数**、**语音** | 一段一段来 |
| **不能** | 图、文件、工具结果 | **开个口，然后整个交出来** |

> **半张图没有意义。半段语音有——它能播。**

**这条分界决定了流式那套词表能有多小**——不必为每一类内容都设计一种增量。
将来多出新的内容块，它照样能走「开口 + 整个交出来」这条路，
**而流式的词表一个字都不用改**。

> **这条判据已经被检验过一次。**语音是后来才加进来的，
> 而判据自己就把它分到了对的那一边——**不是先有四样，再编一条规矩把它们圈起来**。

**语音另有一串文本没有的麻烦**，见 §5.9。

#### 到达的过程有它自己的语法

```text
开一个块（说明这块怎么填）──→ 往里填（只有四样能填）──→ 封上这个块
                                                            │
                                                    记一次账 ──→ 收尾
```

三条要紧的性质：

- **封口的时候交出的是完整的那一块。**消费的一方**可以**自己把增量拼起来，
  但**不必**——**两边各拼一次，就有了两个可能不一致的答案**。
- **一条流必须有结局。**没有结局，等着的那一方**永远不知道该不该继续等**。
- **账只记一次。**记两次就是两次计费，**而这种错查起来极贵**。

##### 「填」有两种模式，开块的时候说明是哪一种

| 这一块说的是 | 怎么填 | 封口时它是什么 | 像什么 |
|---|---|---|---|
| **一件事** | **追加片段**——新来的接在已有的后面 | 所有片段接起来的那一整块 | 模型正在说的一句话、一行行往外吐的日志 |
| **一个状态** | **整体替换**——每一次填都把这块的内容整个换掉 | **最后那一次填进去的内容** | 进度条、一块汇总的面板 |

**判据与 [§5.4](#54-提醒说的是现在什么样还是刚才发生了什么) 同源**：
**说状态的整体替换，说事的追加。**状态有「当前值」，事只有发生过与没发生过。

**说明给在开块那一下，此后这一块怎么填就定了。**
一条消息里各个块**各说各的**——前面几个块追加片段、最后开一个整体替换的块，是允许的。
所以「**先往外吐日志、最后再给一块汇总面板**」这条路走得通：
前面那些块已经封了，**最后那一块整体替换的是它自己先前填进去的内容，不是前面那些块**。

> **取代发生在一个块里，不跨块。**

**两种模式只管「填」这一步，语法的其余部分不因此改变**——
仍然是开块、填、封口、记账、收尾；封口交出的仍然是完整的那一块；
仍然不存在[半条消息](#半条消息不是消息)。

#### 半条消息不是消息

**不要造一个「半条消息」的类型出来。**

[LangChain 是另一种做法](interviews/2026-09-18-dsh-streaming.md)——那边的半条消息是消息的子类，
两半能加起来。**我们不走那条路**，因为[会话日志是唯一的真相来源](../PF-012-agent-loop-and-run/design.md#52-会话日志是唯一的真相来源)：

> **日志里要是能躺着半条消息，读到它的人分不出「还没说完」与「说到一半被掐了」。**

**没说完的东西只是一个正在长的块，不是一条消息。**
它要么长成一条完整的消息，要么按 §5.6 收场——**没有第三种下场**。

#### 组装出来的，必须与一次性拿到的一模一样

**这是一条可验证的性质，不是一句愿望。**

同一次回复，分十次到达再拼起来，与一次性拿到，
**必须得到完全相同的一条消息**。做不到，
「agent 看到了什么」就取决于当时网络怎么样——**而那是不可复现的**。

### 5.6 流断在半路

**到了我们这儿的，全都记下来。**
**至于给不给模型看，是组装上下文那一步的事**——两件事，分开定。

| 为什么断 | **日志里**留下什么 | **喂给模型的那份**里有什么 |
|---|---|---|
| **用户叫停，已经有内容到了他眼前** | **一条完整的消息，标明它被中断了**——内容是已交付的那部分 | 同左，**但没长完的工具调用被剔掉** |
| **用户叫停，什么都还没出来** | 这次尝试留一笔账 | **没有这条消息**——不伪造一条空的 |
| **出错断的，已经有内容到了用户眼前** | 这次尝试的账里**记下已交付的那部分**——**它不成为一条消息** | **没有这条消息** |
| **出错断的，什么都还没出来** | 这次尝试留一笔账 | **没有这条消息** |
| **写到上限截断的** | 一条正常的消息，**连同没长完的工具调用** | 同左，**没长完的工具调用被剔掉** |

**无论哪一种，都另外补一条[中断提醒](#systemremindermessage)**，见下。

#### 半截的工具调用：记下来，但不给模型看

**一段没收齐的参数，构不成一次能执行的调用。**但它**照样留在日志里**——

> **凡是到了我们这儿的数据，日志都要完整。**

**日志不是「模型该看什么」的裁剪结果，它是「实际发生了什么」的忠实留存。**
半截的调用留着，事后才查得到**它当时打算干什么**；丢掉，那个事实就永远没了。

**而组装上下文的时候，要认得出它构不成一次完整的调用，把它剔掉。**

不剔掉，模型会看到一个自己「发起过」的调用却没有任何结果——
**它要么干等，要么再发一次**。

> **剔除这个动作不改日志，所以它仍然是[纯派生](../PF-012-agent-loop-and-run/design.md#53-改日志的动作与纯派生的动作)的**——
> 同一份日志，每次组装都剔掉同样的东西。

**这与 [§5.5「半条消息不是消息」不矛盾**：那条消息本身是完整的
（它明明白白标着「被中断了」），**只是它里面有一个块没长完**。
**一条完整的消息，装着一个不完整的块**——这两件事在不同的层次上。

#### 中断这件事本身，要让 agent 知道

**光把内容剪对了还不够。**agent 下一轮读到的是一段没头没尾的东西：

- 自己上一句话**看上去只说了一半**；
- 或者更怪：**看上去正要调一个工具，然后就没有了**。

**它会去解释这个反常，而它手上没有正确的解释。**
于是它可能重说一遍、重调一次，或者在推理里给自己编一个理由。

所以**补一条[提醒](#systemremindermessage)告诉它：刚才被用户叫停了**。

> **这正是 `SystemReminderMessage` 该干的事**——用户叫停，
> 对这次 run 来说就是**外面来的一件事**。

**不分情形，只要发生了中断就补。**哪怕什么内容都没留下——
**「用户刚刚叫停过」本身就是 agent 该知道的事实**，它关系到用户还想不想让它继续做那件事。

#### 工具调用的参数，收齐了才算数

参数是一段一段到的，**中间任何时刻它都是一段不完整的文本**。

> **不要试图去解析没收齐的参数。**

一个残缺的 JSON **解析出来的东西比解析失败更危险**——
它可能恰好是合法的，**而少了一半字段**。

**解析只发生一次：收齐之后、动手之前。**

#### 用户看见了的，会话日志里必须有

**这是「会话日志是唯一真相来源」在流式下的样子。**

用户已经看见半句话了，日志里要是没有——**他刷新一下页面，那半句就凭空消失了**，
而他会以为自己看错了。反过来，日志里有而用户没看见，同样是错的。

**「日志里有」不等于「成为一条消息」**，上面那张表的两种断法落在两个地方：

| | 已交付的那部分在哪 | 为什么 |
|---|---|---|
| **用户叫停** | **一条标明被中断的消息** | 那是一次正常的控制动作，回复本身没有错，**它就是这一轮说过的话** |
| **出错断的** | **这次尝试的账里** | 这一次调用是一次[故障](../PF-013-model-profiles-and-invocation/design.md#还有一种没走完它不在这张表里)，**它没有交出一份回复**；已交付的那部分是这次失败的尝试留下的事实，**不冒充一条消息** |

**两种都在日志里**，所以刷新之后照样查得到；**出错断的那一种不进给模型的那一份**，
agent 靠那条[中断提醒](#中断这件事本身要让-agent-知道)知道刚才断了。

### 5.7 一份会话日志，两种组装

```text
                  会话日志
        （到了我们这儿的，全都在）
                      │
          ┌───────────┴───────────┐
       按「给人看」            按「给模型看」
          ↓                       ↓
     组装给人的那一份        组装给 agent 的那一份
```

**两侧是对称的，用的是同一套机制**——都是从同一份日志，
**按[块上的标注](#每个块带两个标注给人看吗给模型看吗)筛一遍**，
只是筛选条件不同。

> **所以不存在一份特殊的「上下文」凌驾于另一份之上。**
> 给人的那份，和给模型的那份，**地位相同，来路相同**。

**这个模型不是想出来的，是被互不相干的需求各自逼出来的：**

| 什么东西 | 给人 | 给模型 | 为什么 |
|---|---|---|---|
| [工具执行中的过程](#58-toolinternalmessage工具说它正在干什么) | **✓** | **✗** | 一个跑五分钟的工具能产出几百个块，**而模型拿它们做不出任何判断** |
| [没长完的工具调用](#半截的工具调用记下来但不给模型看) | ✗ | ✗ | 它构不成一次能执行的调用；**给了模型，它会干等或者再发一次** |

**两条来路，指向同一个机制。**真做[全双工语音](#94-设计缺口实时双工下没听到的不给模型看)时，
「用户没听到的那段语音」会是下一条要来找它的需求。

#### 日志记的是发生了什么，不是模型该看什么

> **凡是到了我们这儿的数据，日志都要完整。**

**绝不允许**为了让模型看着干净，**在记下来的那一刻就先删一道**——
**那样出了问题，永远查不到当时到底发生了什么**，
而那恰恰是[「会话日志是唯一真相来源」](../PF-012-agent-loop-and-run/design.md#52-会话日志是唯一的真相来源)要防的事。

**删减只发生在组装那一步**，而**组装每次都从日志重新算一遍**。

#### 两侧的组装都仍然是纯派生的

同一份日志，**每次组装都筛出同样的东西**——所以它不改日志、不进状态空间，
[PF-012 那条「组装是纯派生」](../PF-012-agent-loop-and-run/design.md#53-改日志的动作与纯派生的动作)
**不因为多了一侧而动摇**。

### 5.8 `ToolInternalMessage`：工具说它正在干什么

**用户看着界面上写着「正在调用某个工具」，然后就没有下文了。**
它是卡住了，还是在正常地跑一件慢活？**现在分不出来。**

`ToolInternalMessage` 就是补这个：**让工具把自己执行中的情况说出来。**

#### 工具帧跟 `ToolMessage` 是两条轨

| | `ToolMessage` | `ToolInternalMessage` |
|---|---|---|
| 说什么 | 一次调用的**结论** | 一次调用**进行中**的情况 |
| 一次调用有几条 | **一条** | **一条，块可以很多** |
| 给谁看 | **模型**（也给人看） | **人** |
| 进不进喂给模型的上下文 | **进** | **不进**（§5.7） |
| 在会话日志里活多久 | **一样长**——日志只增不改 | **一样长**。它不出现在模型那一份里，是[组装](#57-一份会话日志两种组装)筛的结果，**不是它活得短** |

> **消息在会话日志里没有寿命之分。**「给谁看」是组装那一步的事，两件事不要混。

#### 执行帧就是这条消息的到达增量

**一次工具执行对应一条 `ToolInternalMessage`**，内容是一串块——
**正如一次模型调用对应一条 `AssistantMessage`**。

> **工具往外发的那些[帧](../PF-006-tools-and-skills/design.md#发帧)，就是这条消息的到达增量。**

它们走的是 [§5.5 那套到达语法](#到达的过程有它自己的语法)，**不是另一份协议**：
开一个块（说明这块怎么填）、往里填、封上、记账、收尾。

**同形换来三件事，一件都不必另外规定：**

| | 因为 |
|---|---|
| **封口交出的是完整的那一块**，看的人不必自己拼 | [到达语法本来就这么定](#到达的过程有它自己的语法) |
| **日志里留的是收尾之后那条完整的消息**，到达的过程不留 | [§9.2](#92-流式不留到达的过程)，与模型的回复同一条规矩 |
| **执行中途被中断，已经交付的那些块留着** | [§6.9](#69-用户看见了的会话日志里必须有)一视同仁——用户看见了的，日志里必须有 |

**把帧另立成一份协议，上面三条就要在那份协议里再定一遍**，
**而两份定得不一样的时候，没有人知道该信哪一份**。

**「不进模型上下文」这条不是我们想出来的。**
[legacy 那边独立到达了同一个结论，而且写了四处](interviews/2026-09-18-legacy-tool-frames.md)，
理由说得比我们更直白：**结果的读者是 agent，进度的读者是人**。

#### 大部分工具不发这个，而那是正常形态

**发不发，是工具作者的选择**；不发的工具**照常工作**，界面上照常显示它在跑。

> **一支工具队伍里，绝大多数工具没有「内部情况」值得说。**

**系统不必预先知道哪个工具会发帧。**
[PF-006 那边没有这么一项声明](../PF-006-tools-and-skills/design.md#帧长什么样由一份协议约定不由工具定义声明)——
**没收到就是没有**，仅此而已。

#### 两种增量语义，每一块自己说

**用的是 [§5.4 那条判据](#54-提醒说的是现在什么样还是刚才发生了什么)——说状态还是说事，
而在这里它落在[到达语法的那两种填法](#填有两种模式开块的时候说明是哪一种)上：**

| 这一块说的是 | 怎么填 | 像什么 |
|---|---|---|
| **现在到哪儿了** | **整体替换**——同一块被新的内容整个换掉 | 进度条 |
| **刚做完一件事** | **追加片段**——已经填进去的照样留着 | 日志 |

**但这一次，用判据的人不同。**

> **提醒是系统产生的，所以系统判得出它说的是状态还是事。**
> **帧是工具产生的，判断发生在工具作者写代码的时候——而且是逐块判，不是一次性表态。**

**所以说明给在开块那一下，系统照它说的办。**
系统**不去查工具定义**，也没有什么「声明」可以与行为对不上——
[这条由 PF-006 定](../PF-006-tools-and-skills/design.md#帧长什么样由一份协议约定不由工具定义声明)：

> **收到什么就按什么办。**

**这比「一次性声明自己是日志型还是进度型」更松，而松出来的那点空间是有用的**：
一个工具**可以先往外吐日志，最后再给一块汇总的面板**——
**前面那些块追加片段，最后开一个整体替换的块**。一次性声明会把这条路堵死，
**而那个限制换不来任何东西**。

#### 帧多了要节流，规则就是 §6.16 那一条

一个工具可以每秒产出上千个增量。**必须有节制**，否则它能把整条会话淹掉。

**节流的规则不另立**：合并相邻的增量可以，**默默丢弃不行**；
砍了多少、为什么砍，都要看得出来——[§6.16](#616-砍了要说不许默默丢) 那一条，
**对模型的回复与对工具的帧是同一条**。

#### 发帧不能把工具本身搞失败

**工具不会因为「说不出话」而执行失败。**发不出去就发不出去，
**这次调用该怎么跑还怎么跑**——它本来就是额外的好处，不是执行的一部分。

### 5.9 语音：生成了不等于听到了

**文本流里，「生成了」约等于「用户看到了」**——字一出来就在屏幕上。

> **语音不是。模型可能已经生成完十秒，而用户才听到第三秒。**

中间隔着一整个播放缓冲，**而这个落差在文本世界里根本不存在**。

#### 本版的语音是普通的输入与输出，不是全双工

**语音块在本版就是一种普通的块**：用户说的话进来，是一条带语音块的消息；
模型说的话出去，也是一条带语音块的消息。**它和文本一样按 §5.5 一段一段到、按 §5.6 收场**，
按[块上的标注](#每个块带两个标注给人看吗给模型看吗)进两侧的组装——**不为播放进度另立规则**。

**「生成了不等于听到了」这个落差仍然存在**，本版只是**不拿它去改日志与组装**：
说出去多少、用户听到多少，本版**不区分**。

> **把「用户没听到的，不给模型看」做成规则，是实时全双工（打电话）才有的要求**——
> 在那里，模型以为自己说过的话用户压根没听见，接下来它会基于一个从未发生的事实往下推。
> **产品负责人已明确：这一条本版不作为架构内核的约束。**它记为一个设计缺口，见 [§9.4](#94-设计缺口实时双工下没听到的不给模型看)。

#### 打断语音，不等于取消工作

用户插话打断，停掉的是**说话**。**它没说要取消那件正在办的事。**

这与 [PF-006「中断不是失败」](../PF-006-tools-and-skills/design.md#67-用户可以中断而中断不是失败)
是同一条精神，但在语音下更容易搞混——**因为打断的动作是无意识的、随口的**。

#### 双工会动摇「消息是一个接一个」这个假设，**本版不解决**

打电话是**两边可以同时说**的。而本 topic 到这里为止，
**整个模型都建立在「消息排成一串」上**。

真做双工，至少这几条会塌：

| 会塌的假设 | 双工下的实情 |
|---|---|
| 消息排成一串，前后分明 | **两边的话在时间上重叠**，只有先后没有前后 |
| 「一轮」是个实在的东西 | **一轮成了显示上的分组**，而且随时可能重新分 |
| 没消息 = 没人说话 | **听不到不等于没说**——不能从「没收到」推出「静默」 |
| **一条消息有稳定的身份** | **身份不能从会变的文本或时间戳算出来**——它得另有来路 |

**最后一行是[重新调研 GPT-Live 之后补上的](interviews/2026-09-18-openai-gpt-live.md)**，
而且它比前三行更硬：前三行说的是「结构变了」，这一行说的是**「认不出这是同一条」**。

#### 语音层是第二个持有上下文的参与者，而那份上下文不是我们的日志

**这一条也是重新调研之后才看清的**，它比「多一种块」要紧得多：

> 真做双工时，对面那个语音层**自己也存着一份对话历史**，
> **而那份历史会被它自己压缩、会掉东西**。

它自己是这么说的：**「那不是你的账，重要的事实和任务状态放在你的应用里。」**

**所以规矩很清楚，而且与本 topic 已有的模型一致：**

> **语音层的历史是它的工作副本，真相在我们的日志里。**
> 它要什么，我们从日志里[组装一份给它](#57-一份会话日志两种组装)。

**这等于多出第三个组装的去处**（给人的、给 agent 的、**给语音层的**），
而且那一份有很硬的额度限制。**怎么组装归 PF-010，本 topic 只记下这件事会发生。**

**本版不解决这些。**产品负责人说的是「**未来**支持实时双工语音对话」——

> **现在把双工的机制预埋进来，是在为一个还没成形的需求造框架。**

**本版做的是：把语音放进能增量的那一类、当普通的输入与输出，并且把上面这几条记在这里**，
好让真要做双工的时候，**知道该回来推翻哪几条，而不是发现整个模型都不对**。

## 六、产品规则

### 6.1 一条消息是谁说的，永远查得到，且不靠解析内容

**七种就是七种。**「这条是人说的还是系统插的」这个问题，
**看它是哪一种就答得出来**，不必去读内容、不必找标记。

**内容里的标记只服务于 agent**（因为它到了对面只剩四种），
**不服务于我们自己的日志**——日志里那个答案必须是确定的。

### 6.2 我们自己那两种，每一家都要有落点，不许落空也不许丢

接一家新的模型供应商，**必须为 `SystemReminderMessage` 与 `CompactionMessage`
各指定一个落点**，而且那个落点得是那一家真的支持的类型。

**两种各自决定，不必落到同一处。**

**不许丢掉。**丢了，agent 在那一家上就永远看不见系统在说什么——
**同一个 agent 换一家模型，行为就变了**，而没人查得出为什么。

**`ToolInternalMessage` 不在此列**——它根本不进请求（§4）。

### 6.3 提醒的标识由系统加，产生提醒的那一处交的是消息

**产生提醒的那一处，交出来的是一条消息，不是一段带标签的文本。**

不守这条，**任何能左右那段文本的人都能冒充系统说话**——
工具的返回、外部来的内容、用户自己粘进来的东西，都可以。
**而 agent 没有任何办法分辨。**

### 6.4 说状态的写清变化，说事的写清发生；消息一律追加

判据见 §5.4：**这条提醒讲的是一个状态，还是一件事。**

- **说状态的，必须写清「从什么变成了什么」**——前值与现值都在这一条里。
- **说事的，写清发生了什么**。

**两类消息在日志里都追加，谁也不取代谁，组装时也不筛掉旧的那几条。**
**agent 看到的是整条变化链，当前值从链尾读出来。**

**块内部另有一种「整体替换」**：一条正在到达的消息，
**说状态的那种块整体替换，说事的块追加片段**
（[§5.5](#填有两种模式开块的时候说明是哪一种)、[§6.15](#615-每一块自己说它是追加片段还是整体替换系统照办)）。
**那是一条消息的到达过程，不是日志**——它换掉的只是这个块自己先前填进去的内容。

### 6.5 来源是一个属性，不是另一种消息

外面是谁捎来的信息——另一个会话的 agent、自己的 subagent、一个后台执行、环境本身——
**记在一个来源属性里**（§4）。

**不为每一类来源另立一种消息。**它们对这次 run 来说是同一件事，
**agent 的处理方式也没有因此不同**。

**而 agent 主要靠正文读懂这是什么事**——正文本来就该说得清楚。
来源属性是**额外的一份确凿信息**：给排查的人用，
也可以给 agent 用（比如它要回话给捎信的那一方）。

### 6.6 内容是块，不在进日志时压成文本

图就是图，工具调用的参数就是结构化的参数。
**压成文本，就得靠解析捞回来——而解析会错，而且错得静默。**

> **模型收不下某个块的模态时，它读的也不是被压扁的原件**：
> [转换件](../PF-013-model-profiles-and-invocation/design.md#转换件)在**落盘之前**给那个块配上派生表示与一段 transcript，
> **挂在原块上，原块一个字不动**；组装时按模型收得下什么取用（[PF-013](../PF-013-model-profiles-and-invocation/README.md) rev 5）。
> **所以出门那一刻不再有「替收不下的模型压一下」这回事**，进日志那一刻也没有。

这与 [PF-006 的附件](../PF-006-tools-and-skills/design.md#工具的产出)是同一条思路：
**日志里留的是引用，要用的时候才去取**。

### 6.7 分次到达的东西，不进消息类型清单

**七种就是七种**（§6.1）。一条正在长的块**不是一条消息**，
**不能被当成消息存进日志、也不能被当成消息喂给 agent**。

它要么长成一条完整的消息，要么按 §5.6 收场。

### 6.8 组装的结果与一次性拿到的必须相同

**这是可验证的**：同一次回复，分十次到达再拼，与一次性拿到，
**得到的消息必须完全相同**。

不成立，则「agent 看到了什么」取决于当时网络怎么样——**而那不可复现**。

### 6.9 用户看见了的，会话日志里必须有

流断在半路而用户已经看见内容了，**那部分必须在日志里**：

- **用户叫停的**：落成**一条标明被中断的消息**；
- **出错断的**：记在**这次尝试的账里**，**不成为一条消息**（[§5.6](#用户看见了的会话日志里必须有)）。

**日志里没有，用户刷新一下页面那半句就凭空消失了**——而他会以为自己看错了。

### 6.10 没收齐的工具调用参数，不解析、不执行

**一个残缺的参数解析出来的东西，比解析失败更危险**——
它可能恰好是合法的，**而少了一半字段**。

**解析只发生一次：收齐之后、动手之前。**

### 6.11 每个块都带「给人看 / 给模型看」两个标注

**两个标注互不决定**，四种组合都成立（§4）。

**标注在块上，不在消息上**——同一条消息里，各个块的去向可能不同。

**标注只说取不取，不说长什么样。**怎么呈现归组装那一侧各自决定。

### 6.12 日志完整，删减只发生在组装那一步

**到了我们这儿的，全都记下来。**
**绝不允许**为了让模型看着干净，**在记下来的时候就先删一道**——
出了问题就永远查不到当时到底发生了什么。

### 6.13 只要发生了中断，就补一条提醒

**不分情形**，哪怕什么内容都没留下。

不补，agent 读到一段没头没尾的东西**会自己编一个解释**——
然后重说一遍、重调一次。

### 6.14 工具帧不进模型的上下文

`ToolInternalMessage` **只进用户那一侧**。

**这不是「默认不进、可以配置」，是不进。**开了这个口子，
一个话多的工具就能把整份上下文吃光，**而它说的每一条对模型都没有用**。

### 6.15 每一块自己说它是追加片段还是整体替换，系统照办

**说明给在开块那一下**，此后这一块怎么填就定了（§5.5）。

**系统不查工具定义**，也不预先知道哪个工具会发帧——
[这条由 PF-006 定](../PF-006-tools-and-skills/design.md#帧长什么样由一份协议约定不由工具定义声明)。

**因此不存在「声明与行为不符」这种错**：压根没有声明。
**同一次执行里前面的块追加片段、最后一块整体替换，是允许的**。

### 6.16 砍了要说，不许默默丢

节流可以**合并相邻的增量**，但**不许默默丢弃**。
砍了多少、为什么砍，**都要能看出来**。

> **一块被悄悄截短的面板，和一块完整的面板，对看的人来说长得一模一样。**

### 6.17 发帧发不出去，不影响这次工具执行

**工具不会因为「说不出话」而失败。**帧是额外的好处，不是执行的一部分。

反过来设计，**一个本来能跑完的工具会因为面板拥堵而失败**。

## 七、取舍

| 选择 | 取的 | 舍的 |
|---|---|---|
| **`SystemReminderMessage` 独立成一种**，而不是带标记的用户消息 | 日志里分得开；每家用最合适的落点；adapter 认得出 | 它在任何一家都不存在，**每接一家都得多定一条映射** |
| **映射推迟到 adapter**，模型层不定死 | 换供应商不改变语义；openai 能用上 `DeveloperMessage` | 同一条提醒在不同家**长相确实不同**，排查跨供应商问题时要多想一层 |
| **标识由系统加**，不让生产者自己包 | 伪造不了——**这是安全性质，不是洁癖** | 生产者少了一点自由；想自定义样式得走别的路 |
| **消息一律追加**，由说状态的提醒自己交代「从什么变成了什么」，而不是让新的取代旧的 | agent 拿到的是**整条因果链**——之前是什么、变成了什么、又变成了什么，一步都不少；日志与组装都不必多一条「同一处只取最新」的规则 | 每条状态类提醒都要多写一份前值，**写漏了链就断在那一条上**；而这条链会一直占着上下文，**直到被压缩收走** |
| **内容是块，不是文本** | 图、思考、结构化参数都留得住原样 | 比一根字符串复杂；每接一家都要处理「这家支持哪些块」 |
| **`CompactionMessage` 单立一种**，而不是塞进 `SystemReminderMessage` | 认摘要靠类型不靠猜内容；「顶替了哪一段」这层关系有地方挂；**将来长复杂了不必回头拆** | **一处有意的冗余**——理论上确实塞得进去。多一种类型，每个 adapter 多一条映射要定 |
| **提醒是日志的一部分**，不是临时的 | 恢复读得回来，压缩看得见它 | 它会一直占着上下文，**直到被压缩收走** |
| **流式另立一套词表**，与七种消息正交 | 消息类型清单不被流式撑大；将来加内容块**不必动流式那一套** | 两套词表都要维护，**而且两者的对应关系要说清楚** |
| **只给「能一点点长」的三样做增量**，其余整个交出来 | 词表极小；**半张图这种没意义的东西根本表达不出来** | 插件新加的内容块**拿不到增量能力**——只能等它整个好了再给 |
| **不造「半条消息」这个类型** | 日志里不会躺着说不清楚的东西 | 与 [LangChain 那种做法](interviews/2026-09-18-dsh-streaming.md)不同，**从那边迁过来的人要改习惯** |
| **中断时留下已交付的部分**，而不是当这次没发生 | 用户看见的与日志里的对得上 | 日志里会有「没说完」的消息，**下游每一处都得认得这个标记** |
| **执行帧与模型响应流同形**——[帧就是 `ToolInternalMessage` 的到达增量](#执行帧就是这条消息的到达增量)，走同一套到达语法，不另立一份帧协议 | 工具这一路与模型那一路只有**一套契约**：一次执行一条消息、封口交完整的块、日志只留最终那一条、节流照同一条规矩 | **「整体替换」这个填法模型那边用不上**——模型的回复只会追加片段，**这一模式是为工具的面板留的**，看这套语法的人得知道有一半自己遇不上 |

| **决策卡片的答复落成哪一种** | **分两种**：[工具等待态](../PF-006-tools-and-skills/design.md#等待态)发出的 → `ToolMessage`；**系统发起的** → `SystemReminderMessage`。**判据就是 [PF-008 的两个维度](../PF-008-human-in-the-loop/design.md#等待态的两个维度)** |

> 后两行看着像「消息形状」因而像是本 topic 的活，**但它们问的都是「组装成消息那一步该怎么做」**，
> 而那一步归 PF-010。本 topic 定的是**有哪几种消息**，不是**某个具体产物落成哪一种**。

### 9.2 流式：不留到达的过程

**「日志里要不要把它当时是怎么一点点到的也留住」——不留。**
判据本身就答了：**不会有人问「那一刻用户屏幕上是什么」。**

**所以[会话日志](../PF-012-agent-loop-and-run/design.md#会话日志)里留的是：**

| 留 | 不留 |
|---|---|
| **最终那条消息** | **每一个增量是怎么到的** |
| **中断时已经交付出去的那一部分**（§6.9） | 它们各自什么时候到、分了几次到 |

**这不动摇 §6.9。**那一条要求的是「用户看见了的**内容**，日志里必须有」——
**它从来不要求留住那段内容是怎么一点一点出现的**。

**工具帧同样不留到达的过程**：帧是 `ToolInternalMessage` 的到达增量（§5.8），
所以留的是收尾之后那条完整的消息——**封口之后的那些块**；
一个整体替换的块，留的就是**最后那一次填进去的内容**。
**执行中途被中断，已经交付出去的那些块照样留着**（§6.9）。

> 参考：[DSH 选的是相反的一边](interviews/2026-09-18-dsh-streaming.md)，
> 而且那边**明确拒绝过**「只存装配后的消息」这个提案。
> **两边取舍不同，因为要支持的能力不同**——他们要回放，我们不要。

**下游要复核**：任何为了「能回放当时的样子」而把每个增量单独存下来的实现。
**那份数据没有消费者。**

### 9.4 设计缺口：实时双工下，没听到的不给模型看

**这不是等着拍板的事，是产品负责人明确留到以后的一块。**

真做实时全双工语音（打电话）时，**模型生成了多少与用户听到了多少会分开**——
而模型以为自己说过、用户却没听见的那一段，**不能让它当成说过**，否则它会基于一个从未发生的事实往下推。
[OpenAI 早一套接口为此设过一个毫秒级的对齐动作，GPT-Live 里没有它](interviews/2026-09-18-openai-gpt-live.md)，
那边把这个目标交给了客户端。

**本版不做，而且不作为架构内核的约束**（产品负责人 2026-09-23）。
回来做的时候，至少要答三件事：

| 要答的 | 为什么 |
|---|---|
| **播放进度怎么回到日志里** | 进度是落盘**之后**才知道的，而[块上的标注在落盘那一刻就写定](../PF-010-context-management-and-assembly/README.md) |
| **没听到的那一段是一个块的一部分，还是另一个块** | 标注在块上，一个块只能整个取或整个不取 |
| **[§5.9 记下的那几条会塌的假设](#双工会动摇消息是一个接一个这个假设本版不解决)怎么重立** | 消息排成一串、「一轮」是实在的、没消息等于没人说话、消息有稳定的身份 |
