## rev 4 · 消息层面没有「取代」，agent 感知整条因果链 — 2026-09-22

**产品负责人直接裁决**：
**只要是消息，在会话日志上就是 append only**；
**之前怎么样、然后变成了什么、然后又变成了什么，因果链不能断，agent 全要感知。**

| 改了什么 | 从什么改成什么 |
|---|---|
| **状态类提醒的命运** | §5.4 原写「说状态的**取代**——只留最新的那份」，现在是**追加**。**两类提醒在日志里一律追加，组装时也不按「同一处只取最新」筛** |
| **判据用来干什么** | 判据本身不变（讲状态还是讲事），但**用途从「决定命运」改成「决定这条提醒怎么写」**：说状态的**必须写清「从什么变成了什么」**，说事的写清发生了什么 |
| **§5.4 那段论证** | 原来用「做成追加会躺着三份互相矛盾的说法」论证取代；现在写成**链自己说清变化、agent 从链尾读当前值，链断了才是问题**——**几份各说各话的来源是每条都没交代前值，不是旧的那几条还在** |
| **§6.4 的标题与正文** | 由「说状态的取代，说事的追加」改为[「说状态的写清变化，说事的写清发生；消息一律追加」](design.md#64-说状态的写清变化说事的写清发生消息一律追加)。**锚点随之变化** |
| **「取代」这个词的落点** | 收敛到**一处**：[一个块内部的整体替换](design.md#填有两种模式开块的时候说明是哪一种)——**那是一条消息的到达过程，与日志无关**。§5.8 不再写「§5.4 那条判据的第二次现身」，§6.4 不再写「这一条落在消息之间」 |
| **§7 取舍** | 「状态取代、事件追加」那一行改写成**「消息一律追加，由说状态的提醒自己交代前值」**，代价换成「每条都要多写一份前值、链会一直占着上下文」 |
| **acceptance** | 「注入的上下文变了三次 → 只剩最新那一份」改为**三条都在、每条说得出前值与现值、当前值读链尾**；「绝不能发生」里两条对调的取代/追加改成**不交代前值、日志里被取代、组装时被筛掉**三条 |

**「填」有两种模式（§5.5）一个字没改**——它本来就在块内部，与消息层无关；
[§5.5 那句「判据与 §5.4 同源」核过仍成立](design.md#填有两种模式开块的时候说明是哪一种)。

**下游要复核**：
任何**在组装时按「同一处只取最新」筛提醒**的实现；
任何**让新提醒覆盖同一处旧提醒**的实现；
任何**只报当前值、不交代前值**的状态类提醒生产者——现在它必须写出「从什么变成了什么」。

**词表与对象**：本次没有新增或改写词条的定义。
[UL-message](../../ubiquitous_language/terms/record-and-context.md#ul-message--消息--message)、
[UL-content-block](../../ubiquitous_language/terms/record-and-context.md#ul-content-block--内容块--content-block)、
[UL-block-annotation](../../ubiquitous_language/terms/record-and-context.md#ul-block-annotation--块标注--block-annotation)、
[UL-incremental-arrival](../../ubiquitous_language/terms/record-and-context.md#ul-incremental-arrival--增量到达--incremental-arrival)
四条逐条回读后出处 rev 改到 4——**它们都没有提过消息层的取代**。

**邻居**：[PF-012 §5.11](../PF-012-agent-loop-and-run/design.md#511-外面进来的事怎么到-agent-眼前) 与
[PF-010 §5.5](../PF-010-context-management-and-assembly/design.md#55-几样东西各自落成哪一种消息)
是对本条规则的转述，**已就地对齐，两边都不升 rev**（[PF-012](../PF-012-agent-loop-and-run/changelog.md) 与 [PF-010](../PF-010-context-management-and-assembly/changelog.md) 各记一次校准）；

## rev 3 · 执行帧与模型响应流同形 — 2026-09-22

**产品负责人直接裁决 [C-21](../../ubiquitous_language/conflicts.md#现有冲突)**：
**工具帧与模型响应流必须同形，统一契约才定得下来。**

| 改了什么 | 从什么改成什么 |
|---|---|
| **一次工具执行落成几条消息** | §5.8 的表原写「一次调用**可能很多条**」，现在是「**一条，块可以很多**」——与「一次模型调用对应一条 `AssistantMessage`」同形 |
| **执行帧是什么** | 新增 [§5.8「执行帧就是这条消息的到达增量」](design.md#执行帧就是这条消息的到达增量)：帧走 [§5.5 的到达语法](design.md#到达的过程有它自己的语法)，**不是另一份协议、不是独立对象、也不是载荷** |
| **消息的寿命** | §5.8 的表原写工具帧「活多久：**可以更短**」，现在写**一样长**——日志只增不改，「不给模型看」是[组装](design.md#57-一份会话日志两种组装)的事 |
| **增量语义挂在哪** | 原本「**每一帧**自己说」是取代还是追加；现在挂在块上：**开块的时候说明这块怎么填**——追加片段，还是整体替换。§5.5 新增[「填」的两种模式](design.md#填有两种模式开块的时候说明是哪一种)，§5.8 与 [§6.15](design.md#615-每一块自己说它是追加片段还是整体替换系统照办) 随之改口 |
| **帧的上限** | §5.8 原来自己写一遍节流纪律，现在**引用 [§6.16](design.md#616-砍了要说不许默默丢)**，不重述 |
| **§6.4** | 补一句：同一条判据在块上还用一次，**落点不同**——一条落在消息之间，一条落在一个块的内部 |
| **§7 取舍** | 新增一行：选了「同一套到达语法」，代价是**「整体替换」这个填法模型那边用不上** |
| **§9.2** | 补明**工具帧同样不留到达过程**：留的是收尾后那条完整的消息（封口后的块），中断时已交付的块照样留 |
| **§4** | `ToolInternalMessage` 那一条写明「一次工具执行对应一条」；块清单补一句**工具过程说的话用的也是这些块，不多出一类** |

**`UL-content-block` 不动**——帧的载荷就是普通内容块，**没有新增块的种类**。

**下游要复核**：
任何**把一次工具执行落成一串消息**的实现；任何**为帧另立一份到达协议**的实现；
任何**按「每一帧自带增量语义」**读取的实现——说明现在给在**开块**那一下。

**词表与对象**：[UL-execution-frame](../../ubiquitous_language/terms/execution-and-outcome.md#ul-execution-frame--执行帧--execution-frame)
形态由「未定」定为**过程**，定义改写为「一条 `ToolInternalMessage` 的到达增量」；
[UL-frame-emission](../../ubiquitous_language/terms/execution-and-outcome.md#ul-frame-emission--发帧--frame-emission) 的定义随之对齐；
[领域对象的待裁](../../domain_objects/pending.md)里「执行帧」一项**闭合删除**。

**PF-006 不改本次**：那边 §4「帧长什么样，由一份协议约定，不由工具定义声明」
应改为**指向本 topic 的到达语法**，**回改归该 topic 的 owner**。

## D-2 已裁决，本 topic 再无未决项 — 2026-09-18

**唯一一项待裁决闭合了：记录里不留「到达的过程」。**

产品负责人**直接答掉了 PM 给的那条判据**：

> **不会有人问「那一刻用户屏幕上是什么」。**

**于是[会话日志](../PF-012-agent-loop-and-run/design.md#会话日志)里留的是最终那条消息**，
外加[中断时已经交付出去的那部分](design.md#69-用户看见了的会话日志里必须有)；
**每个增量是怎么到的、分几次到的，不留**。

**§6.9 不受影响**——那条要求的是「用户看见了的**内容**记录里必须有」，
**从来不要求留住它是怎么一点点出现的**。

**下游要复核**：任何为了「能回放当时的样子」而单独存下每个增量的实现——
**那份数据没有消费者**。

> [DSH 选的是相反的一边](interviews/2026-09-18-dsh-streaming.md)，
> 而且明确拒绝过「只存装配后的消息」。**两边取舍不同，因为要支持的能力不同。**

### 顺带：「记录」这个概念补齐了定义

**PM 此前一直在用「记录」这个词，却从没定义过它**——
[PF-012](../PF-012-agent-loop-and-run/design.md#会话日志) 只从「方程的定义域」这一个视角列过三部分，
而本 topic §5.7 用的是另一个视角。**同名不同义的风险就在那儿摆着。**

产品负责人认可了补上的定义：

> **它本质上就是 append only 的 session log，
> message 只是它的一部分，更多的是各种 events。**

并划了范围：**知道 session log 与 message 的关系就行，
不需要关心那些 events 究竟是什么。**

**本 topic 的 §4「消息」据此点明了两层关系**：消息只是日志的一部分；
日志也不等于「拿去用的那一份」。**定义本身归 PF-012。**

## 两处正文修订 — 2026-09-18

### 一、工具帧的增量语义：不再由工具作者声明

rev 1 写的是「**两种增量语义由工具作者声明，声明与行为不符要明确拒绝**」——
那是照着 [legacy 的类级声明](interviews/2026-09-18-legacy-tool-frames.md)写的。**产品负责人否掉了：**

> **帧不需要在定义里面声明，而是通过数据结构的协议来约定就可以**
> （系统对帧的解析是统一的，**它不根据工具定义判断要不要解析帧**，
> 而是根据它实际收没收到、收到的是什么来决定解析策略）。

**改成：每一帧自己说它是取代还是追加，系统照办。**
于是「声明与行为不符」这种错**压根不存在**——没有声明。
**同一次执行里前面追加、最后取代，现在是允许的**，
而那正是一个「先吐日志、最后给汇总面板」的工具需要的。

**动的地方**：§5.8 两处子节、§6.15 整条重写。
上游 [PF-006 rev 7](../PF-006-tools-and-skills/changelog.md) 同步立了发帧原语，
并明确**帧不在工具定义的四项可选声明里**。

**下游要复核**：任何按「工具声明自己是日志型还是进度型」实施的东西。

### 二、语音那一节的信源被更正：Realtime → GPT-Live

产品负责人主动更正：

> **我们真正未来要兼容支持的机制是 GPT-Live 的**（gpt realtime 那个信源可能有误）。

**重新调研见 [GPT-Live 笔记](interviews/2026-09-18-openai-gpt-live.md)。
结论没变，但依据换了，而且多看见了两条：**

| | |
|---|---|
| **改了依据的一条** | 「用户没听到的，不能让模型以为它说过了」——原先靠 Realtime 那个毫秒级对齐动作，**而 GPT-Live 里没有它**。现在靠的是**记录是我们自己的**：说出去多少、听到多少，本来就可以分开记 |
| **新看见的第一条** | **语音层是第二个持有上下文的参与者**，而那份历史**会被它自己压缩**。官方原话：**「那不是你的账」**。于是将来会有**第三份组装**（给语音层的），而这反过来印证了[「一份会话日志，多种组装」](design.md#57-一份会话日志两种组装) |
| **新看见的第二条** | **一条消息的身份不能从会变的文本或时间戳算出来**——比 rev 1 记的那三条「双工会塌的假设」更硬 |

**最要紧的一句认识**：GPT-Live **不是「Realtime 的全双工版」**，
它是**把语音层和推理层拆成了两个模型**——而我们要兼容的那种模式里，
**我们自己的 agent 就是它的后端**。

**本版仍然不做双工**，这一条没变。

## rev 1 · 草稿 — 2026-09-18

**首版，且明确是草稿。**只做了**消息类型**这一块，
未决项见 [design.md §9](design.md#九未决项)。

### 这一版立住了什么

| 方面 | 结论 |
|---|---|
| 有哪几种消息 | **五种**，按**谁在说话**分：系统（开头）/ 人 / 模型 / 工具 / **系统（中途）** |
| 最后一种 | **`SystemReminderMessage`**，我们加的，**任何一家供应商都没有** |
| 它凭什么独立 | 记录里分得开 · 每家落点不同 · **adapter 认的是类型不是字符串** |
| 它怎么出门 | **每一家都必须有落点**，openai 落 `DeveloperMessage`，anthropic 落 `UserMessage` |
| 标识归谁 | **系统**。生产者交的是一条消息，不是一段带标签的文本 |
| 提醒的两种命运 | **说状态的取代，说事的追加** |
| 内容长什么样 | **一串块**，不是一段文本 |

### 三条最硬的性质

> **一、adapter 认的是类型，不是内容里的字符串。**
> 后者谁都写得出来——**包括一个工具的返回**。

> **二、标识由系统在出门前加，所以伪造不了。**
> 这不是洁癖，是安全性质：约定「生产者自己包」，
> 则任何能左右那段文本的人都能冒充系统说话。

> **三、状态有「当前值」，事只有发生过与没发生过。**
> 判错的后果两个方向不一样：状态做成追加，agent 看到三份互相矛盾的说法；
> 事做成取代，**前一个后台任务跑完这件事被后一个覆盖了**。

### 一处要紧的澄清

产品负责人指示「参考 deepseek harness 现在支持的消息类型」。查下来：

> **那边不是一组平行的消息类型**——只有一个 `Message`，三值 role，
> 外加正交的两条轴。`ToolResultMessage` 的 role 其实是 `user`。

本 topic **按「谁在说话」组织成五种，是产品表达上的选择**。
产品定「有哪几种、各自是谁在说话」，**不定它在代码里由几个类型承载**——
语义对得上即可。详见 [调研笔记](interviews/2026-09-18-dsh-message-types.md)。

**另外**：产品负责人说的「openai 是 `DeveloperMessage`」指的是 **OpenAI API 那边的角色**，
不是 DSH 的类型——**这一点没有出入**，记下来只是免得后来者去 DSH 里找它。

### 两家做法相反的一处，我们取了第三条路

| | 提醒的标签归谁 |
|---|---|
| **DSH** | 生产者自己烘进内容 |
| **legacy** | 框架拥有转义 |
| **本 topic** | **它是一种类型，标识由系统在出门前加** |

**两家相反，说明这是个真的设计选择。**第三条路比两者都严：
生产者连「一段文本」都交不出来，**它交的是一条消息**。

### 草稿期内补进来的一整块：流式

**这是产品负责人指出的缺口，不是有意延后**——初稿定义的全是「完整的一条消息」，
**压根没想到响应是一段一段到的**。

| 补了什么 | 落在 |
|---|---|
| **分次到达的东西不是第六种消息**，与五种正交 | §5.5、§6.7 |
| **能一点点长的只有三样**（文本 / 思考 / 工具调用参数），其余整个交出来 | §5.5 |
| **不造「半条消息」这个类型** | §5.5 |
| **组装结果必须与一次性拿到的完全相同**（可验证） | §5.5、§6.8 |
| **流断在半路的四种收场** | §5.6 |
| **用户看见了的，记录里必须有** | §5.6、§6.9 |
| **没收齐的参数不解析、不执行** | §5.6、§6.10 |

> **一、半张图没有意义。**
> 这条决定了流式词表能有多小——将来多出新的内容块走「开口 + 整个交出来」，
> **流式那一套一个字都不用改**。

> **二、被中断的消息里工具调用一个都不留。**
> 中断发生在动手之前，留着一个就得**凭空造一个结果**。
> [DSH](interviews/2026-09-18-dsh-streaming.md)、[PF-012 尾部对账](../PF-012-agent-loop-and-run/design.md#57-一次尝试三条路通向重新算一遍)、
> [PF-006 中断不是失败](../PF-006-tools-and-skills/design.md#67-用户可以中断而中断不是失败)——**三处独立到达同一个结论**。

> **三、残缺的参数解析出来的东西，比解析失败更危险。**
> 它可能**恰好是合法的，而少了一半字段**。

**与 LangChain 的一处有意分歧**：那边半条消息是完整消息的子类、两半能相加；
**我们不走那条路**——记录里能躺着半条消息，读到的人就分不出
「还没说完」与「说到一半被掐了」。

### D-1 已裁决：不新增消息类型

产品负责人定：**`SystemReminderMessage` 的含义就是「一次 run 中接收到了外部的信息」**——
另一个会话的 agent、自己的 subagent、后台执行的回报、环境变化的通知，**都是它**。
**来源做成一个属性字段**，不另立类型。

§4 的定义据此改写（原来写的是「系统在对话中途插进来的一条提醒」，**边界不如这个干净**）。

### 草稿期内补进来的第二批：块标注、工具帧、语音

**三件事，最后收成一个机制。**

#### 中枢：每个块带「给人看 / 给模型看」两个标注

**产品负责人给的形状，比 PM 原来写的准。**PM 写的是「记录 ⊇ 上下文」，
而正确的形状是**两侧对称**：

```text
              记录（全都在）
                   │
        ┌──────────┴──────────┐
   组装给人的那份        组装给 agent 的那份
```

> **不存在一份特殊的「上下文」凌驾于另一份之上。**

**标注挂在块上，不挂在消息上**——一条被中断的回复，
**它的文本块两边都给，而那个没长完的工具调用块两边都不给，这两个块在同一条消息里**。

**三个互不相干的需求指向这同一个机制**：工具帧给人不给模型、
半截的工具调用留记录但不给模型、用户没听到的语音不能让模型以为说过了。

#### 第六种消息：`ToolInternalMessage`

**用户看着界面上写着「正在调用某个工具」，然后就没有下文了。**

它与 `ToolMessage` 是两条轨：一条说**过程**，一条说**结论**。
**所有消息里，它和 `SystemMessage` 是仅有的两个单边的，而且方向正好相反**——
一个只给 agent，一个只给人。

**两种增量语义**（说「到哪儿了」的取代，说「刚做完一件事」的追加）。
这是 [§5.4 那条判据](design.md#54-提醒说的是现在什么样还是刚才发生了什么)的第二次现身，
**只是这一次用判据的人从系统换成了工具作者**——因为产生者不同。

> ⚠️ **rev 1 原先写的是「由工具作者声明，声明与行为不符要拒绝」，那条已被推翻**——
> 改成**每一帧自己说**，见本页上方「两处正文修订」。

> **一块被悄悄截短的面板，和一块完整的面板，对看的人来说长得一模一样。**
> 所以合并相邻增量可以，**默默丢弃不行**。

#### 能增量的内容加了语音

**判据没动，是判据自己把语音分到了对的一边**：半张图没意义，**半段语音有——它能播**。

语音另带一串文本没有的麻烦（§5.9）：**生成完 ≠ 用户听到了**，中间隔着播放缓冲。
所以 §5.6 那条「用户看见了的记录里必须有」要拆成两句，
**后半句是新的：用户没听到的，绝不能让模型以为它说过了**。

**双工（打电话）本版不解决**，但记下了会塌的三条假设，
好让真要做的时候**知道回来推翻哪几条，而不是发现整个模型都不对**。

### 一处被纠正：把「不给模型看」写成了「不记下来」

rev 1 写的是「被中断的消息里工具调用一个都不留」——**直接抄了 DSH 的做法**，
**没有多问一句「记录里该不该留」**。

产品负责人纠正：**留着，因为要保证到达我们这边的数据的记录的完整性**；
**剔除发生在组装那一步**。

> **这个纠正直接催生了 [§5.7](design.md#57-一份会话日志两种组装)。**

**下游要复核**：任何在「记下来」那一刻就做删减的实现。

### 另一处疏漏：块清单里漏了语音

语音加进了[能增量的那张表](design.md#能一点点长出来的与要么没有要么整个有的)，
**却忘了它首先得是一种块**。产品负责人指出。
**两张表之间缺少交叉核对，是这次疏漏的直接原因。**

### 第七种消息：`CompactionMessage`

**产品负责人明说这是一处取舍**：理论上可以做成 `SystemReminderMessage`，
**但单立一种换来两样东西**：

1. 它有一层别的消息都没有的关系——**它顶替了哪一段**；
2. **两者未必同型**，现在合成一种，将来分家时**所有认过它的地方都要改**。

> PM 起初还推了第三条「系统得认出摘要才能不去二次压它」，**被推翻了**——
> 因为**它依赖的那条断言本身就要作废**（见下）。

**语义上它们本来也不是一回事**：提醒说的是**外面**刚来的信息，
概括说的是**里面**已经过去的那一段。

> **系统那三种消息，时间朝向各不相同**：设定朝**前**、提醒朝**当下**、**概括朝后**。

**「说话的有四个，消息却有七种」**——工具说两种，系统说三种。

### 由此，七种在出门时分成三类

| | 哪几种 | 怎么办 |
|---|---|---|
| **各家都有的** | 前四种 | 直接对应 |
| **我们自己的** | `SystemReminderMessage` · `CompactionMessage` | **由 adapter 决定落成那一家的哪一种**，**两种各自决定** |
| **根本不出门的** | `ToolInternalMessage` | **到不了 adapter 那里** |

**第三类值得单独点出来**——不点破，写 adapter 的人会为它找一个落点，
**而那个落点永远不会被用到**。

**下游要复核**：任何要求两种自有类型落到同一处的实现——
**那是在假设一个不存在的共性**。

### 顺带推翻了 PF-012 的一条断言

PM 曾在 PF-012 推出「**摘要只生成一次，不再被二次压缩**」，并写进了那边的正文与取舍表。
**产品负责人推翻了它：**

> **不断言压缩后的消息不能被再次用来压缩**——
> **「已有的摘要 + 新消息 → 新的摘要」是允许的一种策略。**

**PM 错在哪**：「压缩的输入是上一次压缩点到现在」这条裁决**只说明输入区间是增量的**，
**推不出「产物不可再被收走」**。

[PF-012 §5.5 与 §7 已标注推翻](../PF-012-agent-loop-and-run/design.md#55-想这一步交进闭包拿回装得下的一份)。
**摘要能不能被再次收走、怎么收，归 [PF-010](../PF-010-context-management-and-assembly/README.md)（rev 2，已接受）。**

**下游要复核**：任何按「摘要不可二次压缩」实施的东西。

### 一轮通篇检查：八处标题主语不明

产品负责人指出 §5.1 那一段**没主语**——「为什么**它**必须是独立的一种」，
而**加进 `CompactionMessage` 之后，紧邻的上一节正好变成了它**，
读者会以为「它」指的是压缩摘要。

顺着查了一遍全部小节标题，**共八处改成了明确的主语**，并补齐了
因改标题而失效的锚点。另外清掉了若干处「五种 / 六种」的过时数目。

> **这类问题不是写的时候出的，是加东西的时候出的**——
> 原来紧挨着的两节之间插进一节，代词就指错了人。

`flows.md` 与 `acceptance.md`。流式那一块**确实有流程**（断在半路的四种收场），
但它已经在 §5.6 用一张表说清了；**再开一份流程文档只会变成第二份权威**。
验收标准要等本 topic 定稿才有意义，届时一并补。
