## 二、PM 推导

以下结论不是直接裁决的，是从已拍板内容推出来的。推理链写在这里供核对。

| 结论 | 从哪几条推出 | 推理 |
|---|---|---|
| **组合只有一种关系**，贯穿资产之间、资产到 agent、资产到它的设置与权限 | 三句「本质上也是组合关系」 | "本质上也是"这个说法本身就是在否认它们是不同机制。若是三种，就有三套规则、三处覆盖语义、三个出错的地方 |
| **组装 = 组合关系从一个 Agent Definition 展开求值的结果** | 「资产到 agent 的组装本质上也是组合关系」 | 既然组装也是组合，它就不需要独立定义 |
| **Agent Definition 既能组合别人，也能被组合** | 「sub-agent 的定义属于这一类」（PF-001 §4） | 作为 sub-agent 被引用时是被组合方，被实例化时是组合树的根。两种用法不冲突 |
| **求值与组装是两步，不能合并** | PF-001 §6.2 的合成 + 本 topic 的组合 | 求值答"这个租户有什么可用、生效值是多少"，组装答"这个 agent 实际由什么构成"。合并的话，「组织禁用了某个 skill」与「这个 agent 没引用它」会变成同一件事，而前者是管理决定、后者是设计选择 |
| **"把权限设成自动"是收窄，不是放宽** | 「组织没有禁用 → 租户可以设为自动」+ PF-001 的权限收窄语义 | 权限的每一层给的是**允许集合**，最终取交集。租户定成「自动」就是把集合收窄成单元素 `{自动}`——**选择就是收窄到只剩一个**。若权限是布尔开关，这个例子无法在收窄语义下解释；把它读成允许集合，例子与 PF-001 完全自洽 |
| **设置覆盖的是资产的一项设置，不是资产本身** | 「租户可以有自己对这个 agent definition 的默认模型」 | 例子里用的还是**组织共享的那一个** agent definition，只是它的一项设置在租户层被覆盖。这与 PF-001 的「同能力标识覆盖」（整个资产被替换）是两件事，必须分开说 |
| **Hooks、Rules 是 Plugin 的组合成员，不是第六类** | 五类是穷尽的 + 组合关系成立 | 组合关系一旦成立，「成员」与「独立资产」不再互斥。它们没有被列进五类，就按成员处理 |
| **Service、Middleware 不进产品正文** | 五类是穷尽的 | 它们是技术实现概念。产品设计里出现它们，只会让读者以为自己需要理解运行时 |

## 三、待裁决

### 1. 权限的"默认值"怎么落

**为什么 PM 不能自己定**：几种做法都自洽，且产品长相不同。

按 §5.3 的推导，权限每层给一个**允许集合**，最终取交集。
但产品负责人的例子里还有一句「**默认**执行权限是问一下用户」——
"默认"是集合之外的另一件事：**当交集里剩下不止一个值时，用哪个**。

| 做法 | 后果 |
|---|---|
| (a) 只在**出厂默认层**声明一个默认值 | 最简单。但组织想改"本组织的默认是自动"就做不到，只能收窄成单元素，那等于强制而不是默认 |
| (b) 每层都能声明默认值，**按覆盖**合成 | 组织能设本组织的默认，租户能设自己的默认。代价是权限对象里同时有两种合成语义（集合收窄 + 默认值覆盖） |
| (c) 不要"默认值"，交集含多个值时**取最保守的那个** | 不需要额外机制，但要为每类权限定义"保守"的偏序（禁止 < 问一下 < 自动），而且组织无法表达"我们这儿默认放开" |

我倾向 (b)：它能表达真实需要，且两种语义各自作用在不同的东西上（允许集合 vs 默认取值），
并不冲突。但这是**加一个机制**，需要你点头。

### 2. 模型档案在五类里的位置

从你举的例子看，"默认模型"是 **Agent Definition 的一项设置**。
那么「模型档案」这个对象本身——PF-001 说它 official/customized 同形状、
official 原档只读——它是什么？

| 可能 | 后果 |
|---|---|
| (a) 它不是资产，是**设置的取值域中的一个值** | 五类穷尽成立。组织不能"覆盖官方模型档案"，只能选不同的值 |
| (b) 它是资产，但**五类之外**的第六类 | 五类不穷尽，需要你明确 |

我倾向 (a)，因为你把"默认模型"举成了设置的例子。但 PF-001 里"official 原档只读、
可被同能力标识的 customized 替代"这个表述是**资产的语气**，所以我不自己定。

### 3. 知识、经验、报告、附件与文件是不是资产

**这是我在 PF-001 里发现的一处内部不一致，先报告再处置。**

- PF-001 §4 把资产定义为**「约束 agent 由什么组装而成」**；
- 但 PF-001 的资产种类表里列了「知识、经验、报告、附件与文件」，
  而这些**不参与组装**——它们是 agent 工作时**读写的对象**，不是构成 agent 的零件。

按 PF-001 自己的定义，它们不该在那张表里；按本次的"五类"，它们也不在其中。

我倾向把它们移出资产、归一个单独 topic（工作产物与信息的治理）。
但这会**缩小 PF-001 已定稿的范围**，须由产品负责人确认，PM 不能自己删。

### 4. 组合的引用指向什么

**为什么 PM 不能自己定**：两种做法都自洽，且产品长相相反。

[PF-001 §6.3](../PF-001-identity-scope-and-agent-constraints/design.md#63-依赖与组合) 已定：
**依赖指向能力标识，不指向具体某个资产**，因此覆盖发生后依赖自动指向当前生效的那个。

问题是**组合（包含）是否照此办理**：

| 做法 | 后果 |
|---|---|
| (a) 组合也指向**能力标识** | 组织定制了某个 skill，所有含它的 plugin 与 agent **自动用上新的**。一致性好，但 plugin 作者无法保证自己包里的东西不被换掉 |
| (b) 组合指向**具体资产版本** | plugin 的完整性有保障，但组织的定制进不去包内，要逐个改 |
| (c) 默认 (a)，允许 plugin 声明某成员**不可替换** | 两者兼得，代价是多一个机制 |
