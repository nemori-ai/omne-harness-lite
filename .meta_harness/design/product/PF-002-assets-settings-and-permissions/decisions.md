## 二、PM 推导

以下结论不是直接裁决的，是从已拍板内容推出来的。推理链写在这里供核对。

| 结论 | 从哪几条推出 | 推理 |
|---|---|---|
| **组合只有一种关系**，贯穿资产之间、资产到 agent、资产到它的设置与权限 | 三句「本质上也是组合关系」 | "本质上也是"这个说法本身就是在否认它们是不同机制。若是三种，就有三套规则、三处覆盖语义、三个出错的地方 |
| **组装 = 组合关系从一个 Agent Definition 展开求值的结果** | 「资产到 agent 的组装本质上也是组合关系」 | 既然组装也是组合，它就不需要独立定义 |
| **Agent Definition 既能组合别人，也能被组合** | 「sub-agent 的定义属于这一类」（PF-001 §4） | 作为 sub-agent 被引用时是被组合方，被实例化时是组合树的根。两种用法不冲突 |
| **求值与组装是两步，不能合并** | PF-001 §6.2 的合成 + 本 topic 的组合 | 求值答"这个租户有什么资产可用"，组装答"这个 agent 实际由什么构成"。合并的话，「组织禁用了某个 skill」与「这个 agent 没引用它」会变成同一件事，而前者是管理决定、后者是设计选择 |
| **"把权限设成自动"是收窄，不是放宽** | 「组织没有禁用 → 租户可以设为自动」+ PF-001 的权限收窄语义 | 权限的每一层给的是**允许集合**，最终取交集。租户定成「自动」就是把集合收窄成单元素 `{自动}`——**选择就是收窄到只剩一个**。若权限是布尔开关，这个例子无法在收窄语义下解释；把它读成允许集合，例子与 PF-001 完全自洽 |
| **设置覆盖的是资产的一项设置，不是资产本身** | 「租户可以有自己对这个 agent definition 的默认模型」 | 例子里用的还是**组织共享的那一个** agent definition，只是它的一项设置在租户层被覆盖。这与 PF-001 的「同能力标识覆盖」（整个资产被替换）是两件事，必须分开说 |
| **顺序固定为：资产求值 → 组装 → 投影 → 层级计算** | 「设置权限是资产的属性」+「运行时按组装的确定再做层级计算」 | 项的**存在性**由组装决定——没装工具 X，就没有「工具 X 的执行权限」这一项。因此生效值不可能在组装之前算出来。四步的依赖是**单向**的；换序会得出「还不知道有哪些项，却已经算出了它们的值」这种结论 |
| **有两轮层级计算，作用对象不同** | 同上 | 第 1 步作用在**资产**上（同能力标识覆盖，哪个资产生效），第 4 步作用在**属性项**上（某项设置或权限取什么值）。混为一谈会得出「改一项设置等于换一个资产」 |
| **出厂默认层的设置与权限，是 official 资产自带的** | 「设置权限是资产的属性」+ PF-001「official 是最小必需，位于出厂默认层」 | official 必然在每次组装里，它自带的那份属性因此恒存在——这正是出厂默认层的内容。出厂默认层不需要另一套来源 |
| **配值的资格来自持有** | 「持有它的组织和租户各自可以有对应配好的默认设置和权限」 | 「持有它的」是一个限定，不是修辞。组织没有这个工具，就不该能配这个工具的执行权限——否则会出现「为一个自己没有的东西设置边界」这种既无意义又难以解释的状态 |
| **immutable 是一个机制，管三处** | 「强制 = 把字段值限定为不可被覆盖」+ 资产替换的强制 | 每层能做的事只有两件：给一个值、声明它不可再被下层覆盖。不加 immutable 就是**默认**，加了就是**强制**。这一套同时管设置的字段值、权限的取值、资产的替换——**不需要为「强制」另开一套语义** |
| **权限比设置多一档：可收窄到子集** | 权限取值域是枚举的 | `immutable(v)` 等于收窄到单元素集 `{v}`，是收窄的特例。权限的取值域是枚举（问一下/自动/禁止），所以还能表达「只许问一下或禁止」这种子集；设置的取值域通常开放（比如模型名），谈子集没意义，只有锁与不锁两态 |
| **official 永远可被替代，组织锁的是自己那一层** | 「若该资产是 official 则总是可被替换」+ PF-001 的 official 语义 | official 处在最底层，本来就是被替换的对象；它的不可侵犯性体现在**不可被清空**，而不是不可被替换。组织要锁，锁的是组织自己放上去的那个自定义资产 |
| **设置页没有一份独立维护的字段清单** | 「表单随资产自动增删」 | 页面长什么样是「持有了哪些资产」的函数。这正是「组织设置是投影不是对象」在产品上的样子——真去维护一份清单，它就会与资产各自演化，最终对不上 |
| **两块设置不能混在一个列表里** | 「设置页分两块」+ 两种 context 正交 | 混在一起，用户会以为改一个和改另一个是同类操作；而实际上换个组织之后，一个变了另一个没变 |
| **组合的引用指向能力标识，不指向具体资产** | 「组织可把自定义资产设为强制，不允许被替换，比如重要的安全组件」 | **三个选项里只有这一个成立。**若组合指向具体资产：plugin 里包着 official 的那一个，组织的安全组件**根本进不去**，immutable 白标了——漏洞就在 plugin 里。若允许 plugin 声明某成员不可替换：组织的安全组件同样进不去；要么规定组织的 immutable 优先（那 plugin 的声明在这种场合无效），要么让 plugin 赢（那第三方作者凌驾于部署方之上，不该）——**两种情形下它都不该生效，这个机制没有存在价值**。只剩「指向能力标识」 |
| **组合与依赖用同一条规则** | 上一条 + PF-001 §6.3「依赖指向能力标识」 | 两者都指向能力标识，不需要两套规则。**代价要写明**：plugin 作者不能假定自己包里的零件不被替换，他应当面向**能力标识**编写而不是面向某个具体实现。这是「资产可被自定义替换」这个能力的固有代价，不是缺陷 |
| **五类各自的定义与组合能力（整节）** | 产品负责人给的五类名字 + 组合关系 + 来源材料 | **这一整节是 PM 起草的**，等待逐条修正。判据统一为「它和旁边那一类的区别是什么」：Skill 说怎么做 / Tool 是那个动作 / Slash Command 是用户发起的入口 / Plugin 解决分发 / Agent Definition 组装出 agent。说不清区别的就是同名不同义 |
| **只有 Agent Definition 能组合全部五类** | 「资产到 agent 的组装也是组合关系」 | 组装成 agent 是组合图的终点，只有这个终点需要看到全部种类。其余节点各自只组合与自己有实际关系的那几类 |
| **Skill 与 Tool 互相引用** | 来源材料记载存在 tool–skill 依赖 | 两个方向都有实际含义：skill 声明「我这套方法要用到这些动作」，tool 声明「光有我不够用，得配这份指引」。不需要规定单一方向 |
| **Slash Command 不并进 Skill** | 来源材料：两者是可相互绑定的不同定义，不因手动入口统一就合并 | 同一个 skill 可以有多个入口，也可以完全没有入口（只由 agent 自主使用）。绑定关系是**多对多**，合并会丢掉这一层 |
| **组合图不得成环** | 组合要能求值 | Agent Definition 之间可嵌套 sub-agent，但 A 引用 B、B 又引用 A 必须被拒绝，否则组装永远算不完。这不是策略选择，是可终止性的要求 |
| **三种组合暂不做：Skill 套 Skill、Plugin 套 Plugin、Plugin 装 Agent Definition** | 「先做最小的正确模型」 | 三者都**没有已知需要**，且各自会带来负担：Skill 套 Skill 要环检测与「哪层指引优先」；Plugin 套 Plugin 让「内含成员随 plugin 版本治理」变成多层；Plugin 装 Agent 是个合理设想但目前无人要。**加是加法，不用改已有结构**——真实需求出现时再加 |
| **作者是本 topic 新增的一类使用者** | 「资产可被组合与替换」 | PF-001 里只有用的人和管的人。一旦资产可被替换，**打包的人也成了利益相关方**——他的「我包里的零件会不会被换掉」必须有明确答复，不能让他在事故之后才发现 |
| **Hooks、Rules 是 Plugin 的组合成员，不是第六类** | 五类是穷尽的 + 组合关系成立 | 组合关系一旦成立，「成员」与「独立资产」不再互斥。它们没有被列进五类，就按成员处理 |
| **Service、Middleware 不进产品正文** | 五类是穷尽的 | 它们是技术实现概念。产品设计里出现它们，只会让读者以为自己需要理解运行时 |

## 五、已关闭的问题

| 原问题 | 关闭方式 |
|---|---|
| SlashCommand 去哪了 | 产品负责人补充：**它也是资产的一种**。五类成立 |
| 账号级还剩什么 | 产品负责人裁决：账号只做**标识、鉴权、聚合**，不持有任何范围化对象。**作用域由五层减为四层** |
| 界面语言、时区这类偏好放哪 | 产品负责人裁决：它是**另一种 context**，与协作范围 context **正交**，由**账号**承载。不进四层作用域。记在 PF-001 §4「两种 context」 |
| 「禁用」作用在资产层还是权限层 | 产品负责人裁决：**两种含义都要，在产品上区别出来**。移除 = 不再持有；禁用 = 持有但权限收窄为空。判据是成员该不该知道它存在 |
| 组装之前「我的设置」怎么看 | 产品负责人给出设置页的形态：**表单随资产自动增删**，且分「界面偏好」与「资产设置与权限」两块。页面就是投影视图本身，不存在一份独立的字段清单 |
| 权限的「默认值」怎么落 | 产品负责人裁决：**默认与强制是两回事，强制 = immutable**。我此前提的三个选项都想多了——不需要为默认值另设一套覆盖语义，一个 immutable 标记就够，且它同时管资产、设置、权限三处 |
| 组合的引用指向什么 | **PM 自裁**：指向能力标识。三个选项里另两个都与「组织可用 immutable 保障安全组件」矛盾，推理链见第二节 |
| Tool 与来源材料的地位冲突 | 产品负责人确认有意偏离，理由是动态组装能力 |
| Hooks/Rules、Service/Middleware 的去向 | PM 自裁：前者是 Plugin 的组合成员，后者是技术实现概念不进产品正文 |
| 模型档案在五类里的位置 | **由「五类穷尽」+「默认模型是设置」共同闭合**：它不是资产，是某项设置的取值。记在 PF-001 §4 |
| 知识、经验、报告、附件与文件是不是资产 | **由「五类穷尽」闭合**：不是。它们不参与组装，是 agent 读写的对象。PF-001 rev 2 已把它们移出资产种类表，归属见 PF-001 §8 |
