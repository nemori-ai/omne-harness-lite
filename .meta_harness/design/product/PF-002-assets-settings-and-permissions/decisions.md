### 2026-09-21 · 工作区是资产归属的第三级

**产品负责人原话（一）**，先定「权限不从工作区来」：

> 有些 harness 允许再叠加 attatch 的工作区下的配置文件来计算权限，这里我们产品规定直接不回加载和使用，
> 当然这个定调只针对 权限 计算，不针对资产和设置

**原话（二）**，补出这一级本身：

> 关于资产的归属，组织 - 租户 两级之外，其实还有一级（但它是运行时确定的）就是「项目」，
> 也就是一个会话 attatch 的工作区（宿主机文件系统的一个目录），就是这三级的资产模型是同形的
> 且是覆盖（资产提供的能力和设置）是下到上，特殊的点在于「项目」这一级的资产里解析出来的
> 所有放宽了上面两级权限的都不作数。

| # | 裁决 | 落在哪 |
|---|---|---|
| 1 | **资产归属有三级**：组织 · 租户 · **工作区**；**第三级运行时才确定** | [§4 工作区](design.md#工作区) |
| 2 | **三级的资产模型同形** | 同上 |
| 3 | **覆盖方向是下到上**（越具体越优先），**资产提供的能力与设置都照此** | [§5.5](design.md#55-资产替换的层级) |
| 4 | **工作区这一级解析出来的、放宽上面两级权限的，一律不作数** ⚠️ **已被裁决 8 收编**，见下 | [§5.7](design.md#57-工作区那一级不参与权限计算) |
| 5 | **工作区下的配置文件不参与权限计算**——**不加载、不使用** | 同上 |
| 6 | **这条定调只针对权限计算，不针对资产与设置** | 同上 |
| 7 | **资产归属与作用域层是两套层次**，不合并——归属答「谁持有、谁替换得了谁」，作用域答「属性取什么值」。**工作区不是第五个作用域层** ⚠️ **后半句已被 2026-09-22 的裁决改写**，见[下](#2026-09-22--配值单位有了名字工作区的设置压过租户且挂在租户下) | [§5.8](design.md#58-三条层序各答一个问题) |
| 8 | **所有授权/权限相关的配置，系统加载的时候一律把工作区来的过滤掉**——**放宽的不作数，收紧的同样不作数** | [§5.7](design.md#57-工作区那一级不参与权限计算) |

**裁决 7 的原话**：

> 工作区这个就按资产归属与作用域分两套层次。

**它同时了结了 PM 报上去的那条待裁决**——**PF-001 不用改**。

> **取名是 PM 定的**：产品负责人口中的「项目」，**词条立为「工作区」**，
> 「项目」登记为弃用说法。**理由见[下一节](#二pm-推导)。**

**裁决 8 的原话**：

> 工作区不参与这一维，就是所有和授权/权限相关的配置，系统加载的时候，都把工作区里面来的配置过滤掉

**这一条了结了 PM 并排落盘的一对矛盾。**裁决 4 与裁决 5 本来就互斥：
4 说「**放宽**的不作数」——言下之意收紧的作数，**而那要求配置先加载进来，才判断得出方向**；
5 说「**不加载、不使用**」——那就根本没有可供判断的东西。
**PM 当时把两条并排写进了 §5.7，没看出它们打架。**

裁决 8 选定了裁决 5 那一侧，**并把范围从「权限计算」扩到「所有授权/权限相关的配置」**。
**裁决 4 的原话留着不删**：那是产品负责人当时确实说过的话，
**只是它描述的那套机制（先加载、再判方向）现在不存在了**。

**为什么连「只许收紧」也不留**，三条理由写在 [§5.7](design.md#57-工作区那一级不参与权限计算) 正文里。
**其中第三条是 PM 补的**：「只许收紧」要求系统逐条判断每项配置是放宽还是收紧，
**那个判断本身就是攻击面**——同一条配置在这一维看着是收紧，在另一维可能正好相反。
产品负责人给的是「加载时过滤」这个动作，**这条理由解释了为什么它比「加载后过滤」更省事**。

### 2026-09-22 · 禁用是持有上的开关，对 agent 与移除一样不可见

**产品负责人原话：**

> **禁用应该是某种开关。装配的过程：首先拿到所有它持有的（有使用权的）资产，
> 然后根据禁用表来过滤，这样开始装配时它「可见」的就是 有使用权 且 不被禁用 的那一批东西。
> 这里很自然把 禁用 和 不可用 区分开：禁用 是 不可见，不可用 是 可见但用了一定失败。**

随后逐条确认的后果：

| 定死了什么 | 落在正文哪里 |
|---|---|
| **禁用落在持有关系上，不是权限上**——持有带一个启用/禁用标记，配置原样保留 | [§6.4](design.md#64-移除与禁用是两个动作)、[flows §3.1](flows.md#31-一个资产在某个范围里) |
| **判据改为「收回持有，还是暂时关掉」**，不再是「成员该不该知道它存在」 | [§6.4](design.md#64-移除与禁用是两个动作)、[§7 取舍](design.md#七取舍) |
| **移除与禁用对 agent 一样：都不可见**，装配第一步就滤掉。成员要知道去申请，**看设置页** | [§6.4](design.md#但对-agent-来说两者一样都不可见)、[§5.6 第 1 步](design.md#56-四步资产求值--组装--投影--层级计算)、[acceptance](acceptance.md) |
| **禁用 ≠ 不可用**：禁用是不可见，[不可用](../PF-006-tools-and-skills/design.md#63-不可用时装的是同名替换件不是不装)是可见但用了一定失败 | [§6.4](design.md#但对-agent-来说两者一样都不可见)、[PF-006 §6.3](../PF-006-tools-and-skills/design.md#63-不可用时装的是同名替换件不是不装) |
| **禁用表按层，任一层禁用即不可见**；启用只去得掉本层的标记，**下层开不回上层禁的** | [§6.4](design.md#禁用是逐层配的布尔设置任一层为真即不可见) |
| **禁用改的是构成，不是注入**——动作空间跟着变小，与移除同一行 | [PF-004 §6.5](../PF-004-agent-definition-and-assembly/design.md#65-权限变化动作空间不变) |

**这条取代了 2026-09-17 的「禁用 = 持有但权限收窄为空集」**，
并就此闭合 [C-17](../../ubiquitous_language/conflicts.md#现有冲突)：
[UL-asset-holding](../../ubiquitous_language/terms/circulation-and-entitlement.md#ul-asset-holding--资产持有--asset-holding)
的形态由「未定」定为**属性**，[领域对象那边的同名待裁项](../../domain_objects/pending.md)随之删除。

### 2026-09-22 · 身份与实现解耦、工具定义可自带实现、禁用按析取合成

同日的三条裁决，分别落在资产的身份、工具定义的地位、禁用的合成语义上。

#### 一、每类资产的身份说清楚：身份与实现解耦

**产品负责人原话：**

> 身份 和 实现 是解耦的，比如一个 skill，harness officially impl 有一套，组织自己的有一套，
> 组织/租户自己的可以替换官方的（除非是 meta capability），所以这里才说 身份 和 实现是解耦的，
> 那么每种资产，需要有各自明确的定义，说清楚，哪些信息代表这个资产的身份
> （用来算两种实现是否对应的本质上是同一个东西），就比如 AgentDefinition 里面，
> tool name 是身份，但是 args schema、description 这些不是，因为 args schema 是跟着实现走的，
> description 也可被替换或修改（比如「不可用」的时候）

**随后逐条确认：**

| 定死了什么 | 落在正文哪里 |
|---|---|
| **身份就是「类别 ＋ name」**，在类别内决定同一性；其余一切归实现或设置 | [§4 身份是「类别 ＋ name」](design.md#身份是类别--name其余归实现) |
| **八类各自的身份与「明确不是身份」的信息**逐类写明 | [§4 八类资产](design.md#八类资产)各节的表 |
| **组织新建一个与 official 同类同名的资产，就是在替代它**，没有第二种解释 | [§4 身份是「类别 ＋ name」](design.md#身份是类别--name其余归实现) |
| **[PF-003](../PF-003-asset-transfer-and-sharing/README.md) 复制过去的资产带着同一个 name**，在接收方那边照样参与替代 | 同上；接收方那侧的规则本来就在 [PF-003 §6.8](../PF-003-asset-transfer-and-sharing/design.md#68-能力标识撞车但没有血缘) |
| **「治理层」在正文里不另立一个词，写成「一级归属」「一级治理」**（rev 10） | [2026-09-22 六条补充](#2026-09-22--工作区是一级治理不是目录会话创建时-opt-in挂上就自动加载)第 1 条 + [§5.8 三条层序](design.md#58-三条层序各答一个问题) | 产品负责人说的「治理层（相对于组织层、租户层）」，指的就是**与组织、租户同形地持有资产、给资产配值**这件事——而正文早已把这三者并称为[归属层](design.md#组织的设置是视图不是对象)。另起「治理层」一词，会与 [PF-001 的组织治理](../PF-001-identity-scope-and-agent-constraints/design.md#组织)（成员、角色、邀请）撞名，且读者会去找「工作区的超级管理员是谁」这种不存在的东西。**它不是一重身份这一点不变**——[UL-scope-layer-identity 的表](../../ubiquitous_language/terms/scope-and-resolution.md#ul-scope-layer-identity--作用域层身份--scope-layer-identity)照旧没有它 |
| **「工作区也可以是一个目录」落成「本版由目录承载，别的形态不定义」**（rev 10） | 同上第 2、3 条 | 「也可以是」意味着还有别的形态，但产品负责人没说是什么。**不替他编第二种**（远端仓库？对象存储？都是猜）；写成显式非目标，下游看到的是「只有目录一种，扩展要回来问」，而不是一个看起来合理的清单 |
| **不指定工作区就不会「自动挂上当前目录」**（rev 10） | 原话（二）「默认什么都不加载」+ [§5.7](design.md#57-工作区那一级不参与权限计算) | 「什么都不加载」排除了「按 agent 所在目录自动挂」这种实现——那正是 §5.7 防的隐式路径。取舍表已记 |
| **「工作区只禁得掉自己那批」不必另设一套机制** | 2026-09-22 那条限定 + [§5.8 两套层次](design.md#58-三条层序各答一个问题) | [资产归属](design.md#58-三条层序各答一个问题)那一套本来就记着**每一份资产是哪一级提供的**——否则「同标识覆盖」无从算起。所以这条限定用的是**已有的那个事实**，不是新加一个维度。**它改的只有一处**：算禁用值时，工作区那一级的值**按提供者过滤一次**再进析取 |
| **meta 是例外**：[meta 不可禁用不可替换](../PF-007-meta-capabilities/design.md#meta-与常驻的关系) | [PF-001 §4「来源」](../PF-001-identity-scope-and-agent-constraints/design.md#来源official-与-customized)已就地指路 |

**这不是新概念。**它就是 [PF-001 的能力标识](../PF-001-identity-scope-and-agent-constraints/design.md#范围化对象)——
本次补的是**每一类资产的能力标识由什么构成**；**替代规则仍归 PF-001**，本 topic 不重述。

#### 二、工具定义是实现在数据与治理层面的身份与表示，允许自带完整 package

**产品负责人原话（一）：**

> 工具定义，可以理解成是一个具体的工具实现，在数据和治理层面的身份和表示。
> 就像模型档案（LLMProfile / ModelProfile），模型实际的推理执行甚至是在系统外的。

**原话（二）**，在「a) 只有调用定义／b) 定义＋指向某个已装配实现的引用／c) 定义＋自带完整实现 package」三档里定档：

> 工具定义，从我们的完全动态系统的目标出发，应该是允许能够带到 c 这一档的，
> 剩下是系统实现的问题，不是产品和概念定义层面的事儿了。

| 定死了什么 | 落在正文哪里 |
|---|---|
| **工具定义是这份资产在数据与治理层面的身份与表示**，不是「资产的一半」 | [§4 Tool](design.md#tool)、[PF-006 §5.2](../PF-006-tools-and-skills/design.md#52-工具这个词指三样东西寿命各不相同) |
| **允许自带实现，直到自带一份完整 package** | 同上 |

## 二、PM 推导

### 设置项为什么分这四类

**准绳只有一条**（产品负责人给的）：改了会不会改变安全策略、让运行时无感知地提权。
PM 把它翻成可核对的问题：**这项值改了之后，会不会换掉这次运行要过的那道权限门，或改变一道已放行的权限实际放出去的是什么。**

1. 把 [§4 八类资产](design.md#八类资产)现有的设置项逐个过这一问。过不了的只有一族：目标环境、连接目标、投递目标、来源标识、凭据选择——
   共同点是**决定东西在哪执行、连到哪、送到哪、以谁的名义**。这就是「落点与身份」。
2. 剩下的分两族：改了顶多难用的（模型、语气、超时、阈值……）是「偏好」；指向本系统内另一份资产或位置的（绑定目标、挂哪个位置、启用哪些成员……）是「绑定」。
   绑定单列，是因为它有一条别的类没有的限定：**只能指向自己求值后看得见的东西**——否则工作区能把命令绑到它本不该看见的资产上。
3. 禁用与 `immutable` 不管「怎么做」，管的是别的设置——另立「治理」。`immutable` 从工作区来会锁死会话级，与 §5.7 第二条理由同源，故不许配。
4. 工作区自己带来的资产，落点随资产一起来：限定挡的是**改别人资产的落点**；那份资产能不能动由权限项把门，而这正撞出 [§九那项未决](design.md#九未决项)。

**没有更细分的理由**：再往下分（比如把凭据从落点里拆出来）在本版没有第二条规则需要区分它们；类别的数目要少，每多一类都要有一条只对它成立的规则。

以下结论不是直接裁决的，是从已拍板内容推出来的。推理链写在这里供核对。

| 结论 | 从哪几条推出 | 推理 |
|---|---|---|
| **组合只有一种关系**，贯穿资产之间、资产到 agent、资产到它的设置与权限 | 三句「本质上也是组合关系」 | "本质上也是"这个说法本身就是在否认它们是不同机制。若是三种，就有三套规则、三处覆盖语义、三个出错的地方 |
| **组装 = 组合关系从一个 Agent Definition 展开求值的结果** | 「资产到 agent 的组装本质上也是组合关系」 | 既然组装也是组合，它就不需要独立定义 |
| **Agent Definition 既能组合别人，也能被组合** | 「sub-agent 的定义属于这一类」（PF-001 §4） | 作为 sub-agent 被引用时是被组合方，被实例化时是组合树的根。两种用法不冲突 |
| **求值与组装是两步，不能合并** | PF-001 §6.2 的合成 + 本 topic 的组合 | 求值答"这个租户有什么资产可用"，组装答"这个 agent 实际由什么构成"。合并的话，「组织禁用了某个 skill」与「这个 agent 没引用它」会变成同一件事，而前者是管理决定、后者是设计选择 |
| **"把权限设成自动"是收窄，不是放宽** | 「组织没有禁用 → 租户可以设为自动」+ PF-001 的权限收窄语义 | 权限的每一层给的是**允许集合**，最终取交集。租户定成「自动」就是把集合收窄成单元素 `{自动}`——**选择就是收窄到只剩一个**。若权限是布尔开关，这个例子无法在收窄语义下解释；把它读成允许集合，例子与 PF-001 完全自洽 |
| **设置覆盖的是资产的一项设置，不是资产本身** | 「租户可以有自己对这个 agent definition 的默认模型」 | 例子里用的还是**组织共享的那一个** agent definition，只是它的一项设置在租户层被覆盖。这与 PF-001 的「同能力标识覆盖」（整个资产被替换）是两件事，必须分开说 |
| **顺序固定为：资产求值 → 组装 → 投影 → 层级计算** | 「设置权限是资产的属性」+「运行时按组装的确定再做层级计算」 | 项的**存在性**由组装决定——没装工具 X，就没有「工具 X 的执行权限」这一项。因此生效值不可能在组装之前算出来。四步的依赖是**单向**的；换序会得出「还不知道有哪些项，却已经算出了它们的值」这种结论 |
| **有两轮层级计算，作用对象不同** | 同上 | 第 1 步作用在**资产**上（同能力标识覆盖，哪个资产生效），第 4 步作用在**属性项**上（某项设置或权限取什么值）。混为一谈会得出「改一项设置等于换一个资产」 |
| **出厂默认层的设置与权限，是 official 资产自带的** | 「设置权限是资产的属性」+ PF-001「official 是最小必需，位于出厂默认层」 | official 必然在每次组装里，它自带的那份属性因此恒存在——这正是出厂默认层的内容。出厂默认层不需要另一套来源 |
| **配值的资格来自持有** | 「持有它的组织和租户各自可以有对应配好的默认设置和权限」 | 「持有它的」是一个限定，不是修辞。组织没有这个工具，就不该能配这个工具的执行权限——否则会出现「为一个自己没有的东西设置边界」这种既无意义又难以解释的状态 |
| **immutable 是一个机制，管三处** | 「强制 = 把字段值限定为不可被覆盖」+ 资产替换的强制 | 每层能做的事只有两件：给一个值、声明它不可再被下层覆盖。不加 immutable 就是**默认**，加了就是**强制**。这一套同时管设置的字段值、权限的取值、资产的替换——**不需要为「强制」另开一套语义** |
| **权限比设置多一档：可收窄到子集** | 权限取值域是枚举的 | `immutable(v)` 等于收窄到单元素集 `{v}`，是收窄的特例。权限的取值域是枚举（问一下/自动/禁止），所以还能表达「只许问一下或禁止」这种子集；设置的取值域通常开放（比如模型名），谈子集没意义，只有锁与不锁两态 |
| **official 永远可被替代，组织锁的是自己那一层** | 「若该资产是 official 则总是可被替换」+ PF-001 的 official 语义 | official 处在最底层，本来就是被替换的对象；它的不可侵犯性体现在**不可被清空**，而不是不可被替换。组织要锁，锁的是组织自己放上去的那个自定义资产 |
| **设置页没有一份独立维护的字段清单** | 「表单随资产自动增删」 | 页面长什么样是「持有了哪些资产」的函数。这正是「组织设置是投影不是对象」在产品上的样子——真去维护一份清单，它就会与资产各自演化，最终对不上 |
| **两块设置不能混在一个列表里** | 「设置页分两块」+ 两种 context 正交 | 混在一起，用户会以为改一个和改另一个是同类操作；而实际上换个组织之后，一个变了另一个没变 |
| **组合的引用指向能力标识，不指向具体资产** | 「组织可把自定义资产设为强制，不允许被替换，比如重要的安全组件」 | **三个选项里只有这一个成立。**若组合指向具体资产：plugin 里包着 official 的那一个，组织的安全组件**根本进不去**，immutable 白标了——漏洞就在 plugin 里。若允许 plugin 声明某成员不可替换：组织的安全组件同样进不去；要么规定组织的 immutable 优先（那 plugin 的声明在这种场合无效），要么让 plugin 赢（那第三方作者凌驾于部署方之上，不该）——**两种情形下它都不该生效，这个机制没有存在价值**。只剩「指向能力标识」 |
| **组合与依赖用同一条规则** | 上一条 + PF-001 §6.3「依赖指向能力标识」 | 两者都指向能力标识，不需要两套规则。**代价要写明**：plugin 作者不能假定自己包里的零件不被替换，他应当面向**能力标识**编写而不是面向某个具体实现。这是「资产可被自定义替换」这个能力的固有代价，不是缺陷 |
| **五类各自的定义与组合能力（整节）** | 产品负责人给的五类名字 + 组合关系 + 来源材料 | **这一整节是 PM 起草的**，等待逐条修正。判据统一为「它和旁边那一类的区别是什么」：Skill 说怎么做 / Tool 是那个动作 / Slash Command 是用户发起的入口 / Plugin 解决分发 / Agent Definition 组装出 agent。说不清区别的就是同名不同义 |
| **只有 Agent Definition 能组合全部五类** | 「资产到 agent 的组装也是组合关系」 | 组装成 agent 是组合图的终点，只有这个终点需要看到全部种类。其余节点各自只组合与自己有实际关系的那几类 |
| **Skill 与 Tool 互相引用** | 来源材料记载存在 tool–skill 依赖 | 两个方向都有实际含义：skill 声明「我这套方法要用到这些动作」，tool 声明「光有我不够用，得配这份指引」。不需要规定单一方向 |
| **MCP 带来的动作不是独立资产**（rev 2） | 裁决只说 MCP 是一类资产 | 若每个 MCP 工具各算一份资产，那**对端换个版本、工具清单一变，资产就凭空多出来或消失**——而资产是有能力标识、可被覆盖、可被持有转移的东西，身份必须稳定。**只有「接入点是资产、内容随它治理」这一种答案成立**，形状与「多命令 tool 与它的子命令」完全一致 |
| **MCP 与 Connector 不组合任何资产**（rev 2） | 上一条 | 它们的内容来自系统之外。列为组合方就等于承诺本系统掌握对端成员的身份与生命周期，而那件事做不到 |
| **Plugin 可以打包 MCP 与 Connector**（rev 2） | Plugin 的定位是「分发与组合单元」 | 一套完整的接入方案往往是「几个工具 + 一个 MCP 接入 + 一个消息来源」，分开装等于把分发问题退回给用户。**这一条是 PM 推的**，产品负责人若认为外部接入不应随 plugin 分发，删掉表里那两格即可，不影响其余结构 |
| **Connector 的权限里必须有「送进来的消息按什么身份处理」**（rev 2） | 租户隔离 + Connector 只能送消息进来 | 外部消息进了系统就要被某个身份承接，否则它落在谁的租户里说不清。不定这一项，租户隔离会在入口处破掉 |
| **Slash Command 不并进 Skill** | 来源材料：两者是可相互绑定的不同定义，不因手动入口统一就合并 | 同一个 skill 可以有多个入口，也可以完全没有入口（只由 agent 自主使用）。绑定关系是**多对多**，合并会丢掉这一层 |
| **组合图不得成环** | 组合要能求值 | Agent Definition 之间可嵌套 sub-agent，但 A 引用 B、B 又引用 A 必须被拒绝，否则组装永远算不完。这不是策略选择，是可终止性的要求 |
| **三种组合暂不做：Skill 套 Skill、Plugin 套 Plugin、Plugin 装 Agent Definition** | 「先做最小的正确模型」 | 三者都**没有已知需要**，且各自会带来负担：Skill 套 Skill 要环检测与「哪层指引优先」；Plugin 套 Plugin 让「内含成员随 plugin 版本治理」变成多层；Plugin 装 Agent 是个合理设想但目前无人要。**加是加法，不用改已有结构**——真实需求出现时再加 |
| **作者是本 topic 新增的一类使用者** | 「资产可被组合与替换」 | PF-001 里只有用的人和管的人。一旦资产可被替换，**打包的人也成了利益相关方**——他的「我包里的零件会不会被换掉」必须有明确答复，不能让他在事故之后才发现 |
| ~~**Hooks、Rules 是 Plugin 的组合成员，不是第六类**~~ | 五类是穷尽的 + 组合关系成立 | 组合关系一旦成立，「成员」与「独立资产」不再互斥。它们没有被列进五类，就按成员处理。**rev 3 推翻了其中 Hooks 那一半**：挂件升格为第八类 [Loop Extension](design.md#loop-extension)，见下。**Rules 那一半仍然成立** |
| **Service、Middleware 不进产品正文** | 五类是穷尽的 | 它们是技术实现概念。产品设计里出现它们，只会让读者以为自己需要理解运行时 |
| **Hooks 这一类挂件从「Plugin 的成员」升格为一类资产**（rev 3） | 第八类资产的裁决 | 上一条的推理**在当时是对的**——挂件没被列进那几类，就只能按成员处理。**变的是前提**：产品负责人要求挂件能被**租户与组织超管各自装、各自覆盖**，而「成员」拿不到独立的持有与层级求值（[Plugin 的成员不取得独立的顶层生命周期](design.md#plugin)）。**要么给成员补一套治理，要么让它成为资产**——后者不新增机制，选后者 |
| **Loop Extension 不组合任何资产，但理由与 MCP、Connector 不同**（rev 3） | 「拓展件是系统在固定位置替 agent 调的」 | MCP 与 Connector 空着，是因为**内容在系统之外、管不着**；拓展件空着，是因为**它本来就是一段自足的判断**。**分开写，因为后果不同**：真让拓展件组合一个 Tool，那个 Tool 就会进 agent 的[动作空间](../../ubiquitous_language/terms/capabilities-and-composition.md#ul-action-space--动作空间--action-space)，**agent 面前凭空多出一条它没被授予的工具** |
| **Plugin 可以打包 Loop Extension**（rev 3） | 「自定义自己的 agent plugin」这句原话 + Plugin 是分发单元 | 产品负责人要的就是「一个 plugin 装下去，该带的检查也一起到位」。不允许打包，等于要求用户逐个手装挂件，**而分发问题正是 Plugin 存在的理由** |
| **干预力是权限，不是设置**（rev 3） | 「权限约束能执行什么动作、边界在哪」 | 「这个挂件能不能改写、能不能否决」回答的正是**边界在哪**。归进设置，它就走**覆盖**——租户能把组织给的「只观察」自己改成「可否决」，**组织的边界当场失效**。归进权限走**收窄**，组织锁死就放不宽，与工具执行权限完全同构 |
| **同一位置挂多个拓展件，彼此不构成同标识覆盖**（rev 3） | PF-001 的同能力标识覆盖 + 「一个位置可以挂多个」 | 覆盖的单位是**能力标识**，不是位置。**位置不是标识**——两个不同的挂件恰好挂在同一处，是两份资产各自生效；覆盖只发生在**同一个挂件**的组织版与租户版之间。**不点破，实现会按「一个位置一个挂件」做**，而那会让第二个挂件被静默丢掉 |
| **八类各自「不是身份」的那份清单**（rev 6） | 「身份 ＝ 类别 ＋ name」+ 产品负责人给的那个例子（tool name 是身份，args schema 与 description 不是） | 判据是**它跟不跟着实现走**：跟着实现走的，换一份实现就可以全不一样，**拿它判同一性就等于宣布两份实现永远不是同一个东西**，替代当场失效。按这一条逐类过一遍，得到的就是八张表里那几格。产品负责人只给了 Tool 那一例，**其余七类是 PM 按同一判据推的** |
| **析取不是第三种合成规则**（rev 6） | 「禁用是设置的一种特殊处置逻辑」+ [immutable 一个机制管三处](design.md#54-默认与强制一个机制三处适用) | 「任一层为真即为真」等价于「布尔设置 ＋ 真即 `immutable`」：配真的那一层同时锁死，下层改不动；配假只是默认，下层照样能配真。**两种写法给出的求值结果逐格相同**，所以不必为禁用新开一套语义——**正文主叙述用析取，等价关系只作一句说明**，因为读者要判断的是「能不能开回来」，不是机制 |
| **工作区配得了「禁用」，与 [§5.7](design.md#57-工作区那一级不参与权限计算) 挡授权与权限不冲突**（rev 6） | 「到工作区这一层同理」这句裁决 + 禁用是设置不是权限 | §5.7 挡的是**权力**——谁被允许做什么，它进的是[权限的交集](../PF-001-identity-scope-and-agent-constraints/design.md#62-三种合成语义)。禁用答的是**这个目录上看得见哪些资产**，与工作区本来就能提供资产同一性质，不进那个交集。**代价以[「工作区只能禁用它自己提供的那批资产」这条限定收口](#2026-09-22--工作区只能禁用它自己提供的那批资产)**：§5.7 的第二条理由（「往严里改一样能伤人」）在这一维上**照样成立**——工作区能收掉的**只有它自己拿出来的那批**，别人提供的资产它配的禁用值不参与 |

### 为什么这一级叫「工作区」而不叫「项目」

**这是一处[同义不同名](../../ubiquitous_language/conflicts.md)，按规矩 PM 选一个、其余进弃用。**

产品负责人两次提到它，用的是两个词：讲 [meta runtime context 那一项工作区](../PF-015-session-lifecycle-and-ownership/design.md#56-十四项-meta-runtime-context)（PF-015 rev 7 起是第 10 项）时说
「当前会话 attatch 的**工作区**目录路径」，讲资产归属时说「还有一级……就是**项目**」。
**两个词指同一个东西。**

**选「工作区」的理由**：

| | |
|---|---|
| **「项目」撞得太厉害** | 项目管理、项目文件、「这个项目」——**它在别处的正常用法躲不掉**，[收窄一个通用词的代价极高](../../ubiquitous_language/conflicts.md) |
| **「工作区」在本领域就是这个意思** | 与 `Account`、`Sandbox` 同类：**常用但本来就指这个**，加限定反而不自然 |
| **已经在用了** | 第 11 项 meta runtime context 写的就是「工作区」 |

**层次名跟着走**：**工作区级**，与「组织级」「租户级」并排读着顺。

### 工作区不是「会话级」

**推理**：[会话级的东西一律不外溢](../../ubiquitous_language/terms/agent-runtime-loop.md#ul-session--会话--session)，
而工作区级的资产**留在那个目录上**——**同一个租户下，同一个目录被两个会话挂上，两边看到的是同一批**。
**两者的失效事件完全不同**：会话级跟着那段协作结束而不再适用，工作区级跟着目录走，**换谁来挂都一样**。
**把它当成会话级的一种，会得出「换个会话就该重新解析一遍」这种错误结论。**

### rev 17 的主线裁定与推导（2026-09-23，待产品负责人确认）

| 编号 | 结论 | 类别 | 推理链 |
|---|---|---|---|
| A-G1 | **同一层可以有好几份同标识的资产，但一层对一个身份至多持有一份**；替代发生在持有上，复制进来不自动顶掉原来持有的那份 | 主线裁定 | [PF-003 §6.8](../PF-003-asset-transfer-and-sharing/design.md#68-能力标识撞车但没有血缘)「新增并存」与本 topic 原文「同一身份同层只一份」字面相抵。**两句说的不是同一样东西**：前者说资产（记录）可以并存，后者说持有；把后者的措辞落到「持有」上，两句同时成立。复制若自动顶替，接收方一层原本用着的那份会在没人决定的情况下被换掉 |
| A-G2、R-E1、S10-a | **同标识替换之后，外层为这个身份锁下的权限的界照样管着替换它的那一份**；替换的那份少声明了外层锁住的某一项，那一项按最严算。**设置不跟过去**：外层给原来那份配的值（连锁住的在内）不落到替换它的那一份上 | 主线裁定 | 配值挂在持有上（[§5.2](design.md#组织的设置是视图不是对象)），照字面，下层换上一份同名的，上层那份持有上的锁就管不到新的这份——**租户把组织锁成「问一下」的工具换成自己的，再配「自动」，锁就被绕开**，这是一条安全缺口。权限跟身份走堵住它。**设置不能照搬**：设置里有落点与身份一类，组织给官方 MCP 接入点配的凭据跟到同名的替换上，凭据就交给了另一份实现；组织要一项设置管住所有实现，本来就有「把替换锁住」那条路（[§5.5](design.md#55-资产替换的层级)） |
| S10-b、R-E2 | **权限：锁下的是界，各层取交集；不锁的是挑选，从最具体的一层往外取第一个落在界内的；作者声明的默认值是最外面那个挑选** | 主线裁定 | 纯交集下，[§5.4](design.md#54-默认与强制一个机制三处适用)「组织说默认问一下，成员可改成自动」求出空集，「组织锁死问一下」那一行成员的值还留在输入里、也求出空集——**§5.4 两行都破**；而[拍板记录第 18 行](#一拍板记录)产品负责人的原例（组织没禁用，租户可设为自动）说的正是「不锁可改」。只有「锁的是界、不锁的是挑选」同时过 §5.4 与上一条 |
| （S10-b 推导） | **例外：哪一层把执行权限配成「禁止」，锁不锁都是界**；作者声明的默认值不在此列 | PM 推导（请产品负责人确认——**它收窄了主线 S10-b 的字面**） | 照 S10-b 字面，组织配「禁止」而不锁，成员挑「自动」就生效；而 [PF-007 §5.6](../PF-007-meta-capabilities/design.md#56-一次放行判断走四步)（已接受）写的是「任一层明确禁止 → 拒绝，终局」「**任何层的明确禁止，任何模式都翻不了案——整条链上唯一不可协商的一条**」，[拍板记录第 18 行](#一拍板记录)产品负责人的原例也以「组织**没有禁用**它的使用」为前提才让租户设自动。**三处同时成立只有一种读法**：「问一下」「自动」不锁是挑选，「禁止」配了就是界——与[禁用「真即锁」](design.md#54-默认与强制一个机制三处适用)同形。作者默认若也算，作者写一个「禁止」就没有任何一层打得开，所以它只是挑选。代价：组织说不出「默认关、成员可自己开」 |
| G-9 | **界内谁都没挑到时，取界内离最具体的那个挑选最近的一档；一样近取严的**。锁成空集 → 每一次调用都被拒 | PM 推导（请产品负责人确认） | S10-b 已定「由里到外取第一个落在界内的挑选」，只剩「一个都不落在界内」这一格。**取最严**看着保守，但界是每一层都认可的范围：组织锁「问一下、禁止」两档说的是「不许自动」，作者默认「自动」时取最严会落到「禁止」，把工具整个关掉——**那不是任何一层的意思**。取离人意最近的一档，不越出任何一层的界，也最贴近唯一表过态的那个挑选。一样近（界不连续时）才往严里倒。[PF-007 §6.11](../PF-007-meta-capabilities/design.md#611-ask通向人) 需要求值给出一档，这条让分档的权限总能落到一档 |

### rev 20 的主线推导与 PM 推导（2026-09-24）

前提是[第一节](#2026-09-24--连接件事件目录厚信封两种投递方式触发会话的默认运行模式)那四条原话。**「主线推导」「主线裁定」是主线施工简报（产品批 4b）交来的，不是产品负责人的拍板**，他可推翻；「PM 推导」是落盘时推的。

| 编号 | 结论 | 类别 | 推理链 |
|---|---|---|---|
| M-1 | **[事件订阅](design.md#事件目录与事件订阅)是偏好类设置** | 主线推导 | 它不决定东西落在哪、送到哪、以谁的名义——那是投递目标与鉴权绑定的事；也不管别的设置或权限怎么起作用。它答的是「这份持有要目录里的哪几种」，**改错了是收多了或收少了，进来的每一条照样按会话的身份、过同一道放行**。按 [§5.2 那一问](design.md#设置项分四类资产声明每一项时必须标类别)，门没换、进门的东西的落点也没换，只能是偏好 |
| M-2 | **[触发会话的默认运行模式](design.md#触发会话的默认运行模式)是治理类设置**；治理类「管什么」一格由此写成「**管别的设置与权限怎么起作用**」，工作区配不了它 | 主线推导 | 它决定一个多半无人值守的新会话，在「本该问人」的那一刻是拒、是算、还是放——**改的是那道门自己怎么判**，不是东西落在哪或以谁的名义，所以不是落点与身份；它也显然不是偏好：从 `never` 改成 `bypass-permissions`，后果不是「难用」，是放手。治理类原先只有禁用与 `immutable`，两者一样是「不改做什么，改放不放、锁不锁」，这一项与它们同一性质。**从工作区来就是仓库替人定放行**，与 [§5.7](design.md#57-工作区那一级不参与权限计算)挡的是同一件事 |
| M-3 | **[拓展件不可用处置](design.md#不可用处置是这一件自己的声明)是拓展件定义里的一项声明**，与工具定义的「能不能在后台执行」同一种；不是四类设置里的任何一类，也不是权限，各层不配值 | 主线裁定（闭合 D-5） | 与 [D-5 的 PM 倾向](#三待裁决)同向：它说的是这一件是一道什么样的关，各层能配就等于在两层把同一件做成两件事——那是[同标识替换](design.md#55-资产替换的层级)的活，与[斜杠命令的绑定目标不是设置](design.md#slash-command)同一个理由。[PF-006 §5.3](../PF-006-tools-and-skills/design.md#其中两项声明的是设置项) 已经有了现成的先例：作者的许可（能不能后台执行）写在定义里、不是设置 |
| M-4 | **两种投递方式的动作主体**：① 已有的会话开口接收，主体是会话，本 topic 这一侧的配置是投递目标；② 连接件的事件经受理开新会话，主体是连接件，配置是触发会话的默认运行模式。**以哪个 agent definition、哪个租户身份建新会话，登记为会话那一块的缺口**，不作为本 topic 未决 | 主线裁定 | 原话 3 的「动作主体不同」「具体设计是会话那块的事」。投递目标本来就是「送进哪一个已有的会话」，与 ① 的形状一致，留作 ① 的配置 |
| M-5 | **外部内容选不了类型之外的任何东西**：进哪个会话、开不开新会话、以谁的身份、按什么运行模式 | 主线裁定 | 「以谁的身份」早已是一条固定规则（D-4）；原话 4 让运行模式来自配置者；原话 3 让去处由会话或连接件的配置定。三条合起来，外部内容能决定的只剩它自称是哪一种——而那一种还要在目录里、被订阅 |
| P-1 | **「至少设置上」读作：配置的人必须给；作者声明的默认与出厂默认都不算。哪一层都没给，这份连接件开不出新会话，受理时明说；① 那一路不受影响** | PM 推导 | 原话 4 说的是**配置的时候**要设置上、**配置者**可调，主语是配置它的人。认作者的默认，作者写一个 `bypass-permissions`，没看过这一项的组织就会让它开出放手去做的会话——那条要求就落空了。出厂默认同理。① 那一路不开新会话，已有的会话有自己的运行模式，这一项与它无关；把 ① 也挡住，是拿一项它用不到的设置去罚它 |

**调研参照**（只作参照，不作依据）：
- [connector-products](../../../research/connector-products/research.md)（仓库内，2026-09-24）：**观察到的事实**——两家主流产品里叫 connector 的全是拉取型（C-1）；推型入口没有一家给「可订阅的事件类型目录＋消息包形状」，Claude Code channels 只给自由文本 `instructions` 与扁平 `meta`、不合规的键静默丢弃（C-2、C-5）；成熟事件范式分厚、薄两派，薄派要求消费方回头去拉（C-3）；只有 channels 投进已开着的会话，其余推型先例一律一事件一新会话（C-8）；无人值守时权限提示会让会话挂起，Claude Code 为此给 channel 开了一条权限中继（C-7）。**采纳**：结构化目录与「不对就拒、不静默丢」（对应本产品里「形状对不上的消息只能交给模型猜」这个冲突）；厚信封（本产品的连接件没有读取面，薄信封在这里根本兑现不了）。**没采纳**：权限中继——它等于给外部来源一个管理面，与「它只能送消息进来」相反；本产品用「配置的人事先给运行模式」回答同一个问题。
- Claude Code routines 文档（[code.claude.com/docs/en/routines](https://code.claude.com/docs/en/routines)，2026-09-24 读）：**观察到的事实**——每次触发开一个新会话、不复用；运行中「没有权限模式选择器」、不停下来要批准；触发带的文本被包成「不可信数据」、不能当作批准。**推测（未核实）**：他们选「一律不停」是为了避免无人值守的会话卡住。**用户抱怨**：[issue #95384](https://github.com/anthropics/claude-code/issues/95384)——无人值守的会话仍然卡在一个没人能答的权限模式请求上，「本该构造上就是非交互的」。**这正是 P-1 要防的那种事**：本产品不替配置者选「一律放行」，也不留一个没人想过的默认，而是要他事先选一档。

2. **哪些已接受的结论会松动**：「投递目标本版只能指一个已有的会话」照旧，但它不再是连接件唯一的去处——主线裁定 R-N2「按消息新建会话本版没有」被原话 3 取代；治理类的定义从「管别的设置」放宽到「管别的设置与权限怎么起作用」，禁用与 `immutable` 的规则一个字没动。
3. **是不是在用错地方解决问题**：事件目录与订阅是连接件这类资产自己的形状与设置，只能在这里定；两种投递方式在这里只定存在与主体，会话怎么建留给会话那一块。
