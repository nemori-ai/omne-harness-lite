# PF-002：设置、权限与资产的展开

- 修订：**rev 23**，2026-09-27 · [变更历史](changelog.md)
- 状态：工作区本体与资产层分离的增量为草稿；正式接受范围及已知缺口见 [README](README.md#状态)，待讨论项见 [§九](#九未决项)

## 一、背景与问题

[PF-001](../PF-001-identity-scope-and-agent-constraints/design.md) 说清了设置、权限、资产
**对外**的样子：各自挂在哪一层身份上、多层同时有值时怎么合成。
但它把三者内部都当成了黑箱——资产只有一张"种类表"，设置与权限连表都没有。

黑箱留着，这些问题每次讨论都要重新发明一遍答案：

- 一个 plugin 里装了一个 skill，**这个 skill 是不是也是资产**？能不能被单独引用、单独覆盖？
- **一个 agent 由什么组装而成**，和"一个 plugin 由什么组成"，是不是同一回事？
- "默认模型"是设置——那它是**谁的**设置？全局的，还是某个 agent definition 的？
- 一个工具的执行权限默认是"问一下用户"，**租户能不能改成自动**？依据是什么？
- 组织想在 agent 每次调模型之前插一段自己的检查，**这段东西算不算资产**？谁能装、谁能覆盖？

## 二、目标与非目标

### 目标

1. 把资产的**八类具体抽象**一一定义清楚。
2. 定义资产之间的**组合关系**，以及组装成 agent 与它是不是同一种关系。
3. 说明**设置与权限附着在什么上**，以及它们与资产之间的关系。

| **MCP 对端除动作之外的能力，本版桥到哪一步** | [随采用的客户端](#mcp)，产品不预定清单 |

| **连接件的新会话怎么建、会话怎么开口接收连接件的投递** | [两种投递方式](#两种投递方式动作主体不同)的存在与各自的动作主体由本 topic 定；**新会话以哪个 agent definition、哪个租户身份建，会话怎么在自己里面开口、怎么关**，归会话那一块（[PF-015](../PF-015-session-lifecycle-and-ownership/README.md)），受理那一半归 [PF-014](../PF-014-inbound-intake-and-queueing/README.md)。本 topic 不替它们定 |
| **按对面的线程把消息分进不同会话** | 本版没有。两种投递方式里没有一种按对面的线程分会话 |

## 三、用户与场景

| 使用者 | 什么情况下接触这块 | 他关心什么 |
|---|---|---|
| 组织超级管理员 | 给组织配资产、调设置、定权限边界；**在 loop 的某个位置挂上自己的检查** | 我加了这个东西，成员的设置页会多出什么？我锁死的，成员能不能绕过去 |
| 组织成员 | 在自己的租户里调整这些资产怎么用 | 哪些我能改、哪些是公司定死的？我改了为什么没生效 |

| **agent** | 每次运行 | 我这次由哪些资产组装而成、每一项配置的值是多少 |

**作者在 [PF-001 §6.7](../PF-001-identity-scope-and-agent-constraints/design.md#67-创作与归属)
已有身份**（他是一个租户，署名不随换岗或离开而消失）。
本 topic 给他**新增一重顾虑**：资产一旦可被组合与替换，

### 八类资产

**名字、一句话含义与管理边界归
[PF-001 §4「资产的种类」](../PF-001-identity-scope-and-agent-constraints/design.md#资产的种类)，
本 topic 不重复。**这里补它没有的部分：每一类**具体是什么**、**自带哪些属性**、
**能组合什么**。

判据始终是同一个：**它和旁边那一类的区别是什么**。说不清区别的，就是同名不同义。

#### 身份是「类别 ＋ name」，其余归实现

**一份资产的身份就是它的类别加它的 name。**类别相同、name 相同的两份东西，
**就是同一个东西的两种实现**；类别不同，名字撞了也不相干。
这正是 [PF-001 的能力标识](../PF-001-identity-scope-and-agent-constraints/design.md#范围化对象)——
本节补的是**它由什么构成**，**怎么替代仍归
[PF-001 §6.2](../PF-001-identity-scope-and-agent-constraints/design.md#62-三种合成语义)**，这里只引用不重述。

**其余一切归实现或设置。**参数形状、说明文字、返回形状、内部有哪些子命令、由哪个包提供——
**这些跟着实现走，换一份实现就可以全不一样**；说明甚至会被整段换掉，
[不可用时装上的那份同名替换件](../PF-006-tools-and-skills/design.md#63-不可用时装的是同名替换件不是不装)
换的就是它。所以它们一个都不参与判断「这两份是不是同一个东西」。
**每一类各自的身份、以及各自明确不算身份的东西，写在下面八节各自的表里。**

**身份与实现就此解耦**：同一个身份，平台有一套实现，组织可以有自己的一套，
租户还可以再有自己的一套，凭同一身份互相替代。两个直接后果：

- **组织新建一个与 official 同类同名的资产，就是在替代它**——没有第二种解释，
  不存在「同名但各算各的」这种状态。
- **[复制或分享](../PF-003-asset-transfer-and-sharing/README.md)过来的资产带着原来的 name**，
  所以它在接收方那边照样参与同标识替代，由接收方自己的层级求值决定谁生效。

**同一层可以有好几份同标识的资产，但一层对一个身份至多持有一份。**
复制进来的那份与这一层自己原有的那份[并存](../PF-003-asset-transfer-and-sharing/design.md#68-能力标识撞车但没有血缘)，都是这一层的资产；
**替代发生在持有上，不在资产上**——这一层持有哪一份，哪一份就是这一层在这个身份上的实现。
换持有哪一份是这一层管理者的动作，**不是复制的副作用**：复制进来不会自动顶掉原来持有的那份。

#### Skill

**一段可复用的工作方法**——告诉 agent「遇到这类事情该怎么做」。

它的主体是**可读的指引正文**，可以带上所需的资源文件。
读取一个 skill **不等于运行它带的脚本**，也不自动装载它的全部附件。

| | |
|---|---|
| **身份** | **name**。正文、资源文件、它组合的 tool 清单**都不是**——换一份实现，这三样都可以全变 |
| **和 Tool 的区别** | Skill 说**怎么做**，Tool 是**做的那个动作**。「代码审查该看哪些地方」是 skill，「读文件」是 tool |
| **和 Slash Command 的区别** | Skill 是方法本身，Slash Command 是**用户主动发起它的入口**。两者可绑定，但不是一回事。**同一份正文有两条路到 agent 眼前**：agent 经 [`Skills()`](../PF-007-meta-capabilities/design.md#62-skills通向任意技能) 按需去读，进会话日志的是**一次工具执行的返回**；人敲绑定了它的[斜杠命令](#slash-command)，正文**直接成为用户那条消息里的一个内容块**。两条路都成立，进日志的形状不同 |
| **自带的属性** | 设置：**系统不为这一类另规定设置项**；作者可以给自己的 skill [声明设置](#谁可以使用它是各类资产共用的一项权限)，求出来的值交给谁见 [PF-007 §9.3](../PF-007-meta-capabilities/design.md#93-技能作者自己声明的设置求出来的值交给谁)。权限：[谁可以使用它](#谁可以使用它是各类资产共用的一项权限) |
| **能组合什么** | **Tool**——声明「我这套方法要用到这些动作」 |

#### Tool

**一个可被调用的动作。**

**[工具定义](../PF-006-tools-and-skills/design.md#52-工具这个词指三样东西寿命各不相同)
是这份资产在数据与治理层面的身份与表示**——叫什么、收什么参数、返回什么，以及它的各项声明。
**它可以自带实现，一直到自带一份完整的实现 package。**

**装不进当前运行时的实现，走[同名替换件](../PF-006-tools-and-skills/design.md#63-不可用时装的是同名替换件不是不装)**：
条目照样在原位、形状不变，**可见但用了一定失败**，不是「不算可用」。
怎样把自带的那份实现装进运行时，是系统实现的事——**产品这一层只定它允许自带**。

一个 tool 可以是**多命令**的：一套命令通过统一入口提供，
agent 按类似 Unix CLI 的方式选命令、给参数、取结果。
**整套命令在组装时只占一个槽位**——命令多了不会让 agent 面前的工具条目变多。

| | |
|---|---|
| **身份** | **name**。args schema、说明、返回形状、子命令集合、由哪个包提供实现**都不是**——它们跟着实现走 |
| **子命令是什么** | Tool 的**内部结构**，不是独立资产。它们随这个 tool 一起被持有、配置与授权 |
| **自带的属性** | 设置：超时、并发、目标环境等。**权限：执行权限（问一下 / 自动 / 禁止）**——这是最常被配置的一项 |
| **能组合什么** | **Skill**——声明「光有我不够用，得配这份指引」。有些工具必须与 skill 配套 |

#### MCP

**一个外部工具来源的接入点。**接进来之后，它提供的动作可被 agent 使用。

**在持有与授权上**，它和 Tool 的关系跟「多命令 tool 与它的子命令」是同一个形状——
带来的东西不单独成为资产，随它一起被持有、配置与授权。
**在 agent 面前不是**：多命令 tool 整套只占一个槽位，
**接入点带来的每一个动作，各自是一个模型可见的工具条目**——这是社区通行的做法，本系统照用。

| | |
|---|---|
| **身份** | **接入点的 name**。它提供的动作清单、连接参数、凭据**都不是**——动作清单由对端决定，随时会变 |
| **和 Tool 的区别** | Tool 是**一个动作**，MCP 是**一批动作的来源**。MCP 本身不可被调用 |
| **它带来的动作是不是资产** | **不是。**随这个接入点一起被持有、配置与授权 |
| **动作在 agent 面前是什么** | **对端的每一个动作映射成一个工具条目。**这一批条目**在每一次[执行尝试](../PF-012-agent-loop-and-run/design.md#执行尝试)开始前、与[可用性](../PF-006-tools-and-skills/design.md#62-可用性在每次-run-开始前重算)一起重算，一次尝试之内不变**——对端中途增删动作，下一次尝试才看得到。常不常驻、怎么被发现，归 [PF-006 §6.13](../PF-006-tools-and-skills/design.md#613-mcp-接入点带来的动作) |
| **和 Plugin 的区别** | Plugin 是**本系统内部**的打包与分发单元，成员是本系统的资产；MCP 指向**系统之外**，成员由对端决定、本系统不掌握 |
| **自带的属性** | 设置：连接目标与 **[MCP 凭据](../../ubiquitous_language/terms/capabilities-and-composition.md#ul-mcp-credential--mcp-凭据--mcp-credential)**（都是[落点与身份类](#设置项分四类资产声明每一项时必须标类别)，凭据怎么来、归谁见[下文](#mcp-凭据一份持有一份静态的或经-oauth-取得的)）、**连接超时**与**单次调用超时**（偏好类，两项分开）。权限：**能不能用**，以及**每一个动作的执行权限**（同 Tool 那三档）——一个动作就是一个工具条目，**逐动作的权限就是那个条目的执行权限**，这一批权限项随对端此刻提供的动作而有 |
| **除动作之外的能力** | 对端还可能提供动作以外的东西；本版桥到哪一步，**随采用的客户端**，产品不预定清单 |
| **能组合什么** | **不组合任何资产。**它的内容来自对端，不是本系统的组合关系 |

**一处必须写明的后果**：对端的**可用性与版本不由本系统掌握**。
它提供的动作可能今天有、明天没有，而这**不是故障**——
**只是它不会在一次执行尝试的中途从 agent 面前消失或冒出来**，变化在下一次尝试开始时才生效。
**怎么应对归工具与技能那一块**，本 topic 只定它是一类资产、它的内容不是资产、以及它的动作在 agent 面前是什么。

##### MCP 凭据：一份持有一份，静态的或经 OAuth 取得的

**[MCP 凭据](../../ubiquitous_language/terms/capabilities-and-composition.md#ul-mcp-credential--mcp-凭据--mcp-credential)决定对端以哪个账号认这个接入点。**
它的值有两种来路：**配值的人直接填上一个静态值**，或者**经 OAuth——人到对端点一次同意，系统据此取得**。
**两种来路是同一项设置、同一套规矩**：OAuth 只是换了一种把值配上去的办法，不是另一样东西。

| 这件事 | 怎么定 | 为什么 |
|---|---|---|
| **归谁** | 挂在**租户那一层**的那份持有上，一份持有一份值；**组织那一层不持有 MCP 凭据**——组织接入的接入点，由每个成员在自己的租户层取。**不跨租户身份共用**——同一个人在两个租户下各取各的，接的可以是对端两个不同的账号 | [配值挂在持有上](#组织的设置是视图不是对象)，[跨租户默认拒绝](../PF-001-identity-scope-and-agent-constraints/design.md#租户)；与[连接件的鉴权绑定](#connector)同一个形状。组织那一层为什么不持有，见表下 |
| **谁去取、在哪取** | **有资格给那份持有配值的人，在配值的地方取**——和填一个静态值是同一个动作。**agent 不发起，run 不触发，不出[决策卡片](../PF-008-human-in-the-loop/design.md#决策卡片)** | 取值就是配值，而[配值的资格来自持有](#三方分工资产定形状各层配值运行时求值)。卡片[谁能答，看的是能不能访问那个会话](../PF-008-human-in-the-loop/design.md#67-租户隔离在池子上成立)，不是配值资格——走卡片，一个成员答一张卡就改写了一层他本来配不了的值。**连接又发生在 run 开始之前**，那时没有哪一次工具执行可以停下来等人 |
| **工作区那一级** | **取不了。**仓库带来的接入点若要走 OAuth，装进来也连不上；要用，[把它收进租户层](#57-工作区那一级不参与权限计算)再取 | [落点与身份类不从工作区来](#57-工作区那一级不参与权限计算)；而且工作区那一级的值[只来自选定工作区实例或地址提供的资源](flows.md#12-配置一个资产的设置或权限)，没有人在那一级操作配值 |
| **还没取，或者已经失效** | 算**连不上**：它带来的动作按 [PF-006 §6.13](../PF-006-tools-and-skills/design.md#接入点连不上它的动作就是不可用) 办，一律不可用 | 连不上就是连不上，不另立一条规则 |
| **换一个账号、撤掉** | 就是**改这一项的值、清掉这一项的值**；**下一次执行尝试开始前生效**，正在进行的那次尝试手上的动作清单不变 | 动作集与可用性[本来就在每一次尝试开始前重算](#mcp)；[撤销管的是下一道准入](../PF-001-identity-scope-and-agent-constraints/design.md#66-撤销不等于强制停止) |
| **续期** | **不要人，也不算换值**：续出来的仍是对端同一个账号的，仍归同一份持有。续不上，就是失效，照上面那一行 | 续期没有换掉进门的身份——[落点与身份那一类](#设置项分四类资产声明每一项时必须标类别)要看住的正是「换没换身份」 |
| **随持有生灭** | 持有[移除](#64-移除与禁用是两个动作)，它跟着没；禁用，它一个不丢 | 与所有[属性配值](#组织的设置是视图不是对象)一样 |
| **值本身** | **永不呈现**；呈现得出的只有有没有、哪一层的、什么时候取的 | [PF-016 §6.11「秘密不进任何一份呈现」](../PF-016-cli-tui-delivery-surface/design.md#611-秘密不进任何一份呈现)管的就是这一类 |

**组织那一层不持有 MCP 凭据，每个人在自己的租户层取。**MCP 连接发生在每个人自己的据点上，
组织层的值要用，就得复制到每一台机器：

- **人离职时收不回**——那一份已经在他的机器上了；
- **经 OAuth 取得的，还得在许多台机器上各自续期**。

这与模型凭据[「每台机器上只有自己那一把」](../PF-016-cli-tui-delivery-surface/design.md#620-每台机器上只有自己那一把凭据)是同一条路，两种凭据一并这么定。
组织照样接得进一个接入点、照样配得了它的连接目标；**以对端哪个账号进门，由每个成员自己取**。
**代价**：每个人都得自己去对端点一次同意（或自己填一个值），组织给不出一个大家共用的账号；
组织统一持有、下发凭据这件事，[本版不做](#非目标)。

**不在这里的**：凭据存在哪、怎么加密、什么时候续、多台机器上的副本由谁来续、一次调用中途失效落哪种收场——
归 MCP 桥接契约与它的提供者设计。

#### Connector

**一个外部消息来源的接入件**，把外部的消息送进来。

> **它是唯一方向朝里的一类。**Skill、Tool、MCP、Slash Command、Plugin、Agent Definition
> 回答「agent **能做什么、怎么做**」，[Loop Extension](#loop-extension) 回答
> 「**推进的时候在哪些位置插手**」，**只有它回答「agent 从哪里被触达」**。

| | |
|---|---|
| **身份** | **name**。用什么协议、凭据长什么形状、接的是对面哪个账号**都不是**；它声明的[事件目录](#事件目录与事件订阅)也不是——换一份实现，目录可以不同 |
| **和 Tool 的区别** | **方向相反**。Tool 是 agent 发起动作往外走，Connector 是外部消息往里送 |
| **和 MCP 的区别** | MCP 是**我出去调它**，Connector 是**它进来找我**。两者都指向系统之外，方向不同 |
| **它能做什么** | **只能送消息进来。**没有数据读取面，也没有管理面——接进来的东西不因此获得读取本系统数据或改变本系统配置的资格。**它送进来的事件可以开出一个新会话**（[② 那一路](#两种投递方式动作主体不同)），但进哪个会话、开不开新会话、以谁的身份、按什么运行模式，**外部内容一样都选不了**：它说得出的只有自己是目录里的哪一种 |
| **它声明什么** | 一份[事件目录](#事件目录与事件订阅)：它会送进来的每一种外部事件 |
| **它带身份鉴权** | 连接件是**以对面服务的某一个账号**接进来的。**接的是对面哪个账号（鉴权绑定），是持有上的一项[落点与身份类](#设置项分四类资产声明每一项时必须标类别)设置**——同一个人在两个租户下各配各的，**接的可以是对面两个不同的账号**。**鉴权绑定只在租户那一层配，组织那一层不配**——与 [MCP 凭据](#mcp-凭据一份持有一份静态的或经-oauth-取得的)同一条理由 |
| **自带的属性** | 设置：来源标识、[投递目标](../../ubiquitous_language/terms/interaction-and-dispatch.md#ul-inbound-target--投递目标--inbound-target)、**鉴权绑定**、**[事件订阅](../../ubiquitous_language/terms/capabilities-and-composition.md#ul-event-subscription--事件订阅--event-subscription)**、**[触发会话的默认运行模式](#触发会话的默认运行模式)**。权限：**能不能安装**——取值与其余「谁可以……」[同一种](#谁可以使用它是各类资产共用的一项权限)：一组租户角色，外加一个「自己」 |
| **送进来的消息以谁的身份处理** | **不是一项权限，是一条固定规则**：消息落进哪个会话，**就按那个会话[创建那一刻捕获的租户身份](../PF-015-session-lifecycle-and-ownership/design.md#612-会话持有创建那一刻的租户身份)处理**；对面那个账号**只作来源留在消息上**，不成为任何人的身份。两种投递方式都照这一条 |
| **能组合什么** | **不组合任何资产。** |

**送进来的消息以谁的身份处理，为什么是一条规则而不是一项可配的权限**：
能配，就有人会把它配成「以对面那个账号的身份」——**外部来源就能借连接件，以一个本系统不认识的名义让 agent 做事**，
而放行、成本、隔离都挂在租户身份上，对面的账号哪一样都接不住。
会话本来就持有创建那一刻的租户身份，消息落进它，就只有这一个身份说得通；**只有一个答案，就不该留一个开关**。

**一个人在对面有好几个账号，不另立对象。**鉴权绑定是一项[属性配值](#组织的设置是视图不是对象)，
挂在持有上、随持有生灭——**同一个人换一个租户身份，就是另一份持有、另一份配值**，
「这个租户身份接的是对面哪个账号」已经有地方放。
**同一个租户身份要同时接对面同一个服务的两个账号，就是两份 name 不同的连接件**：
[身份是「类别 ＋ name」](#身份是类别--name其余归实现)，同一身份在同一层只有一份持有、一份配值；
两份连接件用同一套实现完全可以，那本来就不参与身份。

**它为什么仍然是资产**：它在 agent definition 里被声明、被持有、被授权、
按层级求值——**这四件事才是资产之所以为资产的原因**，不是「它提供动作」。
这一条扩展了「组装」的含义，已如实记在
[PF-001 decisions 第四节](../PF-001-identity-scope-and-agent-constraints/decisions.md#四已知的来源问题)。

##### 事件目录与事件订阅

**连接件在正文里声明一份目录，列出它会送进来的每一种[连接件事件类型](../../ubiquitous_language/terms/capabilities-and-composition.md#ul-connector-event-type--连接件事件类型--connector-event-type)：一个类型名、一段说明、一个消息包形状。**
目录是结构化的，不是一段自由文本。

| | |
|---|---|
| **每条送进来的外部消息** | **恰属目录里的一种。**不在目录里的，受理时拒绝，**拒得看得见**——不是静默丢掉 |
| **[事件订阅](../../ubiquitous_language/terms/capabilities-and-composition.md#ul-event-subscription--事件订阅--event-subscription)** | 持有上的一项设置，取值是目录的一个子集：**这份持有要目录里的哪几种**。作者可以给默认值；**组织层与租户层各配各的**。没订阅的那几种送进来，同样在受理时拒绝、看得见 |
| **agent 能不能改订阅** | **不能。**订阅是持有它的那几层配的值，不是 agent 在运行时做的一个动作 |
| **说明给谁读** | **给模型读。**组合了这份连接件的 agent，上下文里带着**被订阅的那几种**的说明——事先就知道会来什么、各是什么意思。**怎么带归 [PF-010 上下文组装](../PF-010-context-management-and-assembly/README.md)**，本 topic 只定「带」，而且只带订阅了的 |
| **消息包随信封整份进来** | 本版只支持**厚信封**：这一种事件要交代的内容全在这条消息里。连接件[没有读取面](#connector)，接收方无处回拉，所以**不支持「只送一个标识、回头去拉」**（[§2 非目标](#非目标)） |

**为什么目录要结构化**：说明是给模型读的，形状是给受理对的。只有一段自由文本，受理那一侧就没有东西可对——
一条形状不对的消息只能交给模型去猜，猜错了不会报错。**结构化之后，「这一条是不是它声明过的那一种」在进门时就答得出**，答不出就拒。

**为什么只带订阅了的说明**：没订阅的那几种根本进不来。把它们的说明也交给 agent，它会去等一种永远不会来的消息，
或者把收进来的一条认成没订阅的那一种。

**为什么 agent 不能自己订阅**：订阅决定了外面有什么能找上这个 agent，甚至开出一个新会话、替它花钱。
**让 agent 自己加订阅，就是被触发的那一方决定谁能触发它。**

**为什么事件订阅只在组织、租户两层有值**：一条消息收不收，在它落进任何一个会话之前就要判（[② 那一路](#两种投递方式动作主体不同)此刻连会话都还没有）；
而 agent 上下文里带的说明，必须与真正收得进来的那几种对得上。**所以这一项在持有那一侧求值**，工作区与会话那两级没有它的值。

##### 两种投递方式，动作主体不同

**外部的事进到会话里，有两条路。两条路的差别不在消息本身，在于是谁在做这件事：**

| | **① 已有的会话开口接收** | **② 连接件的事件开一个新会话** |
|---|---|---|
| **动作主体** | **会话**：一个已经存在的会话，在自己里面开口，接收这份连接件的投递 | **连接件**：它送来的事件经受理开出一个新会话，落进去，触发那个会话的第一次运行 |
| **本 topic 这一侧的配置** | [投递目标](../../ubiquitous_language/terms/interaction-and-dispatch.md#ul-inbound-target--投递目标--inbound-target)：持有上的一项落点与身份类设置，**送进哪一个已有的会话** | [触发会话的默认运行模式](#触发会话的默认运行模式) |
| **消息以谁的身份处理** | 那个会话创建时捕获的租户身份 | 同一条规则：那个新会话创建时捕获的租户身份 |
| **还缺什么、归谁** | 会话怎么开口、怎么关，一份连接件能不能同时给几个会话开口——**归会话那一块**（[PF-015](../PF-015-session-lifecycle-and-ownership/README.md)） | **新会话以哪个 agent definition、哪个租户身份建**——归会话那一块（[PF-015](../PF-015-session-lifecycle-and-ownership/README.md)）；受理怎么开这个新会话、同一件事来两次怎么办——归 [PF-014](../PF-014-inbound-intake-and-queueing/README.md)。见 [§九](#九未决项) |

**为什么是两条路，不是一条**：已有的会话要不要收外面的事，是会话在做决定——它知道自己正在干什么、收进来的东西会插进哪段协作；
连接件自己的事件要不要起一段新的协作，是连接件这一侧的事——它是那个动作的主体。**并成一条，就得让连接件替一个已有的会话决定收什么，
或者让一个已有的会话替每一件外面的事开工**——哪一边都越了权。

**两条路都不给外部内容选择权**：进哪个会话、开不开新会话、以谁的身份、按什么运行模式，
要么是持有这份连接件的那几层配的，要么是会话自己定的。**外部内容只说得出自己是目录里的哪一种。**

**同一份连接件送来的一条事件走哪一路，由什么决定，还没有定**——见 [§九](#九未决项)。

##### 触发会话的默认运行模式

**持有上的一项设置：这份连接件的事件开出来的新会话，起步时是哪一档[会话运行模式](../../ubiquitous_language/terms/agent-runtime-loop.md#ul-session-run-mode--会话运行模式--session-run-mode)**——
`never`、`auto_permission`、`bypass-permissions` 三档之一。

| | |
|---|---|
| **必须给** | **配置连接件的人必须给这一项。**哪一层都没给过的连接件，**它的事件开不出新会话**，受理时明说缺的是这一项——系统不替它挑一个值，**作者声明的默认也不算数** |
| **谁能调** | 配置它的人——租户——可以调；组织在自己那一层给的值与加的锁，照[默认与强制](#54-默认与强制一个机制三处适用)那一套管着租户 |
| **类别** | **[治理](#设置项分四类资产声明每一项时必须标类别)**：它不改东西落在哪、以谁的名义，改的是这个新会话里**「本该问人」的那一刻怎么办**。**工作区配不了它** |
| **改了之后** | **只管此后开出来的新会话。**已经开出来的会话，运行模式是那个会话自己的 |
| **与 ① 那一路无关** | 已有的会话有自己的运行模式；这一项没给，① 那一路照常 |

**为什么非给不可**：连接件开出来的会话，多半**没有人在旁边看着**。放行判断走到「本该问人」的那一刻，
这个会话是一律当被拒、拿已有的授权算、算不出再问人，还是直接放行——**必须有人事先想过**。
给一个出厂默认，就是替每一份连接件做了这个决定：往严里给，它开出来的会话什么都做不成，人还不知道为什么；
往松里给，一个外部来源就能在没人看着的时候让 agent 放手去做。**作者的默认不算**，
因为作者不是那个要为这份连接件在这个组织里跑起来负责的人——**要负责的是配置它的那个人，所以由他给**。

**它的运行模式为什么不跟着外部内容走**：外部内容若能说「这一次按 `bypass-permissions` 跑」，它就替人决定了放行——
与[送进来的消息以谁的身份处理](#connector)是同一件事的另一面。**运行模式只能来自持有上配的这一项。**

#### Loop Extension

**挂在 agent 推进过程某个位置上的一段判断或动作。**

它声明三件事：**挂在哪个位置**、**管哪些情形**、以及自己的**干预力**——
只观察 / 可改写 / 可否决。一共有哪些位置、每个位置上看得见什么改得动什么，
归 [PF-012 §5.8](../PF-012-agent-loop-and-run/design.md#58-loop-拓展点)，本 topic 不重复。

**agent 不知道它存在。**这是它与其余各类最要紧的分别：skill 是给 agent 读的，
tool 是 agent 自己决定要不要调的，而拓展件是**系统在固定位置替 agent 调的**——
装了它，agent 面前的工具条目不会多出一条。

| | |
|---|---|
| **身份** | **name**。挂在哪个位置、看得见什么改得动什么**都不是**（位置不是能力标识，见下） |
| **和 Tool 的区别** | Tool 由 **agent 自己决定**要不要调；拓展件由**系统在固定位置调**，agent 不知情，也拦不住 |
| **和 Skill 的区别** | Skill 是**给 agent 看的方法**，它读了才起作用；拓展件是**不给 agent 看的判断**，它不读也起作用 |
| **和 Connector 的区别** | 两者都不回答「能做什么」。Connector 回答「**从哪里被触达**」，拓展件回答「**推进的时候，在哪些位置插手**」 |
| **位置不是能力标识** | **同一个位置可以挂多个拓展件，各干各的**——它们是不同的资产，彼此不构成[同标识覆盖](../PF-001-identity-scope-and-agent-constraints/design.md#62-三种合成语义)。覆盖只发生在**同一个拓展件**的不同版本之间 |
| **同一个位置上几件的先后** | **就是它们在[装配清单](../PF-004-agent-definition-and-assembly/design.md#装配清单)里的顺序。**几件在同一个位置上[依次过](../PF-012-agent-loop-and-run/design.md#三种形态两种装得进一种拆两半)，后一件看得到前一件的结论——所以先后要有一个说得出来的来处，**而装配清单本来就是「这个 agent 由什么、按什么样子构成」的那一份记录** |
| **自带的属性** | 设置：挂在哪个位置、管哪些情形，以及它自己的配置（比如[默认的重试件](../PF-013-model-profiles-and-invocation/design.md#512-重试站在一个已经存在的位置上)**退避多久再试**）。权限：**干预力**（只观察 / 可改写 / 可否决），以及谁可以安装它。另有注册时声明的**[拓展件不可用处置](../../ubiquitous_language/terms/agent-runtime-loop.md#ul-extension-unavailability-policy--拓展件不可用处置--extension-unavailability-policy)**——**它是这一件自己的一项声明，不是设置，也不是权限**，各层不给它配值（[见下](#不可用处置是这一件自己的声明)）；取值与谁能用哪一种归 [PF-012](../PF-012-agent-loop-and-run/design.md#拓展件是可插拔的服务不可用即卸载报错按策略) |
| **能组合什么** | **不组合任何资产**（同 MCP 与 Connector） |

**干预力是权限，不是设置。**所以它走[收窄](#53-两个例子两种合成)那一套：
组织若把某个拓展件的干预力**锁**在「只观察」，租户就放不宽；组织只给默认值而不锁，
租户可以自己调。**装一个拓展件、却只给它「只观察」，是成立的配法**——
它照样每次都被调到，只是改不动东西。

**干预力只有这三档，[没有「放宽」这一档](../PF-012-agent-loop-and-run/design.md#没有放宽这一档)。**拓展件不能把一次本该「问一下」的动作变成放行——
要让它自动过，去把那项[执行权限](#tool)配成「自动」；放行权留在权限上，不交给挂件。

**从别的 harness 导入的挂件，按它声明的输出能力定干预力。**
Claude Code、Codex 格式的 hook 可以导入成拓展件；它能产出什么，就声明到哪一档，各层再照常收窄：

| 它能产出的 | 导入后声明的干预力 |
|---|---|
| 否决或阻断（`deny`、`block`） | **可否决** |
| 改写输入、追加上下文（`updatedInput`、`additionalContext`） | **可改写** |
| 其余 | **只观察** |

**它的「放行」（`allow`）导入后译成「无意见」，并在导入时明示**——理由就是上面那条：没有「放宽」这一档。
**工作区带来的挂件，不管声明到哪一档，一律只观察**——[工作区提供的资产，权限项取最严值](#57-工作区那一级不参与权限计算)。

**它为什么是资产**：与 [Connector 同一个理由](#connector)——它在 agent definition 里
被声明、被持有、被授权、按层级求值。**这是对资产定义的第二次扩展**，
来龙去脉记在 [PF-001 §4「资产的种类」](../PF-001-identity-scope-and-agent-constraints/design.md#资产的种类)末尾
「关于 Loop Extension」那一段。

> **组织超管在组织层配一份，租户在自己那层覆盖或收窄**，走的就是本 topic 已有的那一套。
> **「让用户能扩展或覆盖策略」不需要另造一套配置与授权**——这正是把它做成资产换来的东西。

##### 不可用处置是这一件自己的声明

**[拓展件不可用处置](../../ubiquitous_language/terms/agent-runtime-loop.md#ul-extension-unavailability-policy--拓展件不可用处置--extension-unavailability-policy)写在这件拓展件的定义里，与工具定义里[「能不能在后台执行」](../PF-006-tools-and-skills/design.md#其中两项声明的是设置项)是同一种东西：作者的一项声明。**
它不是四类设置里的任何一类，也不是权限——**持有它的各层都不给它配值，也收窄不了它。**

**为什么**：它说的是**这一件是一道什么样的关**——依赖不在的时候，放过还是拦住。
允许各层配值，同一件拓展件在组织里是一道硬关、在租户里是一道软关，**同一份资产在两层成了两件事**——
那是[同标识替换](#55-资产替换的层级)的活，已经有一条路；与[斜杠命令的绑定目标不是设置](#slash-command)同一个理由。
读成权限也不对：权限收窄的是**这一件在的时候能做什么**，而这一项管的是它**不在的时候**怎么办。

**后果**：

- **组织要一道「不在就不许跑」的关，挂自己的一件、注册时声明为否决。**它改不了租户挂上的那一件，租户也改不了它的；
  租户换上同名的一份声明为跳过，组织要拦住，就[把替换本身锁住](#替换是一条路径不是一扇后门)。
- **声明了否决，也要干预力求出来是可否决才算数。**[干预力被收窄到另两档的，不在时照跳过办](../PF-012-agent-loop-and-run/design.md#拓展件是可插拔的服务不可用即卸载报错按策略)——
  所以工作区带来的挂件（一律只观察）声明什么都等于跳过，[不在就比在多一份权力](../PF-012-agent-loop-and-run/design.md#拓展件是可插拔的服务不可用即卸载报错按策略)的事不会发生。

#### Slash Command

**用户主动发起某件事的入口。**用户在[交付面](../../ubiquitous_language/terms/interaction-and-dispatch.md#ul-delivery-surface--交付面--delivery-surface)上敲 `/什么` 触发。

它**绑定**要做的事，命令本身不是做事的东西，它是**指路牌**。**绑定目标恰有三种：**

| 绑定目标 | 敲下去之后 | 是不是内容 |
|---|---|---|
| **① 一段自定义提示词** | 命令**自带的那段提示词正文**（带上参数）成为用户这条消息的内容 | **是**——进[待处理消息队列](../PF-012-agent-loop-and-run/design.md#待处理消息队列)，agent 看得到 |
| **② 装配里的一个 skill** | 那个 skill 的**正文逐字成为用户这条消息里的一个内容块**；人附带的参数**另成一个内容块**，不拼进正文 | **是**——同上 |
| **③ 一条系统业务流程** | 触发系统里**某个命令服务或查询服务的一个动作**（压缩这个会话的上下文、列出后台在跑的执行、展示会话的待办……）。**不进队列，不成为消息**，会话日志里只留一条记它发生过的条目 | **不是**——agent 看不到它 |

**③ 的流程清单由系统提供**，本版**不开放组织或租户自己创作**（[§2 非目标](#非目标)）。
**本版点名 [reload 一族](#会话认得哪些命令什么时候变)**；其余不枚举，任何一条都不设计实现。
三种在受理时各怎么走，归
[PF-014](../PF-014-inbound-intake-and-queueing/design.md#510-斜杠命令在受理时分两路走)。

**它不含键盘控制与 shell 命令。**键盘控制是[发出一条控制指令的一种敲法](../PF-014-inbound-intake-and-queueing/design.md#控制指令)，
shell 命令是交给执行环境的动作——不因为都叫「命令」就归成一类。

| | |
|---|---|
| **身份** | **命令名**。绑定目标、参数**都不是** |
| **只有人用它** | 斜杠命令是**人的入口**。**只有经交付面送进来的输入才被识别成命令**——人读、机读两种[呈现形式](../../ubiquitous_language/terms/interaction-and-dispatch.md#ul-presentation-form--呈现形式--presentation-form)一样，脚本驱动交付面[做得了人能做的一切](../PF-016-cli-tui-delivery-surface/design.md#65-人能做的脚本能做脚本能做的人能做)；连接件以及其他不经交付面的来源送进来的 `/xxx`，原样是内容。**模型不调用它**——agent 要方法走 [`Skills()`](../PF-007-meta-capabilities/design.md#62-skills通向任意技能)，要动作走 [`Tools()`](../PF-007-meta-capabilities/design.md#61-tools通向任意非常驻工具) |
| **为什么单独是一类资产** | **为将来的可编程性留一个口子**——让「敲一个名字，触发一件事」这层绑定本身可以被持有、替换与治理，而不是写死在交付面里 |
| **为什么不并进 Skill** | 同一个 skill 可以有多个入口，也可以完全没有入口（只由 agent 自主使用）；① 与 ③ 根本不指向 skill。合并会丢掉这两层 |
| **名字与撞名** | **交付面自己的动作名与 ③ 型命令名是系统保留名，一律在 `omne-official` 前缀下**；**① ② 型的名字不得使用这个前缀**，发布时带了就被拒——**官方提供的 ① ② 型也一样**，它们照 [§5.5](#55-资产替换的层级) 可以被替换，保留名不能。分隔符与拼法归规格。**保留名只认前缀，不认清单**：系统将来再添多少流程与交付面动作，都撞不上已经发布的 ① ② 型。① ② 型之间同名就是同一身份，按 [§5.5](#55-资产替换的层级) 替换 |
| **它由什么构成** | **绑定目标**，与可选的**参数声明**（每个参数带一句给人看的提示）——**这是这份命令本身，不是设置**，不随持有它的那一层配出不同的值。**声明了参数的，按声明解析**——像命令行程序解析它的参数那样；**解析不通过，当场明说哪里不对、不发送**（[PF-016 §5.7](../PF-016-cli-tui-delivery-surface/design.md#57-人要做的事分三族)），① ② ③ 型一条规则。没声明的，命令名之后的整段文本作一个自由参数 |
| **自带的属性** | 设置：本版没有。权限：**谁可以用这个入口——只对人**；**没有权限，就等于没有这条命令**（见下） |
| **能组合什么** | **Skill**（② 型的绑定）。① 带的是自己的正文，③ 指向的是系统流程——**两者都不是资产，不进组合图**。绑定不转移所有权——命令能指向一个 skill，不代表它拥有那个 skill |

**② 型展开的那个 skill，照样要过它自己的「谁可以使用它」。**入口的权限只管「谁能敲这个命令」，
不替那份 skill 放权；否则一个命令就成了绕开 skill 权限的后门。

**绑定目标与参数声明为什么不是设置**：它们说的是**这条命令是什么**。允许各层给它们配值，
同一个命令名就会在组织里展开一段话、在租户里展开另一段——**同一份资产在两层成了两件事**。
那正是[同标识替换](#55-资产替换的层级)要表达的，已经有一条路；**设置是在同一件事上调口味**，不是换一件事。

##### 会话认得哪些命令，什么时候变

**一个会话认得哪些斜杠命令，是它的[会话斜杠命令集](../../ubiquitous_language/terms/capabilities-and-composition.md#ul-session-slash-command-set--会话斜杠命令集--session-slash-command-set)。**
它在[装配](../PF-004-agent-definition-and-assembly/design.md#装配)时定下：会话创建时的那次装配，
只把会话所属的那个人（[创建那一刻捕获的租户身份](../PF-015-session-lifecycle-and-ownership/design.md#612-会话持有创建那一刻的租户身份)）**有权使用的**斜杠命令装进来。

| | |
|---|---|
| **没有权限，就等于不存在** | 无权使用的命令**不装配、不可见**。人在交付面上敲它，后果与敲一个根本没有的名字**完全相同**：当场明说「没有这个命令」、不发送（[PF-016 §5.7](../PF-016-cli-tui-delivery-surface/design.md#57-人要做的事分三族)）。**没有「你不能用」这第二种失败**，也不会把它当一句普通的话送进会话。会话进行中被收回了权限的，**此刻起同样不存在**；反过来，进行中新得到权限的，要等下一次 reload 或重新装配才出现 |
| **① ② 型的增删与禁用，不会自己改变进行中的会话** | 组织或租户加入、移除、禁用了一条 ① ② 型命令，已经开着的会话认得的**还是原来那一批**。要让它在这个会话里生效，人发对应的那条 **reload** |
| **③ 型背后的服务不在了：执行时报错，之后自动不再可见** | ③ 型是交给一项系统服务去办的事。会话进行中那项服务不在了或拒绝了，敲下去就是**那项服务明说的一次失败**，会话日志里那条记它发生过的条目照样记下结果；**随后系统自动刷新这个会话的命令注册表**，那条命令从此不在它的命令集里 |
| **reload 一族：动态热更新，各刷各的注册表** | **本版点名的唯一一族 ③ 型流程**，名字都在 `omne-official` 前缀下，一族里有哪几条、拼法归规格。会话认得的命令、装进来的技能、plugin 这类东西，各自住在一张**注册表**里（会话或运行时的一项服务），用到它们的地方都经注册表取；一条 reload **只按此刻的求值结果重填它对应的那一张**——就像别家的 reload-skills、reload-plugins——这期间那一类资产的增删与禁用、工作区实例或地址上的对应资源改动，都在这一次进来。**它不是一次完整的重新装配**，不动别的注册表，也不改写正在跑的运行已经捕获的构成（[PF-004 §6.3](../PF-004-agent-definition-and-assembly/design.md#63-三类变化三种传播)）；一次完整的重新装配本来就会把全部注册表重填一遍 |

**为什么 ① ② 型的变化要等人发 reload**：斜杠命令不进系统提示词，
按 [PF-004 那条判据](../PF-004-agent-definition-and-assembly/design.md#三类变化背后只有一条判据系统提示词的成分会不会变)它的增删本来就不触发重新装配；
而让命令集在人不知情时自己变，人敲下同一个名字，这一次展开的和上一次就可能不是同一段话。
**等人发 reload，变化发生在人自己选的那一刻。**命令注册表只在三种时刻换内容：会话创建时装配填充、人发对应的 reload、③ 型失败后系统自动刷新；一次完整的重新装配也会重填它。

**为什么权限收回不等 reload**：权限从来都是[下一次使用时就按新值判](../PF-004-agent-definition-and-assembly/design.md#65-权限变化动作空间不变)。
命令注册表若要等 reload 才去掉被收回的那条，这个人在此之前照样敲得出、展开得了——**收回的权限成了空话**。

**为什么 ③ 型不等 reload**：它的消失不是谁对资产做的一个决定，是系统那一侧的一个事实——
没有「人选在哪一刻生效」这回事；留着这条命令，只会让人一再敲出同一个失败。

#### Plugin

**把若干资产打包在一起分发与启用的单元。**

装一个 plugin，等于一次性获得它里面的全部东西；停用它，那些东西一起退场。
它解决的是**分发**问题：作者不必让用户逐个安装十几件东西。

| | |
|---|---|
| **身份** | **name**。它包了哪些能力标识**不是**——换一份实现，包里那批可以整批换掉 |
| **和 Agent Definition 的区别** | Plugin 组合出来的**还是资产**，可以继续被组合；Agent Definition 组合出来的是**一个能跑的 agent** |
| **内含成员的地位** | 随 Plugin 的版本与使用权一起治理。它们**不取得独立的顶层生命周期**——你不能单独卸载 plugin 里的某一个 skill |
| **自带的属性** | 设置：启用哪些成员（**唯一一项会改组合的设置**，[组装展开到它时就地求值](#56-四步资产求值--组装--投影--层级计算)）、成员的默认配置。权限：谁可以启用它 |
| **能组合什么** | **Skill、Tool、Slash Command、MCP、Connector、Loop Extension**，以及 Rules 这类声明性成员 |

#### Agent Definition

**一个 agent 的静态定义**：它由什么组装而成、以什么面貌工作。

**它不是会话，也不是 agent runtime 。**改定义不会改变已经在跑的那个 agent；
一个定义可以同时有很多个 agent runtime 。**定义与实例分别演进**，这条很要紧——
把它们混为一谈，就会出现「我改了配置，正在跑的任务突然换了行为」这种事故。

| | |
|---|---|
| **身份** | **name**。默认模型、人格与语气、它组合了哪些资产**都不是** |
| **sub-agent 的定义** | **也属于这一类**，不是另一种东西。它作为 sub-agent 被引用时是被组合方，被实例化时是组合树的根 |
| **自带的属性** | 设置：**默认模型**、人格与语气、上下文策略、**模型调用的两个时限**（发出之后多久等不到首个 token、开口之后多久没有新内容就算断了——[为什么挂在这里](../PF-013-model-profiles-and-invocation/design.md#617-本-topic-不出现任何时限数值)）等。权限：谁可以实例化它、谁可以派发它 |
| **能组合什么** | **全部八类**——Skill、Tool、Slash Command、Plugin、**MCP**、**Connector**、**Loop Extension**，以及**其他 Agent Definition**（作为 sub-agent） |

| 组合方 ↓ ／ 被组合 → | Skill | Tool | Slash Command | Plugin | MCP | Connector | Loop Extension | Agent Definition |
|---|:---:|:---:|:---:|:---:|:---:|:---:|:---:|:---:|
| **Skill** | ✗ | ✓ | ✗ | ✗ | ✗ | ✗ | ✗ | ✗ |
| **Tool** | ✓ | ✗ | ✗ | ✗ | ✗ | ✗ | ✗ | ✗ |
| **Slash Command** | ✓ | ✗ | ✗ | ✗ | ✗ | ✗ | ✗ | ✗ |
| **Plugin** | ✓ | ✓ | ✓ | ✗ | ✓ | ✓ | ✓ | ✗ |
| **MCP** | ✗ | ✗ | ✗ | ✗ | ✗ | ✗ | ✗ | ✗ |
| **Connector** | ✗ | ✗ | ✗ | ✗ | ✗ | ✗ | ✗ | ✗ |
| **Loop Extension** | ✗ | ✗ | ✗ | ✗ | ✗ | ✗ | ✗ | ✗ |
| **Agent Definition** | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ |

**只有 Agent Definition 能组合全部八类**，因为只有它是组装成 agent 的那个入口。

**三行全空，但理由是两种：**

| 哪几行 | 为什么空 |
|---|---|
| **MCP、Connector** | 它们的内容来自**系统之外**，由对端决定，不是本系统的组合关系。把对端的东西当成组合成员，就等于承诺本系统掌握它们的身份与生命周期——而那件事本系统做不到 |
| **Loop Extension** | 它是**一段自足的判断**，起作用靠的是被挂在那个位置上，不靠调用别的资产。真需要一个动作，那个动作属于它自己的实现，**不是它组合了一个 Tool**——否则 agent 面前的工具条目会凭空多出来 |

三条规则：

1. **引用指向能力标识，不指向具体资产**（见 §6.3）。因此覆盖发生后，
   所有引用自动指向当前生效的那一个。
2. **组合图不得成环——环指的是展开不完的那一种。**Agent Definition 之间可以嵌套 sub-agent，
   但 A 引用 B、B 又引用 A 必须被拒绝：**每一层 sub-agent 都是又一份要组装的 agent**，沿着这个环往下，组装永远算不完。
   **[Skill 与 Tool 互相引用](#51-组合是一种关系不是几种)不算环**：它们声明的是「我要配着它用」，
   组装时两边各放进这一次的构成里一份就完，再引用一次也不会多出第二份——**这张表允许的这种互引，不是要拒绝的那种环**。
3. **组合不转移所有权。**Plugin 里装了某个 skill，不代表 plugin 作者拥有它。

### 几个刻意不做的组合

| 不做 | 为什么 |
|---|---|
| Skill 组合 Skill | 目前**没有已知需要**，而允许它就要引入环检测与"哪一层的指引优先"这类问题。按最小正确模型，等真实需求出现再加 |
| Plugin 嵌套 Plugin | 同上。嵌套会让「内含成员随 plugin 版本治理」变成多层，版本与使用权都要跨层解释 |
| Plugin 含 Agent Definition | 分发一个现成的 agent 是个合理设想，但目前没有需要。留着不做，比先做一个没人用的结构安全 |

> 以上三条是 **PM 按「先做最小的正确模型」推的**，不是产品负责人裁决。
> 真实需求出现时可以加——**加是加法，不用改已有结构**。

### Tool 为什么是资产

值得单独说一句，因为这一条**与前身系统相反**。

`omne-next/omne_harness` 把 Tool 归为"组件"而不是顶层资产。
原因不是它不该是资产，而是**那个系统做不到工具的动态组装**。
本系统能做到，所以 Tool 是**可动态组装的资产之一**。

这条差异是有意的。见 [decisions.md 第四节](decisions.md#四已知的来源问题)。

### Plugin 不是 Cordis plugin

本项目内核用 Cordis，Cordis 也有 plugin 的概念。两者**完全不是一回事**：

| | Cordis plugin | 本 topic 的 Plugin |
|---|---|---|
| 是什么 | 运行时的代码装载单元 | 产品意义上的资产分发与组合单元 |
| 谁关心 | 实现与运行时 | 产品的使用者与管理者 |
| 归哪 | 技术设计 | 产品设计 |

**正文出现「Plugin」一律指后者。**指前者时必须写全「Cordis plugin」。

### 工作区

**工作区资产层**是租户之下的一级资产归属和配值来源。工作区本体、工作区实例和工作区地址的完整产品定义见 [PF-020](../PF-020-workspace/README.md)；本节只定义工作区资源如何进入本 topic 的资产求值。

工作区实例可以提供组织、租户能持有的八类资产以及相应配值，但权限、落点与身份类设置和治理类例外仍按本 topic 过滤。工作区层不是 PF-001 的第五个作用域身份层；它只在设置和资产归属两条求值路径上占一格。

#### 工作区不是目录

**目录只是工作区地址或实例的本地承载，不是工作区本体。**工作区也可以通过 GitHub、云端或其他地址被访问；地址不是身份、不是凭据，也不是宿主机安全边界。工作区实例在本地是否能读写某个资源，仍由 [PF-005](../PF-005-execution-environments-and-sandboxes/README.md) 和具体命令权限决定。

#### 它挂在租户下

工作区有一个治理所有者租户，也可授权其他租户参与；其共享资源可由有效关系授权访问，私有内容仍按租户隔离。
本节“挂在租户下”指会话按其所属租户求值工作区资产层，不表示同一工作区只能被一个租户使用。
两个租户通过同一字符串地址访问，不自动产生授权；参与开发、维护与写入还受 [PF-020 的组织参与限制](../PF-020-workspace/design.md#组织对参与范围的限制)约束。该限制不拦已有资格的只读访问。

#### 它是会话选用的，不指定就是空

会话创建或恢复时必须明确选择一个工作区，或选择一个可解析为工作区实例的地址。未选择工作区时，工作区这一层为空；agent 恰好运行在某个当前目录，不会隐式附着工作区。交付面可以提出默认值，但提交给会话的仍是显式选择。

#### 挂上之后，它的内容在装配时自动进来

会话装配时，系统从选定且可访问的工作区实例取得工作区资源，把其中允许的资产与配值作为本层求值输入；不要求另做一次手工导入。
实例目录下两个同结构的发现入口由 [PF-020](../PF-020-workspace/design.md#两个约定目录)规定：`.omne` 提供工作区共享内容，`.omne.local` 提供实例本地内容，不进入工作区共享同步；实例可跨租户共用，两个来源按各会话租户身份分别求值，而非固定归属某一租户；两者可用内容取并集，同能力资产 local 优先。
具体地址解析、目录内部文件格式、同步和失败恢复不在本 topic 定义。

**两个目录是工作区层的两个来源，不是两个新的归属层。**并集不使本层同能力标识同时有两份生效资产。同能力沿用“类别 ＋ name”，在本层内部按先禁用过滤、再使用资格过滤、最后同标识择取的顺序求值；可用的 local 候选优先于共享候选，不影响不同能力的并集。
被过滤的 local 候选不遮蔽可用的共享候选，上层锁定仍能阻止整个工作区层的替换。替换不把共享资产的配值或凭据迁移到 local 实现，继续遵循“权限的界跟身份走、设置的值跟资产走”。
两个目录中的配值都按工作区来源过滤；同一设置项与规范文本在两目录冲突时，遵循 [PF-020 的目录合并规则](../PF-020-workspace/design.md#目录的合并与作用域)，不能自行把资产替换扩展为逐字段合并。
装配输入必须使用当前会话租户的组织、租户配置与其自己的本地目录，不读取其他参与者的 local 内容或私有凭据。

**它在三条层序各站各的位置**，见 [§5.8](#58-三条层序各答一个问题)：设置压过租户，同能力标识的资产替换租户的，权限一概不从工作区来。工作区提供的资产，其权限取最严值；工作区的禁用值只对它自己提供的资产生效。

## 五、模型

### 5.1 组合是一种关系，不是几种

> **本节是 PM 推导，待产品负责人确认。**推理链见 [decisions.md](decisions.md)。

产品负责人给出的三个判断：

1. 资产之间是**组合关系**；
2. 资产组装成 agent，**本质上也是组合关系**；
3. 设置与某一类资产、权限与某一类资产，**本质上也是组合关系**。

三句话里的"本质上也是"都在说同一件事：**这些不是几种机制，是一种。**

```text
Agent Definition ──→ Plugin ──→ Skill  ⇄  Tool
       │               ├──→ Tool          ↑
       │               ├──→ Slash Command ┘（绑定 Skill）
       │               ├──→ MCP
       │               ├──→ Connector
       │               └──→ Loop Extension
       ├──→ Skill
       ├──→ Tool
       ├──→ Slash Command
       ├──→ MCP
       ├──→ Connector
       ├──→ Loop Extension
       └──→ Agent Definition        （sub-agent）

任一资产 ──→ 它的设置属性
         └─→ 它的权限属性
```

- **Agent Definition** 是唯一能组合全部八类的节点，因为只有它组装出 agent。
  被**实例化**时产生一个运行中的 agent，被**引用**时充当 sub-agent——
  所以它既能组合别人，也能被组合。
- **Plugin** 组合出来的**还是资产**，可以继续被组合。
- **Skill 与 Tool 互相引用**：skill 声明它要用到哪些动作，tool 声明它需要配套的指引。
- **MCP、Connector、Loop Extension 都是叶子**，一个都不往下组合，理由见 [§4](#谁能组合谁)。
- 完整的组合能力见 [§4「谁能组合谁」](#谁能组合谁)。

由此，「组装」不是第二种机制——**组装就是组合关系从一个 Agent Definition 展开求值的结果**。

### 5.2 设置与权限是资产的两种属性

这是本 topic 与 PF-001 相比最实质的一步：
**设置和权限不是一份预先存在的字段目录——它们是具体资产的两种属性。**

一个具体的资产（比如某个工具）自带这两种属性：

| 属性 | 举例 |
|---|---|
| **设置** | 某个 Agent Definition 的「默认模型」 |
| **权限** | 某个 Tool 的「执行权限」：问一下 / 自动 / 禁止 |

于是"谁的设置"这个问题不存在了——**设置总是某个资产的设置**。

#### 三方分工：资产定形状，各层配值，运行时求值

| 角色 | 谁 | 负责什么 |
|---|---|---|
| **定形状** | 资产本身 | 我有哪些设置项、哪些权限项，各自什么含义、取值域是什么。**权限项有哪几项由它的类别定**（[见下](#谁可以使用它是各类资产共用的一项权限)），资产给的是它们的默认值 |
| **配值** | **持有该资产的每一个归属层**——组织、租户、[工作区](#工作区)，各自一份 | 在我这一级，这些项配成什么 |
| **求值** | 运行时 | 沿[层序](#58-三条层序各答一个问题)覆盖 / 收窄，算出这次组装 agent 实际用的值 |

**配值的资格来自持有。**一个层要为某资产配设置或权限，前提是它
[持有](../PF-001-identity-scope-and-agent-constraints/design.md#拥有获权选用)该资产。
组织没有这个工具，就配不了这个工具的执行权限——**配置权不能凭空出现**。

#### 由此得到两个推论

**一、项的目录不需要单独维护。**"有哪些设置项"的答案 = "装了哪些资产"的函数：

- 没装工具 X，就不存在"工具 X 的执行权限"这一项；
- 没引用 agent definition D，就不存在"D 的默认模型"这一项。

**项的存在性由组装决定，所以生效值不可能在组装之前算出来。**

**二、出厂默认层是 official 带来的。**
[official 是最小必需](../PF-001-identity-scope-and-agent-constraints/design.md#来源official-与-customized)，
必然在每次组装里；**出厂默认层的设置与权限，就是 official 资产自带的那一份。**
出厂默认层不需要另一套来源。

#### 「组织的设置」是视图，不是对象

这是上面那条分工的直接后果，但值得单独说，因为它推翻了一个很自然的想法。

**系统里不存在"组织设置"这么一个对象。**真正存在的、可以被读写的最小单位叫
**[属性配值](../../ubiquitous_language/terms/scope-and-resolution.md#ul-attribute-assignment--属性配值--attribute-assignment)**：

```text
一份资产持有 × 一个属性项 → 一个值（可带 immutable）
```

**配值挂在[资产持有](../../ubiquitous_language/terms/circulation-and-entitlement.md#ul-asset-holding--资产持有--asset-holding)上**，
与[「禁用」那个开关同一个宿主](#禁用是逐层配的布尔设置任一层为真即不可见)——
它不是独立的一样东西，是那份持有身上的一项值。由此直接得到两条已经在用的规矩：
**持有没了，配的值跟着没**（[移除](#64-移除与禁用是两个动作)那一行说的就是这件事）；
**禁用只是把这份持有关起来，配的值一个不丢**。

我们平时说的「组织的设置」「租户的权限」，是**在该范围持有的资产集合上做的投影**：

```text
组织 O 的设置  ≝  { O 持有 X 上的属性配值 | X ∈ O 持有的资产 }
租户 T 的权限  ≝  { T 持有 X 上的属性配值 | X ∈ T 持有的资产 }
```

| | 「组织设置」 | **属性配值** |
|---|---|---|
| 是什么 | 一个**视图** | 一份持有上的**一项值**，真正被读写的就是它 |
| 能不能独立存在 | 不能。持有的资产变了，它跟着变 | 不能脱离那份持有——**持有没了它就没了** |
| 管理界面上的「组织设置页」 | 这个视图的呈现 | — |

**为什么这条要紧**：若把「组织设置」当成对象来实现，就会出现一份
独立于资产的字段表，然后它与资产各自演化，最终对不上。
视图不需要维护——**它是持有关系的函数**。

#### 设置项分四类，资产声明每一项时必须标类别

**设置项不都一样重。**有的改错了顶多难用；有的改了之后，**这次运行要过的那道权限门就换了**。
后一种若能从[工作区](#工作区)来，一个仓库就能在不触发任何确认的情况下改变这次运行落在哪里、以谁的名义——
那正是 [§5.7](#57-工作区那一级不参与权限计算) 要挡的同一件事，只是换了个入口。
所以**资产声明每一项设置时，必须标明它属于哪一类**（[设置项类别](../../ubiquitous_language/terms/capabilities-and-composition.md#ul-setting-category--设置项类别--setting-category)）；
类别决定这项值能从哪些层来。

| 类别 | 管什么 | 例子（取自[§4 各类资产](#八类资产)自带的设置） | 工作区能不能配 |
|---|---|---|---|
| **偏好** | 做得合不合口味；改错顶多难用 | 默认模型（仍受[合法目标集](../PF-013-model-profiles-and-invocation/design.md#510-合法目标集合与展示列表是两件事)约束）、人格与语气、上下文策略、超时（Tool 的[前台上限](../PF-006-tools-and-skills/design.md#前台上限与并发上限)，MCP 分连接与单次调用两项，Agent Definition 上模型调用的两个时限）、并发、转后台阈值、默认重试件的退避、Connector 的[事件订阅](#事件目录与事件订阅) | **能**（Connector 的事件订阅[只在持有那一侧求值](#事件目录与事件订阅)，工作区那一级本来就没有它的值） |
| **绑定** | 指向本系统内的另一份资产或一个位置 | 拓展件挂在哪个位置与管哪些情形、Plugin 启用哪些成员 | **能**，但只能指向它自己[求值后看得见](#56-四步资产求值--组装--投影--层级计算)的东西 |
| **落点与身份** | 东西在哪执行、连到哪、送到哪、以谁的名义、用哪把凭据 | Tool 的目标环境、MCP 的连接目标与凭据、Connector 的来源标识、投递目标与鉴权绑定 | **不能**——[加载时与权限一起过滤](#57-工作区那一级不参与权限计算) |
| **治理** | 管别的设置与权限怎么起作用 | [禁用](#禁用是逐层配的布尔设置任一层为真即不可见)、`immutable`、Connector 的[触发会话的默认运行模式](#触发会话的默认运行模式) | 禁用[只管它自己提供的那批](#禁用是逐层配的布尔设置任一层为真即不可见)；**`immutable` 与触发会话的默认运行模式不能配** |

**判一项新设置归哪类，只问一句**：这项值改了之后，会不会换掉这次运行要过的那道权限门，
或改变一道已放行的权限实际放出去的是什么。**会，就是落点与身份。**
例：租户把宿主机那个执行环境的权限配成「自动」，是冲着自己那几个工具配的；
仓库把另一个工具的目标环境改成宿主机，权限门不会响——**门没换，进门的东西换了**。
**改的若是那道门自己怎么判**——锁不锁得住、「本该问人」的那一刻是拒、是算、还是放——**就是治理**：
门还是那道门，进门的也还是那些东西，变的是它放不放行。**这两类都不从工作区来**，禁用只管它自己那批是唯一的例外。

**`immutable` 为什么不许工作区配**：设置那条层序上[会话在工作区之下](#58-三条层序各答一个问题)，
仓库一锁，用户自己会话级的设置就锁死了——与 §5.7「往严里改一样能伤人」是同一条理由。

**工作区自己带来的资产，它的落点类设置随资产一起来。**仓库提供一个 MCP 接入点，连接目标是那份资产的一部分，
不是在给别人的资产配值；这条限定挡的是**改别人资产的落点**。至于那份资产能不能动，
由它的权限项把门——而[工作区提供的资产，权限项一律取最严值](#57-工作区那一级不参与权限计算)。

#### 「谁可以使用它」是各类资产共用的一项权限

**每一类资产都有这一项，而且是同一项**——与[禁用](#禁用是逐层配的布尔设置任一层为真即不可见)一样挂在每一份持有上。
Skill 的「谁可以使用它」、Slash Command 的「谁可以用这个入口」，说的都是它。

| | |
|---|---|
| **取值** | **一组[租户角色](../PF-001-identity-scope-and-agent-constraints/design.md#角色)，外加一个「自己」** |
| **作者不另说时** | **只有「自己」** |
| **「自己」指谁** | 在组织、租户持有的资产上，指**[作者本人](../PF-001-identity-scope-and-agent-constraints/design.md#67-创作与归属)**；在[工作区自带的资产](#57-工作区那一级不参与权限计算)上，指挂上那份工作区的租户本人 |
| **判下来这个人不能用** | **不装进他的会话**——与斜杠命令[「没有权限就等于不存在」](#会话认得哪些命令什么时候变)同一条。这一份在替换次序上视为不存在，同一个标识有下一层的实现、而他用得了，装的是那一份（[§5.6 第 1 步](#56-四步资产求值--组装--投影--层级计算)） |
| **会话进行中被收回** | **已经开始的运行不变，自下一次运行起不再装入**——[撤销管的是下一道准入，不是强制停止](../PF-001-identity-scope-and-agent-constraints/design.md#66-撤销不等于强制停止)。斜杠命令是人的入口、不在运行里，[此刻起就不存在](#会话认得哪些命令什么时候变) |

**「自己」为什么是作者**：[作者的身份本来就在](../PF-001-identity-scope-and-agent-constraints/design.md#67-创作与归属)，不随换岗或离开而变；
默认「只有自己」读作**作者先自己用，要给别人用就配上角色**。读成「持有那一层的某个人」，就得再定「哪个人」，而持有那一层（组织、租户）里没有一个天然的人选。

**判下来不能用为什么是不装、不是装进来用时拒**：**一种失败比两种好认**——人与 agent 只需分辨「有没有」，
不必再分「有、但我不能用」。同一项权限若在斜杠命令上是不装、在工具上是用时拒，「各类共用同一项」就只剩一个名字。

> **所以这一项与别的权限项起作用的地方不同**：执行权限、干预力改的是**发起之后得到什么**，
> 这一项改的是**装不装进来**——它落在组装之前，与[禁用](#禁用是逐层配的布尔设置任一层为真即不可见)同一段（[§5.6 第 1 步](#56-四步资产求值--组装--投影--层级计算)）。
> 它仍是权限不是设置：外层锁下的界照样管着替换它的那一份（[§5.5](#替换是一条路径不是一扇后门)）。
> **official 那一份不受它管**——official [不需要授权](../PF-001-identity-scope-and-agent-constraints/design.md#来源official-与-customized)，任何一层都没有「不许成员用 official」这项权力。

**一类资产不必各配一份「谁可以用」。**各配一份，Skill 与 Slash Command 就会各长一套取值、各有一套默认，
而它们答的是同一个问题——**谁够得着这件东西**。

**权限项只有各类别列出的那些，作者不能另加。**设置项作者可以自己声明——那是这份资产自己去读的值；
**权限不一样，它要有系统里的一道关口据它放行或拒绝**。一项作者自拟的权限，没有哪一道关口会去看它，
**一项没人守的权限只会让人以为有人守。**

### 5.3 两个例子，两种合成

**设置按覆盖**：

```text
资产：agent definition「代码助手」        ← 组织共享的那一个，只有这一个
  ├─ 组织 O 为它配的默认模型 = A
  └─ 租户 (O,我) 为它配的默认模型 = B     ← 覆盖
────────────────────────────────────────────
组装时生效：B
```

注意被覆盖的**不是资产本身**——用的还是组织共享的那个「代码助手」，
只是它的一项设置属性在租户层被配了别的值。这与
[PF-001 的"同能力标识覆盖"](../PF-001-identity-scope-and-agent-constraints/design.md#62-三种合成语义)
（整个资产被替换）**是两件事**。

**权限按收窄**：

```text
资产：工具 X，自带执行权限这项属性，取值域 { 问一下, 自动, 禁止 }，作者默认「问一下」
  ├─ 组织 O 没锁这一项                     ← 没有给界
  └─ 租户 (O,我) 把它配成「自动」           ← 在界内挑一个
────────────────────────────────────────────
组装时生效：自动
```

**权限的每一层能做两件事，性质不一样：**

| 这一层做的 | 它是什么 | 怎么合成 |
|---|---|---|
| **锁下一个允许集合**（带 [`immutable`](#54-默认与强制一个机制三处适用)；锁成一个值是它的特例） | **界** | 各层的界**取交集**——更具体的一层只能在外层的界里再收，突破不了 |
| **配一个值，不锁** | **挑选** | 从最具体的一层往外，**取第一个落在界内的**；作者声明的默认值是最外面那一个挑选 |

**「设成自动」看起来像放宽，其实是在界内挑一个。**界由锁定出来，谁也突破不了；
不锁的配值只是在界里挑哪一个——越具体的一层挑的越算数，**挑到界外的不生效**。
**不锁的配值不是界**：组织说「默认问一下」而不锁，就是在说「没人另挑的话用它」，不是在说「只许问一下」——
否则成员改成「自动」求出来是空集，[默认与强制](#54-默认与强制一个机制三处适用)就分不开了。

**只有一个例外：哪一层把执行权限配成「禁止」，锁不锁都是界。**组织、租户或会话任何一层配了「禁止」，
这一项的界就只剩「禁止」，更具体的一层挑什么都不生效。放行判断里
[「任一层明确禁止」是终局](../PF-007-meta-capabilities/design.md#56-一次放行判断走四步)，任何授权、任何运行模式都翻不了案——
**一个能被下一层挑掉的「禁止」撑不起那一条**。这与[禁用「真即锁」](#54-默认与强制一个机制三处适用)是同一个形状。
作者声明的默认值不在此列，它只是最外面那个挑选。**代价是组织说不出「默认关着、成员想用自己打开」**——要那样，配「问一下」。

如果组织把工具 X 的这项权限**锁成空集**，租户再怎么挑也拿不到：
空集与任何集合的交集还是空集，**每一次调用都被拒**。**这正是 PF-001 要的那条不可突破的边界。**

**谁都没挑到界内的**（连作者的默认值也落在界外），**取界内离最具体的那个挑选最近的一档；一样近，取严的。**
例：组织把执行权限锁成「问一下」「禁止」两档，说的是「不许自动」；作者默认「自动」、也没有人另挑，
落到的是「问一下」，不是「禁止」。**界是每一层都认可的范围**，在界里取离人意最近的那一档，没有越出任何一层说过的话；
取最严的那档，一个「不许自动」就会把工具整个关掉，那不是谁的意思。所以**执行权限、干预力这类分档的权限，求出来都恰好是一档**——界不空，就总有一档可落。

> **这不是[禁用](#64-移除与禁用是两个动作)。**收空权限的工具**照样装得上、agent 照样看得见**，
> 只是每次调用都被拒；禁用的工具**根本不进这一次装配**。

### 5.4 默认与强制：一个机制，三处适用

**「默认」和「强制」是两回事，但它们不需要两套机制。**

每一层对一个东西可以做两件事：

1. **给一个值**；
2. 声明这个值**不可再被下层覆盖**（`immutable`）。

| 加不加 immutable | 这层在说什么 | 下层能做什么 |
|---|---|---|
| **不加** | 「**默认**这样」 | 可以改 |
| **加** | 「**必须**这样」 | 改不了 |

这一个机制同时管三处：

| 用在哪 | 不加 immutable | 加 immutable |
|---|---|---|
| **设置的字段值** | 组织设个默认模型，成员可换 | 组织锁死模型，成员换不了 |
| **权限的取值** | 组织说默认「问一下」，成员可改成「自动」 | 组织锁死「问一下」，成员改不了 |
| **资产的替换** | 组织换了个自定义 skill，成员还能再换自己的 | 组织锁死自己那个（比如安全组件），成员换不了 |

> **权限比另外两者多一档。**权限的取值域是**枚举**的（问一下 / 自动 / 禁止），
> 所以它除了"锁死一个值"，还能**收窄到一个子集**——比如组织说"只许问一下或禁止，
> 不许自动"。`immutable(v)` 就是收窄到单元素集 `{v}`，是收窄的特例。
> 设置的取值域通常是开放的（比如模型名），谈子集没意义，只有"锁不锁"两态。
> **这一段是 PM 推导**，见 [decisions.md](decisions.md)。

> **[禁用](#64-移除与禁用是两个动作)不是第四处，也不是第三种合成规则。**
> 它是每份持有资产上的一项**布尔设置**，合成语义是**析取**——任一层为真即为真。
> 那等价于「布尔设置 ＋ 真即 `immutable`」：某一层配了真，下层就改不动；
> 配假只是默认，下层照样可以配真。**所以上面这一个机制原样够用**，
> 不必为禁用另立一套。

### 5.5 资产替换的层级

**默认的替换次序**：

```text
official（出厂默认）  <  组织自定义  <  租户自定义  <  工作区
```

**越靠右越具体，越具体的覆盖越外面的。**
[工作区那一级是会话创建时选定的、可以为空](#它是会话选用的不指定就是空)，但挂上之后在这条次序上**与另两级一视同仁**——
**除了授权与权限那一维**，见 [§5.7](#57-工作区那一级不参与权限计算)。

**official 可被替代，除了三种情形。**它处在最底层，本来就是被替换的对象
（它只是[不可被清空](../PF-001-identity-scope-and-agent-constraints/design.md#来源official-与-customized)）：

| 例外 | 谁定的 | 效果 |
|---|---|---|
| **[meta 能力](../../ubiquitous_language/terms/capabilities-and-composition.md#ul-meta-capability--meta-能力--meta-capability)** | 结构性的，归 [PF-007](../PF-007-meta-capabilities/design.md#meta-与常驻的关系) | 任何层都替换不了 |
| **组织在自己那层把某份 official 的持有标了 `immutable`** | 组织 | 租户与工作区替换不了 |
| **租户在自己那层把某份 official 的持有标了 `immutable`** | 租户 | 工作区替换不了 |

**`immutable` 锁的是「持有它的那一层以下不许再替换」，不问被锁的那份是 official 还是自定义。**
组织换上自己的审计 skill 并标 `immutable`，租户换不掉；租户把 official 的 `Shell()` 标 `immutable`，
仓库带来的同名工具就不生效。典型用途是重要的安全组件。

**同标识替换发生了，必须可见。**设置页上、以及 agent 通过 [meta 能力](../PF-007-meta-capabilities/design.md#61-tools通向任意非常驻工具)查看那个条目时，
都能看到这份来自哪一层、替换了哪一层的那一份。替换本身不需要谁批准——工作区在这条次序上与另两级一视同仁——
但**静默的替换等于让一个仓库在没人看见的地方换掉租户的东西**，可见性是那条「一视同仁」的代价。

#### 替换是一条路径，不是一扇后门

**同标识替换换掉的是实现，不是管这个身份的那些界。**替换发生之后，外层配下的东西哪些还管着替换它的那一份：

| | 替换之后 | 为什么 |
|---|---|---|
| **权限** | **外层为这个[能力标识](#身份是类别--name其余归实现)锁下的界，照样管着替换它的那一份**——不论那份是哪一层提供的。那份的声明里少了外层锁住的某一项，**那一项按最严的值算** | 不然租户把组织锁成「问一下」的工具换成自己同名的一份、再配「自动」，**锁就从旁边绕过去了**；少声明一项也不能是逃掉它的办法 |
| **设置** | **按资产取值，不跟过去**：外层给原来那一份配的值，**连锁住的在内**，都不落到替换它的那一份上；那一份用它自己这一层配的值与它自己声明的默认值 | 设置里有[落点与身份](#设置项分四类资产声明每一项时必须标类别)那一类——**租户给某个 MCP 接入点取的凭据，要是跟到工作区带来的一份同名替换上，凭据就交给了仓库里带来的另一份实现**；组织给接入点配的连接目标跟过去，也是把别人的实现接到了组织选的对端上。组织要让一项设置管住所有实现，**就把替换本身锁住**（上表那两行） |

> **一句话**：**权限的界跟着身份走，设置的值跟着资产走。**
> 前者管的是「这个身份能被怎样用」，换一份实现不该松动它；后者是「这一份实现怎么配」，换了实现就该重配。

### 5.6 四步：资产求值 → 组装 → 投影 → 层级计算

顺序是有意的，**不能换**。

| 步 | 做什么 | 输入 | 输出 | 语义归谁 |
|---|---|---|---|---|
| **1. 资产求值** | 这个租户有哪些资产可用 | (组织, 账号) + 本会话挂上的[工作区](#工作区)（[没挂就没有这一级](#它是会话选用的不指定就是空)）+ [资产归属那条层序](#58-三条层序各答一个问题) + [各归属层配的「禁用」值](#禁用是逐层配的布尔设置任一层为真即不可见)（含工作区那一级，**但它那一级的值只对它自己提供的资产生效**）+ 各层为[「谁可以使用它」](#谁可以使用它是各类资产共用的一项权限)配的值与会话所属的那个人 | 每个能力标识一个生效资产（**这个人不能用的那几份不参与挑选**） | [PF-001 §6.2](../PF-001-identity-scope-and-agent-constraints/design.md#62-三种合成语义) 的组合 + 同标识覆盖 |
| **2. 组装** | 这个 agent 实际由什么构成 | 一个 Agent Definition + 第 1 步的结果 | 沿组合图展开后的资产集合 | 本 topic §5.1 |
| **3. 投影** | 有哪些设置项、哪些权限项 | 第 2 步装上的每个资产**自带的属性** | 项的集合 | 本 topic §5.2 |
| **4. 层级计算** | 每一项的值是多少 | 第 3 步的每一项 + 各归属层配的[属性配值](#组织的设置是视图不是对象) | **组装时实际用的值** | PF-001 §6.2 的覆盖 / 收窄，[层序见 §5.8](#58-三条层序各答一个问题) |

**第 1 步内部有三小步，次序写死，不能合并：**

1. **先按禁用滤。**每份持有的[「禁用」按析取求值](#禁用是逐层配的布尔设置任一层为真即不可见)——
   官方、组织、租户任一层为真，这份资产不可见；工作区那一层的值只对它自己提供的资产参与。
   **被滤掉的持有在替换次序上视为不存在。**
2. **再按[「谁可以使用它」](#谁可以使用它是各类资产共用的一项权限)滤。**剩下的每份自定义持有，判会话所属的那个人能不能用它；
   **不能用的，同样在替换次序上视为不存在**——这个标识退回下一层。**official 那一份不参与这一滤**：它不需要授权。
   这一项每一类资产都有，**不必等第 3 步投影出来**，所以在这里就求。
3. **最后在剩下的持有里，每个能力标识取最具体的一份。**按 [§5.5 的次序](#55-资产替换的层级)取；
   某一层标了 `immutable` 就在那层截断，更具体的层不参与。

工作区层内有共享与本地两个目录来源时，前两步同样分别过滤候选，第三步以可用 local 候选优先；
没有可用 local 候选则共享候选仍参与。该优先级不改变组织、租户的替换锁定，也不改变工作区层不能给别层资产配禁用值的规则。

**「谁可以使用它」为什么退回下一层，而不是让整个标识不装**：一个标识有 official 那一份时，
**它必须在**——official 是组装的最小必需，[求值结果里一个 official 标识都不许空着](acceptance.md#二绝不能发生的事)；
组织换上一份只给自己人用的实现，**不能因此把 official 从别的成员手里拿走**（[PF-001：没有这项权力](../PF-001-identity-scope-and-agent-constraints/design.md#来源official-与-customized)）。
退回下一层，与被禁用的那份[退出替换](#禁用是逐层配的布尔设置任一层为真即不可见)同一个形状，不必另立一条规则。
**「自己」本来就按每一份的作者求**，同一个标识的几份实现，这个人能用哪几份各不相同——所以这一滤落在持有上。

**为什么不能先替换再禁用**：那样工作区可以先用同名资产替换掉租户那份，再把自己这份禁用——
这个标识就此从会话里消失，[「只禁得掉自己提供的那批」](#禁用是逐层配的布尔设置任一层为真即不可见)这条限定被从旁边绕开。
按上面的次序，**被禁用的那份退出替换，标识退回下一层**：仓库禁得掉的只有自己带来的效果，租户的东西原样在。

**为什么顺序不能换**：

- **1 必须在 2 之前**——组装只能从"可用的"里面装。
- **3 必须在 2 之后**——装了什么，才知道有哪些项。项的**存在性**由组装决定。
- **4 必须在 3 之后**——先有项，才谈得上算它的值。

**唯一会改组合的那项设置，在第 2 步就地求值。**[Plugin 的「启用哪些成员」](#plugin)决定展开这个 plugin 时装进哪几样——
等到第 4 步才有值，第 2 步就不知道该装什么。所以组装展开到一个 plugin 时，**先按层级求出它这一项，再照结果展开**；
这一项要用的只有这个 plugin 自己的持有与各层配在上面的值，第 2 步那一刻都已经在了，**不回头改前面任何一步**。
其余设置——包括别的绑定类设置（比如拓展件挂在哪个位置）——都不改组合，照常在第 4 步求值。

**有两轮层级计算，作用对象不同**：第 1 步作用在**资产**上（哪个资产生效），
第 4 步作用在**项**上（资产的某项设置/权限取什么值）。
混为一谈会得出"改一项设置等于换一个资产"这种结论。

**求值与组装不能合并。**合并的话，"组织禁用了某个 skill"与"这个 agent 没引用它"
会变成同一件事，而它们的产品含义完全不同——前者是管理决定，后者是设计选择。

### 5.7 工作区那一级，不参与权限计算

**[工作区](#工作区)照常提供资产，也照常提供设置**——
[它配的设置值还压过租户配的](#58-三条层序各答一个问题)。
**唯独授权与权限相关的配置，它一概不参与：**

> **系统加载配置的时候，就把工作区来的那部分过滤掉。**
> 不是「加载了但不许放宽」，是**那条路根本不走**。

**为什么**：工作区的内容来自工作区实例或地址，而这些资源可能随他人提供的代码一起到达——
**克隆一份下来，就带着它自己那一套**。

> **一个仓库不能给自己提权。**

**连「只许往严里改」也不给**，有三条理由：

- **判断权不能递给被防的那一侧。**那份配置文件本身就躺在宿主机上，
  而「作用会不会直接落到宿主机上」正是执行环境权限要防的事。
  让它参与决定防线画在哪，**哪怕只准往严了画，防线也已经不由我们说了算**。
- **往严里改一样能伤人。**把该用的工具全收到不可用，这个会话就废了。
  **仓库内容不该握着这种开关。**（这条同样管着[「禁用」那一维](#禁用是逐层配的布尔设置任一层为真即不可见)——
  工作区在那里**只禁得掉它自己提供的那批资产**，别人提供的，它配的值不参与。）
- **一刀切才审得动。**「只许收紧」要求系统逐条判断每项配置是放宽还是收紧，
  **那个判断本身就是攻击面**——一条配置在这一维看着是收紧，在另一维可能正好相反。
  加载时就不收，这个判断压根不存在。

**这不是我们发明的谨慎**：四家在跑的 harness 各自独立地挡了同一类事——
有的让带 `DSH_` 前缀的项目 `.env` **直接硬抛**、
有的让项目配置里写的宽松模式**一律不生效**、
有的给项目层列了一张硬性禁用键清单。
[证据逐条记在调研里](../../../research/agent-harness-session-design/research.md)。

**这一条管三样：授权与权限、[落点与身份那一类设置项](#设置项分四类资产声明每一项时必须标类别)、治理那一类里除禁用之外的项（`immutable`、连接件的[触发会话的默认运行模式](#触发会话的默认运行模式)）。**
后两样与权限一样在加载时就滤掉，理由同上——它们改的不是「怎么做」，是这次运行**过哪道门、以谁的名义、门放不放行**。
其余设置与资产照常从工作区来——**能力和偏好可以从项目里来，权力不行。**

**工作区自己提供的资产，权限项一律取最严值。**
[配值的资格来自持有](#三方分工资产定形状各层配值运行时求值)，而这份资产只有工作区持有；
工作区配的权限又在加载时就被滤掉——**没有任何一层配得了它**，所以它每一项权限都取最严的那个值：

| 权限项 | 取值 | 后果 |
|---|---|---|
| **执行权限**（Tool、MCP 的每一个动作） | **问一下** | 仓库自带的工具与 MCP 动作照样能用，**每一次都要人点头** |
| **干预力**（Loop Extension） | **只观察** | 仓库自带的挂件照样每次被调到，**改不动、拦不住任何东西** |
| **「能不能用」「谁可以用」**（MCP 的能不能用、[谁可以使用它](#谁可以使用它是各类资产共用的一项权限)） | **挂上这份工作区的那个租户本人** | 仓库带来的 skill、斜杠命令、MCP 接入点，**挂上它的那个租户在本次会话中可用；其他租户须以自己的授权与会话另行求值** |
| **其余「谁可以……」**（Loop Extension 谁可以安装、Plugin 谁可以启用、Agent Definition 谁可以实例化与派发） | **同上：挂上这份工作区的那个租户本人** | 理由与上一行相同——要挡的是权力不是能力；这几项答的也是「谁够得着」，**取「无人」就把仓库带来的这几样整个废掉** |
| **Connector 的「能不能安装」** | **不另定** | 仓库带来的连接件本来就接不上：它的投递目标与鉴权绑定是[落点与身份类](#设置项分四类资产声明每一项时必须标类别)、触发会话的默认运行模式是治理类，**都不从工作区来**——它既投不进已有的会话，也开不出新会话；要用，收进租户层再配 |

**「谁可以用」的最严值不取「无人」。**取「无人」，仓库带来的 skill、命令、MCP 就被整个废掉，
与「能力可以从项目里来」相抵——而这一级要挡的只是**权力**，不是能力。
取「挂上它的那个租户本人」限定的是本次求值的使用者：其他租户只有通过自己的工作区关系与组织规则检查后，才能在自己的会话里分别求值可访问实例提供的资产，包括共用实例的 `.omne.local` 来源；不会因此获得这次会话或该租户层私有资产、配值与凭据的使用权。
**权力仍由另外两项卡住**：动作每一次都要问人，挂件只能旁观。

**不认它自己声明的出厂值**——那等于让仓库替自己定权限，一个声明了「自动」的 MCP 接入点克隆下来就能静默外发。
**要放宽，把这份资产[收进租户层](../PF-003-asset-transfer-and-sharing/design.md)再配。**

**[禁用](#禁用是逐层配的布尔设置任一层为真即不可见)也照常从这里来，但只管它自己那批。**
它是一项布尔设置，答的是「这个目录上看得见哪些资产」，
与工作区本来就能提供资产是同一性质；它不进[权限的交集](../PF-001-identity-scope-and-agent-constraints/design.md#62-三种合成语义)，
所以不在这条挡的范围里。**而它能关掉的，只有工作区这一级提供的那批资产**——
[组织、租户、出厂层提供的，工作区配的禁用值不参与](#禁用是逐层配的布尔设置任一层为真即不可见)。

**仓库带来的、会在本机起一个命令的东西，默认不启用。**两样：**以本地命令方式接入的 MCP 接入点**，
以及**从别家导入成拓展件的命令型 hook**。它们一进来就是[禁用](#禁用是逐层配的布尔设置任一层为真即不可见)的；
**要用，由使用这份工作区的对应租户在自己的设置里逐件打开**——**开关不在仓库里**，工作区资源里写什么都打不开它。
打开之后，它照上表取最严值：接入点的动作每一次都要人点头，挂件只能旁观。

> **为什么**：别的资产从仓库来，最坏是 agent 多了一件能力，而每一次用都要人点头；
> **这两样不一样——挂上工作区、开一次会话，就等于在宿主机上跑了仓库里写好的命令**，那一刻没有任何一道门会响。
> 这是「权力不从项目里来」最直接的一处，所以**不等它被用才拦，在它能跑之前就关着**；
> 开关放在使用它的租户那边，因为共享内容不能代替每个参与租户批准本机命令，而仓库自己握着这个开关，就等于没有这一条。

### 5.8 三条层序，各答一个问题

**这是本 topic 最容易被读错的一处：层序不止一条，三条的成员还对不齐。**

| 层序 | 回答什么 | 有哪几级，**`<` 表示越靠右越具体、覆盖越外面的** |
|---|---|---|
| **资产归属** | **这份资产是谁的、谁替换得了谁** | official < 组织 < 租户 < **[工作区](#工作区)** |
| **设置** | **一项设置取什么值** | 出厂默认 < 组织 < 租户 < **工作区** < 会话 |
| **权限** | **一项权限的允许集合有多大** | 出厂默认 · 组织 · 租户 · 会话——**工作区不在其中**。这一维[取交集，本来就没有方向](../PF-001-identity-scope-and-agent-constraints/design.md#62-三种合成语义) |

**一句话记住工作区在三条上的位置：**

> **设置是覆盖，同身份的资产是替换，权限是忽略——除非上面锁了。**

**设置这一维，工作区压过租户。**它配的值按[覆盖](#53-两个例子两种合成)生效，
与「租户压过组织」是同一件事，不是另一套语义。
**但上层加了 [immutable](#54-默认与强制一个机制三处适用) 的，它照样压不动**——
覆盖只发生在**没有被锁死**的项上。组织锁死的默认模型，
目录里放一份配置也换不掉；这正是 immutable 存在的意义。

**权限这一维，工作区一概不参与**，理由与三条反驳在 [§5.7](#57-工作区那一级不参与权限计算)：
**能力和偏好可以从项目里来，权力不行。**

**资产这一维，工作区提供的资产替换租户的那一份**（同[能力标识](#身份是类别--name其余归实现)时），
见 [§5.5](#55-资产替换的层级)；它自己配的那项
[「禁用」](#禁用是逐层配的布尔设置任一层为真即不可见)同样参与，
**但只管它自己提供的那批资产**。

#### 工作区不是「会话级」，两者在设置那条层序上是一前一后的两级

**会话级的东西[一律不外溢](../../ubiquitous_language/terms/agent-runtime-loop.md#ul-session--会话--session)**，
**工作区级的资源留在逻辑工作区上**——这个会话结束了，同一租户的下一个会话重新选择并装载它仍然看得见。
**两者的失效事件完全不同**，所以它们是设置层序上**各占一格的两级**，会话级在最里面。

> **把工作区读成会话级，会得出「换个工作区，会话级的设置就该重算」这种错误结论。**

#### 它不因此多一重身份

**[PF-001 的那四层是身份带来的](../PF-001-identity-scope-and-agent-constraints/design.md#61-层次)**：
出厂默认、组织、租户、会话，每一格对应一重归属。
**工作区不是作用域层身份**——它是[挂在租户下、可由多个地址和实例承载的一级归属](#工作区)，会话创建时才选定。
它在设置那条层序上占一格，**不因此成为第五重身份**；
**权限那条层序仍然只有那四层**，资产归属那条本来就是另一条。

## 六、产品规则

### 6.1 设置页是长出来的，不是画出来的

**我们的设置页和传统软件产品的设置页不是一回事。**

传统软件的设置页是**画好的**：有哪些项，产品定死，写在代码里。
我们的设置页是**长出来的**：

> **一个资产被加进来，它可配置的表单就自动生成、追加到设置页；
> 资产被移除，那块表单自动消失。**

这是[「设置是资产的属性」](#52-设置与权限是资产的两种属性)的直接产品体现——
设置页就是那个投影视图的样子。没有一份独立维护的字段清单，
**页面长什么样，是"持有了哪些资产"的函数**。

### 6.2 设置页分两块

| 块 | 归谁 | 里面是什么 |
|---|---|---|
| **界面偏好** | **账号** | 界面语言、时区一类**属于这个人本身**的偏好。跟着人走，在所有组织里都一样 |
| **资产的设置与权限** | **组织 / 租户** | 持有的每个资产各自的可配置表单，随资产增删自动增减 |

两块**不能混在一起**，因为它们是[两种正交的 context](../PF-001-identity-scope-and-agent-constraints/design.md#contextagent-运行时可感知的上下文信息)：
第一块跟着人，第二块跟着"人在哪个组织"。
把它们放同一个列表里，用户会以为改一个和改另一个是同类操作，
而实际上换个组织之后一个变了一个没变。

### 6.3 组合的引用指向能力标识

一个 plugin 包含某个 skill，**它包的是那个能力标识，不是某个具体资产**。
因此组织换上自己的自定义版本之后，**所有含它的 plugin 与 agent 自动用上新的**。

这与 [PF-001 §6.3「依赖指向能力标识」](../PF-001-identity-scope-and-agent-constraints/design.md#63-依赖与组合)
是同一条规则——组合与依赖不需要两套。

**为什么不能指向具体资产**：那样的话，组织换上的安全组件**进不了 plugin**，
[§5.5 的 immutable](#55-资产替换的层级) 就白标了——漏洞正好留在 plugin 里面。

**代价要说清楚**：plugin 作者**不能假定**自己包里的零件不被替换。
他应当面向**能力标识**编写，而不是面向某个具体实现。
这是"资产可被自定义替换"这个能力的固有代价，不是缺陷。

### 6.4 「移除」与「禁用」是两个动作

组织不让成员用某个工具，有两种意图，**产品上必须能分别表达**：

| 动作 | 持有关系 | 那份配置 | 设置页上的表现 |
|---|---|---|---|
| **移除** | **不再持有** | 随之消失 | 那块表单**消失** |
| **禁用** | **仍然持有**，只是[本层把「禁用」这项设置配成真](#禁用是逐层配的布尔设置任一层为真即不可见) | **原样保留** | 表单**仍在**，标明已禁用，**能再启用回来** |

**判据是：收回持有，还是暂时关掉。**

- 这个范围往后不要这份资产了 → **移除**。配置跟着一起走。
- 只是这一阵不让用，将来还要开回来，配好的值也不想重填 → **禁用**。

两者都保留，因为把它们并成一个动作，总有一头表达不了：
合成「移除」，每次关停都要重配一遍；合成「禁用」，就再也没有办法真正把一份资产还回去。

#### 但对 agent 来说，两者一样：都不可见

[装配从「持有且未被禁用」的那一批开始](#56-四步资产求值--组装--投影--层级计算)——
**被禁用的资产在第一步就被滤掉**，装不上，因此 agent 无从知道它存在。

**成员要知道自己少了什么、能不能去申请，看的是设置页**：
表单还在并标着已禁用，就说明这个能力这个范围有，只是被关掉了。**这件事不靠问 agent。**

> **禁用是不可见，不可用是可见但用了一定失败。**

这两件事必须分开：**禁用在装配之前就把东西挡掉**，
[不可用](../PF-006-tools-and-skills/design.md#63-不可用时装的是同名替换件不是不装)是**装上了、条目还在原位，只是这一次做不了**。
合成一件，agent 就再也分不清「我没有这个能力」和「我有，但现在使不了」——
而这两种处境它该走的下一步完全不同。

#### 禁用是逐层配的布尔设置，任一层为真即不可见

**禁用是每份持有资产上的一项布尔设置**，走的是
[§5.2 那一套](#52-设置与权限是资产的两种属性)：资产定形状，**持有它的每一层各配各的值**，运行时求值。
它不是另一类对象，也不是权限。

**它的合成语义是析取：任一层为真，结果就为真。**

- **任一层把它配成真，这份资产在那个范围里就不可见**——不必层层都配。
- **本层改回假，只是去掉本层自己那一个真**——**下面一层开不回上面一层禁掉的东西。**

**自上而下一层层过滤，没有开得回来的情形。**反过来做，组织的关停就成了一句建议——
**租户一键开回来，那条管理决定等于不存在。**

**[工作区](#工作区)作为[资产归属的一级](#55-资产替换的层级)，同样配得了这项设置、同样参与过滤**——
**但只对它自己提供的那批资产。**

> **工作区配的「禁用」，只对工作区这一级提供的资产生效。**
> **对组织、租户、出厂默认层提供的资产，工作区配的那个值不参与析取。**

**这条限定是有理由的**：工作区的内容来自工作区实例或地址，而这些资源可能随他人提供的代码一起到达——
**克隆一份下来，就带着它自己那一套**。没有这条限定，
**一个仓库把组织下发的审计 skill 配成禁用，这个会话就没有它了**；
而[组织的那条管理决定本来是「下面开不回来」的](#禁用是逐层配的布尔设置任一层为真即不可见)，
**结果被一个工作区地址或实例从旁边绕开**。

**它自己带来的那批，它当然禁得掉。**那批资产本来就是这个目录提供的，
**由它决定这个目录上看得见哪几个，是同一件事的两面**。
禁掉的那份[在替换次序上视为不存在](#56-四步资产求值--组装--投影--层级计算)：
同标识退回租户那份，**仓库借「同名替换再禁用」藏不掉租户的东西**。

**所以[§5.7 的第二条理由在这一维上照样成立](#57-工作区那一级不参与权限计算)**：
**仓库内容不该握着把工具全收成不可用的开关**——它能收掉的，只有它自己拿出来的那些。

> **官方资产不在此列**：official
> [不可被禁用](../PF-001-identity-scope-and-agent-constraints/design.md#来源official-与-customized)，
> 那是结构性的，任何层都没有这项权力。

## 七、取舍

| 面临的选择 | 选了 | 为什么 |
|---|---|---|
| 组合是**一种**关系还是几种 | 一种 | 资产之间、资产到 agent、资产到它的属性，如果各用一套规则，就有三处覆盖语义、三个出错的地方 |
| 设置与权限是**独立对象**还是**资产的属性** | 属性 | 独立对象意味着一份脱离资产维护的字段表，它与资产各自演化，最终必然对不上。作为属性，「有哪些项」自动等于「持有了哪些资产」 |
| Tool 是**组件**还是**资产** | 资产 | 本系统能做工具的动态组装。前身系统把它归为组件是能力所限，不是它本该如此 |
| 「默认」与「强制」用**两套语义**还是**一个标记** | 一个标记（`immutable`） | 两套语义要在每一类对象上各解释一遍；一个标记落在同一个字段上，且资产、设置、权限三处通用 |
| 组合的引用指向**能力标识**还是**具体资产** | 能力标识 | 指向具体资产的话，组织换上的安全组件进不了 plugin，`immutable` 就白标了。代价是 plugin 作者不能假定零件不被替换 |
| 「移除」与「禁用」合成**一个动作**还是**两个** | 两个 | 「收回去」和「留着但关掉」是不同的管理意图：前者配置跟着走，后者配置原样留着、还能开回来。合成一个总有一头表达不了。**代价是 agent 那一侧分不出这两者**——两个动作在它眼里都只是「这东西不在」，[要让成员知道，靠的是设置页](#64-移除与禁用是两个动作) |
| 工作区配的「禁用」**管所有层提供的资产** ／ **只管它自己提供的那批** | **只管它自己那批** | 管所有层，**一个仓库就能把组织下发的审计组件关掉**——而[组织那条管理决定本来是「下面开不回来」的](#禁用是逐层配的布尔设置任一层为真即不可见)，那等于从旁边给它开了个后门，且[「往严里改一样能伤人」](#57-工作区那一级不参与权限计算)在这一维上完全落空。代价是**「禁用」这一项的合成不再是一句无条件的析取**：算一份资产的禁用值时，要先看工作区那一级是不是它的提供者——**多一个条件，换掉一个后门** |
| 工作区配的**设置**：**压过租户** ／ **根本不参与合成** | **压过租户** | 工作区资源里的偏好，本来就该在这个工作区里说了算——**能力和偏好可以从项目里来**，[不能来的只有权力](#57-工作区那一级不参与权限计算)。代价是**同一个租户在不同目录下看到的设置不一样**，而那正是要的；真不想让它变的，上层[加锁](#54-默认与强制一个机制三处适用)即可，**工作区压不动锁住的** |
| 工作区与承载它的目录**是一回事** ／ **分开** | **分开** | 读成一回事，「同一个目录被两个租户身份挂上是两份」就自相矛盾，而且「目录」会被顺手读成 agent 的活动围栏——[它从来不是](../PF-005-execution-environments-and-sandboxes/design.md#工作区的承载目录不是宿主机上的边界)。分开之后，工作区答「持有什么、配了什么」，地址与实例只是访问和装载的来路。代价是**多一个要分清的词**，以及地址与装载策略要另说——本版不限定地址种类 |
| 工作区**按会话所在目录自动挂上** ／ **创建时显式指定，不指定就空** | **显式指定** | 自动挂上意味着 agent 在哪个目录里起来就吃哪个目录的配置——而那份配置[是跟别人代码一起来的](#57-工作区那一级不参与权限计算)，**隐式吃进来正是 §5.7 要防的路**；何况会话未必从某个目录里建起来（远程界面建的会话没有「所在目录」）。代价是**不指定就什么都不加载**，用户得自己说；这正是要的——这一级是 opt-in |
| 工作区**挂在租户下** ／ **全局按目录** | **挂在租户下** | 全局按目录的话，同一台机器上**换个租户身份，上一个身份那个目录里的资产与配值会跟着进来**——那是一条跨租户的泄漏路径，而[跨租户默认拒绝](../PF-001-identity-scope-and-agent-constraints/design.md#64-隔离)是不能让步的。代价是**同一个地址被两个租户身份访问就是两份**，各配各的、互相看不见，**本版也因此没有共享工作区**（[§2 非目标](#非目标)） |
| 组合关系**先做全**还是**先做最小** | 最小 | Skill 套 Skill、Plugin 套 Plugin、Plugin 装 Agent 都暂不做——没有已知需要，且各自会带来环检测或跨层治理的负担。**加是加法，不用改已有结构** |
| Slash Command **单独一类资产** ／ **并进 Skill** ／ **只做交付面自己的动作** | **单独一类** | 产品负责人要的是**给将来的可编程性留口子**：「敲一个名字触发一件事」这层绑定本身可以被持有、替换与治理。并进 Skill 装不下 ① 与 ③；只做交付面动作，这层绑定就写死在交付面里、任何人都换不了。**代价是没有可抄的先例**——在跑的两家同行一家已删掉用户自定义的 `/` 命令，一家把命令并进了 skill（[来源问题](decisions.md#四已知的来源问题)） |
| 斜杠命令**只由交付面识别** ／ **所有来源一视同仁** | **只由交付面识别** | 识别是人机交互面上的一个手势：人敲下 `/` 是在对系统说话。连接件送来的文字是**别人的话**，照命令去执行，就等于让一个外部来源替人触发系统流程。代价是**同一串 `/xxx` 从两个入口进来，后果不同**——这正是要的 |
| 没有权限用的斜杠命令：**看得见、敲了说「你不能用」** ／ **不存在** | **不存在** | 入口是给人用的，给一个人看一条他用不了的入口没有用处；**一种失败比两种好认**——人只需分辨「有没有这条命令」。代价是**人在交付面上分不出「没有」和「不许」** |
| ① ② 型的增删与禁用：**进行中的会话自动跟上** ／ **等人发 reload** | **等人发 reload** | 同一个会话里，人敲下同一个名字，**展开的是哪段话不会在他不知情时变**；而斜杠命令本来就不进系统提示词，不值得为它打断任何东西。代价是**组织刚下架的一条提示词命令，开着的会话里还敲得出来**，直到那个人发对应的 reload。**权限不在此列**，收回即时生效 |
| 保留名：**一份系统维护的名单** ／ **一个前缀** | **`omne-official` 前缀** | 名单会长，每长一次都可能撞上某个租户已经发布的命令，**撞上之后怎么办没有好答案**。前缀让撞名从一开始就不可能。代价是**系统自己的命令名都更长**，拼法归规格 |
| MCP 的动作**各自是一个工具条目** ／ **整个接入点只占一个槽位** | **各自是一个条目** | 社区通行的做法，复用现成的客户端就是这个形状。代价是**对端动作多，agent 面前的条目就多，而且两次执行尝试之间可能变**——所以钉死「每一次执行尝试开始前重算、一次尝试之内不变」 |
| 同标识替换之后，外层配下的**权限的界**与**设置的值**：**都跟过去** ／ **都不跟** ／ **界跟、值不跟** | **界跟、值不跟** | 界不跟，[替换就成了绕开锁的后门](#替换是一条路径不是一扇后门)；值跟过去，租户给原来那份取的凭据就交给了另一份实现——比如仓库带来的那一份。代价是**组织要让一项设置管住所有实现，得把替换本身锁住**，不能只锁那一项设置 |
| 不锁的权限配值：**也是界，一起取交集** ／ **只是挑选** | **只是挑选**；**配成「禁止」的除外，锁不锁都是界** | 当成界，组织说「默认问一下」、成员改成「自动」就求出空集，[「默认」与「强制」](#54-默认与强制一个机制三处适用)再也分不开。「禁止」例外，是因为[放行判断里任一层明确禁止都是终局](../PF-007-meta-capabilities/design.md#56-一次放行判断走四步)。代价是**权限的合成要分两步说**——界取交集、再在界内挑，比一句「取交集」长；以及**组织说不出「默认关、成员可自己开」** |
| Slash Command 的绑定目标与参数声明：**当设置，各层可配** ／ **当命令本身** | **当命令本身** | 当设置，同一个命令名在组织里展开一段话、在租户里展开另一段，[同一份资产在两层成了两件事](#slash-command)——那是替换的活，已经有一条路。代价是**想改一条命令展开什么，只能换一份同名的** |
| 经 OAuth 取 MCP 凭据：**走配值那条路** ／ **在会话里出决策卡片、由 agent 发起** | **走配值那条路** | 与静态凭据同一套规矩：谁能配、配在哪、跨不跨租户都不用另想；答卡的人改不到他配不了的那一层。代价是**用户第一次用一个要 OAuth 的接入点时，不会在会话里被当场问一句**——agent 只看到它的动作不可用，得有人去配值的地方取一次 |
| 工作区提供的资产，权限项取**最严值** ／ **它自己声明的出厂值** | **最严值** | 出厂值由仓库自己写，取它就是让仓库替自己定权限——与[权力不从项目里来](#57-工作区那一级不参与权限计算)正好相反。代价是**仓库自带的挂件在被收进租户层之前只能旁观，自带的 MCP 每个动作都要问人**；放宽与逐运行配置未来再说 |
| 「谁可以使用它」判下来不能用：**不装** ／ **装进来、用的时候拒** | **不装** | 一种失败比两种好认，与斜杠命令「没有权限就等于不存在」同一条；各类若各判各的，「共用同一项」就只剩一个名字。代价是**这一项动的是装配**：会话进行中被收回，工具要等下一次运行才不在，[PF-004 「权限变化不改变动作空间」](../PF-004-agent-definition-and-assembly/design.md#65-权限变化动作空间不变)对它要另说（[来源问题](decisions.md#四已知的来源问题)） |
| 「谁可以使用它」判下来不能用：**标识退回下一层** ／ **整个标识不装** | **退回下一层**；official 那一份不受它管 | 整个标识不装，组织换上一份只给自己人用的实现，就把 official 从别的成员手里拿走了——**那是 PF-001 说谁都没有的权力**。代价是**组织用这一项藏不住一项有 official 实现的能力**：它藏得住的只是自己那一份，成员拿到的是 official 那一份 |
| Connector 送进来的消息以谁的身份处理：**一项可配的权限** ／ **一条固定规则** | **固定规则**：按投递目标那个会话创建时的租户身份 | 能配，就能配成「以对面账号的身份」，外部来源借连接件以一个本系统不认识的名义让 agent 做事；而会话本来就持有一个身份。代价是**连接件不能让同一个会话里的消息各按各的身份算**——要分身份，就得投到不同的会话 |
| Skill 自带「正文变体」「资源的取用方式」两项设置：**留着** ／ **拿掉** | **拿掉** | 没有一处说得出它们指什么，同行的技能也没有「正文变体」；留着一项没人说得出含义的设置，下游就得为它造形状。**加是加法**，将来有真实需要再加 |
| 拓展挂件做成**第八类资产**还是 **loop 自己的一项配置** | 第八类资产 | 做成 loop 的配置，就得为它另造一套「谁能装、组织配了租户能不能改、锁死了怎么办」——**而这套东西资产已经有了**。代价是「资产」这个抽象要多担一层含义：除了「由什么零件构成、朝外开哪些口」，还包括**推进的时候在哪些位置插手**，种类表也因此多一类（见 [PF-001 §4 资产的种类](../PF-001-identity-scope-and-agent-constraints/design.md#资产的种类)） |
| 连接件会送什么：**一份结构化的事件目录** ／ **一段给模型读的自由文本** | **结构化目录** | 自由文本只能交给模型去猜，形状不对的消息进得来、错得悄无声息；目录让「这一条是不是声明过的那一种」在受理时就答得出，[不对就拒](#事件目录与事件订阅)。代价是**作者要为每一种事件写出形状，目录里的每一项都是一份要兑现的承诺**；上游改了消息的样子，连接件的目录得跟着改 |
| 消息包：**整份随信封进来** ／ **只送一个标识、回头去拉** | **整份进来** | 连接件[没有读取面](#connector)，只送标识就没有地方去拉；为此开一个读取面，就改掉了它「只能送消息进来」的定义。代价是**大的内容也得整份送进来**；上游本来只给一个标识的来源，要连接件自己在送进来之前把内容取齐 |
| 外部的事进会话：**只投进已有会话** ／ **只开新会话** ／ **两路都有，动作主体不同** | **两路都有** | 一个已有的会话要不要收外面的事，是会话的决定；连接件自己的事件要不要起一段新协作，是这份连接件的配置的决定。[并成一路，总有一边越权](#两种投递方式动作主体不同)。代价是**开新会话那一路要等会话那一块定下「以哪个 agent definition、哪个租户身份建」**，在那之前它缺一块（[§九](#九未决项)） |
| 连接件开出来的会话的运行模式：**出厂给一个默认** ／ **配置的人必须给** | **必须给**，作者的默认不算 | 这类会话多半无人值守，「本该问人」的那一刻怎么办必须有人事先想过；出厂默认往严里给什么都做不成，往松里给就让外部来源在没人看着时放手去做。代价是**配一份连接件多一步**，没给的[开不出新会话](#触发会话的默认运行模式) |
| 拓展件不可用处置：**一项设置** ／ **一项权限** ／ **这一件自己的声明** | **这一件自己的声明** | 它说的是[这一件是一道什么样的关](#不可用处置是这一件自己的声明)；各层能配，同一件在两层就成了两件事，那是替换的活。代价是**组织改不了租户挂上的那一件在依赖不在时放不放过**——要一道硬关，组织挂自己的一件、声明为否决 |

要么是从已裁决内容推导出的唯一自洽结论，推理链见 [decisions.md](decisions.md)。

| 未决 | 为什么悬着 | 谁来裁 |
