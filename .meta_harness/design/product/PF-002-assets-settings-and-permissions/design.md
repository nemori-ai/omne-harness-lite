# PF-002：设置、权限与资产的展开

- 修订：**rev 3**，2026-09-19 · [变更历史](changelog.md)
- 状态：已定稿，**无未决项**

## 一、背景与问题

[PF-001](../PF-001-identity-scope-and-agent-constraints/design.md) 说清了设置、权限、资产
**对外**的样子：各自挂在哪一层身份上、多层同时有值时怎么合成。
但它把三者内部都当成了黑箱——资产只有一张"种类表"，设置与权限连表都没有。

黑箱留着，这些问题每次讨论都要重新发明一遍答案：

- 一个 plugin 里装了一个 skill，**这个 skill 是不是也是资产**？能不能被单独引用、单独覆盖？
- **一个 agent 由什么组装而成**，和"一个 plugin 由什么组成"，是不是同一回事？
- "默认模型"是设置——那它是**谁的**设置？全局的，还是某个 agent definition 的？
- 一个工具的执行权限默认是"问一下用户"，**租户能不能改成自动**？依据是什么？
- 组织想在 agent 每次调模型之前插一段自己的检查，**这段东西算不算资产**？谁能装、谁能覆盖？

## 二、目标与非目标

### 目标

1. 把资产的**八类具体抽象**一一定义清楚。
2. 定义资产之间的**组合关系**，以及组装成 agent 与它是不是同一种关系。
3. 说明**设置与权限附着在什么上**，以及它们与资产之间的关系。

### 非目标

| 不做什么 | 为什么 |
|---|---|
| 身份、层次与合成语义 | 归 [PF-001](../PF-001-identity-scope-and-agent-constraints/README.md)。本 topic 只定对象的形状与组合 |
| 资产的**运行时装载** | 怎样被发现、装载、卸载，是另一件事。本 topic 定它由什么构成、和谁组合 |
| 资产的**开发与发布流程** | 谁能写、怎么发版、怎么上架，另有归属 |
| 每一项设置与权限的**具体字段** | 本 topic 定「设置是资产的属性、随资产增删」这个结构；某个 tool 到底有哪几项配置，属于那个 tool 自己的定义 |
| 资产怎样在组织之间流动 | 归 [PF-003](../PF-003-asset-transfer-and-sharing/README.md)，它定义转移与分享两个动作 |
| Cordis plugin、Service、Middleware 等实现概念 | 技术设计。产品正文出现它们，只会让读者以为自己需要理解运行时 |

## 三、用户与场景

| 使用者 | 什么情况下接触这块 | 他关心什么 |
|---|---|---|
| 组织超级管理员 | 给组织配资产、调设置、定权限边界；**在 loop 的某个位置挂上自己的检查** | 我加了这个东西，成员的设置页会多出什么？我锁死的，成员能不能绕过去 |
| 组织成员 | 在自己的租户里调整这些资产怎么用 | 哪些我能改、哪些是公司定死的？我改了为什么没生效 |
| 个人用户 | 在自己的个人组织里用 agent | 我装的这个 plugin 带进来了什么？ |
| **Plugin / Skill 的作者** | 打包与发布 | 我包里的零件会不会被别人换掉？换掉之后出了问题算谁的 |
| **agent** | 每次运行 | 我这次由哪些资产组装而成、每一项配置的值是多少 |

**作者在 [PF-001 §6.7](../PF-001-identity-scope-and-agent-constraints/design.md#67-创作与归属)
已有身份**（他是一个租户，署名不随换岗或离开而消失）。
本 topic 给他**新增一重顾虑**：资产一旦可被组合与替换，
「我包里的零件会不会被换掉、换掉之后出了问题算谁的」必须有明确答复（见 §6.3）。

### 八类资产

**名字、一句话含义与管理边界归
[PF-001 §4「资产的种类」](../PF-001-identity-scope-and-agent-constraints/design.md#资产的种类)，
本 topic 不重复。**这里补它没有的部分：每一类**具体是什么**、**自带哪些属性**、
**能组合什么**。

判据始终是同一个：**它和旁边那一类的区别是什么**。说不清区别的，就是同名不同义。

#### Skill

**一段可复用的工作方法**——告诉 agent「遇到这类事情该怎么做」。

它的主体是**可读的指引正文**，可以带上所需的资源文件。
读取一个 skill **不等于运行它带的脚本**，也不自动装载它的全部附件。

| | |
|---|---|
| **和 Tool 的区别** | Skill 说**怎么做**，Tool 是**做的那个动作**。「代码审查该看哪些地方」是 skill，「读文件」是 tool |
| **和 Slash Command 的区别** | Skill 是方法本身，Slash Command 是**用户主动发起它的入口**。两者可绑定，但不是一回事 |
| **自带的属性** | 设置：正文变体、资源的取用方式等。权限：谁可以使用它 |
| **能组合什么** | **Tool**——声明「我这套方法要用到这些动作」 |

#### Tool

**一个可被调用的动作。**

它有两半，缺一不可：**调用定义**（叫什么、收什么参数、返回什么）与
**适配当前环境的实现**。只有一份没法执行的定义，不算可用。

一个 tool 可以是**多命令**的：一套命令通过统一入口提供，
agent 按类似 Unix CLI 的方式选命令、给参数、取结果。
**整套命令在组装时只占一个槽位**——命令多了不会让 agent 面前的工具条目变多。

| | |
|---|---|
| **子命令是什么** | Tool 的**内部结构**，不是独立资产。它们随这个 tool 一起被持有、配置与授权 |
| **自带的属性** | 设置：超时、并发、目标环境等。**权限：执行权限（问一下 / 自动 / 禁止）**——这是最常被配置的一项 |
| **能组合什么** | **Skill**——声明「光有我不够用，得配这份指引」。有些工具必须与 skill 配套 |

#### MCP

**一个外部工具来源的接入点。**接进来之后，它提供的动作可被 agent 使用。

它和 Tool 的关系，跟「多命令 tool 与它的子命令」是**同一个形状**：

| | |
|---|---|
| **和 Tool 的区别** | Tool 是**一个动作**，MCP 是**一批动作的来源**。MCP 本身不可被调用 |
| **它带来的动作是不是资产** | **不是。**随这个接入点一起被持有、配置与授权，正如子命令随 tool |
| **和 Plugin 的区别** | Plugin 是**本系统内部**的打包与分发单元，成员是本系统的资产；MCP 指向**系统之外**，成员由对端决定、本系统不掌握 |
| **自带的属性** | 设置：连接目标、超时等。权限：**能不能用**，以及**执行权限**（同 Tool 那三档） |
| **能组合什么** | **不组合任何资产。**它的内容来自对端，不是本系统的组合关系 |

**一处必须写明的后果**：对端的**可用性与版本不由本系统掌握**。
它提供的动作可能今天有、明天没有，而这**不是故障**。
**怎么应对归工具与技能那一块**，本 topic 只定它是一类资产、以及它的内容不是资产。

#### Connector

**一个外部消息来源的接入件**，把外部的消息送进来。

> **它是唯一方向朝里的一类。**Skill、Tool、MCP、Slash Command、Plugin、Agent Definition
> 回答「agent **能做什么、怎么做**」，[Loop Extension](#loop-extension) 回答
> 「**推进的时候在哪些位置插手**」，**只有它回答「agent 从哪里被触达」**。

| | |
|---|---|
| **和 Tool 的区别** | **方向相反**。Tool 是 agent 发起动作往外走，Connector 是外部消息往里送 |
| **和 MCP 的区别** | MCP 是**我出去调它**，Connector 是**它进来找我**。两者都指向系统之外，方向不同 |
| **它能做什么** | **只能送消息进来。**没有数据读取面，也没有管理面——接进来的东西不因此获得读取本系统数据或改变本系统配置的资格 |
| **自带的属性** | 设置：来源标识、投递目标等。权限：**能不能安装**、**送进来的消息按什么身份处理** |
| **能组合什么** | **不组合任何资产。** |

**它为什么仍然是资产**：它在 agent definition 里被声明、被持有、被授权、
按层级求值——**这四件事才是资产之所以为资产的原因**，不是「它提供动作」。
这一条扩展了「组装」的含义，已如实记在
[PF-001 decisions 第四节](../PF-001-identity-scope-and-agent-constraints/decisions.md#四已知的来源问题)。

#### Loop Extension

**挂在 agent 推进过程某个位置上的一段判断或动作。**

它声明三件事：**挂在哪个位置**、**管哪些情形**、以及自己的**干预力**——
只观察 / 可改写 / 可否决。一共有哪些位置、每个位置上看得见什么改得动什么，
归 [PF-012 §5.8](../PF-012-agent-loop-and-run/design.md#58-loop-拓展点)，本 topic 不重复。

**agent 不知道它存在。**这是它与其余各类最要紧的分别：skill 是给 agent 读的，
tool 是 agent 自己决定要不要调的，而拓展件是**系统在固定位置替 agent 调的**——
装了它，agent 面前的工具条目不会多出一条。

| | |
|---|---|
| **和 Tool 的区别** | Tool 由 **agent 自己决定**要不要调；拓展件由**系统在固定位置调**，agent 不知情，也拦不住 |
| **和 Skill 的区别** | Skill 是**给 agent 看的方法**，它读了才起作用；拓展件是**不给 agent 看的判断**，它不读也起作用 |
| **和 Connector 的区别** | 两者都不回答「能做什么」。Connector 回答「**从哪里被触达**」，拓展件回答「**推进的时候，在哪些位置插手**」 |
| **位置不是能力标识** | **同一个位置可以挂多个拓展件，各干各的**——它们是不同的资产，彼此不构成[同标识覆盖](../PF-001-identity-scope-and-agent-constraints/design.md#62-三种合成语义)。覆盖只发生在**同一个拓展件**的不同版本之间 |
| **自带的属性** | 设置：挂在哪个位置、管哪些情形。权限：**干预力**（只观察 / 可改写 / 可否决），以及谁可以安装它 |
| **能组合什么** | **不组合任何资产**（同 MCP 与 Connector） |

**干预力是权限，不是设置。**所以它走[收窄](#53-两个例子两种合成)那一套：
组织若把某个拓展件的干预力**锁**在「只观察」，租户就放不宽；组织只给默认值而不锁，
租户可以自己调。**装一个拓展件、却只给它「只观察」，是成立的配法**——
它照样每次都被调到，只是改不动东西。

**它为什么是资产**：与 [Connector 同一个理由](#connector)——它在 agent definition 里
被声明、被持有、被授权、按层级求值。**这是对资产定义的第二次扩展**，
来龙去脉记在 [PF-001 §4「资产的种类」](../PF-001-identity-scope-and-agent-constraints/design.md#资产的种类)末尾
「关于 Loop Extension」那一段。

> **组织超管在组织层配一份，租户在自己那层覆盖或收窄**，走的就是本 topic 已有的那一套。
> **「让用户能扩展或覆盖策略」不需要另造一套配置与授权**——这正是把它做成资产换来的东西。

#### Slash Command

**用户主动发起某件事的入口。**用户敲 `/什么` 触发。

它**绑定**要做的事：一个 skill、一段 prompt，或其他上下文。
命令本身不是做事的东西，它是**指路牌**。

**它不含键盘控制、shell 命令或系统命令。**那三样是另外的东西，
不因为都叫「命令」就归成一类。

| | |
|---|---|
| **为什么不并进 Skill** | 同一个 skill 可以有多个入口，也可以完全没有入口（只由 agent 自主使用）。绑定关系是多对多，合并会丢掉这层 |
| **自带的属性** | 设置：命令名、参数提示、绑定目标。权限：谁可以用这个入口 |
| **能组合什么** | **Skill**（绑定）。绑定不转移所有权——命令能指向一个 skill，不代表它拥有那个 skill |

#### Plugin

**把若干资产打包在一起分发与启用的单元。**

装一个 plugin，等于一次性获得它里面的全部东西；停用它，那些东西一起退场。
它解决的是**分发**问题：作者不必让用户逐个安装十几件东西。

| | |
|---|---|
| **和 Agent Definition 的区别** | Plugin 组合出来的**还是资产**，可以继续被组合；Agent Definition 组合出来的是**一个能跑的 agent** |
| **内含成员的地位** | 随 Plugin 的版本与使用权一起治理。它们**不取得独立的顶层生命周期**——你不能单独卸载 plugin 里的某一个 skill |
| **自带的属性** | 设置：启用哪些成员、成员的默认配置。权限：谁可以启用它 |
| **能组合什么** | **Skill、Tool、Slash Command、MCP、Connector、Loop Extension**，以及 Rules 这类声明性成员 |

#### Agent Definition

**一个 agent 的静态定义**：它由什么组装而成、以什么面貌工作。

**它不是会话，也不是运行实例。**改定义不会改变已经在跑的那个 agent；
一个定义可以同时有很多个运行实例。**定义与实例分别演进**，这条很要紧——
把它们混为一谈，就会出现「我改了配置，正在跑的任务突然换了行为」这种事故。

| | |
|---|---|
| **sub-agent 的定义** | **也属于这一类**，不是另一种东西。它作为 sub-agent 被引用时是被组合方，被实例化时是组合树的根 |
| **自带的属性** | 设置：**默认模型**、人格与语气、上下文策略等。权限：谁可以实例化它、谁可以派发它 |
| **能组合什么** | **全部八类**——Skill、Tool、Slash Command、Plugin、**MCP**、**Connector**、**Loop Extension**，以及**其他 Agent Definition**（作为 sub-agent） |

### 谁能组合谁

| 组合方 ↓ ／ 被组合 → | Skill | Tool | Slash Command | Plugin | MCP | Connector | Loop Extension | Agent Definition |
|---|:---:|:---:|:---:|:---:|:---:|:---:|:---:|:---:|
| **Skill** | ✗ | ✓ | ✗ | ✗ | ✗ | ✗ | ✗ | ✗ |
| **Tool** | ✓ | ✗ | ✗ | ✗ | ✗ | ✗ | ✗ | ✗ |
| **Slash Command** | ✓ | ✗ | ✗ | ✗ | ✗ | ✗ | ✗ | ✗ |
| **Plugin** | ✓ | ✓ | ✓ | ✗ | ✓ | ✓ | ✓ | ✗ |
| **MCP** | ✗ | ✗ | ✗ | ✗ | ✗ | ✗ | ✗ | ✗ |
| **Connector** | ✗ | ✗ | ✗ | ✗ | ✗ | ✗ | ✗ | ✗ |
| **Loop Extension** | ✗ | ✗ | ✗ | ✗ | ✗ | ✗ | ✗ | ✗ |
| **Agent Definition** | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ |

**只有 Agent Definition 能组合全部八类**，因为只有它是组装成 agent 的那个入口。

**三行全空，但理由是两种：**

| 哪几行 | 为什么空 |
|---|---|
| **MCP、Connector** | 它们的内容来自**系统之外**，由对端决定，不是本系统的组合关系。把对端的东西当成组合成员，就等于承诺本系统掌握它们的身份与生命周期——而那件事本系统做不到 |
| **Loop Extension** | 它是**一段自足的判断**，起作用靠的是被挂在那个位置上，不靠调用别的资产。真需要一个动作，那个动作属于它自己的实现，**不是它组合了一个 Tool**——否则 agent 面前的工具条目会凭空多出来 |

三条规则：

1. **引用指向能力标识，不指向具体资产**（见 §6.3）。因此覆盖发生后，
   所有引用自动指向当前生效的那一个。
2. **组合图不得成环。**Agent Definition 之间可以嵌套 sub-agent，
   但 A 引用 B、B 又引用 A 必须被拒绝——否则组装永远算不完。
3. **组合不转移所有权。**Plugin 里装了某个 skill，不代表 plugin 作者拥有它。

### 几个刻意不做的组合

| 不做 | 为什么 |
|---|---|
| Skill 组合 Skill | 目前**没有已知需要**，而允许它就要引入环检测与"哪一层的指引优先"这类问题。按最小正确模型，等真实需求出现再加 |
| Plugin 嵌套 Plugin | 同上。嵌套会让「内含成员随 plugin 版本治理」变成多层，版本与使用权都要跨层解释 |
| Plugin 含 Agent Definition | 分发一个现成的 agent 是个合理设想，但目前没有需要。留着不做，比先做一个没人用的结构安全 |

> 以上三条是 **PM 按「先做最小的正确模型」推的**，不是产品负责人裁决。
> 真实需求出现时可以加——**加是加法，不用改已有结构**。

### Tool 为什么是资产

值得单独说一句，因为这一条**与前身系统相反**。

`omne-next/omne_harness` 把 Tool 归为"组件"而不是顶层资产。
原因不是它不该是资产，而是**那个系统做不到工具的动态组装**。
本系统能做到，所以 Tool 是**可动态组装的资产之一**。

这条差异是有意的。见 [decisions.md 第四节](decisions.md#四已知的来源问题)。

### Plugin 不是 Cordis plugin

本项目内核用 Cordis，Cordis 也有 plugin 的概念。两者**完全不是一回事**：

| | Cordis plugin | 本 topic 的 Plugin |
|---|---|---|
| 是什么 | 运行时的代码装载单元 | 产品意义上的资产分发与组合单元 |
| 谁关心 | 实现与运行时 | 产品的使用者与管理者 |
| 归哪 | 技术设计 | 产品设计 |

**正文出现「Plugin」一律指后者。**指前者时必须写全「Cordis plugin」。

## 五、模型

### 5.1 组合是一种关系，不是几种

> **本节是 PM 推导，待产品负责人确认。**推理链见 [decisions.md](decisions.md)。

产品负责人给出的三个判断：

1. 资产之间是**组合关系**；
2. 资产组装成 agent，**本质上也是组合关系**；
3. 设置与某一类资产、权限与某一类资产，**本质上也是组合关系**。

三句话里的"本质上也是"都在说同一件事：**这些不是几种机制，是一种。**

```text
Agent Definition ──→ Plugin ──→ Skill  ⇄  Tool
       │               ├──→ Tool          ↑
       │               ├──→ Slash Command ┘（绑定 Skill）
       │               ├──→ MCP
       │               ├──→ Connector
       │               └──→ Loop Extension
       ├──→ Skill
       ├──→ Tool
       ├──→ Slash Command
       ├──→ MCP
       ├──→ Connector
       ├──→ Loop Extension
       └──→ Agent Definition        （sub-agent）

任一资产 ──→ 它的设置属性
         └─→ 它的权限属性
```

- **Agent Definition** 是唯一能组合全部八类的节点，因为只有它组装出 agent。
  被**实例化**时产生一个运行中的 agent，被**引用**时充当 sub-agent——
  所以它既能组合别人，也能被组合。
- **Plugin** 组合出来的**还是资产**，可以继续被组合。
- **Skill 与 Tool 互相引用**：skill 声明它要用到哪些动作，tool 声明它需要配套的指引。
- **MCP、Connector、Loop Extension 都是叶子**，一个都不往下组合，理由见 [§4](#谁能组合谁)。
- 完整的组合能力见 [§4「谁能组合谁」](#谁能组合谁)。

由此，「组装」不是第二种机制——**组装就是组合关系从一个 Agent Definition 展开求值的结果**。

### 5.2 设置与权限是资产的两种属性

这是本 topic 与 PF-001 相比最实质的一步：
**设置和权限不是一份预先存在的字段目录——它们是具体资产的两种属性。**

一个具体的资产（比如某个工具）自带这两种属性：

| 属性 | 举例 |
|---|---|
| **设置** | 某个 Agent Definition 的「默认模型」 |
| **权限** | 某个 Tool 的「执行权限」：问一下 / 自动 / 禁止 |

于是"谁的设置"这个问题不存在了——**设置总是某个资产的设置**。

#### 三方分工：资产定形状，各层配值，运行时求值

| 角色 | 谁 | 负责什么 |
|---|---|---|
| **定形状** | 资产本身 | 我有哪些设置项、哪些权限项，各自什么含义、取值域是什么 |
| **配值** | **持有该资产的组织与租户**，各自一份 | 在我这一层，这些项配成什么 |
| **求值** | 运行时 | 沿层级覆盖 / 收窄，算出这次组装 agent 实际用的值 |

**配值的资格来自持有。**一个层要为某资产配设置或权限，前提是它
[持有](../PF-001-identity-scope-and-agent-constraints/design.md#拥有获权选用)该资产。
组织没有这个工具，就配不了这个工具的执行权限——**配置权不能凭空出现**。

#### 由此得到两个推论

**一、项的目录不需要单独维护。**"有哪些设置项"的答案 = "装了哪些资产"的函数：

- 没装工具 X，就不存在"工具 X 的执行权限"这一项；
- 没引用 agent definition D，就不存在"D 的默认模型"这一项。

**项的存在性由组装决定，所以生效值不可能在组装之前算出来。**

**二、出厂默认层是 official 带来的。**
[official 是最小必需](../PF-001-identity-scope-and-agent-constraints/design.md#来源official-与-customized)，
必然在每次组装里；**出厂默认层的设置与权限，就是 official 资产自带的那一份。**
出厂默认层不需要另一套来源。

#### 「组织的设置」是视图，不是对象

这是上面那条分工的直接后果，但值得单独说，因为它推翻了一个很自然的想法。

**系统里不存在"组织设置"这么一个对象。**真正存在的、可以被读写的最小单位是：

```text
（身份层，具体资产，属性项） → 值
```

我们平时说的「组织的设置」「租户的权限」，是**在该身份持有的资产集合上做的投影**：

```text
组织 O 的设置  ≝  { (O, X, 项) → 值 | X ∈ O 持有的资产 }
租户 T 的权限  ≝  { (T, X, 项) → 值 | X ∈ T 持有的资产 }
```

| | 「组织设置」 | （层，资产，项）|
|---|---|---|
| 是什么 | 一个**视图** | 真正的对象 |
| 能不能独立存在 | 不能。持有的资产变了，它跟着变 | 能 |
| 管理界面上的「组织设置页」 | 这个视图的呈现 | — |

**为什么这条要紧**：若把「组织设置」当成对象来实现，就会出现一份
独立于资产的字段表，然后它与资产各自演化，最终对不上。
视图不需要维护——**它是持有关系的函数**。

### 5.3 两个例子，两种合成

**设置按覆盖**：

```text
资产：agent definition「代码助手」        ← 组织共享的那一个，只有这一个
  ├─ 组织 O 为它配的默认模型 = A
  └─ 租户 (O,我) 为它配的默认模型 = B     ← 覆盖
────────────────────────────────────────────
组装时生效：B
```

注意被覆盖的**不是资产本身**——用的还是组织共享的那个「代码助手」，
只是它的一项设置属性在租户层被配了别的值。这与
[PF-001 的"同能力标识覆盖"](../PF-001-identity-scope-and-agent-constraints/design.md#62-三种合成语义)
（整个资产被替换）**是两件事**。

**权限按收窄**：

```text
资产：工具 X，自带执行权限这项属性，取值域 { 问一下, 自动, 禁止 }，默认取「问一下」
  ├─ 组织 O 没有禁用它                     ← 没有收窄
  └─ 租户 (O,我) 把它配成「自动」           ← 收窄到 { 自动 }
────────────────────────────────────────────
组装时生效：自动
```

**"设成自动"看起来像放宽，其实是收窄。**关键在于：
权限的每一层给出的是一个**允许集合**，最终结果是各层的**交集**。
租户把它定成「自动」，就是把允许集合收窄成单元素集 `{自动}`——
**选择就是收窄到只剩一个。**

如果组织禁用了工具 X（收窄为空集），租户再怎么设也拿不到它：
空集与任何集合的交集还是空集。**这正是 PF-001 要的那条不可突破的边界。**

### 5.4 默认与强制：一个机制，三处适用

**「默认」和「强制」是两回事，但它们不需要两套机制。**

每一层对一个东西可以做两件事：

1. **给一个值**；
2. 声明这个值**不可再被下层覆盖**（`immutable`）。

| 加不加 immutable | 这层在说什么 | 下层能做什么 |
|---|---|---|
| **不加** | 「**默认**这样」 | 可以改 |
| **加** | 「**必须**这样」 | 改不了 |

这一个机制同时管三处：

| 用在哪 | 不加 immutable | 加 immutable |
|---|---|---|
| **设置的字段值** | 组织设个默认模型，成员可换 | 组织锁死模型，成员换不了 |
| **权限的取值** | 组织说默认「问一下」，成员可改成「自动」 | 组织锁死「问一下」，成员改不了 |
| **资产的替换** | 组织换了个自定义 skill，成员还能再换自己的 | 组织锁死自己那个（比如安全组件），成员换不了 |

> **权限比另外两者多一档。**权限的取值域是**枚举**的（问一下 / 自动 / 禁止），
> 所以它除了"锁死一个值"，还能**收窄到一个子集**——比如组织说"只许问一下或禁止，
> 不许自动"。`immutable(v)` 就是收窄到单元素集 `{v}`，是收窄的特例。
> 设置的取值域通常是开放的（比如模型名），谈子集没意义，只有"锁不锁"两态。
> **这一段是 PM 推导**，见 [decisions.md](decisions.md)。

### 5.5 资产替换的层级

**默认的替换次序**：

```text
official（出厂默认）  <  组织自定义  <  租户自定义
```

**official 永远可被替代。**它处在最底层，本来就是被替换的对象——
不存在"official 不许被换"这回事（它只是[不可被清空](../PF-001-identity-scope-and-agent-constraints/design.md#来源official-与-customized)）。
组织要锁，锁的是**组织自己那一层**。

**组织可以把自己的自定义资产标为 immutable**，租户就不能再替换它。
典型用途是重要的安全组件：公司换上自己的审计 skill，并且不许任何成员换掉。

### 5.6 四步：资产求值 → 组装 → 投影 → 层级计算

顺序是有意的，**不能换**。

| 步 | 做什么 | 输入 | 输出 | 语义归谁 |
|---|---|---|---|---|
| **1. 资产求值** | 这个租户有哪些资产可用 | (组织, 账号) + 四层作用域 | 每个能力标识一个生效资产 | [PF-001 §6.2](../PF-001-identity-scope-and-agent-constraints/design.md#62-三种合成语义) 的组合 + 同标识覆盖 |
| **2. 组装** | 这个 agent 实际由什么构成 | 一个 Agent Definition + 第 1 步的结果 | 沿组合图展开后的资产集合 | 本 topic §5.1 |
| **3. 投影** | 有哪些设置项、哪些权限项 | 第 2 步装上的每个资产**自带的属性** | 项的集合 | 本 topic §5.2 |
| **4. 层级计算** | 每一项的值是多少 | 第 3 步的每一项 + 各持有层配的值 | **组装时实际用的值** | PF-001 §6.2 的覆盖 / 收窄 |

**为什么顺序不能换**：

- **1 必须在 2 之前**——组装只能从"可用的"里面装。
- **3 必须在 2 之后**——装了什么，才知道有哪些项。项的**存在性**由组装决定。
- **4 必须在 3 之后**——先有项，才谈得上算它的值。

**有两轮层级计算，作用对象不同**：第 1 步作用在**资产**上（哪个资产生效），
第 4 步作用在**项**上（资产的某项设置/权限取什么值）。
混为一谈会得出"改一项设置等于换一个资产"这种结论。

**求值与组装不能合并。**合并的话，"组织禁用了某个 skill"与"这个 agent 没引用它"
会变成同一件事，而它们的产品含义完全不同——前者是管理决定，后者是设计选择。

## 六、产品规则

### 6.1 设置页是长出来的，不是画出来的

**我们的设置页和传统软件产品的设置页不是一回事。**

传统软件的设置页是**画好的**：有哪些项，产品定死，写在代码里。
我们的设置页是**长出来的**：

> **一个资产被加进来，它可配置的表单就自动生成、追加到设置页；
> 资产被移除，那块表单自动消失。**

这是[「设置是资产的属性」](#52-设置与权限是资产的两种属性)的直接产品体现——
设置页就是那个投影视图的样子。没有一份独立维护的字段清单，
**页面长什么样，是"持有了哪些资产"的函数**。

### 6.2 设置页分两块

| 块 | 归谁 | 里面是什么 |
|---|---|---|
| **界面偏好** | **账号** | 界面语言、时区一类**属于这个人本身**的偏好。跟着人走，在所有组织里都一样 |
| **资产的设置与权限** | **组织 / 租户** | 持有的每个资产各自的可配置表单，随资产增删自动增减 |

两块**不能混在一起**，因为它们是[两种正交的 context](../PF-001-identity-scope-and-agent-constraints/design.md#contextagent-运行时可感知的上下文信息)：
第一块跟着人，第二块跟着"人在哪个组织"。
把它们放同一个列表里，用户会以为改一个和改另一个是同类操作，
而实际上换个组织之后一个变了一个没变。

### 6.3 组合的引用指向能力标识

一个 plugin 包含某个 skill，**它包的是那个能力标识，不是某个具体资产**。
因此组织换上自己的自定义版本之后，**所有含它的 plugin 与 agent 自动用上新的**。

这与 [PF-001 §6.3「依赖指向能力标识」](../PF-001-identity-scope-and-agent-constraints/design.md#63-依赖与组合)
是同一条规则——组合与依赖不需要两套。

**为什么不能指向具体资产**：那样的话，组织换上的安全组件**进不了 plugin**，
[§5.5 的 immutable](#55-资产替换的层级) 就白标了——漏洞正好留在 plugin 里面。

**代价要说清楚**：plugin 作者**不能假定**自己包里的零件不被替换。
他应当面向**能力标识**编写，而不是面向某个具体实现。
这是"资产可被自定义替换"这个能力的固有代价，不是缺陷。

### 6.4 「移除」与「禁用」是两个动作

组织不让成员用某个工具，有两种意图，**产品上必须能分别表达**：

| 动作 | 结果 | 成员遇到什么 |
|---|---|---|
| **移除** | 该资产不再被这个组织持有 | agent 装不上，也**不知道**有这回事。成员问起，它只能说做不到，说不出为什么 |
| **禁用** | 资产还在，但权限收窄为空集 | agent 装上了，一调就被拒。它能说明「这项被组织关掉了」，成员知道可以去申请 |

**判据是成员该不该知道它存在。**

- 想让成员知道并且可以申请 → **禁用**。它给得出可解释的拒绝理由。
- 不想让成员知道这个能力存在 → **移除**。

两者都保留，因为把它们并成一个动作，总有一头表达不了。

## 七、取舍

| 面临的选择 | 选了 | 为什么 |
|---|---|---|
| 组合是**一种**关系还是几种 | 一种 | 资产之间、资产到 agent、资产到它的属性，如果各用一套规则，就有三处覆盖语义、三个出错的地方 |
| 设置与权限是**独立对象**还是**资产的属性** | 属性 | 独立对象意味着一份脱离资产维护的字段表，它与资产各自演化，最终必然对不上。作为属性，「有哪些项」自动等于「持有了哪些资产」 |
| Tool 是**组件**还是**资产** | 资产 | 本系统能做工具的动态组装。前身系统把它归为组件是能力所限，不是它本该如此 |
| 「默认」与「强制」用**两套语义**还是**一个标记** | 一个标记（`immutable`） | 两套语义要在每一类对象上各解释一遍；一个标记落在同一个字段上，且资产、设置、权限三处通用 |
| 组合的引用指向**能力标识**还是**具体资产** | 能力标识 | 指向具体资产的话，组织换上的安全组件进不了 plugin，`immutable` 就白标了。代价是 plugin 作者不能假定零件不被替换 |
| 「移除」与「禁用」合成**一个动作**还是**两个** | 两个 | 「不给你」和「给了但不许用」是不同的管理意图，合成一个总有一头表达不了。判据是成员该不该知道它存在 |
| 组合关系**先做全**还是**先做最小** | 最小 | Skill 套 Skill、Plugin 套 Plugin、Plugin 装 Agent 都暂不做——没有已知需要，且各自会带来环检测或跨层治理的负担。**加是加法，不用改已有结构** |
| 拓展挂件做成**第八类资产**还是 **loop 自己的一项配置** | 第八类资产 | 做成 loop 的配置，就得为它另造一套「谁能装、组织配了租户能不能改、锁死了怎么办」——**而这套东西资产已经有了**。代价是推翻「资产恰有七类」这句已拍板的话，**产品负责人在知情的前提下选了推翻**（见 [PF-001 decisions](../PF-001-identity-scope-and-agent-constraints/decisions.md#一拍板记录)） |
