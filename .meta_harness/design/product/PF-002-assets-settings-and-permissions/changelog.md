# PF-002 变更历史

记录**产品设计本身**的演进：哪一版改了什么含义、为什么改、下游要复核什么。
错别字、链接修复、段落搬家不记这里。

技术投影用 `provenance.json` 引用具体 rev，所以这里的 rev 不准会直接传导到实现侧。

## rev 7 · 工作区只能禁用它自己提供的那批资产 — 2026-09-22

**产品负责人直接裁决**：「工作区限定『工作区只能禁用它自己提供的那批资产』。」

| 改了什么 | 从什么改成什么 |
|---|---|
| **工作区那一级「禁用」的作用范围** | rev 6 是「照样配得了这一项、照样参与过滤」，**没有范围限定**；现在**只对工作区这一级提供的那批资产生效**。对组织、租户、出厂层提供的资产，**工作区配的那个值不参与析取** |
| **§5.7 的第二条理由** | rev 6 在 [decisions](decisions.md#二pm-推导) 里记着它「在禁用这一维上不适用了」；**这一版由本条限定收口，它照样成立**——工作区能收掉的只有它自己拿出来的那些 |
| **§5.6 第 1 步 · §5.7 · §5.8** | 三处提到「工作区也参与禁用」的措辞一并加上范围限定 |
| **§7 取舍** | 新增一行：选了「只管它自己那批」，代价是**「禁用」的合成不再是一句无条件的析取**——要先看工作区是不是这份资产的提供者 |
| **acceptance** | 新增「同一个工作区把组织提供的资产配成禁用 → 禁不掉」一条场景、一条判据、一条「绝不能发生」 |

**其余关于禁用的结论一个字都没改**：它仍是每份持有资产上的一项布尔设置，
**任一层为真即不可见**，本层改回假只去得掉本层那一个真，**下层开不回上层禁的**；
[official 仍然不可禁用](design.md#禁用是逐层配的布尔设置任一层为真即不可见)。

**下游要复核**：任何**把工作区那一级的禁用值直接并进全局析取**的实现——
现在它要先按**提供者**过滤一次。

## rev 6 — 2026-09-22

**三条裁决落正文**：每一类资产的**身份是「类别 ＋ name」**；**工具定义可以自带实现**；
**禁用是逐层配的布尔设置，合成走析取**。
依据：[产品负责人 2026-09-22 的三条直接裁决](decisions.md#2026-09-22--身份与实现解耦工具定义可自带实现禁用按析取合成)，原话逐字在那里。

### 一、身份与实现解耦

| 位置 | 现在怎么说 |
|---|---|
| [§4 身份是「类别 ＋ name」](design.md#身份是类别--name其余归实现)（新增一节） | **身份 ＝ 类别 ＋ name**，在类别内决定同一性；参数形状、说明、返回形状、子命令集合、实现包**一律不参与**。同一身份下平台、组织、租户各可有一套实现，凭同一身份互相替代 |
| [§4 八类资产](design.md#八类资产)各节的表 | 每一类各加一行 **「身份」**，并列明**明确不是身份**的信息 |
| [acceptance](acceptance.md) | 新增：工作区禁用、同类同名替代（参数与说明不同也照样替代）、以及「两份同名资产并存各算各的」进「绝不能发生」 |

**这一条没有引入新概念**——它就是 [PF-001 的能力标识](../PF-001-identity-scope-and-agent-constraints/design.md#范围化对象)，
本次补的是**它由什么构成**；替代规则仍归 PF-001。

### 二、工具定义可以自带实现，直到完整 package

| 位置 | 现在怎么说 |
|---|---|
| [§4 Tool](design.md#tool) | **工具定义是这份资产在数据与治理层面的身份与表示**，**可以自带实现**；实现装不进当前运行时时走[同名替换件](../PF-006-tools-and-skills/design.md#63-不可用时装的是同名替换件不是不装)。怎么装进运行时**不进产品正文** |

**作废了什么**：「它有两半，缺一不可……**只有一份没法执行的定义，不算可用**」这句整体作废——
**没有可装的实现不是「不可用」的判据**，[不可用由依赖解析算](../PF-006-tools-and-skills/design.md#64-依赖声明与解析)，
后果是可见但用了一定失败。

### 三、禁用是析取合成的布尔设置

| 位置 | 现在怎么说 |
|---|---|
| [§6.4](design.md#禁用是逐层配的布尔设置任一层为真即不可见)（该小节改名） | 禁用是**每份持有资产上的一项布尔设置**，各归属层各配各的，**合成语义是析取**：任一层为真即不可见，下层开不回来。**[工作区](design.md#工作区)同样配得了、同样参与过滤**；official 仍不可禁用 |
| [§5.4](design.md#54-默认与强制一个机制三处适用) | 加一句：析取**等价于「布尔设置 ＋ 真即 `immutable`」**，**不是第三种合成规则** |
| [§5.6 第 1 步](design.md#56-四步资产求值--组装--投影--层级计算) | 输入改成**各归属层配的「禁用」值（含工作区）**，过滤按它的求值结果 |
| [§5.7](design.md#57-工作区那一级不参与权限计算) | 边界写准：它挡的是**授权与权限**；**禁用是设置，不在此列** |
| [§5.8](design.md#58-两套层次不是一套) | 工作区参与「有哪些资产」这一步，**包括它自己配的那项禁用** |
| [flows §1.5](flows.md#15-不让成员用某个工具)、[§3.1](flows.md#31-一个资产在某个范围里) | 「标上禁用标记」改为「把『禁用』这项设置配成真」；状态图不变 |

**作废了什么**：「**禁用记录**」这个说法作废——**它不是第三类东西，是一项布尔设置**。
**§6.4 的结论一条没变**：禁用仍是不可见、配置原样保留、本层开得回本层配的那个真。

## rev 5 — 2026-09-22

**一条裁决落正文：[禁用](design.md#64-移除与禁用是两个动作)是持有关系上的一个开关，
不是权限收窄为空集。**
依据：[产品负责人 2026-09-22 的直接裁决](decisions.md#2026-09-22--禁用是持有上的开关对-agent-与移除一样不可见)，原话逐字在那里。

### 一、判据换了，落点也换了

| 位置 | 现在怎么说 |
|---|---|
| [§6.4](design.md#64-移除与禁用是两个动作) | 判据是**收回持有，还是暂时关掉**。移除 = 不再持有、配置随之消失、表单消失；禁用 = 仍然持有、**配置原样保留**、表单标「已禁用」、**能启用回来** |
| [§6.4 对 agent](design.md#但对-agent-来说两者一样都不可见) | **两者对 agent 一样：都不可见**。装配第一步就按禁用表滤掉，agent 装不上也无从知道。**成员要知道去申请，看的是设置页** |
| [§6.4 按层](design.md#禁用是逐层配的布尔设置任一层为真即不可见) | **禁用表按层，任一层禁用即不可见**；启用只去得掉本层自己的标记，**下层开不回上层禁的**——与权限取交集同向的收窄语义 |
| [§5.3](design.md#53-两个例子两种合成) | 「组织禁用了工具 X（收窄为空集）」改为「组织把这项权限收窄为空集」，并点明**那不是禁用**：收空权限的工具照样装得上、agent 照样看得见 |
| [§5.6 第 1 步](design.md#56-四步资产求值--组装--投影--层级计算) | 资产求值的输入补上**各层的禁用记录**：先按持有取，再按禁用滤 |
| [§7 取舍](design.md#七取舍) | 两个动作的理由改成「配置跟着走 / 配置留着还能开回来」，并写明**代价是 agent 那一侧分不出这两者** |
| [flows §1.5](flows.md#15-不让成员用某个工具)、[§3.1](flows.md#31-一个资产在某个范围里) | 状态图不变，表格补「组装时」一列；两者的差别在**设置页那一列**，不在组装那一列 |
| [acceptance](acceptance.md) | 「移除与禁用可分辨」的判据从**看 agent 的回答**改成**看设置页**；新增两条：租户开不回组织禁的、启用回来用的还是原来配的值 |

### 二、作废了什么

**「禁用 = 权限收窄为空集、agent 装上了一调就被拒、能解释被组织关掉了」这套说法整体作废。**
权限收窄为空集这件事本身仍然存在（[PF-001 §6.2](../PF-001-identity-scope-and-agent-constraints/design.md#62-三种合成语义) 的交集语义没变），
**但它不再叫「禁用」**。

**由此分清了两件一直被混在一起的事：**

> **禁用是不可见，[不可用](../PF-006-tools-and-skills/design.md#63-不可用时装的是同名替换件不是不装)是可见但用了一定失败。**

## rev 4 — 2026-09-21

**补上资产归属的第三级：[工作区](design.md#工作区)。**
依据：[产品负责人两段裁决](decisions.md#2026-09-21--工作区是资产归属的第三级)。

### 一、新增一个概念、一条次序、一条硬规则

| 位置 | 内容 |
|---|---|
| [§4 工作区](design.md#工作区) | 一个会话挂上的宿主机目录，**同时是资产归属的第三级**，与组织、租户**同形**。两处不同：**运行时才确定**、**跟着目录走而不是跟着会话走** |
| [§5.5](design.md#55-资产替换的层级) | 替换次序补一级：`official < 组织 < 租户 < 工作区` |
| [§5.7](design.md#57-工作区那一级不参与权限计算) | **授权与权限相关的配置，一概不从工作区来**——**系统加载的时候就把它滤掉**，放宽的收紧的**都不作数** |

### 二、为什么授权与权限一概不从这里来

**工作区是一个目录，而目录跟着别人的代码一起来**——`git clone` 下来就带着它自己那一套。

> **一个仓库不能给自己提权。**

**连「只许往严里改」也不留**，三条理由在 [§5.7](design.md#57-工作区那一级不参与权限计算)；
最要紧的一条是**「只许收紧」要求系统逐条判断方向，而那个判断本身就是攻击面**——
同一条配置在这一维看着是收紧，在另一维可能正好相反。**加载时就不收，这个判断压根不存在。**

**四家在跑的 harness 各自独立地挡了同一类事**（[证据逐条在调研里](../../../research/agent-harness-session-design/research.md)），
所以这不是我们发明的谨慎，**而是另做一种选择要付举证责任**。

**边界写得很紧**：这条**只管授权与权限**。资产与设置照常从工作区求值——
**能力和偏好可以从项目里来，权力不行**。

### 三、取名：叫「工作区」不叫「项目」

产品负责人两次提到它用了两个词。**PM 选了「工作区」**，「项目」登记为弃用说法，
[三条理由在 decisions](decisions.md#为什么这一级叫工作区而不叫项目)——
核心一条是**「项目」在别处的正常用法躲不掉，收窄它代价过高**。

### 四、[§5.8](design.md#58-两套层次不是一套)：两套层次，不是一套

**「工作区在四层作用域里站在哪」的答案是：它不站在那里。**
资产归属是 `official < 组织 < 租户 < 工作区`，作用域层是 `出厂默认 < 组织 < 租户 < 会话`——
**两套各答各的**：归属答「谁持有、谁替换得了谁」，作用域答「属性取什么值」。
**PF-001 不用改。**

## rev 3 — 2026-09-19

**补入第八类资产：Loop Extension（拓展件）。**七类变八类，随
[PF-001 rev 7](../PF-001-identity-scope-and-agent-constraints/changelog.md) 一同修订。

**这一版推翻了 rev 1 立的一句 PM 推导**——「Hooks、Rules 是 Plugin 的组合成员，不是第六类」。
Rules 那一半仍然成立，**Hooks 那一半被改判**。

### 改了什么

| 地方 | rev 2 | rev 3 |
|---|---|---|
| 资产的种类 | 七类 | **八类**，补入 **Loop Extension** |
| Loop Extension 是什么 | 没有位置。挂件按 [Plugin 的成员](decisions.md#二pm-推导)处理 | **一类资产**：挂在 loop 某个位置上的一段判断或动作，声明位置、情形与干预力 |
| Connector 那句「唯一方向相反」 | 「其余六类回答能做什么」 | **改写**。八类里 Connector 仍是唯一回答「从哪里被触达」的，但「其余」不再整齐——**拓展件回答的是第三个问题**：推进的时候在哪些位置插手 |
| Plugin 能组合什么 | Skill、Tool、Slash Command、MCP、Connector + Hooks、Rules | 同前，**Hooks 换成 Loop Extension 正式列入**，Rules 仍按声明性成员 |
| Agent Definition 能组合什么 | 全部七类 | **全部八类** |
| 「谁能组合谁」矩阵 | 7×7 | **8×8**。Loop Extension 那一行全空，**但空的理由与 MCP、Connector 不是一种**，正文分开写了 |
| §5.1 的组合图 | 没画 MCP、Connector | **补全**，并加上 Loop Extension——三者都是叶子 |
| §8 边界 | 「除 PF-001 与 PF-003 外都还没有产品设计」 | **过时了，重写**：装配归 [PF-004](../PF-004-agent-definition-and-assembly/README.md)，拓展点位置归 [PF-012](../PF-012-agent-loop-and-run/README.md)，只剩「资产的开发与发布」没有主 |

### 为什么值得推翻一条已立的推导

rev 1 那条推导**在当时是对的**：挂件没被列进那几类，而组合关系已经成立，
「成员」与「独立资产」不再互斥——按成员处理是唯一自洽的读法。

**变的是前提。**产品负责人要求挂件能被**租户与组织超管各自装、各自覆盖**，
而 [Plugin 的成员不取得独立的顶层生命周期](design.md#plugin)——它拿不到独立的持有与层级求值。
于是只剩两条路：**给成员补一套治理**，或者**让它成为资产**。
后者不新增任何机制，**这就是选它的全部理由**。

### 一条最容易做错的实现

**同一个位置挂多个拓展件，彼此不构成[同标识覆盖](../PF-001-identity-scope-and-agent-constraints/design.md#62-三种合成语义)。**
覆盖的单位是**能力标识**，位置不是标识。
不点破，实现会按「一个位置一个挂件」做，**而那会让第二个挂件被静默丢掉**。

### 下游要复核

- 任何按「资产恰有七类」实现的枚举、校验或界面；
- **[PF-004](../PF-004-agent-definition-and-assembly/README.md) 的装配**：组装时要多认一类资产，
  且**拓展件不进[动作空间](../../ubiquitous_language/terms/capabilities-and-composition.md#ul-action-space--动作空间--action-space)**；
- **[PF-012](../PF-012-agent-loop-and-run/README.md) rev 2** 里「拓展点不是资产」那几处，**已经不成立**，
  该 topic 的 rev 3 一并修订。

本次一并把下游正文里「资产七类」的措辞同步为「八类」（PF-004、PF-005、PF-006、PF-007
与词表），**那些 topic 的实质内容未变，因此不递增它们的 rev**；
词表里只有 [UL-connector](../../ubiquitous_language/terms/capabilities-and-composition.md#ul-connector--连接件--connector)、
[UL-plugin](../../ubiquitous_language/terms/capabilities-and-composition.md#ul-plugin--插件--plugin)、
[UL-agent-definition](../../ubiquitous_language/terms/capabilities-and-composition.md#ul-agent-definition--agent-定义--agent-definition)
三条实质受影响，出处的 rev 标注随之更新，其余保持旧 rev——**那样才看得出哪些条目真被复核过**。

## rev 2 — 2026-09-17

**补入两类资产：MCP 与 Connector。**五类变七类，随
[PF-001 rev 6](../PF-001-identity-scope-and-agent-constraints/changelog.md) 一同修订。

| | rev 1 | rev 2 |
|---|---|---|
| 资产的种类 | 五类 | **七类**，补入 MCP 与 Connector |
| 外部工具来源 | 没有位置 | **MCP**：一批动作的来源，本身不可调用。**它带来的动作不是独立资产** |
| 外部消息来源 | 没有位置 | **Connector**：把外部消息送进来，**方向与其余六类相反** |
| Plugin 能组合什么 | Skill、Tool、Slash Command | 再加 **MCP、Connector** |
| Agent Definition 能组合什么 | 全部五类 | **全部七类** |
| 组合关系表 | 5×5 | **7×7**，MCP 与 Connector 两行**全空** |

### 两条要点

**MCP 的形状等同于「多命令 tool 与它的子命令」**：接入点是资产，内容随它治理。
反过来做——每个 MCP 工具各算一份资产——会让**资产身份随对端版本漂移**，
而资产是要被持有、覆盖、转移的东西，身份必须稳定。

**Connector 是七类里唯一方向相反的一类**，它回答「agent 从哪里被触达」。
这扩展了「组装」的含义，扩展与撤回条件记在
[PF-001 decisions 第四节](../PF-001-identity-scope-and-agent-constraints/decisions.md#四已知的来源问题)。

### 下游要复核什么

- **不要为每个 MCP 工具登记资产。**
- **Connector 的权限必须回答「送进来的消息按什么身份处理」**——不定这一项，
  租户隔离会在入口处破掉。
- Plugin 可打包 MCP/Connector 这一条是 **PM 推的**，见
  [decisions.md 第二节](decisions.md#二pm-推导)，可撤。

## rev 1 — 2026-09-17

**首版。**把 [PF-001](../PF-001-identity-scope-and-agent-constraints/README.md)
里的设置、权限、资产三者展开。

### 这一版确定了什么

| 方面 | 结论 |
|---|---|
| 三者的地位 | 只有**资产**是独立对象；**设置与权限是资产的两种属性** |
| 身份层的设置 | 是**视图**，即该身份持有的资产集合上的投影。最小单位是（身份层，具体资产，属性项）→ 值 |
| 资产的种类 | **五类且穷尽**：Skill、Tool、Plugin、Agent Definition、Slash Command |
| 组合 | **只有一种关系**，贯穿资产之间、资产到 agent、资产到它的属性 |
| 谁能组合谁 | 只有 Agent Definition 能组合全部五类；Plugin 组合 Skill/Tool/Slash Command；Skill 与 Tool 互相引用；Slash Command 绑定 Skill |
| 引用 | 指向**能力标识**，不指向具体资产。组合与依赖同一条规则 |
| 默认与强制 | 一个 `immutable` 标记，管设置、权限、资产替换**三处** |
| 求值 | **四步且顺序不能换**：资产求值 → 组装 → 投影 → 层级计算 |
| 设置页 | **长出来的**，随资产自动增删；分「界面偏好」与「资产设置与权限」两块 |
| 不让用 | **移除**与**禁用**是两个动作，判据是成员该不该知道它存在 |

### 下游要注意的四处

- **不要为「组织设置」建一张独立的字段表。**它会与资产各自演化，最终对不上。
  设置页是持有关系的函数，不需要维护。
- **四步顺序不能换。**项的存在性由组装决定，所以生效值**不可能**在组装之前算出来。
- **引用必须指向能力标识。**指向具体资产的话，组织换上的安全组件进不了 plugin，
  `immutable` 就白标了——漏洞正好留在 plugin 里面。
- **plugin 作者不能假定自己包里的零件不被替换。**他应当面向能力标识编写。
  这是"资产可被自定义替换"的固有代价，不是缺陷。

### 本版刻意不做的三种组合

Skill 套 Skill、Plugin 套 Plugin、Plugin 装 Agent Definition。

三者都**没有已知需要**，且各自会带来环检测或跨层治理的负担。
**加是加法，不用改已有结构**——真实需求出现时再加，不必改动现有形状。

### 本版留下的缺口

- **未决项：无。**
- **待裁决：无。**

被排除的内容在 [design.md §2 非目标](design.md#非目标)，那是**边界**——
发现它们缺失不算缺陷。下游遇到本文档没回答的问题，应当停下来问，
而不是挑一个看起来合理的实现。
