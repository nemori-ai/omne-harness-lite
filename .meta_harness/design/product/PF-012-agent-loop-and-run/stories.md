### ST-012-01 · 工具任务完成后得到基于真实结果的答复

- **价值**：用户能让会话执行一次实际操作，再得到使用真实工具结果的答复。
- **覆盖场景**：[S1](acceptance.md#一可观察的场景)
- **演示**：
  1. 准备一个已合法选入并允许执行的简单工具，结果带有本次执行生成的可核对标记 → 本次工具、输入和执行条件可辨认。
  2. 用户在会话中请求使用该工具完成任务 → 模型发出调用，工具实际执行并返回结果，最终回复包含真实结果。
  3. 查看同一 Run 的过程与终结 → 调用、结果和完成归属清楚；重复读取组装内容不会新增日志条目或再次执行工具。
- **不含**：多动作批次、人工批准、后台、工具更新和故障恢复；实际模型与工具采用依据及准入仍须成立。
- **前置**：ST-015-01、[ST-006-04](../PF-006-tools-and-skills/stories.md#st-006-04--工具实际执行的是装配选中的唯一实现)
- **就绪**：是

### ST-012-02 · 模型彻底失败时得到明确结果

- **价值**：用户分得清任务已失败与仍在等待，不会在无结果的会话中一直等下去。
- **覆盖场景**：[S18](../PF-013-model-profiles-and-invocation/acceptance.md#一次调用出事)、[S12](acceptance.md#一可观察的场景)
- **演示**：
  1. 准备本 Run 无法自行补齐的调用条件缺口，例如模型凭据不可用，发起一个文本任务 → 本次模型调用在没有回复时按自身规则彻底失败，原因上交到原 Run 消费位置，不假装仍在等模型。
  2. 查看该 Run 与会话 → 本 Run 因缺少处置条件将非常态上交会话，Run 为 failed，失败原因可查，会话和原输入仍在；本租户的非常态接收记录可查，上交不因 Run 已终结而中止。
  3. 故障解除后，用户在同一会话另发一个问题 → 新工作可以开始，原失败 Run 不复活。
- **不含**：模型运行时失联、模态转换否决、改变重试策略，以及跨租户或组织的非常态投递。
- **前置**：ST-014-01
- **就绪**：是

### ST-012-03 · 工具执行失联后不会被系统自动重跑

- **价值**：用户能看到工具的真实失败原因，已经可能发生的外部效果不会被系统悄悄做第二遍。
- **覆盖场景**：[S2](acceptance.md#一可观察的场景)、[S70](acceptance.md#一可观察的场景)
- **演示**：
  1. 发起一次前台工具任务，在调用已发出、结果尚未保存时确认 Agent Runtime 已交还，再让系统整体停机，使原工具执行也失去连续性 → 恢复对账能够核对原执行已不在且没有结果；这与只丢 Agent Runtime 分得清。
  2. 重启系统，不打开或刷新会话，等待自动恢复后再查看工具位置 → 追补失败 ToolMessage，原因为工具执行异常中断；不是用户中断，也没有自动重发原调用。
  3. 查看自动恢复后的处理 → 没有用户查看或新消息触发，原 Run 也不会永远停在等待，agent 看见失败后按任务继续判断；若它另行选择调用，那是新的动作，可与原执行区分。
- **不含**：自动补偿、撤销外部效果、后台工具及仍存活执行的恢复。
- **前置**：ST-012-01、[ST-006-15](../PF-006-tools-and-skills/stories.md#st-006-15--工具自己的运行进程失去后原执行落失败且不重来)
- **就绪**：是

### ST-012-04 · 更换执行者时模型仍在回答原问题

- **价值**：仅 Agent Runtime 消失时，用户的原模型请求继续，不重复付费发问，也不会丢掉已返回的答复。
- **覆盖场景**：[S76](acceptance.md#运行时归属与句柄)、[S78](acceptance.md#运行时归属与句柄)、[S85](acceptance.md#运行时归属与句柄)、[S27](../PF-015-session-lifecycle-and-ownership/acceptance.md#运行时归属与执行关联)
- **演示**：
  1. 发起真实模型请求，只销毁唯一 Agent Runtime，分别覆盖首 token 前和之后 → 原模型执行继续，零句柄期间真实输出及费用仍可查询，没有重新发出请求。
  2. 再发起一轮请求，在原模型仍运行时普通追加一条消息并仅销毁、重起 Agent Runtime → 消息保持排队，重建没有重新发出原请求；同一 Run 的新尝试接续原调用，原消费者取得回复，原步骤收场后才按普通追加规则承接新消息。
  3. 再让模型先完成、新执行者稍后接手 → 原结果仍可承接，只交付一次；费用归原调用与原发起尝试，不因换等待者再计一笔或推定崩溃浪费。
- **不含**：模型自身失联、首 token 前重发规则、内部 hook／压缩调用、reload 和模型副本 ACK／清理。
- **前置**：ST-015-01、ST-014-02
- **就绪**：是

### ST-012-05 · 更换执行者不会让原工具任务重做

- **价值**：用户的前台工具任务可以在等待者消失后继续，结果已经回来时也能被正确认回。
- **覆盖场景**：[S68](acceptance.md#一可观察的场景)、[S71](acceptance.md#一可观察的场景)、[S77](acceptance.md#运行时归属与句柄)
- **演示**：
  1. 发起一次可核对执行次数的前台工具任务，仅销毁 Agent Runtime，保留工具执行 → 工具仍在跑，没有被取消，也没有被补成失败。
  2. 重起 Agent Runtime 后让原工具返回 → 原 Run 接续原执行，用户得到工具结果，实际工具只执行一次。
  3. 再让工具在重起 Agent Runtime 前完成 → 新尝试读取原结果，只承接一次；原调用、原尝试及真实费用归属不变。
  4. 对模型也重复“原调用先完成、等待者稍后接手”的结果承接检查 → 两类原调用均只承接一次，未因先完成而另起调用。
- **不含**：工具自身失联、后台转移、取消和派发子会话；模型在途连续性由前置卡交付。
- **前置**：ST-012-01、ST-012-04
- **就绪**：是

### ST-012-06 · 旧尝试的迟到结果和费用仍可查但不能续跑

- **价值**：用户能查到真实花费和执行结果，同时已经结束或被替代的工作不会偷偷继续。
- **覆盖场景**：[S50](acceptance.md#一可观察的场景)、[S50a](acceptance.md#一可观察的场景)、[S66g](acceptance.md#一可观察的场景)、[S79](acceptance.md#运行时归属与句柄)
- **演示**：
  1. 让原尝试已发出调用，再由新尝试取得同一 Run 的推进资格，随后让旧尝试恢复并尝试继续工作 → 旧尝试不能写推进事实或发起新工作。
  2. 让原已发调用此时返回结果或费用 → 原结果与账目仍保存，归属原调用和原发起尝试；当前尝试可以承接仍在等待的结果。
  3. 在另一轮中让 Run 先终结、原费用稍后到达 → 费用仍归原 Run 并标明迟到，终态不变，没有因此新开或复活 Run。
- **不含**：后台结果作为新输入开启后续 Run、外部效果撤销、模型副本回收和跨会话费用汇总。
- **前置**：ST-012-04、ST-012-05、ST-014-04
- **就绪**：是

第二期按用户确认的子期推进：2A 可控的人机协作（11张）、2B 稳定完成项目长任务（15张）、2C 扩大委托与自主执行（7张）。每张卡的“子期”标示所属批次，不表示交付状态；子期内卡序为 PM 建议。撰写授权与来源范围见 [decisions](design.md)。就绪只表示覆盖的产品场景写定，不表示整包接受、技术承诺接受或实现完成。

### ST-012-07 · 答复后接上原工作和等待期间的新消息

- **子期**：2A · 可控的人机协作
- **价值**：等待不会占着执行者，重建后仍能认回答复和原任务。
- **覆盖场景**：[S4](acceptance.md#一可观察的场景)、[S17](acceptance.md#一可观察的场景)、[S29](acceptance.md#一可观察的场景)、[S52](acceptance.md#一可观察的场景)、[S53](acceptance.md#一可观察的场景)
- **演示**：
  1. 让系统判断和租户 hook 出卡，期间发送普通消息并让后台结果到达 → 卡记录能指认出卡者；Run 停在等人，本次尝试退出、不占计算，新增输入如实入日志。
  2. 回收 Agent Runtime 后答完整批卡 → 同一 Run 以新尝试继续，普通等待不补异常对账，等待期间输入一起承接。
  3. 另让已调用过模型的 hook 出卡，再使系统崩溃，恢复后答复 → hook 接续既有调用及答复，不重复模型请求、不再出新卡，再作原位置的判断。
- **不含**：工具自身执行失联的 Ask 失败、后台卡片及模型可读视图缓存。
- **前置**：ST-008-05、ST-014-02、ST-012-04、ST-006-12
- **就绪**：是

### ST-012-08 · 后台任务完成后主动告诉用户

- **子期**：2B · 稳定完成项目长任务
- **价值**：用户无需回来追问，也能得知后台任务的真实结果。
- **覆盖场景**：[S32](acceptance.md#一可观察的场景)、[S33](acceptance.md#一可观察的场景)、[S75](acceptance.md#持久化投影与完整函数输入)、[S35](../PF-014-inbound-intake-and-queueing/acceptance.md#什么会让队列从空变成非空)、[S36](../PF-014-inbound-intake-and-queueing/acceptance.md#什么会让队列从空变成非空)
- **演示**：
  1. 发起“构建完成告诉我”，工具转后台；在原 Run 尚未终结时仅重建 Agent Runtime → 后台原执行仍关联，不重新发出构建；随后让原 Run 完成，会话没有新输入时不空起主流程 Runtime。
  2. 让后台构建在会话未归档时完成，不发送新消息 → 结果入日志和队列，自动开新 Run 通知用户，旧 Run 终态不变。
  3. 再让后台结果在另一 Run 正在跑时到达 → 不另开 Run，当前 Run 在下一次取批承接结果。
- **不含**：后台卡片、通知渠道和归档后迟到结果承接。
- **前置**：ST-006-12、ST-014-01
- **就绪**：是

### ST-012-09 · reload 后接续原调用并采用有效新选择

- **子期**：2B · 稳定完成项目长任务
- **价值**：用户能更新有效配置，同时继续已经发出的原任务。
- **覆盖场景**：[S86](acceptance.md#重装配与独立执行交接)、[S88](acceptance.md#重装配与独立执行交接)、[S89](acceptance.md#重装配与独立执行交接)、[S90](acceptance.md#重装配与独立执行交接)、[S96](acceptance.md#重装配与独立执行交接)、[S29](../PF-014-inbound-intake-and-queueing/acceptance.md#什么会让队列从空变成非空)、[S7](../PF-015-session-lifecycle-and-ownership/acceptance.md#创建变化与恢复)
- **演示**：
  1. 在模型生成中合法 reload，再让原模型完成 → 保留 Run 并开新尝试，流继续、费用只计一次、原消费者只承接一次；受理 reload 不改变队列或完成判据。
  2. 原工具正在改旧工作区时换新工作区 → 旧工具仍在旧目录，后续调用使用实际生效的新入口；旧模型提出绑定已变化的动作时交回 agent 重判，不按同名执行。
  3. 原动作已批准且绑定参数未变时 reload → 不重复出卡。另做普通等待重建并发布同身份新定义 → 仅重建不升级或重置模式，新 Run 才按最新有效定义装配，历史采用值不改。
- **不含**：失败候选与交接竞争、内部 hook 接续和任何自动升级政策。
- **前置**：ST-012-04、ST-012-05、ST-015-06、ST-020-01
- **就绪**：是

### ST-012-10 · 无效或竞争的 reload 不破坏当前任务

- **子期**：2B · 稳定完成项目长任务
- **价值**：用户能知道实际生效了什么，更新失败或竞争不会悄悄改变原任务。
- **覆盖场景**：[S87](acceptance.md#重装配与独立执行交接)、[S93](acceptance.md#重装配与独立执行交接)、[S94](acceptance.md#重装配与独立执行交接)
- **演示**：
  1. 分别提交缺必需工具、无效配置及绕 immutable 的候选 → reload 明确失败，旧有效数据不被部分替换。
  2. 分别做无变化、重复提交、旧候选晚到和切换途中崩溃 → 不重复外部执行，旧候选不覆盖较新选择；恢复后能解释实际生效结果。
  3. 在交接期间取消 Run 或归档 Session → 不复活或另起推进，应停止的独立执行仍被取消。
- **不含**：新的候选优先级政策、自动补偿或撤销外部效果。
- **前置**：ST-012-09、ST-014-04、ST-015-07
- **就绪**：是

### ST-012-11 · 内部模型回复仍回到原判断位置

- **子期**：2B · 稳定完成项目长任务
- **价值**：用户的内部判断和摘要计算不会因换执行者而丢失或误投到主对话。
- **覆盖场景**：[S83](acceptance.md#运行时归属与句柄)
- **演示**：
  1. 让 hook 判断模型调用在途，仅销毁 Agent Runtime 后重建 → 原请求不重发，原回复由原 hook 位置承接，不作为主流程的下一条回复或工具建议。
  2. 对压缩摘要模型重复同样过程 → 原摘要由原压缩计算消费，费用沿原调用归属，只承接一次。
- **不含**：模型执行自身失联、不同语义 hook 替代以及压缩策略选择。
- **前置**：ST-012-04、ST-012-07、ST-010-01
- **就绪**：是

### ST-012-13 · 卸载更新不会丢掉仍待答的判断

- **子期**：2B · 稳定完成项目长任务
- **价值**：用户已看到的请示不会被更新操作悄悄抹掉。
- **覆盖场景**：[S91](acceptance.md#重装配与独立执行交接)
- **演示**：
  1. 让一个 extension 的判断停在卡片等待，再请求卸载或替换它 → 等待不丢，不把卸载当成原判断完成，也不把旧答复交给不同语义的新判断。
  2. 分别在依赖未满足、原判断恢复失败时查看 → 具体原因可见，系统没有以完成或默认批准掩盖故障。
- **不含**：选择新的卸载或替代政策、后台派发等待及用户答复后的业务判断。
- **前置**：ST-012-07、ST-012-09
- **就绪**：是

### ST-012-12 · 打转守卫不会被压缩或重启洗掉

- **子期**：2B · 稳定完成项目长任务
- **价值**：用户的打转任务能被守卫终止，正常长任务不会仅因时长被杀掉。
- **覆盖场景**：[S6](acceptance.md#一可观察的场景)、[S13](acceptance.md#一可观察的场景)、[S14](acceptance.md#一可观察的场景)、[S40](acceptance.md#一可观察的场景)
- **演示**：
  1. 在已有合法守卫策略下使 agent 重复打转，途中触发压缩及多次崩溃恢复 → 阶梯仍按日志计数，不因压缩或重启归零。
  2. 继续到 L3 → 本 Run 失败，原因可查，不把守卫结束当非常态向上交。
  3. 对照一个持续做新工作且没有预算守卫的任务 → 不因为运行很久就自动停止；本卡不许据时长增加终止条件。
- **不含**：新的检测算法、预算守卫配置、任意轮数上限和通用超时策略。
- **前置**：ST-010-01、ST-015-03
- **就绪**：是

### ST-012-14 · 查清拓展件故障实际怎样处置

- **期次**：第三期 · 性能与体验
- **价值**：用户和排查者能区分拓展件报错、依赖缺席以及正常无意见，知道为什么这一步继续或被拦。
- **覆盖场景**：[S8](acceptance.md#一可观察的场景)、[S9](acceptance.md#一可观察的场景)、[S10](acceptance.md#一可观察的场景)、[S64](acceptance.md#一可观察的场景)、[S64d](acceptance.md#一可观察的场景)、[S64f](acceptance.md#一可观察的场景)、[S64g](acceptance.md#一可观察的场景)
- **演示**：
  1. 分别让未另定策略的只观察与可改写拓展件报错 → 事情照常；可改写件日志明确记“没跑成”，不冒充“无需改写”。
  2. 让未另定策略的可否决拓展件报错 → 按否决处置且处置本身可见，不悄悄放行。
  3. 让未声明特殊不可用处置的租户拓展件依赖缺席，再使循环探测或卸载判定不可用 → 租户件按跳过处置，系统这两类不干预；日志分别说明此刻不在及实际处置。
  4. 让一件执行动作之前、有效干预力为可否决、已声明不可用时否决的租户拓展件依赖缺席 → 动作不执行，日志写清缺席及否决处置，区别于执行失败。
  5. 由组织将同一租户拓展件的干预力收窄为只观察，再重复依赖缺席 → 按跳过处置；缺席不能取得它在场时也没有的阻断能力。
- **不含**：改写模型原回复、重试／转换／放行判断的专属失败规则、新干预力、不可用时的用户自定义替补和重跑已经完成的判断。规则所属能力交付时就须成立，不因本卡在第三期而允许此前假放行。
- **前置**：ST-012-01、ST-008-02
- **就绪**：是

### ST-012-15 · 按原任务看清每笔调用费用

- **期次**：第三期 · 性能与体验
- **价值**：成本负责人能查到一个任务跨尝试的实际花费，分清原执行接续、真实重发和会话旁路开销。
- **覆盖场景**：[S5](acceptance.md#一可观察的场景)、[S27](acceptance.md#一可观察的场景)、[S28](acceptance.md#一可观察的场景)、[S45](acceptance.md#一可观察的场景)、[S17d](../PF-013-model-profiles-and-invocation/acceptance.md#一次调用出事)、[S97](../PF-007-meta-capabilities/acceptance.md#状态族与他者族)
- **演示**：
  1. 让同一个 Run 中的 Agent runtime 连续崩溃三次，同时保持模型与工具原执行的连续性，重建后接续，再查账 → 仍是一笔 Run 汇总；明细保留原调用与原发起尝试，接续没有重复计费，不用“总成本减最后尝试成本”推算浪费。
  2. 另在首 token 前使模型 runtime 失去连续性，恢复后真实重发 → 会话回复只有一份；两次实际发出的费用都列在成本明细里，拿不到实际费用的那次明确记未知。
  3. 让拓展件在 Run 内调用一次模型，再发起一项不属于 Run 的会话旁路调用 → 前者归所插手的 Run，后者归会话级，不被塞进任意 Run。
  4. 在同租户合法派发关系中再向下派一层工作，查看成本归属 → 仍算最初发起方的租户，不随层级漂移。
  5. 让上述一个 Run 按既有模型凭据不可用规则落失败，再在没有新费用事实到达的条件下重复读取汇总与明细 → 费用及未知项保持一致，失败只归这一个 Run，不按尝试拆成多个 Run；迟到真实费用到达后仍须更新原账目，不能冻结未知项。
- **不含**：价格或费率新政策、未知费用估为零、用等待者重建推算浪费、跨租户账单可见性新规则、模型 ACK 与副本清理能力。成本归属正确性随原执行能力成立，本卡只集中交付费用查询旅程。
- **前置**：ST-012-04、ST-012-05、ST-007-02、ST-012-02
- **就绪**：是
