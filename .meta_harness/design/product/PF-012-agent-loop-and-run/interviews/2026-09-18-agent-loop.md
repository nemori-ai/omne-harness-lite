## INT-001 开题：run 是数据，agent-loop 是方程

> **quote**（2026-09-17）：「下一个 PF-009 我们要完成 agent-loop 的产品设计。
> 一个 agent-loop 本质上是一次的 run，但是 run 是数据/治理的概念，agent-loop 是一次
> 完整的 run 的执行逻辑描述（也可以理解成是状态转移方程）。为什么说 run 是数据/治理的
> 概念，是因为产品上我们要求，因为完全有可能系统在一个 run 没进入终态的时候停机了，
> 那我们如果能够记录下最近的 run 的状态是怎样的，那么通过状态转移方程（控制论）
> 我们理论上应该能够恢复出来继续执行的下一步是什么。」

**可恢复性不是附加要求，它是 run 这个概念存在的理由**——这是整个 topic 的地基。
（编号后来调整为 PF-012，见 INT-007。）

## INT-002 三个问题的作答

PM 先推完能推的（run 的状态必须完整到只凭它算得出下一步、转移必须确定、
方程必须覆盖所有可达状态、记录与动作的先后决定失手方向），把三个真有多解的交上去。

**问题一：从中途恢复时，能力的可用性要不要重算？**

> **quote**：「重算」

**问题二：停机时正在跑的后台工具执行，恢复后算什么？**

> **quote**：「系统都停机了，运行在系统里的后台工具执行是不是也是失败了呢其实」

**这句反问纠正了 PM 的一个错误想象**：PM 把后台执行想成了跑在系统外面的独立进程，
所以才会觉得「算失败是在说谎」。实际上它跑在这个系统里，**系统没了它就没了**，
不存在「可能成功了只是结果没回来」。

结论：**算失败，不新增第七种收场。**

**问题三：一个有副作用的动作，恰好在「做了」与「记下」之间停机了，恢复时宁可怎样？**

> **quote**：「只根据最后明确记载的状态来重算，哪怕重做也可以接受」

**三条答案合起来是同一条主线**：**记录是唯一的真相来源，没有明确记载的就当它没发生。**

## INT-004 循环守卫全套到 L4，L3 落失败

> **quote**（选项作答）：「全套到 L4」「就是失败」

L4 在 legacy 是关着的口子；我们有 [PF-008 的决策池](../../PF-008-human-in-the-loop/design.md#决策池)，
直接复用——**比起掐掉一个跑了很久的任务，让人给个方向要友善得多**。

L3 落「失败」而不新增终态：**终态越少越好，而「为什么失败」本来就有地方写**。

## INT-005 叠加三个动作

> **quote**：「然后你要叠加考虑 上下文组装动作的执行（请求模型前）、上下文压缩动作的
> 执行（上下文组装动作执行前）、循环探测动作的执行（模型响应后） 这三个动作的执行」

**这三个动作插进来之后，浮出了一条比它们本身更要紧的分界**：
**改记录的动作 vs 纯派生的动作**。

组装是这一圈里**唯一纯派生**的那个——它不进状态空间，因为重算一定得到同样的结果。
由此得到一条实现判据：**要不要给一个动作建状态点，看它改不改记录。**

## INT-006 压缩的顺序被纠正

PM 把压缩写在了组装之前。被纠正：

> **quote**：「压缩的输入是上一次压缩后到这一次模型请求前到完整上下文，
> 所以这么看，应该是组装前？然后如果发送压缩，补一个追加组装的动作？」

**PM 的顺序错了。不组装就不知道超没超**——占位置的不只是对话，
还有系统提示词、工具定义与[十三扇门那些常驻的东西](../../PF-007-meta-capabilities/design.md#54-十三个槽位是预算的地板也是它的天花板意义)。
「量一量」这个动作本身就要求先组装出来。

正确顺序：**组装 → 量 → 超了才压 → 再组装**。

**这个纠正顺带让「组装是纯派生」第一次兑现了价值**——
第二次组装能随手补上，正因为它不留任何痕迹。

「压缩的输入是上次压缩点到现在」还推出一条硬性质：
**压缩是增量的，摘要只生成一次，不再被二次压缩**——
否则会出现「摘要的摘要的摘要」，而**那种失真是静默的**。

## INT-008 卸载的两条来路，与四类事件都归 agent-loop

PM 从「占位带摘要」推出一条「**摘要的质量落在关键路径上**」写进了 decisions。被纠正：

> **quote**：「『由此我推了一条并写进 decisions：摘要的质量落在关键路径上』不需要哈，
> offloading 机制两种：1）工具开发者自己声明，因此摘要信息工具开发者自己构建；
> 2）工具结果返回后，组装成 ToolMessage（在 agent-loop 里面的逻辑）准在下一步请求模型之前，
> 计算发现单个工具消息的 message tokens 超过限制，因此系统只作首尾保留的机械阶段机制
> 并执行 offloading。这里其实引出来一点，各种的占位消息替换、工具结果的卸载动作执行，
> 都是 agent-loop 里的逻辑。工具切后台是一个事件，工具自己声明要卸载是根据特定格式的
> 返回数据结构让 agent-loop 内的逻辑来解析处理决定要不要做卸载动作，注入的上下文
> （比如 organization context、account context、等等未来可能还有的其他的 context
> 也就是 Cordis 视角的 scope）发生变动也是事件，后台工具执行完成回传结果也是事件，
> agent-loop 要有机制能够获取到这些事件，在下一次的上下文组装时做成 system reminder
> 类型的消息（这个具体在 PF-009 里面会讲）」

**PM 错在把两种机制混成了一种**（以为系统会替工具生成摘要）。
实际上**系统不替工具开发者写摘要**——它只做首尾保留的机械截断。
所以不存在「系统生成的摘要质量」这个关键路径。

这段话同时定下了本 topic 的两块内容：

| | 落点 |
|---|---|
| 卸载的执行位置（落消息时，不在压缩时） | [design §5.10](../design.md#510-卸载结果落成消息之前的那一关) |
| 三类事件 → 收进记录 → 下次组装做成消息 | [design §5.11](../design.md#511-外面进来的事怎么到-agent-眼前) |

**卸载不在事件那张表里**——它不是「外面发生了什么」，
是 agent-loop 解析工具返回值之后自己做的一个动作。
