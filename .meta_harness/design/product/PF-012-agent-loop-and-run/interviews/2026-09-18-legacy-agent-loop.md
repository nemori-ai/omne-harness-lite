## 一、最值钱的三条

### 1.1 一切状态从记录派生，不另建持久结构

`cross-cutting/loop-guard-design.md` 的核心设计洞见，原文：

> **检测与升级状态一律「从消息窗口派生」，不新建任何持久计数结构。**

连「已经原地转了几圈」「阶梯走到第几级」都不另存——恢复时从重建的历史自动复现。

**它顺带堵了一个洞**：崩一次就把循环史洗白。原文明确
「**技术恢复不重置阶梯，只有新的独立权威工作输入才为新工作开启新阶梯**」。

配套一条次序不变式（INV-LG-2），本 topic 把它升为通则：

> 干预产物**先**完成落盘，**再**进入 LLM context；
> **绝不允许「图内可见但 EventLog 无痕」**。

### 1.2 失败处置三档，判据是「谁能解决」

`subsystems/runtime_plane/application-spec.md` §9（ADR-121）：

| 档 | 语义 | 谁能解决 | run 结局 |
|---|---|---|---|
| ③ `surface_to_agent` | 交给 agent | agent 改变行为 | **不中断** |
| ② `retry_then_abort` | 有界重试 | 时间 | 耗尽 → 转① |
| ① `abort` | 终局 | 谁也解决不了 | 经唯一落账点结束 |

**「谁能解决」不问错误长什么样，只问出路在哪**——本 topic 直接采纳。

两条硬约束同样采纳：**凭据错永不重试**（试一百次还是不对，只是把账号锁了）、
**未分类归①**（fail-closed）。

还有一条值得记：`ToolInvocationRequiresHitl` **特意不在这张表里**——
**等人不是失败**，走 interrupt park。（那条链在 legacy 是 designed-not-impl，
我们 [PF-008](../../PF-008-human-in-the-loop/README.md) 已经设计完整。）

### 1.3 唯一终局落账点

同上 §9.4。所有 `.failed` 的 ship 位点收敛为**一个应用层席位**。

附带一个很硬的细节——**漏斗先确保会话存在，再落终局**：

> **第一轮就死掉的会话，它的第一条事实就是自己的失败。**

没有这一条，那种会话会变成幽灵：run 失败了，但没有任何地方看得到它。

## 二、恢复设计

`cross-cutting/recovery-design.md`。

**两种 turn 准入形态**（判别锚 = durable 的派发单因果根）：

| | **新 turn** | **同 turn re-drive**（崩溃后换肉体） |
|---|---|---|
| run 身份 | 铸新 | **沿用**（body 换 soul 不变） |
| 触发行 | 材化 | **不材化**——已 durable |
| 喂入 | 重建史 + **末尾追加**触发 prompt | 重建史**原样**——**零追加、零注入** |
| 循环检测窗口 | 从新触发起算 | 触发留在**原时序位置** → 循环史入窗 → 立刻重检 |

**判别红线**：禁止以「该会话下存在任一非终态单」泛判——
**第一轮还在跑时到达的第二条用户消息有自己的触发身份，它仍是新 turn**。

**四条不变式（INV-RD-1~4）**：

| INV | 内容 |
|---|---|
| **1** | 同 turn re-drive **绝不铸新持久身份**；铸新是新 turn 的专属权利 |
| **2** | turn 的全部诞生材化**幂等**——任意次 drive 收敛同一（组）durable 行 |
| **3** | 喂入 = 重建史**原样，零追加零注入**；触发行处于**原时序位置** |
| **4** | durable 身份**不含瞬态坐标**（实例号 / 步序 / 进程内计数）；**durable 锚 = run** |

**尾部对账**（§2.6.3 item 3）——本 topic 的 §5.9 直接取自这里：

| 崩在哪 | 怎么接 |
|---|---|
| 尾巴停在**悬空的工具调用**（调用落盘了、结果没落） | 合成 interrupted tool result 续跑，**或** fail-loud 停驱 |
| 尾巴已有**完整的最终回复**、只是终态没翻 | **幂等 finalize，不得再驱模型** |

## 三、循环守卫

`cross-cutting/loop-guard-design.md`。

**四个检测策略**：终极兜底（hard cap）、**结果敏感的精确重复**（头号策略，默认 N=3）、
**错误重复**（最强信号）、A-B-A-B 交替环。

**升级阶梯 L0→L4**：

| 级 | 做什么 |
|---|---|
| **L0** | 观测——**永不可关的地板** |
| **L1 / L2** | 干预（注入消息） |
| **L3** | **优雅结束** run（走 Run 生命周期，**禁越权杀图**） |
| **L4** | **升级到 HITL**——designed seam，**day0 关闭** |

**防自激励**（原文注明是 Claude Code `stop_hook_active` 教训的结构化版）：
干预消息带标记 → **不进检测计数**；同级干预每窗口至多一次；**升级只能单调向上**。

## 四、我们能往前走的四处

| 优化点 | legacy 的状态 | 我们为什么能做得更好 |
|---|---|---|
| **循环守卫 L4 实际交付** | designed seam，**day0 关着** | 我们[有决策池了](../../PF-008-human-in-the-loop/design.md#决策池)——agent 打转 → 出一张卡片让人给方向。**比直接掐掉一个跑了很久的任务友善得多**，且复用现成机制 |
| **等人不是失败** | 表里特意排除，但那条链 designed-not-impl | [PF-008](../../PF-008-human-in-the-loop/README.md) 已设计完整，直接接上 |
| **第三档与六种收场合并表述** | 两套说法 | 「交给 agent」= [PF-006 的工具失败作为正常返回](../../PF-006-tools-and-skills/design.md#55-一次工具执行的收场有六种)。**同一件事只说一遍** |
| **恢复时重算可用性** | 只重建消息史 | [PF-006 定了「每次 run 开始前重算」](../../PF-006-tools-and-skills/design.md#62-可用性在每次-run-开始前重算)，**把恢复也算作一次开始**，两条规则就统一了 |

## 五、看过但本版没有采纳的

| 内容 | 为什么不采纳 |
|---|---|
| **三条正交轴的完整交叉映射**（处置轴 ⊥ 严重度轴 ⊥ 恢复域轴） | 严重度轴（4-tier）是**工程治理分类**，不是产品语义；恢复域轴依赖那边的分布式部署形态。**本 topic 只取处置轴** |
| **租约 TTL / 单次 run 超时 / 恢复 RTO 三个独立时钟** | 资源与运维政策，不是产品判断 |
| **同 invocation 内的模型调用重试细节**（退避、次数、席位） | 产品只定「等一等再试」这一档的存在与判据，**次数与退避是可调政策** |
| **节点锚定的执行位点 / fleet 拓扑** | 第一版是单机系统 |
