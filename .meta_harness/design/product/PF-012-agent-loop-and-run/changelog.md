### 同一版的第二件事：从 event loop 的视角重做方程

**产品负责人 2026-09-20 的三条裁决，把方程从「点的清单」变成「段的清单」。**

#### 一、段进了正文

> **一个段，就是 `f` 的取值保持不变的那一段连续执行。段的边界，就是状态点。**

**此前只有点，没有段**——点与点之间那一截在干什么、能不能中途停、停了从哪儿接上，
三个问题正文都没回答。[现在有了](design.md#光有点不够还要说得清点与点之间)，
而且掉出三条性质：拓展件不改变 `f` 的取值、**段是可以重做的最小单位**、
**每一个 `await` 恰好落在段的末尾**。

#### 二、判据换了

| | |
|---|---|
| ~~**看它改不改日志**~~ | 有现成的反例：**拓展件改日志，但它不是状态点** |
| **看跑完它 `f` 的取值变不变** | 那个反例降格成[这条判据的一个实例](design.md#由此得到判据看跑完它-f-的取值变不变)，不再是例外 |

**由此还掉出一条进不进方程的判据**：**看它里面有没有 `await`**。
有 → 协程要在那儿交还 → 它是段的边界 → 进方程；没有 → 它跑在段内 → 是挂件。

**「[输入落盘](design.md#53-改日志的动作与纯派生的动作)」同时改名为「消息落盘」**，
并写明它是[六个状态点里唯一一个条件性的](design.md#消息落盘是唯一一个条件性的状态点)——
**只有队列从空变非空那一刻才是段的边界**，而那恰好就是
[触发](../../ubiquitous_language/terms/agent-runtime-loop.md#ul-trigger--触发--trigger)。

#### 三、压缩整段进闭包，循环探测与卸载判定出表

> **「判定要不要压缩」在 compaction 这个闭包内做；
> agent-loop 看到的就是进了这个闭包，那本质上也是一个 `await` 点。**

> **把压缩放回去，循环探测和卸载还是做成挂件。**

**[转移表因此少了四行](design.md#56-状态转移表)**：

| 原来 | 现在 |
|---|---|
| T1 · **T1a** 量下来在预算内 · **T1b** 超了就压 · **T1c** 压完还超 | **T1** 交进闭包 · **T2** 装得下了 · **T1′** 交不出装得下的 |
| **T2** 循环探测 · **T2a/T2b/T2c/T2d** 四种结局 | **没有了**——[四种结局全落在已有的尾巴形状上](design.md#循环探测的四种结局全落在已有的行上) |
| **T2a′** 模型没给动作，看队列空不空 | **T2′**（只改了名） |
| T3 – T8 | **一个字没动** |

**「量一量」从方程里消失了**：方程只认「装得下 / 装不下」两个回执，
**不必懂窗口，也不必会量**。[压缩闭包的硬约束与动作边界归 PF-010 rev 4](../PF-010-context-management-and-assembly/changelog.md)。

**代价记在[取舍表](design.md#七取舍)**：闭包内部外面看不见；读转移表的人看不出
循环探测和卸载判定发生在哪，得回到[位置表](design.md#十一个位置是推出来的不是挑出来的)去找。

## rev 4 — 2026-09-20

**Run 的边界重新定义，整篇跟着动。**产品负责人在统一建模 run、agent-loop、inbound
与「什么会触发／继续一次 run」时给了一条主干裁决：

> **进入一个 agent loop 是 run start，退出这个 agent loop 是 run end，中途可以被打断；
> 在待处理的消息队列不空且不被 interrupt 之前，agent-loop 不会退出，而是持续消费消息队列。**

**这一条不是补充，是换了 Run 的定义**——rev 3 之前 Run 的边界是「一次执行请求及其结果」，
**边界在哪由『触发』与『收束』两套说法各写一半**；现在它只由一件事决定：**队列空不空**。

### 一、Run 从「一次请求」变成「一段循环」

| | rev 3 | rev 4 |
|---|---|---|
| Run 的边界 | 一次执行请求及其结果，**边界靠触发与收束两套说法拼** | **[进 loop 即开始，出 loop 即结束](design.md#run)**——一个纯粹的逻辑概念 |
| 什么时候退出 | 模型没给动作就完成 | **[队列空](design.md#待处理消息队列)才完成**；队列不空就接着消费 |
| 「触发」是什么 | 一个独立概念，要穷举出「哪些情形会发起一次 run」 | **让队列从空变成非空的那件事**——**那张穷举表塌成一句话** |
| 「收束」是什么 | 一个独立概念 | **队列重新变空** |

> **穷举没有消失，是换了对象。**要穷举的从「什么会发起一次 Run」变成
> **「什么东西会进队列」**，归 [PF-014](../PF-014-inbound-intake-and-queueing/README.md)。

### 二、PF-012 与 PF-014 的那处冲突，是被定义消解的

**旧模型下有一个回答不了的问题**：Run 已经收束，一个后台结果这时候回来了——
**要不要把它叫醒？**而叫醒一个已经停了的方程讲不通，
于是两个 topic 各写了一半，说法对不上。

> **新定义下这个问题不成立。**东西进队列，队列非空，**loop 本来就还没走到退出那一步**；
> 真要是已经退出了，**那说明退出时队列是空的，而它现在非空——开下一个 Run**。

**产品负责人同时裁决了它的产品后果**：「构建跑完了，结果回来了，**要唤醒模型**
（只要会话本身不被终结，一次 run 完成了那就开新的 run）」。

**[§6.12](design.md#612-终态之后再回来的东西不让-run-复活) 据此补了另一半**：

> **「不复活」不等于「没人看」。**不复活**这一个**，与**会有下一个**，
> **是同一条规则的两半，缺哪一半都会做错。**

**缺后一半会怎样**：用户说「跑那个两小时的构建，好了告诉我」，
**结果回来时没人管，他要等到自己下次主动说话才发现两小时前就跑完了。**

### 三、新增概念：待处理消息队列，且它是日志的投影

**裁决只说了有这么一个队列，没说它存在哪。**而本 topic 有两条现成的硬规矩把形状逼了出来：

| 逼它的那条 | 队列若是另一份存储 |
|---|---|
| [收进来是改日志的动作，组装只负责拼](design.md#511-外面进来的事怎么到-agent-眼前) | 队列成了第二个要被消费的地方，**而组装是纯派生的，方程当场失效** |
| [停机是主路径的一部分](design.md#57-一次尝试三条路通向重新算一遍) | **一次重启就丢消息** |

> **于是它只能是[日志里「还没被消费过」的那一段](design.md#待处理消息队列)**——
> 持久、可恢复、不会与日志分叉，**三条性质一条都不用额外设计**。

**排队规则也定了**（产品负责人 2026-09-20）：**默认先到先处理**，
唯一的加急通道是**[插队](design.md#先到先处理只有一个例外)**——带插队命令的用户消息**直接排到最前面**，
并且 **loop 里各种等待态一并解除**。

> **「队列是不是多级优先队列」这个问法，被这条裁决关掉了。**
> **不设第二种优先级**：每多一级就多一处要解释的语义，
> 而插队已经覆盖了「我现在就要」这个全部需求——**一个机制，不是两个**。

### 四、转移表：T1 换了条件，新增 T2a′

| 行 | rev 3 | rev 4 |
|---|---|---|
| **T1** | 尾巴是用户消息 / 工具结果齐了 | **[队列非空](design.md#56-状态转移表)** |
| **T2a′** | **没有这一行** | **模型没给动作 → 看队列空不空**：非空回 T1，空了才落**完成** |

> **旧表把「模型没给动作」直接落完成，新定义下那是错的**——队列非空就还没做完。
> **T2a′ 不是新增机制，是把「完成」的判据写准**：完成＝模型没话说**且**没有待处理的。

### 五、「输入落盘之前」扩成「消息落盘之前」

**产品负责人把转换件的位置改了**：它不该是「请求模型前／组装上下文时」的拓展点，
而应当是**一条消息／内容块落盘前**的拓展点——
**这就把「输入的处理」与「模型生成、工具结果的处理」统一成了一件事**。

| | rev 3 | rev 4 |
|---|---|---|
| 这个位置叫什么 | **输入落盘之前** | **[消息落盘之前](design.md#消息落盘之前每条消息都经过它不只是输入)** |
| 什么经过它 | 用户输入 | **每有一条消息要落盘就经过一次**——用户说的、模型吐的、工具交回来的 |
| 挂什么 | 脱敏 · 敏感信息识别 · 注入与攻击检测 | **再加一件：把收不下的模态转成文本** |

> **这不是为了给转换件找个家，是这个位置本来就该这么大。**
> rev 3 给它写的三条理由——**要挡的是「进来」这个动作本身**——
> **对模型吐出来的内容一模一样成立**；而按 rev 3 的写法，
> **模型生成的内容没有任何位置可以脱敏**。那是一个洞。

**新增[一节专门论证转换为什么必须落在这儿](design.md#模态转换为什么必须落在这里)**，
因为另外三条路各自都不行：组装时转（**一圈两次组装结果不同**）、
调模型之前转（**量的是原图、发的是文本**）、落盘之后转（**改记录或另存一份，都违反只增不改**）。

**转换件的形状也定了**：**一个位置，多件挂件**——声明自己能处理的模态集合，
**块进块出**，**就地给那个内容块记录文本的字段赋值**。
**位置归本 topic，契约归 [PF-013](../PF-013-model-profiles-and-invocation/README.md)**——
「有哪些模态、哪个模型收得下哪些」是那一侧定的。

**锚点因此变了**：`#系统自带的三件各站在哪` → **`#系统自带的几件各站在哪`**。

## rev 3 — 2026-09-19

**把 Loop 拓展点做完整。**产品负责人给的范围是两条：
**拓展点必须完备**，让租户与组织超管能扩展或覆盖策略、自定义自己的 agent plugin；
**先对五家现有 harness 逐一梳理再整合**（Claude Code、Codex、DSH、Grok Build、LangChain）。

**这一版推翻了 rev 2 的三条 PM 推导**，三条都在 [decisions](decisions.md#rev-2-新推的) 里划了线保留原文。

### 一、从「我挑了三个」变成「位置是推出来的」

**rev 2 只开三个位置，理由是「没有消费者的位置就是框架」。**
产品负责人的新要求让这条前提不成立了——**要完备**。
而一旦接受「[拓展点按它相对状态点的位置命名](design.md#按位置命名不按功能命名)」这条裁决，
位置就不再是挑出来的：

> **每个[状态点](design.md#53-改日志的动作与纯派生的动作)有紧前与紧后两条边，每条边就是一个位置。**
> 六个状态点十二条边，**只有「尝试开始之前」不归本 topic**——其余十一条全部开放。

| | rev 2 | rev 3 |
|---|---|---|
| 位置有几个 | **三个**，挑的 | **[十一个](design.md#十一个位置是推出来的不是挑出来的)**，推的 |
| 怎么命名 | 按功能（循环探测 / 放行判断 / 卸载判定） | **按位置**（调模型之后、执行动作之前、执行动作之后）。**不编号**——编号是第二套命名，且位置数一变全篇错位 |
| 那三个是什么 | 「三个拓展点」 | **三件[拓展件](design.md#拓展件)，站在三个位置上** |
| 同一位置挂多个 | 没想过，flows 里写着「本版不发生」 | **常态**。按[瀑布式](design.md#三种形态两种装得进一种拆两半)依次过 |
| 完备性 | 谈不上 | **可论证**：漏没漏位置，等价于问「状态点漏没漏」 |

**「位置不是新机制」是这一版最要紧的一句。**rev 2 担心「开十个是预埋框架」——
**它不是**：位置就是状态点的两条边，**开齐十个没有多造一样东西**，
多造的东西是挂上去的那些，而那些由用户决定装不装。

### 二、「调模型之前」开了：请求攒好、发出之前

**rev 2 明确写着「组装之后、调模型之前开不了拓展点」，理由是「那一圈可能要组装两次，而两次结果必须相同」。**

> **那个理由本身是错的。**「[纯派生](design.md#53-改日志的动作与纯派生的动作)」说的是
> **同一份日志组装两次结果相同**；压缩前后的两次，日志已经变了，**本来就该不同**。

它开了之后要回答的真问题是另一个——**挂件改了日志，请求就过期了，会不会无限触发自己**。
答案是一条与压缩同构的规矩：

> **[同一个位置，同一次经过只跑一轮](design.md#改了日志就重新组装同一位置同一次经过只跑一轮)。**

### 三、拓展件成了第八类资产

**rev 2 写着「别顺手把它并进资产那七类」。产品负责人在知情的前提下选了推翻。**

| | rev 2 | rev 3 |
|---|---|---|
| 挂件是什么 | 「本 topic 不定，归资产那一侧，**而那一侧没有 owner**」 | **[第八类资产](../PF-002-assets-settings-and-permissions/design.md#loop-extension)**，走资产已有的持有、授权与层级求值 |
| 谁能装、怎么覆盖 | 未决 | **组织超管配一份，租户覆盖或收窄**——不必另造一套 |
| 干预力怎么配 | 只说了三档 | **它是权限不是设置**，所以走[收窄](../PF-002-assets-settings-and-permissions/design.md#53-两个例子两种合成)：组织锁死租户放不宽 |
| [§9.3](design.md#八边界与依赖) | 三个缺口之一 | **已闭合** |

**「拓展点」与「拓展件」这一版分开了**——rev 2 两个意思共用一个词。
**拓展点是位置，拓展件是挂上去的东西。**

### 四、两个位置带维度

**「调模型之后」和「执行动作之后」各自不止一种情形**，挂件要声明自己管哪一种：

| 位置 | 维度 | 取值 | 不分会怎样 |
|---|---|---|---|
| **调模型之后** | 收场 | 完整回复 / 失败 | 一个管打转的挂件面对「请求失败」无话可说，**硬让它跑只会得到一个没有依据的判断** |
| **执行动作之后** | 范围 | 这一个 / 这一批全齐 | 「这一批的总量超了预算」**只有等齐了才知道**，不分维度它没地方站 |

**维度不是第十一、十二个位置**，它是同一个位置上的筛选条件。

### 五、环绕式拆两半

**五家摊平之后看出拓展点有三种形态，而不是一种**（[调研笔记](interviews/2026-09-19-loop-extension-points.md#一最硬的发现拓展点有三种形态不是一种)）：

| 形态 | 处置 |
|---|---|
| **点式**（Claude Code · Codex · Grok） | **采用** |
| **瀑布式**（DSH） | **采用**——它正是「同一位置挂多个」的求值办法 |
| **环绕式**（LangChain `wrap_model_call` · DSH `around dispatch`） | **拆两半**：「给结论、由 loop 执行」那一半装得进（落在调模型之后）；「自己循环调下一层」那一半**装不进**——中间几次不经过日志，`f` 当场不纯 |

> **拆的是形态，不是功能。**「失败了重试三次」本系统照做，
> **只是每一次都得在日志里留一条**。代价是日志更长，换来的是换一副身子也能接着跑。

### 六、用 `/btw` 与 `/goal` 回头检验，检出三条

产品负责人指定用两个真实产品功能倒验一遍（[过程](interviews/2026-09-19-loop-extension-points.md#七用-btw-与-goal-回头检验)）。
**结果：`/goal` 的 loop 部分全落在落终态前后与调模型之后，一个位置不缺；`/btw` 一个都用不上，而那是对的。**

| 检出 | 落进哪 |
|---|---|
| **「落终态之前」的「可否决」否决的是「停下来」**，方向与调模型之前、执行动作之前相反 | [§5.8 干预力](design.md#干预力三档直接用-pf-000-的)、[flows §四](flows.md) |
| **挂件自己那次模型调用，钱算进它插手的那个 Run** | [§5.8 末](design.md#挂件自己花的钱算它插手的那个-run) |
| **Run 不是成本唯一的一级**——旁路提问那种调用归会话那一级 | [§4 Run](design.md#run-是三样东西的归属单位) |

**第三条是 `/btw` 戳破的一句已定的话。**rev 2 写「Run 是成本 · 失败 · 收束三样的同一个归属单位」，
读起来像「所有成本都归 Run」，**而旁路提问那笔钱无家可归**。

### 七、§5.3 那张表从「举例」改成「穷举」

**rev 2 那张「改日志 vs 纯派生」的表只列了五个动作**，当时它只是为了讲清那条分界。
**rev 3 拿它做完备性论证，它就必须穷举**——补上了**尝试开始**、**输入落盘**、**落终态**
与**量一量**四行。

> **状态点恰好六个**：尝试开始 · 输入落盘 · 压缩 · 调模型 · 执行动作 · 落终态。
> **少列一个，位置清单就少两条**——这是这一版最容易被漏掉的依赖关系。

### 八、「输入落盘之前」开了，位置从十条变十一条

**产品负责人当天追加的一条**：这个位置要开，**虽然它在 loop 外面，但清单统一记在本 topic**。

理由是企业场景最要紧的三件事都发生在那一刻：**脱敏 · 敏感信息识别 · 提示词注入与攻击检测**。
它们的共同形状是——**要挡的是「进来」这个动作本身**：

> [日志只增不改](design.md#会话日志)。**落盘之后再想脱敏，原文已经永久留在那儿了。**
> **落盘之后的位置，一个都办不了这件事。**

| | rev 3 初稿 | 现在 |
|---|---|---|
| 位置几条 | 十条（十二减二） | **十一条**（十二减一） |
| 减掉的 | 尝试开始之前（PF-015）、输入落盘之前（PF-014） | **只剩尝试开始之前** |
| 「输入落盘之前」 | 不开 | **开**。位置记在本 topic，**那一刻具体看得到什么归 PF-014** |

**完备性论证的形状没变**，变的只是减去几条——**这正是「推出来的清单」比「挑出来的清单」强的地方**：
加一个位置不必重新论证，**只要说明为什么不再减它**。

**顺带去掉了圈数字编号。**位置就叫它站的那个名字。
编号是第二套命名，与[按位置命名](design.md#按位置命名不按功能命名)那条裁决冲突；
而且**本轮位置数一变，全篇编号当场错位**——这个负担不值得背。

### 九、循环的出口，以及三条撞出来的缺口

产品负责人问了一句「**怎么算一次 agent-loop 退出循环？从程序的循环原语角度看，这个方程缺东西没？**」
核下来**方程不缺，正文缺四段话**——都补上了：

| 补了什么 | 落在哪 |
|---|---|
| **循环有两层，出口数不同**：Run 一个出口（落终态），一次尝试三个（落终态 · 停住等 · 被中断） | [§5.6](design.md#这个循环从哪里出去)、[flows §五](flows.md) |
| **T4/T6 的「停住」是出口，不是反复问**——把身子交还，等被叫醒 | 同上，且 T4/T6 两行**就地标注** |
| **方程不保证终止**，靠终态 + L3 + T1c + 拓展件四样，各管一头 | [§5.6](design.md#方程不保证这个循环会停) |
| **「被取消」没有转移行**，它是随时可到的外部事件；取消时在途执行按 [PF-006「中断不是失败」](../PF-006-tools-and-skills/design.md#67-用户可以中断而中断不是失败)处理 | [§5.6](design.md#被取消不在这张表里因为它不是一行)、[flows §5.3](flows.md) |

**「停住不是空转」这一条，产品负责人给的判断是「其实就是 wait/await」。**
正文用产品语言表述——**把身子交还，等被叫醒**——技术类比不写进产品正文，
但它确认了这条语义，记在 [decisions](decisions.md#一拍板记录)。

**这里还撞出一个真缺口，rev 3 初稿没有：**

> **[终态是吸收态](design.md#612-终态之后再回来的东西不让-run-复活)。**
> 日志只增，Run 在时刻 t 落终态、后台结果 t+1 才回来——**尾巴就不是终态了**。
> 照 [T7](design.md#56-状态转移表)「结果齐了 → 回 T1」的字面读法，**Run 会复活**。

**答案其实一直在正文里**——[「Run 的姿态」本来就在方程的定义域里](design.md#方程从日志里读什么)——
**但「看尾巴决定下一步」这句简化说法把它盖住了**。而 [§5.11 明说](design.md#511-外面进来的事怎么到-agent-眼前)
「结果回来了，而 Run 可能早走远了」，**所以这不是假想**：
照转移表实现，一条迟到的结果会把一个已经结算完、通知发出去的 Run 重新拉起来。

新增 [§6.12](design.md#612-终态之后再回来的东西不让-run-复活)，并把那句简化说法改准：

> **先看这个 Run 有没有终态条目，有就停；没有，才看尾巴。**

### 二、两处实质改判

**一、[「恢复」不是异常路径，是常态。](design.md#57-一次尝试三条路通向重新算一遍)**

rev 1 只写了崩溃恢复。实际上**三条路通向同一件事**：

| 什么发生了 | 日志 | 身子 |
|---|---|---|
| 系统崩了 | 在 | 没了 |
| **等人回话，人回了** | 在 | **可能已经被回收** |
| 身子被退役重建 | 在 | 换了一副 |

> **在方程眼里三条一模一样**：日志还在，身子不在了，**重新算一遍 `f`**。

**PM 当时手上没有[执行尝试](../../ubiquitous_language/terms/agent-runtime-loop.md#ul-run-attempt--执行尝试--run-attempt)这个概念**——
词条是后来建的，**而它一建起来，三条路的同构就是明摆着的**。

**二、[Run 的终态与非常态的终局，是两条线。](design.md#512-run-的终态与非常态的终局是两条线)**

**这是交割时撞出来的，rev 1 把它们混成了一条。**

```text
Run：    触发 ──→ 在跑 ──→ 失败      ← 到此为止
                            ↑
非常态： 运行 ──→ 会话 ──→ 租户 ──→ 终局   ← 还在往外走
```

**不写明会怎样**：实现者会写出「Run 失败了，处置也就结束了」——
**于是会话层与租户层的处置永远不会发生**。

**下游要复核**：任何把「Run 落终态」当成整件事收场的实现。

## 「记录」补齐了定义 — 2026-09-18

**rev 1 一直在用「记录」这个词，而 §4 只从「方程的定义域」这一个视角列过三部分。**
[PF-009 §5.7](../PF-009-context-message-types/design.md#57-一份会话日志两种组装) 用的是另一个视角
（一份忠实留存，两种组装从它派生）——**两处视角，谁都没定义它本身**。

**产品负责人认可的定义：**

> **它本质上就是 append only 的 session log，
> message 只是它的一部分，更多的是各种 events。**

并划了范围：**知道 session log 与 message 的关系就行，
不需要关心那些 events 究竟是什么。**

### 由此定住的三条

| | |
|---|---|
| **归会话，不归 run** | run 引用它，不另存一份（rev 1 已有，现在写进定义） |
| **只增不改** | **§5.3 那张表里的「改记录」，一律是「往后加」** |
| **记录 ⊋ 消息** | 不点破这层，[执行的账](../PF-006-tools-and-skills/design.md#54-返回值两种写法一种模型)和**还没做成消息的事件**就没地方安放 |

### 一个疑问被解掉了：只增不改与卸载冲不冲突

**PM 提过这个疑问**——§5.11 写着「卸载是改记录的动作」，
听着像是把日志里已有的东西换掉了。**产品负责人给的形状解掉了它：**

> 占位 `ToolMessage` 让 agent 感知**现在看到的是完整结果的一部分**；
> 它若需要完整的，**自己用 `Tools()` 访问**——
> 而那次访问**在 log 里新增一个 tool call（AssistantMessage）和一个新的 `ToolMessage`**
> （装原始结果，**未必仍然完整，因为允许分页读取**）。

**所以三件看着像「改」的事，全都是追加：**

| | 实际上 |
|---|---|
| **压缩** | 往后加一条概括，让**后续的组装**不再取那一段 |
| **卸载** | **原始结果从来没进过日志**，进去的一直就是占位 |
| **取回全文** | **往后加两条**，占位那条纹丝不动 |

**§5.11 据此重写了最后一段，并新增「agent 取回全文」一节**，
顺带点出三件事：取回来的**未必完整**（分页）；**每来回一趟上下文就多两条消息**；
**所以「占位里要留够用的那部分」这条裁决的价值正是在这里兑现的**。

**下游要复核**：任何把卸载实现成「先写全量、再替换成占位」的东西；
以及任何把取回全文实现成「改写占位那条消息」的东西。

### 这一版立住了什么

| 方面 | 结论 |
|---|---|
| run 与 agent-loop | **run 是数据 / 治理，agent-loop 是执行逻辑**（状态转移方程）。**两个都要** |
| 方程 | `下一步 = f(记录, 环境)`，**`f` 是纯的** |
| 状态在哪 | **记录里**。`f` 的定义域几乎完全落在**消息历史的尾巴**上 |
| 恢复是什么 | **不是「接着上次的进程」，是「重新算一遍 f」** |
| 最要紧的一条分界 | **改记录的动作 vs 纯派生的动作**——纯派生的不进状态空间 |
| 一圈的骨架 | 组装 → 量 →（超了才压 → 再组装）→ 调模型 → 探测 → 判断 → 做 → 回到想 |
| 终态 | **三个**：完成 / 失败 / 被取消。**不可逆，且只从一个出口走** |
| 失败处置 | **三档，判据是「谁能解决」**：交给 agent / 等一等再试 / 终局 |
| 循环守卫 | **四级**：观测（永不可关）/ 干预 / 优雅结束 / **升级给人** |

### 三条最硬的性质

> **一、没有明确记载的，就当它没发生。**
> 恢复从最后明确记载的状态重算——哪怕因此重做一遍。

> **二、要不要给一个动作建状态点，看它改不改记录。**
> 组装是这一圈里唯一纯派生的，所以它可以跑两次而不留痕。

> **三、检测与阶梯一律从记录派生，不另存计数。**
> 所以崩溃恢复会自动复现崩溃前的循环史——**靠反复崩溃洗白打转记录，这条路是堵死的**。

### 四处有意超出 legacy

产品负责人指示以 `omne-next/omne_harness` 的设计为起点。四处我们往前走了：

| 优化点 | legacy 的状态 |
|---|---|
| **循环守卫升级给人（L4）** | 那边是 designed seam，**day0 关着**；我们[有决策池了](../PF-008-human-in-the-loop/design.md#决策池)，直接复用 |
| **等人不是失败** | 那边特意不把它放进失败表，但那条链 designed-not-impl；PF-008 已完整设计 |
| **失败第一档与六种收场合并表述** | 那边是两套说法 |
| **恢复时重算可用性** | 那边只重建消息史；我们把恢复算作一次「开始」，与 PF-006 的规则统一 |

### 两处 PM 被纠正的地方，都记下不改掉

- **「后台执行应算状态不明」**——错在把它想象成跑在系统外面的独立进程。
  它跑在这个系统里，**系统没了它就没了**。

  正确的是**组装 → 量 → 超了才压 → 再组装**。

两条都在 [decisions 第四节](decisions.md#四已知的来源问题)。

**卸载看单条，在结果落成消息时；压缩看整体，在组装量完之后。**
**压缩救不了单条超限**——它收的是前面的历史，而这条新结果是当下正要用的东西。

**§5.12 loop 之外的事件怎么到 agent 眼前。**三类：工具转后台、后台执行完成回传、
注入的上下文变了。统一**收进记录，下一次组装时做成消息**；
**做成哪一类消息归 PF-009**。

> 这一节最硬的一条是被方程逼出来的：
> **事件必须先落进记录，不能攒在内存队列里。**

因为组装是纯派生的，而一圈**要组装两次**——队列被第一次取空，
第二次就拼不出同样的东西，**方程当场失效**。

**下游要复核**：任何让组装去「消费」事件队列的实现。

### 草稿期内闭合的第二处：PF-009 的消息类型已经落地

[PF-009 rev 1](../PF-009-context-message-types/changelog.md) 做完了消息类型那一块，
**本 topic 欠它的四条里闭合了两条**：

| 缺口 | 现在 |
|---|---|
| **消息类型体系** | **已闭合**——[按「谁在说话」分](../PF-009-context-message-types/design.md#七种消息按谁在说话分) |
| **事件做成哪一类消息** | **已闭合**——`SystemReminderMessage`，且**说状态的取代、说事的追加** |

§5.12 已回填：三类事件里**前两类是「事」（追加），注入的上下文变动是「状态」（取代）**。
不这么分，上下文变过三次记录里就躺着三份互相矛盾的说法——**而 agent 不知道哪份是现在的**。

**仍缺两条**：压缩产出什么形状、卸载后的占位算哪一种消息。
**已由 [PF-010 rev 2](../PF-010-context-management-and-assembly/README.md) 做掉。**

### 草稿期内被推翻的一条：「摘要只生成一次」

PM 推出过「**摘要只生成一次，不再被二次压缩**」，写进了 §5.5 与 §7 取舍表。
**产品负责人 2026-09-18 推翻：**

> **不断言压缩后的消息不能被再次用来压缩**——
> **「已有的摘要 + 新消息 → 新的摘要」是允许的一种策略。**

**PM 错在哪**：「压缩的输入是上一次压缩点到现在」这条裁决**只说明输入区间是增量的**，
**推不出「产物不可再被收走」**。两句之间隔着一步没有依据的跳跃。

**§5.5 与 §7 已就地标注推翻，正文未删**——留着能看出这里出过什么问题。
**摘要能不能被再次收走、怎么收，归 [PF-010](../PF-010-context-management-and-assembly/README.md)（rev 2，已接受）。**

**下游要复核**：任何按「摘要不可二次压缩」实施的东西。
