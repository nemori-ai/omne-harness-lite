## 一、背景与问题

前面几个 topic 各自回答了一部分：agent 能做什么（[PF-006](../PF-006-tools-and-skills/design.md)、
[PF-007](../PF-007-meta-capabilities/design.md)）、什么时候停下来等人（[PF-008](../PF-008-human-in-the-loop/design.md)）、
它由什么装配而成（[PF-004](../PF-004-agent-definition-and-assembly/design.md)）、
留下什么（[PF-000](../PF-000-occurrences-and-record-entries/design.md)）、
怎么组装给模型看（[PF-010](../PF-010-context-management-and-assembly/design.md)）、
跑偏了谁接手（[PF-011](../PF-011-off-nominal-handling/design.md)）。

**没有人回答的是：这些串起来，一次运行怎么往前走。**

五个问题因此悬着：

- **一次运行有哪些步骤，从哪一步能到哪一步？**说不清，就没人能实现它，
  也没人能判断某个实现走岔了。
- **系统在一次运行没走完的时候停机了，怎么办？**这是产品要求，不是可选项——
  一个跑了两小时的任务因为一次重启就从头再来，用户不会接受。
- **这一次运行花了多少、成没成、什么时候算完——这三个问题归谁答？**
  答案分散在三个对象上，就永远拼不出「这次失败的任务花了多少钱」。
- **agent 原地打转怎么办？**它会转到什么时候？谁来叫停？
- **想在这套流程里插一手，能插在哪、能做什么？**今天已经有三处在插手了，
  **而它们从没被放在一起看过**。

> **「出错了算谁的」不在这张单子上。**非常态的分层处置归
> [PF-011](../PF-011-off-nominal-handling/README.md)；本 topic 只说
> [Run 这一层的终态与那条阶梯是两条线](#512-run-的终态与非常态的终局是两条线)。

## 二、目标与非目标

### 目标

1. **分清 [Run](#run) 与 [Agent Loop](#agent-loop)**，说明为什么必须是两个概念。
2. **定 Run 的数据与治理面**：它是什么的归属单位、一次 Run 与几次[执行尝试](#执行尝试)的关系、[终态](#运行终态)有哪几种，
   以及**只看日志怎么判断此刻该不该起一副 [agent runtime](#agent-runtime)**——[那是 Run 存在的全部理由](#它存在的理由让起不起协程只看日志就算得出来)。
3. **给出状态转移方程**：状态是什么、有哪些转移、每一步之后落到哪。
4. **定义「重新算一遍」**：三条路通向它，**不只是崩溃恢复**。
5. **定义循环守卫**：agent 原地打转时，系统按什么阶梯介入。
6. **定义 [Loop 拓展点](#loop-拓展点)**：**一共有哪些位置**、每个位置看得到什么、能做什么、不许做什么。
   **位置要完备**——租户与组织超管得能在任何一处插手，**而「完备」必须是推出来的，不是挑出来的**。

## 三、用户与场景

| 使用者 | 什么时候接触这块 | 他关心什么 |
|---|---|---|
| **用户** | 任务跑了一半系统重启了 | 我那个任务还在吗？**会不会重复做一遍** |
| **对成本负责的人** | 看账单 | 这次任务花了多少？**那笔失败的花了多少** |
| **运维** | 排查一个卡住的运行 | 它现在在哪一步？为什么不动了？ |
| **安全负责人** | 评估自动化边界 | agent 能自己转多久？谁能叫停？ |
| **写拓展的人** | 想在流程里插一手 | 我能插在哪？**看得到什么、能改什么** |
| **实现这套东西的人** | 每一天 | 这一步之后该干什么？**这个判断依据从哪来** |
| **agent 自己** | 每一轮 | 我上一步做到哪了？**我是不是刚从一次中断里回来** |

### Run

**一次逻辑上的执行请求及其结果。**它**是一个纯粹的逻辑概念**——
没有哪一段进程、哪一个连接、哪一次请求与它一一对应。
**它的价值在于它能被写下来**——写不下来的东西，停机就没了。

#### 它存在的理由：让「起不起协程」只看日志就算得出来

[Agent Loop](#agent-loop) 回答的是「**[agent runtime](#agent-runtime) 在跑的时候**，下一步该干什么」。
可协程会没——崩了、被回收、[等人的时候主动交还](#agent-runtime-的四条不变式)。
**没了之后，总得有人决定要不要再起一个、起来接手什么**，
而这个决定同样只能看日志：那一刻内存里什么都没有。

> **Run 就是为这个决定而存在的那一族条目。**

**它的充分性判据只有一句，本 topic 每一条设计都用它验收：**

> **把整个运行系统关机、抹掉所有内存、只留[会话日志](#会话日志)，重新开机后必须能回答
> 「现在该不该起一个 agent runtime、它接手什么」，且答案唯一。**
> **能回答，Run 的设计就够了；不能，就还缺条目。**

**没有它，这五件事一件都算不出来：**

| 算不出来的 | 反证 |
|---|---|
| **该不该起** | 日志里躺着一条用户消息。**光看它，分不出「还没人处理」和「已经有一副协程正在处理」**——两种情况在纯消息日志上长得一模一样。宁可多起，同一条消息被做两遍、[外部效果做两次](#514-外部效果的记录追溯与幂等是同一条记录上的两个字段)；宁可不起，消息永远没人管 |
| **哪些还没被处理** | [队列](#待处理消息队列)是「已记录的输入减去已被承接的」。**减数没落在日志里，队列在停机之后就重建不出来** |
| **几条输入算一次推进** | 边界没被写下来，**新的一次尝试吃进去的顺序就取决于崩溃时刻**，而不是日志事实——[`f` 两次的输入不同，算出来的下一步就可以合法地不同](#52-会话日志是唯一的真相来源) |
| **账、失败、结果、外部效果算谁的** | 这些都是要长期成立的事实，**必须挂在日志里有身份的东西上**。协程连身份都随崩溃消失，挂不住（[§5.13](#513-run-拥有什么归属的判据)） |
| **「在等」这件事本身** | 等待期间[一份计算资源都不占](#agent-runtime-的四条不变式)，所以此刻**没有任何内存装得下「谁在等、等什么」**。只能在日志里（[§5.13](#等待必须是一条显式的记录)） |

#### 边界：什么让它开始，什么让它结束

| | |
|---|---|
| **开始** | **存在尚未被承接的输入**，**且没有未终结的 Run**。两条缺一不可：没有输入就没有推进的理由；已经有一个未终结的 Run，那条输入该交给它（见下） |
| **结束** | **落[终态](#运行终态)**，三种之一。**没有第二种结束方式** |

**开始要落一条 Run 开始条目，而它必须写明承接了哪些输入。**
不写，上面那张表的第二行就还是空的。

> **「承接」指的是 loop 把队列里的一批输入取走、交给这个 Run 去处理。**
> **每一次承接都要落一条记录**（[§6.16](#616-日志里至少要有这几种-run-相关的条目)）——
> 不落，「已被承接」这件事就只活在内存里。

**[待处理消息队列](#待处理消息队列)不定义边界，边界定义队列：**

> **队列 = 已记录的输入 − 已被承接的输入。**
> **它是日志的一个投影，不是真相的载体**——崩了重算一遍就有，
> 而边界是日志事实，**崩了必须还在**。

**「触发」与「收束」不是两个独立的概念，是这条规则的两端**——
[触发](../../ubiquitous_language/terms/agent-runtime-loop.md#ul-trigger--触发--trigger)就是**让队列从空变成非空的那件事**，
收束就是**再没有可承接的输入，这个 Run 落终态**。

> **「模型没话说了」不等于做完了。**
> 落「完成」的判据是**模型这一轮没给动作，并且队列也空**（[T2′](#56-状态转移表)）。

#### Run 跑着的时候，又进来一条东西

| 进来的是什么 | 怎么处置 |
|---|---|
| **这个 Run 正在等的那样东西**（人对提问的回话、前台工具交回的结果） | **必须并入当前 Run。**它本来就是这个 Run 在等的——**Run 的存活期跨得过等待**，[等人不是终态](#66-终态不可逆且只有一个出口) |
| **自发到达的**（用户中途补一句、后台结果回来、别的 agent 捎来一句） | **默认也并入。**loop 下一次取用时一并取走，**每次并入追加一条承接记录** |
| **带[插队](../PF-014-inbound-intake-and-queueing/design.md#插队)命令来的用户消息** | **打断**：中断当前这一步、解除各种等待态，那句话排到队首。**这个 Run 不落终态**——[被打断的是这次尝试](#511-外面进来的事怎么到-agent-眼前) |

**默认并入这一条，是[「持有队列并循环取用」](#agent-runtime)的直接后果**——
一次协程生命期内本来就会吃多条。**它的硬条件只有一个：每一次取用都落一条承接记录。**
不落，[新的一次尝试](#57-一次尝试三条路通向重新算一遍)重算时的取用点就与上次不同，
**`f` 的输入序列变了，算出来的下一步可以合法地不同**。

> **这样定，一个很自然的问法就不成立了**：Run 跑着的时候一个后台结果回来，
> **「要不要把它叫醒」**——叫醒一个已经停了的方程本来就讲不通。
> **不必问**：东西进队列，这个 Run 还没终结，**它本来就该被这个 Run 消费**；
> 真要是已经终结了，**那就开下一个 Run**。
> **[§6.12](#612-终态之后再回来的东西不让-run-复活) 那条「不让 Run 复活」照旧成立**：
> 不复活**这一个**，不等于不许有**下一个**。

#### Run 未终结，不等于有一副 agent runtime 活着

**这是本 topic 最容易被读反的一句。**

> **一个 Run 完全可以在没有任何协程活着的时候，合法地处于未终结状态。**

[等人可能等三天](#这个循环从哪里出去)，那三天里协程早已交还，
**而那段工作还好端端地悬在日志上**。把「未终结」读成「有协程在跑」，
要么会去杀一个根本不存在的协程，要么会把一个在等的 Run 当成已经结束。

#### 只看日志，该不该起一个 agent runtime

**这张表就是那个「只读日志的判断」本身。**它不读进程表、不读内存、不读任何活着的东西——
**[充分性判据](#它存在的理由让起不起协程只看日志就算得出来)的兑现就是它。**

| # | 日志里最新的那个 Run | 还没被承接的输入 | 该做什么 |
|---|---|---|---|
| **1** | **一个 Run 都没有** | 没有 | **什么都不做**（会话空闲） |
| **2** | **一个 Run 都没有** | 有 | **落一条 Run 开始条目**（写明承接哪些）→ 起一副 agent runtime → 算下一步 |
| **3** | **未终结，没有悬着的等待** | 不论有没有 | **确保有且仅有一副 agent runtime 在推进它**；没有就起一副，从日志重算接着走 |
| **4** | **未终结，有悬着的等待，等的东西还没到** | 无关 | **不要起 agent runtime。**这段工作当前**一份计算资源都不占** |
| **5** | **未终结，有悬着的等待，等的东西已经落进日志** | — | **起一副**，承接它（落一条承接记录），接着算 |
| **6** | **已终结** | 没有 | **什么都不做**（会话空闲） |
| **7** | **已终结** | 有 | **开下一个 Run**（开始条目可带一个「延续自哪个 Run」的链接）→ 起一副 |

**第 3 行分不出「一副协程正健康地跑着」和「一副跑到一半崩了留下的孤儿」——这不是缺陷，是正解。**
对日志来说这两种情况该做的事完全一样：**确保有一副在推进它**。
「此刻到底有没有活的」属于运行期的资源管理，**它恰恰是停机之后必然不成立的那类事实**，
不进日志语义。

> **「有且仅有一副」靠[尝试序号](#执行尝试)当栅栏**：
> **只有序号最大的那次尝试的写入被接受**，序号更小的写什么都被拒。
> 详见 [§5.7](#同一个-run-同一时刻只有一副协程在推它)。

**第 4 行不等于「这个会话没事干」。**它只说这段工作当前不需要计算资源；
此刻有别的输入到达，照上面那张表并入就是——**无论如何都不会产生第二个 Run**。

#### 一个会话，任一时刻至多一个未终结的 Run

**这不是性能约束，是[重放确定性](#52-会话日志是唯一的真相来源)逼出来的。**

两个 Run 同时在推，它们会交错地往**同一本日志**里写。
那么其中一个的第 k 次求值看见的那段日志，**取决于另一个此刻恰好写进去了几条**——
**那是调度时序，不是日志事实**。新的一次尝试里时序不同，`f` 的输入就不同，
**「重算一定得到同一个答案」当场失效**。

> **这条限制的是治理单位的数量，不是并行度。**
> 一个 Run 内部同时调三个工具、一边等人一边等后台，**全都允许**——
> 它们在同一个 `f` 的推进之下，结果写回同一个 Run。
> **[会话内单活跃](../../ubiquitous_language/terms/agent-runtime-loop.md#ul-single-active-execution--会话内单活跃--single-active-execution)说的就是这件事。**

#### 这一套成立的三个前提

**它们不是推论，是前提**——任何一条不成立，上面整节都要重做。

| 前提 | 不成立会怎样 |
|---|---|
| **同一个会话里，日志条目有确定的先后，写一条是一下子写成的** | 「重算一定得到同一个答案」无从谈起，`f` 是纯的这件事就没有意义 |
| **同一个 Run 不会被两副协程同时推进**（本 topic 用[尝试序号做栅栏](#同一个-run-同一时刻只有一副协程在推它)兑现） | 崩溃恢复可能与一副假死又活过来的旧协程并发，**同一件外部效果做两遍** |
| **一个会话对应一条推进线**（[前面那张表](#只看日志该不该起一个-agent-runtime)描述的是一副协程的处境） | 「一个会话里挂多个 agent 各自推进」要求 `f` 的输入从整本日志改成「本推进线看得见的那一份」，**那是改前提，不是改细节**——本版不支持 |

#### Run 是三样东西的归属单位

**这是「Run 是数据 / 治理的概念」那句话的实质。**

| 归什么 | 归到 Run 意味着 | 不归它会怎样 |
|---|---|---|
| **成本** | 这一次一共花了多少，算在它头上（**明细按[尝试](#执行尝试)记，汇总按 Run 算**，见 [§5.13](#成本两层缺哪一层都会算错)） | 账单只剩会话级的一个总数，**看不出是哪一次任务贵** |
| **失败** | 「这次没成」是它的属性 | 挂在会话上，**一次失败污染整段协作**；挂在[agent runtime](../../ubiquitous_language/terms/agent-runtime-loop.md#ul-agent-runtime--agent-runtime--agent-runtime)上，**实例一回收失败就没了** |
| **收束** | 「这件事做完了」那个时刻属于它 | 没有「完了」这个时刻，**就没法回话给人，也没法结算** |

**三样必须是同一个单位**，因为它们回答的是同一个问题：

> **这一次要做的事，怎么样了。**

分给不同的单位，这个问题就要跨三个对象拼，**而它们的边界不一样，拼出来的答案对不上**。
最具体的一种错法：**成本归实例、失败归 Run**——一次 Run 换过两个 agent runtime，
成本分成两笔而失败只有一笔，**问「这次失败的任务花了多少钱」，答不上来**。

**这三样是最要紧的，但不是全部。**哪些东西非挂在 Run 上不可、哪些该留给那副协程，
判据与完整清单在 [§5.13](#513-run-拥有什么归属的判据)。

> **本 topic 只定归属单位，不定怎么算钱。**
> 成本[按租户归属](../PF-001-identity-scope-and-agent-constraints/design.md#租户)那一层归 PF-001；
> 费率、账单、配额是别处的事。

**Run 是「一次任务」这一级的归属单位，不是唯一的一级。**

系统里存在**不属于任何 Run 的模型调用**——最清楚的例子是**旁路提问**：
用户趁 agent 干活时问一句「刚才那个配置文件叫什么来着」，
它读得到日志，但**问和答都不进日志**，也不改变下一步。
它花钱、会失败，**却不属于任何一次尝试，也不属于任何 Run**。

| 这次调用 | 归到哪一级 |
|---|---|
| Run 里的调用，以及[挂件](#58-loop-拓展点)为这个 Run 做判断时自己发起的调用 | **这个 Run** |
| 不属于任何 Run 的（旁路提问那种） | **会话那一级** |

> **不点破，「Run 是成本的归属单位」会被读成「所有成本都归 Run」**，
> 于是旁路提问的花费要么无家可归，要么被硬塞进一个跟它无关的 Run。
> **归属规则本身归 [PF-015](../PF-015-session-lifecycle-and-ownership/README.md)**，本 topic 只声明 Run 不是唯一的一级。

#### Run 不拥有两样东西

| 不拥有 | 归谁 | 后果 |
|---|---|---|
| **[会话日志](#会话日志)** | 会话 | Run 结束了日志还在；Run **引用**它，不另存一份 |
| **agent runtime** | [agent runtime](../../ubiquitous_language/terms/agent-runtime-loop.md#ul-agent-runtime--agent-runtime--agent-runtime) | 同一次 Run 可能跑在两副不同的 agent runtime 上（见下） |

### 执行尝试

**同一个 Run 内，第几次为它起一副 [agent runtime](#agent-runtime)。**
也就是**那副协程从起到灭的那一段**。

> **Run 是逻辑的，尝试是物理的。**
> 崩溃后恢复、换一份构成、等人回话之后接着跑——**各是一次尝试，但都还是同一个 Run。**

**它不是第二个执行体。**执行体只有一个，就是 agent runtime；
**这一条是从 Run 的角度看它**——同一副协程，站在治理那一侧叫「这个 Run 的第几次尝试」。

**它的身份是 (哪个 Run, 第几次)，从日志里那条[尝试开始记录](#每一次尝试开始都要做四件事)派生，不另存一份。**

| | |
|---|---|
| **为什么需要一个指得到的身份** | 一次[外部效果](#514-外部效果的记录追溯与幂等是同一条记录上的两个字段)可能被重做，**人要能说清「第 2 次尝试发出了那封邮件，第 3 次又发了一遍」**。说不清，重复的外部效果就永远查不出是哪一次干的 |
| **为什么不需要自己的存储** | 它没有任何「只有它知道」的东西：内存态[重算即得](#52-会话日志是唯一的真相来源)，花的钱记在成本条目里，做过的事记在效果条目里。**给它建一套存储，就是凭空多出一份会和日志对不上的状态** |

**序号显式写在那条记录里，不靠「数一数前面有几条」**——
[栅栏要拿它做比较](#同一个-run-同一时刻只有一副协程在推它)，而数数在日志分段归档、只读到一截的时候很脆弱。

**这一条是「归属单位」的直接后果**：一次网络抖动重试若算成两个 Run，
**账和失败都算错**。

**三条路通向一次新的尝试**，[它们在方程眼里是同一件事](#57-一次尝试三条路通向重新算一遍)。

### 会话日志

**一个会话里发生过的事，按发生的顺序留下的那一份流水账。**

> **它只增不改。**

三条，缺一条这个概念就立不住：

| | |
|---|---|
| **归会话，不归 Run** | Run 结束了它还在。Run **引用**它，不另存一份 |
| **只增不改** | **只往后加，不回头改，也不删**（**不改的是内容**，见下） |
| **日志 ⊋ 消息** | 里面还有**各种不是消息的事**，见下 |

**最后一条容易被忽略，而它是要紧的**：把日志和「消息历史」当成一回事，
那些**不是消息的东西**——[每次工具执行的账](../PF-006-tools-and-skills/design.md#54-返回值两种写法一种模型)、
[一次尝试开始这个事实](#57-一次尝试三条路通向重新算一遍)——**就没地方安放**。

> **它的正式词条是
> [UL-session-log](../../ubiquitous_language/terms/record-and-context.md#ul-session-log--会话日志--session-log)。**
> **不要管它叫「记录」**——那与[记录条目](../PF-000-occurrences-and-record-entries/design.md#记录条目)字面撞得太近，
> **一个是那本账，一个是账上的一行。**

#### 「只增不改」怎么和压缩、卸载共存

**看着像在改日志的三件事，其实都是追加：**

| | 看着像 | 实际上 |
|---|---|---|
| **压缩** | 把前面一大段换成一条摘要 | **往后加一条 [`CompactionMessage`](../PF-010-context-management-and-assembly/design.md#57-压缩能做的只有两件事)**——摘要是它的内容，**「从我之后这些块不再模型可读」那份名单是它自己带着的**；**前面那些消息一个字没改，标注也一位没翻** |
| **卸载** | 把大结果换成占位 | **原始结果从来没进过日志**——[进去的一直就是占位](#510-卸载结果落成消息之前的那一关) |
| **取回全文** | 把占位换回原始结果 | **往后加两条新消息**（见 §5.10） |

> **[一条消息都不能擦除](../PF-010-context-management-and-assembly/design.md#612-记录里的消息一条都不能擦除)**，
> 不管它还模型不模型可读。**「不给模型看」不等于「可以删」。**

#### 方程从日志里读什么

**日志是全量的，而方程只读其中一部分。**

> **只有[效力为「依据」](../PF-000-occurrences-and-record-entries/design.md#条目效力--entry-standing)的那些条目进方程的定义域。**

**这不是本 topic 定的**，是
[PF-000 §5.2](../PF-000-occurrences-and-record-entries/design.md#52-那个判断两条独立充分条件) 定的：
只由「解释得了发生过什么」那一条成立的条目，**是留痕，不进定义域**。

**典型的三类「依据」条目：**

| 是什么 | 内容 |
|---|---|
| **消息历史** | 人说的、模型回的、动作发出去的、结果回来的 |
| **Run 的姿态** | 在跑 / 停着等 / 已经[终态](#运行终态) |
| **悬着的东西** | 没答完的[决策卡片](../PF-008-human-in-the-loop/design.md#决策卡片)、转到后台还没回来的执行 |

> **这三类是「依据」条目的典型内容，不是定义域的定义。**
> **判据在 PF-000，不在这里**——不这么写，下一个人会从留痕条目里取状态，
> 而[那正是 PF-000 把两条分开记要挡的事](../PF-000-occurrences-and-record-entries/design.md#52-那个判断两条独立充分条件)。

### 当下条件

**算下一步时，日志之外还要看的那些此刻才成立的事实。**

| 它包含 | 归谁 |
|---|---|
| [当下可用性](../PF-006-tools-and-skills/design.md#62-可用性在每次-run-开始前重算) | PF-006 |
| **这一次用哪个模型**（连同它的窗口有多大） | [PF-004 §6.6](../PF-004-agent-definition-and-assembly/design.md#66-模型在每次请求时确定) |
| [注入](../PF-004-agent-definition-and-assembly/design.md#注入)进来的那些：上下文、权限，以及[按它们现算出来的执行环境落点](../PF-005-execution-environments-and-sandboxes/design.md#61-宿主机始终在场沙箱实现装配时可选装配) | PF-004 · PF-005 |

**它不落日志，每次重算。**

> **当下条件会变，方程不变。**
> 新的一次尝试里，它可能与上一次不同——**那不是不确定性，那是事实**。

### 待处理消息队列

**还没有被 Agent Loop 消费过的那些消息，按到达先后排成一列。**

> **它不是另一份存储，是[会话日志](#会话日志)的一个投影：**
> **队列 = 已记录的输入 − 已被[承接](#边界什么让它开始什么让它结束)的输入。**
> 两边都是日志里的事实，所以**「哪些还没被消费过」从日志本身就算得出来**。

**这一条不是实现取舍，是被两条既有规矩逼出来的：**

| 逼它的那条规矩 | 如果队列是另一份存储会怎样 |
|---|---|
| [收进来是改日志的动作，组装只负责把日志里已有的拼出来](#511-外面进来的事怎么到-agent-眼前) | 队列成了第二个要被消费的地方，而**组装是纯派生的**，方程当场失效 |
| [攒在内存里的东西，一次重启就凭空消失](#511-外面进来的事怎么到-agent-眼前) | **停机就丢消息**——而[停机是主路径的一部分](#57-一次尝试三条路通向重新算一遍)，不是异常 |

**于是它天然具备三条性质**，一条都不用额外设计：

- **持久**：日志怎么活，它就怎么活。停机再起来，**重算一遍就有了**
- **可恢复**：「消费到哪了」[从日志派生，不另存](#67-检测状态从日志派生不另存)
- **不会与日志对不上**：它就是日志算出来的，**没有两份数据可分叉**

#### 先到先处理，只有一个例外

**默认按到达先后，不分级。**唯一的加急通道是**插队**：

> 一条**带着插队命令来的用户消息，直接排到最前面**，
> 并且 **loop 里各种等待态一并解除**。

**不设第二种优先级。**「工具结果要不要天然比用户消息优先」这类分级，
**每多一级就多一处要解释的语义**，而插队已经覆盖了"我现在就要"这个全部需求——
**一个机制，不是两个**。

**队列里有哪几种消息、什么东西在什么情况下会进来、插队怎么被受理**，
归 [PF-014](../PF-014-inbound-intake-and-queueing/README.md)；
**本 topic 只定 loop 怎么消费它、以及它空了会怎样。**

### Agent Loop

**一次 Run 怎么从这一步走到下一步的那套逻辑，写成一个方程。**

```text
下一步  =  f ( 会话日志 , 当下条件 )
```

**`f` 是纯的**：同一份日志配同一份当下条件，算出来的下一步唯一。

> **恢复不是「接着上次的进程」，是「重新算一遍 `f`」。**

**「状态转移方程」是它的另一种说法**（产品负责人 2026-09-17 原话），不是两个概念。

### agent runtime

**反复求值 `f`、把一次 Run 往前推的那个协程。**

它有独立的执行上下文，能在 await 点挂起与恢复，**能被独立取消**，有自己的生命周期。
它**持有[待处理消息队列](#待处理消息队列)并循环取用**，因此是**全系统唯一的 event loop**。

> **`f` 是被求值的那个，agent runtime 是求值它的那个。**
> 方程没有寿命，协程有；**方程算不坏，协程会被取消。**

**它不持有状态。**状态全在[会话日志](#会话日志)里——**这正是 `f` 能被重新算一遍的前提**。
协程没了，日志还在，[下一次尝试](#执行尝试)重新算，得到同一个答案。

它**照一份[装配清单](../PF-004-agent-definition-and-assembly/design.md#装配清单)起**，
但**不等于那份清单**：清单是数据、可跨多次尝试复用，协程每次重新起。
清单怎么算出来，归 [PF-004](../PF-004-agent-definition-and-assembly/README.md)。

> **它就是 [SYS-COMPOSITION 说的「活体」](../../foundation/definition-and-runtime-composition/requirements.md#sys-compositionc1三段结构)。**
> 那一段描述的「计算资源、占用即消耗、可回收可重建、因资源治理而生灭」，
> **逐条说的都是协程**——[命名与归属的裁决见 UL-D-3](../../ubiquitous_language/decisions.md#ul-d-3--runtime-与活体--2026-09-20)。

**它是[模型请求运行时](../PF-013-model-profiles-and-invocation/design.md)与
前台[工具执行运行时](../PF-006-tools-and-skills/design.md)的宿主**——见 [§6.13](#613-取消跟着宿主走)。

### agent 的一步

**Agent Loop 转一圈**：看到处境 → 决定做什么 → 做 → 看到结果。

一次 Run 由一步接一步构成。**一步之内至多一次[模型调用](../../ubiquitous_language/terms/execution-and-outcome.md#ul-model-call--一次模型调用--model-call)，
以及由它带出来的若干次[工具执行](../../ubiquitous_language/terms/execution-and-outcome.md#ul-tool-execution--工具执行--tool-execution)**——
[后两者是兄弟，互不包含](../PF-011-off-nominal-handling/design.md#53-层的顺序不是排出来的是推出来的)。

### 运行终态

**一次 Run 的结局，恰有三种：完成 · 失败 · 被取消。**

**到了就回不去**，且[只从一个出口落账](#66-终态不可逆且只有一个出口)。

> **停下来等人不是终态**——那是它还活着时的一种姿态。

**[被取消自成一种](../PF-006-tools-and-skills/design.md#67-用户可以中断而中断不是失败)，不并进失败。**

### Loop 拓展点

**Agent Loop 上一个开放的位置，挂在某个[状态点](#53-改日志的动作与纯派生的动作)的紧前或紧后。**

> **它按自己相对哪个状态点命名，不按挂在那儿的功能命名**——
> 「落终态之前」是位置，「打转保护」是挂在那儿的一件东西。
> **同一个位置可以挂多个[拓展件](#拓展件)，各干各的。**

| | |
|---|---|
| **一共几个** | **十一个**（[§5.8](#58-loop-拓展点)）。**位置由状态点推出，所以数目有限且可穷举**；挂什么没有上限 |
| **怎么起作用** | **只能靠改会话日志**——追加一条，或决定下一条**还没落盘**的东西长什么样。**它不改方程本身** |
| **它自己是状态点吗** | **不是。**它长在别的状态点的边上，[不新增状态点](#53-改日志的动作与纯派生的动作)——**这正是位置能穷举的原因** |
| **纯派生的动作前后有位置吗** | **没有。**[组装是纯派生的](#53-改日志的动作与纯派生的动作)，它不是状态点 |

### 拓展件

**挂在某个 Loop 拓展点上的一段判断或动作。**它声明自己**挂在哪个位置**、**管哪些情形**，
以及自己的**干预力**——只观察 / 可改写 / 可否决。

**它注册进来之后，就是 [agent runtime](#agent-runtime) 里的一段执行**，
和 loop 自己的主流程用同一种「停下来等外面应答」的办法——
所以**可否决那一档的拓展件能落一张卡片、让 Run 停下来等人**（[§5.8](#等人是-loop-的原语)）。

**它是装了才有的可插拔服务**：它依赖的东西用不了，**就当它被卸载了**；
它在、跑起来却报了错，**按它那一类的处置策略办**（[§5.8](#拓展件是可插拔的服务不可用即卸载报错按策略)）。

> **它是[第八类资产](../PF-002-assets-settings-and-permissions/design.md#loop-extension)。**
> 怎么被持有、谁能装、组织配了租户能不能改，**走资产已有的那一套**，
> 本 topic 不重复；**形状与组合归 [PF-002](../PF-002-assets-settings-and-permissions/README.md)，位置与约束归这里。**

**⚠️ 别混**：**拓展点是位置，拓展件是挂上去的东西。**

## 五、模型

### 5.1 Run 与 Agent Loop 是一体两面

| | **Run** | **Agent Loop** |
|---|---|---|
| 是什么 | **数据 / 治理**的概念 | **执行逻辑**的描述 |
| 回答什么 | 这次运行是什么、归谁、**现在到哪一步了** | **从这一步怎么走到下一步** |
| 形态 | 可记录、可查、可审计的状态 | **状态转移方程** |
| 缺了它会怎样 | 停机之后**不知道当时在哪** | 知道在哪也**算不出下一步** |

**为什么必须分成两个概念**：把它们合成一个，就会写出「Run 对象自己知道怎么往下走」
这种设计——**而那个「知道」活在进程里，停机就没了**。

分开之后，**一个负责被写下来，一个负责被重新算出来**。

### 5.2 会话日志是唯一的真相来源

> **没有明确记载的，就当它没发生。**

三条直接推论：

- **新的一次尝试从最后明确记载的状态重新算。**不猜、不推测、**不去别处取状态**。
- **任何只活在内存里的状态都是缺陷。**它在停机那一刻就没了，而**没人知道少了什么**。
- **哪怕因此重做一遍，也接受**——代价写在 [§6.4](#64-每一次尝试开始agent-都要知道)。

### 5.3 改日志的动作，与纯派生的动作

**这条分界比任何一个具体动作都重要。**

| 动作 | 改日志吗 | 是状态点吗 |
|---|---|---|
| **尝试开始** | **是**——追加[一条尝试提醒](#64-每一次尝试开始agent-都要知道) | **是** |
| **消息落盘** | **是**——追加那条消息 | **是**（[条件性，见下](#消息落盘是唯一一个条件性的状态点)） |
| **上下文压缩** | **可能**——真压了就追加一条 [`CompactionMessage`](../PF-010-context-management-and-assembly/design.md#57-压缩能做的只有两件事) | **是** |
| **上下文组装** | **否**——纯粹从日志算出来 | **否** |
| **调模型** | **是**——追加回复 | **是** |
| **执行动作** | **是**——追加结果 | **是** |
| **落终态** | **是**——[终态是一条事实](#运行终态) | **是** |
| **跑一个[位置](#58-loop-拓展点)上的[拓展件](#拓展件)** | **可能** | **否**——它长在别的状态点的边上 |

> **状态点恰好六个**：尝试开始 · 消息落盘 · 压缩 · 调模型 · 执行动作 · 落终态。
> **这张表要穷举，不是举例**——[十一个拓展点位置就是从这六个推出来的](#58-loop-拓展点)，
> **少列一个，位置清单就少两条**。

> **上表里「改日志」一律是「往后加」**，[日志只增不改](#会话日志)。
> 连压缩也不例外——它加的是一条 `CompactionMessage`，**不是把前面那段抹掉**。

> **纯派生的动作不进状态空间。**重算一定得到同样的结果，
> 所以不必给它建检查点，新的一次尝试里也不必知道「上次做到哪了」。

#### 光有点不够，还要说得清点与点之间

**点回答「日志在哪几处会变形状」，但它回答不了三个问题：**
**点与点之间那一截在干什么、能不能中途停、停了之后从哪儿接上。**

> **一个段，就是 `f` 的取值保持不变的那一段连续执行。**
> **段的边界，就是状态点。**

**一个段里发生的事，合起来只做两件**：往日志里加一批东西，然后**停在一个等待上**。

| 段停在哪种等待上 | 谁在外面 |
|---|---|
| **等模型** | [模型请求运行时](../PF-013-model-profiles-and-invocation/design.md) |
| **等工具** | [工具执行运行时](../PF-006-tools-and-skills/design.md) |
| **等压缩交回** | [压缩那个闭包](../PF-010-context-management-and-assembly/design.md#56-压缩是一个闭包它的调子是三个联合目标) |
| **等人** | [决策卡片](../PF-008-human-in-the-loop/design.md#决策卡片)被答完 |
| **等队列** | 外面还没有东西进来 |
| **不等了** | 落[终态](#运行终态)，这个 Run 到此为止 |

**由此掉出三条性质，都是段的定义的直接后果：**

- **[拓展件](#拓展件)不改变 `f` 的取值。**它往段里多塞了一条，
  **但跑完它，`f` 还指着同一个段**——尾巴的形状没变。
- **段是可以重做的最小单位。**段内任意位置断掉，
  [下一次尝试](#57-一次尝试三条路通向重新算一遍)重新算 `f`，**还是指向同一个段**，从头做一遍。
- **每一个等待都恰好落在段的末尾。**不会出现「段做了一半去等一件事，回来接着做这个段」——
  **那种东西没法重做**。
  [拓展件出卡等人](#等人是-loop-的原语)也不例外：等到了之后**不是接着做，是把这个段从头重做一遍**，
  而段里**已经记下的那几次等待按记录直接交回**，不再真的去等、去调、去问。

#### 由此得到判据：看跑完它 `f` 的取值变不变

> **要不要给一个动作建状态点——看跑完它，`f` 的取值变不变。**

**「看它改不改日志」不够用**，拓展件就是现成的反例：**它改日志，但它不是状态点**。
**它要是能改变 `f` 的取值，就等于自己指定跳到哪一步，而那是被禁的**（[§5.8](#能做什么不能做什么)）。

> **这一条正是位置清单能穷举的原因。**位置由状态点推出；
> 拓展件不产生新状态点，**所以不会「拓展点的拓展点」递归下去**。

**组装是这一圈里唯一纯派生的那一段**：跑一次、跑十次都不留痕，
[前后也推不出拓展点](#十一个位置是推出来的不是挑出来的)。

#### 「消息落盘」是唯一一个条件性的状态点

**六个状态点里，五个是这个 Run 自己提交的，只有它是外面提交的**——
[事件先落进日志，才到 agent 眼前](#511-外面进来的事怎么到-agent-眼前)。

**而它只在一种情况下才是段的边界：**

> **[待处理消息队列](#待处理消息队列)从空变成非空的那一刻。**

**队列本来就非空，再落进一条，`f` 还是「该想了」**——取值没变，**那就不是边界**，
落进来的那条**等下一轮一并被取走**。
**队列空着、Run 正停着等，这时落进一条，`f` 从「停住」变成「该想了」**——**那才是边界**。

> **这正是[插队解除等待态](#先到先处理只有一个例外)与「新消息唤醒一个停着的 Run」
> 是同一件事的原因**：它们都是这一个条件被满足了。

### 5.4 一步的骨架

```text
                  【想】
   队列非空 ──→ 交进⟨压缩闭包⟩ ──→ 装不下 ──→ 上交给会话 ──→ 失败
                   (挂着等)
                      │ 装得下
                      ↓
                 组装 ──→ 调模型 ──→ 回复落盘
               (纯派生)   (挂着等)      │
                                   ◆ 回复落盘之后
                                        │
                         ┌──────────────┴──────────────┐
                     没给动作                        有动作
                         │                             │
                    队列空吗？                    ◆ 放行判断
                    ├ 空 ──→ 【收尾】完成          ├ 要问人 ──→ 【等人】
                    └ 非空 ──→ 回【想】            ├ 全被否 ──→ 回【想】
                                                   └ 放行 ──→ 【做】
                                                                │ (挂着等)
                                                          ◆ 结果落盘之前
                                                                ↓
                                                         结果落盘 ──→ 回【想】

   ◆ = 这几处站着[系统自带的挂件](#系统自带的几件各站在哪)，只能靠改日志起作用。
       [循环探测](#59-循环守卫四级阶梯)站在「回复落盘之后」，[卸载判定](#510-卸载结果落成消息之前的那一关)站在「结果落盘之前」——
       **两件都不在[转移表](#56-状态转移表)里**，因为跑完它们 `f` 的取值不变。
       [拓展点一共十一个](#十一个位置是推出来的不是挑出来的)——**位置由状态点推出，这张图只画得下三处**

   「挂着等」的三处，就是这一步里的三个段各自的末尾（[§5.3](#53-改日志的动作与纯派生的动作)）。
```

### 5.5 「想」这一步：交进闭包，拿回装得下的一份

**这一步的头一件事是把日志交进[压缩那个闭包](../PF-010-context-management-and-assembly/design.md#56-压缩是一个闭包它的调子是三个联合目标)。**

```text
    日志 + 这一次要用的那份模型档案
                  ↓
           ⟨ 压缩闭包 ⟩   ← 要不要压、压哪一段、压到什么程度，全在里面
                  ↓
        ┌─────────┴─────────┐
    装得下了              装不下
        │                   │
     组装 → 调模型      上交给会话
```

**方程只认两个回执。**

| 闭包交回什么 | 方程看见的 |
|---|---|
| **装得下了** | 往下走：组装，调模型 |
| **装不下** | 一件[非常态](../PF-011-off-nominal-handling/design.md)——**这一层腾不出空间了** |

> **「压没压过」方程不问**，看日志的尾巴就知道：**多了一条 `CompactionMessage` 就是压过**。

**这一步为什么是一个[段的末尾](#53-改日志的动作与纯派生的动作)**：
闭包内部**要调模型生成摘要**，那是一次真正的等待——**协程在这里挂起，交回来才继续**。

#### 方程因此不必懂上下文预算

**「这一次有多长、窗口有多大、超没超」，方程一个都不需要知道。**

| 归谁 | 什么 |
|---|---|
| **闭包内部** | 量一量、要不要压、压哪一段、怎么在[三个目标](../PF-010-context-management-and-assembly/design.md#三个联合目标)之间取平衡 |
| **方程** | **只有「装得下 / 装不下」两个回执** |

> **换一整套压缩策略，这张[转移表](#56-状态转移表)一个字都不用动。**

**代价也要记下**：**闭包内部发生了什么，外面看不见**——
压了几轮、丢了多少，都得靠它自己往外说。

**压缩的输入区间两头都有界，两个界都归 [PF-010](../PF-010-context-management-and-assembly/design.md#由此压缩的输入区间是一个左右都有界的区间)**——
**本 topic 不复述**，[否则同一个事实就有了两个说法](../PF-010-context-management-and-assembly/decisions.md#四已知的来源问题)。

#### 压完还超：这一层腾不出空间了

**常驻那部分压不动**——[压缩只碰得到会话上下文那一块](../PF-010-context-management-and-assembly/design.md#给模型那一侧两块分别组装)。
如果光是固定部分就超了预算，**那是装配的问题，不是压缩能解决的**。

按 [PF-011 的判据](../PF-011-off-nominal-handling/design.md#56-了结得了吗看缺的那样东西在谁手上)：
缺的是**上下文空间**，而压缩就在运行这一层——**手段用尽了，上交给会话**。

**与此同时，这个 Run 落终态失败**，原因写明是固定部分超限，
否则运维会一直盯着对话长度查。

> **这是两件事，不是一件。**上交是那件非常态继续往外走，
> 终态是这一次运行到此为止。**两条线，见 [§5.12](#512-run-的终态与非常态的终局是两条线)。**

### 5.6 状态转移表

**看日志的尾巴，决定下一步。**

| # | 日志的尾巴长什么样 | 这意味着 | 下一步 | 落到 |
|---|---|---|---|---|
| **T1** | **[待处理消息队列](#待处理消息队列)非空** | 该想了 | **取一批 → [交进压缩闭包](#55-想这一步交进闭包拿回装得下的一份)** | T2 / **T1′** |
| **T1′** | 闭包**交不出装得下的东西** | 这一层腾不出空间了 | **上交给会话**（§5.5） | **失败** |
| **T2** | **装得下了**（闭包交回） | 可以发了 | **组装 → 调模型** | T2′ / T3 |
| **T2′** | 回复落盘，**模型没给动作**，**队列也空** | 这件事做完了 | **收尾** | **完成** |
| **T3** | 回复落盘，**有动作**，尚未判断 | 该判断了 | ◆ **执行动作之前那一串拓展件**（[放行判断](../PF-008-human-in-the-loop/design.md#52-那个判断函数)是其中一件），**这一批一起判** | T4 / T5 |
| **T4** | 卡片已落盘、**未答完**（不论是谁出的） | 该等了 | **停住**（[这次尝试的出口](#这个循环从哪里出去)） | T4 / T5 |
| **T5** | 这一批卡片**全答完**（或那一串直接给出了结论） | 有结论了 | [回到出卡的那一件接着判](#等人是-loop-的原语)；每个动作都有结论之后，放行的**去做**，被否的**写一条「不许做」及其来由**（人否的就是「人不同意」） | T6 / T8；**后面的件又出卡则回 T4** |
| **T6** | 动作**发出去了，结果没齐** | 该等了 | **停住**（[同上](#这个循环从哪里出去)） | T6 / T7 |
| **T7** | 动作结果**齐了**（转后台的、[被卸载的](../PF-006-tools-and-skills/design.md#610-结果太大时卸载而卸载是第三个维度)，**都以占位算齐**） | 该想了 | 回 T1 | T1 |
| **T8** | 一批动作**全被否** | 也得让它知道 | 回 T1（带着「人不同意」） | T1 |

**T1 排在最前面，这是有用的**：回复落盘、模型没给动作、**但队列非空**，
那个尾巴同时符合 T1 与 T2′ 的前半句——**按 T1 走，回去想**。
T2′ 要求「队列也空」，正是为了把这两种情形分开。

**◆ 标着的那一处站着[系统自带的挂件](#系统自带的几件各站在哪)。**
**[循环探测](#59-循环守卫四级阶梯)与[卸载判定](#510-卸载结果落成消息之前的那一关)不在这张表里**——
它们站在[拓展点](#58-loop-拓展点)上，**跑完它们 `f` 的取值不变**（[§5.3](#由此得到判据看跑完它-f-的取值变不变)）。

> **[挂件不新增状态点](#53-改日志的动作与纯派生的动作)**，它们各自长在某个状态点的边上；
> **站在哪个位置见 [§5.8](#系统自带的几件各站在哪)**。

**等人不只发生在 T3 那一处。**别的位置上的可否决拓展件（比如[循环守卫 L4](#59-循环守卫四级阶梯)、
落终态之前一件「收尾前先问一句」）也会出卡——**出了卡，尾巴就是 T4 的形状**；
答完之后[回到出卡的那个位置、那一件接着判](#等人是-loop-的原语)，
**判完照那个位置原本的走法往下走**。所以这张表**不必为每个位置各补一行「等人」**。

#### 循环探测的四种结局，全落在已有的行上

**它从表里拿走之后，一行转移都不用补**——它的每一种结论都靠[改日志](#69-拓展件只能靠改日志起作用)兑现，
**而改完之后的尾巴，本来就已经在表里了**：

| 探测判定 | 它往日志里落什么 | 方程下一轮读到 |
|---|---|---|
| **无事**（或只记一笔） | 不落，或落一条不进定义域的[留痕](#方程从日志里读什么) | **尾巴没变**——照 T2′ / T3 往下走 |
| **写一条干预消息** | 一条给 agent 看的提醒 | **队列非空 → T1**，回去想 |
| **判定转不动了** | **一条[终态](#运行终态)事实**（失败，原因：原地打转） | **读到终态就收**，和[被取消](#被取消不在这张表里因为它不是一行)同一个机制 |
| **判定要问人** | **一张[决策卡片](../PF-008-human-in-the-loop/design.md#决策卡片)** | **卡片悬着 → T4**，停住等 |

> **这就是把它做成挂件的全部理由**：四种结局，**四个已有的尾巴形状**。
> 留在表里，它得占四行；**拿出来，它一行不占，而产品行为一点没少**。

**[终态](#运行终态)三个**：完成 / 失败 / 被取消。**不可逆，且只从一个出口落账**（[§6.6](#66-终态不可逆且只有一个出口)）。

**T1′ 是这一圈里唯一一个不经过模型就结束 Run 的地方。**

#### 这个循环从哪里出去

**「退出」有两个答案，因为有两层循环。**

| | 退出条件 | 出口几个 |
|---|---|---|
| **[Run](#run)** | **落终态**（完成／失败／被取消）。**「完成」的判据是[队列空](#待处理消息队列)**——模型没给动作、队列里也没有待处理的，这件事才算做完 | **一个**（[§6.6](#66-终态不可逆且只有一个出口)） |
| **一次[尝试](#执行尝试)**——真正在转的那个循环 | **落终态 · 停住等 · 被中断** | **三个** |

**「停住等」（T4、T6）是出口，不是在原地反复问。**

> 它的意思是：**这次尝试到此为止，把协程交还，什么都不占**；
> 等外部事件把日志改了，**新的一次尝试**再重新算一遍。

**这条是被 [PF-004「等人不消耗计算资源」](#agent-runtime-的四条不变式)逼出来的**——
反复去问就违反它了，而**一个在等人的 Run 可能一等三天**。
转移表把 T4 写成落回 T4，说的是「**日志没变，重新算一遍还是这个结果**」，
**不是叫你不停地算**。

> **由此，[一次尝试的边界](#57-一次尝试三条路通向重新算一遍)正好就是这个循环的出口**——
> 那一节讲的三条「通向新尝试的路」，对应的就是这里的三个出口。

#### 方程不保证这个循环会停

**`f` 只回答「下一步是什么」，它没有「转够了」这个概念。**
真正让它停的有四样，各管一头：

| 谁 | 管什么 | 管不到什么 |
|---|---|---|
| **三个[终态](#运行终态)** | agent 说完事了，或出了没法继续的岔子 | agent 一直觉得还没完 |
| **[循环守卫 L3](#59-循环守卫四级阶梯)** | **原地打转** | **不打转地一直干新活** |
| **[T1′ 压完还超](#55-想这一步交进闭包拿回装得下的一份)** | 上下文空间耗尽 | 空间够用但钱烧光了 |
| **挂在[落终态之前或调模型之前](#十一个位置是推出来的不是挑出来的)的[拓展件](#拓展件)** | **预算、轮次、时限** | 没人挂的时候，没人管 |

> **最后一行是有意留给用户的。**「转到什么程度算不值得」是**价值判断，不是状态事实**——
> 与 [L3 为什么不进 PF-011 的模型](#哪些收束根本不进-pf-011-的模型)是同一条道理。
> **系统不替租户定这个数，但把位置留好了。**

**所以「一个不打转、一直在干新活的 agent」不会被系统自己停下来。**
**这是模型的真实边界，不是漏洞**——要管，就在那两个位置挂一件。

#### 「被取消」不在这张表里，因为它不是一行

三个终态里，**完成与失败是方程算出来的，被取消不是**。

> **取消是一件随时可能发生的外部事件**，走的是[「外面进来的事」那条路](#511-外面进来的事怎么到-agent-眼前)：
> 往日志里落一条，然后方程读到终态就停。
> **顺序是硬的——[先落日志，再发停止信号](#615-取消先落日志再发信号)。**

**它在任何状态下都可能来**，不从某个尾巴形状推出来，所以**它没有对应的转移行**。

**取消时那个还在外面跑的工具执行**，按
[PF-006「中断不是失败」](../PF-006-tools-and-skills/design.md#67-用户可以中断而中断不是失败)处理：
落一条正常的工具返回消息占位，语义是「这次执行被用户手动中断了」。

> **与[崩溃那一种](#先对账再进方程)分清楚**：崩溃时后台执行算**失败**（系统没了它就没了）；
> 取消时系统还在，是用户主动停，所以算**中断**。

**产品上的要求是「取消之后不再产生新的外部效果」**；某个执行停不停得掉，
是工具那一侧的能力。**停不掉的那些，结果回来照样落进日志**——
日志是[会话](#只引用不拥有的对象)的，不是 Run 的，而它[不会让 Run 复活](#612-终态之后再回来的东西不让-run-复活)。

**被卸载的结果算「齐」**，两条理由：
[`Tools().read_result`](../PF-007-meta-capabilities/design.md#61-tools通向任意非常驻工具)
给了取回全文的通道；而且**卸载不是全卸载——占位里带摘要，很多时候摘要就够用**。
**所以它不是一个「缺了一半」的结果，而是一个完整的、可按需展开的结果。**

### 5.7 一次尝试：三条路通向「重新算一遍」

**崩溃恢复不是一条异常路径，它是常态。**

| 什么发生了 | 日志 | [agent runtime](#agent-runtime) | 上一次尝试是怎么停的 |
|---|---|---|---|
| **系统崩了** | 在 | 没了 | **断的** |
| **等人回话，人回了** | 在 | **可能已经被回收**——[等人不消耗计算资源](#agent-runtime-的四条不变式)（I-7） | **正常停住的** |
| **[构成变了，清单得重算](../PF-004-agent-definition-and-assembly/design.md#67-装配清单的生与失效)** | 在 | [优雅取消](#614-停止有两级)掉，照新清单起一个 | 视情况 |

> **三条路在方程眼里是同一件事**：日志还在，那个协程不在了，**重新算一遍 `f`**。

#### 「停机」不是机器断电，是失去连续性

**产品负责人 2026-09-20 点出的那句话：**

> **停机的本质，未必是单纯的系统停止运行了。**

**判据只有一条：**

> **一个运行时，与它所服务的那个持久的东西，失去了连续性。**

**照这条判据，上面那三行本来就是同一件事**——
进程没了、实例被回收、机器换了一台、[等人的时候 agent runtime 被回收](#agent-runtime-的四条不变式)，
**在方程眼里全都是「agent runtime 不在了」**。

> **所以「停住等」不是一次异常，是一次计划内的停机。**
> [它正是这个循环的三个出口之一](#这个循环从哪里出去)——
> **设计里天天在发生，而不是偶尔才发生的意外。**

#### 三个运行时，停机之后各算什么

**[按命名约定，系统里恰好有三个 runtime](../../ubiquitous_language/conventions.md#runtime-这个词本系统写死了)**——
它们各是一个协程，各能被单独取消，**而停机之后的处置完全不同。
不并排写出来，实现者会把其中一条套到另一个身上：**

| 运行时 | 停机之后 | 为什么 |
|---|---|---|
| **[agent runtime](#agent-runtime)** | **重新算一遍 `f`** | 它求值的是**纯函数**，状态全在[日志](#会话日志)里——**重算一定得到同一个答案**。**它自己不必被复原** |
| **[一次工具执行](../PF-006-tools-and-skills/design.md#612-工具执行的运行时可以被单独控制而它停了就不重来)** | **不重来**，落[失败](../PF-006-tools-and-skills/design.md#55-一次工具执行的收场有六种) | **它可能已经在外面做了事**——**重来就是做第二遍**，而那些效果收不回来 |
| **[一次模型调用](../PF-013-model-profiles-and-invocation/design.md#513-模型请求的运行时可以被单独控制而它停了看首-token)** | **看首 token 出没出来**：之前可以重发，**之后一律不重发** | 首 token 之前它没有外部效果；**之后有**——[那半句话已经在日志里、用户可能已经看见](../PF-009-context-message-types/design.md#69-用户看见了的会话日志里必须有) |

> **第一行「重算」，后两行「不重算」，这条界线只有一个判据：**
> **这个运行时在外面留下了不可逆的东西没有。**
> 留下了就不能当它没发生过——**这是[外部输出不因被运行时调用就变得可逆](../../../agents/roles/engineering-taste.md)那条品味在三个运行时上的同一次落点。**

##### 另外两样常被摆进这张表，但它们不是 runtime

| 被摆进来的 | 为什么不是 | 它停机之后 |
|---|---|---|
| **[Run](#run)** | **没有独立的执行上下文。**它是[若干协程实例的逻辑包络](#执行尝试)——能跨多次尝试，**本身不是其中任何一个** | 不适用。**是它下面那个 agent runtime 停了**，而 Run 照样活着等下一次尝试 |
| **[装配清单](../PF-004-agent-definition-and-assembly/design.md#装配清单)** | **它是数据**，不占用计算资源、不会停 | 不适用。**下一次尝试直接复用**，除非[它已经失效](../PF-004-agent-definition-and-assembly/design.md#67-装配清单的生与失效) |

> **这两样单独列出来，是因为它们最容易被误当成「第四个、第五个运行时」**——
> 而[叫 runtime 的东西必须是一个协程](../../ubiquitous_language/decisions.md#ul-d-3--runtime-与活体--2026-09-20)。
> **它们停机之后没有处置可言，因为它们根本不会停。**

> **三者各自的细则归各自的 topic，本节只并排摆出来。**
> **并排摆本身是有用的**：它让「为什么 run 能重算而工具执行不能」当场看得见，
> **而这个问题在任何一个单独的 topic 里都答不完整。**

#### 先对账，再进方程

**断的那一种，日志的尾巴可能停在正常运行时不会出现的形状上：**

| 断在哪 | 尾巴的样子 | 怎么接 |
|---|---|---|
| **发出了动作，结果没落盘** | 有调用、无结果 | **合成一条「被中断」的结果**补上，照常走 T7 |
| **模型已给完整回复，终态没落** | 有回复、无终态 | **幂等收尾，绝不再调模型** |
| **后台执行没落完成** | 占位还在，工作没了 | 算**失败**——它跑在这个系统里，**系统没了它就没了** |
| **正常停住的那两种** | **卡片已答完 / 结果已齐** | **不必对账**——尾巴本来就是方程认得的形状 |

**对完账，日志的尾巴就回到方程认得的形状，剩下的照常算。**

#### 每一次尝试开始，都要做四件事

| 做什么 | 依据 |
|---|---|
| **对账**（只有断的那一种需要） | 上表 |
| **重算[当下可用性](../PF-006-tools-and-skills/design.md#62-可用性在每次-run-开始前重算)** | PF-006 定的是「每次 run 开始前重算」，**把每一次尝试也算作一次开始**，两者就统一了 |
| **拉一次 [runtime context](../PF-015-session-lifecycle-and-ownership/design.md#runtime-context)** | 会话空闲期间，**生产方推来的变更一概丢弃**（[§5.11](#511-外面进来的事怎么到-agent-眼前)）。所以尝试起来之后**要自己取一次当前快照**，否则那段时间里变过的东西谁也不会告诉它 |
| **追加一条尝试提醒** | [§6.4](#64-每一次尝试开始agent-都要知道) |

**拉到的那一份与日志对不上时，落一条状态类提醒**：
**前值取[会话日志](#会话日志)里最后感知到的那一份，现值取这一次拉到的**，
按 [PF-009 的写法](../PF-009-context-message-types/design.md#64-说状态的写清变化说事的写清发生消息一律追加)写清「从什么变成了什么」。

> **因果链记的是这个会话感知到的变化，不是世界上发生过的每一步。**
> 空闲期间那块数据改过三次还是三十次，**会话只感知到一次：从它上次看见的那个值，到现在这个值**。
> **这不是丢信息**——那三十次里没有任何一次有 agent 在场，**它们从来不曾是这个会话的事实**。

**重算之后动作空间可能与上一次尝试不同**——**那本来就是事实，早知道比撞上去才发现好**。
不必额外告知 agent 差异：它调一个已经没了的能力，
[替换件](../PF-006-tools-and-skills/design.md#替换件)会给它「用不了 + 原因」。

**那条尝试提醒同时是日志里的「尝试开始」记录**，[它是一条 `SystemReminderMessage`](#64-每一次尝试开始agent-都要知道)，
**四样东西一样都不能少：**

| 带什么 | 为什么不能省 |
|---|---|
| **是哪个 Run、第几次尝试** | [尝试的身份就是这两样](#执行尝试)。没有它，重复的外部效果追不到「是哪一次干的」 |
| **什么时候起的** | 追溯的基本要求，也是「这次尝试卡了多久」的唯一依据 |
| **为什么起**（**首次** / **从一次中断接上来** / **等到的东西回来了**） | 区分「正常往下走」和「这是第 N 次重来」。[要让 agent 判断重做的风险](#64-每一次尝试开始agent-都要知道)，靠的就是这一项 |

**一次尝试结束时也应当落一条记录**——成本与失败归因会更准，
栅栏判断也更直接。**但恢复逻辑必须能在它缺失的时候照常工作：**

> **崩溃时来不及写结束记录是常态，不是数据损坏。**
> 一个「要求尝试开始必须配一条结束」的系统，**在真崩溃面前会直接卡死**。

#### 同一个 Run 同一时刻只有一副协程在推它

[只看日志的那张表第 3 行](#只看日志该不该起一个-agent-runtime)分不出「健康地跑着」与「崩了留下的孤儿」，
所以恢复逻辑会起一副新的。**万一旧的那副其实还半死不活地活着，两副就撞上了。**

**兜住它的办法是拿尝试序号当栅栏：**

> **只有序号最大的那次尝试的写入被接受；序号更小的尝试，写什么都被拒。**

**为什么用序号而不是另设一把锁**：序号[本来就要写进日志](#每一次尝试开始都要做四件事)，
**用它不引入日志之外的第二份状态**——而多一份状态就多一处会和日志对不上的地方。

### 5.8 Loop 拓展点

#### 十一个位置，是推出来的不是挑出来的

**位置不是挑几个好用的开出来，是从[状态点](#53-改日志的动作与纯派生的动作)推出来的：**

> **每个状态点有紧前与紧后两条边，每条边就是一个位置。**

[状态点六个](#53-改日志的动作与纯派生的动作)，两条边，**共十二条**；
**只有一条不归本 topic，其余十一条全部开放**：

| 位置 | 看得到什么 | 挂在这儿的典型东西 |
|---|---|---|
| **尝试开始之后** | 对完账的日志、[当下条件](#当下条件) | 恢复之后要不要多提醒一句 |
| **消息落盘之前** | **那条还没落盘的消息**，不论它是谁产生的 | **脱敏、敏感信息识别、提示词注入与攻击检测、把收不下的模态转成收得下的**（见下） |
| **消息落盘之后** | 刚落盘的那条消息 | 按内容分流、补充上下文 |
| **压缩之前** | **要交进[闭包](#55-想这一步交进闭包拿回装得下的一份)的那份日志与模型档案**（**不是「要被压的那一段」**——那在闭包内部） | 指定哪些不许压 |
| **压缩之后** | 刚落下的那条 `CompactionMessage` | 摘要质量兜底。**闭包这一趟没压，这个位置就不触发** |
| **调模型之前** | **请求已经攒好、还没发出去** | 换模型、加一条系统提醒、按预算拦下 |
| **调模型之后** | **带[收场维度](#两个位置带维度)**：完整回复 / 失败 | [循环探测](#59-循环守卫四级阶梯)、失败分档 |
| **执行动作之前** | 这一个动作及其参数 | [放行判断](../PF-008-human-in-the-loop/design.md#52-那个判断函数)、参数改写 |
| **执行动作之后** | **带[范围维度](#两个位置带维度)**：这一个 / 这一批全齐 | [卸载判定](#510-卸载结果落成消息之前的那一关)、结果脱敏 |
| **落终态之前** | 整条日志、这次要落的那个终态 | **否决停下**、打转保护、收尾前的合规检查 |
| **落终态之后** | 已经落下的终态 | 归档、通知、结算 |

**位置没有编号，就叫它站的那个名字。**编号是第二套命名，与
[按位置命名](#按位置命名不按功能命名)那条冲突；而且**位置数会变**——
**一变，编号就全篇错位**。

#### 「消息落盘之前」：每条消息都经过它，不只是输入

**这是十一个里唯一一个不属于某一步的。**别的位置一步经过一次，
**它是每有一条消息要落进[日志](#会话日志)就经过一次**——
不论那条消息是**用户说的**、**模型吐的**，还是**工具交回来的**。

**四件事都发生在这儿，理由完全一样：**

| 要干的事 | 为什么必须在落盘**之前** |
|---|---|
| **脱敏** | [日志只增不改](#会话日志)。**落盘之后再想脱敏，原文已经永久留在那儿了** |
| **敏感信息识别** | 同上。识别得出、却已经写进去了，等于只留下一条「这里有敏感信息」的记录 |
| **提示词注入与攻击检测** | 拦下来的东西**不该进日志**。让它落盘再删，既违反只增不改，又等于承认曾经进过方程的定义域 |
| **把收不下的模态转成收得下的** | **原样的那个块不动**；转换件交出的那几份（别的模态的内容块，外加一段纯文本兜底）**和原块在落盘那一刻一起定下**。落盘之后再转，要么改已经写下的记录，要么另存一份——**两条都违反只增不改** |

> **四件事的共同形状**：**它们要处置的是「落进日志」这个动作本身**，
> 而不是「落进去之后怎么办」。**落盘之后的位置，一个都办不了这件事。**

**它管的是「每一条」，不只是外面进来的那些。**
上面四条理由**对模型吐出来的内容、对工具交回来的结果，一模一样成立**——
把它缩成「输入落盘之前」，**模型生成的内容就没有任何位置可以脱敏了**。

#### 模态转换为什么必须落在这里

**因为它一旦挪到别处，就没有一个说得通的落点：**

| 挪到哪 | 为什么不行 |
|---|---|
| **组装的时候** | 组装是[纯派生的](#53-改日志的动作与纯派生的动作)，[一圈里要跑两次](#55-想这一步交进闭包拿回装得下的一份)。转换若在组装里，**两次组装结果不同，方程当场失效** |
| **调模型之前** | 那时请求**已经攒好、也量过了**。转换之后内容变短，**量的是原图、发的是文本**，压缩判断跟着错 |
| **落盘之后** | 要么改已经写下的记录（违反只增不改），要么另存一份（**同一张图两处登记，迟早分叉**） |

**而落在这里，三个问题一个都不存在**：原始内容块原样进日志（换个收得下的模型还要用它），
转换出来的那几份**在落盘那一刻就和它一起定死了**，后面组装时**按这次的模型收得下什么去取**——
**取哪一份是组装的纯派生选择，不改日志**；取不到任何一份收得下的，就用那段纯文本兜底。

**转换件跑起来报了错，这条消息不落盘**——转换件这一类的[报错策略](#拓展件是可插拔的服务不可用即卸载报错按策略)就是否决，
而这个位置上的否决意味着什么，[见下面那张表](#干预力三档直接用-pf-000-的)。
**宁可这次请求失败、这个 Run 失败，也不让一个说不清读不读得了的块混进日志。**
（**那个键上根本没有可用的转换件**，是另一回事：视作没装，[按 PF-013 照原样落盘](../PF-013-model-profiles-and-invocation/design.md#转换件)。）

**所以位置记在本 topic，那一刻的细节归别处：**

| 这一条 | 归谁 |
|---|---|
| **这个位置存在、它挂的是[拓展件](#拓展件)、走同一套干预力** | **本 topic**——和其余十个一视同仁 |
| **那一刻具体看得到什么、[队列](#待处理消息队列)怎么排、一次取几条** | [PF-014](../PF-014-inbound-intake-and-queueing/README.md) |
| **转换件的契约**（声明能处理哪些模态或文件媒体类型、进什么出什么、转换出来的那几份怎么挂在原块上、同一类的转换件怎么替换） | [PF-013](../PF-013-model-profiles-and-invocation/README.md)——**「模态」这个概念是它定的** |

**统一记在这儿的理由很实在**：租户要配一个脱敏挂件时，
**他不该先搞清楚「这算 loop 里还是 loop 外」**——他只想知道有哪些位置可挂。

**唯一没开的那一条：**

| 没开 | 归谁 | 为什么 |
|---|---|---|
| **尝试开始之前** | [PF-015](../PF-015-session-lifecycle-and-ownership/design.md#九未决项) | 那一刻**还没有这次尝试**，日志也还没被谁认领——**没有「这一次」可供插手**。想干的事（比如「这个 Run 重试太多次了，别再起」）在**尝试开始之后**做得到，落一条终态事实即可 |

**纯派生的动作前后没有位置。**[组装](#53-改日志的动作与纯派生的动作)（连同「量一量」）是纯派生的，
它不是状态点，所以「组装之前」「组装之后」根本不成其为位置——
**不是不给开，是推不出来**。

> **完备性只到这一句为止**：位置清单随状态点清单而定。
> **将来真多出一个状态点，位置跟着多两条**；
> 不会有「漏掉一个位置」这种事，只会有「漏掉一个状态点」。

#### 两个位置带维度

**「调模型之后」和「执行动作之后」各自不止一种情形，挂件要能说明自己管哪一种。**

| 位置 | 维度 | 取值 | 为什么必须分 |
|---|---|---|---|
| **调模型之后** | **收场** | **完整回复** / **失败** | 两种情形下日志尾巴完全不同。一个管打转的挂件面对「请求失败」无话可说，**硬让它跑一遍只会得到一个没有依据的判断** |
| **执行动作之后** | **范围** | **这一个** / **这一批全齐** | 卸载判定看单个结果就够；**「这一批的总量超了预算」只有等齐了才知道**。不分维度，后一种就没地方站 |

> **维度不是又多出来的位置。**它是同一个位置上的**筛选条件**——
> 挂件声明自己管哪一种，不管的那种它根本不被调到。

#### 按位置命名，不按功能命名

**位置的名字说的是「它站在哪」，不是「它干什么」。**

这不是措辞偏好，它有两个实在的后果：

| 后果 | 说明 |
|---|---|
| **同一个位置可以挂多个拓展件** | **落终态之前**同时站着「打转保护」和「没达成目标就别停」，**两件事各干各的**。按功能命名，这两个就得各占一个「拓展点」，而它们明明站在同一处 |
| **位置的数目不随功能增长** | 功能有多少种，取决于用户想干什么，**没有上限**；位置有多少个，取决于状态点，**十一个** |

#### 系统自带的几件，各站在哪

**系统自己带了几件挂件，各站在一个位置上。**

| 挂件 | 站在 | 干预力 | 谁拥有 |
|---|---|---|---|
| **循环探测** | **调模型之后**（收场＝完整回复） | 可改写 · 可否决 | **本 topic**（[§5.9](#59-循环守卫四级阶梯)） |
| **放行判断** | **执行动作之前** | 可否决（**出卡等人用的就是[那个原语](#等人是-loop-的原语)**） | [PF-008](../PF-008-human-in-the-loop/README.md) |
| **卸载判定** | **执行动作之后**（范围＝这一个） | 可改写 | [PF-006](../PF-006-tools-and-skills/README.md) |
| **[模态转换](#模态转换为什么必须落在这里)** | **消息落盘之前** | 可改写 · 可否决（**转不成就不落盘**） | [PF-013](../PF-013-model-profiles-and-invocation/README.md) |
| **重试** | **调模型之后**（收场＝失败） | 可改写 | [PF-013](../PF-013-model-profiles-and-invocation/design.md#512-重试站在一个已经存在的位置上) |

**标题里不写数目，是有意的**：与[位置按它站的名字叫、不编号](#按位置命名不按功能命名)同一个理由——
**数目会变**，写进标题就等于每加一件都要改一次标题。

> **模态转换与重试各自都非有不可：**
> 没有**模态转换**，一张图发给一个收不下图的模型就**只能卡在那儿**——
> 而**这正是同类产品上最常见的那类投诉**；
> 没有**重试**，[开箱状态下一次网络抖动就打断一轮对话](../PF-013-model-profiles-and-invocation/design.md#系统自带一件默认的所以开箱就有重试)。
> **但它们不因此特殊**——同一套位置、同一套干预力，租户想换一件更好的实现，挂上去就是了。

> **注意「调模型之后」这一个位置上现在站着两件**（[循环探测](#59-循环守卫四级阶梯)与重试），
> 而它们**各管一个[收场维度](#两个位置带维度)**：前者管「完整回复」，后者管「失败」。
> **这正是[维度不是第十二个位置](#两个位置带维度)那句话的兑现。**

> **它们是系统自带的，不是外面挂进来的**，但**走的是同一套位置与同一套干预力**。
> **自带的不享受特权**——这一条要紧：若系统自带的能做外来挂件做不到的事，
> 那说明位置的能力没被定清楚，**而下一个要做同样事情的租户就会卡住**。
>
> **「出卡等人」是检验这句话最硬的一处**：放行判断拦下一个动作、让人点头，
> **用的就是任何一件可否决拓展件都能用的[那一个原语](#等人是-loop-的原语)**——
> 租户想自己写一件「这类操作先问法务」的拓展件，**它能做的与放行判断一样多**，只是选项由它自己写。

#### 能做什么，不能做什么

| 能做 | 长什么样 |
|---|---|
| **追加一条** | 往日志里加一条新的（**落终态也是这一种**——终态是一条事实） |
| **决定下一条还没落盘的东西长什么样** | [卸载判定](#510-卸载结果落成消息之前的那一关)把大结果换成占位；[执行动作之前改参数](#改参数先落一条生效参数) |
| **落一张卡片等人** | 一件可否决的拓展件自己写说明与选项，**Run 停下来等人答完**，答复回到这一件手上再下结论（[等人是 loop 的原语](#等人是-loop-的原语)） |

> **第三行不是第三条通路。**卡片是一条落盘的记录，人的答复也是——
> **它照样只靠改日志起作用**，只是这一条改动要等人来写后半截。

| 不能做 | 为什么 |
|---|---|
| **改写已经落盘的** | [条目一旦写下就不再改变](../PF-000-occurrences-and-record-entries/design.md#记录条目)；[一条消息都不能擦除](../PF-010-context-management-and-assembly/design.md#612-记录里的消息一条都不能擦除) |
| **不留痕地改变下一步** | **`f` 当场不纯** |
| **自己指定跳到哪一步** | **转移由[状态转移表](#56-状态转移表)算**，挂件改的是日志 |

**最后一条容易读歪，所以说明白**：L3「优雅结束」看起来像是挂件直接把 Run 结束了，
实际上它做的是**往日志里落一条终态事实**，而方程读到终态就停。
**同一条规矩，没有例外。**

#### 第二条是硬的，因为它护着 `f` 的纯性

**如果挂件能不留痕地改变下一步**，新的一次尝试里重算就会得到不同的结果——
**`f` 当场不纯，整套恢复机制塌掉**。

> **挂件本身不必是纯的，但它的效果必须被记下来。**

**这与调模型完全同构**：模型也不纯，但它的输出被追加进日志了，
所以恢复时不重跑模型，**读日志里那条回复就是了**。

> **同理：新的一次尝试里，已经有结论的挂件不重跑。**它上次做的判断已经在日志里。
> **还在等人的那一件是唯一的例外**：它没有结论可读，所以**以回放的方式重跑到它停下的那一处**——
> 途中它每一次等（等模型、等人）都**按日志里记下的交回**，不真的再做一遍（[等人是 loop 的原语](#等人是-loop-的原语)）。

**这一条挡住一个很自然的误会**：实现者会觉得「挂件是个函数，重跑一遍就行」——
**不行，它可能不纯**。回放之所以不违反这一条，**是因为回放里它碰不到任何没被记下的东西**。

#### 干预力三档，直接用 PF-000 的

**PF-000 说[干预全部发生在「成为条目之前」的那一刻](../PF-000-occurrences-and-record-entries/design.md#53-干预力只长在瞬态这一半上)——
拓展点就是那一刻。**所以干预力不必另立一套：

| 档 | 它能做什么 | **它跑起来报了错，默认怎么办** |
|---|---|---|
| **只观察** | 看，不改 | **不影响**正在发生的事 |
| **可改写** | 追加一条，或决定下一条还没落盘的长什么样 | **不影响**，但要**留一笔「它没跑成」** |
| **可否决** | 拦住那个状态点，不让它发生；**也能落一张卡片，让 Run 停下来等人**（[等人是 loop 的原语](#等人是-loop-的原语)） | **当作否决**（fail-closed），**且这件事本身要可见** |

> **最后一列是每一档的默认策略，不是唯一的办法。**拓展件是可插拔的服务：
> **它不可用，就当它被卸载了**，这一列根本用不上；**它可用却报了错，才按它那一类的策略办**，
> 而这一列是某一类没有另定策略时的兜底（[拓展件是可插拔的服务](#拓展件是可插拔的服务不可用即卸载报错按策略)）。

> **「等人」不是第四档，是可否决那一档本来就有的。**让一件事等到人点头再发生，
> **本身就是在拦它**——拦得住才谈得上等，只观察与可改写那两档都拦不住任何东西。
> **[PF-000 的三档](../PF-000-occurrences-and-record-entries/design.md#53-干预力只长在瞬态这一半上)因此一档不加。**

> **「可否决那一档挂了当否决」出自 [PF-000 §5.3](../PF-000-occurrences-and-record-entries/design.md#53-干预力只长在瞬态这一半上)**，
> 在本 topic 读作**可否决那一档报错时的默认策略**，按类型细化的策略可以把它说得更具体。
> **中间那一档 PF-000 没说，本 topic 推出来的**：改写没发生，事情照常；
> 但不留那一笔，**排查的人看到一条没被卸载的大结果，分不出是判定说不用卸载，还是判定没跑成**。

**「可否决」否决的是它站的那个状态点，而那个状态点未必是「往前走」：**

| 位置 | 否决意味着 |
|---|---|
| **消息落盘之前** | **这条不落盘**，之后按它是谁产生的分三路（[见表下](#消息落盘之前的否决按消息是谁产生的分三路)）；**转换件转不成也走这一条** |
| **压缩之前** | **这一趟不许压**：装得下照常往下走，**装不下就按[压完还超](#压完还超这一层腾不出空间了)处理**——上交给会话，这个 Run 落失败 |
| **调模型之前** | **这次请求不许发** |
| **执行动作之前** | **这个动作不许做** |
| **落终态之前** | **这次不许收束**——**接着转** |

> **最后这一条方向相反，必须写明。**不写，实现者会按「否决＝拦住往前走」去做，
> **而落终态之前最有价值的那类挂件恰恰是「别停，还没干完」**。

**否决只在「之前」的位置上有意义。**否决拦的是它站的那个状态点，
而站在「之后」的时候，**那个状态点已经发生了**——这张表因此恰好是五个「之前」
（[尝试开始之前不开](#十一个位置是推出来的不是挑出来的)）。可否决那一档站在「之后」，
**它多出来的只有等人**：[循环守卫 L4](#59-循环守卫四级阶梯) 站在调模型之后，就是这样用的。

**执行动作之后，明确不给否决。**那一批动作已经对外发生了，**「拦住它」无从谈起**。
别家的 hook 在这个位置上常带一个「停住」（Claude Code 的 `PostToolBatch` 阻断、两家通用的 `continue:false`），
**到了这里，它只能译成追加一条终态事实：被取消，原因指向那件拓展件**——
挂件[不能自己指定跳到哪一步](#能做什么不能做什么)，**它能做的就是落一条终态**，而这件事既不是完成、也不是 agent 失败，
是**有人（通过这件拓展件）叫停了这次运行**。**别的位置上的「停住」照同一个译法。**
它走的仍是[取消那条路](#615-取消先落日志再发信号)：**先落一条取消请求，发起方写那件拓展件，再落终态**——
[I-16](#617-run-这一层的七条不变式) 照样成立。

#### 拓展件是可插拔的服务：不可用即卸载，报错按策略

**每一件拓展件都是装了才有的、可插拔的服务**——系统自带的那几件也一样。
所以它「出了问题」要先分清是哪一种，**两种的后果完全不同**：

| 情形 | 是什么 | 怎么办 |
|---|---|---|
| **不可用** | 它依赖的服务用不了、它自己起不来 | **视作已卸载**：这个位置这一次**没有它**，瀑布里跳过它；**日志里看得见「这一件此刻不在」**。它依赖的东西回来了，它就又在了 |
| **可用却报错** | 它在，跑起来出了错 | **按它那一类拓展件的处置策略办**。策略由拓展点的协议按类型给出；某一类没另定的，用[三档各自的默认](#干预力三档直接用-pf-000-的)（可否决一档默认当否决） |

**本 topic 只定三件事**：这两分；**每一类拓展件都必须有一条报错时的处置策略**；**策略实际怎么处置了这一次，必须可见**。
各类具体用哪条策略、协议长什么样，**归拓展点协议（规格阶段设计）**。

> **「停在等人」既不是不可用、也不是报错。**一件拓展件出了卡、等了三天，是在按规矩等；
> 当它是出了问题，就等于给卡片设了超时、到点替人作答（[PF-008 §6.1](../PF-008-human-in-the-loop/design.md#61-永远等着系统不替人作答)）。

**代价要写在明面上**：一件把关用的拓展件（比如注入检测）依赖的服务挂了，**这一关这一次就没了**——
因为它被视作卸载，而不是被视作否决。**所以「此刻不在」必须看得见**；
要不要让某件拓展件「不在就不许跑」，**不是本 topic 定的事，正文未述**。

> **为什么这样分**：装与卸是一件插件的生命周期，**「它此刻在不在」是事实，不是一次判断的结论**——
> 把「不在」读成「否决了」，就是替一件根本没跑的东西编了一个结论。
> **只有真跑了、在跑的过程里出了错**，才谈得上「这一次它的结论该怎么算」，而那取决于它是哪一类东西。

#### 消息落盘之前的否决，按消息是谁产生的分三路

| 被否的那条是 | 之后 | 为什么 |
|---|---|---|
| **外面进来的**（用户说的、外面捎来的） | **拒绝这次请求，发送方被告知**——[用户自己发的那条被拦，必须让他看得出来](../PF-014-inbound-intake-and-queueing/design.md#否决了也不许静默) | 请求失败，**会话里什么都没多**；他改了可以再发 |
| **模型吐的回复** | **当作这次模型调用失败了**：收场＝失败，交给[调模型之后（收场＝失败）](#两个位置带维度)上的重试挂件，**退避再来**；[试尽了](../PF-013-model-profiles-and-invocation/design.md#什么时候算试尽)，**这个 Run 落失败**，原因指向那件拓展件 | 那份回复没落盘，日志里这次调用就是**没拿到回复**——与一次真的失败**尾巴一模一样**。**这不是新机制**：否决被翻译成一次「调模型失败」，走的是已有的那条重试 |
| **工具交回的结果** | **这个 Run 落失败**，原因指向那件拓展件 | **没有可退的路**：再跑一次工具，外面的事可能又做一遍；落一个替身，又得凭空给它认一种收场 |

> **没有第四路，尤其没有「落一条替身」这条路。**本系统**没有补偿机制**——
> **宁可这次请求失败、这个 Run 失败，也不留一条说不清的记录**；唯一多给一次机会的是模型回复，因为重来**不对外做任何事**。

#### 没有「放宽」这一档

**拓展件只能收紧，不能放宽。**具体说：**放行判断算出来是「问一下」，没有任何一件拓展件能把它改成放行**；
它能做的是否决（更严），或者自己再出一张卡（更多人把关）。

> **想让某类动作不再问人，去把那项[执行权限](../PF-007-meta-capabilities/design.md#56-一次放行判断走四步)配成「自动」。**

**理由是它会变成第二条授权通道：**
放行这件事已经有一条完整的路——[权限设置、授权表达、会话运行模式，按次序算](../PF-007-meta-capabilities/design.md#56-一次放行判断走四步)——
**谁能改权限有资格约束，人给的授权有作用域、会落成可审计的一笔**。
一件拓展件若能把「问一下」翻成放行，**它就绕开了这整条路**：装它的人未必有权改那份权限，
翻过去的那一下也不落成任何一笔授权。**放行的权威只该有一个出处。**

**从别家搬来的 hook 若带着「允许」**（Claude Code 的 `allow`、两家 `PermissionRequest` 上的 allow），
**在这里只能算「无意见」**——它不拦，也不放；**导入时要明示给装它的人看**，
免得他以为那件 hook 还在替他放行。

#### 改参数，先落一条生效参数

**可改写的拓展件在执行动作之前改了参数，执行之前必须先落一条「生效参数」**——
模型那条回复里的原参数[一个字不动](#能做什么不能做什么)，执行照生效参数做，**两份都在日志里**。

不落这一条，**日志里写的是一个动作、实际跑的是另一个**：重算读到的是原参数，审计查到的是原参数，
**而且没有任何东西会报错**。这正是[不留痕地改变下一步](#第二条是硬的因为它护着-f-的纯性)。

**还有一条随之而来**：[放行判断](../PF-008-human-in-the-loop/design.md#52-那个判断函数)判的、人在卡片上点头的、实际执行的，
**必须是同一份参数**——[人签的是卡片上那段文字](../PF-008-human-in-the-loop/design.md#它同时是撰稿人这一点很要紧)，
放行之后参数再被改一次，那一签就签在了别的东西上。**同一个位置上几件怎么排才守得住这一条，归[拓展件那一侧](../PF-002-assets-settings-and-permissions/design.md#loop-extension)定；本 topic 只定这条性质。**

#### 改了日志就重新组装，同一位置同一次经过只跑一轮

**「调模型之前」的挂件改了日志，那个攒好的请求就过期了**——日志变了，
[组装](#53-改日志的动作与纯派生的动作)出来的东西当然不一样。所以：

> **「调模型之前」有挂件改了日志，就重新组装一次；但不再回到这个位置。**

**这与[压缩那一圈](#55-想这一步交进闭包拿回装得下的一份)同构**：压完再量一次，
还超就上交，**不是再压一轮**。同一个道理——

> **同一个位置，同一次经过只跑一轮。**

不定这条，那儿一个爱改日志的挂件就能把自己无限触发下去，**而 loop 永远发不出请求**。

#### 三种形态：两种装得进，一种拆两半

**把五家的做法摊平看，挂件与 loop 的接法只有三种形状：**

| 形态 | 谁这么做 | 长什么样 | 本系统 |
|---|---|---|---|
| **点式** | Claude Code 的 hooks · Codex · Grok | 到了位置调一次，拿一个结论 | **采用** |
| **瀑布式** | DSH | 同一位置上挂的若干件**按声明的顺序依次过**，前一件的输出是后一件的输入 | **采用**——它正是「同一位置挂多个」的求值办法。**不可用的那一件视作不在，瀑布跳过它**；报错的按它那一类的策略，**策略判成否决，瀑布到此为止** |
| **环绕式** | LangChain 的 `wrap_model_call` · DSH 的 `around dispatch` | 挂件拿到「继续往下走」这个能力，**自己决定调几次** | **拆两半**，见下 |

**环绕式拆两半，判据是「中间那几次经不经过日志」：**

| 哪一半 | 例子 | 处置 |
|---|---|---|
| **挂件给一个结论，由 loop 去执行** | DSH 的 `agent/request-error` 返回一个「重试」的动作，**loop 照办** | **装得进**。它本质就是点式——落在**调模型之后**（收场＝失败） |
| **挂件自己循环调下一层** | LangChain 的 wrap 里 `for attempt in range(3): handler(request)` | **装不进。**中间那两次调用**不经过日志**，[重算时拿不回同一个下一步](#第二条是硬的因为它护着-f-的纯性)——**`f` 当场不纯** |

> **拆的是形态，不是功能。**「失败了自动重试三次」这件事本系统做得到，
> 只是**每一次重试都得在日志里留一条**，而不是藏在一个挂件肚子里。
> **代价是日志更长，换来的是这次 Run 换一个 agent runtime 也能接着跑。**

**Claude Code 与 Codex 的 hooks 是另一种挂法：同一位置的几件并行跑、各自看原始输入、最后按优先级折成一个结论。**
本系统不改用它——**瀑布让后一件看得见前一件改了什么**，而[放行之后参数不许再变](#改参数先落一条生效参数)这类性质
只有在「谁先谁后」说得清的时候才守得住。**别家的一组 hook 搬进来，要么排成瀑布里的先后几件，要么折成一件**；
选哪种、折叠规则怎么定，是搬运那一侧的事，**本 topic 只要求搬进来之后仍是瀑布**。

#### 挂件自己花的钱，算它插手的那个 Run

**挂件可以自己调一次模型**——比如一个「这次任务到底算不算干完了」的判断，
本身就得让模型读一遍日志再说。

> **那笔钱算进它插手的那个 Run。**

依据是 [Run 是成本的归属单位](#run-是三样东西的归属单位)那条的检验句——
**「这次失败的任务花了多少钱」**。判断是为这次任务做的，**不算进去，那个数就不全**。

> **不属于任何 Run 的调用是另一回事**，归会话那一级，见 [§4](#run-是三样东西的归属单位)。

#### 等人是 loop 的原语

**拓展件注册进来之后，就是 [agent runtime](#agent-runtime) 这副协程里的一段执行。**
而协程本来就有一种「停下来，等外面给个应答」的办法——主流程**等模型、等工具、等人**，用的都是它。
**拓展件用的是同一种，不是另一套机制**：一件可否决的拓展件要问人，就落一张卡片，然后在这儿等。

**「等」的是谁，要说准：**

| agent runtime 在等 | 那一头是什么 | Run 里记着的 |
|---|---|---|
| **等模型** | 一次模型调用 | 这次调用发出去了、回复还没落 |
| **等工具** | **一次有自己独立 runtime 的[工具执行](../PF-006-tools-and-skills/design.md#65-工具执行有自己的运行时绑定在-session-上)**——`Ask()` 也是其中之一，它进了等待态，[那是它自己的等待态](../PF-008-human-in-the-loop/design.md#等待态的两个维度) | **agent runtime 在等哪一次执行**（调用已落盘、结果还没落） |
| **等人** | 一张[决策卡片](../PF-008-human-in-the-loop/design.md#决策卡片) | 那张卡片悬着、没答完 |

> **agent runtime 等工具，是这副协程阻塞在那一次执行的结果上；那次执行自己在不在等、等什么，是它自己的事。**
> 两件事挂在两个生命周期上，**不合并**。协程被回收、重建之后，**读 Run 就知道自己上次停在等哪一次执行**，接着等——
> **那次执行本身不受回收影响**（[§6.13](#613-取消跟着宿主走)）。
> 拓展件要问人，借的是 [PF-008 两个维度里 run 的那一列](../PF-008-human-in-the-loop/design.md#等待态的两个维度)；
> 等多久也和任何一张卡片一样：[没有上限，系统不替人作答](../PF-008-human-in-the-loop/design.md#61-永远等着系统不替人作答)。

##### 协程在的时候：挂起，什么都不占

等的那一刻，这段执行挂起，**不轮询、不占资源**，人答了再接着跑——[I-7](#agent-runtime-的四条不变式) 照旧成立。

##### 协程不在了：靠日志，不靠记忆

一个 Run 可能一等三天，协程早被收回了——[那是一次计划内的停机](#停机不是机器断电是失去连续性)。
**停在半路的那段执行保存不下来**，所以等待不靠它，**靠日志里的两样东西**：

| 日志里的 | 它说明了什么 |
|---|---|
| **那张卡片** | **哪一件拓展件、在哪个位置、为哪个动作**出的卡——悬着没答，就是**还在等**。[等待本来就要是一条显式的记录](#等待必须是一条显式的记录)，**卡片就是它，不另造** |
| **人的答复** | 答在那张卡片上的那一笔 |

**新的一次尝试读日志，照下面走：**

| 读到 | 怎么走 |
|---|---|
| **卡片悬着、没答完** | 停在等人（[T4](#56-状态转移表)），什么都不做 |
| **这一批答完了** | 回到**出卡的那个位置、那一件**，**以回放的方式重跑到它停下的那一处**：途中它的每一次等都**按日志交回**；走到出卡那一处，**拿到的是记下的答复，不再出卡**；然后接着往下判 |
| **同一位置上已经有结论的件** | **不重跑**，[读它的结论](#第二条是硬的因为它护着-f-的纯性) |

> **回放不花第二遍钱、不出第二张卡、不再问第二遍模型**——
> 它途中碰到的每一次等，日志里都已经有答案。**这就是为什么等待前的一切效果都必须记下**（[§6.10](#610-能干预的拓展件必须留下结论)）。

##### 写拓展件的人要守的一条

> **等之前记在自己内存里的东西，等回来就没了。**
> 要跨过一次等待带过去的，**只能是经那一种「等」拿到、已经落进日志的东西**。

不守这一条，回放时它算出来的结论就可能与第一次不同——
**`f` 当场不纯**，正是 [§6.9](#69-拓展件只能靠改日志起作用) 要挡的。**这一条必须写进拓展件的作者须知**，
它是拓展件作者唯一要额外守的约束。

##### 一批动作先全部判完，再执行任何一个

[T3](#56-状态转移表) 那一批动作，**每个动作各自并行地过一遍执行动作之前那一串拓展件**：
谁走到要问人，谁就停在那儿；**每个动作要么已有结论、要么停在等人，这个 Run 才进入等人**，
这一轮的卡片[成批落进池子](../PF-008-human-in-the-loop/design.md#53-一批卡片与答完是什么意思)。

| 必须这样 | 不这样会怎样 |
|---|---|
| **并行地判** | 一个一个判，第一个停下来等人，后面的连判都还没判——**卡片只能一张一张来**，人答完一张才看得见下一张 |
| **被放行的也等这一批全判完才执行** | 一批里有的先做了、有的还在等人，**agent 下一步看到的是一个做了一半的现场** |

**答完之后，回放到停下的那一件接着判；它后面的件还可能再出卡**——
所以**人可能看到同一批动作的第二轮卡片**。这是瀑布的直接后果：
后一件要看前一件的结论，**前一件没下结论之前，它无从问起**。

##### agent runtime 被回收时

**没了的是正在跑的那几段拓展件执行**；卡片和它们的记录**留在日志与池子里**，
下一次尝试照上面那张表接着等。

> **这与取消这个 Run 是两回事。**Run 被取消，悬着的卡片随之作废（[flows §5.3](flows.md#53-被取消不在状态转移表里因为它不是一行)）；
> agent runtime 被回收，**Run 还在等，卡片还在**（[§6.13](#613-取消跟着宿主走)）。

##### 两个地方等不了

| 位置 | 为什么 |
|---|---|
| **消息落盘之前** | 那条消息**还没进日志**——协程一没，它也就没了，**回放无从回起**；而且[那一刻看不到有没有 Run 在跑](../PF-014-inbound-intake-and-queueing/design.md#56-消息落盘之前那一刻看得到什么)，**没有一个 Run 可以停下来等**。这里拿不准的，**只能否决**（这条不落盘，[按它是谁产生的分三路](#消息落盘之前的否决按消息是谁产生的分三路)） |
| **落终态之后** | Run 已经收束，[不会被叫醒](#612-终态之后再回来的东西不让-run-复活)，**没有东西可停** |

### 5.9 循环守卫：四级阶梯

**这是本 topic 自己拥有的那件[拓展件](#拓展件)**，站在
[调模型之后](#十一个位置是推出来的不是挑出来的)（收场＝完整回复）。
四级**都只通过改日志来起作用**：

| 级 | 做什么 | 对方程做了什么 | 干预力 |
|---|---|---|---|
| **L0** | 只记一笔（**永不可关的地板**） | 不转移 | 只观察 |
| **L1 / L2** | 往日志里**写一条干预消息** | 落到 T1，agent 带着它继续想 | 可改写 |
| **L3** | **优雅结束** | 落终态**失败**，原因写明是原地打转 | 可否决 |
| **L4** | **出一张卡片问人** | 落到 T4——**复用[等人](../PF-008-human-in-the-loop/design.md#决策卡片)那条路，用的就是[那个原语](#等人是-loop-的原语)，不另造** | 可否决 |

> **这四行正是[把它做成挂件而不是四行转移的理由](#循环探测的四种结局全落在已有的行上)**：
> **每一级的结论，都落在[转移表](#56-状态转移表)里已经有的那个尾巴形状上。**
> **它自己不在那张表里**——跑完它，`f` 的取值不变；
> 变的是**它往日志里落的那一条**，而那一条把尾巴变成了另一种已有的形状。

**阶梯走到第几级，是从日志里数出来的**，不另存计数器。所以：

> **一次崩溃之后，阶梯会自动复现崩溃前的循环史。**
> 靠反复崩溃来洗白打转记录，这条路是堵死的。

**L3 落的是「失败」，不新增终态。**终态越少越好——为什么失败，本来就有地方写。

**L4 是我们比前身走得远的一处**：那边它是个关着的口子，
而我们[已经有决策池了](../PF-008-human-in-the-loop/design.md#决策池)，
直接复用——**比起直接掐掉一个跑了很久的任务，让人给个方向要友善得多**。

### 5.10 卸载：结果落成消息之前的那一关

[卸载这件事是什么](../PF-006-tools-and-skills/design.md#610-结果太大时卸载而卸载是第三个维度)
归 PF-006，**本节只定它在方程里站在哪一步**——它是一件挂在
[执行动作之后](#十一个位置是推出来的不是挑出来的)（范围＝这一个）的[拓展件](#拓展件)。

```text
【做】工具返回 ──→ ◆ 卸载判定
         ├─ 工具自己声明了要卸载 ──→ 用它给的摘要做占位
         ├─ 没声明，但这一条超了限额 ──→ 首尾保留的机械截断
         └─ 都不是 ──────────────────→ 原样
                        ↓
                  落进日志（改日志）
                        ↓
【想】组装 ──→ 量整体 ──→ 超预算才压缩
```

**两个判据，两个时机，别混成一件事：**

| | 看的是什么 | 什么时候 | 碰谁 |
|---|---|---|---|
| **卸载** | **单条**消息有多大 | 工具结果**落成消息时** | 这一条新结果 |
| **压缩** | **整体**超没超预算 | 组装并**量完之后** | 前面的历史 |

**压缩救不了单条超限。**压缩干的是把前面的历史收成摘要，
而这条新结果是**当下正要用的东西**——把它压掉等于这次调用白跑。
所以它必须在落进消息的那一刻就处理完。

**落进日志这一下是状态点**，而**它追加的就是占位那一条**——
**原始结果从头到尾没进过[会话日志](#会话日志)**。

> 所以新的一次尝试里从日志读到的**本来就是占位**，不存在「把大结果重新塞回去」这回事。
> **这不是一次替换，是一开始就只写了这一条。**

它**不在「想」那一圈里**（§5.5），所以那句「这一圈真正的状态点只有压缩一个」仍然成立。

#### agent 取回全文：往后加两条，不是换回去

占位让 agent 知道**自己看到的是完整结果的一部分**。它要是觉得需要完整的，
**自己去调 [`Tools()`](../PF-007-meta-capabilities/design.md#61-tools通向任意非常驻工具)**——
而那一次取回，在日志里的形状是：

```text
… 占位 ToolMessage（一直在，不动它）
   ↓
 + 一条 AssistantMessage（agent 发起的那次 tool call）
 + 一条新的 ToolMessage（取回来的原始结果）
```

**两条新消息，追加在后面。占位那条纹丝不动。**

**由此掉出三件事：**

- **取回来的那份未必完整**——[允许分页读取](../PF-007-meta-capabilities/design.md#61-tools通向任意非常驻工具)，
  一次取一段。所以「取回全文」不是一个原子动作，**可能要来回好几趟**。
- **取回是要花钱的**：每来回一趟，上下文里就多两条消息。
- **所以[「卸载不是全卸载、占位里要留够用的那部分」](../PF-006-tools-and-skills/design.md#卸载)
  这条裁决的价值在这里兑现**——占位够用，就省下整趟来回。
  **只留一个地址的占位，等于把每一次大结果都变成一次额外往返。**

### 5.11 外面进来的事，怎么到 agent 眼前

**有些事不是 agent 做出来的，但它必须知道。它们全都以消息的身份进[队列](#待处理消息队列)：**

| 进来的是什么 | 在队列里是哪一种消息 |
|---|---|
| **用户又说了一句** | `UserMessage` |
| **一次工具执行交回结果** | `ToolMessage`，填在那次调用的位置上 |
| **工具转后台** | 那次调用的位置先落一条**占位** `ToolMessage`（[PF-006 §6.6](../PF-006-tools-and-skills/design.md#66-前台后台-与-等待态是两个维度)） |
| **后台执行完成回传** | **`SystemReminderMessage`**——**那次调用的 `ToolMessage` 位置已经被占位填掉了**，结果回来时**没有它的位置**，只能以提醒的身份进来 |
| **[runtime context](../PF-015-session-lifecycle-and-ownership/design.md#runtime-context) 的某一块被它的生产方改了**，**而此刻[这个 Run 还没闭合](#run)** | `SystemReminderMessage`。组织的、账号的，以及将来会有的其他[视角](../PF-007-meta-capabilities/design.md#612-cordis通向系统自身的装配定义完整本版不实现)——**agent 脚下的地变了** |

> **最后一行那个限定要紧，而且它只管这一类。**
> **生产方推来的 runtime context 变更，在 Run 已经闭合（会话空闲）的时候一律丢弃**——
> **不进队列、不落日志、不成为[记录条目](../PF-000-occurrences-and-record-entries/design.md#记录条目)**。
> 那类提醒[说的是「现在什么样」](../PF-009-context-message-types/design.md#54-提醒说的是现在什么样还是刚才发生了什么)，
> 而**下一次尝试起来时 agent runtime 自己拉一次，拿到的就是当前那一份**（[§5.7 的第三件事](#每一次尝试开始都要做四件事)）。
> **不加这个限定**，组织超管改一次设置，**所有空闲会话各醒一次、各调一次模型**。
> 理由与半径见 [PF-014 §6.10](../PF-014-inbound-intake-and-queueing/design.md#610-注入的上下文变了没有运行在跑时什么都不做)。

> **⚠️ 丢弃只对「推」这一路、且只对 runtime context 的生产方成立。**
> **后台执行完成回传、用户又说了一句、外面送进来的消息、到点了——一律照 [PF-014](../PF-014-inbound-intake-and-queueing/README.md) 受理**，
> **照样能让[队列](#待处理消息队列)从空变成非空、照样开下一个 Run**。
> **两类东西不同**：前者描述「**现在什么样**」，重算即得；后者是「**发生了一件事**」，丢了就没了。

> **[控制指令](../PF-014-inbound-intake-and-queueing/design.md#控制指令)（取消、强停、插队）不在这张表里，但它们同样从外面进来。**
> 差别是它们**是处置不是内容**：**不进队列、即时生效**，
> 各自动的是[哪一层的出口](#这个循环从哪里出去)见下表。

| 控制指令 | 它动什么 |
|---|---|
| **取消 · 强制停止** | **运行的出口**——[落终态「被取消」](#被取消不在这张表里因为它不是一行)。[先落日志再发信号；强停的终结条目由会话这一侧写](#615-取消先落日志再发信号) |
| **[插队](../PF-014-inbound-intake-and-queueing/design.md#插队)** | **一次尝试的出口**——中断当前这一步、解除各种等待态，**运行不落终态**；那句话[排到队首](#先到先处理只有一个例外) |
| **把一次工具执行切到后台 · 中断它** | **一次尝试的出口**——那一条以占位算齐，[可能凑齐了这一批](#56-状态转移表) |

> **受理面、谁能发、怎么排，全归 [PF-014](../PF-014-inbound-intake-and-queueing/README.md)。**
> **本 topic 只说它们各自动的是哪个出口**——而那三行**一个新转移都没有**。

> **[卸载](#510-卸载结果落成消息之前的那一关)不在这张表里。**
> 那不是「外面发生了什么」，是 Agent Loop 解析工具返回值之后自己做的一个动作。

**落点统一：收进日志就是进队列**——[两者是同一件事](#待处理消息队列)，
队列是日志里「还没被消费过」的那一段。**loop 取到它时，agent 就看见了。**

**其中做成 [`SystemReminderMessage`](../PF-009-context-message-types/design.md#systemremindermessage) 的那些**，
还要遵守**[说状态的写清变化、说事的写清发生](../PF-009-context-message-types/design.md#54-提醒说的是现在什么样还是刚才发生了什么)**——
后台回传写的是**事**；注入的上下文变动写的是**状态**，
**所以那一条要带上「从什么变成了什么」**。

**两类在日志里都是追加，[消息之间没有取代](../PF-009-context-message-types/design.md#64-说状态的写清变化说事的写清发生消息一律追加)**，
组装时也不按「同一处只取最新」再筛一道。
**不写清变化**，上下文变过三次，读的人就只看到三份各说各话的当前值，
[而分不出哪条在前](../PF-009-context-message-types/design.md#54-提醒说的是现在什么样还是刚才发生了什么)。

#### 它们必须先落进日志，这是被方程逼出来的

不能把它们攒在内存队列里等组装去取——**组装是纯派生的**（§5.3）。

> 一旦组装要「消费」队列，它就成了改状态的动作。

而 §5.5 那一圈**要组装两次**：第一次量出超了，压完再组装一次。
队列被第一次取空，第二次就拼不出同样的东西——**两次组装结果不同，方程当场失效**。

再加上 §6.1「日志先于可见」：攒在内存里的东西，**一次重启就凭空消失**。

所以：**收进来是改日志的动作，组装只负责把日志里已有的拼出来。**

> **[PF-010 从另一头写了同一条](../PF-010-context-management-and-assembly/design.md#要求四先落盘再组装)**：
> 「事件不许攒在内存里」管**写进来**，「组装不许在落盘之前开始」管**读出去**。
> **两句合起来才是完整的。**

#### 什么时候到，与 loop 走到哪一步无关

它们随时可能到达，但 agent **只在 loop 取到它时才看见**。中间这段间隔是机制的自然结果，
不是缺陷——**[Run 在等人的时候也照收不误](../PF-008-human-in-the-loop/design.md#62-等待期间照常收排队等着解除时一起看到)**，
解除阻塞之后一起看到。

> **这段间隔正是「排队」与「插队」的全部差别。**排队等 loop 自己走到取消息那一步；
> **插队把这段间隔压到最短**——中断当前这一步、解除各种等待态，让 loop 尽快走到那里。
> **它插的是时间，不是别人的位置。**

### 5.12 Run 的终态与非常态的终局，是两条线

**这是本 topic 最容易被读错、也最要紧的一节。**

**非常态怎么分层处置，整块归 [PF-011](../PF-011-off-nominal-handling/README.md)**——
判据是[「缺的那样东西在谁手上」](../PF-011-off-nominal-handling/design.md#56-了结得了吗看缺的那样东西在谁手上)，
**那边管六层**。**本 topic 不重定它，只说清一件事：**

```text
Run 的生命周期：  触发 ──→ 在跑 ──→ 失败（终态，到此为止）
                                      ↑
非常态的阶梯：  agent 的一步 ──→ 运行 ──→ 会话 ──→ 租户 ──→ 终局
                                      │
                              Run 在这里落了终态，
                              而那件非常态还在往外交
```

**三条依据：**

| # | 依据 |
|---|---|
| **1** | [落终局的是那件非常态，不是承接它的那一层](../PF-011-off-nominal-handling/design.md#终局)。**同一条道理在运行这一层也成立** |
| **2** | 会话那一层[能做的是「重算可用性让**下次运行**换个动作空间」](../PF-011-off-nominal-handling/design.md#54-各层的四要素)——**那是下一个 Run 的事，救不活这一个** |
| **3** | [上交即打断](../PF-011-off-nominal-handling/design.md#62-上交即打断)：运行层交出去就停住，**而 Run 的主路径（触发 → 备好 agent runtime → 一步步走 → 收束）确定走不完了** |

**不写明会怎样**：实现者会写出「Run 失败了，处置也就结束了」——
**于是会话层与租户层的处置永远不会发生**，而它们本来可能有办法。

**两条条目，不是一条：**

| 条目 | 说的是 | 归谁的规矩 |
|---|---|---|
| **上交条目** | 这件非常态在运行这一层的收场与原因 | [PF-011 §5.8](../PF-011-off-nominal-handling/design.md#58-上交交的是什么) |
| **终态条目** | 这个 Run 的结局 | [§6.6](#66-终态不可逆且只有一个出口) |

> **它们是两件事，不是[一件事产出多条](../PF-000-occurrences-and-record-entries/design.md#54-一件事什么时候产出不止一条条目)。**

#### 哪些收束根本不进 PF-011 的模型

**这张表挡的是另一个方向的误读**：以为 Run 只要不是「完成」，就得走一遍那条阶梯。

| Run 这样收束 | 是非常态吗 | 为什么 |
|---|---|---|
| **正常做完** | 否 | 主路径走完了 |
| **用户取消** | **否** | [中断不是失败](../PF-006-tools-and-skills/design.md#67-用户可以中断而中断不是失败)，那是用户行使的一条正常路 |
| **循环守卫 L3 结束** | **否** | 见下 |
| **上交给会话之后** | **是** | 那件非常态还在阶梯上往外走 |

**L3 那一行是关键，而且它不显然：**

> **agent 原地打转时，没有哪一层偏离了[主路径](../PF-011-off-nominal-handling/design.md#主路径)。**
> agent 的一步每一步都完整走完（想 → 动作 → 看结果），运行也正在「一步步走」。
> **「转到什么程度算不值得」是一个价值判断，不是一个状态事实**——
> 而 PF-011 处置的是状态事实。

**所以 L3 不是「没办法了往上交」，是运行这一层主动收束。**
这也解释了为什么它落「失败」而不是一路上交到租户：
**上交给会话和租户，它们手上也没有「一条能走通的路」**。

### 5.13 Run 拥有什么：归属的判据

**判据只有一句，而且它就是[「重算一定得到同一个答案」](#52-会话日志是唯一的真相来源)的另一面：**

> **凡是能被「日志还在、重算一遍就有」覆盖的，不必挂在 Run 上——丢了可以算回来。**
> **凡是覆盖不了的，必须挂在 Run 上——丢了就永远丢了。**

**覆盖不了的恰好两类：**

| 哪一类 | 为什么算不回来 |
|---|---|
| **已经对外发生过的** | 重算只算得出「本该发生什么」，**算不出「实际发生过什么」** |
| **带时间与主体的治理事实**（谁、什么时候、为什么） | `f` 是日志的函数，**它推不出人的意图** |

| 东西 | 归谁 | 为什么 |
|---|---|---|
| **结果**（产出、对人的答复、这一次的结论） | **Run** | 要长期成立、要被引用、要当作下一段工作的输入 |
| **失败**（终态原因、错误摘要、发生在哪一步） | **Run** | 协程死了它的错误信息就没了，**而「这段工作失败过」必须长期可解释** |
| **被取消**（谁取消、何时、什么原因、是不是强制） | **Run** | 人的意图，`f` 推不出来；且**必须跨停机成立**（[§6.15](#615-取消先落日志再发信号)） |
| **等待**（在等什么、从什么时候开始等） | **Run** | 见下 |
| **承接范围**（吃了哪些输入） | **Run** | [队列那道减法的减数](#待处理消息队列) |
| **成本** | **Run 汇总，按[尝试](#执行尝试)记明细** | 见下 |
| **外部效果的记录** | **Run + 尝试序号** | [§5.14](#514-外部效果的记录追溯与幂等是同一条记录上的两个字段) |
| 内存态、调用栈、挂到哪一步了 | **那副协程** | `f` 是纯的、日志还在 ⇒ **完全可以重算** |
| [队列](#待处理消息队列)的内存副本 | **那副协程** | 它是日志投影的一份缓存 |
| 取消信号的接收端 | **那副协程** | 那是**传达机制**，不是事实。事实那一份在 Run 上 |
| 这次尝试占着的连接与句柄 | **那副协程** | 资源，天然随协程消亡 |

#### 等待必须是一条显式的记录

**有一个很诱人、但会把整套机制拧死的说法**：`f` 是纯的，给同一份日志它会**再次**算出「我要等 X」，所以不必记。

**它制造了一个死循环：**

> 要知道该不该起一副协程，先得知道这个 Run 是不是在等；
> 要知道在不在等，就得算一遍 `f`；要算 `f`，就得先起一副协程。
> **——要起协程才能知道该不该起协程。**

而且它直接违反[等人不消耗计算资源](#agent-runtime-的四条不变式)：
每判断一次就起一副协程算一遍，等待期间就不可能真的零占用。

**好在这条记录本来就有，不必另造：**

| 在等什么 | 那条记录是 |
|---|---|
| **等人** | [PF-008 的决策卡片](../PF-008-human-in-the-loop/design.md#决策卡片)——它落盘、未答完，**「在等谁、等什么」全在上面** |
| **等一次前台工具执行** | [PF-006 那次执行的账](../PF-006-tools-and-skills/design.md#54-返回值两种写法一种模型)——调用已落盘、结果还没落 |
| **等转到后台的那一次** | 那条[占位 `ToolMessage`](#510-卸载结果落成消息之前的那一关)，**它一直悬着**（[§6.11](#611-悬着的东西不许被压掉)） |

> **所以这一条不新增任何条目，它只是点破：那几条记录本来就在承担「这个 Run 在等」这件事。**
> **[「悬着的东西」本来就在方程的定义域里](#方程从日志里读什么)**，这一节说的是同一批东西。

#### 成本两层，缺哪一层都会算错

**成本重算不出来**——重算得到的是「这次推进**应该**花多少」，而实际花掉的是历史事实，
**尤其是崩溃重来会真的再花一遍**。

| 只记一层 | 会怎样 |
|---|---|
| **只挂 Run、不分尝试** | 一次崩溃之后重算，**要么把已花的忘掉（漏计），要么把重算的再加一遍（重复计）**——两者都是错账，**而且事后分不出是哪一种** |
| **只挂尝试、不汇总** | 对人、对租户可见的账单单位是「**这段工作花了我多少**」，不是「第三次重来花了多少」——**汇总层缺位** |

> **所以两层都要**：**明细按尝试增量记**（崩溃前记多少算多少），**汇总按 Run 算**。
> **附带一个可观测的数字**：这个 Run 的成本减去最后一次尝试的成本，**就是崩溃浪费掉的钱**。

**这不与[「不要把成本挂在 agent runtime 上」](#run-是三样东西的归属单位)冲突**：
**归属单位是 Run**（账单、失败、收束都按它），**明细只是记在日志里的一笔笔流水**，
协程没了它们照样在。

### 5.14 外部效果的记录：追溯与幂等，是同一条记录上的两个字段

**外部效果是[收不回来的那一类](#三个运行时停机之后各算什么)**：发出去的邮件、下过的单、改过的外部系统。
**每一条这样的记录至少要带七样：**

| 带什么 | 干什么用 |
|---|---|
| **哪个 Run** | 哪一段工作干的 |
| **第几次尝试** | 哪一次干的 |
| **这个 Run 内的第几步** | 这段工作的哪一步干的 |
| **幂等键** | **重来的时候不要再做一遍** |
| **对外的标识** | 对方回给我们的那个 id，用来对账 |
| **什么时候** | 实际发生的时刻 |
| **结果** | **成功 / 失败 / 不知道**——三个值，[与 PF-000 那一栏同一套取值](../PF-000-occurrences-and-record-entries/design.md#55-挂在每条条目上的字段) |

#### 幂等键与追溯标识，必须是两个字段

**它们的方向正好相反，合成一个必然牺牲其中之一。**

| | 要做到什么 | 因此 |
|---|---|---|
| **幂等** | 重来时算出来的键**和上次一样**，对方才认得出「这是同一件事，别做第二遍」 | **幂等键里绝不能含尝试序号**——序号重来时必然变。它只能由 (会话, Run, 第几步) 决定，**这三样在重算时都是确定的** |
| **追溯** | 说得清**是哪一次尝试干的** | **必须含尝试序号** |

> **所以同一条记录上并列两个字段**：一个跨尝试稳定，一个逐次不同。
> **合成一个，要么幂等失效（重来又做一遍），要么追溯失效（查不出是哪一次）。**

#### 「不知道」这个值不能省

**崩溃最典型的时刻就是「已经发出去了，结果还没写回日志」。**

新的一次尝试读到一条**只有请求、没有结果**的效果记录，**这本身是重要信息**——
它说的是「**这一步可能已经生效了，别当作没做过**」。

> **只有「成功」和「失败」两个值，这种记录就无处安放**，
> 于是被当成没发生，**于是重做一遍**——而那正是外部效果最不该发生的事。

## 六、产品规则

### 6.1 日志先于可见

**任何要进入 agent 上下文的东西，先落盘，再进上下文。**

绝不允许「图里看得见、日志里没痕迹」——那种东西**一次重启就凭空消失**，
而 agent 的后续判断全建立在它上面。

这条对**循环守卫的干预消息**尤其硬：落盘顺序颠倒，重探时窗口就变了，
**结论可能和上次不一样**——而方程的确定性正是靠「结论必然相同」撑着的。

### 6.2 新的一次尝试不铸新身份

接着跑的那个 Run，**还是原来那个 Run**。身份在数据里，不在进程里。

反过来：**铸新身份是「新一次运行」的专属权利**。分不清这两者，
同一件事会在日志里留下两份，**而且没人看得出它们是同一件事**——
[账和失败都会算错](../../ubiquitous_language/terms/agent-runtime-loop.md#ul-run-attempt--执行尝试--run-attempt)。

### 6.3 喂给 agent 的是日志原样

重建的历史，**零追加、零注入**，触发那条消息停在它原本的位置。

**多塞一句进历史里**，看似贴心，实则**改变了窗口**——
循环检测会因此失准（多出来的那条可能被当成新的工作输入，把阶梯洗白）。

> **这一条与 §6.4 不冲突**：那一条加的是**追加在尾巴上的一条新消息**，
> 不是往历史里插东西。

### 6.4 每一次尝试开始，agent 都要知道

**「从最后明确记载的状态重算」意味着可能重做**——同一封邮件发两遍、同一笔操作做两次。

> **这是用户会遇到的事，不是技术注记。**

所以：**做成一条追加的 [`SystemReminderMessage`](../PF-009-context-message-types/design.md#systemremindermessage)**，
说清这一次是从一次中断接上来的。

**这条消息同时就是日志里的「尝试开始」记录**，因此它**带着这次尝试的序号**，
连同时间与起的原因——[四样一起，见 §5.7](#每一次尝试开始都要做四件事)。

> **不写序号，这一条就只兑现了一半**：外部效果重复了，人只看得到「这里重来过」，
> **看不出是哪一次干的**——而[效果记录上正是拿这个序号追溯的](#514-外部效果的记录追溯与幂等是同一条记录上的两个字段)。

**为什么必须让它知道**：重做的风险由它判断，**不知道就没法判断，也不知道该去核实什么**——
尤其是[「合成被中断结果」那条路](#先对账再进方程)：**那个动作可能真的做了一半**。

**为什么是追加而不是改历史**：§6.3。
**为什么不洗白循环阶梯**：它是系统说的，**不是[新的、独立的权威工作输入](#65-新的尝试不重置循环阶梯)**。

**这一条同时满足「人也要看得见」**——
[`SystemReminderMessage` 对用户可见](../PF-009-context-message-types/design.md#七种消息各自谁感知得到)，
所以外部效果重复了，人追溯得到是哪一次尝试造成的。

### 6.5 新的尝试不重置循环阶梯

**技术上的重来不是新工作。**只有新的、独立的权威工作输入才为新工作开启新阶梯。

不守这条，agent 只要崩得够勤就能无限打转，**而每次崩溃看起来都像意外**。

### 6.6 终态不可逆，且只有一个出口

三个终态：完成 / 失败 / 被取消。**到了就回不去**，也**不许从别的地方落账**。

附带一个很硬的细节：**先确保会话存在，再落终态**——

> **第一轮就死掉的会话，它的第一条事实就是自己的失败。**

没有这一条，那种会话会变成幽灵：Run 失败了，但没有任何地方看得到它。

**「等人」不是终态**，**「已上交」也不是**——后者说的是[另一条线](#512-run-的终态与非常态的终局是两条线)上的事。

#### 超时、被打断、配额耗尽，是原因不是终态

**它们后续该怎么处理，与三种终态之一完全相同**——所以它们**写在终结条目的原因字段上**，
不新开第四、第五种终态。

> **终态是被大量规则读的那个判定值**（[只看日志那张表](#只看日志该不该起一个-agent-runtime)、
> [七条不变式](#617-run-这一层的七条不变式)、账单、告警、统计都读它）。
> **终态集合每扩大一次，所有读它的地方都要跟着改**；而原因字段多一个取值，谁都不用动。

### 6.7 检测状态从日志派生，不另存

循环检测的计数与阶梯，**一律从消息窗口算出来**。

**窗口取自[会话日志](#会话日志)，不是取自「给模型的那一份」**——
[压缩只往后追加一条摘要并点名一批块，一条都不擦除](../PF-010-context-management-and-assembly/design.md#612-记录里的消息一条都不能擦除)，
所以日志里什么都还在。**照给模型那份去数，agent 打转到触发压缩就能把阶梯洗白。**

不新建持久计数结构——多一份状态就多一处会和日志对不上的地方，
**而对不上的时候，没人说得清哪份是真的**。

### 6.8 L0 观测永不可关

最低那一级**只观测、不干预**，因此没有任何理由关掉它。

**关掉它，「agent 在打转」这件事就再也没人知道**——
包括那些还没严重到触发干预的早期迹象。

### 6.9 拓展件只能靠改日志起作用

**没有第二条通路。**它不能不留痕地改变下一步，也不能自己指定跳到哪一步。

**验收办法很干脆**：

> **把一件拓展件上次的判断留在日志里，然后重算一遍 `f`。**
> **算出来的下一步必须与当时相同。**不同，就说明有东西没被记下来。
>
> **还在等人的那一件用回放来验**：把人的答复落进日志，重算——它必须**一张新卡都不出、一次模型都不再调**，
> 走到出卡那一处拿到的就是那条答复（[等人是 loop 的原语](#等人是-loop-的原语)）。

**这一条把[环绕式那一半挡在外面](#三种形态两种装得进一种拆两半)**：
一件自己循环调下一层的挂件，中间那几次**没有条目**，重算就拿不回同一个下一步。

### 6.10 能干预的拓展件，必须留下结论

**一件「可改写」或「可否决」的拓展件，必须有一条条目记下它的结论。**

**理由 [PF-000 K1](../PF-000-occurrences-and-record-entries/design.md#61-k1能干预的必须留下结论) 已经写了**：
干预改变了实际发生的事，不记结论，**重算会得到与当时不同的结果，而且没人看得出哪里不一样**。

**它报了错、或因不可用被视作卸载，也要留一笔**——不然排查的人分不出「判定说不用」「判定没跑成」「那一件此刻不在」。
报错时，**它那一类的策略实际怎么处置了这一次**，也在这一笔里。

**几种结论各自要落下什么：**

| 它做了什么 | 日志里至少要有 |
|---|---|
| **否决** | 否了什么、**哪一件否的**、原因——agent 与人据此[分得出这不是执行失败](../PF-008-human-in-the-loop/design.md#69-人拒绝之后agent-分得出那是拒绝) |
| **在执行动作之前改了参数** | **一条「生效参数」，在执行之前落下**；原参数留在模型那条回复里不动（[为什么](#改参数先落一条生效参数)） |
| **出卡等人** | **那张卡片本身**（标明是哪一件出的），以及答复回来之后它下的那个结论 |
| **自己调了模型再下判断** | 那一次调用的结果与花费——**回放时要从这里交回**（[等人是 loop 的原语](#等人是-loop-的原语)） |
| **要求「停住」** | 一条取消请求（发起方写这一件）＋ 一条终态「被取消」（[为什么这样译](#干预力三档直接用-pf-000-的)） |

### 6.11 悬着的东西不许被压掉

**没答完的卡片（不论是 agent、放行判断还是哪一件拓展件出的）、转后台还没回来的执行，各有一个占位。**
**不许[点名那些占位](../PF-010-context-management-and-assembly/design.md#58-压缩不能做的有三件事)。**

占位被点掉，**agent 就不知道自己还有东西在外面跑**，
而日志层面它们还好端端悬着——**两边静默对不上**，
而[「悬着的东西」本来就在方程的定义域里](#方程从日志里读什么)。

> **两边各管一半。**[「压缩不能拿它怎么样」归 PF-010](../PF-010-context-management-and-assembly/design.md#悬着的东西被点了名两边就静默对不上)，
> **「什么叫悬着」归这里**——那是[方程定义域](#方程从日志里读什么)的一部分，压缩那一侧不知道。

### 6.12 终态之后再回来的东西，不让 Run 复活

**日志[只增不改](#会话日志)。**Run 在某一刻落了终态，一个后台结果在那之后才回来——
**现在日志的尾巴是那条结果，不是终态**。

按 [T7](#56-状态转移表)「结果齐了 → 回 T1（该想了）」的字面读法，**这个 Run 就复活了**。

> **不会。**方程读的**不只是尾巴**，还有 **[Run 的姿态](#方程从日志里读什么)**——
> 它本来就在定义域里，**而「已经终态」是其中一种姿态**。

| | |
|---|---|
| **那条结果还落不落** | **落。**日志是会话的，它记录真实发生过的事 |
| **它改不改这个 Run 的终态** | **不改**（[§6.6](#66-终态不可逆且只有一个出口)） |
| **agent 会不会因此被叫醒** | **这个 Run 不会**——它的方程已经停了 |
| **那会不会有下一个 Run** | **会。**那条结果进了[待处理消息队列](#待处理消息队列)，而**队列非空就要开下一个 Run** |
| **下一个 Run 看得见它吗** | **看得见**——同一条会话日志 |

**所以「看尾巴决定下一步」是简化说法**，准确的说法是：

> **先看这个 Run 有没有终态条目，有就停；没有，才看尾巴。**

**不写这一条会怎样**：[§5.11 明说](#511-外面进来的事怎么到-agent-眼前)「结果回来了，
而 Run 可能早走远了」——**实现者照着转移表做，那条结果就会把一个已经结算完的 Run 重新拉起来**，
而账、终态、通知都已经发出去了。

> **但「不复活」不等于「没人看」，这两件事必须分开读。**
> 一个用户说「**跑那个两小时的构建，好了告诉我**」，结果回来时原来那次 Run 早已收束——
> **若照字面理解成「那就没人管了」，用户要等到自己下次主动说话才发现两小时前就跑完了。**
>
> **[Run 的定义](#run)已经把这件事定死**：那条结果**进队列**，
> **队列非空就要开下一个 Run**。不复活**这一个**，与**会有下一个**，
> **是同一条规则的两半，缺哪一半都会做错。**

### 6.13 取消跟着宿主走

**每一个运行时都有一个宿主，宿主没了它就没了。**
这一条**取代四条分别要记的规则**——它们是同一件事。

| 谁 | 宿主 | **中断一次运行** | **终止 / 归档 / 回收会话** |
|---|---|---|---|
| [模型请求运行时](../PF-013-model-profiles-and-invocation/design.md) | **[agent runtime](#agent-runtime)**（永远） | **停** | 停 |
| [工具执行运行时](../PF-006-tools-and-skills/design.md)（**前台**——agent runtime 正阻塞在它上面） | **会话**（它有自己的 runtime，从不由 agent runtime 承载） | **停**，落[「被中断」](../PF-006-tools-and-skills/design.md#67-用户可以中断而中断不是失败)——那一步不要了 | 停 |
| 工具执行运行时（**已转后台**——agent runtime 不再等它） | **会话** | **不停** | **停** |
| [拓展件](#拓展件)的那一段执行（**含停在等人上的**） | **agent runtime** | **停**；它出的卡随 Run 的取消作废 | 停 |
| `spawn` / `delegate` 出去的[子会话](../PF-007-meta-capabilities/design.md)及其名下一切 | 父会话 | 不停 | **停（递归）** |

> **转后台不换宿主**——工具执行[一直绑在会话上、有自己的 runtime](../PF-006-tools-and-skills/design.md#65-工具执行有自己的运行时绑定在-session-上)，
> 变的只是 **agent runtime 不再阻塞在它上面**。这一节给那句话补上两头：
> **前台的，run 中断时跟着停，因为那一步不要了；后台的，会话终止才带走它。**

**回收 agent runtime 不是取消，这张表也不管它。**
表里两列都是**取消**——作用于 Run 或会话的一个意图，[先落日志再发信号](#615-取消先落日志再发信号)。
**回收**是另一件事：Run 停在等人、等工具（[T4、T6](#这个循环从哪里出去)）时把协程交还，之后再起一副新的；Run 还在，**什么都没被叫停**。

| agent runtime 被回收时 | 怎么样 |
|---|---|
| **工具执行**（前台的、已转后台的都一样） | **一个都不取消。**它们各有自己的 runtime，照跑；Run 里记着[协程在等哪一次](#等人是-loop-的原语)，新协程起来接着等 |
| **拓展件那一段执行**（含停在等人上的） | 那段执行没了，**卡片留着**——[新的一次尝试回放到它停下的那一处接着等](#等人是-loop-的原语) |
| **模型请求** | 不会碰上：等模型不是[这次尝试的出口](#这个循环从哪里出去)，协程不在那时交还 |

> **所以上表里两列说的是取消波及谁，不是谁的协程还活着。**
> 前台工具执行在这次运行被中断时跟着停，是因为**那一步不要了**，不是因为它挂在 agent runtime 上——它从不挂在那里。
> [I-6、I-7](#agent-runtime-的四条不变式) 里的「被取消」，说的正是回收。

**模型请求为什么没有「不停」这一格：它不能转后台**，所以从没换过宿主。
[它停了之后算什么，看首 token](../PF-013-model-profiles-and-invocation/design.md)——首 token 之前可重发，之后一律不重发。

**`handoff` 出去的不在递归范围内。**
[它有独立主会话身份](../PF-007-meta-capabilities/design.md)，已经不挂在派发者名下；
若父会话归档要连坐它，那个身份就名存实亡——**而那正是 `handoff` 区别于另外两种的唯一理由**。

#### agent runtime 的四条不变式

**这四条的主语是 [agent runtime](#agent-runtime)，所以它们归本 topic。**
**编号沿用 PF-004 那一套**，不重排——**既有引用因此不会指错**：

| # | 不变式 | 不成立会怎样 |
|---|---|---|
| **I-1** | 一个会话在任一时刻**至多有一个活跃的 agent runtime** | 两个协程同时以同一个身份说话，日志就没有单一真相 |
| **I-2** | **agent runtime 的起灭对协作中的用户不可见** | 用户会看到 agent「重启了」，而他什么也没做 |
| **I-6** | agent runtime 被取消，**不产生用户可感知的损失** | 取消变成一种故障 |
| **I-7** | **等人回话的时间不消耗计算资源** | 一个等了两天的确认，账单上是两天的运行费 |

**I-6 的具体含义**：取消之前，未完成的事情要么已经持久、要么在下一次尝试里能接续、
要么**明确失败并让人知道**。三者之外没有第四种。

**I-7 靠的是「等待是一个持久的事实，不是一个协程的姿势」**——
[停下来等人不是终态](#66-终态不可逆且只有一个出口)，但那个事实在日志里，
协程可以先被取消；人回话之后起一个新的接着算，用户看到的是他的问题被接上了。

**I-1 是关于 agent runtime 的，不是关于 Run 的。**同一时刻能不能跑两个 Run，
见[会话内单活跃](../../ubiquitous_language/terms/agent-runtime-loop.md#ul-single-active-execution--会话内单活跃--single-active-execution)
与[理由](#一个会话任一时刻至多一个未终结的-run)。

> **Run 与日志那一层自己的七条，见 [§6.17](#617-run-这一层的七条不变式)。**

### 6.14 停止有两级

| | **[优雅取消](../../ubiquitous_language/terms/agent-runtime-loop.md#ul-graceful-cancellation--优雅取消--graceful-cancellation)** | **[强制停止](../../ubiquitous_language/terms/agent-runtime-loop.md#ul-forced-stop--强制停止--forced-stop)** |
|---|---|---|
| 做什么 | 先不接新工作，等真正停当，再释放 | 立刻撤销继续执行的资格 |
| 代价 | 慢，但结果干净 | 快，但**已经发出去的外部效果收不回来** |
| 反馈 | 各项都有结局（I-6） | **逻辑停止、实际停止、外部效果未知，必须分别说** |

**不能把「已经停止」和「外部效果已经撤销」说成一回事**——
这与根约定「外部输出不因被运行时调用就变得可逆」一致。

> **两级的代价不同，但[传播范围一样](#613-取消跟着宿主走)。**
> 强制停止不会多带走一个已转后台的工具执行，优雅取消也不会少带走一个前台的。
> **决定波及谁的是宿主，不是用哪一级。**

**谁有资格发起、怎么发起**，归控制那一侧。本节定的是
**这两级各自意味着什么、必须留下什么**。

### 6.15 取消先落日志，再发信号

**取消的意图作用于 [Run](#run)，执行落在那副协程上。两步都要做，但只有写进日志的那一步算数。**

| 只做一半 | 会怎样 |
|---|---|
| **只停协程，不写日志** | 日志里那个 Run 仍然未终结。[按只看日志的那张表第 3 行](#只看日志该不该起一个-agent-runtime)，恢复逻辑的反应是**再起一副接着干**——**杀了又活，取消等于没发生** |
| **只写日志，不停协程** | 那副还活着的协程继续烧钱、**继续产生撤不回来的外部效果**。每多跑一秒都可能多一件收不回的事 |

**而最硬的一条理由是：有时候根本没有协程可停。**

> [那张表第 4 行](#只看日志该不该起一个-agent-runtime)：Run 在等人，协程早已交还，**此刻这个会话里一副协程都没有**。
> 这时用户说「别弄了」——**作用对象只能是 Run，没有别的东西可以作用**。

**顺序是硬的：**

> **先把取消请求写进日志，再向当前尝试发停止信号。**

反过来会留下一个致命窗口：信号已发、协程已死、日志还没写——
**此刻停机，恢复逻辑看到「Run 未终结」，于是起一副新的，继续推进一件已经被叫停的工作。**
日志先行则相反：哪怕写完立刻停机，恢复逻辑看到那条取消请求，
**知道该做的是终结这个 Run，而不是继续它**。**失败的方向是安全的那一边。**

#### 强制停止的三步闭环

**[优雅取消](#614-停止有两级)那一级不需要这个闭环**——协程在下一个等待点看到取消请求，
自己收尾、自己落终态。**强制停止的定义就是不等收尾，所以终态条目不能由被杀的那副协程来写。**

| 步 | 谁做 | 做什么 |
|---|---|---|
| **1** | 发起方 | 写一条**取消请求**，标明是**强制** |
| **2** | 系统 | **杀掉当前这次尝试**，不等它收尾 |
| **3** | **会话这一侧的治理逻辑** | 看到「有一条强制取消请求 + 没有活着的尝试」，**替它写终结条目**，终态＝被取消，**并标注「可能存在未收尾的外部效果」** |

**第 3 步暴露一件必须明说的事：会话这一侧必须有权写 Run 的终结条目。**
否则强杀之后这个 Run 永远挂在未终结上，[那张表第 3 行会让它被反复复活](#只看日志该不该起一个-agent-runtime)——
**强杀变成无限重启。**

**那句标注也不能省。**强杀就是不等收尾，所以最后一刻发出去的东西有没有落地，
**系统确实不知道**。

> **诚实地记下「不知道」，比默认它没发生要安全**——
> 这与[效果记录上那个「不知道」](#不知道这个值不能省)是同一条道理。

### 6.16 日志里至少要有这几种 Run 相关的条目

**这一节回答的是「从日志里至少要读得出哪几件事」，不是「条目长什么样」。**
条目的形状、[效力](../PF-000-occurrences-and-record-entries/design.md#条目效力--entry-standing)与[寿命宿主](../PF-000-occurrences-and-record-entries/design.md#寿命宿主--lifetime-host)归
[PF-000](../PF-000-occurrences-and-record-entries/README.md)，**本 topic 不重定**。

| 要读得出 | 至少带什么 | 缺了会怎样 |
|---|---|---|
| **Run 开始** | Run 的标识、**承接了哪些输入**、触发原因；**可带「延续自哪个 Run」** | [分不出「没人处理」与「正在处理」](#它存在的理由让起不起协程只看日志就算得出来)；Run 没有身份，一切归属无处可挂 |
| **输入承接** | 哪个 Run、承接了哪些输入、时间 | [队列那道减法](#待处理消息队列)算不出来；[并入点不是日志事实，重算时的取用顺序就与上次不同](#run-跑着的时候又进来一条东西) |
| **在等什么** | 哪个 Run、在等什么、从什么时候开始等 | 分不出[「在推进」与「在等」](#只看日志该不该起一个-agent-runtime)；等待期间零资源占用做不到（[§5.13](#等待必须是一条显式的记录)）。**这一条不另造，卡片与占位就是它** |
| **尝试开始** | Run、**尝试序号**、时间、原因 | 尝试没有可指的身份，外部效果追不到「哪一次」；[栅栏没有比较对象](#同一个-run-同一时刻只有一副协程在推它) |
| **外部效果** | [七样，见 §5.14](#514-外部效果的记录追溯与幂等是同一条记录上的两个字段) | 收不回来的输出与可重算的动作被一视同仁，**重算就会再做一遍**；追溯无据 |
| **成本** | 哪次尝试、成本项与数量、时间 | 结算不了；[崩溃重来造成的重复消耗分辨不出](#成本两层缺哪一层都会算错) |
| **取消请求** | 哪个 Run、谁发起、原因、**是不是强制**、时间 | 取消不跨停机成立，[杀了会复活](#615-取消先落日志再发信号) |
| **Run 终结** | Run、[终态](#运行终态)、原因、结果引用、**是否可能留有未收尾的外部效果** | 终态判定不了，[那张表整个崩塌](#只看日志该不该起一个-agent-runtime)；Run 永不终结 ⇒ 无限复活 |
| **尝试结束**（**建议记，不是必需**） | Run、尝试序号、时间 | 成本与失败归因变粗；只能靠「出现了更大的序号」反推上一次已经死了。**[恢复逻辑必须容忍它缺失](#每一次尝试开始都要做四件事)** |

**刻意不设一种「等待结束」的条目。**被等的东西到达、再被承接，
**这两件事合起来就是等待结束的完整证据**，再记一条是冗余。

> **冗余的害处不是占地方，是它可能与事实不一致**——
> 一旦「等待结束」与承接记录对不上，**没人说得清该信哪个**。

### 6.17 Run 这一层的七条不变式

**[agent runtime 那四条](#agent-runtime-的四条不变式)的主语是那副协程，这七条的主语是 Run 与日志本身。**
**编号续着排，不重排**——既有引用因此不会指错。

| # | 不变式 | 不成立会怎样 |
|---|---|---|
| **I-10** | **日志的任意一段前缀里，Run 开始条目数减去终结条目数，只能是 0 或 1** | 两个 Run 交错着往同一本日志里写，[重放不再确定](#一个会话任一时刻至多一个未终结的-run) |
| **I-11** | **每个 Run 至多一条终结条目；终结之后，日志里不再出现属于它的开始 / 承接 / 尝试开始 / 效果 / 成本条目** | 等于改写历史，[归属变成可变量](#612-终态之后再回来的东西不让-run-复活)。**这条同时要求：落终态之前必须把成本记全** |
| **I-12** | **每条已记录的输入至多被承接一次；若最新的 Run 已终结而它仍未被承接，则必须有一条在它之后的 Run 开始条目把它承接掉** | 左半防重复处理，右半防丢消息——[后一半就是「不复活这一个，但会有下一个」](#612-终态之后再回来的东西不让-run-复活) |
| **I-13** | **每条外部效果条目都带一个已存在的 Run 与一个已存在的尝试序号；它的幂等键完全由 (会话, Run, 第几步) 决定，不含尝试序号；同一个幂等键在同一个 Run 内至多对应一次已确认成功的外部效果** | [追溯与幂等塌成一个](#幂等键与追溯标识必须是两个字段)，必然牺牲其中之一 |
| **I-14** | **「此刻该不该有一副 agent runtime、它接手哪个 Run」只读日志就能回答，且同一段日志前缀恒得同一个结论**——不读进程表、不读内存、不读任何活着的状态 | **Run 存在的全部理由落空**。这也是最容易被实现悄悄破坏的一条 |
| **I-15** | **同一个 Run 内尝试序号严格递增；且恢复逻辑必须能在存在「有开始、没有配对结束」的尝试时正常工作** | 前半句没了，[栅栏](#同一个-run-同一时刻只有一副协程在推它)失效；后半句没了，**真崩溃面前系统直接卡死**——来不及写结束条目是常态，不是数据损坏 |
| **I-16** | **任何终态为「被取消」的终结条目，之前必有一条针对同一个 Run 的取消请求条目** | 出现[「停了，但日志不知道」的窗口](#615-取消先落日志再发信号) |

> **[I-1「一个会话至多一副活跃的 agent runtime」](#agent-runtime-的四条不变式)不在这里重复一遍**——
> 「同一时刻至多一次尝试是活的」就是它，**换个主语不等于多一条**。

## 七、取舍

| 选了什么 | 得到 | 付出 |
|---|---|---|
| **Run 与 Agent Loop 分成两个概念** | 一个能被写下来，一个能被重新算出来 | 读者要先分清两个词 |
| **Run 是成本 · 失败 · 收束的同一个归属单位** | 「这次任务怎么样了」**一个对象答得全** | 三样的粒度被绑在一起，将来想分开算**得改模型** |
| **[成本明细按尝试记、汇总按 Run 算](#成本两层缺哪一层都会算错)** | 崩溃重来花的第二遍钱**记得清也分得出**；「这个 Run 减去最后一次尝试」就是浪费掉的钱 | 账要按两层记，**读的人得知道自己在看哪一层** |
| **[默认把新到的东西并入正在跑的那个 Run](#run-跑着的时候又进来一条东西)** | 长任务里用户补一句**马上被看见**，不必等这一轮跑完 | Run 的边界要到终结时才完全确定；**每一次取用都得落一条承接记录，日志更长** |
| **[幂等键与追溯标识分成两个字段](#幂等键与追溯标识必须是两个字段)** | 重来不会把同一件事做第二遍，**同时又查得出是哪一次干的** | 每条外部效果记录多带一个字段，**而且两个字段的规则不能混着写** |
| **[强杀之后由会话这一侧写终结条目](#强制停止的三步闭环)** | 强杀不会变成无限重启 | **会话这一侧因此有权写 Run 的终结条目**——这是一处必须显式承认的权力 |
| **会话日志是唯一真相来源** | 转移完全确定，重算不必猜 | **可能重做**，且代价由外部效果承担 |
| **组装纯派生、不建状态点** | 可以随便跑第二次；少一类状态要对 | 每圈多算一次组装的开销；**它前后也因此推不出拓展点** |
| **崩溃恢复、等人回来、换 agent runtime 当成同一件事** | 一套机制管三条路，**没有一条是「异常路径」** | 读者要接受「恢复是常态」这个不直观的说法 |
| **压缩整个做成[闭包](#55-想这一步交进闭包拿回装得下的一份)，方程只认两个回执** | 方程**不必懂上下文预算**；换一整套压缩策略，[转移表](#56-状态转移表)一个字不动 | **闭包内部外面看不见**——压了几轮、丢了多少，得靠它自己往外说 |
| **压完还超即失败** | 不做无用的循环压缩，且把问题指回装配 | 用户看到的是一次失败，而不是一次降级 |
| **[循环探测](#59-循环守卫四级阶梯)与[卸载判定](#510-卸载结果落成消息之前的那一关)做成挂件，不占转移行** | 转移表少四行，**而产品行为一点没少**——[四种结局全落在已有的尾巴形状上](#循环探测的四种结局全落在已有的行上)；换一件实现，表不动 | 读表的人**看不出这两件事发生在哪**，得回到[位置表](#十一个位置是推出来的不是挑出来的)去找 |
| **L3 落「失败」不新增终态** | 终态只有三个，所有消费方都好处理 | 「被守卫结束」与别的失败要靠原因区分 |
| **L4 复用决策池** | 不另造机制；比直接掐掉友善得多 | 本 topic 因此依赖 PF-008 |
| **拓展件只能靠改日志起作用** | **`f` 的纯性不被破坏**，重算时不必重跑它们 | 拓展件做不了「观察之外、又不留痕」的事；每挂一个就多一批条目 |
| **位置由状态点推出，十一个一次开齐** | **完备性可论证**，不是「我挑了几个」；租户与组织超管能在任何一处插手 | 十一个里有几个今天没有消费者。**这不是预埋框架**——位置不是新机制，[它就是状态点的两条边](#十一个位置是推出来的不是挑出来的) |
| **环绕式拆两半，只收「给结论、由 loop 执行」那一半** | 重试、兜底照样做得到，且**每一次都在日志里** | 日志更长；**习惯了 LangChain 那种写法的人要换个写法** |
| **[等人是 loop 的一个原语](#等人是-loop-的原语)，拓展件与主流程共用；等待靠日志、回来靠回放** | 租户能自己定人机协作的卡片，**放行判断也只是其中一件**；等三天不占一副协程，崩了照样接着等 | agent runtime 要有回放这种跑法；**拓展件作者要守「等待前后不靠内存传东西」**；人可能看到同一批动作的第二轮卡片 |
| **[拓展件是可插拔的服务：不可用即卸载，报错按类型的策略](#拓展件是可插拔的服务不可用即卸载报错按策略)** | 「它此刻不在」与「它判了否决」分得开；每一类的出错处置各得其所，**不必一刀切** | **一件把关用的拓展件依赖挂了，这一关这一次就没了**——只能靠「不在」看得见来兜 |
| **[消息落盘之前否决了模型回复或工具结果：Run 失败，模型回复先走重试](#消息落盘之前的否决按消息是谁产生的分三路)** | 不留说不清的记录，**不需要补偿机制** | 一次拦截就可能结束整个任务；模型回复那一路，**用户可能看着一份回复吐完又看到另一份** |
| **[没有「放宽」这一档](#没有放宽这一档)** | 放行的权威只有一个出处，**谁能放宽、放宽落在哪一笔，都查得到** | 别家「hook 替人放行」的用法搬不过来，**想免问只能去改执行权限** |
| **[执行动作之后不给否决](#干预力三档直接用-pf-000-的)，别家的「停住」译成被取消** | 不会让人以为还拦得住已经做了的事 | 别家 hook 作者意图的「停一下」在这里是**整个 Run 收束**，而不是暂停 |
| **按位置命名，不按功能命名** | 同一位置可以挂多个，**位置的数目不随功能增长** | 位置名说不出它是干什么的，**读的人得多看一眼挂了谁** |
| **Run 的终态与非常态的终局分成两条线** | 会话层与租户层的处置**不会被 Run 的终态掐掉** | 读者要同时拿着两条线读，**比一条线难讲** |
| **每次尝试重算可用性** | agent 面对的是当下的真实情况 | 前后两次尝试的动作空间可能不同 |
