# PF-012 流程与状态

> **这一页说这套机制怎么动。**[design.md](design.md) 说它是什么。
>
> 两条纪律：**每条旅程都要走到收场**——停在半路的旅程等于没定义；
> **状态流转要穷尽**——没画出来的转移，研发会自己发明一个。

---

## 一、主要旅程

### 1.1 一次运行，从触发到完成

| 步 | 在哪一步 | 发生什么 | 改日志吗 |
|---|---|---|---|
| 0 | **消息落盘之前 → 之后** | 用户说的那句话经过脱敏、注入检测、模态转文本，**落进日志**——[队列从空变成非空](design.md#待处理消息队列) | **是** |
| 1 | —— | 那件事就是一次[触发](../../ubiquitous_language/terms/agent-runtime-loop.md#ul-trigger--触发--trigger)：**没有未终结的 Run，又有没人承接的输入** → **落一条 Run 开始条目，写明承接了哪一条** | **是** |
| 2 | **一次尝试开始** | 不必对账（没有上一次）· 重算可用性 · 追加一条尝试提醒，**带着这是第 1 次尝试、什么时候起的、为什么起** | **是** |
| 3 | **T1 想** | **队列非空** → 取一批 → **[交进压缩闭包](design.md#55-想这一步交进闭包拿回装得下的一份)** → **装得下** | **可能**（[真压了才落一条](design.md#53-改日志的动作与纯派生的动作)） |
| 4 | **T2** | **组装**（纯派生）→ **调模型**，回复落盘 | **是** |
| 5 | **◆ 回复落盘之后** | 循环探测：无事 | 可能记一笔 |
| 6 | **T3 判断** | 回复**带动作** → ◆ 放行判断：直接放行 | 否 |
| 7 | **T5 做** | 发出动作 | **是** |
| 8 | **T6 → T7** | 结果回来 → ◆ 结果落盘之前（卸载判定）→ 落成消息，**进队列** | **是** |
| 9 | **T1 想** | 队列非空，**取走这一批（落一条承接记录）**，回去想，这一轮模型说没有动作了 | **是** |
| 10 | **T2′** | **看队列空不空**——空了 | 否 |
| 11 | **收尾** | **落终态：完成**，退出 loop | **是** |

**一圈里真正的状态点只有那几个改日志的**。其余重算即得。

> **第 10 步是这条旅程里最容易被跳过的一步。**「模型没话说了」**不等于**这件事做完了——
> **这期间用户可能又说了一句、一个后台结果可能刚回来**。
> **队列非空就回第 3 步接着做，空了才收束。**

> **第 5 步与第 8 步那两个 ◆ 不在[转移表](design.md#56-状态转移表)里。**
> 它们站在[拓展点](design.md#58-loop-拓展点)上，**跑完它们 `f` 的取值不变**。

### 1.2 压完还是装不下（两条线在这里分叉）

| 步 | 发生什么 |
|---|---|
| 1 | **T1**：取一批 → 把日志和这一次要用的模型档案**交进[压缩闭包](design.md#55-想这一步交进闭包拿回装得下的一份)** |
| 2 | **闭包内部**：量一量 → 超了 → 压 → 再量 → **还超**（**外面看不见这一段**） |
| 3 | **压不下来了**——[常驻那部分压不动](../PF-007-meta-capabilities/design.md#54-十三个槽位是预算的地板也是它的天花板意义) |
| 4 | **闭包自己失败**，交出一件非常态 → **T1′** |
| 5 | 按 [PF-011 的判据](../PF-011-off-nominal-handling/design.md#56-了结得了吗看缺的那样东西在谁手上)：缺的是上下文空间，而压缩就在运行这一层——**手段用尽**。**留一条上交条目** → 交给会话 → 运行这一层就地停住 |
| 6 | **同时**：这个 Run **落终态失败**，原因写明是固定部分超限 |

> **方程从头到尾没量过一次长度。**它只收到「装不下」这一个回执，
> **至于闭包在里面压了几轮、丢了多少，它不知道，也不需要知道。**

```text
Run：    触发 ──→ 在跑 ──→ 失败      ← 到此为止
                            ↑
非常态： 运行 ──→ 会话 ──→ 租户 ──→ 终局   ← 还在往外走
```

**第 5、6 步是两条条目，不是一条**（[§5.12](design.md#512-run-的终态与非常态的终局是两条线)）。

**会话那一层接手之后能做的是「重算可用性让下次运行换个动作空间」**——
**那是下一个 Run 的事**。这一个救不回来了，所以它的终态不等外面那几层。

### 1.3 agent 原地打转：四级阶梯

| 阶段 | 守卫做什么 | 方程落到哪 | Run 的状态 |
|---|---|---|---|
| 刚开始重复 | **L0** 只记一笔 | 不转移，照常往下 | 在跑 |
| 还在重复 | **L1 / L2** 往日志里写一条干预消息 | **T1**——agent 带着它继续想 | 在跑 |
| 重复到阈值 | **L4** 出一张卡片问人 | **T4**——停住等 | **停着等** |
| 人没给出路 / 或直接到顶 | **L3** 优雅结束 | **落终态失败**，原因写明是原地打转 | **失败** |

**阶梯是从日志里数出来的，不另存计数器**（[§6.7](design.md#67-检测状态从日志派生不另存)）。

> **这张表里没有一行是新的转移。**守卫自己不在[转移表](design.md#56-状态转移表)里——
> [四级的每一种结论，都落在表里已经有的那个尾巴形状上](design.md#循环探测的四种结局全落在已有的行上)。

> **注意 L3 走的不是那条阶梯。**agent 打转时，
> [没有哪一层偏离了主路径](design.md#哪些收束根本不进-pf-011-的模型)——
> 它是运行这一层的**主动收束**，不是「没办法了往上交」。

### 1.4 等人：agent runtime 被取消，人回话之后接着跑

| 步 | 发生什么 | Run | agent runtime |
|---|---|---|---|
| 1 | **T3** 放行判断判出要问人，卡片落盘 | 在跑 | 在 |
| 2 | **T4** 停住，什么都不做 | **停着等** | 在 |
| 3 | 等待期间[agent runtime 被回收](design.md#614-停止有两级)——[等人不消耗计算资源](design.md#agent-runtime-的四条不变式) | **停着等** | **没了** |
| 4 | 等待期间外面来的事[照常收进日志](../PF-008-human-in-the-loop/design.md#62-等待期间照常收排队等着解除时一起看到) | 停着等 | 没了 |
| 5 | 人答完了这一批卡片 | 停着等 | 没了 |
| 6 | **起一个新的 agent runtime → 这是新的一次[执行尝试](../../ubiquitous_language/terms/agent-runtime-loop.md#ul-run-attempt--执行尝试--run-attempt)** | 在跑 | **新的一个** |
| 7 | **不必对账**——上一次尝试是正常停住的，尾巴本来就是方程认得的形状 | 在跑 | 在 |
| 8 | 重算可用性 · 追加一条尝试提醒 · 进方程 → **T5** | 在跑 | 在 |

> **还是原来那个 Run**（[§6.2](design.md#62-新的一次尝试不铸新身份)）。
> 用户看到的是他的问题被接上了，**中间换过一个 agent runtime 这件事他不必知道**。

### 1.5 系统崩了：对账，然后重新算一遍

| 步 | 发生什么 |
|---|---|
| 1 | 系统在 Run 没走完时停机。**日志在，agent runtime 没了**。日志上多半留着一条**有开始、没有配对结束**的尝试记录——**那是正常的，不是数据损坏** |
| 2 | 只看日志判断：**最新那个 Run 未终结、没有悬着的等待** → [该确保有一副协程在推它](design.md#只看日志该不该起一个-agent-runtime) |
| 3 | **对账**——日志的尾巴可能停在正常运行时不会出现的形状上（见下表） |
| 4 | 对完账，尾巴回到方程认得的形状 |
| 5 | 重算可用性 · **追加一条尝试提醒**（序号比上一次大一，原因写「从一次中断接上来」）· 进方程 |
| 6 | 照常算下一步。**循环阶梯不重置**（[§6.5](design.md#65-新的尝试不重置循环阶梯)） |

| 断在哪 | 尾巴的样子 | 怎么接 |
|---|---|---|
| 发出了动作，结果没落盘 | 有调用、无结果 | **合成一条「被中断」的结果**补上，照常走 T7 |
| 模型已给完整回复，终态没落 | 有回复、无终态 | **幂等收尾，绝不再调模型** |
| 后台执行没落完成 | 占位还在，工作没了 | 算**失败**——它跑在这个系统里，系统没了它就没了 |
| **[外部效果](design.md#514-外部效果的记录追溯与幂等是同一条记录上的两个字段)只有请求、没有结果** | 有一条效果记录，结果那一栏是**「不知道」** | **不能当作没发生。**要不要重做，看那一步的[幂等键](design.md#幂等键与追溯标识必须是两个字段)——**键跨尝试不变，重发不会做成两遍** |

**第 5 步那条提醒是必须的**：agent 得知道自己在一次中断之后，
**否则它判断不了「刚才那个动作是不是已经做了一半」**。

> **上一副协程万一没真死，两副就撞上了。**
> 兜住它的是[尝试序号那道栅栏](design.md#同一个-run-同一时刻只有一副协程在推它)：
> **只有序号最大的那次尝试写得进去**，旧的那副写什么都被拒。

### 1.6 一件拓展件否决了动作

| 步 | 发生什么 | 日志里留下什么 |
|---|---|---|
| 1 | **T3**：模型给出一批动作 | 那条回复（已落盘） |
| 2 | ◆ **放行判断**：其中一个要问人 | **一张卡片**（依据） |
| 3 | **T4**：这一批**一起等**（[PF-008：全答完才解除](../PF-008-human-in-the-loop/design.md#53-一批卡片与答完是什么意思)） | —— |
| 4 | 人否了那一个 | **一条「人不同意」** |
| 5 | **T5**：放行的去做，被否的不做 | 各自的结果 |
| 6 | 若**全被否** → **T8**：照样回 T1 走一遍模型 | —— |

**第 6 步不能省**：不让 agent 知道人否了它，**它下一轮还会再发一次**。

> **「人否了」不是一个终态。**三个终态里一格都装不下它——
> 完成没完成，[人拒绝不是失败](../PF-011-off-nominal-handling/README.md#非常态不是报错)，
> 被取消说的是用户叫停整个 Run。

### 1.7 两小时的构建：Run 收束了，结果才回来

**这条旅程专门回答「Run 停了，东西还会不会有人看」。**

| 步 | 发生什么 | 这个 Run |
|---|---|---|
| 1 | 用户说「跑那个两小时的构建，好了告诉我」 | 触发，**Run ①** 起来 |
| 2 | 工具[转后台](../PF-006-tools-and-skills/design.md#66-前台后台-与-等待态是两个维度)，那次调用的位置落一条**占位** `ToolMessage` | 在跑 |
| 3 | **T7**：占位算「结果齐了」→ 回 T1 | 在跑 |
| 4 | 模型说「已经放到后台跑了，好了我告诉你」，**没有动作** | —— |
| 5 | **T2′**：队列空了 | **落终态：完成**，退出 loop |
| 6 | **两小时后**：构建跑完，结果作为 `SystemReminderMessage` 落盘 | **Run ① 不复活**（[§6.12](design.md#612-终态之后再回来的东西不让-run-复活)） |
| 7 | 那条消息进了队列，**队列从空变成非空** | **Run ② 起来**，进 loop |
| 8 | **T1**：取到它 → 组装 → 调模型 → 模型告诉用户结果 | Run ② 在跑 |

> **第 6 步与第 7 步是同一条规则的两半。**
> **只读第 6 步**，会做成「结果回来了没人管」——用户要等到自己下次主动说话，
> **才发现两小时前就跑完了**。
> **只读第 7 步**，会做成「把已经结算完、通知发出去的 Run ① 重新拉起来」——
> 账、终态、通知全乱。

**这条旅程的前提是[会话没被归档](../PF-015-session-lifecycle-and-ownership/design.md#会话归档)**；会话的生命周期归 [PF-015](../PF-015-session-lifecycle-and-ownership/README.md)。

### 1.8 用户插队：loop 被推到取消息的那一步

**排队与插队的差别只有一个：[要不要等 loop 自己走到取消息那一步](design.md#什么时候到与-loop-走到哪一步无关)。**

| | **排队**（默认） | **插队**（带插队命令的用户消息） |
|---|---|---|
| 那条消息落进日志 | **一样落** | **一样落** |
| 在队列里排哪 | **队尾**，先到先处理 | **队首** |
| 正在跑的这一步 | **不动**，跑完再说 | **被推向它的出口**——[怎么推归 PF-014](../PF-014-inbound-intake-and-queueing/README.md) |
| loop 里的等待态 | **不动** | **一并解除** |
| 这个 Run | **不变**，接着跑 | **不落终态**——它只是被推到了下一次取消息的那一点 |

> **插的是时间，不是别人的位置。**两条路最终都走到同一个地方：**T1 取一批消息**。
> **插队只是把中间那段间隔压到最短。**

**「不落终态」这一点要紧**：[§5.6 明写一次尝试的出口有三个](design.md#这个循环从哪里出去)——
**落终态 · 停住等 · 被中断**。插队走的是第三个，**中断的是这次尝试，不是这个 Run**；
新的一次尝试从 T1 进来，**零个新转移**。

### 1.9 用户强制停止：三步闭环，最后一步由会话这一侧收尾

**[优雅取消](design.md#614-停止有两级)那一级不走这条路**——协程在下一个等待点看到取消请求，
自己把该记的记全、自己落终态。**这条旅程说的是不等收尾的那一级。**

| 步 | 发生什么 | 谁做 | 日志里留下什么 |
|---|---|---|---|
| 1 | 用户叫停，并要求立刻停 | 控制那一侧 | **一条取消请求，标着「强制」** |
| 2 | **杀掉当前这次尝试**，不等它收尾 | 系统 | —— |
| 3 | 看到「有一条强制取消请求 + 没有活着的尝试」 | **会话这一侧的治理逻辑** | **一条终结条目**：终态＝被取消，**并标注「可能存在未收尾的外部效果」** |

> **顺序不能倒过来。**先发信号再写日志，中间那一瞬停机，
> 恢复逻辑会看到「Run 未终结」，**于是起一副新的接着推进一件已经被叫停的工作**。
> [先落日志，失败的方向就是安全的那一边](design.md#615-取消先落日志再发信号)。

**第 3 步不能省，也不能交给被杀的那副协程做**——它已经没了。
不写这条终结条目，[那个 Run 永远挂在未终结上，会被反复起协程复活](design.md#只看日志该不该起一个-agent-runtime)，
**强杀变成无限重启**。

**那句标注同样不能省**：最后一刻发出去的东西有没有落地，**系统确实不知道**；
下一个 Run 与排查的人都要看得见这份不确定。

> **停得掉的停，停不掉的记一笔。**在途的工具执行怎么收场见 [§5.3](#53-被取消不在状态转移表里因为它不是一行)。

## 二、状态流转

**一次 Run，从触发到收场，只有这几个状态：**

```text
        ┌────────┐
        │  触发  │
        └────┬───┘
             ↓
        ┌────────┐   卡片未答完 / 结果没齐   ┌──────────┐
        │  在跑  │ ────────────────────────→ │  停着等  │
        │        │ ←──────────────────────── │          │
        └────┬───┘   答完了 / 结果齐了        └─────┬────┘
             │                                      │
     ┌───────┼────────┐                             │ 用户叫停
     ↓       ↓        ↓                             ↓
 ┌──────┐┌──────┐┌────────┐                   ┌────────┐
 │ 完成 ││ 失败 ││ 被取消 │ ← 三个终态         │ 被取消 │
 └──────┘└──────┘└────────┘   不可逆          └────────┘
```

| 从 | 到 | 什么时候 | 日志上那一下 |
|---|---|---|---|
| 触发 | 在跑 | **立即**——不存在「先排着」这个状态。**触发就是[队列从空变成非空](design.md#待处理消息队列)那件事**，且此刻没有未终结的 Run | **Run 开始条目**，写明承接了哪些输入 |
| 在跑 | **在跑**（状态不变） | 又进来一条东西，[默认并入这个 Run](design.md#run-跑着的时候又进来一条东西) | **一条承接记录**——不落，[队列那道减法就算不出来](design.md#待处理消息队列) |
| 在跑 | 停着等 | 卡片落盘未答完（T4）· 动作发出去结果没齐（T6） | **那条等待记录悬着**：未答完的卡片、还没被结果填上的占位 |
| 停着等 | 在跑 | 这一批卡片全答完 · 结果齐了 · **插队解除了等待态** | **一条承接记录**（承接等到的那样东西） |
| 在跑 | 完成 | 模型这一轮没有动作了，**并且队列空**（T2′） | **终结条目**，终态＝完成 |
| 在跑 | 失败 | 压完还是装不下（T1′）· [守卫落了一条终态](design.md#循环探测的四种结局全落在已有的行上)（原地打转）· 上交给会话（§5.12） | **终结条目**，终态＝失败，**原因写明** |
| 在跑 / 停着等 | 被取消 | 用户叫停 | **先一条取消请求，再一条终结条目**（[§6.15](design.md#615-取消先落日志再发信号)）；强杀的那一种[由会话这一侧写](#19-用户强制停止三步闭环最后一步由会话这一侧收尾)，并标注「可能存在未收尾的外部效果」 |

**三个终态，没有第四个。「停着等」不是终态。**

> **「在跑 → 完成」那一行里的「并且队列空」不能省。**
> 少了它，一个刚到的用户消息或刚回来的后台结果**会被一次收束直接跨过去**——
> 而它明明已经在日志里了。

> **「已上交」不在这张图上。**那是[另一条线](design.md#512-run-的终态与非常态的终局是两条线)上的事——
> Run 该落终态就落终态，那件非常态自己往外走。

## 三、一次尝试的边界，与 Run 的状态无关

**这两件事画在同一张图上会互相污染，所以分开画。**

```text
Run：  触发 ─────────────── 在跑 ── 停着等 ── 在跑 ──────── 完成
                            └──尝试①──┘        └──尝试②──┘
                                   ↑                ↑
                            agent runtime 被取消        起一个新的
```

| | **Run 的状态** | **一次尝试** |
|---|---|---|
| 它是什么 | **逻辑的**——这次要做的事怎么样了 | **物理的**——一个 agent runtime 连续跑的那一段 |
| 谁看得见 | 用户、账单、排查的人 | **基本只有排查的人** |
| 换了会怎样 | 那是产品事件 | **用户无感**（[PF-004 I-2](design.md#agent-runtime-的四条不变式)） |
| 成本算谁的 | **账单单位是 Run**——[汇总按它算](design.md#成本两层缺哪一层都会算错) | **明细按它记**（崩溃前花了多少算多少），但它**不单独成一笔账** |
| 靠什么被指到 | 它自己的身份 | **(哪个 Run, 第几次)**，从[那条尝试开始记录](design.md#每一次尝试开始都要做四件事)派生，**不另存** |

**三条路开启新的一次尝试**：系统崩了 · 等人回来 · agent runtime 被取消后重起。
**三条路在方程眼里是同一件事**（[§5.7](design.md#57-一次尝试三条路通向重新算一遍)）。

## 四、十一个拓展点在这条流水线上站在哪

**每个[状态点](design.md#53-改日志的动作与纯派生的动作)的紧前与紧后各是一个位置。**

```text
  ┄┄┄┄┄┄┄ ● 尝试开始 ┄ 之后 ┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄  「之前」归 PF-015，唯一没开的
              │
  ┄ 之前 ┄┄┄ ● 消息落盘 ┄ 之后 ┄┄┄┄┄┄┄┄┄┄┄┄  每条消息都经过，不只是输入
              │                                 脱敏 · 注入检测 · 模态转文本
              │                                 ◆ 模态转换站在「之前」
  ┄ 之前 ┄┄┄ ● 压缩 ┄ 之后 ┄┄┄┄┄┄┄┄┄┄┄┄┄┄  整段进闭包：要不要压在里面判
              │                                 「之后」这一趟没压就不触发
           〔组装〕                              纯派生，前后推不出位置
              │
  ┄ 之前 ┄┄┄ ● 调模型 ┄ 之后 ┄┄┄┄┄┄┄┄┄┄┄┄┄  「之后」带收场维度：完整回复／失败
              │                                 ◆ 循环探测站在这儿（完整回复）
           有动作
              │
  ┄ 之前 ┄┄┄ ● 执行动作 ┄ 之后 ┄┄┄┄┄┄┄┄┄┄┄  「之后」带范围维度：这一个／这一批全齐
              │              ◆ 放行判断站在「之前」
              │              ◆ 卸载判定站在「之后」（这一个）
  ┄ 之前 ┄┄┄ ● 落终态 ┄ 之后

   ● = 状态点（改日志）   ┄ 之前／之后 ┄ = 拓展点   ◆ = 系统自带的挂件
```

**十二条边只有一条没开，等于十一个**——[完整清单与各自看得到什么见 §5.8](design.md#十一个位置是推出来的不是挑出来的)。

> **「落终态之前」的否决方向和别处相反**：调模型之前、执行动作之前的否决是「不许往前走」，
> **落终态之前的否决是「不许停下来」**——接着转。见
> [§5.8](design.md#干预力三档直接用-pf-000-的)。

| 拓展件挂了 | 怎么办 | 依据 |
|---|---|---|
| **只观察那一档**（L0） | **不影响**正在发生的事 | [PF-000 §5.3](../PF-000-occurrences-and-record-entries/design.md#53-干预力只长在瞬态这一半上) |
| **可改写那一档**（L1/L2 · 卸载判定） | **不影响**，但**留一笔「它没跑成」** | 同上 + [§6.10](design.md#610-能干预的拓展件必须留下结论) |
| **可否决那一档**（放行判断 · L3 · L4） | **当作否决**，**且这件事本身要可见** | fail-closed，同上 |

> **fail-closed 落在「落终态之前」是什么意思**：一件「没达成目标就别停」的挂件挂了，
> **按 fail-closed 就是否决停下**——这次不收束，接着转。
> **这正是要按位置想、不要按「拦住往前走」想的原因。**

## 五、这个循环从哪里出去

**「退出」有两个答案，因为有两层循环。**

| | 退出条件 | 出口几个 |
|---|---|---|
| **[Run](design.md#run)** | **落终态**（完成／失败／被取消）。**「完成」的判据是[队列空](design.md#待处理消息队列)** | **一个**。[§6.6：不许从别的地方落账](design.md#66-终态不可逆且只有一个出口) |
| **一次[尝试](design.md#执行尝试)**（真正在转的那个循环） | 落终态 · 停住等 · 被中断 | **三个** |

```text
一次尝试：
    反复算 f
      ├─ 算出「落终态」 ──→ 落一条终态事实，出去      Run 也结束了
      ├─ 算出「停住等」 ──→ 出去，把协程交还          Run 还活着
      └─ 崩了           ──→ 被踹出去                  Run 还活着
```

**外面还有一圈**，那一圈不在本 topic 里：什么事件把新的一次尝试带起来。
[三条路](#三一次尝试的边界与-run-的状态无关)——人回话了、结果回来了、新协程起好了。

> **还有一圈更外面的**：Run 都收束了，队列又非空了，**于是开下一个 Run**。
> **什么东西会让它非空**，归 [PF-014](../PF-014-inbound-intake-and-queueing/README.md)。

### 5.1 「停住等」不是空转

[状态转移表](design.md#56-状态转移表) 里 T4 与 T6 落回自己（T4 → T4、T6 → T6）。
**那不是叫你反复去问「好了没有」。**

> **它的意思是：这次尝试到此为止，把协程交还，什么都不占；
> 等外部事件把日志改了，再重新算一遍。**

**[等人不消耗计算资源](design.md#agent-runtime-的四条不变式)** 是硬要求——
反复去问就违反它了，而且那台机器可能一等就是三天。

| 读法 | 后果 |
|---|---|
| **反复去问「好了没有」** | 一个在等人的 Run 一直占着一个协程。**一千个这样的 Run 就是一千个协程在空耗** |
| **出去，等被叫醒**（正确） | 等着的 Run **一份计算资源都不占**；人回话那一刻，新的一次尝试才起来 |

### 5.2 方程不保证这个循环会停

**`f` 只回答「下一步是什么」，它没有「转够了」这个概念。**
真正让它停下来的有四样，各管一头：

| 谁 | 管什么 | 管不到什么 |
|---|---|---|
| **三个终态** | agent 自己说完事了、或出了没法继续的岔子 | agent 一直觉得还没完 |
| **[循环守卫 L3](design.md#59-循环守卫四级阶梯)** | **原地打转**——翻来覆去做同一件事 | **不打转地一直干新活** |
| **[T1′ 压完还是装不下](design.md#55-想这一步交进闭包拿回装得下的一份)** | 上下文空间耗尽 | 空间够用但钱烧光了 |
| **挂在[落终态之前](design.md#十一个位置是推出来的不是挑出来的)或[调模型之前](design.md#十一个位置是推出来的不是挑出来的)的拓展件** | **预算、轮次、时限**——「花到这个数就停」「转够二十轮就停」 | 没人挂的时候，没人管 |

> **最后一行是有意留给用户的。**「转到什么程度算不值得」是价值判断，不是状态事实
> （[L3 为什么不进 PF-011 的模型](design.md#哪些收束根本不进-pf-011-的模型)是同一条道理）。
> **系统不替租户定这个数，但把位置留好了。**

**所以「一个不打转、一直在干新活的 agent」不会被系统自己停下来**——
这是模型的真实边界，不是漏洞。要管，就在那两个位置挂一件。

### 5.3 「被取消」不在状态转移表里，因为它不是一行

三个终态里，**完成与失败是方程算出来的，被取消不是**。

> **取消是一件随时可能发生的外部事件**，它走的是[「外面进来的事」那条路](design.md#511-外面进来的事怎么到-agent-眼前)：
> 往日志里落一条，然后方程读到终态就停。

**所以它不是 T1–T8 的某一行**——它不从某个尾巴形状推出来，**它在任何状态下都可能来**。

| 取消时正在…… | 怎么收场 |
|---|---|
| 在想（组装、压缩、等模型回复） | 那一步的结果照落，**终态落「被取消」** |
| **等人**（T4，卡片没答完） | 卡片作废，**终态落「被取消」** |
| **等动作结果**（T6，结果没齐） | 见下 |

**那个还在外面跑的工具执行怎么办：**

**按 [PF-006「中断不是失败」](../PF-006-tools-and-skills/design.md#67-用户可以中断而中断不是失败)**——
它落一条正常的工具返回消息占位，语义是「**这次执行被用户手动中断了**」。
**不是失败**，因为失败是「这事没成」，中断是「这事不做了」。

> **与[崩溃那一种](design.md#先对账再进方程)分清楚**：
> 崩溃时后台执行算**失败**（系统没了它就没了）；
> 取消时系统还在，是用户主动停，所以算**中断**。

**停得掉的停，停不掉的记一笔。**产品上的要求是「**取消之后不再产生新的外部效果**」；
至于某个执行停不停得掉，是工具那一侧的能力。**停不掉的那些，结果回来照样落进日志**——
日志是[会话](design.md#只引用不拥有的对象)的，不是 Run 的。

### 5.4 终态之后再回来的东西，不让 Run 复活

**这是上一条掉出来的、最容易做错的一件事。**

日志[只增不改](design.md#会话日志)。Run 在时刻 t 落了终态，一个后台结果在 t+1 才回来——
**现在日志的尾巴是那条结果，不是终态**。

按 [T7](design.md#56-状态转移表)「结果齐了 → 回 T1（该想了）」的字面读法，**Run 就复活了**。

> **不会。终态是[吸收态](design.md#66-终态不可逆且只有一个出口)。**
> 方程读的不只是尾巴，还有 **[Run 的姿态](design.md#方程从日志里读什么)**——
> 它本来就在定义域里，**而「已经终态」是其中一种姿态**。

| | |
|---|---|
| **那条结果还落不落** | **落。**日志是会话的，它记录真实发生过的事 |
| **它改不改这个 Run 的终态** | **不改。**[终态不可逆](design.md#66-终态不可逆且只有一个出口) |
| **agent 会不会因此被叫醒** | **这个 Run 不会**——它的方程已经停了 |
| **那会不会有下一个 Run** | **会。**那条结果进了[队列](design.md#待处理消息队列)，**队列非空就要开下一个 Run** |
| **下一个 Run 看得见它吗** | **看得见**——它在同一条会话日志里 |

> **「看尾巴决定下一步」是简化说法。**准确的说法是：
> **先看这个 Run 有没有终态条目，有就停；没有，才看尾巴。**

> **中间那两行必须一起读。**「不复活**这一个**」与「**会有下一个**」是同一条规则的两半——
> 只读前一半，[两小时的构建就没人管了](#17-两小时的构建run-收束了结果才回来)；
> 只读后一半，一个已经结算完的 Run 会被重新拉起来。

## 六、这套机制自己出问题时

**机制本身也会出问题，不能假装它不会。**

| 情况 | 怎么办 | 为什么 |
|---|---|---|
| **日志写不下去** | **停住，别放过去**，并让这件事本身可见 | 放过去就是[假成功](../../foundation/observability-and-logging/requirements.md)。这与[卡片生成失败时仍然停住](../PF-008-human-in-the-loop/README.md)同形 |
| **一条终态落不下去** | 同上。**不许从别的出口补一条** | [只有一个出口](design.md#66-终态不可逆且只有一个出口)，开第二个出口，两边迟早不一致 |
| **对账对不出来**（尾巴是一种没见过的形状） | **停住并可见**，不猜 | 猜错了就是[凭空改写了历史](design.md#63-喂给-agent-的是日志原样)，而没人看得出来 |
| **一次尝试刚开始就又崩了** | 照常再来一次。**阶梯不重置**（[§6.5](design.md#65-新的尝试不重置循环阶梯)） | 不守这条，**崩得够勤就能无限打转** |
| **日志里有一条「有开始、没有配对结束」的尝试** | **当作正常，照常往下走** | 崩溃时来不及写结束条目是常态。[把它当错误的系统，在真崩溃面前会卡死](design.md#617-run-这一层的七条不变式)（I-15） |
| **强杀之后没有人写终结条目** | **不允许出现。**会话这一侧必须补上那条终结条目 | 否则那个 Run 永远未终结，[被反复起协程复活](design.md#只看日志该不该起一个-agent-runtime)——**强杀变成无限重启** |
| **一副被判定已死的协程又活了过来** | 它写什么都被拒——[序号更大的那次尝试才写得进去](design.md#同一个-run-同一时刻只有一副协程在推它) | 不拦，**同一件外部效果会被做两遍**，而且两次都「合法」 |
| **拓展件跑得很慢** | 它占着那个位置，Run 停在那儿——**这是一个可观察的状态，不是卡死** | 卡在哪个位置、哪一件、停了多久，照着日志就查得出 |
| **同一个位置挂了两件** | **这是常态，不是异常**——[位置不是能力标识](../PF-002-assets-settings-and-permissions/design.md#loop-extension)，两件各干各的 | 按[瀑布式](design.md#三种形态两种装得进一种拆两半)依次过，前一件的输出是后一件的输入；**每一件各留各的条目**，谁改了什么照着日志就查得出 |
