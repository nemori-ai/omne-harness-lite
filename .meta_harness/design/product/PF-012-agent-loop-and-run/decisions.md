# PF-012 决策与来源

产品设计允许 product manager 做判断，但**不允许发明没人拍过板的东西**。
本页把两者分开：哪些是产品负责人裁决的，哪些是 PM 自己推导的，各自依据在哪。

**当前没有待裁决项**；[第三节](#三待裁决)记着 rev 11 登记的那一项、rev 8 那两项与 rev 1 那五条的去向。

## 一、拍板记录

### 2026-09-29 · Agent runtime 装配与安全交接

**直接裁决**：[本轮交流](../PF-004-agent-definition-and-assembly/interviews/2026-09-29-agent-runtime-assembly.md)要求完整装配矩阵；显式 reload 可在同一 Run 的安全交接点采用同身份新定义并开启新尝试；旧模型回复中的未发起动作按新装配核对，已移除或绑定已变不自动执行，原因交回 agent。撤销、卸载与不可用只规定 Cordis 范式下合理的产品原则。

**本 topic 的落点**：补齐重装配安全交接、独立模型／工具执行与待续判断的关联；旧模型建议中尚未发起的动作按新装配核对，绑定已移除或已变则不自动执行。

**取代范围**：PF-004 I-3 的“同一 Run 内所有尝试永远同版”收窄为“普通恢复不静默升级”；PF-002 reload 的“永不重装配当前构成”改为按实际构成影响处理。历史记录保留当时语境；此处不扩张资产刷新范围或更换 AgentDefinition 身份。


### 2026-09-29 · 会话组成与函数输入持久化

**来源**：[PF-015 INT-001 至 INT-003](../PF-015-session-lifecycle-and-ownership/interviews/2026-09-29-session-composition-and-persistence.md)。产品负责人要求完整落盘上述讨论。区分执行进展事实、会话配置与当下条件；允许投影持久化，禁止独立推进权威；历史采用条件不能代替当前授权，纯求值不等于外部执行可重做。

**影响**：本 topic 的变化由其正文拥有；会话完整矩阵归 PF-015，定义装配归 PF-004，执行进展与日志投影归 PF-012。消费者 PF-006/010/013/014/020/021 继续沿自身的调用、组装、入站、工作区及 Job 边界；不把新默认值当成取消专用入口的显式初值要求。冻结规格与实现不在本次修改范围。

## 二、PM 推导

从已拍板内容推出的判断，附可核对的推理链。

### rev 1 立下、rev 2 继续成立的

| 结论 | 从哪几条推出 | 推理 |
|---|---|---|
| **Run 与 Agent Loop 必须是两个概念** | 「run 是数据 / 治理，agent-loop 是执行逻辑」 | 合成一个，就会写出「Run 对象自己知道怎么往下走」这种设计——**而那个「知道」活在进程里，停机就没了**。分开之后，一个负责**被写下来**，一个负责**被重新算出来** |
| **改日志的动作 vs 纯派生的动作，是这套模型里最要紧的一条分界** | 「记录是唯一真相来源」+ 三个动作的叠加 | **纯派生的动作重算一定得到同样结果**，所以不必给它建检查点。由此得到一条实现判据：**要不要给一个动作建状态点，看它改不改日志** |
| **组装是这一圈里唯一纯派生的动作** | 上一条 + 各动作的性质 | 压缩追加摘要、调模型追加回复、执行追加结果——**只有组装什么都不留**。这条性质在 rev 2 里第二次兑现价值：**那个位置也因此开不了拓展点** |
| **不组装就不知道超没超** | 产品负责人对压缩位置的纠正 + [PF-007 的常驻预算](../PF-007-meta-capabilities/design.md#54-十三个槽位是预算的地板也是它的天花板意义) | 占位置的不只是对话——系统提示词、工具定义、十三扇门都占 |
| **压完还超 → 落终态失败，不循环压** | 常驻部分压不动 | 压缩只碰得到会话上下文那一块。**光是固定部分就超了预算，那是装配的问题**。原因要写明是固定部分超限，**否则运维会一直盯着对话长度查**。**rev 2 补了另一半：同时上交给会话**（见下） |
| **L3 落「失败」，不新增终态** | 「终态就是失败」这条裁决的推广 | 终态越少越好，所有消费方（读面、统计、告警、计费）都少一种情形要处理 |
| **loop 之外的事必须先落进日志，不能攒在内存队列里** | 「组装是纯派生的」+「一圈要组装两次」 | 队列被第一次取空，第二次拼不出同样的东西，**两次组装结果不同，方程当场失效**。[PF-010 从另一头写了同一条](../PF-010-context-management-and-assembly/design.md#要求四先落盘再组装) |
| **唯一终态落账点，且先确保会话存在** | legacy 的机制，本 topic 采纳 | 没有这一条，**第一轮就死掉的会话会变成幽灵** |
| **不必额外告知 agent 动作空间的差异** | [替换件](../PF-006-tools-and-skills/design.md#替换件)已经铺好了这条路 | 它调一个已经没了的能力，会拿到「用不了 + 原因」。**这条路已经铺好，不用再铺一条** |
| **新的尝试不重置循环阶梯** | legacy 的 INV + 「检测状态从日志派生」 | 不守这条，**agent 只要崩得够勤就能无限打转，而每次崩溃看起来都像意外** |
| **喂给 agent 的是日志原样，零追加零注入** | legacy 的 INV-RD-3 | 多塞一句进历史里**改变了检测窗口**——多出来的那条可能被当成新的工作输入，把阶梯洗白 |
| **日志先于可见** | legacy 的 INV-LG-2，本 topic 升为通则 | 「图里看得见、日志里没痕迹」的东西**一次重启就凭空消失** |
| **L0 观测永不可关** | 它只观测、不干预 | 关掉它，**「agent 在打转」这件事就再也没人知道** |

### rev 2 新推的

| 结论 | 从哪几条推出 | 推理 |
|---|---|---|
| **Run 必须是成本、失败、收束三样的同一个归属单位** | [UL-run](../../ubiquitous_language/terms/agent-runtime-loop.md#ul-run--运行--run)：「成本、失败与收束的归属单位」 | 三样回答的是**同一个问题**——「这一次要做的事，怎么样了」。分给不同的单位，这个问题就要跨三个对象拼，**而它们边界不一样，拼出来的答案对不上**。最具体的错法：**成本归实例、失败归 Run**——一次 Run 换过两个 agent runtime，成本两笔而失败一笔，**「这次失败的任务花了多少钱」永远答不出来** |
| **崩溃恢复、等人回来、 agent runtime 被取消后重起，是同一件事** | [UL-run-attempt](../../ubiquitous_language/terms/agent-runtime-loop.md#ul-run-attempt--执行尝试--run-attempt)（「重试、换一个 agent runtime 、崩溃后恢复，各是一次尝试」）+ [PF-004 I-7](../PF-004-agent-definition-and-assembly/design.md#61-不变式)（等人不消耗计算资源，实例可回收） | **在方程眼里三条路一模一样**：日志还在，agent runtime 不在了（或换了），重新算一遍 `f`。**rev 1 只把恢复当成一条异常路径，那是错的**——等人是产品有意设计的路（PF-008），而等人之后接着跑走的就是这条。**它是常态** |
| **等人之后的新尝试不必对账**（**已作废**，见 [rev 10 新推的](#rev-10-新推的)第三行） | 上一条 + 对账表 | 对账补的是「断在半路的尾巴」。**等人那一种是正常停住的**，尾巴本来就是方程认得的形状 |
| **方程的定义域 = 效力为「依据」的那些条目** | [PF-000 §5.2](../PF-000-occurrences-and-record-entries/design.md#52-那个判断两条独立充分条件)：「只由第②条成立的条目，不进方程的定义域」 | rev 1 把「消息历史 / 姿态 / 悬着的东西」三类当成定义域的**定义**，那是**列举**。**判据在 PF-000**——不这么写，下一个人会从留痕条目里取状态，而那正是 PF-000 把两条分开记要挡的事 |
| **拓展点只能通过改日志起作用** | 「`f` 是纯的」+「记录是唯一真相来源」 | 能不留痕地改变下一步，**重算就得到不同结果，`f` 当场不纯**，整套恢复机制塌掉 |
| **拓展点本身不必是纯的，但重算时不重跑它** | 上一条 + 调模型的先例 | **模型也不纯**，但它的输出被追加进日志了，所以恢复时读日志里那条回复就行。**拓展点同构**。不点破这一条，实现者会以为「它是个函数，重跑一遍就行」 |
| **拓展点不能自己指定跳到哪一步** | 「转移由状态转移表算」 | L3 看起来像直接结束 Run，**实际上它做的是往日志里落一条终态事实**，而方程读到终态就停。**同一条规矩，没有例外** |
| **拓展点的干预力直接用 [PF-000 三档](../PF-000-occurrences-and-record-entries/design.md#53-干预力只长在瞬态这一半上)** | PF-000：「干预全部发生在『成为条目之前』的那一刻」 | **拓展点就是那一刻**。所以不必另立一套取值，也不必另定「它挂了怎么办」——**「可否决那一档挂了当否决」是 PF-000 的原话** |
| **「可改写」那一档挂了要留一笔** | PF-000 只写了另外两档 | 改写没发生，事情照常；但不留那一笔，**排查的人看到一条没被卸载的大结果，分不出是判定说不用卸载，还是判定挂了**。**这一条是补的，PF-000 没说** |
| ~~**开一个新拓展点的判据：夹在两个状态点之间**~~ | 「组装是纯派生的」+「一圈要组装两次」 | 最具体的反例：**「组装之后、调模型之前」开不了拓展点**——中间插一个能改东西的，第二次就拼不出同样的东西。**rev 3 推翻**：判据改成[「状态点的紧前或紧后」](design.md#十一个位置是推出来的不是挑出来的)，而那个反例的推理本身就是错的——**「纯派生」说的是同一份日志组装两次结果相同**，压缩前后的两次本来就该不同。**调模型之前已开**，见下 |
| ~~**本版只开三个位置，空着的不预开**~~ | [根约定](../../../AGENTS.md)：不为想象中的未来预埋框架 | 「输入落盘之后」「收尾之前」现在都没有消费者，**没有消费者的位置就是框架**。**rev 3 推翻**：产品负责人要求拓展点必须**完备**，租户与组织超管要能在任何一处插手。**而且原推理有一处判断失当**——位置不是新机制，[它就是状态点的两条边](design.md#十一个位置是推出来的不是挑出来的)，**开齐十个没有多造一样东西** |
| ~~**拓展点不是[资产](../../ubiquitous_language/terms/capabilities-and-composition.md#ul-asset--资产--asset)**~~ | 「恰有七类，这七类是穷尽的」是已拍板的（PF-001 rev 6） | 资产约束 **agent 由什么组装而成**；拓展点是 **loop 自己的结构**。并进去就得把「七类」改成八类，**而那要推翻一条已拍板的内容**。**rev 3：产品负责人在知情的前提下选了推翻**——[拓展件是第八类资产](../PF-002-assets-settings-and-permissions/design.md#loop-extension)。**这条推导本身没做错，是前提被改了**；另外它当时把**拓展点**和**拓展件**混成了一个词，rev 3 分开了 |
| **Run 的终态与非常态的终局是两条线** | [PF-011「落终局的是那件非常态，不是承接它的那一层」](../PF-011-off-nominal-handling/design.md#终局) + [PF-011 §5.4 会话那一层](../PF-011-off-nominal-handling/design.md#54-各层的四要素) + [§6.2 上交即打断](../PF-011-off-nominal-handling/design.md#62-上交即打断) | 会话那一层能做的是「重算可用性让**下次运行**换个动作空间」——**那是下一个 Run 的事，救不活这一个**；而运行层交出去就停住，Run 的主路径确定走不完了。**所以 Run 当场落终态，那件非常态继续往外交**。不写明，实现者会写出「Run 失败了处置也就结束了」，**于是会话层与租户层的处置永远不会发生** |
| **上交条目与终态条目是两条，不是一件事的多条** | [PF-000 §5.4](../PF-000-occurrences-and-record-entries/design.md#54-一件事什么时候产出不止一条条目)：产出多条只有两个原因 | 一个说「这件非常态交给会话了」，一个说「这个 Run 失败了」——**它们是两件事**，两个原因一个都不沾 |
| **循环守卫 L3 不进 PF-011 的模型** | [PF-011 §4 非常态](../PF-011-off-nominal-handling/design.md#非常态)：「某一层此刻不在它的主路径上」 | agent 打转时，**没有哪一层偏离了主路径**：agent 的一步每一步都完整走完，运行也正在「一步步走」。**「转到什么程度算不值得」是价值判断，不是状态事实**，而 PF-011 处置的是状态事实。**这解释了为什么 L3 落失败而不是一路上交**——上交给会话和租户，它们手上也没有「一条能走通的路」 |
| **压完还超，除了落终态还要上交** | [PF-011 §5.6](../PF-011-off-nominal-handling/design.md#56-了结得了吗看缺的那样东西在谁手上)：「上下文满了 → 空间 → 压缩就在这一层 → 本层了结」 | 压缩就在运行这一层，**压不动就是手段用尽**——按那条判据该上交给会话。**rev 1 只写了「终局失败」，漏了上交那一半** |
| **「已上交」不是 Run 的一种状态** | 上面两条 | 三个终态不变。**已上交说的是另一条线上的事**，画进 Run 的状态机会让两条线互相污染 |

### rev 3 新推的

| 结论 | 从哪几条推出 | 推理 |
|---|---|---|
| **位置 = 状态点 × {紧前, 紧后}，因此恰好十个** | 「拓展点按相对状态点的位置命名」这条裁决 + [六个状态点](design.md#53-改日志的动作与纯派生的动作) | 一旦按位置命名，**位置就不再是挑出来的，是推出来的**：每个状态点两条边，六个状态点十二条边，减去[归 PF-015 与 PF-014 的那两条](design.md#十一个位置是推出来的不是挑出来的)，**恰好十个**。**这比「我挑了几个」强的地方在于**：将来漏没漏，问的是「状态点漏没漏」，而那是个能查的问题 |
| **拓展件不是状态点，所以位置不会递归** | 「[要不要建状态点，看它改不改日志](design.md#53-改日志的动作与纯派生的动作)」 | 这条判据单看会得出「拓展件改日志 ⇒ 它是状态点」，**那样就有「拓展点的拓展点」，位置永远数不完**。**真正的判据是日志尾巴的形状会不会变**——拓展件追加的条目不改变形状，[状态转移表](design.md#56-状态转移表)读到的还是同一个。**它要是能改变形状，就等于自己指定跳到哪一步，而那是被禁的** |
| **「调模型之后」带收场维度、「执行动作之后」带范围维度，但维度不是新位置** | 五家调研：DSH 把「请求失败」与「拿到回复」分成两个事件；LangChain 的 `after_agent` 要等一批齐 | 同一个位置上**日志尾巴的形状不止一种**。一个管打转的挂件面对「请求失败」无话可说，**硬让它跑一遍只会得到一个没有依据的判断**；而「这一批的总量超了预算」只有等齐了才知道。**维度是筛选条件，不是又多出来的位置**——它不新增边 |
| **「落终态之前」的「可否决」否决的是「停下来」** | `/goal` 的检验 + [干预力三档](design.md#干预力三档直接用-pf-000-的) | 「可否决」否决的是**它站的那个状态点**，而那儿站的状态点是**落终态**。调模型之前、执行动作之前的否决＝不许往前走，**这儿的否决＝不许停**。不写明，实现者会按「拦住往前走」去做，**而那儿最有价值的那类挂件恰恰是「没干完就别停」** |
| **同一个位置，同一次经过只跑一轮** | 「调模型之前」开了之后必然出现的问题 + [压缩那一圈的先例](design.md#55-想这一步交进闭包拿回装得下的一份) | 那儿的挂件改了日志，攒好的请求就过期了，得重新组装。**若重新组装又回到同一个位置，一个爱改日志的挂件就能把自己无限触发下去，loop 永远发不出请求**。压缩已经立过同样的规矩：压完再量一次，还超就上交，**不是再压一轮** |
| **环绕式拆两半，只收「给结论、由 loop 执行」那一半** | 「`f` 是纯的」+ 五家调研 | 判据是**中间那几次经不经过日志**。DSH 的 `agent/request-error` 返回一个重试动作、由 loop 照办——**那本质就是点式**；LangChain 的 wrap 自己 `for attempt in range(3)`，中间两次不经过日志，[重算拿不回同一个下一步](design.md#第二条是硬的因为它护着-f-的纯性)。**拆的是形态不是功能**：重试本系统照做，只是每次都在日志里留一条 |
| **瀑布式就是「同一位置挂多个」的求值办法** | 「同一个位置可以实现多种不同的功能」这条裁决 + DSH 的做法 | 一旦一个位置能挂多个，就必须回答「它们什么关系」。**DSH 已经给了一个现成且自洽的答案**：依次过，前一件的输出是后一件的输入。不采用它就得自己发明一个，**而没有理由认为自己发明的会更好** |
| **系统自带的挂件不享受特权** | 「让用户能扩展或覆盖策略」这条裁决 | 循环探测、放行判断、卸载判定走的是同一套位置与同一套干预力。**若自带的能做外来挂件做不到的事，说明位置的能力没被定清楚**，而下一个要做同样事情的租户就会卡住 |
| **挂件自己那次模型调用，算进它插手的那个 Run** | [Run 是成本的归属单位](design.md#run-是三样东西的归属单位)的检验句 | 检验句是**「这次失败的任务花了多少钱」**。一件判断「算不算干完了」的挂件本身要调模型，**那是为这次任务花的**，不算进去那个数就不全 |
| **Run 不是成本唯一的一级，不属于任何 Run 的调用归会话** | `/btw` 的检验 | **旁路提问**读得到日志、问和答都不进日志、也不改变下一步——它花钱、会失败，**却不属于任何一次尝试，也不属于任何 Run**。不点破，「Run 是成本的归属单位」会被读成「所有成本都归 Run」，**于是这笔钱要么无家可归，要么被硬塞进一个跟它无关的 Run** |
| **`/btw` 一个拓展点都不需要，而这是对的** | `/btw` 的检验 | 拓展点是**能改下一步**的位置，**旁路提问按定义不改下一步**。它要的东西——只读日志、不进日志的一条旁路线程——**都不在 loop 上**。**检验的价值正在这里**：一个产品功能落不进拓展点，不一定说明拓展点不够，也可能说明它本来就不该在这儿 |

### rev 3 后续追加（同日，检验与提问带出来的）

| 结论 | 从哪几条推出 | 推理 |
|---|---|---|
| **位置从十个变十一个，完备性论证形状不变** | 「输入落盘之前要开」这条裁决 | 论证一直是「状态点 × 两条边」，**变的只是减去几条**。rev 3 初稿减两条（尝试开始之前归 PF-015、输入落盘之前归 PF-014），现在只减一条。**这正是「推出来的清单」比「挑出来的清单」强的地方**——加一个位置不必重新论证，只要说明为什么不再减它 |
| **位置不编号** | 「按位置命名」那条裁决 + 本轮位置数从十变十一 | 圈数字是**第二套命名**，与那条裁决冲突；而且**位置数一变，全篇编号错位**——本轮就发生了。位置名本身够短、自解释、永不错位 |
| **「输入落盘之前」必须在落盘之前，不能挪到之后** | [日志只增不改](design.md#会话日志) | 脱敏、注入拦截要挡的是**「进来」这个动作本身**。落盘之后再脱敏，**原文已经永久留在那儿了**；拦下的注入若已落盘，等于承认它进过方程的定义域。**落盘之后的位置一个都办不了这件事** |
| **一次尝试的三个出口，正好是[一次尝试的边界](design.md#57-一次尝试三条路通向重新算一遍)** | §5.7 的三条路 + 转移表的 T4/T6 | §5.7 讲「三条路通向新尝试」，转移表讲「停住」，**两节各讲各的，中间少一句话**。补上之后这两节缝起来了：**出去的三个口，对应进来的三条路** |
| **T4/T6 的「停住」是出口，不是反复问** | [PF-004 I-7](../PF-004-agent-definition-and-assembly/design.md#61-不变式)：等人不消耗计算资源 | 转移表把 T4 写成落回 T4，意思是「日志没变，重算还是这个结果」，**不是叫你不停地算**。按字面实现就是一个在等人的 Run 一直占着一个协程——**一千个这样的 Run 就是一千副 agent runtime 空耗**，直接违反那条不变式 |
| **方程不保证终止，靠四样兜底** | 终态 + L3 + T1c + 拓展件 | **`f` 只回答「下一步是什么」，没有「转够了」这个概念**。L3 只管原地打转，**不打转地一直干新活没有任何东西会停它**。这不是要新增机制——那是价值判断，[与 L3 为什么不进 PF-011 的模型同一条道理](design.md#哪些收束根本不进-pf-011-的模型)；**系统不替租户定这个数，但把位置留好了** |
| **「被取消」没有对应的转移行** | 三个终态 + [外面进来的事那条路](design.md#511-外面进来的事怎么到-agent-眼前) | 完成与失败是方程**算出来的**，取消是**随时可能到的外部事件**——它不从某个尾巴形状推出来。不点破，读者会在表里找它，找不到就以为漏了 |
| **取消时在途的工具执行算「中断」，不算「失败」** | [PF-006 §6.7](../PF-006-tools-and-skills/design.md#67-用户可以中断而中断不是失败) | PF-006 已经定了「中断不是失败」并给了占位形状，**这里只是把它用到 Run 级取消上**。**与崩溃那一种要分清**：崩溃时后台执行算失败（系统没了它就没了），取消时系统还在、是用户主动停 |
| **终态是吸收态：之后回来的东西不让 Run 复活** | [§6.6 终态不可逆](design.md#66-终态不可逆且只有一个出口) + [Run 的姿态在定义域里](design.md#方程从日志里读什么) | **这是核 `/goal` 与取消语义时撞出来的真缺口**。日志只增，终态落在时刻 t、后台结果 t+1 才回来，**尾巴就不是终态了**；照 T7 的字面读法 Run 会复活。**答案其实已经在正文里**——「Run 的姿态」本来就在定义域里——**但「看尾巴决定下一步」这句简化说法把它盖住了**。[§5.11 明说「结果回来了而 Run 可能早走远了」](design.md#511-外面进来的事怎么到-agent-眼前)，所以这不是假想 |

### rev 4 新推的

| 结论 | 从哪几条推出 | 推理 |
|---|---|---|
| **[待处理消息队列](design.md#待处理消息队列)是[会话日志](design.md#会话日志)的一个投影，不是另一份存储** | 「loop 持续消费消息队列」这条裁决 + [§5.11「收进来是改日志的动作，组装只负责拼」](design.md#511-外面进来的事怎么到-agent-眼前) | 裁决只说了有这么一个队列，**没说它存在哪**。而 rev 1 起就有一条硬规矩：**攒在内存队列里的东西，组装一取就没了，方程当场失效**；再加上[停机是主路径的一部分](design.md#57-一次尝试三条路通向重新算一遍)，另存一份就会丢消息。**「日志里还没被消费过的那一段」是唯一同时满足这两条的形状**——持久、可恢复、不会与日志分叉，**三条性质一条都不用额外设计** |
| **「触发」与「收束」不是两个独立概念，是同一条规则的两端** | Run 的新定义 | 边界既然由「队列空不空」划定，**触发就是让队列从空变非空的那件事，收束就是队列重新变空**。此前两者各有一套说法，**于是「什么会发起一次 Run」要被穷举成一张表**；现在它塌成一句话。**穷举不是消失了，是换了对象**——要穷举的变成「什么东西会进队列」，归 [PF-014](../PF-014-inbound-intake-and-queueing/README.md) |
| **PF-012 与 PF-014 的那处冲突，是被新定义消解的，不是被裁决的** | 同上 | 旧模型里 Run 结束之后有东西回来，**必须回答「要不要把它叫醒」**——而叫醒一个已经停了的方程讲不通。新定义下这个问题**不成立**：东西进队列，队列非空，loop 本来就还没走到退出那一步；真已经退出了，那说明退出时队列是空的，**而它现在非空——开下一个 Run**。**两个 topic 原来各写了一半，现在是同一句话** |
| **不设第二种优先级：插队是唯一的加急通道** | 「默认先到先处理 + 插队排最前面」这条裁决 | 产品负责人先前提过「**队列未必是单层，可能是多级优先队列**」，**后一条裁决把它收窄了**：只区分「排队」与「插队」两档。PM 核过是否还需要第三档——**没有一个场景要得到它**：「工具结果比用户消息急」这类分级，**每多一级就多一处要解释的语义**，而「我现在就要」这个需求已经被插队全覆盖。**一个机制，不是两个** |
| **新增 [T2′](design.md#56-状态转移表)：模型没给动作时，先看队列空不空** | Run 的新定义 | 旧表里「模型没给动作」直接落**完成**。新定义下**那是错的**——队列非空就还没做完。**所以这一步必须分叉**：非空回 T1 接着做，空了才落完成。**它不是新增机制，是把「完成」的判据写准**：完成＝模型没话说**且**没有待处理的 |
| **「输入落盘之前」本来就该是「消息落盘之前」** | rev 3 给那个位置写的三条理由 | 那三条理由——**脱敏、敏感识别、注入检测都要挡「进来」这个动作本身**——**对模型吐出来的内容、对工具交回来的结果一模一样成立**。按 rev 3 的写法，**模型生成的内容没有任何位置可以脱敏**，那是一个洞。**扩大这个位置不是为了给转换件找个家，是它本来就该这么大** |
| **模态转换必须落在这个位置，三条替代路线各自都不行** | [组装是纯派生的](design.md#53-改日志的动作与纯派生的动作) + [日志只增不改](design.md#会话日志) + [一圈要组装两次](design.md#55-想这一步交进闭包拿回装得下的一份) | **组装时转**：一圈两次组装结果不同，方程当场失效。**调模型之前转**：那时已经量过了，**量的是原图、发的是文本**，压缩判断跟着错。**落盘之后转**：要么改已写下的记录，要么另存一份，**同一张图两处登记迟早分叉**。而落在落盘之前，三个问题一个都不存在，且**原始块与文本在同一个块里**——后面组装时按模型收不收得下取对应字段，**不需要任何选择规则** |
| **系统必须自带一件转换件，[三件因此变四件](design.md#系统自带的几件各站在哪)** | 「模态转文本」这条裁决 + 产品承诺 | 没有自带件，**一张图发给收不下图的模型就只能卡在那儿**——[这正是同类产品上最常见的那类投诉](../PF-013-model-profiles-and-invocation/interviews/2026-09-20-product-research.md)，而本系统承诺「换个模型接着聊」。**但它不因此特殊**：走同一套位置、同一套干预力，租户要换一件更好的实现，挂上去就是（**这半句对转换件已不成立**：PF-013 裁决 23、30 定了它本版不是资产、组织与租户换不了，正文 rev 13 已收窄，见[「rev 13 新推的」](#rev-13-新推的)）。**顺带把那个标题里的数字去掉**——数目会变，与[位置不编号](design.md#按位置命名不按功能命名)是同一条道理 |
| **转换件的契约归 [PF-013](../PF-013-model-profiles-and-invocation/README.md)，不是 PF-014，也不是两边各一半** | 「模态」这个概念的归属 | 契约的内容是**「声明能处理哪些模态」**——**而「有哪些模态、哪个模型收得下哪些」是大语言模型域定的**。PF-014 管的是**那一刻具体看得到什么**（受理面），不定模态本身。**此前写的「两边各定一半」是没把归属想清楚的措辞**，本版改准 |

| **「停机」的判据是「运行时与它所服务的持久事物失去连续性」** | 2026-09-20 的裁决 | 产品负责人只说了「**未必是单纯的系统停止运行了**」，**没有给判据**。而 §5.7 那三条路本来就**各自都不是机器断电**：等人时 agent runtime 被取消、 agent runtime 被取消后重起，**两条都在系统好端端跑着的时候发生**。**唯一能同时盖住这三条的说法就是「失去连续性」**——写成别的都会漏掉其中一条。**由此还掉出一句**：[「停住等」是一次计划内的停机](design.md#停机不是机器断电是失去连续性)，不是异常 |
| **四个运行时的分界判据是「在外面留下了不可逆的东西没有」** | 四层各自已定的处置 | **四条处置不是并列的四条规则**：run 重算、实例重装配，**是因为它们没在外面留下东西**；工具执行不重来、模型调用看首 token，**是因为它们留下了**。**这一条不是新主张**——[外部输出不因被运行时调用就变得可逆](../../../agents/roles/engineering-taste.md)那条品味早就定了，**本节只是把它在四个域上的落点并排摆出来**。**并排摆本身有用**：「为什么 run 能重算而工具执行不能」这个问题，**在任何一个单独的 topic 里都答不完整** |

### rev 5 新推的

| 结论 | 从哪几条推出 | 推理 |
|---|---|---|
| **[段](design.md#光有点不够还要说得清点与点之间)：`f` 的取值保持不变的那一段连续执行，边界就是状态点** | 「进闭包本质上也是一个 `await` 点」这条裁决 | 裁决把「`await`」这个词摆上了台面，而**点本身说不清点与点之间**——那一截在干什么、能不能中途停、停了从哪儿接上，三个问题此前都没有正文回答。**「取值不变的那一截」是唯一同时答完这三个的说法**：段内断掉，重新算 `f` 还指向同一个段，所以**它就是可以重做的最小单位**；而每一个 `await` 恰好落在段的末尾，**否则那个段就没法重做** |
| **判据从「看它改不改日志」换成「看跑完它 `f` 的取值变不变」** | 段的定义 + [拓展件只能靠改日志起作用](design.md#69-拓展件只能靠改日志起作用) | 旧判据有一个现成的反例：**拓展件改日志，但它不是状态点**。正文此前一直为这件事单开一段解释（「尾巴的形状没变」），**那说明判据本身没说准**。换成新判据之后，那段解释降格成**新判据的一个实例**，不再是例外 |
| **一件事该不该进方程，看它里面有没有 `await`** | 同上 | **有 `await` → 协程要在那里交还控制权 → 它必然是段的边界 → 方程必须知道**；**没有 → 它跑在段内，`f` 的取值从头到尾没变 → 方程不必知道**。**这条判据一次判完了三件事**：压缩内部要调模型生成摘要，**有**，进方程；循环探测、卸载判定都是纯本地判断，**没有**，做成挂件。**产品负责人的裁决与这条判据给出的答案完全一致** |
| **循环探测出表不丢任何产品行为** | 「做成挂件」这条裁决 + [干预力三档](design.md#干预力三档直接用-pf-000-的) | 它的四种结局各自往日志里落一样东西，**而改完之后的尾巴形状表里本来就有**：无事→尾巴没变；写干预消息→队列非空→T1；判定转不动了→落一条终态事实→方程读到终态就收；判定要问人→落一张卡片→T4。**四种结局，四个已有的形状，一行转移都不用补**。**留在表里它占四行，拿出来它一行不占** |
| **[「消息落盘」是六个状态点里唯一一个条件性的](design.md#消息落盘是唯一一个条件性的状态点)** | 段的定义 + [事件先落进日志](design.md#511-外面进来的事怎么到-agent-眼前) | 别的五个都是这个 Run 自己提交的，只有它是外面提交的。**而它只在「队列从空变非空」那一刻才改变 `f` 的取值**——队列本来就非空，再落一条，`f` 还是「该想了」。**这恰好就是[触发](../../ubiquitous_language/terms/agent-runtime-loop.md#ul-trigger--触发--trigger)那个概念**，也解释了为什么「插队解除等待态」与「新消息唤醒一个停着的 Run」是同一件事 |
| **「量一量」从方程里消失，方程不再需要懂上下文预算** | 「判定在闭包内做」这条裁决 | 判定进了闭包，方程就只剩「装得下 / 装不下」两个回执。**代价要一并记下**：闭包内部压了几轮、丢了多少，**外面看不见**，得靠它自己往外说。**换来的是换一整套压缩策略、转移表一个字不动** |

### rev 8 新推的

**先是产品负责人要的那份可行性分析**（2026-09-23 交回，未被否决）。正文只留了结论与约束，推理链在这里：

| 步 | 推理 |
|---|---|
| **1. 操作系统里阻塞调用的形状** | 线程挂起、内核保存它的续体、事件到了再恢复。**续体活在内存里，进程死了就没了** |
| **2. 协程活着时，照搬** | 拓展件的「等」挂起那一段执行，不轮询、不占资源；**主流程已经在「等模型」「等工具」「等人」三处用它**，拓展件用它只是第四处调用点——**一个原语，不是一套新机制** |
| **3. 协程死了，照搬不了** | 本系统的实现语言**没有可落盘的续体**，停在半路的那段执行存不下来。**但本 topic 早就选了另一条路：[日志是唯一真相，新尝试从日志重算](design.md#52-会话日志是唯一的真相来源)**。所以等待的耐久不靠续体，靠两条日志事实：**那张卡片**（哪一件、在哪、为什么动作，悬着就是在等——[§5.13 本来就要求等待是一条显式记录，卡片就是它](design.md#等待必须是一条显式的记录)）与**人的答复** |
| **4. 回来靠回放** | 新尝试读到卡片无答复 → 停在等人；读到答复 → 回到那个位置、那一件，**从头重跑到它停下的那一处**，途中每一次等都按日志交回，到出卡那一处拿到记下的答复、不再出卡。**这正是 [§5.3「段是可以重做的最小单位」](design.md#光有点不够还要说得清点与点之间)在拓展件上的兑现**：不是接着做，是重做一遍，重做时已记下的等待直接交回 |
| **5. 回放的前提** | 那一件停下之前的效果**全都经过日志**（它调模型、它出卡，都记下）——这是 [§5.8「挂件不必纯，但效果必须记下」](design.md#第二条是硬的因为它护着-f-的纯性)已有的规矩；**作者要额外守的只有一条：等待前后不能靠内存里的变量传东西**。「新尝试里不重跑挂件」由此精化为：**有结论的不重跑；挂起中的回放到挂起点** |
| **6. 一批先判完再执行** | M 个动作各起一段执行跑瀑布，谁到等人谁挂起；**所有的要么有结论要么挂起时**，Run 才进等人，卡片成批落。操作系统里多线程各自阻塞在读上、进程整体算「等待中」，是同一个形状。**顺序地判做不到成批**——第一个停下，后面的还没判——所以必须并行 |
| **7. 取消** | [I-7](design.md#agent-runtime-的四条不变式)「等人时协程可被取消」照旧：**取消杀的是那几段执行，卡片与记录留在日志与池子里**，下一次尝试接着等 |
| **8. 代价** | agent runtime 要有一种「回放」跑法（原语按日志交回而不真做）；拓展件作者要被明确告知回放约束；与工具等待态（[PF-008 左列](../PF-008-human-in-the-loop/design.md#等待态的两个维度)）是同形的两处，**本 topic 不合并两条等待** |

### rev 9 新推的

| 结论 | 从哪几条推出 | 推理 |
|---|---|---|
| **模型回复被否决，译成一次「调模型失败」，走已有的重试；这不是新机制** | 「run 失败……顶多模型回复这边做退避重试」+ [调模型之后带收场维度](design.md#两个位置带维度) + [PF-013 重试站在已有位置上](../PF-013-model-profiles-and-invocation/design.md#512-重试站在一个已经存在的位置上) | 回复没落盘，日志里这次调用就是**没拿到回复**——尾巴与一次真的调用失败**一模一样**，方程分不出、也不必分。所以只要把这次调用的收场记成「失败」、原因写「回复在落盘前被某一件否决」，**调模型之后（收场＝失败）上站着的重试挂件就照常接手**：退避、再来、[试尽](../PF-013-model-profiles-and-invocation/design.md#什么时候算试尽)就上交、Run 落失败。**翻译得通，一条新转移都不用加**；PF-013 rev 5 对「转换件转坏了模型回复」已经这样写 |
| **工具结果被否决，不重试，Run 直接失败** | 同一条裁决 + [工具执行停了不重来](design.md#三个运行时停机之后各算什么) | 重来就是再跑一次工具，**外面的事可能做第二遍**，而我们没有补偿；落替身又被裁决排除。**只剩 Run 失败** |
| **不可用＝视作卸载，报错＝按类型的策略；两者分开是因为「在不在」是事实、「这一次该怎么算」是结论** | 「把拓展件视作 plugin」这条裁决 + 本项目以 Cordis 为内核：插件的依赖不在，它就不被装载，依赖回来再装载 | 依赖不在时它**根本没跑**，把这读成「它判了否决」是替一件没跑的东西编了一个结论；**只有跑了、报了错**，才有「这一次的结论该怎么算」，而那取决于它是什么类的东西（转换件报错是否决、打转保护报错也许只该留一笔）。所以策略按类型给，**「可否决挂了当否决」降为可否决一档的默认** |

| **转换件：不可用＝没装（照原样落盘），报错＝否决** | 上两条 + 2026-09-23「处理失败直接报错，不能落盘」+ [PF-013 没有登记转换件不是失败](../PF-013-model-profiles-and-invocation/design.md#转换件) | 不可用被视作卸载，那个键上就等于没人登记，走 PF-013 已有的那条；**「处理失败」说的是跑起来报了错**，那正是转换件这一类的策略：否决 |
| **一件把关用的拓展件依赖挂了，这一关这一次就没了，必须看得见** | 不可用＝卸载 | 这是裁决的直接后果，不是漏洞；**「不在就不许跑」要不要有、放在哪，正文未述**——它牵涉装配（PF-004）与拓展件属性（PF-002），**不在这里发明** |

### rev 10 新推的

前提是[第一节](#一拍板记录) 2026-09-23「据点整体停机后工具执行怎么向 agent 呈现」那条裁决。

| 结论 | 从哪几条推出 | 推理 |
|---|---|---|
| **追补的两条，收场都是失败；「异常中断」是写给 agent 的原因，不是「被中断」那一种收场** | 裁决「让 agent 自行决策是否重新调用一次」+ [PF-006 §5.5 六种收场](../PF-006-tools-and-skills/design.md#55-一次工具执行的收场有六种)（被中断：有人有意停掉，**别自动重试**；失败：**重试、换招，或报告**）+ [PF-006 §6.12 停了算失败](../PF-006-tools-and-skills/design.md#停机之后它不重来) + 2026-09-17「系统都停机了……是不是也是失败了呢」 | 裁决要 agent 自己判断要不要再调——**这正是失败那一格给 agent 的下一步**，与被中断那一格「别自动重试」相反。据点停机也不是任何人有意停掉，落不进被中断的三个触发源。**只有「收场是失败、原因写异常中断」同时满足裁决与两条已接受的规则**，也不多出第七种收场。原「合成一条『被中断』的结果」与此相反，作废 |

### rev 12 新推的（拓展件不可用处置）

前提是[第一节](#一拍板记录) 2026-09-24 那条裁定。前四条是主线随裁定定下、交本 topic 落盘的，后两条是 PM 落盘时推的。

| 结论 | 类别 | 从哪几条推出 | 推理 |
|---|---|---|---|
| **取值恰三种：跳过、否决、替换为指定挂件** | 主线裁定 | 裁定「租户件不可用即跳过，除非注册时声明……策略由 official 提供几种」+「official 的声明替换挂件」 | 裁定点名了两种：跳过（租户件的默认）与替换（official 的）。租户件要有「自己声明的策略」可选，**不能只剩跳过**；它又不能用替换（下一条），剩下的只有「当它判了否决」——而否决是[干预力](design.md#干预力三档直接用-pf-000-的)本来就有的一档，不必新造。**第四种找不到不借新概念的说法**，所以恰三种 |
| **租户件默认跳过，注册时可声明跳过或否决** | 主线裁定 | 裁定原话 +「不在」是事实、不是结论（rev 9 第三行） | 默认跳过是原话。可声明否决，给的是 rev 9 那一行说「正文未述」的「不在就不许跑」——**一件把关件依赖一抖就让整个会话停工，这个代价该由挂它的人自己选**，所以放在注册时，不由系统替他定 |
| **替换为指定挂件只有系统自带的能用，指定挂件在系统层面预先声明** | 主线裁定 | 裁定「只有 official 实现的才显式地在系统层面声明」 | 顶上的那一件得保证自己在，否则还要再问一次「它不在怎么办」，没有尽头。系统预先声明的那几件本身就是最保守的行为（拒、不重试、只记一笔），不依赖原件依赖的任何东西；**租户指定的另一件，系统担保不了它在**。租户要的「不在就不许跑」，否决已经给得出来 |
| **放行判断顶上的是全拒件：需要判断的动作一律拒绝，不放行** | 主线裁定（闭合 rev 11 登记的待裁决，见[第三节](#三待裁决)） | 裁定 + [没有放宽这一档](design.md#没有放宽这一档) + [PF-007 §5.6 每个动作都过四步](../PF-007-meta-capabilities/design.md#56-一次放行判断走四步) | 放行是唯一的授权出处；它不在时放行，等于一道授权从没发生过就生效了，而那个动作做出去收不回。全拒的代价是「做不了」，看得见、等得回来。**PF-007「每个动作都过四步」不破**：四步没人算，就没有一个动作放得出去。**全拒件也不与「放行判断不能被替换」相抵**——那一条挡的是换掉放行的出处，全拒件只会拒、不会放 |
| **声明为否决，只有干预力求出来是可否决、站在「之前」位置上的件才有意义；干预力被收窄到另两档的，不在时照跳过办；「之后」位置上的件不收这个声明** | PM 推导 | [干预力是权限，组织锁在「只观察」租户就放不宽](../PF-002-assets-settings-and-permissions/design.md#loop-extension) + [否决只在「之前」的位置上有意义](#rev-8-新推的) | 一件被组织锁在只观察的拓展件，在的时候拦不住任何东西；它不在时反而能拦，**不在就比在多了一份组织没给的权力**。只有「不在时能做的不多于在时能做的」与收窄那一套同时成立。「之后」的位置上那个状态点已经发生，否决无从拦起，这个声明没有东西可兑现 |
| **「租户挂上的」读作「凡不是系统自带的」**：组织层配的、租户装的、工作区带来的都照这一格 | PM 推导 | 裁定的分界是 official 与 customized + [PF-001 customized 是自定义来源](../PF-001-identity-scope-and-agent-constraints/design.md#来源official-与-customized) | 裁定只分两边：official 的声明替换，其余的跳过或自己声明。组织层挂的也是 customized，**不是 official 就用不了替换**；把「租户」读成字面上的租户一层，组织层挂的件就落在两边都不管的空里 |

**rev 9 第六行「『不在就不许跑』要不要有、放在哪，正文未述」由此有了答案**：要，放在拓展件注册时的不可用处置上（声明为否决）。

## 2026-09-29 运行时归属与句柄

**直接要求**：[INT-001～003](../PF-015-session-lifecycle-and-ownership/interviews/2026-09-29-runtime-ownership-and-handles.md) 要求模型／工具 runtime 归 Session 或 Run 逻辑治理，Agent runtime 仅持句柄，销毁不结束所引用执行，并完整落盘。

**本包处置**：三类 runtime 生命周期归 Session，Run 治理所关联工作；Agent runtime 代表 Run 发起调用并持有句柄。补模型等待 T2w、按执行自身连续性恢复、独立结果记录与显式取消范围。 “代表 Run 发起”沿 [INT-004](../PF-015-session-lifecycle-and-ownership/interviews/2026-09-29-runtime-ownership-and-handles.md#int-004) 作职责解释；Agent Loop 与运行实例不作为同义词。

**PM 推导**：Session 统一生命周期，Run 统一工作归因；Run 外调用直接归 Session。零句柄继续执行要求独立结果记账、持久调用关联与接续查询；仅 Agent runtime 消失不足以判定执行失联。保留显式取消的原传播范围，不由句柄释放隐式取消，不承诺外部效果可撤销。

**取代范围与消费者**：PF-012／013 与 UL-D-3 中“模型 runtime 以 Agent runtime 为宿主”及据此推导“等模型不可释放尝试”的旧说法被取代；PF-011 的树只说明工作归因。历史记录保留，现行正文、流程、验收、词条及对象表改用本轮规则。PF-004 装配、PF-009 流式输出、PF-010 组装压缩、PF-014 入站、PF-020 工作区、PF-021 Job 继续消费原边界，执行接续由 PF-012／013 表达。已冻结 model-request-runtime 等契约及其提供者／装配映射须在后续规格演进中核对宿主、取消、尝试栅栏和恢复；本次产品变更不自动修改其版本或扩大正式接受范围。

**独立产品评审处置**：修正了仅向 Agent runtime 发取消信号的旧详细流程；会话治理负责无 Agent runtime 时的两级取消与幂等终结。限定 T2w 为主流程调用，内部调用按原消费位置接续；普通排队消息在执行等待期间不提前承接。删除“总成本减最后尝试成本就是浪费”的推断，保留原调用归因；资源释放表述限定为 Agent runtime，独立执行仍可占资源。相应验收已补齐；评审不代替正式接受。

**定向复核结果**：原四项实质问题均已闭合，未发现新的阻断问题；另两处等待资源措辞已限定为 Agent runtime 的计算资源。设计门禁 internal（formal skip）、词条／对象对账及差异空白检查通过；不构成实现或形式行为验证。

### 本轮 PM 推导：装配、实例和独立执行的边界

- 会话身份与定义身份固定，而 reload 允许同 Run 采用新内容，因此以新清单和新尝试表达变化；普通恢复必须找当前实际生效清单，不能回到 Run 最初版本或直接读最新来源。
- Model／Tool runtime 由 Session／Run 治理，故 Agent runtime 的退役只改变使用关系；其自身依赖真的失效时仍按各自失败规则处理，不能推导成所有资源永不卸载。
- 未发起动作须按新绑定核对，而已经发起的调用保留原输入，故“模型返回动作建议”与“工具实际执行”必须分清；旧许可不能自动覆盖新实现。
- 重装配可能在等待调用、卡片或拓展判断时发生，故未完成工作的身份、采用依据、结果及等待关系须能恢复；这不推出一律等待、一律拒绝、一律回退或一律取消。
- 重载意图、当前实际生效构成会影响后续求值，故不能只保存一条可丢的命令摘要。持久化布局及交接算法仍属技术设计。

**框架核对依据**：[Cordis 4.0.4 必需服务提供者变化读数](../../basis/cordis/plugin-body-reruns-on-provider-change.md)区分提供者换代／不可用与同实例状态变化，并要求跨重跑保留的事实不能只在消费者闭包内。这里只据此约束产品原则，不指定 inject、effect、插件层次或 API；也不把 DSH 的宿主实现当成本项目方案。

**独立产品评审处置**：评审发现旧 §5.8“放行后不重判”与新 §6.18“当前装配／准入核对”易产生两种相反实现，已区分构成核对和审批重判：原动作同绑定同参数时保留放行结论；尚未发起且绑定已移除或改变则不自动执行，交回 agent。S66d、新增验收与词条同步；定点复核未发现本轮剩余阻断或技术政策越界。评审不代替产品负责人正式接受。

### 2026-09-29 · 能力消费与服务依赖的边界

**直接输入**：[本轮交流 INT-005～008](../PF-004-agent-definition-and-assembly/interviews/2026-09-29-agent-runtime-assembly.md)：会话能力身份见过后保留，失去当前选择或实现时呈现不可用替换件；资产定义数据与执行实现解耦；会话类型必需与 AgentDefinition 显式必需同样不意味着 Loop 直接依赖能力背后的服务。

**本 topic 落点**：能力更新不发生实例交接时同样核对旧模型建议；调用约定或实现改变不自动执行，已发调用保持原输入。

**PM 推导**：①“已知”与“当前允许执行”必须分别求值，否则单调性会变成绕过撤权；②实现更新可发生在稳定入口内部，故不从它推出提供者换代或 Loop 重建；③ schema 更新可能改变调用含义，故即使实例未换也须核对尚未发起的旧动作；已发工作继续沿原输入；④每次求值所需输入不同，故分别保存会话当前采用值、历史数据与实现依据和单次调用快照；⑤Session 是数据／归属，逻辑供给矩阵不推出它是 fiber；实际 inject 边与所有权仍需技术设计和验证。常驻呈现、Slash Command 人的入口及未合法纳入资产仍沿各自边界，不把单调性扩为无条件信息公开。

**已知来源问题与处置**：旧文把能力的选入、数据、实现与服务生命周期混作一种“绑定变化”，因此过度推导 Agent runtime 重建；PF-010 还把提示词成品与实例期固定混为一谈。按本次输入修订，差异记入 C-47。AgentDefinition 版本采用仍沿已拍板的新 Run 或显式 reload 安全交接，不以本次技术分析自行取消该产品边界。框架事实采用 Cordis 4.0.4，区分 provider fiber 换代与同 provider 的数据更新（[已验证 basis](../../basis/cordis/plugin-body-reruns-on-provider-change.md)）；本次额外检查发布包源码，不声称运行了新探针。项目只复用 Cordis，不采用 DSH agent 原语。
