# 通知产品候选

本稿沿正式 notifications 责任及有效旧 PF 细化，尚未接受。通知的技术对象身份未决定，实现未核实，0.0.0 → 0.1.0 能力清单等待负责人选择。

## 产品需求描述

系统和 agent 需要把明确内容送到明确租户，并能继续辨认这次交付的真实结果。发送通知可以独立发生，不要求已有 Schedule、Job 或 agent 会话。通知承担给定内容的交付；分析、生成成果、发起新工作仍归源业务。普通会话回复、成果上报、运行时唤醒和复制邀约分别沿其拥有者的含义，不能因都能展示文字而互相冒充。

发起者、业务归属和收件方分别表达。租户由组织及账号共同确定；同一账号在另一组织中的身份不是替代目的地。指定收件租户、装配通知工具或以系统身份执行，均不授予跨租户传送资格。来源中的私有内容、引用和诊断也要满足披露条件；允许通知维护者，不等于允许交给维护者完整源历史。源业务不因目的地改变而变更归属。

用户需要区分发送请求受理、实际发送、能够确认的送达、已读以及源业务完成。受理表示通知方已经可靠承接交付责任，不表示已送达。有效来源的送达判据是在明确目标租户范围内持久可取回；一次页面显示、事件广播、客户端在线、渠道受理或工具调用返回均不足以单独证明。用户离线不会因此丢掉已送达通知；用户随后取回也不自动成为已读事实。没有已读证据时只表达未确认，不能推定已读或未读。

消费者按一次发送请求及其交付结果查询。原内容、来源、目标、已知结果和未确认部分可以定位；技术重试继续同一逻辑通知，不增加多份独立用户通知。恢复交付不能重新执行源动作，送达不能把失败或取消的源业务变成成功。业务历史按目标租户隔离保留并可查询，查询验当前权限，不因源工作结束、失去访问资格或实例撤除而自动清除。历史索引和物理归档优化不能缩短有效业务保留及可查询范围；具体存储机制服从现行数据责任，本稿不设置 TTL。

框架支持可替换的交付提供者、呈现适配及合法治理配置。提供者必须说明怎样满足目标身份、披露、持久可取回和可确认结果；不满足判据的受理回执只能表达其实际事实。旧 PF 的 CLI/TUI 是已读产品投影，不替新阶段选择，也不固定框架只能存在这些通道。任何具体新通道的产品支持、提供者和权限范围仍须具名决定及相称验证；本稿不因移除旧排除而宣称它们已支持。重试、退避、超时、限流和诊断范围按有效配置治理，不能偷填默认值改变语义。

### J-NO01 系统或 agent 独立发送

发起者希望交付已有内容。前提是业务来源及发起者可辨认、目标租户明确、当前发送和披露资格成立；无 Schedule、Job 或会话来源也是合法情况。通知可靠受理后给出能继续查询本次请求的定位信息；只有目标租户持久可取回已被确认才报告送达。离线收件方仍可在以后取回。

身份不明确、跨租户资格不足或内容不得披露时明确拒绝；目标不可用时报告真实失败、未完或未知，不改投同账号的另一身份。调用超时不能作为未受理证据，先查询原请求。发起者停止等待不撤回已发生交付，不要求额外 agent 会话。对应 CAP-NO01、CAP-NO02、CAP-NO03、CAP-NO04。

### J-NO02 收件人取回并辨认交付

收件人希望在自己的租户范围取回通知并了解其来由。前提是所选租户正确且当前读取资格成立。呈现原通知、允许披露的来源和真实结果；已送达通知在离线及重新进入后可取回。送达、取回、呈现和已读分别有证据；本候选不选择已读操作或协议。

同账号的另一组织不能读取私有内容；收件人也不因通知而取得完整源业务历史的读权。失权时按当前资格拒绝或裁剪，保留原事实；客户端断开只中断呈现。重新连接查询原交付，不因此发出新通知。对应 CAP-NO02、CAP-NO03、CAP-NO04。

### J-NO03 源工作产生定时或组合通知

源业务希望纯通知到点交付，或在执行的实际事件发生后交付声明中的通知。Schedule/Job 拥有接受时的内容、目标和事件选择；开始、成功、失败、取消等只有被声明且实际发生时才触发。等待执行不等于开始，未知结果不等于失败。每个 Job 的一个已选事件对应一次逻辑通知，技术重试继续该意图。纯通知交付不启动 agent 作业会话。

源执行成功与通知送达分开观察；整体 Job 如何结算由 Schedule/Job 拥有。未命中事件不适用，不能伪装成已送达；失败或取消的源执行不因对应通知送达而变成功。通知发送失败不递归产生执行失败通知，也不重做机械动作或 agent 工作。agent 提交成果不隐含另发通知，主动 send 是独立意图，不能冒充原配置义务。恢复只承接原交付；后改 Schedule 不改写已接受 Job 的要求。对应 CAP-NO05、CAP-NO07。

### J-NO04 人类介入等待时主动通知

人类介入拥有者需要让有资格的人知道已有等待事项。无限等待必须让人知道有事项等待，不能仅靠人自行寻找池子。合格入口在人进入时明显显示其租户待办、离线期间持续保留，也是有效兑现方式；不暗要求带外通道或额外业务 send。采用独立提示通知时，通知内容只披露获准的事项定位及必要说明，并沿本域交付判据查询。等待事项、答复资格和是否继续等待归人类介入，入口呈现归应用；通知只承接实际形成的合法提示请求。

通知拒绝、故障或未知不能自动回答问题、解除等待或伪造通知已送达。人后来答复或事项终止，也不使已发通知可逆；查询分别表达原通知事实及允许披露的当前源状态。重启后核对原通知与等待事项，不制造默认答复或重新执行被等待动作。对应 CAP-NO06、CAP-NO07。

### J-NO05 日历维护提示交付

维护责任人需要收到有效政策产生的供应风险提示。日历拥有风险、发布及健康事实，并决定可披露内容和合格目标；通知只承接给定提示。发布成功、仍能查询旧覆盖、供应健康、提示受理、送达和已读分别成立。

提示失败或结果未知不清除风险、不把发布改成未发生，也不重新抓取数据或铸造版本。目标失权时不能把源私有数据交给替代收件人。恢复按原提示核实和继续交付；观察窗口关闭不承担撤回已发内容的效果。对应 CAP-NO06、CAP-NO07。日历的候选细化不扩大通知的上层采用范围。

### J-NO06 查询未知并恢复同一交付

消费者在超时、崩溃或回执丢失后，需要知道原请求发生到哪一步。前提是能够定位原请求并具备当前查询资格。查询区分已知受理、实际尝试、确认送达及尚未知部分；找不到证据不自动等于未发生。恢复先核对权威事实，再在能保持同一逻辑通知及避免重复副作用的条件下继续未完交付。

无法安全重试时保管原责任并报告未知、限制及处置拥有者，不为显示成功盲目重发。消费者确需另发通知时表达新业务意图，不能将它伪装成技术恢复。查询本身只读，不触发源工作、重新发送或改变业务结果。对应 CAP-NO04、CAP-NO07。

### J-NO07 取消与已发生效果分别结算

源业务希望在允许的边界停止尚未发送的纯通知。源拥有者先确认取消资格和实际时序；取消在发送前获胜时阻止发送，通知与源双方保留可核对结果。发送已发生或是否发生未知时，不承诺撤回、不因取消重发，也不把未知改成取消成功。

源执行取消仍按原声明判断取消事件通知，并保留此前已触发的通知责任。源执行已终结时，源取消不能抹掉尚未送达义务。晚到结果仍属于原请求并记录实际效果；恢复继续核对原取消和交付。通用独立发送的取消 API 尚未决定，本旅程不凭 Job 的取消规则授予任意撤回能力。对应 CAP-NO05、CAP-NO07。

### J-NO08 配置、替换与停止交付提供者

装配与运维拥有者需要调整合法交付策略或替换提供者，并辨认未完责任。前提是具体提供者的支持范围、配置、生效点及接续协议已明确。依赖缺席、无效配置或不能满足送达判据时给出真实不可用或拒绝，不能静默采用未经决定的通道、目标或参数。

停止准入和撤除监听只管理实例贡献，不删除业务事实、不使外部输出可逆。在途工作按原身份由合格承接方接续；承接前原方保管，旧引用及晚到结果均有归属。恢复或换代不启动源工作、不创建新的逻辑通知。进展取决于合法策略、持续提供者与目标可用性；本稿不承诺固定耗时或无限自动重试。对应 CAP-NO07、CAP-NO08。

## 阶段与版本支持承诺

0.0.0 → 0.1.0 的通知能力清单等待负责人选择。CAP-NO01–CAP-NO08 是完整长期能力候选，不是该阶段默认全支持或推荐基线。负责人需要为选中的能力明确消费者、支持通道、部署范围及验收；未选事项不据旧 PF 的“当前版本”措辞继承承诺。Q-NO01 记录该选择，Q-NO02–Q-NO04 记录精确技术义务。产品接受、技术接受、实现和运行验证分别成立。

### Q-NO02 请求、通知、尝试与投递身份

发起者需要定位一次发送及其真实结果，收件人不应因技术重试收到多份独立通知，见 J-NO01、J-NO02、J-NO06。身份关系未采用时，尚不能确认重复告知、晚到回执与新的独立发送意图能被正确区分。

公开类型和防重复实现不能凭此候选定案。 技术拥有者为通知公开定义与领域对象/统一语言维护拥有者。完整问题、约束、选项及承接义务见[技术采用 Q-NO02](../../../../packages/notification/notification/docs/internals.md#q-no02)。

<a id="q-no03"></a>

### Q-NO03 可靠承接、确认及未知恢复

源已提交或通知承接、目标提交的回执丢失后，发起者需要查询原交付而不重做源工作，收件人需要在正确租户持久取回内容，见 J-NO03、J-NO06、J-NO07。可靠交接与恢复机制未采用时，尚不能确认未完交付能够安全继续，不能安全重试的原责任仍须保管并如实报告未知。

实现接受前补V-NO05/08/12–15，完整语义保持。 技术拥有者为通知协调者、源业务协调者、目标交付及实际存储拥有者。完整问题、约束、选项及承接义务见[技术采用 Q-NO03](../../../../packages/notification/notification/docs/internals.md#q-no03)。

<a id="q-no04"></a>

### Q-NO04 提供者、配置采用及生命周期

提供者换代、目标离线或依赖缺席时，发起者与收件人仍需要查询原请求和历史，并知道哪些未完交付由谁接续，见 J-NO02、J-NO08。提供者与配置尚未采用，不能确认具体通道满足持久可取回要求，也不能把撤除实例当作撤回已发送内容或清除旧责任。

V-NO15–18须有实际提供者及组合证据。 技术拥有者为通知定义/提供者、合法配置与装配拥有者。完整问题、约束、选项及承接义务见[技术采用 Q-NO04](../../../../packages/notification/notification/docs/internals.md#q-no04)。

### 来源缺证与非目标

原问题集没有额外的来源缺证或待裁非目标问题。正文已经明确的责任边界继续有效，不重新变成产品投票。公开形状、提供者、实际验证及阶段采用的未知分别由上列拥有者承接。
