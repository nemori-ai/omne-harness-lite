# 通知产品设计

采用范围见[topic 入口](README.md)。项目要求取 [requirements](../../../../docs/requirements.md)，责任边界取[通知领域](../../../../docs/domains/notifications/README.md)。本文维护已确认的产品规则，工程机制由技术拥有者说明。

## 产品需求描述

人和 agent 现在只能在一段对话里碰面：一方有话，另一方得在场。系统里发生的事（一次作业做完了、一张卡在等人决定、日历快没有数据）没有统一的去处；外面发生的事要让 agent 知道，也没有入口。通知解决这件事：一件事发生之后，它被可靠地记下，按收件人自己的选择决定给谁、多急，放进收件人随时取得回的地方，再按需要提醒。

收件人有两种：人，和受托的 agent。两种收件人用同一套规则：通知订阅、收件箱、强与弱、合并与节拍。差别只有两处。人稀缺的是注意力，agent 稀缺的是模型调用；给人的提醒落在界面上，给 agent 的提醒是它的会话里的一条输入。

通知只让收件人知道一件事，不替任何人做事。它不生成内容，不发起工作，不重做来源的动作。要一个人做决定归[人类介入](../human-intervention/design.md)；交出一份要验收的工作归[日程与作业](../schedules-and-jobs/design.md)；在一段对话里对 agent 说话归[会话与工作](../sessions-and-work/design.md)。

系统有没有这项能力，不改变会话、agent、模型与工具原有的行为。去掉它，对话、工具调用、等人决定都照常；少掉的只是对话之外没有人被告知。

本范围只做应用内的提醒。邮件、即时通信这类外部去处，机制上留了位置，具体通道不在本范围。同一条通知发给多个租户、稍后再提醒、按事件类型逐个去处配置，也不在本范围。

<a id="model"></a>

### 几样东西分别成立

一件事从发生到被人处理，中间有几个各自成立的事实。它们不是一条往前走的状态线，有前一个不能推出后一个：

| 事实 | 依据 |
| --- | --- |
| 已接下 | 通知记下了这次发送。责任从来源交到了通知 |
| 已送达 | 这条通知在收件人的收件箱里，收件人随时取得回 |
| 已投递 | 往某个去处推了一次，这一次有了结果：成功、失败或未知 |
| 看过、了结 | 收件人自己的处置 |
| 来源那边的结局 | 归来源。通知送到了，不等于那件事成功了 |

接下和送达在同一刻成立：答了「已接下」，通知已经在每个收件人的收件箱里。投递的任何结果都不改送达。结果不知道就是不知道：按原来那次发送去查，不换一个身份重发，也不写成成功或失败。

<a id="j-no01"></a>

### J-NO01 一件事发生了，该知道的人知道了

来源希望把一件已经发生的事交出去一次，之后不用管它给谁、多急、送没送到。前提是来源此刻在系统里登记着，这次发送的主体有资格以这个来源发送，事件属于来源声明过的一种事件类型。

来源交来的是：这是哪种事件、关于来源里的哪个对象、内容是什么、点过去看的定位在哪。它可以点名一个收件人，例如安排的 owner。通知接下之后算出收件人：对这类事件、这个对象，选择不是「不收」的每个收件人，加上被点名的那一个。每个收件人得到一条通知，强还是弱在这一刻定下，之后改订阅不回头改它。没有人要收也是合法的结果，不算失败。

同一次发送再交一遍，得到的是原来的结果，不多出通知。来源没有资格、事件类型没有声明过、点名的收件人不在同一个租户时，明确拒绝。来源此刻没有登记，或判定要用的东西读不到时，回答「这一次没有做，可以再来」，不当成拒绝，也不当成成功。对应 CAP-NO01、CAP-NO02、CAP-NO05。

<a id="j-no02"></a>

### J-NO02 回来之后，在一个面板上看和处置

人离开几个小时回来，希望在一个地方看到这段时间里的事，并分得出轻重。面板分栏：等你决定的、要你处理的、新消息。前两栏是还开着的事，见 J-NO08；新消息是通知。

每条通知写明它来自哪个来源、是什么事件、谁发的、为什么到了你这里（被点名、命中了你的哪条订阅，还是这类事件的缺省）。点它的定位就到那件事所在的地方，到了那里按当前资格重新核。收到一条通知不等于能读它背后的全部历史。

人可以标记看过，可以点「知道了」把它了结，可以划掉。读一条不会自动变成看过或了结。了结或划掉之后系统不会自己把它翻回来；人可以自己恢复。处置只改这条通知，不改来源那边的任何事实：划掉一条「作业失败」，作业仍然是失败的。关掉界面再打开，通知都在。对应 CAP-NO03、CAP-NO04。

<a id="j-no03"></a>

### J-NO03 我定哪些要收，哪些算要紧

收件人希望只被值得的事打扰。每种事件类型由来源给一个缺省：不收、弱、强。之后归收件人：他可以为一类事件设自己的选择，也可以只为一个对象单独设，例如「作业成功」一律不收，只有「每周报表」这一条安排的成功要收。越具体的选择越优先。

强的入箱之后立刻提醒。弱的只入箱，不单独提醒，等节拍时合在一起提醒一次。「设成不收」和「撤掉自己的选择」不同：前者是明确关掉，后者回到这类事件的缺省。来源不能绕过收件人的选择强行打扰。被点名发给你的通知一定入箱；你对这一类选了「不收」时，它按弱处理。对应 CAP-NO09。

<a id="j-no04"></a>

### J-NO04 同一条通知同时到几个地方

人希望通知除了出现在面板上，还能同时到别的地方。每个收件人有一组投递去处。人缺省有「应用内」这一个，不能删。系统里装了别的通道之后，人可以把自己的邮箱或频道加成一个去处，并定这个去处只收强的，还是强弱都收。

同一条通知推到每个启用的去处，各是一次投递，各有各的结果。它仍然是一条通知，只入箱一次。一个去处推不出去，不影响别的去处，也不影响收件箱里那一条。推到系统外面的内容是裁剪过的摘要加一个回到本系统的定位；完整内容要回来之后重新核资格才看得到。通道被卸下时，用它的去处显示为不可用，通知留在收件箱里。对应 CAP-NO10。

<a id="j-no05"></a>

### J-NO05 agent 订阅一类事件，事件来了它被叫醒

agent 希望在没有人对它说话的时候也能对外面的事作出反应，而且不用一直运行着等。它可以列出系统里现在登记着哪些来源、每个来源有哪些事件类型。它可以为自己所在的会话订阅其中一类，写明范围、强弱、期限，并留一句备注：收到时要做什么。期限有三种：一直；命中一次就撤；到某个时刻为止。

agent 的订阅归「订阅」这一项权限，许不许由[动作放行](../meta-capabilities/design.md#动作放行与环境准入)在 agent 发起时判；调用到了通知，就是已经准了，通知没有自己的一套同意。这一项缺省自动。owner 想逐条确认，就在权限设置里把它改成询问；之后 agent 每次订阅，owner 在[放行卡片](../human-intervention/design.md#j-hi03-处理系统的放行卡片)上决定，卡上的放行详情写明来源、事件类型、范围、强弱、期限，和标成「备注（agent 填的）」的那句备注。会话处在跳过询问的运行模式时，照那个模式的定义不问。之后改这一项只影响改动之后 agent 的订阅，已经成立的订阅照常有效。每条订阅记着它的创建者：经 agent 的工具创建的是 agent，并记下它所在的会话与那一次工具调用；在用户界面创建的是 user；系统原生的是 system。agent 撤掉自己的订阅不归「订阅」这一项；调低强弱、缩短期限也是一次订阅，按「订阅」这一项判。agent 不能替别的会话订阅，也不能改 owner 的权限设置。

订阅成立之后，这类事件一发生，通知进这个 agent 的收件箱；订的是强，它的会话收到一条输入并被叫醒。输入里写明来源、事件类型、内容和当时留的备注。一条通知不带任何授权：agent 因它去做的每件事，仍按会话当前的权限判。来自系统外面的内容会被标明是数据，不是指令。会话已归档时投递失败，通知留在收件箱里，不改投别的会话。对应 CAP-NO09、CAP-NO11、CAP-NO13。

<a id="j-no06"></a>

### J-NO06 agent 把事攒着，到点一起看

不是每件事都值得叫醒一次模型。订成弱的通知留在 agent 的收件箱里。每个收件人有一个节拍，由 owner 定。节拍到了，箱里有没了结的，会话收到一条输入，内容是一份机械合成的摘要：有几条，最早的若干条各是什么。箱里没有没了结的，这一拍什么都不发生，不花一次模型调用。

agent 用工具看收件箱、读其中一条的全文、标办完或划掉。没了结的不会无声消失：下一拍还在，直到办完、划掉或被新的一条顶替。即使订的是强，同一个去处两次叫醒之间也有一个最小间隔：第一条立刻投，间隔之内再来的合成一份，到间隔结束时一起投。它们排队，不会丢。对应 CAP-NO11、CAP-NO12。

<a id="j-no07"></a>

### J-NO07 agent 写一条给人看，也可以被别的 agent 订阅

agent 希望在对话之外告诉 owner 一件事，或定期把整理好的东西放到 owner 的面板上。agent 写的每一条是一个事件，来源是 agent，对象是发出它的会话。它缺省点名 owner，所以 owner 的面板上一定收得到；别的 agent 也可以订阅这个会话写的东西。通知上写明是哪个会话里的 agent 写的，人看得出它不是系统发的。

agent 可以给一条带一个替换键。同一个键的新一条顶替收件人箱里旧的那一条，例如每天更新的简报不会越积越多。顶替时缺省不再提醒；要提醒由发的一方打开。被顶替的不能恢复。

agent 写一条不会叫醒它自己。几个 agent 互相订阅时，每条事件带着它是第几层被叫醒之后发的；超过上限就被拒绝，不会转起来停不下。agent 主动写一条是独立的意图：交成果不隐含发通知，agent 写的也不能顶替来源自己该交的事件。对应 CAP-NO14、CAP-NO01。

<a id="j-no08"></a>

### J-NO08 还开着的事，一直看得到

有些事不是「发生过一次」，是「现在还开着」：一张卡在等你决定，一条安排被挡住了，日历的数据快用完了。这类事开着还是了结了，只有来源说了算。所以它们不复制成通知：面板上「等你决定」「要你处理」两栏直接显示来源那边现在还开着的事项，在那里处理就是在来源那里处理，例如在面板上答卡就是答那张卡。

通知只负责提醒。一件事项刚出现时，选了强的收件人被提醒一次；节拍到了，还有开着的就再提醒一次。事项在来源那边了结了，提醒自然停。收件人没有「划掉一件还开着的事」这个操作。提醒的任何结果都不算答复，也不解除等待。来源此刻读不到时，面板上那一栏显示读不出，不显示成「没有」。对应 CAP-NO06。

<a id="j-no09"></a>

### J-NO09 查原来那次发送，以及装上和卸下

来源在回执丢失、进程重启之后，希望知道原来那次发送到了哪一步。它按原来的发送去查，得到：接下了没有、给了哪些收件人、各条现在的处置。查询只读，不触发发送。确定没有接下才回答没有；读不到时回答读不到。

来源和通道可以在系统运行中装上和卸下。装上之后，下一次列目录就看得到，下一次发送就能用。来源卸下之后，它的新发送得到「这一次没有做」；已经在收件箱里的通知照旧可查、可处置；收件人对它的订阅留着，来源回来之后接着生效。目录变了本身也是一件可以订阅的事。对应 CAP-NO04、CAP-NO07、CAP-NO08、CAP-NO13。

<a id="j-no10"></a>

### J-NO10 到点了，系统提醒我

日程到点发出的不只是让 agent 干活的作业，也可以是系统给人的一条提醒。提醒型的安排到点时，由日程以自己的来源点名发一条通知给 owner。到点的判断、错过窗口怎么办、整份作业怎样结算，都归[日程与作业](../schedules-and-jobs/design.md#reminder)；通知只承接这一次发送，并让日程查得到它接下了没有。对应 CAP-NO05。

### 可观察场景

下列场景是产品判据，正文描述的是期望结果。演示通过不替代产品负责人接受。

1. 让一个来源发一条点名给 owner 的强通知，然后关掉界面再打开。面板上应看到这一条，写明来源、事件与缘由。让来源把同一次发送再交一遍，面板上仍然只有一条。
2. owner 把「作业成功」设成不收，只对一条安排设成弱。两条安排各成功一次：面板上只多出后一条的通知，角标变了，没有弹出提示。
3. owner 把「订阅」这一项权限设成询问，会话在需要时问人的运行模式下，agent 订阅一类事件，范围是一个对象，强，备注一句话。会话里应出现一张放行卡片，卡上逐项写着这次订阅的内容；owner 放行之前事件发生，agent 不被叫醒；放行之后事件再发生，会话收到一条输入，里面有事件和那句备注。owner 在面板上看这条订阅，创建者写的是 agent 与它所在的会话。
4. 让一个来源在最小间隔之内连发三条强通知给同一个 agent。会话应先收到一条输入，间隔结束时再收到一条合并的输入，三条通知一条不少。
5. agent 的收件箱是空的，等一拍：会话没有新输入。放进两条弱通知，等一拍：会话收到一条摘要。agent 只办完其中一条，再等一拍：摘要里还有另一条。
6. agent 用同一个替换键连写三条给 owner。面板上只有最新的一条是没了结的，前两条显示为被顶替，过程中没有弹出提示。
7. 让 agent 等人答一张卡。面板的「等你决定」一栏应出现这张卡；在面板上答了它，agent 继续，那一栏里它消失。期间把通知整个卸下：会话里的卡照常能答，agent 照常继续。
8. 会话归档之后让一条强通知到达它。会话没有收到输入；通知仍在这个 agent 的收件箱里；owner 的面板「要你处理」一栏出现一件「投递受阻」。

## 能力定义

| 能力标识 | 定义与范围 | 需求位置 |
| --- | --- | --- |
| CAP-NO01 发送与接下 | 来源交出一件已经发生的事；通知接下它，同一刻它进入每个收件人的收件箱；同一次发送再交得到原结果 | J-NO01、J-NO07 |
| CAP-NO02 身份与资格 | 发送、读、处置、订阅、管去处各按当前资格判；收件人只在本租户；登记了来源、装了工具都不等于获准 | J-NO01、J-NO02、J-NO05 |
| CAP-NO03 收件箱与处置 | 每个收件人一个收件箱；看过、了结、划掉、恢复；处置不改来源的事实；了结之后不被系统翻回 | J-NO02 |
| CAP-NO04 查询与历史 | 按原来的发送查它的结果；通知带来源、事件、缘由；历史保留，查询只读 | J-NO02、J-NO09 |
| CAP-NO05 来源交出事件 | 来源在自己的记录里留下事件并交出一次，交出之前责任在来源，接下之后在通知；提醒型安排到点点名发送 | J-NO01、J-NO10 |
| CAP-NO06 持续事项的提醒 | 还开着的事只有一份，归来源；面板直接显示它；通知只在出现时与节拍时提醒；提醒不算答复 | J-NO08 |
| CAP-NO07 未知与恢复 | 结果不知道保持未知，按原发送核对，不换身份重发；投递失败按退避再投，到上限后成为一件「投递受阻」 | J-NO09、J-NO05 |
| CAP-NO08 来源与通道的装卸 | 来源与通道在运行中登记和撤下；撤下后已入箱的照旧可查，订阅保留 | J-NO09、J-NO04 |
| CAP-NO09 通知订阅 | 收件人对一类事件、在一个范围里选不收、弱或强；越具体越优先；可带备注与期限；agent 的订阅归「订阅」这一项权限，由放行判断判；订阅记创建者（agent 时带会话与工具调用） | J-NO03、J-NO05 |
| CAP-NO10 投递去处 | 一个收件人一组去处；同一条通知推到每个启用的去处，各有结果；出系统的内容裁剪 | J-NO04 |
| CAP-NO11 agent 收件与叫醒 | agent 是收件人；强通知成为它会话里的一条输入并叫醒它；通知不带授权；外部内容标明是数据 | J-NO05、J-NO06 |
| CAP-NO12 合并与节拍 | 弱的等节拍合成摘要；空拍不产生输入与模型调用；强的受最小间隔约束，排队不丢 | J-NO06 |
| CAP-NO13 目录 | 现在登记着的来源、事件类型与通道，按当下现算；目录变了可以被订阅 | J-NO05、J-NO09 |
| CAP-NO14 agent 作为来源 | agent 写的每一条是一个事件，缺省点名 owner，可被别的 agent 订阅；替换键；不叫醒自己；因果深度有上限 | J-NO07 |
