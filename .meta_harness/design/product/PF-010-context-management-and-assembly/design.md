# PF-010：上下文管理与组装

- 修订：rev 7，2026-09-29 · [变更历史](changelog.md)
- 状态：rev 5 已接受为正式版本；**rev 6 待产品负责人确认**。无未决项。

## 一、背景与问题

[PF-009](../PF-009-context-message-types/design.md) 定了**一共有哪几种消息**，
以及**每个内容块带着「给人看吗、给模型看吗」两个标注**。
[PF-012](../PF-012-agent-loop-and-run/design.md) 定了**组装站在方程的哪一步**，
以及**组装是纯派生的**。

**中间那段没人说过：**

> **从一份[会话日志](../PF-012-agent-loop-and-run/design.md#会话日志)，
> 到一份真的能用的上下文，这中间发生了什么。**

这段空着，四个问题每次都要现编答案：

- **用户切进一个跑了三个月的会话，界面上该给他什么？**
  几万条全端出来，界面卡死；只给最后几条，他看不到来龙去脉。
- **给模型的那一份，系统提示词和对话是一起攒的，还是两件事？**
  混作一谈，就会写出「压缩的时候把系统提示词也收走一段」这种东西。
- **压缩过的历史，这一次该从哪儿开始取？**
  取错了，agent 要么看见一段已经被概括过的原文，要么丢掉它其实还需要的上下文。
- **一条刚生成的消息还没落盘，能不能先发给模型？**
  能的话，崩一次就再也对不上账了——**模型看过的东西，日志里没有**。
- **上下文装不下了，压缩到底能动什么？**
  没有边界，「压缩」就会变成「想删什么删什么」——
  **而删掉的东西，用户那边也一起没了**。

本 topic 把这段补上：**组装**，以及**压缩能做什么、不能做什么**。

## 二、目标与非目标

### 目标

1. **定义两侧组装各自的形状**，以及**为什么两侧形状不一样**。
2. **定义给用户那一侧的两个动作**：**往回要历史** 与 **一直收着新的**。
3. **定义给模型那一侧的两块**：系统提示词，与会话上下文。
4. **定义组装必须满足的五条要求**，以及每一条做不到会怎样。
5. **把压缩定成一个闭包**：给它**一条硬约束**（交回来的装得进目标模型的窗口），
   和**三个联合目标**——**要不要压、压到哪，都在它里面判**。
6. **划死压缩的动作边界**：**能做哪两件，不能做哪三件。**

### 非目标

| 不做什么 | 为什么 |
|---|---|
| **具体的算法与策略**：一段取多少条、边界怎么算、前缀怎么对齐、**压缩怎么在三个目标之间取平衡** | **产品定要求与边界，不定策略。**产品负责人两次明确：「**具体的算法策略不是产品设计需要考虑的**」「**具体怎么做（策略、算法）不是产品设计关心的事**」 |
| **怎么通信**（拉取与推送各用什么协议） | **技术选型。**产品只定「有两个不同的动作」，怎么实现归技术设计 |
| 一共有哪几种消息、块上那两个标注 | 归 [PF-009](../PF-009-context-message-types/README.md)。本 topic **用**它们，不重定 |
| 组装站在方程的哪一步、它改不改日志 | 归 [PF-012](../PF-012-agent-loop-and-run/design.md#53-改日志的动作与纯派生的动作)。本 topic 不重定 |
| 系统提示词的组合规则与逐请求数据 | 归 [PF-004](../PF-004-agent-definition-and-assembly/design.md#54-为什么系统提示词必须落在第三列)。本 topic 只说**它是单独一块** |
| **给语音层的那一份组装** | **本版不做。**产品负责人已明确：语音层现在不做设计。[它将来会存在](../PF-009-context-message-types/interviews/2026-09-18-openai-gpt-live.md)，但不在这一版 |

## 三、用户与场景

| 使用者 | 什么时候接触这块 | 他关心什么 |
|---|---|---|
| **用户** | 切进一个老会话 | **马上看得到东西**，而且**往上翻能翻到更早的** |
| **用户** | 正在对话中 | 新的消息**自己就来了**，不用刷新 |
| **agent 自己** | 每一轮 | 我看到的是不是**完整的、该给我看的那些** |
| **付账的人** | 看账单 | 同样的对话，**为什么这个月贵了一截** |
| **排查上下文问题的人** | agent 像是漏看了什么 | 这一次组装**取了哪一段，为什么** |
| **实现这套东西的人** | 每一天 | 我该在什么时候组装，**取什么、不取什么** |

**第四行容易被忽略**：组装做得好不好，**直接反映在账单和响应速度上**——
而那两件事用户都感觉得到。

### 组装

**从会话日志里取出一部分，拼成一份给某一方看的上下文。**

**两侧各有一份**，[两侧地位相同](../PF-009-context-message-types/design.md#57-一份会话日志两种组装)——
**不存在一份特殊的「上下文」凌驾于另一份之上**。

> **组装不写日志。**它只读。同一份日志组装十次，结果一样。

### 给用户那一侧：两个动作，方向相反

| | **往回要历史** | **一直收着新的** |
|---|---|---|
| 方向 | **往更早** | **往更新** |
| 谁发起 | **用户这边要**——切进会话时要一段，往上翻时再要一段 | **不用要**，有新的自己就到 |
| 锚在哪 | **当前已经拿到的最早那一条** | **当前已经拿到的最新那一条** |
| 拿到之后 | **接在前面**（prepend） | **接在后面** |

**切进一个会话时发生的是第一个动作**：

> **永远是先拿一段最近的，不是全量。**

**用户往上翻，不是「再来一次刚才那个动作」**——
那一次锚在「最近」，这一次锚在**当前已加载的最早点位**，**再往前多取一段接上去**。

> **锚点不同，所以是两回事。**

### 给模型那一侧：两块，分别组装

| 块 | 它是什么 | 什么时候变 |
|---|---|---|
| **系统提示词** | 你是谁、你有什么能用 | [组合规则与逐请求数据分开](../PF-004-agent-definition-and-assembly/design.md#54-为什么系统提示词必须落在第三列)：每次请求使用当前合法能力描述与 schema；能力数据更新不因此重建 Agent runtime，压缩不改写这一块 |
| **会话上下文** | 这场对话到目前为止 | **每一轮都在长** |

**系统提示词本版只含文本。**它[不落会话日志](../PF-009-context-message-types/design.md#消息)、每次组装时现算，
所以也不经过[消息落盘之前](../PF-012-agent-loop-and-run/design.md#消息落盘之前每条消息都经过它不只是输入)那一关的[转换件](../PF-013-model-profiles-and-invocation/design.md#转换件)；
只有文本，就不会出现「有效模型收不下系统提示词里某一块」这回事。

**为什么必须分成两块**：两块的**变化节奏完全不同**，而且——

> **只有第二块压得动。**

[PF-012 已经点出过这件事](../PF-012-agent-loop-and-run/design.md#55-想这一步交进闭包拿回装得下的一份)：
量预算的时候**两块都要算**，但压缩**只碰得到会话那一块**。
混成一块，就会长出「把系统提示词也收走一段」这种东西——
**而那等于把 agent 的身份和能力清单压没了**。

## 五、模型

### 5.1 两侧形状不一样，根子是「人有记忆，模型没有」

**这不是两套实现凑出来的差别，是消费者本身不同。**

| | 模型 | 人 |
|---|---|---|
| 记不记得上一轮给过什么 | **不记得** | **记得** |
| 所以每次要给多少 | **一整份** | **一段就行** |
| 能不能自己往回找 | **不能** | **能——他会往上滚** |
| 受不受上下文预算限制 | **受**，超了就得压 | **不受** |

> **模型每轮都要一整份，因为它不记得上一轮看过什么。**
> **人记得，而且人能往上翻——所以给人的可以先给一段。**

**这一条解释了给人那份为什么不受预算约束**：它本来就不打算一次给完。
也解释了为什么[工具帧只给人不给模型](../PF-009-context-message-types/design.md#toolinternalmessage)
在成本上说得通——**给人的那一侧，多几百条不要紧**。

### 5.2 「先一段、再往前接」仍然是纯派生的

**这一条必须写明，否则实现会走歪。**

给定一份日志和一个位置，取出来的那一段是**确定的**——
所以[组装仍然是纯派生的](../PF-012-agent-loop-and-run/design.md#53-改日志的动作与纯派生的动作)，
[PF-012 那条不动摇](../PF-012-agent-loop-and-run/design.md#52-会话日志是唯一的真相来源)。

> **「加载到哪了」是看的人那一边的事，不是日志的状态。**

**不点破这一条，会长出什么**：实现者觉得「给用户的组装得记住加载到哪了」，
于是**把那个位置写回日志**——**日志一旦被组装写脏，`f` 就不纯了**，
而这是整个恢复机制的地基。

### 5.3 给模型的那一份，两块各自的名字里就写着要求

产品负责人给的建模是两个动作相加：**建系统提示词** + **建给模型读的、知道压缩这回事的上下文**。

**第二个名字里有两样东西，正好是下面五条要求里的两条**：

| 名字里的 | 对应哪条要求 |
|---|---|
| **给模型读的** | 要求二：**成分必须是明确标了给模型读的** |
| **知道压缩这回事的** | 要求三：**有压缩记录时，边界由压缩记录定** |

> **不是先有要求再起名字，是这两件事本来就是这一步的定义的一部分。**

### 5.4 组装必须满足的五条要求

**产品只提要求，不定策略。**五条各自回答「做不到会怎样」：

#### 要求一：尽可能最大化前缀一致

**每一次请求，前面那一大段应当尽量和上一次逐字相同。**

**做不到会怎样**：同样一场对话，**成本和响应速度差出一截**——
而这两件事**用户直接感觉得到**（账单变贵，回话变慢）。

> **这条同时是给压缩策略的要求。**
> 压缩一旦动了前面的历史，**整个前缀就变了**——
> 后面那一大段本来可以照搬的东西，全都白费。

**所以它约束的不只是组装这一步。**[到了压缩那一节会看到](#56-压缩是一个闭包它的调子是三个联合目标)，
**前缀一致根本就是压缩自己的三个目标之一**——不是外面加给它的一条约束。

#### 要求二：成分必须是明确标了给模型读的

**不是「没标记就默认给」，是「必须明确标了给模型读」才给。**

> **没表过态，不等于表了同意。**

**这与 [PF-006「不声明就是不能后台」](../PF-006-tools-and-skills/design.md#66-前台后台-与-等待态是两个维度)是同一个调子**，
而这里的理由更硬一层：

**误给的后果收不回来。**模型一旦看见了不该看的——
[没长完的工具调用](../PF-009-context-message-types/design.md#半截的工具调用记下来但不给模型看)、
[工具执行中的帧](../PF-009-context-message-types/design.md#toolinternalmessage)——
**它就会拿着这个往下推理，而你没有办法让它忘掉**。

> **宁可少给，不可误给。**少给了还能再给一次；误给了，这一轮就已经被污染了。

#### 要求三：有压缩记录时，边界由压缩记录来定

**如果历史里存在压缩记录，这一次取哪一段，应当根据压缩记录来确定。**

> **[压缩记录](../../ubiquitous_language/terms/record-and-context.md#ul-compaction-record--压缩记录--compaction-record)
> 就是压缩留下的那条 [`CompactionMessage`](../PF-009-context-message-types/design.md#compactionmessage)**，
> 不是另一份东西。

**但要紧的是下面这句，它正是最容易被写错的地方：**

> **未必是从最后一条 [`CompactionMessage`](../PF-009-context-message-types/design.md#compactionmessage) 开始取。**
> **完全有可能它之前的历史也要。**

**做不到会怎样**：实现者会写出「从最后一条摘要往后取」这条简单规则——
**那是错的**，而且错得静默：agent 少看了一段它其实需要的东西，
**没有任何地方会报错**。

**为什么会这样，见 [§5.9](#59-块级标记解释了组装边界为什么不是一条线)；具体怎么定边界是策略，不在产品这一层。**
**本版只固定一件事：边界由压缩记录决定，而不是由「最后一条摘要的位置」机械决定。**

#### 要求四：先落盘，再组装

**上一次请求模型之后、这一次请求模型之前新增的那些「给模型读的」消息，
必须全部持久化完成，才能开始组装。**

**做不到会怎样**：崩一次，那些没落盘的就没了——
**而模型已经看过它们**。恢复之后重算出来的上下文，
**与当时真正发给模型的不是同一份**，[`f` 当场不纯](../PF-012-agent-loop-and-run/design.md#agent-loop)。

**这与 [PF-012「事件必须先落进记录，不能攒在内存队列里」](../PF-012-agent-loop-and-run/design.md#511-外面进来的事怎么到-agent-眼前)
是同一条的另一面**：

| 那边说的 | 这边说的 |
|---|---|
| **事件不许攒在内存里** | **组装不许在落盘之前开始** |

**两句合起来才是完整的**：一句管**写进来**，一句管**读出去**。

#### 要求五：组装的输入里，必须有当下生效的那份模型档案

**这一次组装是为哪个模型做的，组装自己必须知道。**

**这一条是三条已定规则共同的落脚处：**

| 谁需要它 | 需要档案上的哪一项 |
|---|---|
| **这一次取多长** | **窗口** |
| **这一次那个块给原件、[派生表示](../../ubiquitous_language/terms/record-and-context.md#ul-derived-rendering--派生表示--derived-rendering)，还是 [transcript](../../ubiquitous_language/terms/record-and-context.md#ul-transcript--transcript--transcript)** | **收得下哪些[模态](../PF-013-model-profiles-and-invocation/design.md#模态)**——按它取原件或收得下的那份派生表示，都取不到就给 transcript（[PF-013 转换件](../PF-013-model-profiles-and-invocation/design.md#转换件)）；几份都收得下时挑哪几份是策略 |
| **一张图送进去之前要不要先缩** | **送进去之前的限制**（[PF-013 §8 那条三段交接的第二段](../PF-013-model-profiles-and-invocation/design.md#八边界与依赖)） |

> **三项是同一份档案里的三个事实，不是三套机制。**
> 组装接收那一份，按它处理——**[换模型因此不给 loop 添任何分支](../PF-013-model-profiles-and-invocation/design.md#59-换模型一条事实一个生效点零个新分支)**：
> 用户换了模型，下一次组装拿到的就是新的那一份，**流程一个字都不用改**。

**做不到会怎样**：换模型这条产品承诺**没有落脚点**。
用户切到一个窗口更小的模型，组装照旧按老窗口取——**这一次请求当场装不下**；
切到一个收不下图的模型，组装照旧递原图——**而那个块明明已经挂着派生表示与 transcript 了**。

> **具体用什么手段兑现「送进去之前的限制」**（预处理时多档各存一份、运行时缓存、还是别的），
> **不在产品这一层**——[PF-013 已经把这一段明确划给架构与实现规格](../PF-013-model-profiles-and-invocation/design.md#八边界与依赖)。

### 5.5 几样东西各自落成哪一种消息

[PF-009](../PF-009-context-message-types/design.md#七种消息按谁在说话分) 定了**一共有哪几种消息**，
但**某个具体产物落成哪一种**，是「做成消息」那一步的事——归这里。

**已经定下的四样：**

| 什么东西 | 落成 | 凭什么 |
|---|---|---|
| **[卸载后的占位](../PF-006-tools-and-skills/design.md#卸载)** | **`ToolMessage`** | 它就是那次工具调用的结果，**只是只给了一部分** |
| **agent 取回全文** | **一条 `AssistantMessage` + 一条新的 `ToolMessage`** | 那是**它自己发起的一次新调用**（[PF-012 §5.10](../PF-012-agent-loop-and-run/design.md#510-卸载结果落成消息之前的那一关)） |
| **[工具等待态](../PF-006-tools-and-skills/design.md#等待态)发出的请求，答复回来** | **`ToolMessage`** | **那次工具执行还没完**——答复是它的输入，它拿到之后接着跑 |
| **系统发起的等待，答复回来** | **`SystemReminderMessage`** | **没有哪次工具执行在等它**，它是外面进来的一条信息 |

> **后两行是同一条裁决的两半，而那条裁决不在这里——
> 它是 [PF-008「等待态是两个不同生命周期维度上的」](../PF-008-human-in-the-loop/design.md#等待态的两个维度)。**

**tool 的等待态与 run 的等待态本来就是两回事**，
所以两边的答复落到不同的地方，**是那条裁决的直接后果，不是另加的一条规则**。

**还有一样已经定了，归别处**：[loop 之外的事件](../PF-012-agent-loop-and-run/design.md#511-外面进来的事怎么到-agent-眼前)
落成 `SystemReminderMessage`，**且[两类一律追加、说状态的自己写清「从什么变成了什么」](../PF-009-context-message-types/design.md#64-说状态的写清变化说事的写清发生消息一律追加)**——
那条归 PF-012 与 PF-009，本 topic 不重定。**组装这一侧因此不需要「同一处只取最新」这道筛子。**

**压缩产出什么形状**，见 §5.7。

### 5.6 压缩是一个闭包，它的调子是三个联合目标

#### 闭包：进去一份日志，出来一份装得下的东西

**[Agent Loop](../PF-012-agent-loop-and-run/design.md#agent-loop) 看不见压缩内部。**
它只看见两件事：**把日志交进去，拿一份装得下的东西出来。**

> **「这一次要不要压、压到什么程度」在闭包里判，不在方程里。**

**它在方程眼里是一个 [`await` 点](../PF-012-agent-loop-and-run/design.md#agent-runtime)**——
闭包内部**要调模型生成摘要**，那是一次真正的等待，
[协程会在那里交还控制权](../PF-012-agent-loop-and-run/design.md#613-取消跟着宿主走)。

**闭包的契约只有两句：**

| | |
|---|---|
| **硬约束（后置条件）** | 交回来的东西，**装得进后面那次请求要用的那个模型的最大上下文**——那份[模型档案](../PF-013-model-profiles-and-invocation/design.md#模型档案)由[要求五](#要求五组装的输入里必须有当下生效的那份模型档案)递进来 |
| **做不到怎么办** | **它自己失败**——一件 [off-normal](../PF-011-off-nominal-handling/design.md#非常态)，按 PF-011 那套往外交。**不是方程里的一个分支** |

**硬约束与下面三个目标不冲突，两者的地位不同**：

> **硬约束必须满足；三个目标是在满足它的前提下取的那个平衡。**

**做成闭包换来什么**：[方程不必知道「上下文预算」这回事](../PF-012-agent-loop-and-run/design.md#56-状态转移表)——
它只认**「装得下 / 装不下」两个回执**，**不必懂窗口，也不必会量**。

> **「量一量」不在方程里。**它和「要不要压」「压哪一段」一样，
> 都在闭包内部，**都是策略**。

#### 三个联合目标

**压缩不是「把上下文变短」这一件事，是三件事一起平衡。**

| 目标 | 说白了 |
|---|---|
| **保前缀** | 尽可能保留一致的前缀 |
| **保信息** | 尽可能减少信息损失 |
| **降长度** | 尽可能降低压缩后的上下文长度 |

> **三个是联合目标，不是「一个目标加两条约束」。**

**要紧的是它们两两相冲**——任意押住两个，第三个必然吃亏：

| 押住哪两个 | 第三个会怎样 |
|---|---|
| **保前缀 + 保信息** | **长度降不下来**——什么都不动，当然一个字都没少 |
| **保信息 + 降长度** | **前缀废了**——既要短又不许丢，就只能重写重排，而**一重排，前面照搬不动的那一大段全部作废** |
| **保前缀 + 降长度** | **信息丢得多**——前面动不得，就只能往狠里砍 |

> **所以不存在「最优的压缩」，只有在这三者之间取的一个平衡。**

**取哪个平衡是策略，不是产品设计的事。**产品定的是**硬约束、这三个目标同时成立**，
以及下面两节——**能做哪些动作、不能做哪些动作**。

### 5.7 压缩能做的，只有两件事

| 能做 | 说白了 |
|---|---|
| **对一段历史生成摘要总结** | 把一段历史概括成一条 |
| **点名一批消息内容块，从此不再模型可读** | **点它们的名，不去动它们** |

> **两件事交出来的是同一条东西**：一条
> [`CompactionMessage`](../PF-009-context-message-types/design.md#compactionmessage)——
> **摘要是它的内容，那份名单是它自己带着的。**

#### 那两个标注仍然是这件事的前提

[PF-009 定块标注时](../PF-009-context-message-types/design.md#每个块带两个标注给人看吗给模型看吗)，
产品负责人说过「**有了这个标识位之后，再讨论上下文压缩就很顺了**」。
**顺在这里：**

> **压缩不搬走任何东西，它只是让一批块对模型不再可见。**

**但它不是回头去把块上那一位翻过来。**两者的差别在于**谁在什么时候写了什么**：

| | 谁写的 | 什么时候写的 | 之后还会变吗 |
|---|---|---|---|
| **[块上那两位](../PF-009-context-message-types/design.md#每个块带两个标注给人看吗给模型看吗)** | **产生这个块的人** | 那个块**落盘那一刻** | **不会**——落了就不动 |
| **那份名单** | **做这一次压缩的人** | 那条 `CompactionMessage` **落盘那一刻** | **不会**——它自己也只是一条追加进去的消息 |

**于是「此刻哪些块还模型可读」是算出来的，不是存着的：**

> **块上那一位标着给模型读，且没有任何排在它前面的 `CompactionMessage` 点过它的名。**

#### 名单跟着摘要走，是为了让日志能重放

**回头翻块上那一位，有一处说不过去**：日志里一条早就落盘的消息，
**会因为后来发生的事而变了样**。代价是两笔：

- **「这份日志在第 5 轮的时候是什么样」答不出来**——那一位是第 9 轮翻的，
  回头看只剩最新那个值，**当时究竟把哪些东西给模型看了，再也还原不出来**。
- **[会话日志 append only](../PF-012-agent-loop-and-run/design.md#会话日志) 破了一个口子**，
  而且破在最不该破的地方：**已经交给模型看过的那些东西上**。

**名单自带之后，这两笔都没有了：**

> **任何一个时刻的那份视图，都能由「排在那一刻之前的全部 `CompactionMessage`」算出来；
> 日志本身一个字都没被改过。**

#### 由此掉出三条，都是直接后果

- **压缩只管「给模型看」那一侧，不碰「给人看」那一侧。**
  用户那一侧[本来就不受上下文预算约束](#51-两侧形状不一样根子是人有记忆模型没有)——
  **压缩是为模型那侧的预算做的，跟人那侧没关系**。
- **被压掉的东西，用户照样看得见。**它还在日志里，**一个字都没动**。
- **[「一份会话日志，两种组装」](../PF-009-context-message-types/design.md#57-一份会话日志两种组装)在这里兑现。**
  没有那个机制，压缩就只能靠删——**而删了，两侧一起没**。

> **压缩不改写历史**：它只往后加了一条消息，**而那条消息自己带着它让谁闭嘴。**

### 5.8 压缩不能做的，有三件事

| 不能做 | |
|---|---|
| **从持久化的记录中擦除一条消息** | **无论它是否还模型可读，都不能擦除** |
| **把上一次模型请求之后新产生或到来的消息拿去压** | — |
| **点名那些[悬着的东西](../PF-012-agent-loop-and-run/design.md#611-悬着的东西不许被压掉)** | 没答完的卡片、转后台还没回来的执行，**各有一个占位** |

#### 「不给模型看」不等于「可以删」

**这是第一条禁令最要紧的部分**，而且它容易被当成多余的一句——
**一个模型已经读不到的东西，留着干嘛？**

**留着，因为读者不止模型一个。**

> **被点名之后，它对模型不存在了，但它对人、对排查、对回溯，一直都在。**

这与 [PF-009 那条被纠正过的判断](../PF-009-context-message-types/decisions.md#四已知的来源问题)同源：
**「不给模型看」和「不记下来」是两件事**，混起来的代价是
**出了问题永远查不到当时到底发生了什么**。

**也就是说**：[会话日志 append only](../PF-012-agent-loop-and-run/design.md#会话日志) 这条，
**压缩不是例外**。

#### 模型还没看过的东西，不能先替它压掉

**第二条禁令划的是压缩的输入区间的上界。**

```text
   ┌─ 可以压 ─────────────────────┐ ┌── 不许压 ──┐
   …………………………………………………………………………… │ ▲ │ 新消息 新消息 │ ▲
                                    │ │           │ │
                          上一次模型请求        这一次正要请求
```

**为什么**：那些消息**模型一次都还没看过**。
压了它，**模型永远只能看到概括，看不到原文**——
而它接下来要干的事，恰恰依赖这些刚到的东西。

**这与 [PF-012「压缩救不了单条超限」](../PF-012-agent-loop-and-run/design.md#510-卸载结果落成消息之前的那一关)是同一条**：

> **压缩收的是前面的历史，而新来的这些是当下正要用的东西。**

**它还顺带挡住一种抖动**：允许压最新的，那么这一轮压掉、下一轮又来新的、
再压掉——**每一轮都在动尾巴，而尾巴一动，下一轮的前缀又变了**。
**要求一当场作废。**

#### 悬着的东西被点了名，两边就静默对不上

**没答完的卡片、转后台还没回来的执行**，在日志里
[各有一个占位](../PF-012-agent-loop-and-run/design.md#611-悬着的东西不许被压掉)。
**那些占位不许被点名。**

**为什么**：占位一旦对模型不可见，**agent 就不知道自己还有东西在外面跑**，
而日志那一层它们还好端端悬着——**两边静默对不上**。
agent 会按「那件事不存在」往下走，**而那件事随时可能回来**。

> **「什么叫悬着」不归这里**——它是
> [那个方程定义域](../PF-012-agent-loop-and-run/design.md#方程从日志里读什么)的一部分，
> 归 [PF-012](../PF-012-agent-loop-and-run/design.md#611-悬着的东西不许被压掉)；
> **本节定的是「压缩不能拿它怎么样」。**两边各管一半，缺一半这条就落不了地。

#### 由此，压缩的输入区间是一个左右都有界的区间

| | 界在哪 | 依据 |
|---|---|---|
| **上界** | **上一次模型请求**，**不是「此刻」** | 本节第二条禁令——两者之间隔着的正是模型还没看过的那一批 |
| **下界** | **不是死的**——**已有的摘要可以被再次收走** | 「**已有的摘要 + 新消息 → 新的摘要**」是允许的策略 |

### 5.9 块级标记，解释了组装边界为什么不是一条线

**[要求三](#要求三有压缩记录时边界由压缩记录来定)里那句限定——「未必是从最后一条
`CompactionMessage` 开始选，完全有可能它之前的历史也要」——
在有了「能做什么」之后就讲得通了。**

> **压缩点的是「块」，不是「一条截断线」。**

**被点过名的块可以是散布的**，前前后后到处都有；**没被点过的仍然模型可读**。
所以「这一次取哪一段」这个问题，**答案本来就不是一个起点**：

| 如果压缩是…… | 那么组装边界是…… |
|---|---|
| 从某一点截断 | **一个起点**——「最后一条摘要之后」就够了 |
| **逐块点名**（**实际是这一种**） | **不是一个起点**——**得看哪些块还模型可读**，而它们可能落在最后一条摘要**之前** |

**照「从最后一条摘要往后取」那条简单规则做，会把那些仍然可读的块一并丢掉**——
**而没有任何地方会报错**。

**还要留意一件事：「哪些块还模型可读」没有一个地方存着它。**

> **它是[从全部 `CompactionMessage` 算出来的一份视图](#名单跟着摘要走是为了让日志能重放)**，
> 组装每次现算——**日志里找不到一个叫「当前可读集合」的东西可以直接读。**

> **这一段是 PM 从「能做什么」推出来的，产品负责人给要求三时明说原因不展开。**
> **2026-09-18 经核对确认成立**：「这个解释是正确的。」
> 推理链见 [decisions 第二节](decisions.md#二pm-推导)。

## 六、产品规则

### 6.1 组装只读日志，不写日志

**两侧都是。**「加载到哪了」归看的人那一边，**不写回日志**。

**违反的代价**：日志被组装写脏，恢复时重算不出同一个结果。

### 6.2 没有明确标了「给模型读」的，不进模型那一份

**默认拒绝。**标注缺失、标注不明，**一律不给**。

> **宁可少给，不可误给。**

### 6.3 前缀尽量与上一次逐字相同

**变的往后放，不变的往前放。**这条同时约束[压缩](#要求一尽可能最大化前缀一致)。

### 6.4 有压缩记录时，边界由压缩记录定

**不许**写成「从最后一条摘要往后取」。**它之前的历史也可能要。**

### 6.5 所有该给模型读的新消息落盘之后，才开始组装

**一条都不能漏。**

### 6.6 给用户那一侧，往回要与往后收是两个动作

**锚点不同**：往回要锚在**当前已拿到的最早那条**，往后收锚在**最新那条**。
**切进会话时先要一段最近的，不是全量。**

### 6.7 压缩是一个闭包，要不要压在它里面判

**Agent Loop 只管把日志交进去，拿一份装得下的东西出来。**
**「这一次要不要压、压到什么程度」不在方程里**，[在闭包内部](#56-压缩是一个闭包它的调子是三个联合目标)。

**不许**把「量一量、超了没」做成方程的一个分支——**那等于让方程去懂上下文预算**。

### 6.8 交回来的东西必须装得进目标模型的窗口

**这是硬约束，不是目标。**装不进，**压缩自己失败**，
按 [PF-011](../PF-011-off-nominal-handling/design.md) 那套往外交——**不是方程里的一条分支**。

**哪个模型**由[要求五](#要求五组装的输入里必须有当下生效的那份模型档案)递进来的那份模型档案定。

### 6.9 压缩同时对三个目标负责

**保前缀 · 保信息 · 降长度。**三者两两相冲，**取哪个平衡是策略**。

**不许**把压缩当成「只要变短就行」——那会把另外两个目标当成可以牺牲的东西。
**三个目标是在满足 §6.8 的前提下取的平衡**，不与它并列。

### 6.10 压缩只能做两件事，且落成同一条消息

**对历史生成一段摘要**；**点名一批块，从此不再模型可读**。**没有第三件。**

**两件事交出来的是一条 `CompactionMessage`**——**摘要是内容，名单它自己带着**。
**不许**回头去改已经落盘的块上的标注：**那会让日志不能重放**。

### 6.11 压缩只管「给模型看」那一侧

**不碰「给人看」那一位，也不碰块本身。**被压掉的内容，**用户照样看得见**。

### 6.12 记录里的消息一条都不能擦除

**不管它还模型不模型可读。**[会话日志 append only](../PF-012-agent-loop-and-run/design.md#会话日志)，
**压缩不是例外**。

> **「不给模型看」不等于「可以删」。**

### 6.13 上一次模型请求之后新来的消息，不许压

**模型一次都还没看过它们。**压缩的输入区间**上界是上一次模型请求**，
不是「此刻」。

### 6.14 悬着的东西不许被点名

**没答完的卡片、转后台还没回来的执行**，[各自的占位都不许被点名](#悬着的东西被点了名两边就静默对不上)。
点掉了，**agent 就不知道自己还有东西在外面跑**，而日志那一层它们还悬着。

**「什么叫悬着」归 [PF-012](../PF-012-agent-loop-and-run/design.md#611-悬着的东西不许被压掉)**，本条只定压缩不能拿它怎么样。

### 6.15 组装边界要看「哪些块还模型可读」，不是「最后一条摘要在哪」

**压缩点的是块，不是一条截断线**（§5.9）。
**不许**实现成「从最后一条 `CompactionMessage` 往后取」。
**那份「哪些块还可读」也不是存着的**，是从全部 `CompactionMessage` 现算的。

### 6.16 压缩之后，meta runtime context 要重新给一份完整的

[meta runtime context](../PF-015-session-lifecycle-and-ownership/design.md#meta-runtime-context)
**不是消息**，但模型要感知它。它平时以**变更通知**的形式到达；
**而压缩会把之前那些通知一起收走**。

> **所以压缩之后，那一批必须重新以完整形态给一份。**

**不给会怎样**：模型只剩下压缩摘要里可能提到、也可能没提到的只言片语，
**于是它得靠回忆拼当前状态**——它现在有哪些授权、后台还有什么在跑、
待办剩几条、自己落在哪台机器上。**拼出来的那一份迟早与真的对不上，而且不会报错。**

**这一条对本 topic 是硬要求，不是建议**：
[压缩只能做两件事](#610-压缩只能做两件事且落成同一条消息)说的是**它对消息做什么**；
**meta runtime context 不在那两件事的范围内**，**它不能被当成消息处理掉**。

## 七、取舍

| 选择 | 取的 | 舍的 |
|---|---|---|
| **给用户的先给一段，不给全量** | 再长的会话也**打得开**；不为一次进入付全量的代价 | 用户往上翻时**要等一下**；「一段」多长成了一个要调的东西 |
| **往回要与往后收做成两个动作** | 两个方向各自最合适的形态，互不牵制 | 比「一个动作反复调」复杂；实现要维护两条路 |
| **给模型的分成两块** | 只压得动的那块才被压；**系统提示词不会被误伤** | 量预算时要把两块加起来算，**不能只盯着对话长度** |
| **成分默认拒绝（没标明就不给）** | 误给这件事**从机制上堵死** | 任何一处标注漏了都会表现为「agent 像是少看了东西」，**排查时得先查标注** |
| **要求前缀一致** | 成本与响应速度**实打实地降** | **压缩被约束住了**——它不能随便重排前面的历史 |
| **先落盘再组装** | 恢复之后算出来的与当时发出去的是同一份 | 每一轮多一次等待；**落盘慢就直接拖慢对话** |
| **压缩靠点名，不靠搬走东西** | **两侧不再互相牵制**——模型那侧省了预算，人那侧一个字没少 | 日志**只会越来越大**，从不因压缩而变小；存储成本一直在涨 |
| **名单由 `CompactionMessage` 自己带着，不回头改块上的标注** | **日志能重放**——任何一个历史时刻给模型看的是哪些，都还原得出来 | 「此刻哪些块可读」**没有一个地方存着**，每次都得从全部摘要现算；摘要越多，这笔现算越贵 |
| **把压缩做成一个闭包，要不要压在里面判** | 方程**不必懂上下文预算**；换一套压缩策略，**转移表一个字不动** | 外面**看不见它内部发生了什么**——压了几轮、丢了多少，都得靠它自己往外说 |
| **装不下就让压缩自己失败，不给方程加分支** | 失败沿[一条统一的路](../PF-011-off-nominal-handling/design.md)往外走，方程只有「成 / 不成」 | 一次本可以降级凑合的请求，**现在直接是一件非常态**——回旋余地留给了策略，不留在方程里 |
| **一条消息都不许擦除** | 出了问题**查得到当时到底发生了什么** | 同上，而且**连「早就没人要看的东西」也得留着** |
| **新来的消息不许压** | 模型看得到原文，且**尾巴不动，前缀才稳得住** | **一次实在压不下来的时候，能动的余地更小了**——不能拿最新的开刀 |
| **三个目标联合，不分主次** | 不会退化成「只要变短就行」 | **没有唯一最优解**，策略要反复调，而且**好不好只能整体评价** |
