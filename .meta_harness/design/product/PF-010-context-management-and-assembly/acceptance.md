# PF-010 验收标准

**做成什么样算做对了。**每一条都要能被观察到，
不能观察的不写在这里——那种条款验收时只会变成各人一套解释。

## 一、可观察场景

### 给用户那一侧

| # | 场景 | 应当看到什么 |
|---|---|---|
| S1 | 切进一个有几万条记录的老会话 | **马上有东西可看**；**不是全量加载** |
| S2 | 问「第一次加载了多少」 | **一段最近的**——具体多少是策略，但**绝不是全部** |
| S3 | 界面开着，对方发来新消息 | **自己就到了**，不用刷新，也不用再要一次 |
| S4 | 用户往上翻到顶 | **从当前已加载的最早那条再往前取一段，接在前面** |
| S5 | 反复往上翻 | **一段一段往前接**，直到会话开头 |
| S6 | 问「往前翻和首次加载是同一个动作吗」 | **不是**——**锚点不同**：一个锚在最近，一个锚在当前已加载的最早点位 |
| S7 | 翻了二十次之后，查会话日志 | **一个字都没被写过** |


### 给模型那一侧

| 场景 | 应当看到什么 |
|---|---|
| 问「给模型的那份分几块」 | **两块**：系统提示词 + 会话上下文 |
| 一次压缩之后 | **系统提示词那块纹丝不动**——**它压不动** |
| 看系统提示词里有哪些块 | **只有文本**；会话日志里**找不到**它——它每次组装时现算 |
| 换成一个收不下图的模型，会话里有一张带 transcript 的图 | 组装给的是**它收得下的那份派生表示，或 transcript**——不是原图 |
| 问「装不装得下，按哪一块算」 | **两块加起来算**；但**能压的只有第二块** |
| 连续两轮请求 | **前面那一大段尽量逐字相同** |
| 一个标注不明的块 | **不进模型那一份**（默认拒绝） |
| 上一轮到这一轮之间新来了消息 | **全部落盘之后，才开始组装** |
| 落盘没完成 | **组装不开始**，等着 |

### 压缩是一个闭包

| 场景 | 应当看到什么 |
|---|---|
| 问 Agent Loop「这一轮要不要压」 | **它不知道**——**那个判断在闭包里** |
| 问 Agent Loop「上下文预算还剩多少」 | **它不知道，也不需要知道**——它只认「装得下 / 装不下」 |
| 一次压缩交回来的东西 | **装得进这一次请求要用的那个模型的窗口** |
| 交回来的东西仍然装不下 | **压缩自己失败**，交一件[非常态](../PF-011-off-nominal-handling/README.md)出来——**不是方程的一条分支** |
| 换掉整套压缩策略 | **[状态转移表](../PF-012-agent-loop-and-run/design.md#56-状态转移表)一个字不用改** |

### 压缩能做什么

| 场景 | 应当看到什么 |
|---|---|
| 问「压缩一共能做几件事」 | **两件**：对历史生成摘要、点名一批块从此不再模型可读 |
| 一次压缩之后 | **日志里多了一条 `CompactionMessage`**——**摘要是它的内容，名单它自己带着** |
| 查那些被压掉的块 | **还在日志里，一个字没改**，**块上的标注也一位没翻** |
| 用户界面上看那些被压掉的内容 | **照样看得见**——**压缩不碰「给人看」那一位** |
| 问「压缩把哪段删了」 | **一段都没删**——它只追加一条 |
| 问「第 5 轮的时候给模型看的是哪些块」 | **答得出来**——拿那一刻之前的全部 `CompactionMessage` 算一遍 |
| 三个目标 | **同时成立**，不许退化成「只要变短就行」 |

### 压缩不能做什么

| 场景 | 应当看到什么 |
|---|---|
| 一条消息整条都不再模型可读 | **仍然不许擦除** |
| 有人想删掉早就没人看的历史来省空间 | **不许**——**「不给模型看」不等于「可以删」** |
| 上一次模型请求之后新来的一批消息 | **不许压**——**模型一次都还没看过** |
| 上下文撑爆了，而撑爆它的正是那批新消息 | **仍然不许压它们**；闭包压不下来就自己失败 |
| 要压的那一段里有[悬着的东西](../PF-012-agent-loop-and-run/design.md#611-悬着的东西不许被压掉) | **绕开它们，不许点名** |
| 有人想回头改一个已经落盘的块上的标注 | **不许**——**改了日志就不能重放** |
| 问「压缩输入区间的上界在哪」 | **上一次模型请求**，**不是「此刻」** |
| 问「已有的摘要还能再被收走吗」 | **能**——「摘要 + 新消息 → 新摘要」是允许的策略 |

### 组装边界

| 场景 | 应当看到什么 |
|---|---|
| 日志里有压缩记录 | 边界**由压缩记录定** |
| 问「是不是从最后一条 `CompactionMessage` 往后取」 | **不是**——**看的是哪些块还模型可读** |
| 问「哪些块还模型可读，存在哪」 | **哪儿都没存**——**每次从全部 `CompactionMessage` 现算** |
| 那些仍然可读、但落在最后一条摘要**之前**的块 | **照取不误** |
| 被点名的块的分布 | **可以是散布的**，不是从某点起整段被点掉 |

## 二、绝不能发生的事

| 绝不能发生 | 如果发生了意味着什么 |
|---|---|
| **切进会话时全量加载** | 会话越长越打不开，**而会话本来就该能长期存活** |
| **往前翻被实现成「又从最近取一段」** | 用户永远翻不到更早的——**锚点错了** |
| **「加载到哪了」被写回会话日志** | **日志被组装写脏**，[`f` 不再纯](../PF-012-agent-loop-and-run/design.md#agent-loop)，恢复机制的地基没了 |
| **系统提示词和会话上下文混成一块去压** | **agent 的身份和能力清单被压没了** |
| **没明确标「给模型读」的块被送进了模型** | **误给收不回来**——它会拿着这个往下推理 |
| **在落盘完成之前就组装并发出去** | 崩一次，**模型看过的东西日志里没有** |
| **压缩擦除了任何一条消息** | [append only](../PF-012-agent-loop-and-run/design.md#会话日志) 破了；**出了问题永远查不到当时发生了什么** |
| **压缩动了「给人看」那一位** | 用户那一侧**凭空少了东西**，而他没做过任何操作 |
| **压缩改写了任何一条消息的内容** | 同上，而且**改写过的历史无从对账** |
| **压缩回头翻了已经落盘的块上的标注** | **日志不能重放**——「当时给模型看的是哪些」再也还原不出来 |
| **压缩点掉了一个[悬着的东西](../PF-012-agent-loop-and-run/design.md#611-悬着的东西不许被压掉)的占位** | agent 不知道自己还有东西在外面跑，**而它随时会回来** |
| **交回来的东西装不进目标模型的窗口，却照样往下走** | 这一次请求**当场装不下**，而且**没有任何地方提前说过** |
| **「量一量、超了没」跑进了状态转移表** | **方程被迫懂上下文预算**；换一套压缩策略就得改方程 |
| **压缩动了上一次模型请求之后的新消息** | 模型**永远看不到原文**；而且**每轮都在动尾巴，前缀再也稳不住** |
| **组装被写成「从最后一条摘要往后取」** | 仍然可读的块被一并丢掉，**而没有任何地方会报错** |
| **前缀每轮都变** | 成本和响应速度**实打实地变差**，而用户直接感觉得到 |
| **压缩被当成「只要变短就行」** | 另外两个目标被当成可以牺牲的东西——**而它们是联合目标** |

## 三、判据

| 设计点 | 做到了的判据 | 没做到时的表现 |
|---|---|---|
| 不是全量加载 | 造一个十万条的会话，**打开耗时与会话长度基本无关** | 会话越长打开越慢 |
| 两个动作锚点不同 | 往前翻 N 次，**每次都能拿到更早的一段** | 翻到某处就原地打转 |
| 组装不写日志 | 反复加载、翻页、组装，**日志的字节数纹丝不动** | 日志跟着读操作在长 |
| 两块分开 | 压一次，**系统提示词逐字不变** | 系统提示词也被收走了一段 |
| 默认拒绝 | 造一个标注缺失的块，**它不出现在模型那一份里** | 它被当成「默认给」送了进去 |
| 先落盘再组装 | 在落盘和组装之间强制断电，**恢复后重算出的上下文与当时发出去的一致** | 两者对不上 |
| 压缩只增不改 | 压一次，**日志里消息条数只增不减，内容逐字未变，块上的标注也逐字未变** | 有消息消失、被改写，或有标注被回头翻掉 |
| 日志能重放 | 取任意一个历史时刻，**算得出那一刻给模型看的是哪些块**，且与当时真正发出去的一致 | 只算得出「现在」那一份 |
| 压缩不碰人那侧 | 压一次，**用户界面上的内容一条不少** | 用户那边跟着少了东西 |
| 不压新消息 | 让上一轮之后来一大批消息并触发压缩，**它们原样进上下文** | 它们被概括掉了 |
| 悬着的东西留着 | 造一个后台执行没回来的占位并反复压缩，**那个占位一直模型可读** | 它被点名了，agent 从此不提它 |
| 压缩是闭包 | **换一套完全不同的压缩策略，[转移表](../PF-012-agent-loop-and-run/design.md#56-状态转移表)一个字不用改** | 改策略要动方程 |
| 硬约束兜得住 | 造一个怎么压都装不下的会话，**得到的是一件非常态**，不是一次装不下的请求 | 请求照发，在模型那边炸 |
| 边界按块看 | 造一份「被点名的块散布在各处」的日志，**仍然可读的旧块被取到了** | 最后一条摘要之前的全丢了 |
| 前缀一致 | 连续多轮，**前缀的相同长度稳定且尽量长** | 每轮前缀都从头变 |

## 四、不验收的

| 不验收 | 为什么 |
|---|---|
| 一次往回要多少条、边界具体怎么算 | **策略**。产品只定「先一段，不是全量」「按哪些块还模型可读」 |
| **这一次要不要压、压哪一段、怎么在三个目标之间取平衡** | **全在闭包内部**。产品只定硬约束、三个目标和动作边界 |
| 摘要里写什么、写多长、由谁生成 | 同上 |
| 前缀怎么对齐、缓存怎么做 | 同上 |
| **那份「哪些块还模型可读」怎么算得快** | **实现**。产品只定它是现算的派生视图 |
| 两个动作各用什么协议 | **技术选型**，产品正文不记 |
| 一共有哪几种消息、块上带什么标注 | 归 [PF-009](../PF-009-context-message-types/README.md) |
| **什么叫「悬着」** | 归 [PF-012](../PF-012-agent-loop-and-run/design.md#611-悬着的东西不许被压掉)。这里只验收「不许点名」 |
| **给语音层的那一份组装** | **不做**——语音层现在不做设计 |
| 摘要累积到装不下时怎么办 | 归**会话的生命周期**，[PF-012 划出去了](../PF-012-agent-loop-and-run/design.md#八边界与依赖) |

## 能力数据变化

| 场景 | 必须观察到 |
|---|---|
| Tool 描述／schema 或 Skill 说明合法更新，Loop 不变 | 后续请求可以使用新能力数据；此前请求不改写，压缩仍不改系统提示词 |
