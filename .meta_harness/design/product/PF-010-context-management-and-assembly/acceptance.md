# PF-010 验收标准

**做成什么样算做对了。**每一条都要能被观察到，
不能观察的不写在这里——那种条款验收时只会变成各人一套解释。

## 一、可观察场景

### 给用户那一侧

| 场景 | 应当看到什么 |
|---|---|
| 切进一个有几万条记录的老会话 | **马上有东西可看**；**不是全量加载** |
| 问「第一次加载了多少」 | **一段最近的**——具体多少是策略，但**绝不是全部** |
| 界面开着，对方发来新消息 | **自己就到了**，不用刷新，也不用再要一次 |
| 用户往上翻到顶 | **从当前已加载的最早那条再往前取一段，接在前面** |
| 反复往上翻 | **一段一段往前接**，直到会话开头 |
| 问「往前翻和首次加载是同一个动作吗」 | **不是**——**锚点不同**：一个锚在最近，一个锚在当前已加载的最早点位 |
| 翻了二十次之后，查会话日志 | **一个字都没被写过** |

### 给模型那一侧

| 场景 | 应当看到什么 |
|---|---|
| 问「给模型的那份分几块」 | **两块**：系统提示词 + 会话上下文 |
| 一次压缩之后 | **系统提示词那块纹丝不动**——**它压不动** |
| 量预算时 | **两块都算**；但**能压的只有第二块** |
| 连续两轮请求 | **前面那一大段尽量逐字相同** |
| 一个标注不明的块 | **不进模型那一份**（默认拒绝） |
| 上一轮到这一轮之间新来了消息 | **全部落盘之后，才开始组装** |
| 落盘没完成 | **组装不开始**，等着 |

### 压缩能做什么

| 场景 | 应当看到什么 |
|---|---|
| 问「压缩一共能做几件事」 | **两件**：标记块是否还模型可读、对历史生成摘要 |
| 一次压缩之后，查那些被压掉的消息 | **还在日志里，一个字没改**，只是「给模型看」那一位翻了 |
| 用户界面上看那些被压掉的内容 | **照样看得见**——**压缩不碰「给人看」那一位** |
| 一次压缩之后 | **日志里多了一条 `CompactionMessage`** |
| 问「压缩把哪段删了」 | **一段都没删**——它只翻标注、只追加 |
| 三个目标 | **同时成立**，不许退化成「只要变短就行」 |

### 压缩不能做什么

| 场景 | 应当看到什么 |
|---|---|
| 一条消息整条都不再模型可读 | **仍然不许擦除** |
| 有人想删掉早就没人看的历史来省空间 | **不许**——**「不给模型看」不等于「可以删」** |
| 上一次模型请求之后新来的一批消息 | **不许压**——**模型一次都还没看过** |
| 上下文撑爆了，而撑爆它的正是那批新消息 | **仍然不许压它们**；按 [PF-012 §5.5](../PF-012-agent-loop-and-run/design.md#压完还超这一层腾不出空间了)走 |
| 问「压缩输入区间的上界在哪」 | **上一次模型请求**，**不是「此刻」** |
| 问「已有的摘要还能再被收走吗」 | **能**——「摘要 + 新消息 → 新摘要」是允许的策略 |

### 组装边界

| 场景 | 应当看到什么 |
|---|---|
| 日志里有压缩记录 | 边界**由压缩记录定** |
| 问「是不是从最后一条 `CompactionMessage` 往后取」 | **不是**——**看的是哪些块还模型可读** |
| 那些仍然可读、但落在最后一条摘要**之前**的块 | **照取不误** |
| 被标掉的块的分布 | **可以是散布的**，不是从某点起整段变掉 |

## 二、绝不能发生的事

| 绝不能发生 | 如果发生了意味着什么 |
|---|---|
| **切进会话时全量加载** | 会话越长越打不开，**而会话本来就该能长期存活** |
| **往前翻被实现成「又从最近取一段」** | 用户永远翻不到更早的——**锚点错了** |
| **「加载到哪了」被写回会话日志** | **日志被组装写脏**，[`f` 不再纯](../PF-012-agent-loop-and-run/design.md#agent-loop)，恢复机制的地基没了 |
| **系统提示词和会话上下文混成一块去压** | **agent 的身份和能力清单被压没了** |
| **没明确标「给模型读」的块被送进了模型** | **误给收不回来**——它会拿着这个往下推理 |
| **在落盘完成之前就组装并发出去** | 崩一次，**模型看过的东西日志里没有** |
| **压缩擦除了任何一条消息** | [append only](../PF-012-agent-loop-and-run/design.md#会话日志) 破了；**出了问题永远查不到当时发生了什么** |
| **压缩动了「给人看」那一位** | 用户那一侧**凭空少了东西**，而他没做过任何操作 |
| **压缩改写了任何一条消息的内容** | 同上，而且**改写过的历史无从对账** |
| **压缩动了上一次模型请求之后的新消息** | 模型**永远看不到原文**；而且**每轮都在动尾巴，前缀再也稳不住** |
| **组装被写成「从最后一条摘要往后取」** | 仍然可读的块被一并丢掉，**而没有任何地方会报错** |
| **前缀每轮都变** | 成本和响应速度**实打实地变差**，而用户直接感觉得到 |
| **压缩被当成「只要变短就行」** | 另外两个目标被当成可以牺牲的东西——**而它们是联合目标** |

## 三、判据

| 设计点 | 做到了的判据 | 没做到时的表现 |
|---|---|---|
| 不是全量加载 | 造一个十万条的会话，**打开耗时与会话长度基本无关** | 会话越长打开越慢 |
| 两个动作锚点不同 | 往前翻 N 次，**每次都能拿到更早的一段** | 翻到某处就原地打转 |
| 组装不写日志 | 反复加载、翻页、组装，**日志的字节数纹丝不动** | 日志跟着读操作在长 |
| 两块分开 | 压一次，**系统提示词逐字不变** | 系统提示词也被收走了一段 |
| 默认拒绝 | 造一个标注缺失的块，**它不出现在模型那一份里** | 它被当成「默认给」送了进去 |
| 先落盘再组装 | 在落盘和组装之间强制断电，**恢复后重算出的上下文与当时发出去的一致** | 两者对不上 |
| 压缩只翻标注 | 压一次，**日志里消息条数只增不减，且内容逐字未变** | 有消息消失或被改写 |
| 压缩不碰人那侧 | 压一次，**用户界面上的内容一条不少** | 用户那边跟着少了东西 |
| 不压新消息 | 让上一轮之后来一大批消息并触发压缩，**它们原样进上下文** | 它们被概括掉了 |
| 边界按块看 | 造一份「被标掉的块散布在各处」的日志，**仍然可读的旧块被取到了** | 最后一条摘要之前的全丢了 |
| 前缀一致 | 连续多轮，**前缀的相同长度稳定且尽量长** | 每轮前缀都从头变 |

## 四、本版不验收的

| 不验收 | 为什么 |
|---|---|
| 一次往回要多少条、边界具体怎么算 | **策略**。产品只定「先一段，不是全量」「按哪些块还模型可读」 |
| 压缩在三个目标之间**怎么取平衡** | **策略与算法**。产品只定「三个同时成立」 |
| 摘要里写什么、写多长、由谁生成 | 同上 |
| 前缀怎么对齐、缓存怎么做 | 同上 |
| 两个动作各用什么协议 | **技术选型**，产品正文不记 |
| 什么时候触发压缩 | 归 [PF-012](../PF-012-agent-loop-and-run/design.md#55-想这一步先组装量完才知道要不要压)：组装 → 量 → 超了才压 |
| 一共有哪几种消息、块上带什么标注 | 归 [PF-009](../PF-009-context-message-types/README.md) |
| **给语音层的那一份组装** | **本版不做**——语音层现在不做设计 |
| 摘要累积到装不下时怎么办 | 归**会话的生命周期**，[PF-012 已划出去](../PF-012-agent-loop-and-run/design.md#八边界与依赖) |
