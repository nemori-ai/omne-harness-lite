# PF-010：上下文管理与组装

[PF-009](../PF-009-context-message-types/README.md) 说了**一共有哪几种消息**，
[PF-012](../PF-012-agent-loop-and-run/README.md) 说了**组装站在方程的哪一步**。
本 topic 补中间那段：

> **从一份会话日志，到一份真的能用的上下文，这中间发生了什么。**

一句话概括本版的结论：

> **两侧的组装形状不一样，因为人有记忆而模型没有。**

## 两侧，各自长什么样

| | **给用户的** | **给模型的** |
|---|---|---|
| 分几块 | 一条消息流 | **两块**：系统提示词 + 会话上下文 |
| 一次给多少 | **先一段最近的，不是全量** | **一整份** |
| 怎么继续 | **往回要**（prepend）／**一直收着**（新的自己到） | 每一轮**重新算一遍** |
| 受不受预算限制 | **不受** | **受**，超了要压 |

**模型每轮都要一整份，因为它不记得上一轮看过什么。**
**人记得，而且人能往上翻——所以给人的可以先给一段。**

## 给用户的：两个动作，方向相反

**它们不是「同一个动作来两次」，锚点就不同：**

| | 往回要历史 | 一直收着新的 |
|---|---|---|
| 锚在哪 | **当前已经拿到的最早那一条** | **当前已经拿到的最新那一条** |
| 谁发起 | **用户这边要** | **不用要**，有新的自己就到 |
| 接在哪 | **前面**（prepend） | 后面 |

**切进一个会话，永远是先拿一段最近的。**

> **「加载到哪了」是看的人那一边的事，不是日志的状态。**
> 所以[组装仍然是纯派生的](../PF-012-agent-loop-and-run/design.md#53-改日志的动作与纯派生的动作)——
> **它只读日志，不写日志**。

## 给模型的：两块，分别组装

**为什么必须分开**：两块的变化节奏完全不同，而且——

> **只有会话那一块压得动。**

系统提示词的[成分在装配那一刻就定死了](../PF-004-agent-definition-and-assembly/design.md#54-为什么系统提示词必须落在第三列)，
**不落会话日志、每次现算，本版只含文本**。混成一块，就会长出「把系统提示词也收走一段」这种东西——
**那等于把 agent 的身份和能力清单压没了**。

## 五条要求

**产品只提要求，不定策略。**

| # | 要求 | 做不到会怎样 |
|---|---|---|
| **一** | **尽可能最大化前缀一致** | 成本与响应速度**差出一截**，而这两件事用户直接感觉得到。**这条同时约束压缩** |
| **二** | 成分**必须是明确标了「给模型读」的** | **误给收不回来**——模型看见了就会拿它推理 |
| **三** | 有压缩记录时，**边界由压缩记录定** | 会被写成「从最后一条摘要往后取」——**而那是错的**，且错得静默 |
| **四** | **先落盘，再组装** | 崩一次，**模型看过的东西日志里没有**，`f` 当场不纯 |
| **五** | 输入里**必须有当下生效的那份[模型档案](../PF-013-model-profiles-and-invocation/design.md#模型档案)** | **换模型这条产品承诺没有落脚点**——取多长、给原件还是派生表示还是 transcript，全都无从判断 |

**第二条是默认拒绝**，与 [PF-006「不声明就是不能后台」](../PF-006-tools-and-skills/design.md#66-前台后台-与-等待态是两个维度)
同一个调子：**没表过态，不等于表了同意**。

> **宁可少给，不可误给。**少给了还能再给一次；误给了，这一轮已经被污染了。

**第三条里最要紧的是那句限定**：

> **未必是从最后一条 `CompactionMessage` 开始取——完全有可能它之前的历史也要。**

**为什么会这样，[压缩那一节解释了](#压缩一个闭包一条硬约束三个目标)**——
**压缩点的是「块」，不是一条截断线**。

## 压缩：一个闭包，一条硬约束，三个目标

**Agent Loop 看不见压缩内部。**它只做一件事：**把日志交进去，拿一份装得下的东西出来。**

> **「这一次要不要压、压到什么程度」在闭包里判，不在方程里。**

**闭包的契约只有两句**：交回来的东西**必须装得进后面那次请求要用的那个模型的窗口**；
**装不进就是它自己失败**，按 [PF-011](../PF-011-off-nominal-handling/README.md) 那套往外交，
**不是方程里的一条分支**。

**这样换来的是**：方程**不必懂上下文预算**，「量一量」这个动作从它那里消失了；
换一套压缩策略，**转移表一个字不用动**。

**硬约束之下，才是三个目标。**压缩不是「把上下文变短」这一件事，是三件事一起平衡：

> **保前缀 · 保信息 · 降长度。**

**三个是联合目标，而且两两相冲**——押住任意两个，第三个必然吃亏：

| 押住哪两个 | 第三个 |
|---|---|
| 保前缀 + 保信息 | **降不下来** |
| 保信息 + 降长度 | **前缀废了** |
| 保前缀 + 降长度 | **信息丢得多** |

**所以不存在「最优的压缩」**，只有一个平衡——**而取哪个平衡是策略，不是产品的事**。

| 能做两件 | 不能做三件 |
|---|---|
| **对历史生成一段摘要** | **擦除一条消息**（**不管它还模型不模型可读**） |
| **点名一批块，从此不再模型可读** | **压上一次模型请求之后新来的消息** |
| **两件落成同一条 `CompactionMessage`** | **点名那些[悬着的东西](../PF-012-agent-loop-and-run/design.md#611-悬着的东西不许被压掉)** |

**那两个[块标注](../PF-009-context-message-types/design.md#每个块带两个标注给人看吗给模型看吗)仍然是这件事的前提：**

> **压缩不搬走任何东西，它只是让一批块对模型不再可见。**

**但它不回头去翻块上那一位**——**名单由那条 `CompactionMessage` 自己带着**。
于是「此刻哪些块还模型可读」**是从日志派生的，不是另一份事实权威**：
**块上那一位标着给模型读，且没有任何排在它前面的摘要点过它的名。**

> **这样日志才能重放**：任何一个历史时刻给模型看的是哪些，都还原得出来，
> **而日志本身一个字没被改过**。

**三条直接后果**：压缩**不碰「给人看」那一位**；被压掉的东西**用户照样看得见**；
[「一份会话日志，两种组装」](../PF-009-context-message-types/design.md#57-一份会话日志两种组装)**在这里兑现**——
没有那个机制，压缩就只能靠删，**而删了是两侧一起没**。

**三条「不能做」各自挡住一件事：**

> **「不给模型看」不等于「可以删」。**被点名之后它对模型不存在了，
> **但它对人、对排查、对回溯一直都在**。

> **模型还没看过的东西，不能先替它压掉。**
> 压缩的输入区间**上界是「上一次模型请求」，不是「此刻」**。

> **悬着的东西不许被点名。**没答完的卡片、转后台还没回来的执行，各有一个占位；
> 点掉了，**agent 就不知道自己还有东西在外面跑**。
