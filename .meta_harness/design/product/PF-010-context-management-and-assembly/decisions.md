# PF-010 决策与来源

产品设计允许 product manager 做判断，但**不允许发明没人拍过板的东西**。
本页把两者分开：哪些是产品负责人裁决的，哪些是 PM 自己推导的，各自依据在哪。

**本 topic 自 rev 2 起为正式版本**，组装与压缩两块都已落地，**待裁决与核对项均已闭合**。
**rev 4 把压缩定成闭包**，并按产品负责人的裁决改成「名单由那一次 compaction 自己带着」。

## 二、PM 推导

从已拍板内容推出的判断，附可核对的推理链。

| 结论 | 从哪几条推出 | 推理 |
|---|---|---|
| **两侧形状不同，根子是「人有记忆，模型没有」** | 「给用户先加载一段」+ 模型每轮要完整上下文 | 模型**不记得上一轮给过什么**，所以每轮都得给一整份；人**记得，而且能往上翻**，所以先给一段就够。**这不是两套实现凑出来的差别，是消费者本身不同**。由此还能解释两件已经定下的事：给人那份**不受上下文预算约束**（它本来就不打算一次给完），以及[工具帧只给人不给模型](../PF-009-context-message-types/design.md#toolinternalmessage)在成本上为什么说得通 |
| **「先一段、再往前接」仍然是纯派生的** | 「先加载一段」+ [PF-012「组装是纯派生的」](../PF-012-agent-loop-and-run/design.md#53-改日志的动作与纯派生的动作) | 给定一份日志和一个位置，取出来的那段是**确定的**。**「加载到哪了」是看的人那一边的事，不是日志的状态**。**必须写明这一条**，否则实现者会觉得「给用户的组装得记住加载到哪了」，于是**把那个位置写回日志**——**日志一旦被组装写脏，`f` 就不纯了**，而那是整个恢复机制的地基 |
| **两块必须分开的理由是「只有第二块压得动」** | 「分两块」这条裁决 + [PF-012「常驻那部分压不动」](../PF-012-agent-loop-and-run/design.md#55-想这一步交进闭包拿回装得下的一份) + [PF-004 系统提示词的成分在装配那一刻定死](../PF-004-agent-definition-and-assembly/design.md#54-为什么系统提示词必须落在第三列) | 两块**变化节奏完全不同**：一块恒定，一块每轮在长。混成一块就会长出「把系统提示词也收走一段」——**而那等于把 agent 的身份和能力清单压没了**。量预算时两块都要算，**能压的只有一块** |
| **要求二是「默认拒绝」，与 PF-006「不声明就是不能后台」同调** | 裁决原文「**明确了是给模型读**的」 | 措辞的重点在「**明确了**」——**不是「没标记就默认给」**。与 [PF-006 那条](../PF-006-tools-and-skills/design.md#66-前台后台-与-等待态是两个维度)同一个判据：**没表过态，不等于表了同意**。而这里的理由更硬一层：**误给收不回来**——模型看见了不该看的，就会拿它往下推理，**你没办法让它忘掉**。所以是「**宁可少给，不可误给**」：少给了还能再给一次 |
| **要求四与 PF-012「事件不许攒在内存里」是同一条的两面** | 要求四 + [PF-012 §5.12](../PF-012-agent-loop-and-run/design.md#511-外面进来的事怎么到-agent-眼前) | 那边管**写进来**（事件必须先落进日志），这边管**读出去**（组装不许在落盘之前开始）。**两句合起来才完整**。做不到的后果一样：崩一次，**模型看过的东西日志里没有**，恢复后重算出来的与当时发出去的不是同一份 |
| **要求一约束的不只是组装** | 裁决原文「**这也是给压缩策略的要求之一**」 | 前缀一致这件事，**组装单方面做不到**——压缩一旦重排了前面的历史，前缀当场作废。所以它**同时是压缩那一块的约束**，正文写在[要求一](design.md#要求一尽可能最大化前缀一致)末尾与 [§5.6](design.md#56-压缩是一个闭包它的调子是三个联合目标) |
| **第二块的名字本身就是两条要求** | 建模 `build_llm_readable_compaction_awared_context()` + 要求二、要求三 | 「给模型读的」对应要求二，「知道压缩这回事的」对应要求三。**不是先有要求再起名字，是这两件事本来就是这一步的定义的一部分** |
| **卡片答复分两种，判据与 PF-008 的两个维度是同一条** | 「分两种」这条裁决 + [PF-008「等待态是两个不同生命周期维度上的」](../PF-008-human-in-the-loop/design.md#等待态的两个维度) | 工具等待态的答复落成 `ToolMessage`，因为**那次工具执行还没完，答复是它的输入**；系统发起的落成 `SystemReminderMessage`，因为**没有哪次工具执行在等它**。**不是两条规则，是 PF-008 那条裁决的直接后果** |
| **三个目标两两相冲，所以「最优压缩」不存在** | 「三个联合目标」这条裁决 | 押住任意两个，第三个必然吃亏：**保前缀 + 保信息 → 长度降不下来**（什么都没动）；**保信息 + 降长度 → 前缀废了**（既要短又不许丢，只能重写重排）；**保前缀 + 降长度 → 信息丢得多**（前面动不得，只能往狠里砍）。**三角是从三个目标直接推出来的**，它说明产品这一层能定的只有「三个同时成立」，**取哪个平衡只能是策略** |
| **压缩只管「给模型看」那一侧，不碰「给人看」那一位** | 「标记一个块是否依然还是**模型可读**的」这条裁决的字面 | 裁决点名的是**模型可读**。而且这与[两侧形状不同](design.md#51-两侧形状不一样根子是人有记忆模型没有)自洽：**人那侧本来就不受预算约束**，压缩是为模型那侧的预算做的。**直接后果：被压掉的东西用户照样看得见** |
| **「不给模型看」不等于「可以删」，这句必须写出来** | 「无论是否模型可读都不能擦除」这条裁决 | 裁决特意加了「**无论是否**」，说明它防的正是「反正模型也读不到了，删了吧」这个念头。**读者不止模型一个**——被点名之后它对模型不存在了，**但对人、对排查、对回溯一直都在**。与 [PF-009 那处被纠正的判断](../PF-009-context-message-types/decisions.md#四已知的来源问题)同源 |
| **压缩的两个动作都不改写历史** | 两个「能做」+ 三个「不能做」+ **「名单自己带着」这条裁决** | 两个动作**落成同一条追加的消息**：摘要是它的内容，名单是它自带的。**没有任何一个动作会重写、搬走或回头修改已有的内容**——所以 [append only](../PF-012-agent-loop-and-run/design.md#会话日志) 这条**压缩不是例外** |
| **「哪些块还模型可读」是派生视图，不是存着的状态** | 「名单自己带着」这条裁决 | 名单挂在每一条 `CompactionMessage` 上，**块本身不带「后来被压掉了」这种状态**。于是那份视图只能是算出来的：**块上那一位标着给模型读，且没有任何排在它前面的摘要点过它的名**。**组装每次现算**，日志里找不到一个叫「当前可读集合」的东西可以直接读 |
| **(b) 比 (a) 强的地方是「日志能重放」** | 「名单自己带着」这条裁决 + [append only](../PF-012-agent-loop-and-run/design.md#会话日志) | (a) 是回头把块上那一位翻过来。它有一处说不过去：**一条早就落盘的消息，会因为后来发生的事而变了样**。代价两笔——**其一**，「这份日志在第 5 轮时是什么样」答不出来，那一位是第 9 轮翻的，回头看只剩最新那个值；**其二**，append only 破了一个口子，而且破在**已经交给模型看过的东西**上。(b) 下**任何一个时刻的视图都能由「排在那一刻之前的全部 `CompactionMessage`」算出来，日志本身一个字没被改过** |
| **硬约束与三个目标不是并列关系** | 「压缩完还超它自己就失败」这条裁决 + 「三个联合目标」那条裁决 | 硬约束是**后置条件**：不满足就是失败。三个目标是**调子**：在满足硬约束的前提下取的那个平衡。**两者地位不同**——把硬约束写成「第四个目标」，就等于允许它被别的目标压过去 |
| **「量一量」因此从方程里消失了** | 「判定在闭包内做」这条裁决 | 判定进了闭包，方程就**不必知道窗口有多大、当前有多长**——它只认「装得下 / 装不下」两个回执。**直接后果**：换一套压缩策略，[转移表](../PF-012-agent-loop-and-run/design.md#56-状态转移表)一个字不用动 |
| **「压完还超」是非常态，不是方程的一条分支** | 「它自己就失败（就是一种 off-normal）」这条裁决的字面 | 裁决把它明确归成 off-normal。**所以它沿 [PF-011](../PF-011-off-nominal-handling/README.md) 那条统一的路往外走**，而不是在转移表里多一行。**代价也要记下**：一次本可以降级凑合的请求，现在直接是一件非常态——**回旋余地留给了策略，不留在方程里** |
| **不许压新消息，除了「模型没看过」还挡住了一种抖动** | 第二条禁令 + [要求一](design.md#要求一尽可能最大化前缀一致) | 主理由是裁决自带的：**模型一次都还没看过，压了就永远看不到原文**，而它接下来要干的事恰恰依赖这些。**附带还有一层**：允许压最新的，就会这一轮压掉、下一轮又来新的再压掉——**每轮都在动尾巴，而尾巴一动下一轮前缀又变了**，要求一当场作废。**与 [PF-012「压缩救不了单条超限」](../PF-012-agent-loop-and-run/design.md#510-卸载结果落成消息之前的那一关)是同一条** |
| **压缩输入区间的两个界只由本 topic 说** | 第二条禁令 + 「判定在闭包内做」这条裁决 | 上界是「**上一次模型请求**」，不是「此刻」——两者之间隔着的正是模型还没看过的那一批新消息。下界**不是死的**：已有的摘要可以被再次收走。**闭包化之后 PF-012 不再复述区间**（它只知道「进了闭包，拿回一份装得下的」），**所以这两个界在整条链上只有一个说法** |
| **悬着的东西不许被点名，落点在本 topic** | [PF-012 §6.11](../PF-012-agent-loop-and-run/design.md#611-悬着的东西不许被压掉) 提的要求 | **「什么叫悬着」是那个方程定义域的一部分，归 PF-012**；**「压缩不能拿它怎么样」是压缩的动作边界，归这里**。两边各管一半——占位被点掉，agent 就不知道自己还有东西在外面跑，**而日志那一层它们还好端端悬着** |
| **块级标记，解释了组装边界为什么不是一条线** | 「标记一个**消息内容块**」+ [要求三那句限定](design.md#要求三有压缩记录时边界由压缩记录来定) | 裁决说压缩点的是**块**，不是一条截断线。**块可以散布**——被点名的和没被点名的前前后后都有。所以「这次取哪一段」的答案**本来就不是一个起点**，而是「**哪些块还模型可读**」，**而它们可能落在最后一条摘要之前**。**这正好解释了产品负责人明说不展开的那句「未必是从最后一条 `CompactionMessage` 开始选」**。**2026-09-18 经核对确认成立**：「这个解释是正确的」 |

### 2026-09-29 · 能力消费与服务依赖的边界

**直接输入**：[本轮交流 INT-005～008](../PF-004-agent-definition-and-assembly/interviews/2026-09-29-agent-runtime-assembly.md)：会话能力身份见过后保留，失去当前选择或实现时呈现不可用替换件；资产定义数据与执行实现解耦；会话类型必需与 AgentDefinition 显式必需同样不意味着 Loop 直接依赖能力背后的服务。

**本 topic 落点**：提示词组合规则与当前能力数据分开；数据更新可改变后续请求，不要求重建 Loop，压缩边界保持。

**PM 推导**：①“已知”与“当前允许执行”必须分别求值，否则单调性会变成绕过撤权；②实现更新可发生在稳定入口内部，故不从它推出提供者换代或 Loop 重建；③ schema 更新可能改变调用含义，故即使实例未换也须核对尚未发起的旧动作；已发工作继续沿原输入；④每次求值所需输入不同，故分别保存会话当前采用值、历史数据与实现依据和单次调用快照；⑤Session 是数据／归属，逻辑供给矩阵不推出它是 fiber；实际 inject 边与所有权仍需技术设计和验证。常驻呈现、Slash Command 人的入口及未合法纳入资产仍沿各自边界，不把单调性扩为无条件信息公开。

**已知来源问题与处置**：旧文把能力的选入、数据、实现与服务生命周期混作一种“绑定变化”，因此过度推导 Agent runtime 重建；PF-010 还把提示词成品与实例期固定混为一谈。按本次输入修订，差异记入 C-47。AgentDefinition 版本采用仍沿已拍板的新 Run 或显式 reload 安全交接，不以本次技术分析自行取消该产品边界。框架事实采用 Cordis 4.0.4，区分 provider fiber 换代与同 provider 的数据更新（[已验证 basis](../../basis/cordis/plugin-body-reruns-on-provider-change.md)）；本次额外检查发布包源码，不声称运行了新探针。项目只复用 Cordis，不采用 DSH agent 原语。
