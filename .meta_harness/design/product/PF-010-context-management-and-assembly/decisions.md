## 二、PM 推导

从已拍板内容推出的判断，附可核对的推理链。

| 结论 | 从哪几条推出 | 推理 |
|---|---|---|
| **两侧形状不同，根子是「人有记忆，模型没有」** | 「给用户先加载一段」+ 模型每轮要完整上下文 | 模型**不记得上一轮给过什么**，所以每轮都得给一整份；人**记得，而且能往上翻**，所以先给一段就够。**这不是两套实现凑出来的差别，是消费者本身不同**。由此还能解释两件已经定下的事：给人那份**不受上下文预算约束**（它本来就不打算一次给完），以及[工具帧只给人不给模型](../PF-009-context-message-types/design.md#toolinternalmessage)在成本上为什么说得通 |
| **「先一段、再往前接」仍然是纯派生的** | 「先加载一段」+ [PF-012「组装是纯派生的」](../PF-012-agent-loop-and-run/design.md#53-改日志的动作与纯派生的动作) | 给定一份日志和一个位置，取出来的那段是**确定的**。**「加载到哪了」是看的人那一边的事，不是日志的状态**。**必须写明这一条**，否则实现者会觉得「给用户的组装得记住加载到哪了」，于是**把那个位置写回日志**——**日志一旦被组装写脏，`f` 就不纯了**，而那是整个恢复机制的地基 |
| **两块必须分开的理由是「只有第二块压得动」** | 「分两块」这条裁决 + [PF-012「常驻那部分压不动」](../PF-012-agent-loop-and-run/design.md#55-想这一步先组装量完才知道要不要压) + [PF-004 系统提示词在实例存续期内恒定](../PF-004-agent-runtime-assembly-and-liveness/design.md#54-为什么系统提示词必须落在第三列) | 两块**变化节奏完全不同**：一块恒定，一块每轮在长。混成一块就会长出「把系统提示词也收走一段」——**而那等于把 agent 的身份和能力清单压没了**。量预算时两块都要算，**能压的只有一块** |
| **要求二是「默认拒绝」，与 PF-006「不声明就是不能后台」同调** | 裁决原文「**明确了是给模型读**的」 | 措辞的重点在「**明确了**」——**不是「没标记就默认给」**。与 [PF-006 那条](../PF-006-tools-and-skills/design.md#66-前台后台-与-等待态是两个维度)同一个判据：**没表过态，不等于表了同意**。而这里的理由更硬一层：**误给收不回来**——模型看见了不该看的，就会拿它往下推理，**你没办法让它忘掉**。所以是「**宁可少给，不可误给**」：少给了还能再给一次 |
| **要求四与 PF-012「事件不许攒在内存里」是同一条的两面** | 要求四 + [PF-012 §5.12](../PF-012-agent-loop-and-run/design.md#511-外面进来的事怎么到-agent-眼前) | 那边管**写进来**（事件必须先落进日志），这边管**读出去**（组装不许在落盘之前开始）。**两句合起来才完整**。做不到的后果一样：崩一次，**模型看过的东西日志里没有**，恢复后重算出来的与当时发出去的不是同一份 |
| **要求一约束的不只是组装** | 裁决原文「**这也是给压缩策略的要求之一**」 | 前缀一致这件事，**组装单方面做不到**——压缩一旦重排了前面的历史，前缀当场作废。所以它**同时是压缩那一块的约束**，本版在 [§9.1](design.md#91-组装那一侧留的两个接口压缩都接上了) 记下了这层关系 |
| **第二块的名字本身就是两条要求** | 建模 `build_llm_readable_compaction_awared_context()` + 要求二、要求三 | 「给模型读的」对应要求二，「知道压缩这回事的」对应要求三。**不是先有要求再起名字，是这两件事本来就是这一步的定义的一部分** |
| **卡片答复分两种，判据与 PF-008 的两个维度是同一条** | 「分两种」这条裁决 + [PF-008「等待态是两个不同生命周期维度上的」](../PF-008-human-in-the-loop/design.md#等待态的两个维度) | 工具等待态的答复落成 `ToolMessage`，因为**那次工具执行还没完，答复是它的输入**；系统发起的落成 `SystemReminderMessage`，因为**没有哪次工具执行在等它**。**不是两条规则，是 PF-008 那条裁决的直接后果** |
| **三个目标两两相冲，所以「最优压缩」不存在** | 「三个联合目标」这条裁决 | 押住任意两个，第三个必然吃亏：**保前缀 + 保信息 → 长度降不下来**（什么都没动）；**保信息 + 降长度 → 前缀废了**（既要短又不许丢，只能重写重排）；**保前缀 + 降长度 → 信息丢得多**（前面动不得，只能往狠里砍）。**三角是从三个目标直接推出来的**，它说明产品这一层能定的只有「三个同时成立」，**取哪个平衡只能是策略** |
| **压缩只翻「给模型看」那一位，不碰「给人看」那一位** | 「标记一个块是否依然还是**模型可读**的」这条裁决的字面 | 裁决点名的是**模型可读**。而且这与[两侧形状不同](design.md#51-两侧形状不一样根子是人有记忆模型没有)自洽：**人那侧本来就不受预算约束**，压缩是为模型那侧的预算做的。**直接后果：被压掉的东西用户照样看得见** |
| **「不给模型看」不等于「可以删」，这句必须写出来** | 「无论是否模型可读都不能擦除」这条裁决 | 裁决特意加了「**无论是否**」，说明它防的正是「反正模型也读不到了，删了吧」这个念头。**读者不止模型一个**——那一位翻掉之后，它对模型不存在了，**但对人、对排查、对回溯一直都在**。与 [PF-009 那处被纠正的判断](../PF-009-context-message-types/decisions.md#四已知的来源问题)同源 |
| **压缩的两个动作都不改写历史** | 两个「能做」+ 两个「不能做」 | 一个是**翻标注**，一个是**往后加一条摘要**。**没有任何一个动作会重写或搬走已有的内容**——所以 [append only](../PF-012-agent-loop-and-run/design.md#会话日志) 这条**压缩不是例外** |
| **不许压新消息，除了「模型没看过」还挡住了一种抖动** | 第二条禁令 + [要求一](design.md#要求一尽可能最大化前缀一致) | 主理由是裁决自带的：**模型一次都还没看过，压了就永远看不到原文**，而它接下来要干的事恰恰依赖这些。**附带还有一层**：允许压最新的，就会这一轮压掉、下一轮又来新的再压掉——**每轮都在动尾巴，而尾巴一动下一轮前缀又变了**，要求一当场作废。**与 [PF-012「压缩救不了单条超限」](../PF-012-agent-loop-and-run/design.md#510-卸载结果落成消息之前的那一关)是同一条** |
| **压缩输入区间的上界要精化 PF-012 那条** | 第二条禁令 + [PF-012 §5.5](../PF-012-agent-loop-and-run/design.md#55-想这一步先组装量完才知道要不要压) | PF-012 写的是「上一次压缩后到**这一次模型请求前**」。按这条禁令，**准确的上界是「上一次模型请求」**——两者之间隔着的正是模型还没看过的那一批新消息。**这是精化不是推翻**：原来那句的区间把尾巴多划进来了。**已在 PF-012 就地标注** |
| **块级标记，解释了组装边界为什么不是一条线**（**推导，待核对**） | 「标记一个**消息内容块**」+ [要求三那句限定](design.md#要求三有压缩记录时边界由压缩记录来定) | 裁决说压缩标的是**块**，不是一条截断线。**块可以散布**——被标掉的和没被标掉的前前后后都有。所以「这次取哪一段」的答案**本来就不是一个起点**，而是「**哪些块还模型可读**」，**而它们可能落在最后一条摘要之前**。**这正好解释了产品负责人明说不展开的那句「未必是从最后一条 `CompactionMessage` 开始选」**。**产品负责人当时明说原因不展开，2026-09-18 经核对确认成立**：「这个解释是正确的」 |

## 四、已知的来源问题

| 问题 | 影响 | 处置 |
|---|---|---|
| **PM 把「往前翻更早的」说成「同一个动作再来一次」** | 表达上有歧义——**两个动作的锚点不同**：切进会话那次锚在「最近」，往前翻那次锚在**当前已加载的最早点位**。照字面读，会实现成「又从最近取一段」 | **记下不改掉。**产品负责人纠正：「**不是同一个动作再来一次，是从当前已经加载的最早点位开始再往前多 prepend 一段**……**因为往下最新的有增量它自然继续加载**」。**PM 错在把两个方向当成了对称的两次拉取**，而实际上**一个是「往回要」，一个是「一直收着」**——后者根本不需要发起。已改写为 [§4「两个动作，方向相反」](design.md#给用户那一侧两个动作方向相反) |
| **PM 把「卸载后的占位算哪一种消息」列成了欠 PF-010 的账** | 它根本不是缺口——**产品负责人上一轮已经讲过**（占位 `ToolMessage`，取回是新增一个 tool call 和一个新的 `ToolMessage`） | **记下不改掉。**产品负责人指出：「**卸载后的占位啥意思啊，就是 ToolMessage 啊，这个流程我前面不是介绍给你了吗**」。**PM 错在把裁决写进了 [PF-012 §5.11](../PF-012-agent-loop-and-run/design.md#510-卸载结果落成消息之前的那一关)，却没回去把 [rev 1 §9.1](../PF-012-agent-loop-and-run/changelog.md) 那条「仍缺」划掉**——**落盘一处、缺口清单在另一处，两边没有对齐**。已回填 |
| **产品负责人给的两个动作带了具体协议**（`http get` / `http stream`） | 协议写进产品正文就是**把技术选型冒充产品需求** | **按产品负责人明确要求不记入正文**：「**这个 sse 这个你这里不要记录到文档中，因为这是具体的技术选型**」。正文只说**有两个不同的动作、各自锚在哪**；**怎么通信归技术设计**。原话保留在[交流笔记](interviews/2026-09-18-context-assembly.md)里，**因为那是原始材料** |
