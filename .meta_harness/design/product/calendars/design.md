# 日历产品设计

采用范围见[topic 入口](README.md)。项目要求取 [requirements](../../../../docs/requirements.md)，责任边界取[日历领域](../../../../docs/domains/calendars/README.md)。本文维护已确认的产品规则，工程机制和实际支持分别由技术拥有者及下表说明。

## 产品需求描述

“每月最后一个中国工作日”需要实际假日和调休依据，不能用星期几代替；一份长期安排也不能在日历覆盖耗尽后继续猜日期。日历为人、agent、系统和程序消费者提供可指认、可选择、可复核的日期知识。它独立承担供应数据、不可变版本、覆盖和健康，以及依指定依据计算日期的责任，不要求存在 Session、Schedule 或 Job。

<a id="calendar-model"></a>

业务日历声明适用范围，一国可以有多份含义不同的日历。已发布的业务日历版本带覆盖日期、信息截至时点及权威出处；新版本表达修订，旧版不原地改变。业务日历身份随适用范围建立，发布、切换当前版或恢复供应均不重建该身份。版本经校验发布后成为可复核的历史事实，修订新建版本，不覆盖或自动删除已发布版本。查询结果说明实际采用的身份和版本，供应健康另行说明。公开供应不是某个管理员的个人租户资料；租户消费者选择则仍归该租户，按既有设置和权限判断，不建立“当前环境日历”第二真相。

查询、选择配置和维护供应是三种操作资格。人能读取日历或 agent 装配了 Calendars 工具，不因此取得持久切换、供应刷新或发布权。用户生效环境由既有设置拥有者统一维护。跟随用户环境的安排采用其中自洽的时区与日历，显式绑定的安排保持指定身份；两者都不能改写已接受 Job。完整绑定规则归[日程的环境选择](../schedules-and-jobs/design.md#environment)。日历发布修订后，日程按安排的版本政策重核未接受候选；日历不接受 Job，也不把供应恢复当成漏过工作已执行。[通知](../notifications/design.md)单独承担送达。

供应范围包含中国法定节假日及补班、日本国民祝日及休日、美国联邦假日及 observed 和已生效行政令例外。美国联邦范围不表示全国所有主体放假。三份日历及其种子、更新、校验、历史和发行把关属于完整目标，不能只交付日期计算。

本范围不包括韩国、新加坡、沙特供应、美国州级假日、用户私有上传、会议邀请、个人日历同步或半日计算。可扩展供应能力不等于已经交付这些内容。新增地区仍须说明适用范围、权威来源和自身供应政策，不能改变已有日历身份与历史。

### J-CA01 找到并明确本次计算依据

使用者希望知道哪些日历可用，以及本次究竟使用哪一份。目录发现只要求合法查询范围及当前读取资格，允许不筛选，不要求事先提供日历身份、消费者生效选择或版本输入。目录展示身份、适用区域、时区、版本集、各版覆盖、出处及供应健康，并声明观察位置。

单历读取、解析及计算要求查询资格、日历选择及版本选择明确。使用者可以指定日历身份，也可以明确要求解析某个消费者上下文当前生效的日历，并同时指定某一已发布版本或“当前已发布版本”。选择当前版本时，一次查询只解析一次；指定版本不存在或不可用时不得退回当前版。解析结果给出实际身份和版本，后续计算可以直接用同一选择，也可以先解析再按返回的身份和版本计算；在相同解析依据下答案一致。

单历操作缺少日历选择或版本选择、消费者未配置生效日历、身份或版本不存在时明确说明，不能代选另一国日历或藏一个默认版本。无权读取时拒绝。目录或查询失败与合法空结果分开。退出查询不改配置或发布状态；单历查询响应丢失时可再次读同一明确版本，不能用后来“当前”变化解释旧答复。能力为 CAP-CA01、CAP-CA08。

### J-CA02 判断某日的全日日别

使用者希望知道指定日期在所选适用范围内是否为工作日、法定节假日或其他非工作日。前提是明确日历、版本和日期，而且该日期被实际覆盖。正常结果给出日别、命中的日期依据及实际版本；中国补班日按工作日解释，美国联邦范围如实标明。原供应只含半日事实时，将其保留在出处备注，不由它推成全天非工作日或宣称半日计算已成立。

覆盖外或覆盖有缺口时返回计算依据不足及边界；查询故障另报故障，不把未知日期当普通工作日或“没有假日”。无权者不因可猜身份而看到受保护的消费者配置。取消或再次查询无供应修改，恢复只读同版知识。能力为 CAP-CA02。

### J-CA03 增减或统计工作日

使用者希望从一个日期前后数 N 个工作日，或统计区间内工作日。前提是日历、版本、方向、数量或两个端点完整，计算经过的必要日期都有覆盖。增减从起始日之后或之前开始数；N 为零返回起始日，仍明确本次依据。区间计数包含两端日期。列出后续 N 个工作日严格从起始日之后开始；在月、自然季度或年内取第 N 个或最后一个工作日时，按同一版本逐日判定。返回日期或数量，并给出采用依据，使程序调用、工具调用与再次复核保持同义。

输入不合法或路径跨越未知覆盖时明确拒绝或缺依据，不从后面的已知日期跳过未知区间猜数，不静默补库默认的端点或方向。取消只结束本次计算请求；不存在需撤回的 Schedule 或 Job。重新计算同版可恢复查询，供应故障恢复不改变已有工作事实。能力为 CAP-CA03。

### J-CA04 核对一组有界日期解释

消费者希望先核对规则会落在哪些日期，前提是调用方已解释意图，给出明确规则、时区、范围或数量边界和必要日历版本。日历提供它所承担的日期计算及逐项依据；相同规则、时区、版本得到相同结果。整体 Schedule 预览由日程组合其规则、边界、排除、平移、夏令时与合并政策。以已有安排引用预览和展开同一实际定义预览应一致，日历对两种入口提供相同计算含义。

不支持的表达或必要依据不足时指出具体原因，不靠自然语言猜新意图，不返回伪造时刻。预览不保存安排、接受 Job、扣次数、触发动作或通知，也不预测实际执行时长与重叠结果。取消、超时或重试只影响计算请求。能力为 CAP-CA04。

### J-CA05 合法配置并切换消费者选择

获授权者希望改变之后明确采用消费者选择的计算，而不是维护一份法定事实。前提是既有租户设置的真实写资格、组织允许范围及目标日历使用条件成立。设置拥有者保存选择及修改主体、时点、旧值和新值，返回实际保存和生效结果。日历解析该权威设置，并使使用者能确认所用身份。每名用户只有一份权威生效日历选择；未设置时明确缺失，不代选。跟随环境的 Schedule 重算未接受未来，显式绑定不受偏好切换影响，已接受 Job 一律保持原依据。

只有读取资格、工具装配、人工卡片答复或管理员称谓时，不能推断写设置或供应管理权。非法值、无权或依赖失效时保留真实原因；保存回执未知沿原设置操作查询，不在日历另存成功副本。取消不撤回已成立的设置变更，后续改回也须合法写设置。供应管理配置由部署侧维护边界承担，合法来源与政策可配置，但不能绕过校验、版本和范围承诺。能力为 CAP-CA05。

### J-CA06 无网初始化并采用发布物种子

维护者希望正式发布物在没有网络时仍能提供其声明的日历。选择交付种子供应能力时，每份声明供应的种子必须来自受校验版本，完整覆盖发版日所在自然年，并包含发版时权威已发布的更远覆盖。先落地种子可用，再尽力联网刷新。覆盖内查询不因网络不可用而失败，安装时间不冒充信息取得时间。

种子不足不能宣称满足该发布物供应承诺；刷新失败保留种子和已有正确数据，分别呈现安装结果与刷新失败。重复初始化不重复铸造相同版本、不退回更旧种子。更新发布物包含新种子时，经相同校验与发布规则使其可用，离线升级也能取得新年份数据。中断或取消不撤回已确认的种子发布；恢复先核对原初始化结果，再继续未完成部分。能力为 CAP-CA06、CAP-CA07。

### J-CA07 持续发现、校验并发布修订

供应维护者希望跟随所声明日历的权威发布节奏，同时发现未来年度和已发布年度的合法修订。前提是供应资格、来源和当前采用政策明确。供应方能发现新权威文件，不只重取固定旧地址；保存候选及出处，校验完整性、覆盖和差异。通过后发布新的不可变版本，明确当前版，跨年覆盖累积。

覆盖收缩、关键假日缺失等退化候选不替换当前版。校验同时检查日期唯一性、覆盖连续性、关键节日、补班合理性、来源关系和独立核对结果。重叠日期有新可追溯出处的修改可校验发布；无新出处的静默修改留证待裁，不自动接受或丢弃。两个同源转写不算中国供应的独立来源。相同规范内容不重复发布。下载、格式检查和业务校验分开。失败或取消保留当前可用数据；发布回执未知先查询原提交，不把重发当恢复。日历发布成功不证明日程已采用或通知已送达。能力为 CAP-CA07。

### J-CA08 用历史版本复核旧答案

使用者希望解释旧计算或某次 Job 所采用的日期依据。前提是有权取得原日历版本和必要来源引用。指定历史版本仍可查询原覆盖和信息截至时点，计算得到原知识下的结果；最新修订不回写旧版。日程保存自己的实际采用关系，日历提供该版本知识，二者共同支持复核。

版本查询或介质不可用明确失败或受阻，不能拿当前版替旧版冒充复核。退出供应实例、结束安排、换缓存或用户失权不销毁已承诺的历史依据；读取仍按当前资格。恢复重建访问路径，不能从旧运行内存猜原数据。已发布版本保留，不引入自动清理或下架动作。能力为 CAP-CA08。

### J-CA09 观察供应风险并把关发布物

维护者希望在覆盖耗尽前看到风险，发布责任人希望辨认发布物数据是否足够新鲜。前提是每份日历的实际来源节奏、覆盖及有效告警政策可取得。展示覆盖、信息截至时点、最近成功更新、连续失败、待裁候选及覆盖余量；查询可用性与供应更新健康分开。按该历政策提前告警，不能以仍能回答旧日期隐瞒更新失败。

发布物达到所含日历的严重数据新鲜度条件时不能发行；警告条件须显式呈现，不用一个全局固定天数代替各历政策。政策缺失或状态不可确认时说明尚不能完成该把关，不伪造通过。告警不替日程选择补跑或执行动作；需要送达维护提示时由通知承担其事实。关闭观察或取消刷新不清除原风险；恢复后查询权威状态。能力为 CAP-CA09。

## 阶段与版本支持承诺

在 `0.0.0 → 0.1.0` 研发阶段，已确认的完整目标包含 CAP-CA01–CAP-CA09 和中、日、美三份日历。该范围包含源已承诺但尚未实现的供应及发行条件，不能以只完成纯计算宣告交付。具体发布日期和发布版本尚未指定，产品采用不等于 `0.1.0` 已支持。

独立日历消费者不必创建 Session、Schedule 或 Job。日程与工具入口消费同一日历事实，换提供者不能改变日别、来源、版本、覆盖和拒绝条件。技术候选库不属于产品依赖采用，也没有目标 Node 24 或性能通过声明。

### 可观察场景与交接顺序

下列演示在实现交付时执行，正文描述的是期望结果。

1. 断网完成初始化后，查询三份日历目录。应看到各自已发布版本、发版年覆盖、知识截至时点和出处；再查询覆盖内日期，应得到明确日别而不等待网络。
2. 选择中国补班周末并计算后续工作日。应把补班日算作工作日；随后计算跨覆盖边界的区间，应看到依据不足和边界，而不是猜测数量。
3. 对同一日期分别查询固定版本和当前版本，再发布有合法新出处的修订。固定版本答案保持，当前版本可变；历史版本仍能复核。无新出处的改写只显示待裁候选，当前版保持。
4. 更改用户环境后同时观察跟随安排、显式安排和已接受 Job。仅跟随安排的未接受未来跟随切换；显式安排保持身份，Job 保持原采用依据。
5. 制造供应失败但保留覆盖内数据。旧日期仍能查，供应失败和覆盖风险可见；严重风险阻止发行，未知状态不能显示把关通过。

交接建议先验证同版查询和工作日运算，再验证三历离线供应、更新及发行，最后与日程验证环境变更及历史冻结。供应政策与真实发布物是后两项的必要前提，演示通过不替代产品负责人接受。

## 未决问题与待定事项

以下事项只保留交付版本与未闭合的技术证据。三历和九项能力的完整目标已确定，不再等待能力取舍。

<a id="q-ca01"></a>

### Q-CA01 发布版本与产品交付接受

完整能力范围已确定。产品负责人尚须指定承诺这些能力的发布版本、实际装配及交付接受条件。不能从研发区间或文档采用推出已经发行，不能因发布日期未定而删减设计范围。

### Q-CA02 公开形状、算法与日历计算消费映射

独立调用者和核对日程的用户需要在相同日历版本下得到一致日期，并分清覆盖不足、合法空结果与查询故障，见 J-CA01 至 J-CA04。精确接口、算法对照与消费映射的采用及验证由技术拥有者负责，缺少目标运行证据时不能声称两条计算路径已能互相复核。

技术拥有者为日历公开定义、日期计算及查询适配拥有者，日程整体预览协调者承接消费映射。完整问题、约束、选项及承接义务见[技术采用 Q-CA02](../../../../packages/calendar/calendar/docs/internals.md#q-ca02)。

<a id="q-ca03"></a>

### Q-CA03 供应发布一致性与耐久恢复

供应维护者在并发发布、回执丢失或断电后需要查清原修订是否发布，使用者仍须能按原版本复核旧答案，见 J-CA07、J-CA08。发布恢复机制未采用时，尚不能确认当前版不会指向半份数据、重复铸造版本或覆盖后来已发布的修订。

技术拥有者为日历供应/版本协调者及实际存储提供者。完整问题、约束、选项及承接义务见[技术采用 Q-CA03](../../../../packages/calendar/calendar/docs/internals.md#q-ca03)。

<a id="q-ca04"></a>

### Q-CA04 设置、供应治理及生命周期集成

获授权者切换消费者选择时需要确认实际生效结果、跟随安排的未来变化和已接受工作的原依据，维护者与发布责任人需要按各历政策识别风险，见 J-CA05、J-CA09。治理与生命周期集成未采用时，这些操作及发行把关仍缺少可核对依据，维护实例退出也不能证明历史版本和未完责任已经消失。

技术拥有者为既有设置/权限拥有者、供应治理与发布物拥有者、日历提供者及装配拥有者。完整问题、约束、选项及承接义务见[技术采用 Q-CA04](../../../../packages/calendar/calendar/docs/internals.md#q-ca04)。
