# 2026-09-17 转移与分享

开题交流。本 topic 由产品负责人主导发起，在一次会话内从「一个动作」扩展到「两个动作」。

## INT-001

- 标题：开题——先明确最小的几个不变量
- 时间/顺序：本次会话，PF-002 收口之后
- actor：**产品负责人本人**
- 表达方式：`quote`
- 内容：「还有一块和账号-租户相关的嘛，就是「资产转移」。怎么理解呢，首先我们明确最小的
  几个不变量：1）资产只能从个人组织向公司/团队组织方向转移，不能将公司/团队组织的资产
  转移到个人组织；2）转移到本质是 fork，也就是转移后，如果个人组织的资产变更了，不连带
  影响公司/团队组织的；3）更新后的要同步到团队/公司需要再次执行「转移」动作，通过类似
  patch 的机制完成覆盖」
- 上下文：这块在 PF-002 的非目标里被预告过（「个人与组织之间的资产共享、携入、转让」）
- 状态：当前有效。三条分别落在 design.md §6.1、§4「转移」、§6.6

## INT-002

- 标题：记录者对「转移」一词与实际语义之间张力的观察
- actor：**记录者（AI）**，非产品负责人
- 表达方式：`recorder-interpretation`
- 内容：三条不变量合起来定义的行为是 **fork + 交付**（源保留、目标独立拥有），
  而「转移」一词字面暗示源侧消失。PF-002 的非目标里预留的是「共享、携入、转让」三个词，
  其中**转让**（所有权易手、源消失）与**共享**（同一实体两边消费）都被这三条不变量排除。
- 上下文：为核对 INT-001 与 PF-002 预留范围的对应关系
- 状态：当前有效。处置见 decisions.md 第四节——**保留原叫法**，含义由性质定义承载

## INT-003

- 标题：全量覆盖替换，不要 git 那一套
- 时间/顺序：记录者就「目标侧改过之后再转一次怎么办」给出两个选项之后
- actor：**产品负责人本人**
- 表达方式：`quote`
- 内容：「现在的转移（如果目标组织里有身份实质相同的同一份资产），我们转移的语义就是
  全量覆盖替换，不要考虑什么 git 的 conflict 探测、merge 之类的哈，就是替换，简单粗暴」
- 上下文：记录者当时提的两个选项是「覆盖，目标侧本地改动不进新版本」与
  「目标侧改过就拒绝，逼人先处理」，并倾向前者
- 状态：当前有效。落在 design.md §6.6
- 记录者注：裁决后记录者**收回**了自己上一轮提的「能力标识撞车要显式确认」，
  改为只以血缘作判据——那条额外确认在「简单粗暴」的要求下是多余的，
  而且用血缘作判据反而更不容易误伤。见 decisions.md 第二节对应条目。

## INT-004

- 标题：不变量 1 是系统级的
- actor：**产品负责人本人**
- 表达方式：`quote`
- 内容：「不变量1你的理解就是对的，防止的就是把公司/团队资产资源带出来」

- 状态：当前有效。这条把记录者的推导**升格为裁决**

## INT-005

- 标题：组织之间要能表达隶属；分享是另一种语义
- 时间/顺序：记录者已开始起草正文时插入，本条实质上把 topic 的范围扩大了一倍
- actor：**产品负责人本人**
- 表达方式：`quote`
- 内容：「公司->公司 这个，就是在 团队/公司组织（也就是非个人组织），我们的模型可以再多
  一种组合关系：一个团队是一个家公司下的，一个家公司是另一家的子公司，这种关系模型要能够
  表达出来。个人 -> 个人 和 公司 -> 公司，提供一种「分享」的语义，个人 -> 个人 的分享
  没有限制，公司/团队 -> 公司/团队 的 限制是关系上必需是父子或者亲戚（拥有至少一个共同
  祖先）。然后「分享」和「转移」不一样，转移 是变更影响链直接断了（除非下一次再转移做全量
  替换），而 分享 则是被分享方无变更权只能被动同步分享方的变更。然后 公司/团队 组织之间，
  存在血缘关系的，且账号同时存在两个组织之间，且资产是源组织的这个租户的而不是组织级的，
  也可以「转移」」
- 上下文：记录者此前把「公司→公司」判为非目标，理由是「那是跨组织分发，与本 topic 的
  出发点无关」。本条**推翻了那个判断**
- 状态：当前有效。落在 design.md §4「分享」、§5.1、§6.2、§6.3
- 记录者注：末句三个并列条件里，「资产是源组织的这个租户的而不是组织级的」这一条，
  暴露出 [PF-001 §6.7](../../PF-001-identity-scope-and-agent-constraints/design.md#67-创作与归属)
  的归属表缺了「在租户范围创作」这一行——补上之后，
  「为什么租户级的能带走、组织级的不能」才有依据。

## INT-006

- 标题：别把组织关系设计复杂化
- 时间/顺序：记录者正准备为组织隶属建立独立概念时打断
- actor：**产品负责人本人**
- 表达方式：`quote`
- 内容：「这个我觉得其实就是组织的属性拓展吧？避免设计得复杂化」
- 上下文：记录者当时在考虑「组织树是不是新概念、要不要单独一节、祖先/后代怎么定义」
- 状态：当前有效。落在 [PF-001 §4](../../PF-001-identity-scope-and-agent-constraints/design.md#组织)
- 记录者注：这条**顺带定死了单父**——一个属性容纳一个值。要表达一个组织有两个母公司，
  需要的是一张关系表而不是一个属性，那恰恰是被这句话排除的复杂化。
  它也与 INT-005 里「拥有至少一个共同祖先」的措辞存在张力，处置见 decisions.md 第四节。

## INT-007

- 标题：不同账号创建的组织能否建立关系，这个问题必须被回答
- actor：**产品负责人本人**
- 表达方式：`quote`
- 内容：「然后肯定会有人问，那一个组织是一个账号创建的，由两个不同账号创建的组织，
  能否建立关系呢？我觉得这个问题需要能够被回答。」
- 上下文：记录者当时把「上级组织」的确定时机写成了「创建时指定，此后不变」，
  那个写法表达不了并购与重组
- 状态：当前有效。落在
  [PF-001 §4「隶属关系怎么建立与解除」](../../PF-001-identity-scope-and-agent-constraints/design.md#隶属关系怎么建立与解除)
- 记录者注：回答这个问题时排除掉「单方面指定」之后，只剩「双方超管各做一次」这一种做法，
  而 PF-001 的「邀请与加入」已经是这个形状。真正的收获在**解除之后**：
  分享失效、转移留存——这一格成了两个动作最实在的分水岭，
  也回过头来给了使用者一个选择依据。
