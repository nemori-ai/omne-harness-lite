## rev 3 · 「转移」改名「资产复制」；待确认的邀约有过期 — 2026-09-22

产品负责人同日两条直接裁决（[决策记录](decisions.md#一拍板记录)）。

### 一、「转移」改名「资产复制」

**原话：「『转移』改名『资产复制』」。**

| 改了什么 | 从什么改成什么 |
|---|---|
| **这个动作的正式名** | 「转移」→ **「资产复制」**。理由是**源侧不消失**——它的实质是 fork 一份，旧名字与性质反着走 |
| **词条** | 新立 [UL-asset-copy · 资产复制 · Asset Copy](../../ubiquitous_language/terms/circulation-and-entitlement.md#ul-asset-copy--资产复制--asset-copy)，形态沿用「过程」；**旧 ID `UL-asset-transfer` 进弃用**。[UL-transfer-lineage](../../ubiquitous_language/terms/circulation-and-entitlement.md#ul-copy-lineage--复制血缘--copy-lineage) 同样换 ID，改名**复制血缘 Copy Lineage** |
| **§4 两个小节标题** | 「转移」→「资产复制」；「血缘」→「复制血缘」。**锚点随之变化** |
| **§6.3 · §6.4 · §6.5 · §6.6 · §6.9 标题** | 「复制的通则」「可复制的对象」「首次复制」「重复复制」「复制或分享一个 plugin」。**§6.4 的锚点变化**，[UL-asset-version](../../ubiquitous_language/terms/capabilities-and-composition.md#ul-asset-version--资产版本--asset-version) 与[资产版本的对象条目](../../domain_objects/objects.md)已改到新锚点 |
| **§7 取舍末行** | 原来是「沿用『转移』这个叫法 ／ 改叫『贡献』→ 沿用」，现在是「这个动作叫『资产复制』」，并写明新名字自己的代价——**「复制」是个常见词**，所以词条明写「裸写不作数」 |
| **topic 标题** | front-matter 的 `title` 与正文抬头改为「资产的复制与分享」。**目录名 `PF-003-asset-transfer-and-sharing` 不改**——改目录会牵动全仓链接 |

**`decisions.md` 的拍板记录保留当时的说法「转移」**，那是记录不是现行用词；
[已就地写明](decisions.md#一拍板记录)。

### 二、待确认的复制通知与分享邀请有过期

**原话：「通知和邀请作过期机制，资产本身不存在的话相关的通知和邀请也要自动过期」。**

| 定死了什么 | 落在哪 |
|---|---|
| 待确认的**复制通知**与**分享邀请**都会过期；**时长可配、有默认**，具体多少是政策 | [§6.14](design.md#614-待确认的复制通知与分享邀请会过期) |
| **它指向的那份资产不存在了，相关邀约自动过期** | 同上 |
| 过期后的收场：**不可再确认**，什么都没建立，**发起方可以重新发起**；与撤回同一个结局 | 同上、[flows §3.4](flows.md#34-一份待确认的邀约复制通知与分享邀请同形) |
| 「待确认」这一段**另有三个出口**（撤回 / 到期 / 资产没了） | [flows §3.2](flows.md#32-一段分享关系)、[§3.4](flows.md#34-一份待确认的邀约复制通知与分享邀请同形) |
| 过期之后再点确认 **被拒**；邀约指向的资产被移除时**自动失效** | [flows §2](flows.md#二分支与异常) |

**与 rev 2 那条「分享不过期」不冲突**：那条说的是**确认之后**的使用权，
这条说的是**确认之前**的邀约。[§6.10 已就地点明这是两段时间](design.md#610-分享给的是获权不是拥有)。

**待确认的邀约没有另立概念**——它是两个动作各自状态机上的一个状态，
推理链见 [decisions 第二节](decisions.md#二pm-推导)。

### 三、rev 2 留下的两条待裁决全部闭合

「待确认通知要不要过期」与「『转移』改叫什么」都已裁决，
[`decisions.md` 第三节](decisions.md#三待裁决)现在是**无**。

### 下游要复核什么

- **任何按「转移 / Transfer」命名的实现或契约**——现在叫**资产复制 / Asset Copy**，
  血缘叫**复制血缘 / Copy Lineage**。
- **任何把待确认的邀约做成永不过期的实现**——现在它有过期，且**资产消失会让它自动过期**。
- **[PF-001](../PF-001-identity-scope-and-agent-constraints/changelog.md) 的邀请同一条裁决一起加了过期**（rev 8），两处口径相同。

## rev 2 — 2026-09-22

**转移与分享都要对方确认才发生；分享确认之后的使用权没有期限，没有暂停。**

产品负责人 2026-09-22 三条直接裁决（[决策记录](decisions.md#一拍板记录)）：

- **转移是「通知—确认」**：发起方发出转移通知，目标组织确认，才 fork 一份过去、所有权归目标组织。
  rev 1 把它写成执行者单方面完成的动作，目标侧只有一个「接收」的资格——那个说法退役；首次与重复转移都要确认。

- 使用权是**对一份资产可用性的权利声明**——定义者直接有；被分享方从确认起一直有，直到分享方撤销、自己移除或隶属关系解除。
  **本版不设有效期，也没有暂停这个状态。**
- **分享本质上是邀请使用**：分享方发出、被分享方确认，使用权关系才建立。rev 1 把分享写成单方面的「授予」，
  对方的可用集合里立刻出现它——那个说法退役。与 PF-001 的邀请同一个形状。

落在 [§4 资产复制](design.md#资产复制)（当时叫「转移」）、[§4 分享](design.md#分享)、[§6.6](design.md#66-重复复制全量覆盖替换)、[§6.10](design.md#610-分享给的是获权不是拥有)；
flows 的 §1.1～§1.5（各多一步确认）、§3.1、§3.2（多了「待确认」态）、§4（多了确认与撤回两行）。
新开两条待裁：待确认的通知要不要过期（与 PF-001 邀请一起定）；「转移」改叫什么。

这一版同时闭合了统一语言的 [C-15](../../ubiquitous_language/conflicts.md#现有冲突)：
[PF-001 §6.6](../PF-001-identity-scope-and-agent-constraints/design.md#66-撤销不等于强制停止) 原先顺带写着「使用权暂停或到期」，
那两个状态从没有任何地方定义过；本裁决之后那里改为「撤销分享」，词条 `UL-usage-right` 的形态定为**属性**。

**下游要复核什么**：引用 §4 的词条（`UL-asset-transfer`、`UL-asset-sharing`、`UL-usage-right`）所指变了——两个动作都多了确认这一步；
其余引用本 topic rev 1 的条款没有动。

## rev 1 — 2026-09-17

**首版。**回答 [PF-002](../PF-002-assets-settings-and-permissions/README.md) 没有回答的问题：
资产**怎么进到一个组织里**。

### 这一版确定了什么

| 方面 | 结论 |
|---|---|
| 有几个动作 | **两个**：转移与分享。它们在所有权归属上相反，一个机制表达不了 |
| 转移是什么 | **同一个自然人的两个租户身份之间**的搬运。目标方**独立拥有**一份，此后断链 |
| 分享是什么 | **主体之间的授权**。所有权不动，被分享方**不能改**，**被动跟随**源方的新版本 |
| 边界在哪 | **那棵隶属树**，不是单个组织。个人组织永远在所有树之外 |
| 什么能转 | **只有本人拥有的**：个人组织里的，或团队里他**租户级**的。组织级的不能转，要流动走分享 |
| 重复转移 | **全量覆盖替换**。不做冲突探测、不做合并；产生新版本并**立即生效** |
| 覆盖多少 | **只覆盖内容**。目标组织配的设置与权限值不动，包括标了 `immutable` 的 |
| 判据是什么 | **血缘**，不是能力标识。且由系统判定，不由执行者选 |
| 关系断了之后 | 分享**失效**，转移**留着** |

### 同时改动了 PF-001

本 topic 需要的两个答案属于身份与组织模型，落在
[PF-001 rev 5](../PF-001-identity-scope-and-agent-constraints/changelog.md)，
不在这里另立一份：

- 组织多一个属性**「上级组织」**，以及隶属关系怎么建立与解除；
- 补齐**租户范围创作的所有者是该租户**——「为什么租户级的能带走、组织级的不能」
  的依据就在这里。

### 下游要注意的五处

- **转移与分享不能合并成一个带开关的机制。**它们的所有权归属相反，
  合并之后每条规则都要分支，而且最容易搞错的恰恰是分支条件。
- **全量覆盖只覆盖内容。**把目标组织配的设置与权限值一起冲掉，是安全事故。
- **判首次还是重复只看血缘。**看能力标识会冲掉对方自己做的同名组件。
- **不变量是系统级的。**任何能让团队资产落到个人组织的路径都被挡住，
  不止叫「转移」「分享」的这两个。做导出、打包、另存为模板时要回到这条核对。
- **隶属关系不能单方面建立。**允许单方面指定下级，等于给一个人开了条边界后门。

### 本版刻意不做的四件事

上级对下级的**强制管控**、被分享方**钉版本**、分享的**传递**、
个人组织 → 团队组织的**分享**。

四者的理由各不相同，见 [design.md §2](design.md#非目标)。
共同点是：**加是加法，不用改已有结构**——真实需求出现时再加，不必改动现有形状。

### 本版留下的缺口

- **未决项：无。**
- **待裁决：无。**

被排除的内容在 [design.md §2 非目标](design.md#非目标)，那是**边界**——
发现它们缺失不算缺陷。下游遇到本文档没回答的问题，应当停下来问，
而不是挑一个看起来合理的实现。

## 怎么记下一版

改变含义就递增 rev 并在这里加一节。判断标准：
**读者需要据 rev 判断自己手上的理解是否还成立吗？**需要，就记。

每节至少说清三件事：改了什么含义、为什么、下游要复核什么。
