## 二、PM 推导

从已拍板内容推出的判断，附可核对的推理链。

| 结论 | 从哪几条推出 | 推理 |
|---|---|---|
| **资产复制有两条通则：本人型与组织型** | 2026-09-24 规则 2、3；2026-09-17「账号同时存在于两个组织」 | 规则 3 管「自己的」：同一个自然人在两个组织各有一个租户，东西从他的一个租户到另一个；规则 2 管「同树的」：组织级对组织级。方向表里每一个「复制」格子都落在这两条之一——个人组织 → 我在 T 的租户级、我在 T 的租户级 → 我在 T′ 的租户级（规则 3），T 组织级 → T′ 组织级（规则 2）；「个人组织 → T 组织级」是规则 3 由超管改选组织级（2026-09-24 第三条）。**每一个「不可以」的复制格子，都是两条都够不着**。不是若干特例，是两条通则 |
| **个人组织之间只有分享、没有资产复制** | 上一条、2026-09-17「个人→个人……分享」 | 两个个人组织必属两个不同账号，规则 3 够不着；个人组织不在任何树上，规则 2 也够不着。裁决也正是给这一对配了分享 |
| **分享不要求分享方与被分享方是同一个人** | 「个人→个人的分享无限制」 | 若要求同一人，个人→个人这一格就不存在了。所以分享是**主体之间的授权**；而资产复制交出的是所有权，只在同一个人或同树两个组织之间发生 |
| **边界是那棵隶属树，不是单个组织** | 不变量 1「防止带出来」、2026-09-24 规则 2、3 | 若边界是单个组织，组织—组织与本人型的跨组织复制就该一律禁止；既然同树内允许，边界就画在树上。**个人组织的上级恒为空，因此永远在所有边界之外**——这也是它之间的分享"无限制"的真正原因：那把尺子量不到它们 |
| **不变量 1 也挡住团队里租户级的资产** | 「防止把公司/团队资产资源带出来」 | 租户级资产的所有权归个人，但它诞生在团队的上下文里，用的是团队的信息与语境。若因所有权归个人就放行，一个人只要把东西一直放在租户级，这条不变量就完全失效 |
| **「从租户范围提升到组织范围」不可逆** | [PF-001 §6.7](../PF-001-identity-scope-and-agent-constraints/design.md#67-创作与归属)、规则 2 | 若可退回，组织级的资产先退回某人的租户级、再以本人型带去同树的另一个组织，「组织级之间要两边超管各点一次头」这一关就白设了 |
| **团队→个人的分享也禁止** | 不变量 1 | 分享虽不转移所有权，但团队的内容进入了个人组织的求值。"带出来"看的是内容到没到边界外，不是所有权归谁 |
| **分享方删除了已分享出去的资产，那段分享随之结束** | [flows §二「分享方删除之前要先告知受影响的一方」](flows.md#二分支与异常)、§6.10「分享给的是获权不是拥有」 | 分享指向的是分享方那份资产；资产没了，分享无物可指，只有「结束」一个答案。告知义务不变，删除之后被分享方看到的是「已删除」。落点：`capability.asset-transfer` v2 S-52（主线 2026-09-24 R2-4） |
| **重复复制产生新版本，且立即生效** | 「全量覆盖替换」、PF-002「已发布版本不可变」「不静默替换已选用的版本」 | 版本不可变，所以"覆盖"只能是发布一个新版本，旧的仍在。而 PF-002 那条防的是**被动**收到上游新版；资产复制是**落进那一层的管理者自己要的**写入——本人型是本人发起，组织型是目标超管点头——主动要的结果立即生效，本来就是他要的。两条不冲突 |
| **覆盖的是内容，不含目标侧配的设置与权限值** | PF-002：配值的最小单位是（身份层, 资产, 项）→ 值 | 那些值属于配它的**那一层**，不是资产内容的一部分。一次复制把对方配好的执行权限冲掉，那是安全事故。`immutable` 同理——它约束的是层级覆盖，而复制是有权决定那一层要什么的人做的写入 |
| **判首次还是重复，只看血缘，不看能力标识** | 「全量覆盖替换」 | 拿能力标识作判据，一次复制就能把对方自己做的同名安全组件冲掉，而执行者可能不知道它存在。用复制血缘则只覆盖"自己复制过去的那一份"，覆盖自己的东西天经地义 |
| **这个判定由系统做，不由执行者选** | 上一条 | 让执行者选「新增还是覆盖」，等于把一个可能冲掉对方资产的决定交给一个未必了解对方现状的人 |
| **复制血缘在落进的那一层里找，不在整个目标组织里找**；同一个来源在一个组织里可以有租户级一份、组织级一份，血缘挂在「来源 → 目标组织某一层的那一份」上 | 2026-09-24 第三条（普通成员落租户级、超管可选组织级）；「由系统判定、不由执行者选」；主线 2026-09-24 在两种做法中选定此做法 | 一次复制可以落在两层之一，就要回答血缘在哪儿找。**按层找不需要任何额外规则**，与「普通成员落自己的租户级、超管可选组织级」直接相容：执行者定的是落进哪一层，系统在那一层里判首次还是重复。**按整个组织找要补两条**：血缘找到的那份此刻在组织级、而本人型发起者不是超管时怎么办；一份资产先被本人型复制到我在 T′ 的租户级、后被提升为 T 的组织级、再被组织型复制到 T′ 时，血缘会指到我租户级那份，而组织型写不进别人的租户级。**代价只是血缘定义多一个层**，以及同一来源在一个组织里可以有两份——按层级求值各管各的范围，这本来就是层的用法。「在哪一层」按本 topic 的说法指它归谁：提升之后那份归组织，原作者再复制一次，落他租户级新的一份 |
| **草稿不可复制** | PF-002「已发布版本不可变」 | 复制一个还在变的东西，接收方拿到的内容说不清是哪个状态，而整个版本模型建立在不可变之上 |
| **首次复制的所有者：落在哪一层就归谁** | 2026-09-24 第三条（「是隶属租户下的」「组织级别……还是他自己这个租户自己用」）、[PF-001 §6.7](../PF-001-identity-scope-and-agent-constraints/design.md#67-创作与归属) | 租户范围的所有者是那个租户、组织范围的所有者是那个组织。复制落在哪一层，就按那一层定 |
| **首次复制的作者：本人型是 (目标组织, 本人)；组织型是 (目标组织, 确认的那位超级管理员)** | [PF-001 §6.7](../PF-001-identity-scope-and-agent-constraints/design.md#67-创作与归属) | 作者表达「那个组织里的谁产出了它」，必须是目标组织里的一个租户。本人型是他以该组织成员身份带进来的。组织型里，发起的超级管理员代表的是源组织，未必是目标组织的成员；**把它带进目标组织的是点了头的那位**——没有他的确认它不会落下。源侧那份的作者不动——两个资产两条记录，各自准确 |
| **本人型不需要第二个人确认，复制与分享都是** | 2026-09-24 第二、三条（普通成员复制进组织「不需要超管确认」）、规则 3、[PF-002「租户层由本人管」](../PF-002-assets-settings-and-permissions/flows.md#31-一个资产在某个范围里) | 裁决点名的是个人组织 → 团队这一路；同一个道理覆盖全部本人型：本人型落在他自己的租户级，管它的就是他；超管改选组织级时，管组织级的也是他。**两侧都是同一个人，让他向自己确认一次是空动作**。本人型分享同理：接收的租户就是他自己 |
| **确认由落进那一层的管理者做** | 上一条；矩阵「T′ 超管确认」；规则 1「被共享者用不用他自己确认」 | 四类确认——本人型不需要、组织内分享由接收者本人、组织—组织由目标超管、个人间由对方——都是这一条的实例。它让「谁能替一方确认」与「谁能替它移除」只有一个答案 |
| **组织内分享并入资产分享，接收方是一个租户；不另立新词** | 规则 1；2026-09-22「分享本质上是邀请使用」；2026-09-24 第一条「分享是双方确权的一个动作（同邀请）」 | 规则 1 的「开放」与「对方自己确认用不用」，就是分享的发出与确认；所有权不动、对方不能改、被动跟随、可撤销可移除——四条性质一条不差。差的只是接收方是一个租户。另立一个动作，就要再定一套确认、过期、撤销与关系解除后的处理，而每一条都只会照抄分享的 |
| **跨组织落不到别人的租户级** | 规则 2、3 | 规则 2 只许组织—组织，规则 3 只许落「自己在其他组织的另一个租户下」；别人的租户级两条都不是。道理：跨组织能做主的只有同一个人或两个组织，往别人的租户级写，那个组织没有点头，那个人的租户级又是他的私有部分。要给他用，有「先到我自己的租户级、再组织内分享」这条每一步都有人点头的路 |
| **普通成员对组织级资产没有复制或分享的动作** | 矩阵只有「T 的超管，动组织级的」一行；规则 2；矩阵「T′ 超管确认」 | 组织型由源组织的超级管理员发起；组织级资产在本组织里谁能用归「谁可以使用它」。普通成员对组织级资产既不是所有者、也不是它那一层的管理者 |
| **个人组织 → 团队组织级只有复制，没有分享** | 矩阵个人组织行「同团队 T 的组织级」一格只写「复制」 | 那一格与相邻写「复制和分享」的格子写法不同，只列了复制。道理也在：组织级若持有一份成员私域里的东西，整个团队的运行就建在他的私域上，他随时能改能撤；而分享到他自己的租户级，只影响他自己 |
| **个人组织那一行「同树 T′」「不同树」各列：我在 T′ 也是成员时，T′ 对个人组织就是另一个 T** | 规则 3；矩阵个人组织行「同树 T′ 里我的租户级」一格的备注「个人组织不在任何树上，走『我在 T 的租户级』那一格再往下」 | 个人组织不在任何树上，「与 T 同树」对它无从谈起；规则 3 说自己的资产可以到「自己在其他组织的另一个租户下」，并不挑是哪一个团队。所以那几列的「不可以」说的是**没有一条按树走的路**，不是说个人组织到不了 T′——T′ 若也是我所在的团队，它就是这一行的另一个 T，按前几列读 |
| **被分享来的不能提升到组织级** | [PF-001 §6.7](../PF-001-identity-scope-and-agent-constraints/design.md#67-创作与归属)「持有使用权不自动获得……转让」 | 提升是一次所有权的交付，他从来不是所有者。放开的话，我把个人组织的东西分享到我的租户级、再提升，个人组织 → 团队组织级就多出一条不是复制的路，而那一格只有复制 |
| **关系断了又接上，分享不复活——重新隶属与重新加入都是** | 2026-09-24 第一条 | 原话针对隶属；给的理由「分享是双方确权的一个动作……解除……可以认为是分享方取消……或者被分享方自己放弃」对成员关系同样成立：组织内分享与本人型分享的一方是一个租户，它的成员关系解除，在这段分享上同样等于一方收了手。flows §3.2 的「结束」是终点，再分享是新的一段 |
| **被分享方是一个租户时，它的成员关系解除，这段分享即结束** | 规则 1、上一条、[PF-001：退出后租户不再有效](../PF-001-identity-scope-and-agent-constraints/design.md#退出之后再加入回来的是同一个租户) | 被分享方不再是有效的租户，就不再是这段分享的一方；而分享没有暂停这个状态（2026-09-22） |
| **分享方是一个租户时，它的成员关系解除，这段分享也结束** | [PF-001](../PF-001-identity-scope-and-agent-constraints/design.md#退出之后再加入回来的是同一个租户)「成员关系解除期间，这个租户的租户级私有部分不可达……没有任何身份能够到达它们」；2026-09-22「分享没有暂停状态」 | 分享方退出后，他租户级的那份资产谁也够不着，被分享方也就用不上；「分享中」要求能用，而又没有暂停可去，唯一自洽的是结束。重新加入不复活，理由同上两条 |
| **待确认的复制通知、分享邀请与一段分享关系，都是被逐份指认的对象** | 2026-09-24 第一条（「不复活，应当重新分享」「分享是双方确权的一个动作（同「邀请」）」）；PF-001 把[邀请与隶属请求](../PF-001-identity-scope-and-agent-constraints/design.md#隶属关系怎么建立与解除)定为两种对象 | 「不复活，应当重新分享」说明结束了的一段与再分享的一段是**两段**——一段分享关系被单独指认、有自己的生灭。复制通知与分享邀请与邀请、隶属请求同形：可撤回、可过期、发起时带时长、再发是新的一份——同理是对象；[flows §3.4](flows.md#34-一份待确认的邀约复制通知与分享邀请同形) 与 [PF-016 §6.14](../PF-016-cli-tui-delivery-surface/design.md#614-没有带外通知所以进来就要看得见等着的事) 本来就逐份指名它们。**此前「它们不另立一个概念、只是两个动作各自的一个状态」那条推导作废**：它的前提「没有人需要单独指名它」已不成立 |
| **被分享方选用的是「分享方当前发布的那一版」这个动态目标** | 「只能被动同步分享方的变更」、PF-002 版本模型 | 这样表述，每个已发布版本仍然不可变，而「不静默替换已选用的版本」说的是消费方对版本的自主权——被分享方选用的本来就是动态目标，且他知道，这正是分享的定义 |
| **不提供「钉在某个版本上」** | 「被动同步」 | 钉住就不是被动同步了。那实际上是要一份 fork，而那个动作叫资产复制。两个动作各司其职，不互相模仿 |
| **被分享方可以配自己那层的值、可以替换、可以移除** | 「无变更权」的范围、PF-002 的层级模型 | 「无变更权」针对的是**资产内容**。设置与权限的值属于（他那一层, 资产, 项），是他自己那一层；用别的资产顶上、或者移除，是他对自己求值链的支配权 |
| **本版的分享不带强制** | 上一条、[上级组织不进作用域层次](../PF-001-identity-scope-and-agent-constraints/design.md#组织) | 强制需要跨组织的**管辖权**。裁决只说了隶属关系要能表达，没有人裁决过它附带管辖权。凭空给它加上，是把「隶属」偷换成「被管辖」 |
| **分享不可传递——组织内与本人型分享来的也一样** | [PF-001 §6.7](../PF-001-identity-scope-and-agent-constraints/design.md#67-创作与归属)：持有使用权不自动获得编辑、fork、转让或扩大对外共享的权力 | 不是新规则，是已定条款的直接适用，与接收方是组织还是租户无关。可传递的话，B 一次转手就能把 A 的东西送到与 A 无关的 C，隶属树这条边界被绕开 |
| **关系解除后：分享失效，复制来的留存** | 两个动作各自的所有权归属 | 分享给出去的只是**获权**，范围条件不成立了它就没有依据；资产复制是所有权**已经易手**，能被收回的所有权不是所有权。这一格也给了使用者一个决策依据：要不要让对方在关系结束后还能用 |
| **发起方指定的时长是「发起这个动作时的一个参数」，不是一项[作用域](../PF-001-identity-scope-and-agent-constraints/design.md#61-层次)配值** | [2026-09-22 的时长裁决](#一拍板记录)（原话从数据的角度给的：「邀约这个动作本质上是发出一份数据……四类有各自的默认值+动作发起者可自行填参覆盖」） | 它**只对这一份邀约成立**：跟着这份数据走，这份邀约结束它就不存在了。四层里配的是**对某个范围长期有效的值**，两者不是一回事。真把它当成配值，就得回答「组织级设的时长要不要覆盖发起方填的」——而那个问题不该存在：**填参的人就是发起这个动作的人**。所以它**不进四层**。**与 [PF-001 那边同一口径](../PF-001-identity-scope-and-agent-constraints/decisions.md#二pm-推导)** |
| **复制通知与分享邀请各有各的默认时长，不共用一个** | 同上：「**四类**有**各自的**默认值」 | 裁决的措辞已经把这件事定死了。它本来也只能这样：一份送资产过去、等对方点头的复制通知，和一份邀请对方用自己东西的分享邀请，合理的窗口长度不必相同，共用一个数必然有一类被将就 |
| **具体数值仍不在产品这一层定** | 裁决只说「各有默认值」，没给数字 | 默认多少**要按部署与客群调**，写死一个数字就是把政策当成设计。产品该定的是**有没有这个出口、谁能改它、到期之后怎么收场**，三件都已经定死。这与本设计链一贯的口径一致——[阈值、重试、退避都是策略](../PF-012-agent-loop-and-run/design.md#二目标与非目标) |
| **过期与撤回收场完全相同** | 两者都发生在「待确认」这一段 | 待确认这一段**什么都还没建立**：没有使用权、目标那边也没有那份资产。所以无论是谁让它结束，**结束之后都是「什么都没有」**。**不同的只有谁让它结束**——撤回是发起方，过期是时间或资产的消失替他做了这件事 |
| **已经确认过的不受过期约束** | [「确认之后的使用权不过期」是 2026-09-22 先一轮的裁决](#一拍板记录) | 两条裁决说的是**两段不同的时间**：一段在点头之前，一段在点头之后。**同一个词「不过期」在这两段上的答案相反，所以必须把时间段写清楚**，否则读者会以为后一条裁决被推翻了 |
| **成本按使用方的租户归属** | PF-001：成本按租户归属 | 谁在用就算谁的。资产归谁与谁在消耗是两件事 |
| **资产复制与分享都不进入 agent 的运行语义** | 两者都是治理层动作 | agent 只看到某个能力标识下现在生效的是哪一份。让它感知资产的来路，等于把治理结构泄进运行时 |
