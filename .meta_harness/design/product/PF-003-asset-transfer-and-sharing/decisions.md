## 二、PM 推导

从已拍板内容推出的判断，附可核对的推理链。

| 结论 | 从哪几条推出 | 推理 |
|---|---|---|
| **转移的通则：执行者必须同时是源租户和目标租户** | 「账号同时存在于两个组织之间」、个人组织只有一个成员 | 这一条把四个格子一起解释了：个人→他的团队是同一账号；团队→团队裁决里明确要求账号两边都在；个人→别人的个人组织**不可能**是同一人（两个个人组织必属两个账号）；团队→个人虽是同一人但被不变量 1 挡住。四个结论不是四条特例，是一条通则的四次应用 |
| **个人组织之间只有分享、没有转移** | 上一条 | 两个个人组织必属两个不同账号，永远凑不出"同一个自然人的两个租户身份"。裁决也正是给这一对配了分享 |
| **分享不要求分享方与被分享方是同一个人** | 「个人→个人的分享无限制」 | 若要求同一人，个人→个人这一格就不存在了。所以分享是**主体之间的授权**，与转移的**身份之间的搬运**是两回事 |
| **边界是那棵隶属树，不是单个组织** | 不变量 1「防止带出来」、团队→团队转移需要共同上级 | 若边界是单个组织，团队→团队的转移就该一律禁止；既然同树内允许，边界就画在树上。**个人组织的上级恒为空，因此永远在所有边界之外**——这也是它之间的分享"无限制"的真正原因：那把尺子量不到它们 |
| **不变量 1 也挡住团队里租户级的资产** | 「防止把公司/团队资产资源带出来」 | 租户级资产的所有权归个人，但它诞生在团队的上下文里，用的是团队的信息与语境。若因所有权归个人就放行，一个人只要把东西一直放在租户级，这条不变量就完全失效 |
| **组织级资产不可转移，只可分享** | 「资产是源组织这个租户的而不是组织级的」、[租户级资产的所有者是该租户](../PF-001-identity-scope-and-agent-constraints/design.md#67-创作与归属) | 判据统一成一句话：**你能给出去的只能是你自己的**。组织级那份的所有者是组织不是他。允许组织级转移，等于一个有资格的人就能把整个组织的资产复制到别处 |
| **「从租户范围提升到组织范围」不可逆** | 上一条 | 若可退回，把组织级资产先退回租户级再转走，上一条就白写了 |
| **个人→团队不提供分享** | 分享的定义（所有权不动、源方可随时撤销） | 团队若用分享获得成员的东西，日常运行就建立在一个成员的私域上——他随时能改、能撤，团队毫无办法。这类需要已经有转移覆盖 |
| **团队→个人的分享也禁止** | 不变量 1 | 分享虽不转移所有权，但团队的内容进入了个人组织的求值。"带出来"看的是内容到没到边界外，不是所有权归谁 |
| **重复转移产生新版本，且立即生效** | 「全量覆盖替换」、PF-002「已发布版本不可变」「不静默替换已选用的版本」 | 版本不可变，所以"覆盖"只能是发布一个新版本，旧的仍在。而 PF-002 那条防的是**被动**收到上游新版；转移是目标组织**主动执行**的写入，主动写入的结果立即生效，本来就是执行者要的。两条不冲突 |
| **覆盖的是内容，不含目标侧配的设置与权限值** | PF-002：配值的最小单位是（身份层, 资产, 项）→ 值 | 那些值属于目标组织**这一层**，不是资产内容的一部分。一次转移把对方配好的执行权限冲掉，那是安全事故。`immutable` 同理——它约束的是层级覆盖，而转移是同一级的写入 |
| **判首次还是重复，只看血缘，不看能力标识** | 「全量覆盖替换」 | 拿能力标识作判据，一次转移就能把对方自己做的同名安全组件冲掉，而执行者可能不知道它存在。用血缘则只覆盖"自己转过去的那一份"，覆盖自己的东西天经地义 |
| **这个判定由系统做，不由执行者选** | 上一条 | 让执行者选「新增还是覆盖」，等于把一个可能冲掉对方资产的决定交给一个未必了解对方现状的人 |
| **草稿不可转移** | PF-002「已发布版本不可变」 | 转一个还在变的东西，接收方拿到的内容说不清是哪个状态，而整个版本模型建立在不可变之上 |
| **目标侧那份的作者是 (目标组织, 执行者)** | [PF-001 §6.7](../PF-001-identity-scope-and-agent-constraints/design.md#67-创作与归属) | 作者表达「那个组织里的谁产出了它」。目标侧那份是**新对象**，诞生动作就是这次转移，执行者是以该组织成员身份做的。源侧那份的作者不动——两个资产两条记录，各自准确，且不暴露源组织 |
| **被分享方选用的是「分享方当前发布的那一版」这个动态目标** | 「只能被动同步分享方的变更」、PF-002 版本模型 | 这样表述，每个已发布版本仍然不可变，而「不静默替换已选用的版本」说的是消费方对版本的自主权——被分享方选用的本来就是动态目标，且他知道，这正是分享的定义 |
| **不提供「钉在某个版本上」** | 「被动同步」 | 钉住就不是被动同步了。那实际上是要一份 fork，而那个动作叫转移。两个动作各司其职，不互相模仿 |
| **被分享方可以配自己那层的值、可以替换、可以移除** | 「无变更权」的范围、PF-002 的层级模型 | 「无变更权」针对的是**资产内容**。设置与权限的值属于（他的组织, 资产, 项），是他自己那一层；用别的资产顶上、或者移除，是他对自己求值链的支配权 |
| **本版的分享不带强制** | 上一条、[上级组织不进作用域层次](../PF-001-identity-scope-and-agent-constraints/design.md#组织) | 强制需要跨组织的**管辖权**。裁决只说了隶属关系要能表达，没有人裁决过它附带管辖权。凭空给它加上，是把「隶属」偷换成「被管辖」 |
| **分享不可传递** | [PF-001 §6.7](../PF-001-identity-scope-and-agent-constraints/design.md#67-创作与归属)：持有使用权不自动获得编辑、fork、转让或扩大对外共享的权力 | 不是新规则，是已定条款的直接适用。可传递的话，B 一次转手就能把 A 的东西送到与 A 无关的 C，隶属树这条边界被绕开 |
| **关系解除后：分享失效，转移留存** | 两个动作各自的所有权归属 | 分享给出去的只是**获权**，范围条件不成立了它就没有依据；转移是所有权**已经易手**，能被收回的所有权不是所有权。这一格也给了使用者一个决策依据：要不要让对方在关系结束后还能用 |
| **成本按使用方的租户归属** | PF-001：成本按租户归属 | 谁在用就算谁的。资产归谁与谁在消耗是两件事 |
| **转移与分享都不进入 agent 的运行语义** | 两者都是治理层动作 | agent 只看到某个能力标识下现在生效的是哪一份。让它感知资产的来路，等于把治理结构泄进运行时 |

## 四、已知的来源问题

| 问题 | 影响 | 处置 |
|---|---|---|
| 裁决原话用的是「父子或者亲戚（拥有至少一个共同祖先）」，「**至少一个**」在单父模型里没有意义——任意两个同树组织必然共享根 | 措辞暗示可能想要多父。但同一轮裁决又明确要求「就是组织的属性拓展，避免设计得复杂化」，一个属性只能容纳一个值 | **已按单父落稿**，判据写成「有共同上级」，该表述对多父同样成立。若日后要表达合资公司，改的是 PF-001 的属性形态，本 topic 的判据不用动 |
| 「转移」这个词字面暗示源侧消失，而实际语义是 fork + 交付，源侧保留 | 使用者可能误以为转完之后自己那份就没了 | **保留原叫法**（见 design.md §7 末行）。含义由 §4 的性质定义承载，不靠名字承载 |
