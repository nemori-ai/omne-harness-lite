# PF-003：资产的复制与分享

- 修订：rev 6，2026-09-27 · [变更历史](changelog.md)
- 状态：本轮工作区一致性增量为草稿；此前接受范围及现存未决项见 [README](README.md#状态)，本次不扩大接受或已实现范围。

## 一、背景与问题

[PF-002](../PF-002-assets-settings-and-permissions/design.md) 说清了一个范围**持有**
资产之后会发生什么——怎么配、怎么组装、谁能改。但它没说资产**怎么到一个范围里来**：
怎么从一个组织进到另一个组织，怎么从一个成员手里到另一个成员手里。

资产要在主体之间流动，背后是**两种根本不同的需要**：

- **我要把它交出去，让你独立拥有。**我在自己地盘上捣鼓出一个好用的 skill，
  给团队用；集团做了一套模板，子公司要拿去按自己的情况改。此后你改你的、我改我的，谁也不牵连谁。
- **我要让你能用，但它还是我的。**集团的安全组件下发到各子公司，
  我升级了你就跟着升级，你不能改它；同一个团队里，我做的工具同事也用上，但它还是我的。

一个机制表达不了这两种需要，混在一起的后果很具体：**只有"交出去"**，
集团下发的标准组件立刻失控——每个子公司都能改，改完还叫同一个名字；
**只有"能用"**，个人给团队的东西永远捏在个人手里，团队的日常运行建立在
某个成员的私域上，他一撤销就停摆。

反方向还有一条边界：**团队投入资源产出的东西，不该随人流出去。**
成员离职、子公司被卖掉，都不该成为资产流失的口子。

本 topic 定义这两个动作、它们各自能在谁和谁之间发生，以及它们共同遵守的那条边界。

## 二、目标与非目标

### 目标

1. **定义复制与分享**，说清两者在所有权、修改权、联动方式上的分别。
2. **定死方向与范围**：谁和谁之间可以流动、什么方向、落在哪一层、要谁点头。
3. **定义重复复制**：同一份东西改好了再给一次，会发生什么。
4. **说清关系解除之后各方还剩什么**——这是两个动作最实在的分水岭。

### 非目标

| 不做什么 | 为什么 |
|---|---|
| **强制管控**：上级组织强制下级必须用某个资产、不许替换 | 那需要跨组织的**管辖权**。[隶属关系在 PF-001 里是事实陈述](../PF-001-identity-scope-and-agent-constraints/design.md#组织)（谁属于谁），不附带管辖权，上级也不进作用域层次。真要做集团管控，是另一个 topic |
| **分享的传递**：被分享方再分享给第三方 | PF-001 已定：[持有使用权不自动获得扩大对外共享的权力](../PF-001-identity-scope-and-agent-constraints/design.md#67-创作与归属)。可传递的话，一次转手就能绕开边界 |
| **租户级 → 组织级的提升** | 归 [PF-001 §6.7](../PF-001-identity-scope-and-agent-constraints/design.md#67-创作与归属)：那是同一个组织里所有权的一次交付，不是流向另一个主体。本 topic 只在[方向表](#62-谁能流向谁)里指路 |
| **组织级资产在本组织里给谁用** | 归 PF-002 的权限项[「谁可以使用它」](../PF-002-assets-settings-and-permissions/design.md#谁可以使用它是各类资产共用的一项权限)。组织级的东西本来就是全组织的，不需要再分享一次 |
| 冲突探测、三方合并、版本线分叉 | 复制语义是**全量覆盖替换**，根本没有"合"这个动作 |
| 被分享方「钉在某个版本上」 | 钉住就不是被动同步了——那实际上是要了一份 fork，而那个动作叫复制 |
| 「源侧有更新」的提示（针对复制） | 会把源侧的活动暴露给目标侧。何时再复制一次，由发起方决定——本人型是作者本人，组织型是源组织 |
| 隶属关系本身怎么建立、怎么解除 | 那是组织属性的事，归 [PF-001 §4](../PF-001-identity-scope-and-agent-constraints/design.md#隶属关系怎么建立与解除)。本 topic 只管关系成立或断开之后**资产**怎么样 |
| 资产怎么创作、修订、发版 | 归 PF-002 与开发发布流程。本 topic 只管**已发布版本在主体之间的流动** |

## 三、用户与场景

| 使用者 | 他在什么情况下接触这块 | 他关心什么 |
|---|---|---|
| **既是个人开发者、又是团队成员的人** | 自己捣鼓出一个好用的 skill 或 plugin，想带进团队 | 给出去之后我自己那份还在吗？要不要等管理员批？后来改好了怎么再给一次？ |
| **想把自己的工具给同事用的成员** | 在团队里自己做的东西，同事也想用 | 能不能直接给他用，而不必先交给组织？他不想要了怎么办？ |
| **在集团内跨公司调动的人** | 在 A 公司攒了一套自己的私人工具，调到 B 公司 | 我自己的东西能不能跟着我走 |
| **集团的平台或安全团队** | 要给各子公司下发标准组件，或给一份模板让它们自己改 | 他们能不能改？关系断了之后还能不能用？ |
| **团队管理员** | 有成员把东西带进组织，或别的组织要给我们一份 | 会不会把我们现有的冲掉？我们配好的权限会不会被冲掉？进组织级的东西是不是都经过我？ |
| **对资产外流负责的人** | 成员离职，或子公司被卖掉 | 我们的东西会不会被带走 |
| **两个互不隶属的个人** | 朋友做了个好用的 skill | 能不能直接给我用 |
| **agent** | 在某个租户下运行，用到流进来的资产 | 它感知不到——只看到某个能力标识下现在生效的是哪一份 |

最后一行是有意的：**复制与分享都是治理层的动作，不进入 agent 的运行语义。**

本 topic 说的「团队组织」「公司组织」，指个人组织之外的所有组织，
也就是 PF-001 里**可邀请**的那些。不是新概念，只是需要一个词把它和个人组织对着说。

本 topic 说一份资产「**在组织级**」「**在租户级**」，指的是它**归谁**：组织级的所有者是那个组织，

### 资产复制

**资产复制是把自己拥有的一个资产的某一个已发布版本送出去，在另一个组织里建立或更新一份独立资产的动作。**
它只有两条通则：

- **本人型：同一个自然人的两个租户身份之间。**源是他本人拥有的资产——他个人组织里的，
  或团队里他租户级的；落在他**在另一个组织里的租户级**。源在他的个人组织里、
  而他是目标组织的超级管理员时，他也可以选择落在那个组织的**组织级**。
- **组织型：同一棵隶属树上的两个团队组织之间。**源是源组织**组织级**的资产，
  由源组织的超级管理员发起；**目标组织的超级管理员确认之后**，落在目标组织的组织级。

五条性质，每条都能被一个反例否定：

- **跨主体的复制要对方确认；本人型不需要。**组织型的发起只产生一份待确认的复制通知；
  目标组织的超级管理员点了头，fork 才落下来——首次和重复都一样，重复复制是全量覆盖，
  更不能不经对方点头就写进去。本人型两侧都是他自己，**发起就是两侧的同意**。
- **源保留。**复制之后源侧那份照旧在、照旧能改。
- **落下的那一份独立拥有。**落在租户级的，所有者是那个租户；落在组织级的，所有者是那个组织。
- **此后各走各的。**源侧的后续改动不自动流向目标侧，目标侧的改动也不回流。
- **执行者在源与目标都有租户身份——只对本人型成立。**组织型是两个组织之间的事，
  由各自的超级管理员代表；发起的人不必是目标组织的成员。

第四条是前面几条的推论，但值得单列——它是使用者最容易误解的地方。
很多人以为复制建立了某种"链接"，此后两边保持一致。没有这回事。
组织型在确认之前，发起方可以撤回这份通知；对方不确认它就不发生。
**那份通知不会一直悬着——[它会过期](#614-待确认的复制通知与分享邀请会过期)。**

| 属性 | 业务含义 | 取值与约束 | 何时确定 |
|---|---|---|---|
| 源 | 复制的是哪一份、哪一版 | **发起方拥有的**资产——本人型是他本人的，组织型是源组织组织级的——加上它的某一个**已发布版本**；草稿不可复制 | 发起时 |
| 目标 | 落在哪 | 本人型：他在另一个组织里的**租户级**；源在个人组织、且他是目标组织的超级管理员时，可以改选那个组织的**组织级**。组织型：同树另一个团队组织的**组织级** | 发起时 |
| 是首次还是重复 | 决定新增还是覆盖 | 由**血缘**在落进的那一层里判定 | **系统判定，不由执行者选** |

最后一行有意做成系统判定：让执行者选「这次是新增还是覆盖」，
等于把一个可能冲掉对方资产的决定，交给一个未必了解对方现状的人。

### 分享

**分享是一次「邀请使用」：分享方把自己拥有的一个资产的使用权开放给另一方，
对方确认之后，对方的使用权才建立。所有权不动。**

接收的一方有两种：

| 接收方 | 什么时候是它 | 谁确认 |
|---|---|---|
| **另一个组织** | 同一棵树上两个团队组织之间（组织级对组织级）；两个个人组织之间 | 对方组织的超级管理员——个人组织就是那个账号本人 |
| **一个租户** | 本组织里的另一个成员；或我自己在另一个组织里的租户（本人型） | 那个租户本人；是我自己的，不需要第二个人 |

接收方是本组织里另一个成员的那一种，叫**组织内分享**。它**就是分享**，不另立一套：
所有者「开放」就是发出分享邀请，对方「用」就是确认。

它与 [PF-001 的邀请](../PF-001-identity-scope-and-agent-constraints/design.md#隶属关系怎么建立与解除)同一个形状：
一方发出、另一方确认才成立，不另造一套。**没有确认就没有使用权**——对方的可用集合里不会出现它。
**那份邀请同样[会过期](#614-待确认的复制通知与分享邀请会过期)。**
本人型两侧都是他自己，发起即生效，不经过「待确认」这一段。

四条性质：

- **给的是获权，不是拥有。**用的是 [PF-001 已有的那组概念](../PF-001-identity-scope-and-agent-constraints/design.md#拥有获权选用)，不新造。
- **要对方确认才成立。**分享不是单方面塞给别人一样东西；正因为使用权是对方点头才建立的，他事后才有「移除」这个动作。
- **被分享方不能改它。**内容仍归分享方。
- **被分享方被动跟随。**分享方发布了新版本，他用到的就是新版本。

**复制交出一份所有权，分享只开放使用权**——这是两者最根本的分别。
分享能到的对方也因此更宽：本组织的同事、另一个人的个人组织，复制都到不了。
**交出所有权只在两种当事人之间发生：同一个人，或同一棵树上各由超级管理员点了头的两个组织。**

### 复制血缘

**复制血缘是目标侧那份资产与它的来源之间的对应关系：这一份是从哪个源复制过来的。**
它挂在落进**目标组织某一层**的那一份上——来源 → 目标组织那一层里的那一份。

它只用来回答一个问题：**再复制一次的时候，该更新目标组织那一层里的哪一份。**

- 复制血缘在**首次复制时产生**，此后不变。
- 一份资产要么有一条，要么没有（这个组织自己创作的没有）。
- 它**不传递**。
- **层与层各算各的。**同一个来源在一个组织里可以有两份——某人租户级一份、组织级一份，
  各有各的血缘，按[层级求值](../PF-001-identity-scope-and-agent-constraints/design.md#62-三种合成语义)各管各的范围。
  「在哪一层」按本 topic 的说法，[指它归谁](#承接-pf-001-与-pf-002)。

它对目标组织的可见程度有意做得很浅：**能看到「由某租户在某时送进来第几版」，
看不到源资产本身。**组织之间默认互不可见，个人组织尤其是账号的私域——
知道东西是谁交进来的是治理需要，知道他那边还有什么不是。

## 五、模型

### 5.1 两种需要，两个动作

| | **复制** | **分享** |
|---|---|---|
| **是谁的动作** | **本人型**：同一自然人的两个租户身份之间；**组织型**：同一棵树上两个团队组织之间，由双方的超级管理员代表 | 所有者的授权：把使用权开放给**另一个组织**，或**一个租户**（本组织的同事、我自己在别处的租户） |
| **源资产必须是谁的** | **本人型**：执行者本人拥有的（个人组织里的，或团队里他租户级的）；**组织型**：源组织拥有的（组织级） | 分享方拥有的 |
| **所有权** | 落下的那一份**独立拥有**（fork）——落在谁那一层，就归谁 | **不动**，仍属分享方 |
| **对方能改吗** | 能，那已经是他的了 | **不能** |
| **此后的联动** | **断链**。除非再复制一次做全量替换 | **被动同步**。分享方改了就跟着变 |
| **关系解除之后** | **留着** | **失效** |

最后两行是使用者最该记住的：

> **你要不要让对方在关系结束之后还能用，决定了你该复制还是该分享。**

### 5.2 边界是那棵隶属树，不是单个组织

```text
    ┌──────── 同一棵隶属树 = 一个边界 ────────┐
    │                                          │
    │            集团 G                        │      个人组织 P_A    个人组织 P_B
    │          ┌───┴───┐                       │        （孤立）       （孤立）
    │       公司 C1   公司 C2                  │            │              │
    │          │                               │            └───分享───────┘
    │       团队 T1                            │                无限制
    └──────────────────────────────────────────┘

    树内跨组织：组织级 ⇄ 组织级（复制或分享，两边的超级管理员各点一次头）
               我的租户级 → 我在另一个组织的租户级（复制或分享，只有我自己）
    组织内：    所有者把租户级的资产分享给同事（对方点头）
    个人组织 → 我所在的团队：复制或分享到我的租户级；我是超管时还可复制到组织级
    出树：一律不可
```

「团队资产不出团队」，精确说是**不出那棵隶属树**。

个人组织的上级恒为空、也不能作别人的上级
（[PF-001 §4](../PF-001-identity-scope-and-agent-constraints/design.md#个人组织)），
所以它**永远不在任何树上**，永远在所有边界之外。

两个个人组织之间也因此**永远没有共同上级**。这解释了为什么它们之间的分享
要单独给一条规则：**共同上级这个判据对它们压根用不上**——不是把门放宽了，
是那把尺子量不到它们。

个人组织到团队组织那一路同样不看树：它能到的只是**我自己所在的**团队，
而那一路归「自己的东西」那一条（[§6.2 规则 3](#62-谁能流向谁)）。

## 六、产品规则

### 6.1 一条不变量：团队资产不出那棵树

本节的资产指组织层、租户层拥有或持有的资产，其流转沿本 topic 的复制与分享规则。获准租户分别装配同一工作区的来源，是 [PF-020 的参与关系](../PF-020-workspace/design.md#租户工作区关系)，不等于把这些私有资产复制或分享给对方；也不能借工作区参与绕过原有组织、租户资产的外流约束。

**任何在团队组织里的资产，都不得进入任何个人组织。**
无论它是组织级的，还是某个成员租户级的。

这条不是"某个动作的一条规则"，是**系统恒真的性质**。它约束的不止复制与分享——
导出、另存为模板、「拷到我的空间」、打包下载，任何能让团队资产落到个人组织的路径，
都被同一条挡住。一条保护性质的不变量，如果能从另一扇门绕过去，它就不成其为不变量。

**租户级的资产也一样挡住**，哪怕它的所有者是那个人自己。因为它是在团队的上下文里
产出的：用的是团队的信息、团队的工具、团队的语境。所有权归他，
不改变它诞生在那条边界之内这个事实。

它有一个使用者会有感的后果，是有意的：

> 作者把 X 复制给团队之后，在团队侧继续改进 X′ 的那些工作，**带不回自己的个人组织**。
> 分叉之后，团队那条线上的改进属于团队。

### 6.2 谁能流向谁

**三条规则**，下面那张表是它们逐格的展开：

1. **组织内：所有者可以把自己的资产向本组织里的任何一个成员开放使用权。**
   被开放的人用不用，他自己确认。这就是[组织内分享](#分享)。
2. **同一棵树上跨组织，只有组织—组织。**组织级对组织级，复制或分享都行，
   两边的超级管理员各点一次头。
3. **自己的资产，可以复制或分享到自己在另一个组织里的租户下**——
   只要不是团队组织到个人组织，也不跨树。

主语是「我」（动作发起方，本人）；T 是我所在的团队组织；T′ 是与 T 同一棵隶属树上的另一个团队组织。

| 我是… | 别人的个人组织 | 我在 T 的租户级 | 同团队 T 的组织级 | 同团队 T 的其他租户 | 同树 T′ 的组织级 | 同树 T′ 里我的租户级 | 同树 T′ 里别人的租户级 | 不同树 |
|---|---|---|---|---|---|---|---|---|
| 个人组织下的租户 | 分享 | 复制和分享（规则 3） | 复制（仅我是 T 超管才落组织级） | 不可以（先到我的租户级，再按规则 1） | 不可以 | 不可以（个人组织不在任何树上，走「我在 T 的租户级」那一格再往下） | 不可以 | 不可以 |
| T 的普通成员（动我租户级的） | 不可以（团队 → 个人） | — | 提升 | 分享（规则 1：我开放，对方自己决定用不用） | 不可以（规则 2：同树只有组织 – 组织） | 复制和分享（规则 3） | 不可以 | 不可以 |
| T 的超管，动我租户级的 | 不可以 | — | 提升 | 分享 | 不可以 | 复制和分享 | 不可以 | 不可以 |
| T 的超管，动组织级的 | 不可以 | — | — | 不需要分享：组织级资产谁能用，是 PF-002 的权限项「谁可以使用它」 | 复制和分享（规则 2；T′ 超管确认） | 不可以（规则 2） | 不可以 | 不可以 |

「提升」= PF-001 §6.7 租户范围 → 组织范围的不可逆提升，不是本 topic 的动作，表里只作指路。

**怎么读这张表：**

- **个人组织那一行的「同树 T′」「不同树」各列**：个人组织不在任何树上，「与 T 同树」对它无从谈起。
  **我在 T′ 也是成员时，T′ 对这一行就是另一个 T**——按前几列读。
- **「—」**：这个方向不成立，资产本来就在那里。
- **组织级的资产只由超级管理员动。**表里没有「普通成员动组织级的」那一行：
  普通成员对组织级资产，既没有复制出去、也没有分享出去的动作。
- **团队组织 → 我自己的个人组织**不在列里：它被 [§6.1](#61-一条不变量团队资产不出那棵树) 挡住，与「别人的个人组织」那一列同理。
- **个人组织 → 团队的组织级只有复制，没有分享。**组织级若持有一份某个成员私域里的东西，
  整个团队的运行就建在他的私域上——他随时能改、能撤。
- **表里没有的组合，回到产品设计确认，不要自行补一条。**

**确认由谁做：**

| 动作 | 谁确认 |
|---|---|
| 本人型复制、本人型分享 | **不需要第二个人**——两侧都是我 |
| 组织内分享 | **接收的那个租户本人** |
| 组织—组织的复制或分享 | **目标组织的超级管理员** |
| 个人组织 → 另一个个人组织的分享 | **对方**，即那个账号本人 |

四行是同一个道理：**东西要落进哪一层，就由那一层的管理者点头**——
组织级由超级管理员管，租户级由那个租户本人管
（[PF-002 flows §3.1](../PF-002-assets-settings-and-permissions/flows.md#31-一个资产在某个范围里)）。
本人型之所以不用第二个人，是因为要落进的那一层，管它的就是发起的人自己。

**落在哪一层：**

| 谁发起、从哪来 | 落在哪 |
|---|---|
| 普通成员，从个人组织复制进团队 | 只落**他自己的租户级** |
| 团队的超级管理员，从个人组织复制进本团队 | **他选**：组织级，或他自己的租户级 |
| 本人型，从团队 T 里我的租户级到同树 T′ | 只落**我在 T′ 的租户级** |
| 组织型 | **目标组织的组织级** |

分享同理：接收方是一个组织，就由那个组织持有；是一个租户，就由那个租户持有。

**普通成员落不了组织级，超级管理员落得了，理由是同一条**：组织级由超级管理员管。
普通成员带进来的东西落在他自己的租户级——那是他在这个组织里的私有部分，
不碰任何别人的东西，所以不需要谁批。它要变成全组织的，走[提升](../PF-001-identity-scope-and-agent-constraints/design.md#67-创作与归属)，那是另一个动作。

### 6.3 复制的通则：同一自然人的两个租户身份

**资产复制有两条通则，一条看人，一条看组织：本人型——同一自然人的两个租户身份之间；
组织型——同一棵树上的两个团队组织之间。**

- **本人型：执行复制的人，同时是源租户和目标租户。**
- **组织型：源与目标是同一棵树上的两个团队组织，各由超级管理员代表。**

两条合起来，把方向表里所有「复制」格子、以及不存在的那些，一起解释了：

| 情形 | 哪条通则 | 结果 |
|---|---|---|
| 个人组织 → 我所在的团队 | 本人型 | **✓** 落我的租户级；我是那个团队的超管时可选组织级 |
| 团队 T 里我租户级的 → 同树 T′ 里我的租户级 | 本人型 | **✓** |
| 团队 T 组织级的 → 同树 T′ 的组织级 | 组织型 | **✓** T′ 的超级管理员确认 |
| 团队 T 里我租户级的 → 同树 T′ 的组织级 | 都不适用：本人型只落我自己的租户级，组织型只从组织级出发 | ✗ |
| 任何来源 → 同树 T′ 里别人的租户级 | 都不适用：那既不是我的租户，也不是一个组织 | ✗ |
| 团队 T 里我租户级的 → 同团队 T 的其他成员 | 不跨组织，不是复制的事 | ✗ 用组织内分享 |
| 个人组织 → 别人的个人组织 | 都不适用：不是同一个人，也不在任何树上 | ✗ 这类需要走分享 |
| 团队 → 任何个人组织（包括我自己的） | 被 §6.1 挡住 | ✗ |
| 跨树 | 都不适用 | ✗ |

**本人型不需要额外规定「必须本人操作」——模型已经决定了。**源侧若是个人组织，
除本人外没有第二个成员，别人进不去；源侧若是团队里他的租户级，
那是[他在这个组织里的私有部分](../PF-001-identity-scope-and-agent-constraints/design.md#61-层次)，
别人同样看不到。

**组织型要两边的超级管理员各点一次头**：组织级的东西是组织的，
交出一份、收进一份，都是组织级的决定，而组织级由超级管理员管。

**跨组织为什么落不到别人的租户级**：跨组织，能做主的只有两种当事人——
同一个人（两边都是他），或两个组织（各由超级管理员代表）。
往另一个组织里某个人的租户级写东西，这两种都不是：那个组织没有点头，
而那个人的租户级是他在那里的私有部分，外人不该往里写。
要给他用，我若也是那个组织的成员，先按规则 3 带到**我自己**在那里的租户级，
再按规则 1 分享给他——每一步都有该点头的人点头。

### 6.4 可复制的对象

两个条件都要满足：

- **必须是已发布版本。**草稿还在变，复制过去接收方拿到的内容说不清是哪个状态；
  而整个版本模型建立在[「已发布版本保持不可变」](../PF-001-identity-scope-and-agent-constraints/design.md#67-创作与归属)之上（PF-001 §6.7）。
- **所有权归发起方。**本人型，是他本人的——他个人组织里的，或团队里他**租户级**的；
  组织型，是源组织的，由它的超级管理员代表。**被分享来的不在此列**（[§6.13](#613-分享不可传递)）。

顺带它也堵住一个口子：一份资产[从租户范围提升到组织范围是不可逆的](../PF-001-identity-scope-and-agent-constraints/design.md#67-创作与归属)。
交给组织之后就是组织的，不能退回租户级、再以本人型带走——
要流出去，只能是组织型，也就是组织自己的决定。

**复制的是内容，不是版本号。**目标侧那份有自己独立的版本线，从 v1 开始，
与源侧的版本号无关。源侧的 v7 复制过去可能是目标侧的 v2——两条线各数各的。

### 6.5 首次复制

目标那边**新增一个资产**：

| 项 | 值 | 依据 |
|---|---|---|
| 所有者 | **落在哪一层就归谁**：租户级的归那个租户，组织级的归目标组织 | 复制的目的就是让对方拥有它；租户级、组织级的所有者本来就这样定（[PF-001 §6.7](../PF-001-identity-scope-and-agent-constraints/design.md#67-创作与归属)） |
| 作者 | **本人型：(目标组织, 本人)**；**组织型：(目标组织, 确认的那位超级管理员)** | 这一份是新对象，诞生动作就是这次复制。源侧那份的作者**不动** |
| 能力标识 | **与源侧相同** | 它就是同一个能力的另一份实现。目标那边谁生效，走 PF-002 的层级规则 |
| 版本 | v1 | 独立版本线 |
| 血缘 | 记下来自哪个源，挂在落进那一层的这一份上 | 第二次复制要用 |
| 设置与权限的值 | **没有** | 见 §6.7 |

按 [PF-001](../PF-001-identity-scope-and-agent-constraints/design.md#67-创作与归属)，
作者表达的是「**那个组织里的谁**产出了这个东西」。本人型里，是他以该组织成员的身份把它带进来的；
组织型里，把它带进目标组织的是**点头的那位超级管理员**——发起的人代表的是源组织，
他未必是目标组织的成员，而作者必须是目标组织里的一个租户。

本人型把作者记成目标组织里的他，还有一个好处：**它不暴露源侧**——他个人组织里那份是什么样，目标组织看不到。
源侧那份仍然记着原来的作者，没被改——两个资产两条记录，各自准确。

### 6.6 重复复制：全量覆盖替换

源侧改好了，再复制一次。**目标组织那一层里那份被全量覆盖替换。**

**先定落进哪一层，再由血缘在那一层里找。**每次复制都先定层——普通成员只有自己的租户级，
超级管理员从个人组织复制进本团队时可选组织级或自己的租户级，组织型是组织级；
然后系统只在那一层里找：有这个来源的那一份，就是更新；没有，就是新增——**哪怕别的层里已经有一份**。
所以超级管理员先落自己租户级试用、再选组织级，得到的是组织级新的一份，他租户级那份不动；
租户级那份被[提升](../PF-001-identity-scope-and-agent-constraints/design.md#67-创作与归属)到组织级之后，原作者再复制一次，落的是他租户级新的一份，组织那份不动。

- **不做**冲突探测，**不做**合并，**不比较**目标侧改了什么。
- 新内容**整体**等于源侧这一版的内容。
- 结果是目标侧那份的**一个新版本**，且**立即生效**。

它的精确后果，使用者必须知道：

> **目标侧此前的本地改动，不出现在新版本里。**

那些改动没有消失——它们在旧版本里，而已发布版本不可变，旧版本照旧查得到、
回退得回去。但新版本不含它们。要保留本地改动，得在新版本上重做一遍。

这是选覆盖不选合并的代价，换来的是一整套机制都不用引入（见 §7）。

**为什么立即生效，而 PF-002 说「不静默替换已选用的版本」？**
那条防的是**被动**收到上游新版本——别人发了新版，我这边不该跟着变。
复制不是被动收到，是**要落进的那一层的管理者自己要的一次写入**——
本人型是本人发起的，组织型是目标组织的超级管理员点了头的。
自己要的东西立即生效，本来就是它要的。

### 6.7 覆盖的范围：内容覆盖，配置不动

**覆盖的是资产内容，不含目标那边为它配的设置与权限值。**

按 [PF-002](../PF-002-assets-settings-and-permissions/design.md#52-设置与权限是资产的两种属性)，
配的值的最小单位是（**身份层**，具体资产，属性项）→ 值。那些值属于配它的那一层，
不是资产内容的一部分。一次复制把对方配好的执行权限冲掉，那是安全事故。

新版本改动了属性项的情形，PF-002 已经答过，不需要新规则：

| 情形 | 结果 |
|---|---|
| 新版本**删掉**了某个属性项 | 该项不再存在，配的那个值不参与求值 |
| 新版本**新增**了属性项 | 没配过，走默认 |
| 属性项不变 | 配的值照旧生效，包括标了 `immutable` 的 |

最后一格要特别说明：**`immutable` 挡不住复制，也不该挡。**
它约束的是[层级求值时下层能不能覆盖上层](../PF-001-identity-scope-and-agent-constraints/design.md#62-三种合成语义)，
而复制改的是资产内容，而且是由有权决定那一层要什么的人做出的：
落在组织级的，是超级管理员自己发起或点了头的；落在租户级的，是那个租户本人。
这不是绕过，是同一级的正常权力。

### 6.8 能力标识撞车但没有血缘

目标组织那一层里已经有一个能力标识相同的资产，但它**不是**从这个源复制来的（没有复制血缘）。

**这不是覆盖，这是新增。**

它就是那一层里的又一个资产，和对方自己那份并存。同一能力标识下谁生效，
走 PF-002 的层级与替换规则，由**目标那边自己**决定——不是复制动作的副作用。

判据只有血缘一条，**不看能力标识**。如果拿能力标识当判据，
一次复制就能把对方自己做的同名安全组件冲掉，而执行者可能根本不知道那东西存在。

### 6.9 复制或分享一个 plugin

plugin **内含的成员**一并过去——成员清单见
[PF-002 §4 Plugin](../PF-002-assets-settings-and-permissions/design.md#plugin)，
与那里「加入 plugin 时内含成员一并进来」一致。
内含成员在目标侧同样**不取得独立生命周期**。

plugin 里**引用**的能力标识不跟着走。
[引用指向能力标识](../PF-002-assets-settings-and-permissions/design.md#63-组合的引用指向能力标识)，
由目标那边求值：源侧用的是源侧那份实现，目标侧用的是目标那边那份。
这正是引用指向能力标识要的效果。

源侧有提供者、目标侧没有的，**发起时就告知**，不等到组装才失败——
见 [flows.md](flows.md)。

### 6.10 分享：给的是获权，不是拥有

分享之后，双方各能做什么：

| | 分享方 | 被分享方 |
|---|---|---|
| 所有权 | **仍然是他的** | 没有 |
| 改内容 | 可以 | **不可以** |
| 发布新版本 | 可以 | — |
| 配自己那一层的设置与权限 | 可以 | **可以**——那些值属于（他那一层, 资产, 项），是他自己那一层，不是资产内容 |
| 用别的资产替换掉它 | — | **可以**。他对自己的求值链有支配权 |
| 结束这段关系 | 可以（撤销分享） | 可以（移除，不要了） |
| 再给第三方 | 可以，他是所有者 | **不可以**，见 §6.13 |

**组织内分享**：被分享方是本组织的一个租户，其余同表。

**分享给出去的使用权没有期限，也没有暂停。**从被分享方确认那一刻起它一直有效，直到下面几件事之一发生：
分享方撤销、被分享方移除、让这段分享成立的那层关系断了（[§6.12](#612-关系解除之后)）。
**没有「到期」这个出口，也没有「暂停着、随时能恢复」这个中间态**——要暂时不让对方用，就撤销，要用再分享一次。
定义者对自己的资产直接有使用权，不经过分享（[PF-001 §4](../PF-001-identity-scope-and-agent-constraints/design.md#拥有获权选用)）。

**确认之前**，这次分享只是一份待确认的邀请：分享方可以撤回，被分享方不确认它就不生效。
**谁确认，谁就能移除**：接收方是组织的，由它的超级管理员；是租户的，由他本人
（[§6.2](#62-谁能流向谁)、[flows §4](flows.md#四角色与操作)）。
**这份邀请有过期，见 [§6.14](#614-待确认的复制通知与分享邀请会过期)**——
**「确认之后的使用权不过期」与「确认之前的邀请会过期」说的是两段不同的时间**，两者不冲突。

第四、五行连起来说明了一件事：**本版的分享不带强制。**
上级组织不能逼下级必须用某个东西、不许替换。隶属关系在 PF-001 里是**事实陈述**，
不附带管辖权，上级也不进作用域层次。要做集团强制管控，那是另一个 topic 的事。

**成本按使用方的租户归属**——谁在用就算谁的，与资产归谁无关。

### 6.11 分享的同步与自保

**被分享方选用的不是某一个版本，而是「分享方当前发布的那一版」这个动态目标。**

这个表述让分享与[版本模型](../PF-001-identity-scope-and-agent-constraints/design.md#67-创作与归属)不冲突：每个已发布版本仍然不可变；
「不静默替换已选用的版本」说的是消费方对版本的自主权，
而被分享方**选用的本来就是一个动态目标**，且他知道——这正是分享的定义。

代价要说明白：

> **分享方发布了一个坏版本，被分享方立刻中招。**

被分享方有两个自保手段：**把执行权限收窄**（那是他自己那一层的值），
或者**直接移除这个分享**。不提供「钉在某个版本上」——钉住就不是被动同步了，
那实际上是要了一份 fork，而那个动作叫复制。

**撤销**：分享方可以撤回。撤回**向后生效**，
[不强停正在运行的工作](../PF-001-identity-scope-and-agent-constraints/design.md#66-撤销不等于强制停止)。

### 6.12 关系解除之后

一段分享、一份复制，都建立在某层关系上——同一棵树，或同一个组织。那层关系断了，双方还剩什么：

| 之前发生过什么 | 断的是什么 | 之后 |
|---|---|---|
| 跨组织的**分享**（组织—组织；或我在同树两个组织的租户之间） | 两个组织的**隶属关系**解除 | **失效。**范围条件不再成立，而分享给出去的本来就只是获权 |
| **分享**，被分享方是一个租户（组织内分享；或本人型分享到我在另一个组织的租户） | **被分享方**的成员关系解除 | **结束** |
| **分享**，分享方是一个租户（组织内分享；或本人型从团队租户级发出的） | **分享方**的成员关系解除 | **结束** |
| 任何一种**复制** | 隶属关系或成员关系解除 | **留着。**落下的那一份早已独立拥有；所有权不因关系变化而回收 |

第三行的道理：分享方退出之后，他在那个组织里的租户级[谁也够不着](../PF-001-identity-scope-and-agent-constraints/design.md#退出之后再加入回来的是同一个租户)，
被分享方也就用不上它；而分享没有「暂停」这个状态，所以这段分享只能是结束了。

**关系断了之后又接上——重新隶属、重新加入——分享不复活。**要用，再分享一次，那是**新的一段**。
分享是双方各点一次头才成立的；关系解除，在这段分享上就等于分享方收回、或被分享方放弃。
已经结束的一段，不因为关系又接上了就自己回来。复制过去的本来就留着，没有复活的问题。

这一格是两个动作最实在的分水岭，也给了使用者一个决策依据：

> 卖掉子公司之后，它还能跑你的安全组件吗？
> **分享出去的，不能；复制过去的，能。**

分享失效**向后生效**，不回溯已经发生的事，也不强停正在运行的工作。

成员退出组织是同一个道理的另一个尺度：他在组织级留下的资产[留在组织](../PF-001-identity-scope-and-agent-constraints/design.md#67-创作与归属)、署名照旧；
他租户级的资产——包括本人型复制进来的——留在原处、谁也够不着，重新加入之后原样可用。
但他**再也不能以那个租户的名义发起复制或分享**——那个租户[随成员关系解除而不再有效](../PF-001-identity-scope-and-agent-constraints/design.md#退出之后再加入回来的是同一个租户)，身份还在，只是此刻没有任何动作能以它的名义发起。

### 6.13 分享不可传递

**被分享来的东西，既不能再分享给第三方，也不能复制出去，也不能提升到组织级。**

**组织内被分享来的也一样**：同事分享给我的工具，我不能再分享给第三个同事。
**本人型分享来的同样**：我把个人组织里的资产分享到我在 T 的租户级，那一份在 T 里
不能再分享给同事、也不能提升——要给同事用，先把它**复制**到我在 T 的租户级，
那一份才是我在 T 的，[规则 1](#62-谁能流向谁) 管得到它。

这不是新规则，是 PF-001
[已定的一条](../PF-001-identity-scope-and-agent-constraints/design.md#67-创作与归属)
的直接适用：「持有使用权**不自动**获得编辑、fork、转让或扩大对外共享的权力」。
提升是一次所有权的交付，而他从来不是所有者。

它的实际效果：**资产的流动路径始终可追。**B 从 A 那里拿到的东西，
不会经 B 之手流向与 A 毫无关系的 C——否则隶属树这条边界，一次转手就被绕开了。

### 6.14 待确认的复制通知与分享邀请会过期

**两者都不会无限期悬着。**

| | 复制通知 | 分享邀请 |
|---|---|---|
| **过期时长** | **这一类有自己的默认值**（按部署配置），**发起时发起方可以指定这一份的时长** | 同左，**两类各有各的默认值** |
| **到期之后** | **不可再确认**。发起方要它成立，**重新发起一份** | 同左 |
| **自动过期** | **它指向的那份资产不存在了**（被移除、被删除），它随即过期 | 同左 |

**组织内分享的邀请就是分享邀请**，同一条规则管着。
**本人型不经过这一段**：它不产生待确认的邀约，发起即生效，也就没有东西会过期。

**指定时长是发起这个动作时的一个参数，不是一项配置。**发起方最清楚这一份急不急，
所以窗口由他定；**它只对这一份成立**，跟着这份待确认的邀约走、随它结束而消失，
**不进[四层作用域](../PF-001-identity-scope-and-agent-constraints/design.md#61-层次)**。
不指定时，按这一类的默认值。具体数值仍不在产品这一层定。

**为什么非有过期不可**：一份待确认的邀约是一个**悬着的承诺**。
接收方那边一直挂着一条「有人要给你东西」，而发起方早就改主意了；
**放任它悬着，确认按钮按下去的那一刻，谁也说不清对方现在还想不想给**。
**一个有到期时间的邀约，过期本身就是一个明确的答复。**

**资产没了就自动过期，理由更硬**：一份指向不存在的资产的邀约，
**确认下去只会当场失败**——而失败发生在接收方点头之后，
他会以为是系统出了问题。**在源头就让它过期，接收方看到的是「这份邀约已失效」，
而那正是实情。**

> **过期与撤回效果相同，来路不同**：撤回是发起方主动收回，
> 过期是时间或资产的消失替他收回。**两者都到「结束」，都不留下任何使用权或资产。**

**已经确认过的不受这条约束。**[分享的使用权没有到期](#610-分享给的是获权不是拥有)，
[复制下来的那一份是目标那边自己的](#612-关系解除之后)——它们都已经不是「待确认」了。

## 七、取舍

| 面临的选择 | 选了 | 为什么 |
|---|---|---|
| 一个动作表达两种需要 ／ 分成复制与分享 | **分成两个** | 只有「交出去」，上级下发的标准组件立刻失控；只有「能用」，个人给团队的东西永远捏在个人手里，团队的运行建在成员私域上。两种需要在**所有权归属上是相反的**，一个机制表达不了 |
| fork 一份 ／ 复制过去的也指向同一个实体 | **fork** | 指向同一个实体的话，源侧一改目标侧就跟着变，目标方失去对自己资产的支配权。真要这个效果，那就是分享，不是复制 |
| 全量覆盖 ／ 冲突探测加合并 | **全量覆盖** | 合并要引入冲突态、三方比较、版本线分叉和一套人工处理流程。覆盖**一条新机制都不用加**，代价只有一条且可预期 |
| 覆盖后立即生效 ／ 等目标侧显式选用 | **立即生效** | 复制是要落进的那一层的管理者自己要的写入，不是被动收到上游新版。要求他再点一次「采用」，是为一个不存在的风险加一步 |
| 血缘作判据 ／ 能力标识作判据 | **血缘** | 能力标识作判据会误伤：对方自己做的同名组件被一次复制冲掉，而执行者可能不知道它存在 |
| 血缘在整个目标组织里找 ／ 在落进的那一层里找 | **在那一层里找** | 一次复制可以落在租户级或组织级，每一层由谁管各不相同。按层找，**不需要任何额外规则**，与「普通成员落自己的租户级、超管可选组织级」直接相容；按整个组织找，就要为「找到的那份在组织级而发起者不是超管」「组织型碰上某人租户级那份」各补一条。代价只是同一个来源在一个组织里可以有两份——租户级一份、组织级一份，按层级求值各管各的范围 |
| 组织—组织的复制开不开 ／ 组织级只能分享 | **开** | 同树的组织之间要能**各自独立演化一份**：子公司要的是 fork 集团的模板按自己的情况改，不是被动跟随集团的每一次改动——只有分享，这个需要就无处落脚。**兜底有两道**：两边的超级管理员各点一次头，且出不了那棵树 |
| 普通成员把个人组织的资产复制进团队要不要超管批 ／ 不要 | **不要** | 它只落在他自己的租户级，那是他在这个组织里的私有部分，不碰组织级、也不碰任何别人的东西。要超管批，是给一件只影响他自己的事加了一道别人的关。**要进组织级，照样只有超管做得了** |
| 个人 → 团队也提供分享 ／ 只提供复制 | **提供，落我的租户级** | 它只落到我自己在团队里的租户级，用它的只有我自己。同事要用，得我先把它**复制**成团队里我租户级的一份、再组织内分享给他——那时他用的是边界之内的东西，**用不用由他自己决定、随时可以移除**。团队不会在没人点头的情况下依赖任何人的私域；而进团队组织级的那一路仍然只有复制 |
| 组织内分享单独一套流程 ／ 并入分享 | **并入分享** | 形状完全相同：所有者开放、对方确认、所有权不动、被动跟随、可撤销可移除。差的只是**接收方是一个租户**。另立一套，就有两套确认、两套过期、两套撤销要各自保持一致 |
| 跨组织能否落在别人的租户级 | **不能** | 跨组织能做主的只有同一个人、或两个组织。往别人的租户级写，那个组织没点头，那个人的租户级又是他的私有部分——**外人不该往里写**。要给他用，有「先到我自己的租户级、再组织内分享」这条每步都有人点头的路 |
| 方向只约束这两个动作 ／ 系统级不变量 | **系统级** | 能从别的门绕过去的保护，不是保护。一个叫「导出」的功能就能让它失效 |
| 分享可传递 ／ 不可传递 | **不可传递** | 可传递的话，B 一次转手就能把 A 的东西送到与 A 无关的 C。隶属树这条边界被绕开，而且流动路径再也追不清 |
| 分享带强制 ／ 不带 | **不带** | 强制需要跨组织的**管辖权**。隶属在 PF-001 里是事实陈述，没有人裁决过它附带管辖权，也不进作用域层次。凭空给它加上，是把「隶属」偷换成「被管辖」 |
| 被分享方能钉版本 ／ 只能被动跟随 | **被动跟随** | 钉住就不是分享了——那实际上是要了一份 fork，而那个动作叫复制。**两个动作各司其职，不互相模仿** |
| 关系解除后把复制过去的收回 ／ 留着 | **留着** | 所有权已经易手。**能被收回的所有权不是所有权** |
| 关系断了又接上，此前的分享复活 ／ 不复活 | **不复活** | 分享是双方各点一次头才成立的；关系解除在它上面就等于一方收了手。让它自己回来，等于替两边重新点了头——而那个头可能早就不想点了。**要用，再分享一次** |
| 个人侧配的设置权限值跟着走 ／ 不跟 | **不跟** | 那些值属于（源那一层, 资产, 项）。换了组织就是换了身份层，那个三元组在目标侧不存在。而且源侧的配置未必适合对方 |
| 待确认的邀约**一直悬着** ／ **有过期** | **有过期** | 悬着的邀约是一个**没有答复的承诺**：接收方半年后点了确认，谁也说不清发起方现在还想不想给。过期让「没人管」变成一个**明确的结局**。代价是**发起方要重发一次**，以及**多一项要配的时长**——而那点代价换来的是一个不会越积越多、也不会在确认那一刻才暴雷的待办列表 |
| 资产没了，相关邀约**照旧挂着** ／ **自动过期** | **自动过期** | 挂着的话，确认下去**当场失败**，而失败发生在接收方点头之后——他会以为是系统坏了。**在源头过期，他看到的是「这份邀约已失效」，那正是实情** |
| 「是首次还是重复」由执行者选 ／ 系统判定 | **系统判定** | 让执行者选，等于把一个可能冲掉对方资产的决定，交给一个未必了解对方现状的人 |
| 这个动作叫「资产复制」 ／ 叫「转移」「贡献」 | **资产复制** | 这个动作的实质是 **fork 一份**：**源保留、目标独立拥有、此后各走各的**。「转移」字面暗示源侧消失，**而源侧恰恰不消失**——名字与性质反着走，使用者每次都要被纠正一遍。「复制」把最要紧的那件事直接写在名字上。代价是**「复制」本身是个很常见的词**，所以[词条明写「裸写『复制』不作数」](../../ubiquitous_language/terms/circulation-and-entitlement.md#ul-asset-copy--资产复制--asset-copy)，跨 topic 引用一律写全「资产复制」 |
