# PF-005 变更历史

记录**产品设计本身**的演进：哪一版改了什么含义、为什么改、下游要复核什么。
错别字、链接修复、段落搬家不记这里。

技术投影用 `provenance.json` 引用具体 rev，所以这里的 rev 不准会直接传导到实现侧。

## rev 2 — 2026-09-17

**加了一层：执行环境要声明自己提供哪几种[设施](design.md#设施)。**
起因是产品负责人在「工具与技能」的访谈中裁决——工具声明自己要哪种沙箱时，
「类型」由**两个维度共同确定：（绑定的层级，提供的能力）**，因此沙箱侧
必须有对应的声明；随后单独裁决回写本 topic。

### 改了什么含义

| 方面 | rev 1 | rev 2 |
|---|---|---|
| 一个执行环境「能干什么」 | **没说**。只能从它的名字或类型去猜 | **声明出来**：每个具体的执行环境都要列出自己提供哪几种设施 |
| 宿主机在这件事上 | —— | **不是例外**，用**同一种方式**声明 |
| §6.5「可以有多组执行环境」 | 只陈述了可以 | 补上了**理由**：**因为设施不同**。层级与设施都相同的两个环境没有并存的必要 |
| 那张四格表 | 两维四格 | **不变**。设施与它正交——表分的是寿命与隔离，不是本事 |

### 一处必须说明的用词

裁决的原话是沙箱声明自己提供哪几种「**能力**」，正文用的是「**设施**」。
这不是润色，是**避让**：[PF-001](../PF-001-identity-scope-and-agent-constraints/design.md#范围化对象)
与 [PF-002 §6.3](../PF-002-assets-settings-and-permissions/design.md#63-组合的引用指向能力标识)
已经把「**能力标识**」用掉了，那指的是**一份资产的身份**，与「沙箱能干什么」无关。
沿用原词就是同名不同义。**换的是名字不是实质**，详见
[decisions.md 第四节](decisions.md#四已知的来源问题)。

### 下游要复核什么

- **供给侧在这里，需求侧不在。**本 topic 只定「执行环境要声明自己提供什么」；
  工具怎么声明需求、装配时怎么匹配、匹配不上怎么办，**归工具与技能那一块**。
- **不要把设施并进那张四格表。**设施是开放集合，并进去表会跟着一起长，
  而寿命与本事会被搅成一件事。
- **不要给宿主机开特例。**沙箱声明而宿主机不必声明，热替换的前提当场就破了。
- 本 topic **不定设施的清单**——有哪几种、名字怎么定，随工具生态长。

### 本版留下的缺口

- **未决项：无。**
- **待裁决：无。**
- 来源问题增至两处（新增用词避让一条），均记在
  [decisions.md 第四节](decisions.md#四已知的来源问题)。

## rev 1 — 2026-09-17

**首版。**把 [PF-004](../PF-004-agent-runtime-assembly-and-liveness/README.md)
「执行环境」那一行展开：有哪几种、各自什么性质、里面的东西什么时候还在什么时候没。

### 这一版确定了什么

| 方面 | 结论 |
|---|---|
| 上位概念 | 沿用 PF-004 的**执行环境**。宿主机与各类沙箱都是它的取值 |
| 最要紧的一句 | **宿主机是一个取值，不是默认状态**——这是运行时热替换的分水岭 |
| 分类维度 | **两维**：效用是否持久 × 是否与宿主机隔离 |
| 有几种 | **四种**：无状态沙箱、会话级沙箱、租户级沙箱、宿主机 |
| 无状态沙箱为什么存在 | **不是为了隔离状态，是为了隔离执行**——策略不许动作落在宿主机上 |
| 会话级 | 有**最大连续存活时间**，到点**直接销毁，数据不留存** |
| 租户级 | **跨会话、跨 agent 实例共享**；沙箱可停机换节点，**数据必须可备份可迁移** |
| 宿主机 | **唯一不隔离的**，因此**不提供租户隔离**，必须被显式允许才能用 |
| 核心结构（**仅租户级**） | **本体的存活，与数据的存活，是两件事**。另两类无此区分 |

### 「数据 vs 计算资源」的第三次出现

| | 数据（活得久） | 计算资源（可随时换） |
|---|---|---|
| PF-004 | Agent Definition | 运行实例 |
| PF-004 | 会话历史 | 运行实例 |
| **本 topic** | **租户级沙箱内的数据** | **沙箱本体** |

三次形状一样：**把跑的那个和存的那个分开，跑的那个才可以被随时回收、替换、迁移。**
「云主机允许停机换节点」和「攒下来的东西不能丢」也只有分开之后才能同时成立。

### 下游要注意的五处

- **不要把宿主机实现成「没套沙箱」的默认态。**那样切换就是开关一套机制而不是换一个值，
  运行时热替换做不到，agent 也感知得到。
- **沙箱创建失败绝不能退回宿主机。**那等于绕过安全策略。
- **会话级沙箱的数据不留存是刻意的**，不是还没做。实现时不要「顺手」加上持久化。
- **迁移未完成不得在新节点以空数据起来。**用空的顶上，真假丢失就无法分辨。
- **agent 必须知道自己落在哪、痕迹在不在。**不知道的话，「重算」这条的前提就落空。

### 本版刻意不做的

会话级沙箱的**数据持久化**、租户级沙箱内多个 agent 的**协调与互斥**、
**组织级沙箱**、会话级沙箱存活上限的**调节**。

前两项是有意不做（理由在 design.md §6.3、§6.4），第三项是租户隔离排除的，
第四项属资源政策。

### 本版留下的缺口

- **未决项：无。**
- **待裁决：无。**
- 一处**命名上的偏离**已记在 [decisions.md 第四节](decisions.md#四已知的来源问题)：
  裁决措辞是「把宿主机抽象成一种特殊的沙箱」，正文沿用 PF-004 的「执行环境」作上位词，
  **实质照办、仅名称不同**。产品负责人若坚持用「沙箱」，需回改 PF-004 并升其 rev。

被排除的内容在 [design.md §2 非目标](design.md#非目标)，那是**边界**——
发现它们缺失不算缺陷。

## 怎么记下一版

改变含义就递增 rev 并在这里加一节。判断标准：
**读者需要据 rev 判断自己手上的理解是否还成立吗？**需要，就记。

每节至少说清三件事：改了什么含义、为什么、下游要复核什么。
