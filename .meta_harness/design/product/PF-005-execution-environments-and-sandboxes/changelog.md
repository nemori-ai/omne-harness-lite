## rev 3 — 2026-09-21

**接下执行环境权限这一维，并把一条只活在推导表里的规则搬进正文。**
依据：[产品负责人 2026-09-21 的四条裁决](decisions.md#一拍板记录)。

### 一、[§4 执行环境权限](design.md#执行环境权限)：新增一个概念

**按工具逐个授予，恰三态**：`always-allow`（准它直接落宿主机）·
`auto_place`（**系统算出合适的执行环境**）· `never-allow`（**绝不落宿主机**）。
**在组织级与租户级授予。**

> **它只决定作用落在哪，不决定动作准不准。**

**这一档特意不叫 `auto`**——要与[会话运行模式](../PF-015-session-lifecycle-and-ownership/design.md#会话运行模式)
那一维的 `auto_permission` 分得开：**两者都是三态，且会在同一次执行里一前一后出现**。

### 二、[§6.8](design.md#68-执行环境权限每个工具各配各的)：每个工具各配各的

**互不牵连**——`Shell()` 可以是 `auto_place`，`Computer()` 同时是 `never-allow`。
**粒度是「门」这一级**，与权限那一维的「命令」级不同，**这是各自管的东西决定的**。

跟着定死三件：**meta tool 一样受管**（配 `never-allow` 没关掉门，不触那条红线）、
**[工作区那一级不参与](../PF-002-assets-settings-and-permissions/design.md#57-工作区那一级不参与权限计算)**、
**没声明要用执行环境的工具这一维不适用**（那是实现时的契约，**不是「默认取哪一档」**）。

### 三、[§6.9](design.md#69-落点不可用就是拒绝不降级)：一条规则从推导表搬进正文

**「沙箱创建失败不得退回宿主机」rev 1 起就在 [decisions](decisions.md#二pm-推导) 里**，
**正文却一直没有**。本版补上，**并按裁决推广**：

> **任何落点算出来不可用，这次执行就是被拒——不回退宿主机，也不换更宽松的落点。**

**因为降级就是绕过安全判断**：落点是把租户隔离与两级策略都算进去之后的结果，
而[宿主机恰恰是唯一不提供租户隔离的那一个](design.md#62-宿主机不提供租户隔离因此必须被显式允许)。

### 四、统一语言

**新增 [UL-execution-environment-permission](../../ubiquitous_language/terms/grounding-and-isolation.md#ul-execution-environment-permission--执行环境权限--execution-environment-permission)**，
五条注意全部写明，**其中两条是防撞**：与会话运行模式的分工、门级 vs 命令级。

### 五、下游要复核

**[PF-007](../PF-007-meta-capabilities/README.md)**：[放行四步](../PF-007-meta-capabilities/design.md#56-一次放行判断走四步)
算的是「准不准」，**这一维算的是「落在哪」**，两者在同一次执行里先后发生——
**四步本身不变**，但读的人要知道后面还有一道。

## rev 2 — 2026-09-17

**加了一层：执行环境要声明自己提供哪几种[设施](design.md#设施)。**
起因是产品负责人在「工具与技能」的访谈中裁决——工具声明自己要哪种沙箱时，
「类型」由**两个维度共同确定：（绑定的层级，提供的能力）**，因此沙箱侧
必须有对应的声明；随后单独裁决回写本 topic。

### 改了什么含义

| 方面 | rev 1 | rev 2 |
|---|---|---|
| 一个执行环境「能干什么」 | **没说**。只能从它的名字或类型去猜 | **声明出来**：每个具体的执行环境都要列出自己提供哪几种设施 |
| 宿主机在这件事上 | —— | **不是例外**，用**同一种方式**声明 |
| §6.5「可以有多组执行环境」 | 只陈述了可以 | 补上了**理由**：**因为设施不同**。层级与设施都相同的两个环境没有并存的必要 |
| 那张四格表 | 两维四格 | **不变**。设施与它正交——表分的是寿命与隔离，不是本事 |

### 一处必须说明的用词

裁决的原话是沙箱声明自己提供哪几种「**能力**」，正文用的是「**设施**」。
这不是润色，是**避让**：[PF-001](../PF-001-identity-scope-and-agent-constraints/design.md#范围化对象)
与 [PF-002 §6.3](../PF-002-assets-settings-and-permissions/design.md#63-组合的引用指向能力标识)
已经把「**能力标识**」用掉了，那指的是**一份资产的身份**，与「沙箱能干什么」无关。
沿用原词就是同名不同义。**换的是名字不是实质**，详见
[decisions.md 第四节](decisions.md#四已知的来源问题)。

### 下游要复核什么

- **供给侧在这里，需求侧不在。**本 topic 只定「执行环境要声明自己提供什么」；
  工具怎么声明需求、装配时怎么匹配、匹配不上怎么办，**归工具与技能那一块**。
- **不要把设施并进那张四格表。**设施是开放集合，并进去表会跟着一起长，
  而寿命与本事会被搅成一件事。
- **不要给宿主机开特例。**沙箱声明而宿主机不必声明，热替换的前提当场就破了。
- 本 topic **不定设施的清单**——有哪几种、名字怎么定，随工具生态长。

## rev 1 — 2026-09-17

**首版。**把 [PF-004](../PF-004-agent-definition-and-assembly/README.md)
「执行环境」那一行展开：有哪几种、各自什么性质、里面的东西什么时候还在什么时候没。

### 这一版确定了什么

| 方面 | 结论 |
|---|---|
| 上位概念 | 沿用 PF-004 的**执行环境**。宿主机与各类沙箱都是它的取值 |
| 最要紧的一句 | **宿主机是一个取值，不是默认状态**——这是运行时热替换的分水岭 |
| 分类维度 | **两维**：效用是否持久 × 是否与宿主机隔离 |
| 有几种 | **四种**：无状态沙箱、会话级沙箱、租户级沙箱、宿主机 |
| 无状态沙箱为什么存在 | **不是为了隔离状态，是为了隔离执行**——策略不许动作落在宿主机上 |
| 会话级 | 有**最大连续存活时间**，到点**直接销毁，数据不留存** |
| 租户级 | **跨会话、跨 agent 实例共享**；沙箱可停机换节点，**数据必须可备份可迁移** |
| 宿主机 | **唯一不隔离的**，因此**不提供租户隔离**，必须被显式允许才能用 |
| 核心结构（**仅租户级**） | **本体的存活，与数据的存活，是两件事**。另两类无此区分 |

### 「数据 vs 计算资源」的第三次出现

| | 数据（活得久） | 计算资源（可随时换） |
|---|---|---|
| PF-004 | Agent Definition | 运行实例 |
| PF-004 | 会话历史 | 运行实例 |
| **本 topic** | **租户级沙箱内的数据** | **沙箱本体** |

三次形状一样：**把跑的那个和存的那个分开，跑的那个才可以被随时回收、替换、迁移。**
「云主机允许停机换节点」和「攒下来的东西不能丢」也只有分开之后才能同时成立。

### 下游要注意的五处

- **不要把宿主机实现成「没套沙箱」的默认态。**那样切换就是开关一套机制而不是换一个值，
  运行时热替换做不到，agent 也感知得到。
- **沙箱创建失败绝不能退回宿主机。**那等于绕过安全策略。
- **会话级沙箱的数据不留存是刻意的**，不是还没做。实现时不要「顺手」加上持久化。
- **迁移未完成不得在新节点以空数据起来。**用空的顶上，真假丢失就无法分辨。
- **agent 必须知道自己落在哪、痕迹在不在。**不知道的话，「重算」这条的前提就落空。

### 本版刻意不做的

会话级沙箱的**数据持久化**、租户级沙箱内多个 agent 的**协调与互斥**、
**组织级沙箱**、会话级沙箱存活上限的**调节**。

前两项是有意不做（理由在 design.md §6.3、§6.4），第三项是租户隔离排除的，
第四项属资源政策。

- **未决项：无。**
- **待裁决：无。**
