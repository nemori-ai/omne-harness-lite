**2026-09-22 的原话：**

> 宿主机一定是只要执行环境权限允许就一定可用的（因为 agent runtime 本身就在宿主机上，
> 宿主机不可用那整个系统本质上就不存在了），然后装配时候可选装配（所有的隔离沙箱环境的实现
> 都遵循完整的同一套契约和协议，并声明好自己提供什么能力和可以绑定在哪种层级上）具体的一种
> 沙箱隔离实现，运行时据此计算某个工具的执行当需要运行在隔离沙箱环境里的时候，这个环境是否可用。

**2026-09-21 的原话：**

> 执行环境权限先讨论：怎么理解呢，就是执行环境权限其实防的是「作用能不能直接落在宿主机上」这件事，
> 而这个权限是 per-tool 授予的（组织级/租户级）。这里也有类似的几种授权：always-allow, auto, never-allow。
> 这里需要注意的就是和会话运行模式的区别，两者都是三态都有 auto，但是维度不一样，会话运行模式叠加的
> 它相关的那些授权的 runtime context 算的是动作能不能做，而执行环境权限这边的权限则是管的动作能做的
> 前提下，作用落在哪里（如果落作用的那个对象不可用，那动作依然是要被拒绝的而不是降级到更宽到可落作用的，
> 比如 执行环境权限 的 auto 算出来应该跑隔离容器里，但是容器不可用，那这个执行依然是要被拒绝而不是回退宿主机）

> 执行环境那个正式改名叫 auto_place（含义就是自动决策合适的运行环境）

> 而且我说的运行环境权限三态，是 per-tool 的，比如 shell use 是 auto，computer use 是 never，
> browser use 是 always，是可以不一样的，这点你明确了吧？

> 「没有显式配置的工具」工具声明需要用到沙箱运行时这个你可以理解为是现实时的契约，没声明就认为这个
> 工具的执行用不到，不需要管，你也不需要记录了吧

**2026-09-22 的原话（工作区，六条补充里的第 5 条；全文在 [PF-002 decisions](../PF-002-assets-settings-and-permissions/decisions.md#2026-09-22--工作区是一级治理不是目录会话创建时-opt-in挂上就自动加载)）：**

> 5）这意味着宿主机上的 agent 对工作区（目录）外对文件系统依然有访问的权限（只要不被禁止或 auto 模式拦截）。

落在 [§4 工作区的承载目录不是宿主机上的边界](design.md#工作区的承载目录不是宿主机上的边界)与 [§6.2](design.md#62-宿主机不提供租户隔离因此必须被显式允许)（rev 5）。
**「auto 模式」这个词在正文与词表里没有对应概念**——见[第四节](#四已知的来源问题)。

**上面「没声明就认为用不到」那条是对 PM 一个问题的否决。**PM 报上去的是「没有显式配置的工具，默认落在哪一档」，
并给了两个候选（`never-allow` 最安全但要逐个配、`auto_place` 开箱能用）。
**产品负责人指出那个问题不成立**：这一维只作用在**声明了要用执行环境的工具**上，
**没声明的根本不进这一维**，不是「默认取某一档」。**因此也不作为未决项记录。**

## 二、PM 推导

从已拍板内容推出的判断，附可核对的推理链。

| 结论 | 从哪几条推出 | 推理 |
|---|---|---|
| **分类要两个维度，不是一个** | 「无状态—不绑定」「宿主机纳入同一抽象」 | 把宿主机纳进来之后，出现了两个都叫「不绑定」而含义相反的格子：**无状态沙箱不绑定是因为用完就扔，宿主机不绑定是因为大家共用**。一维说不清这两者，而它们的风险恰好相反——必须拆成「效用是否持久」与「是否隔离」两维 |
| **上位概念沿用「执行环境」，不改叫「沙箱」** | 裁决的措辞是「把宿主机抽象成一种特殊的沙箱」 | **实质照办**：两者在同一抽象下才能互换。但 [PF-004 §4](../PF-004-agent-definition-and-assembly/design.md#执行环境) 已把「执行环境」定为上位概念，改名等于同一个东西两个名字（概念只定义一次是红线）；且「宿主机是一种沙箱」字面绊人——它恰恰是不 sandbox 的那一个。**此处只沿用已有名称，未改变裁决的实质** |
| **执行环境永远存在，不存在「没有执行环境」** | 「动作落在哪」这个问题本身 | 动作总要落在某处。没有这一条，「宿主机是取值不是默认」就没有落脚点 |
| **⚠️ 已被取代** · ~~宿主机是一个取值，装配时必须明确注入一个执行环境~~ | 「热替换而 agent 无感」 | 原推理：把宿主机当默认态，注入就退化成「要不要套沙箱」的布尔问题，切换是换一套机制。**2026-09-22 被取代**——[宿主机始终在场，沙箱实现可选装配，落点每次执行算](design.md#61-宿主机始终在场沙箱实现装配时可选装配)。**这条推导要的那个结果保住了**：热替换仍然成立，**而论据换成了「落点是每次执行算出来的值」**，不再需要「装配时注入一个」这个前提——**那个前提正是[与「每个工具各配各的」打架的那一处](#四已知的来源问题)** |
| **宿主机不提供租户隔离，因此必须被显式允许才能用** | 宿主机「不隔离」这一性质 + [SYS-TENANT](../../foundation/cross-system-constraints/requirements.md#sys-tenant) | 一个租户在宿主机上写的东西另一个租户看得见，这直接顶在租户隔离上。所以它不能是缺省可用的选项。这也正好解释了裁决里那句「安全权限设置不允许直接使用宿主机的浏览器或命令行」——**策略挡的就是这个** |
| **沙箱创建失败不得退回宿主机** ✅ **已被 2026-09-21 裁决确认，并推广成一般规则** | 上一条 | 退回宿主机等于绕过安全策略。失败就是失败。**产品负责人把它从「沙箱创建失败」推广到「任何落点不可用」**，并写进正文 [§6.9](design.md#69-落点不可用就是拒绝不降级)——**此前它只活在这张推导表里，正文没有** |
| **没有「组织级沙箱」，三个沙箱层级是穷尽的** | 租户隔离 | 跨租户共享直接破坏隔离。会话与租户之间没有第三个可共享的层级 |
| **一个会话、一个租户可以同时有多组执行环境** | 裁决举的例子本身（浏览器沙箱、命令行沙箱是两种） | 绑定层级是**每个沙箱各自的**属性，不是会话只能挑一种。否则「浏览器里连续操作」与「命令行里连续执行」不能同时成立 |
| **沙箱不是资产，不走持有/复制/分享** | [PF-002 的资产定义](../PF-002-assets-settings-and-permissions/design.md#八类资产)：约束 agent **由什么组装而成** | 执行环境是动作**落地**的地方，不参与组装。归进资产就得给它持有、复制、分享的语义，而那些对它毫无意义 |
| **租户级沙箱内多个 agent 互相影响是特性，不是缺陷** | 「一个租户的所有 agent 共享一台计算机，**一起在上面做事**」 | 共享工作空间的价值正在于互相看得见。当成缺陷去修就得加隔离，那它就不是共享空间了。正文写明它，是为了让它不被当成 bug 报上来 |
| **本版不引入租户级沙箱内的协调与互斥机制** | 上一条 | 既然互相影响是特性，就没有要修的东西。真出现协调需要，那是另一件事 |
| **agent 必须能知道当前落在哪、痕迹在不在** | 「agent 是图灵机，能感知变化并自己重算」 | 「能重算」的前提是**知道东西没了**。不让它知道，会话级沙箱那条裁决的后半句就落空——它会继续引用不存在的东西 |
| **环境变化在下一轮以提醒到达，不打断当前运行** | [PF-004 §6.4](../PF-004-agent-definition-and-assembly/design.md#64-上下文变化怎样到达-agent) | 执行环境是注入的一种，其变化的到达方式在 PF-004 已定，本 topic 直接适用，不另立一套 |
| **「有状态」的准确含义是「在它活着的期间内有状态」** | 「到点销毁，数据不留存」 | 不是状态永久。它的全部价值是那个窗口——「后一步基于前一步的结果」在窗口内成立 |
| **「能重算」有边界，会话级沙箱是工作台不是保险柜** | 「agent 有能力自己重新执行计算」 | 计算结果能重算、外部内容能重下，但 agent 在沙箱里调试了半天的原创产出**重写 ≠ 重算**。这不改变裁决，是裁决的**代价**，必须写出口——否则重要产出会被留在注定消失的地方 |
| **会话级沙箱到点时仍有动作在执行，按退役方式收口** | [PF-004 §6.7](../PF-012-agent-loop-and-run/design.md#614-停止有两级) | 直接掐断会留下没有结局的动作。 agent runtime 的退役已经定了这个形状，此处适用同一条 |
| **迁移未完成不得在新节点以空数据起来** | 「数据必须可备份可迁移」 | 用空的顶上，用户会以为东西丢了，而实际只是没迁过来——**真假丢失无法分辨**，这比直接失败更糟 |
| **宿主机也要声明自己提供哪些设施** | 裁决只说了「沙箱实现」+ [§6.1 落点每次执行算](design.md#61-宿主机始终在场沙箱实现装配时可选装配) | 若沙箱都声明而宿主机不必，它**当场变回特例**，「两者以同一种方式被处理」就破了，热替换随之落空。**而且算落点时要拿「这次要什么设施」去比，比的那一头必须两边都有** |
| **设施与绑定层级正交，四格表不因设施变宽** | 裁决把类型说成**两个维度共同确定**（绑定层级，提供的能力） | 「共同确定」意味着两者各自独立取值，不是一个维度的细分。并进那张表，表会随设施一起长，而设施是开放集合 |
| **「凭什么要多组执行环境」的答案是设施不同** | §6.5 + 设施 | 此前 §6.5 只陈述了「可以多组」，没说理由。理由只能是设施——层级与寿命相同而设施也相同的两个环境，没有并存的必要 |
| **本 topic 不定设施的清单** | 「先做最小的正确模型」 | 设施随工具生态长，现在定一份枚举，下一个工具就得改产品文档。本 topic 只定**要声明**这件事 |
| **三态的所指是「宿主机准不准」，不是「落点本身」** | 裁决原话「**防的是作用能不能直接落在宿主机上**」 | 顺着那句话，三态都围绕宿主机这一个落点说：`always-allow` 准它直接落、`never-allow` 绝不落、`auto_place` 系统算。**反证**：`never-allow` 若读成「这个工具禁用」，它就窜到[另一维](../PF-007-meta-capabilities/design.md#56-一次放行判断走四步)去了——产品负责人明确说过两维**维度不一样**，那边管「动作能不能做」，**一个工具能不能用是那边的事**，这边不该有第二个开关 |
| **meta tool 一样 per-tool 受这一维管** | 裁决举的例子（shell use / computer use / browser use）**本身就是 meta tool** + [PF-007 §5.7](../PF-007-meta-capabilities/design.md#57-权限能关掉一条命令关不掉一扇门) | 给 `Shell()` 配 `never-allow` **作用在落点上，没有关掉那扇门**，因此不触那条红线。**反过来看更硬**：`Shell()` 恰恰是最该管落点的那一个，**它若不受管，这一维就形同虚设**。产品负责人后来直接用这三个做例子，**等于确认了这条** |
