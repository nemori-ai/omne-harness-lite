# PF-005 决策与来源

产品设计允许 product manager 做判断，但**不允许发明没人拍过板的东西**。
本页把两者分开：哪些是产品负责人裁决的，哪些是 PM 自己推导的，各自依据在哪。

## 二、PM 推导

从已拍板内容推出的判断，附可核对的推理链。

| 结论 | 从哪几条推出 | 推理 |
|---|---|---|
| **分类要两个维度，不是一个** | 「无状态—不绑定」「宿主机纳入同一抽象」 | 把宿主机纳进来之后，出现了两个都叫「不绑定」而含义相反的格子：**无状态沙箱不绑定是因为用完就扔，宿主机不绑定是因为大家共用**。一维说不清这两者，而它们的风险恰好相反——必须拆成「效用是否持久」与「是否隔离」两维 |
| **上位概念沿用「执行环境」，不改叫「沙箱」** | 裁决的措辞是「把宿主机抽象成一种特殊的沙箱」 | **实质照办**：两者在同一抽象下才能互换。但 [PF-004 §4](../PF-004-agent-definition-and-assembly/design.md#执行环境) 已把「执行环境」定为上位概念，改名等于同一个东西两个名字（概念只定义一次是红线）；且「宿主机是一种沙箱」字面绊人——它恰恰是不 sandbox 的那一个。**此处只沿用已有名称，未改变裁决的实质** |
| **执行环境永远存在，不存在「没有执行环境」** | 「动作落在哪」这个问题本身 | 动作总要落在某处。没有这一条，「宿主机是取值不是默认」就没有落脚点 |
| **宿主机是一个取值，不是默认状态** | 「热替换而 agent 无感」 | 若把宿主机当默认态，注入就退化成「要不要套沙箱」的布尔问题，切换是**换一套机制**而不是换一个值，热替换做不到，agent 也感知得到。**裁决要的那个结果只有「取值」这一种做法能兑现** |
| **宿主机不提供租户隔离，因此必须被显式允许才能用** | 宿主机「不隔离」这一性质 + [SYS-TENANT](../../foundation/cross-system-constraints/requirements.md#sys-tenant) | 一个租户在宿主机上写的东西另一个租户看得见，这直接顶在租户隔离上。所以它不能是缺省可用的选项。这也正好解释了裁决里那句「安全权限设置不允许直接使用宿主机的浏览器或命令行」——**策略挡的就是这个** |
| **沙箱创建失败不得退回宿主机** | 上一条 | 退回宿主机等于绕过安全策略。失败就是失败 |
| **没有「组织级沙箱」，三个沙箱层级是穷尽的** | 租户隔离 | 跨租户共享直接破坏隔离。会话与租户之间没有第三个可共享的层级 |
| **一个会话、一个租户可以同时有多组执行环境** | 裁决举的例子本身（浏览器沙箱、命令行沙箱是两种） | 绑定层级是**每个沙箱各自的**属性，不是会话只能挑一种。否则「浏览器里连续操作」与「命令行里连续执行」不能同时成立 |
| **沙箱不是资产，不走持有/转移/分享** | [PF-002 的资产定义](../PF-002-assets-settings-and-permissions/design.md#八类资产)：约束 agent **由什么组装而成** | 执行环境是动作**落地**的地方，不参与组装。归进资产就得给它持有、转移、分享的语义，而那些对它毫无意义 |
| **租户级沙箱内多个 agent 互相影响是特性，不是缺陷** | 「一个租户的所有 agent 共享一台计算机，**一起在上面做事**」 | 共享工作空间的价值正在于互相看得见。当成缺陷去修就得加隔离，那它就不是共享空间了。正文写明它，是为了让它不被当成 bug 报上来 |
| **本版不引入租户级沙箱内的协调与互斥机制** | 上一条 | 既然互相影响是特性，就没有要修的东西。真出现协调需要，那是另一件事 |
| **agent 必须能知道当前落在哪、痕迹在不在** | 「agent 是图灵机，能感知变化并自己重算」 | 「能重算」的前提是**知道东西没了**。不让它知道，会话级沙箱那条裁决的后半句就落空——它会继续引用不存在的东西 |
| **环境变化在下一轮以提醒到达，不打断当前运行** | [PF-004 §6.4](../PF-004-agent-definition-and-assembly/design.md#64-上下文变化怎样到达-agent) | 执行环境是注入的一种，其变化的到达方式在 PF-004 已定，本 topic 直接适用，不另立一套 |
| **「有状态」的准确含义是「在它活着的期间内有状态」** | 「到点销毁，数据不留存」 | 不是状态永久。它的全部价值是那个窗口——「后一步基于前一步的结果」在窗口内成立 |
| **「能重算」有边界，会话级沙箱是工作台不是保险柜** | 「agent 有能力自己重新执行计算」 | 计算结果能重算、外部内容能重下，但 agent 在沙箱里调试了半天的原创产出**重写 ≠ 重算**。这不改变裁决，是裁决的**代价**，必须写出口——否则重要产出会被留在注定消失的地方 |
| **会话级沙箱到点时仍有动作在执行，按退役方式收口** | [PF-004 §6.7](../PF-012-agent-loop-and-run/design.md#614-停止有两级) | 直接掐断会留下没有结局的动作。 agent runtime 的退役已经定了这个形状，此处适用同一条 |
| **迁移未完成不得在新节点以空数据起来** | 「数据必须可备份可迁移」 | 用空的顶上，用户会以为东西丢了，而实际只是没迁过来——**真假丢失无法分辨**，这比直接失败更糟 |
| **宿主机也要声明自己提供哪些设施** | 裁决只说了「沙箱实现」+ §6.1「宿主机是取值不是默认态」 | 若沙箱都声明而宿主机不必，它**当场变回特例**，「两者以同一种方式被处理」就破了，热替换随之落空。**裁决要的那个结果只有把宿主机一并纳入才兑现** |
| **设施与绑定层级正交，四格表不因设施变宽** | 裁决把类型说成**两个维度共同确定**（绑定层级，提供的能力） | 「共同确定」意味着两者各自独立取值，不是一个维度的细分。并进那张表，表会随设施一起长，而设施是开放集合 |
| **「凭什么要多组执行环境」的答案是设施不同** | §6.5 + 设施 | 此前 §6.5 只陈述了「可以多组」，没说理由。理由只能是设施——层级与寿命相同而设施也相同的两个环境，没有并存的必要 |
| **本 topic 不定设施的清单** | 「先做最小的正确模型」 | 设施随工具生态长，现在定一份枚举，下一个工具就得改产品文档。本 topic 只定**要声明**这件事 |

## 四、已知的来源问题

| 问题 | 影响 | 处置 |
|---|---|---|
| **PM 曾推出「沙箱的寿命必须长于 agent runtime」，该推论错误。**它隐含假设了「沙箱里总有值得保留的东西」，而无状态沙箱直接推翻这个前提——它本来就没有该留的东西，销毁不构成任何损失 | 若按错误推论设计，无状态沙箱就没有存在的位置，而它恰恰是安全策略最直接的落点 | **已被产品负责人当场纠正并作废**。正文按「沙箱与 agent runtime 不绑定」落稿：它要么更短（一次调用），要么更长（会话或租户），**唯独不会和 agent runtime 同生共死** |
| 裁决的措辞是「把宿主机抽象成一种**特殊的沙箱**」，而正文用的上位词是「**执行环境**」 | 读者可能以为正文没有照办 | **实质完全照办**（两者同一抽象、可互换），仅沿用 PF-004 已有的名称，理由见第二节对应条目。**若产品负责人坚持用「沙箱」作上位词，需回改 PF-004 §4 并升其 rev** |
| 裁决的措辞是沙箱声明自己提供哪几种「**能力**」，而正文用的词是「**设施**」 | 读者对不上原话 | **必须换，这一步没有选择余地**：[PF-001](../PF-001-identity-scope-and-agent-constraints/design.md#范围化对象) 与 [PF-002 §6.3](../PF-002-assets-settings-and-permissions/design.md#63-组合的引用指向能力标识) 已经把「**能力标识**」用掉了，那指的是**一份资产的身份**（官方版与组织定制版共享同一个能力标识，因此能互相覆盖），与「沙箱能干什么」毫无关系。沿用原词就是**同名不同义**，本区域的红线。**换的是名字不是实质；若产品负责人另有更顺的词，直接替换即可** |
