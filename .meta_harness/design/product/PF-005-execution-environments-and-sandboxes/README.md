# PF-005：执行环境与沙箱

**[PF-004](../PF-004-agent-runtime-assembly-and-liveness/README.md) 把执行环境定成
注入给运行实例的三样东西之一，并定了一条很强的性质：一条 shell 命令，
执行在宿主机还是沙箱里，agent 都能执行。本 topic 把它展开：**
**有哪几种、各自什么性质、里面的东西什么时候还在什么时候没。**

一句话概括本 topic 最要紧的结论：

> **宿主机不是「没有沙箱」的默认状态，它是执行环境的一个具体取值。**

这看着像措辞，实则是运行时热替换的分水岭——把它当默认态，切换就退化成
「开关一套机制」；当成取值，切换才是「换一个值」，**运行实例不重建、动作空间不变、agent 无感**。

## 四种，两个维度

| | **不隔离** | **隔离** |
|---|---|---|
| 效用**不持久** | —— | **无状态沙箱**（一次工具调用） |
| 效用持久 · **会话** | —— | **会话级沙箱**（有最大连续存活时间） |
| 效用持久 · **租户** | —— | **租户级沙箱**（跨会话共享） |
| 效用持久 · **部署** | **宿主机** | —— |

**两个「不绑定」含义相反**：无状态沙箱是**用完就扔**，宿主机是**大家共用**。
只用一维说不清，而它们的风险恰好相反。

## 再加一层：设施（rev 2）

上面那张表分的是**寿命与隔离**，回答「活多久、谁看得见」。它不回答
「在里面能干什么」——那由**[设施](design.md#设施)**回答，而且是**声明出来**的：

> **每一个具体的执行环境都要声明自己提供哪几种设施。这包括宿主机——它不是例外。**

两者**正交**：同为会话级的两个沙箱，设施可以完全不同；同一种设施也可以由
不同层级的环境提供。**表不会因此变宽。**这也补上了「凭什么要多组执行环境」
的答案——**因为设施不同**。

供给侧在这里；工具怎么声明需求、怎么匹配，归**工具与技能**那一块。

## 核心结构（**只针对租户级沙箱**）：本体的存活 ≠ 数据的存活

| | 本质 | **租户级沙箱**的产品要求 |
|---|---|---|
| **沙箱本体** | **计算资源** | 允许停机、允许换一个物理节点 |
| **沙箱内的数据** | **数据** | **必须可备份、可迁移**，与**租户**生命周期一样长 |

**另外两类没有这个区分**：无状态沙箱本来就没有该留的东西，
会话级沙箱**到点销毁、数据不留存**（刻意为之）。

这是「数据 vs 计算资源」在本系统里的**第三次出现**——前两次是
Agent Definition 对运行实例、会话历史对运行实例。三次形状一样。
