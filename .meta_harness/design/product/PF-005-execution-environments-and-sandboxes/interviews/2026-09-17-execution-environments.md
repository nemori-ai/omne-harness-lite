## INT-003

- 标题：沙箱的定义、三个绑定层级，以及对 PM 推论的纠正
- actor：**产品负责人本人**
- 表达方式：`quote`
- 内容：「沙箱是一个工具执行产生效用的一种环境，是相对于 agent 运行的「宿主机」的概念。
  按照一次工具执行产生的效用是否是持久的，沙箱分为有状态和无状态的，因此
  「沙箱的寿命必需长于运行实例」是不完全成立的。「沙箱」和运行实例不绑定，
  按照有状态和无状态来区分，沙箱的绑定是分这几个层级的：无状态-不绑定，一次工具调用
  （比如一次 browser use、一次 shell command，可能因为会话的安全权限设置，不允许直接
  使用宿主机的浏览器或命令行）得到结果这个沙箱的生命周期就结束了；有状态-绑定在会话，
  这个是最常用的，但往往从资源角度考虑有个沙箱最大存活时间的限制……；有状态-绑定在租户，
  这个是我们产品的核心需求，而且因为绑定在租户，意味着这个沙箱资源是跨会话共享的
  （自然也是跨 agent 实例共享的）……当然这不意味着这个沙箱的存活生命是无限的，
  具体来说，确实有需要和租户生命周期一样长的部分，但那是沙箱内的数据，也就是这块产品上
  对技术的要求应该限定在，沙箱（比如云主机）允许停机、换另一个物理节点，
  但是数据必需可备份可迁移」
- 状态：当前有效。落在 design.md §4、§5.1、§5.2、§6.4
- 记录者注：末段那句「**但那是沙箱内的数据**」是本 topic 的核心结构来源——
  它把沙箱本体与沙箱内数据分成两样东西，**「允许停机换节点」与「攒下的东西不能丢」
  才可能同时成立**。这也是「数据 vs 计算资源」在本系统里的第三次出现。

## INT-004

- 标题：宿主机要抽象成同一个抽象下的东西
- actor：**产品负责人本人**
- 表达方式：`quote`
- 内容：「同时我们说「沙箱」（也就是执行环境）是「注入」的，这就意味着，根据一个 session 的
  比如 执行安全策略（也是运行时可变）的不同，agent 视角下应该是无感的，者就意味着我们在对
  「沙箱」的抽象上，应该要把 宿主机 抽象成一种特殊的沙箱，这样才能做到根据比如 session 的
  执行安全策略的变更而在运行时可以热替换」
- 状态：当前有效。落在 design.md §6.1、§5.3
- 记录者注：记录者据此提出两点并获默认通过——① 这个抽象在 PF-004 §4「执行环境」
  已经就位，本 topic 只需展开；② 正文沿用「执行环境」作上位词而非「沙箱」，
  **实质照办、仅名称不同**，理由与处置见 decisions.md 第二、四节。
  把宿主机纳入同一抽象还暴露了**第二个分类维度**（是否隔离）——
  在此之前「绑定层级」一维说不清两个含义相反的「不绑定」。

## INT-005

- 标题：会话级沙箱不对数据的持久作要求
- actor：**产品负责人本人**
- 表达方式：`quote`
- 内容：「目前我们的产品，为了避免过度设计和过早引入复杂度，对于会话级沙箱，
  我们不对数据的持久作要求。具体来说就是一个会话级沙箱过了它的最大连续存活时间就直接销毁，
  里面数据不留存，真的这个会话下次还要用一个会话级沙箱，那就重建，要什么数据就重新再算。
  因为 agent 本质上是一个图灵机，它能够在运行时动态感知到变化（沙箱内数据没了），
  它有能力自己重新执行计算之类的动作」
- 上下文：回答记录者提的问题——记录者当时倾向「数据留下」，理由是「否则会话级和
  无状态的差别只剩一个时间窗口」
- 状态：当前有效。落在 design.md §6.3
- 记录者注：这条裁决**不是妥协，是 PF-004 §6.4 的直接应用**——既然 agent 能感知变化
  并自行调整轨迹，系统就不必替它保管一切。记录者原先那句话本身没错，
  **错在把「只剩一个时间窗口」当成了缺点**：那个窗口就是它的全部价值。
  记录者据此补了一条**代价**进正文（「能重算」有边界，原创产出重写 ≠ 重算，
  因此**会话级沙箱是工作台不是保险柜**），该补充不改变裁决。

### INT-008 沙箱要声明自己提供哪几种能力（→ 正文的「设施」）

- 时间/顺序：**rev 1 被接受为正式版本之后**，在「工具与技能」的访谈过程中
- actor：**产品负责人本人**
- 表达方式：`quote`
- 内容：先在工具与技能的语境里给出——「前面讲到的工具声明用哪种类型的沙箱，
  这里的类型是两个维度共同确定的：（绑定的层级，提供的能力）」；随后单独裁决——
  「PF-005 需要回写升 rev，大体上是对沙箱的抽象模型，添加一个声明的能力，
  也就是一个具体的沙箱实现，应当要声明自己提供哪几种能力」
- 上下文：rev 1 只用「绑定层级 × 是否隔离」两维分类，没有任何地方回答
  「一个执行环境能干什么」。§6.5 虽已写「可以同时有多组执行环境」并举了
  浏览器沙箱与命令行沙箱，但**没说凭什么要多组**
- 状态：当前有效。**据此升 rev 2**
- 记录者注：两处需要说明。
  其一，**用词换了**：正文用「设施」而非原话的「能力」，因为
  [PF-001](../../PF-001-identity-scope-and-agent-constraints/design.md#范围化对象) 与
  [PF-002 §6.3](../../PF-002-assets-settings-and-permissions/design.md#63-组合的引用指向能力标识)
  已把「**能力标识**」用于**资产的身份**，沿用原词即同名不同义。换名不换实质。
  其二，**推了一步**：裁决只说「沙箱实现」，记录者据 §6.1「宿主机是取值不是默认态」
  推出**宿主机也必须一并声明**——否则它当场变回特例，热替换的前提就破了。
  这一步推理记在 [decisions.md 第二节](../decisions.md#二pm-推导)，可核对。
  另外顺手补上了 §6.5 缺的那个理由：**要多组是因为设施不同**。
