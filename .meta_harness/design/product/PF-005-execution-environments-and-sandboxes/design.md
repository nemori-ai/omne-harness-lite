# PF-005：执行环境与沙箱

- 修订：rev 5，2026-09-22 · [变更历史](changelog.md)
- 状态：已定稿，**无未决项**

## 一、背景与问题

[PF-004](../PF-004-agent-definition-and-assembly/design.md) 把**执行环境**
定成注入给 agent runtime 的三样东西之一——动作实际落到哪里，由它决定。它还定了一条很强的性质：
**一条 shell 命令，执行在宿主机还是沙箱里，agent 都能执行。**

但**有哪几种执行环境、各自什么性质、里面的东西什么时候还在什么时候没**，
PF-004 有意留空了。留空的代价现在开始显现：

- **一次工具执行到底落在哪儿？**说不清，就没法回答「这个动作安全吗」。
- **「不允许直接用宿主机的浏览器或命令行」这条限制挡的是什么？**
  它挡的那个东西没有名字。
- **沙箱里的东西什么时候没？**没人知道——**agent 自己也不知道**，
  于是它会把重要的东西留在一个注定消失的地方。
- **一个租户的所有 agent 共用一台隔离的机器**（computer use）——
  这是产品的核心需求，但没有对象承载它。

本 topic 把执行环境展开：有哪几种、各自的状态活多久、数据有什么要求、
以及它们之间怎么互换而 agent 无感。

## 二、目标与非目标

### 目标

1. **定义执行环境的种类**，以及分类所依据的两个维度。
2. **钉死「宿主机是一个取值，不是默认状态」**——这是热替换能不能成立的分水岭。
3. **说清每一类的状态活多久、数据有什么要求**，包括明确**不要求**的那部分。
4. **说清租户级共享的语义**及其代价。

### 非目标

| 不做什么 | 为什么 |
|---|---|
| 用什么技术实现隔离 | 容器、虚拟机、云主机——那是技术选择。本 topic 只定**产品上必须成立的性质** |
| 工具怎么声明它需要什么样的环境 | 归**工具与技能**那一块。本 topic 定环境本身，不定谁来提要求 |
| [执行环境权限](#执行环境权限)怎么配置、谁能改 | 那是 [PF-002](../PF-002-assets-settings-and-permissions/design.md) 的设置与权限。本 topic 只定**它改了之后落点怎么变** |
| 制品、工作副本怎么管 | 「重要产出该存哪」是另一件事。本 topic 只负责说明**沙箱不是存它的地方** |
| 沙箱内数据的备份与迁移**怎么做** | 本 topic 只定**哪一类必须能备份能迁移**，不定机制 |
| 宿主机本身怎么部署、怎么运维 | 归部署那一侧 |
| 具体有哪些沙箱形态 | 浏览器、命令行、完整桌面……本 topic 定的是**分类与性质**，不枚举形态 |

## 三、用户与场景

| 使用者 | 什么情况下接触这块 | 他关心什么 |
|---|---|---|
| **用 agent 干活的人** | agent 帮他跑命令、开浏览器、操作一台机器 | 它在哪儿干的？会不会动到我本机的东西？ |
| **组织管理员 / 安全负责人** | 配[执行环境权限](#执行环境权限) | 能不能禁止 agent 直接碰宿主机？改了之后什么时候生效？ |
| **同一租户里的多个使用者** | 共用一台隔离的机器做事 | 我装的东西别人看得见吗？别人会不会覆盖我的？ |
| **对成本负责的人** | 看账单 | 一台闲着的沙箱是不是一直在烧钱？ |
| **agent 自己** | 每一次工具执行 | 我这次落在哪儿？上次留下的东西还在不在？ |

**最后一行是这块设计的直接消费者。**它答不上来第二个问题，就会把重要的东西
留在一个注定消失的地方——而本 topic 的一条规则就是为了让它答得上来（§6.6）。

### 执行环境

[PF-004 已经定了它](../PF-004-agent-definition-and-assembly/design.md#执行环境)：
**动作实际落到哪里。**本 topic 不改写这个定义，只把它展开。

展开的第一句就是本 topic 最要紧的一条：

> **执行环境永远存在。不存在「没有执行环境」这个状态**——动作总要落在某处。

**落在哪一个，是每扇门、每一次执行现算出来的**（[§6.1](#61-宿主机始终在场沙箱实现装配时可选装配)）。
[宿主机](#宿主机)**始终在场**；隔离的那些由**装配进来的[沙箱实现](#沙箱实现)**提供。

### 沙箱

**与宿主机相互隔离的一种执行环境。**

「沙箱」不是执行环境的上位概念，**它是执行环境中「隔离」的那些**。
宿主机是执行环境中「不隔离」的那一个。两者在同一个抽象下，因此可以互换——
这正是「[执行环境权限](#执行环境权限)一改、落点跟着换而 agent 无感」能成立的前提。

### 沙箱实现

**装配时可以装进来的一个隔离环境提供者。**

**全部沙箱实现遵循同一套契约与协议**，并各自声明两件事：
**提供哪几种[设施](#设施)**、**可以绑定在哪几个层级**（[四种执行环境](#51-四种执行环境)里除宿主机之外的那三个：
一次调用 · 一个会话 · 一个租户）。

**它是被装配的，装不装、装哪一个，是装配方的选择**；
[宿主机不在此列](#宿主机)——它不需要被装配。

> **沙箱实现不是[资产](#67-沙箱不是资产)。**理由与沙箱本身那条一样：
> 资产约束 agent **由什么组装而成**，而它提供的是动作**落地的地方**。

### 宿主机

**[agent runtime](../PF-012-agent-loop-and-run/design.md#agent-runtime) 本身所在的地方，
也是唯一不隔离的执行环境。**

> **它始终在场。**agent runtime 本身就跑在它上面——**宿主机不在，整个系统就不在**。
> 因此**不存在「宿主机不可用」这件事**：[只要执行环境权限允许，它就可用](#61-宿主机始终在场沙箱实现装配时可选装配)。

它的「特殊」还有一处，而这一处很要紧：

> **宿主机不提供租户隔离。**一个租户的 agent 在宿主机上写下的东西，
> 另一个租户的 agent 看得见。

这直接顶在 [SYS-TENANT](../../foundation/cross-system-constraints/requirements.md#sys-tenant) 上。
所以它**不是一个随便可用的选项，而是必须被显式允许才能用的选项**——
这正是[执行环境权限](#执行环境权限)配成 `never-allow` 时要挡的东西（§6.2）。

#### 工作区的承载目录不是宿主机上的边界

会话挂上的[工作区](../PF-002-assets-settings-and-permissions/design.md#工作区)由宿主机上的一个目录承载，
**但那个目录不是 agent 在宿主机上的活动范围**。agent 在宿主机上能读写到哪，
由[执行环境权限](#执行环境权限)（作用能不能落在宿主机上）、各条命令自己的权限与
[放行判断](../PF-007-meta-capabilities/design.md#56-一次放行判断走四步)决定——
**工作区目录之外的文件系统照样够得着，除非被这些权限禁止，或被
[会话运行模式 `auto_permission`](../PF-015-session-lifecycle-and-ownership/design.md#会话运行模式) 那一档按已有授权算出来拦下**。

> 把工作区目录当成围栏，是把「地址」读成了「边界」：[路径是地址，不是钥匙](../PF-001-identity-scope-and-agent-constraints/design.md#路径是地址不是钥匙)——
> 它指认哪一份工作区，不圈定 agent 能碰什么。真要圈定，用的是这一维的 `never-allow`：
> 作用整个落到沙箱里去，而不是在宿主机上画一条目录线。

### 分类的两个维度

**维度一：一次工具执行产生的效用是否持久。**这是主判据。
不持久的，用完即弃；持久的，就要问它绑定在哪一层。

**维度二：是否与宿主机隔离。**

两维一交叉，四种执行环境的位置就定了：

| | **不隔离** | **隔离** |
|---|---|---|
| 效用**不持久** | —— | **无状态沙箱** |
| 效用持久 · 活到**一次会话** | —— | **会话级沙箱** |
| 效用持久 · 活到**租户** | —— | **租户级沙箱** |
| 效用持久 · 活在**部署** | **宿主机** | —— |

**两个「不绑定」含义相反，这是必须拆成两维的原因**：
无状态沙箱不绑定是因为**用完就扔**，宿主机不绑定是因为**大家共用**。
只用一个「绑定层级」维度，这两者会被并到一起——而它们的风险恰好相反。

### 设施

**一个执行环境提供哪几种做事的手段。**浏览器是一种，命令行是一种，文件系统是一种。

> **每一个具体的执行环境都要声明自己提供哪几种设施。这包括宿主机——它不是例外。**

**设施与上面两个维度正交。**三者各回答一个不同的问题：

| 问的是什么 | 由什么回答 |
|---|---|
| 它**活多久**、**谁看得见** | 维度一与维度二，即上面那四种执行环境 |
| 在里面**能干什么** | **设施声明** |

所以两个同为「会话级沙箱」的执行环境，提供的设施可以完全不同；
反过来，同一种设施（比如命令行）也可以由不同绑定层级的执行环境提供。
**上面那张四格表不会因为设施而变宽**——那张表分的是寿命与隔离，不是本事。

**为什么必须有这一层**：没有它，[§6.5「一个会话、一个租户可以同时有多组执行环境」](#65-一个会话一个租户可以同时有多组执行环境)
就没有落脚点——**凭什么要多组？正因为设施不同**。一个 agent 同时用着命令行沙箱和
浏览器沙箱，差别不在寿命，而在里面有什么。

**为什么宿主机也要声明**：[落点是每次执行算出来的](#61-宿主机始终在场沙箱实现装配时可选装配)，
而算它要拿**这次要什么设施**去比。若沙箱都声明设施而宿主机不必，它当场又变回特例，
「宿主机与沙箱以同一种方式被处理」这条就破了——而那正是运行时热替换的前提。

**谁来提需求、怎么对上，不归这里。**执行环境声明**自己提供什么**，是本 topic 的事；
工具声明**自己需要什么**、装配时怎么匹配、匹配不上怎么办，归**工具与技能**那一块。

### 沙箱内的数据

**与沙箱本体分开的一个东西。**三类沙箱里都有数据，但**对它的持久要求只有一类有**：

| | 对沙箱内数据的持久要求 |
|---|---|
| 无状态沙箱 | **无**。一次调用结束就没了，本来就没有该留的 |
| 会话级沙箱 | **无**。到点销毁、不留存，这是刻意的（§6.3） |
| **租户级沙箱** | **必须可备份、可迁移**，需要和**租户**生命周期一样长（§6.4） |

**把本体与数据分开，是为了让租户级那一行成立**——只有分开之后，
「云主机允许停机换节点」和「攒下来的东西不能丢」才可能同时满足。展开见 §5.2。

### 执行环境权限

**按工具逐个授予的一项权限，管的是「这个工具的作用能不能直接落在[宿主机](#宿主机)上」。**

**恰三态：**

| 取值 | 它说什么 |
|---|---|
| **`always-allow`** | **准它直接落宿主机** |
| **`auto_place`** | **由系统算出合适的执行环境** |
| **`never-allow`** | **绝不落宿主机**。去得了隔离环境就去，去不了就[拒绝](#69-落点不可用就是拒绝不降级) |

**在组织级与租户级授予**，每个工具**各配各的**。

> **「作用能不能直接落在宿主机上」只有这一项在管，没有第二项。**
> **把它配成 `never-allow`**，就是「这个工具不许直接使用宿主机」；
> **它不是 `never-allow`**，这个工具就有用宿主机的资格。

> **它只决定作用落在哪，不决定动作准不准。**
> 「这个动作能不能做」是[另一维](../PF-007-meta-capabilities/design.md#56-一次放行判断走四步)的事。

**这一档特意不叫 `auto`。**它要与[会话运行模式](../PF-015-session-lifecycle-and-ownership/design.md#会话运行模式)
那一维的 `auto_permission` 分得开——**两者都是三态，而且会在同一次执行里一前一后出现**：
**一个决定「准不准」，一个决定「落在哪」。**

## 五、模型

### 5.1 四种执行环境

| | **无状态沙箱** | **会话级沙箱** | **租户级沙箱** | **宿主机** |
|---|---|---|---|---|
| **活多久** | **一次工具调用** | 有**最大连续存活时间** | **本体可停机、可换节点；数据与租户同寿** | 与部署同在 |
| **绑定在** | 不绑定（用完就扔） | 一个会话 | 一个租户 | 不绑定（大家共用） |
| **隔离** | 是 | 是 | 是 | **否** |
| **共享范围** | 无 | 该会话 | **该租户的全部会话与全部 agent runtime** | 全部 |
| **数据要求** | **无** | **无**（见 §6.3） | **必须可备份、可迁移**（§6.4） | 归部署 |
| **为什么要它** | 不是为了隔离状态，**是为了隔离执行** | 后一步要基于前一步的结果 | **跨会话共享的工作空间** | 没有隔离需要时最直接 |
| **典型** | 一次 browser use、一次 shell command | 浏览器里连续操作、命令行里连续执行 | computer use：全租户共用一台隔离的机器 | 本机直接执行 |

**第一列「为什么要它」那一格值得单独说**：无状态沙箱存在的理由**不是**
「这些状态不值得留」，而是**「这个动作不许落在宿主机上」**。
它是[执行环境权限](#执行环境权限)的产物，不是状态管理的产物。

### 5.2 租户级沙箱：本体的存活，与数据的存活，是两件事

**这一节只讲租户级沙箱。**另外两类不需要这个区分——无状态沙箱本来就没有该留的东西，
会话级沙箱本版明确不留（§6.3）。对它们谈「停机换节点」也无从谈起。

产品负责人关于**租户级沙箱**的原话：

> 「确实有需要和租户生命周期一样长的部分，**但那是沙箱内的数据**。」

| | 本质 | **租户级沙箱**的产品要求 |
|---|---|---|
| **沙箱本体** | **计算资源** | **允许停机、允许换一个物理节点** |
| **沙箱内的数据** | **数据** | **必须可备份、可迁移**——需要和租户生命周期一样长的是它，不是那台机器 |

**这是「数据 vs 计算资源」在本系统里的第三次出现**，形状与前两次完全一样：

| | 数据（活得久） | 计算资源（可随时换） |
|---|---|---|
| [PF-004](../PF-004-agent-definition-and-assembly/design.md) | Agent Definition | [agent runtime](../PF-012-agent-loop-and-run/design.md#agent-runtime) |
| [PF-012](../PF-012-agent-loop-and-run/design.md) | 会话历史 | agent runtime |
| **本 topic** | **租户级沙箱内的数据** | **沙箱本体** |

三次都指向同一条：**把跑的那个和存的那个分开，跑的那个才可以被随时回收、替换、迁移。**

### 5.3 换执行环境是换一个值，不是开关一套机制

```text
   每一次工具执行
        │
        ├── 这扇门的执行环境权限（运行时可变）
        ├── 这次要用的设施
        └── 已装配的沙箱实现各自声明的（设施 × 可绑定层级）
        │
        ↓
   ┌──────────────────────────┐
   │  这次的落点（算出来的）  │ ──→ agent runtime 照常执行
   │  宿主机 / 某个沙箱       │     （动作空间不变）
   └──────────────────────────┘
```

agent 发起的是「执行一条命令」，从不说「在哪执行」。权限一改，
下一次算出来的落点就换了——**agent runtime 不重建，动作空间不变，agent 无感**。

这条依赖 §6.1：**只有把宿主机与沙箱放在同一套算法里比，这里换的才是「值」而不是「机制」。**

## 六、产品规则

### 6.1 宿主机始终在场，沙箱实现装配时可选装配

**两样东西的地位不一样，这是本节要定死的：**

| | 它怎么来 | 什么时候可用 |
|---|---|---|
| **[宿主机](#宿主机)** | **不装配，始终在场**——[agent runtime](../PF-012-agent-loop-and-run/design.md#agent-runtime) 本身就跑在它上面 | **只要[执行环境权限](#执行环境权限)允许就可用。****不存在「宿主机不可用」** |
| **[沙箱实现](#沙箱实现)** | **装配时可选装配**：装不装、装哪一个，装配方自己定 | 看它**声明的[设施](#设施)与可绑定层级**，**跟这次执行要的对不对得上** |

**全部沙箱实现遵循同一套契约与协议**，因而宿主机与沙箱**以同一种方式被比较**——
这正是热替换的前提。

**落点是每次工具执行现算出来的：**

> **这扇门这次执行该落在哪，按[三态](#执行环境权限)、这次要用的设施、
> 以及已装配的沙箱实现各自声明的（设施 × 可绑定层级）算出来。**
> **算出来要落隔离环境的，就拿设施与层级去匹配已装配的沙箱实现：
> 匹配得上就用，匹配不上[就拒绝](#69-落点不可用就是拒绝不降级)。**

**因此「当前生效的执行环境」是每扇门一个、每次执行一算的**，
不是一次装配定下来的一个全局取值——[粒度本来就是每个工具各配各的](#68-执行环境权限每个工具各配各的)。

**热替换就是这么成立的**：这项权限改了，**不必重建任何东西，agent 也无感**——
因为**落点是每次执行算出来的值**，下一次执行自然按新值算（§5.3）。

### 6.2 宿主机不提供租户隔离，因此必须被显式允许

一个租户的 agent 在宿主机上写下的东西，另一个租户的 agent 看得见。
所以**一个工具的作用能不能直接落在宿主机上，必须被显式授予**，不是缺省可用。

**授予与收回都走[执行环境权限](#执行环境权限)这一项，没有第二处。**
把它配成 `never-allow`，就是「不允许这个工具直接使用宿主机的浏览器或命令行」——
同样的动作改落到一个沙箱里，**动作空间不变，agent 照常执行**。

**这项权限是运行时可变的，因此改了之后不必重建任何东西**（§5.3）——
[下一次执行按新的值算落点](#61-宿主机始终在场沙箱实现装配时可选装配)。

**允许了，范围就是整台宿主机。**[工作区的承载目录不画任何线](#工作区的承载目录不是宿主机上的边界)：
一条 `read` 落在宿主机上，读工作区目录外的文件与读目录内的文件**走的是同一条放行判断**，
没有「出了目录就另算」这回事。要挡，挡的是这扇门落不落宿主机，或者那条命令准不准。

### 6.3 会话级沙箱：到点销毁，数据不留存

- 每个会话级沙箱有**最大连续存活时间**；到点**直接销毁**。
- **本版不对它的数据作持久要求。**销毁即不留存。
- 这个会话下次还要用，就**重建一个新的**，重新计时；
  要什么数据**重新再算**。

理由是**刻意不做**，不是没想到：会话可以无限期存在，但未必每次都要用沙箱；
让它一直占着不释放不合理。而
[agent 能在运行时感知到变化并自行调整轨迹](../PF-004-agent-definition-and-assembly/design.md#64-上下文变化怎样到达-agent)——
它有能力自己重新执行计算。**系统不必替它保管一切。**

「有状态」的准确含义因此是：**在它活着的期间内有状态。**不是状态永久。
它的全部价值就是那个窗口——「后一步基于前一步的结果」在窗口内成立。

**这条有一处代价，必须说出口：**

> **「能重算」是有边界的。**计算结果能重算，外部内容能重下；
> 但 agent 在沙箱里调试了半天的原创产出，**重写 ≠ 重算**。

由此得到一条给所有人的话，包括 agent 自己：

> **会话级沙箱是工作台，不是保险柜。**重要的产出不该只躺在那儿。

### 6.4 租户级沙箱：共享的工作空间

- 它**跨会话共享**，因而也跨 [agent runtime](../PF-012-agent-loop-and-run/design.md#agent-runtime) 共享：
  **该租户的全部 agent 在同一个空间里做事。**
- 它的存活**不是无限的**。允许**停机**，允许**换一个物理节点**。
- 但**沙箱内的数据必须可备份、可迁移**——需要和租户生命周期一样长的是数据，
  不是那台机器。

**同一租户的多个 agent 会互相看见对方的产出，也可能互相覆盖。
这是特性，不是缺陷**——共享工作空间的价值正在于此，就像几个人共用一台电脑。
正文写明它，是为了让它不被当成 bug 报上来。

**跨租户共享不存在。**那会直接破坏
[租户隔离](../../foundation/cross-system-constraints/requirements.md#sys-tenant)，
因此**没有「组织级沙箱」**——三个沙箱层级是穷尽的。

### 6.5 一个会话、一个租户可以同时有多组执行环境

浏览器和命令行是两种不同的沙箱，**绑定层级是每个沙箱各自的**，
不是「一个会话只能挑一种」。一个 agent 完全可能同时用着：
一个会话级命令行沙箱、一个租户级的共享机器，外加一次性的浏览器沙箱。

**要多组的原因是[设施](#设施)不同，不是寿命不同。**浏览器沙箱和命令行沙箱哪怕
绑定层级完全一样，也换不了对方的班——里面有的东西不一样。这条是「多组」的
唯一理由；若两个执行环境的设施相同、层级也相同，那就没有并存的必要。

**这与[落点每次现算](#61-宿主机始终在场沙箱实现装配时可选装配)是同一件事的两面**：
落点按**门**算，几扇门算出几个落点，它们当然可以同时活着。

### 6.6 agent 要知道自己落在哪、上次的东西还在不在

**这次执行落在哪个执行环境**，以及它**是否保留上一次的痕迹**，
属于 [agent 可感知的上下文](../PF-004-agent-definition-and-assembly/design.md#运行期上下文)。
**它感知的是每扇门各自的落点**，不是一个全局取值。

- 落点换了（比如权限收紧、沙箱到期重建），按 PF-004 §6.4 的方式，
  **在下一轮以一条提醒到达**，不打断当前正在进行的运行。
- agent **读到**它，然后自行决定要不要重算——不是系统在背后替它处理。

**不让 agent 知道这件事，它就会把东西留在注定消失的地方**，
而 §6.3 那条「重算」的前提也就落空了。

### 6.7 沙箱不是资产

[PF-002 的资产](../PF-002-assets-settings-and-permissions/design.md#八类资产)
是「约束 agent **由什么组装而成**」的东西；执行环境是动作**落地**的地方，
不参与组装。

因此沙箱**不进那八类**，也不走持有、[复制](../PF-003-asset-transfer-and-sharing/design.md#资产复制)、分享那一套。

**[沙箱实现](#沙箱实现)同理**：它是**装配进来的一个提供者**，
提供的是动作落地的地方，**不参与「agent 由什么组装而成」**，所以它也不是资产。

### 6.8 执行环境权限：每个工具各配各的

**[三态](#执行环境权限)按工具逐个授予，互不牵连。**
`Shell()` 可以是 `auto_place`，`Computer()` 同时是 `never-allow`，
`Browser()` 又是 `always-allow`——**三个值之间没有任何推导关系**，
不会因为其中一个严就连带收紧另一个。

**粒度是「门」这一级，不是命令级。**执行环境是配给一扇门的，
**门后所有命令的作用都落在同一处**；而
[「能不能做」本来就是一条一条命令的事](../PF-007-meta-capabilities/design.md#57-权限能关掉一条命令关不掉一扇门)。
**两维粒度不同不是疏漏，是各自管的东西决定的。**

**三件事跟着这条一起定死：**

- **[meta tool](../PF-007-meta-capabilities/design.md#四概念定义) 一样受它管。**
  给 `Shell()` 配 `never-allow` **并没有关掉那扇门**——门还在，只是规定它的作用落在隔离环境里，
  **不触[「关不掉一扇门」那条红线](../PF-007-meta-capabilities/design.md#57-权限能关掉一条命令关不掉一扇门)**。
  反过来看更清楚：**`Shell()` 恰恰是最该管落点的那一个，它若不受管，这一维就形同虚设**。
- **[工作区那一级不参与](../PF-002-assets-settings-and-permissions/design.md#57-工作区那一级不参与权限计算)。**
  授权与权限相关的配置，**系统加载时就把工作区来的滤掉了**。
- **没声明要用执行环境的工具，这一维对它不适用。**
  工具**自己声明**要不要用——那是实现时的契约，**不是「默认取哪一档」**。

### 6.9 落点不可用就是拒绝，不降级

**这一条只对隔离环境说。**[宿主机不在此列](#61-宿主机始终在场沙箱实现装配时可选装配)——
它始终在场，只要权限允许就可用，**没有「不可用」这回事**。

**算出来该落进隔离环境，那个环境就必须真的到位；到不了位，这次执行被拒。**

> **不回退宿主机，也不换一个更宽松的落点。**

三种到不了位的情形，**处置完全一样**：

| 情形 | 怎么办 |
|---|---|
| **没有一个已装配的[沙箱实现](#沙箱实现)在设施与层级上匹配得上** | **拒绝**，说明差的是哪一样 |
| **匹配得上，但沙箱创建失败** | **拒绝**，明确告诉调用方 |
| **`never-allow` 的工具，隔离环境也去不了** | **拒绝**。没有第三条路 |

**因为降级就是绕过安全判断。**落点是算出来的结果，
**算的时候已经把租户隔离、以及组织级与租户级配的那项权限都考虑进去了**；
这时候「退一步用宿主机」等于把刚才那套判断作废，
**而[宿主机恰恰是唯一不提供租户隔离的那一个](#62-宿主机不提供租户隔离因此必须被显式允许)**。

> **失败是可解释的，静默降级不是。**
> 一次被拒绝的执行，调用方知道发生了什么；
> 一次悄悄落在宿主机上的执行，**没有人会发现隔离已经破了**。

## 七、取舍

| 面临的选择 | 选了 | 为什么 |
|---|---|---|
| 装配时注入一个执行环境 ／ **宿主机始终在场、沙箱实现可选装配、落点每次执行算** | **后者** | 注入一个，「三扇门同时要三个不同落点」就落不下去，而[粒度本来就是每个工具各配各的](#68-执行环境权限每个工具各配各的)。**落点是算出来的值**，热替换因此仍然成立：权限一改，下一次执行自己按新值算，**不必重建任何东西，agent 无感** |
| 宿主机也当成要装配的一个取值 ／ **始终在场** | **始终在场** | agent runtime 本身就跑在它上面——**宿主机不在，整个系统就不在**。给它留一个「装了没有」的状态，等于给一个永远为真的条件留一条永远走不到的假分支 |
| 沙箱实现各自一套接口 ／ **全部遵循同一套契约与协议** | **同一套** | 只有同一套，宿主机与各种沙箱才**以同一种方式被比较**，「换落点」才是换值而不是换机制。**代价是每一个沙箱实现都得把自己的设施与可绑定层级声明清楚** |
| 「沙箱」作上位概念 ／ 「执行环境」作上位概念 | **执行环境** | PF-004 已经把执行环境定成上位概念，改名等于同一个东西两个名字。且「宿主机是一种沙箱」字面绊人——它恰恰是不 sandbox 的那一个。**实质是同一个抽象** |
| 用一个「绑定层级」维度 ／ 拆成持久性与隔离性两维 | **两维** | 一维说不清两个「不绑定」：无状态沙箱是用完就扔，宿主机是大家共用，**风险正好相反** |
| 会话级沙箱的数据留存 ／ 不留存 | **不留存** | 留存要为每个会话保管一份数据，存储成本随会话数长，而这是**过早引入的复杂度**。agent 能感知变化并自行重算，系统不必替它保管一切 |
| 租户级沙箱的数据也不作要求 ／ 必须可备份可迁移 | **必须** | 它是跨会话共享的长期工作空间，数据没了影响的是该租户的全部会话。而且「允许停机换节点」只有在数据能迁移时才成立 |
| 沙箱本身要求长期存活 ／ 只要求数据能迁移 | **只要求数据** | 要求那台机器长期不停，等于禁止运维。**把跑的那个和存的那个分开**，两个要求才能同时满足 |
| 提供组织级沙箱 ／ 不提供 | **不提供** | 跨租户共享直接破坏租户隔离。三层是穷尽的 |
| 租户级共享的互相影响作为缺陷 ／ 作为特性 | **特性** | 共享工作空间的价值正在于互相看得见。当成缺陷去修，就得加隔离，那它就不是共享空间了 |
| agent 不必知道环境情况 ／ 必须能感知 | **必须能感知** | 不知道的话，它会把重要东西留在注定消失的地方，「重算」的前提落空 |
| 沙箱算一类资产 ／ 不算 | **不算** | 资产是「由什么组装而成」，沙箱是「落在哪里」。归进去就得给它持有、复制、分享的语义，而那些对它毫无意义 |
