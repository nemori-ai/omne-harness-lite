# PF-005：执行环境与沙箱

- 修订：rev 1，2026-09-17 · [变更历史](changelog.md)
- 状态：已定稿，**无未决项**

## 一、背景与问题

[PF-004](../PF-004-agent-runtime-assembly-and-liveness/design.md) 把**执行环境**
定成注入给运行实例的三样东西之一——动作实际落到哪里，由它决定。它还定了一条很强的性质：
**一条 shell 命令，执行在宿主机还是沙箱里，agent 都能执行。**

但**有哪几种执行环境、各自什么性质、里面的东西什么时候还在什么时候没**，
PF-004 有意留空了。留空的代价现在开始显现：

- **一次工具执行到底落在哪儿？**说不清，就没法回答「这个动作安全吗」。
- **「不允许直接用宿主机的浏览器或命令行」这条安全策略挡的是什么？**
  它挡的那个东西没有名字。
- **沙箱里的东西什么时候没？**没人知道——**agent 自己也不知道**，
  于是它会把重要的东西留在一个注定消失的地方。
- **一个租户的所有 agent 共用一台隔离的机器**（computer use）——
  这是产品的核心需求，但没有对象承载它。

本 topic 把执行环境展开：有哪几种、各自的状态活多久、数据有什么要求、
以及它们之间怎么互换而 agent 无感。

## 二、目标与非目标

### 目标

1. **定义执行环境的种类**，以及分类所依据的两个维度。
2. **钉死「宿主机是一个取值，不是默认状态」**——这是热替换能不能成立的分水岭。
3. **说清每一类的状态活多久、数据有什么要求**，包括明确**不要求**的那部分。
4. **说清租户级共享的语义**及其代价。

### 非目标

| 不做什么 | 为什么 |
|---|---|
| 用什么技术实现隔离 | 容器、虚拟机、云主机——那是技术选择。本 topic 只定**产品上必须成立的性质** |
| 工具怎么声明它需要什么样的环境 | 归**工具与技能**那一块。本 topic 定环境本身，不定谁来提要求 |
| 安全策略怎么配置、谁能改 | 那是 [PF-002](../PF-002-assets-settings-and-permissions/design.md) 的设置与权限。本 topic 只定**策略改了之后执行环境怎么换** |
| 制品、工作副本怎么管 | 「重要产出该存哪」是另一件事。本 topic 只负责说明**沙箱不是存它的地方** |
| 沙箱内数据的备份与迁移**怎么做** | 本 topic 只定**哪一类必须能备份能迁移**，不定机制 |
| 宿主机本身怎么部署、怎么运维 | 归部署那一侧 |
| 具体有哪些沙箱形态 | 浏览器、命令行、完整桌面……本 topic 定的是**分类与性质**，不枚举形态 |

## 三、用户与场景

| 使用者 | 什么情况下接触这块 | 他关心什么 |
|---|---|---|
| **用 agent 干活的人** | agent 帮他跑命令、开浏览器、操作一台机器 | 它在哪儿干的？会不会动到我本机的东西？ |
| **组织管理员 / 安全负责人** | 配执行安全策略 | 能不能禁止 agent 直接碰宿主机？改了之后什么时候生效？ |
| **同一租户里的多个使用者** | 共用一台隔离的机器做事 | 我装的东西别人看得见吗？别人会不会覆盖我的？ |
| **对成本负责的人** | 看账单 | 一台闲着的沙箱是不是一直在烧钱？ |
| **agent 自己** | 每一次工具执行 | 我这次落在哪儿？上次留下的东西还在不在？ |

**最后一行是这块设计的直接消费者。**它答不上来第二个问题，就会把重要的东西
留在一个注定消失的地方——而本 topic 的一条规则就是为了让它答得上来（§6.6）。

### 执行环境

[PF-004 已经定了它](../PF-004-agent-runtime-assembly-and-liveness/design.md#执行环境)：
**动作实际落到哪里。**本 topic 不改写这个定义，只把它展开。

展开的第一句就是本 topic 最要紧的一条：

> **执行环境永远存在。不存在「没有执行环境」这个状态**——动作总要落在某处。

因此**宿主机不是「没有沙箱」的那个默认状态，它是执行环境的一个具体取值**。
装配时必须明确注入一个，哪怕注入的就是宿主机。理由见 §6.1。

### 沙箱

**与宿主机相互隔离的一种执行环境。**

「沙箱」不是执行环境的上位概念，**它是执行环境中「隔离」的那些**。
宿主机是执行环境中「不隔离」的那一个。两者在同一个抽象下，因此可以互换——
这正是「按安全策略在运行时热替换执行环境而 agent 无感」能成立的前提。

### 宿主机

**agent 运行时本身所在的地方，也是唯一不隔离的执行环境。**

它的「特殊」只有一处，但这一处很要紧：

> **宿主机不提供租户隔离。**一个租户的 agent 在宿主机上写下的东西，
> 另一个租户的 agent 看得见。

这直接顶在 [SYS-TENANT](../../foundation/cross-system-constraints/requirements.md#sys-tenant) 上。
所以它**不是一个随便可用的选项，而是必须被显式允许才能用的选项**——
这也正是「执行安全策略」要挡的东西（§6.2）。

### 分类的两个维度

**维度一：一次工具执行产生的效用是否持久。**这是主判据。
不持久的，用完即弃；持久的，就要问它绑定在哪一层。

**维度二：是否与宿主机隔离。**

两维一交叉，四种执行环境的位置就定了：

| | **不隔离** | **隔离** |
|---|---|---|
| 效用**不持久** | —— | **无状态沙箱** |
| 效用持久 · 活到**一次会话** | —— | **会话级沙箱** |
| 效用持久 · 活到**租户** | —— | **租户级沙箱** |
| 效用持久 · 活在**部署** | **宿主机** | —— |

**两个「不绑定」含义相反，这是必须拆成两维的原因**：
无状态沙箱不绑定是因为**用完就扔**，宿主机不绑定是因为**大家共用**。
只用一个「绑定层级」维度，这两者会被并到一起——而它们的风险恰好相反。

### 设施

**一个执行环境提供哪几种做事的手段。**浏览器是一种，命令行是一种，文件系统是一种。

> **每一个具体的执行环境都要声明自己提供哪几种设施。这包括宿主机——它不是例外。**

**设施与上面两个维度正交。**三者各回答一个不同的问题：

| 问的是什么 | 由什么回答 |
|---|---|
| 它**活多久**、**谁看得见** | 维度一与维度二，即上面那四种执行环境 |
| 在里面**能干什么** | **设施声明** |

所以两个同为「会话级沙箱」的执行环境，提供的设施可以完全不同；
反过来，同一种设施（比如命令行）也可以由不同绑定层级的执行环境提供。
**上面那张四格表不会因为设施而变宽**——那张表分的是寿命与隔离，不是本事。

**为什么必须有这一层**：没有它，[§6.5「一个会话、一个租户可以同时有多组执行环境」](#65-一个会话一个租户可以同时有多组执行环境)
就没有落脚点——**凭什么要多组？正因为设施不同**。一个 agent 同时用着命令行沙箱和
浏览器沙箱，差别不在寿命，而在里面有什么。

**为什么宿主机也要声明**：[§6.1](#61-宿主机是一个取值不是默认状态) 已经定死宿主机是一个取值、不是默认状态。
若沙箱都声明设施而宿主机不必，它当场又变回特例，
「宿主机与沙箱以同一种方式被处理」这条就破了——而那正是运行时热替换的前提。

**谁来提需求、怎么对上，不归这里。**执行环境声明**自己提供什么**，是本 topic 的事；
工具声明**自己需要什么**、装配时怎么匹配、匹配不上怎么办，归**工具与技能**那一块。

### 沙箱内的数据

**与沙箱本体分开的一个东西。**三类沙箱里都有数据，但**对它的持久要求只有一类有**：

| | 对沙箱内数据的持久要求 |
|---|---|
| 无状态沙箱 | **无**。一次调用结束就没了，本来就没有该留的 |
| 会话级沙箱 | **无**。到点销毁、不留存，这是刻意的（§6.3） |
| **租户级沙箱** | **必须可备份、可迁移**，需要和**租户**生命周期一样长（§6.4） |

**把本体与数据分开，是为了让租户级那一行成立**——只有分开之后，
「云主机允许停机换节点」和「攒下来的东西不能丢」才可能同时满足。展开见 §5.2。

## 五、模型

### 5.1 四种执行环境

| | **无状态沙箱** | **会话级沙箱** | **租户级沙箱** | **宿主机** |
|---|---|---|---|---|
| **活多久** | **一次工具调用** | 有**最大连续存活时间** | **本体可停机、可换节点；数据与租户同寿** | 与部署同在 |
| **绑定在** | 不绑定（用完就扔） | 一个会话 | 一个租户 | 不绑定（大家共用） |
| **隔离** | 是 | 是 | 是 | **否** |
| **共享范围** | 无 | 该会话 | **该租户的全部会话与全部 agent 实例** | 全部 |
| **数据要求** | **无** | **无**（见 §6.3） | **必须可备份、可迁移**（§6.4） | 归部署 |
| **为什么要它** | 不是为了隔离状态，**是为了隔离执行** | 后一步要基于前一步的结果 | **跨会话共享的工作空间** | 没有隔离需要时最直接 |
| **典型** | 一次 browser use、一次 shell command | 浏览器里连续操作、命令行里连续执行 | computer use：全租户共用一台隔离的机器 | 本机直接执行 |

**第一列「为什么要它」那一格值得单独说**：无状态沙箱存在的理由**不是**
「这些状态不值得留」，而是**「这个动作不许落在宿主机上」**。
它是安全策略的产物，不是状态管理的产物。

### 5.2 租户级沙箱：本体的存活，与数据的存活，是两件事

**这一节只讲租户级沙箱。**另外两类不需要这个区分——无状态沙箱本来就没有该留的东西，
会话级沙箱本版明确不留（§6.3）。对它们谈「停机换节点」也无从谈起。

产品负责人关于**租户级沙箱**的原话：

> 「确实有需要和租户生命周期一样长的部分，**但那是沙箱内的数据**。」

| | 本质 | **租户级沙箱**的产品要求 |
|---|---|---|
| **沙箱本体** | **计算资源** | **允许停机、允许换一个物理节点** |
| **沙箱内的数据** | **数据** | **必须可备份、可迁移**——需要和租户生命周期一样长的是它，不是那台机器 |

**这是「数据 vs 计算资源」在本系统里的第三次出现**，形状与前两次完全一样：

| | 数据（活得久） | 计算资源（可随时换） |
|---|---|---|
| [PF-004](../PF-004-agent-runtime-assembly-and-liveness/design.md) | Agent Definition | 运行实例 |
| PF-004 | 会话历史 | 运行实例 |
| **本 topic** | **租户级沙箱内的数据** | **沙箱本体** |

三次都指向同一条：**把跑的那个和存的那个分开，跑的那个才可以被随时回收、替换、迁移。**

### 5.3 换执行环境是换一个值，不是开关一套机制

```text
                        ┌──────────────────────────┐
   运行实例 ←──注入──── │  当前生效的执行环境      │
   （动作空间不变）      │  宿主机 / 各类沙箱之一   │
                        └──────────────────────────┘
                                   ↑
                        执行安全策略（运行时可变）
```

agent 发起的是「执行一条命令」，从不说「在哪执行」。策略一改，
注入的那个取值就换了——**运行实例不重建，动作空间不变，agent 无感**。

这条依赖 §6.1：**只有把宿主机也当成一个取值，这里换的才是「值」而不是「机制」。**

## 六、产品规则

### 6.1 宿主机是一个取值，不是默认状态

**装配时必须明确注入一个执行环境**，哪怕注入的就是宿主机。

看着像措辞，实则是热替换能不能成立的分水岭：

| 把宿主机当成 | 注入变成什么 | 切换是什么 | agent 感知得到吗 |
|---|---|---|---|
| 默认 / 无环境 | 「**要不要**套一个沙箱」的布尔问题 | 启用或关闭一套机制 | **感知得到**——两条路走的是不同的东西 |
| **一个具体取值** | 「注入**哪一个**执行环境」 | **换一个值** | **无感** |

第一行那种做法做不到运行时热替换：那不是换值，是换机制。

### 6.2 宿主机不提供租户隔离，因此必须被显式允许

一个租户的 agent 在宿主机上写下的东西，另一个租户的 agent 看得见。
所以**「可以使用宿主机」是一项必须被显式授予的资格**，不是缺省可用。

**执行安全策略挡的就是这个。**「不允许直接使用宿主机的浏览器或命令行」
生效之后，同样的动作改落到一个沙箱里——**动作空间不变，agent 照常执行**。

策略是运行时可变的注入，因此**改了之后不必重建任何东西**（§5.3）。

### 6.3 会话级沙箱：到点销毁，数据不留存

- 每个会话级沙箱有**最大连续存活时间**；到点**直接销毁**。
- **本版不对它的数据作持久要求。**销毁即不留存。
- 这个会话下次还要用，就**重建一个新的**，重新计时；
  要什么数据**重新再算**。

理由是**刻意不做**，不是没想到：会话可以无限期存在，但未必每次都要用沙箱；
让它一直占着不释放不合理。而
[agent 能在运行时感知到变化并自行调整轨迹](../PF-004-agent-runtime-assembly-and-liveness/design.md#64-上下文变化怎样到达-agent)——
它有能力自己重新执行计算。**系统不必替它保管一切。**

「有状态」的准确含义因此是：**在它活着的期间内有状态。**不是状态永久。
它的全部价值就是那个窗口——「后一步基于前一步的结果」在窗口内成立。

**这条有一处代价，必须说出口：**

> **「能重算」是有边界的。**计算结果能重算，外部内容能重下；
> 但 agent 在沙箱里调试了半天的原创产出，**重写 ≠ 重算**。

由此得到一条给所有人的话，包括 agent 自己：

> **会话级沙箱是工作台，不是保险柜。**重要的产出不该只躺在那儿。

### 6.4 租户级沙箱：共享的工作空间

- 它**跨会话共享**，因而也跨 agent 实例共享：
  **该租户的全部 agent 在同一个空间里做事。**
- 它的存活**不是无限的**。允许**停机**，允许**换一个物理节点**。
- 但**沙箱内的数据必须可备份、可迁移**——需要和租户生命周期一样长的是数据，
  不是那台机器。

**同一租户的多个 agent 会互相看见对方的产出，也可能互相覆盖。
这是特性，不是缺陷**——共享工作空间的价值正在于此，就像几个人共用一台电脑。
正文写明它，是为了让它不被当成 bug 报上来。

**跨租户共享不存在。**那会直接破坏
[租户隔离](../../foundation/cross-system-constraints/requirements.md#sys-tenant)，
因此**没有「组织级沙箱」**——三个沙箱层级是穷尽的。

### 6.5 一个会话、一个租户可以同时有多组执行环境

浏览器和命令行是两种不同的沙箱，**绑定层级是每个沙箱各自的**，
不是「一个会话只能挑一种」。一个 agent 完全可能同时用着：
一个会话级命令行沙箱、一个租户级的共享机器，外加一次性的浏览器沙箱。

**要多组的原因是[设施](#设施)不同，不是寿命不同。**浏览器沙箱和命令行沙箱哪怕
绑定层级完全一样，也换不了对方的班——里面有的东西不一样。这条是「多组」的
唯一理由；若两个执行环境的设施相同、层级也相同，那就没有并存的必要。

### 6.6 agent 要知道自己落在哪、上次的东西还在不在

当前生效的执行环境，以及它**是否保留上一次的痕迹**，
属于 [agent 可感知的上下文](../PF-004-agent-runtime-assembly-and-liveness/design.md#运行期上下文)。

- 环境被换掉（比如策略收紧、沙箱到期重建），按 PF-004 §6.4 的方式，
  **在下一轮以一条提醒到达**，不打断当前正在进行的运行。
- agent **读到**它，然后自行决定要不要重算——不是系统在背后替它处理。

**不让 agent 知道这件事，它就会把东西留在注定消失的地方**，
而 §6.3 那条「重算」的前提也就落空了。

### 6.7 沙箱不是资产

[PF-002 的资产](../PF-002-assets-settings-and-permissions/design.md#五类资产)
是「约束 agent **由什么组装而成**」的东西；执行环境是动作**落地**的地方，
不参与组装。

因此沙箱**不进那五类**，也不走持有、转移、分享那一套。
它是被注入的，不是被装配的。

## 七、取舍

| 面临的选择 | 选了 | 为什么 |
|---|---|---|
| 宿主机作为默认状态 ／ 作为一个取值 | **一个取值** | 作为默认状态的话，切换就是「开关一套机制」而不是「换一个值」，运行时热替换做不到，agent 也感知得到 |
| 「沙箱」作上位概念 ／ 「执行环境」作上位概念 | **执行环境** | PF-004 已经把执行环境定成上位概念，改名等于同一个东西两个名字。且「宿主机是一种沙箱」字面绊人——它恰恰是不 sandbox 的那一个。**实质是同一个抽象** |
| 用一个「绑定层级」维度 ／ 拆成持久性与隔离性两维 | **两维** | 一维说不清两个「不绑定」：无状态沙箱是用完就扔，宿主机是大家共用，**风险正好相反** |
| 会话级沙箱的数据留存 ／ 不留存 | **不留存** | 留存要为每个会话保管一份数据，存储成本随会话数长，而这是**过早引入的复杂度**。agent 能感知变化并自行重算，系统不必替它保管一切 |
| 租户级沙箱的数据也不作要求 ／ 必须可备份可迁移 | **必须** | 它是跨会话共享的长期工作空间，数据没了影响的是该租户的全部会话。而且「允许停机换节点」只有在数据能迁移时才成立 |
| 沙箱本身要求长期存活 ／ 只要求数据能迁移 | **只要求数据** | 要求那台机器长期不停，等于禁止运维。**把跑的那个和存的那个分开**，两个要求才能同时满足 |
| 提供组织级沙箱 ／ 不提供 | **不提供** | 跨租户共享直接破坏租户隔离。三层是穷尽的 |
| 租户级共享的互相影响作为缺陷 ／ 作为特性 | **特性** | 共享工作空间的价值正在于互相看得见。当成缺陷去修，就得加隔离，那它就不是共享空间了 |
| agent 不必知道环境情况 ／ 必须能感知 | **必须能感知** | 不知道的话，它会把重要东西留在注定消失的地方，「重算」的前提落空 |
| 沙箱算一类资产 ／ 不算 | **不算** | 资产是「由什么组装而成」，沙箱是「落在哪里」。归进去就得给它持有、转移、分享的语义，而那些对它毫无意义 |
