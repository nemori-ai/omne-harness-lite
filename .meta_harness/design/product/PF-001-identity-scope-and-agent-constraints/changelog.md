# PF-001 变更历史

记录**产品设计本身**的演进：哪一版改了什么含义、为什么改、下游要复核什么。
错别字、链接修复、段落搬家不记这里。

技术投影用 `provenance.json` 引用具体 rev，所以这里的 rev 不准会直接传导到实现侧。

## rev 8 · 两种邀约都会过期 — 2026-09-22

**产品负责人直接裁决**：「通知和邀请作过期机制，资产本身不存在的话相关的通知和邀请也要自动过期。」
那句话的主干落在 [PF-003 rev 3](../PF-003-asset-transfer-and-sharing/changelog.md#rev-3--转移改名资产复制待确认的邀约有过期--2026-09-22)（资产那一侧）；
本 topic 承接它的另一半——**这里的邀约指向的是组织**。

| 加了什么 | 落在哪 |
|---|---|
| **加入组织的邀请**与**建立隶属的那份请求**都会过期；**时长可配、有默认**，具体多少是政策 | [§4 两种邀约都会过期](design.md#两种邀约都会过期) |
| **它指向的那个组织不存在了，这份邀约随即自动过期** | 同上 |
| 到期之后**不可再接受**，重新发一份即可；**过期与撤回收场相同**——不产生租户，也不建立隶属 | 同上、[flows §1.5](flows.md#15-邀请与加入)、[flows §2](flows.md#二分支与异常) |

**原有的规则一条都没改。**rev 7 的 flows §2 只写了「邀请已失效或被撤回」，
**从没说过什么叫「失效」**——这一版把那个词定死成「过期」，并补上自动过期这一条来路。

**「组织不存在了」本版没有触发源**（组织的终结路径整体延后），
**规则仍然先立**，理由在 [decisions 第二节](decisions.md#二pm-推导)。

**下游要复核什么**：
任何**把邀请做成永不过期**的实现；任何**只处理「撤回」这一种失效来路**的实现。
[UL-invitation](../../ubiquitous_language/terms/subjects-and-ownership.md#ul-invitation--邀请--invitation)
的定义与[它的对象条目](../../domain_objects/objects.md)「生灭」已补上过期与自动过期——
原先两处都写着「有效期正文未述」，**现在正文述了**。

## rev 7 — 2026-09-19

**资产从七类变八类：补入 Loop Extension。**

**这一版推翻了 rev 6 立的一句话**——「这七类是穷尽的」。
产品负责人 2026-09-19 在三条路里选了这一条，**明知它要推翻已拍板的内容**：

| 三条路 | 选了吗 |
|---|---|
| plugin 扩容为「打包资产**与拓展挂件**」，七类不动 | ✗ |
| **拓展挂件就是第八类资产** | **✓** |
| 挂件独立成树，自己一套持有与授权 | ✗ |

### 为什么这一条值得推翻那句话

**判据一条没少。**资产的判据是[「在 agent definition 里被声明、被持有、被授权、
按层级求值」这四件事](design.md#资产的种类)——拓展挂件**四条全中**。

**而最后一条正是产品要的那个后果**：

> **组织超管在组织层配一份，租户在自己那层覆盖**，走的就是本 topic 已有的层级求值。
> **另建一套，就要再写一遍持有、授权、求值、转移、分享**——
> 那正是「同一概念只有一个权威定义」要避免的事。

### 资产定义的第二次扩展

| 版本 | 「资产」约束的是 |
|---|---|
| rev 5 及以前 | agent **由什么零件构成** |
| **rev 6** | 再加**朝外开哪些口**（Connector） |
| **rev 7** | 再加**推进时在哪些位置插手**（Loop Extension） |

**与 rev 6 那次同一种性质**，一并如实记下，不假装定义没动过。

### 一行从「不在这张表里」挪了出来

rev 6 那张「为什么不在这张表里」写着：**「Hooks、Rules → Plugin 的组合成员」**。

> **Hooks 那一半现在不成立了**——它就是 Loop Extension，是第八类资产本身。
> **Rules 留在原处不动。**

**下游要复核**：任何按「资产恰有七类」实现的枚举、校验或界面；
任何把 hooks 当成 Plugin 内部成员、因而不给它独立持有与授权的东西。

## rev 6 — 2026-09-17

**资产从五类变七类：补入 MCP 与 Connector。**

| | rev 5 | rev 6 |
|---|---|---|
| 资产的种类 | **五类**：Skill、Tool、Plugin、Agent Definition、Slash Command | **七类**，补入 **MCP** 与 **Connector** |
| 「资产」约束 agent 的什么 | **组装**：由什么构成、有哪些技能工具可用 | **组装**，含义扩为「由什么构成，**以及从哪里被触达**」 |
| 外部工具来源 | 没有位置 | **MCP** 是一个接入点。**它带来的动作不单独成为资产**，随它一起被持有、授权与治理 |
| 外部消息来源 | 没有位置 | **Connector** 把外部消息送进来。**方向与其余六类相反** |

起因是产品负责人在「工具与技能」的访谈中指出这两类此前漏定义，要求回补到对应 topic。
Connector 的含义参照 `omne-next/omne_harness`（外部来源接入件，无数据读取面、无管理面）。

### 「五类穷尽」推出的四条结论，逐条复核过，全部不受影响

Hooks/Rules 是 Plugin 成员、Service/Middleware 不进产品正文、模型档案是设置的取值、
知识与文件是读写对象——**这四条依赖的是「这张表是穷尽的」，不是「恰好五个」**。
七类同样穷尽，推理链完好，只是措辞从「第六类」改为「不在这张表里」。

### 一处必须说明的扩展

Connector 约束的是「从哪里被触达」，与原定义「约束 agent 的组装」方向相反。
**处理方式是显式扩展定义，不是悄悄放行**——理由与撤回条件记在
[decisions.md 第四节](decisions.md#四已知的来源问题)。

### 下游要复核什么

- 引用「资产五类」字样的地方要改：[PF-002](../PF-002-assets-settings-and-permissions/README.md)（同步升 rev）、
  [PF-004](../PF-004-agent-definition-and-assembly/README.md)、
  [PF-005](../PF-005-execution-environments-and-sandboxes/README.md) 的相关引用。
- **MCP 带来的动作不是独立资产**——实现时不要为每个 MCP 工具登记一份资产，
  那会让资产身份随外部服务端的版本漂移。
- 两类的**形状、自带属性与组合关系**归 PF-002，本 topic 只定名字、含义与管理边界。

## rev 5 — 2026-09-17

**组织多一个属性「上级组织」，并补齐租户范围创作的归属。**

| | rev 4 | rev 5 |
|---|---|---|
| 组织之间的关系 | 没有。组织彼此独立 | 组织有**至多一个上级组织**，用来表达「团队属于公司」「公司是另一家的子公司」 |
| 隶属怎么建立 | — | **两边的超级管理员各做一次动作**，一方发起一方接受。解除则任一方单方面即可 |
| 租户范围创作归谁 | §6.7 的归属表只列了「组织范围创作」与「个人组织里创作」，**漏了租户范围** | 补上一行：**在自己的租户范围创作，所有者是该租户** |

改动的起因是 [PF-003](../PF-003-asset-transfer-and-sharing/README.md) 需要回答
「哪些组织之间可以流动资产」与「哪些资产是这个人的、哪些是组织的」。
两个答案都属于身份与组织模型，归本 topic，不在 PF-003 里另立一份。

### 下游要注意的四处

- **这是一个属性，不是一套新机制。**隶属链由「上级组织」自然长出，
  不要为它建独立的组织树对象或关系表。
- **至多一个上级。**一个组织有两个母公司，本版不表达。
  真要做需要的是关系表而不是属性，那时再改。
- **上级组织不进四层作用域。**子组织**不**自动继承上级的设置、权限与资产。
  按隶属链继承会让作用域层数随组织结构变化，还把「隶属」悄悄变成「被管辖」。
- **租户级资产的所有者是那个租户，不是组织。**由此得到一条不可逆：
  从租户范围提升到组织范围是一次交付，所有权随之易手，**不能退回**。
- **隶属关系不能单方面建立。**允许单方面指定下级，等于给一个人开了条边界后门。
  已经存在的两个组织（包括由不同账号创建的）之间可以建立，否则并购与重组无从表达。

## rev 4 — 2026-09-17

**资产作者的标识身份定为租户。**

| | rev 3 | rev 4 |
|---|---|---|
| 作者用什么身份 | 只说了「实际作者与定义所有者分别记录」，没说各用什么身份 | **作者是租户 (组织, 账号)**——正好表达「那个组织里的谁」 |

### 下游要注意的

- **作者记录不随角色变动而变**（角色不进租户身份），也**不随成员关系解除而失效**
  （它记的是当时是谁做的，不是现在谁还在）。
- **所有者与作者分开记**：在组织范围创作的，所有者是**组织**，作者是**那个租户**。
  成员退出时两者去向不同——资产留在组织，作者记录照旧。
- **agent 产出的作者仍是它运行所在的租户**，但要标明是 agent 产出，否则审计答不出
  「这是人写的还是 agent 写的」。
- **official 资产没有作者租户**，所有者与作者都是平台。实现不要为它找一个不存在的租户。

## rev 3 — 2026-09-17

**默认与强制用同一个机制表达。**

每一层对一个东西只能做两件事：给一个值，以及声明它不可再被下层覆盖
（`immutable`）。不加就是**默认**，加了就是**强制**。

| | rev 2 | rev 3 |
|---|---|---|
| 「组织可强制、个人不可改」 | 把那类字段**声明为收窄语义** | 给值时加 **immutable** |
| 适用范围 | 只对权限说得通 | 设置、权限、资产替换**三处通用** |

**为什么换**：rev 2 的解法对权限成立（收窄到单元素），对设置不成立——
设置的取值域通常是开放的（比如模型名），谈不上收窄成子集。
immutable 把「默认 / 强制」的区别落在**同一个字段的一个标记**上，
而不是落在**两种不同的合成语义**上。

对权限而言 `immutable(v)` 就是收窄到 `{v}`，是收窄的特例，两者不冲突。

三处的具体形状见 [PF-002](../PF-002-assets-settings-and-permissions/README.md)。

## rev 2 — 2026-09-17

**设置、权限、资产三者的关系与定义收紧。**

### 改了什么含义

| 方面 | rev 1 | rev 2 |
|---|---|---|
| 三者的地位 | 并列的三类范围化对象 | **只有资产是独立对象**；设置与权限是**资产的两种属性** |
| 「组织的设置」 | 隐含是一个对象 | **是视图**，即该身份持有的资产集合上的投影。最小单位是（身份层，具体资产，属性项）→ 值 |
| 资产的种类 | 七行，含模型档案、知识/文件、Service/Middleware 等 | **五类且穷尽**：skill、tool、plugin、agent definition、slash command |
| Tool | 「不自动成为独立顶层资产」 | **是资产**，因为本系统能做工具的动态组装 |
| 求值 | 资产、权限、设置三路并列求值 | **两轮**：先定哪个资产生效，再定它各项属性取什么值 |
| 作用域层数 | 五层，含账号级 | **四层**：出厂默认 < 组织级 < 租户级 < 会话级。账号只做标识、鉴权、聚合，**不持有任何范围化对象** |
| 账号的地位 | 隐含是作用域的一层 | **是身份概念，不是治理概念**。标识、鉴权、聚合全在身份范畴；治理发生在组织与租户。账号**有**求值——求出「这一个自然人」，但那是**恒等**的、不言自明的、不需要任何机制的求值；它没有治理意义上的求值，因此不占作用域里的一格 |
| context | 没有这个概念 | **两种且正交**：协作范围 context（组织与租户承载）、个人 context（账号承载）。四层作用域只是前者内部的层次。**注意与 Cordis 的 `Context` 同名不同义** |
| 设置的字段目录 | 列为非目标，归另一个 topic | **这样的目录不存在**——项是资产属性的投影 |

### 下游要注意的

- **不要为「组织设置」建一张独立的字段表。**它会与资产各自演化，最终对不上。
  视图是持有关系的函数，不需要维护。
- **两轮求值不能合并。**混了就会把「改一项设置」实现成「换一个资产」。
- **配值要校验持有。**一个层为它并不持有的资产配设置或权限，应当拒绝。
- **不要再有账号级的设置、权限或资产。**一个人的"个人的东西"放在
  **他个人组织的那个租户**里。放到账号上等于给它一个跨所有组织可见的范围，
  个人资产会跨组织泄漏。

### 修正的自我不一致

rev 1 把资产定义为「约束 agent 由什么组装而成」，却在种类表里列了
「知识、经验、报告、附件与文件」——这些不参与组装。rev 2 按本 topic 自己的
定义把它们移出资产，去向记在 §8。

详细形状见 [PF-002](../PF-002-assets-settings-and-permissions/README.md)。

## rev 1 — 2026-09-17

**首版。**建立身份与范围的完整模型。

### 这一版确定了什么

| 方面 | 结论 |
|---|---|
| 身份 | 账号、组织、租户、角色四种，各自的产生时机与稳定性见 [design.md §5](design.md#五模型) |
| 租户 | **(组织, 账号) 组合所确定的身份**，是数据归属与隔离的单位 |
| 角色 | 租户的**可变属性**，不进入身份 |
| 层次 | 出厂默认 < 账号级 < 组织级 < 租户级 < 会话级（rev 2 减为四层） |
| 合成 | 设置**覆盖**、权限**收窄**、资产**组合 + 同能力标识覆盖** |
| 来源 | **official 是最小必需**，位于出厂默认层，不需授权、不可禁用；customized 可替代实质相同的 official |
| 资产 | Agent Definition 是一类资产，一个组织或租户可同时拥有多个 |
| 退出 | **只影响被退出的那一个登录状态**，别的设备不受影响 |
| 角色 | 本版只有超管与普通成员；一个租户**只持一个角色** |
| 成本 | 使用成本**按租户归属、能出账单明细**；**不设**订阅、权益、预算与限额 |
| 注册 | 以**激活**为单一提交点；未激活的账号不能用于任何交互 |

### 下游要注意的两处

- **权限是收窄不是覆盖。**高层是不可突破的边界，低层只能在界内进一步收紧。
  按覆盖实现会形成提权路径——成员能在自己的租户级推翻组织设的约束。
- **归属挂在租户上，不挂在角色上。**成员角色变更之后，他此前创建的东西
  归属不变；变更只影响此后的准入判定。
- **official 可被替代，但不可被清空。**资产求值有下界：每个 official 能力标识
  在结果中必须有东西。把"禁用 official"实现成一项可配置的权限，是错的。

### 本版留下的缺口

- **未决项：无。**
- **待裁决：无。**
- 依据来源缺一处，见 [decisions.md §4](decisions.md#四已知的来源问题)。

## 怎么记下一版

改变含义就递增 rev 并在这里加一节。判断标准：
**读者需要据 rev 判断自己手上的理解是否还成立吗？**需要，就记。

每节至少说清三件事：改了什么含义、为什么、下游要复核什么。
