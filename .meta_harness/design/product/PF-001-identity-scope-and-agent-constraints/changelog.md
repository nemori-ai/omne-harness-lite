## rev 16 · 机器断电与操作系统崩溃：几处读起来没有例外的句子加上同一个限定 — 2026-09-23

**本版只有一条产品负责人的裁决：本 topic 加上与 [PF-017](../PF-017-governance-center-as-deployable-application/README.md) 同一个限定。**
没有新概念，没有改任何小节标题，已有规则一条没被推翻。**例外归 PF-017**
（[§6.7](../PF-017-governance-center-as-deployable-application/design.md#67-重启不让任何人退出登录)、[§6.8](../PF-017-governance-center-as-deployable-application/design.md#68-停机已确认的都在没确认的等于没发生)），
本 topic 只承认自己那几句受它约束，链接过去，不复述规则。

### 为什么

治理中心所用存储的持久性档位（[D-027](../../record/decisions/infrastructure-names-and-sqlite-durability/README.md)）意味着：
机器断电或操作系统崩溃时，崩溃前最后一段已经答复过「成功」的写可能丢失；系统进程自己崩掉不在此列。
产品负责人裁定把它写回产品正文（[PF-017 INT-016](../PF-017-governance-center-as-deployable-application/interviews/2026-09-23-rulings.md#int-016)），
[PF-017 rev 2](../PF-017-governance-center-as-deployable-application/changelog.md) 已写进它自己的 §6.7、§6.8、§6.10、§6.12。
PF-017 随之[登记了一条来源问题](../PF-017-governance-center-as-deployable-application/decisions.md#四已知的来源问题)：
本 topic [flows §3.2](flows.md#32-登录状态)「失效必须在重启之后依然成立……这是安全事故」与[非目标](design.md#非目标)里账号不会消失的说法，
都没有这条例外，只读本 topic 的人会以为它们没有例外。产品负责人的作答是「**PF-001 升 rev 加同一限定**」（[decisions §一](decisions.md#一拍板记录)）。

### 改了哪些句子

| 哪里 | 原来 | 现在 |
|---|---|---|
| [flows §3.2](flows.md#32-登录状态) | 「失效必须在重启之后依然成立……系统重启一次就又能用旧状态访问，这是安全事故。」到此为止 | 原句不动；补「系统自己崩掉（程序异常退出、被强行结束，机器照常开着）之后再起来，同样在这一条里」；加一段「**机器断电与操作系统崩溃是这一条的例外**」——刚退出或刚撤销的可能又有效、系统不知道丢了哪几件、运维者告诉用户再做一次、持有者在列表上再撤销，全部后果以 PF-017 §6.7 为准；再加一句「这不是这张表里的一条转移，『已失效不可回到有效』照样成立」 |
| [flows §三](flows.md#三状态流转) 开头 | 没有 | 一段说明：断电不是下面任何一张表里的一条转移，几处「不可逆」照样成立 |
| [design §4 登录状态](design.md#登录状态) | 「被撤销的那一个立即失效」之后没有任何限定 | 加一段：断电之后撤销可能要再做一次，**那个登录状态会重新出现在列表里**，持有者再撤销即可 |
| [design §2 非目标](design.md#非目标)「账号与组织的终止」 | 「……唯一的例外是一条从未激活的记录到期被清除……所以它不是一条终止路径」到此为止 | 原句不动；补「**机器断电或操作系统崩溃也不是一条终止路径**」：刚注册的账号、刚建的组织可能不在，是那一段没留下来；名字可以重新注册，组织可以重新建 |
| [design §2 非目标](design.md#非目标)「账号恢复……」 | 「账号不会消失，『恢复』没有对象」 | 「**已激活的账号没有消失路径**，『恢复』没有对象」 |
| [design §4 未激活的账号记录不会永久占着那个名字](design.md#未激活的账号记录不会永久占着那个名字) | 「已激活的账号本版不会消失，它的个人组织与租户也就不会」 | 「已激活的账号本版**没有消失路径**，它的个人组织与租户也就没有」 |
| [acceptance §二](acceptance.md#二绝不能发生的事) | 「退出登录后，重启系统又能用旧登录态访问」 | 同一行补「系统进程异常退出或被强行结束之后再起来，同样算」；「意味着什么」一格补「**机器断电或操作系统崩溃之后起来不在这一行**」 |
| [acceptance §三](acceptance.md#三判据)「退出的持久性」 | 「退出后重启系统，再用旧登录态访问，被拒绝」 | 加一支验法：**强行结束系统进程**（机器照常开着）再起来，同样被拒绝；断电的例外不在这里验 |

**后两处「不会消失 → 没有消失路径」不是改规则**：那两句要挡的是「有一条路能让已激活账号消失」，
断电不是这样一条路；收成这个说法，它们在断电例外之下仍然是真话。推理链见 [decisions §二](decisions.md#二pm-推导)。

**正文说「断电是这一条的例外」，不说「唯一的例外」**：从备份恢复会不会带回撤销，
是 [PF-017 §9](../PF-017-governance-center-as-deployable-application/design.md#九未决项) 指给本 topic 的另一问，本版不表态（[decisions §二](decisions.md#二pm-推导)）。

## rev 15 · 已解除的成员只给超级管理员看 — 2026-09-22

**本版只有一条产品负责人的裁决，只动 [flows §4](flows.md#四角色与操作) 那张角色矩阵里成员名单那一行。**
已有规则一条没被推翻，其余各页除 [acceptance](acceptance.md) 各补一条外一个字未改。

### 一行拆成两行

[rev 14](#rev-14--成员名单对本组织有效成员可见两类邀约的读面只归超管--2026-09-22) 定下「成员名单对本组织每一位有效成员可见」，
没有回答**已经解除了成员关系的那些要不要一起给**。产品负责人补齐了这一格：

| 角色矩阵那两行 | 超级管理员 | 普通成员 | 非成员 |
|---|---|---|---|
| 查看成员名单（本组织有哪些**有效成员**、各持什么角色） | 可 | **可** | 不可 |
| 查看**已解除的成员**（成员资格已失效的那些） | 可 | **不可** | 不可 |

表下随之改两处：**「看已解除的成员」并进「管理类动作只归超管」那一句**；
成员名单那一段续写**为什么共事这条理由到有效成员为止**——已解除的那个人分享不了资产、
请不动接手、批不了事，普通成员知道他曾经在过一件事也不多做成；而超管要移除、要再次邀请，
得先知道这个人此前在不在、怎么走的，**那是管理**。
**普通成员取到的名单只含有效成员**，不是把已解除的那些隐去几个字段。

[acceptance §一](acceptance.md#一可观察场景) 补一条可观察场景（成员被移出后普通成员再看名单，里面没有这个人；
同一时刻超管能一并看到），[§二](acceptance.md#二绝不能发生的事) 补一条「绝不能发生」
（普通成员从名单里读出这个组织解除过谁）。

### 下游要复核什么

- **[organization-governance 契约](../../spec/capabilities/organization-governance/v1/contract.md)**：
  ① [S-59 列出组织成员](../../spec/capabilities/organization-governance/v1/contract.md#s-59-列出组织成员)
  的过滤开关此前**两档共用一道授权**，并明写「若产品认为已解除的只该给超管看，那是一条新的产品规则」——
  **本版正是那条规则**。开关拆成两档分别授权：默认档（只要有效的）仍是该组织的有效成员、任一角色；
  「连无效的一起要」这一档**只给该组织的超级管理员**，普通成员请求该档以 `notAuthorized` 拒绝。
  **失败集合不变、不新增失败值**——`notAuthorized` 本来就在。
  ② 该条的证据义务（[三条读面的授权分档演练](../../spec/capabilities/organization-governance/verification.md#规范场景)）
  **要加一支**：普通成员请求「连无效的一起要」必须被拒。
- **任何据「S-59 的开关与授权无关」实现的读面**——本版之后那个开关**跨了一道授权分界**，
  不能再当成纯粹的取值过滤。
- **反过来，任何据此收紧默认档的做法**——默认档的授权本版**没有动**。
- **统一语言与领域对象**：本版**不新增也不改任何概念**，只在既有的
  [成员资格效力](../../ubiquitous_language/terms/subjects-and-ownership.md#ul-membership-standing--成员资格效力--membership-standing)
  上补了「无效的那一面谁看得见」。定义一个字没动；出处不指向 [flows §4](flows.md#四角色与操作) 的，
  复核后把 rev 改到 15 即可，指向 §4 的要逐条回读。

## rev 14 · 成员名单对本组织有效成员可见；两类邀约的读面只归超管 — 2026-09-22

**本版只有一条产品负责人的裁决，只动 [flows §4](flows.md#四角色与操作) 那张角色矩阵。**
已有规则一条没被推翻，其余各页一个字未改。

### 三行补进角色矩阵

产品负责人被问的是：**普通成员能不能看本组织的成员名单，以及两类邀约
（本组织发出的邀请与隶属请求、本组织收到的隶属请求）**。
[flows §4](flows.md#四角色与操作) 此前**没有这三行**——不是写了「不可」，是**一个字也没有**。
答复分两半：

| 新增的那一行 | 超级管理员 | 普通成员 | 非成员 |
|---|---|---|---|
| 查看本组织发出的邀约（邀请与隶属请求） | 可 | **不可** | 不可 |
| 查看本组织收到的隶属请求 | 可 | **不可** | 不可 |
| 查看成员名单（本组织有哪些成员、各持什么角色） | 可 | **可** | 不可 |

[acceptance §一](acceptance.md#一可观察场景) 补两条可观察场景（普通成员看得到名单、看不到那两类邀约），
[§二](acceptance.md#二绝不能发生的事) 补两条「绝不能发生」（名单只有超管看得到、名单里读得出别的组织）。

表下那段随之改两处：**两类邀约的读面归入「管理类动作只归超管」那一句**；
**成员名单单列一段，写明它是协作可见**——它对本组织每一位有效成员可见，
给的只有本组织这一层的成员与角色，**不带任何人在别的组织里的事实**，
也**不松动「读取成员的个人范围」那一行对谁都是「不可」**。

### 下游要复核什么

- **[organization-governance 契约](../../spec/capabilities/organization-governance/v1/contract.md)**：
  它登记的[缺口 G-11](../../spec/capabilities/organization-governance/v1/contract.md#十一已知缺口)
  问的正是这三行，**本版把它闭合**。
  ① [S-59 列出组织成员](../../spec/capabilities/organization-governance/v1/contract.md#s-59-列出组织成员)
  的授权前置**从超管放宽为「该组织的有效成员，任一角色」**——那一条此前是
  「产品没说的地方取了收紧的一档」，现在产品说了；
  ② [S-58 列出组织发出的邀请与隶属请求](../../spec/capabilities/organization-governance/v1/contract.md#s-58-列出组织发出的邀请与隶属请求)
  与 [S-60 列出组织收到的隶属请求](../../spec/capabilities/organization-governance/v1/contract.md#s-60-列出组织收到的隶属请求)
  **维持超管**，两条②上「待产品确认」的标注要去掉——**它们不再是待确认，是已定**。
  **三条的失败集合都不变**，放宽的只有 S-59 那一格授权。
- **任何据「名单是超管特权」实现的界面或授权判定**——普通成员看本组织成员是产品行为，不是放宽。
- **反过来，任何据「名单可见」推出「邀约也该可见」的做法**——两者本版分开定，不同档。
- **统一语言与领域对象**：本版**不新增也不改任何概念**，只在既有的[成员关系](../../domain_objects/objects.md)
  与[两类邀约](../../ubiquitous_language/terms/subjects-and-ownership.md#ul-offer--邀约--offer)上补了「谁看得见」。
  出处标 rev 13 的词条与对象条目，**定义一个字没动**，复核后把 rev 改到 14 即可；
  指向 [flows §4](flows.md#四角色与操作) 的那些要逐条回读。

## rev 13 · 管理动作只归超管；上级组织创建时为空；未激活记录清除连带个人空间 — 2026-09-22

**本版有两条产品负责人的裁决、三处校准。**已有规则一条没被推翻。

### 一、「管理资格」是笔误，本版 ＝ 超管

[flows §4](flows.md#四角色与操作) 角色矩阵里，普通成员「邀请新成员」那一格原写
「有条件：被授予管理资格时」——而 [design §4 角色](design.md#角色) 只定了
**超级管理员与普通成员两种**，**全链再没有第二处定义过「管理资格」这样东西**。
产品负责人的裁决是：**笔误，本版 ＝ 超管**。四处随之落定：

| 哪里 | 原来 | 现在 |
|---|---|---|
| [flows §4](flows.md#四角色与操作) 邀请新成员 × 普通成员 | 有条件：被授予管理资格时 | **不可** |
| [flows §1.5](flows.md#15-邀请与加入) 第 1 步触发者 | 有管理资格的成员 | **该组织的超级管理员** |
| [flows §3.3](flows.md#33-成员关系) 角色调整的前置条件 | 操作者有管理资格 | **操作者是该组织的超级管理员** |
| [design §6.4](design.md#64-隔离) | 组织管理资格不带来…… | **组织的超级管理员身份**不带来…… |

[flows §4](flows.md#四角色与操作) 表下补明**管理类动作本版一律只归超管**，
并点清普通成员那两行「有条件」讲的是**资产的使用与创作权限，不是管理权**——
那正是「管理资格」当初混进来的地方。

**将来「可授予的管理权限」是加法**，不触动本版任何一条，
[理由见 decisions](decisions.md#二pm-推导)。

### 二、上级组织「创建时可指定」删掉

[design §4 组织](design.md#组织) 属性表里「上级组织」的「何时确定」一格，
从「创建时可指定；此后可建立，也可解除」改为
「**创建时为空**；此后通过[隶属请求](design.md#隶属关系怎么建立与解除)建立，也可解除」。

**原来那一格与同一节自相矛盾**：[建立隶属要双方超管各做一次，单方面指定不允许](design.md#隶属关系怎么建立与解除)，
而「创建时由创建者一个人填上」正是那条明文排除的单方面指定。

### 三、三处校准（不新增规则，只把已有的意思写准）

- **未激活记录到期清除时，为它准备的个人组织与第一个租户随之消失**
  （[§4 未激活的账号记录不会永久占着那个名字](design.md#未激活的账号记录不会永久占着那个名字)、
  [flows §3.1](flows.md#31-账号)、[acceptance §一、§三](acceptance.md)）。
  [注册第 2 步](flows.md#11-注册)在激活**之前**就建好了个人组织与第一个租户，
  而 rev 12 只写了「记录被清除、标识释放」——**那两样留在哪里没有交代**。
  **未激活的账号不能用于任何交互**，所以它们从头到尾没有承载过任何东西，
  随记录一起消失**不留任何归属**。这也是**个人组织唯一的消失路径**，
  [§2 非目标](design.md#非目标)「账号与组织的终止」一行据此写明这个例外
  ——**它不是一条终止路径**，被清掉的三样都从未成为可用的东西。
- **「组织没有终结路径」这句话收窄为「团队组织」**（[decisions §二、§四](decisions.md#二pm-推导)）。
  个人组织现在有了那一条消失路径，但它**发不出邀请、也不参与隶属关系**，
  **没有任何邀约指向它**，所以[「指向的组织不存在了就自动过期」本版仍然没有触发源](decisions.md#二pm-推导)，
  [隶属请求宿主那个缺口也仍然不阻断任何东西](decisions.md#四已知的来源问题)。
- **[flows §2](flows.md#二分支与异常)「已过留存期限」那一行的措辞**：
  从「标识已释放，按新注册走」改为「**那条记录连同它的个人空间被清掉，标识释放，
  按新注册走（用户不需要等任何清扫）**」。产品语义不变，
  与 spec 侧「注册入口遇到已过期记录自行清除再新建」是同一句话。

### 下游要复核什么

- **[organization-governance 契约](../../spec/capabilities/organization-governance/v1/contract.md)**：
  ① [S-53 清除未激活账号的个人组织](../../spec/capabilities/organization-governance/v1/contract.md#s-53-清除未激活账号的个人组织)
  的**产品依据现在落在 rev 13 §4**——上面那句「个人组织与第一个租户随记录一起消失」
  就是它要兑现的那条，引用的 rev 要跟着改；
  ② 凡把**邀请、角色调整、隶属建立/解除**的授权前提写成「有管理资格的成员」
  或任何可授予的管理权限的，**一律收成超管**；
  ③ 组织创建那条链**不接受「上级组织」作为入参**——创建时它恒为空。
- **[account-registration 契约](../../spec/compositions/account-registration/v1/contract.md)**：
  **第二条动作链**（遇到已过期的未激活记录、自行清除再新建）现在有了完整的上游依据——
  要清的**不只是账号记录与标识占用**，还有为它建的**个人组织与第一个租户**；
  清完之后新注册拿到的是**全新的个人空间**。**用户不需要等任何后台清扫**，
  这一点与 [flows §2](flows.md#二分支与异常) 的新措辞一致。
- **领域对象条目**：
  [UL-organization](../../domain_objects/objects.md#ul-organization--组织) 的生灭
  ——「本版不要求解散」收窄为**团队组织**，个人组织补上那条唯一的消失路径；
  [UL-tenant](../../domain_objects/objects.md#ul-tenant--租户) 的生灭
  ——「本版无销毁路径」收窄为**已激活账号的租户**；
  [UL-account](../../domain_objects/objects.md#ul-account--账号) 到期那条出口补上连带的两样；
  [UL-invitation](../../domain_objects/objects.md#ul-invitation--邀请) 与
  [UL-affiliation-request](../../domain_objects/objects.md#ul-affiliation-request--隶属请求)
  里「本版无触发源」的**理由**要改成「没有任何邀约指向个人组织，团队组织无终结路径」。
- 统一语言：[UL-invitation](../../ubiquitous_language/terms/subjects-and-ownership.md#ul-invitation--邀请--invitation)
  的中英定义里「有管理资格的成员 / a member with management authority」改成**超级管理员**；
  [UL-account](../../ubiquitous_language/terms/subjects-and-ownership.md#ul-account--账号--account)
  注意②补上到期清除连带个人组织与第一个租户；
  [UL-parent-organization](../../ubiquitous_language/terms/subjects-and-ownership.md#ul-parent-organization--上级组织--parent-organization)
  确认它**创建时恒为空、只能由隶属请求填上**。

## rev 12 · 凭据本版不可更换；有效登录状态有了读面；未激活记录不再永久占名 — 2026-09-22

**本版有三条产品负责人的裁决、两处校准。**已有规则一条没被推翻。

### 一、凭据本版不提供任何写路径

[§2 非目标](design.md#非目标)里「账号恢复与凭据重置」一行扩为
「账号恢复，以及**凭据的一切写路径**——重置与已认证下的**主动更换**都算」；
[§4 账号](design.md#账号)属性表里「凭据」一格，「取值与约束」去掉「可更换」，
「何时确定」从「注册时，之后可改」改为「**注册时，本版不可改**」。

**变的是「主动更换」这一半。**此前非目标只排除了**重置**，而属性表明写「可更换」，
读者据此可以认为「已认证状态下改自己的凭据」是要做的——但那件事**既没有流程、
也没有操作、更没有验收**。现在与「[登录标识不可改](design.md#非目标)」「账号不终止」
同一口径：**身份一经建立就稳定在那里。**将来要开这个口子是**加法**。

[§5 模型](design.md#五模型)那句「『不变』说的是身份本身不会被换掉，不是属性一动不动」
原先举的例子是「账号的凭据可以更换」，**已换成激活状态**——凭据不再是那个例子。

### 二、有效登录状态有了读面：列得出，才撤销得了

[§4](design.md#登录状态) 新增「登录状态」一节，正文第一次在 design 里给它一个概念位置
（此前只在 [flows §3.2](flows.md#32-登录状态) 有状态机）。新增的产品规则是一条：

> **持本账号任一有效登录状态的人，可以列出本账号当前全部有效的登录状态，
> 每一个都带着它的签发时间。**

**撤销仍然逐个**，[flows §1.3](flows.md#13-退出) 增加「查看并撤销某一个登录状态」一段流程，
[flows §3.2](flows.md#32-登录状态) 补明「已失效的不在列表里」。

**为什么非有这条不可**：登录**不是幂等**的——多按一次、回执在网络上丢一次，
就多出一个有效的登录状态。而本版没有全设备撤销、此前也没有任何列表读面，
**那个多出来的登录状态，账号持有者既发现不了、也就撤销不了**。
**能撤销的前提是看得见。**

**[全设备撤销仍然不做](design.md#非目标)**，[理由见 decisions](decisions.md#二pm-推导)：
列表补上的是缺的那一半，逐个撤销本来就有——全设备撤销是省几下手，不是补一个洞。

### 三、未激活的账号记录有留存期限

[§4 账号](design.md#账号)新增「[未激活的账号记录不会永久占着那个名字](design.md#未激活的账号记录不会永久占着那个名字)」一节：

| | 定成什么 |
|---|---|
| 期限多长 | **按部署配置**，产品这一层不定数值 |
| 期限内再来 | 用**同一标识、同一凭据**重新发起注册，**认回的是那条还没激活的记录** |
| 到期之后 | 记录**被清除**，登录标识**随之释放**，任何人都可以拿它注册 |

[flows §1.1](flows.md#11-注册) 与 [§3.1](flows.md#31-账号) 补上规则与收场，
账号状态机因此多一条出口「**未激活 → 不存在**」；[flows §2](flows.md#二分支与异常)
补三行注册分支（凭据相同认回、凭据不同仍报"已被占用"、过期后按新注册走）。

**它解决的是：**[注册第 1 步](flows.md#11-注册)一建立账号那个登录标识就被占住，
发起者若再也不回来，**这个名字被一条永远走不到激活的记录永久占据**——
而他本人什么也没得到，别人也再用不了这个名字。

**「未激活 → 不存在」不是账号终止**：被清掉的是一条从未成为可用账号的记录，
[本版依然没有任何路径能让一个已激活的账号消失](design.md#非目标)。

**期限是部署配置，不是[邀约时长](design.md#两种邀约都会过期)那种由发起者填的参数。**
差别在有没有一个能填这一格的人：邀约有发起者，而一条未激活记录的「发起者」
恰恰是那个还没回来的人。

### 四、两处校准（不新增规则，只把已有的意思写准）

- **「有共同上级」的判据**（[§4 组织](design.md#组织)）：从「两个组织的上级链上有共同的组织」
  改为「**把各自算进自己的上级链之后，两条链有交集，也就是同一棵隶属树（根相同）**」。
  上级链本身不含自己，照原来的字面读法，**一个组织与它自己的上级不算有共同上级**——
  而 [PF-003 §5.2](../PF-003-asset-transfer-and-sharing/design.md#52-边界是那棵隶属树不是单个组织)
  明写那棵树就是边界，团队与它所属的公司分明在同一棵树上。**PF-003 一直就是这个意思**，
  本版改的是这里的字面判据。个人组织那条推论不受影响：把自己算进来，它那条链上也只有它一个。
- **注册回执丢失的收场**（[flows §1.1](flows.md#11-注册)）：激活已提交、成功回执没送达时，
  **账号已经可用**；再去注册会得到「这个名字已经有人用了」，**那不是出了错**，
  持凭据者**直接登录即可**。这条由「提交点在第 3 步」直接推出，不是新规则。

### 下游要复核什么

- **[account-identity 契约](../../spec/capabilities/account-identity/v1/contract.md)**：
  ① 任何为**更换凭据**预备的写操作或入口——本版没有这个动作；
  ② **登录状态**那一组操作要多一个**列出本账号全部有效登录状态（含签发时间）**的读操作，
  授权前提是「持本账号任一有效登录状态」，**不是**超管、也不是别的账号；
  ③ **注册**那条链要吃下「未激活记录有留存期限」：期限内同标识同凭据**认回同一条**、
  到期**清除记录并释放登录标识**，账号状态机因此多一条「未激活 → 不存在」的出口。
  **全设备撤销仍然不做**，别顺手把它一起实现了。
- **[account-registration 契约](../../spec/compositions/account-registration/v1/contract.md)**：
  注册链的「用同一标识重试」现在有了精确含义——**认回的是第 1 步留下的那条记录**，
  且这件事**有时限**；以及「激活已提交、回执未达」的收场是**账号已可用、直接登录**，
  不是一条需要补偿的失败路径。
  **它登记的[缺口 G-2](../../spec/compositions/account-registration/v1/contract.md#九已知缺口)
  （「未激活记录的留存没有期限，标识因此被长期占用……没有说另一个人能不能用这个名字」）
  上游现在有答案了**：期限按部署配置，到期清除并释放标识，**到期之后另一个人可以用**。
  按那条缺口自己写的闭合条件，它是**一条新的产品规则**，契约要随之发布新版本。
- **任何按「两条不含自己的上级链求交」实现 `shareAncestor` 的做法**——
  祖先与后代那一对会被判成假。判据是**把各自算进来再求交**。
  **[organization-governance 契约登记的缺口 G-5](../../spec/capabilities/organization-governance/v1/contract.md#十一已知缺口)
  （「两种读法在祖先—后代那一对上给不同答案」）上游现在有答案了**：取把自己算进来的那一种。
- **任何把留存期限做成[作用域配值](design.md#61-层次)或由注册发起者填参**的做法——它是部署配置。
- 统一语言：[UL-login-identifier](../../ubiquitous_language/terms/subjects-and-ownership.md#ul-login-identifier--登录标识--login-identifier)
  里「凭据可更换」两处要改；
  [UL-login-state](../../ubiquitous_language/terms/subjects-and-ownership.md#ul-login-state--登录状态--login-state)
  补「可被同账号其他有效登录状态列出」；
  [UL-account](../../ubiquitous_language/terms/subjects-and-ownership.md#ul-account--账号--account)
  补未激活记录的留存期限；
  [UL-ancestor-chain](../../ubiquitous_language/terms/subjects-and-ownership.md#ul-ancestor-chain--上级链--ancestor-chain)
  的「有共同上级」判据按新写法改。

## rev 11 · 登录标识本版不可改；邀约的时长由发起者发出时指定 — 2026-09-22

**本版有两条产品负责人的裁决、两处指路校准。**已有规则一条没被推翻。

### 一、登录标识本版不提供修改

注册时定下的那个名字，**本版不提供改**，已列入[非目标](design.md#非目标)；
[§4 账号](design.md#账号)的属性表里「登录标识」一格补上「本版不可改」，
「何时确定」从「注册时」改为「注册时，此后不变」。

口径与本 topic 已有的「账号不终止、凭据不重置」是同一条：
**身份一经建立就稳定在那里，围绕它的变更路径整体延后。**
将来要开这个口子是**加法**——登录标识的两条性质（部署内唯一、只指认不证明持有）都不动。

### 二、邀约的过期时长：每类各有默认，发起者发出时可以指定

[§4 两种邀约都会过期](design.md#两种邀约都会过期)的「过期时长」一格，
从「**有默认值，也可配**」改为「**每类邀约各有默认值（按部署配置），发出时发起者可以指定这一份的时长**」。
[flows §1.5](flows.md#15-邀请与加入)、[§1.7](flows.md#17-建立与解除组织隶属)
的发出步骤补上「可以指定这一份的有效时长」，[acceptance §一](acceptance.md) 增一条可观察场景。

**变的是谁来定这一份的时长。**此前只说「有默认、可配」，读者无从知道这个「可配」
配在哪一层、由谁配；现在明确了：**它是发出这份邀约时的一个参数**，跟着这份数据走，
**不进[四层作用域](design.md#61-层次)**。发起者不指定的，按该类的默认值。

**四类邀约的口径一致**：本 topic 管邀请与隶属请求，
[PF-003 §6.14](../PF-003-asset-transfer-and-sharing/design.md#614-待确认的复制通知与分享邀请会过期) 同版按同一改法管另外两样。

### 三、两处指路校准

- [§6.1](design.md#61-层次) 那张四层表：「会话级 → 本次协作」补括注「**也就是那个会话**」，
  表后补一句指路——**每一格由哪重身份充当**，归
  [UL-scope-layer-identity](../../ubiquitous_language/terms/scope-and-resolution.md#ul-scope-layer-identity--作用域层身份--scope-layer-identity)。
- [§6.4](design.md#64-隔离)「目标范围不可用或成员失权时明确失败」一条，补引
  [UL-membership-standing](../../ubiquitous_language/terms/subjects-and-ownership.md#ul-membership-standing--成员资格效力--membership-standing)
  并写明：「不可用」是**判不出来**，「失权」是**判出来了、答案是无效**；**两者收场相同，但不是同一件事**。

两处都只是把词条已经写明的分界补进正文指路，**规则本身没有变**。

### 下游要复核什么

- 任何**为登录标识预备修改路径**的做法——本版没有这个动作。
- 任何**把邀约时长实现成一项作用域配置、需要跨层合成**的做法——它是发出时的参数，
  只对这一份成立，没有第二个人跟发起者争这一格。
- 任何**四类邀约共用一个默认时长**的做法——裁决明写「四类各有各的默认值」。
- 统一语言：[UL-login-identifier](../../ubiquitous_language/terms/subjects-and-ownership.md#ul-login-identifier--登录标识--login-identifier) 补「本版不可改」；

## rev 10 · 并发移除超管有了收场；当前租户身份在创建那一刻被捕获 — 2026-09-22

**本版有两条新规则、九条补来路、一句指路校准。**规则一条没被推翻。

### 一、并发移除或降级超管的收场

正文此前只给**单次动作**的前置条件：两位超管在不同地方同时移除或降级对方，
两次各自看都满足前置，合起来却把超管清空了。**本版把同时发生时的收场写进正文。**

| 加了什么 | 落在哪 |
|---|---|
| **先成的一方成功，后成的一方被拒**，后者看到的提示与单次被拒时**完全相同** | [flows §2](flows.md#二分支与异常)、[flows §3.3](flows.md#33-成员关系) |
| 「至少一位有效超管」是**任何时刻都成立的事实**，不是每次动作各自检查一遍的前置条件；**这句话在单机与分布式下是同一句话** | [flows §3.3](flows.md#33-成员关系) |
| 可观察场景与判据各补并发那一半 | [acceptance §一](acceptance.md#一可观察场景)、[§二](acceptance.md#二绝不能发生的事)、[§三](acceptance.md#三判据) |

产品负责人的原话是从存储视角给的（独立的一张表、用锁保护至少一个）；
**产品正文不写「锁」「表」**，翻成产品语言的那一步记在
[decisions 第二节](decisions.md#二pm-推导)。

### 二、当前租户身份是创建那一刻捕获的环境值

新立概念 **[当前租户身份](design.md#当前租户身份)**——一个账号此刻以哪一个租户身份行事，
**它是登录状态上的一项选择**。

| 加了什么 | 落在哪 |
|---|---|
| **切换当前组织只影响此后新建的东西** | [§4 当前租户身份](design.md#当前租户身份)、[flows §1.8](flows.md#18-切换当前组织) |
| **任何在某个租户身份下创建的对象持有创建那一刻的租户身份**，此后一切以它计，不随账号切换而变，直到那个租户身份本身失效 | 同上 |
| **这项选择随登录状态走**：登录后初始为个人组织那个租户，切换就是改这项选择 | [§4 当前租户身份](design.md#当前租户身份) |
| 场景、「绝不能发生」与判据各补一条：切换之后先前建的会话仍按旧租户算 | [acceptance §一](acceptance.md#一可观察场景)、[§二](acceptance.md#二绝不能发生的事)、[§三](acceptance.md#三判据) |

## rev 9 · 退出再加入是同一个租户；隶属请求独立成对象 — 2026-09-22

### 一、退出之后再加入，回来的是同一个租户

裁决原话：「账号退出组织之后再次被邀请加入，是同一个租户；租户级私有部分（自定义件、配值）原样回来。」

| 加了什么 | 落在哪 |
|---|---|
| **租户身份 ＝ (组织, 账号) 是定义，不因成员关系断续而变**；再次加入得到的仍是同一个租户，不是一个新身份 | [§4 退出之后再加入，回来的是同一个租户](design.md#退出之后再加入回来的是同一个租户) |

### 二、隶属请求是独立于邀请的另一种对象

裁决原话：「组织之间『建立隶属』用的那份请求，与『加入组织的邀请』是完全独立的两种对象，

| 加了什么 | 落在哪 |
|---|---|

**过期规则、双方各做一次动作、解除单方面即可——这些一条都没改**，改的是「那份请求是什么东西」。
rev 8 的正文只说两者「同一个形状，不另造一套」，**那句话讲的是交互形状，

## rev 7 — 2026-09-19

**资产从七类变八类：补入 Loop Extension。**

### 为什么这一条值得推翻那句话

> **组织超管在组织层配一份，租户在自己那层覆盖**，走的就是本 topic 已有的层级求值。
> **另建一套，就要再写一遍持有、授权、求值、转移、分享**——
> 那正是「同一概念只有一个权威定义」要避免的事。

| **rev 7** | 再加**推进时在哪些位置插手**（Loop Extension） |

**与 rev 6 那次同一种性质**，一并如实记下，不假装定义没动过。

  [PF-005](../PF-005-execution-environments-and-sandboxes/README.md) 的相关引用。
- **MCP 带来的动作不是独立资产**——实现时不要为每个 MCP 工具登记一份资产，
  那会让资产身份随外部服务端的版本漂移。
- 两类的**形状、自带属性与组合关系**归 PF-002，本 topic 只定名字、含义与管理边界。

## rev 5 — 2026-09-17

**组织多一个属性「上级组织」，并补齐租户范围创作的归属。**

| | rev 4 | rev 5 |
|---|---|---|
| 组织之间的关系 | 没有。组织彼此独立 | 组织有**至多一个上级组织**，用来表达「团队属于公司」「公司是另一家的子公司」 |
| 隶属怎么建立 | — | **两边的超级管理员各做一次动作**，一方发起一方接受。解除则任一方单方面即可 |
| 租户范围创作归谁 | §6.7 的归属表只列了「组织范围创作」与「个人组织里创作」，**漏了租户范围** | 补上一行：**在自己的租户范围创作，所有者是该租户** |

改动的起因是 [PF-003](../PF-003-asset-transfer-and-sharing/README.md) 需要回答
「哪些组织之间可以流动资产」与「哪些资产是这个人的、哪些是组织的」。
两个答案都属于身份与组织模型，归本 topic，不在 PF-003 里另立一份。

### 下游要注意的四处

- **这是一个属性，不是一套新机制。**隶属链由「上级组织」自然长出，
  不要为它建独立的组织树对象或关系表。
- **至多一个上级。**一个组织有两个母公司，本版不表达。
  真要做需要的是关系表而不是属性，那时再改。
- **上级组织不进四层作用域。**子组织**不**自动继承上级的设置、权限与资产。
  按隶属链继承会让作用域层数随组织结构变化，还把「隶属」悄悄变成「被管辖」。
- **租户级资产的所有者是那个租户，不是组织。**由此得到一条不可逆：
  从租户范围提升到组织范围是一次交付，所有权随之易手，**不能退回**。
- **隶属关系不能单方面建立。**允许单方面指定下级，等于给一个人开了条边界后门。
  已经存在的两个组织（包括由不同账号创建的）之间可以建立，否则并购与重组无从表达。

## rev 4 — 2026-09-17

**资产作者的标识身份定为租户。**

| | rev 3 | rev 4 |
|---|---|---|
| 作者用什么身份 | 只说了「实际作者与定义所有者分别记录」，没说各用什么身份 | **作者是租户 (组织, 账号)**——正好表达「那个组织里的谁」 |

### 下游要注意的

- **作者记录不随角色变动而变**（角色不进租户身份），也**不随成员关系解除而失效**
  （它记的是当时是谁做的，不是现在谁还在）。
- **所有者与作者分开记**：在组织范围创作的，所有者是**组织**，作者是**那个租户**。
  成员退出时两者去向不同——资产留在组织，作者记录照旧。
- **agent 产出的作者仍是它运行所在的租户**，但要标明是 agent 产出，否则审计答不出
  「这是人写的还是 agent 写的」。
- **official 资产没有作者租户**，所有者与作者都是平台。实现不要为它找一个不存在的租户。

## rev 3 — 2026-09-17

**默认与强制用同一个机制表达。**

每一层对一个东西只能做两件事：给一个值，以及声明它不可再被下层覆盖
（`immutable`）。不加就是**默认**，加了就是**强制**。

| | rev 2 | rev 3 |
|---|---|---|
| 「组织可强制、个人不可改」 | 把那类字段**声明为收窄语义** | 给值时加 **immutable** |
| 适用范围 | 只对权限说得通 | 设置、权限、资产替换**三处通用** |

**为什么换**：rev 2 的解法对权限成立（收窄到单元素），对设置不成立——
设置的取值域通常是开放的（比如模型名），谈不上收窄成子集。
immutable 把「默认 / 强制」的区别落在**同一个字段的一个标记**上，
而不是落在**两种不同的合成语义**上。

对权限而言 `immutable(v)` 就是收窄到 `{v}`，是收窄的特例，两者不冲突。

三处的具体形状见 [PF-002](../PF-002-assets-settings-and-permissions/README.md)。

## rev 2 — 2026-09-17

**设置、权限、资产三者的关系与定义收紧。**

### 改了什么含义

| 方面 | rev 1 | rev 2 |
|---|---|---|
| 三者的地位 | 并列的三类范围化对象 | **只有资产是独立对象**；设置与权限是**资产的两种属性** |
| 「组织的设置」 | 隐含是一个对象 | **是视图**，即该身份持有的资产集合上的投影。最小单位是（身份层，具体资产，属性项）→ 值 |
| 资产的种类 | 七行，含模型档案、知识/文件、Service/Middleware 等 | **五类且穷尽**：skill、tool、plugin、agent definition、slash command |
| Tool | 「不自动成为独立顶层资产」 | **是资产**，因为本系统能做工具的动态组装 |
| 求值 | 资产、权限、设置三路并列求值 | **两轮**：先定哪个资产生效，再定它各项属性取什么值 |
| 作用域层数 | 五层，含账号级 | **四层**：出厂默认 < 组织级 < 租户级 < 会话级。账号只做标识、鉴权、聚合，**不持有任何范围化对象** |
| 账号的地位 | 隐含是作用域的一层 | **是身份概念，不是治理概念**。标识、鉴权、聚合全在身份范畴；治理发生在组织与租户。账号**有**求值——求出「这一个自然人」，但那是**恒等**的、不言自明的、不需要任何机制的求值；它没有治理意义上的求值，因此不占作用域里的一格 |
| context | 没有这个概念 | **两种且正交**：协作范围 context（组织与租户承载）、个人 context（账号承载）。四层作用域只是前者内部的层次。**注意与 Cordis 的 `Context` 同名不同义** |
| 设置的字段目录 | 列为非目标，归另一个 topic | **这样的目录不存在**——项是资产属性的投影 |

### 下游要注意的

- **不要为「组织设置」建一张独立的字段表。**它会与资产各自演化，最终对不上。
  视图是持有关系的函数，不需要维护。
- **两轮求值不能合并。**混了就会把「改一项设置」实现成「换一个资产」。
- **配值要校验持有。**一个层为它并不持有的资产配设置或权限，应当拒绝。
- **不要再有账号级的设置、权限或资产。**一个人的"个人的东西"放在
  **他个人组织的那个租户**里。放到账号上等于给它一个跨所有组织可见的范围，
  个人资产会跨组织泄漏。

### 修正的自我不一致

rev 1 把资产定义为「约束 agent 由什么组装而成」，却在种类表里列了
「知识、经验、报告、附件与文件」——这些不参与组装。rev 2 按本 topic 自己的
定义把它们移出资产，去向记在 §8。

详细形状见 [PF-002](../PF-002-assets-settings-and-permissions/README.md)。

## rev 1 — 2026-09-17

**首版。**建立身份与范围的完整模型。

### 这一版确定了什么

| 方面 | 结论 |
|---|---|
| 身份 | 账号、组织、租户、角色四种，各自的产生时机与稳定性见 [design.md §5](design.md#五模型) |
| 租户 | **(组织, 账号) 组合所确定的身份**，是数据归属与隔离的单位 |
| 角色 | 租户的**可变属性**，不进入身份 |
| 层次 | 出厂默认 < 账号级 < 组织级 < 租户级 < 会话级（rev 2 减为四层） |
| 合成 | 设置**覆盖**、权限**收窄**、资产**组合 + 同能力标识覆盖** |
| 来源 | **official 是最小必需**，位于出厂默认层，不需授权、不可禁用；customized 可替代实质相同的 official |
| 资产 | Agent Definition 是一类资产，一个组织或租户可同时拥有多个 |
| 退出 | **只影响被退出的那一个登录状态**，别的设备不受影响 |
| 角色 | 本版只有超管与普通成员；一个租户**只持一个角色** |
| 成本 | 使用成本**按租户归属、能出账单明细**；**不设**订阅、权益、预算与限额 |
| 注册 | 以**激活**为单一提交点；未激活的账号不能用于任何交互 |

### 下游要注意的两处

- **权限是收窄不是覆盖。**高层是不可突破的边界，低层只能在界内进一步收紧。
  按覆盖实现会形成提权路径——成员能在自己的租户级推翻组织设的约束。
- **归属挂在租户上，不挂在角色上。**成员角色变更之后，他此前创建的东西
  归属不变；变更只影响此后的准入判定。
- **official 可被替代，但不可被清空。**资产求值有下界：每个 official 能力标识
  在结果中必须有东西。把"禁用 official"实现成一项可配置的权限，是错的。

### 本版留下的缺口

- **未决项：无。**
- **待裁决：无。**
- 依据来源缺一处，见 [decisions.md §4](decisions.md#四已知的来源问题)。

被排除的内容在 [design.md §2 非目标](design.md#非目标)，那是**边界**——
发现它们缺失不算缺陷。下游遇到本文档没回答的问题，应当停下来问，
而不是挑一个看起来合理的实现。
