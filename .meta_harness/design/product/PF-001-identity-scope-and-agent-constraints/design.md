# PF-001：身份、范围与对 Agent 的约束

- 修订：**rev 18**，2026-09-24 · [变更历史](changelog.md)
- 状态：rev 16 已定稿；**rev 17 待产品负责人确认**；**无未决项**

## 一、背景与问题

我们的系统服务于组织和个人。同一个人，在自己的空间里和在公司里，与 agent 协作时
应当是不一样的：能用的技能不同、能做的事不同、做事的方式也不同。

但「不一样」具体不一样在哪、由什么决定、冲突时听谁的，此前没有一处说清楚。
后果是三件事各说各话：

- **设置**、**权限**、**资产**三者都有「组织的」和「个人的」之分，
  但三者的层次、覆盖规则各自为政，同一个字段在三处可能得出不同结果而无人能解释。
- 「租户」一词被同时用来指组织、指成员关系、指数据归属单位，同名不同义。
- 组织怎么产生、人怎么加入、谁能管什么——这些没有任何一处拥有，
  于是每次讨论到就重新发明一遍。

这一块不定清楚，agent 在组织里该听谁的、能碰什么，就永远是含糊的。

## 二、目标与非目标

### 目标

1. 把**账号、组织、租户、角色**四种身份一一定义清楚，说明各自何时产生、何时变化。
2. 定义身份如何**约束 agent 的组装与行动**——这是本 topic 存在的理由。
3. 给出**设置、权限、资产**三类对象的层次与合成规则，使同一字段在任何情形下
   有唯一且可解释的结果。
4. 说清楚组织怎么产生、人怎么加入、谁能管什么。

### 非目标

| 不做什么 | 为什么 |
|---|---|
| 核验现实世界的人 | 产品不做实名、不做账号去重、不做跨账号关联图。同一个人持有两个账号，对系统而言就是两个互不相干的身份 |
| 资产的组合形状与求值步骤 | 有哪几类资产、谁能组合谁、组装分几步，归 [PF-002](../PF-002-assets-settings-and-permissions/README.md)。本 topic 只定层次与合成语义 |
| **订阅体系、权益与预算限额机制** | 本阶段**不建立**。不设额度、不设预算、不做超限拦截。与之相对，租户的**使用成本统计与账单明细**是要的，见 §6.4 |
| **「流程规范」作为第四个约束方面** | 它与设置、权限、资产**不能正交组合**——一条「删文件前先问」既可表述为权限，又可表述为设置。四维模型里它会有两个家，而同一条规矩有两个家等于没有家 |
| 技能与工具的运行时发现与装载 | 本 topic 只规定它们属于资产、按什么规则合成，装载机制另有归属 |
| **操作系统层面怎样拦住越权的文件读写** | 本 topic 定的是**谁有资格**（§6.5）；落地时靠什么机制真的拦住，归[执行环境](../PF-005-execution-environments-and-sandboxes/README.md)，不归身份模型 |
| 账号与组织的终止 | 本版不要求永久关闭**已激活**的账号，也不要求解散组织。身份的消亡路径整体延后。**唯一的例外是[一条从未激活的记录到期被清除](#未激活的账号记录不会永久占着那个名字)**——连同为它建的个人组织与第一个租户，而那三样**从未承载任何东西**，所以它不是一条终止路径。**机器断电或操作系统崩溃也不是一条终止路径**：断电前不久刚注册成功的账号、刚建的组织可能不在了——不是它们被终止了，是系统退回到了断电前不久的某一刻，最后那一段没留下来；名字可以重新注册，组织可以重新建。这条例外的范围与收场归 [PF-017 §6.8](../PF-017-governance-center-as-deployable-application/design.md#68-停机已确认的都在没确认的等于没发生) |
| 全设备退出 | 退出只影响被退出的那一个登录状态。一处退出使全部设备失效，本版**不做** |
| 账号恢复，以及**凭据的一切写路径**——重置与已认证下的**主动更换**都算 | 已激活的账号没有消失路径，「恢复」没有对象；忘记凭据怎么办属认证提供者的能力。**主动更换同样不做**：本版没有任何改凭据的动作，注册时定下的那个凭据就一直是它。与本表里「账号不终止」「登录标识不可改」两条同一口径——身份一经建立就稳定在那里，围绕它的变更路径整体延后。将来要开这个口子是**加法** |
| **登录标识的修改** | 注册时定下的那个名字，本版**不提供改**。与「账号不终止、凭据不重置」同一口径：身份一经建立就稳定在那里，围绕它的变更路径整体延后。将来要开这个口子是**加法**——它不触动登录标识的两条性质（[部署内唯一、只指认不证明持有](#账号)） |
| 自助注册的限流与滥用处理 | 部署运维关注点，不改变身份模型的任何形状 |
| 资产怎样在组织之间**主动**流动 | 本 topic 只确认**不自动流入**，并定义组织的[上级组织](#组织)属性。资产复制与分享两个动作归 [PF-003](../PF-003-asset-transfer-and-sharing/README.md) |
| 认证提供者的选型 | 用什么方式验证凭据是技术选择，不是产品设计 |
| 精确的角色与动作矩阵 | 超级管理员与普通成员的边界本版已定；中间角色留待实际需要时再设计 |

## 三、用户与场景

| 使用者 | 什么情况下接触这块 | 他关心什么 |
|---|---|---|
| 个人用户 | 注册之后在自己的空间里用 agent | 我的东西是我的；换台设备还是我的 |
| 组织成员 | 在公司的组织里与 agent 协作 | 我在这里能用什么、能做什么；我的私人东西不会被公司看到 |
| 组织超级管理员 | 管理组织的配置、成员与资产 | 我定的规矩成员能不能绕过去；我管得到组织，但管不到成员的私人空间 |
| **资产的作者** | 在某个范围里创作、修订、发布资产 | 我做的东西归谁？我换岗或离开这个组织之后，署名还在不在 |
| **agent** | 每次在某个范围下运行 | 我现在由什么组装而成、能做什么、该以什么方式做 |

**agent 是这块设计的直接消费者**，而不只是被管理的对象。
它每次运行都要回答「我现在是在谁的什么范围里、能用什么」。

## 四、概念定义

### 账号

一个自然人在本系统中的产品身份。

**账号是身份概念，不是治理概念。**它回答「你是谁」，
不回答「你能用什么、能做什么、怎么做」——后三者归组织与租户（见 §6.1）。

**账号也求值，只是它的求值是恒等的**：给一个账号，求出**这一个自然人**。
这个过程**不需要任何机制**——没有层、没有合成、没有可配置项，因为它不言自明：
账号就是那个人。

| 概念 | 求值出什么 | 怎么求 |
|---|---|---|
| **账号** | 哪一个自然人 | **恒等**，不言自明，无需机制 |
| 组织与租户 | 有哪些资产可用、能做什么、怎么做 | 沿[四层](#61-层次)合成，要真的算 |

这个区分要紧：把账号当成治理对象，就会去问「账号这一层配了什么」——
而它的求值**不接受任何配置**，它只是把身份还原成那个人。

账号只承担**三个作用**：

| 作用 | 含义 |
|---|---|
| **标识** | 指认这是哪一个自然人 |
| **鉴权** | 证明来者确实持有这个身份 |
| **聚合** | 把同一个自然人在不同组织内的存在汇到一处，供他查看与切换 |

**账号不持有设置、权限或资产。**这三样都归租户与组织，见 §6.1。
"聚合"是一个**视图**功能——它让人看见自己有哪些租户，不给他任何跨组织的东西。

账号另外承载**个人 context**（界面语言、时区一类属于这个人本身的偏好）——
那不是范围化对象，在另一个轴上，见 §4「两种 context」。

- 账号**先于任何组织存在**，不隶属于任何组织。
- 账号是登录的主体：登录发生在任何组织范围建立之前。
- 一个现实中的人可以持有多个账号。系统**不核验、不关联、也不记录**两个账号是否属于同一人；
  现实持有人相同**不构成**任何跨账号的权限依据。

| 属性 | 业务含义 | 取值与约束 | 何时确定 |
|---|---|---|---|
| 登录标识 | 用来指认这个账号的对外名字 | **在整个部署内唯一**，理由见取舍表第一行。**本版不可改**，见[非目标](#非目标) | 注册时，此后不变 |
| 凭据 | 证明持有这个账号的东西 | 不以可读形式保存。**本版没有任何改它的动作**——重置与主动更换都见[非目标](#非目标) | **注册时，本版不可改** |
| 激活状态 | 这个账号是否可用 | 未激活的账号不能用于任何交互；**未激活的记录还有[留存期限](#未激活的账号记录不会永久占着那个名字)** | 注册流程的最后一步 |

#### 未激活的账号记录不会永久占着那个名字

[注册第 1 步](flows.md#11-注册)一建立账号，那个[登录标识](#账号)就被占住了。
发起者若再也不回来，这个名字会被一条永远走不到激活的记录**永久占据**——
而他本人什么也没得到，别人也再用不了这个名字。

**所以未激活的账号记录有一个留存期限。**

| | 怎么定 |
|---|---|
| **期限多长** | **按部署配置**，具体数值不在产品这一层定 |
| **期限内再来** | 用**同一标识、同一凭据**重新发起注册，**继续的是那条还没激活的记录**，不是新建一个：走完剩下的步骤，激活的就是它 |
| **到期之后** | 那条记录**被清除**，登录标识**随之释放**，任何人都可以拿它注册 |

**到期清除的不只是那条记录。**[注册第 2 步](flows.md#11-注册)已经为它建起了
[个人组织](#个人组织)和[第一个租户](#租户)，**这两样随那条记录一起消失**。
**未激活的账号不能用于任何交互**，所以那个个人空间从头到尾没有承载过任何东西——
没有创作过的资产、没有加入过的持有、没有配过的值。**清掉它不留下任何归属，也没有任何人因此失去什么**。

**这也是个人组织唯一的消失路径。**[已激活的账号本版没有消失路径](#非目标)，
它的个人组织与租户也就没有；能被清掉的只有那条**从未成为可用账号**的记录连带的那一份。

**它是部署配置，不是[作用域](#61-层次)里的一格，也不像[邀约时长](#两种邀约都会过期)那样由发起者填。**
邀约有一个发起者——他最清楚这一份急不急，所以那一格留给他；
**而一条未激活的记录没有这样一个人**：发起它的那个人恰恰是还没回来的那个，
没有谁站在这里可以为它指定一个窗口。**留多久是这套部署愿意为一个半途而废的注册
扣住多久名字，那是部署的事。**

**期限内认回同一条记录，是为了让「中途失败可以用同一个标识重试」真的成立**
（[flows §2](flows.md#二分支与异常)）：若每次重来都新建一条，第二次就会撞上
「这个名字已经有人用了」——而那个占着名字的人正是他自己。

### 登录状态

**一次通过鉴权的登录。**此后的交互以这个账号的身份进行。
每次登录产生**新的一个**，[各自可被单独撤销](flows.md#32-登录状态)；
它怎么产生、怎么失效，在 [flows §3.2](flows.md#32-登录状态)。

**一个账号可以同时有多个有效的登录状态**——不同设备、不同浏览器各是一个。
[退出只让被退出的那一个失效](#非目标)，别处不受影响。

**持有本账号任一有效登录状态的人，可以列出本账号当前全部有效的登录状态，
每一个都带着它的签发时间。**

**撤销仍然是逐个的**：在这张列表上可以撤销其中任意一个，
[被撤销的那一个立即失效，其余不受影响](flows.md#32-登录状态)。

**为什么必须有这张列表**：登录不是幂等的——同一个人多按一次、
回执在网络上丢一次，就多出一个有效的登录状态，而他自己并不知道。
没有这张列表，那个多出来的登录状态**他既发现不了，也就撤销不了**，
只能一直有效到不知什么时候。**能撤销，前提是看得见。**

**机器断电或操作系统崩溃之后，撤销可能要再做一次。**断电前最后一段做的退出与撤销可能没留下来，
被撤销的那一个又有效了（[flows §3.2](flows.md#32-登录状态)；这条例外的范围与收场归
[PF-017 §6.7](../PF-017-governance-center-as-deployable-application/design.md#67-重启不让任何人退出登录)）。
**它会重新出现在这张列表里**，持有者再撤销一次即可——看得见，才撤销得了，这里同样成立。

> **本版不做[全设备撤销](#非目标)。**有了这张列表，逐个撤销已经能把账号收回来；
> 「一次踢掉全部」是另一个动作，本版不设。

### 组织

一个协作范围。它可以容纳多个账号作为成员，并拥有自己的设置、权限与资产。

- 组织由某个账号创建，**创建者自动成为该组织的超级管理员**。
- 一个账号可以创建一个或多个组织。
- 组织可以邀请其他账号加入（个人组织除外）。

| 属性 | 业务含义 | 取值与约束 | 何时确定 |
|---|---|---|---|
| 是否可邀请 | 这个组织能不能加人 | 个人组织为否，且**不可更改**；其他组织为是 | 创建时，此后不变 |
| 上级组织 | 这个组织隶属于哪个组织，用来表达「团队属于公司」「公司是另一家的子公司」 | 至多一个；可以为空。个人组织**恒为空**，且不可作他人的上级 | **创建时为空**；此后通过[隶属请求](#隶属关系怎么建立与解除)建立，也可解除 |

**「上级组织」是一个属性，不是一套新机制。**由这一个属性自然长出组织之间的隶属链，
不需要另立概念。三条约束随之成立：

- **至多一个上级。**一个组织有两个母公司这种情形，本版不表达——那需要的是一张关系表，
  不是一个属性。真有需要时再加。已经有上级的组织，要先解除才能建立新的。
- **隶属链不得成环。**A 的上级是 B，则 B 及其上级都不能反过来隶属于 A。
  否则「谁是谁的上级」无法回答。
- **个人组织不参与。**它的上级恒为空，也不能作别人的上级。

#### 隶属关系怎么建立与解除

两个已经存在的组织——包括由不同账号创建的两个组织——**可以**建立隶属关系。
不能表达这件事，并购与重组就没法在系统里成立。

**建立需要双方的超级管理员各做一次动作：一方发起，另一方接受。**
发起时产生的那份东西叫**隶属请求**：它由一个组织的超级管理员发给另一个组织，
请对方成为自己的上级，或请对方成为自己的下级；**被接受时，下级组织的「上级组织」属性有了值**。
**发起—接受这个形状与[邀请与加入](flows.md#15-邀请与加入)是同一个形状**，交互上不另造一套。

**但隶属请求与加入组织的邀请是两种不同的对象，不是同一样东西的两种用法：**

| | 谁发给谁 | 被接受时产生什么 |
|---|---|---|
| **加入组织的邀请** | **组织 → 账号** | 一个[租户](#租户)，也就是一段成员关系 |
| **隶属请求** | **组织 → 组织** | 「上级组织」这一个属性的值，**不产生任何租户** |

**关系的主体不同，接受之后的结果也不同**，所以各自是一种对象、各自定义。
**两者只有一处相同：[过期规则](#两种邀约都会过期)。**规则相同不使它们成为同一样东西——
把它们当成一种，就会得出「接受一份隶属请求也该产生一个租户」这类结论。

**单方面指定是不允许的**，哪怕发起方是上级。如果一个组织的管理员能自己把
别人设为自己的下级，他就能单方面打开那条边界——那不是隶属关系，那是后门。
两边的最高治理权都点了头，它才是双方的决定。

两个组织的超级管理员碰巧是同一个人时，他自己发起、自己接受即可，不设特例。

**解除则任一方都可以单方面做，不需要一份隶属请求。**要双方同意才能解散，
等于一方能绑架另一方；而解除本身不夺走任何人**拥有**的东西。
这与[退出组织](flows.md#16-退出组织)一致。

关系解除之后各方还剩什么，归
[PF-003](../PF-003-asset-transfer-and-sharing/design.md#612-关系解除之后)——
那是资产的事，不是组织属性的事。

由这个属性可以谈两个组织的关系：顺着上级一路往上得到它的**上级链**。

**两个组织「有共同上级」，指的是：把各自算进自己的上级链之后，两条链有交集。**
**也就是说，它们在同一棵隶属树上（根相同）**，这与
[PF-003 §5.2 的那个边界](../PF-003-asset-transfer-and-sharing/design.md#52-边界是那棵隶属树不是单个组织)
是同一句话。

**「把自己算进来」这一步不能省。**上级链本身不含自己，
若只比两条不含自己的链，**一个组织与它自己的上级就不算有共同上级**——
而它们分明在同一棵树上，团队与它所属的公司之间反倒成了出树。
把各自算进来之后，祖先与后代、兄弟与兄弟、同一棵树上任意两个组织，
判出来的都是同一个答案：**同树为真，出树为假。**

个人组织的上级链恒为空，把它自己算进来也只有它一个，
所以**任何两个个人组织都不会有共同上级**——这不是一条额外规定，
是上面那条"恒为空"的直接结果。

**上级组织不进[作用域的层次](#61-层次)。**子组织不自动继承上级组织的设置、
权限与资产：那会让作用域的层数随隶属链变化，且把"隶属"悄悄变成"被管辖"。
东西要流过去，走明确的动作（见 [PF-003](../PF-003-asset-transfer-and-sharing/README.md)），
不靠层级自动发生。

#### 两种邀约都会过期

**本 topic 有两样东西要等对方点头**：**加入组织的邀请**，
和[**隶属请求**](#隶属关系怎么建立与解除)。**两者都不会无限期悬着。**

**它们是[两种不同的对象](#隶属关系怎么建立与解除)**——一个组织发给账号、接受产生租户，
一个组织发给组织、接受填上一个属性。**这一节说的是同一条规则管着它们两个，
不是说它们是同一样东西。**

| | 怎么定 |
|---|---|
| **过期时长** | **每类邀约各有默认值**（按部署配置），**发出时发起者可以指定这一份的时长**；具体数值仍不在产品这一层定 |
| **到期之后** | **不可再接受**。要它成立，**重新发一份** |
| **自动过期** | **它指向的那个组织不存在了，这份邀约随即过期** |

**指定时长是发出这份数据时的一个参数，不是一项配置。**发起者最清楚这一份急不急——
一份等着新同事入职的邀请和一次并购谈判里的隶属请求，合理的窗口本来就不一样。
**它只对这一份成立**，跟着这份邀约走、随它结束而消失，**不进[四层作用域](#61-层次)**。
发起者不指定时，就按该类邀约的默认值。

**一份悬着的邀约是一个没有答复的承诺。**放任它挂着，对方半年后点了接受——
而发出它的那个组织早就换了人、改了主意。**一个有到期时间的邀约，过期本身就是一个明确的答复。**

**「指向的组织不存在了就自动过期」与 [PF-003 那条是同一条规矩的两个实例](../PF-003-asset-transfer-and-sharing/design.md#614-待确认的复制通知与分享邀请会过期)**：
一份指向不存在的东西的邀约，**接受下去只会当场失败**，而失败发生在对方点头之后，
他会以为是系统出了问题。**在源头过期，他看到的是「这份邀约已失效」，那正是实情。**

> **过期与撤回效果相同，来路不同**：撤回是发出方主动收回，过期是时间或那个组织的消失替他收回。
> **两者都到「结束」，都不产生租户，也不建立任何隶属关系。**

### 个人组织

账号注册成功时自动产生的组织，是该账号的默认协作范围。

- 它**只有创建它的那一个账号**作为成员，该账号自动是超级管理员。
- 它**不能邀请其他账号加入**。这是结构性禁止，不是一项可被调整的权限设置。
- 它**既没有上级组织，也不能作别人的上级**。它是账号的私域，不是治理链上的节点。
- 每个账号恰有一个个人组织；每个个人组织恰属于一个账号。

### 租户

**(组织，账号) 这一组合所确定的身份。它是数据归属与隔离的单位。**

- 账号 A 加入组织 O，即产生租户 (O, A)。
- 同一组织内的两个成员是**两个不同的租户**：(O, A) 与 (O, B) 各有独立的设置、权限与资产。
- 同一账号在两个组织中是**两个不同的租户**：(O, A) 与 (P, A) 互不相通。
- 账号注册时随个人组织一并产生第一个租户，因此**新账号恰有一个租户**。

**租户身份不含角色。**理由见取舍表第二行。

#### 退出之后再加入，回来的是同一个租户

**租户身份就是 (组织, 账号) 这一组合**，由定义确定。
同一个账号退出组织之后又被邀请回来，得到的仍是 (O, A)，**不是一个新的身份**——
成员关系的断与续改变的是这个身份**此刻有没有效**，不改变它**是哪一个**。

**成员关系解除期间，这个租户的[租户级](#61-层次)私有部分不可达，但不销毁。**
他在这个组织里的 customized 资产、以及他在租户级配的那些值，**留在原处**：
既不跟人走，也不被清掉，只是没有任何身份能够到达它们。**重新加入之后原样可用。**

**这与[作者记录是历史事实](#67-创作与归属)是同一个口径。**归属只能挂在稳定的身份上，
而 (组织, 账号) 正是那个稳定的身份：

- 若退出就销毁，「归属」会因为成员关系的一次断续而蒸发——而这个人可能只是短暂离职又回来。
- 若退出后再加入换成一个新身份，此前的署名与归属就都指向一个再也没人对应的旧身份，成了孤儿。

**解除期间他在这个组织里什么也看不到、什么也做不了**，这与[撤销向后生效](#66-撤销不等于强制停止)
是同一条规矩。**重新加入也不是一次恢复动作**：没有东西被删过，也就没有东西需要恢复，
只是那个身份重新有效了。

### 当前租户身份

**一个账号此刻以哪一个[租户](#租户)身份行事。**

它是**这次[登录状态](flows.md#32-登录状态)上的一项选择**，不是一个独立的东西：登录之后它初始指向该账号
[个人组织](#个人组织)里的那个租户（[flows §1.2](flows.md#12-登录)），
[切换当前组织](flows.md#18-切换当前组织)就是改这项选择。

**它是「动作创建那一刻的环境值」——这是它最要紧的性质。**三条：

- **切换只影响此后新建的东西。**改了这项选择，先前已经建起来的东西一律不动。
- **任何在某个租户身份下创建的对象，持有创建那一刻的那个租户身份**，
  此后一切以它计：成本算在它头上、归属记在它名下、能用什么按它求值。
  一次会话在哪个租户身份下建的，就一直是那个租户的，**哪怕这个账号后来切到了另一个租户身份**——
  直到**那个租户身份本身失效**，也就是[成员关系被解除](#退出之后再加入回来的是同一个租户)。
- **这项选择随登录状态走。**它不是账号上的一项事实——[账号不持有范围化对象](#账号)；
  它也不是被创建对象自己算出来的东西。它回答的只是「**这次登录此刻站在哪里**」。

**为什么要写死这一条**：若一件已经建起来的东西「归谁」跟着账号当前站在哪里跑，
同一个会话上午算在一个租户头上、下午算在另一个头上，**成本、归属与可见性全部随之漂移**，
而[归属只能挂在稳定的身份上](#五模型)。**在创建那一刻把租户身份捕获下来**，
这件事此后就不再取决于任何人怎么切换。

> **这项选择本身不是范围化对象**：它不参与[任何一层的求值](#61-层次)，
> 也不被任何一层配值。它只决定**这一次动作以谁的身份开始**。

### 角色

租户在其所属组织内的属性，决定这个身份**当前能做什么**。

- 角色由该组织的超级管理员分配与收回，包括把超级管理员分配给他人。
- 角色**可变**。变更只影响**此后**的准入判定，不改变已发生的归属与既有事实。
- 任何组织在任何时刻至少有一位有效的超级管理员。
- 超级管理员的作用域是**该组织**，不因此取得平台全局权限、官方原件的编辑权、
  其他组织的管理权，或成员个人范围的访问权。
- 一个租户在其组织内**只持一个角色**。理由见取舍表。
- 本版的角色只有两种：**超级管理员**与**普通成员**。

### Context：agent 运行时可感知的上下文信息

> **不是 Cordis 的 `Context`。**本项目内核用 Cordis，Cordis 有一个叫 `Context`
> 的运行时对象，那是**依赖注入与生命周期的容器**，属技术设计。
> 本 topic 说的 context 是**产品概念**：agent 在运行时能感知到的关于"我现在
> 处在什么情形下"的信息。正文出现 context 一律指后者；指前者时写全 `Cordis Context`。

**context 有两种，彼此正交：**

| Context | 是什么 | 由谁承载 | 换了会怎样 |
|---|---|---|---|
| **协作范围 context** | 我现在在哪个组织、以什么租户身份、什么角色 | **组织与租户** | 能用的资产、能做的事、怎么做，全都变 |
| **个人 context** | 这个人本身的偏好：界面语言、时区、通知方式…… | **账号** | 跟着人走，在所有组织里都一样 |

**正交的含义是两者独立变化**：切换组织不改变界面语言；改界面语言也不影响
自己在哪个组织。它们不在同一个维度上，因此**不能用同一套层次去合成**。

这条澄清了一件事：界面语言这类偏好**不属于**下面说的范围化对象，
也不该被塞进[层次](#61-层次)里去覆盖。它在另一个轴上。

**账号因此不是"什么都不持有"**——它不持有范围化对象（设置、权限、资产），
但它承载**个人 context**。这与 §4「账号」的三个作用相容：
个人 context 正是"属于这个人、与他在哪个组织无关"的那部分，
和「聚合」一样是跨组织的。

> 个人 context 里具体有哪些项、能不能被组织影响，**本 topic 不定义**，见 §8。

### 范围化对象

**协作范围 context 内部**的对象：设置、权限与资产的共同抽象——
**归属于某一层身份、并参与求值的对象**。

| 要素 | 业务含义 |
|---|---|
| 能力标识 | 判定两个对象是否"实质上同一性质"，从而可以互相覆盖。**它由什么构成按资产类别定**，见 [PF-002 §4](../PF-002-assets-settings-and-permissions/design.md#身份是类别--name其余归实现) |
| 所属层 | 它挂在哪一层身份上 |
| 合成语义 | 同一能力标识的对象在多层同时存在时，怎样合成出最终结果 |

### 设置、权限、资产

三者各约束 agent 的一个方面：

| 对象 | 约束 agent 的 | 通俗说 |
|---|---|---|
| **资产** | **组装** | agent 由什么构成——有哪些技能、工具可用，**以及从哪里被触达** |
| **权限** | **行动** | agent 能执行什么动作，边界在哪 |
| **设置** | **方式** | agent 以什么配置、什么参数去做 |

**但三者的地位不同。**只有**资产**是独立存在的对象；
**设置与权限是资产的两种属性**：

```text
一个具体的资产（比如某个工具）
  ├── 属性：设置        它的默认模型、参数……
  └── 属性：权限        它的执行权限：问一下 / 自动 / 禁止
```

- 资产**定形状**：我有哪些设置项、哪些权限项，各自什么含义、取值域是什么。
- **持有该资产的层**各自**配值**：在我这一层，这些项配成什么。
  配值的资格来自[持有](#拥有获权选用)——没有这个工具，就配不了它的执行权限。
- 运行时**求值**：沿层级覆盖或收窄，算出这次组装 agent 实际用的值。

**由此，「组织的设置」「租户的权限」都是视图，不是对象。**
它们是在该身份**持有的资产集合**上的投影：

```text
组织 O 的设置  ≝  { (O, 资产 X, 属性项) → 值 | X ∈ O 持有的资产 }
```

真正可被读写的最小单位是 **（身份层，具体资产，属性项）→ 值**。
把「组织设置」当成对象来实现，就会出现一份独立于资产的字段表，
它与资产各自演化，最终对不上。**视图不需要维护——它是持有关系的函数。**

> 资产的种类、组合关系与求值的完整步骤，见
> [PF-002](../PF-002-assets-settings-and-permissions/README.md)。

### 资产的种类

**「资产」这个抽象下只有这八类。**

| 种类 | 含义 | 管理边界 |
|---|---|---|
| **Skill** | 可独立定义、发布、引用的技能 | 定义所有权、使用权与版本选择分别治理 |
| **Tool** | 一个可被调用的动作 | **可动态组装**，因此是独立资产而非组件。开发、部署、装载与使用分别受权限约束，不能从"可安装"推出任意执行权 |
| **Plugin** | 分发与组合单元，把若干资产打包在一起分发与启用 | 内含成员随 Plugin 版本与使用权治理；独立外部依赖保留自己的身份与使用权。**不是 Cordis plugin** |
| **Agent Definition** | 一个 agent 的**静态定义**：它由什么组装而成、以什么面貌工作 | 一个组织或租户可**同时拥有多个**互不相同的 agent definition。它**不是**会话或 agent runtime；引用了某个组件**不等于**取得该组件的所有权。sub-agent 的定义属于这一类 |
| **Slash Command** | **人主动发起一件事的入口**。绑定目标恰有三种：一段自定义提示词、一个 skill、一条系统业务流程 | 只由交付面识别、只对人；不含键盘控制与 shell 命令。三种绑定目标的形状与名字规则归 [PF-002](../PF-002-assets-settings-and-permissions/design.md#slash-command) |
| **MCP** | **一个外部工具来源的接入点**。接进来之后，它提供的动作可被 agent 使用 | 接入点本身是资产；**它带来的那些动作不单独成为资产**，随它一起被持有、授权与治理。外部服务端的可用性与版本**不由本系统掌握** |
| **Connector** | **一个外部消息来源的接入件**，把外部的消息送进来 | **它是唯一方向朝里的一类**：别的资产约束 agent **能做什么、怎么做**，或**在哪些位置插手**，只有它约束 agent **从哪里被触达**。安装与授权分别治理；它没有数据读取面，也没有管理面 |
| **Loop Extension** | **挂在某个 [Loop 拓展点](../PF-012-agent-loop-and-run/design.md#58-loop-拓展点)上的一段判断或动作** | 它声明**挂在哪个位置**、**管哪些情形**、**干预力多大**（只观察 / 可改写 / 可否决）。**干预力是权限**，所以「装了它、却只给只观察」是成立的配法。**同一个位置可以挂多个，各干各的** |

**这八类是穷尽的。**由此推出几件容易被弄错的事：

| 东西 | 它是什么 | 为什么不在这张表里 |
|---|---|---|
| Rules | **Plugin 的组合成员** | 组合关系一旦成立，「成员」与「独立资产」就不互斥了，不需要为成员另设一类 |
| Service、Middleware | **技术实现概念** | 产品设计里出现它们，只会让读者以为自己需要理解运行时 |
| 模型档案 | 某个 Agent Definition 的一项**设置**的取值 | "默认模型"是设置，不是组装出 agent 的零件 |
| 知识、经验、报告、附件与文件 | agent 工作时**读写的对象** | 它们不参与组装。按本节对资产的定义（约束 agent 由什么组装而成），它们从来就不该在这张表里。归属见 §8 |

**关于 Connector 的方向**：Skill、Tool、MCP、Plugin、Slash Command、Agent Definition
回答「agent **能做什么、怎么做**」，Loop Extension 回答「**推进的时候在哪些位置插手**」，
只有 Connector 回答「agent **从哪里被触达**」。
它仍然是资产，因为它同样是**agent definition 里声明的一项构成**——
声明接了哪个外部来源，和声明装了哪个工具，是同一种动作；
它同样要被持有、授权、按层级求值。

但要如实说明：这使「组装」的含义**不只是「由什么零件构成」，还包括「朝外开哪些口」**。
**这一层含义是 PM 推出来的，不是产品负责人给的**——推理链与可撤回的条件
记在 [decisions.md](decisions.md)。

**关于 Loop Extension**：它既不回答「能做什么」，也不回答「从哪被触达」，
而是回答「**推进的时候，在哪些位置插手**」。

**它仍然是资产，四条判据一条没少**：在 agent definition 里被声明、被持有、被授权、
**按层级求值**。而最后一条正是产品要的那个后果——

> **组织超管在组织层配一份，租户在自己那层覆盖**，走的就是本 topic 已有的层级求值，
> **不必为「拓展/覆盖策略」另造一套配置与授权**。

**这是对资产定义的第二次扩展**：从「由什么零件构成、朝外开哪些口」，
再扩到「**以及推进时在哪些位置插手**」。**与 Connector 那次同一种性质**，
一并记在 [decisions.md](decisions.md)。

### 来源：official 与 customized

**official 是组装出一个 agent 的最小必需。**

- 它不是"一批可以申请使用的官方资源"，而是**底座**：
  没有它，agent 组装不出来。它构成每个
  [Agent Definition](#资产的种类) 静态定义中**不可去除**的那一部分。
- 因此它**不需要授权**，也**不可被禁用**——组织的超级管理员同样没有
  "不允许成员使用 official" 这项权力。这不是一条可以调整的权限设置，
  是结构性的。
- official 位于**出厂默认层**。它是资产求值的下界，不是某一层的可选内容。

**customized 是自定义来源。它对 official 只有一种关系：替代。**

- 当一个 customized 资产与某个 official 资产**实质上是同一个东西**时，
  允许用前者替代后者。判据就是[范围化对象](#范围化对象)的**能力标识**相同。
- 替代**不是移除**：替代之后该能力标识下仍然有东西，最小必需没有被破坏。

| | official | customized |
|---|---|---|
| 位于哪一层 | 出厂默认 | 组织级、租户级皆可 |
| 需要授权吗 | **不需要**，它是底座 | 需要，按拥有与获权判定 |
| 可以禁用吗 | **不可以**，任何角色都不行 | 可以，它本来就是可选的 |
| 可以被替代吗 | 可以，被同能力标识的 customized 覆盖。**例外是 [meta：不可禁用，也不可替换](../PF-007-meta-capabilities/design.md#meta-与常驻的关系)** | 可以，被更高层同能力标识的覆盖 |

**由此，「来源」不是独立于层次的第三个维度，而是层次的体现。**
official 与 customized 的关系，就是出厂默认层与其上各层在[资产合成](#62-三种合成语义)
中的关系，不需要另一套规则。

自定义来源**不会**因为它被 agent 使用就给作者或该 agent 额外的行动权限——
资产决定组装，权限决定行动，两者不互相转化。
来源也不能靠任意请求自报来冒充。

### 拥有、获权、选用

三件不同的事，可同时成立但互不蕴含：

| 事实 | 含义 |
|---|---|
| **拥有**（定义所有权） | 这个定义是谁的 |
| **获权**（使用权） | 谁被允许使用它 |
| **选用** | 某个范围当前实际选了它的哪个版本 |

获得使用权或选用**不转移**定义所有权，也**不证明**节点已安装、agent 已激活或某次动作已获准。
自己拥有的定义可直接作为权利依据，无须伪造一份向自己授予的外部授权。

## 五、模型

```text
账号  ────────────────┐
（自然人的产品身份）    │
                      ├──→  租户 = (组织, 账号)
组织  ────────────────┘      （归属与隔离的单位）
（协作范围）                   ↑
                              └── 角色（可变属性，决定当前能做什么）


agent 运行时感知到两种正交的 context：

  个人 context（账号承载）      ──→ 语言、时区一类，跟着人走，不随组织变
  协作范围 context（组织与租户）──→ 决定资产、权限、设置

协作范围 context 内部分两轮求值：

  第一轮：作用在资产上
  (组织, 账号) + 角色 ──→ 这个租户有哪些资产可用 ──→ 组装出这个 agent

  第二轮：作用在已装上资产的属性上
  每个资产的设置项 ──→ agent 怎么做
  每个资产的权限项 ──→ agent 能做什么
```

**先有资产，才有它的设置与权限**——第二轮的项从第一轮的结果里来。
**两种 context 不合成**——它们不在同一个维度上，各自到达 agent。

四种身份的稳定性不同，这决定了各自能承担什么：

| 身份 | 何时产生 | 何时改变 | 承担什么 |
|---|---|---|---|
| 账号 | 注册 | 不变 | 标识、鉴权、跨组织的聚合视图。**不持有任何范围化对象** |
| 组织 | 被账号创建 | 不变 | 协作范围；成员共享的层 |
| 租户 | 账号加入组织 | 不变。退出只是它[不再有效](#退出之后再加入回来的是同一个租户)，再加入回来的还是它 | **数据归属与隔离** |
| 角色 | 加入时指定 | **随时可被调整** | 当前的行动边界 |

**「不变」说的是这个身份本身不会被换掉，不是它的属性一动不动**——
[账号](#账号)的激活状态会变，[组织](#组织)的上级可以建立也可以解除。
变的是属性，被指认的那个身份还是同一个。

**归属只能挂在稳定的身份上。**

## 六、产品规则

### 6.1 层次

```
出厂默认  <  组织级  <  租户级  <  会话级
```

| 层 | 归属 | 典型内容 |
|---|---|---|
| 出厂默认 | 系统 | official 资产、它们声明的默认设置与默认权限。**official 是最小必需，任何层不得清空** |
| 组织级 | 组织 | 组织内全体成员共享 |
| 租户级 | (组织, 账号) | 我在这个组织里的私有部分 |
| 会话级 | 本次协作（**也就是那个会话**） | 只在本次协作内有效，含当前活动角色 |

**这张表说的是「归属」，不是「有一堆自己的字段」。**一层的设置与权限，
是它**持有的资产**各自属性的投影（见 §4）；持有的资产变了，这一层的内容跟着变。

**这四层是「协作范围 context」内部的层次。**个人 context 在另一个轴上，
不参与这里的合成。

**这四层是[身份](#四概念定义)带来的四层，因此只对权限这一维完整。**
**每一格由哪重身份充当**，归[作用域层身份](../../ubiquitous_language/terms/scope-and-resolution.md#ul-scope-layer-identity--作用域层身份--scope-layer-identity)。
[设置](#62-三种合成语义)那一维**在租户级与会话级之间还有工作区一级**——
那一级[挂在租户下、由工作区逻辑身份与地址/实例承载、会话创建时选定](../PF-020-workspace/README.md)，
不是一种身份，所以不在这张表里；三条层序各有哪几级，归
[PF-002 §5.8](../PF-002-assets-settings-and-permissions/design.md#58-三条层序各答一个问题)。
**权限这一维工作区一概不参与**，所以这张表对权限仍然是完整的。

**账号不在这张表里。**它是[身份概念](#账号)——标识、鉴权、聚合，
三件事全在身份范畴；而治理（持有什么、配什么值、怎么合成）发生在**组织与租户**。

账号**不是没有求值**，它的求值是恒等的：求出这一个自然人，不言自明、无需机制。
正因如此它**不占这张表里的一格**——它的求值早已完成，且不接受任何配置。
问「账号那一层配了什么」，问的是一件不存在的事。

一个人在某个组织里的东西放在**那个租户**里，不在账号上——写错会让它跨组织泄漏。

### 6.2 三种合成语义

| 对象 | 语义 | 怎样合成 | 层次是否有方向 |
|---|---|---|---|
| 设置 | **覆盖** | 取最具体的、有值的那一层的值，更外层的被丢弃 | 有 |
| 权限 | **收窄** | 各层锁下的允许集合（**界**）取交集——更外层锁下的界，更具体的一层突破不了；界内取哪一档，由最具体的、挑在界内的那一层定 | 界那一半**无**（交集可交换）；挑那一半有 |
| 资产 | **组合 + 同标识覆盖** | 不同能力标识的并存；同能力标识的取最具体那一层的 | 同标识时有 |

**「更外层 / 更具体」按上面那条层次读**：出厂默认最外，会话级最具体。

资产求值有一条**下界**：出厂默认层的 official 是最小必需，求值结果里每个 official 能力标识都必须有东西——要么是 official 本身，要么是替代它的 customized。**任何层都不能把它清空**，见 §4「来源」。

#### 默认与强制：immutable

每一层对一个东西只能做两件事：**给一个值**，以及声明这个值
**不可再被更具体的层覆盖**（`immutable`）。

| | 这层在说什么 | 更具体的层能做什么 |
|---|---|---|
| 不加 immutable | 「**默认**这样」 | 可以改 |
| 加 immutable | 「**必须**这样」 | 改不了 |

**「默认」和「强制」是两回事，但不需要两套机制。**这一个标记同时管三处：
设置的字段值、权限的取值、资产的替换。

对权限而言，`immutable(v)` 就是把允许集合**收窄到单元素** `{v}`——
强制是收窄的特例。权限的取值域是枚举的，所以它还能收窄到子集；
设置的取值域通常开放，只有锁与不锁两态。

> 三处的具体形状见 [PF-002 §5.4](../PF-002-assets-settings-and-permissions/design.md#54-默认与强制一个机制三处适用)。

#### 两轮合成，作用对象不同

这一点最容易弄错，单独说清楚：

| 轮次 | 作用在什么上 | 语义 | 回答什么问题 |
|---|---|---|---|
| 第一轮 | **资产** | 组合 + 同标识覆盖 | 这个能力标识下，生效的是哪个资产 |
| 第二轮 | **资产的属性项** | 设置覆盖 / 权限收窄 | 这个资产的某项设置或权限，取什么值 |

**两轮不能混为一谈。**混了就会得出「改一项设置等于换一个资产」这种结论——
而实际上租户改「代码助手」的默认模型时，用的**还是组织共享的那一个**代码助手，
只是它的一项属性在租户层被配了别的值。

**权限的每一层能做的两件事，一件是界，一件是挑。**加了 `immutable` 的是**锁下一个允许集合**——
那是一道**界**，各层的界取交集；没加的只是**在界里挑一个**，越具体的一层挑的越算数，挑到界外的不算。
所以「组织没锁、租户设成自动」**不是放宽**：组织没给界，「自动」本来就在界内，租户只是挑了它。
**「禁止」例外**：哪一层把它配成「禁止」，锁不锁都是界——一个能被下一层挑掉的「禁止」，算不上明确禁止。
组织若把某一项**锁成空集**，租户再怎么挑也拿不到：空集与谁的交集都是空集。
界与挑怎样落到一档，归 [PF-002 §5.3](../PF-002-assets-settings-and-permissions/design.md#53-两个例子两种合成)。
**[禁用不走这条路](../PF-002-assets-settings-and-permissions/design.md#禁用是逐层配的布尔设置任一层为真即不可见)**——
它是持有关系上的一项布尔设置，按**析取**合成（任一层为真即不可见），不是权限的交集。

### 6.3 依赖与组合

资产可以声明依赖。**依赖指向能力标识，不指向具体某个资产**，
因此发生覆盖之后，依赖自动指向当前生效的那一个。

资产之间是**组合关系**，资产组装成 agent **本质上也是同一种组合关系**。
完整的组合形状与求值步骤见
[PF-002](../PF-002-assets-settings-and-permissions/design.md)。

### 6.4 隔离

- 受租户所有权约束的对象与跨范围操作**显式携带**租户身份；
  没有明确所有权或成员资格依据时，跨租户访问**默认拒绝**。
- 目标范围不可用或成员失权时**明确失败**，不静默回退到个人范围。
  **两者收场相同，但不是同一件事**：「不可用」是**判不出来**——那个范围此刻答不了话；
  「失权」是**判出来了，答案是无效**，也就是[成员资格效力](../../ubiquitous_language/terms/subjects-and-ownership.md#ul-membership-standing--成员资格效力--membership-standing)不成立。
- 个人范围的权限与资产**不因**加入组织而共享；
  组织的[超级管理员](#角色)身份**不带来**成员个人范围的访问权。
- 一层的事实**不因**切换组织被复制到另一层，方向两边都算。
- 账号的身份事实（标识、凭据、激活状态）**不是范围化对象**，
  不参与任何层的求值，也不得被当作某一层的设置或权限。
- **账号是一个自然人全部 context 的最大边界。**他的个人 context、他在每个组织里的
  协作范围 context，都在这道墙之内；[两个账号之间没有任何通路](#账号)，
  哪怕背后是同一个人。

  这道边界是**身份的推论**，不是账号行使的一种治理能力——
  不同的身份本就互不相通，因此账号自然成了外壳。
  **边界上没有可配置的东西**：一旦允许在它上面配值，它就变回了一层。

  这也是「聚合」为什么只是视图：账号能**看见**墙内的所有租户，
  却不能把一个租户的东西搬到另一个。**看得见 ≠ 可搬运。**
- 个人与多个组织的使用权**不自动叠加或相互借用**。
- **使用成本按租户归属，且能出账单明细。**一次调用花掉的成本必须能算到发起它的
  那个租户头上，并能逐条列出来。这是隔离模型的推论：既然 (组织, 账号) 是归属单位，
  成本也不例外。**本版到明细为止**——不设额度、不设预算、不做超限拦截。
  实际费用拿不到时明细里记什么，[归 PF-013](../PF-013-model-profiles-and-invocation/design.md#停机之后能不能重来只看首-token)。

### 6.5 本地资源定位

本地部署可能让不同账号的资源同处一台机器。运行时定位这些资源时，
必须从**当前已验证的账号身份、资源声明的范围及相应归属与授权**求得适用范围。

**物理路径、当前工作目录、同一操作系统用户、同盘存放，本身都不构成跨账号或跨租户的访问资格。**

#### 路径是地址，不是钥匙

这条规则**不否认要记地址**。一条路径是[工作区地址](../PF-020-workspace/README.md)，
是发现或访问工作区实例的一种方式；它不是工作区身份，也不是访问资格。租户可以记录自己可访问的地址，
**那是定位，不是授权**。

**资格是另一回事**：它来自工作区归哪个租户，以及来者此刻是不是该租户的有效成员。两者分开之后，
这条规则挡住的是它的反面——

> **另一个账号或租户，哪怕用同一个操作系统用户、进到同一个地址指向的资源，
> 系统也不因此认为它可以访问那个工作区。**

同一地址在不同租户身份下不能绕过隔离；两个租户看到的不是同一个授权上下文，各自的工作区资产与配值互不可见。

**至于操作系统层面那些文件到底防不防得住，不归身份模型**（§2 非目标）。
本节定的是**谁有资格**，不是**用什么机制拦住越权的读写**。

### 6.6 撤销不等于强制停止

角色变更、退出、撤权、撤销分享，影响的是**下一道尚未通过的准入**。
旧菜单、缓存与历史成功不能继续当作授权。

**已经开始的调用是否停止，由独立的运行控制决定**，不能把使用权撤销和强制停止混为一件事。

### 6.7 创作与归属

获授权的用户或 agent 在明确的范围中创作、修订、发布资产。**实际作者与定义所有者分别记录。**

#### 作者用租户身份标识

**作者是一个租户，即 (组织, 账号)。**这正好表达「**那个组织里的谁**产出了这个东西」——
既不是光有账号（说不出在哪个组织的名义下做的），也不是光有组织（说不出是谁做的）。

由此得到三条：

- **作者记录不随角色变动而变。**[角色不进租户身份](#租户)，所以他升职、降职、
  换了岗位，此前产出的东西署名照旧。
- **作者记录是历史事实，不随成员关系解除而失效。**账号退出组织之后，
  [他在组织范围创作的资产留在组织](flows.md#33-成员关系)，作者记录也照旧——
  它记的是"当时是谁做的"，不是"现在谁还在"。
- **所有者与作者是两件事。**在组织范围创作的，**所有者是组织**，**作者是那个租户**。
  两者分开记，才能同时回答"这东西归谁"和"这东西谁做的"。

| 情形 | 所有者 | 作者 |
|---|---|---|
| 成员在**组织范围**创作 | 该组织 | 该租户 (组织, 账号) |
| 成员在**自己的租户范围**创作 | **该租户** | 该租户 |
| 人在自己的个人组织里创作 | 他的个人组织 | 该租户 |
| **agent 产出** | 它运行所在范围的所有者 | **它运行所在的那个租户**，并标明是 agent 产出 |
| official 资产 | 平台 | 平台。**official 没有租户** |

前两行的分别很实在：**在组织范围创作的归组织，在自己租户范围创作的归自己。**
[租户级是"我在这个组织里的私有部分"](#61-层次)，放在那里的东西还没交给任何人。

由此得到一条不可逆：**把一份资产从租户范围提升到组织范围，是一次交付，所有权随之易手。**
提升之后它是组织的，不能再退回租户范围——否则"归组织"就成了可以随时反悔的说法。

**提升只换所有者，不动任何一份持有。**提升之前哪一层持有它、各自配了什么值，提升之后原样还在：
交出它的那个租户照常持有、配的值一个不丢。**组织那一层要持有它，是[组织加入一份资产](../PF-002-assets-settings-and-permissions/flows.md#11-给组织加一个资产)那个动作**，
与别的资产进组织同一条路，不因为它刚被提升就自动发生。
所有权答「这东西归谁」，[持有](../../ubiquitous_language/terms/circulation-and-entitlement.md#ul-asset-holding--资产持有--asset-holding)答「这一层用不用它」——
提升改的是前者；顺手改后者，要么抹掉交出者没说要放弃的配值，要么让组织层在没人加入的情况下多出一份持有。

**agent 产出要能与人产出分辨。**本条正文说创作者可以是"用户**或 agent**"，
若记录里不分辨，审计就答不出"这是人写的还是 agent 写的"。
在 agent 会大量产出东西的系统里，这个区分是实在的需要。

#### 其余

- 在组织范围创作的，**不因作者是自然人就变成个人资产**；agent 创作也不使资产脱离该范围的治理。
- 草稿可修订；**已发布版本保持不可变**，后续改变形成新版本；发现新版本不静默替换已选用的版本。
- 持有使用权**不自动**获得编辑、fork、转让或扩大对外共享的权力。

### 6.8 管理结果

- 用户能看到修改是否实际成立、影响哪些后续使用、受影响的引用与工作。
- 改版、移除或退役前核对相关依赖；**不默认级联删除、不偷偷替换版本、不把资产停用当作停止正在运行的工作**。
- 多步流程部分成功时分别展示已完成与待处理的步骤；未知结果后的重试**认回同一逻辑操作**。
- 过期编辑不得静默覆盖他人已确认的修改。
- 当前权限与目标条件在**实际操作时**核对；旧菜单或预览不构成永久授权。
- 审计保留操作者、范围、对象、变更与依据；凭据不以原文出现。
- 来源故障、权限不足、引用阻断与真实空清单**分别反馈**，不用假成功隐藏管理失败。

## 七、取舍

| 面临的选择 | 选了 | 为什么 |
|---|---|---|
| 登录标识在**部署内**唯一，还是在**组织内**唯一 | 部署内 | 登录发生在任何组织范围建立之前——用户只提供标识和凭据，系统得据此唯一定位账号。组织内唯一的话登录时无法确定目标账号 |
| 租户身份**含角色**，还是不含 | 不含 | 角色是设计上就要变的，而归属必须稳定。若含角色，成员升职后他此前创建的东西要么跟着迁移（那就不是归属了），要么留在一个没人对应的旧身份下（成了孤儿） |
| 权限按**覆盖**合成，还是按**收窄** | 收窄：锁下的界取交集，界内由最具体的一层挑 | 按覆盖的话，组织要守的边界只能锁成一个值，「只许问一下或禁止、不许自动」这样的界说不出来，**一条边界就只能是一个答案**。按收窄，锁下的是一个允许集合，更具体的一层突破不了——组织把「不得删除生产数据」锁上，成员在自己租户级怎么配都放不开。**代价是「默认」与「边界」要分清**：组织没锁的，只是默认，成员可以另挑 |
| 个人租户与组织租户是**两类东西**，还是同一类 | 同一类，个人组织只是不可邀请 | 两类会带来两套角色语义、两套管理操作、以及到处的特判；一个「是否可邀请」的属性就够了，且约束一条没丢 |
| 「多组织」用**多账号**表达，还是用**一个账号多成员关系** | 一个账号多成员关系 | 多账号是给同一个人在系统里开两个互不相干的身份用的，与"在多个组织协作"是不同的需要。混用会让隔离规则无法自洽 |
| 「流程规范」立不立为**第四个约束面** | 不立 | 它与三个面**不能正交组合**：一条「删文件前先问」既可表述为权限（没有不问就删的资格），又可表述为设置（以先问的方式工作）。四维模型里它会有两个家，而同一条规矩有两个家就等于没有家 |
| 一个账号在同组织内持**单角色**还是**多角色** | 单角色 | 多角色要引入「本次以什么角色操作」这个会话级概念，而目前**没有任何场景**需要它。模型已预留位置，将来要加是加法不是改结构 |
| **来源**（official/customized）是独立维度，还是层次的体现 | 层次的体现 | official 就是出厂默认层，customized 就是其上各层。当成独立维度的话，"官方的组织自定义版"该听谁的需要另立一套规则；当成层次，同能力标识覆盖这一条已经回答了 |

## 八、边界与依赖

本 topic 定义身份，以及身份通过设置、权限、资产三类对象产生的约束。
以下内容**紧邻但不属于本 topic**，各自需要独立的产品设计；
本节声明分界，是为了让后来者知道在哪里停手。

| 紧邻的主题 | 它该拥有什么 | 分界在哪 |
|---|---|---|
| [PF-002 设置、权限与资产的展开](../PF-002-assets-settings-and-permissions/README.md) | 八类资产各是什么、谁能组合谁、组装分几步、属性项怎么落 | 本 topic 定**层次与合成语义**，它定**对象的形状与组合** |
| 技能与工具的装载 | 技能、工具在运行时怎样被发现、装载、卸载 | 本 topic 定它们**属于资产、怎样合成**，它定**怎样装载** |
| 知识、经验、报告、附件与文件 | 这些信息与工作产物怎样治理：权限、生命周期、来源与归属 | 它们**不是资产**（§4），不参与 agent 的组装；本 topic 不定义它们 |
| 个人 context 的内容 | 具体有哪些偏好项、各自什么语义、组织能不能对它施加影响 | 本 topic 只定**它存在、由账号承载、与协作范围 context 正交**；有哪些项不归这里 |
| 使用成本与账单明细 | 成本怎么算、明细怎么归集与呈现 | 本 topic 只要求**成本能归属到租户、能出明细**（§6.4），它定怎么算怎么看 |
| [PF-003 资产的复制与分享](../PF-003-asset-transfer-and-sharing/README.md) | 资产怎样跨组织流动：资产复制与分享两个动作、方向与范围、关系解除之后 | 本 topic 只定**不自动流入**，以及组织的隶属属性；主动的流动归它 |
| 插件的开发与部署 | 谁有资格开发部署插件、插件之间怎样隔离 | 本 topic 定插件**属于资产**，它定**开发部署的边界** |

| 会话与运行 | 会话、运行的生命周期与显式的运行控制 | 本 topic 的 §6.6 把「停止正在运行的工作」整个交给它 |
| 持久制品与工作副本 | 制品怎样保存、工作副本怎样隔离 | 资产的**治理**归本 topic，制品的**保存流程**归它 |
| [SYS-TENANT](../../foundation/cross-system-constraints/requirements.md#sys-tenant) | 全局的租户隔离义务 | 本 topic 是它在身份模型上的展开，**不削弱它** |

除 SYS-TENANT、PF-002 与 PF-003 外，上表各项目前都还**没有对应的产品设计**。
它们各自成立 topic 之后，本 topic 的 `README.md` 要补上 `depends-on` 声明；
在那之前，本 topic 不得替它们做定义——**留空比猜一个安全**。

**PF-002 是本 topic 的展开，不是依赖。**本 topic 不引用它的结论，
反过来它引用本 topic 的层次与合成语义。方向不能反。
