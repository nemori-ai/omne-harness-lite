## 二、PM 推导

以下结论不是直接裁决的，是从已拍板内容推出来的。推理链写在这里供核对。

| 结论 | 从哪几条推出 | 推理 |
|---|---|---|
| 登录标识在**部署内**唯一 | 「用账号凭据登录指定账号」 | 登录发生在任何组织范围建立之前——用户只提供标识和凭据，系统得据此唯一定位账号。若标识仅组织内唯一，登录时无法确定目标账号，该裁决无法实现。**只有一个答案成立** |
| 注册以**激活**为单一提交点 | 「注册成功时恰有一个个人租户」 | 注册成功的含义包含身份与个人空间两者。若账号一建立就可用，中途失败会留下没有个人组织的可用账号，与该裁决矛盾。设一个未激活中间态、以个人组织存在为激活前置，是满足该裁决的唯一自洽结构 |
| 账号**不能退出自己的个人组织** | 「个人组织只有该账号一个成员且是超管」+「组织不能失去最后一位超管」 | 退出会使个人组织失去唯一的超管，违反后一条。两条已确认内容共同蕴含此结论 |
| 权限**不需要**层间次序 | 权限按收窄合成 | 交集满足交换律，先交组织还是先交租户结果一样。因此「谁覆盖谁」这个问题对权限不存在，只对设置存在 |
| 合成语义是**对象自身的属性**，不是全局规则 | 「组织可强制某些设置」这一实际需要 | 若合成是全局规则，「组织强制」与「个人可改」无法共存。让每个字段声明自己的语义，两者都能表达且不必新增机制 |
| 个人组织与其他组织是**同一类东西** | 「个人组织只有一个成员、不能邀请」 | 差别只有"能否邀请"一项。分成两类会带来两套角色语义与到处的特判，而一个属性就够，约束一条没丢 |
| **成员退出组织，双方都能发起** | 「个人组织不能退出，因为会使其失去唯一超管」 | 那条论证成立的前提，就是**普通组织可以退**——否则「个人组织不能退」不需要单独论证。至于超管能移除成员，是「超管可分配角色」的极端情形。两侧都已被已确认内容蕴含 |
| **一个租户在组织内只持一个角色** | 「角色是租户的可变属性」+ 目前的全部场景 | 多角色要求引入「本次以什么角色操作」这个会话级概念。**没有任何已确认场景需要它**，按最小正确模型不预埋。模型已预留位置，将来是加法 |
| **本版只有超管与普通成员两种角色** | 「精确的角色与动作矩阵留待实际需要」 | 中间角色（只读、审核）由具体业务需求驱动。没有需求就定义角色，定出来必然是拍脑袋的。这是**边界**，不是缺口 |
| **模型档案不是资产** | 「五类是穷尽的」+「默认模型是 agent definition 的一项设置」 | 产品负责人把"默认模型"举成了**设置**的例子，而五类里没有模型档案。两条合起来只剩一个答案：它是某项设置的**取值**，不是组装出 agent 的零件 |
| **知识、经验、报告、附件与文件不是资产** | 「五类是穷尽的」+ 本 topic 对资产的定义 | 资产的定义是「约束 agent 由什么组装而成」，而这些东西**不参与组装**——它们是 agent 工作时读写的对象。此前把它们列进资产种类表，与本 topic 自己的定义相矛盾。**这是一处自我不一致，已修正**，去向记在 §8 |
| **两轮合成不能混为一谈** | 「设置权限是资产的属性」+ §6.2 的三种语义 | 第一轮作用在**资产**上（哪个资产生效），第二轮作用在**属性项**上（某项取什么值）。混了会得出「改一项设置等于换一个资产」，而租户改默认模型时用的还是组织共享的那一个 |
| **作用域由五层减为四层** | 「账号只做标识、鉴权、聚合」 | 既然账号不持有任何范围化对象，它就不该作为一层出现在求值里。留着一个永远空的层，只会让实现为它写一套没用的代码，还会诱使人把个人事实错放进去。层次变为：出厂默认 < 组织级 < 租户级 < 会话级 |
| **账号不设权限边界** | 产品负责人裁决「这是过度设计的伪命题」 | 两条理由。**其一**，它服务的需求是「我在所有组织里都一样」，而本 topic §1 的出发点恰恰是「同一个人在不同组织里**应当是不一样的**」——需求与设计前提直接矛盾。跨组织的风险本来就不同：在个人组织里自动删草稿没问题，在公司生产仓库里自动删就是事故。**其二**，它名义上叫「在边界上配值」，实质就是把账号级那一层加回来——边界是结构性的（两个账号不通，没得配置），一旦允许在上面配可变的值，它就是层了，只是换了个词。 |
| **形式上等价不等于产品上应该做** | 上一条的教训 | 我从「收窄语义下最外边界与最外层数学等价」推出「所以可以表达跨组织统一的权限」，但没有回到产品前提去检验这个需求**是否应该存在**。数学上能表达 ≠ 产品上该表达。推导走到一个新能力时，要回 §1 问一句：它和这个 topic 的出发点是一致还是相反 |
| **账号是边界，不是层** | 「账号是一个自然人所有 context 的最大边界」 | 层给值并参与合成，边界划定内外、跨出即拒绝。账号**不在求值里给值，而是限定求值的定义域**。此前把它表述为「账号级恒为空」不准确——那暗示它是一层而内容空，实际上它根本不在那个维度上 |
| **「个人的东西」放在个人组织的租户里，不在账号上** | 同上 + 「租户是归属与隔离的单位」 | 两者直觉上像，归属单位却不同。放到账号上就等于给了它一个跨所有组织可见的范围——个人资产会跨组织泄漏 |
| **界面偏好不进四层作用域** | 「两种 context 正交」 | 正交意味着两者独立变化——切换组织不改界面语言。既然不在同一维度，就不能用同一套层次去合成。我此前倾向把它当成某类资产的属性、或者再加一层，两条路都是把两个轴压成一个 |
| **账号不是「什么都不持有」** | 「这种 context 可以放在账号下」 | 账号不持有**范围化对象**，但承载**个人 context**。两句话不矛盾：前者说的是协作范围 context 内部的东西，后者在另一个轴上 |
| **「聚合」是视图，不是持有** | 「一个自然人在不同组织内的聚合的作用」 | 聚合让人**看见**自己有哪些租户、在它们之间切换；它不把任何一个租户的东西带到另一个租户，也不产生一份account 级的合并结果 |
| **配值的资格来自持有** | 「持有它的组织和租户各自可以配」 | 「持有它的」是限定，不是修辞。组织没有这个工具，就不该能配它的执行权限——否则会出现「为一个自己没有的东西设边界」这种既无意义又难解释的状态 |
| **账号恢复、身份终止、注册限流都不是未决项** | 已确认的排除范围 | 账号不会消失所以「恢复」没有对象；终止已被明确排除；限流是部署运维关注点，不改变身份模型任何形状。三者都是**明确排除 ≠ 没想好** |
| **来源是层次的体现，不是独立维度** | 「official 不可禁用、可被实质相同的 customized 替代」 | 「不可禁用」等价于「出厂默认层不可清空」，「实质相同可替代」等价于「同能力标识覆盖」。两条都已经在资产合成规则里，把来源另立一维会产生第二套规则且必然与它冲突 |

## 四、已知的来源问题

核对依据来源时发现一处缺口。**记在这里，不靠猜测补上。**

| 缺口 | 影响 | 本 topic 的处置 |
|---|---|---|
| 身份的两层结构——自然人全局身份与组织内成员关系——目前**只有 [SYS-TENANT](../../foundation/cross-system-constraints/requirements.md#sys-tenant) 一条**正式依据。[SYS-IDENTITY](../../foundation/cross-system-constraints/requirements.md) 的正文是项目定位（项目名、以 Cordis 为内核、服务对象），不含任何身份语义 | 若产品负责人本意另有一条独立的身份约束，它现在没有正文可引 | 只引用 SYS-TENANT。三层身份模型的其余部分由本 topic 的拍板记录承担依据，不假托系统级约束 |

**为什么不直接补一条系统级约束**：系统级约束由产品负责人确认，PM 不能代写。
本 topic 把缺口显式留在这里，比填一条看起来合理的条文安全——
后者会让下游以为那是已确认的要求。
