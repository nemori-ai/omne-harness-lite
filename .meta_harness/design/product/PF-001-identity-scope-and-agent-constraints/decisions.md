## 二、PM 推导

以下结论不是直接裁决的，是从已拍板内容推出来的。推理链写在这里供核对。

| 结论 | 从哪几条推出 | 推理 |
|---|---|---|
| 登录标识在**部署内**唯一 | 「用账号凭据登录指定账号」 | 登录发生在任何组织范围建立之前——用户只提供标识和凭据，系统得据此唯一定位账号。若标识仅组织内唯一，登录时无法确定目标账号，该裁决无法实现。**只有一个答案成立** |
| 注册以**激活**为单一提交点 | 「注册成功时恰有一个个人租户」 | 注册成功的含义包含身份与个人空间两者。若账号一建立就可用，中途失败会留下没有个人组织的可用账号，与该裁决矛盾。设一个未激活中间态、以个人组织存在为激活前置，是满足该裁决的唯一自洽结构 |
| 账号**不能退出自己的个人组织** | 「个人组织只有该账号一个成员且是超管」+「组织不能失去最后一位超管」 | 退出会使个人组织失去唯一的超管，违反后一条。两条已确认内容共同蕴含此结论 |
| 权限**不需要**层间次序 | 权限按收窄合成 | 交集满足交换律，先交组织还是先交租户结果一样。因此「谁覆盖谁」这个问题对权限不存在，只对设置存在 |
| 合成语义是**对象自身的属性**，不是全局规则 | 「组织可强制某些设置」这一实际需要 | 若合成是全局规则，「组织强制」与「个人可改」无法共存。让每个字段声明自己的语义，两者都能表达且不必新增机制 |
| 个人组织与其他组织是**同一类东西** | 「个人组织只有一个成员、不能邀请」 | 差别只有"能否邀请"一项。分成两类会带来两套角色语义与到处的特判，而一个属性就够，约束一条没丢 |
| **成员退出组织，双方都能发起** | 「个人组织不能退出，因为会使其失去唯一超管」 | 那条论证成立的前提，就是**普通组织可以退**——否则「个人组织不能退」不需要单独论证。至于超管能移除成员，是「超管可分配角色」的极端情形。两侧都已被已确认内容蕴含 |
| **一个租户在组织内只持一个角色** | 「角色是租户的可变属性」+ 目前的全部场景 | 多角色要求引入「本次以什么角色操作」这个会话级概念。**没有任何已确认场景需要它**，按最小正确模型不预埋。模型已预留位置，将来是加法 |
| **本版只有超管与普通成员两种角色** | 「精确的角色与动作矩阵留待实际需要」 | 中间角色（只读、审核）由具体业务需求驱动。没有需求就定义角色，定出来必然是拍脑袋的。这是**边界**，不是缺口 |
| **模型档案不是资产** | 「五类是穷尽的」+「默认模型是 agent definition 的一项设置」 | 产品负责人把"默认模型"举成了**设置**的例子，而五类里没有模型档案。两条合起来只剩一个答案：它是某项设置的**取值**，不是组装出 agent 的零件 |
| **知识、经验、报告、附件与文件不是资产** | 「五类是穷尽的」+ 本 topic 对资产的定义 | 资产的定义是「约束 agent 由什么组装而成」，而这些东西**不参与组装**——它们是 agent 工作时读写的对象。此前把它们列进资产种类表，与本 topic 自己的定义相矛盾。**这是一处自我不一致，已修正**，去向记在 §8 |
| **作者记录不随角色变动、也不随成员关系解除而失效** | 「作者用租户标识」+「角色不进租户身份」+「解除后资产留在组织」 | 租户 (组织, 账号) 在加入到退出之间不变，所以升职降职不影响署名；而作者记的是**当时是谁做的**，不是**现在谁还在**，因此退出组织也不该抹掉它。这正是「归属只能挂在稳定的身份上」在作者这一面的体现 |
| **所有者与作者必须分开记** | 「实际作者与定义所有者分别记录」+ 「解除后资产留在组织」 | 在组织范围创作的，所有者是**组织**，作者是**那个租户**。只记一个，就会在「这东西归谁」和「这东西谁做的」之间丢掉一个答案——而成员退出时两者的去向正好不同 |
| **agent 产出要能与人产出分辨** | §6.7 正文「获授权的用户**或 agent**」 | 两者都能创作，若记录里不分辨，审计答不出「这是人写的还是 agent 写的」。在 agent 会大量产出东西的系统里这是实在的需要。**作者仍是那个租户**（agent 代表它运行），只是多一个「由 agent 产出」的标记 |
| **official 资产没有作者租户** | 「official 位于出厂默认层」 | official 不属于任何组织或租户，所以它的所有者与作者都是平台。这是特例，要写明，否则实现会为它找一个不存在的租户 |
| **immutable 取代了「把字段声明为收窄语义」那个解法** | 「强制 = immutable」 | rev 2 曾用「那类字段声明为收窄语义即可」表达强制。它对权限说得通，对设置说不通——设置的取值域通常开放，谈不上收窄成一个子集。immutable 两者都覆盖，且把「默认」与「强制」的区别落在**同一个字段的一个标记**上，而不是落在**两种不同的合成语义**上 |
| **两轮合成不能混为一谈** | 「设置权限是资产的属性」+ §6.2 的三种语义 | 第一轮作用在**资产**上（哪个资产生效），第二轮作用在**属性项**上（某项取什么值）。混了会得出「改一项设置等于换一个资产」，而租户改默认模型时用的还是组织共享的那一个 |
| **作用域由五层减为四层** | 「账号只做标识、鉴权、聚合」 | 既然账号不持有任何范围化对象，它就不该作为一层出现在求值里。留着一个永远空的层，只会让实现为它写一套没用的代码，还会诱使人把个人事实错放进去。层次变为：出厂默认 < 组织级 < 租户级 < 会话级 |
| **账号不设权限边界** | 产品负责人裁决「这是过度设计的伪命题」 | 两条理由。**其一**，它服务的需求是「我在所有组织里都一样」，而本 topic §1 的出发点恰恰是「同一个人在不同组织里**应当是不一样的**」——需求与设计前提直接矛盾。跨组织的风险本来就不同：在个人组织里自动删草稿没问题，在公司生产仓库里自动删就是事故。**其二**，它名义上叫「在边界上配值」，实质就是把账号级那一层加回来——边界是结构性的（两个账号不通，没得配置），一旦允许在上面配可变的值，它就是层了，只是换了个词。 |
| **形式上等价不等于产品上应该做** | 上一条的教训 | 我从「收窄语义下最外边界与最外层数学等价」推出「所以可以表达跨组织统一的权限」，但没有回到产品前提去检验这个需求**是否应该存在**。数学上能表达 ≠ 产品上该表达。推导走到一个新能力时，要回 §1 问一句：它和这个 topic 的出发点是一致还是相反 |
| **账号的求值是恒等的，因此它不占作用域里的一格** | 「账号也有求值能力：确定一个自然人，不言自明」 | 恒等求值没有输入可配、没有多层可合、没有冲突可解。它的结果在身份被确定的那一刻就已经有了。占一格意味着"这里可以配点什么"，而这里配不了任何东西 |
| **账号是身份概念，不是治理概念** | 产品负责人指出「你把账号当作是一个治理性质的概念，它为什么一定要有能够求值的能力呢」 | 标识、鉴权、聚合三件事全在身份范畴；治理（持有什么、配什么值、怎么合成）发生在组织与租户。账号**有**求值，但那是身份域的恒等求值；它没有**治理意义上的**求值，因为治理不在它的域里。我此前接连用「账号级恒为空」「账号是边界」两种说法，都还把账号放在治理域里描述，只是把它的格子填成了不同的东西——错的不是格子里放什么，是不该给它一个格子 |
| **「最大边界」是身份的推论，不是一种治理能力** | 同上 | 不同身份本就互不相通，账号因此自然成了外壳。把这个推论当成「一种可以在上面配值的能力」，就会推出账号该设权限边界那个伪命题。**边界上没有可配置的东西**——一旦允许配值，它就变回了一层 |
| **「个人的东西」放在个人组织的租户里，不在账号上** | 同上 + 「租户是归属与隔离的单位」 | 两者直觉上像，归属单位却不同。放到账号上就等于给了它一个跨所有组织可见的范围——个人资产会跨组织泄漏 |
| **界面偏好不进四层作用域** | 「两种 context 正交」 | 正交意味着两者独立变化——切换组织不改界面语言。既然不在同一维度，就不能用同一套层次去合成。我此前倾向把它当成某类资产的属性、或者再加一层，两条路都是把两个轴压成一个 |
| **账号不是「什么都不持有」** | 「这种 context 可以放在账号下」 | 账号不持有**范围化对象**，但承载**个人 context**。两句话不矛盾：前者说的是协作范围 context 内部的东西，后者在另一个轴上 |
| **「聚合」是视图，不是持有** | 「一个自然人在不同组织内的聚合的作用」 | 聚合让人**看见**自己有哪些租户、在它们之间切换；它不把任何一个租户的东西带到另一个租户，也不产生一份account 级的合并结果 |
| **配值的资格来自持有** | 「持有它的组织和租户各自可以配」 | 「持有它的」是限定，不是修辞。组织没有这个工具，就不该能配它的执行权限——否则会出现「为一个自己没有的东西设边界」这种既无意义又难解释的状态 |
| **账号恢复、身份终止、注册限流都不是未决项** | 已确认的排除范围 | 账号不会消失所以「恢复」没有对象；终止已被明确排除；限流是部署运维关注点，不改变身份模型任何形状。三者都是**明确排除 ≠ 没想好** |
| **至多一个上级组织** | 「就是组织的属性拓展」 | 一个属性容纳一个值。要表达一个组织有两个母公司，需要的是一张关系表而不是一个属性——那恰恰是被裁决排除的「复杂化」。不够用时再加是加法，不改变已有形状 |
| **个人组织的上级恒为空，且不能作他人的上级** | 「个人组织是账号的默认协作范围，不能邀请他人」 | 个人组织是账号的私域，不是治理链上的节点。让它挂在某家公司下面，等于把一个人的私域纳入公司治理，与它的定义直接矛盾。**推论**：任何两个个人组织都不会有共同上级 |
| **隶属关系要双方超级管理员各做一次动作** | 「这个问题需要能够被回答」、邀请与加入的既有形状 | 单方面指定是唯一必须排除的做法：一个人能自己把别人设为下级，就能单方面打开资产流动的边界，那不是隶属关系是后门。排除它之后只剩双方动作，而邀请与加入已经是这个形状，不必另造 |
| **解除隶属任一方单方面即可** | 上一条、退出组织（双方都能发起） | 要双方同意才能解散，等于一方能绑架另一方。而解除不夺走任何人**拥有**的东西——转移过去的对方早已独立拥有，分享出去的本来就只是获权。既然没有东西被夺走，就没有理由要求对方点头 |
| **上级组织不进四层作用域** | 四层作用域的定义、「一个属性拓展」 | 按隶属链继承会使层数随组织结构变化，四层不再是四层；而且它把「隶属」悄悄变成「被管辖」——隶属关系是事实陈述，管辖权是另一回事，没有人裁决过后者。资产要流过去，走明确的动作 |
| **租户级资产的所有者是那个租户** | 四层里「租户级 = 我在这个组织里的私有部分」、§6.7 所有者与作者分开记 | 归属表原先只列了「组织范围创作」与「个人组织里创作」，租户范围这一行缺失。按租户级的定义，放在那里的东西还没交给任何人，所有者只能是该租户——否则「私有部分」就不成立 |
| **从租户范围提升到组织范围不可逆** | 上一条 | 提升即所有权易手。若可退回，「归组织」就成了随时能反悔的说法，组织对自己资产的支配权落空 |
| **隶属请求与加入组织的邀请，过期规则相同** | 2026-09-22 的过期裁决 + [发起—接受是同一个形状](design.md#隶属关系怎么建立与解除) | 正文早就把两者写成同一个形状：**一方发出、另一方接受才成立**。既然形状相同，**给其中一个定过期而另一个不定，就得解释为什么**——而没有任何依据支持这个区别。所以[写成一条规则管两者](design.md#两种邀约都会过期)。**同一天产品负责人进一步裁定两者是两种独立的对象**，见第一节——规则共用与对象独立并不冲突 |
| **发起者指定的时长是「发出这份数据时的一个参数」，不是一项[作用域](design.md#61-层次)配值** | [2026-09-22 的时长裁决](#一拍板记录)（原话从数据的角度给的：「邀约这个动作本质上是发出一份数据……四类有各自的默认值+动作发起者可自行填参覆盖」） | 它**只对这一份邀约成立**：跟着这份数据走，这份邀约结束它就不存在了。四层里配的是**对某个范围长期有效的值**，两者不是一回事。真把它当成配值，就得回答「组织级设的时长要不要覆盖发起者填的」——而那个问题不该存在：**填参的人就是发出这份数据的人**，没有第二个人跟他争这一格。所以它**不进四层**，也不需要合成语义 |
| **默认值按类分，不是四类共用一个** | 同上：「**四类**有**各自的**默认值」 | 裁决的措辞已经把这件事定死了。它本来也只能这样：一份等着新同事入职的邀请、一次并购谈判里的隶属请求、一份送资产过去的复制通知，合理的窗口长度本来就不同，共用一个数必然有一类被将就 |
| **具体数值仍不在产品这一层定** | 裁决只说「各有默认值」，没给数字 | 默认多少要按部署与客群调，写死一个数字就是把政策当成设计。产品该定的是**有没有这个出口、谁能改它、到期之后怎么收场**，三件都已经定死。与 [PF-003 那边同一口径](../PF-003-asset-transfer-and-sharing/decisions.md#二pm-推导) |
| **「组织不存在了就自动过期」现在不会触发，规则照样先立** | 裁决原话 + [团队组织本版没有解散路径](#四已知的来源问题) | 本版**不要求组织解散**，所以这条现在没有触发源。**个人组织确实有一条消失路径**——[随未激活账号到期清除](design.md#未激活的账号记录不会永久占着那个名字)——但它既**发不出邀请**、也**不参与隶属关系**，**没有任何邀约指向它**，所以那条路径不构成这里的触发源。**但它是裁决明确要的那一条**，而且它挡的是一个真实的坏结果——接受一份指向不存在的组织的邀约，**失败发生在对方点头之后**。**先立规则，比等到有了解散路径再回头补更安全**：那时补，已经写好的实现不会有人回头改 |
| **来源是层次的体现，不是独立维度** | 「official 不可禁用、可被实质相同的 customized 替代」 | 「不可禁用」等价于「出厂默认层不可清空」，「实质相同可替代」等价于「同能力标识覆盖」。两条都已经在资产合成规则里，把来源另立一维会产生第二套规则且必然与它冲突 |
| **并发收场落成「先成的成功、后成的被拒，提示与单次被拒相同」** | 2026-09-22 的并发裁决（原话从存储视角给的：「独立的一张表……通过锁来保护至少一个」） | 产品正文不能写「锁」「表」——那是产品之下怎么实现。把那句话翻成产品语言只有一个结果：**锁保护的是「至少一个」这条事实，所以两次同时的动作里只有一次能成立**，另一次撞上的是与单次被拒**同一条**前置条件，因此**看到的必须是同一句提示**（不然用户会以为遇到了另一种错误）。这样写出来的句子**在单机与分布式下完全一样**，正是 [SYS-DEPLOY](../../foundation/cross-system-constraints/requirements.md#sys-deploy)「不改变领域语义」要的那种表述 |
| **「至少一位有效超管」是不变量，不是每次动作各自检查的前置条件** | 上一条 | 若只是前置条件，两次动作各自检查都通过、合起来把超管清空，也说得过去——而那正是要排除的结果。**把它写成任何时刻都成立的事实**，两种收场就只剩一种 |
| **当前租户身份落成三句，不用「查询服务」「命令服务」这类词** | 2026-09-22 的当前租户身份裁决 | 产品负责人给的后半句是**技术分工**（query service / command service），[产品正文不表达它](../AGENTS.md#红线)。这句话在产品层**只剩三件可观察的事**：切换只影响此后新建的东西；已创建的对象持有创建那一刻的租户身份、此后一切以它计，直到那个租户身份失效；而「此刻是哪个租户身份」这项选择随登录状态走。**三句合起来与原话等价**，且每一句都能翻成用户能判断对错的场景 |
| **这项选择挂在登录状态上，不是一个对象** | 上一条 +「[账号不持有范围化对象](design.md#账号)」+「[登录后初始范围是个人组织](flows.md#12-登录)」 | 它没有自己的生灭——登录状态没了它就没了，重新登录得到的是重新从个人组织起算的一项新选择。放在账号上会让它跨登录持久，与 flows §1.2 给的初值矛盾；单独立成一个对象则要为它另造一套生灭，而那套生灭就是登录状态的生灭。**能挂成已有对象一项属性的，不另立对象** |
| **[邀请](../../domain_objects/objects.md#ul-invitation--邀请)的宿主是发出它的那个组织** | [flows §1.5](flows.md#15-邀请与加入)「发出它的那个组织不存在了，它随即自动过期」+ [§4 两种邀约都会过期](design.md#两种邀约都会过期) | 宿主的判据是「**谁没了，它就没了**」。正文明写这个组织没了它就到终点，而它**只能由这个组织发出、只能由这个组织撤回**；被邀请的账号在接受之前对它没有任何持有，账号本版也不会消失。**没有第二个候选**，所以宿主不再是「正文未述」 |
| **本版不做全设备撤销，逐个撤销已经够** | [2026-09-22 的读面裁决](#一拍板记录) | 那条裁决要解决的是「**看不见所以撤销不了**」。列表把那一半补上之后，剩下的一半——**撤销**——本来就有，只是要逐个点。**全设备撤销是省几下手，不是补一个洞**；本版按最小正确模型不做，将来要加是加法，不触动「撤销只及被指定的那一个」这条已定行为 |
| **凭据不同时的反馈，与「标识已被占用」完全相同** | 上面的留存期限裁决 + [登录标识部署内唯一](#二pm-推导) | 裁决只写了「**同标识同凭据**重来认回同一条」。凭据不同的那一半必然落回既有的那一行：标识被占着、又认不回来，**除了「这个名字已经有人用了」没有第二个答案**。写明它，是为了让实现不去发明一句「凭据不对」——那句话会把「这个标识上挂着一条未激活记录」暴露出去 |
| **留存期限是部署配置，不像[邀约时长](design.md#两种邀约都会过期)那样由发起者填** | 同上 + [邀约时长那条推导](#二pm-推导) | 两者看着像，差在**有没有一个能填这一格的人**。邀约有发起者，他最清楚这一份急不急，所以那一格留给他；**未激活记录的「发起者」恰恰是那个还没回来的人**，没有谁站在这里可以为它指定窗口。所以它只能是部署侧的政策。**它同样不进[四层作用域](design.md#61-层次)**——那里配的是对某个范围长期有效的值，而这是部署对半途而废的注册扣住名字多久 |
| **「未激活 → 不存在」不是账号终止，[本版无注销](design.md#非目标)这条不受影响** | 同上 + [账号与组织的终止列在非目标](design.md#非目标) | 被清掉的是一条**从未成为可用账号**的记录：[注册第 2 步](flows.md#11-注册)为它建的个人组织与第一个租户**从未承载任何东西**（未激活的账号不可交互），**随记录一起消失，不留任何归属**，清掉它不会让任何已发生的事实失去主人。而非目标那条讲的是**已激活的账号不会消失**——本版依然没有任何路径能做到那件事。两句话各说各的一段，不冲突 |
| **「有共同上级」的判据要把各自算进自己的上级链** | [PF-003 §5.2「边界是那棵隶属树」](../PF-003-asset-transfer-and-sharing/design.md#52-边界是那棵隶属树不是单个组织) + 本 topic [§4 组织](design.md#组织)原来的字面写法 | 上级链**不含自己**。照原来的字面读法，一个团队与它自己的上级公司，两条链（{公司}、{}∪上级）在祖先—后代这一对上给不出「真」——**团队与它所属的公司会被判成不在同一棵树上**，而 PF-003 明写那棵树就是边界。两处不能都对。**只有一个答案成立**：把各自算进来再求交，此后祖先—后代、兄弟—兄弟、同树任意两点，判出来都是「同树为真、出树为假」。这不推翻 PF-003，**PF-003 一直就是这个意思**；改的是本 topic 那句字面判据 |
| **个人组织那条推论在新判据下照样成立** | 上一条 + [个人组织的上级恒为空、也不能作别人的上级](design.md#个人组织) | 把自己算进来之后，一个个人组织的那条链上**只有它自己**。两个不同的个人组织，两条单元素链不相交，所以**任何两个个人组织仍然不会有共同上级**。这条推论不依赖「链为空」，依赖的是「链上除了自己什么都没有」 |
| **注册回执丢失的收场，由[提交点在第 3 步](flows.md#11-注册)直接给出** | 「注册以激活为单一提交点」 | 提交点一旦定死，「提交了但没看见回执」与「没提交」两者的状态就已经分开了：前者账号可用，后者停在未激活。**不需要新规则，只需要把这两种情形下用户该怎么办说出来**——前者直接登录，后者用同一标识继续。不写出来的后果是：他重试注册撞上「这个名字已经有人用了」，会以为系统出了错，而实情是他已经成功了 |
| **将来「可授予的管理权限」是加法，不推翻本版任何一条** | [「管理资格」是笔误那条裁决](#一拍板记录) | 本版把管理动作全部收在超管名下，**并没有说普通成员永远不能被授予其中某一项**。将来真要开这个口子，加的是「某项管理动作可以被授予」这一层，**超管仍然全部可做、普通成员的默认仍然是不可**——已定的两条行为一条不变。所以现在写死「不可」不是为将来关门，是**不替一个还不存在的授权机制先占一个格子**；那个格子一旦先占着，下游会照着实现一套没人定义过的「管理资格」 |
| **两类邀约的读面与「看已解除的成员」归入「管理类动作只归超管」那一句，有效成员那一份名单不归** | [2026-09-22 的两条可见性裁决](#一拍板记录) + [flows §4](flows.md#四角色与操作) 表下原有的分类 | 裁决给的是**谁能看**，没给**这几行算哪一类**——而表下那段正是按类讲的，不归类就会留下几行悬在分类之外。归法由裁决本身的结果决定，判据只有一条：**可见范围与哪个动作的范围重合**。两类邀约的可见范围**与撤回、接受那两个动作完全重合**，看见之后能接着做的事只有超管能做；「已解除的成员」这一面同理，**它与移除、再次邀请这两个动作重合**，普通成员看见一条已经失效的成员关系，一件事也不多做成。两者都是管理动作的读面。而**有效成员那一份名单的可见范围比任何一个管理动作都宽**（每一位有效成员都能看），它撑的是共事而不是管理，归进管理类会与裁决本身相抵 |
| **名单只给本组织这一层，不带任何人在别的组织里的事实** | 上一条 + 「[租户是归属与隔离的单位](design.md#租户)」+「[切换不把任何一层的事实复制到另一层](design.md#64-隔离)」 | 裁决说的是「**本组织**的成员名单」。一个人在别的组织里的成员关系属于**另一个租户**，本组织的任何角色都够不着它——把它带进名单，等于让一次组织内的读取跨过隔离边界。**只有一个答案成立**，不必上报 |
| **[隶属请求](../../domain_objects/objects.md#ul-affiliation-request--隶属请求)的宿主仍然是「正文未述」** | 同上的判据，用在隶属请求上**推不出结论** | 它的两端都是组织，而正文给的过期触发源是「**它指向的那个组织**」（[flows §1.7](flows.md#17-建立与解除组织隶属)）——**指的是接收方**；**发起方组织没了它怎么样，正文一个字没说**。「过期的触发源」也不等于「宿主」。两端都可能，正文只点了一端，**硬判一个就是替正文补空**。登记在[第四节](#四已知的来源问题) |
