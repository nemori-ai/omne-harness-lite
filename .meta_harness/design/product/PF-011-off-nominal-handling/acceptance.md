# PF-011 验收标准

---

## 一、可观察的场景

| # | 场景 | 通过的样子 |
|---|---|---|
| **S1** | agent 调的工具用不了，动作空间里有替代 | **它自己换一条路走了。处置一步都没走出 agent 那一步，运行与会话完全不知情** |
| **S2** | 额度用完，一次模型调用撞上 | **模型调用、agent、运行、会话，一层都不试**，处置直接从**租户**那一层起步 |
| **S3** | 一件事一路上交到头 | **每一次上交留下一条条目，它们并排存在**，后者不覆盖前者；照着它们看得出**经手的每一层**各做了什么 |
| **S4** | 承载那次运行的实例被回收，之后恢复 | **上交条目全都还在** —— 它们没有挂在实例的寿命上 |
| **S5** | 某一层反复失败很多次 | 模型上下文的增量**有上限，且不随失败次数增长**；阈值之前增量为零 |
| **S6** | 一件事发出去了，回音没了 | 上交条目里记的是「**外部效果不可确定**」，**不是失败，也不是没终态** |
| **S7** | 一次上交的条目写不下去 | **停住，并且这件事本身可见** —— 不是悄悄放过去 |
| **S8** | 把下层的错误码词表整个换掉 | **上层的处置分支输出一个字不变** |
| **S9** | 任何一层靠问人回到了主路径 | 它**没有上交** —— 问人是横切手段，不进阶梯 |
| **S10** | 再往树上加一层 | **四要素填得满**，且模型的四条规则不需要为它开特例 |
| **S11** | 租户层也了结不了 | **落终局**——**不上交给任何「组织层」**，条目里一个字都没跨出这个租户 |
| **S12** | 一次模型调用彻底失败 | 处置**越过「agent 的那一步」**直接到运行层，**没有卡在一个没有人的地方** |
| **S13** | agent 一步里模型调用和工具执行同时出了非常态 | **各交各的**（都交给 agent 的那一步），**互不干涉** |
| **S14** | 一次工具执行转后台 | 那是**工具执行层本层了结**，不产生上交条目；agent 的主路径照常往前 |

## 二、绝不能发生的事

| 绝不能 | 为什么 |
|---|---|
| **为一件这一层根本变不出来的东西反复重试** | 起点判据就是为挡这件事立的。白试一层的代价是真金白银 |
| **跳过中间某一层直接交到最外层** | 那一层的处置从此形同虚设，**而它本来可能有办法** |
| **一层交出去之后还继续往前走** | 上层的处置**落不到实处** —— 它改变不了一个正在动的东西 |
| **上交不留条目** | 恢复之后谁也说不清这件事被谁接过，**上层会重复下层刚试过的事而毫无察觉** |
| **上交时改写下层已经写下的条目** | 条目一旦写下就不再改变。要表达新情况，**追加，不是回头改** |
| **上交条目挂在会先消失的东西上** | 恢复之后依据随它一起没了，**而且不报错** |
| **把下层试过的东西整批塞进模型上下文** | 随失败次数单调增长，压不动就走终局 —— **一条为了让处置更好的规则，反而推着事情去死** |
| **上交条目里出现凭据、密钥、另一个租户的内容** | 条目不可变、记录不可擦除 —— **一次写错就是永久的** |
| **上层去解析下层的错误码或内部阶段名** | 下层改一个内部编码，上层当场坏掉 |
| **给非常态另建一套记录机制** | 双份登记必然分叉 |
| **只记成功与失败，没有「不可确定」** | 缺终态记录会被当成仍在运行 |
| **本 topic 里出现某一层已有处置形状的第二份定义** | 六种收场、卡片、装配失败各有其主，**这里只说「这件事在每一层都成立」** |
| **用「异常」当术语** | 它在这个仓库里已经有两个日常所指。正式词是[非常态](design.md#非常态) |
| **上交跨出租户这个边界** | 那条条目带着这个租户的内容，**交出去它的读者里就有别的租户** |
| **把「找超管处理」做成上交给组织层** | **那是问人，不是上交**——人不在这棵树上。两条路通向同一个人，**但一条搬了内容** |
| **接手方此刻不存在时就地卡住** | 事情会永远停在「已上交」，**而那一层本来就不可能有办法** |

## 三、判据

**怎么算这块设计站得住：**

1. **随便拿一件「不那么正常」的事，两个互不通气的人算出同一个起点。**
   算不一致的那一件，说明**判据还有洞**，不是那两个人的问题。
2. **六层里任取一层，它的四要素都填得满** —— 填不满的那一格说明这一层还没想清楚。
   **当前就有一格是空的**：[一次模型调用「本层了结得了什么」尚无 owner](design.md#92-模型调用那一层还没有-owner)。
   **它是一个已登记的缺口，不是这条判据被绕过去了。**
3. **加一层，四要素填得满，且不需要为它开特例。**
   **这不等于「一个字都不用改」**——rev 2 加三层时逼出了三处修订
   （主路径两种形态、树不是链、一层可能不存在）。
   **判据是「模型有没有为某一层破例」，不是「有没有动过笔」。**
4. **本 topic 里没有一张「非常态有哪些种」的清单。**出现了就是退回穷举，
   而穷举表[列出来的第二天就过期](design.md#57-这不是一张清单是一个判断)。
5. **每一条「绝不能」都举得出一个真实会违反它的做法** —— 举不出来的那条是想象出来的，删掉。

## 四、不验收什么

| 不验 | 归哪 |
|---|---|
| 重试几次、等多久、退避多少 | **策略** |
| 阈值提醒的阈值是多少、写多少字 | **策略** |
| 一条记录条目的结构与字段 | [PF-000](../PF-000-occurrences-and-record-entries/README.md) 与技术设计 |
| 六种收场各自长什么样 | [PF-006](../PF-006-tools-and-skills/README.md) |
| 卡片怎么出、池子怎么组织 | [PF-008](../PF-008-human-in-the-loop/README.md) |
| 装配缺东西怎么失败、沙箱起不来怎么办 | [PF-004](../PF-004-agent-definition-and-assembly/README.md)、[PF-005](../PF-005-execution-environments-and-sandboxes/README.md) |
| 落终局之后的实际后果 | **造成它的那件事自己的 topic**——落终局的是[那件非常态，不是承接它的那一层](design.md#八边界与依赖) |
| 一次模型调用失败了怎么办 | **尚无 owner**，见 [design.md §9.2](design.md#92-模型调用那一层还没有-owner) |
| 错误码词表 | **技术设计**，且上层不读它 |
