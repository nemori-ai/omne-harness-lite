## 二、PM 的推导

**以下不是任何人拍板的，是推出来的。推理链写在这里，可以被逐条验证或推翻。**

| 推导 | 从哪里推出来 |
|---|---|
| **agent 层没有独立的处置机制** | 把 agent 会撞上的事摆出来，形状完全一样——[六种收场全部以一条它读得懂的返回消息到达](../PF-006-tools-and-skills/design.md#55-一次工具执行的收场有六种)。所以这一层的处置就是「如实告诉它，它自己改道」，PF-006 已经定完，本 topic 只加「什么时候算它绕不动了」 |
| **层的顺序由生命周期的包含关系推出** | 不是排出来的。这条判据顺带解决了 agent runtime 为什么不是一层——**一个实例服务多次 run、一次 run 也可能换实例，它不在这条嵌套链上** |
| **起点看偏离在哪一层，不看谁撞见** | 额度用完是 agent 撞见的，但 agent 和 run 都变不出配额。按「谁撞见谁先处置」，这件事要白白浪费两层的处置 |
| **「了结得了吗」的判据是「缺的那样东西在谁手上」** | 这是「靠自己」这个说法唯一可操作的版本。第三种情况（手上有但用尽了）用同一条判据 |
| **给判据不给清单** | 同一种偏离这次了结得了、下次了结不了（有替代就绕，一个替代都没有就上交）。**穷举表列不全，且列出来第二天就过期** |
| **问人排不进阶梯** | 阶梯排的是**作用域的包含关系**，而人不在那条链上。（产品负责人的裁决与这条推导一致） |
| **「落终局」只有最外层能做** | 不是权限设计，是定义的推论：终局的意思就是「沿这条阶梯没人还能让它回到主路径」，**只有走到最外层才谈得上「没人了」** |
| **算不出起点时，从撞见它的那一层起步** | 算不准比白试一层贵。保守起步逐层往上，**最坏只是多过一道** |
| **「事件」与「异常」都不收为术语** | 两者都是被三种以上上下文占着的通用词。「事件」的处置见 [C-11](../../ubiquitous_language/conflicts.md)，「异常」见本文件第四节 |

### rev 2：加三层逼出的三处修订

**这三处都不是新增内容，是 rev 1 里没写明的假设被暴露出来。**

| 修订 | 哪一层暴露的 | 推理 |
|---|---|---|
| **主路径有两种形态**（推进式 / 稳态式） | **租户** | 租户不「走」什么，它是边界不是过程。一开始以为这说明它不该是层，**再想下去发现是 rev 1 的「从开始走到结束」偷偷夹带了「有终点」**。租户的主路径是「作为可用的归属边界持续成立」——**不推进到任何终点，但照样会偏离** |
| **层结构是树，不是链** | **模型调用 + 工具执行** | 两者都在 agent 一步之内，**互不包含，是兄弟**。判据本来就是「**包含**关系」，而包含关系天然形成树——**rev 1 只是一直用链的语言在说它** |
| **一层此刻可能根本不存在** | **模型调用** | 模型彻底失败时，**「agent 的那一步」根本没有发生过**。rev 1 的「往上不许跳」会把事情卡死在一个没有人的地方。**不许跳那条的初衷是「那一层本来可能有办法」，而一层此刻不存在就不可能有办法**——所以跳过它不违反那条规则的精神 |

**由此，rev 1 那句「多一层，多填一行，模型一个字不用改」被改掉了**：
新说法是「四要素填得满，**且不需要为它开特例**」——
**判据是模型有没有破例，不是有没有动过笔。**

### rev 2 的两条附带推导

| 推导 | 从哪里推出来 |
|---|---|
| **阶梯到租户为止** | 组织确实在租户外面，**但上交要留条目，而条目带着这个租户的内容**——交到「组织层」，读者里就有别的租户，撞 [SYS-TENANT](../../foundation/cross-system-constraints/requirements.md#sys-tenant)。[PF-005 在沙箱那一侧做过同一个判断](../PF-005-execution-environments-and-sandboxes/design.md#64-租户级沙箱共享的工作空间)。**「找超管处理」是问人不是上交**——人不在这棵树上 |
| **六种收场在阶梯上分三类** | 加了工具执行层之后掉出来的：**完成与不可用**＝走完主路径，**转后台**＝本层了结，**失败 · 被中断 · 等不到应答**＝上交给 agent。**这解释了「四种非完成里只有一种是失败」更深的理由**——剩下三种都是上交，但原因不同，所以 agent 接手后该做的事不同。**⚠ rev 2 定稿时把「不可用」也判成了上交，通读时改正，见[下一节](#通读时改正的一处归类不可用不是上交)** |

### 通读时改正的一处归类：「不可用」不是上交

**rev 2 定稿时，[收编表](design.md#六种收场在这个模型里各是什么)把「不可用」
和失败、被中断、等不到应答一起判成了「上交给 agent 那一层」。这一格判错了。**

**它犯的正是 [§5.5](design.md#55-起点偏离在哪一层不看是谁撞见的) 立下来要挡的那个错**——
按「谁把消息送出来」判位置，而不是按「谁的主路径偏了」判。
[changelog](changelog.md) 把收编表记在「顺带落定的两件事」之下，
**佐证它本来就不是一次按判据做的判断**。

**改正的依据里，最硬的一条是时序：**

> [替换件在 run 开始前就已经装好了](../PF-006-tools-and-skills/design.md#62-可用性在每次-run-开始前重算)
> （「可用性在每次 run 开始前重算」「不可用是运行期的状态，不是装配期的删除」）。
> **一个先于这次工具执行就已经成立的偏离，不可能以这次工具执行为起点。**

**其余佐证全在 rev 2 自己的正文里**——换句话说，**rev 2 只有收编表那一格不一致**：

| 哪一处 | 它怎么说 |
|---|---|
| [§5.6 第一行](design.md#56-了结得了吗看缺的那样东西在谁手上) | 「一个工具用不了 ｜ 一条能走的路 ｜ **动作空间里还有别的——agent 自己手上** ｜ **本层了结**」 |
| [§5.7](design.md#57-这不是一张清单是一个判断) | 「有替代，agent 绕过去；**一个替代都没有**，同样一件事就得上交」——**上交口在 agent → 运行** |
| [§5.4 工具执行那一行](design.md#54-各层的四要素) | 它的本层了结手段只有等待态与转后台，**清单里根本没有「不可用」** |
| [flows §1.2](flows.md) | 标题就叫「一个工具用不了（**agent 的一步了结**）」 |
| [PF-006](../PF-006-tools-and-skills/design.md#替换件) | 「替换件的应答**是正常返回**，不是错误」——工具执行层的主路径三步全发生了 |

**所以这不是 rev 1 与 rev 2 的两难，是一格归类错误。**曾经登记的那条待裁决随之撤销。

### 顺带定掉的：上交给 agent 那一跳，不另立条目

改正之后剩下的三种确实是上交，于是冒出一个真问题：
**除了那条 agent 必须读懂的返回消息，要不要再留一条 [§5.8](design.md#58-上交交的是什么) 条目？**

**不要，而且这不需要产品负责人拍板**——另立那条与三处已确认的内容矛盾：

| 依据 | 原话 |
|---|---|
| [PF-000](../PF-000-occurrences-and-record-entries/design.md#54-一件事什么时候产出不止一条条目) | 一件事产出多条条目**只有两个原因**：干预点先于结果、增量先于成品。**这一跳两个都不沾** |
| [§6.7](design.md#67-不为非常态另建记录机制) | 「另建一套的代价是双份登记，而**两份登记必然分叉**」 |
| [acceptance 的「绝不能」](acceptance.md) | 「**给非常态另建一套记录机制** ｜ 双份登记必然分叉」 |

**还有一条更直接的：另立的那条，读者答不出来。**
agent 读不到它（它不进模型上下文），剩下只有排查的人看——
**那正是[留痕](../PF-000-occurrences-and-record-entries/design.md#条目效力--entry-standing)，PF-000 早给它安了家。**

结论写进 [§5.8「接收方就是模型的那一跳」](design.md#接收方就是模型的那一跳)。

### 通读未决项时定掉的一条：终局的形状

**原来挂在未决项里的问法是「落终局之后，这个租户进入什么状态、用户看到什么」。
那个问法本身是错的**，所以它不该是未决项。

**推理链：**

1. [终局的定义](design.md#终局)说的是「**这件事的收场**」——
   落终局的对象是**那件非常态**，不是承接它的那一层。
2. 假设反过来，落终局要给租户加一个新状态。**立刻有两处讲不通**：
   - 同一个租户可能同时有好几件事落终局，**它要进入几个终局态？**
   - 一件运行级的事在租户层落了终局，**凭什么让整个租户变样？别的会话还在正常跑。**
3. 所以落终局不改变租户的任何属性。**真正改变状态的是造成这件事的原因**——
   配额耗尽是配额那边的状态，资产被禁是治理那边的状态。

**结论**（已写进 [§八边界与依赖](design.md#八边界与依赖)）：
**本 topic 只负责说「处置到此为止」，实际后果归造成它的那件事自己的 topic。**

### 被两份调研推翻的一处（保留，因为它解释了 §5.8 为什么是现在这个样子）

**PM 原来的倾向**：上抛时**必须带着下面那层试过什么、为什么不行**。理由是不带，上层会重复同样的尝试。

**两份独立调研都判它站不住，而且收敛到同一个替代版本。**

| 查到的 | 事实 |
|---|---|
| **外部先例** | 查了 11 个系统（5 个基础设施 + 6 个 agent harness），**把尝试列表放进跨边界对象的：0 个** |
| **有人明确拒绝并写了理由** | 一个把「完整耐久记录」当作全部产品价值的工作流引擎，明确不把重试写进历史，理由原文：**"This is to avoid filling the Event History with noise"**——一个失败 400 次的任务只产生 2 条事件 |
| **量化** | 每层原样带上下层正文：3 层 × 3 次重试 ≈ **43K token**；**4 层 ≈ 132K，直接撑爆**。改成每层只追加一条有界摘要 + 一个引用：3 层 ≈ 220 token，**8 层 ≈ 590 token** |
| **拐点的位置** | 差三个数量级，而**分界线正好落在「三层变四层」上**——而产品负责人明确说了层数会增加 |
| **内核的地基** | 内核**有 supervision tree 的形状，没有 supervision escalation 的语义**：fiber 父子链只管生命周期归属，失败不沿树上溯；内核自己的失败记录是单值覆盖式。**上交这件事内核一点都不免费提供** |
| **已有的相容性** | 「带着搬运已有记录」会撞 [PF-000 K2](../PF-000-occurrences-and-record-entries/design.md#62-k2依据的寿命不得短于要靠它重建的那个对象)与条目不可变；「带过程流水」会撞[帧不进模型上下文](../PF-009-context-message-types/README.md)与预算 |

**修正后的版本**（[§5.8](design.md#58-上交交的是什么)）：**交的是「下面试过的那些手段的身份与分类」，不是那些手段本身。**

**对原始动机的回答**：上游对「上层重复下层刚试过的事」这个问题的解法完全不同——
**内存里的计数器 + 阈值触发的一条定长提醒，阈值之前零成本**，而且明确**不跨 agent 边界共享**。
本 topic 采纳这个形状（[§6.4](design.md#64-要让-agent-知道只能走阈值触发的定长提醒)），**但不采纳「只在内存里」**——
那与我们自己的恢复接续要求不符。

### PM 对调研结论的两处修改

调研建议把「派发报告」与「替换件应答」列为本规则的**例外**。**PM 不采纳「例外」这个说法**：

| | 调研的说法 | 本 topic 的说法 |
|---|---|---|
| **派发报告** | 规则在这里降级为指引 | **它本来就不在这条链上**——被派出去的 agent 有自己独立的会话与运行，**它不是派发者的下一层** |
| **替换件应答** | 不可用不在适用范围 | **它是 agent 层了结成功的样子**——读懂了、绕路了，**根本走不到上交那一步** |

**理由**：列成例外，读者会以为它们本来该在阶梯上。**凡是需要列例外的地方，通常是边界画歪了。**
这么一改，本 topic 一条例外都不用列。

> **⚠ 这一行在 rev 2 里一度被收编表顶掉过，而顶错了。**
> 加工具执行层时，[收编表](design.md#六种收场在这个模型里各是什么)把「不可用」判成了上交——
> 但 **rev 2 自己的 §5.6、§5.7、§5.4、flows 与 acceptance 全都仍按这一行运作**，
> 不一致的只有那一格。通读时已改正，见[上面那一节](#通读时改正的一处归类不可用不是上交)。
> **这一行逐字仍然成立。**

## 四、已知的来源问题

### PS-1（已闭合）：「异常」一词有两个所指

**这笔债是 [PF-000 记下并指定在本 topic 清的](../PF-000-occurrences-and-record-entries/decisions.md#ps-2全链正文里异常一词有两个所指)。**

| 哪一处 | 用「异常」指什么 |
|---|---|
| [PF-006 正文](../PF-006-tools-and-skills/design.md)（五处） | **程序抛出的那种**（「异常不带语义」） |
| 十个 topic 的 `flows.md` 章节标题 | **不正常的情况**（「异常分支」） |

**处置**（与 [C-11「事件」](../../ubiquitous_language/conflicts.md)同一种）：

> **「异常」不收为术语，裸用时是白话。**正式词是[非常态](design.md#非常态)。

**三处各归各位，谁都不用将就谁**：

- 十份 `flows.md` 的「异常分支」**一个字都不用改**——那本来就是日常义。
- PF-006 那五处**改成「报错」**。它们想说的是「不要只给一个『出事了』的信号」，
  而「不用异常」只挡住了其中一种做法——**错误码、空返回、状态码同样违反那条产品约束**。
- 本 topic 用「非常态」。

**尚未完成的部分**：PF-006 那五处的回改**归其 owner，且要升 rev**，本 topic 不代改。

### PS-2（待复核）：一条内核机制条目的理由写错了

调研过程中发现 `design/basis/cordis/` 下有一条的**结论成立、机制说反了**：
它说异步监听者返回的 Promise 会让某种分发模式「认为没人否决而继续往下走」，
**而源码里那种情形会立刻返回那个 Promise 并停止**，后续监听者一个都不跑。

**该条目自己标着待核对主张，不得单独作为设计依据**，所以这是补一次核对，不是推翻已接受事实。
**归 basis 的 owner**，与本 topic 无关，记在这里只为不让它丢掉。

### PS-3（已闭合）：本 topic 曾用了一个还没有词条的概念

**「一次模型调用」在 rev 2 被立成一层，正文从 [§5.3](design.md#53-层的顺序不是排出来的是推出来的) 起一直在用它，
而当时[词表](../../ubiquitous_language/index.md)里没有这个词条。**

**这违反了「新概念先进词表，再进正文」那条红线，而且是本 topic 自己造成的，不是继承来的。**
不对称当时摆在明面上：同一棵树上的两个兄弟叶层，一次工具执行有词条，一次模型调用没有。

> **✅ 2026-09-19 闭合。**词条是
> [`UL-model-call` · 一次模型调用](../../ubiquitous_language/terms/execution-and-outcome.md#ul-model-call--一次模型调用--model-call)，
> 在 [PF-012 rev 2](../PF-012-agent-loop-and-run/changelog.md) 那一轮补的——
> **那一轮本来就要给方程里的每一步取名，查重与自检是连着走的，不是顺手捎带**。
> 出处同时指向本 topic §5.3 与 PF-012 §5.4，**「这一层失败了怎么办无主」已就地标在词条上**。

**记下不改掉**：红线是本 topic 破的，**闭合的时机比补上这件事本身更值得记**——
它说明「顺手补词条」的风险要靠**把它并进一次本来就要做的取名**来化解，
而不是靠下决心认真一点。

### PS-4（未登记）：PF-006 没说替换件应答算不算「一次工具执行」

[PF-006](../PF-006-tools-and-skills/design.md) 要求**每一次执行都留一份账**——跑了多久、耗了多少计算；
而[替换件](../PF-006-tools-and-skills/design.md#替换件)只回答「用不了 + 为什么」，
**大概率既不需要运行时，也不消耗计算**。

**本 topic 把「一次工具执行」当成树的叶子，所以这个洞会直接传到阶梯上**：
要么那个叶节点走完了自己的主路径，要么**这一次根本就没有叶节点**。

> **无论答案是哪个，[「不可用」不是上交](#通读时改正的一处归类不可用不是上交)这条结论都不变**——
> 两种情况下偏离都不在工具执行那一层。**所以它不阻塞本 topic。**

**PF-006 的未决项一栏写着「无」，这个洞目前没有登记处。归它的 owner。**

### PS-5（待裁决）：「会话授权上下文消亡」指的到底是什么

**[§5.6](design.md#56-了结得了吗看缺的那样东西在谁手上) 那一行写的是「会话授权上下文消亡 → 缺授权 → agent 和运行都变不出来 → 上交」，
而「消亡」这件事按现在已接受的说法不会发生：**

| 哪一处 | 怎么说的 |
|---|---|
| [PF-007 §4](../PF-007-meta-capabilities/design.md#会话授权上下文) | 它**是数据，不是活物**；只追加不回头改，**撤回也是往后再记一笔** |
| [PF-015 §6.7](../PF-015-session-lifecycle-and-ownership/design.md#67-归档不动授权) | **归档不动授权**——撤销归档之后原样还在 |
| [PF-008](../PF-008-human-in-the-loop/design.md) | 「本会话内这类都允许」**这个会话往后一直有效** |

**至少两种读法都讲得通，而它们指向不同的偏离**：
① **某一笔授权被撤回**，于是此刻算出来「不准」——偏离在**要用它的那一层**；
② **这个会话本身没了**——可按现在的模型，[会话没有终态](../PF-012-agent-loop-and-run/design.md#91-会话归-pf-015)，
这种情形是否存在要由[会话生命周期](../PF-015-session-lifecycle-and-ownership/README.md)那边定。

**记下不改掉，也不替它选一个。**这一行在 [changelog](changelog.md) 与本文件里都查不到出处，
**而两种读法会让实现去等完全不同的东西**：照①实施要等人再授权一次，照②实施要处理一个不存在的终态。
**判据一旦定了，[§5.6](design.md#56-了结得了吗看缺的那样东西在谁手上) 那一行要重写。**
