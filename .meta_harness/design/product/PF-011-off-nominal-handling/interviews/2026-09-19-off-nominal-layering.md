# 2026-09-19 · 从「异常不是报错」到一套与层数无关的模型

**参与**：产品负责人 · PM

---

## 一、开题第一句就把前提定死了

> 「这里我们必需先明确一点，所谓的『异常』**并不是单纯指程序运行的报错**，
> 而是指和通常情况下，或者说正常运行路径下相对而言不那么正常的情况。
> 这一点你能理解吗？**理解这一点是我们进行后续设计的关键。**」

PM 扫了 PF-001 到 PF-010，把凡是偏离主干的情况列出来——**十二类，只有一类会报错**：
用户叫停、停下来问人、能力够不着、等不到应答、恢复时记录停在奇怪的形状上、
agent 原地打转、上下文满了、结果太大要卸载、跨租户被拒、环境变了、agent 自己说做不下去。
**最后一类才是「工具真的挂了」。**

当时还找到一处刺眼的东西：PF-006 那句「**没有一种是以异常的形式抛给它的——异常不带语义**」，
里面的「异常」是 exception 的意思；**而它挡的那四种非完成收场，恰恰就是本 topic 意义上的异常**。
**同一句话里两个「异常」，意思正好相反。**这颗雷后来在命名那一步被拆掉。

## 二、中途岔去建了 PF-000，回来时地基变厚了

讨论到「异常与事件的关系」时，产品负责人先把事件划分体系立成了 PF-000。
等回到本 topic，前提句已经变成可操作的东西了：**每一种「不那么正常」的情况，
现在都要回答「留不留、留下的算什么」。**

## 三、二叠态：一句话定死了两者的关系

> 「首先 事件 和 异常 **互相不是包含的关系，而是一件事的二叠态**，
> 比如 工具执行转后台，它是一件事，所以是事件，
> 同时它又是一种非正常主路径下的状态，所以是异常」

PM 用四象限验了一遍，**四格全填得满**——其中最说明问题的是
「**在主路径上 × 留痕**」那一格（一次执行的账，正常得不能再正常，却不进下一步的计算）。
**如果两者是包含关系，这一格该是空的。**

由此掉出一条很实际的后果：**不需要为非常态另建一套记录机制。**

## 四、PM 推了一个问题出来，产品负责人用范围回答了它

PM 当时卡在一个地方：

> 「**偏离主路径，是相对于哪一层的主路径？**同一件事，在一层是异常，在另一层是正常。」
> 例：工具执行转后台，对那次工具执行是偏离；**对整个 run 完全正常**——转后台是设计好的能力。

产品负责人的回答是给范围：

> 「需要先明确对象，针对不同对象，异常的分层处理。具体来说……
> 对 agent 而言、对一次 run 而言、对一个 session 而言」

**范围一给，那个问题自动解了。**

## 五、一处歧义，一次纠正

PM 提出「agent」有两种读法，并给了判断（B：会思考的主体，不是运行实例），
理由是运行实例与 run 不是嵌套关系。

产品负责人的回复同时纠正了另一件事：

> 「**再次强调，假装 PF-012 不存在，不要读它，不要参考它。**B，问人横切三层不进阶梯，继续」

**「再次」两个字是有来由的**——PM 上一轮刚拿那份草稿里的一套框架当骨架用过。
那条作废之后，本 topic 的骨架全部从 PF-001～PF-010 与统一语言重建。

## 六、一条约束把模型逼干净了

> 「我们先考虑当前的三层，如果还有多的层，**理论上应该要能套同一套模型来推广**」

这一句比看上去要紧：**它意味着三层只能是实例，不能是模型本身。**
PM 据此把骨架改成「一层声明四样」，并顺带推出了一条判据——
**层序由生命周期的包含关系定**，而这条判据正好解释了运行实例为什么不是一层。

## 七、PM 那条倾向被两份调研推翻

PM 提了三件待定的事，产品负责人的处置是分开的：

> 「一 这个你得先分析（或者让 subagents）**技术上是否可以**；二 和 三 按你设计的倾向」

**第一件是「上抛时必须带着下面那层试过什么」。**两份独立调研（一份查外部先例与成本，
一份查我们自己的地基），**都判它站不住，而且收敛到同一个替代版本**。

关键事实：

- **11 个系统里，把尝试列表放进跨边界对象的：0 个。**
- 一个把「完整耐久记录」当作全部产品价值的工作流引擎**明确拒绝**，
  理由原文：**"This is to avoid filling the Event History with noise"**——
  一个失败 400 次的任务只产生 **2 条**事件。
- 另一个基础设施把上一次失败记成**恰好一条**，第 N 次重启时第 N-2 次被不可逆覆盖。
- **量化**：每层原样带正文，三层约 43K token，**四层约 132K——直接撑爆**；
  只带身份与分类，**八层仍约 590 token**。**差三个数量级，拐点正好在「三层变四层」。**
- **内核有 supervision tree 的形状，没有 supervision escalation 的语义**——
  失败不沿 fiber 树上溯，内核自己的失败记录是单值覆盖式。**上交这件事内核一点都不免费提供。**

对原始动机（「不带，上层会重复下层刚试过的事」）的回答，上游早就交付过一个：
**内存计数器 + 阈值触发的一条定长提醒，阈值之前零成本**，而且明确**不跨 agent 边界共享**。
本 topic 采纳这个形状，**但不采纳「只在内存里」**——那与恢复接续的要求不符。

### PM 没有全盘采纳调研的两处

调研建议把「派发报告」和「替换件应答」列为规则的**例外**。PM 改成了别的说法：
**派发报告本来就不在这条链上**（被派出去的 agent 有自己独立的会话与运行），
**替换件应答是 agent 层了结成功的样子**（读懂了、绕路了，根本走不到上交那一步）。

> **凡是需要列例外的地方，通常是边界画歪了。**这么一改，本 topic 一条例外都不用列。

另外调研里有一处说「你在任务里提到某标准禁止把调试信息发给不可信客户端」——
**PM 没说过那句话**。它更正的事实本身是对的，但那不是 PM 给的前提。
**subagent 的话不能全盘照收。**

## 八、命名，以及顺带还掉的一笔债

「异常」在这个仓库里已经有两个日常所指，[PF-000 把它记成 PS-2 并指定在本 topic 清](../../PF-000-occurrences-and-record-entries/decisions.md)。

PM 给的方案与 [C-11「事件」](../../../ubiquitous_language/conflicts.md)相同：
**不收「异常」为术语，改给正式概念立名**。三个候选：

| | 中文 | English | PM 的评价 |
|---|---|---|---|
| 甲 | 偏离 | `Deviation` | 最直白，轻微撞名风险 |
| 乙 | 路径偏离 | `Path Deviation` | 最安全，但四个字会被人自动缩成两个字 |
| **丙** | **非常态** | **`Off-Nominal`** | **精确表达「不是坏了，只是不在标称路径上」**；中文读着生 |

PM 当时推的是甲。产品负责人选了丙：

> 「用 非常态」

**丙确实更准**——本 topic 第一句话要说的就是「它不是报错」，
而航天那套 nominal / off-nominal 本来就是为这件事造的词。
