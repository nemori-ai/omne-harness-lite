## rev 2 · 2026-09-19 · 加三层，模型被逼出三处修订

### 产品负责人先问了一句，然后给了范围

> 「那么现在，能加上第四层，租户 吗？」
>
> 「**往上，租户层，同时往下，多一个模型层**」
>
> 「工具执行加」

**这是对 rev 1 那句「将来多一层，多填一行，模型一个字不用改」的检验。**
结果是：**模型站住了，但那句话说轻了。**

### 新的三层

```text
租户                身份持续可用（稳态式）
 └─ 会话
     └─ 运行
         └─ agent 的一步
             ├─ 一次模型调用     ← 新
             └─ 一次工具执行     ← 新
```

租户这一层往上加，模型调用与工具执行往下加。**加的过程逼出三处修订**——
每一处都是 rev 1 里一个没写明的假设。

### 修订一：主路径有两种形态

**租户不「走」什么**，它是一个边界，不是一个过程。

一开始以为这说明租户不该是层，再想下去发现是
**rev 1 的「从开始走到结束」偷偷夹带了「有终点」**：

| 形态 | 谁 |
|---|---|
| **推进式** | 会话 · 运行 · agent 的一步 · 模型调用 · 工具执行 |
| **稳态式** | 租户——**持续成立的那个状态**，不推进到任何终点 |

### 修订二：层结构是树，不是链

**模型调用与工具执行互不包含，是兄弟不是父子。**

好在判据本来就是「生命周期的**包含**关系」，而包含关系天然形成树——
**只是 rev 1 一直用链的语言在说它**。rev 2 写明：**「外面一层」＝ 树上的父节点**。

### 修订三：一层此刻可能根本不存在

**模型调用彻底失败时，「agent 的那一步」根本没有发生过**——
agent 就是模型，模型没给出回复，那个会思考的主体此刻不在那里。

rev 1 的「往上不许跳」会把事情卡死在这里。补的规则是：

> **接手的那一层此刻不存在时，直接交给再外面一层。这不算跳级。**

不许跳那条立的初衷是「那一层本来可能有办法」，而**一层此刻不存在，它就不可能有办法**。

### 顺带落定的两件事

**一、六种收场在阶梯上各是什么**（[§5.4](design.md#54-各层的四要素)）——
加了工具执行层之后，[PF-006 那六种](../PF-006-tools-and-skills/design.md#55-一次工具执行的收场有六种)不再是平的六种：

| | |
|---|---|
| **完成** | 工具执行层走完了主路径 |
| **转后台** | 工具执行层**本层了结** |
| **失败 · 被中断 · 等不到应答** | **上交给 agent 那一层** |

**这是收编，不是重定**——六种收场的定义全在 PF-006，本 topic 一个字不改。

> **这张表定稿时多判了一格**：「不可用」当时也被放进了上交那一行，
> **而它其实也是走完主路径**。通读时改正，依据记在
> [decisions.md](decisions.md#通读时改正的一处归类不可用不是上交)。

**二、阶梯到租户为止**（[§6.8](design.md#68-阶梯到租户为止)）。
组织确实在租户外面，**但上交要留条目，而条目带着这个租户的内容**——
交到「组织层」，读者里就有别的租户，直接撞
[SYS-TENANT](../../foundation/cross-system-constraints/requirements.md#sys-tenant)。
[PF-005 在沙箱那一侧做过同一个判断](../PF-005-execution-environments-and-sandboxes/design.md#64-租户级沙箱共享的工作空间)（「没有组织级沙箱，三个层级是穷尽的」）。

**那「找超管处理」算什么？算问人，不算上交**——人不在这棵树上。

### rev 1 那句话怎么改的

| rev 1 | rev 2 |
|---|---|
| 「将来多一层，多填一行，**模型一个字不用改**」 | 「一层只需声明四样」+ **明说加三层逼出了三处修订** |
| 验收判据「加一层，四条规则**一个字不用改**」 | 「四要素填得满，**且不需要为它开特例**」——**判据是有没有破例，不是有没有动笔** |

### 一个新发现的缺口

**「一次模型调用失败了怎么办」现在没有主**（[§9.2](design.md#91-模型调用那一层还没有-owner)）。
五个 topic 提到「模型请求」，全是拿它当边界标记用，**没有一个拥有它**。
本 topic 只给它位置和骨架，**手段归它自己的 topic**。

### rev 2 定稿之后的一次通读

**含义没有改变，所以不升 rev。**通读补的是「插进新内容时没回头改的旧句子」，
其中几处已经构成前后矛盾：

| 补了什么 | 为什么不算改含义 |
|---|---|
| §5.2 与[§七取舍](design.md#七取舍)里「多填一行，一个字不用改」的原句 | **rev 2 已经推翻过它**（见上面「rev 1 那句话怎么改的」），只是正文没跟着改 |
| §5.1 的「四种组合」与「左下角那一格」 | 效力三档 × 两个面是**六格**；而「左下角」指的那一格，已经被新加的瞬态行顶走了 |
| [acceptance](acceptance.md) S2 的起点还写着会话层 | [§5.5](design.md#55-起点偏离在哪一层不看是谁撞见的) 早把这个例子的起点判给了租户 |
| [§5.4](design.md#54-各层的四要素) 的表只有三列却叫「四要素」 | 补上「终局」列，与 [flows §三](flows.md) 的同类表对齐 |
| [flows](flows.md) 1.4 的「四条上交条目」 | 留条目的是**三次上交**——落终局那一步不是上交 |
| 剩下的 `run` / `session`，以及「那条链」 | 术语中文化与「链改树」都没做干净 |

**通读还翻出一格归类错误并改正了它**：收编表把「不可用」判成了上交，
**而它其实也是走完主路径**——偏离在 agent 那一步，起点也在那里。
依据与五条佐证记在 [decisions.md](decisions.md#通读时改正的一处归类不可用不是上交)。
顺带定掉了[上交给 agent 那一跳不另立条目](decisions.md#顺带定掉的上交给-agent-那一跳不另立条目)。

### 随后的一次未决项清理

**七条筛到两条，没有一条需要产品负责人拍板。**

| 原来的七条 | 去向 |
|---|---|
| 「用尽」的次数 · 阈值提醒的阈值 · 寿命宿主要不要加取值 | **假缺口**——结论在别处已有，复述到未决项会被读成「这里还有个洞」 |
| 终局的形状 | **问法本身错了**，[自行定掉](decisions.md#通读未决项时定掉的一条终局的形状)：落终局的是那件非常态，不是承接它的那一层 |
| 工具交回「不可用」算不算上交 | **归类错误**，改正后撤销（见上） |
| 与那份草稿的地盘交割 | **保留**——被「全程不参考那一份」这条约束锁住，交割要单独做 |
| 模型调用那一层没有 owner | **保留，但形状查清了**：四面都有邻居划好界，[缺口是闭合的](design.md#91-模型调用那一层还没有-owner) |

清理中还翻出两笔账：[PS-3](decisions.md#ps-3已闭合本-topic-曾用了一个还没有词条的概念)（本 topic 用了一个没有词条的概念，
**违反红线，自己造成的**）与 [PS-4](decisions.md#ps-4未登记pf-006-没说替换件应答算不算一次工具执行)（PF-006 的一个洞，不阻塞本 topic）。

## rev 1 · 2026-09-19 · 首次成文

### 开题前先摆正的一件事

产品负责人开题第一句就把前提定死了：

> 「所谓的『异常』**并不是单纯指程序运行的报错**，而是指……**正常运行路径下相对而言不那么正常的情况**。
> 这一点你能理解吗？**理解这一点是我们进行后续设计的关键。**」

扫过 PF-001 到 PF-010，凡是偏离主干的情况列出来有十二类，**只有一类会报错**。
按「报错」理解，做出来的会是一套错误码与重试策略，
而 [PF-006 那一轮裁决](../PF-006-tools-and-skills/decisions.md)挡的正是这件事。

### 这一版定了什么

| | 内容 |
|---|---|
| **两个概念的关系** | 非常态与发生的事**是同一件事的两个面**，不是包含关系 → **不为非常态另建记录机制** |
| **层数无关的骨架** | 一层声明四样：[主路径 · 本层了结得了什么 · 交给谁 · 终局](design.md#52-一层要声明四样) |
| **层序怎么定** | [生命周期的包含关系](design.md#53-层的顺序不是排出来的是推出来的)，**推出来的不是排出来的** |
| **起点** | [偏离在哪一层，不看是谁撞见的](design.md#55-起点偏离在哪一层不看是谁撞见的) |
| **了结得了吗** | [看缺的那样东西在谁手上](design.md#56-了结得了吗看缺的那样东西在谁手上)；第三种情况是「手上有但用尽了」 |
| **阶梯规则** | 起点可任意层 · **往上不许跳** · **上交即打断** |
| **上交带什么** | [身份与分类，不搬运正文](design.md#58-上交交的是什么)，七条细则 |
| **问人** | [横切所有层，是了结手段不是一层](design.md#59-问人横切所有层) |
| **一条验收办法** | **把下层的错误码词表整个换掉，上层的处置分支输出不变** |

### 「非常态」这个名字，以及它顺带还掉的一笔债

「异常」在这个仓库里已经有**两个**日常所指——PF-006 正文里指程序报错，
十个 topic 的 `flows.md` 章节标题里指不正常的情况。
[PF-000 把这笔债记成 PS-2 并指定在本 topic 清](../PF-000-occurrences-and-record-entries/decisions.md#ps-2全链正文里异常一词有两个所指)。

处置方式与 [C-11「事件」](../../ubiquitous_language/conflicts.md)相同：
**「异常」不收为术语，裸用时是白话；正式词取「非常态」。**

产品负责人在三个候选里选了它。中文「非常态」配英文 `Off-Nominal`——
**航天那套 nominal / off-nominal 本来就是为「不是坏了，只是不在标称路径上」造的**，
而这正是本 topic 第一句话要说的事。

**十份 `flows.md` 一个字都不用改；PF-006 那五处待其 owner 改为「报错」并升 rev。**

### 中途被推翻的一处

**PM 原来的倾向是「上抛必须带着下面那层试过什么」。两份独立调研都判它站不住：**

- **11 个系统里，把尝试列表放进跨边界对象的：0 个。**
- 一个把「完整耐久记录」当作全部产品价值的工作流引擎明确拒绝，
  理由原文：**"This is to avoid filling the Event History with noise"**。
- 量化：带正文**三层 43K token、四层 132K 直接撑爆**；只带身份与分类，**八层仍约 590 token**。
  **拐点正好落在「三层变四层」上**，而产品负责人明确说了层数会增加。

修正后的版本见 [§5.8](design.md#58-上交交的是什么)。推理链与两份调研的关键事实
记在 [decisions.md 第二节](decisions.md#被两份调研推翻的一处保留因为它解释了-58-为什么是现在这个样子)。

### 本轮全程未参考 PF-012

产品负责人两次明确要求。两份调研的提示词里也下了同样的硬约束，
**两位调研者都报告说没有打开过它**（有一位读到指向它的链接文本，按约束没有跟进）。

`product/README.md` 登记着本 topic 的地盘目前由那份草稿暂时拿着、「将来可能整块移交」——
**交割要单独做一次，且必须有人同时看两边**，本 topic 不单方面宣布取代。
