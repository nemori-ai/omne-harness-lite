# PF-011：非常态的分层处置

**rev 3**

---

## 一、背景与问题

**系统里「不那么正常」的情况，比正常的情况种类多得多。**

用户叫停、能力够不着、等不到回音、执行转到后台、上次能用的这次不能用、
沙箱换了地方、人拒绝了一次请示、装配缺了一样东西、额度见底——
**这些每一件都要有人接住**。

在此之前，它们各自有主：PF-006 定了工具那一层的六种收场，
PF-008 定了停下来问人的那条路，PF-004 定了装配缺东西怎么办，
PF-005 定了沙箱起不来怎么办。**没人回答的是三个更根本的问题：**

- **谁先接？**同一件事，agent 能绕就绕过去了，用不着惊动任何人；
  可要是它绕不过去呢？
- **接不住往哪交？**交上去的又是什么？
- **交到头还是不行，怎么收场？**

不回答，结果是可以预见的：**每一层都试着处置每一件事**。
agent 为一件它根本变不出来的东西反复重试，运行为一件早该终局的事一遍遍重来，
而真正能解决它的那一层从头到尾没被惊动。

**本 topic 把这三个问题回答掉，并且回答成一套与层数无关的模型。**

---

## 二、目标与非目标

### 目标

1. **定义非常态**，并把它和「报错」彻底分开。
2. **给出一层的四要素**：主路径、本层了结得了什么、交给谁、终局。
3. **定处置的起点与走向**：从哪一层开始、怎么往外走、能不能跳。
4. **定上交时交的是什么**。

### 非目标

| 不在本 topic | 归哪 |
|---|---|
| **穷举有哪些非常态** | **各自的 topic。**本 topic 给判据，不给清单——[判据不是清单](#57-这不是一张清单是一个判断) |
| **某一层已有的处置形状** | 六种收场归 [PF-006](../PF-006-tools-and-skills/README.md)、问人那条路归 [PF-008](../PF-008-human-in-the-loop/README.md)、装配失败归 [PF-004](../PF-004-agent-runtime-assembly-and-liveness/README.md)、沙箱起不来归 [PF-005](../PF-005-execution-environments-and-sandboxes/README.md) |
| **一条记录条目长什么样** | [PF-000](../PF-000-occurrences-and-record-entries/README.md) |
| **怎么组装、怎么压缩** | [PF-010](../PF-010-context-management-and-assembly/README.md) |
| **重试几次、等多久、退避多少** | **策略，不是产品设计。**本 topic 只说「手段用尽了就上交」 |
| **错误码词表** | 技术设计。**本 topic 明确要求上层不读它**（[§6.5](#65-上层只认跨层通用的说法)） |

### 主路径

**一层在没有任何非常态时，本该是什么样子。**

它有**两种形态，都算主路径**：

| 形态 | 长什么样 | 谁是这样 |
|---|---|---|
| **推进式** | 从开始走到结束 | 会话 · 运行 · agent 的一步 · 一次模型调用 · 一次工具执行 |
| **稳态式** | **持续成立的那个状态**，不推进到任何终点 | 租户 |

**稳态式照样会偏离。**租户的主路径是「**它作为可用的归属边界持续成立**」——
成员用得上名下的东西、配额够、隔离没破；**这三样任何一样不成立，它就偏离了**。

> **不写明这两种形态，下一个人给租户那一层填四要素时会卡在第一格**——
> 因为「从开始走到结束」这个说法偷偷夹带了「有终点」。

**主路径是这一层自己的路**：同一件事，可能让里面那一层偏离了主路径，
而外面那一层照走不误。

> **英文用 `Nominal Path`。**中文取好懂的「主路径」，
> 英文取航天那套 nominal / off-nominal 的惯用配对——**两边各自成立，不是互译。**

### 非常态

**某一层此刻不在它的主路径上。**

**它是一个状态，不是一类事。**造成它的那件事照样是一件[发生的事](../PF-000-occurrences-and-record-entries/design.md#发生的事)，
照样产出记录条目、照样有效力和寿命宿主——**同一件事的两个面，不是两样东西**（[§5.1](#51-非常态与发生的事是同一件事的两个面)）。

**它与「报错」无关。**绝大多数非常态不报错（[README 那张表](README.md#非常态不是报错)），
而有些报错根本不构成非常态——一个工具内部捕获并自行重试成功，主路径一步没偏。

### 本层了结

**这一层不需要外面那一层给任何东西，就能继续走完自己主路径。**

> **「外面那一层」是字面意思，限于[树上的父节点](#53-层的顺序不是排出来的是推出来的)。**
> [问人](#59-问人横切所有层)和[等一个外部应答](../PF-006-tools-and-skills/design.md#等待态)都不是「外面那一层给的」，
> **所以靠它们回到主路径，照样算本层了结。**

**不是「恢复原样」。**工具用不了、agent 绕道走别的路，那个工具并没有变回可用；
**主路径继续往前走了，就算这一层了结了它。**

判据见 [§5.6](#56-了结得了吗看缺的那样东西在谁手上)。

### 上交

**一层了结不了一个非常态时，把处置权交给外面一层。**

**「外面一层」＝ [树上的父节点](#53-层的顺序不是排出来的是推出来的)**——
因为层之间是包含关系，而包含关系形成的是树，不一定是一条链。

> **英文用 `Escalation`。**中文不用「升级」——那个词在版本与权限语境里都有正常用法。

上交是一个**动作**，它本身也是一件[发生的事](../PF-000-occurrences-and-record-entries/design.md#发生的事)，
产出它自己的记录条目（[§5.8](#58-上交交的是什么)）。

### 终局

**最外面一层也了结不了时，这件事的收场。**

**终局不是失败的同义词。**它说的是「**一路往外交到头，没有哪一层还能让它回到主路径**」——
至于这算不算失败，由落终局的那一层按自己的语义决定。

## 五、模型

### 5.1 非常态与发生的事，是同一件事的两个面

**两个面互不决定，六种组合都成立：**

| | **在主路径上** | **偏离主路径** |
|---|---|---|
| **依据** | 用户发来一条消息 · 模型给出回复 | **执行转到后台** · 用户叫停 · 人答复了请示 |
| **留痕** | **那次执行的账**（正常得不能再正常，但不进下一步的计算） | 调用没成、准备重来 |
| **瞬态** | 界面上的流式增量 | 「后台那个跑完了」的提示 |

**「留痕 × 在主路径上」那一格最能说明问题**：一件完全正常的事，效力却只是「留痕」。
**如果两者是包含关系，这一格该是空的。**

由此掉出一条很实际的后果：

> **不需要为非常态另建一套记录机制。**它的记录跟正常的事一模一样——
> 同样是记录条目、同样有效力与寿命宿主、同样过 [PF-000 的三条禁格](../PF-000-occurrences-and-record-entries/design.md#六产品规则)。

### 5.2 一层要声明四样

**这是本 topic 的全部模型。**

| # | 这一层要答 |
|---|---|
| **1** | **主路径**——正常情况下它怎么走完 |
| **2** | **本层了结得了什么**——哪些偏离它不用求人就能继续 |
| **3** | **了结不了交给谁**——外面那一层是谁 |
| **4** | **终局**——如果外面没有了，怎么收场 |

**模型不认层数。**[当前分解出的六层](#54-各层的四要素)是实例，不是模型——
再多一层，它照样只需答这四样。

> **但这不等于「加一层一个字都不用改」。**rev 2 往上加租户、往下加模型调用与工具执行时，
> 逼出了三处修订：[主路径有两种形态](#主路径)、[层结构是树不是链](#53-层的顺序不是排出来的是推出来的)、
> [一层此刻可能根本不存在](#61-起点可以是任何一层往上不许跳)。
> **站住的是「没有为哪一层破例」，不是「没有动过笔」**——经过记在 [changelog](changelog.md)。

### 5.3 层的顺序不是排出来的，是推出来的

> **判据：生命周期的包含关系。**

**包含关系形成的是一棵树，不一定是一条链**——
agent 的一步里既有一次模型调用、又有一次工具执行，
**这两样互不包含，是兄弟不是父子**：

```text
租户
 └─ 会话
     └─ 运行
         └─ agent 的一步
             ├─ 一次模型调用
             └─ 一次工具执行
```

**「外面一层」＝ 树上的父节点。**处置沿树往根走，
兄弟之间各交各的父节点，**互不干涉**。

> **树是全局的形状，而一件非常态实际走的是其中一条路**——
> 从它起步的那一层，沿父节点一直到根。**下文把这条路叫「阶梯」。**

这条判据顺带回答了一个容易搞错的问题：**[运行实例](../../ubiquitous_language/terms/agent-runtime-loop.md#ul-agent-instance--运行实例--agent-instance)为什么不是一层。**

一个实例可以服务多次运行，一次运行也可能换实例，**它根本不在这棵树上**。
它是运行的承载物，**生死由运行那一层处置**。

**树的两端是硬的，理由不一样：**

| | 到哪为止 | 为什么 |
|---|---|---|
| **根** | **租户** | 组织确实在租户外面，**但处置权不能往那儿交**——见 [§6.8](#68-阶梯到租户为止) |
| **叶** | 目前是模型调用与工具执行 | **不是原则上的底**，只是当前分解到这里。**再往下分解出新的层，模型照样成立** |

### 5.4 各层的四要素

**当前分解出六层。**这张表是**实例**，不是模型——
[模型只认四要素，不认层数](#52-一层要声明四样)。

| 层 | 主路径 | 本层了结得了的 | 交给谁 | 终局 |
|---|---|---|---|---|
| **租户** | **稳态**：作为可用的归属边界持续成立 | 补配额 · [在别处重建租户级沙箱](../PF-005-execution-environments-and-sandboxes/design.md#64-租户级沙箱共享的工作空间) · 重新启用被禁的资产 | **没有人可交**（[§6.8](#68-阶梯到租户为止)） | **落终局——只有它做得了** |
| **会话** | 建立 → 一次次运行 → 一直可用 | 重算可用性让下次运行换个动作空间 · 换个地方重建执行环境 | 租户 | —— |
| **[运行](../PF-012-agent-loop-and-run/design.md#run)** | [触发 → 备好一副身子 → agent 一步步走 → 收束](../PF-012-agent-loop-and-run/design.md#56-状态转移表) | 重建一副身子 · 缺可选的照装并标明 · 腾出上下文空间 | 会话 | —— |
| **[agent 的一步](../PF-012-agent-loop-and-run/design.md#agent-的一步)** | 看到处境 → 决定做什么 → 做 → 看到结果 → 再来 | 换一条路 · 换个方法 · 先干别的 · 不做了换方向 · 分页取回 | 运行 | —— |
| **[一次模型调用](../../ubiquitous_language/terms/execution-and-outcome.md#ul-model-call--一次模型调用--model-call)** | 发出请求 → 流式回来 → 完整的一份回复 | **未定**——这一层[尚无 owner](#92-模型调用那一层还没有-owner) | agent 的一步 | —— |
| **一次工具执行** | 调用 → 执行 → 把结果交回去 | [进等待态等一个应答](../PF-006-tools-and-skills/design.md#等待态) · [转后台](../PF-006-tools-and-skills/design.md#55-一次工具执行的收场有六种)（声明允许时） | agent 的一步 | —— |

**只有租户那一行的「终局」是实的**，因为[只有走到根，才谈得上「外面没有层了」](#68-阶梯到租户为止)。

> **agent 那一层的「了结」，PF-006 已经定完了。**无论下面那次执行是什么收场，
> **agent 拿到的[全都是一条读得懂的返回消息](../PF-006-tools-and-skills/design.md#55-一次工具执行的收场有六种)**，
> 读懂了就自己绕路。这一层不需要新机制，本 topic 只加一件事：
> **什么时候算它绕不动了。**

#### 六种收场，在这个模型里各是什么

**把[六种收场](../PF-006-tools-and-skills/design.md#55-一次工具执行的收场有六种)放进阶梯，
它们不再是平的六种，而是三类：**

| 收场 | 在模型里是什么 |
|---|---|
| **完成** | 工具执行层**走完了自己的主路径** |
| **不可用** | **也走完了主路径。**[替换件是正常返回](../PF-006-tools-and-skills/design.md#替换件)，而且它[在 run 开始前就装好了](../PF-006-tools-and-skills/design.md#62-可用性在每次-run-开始前重算)——**偏离的是 agent 那一步，起点也在那里**（[§5.6 第一行](#56-了结得了吗看缺的那样东西在谁手上)） |
| **转后台** | 工具执行层**本层了结**——它不再占着这一步，agent 的主路径照常往前 |
| **失败 · 被中断 · 等不到应答** | **上交给 agent 那一层** |

**这解释了 PF-006 那句「四种非完成里只有一种是失败」更深的理由**：
剩下三种都是上交，**但上交的原因不同，所以 agent 接手之后该做的事完全不同**。

> **「不可用」这一格，rev 2 定稿时归错过一次。**
> 当时把它和另外三种一起判成了上交，**而那正是 [§5.5](#55-起点偏离在哪一层不看是谁撞见的) 立下来要挡的错**——
> 按「谁把消息送出来」判位置，而不是按「谁的主路径偏了」判。
> 经过与改正依据记在 [decisions.md](decisions.md#通读时改正的一处归类不可用不是上交)。

**上交给 agent 的那三种，条目就是那条 agent 必须读懂的返回消息本身**，
不另立一条（[§5.8](#58-上交交的是什么) 末尾）。

> **这是收编，不是重定。**六种收场的定义、形状、语义全在 PF-006，
> 本 topic 一个字不改，只说明它们在阶梯上各站在哪。

### 5.5 起点：偏离在哪一层，不看是谁撞见的

**这一条如果不先说清楚，阶梯会从错的地方起步。**

> **额度用完了**，是一次模型调用撞上的，
> 但它偏离的是**租户**的主路径——[使用成本按租户归属](../../ubiquitous_language/terms/subjects-and-ownership.md#ul-tenant--租户--tenant)，
> 这个租户本来该一直用得上自己名下的东西。

按「谁撞见谁先处置」，这件事要让**模型调用重试一轮、agent 的一步换条路试试、
运行换一副身子、会话重算一次可用性**——**四层各做一次注定无用的处置**，
才轮到真正能了结它的那一层。

**层越多，这个错误越贵。**

**所以起点由 [§5.6 的判据](#56-了结得了吗看缺的那样东西在谁手上)定，可以直接落在任何一层。**

### 5.6 了结得了吗：看缺的那样东西在谁手上

| 偏离 | 这一层缺什么 | 谁手上有 | 结果 |
|---|---|---|---|
| 一个工具用不了 | 一条能走的路 | **动作空间里还有别的**——agent 自己手上 | **本层了结** |
| 运行实例没了 | 一副身子 | **装配的能力就在运行这一层** | **本层了结** |
| 上下文满了 | 空间 | 压缩就在这一层 | **本层了结** |
| 装配缺**必需**的资产 | 那个资产 | 这一层拿不到 | **上交** |
| 额度用完 | 配额 | **只有租户那一层给得了** | [**起点直接在租户层**](#55-起点偏离在哪一层不看是谁撞见的)，而配额就在它手上——**本层了结** |
| 会话授权上下文消亡 | 授权 | agent 和运行都变不出来 | **上交** |
| 模型所有路由都失败 | 一个能用的模型 | **这一层拿不到** | **上交，且按[「接手那层不存在」的例外](#61-起点可以是任何一层往上不许跳)越过 agent 那一层**——模型没给出回复，**那个会思考的主体此刻不在那里** |

**还有第三种情况，同一条判据管用：手上有，但用尽了。**

> agent 还有别的路可走 → 本层了结；**别的路都试过、都不行** → 手段用尽 → 上交。

**「用尽」怎么算，本版只定性质，不定次数**：
**同一条路试到不再产生新信息，就算用尽。**具体几次、等多久，是策略，
[归各层自己定](#八边界与依赖)。

### 5.7 这不是一张清单，是一个判断

**同一种偏离，这次了结得了、下次了结不了。**

> 「一个工具用不了」——动作空间里有替代，agent 绕过去；
> **一个替代都没有**，同样一件事就得上交。

所以本 topic 里**不会出现**「这一层的非常态包括以下 N 种」那样一张表。
**穷举表永远列不全，而且列出来的第二天就过期。**

### 5.8 上交，交的是什么

**交的是「下面试过的那些手段的身份与分类」，不是「下面试过的那些手段」本身。**

一层上交时，**留下一条新的记录条目**，说清这一层的收场与原因：

| 要求 | 为什么 |
|---|---|
| **寿命宿主取接收层那一档或更长** | 条目不可变，**没法事后提升寿命宿主**；挂在会消失的东西上，恢复之后依据就没了（[PF-000 K2](../PF-000-occurrences-and-record-entries/design.md#62-k2依据的寿命不得短于要靠它重建的那个对象)） |
| **自包含** | 接收的那一层不必回头翻下层其它条目就能定下一步，**但留得住溯源的路** |
| **只带分类与身份，不搬运正文** | 大小**不随层数与重试次数增长**。搬正文的版本，层数一多就把上下文吃光 |
| **按「事」追加，不取代** | 两次上交在记录里并排存在，后者不覆盖前者 |
| **默认不进模型上下文** | [给模型看默认拒绝](../PF-010-context-management-and-assembly/design.md#62-没有明确标了给模型读的不进模型那一份)。要让 agent 知道，走[阈值触发的一条定长提醒](#64-要让-agent-知道只能走阈值触发的定长提醒) |
| **写入那一刻完成脱敏与租户裁剪** | 条目不可变、[记录一条都不能擦除](../PF-010-context-management-and-assembly/design.md#610-记录里的消息一条都不能擦除)——**写错了就是永久的** |

**下层原来那条记录一个字不改。**上交是**另一件发生的事**，产出它自己的条目；
下层那条失败记录该是留痕就还是留痕。

> **不这么写，实现者只有两条路**：把所有下层记录一律升成「依据」（成本失控），
> 或者回头改写已经写下的条目（违反「条目一旦写下就不再改变」）。**两条都是错的。**

#### 接收方就是模型的那一跳

**工具执行交给 agent 那一跳，接收方就是模型本身**——六层里只有这一处是这样。

> **那条 agent 必须读懂的返回消息，就充当这一跳的上交条目，不另立一条。**

| 为什么不另立一条 | 依据 |
|---|---|
| **另立的那条，读者答不出来** | agent 读不到它（它不进上下文），剩下只有排查的人看——**那是留痕，[PF-000 已经给它安了家](../PF-000-occurrences-and-record-entries/design.md#条目效力--entry-standing)** |
| **同一件事会有两处登记** | [§6.7](#67-不为非常态另建记录机制) 与 [acceptance 的「绝不能」](acceptance.md)都写着：**双份登记必然分叉** |
| **PF-000 限定了什么时候才产出多条** | [只有两个原因](../PF-000-occurrences-and-record-entries/design.md#54-一件事什么时候产出不止一条条目)：干预点先于结果、增量先于成品。**这一跳两个都不沾** |

**所以上表「默认不进模型上下文」那一条，管的是接收方不是模型的那些跳。**
这一跳的条目[本来就被明确标了给模型读](../PF-010-context-management-and-assembly/design.md#62-没有明确标了给模型读的不进模型那一份)，
它进——**这不是例外，是它本来就满足 PF-010 那条的条件**。

### 5.9 问人，横切所有层

**「问人」不是一层，是每一层都可以用的一种了结手段。**

任何一层都可以靠问人回到自己的主路径。**问人排不进阶梯**，
**因为[层的树](#53-层的顺序不是排出来的是推出来的)排的是作用域的包含关系，而人根本不在这棵树上**。

怎么问、卡片长什么样、池子怎么组织，[全部归 PF-008](../PF-008-human-in-the-loop/README.md)，
本 topic 一个字不改。

### 5.10 完整的形状

```text
                    落终局  ←── 租户那一层也了结不了
                       ↑
              ┌────────┴────────┐
              │      租户        │ ←─ 额度用完，起点直接落在这里
              └────────┬────────┘
                       ↑ 上交（留一条新条目）
              ┌────────┴────────┐
              │      会话        │
              └────────┬────────┘
                       ↑
              ┌────────┴────────┐
              │      运行        │
              └────────┬────────┘
                       ↑
              ┌────────┴────────┐
              │   agent 的一步   │
              └───┬─────────┬───┘
                  ↑         ↑
        ┌─────────┴──┐  ┌───┴──────────┐
        │  一次模型调用 │  │  一次工具执行  │  ← 兄弟，各交各的父节点
        └────────────┘  └──────────────┘

   起点可以落在任何一层——看缺的那样东西在谁手上
   任何一层都可以横向问人，问完回到自己的主路径
   接手的那一层此刻不存在时，直接交给再外面一层
```

## 六、产品规则

### 6.1 起点可以是任何一层，往上不许跳

**起点**由[「缺的东西在谁手上」](#56-了结得了吗看缺的那样东西在谁手上)定。

**往上必须逐层。**跳过哪一层，那一层的处置就永远不会发生——
久而久之它形同虚设，而它本来可能有办法。

**有一个例外，而它不违反「往上必须逐层」那条的初衷：**

> **接手的那一层此刻不存在时，直接交给再外面一层。这不算跳级。**

最清楚的例子：**一次模型调用彻底失败时，「agent 的那一步」根本没有发生过**——
agent 就是模型，模型没给出回复，**那个会思考的主体此刻不在那里**。

不许跳那条立的初衷是「**那一层本来可能有办法**」，
而**一层此刻不存在，它就不可能有办法**。
**硬要不跳，事情就会卡死在一个此刻根本没有层的位置上。**

### 6.2 上交即打断

**一层把事情交出去，它自己就停在那里，不再往前走。**

**理由**：交出去还继续跑，上层的处置**落不到实处**——它没法改变一个正在动的东西。

**代价写在明面上**：一次上交就是一次打断，**有些本可以边跑边处理的情况被这条一刀切掉了**。
这是已知的取舍，不是疏漏；[真的疼了再开口子](#七取舍)。

### 6.3 上交必须留下条目，这条不可省

**没有条目的上交等于没发生过。**

恢复之后，谁也说不清这件事被哪几层接过、各自做了什么，
**于是上层会重复下层刚刚试过并失败的事，而且毫无察觉**。

条目的要求见 [§5.8](#58-上交交的是什么)。

### 6.4 要让 agent 知道，只能走阈值触发的定长提醒

**不许把尝试记录整批塞进模型上下文。**

- **到阈值之前，零成本**——什么都不注入。
- **到阈值时，注入一条有上限的提醒**，说清「这条路你已经走过几次了」。
- **原始记录一个字不动**，提醒是追加的，不改写任何已有内容。

**为什么不能整批塞**：上交记录随失败次数单调增长，
而[上一次模型请求之后新来的不许压](../PF-010-context-management-and-assembly/design.md#611-上一次模型请求之后新来的消息不许压)，
压不动就只能走终局——**一条为了让处置更好的规则，反而推着事情去死**。

### 6.5 上层只认跨层通用的说法

**上层的处置分支不读下层的内部编码。**

它读的是收场的类别、能不能重来这一类跨层通用的东西，
**不是下层的错误码字符串、不是它的内部阶段名**。

**验收办法很干脆**：

> **把下层的错误码词表整个换掉，上层的处置分支输出不变。**
> 变了，就说明耦合已经长进去了。

### 6.6 「不可确定」必须能表达

**一件事发出去了、回音没了，这不是失败，也不是没终态。**

上交的条目必须容得下「**外部效果不可确定**」这个值。
只记成功与失败，**缺少终态记录就会被当成仍在进行**。

### 6.7 不为非常态另建记录机制

**它的记录跟正常的事完全一样**（[§5.1](#51-非常态与发生的事是同一件事的两个面)）。

另建一套的代价是双份登记，而**两份登记必然分叉**。

### 6.8 阶梯到租户为止

**组织确实在租户外面**，生命周期包含关系也成立——一个组织有多个租户。
**但处置权不能往那儿交。**

**理由**：上交要留下一条条目，而那条条目**带着这个租户的内容**。
交到一个「组织层」，它的读者里就有**别的租户**——这直接撞
[SYS-TENANT](../../foundation/cross-system-constraints/requirements.md#sys-tenant)
的「跨租户访问默认拒绝」。

[PF-005 在沙箱那一侧做过同一个判断](../PF-005-execution-environments-and-sandboxes/design.md#64-租户级沙箱共享的工作空间)：

> **「跨租户共享不存在。**那会直接破坏租户隔离，
> 因此**没有『组织级沙箱』**——三个沙箱层级是穷尽的。」

**同一条约束，在这里的落点是：阶梯到租户为止。**

> **那「找超级管理员处理」算什么？算[问人](#59-问人横切所有层)，不算上交。**
> 超管是组织级角色，但**人本来就不在这棵树上**。
>
> **两条路看起来通向同一个人，但上交那条搬了内容，问人那条没有。**

## 七、取舍

| 选了什么 | 得到 | 付出 |
|---|---|---|
| **模型与层数无关** | 加一层**不必为它破例** | 读者要先接受「六层只是当前实例」，**不能照着层数背**；模型本身也可能被逼着修订 |
| **起点可以在任何一层** | 不做注定无用的处置 | 每件事都要先算一次「缺的东西在谁手上」 |
| **往上不许跳** | 每一层的处置都有机会发生 | 有时明知中间那层没办法，还是得过一道 |
| **上交即打断** | 上层的处置落得到实处 | **有些能边跑边处理的情况被一刀切掉** |
| **上交只带分类与身份** | 成本对层数近乎恒定 | 上层想看细节得另外去取，**而取细节要另行授权** |
| **默认不进模型上下文** | 常态零成本，不挤预算 | agent 不会自动知道下面试过什么，**要靠阈值提醒补** |
| **给判据不给清单** | 不会过期，新情况自动有归属 | 比照着清单查要多想一步 |
| **层结构是树，不是链** | agent 一步之内的模型调用与工具执行各就各位，**不必硬塞成上下级** | 「往外一层」要理解成「父节点」，比一条链难画 |
| **[阶梯到租户为止](#68-阶梯到租户为止)** | 上交**永远不会跨隔离边界** | 租户层了结不了的，只能落终局或问人——**没有更外面的兜底** |
