# PF-013 决策与来源

产品设计允许 product manager 做判断，但**不允许发明没人拍过板的东西**。
本页把两者分开：哪些是产品负责人裁决的，哪些是 PM 自己推导的，各自依据在哪。

## 一、拍板记录

### 2026-09-28 · 输入 token 允许有依据的估算与可配置余量

产品负责人对异步问题 `call_kOHmvzxQXkWpwbVw0rDIOUnx` 明确回复：

> 允许有依据的估算与可配置余量（推荐）

问题明示了原先发送前须准确计数或有可靠上界的承诺会阻断缺少这类资料的路由，并建议：每条档案仍有明确上限；token 采用适配模型的估算及可配置余量，不保证与上游实际计数完全一致；字节与图片数量精确检查，实际用量以上游返回为准。用户接受了这组后果。这取代本 topic 对 token 实际值必然落在上限内的强保证，不撤销其他输入限额、凭据、计费和失败留痕责任。

本次裁决没有指定余量数值、分词器依赖或计量函数接口；它们仍归精确规格与提供者选择。产品规则的裁定不自动更新已冻结的 MP5/RT7，也不宣称估算器或真实发送已经交付。

### 2026-09-20 · 范围与首批裁决

**分两次给。**第一次划范围并定档案与切换，第二次为「不得拒绝」补上前提。

#### 第一次的原话

> 「model profile 是数据，不是资产这个没问题。但是 **model profile 在产品上需要建模成一个对象**，
> **组织超管和租户可以自行拓展（但需要带上自己的 api key）**，我们 harness officially provided 的
> model profiles **不需要包含 key**（因为这是我们生产部署时候装配阶段配置的），
> **official 和 customized 的 model profiles 需要能够在用户界面聚合展示**。
> profile 的 schema 可以**参考 omne-next/omne_harness 的作为设计的起点**。
> **一个 topic**；**不留**；产品上**切换模型是用户直接的命令不得拒绝**，
> 因此**模型切换这个指令首先需要是一条需要记录的事实**，然后在接受到这个事件之后的
> **下一次的模型请求之前，要判断**（**agent-loop 状态方程没变**，还是**自然地进 compaction
> 的相关流程判断**，**输入带的是新的模型的 profile**，来判断）」

#### 第二次的原话

> 「我说的「不得拒绝」的前提是**用户选择了可进行切换的合法目标模型**哈」

#### 定死了什么

| # | 裁决 |
|---|---|
| **1** | **模型档案是数据，不是资产**——沿用 [PF-001 已有的那一格判定](../PF-001-identity-scope-and-agent-constraints/design.md#资产的种类)，八类资产的穷尽性不动 |
| **2** | **但它在产品上要建模成一个对象**，不是一个裸字符串 |
| **3** | **组织超管与租户可以自行拓展**，自建的**必须带上自己的 API key** |
| **4** | **官方提供的档案不含 key**——那是生产部署的装配阶段配置的 |
| **5** | **官方与自建在用户界面聚合展示**，不是两份清单 |
| **6** | **档案的形状以 `omne-next/omne_harness` 为设计起点**，不是照抄 |
| **7** | **范围是一个 topic**：档案 + 请求与非常态处置 + 会话切换模型 |
| **8** | **九点 aptitudes 不留** |
| **9** | **切换是用户的直接命令，不得拒绝**——**前提是目标为合法可切换的模型** |
| **10** | **切换指令首先是一条要被记录的事实** |
| **11** | **生效点在收到该事实之后、下一次模型请求之前**——不打断正在进行的那一次 |
| **12** | **agent loop 的状态方程不变**：不为切换新增分支，**自然地进已有的 compaction 流程判断**，只是**那次判断的输入换成新模型的档案** |

#### 裁决 12 为什么是本次最要紧的一条

**它把「切换模型」从一条新流程降成了「已有判断的输入变了」。**

换一种写法——「切换时若目标窗口更小则压缩上下文」——会在 loop 里多出一个
**只有切换才会走到的分支**，那个分支的正确性此后要单独维护。
**而按裁决 12，下一次请求前本来就要判断装不装得下**，
切换只是让那次判断读到了另一份档案。**没有新分支，也就没有新的失效点。**

> **这一条的射程比它看起来远。**窗口多大、收得下哪些模态、单张图的大小上限，
> **全都是装配从同一份档案里读到的事实，不是三套机制**——见[裁决 16](#裁决-16--大小上限归装配具体手段归架构)。

### 2026-09-20 · 起草过程中的四次追加裁决

#### 裁决 13 · 自建档案的凭据挂在范围层

PM 把两个选项与各自代价摆出来后，产品负责人选定
**(a) 范围层的一项设置**：组织或租户配一把 OpenRouter 凭据，**该范围所有自建档案共用**；
自建档案自身**不存凭据**，调用时按作用域取所在范围的那把。

**代价已如实写进正文取舍**：做不到「这个模型走另一个账号」；
同范围内所有自建档案的用量记在同一把凭据上，**上游账单分不到单条档案**。

#### 裁决 14 · 模态兼容挡在「算合法目标」那一刻

> 「这个就是我们 omne-next/omne_harness 那时候做的设计，**会话要有从 session log 到会话历史中的
> 数据包含了哪些模态的投影**，**合法的可切换的模型应当是能够兼容所有已存在的模态的模型**，
> **系统应当要有 O(1) 复杂度的判断能力**」

| # | 定死了什么 |
|---|---|
| **14.1** | 会话要有一份**从会话日志投影出来的模态记录**——历史里已经出现过哪些模态 |
| **14.2** | **合法可切换目标 = 兼容该投影全部模态的模型** |
| **14.3** | **这个判断必须是 O(1)**——因此投影是**被维护的事实**，不是每次去扫一遍历史 |

> **这一条让裁决 9「不得拒绝」一个字都不用动**：不兼容的**根本不进合法目标集合**，
> 因而谈不上「拒绝」。**它同时从源头挡掉了同类产品反复出现的那类故障**
> （带图会话切到纯文本模型后，该会话在那个模型下永远发不出去）。

#### 裁决 15 · 重试是 loop 里一个已有拓展点上的可替换拓展件

> 「**model request retry 应当是 loop 里的一个拓展点**，具体策略应当是**解耦的可实现不同的
> 可替代的实现**」

**位置是现成的**：[PF-012 §5.8](../PF-012-agent-loop-and-run/design.md#58-loop-拓展点) 的
「**调模型之后**」带收场维度，**「失败」那个取值的典型挂件原本就写着「失败分档」**。
**本 topic 不新增任何拓展点，PF-012 一个字不用改**——
这省掉了一次[架构内核 PF](../architecture-core.md) 的改动。

#### 裁决 16 · 大小上限归装配，具体手段归架构

> 「这个是**上下文装配时候的处理**，具体来说应当是**上下文装配的那个「函数」同样要接收一个
> model profile（切换后的）并根据它的来进行处理**（但**这是架构、实现规格的设计问题了，
> 不是产品需要关心的**，因为这还涉及比如说是否可以第一次预处理的时候多种档位大小的图片
> 都存一份、还是怎么做运行时缓存之类的取舍）」

**这条同时给了一条通用判据**，已写进正文第九章开头，也用它复查过全部未决项：

> **不是每个「没有答案」的地方都是产品未决项。**判据是[该区红线](../AGENTS.md#红线)那条——
> **这条内容产品负责人能看懂并判断对错吗？**
> 能，才是产品的事；不能，产品正文**指路就够**，挂一个未决反而会让后来者
> 以为产品欠了一个决定，**而那个决定根本不在这一层**。

#### 裁决 17 · 没人挂的时候，系统自带一件

PM 把两个选项与各自代价摆出来后，产品负责人选定
**系统自带一件默认的重试拓展件，用户可替换**。

**它不需要新概念**：[PF-012 §5.8 已经有「系统自带的三件」](../PF-012-agent-loop-and-run/design.md#系统自带的几件各站在哪)
（循环探测 · 放行判断 · 卸载判定），**这是第四件**，同样不享受特权、同样只能靠改日志起作用。

| | |
|---|---|
| **收益** | 一次网络抖动**不打断一轮对话**；开箱即用的稳定性**不取决于有没有人去挂一件** |
| **代价** | 多一件要解释；用户想换策略之前，**得先知道有它在** |

> **PM 曾否掉起草者给这条的理由。**起草者说「零消费者的对称性——我们刚因为这个删掉了 aptitudes」，
> **那个类比不成立**：aptitudes 是**没人读的数据**，删了什么都不会发生；
> 自带重试是**没人挂时的行为**，有无直接改变开箱体验。**两者不同构，不能互相援引。**
> 产品负责人是在「一次抖动打断对话」与「多一件要解释」之间选的，不是在那个类比上选的。

### 2026-09-20 · 第二批：转换件，与「面向状态码」

**同日稍晚，在统一建模 run、agent-loop、inbound 与触发事件的那一轮里给的。**
**完整原话与其余落点记在 [PF-012 decisions](../PF-012-agent-loop-and-run/decisions.md#一拍板记录)。**

#### 裁决 18 · 转换件是「消息／内容块落盘前」的拓展点

> 「转换件的定义应该重新调整一下，它**不应当是请求模型前或者组装上下文时候的一个能力拓展点**，
> 而应当是**一条消息/内容块落盘前的一个能力拓展点**（这就统一了消息请求输入的处理和
> 模型生成/工具结果返回的处理），让一条 XXXMessage 的消息落盘之前，
> 如果有能够将它的一个内容块模态处理成文本的话，就调用并且 **inplace 地**
> 这个内容块的记录它文本性质内容的那个字段被赋值，
> **这样后面用的时候就变得很干净了（根据模型判就可以）**」

**以及同一轮里关于形状的那条：**

> 「这个拓展点，**不应该是一个模态一个拓展点，而应当是统一的 模态->文本 的拓展点**，
> 因为**一个拓展点可以装载多个拓展**……协议应当定义为类似
> **声明自己能够处理的模态集合，输入带数据+这个数据的模态**
> （当然用内容块的话格式本身就统一了），**输出就是文本内容块**」

| 落在哪 | 什么 |
|---|---|
| [§4 转换件](design.md#转换件) | **新增一节**：契约四句话、三件它不做的事、与结果卸载的分界 |
| [PF-012](../PF-012-agent-loop-and-run/design.md#模态转换为什么必须落在这里) | **位置**归那边（它把「输入落盘之前」扩成了「消息落盘之前」） |

#### 裁决 19 · 合法目标随之放宽（2026-09-20，PM 提请，产品负责人确认）

**PM 核出 rev 1 与裁决 18 自相矛盾**：
rev 1 把不兼容的模型全挡在候选之外，**转换件于是永远没有用武之地**，
而裁决 18 里「**根据模型判就可以**」这句话的前提，正是**存在一个收不下原件的模型在用它**。

**PM 把两条路与各自的产品长相摆出来，产品负责人选定「放宽」：**

> **有文本那一份的块，不再把任何模型挡在外面。**
> [模态投影](design.md#模态投影)因此改成「历史里出现过、**且没有文本那一份**的那些」。

| | |
|---|---|
| **收益** | 带过图的会话**切得到纯文本模型**；[同类产品上那类「会话卡死」投诉](#裁决-14--模态兼容挡在算合法目标那一刻)在我们这儿仍然不会发生；**转换件有了真实用武之地** |
| **代价** | 纯文本模型读到的是**那段文字，不是那张图**。[产品必须让用户看得出这次模型读到的是哪一份](design.md#转换件) |

> **[裁决 14](#裁决-14--模态兼容挡在算合法目标那一刻) 一个字没被推翻**——
> 「挡在算合法目标那一刻，不挡在出门那一刻」照旧。**变的是「什么算兼容」。**

#### 裁决 20 · 面向状态码，不为已有状态码的事再造一套词

> 「我觉得有点过度设计了，**就 llm request 各种情况都是有状态码的，
> 面向状态码设计就行了，策略模型应当足够干净了**」

| 落在哪 | 什么 |
|---|---|
| [§5.4](design.md#54-三类事实归本层定死其余照状态码) | **「换一家可能就好」与「等一下可能就好」并回一类**——那正是 5xx 与 429 的分别 |
| [§5.7](design.md#57-上交带什么原样带着状态码不翻译它) | **成因九个取值收成八个**；**上交另外原样带着状态码** |
| [§5.12](design.md#它看得到什么) | **重试策略看得到的第一样就是状态码** |

> **「事实 / 策略」那条界线一个字没改。**本层仍然定死三类事实，拓展件推翻不了；
> 收缩的只是**策略那一侧被本层预先咀嚼过的部分**。

### 2026-09-22 · 凭据是范围上的一项属性，支持自带凭据

**产品负责人裁决（选项作答）**，在「A 属性，挂在范围上／B 独立对象」两条里定：

> 总体上我理解是 A（属性），就是用户完全可以 BYOK，
> 这样未来可以设计权益、订阅扣费这些就可以方便区分了。

| # | 定死了什么 | 落在正文哪里 |
|---|---|---|
| **1** | **OpenRouter 凭据是[组织](../../ubiquitous_language/terms/subjects-and-ownership.md#ul-organization--组织--organization)或[租户](../../ubiquitous_language/terms/subjects-and-ownership.md#ul-tenant--租户--tenant)身上的一项属性**，一范围一把；**不是一个独立对象** | [§5.6](design.md#56-凭据挂在范围上不挂在档案上)、[§6.2](design.md#62-凭据挂在范围上档案自己不存) |
| **2** | 由此三条：**身份即范围**、**轮换是改这一项的值**、**用量归这个范围** | 同上 |
| **3** | **它也不是[设置](../PF-002-assets-settings-and-permissions/design.md#52-设置与权限是资产的两种属性)**——设置总是某份资产的属性，而[档案与凭据都不是资产](design.md#模型档案) | [§5.6](design.md#56-凭据挂在范围上不挂在档案上)、[§4 模型档案](design.md#模型档案) |
| **4** | **范围自带凭据是产品要支持的用法**（原话里的「BYOK」就是指这件事；正文不用这个词，[理由见 P29](#二pm-推导)） | [§5.6](design.md#56-凭据挂在范围上不挂在档案上)、[§6.2](design.md#62-凭据挂在范围上档案自己不存) |

走平台那把凭据的量与走自带那把的量，落在不同的范围上，**将来要区分就区分得开**。

| **P5** | **首 token 之后断的那一种不另立上交条目** | 套用 [PF-011 §5.8「接收方就是模型的那一跳」](../PF-011-off-nominal-handling/design.md#58-上交交的是什么)的三条理由，三条在这里一条不少地成立；另立一条会与 PF-009 那条提醒构成**双份登记** |
| **P6** | **上交接手方分两种**：一个字都没出来 → 越过 agent 的一步交给运行；已经有内容进了记录 → 交给 agent 的一步 | PF-011 的例外判据是「那一层此刻存不存在」。模型给出了哪怕被中断的一份回复，**agent 那一步就在** |
| **P7** | **失败的重试尝试是「留痕」**，不进方程定义域、不进模型上下文 | PF-011 那张「留痕 × 偏离主路径」表写的就是「调用没成、准备重来」。**这同时保住了状态方程的纯性** |
| **P8** | **「凭据没配」与「凭据被拒」合成一个取值「凭据不可用」** | 两者**用户要做的事完全一样**，分开只多一个取值、换不来不同的下一步 |
| **P9** | **成因取值 9 个具名 + 1 个诚实兜底** | 判据是「**下游据它做不同的事**」。**其中「和会话里的模态对不上」是裁决 14 之后新增的第 9 个**——并进「这个范围不再允许」会让用户去找管理员，**而管理员帮不上忙**，下一步不同就是两个取值 |
| **P10** | **「空回复」归「其余全部」那一类**（照状态码由策略定） | 首 token 从没出来过，不受「已经开口说话了」那一类管。**这是判据的应用，不是模型的一部分**，正文已标明可重判 |
| **P11** | **缺凭据不阻止切换，但展示列表要让用户看得出「现在用不了 + 缺什么」** | 不阻止：合法性判定不新造第四条条件（P2）+ 生效点在下一次请求之前。要告知：**缺凭据在切换那一刻就已经确定**。**不拒绝 ≠ 不告诉他** |
| **P12** | **选中的被撤回或被锁掉时，不替用户自动改选** | 「撤销不等于强制停止：撤权管的是下一道准入」，而**下一次请求就是下一道准入** |
| **P13** | **文件块不参与模态判定**（**2026-09-23 起收窄，见 P25**） | PF-009 明写文件块装的是附件的**引用**，不是文件内容——**引用就是一段文本** |
| **P14** | **「官方档案 / 自建档案」与词表里的「官方件 / 自定义件」是两套词，有意不合并** | 档案不是资产（裁决 1）。**用「档案」不用「件」，就是为了不造同名不同义** |
| **P15** | **本层的成因分类落在 PF-012「调模型之后 · 失败」这个取值之内，不新增取值** | 防止有人把九个成因升格成九个收场——**那等于改了 PF-012 的位置模型** |
| **P16** | **模态投影是投影，不是第二份权威** | 增量维护**只为满足裁决 14.3 的 O(1)**，**从日志重算必须得到同一答案**。依据是 [PF-012 §6.7「检测状态从日志派生，不另存」](../PF-012-agent-loop-and-run/design.md#67-检测状态从日志派生不另存)——**那条挡的正是同一个错** |
| **P17** | **「事实 / 策略」这条界线** | 「发不出去 / 重试没用 / 已经开口说话了」是**事实判断**（重试在物理上没有意义），本 topic 定死，拓展件推翻不了；「换一家 / 等一下」是**策略**（试几次、等多久值不值），归拓展件。**不划这条线，一件写得不好的拓展件可以让系统在吐了半句话之后再发一遍** |
| **P18** | **组装的输入里必须有当下生效的那份模型档案**，而这件事要由 PF-010 自己写下来 | 裁决 12 与 16 都建立在它上面，但 PF-010 组装那一节整节是从会话日志那一侧写的，**这一条当时无处落脚**。**缺口已由 [PF-010「要求五」](../PF-010-context-management-and-assembly/design.md#要求五组装的输入里必须有当下生效的那份模型档案)接住**——窗口 · 收得下哪些模态 · 送进去之前的限制，三个事实同出一份档案 |
| **P19** | **转换件交出的块挂在原块上，作为原块的「派生表示」；transcript 也挂在原块上** | 裁决 22 让产出变成「别的模态的块 + transcript」，原先「给块上的文本字段赋值」装不下。剩下三个去处：**①** 另起一批块进消息——同一份内容在消息里出现两次，组装得先猜哪几块是同一个东西，而 [PF-009 的块序列](../PF-009-context-message-types/design.md#消息的内容是一串块不是一段文本)说的是「这条消息装了什么」，不是「它还能怎么读」；**②** 另立一个对象——按「属性优先于新概念」的一贯做法，它没有自己的生灭，随原块生、随原块在；**③** 作为原块的属性。**只有 ③ 不违反任何一条已接受的内容**，且与 [PF-012「落盘之后再转，要么改记录要么另存一份」](../PF-012-agent-loop-and-run/design.md#模态转换为什么必须落在这里)那条理由同向 |
| **P20** | **组装时：收得下原件给原件，否则给收得下的派生表示，都没有就给 transcript** | 裁决 22 说 transcript 是「最后兜底」；[PF-012 §5.8](../PF-012-agent-loop-and-run/design.md#模态转换为什么必须落在这里) 已写「原始内容块原样进日志（换个收得下的模型还要用它）」。两条合起来次序只有这一种。**几份都收得下时挑哪几份**是组装的取舍，归 PF-010，**产品不定** |
| **P21** | **转换失败 ＝「消息落盘之前」这个位置上的否决；转换件的干预力是「可改写 · 可否决」** | 裁决 24「失败直接报错、不落盘」；[PF-012 的否决表](../PF-012-agent-loop-and-run/design.md#干预力三档直接用-pf-000-的)在 rev 8 为这个位置补了「否决＝这条不落盘，发送方被告知」；而[「可否决那一档挂了当否决」](../PF-012-agent-loop-and-run/design.md#干预力三档直接用-pf-000-的)正是「失败了就不落盘」的另一种说法。**它写派生表示是改写，它失败了不落盘是否决——两档都要，缺一档说不通** |
| **P22** | **一个键上没有登记转换件，不是失败**：块照原样落盘、没有 transcript、进模态投影 | 裁决 24 说的是「**处理**失败」。没人登记就没有处理。**反过来当失败处理**，一个没有视频转换件的部署里，**用户连给读得了视频的模型发一段视频都发不出去**——那是拿「没人会转」去惩罚「本来不需要转」。于是模态投影仍有唯一的来路（[§5.11](design.md#511-有-transcript-的块不再把任何模型挡在外面)） |
| **P23** | **交不出 transcript、或交出了文件块，都算转换失败** | 裁决 22 定的是契约的形状：transcript「作为最后兜底」、输出「不能是文件」。**契约之外的产出没法被组装按规则取用**——当成功收下，就是一个号称转过、却没有兜底的块，**模型可能读到空的** |
| **P24** | **转换件的替换只发生在系统装配那一层；组织与租户本版换不了**（**2026-09-23 已由[裁决 30](#2026-09-23--转换失败分三路替换只在系统装配层) 确认，升为拍板**） | 裁决 23：可替换，但「**现在先不升资产地位**」。在组织、租户各层登记、同键按层级替换——**那正是资产的持有与求值**；这么做就是**换个名字把资产请回来**。所以本版的替换只剩一处能发生：随系统装配。**将来要按范围换，就是升资产那个决定** |
| **P25** | **文件块的模态看它的媒体类型；媒体类型不属于四种模态的文件块仍然只是一个引用，不参与模态判定** | 裁决 21「模态由块的媒体类型决定」，且视频只能装在文件块里——所以文件块**可以**有模态。**P13 的道理对剩下那部分照旧成立**：一份文档的文件块装的是引用，引用是文本。**这一条把 P13 收窄，不是推翻** |
| **P26** | **每一次发出只走一家，「试过哪些」由此一家一条** | 裁决 26。[调研](../../../research/model-request-transport-sources/research.md)核过：上游在一次 HTTP 请求内部换家，[§5.5 的留痕](design.md#试过又失败的那几次留痕不进方程)与 [§5.12「已经试过哪些」](design.md#它看得到什么)都拿不到——**我们这边只看得到一次请求** |
| **P27** | **首 token ＝ 这次回复的第一个内容增量：文本、思考、工具调用的参数，哪一种先到都算；响应头不算**（**2026-09-23 由[裁决 31](#2026-09-23--首-token-不论模态) 扩到不论模态，见 P32**；「响应头不算」与下面的理由照旧成立） | 「已经开口说话了」的理由是两条：[用户可能已经看见](../PF-009-context-message-types/design.md#69-用户看见了的会话日志里必须有)、[记录里已经有了内容](../PF-009-context-message-types/design.md#半截的工具调用记下来但不给模型看)。**半截工具调用照样进记录**，所以它也算开口；响应头不带任何内容，两条都不沾。只算文本与思考，吐了半截调用就断的回复会被重发，记录里那半截与新的一份并存——**正是这条规则要防的** |
| **P28** | **「首 token 之前没有任何外部效果」改为「首 token 之前重发不会造出第二份回复；费用可能记两次，照实记成成本」** | [调研 G1](../../../research/model-request-transport-sources/reports/2026-09-23-model-request-transport.md#8-与产品正文的对照缺口只报告不裁决)：请求到了上游、首 token 之前，**上游可能已经开始计费**。原句把「没有外部效果」说满了；而这条规则要守的从来是「**一个逻辑回复只发一次**」，不是「钱只花一次」。[成本是历史事实、按尝试记](../PF-012-agent-loop-and-run/design.md#成本两层缺哪一层都会算错)，多花的那一笔照实记。**上游到底计不计费要实测，结论不改这条规则** |
| **P29** | **正文不用「BYOK」，只说「模型凭据」「范围自带凭据」** | [调研 G5](../../../research/model-request-transport-sources/reports/2026-09-23-model-request-transport.md#8-与产品正文的对照缺口只报告不裁决)：OpenRouter 的 `is_byok` 指「经 OpenRouter 转到上游时用的是账户里登记的**上游供应商**自己的 key」，而本 topic 说的是组织或租户配上**自己的 OpenRouter key**。两件事可以同时成立，**用一个词指两件事，读费用的人会读错**。`is_byok` 是上游字段名，不进词表 |
| **P30** | **实际费用拿不到时，明细记「未知」、拿到了再补一条；要求归 PF-001 §6.4，本 topic 只在引用处写一句** | [调研 G6](../../../research/model-request-transport-sources/reports/2026-09-23-model-request-transport.md#8-与产品正文的对照缺口只报告不裁决)：失败、被中断的调用，传输层只给得出「未知」。记成零，「没花钱」与「不知道花了多少」从此分不开。**成本明细归 [PF-001 §6.4](../PF-001-identity-scope-and-agent-constraints/design.md#64-隔离)**，那边要补这一句 |
| **P31** | **故障断流时，已交付的那部分记在这次尝试的账里，不成为消息**——§5.4 依据表那一格随之改写 | 这是 [PF-009](../PF-009-context-message-types/decisions.md#二pm-推导) 同日的推导：[§5.6](../PF-009-context-message-types/design.md#56-流断在半路)「出错断的：没有这条消息」与 [§6.9](../PF-009-context-message-types/design.md#69-用户看见了的会话日志里必须有)「用户看见了的日志里必须有」要同时成立，**只能记在尝试的账里**。本 topic 引用它：**「已交付的那半句一定在记录里」照旧成立**，不重发的理由一条没少 |
| **P32** | **整交的块（图、文件），首 token 落在「整块交出来」那一刻，不落在「开了口」那一刻**；判据挂在 [PF-009 的两种到达方式](../PF-009-context-message-types/design.md#能一点点长出来的与要么没有要么整个有的)上，不挂在模态清单上 | 裁决 31 只说「算」，没说算在哪一刻。「已经开口说话了」不许重发的理由是两条：[用户可能已经看见](../PF-009-context-message-types/design.md#69-用户看见了的会话日志里必须有)、记录里已经有了内容（P27、P31）。**整交的块开了口、还没交出来时，两条都不沾**——[半张图没有意义](../PF-009-context-message-types/design.md#能一点点长出来的与要么没有要么整个有的)，用户什么都没看见，账里也没有可记的内容；把那一刻当开口，就是把[响应头当开口](design.md#已经开口说话了优先于其余各类)的同一个错，白白关掉重发窗口。**交出来之后两条都成立**，不重发。所以**只有「交出」这一刻与已接受内容自洽**。能一点点长的那几样（含语音），第一片就是内容，与 P27 同理。挂在到达方式上而不列模态，是因为 PF-009 已保证**每一种内容块都落在两种到达方式之一**，新块不用再来问一次 |

> **一条已作废的推导，留在这里作证。**
> PM 起草前曾推出「**模态不支持不构成拒绝理由**」，理由是「生效点在下一次请求之前，
> 所以模态判断只能发生在切换之后」。**[裁决 14](#裁决-14--模态兼容挡在算合法目标那一刻) 推翻了它，而且推翻得对**——

### rev 9 的主线裁定与推导（2026-09-23，待产品负责人确认）

**来由**：共用契约起草前的领域读数、机制读数与对账（任务区 `tmp/assets-runtimes/`，块 C 各读数与 S8、S16、S17 起草者的报回）
把本 topic 的若干缺口与相抵报给主线；主线按「只有一个自洽答案」逐条裁定，记在任务区账本 `pending-user-rulings.md` §二。
**「主线裁定」不是产品负责人的拍板**，他回来可推翻；带 **⚑** 的几条会改变用户看到的东西，**请他特别看一眼**。

| 编号 | 结论 | 类别 | 推理链 |
|---|---|---|---|

| **P41** | **「用哪个模型」那项设置记的是路由名**；一条链上一个名字恰好落到一条档案 | 裁决 40「路由名就是能力」。资产那边[组合的引用指向能力标识，不指向具体资产](../PF-002-assets-settings-and-permissions/design.md#63-组合的引用指向能力标识)，覆盖之后引用自动落到生效的那一个；这里同一条规矩。**§6.1 的立意照旧成立**：名字背后必须是一条档案，名字落到的那一条上有全部事实，要问「看不看得了图」有地方问；§6.1 正文据此改成「设置记的是路由名，但这个名字背后必须是一条档案」 |
| **P42** | **挑胜者之前先滤掉两种：已撤回的、这个范围不允许的；模态对不上的与缺凭据的不滤** | 类推 [PF-002 §5.6 第 1 步的三小步](../PF-002-assets-settings-and-permissions/design.md#56-四步资产求值--组装--投影--层级计算)：**先把「此刻不在这个范围的候选里」的滤掉，再在剩下的里取最具体**——被禁用的、判下来不能用的，在替换次序上都视为不存在，标识退回下一层。已撤回与范围不允许，是档案这边「不在候选里」的两种说法。模态对不上与缺凭据不同：前者是这个会话合不合用，后者是调它的人配没配凭据——**档案本身在、也允许**，滤掉它们，同一个名字就会随会话内容、随配没配凭据在两层之间来回换，排查的人查不出这一次为什么是那一层的 |
| **P43** | **「已下架」只在链上同名的每一条都撤回了时才说**；最具体那一条撤回、链上另有同名在册的，调用照发、用那一条，列表上撤回那条标「已下架」外加「被某层同名档案覆盖」 | P42 的直接后果：撤回的那一条在挑胜者之前就被滤掉，名字落到下一格在册的那一条，**它就是合法目标**。**这与 [§6.9 不替用户改选](design.md#69-合法目标算不出来时不替用户改选) 不相冲**：用户选的是名字，名字没变；那条撤回的若恢复在册，名字又落回它。标注两样都要：「已下架」告诉他原来那条不在了，「被覆盖」告诉他此刻用的是哪一层的 |
| **P44** | **覆盖同样作用在组织层的锁之上：锁的是路由名，供应商、请求参数、凭据都取胜出的那一条的** | 组织锁死的是「用哪个模型」那项设置的**值**，那个值是一个名字（P41）；名字落到哪一条，是覆盖那一维的事，与资产那边「[设置的值跟着资产走](../PF-002-assets-settings-and-permissions/design.md#替换是一条路径不是一扇后门)」同形——锁住一项设置，管不到替换它的那一份。**代价写明**：组织锁得住名字，锁不住它落到哪一条；资产那边组织还能[把替换本身锁住](../PF-002-assets-settings-and-permissions/design.md#55-资产替换的层级)，**档案这边没有这一把**——见第四节 |
| **P45** | **组织层建了一条与官方同名的自建档案之后，没配自己那把凭据的成员就用不了这个名字** | 裁决 40 + [裁决 33 组织那一层不持有凭据](#2026-09-24--组织那一层不持有凭据每人租户层自取) + [自建档案调用时取调它的那个租户那一把](design.md#56-凭据挂在范围上不挂在档案上)。组织那条盖住了官方那条（官方那条用的是出厂默认那一格那一把），成员调这个名字用的是自己那把；没配，就缺凭据——**缺凭据不滤**（P42），名字不会落回官方那条。**这是裁决的直接后果，写进正文的代价** |
| **P46** | **展示列表里，被盖住的同名条目照列、带来源、标「被某层同名档案覆盖」，选不了；怎么呈现归 PF-016** | 裁决 40「像资产一样」+ [PF-002 §5.5 同标识替换必须可见](../PF-002-assets-settings-and-permissions/design.md#55-资产替换的层级)。不列，用户看见一个熟悉的名字，以为用的是官方那条；列成可选，选了也落不到它——那等于一个选不中的候选。**只作标注**是两头都成立的唯一做法。展示列表的公式由此多出这一类（[R-MR-1](#rev-9-的主线裁定与推导2026-09-23待产品负责人确认)「严格等于合法目标 ∪ 当前选中」随之放宽为「外加被盖住的同名条目」） |
| **P47** | **「用哪个模型」这项设置的值是一个路由名，不是某一层的某一行**：切换改的、组织锁的、会话那一格与组织那一格记下的，都只是名字；它落到哪一行，每次用到时按层序现算，同一个名字在两个成员的会话里可以落到不同层的两行。[§4 档案的身份](design.md#档案的身份所在范围加路由名)与 [§5.10](design.md#510-合法目标集合与展示列表是两件事) 各明写一句 | **裁决 39、40 的直接后果**（主线 2026-09-24 追加要求明写）：同名的几条并存（裁决 39），而「路由名就是能力，从下往上在运行时覆盖」（裁决 40）——**设置若记的是某一行，就没有东西可覆盖**：它会钉死在那一行上，租户层再建一条同名的也顶不上来，「运行时覆盖」这句话当场落空。只有名字能让覆盖在运行时发生。**P41 说的是同一件事，这里把它写到设置值的单位上**，免得下游把设置值实现成（范围, 路由名）一对 |

**本 topic 在[架构内核](../architecture-core.md)上，rev 12 动手前的三问：**

1. **谁依赖改的这几条？**顺 `depends-on` 反查：[PF-014](../PF-014-inbound-intake-and-queueing/README.md)（不涉及档案身份）、[PF-016](../PF-016-cli-tui-delivery-surface/README.md)（**展示列表多一类只作标注的条目**，怎么呈现归它）、[PF-012](../PF-012-agent-loop-and-run/README.md)（有效模型是当下条件的一部分，求法照旧四步，只是第一步的名字落到哪一条按层序）。
2. **哪些已接受的结论会松动？**rev 4 已接受的内容一条没动；rev 10 的 P38 被裁决 40 改写；rev 9 的 R-MR-1「展示列表严格等于并集」多了被盖住的那一类；§6.4「会话指向被撤回的档案时说已下架」收窄为链上同名都撤回时。
3. **是真要改，还是用错了地方？**是改——档案凭什么是这一条、名字落到哪一条，都是本 topic 自己的对象上的规则。**三类事实与八个成因、首 token 判据、选中与有效两分都没动。**

### 2026-09-28 · 输入上限的 PM 推导

| # | 结论 | 可核对的理由 |
|---|---|---|
| **P48** | 上游事实与本档案提供的上限分别可读，未知不写成无限、零或空值 | 允许明确未知，意味着不能再用一个看似确定的值替它；自己的上限不能反过来变成上游事实 |
| **P49** | 官方及自建档案的适用输入上限都须为正的有限值；缺项不能发出 | 用户要求的是“我们自己的 model profile”，且档案是统一的可调用模型事实。只约束官方或把无限当上限，都无法形成对实际输入范围的约束；零不能承载已声明的图片输入能力 |
| **P50** | 已知上游限制仍然约束供给，不同维度分别适用 | 允许记录未知并没有授予绕过已知限制的能力；总量和单图的约束对象不同，互换会伪造已知事实 |
| **P51** | 超限原件必须经已有规则取得合规表示，否则不得发出；不新增模态筛选规则 | “提供上限”若不约束实际请求便没有意义；裁决 16 已把内容处理交给组装，大小也不是模态是否支持的问题 |
| **P52** | 范围内不保证上游一定成功，一次成功不消除未知 | 有自己的有限范围只证明本项目限制了发送内容，并不能补出缺失的上游事实；实际结果按既有调用规则诚实记录 |

## 2026-09-29 运行时归属与句柄

**直接要求**：[INT-001～003](../PF-015-session-lifecycle-and-ownership/interviews/2026-09-29-runtime-ownership-and-handles.md) 要求模型／工具 runtime 归 Session 或 Run 逻辑治理，Agent runtime 仅持句柄，销毁不结束所引用执行，并完整落盘。

**本包处置**：取消模型调用依附 Agent runtime 的旧限制；零句柄继续生成和记账，确认模型自身失联才按首 token 分界恢复。 “代表 Run 发起”沿 [INT-004](../PF-015-session-lifecycle-and-ownership/interviews/2026-09-29-runtime-ownership-and-handles.md#int-004) 作职责解释；Agent Loop 与运行实例不作为同义词。

**PM 推导**：Session 统一生命周期，Run 统一工作归因；Run 外调用直接归 Session。零句柄继续执行要求独立结果记账、持久调用关联与接续查询；仅 Agent runtime 消失不足以判定执行失联。保留显式取消的原传播范围，不由句柄释放隐式取消，不承诺外部效果可撤销。

**取代范围与消费者**：PF-012／013 与 UL-D-3 中“模型 runtime 以 Agent runtime 为宿主”及据此推导“等模型不可释放尝试”的旧说法被取代；PF-011 的树只说明工作归因。历史记录保留，现行正文、流程、验收、词条及对象表改用本轮规则。PF-004 装配、PF-009 流式输出、PF-010 组装压缩、PF-014 入站、PF-020 工作区、PF-021 Job 继续消费原边界，执行接续由 PF-012／013 表达。已冻结 model-request-runtime 等契约及其提供者／装配映射须在后续规格演进中核对宿主、取消、尝试栅栏和恢复；本次产品变更不自动修改其版本或扩大正式接受范围。
