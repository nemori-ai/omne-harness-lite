# 2026-09-18 · 流式：DSH 的做法，与另外两家的对照

**这是原始材料，不是结论，更不是依据。**

**缘起**：产品负责人指出 rev 1 定义的全是「完整的一条消息」，
**而响应往往是流式的**，并问：

> **quote**：「你定义的是完整的响应或输入的情况的，但是往往响应会是流式的，
> 比如 openai response api 的消息类型、langchain 的 content block 的类型，
> 在设计上都是有考虑流式的 chunk 以及 chunks -> message 的投影和组装。
> deepseek harness 有没有我不确定，还是说它的流式的机制是不依赖通过定义这种
> chunk 子类型来做的？」

**PM 没想到这一层，如实记为缺口**，然后去查。来源：`/tmp/deepseek-harness`，2026-09-18 读。

## 一、直接回答：有，但形状很特别

**DSH 的流式确实靠一套 chunk 子类型做**——一个**封闭**的判别联合，**七个成员**：

```text
开一个块 ──→ 三种增量之一 ──→ 封上这个块 ──→ 记一次账 ──→ 收尾
```

**关键在于：这套词表不与内容块词表同构。**

| | 内容块词表 | 流式词表 |
|---|---|---|
| 有几种 | 六种（文本 / 思考 / 图 / 文件 / 工具调用 / 工具结果） | 七个成员，**其中只有三种是增量** |
| 开放还是封闭 | **开放**——插件可以加 | **封闭**——加一个成员，所有消费方编译不过 |

**只有三样有增量**：文本、思考、工具调用的参数。
**图、文件、工具结果没有对应的增量**——它们只能「开个口，然后整个交出来」。

## 二、开放与封闭为什么不打架

**开放的那份，通过两个「洞」被引用进封闭的协议里：**

- **开口**的时候说明「这里要长出**哪一类**块」——这个类型取自开放词表；
- **封口**的时候直接交出「**一个完整的块**」——也取自开放词表。

> **插件加一种内容块，不必动流式词表；它只是拿不到增量投递能力。**

**这正是本 topic [§5.5 那条分界](../design.md#能一点点长出来的与要么没有要么整个有的)的来源**——
只不过我们的表述换成了产品语言：**能一点点长出来的，与要么没有要么整个有的。**

## 三、他们写明的「何时该封闭」判据

这是本次调研**最值钱的一条**，出自一条设计笔记（原文大意）：

> 一个新变体如果**必然需要消费端写新代码**才能正确处理，那就该用封闭联合——
> 因为**插件加进来却被静默丢掉，比编译报错更坏**。

反过来，内容块词表开放的代价也被明写：

> **新的核心块必须连同 adapter、UI、压缩支持一起落地。**

**这条判据本 topic 没有直接采纳**（产品不定「开放还是封闭」，那是技术设计），
**但它印证了 §5.5 的分界是有道理的**：增量能力本来就不是白给的，
每加一种都要各处配合。

## 四、与另外两家的对照：一处收敛，一处分歧

### 收敛：三家都是「开始 — 增量 — 结束 + 用某种序号对齐」

| | 形状 |
|---|---|
| **DSH** | 开口 / 三种增量 / 封口，用一个块序号关联 |
| **OpenAI Responses API** | 条目与部分的生命周期事件 + 增量事件，逐层带索引 |
| **LangChain** | 增量块带索引，靠索引对齐合并 |

**三家独立收敛到同一个结构**，这是本 topic 敢照着定的主要理由。

### 分歧：「半条消息」算不算消息

| | 做法 |
|---|---|
| **LangChain** | **算**——半条消息是完整消息的子类，两半能加起来 |
| **DSH** | **不算**——只有一个不对外的「块累加槽」，没有任何「半条消息」类型 |

**本 topic 取 DSH 这一侧**，理由见
[design §5.5](../design.md#半条消息不是消息)：
记录里要是能躺着半条消息，**读到它的人分不出「还没说完」与「说到一半被掐了」**。

## 五、中断怎么处理——这块直接塑造了 §5.6

那边有一条专门的设计笔记讲「取消的流要把已交付的前缀结算掉」。读到的四种情形：

| 情形 | 落成什么 |
|---|---|
| 用户取消，**已有可见内容** | 一条消息 + **显式的「被中断」标记**，内容是已交付的部分 |
| 用户取消，**什么都还没出来** | 只留一笔尝试记录，**不进 agent 看得见的历史** |
| 出错断的 | 同上，**不伪造任何 agent 看得见的内容** |
| 写到上限截断 | 正常消息，**但工具调用全部丢弃** |

**「被中断的消息里工具调用一个都不留」，他们给的理由原文大意是：**

> **中断发生在派发之前；留着一个，就得凭空造一个结果。**

**这句话本 topic 直接采纳了**（[§5.6](../design.md#56-流断在半路)），
因为它与 [PF-010 尾部对账](../../PF-010-agent-loop-and-run/design.md#59-恢复重新算一遍-f但尾巴要先对账)、
[PF-006「被中断不是失败」](../../PF-006-tools-and-skills/design.md#67-用户可以中断而中断不是失败)
是同一条思路——**三处独立到达同一个结论**。

## 六、工具调用参数：整条路上没有一处试图解析半截 JSON

- 参数**全程是原始字符串**，一段一段累积；
- **解析只发生一次**：装配完成之后、执行之前；
- 而且**解析失败不抛错，原样留着字符串**。

**本 topic 采纳**（[§6.10](../design.md#610-没收齐的工具调用参数不解析不执行)），
并补了一条那边没明说的理由：**残缺的参数解析出来的东西比解析失败更危险——
它可能恰好合法，而少了一半字段。**

## 七、记录里存不存到达过程：他们选了存

- 早期是**每个增量一条事件**；
- 曾有人提议**只存装配后的消息**——**被拒**，理由是高保真回放、失败的流、快照回放都依赖它；
- 现在是**每次尝试结算成一条事件，里面嵌一份压缩过的到达过程**。

**本 topic 没有采纳，也没有否掉**——[列为未决](../design.md#92-流式里还剩一件事没定)。
**那是他们的取舍，取决于「要不要支持回放当时的样子」，而那件事本 topic 答不了。**
