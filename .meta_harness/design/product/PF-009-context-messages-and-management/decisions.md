## 二、PM 推导

从已拍板内容推出的判断，附可核对的推理链。

| 结论 | 从哪几条推出 | 推理 |
|---|---|---|
| **按「谁在说话」组织成五种**，而不是照抄 DSH 的两轴模型 | 「参考 DSH 的消息类型」+ 产品文档面向产品负责人 | 那边是**一个 `Message` + 三值 role + 正交的 source/form 两轴**，`UserMessage` 这些名字是特化视图而非并列成员（[调研笔记](interviews/2026-09-18-dsh-message-types.md)）。两轴模型讲给产品负责人听要先解释两个维度才说得清一条消息是什么。**产品定「有哪几种、各自是谁在说话」，不定它在代码里由几个类型承载**——语义对得上即可 |
| **`SystemReminderMessage` 必须独立，不能是「带标记的用户消息」** | 「它不是 SystemMessage，是特殊的一种」这条裁决 | 三条：**①** [记录是唯一真相来源](../PF-010-agent-loop-and-run/design.md#52-记录是唯一的真相来源)，混进 `UserMessage` 就要靠解析内容才答得出「用户到底说了什么」——**而解析会错，标记会被伪造**；**②** 每家最合适的落点不一样，模型层定死就浪费了 openai 的 `DeveloperMessage`；**③** adapter 要认的是**类型**，不是内容里的字符串——后者谁都写得出来 |
| **每一家都必须有落点，不许落空也不许丢** | 「让每个 adapter 识别然后适配成标准的某一种」这条裁决 | 「适配成某一种」蕴含**必须有一种**。丢掉的后果是 agent 在那一家上永远看不见系统在说什么——**同一个 agent 换一家模型行为就变了，而没人查得出为什么** |
| **提醒的标识由系统加，生产者交的是一条消息** | 独立类型这条裁决 + 两家做法相反这个事实 | [DSH 让生产者自己把标签烘进内容](interviews/2026-09-18-dsh-message-types.md)，[legacy 让框架拥有转义](interviews/2026-09-18-legacy-system-reminder.md)——**两家相反，说明这是真的设计选择**。既然我们做成**类型**，生产者交出来的就是一条消息而非一段带标签的文本，**它根本没有机会写歪或伪造**。反过来，约定「自己包起来」，则**任何能左右那段文本的人都能冒充系统说话**——工具返回里带个闭合标签就够了 |
| **说状态的取代，说事的追加** | [DSH 的 `snapshot` / `notice` 两个值](interviews/2026-09-18-dsh-message-types.md) + [PF-010 的三类事件](../PF-010-agent-loop-and-run/design.md#512-事件loop-之外发生的事怎么到-agent-眼前) | 判据唯一：**这条提醒讲的是一个状态，还是一件事**——状态有「当前值」，事只有发生过与没发生过。后果不对称：状态做成追加，记录里躺着三份互相矛盾的说法，**而 agent 不知道哪份是现在的**；事做成取代，**前一个后台任务跑完这件事被后一个覆盖了**，而 agent 还在等它 |
| **内容是一串块，不在进记录时压成文本** | DSH 的块结构 + [PF-006 的附件思路](../PF-006-tools-and-skills/design.md#工具的产出) | 图、思考、结构化参数压成文本就得靠解析捞回来，**而解析会错且错得静默**。要压的时候有的是——发给不支持图的模型时 adapter 自己压，**但那是出门那一刻的事，不是进记录那一刻的事**。这与 PF-006「记录里留引用、要用时才去取」是同一条 |
| **提醒要记得住是哪一处产生的** | §3 的排查场景 | 不记，排查时只剩一句「这条哪来的」。**它不必给 agent 看**——这是给排查的人看的。按[属性优先于新概念](../PF-004-agent-runtime-assembly-and-liveness/design.md)的一贯做法，**这是提醒的一个属性，不是新的一种消息** |
