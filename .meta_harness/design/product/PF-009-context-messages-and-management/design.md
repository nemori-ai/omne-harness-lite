# PF-009：上下文消息类型与上下文管理

- 修订：rev 1 · **草稿**，2026-09-18 · [变更历史](changelog.md)
- 状态：**设计未完成**。本版只做**消息类型**这一块，上下文管理尚未开始。**不要据此实施。**

## 一、背景与问题

前面几个 topic 都在往上下文里放东西，**却没有人说过上下文里一共有哪几种东西**。

| 谁 | 往里放了什么 |
|---|---|
| [PF-004](../PF-004-agent-runtime-assembly-and-liveness/design.md) | 系统提示词的成分，以及它在哪一刻定死 |
| [PF-006](../PF-006-tools-and-skills/design.md) | 工具的返回怎么进消息；[卸载](../PF-006-tools-and-skills/design.md#610-结果太大时卸载而卸载是第三个维度)后换成占位；转后台先放占位 |
| [PF-007](../PF-007-meta-capabilities/design.md) | [十二扇门](../PF-007-meta-capabilities/design.md#54-十二个槽位是预算的地板也是它的天花板意义)常驻占预算 |
| [PF-008](../PF-008-human-in-the-loop/design.md) | 卡片答完之后，结果回到那次 run |
| [PF-010](../PF-010-agent-loop-and-run/design.md) | 事件收进记录，**下一次组装时「做成 system reminder 类型的消息」** |

**每一处都在说「变成一条消息」，而「消息有哪几种」从没定义过。**

四个问题因此悬着：

- **一条消息到底是谁说的？**系统插进来的提醒，与用户真的说的话，
  如果在记录里长得一样——**agent 会把系统的话当成人的话去回应**，
  而「用户到底说了什么」这个事实，从此要靠猜。
- **同一份上下文发给不同供应商，形状并不一样。**谁负责翻译？
  翻译规则写在哪？定不下来，换一家模型就要重写一遍上下文的组装逻辑。
- **压缩产出的那份摘要，是一条什么？**[PF-010 明确把这个问题留给了这里](../PF-010-agent-loop-and-run/design.md#91-依赖-pf-009已开始仍是草稿)。
- **卸载后的占位、转后台的占位，算哪一类？**它们既不是工具真的返回了什么，
  也不是系统在说话。

本 topic 把这些补上。**本版先做第一块：消息一共有哪几种。**

## 二、目标与非目标

### 目标

1. **定义消息类型清单**：一次对话的记录里，可能出现哪几种消息，各自是谁在说话。
2. **定义 `SystemReminderMessage`**：它为什么必须是独立的一种，
   以及它**怎么落到各家供应商**——那里并没有这一种。
3. **定义「一条消息分次到达」**：它与消息类型是什么关系、断在半路怎么收场。
4. **定义上下文管理**：压缩产出什么形状、摘要怎么组织、上下文怎么组装成一次请求。
   **本版尚未开始。**

### 非目标

| 不做什么 | 为什么 |
|---|---|
| 每种消息**具体有哪些字段、叫什么名字** | 产品定**有哪几种、各自是谁在说话**；字段与序列化是技术设计 |
| 各家供应商 API 的**具体调用形式** | 产品只定「同一条消息在不同家落成什么」，怎么发是技术设计 |
| 压缩用什么**算法**、摘要由谁生成 | 产品定产物的**形状与性质**，算法是可调的政策 |
| 一次 run 怎么被驱动、事件怎么收进记录 | 归 [PF-010](../PF-010-agent-loop-and-run/README.md)。本 topic 只定**收进来之后做成什么** |
| 系统提示词的**成分与组装时刻** | 归 [PF-004](../PF-004-agent-runtime-assembly-and-liveness/design.md#54-为什么系统提示词必须落在第三列)。本 topic 不重定 |

## 三、用户与场景

| 使用者 | 什么时候接触这块 | 他关心什么 |
|---|---|---|
| **agent 自己** | 每一轮读上下文 | **这条是谁说的？**是人要我做，还是系统告诉我发生了件事 |
| **写 adapter 的人** | 接一家新的模型供应商 | 我拿到一条内部消息，**该把它变成那边的什么** |
| **排查上下文问题的人** | agent 答非所问、或者对着系统提醒回话 | 这条消息**是哪来的**？它本来该长什么样 |
| **工具作者** | 工具返回很大、或者转了后台 | 我的返回**落成一条什么**，agent 看到的是什么 |
| **产品负责人** | 决定要不要换模型供应商 | 换一家，**agent 的行为会不会变** |

**第一行仍然是直接消费者。**它分不清「系统插的话」与「人说的话」，
就会把一条提醒当成指令去执行，或者对着一条通知回一句「好的」。

### 消息

**一条对话记录。**它是[记录](../PF-010-agent-loop-and-run/design.md#记录)的组成单位，
也是喂给模型的那份上下文的组成单位——**这两者本来就是同一串东西**。

### 五种消息，按「谁在说话」分

| 谁在说 | 这一种 | 它说的是什么 |
|---|---|---|
| **系统**，在开头 | `SystemMessage` | 你是谁、你该怎么做 |
| **人** | `UserMessage` | 我要你做什么 |
| **模型** | `AssistantMessage` | 我的回答，以及我要调哪些工具 |
| **工具** | `ToolMessage` | 你让我跑的那个，结果是这样 |
| **系统**，在中途 | **`SystemReminderMessage`** | **外面有信息进来了，你得知道** |

**前四种各家模型供应商都有，最后一种是我们加的。**

> **头一种与末一种都是系统在说话，但说的不是一回事。**

`SystemMessage` 说的是**长期成立的设定**——它在[实例存续期内恒定](../PF-004-agent-runtime-assembly-and-liveness/design.md#54-为什么系统提示词必须落在第三列)。
`SystemReminderMessage` 说的是**刚刚发生的事**，它随时可能出现，出现在对话中间。
**把后者做成前者，等于把一件偶发的事写进了长期设定。**

### 消息的内容是一串块，不是一段文本

一条消息里装的是**若干个块**，块有这么几类：

| 块 | 装什么 |
|---|---|
| **文本** | 给人和模型看的话 |
| **思考** | 模型的推理过程——**与它给人看的话分开** |
| **图** | 图片本身 |
| **文件** | 一个[附件](../PF-006-tools-and-skills/design.md#工具的产出)的引用，**不是文件内容** |
| **工具调用** | 模型要调哪个工具、传什么参数 |
| **工具结果** | 一次调用的结果，**它自己又是一串块**（所以工具也能返回图） |

**为什么不能是一段文本**：一条消息里可能既有文字又有图；
模型的思考与它的回答是两回事，混在一起就再也分不开；
工具调用的参数是结构化的，压成文本就要靠解析捞回来——**而解析会错**。

### SystemReminderMessage

**一次 run 中，接收到了来自外部的信息。**

**「外部」是相对这次 run 说的**——不是 agent 自己做出来的，也不是人直接对它说的：

| 外面是谁 | 什么样的信息 |
|---|---|
| **另一个会话里的 agent** | 它发来一条消息 |
| **自己派出去的 subagent** | 它干完了，回来报告 |
| **后台的工具执行** | 跑完了，结果回来了 |
| **环境** | 组织与账号的上下文变了，以及将来别的[视角](../PF-007-meta-capabilities/design.md#612-cordis通向系统自身的装配定义完整本版不实现) |

**来源是它的一个属性，不是另一种消息。**

> **这几样对这次 run 来说是同一件事：外面有信息进来了。**

为每一类来源另立一种消息，五种就会变成七种八种，**而 agent 的处理方式并没有因此不同**——
它照样是「读一读，然后接着干」。何况**消息的正文本身就说得清是什么事**，
agent 读得懂，**不必靠类型去认**。

它有三条性质：

- **它不是任何一家供应商的标准类型。**各家都没有这一种——
  所以它**必须在发出去之前被翻译掉**（§5.2）。
- **它由系统产生，不由人产生。**哪怕正文里转述的是另一个 agent 说的话，
  **说这句话的仍然是系统**——是系统在告诉这个 agent「外面有人捎了话来」。
- **它是记录的一部分，不是临时的。**落进[记录](../PF-010-agent-loop-and-run/design.md#记录)、
  参与压缩、恢复时读得回来——与别的消息一视同仁。

## 五、模型

### 5.1 为什么它必须是独立的一种，而不是「一条带标记的用户消息」

最省事的做法是：就发一条 `UserMessage`，内容里加个标记说「这是系统说的」。
**三条理由否掉它。**

#### 一、记录里要分得开

[记录是唯一的真相来源](../PF-010-agent-loop-and-run/design.md#52-记录是唯一的真相来源)。
提醒要是混在 `UserMessage` 里，**「用户到底说了什么」这个事实就得靠解析内容才能回答**。

> **而解析会错，标记会被伪造。**

#### 二、每一家最合适的落点不一样

openai 那边有 `DeveloperMessage` 这一种，语义上比 `UserMessage` 贴切得多；
anthropic 那边没有，只能落成 `UserMessage`。

**在我们的模型里就定死成用户消息，openai 那边就永远用不上更合适的那个。**

> **把选择推迟到 adapter，是让每一家都能用它最合适的形状。**

#### 三、正因为它是一种类型，adapter 才有东西可认

这条听着像循环，其实是实打实的：adapter 要做映射，得先认得出「这是一条提醒」。
**认的是类型，不是内容里的字符串**——后者谁都写得出来。

### 5.2 它在各家落成什么

```text
              我们的记录里
          SystemReminderMessage
                    │
          ┌─────────┴─────────┐
          ↓                   ↓
      openai              anthropic
   DeveloperMessage      UserMessage
```

**这不是我们发明的怪招。**同一个内部类型因供应商能力不同而落成不同角色，
[DSH 已经有现成的先例](interviews/2026-09-18-dsh-message-types.md)：
一条不在开头的 `SystemMessage`，在一条路线上仍是 system，在另一条路线上**被折叠成 user**。

**映射表归 adapter，不归本 topic。**本 topic 定的是：

> **每一家都必须给出一个落点，而且必须落成那一家真的支持的类型。**

**不许落成「发不出去」的东西**，也**不许因为某家没有合适的就把这条提醒丢掉**——
丢掉意味着 agent 在那一家上永远看不到系统在说什么，
**而同一个 agent 换一家模型行为就变了**。

### 5.3 落到对面之后，agent 还得分得出

anthropic 那边它就是一条 `UserMessage`——**agent 看到的和用户真的说话长得一样**。
所以**内容上必须自带标识**。

**而这个标识由系统加，不由产生提醒的那一处加。**

> **这正是「独立类型」比「约定一个文本封套」更安全的地方。**

产生提醒的那一处交出来的是**一条消息**，不是一段带标签的文本——
**它根本没有机会把标签写歪，也没有机会伪造一个**。
反过来，如果约定「自己把内容包进某个标签里」，那么**任何能左右那段文本的人都能冒充系统说话**——
一个工具的返回里带上一个闭合标签就够了，**而 agent 没有任何办法分辨**。

**这一条对工具返回、对外部来的内容尤其硬**，因为那些内容本来就不受我们控制。

### 5.4 提醒说的是「现在什么样」，还是「刚才发生了什么」

**这两种提醒的命运不一样，必须分开。**

| 它说的是 | 新的来了，旧的怎么办 | 例子 |
|---|---|---|
| **现在是什么样** | **取代**——只留最新的那份 | 组织与账号的[上下文](../PF-007-meta-capabilities/design.md#612-cordis通向系统自身的装配定义完整本版不实现)变了 |
| **刚才发生了什么** | **追加**——旧的照样留着 | 一个后台工具跑完了、一次执行转了后台 |

**不分开的后果是不对称的：**

- 把「现在什么样」做成追加：组织信息变过三次，记录里就躺着**三份互相矛盾的说法**，
  而 **agent 不知道哪份是现在的**。它多半会信最早看到的那份——**因为那份离它的任务描述最近**。
- 把「刚才发生了什么」做成取代：**前一个后台任务跑完这件事，被后一个覆盖掉了**，
  而 agent 还在等那个结果。

> **判据很简单：这条提醒讲的是一个状态，还是一件事。**

状态有「当前值」，事没有——**事只有发生过与没发生过**。

**[PF-010 的三类事件](../PF-010-agent-loop-and-run/design.md#512-事件loop-之外发生的事怎么到-agent-眼前)由此各归其位**：
工具转后台、后台执行完成回传，都是**事**；注入的上下文变动，是**状态**。

### 5.5 一条消息是分次到达的

**模型的回复不是一下子给的，是一段一段来的。**用户要看见字往外冒，
而不是盯着空白等三十秒。

> **但分次到达的那些东西，不是第六种消息。**

五种消息回答**谁在说话**；这里回答的是**这一条正在怎样到达**。
两个问题，**所以是两套词表，正交**。

#### 能一点点长出来的，与要么没有要么整个有的

| | 哪些 | 怎么到 |
|---|---|---|
| **能一点点长** | 文本、模型的思考、**工具调用的参数** | 一段一段来 |
| **不能** | 图、文件、工具结果 | **开个口，然后整个交出来** |

> **半张图没有意义。**

**这条分界决定了流式那套词表能有多小**——不必为每一类内容都设计一种增量。
将来多出新的内容块，它照样能走「开口 + 整个交出来」这条路，
**而流式的词表一个字都不用改**。

#### 到达的过程有它自己的语法

```text
开一个块 ──→ 往里填（只有三样能填）──→ 封上这个块
                                            │
                                    记一次账 ──→ 收尾
```

三条要紧的性质：

- **封口的时候交出的是完整的那一块。**消费的一方**可以**自己把增量拼起来，
  但**不必**——**两边各拼一次，就有了两个可能不一致的答案**。
- **一条流必须有结局。**没有结局，等着的那一方**永远不知道该不该继续等**。
- **账只记一次。**记两次就是两次计费，**而这种错查起来极贵**。

#### 半条消息不是消息

**不要造一个「半条消息」的类型出来。**

[LangChain 是另一种做法](interviews/2026-09-18-dsh-streaming.md)——那边的半条消息是消息的子类，
两半能加起来。**我们不走那条路**，因为[记录是唯一的真相来源](../PF-010-agent-loop-and-run/design.md#52-记录是唯一的真相来源)：

> **记录里要是能躺着半条消息，读到它的人分不出「还没说完」与「说到一半被掐了」。**

**没说完的东西只是一个正在长的块，不是一条消息。**
它要么长成一条完整的消息，要么按 §5.6 收场——**没有第三种下场**。

#### 组装出来的，必须与一次性拿到的一模一样

**这是一条可验证的性质，不是一句愿望。**

同一次回复，分十次到达再拼起来，与一次性拿到，
**必须得到完全相同的一条消息**。做不到，
「agent 看到了什么」就取决于当时网络怎么样——**而那是不可复现的**。

### 5.6 流断在半路

**已经到了的那部分，不丢。**但落成什么，看它为什么断：

| 为什么断 | 记录里留下什么 |
|---|---|
| **用户叫停，而且已经有内容到了用户眼前** | **一条完整的消息，但标明它是被中断的**——内容就是已经交付的那部分 |
| **用户叫停，但什么都还没出来** | **不留消息**。这次尝试留一笔账，**但它不进 agent 看得见的历史** |
| **出错断的** | 同上：留一笔账，**不伪造任何 agent 看得见的内容** |
| **写到上限截断的** | 是一条正常的消息，**但其中的工具调用一个都不留**（见下） |

**两条硬规矩：**

> **一、被中断的消息里，工具调用一个都不留。**

因为**中断发生在动手之前**——那些调用还没派发出去。
留着一个，就得给它配一个结果，**而那个结果只能是凭空造的**。
这与 [PF-010 尾部对账](../PF-010-agent-loop-and-run/design.md#59-恢复重新算一遍-f但尾巴要先对账)
处理悬空调用是同一条思路，也与
[PF-006「被中断不是失败」](../PF-006-tools-and-skills/design.md#67-用户可以中断而中断不是失败)一致。

> **二、什么都没出来的那次，不许伪造成一条空消息。**

一条空的 assistant 消息是在说「模型什么也没说」，**而事实是它没说完**。
两者对 agent 的下一步判断完全不同。

#### 用户看见了的，记录里必须有

**这是「记录是唯一真相来源」在流式下的样子。**

用户已经看见半句话了，记录里要是没有——**他刷新一下页面，那半句就凭空消失了**，
而他会以为自己看错了。反过来，记录里有而用户没看见，同样是错的。

**所以第一行那种情形必须留下消息**，哪怕它没说完。

#### 工具调用的参数，收齐了才算数

参数是一段一段到的，**中间任何时刻它都是一段不完整的文本**。

> **不要试图去解析没收齐的参数。**

一个残缺的 JSON **解析出来的东西比解析失败更危险**——
它可能恰好是合法的，**而少了一半字段**。

**解析只发生一次：收齐之后、动手之前。**

## 六、产品规则

### 6.1 一条消息是谁说的，永远查得到，且不靠解析内容

**五种就是五种。**「这条是人说的还是系统插的」这个问题，
**看它是哪一种就答得出来**，不必去读内容、不必找标记。

**内容里的标记只服务于 agent**（因为它到了对面只剩四种），
**不服务于我们自己的记录**——记录里那个答案必须是确定的。

### 6.2 每一家都要有落点，不许落空，也不许丢

接一家新的模型供应商，**必须为 `SystemReminderMessage` 指定一个落点**，
而且那个落点得是那一家真的支持的类型。

**不许丢掉。**丢了，agent 在那一家上就永远看不见系统在说什么——
**同一个 agent 换一家模型，行为就变了**，而没人查得出为什么。

### 6.3 提醒的标识由系统加，产生提醒的那一处交的是消息

**产生提醒的那一处，交出来的是一条消息，不是一段带标签的文本。**

不守这条，**任何能左右那段文本的人都能冒充系统说话**——
工具的返回、外部来的内容、用户自己粘进来的东西，都可以。
**而 agent 没有任何办法分辨。**

### 6.4 说状态的取代，说事的追加

判据见 §5.4：**这条提醒讲的是一个状态，还是一件事。**

**同一处产生的状态类提醒，新的来了就取代旧的**；
事件类的一律追加，**谁也不覆盖谁**。

### 6.5 来源是一个属性，不是另一种消息

外面是谁捎来的信息——另一个会话的 agent、自己的 subagent、一个后台执行、环境本身——
**记在一个来源属性里**（§4）。

**不为每一类来源另立一种消息。**它们对这次 run 来说是同一件事，
**agent 的处理方式也没有因此不同**。

**而 agent 主要靠正文读懂这是什么事**——正文本来就该说得清楚。
来源属性是**额外的一份确凿信息**：给排查的人用，
也可以给 agent 用（比如它要回话给捎信的那一方）。

### 6.6 内容是块，不在进记录时压成文本

图就是图，工具调用的参数就是结构化的参数。
**压成文本，就得靠解析捞回来——而解析会错，而且错得静默。**

> **要压成文本的时候有的是**——发给一个不支持图的模型时，adapter 自己去压。
> **但那是出门那一刻的事，不是进记录那一刻的事。**

这与 [PF-006 的附件](../PF-006-tools-and-skills/design.md#工具的产出)是同一条思路：
**记录里留的是引用，要用的时候才去取**。

### 6.7 分次到达的东西，不进消息类型清单

**五种就是五种**（§6.1）。一条正在长的块**不是一条消息**，
**不能被当成消息存进记录、也不能被当成消息喂给 agent**。

它要么长成一条完整的消息，要么按 §5.6 收场。

### 6.8 组装的结果与一次性拿到的必须相同

**这是可验证的**：同一次回复，分十次到达再拼，与一次性拿到，
**得到的消息必须完全相同**。

不成立，则「agent 看到了什么」取决于当时网络怎么样——**而那不可复现**。

### 6.9 用户看见了的，记录里必须有

流断在半路而用户已经看见内容了，**那部分必须落成一条（标明被中断的）消息**。

**记录里没有，用户刷新一下页面那半句就凭空消失了**——而他会以为自己看错了。

### 6.10 没收齐的工具调用参数，不解析、不执行

**一个残缺的参数解析出来的东西，比解析失败更危险**——
它可能恰好是合法的，**而少了一半字段**。

**解析只发生一次：收齐之后、动手之前。**

## 七、取舍

| 选择 | 取的 | 舍的 |
|---|---|---|
| **`SystemReminderMessage` 独立成一种**，而不是带标记的用户消息 | 记录里分得开；每家用最合适的落点；adapter 认得出 | 它在任何一家都不存在，**每接一家都得多定一条映射** |
| **映射推迟到 adapter**，模型层不定死 | 换供应商不改变语义；openai 能用上 `DeveloperMessage` | 同一条提醒在不同家**长相确实不同**，排查跨供应商问题时要多想一层 |
| **标识由系统加**，不让生产者自己包 | 伪造不了——**这是安全性质，不是洁癖** | 生产者少了一点自由；想自定义样式得走别的路 |
| **状态取代、事件追加**，而不是一律追加 | agent 不会看到三份互相矛盾的「当前状态」 | 多一个维度要判断，**而判错了的后果两个方向不一样** |
| **内容是块，不是文本** | 图、思考、结构化参数都留得住原样 | 比一根字符串复杂；每接一家都要处理「这家支持哪些块」 |
| **提醒是记录的一部分**，不是临时的 | 恢复读得回来，压缩看得见它 | 它会一直占着上下文，**直到被压缩收走** |
| **流式另立一套词表**，与五种消息正交 | 消息类型清单不被流式撑大；将来加内容块**不必动流式那一套** | 两套词表都要维护，**而且两者的对应关系要说清楚** |
| **只给「能一点点长」的三样做增量**，其余整个交出来 | 词表极小；**半张图这种没意义的东西根本表达不出来** | 插件新加的内容块**拿不到增量能力**——只能等它整个好了再给 |
| **不造「半条消息」这个类型** | 记录里不会躺着说不清楚的东西 | 与 [LangChain 那种做法](interviews/2026-09-18-dsh-streaming.md)不同，**从那边迁过来的人要改习惯** |
| **中断时留下已交付的部分**，而不是当这次没发生 | 用户看见的与记录里的对得上 | 记录里会有「没说完」的消息，**下游每一处都得认得这个标记** |

## 九、未决项

### 9.1 上下文管理整块尚未开始

**本版只做了消息类型。**以下全部尚未开始：

| 缺口 | 影响 |
|---|---|
| **压缩产出什么形状、摘要怎么组织** | [PF-010 明确把这个留给了这里](../PF-010-agent-loop-and-run/design.md#91-依赖-pf-009已开始仍是草稿)，那边的 §5.5 悬着 |
| **上下文怎么组装成一次请求** | 谁在前谁在后、常驻部分怎么摆 |
| **卸载后的占位算哪一种消息** | PF-006 定了它的语义，没定它的形状 |
| **决策卡片的答复落成哪一种** | PF-008 定了答复要回到那次 run，没定它长什么样 |

### 9.2 流式里还剩一件事没定

**这一整块是产品负责人指出的缺口**——rev 1 最初只定义了「完整的一条消息」，
**压根没想到分次到达**。§5.5、§5.6、§6.7–6.10 是补上的。

**剩下一件事：记录里除了最终的消息，要不要把「它当时是怎么一点点到的」也留住。**

| 做法 | 换来 | 代价 |
|---|---|---|
| **只留最终的消息**（外加中断时的那条） | 记录小，简单 | **重现不了当时的样子**——出问题时没法回放 |
| **把到达过程也留住** | 能原样回放，排查流式问题有据可查 | 记录变大；**「原样」到什么程度也得定** |

**PM 没有倾向**——这取决于「要不要支持回放当时的样子」这个产品能力，
**而那件事本 topic 答不了**。

> 参考：[DSH 选了第二条](interviews/2026-09-18-dsh-streaming.md)，
> 而且那边**明确拒绝过**「只存装配后的消息」这个提案。**但那是他们的取舍，不是我们的依据。**

**不定它，§6.9「用户看见了的记录里必须有」仍然成立**——
那一条只要求中断时留下已交付的部分，**不要求留住到达的过程**。
