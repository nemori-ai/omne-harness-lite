## INT-005：独立日历服务应用的候选建议

- actor：设计协作者；类型：分析建议；表达方式：recorder-interpretation。
- 状态：独立产品应用定位由 INT-006 确认；产品独立与部署位置的关系按 INT-006 纠正。其余分析不因这一确认而整包获批，未据此新增实现 app 或正式产品正文。
- 依据：INT-001 / INT-003 已确认的责任边界，以及研究 K7/K8 中独立查询、持续供应、版本、健康与首装承诺。
- 判断：具备独立消费者、独立运维责任与不依赖会话生灭的生命周期，足以支持独立应用的产品定位；可独立部署的价值在部署者可以只取得日历能力，并独立维护升级，不依赖日程或 agent 运行。
- 推荐定位（候选）：可独立部署、持续维护权威日历数据，并向消费者提供可追溯日历查询与计算结果的服务应用。
- 比较：仅嵌入 harness 的形态安装简单，但单独使用和独立维护受宿主约束；独立应用有自己的部署与故障责任，需要补足入口、可用性、升级和恢复的产品规则。
- 组合解释：底层日历能力仍可单独取用、被 Cordis 装配；独立 app 是它的一种完整交付方式。成为应用不推导每个 agent 单独部署，也不推导首版必须远程联网调用。
- 首版建议：完整交付可先与 harness 在同一台机器安装运行，保留首装离线可用承诺；集中远程查询、集中供数加本地计算等拓扑不在本条拍定。
- 产品责任候选：供应/校验/版本/查询计算/健康与管理入口；日程与目标、任务推进、未来安排采用新版本的政策继续归日程侧。
- 成本与后续：必须定义谁部署谁调用、停止/升级/数据缺失时的结果，以及新版发布时间与消费者采用时间的区别；独立服务进程停止后的本地继续计算并非已确认承诺。网页 UI、多租户日历编辑、公共 SaaS 不由独立 app 自动推出。
- 术语核对：UL-delivery-surface（PF-016 rev 10）专指向人投影会话日志及接收入站的界面，且不持有领域事实；本候选持有日历领域数据，讨论时使用「日历服务应用」描述，不静默扩张「交付面」词义。未新增正式词条。
- 本项目参照：PF-017 区分领域规则与应用部署/运行责任；这里只借用问题划分，不继承其组织内网、身份与运维政策。

## INT-008：线性与非线性的来源核对及公开纠正

- actor：设计协作者；类型：事实核对、纠正；表达方式：paraphrase。
- 上游：omne-next @ 6263fed545e48ad9efb5714f3fe76a7c1a0af1b5；requirements/capabilities/state-owner-scoped-deterministic-nonlinear-schedule-recurrence.md「表达、预览与兼容承诺」及前导范围，design_docs/cross-cutting/scheduling-expressiveness.md §2。
- 事实：上游非线性仅指确定性的复杂 calendar recurrence arithmetic，例如每月第一个周一、每季度最后一个周五、有限次数及例外组合；不包含任务 DAG、结果驱动的下一时刻、事件条件或自适应重排。基础规则与业务日历数据是两个正交输入。
- 纠正：撤回 INT-002 对「非线性」的初步解释。按任务进展调整安排可以是上层 agent 利用日程能力的行为，但不能从这个术语自动推出已支持条件工作流。
- 查词范围：本项目词条索引及上游 requirements/design_docs/adrs 的相关检索未得到 Routine 的产品定义；Scheduled Job 仅见局部叙述，不能据此声称三者已有上游权威分工。

## INT-009：业务模型候选（尚未定稿）

- actor：设计协作者；类型：建模建议；表达方式：recorder-interpretation。
- 状态：候选，用于当前讨论；未新增正式词条、领域对象条目或产品正文。其中执行型 Job 与 Run 的直接对应、向已有会话投递的分析已由 INT-011 改为 Job 关联专属新会话；其余术语分工仍未定稿。
- 建议按「做什么／何时做／这一次」分工：Routine 是可复用的工作定义（执行交代或通知内容及目标）；Schedule 是绑定 Routine 的一次性或重复时间安排，拥有时间规则、时区、日历使用规则和有效边界；Scheduled Job 是某份 Schedule 在一个具体到期时刻对应的单次工作实例，带出处及所采用定义，追踪本次处置。
- Routine 表达可重复使用的内容，重复日期归 Schedule；一次性工作同样可以使用这套模型。产品入口可以一次提交内容与时间，不要求用户先另建一份 Routine。
- 两种动作均可按上述三层表达：执行型 Job 目标是触发一次逻辑 Run；通知型 Job 直接产生用户通知，不为纯通知启动 agent。执行后的结果交付与单纯定时通知分开。
- 预览给出候选时刻，不意味着已经发生或已经派出 Job；重复扫描、故障恢复不应把同一到期工作当成新的业务任务。重试策略及物化时机留后续。
- 维度正交：用户或 agent 发起／执行或通知／一次或重复／基础线性或复杂非线性时间表达／短中长期跨度。非线性与长期不各建一套作业生命周期。
- 管理边界候选：身份、租户归属与授权分开于创建者；用户与 agent 管理同一模型，agent 的授权方式未裁。安排暂停、结束与单次工作的结果分开；历史所采用的定义与结果可追溯；新修改对未开始工作的生效边界需明确。
- 目标推进：目标可由 agent 持续规划和调整后续安排，日程负责可靠地保留安排、到点推进及提供结果出处；一次 Job 或 Run 的完成不等于长期目标完成。本轮不从时长自动引入另一种 Goal 对象。
- 场景：明天下午提醒（一次性＋通知）、每天早晨生成摘要（线性重复＋执行）、每月第一个周一提醒（非线性重复＋通知）、每月最后一个中国工作日生成报告（非线性＋日历计算＋执行）。
- 本项目需对接的明确差异：PF-012 rev 15 §Run 规定同会话有未终结 Run 时，新输入并入已有 Run；PF-014 rev 8 为定时输入预留受理去处。因此「每次定时执行触发一次独立 Run」不能只靠向原会话发一条消息兑现。以 INT-007 新要求为输入，保留独立执行意图；目标会话、新建还是续用、忙时排队等尚需明确，不静默改成合并已有 Run。
- 后续影响行为的未定项：具体词义是否采用此候选；作业会话归属；到点忙碌/停机错过/上次未完成的处置；agent 创建或修改的授权及生效规则。它们不妨碍当前三层骨架讨论，但影响后续正式规则。

## INT-010：定时执行的两种会话方式

- actor：产品负责人本人；类型：需求确认；表达方式：quote。
- 内容：「『定时执行』我们需要明确两类：每次执行创建一个新会话 和 每次执行在同一个会话中进行，这意味着是需要在日程定义的那个数据模型中有可以对应声明配置的字段。」
- 状态：已被 INT-011 撤销替代；双模式、模式选择字段及复用同一会话的待裁事项均不再作为当前设计输入。下文保留当时的确认与推导，供追溯。
- 已确认：定时执行支持每次新建会话、各次使用同一会话两类；日程定义中必须有显式声明该选择的配置字段。会话方式不由运行时隐式猜测。
- 记录者推导：结合 INT-007「到点触发一次 agent run」，同一会话模式跨次复用的是会话，各次执行仍有各自的 Run；新会话模式则各次执行拥有不同的会话。两种模式独立于线性/非线性、一次性/重复时间规则；定时通知不使用该执行配置。
- 字段形状建议（非正式 Schema）：日程的定时执行配置包含「执行会话方式」；同一会话模式还须能确定稳定的目标会话，具体引用字段及绑定时机未定。Scheduled Job 记录本次实际的会话与 Run 关联。
- 未定：同一会话是选择现有会话还是首次执行时建立；新会话的 agent/上下文等创建配置；默认模式；模式可否修改及生效边界；会话忙碌、已归档、不可用的处置；重试与会话创建的关系。
- 对接保留：PF-012 现行同会话单活跃及新输入并入规则仍需对接。不得据本条默认允许同一会话并发 Run，也不得把到期工作静默并入别的 Run；具体等待或其他处置后续裁定。

## INT-011：定时执行统一使用专属新会话

- actor：产品负责人本人；类型：修正与裁决；表达方式：paraphrase，保留必要短原话。
- 理由原话：「这样看下来反而系统设计变得复杂而去有些问题没法解决」。
- 裁决原话：「定时执行，每次都是创建一个新的会话来执行，不在同一个会话里面承载多个定时任务的执行」「Scheduled Job 只需要和会话关联即可」。
- 忠实转述：定时执行每次新建会话，撤销同一会话复用模式。该会话中的 agent 必须装配统一的成果交付/上报工具，面向关联 Job 交付或上报成果；同时有 hook 确保其完成 Job 目标。用户以 Claude Code / Codex 的 goal slash command 机制作类比，未要求复制其具体实现。
- 子类型理由：产品负责人明确将其视为会话的子类型，而非特定 AgentDefinition，因为特殊之处在于 Agent Loop 的额外定制；无论选择哪份 AgentDefinition，都须附加统一成果提交/上报工具。
- 状态：当前有效；取代 INT-010 全部双模式设计，修正 INT-007/009 中用单次 Run 作为 Job 直接承接单位的解释。
- 当前确定关系：执行型 Scheduled Job 关联为本次工作新建的专属会话；Job 无需额外以某个 Run 作为业务关联单位。会话内正常执行记录仍归现有会话/Run 模型，不因取消 Job 的直接 Run 关联而移除。
- 记录者推导：日程定义不再需要「新建/复用会话」模式开关或复用目标会话配置；需保留新会话的装配输入。专属会话的统一工具与完成检查由该会话的要求保证，不能依赖某份 AgentDefinition 恰好自带。成果呈报与目标完成判定应有明确分工，普通回复或停止输出不能被直接当作 Job 已完成。
- 对接发现：PF-015 rev 13 的「会话类型」当前表示从 AgentDefinition 推导出的用途类目（coding/research 等），其本身不改变放行规则。本次新增子类型表达承接 Job 的执行约束，不能静默塞进用途类目或要求另建一种 AgentDefinition；正式落盘需对齐 PF-015/PF-004/PF-012。将用途与该执行子类型作为可并存维度是记录者建议，尚未改写现行正文。
- 现有可参考机制：PF-012 rev 15 已有 Loop「落终态之前」拓展位置及否决停下的能力；本条未选定技术绑定、未改变内核方程，也未验证任一现有 hook 足以兑现全部目标语义。
- 仍待细化：目标及完成判据如何表达、谁判定成果符合目标、进度上报与最终提交如何区分；无法完成/失败/取消的出口；会话完成后归档方式；同一 Job 的恢复及重试是否/何时新建会话。不得将 hook 存在说成对任意目标成功的保证，也不得默认无限续跑或抵消用户停止。
- 定时通知仍保持直接通知用户的分支，不据此次执行会话裁决创建通知用 agent 会话。

## INT-013：确认三层定义

- actor：产品负责人本人；类型：确认；表达方式：quote。

## INT-019：两类 agent 的原子行动与工具命名讨论

- actor：产品负责人本人；类型：讨论请求；表达方式：quote。
- 原话：「那接下来，我们将 agent 分成两类：1）创建、维护管理日程的；2）日程到点执行后干活的。这两个方向，在日历、日程这块儿，拆解成原子动作来设计可以做的行动空间，我们可以分别命名出哪些工具/工具命令？」。
- 状态：本轮展开两类行动空间与工具候选；具体命名、操作集合与状态转移尚未裁决，不升级正文。

### 协作者候选（未接受）

按 PF-006 多命令范式提出六组普通工具；不是新增 meta 能力，也不要求创建两种固定 AgentDefinition。两组行动空间可按装配和权限组合。

| 工具候选 | 原子命令候选 | 使用范围 |
|---|---|---|
| Calendars() | list、get、classify_date、add_workdays、count_workdays | 两类 agent 可按需计算日期；读取版本、覆盖和来源；不包含系统供应更新管理 |
| Routines() | list、get、create、update | 管理 agent 管工作内容；出厂提供的内容可发现和读取，修改权与采用规则另定 |
| Schedules() | list、get、preview、create、update、pause、resume、stop | 管理 agent 管时间安排；preview 不保存，pause/resume 管未来调度，stop 拟表示结束后续安排，不默认取消已启动 Job |
| ScheduledJobs() | list、get | 管理 agent 查看到期历史、实际结果及通知情况；不由 agent 手工制造到期 Job |
| CurrentJob() | get、report_progress、submit_result、report_problem | 作业会话固定绑定当前 Job；上报和交付不任意填写其他 Job 身份；问题上报不自行裁定 Job 终态 |
| Notifications() | send、get_delivery | 两类 agent 获授权后主动发通知、查看真实交付结果；独立于 Job 成果工具 |

- 管理 agent 的主要空间为 Calendars/Routines/Schedules/ScheduledJobs；执行 agent 的主要空间为只读日历计算与固定当前 Job 的上报交付。执行身份本身不授予修改未来安排权；有需要可另装管理能力。
- CurrentJob.submit_result 提交候选成果，目标完成检查仍生效，不以命令名冒充 Job 已完成；report_problem 表达阻碍或无法继续，不等同于用户取消或系统决定失败。
- Calendar 的持久配置切换与单份 Schedule 选用日历分开；前者作用范围及授权未定，暂不默认提供写租户设置命令。后者可在创建／修改安排时明确日历依据。
- 日历数据刷新发布、系统日程管理不进入普通 agent 行动空间；系统自用机械 Job 不装 CurrentJob。
- delete、run_now、retry、cancel 等依赖留存、生效、重试和取消规则，先不列入建议核心集合；create 是否直接生效、Routine.update 的传播规则仍需闭合 U1/U2。
- 执行并通知 Job 的成果提交与主动 Notifications.send 有不同目的；谁发送配置中的通知、如何防重复仍需随 U7 明确，不因为列出 send 就把系统投递责任交给 agent。
- 六组是按操作对象与绑定范围提出的工具组织，不是技术服务或插件数量；具体命令参数及协议留后续设计。

## INT-020：Routine 与 Schedule 的创建更新是否合并

- actor：产品负责人本人；类型：方案讨论；表达方式：quote。
- 原话：「整体的雏形没问题，现在需要你思考这个问题：一个 routine 和 它的 schedule，在创建和更新的时候，是一起做呢，还是分开做呢，对人和对 agent 分别最友好的操作路径是怎样的？是否值得合并成一个动作？」。

### 协作者建议（候选，未裁决）

默认提供一次创建／修改完整安排的动作，同时保留 Routine 与 Schedule 两个业务对象。对象有独立身份不意味着消费者必须分两次操作。

| 情形 | 候选操作路径 |
|---|---|
| 创建全新安排 | Schedules.create 一次表达工作内容及时间；系统建立 Routine 与 Schedule 并关联，不要求消费者先取得 Routine ID |
| 安排已有／出厂 Routine | 同一 create 入口指定已有内容及时间；不重复创建相同内容定义，不因此改写出厂原件 |
| 修改本安排的内容、时间或两者 | Schedules.update 一次提交完整变更，只影响当前安排；只有时间变化时不改 Routine |
| 修改的内容被其他安排共用或来自不可编辑的出厂原件 | 默认只改当前安排，为其派生可独立修改的内容并重新绑定，其他安排及出厂原件不变；这是建议的产品后果，尚未接受 |
| 有意维护可复用内容或统一影响多个安排 | 保留 Routines.create/update 作为独立操作；明确展示和授权影响范围，不从编辑某份 Schedule 推导批量修改权限；具体传播仍需裁定 |

- 人的路径：在一个创建／编辑页面表达“做什么、何时做、怎样交付”，可选已有 Routine，核对日期预览后一次保存。平常无需管理两个对象 ID；复用与影响范围需要时才出现。
- agent 的路径：一个 create 或 update 调用提交完整意图；成功结果给出 Routine、Schedule 的身份、保存／生效状态及日期解释。preview 按需使用，不强制每次额外调用或人工批准。
- 一次保存须保证内容与时间一起成为有效安排或均不生效，不留下部分成功的活跃安排；成功保存不自动等于已获准启用。授权不能因复合入口而扩大。
- 建议变更以之后新产生的 Job 为界，不回写已产生 Job 的工作定义及历史；该生效边界是本轮建议，非既定规则。
- 比较：强制分开增加人的导航和 agent 的串联调用、ID 传递及半完成恢复；只允许捆绑则妨碍复用与单独维护内容。共同模型加默认复合入口覆盖两种需求；不新增泛化工作流工具。
- 权威状态：本条仅保存判断与候选；PF-021 正文仍 rev 4，U1/U2 的生效、共享内容更新传播及变更范围尚待产品负责人裁定。
