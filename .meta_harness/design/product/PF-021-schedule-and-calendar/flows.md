# PF-021：流程与边界

本文展开 [design.md](design.md) 已确定的旅程与策略组合。精确状态机和可实施契约归后续技术设计，本页不代替技术验证。

## 一、创建租户安排

| 步骤 | 谁做什么 | 可以核对的结果 |
|---|---|---|
| 1 | 用户手动表达，或 agent 使用日程能力表达工作内容与时间 | 确定执行、通知或执行并通知，工作描述填入 Schedule 内的 Routine，并明确日期处理、排除日期、补跑、重叠及适用通知策略 |
| 2 | 解释时间表达；需要日历时请求日期计算 | 看到下一次及有界未来时刻、使用的时间与日历依据；无法计算的原因可见 |
| 3 | 在适用租户与权限下保存安排 | 一次保存包含 Routine、时间与策略配置的 Schedule，返回安排身份及真实生效情况，不另建 Routine 对象 |
| 4 | 按生效规则开始产生到期工作 | 完整且获授权的创建成功即启用；不另设专用草稿审批流程 |

用户在同一入口编辑工作内容、时间与交付要求；agent 一次调用 Schedules.create。
可以先读取出厂预置填入内容，但不要求先创建 Routine 或取得其 ID。
保存不允许部分成功的有效安排；权限未满足或必要信息缺失时不把已输入内容当已启用日程。
创建成功即启用；回执未知时查询实际保存结果，不据未知重复创建；授权确认沿既有规则。

### 修改一份完整安排

用户编辑指定 Schedule，或 agent 调用 Schedules.update，提交内部 Routine、时间、策略类型／参数或其组合的修改。
保存前后的完整安排可核对；只改当前 Schedule，不修改其他日程，也不修改出厂预置。
部分校验或保存失败不能产生新内容配旧时间的部分生效结果；工具返回真实保存与生效状态。
已产生 Job 的工作要求、日期依据与策略不改变，包括等待执行的；update 不改变安排原本的启用、暂停或结束状态。

### 暂停、恢复与结束后续安排

管理 agent 在获授权范围内分别调用 pause、resume 或 stop，得到针对该 Schedule 的处置结果。
这些命令不等同于取消已经开始的 Job，也不删除历史。暂停期间漏过的时刻按日程的补跑声明处理，
resume 不替用户另选策略；结束的安排不能恢复，重复目标状态请求返回真实当前状态；精确转移契约归技术设计。


### 撤回某一次已接受工作

用户从日程工作记录选择 Job，或管理 agent 调用 ScheduledJobs.cancel；系统独立检查取消资格。
尚未开始时，确认取消后该 Job 不再启动；已有会话或 Run 不是前提。已经开始则沿实际动作的停止机制推进，停止确认前显示处理中或受阻。
Schedule、其他 Job、次数消耗与历史都保持原有事实；取消不让这次工作重新成为漏跑。
完成与取消竞争按实际先后返回；已终结的执行不改成取消，纯通知已送出不承诺撤回，组合通知义务沿 design §6.14 保留。
用户可继续用 ScheduledJobs.get 查看停止进展；依赖恢复与宿主重启不复活已取消工作。

### 系统自用安排与出厂内容

系统创建内含机械 Routine 与时间安排的 Schedule，以系统归属保存；不要求先有账号、组织或租户。
到期 Job 保持系统归属，触发预先定义的机械操作并记录真实结果，不新建 agent 会话。
需要通知租户时，经通知能力按明确目标与权限交付，通知目的地不改变日程或 Job 的归属。
管理者身份变化不把系统日程移入其个人范围，也不自动删除系统安排。
系统通过机械功能及其部署配置管理自己的安排；基本生效和停止规则同 Schedule，机械功能也明确自己的补跑／重叠及适用通知声明。

系统可出厂提供常规产品级 Routine 描述。经 list_presets/get_preset 读取并采用后，
内容由对应租户的 Schedule 持有，随后沿租户调度、agent 执行或通知旅程进行；
不共享出厂原件的可变内容，不承诺安装即创建、默认启用或自动采用新版内容。

## 二、定时执行

租户日程中执行与执行并通知的 agent 执行部分遵循这条旅程；执行结果不代替通知结果。
系统自用机械执行沿上节流程，不进入作业会话旅程。

```text
某份 Schedule 的下一次预算候选
  → 到期调派前按最新日历及特殊日期依据重算校验
  → 结合补跑和重叠声明判断本次工作是否接受；跳过可查、不伪造 Job
  → 接受后创建 Scheduled Job，固定本次内容、来源时刻、依据与策略
  → 按策略立即执行、等待先前工作或等待停止确认
  → 为它新建专属作业会话
  → 装配所选 AgentDefinition ＋ 统一成果工具 ＋ 目标完成检查
  → agent 用 CurrentJob.get 读取本次要求，开展工作并用 report_progress 上报进展
  → 通过 submit_result 提交候选成果，或 report_problem 上报问题
  → 依据目标完成检查与成果形成 Job 的处置结果
```

- 未创建成功、未满足统一装配要求，不能显示为已经开始执行。
- 两个不同到期 Job 使用不同会话；不提供复用旧会话的分支。
- 关联会话中的 Run 仍按既有规则执行，不用其终态直接代替 Job 目标完成。
- CurrentJob 固定绑定本会话的 Job，模型不能选择另一个提交目标；它不自动附带 Schedules 管理权限。
- 完成检查对照本次目标与交付要求判断；工具调用成功不能代替成果满足目标。
- 成功、失败、停止与中断处置沿 design §6.10；会话归档沿 PF-015，不另设 Job 专用政策。

### 恢复后的有界补跑

恢复处理取当前时刻 T，识别本日程尚未处理的漏过区间，排除已有 Job 和已有明确跳过处置。
不补跑时记录漏过；补最近 N 次时按最新依据选最近最多 N 次，更早的记为不补；选中的补跑与当前正常到期候选合并，按原定时刻从早到晚处理。
每次接受前重算校验，并按重叠声明处理；因此“补最近三次＋跳过重叠”不承诺三次一定都执行，也可能让后面的当前正常工作因重叠被跳过。
候选撞上本日程既有 Job 的有效时刻时，记录候选跳过，不另建 Job、不往旧 Job 增补来源。
本轮处理过的区间不能在下一轮重开一个 N 次窗口，既有等待 Job 不再次成为补跑对象。
截止限制原定时刻；恢复已过截止时，截止内漏过仍按声明处理，处理完再自然结束。手动 stop 后不新建补跑 Job，补跑也不能超过剩余次数。

### 重叠与等待

跳过不创建本次 Job；并行各自新建独立作业会话；等待的 Job 在到期接受时即已形成事实，之后沿其固定内容执行。
替换先接受新工作并发起对旧工作的停止，停止确认后才能启动；停止失败明确受阻，不暗中并行。
等待或替换受阻期间，不能把未开始的工作显示为正在执行；之后执行仍须通过当前授权与依赖准入。
策略更新对之后接受的新工作生效；新策略可以发起新的停止事实，但不能改写已创建 Job 的采用内容。

## 三、定时通知

```text
通知型安排的某次到期工作
  → 识别本次 Job、通知内容与目标租户
  → 由通知能力发送并送达目标租户
  → 记录实际处置结果
```

这条旅程不启动作业会话，也不调用 agent 来决定通知文案。
通知在目标租户的现有 CLI/TUI 范围内可持久取回即算送达；用户离线不丢失，也不要求已读。不能把发送尝试冒充送达。
需要 agent 临时调查或生成成果且要求通知用户时，使用执行并通知工作类型。

### 执行并通知

同一次到期工作只对应一个 Job：agent 执行部分遵循专属会话旅程，系统机械执行则直接记录操作结果；通知部分承担向目标租户交付通知的义务。
用户能分别看出执行情况、成果和通知情况；不把上报工具成功视为通知已送达。
通知按本次声明的执行事件及对应内容要求触发，未命中事件不产生通知，也不递归通知投递失败。
执行成功且实际触发的声明通知全部送达才算整体成功；执行已完成但通知失败，不能显示两部分都已完成，也不能倒写为从未执行。

### 系统或 agent 主动通知

系统或 agent 表达通知内容与目标租户，在适用权限下发起发送，通知能力承担送达并呈现真实结果。
agent 通过 Notifications.send 发起，并可用 get_delivery 查询该次交付；获取查询定位信息不等于已经送达。
这条旅程不要求来源 Schedule 或 Job，不为发送而额外创建 agent 会话。
同一账号的另一组织身份不是本次目的地；未获授权不能因指定了租户就发送到那里。
目标租户不可用时明确失败或未知，不改投别处；重试机制归技术交接。普通会话回复或 Job 成果提交不能替代该旅程。

## 四、日历首装与持续供应

获授权的使用者能配置、管理、选择和切换日历，并查看所用日历与供应健康。
消费者选择沿既有租户设置；已有 Schedule 的日历身份不自动切换。未形成 Job 的工作在调派前用最新日历校验；供应维护归部署侧，通用运维机制归后续应用设计。


| 旅程 | 正常结果 | 异常边界 |
|---|---|---|
| 首装先载种子 | 中日美均有可用版本；至少完整覆盖发版自然年，信息截至时点保持真实 | 正式发布物种子不满足基线不能宣称满足首装承诺 |
| 首装再尝试刷新 | 有合法新内容时发布新版本 | 失败仍保留种子和安装成功结果，失败事实可见 |
| 重复初始化 | 现有数据不因重载旧种子倒退 | 幂等处理的技术方式归规格 |
| 周期探测与新文件发现 | 按该历节奏取得后续覆盖或修订候选 | 连续失败、覆盖临期可观察；已有可用版保留 |
| 候选校验与发布 | 新版不可变、出处可追溯，当前版明确 | 退化候选不发布；无新出处的静默改动留证待裁 |
| 日程请求计算 | 在覆盖内按所用日历版本返回结果与依据 | 覆盖外明确缺依据；不自行构造缺失日期的答案 |

日历发布新版后，未形成 Job 的候选按最新依据重算，已有 Job 的采用内容和事实不变。
供应恢复后只按 Schedule 声明补调派尚未形成 Job 的漏过时刻，不重新执行已有 Job。

## 五、执行异常与处理边界

| 情形 | 必须保持的边界 | 处理规则及技术承接 |
|---|---|---|
| AgentDefinition 不可用或缺统一工具／完成检查 | 不能当作合格的作业会话继续成功路径；具体原因应可辨认 | 依赖不可用明确失败／受阻；恢复机制归技术交接 |
| agent 停止输出但目标未完成 | 不可直接认定 Job 完成；完成检查仍需生效 | 依据本次目标检查，未达成不宣告成功；无法继续时说明问题并沿既有等待或停止机制处理 |
| 用户要求停止 | 不能由完成检查撤销已有停止权，也不能记为成功 | 沿 PF-012 停止并保留真实外部效果；迟到成果不复活工作，精确转移归技术交接 |
| 会话或宿主中断 | 保留真实执行事实，不能因调度恢复就宣称从未执行过 | 同一运行恢复沿 PF-012 保持原 Job 与会话；外部效果未知如实呈现，不自动重跑已终止工作 |
| 上次 agent Job 还在执行又到下一时刻 | 独立会话不等于自动批准并发，也不合并进上一会话 | 按日程声明选择跳过、替换、并行或等待；补跑也不绕过此选择 |
| 停机时错过若干时刻 | 不伪造已执行或已送达结果 | 按不补或最近 N 次声明处理，补出的 Job 继续使用其工作类型及重叠／通知声明 |
| 系统机械操作失败、中断或结果未知 | 不启动 agent 冒充机械恢复，也不把已触发写成已完成 | 按机械操作实际结果判断，未知不冒充失败；不自动新建业务重跑 |
| 日历依据不足 | 不猜日期，不返回伪造时间 | 依赖日期依据的计算明确受阻；已产生 Job 不被改写，恢复后的漏跑按本日程声明 |
| 修改 Schedule 内 Routine 或时间 | 本安排之外的内容及历史实际执行事实不被改写 | 仅之后产生的 Job 采用新要求；一致性与记录机制归技术交接 |

产品结果与策略边界已定义；精确状态枚举、一致性和故障恢复协议归技术设计，不允许从技术实现默认值反向改写声明。
