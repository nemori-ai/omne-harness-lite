## 二、PM 推导

| 结论 | 前提 | 可核对推理 |
|---|---|---|
| 组合工作仍由同一个 Job 承担，需要 agent 的两类均使用专属新会话 | INT-014 一个 Job 可执行并通知；INT-011 每次执行新建 | 对 agent 执行，增加通知不会取消会话约束；机械执行范围沿 INT-018。Routine 表达两部分内容，Schedule 仍安排时间，执行和通知结果分别呈现 |
| 通知能力不以 Schedule／Job 存在为前提 | INT-015 通知是供系统和 agent 使用的一项系统能力 | 若强制先建日程，通知能力会被缩成定时动作，无法表达已明确的系统和 agent 通知使用面；定时通知是它的消费者之一 |
| 通知必须确定目标租户 | INT-015 对应租户；PF-001 租户定义 | 同一账号可有多个租户，仅知道用户账号不足以确定通知目的地；本能力不新增跨租户权限 |
| 来源与归属分开；系统内部内容与 Job 不借租户归属 | INT-017/018 系统自用独立归属；INT-022 Routine 内含 | 系统 Schedule 内部数据随安排归属，Job 承担其单次工作；租户采用出厂描述后在自己的日程中持有内容，不转移来源或日程归属 |
| 系统机械执行不创建作业会话，专属会话规则限于 agent 执行 | INT-018 自用只能触发机械操作；INT-011 针对 agent 的统一工具和 Loop 要求 | 不需要模型推理与 Agent Loop 的操作没有 agent 会话承接义务；需 agent 的出厂工作归租户，既有租户会话身份可直接承接，不发明系统 agent 身份 |
| Routine 不另立身份与生命周期 | INT-022/023 包含关系；INT-021 检验复用必要性 | Routine 的定位、修改与退出由所属 Schedule 决定，各次 Job 只共用定义，不需要第三个独立管理对象 |
| 创建更新归 Schedules，无独立 Routines 槽 | INT-020 完整意图；INT-022/023 内含及工具更新 | 对同一日程的两部分无需两次有副作用的调用；一次保存不能产生部分生效，读取应直接给出完整内容 |
| 出厂预置查询归 Schedules 的两个只读命令 | INT-018 预置存在；INT-022/023 采用后归日程，取消独立管理槽 | 创建安排前仍需发现和读取产品提供的起点；list_presets/get_preset 承接这两个动作，不另开 CRUD 或引入可写 Routine 对象 |
| 五组普通工具与动作分工 | INT-019 的雏形认可、INT-023 更新授权；PF-006 多命令范式 | 移除独立 Routine 后，日历、日程、Job 历史查询、当前 Job 交付与通知仍有不同对象或绑定范围，保留五组；不升格为 meta |
| CurrentJob 固定当前 Job，submit_result 不叫 complete | INT-011 会话关联与统一交付；目标检查独立 | 任意填 Job ID 会破坏专属成果归属；成果是检查输入，调用成功不替代完成判据 |
| pause/resume/stop 只控制未来安排 | INT-019 原子动作讨论；Schedule 与 Job 分别管理 | 暂停或结束一份时间安排不等于取消某次工作，命令不顺带删除历史；具体合法状态和恢复沿 §6.10，漏跑与重叠沿 §6.11～6.12 的日程声明 |
| 不再设置新建／复用会话开关 | INT-011 每次新建 | 只有一种被允许的行为，不存在供用户选择的另一个有效值 |
| agent Job 不以某次 Run 作为直接业务承接单位 | INT-011 明确只关联会话 | 业务目标与成果交回 Job，会话里的 Run 是其内部工作记录；某个 Run 结束不能替代 Job 完成 |
| 统一成果工具和完成检查由作业会话保证 | INT-011 选任意 AgentDefinition 都要附加 | 若依赖定义自带，换定义便可能失去要求，与“无论选哪份”冲突 |
| 作业子类型与用途分类须分别表达 | INT-011 的 loop 定制；PF-015 现有类型从定义推用途 | 相同定义可用于普通或作业会话，用途不能唯一推导是否承接 Job；不据此新加第六个用途类目 |
| 不自动等同于子会话或派发 | INT-011 只规定专属新会话 | 新建与 parent-child 是不同关系；沿 PF-015 的实际创建关系判断，不另设日程专用的父子关系政策 |
| 安排不随创建它的当次 Run 结束而消失 | 短中长期安排与后续独立新会话 | 若安排随本次 Run 消失，未来到期工作将无可追溯依据；创建会话归档与权限失效的后果不由此推出 |
| 纯定时通知直接交付，不为发送已定义通知启动 agent | INT-007 区分执行与通知；INT-013 内容／时间／实例分工；研究 E08 作旁证 | 通知内容与接收对象已在安排中表达，发送本身不需要 agent 求解；若还需调查或生成成果，则已有执行型承接。此项是 PM 推导，不记成用户逐字排除 |
| 时长不建立另一套 Job 模型 | INT-001 短中长期；INT-013 三层定义 | 时长不改变“内容／何时／某次”分工；长期目标完成仍需另有判据 |
| 租户安排的归属与授权沿已有租户约束 | SYS-TENANCY、PF-001；用户与 agent 都可管理 | 增加入口不产生跨租户权力；具体工具权限沿 PF-002/PF-007，不另设日程授权机制 |
| 日历数据发布与日程采用分开 | 日历是计算依赖，Schedule 拥有时间安排 | 公布新知识与改变一份安排的未来结果是不同产品动作，后者按本次最新依据校验规则处理 |

## 七、日期与可变策略声明的裁决落实

INT-027/028 的直接裁决是：既有 Job 的事实不变；日常预算下一次候选，调派前依据最新日历／特殊日期重算校验；
沿用先前建议的日期解释；补跑、重叠和通知有明确允许类型，作为 Schedule 的可修改配置，在创建或更新时选择。

| 项目 | 当前决定及来源 |
|---|---|
| 日期采用 | INT-027 第 1/2 项：尚未形成 Job 的候选使用最新已发布依据；既有 Job 包括等待中的采用内容不回写。夏令时跳过／取第一次、平移合并、跳过不耗次数、实际工作计次及截止约束沿用研究 K4 的已讨论基线 |
| 技术方向 | INT-027 指定日常 t+1 预算与调派前再校验；原话留访谈，具体预算失效、提前唤醒与校验接受一致性交接技术设计，不把单次预算误读为禁止有界预览或补跑 |
| 补跑 | INT-027 第 3 项、INT-028：Schedule 选择不补或补当前时刻前最近最多 N 次；N 是显式业务上限，创建和更新均能修改 |
| 重叠 | INT-027 第 4 项、INT-028：明确跳过、停止先前后执行、独立并行、等待执行四种类型；是每份 Schedule 的配置，不设置全局单一偏好 |
| 通知 | INT-027 第 5 项、INT-028：声明允许的通知触发事件与内容；开始、成功、失败、取消为可组合事件类型，保存在 Schedule 的内部 Routine 中 |
| 取代范围 | 不采用先前建议的统一漏跑跳过、统一重叠跳过或统一所有结局通知；不再将这三类可配置选择作为过度设计排除。独立重试／补偿体系、任意规则组合与跨日程调优仍不在范围内 |

以下是落地裁决所需的 PM 推导，未冒充用户逐字规定：

| 推导 | 依据及必要后果 |
|---|---|
| 已创建 Job 不变指采用内容与已发生事实不回写，状态仍可继续 | 用户同时要求既有事实不变和“停掉上一次”；停止、结果和进度必须能作为新事实发生，否则两个要求无法同时成立 |
| 排队接受也形成 Job，后续开始不再把它变回日历候选 | 一次到期工作已被接受进入等待，就是既有 Job；以等待为由反复换目标会违背不变原则。首次接受前必须用最新依据校验 |
| 最近 N 次以本次恢复时刻界定，选中后按原时刻从早到晚处理 | 用户用 N 限制业务与资源；若每次检查再取 N 次，实际仍是无界补齐。超过范围和已明确跳过的工作不得下轮再补，已经存在的等待 Job 不算漏过 |
| 截止约束原定时刻，截止内漏过可补；自然结束在漏过区间处置后，手动 stop 不补 | 补跑与等待都允许实际执行晚于原定时刻；把截止同时当成受理期限会静默取消既定补跑声明。手动 stop 是明确停止未来受理的控制事实，不能据旧漏过时刻复活安排 |
| 同一恢复处理中补跑与正常到期候选按原定时刻合并排序 | 补跑原已规定按时间推进，当前工作不应因技术扫描先后随机抢在其前；顺序统一后再应用用户选择的重叠策略，较早补跑也可能导致当前工作被跳过，须可见 |
| 新候选撞上本日程既有 Job 时只记录跳过，不改写或再建 | 已接受事实不可回写，碰撞基线又要求同一时刻一次工作；因此不能给旧 Job 追加来源，也不能为新来源另执行一遍。候选自己的跳过处置保留关联依据 |
| 跳过不建 Job，实际创建 Job 才消耗一次次数 | 已沿用跳过不耗次数；若给跳过也先造工作事实，计数与事实边界会冲突。被跳过的安排仍有可查询处置，不假装执行 |
| 新策略只作用于之后接受的工作；替换停止是独立控制事实 | INT-028 允许更新，INT-027 保护既有事实；因此不能回写旧 Job 的策略，但新工作可以依自身的替换声明请求停止旧工作 |
| 替换须等待停止确认，不支持停止时不能假装替换成功 | 否则“停掉上一次再执行”实际成了未经选择的并行；沿 PF-012 保留未知外部效果，不承诺回滚 |
| 重叠判断按动作阶段；组合通知尾部不单独卡住下一次执行 | 用户讨论的是执行重叠；执行状态与通知状态已分开，通知延迟不能隐式变成执行互斥。纯通知用其交付动作的结束结果判断 |
| 非并行策略面对多个先前工作时按实际集合处理 | 允许从并行改为另一类型；只管最新一个会让其余并行工作继续与新工作冲突。等待须等集合结束，替换须确认集合停止 |
| 通知事件非空、按工作类型适用；未命中不产生义务 | 有条件通知不意味着每次都发。事件选择保存明确，未命中显示不适用；纯通知仍到点发既定内容，不制造执行事件 |
| 通知投递失败不触发执行失败通知；同事件逻辑通知只有一次 | 投递与执行是不同结果；否则一条通知失败会递归制造新通知，也会把传输重试当成多份用户通知 |
| 必需策略由创建／更新明确选择，不暗填默认 | 用户要求按实际任务选择；没有授权把某一种提升为全局默认。已有预置可提供展示后明确采用的配置，不另建策略对象或工具槽 |

统一语言新增三条属性词条；Schedule 与 Scheduled Job 的定义仅精化声明及形成事实的边界，未增加独立业务对象。

| 本次明确的规则 | 性质与依据 |
|---|---|
| 基础规则覆盖一次性、常规周期、位置型周期及明确例外；日期不存在不自动夹到月末 | PM 设计：研究 K4 与已确定的线性／非线性范围；用产品含义约束表达，不把某个库的语法当需求 |
| 非工作日处理四种类型、保持日内时刻、工作日不动，平移可跨周期但不越起止或首次启用 | PM 设计：INT-030 完整定义授权与研究 K4 的跳过／双向平移；避免隐式选方向和把尚未启用的安排补成历史工作 |
| 原日期和结果日期都检查显式排除，结果被排除不再次寻日 | PM 设计：排除表示这一天不做；否则平移会绕过用户的显式排除。固定顺序避免结果由实现默认值决定 |
| 一次性可采用相同日期处理；固定时刻以保持原日表达 | PM 设计：上游 once 与 calendar 的组合限制未被整体接受；本题最新日历校验与统一配置范围适用于全部尚未形成 Job 的候选，不增加另一套一次性调度模型 |
| 单次取消归 ScheduledJobs.cancel，用户提供等价入口，不新增工具槽 | INT-030 同意 INT-029 建议；Schedule 管后续，Job 管本次事实，取消资格与查看资格独立 |
| 等待取消无须会话；运行中等真实停止，终结与取消按先后；通知不承诺撤回 | PM 推导：用户可停止单次工作与事实不回写须同时成立；PF-012 仅覆盖已开始运行，等待阶段由 Job 自己承接取消；取消不是回滚 |
| 执行终结后不取消其已触发通知义务，执行前取消可触发已声明取消通知 | PM 设计：取消针对未结束的主动作，不能把取消入口变成抹除已发生结局或告知义务的手段；纯通知尚未送出则可取消 |
