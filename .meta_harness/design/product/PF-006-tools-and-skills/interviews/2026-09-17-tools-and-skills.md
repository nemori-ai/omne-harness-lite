## INT-001 上下文预算与 meta 标签

- actor：**产品负责人本人**
- 表达方式：`quote`
- 内容：「技能和工具对于系统提示词的组装，因为上下文预算的限制，我们产品上的要求
  不是一个 agent definition 中配好的所有 skills 和 tools 的 descriptions 之类的信息
  全部组装，我们要求的是允许给一个 skill 或一个 tool 声明是否是 meta-skill 或者

  则是通过一个能力发现工具（这是一个 meta-tool，也可能配套有一个相应的 meta-skill，

  记录者在正文中遵守了这一条，未替它做任何假定。
  **用词**：本条及后续 quote 中的「meta 标签 / meta-tool / meta-skill」是产品负责人当时的原话；
  定稿后按 INT-012 的裁决统一改用「**常驻**」，见该条。**quote 一律保留原文，不回改。**

## INT-002 动态创建、独立运行时与工具的可选声明

- actor：**产品负责人本人**
- 表达方式：`quote`
- 内容（同一段陈述的四项要求）：
  1. 「agent 要有运行过程中动态创建、修改技能的能力，当然这需要在被授权
     （也就是权限允许）的情况下」；工具同理。
  2. 「工具执行应当有自己独立的运行时（和 agent runtime 解耦），这样才能过允许
     一个 tool execution 能过在后台执行」。
  3. 「tool definition 要能过可选地声明这个工具是否可以执行在后台、是否可以在前台
     执行超过指定（一种工具的设置项）时长后自动转后台、工具是否拥有非宿主机的执行环境
     （也就是一个工具的开发者首先自己分析这个工具的执行是否是绝对安全的，如果不是，
     那么 ta 需要有途径能过在定义工具的时候就声明要用哪种类型的沙箱）」。
  4. 「系统要有能力根据声明在运行时自动执行相应的策略或机制，以及根据权限的变化
     动态执行不同的注入替换。」
- 状态：当前有效
- 记录者注：第 3 项里「工具开发者自己分析是否绝对安全」这句是**后来推出
  「不得降级满足」的依据**——声明本身就是那个安全判断。

## INT-004 工具执行机制的几项要求

- actor：**产品负责人本人**
- 表达方式：`quote`
- 内容：
  - 「系统要提供原语，支持工具内部业务逻辑执行到一个位置的时候，声明进入一个
    等待外部输入的状态，在拿到外部输入后才继续后续的逻辑执行」
  - 「tool runtime 和 agent runtime 是解耦的，和一次 run 也是解耦（可以记录是哪一次
    run 发起的这个 tool execution，但是声明周期是解耦的）的，但是应该要和 session
    是绑定的（这样一个 run 结束但是 tool execution 未结束，下一次 run 或 若干次 runs
    后才结束，依然能够发生结果回对应的 session）」
  - 「一个工具执行的生命周期应当是可以被用户提前中断的，但中断不意味着失败，
    对于一个允许被切换到后台执行的工具，用户应当要能够手动切后台」
  - 「工具转后台 agent 应当是有感知的（通过占位 ToolMessage）并且当在后台执行完成后
    能以 system reminder 的消息形式通知给 agent（具体机制后面讲 run 的时候聊）」
  - 「工具执行被用户中断，同样应当以一条正常的 ToolMessage 占位替换中断异常来让
    agent 语义化地感知该工具执行是被用户手动中断的而不是工具调用失败」
- 状态：当前有效
- 记录者注：**「语义化地感知」是本 topic 最有分量的一句**。正文由它推出六种收场
  必须都以正常返回到达 agent——异常不带语义。括注「具体机制后面讲 run 的时候聊」
  是边界，本 topic 未越界。

## INT-005 依赖声明与可用性解析

- actor：**产品负责人本人**
- 表达方式：`quote`
- 内容：「skill 应当允许声明自己要生效所依赖的工具集合，并且最好能够声明自己要能够
  生效，所依赖的工具集合的可用性的关系（且、或、必需哪些可选哪些）；工具应当要能够
  声明自己依赖的服务；系统在进行装配时候，应当要（这对 skill 和 tool 实现时候的
  protocol 提出了要求）先执行可用性检测（当然面向 Cordis 开发的话可能这些天然就
  具备了），根据依赖解析树来构建真正可用的 skills 和 tools 以对 agent runtime
  instance 完成装配。」
- 状态：当前有效
- 记录者注：两点。其一，括注「面向 Cordis 开发的话可能这些天然就具备了」是
  **技术怎么兑现**，按本区域约定**未写入产品正文**。其二，「工具声明自己依赖的服务」
  里的「服务」与 [PF-002 排除的 Service](../../PF-002-assets-settings-and-permissions/design.md#八类资产)
  不是一回事，正文已加注区分，否则就是同名不同义。

## INT-006 三个问题的答复

记录者当时提了三个问题，产品负责人逐条作答。

- actor：**产品负责人本人**
- 表达方式：`quote`
- 内容：
  - Q「agent 自己造的工具当场能不能用」→「**当场能用，但不改变 agent definition，
    若改变了 agent definition，应当在下一次 run 的时候重建 agent runtime instance**」
  - Q「等待外部输入的『外部』是谁」→「**是「谁」不重要，本质上就是一个抽象，
    即能够提供回复的对象，重要的是这个原语本身，要能够让系统知道现在是「等待态」，
    并且这个原语可以用来良好表示任何需要提供的 response schema，这样后续的流程
    才可以根据这个 schema 来走同的工具内业务逻辑**」
  - Q「meta 是定义固有属性还是可覆盖的设置」→「**meta 不是设置，而是 agent definition
    里声明要装配的一个 skill 或者 tool 时候对应条目带着的一个标签，同理 plugin 里面
    声明包含的一个 skill 或 tool 应当也能声明这样的标签**」
- 状态：当前有效
- 记录者注：第一条**顶到了 PF-004 的一条表述**（构成变了却不重建实例），
  已作为来源问题报告，见 [decisions.md 第四节](../decisions.md#四已知的来源问题)。
  第三条把 meta 从「资产的属性」改成「引用条目上的标签」，**比记录者预设的两个
  选项都轻**——不需要层级求值。

## INT-007 不可用时装同名替换件，可用性每次 run 前重算

- actor：**产品负责人本人**
- 表达方式：`quote`
- 内容：「可用性解析算实质装配这块我更进一步描述产品上的设计：**不是不可用就不装配，
  而应当是不可用时装配上去的是一个同名但明确让 agent 能够感知当前不可用的替换件**，
  还有这个可用性计算，**应当是每次 run 开始前都完成计算**。」
- 状态：当前有效
- 记录者注：这一条**改变了整个 topic 的骨架**。记录者原先的理解是「不可用就不装，
  并让能力发现工具查得到」，那条路会让动作空间随环境波动变形。
  替换件把「依赖不满足」从**装配期的删除**变成**运行期的状态**，
  [I-4](../../PF-004-agent-runtime-assembly-and-liveness/design.md#61-不变式) 因此得以守住。
  三层模型是在这一条之后才立得起来的。

## INT-009 skill 与 tool 的取用机制不一样

- actor：**产品负责人本人**
- 表达方式：`quote`
- 内容：「skill 和 tool 机制不一样：1）skill 本质上是一堆的文本，我们应当提供一个
  Skills() 的 multiple command meta tool，支持可以搜索可用的技能、按名称加载访问
  技能文档的能力，参见 omne-next/omne_agent_capabilities 还是哪里的；2）tool 的动态
  加载相对复杂一些，具体来说是提供一个 Tools() 的 meta tool，来发现和执行工具，
  参见 omne-next/omne_agentic_toolkits 还是哪里的，可能那边叫 tool_execution_tool」
- 状态：当前有效
- 记录者注：**「发现和执行」合一是关键**——它意味着非 meta 的工具压根不需要进槽位。
  记录者据此修正了自己此前那张三层表的第二层：不是「知晓范围」，是「呈现方式」。
  关于两处参考实现，记录者查阅后**只作印证与提醒**：它提示了一件本来会漏掉的事——
  非 meta 工具的**参数格式**同样不常驻，而那往往比说明文字还长。
  该结论在 decisions 第二节有独立的推理链，**不以前身系统为依据**。

## INT-010 取用不改变 system prompt

- actor：**产品负责人本人**
- 表达方式：`quote`
- 内容：「**Skills() 和 Tools() 对未常驻在 system prompt 里的技能的访问或工具的调用，
  都不会导致 system prompt 改变**，那么答案你清楚了吧？」
- 上下文：记录者此前问过一个问题——技能被取用之后是「一次读取」还是「一次激活」，
  并指出前身系统用的是后者（`manage_skills activate`）
- 状态：当前有效
- 记录者注：这一句**直接排除了「激活」那条路**，因为激活会让系统提示词在运行中变形。
  由此得到一条比原问题更强的结论：**系统提示词的成分在运行实例存续期内恒定**——
  唯一能改变它的是 meta 标签，而那在装配时就定死了。这同时守住了
  [PF-004「成分在装配时确定」](../../PF-004-agent-runtime-assembly-and-liveness/design.md#54-为什么系统提示词必须落在第三列)。

## INT-012 用词：改用「常驻」，对齐 omne-next

- 时间/顺序：**PF-006 rev 1 初稿提交之后**
- actor：**产品负责人本人**
- 表达方式：`quote`
- 内容：「PF-006 我想了想不要叫 meta 标签，用「常驻」这个概念，对齐 omne-next 的」
- 状态：当前有效。**全包据此换词**
- 记录者注：核对过 `omne-next/omne_agent_capabilities` 的中文文档，那边用的正是
  「**常驻**」，并有「常驻层级」的说法（`pinned` 层），与本 topic 的模型对得上。
  **但只借词、不借机制**：那边的常驻层级带**容量上限**（`max_pinned_skills`）与
  **按使用频次自动晋升**，本 topic 是**显式标记**，两样都不做——
  自动晋升会让呈现方式变成运行期可变的，与「成分在装配时定死」直接冲突。
  这一点已记进 [decisions.md 第四节](../decisions.md#四已知的来源问题)。
  换词**不改变任何结论**，三层模型、六种收场、替换件机制全部原样成立。
