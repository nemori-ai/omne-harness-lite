## INT-014 两种范式、四项声明、两种返回形态

> **quote**：「就是我们会给工具开发者两种 tool schema declaration 的范式：
> 1）普通工具函数的 schema 范式，也就是没有 command 都是 args；
> 2）多命令工具范式，参见 omne-next/omne_core_v1。
> 我们还允许工具开发者在定义工具的时候作如下可选声明：1）依赖的外部服务；
> 2）依赖的存储；3）依赖的执行环境；4）是否可以后台执行，前台跑多久自动转后台。
> 我们提供一个等待态的原语（注意这不是定义时候声明的，是函数逻辑里面可以用的
> 你可以理解成可恢复接续的「断点」，或者 thread context 切换的什么机制，
> 你从操作系统、线程的角度来思考，但这是技术细节不需要你产品设计时候做）。
> 我们提供两种工具函数返回结果的形态：1）正常 ts/js 函数怎么返回就怎么返回，
> 此时系统会把整个返回值当作字符串来使用；2）使用约定的 ToolResult 数据结构来返回，
> 这个数据结构提供格式化地返回进 ToolMessage 的内容、（可选）offloading 的原始结果、
> （可选）附件存储地址/ref。那无论哪种结果，因为本质上一次 tool execution 是一个
> job（span），因此完成后上报给系统，都要进一步带上各种的 metadata，
> 比如 wall time、cpu time 之类的，噢对了正常 ts/js 函数返回，但是上报的时候被
> transform 成 ToolResult 这样在 agent-loop 视角就是统一的模型了。
> 这些在 PF-006 看怎么调整排版，集中来写，就是工具定义、返回值、特性声明这些。」

### 这段话里有一处对 PM 的纠正

**「注意这不是定义时候声明的」**——rev 4 的 §6.11 把
「等待态要什么形状的应答」列成了工具定义的一项声明。**那是错的。**

PM 错在把 §4 那句「它自己**声明**要一个什么形状的应答」里的「声明」
读成了定义时的静态声明。实际上它是**函数逻辑里用得上的原语**：

> **等不等是这一次跑出来的事**——同一个工具，参数不同就可能这次等、下次不等。

正式记录在 [decisions 第四节](../decisions.md#四已知的来源问题)。

## INT-015 不声明就是不能后台

PM 在 rev 5 交付时报告了一处自己没敢填的缺口：§6.6 只写了「**可以**声明能不能后台」，
**没定不声明时算哪种**。产品负责人当即裁决：

> **quote**：「不声明就是不能后台，补进 §6.6。」

落在 [design §6.6](../design.md#66-前台后台-与-等待态是两个维度)。
理由与[执行环境不许降级满足](../design.md#68-工具怎么提执行环境的要求)同一条：

> **没表过态，不等于表了同意。**

**这条裁决顺带点破了四项声明的一处不对称**：前三项声明的是**我需要什么**——
没说就是不需要，少一个前提反而更容易可用；第四项声明的是**我允许什么**——
**没说就是不允许**。不点破，会有人把「四项都可选」理解成「四项都是不填就宽松」。

## 查阅 `omne_core_v1` 之后，本版没有采纳的几样

产品负责人让「参见 `omne-next/omne_core_v1`」。读下来那边还有几样东西，
**本版都没有采纳**，理由记在 [decisions 第四节](../decisions.md#四已知的来源问题)：

| 看到的 | 本版怎么处理 |
|---|---|
| 工具**自带 `help` 命令** | **不采纳**——统一走 [`Tools().inspect`](../../PF-007-meta-capabilities/design.md#61-tools通向任意非常驻工具)。这是一处**有意偏离** |
| **两层 gating**（读过命令说明 / 读过技能说明才放行） | 不采纳，无裁决支撑 |
| **batch 模式**（一次调用跑 N 个动作） | 不采纳，无真实需求推着走 |
| **命令可见性** | 同上 |
| 三种 **dispatch 模式** | 收敛成一条产品语义：**定义里带多少，归工具作者定** |

**那边的做法不构成本 topic 的依据**，只作起点与印证。
