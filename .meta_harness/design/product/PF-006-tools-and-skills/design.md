# PF-006：工具与技能

- 修订：rev 20，2026-09-27 · [变更历史](changelog.md)
- 状态：本次工作区一致性增量已正式接受；此前接受范围、现存未决与技术投影状态见 [README](README.md#状态)。

## 一、背景与问题

[PF-002](../PF-002-assets-settings-and-permissions/design.md) 说了工具和技能**各自是什么**，
[PF-004](../PF-004-agent-definition-and-assembly/design.md) 说了它们**在装配的哪一步进来**。
中间那段没人说过：

> **一份定义，怎么变成 agent 真的能用的动作。**

这段空着，四个问题每次讨论都要重新发明一遍答案：

- **配了十个技能，agent 一个都不用**——是模型不行，还是它压根不知道有这些东西？
  这两件事的处理方式完全相反，而现在分不出来。
- **上下文预算**。所有工具的说明和参数格式全塞进系统提示词，几十个工具就能把预算吃光，
  留给干活的没多少。但不塞，agent 又不知道自己有什么。
- **一个技能声明它要用某个工具，而那个工具没装**。装配是该失败，还是照装？
  照装的话，agent 会读到一份自己执行不了的指引。
- **一次工具执行还没完，这一轮就结束了**。结果回来时该给谁？agent runtime 可能已经退役了。

本 topic 把这段补上：**能做什么、怎么够得着、现在做不做得了**——三件事分开定义，
以及一次工具执行从发起到收场的全部形态。

## 二、目标与非目标

### 目标

1. **把三件事分开**：动作空间、呈现方式、当下可用性。三者正交，变化节奏各不相同。
2. **定义常驻标记**：谁常驻在系统提示词里，谁不常驻，标记挂在哪。
3. **定义一份工具定义的形状**：有哪几种范式、能声明什么、什么不在定义里。
4. **定义返回值的形状**：工具作者有几种写法，而系统看到的是什么。
5. **定义依赖声明与可用性解析**：依赖怎么声明、什么时候算、算出不可用怎么办。
6. **定义工具执行的生命周期**：它绑在谁身上、有哪几种结局、agent 怎么感知。
7. **定义工具跟外面通信的两个原语**：等待态与发帧。**两个都不在工具定义里。**
8. **固定 agent 创建与修改工具/技能的最小必要部分**，其余留给后续 topic。

### 非目标

| 不做什么 | 为什么 |
|---|---|
| `Skills()` 与 `Tools()` 这两个常驻工具的**具体产品设计** | 归 **PF-007**。本 topic 只定它们必须成立的性质，不定它们各有哪些命令、怎么用 |
| agent **怎么**创建、编辑、动态装载技能与工具 | 另有 topic。本 topic 只固定「造出来的是资产」「归属算得出来」「当场能用」这三条最小必要 |
| **从外部获取**尚未持有的资产（marketplace 那一层） | 那是资产怎么到手，归 [PF-002](../PF-002-assets-settings-and-permissions/README.md) 与 [PF-003](../PF-003-asset-transfer-and-sharing/README.md)。本 topic 只管**已经在装配清单里**的东西 |
| 执行环境有哪几种、各自活多久 | 归 [PF-005](../PF-005-execution-environments-and-sandboxes/README.md)。本 topic 只定**工具怎么提要求** |
| 设施一共有哪几种、名字怎么定 | 同上，PF-005 已明确不定这份清单 |
| 一次 run 怎么被驱动、system reminder 怎么送达 | 归 **run** 那一块。本 topic 只定「结果回到 session」「以提醒形式到达 agent」这个产品语义 |
| 工具与技能的**开发与发布流程** | 谁能写、怎么发版、怎么上架，另有归属 |
| 依赖声明**写成什么样**（名字怎么拼、清单怎么排） | 产品只定它是[一串必需项的抽象名字](#依赖)，写成什么样是技术设计 |
| 两种范式、`ToolResult`、执行的账**具体有哪些字段、叫什么名字** | 产品定**形状与语义**（有几种、各装什么、谁决定），字段名与结构是技术设计 |
| 一份工具定义里**要不要带返回形状的描述**、带成什么样 | 产品定的是[返回值的两种写法与系统看到的那一种](#54-返回值两种写法一种模型)；定义里描不描述返回形状，产品不定，归规格 |
| 工具与技能的 **name 怎么写**（用哪些字符、多长） | 归规格。产品只要求**同一类别内唯一**——[身份是「类别 ＋ name」](../PF-002-assets-settings-and-permissions/design.md#身份是类别--name其余归实现) |
| 等待态**怎么实现**（怎么停下、怎么接着跑） | 产品只定它是一个**工具函数用得上的原语**，以及它与前后台正交。断点怎么存、上下文怎么切，是技术设计 |
| 帧**落成哪一种消息、给谁看、怎么增量更新** | 归 [PF-009](../PF-009-context-message-types/README.md)。本 topic 只定**工具这一头**：它有个原语可以往外发，发不出去不影响执行 |
| 帧**具体长什么样**（块里装什么、字段怎么排） | 形状归 [PF-009 的到达语法](../PF-009-context-message-types/design.md#到达的过程有它自己的语法)，本 topic 不另立一份；产品在这里定的是「**不由工具定义声明**」这条选择本身，以及它带来的后果。再往下的具体形状是技术设计 |
| 执行的账**谁读得到、留多久、进不进计费** | 归观测与计量。本 topic 只定**每次执行都要留下它**，以及**它不进 agent 的上下文** |

## 三、用户与场景

| 使用者 | 什么情况下接触这块 | 他关心什么 |
|---|---|---|
| **配 agent 的人** | 给一个 agent definition 挑工具和技能 | 我配的东西它到底会不会用？为什么配了没生效 |
| **管上下文预算的人** | 发现 agent 反应变慢、干活变差 | 系统提示词里现在塞了多少东西？哪些是必须常驻的 |
| **技能与工具的作者** | 写一个工具，或写一个要配套使用的技能 | 我该用哪种范式？返回值要不要用那个结构？我这套方法要用到的工具没装，会怎样？ |
| **用 agent 干活的人** | 一次操作跑了很久 | 我能不能让它转后台？我中途叫停算失败吗 |
| **agent 自己** | 每一次动作 | 我现在有什么可用？这个为什么调不通？上次那个跑完了没 |

**最后一行仍然是直接消费者。**它分不清「我没有这个能力」和「我有但现在用不了」，
就会在该绕路时放弃，或者在该放弃时死磕。

### 三层：能做什么 / 怎么够得着 / 现在做不做得了

**这是本 topic 的核心。**三件事此前混作一谈，于是「agent 不会用这个工具」
永远查不出原因。分开之后，每一层各有各的答案：

| 层 | 回答什么 | 由谁决定 | 什么时候变 |
|---|---|---|---|
| **动作空间** | 我**能做**什么 | 构成（[PF-004 I-4](../PF-004-agent-definition-and-assembly/design.md#61-不变式)） | 装配时；运行中 agent 自己追加 |
| **呈现方式** | 哪些**直接占槽位**，哪些**经代理够得着** | **常驻标记** | 装配时 |
| **当下可用性** | 现在**做不做得了** | **依赖解析** | **每次 run 开始前重算** |

**三层正交**：呈现方式不改变动作空间，可用性也不改变动作空间。
一个工具可以「在动作空间里 + 不占槽位 + 当下不可用」——三个取值互不牵连。

### 常驻

**一个工具或技能，始终出现在系统提示词里**——它这个能力身份**始终对 agent 可见**，
不必经取用入口去找。

它由**常驻标记**决定。常驻标记是**「装配它」这条引用上的一项设置**：

> **常驻标记不是工具或技能自身的属性，是引用条目上的一项设置。**

同一个工具，在 agent A 的清单里可以是常驻，在 B 的清单里可以不是。
这是对的——**上下文预算是装配方的问题，工具作者根本不知道**。

**引用条目长在 Agent Definition 或 Plugin 里**，所以这项设置是那份 Agent Definition 或 Plugin 的设置，
照 [PF-002 的三方分工](../PF-002-assets-settings-and-permissions/design.md#三方分工资产定形状各层配值运行时求值)走：
写这条引用的人给出默认值，持有那份资产的各层配值，运行时求值。

**它归[偏好](../PF-002-assets-settings-and-permissions/design.md#设置项分四类资产声明每一项时必须标类别)类。**
改了它，换掉的只是 agent 看见东西的方式——[动作空间不变、可用性不变](#51-三层正交)，
每次调用要过的那道执行权限门也不变；配错了，顶多是预算吃紧或 agent 少直接看见一样东西，**是「难用」，不是换了门**。
它也不是绑定类：它不指向任何别的资产或位置——指向那件东西的是引用本身。

**常驻标的是「看不看得见」，不是「看见的是什么」。**可见时呈现成什么，是装配时的策略：

| 常驻的是 | 呈现成什么 |
|---|---|
| **技能** | **name 与[说明](#技能的说明)**进系统提示词；正文不进，按需取 |
| **工具** | 由各模型的适配按对应供应商的方式呈现 |

本 topic 说「出现在系统提示词里」「占一个槽位」，指的都是这种**始终可见的呈现**，
不限定它落在一次模型请求的哪个位置。

**没标常驻的不是「不能用」，是「不占位置」**——它照样在动作空间里，
经取用入口够得着（§5.1）。

#### 技能的说明

**技能的说明回答「什么时候该用这份方法」——它是触发与路由的依据。**
常驻时进系统提示词的是它，[`Skills().search`](../PF-007-meta-capabilities/design.md#62-skills通向任意技能) 按它找，
[替换件](#替换件)换掉的也是它。

所以说明写得好不好，直接决定 agent 该想到这份方法的时候想不想得到。
**正文与资源按需取**，走 [`Skills().read`](../PF-007-meta-capabilities/design.md#62-skills通向任意技能)。

### 槽位

**agent 在系统提示词里直接看见的一个条目。**

标了常驻的占一个槽位，没标的不占。此外有**一批恒定占槽位、且关不掉**的条目——
[PF-007 定义的 **meta**](../PF-007-meta-capabilities/design.md#meta)，
其中包括能力发现与取用的入口（§6.1）。

**不占槽位不等于不在动作空间里**（§5.1）。

### 依赖

**一个工具或技能声明「我要成立，必须在场的东西」——一串名字。**

每一项指一样**可以在场、也可以不在场**的东西，而且**用抽象的名字指，不指具体的资产**。
**谁生效在那个名字上，谁就满足它。**

名字是哪几种，**没有穷尽的清单**。举几个已经在用的：

| 这一项指什么 | 谁会声明 | 例子 |
|---|---|---|
| 某个[能力标识](../PF-002-assets-settings-and-permissions/design.md#63-组合的引用指向能力标识)下的工具 | 技能 | 「我这套代码审查方法要用到**读文件**、**跑测试**」 |
| 某个**外部服务** | 工具 | 「我要连上某个外部系统才能工作」 |
| 执行环境的某种[设施](../PF-005-execution-environments-and-sandboxes/design.md#设施) | 工具 | 「我需要一个带浏览器、且至少绑定在会话上的沙箱」 |
| 某个**存储** | 产出[附件](#工具的产出)的工具 | 「我的附件放这个存储」——[连同「有工具读得出它」一起算](#64-依赖声明与解析) |
| 有效模型的某种**[模态](../PF-013-model-profiles-and-invocation/design.md#模态)能力** | 工具 | 「调我要模型给得出图」「我的结果里有图」（[§6.11](#611-工具两端各要什么模态)） |

**这张表是例子，不是外延。**将来多一种可以在场也可以不在场的东西，
**它就能作为一项进来，不必为它另造一套机制**——这正是「用抽象的名字指」的价值。

> **「外部服务」不是 [PF-002 排除的那个 Service](../PF-002-assets-settings-and-permissions/design.md#八类资产)。**
> 那一条排除的是 Cordis 的运行时概念；这里说的是产品意义上的外部依赖——
> 一个工具要连的对端。指前者时必须写全 `Cordis service`。

#### 只有且，只有必需

**一串名字，全部都要在场**——**没有「或」，也没有「可选」。**

**「或」被抽象的名字消掉了。**技能依赖的是「读文件」**这个能力标识**，
不是「甲工具或乙工具」；**同一个名字底下可以有不止一个候选提供者**，
谁生效谁满足，**这件事在声明这一侧根本看不见**。
真要写「甲或乙」，说明该给它们一个共同的名字。

**「可选」不进声明。**可有可无的东西**用的时候现探**——
写进声明，它就成了一个必须在场的前提，反倒把本来能用的东西判死。

> **判据：少了它这东西还成不成立。**成立，就别写进去。

### 可用性

**一个工具或技能当下能不能真的用。**

它是**依赖解析的结果**，不是一个被谁配置的开关：

> **[声明](#依赖)里的每一项都有一个在场的提供者、且它说自己可用 → 可用；
> 缺一项 → 不可用。**

**每次 run 开始前重算一遍**——因为那些提供者本身就在变：
**换了一个、没了一个，这一项就得重算**。「换模型之后哪些工具还在」
（[§6.11](#它同时决定了换模型之后哪些工具还在)）就是这一条的一个取值。

### 替换件

**当一个工具或技能不可用时，装在它位置上的那个东西。**

**它和原件同形**：工具的名字与调用参数一模一样，技能的名字一模一样。
从[动作空间](#三层能做什么--怎么够得着--现在做不做得了)那边看过去，
这个条目的形状一点没变。

**只有一处不同：它的说明换了**——换成讲清「这个现在用不了，原因是什么」，
好让 agent 在动手之前就读得到。

**但读得到不等于它就不调了。**说明是给模型看的，不是一道闸。
所以替换件**只有一种行为**：**不论怎么调、带什么参数，都必定走到「用不了」这一个结局**，
并带上原因——[六种收场](#55-一次工具执行的收场有六种)里的**不可用**那一种。
**它不会执行原来那件事，也不会时灵时不灵。**

**这个收场是一条正常的返回，不是报错。**理由见 §6.3。

### Tool Execution

**一次工具执行。**它是**计算资源**，有自己的运行时。

| | 本质 | 绑在谁身上 |
|---|---|---|
| **Tool Definition** | 数据 | 谁持有它（一类[资产](../PF-002-assets-settings-and-permissions/design.md#八类资产)） |
| **动作空间里的那个条目** | 构成的一部分 | **agent runtime** |
| **Tool Execution** | **计算资源** | **会话**——它有**自己独立的 runtime**，从不由 agent runtime 承载 |

**这是「数据 vs 计算资源」在本系统里的第四次出现**，但这次换了宿主——
前三次的计算资源都挂在 agent runtime 上，**这次挂在会话上**（§5.2）。
**前台还是后台，说的不是它挂在谁身上，而是 agent runtime 这副协程有没有阻塞在它上面。**

### 工具跟外面通信的两个原语

**一次工具执行不是一个黑盒子。**它跑的过程中可以跟外面说两种话，
**方向相反，性质也相反**：

| | **等待态** | **发帧** |
|---|---|---|
| 方向 | **要**一个应答进来 | **给**一点情况出去 |
| 阻不阻塞 | **阻塞**——停下来等 | **不阻塞**——说完接着干 |
| 落空了会怎样 | 「等不到应答」是[六种收场之一](#55-一次工具执行的收场有六种) | **什么也不会怎样** |
| 系统要不要知道 | **必须知道它正在等** | 不必 |

> **等待是执行的一部分，发帧不是。**

**两个都不是[工具定义](#53-一份工具定义长什么样)里的声明**，
它们是**工具函数自己的逻辑里用得上的东西**。

#### 等待态

**一次工具执行中途停下来，等一个应答，拿到之后才继续。**

停下来的时候它说明**自己在等什么形状的东西**，后续按拿到的内容走不同的分支。

> **「谁来应答」不是这个概念的一部分。**人、外部系统、另一个 agent——
> 谁都可以，形状一样。要紧的是**系统知道它正在等**，以及**它等的是什么形状**。

**工具定义里没有「我会不会等」这一格**——**等不等是这一次跑出来的事**，
同一个工具，参数不同就可能这次等、下次不等。

**等待态与前台/后台是两个维度**，不互相决定（§6.6）。

**它是这次工具执行自己的等待，不是 agent runtime 的等待。**
前台时 agent runtime 阻塞在这次执行上，那是**协程在等工具回话**；工具在等应答，是**工具在等外面**——两回事。
所以 agent runtime 被回收，**工具的等待态原样还在**：[`Ask()`](../PF-007-meta-capabilities/design.md#611-ask通向人) 的那张卡照样挂着，
人回了话，工具拿到应答接着跑；协程重建后照 [Run](../PF-012-agent-loop-and-run/design.md#run) 里记的「在等这一次」接着等它。

#### 发帧

**一次工具执行的过程中，它主动交出一点「我正在干什么」。**

补的是一个具体的窟窿：用户看着界面上写着「正在调用某个工具」，
**然后就没有下文了**——它是卡住了，还是在正常地跑一件慢活，**现在分不出来**。

**发出去的东西落成什么消息、给谁看、怎么增量**，归
[PF-009](../PF-009-context-message-types/design.md#toolinternalmessage)。
**本 topic 只定这个原语本身。**

三条性质：

- **它不承诺任何事。**发不出去就发不出去，**这次调用该怎么跑还怎么跑**——
  **工具不会因为「说不出话」而执行失败**。
- **系统不必预先知道哪个工具会发帧。**没收到就是没有，
  **绝大多数工具一帧都不发，那是正常形态**。
- **帧自己说清它要干什么**，见下。

##### 帧长什么样，由一份协议约定，不由工具定义声明

**那份协议不是这里另立的一份。**帧的形状就是
[PF-009 §5.5 的到达语法](../PF-009-context-message-types/design.md#到达的过程有它自己的语法)——
开一个块（说明这块是追加片段还是整体替换）、往里填、封上这个块、记一次账、收尾；
一次工具执行的那些帧，是
[同一条 `ToolInternalMessage` 的到达增量](../PF-009-context-message-types/design.md#执行帧就是这条消息的到达增量)，
**不是一串各自独立的东西**。

**系统对帧的解析是统一的。**它**不去查工具定义**来决定要不要解析帧，
而是**看实际收到了什么，再决定怎么处理**。

> **收到什么就按什么办——没收到就是没有。**

**这条省掉了一整层东西**：不必在定义里加一格「我发不发帧」，
不必在运行时核对「声明的和实际发的对不对得上」，
也不必处理「声明了不发却发了」这种情形——**因为压根没有声明**。

**它还顺手留了一条路**：一个工具**可以先往外吐日志，最后再给一块汇总的面板**——
**前面那些块追加片段，最后开一个整体替换的块**。
**预先声明就把这条路堵死了**——而那个限制换不来任何东西。

### 工具的产出

**一次工具执行交出来的东西，分三部分。前两部分在它跑完的时候，第三部分在它跑的过程中：**

| 部分 | 什么时候 | 去哪 | 谁在读 |
|---|---|---|---|
| **进消息的那部分** | 跑完 | 直接进对话 | **agent**——读就是了 |
| **附件** | 跑完 | 存进某个存储 | **agent**——消息里告诉它地址，它自己去取 |
| **[帧](#发帧)** | **跑的过程中** | 汇成那次执行的**那一条 `ToolInternalMessage`** | **人**——**agent 看不到**（[PF-009](../PF-009-context-message-types/design.md#toolinternalmessage) 定的） |

**前两部分为什么要分**：有些产出根本不适合进对话——一张图、一个几十兆的文件、
一份二进制数据。硬塞进去，一条消息就把上下文吃光了。

**第三部分为什么在这张表里**：它跟前两部分一样是这次执行交出来的东西，
**但读者换了个人**。前两部分回答「这件事办成什么样了」，帧回答「这件事现在办到哪了」——
**后一个问题只有正在等的人才关心**，办完之后它就没有意义了。

> **帧不顶替结果。**一个工具把过程播报得再细，**跑完照样要给结果**——
> 否则 agent 手上什么都没有：**它压根看不见那些帧**。

### 卸载

**即便是「进消息的那部分」，也可能大到装不下。**

卸载 = **原始结果存起来，消息里换成一条带摘要的占位**。

**卸载不是全卸载**：占位里留着**够用的那部分内容**，加上有多大、怎么取全文。
很多时候 agent 看占位就够了，根本不必去取全文——**这正是卸载值得做的理由**。
只留一个地址的占位，等于把每一次大结果都变成**一次额外往返**。

> **「换成」说的是相对于原始结果，不是在记录里替换。**
> [会话日志里从头到尾只有占位那一条](../PF-012-agent-loop-and-run/design.md#510-卸载结果落成消息之前的那一关)——
> **原始结果从来没进过日志**；而 agent 取回全文，是**往后追加两条新消息**。

**留下的是什么，看它走哪条来路**（§6.10）。

## 五、模型

### 5.1 三层正交

```text
装配清单：  [ 工具A ] [ 工具B ] [ 技能C ] [ 工具D ] …… 几十个
                ↓         ↓         ↓         ↓
动作空间：   全都在里面。agent 能发起的动作 = 这一整份清单
                ↓         ↓         ↓         ↓
呈现方式：  常驻→槽位   代理     代理     常驻→槽位
                                （+ 恒定占位的 meta，见 PF-007）
                ↓         ↓         ↓         ↓
当下可用：    ✓        替换件      ✓         ✓
```

**三层各答一问，互不替代：**

- 问「agent 能不能做这件事」→ 看**动作空间**。
- 问「它现在知不知道自己能做」→ 看**呈现方式**。
- 问「它现在做不做得了」→ 看**可用性**。

**三个问题的修法完全不同**：动作空间不对，改 agent definition；
呈现方式不对，调常驻标记；可用性不对，去看依赖谁没满足。
混作一谈，就只剩「它怎么不会用」这一句无从下手的抱怨。

### 5.2 「工具」这个词指三样东西，寿命各不相同

```text
Tool Definition ──装配──→ 动作空间里的条目 ──调用──→ Tool Execution
   数据，长期                构成，绑 agent runtime          计算资源，自己的 runtime，绑会话
   资产的身份与表示          换执行环境不改变它        比发起它的那一轮、那副协程都活得长
   （可自带实现）
```

**第一段不是「工具」这类资产本身，是它在数据与治理层面的[身份与表示](../PF-002-assets-settings-and-permissions/design.md#tool)。**
[身份是「类别 ＋ name」](../PF-002-assets-settings-and-permissions/design.md#身份是类别--name其余归实现)，
**定义连同它可能自带的实现，都是这个身份下的一份表示**——同一个 name 下，平台一份、组织一份、租户一份，
彼此替代，[§6.3 的替换件](#63-不可用时装的是同名替换件不是不装)也占的是这同一个位置。

**最要紧的是第三段：它有自己独立的 runtime，绑在会话上，不长在 agent runtime 或某一次 run 身上。**

| | 记录得下来吗 | 生命周期绑在一起吗 |
|---|---|---|
| 是**哪一次 run** 发起的 | **记得下来** | **不绑** |
| 是**哪个 agent runtime**发起的 | 记得下来 | **不绑**——前台后台都一样 |
| 属于**哪个会话** | 记得下来 | **绑**；结果也送回这里 |

#### 前台、后台说的是 agent runtime 在不在等它

**前台** = agent runtime 这副协程**阻塞在这次执行上**，等它的结果回来才往下走；
**后台** = agent runtime **不再阻塞在它上面**，接着干别的，结果以提醒回来。
**执行本身挂在哪没有变过**——前后台都是它自己的 runtime、绑在会话上。

**「agent runtime 在等哪一次执行」是 agent runtime 的状态，记在 [Run](../PF-012-agent-loop-and-run/design.md#run) 里。**
协程被回收、重建之后，读到「上次在等 X」，**就接着等 X**；X 那边一直在跑、一直在等，什么都没发生。

因此：一次 run 结束了，转了后台的执行可以还在跑；再过几轮跑完了，**结果照样回得到那个会话**；
发起它的 agent runtime 哪怕已经退役，也不影响这件事——**收件人是会话，不是那个 runtime**。

### 5.3 一份工具定义长什么样

**两种范式，工具作者挑一种：**

| | 形状 | 适合什么 |
|---|---|---|
| **单函数** | 没有命令，**全是参数** | 一个工具就干一件事 |
| **多命令** | **先选命令，再给那个命令的参数** | 一个工具是**一族相关的动作** |

**为什么非要有第二种**：[十三扇门那些常驻工具](../PF-007-meta-capabilities/design.md#54-十三个槽位是预算的地板也是它的天花板意义)
全是这个形状。换成单函数范式，`Tools()` 的每个命令都得立成一个独立工具——
**一族动作吃掉一族槽位**，而槽位是预算的地板。

> **多命令范式把「一族动作」压进一个槽位。**

反过来，**单函数范式的价值是不必套壳**：只干一件事的工具，
再套一层命令分派，除了让 agent 多填一个字段什么也没换来。

#### 工具说明与每个参数的说明，必填

**一份工具定义，必须带着「这个工具干什么」的说明，以及它每个参数各自的说明。**
缺了哪一样，它就不是一份完整的工具定义。

**为什么是必填**：这两样要原样交给模型供应商——各家接收一个工具时，要的就是「它干什么」和「每个参数是什么」。
缺了，系统就拼不出供应商要的那一份；**模型也只能对着一个名字和一串参数名去猜**。

**多命令工具照同一条算**：模型面前「选哪个命令」那一格的说明，[就是那份一行一命令的清单](#多命令工具的定义里带多少是工具作者的权衡)，
所以**每个命令那一行说明也必填**；作者带了某个命令的完整参数，那些参数同样**各带说明**——
`Tools().inspect` 与 `help` 答用法，靠的就是它们。

#### 多命令工具的定义里带多少，是工具作者的权衡

**先说不随作者选择而变的那一面：多命令工具在模型面前只有一种样子——一份紧凑的命令清单。**
模型看到这个工具时，只有两格要填：

| 模型面前的 | 是什么 |
|---|---|
| **选哪个命令** | 只能从这个工具的命令里选一个；**每个命令一行说明**，合起来就是那份清单 |
| **交给这个命令的参数** | 模型面前**不规定它长什么样**——每个命令要什么参数，不摊在这里 |

**为什么只有这一种**：多命令范式为的是两件事——**一族动作只占一个槽位**，**上下文紧凑**。
把全部命令的参数都摊到模型面前，槽位还是一个，**紧凑就没了**：命令越多、参数越复杂，吃掉的预算越多，
而这些命令大多数这一轮根本用不到。**所以不管作者带没带，系统都不把每个命令的完整参数展开到模型面前。**

**作者可以带、也可以不带的，是每个命令的完整参数：**

| 定义里带什么 | 系统拿它做什么 | 模型面前 |
|---|---|---|
| **只带命令清单**，每个一行说明 | 交上来的参数，系统**没有据以校验的东西**，对不对由工具自己判；`Tools().inspect` 答得出的只有那份清单 | **命令清单** |
| **带了全部命令的完整参数** | 系统**据它校验交上来的参数**；`Tools().inspect`（以及作者带的 `help`）**据它答每个命令的详细用法** | **同样只是命令清单**——完整参数不进模型面前 |

**两种写法在模型面前一模一样。**所以 **agent 对一个还不熟的命令，动手前仍要先问一次详细用法**——不管作者带没带。
带不带完整参数，差在**系统校不校验得了、问得到多细**；**这个选择归工具作者**——只有他知道值不值得为每个命令把参数写全。

**详细用法从哪问**：走
[`Tools().inspect`](../PF-007-meta-capabilities/design.md#61-tools通向任意非常驻工具)——
它对两种范式都管用，**任何工具都问得到**。

**`help` 是多命令工具的一种可选命令空间，不强制。**作者可以给自己的多命令工具带一个 `help`，
让 agent 在这个工具里面就问得到用法；不带也完全成立，`inspect` 照样答得出。

> **带了，就必须与 `inspect` 说得一致。**同一个工具的用法有两处说法，
> 一旦对不上，**agent 分不出该信哪个**——所以两处不一致是缺陷，不是风格差异。

#### 六项可选声明

| 声明什么 | 不声明是什么意思 | 规则在哪 |
|---|---|---|
| 依赖哪些**外部服务** | 不依赖 | §6.4 |
| 附件放进哪个**存储** | 不产出附件 | §6.4 |
| 需要什么样的**执行环境** | 没有特殊要求 | §6.4、§6.8 |
| **调用它需要模型给得出哪些[模态](../PF-013-model-profiles-and-invocation/design.md#模态)** | 只要文本——**所有模型都给得出** | **§6.11** |
| **它的结果里会有哪些模态** | 只有文本 | **§6.11** |
| **能不能后台执行**、前台跑多久自动转后台 | **不能后台**（§6.6） | §6.6 |

**六项都是可选的，不声明才是常态。**

**但「不声明」的意思，并不一样。**前五项不声明是「我不要」——
不依赖、不产附件、对环境没要求、参数只要文本、结果只有文本，
**少一个前提，反而更容易可用**。
最后一项不声明是「**我不许**」——**默认不能后台**。

> **差别在于：前五项声明的是「我需要什么」，最后一项声明的是「我允许什么」。**

需要什么，没说就是不需要；允许什么，**没说就是不允许**。

> **前五项进的都是[依赖声明](#依赖)那一串名字**——
> 外部服务、存储、执行环境的设施，以及中间那两项指的**这一次用的那个模型的能力**。
> **它们不是五种不同的机制，是同一串清单里的五类名字。**
> 两端的模态各一项，而**各自的候选提供者不同**，见 [§6.11](#611-工具两端各要什么模态)。

**声明不是免费的。**每多一项，就多一个可能不被满足的前提：
声明了依赖某个存储，那存储没配好，这工具**整个**不可用——
哪怕它九成的用法根本不产出附件。

> 该声明的是**它真的要的**，不是**它可能会用到的**。

这与 §6.4「声明与实际必须对得上」是同一条规矩的两面：
**少声明了在运行时炸，多声明了在装配时就已经不可用。**

#### 其中两项声明的是设置项

六项里，**有两样是可以被各层改的值**，其余是这个工具自己的事实：

| 声明 | 它是什么 | 类别（[PF-002 §5.2](../PF-002-assets-settings-and-permissions/design.md#设置项分四类资产声明每一项时必须标类别)） |
|---|---|---|
| 需要什么样的执行环境 | **设置项「目标环境」**：形状是「绑定在哪一层 × 要哪几种设施」，默认值是作者给的那一份（§6.8） | **落点与身份**——改了它，这次执行落在哪就换了 |
| 前台跑多久自动转后台 | **设置项「转后台阈值」**（§6.6） | **偏好**——改错了顶多节奏不合适 |
| 外部服务、存储、两端模态 | [依赖声明](#依赖)里的名字。**谁满足它，看谁生效在那个名字上**，不靠哪一层配 | 不是设置 |
| 能不能后台执行 | **作者的许可**——他的代码有没有准备好在那种时序下被使用，只有他知道。人可以决定「现在切」，[不能决定「它能不能切」](#66-前台后台-与-等待态是两个维度) | 不是设置 |

> **定义里声明的是设置项的形状与默认值，不是它最终的值。**
> 持有这个工具的各层按 [PF-002 的三方分工](../PF-002-assets-settings-and-permissions/design.md#三方分工资产定形状各层配值运行时求值)配值，
> 运行时求值；**类别决定这项值能从哪些层来**——落点与身份类的，工作区配不了。

**六项声明之外，工具还有两项偏好类设置：[前台上限与并发上限](#前台上限与并发上限)。**
同样是定义给默认值、各层配值；**定义不给、也没有哪一层配，就没有这一项限制**。

#### 不在定义里的三样

| | 它在哪 |
|---|---|
| **[等待态](#等待态)** | 工具**函数自己的逻辑里**用的一个原语 |
| **[发帧](#发帧)** | 同上，另一个原语 |
| **要不要[卸载](#610-结果太大时卸载而卸载是第三个维度)** | 工具**每一次返回值里**的事（§5.4） |

> **这条界线决定了工具作者该在哪里做判断。**

「我必须跑在沙箱里」是作者对这个工具的判断，跟这次传了什么参数无关，所以它写在定义里（作为「目标环境」那项设置的默认值）。
而「这次要不要停下来等个应答」「这次该不该往外播报」「这次的结果该不该卸载」，
都取决于**这一次跑成什么样**——同一个工具，查一条记录和导出整张表，
没有理由给同一个答案。

**发帧还多一条理由**：就算某个工具真的每次都发帧，**在定义里写上这一格也没人要用**——
[系统是按实际收到什么来解析的](#帧长什么样由一份协议约定不由工具定义声明)，
那一格从头到尾不会被读一次。

### 5.4 返回值：两种写法，一种模型

**工具作者有两种写法：**

| 写法 | 系统怎么用它 |
|---|---|
| **就按普通函数那样返回** | **整个返回值当字符串用** |
| **返回一个 `ToolResult`** | 按里面的字段分别处理 |

`ToolResult` 装三样，后两样可选：

| 装什么 | 是什么 |
|---|---|
| **进消息的内容** | 已经组织好的、给 agent 看的那部分 |
| **要卸载的原始结果**（可选） | 给了它，就是[声明这次要卸载](#610-结果太大时卸载而卸载是第三个维度)；**摘要由工具作者自己写** |
| **[附件](#工具的产出)的地址** | 附件存在哪，agent 按址自己去取 |

#### 两种写法，到 agent-loop 那里只剩一种

**普通返回在上报的时候会被转成 `ToolResult`。**

> **工具作者的方便，不传染给系统。**

写个三行的小工具不必先学一套结构；而
[agent-loop](../PF-012-agent-loop-and-run/README.md) 那边**只有一种形状要处理**，
不必在每个位置都判断「这次返回的是哪一种」。

**两种写法的能力不对等，这是有意的**：只有 `ToolResult` 能带卸载和附件。
按普通函数那样返回的，**就是一段文本**——想要更多，就用那个结构。

#### 每一次执行都留一份账

**一次工具执行是一件有头有尾、可以单独记账的事。**
它完成的时候，连同结果一起上报的还有这次的账：跑了多久、耗了多少计算，这一类事实。

**这份账不进 agent 的上下文。**它是给系统的——诊断、计量、看清楚是哪个工具在拖后腿。
塞进 ToolMessage 只会白占位置：**agent 拿 cpu 时间做不出任何判断**。

> 账**怎么被消费**（谁读得到、留多久、进不进计费）归观测与计量那一块，
> 本 topic 只定**每次执行都要留下它**，以及**它不进上下文**。

### 5.5 一次工具执行的收场，有六种

**agent 必须分得清它们**，因为下一步动作完全不同：

| 收场 | 它是什么 | agent 该怎么办 |
|---|---|---|
| **完成** | 拿到结果 | 继续 |
| **失败** | 真的没成——**包括它自己的 runtime 失去了连续性**（[§6.12](#停机之后它不重来)，写给 agent 的原因是「异常中断」） | 重试、换招，或报告 |
| **不可用** | 这个东西现在用不了（替换件应答） | **绕路**——别重试，重试一百次也一样 |
| **转后台** | 还在跑，位置先占着 | **先干别的**，跑完了会来通知 |
| **被中断** | 有人有意停掉了它：用户叫停、agent 掐掉自己发起的后台执行、前台跑到了上限，或它所在的那一层被有意停掉（[§6.12](#它的宿主是谁决定了什么会带走它)），**不是失败** | **别自动重试**——重试就是无视停掉它的那个意思 |
| **等不到应答** | 等待态到头了，没人回 | 按等不到处理，不是失败也不是被拒 |

> **四种「非完成」里只有一种是失败。**把它们混成一种，agent 的下一步必然是错的：
> 该绕路时死磕，该等待时重来，用户刚叫停它又跑一遍。

#### 转后台是前台那一次调用的收场，后台执行另有自己的收场

**转后台收掉的是前台那一次调用**——agent runtime 不再阻塞在它上面，位置上的那条返回就此落定，这一轮接着往下走。
**执行本身还没完**：它在后台接着跑，**跑到头还有它自己的一个收场**，
以[提醒](#66-前台后台-与-等待态是两个维度)的形式到达 agent。

| | 收场从哪几种里出 |
|---|---|
| **前台那一次调用** | 六种都可能 |
| **转后台之后的那段执行** | **完成、失败、被中断、等不到应答**四种之一（[本版后台不进等待](#66-前台后台-与-等待态是两个维度)，最后一种本版不出现） |

后一行少的两种不是漏了：**不可用**只出自替换件，而替换件从不真的跑，转不了后台；
**转后台**是单向的一步，[已经在后台的不会再转一次](flows.md#32-一次工具执行)。

**六种都以正常的工具返回消息到达 agent**（后台那段执行的收场以提醒到达），语义写在消息里。
**没有一种是以[报错](../PF-011-off-nominal-handling/design.md#非常态)的形式抛给它的**——
报错不带语义，agent 只能猜。

#### 参数说完了却解析不了的调用：不执行，以失败回给 agent

模型给出的一个工具调用，参数已经说完，却解析不成这个工具要的形状——
**这次调用不执行，结果记失败、原因写明参数解析不了，照常回给 agent**；那个调用块照原文留在它自己的回复里。

**它和[流断在半路时没长完的那个调用块](../PF-009-context-message-types/design.md#半截的工具调用记下来但不给模型看)不是一回事。**
那时回复本身就没收完，半截调用两边都不给；这里回复是完整的，运行还在转，
**agent 必须看见才改得了**——不回给它，它会以为调用已经发了出去，等一个永远不会来的结果。
落在失败这一格，给它的下一步正是「换招」：改了参数再调。

#### 这张表同时划出了这一层的非常态边界

**产品负责人 2026-09-20 给的分法**：
**一层能自行了结的[非常态](../PF-011-off-nominal-handling/design.md#非常态)要穷举出情形，
了结不了的[上交](../PF-011-off-nominal-handling/design.md#上交)、不必穷举。**

**这一层的那条线，正好落在这张表上：**

| | 什么 | 怎么走 |
|---|---|---|
| **本层了结得了的** | **恰好就是这六种收场**——**它们是穷举的** | **以一条正常的工具返回消息到达 agent**，带语义，**不上交** |
| **本层了结不了的** | 其余全部：工具的实现自己炸了、执行环境塌了、结果落不了盘…… | **[上交](../PF-011-off-nominal-handling/design.md#上交)给外面一层**，[带身份与分类，不带正文](../PF-011-off-nominal-handling/design.md#58-上交交的是什么)。**不必穷举** |

> **为什么前者非穷举不可**：agent 要据它选下一步，**多一种它不认识的，它就只能猜**。
> **为什么后者不必穷举**：它已经交出去了，**这一层不再需要为它选下一步**——
> 而[列举永远列不全，列出来的第二天就过期](../PF-011-off-nominal-handling/design.md#57-这不是一张清单是一个判断)。

**这与 [PF-013 在模型调用那一层的分法是同一条](../PF-013-model-profiles-and-invocation/design.md#54-三类事实归本层定死其余照状态码)**，
**只是那一层的「了结得了」是「再试一次就好」，这一层的是「有一个说得清的收场」。**

## 六、产品规则

### 6.1 常驻标记挂在引用条目上，agent definition 压 plugin

- 标记标在**「装配它」这条引用**上，不在工具或技能自身。
- 一个 plugin 在包含某个成员时，**同样可以标**。
- 两处都标了，**以 agent definition 为准**。

第三条的理由和第一条完全一样：**上下文预算是装配方的问题**。
plugin 作者不知道使用他的 agent 还装了多少别的东西，
把最终决定权留在他那儿，预算就永远收不拢。

**有一批条目恒定占槽位，任何人都改不掉**——它们是
[PF-007 定义的 **meta**](../PF-007-meta-capabilities/design.md#meta)：
一整类能力的统一入口，其中就包括能力发现与取用的那两扇门。

它们不能不是常驻——否则 agent 无从发现任何东西，整套机制转不起来。
**这是一条自举约束**，而 PF-007 把它推得更深：
**meta 必定常驻不是产品选择，是结构逼出来的**（够到非常驻能力的唯一途径就是 meta，
若 meta 自己也不常驻，那就永远够不着它）。

> **本 topic 只需要知道「有这么一批，且关不掉」。**
> 具体有哪十三扇、各自长什么样，归 [PF-007](../PF-007-meta-capabilities/README.md)。

### 6.2 可用性在每次 run 开始前重算

**不是装配时算一次就定了。**理由是它依赖的东西自己会变：
外部服务会断，执行环境会被策略换掉，被依赖的工具可能刚刚被移除。

> **一次 run 里的每一次执行尝试，都算一次「开始」**——重试与从中途恢复
> [各自重算一遍](../PF-012-agent-loop-and-run/design.md#57-一次尝试三条路通向重新算一遍)。
> **这一条归 [PF-012](../PF-012-agent-loop-and-run/README.md)**，本 topic 只定「每次开始前要重算」。

由此得到一条必须让所有人有心理准备的性质：

> **同一个 session 里，上一次 run 能用的东西，这一次可能就不能用了**，反过来也一样。

这不是故障。agent 得能承受它——所以才有 §6.3 的替换件，
以及「它必须知道自己现在有什么」这条要求。

### 6.3 不可用时，装的是同名替换件，不是不装

**这是本 topic 最容易做错的一条。**

| 做法 | 后果 |
|---|---|
| 不可用就**不装** | **动作空间随环境波动而变形**，[I-4](../PF-004-agent-definition-and-assembly/design.md#61-不变式) 当场作废。agent 不知道自己少了什么，用户查不出东西为什么没了 |
| **装同名替换件** | **形状恒定**。agent 当场知道「这个我有，但现在用不了」，可以绕路；用户问得出原因 |

因此：**不可用是一个运行期的状态，不是装配期的删除。**

**agent 一共只会遇到两种情形**，本 topic 管的是第二种：

| agent 遇到的 | 什么造成的 | 动作空间 | 它的感受 |
|---|---|---|---|
| **不可见** | [移除](../PF-002-assets-settings-and-permissions/design.md#64-移除与禁用是两个动作)（不再持有）、[禁用](../PF-002-assets-settings-and-permissions/design.md#64-移除与禁用是两个动作)（仍然持有但装配时被滤掉） | **变小** | **不知道有过这回事** |
| **可见但用了一定失败** | **依赖不满足**（本 topic） | **不变** | **知道有、知道现在用不了、知道缺什么** |

> **[禁用是不可见，不可用是可见但用了一定失败](../PF-002-assets-settings-and-permissions/design.md#但对-agent-来说两者一样都不可见)。**

**这一行界线必须守住**：不可见的东西 agent 连绕路都无从谈起，它只会以为自己没这个能力；
可见而用不了的，它读得到原因，**当场就能换一条路**。
[把不可用做成「不装」，就是把第二种塌进第一种](#63-不可用时装的是同名替换件不是不装)。

**「同名」要求的其实是同形。**工具连调用参数都与原件一致，技能的名字一致——
差一点都不行：agent 手上那份用法一旦对不上，它连「这东西本来能怎么用」都看不出来，
**而形状恒定正是这一条的全部目的**。

**同形之下只换一样东西：它的说明。**说明改成讲清「现在用不了、缺什么」，
agent 在动手之前就读得到，可以直接绕路。

**但说明不是闸。**它给模型看，模型读不读、听不听，不由系统决定——
**agent 照样可能去调它**。所以替换件**只有一种行为**：

> **调用它，必定得到「不可用」这一个收场，带着原因。**

不论怎么调、带什么参数，结果都一样；**它不会执行原来那件事，也不会时灵时不灵**——
那样 agent 就再也判断不了自己手上到底有什么。

**这个收场以一条正常的返回到达 agent**，不是报错——它要回答的是「为什么」，
而[报错](../PF-011-off-nominal-handling/design.md#非常态)带不了这个信息。

### 6.4 依赖声明与解析

**声明写在哪、一共有几项**，见 [§5.3](#53-一份工具定义长什么样)；**这一节定的是系统拿到之后怎么算。**

- **技能**声明它要用到哪些工具，**用[能力标识](../PF-002-assets-settings-and-permissions/design.md#63-组合的引用指向能力标识)指**，
  不指某一份具体的工具资产。
- **工具**声明它依赖哪些外部服务。
- **产出[附件](#工具的产出)的工具**，声明它把附件放进**哪个存储**。
- **工具，以及带脚本的技能**，声明它需要什么样的执行环境——**由两件事共同确定：
  绑定在哪一层，以及要有哪几种[设施](../PF-005-execution-environments-and-sandboxes/design.md#设施)。**
  技能也要声明，是因为它**可以带可执行的脚本**
  （[PF-002](../PF-002-assets-settings-and-permissions/design.md#八类资产)），
  而脚本要跑就要落地；不给它地方声明，就只能靠猜或者默认塞给宿主机——
  **后者直接绕过了安全判断**。跑脚本这个动作本身归
  [PF-007 §6.2](../PF-007-meta-capabilities/design.md#62-skills通向任意技能)。
- 装配与每次 run 前，**逐项看有没有在场且可用的提供者**，算出这一项当下可不可用。

**怎么算，一句话说得完**：

> **每一项都有提供者且提供者可用 → 可用；缺一项 → [不可用](#63-不可用时装的是同名替换件不是不装)。**
> **提供者换了或没了 → 重算。**

**没有「部分可用」。**[声明里只有必需项](#只有且只有必需)，所以结果只有这两个。
一样可有可无的东西**不进声明**，用的时候现探——它探不到，是那一次执行的事，
**不是这个工具当下不可用**。

**声明与实际必须对得上。**一个工具声明自己只要 A，实际却去用了 B——
那它的可用性算出来是对的，跑起来是错的，而且**排查时所有人都会先怀疑别处**。

**存储那一项，成立的条件比别的项多一半**：

> **光那个存储在不够，还得有工具能把东西从里面读出来。**

一个工具产出了附件，却没有任何工具能从那个存储取回来——那个附件**等于不存在**，
而 agent 会拿着一个地址反复尝试，**却永远取不到**。

所以**这一项算不算被满足，连同「读取那个存储的工具在不在」一起判**；
它没被满足，这个工具就和缺了任何别的一项一样，**当下不可用**。

### 6.5 工具执行有自己的运行时，绑定在 session 上

- **工具执行的运行时与 [agent runtime](../PF-012-agent-loop-and-run/design.md#agent-runtime) 解耦**——
  它是自己独立的一个 runtime，**从不由 agent runtime 承载**，前台后台都一样。这是它能在后台继续跑的前提。
- **与一次 run 解耦**：记录得下来是哪一次 run 发起的，但**生命周期不绑在一起**。
- **与会话绑定**：结果回到那个会话；**它的宿主就是会话**。
- **前台 / 后台只说 agent runtime 阻不阻塞在它上面**（[§5.2](#前台后台说的是-agent-runtime-在不在等它)）。
  所以 **agent runtime 被回收，不影响任何一次工具执行**：前台的照样跑、照样等，协程重建后接着等它（[§6.12](#它的宿主是谁决定了什么会带走它)）。
- **[会话被归档](../PF-015-session-lifecycle-and-ownership/design.md#63-归档先停活儿再落状态)时仍未结束的工具执行，不论前台后台，收场都是[被中断](#55-一次工具执行的收场有六种)。**
  归档是会话这一级**有意的停止**——[人手动归档或到期自动归档](../PF-015-session-lifecycle-and-ownership/design.md#62-归档有两条来路人手动或到期自动)——不是这次执行没做成，所以不算失败；
  而收件人都没了，跑完也没处送。**这一刀是不可逆的**：撤销归档不会把它接回来。

### 6.6 前台/后台 与 等待态，是两个维度

**它们不互相决定**，四种组合都成立：

| | **不在等待** | **在等待** |
|---|---|---|
| **前台** | 正在跑，占着这一轮 | 停着等应答，这一轮等着它 |
| **后台** | 在后台跑 | 在后台等应答 |

> **本版把「后台 × 在等待」这一格关着：要等应答的执行只在前台等。**
> 产品负责人 2026-09-23 的原话是「目前我们应该只定了要等待答复的工具只能阻塞在前台，但未来未必」
> （[D-058 Q15](../../record/decisions/message-and-shape-rulings/decision.md)）。
> **关着的是这一版的用法，不是这个模型**：两个维度仍然正交，
> 而一次执行的真实结果落成哪种消息，[只看那个位置上有没有占位](../PF-009-context-message-types/design.md#systemremindermessage)——
> 没有占位就落成工具返回消息，已经有占位（转了后台）就以提醒到达。**这是一条判断，不是一张按工具分的表**，
> 将来打开这一格，结果怎么到达不必重写。

[工具定义](#53-一份工具定义长什么样)可以声明：

- **能不能在后台执行**；
- **前台跑超过多久自动转后台**（多久是它的一项设置，[偏好类](#其中两项声明的是设置项)：定义给默认值，持有它的各层可以改）。

**不声明就是不能后台。**

> **默认往保守的那一边倒。**

理由与[执行环境不许降级满足](#68-工具怎么提执行环境的要求)是同一条：
**没表过态，不等于表了同意。**一个工具的作者从没想过「我被丢到后台会怎样」，
系统就替他想了——而**转后台改变的是这次执行的语义**：
run 不再等它，结果换个时候以提醒的形式回来。
**它的代码里可能压根没准备好在那种时序下被使用。**

反过来，默认可以后台的代价是**静默的**：没人会收到报错，
只会偶尔看到一个工具在不该异步的地方异步了，**而排查时所有人都会先怀疑别处**。

用户**也可以手动把它切到后台**——**前提仍然是这个工具声明了允许**。
手动这条路不绕开声明：**人可以决定「现在切」，但不能决定「它能不能切」。**

**转后台有三个触发源，[插队](../PF-014-inbound-intake-and-queueing/design.md#插队)是其中之一。**

| 触发源 | 谁发起 |
|---|---|
| **前台跑到了转后台的时长，或到了[前台上限](#前台上限与并发上限)** | 系统，按这个工具的设置 |
| **用户手动切** | 用户 |
| **用户[插队](../PF-014-inbound-intake-and-queueing/design.md#插队)，而这个工具允许转后台** | **系统顺带触发**——[「最大程度保留」那条原则的结果](../PF-014-inbound-intake-and-queueing/design.md#53-插队的核心原则)：能保留的就保留，转后台保留得最多 |

> **第三行照样不绕开声明。**工具没声明允许，插队时它被**中断**，不是被转后台。

**「发起时就在后台」不是一次「转」**：agent 在发起时就决定这次不占前台（[PF-007 `run_in_background`](../PF-007-meta-capabilities/design.md#64-shell通向命令行)），
前台那一次调用当场就以转后台收场，位置上同样放一条占位，原因写「**发起时就在后台**」。
**它同样不绕开声明**：没声明允许后台的，这样发起也起不来。

#### 前台上限与并发上限

**这两项是工具的[设置](../PF-002-assets-settings-and-permissions/design.md#tool)**（偏好类：定义给默认值，持有它的各层可以改；**不设就没有这一项限制**）：

| 设置 | 它管什么 | 到了会怎样 |
|---|---|---|
| **前台上限**（超时） | 一次执行**在前台跑**最多多久。**停在等待态上的时间不算**，转了后台之后也不再算 | **允许后台的，转后台**（原因同「转后台」）；**不允许的，被中断**，占位原因写「**前台超时**」 |
| **并发上限** | 同一个会话里，同一个工具**同时在执行**的最多几次，前台后台一起算 | **超出的排队**，按发起的先后轮到，不拒绝 |

**等待态上的时间不算，是被 [§6.6 的等待上限判据](#66-前台后台-与-等待态是两个维度)逼出来的**：
[`Ask()`](../PF-007-meta-capabilities/design.md#611-ask通向人) 停在前台等人、永不过期；前台上限要是把等人的时间也算进去，
**它就成了一个替人签字的到点**——那正是下面「不花钱的等待不该设上限」要挡的。

**超时被中断，不是失败**：上限是持有它的那一层**有意**给的一个界，到点停下，是那个意思在起作用；
落成失败，agent 会照「重试」去读它，**再跑一次同样会撞到同一个界**。

**转后台 agent 要有感知**：位置上先放一条占位的工具返回消息，
说明它转后台了。跑完之后，以**提醒**的形式到达 agent
（**怎么送达归 run 那一块**，本 topic 只定这个产品语义）。

**等待态也要能被系统看见。**一次工具执行停在那里等应答，和它卡死了，
从外面看可能一样——**但处理方式完全相反**。等待态必须是显式的状态，
而且**它等的是什么形状的应答，要说得出来**，否则没人知道该给它什么。

**要不要给等待设上限，不是这个原语的属性，是每一个使用它的人的属性。**

判据只有一条：**这个等待占不占着东西。**

| 等的时候占着资源 | 例如一个沙箱里的进程停在那儿等 | **可以设上限**，到头了按 §5.5 的第六种收场 |
|---|---|---|
| **等的时候什么都不占** | 问询发生在动手之前，世界里什么都没发生 | **不该设上限。**不花钱的等待没有理由到点 |

上限具体是多久属于资源政策，与
[会话级沙箱的最大存活时间](../PF-005-execution-environments-and-sandboxes/design.md#63-会话级沙箱到点销毁数据不留存)同类，
**本版不定**。

**[PF-007 的 `Ask()` 明确落在第二行](../PF-007-meta-capabilities/design.md#611-ask通向人)**：
它不设上限，系统永不替人作答。一旦设了上限，就必须规定「到点算什么」——
**那就是系统替人签了字**。

**「等不到应答」这个收场本身不作废**，它对第一行仍然成立。

**还有第三个维度与这两个都不相干——[结果卸载](#610-结果太大时卸载而卸载是第三个维度)，见 §6.10。**

### 6.7 用户可以中断，而中断不是失败

- 一次工具执行的生命周期，**用户可以提前中断**。
- **中断不意味着失败。**它以一条正常的工具返回消息占位，
  语义是「**这次执行被用户手动中断了**」。

为什么非要区分：**失败是「这事没成」，中断是「这事不做了」。**
把中断当成失败递给 agent，它会重试——而用户刚刚明确表示不想让它跑。
**agent 越勤快，后果越糟。**

#### 占位消息一律要说清原因

**占位不说原因，agent 只能按「失败」去读它**——而那正是上一段要挡的事。

| 占位的原因 | 什么时候 |
|---|---|
| **用户手动中断** | 用户直接叫停这一次执行 |
| **转后台**（自动 / 用户手动切） | §6.6 的前两个触发源；自动那一种含[前台上限](#前台上限与并发上限)到点而工具允许后台 |
| **发起时就在后台** | agent 发起时就决定这次不占前台（[§6.6](#66-前台后台-与-等待态是两个维度)） |
| **因[插队](../PF-014-inbound-intake-and-queueing/design.md#插队)转后台** | 插队，而这个工具**声明了允许** |
| **因插队被中断** | 插队，而这个工具**不允许**转后台 |
| **人拒绝回复** | 插队时这次执行正停在 [`Ask()`](../PF-007-meta-capabilities/design.md#611-ask通向人) 上等人——[它不可转后台](../PF-007-meta-capabilities/design.md#611-ask通向人)，所以被中断 |
| **运行被取消** | 这一次运行被取消时它还在前台（[§6.12](#它的宿主是谁决定了什么会带走它)）——**不借「用户手动中断」**：取消的可能不是用户，而且停的是这一步，不是这一次执行 |
| **前台超时** | 到了[前台上限](#前台上限与并发上限)，而这个工具**不允许**转后台 |
| **会话被归档** | 归档时它还没结束，前台后台都算（[§6.5](#65-工具执行有自己的运行时绑定在-session-上)） |
| **工具执行异常中断** | 据点停过机，恢复时这次调用还没有返回消息，工具执行运行时里也找不到它（[§6.12](#停机之后它不重来)）——由系统在恢复时追补 |

**后台那一段被 agent 自己掐掉**（[`BkgJobs().terminate`](../PF-007-meta-capabilities/design.md#610-bkgjobs通向自己发起的执行)）时，
原因写「**被 agent 停掉**」——**它写在那段执行收场的提醒里，不在占位上**：那次调用的占位早在转后台时就放下了。
与「用户手动中断」分开，[是 PF-007 的要求](../PF-007-meta-capabilities/design.md#610-bkgjobs通向自己发起的执行)：两者都是中断，**要分得出是谁做的**。

> **这几种是「原因」的取值，不是几种收场。**
> 它们落在[六种收场](#55-一次工具执行的收场有六种)里的**转后台**、**被中断**与**失败**三格上——
> 最后一种落在**失败**，**不是被中断**：没有任何人叫停它，agent 该自己判断要不要再调。
> **一格都没多。**

**后台那一段的收场以提醒到达，原因同样要写清。**转了后台的执行随据点停机没了、也没有它结束时回来的那条提醒，
系统在恢复时追补一条提醒，说清「**后台工具执行异常中断**」——收场同样是**失败**。

> **「因插队转后台」那一条尤其不能省**：转后台是一个**正常的收场**，
> 不说原因的话，agent 会以为是它自己或工具作者的安排，**而实际上是用户按了一下**。

### 6.8 工具怎么提执行环境的要求

- 工具**在定义时**声明「**目标环境**」这一项设置：它的**形状**由两部分组成——**绑定在哪一层** + **需要哪几种设施**；
  它的**默认值**是**工具作者的判断**：他最清楚这个工具的执行是不是绝对安全。
- 它归**[落点与身份](../PF-002-assets-settings-and-permissions/design.md#设置项分四类资产声明每一项时必须标类别)类**：
  持有这个工具的组织、租户可以在自己那一层配值，**工作区配不了**。
- **求值出来的那一份，就是这次执行的要求。**运行时按它**自动匹配**：给它一个满足要求的执行环境。
- **[执行环境权限](../PF-005-execution-environments-and-sandboxes/design.md#执行环境权限)改了，下一次执行按新值现算落点**——
  [不必重建任何东西，agent 无感、动作空间不变](../PF-005-execution-environments-and-sandboxes/design.md#53-换执行环境是换一个值不是开关一套机制)。

**要求满足不了，这个工具就不可用**，走 §6.3 的替换件。
**绝不能退一步给它一个不满足要求的环境**——要求里写着要隔离，
是因为给出它的人判断这东西不安全；降级满足等于绕过那个判断，
与 [PF-005「沙箱创建失败不得退回宿主机」](../PF-005-execution-environments-and-sandboxes/design.md#62-宿主机不提供租户隔离因此必须被显式允许)是同一条。

### 6.9 agent 创建与修改工具、技能：本版只定三条

**其余全部归后续 topic**，这里只固定最小必要的部分：

1. **要有授权才能做。**没有授权，创建与修改都不发生。
2. **造出来的是一份[资产](../PF-002-assets-settings-and-permissions/design.md#八类资产)**，不是临时草稿。
   它的**归属算得出来**——租户上下文本来就注入在 agent runtime 里，
   不需要为这件事另加机制。
3. **经显式增量装载后当场能用，但不改变 agent definition。**动作空间就地变长，
   [agent runtime](../PF-012-agent-loop-and-run/design.md#agent-runtime) 不重建。
   **改了 definition 的，在下一次 run 时重建 agent runtime。**

单纯在工作区写入技能、工具或 Agent Definition 文件不等于完成装载，不自行触发当场可用或下一 run 重建。工作区来源沿 [PF-020](../PF-020-workspace/design.md#装载附着与装配)，在实际装配或显式资产 reload 时校验和加载；候选校验失败，原内存数据不变。

第 3 条是[构成变了却不重新装配的那个例外](../PF-004-agent-definition-and-assembly/design.md#63-三类变化三种传播)：
**它装上来的是非常驻的东西，系统提示词的成分一个字没动**——
判据与落点都在 PF-004，本 topic 只定它的产品语义。

### 6.10 结果太大时卸载，而卸载是第三个维度

**[卸载](#卸载)的产品形态：**

| | 原样 | 卸载之后 |
|---|---|---|
| 消息里是什么 | 完整结果 | **一条占位**：够用的那部分 + 有多大 + 怎么取全文 |
| 原始结果 | —— | **存着，没丢** |
| agent 想看全的 | 直接读 | **分页取回**（[PF-007 的 `Tools()`](../PF-007-meta-capabilities/design.md#61-tools通向任意非常驻工具)） |

#### 两条来路，产物不同

| 来路 | 谁决定 | 占位里留下的是 |
|---|---|---|
| **工具自己声明** | **工具开发者**——在 [`ToolResult`](#54-返回值两种写法一种模型) 里给出要卸载的原始结果 | **他自己构建的摘要**，也就是那条进消息的内容 |
| **系统兜底** | 系统发现**单条工具消息超了限额** | **首尾保留**的机械截断 |

**产物不同是有意的**：工具开发者知道自己这份结果哪部分要紧，
他写的摘要有信息量；**系统不知道，所以它不猜**。

> **系统不替工具开发者写摘要。**
> 猜出来的摘要比机械截断更危险——**因为它看上去是有意义的**。

机械截断诚实：agent 一眼看得出中间缺了一段。而一份由系统臆造的摘要，
agent 会当成完整的转述用下去，**而它不知道自己漏了什么**。

#### 执行这件事的逻辑在 agent-loop 里

**判断要不要卸载、以及执行卸载这个动作，都是
[agent-loop](../PF-012-agent-loop-and-run/README.md) 里的逻辑**——
工具返回的那个结构由它解析，单条消息超没超限额也由它算。

**本 topic 定的是卸载这件事的产品语义**：它是什么、占位里该有什么、
它与执行姿态正交。**谁在什么时候执行它，归那边**——落点是
[PF-012 §5.10](../PF-012-agent-loop-and-run/design.md#510-卸载结果落成消息之前的那一关)
（**那个 topic 目前还是草稿**）。

**必须让 agent 分得出「结果被卸载了」与「工具没返回什么」。**
混在一起，它会以为这次调用白跑了，于是重来一次——**而重来一次得到的还是一条占位**。

**卸载与执行姿态互不相干**，这是三个正交的维度：

| 维度 | 问的是什么 |
|---|---|
| **前台 / 后台**（§6.6） | 这次执行，**run 等不等它** |
| **等待态**（§6.6） | 这次执行，**中途要不要停下来等外部输入** |
| **卸载**（本节） | 这次执行**的结果**，**进不进得了消息** |

**两两正交**：后台执行的结果可以被卸载，进过等待态的执行的结果也可以被卸载；
反过来，卸载**不影响**它是前台还是后台、也**不影响**它等没等过。

**不写明这一条，很容易长出「结果大就转后台」这种耦合**——那是两件事：

> **结果有多大，与它该不该占着 run，毫无关系。**

### 6.11 工具两端各要什么模态

**一个工具跟模型之间有两条通道，两端各要一件事：**

| 哪一端 | 它要模型做什么 | 例子 |
|---|---|---|
| **调用它的时候** | 模型要**给得出**参数里那些模态 | 一个「照着这张草图改」的工具，参数里要一张图——**模型得吐得出图** |
| **结果回来的时候** | 模型要**收得下**结果里那些模态 | 一个截图工具，结果里是一张图——**模型得看得了图** |

**两端各是[依赖声明](#依赖)里的一项必需项**：指的不是外部服务，
是**这一次[有效模型](../PF-013-model-profiles-and-invocation/design.md#选中模型-与-有效模型)的模态能力**。
所以它们**走[可用性](#可用性)已有的那一套**，[每次 run 开始前重算](#62-可用性在每次-run-开始前重算)，
缺了就[装同名替换件](#63-不可用时装的是同名替换件不是不装)——**本 topic 不另造一套机制**。

#### 两端的差别在候选提供者，不在规则

**规则只有一条，两端一样：这一项有提供者就满足，没有就不可用。**
**不一样的是谁能当提供者：**

| 哪一端 | 这一项要什么 | 谁满足得了 |
|---|---|---|
| **调用它的那一端** | **模型给得出参数里的这种模态** | **只有有效模型自己。**模型吐不出那种东西，**这次调用根本构造不出来**——它不是「效果差一点」，是「压根发不出去」 |
| **结果那一端** | **这种模态的结果能被模型收下** | **有效模型的输入能力，或者 [PF-013 的转换件](../PF-013-model-profiles-and-invocation/design.md#转换件)**——后者在落盘之前把那个块转成文本，**收不下图的模型照样读得到** |

> **「结果降级」不是另一条规则**，只是这一项**被转换件而不是被模型满足了**。
> **两者都没有，才轮到不可用**——转换件转不出来的那些。

**候选提供者只有一个的那一端，看着就「严」**：调用端没有第二个人能顶上。
**把两端做成同一条规则，必错一头**——
要么两端都放行（于是模型吐不出图的时候，工具调用**每次都构造失败**），
要么两端都只认模型（于是**转换件白装了**，一个截图工具在纯文本模型下永远不可用，
而它明明能把截图说成一段文字）。

#### 它同时决定了换模型之后哪些工具还在

**[换模型是用户的直接命令，合法目标不得拒绝](../PF-013-model-profiles-and-invocation/design.md#65-切换是用户的直接命令合法目标不得拒绝)**，
所以**换完之后动作空间不变**：新模型满足不了某一端模态的那几个工具，
**变成[不可用](#可用性)，原位装上[同名替换件](#63-不可用时装的是同名替换件不是不装)**——
那是[可用性重算](#62-可用性在每次-run-开始前重算)的自然结果，**不是一次失败**，
也正是[三层正交](#51-三层正交)那条：可用性变了，动作空间不跟着变。

> **而它对用户必须是看得见的。**换到一个吐不出图的模型，
> 那几个要图当参数的工具**应当当场说得出自己为什么用不了了**——
> **agent 要知道它存在、调用必得「不可用」、并且能解释。**

### 6.12 工具执行的运行时可以被单独控制，而它停了就不重来

**[它与 agent runtime、与一次 run 都是解耦的](#65-工具执行有自己的运行时绑定在-session-上)**，
所以它**可以被单独动**，而[插队](../PF-014-inbound-intake-and-queueing/design.md#插队)正压在这一条上面：

| 单独动它的手段 | 谁能发 | 结果 |
|---|---|---|
| **切到后台** | 用户，**或[插队](../PF-014-inbound-intake-and-queueing/design.md#插队)顺带触发**（前提仍是[这个工具声明了允许](#66-前台后台-与-等待态是两个维度)） | 收场＝**转后台** |
| **中断它** | 用户，**或插队顺带触发**；**agent 自己**只对它发起的、已在后台的执行（经 [`BkgJobs().terminate`](../PF-007-meta-capabilities/design.md#610-bkgjobs通向自己发起的执行)） | 收场＝**被中断**（[不是失败](#67-用户可以中断而中断不是失败)） |

> **「单独」这两个字是硬的**：动一次工具执行，**不动这一次模型调用，也不动这个 run**。
> **只有一个「全停」按钮的话**，一次模型回复刚开始、而三个工具调用里已经跑完了两个，
> **那两个的结果就一起没了**——而[它们的外部效果已经发生](../PF-014-inbound-intake-and-queueing/design.md#53-插队的核心原则)。

#### 停机之后，它不重来

**工具执行的运行时是[计算资源](#tool-execution)，停机就没了。**
**而它与别的三层不同的地方在于：它不重算。**

| | [run / agent-loop](../PF-012-agent-loop-and-run/design.md#57-一次尝试三条路通向重新算一遍) | **一次工具执行** |
|---|---|---|
| 停机之后 | **重新算一遍**——状态都在日志里 | **不重来** |
| 为什么 | 它是[纯函数的求值](../PF-012-agent-loop-and-run/design.md#agent-loop)，**重算一定得到同一个答案** | **它可能已经在外面做了事**，[而那些效果收不回来](../../foundation/README.md)。**重来就是做第二遍** |
| 那它算什么 | —— | **算[失败](#55-一次工具执行的收场有六种)**——[产品负责人 2026-09-17 的裁决](../PF-012-agent-loop-and-run/decisions.md#一拍板记录)：「**系统都停机了，运行在系统里的后台工具执行是不是也是失败了呢**」；**写给 agent 的原因是「异常中断」**（见下） |

> **落成「失败」而不是「状态不明」，是有依据的**：[它跑在这个系统里](#65-工具执行有自己的运行时绑定在-session-上)，
> **系统没了它就没了**——不是一个还在别处跑着、将来会回来的东西。
> **登记成「状态不明」会多出第七种收场，而那一种没有任何人知道该拿它怎么办。**

**没有例外。**哪怕能证明它停下时还没来得及在外面做任何事，也按失败算、不重来。
这一层看不全一次执行在外面做过什么——**「它从没开始」要靠这一层给不出的证明**；
而[失败](#55-一次工具执行的收场有六种)的下一步本来就包括重试，
**由 agent 看着情况决定要不要再来一次，不由系统替它断定「那一次没做过」**。

**「停机」的主语是这次执行自己的 runtime。**
**判据是：工具自己的那个 runtime 失去了连续性**——它所在的进程没了、机器换了一台。
这对前台、后台的执行都一样。

**agent 看到的，是恢复时追补的一条消息，原因写「异常中断」：**

| 这次执行停机时 | 恢复时 agent 收到什么 | 前提 |
|---|---|---|
| **在前台** | 那次调用的位置上追补一条**占位的工具返回消息**，原因写「**工具执行异常中断**」 | 日志里登记着这次调用、还没有它的返回消息，**工具执行运行时里也找不到它** |
| **已转后台** | 追补一条**提醒**，说清「**后台工具执行异常中断**」 | 占位的返回消息在，**工具执行运行时里找不到它**，日志里**也没有它结束时回来的那条提醒** |

**两条的收场都是失败，「异常中断」是原因，不是[被中断](#67-用户可以中断而中断不是失败)。**
被中断是有人有意停掉它，agent 不该自己重来；**这里没有任何人叫停**，它是没了——
**要不要再调一次，由 agent 自己决定**，正是失败那一格给它的下一步。

> **前提里的「找不到它」不能省。**光看日志，「还在跑」与「已经没了」长得一样；
> 而协程被回收、执行照跑是天天发生的事（见下）。**找得到就照常接着等，不追补。**
>
> **什么时候对、由谁对**——在 agent runtime 恢复时对账，以及据点恢复时那些没有协程要恢复的会话——
> 归 [PF-012 §5.7](../PF-012-agent-loop-and-run/design.md#先对账再进方程) 与会话、agent runtime 的技术设计。

**agent runtime 被回收，对任何一次工具执行都不是停机。**那是协程计划内的一次停机，
[工具执行从不由它承载](#65-工具执行有自己的运行时绑定在-session-上)：前台的照样跑、照样等，
[协程重建后读 Run 里记的「在等哪一次」接着等](#前台后台说的是-agent-runtime-在不在等它)。

> **会话被归档也不是停机。**不是连续性断了，是会话这一级被**有意收掉**——
> 收场是[被中断](#65-工具执行有自己的运行时绑定在-session-上)，不是失败。

#### 它的宿主是谁，决定了什么会带走它

**宿主只有一个：会话。**前台后台的差别只在 agent runtime 阻不阻塞在它上面，
所以**回收协程与取消一次运行是两件事**，不能混着读：

| 这次工具执行 | 宿主 | **agent runtime 被回收**（计划内停机） | **取消这一次运行** | **[会话被归档](../PF-015-session-lifecycle-and-ownership/design.md#63-归档先停活儿再落状态)** |
|---|---|---|---|---|
| **前台**（agent runtime 阻塞在它上面） | **会话** | **不受影响**，照样跑、照样等 | **跟着停**，落[「被中断」](#67-用户可以中断而中断不是失败)，原因「运行被取消」 | **停**，落「被中断」 |
| **已转后台** | **会话** | **不受影响** | **不停** | **停**，落「被中断」 |

**「取消这一次运行」那一列照 [PF-012 §6.13](../PF-012-agent-loop-and-run/design.md#613-取消跟着宿主走) 的取消语义走**：
取消一次运行，就是不要这一步了——前台那次执行正是这一步在等的东西，所以跟着停；
已转后台的不是这一步在等的，所以不停。**取消不等于回收**：回收只是协程换一副，这一步还在，照样等。

**所以[「被中断」的触发源](#67-用户可以中断而中断不是失败)是这几个**：
用户直接叫停这一次执行（含[插队](../PF-014-inbound-intake-and-queueing/design.md#插队)顺带触发）、
**这一次运行被取消而它还在前台**、**agent 掐掉自己发起的后台执行**、**会话被归档**，
外加一个不来自任何动作、来自设置的：**前台跑到了上限而它不许转后台**（[前台上限](#前台上限与并发上限)）。
**每一个都是有意的停止**——这正是它们都落在被中断、而不落在失败的理由；各自的占位或提醒原因[都不一样](#占位消息一律要说清原因)。

> **这也解释了 [§6.5](#65-工具执行有自己的运行时绑定在-session-上) 为什么非绑会话不可。**
> 挂在 agent runtime 上，协程每回收一次，前台那个跑了两小时的构建就跟着死一次；
> **而回收是计划内的、天天在发生的事**（等人的时候就会回收）。
> 依据见 [UL-D-3](../../ubiquitous_language/decisions.md#ul-d-3--runtime-与活体--2026-09-20)。

### 6.13 MCP 接入点带来的动作

**[MCP](../PF-002-assets-settings-and-permissions/design.md#mcp) 对端的每一个动作，在动作空间里是一个工具条目**——
agent 看到的是一个个可以直接调用的工具，而不是把整个接入点压成一个多命令工具。
这是社区通用的做法，接进来的现成 MCP 服务不必为本系统改造。

| 这些条目 | 怎么定 | 为什么 |
|---|---|---|
| **常不常驻** | **不常驻**，经 [`Tools()`](../PF-007-meta-capabilities/design.md#61-tools通向任意非常驻工具) 发现与调用 | [常驻标记挂在「装配它」那条引用上](#常驻)，而装配引用的是接入点，不是对端的某一个动作 |
| **随谁被持有与授权** | **随接入点**（[PF-002](../PF-002-assets-settings-and-permissions/design.md#mcp)）。一个动作的执行权限，就是这个工具条目的执行权限，配在接入点那份持有上 | 那些动作本身不是资产，没有自己的持有 |
| **有哪些** | **由对端决定**；**每一次[执行尝试](../PF-012-agent-loop-and-run/design.md#执行尝试)开始前**与[可用性](#62-可用性在每次-run-开始前重算)一起重算，**一次尝试之内不变** | 对端今天有明天没有[不是故障](../PF-002-assets-settings-and-permissions/design.md#mcp)；但一次尝试是一段连续的计算，agent 在里面拿着的那份清单不能半路变形。**尝试与尝试之间本来就要[重算可用性](../PF-012-agent-loop-and-run/design.md#每一次尝试开始都要做四件事)**，动作集跟着一起算，不另立一个节奏 |

**动作集在尝试与尝试之间可以变，这不破 [I-4](../PF-004-agent-definition-and-assembly/design.md#61-不变式)。**
I-4 说的是动作空间只由构成决定——装进来的是这个接入点，**它带来哪些动作本来就是它的内容**；
权限变了照样不改动作空间。

**技能不能按能力标识依赖某个 MCP 动作**：那些动作不是资产、没有[能力标识](../PF-002-assets-settings-and-permissions/design.md#63-组合的引用指向能力标识)，
[Skill 也不组合 MCP](../PF-002-assets-settings-and-permissions/design.md#谁能组合谁)。
一份技能要那个对端在场，它声明的是一项**外部服务**。

#### 接入点连不上，它的动作就是不可用

**一次尝试开始前接入点连不上，它带来的每一个动作都算[不可用](#可用性)，原位装[同名替换件](#63-不可用时装的是同名替换件不是不装)**，
说明「接入点连不上」。和任何一个依赖不满足的工具一样，**这不是另一条规则**。

**替换件替的是最近一次拿到的那份动作清单**——连不上就拿不到这一次的，
而替换件要与原件同形，只有上一次的清单说得出原件长什么样。
代价是那份清单可能已经过时：某个动作对端其实已经删了，agent 看到的替换件仍在；
**等接入点连上，下一次尝试开始前清单照常重取，多出来的自然消失**。

## 七、取舍

| 选择 | 取的 | 舍的 |
|---|---|---|
| **两种定义范式**（单函数 / 多命令），而不是只留一种 | 一族动作压进一个槽位；简单工具不必套壳 | 工具作者多一个选择要做；读工具定义的人要先分清这是哪一种 |
| **多命令工具在模型面前只有一种样子：紧凑的命令清单**；作者带的完整参数只用来校验与答用法，不进模型面前 | 一族动作一个槽位，**而且紧凑**——命令再多，模型面前也只是一行一个 | **agent 对不熟的命令，动手前总要先问一次详细用法**，多一趟往返；作者把参数写得再全，模型面前也看不到 |
| **多命令工具带不带各命令的完整参数，由作者定** | 值不值得为每个命令把参数写全，只有作者知道 | 不带的，系统校验不了交上来的参数，`inspect` 也答不出细节——**同类工具问得到的详细程度不一** |
| **工具说明与每个参数的说明必填** | 拼得出各家模型供应商要的那一份；模型不必对着参数名猜 | 作者多写一些字；**缺一处说明的定义就不完整** |
| **`help` 是多命令工具可选的一个命令空间**，不强制；`Tools().inspect` 对两种范式都管用 | 作者可以让工具自己讲清用法，带着 `help` 迁移过来的工具不必改 | 同一件事可能有两处说法，**带了就得与 `inspect` 说得一致**，不一致是缺陷 |
| **两种返回写法，进系统前统一成一种** | 小工具三行就能写；系统内部只有一种形状要处理 | 两种写法**能力不对等**（只有结构化的那种能带卸载与附件），作者得知道这件事 |
| **每次执行都留一份账，但账不进上下文** | 查得清是谁在拖后腿，又不占 agent 的预算 | 账的消费方（诊断、计量）要另有入口，本 topic 不提供 |
| **产出分成「进消息的」与「附件」两部分** | 大产出不必硬塞进对话；agent 按需去取 | 多一个存储依赖要声明、要算可用性，且**读得出来**才算数 |
| **给工具一个发帧的原语**，让它能播报自己跑到哪了 | 用户不必对着「正在调用某工具」干等，分得出卡住和慢活 | 工具作者多一件事要想；**发多了反而是噪音**，而系统不替他把关 |
| **帧不在定义里声明，系统按实际收到什么解析** | 省掉「声明」与「核对声明」两层，且工具可以在同一次执行里换着发 | **丢掉了一层早期校验**——工具发出不合协议的东西，只能在收到那一刻才发现 |
| **结果太大时卸载而不是截断** | **原始结果没丢**，agent 要看全的能分页取回 | 多一条占位提示要设计，且 agent 得学会「这里有东西没展开」 |
| **不可用时装同名替换件**，而不是不装 | 动作空间形状恒定，agent 能绕路，用户查得出原因 | 系统里会存在一批"占着位置但不干活"的东西，实现上要处理它们 |
| **可用性每次 run 前重算**，而不是装配时算一次 | 环境变化能及时反映；不会拿着过期的判断去调用 | 每次 run 都有一次解析开销；agent 得承受"上轮能用这轮不能"的波动 |
| **常驻标记挂在引用上**，而不是资产属性 | 上下文预算归装配方管，工具作者不必猜 | 同一个工具在不同 agent 里长相不同，排查时要先问"在谁的清单里" |
| **常驻只管看不看得见，看见什么归装配策略** | 技能与工具各按最合适的方式呈现，工具随各家模型的习惯渲染 | 同一个常驻工具在不同模型面前长相不同，排查时还要问「这次用的是哪家」 |
| **agent definition 压 plugin** | 预算的最终决定权在装配方 | plugin 作者的意图可能被推翻，他得接受这一点 |
| **工具执行绑 session、不绑 run** | 长任务可以跨轮存活，结果不会因为一轮结束就丢 | 多了一层归属关系要维护；会话归档时要有收场逻辑 |
| **工具执行从不由 agent runtime 承载**；前台 / 后台只说协程阻不阻塞在它上面 | 协程随时可以回收重建（等人时就回收），**任何一次工具执行都不受牵连**，`Ask()` 的卡也不会成孤儿 | Run 得记下「agent runtime 在等哪一次执行」，协程重建后才接得上；**回收与取消要分开读** |
| **MCP 接入点连不上 = 它的动作不可用**，沿用上一次的清单装替换件 | 与所有工具同一条规则；agent 看得到平时有的动作、知道它们现在用不了 | 那份清单可能过时，替换件可能替一个对端已经删掉的动作，直到下一次连上 |
| **停了不重来，不设「可证明从未开始」的例外** | 只有一条规则；系统从不替 agent 断定「那一次没做过」 | 真没开始的那一次也记失败，**要不要再来由 agent 决定**，多一次往返 |
| **停机时没了的执行，收场落失败、原因写「异常中断」**，而不是落被中断或新增一种收场 | 收场仍是六种；agent 读到的下一步（自己判断要不要再调）与裁决一致 | 「异常中断」与「被中断」字面相近，**读的人得分清哪个是原因、哪个是收场** |
| **MCP 对端每个动作一个工具条目** | 与社区通用做法一致，现成的 MCP 服务接进来不必改 | 对端动作多，`Tools()` 里的条目就多；动作集随对端在尝试与尝试之间变 |
| **六种收场都用正常返回**，不用报错 | agent 拿得到语义，下一步做得对 | 返回消息的形态变多，读的人要能分清 |
| **前后台与等待态解耦** | 四种组合都能表达，人在回路与长任务互不干扰 | 比"一个状态机"复杂；要说清楚两个维度各自的含义 |
| **本版要等应答的执行只在前台等**，模型不改 | 少一种组合要兑现；结果怎么到达仍按「有没有占位」判断，将来打开不改 | 一个要等人的执行，本版不能扔到后台让 agent 先干别的 |
| **前台上限到点，不许后台的落被中断，不落失败** | agent 不会去重试一次必然再撞上同一个界的执行 | 真是工具卡住了的那种，agent 也不会自动再试——要不要再来，它得读原因自己判断 |
| **依赖声明只有[一串必需项的抽象名字](#只有且只有必需)**，不表达「或」与「可选」 | 解析只有一条规则：每项都有提供者就可用，缺一项就不可用。**没有第三态，也没有第二套语义** | 作者得想清楚自己到底非要什么：「甲或乙」要先给它们一个共同的名字，可有可无的东西得改成用时现探 |
| **本版不定等待上限、不定设施清单** | 不为想象中的政策预埋结构 | 真要用时还得再定一次 |
