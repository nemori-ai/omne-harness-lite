## rev 12 — 2026-09-22

**两条裁决落正文：[依赖声明](design.md#依赖)是一串必需项的抽象名字；
[资产禁用](../PF-002-assets-settings-and-permissions/design.md#64-移除与禁用是两个动作)对 agent 是不可见，与本 topic 的「不可用」不是一回事。**
依据：[产品负责人 2026-09-22 的两条裁决](decisions.md#一拍板记录)。

### 一、依赖声明：一串名字，只有且，只有必需

此前 [§4](design.md#依赖) 写「依赖项有**三类**」，而 [§5.3](design.md#六项可选声明) 说两端的模态声明
「也是依赖声明的一种」、[§6.4](design.md#64-依赖声明与解析) 另有一项「附件放进哪个存储」——**三类并不穷尽**。
现在正文这样说：

| 位置 | 现在怎么说 |
|---|---|
| [§4 依赖](design.md#依赖) | 依赖声明是**一串必需项的名字**。每一项指一样**可以在场也可以不在场**的东西，**用抽象的名字指，不指具体资产**；**谁生效在那个名字上，谁就满足它**。表改成**例子**性质，并补上**存储**与**有效模型的模态能力**两行，明写「**这张表是例子，不是外延**」 |
| [§4 只有且，只有必需](design.md#只有且只有必需) | **没有「或」**——它被抽象的名字消掉了（技能依赖「读文件」这个能力标识，不是某一份工具；同一个名字底下可以有不止一个候选提供者）。**没有「可选」**——可有可无的东西**用的时候现探**，写进声明反倒把本来能用的判死 |
| [§4 可用性](design.md#可用性) | 补上成立与重算的规则：**每一项都有在场且可用的提供者 → 可用；缺一项 → 不可用；提供者换了或没了 → 重算** |
| [§5.3](design.md#六项可选声明) | 「中间那两项是依赖声明的一种」改为**前五项进的都是同一串清单**，只是名字分几类；两端的差别改述为**候选提供者不同** |
| [§6.4](design.md#64-依赖声明与解析) | 「技能声明工具之间的且、或、必需、可选」改为**用能力标识指**；解析规则收成一句话；「可选依赖不满足不导致不可用」改为**没有「部分可用」**，因为声明里本来就只有必需项。**存储那一项**的措辞对齐：「有工具读得出它」是**这一项**成立的条件 |
| [§6.11](design.md#两端的差别在候选提供者不在规则) | 「两端不对称」改为**两端的差别在候选提供者，不在规则**：调用端「模型给得出这种模态」**只有有效模型满足得了**；结果端「这种模态的结果能被模型收下」**由有效模型的输入能力或[转换件](../PF-013-model-profiles-and-invocation/design.md#转换件)满足**。**「结果降级」不是另一条规则**，只是这一项被转换件满足了；两者都没有才不可用 |
| [§2 非目标](design.md#非目标)、[§7 取舍](design.md#七取舍) | 「产品只定要能表达且、或、必需、可选」相应改写；取舍那一行的收益改成「**解析只有一条规则，没有第三态**」，代价改成「作者得想清楚自己到底非要什么」 |
| [flows](flows.md)、[acceptance](acceptance.md) | 「A 或 B 只装 A 判可用」「可选依赖不满足判可用」这两类场景**全部改写**：换成**换掉某个能力标识下的提供者仍可用**、**没写进声明的东西不在仍可用**、**缺声明里任意一项即不可用**，并补上两端模态各自的三条。flows 的装配步骤 2–3 与「没有第三态」那段、acceptance 的不验收表相应对齐 |

**「三类」这个说法作废**，[C-18 就此闭合](../../ubiquitous_language/conflicts.md#现有冲突)。

### 二、禁用是不可见，不可用是可见但用了一定失败

[§6.3](design.md#63-不可用时装的是同名替换件不是不装) 那张「移除 / 禁用 / 依赖不满足」的三行表，
收成 **agent 只会遇到的两种情形**：

| agent 遇到的 | 什么造成的 | 动作空间 | 它的感受 |
|---|---|---|---|
| **不可见** | 移除、**禁用** | 变小 | 不知道有过这回事 |
| **可见但用了一定失败** | 依赖不满足 | 不变 | 知道有、知道现在用不了、知道缺什么 |

**「禁用 = 动作空间不变、知道有、知道被禁」那一行作废**——
禁用现在[在装配第一步就被滤掉](../PF-002-assets-settings-and-permissions/design.md#56-四步资产求值--组装--投影--层级计算)。
**本 topic 管的只有第二种**，而这条界线要守住：塌成一种，agent 就分不清「我没有这个能力」和「我有，但现在使不了」。

### 三、下游要复核

- **[§5.5 六种收场](design.md#55-一次工具执行的收场有六种)没有增减**，[三层正交](design.md#51-三层正交)没有变化，
  [替换件](design.md#替换件)与装配的说法照旧——rev 11 刚定的那两条一个字没动。
- **[PF-013 §5.10](../PF-013-model-profiles-and-invocation/design.md#510-合法目标集合与展示列表是两件事)** 那张同形的表讲的是模型档案的展示列表，
  四行分别是移除 / 已下架 / 模态对不上 / 范围没配凭据。**「移除」那一行本来就是「不再持有 → 不知道有过这回事」，与新说法一致，未改**；
  另三行讲的都是「看得见、选不了或用不了」，落在第二种情形里。
- **统一语言**：[UL-dependency-declaration](../../ubiquitous_language/terms/reach-and-availability.md#ul-dependency-declaration--依赖声明--dependency-declaration) 定义按此重写、删掉「三类还没有定论」那段，
  [UL-current-availability](../../ubiquitous_language/terms/reach-and-availability.md#ul-current-availability--当下可用性--current-availability) 的「别混：与资产禁用不同」按**禁用不可见、不可用可见但必败**改写。
- 照 rev 11 做过的判断，**除了「依赖的外延」与「禁用落在哪一侧」这两个问题，全部继续成立**。

## rev 11 — 2026-09-22

**一条裁决落正文：替换件到底是什么形状、被调用时会怎样。只有两节变了。**

### 一、它与原件同形，只换说明

此前正文只说它「同名、占同样的位置」，**没说同到什么程度**，
于是它是「另一个东西」还是「同一个条目的另一副面孔」一直悬着。
产品负责人 2026-09-22 裁决：**它是与原件同形的一种实例**——
工具的名字与调用参数一致，技能的名字一致，**只有说明换成「现在用不了以及为什么」**。
[§4 替换件](design.md#替换件)与 [§6.3](design.md#63-不可用时装的是同名替换件不是不装) 已补齐。

**为什么非同形不可**：换说明是为了让 agent 提前知道；
可形状但凡差一点，agent 连「这东西本来能怎么用」都看不出来，
[动作空间形状恒定](design.md#63-不可用时装的是同名替换件不是不装)也就落空了。

### 二、调用它必定得到「不可用」

说明是给模型看的，**不是一道闸**——agent 照样可能去调。
所以替换件**只有一种行为**：不论怎么调、带什么参数，都走到
[六种收场里的「不可用」](design.md#55-一次工具执行的收场有六种)那一种，带上原因，
**正常返回，不走报错**。

**怎么把它做出来**（包一层，还是换一份装进去）**是开发关心的事**，不进产品正文。

### 三、下游要复核

**只有 [§4 替换件](design.md#替换件)与 [§6.3](design.md#63-不可用时装的是同名替换件不是不装) 变了。**
其余各节与 flows、acceptance 一个字没改：**六种收场没有增减**，
**三层正交没有变化**，依赖解析与装配的说法照旧。
照 rev 10 做过的判断，除了「替换件是不是一个独立的东西」这一个问题，全部继续成立。

**统一语言那边跟着定了**：[UL-stand-in](../../ubiquitous_language/terms/reach-and-availability.md#ul-stand-in--替换件--stand-in)
的形态由「未定」定为**视图**——身份仍是原条目的，说明与应答都从依赖解析的原因算出来，
丢了能原样重算。[C-16 就此闭合](../../ubiquitous_language/conflicts.md#现有冲突)，
[形态取值表](../../ubiquitous_language/conventions.md#形态这个词指的是哪一类东西)**不增补「替身」这一类取值**；
[领域对象那边的同名待裁项](../../domain_objects/pending.md)随之删除。

## rev 8 — 2026-09-20

**工具域这一层在四个域的联合修订里被补齐。**四件事，**六种收场一格未动**。

### 一、工具定义多了两项可选声明：两端各要什么模态

**产品负责人 2026-09-20 的裁决：**

> **两者的定义和声明要包含多模态支持能力的声明**——模型声明自己支持的输入模态和输出模态，
> **工具声明自己的 input schema 需要的模型输出模态的支持，
> 以及 tool result 需要的模型输入模态的支持**。

| 哪一端 | 声明什么 | 不声明是什么意思 |
|---|---|---|
| **调用它的时候** | 模型要**给得出**参数里那些[模态](../PF-013-model-profiles-and-invocation/design.md#模态) | 只要文本——**所有模型都给得出** |
| **结果回来的时候** | 模型要**收得下**结果里那些模态 | 只有文本 |

**两项都是[依赖声明](design.md#依赖)的一种**——依赖的不是外部服务，
是**这一次[有效模型](../PF-013-model-profiles-and-invocation/design.md#选中模型-与-有效模型)的能力**，
所以走[可用性已有的那一套](design.md#62-可用性在每次-run-开始前重算)，**不另造机制**。

**[但两端不对称，这是本版最要紧的一条](design.md#611-工具两端各要什么模态)：**

| 哪一端 | 模型不满足时 | 为什么 |
|---|---|---|
| 调用它那一端 | **工具不可用** | **没有兜底**——模型吐不出那种东西，这次调用**压根构造不出来** |
| 结果那一端 | **照样可用，结果降级** | **有兜底**——[转换件把那个块转成文本](../PF-013-model-profiles-and-invocation/design.md#转换件)；转不出来才算不可用 |

> **两端做成同一条规则会怎样**：都放行，模型吐不出图时**每次调用都构造失败**；
> 都严格，**转换件白装了**——一个截图工具在纯文本模型下永远不可用，
> 而它明明能把截图说成一段文字。

### 二、非常态的边界落在六种收场上

**产品负责人给的分法**：**能自行了结的要穷举情形，了结不了的作为异常上交、不必穷举。**

> **这一层的那条线，正好就是[那张六种收场表](design.md#这张表同时划出了这一层的非常态边界)**——
> **六种是穷举的**，各以一条带语义的工具返回消息到达 agent，**不上交**；
> **其余全部上交**，不必穷举。

**没有新增任何收场**，只是把这张表**原本就承担的那个角色写出来**。

### 三、工具执行的运行时可以被单独控制，而它停了不重来

**[§6.12 新增](design.md#612-工具执行的运行时可以被单独控制而它停了就不重来)：**

- **「单独」是硬的**：动一次工具执行，**不动这一次模型调用，也不动这个 run**。
  [插队正压在这一条上](../PF-014-inbound-intake-and-queueing/design.md#53-插队的核心原则)——
  只有一个「全停」按钮的话，**已经跑完的那两个工具调用的结果会一起没了**。
- **停机之后不重来**，[落成失败](design.md#55-一次工具执行的收场有六种)。
  **它与 run 不同**：run [重新算一遍就是了](../PF-012-agent-loop-and-run/design.md#57-一次尝试三条路通向重新算一遍)，
  **而一次工具执行可能已经在外面做了事，重来就是做第二遍**。
  依据是[产品负责人 2026-09-17 的裁决](../PF-012-agent-loop-and-run/decisions.md#一拍板记录)，
  **本版只是把它写进本 topic 自己的正文**。
- **「停机」的判据**：**这个运行时与它所服务的那个会话失去了连续性**——
  进程没了、实例被回收、机器换了一台，**在这一层眼里是同一件事**。

### 四、两笔回补：转后台多一个触发源，占位原因多三种

**[PF-014](../PF-014-inbound-intake-and-queueing/README.md) 起草时记下来的账。**

| 回补 | 内容 |
|---|---|
| **[转后台的第三个触发源](design.md#66-前台后台-与-等待态是两个维度)** | **用户插队，而这个工具声明了允许**。**照样不绕开声明**——没声明的，插队时它被中断 |
| **[占位原因多三种](design.md#占位消息一律要说清原因)** | 「**因插队转后台**」「**因插队被中断**」「**人拒绝回复**」。**它们是新的取值，不是新的收场**——仍然落在转后台与被中断那两格上 |

### 下游要复核

- **任何按「四项可选声明」枚举**工具定义的东西——**现在是六项**；
- **任何按「可用性只看依赖与执行环境」实现的重算**——**现在还要看这一次的模型给得出/收得下什么**；
- **任何把停机时在跑的工具执行记成「状态不明」**的实现——**它落「失败」**；
- **任何只按「用户手动」一种触发源实现转后台**的东西。

## rev 7 — 2026-09-18

**工具跟外面通信的原语从一个变成两个**，且**一次执行的产出从两部分变成三部分**。

起因是 [PF-009](../PF-009-context-message-types/README.md) 在设计工具帧时
掉出来的一个问题：帧要从工具内部发出来，**而工具手上没有发东西的原语**。
产品负责人据此提出补一个发帧原语，并授权升 rev 顺带补上产出那笔欠账。

### 一、§4 立起「两个原语」这个说法

**等待态不再是孤零零的一节**，它和发帧并排，**而这层并排本身就是内容**：

| | **等待态** | **发帧** |
|---|---|---|
| 方向 | **要**东西进来 | **给**东西出去 |
| 阻不阻塞 | **阻塞** | **不阻塞** |
| 落空了 | 「等不到应答」是六种收场之一 | **什么也不算** |
| 系统要不要知道 | **必须知道** | 不必 |

> **等待是执行的一部分，发帧不是。**

由此点破一条必须写进正文的规矩：**工具不能因为「说不出话」而执行失败**。

### 二、产出补上第三部分

rev 6 之前「工具的产出」只讲了**跑完时**交出的两部分（进消息的 / 附件）。
现在补上**跑的过程中**那一部分——帧。

**三部分里，第三部分的读者换了个人**：前两部分给 agent，**帧给人**。
由此掉出一条工具作者迟早会踩的规矩：

> **帧不顶替结果。**播报得再细，**agent 一帧都看不见**——
> 跑完照样得给结果，否则等于什么都没给它。

### 三、帧不在定义里声明——这一条推翻了 PM 的判断

PM 原本主张「帧要在定义里声明它是日志型还是进度型」。**产品负责人纠正：**

> **帧不需要在定义里面声明，通过数据结构的协议来约定就可以。**
> 系统对帧的解析是统一的，**它不根据工具定义判断要不要解析帧，
> 而是根据实际收没收到、收到的是什么来决定解析策略。**

**于是「不在定义里的两样」变成了三样**（等待态、发帧、要不要卸载）。

**发帧的理由与另外两样不同**：等待态与卸载不在定义里，是因为它们**取决于这一次跑成什么样**；
发帧多一层更硬的理由——**就算某个工具真的每次都发帧，那一格也不会被读一次**。

> **一格从不被读的声明，不是可选项，是废字段。**

**代价认在 [§7 取舍](design.md#七取舍)里**：没有声明，就没有「声明与行为不符」这种错可抓，
不合协议的帧只能在收到那一刻才发现。换来的是省掉两层，
以及**一个工具可以先吐日志、最后给一块汇总面板**——**预先声明会把这条路堵死**。

### 四、这一版没动的

**四项可选声明仍然是四项。**发帧没有变成第五项——**这正是上一节那条裁决的直接后果**。

### 下游要复核

- 任何在工具定义里给「帧」留了一格的实现；
- 任何按「先查工具定义，再决定要不要解析帧」写的分派逻辑；
- 任何让「发帧失败」影响这次执行成败的实现。

**帧出了工具这道门之后的事**——落成哪一种消息、给谁看、怎么增量更新——
归 [PF-009](../PF-009-context-message-types/README.md)，本 topic 不定。

## rev 6 — 2026-09-18

**补上 rev 5 自己留下的那个缺口：没声明能不能后台时，算哪种。**

> **不声明就是不能后台。**

rev 5 写的是「工具定义**可以**声明能不能在后台执行」，**却没说不声明算什么**。
下游实现只能自己猜，而两种猜法的后果相反。

**默认往保守的那一边倒**，与[执行环境不许降级满足](design.md#68-工具怎么提执行环境的要求)同一条理由：

> **没表过态，不等于表了同意。**

转后台**改变的是这次执行的语义**——run 不再等它，结果换个时候以提醒的形式回来。
一个从没想过这件事的工具，**它的代码里可能压根没准备好在那种时序下被使用**。
而默认放宽的代价是**静默的**：没人收到报错，只会偶尔看到一个工具在不该异步的地方异步了，
**排查时所有人都会先怀疑别处**。

**顺带明确一条**：用户手动切后台，**前提仍然是这个工具声明了允许**。

> **人可以决定「现在切」，但不能决定「它能不能切」。**

### 由此点破了四项声明的一处不对称

**「不声明」的含义，四项并不一样：**

| | 声明的是 | 不声明的意思 |
|---|---|---|
| 外部服务 / 存储 / 执行环境 | **我需要什么** | 不需要——**少一个前提，反而更容易可用** |
| **能不能后台** | **我允许什么** | **不允许** |

不点破这层差别，会有人把「四项都可选」理解成「四项都是不填就宽松」，
**而第四项恰恰相反**。

**下游要复核**：任何把「没声明」当成「可以后台」的实现；
以及任何允许用户手动把未声明工具切到后台的实现。

## rev 5 — 2026-09-18

**把工具定义、返回值、特性声明集中到一处。**产品负责人给出了此前从未落过盘的
两块内容——**定义有几种范式**、**返回值有几种写法**——并要求「集中来写」。

### 新增 §5.3：一份工具定义长什么样

**两种范式，工具作者挑一种：**

| | 形状 | 适合什么 |
|---|---|---|
| **单函数** | 没有命令，全是参数 | 一个工具就干一件事 |
| **多命令** | 先选命令，再给那个命令的参数 | 一个工具是**一族相关的动作** |

> **多命令范式把「一族动作」压进一个槽位。**

[十三扇门那些常驻工具](../PF-007-meta-capabilities/design.md#54-十三个槽位是预算的地板也是它的天花板意义)
全是这个形状——换成单函数范式，`Tools()` 的每个命令都得立成独立工具，
**一族动作吃掉一族槽位**。

**四项可选声明**（依赖的外部服务 / 存储 / 执行环境 / 后台执行）在这一节集中列出，
**规则仍归 §6.4、§6.6、§6.8**——这一节答「我作为工具作者要写什么」，
那几节答「系统拿到之后怎么处理」。

**另外两处判断：**

- **多命令工具的定义里带多少，归工具作者定**——只带命令清单则定义小但要多问一次，
  带全部参数则一次到位但吃预算。**系统不替他选，也不搞折中。**
- **不给多命令工具配自带的 `help`**，统一走 `Tools().inspect`。
  **这是一处有意偏离 legacy**：留两条路就多一处会和 `inspect` 说得不一样的地方。

### 新增 §5.4：返回值两种写法，一种模型

| 写法 | 系统怎么用 |
|---|---|
| 按普通函数那样返回 | **整个返回值当字符串用** |
| 返回一个 `ToolResult` | 按字段分别处理：**进消息的内容** / （可选）**要卸载的原始结果** / （可选）**附件地址** |

> **普通返回在上报时被转成 `ToolResult`——工具作者的方便，不传染给系统。**

因此 [agent-loop](../PF-012-agent-loop-and-run/README.md) 那边**只有一种形状要处理**。

**每一次执行都留一份账**：一次工具执行是一个有头有尾、可单独记账的事，
完成时连结果一起上报的还有跑了多久、耗了多少计算这类事实。
**这份账不进 agent 的上下文**——agent 拿 cpu 时间做不出任何判断。

### 一处纠正：等待态不是定义时的声明

rev 4 的 §6.11 把「等待态要什么形状的应答」列成了工具定义的一项声明。**那是错的。**

> **等待态是工具函数逻辑里用得上的一个原语，不是定义里的一格。**

工具定义里没有「我会不会等」——**等不等是这一次跑出来的事**，
同一个工具，参数不同就可能这次等、下次不等。§4 的措辞已一并改掉。

**下游要复核**：任何在工具定义里给等待态留了字段的实现。

### §6.11 被删掉，并进 §5.3

rev 4 加那节索引，是因为当时声明项散在六处却没有正文落点。
**rev 5 有了正文落点，索引再留着就是第二份会漂移的权威。**

### 编号变动

**「一次工具执行的收场，有六种」从 §5.3 挪到 §5.5。**内容一字未改，
跨 topic 的引用已全部更新（PF-007、PF-008、PF-012）。

## rev 4 — 2026-09-18

**补一块此前漏掉的需求：工具的产出。**产品负责人在设计 agent-loop 时想起
这块本该在工具这里提，因此回补。

### 产出分两部分

| 部分 | 去哪 |
|---|---|
| **进消息的那部分** | 直接进对话 |
| **附件** | 存进某个存储；**消息里给地址，agent 自己去取** |

有些产出根本不适合进对话——一张图、一个几十兆的文件。硬塞进去，
**一条消息就把上下文吃光了**。

**由此多出一个可用性场景**（§6.4）：

> **光能写进去不够，还得有工具能把它读出来。**

产出了附件却没人读得回来，那个附件**等于不存在**——
而 agent 会拿着一个地址反复尝试，**永远取不到，且它不知道为什么**。
所以「产出附件的工具可不可用」要**连同「读取那个存储的工具在不在」一起算**。

### 结果太大就卸载（§6.10）

原始结果存起来，消息里换成**一条占位**：够用的那部分 + 有多大 + 怎么取全文；
要看全的走 [`Tools().read_result`](../PF-007-meta-capabilities/design.md#61-tools通向任意非常驻工具) 分页取回。

> **卸载不是丢弃，也不只是留个地址。**

**两条来路，产物不同：**

| 来路 | 谁决定 | 占位里留下的是 |
|---|---|---|
| **工具自己声明** | 工具开发者——返回一个约定格式的结构 | **他自己构建的摘要** |
| **系统兜底** | 系统发现**单条工具消息超了限额** | **首尾保留**的机械截断 |

> **系统不替工具开发者写摘要。**
> 猜出来的摘要比机械截断更危险——**因为它看上去是有意义的**。

机械截断诚实：agent 一眼看得出中间缺了一段。而一份臆造的摘要，
它会当成完整转述用下去，**而它不知道自己漏了什么**。

**判断要不要卸载、以及执行卸载这个动作，都是
[agent-loop](../PF-012-agent-loop-and-run/README.md) 里的逻辑**——
本 topic 定的是**卸载这件事的产品语义**，谁在什么时候执行它归那边。

占位还必须让 agent 分得出「结果被卸载了」与「工具没返回什么」——
写得像「没有结果」，它会重来一次，**而重来得到的还是一条占位**。

### 三个正交维度

| 维度 | 问的是什么 |
|---|---|
| 前台 / 后台 | 这次执行，**run 等不等它** |
| 等待态 | 这次执行，**中途要不要停下来等外部输入** |
| **卸载** | 这次执行**的结果**，**进不进得了消息** |

**两两正交。**写明这一条是为了挡住「结果大就转后台」那种耦合——

> **结果有多大，与它该不该占着 run，毫无关系。**

**下游要复核**：任何把结果大小与执行姿态绑在一起的实现，以及任何把卸载
做成截断的实现。

### 顺带补的一节索引（§6.11）

这一版添了两项声明（附件存储、卸载）之后，发现**工具定义的声明项已经散在六处**，
工具作者要知道「我能声明什么」得翻遍全文。补了一节 **§6.11 做索引**——
只列「声明什么 / 归哪一节 / 不被满足会怎样」，**语义仍归各节，不在那里重讲**。

**它不改任何已定的含义**，但顺带划出一条之前没写过的界线：

> **上表六项全在定义里，一次定死；卸载走的是每次返回值里的标记。**

因为「必须跑在沙箱里」是工具的固有属性，而「这次该不该卸载」取决于**这次跑出来多大**。

**下游要复核**：把卸载标记设计成工具定义里的静态字段的实现——那是错的一侧。

## rev 3 — 2026-09-17

**一条推过头的推导被修正。**

rev 1/2 写的是「**等待态等不到应答要有上限**，到头按第六种收场」。
那条的理由是「一次执行不能永远占着资源等一个不会来的应答」——
**这个理由只对占着东西的等待成立。**

改为：**要不要设上限，不是这个原语的属性，是每一个使用它的人的属性。**
判据只有一条——**这个等待占不占着东西**：

| 占着资源的等待 | 可以设上限，到头按第六种收场 |
|---|---|
| **什么都不占的等待** | **不该设。**不花钱的等待没有理由到点 |

**[PF-007 的 `Ask()` 落在第二行](../PF-007-meta-capabilities/design.md#611-ask通向人)**：
它的等待发生在动手之前，世界里什么都没发生。一旦设了上限，
就必须规定「到点算什么」——**那是系统替人签字**。

**「等不到应答」这个收场本身不作废**，对第一类等待仍然成立；
[六种收场](design.md#55-一次工具执行的收场有六种)一个不少。

**下游要复核**：任何给不占资源的等待（尤其是 `Ask()`）加了超时的实现，全部作废。

**这笔账的来源**：[PF-007 rev 2](../PF-007-meta-capabilities/changelog.md) 在设计
`Ask()` 时发现并报告，产品负责人授权回改。

## rev 2 — 2026-09-17

**两处修订，都是被 [PF-007](../PF-007-meta-capabilities/README.md) 落下来之后倒逼的。**

| | rev 1 | rev 2 |
|---|---|---|
| 恒定占槽位的有几个 | **「只有能力发现与取用的两个入口」** | **一批**——[PF-007 定义的 **meta**](../PF-007-meta-capabilities/design.md#meta)，共十三扇门（**rev 2 当时是十二扇，`Engram()` 于 PF-007 rev 5 补入**），那两个入口只是其中之二 |
| 谁要声明执行环境需求 | **工具** | **工具，以及带脚本的技能** |

### 为什么改第一处

rev 1 那句话写在 PF-007 存在之前，**当时只知道那两个**。
照字面实现会只留两扇门，另外十扇无处安放。

改法是**把「有哪些」让给 PF-007**，本 topic 只保留它需要的那一件事：
**有这么一批，且关不掉**。顺带引入了 PF-007 给出的更深的理由——
**meta 必定常驻不是产品选择，是结构逼出来的**。

### 为什么改第二处

[PF-002 已经定了](../PF-002-assets-settings-and-permissions/design.md#八类资产)
skill **可以带可执行的脚本**，而 [PF-007 §6.2](../PF-007-meta-capabilities/design.md#62-skills通向任意技能)
给了跑脚本的入口。**脚本要跑就要落地**，就得知道它要什么样的环境——
rev 1 只写了工具能声明，技能没地方说，**只能靠猜或者默认塞给宿主机，
而后者直接绕过安全判断**。

### 下游要复核什么

- **「恒定占槽位的有两个」这句话作废**，改看 PF-007。
- **带脚本的技能同样要声明设施需求**，不能默认给宿主机。
- 本 topic 的 `depends-on` 增加了 PF-007。

## rev 1 — 2026-09-17

**首版。**补上 [PF-002](../PF-002-assets-settings-and-permissions/README.md)
与 [PF-004](../PF-004-agent-definition-and-assembly/README.md) 之间那段空白：
**一份定义怎么变成 agent 真的能用的动作。**

### 这一版确定了什么

| 方面 | 结论 |
|---|---|
| 最要紧的一句 | **能做什么 / 怎么够得着 / 现在做不做得了，是三件事，正交** |
| 动作空间 | 由构成决定，[I-4](../PF-004-agent-definition-and-assembly/design.md#61-不变式) 不变 |
| 呈现方式 | **常驻标记**决定。标记挂在**「装配它」这条引用**上，不在工具自身 |
| 谁压谁 | **agent definition 压 plugin**——上下文预算是装配方的问题 |
| 自举点 | **能力发现与取用的入口必须是常驻**，否则整套机制转不起来 |
| 非常驻的工具 | **不进槽位**，经取用入口**发现并执行**；全程 **system prompt 不变** |
| 技能的取用 | 取回正文作为这一次的返回内容，**不产生「已激活」状态** |
| 由此得到 | **系统提示词的成分在运行实例存续期内恒定** |
| 依赖 | 三类：其他工具、外部服务、执行环境的**设施**。要能表达**且 / 或 / 必需 / 可选** |
| 可用性 | 依赖解析的结果，**每次 run 开始前重算** |
| 不可用怎么办 | **装同名替换件，不是不装**。形状恒定，agent 知道缺什么 |
| 工具执行 | 有自己的运行时；**绑 session，不绑 run、不绑运行实例** |
| 收场 | **六种**：完成 / 失败 / 不可用 / 转后台 / 被中断 / 等不到应答 |
| 前后台与等待态 | **两个维度，解耦**，四种组合都成立 |
| agent 造工具 | 三条最小必要：**要授权**、**是资产且归属算得出**、**当场能用但不改 definition** |

### 「数据 vs 计算资源」的第四次出现

| | 数据（活得久） | 计算资源（可随时换） | 计算资源挂在谁身上 |
|---|---|---|---|
| PF-004 | Agent Definition | 运行实例 | — |
| PF-004 | 会话历史 | 运行实例 | — |
| PF-005 | 租户级沙箱内的数据 | 沙箱本体 | — |
| **本 topic** | **Tool Definition** | **Tool Execution** | **Session**（不是运行实例） |

**前三次的计算资源都挂在运行实例上，这次换了宿主。**正因如此，
一次 run 结束了它发起的执行还能继续，结果照样回得到那个 session。

### 下游要注意的六处

- **不可用绝不能实现成「不装」。**动作空间会随环境波动变形，I-4 当场作废，
  而且用户查不出东西为什么没了。
- **取用技能、调用非常驻工具，绝不能改 system prompt。**成分一旦变成运行期可变的，
  [PF-004 §5.4](../PF-004-agent-definition-and-assembly/design.md#54-为什么系统提示词必须落在第三列) 那一条就废了。
- **六种收场都要以正常返回到达 agent**，一种都不能用异常。异常不带语义，它只能猜。
  尤其是**中断**——当成失败递过去，agent 会重试用户刚刚叫停的东西。
- **执行环境要求满足不了时，不许降级给一个不满足的。**工具作者声明要隔离，
  是因为他判断这东西不安全。
- **工具执行不能绑在 run 上。**绑了，长任务一到轮次边界就死。
- **agent 造出来的东西是资产，归属由运行时注入的租户上下文算出**，
  不需要为它另加一套归属机制。

### 本版刻意不做的

`Skills()` 与 `Tools()` 的**具体设计**（归 PF-007）、agent **怎么**创建编辑装载
（归后续 topic）、**从外部获取**尚未持有的资产、依赖表达式的语法、
等待态的上限、设施清单、提醒的送达机制。

前两项是明确划给别处的，其余是「先做最小的正确模型」——
现在定，下一个用例就得改产品文档。

### 本版留下的缺口

- **未决项：无。**
- **待裁决：无。**
- 一处**需要上游配合修订**的事项已报告：**PF-004 的「构成变了就重建实例」
  需要精化为「definition 变了才重建」**。本 topic 不擅自改写上游正文，
  见 [decisions.md 第四节](decisions.md#四已知的来源问题)。

被排除的内容在 [design.md §2 非目标](design.md#非目标)，那是**边界**——
发现它们缺失不算缺陷。

改变含义就递增 rev 并在这里加一节。判断标准：
