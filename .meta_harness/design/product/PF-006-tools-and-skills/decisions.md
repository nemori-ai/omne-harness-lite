## 二、PM 推导

从已拍板内容推出的判断，附可核对的推理链。

| 结论 | 从哪几条推出 | 推理 |
|---|---|---|
| **「能做什么」「怎么够得着」「现在做不做得了」是三层，正交** | 常驻标记 + 同名替换件 + [I-4](../PF-004-agent-definition-and-assembly/design.md#61-不变式) | 三条裁决各自约束了一件事，而三件事**都不改变动作空间**：常驻标记只改呈现，可用性只改当下能不能跑。**只有分成三层，I-4 才能在这些机制下继续成立**；合成一层就必然有一个要破 |
| **能力发现与取用的入口必须是常驻** | 「能力发现工具是一个 meta-tool」 | 这是**自举点**：入口本身若不常驻，agent 无从发现任何东西，整套机制转不起来。裁决已明说它是 meta-tool（正文用词为「常驻工具」），此处只是把「必须」写出来 |
| **非常驻的工具不进槽位，经取用入口调用** | 「Tools() 用来**发现和执行**工具」+「调用不改变 system prompt」 | **发现与执行合一**意味着工具不需要先"加载进"什么地方。若只发现不执行，发现之后仍要把它放进槽位，system prompt 就变了——与裁决直接矛盾。**只有这一种读法自洽** |
| **常驻机制省下的不只是 description，还有参数格式** | 「不常驻」+ 工具必须可被正确调用 | 非常驻工具的参数格式同样不在系统提示词里，否则省不下多少。由此推出一条产品要求：**agent 必须有办法知道一个非常驻工具收什么参数**。具体怎么给（发现时一并给，还是单独一步）是 PF-007 与实现的事 |
| **取用一份技能不产生「已激活」状态** | 「不会导致 system prompt 改变」 | 若取用会让技能持续出现在系统提示词里，那就是改变了成分。**裁决直接排除了这条路**，于是取回的正文只能作为这一次的返回内容进入对话，随上下文自然存续 |
| **系统提示词的成分在 agent runtime 存续期内恒定** | 上一条 + [PF-004 §5.4](../PF-004-agent-definition-and-assembly/design.md#54-为什么系统提示词必须落在第三列) | 唯一能改变成分的是常驻标记，而它在装配时就定死了。**运行中没有任何动作能改 system prompt**——这条同时守住了 PF-004 的「成分在装配时确定」 |
| **替换件的应答是正常返回，不是错误** | 「明确让 agent 能够感知当前不可用」 | 「感知」要求它读得懂**为什么**，而异常不带这个信息。给一个错误码，agent 只会当成失败去重试 |
| **agent 一共只遇得到两种情形，不可用是第二种** | 替换件 + [PF-002 的移除与禁用](../PF-002-assets-settings-and-permissions/design.md#64-移除与禁用是两个动作)（2026-09-22 裁决） | 差别落在同两个维度上：动作空间变不变、agent 知不知道。**不可见**（移除、禁用：变小、不知道）与**可见但用了一定失败**（依赖不满足：不变、知道缺什么）。**不需要为不可用另立机制**，但**这条界线要守住**——塌成一种，agent 就分不清「我没有」和「我有但使不了」 |
| **可用性只有两态，没有「部分可用」** | [声明里只有必需项](design.md#只有且只有必需)（2026-09-22 裁决） | 每项都有提供者就可用，缺一项就不可用。没写进声明的东西不满足，是**那一次执行**的事。第三态没有对应的产品含义，加了只会让所有判断多一个分支 |
| **上一次 run 能用的，这一次可能不能用** | 「每次 run 开始前都重算」 | 直接后果。必须写进正文，否则会被当成故障报上来；而 agent 也得能承受这件事 |
| **外部服务恢复后自动换回真身，无需人工干预** | 同上 | 重算是无条件的，不是"变坏时才算"。否则恢复之后没有任何事件触发它换回来 |
| **一次工具执行有六种收场，四种「非完成」里只有一种是失败** | 「中断不是失败」+ 替换件 + 转后台占位 + 等待态 | 裁决直接给了「完成 / 失败 / 中断 / 转后台」四种；替换件带来第五种（不可用），等待态带来第六种（等不到）。**都必须以正常返回到达**——这是「语义化地感知」那条裁决的必然要求，异常带不了语义 |
| **agent 必须能分清「没成」「没做」「做不了」「还在做」** | 上一条 | 这是六种收场存在的**唯一理由**。分不清，agent 的下一步必然错：该绕路时死磕，用户刚叫停它又跑一遍 |
| **要不要给等待设上限，是使用者的属性，不是这个原语的属性**（rev 3 修正） | 「等待态」+ 资源角度 | **rev 1/2 的写法是「等待态等不到应答要有上限」，那条推过头了。**它的理由——「一次执行不能永远占着资源等一个不会来的应答」——只对**占着东西的等待**成立。判据是**这个等待占不占资源**：占着的（比如沙箱里一个进程停着等）可以设上限，到头按第六种收场；[`Ask()` 那种不占任何东西的](../PF-007-meta-capabilities/design.md#611-ask通向人)**不该设**——**不花钱的等待没有理由到点，而设了上限就必须规定「到点算什么」，那是系统替人签字**。**「等不到应答」这个收场本身不作废**，它对前一类仍然成立 |
| **前台 → 后台是单向的** | 「转后台 agent 有感知，通过占位 ToolMessage」 | 占位消息一放，这一轮就继续往下走了。再拉回前台等于要求时间倒流 |
| **session 结束时未完成的执行随之收场** | 「与 session 绑定」 | 收件人都没了，跑完也没处送。形状与 [PF-005 会话级沙箱到点销毁](../PF-005-execution-environments-and-sandboxes/design.md#63-会话级沙箱到点销毁数据不留存)一致 |
| **收件人是 session，不是发起它的 agent runtime** | 「与 run 解耦、与 session 绑定」 | 实例可能在执行完成前就退役了。送给实例，结果就丢了——而裁决明确要求它送得到 |
| **要求满足不了时，绝不能降级给一个不满足要求的执行环境** | 「工具开发者自己分析执行是否绝对安全，不安全就声明要哪种沙箱」 | 声明本身就是那个安全判断。降级满足等于绕过它，与 [PF-005 沙箱创建失败不得退回宿主机](../PF-005-execution-environments-and-sandboxes/design.md#62-宿主机不提供租户隔离因此必须被显式允许)同性质 |
| **「外部服务」不是 PF-002 排除的那个 Service** | 「tool 应能声明自己依赖的服务」+ [PF-002 把 Service 列为技术实现概念](../PF-002-assets-settings-and-permissions/design.md#八类资产) | 两处的「服务」不是一回事：PF-002 排除的是 Cordis 的运行时概念，这里说的是工具要连的对端。**正文必须加注区分**，否则就是同名不同义 |
| **声明与实际必须一致，不一致属缺陷** | 依赖解析这件事本身 | 声明只要 A 却去用 B，可用性算出来是对的、跑起来是错的。这类故障**排查时所有人都会先怀疑别处**，代价远高于普通缺陷，必须在正文点名 |
| **装配清单的条目数在依赖解析前后不变** | 「不是不可用就不装配」 | 替换件占同样的位置。这是「形状恒定」在产品上的具体样子，也是可验收的判据 |
| **本版不定设施清单、不定等待上限、不定重名规则** | 「先做最小的正确模型」+ 裁决划定的边界 | 三者都还没有真实需求推着走。现在定，下一个用例就得改产品文档 |
| **「光能写进去不够，还得有工具能把它读出来」是可用性的判据，不是建议** | 「产出附件的工具要声明存储」+「要有能读出来的工具」这两条裁决 | 产出了附件却没人读得回来，**那个附件等于不存在**——而 agent 会拿着一个地址反复尝试，**永远取不到，且它不知道为什么**。所以这两件事要**一起算可用性**，不能分开判 |
| **卸载不是丢弃，占位提示必须让 agent 知道「这里有东西，只是没展开」** | 「被替换成指向卸载结果的占位提示」 | 提示若写得像「没有结果」，agent 会重来一次——**而重来一次得到的还是一条占位**。这是个会稳定复现的死循环 |
| **系统不替工具开发者写摘要——兜底那条路只做机械截断** | 两条来路的裁决 | 工具开发者知道自己这份结果哪部分要紧，**系统不知道**。**猜出来的摘要比机械截断更危险，因为它看上去是有意义的**：机械截断诚实，agent 一眼看得出中间缺了一段；而一份臆造的摘要，agent 会当成完整转述用下去，**它不知道自己漏了什么** |
| **三个维度两两正交，要明写出来** | 「卸载与前后台、与等待态不耦合」 | 不写明，很容易长出「结果大就转后台」这种耦合。**结果有多大，与它该不该占着 run，毫无关系**——前者是内容的事，后者是节奏的事 |
| **多命令范式存在的理由是「把一族动作压进一个槽位」** | 两种范式的裁决 + [PF-007 的十三扇门与槽位预算](../PF-007-meta-capabilities/design.md#54-十三个槽位是预算的地板也是它的天花板意义) | 那十三个常驻工具**全是多命令形状**。换成单函数范式，`Tools()` 的每个命令都得立成独立工具——**一族动作吃掉一族槽位**，而槽位是预算的地板。反过来单函数的理由也清楚：**只干一件事的工具再套一层分派，除了让 agent 多填一个字段什么也没换来** |
| **多命令工具的定义里带多少，归工具作者定**（**2026-09-24 部分取代**：模型面前只有命令清单一种样子，作者带的完整参数只用于校验与答用法——[产品负责人裁定](#2026-09-24--说明必填多命令工具在模型面前只有紧凑的命令清单一种样子)；「带不带完整参数归作者定」仍成立，「带了就一次到位」那一端作废） | 那边两种 dispatch 模式正好是这个权衡的两端 | 只带命令清单 → 定义小，但**agent 动手前得先问一次**；带全部命令的完整参数 → 一次到位，但**命令越多越吃预算**。两端都成立，而**只有工具作者知道自己有几个命令、参数复杂到什么程度**。系统不折中——**折中往往两头都不占** |
| **不给多命令工具配自带的 `help` 命令，统一走 [`Tools().inspect`](../PF-007-meta-capabilities/design.md#61-tools通向任意非常驻工具)** | 「概念只定义一次」+ `inspect` 已经存在 | legacy 那边每个多命令工具自带 `help`。但 `inspect` 干的就是这件事，**而且对单函数工具一样管用**。留两条路，**就多一处会和 `inspect` 说得不一样的地方**——而 agent 分不出该信哪个。**这是一处有意偏离 legacy** |
| **两种返回写法能力不对等，是有意的** | 「普通返回整个当字符串用」这条裁决 | 只有 `ToolResult` 能带卸载与附件；按普通函数返回的**就是一段文本**。不对等不是缺陷——它让「要更多就用那个结构」成为一句话讲得清的规矩，**而不是一堆散落的例外** |
| **执行的账不进 agent 的上下文** | 「上报给系统」这条裁决的字面 | 裁决说的是上报给**系统**，而 ToolMessage 是给 **agent** 的。塞进去只会白占位置——**agent 拿 cpu 时间做不出任何判断**。账该被谁消费（诊断、计量）归观测那一块，本 topic 只定它必须留下、且不进上下文 |
| **四项声明里，「不声明」的含义并不一样** | 「不声明就是不能后台」这条裁决 + 另外三项的性质 | 前三项声明的是**我需要什么**——没说就是不需要，**少一个前提反而更容易可用**；第四项声明的是**我允许什么**——**没说就是不允许**。不点破这层差别，会有人把「四项都可选」理解成「四项都是不填就宽松」，**而第四项恰恰相反** |
| **手动切后台不绕开声明** | 「不声明就是不能后台」的推广 | 人可以决定**「现在切」**，但不能决定**「它能不能切」**。留这个口子，声明就形同虚设——**一个从没准备好异步的工具，照样会被丢到后台去** |
| **rev 4 的 §6.11 索引节要删掉，并进 §5.3** | 「集中来写」这条裁决 + 「概念只定义一次」 | 声明项一旦在 §5.3 正面写清楚，再留一份索引就是**第二份会漂移的权威**。rev 4 加索引是因为当时声明项散在六处却没有正文落点；rev 5 有了正文落点，索引的存在理由就没了 |
| **两个原语该并起来讲，因为它们的对照本身就是内容** | 发帧那条裁决 + 等待态原有的定义 | 两个原语在**每一项上都正好相反**：一个要东西进来、一个给东西出去；一个阻塞、一个不阻塞；一个落空了要算一种收场、一个落空了什么也不算。**分两处写，读者得自己去发现这层对照**；并在一处，这层对照替两条定义各省了一半解释 |
| **发帧落空不构成任何一种收场** | 「六种收场」+ 帧的读者是人 | 六种收场回答的是「**这次调用办成什么样**」，而帧回答的是「现在办到哪了」。播报没送出去，**事情本身照办不误**——把它算成一种收场，等于让一个纯粹的旁白决定正剧的结局。**反过来更要点破：工具不能因为「说不出话」而失败** |
| **帧不顶替结果** | 帧只给人看（[PF-009](../PF-009-context-message-types/design.md#toolinternalmessage)）+ 六种收场都要到达 agent | 一个工具把过程播报得再细，**agent 一帧都看不见**。所以「我都发过帧了，结果随便给一个」这条路是堵死的——**那等于什么都没给 agent**。这一条必须写在正文，否则工具作者迟早会踩 |
| **不在定义里的从两样变成三样，但发帧的理由与另外两样不同** | 「帧由协议约定」这条裁决 | 等待态与卸载不在定义里，是因为**它们取决于这一次跑成什么样**。发帧多一层更硬的理由：**就算某个工具真的每次都发帧，那一格也不会被读一次**——系统是按实际收到什么解析的。**一格从不被读的声明，不是可选项，是废字段** |
| **丢掉的那层校验要在取舍表里认下来** | 「系统按实际收到什么解析」 | 没有声明，就**没有「声明与行为不符」这种错可抓**——工具发出不合协议的东西，只能在收到那一刻才发现。这是真的代价，[§7](design.md#七取舍) 明写。换来的是省掉「声明」与「核对声明」两层，以及**一个工具可以先吐日志、最后给一块汇总面板** |

**2026-09-23 的推导**（rev 15；前提是上面那条 2026-09-23 裁决与[块 B-1 的调研缺口](../../../research/tool-execution-runtime-sources/README.md)）：

| 结论 | 从哪几条推出 | 推理 |
|---|---|---|
| **带了 `help`，就必须与 `inspect` 说得一致** | 「help 可选」裁决 +「meta tools 需要注意设计实现」+ 本页原先那条「多一个 help 就多一处会说得不一样」的理由 | 裁决放开了「带不带」，**没有放开「两处说法可以不同」**——后者正是原先不许带的理由，它仍然成立：agent 分不出该信哪个。所以「可选」与「一致」同时成立，不一致记为缺陷 |
| **常驻这项设置归偏好类** | 裁决「常驻是引用上的设置项」+ [PF-002 §5.2 判类准绳](../PF-002-assets-settings-and-permissions/design.md#设置项分四类资产声明每一项时必须标类别) + [§5.1 三层正交](design.md#51-三层正交) | 准绳问：改了会不会换掉这次运行要过的那道权限门，或改变一道已放行的权限放出去的是什么。**常驻只改呈现**——动作空间不变、可用性不变、非常驻的照样经 `Tools()` 过同一道执行权限门，**所以不是落点与身份**。它不管别的设置，**不是治理**。它不指向别的资产或位置（指向那件东西的是引用本身），**不是绑定**。剩下的只有偏好：配错了是预算吃紧或少直接看见一样东西——「难用」。**后果**：工作区也能配它 |
| **常驻这项设置挂在 Agent Definition / Plugin 上，由持有它们的各层配值** | 同上 + [PF-002 三方分工](../PF-002-assets-settings-and-permissions/design.md#三方分工资产定形状各层配值运行时求值) | 引用条目是 Agent Definition 或 Plugin 的一部分；设置总是某个资产的设置，所以它是**那份 Agent Definition 或 Plugin 的设置**：写引用的人给默认值，持有它的各层配值。「agent definition 压 plugin」不受影响——那是两份资产各自的这项设置落在同一个成员上时听谁的 |
| **定义里六项声明只有两项是设置：目标环境（落点与身份）、转后台阈值（偏好）** | [PF-002 §5.2](../PF-002-assets-settings-and-permissions/design.md#设置项分四类资产声明每一项时必须标类别) 把「Tool 的目标环境」列为落点与身份、「转后台阈值」列为偏好 + [依赖声明用抽象名字](design.md#依赖) + 「人可以决定现在切、不能决定能不能切」 | 外部服务、存储、两端模态是依赖声明里的名字，**谁满足它看谁生效在那个名字上**，没有哪一层要为它配值；**能不能后台**是作者对自己代码时序的许可，若成了设置，持有者就能替作者表态——正是 [§6.6](design.md#66-前台后台-与-等待态是两个维度)「没表过态不等于表了同意」要挡的。只剩两项是「值」：它们在定义里声明的是**形状与默认值**，各层配值 |
| ~~**工具执行的宿主：前台是 agent runtime，转后台后是会话；收件人始终是会话**~~ **已撤回（2026-09-23，产品负责人纠正，见[第一节（二）](#2026-09-23二-工具执行从不由-agent-runtime-承载mcp-连不上就是不可用)）** | 2026-09-17「与 agent runtime 解耦、与 run 解耦、与 session 绑定」+ [PF-012 §6.13 取消跟着宿主走](../PF-012-agent-loop-and-run/design.md#613-取消跟着宿主走) + §6.12「前台的跟着停」 | 2026-09-17 的「解耦」是说它**是自己的一个运行时**，所以能转后台；**不等于前台时 agent runtime 死了它还活**——前台的结果要交回 loop，loop 没了无处可交，PF-012 已把前台的宿主定为 agent runtime。「与 session 绑定」在两边都成立：会话是最外面那一层宿主，也是收件人。**所以唯一自洽的说法是：宿主随前后台换，收件人不换** |
| **「转后台」是前台那一次调用的收场，后台那段执行另有收场（完成 / 失败 / 被中断 / 等不到应答）** | 六种收场 + 前台到后台单向 + 替换件从不真的跑 | 转后台之后执行还在跑，它跑到头总要有个结局；那个结局不可能是「不可用」（替换件转不了后台），也不可能再是「转后台」（单向）。剩下四种。这回答了调研报的「转后台被称终态，但后来的了结用哪套词」 |
| ~~**agent runtime 被回收：对前台是停机，对后台不是**~~ **已撤回（同上）**：回收对任何一次工具执行都不是停机 | 停机判据「与宿主失去连续性」+ 上一条宿主 | 判据里的「宿主」一旦分前后台，同一件事就分两边：前台的宿主没了，停机、落失败；后台的宿主是会话，会话还在，照跑。原先正文「在这一层眼里是同一件事」只对前台成立 |
| **会话归档时在途执行的收场是「被中断」** | [§5.5 六种收场](design.md#55-一次工具执行的收场有六种) + [PF-015 归档有两条来路](../PF-015-session-lifecycle-and-ownership/design.md#62-归档有两条来路人手动或到期自动) + 停机算失败的理由 | 逐个排除：完成、转后台不是；**不可用**只属替换件；**等不到应答**只属等待态到头；**失败**是「这事没成」，停机算失败是因为**失去连续性、没人有意停它**——归档恰恰是有意的（人手动或到期自动），执行本身没出错。剩下「被中断」：**这事不做了，别自动重试**，正合归档。PF-015 两处说法（被中断 / 被取消）统一为这个词 |
| **「停了不重来」不设「可证明从未开始」的例外** | 停机不重来的理由（外部效果收不回来）+ 失败的下一步本来包括重试 | 例外要成立，得有人证明「它在外面什么都没做」——而**一次执行在外面做了什么，恰是这一层看不全的**。放进例外，就多一条「系统替 agent 断定没做过」的路，判错一次就是做第二遍。不设例外的代价只是真没开始的那一次也落失败，**agent 看着情况重试即可**。只有一个答案自洽 |
| **换模型之后动作空间不变，模态不兼容的工具变成不可用替换件** | [§4 三层正交](design.md#三层能做什么--怎么够得着--现在做不做得了) + [§6.3](design.md#63-不可用时装的是同名替换件不是不装) + [I-4](../PF-004-agent-definition-and-assembly/design.md#61-不变式) | 两端模态是依赖声明里的项，缺了就是**不可用**；不可用装替换件、**不改动作空间**。原先 §6.11 那句「动作空间可能变小」与这三条都矛盾，而它自己下一句又说「与同名替换件是同一条」——**两句里只有后一句自洽** |
| **MCP 动作不常驻、随接入点持有与授权、每次 run 前与可用性一起重算、run 内不变** | MCP 映射裁决 + [常驻挂在「装配它」的引用上](design.md#常驻) + [PF-002：对端动作不是资产](../PF-002-assets-settings-and-permissions/design.md#mcp) + [§6.2](design.md#62-可用性在每次-run-开始前重算) | 装配引用的是接入点，**没有哪条引用指向单个动作**，所以没有地方给它标常驻；动作没有自己的持有，**逐动作的执行权限只能配在接入点那份持有上**；对端清单会变，只能在一个已有的重算时点吸收——**run 开始前**；run 内再变，agent 手上的清单就半路变形。I-4 不破：装进来的是接入点，它带来哪些动作是它的内容 |
| **技能不能按能力标识依赖某个 MCP 动作；要那个对端在场，声明外部服务** | [PF-002 组合矩阵：Skill 不组合 MCP](../PF-002-assets-settings-and-permissions/design.md#谁能组合谁) + 动作不是资产、没有能力标识 + [依赖名字不限种类](design.md#依赖) | 能力标识只指资产；动作不是资产。依赖声明本来就接受「外部服务」这类名字，所以不必为 MCP 另开一种依赖 |

### 2026-09-29 · 能力消费与服务依赖的边界

**直接输入**：[本轮交流 INT-005～008](../PF-004-agent-definition-and-assembly/interviews/2026-09-29-agent-runtime-assembly.md)：会话能力身份见过后保留，失去当前选择或实现时呈现不可用替换件；资产定义数据与执行实现解耦；会话类型必需与 AgentDefinition 显式必需同样不意味着 Loop 直接依赖能力背后的服务。

**本 topic 落点**：替换件覆盖已知能力卸载及不再选入；数据与实现按单次使用固定，MCP 已知动作不删除。

**PM 推导**：①“已知”与“当前允许执行”必须分别求值，否则单调性会变成绕过撤权；②实现更新可发生在稳定入口内部，故不从它推出提供者换代或 Loop 重建；③ schema 更新可能改变调用含义，故即使实例未换也须核对尚未发起的旧动作；已发工作继续沿原输入；④每次求值所需输入不同，故分别保存会话当前采用值、历史数据与实现依据和单次调用快照；⑤Session 是数据／归属，逻辑供给矩阵不推出它是 fiber；实际 inject 边与所有权仍需技术设计和验证。常驻呈现、Slash Command 人的入口及未合法纳入资产仍沿各自边界，不把单调性扩为无条件信息公开。

**已知来源问题与处置**：旧文把能力的选入、数据、实现与服务生命周期混作一种“绑定变化”，因此过度推导 Agent runtime 重建；PF-010 还把提示词成品与实例期固定混为一谈。按本次输入修订，差异记入 C-47。AgentDefinition 版本采用仍沿已拍板的新 Run 或显式 reload 安全交接，不以本次技术分析自行取消该产品边界。框架事实采用 Cordis 4.0.4，区分 provider fiber 换代与同 provider 的数据更新（[已验证 basis](../../basis/cordis/plugin-body-reruns-on-provider-change.md)）；本次额外检查发布包源码，不声称运行了新探针。项目只复用 Cordis，不采用 DSH agent 原语。
