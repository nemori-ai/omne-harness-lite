## 二、PM 推导

从已拍板内容推出的判断，附可核对的推理链。

| 结论 | 从哪几条推出 | 推理 |
|---|---|---|
| **「能做什么」「怎么够得着」「现在做不做得了」是三层，正交** | meta 标签 + 同名替换件 + [I-4](../PF-004-agent-runtime-assembly-and-liveness/design.md#61-不变式) | 三条裁决各自约束了一件事，而三件事**都不改变动作空间**：meta 只改呈现，可用性只改当下能不能跑。**只有分成三层，I-4 才能在这些机制下继续成立**；合成一层就必然有一个要破 |
| **能力发现与取用的入口必须是 meta** | 「能力发现工具是一个 meta-tool」 | 这是**自举点**：入口本身若不常驻，agent 无从发现任何东西，整套机制转不起来。裁决已明说它是 meta-tool，此处只是把「必须」写出来 |
| **非 meta 的工具不进槽位，经取用入口调用** | 「Tools() 用来**发现和执行**工具」+「调用不改变 system prompt」 | **发现与执行合一**意味着工具不需要先"加载进"什么地方。若只发现不执行，发现之后仍要把它放进槽位，system prompt 就变了——与裁决直接矛盾。**只有这一种读法自洽** |
| **meta 机制省下的不只是 description，还有参数格式** | 「不常驻」+ 工具必须可被正确调用 | 非 meta 工具的参数格式同样不在系统提示词里，否则省不下多少。由此推出一条产品要求：**agent 必须有办法知道一个非 meta 工具收什么参数**。具体怎么给（发现时一并给，还是单独一步）是 PF-007 与实现的事 |
| **取用一份技能不产生「已激活」状态** | 「不会导致 system prompt 改变」 | 若取用会让技能持续出现在系统提示词里，那就是改变了成分。**裁决直接排除了这条路**，于是取回的正文只能作为这一次的返回内容进入对话，随上下文自然存续 |
| **系统提示词的成分在运行实例存续期内恒定** | 上一条 + [PF-004 §5.4](../PF-004-agent-runtime-assembly-and-liveness/design.md#54-为什么系统提示词必须落在第三列) | 唯一能改变成分的是 meta 标签，而它在装配时就定死了。**运行中没有任何动作能改 system prompt**——这条同时守住了 PF-004 的「成分在装配时确定」 |
| **替换件的应答是正常返回，不是错误** | 「明确让 agent 能够感知当前不可用」 | 「感知」要求它读得懂**为什么**，而异常不带这个信息。给一个错误码，agent 只会当成失败去重试 |
| **不可用与「移除 / 禁用」是同一形状的第三种** | 替换件 + [PF-004 的移除 vs 禁用](../PF-004-agent-runtime-assembly-and-liveness/design.md#63-三类变化三种传播) | 三者的差别正好落在同两个维度上：动作空间变不变、agent 知不知道。移除（变小、不知道）／禁用（不变、知道被禁）／依赖不满足（不变、知道缺什么）。**不需要为第三种另立机制** |
| **可用性只有两态，没有「部分可用」** | 「必需 / 可选」的区分 | 可选依赖不满足的仍算可用，必需依赖不满足的就是不可用。第三态没有对应的产品含义，加了只会让所有判断多一个分支 |
| **上一次 run 能用的，这一次可能不能用** | 「每次 run 开始前都重算」 | 直接后果。必须写进正文，否则会被当成故障报上来；而 agent 也得能承受这件事 |
| **外部服务恢复后自动换回真身，无需人工干预** | 同上 | 重算是无条件的，不是"变坏时才算"。否则恢复之后没有任何事件触发它换回来 |
| **一次工具执行有六种收场，四种「非完成」里只有一种是失败** | 「中断不是失败」+ 替换件 + 转后台占位 + 等待态 | 裁决直接给了「完成 / 失败 / 中断 / 转后台」四种；替换件带来第五种（不可用），等待态带来第六种（等不到）。**都必须以正常返回到达**——这是「语义化地感知」那条裁决的必然要求，异常带不了语义 |
| **agent 必须能分清「没成」「没做」「做不了」「还在做」** | 上一条 | 这是六种收场存在的**唯一理由**。分不清，agent 的下一步必然错：该绕路时死磕，用户刚叫停它又跑一遍 |
| **等待态等不到应答要有上限，到头按第六种收场** | 「等待态」+ 资源角度 | 没有上限，一次执行可以永远占着资源等一个不会来的应答。这与[会话级沙箱的最大存活时间](../PF-005-execution-environments-and-sandboxes/design.md#63-会话级沙箱到点销毁数据不留存)同类。**上限具体多久属资源政策，本版不定** |
| **前台 → 后台是单向的** | 「转后台 agent 有感知，通过占位 ToolMessage」 | 占位消息一放，这一轮就继续往下走了。再拉回前台等于要求时间倒流 |
| **session 结束时未完成的执行随之收场** | 「与 session 绑定」 | 收件人都没了，跑完也没处送。形状与 [PF-005 会话级沙箱到点销毁](../PF-005-execution-environments-and-sandboxes/design.md#63-会话级沙箱到点销毁数据不留存)一致 |
| **收件人是 session，不是发起它的运行实例** | 「与 run 解耦、与 session 绑定」 | 实例可能在执行完成前就退役了。送给实例，结果就丢了——而裁决明确要求它送得到 |
| **要求满足不了时，绝不能降级给一个不满足要求的执行环境** | 「工具开发者自己分析执行是否绝对安全，不安全就声明要哪种沙箱」 | 声明本身就是那个安全判断。降级满足等于绕过它，与 [PF-005 沙箱创建失败不得退回宿主机](../PF-005-execution-environments-and-sandboxes/design.md#62-宿主机不提供租户隔离因此必须被显式允许)同性质 |
| **「外部服务」不是 PF-002 排除的那个 Service** | 「tool 应能声明自己依赖的服务」+ [PF-002 把 Service 列为技术实现概念](../PF-002-assets-settings-and-permissions/design.md#七类资产) | 两处的「服务」不是一回事：PF-002 排除的是 Cordis 的运行时概念，这里说的是工具要连的对端。**正文必须加注区分**，否则就是同名不同义 |
| **声明与实际必须一致，不一致属缺陷** | 依赖解析这件事本身 | 声明只要 A 却去用 B，可用性算出来是对的、跑起来是错的。这类故障**排查时所有人都会先怀疑别处**，代价远高于普通缺陷，必须在正文点名 |
| **装配清单的条目数在依赖解析前后不变** | 「不是不可用就不装配」 | 替换件占同样的位置。这是「形状恒定」在产品上的具体样子，也是可验收的判据 |
| **本版不定设施清单、不定等待上限、不定重名规则** | 「先做最小的正确模型」+ 裁决划定的边界 | 三者都还没有真实需求推着走。现在定，下一个用例就得改产品文档 |
