# PF-006 故事卡

**已发到**：ST-006-23

顺序已由产品负责人确认，见[拍板记录](design.md)。先取得一次真实工具结果，再核对装配与替换，随后交付执行控制和工具产出；与环境卡的穿插先后按该记录执行。

演示使用执行仓库的模型调用示例（`examples/model-invocation-minimal-demo`）集成独立工具运行时后的程序化入口。调用方提供本次合法采用的输入，产品负责人观察公开调用结果、执行进展和实际产物。等待、停止、后台、停机收场和结果读取按各自的公开能力演示；单次调用成功不代表这些能力已交付。演示不以完整会话界面、Agent Loop 或具体元工具实现为前置。

演示中的时长、限额和依赖状况均为该次明确准备的输入，不是产品默认值。卡片只规定操作与可见结果；技术接口、装载机制和输入刷新方式由后续技术工作确定。

### ST-006-04 · 工具实际执行的是装配选中的唯一实现

- **价值**：调用者能确认实际执行承接了既有覆盖规则的选择结果，不会仅因名字相同而调用未选中的实现。
- **覆盖场景**：[S118](acceptance.md#独立工具运行时的调用与控制)
- **演示**：
  1. 为同一租户准备两份同名工具候选，各自约定不同的返回文字和执行标记；按现行覆盖规则合法选中其中一份，完成登记与装配 → 公开演示显示该工具只有一个生效实现，并列出选中资产、版本与约定结果。
  2. 从这份装配的公开入口调用该工具 → 返回选中实现约定的文字。
  3. 核对本次调用依据与实际执行标记 → 资产和版本与装配选择一致，只有选中实现的标记产生，未选中候选没有执行。
- **不含**：资产获取、分享、重名选择政策，以及具体装载方式。
- **前置**：无
- **就绪**：是

### ST-006-05 · 更新工具实现后，旧调用仍按原输入收场

- **价值**：使用者更新工具时，已经发出的工作不会被悄悄改写或重复执行。
- **覆盖场景**：[S119](acceptance.md#独立工具运行时的调用与控制)
- **演示**：
  1. 准备两份合法实现，约定不同结果；先采用第一份，发起一项尚未完成的调用 → 演示显示原调用所用的实现、参数、采用依据与已经开始的事实。
  2. 合法采用第二份实现，再发起一项新调用 → 新调用按更新后的输入执行，取得第二份约定的结果。
  3. 让原调用完成 → 原调用取得第一份约定的结果；参数没有改变，也没有重新执行。
  4. 另做一轮同样的更新演示，让已发旧调用自身的执行进程意外退出，恢复后查询原调用 → 原调用明确收为失败，原因是「工具执行异常中断」；它仍对应第一份实现、原参数与原采用依据，没有换函数、改参数或重发。
  5. 按第二份合法输入另发一次调用 → 新调用取得第二份实现的约定结果，采用依据与之相符；原调用仍保持失败，没有被重新执行。
- **不含**：文件变化自动触发更新、更新监听机制、旧动作建议的重新确认和外部效果撤销。
- **前置**：ST-006-04
- **就绪**：是

### ST-006-03 · 调用不可用工具时取得具体原因

- **价值**：使用者和模型都能知道这项工具当前缺什么，不会把没有执行误认为成功。
- **覆盖场景**：[S18](acceptance.md#六项可选声明)、[S45](acceptance.md#可用性与替换件)、[S55](acceptance.md#可用性与替换件)
- **演示**：
  1. 准备一个已知工具，它依赖指定存储，正常执行会写入一份处理结果；让该存储缺席并合法采用本次输入 → 演示公开显示底层执行实现已换成同名同形替换件，工具名与参数形状保留，说明指出缺少的存储。
  2. 让模型仍按原名调用该工具，由演示交给独立工具运行时 → 调用正常返回「当前用不了」及缺少的具体存储，原工具的处理结果没有产生。
  3. 把这份结果交回模型 → 演示显示模型收到同一项不可用原因，产品负责人能直接读出缺什么；结果不是抛出的错误。
- **不含**：模型随后选择什么办法、是否另发调用、依赖恢复后的替换、Run 之间的可用性重算。
- **前置**：ST-006-04
- **就绪**：是

### ST-006-06 · 依赖恢复后，同一个工具位置重新能用

- **价值**：调用者在依赖缺席和恢复之间仍能使用同一工具入口，知道它现在为什么能用或不能用。
- **覆盖场景**：[S120](acceptance.md#独立工具运行时的调用与控制)
- **演示**：
  1. 为同一个已知工具准备三份依次采用的合法输入：必需依赖齐全、缺席、恢复；合法选入和治理条件始终成立 → 负责人能核对三份输入的差别仅在这项依赖状况。
  2. 采用第一份输入后调用 → 真实现执行，得到约定结果。
  3. 采用第二份输入后用同名、同参数形状调用 → 底层已换成替换件，正常返回具体不可用原因，原作用没有发生。
  4. 采用第三份输入后再次调用 → 真实现再次执行并取得结果；公开工具位置、名字和参数形状与前两次一致，没有通过删除再重建恢复。
- **不含**：输入刷新频率、监听方式、完整 Session 中每次 Run 的重算，以及撤权后仅因依赖恢复就自动放行。
- **前置**：ST-006-03
- **就绪**：是

### ST-006-07 · 工具执行没成功时得到明确失败结果

- **价值**：调用者能分辨操作失败与工具不可用，不会把没有办成的事当成成功。
- **覆盖场景**：[S70](acceptance.md#六种收场分得清)
- **演示**：
  1. 准备一个能够自行报告执行失败的工具，设置明确会失败的业务输入 → 演示显示工具本身可用，参数合法。
  2. 从公开入口调用 → 工具实际执行后正常返回失败收场和失败原因，没有返回成功结果。
  3. 将结果交回模型 → 模型收到的工具结果明确为失败，区别于同名替换件的不可用结果。
- **不含**：本层无法了结的实现故障、基础设施异常上交和模型随后是否重试。
- **前置**：无
- **就绪**：是

### ST-006-02 · 参数无法解析的完整调用得到明确失败结果

- **价值**：调用者知道工具没有执行以及失败原因，不会一直等待一个不存在的执行结果。
- **覆盖场景**：[S77](acceptance.md#六种收场分得清)
- **演示**：
  1. 准备一个执行后会创建指定文件的演示工具，选取一份模型已结束生成、但工具参数无法解析的完整调用 → 产品负责人能读到原始调用块，并确认目标文件尚不存在。
  2. 把这份调用交给独立工具能力 → 调用以正常返回交回失败收场，原因明确写出参数解析不了；指定文件仍未产生。
  3. 把失败结果交回模型，并读取演示展示的原模型回复 → 模型收到的是说明失败原因的工具结果；原回复中的调用块逐字保留，没有被修补或替换。
- **不含**：模型尚未结束生成的调用、参数成功解析后工具自身报错、自动修复参数和重新调用。
- **前置**：无
- **就绪**：是

### ST-006-08 · 工具等到所需应答后继续完成

- **价值**：调用者知道工具在等什么，能补足输入让工作继续。
- **覆盖场景**：[S14](acceptance.md#工具定义的两种范式)、[S87](acceptance.md#前后台与等待态正交)
- **演示**：
  1. 调用一个会按本次输入决定是否等待的演示工具，这次让它需要补充一个带文字说明的选择 → 公开进展显示正在等待，并说明可接受的应答形状。
  2. 通过公开能力交入所需应答 → 原执行继续并返回与该应答对应的结果。
  3. 再次调用同一工具，这次输入已足够 → 它直接完成，没有进入等待；两次均正常。
- **不含**：Ask 的具体实现、问询界面和后台等待。
- **前置**：无
- **就绪**：是

### ST-006-09 · 占着资源却等不到应答时明确收场

- **价值**：调用者能分辨无人应答与执行失败，不再等待已经结束的工具。
- **覆盖场景**：[S74](acceptance.md#六种收场分得清)
- **演示**：
  1. 准备一个占着宿主机执行资源等待应答的工具，为本次等待明确设置上限 → 演示显示正在等待、所需应答及本次上限。
  2. 不提供应答，让等待达到该上限 → 执行收为「等不到应答」。
  3. 读取公开结果并交回模型 → 返回说明没有等到应答，没有标成失败、被拒或成功。
- **不含**：对不占资源的问询设置上限、替人给默认答案和 Ask 的具体实现。
- **前置**：ST-006-08
- **就绪**：是

### ST-006-10 · 停止一次工具执行后，它不会自行重来

- **价值**：调用者能单独叫停工具，并看清已经发生的效果仍然存在。
- **覆盖场景**：[S121](acceptance.md#独立工具运行时的调用与控制)
- **演示**：
  1. 发起一个先写入一段标记、随后继续工作的工具 → 负责人看到标记已经写入，执行仍在进行。
  2. 通过工具运行时公开控制能力请求停止这一次执行 → 原执行收为被中断，原因说明本次由用户手动请求停止。
  3. 读取原执行结果并检查标记 → 没有自动另起一次执行，标记仍在；结果没有声称先前的写入已被撤销。
- **不含**：模型之后明确另发调用、agent 的自动重试策略、Run 取消、会话归档和具体 BkgJobs。
- **前置**：无
- **就绪**：是

### ST-006-11 · 没允许后台的工具切不到后台

- **价值**：工具作者没有许可异步执行时，调用者不会把它放进未准备好的运行方式。
- **覆盖场景**：[S16](acceptance.md#六项可选声明)、[S17](acceptance.md#六项可选声明)、[S86](acceptance.md#前后台与等待态正交)、[S123](acceptance.md#独立工具运行时的调用与控制)
- **演示**：
  1. 准备两份演示工具：一份省略后台许可，一份明确不允许后台。为两者明确设置本次自动转后台的时长和更晚的前台上限，再发起调用 → 公开演示显示两种许可、本次时长设置与前台执行状态。
  2. 让两次执行都达到本次自动转后台的时长，且继续运行 → 两次执行仍在前台，没有自动转后台。
  3. 在前台上限到达前，分别通过公开控制能力请求两次执行转后台 → 两次请求都未使执行转后台，执行仍在前台。
  4. 让两次执行都达到本次前台上限 → 两次执行均收为被中断，公开结果明确说明「前台超时」，没有转后台占位。
  5. 再查询这两次调用的执行结果 → 原执行均保持被中断，工具运行时没有自动另起执行。
- **不含**：前台超时后的 agent 策略、修改作者许可和后台任务管理入口。
- **前置**：无
- **就绪**：是

### ST-006-12 · 手动转后台后，仍能查到原执行的最终结果

- **价值**：调用者能先停止等待，同时保留正在进行的工作和它最终交出的结果。
- **覆盖场景**：[S85](acceptance.md#前后台与等待态正交)、[S122](acceptance.md#独立工具运行时的调用与控制)
- **演示**：
  1. 发起一个明确允许后台、尚未完成的工具 → 公开进展显示这一次执行正在前台运行。
  2. 通过工具运行时公开控制能力手动转后台，将实际占位结果交给模型 → 模型收到说明已转后台的占位；原执行仍在进行，没有被报告为最终完成。
  3. 让原执行完成，从公开能力读取它的最终收场和结果 → 能与原调用对应，结果是该执行实际产生的内容；前台占位与最终完成分得开。
- **不含**：BkgJobs 实现、完整会话提醒送达和模型收到占位后的下一步选择。
- **前置**：无
- **就绪**：是

### ST-006-13 · 允许后台的长任务到时自动转后台

- **价值**：调用者不必一直阻塞着等待明确允许后台的长任务。
- **覆盖场景**：[S81](acceptance.md#前后台与等待态正交)
- **演示**：
  1. 准备两个允许后台的执行：一个明确设置转后台时长，另一个不设该时长但明确设置前台上限 → 负责人能读到两组本次有效设置。
  2. 让第一个执行超过它的转后台时长 → 它自动转后台，前台取得相应占位，原执行继续。
  3. 让第二个执行达到它的前台上限 → 它同样自动转后台，没有因缺少专用时长而一直占着前台。
- **不含**：默认时长、用户插队、禁止后台工具到时后的 agent 策略。
- **前置**：ST-006-12
- **就绪**：是

### ST-006-23 · 同一会话的工具超出并发上限后按先后排队

- **价值**：调用者集中提交同一工具的工作时，超出的调用会等到名额，不会被当成失败拒绝。
- **覆盖场景**：[S84](acceptance.md#前后台与等待态正交)
- **演示**：
  1. 为同一工具提供合法的同一会话归属输入，明确允许后台，并将本次有效并发上限设为二 → 负责人能核对四次待演示调用的归属、工具名和上限。
  2. 先发起两次长执行，一次留在前台、一次在后台 → 公开进展显示两次都在执行，合计占满本次上限。
  3. 再按顺序发起第三次、第四次调用 → 两次都被受理并排队，没有因超限被拒。
  4. 让第一项在跑的执行完成 → 第三次调用先开始，第四次仍在排队；另一项原执行继续。
  5. 让另一项原执行完成，再完成后续工作 → 第四次调用随后开始，四次均取得各自结果，排队顺序与发起顺序一致。
- **不含**：完整会话的创建和恢复、跨会话配额、全局调度策略及 BkgJobs 实现。
- **前置**：ST-006-12
- **就绪**：是

### ST-006-14 · 等待应答不会耗尽前台执行时长

- **价值**：调用者补充应答时，工具不会仅因等待时间长而被前台上限掐掉。
- **覆盖场景**：[S83](acceptance.md#前后台与等待态正交)
- **演示**：
  1. 为演示工具明确设置前台上限，让它很快进入一个没有等待上限的应答等待 → 公开进展显示正在等待，负责人能读到本次前台上限。
  2. 等待超过该前台上限的时长 → 执行仍在等待，没有出现「前台超时」收场。
  3. 交入所需应答，让工具在剩余执行时长内完成 → 原调用取得正常结果，等待时间没有算进前台执行时长。
- **不含**：Ask 实现、等待上限政策和实际运行时间超过前台上限的分支。
- **前置**：ST-006-08
- **就绪**：是

### ST-006-15 · 工具自己的运行进程失去后，原执行落失败且不重来

- **价值**：部署使用者能识别执行因停机而失败，避免恢复时悄悄重复外部操作。
- **覆盖场景**：[S61](acceptance.md#工具执行的归属与跨轮)
- **演示**：
  1. 发起一个先写入一次标记、随后继续运行的工具 → 负责人看到标记恰好出现一次，原执行还未完成。
  2. 模拟承载该工具执行的进程意外退出，再恢复工具运行时 → 公开查询原执行得到失败收场及「工具执行异常中断」原因；标记没有再写一次。
  3. 另发一次调用，在它尚未产生外部效果时模拟同样的进程意外退出并恢复 → 该执行同样落失败，没有被判为「从没开始」而自动重来。
- **不含**：Agent runtime 回收、用户请求停止，以及完整会话恢复时的占位和提醒追补。
- **前置**：无
- **就绪**：是

### ST-006-16 · 工具完成后能查到计算账目，模型消息保持干净

- **价值**：负责诊断的人能看清一次执行花了多少资源，模型不用为这些账目占用上下文。
- **覆盖场景**：[S28](acceptance.md#返回值两种写法一种模型)、[S29](acceptance.md#返回值两种写法一种模型)
- **演示**：
  1. 通过公开能力发起一次有实际计算过程的工具调用 → 演示显示调用已开始及其对应身份。
  2. 等待完成，读取公开返回的结果与本次计算账目 → 能对应同一次执行，账目包含耗时、计算消耗等实际事实。
  3. 将工具消息交给模型并读取该消息 → 有工具结果，没有 CPU 时间等计算账目。
- **不含**：账目的计费规则、长期保留政策和诊断界面。
- **前置**：无
- **就绪**：是

### ST-006-17 · 人能看到工具过程消息的流式输出，工具仍以自己的结果收场

- **价值**：使用者能从[工具过程消息（`ToolInternalMessage`）](../PF-009-context-message-types/design.md#58-toolinternalmessage工具说它正在干什么)的流式输出了解进展，同时能分清过程消息与最终结果。
- **覆盖场景**：[S90](acceptance.md#工具跟外面通信的两个原语)、[S91](acceptance.md#工具跟外面通信的两个原语)、[S94](acceptance.md#工具跟外面通信的两个原语)
- **演示**：
  1. 调用一个按本次输入决定是否发帧的工具，这次让它先发日志、再发汇总面板 → 负责人看到同一条工具过程消息随增量到达而更新，依次呈现日志和面板；执行尚未因此收场。
  2. 让本次工具完成，核对交给模型的内容 → 最终工具结果另行返回，收场为正常完成；过程消息给人看，不进入模型的内容，日志和面板没有被当成第七种收场。
  3. 再次调用同一工具，这次一帧都不发 → 仍正常完成，系统没有要求补交发帧声明。
- **不含**：具体交付面的呈现样式、帧协议字段和用工具过程消息代替给模型的结果。
- **前置**：无
- **就绪**：是

### ST-006-18 · 工具过程消息的流式输出发不出去时，工具照常完成

- **价值**：使用者接收工具过程消息的端点断开，不会让原本能办成的工具工作失败。
- **覆盖场景**：[S92](acceptance.md#工具跟外面通信的两个原语)
- **演示**：
  1. 准备一个发进度帧、最后返回约定结果的工具，并使演示接收端缺席 → 负责人能确认本次没有接收工具过程消息流式增量的端点。
  2. 从公开入口执行该工具 → 用于更新同一条工具过程消息的帧不能送达，工具仍继续执行。
  3. 读取最终结果 → 正常完成并取得约定结果，未因过程消息的流式输出无法送达而改成失败收场。
- **不含**：补发历史帧、过程消息可靠送达保证和具体接收界面。
- **前置**：ST-006-17
- **就绪**：是

### ST-006-19 · 工具产出的图片存进声明的存储，消息给出地址

- **价值**：使用者能找到工具实际产出的图片，知道它保存在哪里。
- **覆盖场景**：[S98](acceptance.md#工具的产出三部分)、[S100](acceptance.md#工具的产出三部分)
- **演示**：
  1. 准备一个产出图片的工具，为它声明附件存储，并准备获准读取该存储的能力 → 负责人能读到工具声明的存储及本次可用条件。
  2. 实际调用该工具 → 返回消息包含图片地址，指向工具声明的存储。
  3. 通过演示调用方获准使用的读取能力打开该地址 → 看得到本次产出的图片，内容与预期一致。
- **不含**：Files 或其他具体元工具实现，以及模型是否自行决定取图。
- **前置**：无
- **就绪**：是

### ST-006-20 · 附件存得进却没有工具读得出时，产出工具不可用

- **价值**：调用者不会拿到一个注定无法通过工具取回的附件地址。
- **覆盖场景**：[S101](acceptance.md#工具的产出三部分)
- **演示**：
  1. 准备声明附件存储的产出工具，存储可写，但当前合法装配中没有任何工具能读取它 → 负责人能核对缺的是读取能力，而不是存储本身。
  2. 合法采用这份输入，查看该工具的可用性 → 工具为不可用，原因指明附件所在存储没有可用的读取工具。
  3. 仍按原名调用 → 正常取得同一项不可用原因，没有执行产出操作或交出假成功的附件地址。
- **不含**：补装读取工具、实现 Files，以及附件存储的选择政策。
- **前置**：ST-006-03
- **就绪**：是

### ST-006-21 · 大结果保留工具作者的摘要，原文仍可核对

- **价值**：调用者先读到够用的摘要，需要核对时原始结果仍然存在。
- **覆盖场景**：[S102](acceptance.md#工具的产出三部分)、[S103](acceptance.md#工具的产出三部分)、[S107](acceptance.md#工具的产出三部分)
- **演示**：
  1. 准备一个会产生超出本次消息限额的结果的工具，由工具作者给出约定摘要，并声明本次返回要卸载 → 负责人知道摘要和原文各是什么。
  2. 实际执行并读取交给模型的工具消息 → 消息为卸载占位，含作者给出的摘要、原结果大小和取全文的说明，明确表明工具已有结果。
  3. 由演示调用方从原结果保存处读取全文 → 与工具实际产出的原文一致，没有只保留截断部分。
  4. 将占位与一次确实没有返回内容的结果并排展示 → 负责人能读出前者是已卸载的大结果，二者没有混成空返回。
- **不含**：Tools.read_result 的具体实现、分页入口、模型自行取回全文，以及后台／等待状态下的组合变体。
- **前置**：无
- **就绪**：是

### ST-006-22 · 未主动卸载的超限结果按首尾截断形成占位

- **价值**：工具作者没有准备摘要时，调用者仍能取得可辨认的结果片段，系统不会冒充作者总结。
- **覆盖场景**：[S104](acceptance.md#工具的产出三部分)
- **演示**：
  1. 准备一个不主动声明卸载、返回值却超过本次单条消息限额的工具，原文头尾各带不同的已知文字 → 负责人能核对原文和本次限额。
  2. 实际执行并查看形成的工具消息 → 系统兜底形成卸载占位，内容由原文首尾保留的片段组成，没有系统编写的摘要。
  3. 从原结果保存处读回全文，对照占位 → 首尾片段来自原文，原文仍完整保存。
- **不含**：默认限额、摘要生成、具体全文取回元工具和后台／等待组合变体。
- **前置**：ST-006-21
- **就绪**：是
