# PF-006：工具与技能

**[PF-002](../PF-002-assets-settings-and-permissions/README.md) 说了工具和技能各自是什么，
[PF-004](../PF-004-agent-definition-and-assembly/README.md) 说了它们在装配的哪一步进来。
本 topic 补中间那段：**一份定义怎么变成 agent 真的能用的动作。

一句话概括本 topic 的结论：

> **「能做什么」「怎么够得着」「现在做不做得了」是三件事，正交，变化节奏各不相同。**

三件事混作一谈，「agent 怎么不会用这个工具」就永远查不出原因——
而它们的修法完全不同。

## 三层

| 层 | 回答什么 | 由谁决定 | 什么时候变 |
|---|---|---|---|
| **动作空间** | 我**能做**什么 | 构成 | 装配时；运行中 agent 自己追加 |
| **呈现方式** | 哪些**直接占槽位**，哪些**经代理够得着** | **常驻标记** | 装配时 |
| **当下可用性** | 现在**做不做得了** | **依赖解析** | **每次 run 开始前重算**（[每一次执行尝试都算一次开始](design.md#62-可用性在每次-run-开始前重算)） |

**常驻标记是「装配它」这条引用上的一项设置**（偏好类），不在工具自身——上下文预算是装配方的问题，
工具作者不知道。两处都标了，**agent definition 压 plugin**。
**常驻只管能力身份看不看得见**；看见的是什么归装配策略——技能是 name 与说明进系统提示词，工具由各模型的适配按供应商的方式呈现。

**不可用时装的是[同形、只换说明的替换件](design.md#替换件)，不是不装。**否则动作空间随环境波动变形，
[I-4](../PF-004-agent-definition-and-assembly/design.md#61-不变式) 当场作废，
而且用户查不出东西为什么没了。

## 一次工具执行的六种收场

**完成 / 失败 / 不可用 / 转后台 / 被中断 / 等不到应答。**

四种「非完成」里**只有一种是失败**。六种都以正常的返回消息到达 agent，
没有一种以报错形式抛给它——报错不带语义，agent 只能猜。

## 「工具」这个词指三样东西

```text
Tool Definition ──装配──→ 动作空间里的条目 ──调用──→ Tool Execution
   数据，长期                构成，绑 agent runtime          计算资源，自己的 runtime，绑会话
```

工具执行与模型请求的生命周期都归会话。Agent runtime 持有访问、等待和控制句柄，句柄释放不取消执行；Run 保留工作与成本归属。
**前台 / 后台说的是 agent runtime 这副协程有没有阻塞在它上面**，不是它挂在谁身上。
正因如此，agent runtime 被回收不影响任何一次执行；转了后台的在 run 结束之后还能继续，结果照样回得到那个会话。

## 一份工具定义，一次返回值

| | 有几种 | 要点 |
|---|---|---|
| **定义的范式** | **两种**：单函数 / 多命令 | **多命令把一族动作压进一个槽位**，模型面前**只有一份紧凑的命令清单**；作者带不带各命令的完整参数，只影响系统校不校验、问得到多细 |
| **说明** | **必填**：工具说明，与每个参数各自的说明 | 它们要原样交给模型供应商；缺了就不是一份完整的定义 |
| **定义时的可选声明** | **六项**：外部服务 / 存储 / 执行环境 / **调用它要模型给得出哪些模态** / **结果里有哪些模态** / 后台执行 | **全是可选的**，而**声明不是免费的**——多一项就多一个可能不被满足的前提。其中**目标环境**（落点与身份类）与**转后台阈值**（偏好类）是[设置项](design.md#其中两项声明的是设置项)：定义给形状与默认值，各层配值 |
| **返回的写法** | **两种**：普通函数返回 / `ToolResult` | 普通返回**在上报时被转成 `ToolResult`**，[agent-loop](../PF-012-agent-loop-and-run/README.md) 只见一种形状 |

**「不声明」的含义，六项并不一样**：前五项声明的是**我需要什么**（没说就是不需要），
最后一项声明的是**我允许什么**——**没说就是不允许，即默认不能后台**。

**不在定义里的三样**：[等待态](design.md#等待态)与[发帧](design.md#发帧)（两个都是函数逻辑里的原语）、
要不要[卸载](design.md#610-结果太大时卸载而卸载是第三个维度)（每次返回值里的事）。

> **一次工具执行还是一件可以单独记账的事**——完成时连结果一起上报的还有这次的账，
> 而**那份账不进 agent 的上下文**。

## 工具跟外面通信的两个原语

**方向相反，性质也相反：**

| | **等待态** | **发帧** |
|---|---|---|
| 干什么 | **要**一个应答进来 | **给**一点情况出去 |
| 阻不阻塞 | **阻塞** | **不阻塞** |
| 落空了 | 「等不到应答」是六种收场之一 | **什么也不会怎样** |

**两个都不在定义里。**等待态是因为「等不等是这一次跑出来的事」；
发帧是因为**系统按实际收到什么来解析，压根不查定义**——
所以连「我发不发帧」这一格都不必有。

**一次执行交出来的东西因此分三部分**：进消息的、附件、**过程中的帧**。
前两部分的读者是 agent，**帧的读者是人**——[agent 看不到帧](design.md#工具的产出)，
所以**帧发得再详细也不顶替结果**。
