# PF-008：Human in the Loop

- 修订：rev 6，2026-09-23 · [变更历史](changelog.md)
- 状态：rev 5 已正式接受；**rev 6 待产品负责人确认**；**一项待裁决**——见 [§9](#九未决项)

## 一、背景与问题

[PF-007](../PF-007-meta-capabilities/design.md#611-ask通向人) 定了 `Ask()` 这扇门：
agent 拿不准的时候怎么问人、动手之前怎么请示。但那写的全是 **agent 那一侧**——
问出去之后发生什么，那份设计停在一句「agent 停下来等」。

这段空着，四个问题没有答案：

- **停下来的到底是什么？**一次工具执行停住，和一个 run 停住，是同一件事吗？
  说不清，就没法回答「这个东西卡住了，我手上别的活还跑不跑」。
- **人在哪里看到这些问题？**散落在各个会话里，人得一个个点进去找吗？
  同时开着五个会话的人，怎么知道哪几个在等他。
- **答完怎么回去？**人在别处答的，怎么落回那个正在等的 run。
- **如果不是 agent 想问，而是系统认为该问呢？**agent 自己不觉得有问题，
  但这个动作危险。PF-007 提过有这么一个判断，**却没有它的落点**。

本 topic 回答这四个。

## 二、目标与非目标

### 目标

1. **定义 HITL**，以及它挂在哪些生命周期上。
2. **区分两个维度的等待态**，说清什么时候 run 跟着停、什么时候不跟着停。
3. **定义那个判断函数的产品职责**：什么时候跑、吃什么、吐什么。
4. **定义决策池**：卡片长什么样、怎么陈列、谁能答、答完怎么回去。
5. **说清一批卡片时「答完」是什么意思**，以及解除的是谁的阻塞。

### 非目标

| 不做什么 | 为什么 |
|---|---|
| `Ask()` 这扇门本身的命令与形状 | 归 [PF-007](../PF-007-meta-capabilities/design.md#611-ask通向人)。本 topic 接在它后面 |
| 等待态原语本身 | 归 [PF-006](../PF-006-tools-and-skills/design.md#等待态) |
| **Run 怎么被驱动、会话怎么建与怎么收束** | 分别归 [PF-012](../PF-012-agent-loop-and-run/README.md) 与 [PF-015](../PF-015-session-lifecycle-and-ownership/README.md)。本 topic 只引用，见 [§4](#只引用不拥有的两个对象) |
| 那个判断函数**怎么实现** | 产品只定它的职责与必须满足的性质 |
| 池子的**界面长什么样** | 产品定「人必须能做到什么」，不画界面 |
| 通知怎么送达（推送 / 邮件 / 红点） | 技术设计。产品只要求**人得知道有东西在等他** |
| 卡片在池子里怎么排序、怎么分组 | 同上。产品只要求**人找得到该他答的那张** |

## 三、用户与场景

| 使用者 | 什么时候接触这块 | 他关心什么 |
|---|---|---|
| **用户** | agent 停下来问他 | 它问我什么？我答了会发生什么？ |
| **同时开着好几个会话的人** | 手上一堆任务在跑 | 哪些在等我？先答哪个？答了哪个能接着跑 |
| **安全负责人** | 评估这个系统 | 危险动作会不会被拦下来给人看？拦的依据是什么 |
| **租户管理员** | 看全局 | 这个租户里有多少会话卡在等人 |
| **agent** | 每次运行 | 我问出去的那些问题，有答案了吗 |

**「同时开着好几个会话的人」最能体现这个池子的价值**——他不必挨个会话去看谁在等他。

但那是**场景**，不是**条件**：

> **所有需要人输入的等待，一律进池子，与当前有几个会话、活不活跃无关。
> 机制本身从不关心这件事。**

只有一个会话的时候池子照样在，只是人多半直接在会话里就答了——
**那是人的选择，不是系统的分支。**

这条得写明白，否则很容易长出一个「会话少的时候就不发卡片」的优化：
它省不下什么，却让**「东西在不在池子里」取决于一个会变的外部状态**，
而那种退化没人会注意到——直到有人发现某张卡片从来没出现过。

### 只引用、不拥有的两个对象

本 topic 绕不开这两样，但**只用到它们各自的几件事**。
它们的完整定义归 [PF-012](../PF-012-agent-loop-and-run/README.md)（Run 与 Agent Loop）与
[PF-015](../PF-015-session-lifecycle-and-ownership/README.md)（会话的生命周期与归属），
**本 topic 引用不改写**。
这与 [PF-004 的做法](../PF-004-agent-definition-and-assembly/design.md#三个只引用不拥有的对象)一致。

| 对象 | 本 topic 用到的 | 本 topic **不**说它 |
|---|---|---|
| **[Run](../PF-012-agent-loop-and-run/design.md#run)** | 它**有一个等待态**；它被阻塞、被解除；一次 llm 响应回来之后是它的一个节点 | 谁决定现在该跑、怎么推进、怎么收束 |
| **[会话](../PF-015-session-lifecycle-and-ownership/design.md#会话的生命周期)** | 卡片**归属于**某个会话；等待期间它**照常收消息、进队列**；[会话被归档](../PF-015-session-lifecycle-and-ownership/design.md#会话归档)时悬着的卡片一并清掉 | 会话怎么建、历史怎么存、**那个队列本身怎么运作** |

**写下这张表是为了防一件事**：把「run 卡在等人」和「会话被占住」当成同一件事。
**会话是长期的，run 是短暂的**——卡在等人的是 run，会话只是因此暂时不接新活。

### HITL

**一次执行停下来等人输入，人不输入就一直等着。**

三个词都要紧：

- **停下来**——不是轮询、不是重试，是真的停在那里；
- **等人输入**——等的是人，不是等时间，也不是等别的系统；
- **一直**——[没有上限](../PF-007-meta-capabilities/design.md#611-ask通向人)。

### 等待态的两个维度

> **停下来等人，这件事可以挂在两个不同的生命周期上。**

| | **tool 的等待态** | **run 的等待态** |
|---|---|---|
| 谁停下来 | **一次工具执行** | **一个 run** |
| 谁发起 | 工具内部的业务逻辑（[PF-006 的原语](../PF-006-tools-and-skills/design.md#等待态)） | **系统**（[放行判断](#放行判断)，在拿到一次 llm 响应之后算出来），**或一件[拓展件](../PF-012-agent-loop-and-run/design.md#拓展件)**——经 [PF-012 的那个原语](../PF-012-agent-loop-and-run/design.md#等人是-loop-的原语) |
| 解除 | 那次执行等到了它要的输入 | 那个 run 等到了它要的输入 |
| 对 run 的影响 | **看它在前台还是后台**（§5.1） | 直接停 |

两者能分开，是因为
[run 与工具执行的生命周期本来就解耦、可以异步](../PF-006-tools-and-skills/design.md#65-工具执行有自己的运行时绑定在-session-上)。

**`Ask()` 属于左边那一列。**run 之所以也停住，是因为它**恰好是前台调用**——
而不是因为这两个维度是同一件事。这个「恰好」是本 topic 的关键分辨，§5.1 展开。

**拓展件出卡等人，借的是右边那一列。**一件挂在 loop 上的[拓展件](../PF-012-agent-loop-and-run/design.md#拓展件)
要问人时，**没有哪一次工具执行可以承载这个等待**——它停住的是 run。
**它怎么停、协程没了之后怎么接着等**，归 [PF-012 的那个原语](../PF-012-agent-loop-and-run/design.md#等人是-loop-的原语)；
**停下来之后卡片进哪、谁能答、答完怎么算**，与右边那一列的其他卡片一样，归这里。

### 决策卡片

**一次需要人输入的请求，带齐让人当场就能判断的全部信息与选项。**

**「当场」是这个定义的重点**：人不必回到原来那个会话去翻上下文，
读这张卡片就够了。

### 决策池

**一个租户范围内，所有等着人输入的卡片，陈列在一处。**

**它是陈列，不是主体。**等的永远是某个会话里的某个 run 或某次工具执行；
池子只是把它们摆到一起，让人一眼看见。

> **不存在「组织在等什么」这回事。**组织不会等，**等的永远是某个会话**。

这个分辨很要紧。把池子当成主体，就会做出一个「组织待办中心」——
那是另一个东西：它会开始有自己的状态、自己的流转、自己的归属，
而**真正在等的那个 run 反倒被隔在一层之外**。

### 放行判断

**一个函数。**在一个 run 里，拿到一次 llm 响应之后跑（§5.2）。

它**既是判官也是撰稿人**：既算出要不要停，也写出给人看的那张卡片。

**它是系统自带的一件[拓展件](../PF-012-agent-loop-and-run/design.md#系统自带的几件各站在哪)**，站在执行动作之前；
出卡等人用的，**就是任何一件可否决拓展件都能用的[那一个原语](../PF-012-agent-loop-and-run/design.md#等人是-loop-的原语)**——
它不享受特权，**差别只在它的选项是定死的**（§5.2）。

**只有往严里走的两处限制是它独有的**，都定在 [PF-012](../PF-012-agent-loop-and-run/design.md#系统自带的几件各站在哪)：
**它不能被替换、禁用或收窄**——放行的权威只该有一个出处，能被同名替身顶掉或被配成只观察，出处就换了人；
**它此刻不可用时怎么办**，[还待产品负责人裁决](../PF-012-agent-loop-and-run/design.md#92-待产品负责人裁决)。

## 五、模型

### 5.1 三种情形，中间那一种最容易被漏掉

```text
前台工具进等待态   →   tool 停  +  run 跟着停      ← Ask() 就是这种
后台工具进等待态   →   tool 停  ,  run 照跑不误
系统算出来要问     →   run 停                      ← 这次响应里的工具一个都还没开始
（或一件拓展件要问）                                  ← 它站在 loop 的某个位置上，同样没有工具执行可承载
```

**中间那一行恰恰证明了两个维度必须分开**：一个转到后台的工具进了等待态，
它**同样需要人输入、同样该进池子**，但 run 不管它，接着干别的去了。

> **本版这一行不出现**：[要等应答的执行只在前台等](../PF-006-tools-and-skills/design.md#66-前台后台-与-等待态是两个维度)（产品负责人 2026-09-23 的本版限定，「但未来未必」）。
> **模型不因此收成两行**——它说的是两个维度为什么必须分开，这个理由不因为本版暂不用它而失效；将来打开，这里一个字不必改。

若把两个维度压成一个，这一行就没处安放——要么错误地把 run 也停掉
（后台的意义当场作废），要么让它不进池子（**那就没人知道它在等，它会永远等下去**）。

**第三行也只能挂在 run 上**：那一刻 llm 刚回话，**这次响应里的工具一个都还没开始**，
所以**没有对应的那次工具执行可以承载这个等待**。

（此刻**可能仍有后台执行在跑**——第二行说的就是这种。但它们与这个等待毫不相干，
承载不了它。**「有工具在执行」与「有那次工具执行」是两回事。**）

> **`Ask()` 让 run 停住，是前台/后台在起作用，不是新机制。**

### 5.2 那个判断函数

#### 什么时候跑

> **只看一件事——这次 llm 响应里有没有 tool calls。有才跑，没有就不跑。**

纯文本的响应不过这一关：**agent 只是在说话，它没有要动手，没什么可拦的。**

这条同时给了开销一个边界——**不是每次 llm 响应都要判一遍**。

#### 吃什么，吐什么

| | 内容 |
|---|---|
| **入** | 这次 **llm 响应**（被判断的对象）· **租户的权限清单** · [**会话授权上下文**](../PF-007-meta-capabilities/design.md#会话授权上下文) · **会话运行模式** |
| **出** | **要不要停下来、阻塞 run 往下走** · **给人的决策卡片**（说明 + 选项） |

后三样输入正是
[PF-007 定的「放行不由任何一样东西单独决定」那三样](../PF-007-meta-capabilities/design.md#611-ask通向人)。
**本 topic 给它们补上了第四样：被判断的对象本身。**

三样依据各自回答什么，[PF-007 已经定了](../PF-007-meta-capabilities/design.md#611-ask通向人)，
这里不重复。要紧的是它们**合起来**才得出结论——
这也解释了为什么同一个动作，在两个会话里可以一个放行、一个要问人。

#### 它同时是撰稿人，这一点很要紧

> **人签的是这个函数写出来的那段文字。**

所以那段文字写不清楚，这张卡片就是废的——**不是「信息少一点」，
而是人会在看不懂的情况下点同意**。§6.3 的两条要求由此而来。

#### 它吐出来的卡片，选项是固定的

说明由函数写，但**选项不是它写的，是定死的**：

| 选项 | 这一笔落在哪 | 活多久 |
|---|---|---|
| **不允许** | —— | 这个动作不做 |
| **这次允许** | 就这一次 | 动作做完即止 |
| **本会话内，这类情况都允许** | [会话授权上下文](../PF-007-meta-capabilities/design.md#会话授权上下文) | **这个会话往后一直有效**，[归档也不丢](../PF-015-session-lifecycle-and-ownership/design.md#67-归档不动授权) |
| **将来本租户所有会话，这类情况全允许** | [权限设置](../PF-002-assets-settings-and-permissions/design.md#52-设置与权限是资产的两种属性) | **长期，直到人再去改** |

**后三档正好是 [PF-007 定的那三个时间尺度](../PF-007-meta-capabilities/design.md#611-ask通向人)**——
不是新造的，是**把那三层直接摆到人面前让他挑**。

#### 为什么要把作用域摆成看得见的选项

**人本来就可以[用嘴说出任何一档作用域](../PF-007-meta-capabilities/design.md#会话授权上下文)**，
包括「以后所有会话都这样」。卡片的价值不在于**只有它才给得了长期**，
而在于它把那句话里说不出来的东西摆了出来：

| 用嘴说 | 这张卡片 |
|---|---|
| 作用域要靠系统**理解**他的意思 | **作用域是他自己按下去的那一档**，没有理解的余地 |
| 后果只能靠他自己想 | **后果就印在选项旁边** |

**越是作用域大的授权，这个差别越值钱。**所以在系统拦下一个危险动作的这个位置上，
**四档全部明码摆出来**——这是这张卡片存在的理由之一。

> **这不是说「用嘴说的不算数」。**算数，[PF-007 已经定了](../PF-007-meta-capabilities/design.md#会话授权上下文)。
> 这里做的是**在最该看清后果的地方，不让人靠一句话把事办了**。

#### 第三档和第四档各有约束

- **第四档（本租户所有会话）写的是租户的权限设置，因此受资格约束**：
  **只有有权改那份设置的人才选得了**。没这个权限的人，这一档不该出现在他的卡片上。

  否则就正是 [PF-007 点出的那个洞](../PF-007-meta-capabilities/design.md#611-ask通向人)——
  **会话里坐着的那个人，未必是设权限的那个人。**

- **第四档还要写得进去才出现**：租户那一层的权限设置能取什么值，受外层约束。
  组织把这类动作的执行权限收窄到不含「自动」时，第四档写下去也不生效——**这时它不出现**。
  一般地说：**一档选项只有在它会写下的那个值落在此刻允许的范围里时才出现**；
  摆一个按下去没有效果的选项，人会以为自己给了长期授权，下一次却照样被问。

- **明确禁止的动作根本走不到这里**：它在判断那一步就被否掉了，**不产生卡片**。
  **不存在「这件事禁止，但你可以选允许多久」这种问题。**

### 5.3 一批卡片，与「答完」是什么意思

一次停下来，可能产生**不止一张卡片**：

| 来源 | 几张 |
|---|---|
| [`Ask().ask` 一次问 N 个问题](../PF-007-meta-capabilities/design.md#611-ask通向人) | **N 张** |
| 一次 llm 响应里有 M 个动作被判定要人点头 | **M 张** |
| **一件或几件拓展件在同一次停下里各自出卡**（比如 M 个动作里有几个被租户挂的某一件拦下来问） | **各出几张算几张**，与放行判断出的卡[同一批](../PF-012-agent-loop-and-run/design.md#一批动作先全部判完再执行任何一个) |

**一批卡片答完之后，还可能有下一批。**拓展件在一个位置上是[依次过](../PF-012-agent-loop-and-run/design.md#三种形态两种装得进一种拆两半)的，
后一件要看前一件的结论——**前一件等人期间，后一件无从问起**。所以同一批动作可能先出一轮、答完再出一轮。
**每一轮都照这一节的规矩**：全答完才解除，答到一半什么都不发生。

**解除阻塞要求这一批全部答完**，而「答完」**包括人明确表示不回答**。

但必须说清**解除的是谁的阻塞**：

| 这一批卡片阻塞的是 | 全部答完之后 |
|---|---|
| 一次**前台**工具执行 | 那次执行继续，**run 也跟着继续** |
| 一次**后台**工具执行 | 那次执行继续，**run 本来就没停** |
| 一个 **run** | 那个 run 继续 |

**答到一半，什么都不会发生。**这不是设计上的将就：一个问了三件事的 agent，
只拿到两个答案就往下走，**那是拿着残缺的前提做决定**——
而它做出来的东西看上去和正常的一模一样。

### 5.4 一个会话，同一时刻最多一个 run 在等

因为[等待期间到达的消息进队列、由当前这个 run 在下一步消费](#62-等待期间照常收排队等着解除时一起看到)，**不会另起一个 run**。

**但同一个会话可以同时有别的东西在等**：那些转到后台的工具执行。
它们各等各的，互不影响，**也不影响 run**。

所以池子里出现同一个会话的好几张卡片是正常的，
而且**它们解除的东西不一样**——这正是 §6.6 要求卡片说清楚的原因。

### 5.5 两条入口，一件事

人可以在**原来那个会话里**直接答，也可以在**池子里**答。

> **这是同一件事的两个入口，不是两件事。**

**注意「在会话里答」指的是在会话里那张卡片上答，不是发一条消息。**
这一条消解了一个本来会很麻烦的歧义——等待期间用户发来的话，
到底是答复还是新的交代？**不必猜，也不必靠「当前有没有卡片挂着」去推测：
答复只在卡片上做，消息永远是消息。**

分成两件事的代价是立刻的：同一张卡片会有两套状态、两套规则，
而**「在会话里答了，池子里那张还在」**这种事一旦发生，人就再也不信任这个池子了。

因此：**一张卡片只能被答一次**，在哪儿答的都算数，答完两处一起消失。

## 六、产品规则

### 6.1 永远等着，系统不替人作答

没有超时，没有默认答案。「你不回我就当你同意」和「你不回我就当你拒绝」**同样不允许**。

这条继承自 [PF-007](../PF-007-meta-capabilities/design.md#611-ask通向人)，理由也一样：
**等待期间世界里什么都没发生**，不花钱的等待没有理由到点；
而一旦设了上限，就必须规定「到点算什么」——那就是替人签了字。

**直接后果**：卡片不会自己消失。清掉一张卡片只有两条路——
**人处理它，或者[那个会话被归档](../PF-015-session-lifecycle-and-ownership/design.md#会话归档)**。
堆在池子里是产品的正常状态，不是故障。
（**它等的那次执行已经因停机没了**的卡片怎么办，这两条都不覆盖，[待裁决](#91-待产品负责人裁决执行已经没了它的卡片怎么办)。）

**「人处理它」有两种形式，而不是一种**：

| 形式 | 它长什么样 | 入口 |
|---|---|---|
| **回复** | 人给出答案 | 在卡片上作答 |
| **明确拒绝回复** | 人表示「**这个我不答**」——[它解除那张卡片，也计入「答完」](#65-不回答是合法答复) | 在卡片上点「我不答这个」（**跳一张**）；或[发一条插队指令](../PF-014-inbound-intake-and-queueing/design.md#插队)（**解除运行等待态上悬着的全部**） |

> **展开这个词不是新增第三条路。**两种都是「人处理它」，
> **本节的穷举一个字没改**；变的只是把一个已有的词说全。

> **而这条穷举禁的到底是什么，要分清**：禁的是**没有事件也要给答案**（超时到点、默认答案），
> 是**系统替人作答**。**插队那一刻世界里发生了一件事，而且是人做的**——
> [时间流逝替人签字，和人自己改变主意，是两回事](../PF-014-inbound-intake-and-queueing/design.md#544-这没有推翻-pf-008它把一个词说全了)。

**这条对拓展件出的卡同样成立。**它不会自己消失、不会到点，清掉它同样只有那两条路——
**人处理它，或那个会话被归档**。

**「系统替人作答」也包括一件拓展件替人作答。**租户挂的拓展件是系统里的一段判断，不是人：
它在人看到卡片之前替人点「允许」、替人把答案填上，**和超时到点替人签字是同一种越权**。
所以——

| 拓展件想做的 | 在这里 |
|---|---|
| 替人答一张已经出的卡（别家 hook 里 `AskUserQuestion` 填答案、`Elicitation` 代填表单那一类） | **不允许** |
| 把放行判断算出的「问一下」直接改成放行（别家 `PermissionRequest` / `PreToolUse` 的 allow） | **不允许**——[没有「放宽」这一档](../PF-012-agent-loop-and-run/design.md#没有放宽这一档) |
| 从别家搬来的 hook 带着上面两种输出 | **一律只算「无意见」**，导入时明示给装它的人 |

> **这两条是一件事的两面**：卡片上的答案只能来自人，**放行只能来自权限与人给的授权**。
> 一件拓展件能做的是**收紧**（否决）或**多问一句**（自己出一张卡），不能替人把这一关跨过去。
> 想让某类动作不再问人，**是有资格的人去把那项执行权限配成「自动」**，不是装一件替人点头的拓展件。

### 6.2 等待期间照常收，排队等着，解除时一起看到

一个 run 停下来等人的时候，那个会话**照常接收**——用户发来的新消息、
后台执行完成的通知，**都收下**。

**收下不等于立刻处理**：它们**进队列等着**，在阻塞解除、
agent 走下一步的时候**一起被它看到**。

#### 为什么不能挡

| 挡回去会怎样 |
|---|
| **用户发来的新消息**——那是他的**主动意图**。挡回去等于告诉他「你现在不能说话」，而他多半只是**忘了还有卡片要答** |
| **后台执行完成的通知**——拒收它是荒谬的：那次执行是**这个 run 自己发起的**，转后台时[位置上还留着占位](../PF-006-tools-and-skills/design.md#66-前台后台-与-等待态是两个维度)。**那不是打扰，那正是它自己在等的东西** |

第二行尤其硬。一个 run 卡在等人，同时它先前转到后台的活干完了——
**把这个完成通知挡在门外，等于让它永远收不到自己要的结果。**

#### 用户那条要配一个弱提示

告诉他：这个会话要继续，还需要他答几张卡片。

**「弱」是关键**——不是拦截、不是弹窗、不是报错，就是一句
「这边还有 N 张在等你」。

> **挡住人说话，和提醒人还有事没做，是两件完全不同的事。**
> 前者让人觉得系统在跟他较劲，后者让人想起来该去处理。

#### 新消息不另起 run

它在队列里等着，**被当前这个 run 在下一步消费**——
所以[一个会话同一时刻最多一个 run 在等](#54-一个会话同一时刻最多一个-run-在等)仍然成立。

**队列本身归 [PF-014](../PF-014-inbound-intake-and-queueing/README.md)**，
本 topic 只定这里的行为：**照收、排队、一起交付**。

#### 中断不排队

中断**不是消息，是控制动作**，它立即生效。

这条路必须始终开着，否则用户就被自己的 agent 锁死了。
中断走 [PF-006 那条](../PF-006-tools-and-skills/design.md#67-用户可以中断而中断不是失败)：
**记为被中断，不是失败。**

### 6.3 卡片自包含，但要留得住溯源的路

**自包含**：人读这张卡片就够了，不必回到原会话去翻上下文。

**但「通常不必回去」不等于「不许回去」**——卡片必须能溯源回它所属的会话。

理由直白：那段说明是[一个函数写出来的](#52-那个判断函数)，它可能写偏、写漏。
**堵死溯源，人就只能在看不懂的时候二选一：瞎点，或者干脆不管。**
两条都是坏的。

### 6.4 两个答复入口，一张卡片只能答一次

见 §5.5。**在哪儿答的都算数，答完两处一起消失。**

### 6.5 「不回答」是合法答复

人可以明确表示**这个我不答**。这会解除那张卡片，也计入「答完」。

但 agent 拿到的是**「没有答案」，不是失败**——
它据此自己决定怎么办（改道、收尾、或者如实告诉用户做不下去了），
**而不是重试一个人刚刚拒绝回答的问题**。

> **人不想答，和人答不上来，和系统出错了，是三件不同的事。**

### 6.6 卡片要让人看出「答了它会解除什么」

人在池子里看着五张卡片，他会想知道：**我答了这张，那个任务是不是就接着跑了？**

看不出来的话，他只能一张张试——而**试错在这里是昂贵的**，
因为每一张卡片背后都可能是一个正在等的、跑了很久的任务。

由 §5.3 那张表，答案有三种：解除一次前台执行（run 跟着走）、
解除一次后台执行（run 本来就在跑）、解除一个 run。**卡片上要能看出是哪一种。**

**拓展件出的卡解除的是一个 run，但要说实话**：答完这一批，那个 run 可能[接着又停在下一轮](#53-一批卡片与答完是什么意思)——
卡片不能让人以为「答了这张它就一定跑起来」。

### 6.7 租户隔离在池子上成立

池子是**租户范围**的。一个人属于多个租户，他在各租户的卡片
**分属各自的池子，不混在一起**——[跨租户默认拒绝](../PF-001-identity-scope-and-agent-constraints/design.md#租户)在这里同样成立。

**谁能答一张卡片，跟他能不能访问那个会话是同一个判断**，不新开一套资格面。
同一概念只定义一次；在这里另立一套「答复资格」，
两套规则迟早会在某个边角上给出不同答案。

### 6.8 三种来源的卡片，同一个形状；选项与记录不同

**卡片有三种来源**：**agent 发起**、**系统发起**（[放行判断](#52-那个判断函数)）、**拓展件发起**
（租户或组织挂在 loop 上的一件[可否决拓展件](../PF-012-agent-loop-and-run/design.md#干预力三档直接用-pf-000-的)）。

**「形状一样」指的是**：都是一张**带说明、带选项、可自由作答**的卡片。
人不必去理解「这张是 agent 问的、那张是系统拦的、另一张是租户的某条规矩要问的」——
**那是把系统内部的结构负担转嫁给他。**

**但选项集本来就不同**，而且这不需要向人解释：

| 卡片 | 选项 | 谁写 |
|---|---|---|
| [`Ask().ask`](../PF-007-meta-capabilities/design.md#611-ask通向人) | **agent 自己写的候选项** | agent |
| [`Ask().request_approval`](../PF-007-meta-capabilities/design.md#611-ask通向人) | 同意 / 不同意 | 定死的 |
| **系统拦下来的** | 不允许 / 这次 / 本会话 / 本租户（[§5.2](#52-那个判断函数)） | **定死的** |
| **拓展件出的** | **出卡的那一件自己写**；人照样可以自由作答 | 那一件拓展件 |

**人看到什么选项，取决于这张卡片在问什么**——本来就该不一样。
要一致的是**卡片这个东西的样子**，不是它的内容。

> **拓展件的选项由它自己写，是「租户自己定人机协作」的全部落点**：
> 「这条命令动了生产库，要不要只读执行」「这份合同要不要先给法务看」——
> 选项是什么、答了之后怎么办，**都是那一件的事**；本 topic 只保证它和别的卡片一样被陈列、被答、被算进一批。
> **它写的选项不能替人跨过权限那一关**：选了「允许」，那一件能做的也只是**不再拦**，
> 放行判断那一关照样要过（[§6.1](#61-永远等着系统不替人作答)）。

**从别家搬来的 hook 出的卡，选项借的是放行判断那四档的样子，但不带授权含义。**
人在这张卡上选哪一档，都只是**对那一件搬来的 hook 的答复**：它据此不再拦这一次，
**不写[会话授权上下文](../PF-007-meta-capabilities/design.md#会话授权上下文)，也不写权限设置**。
**卡片样式上必须与系统拦下来的那种分得开**——否则同一个动作上，人会先后看到两张选项同名、含义不同的卡：
一张选了「本租户都允许」真会写进权限，另一张选了什么都不留下，**而他分不出自己按的是哪一张**。

**记录里必须分得出来源，拓展件出的还要标出是哪一件。**三者的性质差很远：

| | agent 发起 | 系统发起 | 拓展件发起 |
|---|---|---|---|
| 谁认为该问 | **agent 自己** | **系统**，agent 并不觉得有问题 | **租户或组织定的一条规矩**，agent 与系统的权限判断都不觉得有问题 |
| 说明谁写的 | agent | [那个函数](#52-那个判断函数) | **那一件拓展件** |
| 记录里标什么 | 来源 | 来源 | 来源，**以及是哪一件** |
| 审计时意味着 | agent 在谨慎行事 | **有个动作被拦下来了** | **有个动作碰到了租户自己的规矩**——哪条规矩拦得最多、谁在答，按那一件就查得出 |

系统发起的是安全事件的线索，agent 发起的不是。混在一起，审计就看不出「这个 agent 频繁触碰危险动作」；
**拓展件发起的不标是哪一件，租户就说不清自己哪条规矩在起作用**，也没法判断它该不该留。

### 6.9 人拒绝之后，agent 分得出那是拒绝

一个动作被人否掉，agent 拿到的必须是**「人不同意」**，
而不是一个看起来像执行失败的结果。

**拓展件出的卡同理**：人答了之后，是那一件据答复下结论——它若因此否掉这个动作，
agent 拿到的是**「不许做」及其来由**（哪一件、依据的是人的哪一笔答复），同样不是执行失败。

混在一起，agent 会**重试一件人刚刚否掉的事**——
而且它会觉得自己在尽职尽责。这与 [PF-006 六种收场](../PF-006-tools-and-skills/design.md#55-一次工具执行的收场有六种)
要「分得开」是同一条道理。

## 七、取舍

| 选择 | 取的 | 舍的 |
|---|---|---|
| **两个维度的等待态分开** | 后台工具的等待有地方安放；run 不被无谓地停住 | 概念上多一层，读者要先分清「谁停了」 |
| **永远等，不设上限** | 系统永远不会替人作答 | 卡片会堆积，且**产品得另想办法让人知道有东西在等他** |
| **等待期间照收、排队，不挡** | 用户随时说得上话；后台执行的完成通知进得来 | 解除阻塞时，agent 要一次面对攒下的一批东西，而不是干干净净一条 |
| **池子是陈列，不是主体** | 真正在等的那个 run 没有被隔开 | 池子没有自己的状态可管，一些"待办中心"式的功能长不出来 |
| **一批卡片全答完才解除** | agent 不会拿着残缺的前提往下走 | 人答到一半就走开的话，**什么都不会发生** |
| **卡片自包含** | 人不必回原会话翻上下文 | 那段说明的质量成了关键路径——**写砸了人就在看不懂的情况下签字** |
| **三种来源形状一样** | 人不必理解系统内部结构 | 得靠记录而不是靠界面来区分，审计要多走一步 |
| **拓展件的卡由它自己写选项** | 租户能按自己的规矩定人机协作，**不必等系统加一种卡** | 选项写得好不好落在拓展件作者身上；**同一批动作可能有第二轮卡片** |
| **拓展件不能替人作答、不能把「问一下」变放行** | 卡片上的答案只来自人，放行只来自权限与授权 | 别家「hook 替人放行 / 代答」的用法搬不过来 |
| **搬来的 hook 出的卡借四档的样子，但不带授权含义** | 授权只有放行判断那张卡一个入口 | 同样的四档，两种含义，**只能靠样式让人分清** |
| **一档选项写得进去才出现** | 人按下去的每一档都真的生效 | 同一类动作在不同组织下，卡片上的档数不一样 |
| **答复资格跟会话访问权一致** | 不新开一套资格面 | 想让"不能访问会话但能审批"的角色存在，本版做不到 |

**第二行值得多说一句**：不设上限是一条硬规则，但它把一个问题推给了产品——
**人怎么知道有东西在等他**。池子解决的是「找得到」，不是「知道」。
通知归技术设计，但**产品要求它必须存在**：没有通知，
「永远等着」就会变成「永远没人管」。

## 九、未决项

### 9.1 待产品负责人裁决：执行已经没了，它的卡片怎么办

**情形**：据点停机时，一次执行正停在 [`Ask()`](../PF-007-meta-capabilities/design.md#611-ask通向人) 上等人。
恢复时这次执行[落失败、原因「异常中断」](../PF-006-tools-and-skills/design.md#停机之后它不重来)——**它已经终局了**，
而它出的卡片还挂在池子里。[§6.1](#61-永远等着系统不替人作答) 清卡只有两条路（人处理、会话归档），**这一种不在其中**。

| | 怎么办 | 长相 | 代价 |
|---|---|---|---|
| **甲** | **恢复对账时，把阻塞的执行已经终局的卡片关掉**，标明「它等的那次执行已经没了」 | 池子里不留一张答了也没用的卡 | §6.1 的穷举**多一条清卡的路**；它不是超时、不是替人作答——关卡的依据是一件已经发生的事（执行没了），不是时间流逝 |
| **乙** | **卡片照挂**；人答了，答复到达时按「那次执行已终局」丢掉，并告诉他 | §6.1 一个字不改 | 人会去答一张注定没用的卡，**答完才知道白答了**；池子里的卡不再都是「答了有用」的 |

**PM 倾向甲**：池子的价值在于「每一张都值得答」，乙让人替一件已经没了的事花判断；
甲多出的那条路与「系统不替人作答」不冲突——它关的是一张**没有人在等**的卡，不是替谁作了答。
**两种长相不同，且改的是 §6.1 那条穷举，所以不自定**；在裁决之前，不要在实现里自己发明一套清卡规则。
