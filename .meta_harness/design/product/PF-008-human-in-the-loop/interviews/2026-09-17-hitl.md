# 2026-09-17 · HITL

**这是原始材料，不是结论。**产品事实见 [decisions.md](../decisions.md)。

本篇按发生顺序记录。**产品负责人的 `quote` 一律保留原话，不回改**——
包括其中被后来修正掉的说法，那正是这份记录的价值。

## INT-001 开题：四条需求

> **quote**：「接下来谈 PF-008，是对 HITL 的产品设计。大的模型上，有这几点产品需求：
> 1）HITL 的定义是一次 run 执行到了一个地方，然后它停下来等待用户的输入，用户不输入，
> 这个 run 就永远处于那个等待态；2）这个等待的出发，可以是 agent 通过调用工具（也就是
> PF-007 里的 Ask 工具），也可以是系统（这个业务逻辑的执行点位是在一个 run 中，拿到一次
> llm call 的 response 之后，至于是通过 hook 还是直接在 loop 中编码这个阶段，产品设计
> 不决策）通过一段「计算」后发起等待；3）产品上要求有一个集中的决策处理池，所有 session
> 的所有 run 中的无论是 agent 发起的还是系统计算发起的需要等待人进行输入的，在这个池子
> 里面都以自包含完整上下文信息和选项的卡片形式陈列，人点进一张决策卡片并在卡片上完成
> 答复后，结果要能够自动回传回对应的 session（或 session 的那个 run）；4）一次 run 可能
> 有多个需要人决策（比如 ask 允许问多个问题，那每个问题对应就会在决策池里面多一张卡片），
> 解除阻塞必需所有卡片完成答复（或者用户点击不回答/拒绝回答）。」

四条构成了本 topic 的骨架。**「产品设计不决策」那一句被原样接住**，写进了 §2 非目标。

## INT-002 PM 提出三个问题，两处答案带纠正

PM 先自行筛掉了一批能推出来的（卡片四个出口与 PF-007 同形、两个答复入口同一件事、
答复资格跟会话访问权一致、拒绝回答是合法答复、一个 run 同时刻只有一批卡片来源单一、
卡片不会自己消失），只把三个真有多解的交上去。

**问题一：一个 run 停下来等人的时候，那个会话还收不收新的任务输入？**

> **quote**：「只收答复与中断」

采纳，落进 §6.2。**代价写进取舍**：用户连插一句「先别管那个」都不行。

**问题二：系统计算发起的那种等待，卡片上的「完整上下文」从哪里来？**

PM 给的三个选项是「只用拦下的那次调用」「骨架 + 从上下文取 agent 的意图」
「要求工具调用自带说明」。产品负责人的答案不在其中：

> **quote**：「我们在 PF-007 的讨论的时候有提到说有一个模型来计算，就是这里，
> 这个模型不进算出来要不要人裁决，还会生成人能理解的说明信息」

**这个答案改变了问题的性质**：说明不是「取」来的，是**那个函数写出来的**。
由此推出 §5.2 的一句要害——**人签的是这个函数写出来的那段文字**——
以及 §6.3 的两条要求（自包含，但溯源不能堵死）。

**问题三：这个集中的决策池，是谁的池子？**

> **quote**：「租户池子，但理由不是你给的选项3的，因为我们说了这个等是一个会话在等，
> 所以不存在「组织在等什么」这个概念」

**结论与 PM 的推荐一致，但理由被推翻。**PM 在选项里把「组织视图」的价值描述成
「让管理员看得见全组织有多少 run 卡在等人」——那个描述的前提就是错的。
这条纠正直接长成了 §4「决策池」里的一句定义：**池子是陈列，不是主体**。

## INT-003 关键纠正：等待态是两个不同生命周期维度上的

PM 在回复里提出「HITL 是 run 级的，PF-006 的等待态只是它的成因之一」。这被纠正：

> **quote**：「另外关于等待态，你需要区分，因为我们说过 run 的生命周期、agent 的生命周期、
> tool 等生命周期，是解耦的是可以异步的，所以这里的等待态是两个不同的生命周期维度上的，
> 系统发起的是 run 的等待态，ask tool 发起的（也就是 tool 的等待原语）是 tool 的等待态，
> 只是刚好在 ask 这个场景下，导致了 run 也进入了等待态」

**「刚好」这个词是整条纠正的关键。**`Ask()` 让 run 停住，是
[前台/后台](../../PF-006-tools-and-skills/design.md#66-前台后台-与-等待态是两个维度)
在起作用，**不是因为两个维度是同一件事**。

PM 据此重做了模型，并掉出了一个之前没看到的情形——**后台工具进等待态：
tool 停，run 照跑**。它同样需要人输入、同样该进池子，但不阻塞 run。
这一行是两个维度必须分开的证据（§5.1）。

处置：PM 原来那个判断记进 [decisions 第四节](../decisions.md#四已知的来源问题)，
**不静默改掉**。

## INT-004 那个「模型」，在产品上就是一个函数

> **quote**：「这个「模型」你可以理解就是系统在run中拿到 llm call response 后，
> 将 llm call response、tenant permission context、session user approvals context、
> session run mode 作为输入的一个函数，你在产品上就这么理解就行了，这个函数的输出是
> 判断当前是否要进入等待态阻塞run执行下一步、给人的决策卡片（解释说明和选项）」

**四进二出**，写进 §5.2。

值得记的一点：后三样输入正是
[PF-007 定的「放行不由任何一样单独决定」那三样](../../PF-007-meta-capabilities/design.md#611-ask通向人)。
本 topic 补上的是**第四样——被判断的对象本身**。所以两份设计不冲突，
是同一个东西的两个视角。

「**你在产品上就这么理解就行了**」这半句同样重要：它划掉了把这个函数
神秘化成「未来的分类模型」的余地——**产品上它就是一个函数，不多不少**。

## INT-005 触发条件：有没有 tool calls

> **quote**：「然后这个 函数 是否执行的判断条件是 llm call response 是否包含 tool calls
> （也就是回答你的第二个问题，纯文本回复要不要计算，答案是不要）」

这同时回答了 PM 早先问的「纯文本回复要不要过这个模型」。

产品上的读法：**agent 只是在说话，它没有要动手，没什么可拦的。**
副产品是给开销划了边界——不是每次 llm 响应都要判一遍。

## INT-006 机制统一，不看会话数

PM 在 §3 写了一句「『同时开着好几个会话的人』是这个 topic 真正的服务对象。
只有一个会话的话……根本不需要池子」。被指出有过度设计的诱导风险：

> **quote**：「话是对的，但这样表述会让系统设计者看到之后存在过度设计风险，因为它会想，
> 那我设计的时候要不要考虑当前活跃的会话数量的问题来决定卡片往不往池子发呢。而实际上
> 我们的统一模型是都有发，和有几个会话无关，也就是机制本身从来不关心有多少个会话在活跃中」

**这是一条关于「怎么写」的纠正，不是关于「是什么」的**——
但它照样改变了正文：把那句话从**看似的条件**改回**纯粹的场景**，
并在验收里加了一条红线（按活跃会话数决定发不发）。

值得记下的判断方法：**一句描述价值的话，若读起来像判据，它就会被实现成判据。**

## INT-007 关于后续安排

> **quote**：「PF-008 设计完后，记得提醒我一下，接下来的几块产品设计是和 agent-loop
> 以及 session、inbound 相关的，会是多个 PF 而不是单个」

这条直接影响了本 topic 对 **Run 与会话**的处理方式：既然它们的完整定义要到后面
**多个** topic 才落定，本 topic 就按
[PF-004 的先例](../../PF-004-agent-runtime-assembly-and-liveness/design.md#两个只引用不拥有的对象)
**只引用、不拥有**，并写明用到它们的哪几件事（§4）。

## INT-008 改判：等待期间不是拦下，反而就是排队

PM 按 INT-002 的作答写了 §6.2「只收答复与中断，新任务明确挡下」。**当天被推翻**：

> **quote**：「『发来的新任务被**明确挡下并说明原因**，不是悄悄排队、也不是被当成答复。』
> 这里我们需要的（人因工程角度）不是拦下，反而就是排队。你想这几种情况：
> 1）用户忘记答复但是发来新消息，这是用户的主动意图，消息还是能发，进响应队列，
> 弱提示告诉用户这个会话要继续执行还需要 ta 答复几个决策卡片；
> 2）run 在等待态，但是后台工具执行完了，通过 system reminder 类型的消息
> （因为后台执行的工作在转后台的时候，会是先用 ToolMessage 占位）返回了，
> 当然不能拒收啦，肯定是进 buffer 或者队列，next step 的时候消费进来然后
> agent 下一步执行的时候（解除阻塞态）消息一起它都看得到」

**第二个场景是决定性的**：后台执行的完成通知是**这个 run 自己等的东西**，
转后台时位置上还留着占位。挡在门外，它就永远收不到结果。

**更该记的是 PM 给选项时的疏漏**：选项描述把「歧义为零」写成了挡下来的主要收益，
**而那个歧义另有解法**——答复只在卡片上做，消息永远是消息，
不必像 legacy 那样靠「有没有 outstanding request」去猜自由文本。
**PM 当时没想到这条，于是把一个可解的问题写成了取舍。**

处置：改判与这处疏漏都记进 [decisions 第四节](../decisions.md#四已知的来源问题)。

## INT-009 系统拦截的卡片：选项固定，四档授权

> **quote**：「噢对了，系统拦下来后出的那个卡片（也就是那个函数的返回的决策卡片，
> 选项是固定的，这次允许、本会话内接下去这类情况都允许、
> 将来本租户所有会话这类情况全允许）」

**后三档正好是 [PF-007 的三个时间尺度](../../PF-007-meta-capabilities/design.md#611-ask通向人)**——
这一版把那三层直接摆到人面前让他挑。

PM 据此推了三条（都在 [decisions 第二节](../decisions.md#二pm-推导)）：
**还要有「不允许」这一档**（否则这一关退化成「问你允许多长」而非「问你允不允许」）、
**第四档受资格约束**、**被明确禁止的动作不产生卡片**。

**它与 PF-007「不得静默升格」的关系值得记**：不冲突，**分界是「明不明确」**——
那里禁的是把一句顺口话由系统解释成长期授权，这里是人看着标好后果的选项按下去。

> **禁的是系统替人解释，不是禁止人给长期授权。**

但 PF-007 的措辞（「长期授权只能从设置与权限走」）会误导，
已记为**上游欠账**，等产品负责人授权再动。
