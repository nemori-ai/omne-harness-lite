# PF-008 流程与状态

`design.md` 说等待与池子**各是什么**，这里说它们**怎么动**。

## 一、主要旅程

### 1.1 agent 问人，人就在跟前

**最短的那条路，也是最常走的。**

| 步骤 | 发生什么 |
|---|---|
| 1 | agent 调 [`Ask().ask`](../PF-007-meta-capabilities/design.md#611-ask通向人)，一次问了三件事 |
| 2 | 这次工具执行进入 **tool 的等待态**；因为是前台调用，**run 也跟着停** |
| 3 | 池子里出现**三张卡片**，原会话里也看得见这三张 |
| 4 | 人就在这个会话里，**当场把三张都答了** |
| 5 | 三张全答完 → 那次工具执行拿到结果继续 → **run 跟着继续** |

**第 3 步的两处不是两件事**：同一批卡片，两个入口
（[§5.5](design.md#55-两条入口一件事)）。

### 1.2 人不在跟前，去池子里答

| 步骤 | 发生什么 |
|---|---|
| 1 | 同上，三张卡片挂着，**run 一直等着** |
| 2 | 人早就关掉那个会话去干别的了 |
| 3 | **通知到达**——他知道有东西在等他 |
| 4 | 打开池子，看见的是**这个租户里所有在等他的卡片**，可能来自好几个会话 |
| 5 | 点进一张，**卡片自带完整说明与选项**，不必回原会话翻上下文 |
| 6 | 答完三张 → 结果**自动回传**到那个 run → 它接着跑 |

**第 3 步没有的话，「永远等着」就变成「永远没人管」。**

**第 5 步是池子的全部价值**：没有自包含，人在第 5 步就得回原会话，
那池子只是个索引，省不了事。

### 1.3 系统拦下一个动作

| 步骤 | 发生什么 |
|---|---|
| 1 | agent 想干一件事，**它自己不觉得有什么问题** |
| 2 | llm 响应回来，**里面有 tool calls** → [判断函数](design.md#52-那个判断函数)跑起来 |
| 3 | 它拿这次响应，加上租户权限清单、会话授权上下文、会话运行模式，一起算 |
| 4 | 算出来：**这个动作要人点头**，同时**写出给人看的说明与选项** |
| 5 | **run 进入等待态**——注意此刻**一个工具都还没开始执行** |
| 6 | 卡片进池子，与 agent 自己问的那些**长得一样** |
| 7 | 人点「同意」→ 动作执行，这笔同意进[会话授权上下文](../PF-007-meta-capabilities/design.md#会话授权上下文) |
| 8 | 人点「不同意」→ **agent 拿到的是「人不同意」**，不是执行失败 |

**第 5 步只能挂在 run 上**——那一刻没有任何「一次工具执行」可以承载这个等待。

**第 8 步是硬的**：混成失败，agent 会重试一件人刚否掉的事，
而且它会觉得自己在尽职尽责。

### 1.4 纯文本响应：这条路根本不走

| 步骤 | 发生什么 |
|---|---|
| 1 | llm 响应回来，**里面没有 tool calls**，agent 只是在说话 |
| 2 | **判断函数不跑** |
| 3 | run 照常往下走 |

**agent 没有要动手，没什么可拦的。**这条同时给了开销一个边界。

### 1.5 答到一半走开了

| 步骤 | 发生什么 |
|---|---|
| 1 | 三张卡片，人答了两张，去忙别的了 |
| 2 | **第三张还挂着** |
| 3 | **run 一直等着**——两张的答案不会被送出去 |
| 4 | 一小时后人回来，答掉第三张 |
| 5 | 这时三个答案**一起**回到那个 run，它继续 |

**第 3 步不是将就**：一个问了三件事的 agent，只拿到两个答案就往下走，
**那是拿着残缺的前提做决定**——而它做出来的东西看上去和正常的一模一样。

### 1.6 后台的工具在等，run 照跑

| 步骤 | 发生什么 |
|---|---|
| 1 | 某个工具执行转到了后台 |
| 2 | 它内部跑到一处，**进入等待态**，需要人输入 |
| 3 | 卡片进池子 |
| 4 | **run 完全不受影响**，接着干别的 |
| 5 | 人什么时候答，那次后台执行什么时候继续 |
| 6 | 人一直不答 → **它就一直等着**，而 run 可能早就结束了 |

**这条旅程是两个维度必须分开的证据。**压成一个的话，第 4 步就不成立。

**第 6 步要留意**：run 结束了，那次后台执行还在等——
它的结果最终回到 **session**（[PF-006](../PF-006-tools-and-skills/design.md#65-工具执行有自己的运行时绑定在-session-上)），
不是回到那个已经结束的 run。

### 1.7 人明确表示不答

| 步骤 | 发生什么 |
|---|---|
| 1 | 人点进卡片，觉得这个问题他答不了、或者不想答 |
| 2 | 点「**不回答**」 |
| 3 | 这张卡片**解除**，计入「答完」 |
| 4 | 那一批全部了结之后，agent 拿到的是**「没有答案」** |
| 5 | agent 自己决定：改道、收尾、或者如实告诉用户做不下去了 |

**第 4 步不是失败。**人不想答、人答不上来、系统出错了——**这是三件不同的事。**

### 1.8 用户直接叫停

| 步骤 | 发生什么 |
|---|---|
| 1 | 人觉得这件事压根不该做 |
| 2 | **中断整个 run** |
| 3 | 那一批卡片**一并清掉**，池子里不留孤儿 |
| 4 | 记为[**被中断**，不是失败](../PF-006-tools-and-skills/design.md#67-用户可以中断而中断不是失败) |

**这条路必须始终开着**——否则会话只收答复与中断的规则会把用户锁死在
一个他根本不想继续的任务里。

## 二、异常分支

| 分支 | 怎么处理 | 为什么 |
|---|---|---|
| **卡片挂了很久没人答** | **就一直挂着**，run 一直等 | 不设上限、不替人作答。这是正常状态，不是故障 |
| **等待期间用户在会话里发了个新任务** | **明确挡下并说明原因**，不排队、不当成答复 | 悄悄排队的话，用户以为自己交代了事情，其实什么都没发生 |
| **同一张卡片，会话里和池子里都点了答** | **只算第一次**，另一处随即消失 | 一张卡片两套状态，人就再也不信任这个池子了 |
| **人在池子里看到一张看不懂的卡片** | **能溯源回原会话** | 说明是函数写的，可能写偏。堵死溯源，人只能瞎点或者不管 |
| **会话走到终态，卡片还挂着** | **一并清掉**，不留孤儿 | 与 [PF-007 的第四个出口](../PF-007-meta-capabilities/design.md#611-ask通向人)同形 |
| **run 结束了，某个后台执行的卡片还挂着** | **照样挂着**，它等的不是那个 run | 结果最终回到 session |
| **人拒绝了一个动作** | agent 拿到**「人不同意」** | 混成失败，agent 会重试一件人刚否掉的事 |
| **人对一张卡片点「不回答」** | 解除它，计入答完；agent 拿到**「没有答案」** | 不是失败，也不是被拒 |
| **llm 响应里没有 tool calls** | **判断函数不跑** | agent 只是在说话，没什么可拦的 |
| **判断函数写出来的说明含糊不清** | **产品缺陷，不是可接受状态** | 人签的是那段文字。看不懂还签，等于没有这一关 |
| **人同时属于两个租户** | 两边的卡片**分属各自的池子，不混** | 跨租户默认拒绝 |
| **有人想答一张他访问不了那个会话的卡片** | **答不了**，他也看不到它 | 答复资格跟会话访问权是同一个判断 |
| **判断函数算出「要问」，但卡片生成失败** | **仍然停住**，并明确告知人这里出了问题 | 生成不出说明就放行，等于让最危险的那次调用绕过了这一关 |

**最后一行值得多看一眼**：失败时的方向要选对——
**这一关的失败必须是「停下来」，不能是「放过去」。**

## 三、状态流转

### 3.1 一张决策卡片

| 状态 | 能转到哪 | 谁触发 |
|---|---|---|
| **等着** | 被答复 / 被拒答 / 随 run 被中断清掉 / 随会话终态清掉 | 人，或生命周期 |
| 以上四种 | 终态 | —— |

**「等着」这个状态没有超时出口。**它可以停留任意久
（[§6.1](design.md#61-永远等着系统不替人作答)）。

**四个出口与 [PF-007 的问询出口同形](../PF-007-meta-capabilities/design.md#611-ask通向人)**，
不另立一套。

### 3.2 一批卡片

| 状态 | 怎么变 |
|---|---|
| **还差几张** | 答掉一张，少一张 |
| **全了** | 最后一张答完的瞬间 |
| **作废** | run 被中断，或会话终态 |

**只有「全了」才触发解除。**「还差几张」是个稳定状态，可以停留任意久。

### 3.3 被阻塞的那个东西

| 阻塞的是 | 解除之后 |
|---|---|
| 一次**前台**工具执行 | 那次执行继续，**run 跟着继续** |
| 一次**后台**工具执行 | 那次执行继续，**run 本来就在跑** |
| 一个 **run** | 那个 run 继续 |

**三种情形的差别不在人这一侧**——人只是答了一批卡片。
差别在**解除了什么**，而[卡片要让人看得出来](design.md#66-卡片要让人看出答了它会解除什么)。

## 四、谁决定什么

| 事情 | 谁决定 | 谁不能决定 |
|---|---|---|
| **要不要停下来问人**（agent 那条路） | **agent** | 系统不替它决定什么该问 |
| **要不要停下来问人**（系统那条路） | **[判断函数](design.md#52-那个判断函数)** | agent 不知道、也挡不住 |
| **判断函数跑不跑** | **这次响应里有没有 tool calls** | 没有商量余地 |
| **人回答了什么** | **人**，而且只有人 | 系统不替人作答、不替人解释 |
| **一张卡片等多久** | **没人定，因为不设上限** | 谁都不能规定「到点算什么」 |
| **一批卡片什么时候算答完** | **全部了结**（含明确不答） | 不能答一半就放行 |
| **在哪里答** | **人**：会话里或池子里都行 | 但**只能答一次** |
| **谁能答某张卡片** | 跟**他能不能访问那个会话**同一个判断 | 不另开一套资格面 |
| **等待期间会话收不收新任务** | **不收。**只收答复与中断 | agent 与用户都改不了这一条 |
| **叫停整个 run** | **用户**，任何时候 | 这条路必须始终开着 |
| **卡片什么时候消失** | **人处理它，或会话终结** | 它不会自己消失 |
| 卡片归哪个池子 | **它所属会话的租户** | 跨租户不混 |

**「不设上限」与「只收答复与中断」这两条合起来，会把用户锁死**——
所以**中断那一行是这张表的安全阀**，删掉它，整套设计就不成立。
