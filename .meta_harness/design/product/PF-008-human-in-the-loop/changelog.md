## rev 1 — 2026-09-17

**首版。**接在 [PF-007](../PF-007-meta-capabilities/README.md) 后面——
那份设计定了 agent 怎么问人，停在一句「agent 停下来等」；
**等待怎么被承载、人在哪里答、答复怎么回传**，本 topic 回答。

### 这一版确定了什么

| 方面 | 结论 |
|---|---|
| HITL 是什么 | 一次执行停下来等人输入，**人不输入就一直等着** |
| 等待挂在哪 | **两个维度**：tool 的等待态、run 的等待态。两者解耦 |
| `Ask()` 属于哪个 | **tool 的**。run 跟着停是因为它**恰好是前台调用** |
| 系统那条属于哪个 | **run 的**。那一刻**这次响应里的工具一个都还没开始执行** |
| 判断函数什么时候跑 | **只看这次 llm 响应里有没有 tool calls**。纯文本不跑 |
| 它吃什么吐什么 | **四进二出**（见下） |
| 人在哪里答 | **决策池**（租户范围）**或原会话**，两个入口一件事 |
| 一批卡片 | **全部答完才解除**，「答完」含明确不答 |
| 解除的是谁 | 三种：一次前台执行（run 跟着走）/ 一次后台执行（run 本来就在跑）/ 一个 run |

### 那个判断函数

| | 内容 |
|---|---|
| **跑不跑** | 看这次 llm 响应**有没有 tool calls**。有才跑 |
| **入** | 这次 llm 响应 · 租户权限清单 · 会话授权上下文 · 会话运行模式 |
| **出** | 要不要停下来阻塞 run · **给人的决策卡片（说明 + 选项）** |

后三样输入正是 [PF-007 定的那三样](../PF-007-meta-capabilities/design.md#611-ask通向人)；
本版补上第四样——**被判断的对象本身**。

**它同时是判官和撰稿人**，这一点决定了一条产品要求：

> **人签的是这个函数写出来的那段文字。**写不清楚，这张卡片就是废的——
> 不是「信息少一点」，是**人会在看不懂的情况下点同意**。

### 两个维度分开，掉出了第三种情形

```text
前台工具进等待态   →   tool 停  +  run 跟着停      ← Ask() 就是这种
后台工具进等待态   →   tool 停  ,  run 照跑不误     ← 最容易被漏掉的一行
系统算出来要问     →   run 停                      ← 这次响应里的工具一个都还没开始
```

**中间那一行是两个维度必须分开的证据。**压成一个的话它没处安放：
要么错误地把 run 也停掉（转后台的意义当场作废），
要么让它不进池子——**那就没人知道它在等，它会永远等下去，而且没人会发现**。

### 池子是陈列，不是主体

> **不存在「组织在等什么」这回事。**组织不会等，等的永远是某个会话。

这个分辨来自产品负责人的一处纠正（见 decisions 第四节）。它挡住的是一个
很容易做出来的东西：**一个以组织为主体的「待办中心」**——那样一来池子会
开始有自己的状态、流转、归属，而**真正在等的那个 run 反倒被隔在一层之外**。

### 两处 PM 被纠正的地方，都记下不改掉

- **「HITL 是 run 级的」**——错在把两个维度压成了一个。
- **「组织视图能看见全组织有多少 run 卡在等人」**——结论（租户池）没错，
  但**前提错了**，而错误的前提会长出错误的东西。

两条都在 [decisions 第四节](decisions.md#四已知的来源问题)。

### 下游要注意的八处

- **后台工具的等待态不阻塞 run，但照样进池子。**这两句缺一不可。
- **判断函数只在有 tool calls 时跑。**纯文本响应一次都不该跑。
- **这一关失败时必须「停住」，不能「放行」**——否则最危险的那次调用就绕过去了。
- **人拒绝 ≠ 执行失败；不回答 ≠ 失败。**混在一起 agent 会重试人刚否掉的事。
- **一批卡片答到一半，什么都不会发生。**不许提前放行。
- **一张卡片只能答一次**，会话里和池子里是同一件事。
- **中断这条路必须始终开着。**「只收答复与中断」加上「永远等待」，
  没有中断就是把用户锁死。
- **机制不看会话数。**所有等待一律进池子，与当前有几个会话、活不活跃无关。
  「同时开着好几个会话」是**场景**不是**条件**——按会话数决定发不发，
  会让机制在「只有一个会话」时**悄悄退化，而没人会注意到**。

### 本版刻意不做的

Run 怎么被驱动与收束、会话怎么建与怎么收输入（归后续**多个** topic）、
会话运行模式本身（另有归属）、判断函数怎么实现、通知怎么送达、
池子的界面与排序。

### 本版留下的缺口

- **未决项：无。待裁决：无。**
- **依赖两个尚未成文的对象**：Run 与会话。按
  [PF-004 的先例](../PF-004-agent-runtime-assembly-and-liveness/design.md#两个只引用不拥有的对象)
  只引用、不拥有，用到哪几件事写在 [design.md §4](design.md#只引用不拥有的两个对象)。
- 以上均见 [decisions.md 第四节](decisions.md#四已知的来源问题)。

被排除的内容在 [design.md §2 非目标](design.md#非目标)，那是**边界**——
发现它们缺失不算缺陷。
