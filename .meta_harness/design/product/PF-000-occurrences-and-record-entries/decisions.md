### 关于第三行：投票是怎么做的

**产品负责人明确要求不接受 PM 的单方判断**，指定了裁决方式。执行如下：

- **三份提示词完全相同**，给的是原始材料路径（上游源码与文档、我们自己的
  foundation 与十二个 PF），**不含 PM 的倾向**，也不暗示哪一方更权威。
- **强制二选一**，并强制给出**落选方最强的论证**、**自己这方的已知弱点**与**置信度**。
- **结果 3:0，三票全部投「两套」，全部高置信度。**
- **三票各自找到的决定性反证互不重复**——票数一致本身不构成证据，
  这一点在汇报时已向产品负责人说明。

**落选方的论证不是稻草人**：三票都承认「按域分」回答了设计者最常问的
「我该站在哪里插手」，也都承认它携带了所有权与生命周期信息。
**否决它的理由是：那回答的是「归谁管」，而本 topic 问的是「以什么形态存在」。**

## 二、PM 的推导

**以下不是任何人拍板的，是从已确认内容推出来的。推理链写在这里，可以被逐条验证或推翻。**

| 推导 | 从哪里推出来 |
|---|---|
| **判断打在「一件发生的事」上，不打在条目上** | 设计者手上拿到的永远是「刚发生了一件事」。把判断推到条目层，这一层给他的是一张空表——**他还没有条目可标** |
| **效力三档，不是两档** | 压成两档，设计者只会往两头掉：把审计当「反正方程不读，不用留」（违 [C3](../../foundation/observability-and-logging/requirements.md)），或把审计当依据（于是方程开始从解释性记录里取状态，[PF-012 §5.2](../PF-012-agent-loop-and-run/design.md#52-会话日志是唯一的真相来源) 破功） |
| **两条充分条件必须分别记** | 「只由第②条成立的不进方程定义域」这条规则，**只有在①②分开标记时才表达得出来** |
| **干预力只在瞬态上有取值** | 一条已提交的条目不干预任何事，它只是被读的数据——这是 [PF-012 §6.1「记录先于可见」](../PF-012-agent-loop-and-run/design.md#61-日志先于可见) 的另一面。逐个查过看似反例的三处（决策卡片、immutable 标记、放行判断），**全是「条目是干预的产物，不是干预本身」** |
| **产出多条条目只有两个原因** | 枚举上游 harness 全部成对的事件，**无一例外落在「干预点先于结果」或「增量先于成品」**；没有一对是「因为要既持久又实时」。不写死这条，下一个人会给每条事实配一个实时孪生 |
| **「事件」不收为术语** | 它在内核里指总线上的一条消息，在上游同时指两套东西，在中文里指任何发生的事。按取名规矩，**收窄一个通用词的代价是它在别处的正常用法全变成冲突**。而我们要的两层各有更准的名字 |
| **不新开一卷，并入「记录与上下文」** | 新开一卷，那一卷就是本 topic 的马甲——`ubiquitous-language` skill 的分卷判据自己的禁令。代价是那一卷的问题陈述要从「一段协作留下了什么」放宽为「留下了什么」，因为租户级的事不属于任何一段协作 |
| **寿命宿主与租户身份分开** | 一条归会话的条目**同时**归某个租户——两者嵌套，不能并列为一根轴的取值。且 [SYS-OBSERVABILITY.C2](../../foundation/observability-and-logging/requirements.md) 明写「因果先后与同一流程归属**分别表达**」 |
| **[Cordis plugin](../PF-002-assets-settings-and-permissions/design.md#plugin-不是-cordis-plugin) 不是寿命宿主的取值** | 它回答「谁产生了这条」，那是出处。**一旦它能当取值，功能领域就能当，被否决的那套分法就换个轴名整体回来**。说的是运行时的代码装载单元，不是[产品里那类叫 Plugin 的资产](../PF-002-assets-settings-and-permissions/design.md#plugin)：评审当时给的滑坡是「插件能当取值，能力/seam 下一步就能当」（[交流笔记](interviews/2026-09-19-event-partitioning.md)），而「能力/seam」与 [§6.5 堵的功能领域](design.md#65-两条必须堵死的后门)是同一条轴——那条轴上的东西是代码模块，不是被组织持有、授权、按层级求值的资产 |
| **「不可确定」必须是合法值** | 没有它，[C3](../../foundation/observability-and-logging/requirements.md) 的「不得以缺少终态记录冒充仍在运行」守不住——真实世界里有第三种：发出去了，回音没了 |
| **工程观测记录是派生投影，不是第四档效力** | 否则 C3/C5 会被实现成「打了日志就算有记录」 |

### 被推翻过的推导（保留，因为它解释了现在的形状）

| 曾经这么想 | 为什么不成立 |
|---|---|
| **「归属」是独立的一维** | 它自己没通过用来否决「按域分」的那条检验——取值来自三个不同判据。三个反例：**装配清单条目挂在 agent runtime 上却绝不随它消亡**；**一张决策卡片有四个不同的「谁」**；**一次工具执行绑会话、账却归租户**。拆成「寿命宿主」与「租户身份」两个字段之后才成立 |
| **三根平权的正交轴** | **「依据 × 可干预」是空集**，所以干预力不是一根平权的轴，只是瞬态那一半的子结构 |
| **一件事产出多条，是因为「既要持久又要实时」** | 一条持久条目照样能实时送达，**那是一次投递，不是第二条条目** |
| **旧截图的问题是「要不要留」** | **它一位都不涉及效力**，全在可见性那一侧。这次误判已作为[校准表](design.md#56-校准表拿真实发生过的事走一遍)的一行保留 |

## 四、已知的来源问题

**记下来，不静默改掉。**

### PS-0：§5.3「可否决那一档挂了必须当作否决」没有区分「不可用」与「报错」

[PF-012 rev 9](../PF-012-agent-loop-and-run/changelog.md) 按产品负责人 2026-09-23 的裁决把拓展件定为 opt-in 的可插拔服务：**不可用**（它依赖的服务用不了）视作已卸载，这一次那个位置没有它、日志可见；**可用却运行时报错**才按拓展件类型的处置策略办。§5.3 那句从此读作**可否决一档报错时的默认策略**，不覆盖「不可用」。**下一次修订 §5.3 时补这个限定；本条不单独升 rev**，规则归 PF-012。

### PS-1：`Computer()` 的截图预算，措辞与 PF-010 的禁令冲突

| 哪一处 | 原文 |
|---|---|
| [PF-007 §6.7](../PF-007-meta-capabilities/design.md#67-computer通向图形界面) | 「因此要有上限，并在超出时**裁掉历史里的旧截图**」 |
| [PF-010 §6.12](../PF-010-context-management-and-assembly/design.md#612-记录里的消息一条都不能擦除) | 「**记录里的消息一条都不能擦除。不管它还模型不模型可读。**」 |

**冲突压在一个词上：「裁掉」的宾语是什么。**若指记录里那条，两条直接打架。

**已由产品负责人闭合**（第一节第四行）：**截图是一个[内容块](../PF-009-context-message-types/design.md#消息的内容是一串块不是一段文本)，
超出预算时把它块上「给模型看」那一位翻掉即可**——
这正是[PF-010 §5.7 定义的压缩两个动作之一](../PF-010-context-management-and-assembly/design.md#57-压缩能做的只有两件事)，
**记录里的块一直在，「给人看」那一位不动，排查照样看得见**。

**处置**：PF-007 §6.7 的措辞要改，并指向 PF-010 §5.7，**不在 PF-007 那边重新定义这个动作**。
**回改归 PF-007 的 owner，且要升 rev**——本 topic 不代改。

### PS-2：全链正文里「异常」一词有两个所指

[PF-006 正文](../PF-006-tools-and-skills/design.md)用「异常」指程序抛出的那种
（「异常不带语义」），而十个 topic 的 `flows.md` 章节标题用「异常分支」指
**不正常的情况**。**同名不同义**，且后者才是将来 PF-011 的地盘。

**与本 topic 的关系**：PF-006 那几处想说的是「agent 收到的必须是一条它读得懂的消息」，
**而「不抛异常」只挡住了这一类做法的四分之一**（错误码、空返回、状态码同样违反）。
**这是表达层次的问题，不是产品结论的问题。**

**处置**：**✅ 已闭合（2026-09-19，PF-011 开题时）。**

「异常」**不收为术语，裸用时是白话**；正式词是
[非常态 `Off-Nominal`](../../ubiquitous_language/terms/execution-and-outcome.md#ul-off-nominal--非常态--off-nominal)，
归 [PF-011](../PF-011-off-nominal-handling/README.md)。三处各归各位：
**十份 `flows.md` 的「异常分支」一个字都不用改**；
**PF-006 那五处改为「报错」**——它们想说的是「不要只给一个『出事了』的信号」，
而「不用异常」只挡住了其中一种做法。
记录见 [C-12](../../ubiquitous_language/conflicts.md)。

**尚未完成的部分**：PF-006 那五处的回改**归其 owner，且要升 rev**。

### PS-3：[PF-012 rev 6](../PF-012-agent-loop-and-run/design.md#616-日志里至少要有这几种-run-相关的条目) 点名要的几种条目与几个字段，本 topic 还没有

**PF-012 定了「Run 这一层从日志里至少要读得出哪几件事」**——
Run 开始 · 输入承接 · 在等什么 · 尝试开始 · 外部效果 · 成本 · 取消请求 · Run 终结（以及建议记的尝试结束）。
**它明说这只是「要读得出什么」，条目的种类与形状归本 topic**，
[边界表里写着这一条](../PF-012-agent-loop-and-run/design.md#八边界与依赖)。

**而本 topic 现在两处对不上：**

| 缺什么 | 影响 |
|---|---|
| **没有「记录条目有哪几种」这一层** | [§5.5](design.md#55-挂在每条条目上的字段) 定的是**每条都必填的字段**，[§5.6](design.md#56-校准表拿真实发生过的事走一遍) 是校准用的例子，**两者都不是种类表**。下游会各自发明一套 |
| **[§5.5](design.md#55-挂在每条条目上的字段) 没有 PF-012 要的那几个字段** | **尝试序号**、**这个 Run 内的第几步**、**幂等键**、**对外标识**——四个都只在 PF-012 正文里，本 topic 的字段表里一个都没有 |

**没有直接矛盾，两处反而是对上的**：
[「外部效果的确定性」三值](design.md#55-挂在每条条目上的字段)与 PF-012 要的「成功 / 失败 / 不知道」是同一套；
[寿命宿主的首批取值](design.md#92-寿命宿主的首批取值表尚未封板)里本来就有「执行尝试」，
而 PF-012 rev 6 把执行尝试定成**从日志派生、不另存的视图**——**那不影响它当寿命宿主**，
但**本 topic 复核那张表时要看一眼**。

**处置**：**记下，不代改。**归本 topic 的 owner：要不要立一层「条目种类」、
那四个字段往哪放（无条件必填，还是只对某几类条目要求），**都是本 topic 的判断**。
**PF-012 不代定，也不在那边自建一套字段规矩。**

### PS-3：会话空闲期间被丢弃的那一推，不产生任何条目——**只登记，本 topic 正文不改**

**产品负责人 2026-09-22 裁决**：
[runtime context](../PF-015-session-lifecycle-and-ownership/design.md#runtime-context) 的生产方在
[Run 已闭合（会话空闲）时推来的变更一律丢弃](../PF-014-inbound-intake-and-queueing/design.md#610-注入的上下文变了没有运行在跑时什么都不做)——
**不进队列、不落日志、不成为记录条目**（[PF-014 rev 3](../PF-014-inbound-intake-and-queueing/changelog.md) ·
[PF-012 rev 7](../PF-012-agent-loop-and-run/changelog.md)）。

**与本 topic 对上了，不是例外**：拿[§5.2 那两条独立充分条件](design.md#52-那个判断两条独立充分条件)量它——
**①丢了下一步照样算得出**（下一次尝试开始时 agent runtime 自己拉一次就有当前值）、
**②没有需要解释的发生过程**（那段时间没有 agent 在场，会话也不曾感知过它）。
**两条都不成立，所以它本来就不必留下任何条目。**

**登记在这里的理由**：那两个 topic 写的是「不落日志、不成为记录条目」这个**结论**，
**判据在本 topic**。将来若第①条被削弱（比如出现一块拉不回来的 runtime context），
**这条结论要回头重判**——那是本 topic 的判据在管的事。
