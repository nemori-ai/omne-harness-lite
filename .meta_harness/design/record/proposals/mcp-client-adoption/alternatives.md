# 候选与取舍

## 选择对象与必要约束

见 [design.md](design.md#需要作出的选择)。必须保留的是 N-1～N-10（N-11 是候选假设）；可调整的是实现路径、桥接范围、列举缓存策略。
E-n 指 [mcp-client-reuse 证据记录](../../../../research/mcp-client-reuse/evidence.md)。

**看过、没有列成候选的两条**：
- **「Codex 形状 ＋ 官方 SDK」**：这就是 C。C 的连接池、run 前重列、resources／elicitation 的处理本来就对照过 Codex 的形状，
  再单列一条只是改名。
- **经外部 MCP 聚合网关接入**（本系统只连一个网关端点）：这是部署拓扑，不是客户端选择——系统里仍要有一个客户端，
  而 N-5 的按持有分凭据会被推到网关里去，研究没有覆盖任何网关，拿不出证据，不凑数。

## 推荐与仍待区分的事项

**推荐 C。**

- **先排除 A**：它与硬约束 N-10 正面相抵，另有四处结构性反例（design.md 表中 N-2、N-3、N-5、N-8 各行），不是调配置能消掉的。
- **B 与 C 用的是同一个 SDK**，差别只在要不要把 DSH 的 400 行连接监督 fork 进来。而那 400 行的所有权模型（一实例一连接一份静态配置）
  恰好是 N-5 要换掉的那一层；换完之后剩下的是退避与关闭屏障，**这点收益不值一段对预发布包的长期 fork 跟踪**。
  B 真正有价值的部分——作者踩过的失败处理——以核对清单进入 C 的提供者设计，就能拿到。
- **D 的收益是 C 的反例全部成立时才兑现的**，而它所借形状的来源自己就站在 SDK 上。
- **C 与产品负责人的裁决同向**：「复用社区现有的通用做法」在协议层就是官方 SDK；「看直接复用的方案支持到哪种程度」
  落成下表——SDK 能支持的上限，减去本项目本版有产品前提或架构前提尚未到位的那几项。

**会让选择翻盘的证据**：
- SDK 不允许自定义传输、且产品确认 N-11 → C 的 stdio 一格失守，D 或「B 的传输层 ＋ 自写拉起」重新上桌。
- SDK 长期落后于 MCP 协议修订（例如 2026-07-28 版迟迟不进），而目标服务端开始拒绝旧版 → D 上桌。
- 产品或架构决定工具协议采纳 `dsh-tools`（即推翻 SYS-KERNEL「工具协议自定」的现行读法）→ A 的主要代价消失，需重评。

### 本版桥到哪一步（C 路径下的推荐）

「推荐」列是作者建议，不是接受。「SDK」列除注明外**均未取证**。

| MCP 能力 | 推荐本版 | 落到本系统的什么 | 前提、理由与未决 |
|---|---|---|---|
| `tools/list`（含分页）、`tools/call` | **桥** | 每动作一个工具条目（N-1）；run 前完整列举，分页中断按「这次没拿到清单」处理 | 分页中断的处置是作者建议，提供者设计定稿 |
| `notifications/tools/list_changed` | **只记「清单可能已变」**，不改当前 run | 下一次 run 前的重列依据；是否据此省掉无变化时的重列归提供者设计 | N-2：run 内不变。重连后一律视作已变 |
| 取消（`notifications/cancelled`） | **桥** | 本系统中断一次执行 → 通知对端 → 收场被中断 | N-4；取消不等于对端一定停下，外部效果不回滚 |
| 进度通知 | **可桥**（非必需） | [发帧](../../../product/PF-006-tools-and-skills/design.md#发帧)，不阻塞，丢了不影响收场 | 帧长什么样由一份帧协议约定（PF-006 发帧一节），尚未起草；不桥也不违反任何性质 |
| 日志通知 | **桥到本系统运行日志** | 可观测性，不进模型 | —— |
| elicitation（表单形态） | **桥，但以等待态契约就位为前提** | 本次工具执行进入[等待态](../../../ubiquitous_language/terms/execution-and-outcome.md#ul-tool-wait-state--工具等待态--tool-wait-state)，人经决策卡片作答；拓展件不得代填（N-9）；等待期间单次调用超时停表（Codex 的做法，研究报告 §三） | 卡片形状、接受／拒绝／取消三种回应与 PF-008 的对应未定；**未定之前不向对端声明该能力**——不声明是协议层可观察的显式排除。与任何一次工具调用无关的 elicitation 请求没有等待态可挂，建议一律回绝 |
| elicitation 的其他形态、2026-07-28 协议的多轮工具输入 | **待核后再定** | 多轮工具输入把「要输入」做成调用的续接（E-15），与等待态可能更贴 | 取决于 SDK 支持哪一版协议 |
| resources（列举、读取、模板、订阅） | **不桥为条目** | —— | Codex 把它做成三个跨服务的通用工具（E-13），在产品模型里是「不隶属任何接入点的动作」，与「动作随接入点被持有与授权」对不上；要桥，先由产品答「读资源算不算接入点的动作」 |
| 调用结果里的 `resource_link`、内嵌资源、图片、音频 | **按工具产出处理，不丢** | 文本或附件，按[工具产出](../../../ubiquitous_language/terms/execution-and-outcome.md#ul-tool-output--工具产出--tool-output)的规则 | 这是结果投影，不是「桥 resources」；精确投影归工具产出与两端模态的契约 |
| prompts | **不桥** | —— | 可能的去处是斜杠命令的「自定义 prompt」型，但斜杠命令是资产、有能力标识，MCP 带来的内容不是资产——这要产品裁，不由客户端定 |
| sampling | **不声明** | —— | 对端借本系统的模型发请求，要走 OpenRouter、用[模型凭据](../../../ubiquitous_language/terms/capabilities-and-composition.md#ul-model-credential--模型凭据--model-credential)、有费用归属与放行判断，是一整块新的产品面 |
| roots | **不声明** | —— | 把本地目录告诉对端，是落点与身份类的事；工作区虽由目录承载，是否对外暴露产品未述 |
| 任务式执行（对端要求以任务方式调用的动作） | **不桥** | 建议：列举时即识别，这类动作装替换件并说明「本客户端不支持任务式执行」 | DSH 在调用时才抛错（E-4）；按 PF-006 §6.3 的精神，确定用不了的应在动作前让 agent 读到。能否在列举结果里识别出来**未核** |
| 鉴权：静态请求头、stdio 环境变量 | **桥** | 值来自持有上的凭据设置（N-5） | 不从宿主环境插值；子进程环境不继承宿主的敏感变量（DSH 的过滤做法可借，E-5） |
| 鉴权：OAuth | **本版不桥** | —— | 需要人参与授权、令牌归哪份持有、刷新与持久化在哪——都是产品面与存储面问题；SDK 是否提供可用的鉴权提供者未核。**这一项限制了能接的远端服务范围，接受时须知情** |
| 传输：stdio、Streamable HTTP | **桥** | stdio 拉起走执行环境接口（N-11，候选假设） | 两源重连各只覆盖一种传输，C 要两种都覆盖 |
| 传输：旧式 SSE | **不桥** | —— | DSH 也没有（E-5）；只影响老旧服务端 |

**最小区分调查**（按消费时点排序）：
1. 取 SDK 发布包（研究钉的 `1.29.0` 与当前最新版各一），核协议版本常量、自定义传输接口、elicitation 处理器与能力声明、鉴权提供者；记 SHA，落 `research/mcp-client-reuse` 下一轮。**C 定稿前必须完成。**
2. 核 SDK 列举结果里能否识别「必须以任务方式调用」的动作——决定上表任务式执行一格。
3. 产品确认 N-11（stdio 拉起位置是否受执行环境落点约束）——决定 C 是否必须依赖自定义传输。
