# 投票 3（独立评审，opus，2026-09-22）

> 原件。三位评审收到**完全相同**的中立 prompt（见 [review.md](../review.md#投票怎么派的)），互不知情，禁止读 `tmp/`。

## 1. 投票

**A**——维持两份 data 契约、两个能力、一个组合的拆分。

## 2. 本方（A）最强论证

**A-1. 产品正文与 SYS-TENANT 自己就把这条线画了，而且画的正是「身份 vs 治理」。** PF-001 design.md §4 账号：「**账号是身份概念，不是治理概念。**它回答「你是谁」，不回答「你能用什么、能做什么、怎么做」」；「账号**先于任何组织存在**」；§6.4「账号的身份事实**不是范围化对象**」。SYS-TENANT：「区分自然人全局身份与租户成员关系」。B 要把一个**明确非租户范围化、先于组织存在**的事实装进一个以租户命名的能力里，恰好抹掉 SYS-TENANT 要求区分的那两层。

**A-2. 两边各有互不相干的独立消费者，而且两张消费者表都已经写出来了。** `account-identity` S-2 的消费者没有一个需要组织、成员或邀约；`organization-governance` §十二消费者核对（PF-002 配值资格、PF-003 复制前提与分享边界、PF-007 全局授权表达、PF-015 会话创建）没有一个需要凭据校验或登录状态签发。这正是 handbook 落点 #8「独立变化原因 **且** 独立消费者」两条同时成立的形状。合并的代价可计量：治理侧尚未闭合的产品未决（G-11）一旦落定，就要把登录路径消费的那份契约一起升版。

**A-3. 失败隔离已经是双向写死的契约条款，不是装配习惯。** `organization-governance` S-43 与 `account-identity` S-28 构成一条可检验的单向边。B 之下这条边只是从**契约条款**降级成**一个能力内部的实现分支**，没有版本、没有消费者可依据、评审也管不着。

**A-4. SYS-DEPLOY 要的那条缝，现在已经是写出来的协议，不是一次函数调用。** `account-identity` S-30 与 `organization-governance` S-42 各自逐条列了「本版（单机）由谁给 / 跨进程之后谁重新兑现」。B 把这条缝移进能力内部，那批待兑现项就从契约层消失了；等真要把鉴权独立成节点时，这张表得重新发明一遍，而**失效是静默的**。

**A-5. 组合不是「把依赖汇总起来」，它拥有的东西两方都承诺不了。** S-4「注册成功 ≝ 账号已激活 ∧ 个人组织存在且成员有效为超管」是一个合取，S-5 四个终结结果、S-10 唯一提交点、S-12 重试规则、S-34 第二条清除链——这些都不是任一参与方的操作语义。B 之下「谁在什么时候发起清扫」这类责任交接将失去一个有身份的拥有者。

## 3. 落选方（B）最强的论证

**B-1. 用治理契约自己的准入判据去量账号/个人组织这条边，它不及格。** `organization-governance/README.md` 准入核对「语义拥有者」行的原话：组织与成员被「两条**跨行不变量**和**一次同提交**绑在一起……**把它们分开就得自造一套跨边界提交协议，而没有任何瓶颈测量支持那样做**」。账号与个人组织恰好满足同一描述：跨行不变量写在 composition S-13 与 S-35；而拆分**确实逼出了**那套自造协议——唯一提交点 + 幂等重跑、两份交接凭证、`Registration.tla` 加三个检查配置、一条第二动作链。同样也没有任何瓶颈测量支持这条拆分。**同一把尺子量出两个相反结论**，这是 A 最难回答的一点。

**B-2. A 的招牌理由——重启半径——在能力契约这一层不成立。** composition 与 governance S-4 末段都写「换一次认证方式就会把整个组织治理重启一遍」。但 `organization-governance` S-4 开头就写着「本契约 **inject** 账号能力的读面」。按最小内核模型，**account-identity 的提供者换代本来就会把治理重跑一遍**。真正收住半径的是「把凭据校验切成独立 provider 节点」，而这件事 `account-identity/README.md` 自己标注为「实施提示（归 realization）」——它在 B 之下同样可做。所以这条论证是一个**提供者设计的理由，被当成能力边界的理由用了**。

**B-3. 「当前租户身份」这项事实的所有权是裂开的。** governance S-14：当前租户身份是「**按 `LoginStateId` 记的一项选择**」，治理拥有它的存与取；但登录状态词条注 ④ 写「它失效，那项选择**随之不存在**」，而登录状态记录归 `account-identity`。撤销（account S-16）不会、也无权去动那项选择。于是「随之不存在」在存储层**没有拥有者**，代价是治理每次查询与切换都要回调 S-17 并维护一张四出口映射表。这正是 `decompose.md`「反查边界是否合理」点名的信号：**重复拥有同一事实、反复同步**。

**B-4. 拆分逼出了一条没有授权前置的删除操作，其安全性只靠装配。** governance S-53 **没有授权前置**；S-42 自认它在本版成立靠的是「只有 composition 的清除链够得着它」，并写明跨进程后「**等于给了一条直接删任何账号个人组织的入口**」。同形的还有 account 侧 S-30 的 `identifier-held-by-expired-record` 只流向组合。这两处都是**边界制造出来的、目前只由装配兜住的洞**。

**B-5. 边界当前的守卫本身也只是「装配给」。** 两份交接凭证「不可伪造」在本版由「产出方与核实方在同一进程」兑现；新鲜度则完全靠组合的流程规则「同一次尝试内产出即用」，而凭证本身「本版不绑定尝试、不作废」。A 用来换取分布式就绪的那条缝，**今天的守卫是一条流程约定**。

**B-6. 生命周期与资源所有权指向合并。** `domain_objects/objects.md` 把个人组织的死写进了账号的生命周期；个人组织没有独立生灭，也没有邀请、没有上级、只有一个成员、角色固定。按「生命周期与资源所有权」这条判据，它不该落在边界的另一侧。

## 4. 本方（A）已知弱点

**W-1. 招牌论证被夸大了（即 B-2）。** 「换一次认证方式会把整个组织治理重启一遍」在 composition S-2 后注与 governance S-4 末段被写成硬约束，但因为治理 inject 账号读面，这个结论在当前边界下同样成立。A 真正买到的只是**反方向**的半径收敛。**这一句应当被改写，否则它是一条经不起核对的依据。**

**W-2. 分布式就绪的收益是记账式的，不是已兑现的。** S-30/S-42 把跨进程责任**记下来**，但 G-7 明写跨进程协调未定义，且两份凭证的不可伪造与新鲜度目前都由单机装配和流程约定兑现。

**W-3. 复杂度没有瓶颈证据支撑。** 按 handbook 表 D，这是应当**自证 + 标价**的结构，而现有材料里只做了自证，没有把价送回需求方。

**W-4. 组合契约自身没有独立消费者。** composition S-2 列出的非参与方只有「注册入口」与「清扫提供者」，后者还明写「不承担任何正确性」。它的正当性只能靠「整体性质两方都承诺不了」这一条支撑。

## 5. 置信度

**70%。** 会让我改票的证据：**其一**，若能证明个人组织与第一个租户在产品语义上必须与账号记录落在同一提交边界；**其二**，若逐一核查后发现「独立消费者」在装配上其实都要先走 S-36 把 `LoginStateId` 换成租户身份，即真实消费路径没有一条只碰一侧。

## 6. 附：一种可能更好的第三种拆法（投票仍为 A）

**按生命周期切，而不是按「账号 vs 组织」切**：把**个人组织与第一个租户的创建与清除**移进 `capability.account-identity`（依据：两条对象条目已经把个人组织的生灭完全写成账号生灭的附属；PF-001 §4 个人组织的四条性质使它几乎是惰性的），`capability.organization-governance` 只保留**团队组织、成员关系、两类邀约、隶属关系、当前租户身份**。

后果：注册变成账号能力内部的一次提交，`composition.account-registration` 连同唯一提交点协议、两份交接凭证、`Registration.tla` 三个配置与 S-53 那条无授权前置的删除操作**一起消失**；同时 A-1～A-4 **全部保留**。

代价与未核项：`UL-organization` 会按变体分属两个拥有者，S-6 四条结构性禁止的权威归属要重新裁一次；B-3（当前租户身份挂在登录状态上却归治理）在这一拆法下**仍未解决**。这条路线没有在现有材料里被评估过，值得在接受这五份候选之前做一次显式比较。
