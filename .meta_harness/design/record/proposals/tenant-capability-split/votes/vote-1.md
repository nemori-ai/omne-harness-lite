# 投票 1（独立评审，opus，2026-09-22）

> 原件。三位评审收到**完全相同**的中立 prompt（见 [review.md](../review.md#投票怎么派的)），互不知情，禁止读 `tmp/`。

## 1. 投票

**A**——维持当前拆分（两份 data、两个能力、一个组合）。

## 2. 本方（A）最强论证

1. **两个能力的消费者集合不同、且几乎不重叠，合并会把重启半径扩到全系统。**
   `spec/capabilities/account-identity/v1/contract.md#S-2` 的消费者表里，`#S-17 校验登录状态` 的消费者写的是**「一切需要判断『来者是谁』的能力」**；而 `organization-governance/v1#S-2`「不拥有」表把资产、分享、会话指向 PF-002／PF-003／PF-015 那几份契约。合并成 `capability.tenant` 后，只想问「来者是谁」的能力必须 inject 一个同时承载**二十五个治理操作**的服务键；按 Cordis「必需服务换提供者 ⇒ 消费者先卸载再重跑」，治理侧任何一次提供者换代都会连带重启全系统的身份校验消费者。这正是 `references/decompose.md` 与 `capabilities.md#能力维度的正交性`「独立消费者／变化可被边界隔离」两格要判的事。

2. **两条独立变化原因由产品正文钉死，而且契约已经把它们写成承诺。**
   `product/PF-001.../design.md#非目标` 明列「**认证提供者的选型**」为技术选择（即：它会换），同表又写「精确的角色与动作矩阵……中间角色留待实际需要时再设计」（即：治理规则也会换）。这两条变化互不触发，现在各有条款兑现：`account-identity/v1#S-2`「换一套组织治理规则不会让本契约重新装载」、`organization-governance/v1#S-4`「依赖方向是单向的：治理 → 账号，账号不得反向依赖」。B 之下这两句话在契约层面**没有可写的位置**。

3. **失败隔离现在是契约条款，而且是非对称的。**
   `organization-governance/v1#S-43`：账号读面／登录状态校验面不可用时，S-20／S-21／S-23／S-25／S-36／S-37 一律 `unavailable` 明确失败、不静默降级；反向 `account-identity/v1#S-28` 写明「本契约**只依赖存储**，不消费任何其他契约的读面」，因此治理侧全挂时登录、校验、撤销照常。这条非对称隔离在 B 的单一提供者边界里失去表达处。

4. **SYS-DEPLOY 要的正是这条缝隙保持可见，而它已经被盘点完毕。**
   三份契约各有一节逐条列「装配给 vs 协议须给」：`account-identity/v1#S-30`、`organization-governance/v1#S-42`、`account-registration/v1#S-25`。其中 composition S-25 明写「**三步的次序不是装配给的**——它是本契约的条款 S-8，由每步前置强制；跨进程**不变**」。B 把跨 owner 的次序降级成能力内部的函数调用顺序之后，这份盘点没有宿主，未来要拆分时得重新发现它。

5. **composition 不是「依赖汇总」，它拥有自己的条款和已触发的证明义务。**
   `account-registration/v1` 拥有唯一提交点（S-10）、三条幂等边界（S-9）、四个终结结果（S-5）、两条动作链的完整交错表（S-34），并因「以自定义协议省略跨边界原子提交」触发行为模型义务，已登记三个 formal task、跑过两轮无反例。B 不会让这些性质消失，只会把它们从一份可独立评审、独立登记 formal task 的契约降成某个能力契约里的一节。

## 3. 落选方（B）最强论证

1. **两条真正的跨边界不变量，正在用一整套自造协议撑着，而内核不给跨边界提交。**
   `account-registration/v1#S-13`「一个可用账号有且仅有一个个人组织」与 `#S-35`「个人组织不会变成孤儿」的代价是可数的：一套交接凭证机制（`data/identity-values/v1#S-35`，两处实例 `account-identity/v1#S-14` 激活依据与 `#S-38` 清除依据）、一条**只为它开的组织销毁路径**（`organization-governance/v1#S-53`，S-3 亲口承认它是「不定义组织终结路径」的**唯一例外**）、一条第二动作链（`#S-34`）、三个 TLA+ 配置。合并后「建组织＋激活」「清组织＋清记录」都能落进单次提交，这一整套连同它保护的不变量一起变成结构性事实。`references/decompose.md#反查边界是否合理` 点名的三个线索——**要求跨拥有者同提交、重复拥有同一事实、反复同步修改**——这里三条全中。

2. **一个单调事实被三个跨契约读取点共享，两条不变量全挂在它上面。**
   `account-identity/v1#S-18` 的「是否已过留存期限」在 `#S-14` 前置③、`organization-governance/v1#S-20` 前置②、`#S-53` 三处各读一次；`account-registration/v1#S-25` 最后一行自陈：「**S-35 与 S-13 的三个前提全部挂在这一条上，它失效时两条不变量一起失效，且失效是静默的**」。在一个能力里它只是一次读。

3. **个人组织的生灭完全由账号决定——按生命周期与所有权判据，所有权在账号那侧。**
   `domain_objects/objects.md` 组织条目：「个人组织**唯一的消失路径**是随未激活账号到期清除」；租户条目同理。治理契约被迫为它开例外（S-53）、被迫依赖别人字段的单调性（S-4「本契约依赖它的单调性」），都是这个错位的症状。

4. **「当前租户身份」这份事实本身就骑在边界上：一条记录、两个 owner。**
   `organization-governance/v1#S-14`「当前租户身份是登录状态上的一项选择」按 `LoginStateId` 记；`account-identity/v1#S-2` 的「不拥有」表亲自写明「它按 LoginStateId 记，**但它是治理契约拥有的事实**」。撤销时这项选择随谁失效、由谁删，要把两份契约拼起来才读得出。

## 4. 本方（A）已知弱点

1. **没有一条瓶颈证据，代价却是可数的。** 三份契约正文 4200+ 行、两处交接凭证、一条纯为跨边界而生的第二动作链、四个 formal 配置，以及三、四轮评审才收敛的 catalog 消费 clauses。AGENTS.md「复杂度必须有收益证据」这条，A 目前只能拿产品非目标表里那句「认证提供者选型是技术选择」当前瞻理由，拿不出测量。

2. **A 最硬的那条「换认证不会重启治理」在 realization 层可以另解，因此作为能力边界的理由弱了一截。** `capabilities/account-identity/README.md` 自己的「实施提示」写着：S-15 的凭据校验与其余账号事实**可以分成两个 provider 节点**。既然重启半径能在提供者设计里解决，B 之下同样能把凭据校验做成独立 provider 节点。

3. **单向依赖不是免费的：它把两处本可现读的前置换成了不查新鲜度的凭证。** `#S-14` 明写它不核实新鲜度，新鲜度只能靠组合的流程规则「同一次尝试内产出即用」。跨进程后这两个前置还可能变成空守卫（`account-identity/v1#S-30` 末行）。

## 5. 置信度

**70%。** 会让我改票的证据：(a) 出现一份已接受的装配／部署判断，说明身份校验与组织治理在本项目必然同进程、同存储、同生命周期，且**不存在只需要「来者是谁」的消费者**；或 (b) 交接凭证那套机制在实际演练中被证明是主要正确性风险来源。

## 6. 第三种拆法（不参与投票）

**A′：A 的边界不动，但修掉 B 论证 3、4 指出的两处错位。**

- 把**当前租户身份**这项选择从 `organization-governance`（S-14／S-36／S-37）移出，作为登录状态记录上的一个字段读写面归 `account-identity`，治理侧只提供「该 TenantId 此刻是否有效」的判定（S-26 已有）。这样 `LoginStateId` 这条记录不再有两个 owner，撤销与失效的责任也收进一处。
- 把 `organization-governance/v1#S-53` 那条例外重新表述成「**未激活账号记录清除链**」整体归 composition 所有的一个受限写面，使治理契约「不定义组织终结路径」不必自己开例外。

这不改变 A/B 的主轴，但能消掉 B 的论证 4 和论证 3 的一半，同时保住 A 的四条收益。
