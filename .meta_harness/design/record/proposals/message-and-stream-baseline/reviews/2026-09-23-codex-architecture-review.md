**2. 最强反证及其处置**

**最强反证：D 的“拼回原始参数、丢弃 `partial`”仍然不能兑现 N7 的“收齐才解析、只解析一次”。**

- **类别、位置**：性质承载／投影对齐；[提案 design.md「剩余责任」「证据义务」:100、134][P]。
- **一手证据**：pi 普通 function 参数分支确实将上游 `function.arguments` 原样赋给 `delta`，但紧接着调用 `parseStreamingJson`；封口时又解析一次。因此，原始片段可取回，**不代表可以“不必动 pi”**。[pi `openai-completions.ts`:646、459][PC]
- **触发场景、后果**：收到 `{"path":` 等未收齐参数时，pi 已先执行残缺解析，外层随后丢弃解析结果也不能消除这次行为；与 [PF-009 §6.10][P9] 直接不符。
- **作者需明确**：传输 fork 必须承担禁止中间解析的责任，并明确最终唯一解析点；不能只登记“保留原串”的补丁。

**处置：非阻断起点选择，必须在传输契约定稿前闭合。**修正仍位于 D 已选择的 pi-ai 定向 fork 内，不改变数据契约、到达语法和装配器的边界。改选 C 同样不能绕过 D-019，所以这条反证不足以推翻 D。[D-019「选择与范围」][D19]

另一个重要限定：上述“delta 原样”只核实了普通 function 分支。custom grammar 分支会构造 JSON delta，不能推广为“所有 `toolcall_delta.delta` 都是原始供应商片段”。[pi `openai-completions.ts`:411、448、651][PC]

按角色要求，落选方 **C 的三条最强论证**是：

1. **检查单不是 D 独占的收益。**C 同样可以核对 DSH 不变量；D 没有继承填法、语音、切分不变及合并不变的实现证据。[alternatives.md「C」「D」][A]；[研究 notes/dsh-llm.md「D11」][RD]
2. **上游检查并非全部语义中立。**`max-tokens` 携未封口块会被拒绝；已封口索引却可以再次 `block-start`，因为伴件只记录当前打开的索引。它不是可直接升级为本项目条款的完整检查集。[DSH `invariant.ts`:46、60、75][I]
3. **仍须剥离模型专属假设。**工具调用身份、`TokenUsage`、`replayState` 与可扩展结束原因，都不能因骨架被选中而自动成为共用协议。[DSH `types.ts`:130、149、368、390][T]；[alternatives.md:100][A]

D 的已知弱点正是：**收益是一份受约束的起草起点，而非一套已验证协议。**我对骨架可承载的判断置信度为中等偏高；若块身份定稿后无法与流内索引稳定对应，或合法内容必须引入改变关联方式的新增量操作，应改票为 C。[alternatives.md「会改变选择的证据」][A]

伴件还存在三个不能漏掉的差别：

- 只检查 **usage 至多一次**，不检查必须出现，也不检查 usage 前全部块已封口。

**场景 a：先吐日志，最后一块替换为汇总面板**

以下只是走查记号，不是拟定 Schema；面板取产品已允许的文本块：

```text
开 0：文本，追加
填 0："开始\n" → 填 0："完成\n"
封 0：完整文本 "开始\n完成\n"

开 1：文本，整体替换
填 1："完成 1/2" → 填 1："完成 2/2"
封 1：完整文本 "完成 2/2"

工具流记账位置 → 收尾
```

结果是同一条 `ToolInternalMessage` 的两个块：日志完整保留，面板只留最后值；另有独立 `ToolMessage` 承载执行结果。没有修改块 0，也没有重开它。[PF-009 §5.5:528、§5.8][P9]；[PF-006「发帧」「工具的产出」][P6]

相邻同块的追加片段可连接，替换更新可归约为最后值；不能跨开块、封口、记账和收尾边界合并。这里证明的是**最终装配内容**可一致，不是每个观察者看见的中间画面相同。[PF-009 §6.16、§9.2][P9]

**结果：不需要改变增量结构。**工具记账载荷仍未裁，故没有虚构一笔 token 用量来冒充完整走通。

第五行是最容易误判的地方：原始 `ToolCallBlock.arguments` 是字符串，**封口交出了完整的块值，不等于这串参数构成完整调用**。因此骨架已有表达位置；pi 也确实先 `finishBlock`，随后才发 `done(length)`。[pi `openai-completions.ts`:679–699][PC]

反过来，直接送“未封口调用＋`finish(max-tokens)`”会被上游伴件拒绝。作者须明确截断的规范化边界及完整性判定，不能同时无条件继承该检查，又假定所有截断输入天然合法。这是语法语义的待闭合项，**尚未构成必须新增增量操作的证据**。[DSH `invariant.ts`:75][I]

五种收场均须由 agent loop 补中断提醒；计费未知不能冒充零。前者已有责任归属，后者不能由“usage 只一次”推得。[P:102][P]；[PF-013 §5.13][P13]

**6. F 四问**

1. **dispose 时在途增量归谁？**  
   不能归纯装配器的生命周期自动处理。产品上分别归模型请求运行时和工具运行时；提案只明确了装配职责、尝试账和首 token owner，**未写取消、断流、最终提交竞态中的唯一结算者**。尤其不能把“服务卸载”直接当成“中断消息已持久化”。[P:96、99、153][P]；[PF-013 §5.13][P13]；[PF-006 §6.12][P6]

2. **依赖消失谁被卸载？**  
   提案只有包依赖方向，没有服务注入及装配图，**本次无法判定实际卸载范围**。三层为纯模块不会自行解决这一问题；下游必须保持模型请求与工具执行可单独停止，不能因共同依赖失效而无依据地相互带走。[P:120–123][P]；[PF-012 §6.13][P12]

3. **事件是否跨边界泄漏？**  
   数据侧排除了共享 `partial`，工具过程消息也有明确模型禁入规则；但没有事件派发绑定，不能声称已验证不泄漏。跨边界信封的租户／会话身份及授权校验也尚未落实；块标注不代替租户隔离。[P:100、128][P]；[PF-009 §6.14][P9]；[PF-000 §5.5][P0]

4. **跨进程后哪些保证失效，装配给与协议给分开了吗？**  
   JSON 表示和顺序归约规则可以保留；进程内调用顺序、来源唯一性、取消信号传播、共享生命周期及内存前缀不能随序列化自动保留。**本稿未给出两类保证的显式分表**，因此 SYS-DEPLOY 只到结构方向可行，尚不到装配明确。[P「契约、动作链与 Cordis 投影」][P]；[SYS-DEPLOY][SYS]；[handbook「F 反向核对」][HB]

以上是下游责任缺口，不是已经观察到某个实现泄漏或错误卸载。

**7. 转交 spec-reviewer 的表达问题**

- “账只一次”须统一为至多／恰好一次，并区分流内用量事件与耐久成本条目。[P:94、149][P]
- “封口块＝所有填的结果”须按追加／替换分别定义，并限定内容、元数据及落盘前派生属性的比较范围。[P:91、94、95][P]
- 明确“任意切分／合并”的允许操作域，不能将任意改写替换快照或语音编码边界都算作合法切分。[P:137][P]
- 核对“顺序状态机初判不触发”指额外证明门槛，还是被误写成免除 SYS-SPEC 行为规格义务。[P:118][P]；[SYS-SPEC][SYS]
- N11 原文是语言无关与可跨进程表示；交接缺口引用的“供应商中立”是否另有权威要求。[P:53、152][P]
- PF-009 §7 的“三样做增量”与 §5.5 的四样不一致。[PF-009 §7][P9]
