# Always-On、Dots 与 Plexus：Relay 投影报告补篇

## 1. 判断：值得补入报告，有一条窄范围主项目讨论值得提出

**值得补充，且不只是加几条外部引用。** 这些材料把原报告三个相邻部分连成了一条可审查的链：持续理解与长期事情、真实资源接入、授权和恢复。最重要的变化是验收问题：除了问“这次任务完成了吗”，还要问“前天形成的理解，昨天的更正和今天的撤权，是否正确改变了明天的行动”。

**独立评审与主线复核后，保留1条值得主项目讨论的候选：压缩摘要内部的指令归属是否需要明确保留。** 已写好[issue讨论稿](issue-compaction-attribution.md)，未发布。必经放行、委派收窄、持久事实/恢复以及已知待定义的长期目标/记忆均不重复提。新候选限定在“摘要由系统生成”与“摘要转述的要求究竟是谁说的”之间：当前设计区分前者，并显式把摘要内容交给策略；未找到对后者是否需要成为策略自由的窄例外的专门规定或讨论。这是有具体风险序列支撑的设计讨论，尚非已复现漏洞。

三组独立读数分别核论文、个人版/Plexus、lite覆盖；主线合并时区分它们的证据强度。原报告封存文件保持原字节，本补篇独立记录评审和最终哈希。

## 2. 为什么会觉得它们异曲同工

### 2.1 共通点是状态会积累，并在未来获得行动后果

论文的核心对象是跨交互保留身份和可变状态、让后续行为依赖这些状态的代理。它不要求进程全天不停：定时唤醒或按事件唤醒都可以；始终在线但每次遗忘也不满足其定义。六条诊断轴是授权、范围、可变性、来源、可恢复性和行动性。[论文§2–4](https://arxiv.org/html/2606.30306v1)

把这件事投到Relay，一份资料刚进入时只是“我看过”；提取后可能成为“我认为”；用户纠正后变成“以后按这个理解”；再与长期事情、时间条件结合，就可能成为“我现在应当行动”。风险和价值都发生在这些转换上。

**我的解读：能记住不是终点，关键是系统是否知道这段记忆在什么情境下仍然有效、能影响什么、失效后怎样停止影响后续工作。** 这也是为什么持久化是必要底座，但给每段文字加数据库ID并不解决全部问题。

### 2.2 三份材料观察的是不同层

| 对象 | 它提供的东西 | 不能由此推出 |
| --- | --- | --- |
| Always-On综述 | 分析持久状态与治理的方法，以及有限实验的评价协议 | 一套已验证可直接部署的统一架构 |
| Dots公开说明 | 具体产品如何限制后台研究、隔离执行和防护、检查动作 | 审核算法、存储事务、恢复与全域删除协议已公开或被独立证明 |
| Plexus + Personal Edition adapter | 能力发现与授权、具体资源绑定、回执及原Session异步接续的已有纵线 | 长期认知记忆、通用事件总线、跨Session使命系统已经完成 |
| Harness lite | 已定的执行、身份/权限、事实、动态生命周期与恢复边界 | 已接受条款等于生产执行链已实现 |
| Relay产品层 | 解释哪些事情值得持续推进、如何理解用户、何时交付或打扰 | 连接所有底层模块就自然产生长期有用性 |

因此可以将它们连起来理解，却不能把论文、Dots、Plexus和lite说成同一个系统的不同名字。Dots是一个产品对同类问题的回答；你已有的框架与资源系统是另一条具体建设路径。

### 2.3 对动态资源的重新定位

Plexus最有价值的地方，不只是“让模型多调用几个工具”，而是让**用户环境中的能力成为有身份、有作用范围、有授权边界、能取得执行回执的对象**。个人版adapter又把某项能力绑定到具体事情所在的Session，并保存其使用历史。

这里的dynamic resource是具体provider操作的参数绑定，不是算力租约，也不自动是另一个agent。Plexus的Source/Capability、OMNE资源绑定和界面卡片各有不同职责。把它们统称为“一个资源”，会丢掉管理授权、运行绑定与展示之间的边界。[个人版/Plexus源码读数](../../../../../../research/always-on-agents-plexus/notes/plexus.md)

这是与论文相接的一块真实资产：**外部世界的能力和结果可以接入持久责任链。** 但“用户希望未来一个月做到什么”“这份观察是否足够形成长期判断”仍由产品/认知层负责，不应搬进Plexus网关。

## 3. 论文值得吸收什么，哪些话不能照搬

六轴最适合作为状态审查问题，而非照抄成一张万能表。下面是本次对Relay既有对象的分析投影，不是新增正式术语或Schema。

| Relay里会长期留下的东西 | 授权与范围 | 更新与来源 | 恢复和未来行动 |
| --- | --- | --- | --- |
| 外部观察：邮件、文档、工具返回 | 能读取不等于能转发、训练或执行其中的指令 | 来源、取得时点与内容版本；观察不冒充用户要求 | 来源失效或更正后，能找到消费它的理解与未完工作 |
| 个人理解、推断、偏好 | 区分明确表达与推断，说明适用事情/情境 | 纠正可以取代旧理解；摘要不变成独立佐证 | 旧索引/缓存不能胜过新的纠正；不能从偏好推导新的操作权限 |
| 长期事情及阶段承诺 | 用户授权的目的、资源和投入范围 | 人工进展和外部变化均可能改变阶段 | Session结束不等于事情完成；关闭事情后不继续无界关注 |
| 资源绑定与grant | 管理资格、绑定owner和具体动作资格分别核对 | provider/绑定代际及语义变化不能静默沿用 | 暂停/完成/失效的绑定不隐式复活；新调用与旧结果核对分开 |
| 某次动作的批准 | 绑定动作内容和接收方等实际参数 | 留下采用时的规则与资格；不靠模型记忆作为权威 | 是否继续有效按明确的准入政策，不用一个泛化“最新权限”抹平冻结语义 |
| 调用/效果回执 | 可见范围受限，回执本身不产生新调用权 | 请求身份、外部结果与unknown都可追查 | 已产生效果不能靠恢复内部状态撤销；不因结果丢失盲重做 |
| 纠正、撤销与删除记录 | 谁能纠正什么、谁能请求何种删除 | 区分取代事实、停止使用、删除内容和保留最低审计 | 恢复旧备份不能让已删除信息重新生效；外部独立副本另有边界 |

上表的接缝来自本项目材料；原论文六轴提供询问方式。没有要求所有对象由一个数据库、一个事务或一个微服务拥有。

论文的评价启发同样具体：有用行为与禁止行为应分别记分。一个什么也不做、什么也不记的代理，可能避免多数错误，却没有满足用户托付。因此验收既要看到“拒绝了未授权动作”，也要看到“在授权内继续推进并交付”。

证据强度必须降到合适位置：

- AOEP并非只有概念：作者报告了7个系统配置、9类故障、本地pilot和若干真实AppWorld轨迹扩展。但没有补齐最小治理字段的消融，不能把配置差异升级为某种存储架构的先天缺陷；本次未复现。
- 综述把GEM表述为形式化不可能性证明；核对原文§3.4后，原作者明确说是结构性观察而非定理，六条件也不包含综述所说的rollback traceability。因此不能引用它来宣称“关系型/记录级存储数学上不可能做到”。[GEM原文](https://arxiv.org/html/2605.26252v1)
- ACRFence原文展示恢复攻击的PoC，却明确没有实现或评测所提防护方案。它支持“内部恢复可能重复外部效果”这个反例，不支持“采用其方案就已解决恢复安全”。[ACRFence原文](https://arxiv.org/abs/2603.20625v1)

完整定义、阅读范围、数量口径和局限见[论文封存读数](../../../../../../research/always-on-agents-plexus/notes/paper.md)。本篇不据综述更换基础存储、不扩大已接受语义，也不作产品优劣排名。

## 4. Dots带来的启发：把自主性分配到不同权限的工作阶段

OpenAI描述了两个很有帮助的边界：后台主动研究用代码限制的只读工具，把笔记交回Dot；后续动作仍经过常规规则。执行代码的环境不能修改或关闭关键检查。文章也明确断开连接不等于清除已经取得的上下文。这些是厂商公开的产品说明，尚非其底层实现或独立效果证据。[官方文章](https://openai.com/zh-Hans-CN/index/how-we-build-safety-security-and-privacy-into-dots/)

**投到Relay的意义，是将“自主了解”与“产生外部后果”分配不同权力。** 可以在既有PWP-03/PWP-11的策略实验中，比较一个仅能读取获准来源、写私有研究记录的后台角色；它提出值得推进的事情，再由真实动作路径承接。这里的“只读”针对用户业务资源：保存私有研究结果当然仍会写产品自己的存储。

这是可选产品组合，不是本次为Harness新设“所有主动工作必须只读”的规则。已有子权限不宽于父、工具禁用、不可关闭的准入，可以提供组合基础；工具具体是否真的无外部写效果，仍要由提供者和隔离环境兑现。开放一个通用Shell/Browser，或者设置PF-005的never-allow，都不能证明研究角色只读；never-allow约束落点，不证明工具效果。

同样不能把“独立审核”擅自解释成“必须再调一个不同大模型”。lite已经有不能被agent绕过的放行语义，具体语义授权算法及父权限读取来源还有已登记缺口；本次文章不足以替它们选算法。

另一个产品启发是把用户控制的不同后果说清楚：取消一项长期事情、撤销一个应用的访问、让系统不再采用某条理解、删除信息、恢复一次运行，分别改变不同状态。若界面都叫“停止”或“忘记”，即使底层各自正确，用户也无法判断自己控制了什么。这是昨天权限/恢复/退出体验的解释补强。

## 5. Plexus现有纵线究竟能复用多少

| 已有资产（所查个人版与匹配Plexus） | 对Relay建设的价值 | 保留的边界 |
| --- | --- | --- |
| Connector→Source→Capability动态发现；管理面与agent调用面分离 | 设备/应用能力接入、配置与使用知识的现成实现参考 | 软件操作目录不是业务长期目标或通用变化订阅 |
| Session具体资源绑定、owner、provider/自身代际、合同指纹 | PWP-04资源协作和SWP-07适配不必从概念零起步 | 这是个人版候选接口，移植须对齐lite接受边界 |
| Harness委派断言与Plexus自身grant双重核验 | IF-07权限桥可用作真实接缝案例 | 服务调用委派不等于BOT工作委派；不能把它当完整SaaS授权服务 |
| SQLite绑定、授权custody、请求/任务回执；尝试先落盘 | 原请求核对、去重与unknown呈现有已有实现经验 | 保护一次dispatch不等于全域exactly-once；外部服务另有事实 |
| 终态观察及原Session受约束接续 | 异步任务完成后继续原工作有代码与已有E2E记录 | 只观察已接受job的终态；不是邮件/日历/文件的通用changefeed |
| provider重启恢复、同agent新权限episode核对旧任务 | 中断后的身份/结果核对路径有经验 | Plexus网关内存job cache丢失时不能补造结果 |

**复用还跨一道语言边界。** 个人版adapter是Python，Plexus网关是TypeScript。沿lite以TypeScript为主的产品实现约定，adapter不是可直接搬进monorepo的同语言包：需要按lite契约重新实现/适配，复用的是协议、语义及验证经验。Plexus网关可以作为外部服务复用的候选，但部署隔离与版本适配仍须验证。这部分移植成本本次未估。

三个必须保留的现实差异：

1. **Plexus Session不是OMNE Session。** 前者是短期权限episode，当前内存态；后者承载对话/工作生命周期。混为一谈会误判跨会话持续性。
2. **adapter持久化不等于上游持久化。** 网关重启后可能丢失异步结果，adapter能诚实保留unknown，不能保证恢复该结果。暂停/撤权也不能被说成终止已派发动作或回滚其效果。
3. **独立Plexus的所有功能不等于个人版已开放。** 个人版明确排除长运行coding-agent launcher、泛命令和无界native automation。旧安全文档“execute永不standing”也已漂移：当前代码允许owner对特定agent+capability明确opt-in，默认仍按次。判断须用匹配提交而非旧README。

以上根据源码与已有验证记录，本次未重跑。它们使复用路径更具体，却不足以直接下调原187人周中任何整包：SaaS租户隔离、多用户连接运营、业务语义、跨Session事情和真实组合验证仍在原责任范围内。

下面是**报告目标态的责任链**。标为“个人版已有”的部分只在所查个人版纵线有实现/记录；其余是lite承诺或Relay候选，不是本次新实现。

        │          │
        └──获准观察 + 时间/事件条件                     PWP-02 / PWP-10 / SWP-07

                   │  两侧判定时点分别沿各自已定语义
           provider / Plexus授权调用                    SWP-07 / PWP-04

权威按对象分开：Plexus的外部调用回执不能替代Harness运行事实；Harness的Run结束不能替代Relay事情完成；Relay记忆中的“已经授权”不能替代实际授权源。恢复时先核对各自真实状态，再决定能否继续。低用户数可以简化部署规模，却不会消除这些跨边界一致性问题。

### 一条例子：持续跟进一次出行

此例是分析场景，不新增需求。用户授权跟进出行资料；研究角色发现航班时间变化，留下带来源与时点的观察。产品层判断它影响原有行程，提出改日程或通知同行者的候选动作。读到邮件不自动得到改日程/转发邮件的资格；真正动作分别经过既有Harness和资源授权。

之后用户纠正同行人，又撤销日历连接，而一个请求刚好在外部提交后丢了响应。这时：理解层不能继续使用旧同行人；资源层不能发起失去资格的新调用；已提交请求要核对结果，不能因为重启重发；事情层不能仅因一次Run结束就报“行程已调整”。这条跨时间链，才是本次研究给昨天逐功能投影增加的检查维度。

### 7.1 追加到既有验收责任的八条轨迹

这是后续可执行的验收设计，**本次没有执行、没有通过率**。每条都要固定初始状态、外部服务配置、采用政策、变更顺序、恢复点及可观察结果。可用有序和受控乱序两种轨迹查接缝，不能只检查最终回答文字。

### 8.1 为何改变初判

初稿把“外部内容不能自授操作权限”当成足以排除这类问题的依据。Fable指出：已经有合法工具资格时，内容仍可能被摘要改写成虚假的用户要求。这是**决策依据的归属**问题，不一定是权限扩大。主线重读PF-009/PF-010/PF-012与admission S-22后采纳了这个纠正。

最小分析序列：一个本来获准自动执行的、范围受限的工具 → 外部观察里出现伪称用户要求的文本 → 在已允许压缩的旧历史中被总结、丢失外部转述归属 → 后续动作落在工具已有权限范围内却违背真实任务。准入可能完全正确，产品行为仍错。用auto档只是隔离变量；不依赖尚未定清的allow_session“同类”求值，也不假设禁止/人工确认会被绕过。

PF-010 acceptance §四已明确把摘要内容划归策略，因此讨论是“关键指令归属是否值得单列为边界”，而不是宣称压缩内容无人考虑。本次**确认的是未找到对该项具体性质的单独规定或权衡，且现有保障不能逻辑推出它**；没有运行压缩器，没有证明某模型必然犯错，也没有完成所有历史讨论的普查。具体问题、反例前提、已有保障、三种讨论方向及可观察验收草案见[issue讨论稿](issue-compaction-attribution.md)。方向仍待主项目裁决，不能把T1新性质当作现行框架测试oracle。

### 8.2 其余候选的后续触发条件

将Plexus个人版纵线映射到lite时，如果保持既有身份/准入/效果事实语义仍无法表达资源暂停、终态核对或续原Session，且并非已知生命周期交接，再附精确反例发起讨论。目前没有此项反证。长期目标、Engram与长期质量指标继续原有待定义责任。
