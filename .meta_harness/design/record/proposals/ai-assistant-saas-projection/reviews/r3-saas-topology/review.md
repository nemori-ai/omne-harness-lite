## 一、性质／正确性

### R3-A01 · 外部效果结局与幂等键出现双拥有者 —— **阻断（高）**

- **位置**：`saas-design.md` §4.1 表「外部动作与远端派发 → 写入 owner SP-06/07；持久动作台账」；§2.2 接缝表「外部执行：幂等键…」；§2.3「SP-06…执行结论复用框架 owner」；`execution-topology.md` 共同事实表第 4 行。
- **依据**：PF-012 rev21 §5.14「外部效果的记录：追溯与幂等，是同一条记录上的两个字段」——幂等键**只能由 (会话, Run, 第几步) 决定**、外部标识与「不知道」三值结果属于 Run 日志；baseline FC-29「未知外部效果…有可追溯语义」归框架。
- **因果**：§4.1 把「外部动作」的写入 owner 给了 SP-06/07 的台账，§2.3 又说执行结论复用框架 owner；两处正文互斥。更关键的是**谁铸幂等键没写**。反例交错：cell 的一步调用 SP-07 发邮件 → 供应商已受理 → 回执写回前 cell 崩溃 → 框架按 PF-012 §5.7 重算同一步（新 attempt，同 step）→ 再调 SP-07。若 SP-07 以自己的 request id／attempt 铸键，供应商视为新请求 → **第二封邮件**，直接违反 EP-03 验收「不制造第二封邮件」与 P04。
- **为什么本阶段必需**：这是 12 条链里所有外部效果分支的共同提交点；实施者据 §4.1 建独立台账即会产生上述双发。
- **能否一处措辞闭合**：**能**——因此闭合后即降级。最小修订：在 §4.1 与 §2.3 统一为「外部效果结局的权威记录是框架 Run 日志（PF-012 §5.14）；SP-06/07 台账是适配器侧证据与对账输入，不得单独宣告成功；幂等键由框架按 (会话,Run,步) 提供并透传到适配器，SP-07 按该键去重，不自铸」；并在 §2.2 接缝表把「框架向效果适配器交付幂等键」登记为**必需框架接缝**（当前 FC-07 执行 runtime 未交付，需主线登记）。

### R3-A02 · 控制库 PITR 之后 generation 会倒退，围栏失效 —— **阻断（高）**

- **位置**：`saas-design.md` §5.1「`tenant -> cell + generation + placement_state`…generation 是拒绝过时请求的候选围栏值」；§4.1「资格/代际与其 outbox 同事务」；§6.3「灾难恢复…核对更晚的撤权/注销墓碑」；§10 EP-08 验收「恢复不复活撤权和删除」。
- **因果**：撤权代际与 assignment 代际都只存在控制库。控制库按 PITR 恢复到 T1 后：（a）T1 之后提交的撤权行与其 outbox 一并丢失——若 outbox 尚未投递到 SP-11 审计库，**没有任何地方还留着这条撤权**，§6.3 说的「从独立回执补齐」无从补齐；（b）注册表重新从 T1 的值递增 generation，而 cell／效果网关已经见过更高的代际——**已被围栏的旧代际重新变「有效」**，或新 owner 拿到一个比 zombie 更小的代际。设计假设 generation 单调，PITR 打破了这个假设，而 §5.1 只讨论了「旧进程继续写磁盘」这一种围栏失效。
- **为什么本阶段必需**：EP-08 把「恢复不复活撤权」写成验收，而机制按现文兑现不了；这是持久化与一致性主线上的核心项。
- **能否一处措辞闭合**：**基本能**。最小修订：（1）generation 带 **restore epoch 前缀**，每次从备份恢复控制库必须先递增 epoch，cell／网关拒收 epoch 低于当前值的任何代际；（2）明确「撤权/删除/分配代际」这类事实的 RPO 不等于数据库 RPO：恢复后**默认把 T1 之后可能存在的授权视为可疑，拒新效果直到与审计库、各 cell 最后观测代际对账完成**；（3）SLI「撤权执行差距」加入恢复场景。

### R3-A03 · 预算预留与凭据取用是每次模型调用的网络依赖，与「离线会话继续」的关系没说清 —— **高（非阻断，需明确）**

- **位置**：§8 候选预算过程「原子预留…→ 允许模型/执行动作」；§3.3「不把每次工具调用改成治理中心现查」；§1 进展共同前提「资源配额允许」；`execution-topology.md` 总体拓扑 `B → H → HR → OR`（预算检查在路由**之前**）。
- **依据**：PF-016 §6.17 会话离线继续、无时长上限；PF-013 §5.6 凭据按租户取「所在范围那一把」、据点离线用副本。
- **因果**：拓扑图把预算放在进入 cell 之前，但 Agent Loop 内每一步都会再调模型；按 §8 每次调用要先在 SP-10 的共享 reservation 行原子预留。那 SP-10 不可达时 cell 里的会话怎么办？停（与 §6.17 的精神相悖但符合「进展前提」）还是继续（违反 P07/EP-09「并发不超发」）？正文两边都能读出来。同一问题也落在凭据上：§6.1 说密钥只在 vault、助理只见引用；PF-013/PF-016 说据点持有凭据副本供离线用。**cell 到底持有租户 OpenRouter 密钥副本，还是每次从 vault 取？**
- **后果**：P07 的保护点不确定；平台付费租户的预算硬上限只能靠 SP-10 预留（OpenRouter 侧无租户级上限），这个依赖若不写明，实现会各取所需。
- **最小修订**：在 §3.3 增加一句明确的区分——「§6.17 保护的是 harness 会话不因**治理中心**不可达而停；模型调用的**预算预留与凭据取用**是 SaaS 效果入口，SP-10/vault 不可达时**新模型调用等待并可解释**（属进展前提），已发出的调用照常结算」；并在 §5.1 写明 cell 对租户凭据是「引用+短期取用」还是「本地副本」，二选一并给出相应的撤销传播时间承诺。

### R3-A04 · 返回 cell 的任何内容都进入不可擦除的会话日志 —— **中**

- **位置**：§5.3「检查范围包括…最终成果」；`execution-topology.md` EP-05「受限材料」段。
- **依据**：PF-012 §6.1「任何要进入 agent 上下文的东西，先落盘」；PF-010 §6.12「记录里的消息一条都不能擦除」。
- **因果**：节点乙的「获准聚合结果」回到云 cell 的那一刻即成为永久日志，M05.5 要求的「先说明结果是否仍可能包含敏感内容」因此是**不可撤销的决定点**；§9 的删除链对它也无效。正文把「结果」当作一个出站通道检查，但没写出这一通道的落点是不可擦除的。
- **最小修订**：§5.3 加一句「出节点即入 cell 会话日志且不可擦除；出站判断在节点侧完成，且该判断本身记入节点台账」。

### R3-A05 · Zombie cell 的模型花费对 BYOK 租户不可围栏 —— **中**

- **位置**：§5.1 围栏段；§6.1「失窃处理…轮换服务身份」；§8。
- **因果**：围栏能收回的是存储写权与 SaaS 网关资格；但 cell 直连 OpenRouter（拓扑 `HR → OR`），用的是租户自己的密钥（副本）。旧 owner 失联后若仍活着，会继续用**用户自己的余额**为过期会话付费；平台可轮换平台密钥（波及全部 cell），却不能轮换用户密钥。§5.1 只写「不能防止旧进程…直连外部服务」，没有把这一条落到费用性质上。
- **最小修订**：§5.1/§8 明示「未完成围栏期间的模型花费属 unknown 费用窗口，向 BYOK 用户如实披露；迁移决策把该窗口计入代价」。

### R3-A06 · 注册链的跨 owner 幂等缺少查找键 —— **中**

- **位置**：§10 EP-01「注册键绑定人/个人 tenant/成员和供应意图同事务」；`execution-topology.md` EP-01「孤立的中间资源由供应协调者核对接续」。
- **依据**：`composition.account-registration/v2`（accepted）由框架治理 owner 提交；§4.1 自己声明跨外围库与 harness 库不假装原子。
- **因果**：交错——SaaS 调框架建账号 → 框架提交 → SaaS 崩溃未写 (issuer,subject) 绑定 → 用户重登 → 无绑定 → 再建一个 person → **一人两助理**，违反 P01/S01。「核对接续」需要框架侧能按外部绑定引用查回孤立账号，或框架注册接受外部幂等引用；两者都不在当前接受契约里。
- **最小修订**：把「框架注册接受/可按外部绑定引用查找」登记为必需接缝；在此之前 SaaS 必须「先持久写供应意图，再调框架，恢复时按意图记录里的框架回执/引用对账」。同时修正 §10 EP-01 的「同事务」措辞（见 R3-A16）。

## 二、边界与反向核对

### R3-A07 · 多租户共享 cell 与两条框架不变式的承载复查未写 —— **中**

- **位置**：§5.1「不同 tenant 可以由同一 cell 承载，前提是框架隔离契约与内存成本验证成立」。
- **依据**：PF-005 §6.2「宿主机不提供租户隔离…允许了，范围就是整台宿主机」；PF-016 §6.20「每台机器上只有自己那一把凭据」（CLI 形态裁定，其理由是「人离职时收不回」）。
- **因果**：共享 cell 上任一租户的工具若落宿主机，其他租户可见；且一台机器上并存多个租户凭据，正是 PF-013 §5.6 反对组织持有凭据时列举的场景。设计只笼统说「框架隔离契约成立」，没有点名这两条并给出前提（共享 cell 上执行环境权限对所有租户 `never-allow` 宿主机、工具一律进沙箱；凭据不落盘或按 R3-A03 的引用模式）。
- **最小修订**：§5.1 把「前提」具体化为上述两条，并说明是「有前提地能」。

### R3-A08 · 治理中心作为部署组件在拓扑里缺席，其存储与「托管 PostgreSQL」不匹配 —— **中**

- **位置**：§2.1 Control 平面「模块化服务 + 控制数据库」；§4.1「首期可以用一个托管 PostgreSQL 集群承载外围控制与业务表」；§2.3「控制关系库可承载框架提供者」；`component-index.json` SP-05 `framework_authority` 无 FC-28，`work-packages.json` SWP-05 却列 FC-28。
- **依据**：baseline FC-28（`apps/tenancy-host`、`packages/infra/storage-sql`；「Docker 单机和同机备份」）；`packages/infra/storage-sql` 现有实现为 SQLite（源码 54 文件含 sqlite 引用，未见 PostgreSQL 驱动）。
- **因果**：框架的账号/成员/凭据权威是治理中心这个可部署应用（PF-017「要么整体起来要么不起来」「备份与恢复交付目标」），它在 SaaS 拓扑里没有独立位置——是与外围模块同进程？独立实例？HA 如何？若「控制关系库承载框架提供者」意味着框架治理跑在 PostgreSQL 上，那需要一个当前不存在的 provider；若治理中心继续用 SQLite，则 §6.3 的备份/PITR 表述对它不适用，需要单独的备份/恢复与 SPOF 说明。
- **最小修订**：拓扑增「治理中心（FC-28）」一个节点，写明其实例数、存储与备份路径；component-index SP-05 补 FC-28；把「PostgreSQL 提供者」或「治理中心独立 SQLite + 自身备份」二选一写成显式假设。

### R3-A09 · 候选 A 未命名围栏原语 —— **中**

- **位置**：`alternatives.md` A「旧 VM 不可达不代表其停止；恢复时必须围栏存储/外部入口」；`saas-design.md` §5.1「取得其已停止的可信证据」。
- **因果**：VM 方案里可用的可信证据是具体的：云 API 确认实例已停止、块存储卷 detach、工作负载身份吊销。若 cell 状态在本地盘（session-log-jsonl 默认写文件），唯一围栏是「实例停止」；若在网络卷，detach 即围栏。设计未说 cell 状态放哪，导致 §5.1 迁移步骤「原 owner 停止并围栏」不可实施化。
- **最小修订**：A 方案写明 cell 持久状态位于可 detach 的网络卷（或托管存储），围栏 = 云 API stop + volume detach + 工作负载身份吊销三者取证。

### R3-A10 · 两个凭据保管方（FC-08 custodian 与 SP-07 vault）—— **低／待裁决**

- **位置**：§2.3 SP-07「自建…凭据桥」；baseline FC-08 `capability.credential-custodian/v2`（accepted，未建包）。
- **后果**：同一 Gmail 账户若日后既经 MCP 端点又经产品适配器接入，会有两份 refresh token 独立刷新——正是 §3.1 自己警告的「并发刷新覆盖」。不据此否决，但应登记为「重复拥有同一事实」的潜在信号，交主线裁决保管方归属。

### R3-A11 · 平台付费来源的滥用控制未列 —— **中**

- **位置**：§8、§11、§6.4；需求 M16.3「平台服务即用」。
- **因果**：一万种子用户 + 注册即得平台模型额度 + 可自主后台工作的 agent，是典型的密钥/额度滥用面（批量注册、prompt 注入诱导高消耗）。这不是吞吐问题，是 P07 与平台账单的安全问题；SP-10 的公平并发只按租户/来源限流，未提注册滥用、异常消耗告警、平台来源熔断。
- **最小修订**：SP-10/SP-11 增「平台付费来源的异常消耗检测与全局熔断」一项，数值待定。

### R3-A12 · OpenRouter 供应商数据策略未纳入「来源集合」核验 —— **低**

- **位置**：§8 OpenRouter 段；P08「只在所许可地点处理和传送资料」。
- **因果**：非受限资料也会经 OpenRouter 路由到具体供应商，供应商的数据留存/训练策略是 P08 的一部分；设计只核验 fallback 与 key 归属。最小修订：把 provider 数据策略设置列入「平台路由设置变化后重新验证」的清单。

## 三、成本／替代方案

### R3-A13 · 三候选实质性与推荐评估 —— 无阻断

三个候选在宿主模型、责任归属、锁定来源上确实不同（VM 常驻 / K8s 编排有状态 cell / 托管平台 + 独立常驻层），不是改名或调参；共同边界清单与六项共同验证合理；没有多活、分片、万实例。A 的选择条件写成了可检验的团队前提，符合小团队约束。

**对推荐 A 的实质反论点（落选方最强论证）**

1. **B 的运维一致性论证**：A 要自写 cell 清单、drain、围栏、重建工具（alternatives A「代价」段承认）。这些恰是 StatefulSet + 受控 operator 已提供骨架的部分（稳定身份、卷绑定、有序更新）。小团队「没有 K8s 经验」的成本是学习成本，而 A 的成本是**长期自维护脚本**，后者随 cell 数线性增长。
2. **B/C 的安全补丁面**：A 把 OS 补丁、镜像、SSH 面、云实例凭证暴露都留给团队；alternatives §A 只以一句「维护 VM 安全更新」带过，未标价。托管 K8s 或托管容器把宿主补丁移到供应商侧。
3. **C 对无状态外围的贴合**：设计自己承认「大多数已注册用户处于休眠」「常规 CRUD 按普通小型 SaaS」——这正是托管容器/函数擅长的形状；A 在外围侧仍需两台 VM 常驻，C 的混合形态（外围托管 + cell 少量 VM）已被推荐吸收，但 alternatives 把 C 整体列为落选而不是把 A 写成「A 的 cell 层 + C 的外围层」。

**A 的已知弱点**：围栏原语未命名（R3-A09）；VM 补丁与镜像供应链人力未量化；cell 状态存放位置未定，直接影响迁移停机与 RPO。

**置信度**：中高。**改票条件**：团队已有能值班的 K8s 能力（→B）；或某托管平台经实测能承载单写常驻 cell 且给出可 detach 的持久卷与实例停止证明（→C 替换 cell 宿主）。

## 四、表达／引用（影响判断的明确问题）

### R3-A16 · §10 EP-01「同事务」与 §4.1、execution-topology EP-01 相互矛盾 —— **中**
§10 EP-01 写「注册键绑定人/个人 tenant/成员和供应意图同事务」，§4.1 与 topology EP-01 都说跨 owner 不假装原子。若指同一 SaaS 库内的意图行，请写成「供应意图与 IdP 绑定同事务；框架账号创建是随后一步」；若真要跨 owner 同提交，须按 §4.1 自己的规则指出共同触碰的表/行。

### R3-A17 · PF-016 §6.17 由 CLI 形态裁定推广到平台 cell 属显式假设 —— **低**
§3.3 引用 §5.6/§6.17 无误（已核原文）。但 §6.17 的理由是「会话与工具明明都在**本机**」「不让网线决定他能不能干手上的活」——写给用户自有据点。把它套到平台运营的云 cell 时，「撤销生效点被拖长」的代价从用户自担变成平台内部分区的代价。按简报这是已裁方向，不重开；只要求正文写一句「本设计把 PF-016 §6.17 作为 cell 的运行前提采用，其原理由针对用户自有据点」，以免后续 reviewer 反复质疑。

### R3-A18 · 「装配给／协议给」未分表 —— **低**
baseline FC-26 边界「跨进程装配给保证需协议重新兑现」。设计 §2.2/§4.3 分散提到 Cordis 进程内事件不跨进程，但没有一张表列出 cell 内由装配给、cell↔外围由协议给的保证（例如：Run 与工具执行的取消传播、会话租户身份不变、日志先于可见）。建议在 §5.1 后加一小表。

### R3-A19 · 框架对用户输入「一律不去重」，接缝应写成查询而非去重 —— **低**
PF-014 §6.3「用户自己发的东西一律不去重」。§4.2 写「harness 必须能关联原请求/查询接受情况」——方向正确，但请明确是**按 SaaS 请求身份查询已受理事实**的接缝，不是期望框架按请求 id 去重；否则实施者可能把重投交给框架。

### R3-A20 · component-index 与 work-packages 的框架依赖不一致 —— **低**
SP-05 `framework_authority` 缺 FC-28（SWP-05 有）；SP-07 在 component-index 无 `framework_authority`（SWP-07 列 FC-07/08/12/29）。不影响判断，转 spec-reviewer 类问题，顺手列出。
