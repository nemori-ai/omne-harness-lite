## 发现（R4-B01 – R4-B08）

### R4-B01 · 中高 · M09.4 / M09.6 / M10.6 / M12.4 —「真实 Schedule Job」的触发方式未定，持久化与成本后果因此不可判

- **出处**：m07-m12.md L706、L773、L1062、L1512；JSON M09.4 `execution[2]`、`unresolved[1]`；work-plan IF-08 `output`。
- **依据**：PF-021 §6.1（租户日程归明确租户，创建者只有用户与 agent，「系统」只能建机械日程且不启动 agent）、§6.3（每个 agent Job 新建会话）、§6.4（完成检查要求候选最终成果与达成依据，Run 结束不算完成）、§6.9（补跑/重叠/通知声明必填，不隐含默认）、§6.10 业务历史本版不删除。
- **因果**：四条 feature 都写「真实声明的处理日程到期产生 Job 并新建专属会话；处理延迟/归并可配置」，但没有说这份 Schedule 是**按事件到达一次性创建**（去抖后到期一次）还是**周期轮询**。两种选择后果不同：(a) 周期轮询——1 万用户 × 每 tick 一个不可删除的作业会话 + 至少一次 OpenRouter 调用（agent 必须调模型才会去调工具），且空 tick 的「无待处理意图」按 §6.4 无法「正常宣告成功」，除非 Job 目标把它定义为合法达成；(b) 按事件一次性——需要产品以**租户归属**经 IF-04 代用户创建 Schedule，每次创建都要明示 §6.9 的三项声明，且「归并」不能靠 §6.11 的同时刻合并（那只在一份 Schedule 内成立），必须由 PWP-10 自己判「该事情已有未到期处理 Schedule 则不再建」。目前谁持有创建权、空 Job 怎么算、归并在哪一层，四条都没写，而这正是本组持久化足迹的主要来源。
- **最小修订**：在 EP-04 步骤 2 或四条 feature 的 `product_work` 里写死一种：推荐语式「PWP-10 以租户归属经 IF-04 创建**一次性**处理 Schedule（延迟=去抖窗口），同一事情存在未到期处理 Schedule 时归并到它而不新建；补跑/重叠声明由产品配置显式给出；不采用无事件的周期轮询」。若选轮询，则必须补「空 Job 的目标定义与完成判据」及会话增长的保留政策。

### R4-B02 · 中高 · M07.6 / M09.2 / M07.4 — 产品澄清项与 PF-008 卡片是两条通道，自然语言回答会被框架记成「拒绝回复」

- **出处**：M07.6 执行链 2–3（L177–178：「SP-03/SP-08 创建可追溯澄清项…用户回答进入原会话」）、M09.2 步骤 3（L641「SP-03/框架澄清」）、M07.4 步骤 3（L116「框架 HITL」）。
- **依据**：PF-007 §6.11 `ask` 前台阻塞、不可转后台、无超时；PF-008 §6.4 一张卡只能在两个答复入口之一答一次；**PF-014 §5.4 第 4–5 行：loop 停在 `Ask()` 等人时用户插队一句话 ⇒ 「中断这次执行，记作人拒绝回复」；运行等待态上悬着卡片时插队 ⇒ 卡片从决策池移除、每张记作「人明确拒绝回复」**。
- **因果**：M07.6 允许「自然语言补充」并让「用户回答进入原会话」。若框架 Run 正停在 Ask 卡片上，用户在聊天框里用自然语言回答（客户端通常按插队/新输入发送），PF-014 会把它当作对卡片的**拒绝**，agent 据此「改道」——恰与 M07.6 验收「复用已明确回答、不重复问时区」相反；若客户端按排队发送，则卡片永远悬着、回答排在队列里无人消费。两条 feature 都没写产品澄清项与 PF-008 卡片之间是「同一张卡的投影」还是「Run 不等卡、由事情等」。
- **最小修订**：一句话选定其一并写进 M07.6/M09.2/M07.4 的 `commit_point`：「产品澄清项即 PF-008 卡片的投影；自然语言回答由 PWP-07 解释后经 PF-008 答复入口回卡（或显式记为不回答），不作为新输入送入受理面」；或「框架 Run 不以 Ask 等待产品澄清，缺事实即终结 Run，由产品事情持有等待，回答到达后作为新输入开新 Run」。两者都可；不选则 Run 生命周期与验收相互矛盾。

### R4-B03 · 中高 · M08.9 —「明确删除」的传播范围没有把框架会话日志与日程业务历史列为不可达

- **出处**：M08.9 执行链 3（L579「删除传播到主存储、索引和访问票据」）、验收负向（L588）。
- **依据**：PF-010 §6.12 记录里的消息一条都不能擦除；PF-021 §6.10 日程/Job/通知业务历史本版不删除；`data.content-blocks/v3` 文本块内联、`renderings/transcript` 内联（S-19），文件/图像可为 AttachmentRef `(storage,key)` 引用（S-21）；EP-10 步骤 3 已承认「框架未支持清理的范围进入明确保留/未覆盖清单」。
- **因果**：资料一旦进入会话（粘贴文本、OCR 派生文本、模型对材料的引用输出、图像 transcript），这些内容内联在会话日志里，SP-04 删除到不了；AttachmentRef 只保引用，字节删除后日志中的引用悬空。M08.9 只写了 SP-04/SP-12 的传播链，用户看到的「已删除」会与会话历史仍可见的内容矛盾——这是本组唯一一处产品承诺超出持久化权威可达范围的地方。
- **最小修订**：M08.9 `authoritative_facts` 加一行「框架会话日志中已内联的内容与 Job/通知业务历史不在删除路径内，按 EP-10 进入未覆盖清单并对用户可见；日志中的 AttachmentRef 在字节删除后读取为不可用而非重定向」。一句话可闭合，但必须闭合，否则 S23/X27 的删除后果说明失真。

### R4-B04 · 中 · M10.2 / M10.5 / M10.7 —「送达」一词跨了两种不重合的语义

- **出处**：M10.2 步骤 3（L935「框架通知/作业会话+SP-08：到时提醒走真实送达」）、M10.5 步骤 4、M10.7 验收正向（L1105）。
- **依据**：PF-021 §6.5「持久进入该租户可取回的范围即算送达；不要求用户在线或已阅读，不引入邮件、短信等带外渠道」；框架基线 FC-22 边界同此。
- **因果**：FC-22 的「送达」是框架侧事实（进入租户可取回范围），用户看到的「已提醒到手机」是 SP-08 自己的投递回执。三条 feature 把两者写在同一步，验收「提醒已建立/已送达」若按 FC-22 口径判，会在推送失败时仍显示已送达——与 M10.7 负向「送达失败」自相矛盾。
- **最小修订**：在 M10.2 `commit_point` 写「FC-22 送达=框架通知事实，SP-08 投递回执=用户可见的已提醒；前者是后者的输入，不能替代」；M10.5/M10.7 引用同一句。

### R4-B05 · 中 · M09.4 / M09.6 — 执行链依赖 PF-021，但「框架依据」表未列 FC-21，PF-021 条款被塞进 FC-15 条目

### R4-B06 · 中 · M12.2 — 把 FC-10 沙箱当成对外托管页面的隔离依据

- **出处**：M12.2 框架依据 FC-10（L1442）、执行链 2（L1448「在隔离构建/运行环境启动…生成代码不持主应用 cookie/密钥」）。

### R4-B07 · 低中 · M08.2 / M08.4 / M11.7 / M12.3 — SP-04 与 PF-020 Workspace 对「文件版本」的双重持有未写明主从
