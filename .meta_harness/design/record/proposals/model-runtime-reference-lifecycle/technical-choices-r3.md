# 候选 A 的技术收敛：不把未定事项交给实现者

2026-09-29，revision 3；**作者技术选择，待独立评审与主线接受**。本页在三候选责任边界之内收敛技术选项；不是已发布规格，不释放实现。取代 [revision 1](technical-choices.md) 的 T3/T4/T6 持久源选择及后继版本预估：独立评审指出 PF-012 §5.2 的执行事实唯一日志要求，不能由 PF-015 非日志设置/注册例外推出完整执行事实可独立外置。修订记录原错误，保留 A 能力内边界。实现只在后继契约及 realization 被接受后启动。

## T1 一个模型能力，两种寿命

沿已有 `createModelRuntime` 与 `modelRuntime` 服务扩面。原 `CallContainerStore` 仍持真正执行 owner；service 创建/委托实际执行，消费者只取得撤除自己的等待与观察的资源。执行不会挂到访问这次服务的 caller Context 上。Cordis 只负责装配与消费 effect 的清理，原调用的显式 owner 负责实际请求、流装配、待确认追加和 lease。

新增的定位资源不另有领域身份；`CallKey={session,callId}` 是唯一序列化引用。调用方持有的 ref 没有方法、AbortSignal、Context、Promise 或权限令牌。租户、原 Run/attempt 和真正执行代际从权威绑定取得；不得根据请求者此刻的 Run 改写原归属。

单机首发每份真实调用只有一个执行 owner。未来的远程 owner 发现/挂接必须另有协议，不将进程内 Map 推广成分布式锁。真实 service owner 关闭仍执行现有停止/认回/释放；服务换代后新实例不因 ref 存在而重发。

## T2 解析和借用消费资源独立于 open/dispatch

后继 RT 增加一个明确操作，候选语言绑定名 `acquireCall`：显式 CallKey + 当前访问上下文 + 观察选项。它返回已授权的当前状态读数，以及适用时的可释放消费资源；不能顺带 open、dispatch、reconcile、interrupt 或 settle。

- 在途：在一次本地准入区间绑定精确原容器代际，再返回原执行的可等结果及流快照/后续观察。竞争中已完成则转读取原结果，不能新建发送。
- 完成待处分：读取原完整事实，可取得当前合法处分的原结果入口；是否能处分是与读权分开的资格判定。
- 已有 final response/调用终结：读原事实。结果不迁到查询者 Run，不自动进入 after_model_call，也不赋予旧失败主体在新 Run 上重试的权力。
- 确认失联：返回明确恢复所需状态或沿既有恢复入口报告；本操作无恢复副作用。未知/超时/本地查无一律不能走此分支。
- 无权、来源不可读、合法 ref 查无、服务停止分别沿后继契约的封闭失败集合表达；无权先于存在性查询，不能用 callNotFound 泄露对象。

消费资源 `release` 幂等且仅撤本消费者；等待者 abort 只取消本次等待。普通消费资源没有 execution close 能力。其 wait 不能无限持有一个已释放观察端，慢观察者按显式容量策略失败/撤除，实际执行仍由 owner 独立收尾。

原十三操作继续保留各自责任；不以维持数量为由把 acquireCall 塞进 readAttempts 的默认纯历史读取。独立公共 invokeModel 不需要这些运行时身份与持久端口。

## T3 发前 ref 的承诺边界

openCall 成功返回 CallKey 之前必须确认同一 Session 日志上的调用创建事实已提交；该事实或其可核内容引用必须保留：调用身份、创建租户、Session/原 Run/原 attempt 的来源、实际采用绑定，以及请求输入或能精确恢复它的引用。记录中绝不保存凭据值；引用内容必须有可取得且不可偷换的版本/摘要依据，单存可变档案名不足。

“已创建”只代表接受了调用及原输入，不代表已发送。首次 dispatch 仍以原已出门记录为网络前锚；模型设置变化不能改这份已创建绑定。发前崩溃后能读出“已创建而尚未确认发送”，后继有资格者可按独立 dispatch 规则继续，acquireCall 自身不发送。

open 记录提交回执未知时，禁止返回成功或第二次铸号重试。保留同一创建操作/键的认回责任；权威读回明确已有原记录可返回原 key，明确未提交方可沿原 key 重送，无法确认则 unavailable。该规则不保证客户端在获得任何返回前就知道随机新 key；服务自己必须保留原操作责任，客户端请求关联的幂等形状由后继九项规格明确。

## T4 完整结果与消费者处分分开持久

MR9 的 PendingModelResponse 是完整事实但当前明令未保存，final ModelResponse 又必须有真实 disposition。因此不能仅靠 Map 保存 Promise，也不能为了提前落账就预填 consumed/persisted。

作者选择在**同一 Session 日志持久记录未处分完整结果已经存在的事实**。原 final response 仍是唯一最终回复处分记录。日志为调用创建、进展、完成、处分/最终账的权威；模型私有行只能是有来源进度的投影，不能成为 created/pending 事实的另一权威。

完整输入、pending payload 可直接承载于技术记录或按已规定的不可变内容引用外存。这里选择外存不可变 payload、同日志记录可核引用：减少大块结果在 pending/final 两阶段重复内联；外部存储只保存不可变内容，不拥有调用阶段。模型提供者先确认 payload 可取得，再写日志事实 marker，marker 原子提交是该 pending 事实可恢复/可对外宣称的唯一发布点。marker 至少能核 CallKey/dispatch/ResponseId、内容引用与摘要及来源/时刻；精确字段与引用类型由后继 MS/MR 数据契约拥有。创建输入引用采用同一发布原则。

没有 marker 的 blob 不构成执行/结果存在，也不允许发送或消费；marker 提交回执 unknown 时保持同一键/原 payload，权威认回，不铸新 ResponseId 或另写不同结果。payload 写成功而 marker 确认未提交只留下未发布内容，清理不影响任何已发布调用；payload 不可读时明确 unavailable，不能把该事实解释为不存在或失败。不把 marker 与 blob 视为跨存储同一事务，这里只要求先内容后引用的安全序；可回收内容必须保证仍被有效记录引用时不可删除。

保存顺序：完整 pending payload 持久且日志结果事实 marker 提交确认后，才向任何后继消费者宣称可恢复取得结果。真实流已发出的部分不被保存失败抹掉；失败时 owner 保留完整事实与原写任务，暴露 unavailable，禁止伪报可恢复。零消费者数不触发处分、不丢 pending，不把服务真实关闭后的完整结果改写为 interrupted。

处分继续沿原日志响应唯一键及原子消息+响应批：先确认原 final batch，再更新模型状态投影；后一步失败不回滚已发生 final。查询遇旧 pending 投影时先核对应的日志来源进度/原 final，不能重新处分；日志同时存在 pending marker 与 final 不表示两笔费用。已完成 pending 的真实 usage/cost 必须进入原 Run/Session 当前总账，不能等一个可能永远不来的处分。后继 CA 及成本读面明确按同 ResponseId 合并：无 final 时取已提交结果事实，final 确认后由同次 final 接替；两者不相加，unknown 不填零，补账仍覆盖同一原请求的事实。结果内容与费用的来源必须同一 dispatch；处分不能修改已发生费用。未收尾流沿既有“不补一笔不存在的账”边界，此处只扩已收尾且事实已发布的结果。这个继承成本要求不可选，不以单次查询能看到费用冒充总账完整。

后续处分只可确定 disposition 与实际提交时 late，不得改其余原事实。同 Session 后继 Run 只读不需要原 Run 仍活；原 Run 已终态的结果不能借查询产生新工作。无人再处分与真实 owner 关闭时，保留未处分可查事实。后继 RT 明确分开调用收场与回复处分：完整/截短回复的结果事实 marker 提交时调用进入 complete，有回复的用户中断进入 interrupted；稍后 persisted/vetoed/consumed 只改变处分事实，不重新改变调用终态。已开口后的 failed/无回复中断仍沿原直接 final 结算路径；首内容前失败仍 awaiting_decision，不偷改重试政策。实际传输、门和写任务停止且已确认结果事实持久之后，可释放原执行资源/lease，未处分事实由日志及不可变内容引用保留，不靠活执行容器永久占资源。settleReply 对已终态而处分待定的原结果仍可在具备当前合法处分资格时提交；已确认 final 吸收，重复只认回原 final。真正 owner 关闭不会把已完成结果改成 interrupted，也不假造消费。

## T5 原执行事实与当前尝试新动作分开授权

已获准发送的实际执行跨消费者换代后，首内容与完成事实仍属原 dispatch。`model_call_opened` 的写入必须验证原 dispatch 事实、尚无冲突响应及合法原执行资格，再以同一日志的条件提交；不能机械使用新 attemptId 改归属，也不能让旧 Agent 的新 dispatch 绕过当前尝试 fence。

技术方向是保留“新动作” fenced、“原执行事实”不因尝试被替换失权的区分。opened 拟复用 settlement 的完整前缀+tailEquals 重读方式，但具体 append 分类与 SL3 S10 冲突须在后继 SL/RT 契约表达，不能只把代码 fence 改成 unfenced。取消意图/归档与 opened 的相对顺序必须落在同一本 Session 日志的提交次序；该日志是两写方共同对象。取消已先获准生效则不对观察者放出新内容，已开口事实不因此被回写删除。

旧请求结果可记录与旧 Agent 可推进是两种资格。处分请求按当前结果消费者资格核验原用途/等待关联；控制另验取消资格；read/acquire 绝不兼授两者。后继 Run “查旧结果”不能产生原失败主体的再次发送许可。

## T6 直接查询、未知与失联

模型状态投影按 CallKey 索引；创建/pending/final 来源都带日志绑定/代际、提交坐标及原记录摘要。指定调用查询不每次从日志头扫。行中一切状态可由同一本日志及其不可变内容引用重建，不以最近写入时间充当可信新鲜度。投影更新与日志追加若不共享一次存储提交，则必须先取日志头进度核新鲜度，过期时追尾/重建期间返回 unavailable，不把多存储提交假称原子。正常维护要由追加交接更新投影，使正常当前值读取不退化为每次扫完整历史；故障/冷重建开销单列。

在途状态须同时说明哪个实际 owner 在履责。Map absent 只说明本实例没有它；新进程必须先取得唯一恢复权并实际确认旧网络/写者停止，才能沿原 reconcile 规则判定。单机装配可由原 host 保留集合与真实物理停止端口给出证据，不以可随意伪造的 alive=false 布尔量替代。源不可读、代际不可认回、unknown append 尚未消除时返回 unavailable 并保留引用。

final 事实具有终态吸收性，可按已确认的原来源直接读取；状态投影落后时不能冒充当前。不把一次可能线性的恢复/重建混入每次正常查询；重建期间明确不可用。性能验收分正常指定读取、日志追尾/认回与结果列表，分别计 I/O 和返回规模。

## 后继规格与验证门

预期有限改动是 RT11（状态/新操作/身份发布与恢复）、MR10（未处分完整事实的持久 payload 角色及不可变约束）、MS7（调用创建/结果存在两类技术记录及引用形状）、CA3（已完成未处分结果按 ResponseId 计账、final 接替及补账关系）、SL4（已准入执行事实的授权提交分类，若独立审查确认 SL3 已能表达则免升）、runtime v20（内部 registry/存储/consumer effect 组合）。Schema 跨引用必须检查环与责任归属：MS 记录只拥有来源定位/引用，MR 继续拥有完整响应事实；不在两处定义同一 payload。原13操作的其它语义与runner规则保持。所有版本目前只是候选目标，须先核 registry 避免撞号。

验证必须含消费者归零、多消费者竞争、返回 ref 后发前崩溃、完整 pending 保存与 final 批 unknown、跨尝试 opened、跨租户/撤权、原 Run 终态后的旧结果、旧注册代际迟到清理、首内容后失联零发送、真实 owner 关闭和索引增长读取。TLA 模型至少覆盖前六类有并发/跨提交的状态性质，并有有针对性的负控；真实网络/日志/存储故障测试不由有限状态模型代替。
