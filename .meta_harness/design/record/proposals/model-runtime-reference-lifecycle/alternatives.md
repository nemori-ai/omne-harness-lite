# 候选与取舍

## 同一个选择对象与必要约束

选择“按稳定引用找到原模型执行／结果、取得消费资源”的能力边界和驱动方式。全部候选都必须满足 [正文的性质分组](design.md#性质覆盖范围与演化责任)；**没有一个候选可以省掉发前身份、零消费者结果留存或当前授权**。责任切分与所需耐久机制是两个维度：A 也可新增必要记录，C 也不得把模型事实变成第二套权威。

三个候选都保持公开函数层独立、全部发送经既有准入/传输、不复制 Session/Run 治理、不采用 DSH Agent 原语。具体字段、服务键、操作名与存储结构均未定稿。

## 候选 A：现有模型服务扩展解析和消费面

**责任与机制。**定位、授权、消费者取得及执行阶段解释都由现 modelRuntime 承担；原 CallContainerStore 管活执行与实际 owner，原日志管耐久事实，增加有来源进度的查询投影。执行仍由当前直接调用路径驱动；消费者等待/观察只是可撤资源，不拥有连接。发前引用与未处分结果必要的耐久保护也归该模型能力协调，不以“已有日志”冒充已解决。

**性质保护点。**身份/输入/原账在现调用绑定和结算路径；零消费者继续在原执行 owner；重等从原容器取得资源，终态从原事实读取；opened 与 pending 的新保证在同一能力演进后交给原日志提交边界。Session/Run 的当前权限与终态是显式输入，模型不承接其全部状态机。所有准入与计量继续过原路径。

**可能失去保护点的性质。**若仅加 `get` 和 Promise 引用，INV-02、LIV-01/02 的发前和 pending 耐久仍无保护；若新消费者可直接带旧 outcome 调 settleReply，INV-06 的唯一合法处分会暴露。A 必须补这两处精确语义才可采用，并不能凭现类/Map复用声称通过。

**反查信号。**现执行/事实责任集中，少一个新的状态 owner；但发前记录或 pending 若落在独立后端且与原日志要求同提交，仍出现真实跨 owner 协调。必须命名共同存储对象或明确可恢复协议，不能用进程锁解决。若反复要求定位与执行一起发布，属候选 A 已知演化耦合。

**可计数代价（结构下界，非工时估算）。**新增独立模型能力 0；新增独立 registry 插件 0；新增公开行为至少 1 组（解析/取得消费资源，能否合一待九项规格）；需精化 2 个耐久断点（发前公布、未处分结果）；1 条 opened 写授权边界；所有消费入口/文档/验证须随精确版本同步。当前状态投影是每调用数据，不导致每调用一条 fiber。

**关键反例。**A 发出引用后尚未 dispatch 就进程死亡，后继只能“查无”；或零消费者完成后只有内存回复，新消费者到来前实例换代导致丢结果。这两种都否定“只扩 get 即完成”的 A 简化版，但不自动否定补足耐久的 A。

**收益与风险。**复用原调用 owner、日志与结算，最少引入新的同步责任；风险是公开面变宽和定位可用性仍受同一个模型提供者状态影响。提供者撤除后从新实例读耐久事实如何恢复，需明确，不能保证整个服务缺席时仍可查询。

## 候选 B：独立模型定位服务，与执行服务分工

**责任与机制。**独立的模型 registry 负责引用解析、活实例登记/代际、读授权入口和消费资源分发；现 modelRuntime 负责发送、首内容、控制、结果与原账。registry 读取同一原日志与派生查询，不自行定义模型终态。其独立责任是假设“即使执行提供者替换或不可用，查询服务仍独立存在”；该需求是否必要尚无证据。仍是模型专属，不扩通用 runtime 平台。

**性质保护点。**独立 registry 保留定位入口和精确实例登记，执行 owner 不挂消费者；原执行写原日志。发布引用与执行登记通过显式握手，登记携带代际/原身份以防旧注销删新实例；耐久身份、pending 保留与 opened 权限仍须由模型执行侧同原日志闭合，独立服务本身不会获得这些保证。

**可能失去保护点的性质。**INV-02、SAF-02 在“registry 已发布但执行未接纳”窗口失去原本单方控制；INV-06/LIV-02 在 lookup→attach 跨提供者换代时有竞态；执行完成与 registry 注销/状态更新不同步会把终态误读为 lost。若 registry 缓存完整终态而不再校原日志，又形成重复权威。

**反查信号。**至少多 1 个模型能力 owner；活执行登记与发布／终态注销至少 2 条跨 owner 交接。若要求这两方同提交且无共同存储对象，即边界警报；若每次模型阶段新增都同时改 registry 与 executor，变化并未隔离。反之只传通用定位信息而全部模型状态沿原读端取得，可以减少重复，但独立能力的价值也须重证。

**可计数代价。**相对 A 至少多 1 独立插件/服务契约、1 段 registry↔执行者协议和两方装卸组合验收；登记/替换/撤除与 attach/finish 的竞态至少新增 1 组形式义务。发前/未处分 2 断点、opened 1 边界及当前查询索引代价与 A 相同，不能算作 B 省下的工作。服务实例可按部署装配，不按 Session×Run 叉乘。

**关键反例。**registry 查到 owner X，X 完成并卸载，替代 owner Y 使用同键；X 的迟到注销删掉 Y，或旧句柄从 registry 成功返回后再无结果入口。须精确实例比较与授权后 attach 的明确收敛协议，单独 Map 服务不足以解决。

**收益与风险。**查找实现可独立演化，多个受授权消费者无需依赖执行提供者的全部公开面；若这种独立可用性有真实要求，新增边界有价值。风险是状态重复、失败诊断归属不清与跨 owner 同步成本。当前材料没有证明独立生命周期/消费者必须由第二服务满足。

## 候选 C：同一日志上的耐久模型动作协调器驱动执行

**责任与机制。**模型能力先将可恢复的调用接纳/动作意图及结果事实写入同一 Session 日志；模型专属协调器从这些事实驱动原执行函数，进程内实例索引只作执行存在的线索。公开请求的含义由“直接驱动执行并保留可查引用”变为“耐久接纳意图，协调器据其推进”；定位、状态查询和结果重取从有来源进度的投影取得。该协调器属于 model runtime，不处理 Session/Run 调度，也不成为通用 job 系统。

**性质保护点。**INV-02/LIV-01/02 的可恢复事实在发前接纳与未处分完成记录；消费者出现/消失不驱动执行状态，重启后协调器按原身份接回。原归属、输入、首内容和结算仍受模型规则约束。持久意图不是可重复发送许可：网络 send 和记录无法凭本地事务原子化，仍须辨别旧执行是否活、已发生 send、unknown 与首内容。

**可能失去保护点的性质。**INV-06、SAF-02/03 在协调器重放意图时最脆弱：若“有请求未完成”就再发，等于制造重复上游请求；不能用幂等任务键假称上游只执行一次。执行 owner 与协调器代际没有唯一推进协议时，旧/新 writer 并发破坏原批结算与授权。零消费者回复记录也不能预先赋予消费处分。

**反查信号。**采用同一原日志可避免第二份状态权威，但产生新的持久动作接纳责任；若另开 job store 写状态、日志再记事实，就出现两份同调用状态及跨 owner 同提交。协调器若复制 Run 的任务等待/终态逻辑，将越界并反复同步修改。保留模型调用级别、只驱动原模型操作才能守住范围。

**可计数代价。**相对 A 至少新增 1 个耐久动作协调责任（不预定独立服务）、1 套动作接纳/认回/推进幂等协议、1 套旧新协调者与在途执行的并发证明；至少覆盖接纳、发送不确定、首内容、未处分结果、处分 5 个恢复切面。不是“一条多写日志”的参数变化。发前和 pending 已有断点可以融入统一协议，但不会降低 opened、授权和未知费用的原义务。

**关键反例。**意图已耐久，上游已接请求，实际发送确认尚未被协调器记下就重启；重放导致重复发送/计费。正确 C 必须保留不确定性和恢复准入，不能以耐久队列自动重试替代 PF-013 的规则。

**收益与风险。**当大量模型动作需要统一跨进程接纳、恢复和排空，命令与执行的分离会形成可重复的责任闭合；具体完成不要求消费者常驻。风险是把原本局部 ref 扩展变成模型专属调度框架；当前单机、既有 owner 保留和窄缺口未证明需此强度。本候选未承诺多节点一致性。

## 推荐、改票条件与最小区分证据

**作者推荐 A，前提是必要耐久与写权保护点由同一模型责任闭合。**已有能力的归属、内容门和结算可复用，当前没有独立定位生命周期或耐久调度的必要性证据。推荐 A 不代表可以跳过 design.md 的六项缺口，更不代表主线已完成四表或接受。

| 候选 | 什么证据改变票 | 最小区分调查；本次均未执行 |
|---|---|---|
| A → B | 明确要求模型执行提供者不可用/换代期间查询入口仍可独立服务，且 A 的原日志读面或内部组合无法满足；新边界能把一次真实修改限制在 registry | 在固定输入下撤执行提供者，比较旧调用状态读与活性判断所需依赖；若仅历史读就够，不能据此要求新 registry |
| A → C | 发前接纳和未处分结果的恢复都要求模型动作由同一耐久协调者驱动，A 被迫反复增加相同恢复协议，且明确的故障轨迹证明集中协调能减少重复责任 | 同一 CallKey 做发前成功后崩溃、上游接收后未知、完成待处分后重启三轨；数清新增持久写方和恢复协议，不按代码行数评价 |
| B → A | 读取、发布、取消、阶段新增始终跨两方同步修改；独立 registry 没有可独立使用/更换的消费者结果 | 以 opened 和 pending 两条真实变更做消费者/owner影响表；若 B 两边都改而 A 一边可闭合，回 A |
| C → A/B | 原 owner + 必要同日志事实即可通过全部局部故障轨迹；耐久动作协议只增加发送不确定性分支而不提供要求中的新增保证 | 对相同输入、同失效点比较行为保护和新增状态数；没有统一动作驱动需求则收回协调器 |

**共同的反证门。**任何候选只要把 Map absent 当失联、把消费者 release 当 cancel、把日志投影当第二权威、把 no consumer 当 consumed、把查询后继 Run 当原归属迁移，均不能按当前产品采用。改票改变机制和边界，不能悄悄改变这些需求。

候选 B/C 的合理成本不是拒绝需求的理由；若 A 的责任边界确实不能承载，应重分解。未来 Tool/Agent 同样需要引用解析可作为后续独立研究输入，本次没有第二个已验证消费者，不因此预建通用 registry 抽象。
