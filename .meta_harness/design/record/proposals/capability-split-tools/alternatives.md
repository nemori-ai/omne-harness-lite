# 候选与取舍

## 选择对象与必要约束

选择对象、八条必要性质 K-1～K-8、五个对象的归属画像，都见 [design.md](design.md#需要作出的选择)。

**不可调整的**：K-1～K-8；[D-032](../../decisions/tool-execution-runtime-baseline/README.md)（运行时自研，执行宿主不在 agent runtime 之下）；
[D-037](../../decisions/mcp-client-adoption/README.md)（官方 SDK 上自写薄桥）；[D-033](../../decisions/hooks-compat-baseline/README.md)（兼容层的 fork 边界）；
[D-058](../../decisions/message-and-shape-rulings/README.md) Q8、Q10、Q15。

**可调整的**：能力契约的数目、插件的数目与粒度、领域归属、节点名、执行宿主的 fiber 形状。

**所有候选共有的两条反查信号**（跨 owner 同提交：执行记录 × 会话日志；重复拥有同一事实：注册表快照 × 装配清单）不区分候选，
承接办法见 [design.md 剩余责任](design.md#剩余责任与能力演化)；下文只写**因候选而不同**的信号。

## 五个候选

| 可识别候选及范围 | 如何兑现必要性质 | 差异、总负担及关键反例 | 当前证据与缺口 |
|---|---|---|---|
| **A 一个插件承载全部**：一个领域 `tools`，一个插件、一条宿主 fiber 提供运行时、注册表、派发器、桥四个服务（放行判断只有接口，装不进来）；契约可以仍是五份，也可以并成一份 | K-1、K-2、K-5、K-7 保住；**K-3、K-6、K-8 失去** | 装配最简单，注册表不用可选取用就能直接读执行者表和桥的可用性。**反例**：桥的一次 SDK 升级，或者改一个连接超时的默认值，整个插件都要重跑，会话里正在跑的构建落「失败 · 异常中断」——而它跟 MCP 毫无关系 | 结构性反例由 [`plugin-body-reruns-on-provider-change`](../../../basis/cordis/plugin-body-reruns-on-provider-change.md) ＋ H-1 推出；机制读数的自证分解 δ 已排除它 |
| **B 五个插件同在 `tools`**（机制读数草图原样）：每份契约一个插件；执行宿主只 inject 存储、时钟；五个对象和 hooks 兼容层都在 `tools` | K-1～K-8 全部保住；K-3 的前提是存储、时钟不在进程内换代 | 本批只拍一个领域名。**反例**：派发器的拥有者、宿主和唯一的运行时调用方都在 agent loop 一侧；读数之后给它追加的裁定里，改语义的有五条是 PF-012 的 loop 语义，零条涉及执行运行时——`tools` 里的这个包会跟着 PF-012 反复改；agent loop 立节点之后，还要把两个节点搬走 | 同步修改的证据只有那一批主线裁定（待确认）；agent loop 还没有契约可以对照 |
| **C 五个插件按拥有者分领域**（**推荐**）：插件边界与 B 相同；运行时、注册表、MCP 桥、放行接口在 `tools`；**派发器和 hooks 兼容层在 agent loop 那一侧的领域** | 与 B 相同 | 每个节点都落在它拥有的产品 topic 所在的领域，以后不用搬。代价：本批要拍两个领域名；loop 那一侧的领域暂时只有两个节点，而它的主体（agent loop）还没有契约，这个边界要等 agent loop 契约起草时才会被真正检验 | 同 B |
| **D 执行宿主拆成两条 fiber**（机制读数自证分解 ζ）：在 C（或 B）的边界上，执行宿主改为「活体持有者（父，不 inject）＋ 服务门面（子，inject 存储、时钟）」 | K-3 加强：存储、时钟换代只重跑门面，在途执行不动；**K-7 变成有前提的**：门面必须是执行记录唯一的写入者 | **反例**：门面缺席（存储正在换代）期间，一次执行完成了，它的收场只能停放在持有者的内存里；这时进程被杀，恢复扫描会把一次确实产出过结果的执行落成「失败 · 异常中断」。另外，持有者若以服务键对外，任何插件都能 `ctx.get` 到它，绕开首胜写直接停掉执行（[`inject-has-no-optional-form`](../../../basis/cordis/inject-has-no-optional-form.md)：「不 inject」不是访问控制） | 本版存储、时钟的换代是启动期事件（[`infra/storage-sql`](../../../realization/packages/infra/storage-sql/README.md) 的升级守卫在插件体内，配置错误即启动失败）；H-3「子插件重跑不牵连父」无 probe |
| **E 派发器并进 agent loop 的提供者**（机制读数自证分解 γ）：派发器的契约并进 agent loop 能力，或契约保留、由 agent loop 插件兑现；其余同 C | K-1～K-8 保住 | 少一个服务、少一条依赖边。**反例**：agent loop 能力**还没有契约**——派发器的契约要么等它，要么以后再并进去；拓展件的作者（三个块的自带件、compat 件、租户自己的件）只消费拓展点协议那一半，却要跟着 agent loop 的每次版本变化走；登记目标变成一个依赖很多的插件，它每换代一次，所有贡献者都要重新登记 | 两份读数都判「可行，但不更便宜」 |

候选不以改名或参数变化凑数：A 与 E 改的是插件和契约的数目，D 改的是执行宿主的 fiber 结构，B 与 C 改的是领域边界。
落选方各有一条可以复述的反例或代价，下面逐个展开。

### A 一个插件承载全部

- **失去的保护点**：K-3、K-6、K-8。另外，放行判断本批「只有接口、没有提供者」，而这个一体插件没法表达「四个服务都在、只有这一份不在」——所以放行提供者只能另成插件，A 实际上是「四合一 ＋ 放行另立」。
- **反查信号**：**反复同步修改**。四个维度各自的改动——执行语义、会话可见集合、拓展点协议、MCP 桥接范围——全都落在同一个包、同一个插件上；
  如果契约也并成一份，所有消费者（agent loop、`BkgJobs()`、斜杠命令识别、hooks 导入、`Tools()`/`Skills()`）都会看到与自己无关的版本变化。
- **可计数代价**：执行宿主的必需依赖是 4 个（存储、时钟、资产求值、会话日志读写）；即使把后两个改成可选取用压到 2 个，**会让全部在途执行一齐停机的更新来源仍是 4 个维度**，而 B 和 C 只有 1 个。
- **何时它更好**：进程从不就地更新任何维度、只随整体重启，而且放弃可独立部署。这与 [SYS-DYNAMIC](../../../foundation/fully-dynamic-system/requirements.md) C2、[SYS-DEPLOY](../../../foundation/cross-system-constraints/requirements.md#sys-deploy) 都相左。

### B 五个插件同在 tools

- **性质承载**：与 C 完全相同。
- **失去的保护点**：没有。失去的是**拥有者对齐**——`tools` 领域里放着一个 PF-012 拥有的能力。
- **反查信号**：**跨领域的反复同步修改**。派发器 ↔ agent loop：派发返回的每一种效果（否决、停住、出卡、重试、改目标模型）都由 agent loop 的状态转移消费；
  读数之后给派发器追加的裁定里，五条改的是 PF-012 的 loop 语义，一张自带件缺席处置表跨四个 topic，**零条涉及执行运行时**（[归属画像](design.md#五个对象的归属画像)）。hooks 兼容层同理。
- **可计数代价**：本批拍板的领域名 1 个；预期的后续搬迁 2 个节点（派发器、hooks 兼容），连同契约 README 的「提供者映射」、bindings 和投影里的引用一起改。在源码存在之前搬，成本低；源码存在之后，就是搬目录加改导入（[D-024](../../decisions/tenancy-domain-name/README.md) 的理由）。
- **何时它更好**：产品负责人只想在本批拍一个领域名，把 agent loop 那一侧的领域名留到 agent loop 契约开工时再定。

### C 五个插件按拥有者分领域

- **性质承载**：K-1～K-8 与 B 相同。
- **失去的保护点**：没有。
- **反查信号**：`tools` 里的放行提供者和卸载判定，要**跨领域**向 loop 那一侧的派发器登记；块 C 的模态转换和重试本来就是跨领域登记。
  这些都是经公开契约（`data.loop-extension` 加上派发器的登记条款）的贡献，**不是同步修改的信号**。没有因 C 而新出现的信号。
- **可计数代价**：本批要拍板的领域名 2 个；后续搬迁 0 个；loop 那一侧的领域暂时只有两个节点。
- **弱点**：loop 那一侧的领域边界要到 agent loop 契约起草时才会被真正检验。到那时如果发现 agent loop 本身应该落进别的领域，这两个节点还是要跟着走——只不过要搬也是整个领域一起搬，而不是从 `tools` 里单独拆出来。

### D 执行宿主拆成两条 fiber

- **形状**：活体持有者是父插件，不 inject 任何服务，持有活体表和各条执行 fiber；服务门面是它的子插件，inject 存储和时钟，对外提供运行时服务，是执行记录唯一的写入者。
  门面重跑不牵连父（H-3）；父卸载带走门面和全部执行（H-1）。执行完成时，经父给子的进程内交接把收场交给门面；门面不在，就先停放。
- **加强的保护点**：K-3——存储或时钟换代时，在途执行不动。
- **变成有前提的**：K-7。持有者一旦写行，就出现第二个写入者；停放期间，收场只存在于内存。
- **反查信号**：**重复拥有同一事实**。门面缺席期间，收场停放在持有者那里，行上还没有；「这次执行还活着吗」由持有者回答，行上的状态由门面写，两处要对齐。
- **可计数代价**：多 1 个插件和 fiber；多 1 个进程内交接接口；多 1 个停放队列，以及它自己的一种失败（见反例）；装卸配对多 1 行；多 1 条 probe（H-3）；
  还要多一项结构检查：持有者不得以服务键对外，否则任何插件都能 `ctx.get` 到它。
- **何时它更好**：存储、时钟在进程内换代成为运行期常态。

### E 派发器并进 agent loop

- **性质承载**：K-1～K-8 保住。
- **失去的保护点**：没有直接失去的；失去的是**拓展点协议独立定版本的能力**——它有 agent loop 之外的消费者：拓展件作者按 `data.loop-extension` 写件、hooks 兼容层、三个块的自带件。
  手册的判据是：确认一项独立维度，就给它独立的插件（[提供者投影](../../../../agents/skills/harness-design-handbook/canonical/references/project.md#从能力维度确定插件边界)）。E 等于主张派发器不是独立维度，而它自己的变化原因（结论集合、报错策略、回放）和消费者都说明它是。
- **反查信号**：反复同步修改**移到了契约层**——拓展点协议每改一次，agent loop 契约就出一个新版本；拓展件作者会看到与自己无关的 agent loop 修订。
- **可计数代价**：少 1 个插件、少 1 份契约（如果并入）；但派发器契约的起草要**挂起**，等一份还不存在的 agent loop 契约；
  登记目标从一个只 inject 会话日志的插件，变成一个 inject 运行时、注册表、模型请求运行时、会话日志的插件（至少 4 个必需依赖），任何一个换代，全部贡献者都要重跑登记。
- **何时它更好**：agent loop 契约起草之后，调查证明拓展点协议与 agent loop 总是一起改，而且 agent loop 之外没有拓展件作者（例如决定不再支持 hooks 兼容）。

## 两个子选择

### 注册表落在哪个领域

| 选项 | 如何兑现 | 代价与反例 | 改票条件 |
|---|---|---|---|
| **R-t `tools`（推荐）** | 主体语义在 PF-006（可用性、替换件、常驻、槽位、依赖解析）；主要消费者是 agent loop、`Tools()`/`Skills()`、放行取定义；它可选取用的执行者表和 MCP 桥都在同一领域 | 会话斜杠命令集与 reload 是 PF-002 的语义，却放在 `tools`；inject 资产求值是一条跨领域边 | 块 A 的拆分提案把「会话级快照」放在求值那一侧；或者 PF-002 的命令集语义（例如热更新对进行中运行的呈现时机）成为注册表改动的主要来源 |
| R-a 块 A 的领域（独立插件） | 与填表的来源（资产求值）同领域；命令集与 reload 的 PF-002 语义归位 | 可用性、替换件、常驻、槽位这些 PF-006 语义进了资产领域；它要可选取用 `tools` 的执行者表和 MCP 桥，两条跨领域边；资产治理可能在治理中心一侧，而注册表一定在据点侧（**未核**） | 同上 |
| R-β 并进资产求值的提供者（机制读数的自证分解 β） | 少一个服务 | 会话级的失效事件（reload、③ 型失败）混进求值的责任；求值提供者每换代一次，就牵连所有会话的快照 | 块 A 的求值本来就按会话持有快照 |

**本包没有读块 A 的拆分提案**，这个子选择必须和那份提案对齐成一个答案（[交接缺口](design.md#交接缺口)）。

### 放行判断将来的提供者落在哪

本批没有提供者，**不建节点**；契约住在 `spec/capabilities/`，与领域无关，这个子选择不影响本批的任何产物。
候选有三处：`tools`（放行判的是工具动作——主线已裁定放行四步只判工具，含 MCP 动作和 meta）；PF-008 那一侧（出卡与决策池）；PF-007 权限那一侧。
**建议到它的提供者设计时再定**；到那时要回答的是，它的主要变化来源是授权表达（PF-007），还是卡片与作答（PF-008）。

## 推荐与改票条件

**推荐 C**，注册表取 R-t，放行判断的提供者本批不建节点。理由按排除顺序：

1. **先排除不能兑现必要性质的**：A 失去 K-3、K-6、K-8，而且装不下「只有接口」的放行；E 让拓展点协议依附于一份尚未起草的契约，并把登记面放到依赖最多的插件上，还与「独立维度独立插件」的判据相左。
2. **D 与 C 相比**，只多保住一种情形——存储、时钟在进程内换代；代价是多一个进程内接口、一个停放队列，以及一种新的丢失方式。
   本版的存储、时钟换代是启动期事件，所以 D **不作默认**，而是作为运行时提供者设计的选择点，触发条件写在下面。
3. **B 与 C 的性质承载完全相同**。B 留下一条跨领域的同步修改信号，外加一次可以预见的搬迁；C 多拍一个领域名。
   照 [D-024](../../decisions/tenancy-domain-name/README.md) 的理由——名字在第一次建包之前定，代价是零——选 C。

**改票条件**（什么证据会让落选方重新上桌）：
