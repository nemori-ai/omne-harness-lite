## 注册表领域三票

| 票 | 选择 | 决定性理由 | 最强反证（自判未压过） |
|---|---|---|---|
| architecture-reviewer | Y（`tools`） | **可计数代价**：每次执行尝试都跑的 `refreshAvailability`（asset-registry S-24）依赖 `tools` 里活着的服务（MCP 桥 S-12/S-24 ④/S-32；执行者表 C-mechanism-b §4.2 O-18）；对块 A 没有任何运行时服务边（求值是纯函数，asset-evaluation S-11；据点侧不 inject 块 A 的任何东西，C-mechanism-a N-2；`fill` 收值，S-22 ①）。跨领域运行时边：R-t 0 条，R-a 2 条，均带失败模式。块 A 自己的产物也已把注册表放在块外（asset-evaluation S-2「注册表 → 块 B」） | reload 一族、命令集门控、markFailed/onAssetChange 是 PF-002 语义（B-domain-b INV-30/SAF-28/LIV-15），落 `tools` 后 PF-002 每次修订都改 tools 节点——「反复同步修改」信号。未压过：语义住在契约里，两种落点契约相同，绑定只是值传入与副本读；信号对称（R-a 下 PF-006 语义同样跨界驱动改动） |
| Opus 5.5 | Y（`tools`） | **可计数代价**：热路径每次要调 `tools` 至少 3 项服务（MCP 桥三面、放行的 SessionRunMode、执行者表），反向另有放行取定义、执行运行时读注册表两条边；R-t 下块 A 一侧只剩对纯计算的 import 与只作提示的治理通知（S-41 通知关掉收回照样生效）。B-domain-b 的 INV-02/03/04、SAF-01、LIV-01 只落〔工具〕一个 owner | 契约 S-1 五项里三项是 PF-002 语义，按「契约拥有的事实归领域」数语义 R-a 占多数。未压过：三项都是派生视图上的时序规则，快照不持久、装配清单才是权威（S-18），在资产领域不产生状态 |
| Codex gpt-6 | Y（`tools`） | 跨领域接缝可计数更少：R-t 只需跨域取 `asset-evaluation`；R-a 还需跨域取执行者表与 MCP 桥，共两条 | PF-002 §4 完整定义了命令集与 reload，似乎应归资产域。未压过：它只覆盖 `slash_command` 一张表；可用性、依赖解析与替换件由 PF-006 负责 |

**计票**：三票全选 `tools`。决定性理由同一根（跨领域运行时服务边 R-t 少于 R-a），计法各异（热路径服务数；活边 0 对 2；接缝 1 对 2）。反证：Opus 与 Codex 同源（PF-002 语义归属），architecture-reviewer 是不同信号（反复同步修改）——**反证不完全重复**，三票有效。两票各给第三种切法（归装配清单 owner／loop 侧领域），均自判不比 `tools` 便宜（PF-004 契约尚无，tools 活边照付）。

**结论**：采纳 R-t，注册表落 `tools`；asset-evaluation 落 `core`（纯），两份提案由此对齐成一个答案。改票条件保留（块 A 求值改为按会话持有快照；或 PF-002 命令集语义成为注册表改动的主要来源）。
