# 起草笔记：`data.identity-values` v1（候选 C）

本文件记**我做的每一个非显然选择及理由**、**我认为简报里站不住的地方**、**我标为 gap 的东西**。
它不是契约的一部分，不随契约一起落盘。

---

## 一、非显然选择

### 1. TenantId 的规范序列化形式选了「两字段结构」，不是拼接串

**简报只说「规范序列化形式一种」，没说是哪一种。**两个候选：

| 候选 | 代价 |
|---|---|
| 拼接串 `<OrganizationId>:<AccountId>` | 要保证可逆，就必须**现在**给不透明标识加字符集约束（至少排除分隔符）。而标识的具体形式明确归 realization（G-04）——为了让拼接可逆而在这里钉一个字符集，就是**填一个看起来合理的默认值**，正是简报禁止的那件事 |
| **两字段结构（选中）** | 需要单一标量键的实现要自己造一个，多一步 |

还有第二个理由，我认为比第一个更重：**拼接串是「缓存键前缀冒充隔离」这条错误最顺手的入口**。
一旦契约发布了一个官方的标量形式，实现自然会拿它当 key 前缀，然后「分了前缀」就会被当成「隔离了」。
契约里同时有 S-22（禁止以缓存键前缀冒充隔离）和一个官方标量形式，是在**自己挖自己的墙脚**。

所以 S-7 明确写了**本版没有标量形式**，并给需要它的实现两条硬约束：不得对外发布为身份、不得把解析结果当授权依据。

### 2. `ScopeLayerIdentity` 只留两个变体，并把排除的四个逐条写明理由

简报说「组织级 → OrganizationId；租户级 → TenantId；会话级 gap」。
我把它做成**封闭的两变体 tagged union**，并在 Schema 与正文里**逐条写明为什么排除** `account`、`factory_default`、`workspace`、`session`。

- 只写「有两个变体」，下一个人会以为剩下的是没想到；写明四条排除理由，他就知道**每一个都是被裁掉的**。
- `factory_default` 是我自己加的排除项（简报没提）。理由：UL-scope-layer 有四层，出厂默认是其中之一，
  不写排除理由，实现会顺手给它铸一个 `"system"` 身份值——**那就凭空造了一个叫「系统」的主体**，
  而它一旦存在，就会有人问「系统这个租户的资产归谁」。
- `workspace` 也是我加的。PF-002 §5.8 明说工作区不是一重身份，但它在两条层序上都占格，
  **最容易被误加进这个类型**。

**`session` 不在枚举里，是一个设计动作，不是遗漏。**枚举里没有它，需要会话级层身份的消费者
会在构造那一刻失败并去找 G-01，而不是照一个猜测（比如拿 SessionId 塞进去）继续走。

### 3. `LoginIdentifier` 单独立了一个定义项，虽然简报的元素表里没有它

简报把「登录标识是账号的一项属性」写在 AccountId 的约束栏里。我把它**提成一个独立的定义项**，
因为 S-2 要说的不是「AccountId 有个兄弟」，而是一条**禁止**：
**登录标识不得出现在 TenantId 中，不得作为任何归属记录的键。**
这条禁止要成立，两者必须都有名字——只有一个有名字的时候，禁止句写不出来。

代价是多一个定义项，而它的具体形式同样是 G-04。我认为值得：
把一个人自选的对外名字复制进每一条资产、每一笔账单，是那种一旦发生就很难回收的错误。

### 4. 三值的名字用了 `effective` / `ineffective` / `unavailable`，并让形状本身区分它们

简报说「三值：有效(角色) / 无效 / 不可用」。我做了两个补充：

- **`effective` 必带角色、另两值必不带**（Schema 的 `oneOf` 强制）。
  这样**没有「有效但角色未知」这一态**——那一态是「先判有没有效、再另查角色」的实现顺手造出来的，
  它一旦存在，就会有代码在角色还没查到时按最宽处理。
- **`unavailable` 与 `ineffective` 在形状上就是两个不同的实例**，不是同一个枚举里的两个字符串值加一个标志位。
  折叠这两者是整份契约里代价最大的一个错误（见 D 表 A 的 SAF-16），形状上分开能让它在类型层面就折不掉。

### 5. 隔离义务写成「谁在何处保护 / 违反时可观察到什么」两栏，而不是一句禁令

简报给的是七条禁令。禁令的问题是**另一个 owner 照着它没法自检**——「显式携带」要检查什么？
所以每条都补了第二栏：**违反时能观察到什么**。例如 S-18 的观察是「不带身份的请求得到了 200 和一个空列表」；
S-20 的观察是「把进程换个工作目录启动，同一个请求的放行结果变了」。
这一栏是给 V-2/V-3/V-4 写检查器用的，也是给评审用的：**说不出观察，那条义务就是空的。**

### 6. S-19 的六条路径配了一张「容易漏在哪」的表

读和写没人漏。真正漏的是**覆盖**（按键 upsert 只校验「有没有这条」不校验「这条是不是你的」）、
**删除**（批量按前缀走）、**订阅**（主题里没有身份分量，或有但只用于过滤）、
**清理**（后台任务不经准入判定）。把四个具体的漏法写出来，比重复六个词有用。

### 7. 不建任何形式模型，并写明理由

本契约没有状态转移，结构约束（至多一个上级、无环、个人组织不在链上、共同上级）
由治理契约的 `Affiliation.als` 检查，**那份模型消费本契约的值定义**。
在这里再造一份平行的 Alloy 模型，就会有两份结构约束各自演化。
这一条按 [design/AGENTS.md 的 spec 门槛](../../../../../AGENTS.md#状态和交接红线)——工件按性质选用，不为填满目录制造平行模型。

### 8. V-1 的状态写成「未登记」而不是「未开始」

简报的通用约定说 `verification.md` 写「未开始」。但我在起草期间**确实跑了一次**
本地形状自检（Schema 过 Draft 2020-12 元模式；本页正反实例全部按预期通过/拒绝）。
写「未开始」是不准确的，写「已通过」是把一次没有输入快照、没进 `record/evidence/` 的本地运行
冒充成证据。所以写成**「未登记」+ 明确说明它不作为证据**。

### 9. 交付了三个文件，没有 `README.md` 与 `verification.md`

任务的「写什么」只列了三个文件，我照办。但**真要落盘到 `spec/data/identity-values/`，
这个包是不完整的**：按[规格模板包](../../../../../spec/.templates/data/README.md)，
还需要可变的包入口 `README.md`（导航 + 采用状态）与版本外的 `verification.md`（覆盖与实际证据）。
本稿把验证义务暂放在 contract.md 的「验证义务」一节——**那是权宜，不是正确位置**：
验证结果会变，而契约版本目录发布后不可原地覆盖，两者的失效事件不同。
落盘时必须把那一节整体搬进 `verification.md`。

### 10. 文中链接用的是投标目录的相对路径

本稿在 `tmp/.../bids/identity-values-C/`，所有指向 `.meta_harness/` 的链接按这个位置写成 `../../../../.meta_harness/design/…`，
**现在是能点开的**。落盘到 `spec/data/identity-values/v1/` 之后这些路径全部要重写为 `../../../../<区>/…`（层数相同、前缀不同）。
我没有写成落盘后的路径，因为那样本稿现在一个链接都点不开，评审无法核对依据。

## 二、我认为简报里站不住或需要修正的地方

### A. 「新概念不得自造」与简报的元素表直接冲突：`MembershipStanding`、`ScopeLayerIdentity` 都不在词表里

**这是我最想报上去的一条。**

任务的硬要求是「用统一语言的词与正式英文名，新概念不得自造，需要时标为 gap」。
但简报「契约一」的元素表里有两个名字**不在 [index.md](../../../../../ubiquitous_language/index.md) 里**：

- **`MembershipStanding`**——它指的是一个**已有**的产品事实：
  [objects.md 把「成员关系」并入 UL-tenant](../../../../../domain_objects/objects.md#ul-tenant--租户)，
  并明确分界「**身份是值，有效性是记录**」。所以「有效性」这一面是有依据的，**但它没有词条，也就没有正式英文名**。
- **`ScopeLayerIdentity`**——[UL-scope-layer](../../../../../ubiquitous_language/terms/scope-and-resolution.md#ul-scope-layer--作用域层--scope-layer)
  的正式英文名是 `Scope Layer`，词条正文有「归属」一栏，**但「层 + 它的身份值」这个组合没有名字**。

按[统一语言区的红线](../../../../../ubiquitous_language/AGENTS.md)——「**先词条，后正文**，顺序是硬的」——
**这两个名字现在不能在规格正文里用**。

**我的处理**：照简报的元素表定义了这两项（否则契约缺两块必需的形状），
但在 Schema 的 `$comment` 与契约的 **G-07** 里**双重标注**它们不是从词表取的，
并写明「本契约接受前须补词条或换用已有词」。

**我建议主线：先补两条词条再接受这份契约。**理由不是形式主义——
`MembershipStanding` 的三值是整份隔离义务的支点（S-25 是 17 条「有前提地能」共用的前提），
一个支点级别的概念没有词条，将来每个 owner 都会按自己的理解译一遍，
而[译法分叉会直接传导到契约](../../../../../AGENTS.md#全局只有一套说法)。

### B. AccountId 与 `objects.md`「账号的身份是登录标识」对不上

简报裁定 AccountId **不透明**、登录标识是**一项属性**。
但 [objects.md 的 UL-account 条目](../../../../../domain_objects/objects.md#ul-account--账号)写的是：

> **身份**：登录标识，整个部署内唯一，注册时确定

**这两处说法对不上。**我按简报的裁定写（S-1/S-2 把两者分开），理由在上面第 3 条：
登录标识进 TenantId 会把一个人的对外名字复制到全系统的归属记录里。
PF-001 §4 也确实把登录标识列在账号的**属性表**里，所以简报的读法有正文依据。

**但对不上这件事不能静默统一掉**——按 [design/AGENTS.md](../../../../../AGENTS.md#全局只有一套说法)，
它该进 [conflicts.md](../../../../../ubiquitous_language/conflicts.md)。
我在投标目录里写不了那个文件，所以**登记为 G-08 并在这里点名**：
**请主线把它记进 conflicts.md，并由 PF-001 的 owner 裁一次。**
若裁定为「账号的身份就是登录标识」，S-1/S-2 要重写，**TenantId 的 account 分量随之改变**——
这不是措辞问题，是会传导到每一条归属记录的问题。

### C. 简报把「ScopeLayerIdentity = 身份带来的两层」说窄了

简报写「组织级 → OrganizationId；租户级 → TenantId；会话级 gap」，只提三格。
但 UL-scope-layer 是**四层**，出厂默认也是其中一格。
只提三格的写法留下一个没人回答的问题：**出厂默认那一格用什么身份值？**
我把它写成**显式排除 + 理由**（没有身份值，不得铸一个「系统」主体）。
建议其余候选也统一这么处理——**留白的那一格是会被填的**。

### D. 「判定依据只由身份 + 持有记录 + 成员资格构成」需要说清是**封闭**列表

简报这句话读起来像在描述，不像在禁止。我把它写成 **S-20：构成是封闭的**，
并列出五类明确不得进入的东西（物理路径类、OS/进程类、存储位置类、网络位置类、运行实例身份类）。
**开放列表挡不住任何东西**——检查器没法检查「大概就这些」。
其中「运行实例身份（`Fiber.uid` 一类）」是我加的：简报在「身份形式」一栏说过
标识不来自运行时，但没把它也写进判定依据的禁止项，而**这是本项目内核就在手边的那个诱惑**。

### E. 「计量按 TenantId（口径 gap）」这个组合需要写得更克制

简报把它列进消费者核对场景。我写了场景 8，但把承诺压到最小：
**本契约只承诺 TenantId 可被每次调用携带且不漂移**，口径本身完全不碰。
理由：D 表 A 把 SAF-19/LIV-10 判成**阻断**，那意味着这条场景**现在走不通**。
写成一个看起来完整的场景，会让读者以为计量已经有依据了。

### F. 简报说「数据契约 + 静态检查义务列表」，但没说静态检查由谁提供

S-17/S-20/S-23/S-27/S-28 全靠静态检查兑现，而**静态检查器的形式归 realization，realization 还没开始**。
我在 V-2 里写明了这件事，但要提醒主线：**这五条现在是「写下来了，没人检查」的状态**。
它们不是缺口（语义是定的），是**证据义务未闭合**——两者不同，别在 registry 里混登。

## 四、我**没有**做的事（供主线核对范围）

- 没有写 `registry` 的任何条目（catalog / covers / formal-tasks）——那是契约成稿后主线登记的事。
- 没有碰 `.meta_harness/` 下的任何文件，包括 conflicts.md 与词表——G-07/G-08 只在这里点名。
- 没有读其他候选者的目录。
- 没有定义邀约过期（契约二）、任何操作、任何状态转移——那些归契约三/四/五。
- 没有为「个人组织 ⇒ 不可邀请/上级恒空/不可作上级」写判定逻辑——本契约只给取值域与蕴含关系的**表述**，
  判定的操作、前置与提交点归 `capability.organization-governance` v1。
