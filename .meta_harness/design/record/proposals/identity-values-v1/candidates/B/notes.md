# 起草笔记 · `data.identity-values` v1（候选 B）

本文件记录**每一个非显然选择及其理由**、**我认为简报里站不住的地方**、**我标为 gap 的东西**。
它不是契约的一部分：契约正文只写最终承诺，推导与异议留在这里。

---

## 一、非显然选择

### 1. TenantId 的规范序列化形式选了两字段对象，标量编码推给 realization

**选择**：`{"organization": ..., "account": ...}` 是**唯一**的规范序列化形式（S-6）；相等与唯一性判定**只在这个结构形式上定义**；实现若需要标量键，必须单射、一个部署一条规则、且**不得解析回分量来作判定**。

**为什么不选拼接字符串**：拼接要成立必须先钉死分隔符与标识的字符集——而简报明写"不透明标识的具体形式留 realization"。在词法形式未定的前提下定义拼接，等于**偷偷把 realization 的自由度锁死**，而且锁得不显眼：只要某天某个标识里出现了分隔符，注入就成立，且注入的是**归属键**。

**为什么不两种都给**：简报要求"规范序列化形式一种"。两种形式并存必然分叉——一处比结构、一处比字符串，而两者在标识含空白或大小写差异时会给出不同答案。

**代价（诚实记下）**：存储索引、日志字段、度量标签都要一个标量。我把这件事**显式交给 realization 并加了三条约束**，而不是假装它不存在。缺点是这三条约束目前没有自动检查兜着，只能靠 SC-8。

### 2. 引用键用不透明的 AccountId，不用登录标识——这与 `objects.md` 现有条目不一致

**选择**：S-1 定 AccountId 为账号的规范标识；S-2 明确**登录标识是属性，不是引用键**。

**理由**：PF-001 §4 的属性表给了登录标识的唯一性与"注册时确定"，**没有给它的变更路径**。"没有变更路径"与"承诺永不改变"是两回事——前者是正文当下的形状，后者是一条本契约没有依据去承诺的性质。把一个不承诺恒定的值当引用键，引用会在它变的那一刻**集体失效**，而失效的是作者记录、持有键这类不可再生的东西。

**不一致点**：[`domain_objects/objects.md` 的 UL-account 条目写「身份：登录标识，整个部署内唯一，注册时确定」](../../../../../domain_objects/objects.md)。本契约与它**不一致**。我没有静默统一，而是：契约里按 AccountId 写，并登记 G-06，指名由 PF-001 owner 裁"登录标识可不可改"。**若裁定为不可改，objects.md 那条仍然成立，本契约的 S-1 也仍然成立**——身份依据与引用键可以是两件事，但那需要一次明确的裁决，不是起草者可以替谁定的。

### 3. `ScopeLayerIdentity` 只有两个变体，出厂默认层**不给**一个"空值变体"

**选择**：Schema 的 `oneOf` 恰有 `organization` 与 `tenant` 两支。出厂默认层**不在枚举里**（不是"在枚举里但不带值"），会话级**刻意缺席**。

**为什么不给出厂默认层一个变体**：给了它，那个变体就会出现在**归属字段**里；而一旦归属字段能取到"出厂默认"，就有人会写出一个 `platformTenant` 或 `systemOrganization` 去填它——一个没有任何自然人对应的身份值，会污染计量、署名与审计。PF-001 §6.7 明写 **official 没有租户**，PF-002 §5.2 明写**出厂默认层的设置与权限就是 official 资产自带的那一份、不需要另一套来源**。所以正确的形状是**那一格根本没有身份值**，而不是"有一个空的"。

**为什么会话级也刻意缺席而不是留 `null`**：留 `null` 会被下游当成"可以先传 null 跑起来"。缺席则任何试图表达会话级层身份的代码**当场编译不过或校验失败**——这正是手册说的"未决项以显式 gap 出现，不填一个看起来合理的默认值"。

### 4. `MembershipStanding.unavailable` **不带**原因字段

**选择**：三支都只有判别式，`unavailable` 不携带 `reason`、`retryAfter` 之类。

**理由**：带上原因，消费者就会**按原因分支**——"存储不可用可以重试所以先当无效跑着"。而唯一正确的消费方式只有一个：失败（S-10）。诊断信息属于可观测性，走 log 与 trace，不进这个判定值。

### 5. 不透明标识的表示定到"非空、禁首尾空白、逐码点相等"

**选择**：S-13 + Schema 的 `pattern`。

**理由**：相等性是本契约的**核心承诺**（TenantId 的结构相等由分量相等构成）。若不定相等语义，两个实现会一个做 Unicode NFC 规范化、一个不做，`"ｏｒｇ"` 与 `"org"` 在两处得到不同答案——而这个答案是**归属**。禁首尾空白是同一件事的最小版本：它是最常见的"看起来相等但不相等"来源。

**这是不是越界？**我判断不是：`表示与边界校验`正是数据契约拥有的那一节。词法形式（长度、字符集、是否 UUID）我没有碰，留给 realization（G-05）。

### 6. 隔离义务每条都写成「谁在何处保护 / 违反时可观察到什么」两行

**理由**：这份契约的读者不是"实现它的人"，而是**十几个各自实现别的东西、需要照着自检的 owner**。一条只写"必须隔离"的条款，自检时人人都会觉得自己做到了。写出**违反时的可观察现象**，自检才有落点——S-23 那条尤其典型：**把缓存前缀或事件过滤器去掉，同一次调用如果返回了跨租户数据，就说明判定本来就不在数据访问层**。这是一个可以真的去做的实验。

### 7. 明确写出"不建 TLA+、不建 Alloy"以及理由

**理由**：`spec/README.md` 说工件按性质选用、不预造空模型；但沉默地不建，和**写清楚为什么不需要**，对评审者是两回事。本契约的值**没有状态转移**（S-4、S-5 的"没有这条边"本身就是条款），结构关系里需要找反例的那部分（上级链无环、至多一个上级）归 `capability.organization-governance` 的 `Affiliation.als`。在这里建模只会产出一份与 Schema 同义的平行工件。

### 8. 用 SC-1～SC-8 承接 Schema 覆盖不到的条款

**理由**：S-20（判定依据的构成）、S-24（账号记录无跨账号字段）、S-4/S-5（不存在某条写路径）这类条款，**Schema 一个都管不了**——它们约束的是代码形状与依赖方向，不是交换数据的形状。D 对账已经把它们记为"静态检查"，我把它们落成八条**能被另一个 owner 照着跑**的检查，且每条在该语义消失时会失败（手册对证据的要求）。状态一律"未开始"，不以"已列出"充当"已通过"。

### 9. 「装配给 vs 协议给」写成契约条款，并明确区分两类

**理由**：手册第 F 步说这个结论要**写进契约**。我把它分成两类：**值的性质**（结构相等、枚举闭合、逐码点相等）与部署形态无关，**分布式不需要新兑现**；**判定**（唯一性、编码规则唯一、判定新鲜度、跨边界传递）单机由存储给，分布式必须由协议重新兑现。不分这两类的话，整张表会被读成"分布式之后一切都要重做"，而实际上真正需要协议的只有第二类。

## 二、我认为简报里站不住或需要回报的地方

### A. 简报引入了两个统一语言里没有的名字

`MembershipStanding` 与 `ScopeLayerIdentity` 在[词条索引](../../../../../ubiquitous_language/index.md)里**都查不到**。而硬要求写的是"用统一语言的词与正式英文名，**新概念不得自造**，需要时标为 gap"。

**这两条要求在简报内部是冲突的**：它既要求 Schema 定义这两项，又禁止自造概念。我的处理：**按简报定义它们，但只在契约内使用这两个名字，并登记 G-07 说明它们尚未立词条**，不把它们当作已定的正式英文名散播出去。

**语义来源是有的，不是凭空**：`MembershipStanding` 对应 [`objects.md` 对 UL-tenant 的「并入」](../../../../../domain_objects/objects.md)所说的"成员关系是租户**此刻有没有效**那一面"，再加上"判不出来"这第三种；`ScopeLayerIdentity` 对应 [UL-scope-layer](../../../../../ubiquitous_language/terms/scope-and-resolution.md#ul-scope-layer--作用域层--scope-layer) 的"**由身份带来的**归属层"那半句。**但"有语义来源"不等于"已立词条"**，顺序是硬的，所以我登记成 gap 而不是自己在词表外把名字定死。

**同一问题还有第三个**：**登录标识**在词表里也没有词条（G-08），因此它的正式英文名未定。契约里我只用中文称呼它，没有铸一个 `LoginIdentifier` 当正式名。

### B. 「资产持有的键 (归属层, 资产)」这个消费者场景，本契约只供得出三分之二

[UL-asset-holding](../../../../../ubiquitous_language/terms/circulation-and-entitlement.md#ul-asset-holding--资产持有--asset-holding) 写明持有关系的范围**有三种：组织、租户、工作区**。而简报给 `ScopeLayerIdentity` 定的是"身份带来的**两层**"。

**后果**：本契约供不出工作区那一级的持有键。我的处理：S-22 只承诺**工作区的宿主是租户**（这是 PF-002 §4 明写的），把"工作区靠什么标识那个目录"登记为 G-04 指回 PF-002（objects.md 本身也记着"靠什么标识那个目录，正文未述"）。

**建议主线知道这件事**：`data.identity-values` 不是"资产持有键的完整供给方"。要么资产领域的契约自己定义工作区身份（它本来就拥有工作区这个对象），要么将来本契约出 v2 扩这一格。**当前不填。**

### C. 「账号记录不含跨账号关联字段」是一条数据契约在约束**另一份契约**的记录形状

这是 D 的裁定（隔离义务全部进 `data.identity-values`），我照做了，但要指出它的形状：**S-24 的兑现方是 `capability.account-identity`，不是本契约的任何消费者**。

**这不是错误，是一个需要 registry 兜住的关系**：covers 必须把 S-24 与 `capability.account-identity` 的账号数据形状条款**双向连起来**，否则这条义务会变成一条谁都没认领的话。我在契约里把它的保护点写成"账号记录的**数据形状**"并配了 SC-2，就是为了让它有一个明确的落点。

### D. `unavailable` 进数据契约这件事，值得记一条不同意见

把"判定依据读不到"做成**值的一个取值**，而不是操作的一个**失败**，代价是：**每一个消费点都要处理三分支**，且"值"与"失败"的界线被抹了一道——一个纯粹的表示失败被编码成了领域值。

**我仍然保留三值**，理由是跨边界时"失败"没有统一表示：HTTP 状态码、异常、错误值、队列里的 nack，各家形状不同；而三值在**任何**传输形式下同形，所以它在数据契约里比在每个能力契约里各写一遍更省。

**但这个取舍应当被知道**：另一种同样自洽的做法是判定面返回二值 + 明确失败，把 `unavailable` 挪出数据契约。**若主线改判，S-9/S-10 与 Schema 的 `MembershipStanding` 一起动，其余条款不受影响。**

### E. 简报把 `TenantId` 的"无销毁路径"写成性质，但它实际上是**两个组织/账号无终结路径**的推论

PF-001 里账号[本版无注销](../../../../../product/PF-001-identity-scope-and-agent-constraints/flows.md#31-账号)、组织[本版不要求解散](../../../../../product/PF-001-identity-scope-and-agent-constraints/design.md#组织)。TenantId 的"永久可引用"**依赖这两条**。

**这在契约里写成了什么**：S-1 与 S-3 各自写明"不回收、不复用"，S-5 的"永久可引用"写成"只要它的两个分量存在"。**一旦将来任何一方引入了终结路径，S-5 的这半句会立刻失效**——这正是我把前提写在条款里、而不是写成无条件承诺的原因。这一条也应当在 covers 里挂回 PF-001 的那两节，好让 PF-001 改这两条时能点到本契约。

### F. 简报的隔离义务里没有单列「跨边界重验」，我加了 S-30

依据是 [SYS-TENANT](../../../../../foundation/cross-system-constraints/requirements.md#sys-tenant) 与手册的[身份与作用域](../../../../../../agents/skills/harness-design-handbook/canonical/references/architecture/modeling/identity-and-scope.md)："进程内归因信息不自动成为远程凭证；一个租户标识本身只说明声称的身份，不证明权限。"

简报的六路径条款管的是**同一进程内的判定**；跨进程传递是另一处会漏的地方，而 SYS-DEPLOY 要求现在就把边界画清。**这条不是我发明的需求，是把一条已有的系统约束落成可自检的条款。**
