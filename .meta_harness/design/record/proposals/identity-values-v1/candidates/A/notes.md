# 起草笔记：非显然的选择、对简报的异议、登记的缺口

本页**不是契约**，不被引用为依据。它记三样东西：我做的每一个非显然选择及理由、
我认为施工简报（任务区材料 `tmp/tenant-domain-design/E-brief.md`，**未随本包迁入**）哪些地方站不住、以及哪些我标成了 gap。

## 一、非显然的选择

### 1. TenantId 的规范形式选「记录」，并**拒绝**定义标量编码

简报要求「规范序列化形式一种」。最顺手的做法是定一个标量串
（例如 `"<OrganizationId>:<AccountId>"`），它能直接当索引键、缓存键与计量聚合键，
所有消费者都会喜欢。**我没有这么做。**

理由：**分隔符编码要成为双射，必须先固定标识的词法空间**——至少得保证分隔符
不出现在标识里。而简报自己把「不透明标识的具体形式」留给了 realization。
先定编码、再定词法，就是**用一个看起来合理的默认值把后面的裁决锁死**：
等到词法真的定下来允许 `:`，这个编码已经在索引与账单明细里到处都是了。

所以 S-9 只定记录形式，并把标量键登记成 **G-TENANT-KEY**，写明它的解锁顺序是
「先 G-ID-LEXICAL，再它」。**这条的代价是实打实的**：需要标量键的消费者现在拿不到，
必须等。我认为这个代价比一个会被推翻的编码便宜。

### 2. 不透明标识只约束到「非空字符串 + 按字节精确相等」

没有填 `pattern`、没有填 `maxLength`、没有说 UUID 或 ULID。
「不透明」不等于「无约束」，所以我给了**最小身份语义**：非空、类型是标量字符串、
相等按字节（不折大小写、不做 Unicode 归一化、不裁空白）、部署内唯一、不来自运行时。

**「按字节精确相等」这一句是我补的，简报没写。**不补的话，「不透明」会被实现者
读成「随便怎么比」——而大小写折叠是最常见的那种「随便」，它会让两个不同的账号
在某一条路径上被认成同一个。这是一条**隔离事故**，不是风格问题。

### 3. 把「AccountId ≠ 登录标识」单独立成 S-2

简报在元素表里用括号提了一句。我把它提成正式条款，因为**这是最容易被实现者省掉的一步**：
登录标识部署内唯一、用户可见、注册时定，看上去完全够格当主键。
一旦持久记录引用登录标识，「凭据可更换、标识不可改」这条约束就成了整个系统的隐性依赖，
将来任何改登录标识的需求都会变成数据迁移。S-2 明确写「不得互相替代，也不得互相推导」。

### 4. 「显式携带」扩成 ScopeLayerIdentity，而不是只有 TenantId

简报写「受租户所有权约束的对象与跨边界操作**显式携带 TenantId**」。
但 [PF-001 §6.7](../../../../../product/PF-001-identity-scope-and-agent-constraints/design.md#67-创作与归属)
明确有**所有者是组织**的对象（在组织范围创作的资产），
[§6.1](../../../../../product/PF-001-identity-scope-and-agent-constraints/design.md#61-层次) 也有组织级这一层。
照简报的字面写，组织级对象要么被迫塞一个 TenantId（那就把「归组织」讲成了「归某个人」），
要么不受这条约束（那就在组织级开了个口子）。

S-14 因此写成：**按对象的归属层携带对应的 ScopeLayerIdentity 值**——
租户级携带 TenantId，组织级携带 OrganizationId；**跨范围操作另外携带发起方的 TenantId**。
这是对 §6.4 的**表示层投影，不扩张它的范围**：§6.4 说的仍是同一件事，
只是把「租户身份」在组织级对象上的正确对应写了出来。

### 5. MembershipStanding 做成带标签的联合，而不是 `{standing, role?}`

一个可选的 `role` 字段允许出现 `{"standing":"valid"}`（有效但没角色）和
`{"standing":"invalid","role":"member"}`（无效却带角色）。
前者无法用于任何准入判定，后者会被下游读成有效。两个都是**无意义值**，
而无意义值一旦能被表达，迟早会被产生出来。

所以 `valid` **必须**带角色，另两个**必须不**带，Schema 逐个 `additionalProperties: false`。
同理：`null` 与布尔一律非法——**`unavailable` 不是「空」**，
空值会被下游按「没有」处理，而「没有」会走放行或静默回退那条路，正是 S-22 要挡的。

### 6. 会话级层身份：**Schema 拒绝它**，而不是留一个开放的 `layer` 枚举

`ScopeLayerIdentity` 的 `oneOf` 只有 organization 与 tenant 两支，
`{"layer":"session", ...}` 直接校验失败。

这是个有意的取舍。开放枚举更「面向未来」，但它意味着**今天就能写出一个会话级层身份**，
而它的含义[归 PF-015 且尚未定义](#三我登记的-gap)。写得出来的东西一定会被写，
然后每个消费者各自猜一套。**拒绝比占位安全**：加一支是 v2 的加法，不是改结构。

同理，`factoryDefault`、`workspace`、`account` 三种写法也各自被拒，理由分别是
「归系统、不是身份带来的」「不是一重身份」「求值恒等、不占一格」——
这三条都写进了 [examples.md](examples.md#6-scopelayeridentitys-13) 的非法表，
因为它们是**读者最可能自己补出来的三种**。

### 7. S-26（跨边界身份只声称、不证明）是我补的，简报的隔离清单里没有

依据是 `harness-design-handbook` 的
[身份与作用域](../../../../../../agents/skills/harness-design-handbook/canonical/references/architecture/modeling/identity-and-scope.md)
「进程内归因信息不自动成为远程凭证」，加上
[SYS-DEPLOY](../../../../../foundation/cross-system-constraints/requirements.md#sys-deploy)
要求领域语义在分布式后不变。

补它的理由：其余隔离条款在单机下由「同一个进程、同一个存储」顺手兑现，
唯独这一条在单机下**根本不会被触发**，因而最容易在分布式化时被漏掉——
而漏掉它的后果是「带个 TenantId 的消息即被当作该租户执行」，隔离一次性失效。
它同时出现在[第七节的装配给/协议给表](contract.md#七装配给-vs-协议给)里。

### 8. `personal` 的三条写成「值域上的结构谓词」，判定执行归治理契约

data 契约不能写状态转移，但 [S-5](contract.md#32-组织的种类) 那三条
（不可邀请、上级恒空、不可作上级）确实是**跟着 kind 走的**，
消费者需要知道「给定 kind 就能判」。所以我写「本契约只承诺这三条是可从 kind 判定的谓词，
**执行这些判定的写路径前置**归 `capability.organization-governance` v1」——
既不把规则藏起来，也不在数据契约里长出一个状态机。

### 9. 不建行为/结构模型，只出 Schema + 静态检查清单

本契约没有操作、没有状态转移、没有并发，TLA+ 与 Alloy 在这里会是**平行工件**
（`Membership.tla`、`Affiliation.als`、`Registration.tla` 的义务都在别的契约上）。
按[规格与证据](../../../../../../agents/skills/harness-design-handbook/canonical/references/architecture/assurance/specification.md)
「不为填满目录制造平行模型」，我只给 Schema，并把六条静态检查写成**具名义务且标「尚未执行」**。
Schema 已用 Draft 2020-12 校验通过，40 个正反实例的判定与 [examples.md](examples.md) 所述一致；
**这一条是工具结果，不是契约的接受依据**。

### 10. 「装配给 vs 协议给」里，TenantId 的结构相等标为「不变」

这不是填表凑数，它是**把 TenantId 做成值类型而不另铸标识的那笔收益**：
另铸标识的话，「两个 TenantId 是不是同一个」在分布式下会变成一次跨节点查询，
而值类型的结构相等在哪儿算都一样。同理 S-8「无销毁路径」在分布式下仍是
「没有这条路」，不是「有条路但加了锁」——**差别在于前者不需要协议**。

## 二、我认为简报站不住或需要商榷的地方

### A. 「TenantId 无销毁路径」是**有前提的**，简报把它写成了无条件

简报写「无销毁路径」。它在本版成立，**靠的是组织与账号都没有终结路径**
（[PF-001 §2 非目标](../../../../../product/PF-001-identity-scope-and-agent-constraints/design.md#二目标与非目标)：
「账号与组织的终止」整体延后）。一旦将来有了组织解散或账号注销，
S-8 的「历史引用永久可解析」就失去支撑，而依赖它的是
**作者署名**（C-2）与**会话归属**（C-7）这两处最不能出孤儿的地方。

我在 S-8 里写了「本版」，但**这个前提值得在主线单独记一笔**：
它不是本契约能自己保住的东西。同一个前提也解释了为什么
`data.offer-expiry` 的「指向的组织不存在」分支本版无触发源。

### B. 「新概念不得自造」与简报指定的两个名字**互相冲突**

硬要求写「新概念不得自造，需要时标为 gap」，而简报的元素表直接给了
`MembershipStanding` 与 `ScopeLayerIdentity` 两个名字，两者**都不在统一语言里**
（统一语言的[先词条、后正文](../../../../../AGENTS.md)是硬顺序）。

我的处理：**两个都用，两个都登记成 gap**（G-UL-STANDING、G-UL-LAYER-IDENTITY），
并写明「本契约接受之前须补词条」。理由是它们各自的性质不同——

- `ScopeLayerIdentity` 我判为**纯表示名**：它是 UL-scope-layer 在规格里的写法（层 + 该层的身份值），
  没有引入新的产品含义，补不补词条是统一语言区的判断；
- `MembershipStanding` **是一个新概念**。统一语言里最近的是
  [UL-tenant 的「并入」注](../../../../../ubiquitous_language/terms/subjects-and-ownership.md#ul-tenant--租户--tenant)
  （成员关系是租户「此刻有没有效」那一面），但那讲的是**对象的一面**，
  不是**判定结果的三值域**——尤其 `unavailable` 这一支在任何产品正文里都没有对应的词。
  它**该有一个词条**，而这件事不该由契约起草者顺手定掉。

### C. 「不可用 ≠ 无效」与「缺席即拒绝」并列，容易被读成同一件事

简报把两者放在同一串要点里。但对消费者来说它们是**两种不同的结果**：

| 情形 | 收场 | 消费者看到 |
|---|---|---|
| **没带身份**（S-15） | **拒绝** | 一个授权结论：不允许 |
| **带了但判不出来**（S-12 `unavailable` → S-22） | **失败** | 一个错误：这次没判成 |

把「失败」实现成「拒绝」，用户会看到「你没有权限」而实际上是数据库读不到；
把「拒绝」实现成「失败」，一次正常的越权尝试会被当成系统故障报警。
我把它们拆成 S-15 与 S-22 两条，各自给了不同的可观察反例。

### D. 「判定依据只由身份 + 持有记录 + 成员资格构成」需要与资产契约对齐一处

我把这条写成**封闭清单**（S-17），因为不封闭它就挡不住 S-18 的路径。
但按这个读法，[PF-002 的「禁用」](../../../../../product/PF-002-assets-settings-and-permissions/design.md#禁用是逐层配的布尔设置任一层为真即不可见)
必须算作**持有记录上的一项**，而不是第四样依据——
统一语言的 [UL-asset-holding](../../../../../ubiquitous_language/terms/circulation-and-entitlement.md#ul-asset-holding--资产持有--asset-holding)
（「带一个启用/禁用标记」）支持这个读法。

**若资产契约的 owner 另有读法**（例如把禁用做成独立于持有的一张表），
S-17 就会与它冲突。这是一处需要在资产契约成稿时对齐的点，我按现有词条读法写了，
**没有替资产 owner 裁**。

### E. 简报让 data 契约承担「静态检查义务列表」，边界要说清

静态检查是**验证设施**，它的执行结果归版本外的 `verification.md` 与 record 的 evidence。
契约里能有的只是**义务本身**。我照此写：六条清单进契约的「规范表达与验证义务」，
逐条标「**尚未执行**」，并明确「Schema 存在不表示形状已被校验过」。
简报的措辞（「静态检查义务列表」）没区分这两层，照字面容易写出一份带通过状态的清单。

### F. 「路径是地址，不是钥匙」在 data 契约里只能表达到一半

S-18 能写的是**资格的来源**（判定依据的构成不含物理位置）。
**真的拦住越权的文件读写**归
[PF-005 执行环境](../../../../../product/PF-005-execution-environments-and-sandboxes/README.md)，
这是 [PF-001 §2 非目标](../../../../../product/PF-001-identity-scope-and-agent-constraints/design.md#二目标与非目标)
明写的分界。简报未区分这两层；我在 S-18 与[第十一节明确不承诺](contract.md#十一明确不承诺)各写了一遍，
因为这一处**读错的方向是「以为契约管了拦截」**，那比漏掉更危险。

### G. 与 D 对账表 A（任务区材料 `tmp/tenant-domain-design/D-reconciliation.md`，**未随本包迁入**）的对应（过程引用，不进契约正文）

表 A 里 17 条「有前提地能」的前提高度重合，简报据此裁定把隔离义务做成一份共用数据契约。
本契约的 S-14～S-26 就是那些前提的正文化。逐条对应关系我**没有写进契约**——
按简报通用约定，D 的编号只作过程引用，正文引 PF 小节。这里留一笔供主线核对：
INV-11 → S-20/S-21；INV-12 → S-13；SAF-7 → S-14/S-17；SAF-8 → S-20；SAF-9 → S-17/S-18；
SAF-10 → S-8 + C-5；SAF-15 → S-7 + C-2；SAF-16 → S-12/S-22；SAF-17 → S-23；SAF-21 → S-24/S-25。

## 三、我登记的 gap

**一条都没有填默认值。**逐条见[契约第十节](contract.md#十已知缺口)，这里只说为什么它们是 gap 而不是待办：

| gap | 为什么不能现在定 |
|---|---|
| **G-SESSION-LAYER** 会话级层身份 | 它的含义归 [PF-015](../../../../../product/PF-015-session-lifecycle-and-ownership/README.md)，产品正文尚未给出。Schema 拒绝它而不是占位 |
| **G-METERING** 成本计量口径 | [PF-001 §6.4](../../../../../product/PF-001-identity-scope-and-agent-constraints/design.md#64-隔离) 只要求「成本能归属到租户、能出明细」，**怎么算怎么看没有 topic**。本契约只承诺 TenantId 可被每次调用携带且可精确聚合 |
| **G-PERSONAL-CONTEXT** 个人 context 内容 | 同样**无 topic**，PF-001 §8 明说不在那里定义。S-21 只定「它不进层」这一条否定式约束 |
| **G-ID-LEXICAL** 不透明标识的词法形式 | 简报自己划给 realization。不阻断本契约，但**阻断 G-TENANT-KEY** |
| **G-TENANT-KEY** TenantId 的标量键编码 | 见上文选择 1。解锁顺序：先 G-ID-LEXICAL，再它 |
| **G-UL-STANDING** / **G-UL-LAYER-IDENTITY** | 见上文异议 B。它们阻断的是**本契约的接受**，不是它的起草 |

**另外两件我判为「不是本契约的 gap」，登记在这里以免被当成漏项：**

- **隶属请求的宿主未裁**（发起方组织还是接收方组织）——
  [领域对象条目已登记为待裁](../../../../../domain_objects/objects.md)，
  它影响 `data.offer-expiry` 与治理契约，**不影响身份值的形状**；
- **采用的 Cordis 精确版本无决定记录**——影响 realization 的全部绑定，
  本契约不依赖任何 Cordis 语义（身份一律不来自运行时，这正是 S-1 的内容），**不受阻**。
