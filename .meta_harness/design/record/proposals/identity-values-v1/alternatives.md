# 候选与取舍

三份候选由三位起草者**各自独立**完成，输入相同（同一份施工简报、同一批产品正文），
交付形状相同（`contract.md` ＋ `identity-values.schema.json` ＋ 起草笔记，A 另附 `examples.md`）。
原件在 [`candidates/`](candidates/README.md)。

**本页正文的来源是主线的合并裁定**（原件 `tmp/tenant-domain-design/identity-values-merge.md`，
任务区材料，不随本包迁入）。**裁定本身是主线做的，不是本页推导出来的。**

## 选择对象与必要约束

见 [design.md 的「需要作出的选择」](design.md#需要作出的选择)。这里只重复两条不可调整的约束：
[跨租户访问默认拒绝](../../../foundation/cross-system-constraints/requirements.md#sys-tenant)，
以及同一个概念只有一份定义。

**三份候选都满足这两条。**因此择优不是「谁对谁错」，是**边界画在哪更便宜**。

## 三份候选

| 候选 | 骨架与取向 | 怎么兑现必要性质 | 差异、总负担与关键反例 | 证据与缺口 |
|---|---|---|---|---|
| **[A](candidates/A/contract.md)** | **可自检优先**。唯一附 `examples.md`（40 例正反实例），把「什么被拒」当规范工件；把「显式携带」从 `TenantId` 扩成按归属层的 `ScopeLayerIdentity` | 隔离义务两栏写法（谁在何处保护／违反时可观察到什么）；「缺席即拒绝」与「不可用即明确失败」**分成两条**（一条是授权结论，一条是错误） | **最大的实质贡献**：简报字面要求「对象显式携带 `TenantId`」，但 [PF-001 §6.7](../../../product/PF-001-identity-scope-and-agent-constraints/design.md#67-创作与归属) 有**所有者是组织**的资产。照字面写，组织级对象要么被迫塞一个 `TenantId`（把「归组织」讲成「归某个人」），要么不受这条约束（在组织级开口子）。**这是一条真反例，两份别的候选都没发现** | 附 40 例，是三份里唯一有可执行反例的 |
| **[B](candidates/B/contract.md)** | **表示层最严**。把不透明标识的相等语义写死（非空、禁首尾空白、逐码点相等）；把「表示层校验」与「判定」分成两条；列 SC-1～SC-8 八条可被别的 owner 照着跑的静态检查 | 枚举闭合、未知取值一律拒绝且禁降级；`MembershipStanding` 的 `unavailable` **不带原因字段**（带了消费者就会按原因分支，而唯一正确的消费方式是失败） | **诚实记下了与既有条目的不一致**：`domain_objects/objects.md` 的账号条目写「身份：登录标识」，而 B 用不透明 `AccountId` 作引用键。B **没有静默统一**，而是登记缺口并指名由产品负责人裁。**这一条后来成了主线裁定的第一项** | 静态检查义务写得最细，但**八条都没有自动检查兜着** |
| **[C](candidates/C/contract.md)** | **结构最完整**，篇幅也最大（730 行笔记＋正文）。骨架七段：值与身份 → 派生谓词 → 隔离义务 → 装配给／协议给 → 消费者场景 → 缺口 → 不承诺 | `ScopeLayerIdentity` 做成**封闭的两变体**，并**逐条写明为什么排除** `account`、`factory_default`、`workspace`、`session`；判定依据的构成写成封闭清单（含「运行实例身份如 `Fiber.uid`」这一禁止项） | **把「排除」写成正文**：只写「有两个变体」，下一个人会以为剩下的是没想到；写明四条排除理由，他才知道**每一个都是被裁掉的**。`factory_default` 与 `workspace` 两条排除是 C 自己加的，简报没提 | 10 行装配给／协议给对照表，是三份里最细的 |

**三份在这几件事上完全一致，因此它们不是本次的选择点**：`TenantId` 用两字段记录而不是拼接串
（三票一致，理由也一致：拼接要可逆就得先钉死标识的字符集，而字符集归 realization）；
本契约不建行为模型也不建结构模型；出厂默认层**没有**身份值。

## 四个真正分歧的点

| 分歧 | A | B | C | 合并取谁 |
|---|---|---|---|---|
| 「显式携带」携带什么 | **按归属层的 `ScopeLayerIdentity`**，跨范围操作另带发起方 `TenantId` | `TenantId` | `TenantId` | **取 A** |
| 不透明标识的相等语义写不写进契约 | 写（按字节精确相等） | **写得最细**（非空、禁首尾空白、逐码点相等，并与表示层校验分条） | 不细写 | **取 B** |
| `ScopeLayerIdentity` 的排除项写不写理由 | 不写 | 不写 | **逐条写明四个排除项的理由** | **取 C** |
| 正反实例算不算规范工件 | **算**（40 例） | 不附 | 不附 | **取 A 为底**，补 B/C 的反例 |

**这四条没有一条是「谁写得更好」**，每一条都对应一个会被实现者踩到的具体错误：
组织级对象被塞 `TenantId`、两个实现的大小写折叠不一致、
有人给出厂默认层铸一个 `"system"` 身份值、条款边界只有正例说不清。

## 择优规则：合并成一份的依据

**落盘的不是三份中的任何一份，是一份合并件。**主线定的规则：

- **骨架取 C**（值与身份 → 派生谓词 → 隔离义务 → 装配给／协议给 → 消费者场景 → 缺口 → 不承诺）；
  C 的层身份逐格排除理由、判定依据封闭清单、10 行装配／协议表**原样保留**。
- **并入 B**：表示与边界校验整块（不透明标识非空／禁首尾空白／禁解析、
  `TenantId` 缺席即非法且禁环境值补齐、枚举闭合未知拒绝且禁降级、
  表示层校验与判定分开、语义身份与实现地址分开）；
  「同一目录在两个 `TenantId` 下是两份工作区」；
  「成员无效 ⇒ 租户级持有不可达不销毁：不铸新身份、不删、不改键」；
  可测措辞「去掉前缀后同一调用若返回跨租户数据即已违反」；SC-1～SC-8 八条静态检查义务转入
  [验证入口](../../../spec/data/identity-values/verification.md)。
- **并入 A**：「按归属层携带对应的 `ScopeLayerIdentity` 值；跨范围操作另带发起方 `TenantId`」
  **替换**三份里「显式携带 `TenantId`」的写法；「缺席即拒绝」与「不可用即明确失败」**分为两条**；
  `examples.md` 以 A 的 40 例为底，补 B/C 的反例。
- **A S-26 / B S-30 的跨进程重验保留一条**：`TenantId` 只声称身份、不证明资格；
  跨进程或经队列须显式传递并在接收边界重验。**单机下不会触发，分布式最易漏。**
- 条款重编号为连续 `S-n`；每条隔离义务保留两栏写法；性质表来源一律引 PF 小节，
  **不引三份笔记里的 INV/SAF/LIV 编号**——[那些编号只在一次分析产物内有效](../../../registry/README.md#id-namespaces)。

## 主线裁定的争议点

**这些是三份候选各自登记为缺口、由主线拍下来的。**

| 争议 | 裁定 |
|---|---|
| `AccountId` 与 `objects.md`「账号的身份：登录标识」对不上（B G-06/G-08、C G-08） | **不是冲突，是两个问题。**产品层「靠什么指认这个人」＝ 登录标识（对象条目说的是这个）；规格层「跨对象引用用什么键」＝ 不透明 `AccountId`。契约写明这一区分，**不登 conflicts、不改 objects.md** |
| `TenantId` 的标量编码 | **不给**（三票一致）。登记缺口：标量键编码待不透明标识词法（realization）定下后，另立数据契约或 v2 |
| `MembershipStanding` / `ScopeLayerIdentity` 无词条 | **已立词条**，契约直接引用；另立「邀约」（总称）与「登录标识」两条 |
| 登录标识能否更改 | 产品负责人 2026-09-22 裁定**本版不提供修改**，列入 PF-001 非目标；契约写「本版无变更路径」，**不再是缺口** |
| 邀约过期时长的配置层次 | 产品负责人裁定：**每类各有默认值（部署配置），发出时发起者可指定这一份**；落进 PF-001 与 PF-003 |
| 出厂默认层的身份值 | **没有**；Schema 不含该变体；**禁止铸「平台租户」** |
| 工作区持有键 | 本契约**不供**，登记缺口指向资产领域契约 |
| 会话级层 | **缺席**而非 `null`；缺口指向 PF-015 |
| 静态检查义务 | 义务写进[验证入口](../../../spec/data/identity-values/verification.md)，状态「未开始」；本地形状自检**如实写「未登记」**（无输入快照、未进 `record/evidence/`），**不写「已通过」** |

## 推荐与仍待区分的事项

**推荐就是已落盘的那份合并件**——[`spec/data/identity-values` v1](../../../spec/data/identity-values/README.md)。
**推荐不是接受。**

仍待区分、且**不能靠再比一次候选解决**的两件事：

1. **标量键**。它的解锁顺序是硬的：先定不透明标识的词法（realization），再谈编码。
   在那之前，需要标量键的消费者**拿不到**，必须等。**这个代价是实打实的**，
   三份候选都选择付它，理由相同：一个会被推翻的编码一旦进了索引与账单明细就收不回来。
2. **会话级层身份**。它等的是 PF-015 的产品正文，而不是一次技术选择。

**三份候选没有一份被反例排除。**它们的差异是覆盖面的差异，不是正确性的差异——
这也是为什么结果是合并而不是三选一。
