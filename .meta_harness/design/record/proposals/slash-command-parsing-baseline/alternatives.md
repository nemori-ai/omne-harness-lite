## 逐条性质对照

「兑现」＝按原样满足；「需改」＝有对应机制但要改形状；「相抵」＝方向相反，照搬即违反。依据见上表各格。

| 性质 | A omne-next | B Codex | C Claude Code | D 自研 |
|---|---|---|---|---|
| N1 开头至多一条 | 相抵（递归多条） | 兑现 | 相抵（叠六个 skill） | 兑现（借 B） |
| N2 两种形式一样识别 | 需改（只对 chat 入站识别，与「不经交付面不识别」同向；两种形式未设计） | 未核对（只读了 TUI，exec / app-server 未读） | 相抵（按会话形态分叉） | 兑现（同一文法） |
| N3 未知名不发送 | 兑现（fail loud） | 兑现（单测） | 相抵（非交互送模型） | 兑现（借 A、B） |
| N4 字面发送 | 兑现（红线），记法未设计 | 需改（前导空格，不可见） | 需改（只对路径与标点首词） | 兑现（文法独立出路） |
| N5 参数按声明、否则一个自由参数 | 兑现（先查声明） | 相抵（命令自解析） | 需改（占位符成熟，声明与占位符关系要定） | 兑现（声明 + 占位符子集） |
| N6 一个名字一种解释、同名替换 | 相抵（限定名、无替换） | 需改（只有系统名，谈不上替换） | 需改（有洞：skill 对非 skill 内建） | 兑现（读面投影） |
| N7 三种绑定目标 | 需改（③ 走 `$`） | 相抵（无 ① ②） | 需改（① ② 合一于 skill） | 兑现 |
| N8 两路受理与留痕 | 需改（留痕未设计） | 相抵（不留原命令、③ 无记录） | 需改（形状对，③ 的记录可能对模型可见） | 兑现（借 C 的两份形状） |
| N9 落盘前看到展开 + 标注 | 未设计 | 相抵（内建不到内核） | 需改（钩子看到的是展开前的原文与命令信息） | 兑现 |
| N10 不替 skill 放权 | 需改（资格在执行端，未落到 ②） | 不涉及（无 ②） | 相抵（人敲绕过 `PreToolUse`） | 兑现（受理展开时判） |
| N11 独立资产、与 skill 多对多 | 需改（至多绑一个 skill） | 相抵（已删用户定义 `/`） | 相抵（并入 skill） | 兑现 |
| N12 语言无关 | 需改（参数文法交给库） | 相抵（文法在分派代码里） | 需改（文档即定义，且在变） | 兑现（文法契约 + 用例） |

**判读**：A、B、C 各自至少有两条「相抵」，且都落在当前产品正文已写定的性质上（其中 N7、N11 直接出自产品负责人原话），
这些性质本包不能调整；**把「相抵」逐条改掉之后，三者剩下的都是 D 要借的那几个部件**。
这是推荐 D 的主要理由，不是「自研更好」。

## D 的组成：借什么、从哪借、为什么只借这些

| 部件 | 来源 | 为什么借 | 不借的部分 |
|---|---|---|---|
| 只认整段第 0 字节；名字到第一个空白（含换行）为止；名字 token 含 `/` 即「不是命令」 | B（CX-2 单测） | 有单测、边界窄：`/usr/bin/python`（A1）、`/Users/x` 自然放行，其余任何形似命令的输入都走「未知名即拒」，一次拼错不会悄悄变成一句话 | 前导空格当字面：不可见、机读形式无对应 |
| 失败一律明说、不降级；字面发送是文法上的独立出路，**不靠先失败再回退** | A（ON-4） | 与 N3、N4 同向，且把 N4 从「有个出口」提升为可写进文法的规则 | 递归、限定名、`$` 语法类 |
| 先查声明再切参数；禁可变数量位置参数；没声明即整段一个自由参数 | A（ON-3）+ PF-002 | 声明是资产的设置，切法是文法，两者分开才能随同名替代换声明 | 「用现成库」——改为自己钉文法 |
| 有效命令集带版本；交付面预判、受理面以此刻为准再判 | A（E-S7 的 epoch） | 给 PF-014 §9.5 第二行留出可表达的位置，不替产品选答案 | 「落后即 fail-closed」这一具体答案——那是产品未决 |
| ① 正文的占位符（候选子集：`$ARGUMENTS`、具名 `$name`、`\$` 转义） | C（CC-6） | 最大的现成语料是 Claude Code 命令文件；Codex 迁移器因不认占位符整条跳过（CX-10），是不兼容的代价实例 | 无占位符时往正文末尾追加 `ARGUMENTS:`、按下标 `$N`——待区分，见下 |
| 留痕：原命令一份 + 展开全文一份；标注带命令名、绑定类别、所绑资产身份 | C（CC-7、CC-9） | 与 N8、N9 同形，且已有真实运行记录 | 本地命令「告诫 + 命令 + 输出」三条——③ 只留一条留痕条目，agent 看不到 |

## 推荐与仍待区分的事项

**推荐 D。**理由：N1–N11 都已写进当前产品正文（N7、N11 直接出自产品负责人原话），
A、B、C 各自与其中至少两条方向相反；逐条修正它们等于重写，修完剩下的部件 D 全部照借。
D 的代价是**没有先例**、要自己拥有文法、判定用例与导入器——这项代价 PF-002 §7 在立「单独一类资产」时已经标价并被接受，
本包没有新增它，只是把它落到了解析这一层。**推荐不是接受**；本包未经评审（见 [review.md](review.md)）。

**会让选择改变的证据**：
- 产品负责人放开 N1（允许一行多条），A 的递归与 C 的叠加重新可比——那时要回来比两者的切分律。
- 产品负责人把 ③ 改到另一个符号下，A 的三种语法类整体重新上桌。
- 判定用例集写出来后，发现 B 的「名字含 `/` 即不是命令」与某条产品规则冲突（例如要支持带命名空间的名字又选了 `/` 作分隔符）——改借别的边界规则，不影响 D 的结构。

**仍待区分的事项**（都是技术自由度，先由技术设计给候选；标「产品」的涉及人看到的长相，要交产品负责人）：

| # | 待区分 | 候选 | 最小区分调查 | 影响 |
|---|---|---|---|---|
| Q1 | **① 的参数语法要不要兼容 Claude Code 占位符**，兼容到哪一级 | 全兼容（含 `$N`、无占位符时追加）；子集（`$ARGUMENTS` + 具名 + 转义）；不兼容、另立语法并在导入器里翻译 | 统计本机与常用插件里 Claude Code 命令文件、skill 的占位符实际用法与频次；看子集覆盖多少、翻译会丢什么 | 导入器的丢失面；文法契约的复杂度 |
