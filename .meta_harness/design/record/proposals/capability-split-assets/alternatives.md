# 候选与取舍

编号（INV-／SAF-／LIV-／P-／O-／N-／H-／MR-）沿 [design.md](design.md#本选择要承载的性质)，只在本包内有效。
本页的「插件」一律指 Cordis 插件；「（无词条）」的用词见 design.md 抬头。

## 选择对象与必要约束

选择对象见 [design.md「需要作出的选择」](design.md#需要作出的选择)：**块 A 落在 #8 的两个对象（具体资产、资产持有）及挂在它们上面的复制与分享，切成几份能力契约、由几个插件兑现、各自落在哪一处进程与哪个包。**
必须保留：design.md 的[性质表](design.md#本选择要承载的性质)；已接受契约 v1 的公开面；Cordis 4.0.4 的内核语义；不提供 in-memory 实现。
可调整：契约数、插件数与切线、纯部分做模块还是服务、包布局与名字。

| 可识别候选及范围 | 如何兑现必要性质 | 差异、总负担及关键反例 | 当前证据与缺口 |
|---|---|---|---|
| **A** 一个插件提供四份契约：形状校验、求值（作为服务）、资产治理、资产流转都由中心一个插件兑现 | 中心内一切同一实例、一次提交；据点要么经入口层问中心求值（A-远程），要么也装同一个插件（A-双装） | 一个包。**关键反例**：据点没有求值提供者——离线时装配、reload、使用前的权限读无从求值；双装则缺依赖停在 `PENDING` | PF-016 §6.17、§5.6 是现成反证；无运行 |
| **B** 数据与求值做纯模块落 `core`、两侧 import；资产治理与资产流转由中心**一个插件**提供（主线裁定方向） | 五处同一提交落在一个 owner 的一次提交；两侧同一份纯代码 | 三个包、一个插件。**关键反例**：血缘对应的私有性从结构保护降为读面测试（A、D、E 同有，只有 C 没有） | 组织治理节点是同形先例；basis 七条 probe 通过；无运行 |
| **C** 治理与流转**各一个插件**，跨 owner 同一提交靠共同存储对象 | 流转插件的确认事务直接写、锁治理插件的表 | 四个包、两个插件。**关键反例**：插件边界隔离不了表——P-13 使同一提交只能由流转直接写治理的三张表，INV-2、SAF-2 降为自律 | core/storage P-13 是现成反证；无运行 |
| **D** 按中心／据点两侧拆：中心同 B，据点另立一个资产据点插件提供求值服务、持资产事实副本、收集输入 | 据点的装配、注册表、放行 inject 同一个求值服务 | 四个包、每处进程一个插件。**关键反例**：求值要组织治理的事实（角色、上级链），资产据点插件不是它们的 owner——要么第二份副本，要么只剩一层包装；推翻 MR-3 | 无运行 |
| **E** 沿两个 #8 对象拆：记录插件与持有插件 | 流转随记录插件；两边经共同存储对象同提交 | 四个包、两个插件。**关键反例**：提升跨两个 owner（INV-3）；记录与持有互读，inject 成环，一条边只能退成 `ctx.get` | 推导（H-6、INV-3）；无运行 |

另有一个**契约层变体**（B 的插件形状、两份契约并成一份），它不改变任何性质的保护点，只移动契约层的变化半径，单列在[后文](#候选-b-的契约层变体两份能力契约并成一份)，不算独立候选。

## 性质承载矩阵

P-1（同一存储、同一约束域）是五个候选共有的前提，格内不重复写。

|---|---|---|---|---|---|

## 候选 A

**形状**：资产领域一个插件（候选 `packages/assets/assets`），在中心装；它 provide 五个面——资产、持有、流转、快照，外加**求值**；形状校验也由这个包导出。
据点要求值有两种变体：**A-远程**，据点的装配、注册表、放行经入口层问中心；**A-双装**，据点也装同一个插件，只用它的求值面。

**最强论证**：一个包、一个版本号覆盖全部资产逻辑；中心里设置视图与求值是同一实例，不可能分叉；依赖图最简单，资产领域对外只有一个名字。

**失去保护点的性质**：

1. **LIV-1 失**（关键反例）。A-远程：治理中心问不到时，装配、reload 与每一次使用前的权限读都问不到——与 [PF-016 §6.17](../../../product/PF-016-cli-tui-delivery-surface/design.md#617-治理中心不可达已经开着的会话照常干活)「已经开着的会话照常干活」正面相反；
   工作区文件与会话值还得送进中心，而[治理中心](../../../ubiquitous_language/terms/grounding-and-isolation.md#ul-governance-center--治理中心--governance-center)「不知道任何会话」、工作区目录在据点（[PF-016 §5.6](../../../product/PF-016-cli-tui-delivery-surface/design.md#56-哪些东西在中心一侧哪些在据点一侧)）；
   权限按下一次使用时的值判，A-远程让每一次工具调用前多一次跨进程往返。
   A-双装：同一个插件在据点 inject 不到 `memberships`、`organizations`（据点没有组织治理的提供者），停在 `PENDING`（basis [`inject-has-no-optional-form`](../../../basis/cordis/inject-has-no-optional-form.md)）；
   要它在据点起来就得给它第二种装法（config 分支或另一个入口）——同一个插件名下两份实现，正是 [N-2](design.md#n-2-求值不做插件不进-ctx)、[N-5](design.md#n-5-不为租户组织工作区开-isolate) 说的「要并存两份才轮得到插件与 isolate」，实际退化成 D 或 B。
2. **INV-5 失**：同上。
3. **INV-4 弱**：与 B 同一处境（全部面在一个插件）。

另外与已写下的条款冲突：[AM](../../../spec/data/asset-model/v1/contract.md#这份契约拥有什么)写明它「没有操作……因此不需要插件」；realization 规则把 `data.*` 纯模块放 `core`——
正文契约、`data.call-accounts` 的规范串、注册表、装配这些 AM 的消费者，要为一组类型去依赖一个带 Cordis 插件与存储协议的包。

**反查信号**：

- **反复同步修改**：求值的任何修改都要重发中心那个插件；A-双装下据点消费者 inject 求值服务，插件每换代一次它们就跟着重跑。
- **重复拥有同一事实**：A-双装若在据点给那一份插件接本机存储，据点就成了持有与配值的第二个写入者。
- **跨 owner 同一提交**：无新增。

## 候选 B

**形状**：见 [design.md「装配草图」](design.md#装配草图可独立引用)。数据形状 `packages/core/asset-model`、求值 `packages/core/asset-evaluation` 两个纯模块，两侧 import；
资产治理与资产流转由中心一个插件提供（候选 `packages/assets/asset-governance`，四个服务面），由 `apps/tenancy-host` 装配。

**最强论证**：唯一一个同时做到两件事的候选——INV-1、INV-2、SAF-1～3 全落在**一个 owner 的一次提交**里；LIV-1、INV-5 由**同一份纯代码**在两侧给。
不推翻任何主线裁定；对已接受契约零改动（入口契约出 v2 是五个候选共有的）。形状与组织治理节点同构（一个插件、一条 fiber、几个服务面），已有实现与测试可照。

**失去保护点的性质**：

1. **INV-4 弱：从结构保护降为读面测试**（关键反例）：资产面、持有面与血缘对应同在一个插件。**只有 C 保得住这一条的结构**，A、D、E 与 B 同样没有。
   [X-3](#仍待区分的事项) 若能写成结构检查（读面模块不引用血缘对应表），这一格升为「能」。
2. 不失保护点、但要标价的：插件内**两条写路径碰同三张表**（落地与治理操作），INV-2 靠共用内部写函数守——这是同一 owner 之内的纪律，不是跨 owner 的自律。

**反查信号**：

- **跨 owner 同一提交**：1（团队 → 团队复制 vs 隶属解除，五个候选共有）。
- **重复拥有同一事实**：无。
- **反复同步修改**：PF-002 与 PF-003 的改动落在同一个包、同一个插件——一次流转的修改让资产治理的面一起换代，入口层随之重跑。
  **本版没有热替换，入口层反正 inject 全部面，这一条的可观察代价为零**；契约层两份各自出版本。

**可计数代价的补充**：新增结构检查一条——据点侧不 import 资产提供者的包（候选 `packages/assets/asset-governance`；据点只拿形状与求值两个纯模块，中心那个插件的包永远不进据点的依赖图）；每个资产面、持有面读面一条「推不出源」的反例测试。

## 候选 C

**形状**：治理与流转各一个插件、各一条 fiber：`packages/assets/asset-governance`（资产面、持有面、快照面）与 `packages/assets/asset-transfer`（流转面）；流转插件 inject 治理的资产面与持有面。
确认的同一提交靠共同存储对象：流转插件开事务、**直接写**治理插件的记录、版本与持有，锁治理插件的记录行与持有行；团队 → 团队复制取组织治理的隶属哨兵（同 B）。

**最强论证**：插件边界与契约边界一致——PF-002 与 PF-003 两个变化原因各有一个可单独装卸、单独换代的单元；
INV-4 有结构保护：血缘对应只在流转插件的表里，治理插件的代码里根本没有那张表；流转的一次缺陷不让治理的面一起消失。

**失去保护点的性质**：

1. **插件边界隔离不了表**（关键反例）：[core/storage P-13](../../../realization/packages/core/storage/design.md#协议) 不许在事务里调用别的插件的面，确认的同一提交只能由流转插件直接写治理插件的三张表。
   INV-2 由此有两个写入者：唯一约束（持有键、记录号）有存储兜底；「版本号接着自己的线往下数」「所有者至多变一次」「落地的记录所有者是目标组织、作者是 (目标组织, 发起者)」要两个包各守——**弱**。
   SAF-2「再复制不碰持有与配值」变成流转插件对别人表的自律——**弱**。
2. **两条退路都更差**：经治理的公开操作落地 ⇒ 多次提交，INV-1 **失**（「已落地仍待确认、还能被撤回」可见，[PF-003 flows §3.4](../../../product/PF-003-asset-transfer-and-sharing/flows.md#34-一份待确认的邀约复制通知与分享邀请同形)）；
   把事务句柄暴露给对方的面 ⇒ [组织治理节点已否的形状](../../../realization/packages/tenancy/organization-governance/design.md#跨-owner-的同一提交账号行上的过期事实加组织行对账号行的引用约束)：把存储抽象焊进两份契约的公开面，跨进程后整套作废。
   **只用存储哨兵把两次提交排成次序也不行**：哨兵只排次序、不给原子，两次提交之间崩溃照样留下半个。
3. **「失败隔离」没有可观察收益**：入口层 inject 两个插件的全部面，任一缺席中心整个不起来（[PF-017 §6.6](../../../product/PF-017-governance-center-as-deployable-application/design.md#66-要么整个起来要么不起来)、[gce S-34](../../../spec/compositions/governance-center-entry/v1/contract.md#s-34-起来即整体停机时在途请求归谁)）；本版装配不换代。
4. **事件归属别扭**：落地的发布与持有变化由治理那一侧的事件承载（[AT S-33](../../../spec/capabilities/asset-transfer/v1/contract.md#s-33-本版不发本契约自己的事件)）；流转插件写了治理的表，要么代发治理的事件，要么这批通知丢了（不影响正确性）。

**反查信号**：

- **跨 owner 同一提交**：5（复制确认、分享确认、资产没了 vs 确认、被分享方移除，外加 og 那一处）。
- **重复拥有同一事实**：流转插件写治理的三张表。
- **反复同步修改**：治理改表形状，流转的落地代码同一提交改；流转包要依赖治理包的表常量或内部写函数——包级耦合到对方的内部。

## 候选 D

**形状**：中心同 B；据点另立一个**资产据点插件**（候选名，例如 `packages/assets/asset-base`），provide 求值服务，自己持有资产那一片的中心事实副本、读承载清单、拼求值输入；
据点的装配、注册表、放行 inject 它。求值契约的提供者由纯模块变为这个插件（纯模块仍在，给中心的设置视图用）。

**最强论证**：给机制分解指出「无主」的两件事一个有契约的 owner——据点一侧的求值输入收集（O-17 据点半）与资产事实的副本（O-20 的资产那一片）；
装配、注册表、放行三处拿同一个服务面、同一份快照求值，不会各自拼输入。

**失去保护点的性质**：

1. **副本放错了 owner**（关键反例）：求值要的输入不只资产事实——「谁可以用」按租户角色判（成员资格与角色，[og S-26](../../../spec/capabilities/organization-governance/v1/contract.md#s-26-成员资格判定)）；
   分享来的持有此刻可不可用要读上级链（[og S-34](../../../spec/capabilities/organization-governance/v1/contract.md#s-34-上级链与有共同上级)、[AT S-9](../../../spec/capabilities/asset-transfer/v1/contract.md#s-9-分享此刻是否生效)）。
   资产据点插件要么持一份组织治理事实的副本（据点上于是有两份：它的，与据点装配为整个中心持的那份，MR-3），要么向另一个 owner 取——那它就只剩一层包装，而没有独立行为与边界价值的包装层是该删的。
2. **INV-5 有前提**：两条调用路径（中心的设置视图直接调纯模块、据点经插件）；包装层一长出自己的逻辑就分叉。
3. **求值变成服务**：装配、注册表、放行三处 inject 它，插件换代一次三处跟着重跑；注册表的快照不持久、重启时由装配清单与求值重填，这一重跑是正确的，代价是每次换代一次重填。

**反查信号**：

- **重复拥有同一事实**：据点上两份组织治理事实的副本。
- **反复同步修改**：资产治理、资产流转、组织治理任一读面改版，资产据点插件的副本形状同步改。
- 推翻主线裁定 MR-3（副本归据点装配、不另立契约）。

## 候选 E

**形状**：沿两个 #8 对象切：**记录插件**（候选 `asset-records`：创作、修订、发布、提升、删除；流转随它）与**持有插件**（候选 `asset-holdings`：加入、移除、禁用、锁、配值、视图、快照）。

**最强论证**：两个都满足 #8 判据的对象各一个插件，边界正好对着判据；创作与发布（记录）与设置与权限（持有）的读写频率、消费者都不同——设置页与装配频繁读持有，创作面很少被据点消费。

**失去保护点的性质**：

1. **提升跨两个 owner**（关键反例之一）：记录的所有者与原租户那一格持有的来路要在一次提交里一起变（INV-3，推导）；分开就要一方写另一方的持有行，
   或接受一个「以自己拥有持有、却已不是所有者」的可见窗口——那一格读出来是 [AM S-19](../../../spec/data/asset-model/v1/contract.md#s-19-使用权来路) 意义下的非法值。INV-3 **失**。
2. **互相依赖**（关键反例之二）：加入持有要看记录此刻未删、能力标识相符；删除记录前要列出持有它的引用方；「资产没了」同时看两边。
   两边互相 inject ⇒ 必需依赖缺席即 `PENDING`，双方都等对方先 provide（H-6，推导）；只能让一条边退成调用时 `ctx.get`——不登记依赖、可能取到 `undefined`，那一边的「要么整个起来」失去结构支撑。
3. INV-1、SAF-2 **弱**，SAF-1、SAF-3 **有前提**：复制与分享的落地同时写两边，流转放哪一侧都一样。

**反查信号**：

- **跨 owner 同一提交**：7（复制确认、分享确认、被分享方移除、资产没了 vs 确认、提升、加入持有 vs 删除记录，外加 og 那一处）。
- **重复拥有同一事实**：持有上「自己拥有」这一支的来路复述记录的所有者。
- **反复同步修改**：记录的形状（所有者、删除语义）一改，持有插件同步改。

## 候选 B 的契约层变体：两份能力契约并成一份

**形状**：插件同 B；契约层把资产治理与资产流转并成一份能力契约。

**最强论证**：一个插件兑现一份契约，没有「一个提供者两份契约」的解释成本；「落地写入由谁完成」这张交接表不必出现在任何契约里。

**代价**：PF-003 的每一次修改都让整份契约出一个新版本，只用治理面的消费者（入口层的治理路由、据点副本经快照面）看到与自己无关的版本号变化——契约层的**反复同步修改**；
资产流转已有一份独立成稿的候选契约（[`capability.asset-transfer` v1](../../../spec/capabilities/asset-transfer/README.md)，含 TLA+ 模型与七个配置），并成一份要重排它的条款号与 formal 映射。
**它不改变任何性质的保护点**，只移动契约层的变化半径，所以不列为独立候选；改票条件见下表末行。

## 反例是否互不重复

| 候选 | 关键反例 | 是否与别的候选共有 |
|---|---|---|
| A | 据点没有求值提供者：离线时装配、reload、使用前的权限读无从求值；双装则缺依赖停在 `PENDING` | 独有（D 在据点有提供者；B、C、E 在据点有纯模块） |
| B | 血缘对应的私有性从结构保护降为读面测试 | **不独有**：A、D、E 同有，只有 C 没有——它是 B 相对 C 的已标价代价，不是 B 被排除的理由 |
| C | 插件边界隔离不了表：同一提交只能由流转直接写治理的三张表 | 独有（E 有同类问题，但轴不同：记录 ↔ 持有，且另有提升与 inject 成环） |
| D | 求值要组织治理的事实，资产据点插件不是它们的 owner：第二份副本或一层包装 | 独有 |
| E | 提升跨两个 owner；记录与持有互读、inject 成环 | 独有 |

A、C、D、E 的关键反例互不重复。共有的弱点另列，不算任一候选的独有反例：团队 → 团队复制要在事务里取组织治理的隶属哨兵并直接读上级链列（五个候选同，X-1）；
入口层 inject 全部资产面、随领域契约同步改路由（五个候选同）。

## 推荐与改票条件

**推荐 B**——这是主线裁定的方向（MR-1），**不是接受**。

理由：

1. **先排除不能兑现必要性质的**：A 在 LIV-1、INV-5 上失去保护点（据点没有求值提供者），还与 AM「数据契约不需要插件」和 realization 的 `core` 规则相抵。
2. **C、E 能兑现，但付出真代价、换不到本版可观察的收益**：P-13 使「同一提交」只能靠一方直接写、锁另一方的表——插件边界没有隔开任何事实，
   只多出 5／7 处跨 owner 同一提交与一个写他人表的写入者（INV-2、SAF-2 降为自律）；它们买的「失败隔离」被入口层的「起来即整体」抵消。E 另有 inject 成环与 INV-3 的失守。
3. **D 能兑现，但与 MR-3 相抵**，且求值输入要组织治理的事实，资产据点插件不是它们的 owner。
4. **B 的代价是真实的**：INV-4 的保护从结构降为测试（只有 C 保得住结构）；PF-003 的修改让治理面一起换代（本版可观察代价为零）；插件内两条写路径碰同三张表。
   **接受 B 的人要明知：血缘对应不出流转一方这件事，在 B 下靠读面测试与评审守，不靠插件边界。**

这与项目的品味同向——先做最小的正确模型；复杂度要有收益证据；删掉没有独立行为或边界价值的包装层——但**选择的依据是上面的反例与计数**，不是品味本身。

**改票条件——什么证据会让落选方重新上桌：**

| 落选方 | 重新上桌的证据 |
|---|---|
| **A** | [PF-016 §6.17](../../../product/PF-016-cli-tui-delivery-surface/design.md#617-治理中心不可达已经开着的会话照常干活) 放宽为「治理中心不可达时会话停下」，**并且**工作区与会话层的值改为中心可见（[PF-002 非目标](../../../product/PF-002-assets-settings-and-permissions/design.md#非目标)「目录之外的承载形态」开题）——求值不再必须在据点跑 |
| **C** | ① 产品接受「确认之后异步落地」并给出一个可见的中间态；② 或复制改为「在目标侧产生一份草稿、由目标方另行发布」，落地不再写版本与持有；③ 或 PF-017 §6.6 放宽为按路由分组可用，使流转的失败隔离有可观察价值，**并且**变更历史显示两部分代码极少同一提交修改；④ 或评审确认 INV-4 在 B 下既写不成结构检查、读面测试也守不住（X-3 否定）。另：中心演化为多存储、流转与资产记录不在同一约束域时，要的是协议级的原子提交，**不自动偏向 C** |
| **D** | MR-3 被推翻：据点副本按领域分 owner、各出契约，**并且**组织治理在据点也有副本的 owner 给出读面（资产据点插件只持资产那一片）；或出现按部署、按组织替换求值策略的需求（求值要并存两份实现，才轮到插件与 isolate） |
| **E** | 「资产的开发与发布流程」开题成独立 PF（[PF-002 非目标](../../../product/PF-002-assets-settings-and-permissions/design.md#非目标)），记录一侧有了独立的变化原因与消费者；**并且**持有的使用权来路与记录的所有者解耦（提升不再要求改持有，X-2）；**并且**复制与分享的落地不再写持有 |
| **B 的契约层变体（并成一份）** | 两份契约的版本历史显示每次必同升（契约层的反复同步修改）；或资产流转在入口层之外没有独立消费者 |
