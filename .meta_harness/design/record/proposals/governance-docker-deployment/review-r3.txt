## 先答简报里的三个核心问题

**1. 官方事实独立核对（不沿袭 R1 推断）。**今日抓取 docs.docker.com「Start containers automatically」原文：`on-failure`——"It doesn't restart the container if the daemon restarts"；`unless-stopped`——"Similar to `always`, except that when the container is stopped (manually or otherwise), it isn't restarted even after Docker daemon restarts"；通则——"If you manually stop a container, the restart policy is ignored until the Docker daemon restarts or the container is manually restarted"；并警告不要与宿主进程管理器组合。**结论**：R1 B1 的触发场景（on-failure 在 daemon 重启后复活）与官方文字相反，R2 不采纳是对的；但 B1 的底层关切（停止意图必须跨 daemon 重启保留）成立，R3 选 `unless-stopped` 与官方措辞一致。官方"manually or otherwise"对「自行崩溃退出、未被手动停止」的容器在 daemon 重启后是否拉起**留有歧义**，这正是 R4 探针要答的格；docker.md 标「仍待隔离 daemon 矩阵」是恰当的。另：r2 探针看到的 `State.Running=true` + `Status=restarting` + `Pid=0` 依我对 moby `container/state.go#SetRestarting` 的记忆是 Engine 的**正常过渡态**（重启退避期把容器视为 running、进程视为 stopped），不是夹具异常；它对本设计的影响见 N2。

**2. 「先停 timer/中心再维护 daemon/OS，否则算故障」是否承接 EC3 S-59。**分两层答：
- **契约层：承接。**S-59「关闭」行的义务对象是*支持的正常关闭路径*上的提供者行为（等在途、真实结束才释放属主、无有限上界），并且 S-59 自己就把「强制终止」定名为「非正常故障」而不列举触发事件；S-34 同。docker.md 支持的路径（Compose `stop`/`down` + `stop_grace_period: -1s`，脚本不加 `--timeout`、无强杀兜底、超时不自报已停止）把这些义务原样落在应用上，没有降级。PF-017 §5.2 把「机器停了」列为停止原因、§6.8／§6.18 只要求已确认事实在「正常重启、进程崩溃、操作系统故障与断电」后保留、备份失败/未完成可区分——产品没有要求 OS 关机是优雅关闭。所以**接受 A 不需要新的产品硬要求**，也不应把无人值守优雅关机自动升格为硬要求。
- **装配层：相对已交付的原生绑定，是一次可见的收窄，但没有标价。**D055 采用的 maintenance-binding.md 第 25 行与 `deploy/omne-tenancy.service:18` 用 `TimeoutStopSec=infinity` 让 `systemctl stop`／OS 关机都落在正常关闭路径里（reboot 会等中心退出）；A 下这两类事件（还有 `systemctl restart docker`、Engine 升级）变成「外部故障」。docker.md 把它写在正文「生命周期与停止意图」段，**不是藏在手册**；但这项收窄是一个代价选择，设计既没有按对账表 D 自证（换一种机制重走：live-restore、docker.service 的单元顺序、候选 B 的 `BindsTo`），也没有以回询格式交给有权者，目前只以「正常操作一律使用上述入口」的口吻自定了答案。**该由 PF-017 owner／部署方认下这项代价并记进接受决定**（范围外 1），不能只留在节点笔记里。补一句反证：即便采用 live-restore，它也只救 daemon 重启/补丁升级，救不了 OS reboot——所以手动序列对 reboot 无论如何都需要，A 与替代机制的真实差距只在 Engine 维护那一格；这个差距应写出来再让人拍板。

**3. Compose/control-helper 会不会成为多余的第二生命周期系统。**判断：**不会成为第二个生命周期拥有者**——脚本无常驻、无循环、不自动重启、timer 永不 `up/start/run`，自动重启只有 Engine 一个主体；`start` 失败后的显式 `stop` 是一次性有界动作。但脚本**是第二个「停止意图」的决定点**（它发出的 `stop` 会置 Engine 的 manually-stopped 状态），其正确性完全依赖 Engine 状态字段语义（N2）。Compose 本身的增值是可审阅的固定拓扑声明；其代价是依赖未记入官方文档的负 duration 传递（N10）与 `up` 的隐式重建语义（脚本已用「运行/重启中拒绝 start」挡住，但重建会删旧容器及其日志，见 N4）。Docker healthcheck 在本设计里纯信息性（unhealthy 不触发任何动作，只被 `start` 等待和 `status` 读取），每 30 秒起一个 `ops full-health` 进程是它的常驻成本，不构成第二套生命周期。

## 非阻断

**N1 · 反向核对 —— 「非手动停止 × daemon 重启」这一格没有期望值，自动拉起是否算预期未写。**
位置：docker.md「生命周期与停止意图」第 32／34 行；R2 表第 4 行只写「可能强杀；重启后按 Engine 状态及应用 guard 恢复」。依据：官方 `unless-stopped` 措辞；PF-017 §5.2「停止（运维者动手，或机器停了）→ 再次启动成功」未指明由谁启动。触发：宿主未按序列直接 reboot（或 Engine 被 kill）；开机后 Engine 按 `unless-stopped` 自行拉起中心，走崩溃恢复启动（§6.10 小段等钟、guard、隔离残余照拒），`Persistent` timer 随即 exec 备份。后果：这是 A 下唯一一种「不是运维者启动的启动」，且**跳过宿主侧 validate**（N5 的宿主祖先检查不会重跑）；不写明期望，验收项 2 的「强杀/daemon 消失后」就没有判据，运维者也无法区分「它自己起来了」是预期还是故障。作者需明确：补一格「daemon 强杀（非手动停止）× daemon 重启 ⇒ 期望 Engine 拉起，视为崩溃恢复启动；容器内检查照跑、宿主侧 validate 不重跑」，并列为 R4 探针的一支。

**N2 · 投影对齐 —— 脚本判「已启动/已停止」的谓词未定，`State.Running`/`RestartCount` 不能用。**
位置：docker.md 动作表 `start`（「已有 running/restarting 中心则拒绝」）、`status`（「只读容器运行…不拿 running 当健康」）。依据：`tmp/next-iteration/preserved-docker-restart-probe-r2/report.md` R2 行——`RestartCount=1`、`State.Running=true` 与 `Status=restarting`、`Pid=0`、旧 `StartedAt` 同时出现。触发：中心处于重启退避（启动失败循环）时运维者跑 `status`/`start`。后果：若实现按 `State.Running` 判「运行中」，`status` 会把崩溃循环报成运行；若按 `RestartCount` 判「第二次启动完成」，`start` 的健康等待可能把过渡态当已起。作者需明确：写死谓词——「运行中」= `State.Status=="running" && Pid>0`；「重启循环中」= `Status=="restarting"`；「已停止」= `Status in {exited, created}`；启动完成须以 `StartedAt` 改变 + `Status==running` 交叉；`RestartCount` 只作诊断。一句可闭合。

**N3 · 反向核对／代价 —— `start` 的有界健康等待与升级迁移时长相互作用，慢迁移会被「成功后立即停掉并报失败」。**
位置：docker.md `start` 行（默认 120 秒，失败必须对确切容器正常 stop）；healthcheck `start_period 30s / interval 30s / retries 3`。依据：`src/main.ts:70-77`——SIGTERM 处理器在 `boot()` 之前登记，信号只是 resolve 一个 Promise，`boot()` 不被中断，撤除在 boot 完成后才开始（结构阅读，未执行）；tenancy-host README「升级整体性」快照/确认机制。触发：GiB 级库升级，迁移 > startupWaitSeconds；脚本判失败并 `stop`。后果：中心实际完成迁移并确认快照后立即撤除、退出 0，脚本却报「启动失败」，运维者需再 `start` 一次——数据无害，但「失败」语义失真；且 `die`（真正的启动失败）与「仍在启动」在脚本里没有区分，后者若走 `stop` 会把第二次快照恢复+迁移强加给下次启动。作者需明确：等待谓词区分「容器 die/进入 restarting ⇒ 立即失败并 stop」与「到期仍在 starting ⇒ 报 timeout、是否 stop 由作者定并写明后果」；说明 stop 落在迁移期间为何安全（快照/确认序列）；`startupWaitSeconds` 是部署输入而非产品参数。

**N4 · 内核负面清单（持久化）／反向核对 —— 工程记录随容器重建消失，升级序列本身会删掉升级前的记录。**
位置：docker.md「健康、调度、升级与日志」段（`local` 驱动、「控制脚本只写元信息」）与升级序列「固定新 image → start」。依据：Compose `up` 在镜像变化时删旧建新；Docker 日志随容器删除；EC3 S-30 工程记录、PF-017 §6.10「这段等待记在中心的工程记录里，运维者看得见」、foundation observability「保留策略有边界」；原生绑定下记录在 journald 跨升级保留（`deploy/README.md:20`）。触发：任一升级或 `down`；随后要追查升级前的 still-stopping 诊断、defect 明细或停止残余原因。后果：从原生路径迁到 A 后，可追溯性下降而设计未写明；「正常控制不以 down 删除诊断对象」这句与 `up` 重建实际相抵。作者需明确：写出记录保留边界——升级序列在 `up` 前导出旧容器日志（或日志落到持久挂载），或明确接受「重建即丢」并让有权者认下（范围外 4）。

**N5 · 承载复查 —— 隔离祖先检查在挂载边界被截断，宿主侧 validate 成为新的、契约外的保护点，其成立前提未写。**
位置：docker.md「身份、权限与持久布局」第 42 行（state-dir 及可见宿主祖先不处于永久隔离根下，脚本按 storage 的 marker 名检查）。依据：`storage-sql/src/sqlite/protection.ts:29-34` 从库路径逐级 `lstat(<dir>/.omne-isolated)` 直到文件系统根——容器内到 `/` 为止，宿主上 `/state` 以上的祖先对应用不可见；EC3 S-59「生产打开拒绝…不能核实也拒绝」。触发：state-dir 被指到宿主上某个 `.omne-isolated` 根之下的子树。后果：应用自身的「不能核实也拒绝」在容器内退化为「只核到挂载点」；补偿者是 Bash validate，只在显式 validate/start 跑（N1 的自动拉起不跑）。现实误配要同时满足「子树布局恰好是 `data/center.sqlite`」，概率低，且「迁明文」已在保证之外，所以不阻断；但这是一条**装配给**前提，须显式登记并带负例。作者需明确：（a）写明容器内祖先核查止于 `/state`，宿主祖先由 validate/start 核，Engine 自动拉起不重核；（b）脚本的判据须与 `protection.ts` 一致——任何名为 `.omne-isolated` 的目录项存在即拒绝（lstat 存在性，不限普通文件、不看内容）；（c）验收项 3 的「隔离子树」负例覆盖「marker 在 state-dir 之上」与「marker 在 state-dir 之内」两种。

**N6 · 代价 —— B2 以手册序列闭合，没有按表 D 自证，落选机制未标价、未回写候选比较。**
位置：docker.md 第 34 行；alternatives.md 仍是 R1（B 行的优先条件只写「Compose 负停止配置无法成立」）。依据：R1 B2 要求作者在 live-restore／shutdown-timeout／手册三者间明确认领；handbook reconciliation 表 D「回询前必须证明代价不来自自己的建模」。触发：接受决定形成时。后果：接受记录里只有「选了手册」，没有「为什么不是 live-restore/单元顺序」，下次有人问「Engine 升级为何要停中心」无处可查；B 的最强论证之一（`BindsTo/After=docker.service` 让 daemon 维护自动先停中心）从未被正面回答。作者需明确：在 alternatives 加一段 R3 修订——列出 live-restore 的适用与不适用（只救 daemon 重启，不救 reboot；daemon 配置变更时失效），列出 B 的单元顺序方案，写明 A 选手册的理由与代价；交范围外 1 裁决。

**N7 · 投影对齐 —— `unless-stopped` 下「退出 0 但非手动停止」会被重启，与原生 `Restart=on-failure` 行为相反，未作为负例写出。**

**N9 · 承载／分发 —— amd64 镜像如何构建与验证未定，应用层是否架构无关未断言。**

位置：docker.md 第 32 行；research P1–P3 只覆盖 `stop`/`down`。依据：Compose 官方 `stop_grace_period` 页只写正 duration 与默认 10s；Engine CLI `-t -1` 有据。触发：Compose/Engine 升到非 2.40.3/29.1.3。后果：负值被静默按默认处理时，中心会在 10 秒后被 SIGKILL，且没有任何检查会失败。作者需明确：validate/start 必须对实际容器 `inspect` 断言 `Config.StopTimeout == -1`（这就是绑定的探针），并声明脚本永不发 `restart`/`up --force-recreate`（这两个动词未验）。一句可闭合。

## 范围外待裁决（只列，不据此否决）

1. **无人值守 reboot／Engine 维护是否允许成为「非正常故障」**（每次未按序列的重启可能留隔离残余、`outcome-unknown`、自动崩溃恢复启动），还是要求它们走正常关闭（⇒ 候选 B 的单元顺序，或 A+live-restore 另行映射）。**Owner：PF-017 owner／部署方。**接受 A 不需要新的产品硬要求，但这项代价须写进接受决定而非只在 docker.md。
2. **Engine 重启次数不封顶作为默认**（原生绑定隐含 systemd StartLimit）——docker.md 第 32 行已要求「采用时明确接受」。Owner 同上。
3. **timer／运维者主体 = Docker API = 宿主 root 等价**（R1 范围外 2 未裁）。Owner 同上。
4. **工程记录跨升级/`down` 的保留期望**（N4）。Owner：PF-017 owner 与 observability 要求的维护者。
5. **Engine 自行拉起（非运维者启动）在「停止是运维者的动作」下是否可接受**（N1）。PF-017 §5.2 未禁止，需确认口径。Owner：PF-017 owner。

## 候选评价

**推荐方**：A（R3 形态：Compose + `unless-stopped` + 手动维护序列 + 宿主 timer 只 exec），**有条件**——条件是范围外 1–3 由有权者认下，N1/N2/N5/N10 落字，R3/R4 探针闭合。

**落选方 B 最强论证**（宿主 systemd 拥有容器生命周期）：
1. `TimeoutStopSec=infinity` + `BindsTo/After=docker.service` 让 `systemctl stop/restart docker`、OS reboot 都先按无限等待停中心——A 把这些全部划成外部故障（docker.md 第 34 行 vs maintenance-binding.md 第 25 行）。
2. systemd `StartLimit` 与 `Restart=on-failure` 提供有界重试且退出 0 不重启——A 不封顶且退出 0 也重启（docker.md 第 32 行；N7）。
3. 已有产品级 systemd 证据（`2026-09-26-tests-governance-maintenance`）与 journald 记录保留可直接接续——A 的日志随容器重建消失（N4）。
4. 单一「停止意图」状态（systemd 的 active/inactive），不存在 Engine `HasBeenManuallyStopped` 与运维意图两套状态需对齐（N2）。

**推荐方 A 已知弱点**：上述四条；负 grace 无官方文档（N10）；daemon 矩阵未验；宿主 root 等价的 timer 主体在 A/B 下都存在，不是 A 独有。

**B 的代价（为何仍不优先）**：前台 attach 的客户端退出≠容器退出、daemon 断连/attach 失败、同库已有容器与重启竞争、Engine 与 systemd 双管理器（官方明确警告）——alternatives.md 已述且无收益证据；用户已明确采用 Docker 内网部署。C 未重审，R1 结论不变（新增 PID1/supervisor 收场所有权，无收益证据）。

**置信度**：中。**改票条件**：（a）范围外 1 裁定无人值守 reboot/Engine 维护必须是正常关闭 ⇒ B（或另立 A+live-restore 候选比较）；（b）R3/R4 显示显式 stop + exit1 在 daemon 重启后被拉起 ⇒ A 的停止意图保证失效 ⇒ B；（c）负 grace 在生产 Linux Engine 的任一支持动词上不成立 ⇒ B。
