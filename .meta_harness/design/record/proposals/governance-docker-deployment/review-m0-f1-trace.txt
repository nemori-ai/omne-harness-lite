The same `normal_stop` implementation is exercised on real restarting via start-failure cleanup, while a direct `stop` entry is wired to it and checked with an injected restarting status. The older Engine experiment explains why the control handles empty acknowledgement and no-revival cautiously. Additional real fault injection is not intrinsically necessary to judge the *unknown-result and single-request branches* here. Existing records do **not** establish final-helper direct stop on restarting, sustained final-helper second-owner no-revival/event history, final-helper-alive lost acknowledgement, or real completion-before-TERM. If “必须重验” is read as requiring each of those as an actual final-helper Docker execution, the present evidence cannot close that literal requirement; only root can accept a more precise finite evidence combination. Do not describe the arm64 one-shot inspect as a continuous event window, or the amd64 second-owner as restarting.
