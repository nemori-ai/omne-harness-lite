## Findings, most severe first (none blocking)

**1. Low · wording is broader than the code: the 5s deadline doesn't stop a stalled import.**
- **Where:** `apps/tenancy-host/deploy/docker/health.mjs:47-53` waits for `loadCommand()` without also watching the deadline. `docker.md:50` says the deadline "覆盖完整调用".
- **What the deadline does do:** the monotonic checks at `:53` and `:63` block any late success. For socket reads, cancellation goes through the existing path: `main.ts:92-97` → `maintenance-command.ts:96-98` → `socket.destroy` at `:91-92`.
- **What it doesn't do:** if the import never settles, the process only ends when something outside kills it.
  - Docker's own health timeout does kill it. Case C shows this.
  - The helper's check (`omne-center:710-711`, `timeout --signal=KILL docker exec`) kills only the host-side exec client. The probe inside the container keeps running until the import settles.
- **Why no guarantee is broken:** there's still one process and no child process. A hung local-file import is hypothetical.
- **Type:** future enhancement. Either also watch the deadline during the import, or narrow the wording in `docker.md`.

**2. Low · missing evidence: the default timing order isn't tested on the real image.**
- Case C only covers Docker killing the probe first (outer 2s, inner 5s).
- With the defaults (outer 7s, inner 5s) the probe should expire on its own. That path is tested only in `tests/docker-health.spec.ts:87-117`, against the source `main` (not `dist`) and a real socket.
- D072 required only the shorter-outer case, and no child process exists on either path, so this doesn't reopen F5.

**3. Low · architecture residue: the probe now loads the whole public index.**
- `src/index.ts:2-55` loads `boot`, `config`, `keys`, `migrations`, `manifest` and `log` up front. The old CLI path loaded them lazily through `main.ts:59/73/85`. D072 recorded this counterargument itself.
- **Today:** no top-level side effects in the app source (the grep found no top-level handlers, timers or awaits in `src`). Case N reached a real Engine `healthy` state, so the process exits cleanly. The case C log (`raw/logs-4.stdout:2`) shows about 216ms from health start to the request on arm64, well inside 5s.
- **Risk:** if a package pulled in by the index later gains import-time side effects, they would run inside every 30s probe, as UID 10001, in the center container. Worth adding as a review trigger.
- **Type:** future enhancement.

**4. Low · traceability gaps in the records.**
- `review.md:91-101` still shows F2, F3, F4 and F9 as 待补. The only record that they're done is in `evidence/2026-09-27-tests-docker-health-binding/README.md:5` and in the README itself.

## Answers to the review questions

**F5 is closed within D072.**
- **By construction:** there's no child-process path left in `health.mjs`. The probe's ppid is 0 (`logs-4.stdout:2`), so its parent is outside the container, not Node PID1. Nothing can be reparented to PID1.
- **By evidence (case C):**
  - PID 13 (start ticks 535861) is gone by 03:50:36.316Z.
  - Engine `Health.Log` shows exit −1 with the 2s timeout.
  - Descendant and ops-client lists are empty in every sample, and the late write got EPIPE (`oracle.stdout`).
- **Other checks:**
  - **Output cap:** the 64KiB limit counts UTF-8 bytes; the 'é' test at `spec:127` covers this.
  - **Oversize error:** an oversize error thrown from `stdout` is caught at `maintenance-command.ts:205/207` and returns 1.
  - **Strict fields:** `maintenanceExit` returns 0 for any validated full-health (`:146`), so the wrapper's own field check at `health.mjs:13-22` is necessary, and it's there.
- **Architecture:**
  - Compose, the Dockerfile and the helper still bind the same health command (`compose.yaml:40`, `Dockerfile:9`, `omne-center:378`).
  - No new transport, supervisor or policy was added.
  - Tenant and credential boundaries are unchanged.

**F2 is resolved** (`README:28-44`): verify the trusted archive SHA before loading, then use the local ID from the load. The problem was real: in case N the private legacy store reported ID `ab9ade…`, the outer image was `bc41ea…`, and they matched by RootFS and BUILD. Comparing RootFS layer IDs is still not an operator step. The pre-load archive SHA is enough as the integrity check.

**F3 is resolved** (`README:49-53,170-172`), apart from finding 5.

**F4 is resolved** (`README:132-142`). It shows how to find the process holding the lock and forbids deleting the lock file or killing a guessed PID.

**F9 is resolved** (`README:152-156,240-241`): the log command is given, and TUI against the Docker center is stated as untested.

**F1's layered disposition is sufficient** (`review.md:105-113`).
- Each item says whether it was seen on a real Engine, used a real shell signal, or used a stubbed Docker response. Stubs stay labelled as stubs.
- My earlier claim that amd64 was also restarting is corrected (the trace at line 10 shows `status=running`).
- The real combinations never observed are listed by name: direct stop on a restarting container, a sustained no-revival window, a lost acknowledgement while the helper is alive, and completion before TERM.
- Requiring any of them later is reserved as a new requirement. No required guarantee is silently dropped.

**The I4 evidence fits the changed surface.**
- The product change is only `health.mjs` plus the operator README; `dist` JS bytes are unchanged.
- **N on both architectures:** a real center reaches strict healthy, and the business journey, backup and stop to exit 0 all pass.
- **C:** covers cancellation.
- **Stated limits, all fair:**
  - C's peer is a QA socket server, not the center.
  - amd64 ran under named Rosetta emulation.
  - The arm64 `comm` fix re-evaluates unchanged raw files (236 unchanged); it is not a new run.
  - The stale `business_complete=false` field is not used as evidence either way.
  - Portability of the old staging paths in third-party `.bin` files remains unverified.
- Old I3 evidence stays at its original scope.

**Strongest argument for blocking:** loading the whole public index into every probe is exactly the dependency widening D072 acknowledged. Unlike the old `execFileSync`, nothing hard-bounds a stalled import. It doesn't hold up: there's no child process, Docker's kill is confirmed in case C, and the success path exits cleanly on the real image. It remains a future hardening item.
