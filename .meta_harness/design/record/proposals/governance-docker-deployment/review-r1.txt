## 阻断

### B1 · 投影对齐／反向核对：Engine `restart: on-failure` 与中心退出码语义叠加后，「运维者主动停止的中心不被复活」在 daemon 重启这条路上没有保护点

- **位置**：design.md「候选A的责任投影」第 5 条（"Engine restart策略候选on-failure，只用于异常退出；显式停止后不重启须实测"）；DK4；Q1 只写「restart行为」。
- **依据**：
  - Docker 官方 *Start containers automatically*："If you manually stop a container, the restart policy is ignored **until the Docker daemon restarts** or the container is manually restarted"；`on-failure` 的判据是「exit code indicates an error」。
  - 本仓库 `apps/tenancy-host/src/main.ts:76-77` + `boot.ts:225-243`：撤除有残余（controller/storage 槽非 clean、任一 fiber dispose 失败）⇒ `HostDisposal.complete=false` ⇒ **退出 1**；这是 D055 有意设计的可见失败。`docker kill`/超时 SIGKILL ⇒ 137。
  - PF-017 §5.2「停止（运维者动手）」、§6.18「运维者有意停止中心时，备份安排不能把它自行启动」「核对完成前不重新开放业务访问」。
- **触发场景**：运维者 `docker compose stop` 停中心（为升级、换密钥、改部署参数，或恢复核对期间**有意保持停机**）；本次撤除以 `dispose-incomplete` 退出 1（或被强杀）。之后宿主重启／Engine 升级／`systemctl restart docker` ⇒ daemon 重启 ⇒ `on-failure` 按「上次退出码非零」把中心**自动拉起**——在旧镜像、可能已被换过的密钥或参数上，并重新开放业务。
- **后果**：DK4 只挡住了 timer 这条复活路径，Engine 自己这条没人认领；PF-017「停止是运维者的动作」在 daemon 重启后失守。附带：`on-failure` 不带 `max-retries` 时，升级启动失败（迁移 1 GiB 级库可能超过 Docker「启动成功」阈值）会进入无上界的「恢复快照→重跑迁移→失败」循环，与 systemd 模板的 `StartLimit` 行为不等价。
- **作者需明确**：Engine 重启策略与本应用退出码语义的组合表，逐格写「崩溃／有意停止且退出 0／有意停止且退出 1／强杀」× 「daemon 不重启／daemon 重启」的期望与实际；Q1 必须含「stop→exit≠0→daemon restart」「kill→daemon restart」「boot 失败≥阈值的重试次数」三支。是否改策略、改停止动词（`down` vs `stop`）或改退出码约定，由作者比较代价后提出，我不代选。
- **为什么本阶段必需**：这是 A 与 B 的分水岭（谁拥有生命周期）；接受后再改会改部署契约与运维手册。**不能一处措辞闭合**——是机制选择。

### B2 · 反向核对：Docker daemon 的停止路径是第二条「到期强杀」路径，DK2 的义务没有把它排除也没有给它认领者

- **位置**：design.md DK2「容器停止路径等待，不添加期限到点强杀」；正文末段只排除「管理员 docker kill、强制 shutdown 或整机损毁」；alternatives.md A 行「Compose的正常停止必须能传无限等待」。
- **依据**：Docker *live-restore* 文档："By default, when the Docker daemon terminates, it shuts down running containers"；`dockerd --shutdown-timeout` 默认 15 秒（daemon 级，不是 `stop_grace_period`）。EC3 S-59「关闭」行：正常关闭无有限上界；「强制终止是非正常故障」。现行 B 方案的 `TimeoutStopSec=infinity`（`deploy/omne-tenancy.service:18`）覆盖了 systemd 的关机路径；A 方案下这条覆盖消失。
- **触发场景**：常规 `reboot`、`apt upgrade docker-ce`、`systemctl restart docker`——都是运维者的**日常动作**，不是「强制 shutdown」。备份／排空进行中 ⇒ daemon 以 15 秒（或其配置）强杀中心 ⇒ 每次例行重启都变成 S-59 意义上的「非正常故障」：隔离残余、`outcome-unknown`、`.owner-lock` 靠 OS 释放、下次启动走崩溃恢复。
- **后果**：DK2 写的是一条设计并不兑现的保证；运维手册若照写「stop 无上界等待」会误导；Q2 的「强杀后重启/残留」矩阵没有把这条最常见的强杀来源列进去。
- **作者需明确**：daemon 停止路径由谁兑现——`live-restore` 采用与其限制（仅 patch 升级、daemon 配置不变、FIFO 日志满阻塞）、`shutdown-timeout` 取值、还是把「重启／升级 Engine 前必须先 `compose stop` 并确认退出」写进运维手册与验收；相应更新 DK2 的适用范围和 Q1/Q2 探针。
- **为什么本阶段必需**：它决定「正常停止」这条性质在 A 下的真实覆盖面，直接进验收矩阵。**可由「范围声明 + 一项配置决定 + 手册条目」闭合**，但不是改一句话；若作者选择只做范围声明（把 daemon 停止归入强制终止），需同步改 DK2 与 M0 验收口径，并由有权者认下代价（见范围外第 1 条）。

## 实现后应验（在 Q2–Q4 之上）

- 正常停止：IO 门挂住 >31 s 与 >`stop_grace_period` 默认值时仍 deactivating、第二属主 `occupied`，放行后退出 0；`stop`/`down`/`restart`/recreate 四种动词各一次。
- 强杀矩阵：`docker kill`、daemon 停止（默认 15 s）、宿主 reboot，各在「备份中／发布中／排空中」切点；重启后隔离残余被拒、`.owner-lock` 可取得、status 结果。
- 复活矩阵：有意停止（退出 0／退出 1）、强杀 → daemon 重启 → 中心是否被拉起；timer 触发 → 已停中心不拉起（已有 systemd 证据不迁移）。
- 升级：新镜像启动失败 → 重试次数有界、快照恢复、旧 tag 照常起；成功路径公开/完整体检。
- 权限：容器内非 root、宿主文件 uid 映射、只读密钥/证书挂载、socket 目录 0700 核验通过；`exec --user root` 被拒。
- 挂载：标记之下子树挂载的负向用例。

## 候选评价

- **推荐方**：A 有条件成立——前提是 B1、B2 各有明确认领且 Q1 证明无界等待跨全部停止动词成立。
- **落选方 B 最强论证**：① daemon 重启／关机语义由 systemd 拥有（`TimeoutStopSec=infinity`、`StartLimit`），B1/B2 在 B 下天然有保护点（`deploy/omne-tenancy.service`）；② timer 主体保持非 root `omne`，无 docker 组 root 等价（N1）；③ 单一生命周期拥有者，不存在 Engine 的 `HasBeenManuallyStopped` 与运维意图两套状态；且现有 `maintenance-systemd-product-r1` 证据可直接接续。
- **推荐方 A 已知弱点**：上述三条；Compose 负 grace 无官方文档；两级停止路径（Compose/Engine/daemon）需分别取证。
- **置信度**：中低。**改票条件**：Q1 证明 Compose 不能在全部停止动词上表达无界等待，或找不到既「崩溃后重启」又「有意停止后跨 daemon 重启不复活」的 Engine 策略组合——则 B 优先；C 仍不优先（新增 PID 1/supervisor 的收场所有权，无收益证据，alternatives.md 已述）。

**未决政策 owner**：PF-017 owner／部署方（范围外 1、2）；**证据缺口 owner**：机制探针执行者（Q1 及 B1/B2 追加支）、verification owner（Q2–Q5）。本报告是意见与证据，不构成接受。
