# CLI-TUI 交付面：承载分析与框架

## 需要作出的选择

**这个交付面用什么技术做出来，它的大框架是什么形状。**可观察结果落在两处：

- **人**：在终端里说话、看日志流、答卡片、发控制指令、切身份与模型、几天后回来接着聊；
- **脚本**：用同一条受理与同一份投影，把「输入 → 受理 → Run → 模型/工具 → 等人 → 终态 → 记录」
  整条链跑通、断言、离线重放。

**必须保留的**是 [alternatives.md](alternatives.md) 开头那张性质表。
**可调整的**是呈现形态、渲染库、进程切分、分发渠道、协议形状。
**不在本次选择范围内的**：任何领域语义。

> **界面不是能力，是投影。**
> 交付层的全部领域语义来自[架构内核 PF](../../../product/architecture-core.md) 已立的对象：
> 会话日志是唯一真相，决策池是唯一答题处，控制指令是唯一控制入口。
> CLI-TUI 只做三件事：**把日志投影成人能看的、把人做的事变成入站到达或控制指令、
> 把这两条通道同样暴露给脚本。**
> 因此它的技术选型只需回答「用什么把行画到终端上」，而不必回答任何「agent 该怎么跑」的问题。

**交付深度**已由 [D-022](../../decisions/cli-tui-delivery-form/README.md) 定死：
只到选型、路径、实施注意事项与大框架，**不下沉到模块级实现逻辑**——
几乎所有系统模块与领域的架构与规格设计都尚未开始，现在写细节等于替那些设计预先拍板。

## 现有能力如何承载

**这个交付面相对目标态是「新增」**——本提案落盘时，没有任何已立 PF 拥有「终端里长什么样」这件事
（2026-09-22 已裁定为它开题 **PF-016**，正文另行起草；它不在架构内核清单上）。
但它新增的只是呈现与受理的**具体形态**，不新增任何领域概念。它是三个已立 PF 在人这一侧的第一次具体化：

| 已立的 PF | 它立了什么 | 交付面在其中是什么 |
|---|---|---|
| [PF-008 Human in the Loop](../../../product/PF-008-human-in-the-loop/README.md) | 人**在哪里**看到问题、怎么答、答完怎么回去；决策池；永远等着 | **那个「哪里」的第一个实例** |
| [PF-014 输入的受理与排队](../../../product/PF-014-inbound-intake-and-queueing/README.md) | 外面进来的事怎么被收下；控制指令的受理 | **一个入站来源**，以及控制指令的一个发出口 |
| [PF-015 会话的生命周期与归属](../../../product/PF-015-session-lifecycle-and-ownership/README.md) | 会话怎么建、活成什么样、什么时候归档；运行模式 | **会话管理的一个客户端** |

逐条承载：

| 要求 | 现有能力与精确坐标 | 怎么组合、谁交接责任 | 未覆盖承诺 / 实现缺口 / 未确认前提 |
|---|---|---|---|
| 人说的每句话先落盘再被承接 | [PF-014](../../../product/PF-014-inbound-intake-and-queueing/README.md) 入站到达与受理；PF-010 到达先落盘 | 交付面**提交**，受理是 PF-014 的动作；回执以投影回来 | **实现缺口**：受理的契约与实现都不存在（`packages/` 空骨架） |
| 屏幕上那条流从哪来 | [PF-012](../../../product/PF-012-agent-loop-and-run/README.md) 会话日志；PF-000 记录条目；PF-009 消息类型 | 交付面**只读**日志的投影，顺序与日志一致 | **语义缺口**：会话日志投影协议已在 PF-015 立，但投影事件族尚无契约 |
| 停下来等人 | [PF-008](../../../product/PF-008-human-in-the-loop/README.md) 决策池与卡片 | 交付面摆出卡片、把答复经同一个池子交回 | 无新责任；**通知形态未定**（见交接缺口） |
| 控制指令 | PF-014 的五条：取消 · 强制停止 · 插队 · 切后台 · 中断工具执行 | 交付面是一个发出口，受理仍在 PF-014 | **产品缺口**：插队与取消在界面上必须分得开，这是呈现要求不是新语义 |
| 会话的建/进/归档/运行模式 | [PF-015](../../../product/PF-015-session-lifecycle-and-ownership/README.md) | 交付面是客户端 | **PF-015 仍是草稿**：归档撤销、运行模式三档、元 runtime context 的三项字段按草稿做，接受后可能重做 |
| 身份、作用域与设置的呈现 | PF-001 当前租户身份、PF-002 作用域求值 | 交付面只读求值结果与来源层；切换是 PF-001 的动作 | 无新责任 |
| 模型与执行环境的呈现与切换 | [PF-013](../../../product/PF-013-model-profiles-and-invocation/README.md)（草稿）、[PF-005](../../../product/PF-005-execution-environments-and-sandboxes/README.md) | 交付面是入口；宿主机允许是一次授权动作 | **PF-013 仍是草稿**；执行环境权限三态的默认档产品未定 |
| 账号、组织、邀请、隶属、资产流转 | 三份租户契约：[account-identity](../../../spec/capabilities/account-identity/README.md)、[organization-governance](../../../spec/capabilities/organization-governance/README.md)、[account-registration](../../../spec/compositions/account-registration/README.md) | 治理族命令与契约操作**一一对应**，交付面不重写语义 | **三份都是 `candidate`**，[catalog 已登记、未接受](../../../registry/README.md)；治理族的精确命令清单**应从 catalog 生成而非手写** |
| 模型请求经 OpenRouter | [SYS-LLM](../../../foundation/cross-system-constraints/requirements.md#sys-llm)；[pi-ai 定向 fork](../../decisions/model-provider-pi-ai-fork/README.md) | 传输层不在本提案重选 | **凭据落在哪未决**（见 [alternatives.md](alternatives.md) 的 Q-凭据） |

**结论：领域侧一条都不缺。**缺的只有「投影与受理这一层本身」。

## 剩余责任与能力演化

| 剩余问题 | 关系 | 归属理由与消费者影响 |
|---|---|---|
| 把日志、决策池、会话状态**组合成一份面向人与脚本的只读投影**，并把人/脚本要做的事**受理进已有入口** | **新增一个能力维度**：前端门面 | 独立变化原因（呈现与受理形态随交付面变，不随领域变）＋ 独立消费者（界面、无界面模式、未来的桌面壳）。消费者是交付面自己，不是任何领域 owner |
| 投影事件与提交的**语言无关契约** | 新增契约 | 三种传输（本机 socket、stdio、进程内）语义必须相同；TS 类型是 Schema 的投影，权威在 Schema |
| 本机与中心之间的**协议投影** | 已有契约的远端投影 | 三份租户契约的操作在协议上一一对应；**不新增语义**，daemon 只做客户端 |
| 界面观感类配置 | 新增数据，不进作用域求值 | 本机偏好随机器走，与个人 context 是两回事 |
| 渲染、终端差异、分发、测试驱动 | **非结构性**（实现选择） | 不产生领域责任；归 [realization 的应用节点](../../../realization/README.md) |

**提出新维度的依据**：检查过让已有能力承担这一层的三条路，都不成立——

1. **挂在会话或 Run 能力上**：那会让「终端里长什么样」跟着领域对象走，
   换一个交付面（桌面壳、Web）就要改领域能力；且它会拥有领域状态，直接违反「交付面不持有任何领域状态」。
2. **让每个领域能力各自暴露一个读面**：投影的顺序保证（与日志一致）与断线续读的序号是**跨能力**的，
   分散到各 owner 就没人拥有那条顺序。
3. **只做一层薄适配、不立能力**：本机与中心拆开之后，
   「投影顺序＝日志顺序」「提交幂等」「断线续读」三条必须由**协议**重新兑现——
   没有拥有者的适配层承担不了这三条。

**前端门面承诺什么**：把已有服务面组合成投影事件流与受理入口；**不承诺**任何领域保证，
**不持有**任何领域状态，**不拥有**任何存储。它通过 inject 消费 harness 的服务面与治理契约的客户端提供者，
是 harness 的**消费者**而不是它的一部分。

## 框架：拓扑、分层、通信、进程

**深度到插件边界与契约轮廓为止。**字段、状态机、每个操作的前置后置等架构与规格设计正式开工再展开。
**实现形状（精确包名、技术栈采用的精确版本、分发渠道、装配清单）的家在
[realization 的应用节点](../../../realization/README.md)`apps/cli/architecture.md`**，不在本页。

### 拓扑

```text
                 ┌───────────────────────────────┐   HTTPS 请求/响应 · 登录状态作 bearer · 版本协商
                 │ 中心治理节点（独立应用）          │◄─────────────────────────────────────────┐
                 │ 账号身份 · 组织治理 · 注册组合     │  三份租户契约的事实；不知道任何会话          │
                 │ 资产分享/复制 · 凭据签发（未决）   │                                            │
                 └───────────────────────────────┘                                            │
 ══════════════════════════════ 用户本机（每位同事一台）══════════════════════════════════════╪═══
 ┌─────────────────┐ 本机 socket ┌──────────────────────────────────────────────────┐      │
 │ 客户端           │◄──────────►│ 本机节点 daemon（按 OS 用户一个，按需拉起）           │──────┘
 │ 界面 · 无界面     │ 行分隔 JSON │ 会话日志（唯一写者）· 受理与队列 · 决策池 · 通知        │
 │ 每个终端一个      │ 按登录状态  │ agent runtime 协程（每个活跃会话一副，同进程）          │
 └─────────────────┘ 认证        │ 模型传输与账本 · 治理客户端与缓存 · 前端门面 · socket 监听 │
                                 └──────────────┬───────────────────────────────────┘
                                                │ 子进程（工具执行）
                       ┌────────────────────────┴───────────────────────────┐
                       │ 前台执行进程组（每个 Run 一组）· 后台执行进程组（每次执行一组）│
                       │ pty shell · MCP server · 沙箱实现的驱动                  │
                       └────────────────────────────────────────────────────┘
```

**为什么 v1 不切工作进程**：切进程的唯一理由是故障隔离，而本项目零测量；
独立评审指出否决「daemon 内跑协程」的证据全是别家**渲染层**的缺陷，渲染层在客户端进程里、与 daemon 无关。
**契约保持进程无关**，测出隔离或内存瓶颈后再把 runtime 搬进工作进程，只换提供者不改契约。

### 分层与依赖方向

四层，自上而下：**应用装配**（一个可执行文件，两份固定装配清单：客户端 / daemon）→
**交互层包家族 `frontend`**（契约 · daemon 侧门面 · 本机 socket 两端 · 终端界面 · 无界面模式）→
**harness 能力族**（架构内核 PF 的实现，尚未设计；v1 全部本地提供者，装在 daemon 里）→
**内核**（Cordis 官方包 + 本项目 fork 的 DSH 原语）。
租户契约的实现另成一族：本地提供者装进中心治理节点，HTTP 客户端代理提供者装进 daemon。

依赖方向的四条规矩：

1. **界面与无界面模式只依赖契约**，经 socket 客户端拿到实现，对 harness 内部零感知。
2. **门面是 harness 的消费者，不是它的一部分**；它自己不持有任何领域状态。`frontend` 家族里只有它依赖 harness。
3. **同一个可执行文件按命令决定装哪一份清单**。「内嵌模式」是两份装进同一进程、传输换进程内，**只供验证与调试**。
4. **中心治理节点是另一个完整的应用**，独立分发、独立部署；与 CLI 之间只有一条边。

`frontend` 这个家族名是 [D-022](../../decisions/cli-tui-delivery-form/README.md) 接受的；
包名与两层布局的精确形状归应用节点，**只在规格接受后建成员**。

### 通信：两份契约、三条边

| 边 | 契约 | 传输 | 认证 |
|---|---|---|---|
| 客户端 ↔ daemon | **前端契约** | 本机 socket，行分隔 JSON | **每条连接出示登录状态凭据**；daemon 不从 OS 用户推断账号；socket 文件权限只是第二道 |
| daemon ↔ 中心 | **治理契约的线上投影** | HTTPS 请求/响应，JSON 体；**v1 无推送** | 登录状态作 bearer；版本头协商 |
| 无界面模式对外 | 前端契约 | stdio 行分隔 JSON，**是 socket 帧的转发** | — |
| 内嵌模式 | 前端契约 | 进程内 | 只供验证 |

**前端契约的两个方向**：

- **下行 · 投影事件**：会话日志投影协议的**第一个消费者**——会话日志、决策池、会话状态
  已发生之事的只读投影，每条带来源坐标（记录条目 ID / 序号），顺序与日志一致。
  **不是第二份存储，不是 UI 状态，不是新的一类投影协议。**
  族轮廓：会话 · 记录条目 · 流式片段（落盘那一刻以记录条目为准）· 运行（runtime 起落对用户不可见）·
  等待与卡片 · 受理回执 · 非常态 · 通知 · 观测。
- **上行 · 提交**：人或脚本要系统受理的事。**不是直接写日志**；受理结果由系统回一条投影事件。
  族轮廓与幂等语义：说话（带幂等键，**用户自己重发的两条都算**，键只用于同一条的传输重试）·
  答卡片 · 控制指令 · 会话管理 · 身份与范围 · **治理（直通中心，按各操作自己的规格，不补造请求身份）**· 查询。

三条契约级规矩：**每条投影事件带来源坐标与单调序号**（断线续读靠它）；
**秘密值不进契约**；**契约有版本字段，改动发新版本**——
CLI 打印的每一行结构化文本都会变成接口。

传输侧两条：**有界缓冲**（每条订阅一个有界队列，写日志路径从不等待订阅者，慢客户端超限即断、按最后序号续读）——
内核不提供背压与可靠投递，这两条由传输层自己兑现；
**断线不卸载界面**（客户端代理提供者断线时标记「不可达」并保持 ACTIVE，界面不被重跑；
界面状态由界面包**显式持有**，不依赖 fiber 存活）。

### 进程模型

| 进程 | 生 | 灭 | 持有什么 |
|---|---|---|---|
| **客户端** | 每个终端或每次调用一个 | 用户退出；只是观察者走了 | 零领域状态；**显式的界面状态**；本机偏好；登录状态凭据的引用 |
| **本机节点 daemon** | 任一命令按需拉起；是否常驻未决 | 空闲策略；或版本不一致时排空后重启 | 会话日志、决策池、队列投影、agent runtime 协程、模型账本、治理缓存、登录状态。**本机唯一写日志的进程** |
| **中心治理节点** | 部署一次 | — | 三份租户契约的事实；不知道任何会话 |

**工具执行的子进程按宿主分组**：前台工具执行每个 Run 一组（取消/强制停止这个 Run 带走它）；
已转后台的工具执行**每次执行自己一组**（会话归档、daemon 退出带走它，Run 的取消**不**带走它）；
终端会话挂在执行环境上。

五条不变式：

1. **单写者**：只有 daemon 写会话日志；尝试序号栅栏在它一处执行。
2. **daemon 随时可杀**：等于 PF-012 的「停机」，恢复走「先对账再重算」；后台执行随 daemon 退出算失败。
3. **强制停止三步闭环**：落取消请求条目 → 向该 Run 的前台进程组发信号并宽限后强杀 →
   daemon 写终结条目并标「可能有未收尾的外部效果」。模型流的中断由同进程的 runtime 直接执行。
4. **首 token 之后不重发**由模型传输在 daemon 内守，与 runtime 同进程。
5. **任何进程都不是领域对象的宿主**：客户端退出＝观察者走了；daemon 退出＝这一批 runtime 没了，
   **不是取消、不是失败**。

### 交互面

原则：**会话与组织都是一等对象 → 动作是一等子命令**；**斜杠命令与子命令共享同一份命令定义**；
**脚本能做的人能做，人能做的脚本也能做**。

命令族轮廓：界面模式入口 · 无界面模式 · 会话族（列/看/续/归档/撤销归档/运行模式）· 日志投影（可续读、可机器读）·
治理族（登录与登录状态管理、账号、组织、邀请、隶属、租户、资产——**精确清单从 catalog 生成**）·
本机族（首启引导、设置只读面、模型、节点管理、体检与还原、版本）。
**退出码族有含义**（正常 / 系统错误 / 用法错误 / 等人中退出 / Run 失败 / 治理操作被规格的失败集合拒绝 / 信号），
它与机器可读输出的精确形状是**契约的一部分**，归 spec。

## 契约与 Cordis 投影

**到插件边界为止。**落点按最小内核模型逐个判：

| 对象 | 落点 | 理由 |
|---|---|---|
| 前端契约的帧形状 | **数据** | 只有形状没有行为，不进 `ctx` |
| 前端门面（投影与受理 + 治理直通） | **plugin + service** | 独立变化原因 **且** 独立消费者——本设计唯一新增的能力维度 |
| 本机偏好、界面状态 | 数据 | 前者随机器，后者随客户端进程 |
| 界面 / 无界面 / socket 两端 / 治理 HTTP 客户端 | **fiber** | 各有独立资源、失败要隔离 |
| 调试流 | 非结构性（可观测性调整） | 不走能力主线 |

装配草图（三棵根，各一份清单）：

```text
daemon 装配根
 ├─ harness 各插件（尚未设计；假定提供：日志读写面 · 受理 · 决策池 · 控制受理 · 会话管理 ·
 │                   作用域求值读面 · runtime 调度 · 模型传输 · 通知）
 ├─ 治理契约的 HTTP 客户端代理提供者   effect: 显式绑定连接状态；不可达 → 准入面明确失败
 ├─ 前端门面                          provide 门面服务；inject 上述服务面；
 │                                    effect: 订阅日志新增 → emit 投影事件；提交走服务方法
 └─ 本机 socket 服务端                 inject 门面；effect: 监听、认证、每连接一条有界订阅，disposer 关闭

客户端装配根
 ├─ 本机 socket 客户端                 provide 门面服务（远端实现；断线标记不可达、不卸载）
 └─ 二选一：终端界面（effect: raw mode / 键盘协议 / resize / 渲染循环，disposer + 退出钩子还原终端）
            无界面模式（effect: 接管 stdout / 读 stdin，disposer 刷缓冲）

中心治理节点装配根
 ├─ 租户契约的本地提供者（尚未设计）+ 存储 + 凭据签发
 └─ HTTPS 服务端                       effect: 监听、版本协商，disposer 关闭

内嵌模式 = 前两棵装进一个进程；中心用测试替身
```

**六问的答案**：契约是数据、门面是服务；每个传输端、界面、无界面、门面各自独立 fiber；不 isolate；
界面 inject 门面但**断线不触发重跑**（代理保持 ACTIVE）；
**投影事件是通知（`emit`）、提交是异步控制走服务方法不走 `bail`**；
装载与撤除配对——raw mode ↔ 还原序列（另加退出钩子与信号处理）、监听 ↔ 关闭、连接 ↔ 显式断开。

**多进程在 Cordis 范式下怎么成立**：fiber 树、服务解析、`inject` 重载、五种派发、effect 释放
**全部只在一个进程内**。所以**能切的是装配，不是能力**：每个进程一棵根 context、一份清单；
跨进程的服务面靠**远端代理提供者**在本进程 `provide` 同名服务、实现走协议；
跨进程的事一律是协议消息，**不是 Cordis 事件**。
v1 只用到它的一处：治理契约在 daemon 里是 HTTP 客户端代理提供者。
真要把 agent runtime 搬进工作进程时要守四条：跨 realm 服务面只能异步；单写者与序号栅栏由 daemon 真实现兑现、
代理只转发；代理的生命周期由**显式 effect** 绑到连接（断线 → 标记不可用 → 依赖方按契约失败，
**不是「进程自然退出」**）；代理挡住重载风暴，只有协议版本变才断连。

**反向核对四问**：客户端退出不撤销任何领域动作；daemon 退出带走 runtime 与后台执行，
在途工具执行按 PF-012 对账规则算失败或不知道；投影事件在 daemon 内派发，只按订阅转发；
**跨进程后哪些保证失效**——「投影顺序＝日志顺序」「提交幂等（会话族）」「断线续读」**是契约给的**，
v1 在 socket 上兑现；「零序列化」「同步可见」**只在内嵌模式成立，不得被任何测试当成契约保证**。

## 证据义务与受阻消费

| 依赖的性质与前提 | 谁保证、谁只是假设 | 所需证据与当前结果 | 闭合条件与受影响选择 |
|---|---|---|---|
| 渲染层能兑现中文输入与流式不卡 | **假设**：来自六家调研的文档与源码读数，**本机未装 pi-tui，零运行时取证** | E1–E3 三个区分实验，**均未执行** | 跑完才知道 D2 是否成立；失败则 D2 改选 |
| daemon 随时可杀后恢复一致 | PF-012 保证语义；交付面只负责不丢观察 | 崩溃注入（受理与落盘之间、落盘与组装之间、首 token 前后、工具执行中各杀一次），**未执行** | harness 首批能力有可实施规格之后；做不到则「重算」在实现上没成立 |
| 界面与无界面同一投影同一受理 | 交付面自己 | 同一场景两种模式的记录条目序列逐条相同，**未执行** | 契约与两种传输都在之后；这是「界面不是能力」唯一可核的证据 |
| 治理操作的失败集合逐条命中 | 三份租户契约（`candidate`） | 两个登录状态对一个隔离中心的脚本，**未执行** | 三份契约接受之后 |
| 跨进程后三条保证由协议兑现 | 前端契约（**尚未起草**） | 三种传输语义等价的对照，**未执行** | 契约起草并接受之后 |
| 秘密值不上任何可见面 | 可观测要求；PF-013 | 哨兵串在任何输出面搜不到，**未执行** | 凭据归属（Q-凭据）裁决之后 |

**受阻消费**：`packages/` 与 `apps/` 是空骨架，harness 首批能力的**架构与规格都还没开始**。
在它们有可实施规格之前，交付面能独立做的只有：区分实验、前端契约起草、
按契约实现的**替身**（只回放契约允许的事件序列，**不长出任何产品行为**；
替身里「看起来合理」的行为都是 gap，不是设计）、以及与 harness 无关的体检/还原/非 TTY 拒绝。
