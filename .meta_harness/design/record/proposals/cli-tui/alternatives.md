# 候选与取舍

十一个决定点，每个先写**选择对象与必须保留的性质**，再列 3 个以上实质候选（多数另有一条基线），
用**同一把尺**比较：兑现必要性质的方式 · 总负担 · 演化与维护归属 · 证据与缺口。最后给推荐与否决依据。

**推荐不等于接受。**本页全部推荐都是本设计自定、可被推翻的选择；
[decisions](../../decisions/README.md) 里没有任何一条接受它们。

六家调研的结论按序号引[研究结论](../../../../research/agent-harness-cli-tui/research.md)（「结论一」～「结论十三」），
逐家报告在[该 topic 的 reports/](../../../../research/agent-harness-cli-tui/README.md)。

## 选择对象与必要约束

**选择对象**：CLI-TUI 交付面用什么技术做、大框架什么形状。
**必须保留的性质**（各决定点再各自收窄）在 [design.md](design.md) 的承载分析里，摘要为：

| 类 | 要守住的 |
|---|---|
| 不变量 | 交付面不持有任何领域状态（显示的每条指回一条记录条目，提交的每件事成为一条入站到达/卡片答复/控制指令记录）；会话日志只增不改且交付面没有写日志通路；卡片答复只经决策池；界面模式与无界面模式消费同一份投影与同一条受理；跨租户默认拒绝；所有模型请求经 OpenRouter |
| 安全 | 永不替人作答（无超时、无默认答案）；进程以任何方式退出后终端被还原（SSH 断线与 `kill -9` 明确不覆盖）；机器可读输出通道只承载契约内容；宿主机执行环境未显式允许前不落任何动作；调试开关不改变领域行为；秘密值不上任何可见面；界面模式在非 TTY 下拒绝启动 |
| 进展（带前提） | 日志新增后界面有限时间内显示；人提交后有限时间内成为落盘的入站到达；无界面模式在终态且无未答卡片后退出；重新进入会话后该起的 runtime 有限时间内起；一帧内多次日志变化合并渲染，不因输出速率拖垮输入响应 |

**可调整的约束**：呈现形态、渲染库、进程切分、分发渠道、协议形状。
**不可调整的**：[SYS-KERNEL](../../../foundation/cross-system-constraints/requirements.md#sys-kernel)（内核层复用 Cordis 与 DSH `agent` 原语）、
[SYS-TENANT](../../../foundation/cross-system-constraints/requirements.md#sys-tenant)、
[SYS-LLM](../../../foundation/cross-system-constraints/requirements.md#sys-llm)（模型请求统一经 OpenRouter）、
[SYS-SPEC](../../../foundation/cross-system-constraints/requirements.md#sys-spec)（契约语言无关、JSON Schema 为权威）、
[可观测要求](../../../foundation/observability-and-logging/requirements.md)。

**两条已由 [D-022](../../decisions/cli-tui-delivery-form/README.md) 接受的前提**，本页不再作为候选比较：
产品形态是面向生产分发、多名同事各自装 CLI 进同一个组织；会话、Run、工具执行在用户本机，中心只管身份、治理与资产流转。

## 总览

|---|---|---|---|
| D1 | 运行时与语言 | **Node 24 + TypeScript**（workspace 既定） | Cordis 是 TS；SYS-KERNEL；不是真正的开放选择 |

| D3 | 呈现路线 | **只做内联 scrollback**，历史窗口化，完整历史走命令 | 五家共识；alt-screen 是产品级投入 |
| D4 | 终端差异承担 | **继承白名单 + 转义协商，暴露配置覆盖；非 TTY 拒绝启动界面** | 不写死特判、不改用户终端设置 |

| D6 | 进程模型 | **本机 daemon 内跑 agent runtime 协程 + 客户端；工具执行子进程按宿主分进程组；中心治理节点在远端**。每会话工作进程降为演化边 | 会话在本机已裁定；待机与拉起空闲会话要有宿主；**零测量不引入优化性复杂度** |
| D7 | CLI 命令体系形态 | **会话族与治理族都是一等子命令**；非交互是子命令而非标志位 | 与 PF-015 的会话对象、三份租户契约的操作一一对应 |
| D8 | 分发形态 | **v1 发 npm 包（含 `bin`），单文件二进制作为第二阶段** | 必须可安装、跨平台、可升级；单文件的两条路各有已知门槛 |
| D9 | 测试驱动方式 | **虚拟终端断言 + 真 pty 冒烟 + 隔离节点多客户端** | Pi 与 DSH 共用的做法；多主体流程要多客户端 |
| D10 | 配置文件形态 | **本机偏好单独一份、随机器走，不参与作用域求值**；它**不是**个人 context | Kimi 分家先例；fable 评审纠正 |
| D11 | 线上协议与认证 | **daemon ↔ 中心：v1 只用 HTTPS 请求/响应，登录状态作 bearer，显式版本协商；无推送**。客户端 ↔ daemon：本机 socket，**每条连接出示登录状态** | 中心不知道任何会话、准入现读，v1 说不出要订阅什么；同一 OS 用户不是钥匙 |
| — | 模型传输层 | **不重选**：[pi-ai 定向 fork](../../decisions/model-provider-pi-ai-fork/README.md)，在 daemon 内与 runtime 同进程 | 凭据放哪是未决回询，见本页末 |
| — | 检索工具（ripgrep 一类） | **不在本提案定**：那是 PF-006 工具层的事 | 结论五只作提醒 |

## D1 运行时与语言

**选择对象**：客户端、daemon、治理节点用什么运行时。
**必须保留**：与 Cordis（TS 包）同进程装配；[SYS-KERNEL](../../../foundation/cross-system-constraints/requirements.md#sys-kernel)。

| 候选 | 兑现必要性质 | 总负担 | 演化与维护 | 证据与缺口 |
|---|---|---|---|---|
| **A · Node 24 + TS**（workspace `engines: node >=24 <25` 已钉） | 与 Cordis 同进程零转换 | 客户端启动成本在四家实测里居中偏高的一档，但**客户端只装界面、不装 harness**（D6），实际要付的比 Kimi 那 1242 ms 少得多 | 与仓库既定工具链一致 | 结论六；仓库 `package.json` |
| B · Bun | 同为 JS，可 `--compile`；Claude Code 189 ms 单文件启动 | 引入第二运行时；Cordis 与 pi-ai fork 在 Bun 下要重验 | Bun 的 JSC 差异会变成自家的 bug（Claude Code 的 AVX/SIGILL 一族） | 结论六、七 |
| C · Rust（Codex 路线） | 12 ms 启动、24 MiB | 与 Cordis 无法同进程；等于重写 harness | 违反 SYS-KERNEL | 结论六；Codex 作者原话「不是因为 TUI 才选 Rust」 |
| 基线 · 不指定，各包自选 | — | 装配层无法保证同进程 | — | — |

**推荐 A**。B 保留为 D8 第二阶段的打包目标之一。**否决 C**：与硬约束直接冲突。

## D2 终端渲染层

**选择对象**：用什么把行画到终端上。
**必须保留**：渲染层不持有领域状态、退出还原终端、流式下键入不卡、中文输入法与宽字符可测、可提供线性输出。
**必须能被替换**：渲染层坐在自有适配边界后面，换库不动契约。

先摆事实基线（结论一、二）：**没有一家直接使用上游 TUI 框架的原样版本**；三家血缘指向 pi-tui；
Ink 的两家都把渲染后端换掉了；Pi 从零建了 18k 行；DSH 用 pi-tui 打 pnpm patch，后整包删 TUI。

| 候选 | 兑现必要性质 | 总负担 | 演化与维护 | 证据与缺口 |
|---|---|---|---|---|
| **A · pi-tui 钉版直接采用**（精确版本待钉；适配边界自有；**不 fork，不打渲染核心 patch**） | 组件只是 `render(width): string[]`，不持状态；三态差分 + CSI 2026 同步输出兑现流式下的输入响应；`Focusable` + 光标标记让 IME 候选窗跟光标；输入排空与还原序列兑现终端还原的可覆盖部分；配套虚拟终端直接给 D9 用 | 运行时依赖只有东亚宽度表与 markdown 解析两项；本项目界面小 | **上游节奏快、issue 有自动关闭门禁**（结论二）；升级只能整版 re-baseline；上游改约定要跟；**scrollback 墙是这条路线的结构性上限**（结论三） | [Pi 报告](../../../../research/agent-harness-cli-tui/reports/2026-09-21-pi.md) §1.2/§2.2/§2.5/§3.5；[Kimi 报告](../../../../research/agent-harness-cli-tui/reports/2026-09-21-kimi.md) §3.1；[DSH 报告](../../../../research/agent-harness-cli-tui/reports/2026-09-21-deepseek-harness.md) §3.3。**缺口：本机未装 Pi，零运行时取证** |
| B · Ink + React 19 | 声明式，模型最熟 | React 与 reconciler 整套；Yoga 布局；两家用户都换了渲染后端 | 上游 Ink 的增量渲染与性能埋点正是两家 fork 掉的地方 | [Claude Code 报告](../../../../research/agent-harness-cli-tui/reports/2026-09-21-claude-code.md) §1.3–1.5；[Cursor 报告](../../../../research/agent-harness-cli-tui/reports/2026-09-21-cursor.md) §1 |
| C · 自建最小渲染器 | 界面小，理论上几百行起步 | Pi 的账在案：按键解析 1.4k、宽字符 1.3k、编辑器 2.5k 行——中文场景都躲不掉 | 持续维护税（Pi 两份 CHANGELOG 合计 6,993 行） | 结论一；Pi 报告 §4.1 |
| D · fork pi-tui（Kimi 路线） | 同 A，外加可改核心 | 自家维护一份 18k 行的分叉 | Kimi 自己改渲染核心又 revert（0.80.6）；上游 bug 直接变自家的 | 结论二；Kimi 报告 §3.3、§4.3 |
| 基线 · 不做 TUI（DSH 路线） | 无渲染层 | 零 | 生态立刻补洞 | 结论十三 |

**推荐 A，附三条纪律：**

1. **适配边界是自有的**：渲染层只从交互层的一个内部端口被调用；契约面对它零感知。换成 B/C 只改这一个包。
2. **不打渲染核心 patch**。允许的只有包管理器 patch 级别的**非渲染**小改，且每条要有上游 issue 或 PR 引用。
   渲染核心的不满先开上游 issue，再在适配层绕，最后才谈 fork。
3. **升级只走整版 re-baseline**，以 D9 的黄金输出对比为门。

**否决 B**：内核是 Cordis 的组合模型，再叠 React 是两套生命周期；两家实证上游原样版本撑不住。
**否决 C**：中文是主要输入语言，输入侧那约 5,660 行是起步价不是可选项。
**否决 D**：fork 只在纪律 1–2 失守后才谈。

**两位独立评审在不读本页的前提下被迫四选一，都选 A，反证互不重复**——记录与改选触发见 [review.md](review.md)。

## D3 呈现路线

**选择对象**：界面占不占整个屏幕。**必须保留**：可提供线性输出；顺序与日志一致。

| 候选 | 兑现必要性质 | 总负担 | 演化与维护 | 证据与缺口 |
|---|---|---|---|---|
| **A · 只做内联** | 终端原生滚动与搜索白拿；线性输出天然对齐日志顺序 | 历史必须窗口化（Kimi 15 轮、Cursor 10 轮） | **结构性上限**：人往上滚时发生重排 → 整屏重绘并可能抹掉 scrollback | 结论三 |
| B · 只做全屏（alt-screen） | 无 scrollback 墙 | 自己实现滚动、搜索、鼠标 | 没有一家敢把默认切过去 | 结论三；Pi 报告作者原文 |
| C · 两套并存 | 各取所长 | 两套渲染器、两套语义 | 产品级投入 | Pi 报告 §2.1–2.3 |
| 基线 · 只打印不重绘 | — | — | 流式体验不可接受 | — |

**推荐 A**，窗口化的代价显式交给设计：界面只挂最近 N 轮，**被裁掉的不在界面里展开**，完整历史由日志命令给。
alt-screen 登记为 gap，改选条件见本页末 E2。

## D4 终端差异的承担方式

**选择对象**：终端能力与转义支持的差异由谁承担。**必须保留**：不静默降级；不可逆的外部输出不发生。

| 候选 | 兑现必要性质 | 总负担 | 演化与维护 | 证据与缺口 |
|---|---|---|---|---|
| A · 写死特判（Codex 路线） | 精确 | 独立探测组件、三套策略、终端复用器轮询线程 | 判据会漏且静默降级（Codex #42020） | 结论八 |
| **B · 环境白名单 + 转义协商 + 用户配置覆盖**（Pi/Kimi 路线） | 渲染层自带；键盘协议协商挂设备属性哨兵，不需要启动超时 | 一份终端配置文档 | 做不到的坦白写 | 结论八；Pi 报告 §2.5、§2.7 |
| C · 白名单 + 替用户改设置（Cursor 路线） | 体验最顺 | 调外部命令改终端偏好 | **改用户配置是外部输出，不可逆** | 结论八 |
| D · 模式栈 + 运行时探测（Claude Code 路线） | 最完整 | 有状态的 stdin 剥离器 | 探测预算与丢键二选一（Claude Code #45163） | 结论八 |

**推荐 B**；**否决 C 的每一步**（不可逆外部输出）；非 TTY 下界面模式拒绝启动并指向无界面模式。

## D5 无界面模式的输入与输出形态

**选择对象**：脚本怎么喂进来、怎么读回去。**必须保留**：与界面模式同一份投影、同一条受理；机器可读通道只承载契约内容。

| 候选 | 兑现必要性质 | 总负担 | 演化与维护 | 证据与缺口 |
|---|---|---|---|---|
| **A · 行分隔 JSON 事件流进出** | 一行一个事实，与日志条目一一对应；输入流可喂卡片答复与治理提交 | 要定契约 | 被脚本解析就是接口（DSH #20119 事故） | [本机实测](../../../../research/agent-harness-cli-tui/reports/2026-09-21-本机实测.md) §10.1(a)；Claude Code 报告 §2.5 |
| B · 只打印最终答案（DSH headless） | 最简单 | — | 无法用于端到端验证 | DSH 报告 §2.2 |
| C · `--json` + 输出 schema（Codex exec） | 结构化结果可校验 | 多一个机制 | 与 A 不互斥 | 本机实测 §10 |
| D · JSON-RPC 双向 | 最完整 | 等于第二个 UI 面 | DSH 把编辑器协议砍回自动化协议的教训 | DSH 报告 §3.2 |

**推荐 A，吸收 C 的「取最后一条消息」旗标**。stdout 纯净是纪律，靠接管不靠自觉（Pi 的 stdout 接管先例）。

## D6 进程模型

**选择对象**：用户本机上有哪几类进程、中心在哪。
**必须保留**：进程退出不丢东西；[单节点边界清晰](../../../foundation/cross-system-constraints/requirements.md#sys-deploy)；
[超长期待机](../../../foundation/long-running-and-evolving/requirements.md)；
空闲会话必须被拉起（PF-014）；通知必须存在（PF-008）；
会话内单活跃、尝试序号栅栏、取消跟着宿主走、强制停止三步闭环（PF-012）；
**已接受前提：会话、Run、工具执行在本机**（[D-022](../../decisions/cli-tui-delivery-form/README.md)）。

| 候选 | 兑现必要性质 | 总负担 | 演化与维护 | 证据与缺口 |
|---|---|---|---|---|
| A · 本机单进程（界面 + harness），中心只管身份 | 兑现不了待机与拉起空闲会话 | 最轻 | — | — |
| **B · 本机 daemon 内跑全部 agent runtime 协程 + 客户端；工具执行子进程按宿主分进程组** | 待机、拉起有宿主；runtime、模型传输、日志写者同进程，PF-012 的宿主关系不跨进程；进程组按 Run（前台）与按执行（后台）分 | 中 | 隔不住原生崩溃与内存无界增长——**但本项目零测量，且渲染层不在 daemon 里**；测出瓶颈后沿演化边切工作进程，契约不变 | [fable 评审](review.md) §2.8/§6；DSH 持久 bash 3.5 s 只说明子进程要分组 |
| C · 本机 daemon + 每个活跃会话一个工作进程 + 客户端 | 故障隔离最好 | 多一套运行时协议、拉起与回收策略、四份装配清单 | 前提「DSH `agent` 原语可跨进程」**未核**；运行时与宿主跨进程后强制停止、首 token 不重发要重新绑定 | 第一轮草案推荐它；fable 评审逐条否决其证据 |
| D · 每个 Run 一个工作进程 | 隔离最细 | 每句话付一次进程启动 | — | 结论六 |
| 基线 · 每次命令起一个进程 | — | 每次调用付整个启动成本 | — | 结论六 |

**推荐 B 作 v1，C 保留为演化边。**第一轮草案推荐 C；独立评审指出其否决 B 的证据**全是别家渲染层的缺陷**
（渲染层在客户端进程里，与 daemon 无关），且违反「没有可重复的瓶颈测量，不引入优化性复杂度」，本轮采纳。
**切换到 C 的条件是测出隔离或内存瓶颈，不是预感。**

## D7 CLI 命令体系形态

**选择对象**：动作怎么暴露给人和脚本。**必须保留**：脚本能做的人能做，人能做的脚本也能做。

| 候选 | 兑现必要性质 | 总负担 | 演化与维护 | 证据与缺口 |
|---|---|---|---|---|
| **A · 一等子命令**（会话族 + 治理族） | 与 PF-015 的会话对象、三份租户契约的操作一一对应；每个子命令有自己的帮助 | 子命令多；治理族没有先例可抄（六家的组织功能都不在 CLI 里） | 加动作不改顶层 | 本机实测 §10.1(b) |
| B · 标志位 | 简洁 | 顶层帮助膨胀（Claude Code 302 行） | 会话动作越多越挤 | 同上 |
| C · 顶层只有 REPL，一切走斜杠命令 | 界面里最顺 | 脚本不可达，直接违反必要性质 | — | — |

**推荐 A**，斜杠命令与子命令**共享同一份命令定义**。

## D8 分发形态

**选择对象**：同事怎么把 CLI 装到自己机器上。
**必须保留**：可安装、跨平台、可升级、客户端与节点版本可核对。

| 候选 | 兑现必要性质 | 总负担 | 演化与维护 | 证据与缺口 |
|---|---|---|---|---|
| **A · npm 包（含 `bin`），要求本机 Node 24** | 装得上、升得了；与 workspace 工具链一致 | 用户要装 Node；启动付 Node 冷启动，但客户端只装界面 | Claude Code 2.1.112 之前一直是这条路 | 结论七 |
| B · Node SEA 单文件 | 无需装 Node | Kimi 的账：未开 snapshot/code-cache 则 1242 ms 启动 + JS 明文；不支持 musl | 要自己维护三平台构建 | 结论六 |
| C · Bun `--compile` 单文件 | 189 ms 启动 | 第二运行时；AVX 硬门槛、glibc 2.26 下限 | 迁移一天切断生态 | 结论六、七 |
| D · 外挂完整 Node（Cursor 路线） | 无需编译 | 每次调用 801 ms；697 MB | — | 结论六 |

**推荐 A 作 v1，B 或 C 作第二阶段**，二选一时按结论六的同口径方法先测再选（E5）。
**分发的可移植性下限由最弱的随包文件决定**（Codex 随包 `zsh` 要 GLIBC_2.38）；随包工具进入分发前过同一道检查。
**Windows 的具体待遇登记为 gap**：三家的测试都不在 Windows 跑，v1 实为未承诺项。

## D9 测试驱动方式

**选择对象**：这个交付面怎么被自动验证。**必须保留**：界面与无界面跑同一场景得到相同的记录条目序列。

| 候选 | 兑现必要性质 | 总负担 | 演化与维护 | 证据与缺口 |
|---|---|---|---|---|
| **A · 虚拟终端断言 + 真 pty 冒烟 + 隔离节点多客户端** | 渲染断言落在真实终端解析结果上；多主体流程（邀请、隶属）要两个登录状态对一个中心 | 两个开发依赖 + 测试用中心节点 | Pi 与 DSH 都这么做 | Pi 报告 §3.5；DSH 报告 §1.4、§4.7 |
| B · 只做快照字符串对比 | 便宜 | 断言 ANSI 字节不是画面 | — | — |
| C · 终端复用器驱动 | 最接近真实 | CI 要装终端复用器 | 作为 A 的补充 | Pi 的交互测试流程 |

**推荐 A，C 作为手动验收流程**。

## D10 配置文件形态

**选择对象**：界面观感类配置放哪。**必须保留**：不参与作用域求值；丢了不影响领域行为。

| 候选 | 兑现必要性质 | 总负担 | 演化与维护 | 证据与缺口 |
|---|---|---|---|---|
| **A · 本机偏好单独一份、随机器走** | 丢了只影响观感（主题、键位、窗口轮数、粘贴阈值） | 一份文件 | Kimi 的 `tui.toml` / `config.toml` 分家先例 | Kimi 报告 §3.1 |
| B · 塞进设置资产走四层求值 | 统一 | 主题也要租户覆盖？语义不对 | — | — |
| C · 等同 PF-002 的个人 context | 看似现成 | **个人 context 由账号承载、跟着人走**；本机偏好随机器走，**不是同一物** | 第一轮草案的错，fable 评审纠正 | [统一语言](../../../ubiquitous_language/index.md) |
| D · 只用环境变量 | 零文件 | 不可发现 | — | — |

**推荐 A**，用[本机偏好](../../../ubiquitous_language/index.md)这个词条。个人 context 里的语言、时区仍从账号经中心取。
**不许进这份文件的**：任何改变 agent 行为的东西。

## D11 线上协议与认证

**选择对象**：daemon 与中心之间、客户端与 daemon 之间用什么协议、怎么认证。
**必须保留**：登录状态作凭据；显式版本协商（客户端与节点各自升级）；断线续读（投影事件带单调序号）；秘密值不上任何可见面。

| 候选 | 兑现必要性质 | 总负担 | 演化与维护 | 证据与缺口 |
|---|---|---|---|---|
| **A · v1 只用 HTTPS 请求/响应，JSON 体，bearer＝登录状态，版本头协商；推送留到出现具名需求** | 治理操作全是请求/响应；中心不知道任何会话、准入每道现读，v1 没有要订阅的东西 | 一种连接 | 出现「邀请到达要即时提醒」之类需求再加 WebSocket 或 SSE | fable 评审 §3.2 |
| B · HTTPS + WebSocket 订阅 | 请求与流式各走各的 | 两种连接；**说不出订阅什么** | Kimi 的客户端协议是 UI ↔ 内核，不是治理 | 第一轮草案 |
| C · gRPC | 强类型、流式内建 | protobuf 工具链；[SYS-SPEC](../../../foundation/cross-system-constraints/requirements.md#sys-spec) 要求 JSON Schema，两套 schema | — | — |
| 基线 · 明文 HTTP、无认证 | 不兑现任何必要性质 | 不可接受 | — | — |

**推荐 A**。**客户端 ↔ daemon 的本机 socket 也要认证**：每条连接出示登录状态凭据，
daemon **不从 OS 用户推断账号**（PF-001：同一操作系统用户不构成跨账号访问资格）；socket 文件权限只是第二道。
凭据存 OS 钥匙串优先。**TLS 证书怎么发、自托管中心的信任怎么建立，登记为 gap**。

| # | 做什么 | 改选条件 |
|---|---|---|
| **E1 输入侧** | Node 24 + 钉版 pi-tui 的约 50 行编辑器/焦点夹具，在终端复用器（开扩展按键）、VS Code 终端、一个现代终端三宿主下：拼音逐字输入 200 字；粘贴 5,000 字中英混合；开关硬件光标。量候选窗跟随、粘贴到首帧墙钟、渲染写出字节 | 候选窗错位或冻结 > 2 s，且最小复现只能改渲染核心才转绿 → A 的「不打渲染核心 patch」破产 → 改 D；若连 D 也要改同一处（0.80.6 证明会被回退）→ 改 C |

### 仍待区分、且不由实验决定的

以下不是技术未知，是**产品裁决**；在裁决前两种表述分别往下推，不自行选便宜的那个：

| # | 问题 | 两种产品长相 |
|---|---|---|
| Q-凭据 | **组织的 OpenRouter 凭据落在哪**：中心为每个租户签发独立可撤销的凭据、组织那把不出中心（本设计推荐，租户是 PF-013 认可的范围）；还是中心代发模型请求（改「中心只管治理」） | 「同事笔记本上只有自己租户那把」 vs 「笔记本上没有任何模型凭据、每次调用经中心」 |
| Q-常驻 | **daemon 是否常驻同事的笔记本**：常驻则待机、拉起空闲会话、通知都有宿主；不常驻则 PF-014 的队列要求与 PF-008 通知只在有客户端时兑现。[超长期待机要求](../../../foundation/long-running-and-evolving/requirements.md)明写不从候选实现推定常驻进程形式 | 「装了就有个后台进程」 vs 「开了终端才有」 |
| Q-通知 | 桌面通知（尽力而为）算不算 PF-008 要求的「通知必须存在」 | 算 vs 要另建通道 |
| Q-解除 | 成员被解除后，本机留存的会话日志与资产副本怎么办 | 本机自动清理 vs 保留但不可用 vs 产品另定 |
| Q-多账号 | 同一 OS 用户多账号：按「每条连接出示登录状态」隔离够不够，还是要按账号分 daemon | 够 vs 分 |
| Q-续会话 | 界面模式无会话参数时自动续上最近会话还是总是新建 | 「打开就接着聊」 vs 「打开就是新的一段」 |
| Q-离线 | 中心不可达时已开会话能否继续 | 「离线还能跟本机 agent 干活」 vs 「治理是硬前提，断了就停」 |
| Q-自托管 | 「本地个人自托管中心」是不是一种正式部署形态 | 起中心是产品功能 vs 只是研发夹具 |

回询的四段格式（当前结构与可计数代价 → 替代表述及其代价 → **两者在产品语言上的差别** → 建议与理由）
在实际发起回询时补；本页只登记问题与两种长相。
**Q-凭据与 Q-常驻直接改变 daemon 与中心的形状**，在裁决前不写模型传输的提供者设计。
