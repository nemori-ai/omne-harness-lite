# 候选与取舍

## 选择对象与必要约束

选择对象、三个 #8 单元（P-1 档案目录、P-2 模型请求运行时、P-3 模态转换）与必须保留的 M-1～M-26 见 [design.md](design.md#需要作出的选择)。
**不可调整**：M-1～M-26、D-019、D-022 ③④、D-035、D-058。**可调整**：能力边界与契约份数、插件与服务键、inject 方向、包布局与领域名。

候选按对账（`D-reconciliation-c.md` 表 D「D1 自证」）点名的比较项展开，每块另补对账里出现过、或本包检查时发现的真实路径。
每个候选写四样东西：

- **怎么承载**：M-n 由谁、在哪一处兑现。
- **失去保护点**：哪一条 M-n 在这个切法下没有了承载者，或者退成了「有前提地能」。
- **反查信号**（[能力覆盖与演化「反查边界是否合理」](../../../../agents/skills/harness-design-handbook/canonical/references/decompose.md#反查边界是否合理)）：跨 owner 同一提交、重复拥有同一事实、反复同步修改。这些是线索，不自动要求合并或拆分。
- **可计数代价**：新增的能力契约、须出新版的已接受契约、插件、服务键、inject 边、新增的跨进程协议项、重载链深度，以及每次调用多付的东西。

矩阵里的记法：**保**＝结构上兑现；**前提**＝有前提地能（前提写在正文）；**失**＝这个切法下没有保护点；**—**＝与本块无关。

## P-1 档案目录（中心）

### P1-A · 独立插件、独立能力契约 `capability.model-profile-directory` v2，放在中心；据点由同一服务面的读提供者 P-1r 供读

**怎么承载**
- M-1：中心单一存储上的唯一约束。判定与写入同一提交，唯一写入者是 P-1（[MP S-23](../../../spec/data/model-profile/v2/contract.md#s-23-跨部署形态会变的判定) 第 1 行「单一裁决点」）。
- M-2：只开一条「在册 → 已撤回」的写路径；官方清单在插件体里装入，是持久写、幂等、只增不删。
- M-3、M-5：凭据以范围身份为键，存在 P-1。「取值」这种问法只在发出那一刻，经据点读提供者交给传输适配；其余的面只答「有没有」。
- M-4：现读组织治理已接受的[成员资格判定](../../../spec/capabilities/organization-governance/v1/contract.md#s-26-成员资格判定)面。
- M-6：P-1 在中心，P-1r 在据点，带副本。
- M-7：`resolveCredential(scopeChain)` 取最具体的一把；链上不含个人范围，也不含别的租户。

**失去保护点**：结构上没有失去的。有两条退成「有前提地能」：
- M-4 的判定与写入不在同一个提交里。按 [PF-001 §6.6「撤销不等于强制停止」](../../../product/PF-001-identity-scope-and-agent-constraints/design.md#66-撤销不等于强制停止)的读法——撤权管的是下一道准入——现读就够了。资产治理候选契约消费同一个面时也是这样做的。
- M-1 在主线改判的「隶属树内唯一」读法下：判定域的一部分（哪几个组织在同一棵树里）是组织治理的事实。见下面的反查信号。

**反查信号**
- **跨 owner 同一提交：条件性地出现一处。**改判后的「隶属树内唯一」如果要求**隶属关系变化之后仍然成立**，就会出问题：
  两个组织各有一条同名自建档案，后来隶属进同一棵树，树里就有了两个同名。要守住它，「接受隶属」（组织治理的写）必须与「目录里的名字」落在同一个提交里。
  可两个写入者没有共同的存储对象，只剩两条路：要么让组织治理反过来读目录，依赖方向从「目录 → 治理」变成双向；要么改选 P1-B。
  **若只要求建档那一刻在树内唯一，这个信号不出现。**
- **重复拥有同一事实：无。**档案行与凭据只在 P-1；角色与成员资格只在组织治理；「用哪个模型」的取值与锁在资产那一侧。
- **反复同步修改：无。**PF-013 的档案规则变了，只动 `data.model-profile` 与 S16a，两者同一个 owner；组织治理不动。

**可计数代价**：
- 新增能力契约 1 份。
- 须出新版的已接受契约 1 份：入口组合 v2。所有「目录在中心」的候选都要付这一份。
- 插件：中心 1、据点 1（P-1r）。服务键：中心 1、据点 2。
- inject 边：P-1 出 2 条（存储、组织治理读面）；P-2 进 P-1r 2 条。
- 新增跨进程协议项 2 个：目录读的新鲜度上界；秘密怎样送到据点、轮换怎样传播。所有候选都有。
- 故障域：目录自成一个。官方清单装入失败，只让目录这一条 fiber `FAILED`。

### P1-B · 并进 `capability.organization-governance` v3：档案目录与凭据都归组织治理，由它的提供者插件多提供一两个服务面

**怎么承载**：
- M-3：字面归属最直接。凭据是「组织或租户身上的一项属性」，而组织与租户记录正是组织治理的事实。
- M-4：角色判定与目录写入在同一份存储里，能同一提交，比 A 严。
- M-1：若判定域是隶属树，树与名字归同一个 owner，接受隶属时可以在同一提交里查名字。
- 其余与 A 相同。

**失去保护点**
- **组织治理 v1 的边界。**它的 [S-2](../../../spec/capabilities/organization-governance/v1/contract.md#s-2-本契约不拥有什么) 明写不拥有「资产持有、属性配值、求值」；
  [PF-016 §5.6](../../../product/PF-016-cli-tui-delivery-surface/design.md#56-哪些东西在中心一侧哪些在据点一侧) 把档案与凭据跟设置、资产并列为「范围化对象」。
  并进来，组织治理就开始拥有一类范围化对象，与块 A 的资产治理分成了两个家。
- **提交域。**[S-17](../../../spec/capabilities/organization-governance/v1/contract.md#s-17-同一组织的成员写入序列化) 按组织序列化成员写入，而名字判定的提交边界横跨组织（全局，或整棵隶属树）。
  v2 要为此另开一个提交域，形式模型也要补——`Membership.tla` 只建模了成员写入。
- **故障隔离。**官方档案清单在插件体里装入。一份格式有误的发布清单让插件体抛出，整条 fiber `FAILED`，什么服务都不出现
  （[`plugin-throw-fails-fiber`](../../../basis/cordis/plugin-throw-fails-fiber.md)）。
  在 B 下，这意味着成员资格判定、我的租户、切换当前租户身份一起消失：用户登录进来，什么治理动作都做不了。
  把装入挪出插件体、改成装配期迁移，能减弱这条反例；但「目录的一次缺陷换代，连带整个治理面重载」仍然存在——消费治理面的插件会跟着重跑
  （[`plugin-body-reruns-on-provider-change`](../../../basis/cordis/plugin-body-reruns-on-provider-change.md)）。

**反查信号**
- **反复同步修改（主要的一个）。**PF-013 每改一次档案规则，组织治理就要出一个新版，尽管租户规则一条都没变。
  眼下排着队的就有三条：撞名判定域的改判、U-2 撤回之后能否恢复、同名再上架（MP G-6）。
- 跨 owner 同一提交：消失。这是 B 唯一的结构性收益。
- 重复拥有同一事实：无。

**可计数代价**：
- 新增能力契约 0 份。
- 须出新版的已接受契约 2 份：组织治理 v2、入口组合 v2。组织治理 v2 还要连带付：一份新决定；资源重新冻结（v1 包冻了 6 项资源）；
  v1 的消费者不会自动升级——账号注册组合、入口组合、资产治理候选各自决定何时升；已实现的提供者节点要重开。
- 插件：中心 0（组织治理插件的服务面从 4 个变成 5～6 个），据点 1。
- 故障域：目录与治理合成一个。

### P1-B′ · B 的收窄：只把凭据的配与取并进组织治理 v2，档案目录仍然独立（即 A 减去凭据）

**怎么承载**：M-3 在组织治理；M-1、M-2 在 P-1，与 A 相同。

**失去保护点**：
- **M-4 被拆到两个 owner。**[flows §4](../../../product/PF-013-model-profiles-and-invocation/flows.md#四角色与操作) 里「建一条自建档案」与「配这个范围的凭据」是同一批角色、同一条授权线；B′ 让两份契约各写这张角色矩阵的一格。
- **M-7 退成有前提。**P-2 的「有没有凭据」与「取值」来自组织治理，档案来自目录，据点读提供者要对着两份契约各做一份副本。

**反查信号**：
- 重复拥有同一事实：「谁能碰这个范围的模型配置」这张矩阵在两处写。
- 反复同步修改：flows §4 那几行改一次，两份契约一起动。

**可计数代价**：
- 新增能力契约 1 份（不含凭据的 S16a）。
- 须出新版的已接受契约 2 份（组织治理 v2、入口组合 v2）。
- 与 A 相比：多出一份已接受契约的新版，插件一个不少。

### P1-C · 并进运行时：档案目录、凭据与调用由一份 `capability.model-request-runtime` 拥有（原 S16 简报的切法）

它有三种落法：

| 落法 | 结果 |
|---|---|
| **C1** 一份契约、一个插件，放在据点 | **M-6 失**：甲在组织层配的东西乙看不到（PF-016 §5.6）。**M-1 失**：每个据点各一份存储，没有单一裁决点——MP S-23 第 1 行明写「按组织或租户分片各自判重也不成立」 |
| **C2** 一份契约、一个插件，放在中心 | **M-25 失**：会话与 Run 在本机（D-022 ③），而「模型请求经中心出去」已被 [PF-016 §7](../../../product/PF-016-cli-tui-delivery-surface/design.md#七取舍) 否决。**M-13 失**：宿主 agent runtime 在据点 |
| **C3** 一份契约、两个插件：中心拥有写面，据点拥有调用 | 性质都能在契约层写出来，见下 |

C3 展开：

- **失去保护点**：没有哪条性质失去保护点。失去的是**版本边界**——中心侧的管理写面与据点侧的调用共用同一个契约版本号。
- **反查信号：反复同步修改（最强的一个）。**PF-013 改撞名规则，整份运行时契约就要升版，据点侧的消费者（agent loop、拓展件）被迫面对一次与它们无关的版本；
  反过来，改首 token 或重试规则，中心侧的管理面也跟着升。两组消费者（管理面、agent loop）互不相交。
- **可计数代价**：
  - 能力契约少 1 份（S16a 并进 S16b）。代价是这一份的「装配给 vs 协议给」表，要连契约内部的跨进程边一起列进去。
  - 插件 2 个，与 A 相同。
  - 中心与据点两个应用的发版被一份契约绑在一起。

**检查过、但不列为候选的路径**：
- **并进资产治理**：档案不是资产（[PF-002 decisions「模型档案在五类里的位置」](../../../product/PF-002-assets-settings-and-permissions/decisions.md)），资产治理那套持有、分享、版本选用对档案都不适用。
- **中心与据点各一份目录**：就是 C1 的变体。

### P-1 性质矩阵

| | A | B | B′ | C3 |
|---|---|---|---|---|
| M-1 路由名唯一 | 保（全局读法）；前提（隶属树读法，且须跨隶属变化成立） | 保 | 同 A | 保 |
| M-2 撤回不删行 | 保 | 保 | 保 | 保 |
| M-3 凭据是范围的属性 | 保 | 保（字面最直） | 保 | 保 |
| M-4 授权 | 前提（现读） | 保（可同一提交） | 前提，且一张矩阵分两处写 | 前提（现读） |
| M-5 凭据值不外泄 | 保 | 保 | 保 | 保 |
| M-6 中心一侧、据点有副本 | 保 | 保 | 保 | 保（C1 失） |
| M-7 最具体的一把 | 保 | 保 | 前提（两个来源的副本） | 保 |
| M-25 会话在据点 | 保 | 保 | 保 | 保（C2 失） |
| 故障域 | 目录自成一个 | 与治理合一 | 凭据与治理合一 | 一份契约、两个插件 |

### P-1 推荐与改票条件

**推荐 P1-A。**

- B 唯一的结构性收益——授权与写入同一提交、隶属树与名字同一个 owner——在现行读法下并不需要：PF-001 §6.6 下现读就够；隶属树内唯一可以读成建档时的检查。
  换来的代价却是：多一份已接受契约的新版；目录与身份、治理合成一个故障域；PF-013 每改一次都要为组织治理发版。
- B′ 把同一条授权线拆到了两个 owner。
- C3 把两个应用的发版绑在一份契约上。
- C1、C2 被产品正文排除。

**改票条件**：

- **→ B**，满足任一条：
  - 裁定「隶属树内唯一」必须在隶属关系变化之后仍然成立（不只是建档那一刻），而且不接受「组织治理反过来读目录」这条依赖；
  - 产品要求撤权与写入同一提交——例如「超管资格一失去，他已经发出、尚未提交的建档就必须失败」，而在组织治理之外找不到两者共同的存储对象。
- **→ B′**：「范围上的秘密属性」出现第二个消费者。例如 U-1 判乙之后，MCP 凭据也改为挂在范围上、走同一套配与取。
  那时凭据值得一个与档案无关的家：组织治理 v2，或一份独立的范围秘密能力。
  现状下它只有一个消费者——[MCP 凭据](../../../ubiquitous_language/terms/capabilities-and-composition.md#ul-mcp-credential--mcp-凭据--mcp-credential)是资产持有上的设置，不是范围的属性。
- **→ C3**：中心侧目录不再有独立的消费者。例如产品取消自建档案，只剩随发布的官方清单；目录就退化成运行时读的一份发布数据，落点变成 #1。

## P-2 模型请求运行时（据点）

### P2-A · 选择与调用放在同一份能力、同一个插件里；一次调用是宿主上的 effect；传输适配是内部依赖

**怎么承载**：
- M-9：合法目标与出门前检查读同一批输入，在同一个进程里现算。
- M-11：三类事实与首 token 是发出守卫，不在任何挂件里（N-7）。
- M-12：两类锚点的写入时序由 P-2 兑现。
- M-13、M-16：调用的 effect 挂在宿主上。
- M-14：传输适配的九条义务。
- M-15：默认重试件是一个零依赖的小插件，与 P-2 互不 inject。
- M-17：凭据每次发出时现取。
- M-18：`openCall` 绑定档案快照。
- M-10：投影缓存只有一个写入者。

**失去保护点**：结构上没有。M-9 的新鲜度与 M-12 的锚点属于「有前提地能」，这两个前提所有候选都有。

**反查信号**：无。切换事实、锚点、失败发出的响应体都只由 P-2 写；回复消息与它的响应体同一提交，那是 loop 的追加口（块 D），换哪个候选都一样。

**可计数代价**：
- 契约 1 份（S16b），插件 1 个，服务键 1 个。
- inject 边：出 3 条（读提供者的两个服务、作用域求值），进 1 条（agent runtime）。重载链 2 层。
- 每次调用：1 个 effect，外加 1 条在途表项。
- 代价是 P-2 更大（N-4 自己也承认）。

### P2-B · 选择独立成一份能力 `capability.model-selection`（合法目标集合、展示列表、切换、选中与有效模型、模态投影缓存），调用运行时 inject 它

**怎么承载**：每条性质都写得出来，但有三处变成「有前提地能」：
- **M-9 出门前核对有效模型，变成了跨能力的一问。**运行时在出门前向选择能力现问一次。同进程无碍；拆开部署后，这就是一条协议。
- **M-18 两边读的必须是同一份档案。**选择能力判合法时读到的档案，与运行时绑定的快照必须一致，否则判的是旧属性、发的是新属性。
  解决办法是让选择能力把（引用, 档案快照）成对交给运行时（[MP S-1](../../../spec/data/model-profile/v2/contract.md#s-1-档案的身份所在范围与路由名)「档案与引用成对交出」），接口因此变宽。
- **传输能承载的模态放在哪。**若 D 对账「需主线看」第 5 项被采纳，合法目标会多一个输入：「本据点的传输能承载的模态」。
  这个事实在运行时的传输适配里，选择能力要么反过来读运行时（与运行时读选择能力成环），要么在装配配置里再声明一份。

**失去保护点**：没有哪条直接失去。

**反查信号**
- **反复同步修改（主要的一个）。**[PF-013 §5.9](../../../product/PF-013-model-profiles-and-invocation/design.md#59-换模型一条事实一个生效点零个新分支)～§5.11 与 §6.5～§6.10 都是「这次能不能发」的规则。
  主线裁定 C-10 一条，就同时改了有效模型的求值（选择一侧）与出门前检查（运行时一侧）。
- **重复拥有同一事实（条件性）**：上面那条「传输能承载的模态」。
- 跨 owner 同一提交：无（切换不需要同一提交，见设计正文「存储、写入者与提交点」）。

**可计数代价**：
- 契约 2 份，插件 2 个，服务键 2 个。
- inject 边合计 7 条，A 只有 4 条：选择出 2 条（读提供者、作用域求值），运行时出 3 条（选择、读提供者、凭据），agent runtime 进 2 条。
- 重载链 3 层：读提供者 → 选择 → 运行时 → agent runtime。

**谁会受益**：一个只要「选择」、不要「调用」的消费者。**现在没有这样的消费者**：
- 交付面的模型列表与切换命令都进据点、经 P-2 的服务面拿；
- 治理中心不知道任何会话（M-25）；
- 将来经 hook 实现的 model selector（D-058 8c）是一件拓展件，跑在 agent runtime 里，本来就够得着 P-2。

**变体 B-2：只把模态投影拆成服务，或挂在「消息落盘之后」维护**。反例同 N-3：唯一的消费者是合法目标；挂在拓展点上，一旦被视作卸载就会静默落后。
计数：多 1 个服务、多 1 条 inject 边，收益为零。

### P2-C · 调用做成 fiber：每次模型调用是一条子 fiber（C1 挂在 agent runtime 下；C2 挂在 P-2 下）

**怎么承载**：M-13 在 C1 下成立（父 fiber 卸载时带走子 fiber）；C2 要另接一条宿主上的 effect 去撤子 fiber。

**失去保护点**
- **M-11、M-12 从「结构上不会自动重发」退成「有前提」。**调用 fiber 只要 inject 了任何会换代的服务，提供者一换代，内核就先卸载、再**重跑插件体**——
  而插件体就是这次调用，重跑就是再发一次（[`plugin-body-reruns-on-provider-change`](../../../basis/cordis/plugin-body-reruns-on-provider-change.md)「已知的误用：给长时操作加 inject」）。
  开过口的调用会被自动再发，只能靠每次重跑先读锚点、自己拦下。
  在 A 下，换代只触发撤除与结算；要不要再发，由下一次尝试读完日志再决定。
- **「一次调用最终落到终态」，以及错误尽早暴露。**依赖不齐时 fiber 停在 `PENDING`，插件体不跑（[`inject-has-no-optional-form`](../../../basis/cordis/inject-has-no-optional-form.md)）。
  这次调用既不失败、也不开始，loop 停在「等模型」上，没有人来收场。在 A 下，P-2 不在时 `openCall` 直接失败（`runtimeStopped`）。
- **失败是一个值，不是插件失败。**上游 503 要交给「调模型之后·失败」；而插件体抛出只会得到 `FAILED`、什么都不提供（[`plugin-throw-fails-fiber`](../../../basis/cordis/plugin-throw-fails-fiber.md)）。
  调用体因此必须接住一切，再另找一条通道把结果交出去。

**反查信号**：重复拥有同一事实（机制层）。一次调用同时有两套状态：它自己的领域状态机（待发出、在途、说话中、三个终态）和 fiber 的六态，说的是同一件事。
调用的身份仍然要落日志——`Fiber.uid` 只是本次 registry 里的实例身份（design H-7）。

**可计数代价**：
- 契约 0 份。
- 每次调用多一条 fiber（并行判定时，N 次调用就是 N 条），多一次 inject 解析和一套六态。
- 多一条结果回传通道。

### P2-D · 传输适配做成独立的插件与服务 `modelTransport`，运行时 inject 它

**怎么承载**：**M-14 退成有前提。**单家发出、无隐藏重试、首 token 可观察、费用来源，都变成了「绑在这个服务键上的那个提供者」的性质。
换上一个内部带重试的传输提供者，M-14 就被静默违反。要堵住它，要么再立一份传输契约去约束提供者，要么在运行时契约里约束它的依赖。

**失去保护点**：没有哪条直接失去，但故障半径变大：
- 换传输 → 运行时重载 → 全部 agent runtime 重载。在途调用里，没开口的在新尝试里再发，开过口的记「说到一半断了」——为一次传输替换，付出一次全据点的调用中断。
- 改用 `ctx.get` 可以避开重载，可运行时就得在每次发出时处理「传输不在」。这不属于八个成因里任何一个上游类，只能归「没认出来」。

**反查信号**：单一消费者的服务（N-2）。#8 要求「独立变化原因且独立消费者」，它只有前一半。

**可计数代价**：
- 插件、服务键、inject 边各多 1（或者每次发出多一条缺席路径）。
- 重载链多一层。
- 若再为它立契约，再多 1 份。

### P-2 推荐与改票条件

**推荐 P2-A。**
- B 所有「能」都要多付一条跨能力接口，还会出现「反复同步修改」这个信号，而眼下没有任何消费者能从拆分里受益。
- C 让「开过口的不再发」从结构保证退成每次重跑都要守的纪律，还带进 `PENDING` 悬住的风险。
- D 为一个只有一个消费者的东西开服务，并把 M-14 变成绑在服务键上的提供者的性质。

**改票条件**：

- **→ B**，满足任一条：
  - 出现一个只要「选择」、不要「调用」的消费者，而且它经 P-2 的服务面拿不到——例如交付面必须在据点之外的另一个进程里，在运行时不在的时候也列得出展示列表；
  - 治理中心有了读会话的面（要先改 UL-governance-center「它不知道任何会话」）；
  - S16b 的修订历史显示，选择规则与发出规则各自独立变化：连续多次修订，都只动其中一侧。
- **→ C**：一次调用需要自己的依赖集，或按调用注入的配置（例如同一会话里不同调用走不同的传输或凭据提供者实现）；
  或者 H-1 不成立，而在宿主下开子作用域的代价比一条 fiber 还高。无论哪种，都**必须同时拿出「重跑即再发」的守卫方案**。
- **→ D**：传输出现第二个消费者（一条不经 P-2 的发出通道）；或必须在不重启 P-2 的前提下热换传输。

## P-3 模态转换（据点）

### P3-A · 独立登记表插件：S17（`capability.modality-projection` v2，已收窄为「投影判定函数＋转换件登记与挂件」）由 P-3 兑现；每个键上的转换件是 P-3 之下的子插件 P-4\*

**怎么承载**：
- M-19：登记表是「键 → 实现」；同键重复登记在装配时失败（`keyTaken`）。
- M-21：分派者看得见全部的键，媒体类型键优先。
- **M-20**：**声明了哪些键，来自 P-3 的装配配置；活着的实现，来自 P-4\* 的登记 effect。**
  声明了却没有活的实现，就是不可用，也就是转换失败、否决；没声明的键，块照原样落盘。两种情形分得开。
- M-22：P-3 不 inject P-2，也不需要宿主。
- M-23：输出约束写在 S17 的 `convert` 条款里。
- M-24：在 runner 眼里，P-3 只是站在「消息落盘之前」的一件普通拓展件；键表是它内部的事，外来的拓展件照样可以这么写。

**失去保护点**：结构上没有。有一条前提：P-3 整件不在时，由 runner 的 fail-closed 行兜住（C-7），这时 runner 要能判断哪些消息需要转换（含非文本模态块或文件块的消息）。这一点 S15 须写明。

**反查信号**：无。P-3 与 P-2 唯一的接点是日志里块上的 transcript——P-3 写，P-2 的投影读——两者之间没有 inject 边。

**可计数代价**：
- 契约 1 份（S17，已收窄）。
- 插件 1 + k 个（k = 装配里的转换件数）。服务键 1 个。
- inject 边：P-3 → runner 挂载接口 1 条；P-4\* → P-3 共 k 条。
- 动态性代价：k 条 fiber，这是为失败隔离付的价（Y-3）。

### P3-B · 并进 runner：在 `capability.loop-extension-runner` 的「系统自带件」一节里加一张转换件子表，转换件向 runner 登记

**怎么承载**：runner 本来就认识系统自带的五件和它们的 fail-closed 行（C-7），加一张子表，就能守住 M-19～M-21。

**失去保护点**：**M-24。**runner 要为一件系统自带件内置三条语义：按键分派、键的优先次序、「声明了就必须在场」。
外来的拓展件拿不到同样的机制——[PF-012 §5.8](../../../product/PF-012-agent-loop-and-run/design.md#系统自带的几件各站在哪) 说得很清楚：「若系统自带的能做外来挂件做不到的事，那说明位置的能力没被定清楚」。
C-7 已经让 runner 为五件各留一行不可用时的处置，B 又在那之上加了一层特殊处理。

**反查信号**：**反复同步修改。**PF-013 转换件契约的任何变化（新的键规则、新的输出约束）都要为 runner 契约发版，而 runner 的 owner 与变化原因在 PF-012。
另外，故障域变大：runner 那条 fiber 出事，十一个位置全部「此刻不在」。

**可计数代价**：
- 契约 0 份，但 S15 多一节、多一张子表。
- 插件 k 个；runner 多一个服务面。
- runner 的故障域扩到了转换。

### P3-C · 并进运行时：P-2 拥有转换件登记与模态转换挂件

**怎么承载**：模态投影的缓存与转换放在同一个插件里。

**失去保护点**：**M-22 退成有前提。**转换跑在「消息落盘之前」，输入消息落盘时可以没有 agent runtime。
P-2 不需要宿主也能做转换，但它的三条 inject（读提供者、凭据、作用域求值）就成了「接受一张图」的前置条件：
任何一条换代，P-2 重载，登记表跟着没了，正在进行的转换被中止，那几条消息按 C-7 被否决。
用户发一张图能不能进会话，从此取决于模型目录与凭据的提供者此刻在不在——两件毫不相干的事被接在了一起。

**反查信号**：变化原因不重合（新媒体类型 vs 发出失败模型），消费者也不相交（runner 与转换件 vs agent loop）——即 Y-2。

**可计数代价**：
- 契约 0 份，但 S16b 多一节。
- 插件 k 个。
- 输入消息落盘多出 3 条 inject 前置。

### P3-D · 每个转换件是一件独立的系统自带拓展件（按键过滤），不设登记表

**怎么承载**：与 [UL-modality-converter](../../../ubiquitous_language/terms/capabilities-and-composition.md#ul-modality-converter--模态转换件--modality-converter) 的字面读法最贴（「挂在消息落盘之前的一件拓展件」），也直接复用 runner 现成的逐件顺序求值。

**失去保护点**
- **M-19：同键一件，没有人守。**只能交给装配清单的检查器，而装配清单本来不理解「键」。
- **M-21：键的优先次序没人管。**一个文件块同时命中两个键，逐件求值时两件都跑，改写按顺序叠加（S15 简报「rewrite 顺序叠加」），
  结果是两份派生表示、两段 transcript。要避免，后一件就得知道前一件的键——拓展件之间互相耦合。
- **M-20：不可用被当成没装。**转换件不可用会被视作卸载，那个键此刻就没人管，块于是照原样落盘、没有 transcript，投影永久多出一种模态。
  这正是 C-7 要堵的那条路。runner 要分清「没装」与「装了但不在」，就得持有一张声明的键表——那就是 B。

**反查信号**：重复拥有同一事实。[`data.loop-extension` 系统自带件表](../../../spec/data/loop-extension/v2/contract.md#消费者)里「模态转换」这一行要改成 k 行，每行各自声明自己的键，键表散落在 k 份声明里。

**可计数代价**：
- 契约 0 份，登记表插件 0 个，插件 k 个。
- 三条性质失去保护点。

|---|---|---|---|---|

| M-20 不可用即否决，没登记才原样落盘 | 保（声明与在场分开） | 保 | 保 | **失** |
| M-21 媒体类型键优先 | 保 | 保 | 保 | **失** |

### P-3 推荐与改票条件

**推荐 P3-A。**
- B 让 runner 为一件系统自带件长出外来件拿不到的机制，与 M-24 相冲。
- C 把「接受一张图」接到了模型目录与凭据的可用性上。
- D 让三条性质失去保护点。
- A 的代价是一份契约和 k 条 fiber，都已标价。

**改票条件**：

- **→ B 或 D**：`data.loop-extension` 给**所有**拓展件一种通用的「按键独占」声明——同键一件、声明了却不在即否决、键的优先次序——由 runner 按它派发。
  那时转换件只是这个通用机制的一个使用者，不享受特权，P-3 就可以消解；D 是那时最自然的形态。
- **→ C**：P-2 不再有外部依赖（目录与凭据变成本地数据，不经 inject）；或者转换件必须知道有效模型——产品正文明文说它不该知道，须先改 PF-013。
- **→ 不再每键一条 fiber**：所有转换件都是没有外部资源的纯函数，而且能接受「一个键出错，连带同一插件里的其他键」（Y-3 的改判条件）。
