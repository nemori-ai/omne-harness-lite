# 候选与取舍

## 选择对象与必要约束

选择对象与五条必须保留的性质见[设计正文](design.md#固定图与拥有者)：结论不变、缺陷暴露为缺陷、不发布半套图、导入后改 JSON 不串版、作者 Schema 不进模块级缓存。
负责人的方向是硬约束：按需、编译后缓存、**Schema 没变时重新导入（新测试文件、新进程）不再编译**、有成熟库或优化就用。

数字出自[研究](../../../../research/fixed-schema-compile-cost/research.md)，测量期间机器负载 6.7～16；同一轮里交替测量，不同轮之间只比比例，哪些是主线复跑、哪些只有转述以研究为准。

| 候选 | 如何兑现必要性质 | 差异、总负担与关键反例 | 证据 |
|---|---|---|---|
| **A 现状：加载时编译全部固定定义** | 导入即编，失败即抛；结论是基准 | messages 导入 621～1053 ms（三轮），每个测试文件、每次 CLI 启动都重付；同进程再建一次运行时又付约 430 ms（实例间不复用）；Node 编译缓存对 `new Function` 无效（复跑 621→674，噪声内） | 研究：现状拆分、compile cache |
| **B 只按需编译＋进程内缓存**（pi 1.0 的做法：首次校验才 `Compile`，WeakMap 按 Schema 对象缓存） | 首用才编，进程内复用；结论不变；缺陷推迟到首用才暴露 | 从不校验的导入路径变快；但**满足不了「重新导入不再编译」**——每个新测试文件、新进程都重编；按需只编一个定义也省不到一半（ToolDefinition 的引用闭包覆盖大部分定义，CPU 469→267 ms，复跑）；Ajv 自身 JIT 预热占冷启动约 2/3 | 研究：按需编译、同行 pi |
| **C 构建期生成 standalone 校验模块，运行时用到才加载**（本设计） | 生成失败即构建失败，整份产出；绑定构建时字节；运行时不编译固定图；作者 Schema 仍运行时、归持有者 | messages 导入 35～40 ms（再加 Node 编译缓存约 12 ms），元校验器 79→5 ms；messages 对拍 58 万多对零差异（主线复跑），tool-definition 与元校验器的零差异只有转述；代价：exact 关键字改 `code` 型、生成产物每包 0.3～1 MB、与 Ajv 版本耦合（升级要重生成）、测试运行器不得转换生成模块、多一个构建步骤 | 研究：standalone 支持、对拍、导入矩阵、vitest 探针 |
| **D 换库**（TypeBox 1.x、@exodus/schemasafe、@cfworker/json-schema、@hyperjump/json-schema） | 取决于库 | TypeBox 1.x 与 schemasafe 编译更快或同量级，但**表达不了 exact 关键字**（前者的 `~refine` 拿不到根与路径，后者只支持自定义 format）；TypeBox 把资源嵌进 `$defs` 时有 12 对栈溢出；cfworker、hyperjump 是解释型，一万次校验慢 10～20 倍；@sinclair/typebox 0.34 不能处理普通 JSON Schema | 研究：替代库表 |
| **E 运行时按内容哈希写盘缓存**（未命中现场生成 standalone 代码写缓存目录，命中直接加载） | 结论同 C；首次未命中时付编译 | 不需要构建步骤；但命中仍 65～89 ms（其中哈希 30～50 ms，原型的单次转述），未命中 1.27 s；**运行时写盘**：缓存目录的所有权、并发写、被当作库使用时往用户目录写文件，都要另外定；没有成熟的通用实现（Fastify 的 `StandaloneValidator` 只给存取钩子） | 研究：哈希缓存原型、现成工具 |

Ajv 选项级优化（`code.optimize:false`＋`validateSchema:false`）最多省 58%，全开仍比 C 慢 15～20 倍，只作对照，不单列候选。

## 推荐与仍待区分的事项

**推荐 C**，作者 Schema 部分用 B 的做法（首用才建、归持有者）。

- 只有 C 同时满足负责人的三条：按需（用到才加载）、编译后复用、Schema 没变时重新导入不再编译——编译只发生在构建里，构建产物不变就不重做。
- C 不换校验引擎：生成的仍是 Ajv 的代码，语义差异只可能出在我们自己的关键字适配层，由每包的等价测试兜住。
- C 把「缺陷暴露为缺陷、不发布半套图」从导入时挪到构建时，性质更强而不是更弱；原设计里「加载时编译」这句话被取代，它要保护的性质都保留。
- B 是不能做 C 的地方的退路（作者 Schema、asset-model 的端口组合图）；E 留作以后若有「大量运行时生成的 Schema」再议；
  D 里 TypeBox 1.x、schemasafe、cfworker 被 exact 语义排除，hyperjump 据转述能表达 exact 语义，被排除是因为它不降导入成本、每次校验慢一个数量级。

仍待区分的（施工中实测，不改变选择）：其余约二十个包能否都顺利生成（loop-extension 的两个运行时尚未生成过）；
全部生成产物的总体积——被多包引用的公共资源（content-blocks、call-accounts 等）按包生成时进入每个包的产物，是体积的乘数；整张导入图的收益；测试运行器下 Node 编译缓存是否有收益。
若整图读数显示生成模块的累计解析成本吞掉大部分收益，或等价测试在其余包上出现不一致，退回 B＋Node 编译缓存重新比较。
