# 候选与取舍

编号（INV-／SAF-／LIV-／P-）沿 [design.md](design.md#本选择要承载的性质)，只在本包内有效。
「入口层」「运维面」「登录状态的出示物」「登录状态列表句柄」尚无词条（见 design.md 抬头）。

## 选择对象与必要约束

选择对象见 [design.md「需要作出的选择」](design.md#需要作出的选择)：**入口层（无词条）与运维面（无词条）在 Cordis 装配里落在哪、由谁拥有。**
必须保留：design.md 的[性质表](design.md#本选择要承载的性质)；五份已接受契约 v1 的公开面；Cordis 4.0.4 的内核语义。
可调整：代码落在 `packages/` 还是 `apps/`、几条 fiber、运维面在不在进程内、中心标识由谁铸造。

两个轴的组合方式：入口层在 A、B、C 中取一个，运维面在「A 的运维面」与 D 中取一个。
B 自带运维面的一种放法（放进装配）；**C 既不决定运维面，也不给中心标识找持有者**，它必须向别处借。

| 可识别候选及范围 | 如何兑现必要性质 | 差异、总负担及关键反例 | 当前证据与缺口 |
|---|---|---|---|
| **A** 入口层是一条独立、**不 provide** 的 fiber，落 `packages/tenancy/governance-center-entry/`；运维面是同包内另一条 fiber，走只在本机可达的通道 | 一个监听、一条判定次序、一张封闭路由表；inject 全部所需服务并排在清单最后；插件体首启铸造中心标识；运维面只 inject `storage`、`clock` | 新增一包、两插件、一份组合契约，不改任何 v1 契约。**关键反例**：中心标识由一个投影层铸造，出现第二个入口时同一条部署事实就有两个铸造者 | 主线裁定方向。basis 四条 probe 通过；P-5、P-6、P-8 待升格；无运行 |
| **B** 入口层并入 `apps/tenancy-host`，作为装配的一节 | 同样的判定次序写在装配代码里；`boot()` 等六条 fiber 都可用后铸标识、开监听；运维面也在装配里 | 少一个包，部署层事实集中在一个节点。**关键反例**：装配节点要兑现一份组合契约的语义；协议测试离不开生产装配 | tenancy-host 节点现写「入口层身份核实——不写」；无运行 |
| **C** 拆成三扇门，各归 account-identity／organization-governance／account-registration 插件 | 每个领域插件登记自己那部分路由，各自先核版本再认人（OG 的门调 AI S-17） | 每份契约的线上投影随自己演进。**关键反例**：运行中一个 owner 重跑只关它自己那扇门——「能登录却答不出成员资格」；OG S-42 末段与之直接相反，要三份 v2 | 无运行；OG S-42 末段是现成反证 |
| **D**（运维面的替代）进程内不设运维面；运行中的中心写一条状态记录，本机命令在进程外读它、自己探存储、自己看时钟 | 运行时只有一个监听；命令入口可用包级规则守「不导入任何 `tenancy/*` 包」 | 零进程内运维通道。**关键反例**：完整体检变成命令此刻看到的，不再是中心看到的 | 无运行 |

## 性质承载矩阵：入口层轴

「能」＝有结构上的保护点；「有前提地能」＝保护点成立要一个写明的前提；「弱」＝保护点降格为多处约定或跨包测试；「失」＝在该候选里找不到保护点。

| 性质 | A | B | C |
|---|---|---|---|
| INV-1 两张面，没有第三张 | 有前提地能：唯一网络监听属于入口层包；「`tenancy/*` 不引入监听模块（入口层包除外）」规则落地 | 有前提地能：监听在 `apps/tenancy-host`，同一条规则对 `packages/` 照样成立 | **失**：每个领域包都要能开面，「不引入监听」无法成立；共享路由形态下任何 inject 路由服务的插件都能多开一张面——第三张面只差一次 inject |
| INV-2 中心标识 | 能：入口层插件体首启铸造，表与治理事实同一存储 | 能，但由装配节点持有一条产品事实 | **失**：三个 owner 都不拥有它，要第四个持有者 |
| INV-3 没有会话、不推送 | 能：路由表里没有 | 能：同左 | 能：三张路由表各自没有 |
| INV-4 只量中心的钟 | 能：信封不含时间（契约条款） | 同 | 同 |
| INV-5 完整体检是中心的自述 | 能：运维面在中心进程内现读 | 能：运维代码在同一进程 | 不决定（C 不含运维面） |

| SAF-2 认人只有一条路 | 能：唯一的判定次序；分派只收「已核实的调用方」；一张表可被一个测试遍历 | 能，但遍历测试要起生产装配 | **失**：三条同形的路，没有一张可被一个测试遍历的表；「只有一条路」降格为跨包约定 |

| SAF-6 身份只从认人推出 | 能 | 能 | 能：各 owner 自推导 |

| SAF-8 体检不越界、秘密不进输出 | 能：一份契约 Schema 枚举全部输出 | 能 | **弱**：三份输出各自枚举 |
| SAF-9 不半开 | 有前提地能（P-5、P-6）：inject 全部所需服务、排最后；运行中任一被消费服务换代或不可用，入口层卸载重跑，门随之关上 | 启动：能。运行中：**弱**——开监听的若是非插件代码、调用时解析服务，某个领域服务缺席时门照样开着（本版无热替换，这个差别在出现运行期换代之前是潜在的）。若把入口写成装配内的一个插件并 inject，这一格与 A 相同 | **失**：启动时 AI 的门先于 OG 的门开，有一段「能登录却答不出成员资格」的窗口；运行中一个 owner 重跑只关它自己那扇；补一道全局就绪闸门，就多出第四个拥有次序的单元 |
| SAF-10 停机不留半个 | 能：一个 effect 内「停止接收 → 等 → 关闭」 | 能：在 `dispose()` 里同样排 | 能，但三扇门各自停，撤除期间一部分门仍在收 |

| LIV-2 答不出之后恢复不必重新登录 | 能：入口层没有按请求保存的状态 | 同 | 同 |

## 性质承载矩阵：运维面轴

| 性质 | A 的运维面（进程内 fiber，本机通道） | D（进程外命令读状态记录） |
|---|---|---|
| INV-1 右边只有一张面 | 能：一条只在本机可达的通道，只在中心进程里 | 能，且更强：进程内没有第二条通道 |
| INV-5 完整体检是中心的自述（含时钟开着时往回倒、中心自身的故障） | 能：在中心进程内现读 `storage`、`clock`；入口层遇到的中心自身故障怎样到达运维面，承载者未定（design.md 交接缺口） | **失**：「数据所在够不够得着」「时钟正不正常」变成命令此刻看到的；中心进程看到的存储故障、时钟提供者的运行时状态（开着时往回倒、崩溃重启后落在旧租约窗口里）与入口层遇到的中心自身故障都进不了记录，除非中心持续改写记录 |
| SAF-7 运维者没有门 | 有前提地能：传递 import 图静态检查；运维面只 inject `storage`、`clock` | 有前提地能：命令入口不导入任何 `tenancy/*` 包——**包级规则，粒度比 A 强**；但命令自己打开存储，要同一条「只做可达性探测」的检查 |
| SAF-8 体检不越界、秘密不进输出 | 能 | 能：状态记录是一份新的落盘输出，要进输出枚举 |
| SAF-9 不半开 | 能：运维面排在入口层之前，运维面失败即启动失败 | 不涉及启动整体性；但记录写失败时中心是照常起来还是起不来，要另定 |

## 候选 A

**形状**：入口层是一条挂在根 Context 下、与六条领域 fiber 平级、**不 provide 任何服务**的 fiber，落 `packages/tenancy/governance-center-entry/`（包与插件名 `governance-center-entry` 是候选）；
运维面是同包内另一个插件（候选名 `governance-center-ops`）的 fiber。形状细节见 [design.md「装配草图」](design.md#装配草图)。

**最强论证**：三条最要紧的性质——一条判定次序（SAF-2）、不半开（SAF-9）、内部面不直接暴露（SAF-11）——各有**一个**结构保护点；
而且不改任何已接受的 v1 契约，也不让装配节点兑现契约语义。入口层包可以被装进测试装配（配可控时钟）单独验证，
将来要拆出一个边缘进程时，它是一个可以整体搬走的包。

**失去保护点的性质**：

1. **SAF-7 的保护点在包里，不在包边界上。**运维面与入口层同包，而入口层引用全部治理服务名；
   「运维面没有门」只能按运维面插件的传递 import 图检查，包级依赖规则用不上。Cordis 在进程内不给访问边界（P-8），这一格没有运行时保护。
   若传递 import 检查在现有检查形式里做不出来，退路是把运维面拆成独立包，用包级规则守——代价多一个包。**这一条 B 同样有**，不是 A 独有。
2. **INV-2 的持有者是一个投影层。**中心标识是部署事实，却由线上投影的提供者铸造与持有；入口层因此 inject `storage`，
   进程里唯一面向网络的单元握着一条可以绕过 AI、OG 的原始存储通路。「只碰 `governance_center` 一张表」在没有结构检查之前只是约定。

**反查信号**：

- **重复拥有同一事实（潜在）**：一旦出现第二个入口——第二种线上协议，或拆出去的第二个边缘进程——两个入口都会想铸中心标识，同一条部署事实有两个拥有者。
- **反复同步修改（投影固有）**：任一领域契约的公开面改版，入口契约与路由表要同步改。三个候选都有这一条；A 把它集中在一个包、一份契约里。
- **跨 owner 同提交**：无。入口层除铸标识外不写；每个请求落在一个 owner 的一次提交里（注册链归 AR 自己）。

**可计数代价**：

| 项 | 数 |
|---|---|
| 新包 | 1（`packages/tenancy/governance-center-entry`） |
| 新插件 ／ fiber | 2 ／ 2 |
| 新契约 ／ 改版的已接受契约 | 1 份组合契约（含 Schema）／ 0 |
| 监听 | 2：网络 1、本机 1，各一个 effect |
| inject 边 | 入口层 6（`logins`、`registration`、`organizations`、`memberships`、`offers`、`storage`）；运维面 2（`storage`、`clock`） |
| 迁移片段 | +1（`governance_center`，一行），由装配合成 |
| 路由 | 28：27 条契约操作投影（AI 3、AR 1、OG 23）＋ 公开体检 1；3 条不经认人；4 条读面补授权 |
| 结构检查 | `restricted-call-sites` 加 3 个方法限定；新规则 2 条（`tenancy/*` 不引入监听模块，入口层包除外；运维面插件的传递 import 图不含治理服务名）；建议再加 1 条（入口层包只碰 `governance_center`） |
| tenancy-host 修订 | 装载清单末尾加 2 项、迁移合成加 1 个片段、撤除次序加 2 步、监听与本机通道配置 |

## 候选 B

**形状**：监听、判定次序、路由表、中心标识的铸造与运维面都写在 `apps/tenancy-host` 里；`boot()` 等六条 fiber 都可用之后铸标识、开监听，
运维面是装配里的本机通道或 `tenancy-host status` 一类命令。**变体**：在装配里定义一个插件并 inject——那时它的承载与 A 相同，
差别只剩节点归属（装配 vs 提供者）、扫描范围与可复用性，下文的反例对这个变体仍然成立。

**最强论证**：少一个包；PF-017 §5.1 图里「下面那一层」恰好就是部署，而部署这一层的全部事实——配置、密钥、参数、标识、体检——
在 B 里集中在一个节点；装载次序、启动整体性与「最后才开门」在一段顺序代码里一眼看全；
realization 本来就让装配节点的 `architecture.md` 登记「人和脚本各从哪个面进来」。

**失去保护点的性质**：

1. **SAF-11 的结构检查**：`restricted-call-sites` 只扫 `packages/`，入口代码在 `apps/` 下就脱离了守 AI S-30 第 8 行与 OG S-42 第 4 行的检查。
   扩一次扫描范围即可补回——这是代价，不是排除理由。
2. **SAF-9 的运行期一半**：非插件代码在调用时解析服务，某个领域服务缺席时门照样开着。本版没有热替换，这一差别是潜在的。
3. **语义归属**：判定次序、答复集合、拒绝同形必须写进一份契约；在 B 里兑现那份契约的是一个装配节点。
   realization 的准入写「应用节点不持有能力语义」、红线写「整体保证缺独立协调责任时回能力分解，不在 `apps/` 里补一段逻辑了事」——
   入口层的判定次序正是一项独立的协调责任。

**反查信号**：

- **反复同步修改**：tenancy-host 为两类无关的原因改——线上协议与投影的变化，以及存储、时钟、密钥与清单的变化。
- **装配拥有产品事实**：中心标识由装配节点铸造与持有。

**可计数代价**：新包 0；tenancy-host 增加监听、28 条路由、标识铸造与运维面；迁移片段 +1（在装配里）；
realization 准入例外 +1（装配节点兑现组合契约）；`restricted-call-sites` 扫描范围 +`apps/tenancy-host`；
协议的场景测试无法用测试装配（可控时钟、可注入故障的存储）单独起，只能起生产装配（真实密钥文件与环境），
或把判定代码抽成一个包——那就回到了 A；将来拆出边缘进程时要搬代码、搬节点、搬绑定。

## 候选 C

**形状**：三扇门——AI 的门（登录、退出与撤销、列出）、AR 的门（注册）、OG 的门（其余治理操作）。
每扇门先核版本、再认人（OG 的门调 AI S-17），再办自己的事。**最强形态**：一个基础设施插件 provide 共享路由服务，
三个领域插件 inject 它，把各自的路由作为 effect 登记，随各自的 fiber 撤除。

**最强论证**：每份契约的线上投影与它自己的契约同版本演进——OG 出 v2 加一个操作，只改 OG 的包；
没有一个必须认识三份契约的中心模块；路由作为 owner fiber 的 effect 登记，是 Cordis 里自然的组合形状；
若 SYS-DEPLOY 的演化沿能力边界把账号身份与组织治理拆成独立服务，每个服务本来就要有自己的接收边界（[IV S-30](../../../spec/data/identity-values/v1/contract.md#s-30-跨边界须重新验证)），C 已经是那个形状。

**失去保护点的性质**：

1. **SAF-9**：启动时 AI 的门先于 OG 的门开；运行中 OG 的 fiber 因依赖换代重跑，它的路由随之撤下而 AI 的还在——
   正是 [PF-017 §6.6](../../../product/PF-017-governance-center-as-deployable-application/design.md#66-要么整个起来要么不起来) 点名的「能登录却答不出成员资格」。补一道全局就绪闸门，就多出第四个拥有次序的单元。
2. **SAF-2**：「只有一条路」变成三条同形的路，没有一张能被一个测试遍历的表。
3. **SAF-11**：[OG S-42 末段](../../../spec/capabilities/organization-governance/v1/contract.md#s-42-装配给的保证-vs-协议须给的保证)写明它的面是能力间内部面、**不得被直接暴露成终端 API**；C 恰恰这样做。
4. **INV-1**：「领域包不引入监听」这条规则无法成立；共享路由形态下，第三张面只差一次 inject。
5. **INV-2**：三个 owner 都不拥有中心标识。

**反查信号**：

- **重复拥有同一事实**：判定次序、拒绝的形状、可接受的协议版本集合，各在三处。
- **反复同步修改**：协议版本一升，三个包、三份契约一起改。
- **跨 owner 的逐字一致**：拒绝同形要求三个 owner 的输出逐字相同，却没有单一拥有者——它是「跨 owner 同提交」在输出上的近亲。

**可计数代价**：已接受契约改版 3（AI v2、OG v2、AR v2——把「内部面」改成终端面、各自拥有线上答复）；
第四个持有者 1（版本关、公开体检、中心标识）；判定次序 3 份（或 1 个共享库加 3 个调用点，调不调用无法强制）；
跨包逐字比较测试 1；全局就绪闸门 1；共享路由的基础设施插件 1（共享路由形态）；「不引入监听模块」规则作废；
运维面仍要从 A 或 D 借。

## 候选 D

**形状**：进程内不设运维面。运行中的中心在启动成功时写一条状态记录（这次什么时候起来的、版本、中心标识、密钥在不在与完整不完整、每项部署参数的值；不含任何秘密），
落在中心所在机器上；`tenancy-host status`（候选名）作为另一个进程在本机运行：读这条记录，用同一份存储配置自己打开存储探一次可达性，自己看时钟，输出完整体检。
入口层仍按 A（或 B、C）。

**最强论证**：运行时只有一个监听，运维者在中心进程里没有任何通道；命令入口可以用**包级**规则守「不导入任何 `tenancy/*` 包」，比 A 的传递 import 检查粒度更强；
中心停着时命令仍能说出一些东西（上次什么时候起来、数据所在够不够得着）。

**失去保护点的性质**：

1. **INV-5**：[PF-017 §4](../../../product/PF-017-governance-center-as-deployable-application/design.md#中心体检) 把中心体检定义为**中心**关于「我此刻在不在、能不能答」的自述，
   完整部分明列「此刻能不能答」那一组：数据所在够不够得着、时钟正不正常（含开着时往回倒了）、有没有遇到中心自身的故障。
   在 D 里，「数据所在够不够得着」是命令此刻看到的——中心以服务账号跑、命令以运维者的账号跑，一个挂载点或一个权限不同，两边就给出不同的答案；
   时钟提供者的运行时状态（开着时往回倒、崩溃重启后落在旧租约窗口里，此刻只答「不可用」）只有中心自己知道；入口层遇到的中心自身故障进不了命令。
   要补回来，中心就得在运行中持续改写记录——那又是一个进程内的运维写者，外加一个陈旧窗口。
2. **完整体检的「在不在」**：中心崩溃后记录仍写着「某时起来了」，而此刻没有人在应答；要补一套存活检测（进程号或锁文件）。

**反查信号**：

- **重复拥有同一事实**：状态记录复制了中心在内存里持有的事实，崩溃后二者分叉；「时钟正不正常」的判断要在命令里重写一遍或近似，同一个判断两个拥有者。
- **反复同步修改**：体检字段每加一项，写者（中心）与读者（命令）一起改；升级期间还有新命令读旧记录的跨版本问题。

**可计数代价**：状态记录格式 1（带版本）；写者 effect 1（启动时写；要部分补回 INV-5 还得周期改写）；命令入口 1；
存储探测路径在命令里复制 1（同一份方言配置与连接）；时钟判断复制 1；存活检测 1；落盘输出 +1（要进秘密的输出枚举）。

## 排除的其他运维面路径

它们是真实走得通的路，因约束被排除，排除依据留在这里：

- **运维面作为入口层监听上的一条路由，按对端地址（本机回环）放行**：把网络位置当资格（[IV S-21](../../../spec/data/identity-values/v1/contract.md#s-21-判定依据的构成封闭)；
  [PF-017 §6.2](../../../product/PF-017-governance-center-as-deployable-application/design.md#62-中心只认登录状态不认客户端)「中心不知道、也不试图知道来者是哪台机器」），而且在左边那张面上多开了一扇门（INV-1）。
- **运维面并进入口层的 fiber**：运维代码与 inject 了全部治理服务的单元同处，「没有门」无从静态检查；随入口层重跑；变化原因不同（[design.md 第 5 条](design.md#为什么不拆为什么不并)）。

## 反例是否互不重复

| 候选 | 关键反例 | 是否与别的候选共有 |
|---|---|---|
| A | 中心标识由投影层铸造：出现第二个入口时，同一条部署事实有两个铸造者 | 独有（B 的持有者是装配，C 没有持有者，D 不涉及） |
| B | 装配节点兑现一份组合契约的语义；协议测试离不开生产装配 | 独有 |
| C | 运行中一个 owner 重跑只关它自己那扇门——「能登录却答不出成员资格」；与 OG S-42 末段直接相反 | 独有 |
| D | 完整体检变成命令看到的，不是中心看到的 | 独有 |

四条互不重复。共有的弱点另列，不算任一候选的独有反例：运维面「没有门」没有运行时保护（A、B 同，P-8）；投影随领域契约同步修改（A、B、C 同）。

## 入口契约为什么是一份 composition 契约

入口层的语义必须进契约——三个出口、拒绝同形、判定次序、身份推导、补授权、失败映射都是产品可观察的，
[tenancy-host](../../../realization/apps/tenancy-host/architecture.md#交付面与非目标) 也明写它「取决于尚未起草的契约」。
可选的契约形态有三种：

**（一）三份能力契约各加线上条款**（AI、OG、AR 各出新版本）——不选：

- 判定次序是**对所有请求**的一条性质，跨三份契约的操作；写进三份就是同一条次序三份陈述，任何一份改动都要三份一起改版，分叉时没人看得见。
- 版本关、公开体检、中心标识不属于三者中的任何一个，这个形态仍要第四个家。
- 三份 v1 已被 [D-023](../../decisions/tenant-domain-design-acceptance/README.md) 接受并冻结；[OG S-42 末段](../../../spec/capabilities/organization-governance/v1/contract.md#s-42-装配给的保证-vs-协议须给的保证)写明它的面是内部面、终端 API 归装配之前的那一层——这个形态把它反过来。
- OG 的线上条款得规定 AI S-17 的拒绝怎样呈现（OG 的门要认人），一份契约就拥有了另一份契约的拒绝形状。

**（二）一份 data 契约**（信封、四种答复、中心标识、体检字段的形状）——不选：

- data 契约拥有值与纯判断（[identity-values](../../../spec/data/identity-values/v1/contract.md)、offer-expiry 都是这个形态）。入口层的实质是一条动作链上的行为义务：
  步骤的次序、每一步的失败映射、δ＝0 不缓存、在接收边界重新鉴别、补授权、这条边的「装配给／协议给」表、运维面上没有治理路由，
  外加一个提交点（首启铸造中心标识）与一个撤除次序。这些是组合的领地，不是值的形状。
- 那些形状现在只有一对消费者：入口层与客户端代理，而它们实现的是同一份契约。单独立一份 data 契约，就给一组只因这一个组合而变的形状多立了一个拥有者。

**（三）一份组合契约**（主线裁定：`composition.governance-center-entry` v1，「治理中心入口」，取代 apps/cli 节点里的拟议名「治理契约线上投影协议」）——选：

- handbook 的判据：[整体性质无法归属单方时明确组合契约](../../../../agents/skills/harness-design-handbook/canonical/references/decompose.md#s3让未覆盖责任决定演化)。
  判定次序、封闭的答复集合、拒绝同形正是三份契约的操作在同一条路上组合时才出现、又不属于任一方的整体性质。
- 它不是能力：不拥有任何治理事实，进程内没有消费者 inject 它（[design.md](design.md#剩余责任与能力演化)）。
- 它拥有：客户端那一面（信封、出示物、判定次序、四种答复、逐条投影 AI／OG／AR 操作的路由表、身份推导、补授权、失败映射、δ＝0 不缓存、公开体检）；
  运维面（完整体检只在本机、没有治理路由）；中心标识的形状与铸造；这条边的「装配给／协议给」表。
  **中心标识与信封的形状随本契约的 Schema**，不另立 data 契约。
- 它唯一持有的事实是中心标识——这是这份组合契约与其他组合（例如[账号注册](../../../spec/compositions/account-registration/v1/contract.md)，没有自己的事实）不同的地方，代价记在[候选 A](#候选-a)。

**（二）会重新上桌的条件**：`GovernanceCenterId` 或信封形状在本组合之外出现第二个消费者——例如据点身份里「哪个治理中心」被写进另一份契约的持久形状，
或第二种协议复用同一个信封。那时把这些形状拆进一份 data 契约（或身份值契约的下一版）。

## 传输机制为什么不进契约

- **契约写性质，提供者设计写绑定。**线上用 HTTP/1.1 + JSON、本机用受文件权限保护的套接字，是「这些性质由什么兑现」；
  换传输的失效事件是「实现换方案」，家在 realization，不在 spec。把传输写进契约，等于把一个实现选择焊进领域承诺，换一次传输就要发一版契约。
- **[SYS-DEPLOY](../../../foundation/cross-system-constraints/requirements.md#sys-deploy) 要求同一句话在单机与分布式下都成立。**传输恰恰是跨部署形态、跨时代会变的那一层（单机直连、网关、别的协议）；契约的每一条都要在换传输后仍是同一句话。
- **进契约的是与传输无关的表述**：信封的逻辑字段与版本声明；四种答复是封闭集合；「逐字相同」覆盖**协议层可观察的整份答复**；
  公开体检与「版本对不上」的格式跨协议版本不变；运维面**只在中心所在的机器上可达、且从不以对端的网络位置作资格**；
  防冒充——[PF-017 §8](../../../product/PF-017-governance-center-as-deployable-application/design.md#八边界与依赖) 对技术设计的硬要求——写成性质：客户端确认不了连上的真是那个中心，就不交出登录状态、不接答复。
  怎样确认是机制，不进契约；主线裁定它的材料是部署配置输入（与 TLS 证书同类），不算[部署密钥](../../../ubiquitous_language/terms/grounding-and-isolation.md#ul-deployment-key--部署密钥--deployment-key)。
- **传输的候选**由将立的提供者节点定并记候选；它与 [cli-tui 提案 D11](../cli-tui/alternatives.md#d11-线上协议与认证)（HTTPS、登录状态作 bearer、显式版本协商、无推送）同向，二者都未被接受。

## 推荐与改票条件

**推荐：入口层取 A，运维面取 A 的形状**——这是主线裁定的方向，**不是接受**。

理由：A 是唯一一个让「一条判定次序」「不半开」「内部面不直接暴露」各有一个结构保护点、同时不改任何已接受 v1 契约、也不让装配节点兑现契约语义的候选。
B 的承载与 A 接近，差在语义归属与可测性；C 在不半开与内部面两处直接失去保护点，还要三份 v2；D 让完整体检不再是中心的自述。

**接受 A 的人要明知的代价**：中心标识由投影层持有，面向网络的单元因此握着存储；运维面「没有门」只有静态检查、没有运行时边界；
每次领域契约公开面改版，入口契约同步改版。

**改票条件——什么证据会让落选方重新上桌：**

| 落选方 | 重新上桌的证据 |
|---|---|
| **B** | realization 的准入改为允许装配节点兑现组合契约，**并且**变更历史显示入口层包与 tenancy-host 同一提交修改的次数多于与三份领域契约同一提交修改的次数——即「变化原因不同」这条在事实上不成立 |
| **C** | SYS-DEPLOY 的演化沿能力边界拆开了账号身份与组织治理（不同进程），每个服务都得有自己的接收边界；**或**变更历史显示入口层每次改动都只随某一份领域契约改动、判定次序与协议版本多年不动 |
| **D** | 评审或测试找到一条从本机通道通向治理事实或秘密、而静态检查关不上的路；**或**目标平台上没有受文件权限保护的本机通道；**或** PF-017 放宽「体检是中心的自述」、或要求中心停着时也给完整体检 |
| **A 的变体：把中心标识交给一个独立的部署事实持有者** | 出现第二个入口（第二种协议或拆出去的边缘进程）；**或**评审确认「入口层包只碰 `governance_center`」这条检查做不出来；**或**部署事实在标识之外继续增长，需要一个拥有者 |
| **A 的变体：运维面拆成独立包** | 运维面插件的传递 import 检查在现有检查形式里做不出来，或它被证明守不住 |

**仍待区分的事项**（最小区分调查，结果会改变上面两个变体的去留）：
传递 import 检查能否以现有 `tools/ts-checks` 的规则形式实现；「入口层包只碰一张表」能否静态检查；中心自身的故障到达完整体检的承载者选哪一个。
