## 反例与契约依据

节点 README 和 bindings 采用 `capability.account-identity/v1#S-8`。v1 契约 `contract.md:224,235` 要求凭据材料“不以可读形式保存”。S-8 另有两条读取/返回边界（236～241 行），不应把整个 S-8 简写成只有第一条。节点 README 明确仅由本提供者承担第一条的派生责任。

现行节点 `verification.md:11` 却将第一条写成“derive 的输出不含输入明文的任何子串”。`bindings.yaml:16` 使用相同推断。测试 `obligations.spec.ts:31～48` 将它具体化为：材料任意位置出现输入的任意长度不小于 3 的子串就失败。

本次固定输入是原测试的公开 fixture 字符串，以及合法的 16 字节盐 `ade70000000000000000000000000000`。该盐的 base64url 编码为 `recAAAAAAAAAAAAAAAAAAA`。原实现 `scrypt.ts:95～96` 从随机源取盐并调用 scrypt；`scrypt.ts:104～112` 明确编码方案、参数、盐和哈希。

两版实际运行结果均为：

- 旧子串判据检测到 `rec`，它已存在于独立盐字段的编码中。
- 材料不包含完整 fixture 字符串，原 `verifyMaterial` 返回 `match`。
- scrypt 源文件 SHA 为 `223d1716dbdd56a957feab8bb9f0aa35f870d46dcca46168dbbf5ecdfb888bcc`。
- 两版材料 SHA 均为 `65601c1a14f2baf1256b15b56c2fca2a31b5dd328cb91126730e24dbe7772918`。

这里的固定盐是随机源接口可能返回的一组字节，不是让产品在生产中使用固定盐的建议。原调用点不按凭据选择或过滤盐。盐的编码偶然与凭据片段相同，不能据此推出实现保存了该凭据片段。

原真实失败的输出确实是 `expected 'rec' to be undefined`，位置为 `obligations.spec.ts:47`。本诊断证明旧判据存在能在 BASE 与 HEAD 同时复现的误报输入；原随机盐/材料没有保留下来，因此不能证明原失败的 `rec` 一定位于盐段，也不能重建那次随机抽样。
