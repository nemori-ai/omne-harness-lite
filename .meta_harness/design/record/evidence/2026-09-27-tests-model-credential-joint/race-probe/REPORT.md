# P3 SQLite credential contention: one measured public-path run

## Result and scope

The one authorized new cross-package run **failed**: second `bindCredential` returned the public `{ failure: 'unavailable' }`. The actual directory binding reader had reached its barrier while the first SQLite connection held `BEGIN IMMEDIATE`. The barrier was released **50.227 ms** later, within the required 100 ms. The CCL store resolved `{ stored: true }` **0.530 ms** after release; `storage.atomic` returns only after its write commits, so that commit had completed by this resolution. The second bind returned `unavailable` **15.177 ms after the store resolution**, or **65.911 ms after its launch**. The first commit was thus before the second failure, but only 15.177 ms is measured between their public resolutions; there is no direct `COMMIT` timestamp. Both storage instances and both Cordis assemblies closed; temporary database and key were removed. Exit was `1`, stderr was empty, PID was `175909`. The raw event trace is `trial.stdout`; `trial.exit`, `trial.stderr`, and `trial.pid` are separate raw files.

This excludes a **5 s deadline exhausted while this trial's reader held the writer lock**. It does not identify the failing operation or SQLite errcode. The public `unavailable` remains contract-permitted for real storage unavailability; this run does **not** show that such a busy deadline elapsed, and it does **not** meet V3-15's successful-order acceptance. V3-15 and the MCR-V4 joint contention branch remain **unverified**, not disproved. No second cross-package run or retry-to-green occurred.

## Cause limit: second clock is an uncontrolled input

The fresh second Cordis directory also starts a second `LeaseClock` on the same database. In a fresh database, the first clock writes a lease ending `w + 10,000 ms` (`clock/src/clock.ts` lines 125–139; `clock/src/lease.ts` line 8). A later clock reads that row and sets its own high-water mark to the stored `lease_until` (clock lines 154–157); `now()` returns `unavailable` while wall time is below that high-water mark (lines 97–110). This trial completed at process monotonic time 727 ms, so under ordinary wall-clock progress the second clock cannot yet answer a new time. **The clock value and stored lease number were not recorded**, so the direct runtime cause is an inference, not an observed phase result; a clock jump or an earlier failure remains unexcluded.

The measured script checked only that second OG `memberships.standing` succeeded **before** contention. OG wraps even that read in `storage.atomic` (`organization-governance/src/memberships.ts` line 354; `src/runtime.ts` lines 82–90), so the concurrent authorization can contend for the SQLite writer before directory's own write. Directory `bind` authorizes first, enters `storage.write`, and only calls `clock.now()` when the existing binding differs (`model-profile-directory/src/runtime.ts` lines 441–456). The old frozen verifier's `secondPreflight` binds the **same** reference (its lines 263–269), which returns at directory line 454 and therefore cannot prove that second clock could support the later rotation. Its three old `unavailable` results remain unexplained by direct cause evidence. The present run's fast failure is consistent with clock unavailability after the first commit, but OG/storage unavailability during authorization or the directory write is not ruled out by the recorded public result.

No driver-only diagnostic was executed; the optional probe was paused when the clock confound was identified. In particular, no extended `SQLITE_BUSY` errcode was observed. The static driver has a 5 s retry deadline for exact SQLite busy code `5` (`storage-sql/src/sqlite/driver.ts` lines 199–213); `storage-sql/src/sqlite/errors.ts` may classify other busy-family codes as `StorageUnavailable`, but no numeric code was captured here.
