### 中心是怎样起的

全部照承载装配 README（仓库里的 `apps/tenancy-host/README.md`）的部署方式（逐条命令在 [`commands/commands.txt`](commands/commands.txt)）：

1. **TLS 材料**：`openssl req`／`x509` 生一张自签 CA（ECDSA P-256）与它签的 `localhost` 叶子证书（SAN `DNS:localhost, IP:127.0.0.1`）；每次调用自带配置文件，不读系统 `openssl.cnf`。另生一张**别的 CA** 签的同名证书与一张**同一 CA 签给 `wrong-host.invalid`** 的证书，给反向用例。
2. **部署密钥**：`node dist/cli.js keygen <dir>`，四个 `_FILE` 变量取自它的标准输出。
3. **配置**：全部经环境变量；密钥、证书链与 TLS 私钥走 `_FILE`；子进程的环境只有部署配置与 `PATH`。五项部署参数 `P7D`／`P14D`／`1209600000`／`604800000`／`P7D`，凭据政策 `{"minLength":12}`，等钟上界 `15000` ms。
4. **起进程**：`node dist/cli.js serve`；**就绪**＝运维面套接字 `governance-center-ops.sock` 答出一份完整体检（不读进程内部）。
5. **结束**：`SIGTERM`，每次都断言退出码 0；强行结束一律 `SIGKILL`。

一次运行里起了 17 个 `serve` 进程（中心 A 的 15 次启动、另一个中心 B、同一地址从零重立的 F），另有 9 次预期的启动失败、6 次 `cli.js` 用法错误与 3 次 `keygen`。

## 异常

**本次没有发现实现与契约不符的缺陷。**下面三处是**契约与产品正文、或两份契约之间没写定的地方**，
套件照契约断言、另把观察原样记进 [anomalies.txt](output/anomalies.txt)，**不判谁对**——需要主线裁。

| # | 在哪 | 观察 | 最小复现 | 需要裁的最小问题 |
|---|---|---|---|---|
| A-1 | PF-001 flows §二「撤销登录状态 2：指定的那一个已经失效 ⇒ 这个登录已经不在有效之列」 vs EC S-20／AI S-16「已撤销 ⇒ `ok`」 | 列表上的某一项被撤销之后再撤它，线上是 `{"result":"ok"}`，与一次成功的撤销逐字相同；客户端据此呈现不出「不在有效之列」 | 登录两次得 L1、L2；L1 撤 L2 ⇒ `ok`；L1 再撤 L2 ⇒ `ok`（transcript `pf001-2-revoke-branches` 的 `ada1:revokeLoginState`） | 产品那一行是否改读成「已撤销的再撤算成功」，还是契约要给「已失效」一个可区分的答复（EC 新版本） |
| A-2 | PF-001 flows §二「注册 1：凭据不符合规则 ⇒ 具体哪条规则不满足」 vs EC S-7 与 Schema `RouteFailure` | 线上只有 `{"failure":"credential-rejected"}`；AI v2 说规则「随这个失败值附带、由政策自己描述」，但入口契约的线上形状里没有承载它的成员 | 凭据政策 `{"minLength":12}`，注册时给 5 个字符的凭据（transcript `pf001-2-register-branches` 的 `weak credential`） | 「哪条规则」要不要上线（EC 新版本加一个成员），还是由客户端按公布的政策自己说明（那份政策现在也不在线上） |
| A-3 | EC S-21 解除隶属「已解除后重发 ⇒ `noSuchAffiliation`」 vs OG S-33 ②「发起者是任一方组织的超管」与 ⑦ 的判定先后 | 由**下级一方**重发得 `noSuchAffiliation`（与两份契约都一致）；由**原上级一方**重发得 `notAuthorized`——关系已不在，原上级不再是「任一方」 | cy（Y 的超管）接受 X 的隶属请求后解除它 ⇒ `ok`；cy 再发同一次解除 ⇒ `notAuthorized`（transcript `pf001-1.7-affiliation` 的最后一次 `cy1:dissolveAffiliation`） | EC S-21「重发」一列是否只对下级一方成立（改写那一格），还是 OG S-33 要先判「属性已空」再判授权（OG 新版本；本页的推断：那样会向任何超管透露一个组织当下有没有上级） |

**不是缺陷、但值得运维者知道的一处观察（O-1）**：手动走 README 的步骤时，运维面目录放在一个很深的路径下，`serve` 以
`startup-failed`（`stage: plugin`、`item: governance-center-ops`、`OpsSocketError: … could not be prepared or bound`）起不来——
套接字的完整路径超过了 Unix 套接字 108 字节的上限；说明里没有点出是路径太长。套件里的目录短，不受影响；这不是本次 run 的一部分，只是写 README 时的观察。

**输入缺口（I-1）**：简报设想从 `apps/tenancy-host` 的 devDependencies 取 `ajv` 校验答复形状，但它不在那里（只在三个产品包里）；加它要改锁文件，按公共约定不加。
所以本次**没有做全量 Schema 校验**：答复的形状按契约的成员名与书写次序在用到的地方逐条比对（T07、T10、T13、T16、T17、T19、T33 等），
另加 T45 的逐份外形与 RFC 8785 写法核对。要全量校验，需要主线决定是否给本包加 `ajv` 开发依赖。

## 边界

- **有界**：一台机器、一个 sqlite 文件库、一次运行；每个场景一到几次；并发只有 T22 的两轮两请求。**不是性质证明**。
- **没有做的故障**：存储够不着、钟回拨或前跳、断电、升级、注册中途停机、入口层自身缺陷——理由逐行写在场景表里。
- **「另一台机器」**以回环地址 127.0.0.2 近似；「搬家」是同一台机器上换目录、端口与运维面目录。
