# 同步接管与可选依赖的关闭次序

本次运行核对结构复评提出的两项反例。BASE 为
`588628544ab92bd542f24efa1801634eb6eee56e`，命令、输入与结果散列见 [run.json](run.json)。
[驱动](control-order-probe.mjs)使用真实 Cordis 和受控资源，仍是机制探针，不是产品 loader。

[输出](control-order-probe.stdout)保留两个正控与两个负控：

- 同步接管正控：同 tick 第二次 load 被拒绝，首个不受影响，恰一次 apply。
  缺少接管的负控：第二个句柄可在 apply 前关闭共享 lifetime，使首个无法启动。
- 可选次序正控：提供者在前，消费者晚完成的后半程保存成功，随后才关闭提供者。
  忽略可选边的负控：提供者在后，被先关闭，消费者后半程得到 backend-closed。

准备阶段的小型声明检查同时断言：后置可选提供者拒绝、前置可选提供者允许、可选依赖缺席允许。
这没有把可选依赖变成必需依赖。正负控仍需正式声明/schema、实际提供者和独立 QA 接续。
