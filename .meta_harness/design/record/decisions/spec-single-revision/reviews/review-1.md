## 1. 二选一

终态取**乙**：路径去掉版本号，原地修订，修订号记在登记里。

**第三种终态**：我没有找到明显更好的。考虑过「甲加一个不带版本的别名路径」，它让同一份东西有两个名字，放弃。对乙只有一处细化建议（我的推断）：对账粒度做到条款级。catalog 的 `dependencies[].clauses` 和 bindings 的 `#S-n` 已经是条款级，如果每次修订的 changelog 用机器可读方式列出改动的条款号，对账器就可以只点名消费了这些条款的人。这是乙的实现细节，不是另一种终态。

**简报的对等性**：大体对等，有两处不对称。
- 甲的描述漏了一个后果：「全部消费者」包括其他契约的冻结字节。这对甲偏宽，见第 4 问。
- 乙的描述引了「产品 rev 已有对账器」作先例。先例属实，但它对的是「词条、对象、节点引用产品 rev」，不是契约之间的依赖或 bindings，乙仍要新写对账器。这对乙偏宽。

## 2. 选乙的三条最强理由

**理由一：版本号写在路径里，引用就写进了冻结字节；甲的两条规则合起来，每次修订都要连锁重发。**
- 契约间引用落在冻结字节里：
  - 最新版的 110 个冻结 Markdown 中，55 个文件共有 1848 个链接指向别的版本目录（我自己数的）。被指最多的是 identity-values 301、asset-model 209、content-blocks 180。
  - 正文抬头还逐条写着依赖版本，例如 `model-request-runtime/v12/contract.md` 的「精确语义依赖」列表。
  - Schema 的 `$ref` 是含 `v{N}` 的绝对地址，由 `_schemas` 按路径推出的 `$id` 解析。
- 甲要求「发布新版时删旧版」又「冻结字节不变」。于是 X 一修订，所有引用 `X/vN` 的最新版都得出新版，它们的依赖方再跟着出。
- 我按 catalog 依赖算了每份契约的传递依赖方数量（共 44 份）：identity-values 43、offer-expiry 40、content-blocks 32、asset-model 30、tool-definition 27、model-profile 25；均值 10.2，中位数 5.5，只有 6 份为 0。
- 乙的路径稳定，被依赖方修订时依赖方字节不动。只有条款标题真的变了，`_markdown` 的锚点检查才点名确实引用它的那几处。
- 同一条理由也覆盖产品锚点：最新版冻结规格里有 3534 个带锚点的产品链接（盘点 C7，我未复核该数），冻结文件又不能改。乙可以原地修；甲下产品改一个标题就要出新版再连锁。

**理由二：「每版一个目录、整包拷过去」的做法，已经让形式化正版在树里漂移。**
裁决要求形式化正版持续维护；甲每次修订都要重做一次整包拷贝和任务重登记，乙没有这一步。
- `model-request-runtime` 有 11 个版本目录、553 个文件；`contract.md` 从 215 KB 长到 391 KB，每版都是近乎全文的拷贝。
- v12 的 `formal/` 里有 13 个 `.tla`，`formal-tasks.json` 给 v12 只登记了 2 个任务（都是 AckLifecycle）。MRR 其余任务挂在 v2 到 v11 上：2、3、6、6、10、10、10、11、6、3。
- 任务 ID 和命令行都嵌着版本，例如 `organization-governance-v1-membership`，命令里写着 `…/v1/formal/Membership.cfg`。
- organization-governance 的 v3 目录里只有一个 `contract.md`，模型留在 v1。
- 甲写了「形式工件与任务随之带过去」，但上面的事实说明这一步在现行做法下就是被跳过的那一步。乙下模型与任务 ID 原地不动。

**理由三：乙复用仓库里已有的修订机制，全链只剩一种「版本」概念。**
- 产品 topic 已经是「README front-matter 的 `revision` 加 changelog」，例如 PF-013 的 `revision: 17`。
- 两个对账器已在 `make design-check` 里，缺省判失败：
  - `domain_objects.py` 的 `_load_revisions`、`_stale`；
  - `realization_nodes.py` 的 `cited`、`_stale`。
- 甲保留两套并行的版本语义（产品用 rev，规格用 vN）。
- 引用稳定性：我数到设计根内约 7213 个 Markdown 链接指向各契约当前最新版目录（口径含旧版目录里的源文件，偏大），其中 product 2385、realization 806、record 80。甲下每次修订都会打断指向该契约的那一部分，包括按规矩不改的 `record/`。乙只需一次性改写。
- 可审性（我的推断）：原地修订的 diff 就是改动本身；甲每次是一个新的 391 KB 文件。

## 3. 对乙最强的三条反证

**反证一：冻结从机器保证退化成流程保证。**
- 现在 `_frozen` 不需要信任任何人，字节一变就报 `frozen file changed`。乙之后，「改字节、重算哈希、升修订号」放在同一个提交里，任何一致性检查都能通过。
- 仓库历史上明确反对过这种做法：
  - D-023（`tenant-domain-design-acceptance/decision.md` 第 42–44 行）终止了「直接落在 v1 上」；
  - D-066 第 22 行写「不通过重算旧坐标 hash 让冲突消失」。
- 检查器现在不读 acceptance.json 里的哈希（盘点 C15）。乙必须新增「登记哈希等于当前修订的接受声明哈希」这道门，否则没有东西拦静默改义。
- 靠人或 agent 复核的标记在这个仓库会烂：covers 的 `reviewed` 只有 87／3352。identity-values 有 38 个直接依赖方，它每修订一次就产生 38 条「待复核」；对账器缺省判失败，压力会导向机械升号。
- 代价落在接受门（负责人和评审）以及下游实现者身上：他们不能再凭坐标断定字节。

**反证二：现有实现依据的是旧版，乙之后旧字节在树里没有名字。**
- `realization/packages/model/model-request-runtime/bindings.yaml` 的 16 行条款全部指向 v2、v3、v4（6、7、3 行），而规格已到 v12。盘点称这样只绑旧版的节点有 13 个、旧条款行共 268 行（我只抽查了这一个节点）。
- `check_bindings` 只核 node、kind 和条数，不核条款坐标（`realization_nodes.py` 第 406–440 行）。迁错了，检查不会报。
- 乙下绑定只能写「核对于修订 N」，N 对应的字节只在 Git 历史里。若不同时登记「修订号对应哪个提交」，证据无法复核。
- 修订号必须接着现有的 vN 往下数（我的推断）。否则 `record/` 里上万处 `X/vN` 文字会与新的修订号撞号（盘点数：decisions 1248、evidence 17949，未复核）。
- 这一条在甲下同样存在，但乙连 `vN` 这个名字也拿掉了。代价落在实现映射的维护者和验收者身上。

**反证三：迁移面更大，而且推翻了一条被声明为不变的结构。**
- `spec/README.md`「路径即身份」写明「这一层的目录结构不随组织方式调整而变动」，`$id` 和 frozen 键都以含版本的路径为准。
- 乙要同时改的东西：
  - 全部 `$id`，包括 `packages/` 里随包发布的约 36 份 Schema 拷贝；
  - 1104 个 frozen 键、122 个任务的路径与 ID；
  - 检查器的 `_catalog`（要求路径在 `v{version}` 下）、`_schemas`（按 `version[1:]` 推 `$id`）、`Coordinate.read`、`check_coordinates` 的坐标正则，以及 `design_review.py`；
  - 我 grep 到 104 个含版本路径的代码或 JSON 文件；
  - 包的导出子路径，例如 `packages/core/messages/package.json` 的 `./schema/v2`、`/v3`、`/v6`；`src/schema.ts` 运行时导入 `content-blocks/schema/v2` 和 `offer-expiry/schema/v1`。
- 甲几乎不用改检查器。
- 发布后的隐患：不带版本的 `$id` 分不清线上或落盘数据属于哪个修订。根 AGENTS.md 写明发布时要重定兼容规则，到那时可能得把版本重新引回身份，届时只剩 `baseline_id` 这一个粗粒度开关（我的推断）。
- 代价落在工具维护者和将来写发布政策的人身上。

## 4. 甲最致命的一条

**甲的两条规则在现有引用方式下不能同时成立，除非每次修订都做一次连锁的「行政迁移」。**
- 第 5 问列的「最新版冻结字节引用旧版」（119、31、918）在甲下不是一次性的迁移问题，而是终态的常态。
- 删掉 `X/vN` 就打断所有引用它的最新版：
  - `_markdown` 报 `broken local link`；
  - `_schemas` 报 `unresolved schema resource`；
  - 改这些引用又撞 `_frozen`。
- 所以依赖方只能出新版，再传递下去。identity-values 一动，其余 43 份全部要重发，连带每份的接受声明（`_acceptance` 要求每个坐标恰好声明一次）、任务 ID、随包 `$id`、bindings 坐标。
- D-066 做过一次这样的迁移（33 份 v1 迁 v2）。它需要专门的工具 `rebase_resources.py`、一份登记 `version-migrations.json` 和一项决定，并留下 4599 处悬空的文字引用（盘点 C23，未复核）。
- 版本号从此不再表示语义变化，「v13 等于 v12 改了一个链接」会成为多数（我的推断）。
- 甲若为避免连锁而允许「只改引用的冻结字节可以原地改」，那就是乙的冻结语义加上会说谎的版本路径，比两者都差。

## 5. 从现状走到乙：五批

原则：先收敛语义，再删旧版，最后才动路径。旧版目录在第 4 批之前一直留着，所以前面每一批的旧消费者都不受影响。

**第 0 批：立决定、改规则文字。**
- 新决定进 `record/decisions/`，明确取代 D-023、D-028、D-040、D-066 等「旧版保留、不可原地覆盖」的范围（盘点 C22）。
- 同步改根 AGENTS.md、`.meta_harness/AGENTS.md`、`spec/README.md`、`registry/README.md`（顺便修正过时计数，C21）、`tooling/README.md`。
- 只动文档，`make check` 不受影响。

**第 1 批：检查器先行，不动规格内容。**
- catalog 加修订号字段，初值取现有 vN。
- `_frozen` 改为「哈希对应当前已接受修订」，并新增与接受声明哈希的比对。
- `--previous-frozen` 的只追加语义改为「修订号只增」（C2）。
- 新增三项判定，先只报告：
  - 一份契约只有一个版本条目；
  - 依赖与 bindings 的「核对于修订 N」对账；
  - 模型没有任务覆盖（C19，文档说会判失败而代码没有）。
- 补删版本、原地修订的测试（盘点 4.7：现在没有）。
- `frozen.json` 保持 `files{path: sha}` 的形状，避免打断直接读它的两处测试：`packages/core/stream-assembly/tests/fixtures.spec.ts` 和 `tools/core-verification`。
- 树不变，检查保持绿。

**第 2 批：语义收敛，按依赖拓扑自底向上，一份契约或一簇一个提交。**
- 2a 定留存版：
  - organization-governance 先由负责人裁出一份合并后的正文。它的三条线都被最新版消费（我按 catalog 核的）：
    - v1：model-profile-directory v5、asset-governance v2；
    - v2：account-registration v2、governance-client-operations v2、governance-center-entry v3；
    - v3：asset-transfer v2。
  - 这是设计工作，不是迁移。
  - 其余契约留数字最大的一版，但要核它是否自足。迹象：offer-expiry v2 正文写「前版列出的四类」，大小 10.7 KB 对 v1 的 48.8 KB；account-identity v3 是 105 KB 对 v2 的 203 KB。
- 2b 形式化归位：
  - 只在旧版里有的 28 个工件搬进留存版并登记任务；
  - MRR 旧版任务所检的模型，在 v12 里有字节相同副本的，改指 v12 并去重；
  - 字节不同的 4 个 final-plan 任务，裁定哪份是正版。
  - 以上数字出自盘点 7.1、7.2，我只核了 v12 是「13 个模型、2 个任务」。
- 2c 原地改最新版的依赖、`$ref` 和链接（119、31、918），让它们指向留存版。
  - 逐条用 catalog 的 `clauses` 核对：被消费的条款在留存版里是否同号同义；不等价的走设计修订，不机械改指。
  - 有随包 Schema 拷贝的数据契约，包内拷贝必须在同一提交里同步，否则比字节的测试会红（例如 `versioned-schema.spec.ts`）。
- 2d 把只在旧版上有覆盖的 80 个需求条款迁到留存版（盘点 C13，未复核）。
- 每个提交内升修订号、更新哈希、写 changelog。

**第 3 批：消费者离开旧版，按节点或包分批。**
- bindings 的 268 行：
  - 条款在留存版同号同义的，改坐标并更新 `alignment_checked`；
  - 不同的，保留证据但标「核对于旧修订，待复核」，如实下调节点状态，不机械重绑。
- 两个应用 `architecture.md` 里的 16 个旧坐标。`check_coordinates` 会核它们在不在 catalog 里，所以必须早于第 4 批。
- 约 25 个读旧规格的测试、约 20 份随包 Schema 和包的导出子路径。
- 规格 topic 的 README 与 verification、实现映射、产品投影、`record/` 里指向旧版目录的链接。`record/` 里的改成「坐标文字加提交号」。
- 删除之前，在登记里记下每个旧版最后存在的提交，供证据回溯。

**第 4 批：删旧版。**
- 65 个目录连同它们在 catalog、frozen、formal-tasks、covers 里的条目，在同一提交里删除（C1）。
- 处置 `version-migrations.json` 和 `model-request-runtime/v-next/`。
- 「一份契约一个版本」由只报告升为判失败。

**第 5 批：机械去掉路径里的版本段，单个原子提交。**
- 用脚本统一改写：`git mv`、`$id`、frozen 键、任务路径与 ID、检查器的路径规则、代码路径、全部链接。
- 验证方法：除路径替换外，内容逐字节相同。
- 先处理撞名：盘点称有 10 个版本目录自带 `verification.md`，会与 topic 根下的同名文件冲突。

**最危险的是第 2 批（2a 和 2c）。**
- 它是唯一一批「含义可能悄悄变了而检查全绿」的：检查器只核链接可达和哈希一致，不核条款是否等价；盘点第 10 节也承认语义层面没有判断。
- 第 1 批刚把 `frozen file changed` 这张机械安全网换成流程门，第 2 批正好在没有它的时候做语义改动。
- 建议第 2 批每个提交都过设计评审（判表达），organization-governance 的合并单独过负责人。
- 其次危险的是第 3 批的 bindings，因为检查器不核条款坐标。

## 6. 没核对到的事实与结论所依赖的假设

**没有核对的事实**：
- 没跑任何检查，所以「每批之后保持全绿」是按检查器代码读出来的推断。
- 以下盘点数字我没有复核：
  - `$ref` 的 31 条边；
  - bindings 268 行与「13 个节点只绑旧版」（只核了 MRR 一个节点）；
  - 约 25 个测试、约 20 份随包 Schema；
  - 28 个只在旧版的形式工件、61 个字节相同的任务；
  - 80 个只在旧版有覆盖的条款；
  - 投影 3803 个链接；
  - acceptance 里的 587 个旧哈希；
  - 4599 处悬空文字引用。
- 我的链接计数口径与盘点不同：我把旧版目录里的源文件也算进去了（指向旧版的得 10944，盘点是 9320），只能当量级用。
- 没有判断任何一对新旧条款是否语义等价，也没有逐份确认最新版是否自足。
- 没读手册的「规格演进」一节，也没读产品投影的版本规则。

**负责人需要补的两个裁决点**：
- 投影模板写「旧版本保留，不删除」，这次裁决是否也管投影的旧版，我不知道。
- organization-governance 三条线怎么合成一份，需要设计裁决。

**结论依赖的假设**：
- 正式发布前「破坏性重构、不留兼容」的阶段政策持续有效（根 AGENTS.md）。若很快要对外发布并支持多版本并存，反证三的分量会明显加重。
- 「旧字节在 Git 历史里」要求 main 的历史不被改写、被引用的提交一直可达；我没有核对现有 `snapshot_commit` 是否都还可达。
- 负责人接受「修订号接着 vN 往下数」，并接受新写两样东西：依赖与 bindings 的对账器、接受哈希门。没有这两样，反证一成立，乙不如维持现状。
