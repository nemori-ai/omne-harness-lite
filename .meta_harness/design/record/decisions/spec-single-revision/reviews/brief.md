## 要你判断的事

裁决要落成一条长期规则。有两种候选的**终态**。两者都满足「树里每份契约只有一版」；差别在于「版本」记在哪里、修订怎么做。

### 方案甲：保留带版本号的路径，发布新版的同时删掉旧版目录

- 路径仍是 `spec/{family}/{topic}/v{N}/…`；坐标仍是 `<contract_id>/v<N>`；Schema 的 `$id` 仍含 `v{N}`。
- 修订 = 新建 `v{N+1}/` 目录（形式工件与任务随之带过去），**同一次变更里**把全部消费者迁到 `v{N+1}`，并删除 `v{N}/` 及其登记。
- 「冻结」的含义不变：一个版本目录一经发布，字节不再变；要变就出下一版。
- 任一时刻每份契约只有一个版本目录；旧字节在 Git 历史里。

### 方案乙：路径去掉版本号，原地修订，修订号记在登记里

- 路径改为 `spec/{family}/{topic}/…`（没有 `v{N}` 段）；契约身份是 `<contract_id>`；修订号是登记与正文抬头里的一个字段
  （与本仓库产品设计 topic 现在的 `revision` 同一做法：一份正文、一个修订号、一份 changelog）。Schema 的 `$id` 不含版本。
- 修订 = 原地改正文与形式工件，升修订号，记 changelog，过接受门；登记里的哈希随修订更新。
- 「冻结」的含义改为：登记的哈希对应「当前已接受的那一修订」；字节变了而修订号、接受记录没跟上，判失败。
- 消费者按契约身份与条款号引用；需要精确性的消费者（实现映射的 bindings、投影的 provenance）记「核对于修订 N」，
  修订升了由对账器把没复核的列出来（本仓库对产品 topic 的 rev 已有这样一个对账器）。旧字节在 Git 历史里。
