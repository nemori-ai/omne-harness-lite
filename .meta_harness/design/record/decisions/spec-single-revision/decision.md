# D-113：规格只留最新一版——路径去掉版本号，原地修订，修订号记在登记里

- 当前状态：**方向与过渡规则已接受，自本记录起生效；切换尚未执行。**在[第五节](#五分批与现在做到哪)的切换那一批完成之前，树里仍是带版本号的目录，检查器仍按「冻结字节不可改」判。
- 来源提案或研究：[现状盘点](inventory.md)（44 份契约、109 个版本目录、65 个旧版，二十三条约束）；三份[独立评审](reviews/README.md)（同一份中立简报、强制二选一，三份都选了本记录接受的那一种）。两种终态的比较就在评审简报与三份评审里，没有另立提案包。
- 需求或方法前提：发布前的阶段政策——依据新规格直接做破坏性重构，不为旧版保留兼容过渡；发布时重新制定兼容与迁移规则。
- 实际接受依据：负责人（产品与架构负责人）2026-10-01 在「整洁之道各条取舍」的问答里写下「只留最新一版、旧版及时丢弃、形式化正版持续维护」，原话见第一节。**终态取哪一种、过渡期怎么走、分几批，是主会话在他当晚的授权下定的**，逐条列在下面供他回看，不同意哪一条改那一条即可。

## 一、裁决原话

> 规格不作长期权威保存，但这个意思是永远只保存最新一版的规格，被覆盖的旧版及时丢弃避免认知负担，同时形式化正版需要持续维护保存

同日确认过的转述：规格仍是权威，不是一次性的；被取代的旧版及时删除；形式化的正版（TLA+、Alloy、JSON Schema）持续维护保存。

## 二、接受了什么

**终态：每份契约在树里只有一份正文，路径里没有版本号；修订在原地做，修订号记在登记里。**

1. **路径与身份。**资源位置是 `spec/{family}/{topic}/…`，契约身份是 `contract_id`。Schema 的 `$id` 不含版本。
2. **修订。**原地改正文与形式工件，升修订号，写 changelog，过接受门；登记里的哈希随之更新。**修订号接着现在的版本号往下数**（现在是 v12 的，下一次修订记 13），已发生的记录里「某契约 vN」的说法因此仍然对得上。旧字节在 Git 历史里，登记记下每个修订对应的提交。
3. **冻结的含义。**登记的哈希等于「当前已接受的那一修订」的接受声明里的哈希。字节变了而修订号与接受声明没跟上，判失败。这道门把「改字节、重算哈希、悄悄过检查」拦在接受记录上——接受声明在只追加的 `record/` 里，必须是新增的一份。
4. **消费者怎么引用。**按 `contract_id` 与条款号引用；**条款号永不复用**。需要精确性的消费者——契约之间的依赖、实现映射的 bindings、需求覆盖、投影的来源——各记「核对于修订 N」。契约一修订，对账器按**被改动的条款**点名消费了它们的人；不复核就批量改号等于把这道检查关掉，与产品 rev 的规矩相同。
5. **形式化正版。**模型与任务的路径不再随版本变，登记一次一直有效。**每个模型要么有任务，要么写明为什么不跑**，缺了判失败。
6. **起草中的修订不进主线的树。**修订在分支上做，合入即接受；`v-next/` 这种与已接受正文并存的候选目录退役。并行分支撞了修订号，后合入的一方重编。

## 三、为什么是这一种

候选有两种终态，都满足「树里每份契约只有一版」：

- **甲**：保留带版本号的路径，发布 `v{N+1}` 的同一次变更里迁完全部消费者并删掉 `v{N}`。
- **乙**：上面接受的这一种。

三份独立评审都选乙，理由互相印证，反证各不相同：

| | 事实 | 出处 |
|---|---|---|
| 甲的致命处 | 版本号写在路径里，引用就写进了别的契约的冻结字节；「删旧版」与「冻结字节不变」叠在一起，修订一份契约，引用它的契约都得跟着出新版，再传下去。按依赖图算，修订一份底层数据契约要带动 40～43 份（共 44 份） | 三份评审各自独立算出 |
| 现状就是证据 | 最新版指向旧版的依赖 119 条、Schema 引用 31 条、链接 918 个——都是过去靠「消费者继续钉旧版」躲连锁留下的；这次裁决取消的正是这条退路 | 盘点第 1 节 |
| 形式化已经漂了 | 模型请求运行时 v3～v11 的 65 个任务里，61 个所检的模型在 v12 里逐字节相同，v12 却只登记了 2 个任务；最新版里有 13 个模型没有任何任务 | 盘点第 7 节 |
| 与别处一致 | 产品 topic 早就是「一份正文、一个修订号、一份 changelog、按 rev 引用、对账器点名」；只有规格一区是另一套 | `design/product/`、两个对账器 |

**乙的代价，以及拿什么兜**（评审提出的反证，逐条认下）：

| 反证 | 怎么兜 |
|---|---|
| **静默漂移**：路径不变，条款含义变了，引用照样解析得到。今天 bindings 的条款坐标没人核，依赖没有复核戳 | 对账器（按条款点名）、条款号不复用、bindings 条款坐标的检查——**这三样是切换的前置条件，没建成不切换** |
| **冻结从机器保证退成流程保证**：此前有决定明文反对「重算哈希让冲突消失」 | 第二节第 3 条的接受声明哈希门；签署权仍在人 |
| **一份正文容不下并存的候选**；并行修订会撞号（产品 rev 撞过两次） | 修订在短分支上做、逐卡合入；撞号后到者重编 |
| **迁移面大**，且推翻了「这一层目录结构不变」的声明 | 语义上的改动先在现行规则下拆小做完，最后一次机械换形用脚本逐文件证明「新字节＝旧最新版字节去掉版本段」 |
| **发布之后**不带版本的 `$id` 分不清数据属于哪个修订 | 现在是发布前，不留兼容；发布时重新制定兼容与迁移规则那一步里一并定 |

**关于简报的对等性**：两份评审指出简报对乙多写了一句「本仓库已有这样一个对账器」的先例，而那个对账器只管产品 rev 的引用，规格的对账器还得新写；一份指出甲的描述漏写了「全部消费者包括别的契约的冻结字节」。这两处偏差方向相反，三份结论都是在指出它们之后给的。

## 四、过渡期的规矩（自本记录起，到切换完成）

1. **现行机制继续运转**：新版本仍落成 `v{N+1}/` 目录，冻结字节仍不可改，检查器照旧判。这是过渡机制，不是终态。
2. **「钉旧版」这条退路关掉**：新写或新修订的契约、bindings、覆盖登记、形式任务，一律指向各契约的最新版；不再新增指向旧版的引用。
3. **旧版目录是一笔要还的债**：`make spec-retention` 列出每个旧版目录还被谁消费（依赖、覆盖登记、形式任务、绑定行、链接），按最容易迁走的排在前面。它现在只报告、不拦合并；要不要设一道「旧版个数只减不增」的门，等批 2 开工时再定——现在就设，会把正常的契约修订卡死。
4. **消费者迁完的旧版就删**，连同它在各登记里的条目，在同一次变更里。**眼下没有一个旧版满足**：65 个旧版每个都还被登记或链接引用着，其中 `record/` 里的链接按规矩不改，要等切换那一批统一处置。所以过渡期里实际能做的是把登记与绑定里的引用迁走（批 2），目录的删除集中在批 4。
