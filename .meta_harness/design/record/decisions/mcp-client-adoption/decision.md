## 理由与保留前提

**理由**（取自[提案推荐](../../proposals/mcp-client-adoption/alternatives.md#推荐与仍待区分的事项)，产品负责人未另述理由）：
A 与 SYS-KERNEL 正面相抵（连带六个 DSH 包与 `dsh-tools` 工具契约）且有四处结构性反例（断连预算耗尽即撤销登记、跨租户共用一份凭据、run 中途被推送换代、连接挂 Agent）；
B 与 C 用同一个 SDK，差别只是要不要 fork 400 行连接监督，而那 400 行的所有权模型正是按持有分连接要换掉的一层；
D 所借形状的来源 Codex 自己建在官方 Rust SDK 上，论证的是 C 不是 D。
产品负责人「复用社区通用做法」的裁决在协议层就是官方 SDK。
stdio 落点取「一律据点机」的依据是第三轮研究：逐服务端选落点的同行只有 Codex 一家且为实验性、自家协议，其余全部在客户端进程所在机拉起。

**保留前提：**

- **SDK 是一般第三方依赖**，精确钉版、不用 `^` 宽范围（DSH 声明 `^1.12.0` 的教训）；协议版本跟进全靠 SDK 节奏。
- **OAuth 的桥接方向已接受，但三件产品面事项未闭合**（授权流程、令牌归属、刷新与持久化）；它们闭合之前 OAuth 一格只能停在设计，不能开工；本决定不替它们填默认。
- **elicitation** 在等待态与决策卡片契约就位前不向对端声明——这是协议层可观察的显式排除，不是默认开。
- **连接与 stdio 子进程的宿主**归架构设计；本决定不预设宿主（提案 C 路径的读法）。
- **上一次清单的持久副本**按 [D-026](../infrastructure-persistence-choices/README.md) 落持久存储；从未连上过的接入点没有清单，归产品（PF-002 接入流程），本决定不填。
- 提案用的「薄桥」「替换件同形」是描述性说法，**不是统一语言词条**；接入点连对端的那份凭据**没有词条**，进规格前由词表 owner 立词。
