# clock 实现设计

## 实现路径与来源

**自建一个小的 Cordis 插件，不依赖第三方时间库。**要兑现的只有一句话——「先后两次 `now()` 后者不小于前者，跨重启也成立；钟往回倒了——启动时或运行中——就不服务，直到追上」——没有可复用的实现；能复用的是 Node 内置的 `Date.now()`（墙钟），以及经 `storage` 服务写一行高水位。

### 高水位为什么是写在前的租约，不是写在后的节流

高水位若写成「已读到的最大 `now`」——读出之后再推进——写在后的高水位有一条反证：

> 实例在 `t` 返回 `now = t`，节流窗口内尚未写高水位；进程崩溃；墙钟被调回 `t − 1s`；重启读到高水位 `h < t − 1s`（上一次节流写的值），锚检查 `Date.now() ≥ h` 通过；新实例返回 `t − 1s < t`。**后退发生了，而检查没响。**

写在后的任何节流宽度都留这个窗口；`now()` 是同步的，又不能在每次返回前 `await` 一次写。所以把写挪到**前面**：

|          | 写在后 + 节流（落选）                                                  | **写在前的租约（选）**                                                                                                                      |
| -------- | ---------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| 最强论证 | 简单；写频率与调用频率解耦；无「租约到期」这种新状态                   | 崩溃窗口不存在：返回值永远 ≤ 已落盘的界                                                                                                     |
| 弱点     | 上面的反证；只有在「崩溃前一定来得及写」的前提下成立，而那个前提没人给 | 空闲时也要每 L/3 写一次（否则空闲后第一次调用撞上过期租约）；崩溃后快速重启要等至多 L；多一列 `written_at` 才能把「回拨」与「快速重启」分开 |
| 置信度   | —                                                                      | 高：不变量只有一条且每一步都能对照它检查；两个常量的取值是政策，机制不依赖具体值                                                            |

**常量**：租约宽度 `LEASE_WIDTH_MS = 10_000`（L = 10 s）、续约周期 `RENEW_PERIOD_MS = floor(L/3)`。本版 `clock` **无可调 config**（`ClockConfig` 是空的严格对象，多给任何键即 config 校验不过）——两个常量写死在包里；要可配时加 config 并走同一条「非法即启动失败」政策。

**表与迁移（本包自带）**：一张单行表 `clock_lease`（`CLOCK_LEASE_TABLE`）：`id INTEGER PRIMARY KEY CHECK (id = 1)`、`lease_until BIGINT NOT NULL`（毫秒）、`written_at BIGINT NOT NULL`（毫秒；pg 的 `integer` 只有 4 字节，毫秒时刻必须 `bigint`，pg 驱动把它读成 string，读出时归一为 number、非安全整数即抛）。迁移片段 `clockMigrations`（`readonly MigrationFragment[]`，恰一个片段 `clock_lease`，只带 `up`）从本包导出，**由装配经 `composeMigrations` 合进它传给 `storage-sql` 的 `MigrationProvider`**；建表带 `IF NOT EXISTS`，不引用任何别的表，与其他迁移次序无关。同一迁移另以 `clockLeaseMigration`（带 `up`／`down` 的 Kysely `Migration`）导出。

**三条写（SQL 形状，实际经 Kysely 构造；每条写先 `lockRow('clock_lease', { id: 1 })`）**：

| 时机           | 语句                                                                                                               | 守卫                                                                                                                                                                                                                                                                        |
| -------------- | ------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 启动，行不存在 | `INSERT (1, w + L, w)`，`w` 为此刻墙钟                                                                             | 主键冲突（`UniqueViolation`）⇒ 另一实例已建 ⇒ 同一事务内转读                                                                                                                                                                                                                |
| 续约（定时器） | `UPDATE SET lease_until = w + L, written_at = w WHERE id = 1 AND lease_until < w + L`                              | 只增不减：另一个更快的写者已推得更远、或墙钟正落后（`w + L` 不超过现有界）时本次不写——单实例运行期间行里 `lease_until = written_at + L`（撤除写下的是 `(x, x)`，下一实例启动时的那次续约改回这个形状），所以 `written_at` 在行上也只增不减（两个实例共用一行时不保证，Q-8） |
| 撤除           | `UPDATE SET lease_until = x, written_at = x WHERE id = 1 AND lease_until = <本实例最后写下的值>`，`x = max(hw, w)` | 比较并写：只收回**自己**推出去的租约；别人推过就不动——快速重启因此不用等。取 `max(hw, w)` 而不是 `w`：撤除时墙钟若正落后于 `hw`，写 `w` 会把「用过的最晚时刻」往回改，下一次启动就查不出这次回拨                                                                            |

写都在 `storage.write` 里，一条语句一次提交，不与任何业务行同事务；**没有跨 owner 的「同一提交」**，这一行只有本节点写。

### 运行中回拨：每次现读墙钟，比对用过的最晚时刻

入口契约 S-36 末行要时钟的提供者在**运行中**检出回拨，让要看时间的答不可用，[PF-017 §6.10](../../../../product/PF-017-governance-center-as-deployable-application/design.md#610-时间不能倒着走)（PF-017 rev 1 已接受（2026-09-23））第 2 行要「直到钟追上中心用过的最晚时刻」，并让运维者在完整体检里看得见（`clockSane`）。
按单调钟推算的 `now()` 不随墙钟后退，所以**本来就不会用更早的时刻**——但它也就看不见回拨：照常答一个已偏离墙钟的时刻，`clockSane` 一直是 `true`。本节点让 `now()` 每次现读墙钟、比对 `hw`：

|          | 单调钟推算 + 定期比对墙钟，差值超阈值即不可用、追上后重锚（落选）                                                                                                                                                                                                                  | **每次 `now()` 现读墙钟，比对用过的最晚时刻 `hw`（选）**                                                                                                                                                                           | 不检出，写成缺口（落选）                                                                                                                                                                                                           |
| -------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 最强论证 | 机制最小：只在续约定时器里加一段比较；阈值挡住墙钟的细小抖动，不会为几毫秒的回拨答不可用                                                                                                                                                                                           | 检出零延迟，「追上」的判据就是 PF 那句话本身；**启动时的旧租约窗口与运行中回拨是同一条规则**（`w < hw`）；墙钟往前走（校时步进、休眠恢复）立刻跟上，不再有「推算值落后墙钟、直到重跑」那条超长期待机下的常态边界；没有阈值常量要定 | 零改动                                                                                                                                                                                                                             |
| 弱点     | 检出最迟晚一个周期（L/3 ≈ 3.3 s），其间照常答一个已偏离墙钟的时刻、`clockSane` 仍是 `true`；阈值要吸收单调钟与墙钟之间的漂移，取值取决于平台上两者是否同受校时调频（**假设，须按 source-check 取证**）；要不落后于墙钟还得再加「向前重锚」——加上之后它就是右边这一列多了延迟与阈值 | 任何幅度的回拨都答不可用（毫秒级回拨 ⇒ 毫秒级不可用）；墙钟向前跳过租约界时有至多一个续约周期的不可用（下表）                                                                                                                      | 入口契约 S-36 末行、S-26 `clockSane`、S-32 前提 P3「时钟未倒退」的运行中那一半都没有承接者，[governance-center-entry N-5](../../tenancy/governance-center-entry/design.md#实施缺口与消费者影响) 不闭合；PF-017 §6.10 第 2 行不成立 |
| 置信度   | —                                                                                                                                                                                                                                                                                  | **中高**：只多一条不变量「返回值 ≥ `hw`」，每一步都能对照；平台假设只影响代价，不影响正确性                                                                                                                                        | —                                                                                                                                                                                                                                  |

### 启动时的租约窗口与入口层等钟

- 启动判定之后，`hw` 起始为：首次建行 ⇒ 此刻墙钟；接手既有行 ⇒ **旧行的 `lease_until`**——前一个实例可能已返回到那里。于是崩溃后快速重启时墙钟落在 `[written_at, lease_until)`，`now()` 答 `'unavailable'` 直到 `w ≥ lease_until`：**等待至多 L − (w − `written_at`) ≤ L = `LEASE_WIDTH_MS`**——续约写下的行满足 `lease_until = written_at + L`；干净撤除写下的行 `lease_until = written_at`，不等。
- 这段不可用与运行中回拨走同一条规则，对外都只是返回值（S-34）；插件在启动判定之后照常 provide，不把「还在窗口里」做成面缺席。
- 窗口结束那一刻租约界已经在前面：启动判定之后插件体 `await` 过一次续约，把界推到启动时刻 + L（≥ 旧 `lease_until`）；墙钟与 `written_at` 恰好相等、那次续约没推动时，界等于旧 `lease_until`，窗口结束那一刻仍读得到，下一次定时续约早于它把界推开。
- 入口层在开门之前等 `now()` 给出一个时刻，上界 `clockReadyTimeoutMs` 由装配给（[tenancy-host 其余 config](../../../apps/tenancy-host/design.md#其余-config候选变量名)、[governance-center-entry「谁来等钟」](../../tenancy/governance-center-entry/design.md#中心标识版本与启动时刻怎么到达运维面)），**必须严格大于 `LEASE_WIDTH_MS`**：等待从本插件 `ACTIVE` 之后才开始、剩下的窗口只会更短，严格大于保证窗口恰为 L 时入口层在窗口结束之后还读得到一次。所以快速重启只是慢起，不会启动失败。
- 超界仍读不到只有三种来路，都应当启动失败：续约一直写不进（存储不可用）、等待期间墙钟又往回倒了、存储缺陷闩住了本实例。入口层把原因说成「钟」，三者在本节点的日志里分得开。
- **一条读法**：上一次是崩溃退出、且启动时的回拨幅度小于窗口，本节点分不出「回拨」与「快速重启」，按快速重启等到追上再服务——「不用比用过的最晚时刻更早的时刻」仍成立，PF-017 §6.10 第 1 行「启动时钟比它早就不起来」在这一窄带里读作「追上之前不起来」。上一次是干净撤除时 `written_at` 就是用过的最晚时刻，任何回拨都是确定回拨、启动失败。

### 迁移前的只读回拨核对

tenancy-host 要在迁移之前、不碰数据地核一次「钟比中心用过的最晚时刻早」（[tenancy-host R-U1](../../../apps/tenancy-host/design.md#升级的整体性迁移前只读核对快照与确认)）；本包导出 `clockPreflight(sources?: TimeSources) → PreflightCheck`（形状在 [core/storage](../../core/storage/design.md#迁移片段与迁移前核对的共用形状)，语义见 [storage-sql「迁移前只读核对」](../storage-sql/design.md#迁移前只读核对)），由装配放进 storage-sql 的 `upgrade.checks`。

- **判据与启动判定是同一个纯函数**（`isRolledBack(wall, row)`：`wall < written_at`，已导出），不另立第二条规则。
- 读法：`tables` 里没有 `clock_lease` ⇒ 无历史，通过；有表无行 ⇒ 无历史，通过；有行 ⇒ 现读墙钟一次与 `written_at` 比，早 ⇒ `{ ok: false, check: 'clock-rolled-back', detail }`，`detail` 写出两个时刻。「表在不在」由 storage-sql 在同一读事务里读好给它，本包**不以「读表报错」推断「没有表」**。
- **只读**：只经 `ReadTx` 读一行，不建行、不续约。只拒确定回拨；落在旧租约窗口里的是快速重启，交给插件启动之后去等。
- 两处判据一致，所以「核对通过而插件启动时抛出回拨」只可能是两次读墙钟之间钟又往回倒了——那时迁移已跑过，走「全撤 ⇒ 恢复快照」。
- 本包仍是仓库里唯一把墙钟当时间源读的地方（storage-sql 的 sqlite Driver 另用 `Date.now()` 计写锁等待期限，不作时间源）；核对函数在本包里，不越出 `no-wall-clock` 规则对 `infra/` 的豁免。形状取自 `core/storage` 的类型，**不 import storage-sql**。

## 状态、并发与失败映射

**实例状态**（内存）：`hw`（本实例用过的最晚时刻；起始值见[启动时的租约窗口](#启动时的租约窗口与入口层等钟)）、`leaseUntil`（本实例确知已持久化的界）、`lastWritten`（本实例**自己**最后一次写成功的值，接手既有行时为 0——撤除只收回它，从未写过就不动别人的）、`latched`（确定回拨或存储缺陷）、`behind`（当前是否处在「墙钟落后于 `hw`」的一段里，只用于成对记日志）、一个在途续约写的句柄（至多一个）。**持久状态**：`clock_lease` 一行。

**`now()` 的判定次序**（同步，不抛异常）：① `latched` ⇒ `'unavailable'`；② 现读墙钟 `w`；③ `w < hw` ⇒ `'unavailable'`（墙钟落后于用过的最晚时刻：启动时的旧租约窗口，或运行中回拨；进入这一段记 warn、离开记 info）；④ `w > leaseUntil` ⇒ `'unavailable'`（租约没续上——续约写失败、存储不可用、墙钟向前跳过了界，都落这里）；⑤ `hw = w`，返回 `w`。**没有第六种结果**。
不变量两条：任何返回值 ≥ 本实例此前的任何返回值（③⑤）；任何返回值 ≤ 当时已持久化的 `lease_until`（④）。

**续约**（定时器，每 L/3）：在途续约未回来则**跳过本轮**（不排队；约束「L/3 + 写锁等待上限 5 s < L」保证跳过一轮仍在租约内——它假定一次续约至多等一次锁、别的写者持锁以毫秒计：AI 节点的 S-13／S-15 已把凭据计算放在事务外，见[该节点 R-8](../../tenancy/account-identity/design.md#对存储提供者的要求清单)），否则现读墙钟 `w`、发一次 `storage.write`（守卫更新，按受影响行数判是否推进了自己的界）；成功 ⇒ `leaseUntil = w + L`；守卫落空而 `w + L` 大于本实例已知的界（行上的界已被别的写者推到 ≥ `w + L`）⇒ 本实例只认到 `w + L` 为止，不冒领对方推得更远的那一段——仍满足「≤ 已持久化的 `lease_until`」。墙钟正落后于 `hw` 时，这次写推不推得动界取决于 `w` 与行上 `written_at` 的先后，而 `written_at` 在两种情形下都不会被改小：单实例运行期间行上恒有 `lease_until = written_at + L`（插入与续约都这么写；撤除写下的 `(x, x)` 在下一实例启动时的那次续约就被改回这个形状），守卫条件 `lease_until < w + L` 因而等价于 `written_at < w`——`w` 不晚于 `written_at` ⇒ 写落空；`w` 落在 `(written_at, hw)` ⇒ 写照常把界推到 `w + L`（仍大于 `hw`），`written_at` 变大。两个实例共用一行时不保证（Q-8）。失败按存储协议的类型分两支：`StorageUnavailable`（瞬时）⇒ 记一条结构化日志（级别 warn，含 `cause`），`leaseUntil` 不动——墙钟越过它之后 `now()` 开始返回 `'unavailable'`，下一次定时器再试，存储恢复后一次成功续约即恢复服务，不需要重启；`StorageDefect`（表不在、列不对——重试也不会变）⇒ 记 error 日志并 **`latched = true`**，不再重试——定时器没有调用方可把缺陷上抛给，闩住是它唯一能做的「不吞错」。**写不进 ⇒ `'unavailable'`**的路径就是①或④，没有第三条。

**并发**：`now()` 是同步的，JS 单线程下读 `hw`、比较、改 `hw` 之间不会插进别的调用；续约写与 `now()` 不互斥，`leaseUntil` 只在写成功后单调增，`hw` 只在⑤单调增。**跨进程**：两个进程各起一个本插件对同一存储时，守卫 `lease_until < w + L` 让两者只推不缩，各自返回值 ≤ 落盘界；但两个进程的 `hw` 各管各的，**跨进程的先后不保证**——S-17 明写本版单机一个实例，跨进程归 [投影 Q-8](../../../../product/PF-001-identity-scope-and-agent-constraints/projection/v1/projection.md#7-未决项)；同一份库只有一个属主由 [storage-sql 的属主排他](../storage-sql/design.md#排他为什么是随进程死亡释放的锁)在开了升级守卫的部署里给出。

**失败映射**：只有一种对外失败 `'unavailable'`；来路五条（闩住、启动时的旧租约窗口、运行中回拨、续约未成、存储不可用）在日志里区分，对消费者不区分——契约 S-16 只给一个值。

**崩溃与恢复**：进程崩溃时 `lease_until` ≥ 一切已返回值，重启走启动判定。**操作系统崩溃或断电时这一条不成立**：落盘的界可能退回到上一次检查点附近——空闲时可达约 55 分钟之前，实际由操作系统的回写延迟决定；重启时墙钟若落在丢掉的那一段里，回拨检不出，那一段里的过期与到期判定在同一口钟上复活。窗口、量级的出处与后果见 [R-C2](#对存储提供者的要求清单)；D-027 不承诺这一条。已知边界：检出确定回拨后启动失败，恢复前的不可用时长等于回拨幅度，**无运维出口**（删行等于宣布不可检测）；运行中回拨同理，答不可用直到墙钟追上，重启也绕不过——落盘的 `written_at` 或 `lease_until` 在墙钟前面，重启要么判确定回拨、要么在窗口里等到追上。租约表被人手动删掉 ⇒ 启动当作首次（插入），**这会让「不后退」失守**——那是运维操作，不是本节点能挡的；写进 verification 覆盖缺口。

## 实施缺口与消费者影响

- **常量 `LEASE_WIDTH_MS`、`RENEW_PERIOD_MS`** 的取值是本节点自定、未经政策裁定；无可调 config 是本版选择，要可配时加 config 并走「非法即启动失败」。owner：本节点。
- **回拨的收场形状**：已定为启动期抛出（`ClockRollbackDetected` ⇒ fiber `FAILED` ⇒ 装配启动失败）。落选方「进程照常起来、`now()` 永久 `'unavailable'`」的问题是六条 fiber 全 `ACTIVE` 却什么都不服务——装配「不半开」的政策被绕过，只有日志是信号。消费者在启动失败下看到的是 `PENDING`，那正是「装配没起来」的正确形态。
- **`clock_lease.id` 是 sqlite `INTEGER PRIMARY KEY`**（rowid 别名，不建索引）：storage-sql 的约束名反查对它拿不到 `<table>_pkey`，`start()` 里并发建行撞主键那一支在 sqlite 下会以 `StorageDefect` 而不是 `UniqueViolation` 收场。`BEGIN IMMEDIATE` 下两个实例的建行本就串行、后者读到既有行，该分支不可达，本版无害；pg 下 `SERIAL`／`integer` 主键正常报 `clock_lease_pkey`。装配的迁移纪律因此写明「业务表主键列不得是 `INTEGER PRIMARY KEY`」，本表是登记在案的例外。
- **注入面 `TimeSources { wall, monotonic }`**：`now()` 改为现读墙钟之后 `monotonic` 不再参与任何计算，字段按「注入面只增不改」保留；删掉它是一次注入面的不兼容改动，归本节点与消费它的测试一起做。
- **两条平台假设**（只影响代价、不影响正确性，须按 source-check 取证）：校时服务只在偏差超过其步进阈值时才让墙钟往回跳；Node 的计时器按单调时间到期，休眠恢复之后至多一个续约周期就会触发续约。
- **跨进程不保证先后**：Q-8。
- **包内测试的夹具写 `upgrade: false`**：storage-sql 规定带迁移时 `upgrade` 必须显式给出（[该节点「守卫为什么显式开启」](../storage-sql/design.md#守卫为什么显式开启)）；本包测试带 `clock_lease` 迁移装 storage-sql 时一律显式关守卫（`tests/support.ts`、`tests/plugin.spec.ts`），升级守卫与本包核对的组合由 `tests/preflight.spec.ts` 显式开启守卫来测。与 storage-sql 那一条互指。
- **租约表被外部删除**无法防御，只能观测（启动时行不存在且不是首次部署——本节点分不出「首次」与「被删」，记 info 日志）。owner：装配的运维约定。
- **上游语义**：basis 四条（`plugin-body-reruns-on-provider-change`、`effect-disposal-concurrent-not-ordered`、`isolate-hides-instances-not-data`、`plugin-throw-fails-fiber`）与 kernel-basis 一条不对应条目的 probe（`provide-is-effect-managed`）均已在 4.0.4 上通过；装卸表各行引用它们作证据来源。bindings 仍为空表，因为无契约条款可绑。
- **C-15 严格递增的时刻（[D-040 §八 M58](../../../../record/decisions/mainline-self-rulings-2026-09/decision.md#八实现映射起草反推出的契约修订m31m442026-09-25-追加)，下一程实施）**：资产流转与组织治理 v2 要「先后两次串行提交写下的时刻不相等」（`capability.organization-governance/v2#S-42` 末行、`capability.asset-transfer/v1#S-34`），主线选时钟不选提交序。本节点修订为：同一进程内后一次 `now()` 返回值 ≥ 上一次＋1 ms，其余情形仍等于墙钟读数，偏离墙钟的上界是同一毫秒内的调用次数；`clock.monotonic-in-process` 断言改写为「非递减、每个返回值 ≥ 当时墙钟读数且 ≤ 墙钟＋同毫秒调用数」；租约上界按同一 `now()` 计算，`lease_until ≥ 一切已返回值` 保持。闭合前 [asset-governance](../../assets/asset-governance/README.md) 把依赖它的条款标「有前提：C-15」。owner：本节点。
- **消费者**：AI、OG、入口层、运维面必需 inject `clock`；本节点换代它们重跑，接口形状归 offer-expiry，本节点不改——运行中回拨也只用既有的 `'unavailable'` 表达，不加新的返回值。`apps/tenancy-host` 另消费两样：`LEASE_WIDTH_MS`（核 `clockReadyTimeoutMs` 严格大于它）与迁移前的只读核对。测试装配用可控 `clock`（offer-expiry 演练要求「只许前推」），不用本节点。
