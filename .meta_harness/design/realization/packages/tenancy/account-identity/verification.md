# account-identity 验证与证据

契约侧的证据义务权威在 [`spec/capabilities/account-identity/verification.md`](../../../../spec/capabilities/account-identity/verification.md)——
v1 段（八条规范场景、两条静态检查、若干条没有场景号的注入义务）与 [v2 段](../../../../spec/capabilities/account-identity/verification.md#v2候选的证据义务)（改写或新增的那几行）。
本页按**本节点的兑现点**逐条登记状态，不复述契约的场景正文。

**版本**：本节点按 v2 实现（[design](design.md#实现路径与来源)）。「版本」一列写 `v1＝v2` 的，两版同号条款逐字相同；写 `v2` 的是 v2 改写或新增的。
**以后取得的每一份证据都写明它针对哪一版**：针对本节点实现的演练是 v2 的证据；要把它同时算作钉 v1 的 organization-governance、account-registration 所消费条款的证据，须逐条另行写明（契约 v2 段的继承规则）。

## 覆盖缺口

按上面这次 run 的对应清单，本节点还缺的证据（都针对 v2）：

- **S-32 的 OS 进程重启一支没有 `exchange`**：另起 Node 进程的那条用例按名字只断言 `verify` 得 `login-state-rejected`；`exchange` 那一半只在同一库文件两次装载与同进程整装配重启里有。契约 v2 写「只跑 S-17 不得记作本条的 v2 已验证」——OS 进程重启这一支因此还不算 v2 已验证。owner：本节点 + 装配（`apps/tenancy-host` 的 `process.spec.ts`）。
- **S-47 第 ② 支没有 OS 进程重启**：两条承担者都是同进程重启；「另起进程后同一批出示物 `exchange` 得同一 `LoginStateId`」没有用例。owner：同上。
- **S-35 的规则形式不存在**：identity-values 的 SC-2 不在 `tools/ts-checks` 的 20 条规则里，本包 `scenarios.spec.ts` 的占位跳过；只有类型层一半。owner：identity-values 节点提出规则、`tools/ts-checks` 落规则。
- **S-45 熵下限的实现审阅**不是测试，本 run 不承担；两条文本规则有。owner：本节点（审阅留痕归评审记录）。
- **S-30 新增五行的结构检查**是 design 对照表与评审，没有测试形式；对照已写、**未经评审**。owner：本节点 + 装配节点。
- **「S-16 重复退出 ⇒ `not-authorized`」**没有名字写「重复退出」的用例；相关的是「发起方已失效：S-16 ⇒ not-authorized」一条。owner：本节点（要逐字对上就补一条同名用例）。
- **本包内 10 条跳过的占位**：指向别处的那些事除 S-35 规则形式外都在同 run 里有承担者（见上表各行）；**跳过不是通过**，是否把占位改成指向承担者的注释归本包 owner。

其余不在本 run 证据范围内的：

- **S-39 政策（报 spec owner）**：契约写「变更只影响此后的判定，不追溯地把已经做出的认回或清除改写」。过期事实落盘之后，「定死」与「读时按当前参数算」两种算法都满足单调，差别只在尚未落盘的记录上：调短时前者不提前到期、后者提前；调长时前者不推迟、后者推迟。**这是政策选择，不是机制约束**；v2 没有收口，本节点默认定死，裁为另一种只换一个比较式。
- **契约措辞两处（报 spec owner，不改语义）**：S-30 第 7 行左列「同一时间源 + 同一参数源」描述的是旧的兑现方式，本节点用的是右列的「由单点判定并携带的事实」；S-4「AccountId 产生时由存储生成」本节点读作「在存储提交内生成、由主键约束保证唯一」。v2 两处都未改。另有 S-30 第 4 行「前置检查与写入在同一次提交内」的读法：本节点把凭据计算挪到提交之前、在提交内按同一行确认（[design 实施缺口](design.md#实施缺口与消费者影响)），若契约本意是计算也在提交内，须收口。
- **v2 的版本坐标**：本页的义务对着提交 a990202 的 v2 正文登记；registry 现把 v2 记为 `accepted`（接受依据 `governance-center-design-acceptance`）。S-45 交换表示的上界 1024 若将来改值，S-44 ⑤ 的边界支跟着改。
- **Node 两条假设**（`randomBytes` 失败即抛出、`base64url` 不带填充）：basis 只收 Cordis，按 source-check 取证之前，分别由「随机源不可用」注入与「出示物的形状」单测守。
- **v1 数据的收场**：[存储形状](design.md#持久记录的存储形状与迁移片段)一节的前提（没有按 v1 行为签发的行）不成立时怎么收，没有证据形式，也没有 owner 的裁决——报产品负责人与 spec owner。
- **S-30 右列协议给保证（十四行）**：本版一条也不兑现，也没有证据形式；跨进程演化时逐行重开。
- **S-21 前提**（一切交互经 S-17 或 S-44）、**S-25 另一半**（其他 owner 的数据）、**G-4 运行控制**：不在本节点。
