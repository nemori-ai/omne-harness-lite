## 实现路径与来源

**自建一个包、两个插件。**契约是本项目自己的线上投影，没有可采用的现成实现；能复用的是下表的构件。
形状依据[提案 `governance-center-entry`](../../../../record/proposals/governance-center-entry/README.md) 的[候选 A](../../../../record/proposals/governance-center-entry/alternatives.md#候选-a)：
入口层一条 fiber、运维面同包另一条 fiber，两条都不 provide、装在装载清单最后；
为什么入口层不拆成三扇门、监听与判定不拆、不并进装配、不并进任一领域插件、运维面不并进入口层、中心标识不进 ctx、认人不走事件、入口层必须 inject，

## 插件边界、服务面与三处关键选择

| 插件（候选名）                      | inject（全部必需）                                                                                                                    | provide | 取得的资源                                                                                              | config（候选字段；非法 ⇒ 启动失败）                                                                                                                                                                                                                            |
| ----------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- | ------- | ------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `governance-center-entry`（入口层） | `logins`、`registration`、`organizations`、`memberships`、`offers`、`storage`、`credentials`（只用 `parse`）、`clock`（只在启动时用） | **无**  | 一个 TLS 监听（effect）；启动时读或铸中心标识一次、等钟可读一次；插件体返回后等 `openSignal` 兑现才开门 | `listen`（地址与端口）、`tls`（证书链与私钥 PEM）、`version`（中心所装版本）、`drainTimeoutMs`（排空上界，正整数）、`clockReadyTimeoutMs`（等钟的上界，正整数）、`openSignal`（装配传入的 Promise，兑现即「可以开门」；缺席或不是 thenable ⇒ config 校验不过） |
| `governance-center-ops`（运维面）   | `storage`、`clock`                                                                                                                    | **无**  | 一个本机套接字监听（effect）；三条通知的监听者；装载时发一次 `listening`                                | `socketDirectory`（绝对路径）、`deploymentKey`（`{ present: true, complete: true }`，只收字面 `true`）、`deploymentParameters`（五项正整数毫秒）                                                                                                               |

- **入口层不 inject** `accounts`（S-13／S-14／S-18／S-38 不投影，[S-24](../../../../spec/compositions/governance-center-entry/v1/contract.md#s-24-有意不投影)）、
  `organization-purge`（S-53）。`credentials` inject，但**只调它的 `parse`**，不碰 `derive`／`verify`／`checkPolicy`，见下面第一张表。
  `clock` inject，**只在启动时用**：启动成功以中心的钟可读为条件，入口层就绪之前等它可读一次、开门那一刻再读一次作 `startedAt`（[下文](#中心标识版本与启动时刻怎么到达运维面)）；请求处理不读钟，客户端的钟从不参与判定。
- **就绪与开门分两步**：插件体绑好端口（不受理）、标识就绪、钟可读之后**返回**，fiber 随之 `ACTIVE`；开门挂在装配给的 `openSignal` 上，装配在全部 fiber `ACTIVE` 且升级快照确认之后兑现它（[下文](#就绪与开门为什么分两步)）。
- **运维面不引用任何治理服务**：它的源码目录只许导入 `kernel-basis`、`storage` 协议、`offer-expiry`、Node 内置与本包一个不导入任何 `tenancy/*` 包的事件声明模块（导入白名单，SC-2 的兑现形式，[下文](#本节点约束存储要求之外)）。
- **四条通知**都用 `emit`（通知，不是控制；返回值被丢弃，[`async-control-not-bail`](../../../../basis/cordis/async-control-not-bail.md)）：
  `governance-center-entry/serving`（候选名，载荷 `{ centerId, version, startedAt }`，入口层开门前发一次，见到下一条时再发一次）、
  `governance-center-entry/stopped`（候选名，无载荷，入口层关门时发一次）、
  `governance-center-entry/defect`（候选名，**无载荷**，每记一次缺陷发一次）与
  `governance-center-ops/listening`（候选名，无载荷，运维面每次装载时发一次；入口层若正开着门就重发 `serving`）。不落存储、不经服务；本版不开任何控制类事件，认人是一次显式调用。
  运维面只在 `serving` 与 `stopped` 之间应答——**两张面同起同停**；第四条让两者被各自重跑、次序不定时仍能对上（[下文](#运维面重跑之后怎么恢复应答)）。
- **accepted_protocol_versions 是包内常量**（候选 `ACCEPTED_PROTOCOL_VERSIONS`，非空；候选值 `["1"]`），不是 config：
  哪些线上协议版本对得上，由本包的路由表实现了哪些版本决定；做成 config 就让装配能宣称接受一个代码没实现的版本。
  它随本包版本定下、运行期间不变，[S-8](../../../../spec/compositions/governance-center-entry/v1/contract.md#s-8-协议版本与跨版本不变的两样)「缺即启动失败」因此在结构上不会发生；
  `version` 是中心所装版本的标识，归装配给值。二者的对应关系（S-18 末句）本节点的选择是：没有推导关系，各是各的。

### `credentials`：必需 inject，只用 `parse`

注册与登录的载荷里有凭据材料。线上它是一个非空字符串，内部格式归凭据方案的 owner；
[S-19](../../../../spec/compositions/governance-center-entry/v1/contract.md#s-19-免认人的两条路由注册登录) 要入口层自己做它的表示层校验，且规则与账号能力提供者判凭据材料的规则**同源**。
那条规则只在可整体替换的 [`credentials.parse`](../credential-verification/design.md#能力到-cordis-的投影) 上；解析不过 ⇒ `invalid-input`。注册那一支尤其不能省：交进去再被判不合格，收场是 `interrupted`，契约明令不交。
入口层对 `credentials` **只调 `parse`**，`derive`／`verify`／`checkPolicy` 仍只由账号能力调用（结构检查，[本节点约束](#本节点约束存储要求之外)第 7 条）。

|          | `resolveOptional(ctx, 'credentials')` 调用时解析（落选）                                                                                                                                                   | **必需 inject（选）**                                                                                                                                                                                                                                                                    |
| -------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 最强论证 | 凭据形式是本域唯一整体替换的地方，账号能力对它就是调用时解析（[account-identity 的理由](../account-identity/design.md#s-15-归本节点credentials-作可选依赖在调用时解析)）；换认证方式时入口层不重跑、门不关 | [S-34](../../../../spec/compositions/governance-center-entry/v1/contract.md#s-34-起来即整体停机时在途请求归谁)：入口层用到的面缺席，客户端一面整体不应答；不会出现「凭据提供者缺席时注册与登录答 `unavailable`、别的路由照常」这种局部半开。同源由「调的就是同一个实例」兑现，不复制规则 |
| 本方弱点 | 凭据提供者缺席期间注册、登录的凭据表示层判不了，只能答 `unavailable`，其余照常——局部半开                                                                                                                   | 换凭据提供者 = 入口层卸载重跑，门关再开（换代期间新请求问不到，在途跑完）                                                                                                                                                                                                                |
| 置信度   | —                                                                                                                                                                                                          | 高                                                                                                                                                                                                                                                                                       |

### 中心标识、版本与启动时刻怎么到达运维面

运维面装在入口层之前，而中心标识由入口层在自己的插件体里读或铸；两张面**同起同停**：运维面只在客户端一面应答的那段时间里应答。
完整体检要的 `centerId`、`version` 是「启动时载入的那一个」，`startedAt` 是「这一次启动成功的时刻」——即入口层开始分派的那一刻（[S-34](../../../../spec/compositions/governance-center-entry/v1/contract.md#s-34-起来即整体停机时在途请求归谁)）。
**启动成功以中心的钟可读为条件**：入口层在插件体里等 `clock.now()` 给出一个时刻，上界是 config `clockReadyTimeoutMs`（候选名，装配给值），超界 ⇒ 插件体抛出 ⇒ 启动失败；
`openSignal` 兑现、开门那一刻**再读一次**，那个时刻就是 `startedAt`，随 `serving` 通知交给运维面（为什么读两次见[下文](#就绪与开门为什么分两步)）。

|          | 运维面自己读 `governance_center`（落选）                                                         | 装配经 config 传给运维面（落选）                                                                                                                                | **入口层开门前 `emit serving`、关门时 `emit stopped`（选）**                                                                                                          |
| -------- | ------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 最强论证 | 运维面不依赖入口层起没起来；重跑后可自取                                                         | 与部署参数走同一条路，运维面只读 config                                                                                                                         | 标识只有一个铸造者与一个载入点；`emit` 同步派发，监听者在入口层开门之前就拿到三样；`startedAt` 是入口层开门那一刻读到的中心的钟；同一对通知顺带给出「同起同停」的边界 |
| 本方弱点 | 首次启动时那一行只是占位（入口层后装、后铸）；读到已铸的值也不知道客户端一面此刻开没开门、何时停 | 运维面装载时标识还没铸：要么装配自己铸（装配胶水拥有契约语义，[红线](../../../AGENTS.md#红线)），要么把运维面挪到入口层之后（运维面失败时入口层已在分派，半开） | 运维面对入口层有一条运行时通知依赖；运维面重跑会丢三样直到入口层下一次开门（[N-4](#实施缺口与消费者影响)）                                                            |
| 置信度   | —                                                                                                | —                                                                                                                                                               | 中高                                                                                                                                                                  |

谁来等钟：

|          | 运维面在自己的插件体里等钟可读，入口层照旧不 inject `clock`（落选）                                                                                   | **入口层 inject `clock`，开门之前等（选）**                                                                  |
| -------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| 最强论证 | 入口层的 inject 集合更小，时钟换代不让客户端一面重跑                                                                                                  | 「钟可读」在开门那一刻判：判的位置与启动成功的位置是同一个插件体里相邻的两步，`startedAt` 就是判过的那个时刻 |
| 本方弱点 | 运维面等到之后、入口层开门之前，钟仍可能重新读不到（续约写失败），开门那一刻的 `startedAt` 又无定义；要补就得让运维面反过来挡入口层开门，那是控制事件 | 时钟换代让入口层重跑（门关再开）；入口层多一条只在启动时用的依赖                                             |
| 置信度   | —                                                                                                                                                     | 高                                                                                                           |

`clockReadyTimeoutMs` 须**严格大于**时钟节点的租约宽度 `LEASE_WIDTH_MS`（候选 10 s，[clock 节点「启动时的租约窗口与入口层等钟」](../../infra/clock/design.md#启动时的租约窗口与入口层等钟)）：崩溃后快速重启落在租约窗口里时，钟至多这么久读不到；取值不大于它，快速重启就可能启动失败。取值归装配。

### 运维面重跑之后怎么恢复应答

契约的前提是**本版运行中不换代存储与时钟的提供者**（装配给，[S-34](../../../../spec/compositions/governance-center-entry/v1/contract.md#s-34-起来即整体停机时在途请求归谁)「前提」、[S-36](../../../../spec/compositions/governance-center-entry/v1/contract.md#s-36-装配给的保证-vs-协议须给的保证)「起来即整体」行）；下面是这条前提被破时，两张面仍能各自恢复应答的做法。
两个插件都 inject `storage`、`clock`，任一换代，内核把它们**各自**重跑，次序不定。只靠 `serving` 通知时，入口层先重跑完、先发了 `serving`，后重跑的运维面就错过了它，此后永不应答。

做法：

- **运维面每次装载**：先挂三条监听，再 `emit('governance-center-ops/listening')`。不读 `governance_center`：`centerId` 只从 `serving` 携带。
- **入口层**监听 `listening`：闸是 `serving` ⇒ 重发一次 `serving`（同一个 `centerId`、`version`、`startedAt`）；闸不是 `serving` ⇒ 什么都不做，等自己开门时发。
- **运维面应答的门不变**：见过 `serving`、其后没有 `stopped`。

|          | 按「自己读行」为门：读到已铸的值就应答（落选）                                                                                                               | 读行 + 握手：门仍是 `serving`，读到的 `centerId` 与 `serving` 交叉核对（落选）                                                     | 只靠 `serving`，不握手（落选，原做法） | **只握手（选）**                                                                                                                                                |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 最强论证 | 不依赖入口层的通知就答得出标识，重跑后自己恢复                                                                                                               | 标识有两个来源，不一致时看得见                                                                                                     | 机制最少                               | 谁后重跑都拿得到 `serving`：运维面后到，它的 `listening` 让开着门的入口层重发；入口层后到，它开门时本来就发。同起同停在启动、换代、停机都成立；标识只有一个来源 |

### 就绪与开门为什么分两步

装配在全部 fiber `ACTIVE` 之后才确认升级快照；入口层若在自己的插件体里就开门，开门与确认之间有一段窗口，进程在窗口里崩溃，下一次启动恢复快照，窗口里已提交的写随之消失、首次启动时标识随之重铸（[tenancy-host 缺口 U-1](../../../apps/tenancy-host/design.md#实施缺口与消费者影响)）。
所以入口层把「就绪」与「开门」分开：插件体只做到**绑好端口不受理**（闸 `closed`，连接一律关闭不答）、标识就绪、钟可读，然后返回；开门由 config `openSignal`（候选名，装配传入的 Promise）放行。
开门之前两张面都不答，没有人见过标识、也没有任何请求被受理：崩溃落在开门之前，恢复快照丢掉的只有这次启动自己的写，首次启动时重铸的标识无人见过，无害。

|          | 插件体里 `await openSignal` 再返回（落选）                                          | **插件体返回后，由 `openSignal` 的续延开门（选）**                                                                                                                               |
| -------- | ----------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 最强论证 | 开门仍在插件体里，开门时钟读不到可以照旧抛出 ⇒ `FAILED`，「启动失败」有内核给的形态 | 装配的放行条件「全部 fiber `ACTIVE`」对入口层也成立——插件体不返回，入口层就一直是 `LOADING`，装配等不到它，放行永不发生                                                          |
| 本方弱点 | 与装配的放行条件互相等待（死锁）；要解开就得另发一条「就绪」通知、让装配改等它      | 开门发生在插件体之外：那一刻的失败不能再让 fiber `FAILED`，只能关掉监听、记一条 error 记录、不发 `serving`；装配要靠等 `serving` 才知道门开没开（[N-12](#实施缺口与消费者影响)） |
| 置信度   | —                                                                                   | 中高                                                                                                                                                                             |

|          | `startedAt` 取插件体里等钟那一次的读数（落选）   | **开门那一刻再读一次（选）**                                                                                                                                                                                                |
| -------- | ------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 最强论证 | 只读一次钟，开门时没有失败支                     | 契约说 `startedAt` 是「启动成功那一刻」读到的时刻，而启动成功就是开始应答（[S-34](../../../../spec/compositions/governance-center-entry/v1/contract.md#s-34-起来即整体停机时在途请求归谁)）；两次之间隔着装配确认快照的时间 |
| 本方弱点 | 比开门早一段装配确认的时间，不是契约说的那个时刻 | 开门那一刻钟又读不到（续租写失败）时要再等：同一个上界 `clockReadyTimeoutMs`，超界 ⇒ 关掉监听、记 error、不发 `serving`，中心没有起来                                                                                       |
| 置信度   | —                                                | 中                                                                                                                                                                                                                          |

`openSignal` 的三种结局与撤除：

- **兑现**：本 fiber 仍活跃、闸仍是 `closed` ⇒ 读钟 → `emit serving` → 开闸。入口层之后换代重跑时，新插件体见到的是同一个已兑现的 Promise，就绪即开门（快照早已确认）。
- **拒绝**（装配确认失败）：闸保持 `closed`，不发任何通知；拒绝由续延处理掉，不留未处理的 Promise 拒绝；装配随后自己撤除一切，这次失败归装配。
- **一直不兑现**：闸保持 `closed`；撤除时走「未开门」那一支（[停机](#成对的装载与撤除)）。

`openSignal` 是运行时对象，不是配置文件里的数据：它只能由装配在装载时构造并传入；config 校验只核「在场且是 thenable」。

### 缺陷怎么到达完整体检

[S-26](../../../../spec/compositions/governance-center-entry/v1/contract.md#s-26-完整体检) 的 `defectCount` 数的是 [S-14](../../../../spec/compositions/governance-center-entry/v1/contract.md#s-14-失败映射) 记过的缺陷；缺陷在入口层发现，计数在运维面答出。提案把承载者留给本节点（[交接缺口](../../../../record/proposals/governance-center-entry/design.md#交接缺口)）。

|          | 装配提供一个诊断汇服务，两个插件都 inject（落选）                    | **入口层 `emit` 无载荷通知、运维面监听计数（选）**                                                                     |
| -------- | -------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| 最强论证 | 有类型的服务面，可单独测；汇若在装配层，计数跨运维面重跑存活         | 不新增服务名与 inject 边；运维面导入白名单只多一个无依赖的声明模块；通知的返回值被丢弃，入口层的答复不等它、不受它影响 |
| 本方弱点 | 多一个服务、两条 inject 边；汇的实例归装配拥有，就是装配胶水持有状态 | 运维面不在（未装、重跑中）时通知丢失、计数少记；计数随运维面实例消失——与契约「重启归零」同寿命，但运维面重跑也归零     |
| 置信度   | —                                                                    | 中高                                                                                                                   |

### 一个请求在入口层怎么走

阶段与 [S-10](../../../../spec/compositions/governance-center-entry/v1/contract.md#s-10-判定次序) 的步一一对应；「查」指一次参与方调用。任何一次调用抛出或给出集合外的值都走缺陷路径（`unavailable` + 缺陷），下表不再逐行重复。

| 阶段       | 做什么                                                                                                 | 查吗       | 出口                                                             |
| ---------- | ------------------------------------------------------------------------------------------------------ | ---------- | ---------------------------------------------------------------- |
| 闸         | 分派闸未开或已关 ⇒ 关闭连接，不写答复                                                                  | 不查       | 问不到                                                           |
| 0 公开体检 | 请求体解析为对象、恰有一个 `operation` 成员且等于 S-18 的路由标识                                      | 不查       | 公开体检固定字节                                                 |
| ① 版本     | 体解析不了、不是对象、`protocolVersion` 缺席、重复、不是字符串或不在常量集合内                         | 不查       | `version-mismatch`                                               |
| ①′ 信封    | `operation` 缺席、重复或不在路由表，有表外成员                                                         | 不查       | `invalid-input`                                                  |
| 免认人     | 注册、登录：`payload` 不重复、载荷内无重复成员、过 Schema、`parseLoginIdentifier`、`credentials.parse` | 不查       | `invalid-input`                                                  |
| ② 认人     | 其余路由：[S-11 行](#能力到-cordis-的投影)（出示物重复即「多个出示物」）                               | 视情形     | `login-state-rejected`；`unavailable`                            |
| 载荷       | `payload` 不重复、载荷内无重复成员、过该路由的 `Payload_<路由>` Schema 与 identity-values 解析         | 不查       | `invalid-input`                                                  |
| 推导       | 标「TenantId」的路由：`memberships.currentTenant(认人所得 LoginStateId)`                               | 查         | `login-state-rejected`；`unavailable`                            |
| 补授权     | 四条读路由                                                                                             | 查         | `{ failure: "notAuthorized" }`；`unavailable`                    |
| ③ 办事     | 调被投影的操作、按映射写出                                                                             | 领域自己查 | 路由结果；`unavailable`；`invalid-input`；`login-state-rejected` |

每个阶段只读前面阶段的结果；Schema 按成员分段校验（先 `Envelope` 的顶层成员、认出人之后再校载荷那一段），因为整份 `Envelope` 一次校验分不出不合格的是哪个成员，而答复取决于那个成员。

## 中心标识：迁移片段与读或铸

**迁移片段**（本包导出 `governanceCenterMigrations: MigrationFragment[]`，与 [`clockLeaseMigration`](../../infra/clock/design.md#高水位为什么是写在前的租约不是写在后的节流) 同形，由装配合进它给 storage-sql 的 `MigrationProvider`，与其他片段次序无关）：

| 表（候选名）        | 列                                                                                               | 约束                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| ------------------- | ------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `governance_center` | `slot`（TEXT NOT NULL，本包只写常量 `'center'`）、`center_id`（TEXT，**可空：NULL 即「未铸」**） | 主键 `slot`，不命名，两方言都报 `governance_center_pkey`（[迁移纪律 M-3](../../../apps/tenancy-host/design.md#迁移纪律每条对应一个提供者要求)，TEXT 列、不是 rowid 别名）；**不建 CHECK**（M-7：`center_id` 的形状由本包读回时核）；`ifNotExists`；**建表之后插入占位行** `('center', NULL)`，以 `ON CONFLICT (slot) DO NOTHING` 插入（候选：Kysely `onConflict(oc => oc.column('slot').doNothing())`，两方言都有；迁移不经存储协议，[core/storage 不用它](../../core/storage/design.md#语句级失败不废事务p-2不改用-on-conflict-do-nothing)的那条选择管的是运行期写路径），所以片段可重跑、重跑不碰已铸的值（M-1）；**不带 `down`**——撤掉这张表就是丢掉中心的身份 |

提案给的列候选里还有 `created_at`，本节点不要：契约里没有它的消费者，多一列就多一个没有人读的持久事实（`tenancy/` 下的源码也不许取墙钟，只能来自 `clock`）。

**占位行就是契约 [S-28](../../../../spec/compositions/governance-center-entry/v1/contract.md#s-28-铸造存放与不变) ② 说的「那一格与存储结构同时立起，状态是未铸」**：读或铸判「是不是第一次」时只看那一格、不看别的数据（读或铸也只碰这一张表）。迁移前核对判「已有别的治理事实却没有这张表」是另一件事，见 [R-GC8](#对存储提供者的要求清单)。
这一读法成立的理由：**「行在、值为未铸」只可能出现在从未开过门的数据上**——治理事实只经入口层的路由写入，路由只在标识铸好、开门之后才受理。
收场与契约 S-28 ④ 的三种读法、失败集合四支逐一对应：

| 读到的                                | 读法（S-28 ④）                                                                                         | 收场                                                                                                                                                                                                                    |
| ------------------------------------- | ------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 行在，`center_id` 为 NULL             | 未铸                                                                                                   | **铸**：生成 128 位随机，写进这一行——首次启动的提交点                                                                                                                                                                   |
| 行在，值合 S-27（`^[0-9a-f]{32}$`）   | 已铸                                                                                                   | 用它，不再铸                                                                                                                                                                                                            |
| 行在，值不合 S-27                     | 失败支「值不合 S-27」                                                                                  | **启动失败**，点名这一支；不修、不重铸，公开体检从没交出过那个值                                                                                                                                                        |
| **行不在**（表在）                    | 失败支「那一格不存在」                                                                                 | **启动失败**，点名这一支；**不当作未铸**（S-28 ⑦）                                                                                                                                                                      |
| 表不在                                | 失败支「读不到」（S-28 **前提**段末句：只剩迁移登记、别的结构都丢了的存储按「读不到 ⇒ 启动失败」收场） | 由迁移前的只读核对挡在迁移之前、不重建（[R-GC8](#对存储提供者的要求清单)）；漏过来时这次读得 `StorageDefect` ⇒ 启动失败、不铸，点名的是「读不到」、缺陷原文随附——本包只碰这一张表、不读目录，分不出「表不在」与别的缺陷 |
| `StorageUnavailable`、`StorageDefect` | 失败支「读不到」                                                                                       | 原样上抛 ⇒ 启动失败。**读不到绝不当作未铸**（S-28 ⑦）                                                                                                                                                                   |
| 铸的那次写失败                        | 失败支「写不进」                                                                                       | 启动失败；那一格仍是未铸，下一次启动仍算第一次（S-28 ③、⑧）                                                                                                                                                             |

|          | 专用哨兵字符串表示「未铸」，列保持 NOT NULL（落选）                              | 另加一列 `minted` 布尔（落选）                          | **`center_id` 可空，NULL 即未铸（选）**                                                                                                                                                                                  |
| -------- | -------------------------------------------------------------------------------- | ------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 最强论证 | 列不可空；读者忘了判哨兵时，哨兵不合 S-27 ⇒ 启动失败，失败方向是关着的           | 状态显式成一列                                          | 「还没有值」就是没有值：三态落在三种互斥的读数上（行不在／NULL／字符串），没有一个与标识共享值域的魔法常量；严格类型下 `string \| null` 逼读者两支都写                                                                   |
| 本方弱点 | 哨兵与标识共享值域，要永远排除在 S-27 之外；值恰好损坏成哨兵时会被当成未铸而重铸 | 两列可能互相矛盾（`minted` 真而值空），多一种要判的损坏 | 可空列给了一条「退回未铸」的写法：只有本包写这张表（[约束](#本节点约束存储要求之外)第 4 条），唯一的 `UPDATE` 带 `WHERE center_id IS NULL`、从不写 NULL；本包之外有人把值改成 NULL，下次启动会重铸——列为已知边界（见下） |
| 置信度   | —                                                                                | —                                                       | 中高                                                                                                                                                                                                                     |

**读或铸**（入口层插件体里，一次 `storage.write`）：`tx.lockRow('governance_center', { slot: 'center' })` 锁住那一行（[P-4](../../core/storage/design.md#协议候选形状)）→ 读它 → 按上表收场；铸的那一支 `UPDATE governance_center SET center_id = <新值> WHERE slot = 'center' AND center_id IS NULL`，这次提交就是首次启动的提交点。启动失败一律抛出具名错误（候选 `GovernanceCenterIdentityError`，原因字段恰为 S-28 ④ 的四支：读不到、写不进、那一格不存在、值不合 S-27），启动失败说明据它点名是哪一支。

**自构的交错**：
(a) 两个写者同时首启（入口层重跑时旧插件体仍在执行，或两个进程指向同一份数据）——两者 `lockRow` 同一行，P-4 把它们排成先后：后者等前者提交，读到已铸的值、直接用。两个写者共同触碰的存储对象就是这一行。`WHERE center_id IS NULL` 是第二道：万一锁没排上序，后者的更新影响零行，重读拿到前者的值。
(b) 读那一行时存储抖动——提供者若把失败折成「空结果」，读到的是「行不在」⇒ **启动失败**，不是铸一个新的：占位行让这类故障的方向是关着的。挡住它的仍是 R-GC5（P-8：不可用只以 `StorageUnavailable` 到达），由一致性套件 C-9a 证；T-8 用会注入故障的存储核「读不到 ⇒ 起不来、不铸」。
(c) 表被整张删掉、迁移登记也被清空——迁移会重建这张表并插入占位行，入口层随后铸出**另一个**标识。挡住它的只有迁移前核对（R-GC8）：非空库里没有 `governance_center`。契约 S-28 前提写的正是这条判据（「已有别的治理事实却没有那一格所在的表」），机制归存储提供者、判据归本包（[N-17 已闭合](#实施缺口与消费者影响)）。
(a) 的 pg 分支要真并发才看得见，写进 [verification](verification.md#证据义务) 作 T-8 的真并发演练。

**已知边界**（本包只碰一张表，契约 S-28 ② 也明写读或铸这一步不判治理事实是否为空）：有人把一张新建的 `governance_center`（只有占位行）拼进一份已有治理事实的数据，或把已铸的值改回 NULL——下次启动读到「未铸」，会铸出新标识。两者都要本包之外的写者动这张表；本节点不为它读别的表。
**前提**：`governance_center` 与第一批治理事实的表出现在同一个数据格式里，不存在「先有事实、后建这张表」的已发布数据；将来若有，须由那一版的迁移显式处置占位行。

**之后**：标识载入插件实例（公开体检答复的固定字节在这时构造）；运行期间入口层再也不碰存储。入口层重跑是一次新的「启动」：重新读（不会再铸），读不到 ⇒ 重跑失败、客户端一面保持问不到。

## 出示物的线上形状：对齐义务

出示物在线上的形状归本契约的 Schema：[IV S-31](../../../../spec/data/identity-values/v1/contract.md#s-31-不透明标识的交换表示) 码点表内的非空字符串（首末不是那张表列出的空白码点，逐码点比较）；
[AI v2 S-45](../../../../spec/capabilities/account-identity/v2/contract.md#s-45-登录状态出示物) 只定它「高熵、不透明、交换表示同 S-31」，字母表与长度留给实现。
**对齐义务**：[account-identity 节点](../account-identity/design.md#能力到-cordis-的投影)选定的出示物表示（候选：32 字节随机的 base64url，`A`–`Z`、`a`–`z`、`0`–`9`、`-`、`_`，不带填充，43 个字符）必须落在这个形状里——
base64url 的字母表里没有空白码点，候选本身满足；将来那边换表示，要先核这一条。本节点这一侧的证据是 T-10：登录成功答复连同 `operation` 过 `Exchange`，其中 `loginState` 过出示物的 Schema。
**入口 Schema 的 `LoginStatePresentation` 就是 S-45 交换表示的投影**（四条同一：`minLength` 1、`maxLength` 1024、不含代理码点、首末不是 S-31 的空白）；账号能力签发的 43 个字符的 base64url 过它，对齐成立。第 ② 步仍以 `parseLoginStatePresentation` 为准，Schema 校验只在测试里核答复。
Schema 的 pattern 注明须在按码点匹配的正则方言下求值：本包用 `ajv` 校验时保持 `unicodeRegExp`（**假设**：`ajv` 8 默认开启、以 `u` 标志编译 pattern，须按 source-check 取证）。

## 工程记录的关联号

工程记录里的账号与租户只以关联号出现（S-30）：`hex(SHA-256(标签 ‖ 0x00 ‖ 输入))`，标签候选 `omne.governance-center-entry.account-correlation.v1`，租户用它的规范 JSON 形式作输入。

|          | 部署级密钥的 HMAC（落选）                                                | **域分离的 SHA-256（选）**                                                                                                                                                                     |
| -------- | ------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 最强论证 | 已经知道某个 `AccountId` 的人也算不出它的关联号                          | 不引入新的秘密；确定、跨重启稳定，同一账号的记录可关联；还原不出 `AccountId`、`TenantId`                                                                                                       |
| 本方弱点 | 多一份要保管、要轮换的部署配置输入；换钥即全部关联号改变，跨换钥关联不上 | 已经知道某个 `AccountId` 的人（例如同组织成员在成员列表里见过它）算得出它的关联号、从而在记录里认出它——契约要的是「还原不出」，不是「关联不上」；读记录的人与握着磁盘的人是同一类（S-30 末段） |

**入口层实例状态**（内存，随实例消失）：配置常量、路由表、五份固定字节（四种答复 + 公开体检）、中心标识、分派闸（`closed → serving → draining`；未开门就撤除或开门失败时 `closed → retired`，此后 `openSignal` 再兑现也不开）、在途计数。
**运维面实例状态**：`centerId`、`version`、`startedAt`（未到时为空）、`defectCount`。**持久状态**：`governance_center` 一行——迁移插入占位（未铸），入口层首次启动时写一次（未铸 → 已铸），此后没有任何写。

### 提交点：入口层在路由上不提交任何东西

[S-17](../../../../spec/compositions/governance-center-entry/v1/contract.md#s-17-路由表封闭每条路由的九件事从哪读) 第 3 件事：入口层的现读都是纯读，路由的提交点就是被投影操作那一次提交。逐类核对有没有哪条路由需要入口层参与提交——**没有**：

| 路由类                            | 入口层的读与领域的提交之间可能插进什么 | 收场                                                                                                                                                                  | 需要共同存储对象吗                                        |
| --------------------------------- | -------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------- |
| 撤销（② AI S-44 读 → AI S-16 写） | 目标在别处被撤                         | S-16 幂等答 `ok`——这次撤销要的状态已成立（契约 S-20 末段）                                                                                                            | 否：S-16 在自己那一次提交里重判发起方有效、目标存在与归属 |
| 同上                              | 出示的那一个被撤                       | S-16 答 `not-authorized` ⇒ `login-state-rejected`（S-33）                                                                                                             | 否，同上                                                  |
| 补授权（OG S-26 读 → 被投影的读） | 调用方在该组织里被解除                 | 这一次读照常答出——准入在闸上已通过，与 S-33 同一口径；下一个请求在闸上被拒                                                                                            | 否：两步都是纯读，契约不要求同一快照                      |
| 推导（OG S-36 读 → 领域写）       | 当前租户身份被切换                     | 以请求到达时推导出的那一个行事（契约 S-12、[`data.identity-values/v1#S-28`](../../../../spec/data/identity-values/v1/contract.md#s-28-当前租户身份在创建那一刻捕获)） | 否：领域在自己的提交里按它收到的身份判授权                |
| ② 认人 → 领域写                   | 出示的那一个被撤                       | S-33                                                                                                                                                                  | 否                                                        |

入口层唯一的写是启动时那一次读或铸，只一个写者（本包），它的两条交错见[上文](#中心标识迁移片段与读或铸)。

**失败映射**：S-14 的表逐格写进每条路由的 `switch`；「交给领域的输入里没有来自载荷的项」那一行（领域答表示层不合格 ⇒ 缺陷）按[路由表](#路由到服务方法)逐条标出：OG S-27、S-36，AI S-37；补授权那几次读的 `invalidInput` 也是缺陷，由契约 S-13 单列。**撤销路由不在其列**：目标来自载荷里的句柄、由账号能力包判表示层，S-16 的 `invalid-input` 照「有来自载荷的项」那一行答 `invalid-input`。

**配置错误**：两个插件的 config 全部经 `definePlugin` 的 Config 校验；证书与私钥解析不了、套接字目录不存在或权限不对、残留套接字有人在听，都在插件体里抛出。一律 ⇒ `FAILED` ⇒ 装配整体启动失败，与同批节点一个政策（T-14）。

**并发**：请求之间不共享任何可变状态，除在途计数（只在闸与完成回调里加减）。一个请求内的领域调用逐个 `await`，没有并发调用。

**停机**（入口层那一个 effect 的 disposer，按序，[`effect-disposal-concurrent-not-ordered`](../../../../basis/cordis/effect-disposal-concurrent-not-ordered.md)：只有同一个 effect 内部有序）按闸的状态分两支。
**未开门**（闸 `closed` 或 `retired`）：闸置 `retired`（此后 `openSignal` 再兑现也不开）→ 关闭已接的连接 → `server.close()` 释放端口；**跳过停收与等在途**——没有受理过任何请求，也没有发过 `serving`，所以不发 `stopped`。
**已开门**（闸 `serving`），三步：
① 闸 `serving → draining` 并 `emit('governance-center-entry/stopped')`：此后到达的请求一律关闭连接不答，运维面同时停答；② `server.close()`：不再接受新连接；
③ 等在途计数归零，上界 `drainTimeoutMs`；到时仍未答完的，销毁它们的连接。
**内核不取消在途调用**：被销毁连接的那些请求里的领域调用照样跑完，按各自那一次提交收场——那件事要么已提交、要么没发生，来者收不到答复（[S-34](../../../../spec/compositions/governance-center-entry/v1/contract.md#s-34-起来即整体停机时在途请求归谁)、PF-017 §6.8）。
disposer 返回之后仍在跑的请求若再遇到缺陷，只写工程记录、不再 `emit`（本插件已撤除，运维面可能也已撤除）。

**撤除之后仍然为真的**：中心标识与全部治理事实在存储里；入口层没有需要交接的在途状态，也没有需要恢复的东西。

**次序由装配保证**（入口层与运维面之间没有 inject 关系）：装载时运维先于入口，撤除时入口先于运维——所以 `serving` 发出时运维面一定在听，`stopped` 发出时运维面还没撤；两张面在同一对通知之间应答，**同起同停**。

**换代与重跑**：前提是存储与时钟的不可用只以返回值出现、不让面缺席，所以入口层只在参与方**换代**（或清单错误）时卸载。
换代 = 走一遍上面的撤除再走一遍装载：换代期间新请求不应答（两张面都问不到），在途请求跑完、按各自那一次提交收场，其间参与方给出的「不可用」照常映射 `unavailable`；**门关与重跑本身不记缺陷、不发缺陷通知**。
新实例重读标识、等钟，见到的 `openSignal` 是同一个已兑现的 Promise（快照早已确认），于是就绪即开门、再发 `serving`；运维面见到同一个标识 ⇒ 恢复应答，`startedAt`、`defectCount` 保留；见到不同的标识 ⇒ 不可能发生的状态，记一条 error 记录、保留原值、不恢复应答。
**崩溃**：什么都不跑。重启时入口层读回同一个标识；残留的运维套接字文件由启动时的试连处理。
