# hooks-import 实现设计

契约：[`capability.hooks-import` v1](../../../../spec/capabilities/hooks-import/v1/contract.md)（下文「契约 S-n」「契约 G-n」都指它）。
本页的插件名、服务名、方法名一律是**候选**；契约的九件事不复述，只写兑现点与缺口。

## 实现路径与来源

**起点是 D-033 接受的候选 A：fork 无运行时的一半，其余自写。**

| 部分 | 来源 | 本节点的处置 |

| 两张方言映射表 | 自写，**以契约 S-23、S-24 为唯一权威** | 一个静态数据模块，逐行对契约的表；不据研究材料另推导来源产品行为 |
| 执行器（被调到时的全过程） | 自写 | 契约 S-16～S-22；**不继承** DSH「执行器拒绝 ⇒ 非阻断、永不抛」（契约 S-19 与 runner S-12 末条） |

## 契约到 Cordis 的投影

### 纯函数、插件与服务键

| 单元 | 公开入口（候选） | 必需 inject | 调用时取用 | 配置 |
|---|---|---|---|---|
| 导入 | 包入口导出 `importHostHooks(host, config) → ImportReport \| invalidInput` 与报告类型 | — | — | — |
| 兼容插件 `hooks-compat` | 不 provide；向 runner 登记一个外部命令执行器 | runner 的实现登记面 `loopExtensionImplementations`（[loop-extension-runner](../loop-extension-runner/design.md#实现怎样在场贡献者登记runner-从不-inject-贡献者)）——登记执行器，也经它的 `resolveExecutionEnvironment` 解析输入里的执行环境句柄（[runner 节点](../loop-extension-runner/design.md#执行环境句柄每次调用一只按会话解析)） | 执行环境那一侧的起进程与停进程两面（候选 `executionEnvironments`，收句柄解析出的执行环境引用；PF-005 那一套，无契约、无提供者） | 无 |

- **导入为什么不是服务**：契约 S-11 ④ 它是纯函数，不读存储、不写任何东西；做成服务只会多一条 inject 边。谁调它、怎样把报告交给资产治理落地，归装配与资产治理（缺口 HI-N5）。
- **执行器为什么一个**：runner 对 `command` 件只认「有没有一个命令执行器」（runner 节点登记面）；两家来源产品的差别在方言数据与编解码里，不在执行器的数目里。
- **配置错误政策**：本包没有配置；runner 已有一个命令执行器时再登记 ⇒ 登记抛出 ⇒ 本插件 `FAILED`、装配启动失败（与同批各节点同一条）。

| 选择 | 落选方的最强论证 | 本方的弱点 | 置信度 |
|---|---|---|---|
| **导入是包导出的纯函数，不是服务** | 做成服务，导入的调用方经 inject 拿到它，将来导入挪到另一个进程时换提供者即可，不必改包依赖 | 调用方直接依赖本包；导入要跨进程时（例如治理中心侧导入）得另起一个服务面 | 高：契约 S-11 ④、S-26 末行「导入是纯翻译，跨进程之后不变」 |
| **一个包、两样东西**（纯函数与兼容插件同包） | 拆成两个包：导入只依赖纯模块，执行器才依赖 runner 与执行环境，谁只要导入就不背运行时依赖 | 只要导入的调用方也装上了执行器的依赖 | 中：两者共用方言映射表与 fork 的 `codec`，拆开要么第三个包、要么复制；D-039 定的节点只有一个 |
| **注销与停进程同一个 effect** | 分两个 effect 各管各的，撤除函数更短、更好测 | 一个撤除函数里有先后两步，一步抛错时后一步靠 `finally` 保住 | 高：basis `effect-disposal-concurrent-not-ordered` 的读数，两个 effect 的完成次序不受控 |

### 一次被调到的子进程：起、限时、停

- **起**：先解析执行环境句柄（解析不出即「起不来」，不起），再把解析出的执行环境引用交给执行环境那一侧起，单机上每次落在**新的进程组**里；以 (执行环境引用, 进程组) 登记进本插件实例的在途集合，挂上三个「停」的来源：handler 时限到、本插件撤除、运行被取消。
- **停**：请执行环境按进程组停（契约 S-26 第 2 行「同一台机器上按进程组停」、S-27 末行），等它答「确认退出」或「未确认」。确认退出 ⇒ 这一次按报错交回（超时）或由 runner 按中途撤下记（撤除）。**答未确认、答不了或执行环境那一侧缺席 ⇒ 执行器当场按报错交回，`error` 写明「已请求停止、未确认退出」，不挂起**；子进程留给执行环境按进程组善后（C-7）——「没确认就不算停下」落成「如实报错、不假装停下」，而不是让这一次经过无限等下去（D-040 §八 M64）。执行器自己不设确认计时器（不自造政策值）：**有前提**——执行环境那一侧的停进程组请求有界地答复，这一条写进 HI-N1 的闭合条件。停用的是起的时候解析出的那个引用，不再解析句柄——调用返回或 runner 换代之后句柄已失效，引用仍有效（runner 节点的装卸表）。
- **运行被取消**（契约 S-27 取消一行、runner S-21 ⑥ `cancelled`；D-040 §八 M39）：runner 把调用方的中止信号随调用交来（[runner 的取消段](../loop-extension-runner/design.md#状态并发与失败映射)）；执行器收到即按上一条停进程组，然后以「已中止」拒绝这一次调用——**不译成 `veto`、不按报错、不自造任何结论**，runner 丢弃它交回的东西、不留记录。runner 不等它（那边的取舍），所以「确认退出」是执行器自己托管的收尾：停不下或确认不了只记 error 级日志，那一次已经没有结论可交。
- **脚本的副作用不可逆**（契约 S-3）：停下它不撤销它写过的文件、发过的请求。

### 事件：派发、过滤与边界

- **不发、也不监听任何 Cordis 事件**（契约 S-25）：导入是一次纯翻译；兼容件被调到时的一切都经 runner 落成结论。
- **F② 依赖消失时谁被卸载**：只有 runner 登记面的换代会让本插件重跑；范围只到本插件与它的在途子进程。
- **F③ 有没有一条通道能越过会话或租户边界**：没有事件。**越界的风险在子进程落在哪**：它必须落在**这一次会话**的执行环境里（契约 S-26 第 1 行）：执行器手里只有这一次调用的执行环境句柄，runner 按经过所在的会话解析它（runner S-50），执行器没有能指认别的会话的参数，也没有回退宿主机的分支。执行环境没有提供者（HI-N1）之前解析一律失败，本插件对每一件兼容件都报「起不来」。日志只读句柄只及本会话（runner S-9），执行器经它读 `ask` 记录与数 `stop_hook_active`，读不到别的会话。

### 存储要求：无

导入不读不写存储；执行器只经日志句柄读、自己不写（结论由 runner 写）。本节点不 inject 存储，没有要求清单，也没有跨 owner 的同一提交。

### 装配给 vs 协议给

契约 S-26 左列，本版单机怎样兑现：

| 契约 S-26 的保证 | 本节点单机的兑现 |
|---|---|
| 子进程落在会话级执行环境里 | 执行器只经 runner 解析的句柄取执行环境；装配（[cli](../../../apps/cli/README.md)）要把句柄解析的来路与执行环境那一侧接上——**受阻**：执行环境没有契约、没有提供者（HI-N1；runner 契约 G-20），闭合之前一律「起不来」 |
| 超时后子进程确实停下 | 同一台机器上请执行环境按进程组停；确认退出 ⇒ 按报错（超时）交回，未确认 ⇒ 按报错交回「已请求停止、未确认退出」、不挂起（M64），子进程归执行环境善后 |
| 运行被取消时子进程确实停下 | 中止信号随 runner 的叫停在同一进程里送到执行器，按进程组停；那一次不留记录 |
| 回放不重跑 | 执行器起子进程之前先读 `ask` 记录与答复，有即直接交回 |
| 导入是纯翻译 | 纯函数，不读不写 |

## 状态、并发与失败映射

**本插件的状态**只有在途子进程集合（进程组号与它属于哪一次调用），只在实例里；**没有耐久事实**。一次调用的步骤：情形与 matcher → 回放检查 → 造原生输入 → 解析执行环境句柄 → 起子进程 → 等退出、时限或中止信号 → 按方言解码 → 按优先级译成一条结论交回 runner（中止时不交结论）。
**并发**：同一批动作各自的经过并行时，几件兼容件可能各起一个子进程，互不共享状态。
**失败映射**：见契约 S-19 的四行；本插件自己的缺陷（映射表查不到一个已导入的事件——那说明导入与映射表不同版）上抛，由 runner 记成报错。

|---|---|---|---|
| 向 runner 登记外部命令执行器 | 兼容插件 fiber；拿回注销函数包进 `ctx.effect` | 已有执行器 ⇒ 抛出 ⇒ `FAILED` | 注销；此后全部兼容件「此刻不在」、按声明跳过 |
| 在途子进程集合（同一个 effect 的撤除函数负责），每项是 (执行环境引用, 进程组) | 兼容插件 fiber；每起一个进程即入集合，停进程组的请求得到答复（确认退出或未确认）即出集合（含取消之后自己托管的那段收尾） | 句柄解析不出或起进程失败都在开始之前 ⇒ 「起不来」，不入集合 | 撤除函数：对集合里每个进程组请执行环境停止 → 等答复；未确认的记 error 级结构化日志、归执行环境按进程组善后（M64）→ 撤除函数里的异常只进日志（basis [`effect-disposal-concurrent-not-ordered`](../../../../basis/cordis/effect-disposal-concurrent-not-ordered.md)），所以每一步自己记 error 级结构化日志。**仍为真**：脚本已做的外部效果；runner 仍在时把那几次记成报错，runner 一并撤除时那几次不留记录（runner 节点 M63） |
| 每次调用的时限计时器 | 那一次调用；退出即清 | — | 撤除时随进程停一起清 |

**注销与停进程放进同一个撤除函数、次序写死**（先注销、再停进程）：同一 fiber 的各个 effect 撤除时并发、不保证次序，分成两个 effect 会出现「进程已停、执行器仍登记着、runner 又派来一件」的窗口。
