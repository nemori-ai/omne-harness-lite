# session-log-jsonl 实现设计

## 实现路径与来源

**自建一个 Cordis 插件与它背后的一个不依赖 Cordis 的闭包，只用 Node 内置模块与本仓库的纯模块。**会话日志的判重、尝试栅栏与「一本日志一个租户」是本项目的产品语义（PF-012、PF-015），DSH 没有对应物；[D-026](../../../../record/decisions/infrastructure-persistence-choices/decision.md) 已把会话日志一类的本地持久化定为**文件系统 JSONL**，格式与目录留给本节点——所以不引嵌入式键值库，也不把日志放进 SQL（据点装配[关键选择 3](../../../apps/cli/design.md#关键选择)）。

| 用什么 | 从哪来 | 用来做什么 |
|---|---|---|
| `node:fs/promises`（追加写、`datasync`、按偏移读、`truncate`、`rename`、目录 `sync`） | Node ≥ 24 内置 | 日志与索引的落盘、确认、截回、重写 |
| `node:crypto`（SHA-256） | 同上 | 会话指认 → 目录名 |
| `node:sqlite`（只用来持一把随进程死亡释放的文件锁） | 同上 | 日志目录的属主排他——借 sqlite 的文件锁作原语，与 [`infra/storage-sql` 升级守卫的属主锁](../../infra/storage-sql/design.md#排他为什么是随进程死亡释放的锁)用的是同一原语（那边 2026-09-23 取证：同进程两句柄互斥、持有者被杀即可取得）；两者锁的对象与目的不同（那边是 sqlite 库的升级属主，这里是日志目录的属主），主线已裁不抽共享件（SLJ-3，观察项） |
| `readJsonStrict`、`writeJsonLossless`、`JsonNumber` | [`core/content-blocks`](../../core/content-blocks/design.md#严格的无损-json-读写)（[D-040 §八](../../../../record/decisions/mainline-self-rulings-2026-09/decision.md#八实现映射起草反推出的契约修订m31m442026-09-25-追加) M36、M53） | 载荷与整行的严格无损读写（契约 S-11 第 2 条） |
| `TenantId`、不透明标识的词法（`data.identity-values/v1#S-31`） | [`core/identity-values`](../../core/identity-values/README.md) | 租户身份、判重键与读取键的表示层校验 |
| `SessionRef` | [`core/messages`](../../core/messages/README.md) | 会话指认 |
| `RunId`、`AttemptId` | [`core/call-accounts`](../../core/call-accounts/README.md) | 条目壳的运行与尝试 |
| `definePlugin` | [`core/kernel-basis`](../../core/kernel-basis/README.md) | 插件骨架与配置校验（配置错误 ⇒ 启动失败的唯一实现点） |

**Cordis 版本**：`@deepseek-ai/cordis` 4.0.4（[D-025](../../../../record/decisions/cordis-adoption-version/README.md)）。机制语义引 [basis](../../../../basis/README.md) 条目。
**配置**：`dir`（日志根目录，绝对路径，无初值）与[策略配置项](#策略配置项)两项。**配置错误政策：启动失败**（形状不对、`dir` 缺席或不是绝对路径、策略项越界 ⇒ 插件体不跑、fiber `FAILED`、不 provide；basis [`plugin-throw-fails-fiber`](../../../../basis/cordis/plugin-throw-fails-fiber.md)）——与 `infra/storage-sql`、`infra/clock` 与三个持钥节点同一政策。

## 能力到 Cordis 的投影

### 插件边界与服务面

**一个插件 `session-log-jsonl`（候选名），一条 fiber，不 inject 任何服务。**它 provide 一个服务 `sessionLog`，方法取契约名：`append`、`readByKey`、`readSince`。

插件体依次：建日志根目录 → 取属主锁 → 开闭包 → 登记**一个** effect（撤除次序全在里面）→ `ctx.provide('sessionLog', …)`。它持有：

| 持有 | 是什么 | 权威 |
|---|---|---|
| 属主锁 | `<dir>/.owner-lock` 上一个持住的 `BEGIN EXCLUSIVE`（`node:sqlite`，`timeout: 0`） | 它在，本实例就是这份日志根唯一的写者 |
| 常驻日志表 | 会话 → { 打开状态、判定态、行偏移表、文件句柄、队列、在途读计数 } | **不是权威**：日志文件才是；任何一本可按文件重开 |
| 撤除标记 | 本实例是否已关准入 | 关了之后到达的调用答 `unavailable` |

### 落盘形状

```text
<dir>/
├── .owner-lock                       属主锁（node:sqlite 借文件锁；无业务内容）
└── <SHA-256(SessionRef 的 UTF-8) 十六进制>/     一本日志一个目录
    ├── entries.jsonl                 权威：一行 = 一次提交（一批）
    └── index.jsonl                   派生：一行对应 entries.jsonl 的一行，只含键与偏移
```

- **`entries.jsonl` 的一行**（候选形状）：`{"v":1,"session":…,"first":n,"entries":[{"tenant":…,"run"?:…,"attempt"?:…,"dedupeKey"?:…,"readKeys":[…],"payload":…}…]}` 加换行。`first` 是这一批第一条的位置，这一批依次取 `first`、`first+1`……；`session` 每行都写，打开时核它等于被指认的会话（目录名是散列，两个会话撞散列时由这一核挡住，撞了即受损）。整行以 `writeJsonLossless` 写、`readJsonStrict` 读。
- **`index.jsonl` 的一行**：`{"v":1,"first":n,"count":k,"start":字节偏移,"end":字节偏移,"dedupe":[…],"read":[[键,位置]…],"runs":[[运行,本行最大尝试序号]…]}`；首行另带 `tenant`。它**从不是判定的依据本身**：判定态 = 索引覆盖的那一段 ∪ 索引之后按日志补读的那一段。
- **一行一次提交**：一批条目只落成一行，所以「半批」在盘上的唯一形态是一行没写完——打开时认得出、丢得掉（[关键选择三](#关键选择)）。

**打开一本日志**（懒打开：这本日志第一次被触碰时，在它自己的队列头上做一次；读等它做完）：

1. 目录不存在 ⇒ 空日志：尾 `0`、租户未定（契约 S-5 第 4 条：这是读得到的事实）。**读不建目录**，第一次追加才建。
2. 严格读 `index.jsonl`：末行不完整即忽略；任一完整行读不出、或与前一行不衔接（`first`、`start` 对不上）⇒ **整份索引作废**。
3. 核索引末行：`entries.jsonl` 在它的 `start` 处那一行的 `first` 与 `count` 须与索引一致，`end` 不超过文件长度；不一致 ⇒ 索引作废、从字节 0 读。
4. 从索引末行的 `end`（或 0）读到文件尾，逐行严格读，核 `v`、`session`、`first` 连续。
5. **文件尾**：最后一个有效行之后若还有字节——其中**再无完整的有效行** ⇒ 半截尾，是没提交完的那一批 ⇒ 截到最后一个有效行的末尾并 `datasync`；**之后还有有效行** ⇒ **受损**：本实例对这本日志一律 `unavailable`、记 error 日志，**不截、不改**（截中间会让位置重排）。
6. 折叠出判定态；索引作废或落后的，按日志补齐（落后：追加缺的行；作废：整份重写——临时名 → 落盘 → 改名 → 目录落盘）。索引补不齐只记 warn、不影响答复。

### 关键选择

**一、判重与栅栏怎样「判定与写入同一步」：属主文件锁 ＋ 每本日志一条队列 ＋ 由耐久内容折叠出的判定态（选）。**

| | 每次追加都现扫描整本日志再写，不留内存态 | 进程内每本日志一把锁，不要属主锁 | 日志放进 SQL，用唯一约束判重 | **属主文件锁 ＋ 每本日志一条队列 ＋ 判定态由盘上内容折叠（选）** |
|---|---|---|---|---|
| 落选方的最强论证 | 没有任何「内存态与盘不一致」的可能 | 最简单；单进程、单实例时就是对的 | 判重落在数据库的唯一约束上，与执行记录同一事务域 | —— |
| 本方弱点 | —— | —— | —— | 判定态常驻内存（有上界，见[策略配置项](#策略配置项)）；属主锁借 `node:sqlite` 的文件锁作原语，与 storage-sql 各自实现（SLJ-3，已裁观察项）；插件重跑时新实例若早于旧实例放锁即启动失败（SLJ-4） |
| 为什么选它 | 扫描本身不排除两路并发各扫一遍「不在」再各写一条——**仍要一个序列化点**；每次追加的代价与日志长度成正比，「超长期待机」的会话越跑越慢 | **不算数**：锁随插件实例生灭——插件重跑时旧实例在途的追加与新实例互不相知，两边各判一次「不在」各写一条（契约 [S-14](../../../../spec/capabilities/session-log/v1/contract.md#s-14-同一会话的追加一条接一条判定与写入是同一步) 第 4 条） | 推翻 D-026（会话日志落 JSONL）要一份新决定；据点装配关键选择 3 已按 JSONL 走出站项 | 进程内队列**只在属主锁持有者的寿命内被依赖**：新实例在旧实例放锁之前拿不到锁、写不了一个字节，而旧实例放锁是它撤除的最后一步、在排空之后；判定态只从盘上内容折叠、只在确认落盘之后前进，所以它总等于「提交点之前已提交的全部」 |
| 置信度 | | | | 中高 |

**两个写入者共同触碰的存储对象**：**这本日志的 `entries.jsonl`**——判重键与栅栏比较的都是它里面已提交的行（契约 [S-8](../../../../spec/capabilities/session-log/v1/contract.md#s-8-判重键) 第 2、5 条）；**写它的权利由 `<dir>/.owner-lock` 上的文件锁排他**（随进程死亡释放，同进程第二个句柄也拿不到）。跨 owner 那一侧（执行宿主的出站项、模型请求运行时的结算、派发器的两副协程）与本节点共同触碰的就是**判重键所在的那一行**（契约 S-8 第 5 条；执行宿主节点 L-5）。

**反证四条交错**：

- **同一实例、同一本日志、两路并发交同一个判重键**：两路进同一条队列，后一路在前一路确认落盘、判定态前进之后才判 ⇒ `alreadyRecorded{keys}`。把队列拿掉（故障注入），两路对同一份判定态各判「不在」⇒ 两行同键——这就是契约模型里 `Serialized = FALSE` 那份否定配置在实现上的对应，[verification](verification.md#证据义务) V-6 让它必须失败。
- **插件重跑：旧实例手里一次追加在途，新实例起来**：旧实例撤除时先关准入、等在途那一批写完并确认、关句柄、**最后**放锁；新实例插件体第一步取锁——早于旧实例放锁 ⇒ 取不到 ⇒ 启动失败（响的，SLJ-4）；晚于 ⇒ 旧实例的提交已全在盘上，新实例懒打开时从盘上折叠，看得见它。两种次序下都没有第二个写者。
- **进程在一行写完之后、确认之前被杀，重启后写入方以同一批重交**：那一行在盘上是完整的 ⇒ 新实例打开时把它当已提交折叠进来 ⇒ 重交得 `alreadyRecorded`；那一行没写完 ⇒ 打开时当半截尾截掉 ⇒ 重交写进。两种都只留一条（契约 [S-22](../../../../spec/capabilities/session-log/v1/contract.md#s-22-回执丢失与结果未知) 第 1 条）。把判定态换成只在进程里、不从盘上重建的集合（故障注入）⇒ 重启后同键写进第二条——契约场景 [S-26](../../../../spec/capabilities/session-log/v1/contract.md#s-26-判重停机重排不多一条) ① 要它必须失败。
- **两个据点进程指着同一个 `dir`**：后起的那个取不到属主锁 ⇒ 启动失败。

**反证不了、要真跑的**：栅栏在两副协程真并发下的交错（契约场景 S-27 第三支）、两个进程抢锁与锁随 `SIGKILL` 释放——见 [verification](verification.md#证据义务) V-4、S-27。

**二、「确认落盘」取每批 `fdatasync`（选）。**契约 [G-3](../../../../spec/capabilities/session-log/v1/contract.md#十已知缺口) 把刷盘政策与断电边界留给本节点写明。

| | 只写进操作系统，不强制刷盘（与 D-027 对 SQL 存储取 `synchronous = NORMAL` 同口径） | 刷盘政策做成配置项 | **每批写完 `fdatasync`，返回成功在它之后（选）** |
|---|---|---|---|
| 落选方的最强论证 | 契约 S-13 第 2 条只要求「进程崩溃再起来不丢」，写进操作系统就够；首 token 热路径上少一次耐久写（模型请求运行时节点 MRR-N7 未测）；与同一据点里那份 sqlite 的断电边界一致，只有一种口径 | 策略不写死：将来要换就改配置 | —— |
| 本方弱点 | —— | —— | 每批多一次 `fdatasync`，延迟未测（实施程测量项，与 MRR-N7 同一测量）；它守住的只是日志一侧——SQL 一侧按 [D-027](../../../../record/decisions/infrastructure-names-and-sqlite-durability/decision.md) 仍可能在断电时丢最后一段，**跨两种存储的断电次序不保证**（已知边界 SLJ-2） |
| 为什么选它 | **会话日志是下游写入的前提**：执行宿主把出站项标成「已送达」、模型请求运行时发出请求，都在日志追加返回之后。只写进操作系统时，断电可以丢掉日志里那一行、却留下 sqlite 里更晚提交的「已送达」——两个文件的回写次序没有保证——**那条消息永远丢了**（据点装配[同一提交表](../../../apps/cli/design.md#存储要求清单与跨-owner-的同一提交)第一行的形状②由此失守）；刷盘之后，日志一侧总不晚于依它写下的那一侧 | 它不是调优旋钮而是上一格那条因果的前提：配成「不刷」时那条因果无声地断；D-027 同样没为 sqlite 开这个开关 | 断电边界随之收窄为：**本节点确认过的批次，断电后仍在**（前提：本地文件系统如实执行 `fdatasync`，SLJ-7）；日志一侧唯一还会在断电时丢的是「写了、没确认」的那一行，它的写入方本来就没收到成功 |
| 置信度 | | | 中高：主线 2026-09-25 已裁接受——D-027 的 `NORMAL` 只管 sqlite 那一份存储，不约束文件系统日志；契约 S-13 第 5 条「提交即持久」是契约性质 |

**三、一行一次提交（选），不做「一行一条条目加提交标记行」。**

| | 一行一条条目，批尾另写一行提交标记；打开时丢掉最后一个标记之后的条目 | **一整批落成一行（选）** |
|---|---|---|
| 落选方的最强论证 | 每行就是一条条目，别的工具直接按行读就是条目流 | —— |
| 本方弱点 | —— | 一行可能很大（一批里带图片的工具结果）；外部工具要按「行 → 批 → 条目」两层读 |
| 为什么选它 | 「标记之后的条目不算」是第二种判读规则，写入与打开两处都要守；标记行本身也会写一半 | 半批在盘上只有一种形态——**最后一行没写完**；打开时的判读只有一条规则（契约 [S-13](../../../../spec/capabilities/session-log/v1/contract.md#s-13-提交与持久) 第 3 条） |
| 置信度 | | 高 |

**四、派生索引文件 `index.jsonl`（选），不是每次打开都扫全本日志。**

| | 打开时扫描整本 `entries.jsonl` 重建判定态，不落索引 | **落一份派生索引，打开时读索引、再补读索引之后的日志（选）** |
|---|---|---|
| 落选方的最强论证 | 少一个文件、少一套「索引错了怎么办」；判定的依据只有一份 | —— |
| 本方弱点 | —— | 多一套重建与核对（打开步骤 2～6），重建本身是证据义务（[verification](verification.md#证据义务) V-1） |
| 为什么选它 | 日志行里带着载荷（工具输出、图片），常驻上界逐出之后再触碰、或每次重启，都要把整本载荷读一遍才判得出下一次追加；长期待机的会话越久越慢 | 索引只含键与偏移，读它不碰载荷；它**从不是判定的依据本身**——错了、缺了、落后了都按日志补回，最坏情况退化成左列 |
| 置信度 | | 中：没有测量；「超长期待机」让左列的代价随会话寿命单调增长，是选它的理由，不是测出来的 |

**五、日志目录的属主排他借 `node:sqlite` 的文件锁作原语（选），与 `infra/storage-sql` 升级守卫的属主锁同一原语、各自实现**（两者锁的对象与目的不同，主线已裁不抽共享件，SLJ-3）。落选方与那边相同：pid 锁文件（被杀的进程留下锁文件，重启被判「被占」直到有人删；进程号会被复用）、不排他只写运维约定（两个进程各写一段，判重与栅栏各判各的）。对比与取证见 [storage-sql 那一节](../../infra/storage-sql/design.md#排他为什么是随进程死亡释放的锁)，本节点不重抄。**取不到即启动失败、不等待**，与那边同一收场。置信度：中高（机制那边已取证；网络文件系统上不可靠——SLJ-7）。

## 策略配置项

默认值只是配置层的初值（配置对象 `defaultSessionLogPolicy`，候选名），**代码里不散放常量**；装配可覆盖。越界 ⇒ 启动失败。初值**都没有测量依据**，是最小起点（SLJ-5）。

| 配置项（候选名） | 管什么 | 初值 | 合法范围 | 为什么它是配置而不是常量 |
|---|---|---|---|---|
| `appendQueueLimit` | 每本日志排队（含正在做的那一次）的追加上限；超出的那一次答 `unavailable`、什么都没写 | 64 | 整数 ≥ 1 | 并发写入方个数随部署与负载变；缓冲必须有界 |
| `residentLogsLimit` | 常驻内存的日志（判定态、偏移表、文件句柄）个数上限；超出时逐出最久未用且空闲（队列空、无在途读）的那本，下次触碰按索引重开 | 256 | 整数 ≥ 1 | 长期待机下触碰过的会话只增不减；上限随机器内存与句柄配额变 |

**不做成配置的**（它们是正确性机制，不是策略）：刷盘（每批 `datasync`，[关键选择二](#关键选择)）；属主锁取不到即失败、不等待（与 storage-sql 同一收场）；一行一批的格式。**本节点不设任何超时**：写与确认挂住时，队列里后面的追加一直等——本地文件系统上这是故障而非常态；要不要给它一个上界，有测量或出现网络存储需求时再议（SLJ-5）。

## 状态、并发与失败映射

**写权**：日志根下的一切只由持属主锁的那一个实例写。**提交点**：那一行完整写进 `entries.jsonl`。**确认**：`datasync` 返回。**判定态、尾、索引**只在确认之后前进。**并发**：同一本日志的追加经它的队列一条接一条；不同日志互不排队；读不排队，只等懒打开做完，读到的是开始那一刻的内存尾。

**失败映射**（没有 catch-all）：

| 情形 | 映射 |
|---|---|
| 输入不合（契约 S-17 ⑥、S-18 ⑥、S-19 ⑥ 列的各情形） | `invalidInput`，在一切判定之前、不进队列 |
| 三道判定得出「不写」 | `tenantMismatch`／`attemptSuperseded`／`alreadyRecorded{keys}`，按这个次序 |
| 队列已满 | `unavailable`（确定什么都没写） |
| 本实例已关准入（撤除中或已撤） | `unavailable`；排队中尚未开始的那些同样答 `unavailable`（确定没写） |
| 写不全、写报错、`datasync` 报错 | **截回写前的偏移并 `datasync`**：成 ⇒ 这一批确定没写下，答 `unavailable`，这本日志照常；截回也失败 ⇒ 这本日志在本实例内「写入不可信」：此后追加一律 `unavailable`、记 error 日志，读照旧只读到确认过的尾；重启后按盘上内容重开（SLJ-9） |
| 打开时发现受损（中间一行读不出、`first` 不连续、`session` 对不上） | 这本日志在本实例内一律 `unavailable`，记 error 日志（说清哪一行、什么问题）；不截、不改——受损不是半截尾 |
| 读时 I/O 失败，或确认范围内的一行读不出 | `unavailable`，**不交空序列、不交半段**；后者另按受损处置 |
| 首次追加建目录或文件失败 | 同「写报错」：没写下，`unavailable` |
| 索引写失败、索引读不出 | 不影响答复；记 warn，下次打开按日志补齐 |
| 编码或折叠抛出（缺陷） | 原样上抛、error 日志——**不折成 `unavailable`**：那会把一次缺陷说成「判断不了」 |

## 成对的装载与撤除

| 取得的资源／注册贡献 | 实例拥有者与对外可用时点 | 部分初始化失败 | 撤除、静止／交接与保留范围 |
|---|---|---|---|
| 配置校验 | `definePlugin` 在插件体之前校验（basis [`plugin-throw-fails-fiber`](../../../../basis/cordis/plugin-throw-fails-fiber.md)） | 失败 ⇒ fiber `FAILED`、不 provide，无部分状态 | —— |
| 日志根目录（没有就建） | 本 fiber；插件体第一步 | 建不成 ⇒ 抛出，启动失败 | 撤除不删；目录与其中一切是持久事实 |
| 属主锁 | 本 fiber；插件体第二步，此后才碰日志 | 取不到 ⇒ 抛出「被占」，启动失败 | 撤除的**最后一步**放（末行）；进程死亡时由操作系统释放 |
| `ctx.provide('sessionLog')` | 本 fiber；插件体末步，此后可解析 | 抛出 ⇒ 随 fiber 撤；effect 已登记，锁由它放（`provide` 经 effect 纳管：kernel-basis probe `provide-is-effect-managed`，**待核对主张**） | 服务消失，下游重跑或 `PENDING` |
| 常驻日志表（懒打开的各本日志、文件句柄、队列） | 本 fiber；随调用按需打开 | 某本日志打开失败只影响它自己（`unavailable`），不影响别本 | 见末行 |
| **一个** `ctx.effect` 里的撤除次序：① 置撤除标记、关准入（新调用答 `unavailable`）→ ② 各队列里**尚未开始**的追加答 `unavailable`（确定没写）→ ③ 等**正在做**的那一次追加各自走完（写、确认、推进判定态）与在途读返回 → ④ 关全部文件句柄 → ⑤ 放属主锁 | 本 fiber | 登记 effect 本身失败（`INACTIVE_EFFECT`）⇒ 插件体自己放锁再重抛 | **在途的那一次跑完，按它自己那一次提交收场**——内核不取消在途调用，①～⑤必须在同一个 effect 里按序写，不能靠两个 effect 的逆序（basis [`effect-disposal-concurrent-not-ordered`](../../../../basis/cordis/effect-disposal-concurrent-not-ordered.md)）。③没有超时（同 storage-sql 撤除②）。⑤在④之后：放锁之前别的实例不得开写。**保留**：日志根下的全部已确认行——它们是会话的真相来源，撤除不回滚任何一行 |

**重跑**（`fiber.update` 或父 fiber 重启；本插件不因别人换代重跑，它没有 inject）：先走上面的撤除，再从配置校验重来；新插件体若在旧 effect 放锁之前开始 ⇒ 取锁失败 ⇒ `FAILED`（SLJ-4）。据点装配本版运行期不换代（[关键选择 2](../../../apps/cli/design.md#关键选择)），这一支只在测试与排空重启里出现。

## 装配给与协议给：本节点单机怎样兑现左列

照契约 S-21 逐行；右列本节点一条都不兑现。

| 保证 | 本节点单机怎样给 | 归谁 |
|---|---|---|
| 判重与栅栏在提交点上判、与写入同一步 | 每本日志一条队列 ＋ 属主锁 ＋ 判定态由盘上折叠 | 本节点 |
| 单写者 | `<dir>/.owner-lock` 上随进程释放的文件锁；同进程第二个实例同样取不到 | 本节点 ＋ **装配**（只装一份、`dir` 只给这一个进程；本地文件系统） |
| 条目壳上的租户就是会话持有的那一个 | 本节点只守「不混」 | **写入方**，经 `sessionTenancy`（装配放进同一进程） |
| 调用方身份已核实 | 进程内能力间面 | **装配**：不把本服务接到任何入口 |
| 读到的就是读那一刻已提交的全部 | 唯一写者的内存尾就是已确认的尾 | 本节点 |
| 提交即持久 | 每批 `datasync`；首次建文件与目录各落盘 | 本节点（每批 `datasync`，主线已裁接受；跨存储的断电次序不保证，已知边界 SLJ-2）＋ 装配（本地文件系统，F-2） |
| 载荷原样 | 严格无损读写 | 本节点 |

**归装配的事项**（点名给 `apps/cli`）：`dir` 的位置（与 SQL 存储文件同属据点数据目录，候选、未钉）；**只装一份、装在根上**；日志根必须在本地文件系统上；不把 `sessionLog` 暴露成入口；**开闸在存储升级确认之后**——会话日志不在 `storage-sql` 升级快照里，确认之前若有追加、随后快照被恢复，两处存储就不一致（[storage-sql 属主实例](../../infra/storage-sql/design.md#属主实例排他迁移前只读核对升级快照与确认)）；撤除次序——本插件没有 inject，它随根撤除，派发器与模型请求运行时由装配先撤（据点装配已按 D-040 §八 M48 A-1 承接）。

## 实施缺口与消费者影响

契约第十节的缺口不重抄；下表是**本节点自己的**缺口，编号 SLJ-n 只在本节点内有效。

| # | 缺口 | 受阻的消费或条款 | owner | 闭合条件 |
|---|---|---|---|---|
| SLJ-1 | **真承接者未到**：本节点是契约第十一节的最小提供者；整本会话日志的契约与真提供者归 loop 与会话那一程（契约 G-1，据点装配 C-1） | 产品据点清单里派发器与模型请求运行时停在 `PENDING`（本版不装本节点，据点装配关键选择 5） | 主线 → loop 与会话那一程 | 那一程的契约收下或取代 SL v1，提供者节点与本节点互指或取代本节点 |
| SLJ-2 | **已知边界（主线已裁，2026-09-25）：每批 `datasync` 接受；跨两种存储的断电次序仍不保证。**D-027 的 `NORMAL` 只管 sqlite 那一份存储，不约束本节点的文件系统日志；契约 S-13 第 5 条「提交即持久」是契约性质，本节点照[关键选择二](#关键选择)兑现，**日志一侧确认过的批次断电后仍在**。SQL 一侧按 D-027 仍可能丢最后一段已提交事务；`storage-sql` 升级未确认即撤除时恢复快照，是同一形状的另一条来路（SQL 回退、日志不回退）——两种情形下，日志里已确认的条目都可能指着 SQL 一侧已经不在的行。**受影响的是 SQL 一侧的两处**：会话持有租户 `capability.session-tenancy/v1#S-6`（[session-tenancy-table](../session-tenancy-table/design.md#实施缺口与消费者影响) STT-3）、装配清单 `capability.assembly-manifest/v1#S-24` 与 S-13（[assembly-manifest-store](../../assets/assembly-manifest-store/design.md#实施缺口与消费者影响) AMS-4、AMS-5）——它们引这一条，不另论证。每批多一次耐久写的延迟未测，记为**实施程测量项**（verification V-13，与模型请求运行时 MRR-N7 同测） | 契约 S-13 第 5 条、G-3；ST S-6、AM S-24；首 token 热路径 | 主线（边界）；实现者（测量） | 不闭合的已知边界：产品要求跨存储的断电次序时另出决定（sqlite 改 `FULL`，或两处落进同一事务域）；升级恢复那一条来路由据点装配「开闸在确认之后」挡住；测量结果记入 verification |
| SLJ-3 | **已裁：观察项（主线，2026-09-25）——不抽共享件。**`infra/storage-sql` 的排他是升级守卫的属主（sqlite 库级），本节点是日志目录的属主（借 sqlite 文件锁作原语）：机制与目的都不同，两份实现不是同一概念的两份权威 | —— | 主线 | 出现第三个「目录属主」消费者时再议抽共享件 |
| SLJ-4 | **插件重跑时新实例早于旧实例放锁 ⇒ 启动失败**：重跑时旧 effect 的撤除是否先于新插件体**完成**，basis [`plugin-body-reruns-on-provider-change`](../../../../basis/cordis/plugin-body-reruns-on-provider-change.md) 只说「先卸载再重跑」——**待核对主张**，与 storage-sql 交错 (d) 同一件 | 运行期重跑（据点装配本版不做） | `core/kernel-basis` owner | 按 source-check 取证后定要不要一条测试；若旧撤除不先完成，改为有界等待锁（届时是一个策略配置项） |
| SLJ-5 | 两个策略项的初值没有测量依据；写与确认没有超时 | 长期待机的内存与句柄上界；挂住的文件系统 | 实现者 | 有测量再调初值；出现网络存储或挂住的实际案例再议超时 |
| SLJ-6 | **读没有分页**：`readSince(…, 0)` 把整本日志（含载荷）一次读进内存——契约的接口就是这样 | 长日志的读方（投影追尾、拓展件的日志只读句柄） | loop 与会话那一程（SL G-1） | 那一程的契约给分页或流式读 |
| SLJ-7 | **断电边界的部署前提**：`datasync` 在 macOS 上不刷盘缓存（要 `F_FULLFSYNC`），网络文件系统上文件锁与刷盘都不可靠 | 契约 S-13 第 2 条（本节点口径下）、S-21 第二行 | 装配（运维约定） | 部署说明写明「日志根在本地 Linux 文件系统」；要跨平台断电级持久再改实现 |
| SLJ-8 | **产品据点清单本版不装本节点**（据点装配关键选择 5）；装上即完整工作，但调用方 agent loop 缺席（C-8） | 本节点在产品路径上没被演练 | 主线 | 据点装配的改选条件成立 |
| SLJ-9 | **「写入不可信」的日志要重启才恢复可写**：截回失败之后，本实例不再信任那本日志的文件状态 | 那一会话此后的全部追加 | 本节点 | 有真实案例再加进程内的重开（重开时的判读与「打开一本日志」相同） |
| SLJ-10 | **没有修复工具**：受损的日志本实例拒绝读写，人工修复（截掉受损处之后的行、接受位置重排）没有入口 | 受损那一会话 | 运维 ＋ loop 与会话那一程 | 那一程定下受损日志的处置 |

**报给主线**（不在本节点改）：四个消费者节点（执行宿主 L-1～L-5、模型请求运行时 L-1～L-8 与 MRR-N1、派发器 RL-1～RL-6、据点装配 L-a～L-f 与 C-1、验收装配表「会话日志」一行）改指本节点、两边互指；[`run-attempt-facts-derived`](../run-attempt-facts-derived/design.md#对会话日志提供者的要求) 对本节点的读要求（FR-1～FR-5）已由上文各条接住。
