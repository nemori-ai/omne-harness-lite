## 施工反例与候选比较

SLJ3-RG1 的两份磁盘状态可以有同样合法的 `index.jsonl`：一次健康关闭；一次写／截回失败后进程退出。原 `openJsonlSessionLog({dir, policy})` 只能检查文件，既不能由索引结构正确推出健康，也不能由取到锁推出旧物理进程已退出。失败后才补写 dirty 标记仍可能失败；统一全扫又取消已采用的正常索引路径及 [V-1](verification.md) 内容错误反例。

| 实质候选 | 最强支持理由 | 必须承担的代价／本次判断 |
| --- | --- | --- |
| A：调用者显式指定健康打开或全量恢复 | 不增加 provider 文件；进程主管本来就知道启动原因，可控制恢复开闸 | 要保证每本日志的历史，主管仍需在改写前可靠持久化状态；仅一个 `recover: true/false` 默认值不能覆盖 SIGKILL、主管自身重启和未触碰日志。将本应紧邻文件写入的前置动作移到调用者，缺调用顺序即误判健康；本次不选 |
| B：provider 按日志预写 active／关闭写 clean，主管提供物理进程退出事实 | 在任何可能改写之前建立可靠信号；异常退出无需补写，健康 LRU 可保留索引；退出事实与写锁各守自己的边界 | **推荐**。增加每次冷打开和健康逐出的元数据同步及故障分支；必须有可信装配输入，标记不证明进程死亡；标记损坏不能自愈为 clean。置信度中，需真实 FS／多进程证据 |
| C：让现有索引或属主锁文件成为失效信号 | 少一个常驻文件；可沿已有文件读写和版本核对 | 出错后删索引不可靠；改写前必删索引会使正常 LRU 重开总全扫，且缺索引仍不能证明旧进程死亡；若另加持久状态和属主字段，实际承担 B 的协议。现有 SQLite 长持独占事务也没有已采用的、崩溃后可读的提交状态；本次不改锁原语为新的状态数据库 |

推荐 B 的细化取舍：

| 选择 | 落选方最强论证 | 推荐方弱点与改票条件 |
| --- | --- | --- |
| 每本日志一份标记，不用根级单标记 | 根标记只需每次启动／关闭同步一次 | 每本增加同步成本；但根 clean 必须证明根下所有未懒加载日志都已恢复，或再维护已恢复集合，超出最小方案。只有测量证明成本不可接受且有同样完整的懒恢复方案，才复议 |
| 生死观察作为独立闭包的必填装配输入，不新建 service/fiber | 固定某 OS 的进程出生标识能减少装配工作 | 本方增加调用者责任；当前未采用跨平台进程识别机制，不将 PID、超时或锁释放冒充退出。若已有经过来源核对、覆盖主管重启的进程提供者，可由装配复用；不能提供事实时保持不可用并交主线 |
| 保留健康索引，只有 active／旧布局迁移全扫 | 每次全扫实现简单、移除 SLJ-11 的信任前提 | 推荐方仍承担原 SLJ-11 及 V-1 反例；不能把恢复标记当索引内容校验和。放弃健康路径须另有采用，不能在本次施工悄改 |

## 公开面、必需输入与迁移

纯函数、三个服务操作及返回值不变；仍是一条 Cordis fiber、无 inject、无业务事件。候选闭包改为 `openJsonlSessionLog({dir, policy, processOwnership})`；插件 factory 从可信装配取得同一输入，不把它加到 `sessionLog` 三操作服务面。静态导入纯面不读文件、不读取进程状态、不加载 Cordis。

`processOwnership` 是本地生命周期依赖，非租户配置、非可序列化协议；候选字段如下：

| 候选成员 | 责任、校验、缺席及失败 |
| --- | --- |
| `current: string` | 非空、不可复用的**物理进程本次生命身份**，由实际启动／管理该进程的宿主提供；同一进程的不同实例、fiber 重跑、close 后重开必须相同。不是 PID，也不是每次 open 随机一个新值。provider 捕获为不可变值 |
| `observeExit(owner): Promise<'exited' \| 'alive' \| 'unknown'>` | 对已保存的 owner 取得可信事实。`exited` 必须表示那个物理进程实际退出已确认；不是请求过 kill、服务已卸载或锁可取。`owner === current` 直接按 alive，禁止回调覆盖。未知历史、观察失败、抛出或返回非法值均按 unknown，相关日志 unavailable；不自动重试或轮询 |
| `observeLegacyExit(dir)`，可选，同样三种返回值 | 只处理已有日志目录却没有正式标记的旧布局。`exited` 表示装配已确认本根全部旧布局物理写进程退出，无潜在旧文件任务；主管必须保有实际退出依据。缺席／unknown／alive 时该日志 unavailable，不能猜 missing＝clean。不是一般绕过 owner 检查的开关，不能覆盖合法 active 或损坏标记 |

整项依赖缺席、成员形状非法或空 current 属同步配置错误：闭包构造／插件初始化失败、不发布服务、不碰日志。运行中观察异常是恢复不可用，不报 invalidInput、不假造业务拒绝。返回 Promise 仍在途时 provider 拥有该初始化任务；close 必须等待它真正结束，无隐藏超时。观察器只提供事实，不被授予关闭进程或改日志的责任。

**归装配**：原 `apps/cli` 节点的根目录与开闸 owner，以及独立闭包的实际宿主调用者，需提供身份生成／保存、与物理子进程生命绑定、退出确认及旧布局迁移证据。子进程 exit/wait 的真实完成可作为被主管持有的实例证据；主管自身重启后若无法还原此前身份，则 unknown。不能仅凭“记录查不到”答 exited。PID 复用时新进程不继承旧身份；若没有可靠出生身份／主管记录来区分，仍 unknown。本页不指定未经取证的 OS 探测算法，不新建通用进程平台，RG-G1 明确承接这一缺口。

现有提供者调用者、插件装配、测试和双语 README 均须显式增加此输入。新配置不能由适配器偷偷填“旧 owner 都已退出”。SL2 旧 writer 迁移除 D084 全写方停准入／排空和 SL3 四参数切换外，还需确认旧物理进程退出；旧目录经一次独占全扫后安装新标记。保留旧源码制品作为历史证据，旧写器不得再打开新布局目录；回滚写器不理解标记，会破坏 clean 含义，未定义回滚迁移。无此输入的现有调用者保持受阻，不以签名兼容层规避。

## 文件布局与权威

```text
<dir>/.owner-lock
<dir>/<SHA256(SessionRef)>/entries.jsonl
<dir>/<SHA256(SessionRef)>/index.jsonl
<dir>/<SHA256(SessionRef)>/recovery.json       # 候选正式标记
<dir>/<SHA256(SessionRef)>/recovery.json.next  # 候选同目录写入暂存；最多一个
```

`entries.jsonl` 继续拥有业务事实和提交点；`index.jsonl` 仍是有原前提的派生判定来源。`recovery.json` **只拥有“可走正常打开，还是必须证实旧 owner 退出并全扫”的物理恢复门**，不记录 tail、tenant、keys、run、业务结果或判定点，不与业务追加组成新的双文件事务。

候选格式严格闭合：`{"v":1,"state":"clean"}` 或 `{"v":1,"state":"active","owner":"…"}`。数字 1 仅为提供者文件格式版本；重复成员、额外成员、未知版本、非法 owner 或语法损坏均拒绝读取为状态。编码可复用 core 严格 JSON 公开面。标记版本与原日志／索引折叠版本分别拥有其变更，不借改版本抹掉历史。`next` 永不作为判定权威，无论它比正式标记看起来新或完整多少。

原属主锁仍排他所有这些文件的写入；除锁以外不新增 SQLite 表、数据库或跨存储原子保证。文件名只在原 SHA256(SessionRef) 所属目录下使用，仍受根 dev/inode、目录不被外部改写、本地 FS 的原前提约束；标记不提升为安全沙箱。

### 单份标记的耐久替换

所有步骤由持根锁的 provider 持有，并纳入该本日志的打开／关闭任务，不能与该日志其他文件操作重叠：

1. 严格读取正式标记并作恢复门判定；只在允许继续后处理遗留 `next`。旧 `next` 不阻止识别正式 clean／active，但清理失败则停止该次打开，不修改业务文件。
2. 以独占创建写完整 `next`，`datasync`，确认关闭其句柄；不能直接 truncate 正式标记。新 session 目录先同步其父根，沿原 F-3 固化目录存在。
3. 同目录 rename 覆盖 `recovery.json`，随后同步 session 目录。**上述全部成功**才称新状态耐久。未确认的 rename／sync 不当作成功。
4. 对 active，成功完成步骤 3 后才允许打开路径修复 entries、维护 index、开始首次 entries/index 创建或发布该日志判定态。对 clean，必须先达到下节全部关闭前提才开始步骤 2。

任一步失败都有被拥有的实际句柄／任务收口；不捕获后继续文件写。替换失败时不假定旧值或新值已落盘，不回写“修正”clean。只要还没有成功完成 active 耐久步骤，就**绝不开始业务文件改写**；因此即使系统重启看到旧 clean，也不会漏掉本轮改写。active 之后若任何业务写进入不可信态，已有 active 已经足够，完全不依赖失败后再写 dirty。

clean 替换失败也不反向撤销已经确认的业务批。close 报明确失败，不声称完成、不释放属主锁；宿主若无法收口只能执行既有实际进程终止路径。若 rename 已见 clean 但目录同步失败，clean 的前置事实仍已成立：所有文件任务结束、句柄关闭、索引已可安全重新打开。崩溃后看到旧 active 只多做一次恢复，看到 clean 也不会跨过尚在途的写。不能以这条安全分析把失败的 close 报成功。

正式标记在正常卸载／LRU 后**保留为 clean**，不删除；active 仅在成功关闭前提满足时替换成 clean，不提供手动清零接口。`next` 正常由 rename 消耗；错误／崩溃后的遗留仅由下次独占打开按上述规则移除。损坏正式标记不借删除文件转成 legacy，保持 unavailable；无通用修复工具沿原 SLJ-10。

## 打开、运行与撤除的状态次序

| 入口状态 | 允许的行为及对外可用时点 |
| --- | --- |
| session 目录不存在，根仍是同一可读根 | 读返回原空日志语义，不创建目录／标记。首次追加先在空态完成所有输入和四道业务判定；仅全过后建目录、耐久 active、创建业务文件并写一批。tailChanged／其他确定拒绝不能产生首次日志目录、标记或业务文件 |
| 正式 clean | 取根锁后耐久替换为本进程 active，再按原正常索引打开步骤处理；索引覆盖段仍直接取索引，末行核对及后缀补读保持。判定态完整、必要尾修复同步完成后可用。clean 不是“索引内容绝对正确” |
| 正式 active，owner 是当前物理进程 | 该日志 unavailable，不全扫、不改标记；即使旧实例 close 已释放锁或换了 fiber，也不得绕过 D084 的进程重启。健康已打开的驻留实例继续用其自身状态，不把每次操作误当冷重开 |
| 正式 active，owner 不同 | 在取得根锁后，只有 observeExit 确认 exited 才继续；alive／unknown 不改文件、该日志 unavailable。确认后先耐久替换成本进程 active，再从 entries 字节 0 严格全扫，完全不读旧索引作为判定依据 |
| session 目录存在但正式标记缺席 | 这是旧布局或首次设置中断，不能依据空文件／索引合法判断健康。只有 observeLegacyExit 确认旧物理写者全退出才按上行全扫；缺 entries 且该目录确无任何业务数据的情形才可折叠为空。entries 缺席而仍有索引等业务文件则 unavailable，不把丢失数据当新日志 |
| 标记损坏／未知版本或根不可核对 | unavailable，不清理成空、不调用 legacy 分支、不删除权威字节；影响本日志，根本身失效则按原规则影响全实例 |

恢复的全扫不跳前缀：折叠完整合法批；真正半截尾截到最后完整行并 datasync；中间受损、后面有完整有效行、session 错配、first 不连续继续 unavailable，不跳过／重排。恢复中的两个读面和追加均不可答成功；等待同一被拥有的懒打开完成后才能调用。恢复错误使该日志 unavailable。失败的恢复也已经持久标记本进程 active，下一次恢复必须等这个物理进程真正退出。

旧索引在全扫期间不得复用。全扫成功后据新折叠态重建索引；索引写失败仍沿原规则告警、已完成权威恢复的日志可用，**但不能将未处理的旧索引带入 clean 状态**。进入 clean 前必须成功耐久替换正确索引，或删除该旧索引并同步目录，保证下次正常打开退化为全扫。两种都失败则不写 clean、关闭失败保留锁；这项条件避免“本轮从头恢复正确，下轮又信旧错索引”。正常健康打开／追加的索引仍按原增量维护及版本规则，不新增逐行内容全量核对。

| 运行／关闭路径 | 所有权与留下的事实 |
| --- | --- |
| 健康运行 | 标记保持 active；已确认批更新同一 entries 文件折叠态，标记不随每批 tail 更新。成功截回并同步后可继续健康，不强制重启 |
| 不可信写／截回失败 | 原 SLJ3-P5 生效，三操作 unavailable，未开始追加零写拒绝；不尝试补写 dirty，不允许 clean，也不自动重试业务提交 |
| 健康 LRU 逐出 | 只有队列空、无读、无任何文件／修复任务才开始；以同一本日志的生命周期占有阻止新调用插入，关闭文件句柄，满足索引安全条件后耐久 clean，最后移除驻留项。中途失败不能冒称逐出成功。其他调用等待此过渡或依原容量政策 unavailable，不能另开第二个同日志实例 |
| 不可信日志的 LRU | 不作健康逐出，不写 clean。若实际任务都已结束，可以关闭句柄并移除驻留项以释放硬上界；active 保留，冷开按 current-owner 规则 unavailable。任务仍在途则不可逐出。无须无界内存 tombstone，磁盘 active 是跨 LRU 的门 |
| 整体 close／Cordis 单 effect | 关全实例准入和旧引用→拒未开始追加→等真实读／写／打开／修复／元数据任务结束→关句柄→逐本健康日志耐久 clean；不可信日志只保留 active→全部必要清理成功后最后放根锁。关闭返回不等于当前物理进程退出；不可信日志即使完成这次资源关闭，仍必须实际重启后恢复 |
| 关闭失败／任务停止无法确认 | close 不报成功；保留已取得的锁与任务所有权，不能启动竞争的新 owner。无新 timeout、锁等待或隐式重试；宿主的强制退出后，由主管确认实际退出，后继独占恢复 |

逐本 clean 避免未加载日志被根级关闭洗成健康：close 只处理本实例已拥有并成功打开的驻留日志，既有未触碰 active 保留。先前已健康逐出的 clean 也无需再改。关闭中部分日志 clean、部分 active 后 SIGKILL 是合法中间状态；新 owner 逐本走对应路径。

两条反证必须真实执行：① A 进入写 IO，尚未结束时 B 尝试 open；A 无权先 clean／放锁，B 取锁失败。即便 A 后续关闭并放锁，留下 active 的日志也因 A 物理进程仍 alive 而挡住 B。② A 的不可信日志被移出 LRU，同进程 B 重开；不能因内存项消失而走索引，磁盘 active＋同物理身份必须拒绝；只有 A 所属物理进程退出且新进程独占后才全扫。共同业务提交对象仍是 **entries.jsonl**；标记和宿主退出观察只建立恢复前提，不替代 S-33 同提交比较，也没有新增跨 owner 同提交承诺。

## 同步／崩溃后果与存储要求

所有真实 SIGKILL 点均应通过子进程发出阶段通知、父进程确认 kill 后等待真实 exit，再启动后继；不能以 mock Promise 的 reject 代替进程死亡。以下可见旧／新表示原 F-2/F-3/F-4 下的同步边界，断电持久性仍需部署存储证据，不能由 SIGKILL 一次演练推及所有介质。

| 中断／IO 故障窗口 | 后继必须看到的约束与收场 |
| --- | --- |
| 取锁前、读取标记／观察旧 owner 时 | 业务文件未改；不能有服务成功结果伪称已恢复；锁未取得不触碰日志 |
| active 的 next 创建／写／datasync／close／rename 前后，目录同步未确认 | 本轮业务文件尚未改。正式标记可能旧 clean、旧 active 或新 active；只按正式状态和退出事实选择，next 不作证据。同步失败实例不继续写 |
| active 已耐久，首次业务文件创建／目录同步任一点 | active 必须保留；后继不信索引。完整持久批保留；没有业务文件且确无数据可为空；缺 entries 却有业务派生物不猜空 |
| append 半写、完整写但 datasync 未回、datasync 失败／成功但回执丢失、截回／截回 datasync 失败 | 不要求后继猜当时返回值；active 触发实际退出＋全扫。盘上完整合法批全收、仅真半截尾按规则修复，keys/tail/tenant/fence 同源折叠；未确认调用仍由消费者按自身身份认回 |
| 全扫／尾修复／修复 datasync／索引重建任一点 | 本进程 active 已耐久，没完成的判定态不发布。若又退出，下一进程重走全扫；损坏中间不可截断伪修复 |
| 健康关闭的文件句柄关闭前 | 正式状态仍 active，不得提前 clean；实际任务在途则不释放锁 |
| clean 的 next 写／datasync／close／rename／目录 sync 任一点 | 所有业务文件任务及句柄早已结束，索引已可安全打开；正式值若仍 active，后继全扫，若为 clean，正常索引路径。任何失败仍使本次 close 失败，不早放锁 |
| clean 已耐久、放锁前后，或关闭多个日志之间 | clean 日志可正常重开；残留 active 逐本等物理旧 owner 退出。取锁和观察退出缺一不可；不能从其他日志 clean 推出本日志 healthy |

新增抽象存储要求是：在允许业务改写前可耐久建立恢复前置状态；同目录原子替换与目录持久确认；失败可识别；状态不能被另一写者并发覆盖。分别服务 SL3 S-13/S-21/S-22/S-23/S-35，沿 F-2/F-3/F-4/F-6/F-7/F-8 实现。无法提供目录同步或同目录原子替换的存储部署不可声称支持本恢复路径。没有另选数据库。

Cordis 采用版本仍为 D-025 的 4.0.4；关闭序列继续在一个 effect 内，依据 [`effect-disposal-concurrent-not-ordered`](../../../../basis/cordis/effect-disposal-concurrent-not-ordered.md)，配置失败沿 [`plugin-throw-fails-fiber`](../../../../basis/cordis/plugin-throw-fails-fiber.md)。原 `provide-is-effect-managed` 待核对主张、Node 文件锁／实际停止／目录同步的取证义务保留；未增新的已核对上游保证。宿主物理身份及退出观察是**装配假设，须 source-check 与真实进程演练闭合**，不是 Cordis 行为。

观测增加恢复来源（clean／active／legacy）、阶段、受限相关标识、owner 观察状态、全扫／修复计数及 close 失败因果；不得输出条目 payload、业务键正文、裸路径或原始错误中的秘密。元数据失败与业务 unknown 分开解释，既不假成功，也不据诊断记录代替权威日志。
