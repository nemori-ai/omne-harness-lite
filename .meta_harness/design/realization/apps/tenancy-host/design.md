**本节点自建的只有四样**：① 装载清单与 `boot()`／它返回的 `TenancyHost.dispose()`；② 迁移的**合成**（owner 导出片段，本节点定次序并给出跨 owner 那条外键的目标与名字）与**升级整体性的编排**（把只读核对交给存储提供者、全部 fiber `ACTIVE` 后确认快照、确认之后才放行入口层开闸，[下文](#升级的整体性迁移前只读核对快照与确认)）；

四样里没有任何一样拥有领域事实或判定；[装配胶水不得暗中拥有未定义能力](../../AGENTS.md#红线)——凡是本页写不进上面四样的逻辑，都回它所属的 provider 节点或契约。

**复杂度声明**：本节点没有缓存、池、队列、重试；定时器只有两个上界（等 `serving`、撤除总超时），都只把「挂住」变成说得出原因的失败。三处像「机制」的东西——启动的整体性（任一 fiber 失败 ⇒ 全撤 ⇒ 退出）、密钥配对自检、升级的整体性（只读核对、快照、确认与两步开闸）——
都是正确性检查：第一处保护「配置错误一个政策」与[入口契约 S-34](../../../spec/compositions/governance-center-entry/v1/contract.md#s-34-起来即整体停机时在途请求归谁)「起来即整体」，第二处保护「两份交接凭证不可伪造」的配对前提（[AI S-30 第 9 行](../../../spec/capabilities/account-identity/v2/contract.md#s-30-装配给的保证-vs-协议须给的保证)），
第三处保护 [PF-017 §6.9](../../../product/PF-017-governance-center-as-deployable-application/design.md#69-升级同一个中心要么整体成要么整体不成)「升级整体成或整体不成」——快照的具体机制归存储提供者，本节点只编排。

## 公开面

[SYS-OPEN](../../../foundation/cross-system-constraints/requirements.md#sys-open) 把本项目的 runtime 定为核心能力的**一种消费者**；本节点就是治理中心那一种消费方式的装配。**装配不变**：装载清单、次序、config 来源、密钥与配对自检、迁移合成、两步开闸与撤除都照本页，本程追加的两条 fiber 也照[本程追加](#本程追加资产治理与模型档案目录的中心侧候选尚未实现)。

- **本节点没有能力的函数面**，也不该有：自建的四样都是装配，不拥有领域事实或判定（[上节](#实现路径与来源)）。公开入口 `src/index.ts` 导出的 `boot`、`buildManifest`、`hostMigrationFragments`、`readHostConfig`、`verifyKeyPairing`、`generateKeyFiles` 是**装配的构件**：要以另一种方式装同一批提供者，可以取用它们，也可以不经本节点、直接 import 各提供者的函数面与插件。
- **各提供者的两面写在各自节点**：identity-values、offer-expiry 全部即函数面；组织治理的两面见[它的公开面](../../packages/tenancy/organization-governance/design.md#公开面)；资产提供者的函数面（候选子入口 `./judgments`）见 [asset-governance「公开面」](../../packages/assets/asset-governance/design.md#公开面)——本节点照旧只装它的包主入口（插件）。
- **只在本装配里成立、不随函数面走的**：同一存储、同一约束域（[三件事](#同一存储同一约束域本节点要保证的三件事)）、恰一个 `clock` 实例、配置错误即启动失败、起来即整体。另一种消费方式要么自己给出这些前提，要么放弃建立在它们之上的那些保证（例如跨 owner 的同一提交）。

## 装载清单与顺序

一个根 `Context`；按下列顺序 `ctx.plugin(plugin, config)`：

```text
storage-sql → clock → credential-verification → account-identity → organization-governance → account-registration
            → asset-governance（设计已接受）→ model-profile-directory 中心 P-1（设计已接受）
            → governance-center-ops → governance-center-entry
```

标「设计已接受」的两条是本程追加、**尚未实现**（[本程追加](#本程追加资产治理与模型档案目录的中心侧候选尚未实现)）；已实现的清单（HUB `c9b5850`）是去掉这两条的八条。

- **顺序 = 依赖序**。`clock`、AI、OG 必需 inject `storage`，AR 必需 inject 三个领域面；迁移在 `provide('storage')` 之前跑，装 `storage` 先于一切让「表已在」对后面每个插件都成立。
- **运维面与入口层装在最后，运维面先于入口层**（[governance-center-entry「次序由装配保证」](../../packages/tenancy/governance-center-entry/design.md#成对的装载与撤除)；提案装配草图）。
  入口层开闸那一刻就是中心「起来了」的那一刻（[S-34](../../../spec/compositions/governance-center-entry/v1/contract.md#s-34-起来即整体停机时在途请求归谁)），而开闸由本节点在全部 fiber `ACTIVE` 之后放行（下文「两步开闸」一条），所以装载时两者谁先谁后都不会半开；
  这条先后要的是**撤除那一半**：本节点逆序撤除，入口层先撤，它关闸时发的 `stopped` 通知运维面还在听（两张面同起同停）。
  两者之间没有 inject 关系，**这条先后只由本清单保证**。
- 入口层必需 inject `logins`、`registration`、`organizations`、`memberships`、`offers`、`storage`、`credentials`、`clock`（最后一个只在启动时等钟可读用），运维面必需 inject `storage`、`clock`——都在前面装过；
  所以它们也纳入下一条的同步 `PENDING` 判定：前面任一面没起来（清单错误），入口层停在 `PENDING`，本节点在装它那一步就判清单错误、全撤、启动失败。
- **入口层不 `PENDING` 之后还要等钟可读**：[S-34](../../../spec/compositions/governance-center-entry/v1/contract.md#s-34-起来即整体停机时在途请求归谁) 以「中心的钟可读」为启动成功的条件，入口层在插件体里（开闸之前）等 `clock.now()` 给出一个时刻，上界是本节点给的 `clockReadyTimeoutMs`；
  超界 ⇒ 入口层插件体抛出 ⇒ `FAILED` ⇒ 本节点逆序全撤、恢复快照、启动失败，**说明里点名原因是钟**。这一步是 `await` 入口层 fiber 的一部分，不是本节点另设的等待。
- **`PENDING` 是结构判定，不是等待**：`ctx.plugin()` 返回后**同步**读 `fiber.state`，为 `PENDING` 即视为**清单错误**（它需要的服务不在前面装的插件里）⇒ 撤已装的 ⇒ 启动失败；**不设等待常量**。`core/kernel-basis` 的 `bootAssembly` 源码已按同一形状写（同步查 `FIBER_STATE.PENDING`，失败时逆序撤已装的）。
- **不 `PENDING` 就 `await` 它**：config 校验失败或插件体抛出 ⇒ fiber `FAILED` ⇒ `await` 拒绝（basis [`plugin-throw-fails-fiber`](../../../basis/cordis/plugin-throw-fails-fiber.md)）⇒ 按逆序撤除已装的 fiber ⇒ 快照未确认时由存储提供者恢复 ⇒ 撤完调 `guard.pending()` 核恢复有没有成（R-U8）⇒ 进程退出非零。**不半开**：一份漏配 `activation` 私钥的部署，`storage` 与 `clock` 已经 `ACTIVE` 也一起撤掉，而不是让 AI／OG 带病服务、注册每次 `interrupted`；入口层端口被占，前面七条 fiber 一起撤掉，升级的迁移随快照撤回。
- **两步开闸**：全部 fiber `ACTIVE` 之后确认快照（[升级的整体性](#升级的整体性迁移前只读核对快照与确认)）；确认成功才兑现入口层的 `openSignal`，入口层开闸、发 `serving`；本节点有界地等到 `serving`，`boot()` 才返回成功，等不到即启动失败（快照已确认、不恢复，缺口 U-4）。
  确认失败 ⇒ 不兑现（以拒绝结束）⇒ 逆序全撤 ⇒ 恢复快照 ⇒ 启动失败——闸从未开过（[两步开闸](#两步开闸就绪与开闸分开)）。
- **不用 `isolate`、不用 `intercept`**：一个部署一份实现、一份数据（basis [`isolate-hides-instances-not-data`](../../../basis/cordis/isolate-hides-instances-not-data.md)）；config 在 `ctx.plugin` 时直接传，没有向下注入的政策链。

|          | 只 `ctx.plugin` 八次、全靠 inject 自动排序（落选）                                                          | **清单顺序 + 同步查 `PENDING` + 逐个 `await`（选）**                                                                                |
| -------- | ----------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| 最强论证 | 内核本来就按依赖装；少写一个顺序                                                                            | 第一个失败的 fiber 是确定的；清单错误在装那一条时就暴露，不会静默挂起；运维面先于入口层这条先后没有 inject 关系可依，只有清单给得出 |
| 弱点     | 一个 `FAILED` 的 fiber 会让依赖它的全部停在 `PENDING`，进程看起来「起来了」但什么都不服务——正是要避免的半开 | 顺序是本节点维护的一份知识；加一个插件要放对位置。置信度：**高**（`bootAssembly` 已同形并有测试）                                   |

## 存储装配：迁移由 owner 导出片段、本节点合成

### 迁移的所有权

|          | 全部迁移写在本节点（落选）                                                                | **owner 导出 `Migration` 片段，本节点合成（选，与 `infra/clock` 同形）**                                                                                                                                                   | 本节点自己 `CREATE TABLE organization`、OG 只导出列定义（落选） |
| -------- | ----------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------- |
| 最强论证 | 只有装配同时看得见两边，一处就写全                                                        | 表是各 owner 事实的存储形状，列跟着 owner 的设计变；片段放在 owner 包里，**列的变化与迁移的变化在同一个包、同一次修改**——「迁移随 owner 列变化同步修改」这条代价落在最贴近变化的地方                                       | 跨 owner 那条外键能由本节点直接写进 `CREATE TABLE`              |
| 弱点     | **每次 owner 改列，本节点的迁移都要同步改**——两个包、两次修改，谁也不会因为漏改而编译失败 | 跨 owner 的那条外键**不能事后加**：sqlite 的 `ALTER TABLE` 不支持 `ADD CONSTRAINT`（外键只能在 `CREATE TABLE` 里声明），所以 OG 的片段要以**工厂参数**接收外键的目标与名字（[下文](#合成规则)）；两个 owner 包各多一个导出 | 一张 OG 的表由装配建，OG 的设计与它的表分家                     |
| 置信度   | —                                                                                         | **中高**：代价被搬到 owner 包里而不是消失；缓解见下                                                                                                                                                                        | —                                                               |

**代价与缓解**：owner 改了列（尤其是被外键引用的 `account.account_id` 或引用列 `organization.owner_account`），本节点合成时传给工厂的参数就对不上——
这类错误**不会在编译期暴露**。缓解三条：① 本节点的 `assembly.fk-organization-owner-account` 与 `assembly.constraint-names-resolve` 在装配的 CI 里跑，对不上即红；
② owner 片段带自己的幂等测试（归各 owner）；③ 外键的目标与名字只在本节点一处出现（合成函数的两个参数），改名只改一处。

### 合成规则

```text
hostMigrationFragments = [
  ...accountIdentityMigrations,                                // AI 包导出：一个片段 account_identity（account、login_state）
  ...organizationGovernanceMigrations({                        // OG 包导出的工厂：六张表，片段名即表名
    ownerAccountReference: { table: ACCOUNT_TABLE, column: ACCOUNT_ID_COLUMN },   // 'account'、'account_id'，取 AI 包导出的常量
    ownerAccountForeignKey: ORGANIZATION_OWNER_ACCOUNT_FK,     // 'organization_owner_account_fk'；ON DELETE RESTRICT，不延迟——由工厂内的 CREATE TABLE 声明
  }),
  ...clockMigrations,                                          // clock 包导出：一个片段 clock_lease（只带 up）
  ...governanceCenterMigrations,                               // governance-center-entry 包导出：governance_center 建表 + 一行未铸的占位
  // ↓ 本程追加（设计已接受，尚未实现）：只追加在末尾（M-9）
  ...organizationGovernanceV3Migrations,                       // OG 包单独导出：organization、membership 各加一列时刻（可空）
  ...assetGovernanceMigrations,                                // asset-governance 包导出：资产、流转两组表与显式命名的唯一索引
  ...modelProfileDirectoryMigrations,                          // model-profile-directory 包导出（片段与表名以该节点为准）
]
provider = composeMigrations(hostMigrationFragments)
```

（`src/migrations.ts`；`composeMigrations` 归 [`core/storage`](../../packages/core/storage/design.md#迁移片段与迁移前核对的共用形状)：按给定次序给片段编号名 `0001_<片段名>`、`0002_…`，片段重名即抛，交给 Kysely `Migrator` 的 `MigrationProvider`。`Migrator` 自己的登记表是 `kysely_migration` 与 `kysely_migration_lock`。）

- **次序**：AI 片段先于 OG 片段（外键目标要先存在）；`clock_lease` 与 `governance_center` 两张表不引用任何别的表，与其他迁移次序无关，放最后一批。
- **编号名一经发布不改、不重排；新片段只追加在末尾**（M-9）。升级前的只读核对以「库里登记过的迁移名序列是否为本次合成序列的前缀」判数据格式能否接手（[下文](#升级的整体性迁移前只读核对快照与确认)），重排一次，所有旧库就都被判成接不了。
- **跨 owner 的外键归本节点**：目标（`account.account_id`）、名字（`organization_owner_account_fk`）、`ON DELETE RESTRICT`、不延迟，都由本节点作为参数给出；OG 的片段只负责把它写进 `organization` 的 `CREATE TABLE`。OG 的包因此**不 import** AI 的包——它只收到两个字符串。
- **有数据的片段**：`governanceCenterMigrations` 不只建表，还**插入一行占位**（`slot = 'center'`，未铸状态；列与「未铸」的表示以 [governance-center-entry 节点](../../packages/tenancy/governance-center-entry/design.md#中心标识迁移片段与读或铸)为准），入口层启动时把它铸成标识。它的幂等是**存在即不插**：那一行已在（占位或已铸）就不插、不覆盖、不重置——否则重跑迁移会把已铸的标识打回未铸（M-1）。
- **本节点不改任何片段的内容**；`clock_lease`、`governance_center` 原样合入。

### 同一存储、同一约束域：本节点要保证的三件事

两个 tenancy 节点跨 owner 的「同一提交」不是靠事务句柄，而是靠**两个写入者共同触碰的存储对象**——推理在
[AI「过期事实」](../../packages/tenancy/account-identity/design.md#已过留存期限是首次观测时落盘的单调事实不是每次读时重算的谓词)与
[OG「跨 owner 的同一提交」](../../packages/tenancy/organization-governance/design.md#跨-owner-的同一提交账号行上的过期事实加组织行对账号行的引用约束)，本页不重复。
那两个对象是 **账号行（`account.expired_at` 一列，在 `lockRow` 下落盘）** 与 **外键 `organization_owner_account_fk`**。它们存在的前提全在装配：

1. **恰一个 `storage` 实例、恰一个库文件**：AI、OG、clock、入口层、运维面解析到的是同一个 `provide('storage')`。两个实例指向两个文件时 sqlite 无法跨库建外键，孤儿组织立刻可达且无声——本节点的装载清单里只允许一个 `storageSqlPlugin`（`assembly.manifest-shape`，[verification](verification.md#证据义务)）。
   **同一条也兑现中心标识那一侧**：`governance_center` 与全部治理事实在这一个实例、这一个库里，备份库就备份了标识、恢复库就恢复了标识——
   与 [governance-center-entry 的 R-GC6](../../packages/tenancy/governance-center-entry/design.md#对存储提供者的要求清单) 互指（[S-28](../../../spec/compositions/governance-center-entry/v1/contract.md#s-28-铸造存放与不变) 性质 2、[S-36](../../../spec/compositions/governance-center-entry/v1/contract.md#s-36-装配给的保证-vs-协议须给的保证)「中心标识与治理事实同一存储」行）。把标识放进库旁的文件或另一个 `storage`，「只备份了库」就会把它丢掉。
2. **两张表由同一份合成的 `MigrationProvider` 建在同一 schema**：AI 片段在前、OG 片段在后，外键目标由本节点传入。
3. **那条外键真的存在且 `foreign_keys=ON`**：一致性套件只证提供者会把违反报成两向（[core/storage 覆盖缺口](../../packages/core/storage/verification.md#覆盖缺口)明写「装配还欠一条检查」）；真实外键的存在由本节点的测试 `assembly.fk-organization-owner-account` 证。

**自构的两条反证**：(a) 装配把 AI 与 OG 装在两个 `isolate` 标签下各给一个 `storage`——两个库、无外键，S-20 与 S-38 的交错终态「个人组织在、账号不在」可达；本节点不用 `isolate` 就是为此。(b) 合成时给工厂传了 `DEFERRABLE INITIALLY DEFERRED`——S-20 插入指向已删账号的组织行时语句不报错、COMMIT 才报，OG 的「提交内重读 ⇒ `accountDoesNotExist`」分支永远走不到；M-4 挡它。反证不了的部分——两条交错本身的终态——归 AI S-43 第 2 支的三节点真并发演练，本节点只提供夹具。

### 升级的整体性：迁移前只读核对、快照与确认

[PF-017](../../../product/PF-017-governance-center-as-deployable-application/README.md)（rev 2）[§6.9](../../../product/PF-017-governance-center-as-deployable-application/design.md#69-升级同一个中心要么整体成要么整体不成) 要求升级整体成或整体不成：起不来，数据必须还是升级前的样子，旧版本照常能起；
[§6.6](../../../product/PF-017-governance-center-as-deployable-application/design.md#66-要么整个起来要么不起来) 与 [§6.10](../../../product/PF-017-governance-center-as-deployable-application/design.md#610-时间不能倒着走) 要求「版本接不了这份数据」「钟比中心用过的最晚时刻早」时不起来、数据原样不动，并告诉运维者差的是哪一样。
**没有一份契约拥有这一条**——入口契约把启动的收场归承载装配（[S-32 末段](../../../spec/compositions/governance-center-entry/v1/contract.md#s-32-进展性质与前提)）——所以本节点直接承接产品要求：**编排归本节点，快照机制归存储提供者**。

```text
[起插件之前]       根 Context 只挂日志；config 解析、密钥配对自检    —— 失败：不碰数据
[storage-sql 插件体，upgrade: { checks, guard }；guard 由本节点 createUpgradeGuard() 构造]
  ① 取独占；guard 挂到本实例                                        —— 失败：「被占」，不碰数据
  ② 有遗留快照 ⇒ 先恢复（上一次启动没确认就断了）
  ③ 只读核对，一次只读事务：数据格式版本能否接手；时钟未回拨；
     非空数据里有 governance_center 表                               —— 失败：不碰数据（指内容，见下）
  ④ 有待跑迁移 ⇒ 建快照（sqlite）
  ⑤ 迁移（pg：一个事务）
  ⑥ provide('storage')
[其余七条 fiber]    clock … governance-center-entry                  —— 任一失败：逆序全撤，storage 撤除时恢复快照
                    （入口层到此端口已绑、闸关着；对外没有任何提交）
[全部 ACTIVE]       guard.confirm() ⇒ { migrated, snapshotTaken, snapshotRemoved }；断言 snapshotTaken ⇒ snapshotRemoved；
                    migrated ∧ ¬snapshotTaken（pg）⇒ 不拒起，启动日志具名「本次升级不可撤回（U-3）」
                                                                      —— 抛出（含 UpgradeGuardNotAttached）或断言不成立：不兑现 openSignal，逆序全撤，恢复快照
[确认之后]          兑现 openSignal ⇒ 入口层开闸、发 serving ⇒ boot() 返回成功  —— 有界等不到 serving：逆序全撤，不恢复（U-4）
[任一次逆序撤完之后] guard.pending()：`pending { location }` ⇒ 「升级未确认：恢复失败，快照在 X」（R-U8）；`clear` 或 `never-attached`（被占、config 失败等根本没走到守卫）⇒ 不另报
```

「不碰数据」在 sqlite 上指**内容**不变：关最后一个句柄时 sqlite 会把预写日志检查点进库文件，已提交内容不变、字节可能变；上一次是干净关闭（预写日志为空）时才逐字节不变（[storage-sql 实施缺口](../../packages/infra/storage-sql/design.md#实施缺口与消费者影响)）。

| 最强论证 | 不改 storage-sql；整个升级在一处代码里看得见     | 「库是一个文件」「预写日志里还有已提交的内容」「pg 没有文件」只有存储提供者知道；装配知道了就是胶水拥有存储机制（[红线](../../AGENTS.md#红线)），换 pg 整段作废 |
| 弱点     | 同左                                             | storage-sql 的设计与源码都要改（R-U1～R-U8 全是新增）；确认要一个存储协议之外的导出（守卫对象）。置信度：**中高**                                               |

#### 守卫对象：确认绑在实例上，不绑在 config 上

确认与撤后核查若以 config 为键（按 config 算出快照位置去删、去看），装配只要交错一份 config——交给插件的是 A、确认时用的是 B——就会走出这条链：在 B 的位置找不到快照 ⇒ 当作「没有待确认的升级」返回成功 ⇒ 本节点兑现 `openSignal`、入口层开闸、答复提交 ⇒ 之后任一次撤除，storage-sql 在真实位置看到快照仍在 ⇒ 恢复 ⇒ **答复过的写消失**，恰是[两步开闸](#两步开闸就绪与开闸分开)要排除的那件事。所以确认绑在**实例**上：

- 本节点 `const guard = createUpgradeGuard()`（storage-sql 包导出），storage 的 config 写 `upgrade: { checks, guard }`；插件体取到独占之后把 `guard` 挂到本实例，快照在哪只有实例自己知道。
- `guard.confirm()` 返回 `{ migrated, snapshotTaken, snapshotRemoved }`；`guard` 没挂到任何实例 ⇒ 抛 `UpgradeGuardNotAttached`。本节点断言 **`snapshotTaken ⇒ snapshotRemoved`**——「拿了快照就必须删到」是守卫自己的不变量，与方言无关：拿了快照却没删到，说明确认没落在那个快照上 ⇒ 启动失败，具名原因「升级确认没有删到快照」。两种失败都在兑现 `openSignal` 之前，都走「逆序全撤 ⇒ 恢复快照」，闸从未开过。
- **`migrated ∧ ¬snapshotTaken` 就是 U-3**：pg 上没有快照，`snapshotTaken` 为假、断言自然成立；跑过迁移而没有快照，这次升级在迁移提交之后撤不回。**不拒起**，启动日志具名写「本次升级不可撤回（U-3）」，与[实施缺口 U-3](#实施缺口与消费者影响) 互指。sqlite 上有待跑迁移就一定拿快照（R-U3），这一支只在 pg 上出现。
- `guard.pending()` 不抛，三种结果：`never-attached`（守卫从未挂上实例——被占或 config 失败时的常态）、`clear`、`pending { location }`；只有最后一种要在启动失败说明里点出位置，是 R-U8 的撤后核查。
- **前提**（与入口层的 `openSignal` 同一条）：守卫的**引用**经 config 原样到达插件体——**已取证（2026-09-23）**：顶层 config 会被 zod 校验重建，但 `z.custom` 放行的值同引用、不冻结、重跑时仍是同一个；所以 storage-sql 的 Config 用 `z.custom` 描述 `guard` 与各 check（[入口层节点「依赖的上游机制语义」](../../packages/tenancy/governance-center-entry/design.md#依赖的上游机制语义)同一行）。不成立时插件体拿到的是拷贝，挂上去的不是本节点手里那一个 ⇒ `confirm()` 抛 `UpgradeGuardNotAttached` ⇒ 启动失败：**失败是响的**，不会退回「找不到 ⇒ 成功」。

|          | `confirmUpgrade(config)`／`pendingUpgrade(config)`，以 config 为键（落选） | **守卫对象随 config 传入，确认绑在实例上（选）**                                                                                                                                                   |
| -------- | -------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 最强论证 | 不依赖「内核原样传递 config」；两个函数无状态                              | 交错一份 config 不再能「找不到 ⇒ 成功」：没挂上即抛，挂上了只认本实例的快照；与 `openSignal` 同一模式，装配里只有一种「运行时对象随 config 进插件」的写法                                          |
| 弱点     | 交错 config ⇒ 静默成功 ⇒ 开闸后撤除时恢复 ⇒ 答复过的写消失，只有日志看得出 | 依赖上面那条前提（已取证）；多一个导出类型与一种异常；返回值多一位 `snapshotTaken`，断言才与方言无关（pg 上 `snapshotTaken` 为假，`migrated ∧ ¬snapshotTaken` 只记日志、归 U-3）。置信度：**中高** |

确认放在哪、开闸与它谁先谁后，见下一节[两步开闸](#两步开闸就绪与开闸分开)。

**自构的四条反证**：
(a) 迁移跑完，clock 启动时检出回拨（或入口层端口被占）⇒ 逆序全撤 ⇒ storage-sql 撤除时恢复快照 ⇒ 库回到升级前、迁移登记仍是旧序列 ⇒ 旧版本的只读核对通过、照常能起。成立。
(b) 首次启动：入口层铸出标识、端口已绑；确认之前进程被杀 ⇒ 下一次启动见遗留快照「库不存在」⇒ 删库 ⇒ 重铸出另一个标识。要成为反例，得有人在这之前读到过第一个标识，或有一次对外提交随恢复消失——但入口层的闸在 `openSignal` 兑现之前关着、运维面在 `serving` 之前不答，兑现又在确认之后：**反证不成立**。非首次启动同理，确认之前没有对外提交可丢。残余落在确认之后，见缺口 U-4。
(c) 两个进程同时对同一份库启动：A 建快照、迁移；B 的只读核对读到 A 迁移到一半的登记，或在 A 恢复时握着被替换掉的文件。本节点自己挡不住（多实例是 [PF-017 非目标](../../../product/PF-017-governance-center-as-deployable-application/design.md#非目标)，运维面的残留套接字检查在迁移之后才跑）；挡它的是存储提供者的属主独占——插件体第一步取、撤除最后一步放、随进程死亡释放，B 在第一步即「被占」（[storage-sql 交错 (a)(b)](../../packages/infra/storage-sql/design.md#自构的交错)）。已实现：sqlite 在库旁的 `<file>.owner-lock` 上持锁，pg 持会话级咨询锁；两进程同时 `boot()` 的真并发演练在 `tests/process.spec.ts`（交错 I-9）。pg 的锁连接断开时的收场未定，缺口 U-2。
(d) pg：迁移事务已提交，之后入口层端口被占 ⇒ 撤不回。R-U7 只给迁移本身的原子：pg 上「迁移单事务」成立，「迁移后装配失败回滚」不成立——**PF-017 §6.9 在 pg 上本程不兑现**，显式缺口 U-3，pg 第一次跑之前定手段。
(a) 由 [verification](verification.md#证据义务) 的 `assembly.upgrade-restore-on-boot-failure` 真跑；(b) 的反面由 `assembly.no-commit-before-open` 演练；(c) 由 storage-sql 的 `upgrade.exclusive-owner`（两个子进程真跑）证，本节点另加两进程同时 `boot()` 的装配演练；(d) 眼下写不出会通过的测试。两者都记在 [verification 覆盖缺口](verification.md#覆盖缺口)。

### 两步开闸：就绪与开闸分开

入口层开闸就是中心「起来了」（[S-34](../../../spec/compositions/governance-center-entry/v1/contract.md#s-34-起来即整体停机时在途请求归谁)），确认快照就是升级的不可回退点（R-U6）。两者做不成一个原子动作；本节点把次序定成**先确认、后开闸**，开闸有没有发生由有界地等 `serving` 判定：

```text
全部八条 fiber ACTIVE   入口层：端口已绑、闸关着、标识就绪、钟已读到；运维面：套接字已绑、不答
  ↓ guard.confirm()（R-U6）抛出或 snapshotTaken ⇒ snapshotRemoved 不成立 ⇒ 拒绝 openSignal ⇒ 逆序全撤 ⇒ storage 撤除时恢复快照 ⇒ 启动失败
  ↓ 兑现 openSignal      入口层的续延：再读钟 → emit serving → 开闸
  ↓ 等 serving（有界）    收到 ⇒ boot() 返回成功；超界 ⇒ 逆序全撤、启动失败，快照已确认、不恢复（U-4）
```

- **`openSignal`** 是本节点在装入口层之前构造的一个 Promise，经入口层 config 传入；它是运行时对象，只能由装配在装载时构造，不来自环境变量。入口层插件体**不** `await` 它：插件体不返回，入口层就停在 `LOADING`，本节点等不到「全部 `ACTIVE`」，放行永不发生——入口层节点[就绪与开门为什么分两步](../../packages/tenancy/governance-center-entry/design.md#就绪与开门为什么分两步)。
- **开闸之前没有任何对外提交**：入口层的闸关着、连接一律关闭不答；运维面在 `serving` 之前不答；其余 fiber 没有自己的对外入口。确认之前的写只有启动自身的写——迁移、`clock_lease`、首次启动铸的中心标识——没有人读到过它们，恢复快照把它们一起撤回（反证 (b)）。
- **确认失败**（`guard.confirm()` 抛出——含守卫没挂上的 `UpgradeGuardNotAttached`——或 `snapshotTaken ⇒ snapshotRemoved` 不成立，[守卫对象](#守卫对象确认绑在实例上不绑在-config-上)）：不兑现，以拒绝结束 `openSignal`（入口层的续延吸收这次拒绝，闸保持关着）⇒ 逆序全撤 ⇒ storage-sql 撤除时恢复快照（R-U4）⇒ 启动失败，说明写「升级确认失败」并带具名原因。
- **确认之后**：此后的进程死亡按「升级已完成、中心停着」收场——库是新版本的完整数据，没有写到一半的东西；下一次用同一版本启动没有遗留快照、没有待跑迁移，照常起来。旧版本起不来是升级完成的正常后果，不是 §6.9 说的「升级到一半」。
- **本节点对入口层的要求**：兑现之后到开闸，除进程死亡外**不要有让中心起不来的失败支**——那一段在确认之后，失败就是「库已升级、中心没起来、旧版本也起不来」。入口层节点在开闸那一刻再读一次钟、超界即放弃开闸（该节点「`startedAt` 开门那一刻再读一次」一表与其 N-12）：那一支正落在这一段里，即 U-4——已接受的残余情形（裁 (b)）。
- **`boot()` 在兑现之后有界地等 `serving`**：入口层在开闸之前已是 `ACTIVE`，开闸那一刻的失败不能再让它 `FAILED`，本节点只能从「等不到 `serving`」得知（入口层节点 N-12）。
  本节点在装入口层之前，在根 Context 上登记一个 `serving` 通知的监听（只记录、不做控制；`emit` 同步派发，[`async-control-not-bail`](../../../basis/cordis/async-control-not-bail.md)），兑现之后等它，上界 = `clockReadyTimeoutMs` 加 `SERVING_GRACE_MS`（1 s，盖住入口层开闸时那一次再读钟的上界）。
  等到 ⇒ `boot()` 返回成功。超界 ⇒ **启动失败**，说明点名原因是钟、写「钟读不到或回拨：重启前先核钟」，逆序全撤；**快照不恢复——它在兑现之前已确认、已不存在**（下表）。这一支就是 U-4，**已接受的残余情形（裁 (b)）**：库已是新版本的完整数据、没有已确认的提交丢失；老版本不能再起。钟若只是暂时读不到，同一版本重启即照常起来；钟若往回拨了，照原样重启会在迁移前的只读核对（`clockPreflight`）上再次失败——所以说明写「重启前先核钟」，而不是「重启即可」。
  这个监听由本节点显式注销（`context.on` 返回的注销函数，在失败收场与撤除开始时各调一次），不依赖根 Context 的撤除收回它。

| -------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |

`synchronous` 按 D-039 显式给 storage-sql 的 `full`；WAL 下依赖底层正确兑现同步请求。没有降档环境开关。

**`upgrade` 必须显式给**（[storage-sql「守卫为什么显式开启」](../../packages/infra/storage-sql/design.md#守卫为什么显式开启)）：config 带 `migrations` 时，`upgrade` 只能是 `{ checks, guard }` 或 `false`，**缺席即配置错误** ⇒ storage-sql 的 Config 拒 ⇒ fiber `FAILED` ⇒ 启动失败——「忘了开守卫」不再静默退回「只有幂等」。

- **生产装配（本节点的 `boot()`）给 `{ checks, guard }`**：`checks = [数据格式核对, clockPreflight(), governanceCenterPreflight]`（[升级的整体性](#升级的整体性迁移前只读核对快照与确认)），`guard = createUpgradeGuard()`（[守卫对象](#守卫对象确认绑在实例上不绑在-config-上)）；本节点没有「不开守卫」的分支，也不从环境变量读这一项。
- **测试装配**（kernel-basis 的 `bootAssembly`、一致性套件、各节点的场景演练）若不走守卫，写 `upgrade: false`——那是显式声明「这份库不是生产库」，下一节的运维约定因此成立。

### 运维约定（owner：本节点）

以下两条在节点内防不住、也没有证据形式，只能作为部署与运维的约定写下；两条并列，出处各自互指：

- **生产库不得被非守卫实例打开**——一致性夹具、命令行工具、误配的第二个部署都算。非守卫实例（`upgrade: false`）不取独占、不看也不建快照：它可能在一个尚未确认的升级脚下写库（那些写随后被恢复撤掉），或在属主恢复快照时握着被替换的文件。与 [storage-sql「排他为什么是随进程死亡释放的锁」](../../packages/infra/storage-sql/design.md#排他为什么是随进程死亡释放的锁)互指：排他只在属主之间成立。
- **库文件与其中 `clock_lease` 一行不得手工改动（租约表不得手动删）**——删了它，`now` 不后退就失去依据（[时钟装配](#时钟装配)末条；[clock 覆盖缺口](../../packages/infra/clock/verification.md#覆盖缺口)）。
- **客户端一面默认只监听本机或私有网络；公网暴露须有前置的网络边界**——入口契约明确不承诺限流与登录试探防护（[S-3](../../../spec/compositions/governance-center-entry/v1/contract.md#s-3-本契约明确不承诺什么)），注册与登录路由对任何能到达端口的连接开放；第一版按「自己人开发与实验」定基调（D-029），登录状态没有寿命只有撤销，出实验之前那一条必须先闭合。

## 时钟装配

- 装 [`infra/clock`](../../packages/infra/clock/design.md) 的 `clockPlugin`，`provide('clock')` **恰一次**——[OE S-17 第 1 行](../../../spec/data/offer-expiry/v1/contract.md#s-17-装配给的保证-vs-协议须给的保证)「同源可比」的装配那一半；另一半（消费者不得另用 `Date.now()`）是 `tools/ts-checks` 的 `no-wall-clock` 规则（扫描根含 `packages/` 与 `apps/`，只豁免 `infra/` 与测试，所以对本节点同样生效；本节点的日志时间戳由 Cordis 在写日志时取，本节点不读墙钟）。
- **config 是空对象**（源码 `ClockConfig = z.object({}).strict()`）：租约宽度与续约周期是包内常量；要可配时由它加 config 并走同一条「非法即启动失败」。
- 它 `inject: ['storage']`，所以装在 `storage` 之后；它的片段 `clockMigrations` 已合入本节点的 `MigrationProvider`，表在它的启动判定之前已存在——缺了这一步，启动判定读表得 `StorageDefect` ⇒ 抛出 ⇒ 启动失败（clock 包内测试已覆盖「缺迁移 ⇒ 启动失败」）。
- **启动期两种失败都是抛出 ⇒ fiber `FAILED` ⇒ 整个装配启动失败**：① 启动判定那次写失败（`StorageUnavailable`／`StorageDefect`）；② **检出回拨**（`wall < written_at`）——源码抛 `ClockRollbackDetected`。回拨是环境错误，与「打不开库即启动失败」同一政策，不半开着提供一个永远 `'unavailable'` 的时钟。**运行期**的「崩溃后快速重启落在旧租约窗口内」「续约写失败」仍是 `now()` 返回 `'unavailable'`——那是抖动，不是环境错误；AI 映射 `storage-unavailable`、OG 映射 `unavailable`，入口层再映射成线上的 `unavailable`，本节点不介入。
- **启动成功以钟可读为条件**（[S-34](../../../spec/compositions/governance-center-entry/v1/contract.md#s-34-起来即整体停机时在途请求归谁)）：崩溃后快速重启落在旧租约窗口里时，`now()` 至多一个租约宽度答 `'unavailable'`；入口层在开闸前等它可读，上界 `clockReadyTimeoutMs` 由本节点给、必须大于 clock 包导出的 `LEASE_WIDTH_MS`（[其余 config](#其余-config候选变量名)），所以快速重启只是起得慢一点，不会启动失败；超界仍读不到才是启动失败。
- **迁移之前还有一次只读的回拨核对**：`clockPreflight()`（[clock「迁移前的只读回拨核对」](../../packages/infra/clock/design.md#迁移前的只读回拨核对)），判据与 clock 启动判定同一个纯函数，本节点放进 storage-sql 的 `upgrade.checks`（[升级的整体性](#升级的整体性迁移前只读核对快照与确认)）；clock 插件自己的启动判定照旧，迁移之后检出回拨就走「全撤 ⇒ 恢复快照」。
- **启动时的窄带**（[clock「启动时的租约窗口」](../../packages/infra/clock/design.md#启动时的租约窗口与入口层等钟)的读法）：上一次是崩溃退出、且启动时的回拨幅度小于租约宽度时，clock 分不出「回拨」与「快速重启」，按快速重启**等墙钟追上用过的最晚时刻再起，不拒起**；[PF-017 §6.10](../../../product/PF-017-governance-center-as-deployable-application/design.md#610-时间不能倒着走) 第 1 行「启动时钟比它早就不起来」在这一窄带里读作「追上之前不起来」——「不用比用过的最晚时刻更早的时刻」仍成立。上一次是干净撤除时，任何回拨都是确定回拨、启动失败。等待至多一个租约宽度，落在 `clockReadyTimeoutMs` 之内。
- **运行中钟往回倒**：[S-36](../../../spec/compositions/governance-center-entry/v1/contract.md#s-36-装配给的保证-vs-协议须给的保证) 末行把它定为装配给——时钟提供者在运行中检出回拨、让 `now()` 答 `'unavailable'`，入口层据此答 `unavailable`、运维面的 `clockSane` 答 `false`（[PF-017 §6.10](../../../product/PF-017-governance-center-as-deployable-application/design.md#610-时间不能倒着走)「开着时往回倒」那一行）。**本节点转交 `infra/clock`**：它的 `now()` 每次现读墙钟、与用过的最晚时刻比对，早于它即答 `'unavailable'` 直到追上（[clock「运行中回拨」](../../packages/infra/clock/design.md#运行中回拨每次现读墙钟比对用过的最晚时刻)）——已实现（与 governance-center-entry 的 N-5 同一件事）。
- **测试装配不用本节点的时钟**：需要前推时间的演练（AI S-41、OG S-47）用 `core/offer-expiry` `./testing` 的 `testClock(start)`（`advance` 只前推、`setUnavailable`）经 kernel-basis 的 `bootAssembly` 作为 `services` 传入；那不是本节点的清单。
- **租约表被外部删除**无法在节点内防御（[clock 覆盖缺口](../../packages/infra/clock/verification.md#覆盖缺口)）：本节点把它写成运维约定——库文件与其中 `clock_lease` 一行不得手工改动（[运维约定](#运维约定owner本节点)，与「生产库不得被非守卫实例打开」并列）；没有证据形式。

## 密钥装配：两对 Ed25519 密钥作为部署配置输入

**两对密钥、四份 PEM**：`activation`（私钥 → `account-registration`，公钥 → `account-identity`）、`purge`（私钥 → `organization-governance`，公钥 → `account-identity`）。
形式与「不在启动时生成、跨重启不变」的前提归 [identity-values 节点](../../packages/core/identity-values/design.md#依赖作用域与绑定)；本节点定**从哪读、给谁、缺了怎么办、配没配对**。

**这四份 PEM 就是本装配对 [PF-017 部署密钥](../../../product/PF-017-governance-center-as-deployable-application/design.md#部署密钥)的兑现形式**（PF-017 decisions 推导 12 以「技术侧需要一套部署级秘密」为前提，就是这一套）。
完整体检的 `deploymentKeyPresent`／`deploymentKeyComplete` 是「启动时载入的结果」（[S-26](../../../spec/compositions/governance-center-entry/v1/contract.md#s-26-完整体检)）：四份都有来源即「在」，四份都合形状且两对都配对即「完整」；任一不成立本来就启动失败，
所以本节点在配对自检通过之后给运维面的 config 传字面 `{ present: true, complete: true }`，**不传任何 PEM**。入口层的 TLS 证书链与私钥**不是**部署密钥（[S-3](../../../spec/compositions/governance-center-entry/v1/contract.md#s-3-本契约明确不承诺什么)），不算进这两项。

### 来源：环境变量或文件路径，`_FILE` 惯例

| 变量（`src/config.ts` 的 `ENV`）                              | 内容                                           |
| ------------------------------------------------------------- | ---------------------------------------------- |
| `OMNE_TENANCY_ACTIVATION_SIGNING_KEY_PEM` / `…_PEM_FILE`      | activation 私钥（PKCS#8 PEM）的文本 / 文件路径 |
| `OMNE_TENANCY_ACTIVATION_VERIFICATION_KEY_PEM` / `…_PEM_FILE` | activation 公钥（SPKI PEM）                    |
| `OMNE_TENANCY_PURGE_SIGNING_KEY_PEM` / `…_PEM_FILE`           | purge 私钥                                     |
| `OMNE_TENANCY_PURGE_VERIFICATION_KEY_PEM` / `…_PEM_FILE`      | purge 公钥                                     |

规则：**每份密钥恰一个来源**——两个变量都缺 ⇒ 启动失败；两个都设 ⇒ 二义 ⇒ 启动失败；文件读不到 ⇒ 启动失败；
文件不是普通文件，或对 group／other 可读（POSIX 权限位，先打开再对同一句柄取 `stat`，不查一个路径读另一个文件；DSH 的先例是 `0600`，[研究](../../../../research/agent-harness-persistence-and-identity-infra/research.md#第二部分身份基础设施)）⇒ 启动失败。
内联变量取值就是 PEM 文本本身（含换行）；base64 一行的形式本版不支持。

|          | 只支持环境变量（落选）             | 只支持文件路径（落选）                                              | **两条都支持，`_FILE` 惯例，二义即失败（选）**                                                                           |
| -------- | ---------------------------------- | ------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| 最强论证 | 12-factor 的正统；一条代码路径     | 秘密不进 `/proc/<pid>/environ` 与子进程继承；权限位可查（DSH 先例） | 容器与本机两种运行方式各得其所；`_FILE` 是 Docker 官方镜像的通行惯例                                                     |
| 弱点     | 多行 PEM 在 shell 里难写；泄露面大 | 本机开发要先写文件                                                  | 两条代码路径、一条二义规则。置信度：**中**——两条路的取舍在研究里是并列的，没有一方被否定；主线可裁掉一条，本节点只删一列 |

### 配对自检：起 Context 之前签一次、核一次

四份 PEM 各自形状合法，**不等于**两把私钥与两把公钥两两配对——一份用两次 `keygen` 拼出来的部署，每个持钥插件都能启动，
而注册主链的 ③ 与清除链的 ② 会**永远** `warrant-invalid`／`purge-warrant-invalid`。没有哪个插件能单独发现这一点（各自只见一把钥匙），所以它归装配。
在装任何插件之前（根 Context 此时只挂了日志、没有任何插件 fiber、未碰数据），对两对各做一次（`src/keys.ts` 的 `verifyKeyPairing`，失败是具名阶段 `key-pairing`，点名是哪个变量或哪一对）：

```text
signing      = loadSigningKey(privatePem)          // 不合 ⇒ 启动失败
verification = loadVerificationKey(publicPem)      // 不合 ⇒ 启动失败
warrant      = issueHandoffWarrant(signing, purpose, PROBE_ACCOUNT_ID)
verifyHandoffWarrant(verification, purpose, PROBE_ACCOUNT_ID, warrant) === 'ok'   // 否则 ⇒ 启动失败
```

`PROBE_ACCOUNT_ID` 是一个固定的、只在此处使用的合法 `AccountId` 字面（`tenancy-host-key-pairing-probe`），凭证不落库、不外流。
**四个原语全是 identity-values 已有的公开入口**——本节点不新增任何能力，也不重复 `loadSigningKey` 的形状校验之外的逻辑：形状仍由持钥插件的 Config 各自核（下表），
装配层只多核**跨插件的配对**这一件事。它是 AI bindings 里「activation／purge 私钥只由产出方持有且与本节点的公钥配对……由装配兑现」那条前提的保护点。

### 谁核形状：持钥插件的 Config，不是装配；谁核配对：装配

|          | 装配层用 `loadSigningKey`／`loadVerificationKey` 预核形状，再传给插件（落选） | **形状由三个插件各自的 Config（经 `definePlugin`）核；配对由装配核（选）**                                                                                                                                                     |
| -------- | ----------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 最强论证 | 更早失败（config 解析阶段就退出，不必等装到 AR）                              | 「配置错误 ⇒ 启动失败」只有**一个实现点**（[kernel-basis](../../../../../packages/core/kernel-basis/SPEC.md)）；三个持钥节点的设计都已把形状校验写在自己的装卸表里。配对是**跨插件性质**，只有装配看得见两把钥匙 |
| 弱点     | 同一件事两处做；插件的校验被架空后将来独立测不到                              | 配对自检本身要先 `load*Key`——形状校验事实上跑了两遍（自检一遍、插件 Config 一遍），但**政策仍只有一个实现点**，自检失败也是同一收场。置信度：**高**                                                                            |

**来源缺失（变量与文件都没有）是装配层的配置错误**，在 config 解析阶段就启动失败，不等到插件；这与「形状由插件核」不冲突：前者是「有没有」，后者是「对不对」，配对是「合不合」。

### 私钥不经服务 store 可达

- 私钥只出现在 `account-registration` 与 `organization-governance` 两个 config 对象里，公钥只出现在 `account-identity` 的 config 里；入口层的 TLS 私钥只出现在入口层的 config 里，运维面的 config 里没有任何 PEM；本节点**不 `provide`、不 `mixin` 任何持钥服务**，启动失败的结构化记录只写变量名，不写值。
- **但「不进 ctx」这句话不成立**：每个持钥插件的 config 挂在它自己的 fiber 上，同进程任何拿到根 `Context` 的代码都能沿 fiber 树读到它。单进程内没有硬隔离——「私钥不外泄」是装配纪律，[identity-values 覆盖缺口](../../packages/core/identity-values/verification.md#覆盖缺口)已明写没有可机检的完整形式。
- 本节点给的证据因此**只到两件事**：config 对象里 PEM 字段的归属恰如上表；服务 store 里没有任何含 PEM 文本的值（[verification](verification.md#证据义务)）。**不声称**别的代码读不到。

### `keygen` 与重生的后果

- 导出函数 `generateKeyFiles(directory)`：调 `generateHandoffKeyPair()` 两次，以排他方式写四份 PEM 文件（`0600`；目录不存在即以 `0700` 建出）；四份里任一已存在 ⇒ 删掉本次建出的、一份都不留，抛 `KeyFilesExist`；不读任何配置、不连库。进程子命令 `tenancy-host keygen <dir>`（`src/main.ts`；[PF-017 §8](../../../product/PF-017-governance-center-as-deployable-application/design.md#八边界与依赖) 把「命令怎么拼」交给技术设计）在标准输出写一行 JSON，给出四个 `_FILE` 变量与路径（`KEY_FILES`），不含密钥内容。
- **本版不轮换。**重生密钥等于换钥：已签发、尚未核实的凭证一律核不过——注册主链两步之间重启并换钥 ⇒ ③ `warrant-invalid` ⇒ `interrupted`，重来会重新产出；清除链两步之间换钥 ⇒ ② `purge-warrant-invalid`（缺陷型）⇒ 重扫时 ① 幂等再签。**两条都是契约已定义的收场，不需要迁移期**；换钥须在进程停止时做，运行中换钥的语义本版不定义。

### 装载清单与撤除次序

新的顺序见[装载清单](#装载清单与顺序)的代码块：资产提供者与 P-1 装在 AR 之后、运维面与入口层之前（它们 inject 的 OG 面已在前面；资产提案原话「排在组织治理之后、运维面与入口层之前」）。两者之间没有 inject 关系，谁先谁后不影响正确性，本节点取「资产在前」只为撤除次序可解释。
同步 `PENDING` 判定、逐个 `await`、任一 `FAILED` 逆序全撤并恢复快照，都照已实现的规则走，**不新增等待常量**。逆序撤除变为：入口层 → 运维面 → P-1 → 资产提供者 → AR → OG → AI → CV → clock → storage。

三组片段**只追加在合成序列末尾**（[合成规则](#合成规则)代码块末三行；M-9）：OG 的 v2 片段**单独导出**，不塞进原工厂的返回值——原工厂的片段在序列中间，往里加一个会让已发布的编号名移位、每个旧库都过不了数据格式核对。

### 同一存储、同一约束域（三件事的第 1 条扩到新表）

资产提供者的确认事务要取 OG 的隶属哨兵、锁 OG 的组织行、在同一事务里读 OG 的行（[asset-governance「跨 owner 的同一提交」](../../packages/assets/asset-governance/design.md#跨-owner-的同一提交组织治理的隶属哨兵组织行与事务内读)，X-1～X-3）。这些锁与读成立的前提全在本节点：**资产提供者、OG、P-1 解析到的是同一个 `provide('storage')`、同一个库**；本节点仍不用 `isolate`、清单里仍只允许一个 `storageSqlPlugin`（`assembly.manifest-shape` 须把两条新 fiber 纳入）。
**自构反证**：把资产提供者装在一个 `isolate` 标签下、给它另一个 `storage`——隶属哨兵与组织行锁落在两个库里、互不相见，解除隶属与团队 → 团队复制的确认交错时复制落在树外（AT S-12 被破）；本节点不用 `isolate` 就是为此。反证不了的交错本身归资产节点的真并发演练（其 verification D-4、D-8、D-9）。**这是 X-1～X-3 唯一的装配前提**，它的结构检查列为实现后第一波必跑项（[verification](verification.md) 本程追加一行，N2 TH-1）。

### 时钟：严格递增是交接事项

资产提供者与 OG v3 都要求同一个时间源上「先后两次串行提交的时刻不相等」（AT S-34、OG v3 S-42 末行）；本节点保证的是**只装一份 `clock`**；严格递增的手段已由 D-060 §八 M58 选定为时钟，登为 [`infra/clock` 的缺口 C-15](../../packages/infra/clock/design.md#实施缺口与消费者影响)（下一程实施；[asset-governance N-1](../../packages/assets/asset-governance/design.md#实施缺口与消费者影响)）。C-15 闭合之前，那两行在本装配上兑现不了（U-7）。

## 状态、并发与失败映射

**本节点无领域状态、无提交点、无锁。**运行时状态只有：一个 Context、八条 fiber 的句柄、`openSignal` 与它的兑现／拒绝两个把手、一个「已进入撤除」的开关。全部提交点在 AI／OG 的 `storage.write` 与入口层启动时那一次读或铸里，全部冲突裁决在存储的行锁、唯一约束与外键上（[core/storage](../../packages/core/storage/design.md#状态并发与失败映射)）。
升级快照的「未确认／已确认」是**存储提供者落在磁盘上的状态**（R-U5），不是本节点的内存状态——进程崩溃之后它照样说得出上一次启动有没有确认。

**启动失败**的精确含义：`boot()` 拒绝，已装的 fiber 已按逆序 `dispose()` 完毕（disposer 异常只记日志，basis [`effect-disposal-concurrent-not-ordered`](../../../basis/cordis/effect-disposal-concurrent-not-ordered.md)），快照未确认时已由存储提供者在撤除路径上恢复（sqlite：本次跑过的迁移随之撤回，库回到升级前；pg 见缺口 U-3），**撤完之后本节点调一次 `guard.pending()`**——撤除路径上的恢复失败内核只记日志、`dispose()` 照常 resolve，只有回头看磁盘才分得清「已恢复」与「恢复失败、快照仍在」（R-U8），后者单列为「升级未确认」阶段；
调用方（进程入口 `main` 的 `serve`：退出码 1；测试里是测试本身）据此退出非零；`boot()` 在拒绝之前已落恰一条结构化记录 `startup-failed`（拒绝值 `HostStartupFailure`，带具名阶段 `stage`、点名的项 `item`、恢复失败时快照的位置 `snapshot`），**告诉运维者差的是哪一样**（[PF-017 §6.6](../../../product/PF-017-governance-center-as-deployable-application/design.md#66-要么整个起来要么不起来)）：
失败的阶段（config 解析／配对自检／被占／遗留快照恢复／只读核对：格式版本或时钟回拨／建快照／迁移／哪条 fiber，入口层等钟超界单列为「钟读不到」／升级确认／确认之后开闸时钟读不到——说明写「钟读不到或回拨：重启前先核钟」（U-4）／升级确认没有删到快照（`snapshotTaken ⇒ snapshotRemoved` 不成立）或守卫没挂上（`UpgradeGuardNotAttached`）／升级未确认：撤完之后 `guard.pending()` 仍见快照）、错误类型与消息（缺了哪个变量、哪个迁移名对不上、哪条 fiber），**不含任何 PEM 文本或 config 值**（[S-29](../../../spec/compositions/governance-center-entry/v1/contract.md#s-29-秘密不进任何输出) 把启动失败说明列在「任何输出」里）。
恢复快照本身失败时，记录里另写快照的位置，快照不删（R-U8）：插件体内的恢复失败由 storage-sql 以具名阶段抛出，撤除路径上的由 `guard.pending()` 回头看见。

**运行期失败**全部归提供者与契约：`storage` 不可用 ⇒ 各操作的「不可用」字面（经 `core/storage` 的 `mapStorageError`）；`StorageDefect` 与其他异常上抛——那是缺陷，本节点不捕获、不重试，让它在日志里可见（[OG](../../packages/tenancy/organization-governance/design.md#状态并发与失败映射)、[storage-sql 错误码映射](../../packages/infra/storage-sql/design.md#错误码映射表)）。**本节点没有 catch-all**。

**并发**：sqlite 一个写句柄 + 进程内写队列、读句柄独立——协议 P-12 的要求由 storage-sql 兑现；`scrypt` 的并发上限本版不限流。**跨进程**：本版一个进程；两个进程指向同一文件时 R-1～R-7 仍由 sqlite 文件锁与约束给，但 `clock` 跨进程不保证先后（投影 [Q-8](../../../product/PF-001-identity-scope-and-agent-constraints/projection/v1/projection.md#7-未决项)），升级快照的建立与恢复要「同一份库同一时刻只有一个属主进程」，由 storage-sql 的属主独占兑现（插件体第一步取、撤除最后一步放、随进程死亡释放；多实例本是 PF-017 非目标）。

**撤除次序**：`dispose()` 按装载的**逆序**逐个 `await fiber.dispose()`：入口层 → 运维面 → AR → OG → AI → credentials → clock → storage。
入口层最先撤，它的停机三步在自己那个 effect 里有序完成（[S-36](../../../spec/compositions/governance-center-entry/v1/contract.md#s-36-装配给的保证-vs-协议须给的保证)「停机时先停收、再等在途、再关闭」行）；运维面在它之后撤，`stopped` 发出时运维面还在听，两张面同起同停。排空超时后仍在跑的领域调用不被取消，跑完、按各自那一次提交收场；`storage` 最后撤，它关准入之后才发起的存储调用得 `StorageUnavailable`，那件事就没有发生——没有半个（[S-34](../../../spec/compositions/governance-center-entry/v1/contract.md#s-34-起来即整体停机时在途请求归谁)）。
不直接 dispose 根 Context——那会让八条 fiber 的 disposer **并发**跑（子 fiber 的 dispose 是父的 effect，各 effect 并发驱动），
`clock` 收回租约的那次写可能撞上已关准入的 `storage` ⇒ 只记日志、租约留着、下次启动最多等一个租约宽度——不破正确性，但可避免。
逆序让每个 disposer 看到它依赖的服务仍活。**顺序只约束发起，不保证异步完成**——storage 的 disposer 自己在一个 effect 内组合了「关准入 → 等在途 → 关句柄」，本节点不替它排。

**崩溃**（`SIGKILL`、断电）：什么都不跑。sqlite 由 WAL 恢复到最后一个完整提交（本中心显式 FULL，底层须兑现同步请求，[storage-sql](../../packages/infra/storage-sql/design.md#实施缺口与消费者影响)）；`clock_lease` 未收回 ⇒ 下次启动最多等一个租约宽度；领域层没有在途状态要恢复（两条动作链各自幂等，[AR](../../packages/tenancy/account-registration/design.md#状态并发与失败映射)）。

## 「归装配」的事项逐条承接

四个基础设施节点与五个 tenancy 节点（加两个 core 纯模块）各自写下的「归装配」，以及六份契约「装配给」表里的每一行（六份都 `accepted`，其中 `composition.governance-center-entry/v1` 的 S-36 由 D-028 接受），逐条在本节点的哪一行**承接**（本节点自己给）或**转交**（本节点装的某个提供者给，本节点只保证装了它、且只装一份）；承接不了的写明是缺口与 owner。

**客户端这条边上哪些由协议重新兑现，以入口契约 [S-36](../../../spec/compositions/governance-center-entry/v1/contract.md#s-36-装配给的保证-vs-协议须给的保证) 为准**：这条边只把调用方搬到进程外，领域没有拆开——靠「同一存储、同一提交、同一时钟」的行仍由本节点的装配给；
和调用方身份有关、和流向调用方的值有关的行由协议给，兑现者是 governance-center-entry。中心自身被拆开之后还要补的，是入口契约 G-8，不在本版。

「状态」列里的「已承接」「已转交」指本节点或被转交的提供者已在源码里按这一行兑现（HUB `c9b5850`）。列里点名的 `assembly.*` 与各节点测试都已写成，运行结果登记在运行 `2026-09-23-tests-tenancy-leg-2`；**逐条覆盖以 [verification.md](verification.md) 为准**，本列写成「证据见 verification」的，是那边回填之前不在这里下结论。

## D-039 的单机持久性装配

buildManifest 在 SQLite storage config 中固定 `synchronous: 'full'`，沿 storage-sql 的新枚举配置传递；没有降档环境变量。按 D-039 选择，不修改 PostgreSQL、迁移顺序、guard 确认或快照协议。WAL FULL 依赖底层兑现同步；旧备份安全开放与整机灾备不由此闭合。

## D-040/D-041 有界账号增量

本期生产装配限定SQLite FULL；buildManifest在打开提供者前拒绝PG，新组合锁序精化仍延期。迁移保留原九条全局前缀，新账号有界片段为第十条，不能跟随owner数组位置插入旧前缀。已有九条序列的真实SQLite中心文件升级/再次启动及中心ID保留已回归；完整业务Promise排空（包含事务外凭据准备）仍未实现，运输drain不能背书新版整装。上文PG只接线的旧映射被本增量限定，不作为当前支持声明。

新增维护提供者精化（candidate，未实施）：[maintenance-binding](maintenance-binding.md)。
