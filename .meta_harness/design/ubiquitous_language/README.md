# 统一语言

**这个系统里，同一个概念只有一个说法；那个说法在这里定义。**

## 这里拥有什么，不拥有什么

**分工只有一句话：**

> **这里拥有「这个词精确指什么」，topic 正文拥有「为什么是这个形状、有什么后果」。**

| | 归这里 | 归 topic 正文 |
|---|---|---|
| **一个词指什么** | ✅ 中英文名 + 中英文无歧义定义 | —— |
| **它最容易和谁混** | ✅ | —— |
| **哪些说法不要再用** | ✅ | —— |
| **为什么设计成这样** | —— | ✅ |
| **它有哪些产品规则** | —— | ✅ |
| **边界、取舍、验收** | —— | ✅ |

**所以这里不是第二份权威，它是另一层。**词条**必须标明出处**——
定义的**依据**永远在别处（**某个 topic**，或**产品负责人对跨全链概念的直接裁决**），
这里只负责把它写成一条**能被一致引用的话**。

> **判断一句话该写在哪：它回答的是「这是什么」还是「为什么」？**
> 「为什么」一律不写在这里，**哪怕它很精彩**。

## 怎么用

| 你在做什么 | 怎么办 |
|---|---|
| **写产品设计，要提到一个概念** | 先查这里有没有。**有，就用这里的说法**；措辞可以变，**词不能变** |
| **要引入一个新概念** | **先来这里加条目**，定义清楚无歧义**之后**再在正文里用。[流程见 conventions](conventions.md#加一个新词条) |
| **发现两处说法对不上** | **不要静默统一掉**。记进 [conflicts.md](conflicts.md)，那是发现，不是麻烦 |
| **要翻译成英文** | 用词条里的英文名，**不要自己另译** |
| **改了某个 topic 里概念的含义** | 回来改词条，并在词条里更新出处的 rev |

## 词条在哪

**先查[全部词条索引](index.md)**——加任何新词之前都从那里搜一遍。

词条按**「这个概念在回答什么问题」**分卷。

> **分卷维度不是 PF 编号，也不是「被描述的对象」。**
> 按 PF 分，同一个概念会有好几个家（「租户」PF-001/003/005 都在用）；
> 按对象分，对象一被重新分解，整卷就得搬家。
> **「它回答什么问题」不会因为这两件事而改变**——
> 判据与反例见 [conventions](conventions.md#分卷按它回答什么问题)。

| 卷 | 回答什么问题 | 典型词条 |
|---|---|---|
| [架构内核与扩展](terms/architecture-core-and-extension.md) | 这个系统**哪一部分立规矩**，其余部分怎么建在它之上 | 架构内核 |
| [主体与归属](terms/subjects-and-ownership.md) | **谁**在用这个系统，东西**归谁** | 账号 · 组织 · 租户 · 租户角色 |
| [作用域与求值](terms/scope-and-resolution.md) | 一个值**怎么被算出来** | 作用域层 · 能力标识 · 覆盖与收窄 |
| [能力与构成](terms/capabilities-and-composition.md) | agent **由什么构成**，因此**能做什么** | 资产八类 · agent 构成 · 动作空间 |
| [流转与授权](terms/circulation-and-entitlement.md) | 东西**怎么在主体之间流动**，谁**凭什么**用它 | 所有权 · 使用权 · 转移 · 分享 |
| [Agent 运行时闭环](terms/agent-runtime-loop.md) | 一段协作**怎么从触发走到收束，又怎么回到会话** | 会话 · 运行 · 触发 · 装配 · 装配清单 · agent runtime · 优雅取消 |
| [取用与可用性](terms/reach-and-availability.md) | 一样能力此刻**够不够得着、做不做得了** | 常驻 · 当下可用性 · 替换件 · 依赖声明 |
| [执行与收场](terms/execution-and-outcome.md) | 一件事**怎么跑、跑偏了谁接手、怎么了结** | 工具执行 · 等待态 · 发帧 · 卸载 · 六种收场 · 主路径 · 非常态 · 上交 |
| [落地与隔离](terms/grounding-and-isolation.md) | 动作**实际落到哪里** | 执行环境 · 沙箱 · 宿主机 · 设施 |
| [交互与派发](terms/interaction-and-dispatch.md) | agent 跟人、跟别的 agent**怎么来往** | 派发三模式 · 通信两规则 · 问询与请示 · 决策卡片 |
| [记录与上下文](terms/record-and-context.md) | **留下了什么**，怎么**组装**给读的人或模型 | 发生的事 · 记录条目 · 条目效力 · 会话日志 · 消息七种 · 块标注 |

**一个词条只属于一卷。**跨卷使用是常态，跨卷**定义**不是——
**放不进任何一卷，多半说明它还不是一个清楚的概念**，那时该回去把概念想清楚，
而不是新开一卷。

## 规矩

| 文件 | 拥有什么 |
|---|---|
| [index.md](index.md) | **全部词条一览**，查重从这里开始。**它不是定义** |
| [conventions.md](conventions.md) | **词条长什么样、名字怎么取、怎么分卷、怎么加** |
| [decisions.md](decisions.md) | **不归任何 topic 的那些概念**，产品负责人对它们的直接裁决 |
| [conflicts.md](conflicts.md) | **提取时发现的对不上的地方**，如实记录，不静默改掉 |

> **有些概念不归任何一个 topic**——[会话与运行](terms/agent-runtime-loop.md)、
> [架构内核](terms/architecture-core-and-extension.md)都是。
> 它们是**跨全链的治理概念**，被很多 topic 引用却没有哪一个拥有，
> **依据在 [decisions.md](decisions.md)**。**这是出处的第二种合法形式，没有第三种。**

需要新增或修改概念时，加载
`ubiquitous-language` skill。

## 它怎么生长

**词表跟着设计长，不是一次修完的工程。**

| 什么时候动它 | 动什么 |
|---|---|
| **设计里出现一个新概念** | **先加词条**，定义清楚无歧义之后才在正文里用 |
| **某个 topic 改了一个概念的含义** | 回来改词条，**并更新出处的 rev** |
| **一个 topic 升了 rev** | 照词条里标的 rev，**复核受它影响的那些** |
| **发现两处说法对不上** | 记进 [conflicts.md](conflicts.md)，**不静默统一掉** |

**词条里的出处与 rev 就是它跟设计对齐的凭据**——那一处改了，照着 rev 就找得到该复核什么。

> **还没进词表的概念不等于不存在。**这里收的是**已经稳定到值得固定说法**的那些；
> 一个还在 draft 里摇摆的概念，**现在收它等于把草稿定成语言**。

## 失效事件

**某个概念的含义变了。**

这与 product 的失效事件（产品方向改变）**不是一回事**：一个词的所指可以在
产品方向没变的情况下被澄清，产品方向变了也未必动到词义。所以它自己一个家。

## 这里不做的

| 不做 | 为什么 |
|---|---|
| **机器可读的词表** | 手写的家只有这一份。将来要给工具吃，由生成器产出到 [views/](../views/README.md)，**不在这里维护第二份** |
| **给每个实例建词条** | `Tools()` `Shell()` 是 **meta tool 的实例**，不是概念。定义「meta tool」，不定义十三个名字 |
| **收录只在一处出现的修辞** | 那是文风，不是术语。[准入判据见 conventions](conventions.md#什么配有词条) |
| **改 topic 正文的措辞** | 这里立规矩，**回改是另一件事**，要各 topic 的 owner 自己做并记 changelog |
