# 设计知识的准入与归属

本文件帮助 agent 判断一份材料是否值得进入设计链，以及应由哪个目录持续维护；
产品心智与通用权威边界沿用父级约定。

## 先判断失效事件，再选目录

这里保存后续需求分析、设计和维护要继续消费的知识。准入依据是持续的消费对象，
不是任务名称、文件格式或评审状态。选目录只问一个问题：**什么事件会让这条事实失效**——
产品方向改变归 product，对象被重新认定或分解归 domain_objects，系统目标改变归 foundation，上游换版本归 basis。形成过程与某次运行结果归本工作树 tmp，不进入永久设计链。
系统级预期归 [architecture](architecture/README.md)；新或已迁模块的公开形状、行为承诺和必要实现理由随接口拥有者维护。
模块形状、行为及实现理由归实际接口/提供者拥有者。先读[准入与停止条件](README.md#准入与停止条件)，再进入实际拥有者。

一次交付的计划、派发、文件盘点与进度放本次明确工作区的 `tmp/`，不作为 design topic。
不要因任务名称里出现「迁移」「重构」就另建目录；迁移对照与施工过程留任务tmp，当前采用范围和验证义务归实际拥有者；接受过程与原始证据留任务区，不要求形成史永久可追溯。

创建或迁入材料前执行四步：指出任务结束后的持续消费者；判断它何时失效从而定位唯一拥有者；
核对该目录 README 的最低信息与停止条件；再从本地 `.templates/` 建包并裁剪。
任一步无法回答就停止建包，把待核对输入留在任务区；不要先创建空 topic、`plan.md`
或第二份权威等待以后补齐。

尚未形成正式结论的产品交流放本工作树 `tmp/<task>/`；已确认规则、范围和必要理由
由 topic owner 写入现行正文。触发与记录边界见 `harness-design-handbook` skill 的「需求归位」→「何时自主启记访谈」。

## 全局只有一套说法

**同一个概念，在整个设计链里只有一个词；那个词定在
[ubiquitous_language/](ubiquitous_language/README.md)。**

这条**对所有目录成立**——产品条款、系统约束、上游读数、精确规格、提供者设计、
当前采用理由，用的都是同一套词。**统一语言的失效事件是「某个概念的含义变了」**，
与product的产品方向和模块的行为承诺都不同，所以它自己一个家。

| 情况 | 怎么办 |
|---|---|
| 要提到一个概念 | **先查[词条索引](ubiquitous_language/index.md)**；有就用那里的词 |
| **要引入一个新概念** | **先加词条**，定义清楚无歧义**之后**才能在正文里用 |
| 发现两处说法对不上 | 记进 [conflicts.md](ubiquitous_language/conflicts.md)，**不静默统一掉** |
| 要确定某个词的正式英文名 | 从词条取，**不自己另译**——译法分叉会使公开接口和承诺产生歧义 |

**词表拥有「这个词精确指什么」，各 topic 正文拥有「为什么是这个形状、有什么后果」。**
两者不是同义复制：**「为什么」一律不写进词表**，写进去就是第二份权威。

进 `ubiquitous_language/` 先读它自己的 [AGENTS.md](ubiquitous_language/AGENTS.md)——查一个词、在正文里用一个已有的词，
到那里就够了。**真要新增或修改词条**（取名、选卷、写定义、判形态、复核出处），再按它的指引加载 `ubiquitous-language` skill。

## 有哪些对象，也只有一份

**产品设计与架构、规格之间隔着一站：[domain_objects/](domain_objects/README.md)。**
产品正文按问题分 topic，一个对象的事实散在很多 topic 里；那里把它们**跨 topic 收成一份**——
每个有身份的对象一条：宿主、身份依据、生灭、依据出处（带 rev）。它的失效事件是「一个对象被重新认定或重新分解」。

| 情况 | 怎么办 |
|---|---|
| 给一个词条写「形态」，写的是「对象」 | **同时**在 [objects.md](domain_objects/objects.md) 立一条；检查器会因为缺它而失败 |
| 改了某个产品 topic 并升了 rev | 检查器点名的词条出处与对象依据**逐条复核**，成立再把 rev 改到当前值；**不复核就改 rev 等于把检查关掉** |
| 碰到一个像对象、却哪儿都没定义的东西 | 进 [pending.md](domain_objects/pending.md) 并写清谁来裁，同时将持续未决写进所属 topic 的当前正文 |
| 架构或规格设计要「相关领域对象」 | 从[领域对象地图](views/domain-object-map.md)找入口，读 objects.md 的条目，**依据仍以它指向的产品正文为准** |

**条目不自带任何划分。**能力边界、限界上下文、聚合与存储切分是系统架构设计的结论，不写进对象条目。

进 `domain_objects/` 先读它自己的 [AGENTS.md](domain_objects/AGENTS.md)。**来取输入的人读到那里为止**；
真要立条目、登记待裁或处置对账器的点名，再按它的指引加载 `domain-objects` skill。

## 承诺与过程的归属

模块公开类型与行为承诺随实际拥有者维护，必要形式资源与验证方法同归成员。系统预期归architecture，产品规则归product，不在两处复制同一承诺。

本次迁移对照、覆盖核对、提案、评审和单次运行输出留任务tmp，不要求永久形成史。持续维护的验证义务归拥有者的verification；不能把执行日志改成ADR或设计正文。

当前结构由实际源码及明确系统预期派生。views只导航剩余设计源，不证明实施、接受或验证状态；缺事实回真正拥有者补，不手写另一份汇总权威。

## 状态和交接红线

- 观察、推断、候选、评审、接受、发布、实现与验证分别记录；文件存在或 reviewer 无意见不能提升状态。
- 按[架构维护规则](architecture/README.md)确定唯一接口与行为拥有者，使用执行仓库包模板；必要验证义务不因物理移动消失。
- 产品条款先投影到现有能力及组合；只有合理组合或扩展仍不能拥有剩余独立责任时才提出新能力维度及它独立的契约边界（装配时由独立插件承载）。
- 有持续消费者的当前设计候选由实际设计专题维护唯一正文，明确候选状态；采用后才迁到真实成员。探索稿、被替代候选和形成过程留 tmp，不为保留它们创建空包。
- 必要的候选比较留本工作树 tmp；不为落盘强凑候选。获准采用的终态和必要理由回到实际拥有者，不持久化提案/决策形成史。
- 所属成员的形式工件按性质需要选用；optional 表示不是每个 topic 都预建，已经触发的证明义务必须闭合或明确阻断。
- basis 条目必须给出 symbols 与一个在该语义消失时会失败的 probe；给不出就记为待核对主张，不作为设计依据。
- 绑定的证据可以是测试或形式任务，但**必须写明成立前提**；两种形式都拿不出时，问题在性质表述本身，
  退回把性质改写成有界形式，不新设一个「无法验证」的状态把缺证据登记成已处理。

## 按当前缺口展开

- 新建或吸纳主题：读所属目录的 README 与本地 `.templates/`；按[信息包规则](README.md#主题是信息包)裁剪，模板本身不代表知识已准入。
- 比较方案和接受过程写本工作树 tmp；终态按架构维护规则定位实际拥有者。不能通过换目录提升状态，不要求永久历史追溯。
- 现有条款与实现或证据冲突：加载 `harness-design-handbook` skill，读其「规格演进」，定位拥有者和消费者，不能在施工计划里重写契约。
- 需要知道某个上游机制到底保证什么：读 [basis/](basis/README.md) 的条目，不在本次分析里重新推导一遍。

普通局部修订直接接续已有主题；当前准入、拥有者与缺口清楚后停止扩展阅读，不为一次任务补齐所有目录。
进入 `product/` 工作时先读它自己的 [AGENTS.md](product/AGENTS.md)——那里有该区的维护规矩与阅读地图；
真要在那里落字，再按它的指引加载 `product-design` skill，
那份会把视角切成 product manager，**只读产品正文取输入的人不加载**。
`record/` 已退出 Git；不在这里写提案、决策形成史、评审或运行日志。
