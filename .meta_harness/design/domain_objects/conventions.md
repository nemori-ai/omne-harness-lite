# 对象条目的格式契约

**一条对象条目、一项待裁长什么样，每个字段是什么意思，对账器守哪几条。**
读条目的人靠它读懂，写条目的人靠它写对，对账器靠它解析——三方共用这一份。

**宿主怎么判、几个叫法算不算同一个、待裁的「谁来裁」该指到谁、升了 rev 怎么逐条复核、全量重提怎么做**不在这里：
那是落字的人才需要的判断与流程，归 `domain-objects` skill，只此一份。谁该加载它、谁不必，见本区 [AGENTS.md](AGENTS.md)。

## 一条对象条目长什么样

````markdown
### UL-tool-execution · 工具执行

- **宿主**：[会话](objects.md#ul-session--会话)；前台后台不改变生命周期归属，agent runtime 只持有执行句柄
- **身份**：正文未给标识；只要求记得下「哪一次运行、哪个 agent runtime 发起、属于哪个会话」
- **生灭**：发起 → 前台/后台 × 执行中/等待 → 完成 · 失败 · 被中断 · 等不到；停机后不重来，算失败；会话被归档时随之收场
- **依据**：[PF-006 §6.5](../product/PF-006-tools-and-skills/design.md#65-工具执行有自己的运行时绑定在-session-上)（rev 21）；[PF-012 §6.13](../product/PF-012-agent-loop-and-run/design.md#613-取消跟着宿主走)（rev 17）
- **并入**：「工具执行运行时」「一次工具调用」——正文当同一物用
- **未裁**：具体执行标识格式正文未述；PF-011 的归因树与生命周期归属是不同关系，不据此改宿主
````

**标题**：词条 ID · 中文名，**与[统一语言](../ubiquitous_language/index.md)里那一条逐字一致**。英文名不重复写，从词条取。
条目之间互相指，在 `objects.md` 里写站内锚点 `#ul-session--会话` 就行（上面示例写全了文件名，只因为这一页不是 `objects.md`）；
总表靠「宿主」里的这些链接倒排出「谁寄宿在谁身上」。

| 字段 | 必填 | 它是什么 | 它不是什么 |
|---|---|---|---|
| **宿主** | ✅ | 它的**寿命**跟着谁——谁没了它就没了。没有就是 `—`。会换宿主的，每种情形都列着 | 「归属于哪个租户」不是宿主，那是归属 |
| **身份** | ✅ | 靠什么分得出这一个与那一个、在什么范围内唯一。**「正文未述」是一个合法且常见的值**：它说的是产品正文还没定，不是这里漏写 | 字段名、ID 格式 |
| **生灭** | ✅ | 一行：怎么来、经过哪些状态、怎么没。没有终结的照实写「无删除」 | 转移条件与理由——那在该 topic 的 `flows.md` |
| **依据** | ✅ | 至少一条指向 `product/` 某个 topic 的 `design.md` 或 `flows.md` 的链接，带 rev；定义处是第一条。**这一条里别的字段，每个字都应当指得回这里** | changelog、decisions、interviews——那是历史与推导 |
| **并入** | 按需 | 这条对象吸收了哪些别的叫法，**以及凭什么说是同一个** | 该弃用哪个词——那归词条的「弃用」 |
| **未裁** | 按需 | 这条对象身上还悬着的建模问题，写着去哪裁。**下游用到它之前要先闭合** | 已经裁过的——裁完就删，结论落进上面几栏 |

**「身份」「生灭」各只有一行，是有意的。**这里不是产品正文的摘要；
**条目与依据不一致时，永远以依据为准。**

「依据」里 rev 的写法与词条「出处」是[同一条规矩](../ubiquitous_language/conventions.md#rev-怎么写怎么读)：
指向产品正文的链接后面跟着它那个 topic 的 `（rev N）`，同一个 topic 连着的几条可以共用后面那一个。

### 变体不立条目

形态为「变体」的词条（个人组织、子会话、各类消息）**不在这里立条目**——它没有独立于父类的身份机制，
骨架与父对象相同。总表会从词条的「父」自动把它挂到父对象下面。
**一个变体有了自己特有的身份规则或生灭规则，那它就不再是变体**：词条的形态先变，这里才有它的条目。

## 什么进 objects.md，什么进 pending.md

**判据只有一处**：统一语言词条的[形态](../ubiquitous_language/conventions.md#形态这个词指的是哪一类东西)。

| 情形 | 去哪 |
|---|---|
| 有词条，形态为「对象」 | **objects.md 必有一条** |
| 有词条，形态为「未定」 | **pending.md 必有一项**；统一语言的 conflicts.md 同时有一条 |
| 没有词条，但正文把它当对象用（能被指名、能被配置、有状态） | 能立词条就先立词条；**立不了的进 pending.md** |
| 有词条，形态为变体 / 属性 / 规则 / 过程 / 视图 / 状态 / 位置 / 总称 | 都不进 |

### 一项待裁长什么样

````markdown
### 存储

- **现象**：工具定义可以指名声明「把附件放进哪个存储」，存储没配好则该工具整个不可用；但全系统没有任何一处定义它
- **牵涉**：[PF-006 §4 工具的产出](../product/PF-006-tools-and-skills/design.md#工具的产出)（rev 12）
- **挂着谁**：[附件](objects.md#ul-attachment--附件)存在它里面，附件的宿主与留存因此都定不下来
- **谁来裁**：PF-006 的 owner；已记入该 topic 的 decisions「已知的来源问题」
- **闭合条件**：有一个 topic 定义了它，并立了词条，或明确说它不是一个产品概念
````

| 字段 | 必填 | 它是什么 |
|---|---|---|
| **现象** | ✅ | 正文怎么在用它、缺的是什么。有词条的，点出词条 ID |
| **牵涉** | ✅ | 在哪几节露的面，带 rev |
| **挂着谁** | 按需 | 哪些对象条目因为它而定不下来 |
| **谁来裁** | ✅ | 真能裁这件事的人或环节 |
| **闭合条件** | ✅ | 一个看得见的事件；它发生了，这一项就从这里删掉 |

标题用它在正文里的叫法，不编号。

## 对账

对账器替这一区、也替统一语言守着下面这些，**不过就失败**。命令与参数在工作区的 `tooling/README.md`「领域对象对账」；
执行仓库的 `make design-check` 把它与链接检查一起跑。

| 查什么 | 为什么 |
|---|---|
| 每个词条都有合法的「形态」；变体顺着「父」往上走得到一个形态为「对象」的词条 | 形态是这里的准入判据，缺了就没法对账 |
| 词条索引 `index.md` 的每一行，与分卷里的标题在 ID、中文名、英文名、锚点上一致 | 索引是手写的，会漂 |
| 形态为「对象」的词条 ⇔ objects.md 有同名条目；形态为「未定」的词条 ⇒ pending.md 与 conflicts.md 都提到它 | 两边不各说各话 |
| 条目四个必填字段齐全；「依据」的每条链接都指向某个 topic 的 `design.md` 或 `flows.md`，且带着 rev；待裁四个必填字段齐全 | 依据指到历史与推导上，等于没有依据 |
| 链接与锚点都还在——这一项由 `check_design.py` 对设计根下全部 Markdown 统一查 | 标题一改，锚点就断 |
| **每条「依据」、每条词条「出处」、每项待裁「牵涉」标的 rev，等于该 topic 当前的 rev** | **这是全部对账里最要紧的一道**：rev 是词表、对象条目与产品正文对齐的唯一凭据，凭据自己不被检查，整套对账就是自证 |
| 每个 topic 的 rev 只有一个说法：`README.md` front-matter 的 `revision` 为准，`design.md` 抬头、`changelog.md` 最新一节与产品区两张手写 rev 表若写了 rev，必须与它相等 | rev 自己有两个说法的话，上一道检查无从比对 |
| `views/domain-object-map.md` 与现在算出来的一致 | 派生物入库，靠这个守住不漂 |

**rev 对不上不代表内容错了**，它只代表「那边改过，这条还没人回头看」。处置只有一条路：**回头看过，再改 rev。**
不复核就改 rev，等于把这道检查关掉——对账器证明得了「rev 写的是当前值」，证明不了「有人回头看过」。

**对账器查不了的**是「产品正文里冒出一个新对象，却没人给它立词条」：上游是散文。
那个方向靠[新概念先进词表、再进正文](../product/AGENTS.md#红线)这条落字时的规矩，以及定期的全量重提兜底；
两样的做法都在 `domain-objects` skill。
