# 待裁

**像对象、但对象性还没有人裁过的东西。**缺定义的、两处正文说法相左的、悬空引用的。
每项都写清**谁来裁**与**闭合条件**——一项没有 owner 的待裁，六个月后就是一个没人记得问过的问题。

> **这里不裁决。**裁决权在各 topic 的 owner 与产品负责人手上；这里只保证这些问题不从视野里消失。
> 架构或规格设计要用到其中某一项之前，**先让它闭合，不要就地猜一个**。

格式见 [conventions](conventions.md#一项待裁长什么样)。第一节的各项在统一语言里有词条、形态标为「未定」，
同时登记在 [conflicts.md](../ubiquitous_language/conflicts.md#现有冲突)（两种读法的原文与出处在那里）；其余没有词条。

## 有词条，形态未定

当前没有形态为「未定」的词条。出现时在这里立项，并同时登记在 conflicts.md。

## 没有词条

### 存储

- **现象**：工具定义可以指名声明「把附件放进哪个存储」，存储没配好则该工具整个不可用；被卸载的工具结果也「存着，没丢」。但全系统没有任何一处定义它——是对象、是一项设置、还是执行环境的一种设施，没人说过
- **牵涉**：[PF-006 §4 工具的产出](../product.0.0.1.legacy/PF-006-tools-and-skills/design.md#工具的产出)（rev 24）；[PF-006 §6.4](../product.0.0.1.legacy/PF-006-tools-and-skills/design.md#64-依赖声明与解析)（rev 24）；[PF-012 §5.10](../product.0.0.1.legacy/PF-012-agent-loop-and-run/design.md#510-卸载结果落成消息之前的那一关)（rev 25）
- **挂着谁**：[附件](objects.md#ul-attachment--附件)存在它里面，附件的宿主与留存因此都定不下来；被卸载的工具结果须保持可回取全文（PF-006 §6.10），物理存储归属与机制仍待技术设计
- **谁来裁**：PF-006 的 owner
- **闭合条件**：有一个 topic 定义了它，并立了词条，或明确说它不是一个产品概念

### 跨会话的那个对象

- **现象**：元能力产品说待办「活在一次会话里，不跨会话继承。跨会话的东西不装在这扇门后面」，并在边界一节登记为「尚无归属」。它曾被叫作「目标」，但设计链里没有它的定义
- **牵涉**：[元能力：产品规则](../product/meta-capabilities/design.md#meta-todo)（rev 3）；[元能力：产品规则](../product/meta-capabilities/design.md#协作拥有者与非目标)（rev 3）
- **谁来裁**：产品负责人——它要不要做、归哪个 topic，都还没有人说过；由元能力产品保留跨会话对象缺项
- **闭合条件**：有 topic 认领它，或明确本版不做

### 一次派发

- **现象**：`spawn` / `delegate` 的一次派发有状态（在跑 → 完成 · 失败 · 被中断）、可被查询与撤回、至多带一份报告；它由一次工具执行承载，产生一个子会话，**`spawn` 那种还要在子会话日志里落下一条起始输入记录**。元能力产品已明确后续普通消息沿输入规则，不把派发等同 Run；派发本身与承载工具执行如何建模仍需明确。词条 UL-agent-dispatch 讲的是派发这个过程
- **牵涉**：[元能力：产品规则](../product/meta-capabilities/design.md#meta-agents)（rev 3）；[元能力：产品规则](../product/meta-capabilities/design.md#一次报告与后续消息)（rev 3）
- **挂着谁**：[派发报告](objects.md#ul-dispatch-report--派发报告)的宿主
- **谁来裁**：系统架构设计；元能力产品提供派发工作、一次报告和显式撤回的产品语义
- **闭合条件**：明确一次派发与承载工具执行的身份关系，不把它等同子会话或某一个 Run

### agent 之间的消息

- **现象**：元能力产品定义了「谁能给谁发」的两条规则；普通消息已沿接收会话的输入与 Run 规则处理，但无派发关系主会话通信的精确身份、重试、不存在目标以及持久交接协议仍未闭合，不由入口命令名补造
- **牵涉**：[元能力：先说谁能给谁发消息](../product/meta-capabilities/design.md#双向通信与消息失败)（rev 3）；[PF-014 §4 入站到达](../product.0.0.1.legacy/PF-014-inbound-intake-and-queueing/design.md#入站到达)（rev 14）
- **谁来裁**：元能力、Session 与入站拥有者
- **闭合条件**：实际入站与消息拥有者明确普通通信的身份、持久交接、重试和目标不存在协议，并对应到消息类别

### 外部 harness 的 agent

- **现象**：能被派发指向、「能不能派给它」本身是一项要被授予的权限；但它在本系统里有没有一条登记记录，完全未述
- **牵涉**：[元能力：派给外部 harness 的 agent](../product/meta-capabilities/design.md#外部-harness-派发)（rev 3）
- **谁来裁**：元能力产品拥有者
- **闭合条件**：正文写明它靠什么被指到、由谁登记与撤销

### 使用成本明细

- **现象**：PF-001 要求「一次调用花掉的成本必须能算到发起它的那个租户头上，并能逐条列出来」，同时明说成本怎么算、明细怎么归集与呈现「目前没有对应的产品设计」
- **牵涉**：[PF-001 §6.4](../product.0.0.1.legacy/PF-001-identity-scope-and-agent-constraints/design.md#64-隔离)（rev 26）
- **谁来裁**：产品负责人——「观测与计量」这一块还没有 topic
- **闭合条件**：有 topic 认领计量，并说明一条明细是什么

### 通知发送与投递结果

- **现象**：PF-021 已确定一次发送请求及其结果是用户可查询的单位，技术重试不成为多份独立用户通知，业务历史保留；通知、发送尝试与投递子记录如何分解及标识尚未定义
- **牵涉**：[PF-021 §6.5 通知发送与租户送达](../product.0.0.1.legacy/PF-021-schedule-and-calendar/design.md#65-通知发送与租户送达)（rev 8）；[技术设计交接](../product.0.0.1.legacy/PF-021-schedule-and-calendar/design.md#十技术设计交接事项)（rev 8）
- **谁来裁**：系统架构与规格，按 PF-021 已定查询单位、租户边界和送达判据决定记录分解及身份；不得以技术重试改变通知条数或业务历史范围
- **闭合条件**：明确记录关系、身份和生命周期，按所判形态补统一语言与对象条目，或说明投影到哪个既有对象；技术问题不再等待一项产品记录建模政策
