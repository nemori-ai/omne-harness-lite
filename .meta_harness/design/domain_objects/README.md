# 领域对象

**系统里有哪些东西是「有身份的」——分得出这一个与那一个，并且有自己的生命周期、运行时实例或耐久记录。**
**它们各自的身份靠什么、寄宿在谁身上、怎么生怎么灭、依据在哪。**

这是**产品设计与系统架构、规格设计之间的那一站**。

```text
product/ （每个 topic 讲一个问题）  ┐
                                     ├─→ domain_objects/ ─→ 系统架构 · 规格
ubiquitous_language/（每个词指什么）┘    （跨 topic 收成一份：有哪些对象）
```

产品正文按**问题**分 topic，一个对象的事实散在很多 topic 里——
[会话](objects.md#ul-session--会话)被十四个 topic 讲到，没有哪一个 topic 拥有「会话到底是个什么样的对象」这句话的全貌。
统一语言按**词**收，回答「这个词指什么」，不回答「它寄宿在谁身上、和谁其实是同一个东西」。
**架构与规格开工时要的恰恰是后者**：一份跨 topic 收齐的对象清单，每条都指得回依据。

## 这里拥有什么

| 文件 | 拥有什么 |
|---|---|
| [objects.md](objects.md) | **对象条目**：每个对象的宿主、身份依据、生灭、依据出处（带 rev）、并入了哪些异名、还悬着什么 |
| [pending.md](pending.md) | **待裁**：像对象、但对象性还没人裁过的东西——缺定义的、两处正文说法相左的、悬空引用的。**每项带「谁来裁」与闭合条件** |
| [conventions.md](conventions.md) | **格式契约**：条目与待裁项长什么样、每个字段什么意思、什么进哪个文件、对账器守哪几条。读的人、写的人与对账器共用 |
| [AGENTS.md](AGENTS.md) | 进到这一区的人各走哪条路：谁只读、谁要加载 skill，以及落字的红线 |

**宿主怎么判、几个叫法算不算同一个、待裁怎么写、升了 rev 怎么逐条复核、全量重提怎么做**——这些是落字的人才需要的判断与流程，
归 `domain-objects` skill，**只此一份，这一区不另存**。

**总表不在这里。**它由生成器产出到 [views/domain-object-map.md](../views/domain-object-map.md)——
谁还在讲这个对象、哪些依据的 rev 落后了、宿主树长什么样，都是算出来的，不手写。

## 这里不拥有什么

> **这里拥有「跨 topic 收齐之后，这个对象的骨架是什么」；**
> **「这个词指什么」归[统一语言](../ubiquitous_language/README.md)，「为什么是这个形状、有什么后果」归各 [product](../product/README.md) topic。**

| 不拥有 | 归谁 | 所以这里怎么写 |
|---|---|---|
| 一个东西**是不是对象** | 统一语言词条的[「形态」字段](../ubiquitous_language/conventions.md#形态这个词指的是哪一类东西) | **形态为「对象」的词条，这里必有一条；这里有一条的，词条形态必为「对象」。**两边由检查器对账，不各说各话 |
| 产品规则、取舍、理由 | 各 topic 的 `design.md` | 条目**只写骨架**，每句话都指得回「依据」；**与依据不一致时以依据为准，改这里** |
| 状态机的完整转移 | 各 topic 的 `flows.md` | 「生灭」只写一行，链到那张状态图 |
| 同物异名里该弃用哪个说法 | 统一语言词条的「弃用」 | 这里的「并入」只记**这条对象吸收了哪些叫法、为什么算同一个** |
| 能力边界、限界上下文、聚合划分、存储切分 | **系统架构设计**（尚未开始） | **条目不自带任何划分**，只记可被核对的属性。任何划分都是这些属性上的一次透视，不是这里的骨架 |
| 属性、字段、取值域 | 规格（JSON Schema） | 不收。这里到「有这么一个对象」为止 |

## 键是统一语言的词条 ID

**每条对象条目的标题就是它的词条 ID。**没有词条的东西，**不许在 objects.md 立条目**——
先按统一语言的规矩（`ubiquitous-language` skill）立词条；立不了（写不出无歧义定义、还没人拍板）的，进 [pending.md](pending.md)。

为什么不自己发号：[`design/README.md`](../README.md#组织原则) 写明对象「会被重新分解，不适合当永久地址」。
词条 ID 是全链最稳的键（「改 ID 等于换概念」），对象被拆、被并的时候，先动的是词条，这里跟着动。

## 它怎么生长

| 什么时候动它 | 动什么 |
|---|---|
| **统一语言新增了一个形态为「对象」的词条** | 在 objects.md 加一条。检查器会因为缺这一条而失败 |
| **某个 topic 升了 rev** | 检查器列出「依据」指向该 topic 的条目——**逐条复核**，成立就把 rev 改到当前值，不成立就改条目 |
| **一个词条的形态变了**（对象 ⇄ 视图 / 属性 / 未定） | 条目跟着增删；降为「未定」的移进 pending.md |
| **发现一个像对象、却哪儿都没定义的东西** | 进 pending.md，写清谁来裁；**同时**按[产品区的规矩](../product.0.0.1.legacy/AGENTS.md#红线)记进所属 topic 的 现行正文的未决项 |
| **pending 里的一项被裁了** | 成了对象 → 立词条、立条目，从 pending 删掉；不是对象 → 从 pending 删掉，仍有效的含义归所属 topic 现行正文 |
| **怀疑整体漂了**（大改版之后、架构开工之前） | 做一次全量重提，与现有条目逐条对账；流程在 `domain-objects` skill 的 `references/full-reextraction.md` |

**对账分两层。**能机械查的——条目与词条形态一一对应、依据的链接与锚点还在、依据的 rev 是不是当前值、
总表是不是最新——由 `tooling/` 的检查器查，**不过就失败**。
检查器**查不了**的是「PF 正文里冒出一个新对象，却没人给它立词条」：上游是散文，这个方向只能靠
「[新概念先进词表，再进正文](../product.0.0.1.legacy/AGENTS.md#红线)」这条落字时的规矩，以及定期的全量重提兜底。

## 失效事件

**一个对象被重新认定或重新分解**——拆成两个、两个并成一个、从对象降成属性或视图、换了宿主。

它与相邻几家的失效事件都不同：词义没变（统一语言不动）、产品方向没变（product 不动），
对象的骨架照样可能因为**跨 topic 收齐时的判断**变了而变——
一条[消息](objects.md#ul-message--消息)与它装着的那些[内容块](objects.md#ul-content-block--内容块)
算一个对象还是两个，就是这种判断。
反过来，上游一改，这里**不自动失效**，而是进入待复核：rev 对不上的条目由检查器点名。
