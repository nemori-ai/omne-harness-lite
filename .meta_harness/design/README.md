# 系统设计链

这里维护待设计系统从需求到实现映射的完整设计链；目前有目录入口和 topic 模板包，尚未导入具体产品正文。

| 目录 | 归属 |
|---|---|
| [requirements/](requirements/README.md) | 产品需求、系统目标与全局约束 |
| [research/](research/README.md) | 可核对的观察、来源与局限 |
| [proposals/](proposals/README.md) | 能力覆盖、剩余责任与候选设计取舍 |
| [decisions/](decisions/README.md) | 已接受选择、理由、范围与取代关系 |
| [architecture/](architecture/README.md) | 当前系统视图、能力基与组合关系 |
| [spec/](spec/README.md) | 精确规格及唯一 catalog、冻结与形式任务记录 |
| [providers/](providers/README.md) | 按实际产品包组织的插件提供者设计与符合性证据 |
| [assemblies/](assemblies/README.md) | 按实际应用组织的组合、配置与真实集成证据 |
| [migrations/](migrations/README.md) | 长期迁移约束、来源与实际执行记录 |

## 家族准入

材料进入本目录，是因为后续设计或维护会持续消费其中的知识。先判断知识的拥有者，
再选择 family 和模板；完成一次任务、写成 Markdown 或已经过评审，都不是准入理由。

| family | 准入所需的知识 | 不由它承担 |
|---|---|---|
| requirements | 有来源、确认范围与可观察结果的要求；未决条款明确标注 | 实现步骤或未经确认的机制偏好 |
| research | 对持续设计问题有用、可核对来源并说明局限的观察 | 一次搜索记录、会话过程和整包原始日志 |
| proposals | 需要持续消费的选择对象、能力覆盖与至少三个实质候选的比较，详见[提案准入](proposals/README.md#主题准入与候选比较) | 一次施工安排，或已定选择下的普通任务拆分 |
| decisions | 已发生接受的选择、来源修订、范围与理由 | 尚待接受的决定草稿或评审者建议 |
| architecture | 有契约与决定依据的当前能力基、组合和覆盖视图，候选明确单列 | 第二份契约正文或任务完成率 |
| spec | 有语义拥有者、适用范围和版本边界的精确承诺；候选与已接受状态分明 | 实现细节、可变执行日志或未经登记的正式承诺 |
| providers | 能力到具体插件提供者的兑现关系、源码采用与符合性边界 | 通用编码计划或以文件存在代替实现证据 |
| assemblies | 实际提供者选择、配置、消费关系和完整动作链 | worker 调度或模块各自通过后的整体成功推断 |
| migrations | 需要长期维护的前后身份/采用对应、过渡约束、消费者切换与收口证据 | 一次交付的排期、派发单、文件搬运清单和进度跟踪 |

各 family 入口拥有具体准入和模板使用要求。一次施工的工作材料放本次明确工作区的 `tmp/`；
任务完成后只将有持续消费价值的结论整理回对应拥有者，不把整份计划和任务日志转为长期主题。
方法自身的演化归 `method/`，不冒充待设计系统的知识。

## 主题是信息包

每个 family 的 README 导航实际主题和本地 `.templates/`；每个 topic 子目录的 README
导航本主题的范围、输入、当前状态与按需正文。先读入口，当前问题需要时才展开详细设计、取舍、证据或评审。

例如：

```text
proposals/
├── README.md
├── .templates/topic/
│   ├── README.md          可复制的主题入口
│   ├── design.md          现有能力覆盖、演化与契约/插件设计
│   ├── alternatives.md    候选比较与依据
│   └── review.md          实际评审与处置
└── <topic>/               实际主题，由模板包起步
```

### 建包与维护

1. 先找现有主题；只有形成新的持续消费对象时才复制相应模板包，给子目录取可辨认的主题名。
2. 模板提示和 `{{说明}}` 是填写指导，成稿时替换或移除；不伪造身份、来源、接受或执行记录。
3. 以包为单位起步、按实际问题裁剪正文与附属材料；删除不适用文件时同步入口链接，保留影响结论的未知及闭合条件。
4. 包内链接保持相对路径，复制后仍可导航。跨包引用实际主题及可恢复修订，不引用模板包作为需求、决定或契约依据。
5. 每项含义只有一个拥有者；入口给摘要与路由，正文保存判断，证据保存观察，评审保存意见与处置，不在几个文件中维护同义权威。

这是信息组织单元，不要求每个主题具有相同文件数，也不要求每个需求依次创建所有 family。
研究、候选规格、原型可相互校准；同一主题的输入与结论有明确快照，实际状态逐项记录。
短小局部改动直接修改已有正文；任务级排期与进度仍放工作区 `tmp/`，稳定知识回到其拥有者。

## 知识怎样被下一步消费

- 需求保存可观察结果和确认范围；提案检查现有能力及组合，把未覆盖责任解释为组合、扩展、新增等演化。
- 新独立维度给出独立插件边界；精确承诺归规格，具体兑现归提供者/装配，整体保证仍须检验所有组合前提。
- 决定记录真实接受范围，规格记录精确版本；接受后的变化更新能力地图，使下一项需求能找到新的承载者。
- 验证记录反馈实现违约、语义遗漏、前提变化或新要求；研究/提案/决定按其职责处理，不用新结果暗改旧规范。

`.templates/` 只拥有模板，不是实际知识主题；它不参与能力地图、接受/发布清单或正式规格发现。
各 family 维护自己的模板形状，`method/` 和 skill 不维护另一份副本。模板不是登记格式，也不自动创建 catalog。
