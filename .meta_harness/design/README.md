# 系统设计链

这里维护待设计系统需求、产品、统一语言、领域对象、系统预期与上游机制知识。各目录入口导航实际 topic 与本地模板；
目录内容随采用基线演进，不能用迁移阶段或一次性数量描述长期状态。

系统级预期与新维护位置从 [architecture/](architecture/README.md)进入；模块承诺就近维护。
公开接口、薄SPEC、模型和验证资源归实际成员，不另设中央模块规格/实现映射。

## 终态与过程材料

Git 保存当前有效的需求、系统预期、承诺和必要理由，不保存决策形成史或开发流水。实现侧终态归对应包/应用；提案、决策过程、评审及原始执行证据归本工作树 `tmp/`。不要求永久溯源，不把旧 record 换名搬家或改成历史 Git 链接台账。

## 组织原则

**每一个会被继续消费的事实，只有一个手写的家；那个家由「什么事件会让这条事实失效」决定。
其余要么是散文，要么是派生物。**

因此目录不按文档体裁分（设计/说明/视图），也不按被描述的对象分（会话/运行/工具）。
体裁会变，对象会被重新分解，两者都不适合当永久地址；失效事件不会变——
需求失效是因为需求方改主意，契约失效是因为语义变更，上游机制的读数失效是因为上游换版本。

`domain_objects/` 不是这条规矩的例外：它**不是按对象分的一组目录**，而是「有哪些对象」这一件事的一个家，
条目以统一语言的词条 ID 为键，不自己发号。对象被重新分解时，变的是这个家里的条目，地址不动。

| 目录                                    | 保存什么                                               | 什么事件让它失效           |
| --------------------------------------- | ------------------------------------------------------ | -------------------------- |
| [ubiquitous_language/](ubiquitous_language/README.md) | 每个概念精确指什么——全链只有这一套说法 | 某个概念的含义变了         |
| [product/](product/README.md)           | 每个 topic 的产品设计：概念、模型、产品规则、验收       | 产品方向改变               |
| [domain_objects/](domain_objects/README.md) | 跨 topic 收齐的领域对象：身份依据、宿主、生灭、依据出处，以及对象性待裁项——**产品设计与架构、规格之间的那一站** | 一个对象被重新认定或重新分解 |
| [foundation/](foundation/README.md)     | 系统目标与全局约束（`SYS-*`）                          | 系统目标改变               |
| [architecture/](architecture/README.md) | 全系统架构预期、维护边界及承诺归属 | 已接受的架构方向或拥有者改变 |
| [basis/](basis/README.md)               | 内核与上游的机制语义条目及其 probe                     | 上游换版本                 |
| [views/](views/README.md)               | 全部派生的聚合视图                                     | 上游任一处变动             |

**核实事实与版本化读数不在这张表里。**它们归与 `design/` **平级**的顶层
[`research/`](../research/README.md)：那里拥有「这条事实成立到什么程度」，
设计链这边拥有「因此该怎么做」。**本目录下不设第二个 research 家。**

模块验证义务归实际拥有者；一次覆盖核对、迁移对照及执行结果留任务tmp，不维持中央形成史或覆盖登记。

## 派生物纪律

`views/` 下每一份都由生成器产出，带 `derived-from` 与生成时间。

**派生物不得被引为依据。** 需要引用时引上游那份手写的家。
视图用于找到入口和发现缺口，不用于证明任何状态；它与上游不一致时以上游为准，
并按 [views/](views/README.md) 重新生成，不手改视图使其看起来一致。

## 状态词怎样组合

这些词描述不同维度，不组成一条可以凭较后状态倒推较前状态的流水线：

| 状态词 | 精确含义 | 不能据此声称 |
|---|---|---|
| `candidate` | 内容可被审阅，选择或新谱系采用仍未由有权者闭合 | 已接受或可供消费者发布使用 |
| `accepted` | 有权者接受明确对象、修订和范围 | 实现符合或应用已经装配 |
| `implemented` | 具名提供者在固定源码修订上声称兑现精确契约，并有相称符合性证据 | 应用选择了该提供者，或完整动作链成立 |
| `assembled` | 具名应用选择精确提供者、配置和版本，并通过真实组合证据 | 所有部署或未覆盖故障条件都成立 |
| `gap` | 某个必要语义、证据、提供者、采用或装配输入仍缺失；必须标明 owner 与闭合条件 | 对象不存在，或可以用相邻状态替代 |

同一对象可以同时是 accepted的承诺、尚未 implemented 的提供者和尚未 assembled 的应用。
入口只解释词义；实际状态由当前承诺拥有者及明确的实现/验证范围拥有。

## 准入与停止条件

材料进入本目录，是因为后续设计或维护会持续消费其中的知识。先判断这条事实**何时失效**，
再选目录和模板；完成一次任务、写成 Markdown 或已经过评审，都不是准入理由。

| 目录         | 进入前必须能回答                                                     | 不满足时停止在何处                                                       |
| ------------ | -------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| ubiquitous_language | 这个词是否被一个以上 topic 用，读错它会不会让人把设计或实现做错      | 写不出无歧义定义就先别收——那说明这个概念自己还没想清楚，收它等于把草稿定成语言 |
| product      | 这解决谁的什么问题、不做会怎样、边界到哪；它与现有 topic 的区别是什么 | 答不上来就先不建包，把待答交流留在执行工作树 tmp，持续未决归当前正文；不建空壳 |
| domain_objects | 它有没有统一语言词条、形态是不是「对象」；身份、宿主、生灭能不能各指回产品正文的某一节 | 没有词条的先立词条；立不了的进 `pending.md` 并写清谁来裁；指不回正文的那一栏写「正文未述」，不补一个看起来合理的 |
| foundation   | 这条约束是否由产品负责人确认，适用范围与例外是否明确   | 未确认的不写进正文；设计推导出的结论回其 topic，不上升成系统约束         |
| basis        | 这条机制语义是否跨多次设计被反复依赖，能否给出 symbols 与会失败的 probe | 只在本次用到的上游读数写进本次分析产物；给不出 probe 时记为待核对主张    |
| views        | —                                                                     | 不手写，不手改；缺内容说明上游缺或生成器缺                               |

各目录入口拥有具体准入、停止条件和模板使用要求。一次施工的工作材料放本次明确工作区的 `tmp/`；
任务完成后只将有持续消费价值的结论整理回对应拥有者，不把整份计划和任务日志转为长期主题。
可复用设计方法及其演化归 `harness-design-handbook` skill
，维护过程放任务 tmp，不冒充待设计系统的知识。

## 主题是信息包

`views/`只派生剩余设计源，`ubiquitous_language/` 与 `domain_objects/` 按条目组织，其余目录按 topic 组织。每个目录的 README 导航实际主题
和本地 `.templates/`；每个 topic 子目录的 README 导航本主题的范围、输入、当前状态与按需正文。
先读入口，当前问题需要时才展开详细设计、取舍、证据或评审。

例如：

```text
product/<topic>/
├── README.md          当前范围与导航
├── design.md          当前概念、规则、必要理由和未决
└── acceptance.md      可观察的产品结果
```

提案、接受过程、评审与运行日志只落执行工作树 `tmp/<task>/`。

### 建包与维护

1. 先找现有主题；只有形成新的持续消费对象时才复制相应模板包，给子目录取可辨认的主题名。
2. 模板提示和 `{{说明}}` 是填写指导，成稿时替换或移除；不伪造身份、来源、接受或执行记录。
3. 以包为单位起步、按实际问题裁剪正文与附属材料；删除不适用文件时同步入口链接，保留影响结论的未知及闭合条件。
4. 包内链接保持相对路径，复制后仍可导航。跨包引用实际主题及可恢复修订，不引用模板包作为需求、决定或契约依据。
5. 每项含义只有一个拥有者；入口给摘要与路由，正文保存当前规则与必要理由；可复跑资源归其消费者，过程观察与评审放任务 tmp，不在几个文件中维护同义权威。

这是信息组织单元，不要求每个主题具有相同文件数，也不要求每个需求依次创建所有目录。
研究、候选规格、原型可相互校准；同一主题的输入与结论有明确快照，实际状态逐项记录。
短小局部改动直接修改已有正文；任务级排期与进度仍放工作区 `tmp/`，稳定知识回到其拥有者。

## 知识怎样被下一步消费

- 需求保存可观察结果和确认范围；提案检查现有能力及组合，把未覆盖责任解释为组合、扩展、新增等演化。
- 上游机制的读数从 basis 取，供提供者设计与装配核对用，不在每次分析里重推；上游换版本时由 probe 失败暴露，而不是等设计出错。
- 新独立维度有独立的契约边界，装配时由独立插件承载；新或已迁单元的精确承诺随接口拥有者维护，实际兑现由源码与证据说明。整体保证须检验所有组合前提。
- 承诺拥有者维护当前采用范围与必要理由；消费者经实际公开入口找到有效承诺，不保存决定形成史。
- 验证记录反馈实现违约、语义遗漏、前提变化或新要求；原始结果留任务tmp，不用新结果暗改旧规范。

`.templates/` 只拥有模板，不是实际知识主题；它不参与覆盖关系、接受/发布清单或正式规格发现。
各目录维护自己的模板形状，skill 不维护另一份副本。模板不授予采用或接受状态。

具体方法继续由 `harness-design-handbook` skill 按需导航；
产品事实和接受状态只由本设计链的实际 owner 维护。
