# 设计在里程碑内保持稳定的契约

本页的读者是给 agent 布置领域设计或契约设计的人类协作者。
它从设计角度讲方法：契约为什么会在交付中途改变，怎样在设计时预防，以及怎样指导和评审 agent 的产出。

本页是学习材料，不是项目规则。
依赖方向、成员文档和演进政策由文中链接的拥有者正文规定。两者不一致时以拥有者正文为准。
交付线、联调轨道与里程碑基线的项目规则尚未定稿。定稿前本页只把它们当作背景，定稿后以[工程规则](../../docs/engineering/README.md)正文为准。

## 先分清两种稳定

**里程碑内稳定是一项协作承诺。**在一个里程碑期间，其他交付线只按契约开发，不跟踪提供者的内部变化。
契约在这段时间里只以可加的方式改变，消费者已经写好的代码继续成立。

**跨里程碑兼容是一项版本承诺。**本项目在 0.0.0 至 0.1.0 阶段不承诺它。
[当前演进政策](../../docs/engineering/publication.md#当前演进与消费者)鼓励有正向收益的破坏性重构，并要求同批同步消费者、删除被替代实现。

所以设计目标不是「契约永远不变」。目标有两个：

1. 里程碑期间的改变都是可加改动。
2. 必要的破坏性改动集中在可以安排的点上，不在各条线里随时发生。

本页的「契约」指三样东西：

- 公开类型，拥有数据形状。
- 成员的 `SPEC.md`，拥有类型表达不了的行为：结果、失败、所有权、生命周期、并发、事务、取消和恢复。归属见[成员文档要求](../../docs/member-documentation.md#行为契约与完整文档)。
- Cordis 服务定义与事件，拥有装配时的接缝。精确规则归 [Cordis 集成约定](../../docs/architecture/cordis-integration-conventions.md)。

三者中行为最危险。类型改了，编译器会报错。行为改了，编译照样通过，消费者在运行时才得到错误结果。

## 契约为什么会在中途改变

回看一个里程碑里的契约改动，原因大多落在下面六类。设计时逐类预防，比事后加检查便宜得多。

| 原因 | 典型表现 | 预防它的方法 |
| --- | --- | --- |
| 契约从提供者的实现长出来 | 契约暴露内部步骤、存储形状、队列或具体 SDK 类型。实现一改，契约跟着改 | [方法一](#方法一从消费者的场景出发)、[方法二](#方法二按变化速度分层把易变的部分藏起来) |
| 形状冻结时语义还没想清 | 失败集合、顺序、生命周期或所有权留空。后来补定义时只能改契约 | [方法四](#方法四冻结之前把语义写完整) |
| 为将来可能的用途预留了面 | 没有具名消费者的字段或管理接口。真正用到时发现形状不对 | [方法一](#方法一从消费者的场景出发) |
| 形状本身不能加 | 封闭的输出联合、位置参数、来回两用的类型。任何新增都是破坏性改动 | [方法三](#方法三让形状天生可加) |
| 变化速度不同的东西混在一个接口里 | 稳定的身份与所有权，和易变的策略、参数放在一起 | [方法二](#方法二按变化速度分层把易变的部分藏起来) |
| 直接使用外域的内部模型 | 外域每次调整都传进本域契约 | [方法五](#方法五经自己的投影使用外域) |

## 方法一：从消费者的场景出发

契约的内容由真实消费者的需要决定，不由提供者能提供什么决定。这个方法叫消费者驱动契约（Ian Robinson，2006）。

设计时按下面的顺序做：

1. 列出每个具名消费者。一条交付线、一个运行时或一个应用都可以是消费者。
2. 为每个消费者写一到三个场景，用「给定……当……则……」的句式。场景说清消费者要完成什么，需要契约给出哪些事实，接受哪些输入，遇到哪些失败时怎样继续。
3. 从全部场景反推契约：契约是满足这些场景的最小集合。
4. 删掉没有场景支撑的条目，或者把它们明确推迟到以后的里程碑。

场景先于类型。先写类型会让设计者从自己的实现出发补字段。先写场景会逼出消费者真正要的事实，例如「失败后能不能重试」，而这类事实在类型里往往没有位置。

本项目已经规定外域概念怎样进入本域，以及新增跨域概念时要回答的五个问题，见[领域语义依赖与模型边界](../../docs/architecture/layers-and-dependencies.md#领域语义依赖与模型边界)。消费者场景是回答这五个问题的原材料。

## 方法二：按变化速度分层，把易变的部分藏起来

Parnas 在 1972 年提出：按「哪些设计决定可能改变」划分模块，每个模块隐藏一个可能改变的决定。
契约是模块之间唯一可见的部分，所以它只应该包含不容易改变的决定。

把候选条目按变化速度分成三层：

| 层 | 内容 | 放在哪 | 什么时候定 |
| --- | --- | --- | --- |
| 核心语义 | 身份、所有权、租户、权威状态、失败类别、生命周期阶段 | 契约 | 里程碑开始之前 |
| 可扩展面 | 可选能力、附加字段、新的变体 | 契约，但按[方法三](#方法三让形状天生可加)设计成可加的形状 | 用到时加入 |
| 易变细节 | 策略、参数、提供者的选择、内部步骤、存储形状 | 配置、提供者或装配，不进契约 | 由拥有者随时调整 |

Robert C. Martin 的稳定依赖原则说：依赖应当指向更稳定的一方。稳定抽象原则说：越稳定的包越应当抽象。
契约成员被多条线依赖，所以它应当是最稳定、最抽象的一层，不含实现细节。

John Ousterhout 把小接口、大实现的模块叫作深模块。对契约来说，可见的条目越少，可能改变的地方就越少。
不要为了「完整」给契约加一整套管理或调试接口。本项目的外域概念表也要求：与本域职责无关的内容不进入本域模型，不为将来可能使用而预留整套外域对象或管理接口。

## 方法三：让形状天生可加

### 可加的依据

Bertrand Meyer 的契约式设计和 Liskov 的替换原则给出同一条规则：

- 可以放宽前置条件，也就是接受更多输入。
- 可以加强后置条件，也就是保证更多结果。
- 不能收紧前置条件，也不能放宽后置条件。

满足这条规则的改动不破坏已有的使用方，这就是可加改动。

### 先判断谁写谁读

把这条规则落到 TypeScript 形状上时，关键不是「输入还是输出」，而是**谁构造这个值，谁读取这个值**。
构造值的一方叫写方，读取值的一方叫读方。改动对写方和读方的影响相反。

| 改动 | 对写方 | 对读方 |
| --- | --- | --- |
| 加可选字段 | 不破坏 | 不破坏，读方忽略不认识的字段 |
| 加必填字段 | 破坏 | 不破坏 |
| 必填改为可选 | 不破坏 | 破坏，读方必须处理字段缺失 |
| 可选改为必填 | 破坏 | 不破坏 |
| 删除字段 | 破坏，对象字面量会触发多余属性检查 | 破坏 |
| 给联合加成员 | 不破坏 | 破坏，除非契约事先声明这个联合是开放的 |
| 从联合删成员 | 破坏 | 不破坏 |

用这张表时要找全写方：

- 一个契约有多个提供者时，每个提供者都是输出值的写方。
- 消费者按契约开发时使用的替身也是写方。给输出加必填字段，会破坏所有替身。
- 消费者传入的回调，参数由提供者写、消费者读，返回值由消费者写、提供者读。方向与普通函数相反。
- 由别人实现的接口，例如提供者接口或插件接口，加必填方法会破坏所有实现者。加可选方法不破坏实现者，但调用者必须处理方法缺失。

### 设计成可加的形状

- **每个类型只朝一个方向流动。**来回两用的类型同时有写方和读方的约束，几乎任何改动都是破坏性的。把它拆成请求形状和结果形状。
- **用具名字段的选项对象，不用位置参数。**选项对象可以加可选字段。位置参数只能加在末尾，而且顺序一旦定下就不能改。
- **冻结前决定每个输出联合是开放还是封闭，并写进 SPEC。**开放的联合要求读方保留默认分支处理不认识的成员，以后加成员是可加改动。封闭的联合允许读方穷举，以后加成员是破坏性改动。两种都可以，但不能不决定。
- **失败分两层表达。**失败类别少而封闭，消费者按类别决定下一步。具体原因作为开放的细节，以后可以加。
- **读方只读自己需要的字段。**Martin Fowler 把这种做法叫宽容读者。它让提供者加字段时不影响读方。
- **能力差异用声明表达，不用版本号判断。**提供者声明自己支持哪些可选能力，消费者按声明分支。

### 不要用「万能袋」逃避设计

`Record<string, unknown>`、通用 JSON、不透明回调或句柄看起来让契约永远不用改。
实际上它们只是把破坏性改动从编译期推到运行期：形状没变，含义变了，消费者在运行时才失败。
项目规则同样指出，把外域对象封装成通用 JSON、回调或句柄不构成边界隔离，见[隔离语义，不隐藏责任](../../docs/architecture/layers-and-dependencies.md#隔离语义不隐藏责任)。
确实需要扩展点时，为它定义拥有者、取值范围和读方的处理规则。

## 方法四：冻结之前把语义写完整

形状稳定而语义漂移，比形状改变更糟，因为编译器不会提醒任何人。
冻结一个操作之前，逐项回答下面的问题，并写进 SPEC：

1. 前置条件：调用者必须满足什么？不满足时得到什么结果？
2. 结果：成功时保证什么？观察到的成功是否等于可靠承接？
3. 失败：失败集合是什么？未知结果怎样表达？失败后状态处于哪一步？
4. 顺序与并发：并发调用时的顺序保证是什么？同一对象能否重入？
5. 生命周期：对象怎样创建、撤除和恢复？撤除后的调用得到什么？
6. 所有权与租户：谁拥有权威状态？跨租户访问怎样被拒绝？
7. 重试与幂等：调用者能否重试？重复调用的结果是什么？
8. 取消：取消后已经发生的外部副作用怎样交代？

回答不了的问题，不要猜。
把它明确写成「本里程碑不承诺」，并且让形状不暴露它。形状不暴露，以后加入就是可加改动。形状暴露了而语义没定，以后补定义就是破坏性改动。

Mary 和 Tom Poppendieck 把这种做法叫作在最后负责时刻决定：不需要现在定的事，留到不得不定时再定。
但对契约有一个例外：被其他线消费的部分必须在里程碑开始时定清。其他线开始按它开发的那一刻，就是它的最后负责时刻。

## 方法五：经自己的投影使用外域

本域需要外域的知识时，按[外域概念的进入方式](../../docs/architecture/layers-and-dependencies.md#外域概念的进入方式)选择：消费公开契约、建立消费投影、保留有类型的引用，或者交给外部协调者。

对稳定性来说，投影的作用是隔离。DDD 把这层转换叫防腐层。

- 本域只引用外域的标识和公开契约，不导入外域的内部类型。
- 语义不适配时，在本域边界建立只含本域所需事实的窄投影。
- 外域的可加改动不进入投影，本域不受影响。
- 外域的破坏性改动只需要修改投影的转换处，本域契约不变。

## 方法六：用替身和行走骨架提前暴露缺口

契约设计会遗漏语义，这很正常。要做的是让缺口在改动还便宜的时候暴露出来。

- **替身和契约一起设计。**替身按契约的行为实现，不只是返回固定值。写替身时必须决定失败何时发生、结果按什么顺序到达，这会逼出 SPEC 里漏掉的语义。
- **一套一致性测试同时验证替身和真实提供者。**这样，各条线按替身开发的结果，到联调时对真实提供者仍然成立。
- **里程碑早期跑通行走骨架。**Alistair Cockburn 把行走骨架定义为：用最薄的真实实现把系统端到端连起来。在联调轨道上尽早让每个契约被真实调用一次，缺失的语义就会在早期出现，而不是在里程碑末尾集中出现。

## 一个里程碑里的节奏

### 开始之前：契约设计

按接缝组织设计，而不是按领域逐个设计。一个接缝是一组提供者和它的全部消费者。每个接缝产出下面的内容：

1. 消费者场景表。
2. 每个条目的层：核心语义、可扩展面，或不进契约。
3. 每个类型的写方和读方。
4. 每个输出联合的开放性。
5. 按方法四填完的语义清单。
6. 本里程碑不承诺的事项清单。

评审通过后，这些契约成为本里程碑的基线。

### 期间：只做可加改动

想做一项破坏性改动时，按顺序问三个问题：

1. 能不能用可加的方式表达？例如加一个新操作，而不改旧操作的含义。或者加一个新字段，而不改旧字段的含义。
2. 能不能推迟到下一个里程碑？
3. 前两项都不能时，把它安排在联调轨道上。

在联调轨道上有两种做法：

- **同批改动。**在一次交付里修改提供者、同步全部消费者并删除旧形状。这是当前演进政策的默认做法。
- **扩、迁、收。**先加新形状，各消费者分别迁移，最后删除旧形状。Danilo Sato 把它叫作并行改变。只在消费者分布在多条并行的线、无法同批改动时使用。它会让两种形状暂时并存。当前政策规定，没有明确要求时不增加兼容双轨。所以使用前要取得明确批准，并在同一里程碑内完成删除。

### 结束之后：回看

列出本里程碑所有的契约改动，按[六类原因](#契约为什么会在中途改变)归类。
下一次契约设计重点预防最常出现的那一类。

## 怎样指导 agent

### 布置契约设计时给出的输入

- 具名消费者，以及每个消费者的场景。没有场景时，先让 agent 起草场景交你确认，再设计形状。
- 本里程碑的范围，以及明确不在范围内的事。
- 已有的外域公开契约和可用的投影。
- 要求的产出：本页「开始之前」一节列出的六项内容。

设计判断沿 `harness-design-handbook` skill 进行。评审按判断对象选择 reviewer，见[评审分工](../agents/roles/README.md#按判断对象选择-reviewer)。
把一批契约当作语义整体评审时，派 design-reviewer 的 choice 类判断。核对 SPEC 是否完整、无歧义时，派 expression 类判断。

### 评审 agent 产出时问的问题

1. 每个条目都有具名消费者和场景吗？
2. 契约里有没有提供者的实现细节，例如存储形状、内部步骤、队列或具体 SDK 类型？
3. 每个类型的写方和读方是谁？加一个字段会破坏谁？
4. 每个输出联合是开放还是封闭？SPEC 写明了吗？
5. 失败、未知、撤权、取消和恢复都写了吗？
6. 有没有用 `unknown`、通用 JSON 或不透明回调代替设计？
7. 有没有直接导入外域的内部类型，而不是使用公开契约或投影？
8. 契约的形状有没有为了迁就 Cordis 机制而改变？领域与能力独立于 Cordis 建模，对不上时先换提供者设计（D-112）。
9. 本里程碑不承诺的事项，有没有被形状暴露出来？

### agent 常见的偏差

- 把实现里的类型直接导出成契约。
- 为了「完整」预留一整套管理接口。
- 输出联合默认封闭，而 SPEC 没有说明。
- 把可选输入改成必填，理由是「更严谨」。
- 用 `metadata: Record<string, unknown>` 作扩展点。
- 在线内顺手修改契约，去配合自己的实现。

看到这些偏差时，要求 agent 回到消费者场景重新说明理由，不要只让它改掉那一处。

### 可以直接使用的指令模板

> 为〈接缝名〉设计本里程碑的契约。
> 消费者：〈列出具名消费者〉。范围：〈本里程碑范围〉。不在范围：〈列出〉。
> 先为每个消费者写一到三个「给定……当……则……」场景，交我确认后再设计形状。
> 形状确认后，产出六项：消费者场景表，条目分层，每个类型的写方和读方，每个输出联合的开放性，完整的语义清单，本里程碑不承诺的事项。
> 只引用外域的公开契约和标识。不要导入外域的内部类型，不要使用 `unknown` 或通用 JSON 作扩展点。
> 不能确定的语义列为待决，不要猜测。
