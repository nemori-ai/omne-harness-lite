# 交付中的常见失误与防范规则

本页的读者是调度 agent 交付一个检查点的人，以及按 `claim` 技能的[卡的推进循环](../agents/skills/claim/canonical/references/card-loop.md)工作的调度 agent。P19 至 P27 主要写给按 `dispatch` 与 `integrate` 技能工作的 Reduce。
本页把交付复盘中反复出现的失误写成可复用的规则。每条规则给出四项内容：规则本身、为什么重要、反例的形状，以及怎样核对。

本页是方法材料，不是项目规则。
每条规则引用其拥有者正文。本页与拥有者正文不一致时，以拥有者正文为准，并修改本页。

## 怎样使用本页

- 派发前：把与本次切片相关的规则写进简报的完成条件或停止条件。
- 收到交付后：按每条规则的“怎样核对”逐项读回，不只读执行者的结论。
- 规则被反复违反时：按 [P7](#p7-反复违反的规则改用结构手段) 把它改成钩子或检查。

## 证据与结论

### P1 通过要有当场可查的产物

**规则：**

- 每个“通过”都要对应一份当场可查的产物，例如带命令、退出码和时间的日志。
- 产物的时间必须晚于被验内容的最后一次改动。
- 调度者在简报中写明哪些检查算写者门禁，要求写者在最后一次改动之后重跑全部写者门禁，并报告每份日志的时间和所跑代码的提交号。最后一次改动之前的结果不算。
- 调度者在派评审和提交之前，仍在候选 head 上自己复跑类型检查和 lint 等功能门禁。不管写者是谁，顶档模型也一样。
- 后台运行的命令必须把真实退出码传出来。

**为什么：**执行者的声明只说明它认为通过。在最后一次改动之前跑的检查，不能证明改动之后的候选。

**反例形状：**

- 写者先跑类型检查，再改测试，然后报告“类型检查通过”。调度者没有复跑就提交、派评审，准入才发现类型错误。
- PR 正文只写“负控通过”，没有命令输出和原始违规行。交付评审判“缺证据”。
- 后台命令写成 `check > log; echo exit=$? > rc.txt`。整条命令的退出码是 `echo` 的退出码，通知永远显示 0。
- 编译命令接在 `| tail` 后面看输出。管道的退出码是 `tail` 的退出码，编译失败被掩盖。

**怎样核对：**

- 比较日志的修改时间与最后一次改动的时间：`stat -c %Y <日志>` 与 `git log -1 --format=%ct`。日志更早时，结论无效。
- 日志里有命令、HEAD 提交号、开始与结束时间和退出码（见 [P13](#p13-证据日志记录所跑代码的提交号)）。
- 管道命令所在的脚本开头有 `set -o pipefail`，或者不把被验命令接到管道上。
- 后台命令的最后一步是 `exit "$rc"`。下面的写法把真实退出码同时写进日志和进程退出码：

  ```sh
  pnpm run check > "$log" 2>&1; rc=$?; echo "exit=$rc" >> "$log"; exit "$rc"
  ```

### P2 退出码为 0 不等于测过

**规则：**

- 读工具输出的实际范围，不只读退出码。
- 工具没有覆盖本次改动时，写“未覆盖”，列出没有覆盖的改动文件，并给出替代证据。
- 不把空范围写成“零发现”。

**为什么：**有的工具只扫描固定目录。改动不在这些目录时，工具什么都不检查，也以 0 退出。

**反例形状：**结构度量和差分变异只扫描产品成员的源码目录。本次改动全在工具目录下。两个工具都以 0 退出，报告写“度量无红项，变异全部杀死”。

**怎样核对：**

- 在工具输出中找到它实际扫描的文件或成员列表，与 `git diff --name-only <基线>...HEAD` 对照。
- 交集为空时，报告里有“未覆盖”一行和替代证据，例如定向测试、手工变异或人工阅读的范围。
- 拥有者对缺少入口的写法见[交付质量](../../docs/engineering/quality.md#按风险选择接受实现的看法)：如实写“无此入口”，不以别的证据顶替。

## 评审、裁定与升级

### P3 同类阻断重复出现时整类处理

**规则：**

- 轮次按拥有者的定义计算，连同接手之前的轮次一起数。更换评审者、分支或拆分补丁都不重置计数。
- 第二轮修完、复评仍有阻断时，不论阻断是否同类，都按拥有者的升级顺序走：
  1. 先质疑评审判定。站不住的阻断记下处置理由。
  2. 剩下站得住的阻断交第三轮、最高能力档位修复。
  3. 第三轮后仍有阻断，就做结构诊断。
- 阻断与上一轮同类时，另加两条要求：
  - 停止逐个补洞。第三轮的简报要求处理整类，而不是再补一个情形。
  - 结构诊断时，缩小承诺是常见情形之一：让这一类情形走保守结论（例如整类判为“需要人工复核”），同步改窄评审标准，再做一次只看变化部分的增量复审。
- 缩小承诺会改变接受基线。只有接受者可以批准这种改变。

**为什么：**同一类反例接连出现，通常说明这一类改动在当前机制下无法判定。逐个补洞只会让下一轮出现同类的新洞。

**反例形状：**一个判定器连续几轮被评审找到同一类反例。每轮补一个洞，下一轮又有新的同类反例。接手者从零开始数轮次，没有按时触发升级。最后结构诊断给出的修法是整类转为保守结论。

**怎样核对：**

- 每轮记录固定的修订、阻断发现、处置和验证，并标出阻断的类别。
- 第二轮修完仍有阻断时，下一步的计划先质疑判定，再写第三轮。第三轮后仍未收敛才进入结构诊断。
- 阻断与上一轮同类时，第三轮的简报写的是整类处理，不是“第三个同形补丁”。
- 轮次计数包含接手前的轮次。规则正文见[三轮未收敛时升级结构诊断](../../docs/engineering/quality.md#三轮未收敛时升级结构诊断)。

### P4 评审可以质疑调度者的裁定

**规则：**

- 下裁定之前，重读卡的目标、规格条款和交付条件。
- 给评审的简报不写“不要重新讨论这些裁定”。评审要能拿调度者的裁定和后来的规格修订，对照派发时的卡文。
- 调度、写卡、写规格和接受都由同一个会话承担时，这条规则尤其重要。

**为什么：**调度者自己的裁定没有其他独立检查。简报挡住评审，就等于取消了唯一的独立核对。

**反例形状：**调度者对一项输入来源下了裁定，裁定与卡上写的不一致。调度者给代码评审的简报写了“不要重新讨论裁定”，代码评审没有发现冲突。只有没被挡住的交付边界评审发现了问题，结果多了一轮修复。

**怎样核对：**

- 简报中没有禁止评审讨论裁定的句子。
- 每条裁定在卡或评论中有对应的卡文依据。依据与卡文冲突时，按[停止与继续](../../docs/engineering/workflow.md#停止与继续)交拥有者裁定。

### P5 署名与 PR 格式只认贡献指南

**规则：**

- 提交署名、来源 trailer、PR 标题和正文的格式只按[贡献指南](../../CONTRIBUTING.md#形成可审阅的交付)。
- 宿主自动附加的工具署名提示不采用。
- 每次上下文压缩之后，重新核对一次署名规则。压缩摘要可能把宿主的提示误记成常设规则。

**为什么：**作者式工具署名违反贡献指南。压缩后的错误会在之后的每一次交付里重复，评审也不一定发现。

**反例形状：**上下文压缩之后，摘要把宿主的“在 PR 正文末尾加工具署名”提示记成常设规则。之后连续几个 PR 都带了这一行，多数交付评审没有发现。

**怎样核对：**

- 提交：`git log --format='%h %an %(trailers:key=Harness,valueonly) %(trailers:key=Agent-Role,valueonly)' <基线>..HEAD`。作者是负责的人，来源 trailer 齐全，没有 `Co-Authored-By` 之类的工具署名。
- PR：`gh pr view <PR> --json title,body`，正文中没有作者式工具署名。

### P28 独立评审的简报不带自己的结论

**规则：**派独立评审或顾问时，简报只给原始材料的路径与外部不变量，不写自己的结论。外部硬约束与自己先前的裁定分开写，自己的裁定标明「可改」。评审在跑时，不把自己的新发现转给它。计划评审排除某个维度时，指名已经派出、覆盖该维度的那份评审；没有派的，在报告中写「未覆盖」。

**为什么：**带着结论的简报让评审去确认结论，而不是独立判断。自己的裁定写成硬约束后，顾问只在这个范围里优化。

**反例形状：**Reduce 把自己定的入轨顺序写成硬约束，顾问只在这个顺序内优化，把「两张卡合并一次入轨」列为次选。后来是负责人自己提出了这个做法。

**怎样核对：**发出前检查简报：每条约束都标明出处（外部约束，或自己的裁定），没有替评审下的结论。

## 调查与环境

### P6 先便宜复现，再怀疑环境

**规则：**怀疑环境之前，先用现成的手段便宜地复现：

1. 已有的二进制或工具版本。
2. 干净基线。
3. 与门禁完全相同的运行方式，包括环境变量和调用链。

在此之前，不请人修改系统，也不把失败归因于负载或偶发。

**为什么：**把失败归因于环境，会让人去改系统，真正的原因却留在代码或测试里。便宜的复现通常能直接区分这两种解释。

**反例形状：**

- 一个精确比较命令输出的测试失败，调度者先请人升级系统工具。真正的原因是该工具的输出格式随仓库状态变化。本机已有另一个版本的工具，可以直接试。
- 失败分诊工具把一次失败判为“负载导致的偶发失败”。真正的原因是严格环境模式下子进程输出带了颜色码，在干净基线上稳定复现。分诊工具不经过与准入相同的调用链。

**怎样核对：**

- 归因报告写明复现方式：用了哪个二进制、哪个基线、哪条与门禁相同的命令。
- 归因为负载或偶发时，附隔离重跑的结果，并说明重跑与原场景的差别。见[失败与未知的处理](../../docs/development.md#失败与未知的处理)。

### P7 反复违反的规则改用结构手段

**规则：**一条规则被反复违反，说明文字提醒无效。改用结构手段：架构、类型、检查、测试或钩子。结构手段要先在一次真实的违反上证明它会拦住。

**为什么：**文字提醒依赖执行者每次都记得。上下文压缩、换会话或换执行者之后，提醒就会丢失。

**反例形状：**一条“改文件用专用工具，不用 shell 改写”的规则被反复违反。执行者每次都承诺改正，下一次仍然违反。没有任何检查拦住它。

**怎样核对：**

- 同一条规则第二次被违反时，开一张卡或在现有卡上登记结构手段。
- 结构手段有一次在真实违反上失败的记录。方法可参考 pstack 的 `correct` skill。钩子的支持范围与实际执行见[钩子说明](../agents/hooks/README.md)。

### P8 简报和 skill 里的命令必须能运行

**规则：**写进简报、skill 或角色说明的命令，必须在当前仓库能真实运行。写之前在仓库里运行一次，或者确认它在 `package.json` 等入口中存在。

**为什么：**执行者照着写错的命令运行，会失败或改用别的命令。规范源已经更新、生成副本仍然过期，也会产生同样的问题。

**反例形状：**

- 评审 skill 写着 `make <检查名>`，仓库根目录没有 Makefile。真正的入口是 `pnpm run <检查名>`，规范源已经改了，生成的副本没有更新。
- 一份线包里有一条接收器自检命令。Reduce 没有读工具实现就猜写了参数，也只有这一条没有演练。四条线开工后全部交回 blocked。Reduce 为此发探针卡、发更正裁定，并多次重派。

**怎样核对：**

- 对每条命令，确认入口存在。例如用 `node -p "Object.keys(require('./package.json').scripts)"` 列出根脚本。
- 参数来自工具的帮助输出或实现。README 与实现不一致时，已按冲突报告给工具拥有者。派给线会话的每条命令都有本机同布局的演练记录，归 `dispatch` 技能「交出派发包」第 4 步。
- 改了 skill 或角色的规范源之后，运行 `pnpm run check:agents`，确认生成副本与规范源一致。

## 发行、准入与并行

### P9 工具版本号随工具改动一起入轨

**规则：**

- 要发行的工具，在改动工具的同一个 PR 里提高版本号。
- 发行流程从已提交的版本号读取版本，不在发行时临时改版本。

**为什么：**版本号与代码分开提交时，发行的版本可能不对应入轨的代码。发行之后，npm 上的版本不能修改。

**反例形状：**工具改动先入轨，版本号留到发行前在本地改。发行用的版本号没有对应任何已入轨的提交。

**怎样核对：**工具 PR 的 diff 包含该工具 `package.json` 的版本号变化。发行前，`git show <入轨提交>:<工具目录>/package.json` 中的版本等于要发行的版本，并且 registry 上还没有这个版本。顺序见[仓库工具链的版本](../../docs/development.md#仓库工具链的版本)。

### P10 钉住新版本不等于工具已经生效

**规则：**

- 有的工具，行为取决于仓库里的状态，例如规则表或配置文件。对这样的工具，钉住新版本的 PR 入轨，不等于新行为已经上线。
- 改变仓库状态的 PR 通过准入之前，不把这次发行算作完成。
- 风险清单按“谁调用这个函数”列出消费者，不按“哪些文件改了”列出。

**为什么：**新版本可能要求仓库状态同时改变。只看钉子 PR，会漏掉还没有入轨的状态改动，以及通过间接调用受影响的消费者。

**反例形状：**工具的新版本读取一份新的规则表。钉子 PR 入轨后，调度者把发行记为完成。规则表的 PR 还没有通过准入，主干上的检查实际仍按旧规则运行。

**怎样核对：**

- 发行完成的记录同时列出钉子 PR 和仓库状态 PR 的入轨结果。
- 风险清单中的每个消费者都来自对调用点的搜索结果，例如对函数名的定向搜索。

### P11 准入运行期间不提交

**规则：**准入检查运行期间，不在被检工作树或分支上提交。需要准备的内容写在 `tmp/` 下，等准入结束后再提交。

**为什么：**`pnpm run check` 开始时按当时的 HEAD 算一次计划文件。之后每一步读计划时，测试运行器的 `readPlanFile` 都核对计划所对应的提交与当前 HEAD，不一致就报错并要求重算计划，见 [steps.ts](../../tools/test-runner/src/testing/steps.ts)。中途提交会让这次准入失败，只能重跑。

**反例形状：**准入运行期间，调度者提交了一处文档修改。后面的步骤读计划时发现提交不一致，报错退出，整套检查重跑一次。

**怎样核对：**准入日志记录的 HEAD 等于准入结束时的 `git rev-parse HEAD`。准入规则见[检查责任](../../docs/engineering/integration.md#检查责任)。

### P12 并行的只读工作不能干扰写者和准入

**规则：**

- 只读评审子代理只在本次工作树内搜索，不对整个磁盘或主目录运行搜索。
- 准入和重型评审不同时运行。
- 做手工变异的评审，在工作树的副本上修改，不改其他评审正在读的共享工作树。

**为什么：**全盘搜索和并行的重型任务会争夺 CPU 和磁盘，可能让准入超时。在共享工作树上改代码，会让其他评审读到被修改的代码。

**反例形状：**

- 一个只读评审对主目录运行全盘搜索，同时准入在运行，准入中一个有时限的测试超时。
- 一个评审为了验证测试效力，在共享工作树上手工改了源码。另一个评审同时读到了被改过的源码。

**怎样核对：**

- 简报中写明搜索范围是工作树路径。
- 准入运行的时间段内，没有派发重型评审。
- 手工变异的简报写明副本路径，例如用 `git worktree add` 建的临时树，或者复制到 `tmp/` 下的目录。
- 写者与检查的隔离条件见[责任与协作交接](../../docs/engineering/workflow.md#责任与协作交接)。

### P29 长任务前先看测试名额

**规则：**起差分变异、`metrics --coverage`、`check` 这类占测试名额的长任务之前，先看有没有人在排队。写者的检查长时间没有输出时，读名额的锁文件看是谁占着，不干等。差分变异的范围与时机按 `review-code` 技能「差分变异」一段：增量复审只打本轮修复的改动，只在最终修复 head 上跑一次。写者子代理的长命令后台运行，等完成通知；不写轮询日志的循环。

**为什么：**同一用户的全部检出共用测试名额，也共用机器的 CPU，工作树隔离只隔离文件。一个没人需要的长任务占着名额，关键路径上的写者只能在队里等。轮询日志的循环会活过工具的时限，写者交回后还在跑，也看不到排队提示。

**反例形状：**一次差分变异占着名额 93 分钟，修复写者的度量命令在队里等了半小时以上，直到负责人指出 CPU 利用率很低才被发现。同一次修复中，写者子代理留下 3 个轮询日志的 shell，交回后还在跑。

**怎样核对：**起长任务前读名额的锁文件，方法见[运行名额](../../scripts/README.md#运行名额)。长任务的日志开头记下工作进程数及其来历。写者交回后，核对它没有留下仍在运行的进程。

## 证据日志与脚本

### P13 证据日志记录所跑代码的提交号

**规则：**每份证据日志都记录所跑代码的提交号和工作树是否有未提交改动。有基线与候选对比时，两边的提交号都记录。

**为什么：**没有提交号的日志无法判断它证明的是哪一个候选。候选前进后，旧日志不能无条件沿用。

**反例形状：**一份“变异全部杀死”的日志没有记录提交号。之后候选又提交了几次修复，没人能说清这份日志对应哪一次。

**怎样核对：**日志开头有 `git rev-parse HEAD` 的完整输出与 `git status --porcelain` 的行数。对比类证据有“基线”和“候选”两个提交号。下面是一种通用的日志头：

```sh
log="tmp/<任务>/<检查名>-$(date +%Y%m%dT%H%M%S).log"
{
  echo "cmd: <命令>"
  echo "head: $(git rev-parse HEAD)"
  echo "dirty: $(git status --porcelain | wc -l)"
  echo "start: $(date -Iseconds)"
} > "$log"
```

### P14 证据脚本每一步都核对成功

**规则：**多步证据脚本的每一步都核对成功。任何一步失败，脚本立即停下并以非 0 退出。

**为什么：**中间一步静默失败后，后面的步骤在错误的状态上运行，最后的结论没有意义。

**反例形状：**负控脚本先用 `git revert -q` 撤销修复，再跑测试，期望测试失败。`git revert` 因冲突失败，但脚本继续执行。测试在未撤销的代码上通过，脚本把它记成“负控无效”或“通过”。

**怎样核对：**

- Bash 脚本开头有 `set -euo pipefail`，或者每一步后都检查 `$?`。
- 改变状态的步骤之后，读回状态。例如撤销之后，用 `git diff --stat` 确认目标文件确实变化。
- 日志中每一步都有退出码，最后的退出码等于第一个失败步骤的退出码。

## 子检查点

### P15 子检查点沿用父项材料，并按风险裁剪

**规则：**

- 子检查点不重做上下文整理，沿用父项的上下文包，只补缺和变化。
- 机械的子项，例如发行或改钉子，由调度者自己做，不派子代理，也不做多面评审。
- 准入运行期间，预先写好下一次的派发、简报和卡正文。
- 同一份证据只在最终 head 上跑一次。
- 评审力度按风险选择。中等的工具修复用一次合并评审。多面评审留给契约成员或跨成员的改动。

**为什么：**子检查点的范围小。重复整理上下文、派子代理和多面评审，花费的时间比改动本身多，也不增加信息。

**反例形状：**一次只改一个版本钉子的子检查点，又派了便宜档整理全套上下文，派了开发者子代理改一行，再并行派了多面评审。同一份变异证据在几个中间 head 上各跑了一次。

**怎样核对：**

- 子检查点的上下文地图引用父项材料，只写差额。
- 机械子项的提交来源是调度者本人，没有对应的子代理派发。
- 重型证据日志的提交号等于最终 head（见 [P13](#p13-证据日志记录所跑代码的提交号)）。
- 评审派发数量与风险级别对应。级别定义见[按风险选择接受实现的看法](../../docs/engineering/quality.md#按风险选择接受实现的看法)。

## 子代理与角色

### P16 子代理写不了报告文件时内联交回

**规则：**

- 子代理不能写报告文件时，调度者要求它在回复中内联交回完整报告，由调度者保存到证据目录。
- 报告的字段要求不因内联而放宽。例如独立验收报告缺少提交号、运行号、退出码或验证者中的任何一项时，不能判 Pass。

**为什么：**子代理的写权限因宿主而不同。有的宿主上验收子代理写不了报告文件，报告只存在于一次回复中，之后无法复查。

**反例形状：**验收子代理写报告文件失败，最后只交回一句“验收通过”。证据目录里没有报告，判决无法核对。

**怎样核对：**

- 证据目录中有完整的报告文件。文件由调度者保存时，写明它来自子代理的内联回复。
- 报告含有角色要求的全部字段。验收报告的字段要求见 [qa 角色](../agents/roles/qa/role.md)。

### P17 改动带宿主资格摘要的角色提示，要在该宿主上重新取得资格

**规则：**

- 有的角色提示由宿主资格记录中的摘要绑定，例如 Cursor 资格记录中的 SHA-256。改动这样的提示，会使该宿主上的资格证明失效。
- 改动之后，要在该宿主上重新取得资格。没有新的证明时，不更新摘要。
- 需要给这类角色增加的约束，优先放在调度者一侧：写进简报、派发要求或本页规则，不改角色提示。

**为什么：**摘要证明的是“这份提示在该宿主上验证过”。只改摘要不重新验证，会把未验证的提示伪装成已验证。

**反例形状：**为了让验收角色“最后一次改动后重跑门禁”，直接改了角色提示，再把资格记录中的摘要改成新提示的摘要。资格记录显示 proved，但新提示从未在该宿主上运行过。

**怎样核对：**

- 角色提示的 diff 旁边，有对应宿主的新资格证明。只有摘要变化、没有证明时，不接受。
- 资格门禁的规则见 [Cursor 原生角色与资格](../agents/skills/design-subagents/canonical/references/cursor.md#生成前的角色资格门禁)。

### P18 子代理中途停下时按现场接续

**规则：**子代理中途停下、没有交回时，先读它留在工作树里的现场，再派一个新的子代理接着做。接续简报包括原简报、已有改动清单、剩下的失败与调度者的推断。操作顺序见[卡的推进循环](../agents/skills/claim/canonical/references/card-loop.md#角色与模型)。

**为什么：**宿主可能因限流（例如 429）让子代理中途停下。这时子代理没有交回报告，但工作树里通常留着它未提交的改动和日志。当作它什么都没做，会重复工作；直接丢掉改动，会丢掉有效的成果。

**反例形状：**子代理撞上限流，中途停下，没有交回报告。调度者按原简报重派，新的子代理重做已经完成的部分；或者调度者清掉工作树重来，已经完成的改动丢失。

**怎样核对：**

- 重派之前，进度记录中有 `git status`、`git diff --stat` 与子代理日志的摘要，以及对它做到哪一步的判断。
- 接续简报列出已有改动和剩余工作。重派时换了模型，进度记录写明这次偏离。

## Reduce：决定、派发与收口

### P19 已采用的决定由 Reduce 安排写回

**规则：**按[提问前三问](../../docs/engineering/map-reduce-states.md#提问前三问)第 3 问的核对项处理待决事项。已经采用、只差写回的决定，不作为问题交给人。

**为什么：**Reduce 的职责是让里程碑不被阻塞。把已经定过的事交还给人，会让人成为调度瓶颈，依赖它的卡也会停下等待。

**反例形状：**

- 一组早已采用的决定一直没有写回。Reduce 把其中几项写成「范围待负责人裁定」，依赖它们的卡交回 blocked，接受也被卡住。
- 一张产品选择问题卡写着「这些能力都只是候选」，实际上负责人已经在另一张卡上定了全部执行。问题的前提错了，后续正文要返工。

**怎样核对：**

- 每个交给人的问题都写明三问为何没有消除它。
- 问题卡引用了查过的卡评论与规格决定链接。

### P20 写范围按被删形状的全仓命中来定

**规则：**卡要删除或改名一个形状时，Reduce 先在全仓搜索这个形状的全部命中，再定写范围。写范围不只按类型检查或编译的失败清单来定。操作顺序见 `dispatch` 技能第 5 节。

**为什么：**编译只报告代码里的引用。成员规格、契约正文和说明页里的同名描述不会让编译失败，却同样要随形状一起改。写范围漏掉它们，执行者要么越界，要么交回不完整的结果。

**反例形状：**一次新 attempt 只按类型检查的失败清单，列了适配器成员的源码与测试。登记之后才发现，契约成员的多处正文还写着被删的事件，只好立即再登记一个 attempt。

**怎样核对：**登记 attempt 前的检查记录中，有对被删形状的全仓搜索命令与命中清单。清单中的每个命中或被写范围覆盖，或写明不改的理由（例如历史记录），或已回到分解。派发命令见[派发命令](../../tools/dev-flow/src/delivery/README.md#派发命令)。

### P21 接管超出写范围时，先换 attempt 再换树

**规则：**Reduce 接管一张卡，而需要的写范围超出该卡的 binding 时，先为这张卡登记新 attempt，再换一棵新树并读回。操作顺序见 `integrate` 技能「blocked 或 failed：redo 或接管」。

**为什么：**准入的 change-scope 只按 binding 判断写范围。接管时授权了更大的范围，但没有写进 binding，超出的改动照样被拒绝。在旧树上再运行 `start` 会报这棵树已经绑定了另一个任务。

**反例形状：**接管时授权了更大的写范围，但没有登记新 attempt。全量准入的 change-scope 仍按旧 binding 拒绝了超出范围的改动。

**怎样核对：**

- 新树中 `integration/cli.ts status` 的 attempt 等于新 attempt，`relation` 为 `current`。
- 候选的改动都在新 binding 的写范围内。处置规则见[遇阻交回与处置](../../docs/engineering/map-reduce-states.md#41-遇阻交回与处置)。

### P22 收口前请联调轨道上的其他写者暂停合入

**规则：**联调轨道上还有本里程碑以外的写者时，Reduce 在开始整波检查之前，请对方暂停往联调轨道合入。放行之后通知对方恢复。操作顺序见 `integrate` 技能「收口一波」第 1 步。

**为什么：**整波检查的对象是联调轨道头。检查之后别的会话又合入了 PR，候选就变了，旧证据失效，收口要回到监督重新检查。

**反例形状：**放行窗口中，另一条独立推进的工具线照样往联调轨道合 PR。每合入一次，Reduce 就要换收口点，重做整波检查，并重发线包修订与全线 delta。

**怎样核对：**

- 协调卡上有暂停请求与恢复通知，暂停请求早于整波检查。
- 放行前读回的联调轨道头仍等于 F，即整波检查之后、放行之前没有新的合入。轨道单写的规则见 [Reduce 状态空间](../../docs/engineering/map-reduce-states.md#3-reduce-状态空间)。

### P23 审计带出的新问题另立小卡

**规则：**评审或审计带出的新问题不属于当前卡的范围时，不把它并进正在推进的卡或正在集成的批次。先查有没有同一结果的卡，没有就另立小卡，在单独的分支上并行交付。

**为什么：**并进主线卡会让候选变大，评审、准入与修复都随之变慢。小卡可以独立验证与接受，主线卡也不必等它。

**反例形状：**一张主线卡收进了两个审计项。候选随之膨胀，评审与准入反复，交付明显拖延。

**怎样核对：**主线卡的候选只包含本卡判据要求的改动。审计项各有自己的卡与分支，并引用来源。建卡与查重规则见[整理需求并定位已有卡](../../docs/engineering/agent-delivery.md#1-整理需求并定位已有卡)。

### P24 非交付决定的评论不写「决定」列表字段

**规则：**按[接受、取消与重开](../../docs/engineering/delivery.md#4-接受取消与重开)，只有交付决定的评论写「决定」列表字段。范围裁定、接管说明等评论需要字段时换一个字段名，例如「裁定」。

**为什么：**读卡逻辑把写了「决定」列表字段的评论读成交付决定。种类不合法时，这张卡带上偏离，对这张卡运行的派发命令与 `start` 都会拒绝。

**反例形状：**一条范围裁定评论用「决定」作列表字段名（#793）。之后对这张卡运行派发命令时报 `decision-kind-invalid`。

**怎样核对：**发评论前检查正文中没有字段名为「决定」的列表行，包括前面有空白的行，除非这条评论就是交付决定。

### P25 看似未决的实现，先从产品正文往下核对

**规则：**认为某个实现还没有定、需要人拍板时，先按[提问前三问](../../docs/engineering/map-reduce-states.md#提问前三问)第 3 问的「自上而下核对」，从产品正文往下逐层确认它确实没有设计过。经过三问仍要人决定的，才向人提出，并写明核对过哪几层。

**为什么：**只看成员规格或实现，容易把上层已经定下的事当成未决。问题卡交到人手里，人要做一次本可以省掉的判断，依赖它的工作也停下来等。

**反例形状：**调度者只读了成员规格，发现其中没有写某个行为，就把它判为未决，发问题卡请负责人拍板。答案其实写在产品正文或架构里。

**怎样核对：**每个交给人的未决项都列出已核对的层：项目要求与产品正文、架构、领域、成员规格，以及相关卡评论中的具名决定，并说明每层为什么没有答案。

### P26 裁定更正后检索在途草稿

**规则：**人在波中更正一条裁定后，Reduce 在更正之前写成、还没有合入的草稿中检索被更正的说法，逐处改正，并在这些草稿的最终评审里加一项「与更正一致」。

**为什么：**更正只约束以后的写作。已经写好的草稿仍带着旧说法，评审不知道有这次更正，就不会查。

**反例形状：**一份修订草稿在更正之后仍写着更正之前的说法，直到合入前才被发现。

**怎样核对：**记下每条更正中旧说法的关键词。合入每份在途草稿之前，在它的分支上检索这些关键词，结果为空，或每处都有理由。

### P27 报 ETA 前先给串行等待分类

**规则：**Reduce 报 ETA 或说「只能串行」之前，逐段检查关键路径上的串行等待：它是真依赖（同一批文件或类型），还是习惯。是习惯的，先去掉再报。是真依赖的，先按争用的文件切开，方法见 [波段编排的判断方法](../agents/skills/dispatch/canonical/references/wave-planning.md)。

**为什么：**习惯性的等待看起来像依赖，会把 ETA 拉长数小时。

**反例形状：**M1.5 收尾时，Reduce 首次报的 ETA 是 21 小时，逐条分类后省回约 7 小时。其中的习惯有：修复轮等一个只出报告的差分变异跑完；gate 合入后又在 F 上跑一次整波检查，而 F 的树与已通过这项检查的 PR head 相同。

**怎样核对：**ETA 中每段串行等待都写出它依赖的文件或类型。写不出的，按习惯再查一遍。

## 维护本页

- 新的复盘发现一类重复出现的失误时，在相应的组下增加一条规则，编号接续。
- 规则已经由检查或钩子强制执行时，在“怎样核对”中写明该检查，保留规则。
- 拥有者正文改变后，修改对应规则，或者删除已经被拥有者完整覆盖的规则。
