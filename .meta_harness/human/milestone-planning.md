# 以里程碑为终点倒排交付

本页的读者是规划一个里程碑、并与 agent 一起推进它的人类协作者。
它讲怎样从里程碑的结束标志往回排：先定检查点，再切卡、排依赖、前置风险，最后定节奏。目标是在一个里程碑里交付得快，风险点少，质量有保证。

本页是学习材料，不是项目规则，也不是工具链的一部分。它借用敏捷开发与精益开发的成熟做法，解释它们在本项目里怎样落地。
里程碑、交付线、契约基线与轨道的规则由[多层分支集成](../../docs/engineering/integration.md#交付线)拥有。卡、阶段、属性与条件由[交付协议](../../docs/engineering/delivery.md#2-卡片与阶段)拥有。建卡和派发的操作由[通过对话操作交付卡](../../docs/engineering/agent-delivery.md)拥有。两者不一致时以拥有者正文为准。
契约怎样设计才能在里程碑内保持稳定，见[设计在里程碑内保持稳定的契约](stable-contracts.md)。本页不重复那部分方法。

## 先认清瓶颈：稀缺的是人的时间

与 agent 协作时，写代码和写文档的产能很高，并且可以并行。真正限制交付速度的通常是下面几样：

- **人的决定。**具名决定、取舍和产品规则只能由负责人给出。一个决定没有给出，依赖它的卡全部停下。
- **人的评审与接受。**agent 的评审给出发现，但接受归具名负责人。评审队列变长时，已完成的卡在队列里等待，交付并没有更快。
- **共享的写对象。**锁文件、根 `package.json`、registry、契约成员这类对象只能单写，见[责任与协作交接](../../docs/engineering/workflow.md#责任与协作交接)。改它们的卡只能串行。
- **集成与确认。**进入轨道要经过 gate，有的还要人确认。轨道前进后，其他分支要同步。
- **共享资源。**检查名额、CI 与付费模型预算都有限。

所以排期的单位不是「agent 要做多少小时」，而是「人要在什么时候做哪些决定和评审」，以及「哪些卡能在不共享写对象的前提下并行」。
这是约束理论（Goldratt）的基本观点：整体产出由瓶颈决定，提高非瓶颈环节的产能不会让交付变快，只会让等待变长。

Little 定律给出一个直接的推论：平均交付时长等于在制品数量除以单位时间的完成数量。
如果负责人一天只能接受五张卡，同时让二十个 agent 开工，平均每张卡就要在队列里等四天。限制在制品数量，比增加 agent 更能缩短交付时长。

## 一个里程碑的骨架

先定检查点，再填工作。检查点从结束标志开始往回排。

```mermaid
flowchart RL
  E["结束标志<br/>联调轨道上联合验收通过"] --> S["稳定窗口<br/>只修缺陷，不加范围"]
  S --> F["范围截止<br/>线内的卡已提升到联调轨道"]
  F --> W["行走骨架跑通<br/>每个契约在联调轨道上被真实调用一次"]
  W --> B["契约基线登记<br/>基线卡登记之后再派发其他卡"]
  B --> G["里程碑开始<br/>目标、范围、结束标志与风险清单"]
```

图中箭头从后一个检查点指向它依赖的前一个检查点，读法是「要达到左边，先要有右边」。

| 检查点 | 必须成立的事实 | 由谁判断 | agent 做什么 |
| --- | --- | --- | --- |
| 里程碑开始 | Milestone 已建，描述写明范围与结束标志；风险清单有初稿 | 负责人 | 起草验收场景、范围外清单与风险清单 |
| 契约基线登记 | 各接缝的契约经过评审；基线卡在评审后登记基线提交与契约成员 | 负责人；评审派 design-reviewer | 按接缝设计契约，跑联合回顾，整理决定批 |
| 行走骨架跑通 | 最薄的真实装配在联调轨道上端到端跑通，每个跨线契约至少被真实调用一次 | 集成 owner | 实现骨架所需的最小路径；暴露缺失的语义 |
| 范围截止 | 计划内的线内的卡都已提升到联调轨道，或者被明确移出本里程碑 | 各线 owner 与负责人 | 完成卡、提交候选、补证据 |
| 稳定窗口 | 只合入缺陷修复与验收所需的改动 | 负责人 | 修缺陷，跑联合验收，汇总证据 |
| 结束标志 | Milestone 描述里的结束标志成立 | 负责人 | 整理验收证据与回看材料 |

契约基线与里程碑内的规则见[里程碑与契约基线](../../docs/engineering/integration.md#里程碑与契约基线)。

## 第一步：把目标写成可验收的结束标志

里程碑的目标要能在联调轨道上被观察到。只写「完成 Session 设计」这类说法，到里程碑末尾无法判断是否完成。

1. 写一句结束标志，说明在哪条轨道上、用什么证据判断完成。
2. 为结束标志写三到八个验收场景，句式为「给定……当……则……」。每个场景说明一个可观察的系统行为。
3. 写范围外清单：本里程碑明确不做的事。范围外清单和范围一样重要，它防止 agent 顺手扩大范围。
4. 把验收场景交给后面的步骤使用：它们决定行走骨架走哪条路径，也是联合验收的用例。

可以让 agent 从产品正文和需求起草场景，再由你确认。不要让 agent 自己决定范围外清单，范围取舍归负责人。

## 第二步：按接缝与交付线切卡

### 切卡的原则

- **一张卡是一个可以独立接受的结果。**卡的结果要能被具名的人判断「接受」或「不接受」。
- **按结果纵向切，不按技术层横向切。**「实现存储层」「实现接口层」这类卡完成后仍不能演示任何行为。优先切成「某个场景在某条线上可以运行」。
- **契约先行的部分单独成卡。**跨线的接缝先由联调轨道上的卡定契约，线内的卡在契约下实现。性质与合法组合见[卡属性与合法组合](../../docs/engineering/delivery.md#卡属性与合法组合)。
- **卡的大小以一次 agent 会话能完成、一次评审能看完为准。**规则里还有一条与轨道有关：预计半天以上的卡直接进入目标轨道，见[卡进入哪条轨道](../../docs/engineering/integration.md#卡进入哪条轨道)。

### 让卡在开工前就「就绪」

agent 不能安全地补全缺失的输入。缺了输入，它会猜，猜的结果看起来很确定。所以卡进入 Ready 之前，下面几项都要齐：

- 范围、范围外与接受者。
- 现行依据：哪一份正文、哪个提交。
- 验收判据与需要的证据。
- 交付条件：开工前必须成立的前置结果。
- 写范围：只写哪些路径。

Ready 的含义见[卡片与阶段](../../docs/engineering/delivery.md#2-卡片与阶段)。Ready 不是永久许可，开工前要再读回一次。

### 用条件表达依赖

依赖写进卡的交付条件，不写在 Priority 或口头约定里。规则见[条件、关系与解锁](../../docs/engineering/delivery.md#3-条件关系与解锁)。

- 线内的依赖：引用本线的卡。
- 跨线的依赖：不引用其他线的卡，写一条 `capability` 条件，目标是一个契约形状。见[跨线依赖](../../docs/engineering/integration.md#跨线依赖)。
- 跨线的真实装配与联合验收：放在联调轨道上的 `integration` 卡里。

这样做以后，跨线的阻塞点只出现在联调轨道上。排期时只需要盯住联调轨道上的少数几张卡。

## 第三步：找出关键路径，再倒排

### 画依赖图

把全部卡和它们的交付条件画成一张图。图上从「里程碑开始」到「结束标志」最长的一条链就是关键路径。
在本项目里，关键路径通常经过这几处：契约基线、承接跨线装配的 `integration` 卡、行走骨架、联合验收。

可以让 agent 从卡的条件表生成这张图，并标出每条链的长度。图上要同时标出人的步骤：每一次具名决定、每一次接受、每一次 gate 确认。它们也在关键路径上。

### 往回排

从结束标志的日期往回排每个检查点：

1. 先放稳定窗口。它是整个里程碑的缓冲，不是可以挪用的空闲时间。
2. 再放范围截止、行走骨架与契约基线。
3. 最后把各条线的卡排进检查点之间的空档，关键路径上的卡先排。

缓冲集中放，不分散到每张卡上。关键链方法（Goldratt）的做法是：每张卡按不加余量的估计排，把省下来的余量合成一个放在末尾的项目缓冲；非关键链汇入关键链的地方再放一个汇入缓冲。
分散的余量会被各张卡悄悄用掉。集中的缓冲可以被看见，也可以被管理。

### 排人的时间

把人的步骤当作资源排进日程：

- **决定批。**把需要负责人拍板的事攒成一批，固定时间集中交给负责人，例如每天一次。每一项都带上选项与推荐，负责人可以只回「按建议」。
- **评审窗口。**估算每天能接受的卡数，按它限制同时开工的卡数。
- **确认窗口。**gate 的确认也排进日程，不让已经通过检查的候选长时间等待。

### 限制在制品

- 每条线同时进行的写者不多于该线 owner 能及时评审的数量。
- 改同一个共享写对象的卡串行，不要让它们并行再在合并时解决冲突。
- 只读的调查与评审可以大量并行，它们不争写对象，只消耗模型预算。

## 第四步：把风险前置

### 开始时列出风险

在里程碑开始时列一张风险清单，每项写明：风险是什么，最早在什么时候能暴露，谁处理。常见的几类如下：

| 风险 | 典型表现 | 前置的做法 |
| --- | --- | --- |
| 契约语义缺口 | 联调时才发现失败、顺序或所有权没有定义 | 基线前做一次跨域的联合回顾；早跑行走骨架 |
| 技术未知 | 不确定一个库或上游机制能否满足要求 | 开一张限时的调查卡，先回答问题再排实现 |
| 外部依赖 | 等上游版本、等别的线的契约 | 用 `capability` 条件表达，提前约定形状，按替身开发 |
| 环境缺口 | 云端镜像没有某种数据库或形式工具 | 开工前确认验证环境；缺失时把「未执行」写进证据 |
| 人的时间 | 负责人这几天没有空做决定 | 提前排决定批，把决定往前移 |

### 先做风险最高的部分

- 行走骨架尽量早。它用最薄的真实实现把系统连起来，缺失的语义会在早期暴露，而不是在里程碑末尾集中出现。
- 调查卡排在依赖它的实现卡之前，并且有时间上限。时间到了还没有答案时，把问题交负责人决定，而不是继续调查。
- 不可逆的决定早做，可逆的决定在最后负责时刻做。契约基线上的形状是本里程碑内最难撤回的决定，要在基线登记之前想清楚。实现细节可以晚定。

### 范围与时间冲突时砍范围

里程碑的结束时间和质量门槛不动，范围可以动。时间不够时按下面的顺序处理：

1. 把未开工、不在关键路径上的卡移出本里程碑。
2. 把一张卡缩小成可以独立接受的一部分，剩下的另建卡。
3. 上面两项都不够时，交负责人决定是否推迟结束标志。

不要用降低验证或跳过评审来换时间。被跳过的检查不会消失，它们会变成下一个里程碑的缺陷。

## 第五步：定节奏

### 同步与提升

同步与提升以事件触发为主，见[同步与提升的节奏](../../docs/engineering/integration.md#同步与提升的节奏)与[线轨道的同步与提升](../../docs/engineering/integration.md#线轨道的同步与提升)。从排期的角度看，要点有两个：

- **小批量、勤提升。**一条线攒了很多卡再提升，联调轨道上的问题会集中出现，也更难判断是哪张卡引入的。
- **破坏性改动集中安排。**里程碑内线内的卡只做可加改动。破坏性改动由联调轨道上的 `integration` 卡一次完成，完成后在基线卡上补登记新基线。排期时把这类卡当作关键路径上的事件处理，提前通知受影响的线。

### 检查点会议

在每个检查点，以及检查点之间按固定间隔，对照倒排的日程看一次实际进度：

1. 关键路径上的卡比计划快还是慢。
2. 缓冲用掉了多少。缓冲用掉的比例明显超过关键路径完成的比例时，要采取行动：砍范围、增加并行，或者提前交负责人决定。
3. 决定批、评审队列和 gate 确认有没有积压。
4. 联调轨道上能演示什么。演示比报告可靠。

可以让 agent 准备这份对照：从卡的 Stage、条件和合入记录生成进度表，标出偏离和积压。判断和取舍仍由人做。

Project 的 Iteration 字段只在负责人采用了迭代节奏之后使用，见[建卡或修订卡](../../docs/engineering/agent-delivery.md#2-建卡或修订卡)。没有采用时，用 Milestone 与检查点安排日程就够了。

## 质量怎样保证

质量在每张卡里形成，不在里程碑末尾集中检验。

- **每张卡带着证据交付。**验收判据要求的证据随候选一起交回。验证的轻重按成果与风险选择，见[按成果和风险验证](../../docs/engineering/quality.md#按成果和风险验证)。
- **评审按对象分工。**代码、文档、交付边界与设计各有评审方式，见[评审分工](../agents/roles/README.md#按判断对象选择-reviewer)。评审给出发现，接受归具名负责人。
- **进轨道的 PR 说清两件事。**它包含哪些卡，以及契约有没有变化。见[进轨道 PR 的说明](../../docs/engineering/integration.md#进轨道-pr-的说明)。
- **联调轨道持续可用。**每次提升之后，联调轨道上的检查与行走骨架都要通过。联调轨道长时间是红的，就没有地方判断各条线的结果能不能组合。
- **联合验收用第一步写的场景。**场景在里程碑开始时就写好，结束时不再临时决定「怎样算完成」。

## 人与 agent 怎样分工

| 工作 | 人做什么 | agent 做什么 |
| --- | --- | --- |
| 目标与结束标志 | 定目标、结束标志与范围外清单 | 从产品正文起草验收场景 |
| 契约设计 | 确认消费者场景，拍板取舍，接受基线 | 按接缝设计契约，跑联合回顾，整理决定批 |
| 切卡 | 确认范围、属性与接受者 | 起草卡正文、条件表与写范围 |
| 排期 | 定优先级与取舍，接受倒排的日程 | 从条件表算依赖图和关键路径，标出人的步骤 |
| 实施 | 回答决定批，处理阻塞 | 在隔离的工作树里实现，形成候选和证据 |
| 评审与接受 | 看评审发现，作出接受决定 | 按评审分工给出发现 |
| 跟踪 | 判断偏离，决定砍范围或调整 | 生成进度对照，标出积压与风险变化 |
| 回看 | 决定下一个里程碑要改的做法 | 汇总偏离的原因与数据 |

## 怎样指导 agent 做倒排

### 给 agent 的输入

- Milestone 的描述：范围、结束标志与范围外清单。
- 现有的卡，以及它们的属性和条件表。
- 每条线的 owner，以及负责人每天能用于决定和评审的大致时间。
- 已知的共享写对象和在途的卡。

### 要求 agent 产出的内容

1. 检查点日程：每个检查点的日期，以及它必须成立的事实。
2. 依赖图与关键路径，人的步骤单独标出。
3. 每条线按检查点倒排的卡顺序。
4. 在制品上限：每条线同时进行的写者数量，以及理由。
5. 风险清单：每项的最早暴露时间与处理方法。
6. 需要负责人决定的事项清单，每项带选项与推荐。

### 评审 agent 产出时问的问题

1. 结束标志能在联调轨道上被观察到吗？
2. 关键路径上有没有人的步骤？它们排进日程了吗？
3. 有没有两张并行的卡写同一个共享写对象？
4. 缓冲是集中放的，还是摊在每张卡上？
5. 行走骨架排在什么时候？它之前要完成的卡是不是最少？
6. 风险最高的卡排在前面了吗？调查卡有时间上限吗？
7. 每张卡进入 Ready 时输入齐全吗？
8. 时间不够时，先砍哪些卡？

### agent 常见的偏差

- 按 agent 的工作时长排期，忽略决定、评审与确认的等待。
- 让所有线同时开工，在制品远超评审能力。
- 按技术层切卡，到里程碑末尾才能演示行为。
- 给每张卡加余量，没有集中的缓冲。
- 漏掉经共享文件形成的隐性依赖，例如锁文件与根脚本。
- 把行走骨架排到所有实现完成之后。
- 把 Priority 当作依赖，或者用口头约定代替交付条件。

看到这些偏差时，要求 agent 回到依赖图与人的时间重新说明，不要只改日期。

### 可以直接使用的指令模板

> 为里程碑〈名称〉做倒排计划。
> 结束标志：〈写明〉。范围：〈列出〉。范围外：〈列出〉。
> 负责人每天大约有〈小时数〉用于决定与评审。各线 owner：〈列出〉。在途的卡与共享写对象：〈列出〉。
> 先列出检查点与每个检查点必须成立的事实，交我确认。
> 确认后，从现有卡的条件表画依赖图，标出关键路径和其中的人的步骤，按检查点倒排各线的卡，给出每条线的在制品上限、集中的缓冲、风险清单，以及要我决定的事项与推荐。
> 不要按 agent 工时估算整体日期。估不准的地方列为假设，不要猜。

## 结束之后：回看

里程碑结束后做一次回看，只回答下面几个问题：

1. 每个检查点实际在哪一天达到，和计划差多少。
2. 延误主要来自哪一类：等决定、等评审、等确认、契约变化、环境缺口，还是估算偏差。
3. 缓冲用在了哪里。
4. 契约改动的原因按[六类原因](stable-contracts.md#契约为什么会在中途改变)归类。

下一个里程碑先处理最常出现的那一类延误。可以让 agent 从卡的时间线和合入记录汇总数据，结论由人来下。
