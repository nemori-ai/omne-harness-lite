# 一个检查点的内层循环

**状态：流程草稿。**本页不是 skill，agent 不自动加载它。人可以按本页调度，也可以把本页作为指令交给调度 agent。

- 已验证的场景：一条交付线上的多个连续检查点。条件是本地宿主、单会话串行调度、经 gate 直接进入轨道，多数卡是接续已有的 attempt。
- 没有验证的场景：云端宿主、多会话并行、子卡先进父卡分支的路线。
- 规则正文归各拥有者。本页只给顺序、产物、门槛和已知问题。本页与拥有者正文冲突时，以拥有者正文为准，并修改本页。

外层循环是一份检查点计划：按顺序推进检查点，一次只有一个检查点在内层循环中。
内层循环是一个检查点从定向到收尾的全过程。本页讲内层循环。

本页与相邻材料的关系：

- [开发卡从认领到开工前](claim-to-start.md)讲一张新卡怎样派发、认领和通过 `start`。本页的“派发”和“开工”两个阶段遇到新卡时，按那一页执行。
- [交付中的常见失误与防范规则](delivery-pitfalls.md)把复盘中的失误写成规则 P1 至 P17。本页在每个阶段列出适用的规则。

## 术语

| 词 | 本页的含义 |
| --- | --- |
| 检查点 | 外层计划中的一个交付步骤，结果可以单独入轨或发布。一张卡可以对应多个检查点 |
| 子检查点 | 从一个检查点分出的小步骤，例如发行一个工具版本，或修改一个版本钉子 |
| 调度者 | 主会话。负责编排、写简报、裁定、按授权接受和运行 gate |
| 写者 | 一次派发中唯一写工作树的执行者 |
| 功能门禁 | 迭代中的检查：类型检查、受影响成员的测试、lint、`check:docs` 等 |
| 准入 | 进入任何一条主干之前的完整检查，即 `OMNE_ADMISSION=1 pnpm run check` |
| gate | `github-gate` 上的发布流程，包括 `gate-publish` 与 `gate-release` |
| `<本卡材料>` | 工作树内的 `tmp/issue-<号>/`。该目录被 Git 忽略，不提交 |

## 角色与模型

模型分四档。具体模型名和档位钉值归[研发角色源包](../agents/roles/README.md#模型配置与本次派发)，本页不复述。
派发时显式传模型。需要时传推理档位。

| 承担 | 做什么 | 为什么 |
| --- | --- | --- |
| 调度者（主会话） | 编排、写规格与计划、写简报、裁定、按授权接受、gate 与发布、维护卡与看板、机械子项 | 这些工作需要全局上下文和授权。调度者不当常规写者 |
| 便宜档 | 搜集与提炼上下文、交接梳理、链接与锚点核对、看板与标签读回、消费者盘点 | 读多写少，按清单执行 |
| 经济档 | 机械写作：文档单点同步、测试补断言、索引、探针脚本、规格完整的单模块切片 | 规格完整时，质量与中档相当，成本更低 |
| 中档 | 能力与组合行为、具体提供者、契约成员与消费者迁移；代码评审、交付边界核对、文档评审；用较低推理档位转写已定的设计 | 项目默认档 |
| 顶档 | 内核原语与生命周期、并发与失败语义、安全敏感改动、精确算法、跨多个包的改动；机制不明时的根因定位；第三轮修复；结构诊断；设计评审中的“选择”与“计划” | 这些工作出错代价最高，或需要不同于前两轮的判断 |

几类角色的默认选择：

- 独立验收（`qa`）默认用经济档。结论直接卡住发布，或要驱动真实终端矩阵、多个服务时，用顶档。一次验收可能要几十分钟，不要压低推理档位。
- 修复轮用实施时的档位。实施用的是经济档时，修复升到中档。
- 档位拿不准时上调一档。顶档和多模型对抗类技能成本最高，使用前确认它能换来不同的判断。

派发规则：

- 一次只有一个写者，在本次工作树里写。只读评审、验收和上下文整理可以并行，但要遵守 [P12](delivery-pitfalls.md#p12-并行的只读工作不能干扰写者和准入)。
- 每次派发用新的子代理。把原简报、后续指示和上一轮报告合并进新简报。只读评审在同一轮内的追问可以复用原子代理。
- 简报只给指针，不内联大段上下文。简报写明检出、分支、写范围、必要输入、完成条件和停止条件。
- 子代理的结论是证据，不是接受。调度者读 diff，写自己的总结。

## 两种入口

| 入口 | 判断依据 | 准备阶段的差别 |

## 1 定向

**目标：**弄清这张卡要交付什么、依据在哪、现状到了哪一步、还缺什么，并把缺口变成可执行、可验收的方案。本阶段不改产品文件。

**承担：**便宜档搜集，调度者整理、核对并起草规格与计划。上下文包在卡第一次进入时整理一次。之后每个检查点只补缺和变化（[P15](delivery-pitfalls.md#p15-子检查点沿用父项材料并按风险裁剪)）。

步骤：

1. 读卡：正文、交付修订、交付条件、执行区，以及评论中的派发、start 事实、候选、报告和决定。
2. 核远端事实：轨道尖端、远端分支尖端、PR 状态与 head。与卡上的记录比较，不一致时先记录反例。
3. 核开工条件：交付条件中阶段为 `start` 的每一行都读回依据。再核本检查点在外层计划中的前置。任何一项不满足时，本检查点标为阻塞，回到外层计划排下一个可做的检查点。
4. 写 `<本卡材料>/context-map.md`：
   - 交付成果与卡判据，用白话讲一遍；
   - 依据清单，每条带链接和精确修订；
   - 现状：已有候选、已有证据、失败和未测量项、哪些旧证据仍然适用；
   - 缺口清单：要补的实现、验证、文档、发行与登记；
   - 受影响的成员和现有消费者；
   - 适用的研发品味与防御指导条目，逐条写编号；
   - 选中的方法 playbook 与执行角色；
   - 仍然未知的点。
5. 写 `<本卡材料>/spec.md`。接续卡只写已采用规格之外的差额。结构可以采用 Matt 的 `to-spec` 模板，按[技能引用与采用边界](../../docs/engineering/skills.md#matt-补充与候选)加载。规格中加两节：
   - **依据与已定事项：**每条依据带链接与精确修订。已采用的规格与决定直接引用。
   - **工程约束：**按下表逐项写“本卡适用的具体条目”。不适用的写“不适用，因为……”。
6. 写 `<本卡材料>/plan.md`。按纵向切片组织，开头放进度总览。每个切片写：端到端行为、阻塞关系、验收勾选项（对应卡判据）、文件、命令、依据、实施者档位，以及[切片循环](#4-实施)的七步待办与承担者。
7. 处理待决事项。先按“过度设计 → 调度者可以自己定 → 必须上报”筛一遍。只有产品规则、范围变化、新的破坏性契约变化和需要接受者本人做的动作才上报。其余由调度者具名裁定，写进“已定事项”，并在卡上留评论。裁定前重读卡的目标和规格条款（[P4](delivery-pitfalls.md#p4-评审可以质疑调度者的裁定)）。
8. 核对 `plan.md` 中的相对链接和锚点。`check:docs` 不检查被 Git 忽略的 `tmp/`，这一步要单独做。

规格中“工程约束”一节的条目来源：

| 小节 | 拥有者 |
| --- | --- |
| 研发品味 | [研发品味](../agents/roles/engineering-taste.md) |
| 演进政策与提交 | [演进与交付边界](../../docs/engineering/publication.md#当前演进与消费者)、[贡献指南](../../CONTRIBUTING.md#提交与-pr-表达) |
| 领域边界与依赖方向 | [依赖关系与禁止方向](../../docs/architecture/layers-and-dependencies.md#依赖关系与禁止方向)、[领域语义依赖与模型边界](../../docs/architecture/layers-and-dependencies.md#领域语义依赖与模型边界) |
| SOLID | [方法依据与采用范围](../../docs/architecture/layers-and-dependencies.md#方法依据与采用范围)、`review-code` skill |
| TypeScript 实践 | [pstack 方法入口](../../docs/engineering/skills.md#pstack-方法入口)。写范围含 `.ts` 时，实施者加载 `typescript-best-practices` |
| 防御指导 | [防御性研发模式](../../docs/defensive-patterns.md#当前指导) |
| 验证级别 | [按风险选择接受实现的看法](../../docs/engineering/quality.md#按风险选择接受实现的看法) |

**出口门槛：**

- [ ] 上下文地图齐全，缺口清单里每一项都有来源。
- [ ] `spec.md` 与 `plan.md` 齐全，每条卡判据都有对应的切片和验收命令。
- [ ] 待决事项已裁定或已上报，需要留档的决定已写到卡评论。
- [ ] 开工条件全部满足，或本检查点已标为阻塞并在外层计划登记。
- [ ] 没有上报项时直接进入下一阶段，不另外请示开工。

## 2 派发

**接续卡：**核对卡上现有的派发评论。派发评论没有被编辑过；binding 与派发的 task 逐字段一致；写范围和修订够用。不够用时，发新的派发，不编辑旧评论。

**新卡：**按[开发卡从认领到开工前](claim-to-start.md)第 1 至 4 节执行：派发前核对、正式派发、写卡正文、认卡评论。

**出口门槛：**

- [ ] 派发评论有完整的授权区块，`start` 条件的摘要与当前卡正文一致。
- [ ] 卡正文的 binding 与派发的 task 逐字段一致。
- [ ] 卡上有一条“接手与现状”评论：新卡写认卡，接续卡写核对结果。

## 3 开工

1. **一次 attempt 一棵工作树**，放在主检出的 `.worktrees/issue-<号>-<短名>`。task context 绑定“工作树 + 分支”。见[已知问题](#已知问题)中的工作树条目。
2. 准备环境：
   1. 安装依赖：`pnpm install --frozen-lockfile --prefer-offline`。
   2. 生成 agent 投影。新工作树、agent 源没有改动时，运行 `uv run --locked python .meta_harness/tooling/src/initialize_agents.py --project-root .`。改了 agent 源之后，这种写法会失败，按[改了 agent 源之后重新生成投影](#改了-agent-源之后重新生成投影)操作。
   3. 运行 `pnpm run check:agents`，退出码应为 0。没有投影时，后续检查会报缺少生成目录。
   4. 记录实际的 Node、pnpm 与 git 版本。
3. 运行 `start`，再运行 `status`：

   ```sh
   node --experimental-strip-types tools/dev-flow/src/integration/cli.ts execute --root "$PWD" --input <临时目录>/start.json
   node --experimental-strip-types tools/dev-flow/src/integration/cli.ts status
   ```

   `start.json` 的写法见[开发卡从认领到开工前](claim-to-start.md#8-start-与读回)。接续卡的 authority 用原派发评论。
4. `start` 失败时停下，按错误码（`unknown`、`refused`、`stale`、`input-error`）处理。不手写 task context。错误原因不明时，先按 [P6](delivery-pitfalls.md#p6-先便宜复现再怀疑环境) 便宜复现，再怀疑环境。

**出口门槛：**

- [ ] `status` 读到 `bound=true`，relation 为 `current` 或 `behind`，各字段与 binding 一致。
- [ ] 依赖已安装，`check:agents` 退出码为 0。
- [ ] 卡的 Project Stage 为 In progress，并已读回。

## 4 实施

**目标：**按 `plan.md` 逐个切片实施，直到全部卡判据都有证据。

**承担：**调度者调度。写者一次一个，在本次工作树里写。派发期间，调度者不在这条分支上提交。

每个切片按七步走：

1. 便宜档补本切片的上下文，只补差额。
2. 调度者写简报：卡与修订、分支、写范围、必要输入、适用的品味与防御条目、完成条件、停止条件。简报中的每条命令都要能在当前仓库运行（[P8](delivery-pitfalls.md#p8-简报和-skill-里的命令必须能运行)）。简报要求写者在最后一次改动之后重跑全部门禁，并报告每份日志的时间和所跑代码的提交号。最后一次改动之前的结果不算（[P1](delivery-pitfalls.md#p1-通过要有当场可查的产物)）。
3. 写者实施，交回改动、命令、退出码与未覆盖项。证据脚本每一步都核对成功（[P14](delivery-pitfalls.md#p14-证据脚本每一步都核对成功)）。
4. 调度者复跑功能门禁，核对写范围。见[5 验证](#5-验证)。
5. 评审：只有切片风险高时才在这里评审。常规评审集中到实施完成之后。见[6 评审](#6-评审)。
6. 有阻断时按[升级阶梯](#评审与修复的升级阶梯)修复。
7. 调度者提交并推送，更新 `plan.md` 的勾选和外层计划的进度。提交署名与 trailer 按贡献指南（[P5](delivery-pitfalls.md#p5-署名与-pr-格式只认贡献指南)）。

切片之间：

- 目标分支前进时，先用普通的 `git merge` 合入，再运行 `task-sync`。taskBase 不变。见[已知问题](#已知问题)中的 task-sync 条目。
- 发现范围、依据或规格冲突时，只暂停依赖它的切片，回到定向阶段裁定。
- 结构度量、差分变异和品味逐条核对，在若干切片完成后集中跑一次，不在每个切片跑。
- 卡上只在关键进展、阻塞和出现可审阅候选时更新事实，不逐次贴日志。

**出口门槛：**

- [ ] `plan.md` 中的切片全部勾选。
- [ ] 集中度量已跑，读数与处置已记录。工具不覆盖的范围写“未测量”，不写零。
- [ ] 候选已推送。PR 正文更新到固定的 head，并有“所含的卡”和“契约变化”两节。

## 5 验证

调度者在候选 head 上自己复跑功能门禁，至少包括类型检查和 lint。写者已经报告通过时也要复跑，不管写者是谁。

1. 按[按改动选择检查](../../docs/development.md#按改动选择检查)选命令。
2. 每份日志记录命令、HEAD 提交号、开始与结束时间和退出码（[P13](delivery-pitfalls.md#p13-证据日志记录所跑代码的提交号)）。
3. 后台运行时，把真实退出码传出来（[P1](delivery-pitfalls.md#p1-通过要有当场可查的产物)）。
4. 读工具输出的实际范围。工具没有覆盖本次改动时，写“未覆盖”和替代证据（[P2](delivery-pitfalls.md#p2-退出码为-0-不等于测过)）。

**出口门槛：**每份日志都晚于最后一次改动，退出码为 0，未覆盖范围已写明。

## 6 评审

评审按风险选择。级别定义与派发条件归[按风险选择接受实现的看法](../../docs/engineering/quality.md#按风险选择接受实现的看法)。

| 候选内容 | 派什么评审 |
| --- | --- |
| 含代码，风险为 L2，并有未交代的红项或接受者说不清的地方 | `review-code`（实现评审者，中档） |
| 含代码，风险为 L3 | `review-code`，逐行读热点 |
| 含正式文档 | `review-docs` |
| 任何候选，在接受之前 | `review-delivery`，逐条核对卡判据 |
| 有可运行的交付面，风险为 L2 或 L3 | `qa` |
| 契约成员或跨成员的改动 | 多面评审：上面适用的各项分别派发 |
| 中等的工具修复 | 一次合并评审，不分面派发 |

- 风险为 L0 时不派评审，L1 只在读数有未交代的红项时派。
- 纯文档的检查点用 `review-docs` 加 `review-delivery`。
- 给评审的简报不写“不要重新讨论裁定”（[P4](delivery-pitfalls.md#p4-评审可以质疑调度者的裁定)）。
- 只读评审只在本次工作树内搜索。做手工变异的评审在副本上改（[P12](delivery-pitfalls.md#p12-并行的只读工作不能干扰写者和准入)）。
- 评审之间可以并行，但不与准入同时运行。
- 子代理（例如某些宿主上的 `qa`）写不了报告文件时，要求它在回复中内联交回完整报告，由调度者保存到证据目录。报告缺少角色要求的字段时，不能判 Pass（[P16](delivery-pitfalls.md#p16-子代理写不了报告文件时内联交回)）。
- 想给评审或验收角色增加约束时，写进简报，不改带宿主资格摘要的角色提示（[P17](delivery-pitfalls.md#p17-改动带宿主资格摘要的角色提示要在该宿主上重新取得资格)）。

**出口门槛：**每条阻断发现都有处置：接受并修复、记下理由后驳回，或按阶梯升级。

## 7 修复

1. 把全部阻断合成一轮集中修复，不逐条派发。
2. 修复后复跑受影响的功能门禁。
3. 只复评被点名的项。
4. 记录本轮的修订、阻断发现、类别、处置和验证。轮次连同接手前的一起数（[P3](delivery-pitfalls.md#p3-同类阻断重复出现时整类处理)）。

不收敛时按下节的阶梯升级。

## 评审与修复的升级阶梯

轮次的计算方法与升级顺序归[三轮未收敛时升级结构诊断](../../docs/engineering/quality.md#三轮未收敛时升级结构诊断)。下面是它在内层循环中的操作顺序。

| 轮 | 修复方 | 前置动作 |
| --- | --- | --- |
| 第 1、2 轮 | 实施时的档位。实施用经济档时，升到中档 | 无 |
| 第 3 轮 | 顶档，或调度者亲自修 | 先逐条质疑评审判定：判得对吗，合理吗，本阶段必须闭合吗。站不住的发现记下理由，不计入未收敛 |
| 仍不收敛 | 停止局部修补 | 冻结当前修订和三轮记录，做结构诊断。可以请只读的顶档顾问给出根因、影响范围、应保留内容和修复路径 |

两条补充：

- 第二轮的阻断与第一轮同类时，第三轮不再逐个补洞，而是整类处理：缩小承诺、让这一类走保守结论、同步改窄评审标准，再做一次增量复审。缩小承诺要经接受者批准。见 [P3](delivery-pitfalls.md#p3-同类阻断重复出现时整类处理)。
- 更换评审者、分支或拆分补丁都不重置轮次。

## 8 准入

**准入在最终 head 上跑一次。**

1. 固定候选：记录 head、taskBase 和 targetBase。目标分支在此之后前进时，先合入并运行 `task-sync`，再按影响重验。
2. 运行准入：`OMNE_ADMISSION=1 pnpm run check`。卡要求时加 `FULL=1`。用[日志头](delivery-pitfalls.md#p13-证据日志记录所跑代码的提交号)记录 head，并传出真实退出码。
3. 准入运行期间：
   - 不在被检工作树或分支上提交（[P11](delivery-pitfalls.md#p11-准入运行期间不提交)）；
   - 不派重型评审，不做占 CPU 的实验（[P12](delivery-pitfalls.md#p12-并行的只读工作不能干扰写者和准入)）；
   - 在 `tmp/` 下预先写好 gate 确认说明、接受评论、卡正文更新和下一次派发。
4. 准入失败时，先定向复现，不反复全量重跑碰运气。复现用与准入相同的调用方式，见[已知问题](#已知问题)。修复后在新的最终 head 上再跑一次准入。

**出口门槛：**准入退出码为 0。日志中的 head 等于当前的 `git rev-parse HEAD`。

## 准入与评审的节奏

一个检查点的检查按下面的顺序排，使每份重型证据只在最终 head 上跑一次。

```mermaid
flowchart LR
  A["切片实施"] --> V["调度者复跑功能门禁"]
  V --> R["按风险评审（只读，可互相并行）"]
  R --> F["集中修复一轮"]
  F --> V2["复跑受影响的功能门禁"]
  V2 --> AD["最终 head 上的准入"]
  AD --> G["gate"]
```

- 先复跑功能门禁，再派评审。这样类型错误等便宜的问题不会等到准入才暴露。
- 评审不与准入同时运行。两者都占用 CPU 和磁盘，并且准入期间不能提交。
- 没有评审发现时，直接在被评审的 head 上运行准入。
- 准入期间做只读、不占资源的准备工作，例如写确认说明和下一次的简报。

## 9 gate

1. 集成：派发 `gate-publish`。改到仓库工具链路径时，先确认 `repo-toolchain-review`，再确认 `publish`。
2. npm 发行：先查 registry 上的版本，确认版本号已随工具 PR 入轨（[P9](delivery-pitfalls.md#p9-工具版本号随工具改动一起入轨)）。再派发 `gate-release`，确认 `npm-release`，读回 integrity 与来源证明。
3. 确认说明写明本地检查的实际命令与结果、已核对的卡上条件。调度者代接受者确认时，写明授权依据。
4. 新版本的行为取决于仓库状态时，改变仓库状态的 PR 通过准入之前，不把发行算作完成（[P10](delivery-pitfalls.md#p10-钉住新版本不等于工具已经生效)）。
5. PR 标题和正文按贡献指南，不加作者式工具署名（[P5](delivery-pitfalls.md#p5-署名与-pr-格式只认贡献指南)）。

**出口门槛：**读回运行结论、目标分支等于结果、记录标签存在、PR 上有发布决定评论。

## 10 接受

在卡上写决定评论：对象、修订、范围、证据、保留的未测量项。

- 只接受本检查点的切片时，写成切片接受。
- 卡的全部判据都闭合之后，才写整卡的交付决定并关卡。卡与检查点的对应关系登记在外层计划中，按它判断是否该整卡接受。
- 写决定前重读卡判据，评审发现与调度者的裁定都要对照卡文（[P4](delivery-pitfalls.md#p4-评审可以质疑调度者的裁定)）。

**出口门槛：**决定评论存在，范围与实际入轨的内容一致。

## 11 收尾

1. [契约基线](../../docs/engineering/integration.md#里程碑与契约基线)登记：追加一条记录，写成员、旧比较基线、入轨结果、契约变化类别（无、可加或破坏性）及依据、是否前移基线、受影响的消费者与重验结果。
2. 卡：更新执行区与当前进展。整卡接受后关卡，把 Project Stage 改为 Accepted 并读回。
3. 外层计划：本检查点标为完成，追加运行号和结果，然后切到下一个检查点。
4. 清理 tmp：被引用的材料保留，其余归档或删除。工作树的清理条件见[工作树清理条件](../../docs/engineering/workflow.md#工作树清理条件)。

**出口门槛：**登记、卡、Project 和外层计划都已更新并读回。

## 子检查点的效率规则

子检查点范围小，不需要完整的十一个阶段。规则来源见 [P15](delivery-pitfalls.md#p15-子检查点沿用父项材料并按风险裁剪)。

- 不重做上下文整理。沿用父项的上下文包，只补缺和变化。
- 机械子项，例如发行、改钉子，由调度者自己做。不派子代理，不做多面评审。
- 准入运行期间，预先写好下一次的派发、简报和卡正文。
- 同一份证据只在最终 head 上跑一次。
- 评审力度按风险：中等的工具修复用一次合并评审，多面评审留给契约成员或跨成员的改动。

## 常用命令

下面的命令在工作树根目录运行。尖括号是占位符。

| 目的 | 命令 |
| --- | --- |
| 生成 agent 投影（agent 源没有改动时） | `uv run --locked python .meta_harness/tooling/src/initialize_agents.py --project-root .` |
| 核对投影 | `pnpm run check:agents` |
| 读任务状态 | `node --experimental-strip-types tools/dev-flow/src/integration/cli.ts status` |
| 同步目标分支后更新 targetBase | 先 `git merge <目标提交>`，再用 `{"kind":"task-sync","target":"<目标提交的 40 位提交号>"}` 运行 `cli.ts execute` |
| 文档检查 | `pnpm run check:docs` |
| 准入 | `OMNE_ADMISSION=1 pnpm run check` |
| 定向复现准入中的测试失败 | `npx turbo run test:<层> --filter=<成员> --only --env-mode=strict -- <测试文件> -t <用例>` |
| 后台运行并传出退出码 | `<命令> > "$log" 2>&1; rc=$?; echo "exit=$rc" >> "$log"; exit "$rc"` |

### 改了 agent 源之后重新生成投影

编译器不覆盖内容或权限不同的既存文件。agent 源改动之后，直接输出到 `.meta_harness` 会报 `ERROR: output differs; use a fresh staging directory: <路径>`。工具的规则见[Agent 编译与使用](../tooling/README.md#使用)。按下面的顺序操作：

1. 编译到一个新的暂存目录。
2. 把与现有产物不同的生成文件复制到 `.meta_harness/`。
3. 运行 `link_agents.py --project-root .` 和 `pnpm run check:agents`。
4. 删除暂存目录。

```sh
set -euo pipefail
stage="$(mktemp -d tmp/<任务>/agents-stage.XXXXXX)"
uv run --locked python .meta_harness/tooling/src/compile_agents.py --source .meta_harness/agents --output "$stage"
diff -rq "$stage" .meta_harness | grep -v '^Only in .meta_harness' || true   # 列出将要复制的文件
rsync -rlpc "$stage"/ .meta_harness/                                          # 只复制内容或权限不同的文件
uv run --locked python .meta_harness/tooling/src/link_agents.py --project-root .
pnpm run check:agents
rm -rf "$stage"
```

- 用脚本运行这段命令，或在每一步之后检查退出码。不要把编译命令接到 `| tail` 之类的管道上看输出。管道的退出码是最后一个命令的退出码，会掩盖编译失败。
- 删除了某个 agent 源时，旧的生成文件不会被自动删除，`check:agents` 也不检查多出的文件。要手动删除对应的生成文件。

## 已知问题

本节的现象来自实际运行。工具行为变化后，以实际输出为准，并修订本节。

- **工作树与 task context。**task context 绑定“工作树 + 分支”。
  - 同一棵树换分支后，`start` 报 `stale: Context belongs to another tree or branch`。
  - 同一张卡开新 attempt 时，旧树上 `start` 报 `stale: Worktree is already bound to another task`。同一分支不能同时检出在两棵树里。做法：把旧树的 `<本卡材料>` 移到主检出的 `tmp/` 下保存，推送分支，移除旧树，在同一分支上建新树，再还原材料。
  - 不要手删 context。
- **投影先于检查。**新工作树没有生成 agent 投影时，`pnpm run check` 报缺少生成目录。umask 让投影文件带组写权限时，`check:agents` 报权限不符，对报错的文件运行 `chmod g-w`。
- **验收夹具依赖构建产物。**有成员的验收夹具从 `dist` 导入时，准入的依赖检查报模块无法解析。准入前先构建该成员及其依赖。
- **交付条件为空。**卡没有前置条件时，“交付条件”整节正文必须恰好是 `无`，不带句号。否则 `start` 报条件表无法建立完整引用。
- **后台运行或管道吞掉退出码。**`<命令> > log; echo exit=$? > rc.txt` 的整体退出码是 `echo` 的退出码，通知永远显示 0。`<命令> | tail` 的退出码是 `tail` 的退出码，命令本身的失败被掩盖。用[常用命令](#常用命令)中的写法，或在脚本开头写 `set -o pipefail`。
- **合并目标分支后要 task-sync。**只合并不运行 `task-sync` 时，`targetBase` 仍是旧值，影响面计算按旧基线进行。显式传入不等于 `targetBase` 的基线，检查以 2 退出。
- **失败分诊不复现准入环境。**`test:triage` 不经过 turbo 的严格环境模式，可能把依赖环境的失败报成“隔离后稳定通过”。用[常用命令](#常用命令)中的 turbo 命令定向复现。
- **准入期间提交。**计划文件与 HEAD 不一致，这次准入作废。见 [P11](delivery-pitfalls.md#p11-准入运行期间不提交)。
- **只读子代理全盘搜索。**对 `/` 或主目录运行搜索会拖慢准入。简报写明搜索范围是工作树。
- **派发评论不可再改。**编辑过的派发评论使 `start` 以 `unknown` 失败。要改派发内容时，发新的派发。
- **gate 确认说明有长度上限。**确认说明不超过 1024 个字符。
- **上下文压缩后的署名。**压缩摘要可能把宿主的署名提示记成常设规则。每次压缩后按贡献指南复核一次（[P5](delivery-pitfalls.md#p5-署名与-pr-格式只认贡献指南)）。
