# 性能评测

评测量的是 harness 自己在会话路径上的代价：每一步读几次存储、提交几次、提交多少字节，随会话变长涨不涨。模型由本机的脚本作答，不发真实请求，不花钱。规则归 `tools/perf-harness/SPEC.md`（判定、可比性、报告）与 `benchmarks/SPEC.md`（套件、口径、代价模型）；本技能只写怎样用。

## 先知道四件事

- **只走根命令 `pnpm run perf`。** 它用仓库钉的 Node 起；直接敲 `node` 可能是另一个版本，时间读数会被判阻塞。要干净的输出用 `pnpm --silent run perf -- …`。
- **它只在自己起的实例上跑。** 每个套件起一个实验装配的服务端（空闲端口，状态在 `tmp/perf/data/` 下，跑完删掉）。不要把它指向别的服务，也不要为了腾机器去动别人的实例：负责人在 8787 端口上的服务不压测、不重启、不写入。
- **它量的是构建产物。** 先构建：`pnpm --workspace-concurrency=1 --filter @omne-harness/harness-server... --filter @omne-harness/cli... --filter @omne-harness/benchmarks... -r run build`（整仓已经 `pnpm run build` 过就不用）。改了产品代码或设施没重新构建，量到的、用到的是旧的。
- **`run` 与 `compare` 会排进整机的运行名额。** 机器上有别的重任务在跑时它会等。它在跑的时候不要同时跑测试或构建：读次数跟着时钟走，会被带偏。

## 命令

| 要做什么 | 命令 | 大约多久 |
| --- | --- | --- |
| 看这台机器的环境记录、标识、有哪些套件、有没有基线 | `pnpm --silent run perf -- env [套件]` | 几秒，不跑套件 |
| 跑一个或几个套件的短档 | `pnpm --silent run perf -- run <套件…> --tier short` | 一个套件 1 到 4 分钟 |
| 跑全部套件的短档 | `pnpm --silent run perf -- run --tier short` | 约 20 分钟 |
| 跑全档（多轮是 200 轮） | `pnpm --silent run perf -- run <套件> --tier full` | 10 到 30 分钟 |
| 比两个提交 | `pnpm --silent run perf -- compare <基准> <候选> <套件> --tier short` | 备检出与构建约 10 分钟一个提交，再加跑的时间 |
| 只比计数、不做计时的轮次 | 上一条加 `--counts-only` | 少掉十轮以上的重复 |
| 比两份已有的结果 | `pnpm --silent run perf -- compare <结果目录> <结果目录>` | 立刻 |
| 这之后的改动会影响哪些套件 | `pnpm --silent run perf -- affected --base <提交>` | 立刻 |
| 重新打印一份结果的报告 | `pnpm --silent run perf -- report <结果目录>` | 立刻 |

结果写在 `tmp/perf/results/<时刻>/<套件>.<档>/result.json`，报告打印在标准输出。退出码：0 通过；1 有门失败、计数不同或候选变慢；2 阻塞或用法不对。

## 选哪个套件

| 套件 | 问的是什么 |
| --- | --- |
| `multi-step` | 一轮里走很多步，一步的代价随步数涨不涨 |
| `multi-round` | 连着很多轮，一步的代价随轮数涨不涨；全档另看内存、状态字节、每轮用时三条曲线 |
| `cold-open` | 服务端重启之后接下一条输入，代价随会话长度涨不涨 |
| `catch-up` | 客户端回到一个会话开观察，代价随会话长度涨不涨 |
| `compaction` | 反复压缩的会话，一次压缩的代价随压缩次数涨不涨 |
| `tool-result` | 工具结果变大，一步的读写次数变不变 |
| `background-calls` | 后台开着的命令变多，一步的读写次数变不变 |
| `attachments` | 输入带的文件变大，受理它的读次数变不变 |

只说「跑一下性能评测」而没有点名时，跑 `multi-step` 与 `multi-round` 的短档：它们回答「每一步多少、随会话变长涨不涨」。改了某处代码想知道该跑谁，用 `affected`。

## 怎样读报告

- 第一行是结局。「pass, with N known failures accepted」的意思是：有 N 道门今天不过，各带一条接受记录（卡号与原因），这次照旧不过，没有新的坏消息。
- 每道门一行：通过、失败或阻塞。**阻塞不是通过**：没有基线、样本不够、机器状态不合格、套件没跑起来，都是阻塞，要写明原因，不要报成「没问题」。
- 一道已知失败的门如果这次过了，它会转成失败并提示撤掉接受记录：这是好消息，照提示改套件源码里的那条记录。
- 「Samples every gate has to judge one way」是每道门的必过与必败样本。样本的结局不对，那道门按阻塞算。
- 读数分三种，能不能比不一样：
  - 由步骤决定的计数（提交次数、提交字节、请求体字节）：同一个负载两次运行逐项相等，任何机器上都一样，可以和基线逐项比。
  - 跟着时钟走的计数（读次数）与时间：同样的一步两次相差百分之一二，换一台机器就不能比。两个提交之间只认 `compare` 的成对比较。
  - 「Can it be compared」一节写着这次和基线能不能比、比的结果。
- 成对比较有四个结论：变快、变慢、没有变化、证据不足。证据不足按阻塞处理，不要解读成「差不多」。输出不同（两个提交做的不是同一件事）时不判快慢。
- 报告最后一节写着这些读数没盖住什么。转述结论时带上它。

## 交报告时要带的

结局与每道门的结论；和基线或另一个提交能不能比，比的结果；跑在哪个提交上、工作树脏不脏；阻塞的每一项及原因；读数没盖住什么。数从报告里抄，不估。

## 加一个套件、改一道门

套件是 `benchmarks/src/suites/sessions.ts` 里的一段声明：负载（几轮、每轮几步、每步调什么）、轴、哪几个量立门、已知失败的接受记录。期望值写在源码里并注明出自代价模型的哪一栏，不许拿上一次的实测当期望。新套件要进 `benchmarks/SPEC.md` 的表，它产出的条目种类要进 `benchmarks/src/coverage.ts`。写计数基线用 `run … --write-baseline`，只有干净的工作树写得成。

## 踩过的坑

- 一轮在跑的时候客户端读一次历史，就会被算进那一步的读。套件的驱动器在一轮结束前不发请求；自己加探针时照这个做。
- 工具结果超过十几 KiB 就单独保管，不进下一次请求；想靠工具结果把上下文撑大是撑不动的，`compaction` 靠的是每轮约 10 万字节的输入。
- 压缩要触发比例高过保留比例（保留是型号窗口的百分之十六）才有东西可摘要，所以 `compaction` 把触发线设在百分之二十。
- 重启后的第一条输入，提交次数五次一档地跳，同样的负载两次运行差一两档：那一段只对提交字节与读次数立门。
- 收自己起的进程按进程号，不按名字匹配。
