# 全量重提

**把统一语言与全部产品 topic 从头过一遍，重新提出「系统里有哪些有身份的对象」，再与现有条目逐条对账。**

## 什么时候做，什么时候不做

做：一批 topic 大改之后；架构或规格设计开工之前；或者怀疑 `objects.md` 整体漂了。

**平时不做。**逐条复核由 rev 对账驱动，那条路便宜而且够用；重提贵，专门用来抓 rev 对账抓不到的那一类——
**产品正文里有一个对象，却从头到尾没人给它立过词条**。

下面这套是 2026-09-21 首次提取实际用过的（十五路分块、388 条原始条目归并成 28 条对象与 15 项待裁），可原样重复。

## 五步

### 1. 预生成锚点表

对 `design/ubiquitous_language/terms/*.md` 与每个 topic 的 `design.md`、`flows.md`，
用设计链链接检查**同一套 slug 算法**（`tooling/src/design_validation.py` 的 `github_anchor`）
产出「行号 · 级别 · 标题 · 锚点」表。

**锚点只许从表里抄，不许各自算。**十几个执行者各算各的，中文标题加标点的锚点一定有人算错，
而错的锚点要到聚合之后才暴露，那时已经分不清是锚点错还是标题改过。

### 2. 分块通读

- 统一语言按卷分，产品正文按 topic 分；大 topic 独占一块，小的两三个合一块。
- **每块一个执行者，互不通气。**通了气，后读的人会顺着先读的人的口径走，独立性就没了。
- 只读 `design.md` 与 `flows.md`（`README.md` 可读来定位）。**不读** `changelog.md`、`decisions.md`、`interviews/`——
  那是历史与推导，不是最终设计；读了，已经被推翻的对象会混回来。
- **要通读，不要只搜关键词。**对象常常藏在「模型」「产品规则」里，不在「概念定义」里；
  最危险的那种——被反复使用却从没定义过的——关键词根本搜不到，因为你不知道该搜什么。
- 产品正文的分块里，**只记正文显式链到的词条**，不要自己去词表里搜来配——词表另有人读；
  配对留给聚合，才看得出「正文在用、词表没有」的缺口。

### 3. 统一口径、统一格式

所有分块共用一份口径，聚合才做得了。口径见下面[分块口径](#分块口径)，派发时原样给到每个执行者。

### 4. 聚合：每条原始条目必须被恰好一个去向认领

去向只有五种：**某条对象**、**某个变体**（挂到父对象）、**某项待裁**、**某个视图**、**排除**（写理由）。
同一个对象会从七八个分块里各冒出来一次，叫法还不一样；聚合就是给每条原始条目指一个去向。

**用脚本核对「无人认领」与「重复认领」都为零。**

> **这一步是防漏的全部保证，不能省，也不能改成抽查。**
> 人工聚合几百条，漏掉三五条是常态；而漏掉的恰恰是叫法生僻、哪个已有对象都不像的那些——
> 正是重提要抓的东西。

### 5. 与现有条目逐条对账

| 重提的结果 | 怎么办 |
|---|---|
| 冒出一个新对象 | 能立词条就立词条、立条目；立不了进 `pending.md` |
| 与现有条目的宿主、身份或生灭对不上 | 回读依据：正文变了就改条目；正文自己两处相左，记进统一语言的 `conflicts.md` 或该 topic 的 `decisions.md`，**不在这里静默选一个** |
| 现有条目在重提里没人提到 | 多半是正文删掉了它，或它降级了——回读依据确认，再按「对象被重新认定」处置 |
| 几个分块对同一个东西判得不一样 | 这本身就是发现：要么定义依赖上下文（词条「独立」自检没过），要么确实是两个东西 |

## 分块口径

派给每个执行者的口径至少包含这些，措辞可以按当次任务调整：

**入选判据**——与词条「形态」里「对象」那一行同一句，不另立标准：
有独立身份（分得出这一个与那一个，能被标识、被引用），并且有自己的生命周期、运行时实例或耐久记录三者之一。

**提取时分三级，聚合时再归并**：

| 级 | 含义 | 聚合后的去向 |
|---|---|---|
| A 一等对象 | 独立身份 + 独立生命周期，不依附别的对象也成立 | 对象 |
| B 从属对象 | 有身份、可寻址，但寿命依附某个宿主 | 对象（宿主非空） |
| C 变体 | 某个 A/B 的子种类，没有独立于父类的身份机制与生灭 | 变体；**有了自己特有的身份或生灭规则，就升为 A/B** |

**不入选、但临界的要记进排除清单并写一行理由**：属性与标记；规则、语义与策略；过程与动作
（**一次动作留下的有身份的东西才是对象**——一次派发交回来的派发报告是，派发不是）；
正文明说「是视图不是对象」的；枚举值与状态值；只是在说「谁」的角色称谓；自身不会有实例的总称。
**拿不准的放进排除清单，不要硬塞进对象清单，也不要悄悄丢掉**——排除清单是聚合时发现分歧的地方。

**每个对象记**：中英文名（正文没给英文就写 —）、级别、身份、生命周期、运行时、宿主、关键关系、
别名与旧说法、正文显式链到的词条、依据链接（锚点抄自锚点表，定义处放第一条，附行号）、
一两句贴近原文的摘录、疑点。

**纪律**：

- **忠于正文。**身份、生灭、关系都要有原文依据，不用常识补全；正文没说就写「未述」。
- **推断的标明是推断**，写在「疑点」里。
- **「只引用、不拥有」的对象照样列**，注明定义归哪个 topic，其余字段只填本 topic 新增的信息——
  聚合靠它看出「这个对象被多少个 topic 讲到」。
- 宁可多列一个带疑点的 B/C，也不要漏掉一个 A。
- 执行者只读设计区、只写自己那一份报告，不改任何设计正文。

## 工作材料留在任务区

分块报告、锚点表、口径与聚合脚本是**一次施工的工作材料**，放在当次任务区的 `tmp/`，不进设计链。
**进设计链的只有对账之后的条目、词条与待裁改动**——以及由生成器重新产出的总表。
