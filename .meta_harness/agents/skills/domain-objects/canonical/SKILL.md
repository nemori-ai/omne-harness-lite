# 领域对象

**加载它，意味着你此刻是收账的，不是设计的。**

产品正文按问题分 topic，同一个对象的事实散在十几个 topic 里；统一语言按词收，只回答「这个词指什么」。
你的活是把散着的那些**跨 topic 收成一条骨架**——它寄宿在谁身上、靠什么分得出这一个与那一个、
怎么来怎么没——而且**每个字都指得回产品正文**。架构与规格的人开工时，靠这一份知道该去读哪一节、该问什么。

收账的人有三件事不做，后面每一节都是这三条的展开：

- **不替正文补空。**正文没说的就写「正文未述」。你补上一个看起来合理的，下游会把它当成已定事实实现出来，而且再也查不出是谁定的。
- **不裁产品分歧。**两处正文说法相左，你的产出是「记下来、写清谁来裁」，不是挑一个。
- **不划边界。**能力边界、限界上下文、聚合、存储切分是系统架构设计的结论。条目只记可被核对的属性，任何划分都是这些属性上的一次透视。

**路径都从私有工作区根 `.meta_harness/` 算起**，因为这份正文会被编译到几个宿主目录下，相对链接在那里不成立。

| 文件 | 拥有什么 |
|---|---|
| `design/domain_objects/AGENTS.md` | 该区的常驻约定：谁该加载本 skill、谁不该，红线 |
| `design/domain_objects/README.md` | 这一区拥有什么、不拥有什么、失效事件 |
| `design/domain_objects/conventions.md` | **格式契约**：条目与待裁项长什么样、每个字段什么意思、对账器守哪几条 |
| `design/domain_objects/objects.md` · `pending.md` | 正文：对象条目、待裁 |
| `design/views/domain-object-map.md` | 派生总表，**生成器产出，不手写不手改** |

格式以 `conventions.md` 为准，这里不重复字段表；**这份给的是怎么判、怎么维护**。

撰写或修订对象条目、待裁项与复核记录前，必须加载 `asd-ste100` skill。遵循其适用写作规范。
本 skill 继续负责对象收账与依据核对；清晰化不得补造事实或替产品负责人裁决。
「一个东西是不是对象」不在这里判——那是词条的「形态」，判法归 `ubiquitous-language` skill 的「判形态」。

## 一、立一条：四个字段怎么判

**先决条件：词条已经存在，形态是「对象」。**条目以词条 ID 为键，没有词条的东西不许立条目——
先按 `ubiquitous-language` skill 立词条；立不了的（写不出无歧义定义、还没人拍板）走[第三节](#三进-pending把缺口写成有人管的样子)。
顺序反过来，就是在词表之外另发了一套号。

### 宿主：问「谁没了，它就没了」

宿主讲的是**寿命**，不是归属。最常见的错是把两者混了：一份资产**归属于**某个租户，
那是所有权；会话级沙箱**寄宿于**会话，会话归档它就销毁，那才是宿主。
判不出来的时候问自己：「那一头没了，这一头是跟着没，还是只是没了主人？」

- **会换宿主的，把每种情形都写出来。**工具执行前台时跟着 agent runtime，转后台就换成会话——
  只写一个，取消语义就会被做错。
- **「挂在会话下」要有正文依据，不能凭直觉。**这个系统里大半对象看着都像挂在会话下；
  正文没说寿命跟着谁的，照实写「正文未述」，并在「未裁」里点一句。
- 没有宿主的写 `—`，不要为了整齐挂到租户上。

### 身份：写正文给了什么，不写你觉得该有什么

靠什么分得出这一个与那一个、在什么范围内唯一。**正文常常没给标识**，只给了约束
（「只要求记得下是哪一次运行、哪个 agent runtime 发起」）——那就照抄这条约束。
字段名、ID 格式一律不写，那是规格的事。

### 生灭：一行，链到状态图

怎么来、经过哪些状态、怎么没。没有终结的照实写「无删除」——这个系统里会话就只有归档、没有删除，
写成「创建 → 销毁」就是替正文发明了一个出口。转移条件与理由不写，它们在该 topic 的 `flows.md`。

### 依据：定义处放第一条

只指 `product/` 某个 topic 的 `design.md` 或 `flows.md`，每条带 rev；rev 取该 topic
`README.md` front-matter 的 `revision`，那是唯一的权威值。**不指 changelog、decisions、interviews**——
那是历史与推导，依据指到那上面等于没有依据。

### 写到哪停

> **写到「架构与规格的人据此知道该去读哪一节、该问什么」就停。**

「身份」「生灭」各只有一行是有意的。想多写一句的时候，多半是在复述依据——
而复述一旦和依据不一致，读者就得猜哪个算数。**条目与依据不一致时永远以依据为准，改条目。**

## 二、几个叫法，算不算同一个对象

产品正文写了很久，同一个东西在不同 topic 里常有几个叫法；反过来，一个叫法底下也可能压着两个东西。

**并入的判据：正文把它们当同一物用。**具体看三样——身份机制是不是同一个、是不是同生同灭、
在正文里能不能互换而句子不变味。三样都是，就并入，并在「并入」里**写凭什么**：

> 「成员关系」并入租户——design 只定义租户，flows 却把「无 → 成员 → 无」的状态机挂在成员关系名下；
> 二者同生同灭、同一身份，是租户的生灭那一面。

**三样里有一样说不准，就不要并。**正文说两个东西是「同一个协程的两个视角」，可一个有词条、
一个形态未定，日志里各自怎么指认也没说——那是一项待裁，不是一次并入。
并错的代价比不并大：并了，下游就只建一个；那个被吞掉的，从此没人记得它有过自己的问题。

**「并入」不管用词。**该弃用哪个说法归词条的「弃用」；正文回改归各 topic 的 owner。
这里只记「这条对象吸收了哪些叫法、为什么算同一个」。

## 三、进 pending：把缺口写成有人管的样子

进哪个文件的分流表在 `conventions.md`，判据只有词条形态一处。这里讲的是怎么把一项待裁写好。

**什么值得进。**正文确实在把它当对象用——能被指名、能被配置、有状态——而且下游绕不开它。
只在一句话里露过面、证据单薄的，不进；pending 不是疑问收集箱，塞满了，真正悬着的那几项就没人看了。

**「谁来裁」要指到真能裁的人。**

| 缺的是什么 | 谁来裁 | 同时要做 |
|---|---|---|
| 某个 topic 用了它却没定义 | 该 topic 的 owner | 记进该 topic 现行正文的未决项 |
| 要不要有它、归哪个 topic 都没人说过 | 产品负责人 | 同上，记在最先用到它的那个 topic |
| 两处产品正文说法相左 | 涉及的各 topic owner，定不了上交产品负责人 | 词条形态写「未定」，`ubiquitous_language/conflicts.md` 立一条，写清两种读法与各自出处 |
| 它怎么存、怎么切、怎么标识 | **不是产品问题**。写「系统架构设计」 | **不要**挂到产品 owner 名下——不是每个缺口都是产品未决项，挂错了，产品负责人会收到一堆他答不了的问题 |

**「闭合条件」写成一个看得见的事件**：「有一个 topic 定义了它，并立了词条或明确说它不是概念」，
不写「想清楚之后」。一项没有 owner、没有闭合条件的待裁，六个月后就是一个没人记得问过的问题。

标题用它在正文里的叫法，不编号，不给它发明一个正式名——取名是立词条那一步的事。

## 四、topic 升了 rev：逐条复核

rev 是词表、对象条目与产品正文对齐的**唯一凭据**。某个 topic 升了 rev，凡「依据」或「出处」还标着旧 rev 的，
对账器会逐条点名（命令与参数见 `tooling/README.md`「领域对象对账」；`--stale report` 只列不拦，适合边改边看）。

**被点名不代表内容错了**，只代表「那边改过，这条还没人回头看」。每一条这样过：

1. **读那个 topic 的现行正文**，核对宿主、身份、生灭与适用边界；本次差量核对放工作树 tmp。
2. **回读依据指向的那一节现行正文。**锚点断了的尤其要读：标题被改，多半意味着那一节被重写了。
3. 三种结果：

| 读完发现 | 怎么办 |
|---|---|
| 骨架仍成立 | 把 rev 改到当前值。顺手看依据是不是还指在「定义处」——正文挪过章节的，换成现在的那一节 |
| 宿主、身份或生灭变了 | 先改条目，再改 rev |
| 它还是不是对象都动摇了 | 这是[重新认定](#五对象被重新认定)，先动词条 |
| 现行正文自己两处说法相左，看不出哪边算数 | 条目照实写——定不下来的那一栏写「正文两处说法相左」，在「未裁」里点明是哪两节、去哪裁，并记进所属 topic 现行正文的未决项；**然后 rev 照样改到当前值** |

**落后的 rev 只有一个意思：没人回头看过。**悬而未决不靠它表达，那由「未裁」承载。
拿一个故意留旧的 rev 去标「这里有争议」，对账器就永远是红的，而红久了的检查没有人再看。

> **不读就批量改 rev，等于把这道检查关掉。**对账器只能证明「rev 写的是当前值」，
> 证明不了「有人回头看过」——后一半全靠这一步的人。

词条「出处」的复核是同一套动作，判的是「定义还成不成立」，做法见 `ubiquitous-language` skill。
**谁升的 rev，谁负责把被点名的两边都复核完**；交付时对账器应当是干净的。

## 五、对象被重新认定

这是这一区的失效事件：拆成两个、两个并成一个、从对象降成属性或视图、换了宿主、pending 里的一项有了裁决。

**先动词条，再动这里。**对象性归词条的「形态」，条目只是跟着走：

| 发生了什么 | 词条那边 | 这里 |
|---|---|---|
| 降成属性 / 视图 / 变体 | 改形态（变体写明父） | 删条目；它身上的「未裁」若还成立，移到新宿主对象的条目下 |
| 降成「未定」 | 改形态，conflicts.md 立一条 | 条目移进 pending.md，补「谁来裁」与闭合条件 |
| 一拆二 | 立新词条，旧词条收窄或弃用 | 各立一条；**依据要重新指**，不能两条共用原来那一节了事 |
| 二并一 | 留一个，另一个进「弃用」 | 留一条，「并入」写明吸收了谁、凭什么 |
| pending 的一项裁成了对象 | 立词条 | 立条目，从 pending 删掉 |
| pending 的一项裁成不是对象 | —— | 从 pending 删掉；仍有有效含义时写入当前拥有者的正文 |

形态变了算「含义变了」，要按改词条的规矩走，不是改一个字段那么轻——所有照着旧形态做的设计都得复核。

**这里没有 changelog，也不写历史。**`objects.md` 只写现在是什么样；裁过的「未裁」直接删掉，结论落进上面几栏。
讨论、复核与变化过程放本工作树 tmp；产品正文保存当前含义和必要理由。

## 六、机器查不了的那一半

对账器查得了「形态为对象的词条有没有条目」「rev 是不是当前值」「总表是不是最新」，
**查不了「产品正文里冒出一个新对象，却没人给它立词条」**——上游是散文。这个方向靠两样兜：

- **落字时的规矩**：新概念先进词表、再进正文；立词条必判形态；形态一写「对象」，对账器就来要条目。
  所以你在复核或通读时撞见一个正文在用、词表里却没有的东西，**不要绕过去**——按第三节登记。
- **全量重提**：平时不做，逐条复核由 rev 驱动；重提专门用来抓「漏了整个对象」这一类。
  流程、分块口径与防漏的核对在 `references/full-reextraction.md`。

## 七、落盘之前

- 对账器默认模式通过——形态与条目一一对应、必填字段齐、依据 rev 为当前值。
- 改过 `objects.md` 或词条形态的，**重新生成** `design/views/domain-object-map.md`（同一个工具带 `--write`），不手改它。
- 设计链的链接检查通过——标题一改锚点就断，条目之间靠锚点互指。
- 新立的词条在 `design/ubiquitous_language/index.md` 有一行。
- 进了 pending 的产品缺口，所属 topic 现行正文的未决项里查得到。
- 回头看一遍自己写的每一栏：**有没有哪个字是正文没说、你觉得应该是这样的？**有，就改成「正文未述」。
