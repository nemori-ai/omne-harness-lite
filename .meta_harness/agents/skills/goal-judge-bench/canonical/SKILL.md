# 目标判定器的评测与调优

判定器回答「agent 说做完了，是不是真的」。它的题目怎样写、材料怎样打包、线画在哪、用哪个型号，都由评测台上的数定。规则归 `packages/goal/SPEC.md`「判定的评测」：门槛、回归表、采用条件在那里，这里只写做法。

评测台在 `packages/goal/goal-bench`，不进发行。命令都在这个目录下跑：`pnpm run -s bench <命令>`，不带命令时打印用法。

## 先知道五件

- **判定器是确定的。** 同一个请求答同样的答案。所以答复按请求的摘要存一次（`experiments/<名>/replies.jsonl`），之后重放不花钱；「问三次取多数」没有用。
- **只改读法的不用发请求。** 线（`line`）不进请求。换一条线重放，全部命中存下的答复。
- **留出的两份对一个候选只看一次。** `tune` 用来调；`verify` 与 `canary` 是留出的。看过留出的数再改方案，那一份就不再是留出。
- **真实请求花钱，先记账。** `run` 与 `compare` 发之前估费用，超过 `--max-cost`（缺省 1 美元）就不发。一次判定约 0.0003 美元。密钥从 `--key-file` 读，只进认证头，不打印。
- **正确答案不是人标的。** 母本里每条判据都真成立；每个用例只改母本一处，改法决定正确答案。所以不要为了让数好看去改答案：能改的只有母本与变异本身，改了要重新签字。

## 一轮调优

1. **核数据，重现起点。** 两条都不发请求；第二条的数要与留下的对照相同。

   ```sh
   pnpm run -s bench validate
   pnpm run -s bench compare --name default-vs-baseline-heldout --config configs/final.json --offline
   ```

2. **在调的那一份上量现行缺省。** `run --name <名> --split tune --config configs/final.json`。报告在 `experiments/<名>/report.json`：`gates` 是三道门槛，`ranking` 是排序用的数，`wrong` 是读错的条目（按代价排）。
3. **读错例，不读总数。** 对 `wrong` 里代价大的几条逐条看判定器拿到了什么、答了什么：

   ```sh
   pnpm run -s bench show --case <母本>/<用例> --config <配置> --ids A2,N1
   ```

   编号取自 `wrong` 的 `id`；`U` 是「未声明的不可达」，对应两道是非题。是非题的答复 `noul` 就是「是」的概率。报告页（`<--out 目录>/<名>/report.md`，不给 `--out` 时在系统临时目录的 `goal-bench/` 下）有一张「读错的归类」，先看它再挑用例。

   先分清是哪一种，按这个次序问：
   - 判据要的事实在不在 `state.evidence.<编号>` 或 `state.facts.activity` 里？不在，是打包的事。
   - 在，而题目的 `instructions` 没说清怎样算？是题目的事。
   - 选项选对了，概率不到线？是线的事。
   - 事实在、题目清楚、高概率选错？是判定器读漏了，型号的事。

   同一种错出现三次以上才值得改一根轴。
4. **一次只动一根轴。** 轴就是 `JudgeConfig` 的字段，取值范围在 `JudgeConfigSchema`（`packages/goal/goal-contract/src/judge/material.ts`）。配置文件只写要改的字段，盖在**基线方案**（同一个文件里的 `BASELINE_JUDGE_CONFIG`）上。要在现行缺省上动一根轴，把缺省的文件放在前面，几份从左到右叠：

   ```sh
   echo '{"packaging":{"excerpt":800}}' > /tmp/excerpt-800.json
   pnpm run -s bench run --name excerpt-800 --split tune --config configs/final.json,/tmp/excerpt-800.json
   ```

   只给自己那一份，量到的是「基线加这一样」，和缺省不可比。要一种现有字段表达不了的写法时，在打包函数（同目录的 `pack.ts`）里加一个可切换的值，把它加进 `JudgeConfigSchema` 并让旧值作 `.default`：这样以前的实验照样能重放。
5. **量，记。** 实验名只用小写字母、数字与短横。量完在 `experiments/ledger.json` 加一条，四个字段都要：`name`、`axis`（哪根轴）、`changed`（改了什么）、`conclusion`（结论与采不采用）。数不用抄，表里别的列都取自报告：`pnpm run -s bench ledger` 把每条记录和它自己报告里的数拼成一张表，跑过而没记的排在最后、写着「没有记」。没有采用的也记，写为什么。
6. **合起来，再各拿掉一样。** 把单轴里有用的写进一份候选文件 `configs/<候选>.json`。消融是对候选的每一样各写一份小文件，把那个字段写回基线的值，叠在候选后面各量一次（`--config <候选>,<拿掉某样>.json`）。比三个数：误判成立的次数、误收场的次数、加权损失。拿掉之后三个都不变差的那一样不要。一个配置改了进请求的字段而离线全命中，说明它以前量过，数可以直接用。
7. **线最后定。** 线只改读法：`--config <候选>,<线>.json`（内容如 `{"line":0.7}`）加 `--offline`，几条线各跑一次，各用一个名字。线救不了高置信度的错，它只在「少漏放」与「少误判」之间换。
8. **写定候选，再看留出。** 把候选的配置与理由写进台账，然后才跑：

   ```sh
   pnpm run -s bench compare --name <候选>-vs-default-heldout --split verify,canary \
     --base configs/final.json --config <候选> --key-file <密钥文件>
   ```

   密钥文件的位置由负责人给，不写进仓库。对照表打印在终端，也写进 `experiments/<名>/compare.json`；每项指标带 95% 区间，末尾是加权损失的成对差。
9. **照规格的采用条件定。** 采用了：改 `material.ts` 里的 `DEFAULT_JUDGE_CONFIG` 与 `configs/final.json`（两者要相等，有用例守着）；不带 `--offline` 重跑第 1 步第二条，留下新的 `compare.json`；在 `packages/goal/goal-contract` 先 `pnpm run build`，再在它和 `packages/goal/goal-bench` 下各跑 `pnpm exec vitest run --mode fast`，在 `apps/harness-server` 下跑 `pnpm exec vitest run --mode slow tests/rows/goal`。没采用：实验记录照样进仓库。
10. **交出五样。** 留出的对照表（第 8 步的输出）；消融表与全部实验的记录（`bench ledger`）；留出上的错例（`compare.json` 里候选一边的 `wrong`，硬错用 `show` 逐条读原文）；花费（各报告的 `cost`）。门槛没过的写差多少。

## 加数据

- 母本是 `data/parents/<编号>-<名>.json`，形状是 `src/case.ts` 的 `ParentSchema`：目标正文、进展清单、工具调用、每条要读才判得了的判据的检查（`oracle`）、一组变异。变异有 13 种，归成 8 类，见同一个文件的 `FAMILY_OF`。
- 写完跑 `validate --parent <编号>`：干净的会话要过自己的检查，每个改坏的用例要不过。全过之后 `sign --by <谁>`。母本一改，签字失效。
- `split` 写明进哪一份。最刁的进 `canary`。数据的下限在 `src/check.ts` 的 `MINIMUM`。
- 一个变异的正确答案有争议时不留。争议的判法：换一个合理的 agent，它能不能绕过去；判据的字面有没有真的被违反。
- 真实会话里出现一次误判，照原样做成母本：正文、清单与被引用的工具结果照抄，隐去与判定无关的内容。

## 查验的评测

查验的一方是一个真的会话，量它要真的起它。规则归同一节规格的末几条；什么时候必须重跑见那里的回归表。下面的命令除第 1 步外都在 `packages/goal/goal-bench` 下跑。`<名>` 是实验的名字，结果留在 `experiments/<名>/`。

1. **先构建。** 在仓库根 `pnpm run -s build`：运行器起的是 `apps/harness-server/dist/lab/bin.js` 与 `apps/cli/dist/bin.js`。
2. **核成品。** `pnpm run -s bench examine validate`：每份成品的每条判据有一个检查程序，干净的要全过，每处改坏要只让自己那条不过。列出的就是用例：成品原样、每处改坏单独查、一处「查过再改好」、一处「查过再换成另一处坏」。
3. **验量具，不花钱。** 两个脚本化的查验员各跑一遍：

   ```sh
   pnpm run -s bench examine run --name <名>-truthful --examiner truthful --key-file <密钥文件> --credential-file <登录凭据文件>
   pnpm run -s bench examine run --name <名>-lenient --examiner lenient --key-file <密钥文件> --credential-file <登录凭据文件>
   ```

   `truthful` 的报告要一处不错；`lenient` 要把没做到的全答成成立、做到的一条不错。不是这样就先修运行器，不跑真的。看的是「读错的」那张表与前两行的分子；「门槛」一段在条数少时一定写没过，那是分母小，不是量具坏了。
   只想跑一部分时加 `--only <成品编号或用例名>[,…]`。每个用例起一台自己的服务：`--parallel <几台>`（缺省 1），端口从 `--port`（缺省 47400）起每台加一，运行目录在 `--work`（缺省在系统临时目录），页面写到 `--out`。
4. **跑真的。** 同一条命令，`--examiner real`（缺省），加 `--parallel 4`。一批约 0.03 美元、一分钟上下；`--max-cost` 缺省 3 美元，到了就不再起新用例。存下的用例不重跑：中断了再跑同一个 `--name` 就接着做。两个文件的位置由负责人给，不写进仓库；它们只经标准输入交给服务与命令行。
5. **读报告。** 页面写到 `<out>/<名>/examination.md`（缺省在系统临时目录），数留在 `experiments/<名>/examination.json`，每个用例的读数、查验一方的每次调用与花费留在 `answers.jsonl`。先看「没做到的被答成成立」与它的区间，再看「做到了却不敢认」、每批的花费与用时、「它动了被查的活吗」。读错的逐条在 `answers.jsonl` 里看它跑了什么。`examine report --name <名>` 只凭存下的重出页面。
6. **记台账，改说明。** 在 `experiments/ledger.json` 加一条。设置项里这个选项的说明（`packages/goal/goal-local/src/judge-setting.ts` 的 `EXAMINERS`）照量出来的数改。门槛没过照实写差多少。

加成品：`data/products/<编号>-<名>.json`，形状是 `src/examine/product.ts` 的 `ProductSchema`。成品要小、只用 `node` 与命令行就验得了；每处改坏用「把哪一段换成什么」写，换的那一段在文件里只出现一次；检查程序放在成品之外，从成品的目录里跑，退出码 0 算成立。查法写给查验的一方看，写动手做什么、该看到什么，不写检查程序本身。改坏的要像真的半成品：自带的用例照样过、文档照样写着做了。

读数取目标记下的那一份。查验一方交的引用指不到这一轮的调用时会被整次退回并列出可引用的编号，它再交一次：每批多一次调用是正常的，一直交不对的那一批记成判不了。

## 什么时候停

- 留出的两份看过了。之后想到的改法记进台账的「下一轮先试」，等补了新的留出母本再做。
- 候选在调的那一份上两道硬门槛（误判成立、误收场）已经是 0 或 1，剩下的错都是「选对了但概率不到线」。这是线的取舍，归负责人。
- 一根轴连试两种写法都没有让加权损失降下去。
- 花费到了上限。

## 量过、不必重试的

型号或上游变了才值得重量：

- 在题目里加通用的告诫（「证据不确定时不要选成立」这一类）：误判成立到 0，但成立的漏掉四成到七成。针对性的话要写在带标记的那条证据旁边，不写在题目里。
- 一题一次请求：贵 2.3 倍，硬门槛不变好。
- 摘录截短或只取结尾：更差。
- `typesafe/jev-1.14` 与 `jev-1.13`：便宜一半，误判成立翻倍。
- 命令通过之前 agent 写过它所用的测试时，只问「这次通过可信吗」（`unsettled: covers`）：漏放少约三成，但误收场从 0 到 1，没有采用。见下面「容易错的地方」的头两条。

## 容易错的地方

- 减少「判不了」会把旧的认错放出来。一个用例里有一条高把握的认错时，旁边那条真成立的判据一读对，这个用例就成了误收场。所以先比误判成立与误收场的次数，再看漏放与加权损失；漏放降了而误收场升了，不采用。
- 把一类题从判定器挪给系统（例如证据过时由系统判），误判成立率的分母会变小：错的次数不变，比例也会变。对照时连分母一起读，结论里两个都写。
- 真实旅程里判定不对时，先把那次会话重建成判定器的请求再看：用发行版自己的 `describeCall` 与 `packJudge`，从整份会话历史与目标的读回算出 `state` 与题目，再拿去单问、一次只改一处。重建出来的请求里看得出是哪一种错（打包、题目、线、型号），和读评测台的错例是同一套问法。
- 评测台从 `dist` 读 `goal-contract`。改了打包函数先在 `packages/goal/goal-contract` 下 `pnpm run build`，否则量的是旧的。
- `--offline` 时有一个请求没存过答复，整次运行失败，并留下一个空的 `experiments/<名>/`，要自己删。改了进请求的字段而没发过请求，是预期的失败；什么都没改却失败，说明打包的输出变了，先确认是不是有意的。
- 离线重跑一个已有名字的实验会改写它的 `report.json`。要比新旧，换一个名字。
- 守则那道题「违反」不过线，哪个选项概率最高就读哪个。读 `wrong` 里「守住了说成违反」的条目时先看概率。
- 交给判定器的材料里没有的事实，它不会知道。判据提到「今天」「现在」而材料里没有时间，就一定判不准。
