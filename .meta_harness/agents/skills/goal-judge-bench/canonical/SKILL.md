# 目标判定器的评测与调优

判定器回答「agent 说做完了，是不是真的」。它的题目怎样写、材料怎样打包、线画在哪、用哪个型号，都由评测台上的数定。规则归 `packages/goal/SPEC.md`「判定的评测」：门槛、回归表、采用条件在那里，这里只写做法。

评测台在 `packages/goal/goal-bench`，不进发行。命令都在这个目录下跑：`pnpm run -s bench <命令>`，不带命令时打印用法。

## 先知道五件

- **判定器是确定的。** 同一个请求答同样的答案。所以答复按请求的摘要存一次（`experiments/<名>/replies.jsonl`），之后重放不花钱；「问三次取多数」没有用。
- **只改读法的不用发请求。** 线（`line`）不进请求。换一条线重放，全部命中存下的答复。
- **留出的两份对一个候选只看一次。** `tune` 用来调；`verify` 与 `canary` 是留出的。看过留出的数再改方案，那一份就不再是留出。
- **真实请求花钱，先记账。** `run` 与 `compare` 发之前估费用，超过 `--max-cost`（缺省 1 美元）就不发。一次判定约 0.0003 美元。密钥从 `--key-file` 读，只进认证头，不打印。
- **正确答案不是人标的。** 母本里每条判据都真成立；每个用例只改母本一处，改法决定正确答案。所以不要为了让数好看去改答案：能改的只有母本与变异本身，改了要重新签字。

## 一轮调优

1. **核数据，重现起点。** 两条都不发请求；第二条的数要与留下的对照相同。

   ```sh
   pnpm run -s bench validate
   pnpm run -s bench compare --name final-vs-baseline-heldout --config configs/final.json --offline
   ```

2. **在调的那一份上量现行缺省。** `run --name <名> --split tune --config configs/final.json`。报告在 `experiments/<名>/report.json`：`gates` 是三道门槛，`ranking` 是排序用的数，`wrong` 是读错的条目（按代价排）。
3. **读错例，不读总数。** 对 `wrong` 里代价大的几条逐条看判定器拿到了什么、答了什么：

   ```sh
   pnpm run -s bench show --case <母本>/<用例> --config <配置> --ids A2,N1
   ```

   先分清是哪一种：材料里没有它要的事实（打包的事）；事实在，题目问得不清（题目的事）；选对了但概率不到线（线的事）；判定器读漏了（型号的事）。同一种错出现三次以上才值得改一根轴。
4. **一次只动一根轴。** 轴就是 `JudgeConfig` 的字段（`packages/goal/goal-contract/src/judge/material.ts`）。配置文件是盖在基线方案上的一部分字段。要一种现有字段表达不了的写法时，在打包函数里加一个可切换的值，旧值仍是缺省，这样以前的实验照样能重放。
5. **量，记。** `run --name <轴>-<改了什么> --split tune --config <文件>`。每个实验在台账里记一行：改了什么、误判成立、误收场、漏放、守则漏报、加权损失、每次判定的费用、结论。没有采用的也记，写为什么。
6. **合起来，再各拿掉一样。** 把单轴里有用的合成候选。再从候选各拿掉一样各量一次（消融）：拿掉之后数不变差的那一样不要。
7. **线最后定。** 用候选存下的答复按几条线各重放一次。线救不了高置信度的错，它只在「少漏放」与「少误判」之间换。
8. **写定候选，再看留出。** 把候选的配置与理由写进台账，然后才跑：

   ```sh
   pnpm run -s bench compare --name <候选>-vs-default-heldout --split verify,canary \
     --base configs/final.json --config <候选> --key-file <密钥文件>
   ```

   对照表里每项指标带 95% 区间，末尾是加权损失的成对差。
9. **照规格的采用条件定。** 采用了：改 `DEFAULT_JUDGE_CONFIG` 与 `configs/final.json`（两者要相等，有用例守着），重跑第 1 步第二条并把新的 `compare.json` 留下，再跑 `goal-contract`、`goal-bench` 与服务端 `tests/rows/goal` 的用例。没采用：实验记录照样进仓库。
10. **交出五样。** 留出的对照表；消融表；留出上的错例（硬错逐条读原文）；花费；全部实验的记录。门槛没过的写差多少。

## 加数据

- 母本是 `data/parents/<编号>-<名>.json`，形状是 `src/case.ts` 的 `ParentSchema`：目标正文、进展清单、工具调用、每条要读才判得了的判据的检查（`oracle`）、一组变异。变异有 13 种，归成 8 类，见同一个文件的 `FAMILY_OF`。
- 写完跑 `validate --parent <编号>`：干净的会话要过自己的检查，每个改坏的用例要不过。全过之后 `sign --by <谁>`。母本一改，签字失效。
- `split` 写明进哪一份。最刁的进 `canary`。数据的下限在 `src/check.ts` 的 `MINIMUM`。
- 一个变异的正确答案有争议时不留。争议的判法：换一个合理的 agent，它能不能绕过去；判据的字面有没有真的被违反。
- 真实会话里出现一次误判，照原样做成母本：正文、清单与被引用的工具结果照抄，隐去与判定无关的内容。

## 什么时候停

- 留出的两份看过了。之后想到的改法记进台账的「下一轮先试」，等补了新的留出母本再做。
- 候选在调的那一份上两道硬门槛（误判成立、误收场）已经是 0 或 1，剩下的错都是「选对了但概率不到线」。这是线的取舍，归负责人。
- 一根轴连试两种写法都没有让加权损失降下去。
- 花费到了上限。

## 量过、不必重试的

型号或上游变了才值得重量：

- 在题目里加通用的告诫（「证据不确定时不要选成立」这一类）：误判成立到 0，但成立的漏掉四成到七成。针对性的话要写在带标记的那条证据旁边，不写在题目里。
- 一题一次请求：贵 2.3 倍，硬门槛不变好。
- 摘录截短或只取结尾：更差。
- `typesafe/jev-1.14` 与 `jev-1.13`：便宜一半，误判成立翻倍。

## 容易错的地方

- 评测台从 `dist` 读 `goal-contract`。改了打包函数先在 `packages/goal/goal-contract` 下 `pnpm run build`，否则量的是旧的。
- `--offline` 时有一个请求没存过答复，整次运行失败。这通常说明打包的输出变了：先确认是不是有意的。
- 离线重跑一个已有名字的实验会改写它的 `report.json`。要比新旧，换一个名字。
- 守则那道题「违反」不过线，哪个选项概率最高就读哪个。读 `wrong` 里「守住了说成违反」的条目时先看概率。
- 交给判定器的材料里没有的事实，它不会知道。判据提到「今天」「现在」而材料里没有时间，就一定判不准。
