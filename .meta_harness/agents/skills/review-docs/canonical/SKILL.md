# 文档变更评审

范围是本次候选里的正式文档，以及这次会话已经定下来、应当写入正式文档的设计。正式文档是产品正文、`docs/` 和随包文档里这次任务拥有的位置。任务 `tmp/` 不是正式落点。

开出 PR 后，父会话发现候选含正式文档变更时主动加载本技能并派发，不等用户点名。没有这类变更时写没有文档变更并停止。

派只读子代理。各面可以交给一个子代理，也可以分开派。

落盘遗漏：对照已定设计，列出应当写入正式文档、但候选里没有的点。写明该落的路径。父会话在简报里列出本次会话中被更正过的裁定，以及每条被取代的旧说法；评审按更正后的裁定对照。

表达：按 `pstack:deslop`、`pstack:unslop` 和本仓库 `asd-ste100` 看变更后的正文。标出把过程、会话或草稿状态写成了给后来读者的规范的句子。这一项只列问题，不改写。

断链：在候选工作树运行 `pnpm run check:docs`。改了设计区时再运行 `pnpm run check:design`。失败的链接和锚点原样列入。命令失败时交回命令和输出。

下层与上层：上层是已接受的产品正文、项目要求、架构和领域正文。下层是更具体的说明和随包文档。列出下层与上层已接受承诺相矛盾的两处原文。候选里还带着简报所列旧说法的地方，也逐处标出。没有矛盾时写没有发现。

图：列出有必要补的图和建议补的图。每条写明放在哪一节、图要说明什么关系。UML 只在它能降低理解难度时建议。这一项只列建议，不在评审里改图。

各面分开交回。没有发现时写没有发现，并写清看过的路径。交付边界和验收标准归 `review-delivery`。代码结构归 `review-code`。
