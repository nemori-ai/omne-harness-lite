# 卡的推进循环

一张卡从第一个切片到候选固定的全过程。规则归 `docs/engineering/quality.md`（风险级别、升级阶梯）、`docs/engineering/integration.md`（准入、双基线）、`docs/development.md`「按改动选择检查」（门禁命令）、`CONTRIBUTING.md`（署名、PR）。本页只给顺序、产物与门槛。反复出现的失误与防范归 `.meta_harness/human/delivery-pitfalls.md`，下面用 P 编号引用。

## 阶段与门槛

| 阶段 | 产物 | 出口门槛 | 适用规则 |
| --- | --- | --- | --- |
| 实施 | 写者交回的改动、命令、退出码与未覆盖项 | 改动在写范围内 | P1、P8、P14 |
| 验证 | 你在候选 head 上复跑功能门禁的日志 | 日志晚于最后一次改动，退出码 0，未覆盖范围已写明 | P1、P2、P13 |
| 评审 | 按风险选择的评审报告，存证据目录 | 每条阻断发现都有处置 | P4、P12、P16、P17 |
| 修复 | 集中修复的提交与复评结果 | 被点名的阻断已闭合，或已按阶梯升级 | P3 |
| 准入 | 最终 head 上的准入日志 | 退出 0，日志里的 head 等于最终 head | P11、P12、P13 |

## 切片的七步

`plan.md` 里每个切片按这七步走，每步写承担者：

1. 便宜档子代理补本切片的上下文，只补差额。
2. 写简报：卡与修订、分支、写范围、必要输入、适用的品味与防御条目、完成条件、停止条件。简报里的命令都要能在当前仓库运行（P8）。要求写者在最后一次改动后重跑全部门禁，并报告每份日志的时间与提交号（P1）。
3. 写者实施，交回改动、命令、退出码与未覆盖项。证据脚本每一步都核对成功（P14）。
4. 你复跑功能门禁，核对写范围。见[验证](#验证)。
5. 只有切片风险高时在这里评审。常规评审集中到实施完成后。见[评审](#评审)。
6. 有阻断时按[升级阶梯](#评审与修复的升级阶梯)修复。
7. 提交并推送，更新 `plan.md` 的勾选。署名与 trailer 按贡献指南（P5）。

切片之间：

- 不在线内的卡，目标分支前进时先 `git merge` 合入，再运行 `task-sync`，taskBase 不变。线内的卡在波内不合并联调轨道。
- 发现范围、依据或规格冲突时，只暂停依赖它的切片，回到卡级准备裁定。
- 结构度量、差分变异与品味逐条核对，在若干切片完成后集中跑一次，不在每个切片跑。
- 卡上只在关键进展、阻塞与出现可审阅候选时更新事实，不逐次贴日志。

## 验证

在候选 head 上自己复跑功能门禁，至少类型检查与 lint。写者报告通过时也要复跑。

1. 按 `docs/development.md`「按改动选择检查」选命令。
2. 每份日志记录命令、HEAD 提交号、起止时间与退出码（P13）。
3. 后台运行时把真实退出码传出来：`<命令> > "$log" 2>&1; rc=$?; echo "exit=$rc" >> "$log"; exit "$rc"`（P1）。
4. 读工具输出的实际范围。工具没覆盖本次改动时写「未覆盖」与替代证据（P2）。

## 评审

实现评审与独立验收按风险级别派发，级别定义归 `quality.md`「按风险选择接受实现的看法」：

| 级 | 实现评审者（`review-code`） | `qa` |
| --- | --- | --- |
| L0、L1 | 不派。例外：机器读数有实施者没交代的红项时，只看那几处 | 不派 |
| L2 | 有未交代的红项，或读完摘要仍说不清某处时派 | 有可运行交付面、验收标准写得成「触发 → 可观察结果」时派 |
| L3 | 派，它逐行读热点。你仍逐行读热点 | 派 |

文档评审与交付边界核对不受级别约束：候选含正式文档变更时开 PR 后跑 `review-docs`；任何候选开 PR 后、接受前跑 `review-delivery`。

力度：契约成员或跨成员的改动分面派发；中等的工具修复合成一次评审。给评审的简报不写「不要重新讨论裁定」（P4）。只读评审只在本工作树内搜索，手工变异在副本上改（P12）。评审之间可以并行，不与准入同时跑。子代理写不了报告文件时内联交回，缺字段不判 Pass（P16）。要加约束写进简报，不改带宿主资格摘要的角色提示（P17）。

## 修复

1. 全部阻断合成一轮集中修复，不逐条派发。
2. 修复后复跑受影响的功能门禁。
3. 只复评被点名的项。
4. 记录本轮的修订、阻断、类别、处置与验证。轮次连同接手前的一起数（P3）。

## 评审与修复的升级阶梯

轮次算法与升级顺序归 `quality.md`「三轮未收敛时升级结构诊断」。操作顺序：

| 轮 | 修复方 | 前置动作 |
| --- | --- | --- |
| 第 1、2 轮 | 实施时的档位；实施用经济档时升到中档。第 1 轮续用实施子代理，第 2 轮换新的 | 无 |
| 第 3 轮 | 顶档，或自己修 | 先逐条质疑评审判定：判得对吗，合理吗，本阶段必须闭合吗。站不住的记下理由，不计入未收敛 |
| 仍不收敛 | 停止局部修补 | 冻结当前修订与三轮记录，做结构诊断 |

线内的卡两轮未闭合即停下：卡不进批次，批次报告写明，进下一波队列。不在线内的卡按上表升级。阻断与上一轮同类时，第 3 轮整类处理（P3）。换评审者、分支或拆补丁都不重置轮次。

## 准入与评审的节奏

```mermaid
flowchart LR
  A["切片实施"] --> V["复跑功能门禁"]
  V --> R["按风险评审（只读，可并行）"]
  R --> F["集中修复一轮"]
  F --> V2["复跑受影响的门禁"]
  V2 --> AD["最终 head 上准入一次"]
  AD --> PR["开 PR，交接报告"]
```

- 先复跑门禁再派评审，便宜的问题不等到准入才暴露。
- 评审不与准入同时跑。准入期间不提交（P11）、不做占 CPU 的事（P12）；可以写交接报告与下一张卡的简报。
- 没有评审发现时，直接在被评审的 head 上准入。
- 准入失败先定向复现（`npx turbo run test:<层> --filter=<成员> --only --env-mode=strict -- <测试文件> -t <用例>`），不反复全量重跑。修复后在新的最终 head 上再跑一次。

## 子项的效率规则

范围小的子项不走完整阶段（P15）：沿用线级与父项的上下文，只补差额；发行、改钉子这类机械子项自己做，不派子代理、不做多面评审；同一份证据只在最终 head 上跑一次。
