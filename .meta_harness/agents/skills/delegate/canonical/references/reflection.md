# 反思

派发经验分两级写入：会话负责人交回本会话的台账增量，reduce 在放行之后提炼并写派发台账。里程碑完成后再做一次跨波反思。字段、汇总口径、写回门槛与命令见[台账口径](ledger.md)。

| 谁 | 时点 | 产出 | 挂点 |
| --- | --- | --- | --- |
| 会话负责人：线负责人、卡执行者，以及 reduce 自己派写者的部分 | 波段交回之前。不在 map-reduce 里的会话，在卡交付或一批切片收口时 | 本会话的台账增量与至多 3 条教训候选，附在交接报告里。这是交付的一部分 | `line`「交回」；`claim`「交回」 |
| reduce 负责人 | 本波放行之后（不是 VERIFY_WAVE 之后、放行之前） | 提炼后写 `ledger.json` | `integrate`「收口一波」 |
| 里程碑负责人 | 里程碑完成后一次 | 各类别跨波计数的变化表；对 `dispatch-policy.json` 的收紧提案；通用教训的改动提案 | `integrate`「收口一波」末步 |

## 会话负责人

1. 核对本会话的全部流水：`ledger.py check --flows <文件…>` 退出 0。
2. 汇总增量：`ledger.py aggregate --flows <文件…> --batch <批次 ID> --out <增量文件>`。核对 `excluded` 列出的行。把缺的验收报告贴到卡评论后，可以重跑。
3. 写至多 3 条教训候选。每条写现象、证据链接与建议去处：
   - 属于本线的教训，写进本线的 `constraints.md`。
   - 属于项目的教训，写进交接报告「给集成节点的提示」。
   - 反复违反的规则，提议改成结构手段（P7）。
   - 新的失误，提议写进 `.meta_harness/human/delivery-pitfalls.md`。
4. 把增量文件的内容与教训候选附在交接报告第 4 节。增量文件大时贴摘要，并写明原件位置与 sha256。附在哪张卡的交接报告、交回记录怎样给链接，见 `docs/engineering/integration.md`「线会话记录」。
5. 不写 `ledger.json`。

不在 map-reduce 里的单卡会话同样附交接报告，由下一次 reduce 或里程碑反思收录。

- 完成判据：交接报告第 4 节有本会话的台账增量（或摘要、位置与 sha256）与教训候选。`check` 与 `aggregate` 都退出 0。

## reduce 负责人

1. 收齐本波各会话交接报告里的增量，加上 reduce 自己派写者那部分流水的增量。
2. 按批次 ID 去重。逐条核对台账口径的「写回门槛」。
3. 合入并核对：`ledger.py apply --ledger <ledger.json> --increment <文件…>`，然后 `ledger.py check --ledger <ledger.json>`。
4. 提交，作为下一波联调轨道上的第一个提交。提交信息列出全部批次 ID。这个提交随下一波候选接受整波检查。里程碑最后一波没有下一波，经 gate 单独开 PR。
5. 教训候选按去处转交。通用教训交负责人。规则与技能的改动仍由负责人接受。

- 完成判据：`apply` 与 `check --ledger` 都退出 0。提交存在，提交信息列出全部批次 ID。重放同一批次时，台账字节不变。

## 里程碑反思

1. 比较各类别跨波的计数。
2. 列出样本达到 5 的格子。样本不到 5 的格子写「n 次里成 k 次」。
3. 起草收紧提案。每条写支持与反驳的格子与批次 ID。提案交负责人接受。接受之后才改 `dispatch-policy.json` 并升 `version`。
4. 通用教训可以按 pstack `reflect` 的流程整理。输入换成派发流水与验收报告的摘要，改动交项目的维护入口，由负责人接受。差异见 `docs/engineering/skills.md`「派发与编排」。

- 完成判据：变化表与收紧提案已交负责人。提案每条都引用格子与批次 ID。

P 编号指 `.meta_harness/human/delivery-pitfalls.md` 的失误条目。
