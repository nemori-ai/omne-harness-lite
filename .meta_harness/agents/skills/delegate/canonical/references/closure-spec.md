# 闭包规格

developer 的派发模板是 `.meta_harness/agents/roles/developer-task.md`，闭包规格按它的十二个字段写。本页只给它没有的补充节、字段的固定写法和映射表。

## 文件形状

简报检查 `brief-check` 按下面的固定写法解析闭包规格。写法不符时，它报错误。

- 十二个二级标题，名字与 `developer-task.md`「项目」列逐字相同：身份与位置、模型与推理强度、目标边界、验收清单、实施规格、性质及证据义务、施工计划、自主范围与动作授权、工作树与协调、方法与知识入口、当前认知、返回与恢复。不适用的字段写「不适用：<一句理由>」，或写一条指针。
- 三个补充二级标题：`## 已知会受影响的现有用例`、`## 停止条件`、`## 追加记录`。
- 「身份与位置」下有六个固定行：`- 闭包：<ID>`、`- 卡与修订：#<号> r<修订>`、`- 工作树：<绝对路径>`、`- 分支：<名>`、`- 基线：<40 位提交号>`、`- 清晰度：定|界|探`。清晰度的判法见[台账口径](ledger.md)「清晰度判法」。
- 「目标边界」下有两个三级标题：
  - `### 写范围`：每行写 ``- `<仓库相对路径>`（新建）? — <推出依据：被谁调用、谁读它>``。只有新建的文件带「（新建）」。
  - `### 排除的调用方`（可以为空）：每行写 ``- `<路径>` — <不改的理由>；停止条件：<需要改它时停下交回>``。
- 「方法与知识入口」的第一行是 `- 先读：<writer-conventions.md 的绝对路径>`。
- 「验收清单」每条写命令、预期与具名变异，变异写成 `变异：<改哪一处> → <哪条用例变红>`。有慢层时写明层与 `timeout`。改动含代码时列 `pnpm run lint:rules`。写明失败时先在基线上复跑同一检查。
- 「实施规格」可以有 `### 命名账本`：本闭包涉及的成员名、交换表示、对外字段与事件名。写不出的名字由派发者先定，不留给写者「报回」。否则写者每轮都正确地停在同一类缺口上，返工的是规格。
- 「追加记录」每条写 `- <UTC 时间> <原因>：<要求>`。

## 补充节的写法

- **已知会受影响的现有用例。**列出派发者读代码时已知会变红的用例，写明哪些断言要改写。简报明确要求的改写不算放宽断言。
- **停止条件。**只写本闭包特有的条件。通用的停止与上报归 `developer-contract.md`「必须上报的情形」，这里不重写。单个闭包的预算（例如「同一问题连试三种做法都不行就停」）需要时写在这里。
- **追加记录。**派发后的每条要求先写在这里，再发给写者。验收按原规格加追加记录判断。

本闭包要禁止「顺手清理所改文件」时，写进「目标边界」的不在范围内一项。没有写时，按 `developer-contract.md`「自主实施与协作」执行。
