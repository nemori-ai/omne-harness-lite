# 派发子代理

本技能给派发者十二步：每一步的动作、完成判据和依据。派发者是把一次写入、评审或验收交给子代理的主代理，任何会话都可能是派发者。

规则归下列拥有者，本技能只给顺序、产物与门槛，不另立规则：

- 派发者的义务 D1～D8 与合回：`docs/engineering/workflow.md`「派发子代理的契约」。下文写「D3」即指该节的 D3。
- 上游方法的采用范围与项目差异：`docs/engineering/skills.md`「派发与编排」。
- 写者的输入、停止、上报、提交权限与交付说明：`.meta_harness/agents/roles/developer-contract.md`。
- 修复轮次的计法与升级时点：`docs/engineering/quality.md`「三轮未收敛时升级结构诊断」。
- 模型钉值、档位规则与两种宿主的传值机制：`.meta_harness/agents/roles/README.md`「模型配置与本次派发」与 `dispatch-policy.json`。

## 何时不派

下面两类工作由派发者自己做，不派子代理：

- 几次工具调用能做完的工作，或目标已知的查找。
- 工作量不大、自己顺手能做完的工作。主会话连续工作时有上下文缓存，成本低。新子代理要重新写入缓存，总成本可能更高。

决定派发之后，再按下面的步骤做。

## 贯穿各步的六句话

- **先推出写范围，再写别的。**写范围从调用方与消费方推出，不从印象写出。
- **指针，不内联。**上游正文、拥有者正文与共用约定只给路径与小节名。
- **停下不是失败。**写者遇到停止条件时按约定交回，规格要给出这条出路。
- **读 diff，不转述。**子代理的交回是证据，不是接受。
- **验收者不是写者。**
- **追加留痕。**派发后的每条要求都写进闭包规格。

## 步骤

### 1 定框

1. 写下完成谓词、要交回的产物和形状（分区、竞速或混合）。
2. 在本会话已有的进度记录里建闭包表。卡执行者写在 `plan.md` 进度总览里。线会话写在 `state.md`「本波进度」之后。没有这两份记录的会话（reduce、普通会话）写在任务 tmp 的 `plan.md` 里。格式按 `claim` 技能 `references/plan-template.md`「进度更新」第 4 部分。
3. 建派发流水 `tmp/<任务>/delegate/flow.jsonl`。`<任务>` 是 `issue-<号>`、`line-<线>` 或会话自己的任务目录。

闭包表是恢复的入口。上下文压缩或会话重启后，先重新加载本技能，读闭包表，再用工作树事实核对每个在途闭包。

- 完成判据：闭包表与流水文件都存在。
- 依据：`swarm`「Phase A: Frame」；`poteto-mode`「Subagents」。

### 2 切闭包

1. 先切工单。每个工单写端到端行为与阻塞边，不写路径。
2. 再把每个工单落成闭包：一个写者、一组互不相交的写范围、一个基线。
3. 先推出写范围，再写别的。在基线上从要改的符号或文件出发，用 `git grep -n -w <符号> <基线>` 找调用方与导入方，再查读取它的测试与文档。要改的路径放进写范围，每个路径记下推出依据。不改的调用方记下理由与停止条件（D1）。
4. 把两个闭包判为串行之前，点名它们争用的文件、类型或资源。点不出来，就并行。

- 完成判据：每个闭包有路径级写范围与推出记录。闭包之间写范围不相交。依赖边已写明。
- 依据：`to-tickets`「Draft vertical slices」；`implement-spec`「Steps」第 1、2 步（两者都读 `skills.md`「派发与编排」钉住的文件）；D1。

### 3 写规格

1. 按 `roles/developer-task.md` 的十二个字段写闭包规格，再加[闭包规格的补充节与固定写法](references/closure-spec.md)。评审者与验收者的简报按下文「评审派发」写。
2. 指针，不内联。「方法与知识入口」第一行给出[写者共用约定](references/writer-conventions.md)的绝对路径。
3. 按[台账口径](references/ledger.md)「清晰度判法」判定清晰度（定、界、探），写进「身份与位置」。
4. 规格可能让写者交回待定项时，要求写者按写者共用约定「交回格式」逐项分类。
5. 运行简报检查，处理每一条警告：把调用方放进写范围，或在「排除的调用方」写理由与停止条件。

```sh
node --experimental-strip-types tools/dev-flow/src/delegate/brief-check-cli.ts --spec <闭包规格.md> --base <基线>
```

- 完成判据：简报检查退出 0。清晰度已写。
- 依据：`writing-for-agents`「Context pointers」「Steps and completion criteria」；D1、D3。

### 4 选模型

1. 用 `render_pair.py --resolve` 取策略默认的模型与档位。命令、规则与两种宿主的传值机制见 `roles/README.md`「模型配置与本次派发」。
2. 任务命中 `top_risks` 时，按策略用顶档。
3. 档位拿不准时，往强的方向上调一档。
4. 写者、评审者与验收者用策略给出的模型，不用 Haiku。Haiku 只用于纯读的仓库调研与上下文地图汇总（负责人 2026-10-30 裁定，见 #960 卡正文「决定与剩余责任」）。
5. 可以读派发台账里本类别的计数作参考。样本少于 5 时，只写「n 次里成 k 次」。台账目前只积累计数，不据它改默认档位。

- 完成判据：闭包规格「模型与推理强度」已写下 requested 模型与档位、`policy_version`、角色源树哈希、宿主与版本，以及一句选择理由。第 12 步把这些值原样写进流水。
- 依据：D6。

### 5 备环境

1. 用一条命令建出全部闭包工作树，装依赖、生成投影、构建被测成员：

   ```sh
   node --experimental-strip-types tools/dev-flow/src/integration/worktree-cli.ts prepare-closures \
     --base <提交> --closure <名称>:<分支> [--closure <名称>:<分支> ...] [--build <turbo 过滤器> ...]
   ```

   命令失败时，按输出的 `resume` 重跑同一条命令。
2. 借用别的工作树里的工具、共用克隆或运行名额之前，按 D8 确认没有写者，把核对结果记进闭包表。
3. 本机特有的环境写法（shell、编码、包索引）写进闭包规格「工作树与协调」。宿主与工具的坑见 `claim` 技能 `references/known-issues.md`。

- 完成判据：每个闭包的 `<树>/tmp/closures/<名称>/ready.json` 存在，且各步成功。借用对象的写者核对已记进闭包表。
- 依据：D2、D8。

### 6 扇出

1. 用一条消息发出全部独立闭包。
2. 写、评审、验收按项目角色派（`roles/README.md`）。只读调查可以用 `general-purpose` 或 `Explore`。
3. 默认在后台运行。下一步依赖结果、且前台没有别的工作时，在前台运行。
4. 派发者与它派的子代理共用宿主的一个限流池。进入无人值守的时段之前，少派并行。做法见 `integrate` 技能「监督：两条等待一直挂着」中限流池一段。

- 完成判据：闭包表每一行的状态都是「进行中」。
- 依据：`swarm`「Phase B: Fan out」；`implement-spec`「Steps」第 4 步。

### 7 等待与追加

1. 等完成通知，不轮询。线会话等自己派的子代理时，按 `line` 技能「等待」前台阻塞。等的同时推进不依赖它的工作。
2. 要改变正在跑的子代理的做法时，先看它在做什么（日志、进程、工作树）。它还在跑长任务，追加消息要等它下一次调用工具才送达：需要立刻生效就停掉它，自己接手或带完整范围重派；它已经在收尾，就让它做完。
3. 追加留痕。每条追加要求先写进该闭包规格的「追加记录」，再发出。
4. 选续用还是新开：
   - 同一闭包的追加与原范围内的补做，可以续用原写者。
   - 只读评审同一轮内的追问，可以续用原评审者。
   - 新一轮修复、换人与升级，一律新开子代理。新简报带上原规格、追加记录与上一轮报告。
5. 子代理中途停下、没有交回时（例如宿主返回 429），工作树里通常留着它未提交的改动和日志。读 `git status`、`git diff --stat` 与日志，判断它做到哪一步。写接续简报：原规格、已有改动、剩下的失败与你的推断。新开子代理接着做，保留它的改动（P18）。再次限流时，可以在角色源允许的范围内换模型，并把这次偏离记进闭包表。
5. 完成通知只表示通知已送达。用工作树事实核对：分支头、提交与日志。

- 完成判据：每条追加都在闭包规格里留痕。闭包表的追加数已更新。
- 依据：`poteto-mode`「Subagents」；D7。

### 8 汇总

1. 读 diff，不转述。读每个闭包的交回与 diff。
2. 运行 `git diff --name-only <基线>..<闭包分支>`，核对改动都在写范围内。
3. 写一张结果表：闭包、结论、越界核对结果、未覆盖项。

- 完成判据：每个闭包都有结果、越界核对结果与未覆盖项。
- 依据：`swarm`「Phase C: Aggregate」。

### 9 独立验收

1. 按 `quality.md`「按风险选择接受实现的看法」决定派 qa、派实现评审，还是由派发者在写者分支头复跑验收命令。
2. 验收者不是写者。简报按下文「评审派发」写。
3. 逐条判定验收清单。验收失败时按 D4 先在基线上复跑同一检查。
4. 每条缺陷标出归属：写者、规格或环境（D5）。
5. 验收报告贴卡评论。只留在 tmp 的报告进不了派发台账。
6. 下一轮之前按 `quality.md`「够了就收口」判断：核心保证已有证据守住时，剩余边角写成已知限制，不再派验收。

- 完成判据：每条验收都有结论。每条缺陷都有归属。报告有可引用的链接。
- 依据：D4、D5。

### 10 升级

1. 轮次按 `quality.md`「三轮未收敛时升级结构诊断」计。
2. 归属为规格的阻断按 `quality.md` 同一节处理：先修规格，在「追加记录」记一条。
3. 到升级时点，按 D6 依起点档位选接手或重做：
   - 接手：新写者拿到原规格、追加记录、历次验收报告与原分支。
   - 重做：从基线新开分支与工作树。原分支只作对照，不合回。
4. 强模型到第三轮仍有阻断时，按 `quality.md` 冻结当前修订，做结构诊断。线内的卡另按 `claim` 技能 `references/card-loop.md`「评审与修复的升级阶梯」表后第一条处理。

- 完成判据：流水的 `escalation` 字段写下目标模型与档位、接手或重做、理由与触发报告的链接。卡评论有一段摘要。
- 依据：D5、D6；`quality.md`。

### 11 合回

1. 按 `workflow.md`「合回由派发者完成」从写者的本地分支合回：同一仓库的工作树共用引用，直接合并写者的分支。
2. 在写者分支头复跑写者门禁与 `pnpm run lint:rules`。`lint:rules` 拒绝 `Co-Authored-By` 这类作者式署名，合回之后再发现只能改写历史。
3. 合并到卡分支。写者提交的 `Agent-Role` 是写者的角色名（如 `developer`）。派发者的合并提交写 `Agent-Role: main`（`CONTRIBUTING.md`「形成可审阅的交付」）。
4. 把闭包表的状态改为「已合回 <提交>」。
5. 按 `workflow.md`「工作树清理条件」用 `worktree-cli.ts remove` 清理闭包工作树。

- 完成判据：复跑日志晚于写者最后一次提交，且退出 0。合并提交存在。闭包表状态为「已合回 <提交>」。
- 依据：`workflow.md`「合回由派发者完成」。

### 12 记流水与反思

1. 每次独立验收后，在 `flow.jsonl` 追加一行。字段见[台账口径](references/ledger.md)「流水字段」。
2. 运行流水核对，命令见台账口径「命令」。
3. 到反思时点，按[反思](references/reflection.md)做。反思时点是：卡交付或波段交回之前、reduce 放行之后、里程碑完成之后。

- 完成判据：`ledger.py check --flows <文件>` 退出 0。到了反思时点时，反思页规定的产出已交出。
- 依据：`docs/engineering/integration.md`「线会话记录」（台账增量附在交接报告第 4 节）。

## 评审派发

本节给 `review-code`、`review-docs`、`review-delivery` 与 qa 共用。各面的判据仍归各自的技能与角色。

- 模型按第 4 步选。
- 简报给规格、验收标准与基线，只给证据路径，不给派发者的结论（P4）。各类评审另给的材料按下表：

  | 评审对象 | 简报另给 |
  | --- | --- |
  | 交付边界（`review-delivery`） | 调度者的裁定，用来列出与卡文冲突的项 |
  | 设计选择 | 不给裁定 |
  | 代码（`review-code`）与 qa | 不另给，只有规格、验收标准与基线 |

- 只读评审只在本工作树内搜索。手工变异在副本上改（P12）。
- 子代理写不了报告文件时，内联交回。缺字段的报告不判 Pass（P16）。
- 要加约束时，写进简报。带宿主资格摘要的角色提示保持原样（P17）。
- 收齐各面报告后，去重，合成一份。

P 编号指 `.meta_harness/human/delivery-pitfalls.md` 的失误条目。
