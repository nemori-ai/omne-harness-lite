# 集成

协作规则归 `docs/engineering/integration.md`「集成节点的清单」，其中「线会话记录」「失败处理」「等待监督」与本技能直接相关。Reduce 的阶段、阶段内的核对、收口顺序与提问前三问归 `docs/engineering/map-reduce-states.md` 第 3 节，redo 与接管处置归第 4.1 节。首次开工和恢复时先读这些节。工程规则、接受与权限沿拥有者，本技能不另授权限。

本技能给 SERVE 与 VERIFY_WAVE 的动作顺序，以及 RELEASE_WAVE 的入口。建卡、首次消息与发 delta 按 `dispatch`。反复出现的失误与防范归 `.meta_harness/human/delivery-pitfalls.md`，下面用 P 编号引用。

## 监督：两条等待一直挂着

波内挂两条等待，命令用法归 `tools/dev-flow/src/delivery/README.md`「事件等待」：

```sh
node --experimental-strip-types tools/dev-flow/src/delivery/wait-cli.ts pr-ready --base <联调轨道> [--ignore <pr>@<处理时的完整 head> ...] --since <ISO 时间或 delivery id>
node --experimental-strip-types tools/dev-flow/src/delivery/wait-cli.ts any --comment <线父卡>:line-handoff [--comment <线父卡>:line-handoff ...] --since <ISO 时间或 delivery id>
```

- 每条参加线写一个 `--comment`。
- 两条等待同时挂着的方法取决于宿主：
  - Claude Code：两条等待命令都作为宿主跟踪的后台任务运行，同样带 `--timeout`。任务结束时，宿主唤醒会话。
  - 宿主不能唤醒已结束的回合时（例如 Codex）：能合并的条件合进一条前台阻塞的 `wait-cli any`。`any` 不接受 `pr-ready`，所以 `pr-ready` 与交回记录的等待轮流前台阻塞。每次都带有界的 `--timeout`。退出 3 时先按「等待监督」第 5 步读回，再换另一条等待，各自的 `--since` 不变。
  - 这条宿主差异只适用于 Reduce。线会话的等待一律前台阻塞，没有例外。
- 命中只是唤醒。唤醒后读回全部参加线父卡的交回记录与待处理的提升 PR，按已处理集合去重后逐条处理，再重挂。读回、去重与重挂起点归 `docs/engineering/integration.md`「等待监督」。处理一项时，另一条等待保持挂起。
- 本波已处理的每个提升 PR 都累加一条 `--ignore <pr>@<处理时的 head>`，再重挂 `pr-ready`。
- 等待命中只表示有事件。Issue 关闭或评论命中不代表整波已放行。
- 等待命令退出 2 时诊断并恢复，恢复后先对账，不报告空队列成功。
- 等另一个会话在某张卡上贴特定评论时，先看那张卡已有的评论用什么标记，等待就用这个标记。也可以在要求里写「沿用你已用的标记」。对方可能在读到你的要求之前，已经用自己的标记贴出了评论。这时只等你新指定的标记，就会错过它。
- Reduce 自己启动的 gate 运行与审批、子代理、检查进程和约定期限由 Reduce 自己观察。审批交有权者，不自动批准。期限到达时核对事实，再决定等待、重排或取消。沉默保持 unknown，不判线失联。
- 各线在波中还有两类事要 Reduce 处理（PanQiWei 2026-11-01 决定）。线父分支进线轨道的 PR 等 gate 审批时，Reduce 代 PanQiWei 确认。线把线包「需 Reduce 批复」一节里设计点的候选与评审报告贴到线父卡上，Reduce 监视线父卡评论并批复，不另建卡。两者都不是波中问答，线在等待期间推进不依赖它的闭包。
- 波内维护一份总控页，数据与命令按 [总控页](references/cockpit.md)。它只收第三层请求，回答「谁在等我、下一步做什么」；线自己的进度用线的进展页，不并进总控页。
- Reduce 自己派的长跑子代理按 `delegate`「等待与追加」巡检：开始时间写进闭包表，跑过 10 分钟就看工作树事实。状态页把在跑清单与开始时间放在一眼能看到的位置。
- Reduce 与它派的子代理共用宿主的一个限流池。Reduce 撞上限流时，会话停在原地，直到被唤醒或有人输入。进入无人值守的时段之前：
  1. 给 Reduce 自己留额度，例如少派并行的子代理。
  2. 用宿主的定时唤醒挂一个兜底唤醒，Claude Code 用 ScheduleWakeup 或 CronCreate。醒来后按「恢复」重读持久事实，重挂两条等待。
- Reduce 自己撞上 429 时，按「恢复」处理，不当成没有发生。
- 负责人在场并盯着额度时，可以放开并行。

## 处理一条交回

先读交回记录的结果，再读线父卡上的本波交接报告，以及它列出的本波其他卡的证据。

### ready：接收线轨道提升

一次接管一个提升 PR。先核对线父分支进线轨道的那次准入与 gate 合入证据，以及冻结 head。线内工作不逐个准入，规则见 `docs/engineering/integration.md`「线父分支」。本波另有几张卡时，父分支进线轨道的那一个 PR 逐张列出它们与线父卡的 attempt，`ri-notes` 读取一个 PR 声明的多张卡，接受仍逐卡进行，见同页「本波有几张卡」。保存来源原 head、候选 head、目标 head、targetBase 和 merge 链。

1. 核对 Line 已停写。线父分支进线轨道时，已在合并结果上跑过一次准入。RI 合并结果的树与那次准入时的树相同（期间 mainline 没有前进）时，复用那次准入，下面第 3 步不再跑准入，比对方法见 `docs/engineering/integration.md`「树相同时复用准入」。树不同时，在 RI 合并结果上跑一次准入。在具有 Reduce 自己 binding 的隔离候选上处理同步和冲突；需要修正来源轨道时，由 Reduce 按获准路线经 gate 写回，再读回提升源头。线父卡本波的 attempt 绑定在线的父分支工作树上，不承担这项修复。
2. 完成跨域修改与消费者迁移。Reduce 负责交回后的全部集成冲突、跨域修改、消费者迁移和改后验证，不把集成缺陷退回线会话。自己派写者时按 `delegate`。
3. 验证：用 `node --experimental-strip-types tools/dev-flow/src/integration/worktree-cli.ts projections --tree <树>` 生成宿主投影，它最后运行 `pnpm run check:agents`；再运行 `pnpm run admission`（等于 `OMNE_ADMISSION=1 pnpm run check`，另写准入日志）。全机准入一次一个，由 `scripts/with-test-slot.mjs` 的运行名额排队保证；准入命令自动排队，不需要人工互斥。名额的覆盖缺口由 L-ENG 核实。准入只有一步失败时，修复后用 `pnpm run admission --resume-from <H1>` 补跑，H1 是失败的那个头，不整次重跑。规则见 `docs/engineering/integration.md`「增量准入」。候选或基线变动后，重做受影响的验证与评审。准入是一条全机串行的队列：
   - 入队前在该树离线装依赖、刷新索引、修好 CRLF 工作副本，再跑轻量预检（`acceptance:lock`、`check:docs`、`lint:oxlint`、`format:check`）。工具链的 `pnpm run preflight` 合入之后用它。
   - 只有少数用例因超时或负载失败时，先确认没有并发负载，只重跑失败用例所在的文件，再补跑没有开始的轻步骤。全过记为通过，确认说明写明原准入记录与定向重跑。
   - 准入期间不派会跑测试的子代理。
   - 合入目标分支按批次顺序串行。合入前的准备彼此独立：合并目标分支、`task-sync`、证据起草、语义复核草稿与 qa 干净重跑。等关键路径时把它们一次扇出，做法见 `delegate`「扇出」。
4. gate：按既有权限发 gate，绑定精确的 workflow、ref、head、runId 与 runAttempt。需要审批时交有权者。线父分支进线轨道时，线负责人已对线父卡本波的 attempt 与本波其他卡写入 `integrating`。提升阶段记录实际 PR 与 gate 事实；接受决定读回后再运行 `board-cli.ts accepted`。规则归 `agent-delivery.md`「4. 推进和更新状态」。
5. 读回合入：PR 实际合入，且合并提交在目标轨道可达，才记合入。gate 成功、PR 关闭或审批完成都不能单独记合入。合入被回退时，本批次重新未解决。

收件时，评审与 qa 报告以卡评论为准。只放在任务 tmp 的报告不进台账增量，落盘与贴卡的做法见 `delegate`「独立验收」。

评审或审计带出的新问题不属于本批次时，不把它并进正在集成的批次或正在推进的卡。先按 `agent-delivery.md`「1. 整理需求并定位已有卡」查有没有同一结果的卡；没有就另立小卡，按 `dispatch` 第 3、5 节求交并登记，在单独的分支上并行交付（P23）。

### 几张连续的卡合成一个批次

这一节只适用于 Reduce 连续推进且直接进入联调轨道的 `integration` 卡。线内工作的批次是线父分支，由线负责人按 `docs/engineering/integration.md`「线父分支」处理。Reduce 是几张连续的这类卡的唯一写者时，按这一节合并它们，规则见 `docs/engineering/integration.md`「卡进入哪条轨道」的例外。

1. 每张卡照常开工、实现，判据证据贴在各自的卡上。
2. 从联调轨道头切一条个人批次分支，按依赖顺序把各卡的分支合进来，在本地解决冲突。
3. 在批次头上按「ready：接收线轨道提升」第 3 步验证，准入只跑一次。
4. 开一个个人批次 PR，手写「所含的卡」与「契约变化」，逐张列出。个人批次不使用 ri-notes。按 ready 第 4、5 步只走一次 gate，读回合入。
5. 接受逐卡进行。

### blocked 或 failed：redo 或接管

核对线已停写，读清已完成部分与剩余工作，然后选一种处置：

- redo：更正输入，按 `dispatch` 第 5 节在线父卡上登记新 attempt，再按 `dispatch`「放行」一节的发布方法发 redo delta。redo 不推进波号。
- 接管：Reduce 自己完成剩余工作。线会话继续等待下一条 delta。自己派写者时按 `delegate`。

处置规则（不另写处置记录、处置不等于已解决）见 `map-reduce-states.md` 4.1。处理一条交回时，其他事件继续落在等待里。

接管需要的写范围超出该卡 binding 时，准入的 change-scope 只按 binding 的写范围判断，超出的改动照样被拒绝。这时先换 attempt，再换树（P21）：

1. 按 `dispatch` 第 5 节为该卡登记新 attempt。spec 写新的 `writeScope`，分支沿用原分支（`swap` 只在同一分支上换树）。spec 的 `basis` 是授权依据 URL 的列表，其中要有能覆盖新写范围的授权，例如人给本里程碑的授权评论。旧 attempt 的派发评论只授权旧的写范围，不够。需要写明接管对象、写权转移、新写范围与剩余责任时，在卡上发一条评论，把它的 URL 一并列入。这条评论不写「决定」列表字段（P24）。
2. 先 `post --dry-run`，再用 `scope-cli.ts` 把拟写的 binding 与本波其他 binding 求交，然后 `post` 与 `bind`。
3. 旧树先提交并推送。然后用 `worktree-cli.ts swap` 换一棵新树，不在旧树上再运行 `start`。`swap` 只复制旧树的 `tmp/issue-<N>/`，其他过程目录自己复制。命令归 `tools/dev-flow/src/integration/README.md`。
4. 在新树里用 `integration/cli.ts status` 读回新 attempt 与 `relation=current`。

### 用部分认可解开下游

一张卡的剩余部分要花很长时间，已完成部分可以入轨，而下游卡只依赖已完成部分时：

1. 先准入并合入已完成部分。
2. 由这张卡的有权接受者，或持有可核对授权的代笔者，按 `docs/engineering/delivery.md`「4. 接受、取消与重开」记一条 partial 决定，写明已认可范围与剩余责任。
3. 剩余部分在本波收口前做不完时，由有权者按 `map-reduce-states.md` 第 3 节的 `resolved` 显式移出本波，写明剩余责任。既没做完也没移出时，本波的 WaveReady 不成立，R(w) 不能收口。
4. 剩余部分在同一张卡上继续，全部完成后再接受并关闭。

下游卡的条件是否满足，仍按该条件自己的判据核对。部分认可不满足要求整卡结果的条件。

## 收口一波

1. 联调轨道上还有本里程碑以外的写者时（例如独立推进的工具线），开始整波检查之前，请对方暂停往联调轨道合入。在与对方约定的协调卡（对方的线父卡或专门的协调 Issue）上发请求。卡上已有往来标记时沿用它；还没有时，在请求里写明请对方回复用的标记。等待对方确认时用事件等待，不轮询。没有得到确认就开始检查时，放行前再读回联调轨道头，核对它仍等于 F。理由：整波检查的对象是联调轨道头，检查之后轨道头前进，候选就变了，旧证据失效，要回到监督重新检查（P22）。放行后按 `dispatch`「放行」第 6 步通知对方恢复合入。
2. 全部预期项有效解决后，在联调轨道头运行 `OMNE_ADMISSION=1 FULL=1 pnpm run check` 及里程碑联调命令，确定最终 F。F 与已通过这项检查的头树相同时不重跑：准入部分在那次全量准入所在的工作树里运行 `node --experimental-strip-types tools/test-runner/src/testing/cli.ts admission-evidence --for <F>` 核对；里程碑联调命令的结果用 `git rev-parse <提交>^{tree}` 比对。证据写法见 `docs/engineering/integration.md`「树相同时复用准入」。没有里程碑联调命令时报告「未运行」。任一未决项、未知写入、未解决失败或失效证据都阻止收口。
3. 检查失败或候选变化时回到监督，旧证据失效。
4. 整波检查通过后，按 `dispatch`「放行」一节建后继、给全部存续线发 delta、接受并读回 R(w)、关闭 R(w)。
5. 调整后一波预案时，按 `dispatch` 技能的 `references/wave-planning.md` 用本波实际耗时、集成负荷和新事实修正取舍。
6. 放行之后，按 `delegate`「反思」做 reduce 提炼并写 `ledger.json`，作为下一波联调轨道上的第一个提交。这个提交随下一波候选接受整波检查。里程碑最后一波没有下一波，经 gate 单独开 PR。每波的复盘按下面的顺序（PanQiWei 2026-11-01 定）：
   1. Reduce 复盘本波派发：流水、各线交回的台账增量与经验、反思。
   2. 经验写进仓库的技能、角色、文档与台账，经卡、准入与 gate 进入联调轨道。
   3. 各线轨道 FI 到这个头并读回。下一波线包与首次消息的技能来源 revision 写这个提交，线包的「本波经验摘要」写聚合后的要点。
   4. 下一波按最新经验派发。
7. 里程碑完成后，按 `delegate`「反思」做一次里程碑反思。

## 报 ETA 之前

报 ETA 或说「只能串行」之前，逐段给关键路径上的串行等待分类：是真依赖，还是习惯（P27）。真依赖按争用的文件切开，方法见 `dispatch` 技能的 `references/wave-planning.md`。

## 提问前三问

向人提任何设计或方案问题前，先按 `map-reduce-states.md`「提问前三问」逐问检查，包括第 3 问的各个核对项（P19）。其余自行决定并留简短依据。

三问也覆盖子代理交回的待定项清单：

- 简报要求子代理逐项分类待定项，格式见 `delegate` 写者共用约定（`writer-conventions.md`）的交回格式。
- 子代理交回的清单，Reduce 先逐项过三问，再给负责人看。

## 裁定更正与独立评审

人在波中更正一条裁定后，检索更正之前写成、还没有合入的草稿（P26）。派独立评审或顾问时，简报按 P4 写，不带自己的结论。评审派发的通用做法按 `delegate`「评审派发」。

## 恢复

上下文压缩后续接，也按恢复处理。先重新加载本技能，并核对它的目录是当前检出的投影，不是旧工作树里的副本。压缩后只剩摘要，技能正文会淡出。

恢复时从 GitHub 重读事实，不按会话记忆认定成功：

1. 读当前收口卡、各线父卡上本波的 attempt 与 binding、各线父卡上最后的 delta 与交回记录、联调轨道上开放的提升 PR、在途 gate 运行。再读人给本里程碑的授权评论，弄清哪些可以代接受、代确认 gate，哪些仍要问人。
2. 结果未知的写入、合入或发布先读回实际结果，再决定下一步。结果未知时不重复 POST 或 merge。
3. 从读回的事件重挂两条等待，再继续处理。
4. 有未合回的闭包时，读任务 tmp 进度记录里的闭包表。
5. 人请求停止时冻结新写入；STOPPED 不等于 DONE。

会话的目标文本（goal）只写完成条件，外加一个指向现行规则文件的路径。不把派发规则、并发上限、档位这类会变的规则抄进目标文本。抄进去的规则在负责人改了之后，仍会在每次打卡时重新注入旧版。

## 交给后继会话

工作改由另一个会话接续时（例如下一个里程碑换一个 Reduce 会话，或换一台机器），交给它一个交接包。交接包是一个能单独打包的目录，只带结论，不带推理过程和中间数。它包含：

- 「已做完、不要重做」表。
- 决定表，分问题、裁定、理由三栏。容易被重开的决定，再配一句「为什么是这个形状」。
- 负责人以后要做的事，按阶段排成提醒清单。后继会话到点提醒负责人。
- 术语表。

用脚本生成交接包，再用脚本核对其中的全部引用都在包内。最后派一个只拿到这个目录的新代理，按交接包里写的开工第 1 步走一遍，记下它卡住的地方并补齐。作者自己读，读不出包里缺了什么。
