# Plugin

## 它是什么

一份 Plugin 是一个目录，最上面一份清单 `plugin.json`。清单列出它的成员，每个成员写三样：放到哪个拓展点、哪个键，以及这一项是什么。

| 成员的写法 | 这一项是什么 | 例 |
| --- | --- | --- |
| `data` | 清单里的这份数据 | 整个应用的令牌、一个部位的样式、页面的次序 |
| `directory` | 包里的一个子目录 | 一个目录型的资产，例如一个 Skill |
| `module` 加 `export` | 包里一个文件的一个导出交回的东西 | 一个部位的画法、一种工具调用的卡片、一份协议 |

- **它是资产的一个类别。** 类别 `plugin`，定义放在点 `plugin.plugins` 上。从一个目录发布，和任何一份资产一样被持有、启用、禁用、移除。一个租户要装什么由它持有的推出，没有第二个地方记着装没装。
- **它是约束最少的那个类别，清单写什么就放什么。** 别的类别的一份定义是它自己那个点上的一项，内容由那个类别的领域读。一份 Plugin 的定义是「哪些项放到哪些点上」：成员可以落在别的点上，可以是另一类资产，也可以是不单独持有的东西，例如界面的令牌、样式与画法，一份对客户端开放的协议。
- **它不认识任何一个具体的类别。** 指向一个类别的点的成员，交给那个类别的正文契约判；Plugin 只把成员交过去，并把那一类说的话原样带回来。类别的只读面每次判的时候现问，不在登记时固化，所以后来才登记的类别，它的成员同样被判。有一个成员不合格或它的类别不可用，整份不发，原因指到那个成员。
- **读的一方分不出一份定义来自哪里。** 一份 Plugin 带着的定义，是那个类别的点上的一项：资产引用与版本是这份 Plugin 在持的那一版，`within` 是成员写的目录。读它的一方照读任何一份那一类的定义去读，只是读口只看得见那个子目录。
- **皮肤是收窄的一类，不是另一种东西。** 清单写明自己是皮肤、只有客户端一侧成员的一份 Plugin，在资产里是单独的类别 `skin`；清单、包、装载、换代都与 Plugin 相同。启用归资产，界面此刻用哪一套归客户端：皮肤的成员放在「租户之下、这一套」这一层，外壳发问时带上在用的那一套，所以各处一起换。
- **清单是数据。** 不运行一份 Plugin 的任何代码，就算得出它装上之后往哪些点上放哪些项。
- **「放」不在 Plugin 手里。** 成员只说放什么、放到哪。放的是装载方，只放清单里写过的。代码成员的导出交回「这一项的内容」，交给它的东西里没有放东西的口。
- **一份 Plugin 的贡献一起出现、一起退场。** 它在树上占一个自己的作用域，名字是 `plugin:<名字>@<版本>`。有一个成员放不上，这一份什么都不留下。
- **版本是内容的摘要。** 内容变了版本就变，同一个版本的内容永远相同。换了版本是新的一代：旧的一代留到新的一代有了结局。
- **装着的向要装的收敛。** 「要装什么」由来源按主体给出，装载方读到表就照状态表走一步。读不到表不等于表是空的：装着的不动。
- **两棵树各有一个装载方，用同一张状态表、同一个回路、同一个底。** 清单里分 `client` 与 `server` 两侧，各装各的。客户端的装载方经带身份的协议问服务端要装什么，把成员放到界面的点上。服务端每个租户一个回路、一份底的记录，一份 Plugin 是一个 fiber。
- **先起底，再补装。** 随应用构建的那一部分总是先起来。装的时候连着倒下到了上限，下一次不再装那几份，并说出停掉了哪几份。服务端也一样。
- **代码从不出示身份。** 它代哪个租户、以谁的名义，由它所在的通道定。它够得着的只有交到它手里的：服务端的代码只拿到口，口里绑着这次调用者的主体，口上只来往数据。
- **口是借来的，一次调用一开一关。** Plugin 在 `needs` 里写它要的口，装上时钉住。一次调用进来，用调用者的主体打开；处理函数返回或抛出，关上。哪些领域借什么口，由各领域自己往 `plugin.ports` 上放。

## 它不是什么

- 它不是运行着的东西。它是定义；装上之后由一个作用域（Cordis fiber）承载，那是它的活体，可以丢、可以重建。
- 它不是一个主体。它只在被调到的时候行事，用的是这次调用者的主体；没有被调到时，手里没有任何主体。
- 它不决定一个点收什么。成员放得上放不上、同一个键上两项听谁的，由那个点的规矩判。两份 Plugin 往同一个键上放，那个键上两份都不算数，这不是装失败。
- 一个点缺省就收它的条目。关着的点在规矩里写明理由，由登记表守。代码交回的东西怎样成为一项：点的拥有者写了专门的写法（放在 `plugin.guest-forms` 上）就用它，没写用通用写法；通用写法下服务端的函数拿不到口。
- 它不决定谁持有它、哪一份胜出。那归资产与规则；来源交给装载方的一组里，每个名字至多一份。
- 它的代码不拿整棵树。客户端的代码文件里不写任何包名，要用的共用库由宿主在调用时交进去，交给它的外壳只能切页、提示、读当前租户。服务端的代码只拿到 `{ ports }`，它所在的上下文里取不到任何受信名。
- 口不是通行证。装上不等于许可：经口的每次调用以调用者的名义进出借这个口的领域，由那个领域照自己的规矩判。
- 契约不是执行域的隔离。服务端的代码和服务在同一个进程里运行：它管得住老实的代码，管不住存心越界的代码，也管不住运行当中死循环、吃光内存。那归执行环境的受限执行域。
- 装失败不是系统倒下。那一份记原因并报出去，别的照常。画的时候抛出也不是装失败：那一处落回原来的画法。
- 清单里写不出作用域。成员算在谁的名下，由装载方照「是谁持有它、是谁要装它」打上。
- 客户端报给服务端的样子不是事实的权威。它是客户端那棵树的投影，客户端不在了，它报的就去掉。

## 拿它怎样量一个设计

1. 新加的一样东西，是往已有的点上放一项，还是要一个新的点？前者写成成员；后者先由点的拥有者声明这个点和它的规矩。
2. 这一项不运行代码就看得出来吗？能写成 `data` 就不写成 `module`。
3. 设计里有没有让 Plugin 的代码自己去放、自己去撤？有，就把「放」收回到清单与装载方。
4. 装到一半失败了，界面上、登记表上会不会留下半份？一份占一个作用域，撤就是撤这个作用域。
5. 它让应用或服务起不来的时候，人还进得去吗？进去之后看得出停掉了哪一份、知道怎样放开吗？
6. 一个租户装的东西，别的租户、没登录的人看得到吗？作用域是装载方打的，不是成员自己说的。一个租户挂的协议，别的租户调它，得到的答复和它不存在时一样吗？
7. 来源一时读不到，设计是把它当成「什么都不用装」吗？那会把装着的全卸掉。读不到就是读不到。
8. Plugin 的代码拿得到主体、存储、签发者或登记表服务吗？拿得到就错了：它只拿到口。
9. 口的方法上有「租户」这个参数，或来往的是对象、函数吗？有就错了：主体绑在口里，口上只来往数据，换到受限执行域时契约才不用改。
10. Plugin 能把一次调用的口存下来过后再用吗？能就错了：调用返回之后口答 `closed`。
11. 这个点的规矩写着开还是关？关的理由是那四类之一吗？它的函数会拿到主体或要用口时，拥有者写了专门的写法吗？写法有没有把主体交到代码手里？
12. 说「租户隔离」的时候，写明了它只对老实的 Plugin 成立吗？让不受信的租户装服务端的代码，要先有受限执行域。
13. 要给一类东西「同一时刻只用一份」，是不是想让资产为这一类多一条规则？那是让治理去定界面此刻用哪份。把它放成发问的作用域里的一段。
14. Plugin 的类别判定里出现了某个具体类别的名字或分支：错了。指向一个类别的点的成员，交给那个类别的正文契约判；后来才登记的类别同样被判，写死的分支答不了它。
15. 一个类别领域为「来自 Plugin 的定义」写了特殊分支：错了。它读到的是自己那个点上的一项，带 `within` 时只是读口看得见的是一个子目录。

## 现状

两棵树的装载方都只读点的规矩：一项交数据的点收数据成员，一项交函数的点收代码成员，类别的点收那一类的定义，关着的点都不收。装载方不认识任何具体的点。专门的写法有两份，各归点的拥有者：`access.protocols`（接入层）与 `tool.entry-sources`（Tool）。出借的口有通知的 `notifications` 与 Tool 的 `web`。客户端一侧不收目录成员。做到哪一步，以源码为准。
