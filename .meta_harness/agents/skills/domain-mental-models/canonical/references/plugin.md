# Plugin

## 它是什么

一份 Plugin 是一个目录，最上面一份清单 `plugin.json`。清单列出它的成员，每个成员写三样：放到哪个拓展点、哪个键，以及这一项是什么。

| 成员的写法 | 这一项是什么 | 例 |
| --- | --- | --- |
| `data` | 清单里的这份数据 | 整个应用的令牌、一个部位的样式、页面的次序 |
| `directory` | 包里的一个子目录 | 一个目录型的资产，例如一个 Skill |
| `module` 加 `export` | 包里一个文件的一个导出交回的东西 | 一个部位的画法、一种工具调用的卡片 |

- **清单是数据。** 不运行一份 Plugin 的任何代码，就算得出它装上之后往哪些点上放哪些项。
- **「放」不在 Plugin 手里。** 成员只说放什么、放到哪。放的是装载方，只放清单里写过的。代码成员的导出交回「这一项的内容」，交给它的外壳没有放东西的口。
- **一份 Plugin 的贡献一起出现、一起退场。** 它在树上占一个自己的作用域，名字是 `plugin:<名字>@<版本>`。有一个成员放不上，这一份什么都不留下。
- **版本是内容的摘要。** 内容变了版本就变，同一个版本的内容永远相同。换了版本是新的一代：旧的一代留到新的一代有了结局。
- **装着的向要装的收敛。** 「要装什么」由来源按主体给出，装载方读到表就照状态表走一步。读不到表不等于表是空的：装着的不动。
- **两棵树各有一个装载方。** 清单里分 `client` 与 `server` 两侧，各装各的。客户端的装载方经带身份的协议问服务端要装什么，把成员放到界面的点上。
- **先起底，再补装。** 随应用构建的那一部分总是先起来。装的时候连着倒下到了上限，下一次不再装那几份，并说出停掉了哪几份。

## 它不是什么

- 它不是运行着的东西。它是定义；装上之后由一个作用域（Cordis fiber）承载，那是它的活体，可以丢、可以重建。
- 它不决定一个点收什么。成员放得上放不上、同一个键上两项听谁的，由那个点的规矩判。两份 Plugin 往同一个键上放，那个键上两份都不算数，这不是装失败。
- 它不决定谁持有它、哪一份胜出。那归资产与规则；来源交给装载方的一组里，每个名字至多一份。
- 它的代码不拿整棵树。代码文件里不写任何包名，要用的共用库由宿主在调用时交进去；交给它的外壳只能切页、提示、读当前租户。
- 装失败不是系统倒下。那一份记原因并报出去，别的照常。画的时候抛出也不是装失败：那一处落回原来的画法。
- 清单里写不出作用域。成员算在谁的名下，由装载方照「是谁要装它」打上。
- 客户端报给服务端的样子不是事实的权威。它是客户端那棵树的投影，客户端不在了，它报的就去掉。

## 拿它怎样量一个设计

1. 新加的一样东西，是往已有的点上放一项，还是要一个新的点？前者写成成员；后者先由点的拥有者声明这个点和它的规矩。
2. 这一项不运行代码就看得出来吗？能写成 `data` 就不写成 `module`。
3. 设计里有没有让 Plugin 的代码自己去放、自己去撤？有，就把「放」收回到清单与装载方。
4. 装到一半失败了，界面上、登记表上会不会留下半份？一份占一个作用域，撤就是撤这个作用域。
5. 它让应用起不来的时候，人还进得去吗？进去之后看得出停掉了哪一份、知道怎样放开吗？
6. 一个租户装的东西，别的租户、没登录的人看得到吗？作用域是装载方打的，不是成员自己说的。
7. 来源一时读不到，设计是把它当成「什么都不用装」吗？那会把装着的全卸掉。读不到就是读不到。
