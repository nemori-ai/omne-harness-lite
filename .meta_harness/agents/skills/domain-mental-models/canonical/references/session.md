# Session 与会话日志

## 会话日志

**它是什么。** 一个会话的唯一事实源。它只增不改。这个会话里发生过什么，以它为准。

- 别的东西都是它的投影或缓存：列表里的标题、当前这一轮、界面上的对话。投影丢了，能从日志重算。
- Agent 的执行记录也在这同一份日志里，不是另一份。Agent 定义自己需要一份什么样的执行记录，Session 来提供。
- 所以任何一个运行着的对象没了都不要紧：Session 的实例、Agent 的实例、一次观察。重新起一个，从日志接着来。
- 它只有一个写入者：会话存储里的那一个，在存储的写线程里、一个存储事务里写条目、移修订号。同一个会话的两次提交只有一个后继。
- 把命令交给写入者的一方叫提交方，可以有几个：会话自己的命令；模型日志与工具日志的消费；Agent 执行日志的解释；Agent 日志提交自己的记录时，带上会话的命令一起提交。它们都不自己写日志。

**它不是什么。** 不是消息列表，也不是调试日志。它记的是事实：受理了什么输入，开了哪一轮，登记了哪次调用，哪次调用给了什么结果，这一轮怎样结束。

## Session

**它是什么。** 管一个会话的业务流程的领域。它回答的是「这份工作现在该怎样」：

- 这条输入收不收，排在哪。
- 开不开一轮，这一轮的推进资格交给谁。
- 取消、冻结、归档，会话处在生命周期的哪一段。
- 这一轮算不算结束了，结局是完成、失败还是被取消。

它拥有会话日志。日志里每一条事实都经它的写入者写进去，别的领域要留下事实，交一条会话命令给它。

- **受理流水线里有一步「解析这段话」，它是一个口，由命令领域来接。** Session 把成员本人的输入和请求里带的发送方所见交过去，拿回三种答复之一：输入（带展开之后的内容）；操作请求；拒收并写明原因。答操作请求时这一次受理不提交：交付面先请 Session 记下命令名与参数，再经入口的进程内调用、用发这句话的那个登录去做那个操作，结果是那个操作自己写下的条目。会话自己的四条系统命令（`/model`、`/permission`、`/archive`、`/reload`）由适配成员交出，由应用的装配登记到命令领域。系统主体送来的输入不解析。
- **每条输入有一个来源，来源是别的领域登记的声明。** Session 不认识登记的是谁，核心成员里不出现任何来源的名字。作者角色、叫不叫醒、占不占待交预算在受理时由主体的种类与声明算出，和输入写在同一次提交里，请求方不能自报。受理前处理的处理件按固定顺序运行：一个拦下就拒收，不可用答依据不可用，不当成放行。提交之后没有拓展点，要在受理之后做事的一方订阅观察。
- **新 Run 开始与显式重装是会话的采用点。** 定义版本、常驻工具与常驻段只在这里由采用来源重判，答三种之一：用这一套；照原来那套，并记下新版没用上的原因；没有可用的采用，不开始，输入留着。一轮在跑时的重装在下一个安全点生效：Agent 交出交接证明，Session 在一次提交里记采用、撤旧、开新；已经发出的工具调用不重做。
- **冻结是 Session 拥有的独立生命周期状态，不是归档。** Tool 在采用点给出冻结判定，Session 执行状态转换。冻结不可逆：不再开新 Run，在途的 Run 按原规则收场，不被取消。冻结的会话可以归档，撤销归档后仍是冻结。
- **控制不经解析。** 停止、插队、停一个调用、转后台、重试，是会话协议里各自的操作，不进队列，都点名目标。它们从哪个键、哪个按钮来，Session 不知道。

**它不是什么。**

- 不是干活的。它不执行循环，不发模型请求，不运行工具。它不是第四个 runtime。
- 不发起 Model 或 Tool 的调用。会话路径上，调用、重试、中断由 Agent 发起。控制送到调用当前的等待者：还在某一步等待里的调用，Session 的控制经 Agent 的控制入口送达，因为答复要回到那一步；转了后台的调用没有在等它的步，Session 凭调用引用直接交给 Tool。
- 不是后台结果的接收者。后台调用的结局由 Agent 的结果接收方保管；Session 解释这条记录，按自己的投递资格决定要不要把它受理成一条输入。资格从快照派生：会话没有归档，资格就在。用户感到的「叫醒」就是这条输入走普通的承接与开 Run 规则，没有另一个唤醒机制。
- 不是物理收场的判断者。取消、归档、换代只改变资格与责任。模型发没发出、工具停没停、环境关没关，由各自的拥有者报告，Session 只对账。

**它和邻域怎样认识。** Session 是最外层。它认识全部邻域：Agent、Model、Tool、Runtime Context、Request Context、执行环境。邻域都不认识它。

- 邻域的契约只用通用角色：外部协调者、提交参加者、消费者拥有者、作用域持有者、历史持有者、维护者。Session 是这些角色在会话路径上的具名实现者。
- 认识只发生在 Session 的适配成员里。名称与形状的翻译都在那里。Session 的契约成员不导入 Model、Tool 的契约。
- 适配成员读邻域的公开事实，用来对账和承接结果。Model 和 Tool 的结果与账目，Session 从同一份会话日志里读。

## 拿它量一个设计

- 要给会话加一个新的事实：它先是日志里的一种条目，然后才是别的。没进日志的，不算发生过。
- 要加一个「当前怎样」的字段：它是日志的投影。写清它从哪些条目算出来，丢了怎样重算。
- 一个运行对象里存了日志里没有的事实：错了，它丢了就算不回来。
- Session 的代码要知道模型回了什么、工具做了什么：从日志读。
- Session 的契约成员里出现了 Model 或 Tool 的类型：错了，那属于适配成员。
- 邻域的契约里点名了 Session：错了，它应当写通用角色。
- Session 发出取消之后等着模型或工具真的停下才算取消：错了。取消生效就记终态，实际停没停由对方报告，Session 对账。
- 一轮当中的事要 Session 逐步决定：越界了，Run 之内归 Agent。见 [cross-domain.md](cross-domain.md)「Run 是边界」。
- 提交之后的通知只是叫醒。丢了、重复了、合并了都不改变事实；要靠它保证正确的设计是错的。
- 另一段代码也要往会话日志里写：它是一个新的提交方，不是第二个写入者。让它交一条会话命令，由写入者写。
- Session 的核心成员或接入成员里出现某条斜杠命令的名字，或出现「Skill」这个词：错了。命令的名字只在适配成员交出的命令来源里。
- 按输入的来源另设优先级，或在核心成员里按来源的名字分支：错了。受理之后，排队与承接的规则不按来源分。
- 一个控制操作的请求里没有它针对的那一轮或那次调用：错了。
- 单独停止一次后台调用或取消原 Run 之后，就丢掉它的结局：错了。投递资格只看会话有没有归档；被单独停止过的调用，结局受理成不叫醒的输入。
- 一轮在跑时的重装立刻换掉这一步的组合，或重发已经发出的工具调用：错了。重装在下一个安全点生效，新采用只影响还没开始的经过。
- 冻结时取消在跑的 Run，或撤销归档让冻结的会话重新能开 Run：错了。
- 撤销归档恢复被取消的 Run、调用或卡片：错了。撤销归档回到休眠，要继续就显式提交新任务。
- 每次提交之后都要做的事，例如发通知、更新按库保存的缓存：挂在写入者这一头，只留一处。挂在各个提交方身上是错的，新加的提交方会漏掉。见 [cross-domain.md](cross-domain.md)「一类事实只有一个写入者」。
