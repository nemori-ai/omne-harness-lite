# Runtime Context

## 它是什么

各领域之间「知道」这件事的解耦层，是一个正交的维度。

核心的几个领域干活时，要知道很多不归它们管的事：我是哪个租户，现在是什么权限模式，选的是哪个工作区，当前用哪个模型档案。这些事实各有拥有者。如果每个核心领域都直接去问每个拥有者，就是一张多对多的依赖网，谁变了都牵动一片。

Runtime Context 把它拆开：

- **拥有事实的一方发布。** 它把自己的数据做成一块块，登记到 Runtime Context。块声明和数据的值仍然归它。
- **要用的一方读取或订阅。** 它用自己的形状声明需要，不点名块键。集成方登记时把需要绑到块上，形状不同时附带翻译。读者拿到的是快照和之后的变化。
- **两边互不认识。** 发布的一方不知道谁在读。读的一方不知道值是谁算出来的。

三条规则：

1. 值归生产者。Runtime Context 只是供给，不取得那份事实的治理权。
2. 一个作用域里登记哪些块、谁有资格读，由这个作用域的持有者定。持有者有两个：会话持有会话级作用域；静态作用域持有者持有租户级作用域，它登记的是这次部署的事实。会话级作用域以所属租户的租户级作用域为父，读一个块先查自己，再查父级。
3. 读不到就是读不到。一次读取的结果是成功、拒绝、缺项、未知之一。缺项、未知和拒绝不能变成空，也不能变成默认值或旧值。

运行时上下文只经会话日志里的提醒到达模型。会话作为作用域持有者以模型类读者读块，把快照与变化写成提醒追加进历史。请求组装不读 Runtime Context。

## 它不是什么

- 不是指挥通道。它从不向任何领域发指令。「许不许」「提交」「取消」这些决定，各走各自直连的窄端口。数据走它，决定不走它。
- 不是一个什么都往里放的大对象。模型上下文是一次请求实际用的输入，执行环境是动作的落点，它们和 Runtime Context 是三样东西。Request Context 和它同在一个包组，但变化理由不同，也是另一样东西。
- 不是事实的拥有者。它里面的每一块都有一个外面的生产者。它不持有耐久状态：进程重建之后，持有者从自己的日志交回注册，生产者重新供值，读者重新绑定。
- 不是授权。一份读取资格只决定能读哪些块，不决定能做什么。
- 唤醒不是变化本身。读者收到唤醒后以读到的值为准；唤醒丢了，下一次拉取补齐。

## 拿它量一个设计

- 核心领域的代码里出现了某个治理领域的类型，只是为了「知道一个值」：这个值应当是 Runtime Context 里的一块。
- 加一个新的治理领域，却要改 Session、Agent 或 Tool 的代码：多半是没走这一层。
- 有人想经它传一个「去做某事」的信号：走错了，那是控制，不是知道。
- 一块数据说不出生产者是谁：先找到拥有者，再登记。
- 读的一方拿到缺项，就当成空或默认值继续：错了。缺项是一个要如实处理的结果。
- 消费者的契约里写着块键：错了。它声明自己的需要，绑定归集成方。
- 请求组装直接读 Runtime Context，让块的值进模型：错了。模型只看会话日志里的提醒。
- 一份事实只在 Runtime Context 的投影里有，别处没有：进程重建之后它就没了。
