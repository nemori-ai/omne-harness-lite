# Runtime Context

## 它是什么

各领域之间「知道」这件事的解耦层，是一个正交的维度。

核心的几个领域干活时，要知道很多不归它们管的事：我是哪个租户，现在是什么权限模式，选的是哪个工作区，当前用哪个模型档案。这些事实各有拥有者。如果每个核心领域都直接去问每个拥有者，就是一张多对多的依赖网，谁变了都牵动一片。

Runtime Context 把它拆开：

- **拥有事实的一方发布。** 它把自己的数据做成一块块，登记到 Runtime Context。数据的值仍然归它。
- **要用的一方读取或订阅。** 它声明自己要读哪几块，拿到的是快照和之后的变化。
- **两边互不认识。** 发布的一方不知道谁在读。读的一方不知道值是谁算出来的。

三条规则：

1. 值归生产者。Runtime Context 只是供给，不取得那份事实的治理权。
2. 一个会话里登记哪些块、谁有资格读，由这个会话的作用域持有者定。持有者是 Session 一侧的集成方。
3. 读不到就是读不到。缺项和未知不能变成空，也不能变成默认值。

## 它不是什么

- 不是指挥通道。它从不向任何领域发指令。「许不许」「提交」「取消」这些决定，各走各自直连的窄端口。数据走它，决定不走它。
- 不是一个什么都往里放的大对象。模型上下文是一次请求实际用的输入，执行环境是动作的落点，它们和 Runtime Context 是三样东西。
- 不是事实的拥有者。它里面的每一块都有一个外面的生产者。

## 拿它量一个设计

- 核心领域的代码里出现了某个治理领域的类型，只是为了「知道一个值」：这个值应当是 Runtime Context 里的一块。
- 加一个新的治理领域，却要改 Session、Agent 或 Tool 的代码：多半是没走这一层。
- 有人想经它传一个「去做某事」的信号：走错了，那是控制，不是知道。
- 一块数据说不出生产者是谁：先找到拥有者，再登记。
- 读的一方拿到缺项，就当成空或默认值继续：错了。缺项是一个要如实处理的结果。
