# 统一语言

**先定义，再使用。**一个词进了正文，就再也不是一个人的事了。

词表在设计链的 `design/ubiquitous_language/` 下，五份：

| 文件 | 拥有什么 |
|---|---|
| `README.md` | 入口：分卷、这里拥有什么、它怎么生长 |
| `index.md` | **全部词条一览，查重从这里开始**。它不是定义 |
| `conventions.md` | **词条格式与流程的权威正文** |
| `decisions.md` | **不归任何 topic 的概念**，产品负责人对它们的直接裁决 |
| `conflicts.md` | 发现的对不上的地方 |

**本 skill 给的是判断力**，格式与流程的权威正文在 `conventions.md`，不在这里重复。
**路径都从设计根算起**，因为这份正文会被编译到几个宿主目录下，相对链接在那里不成立。

## 顺序不能换

```text
查重 → 取名 → 选卷 → 写定义 → 自检 → 记索引 → 才能在正文里用
```

**「才能在正文里用」是硬的。**先写正文再补词条，补的时候人已经默认那个词是对的了，
**查重和自检都会走过场**——而这两步正是这件事的全部价值。

## 一、取名：不许占用通用词

**这是最容易犯、也最贵的错。**

一个通用词被定义到一个很窄的概念上之后，**它在别处的正常用法就全成了冲突**，
而那些用法躲不掉——它们本来就是那个词的常见意思。

> **判据：这个词在别的上下文里，会不会也被用来指别的东西？**
> **会，就加限定词。**

真的踩过的：

| 想叫 | 撞上了什么 | 改成 |
|---|---|---|
| `Role` 角色 | 消息也有 role（user / assistant / system） | **`Tenant Role` 租户角色** |
| `Layer` 层 | 系统里到处是层 | **`Scope Layer` 作用域层** |
| `Context` 上下文 | 给模型看的上下文、Cordis Context——**一个词三个所指** | **`Runtime Context` 运行时 context** |
| `Injection` 注入 | 依赖注入 | **`Runtime Injection` 运行时注入** |
| `Composition` 组合 | 作用域合成也叫 composition | **`Asset Composition` 资产组合** |
| `Lineage` 血缘 | registry 里已有一份（设计对象的身份谱系） | **`Transfer Lineage` 转移血缘** |

**中文同样要防。**单字词与两字通用词最危险：「层」「块」「帧」「态」「组装」「求值」
——在自己那一段里读着很顺，跨 topic 就全是歧义。

**但别矫枉过正。**`Account` `Organization` `Tenant` `Sandbox` 这些虽然常见，
**但它们在本领域就是这个意思**，业界也这么用，加限定反而不自然。

> **要加限定的是「被收窄了的通用词」，不是「本来就是这个意思的常用词」。**

**判断不了的时候，用这个测试：**

> **把这个词单独写在一张纸上给另一个 topic 的人看，他会不会想到别的东西？**

## 二、分卷：按「它回答什么问题」

**卷不是抽屉，是语义维度。**选错维度，整套词表会在第一次重构时全部搬家。

**两个看着顺手、实则会塌的维度：**

| 别按 | 会怎样 |
|---|---|
| **按来源 topic 分** | 同一个概念被多个 topic 用，**于是它有好几个家**——那正是统一语言要消灭的东西。而且 topic 一重排编号，卷全错 |
| **按被描述的对象分** | **对象会被重新分解。**今天「工具」是一类，明天拆成「调用定义」和「执行体」，这一卷就得拆 |

**问题不会因为编号重排或对象重分解而改变**，所以按问题分：

> **谁 · 怎么算 · 由什么构成 · 怎么流动 · 怎么来怎么没 · 落在哪 · 怎么来往 · 留下了什么**

**检验只有一个办法：**

> **看同一个来源 topic 的概念，有没有被分到不同卷。**
> **全都落在同一卷，那这个卷就是那个 topic 的马甲。**

**卷的数目要少。**放不进任何一卷就新开一卷，是最容易犯的懒——
**多半是那个概念自己还没想清楚**，不是维度不够用。

## 三、写定义：中英各自成立，不是互译

**两条定义讲同一件事，但各自用各自语言里自然的说法。**

| | ✗ | ✓ |
|---|---|---|
| 中 | 一个代表隔离边界的容器对象 | 资源、数据与成本的归属边界，也是隔离边界 |
| EN | A container object representing an isolation boundary | The boundary of ownership, isolation and cost attribution |

左边是**把另一边逐字搬过来**的结果：中文读着像译文，英文读着像中式英语，**两边都不精确**。

**英文名用领域惯用词，不自造。**这个概念在 `spec/`、`basis/` 或上游文档里
已经叫什么，就用什么——**已经有名字的，不另起一个**。

### 三个自检，过不了就重写

| 测试 | 怎么做 | 不过说明 |
|---|---|---|
| **替换** | 把正文里这个词**换成定义原文**，句子仍然成立、意思不变 | 定义**比这个词多说了或少说了**东西 |
| **边界** | 说得出一个「**差一点就是它、但不是它**」的东西，并说得出差在哪 | 定义**没划出边界**，只在描述典型情况 |
| **独立** | 不看 topic 正文，**只读这一条**，能判断手上一个具体东西算不算它 | 定义**在偷偷依赖上下文** |

> **最常见的失败是「独立」。**写的人脑子里装着整个 topic，
> 于是写出一条**只有他自己读得懂**的定义。

## 四、出处必填，否则就是发明

> **一条查不到出处的词条，说明它是在这里被发明出来的。**
> 那触了产品设计的红线（`design/product/AGENTS.md`）：**不发明没人拍板的东西。**

**出处只有两种合法形式，没有第三种：**

| 形式 | 用在什么时候 |
|---|---|
| **指向某个 topic 的某一节** | **绝大多数词条。**必带 rev——**topic 升 rev 时，照着 rev 就能找出哪些词条要复核** |
| **指向 `decisions.md` 的一条** | 这个概念**不归任何一个 topic**：跨全链的治理概念，被很多 topic 引用却没有哪一个拥有它 |

**第二种不是后门。**成立条件很窄：**确实跨全链、确实没有归属、
且产品负责人确实直接裁决过**——三条缺一，就该回去找那个 topic，或者把它提上去。

**用第二种时，把推理链一并写进 `decisions.md`**：产品负责人给的通常是**几条判断加几条裁决**，
**定义的措辞是你写的**。哪一句从哪来，要能被逐条核对、逐条推翻。

## 五、这里拥有什么，不拥有什么

> **词表拥有「这个词精确指什么」，topic 正文拥有「为什么是这个形状、有什么后果」。**

**判断一句话该写在哪：它回答的是「这是什么」还是「为什么」？**
**「为什么」一律不写进词表，哪怕它很精彩**——写进去就是第二份权威，
而两份权威一定会分叉。

## 六、发现对不上的地方，记下来，别顺手改

**提取概念时一定会撞见三类情况**，处置各不相同：

| 类型 | 怎么办 |
|---|---|
| **同名不同义** | **必须裁决**：承认是两个概念各起各的名，还是统一。PM **不替产品负责人挑** |
| **同义不同名** | 选一个进词条，其余进「弃用」；**正文回改由各 topic 的 owner 自己做并记 changelog** |
| **定义打架** | **必须裁决。**记清楚哪两处、各自原文、差在哪 |

**一律记进 `conflicts.md`，不静默统一掉**——静默改掉会让后来者
以为这里从没出过问题，**而那些地方正是最该被复核的**。

**但也有 PM 该自己定的。**判据与 `product-design` skill 的「什么时候问，什么时候自己定」一致：
**只有一个答案在逻辑上成立时，把推理做完，别上报。**

> 例：两个概念都已拍板、都不能改名，那唯一自洽的结论就是
> **「这个词裸用时不作为术语，必须带限定」**——这条 PM 自己定，写清推理即可。

## 七、什么不配有词条

**五条都过才收：**

| 判据 | 问自己 |
|---|---|
| **跨 topic** | 它被**一个以上** topic 使用，或显然会被 |
| **误读有代价** | 读错它会有人**把设计或实现做错**，而不只是读着别扭 |
| **写得出无歧义定义** | 写不出来说明**它还没想清楚**，先别收 |
| **不是实例** | 它是**一类**东西，不是某一个。`Tools()` 是 **meta tool 的实例** |
| **不是修辞** | 「门」若只是比喻，不收；若它**承担了精确所指**，收，并写明它等于什么 |

**反过来：只要在两个以上 topic 出现、且含义必须一致的名词，一律要收。**
**漏掉一个，那个词就会在第三个 topic 里被重新发明。**

## 八、从一份设计里把概念捞出来

**从它的「概念定义」一节进，但不要只看那一节。**产品规则与模型里常常藏着
被反复使用却没有正式定义的词——**那种词最危险**，因为每个人读到的都是自己猜的。

**留意「承接前面的 topic」那张表**：它写明了哪些概念**不在本 topic 拥有**，
顺着它能直接找到权威出处，**也能发现某个概念其实哪儿都没定义**。

**出处必须记到 rev。**那不是为了留痕，是为了**将来那份设计改了，照着 rev
就找得到该复核哪些词条**——词表跟着设计长，这是它唯一的对齐手段。

> **不是每个概念都该现在收。**词表收的是**已经稳定到值得固定说法**的那些；
> 一个还在 draft 里摇摆的概念，**现在收它等于把草稿定成语言**。
