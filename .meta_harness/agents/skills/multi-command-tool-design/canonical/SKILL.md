# 多命令工具设计

多命令工具对模型是一个工具。模型在一次调用里点名命令并给出字段，就像在命令行里写 `files write --path …`。这样做的目的有两个：

- 声明只占一个槽位，系统提示与工具声明更短，提示缓存的前缀更稳定。
- 模型按需取得用法：常用命令看一行签名就够，不熟的命令再问 help，写错了从回执里一次改对。

省 token 不自动等于省调用。渐进披露可能多出 help 调用，所以每次改动都按联合目标验收：同一任务上，总 token 与工具调用次数都不比改动前多。本仓库的形式模型、实现与基准依据 D-94、R2-D393 至 R2-D396。

## 先认清三条不变量

1. **一个工具一条声明。** 声明名就是工具名，不按命令展开成 `<工具>.<命令>`。命令只出现在调用参数里，路由从参数选命令，不从名字拆。
2. **解码是偏函数。** 编码出的调用总能解回同一命令与参数；其余输入得到封闭的拒绝类别，不猜命令、不默认第一个。拒绝要让模型读到原因与用法。
3. **错误不能变成成功。** 未知命令、字段无效、调用点名的命令与准入的不一致，都是失败结果，带固定原因。不要把 `rejected …` 当作正常返回。

`@omne-harness/tool-contract` 的 `command-call.ts` 拥有这些规则的唯一实现（`decodeCommandCall`、`selectCommand`、`commandArguments`、`commandMenu`、`commandSignature`、`commandCallSchema`）。新工具复用它们，不另写一份解析或菜单。

## 三层披露怎样分工

| 层 | 何时出现 | 写什么 | 不写什么 |
| --- | --- | --- | --- |
| L0 声明 | 每次请求 | 工具用途一句；菜单首行写调用形式；每命令一行 `<命令> <签名> - <摘要>` | 字段类型、字段说明、完整 schema、运维构造值 |
| L1 help | 模型主动问某个命令 | 用法行、完整 JSON Schema、逐字段说明、规则 | 其余命令的细节 |
| L2 回执 | 调用出错 | 固定原因加该命令的用法行；调用层的错再附菜单 | 原始堆栈、猜测的修正 |

签名由 `commandSignature` 从参数 schema 机械派生：必填字段写名字，可选字段加 `?`，封闭取值写 `=a|b`。作者只维护一份参数契约，L0、L1 与校验都从它派生，所以三层不会说法不一。

写摘要时把它当作 `--help` 的一行：说清命令做什么和它最重要的副作用。字段名本身要自解释（`parents`、`recursive`），因为 L0 只给名字。

## 选调用编码

编码是每个工具的策略选择，定义里用 `encoding` 声明，取值是封闭集合：

- `wrapped`：`{"command": "<命令>", "params": {…}}`。字段与调用层分开，任何字段名都可用。默认选它。
- `flat`：`{"command": "<命令>", …字段}`。少一层嵌套。前提是没有命令声明名为 `command` 的字段，也没有 executor-owned 参数；定义判定会以 `flat-conflict:<命令>` 拒绝违反者。

给 help 选主题时用 `name` 一类字段，不要叫 `command`，这样 flat 仍可选。要换编码，先按下文的基准筛选，再改；不要凭直觉认为嵌套少就更省。

## 把复杂度放在路由一侧

- 请求来源（本仓库是 harness-server 的可信 Tool 请求来源）按工具名查定义，用 `selectCommandText` 从生效参数选命令。点名已知命令的调用都送到该命令，由它的参数解析判整次调用，模型因此读到精确原因。没点名已知命令的调用答 unavailable。
- 绑定一侧用 `commandArguments` 切出所选命令的参数，再交给作者的参数解析。注册保持作者原有的解析器。不要在注册时包装解析器：把已注册的操作再登记一次时，参数会被切两次。
- 工具定义不能含运维构造值（shell 可执行文件、工作区根）。发行清单用不同的构造值重算定义并比较摘要，定义随构造值变化就无法固定。这类放置事实放在运行时结果里，例如 `Shell.info` 写出 shell 与起始目录。

## 找能省掉的调用

提示缓存命中率高时（本仓库基线约 84%～92%），每少一轮请求都比压缩声明更值。先读基线的调用轨迹，按「工具 + 命令」逐项问：这次调用是任务本身需要的，还是工具形状逼出来的？

- 形状逼出来的调用，改形状消除。例如 `write` 加 `parents`，新项目不必先逐个 `mkdir`。新字段走同一放置与授权检查，不扩大边界。
- 环境探测类调用（平台、shell、目录）由放置事实的拥有者提供。不在工具说明里硬写运维值。
- 不设「先 help 再调用」的门。门会让调用数至少增加「首次使用的命令数」，L0 签名加 L2 回执已经满足「不熟先取用法」。

## 验证：契约、性质与基准

1. **性质测试**（参考 `packages/tool/tool-contract/tests/command-call.spec.ts`）：两种编码的往返；每个拒绝类别的精确输入；签名派生；schema 的 `command` 取值恰为命令表；flat 冲突的判定；再登记不改解析器。
2. **组合测试**：经真实请求来源与绑定发整次调用，覆盖点名别的命令、未知命令与无效字段各得到什么结果。
3. **基准**：给被测 agent 的请求只写需求与验收标准，不点名工具、命令或方法。计数按「工具 + `arguments.command`」，并把调用分成任务、披露（help）与出错三类。先筛选：每个候选在两个任务上各跑 3 次；再定稿：三个任务各 5 次，与基线比较均值与中位数。报告系统提示与工具声明的 token、模型调用、工具调用、prompt 与 completion token 及花费。花费受缓存影响波动大，结论以 token 与调用次数为准，花费如实列出。
4. 解释每个数字再下结论：同样的调用数，先确认任务真的完成（验收脚本通过），再看差异来自哪一类调用。

## 交付前自查

- [ ] 模型请求里每个工具只有一条声明，名字是工具名。
- [ ] 菜单与签名来自 `commandMenu`，作者描述里没有重复的命令清单。
- [ ] help 按命令给全量用法；未知命令与无效字段是失败结果，原因后附用法。
- [ ] 定义不随运维构造值变化，发行清单检查通过。
- [ ] 参数只在绑定一侧切一次，再登记安全。
- [ ] coding 提示词的工具段与声明一致，不写死某种编码的调用形式。
- [ ] 同一任务上总 token 与工具调用次数都不多于改动前，证据随卡贴出。
