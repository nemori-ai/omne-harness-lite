# 个人工程复盘

选择这条主线时阅读。重点让读者理解作者在具体条件下如何作出判断，以及选择的后果。
作者可以讲已经走过的路，也可以解释当前设计；尚未实施的选择必须保持设计时态。

## 组织文章的思路

以下是论证需要覆盖的问题，可按故事重点合并、调整顺序或省略不相关部分，
不用逐项做成标题，也不强求按研发时间流水记账。

1. **一件值得讲的具体事情。**从某个困扰、约束、出乎意料的结果或明确的设计偏好切入。
   让读者尽早知道作者在解决什么，以及这篇文章主要想解释哪个决定。
2. **当时的处境。**只交代影响选择的目标、已有系统和团队条件。
   说明作者当时知道什么；不能把后来获得的信息写成当初早已洞察的理由。
3. **面前的选择。**讲真实认真考虑过的方案，解释各自吸引力、成本和不适用之处。
   篇幅跟随关键取舍，不能凭空补三套方案凑比较，也不要把放弃的方案写得一无是处。
4. **判断如何变成设计。**挑最能体现取舍的一两个机制讲透：它如何工作，
   为什么能解决前面的问题，作者接受了什么新负担。代码或图服务于这段解释。
5. **实际发生的后果。**有运行经验时讲收益、失败、意外和修正，用记录或数据支撑；
   只有设计时讲预期和待验证处，避免用「最终证明」等叙事替代尚未发生的结果。
6. **今天怎么看。**哪些选择仍成立，哪些会因条件变化而重做。
   让读者带走判断方法与适用条件，结尾不必上升为所有系统的普遍规律。

## 访谈与叙述的着力点

- 作者说「我喜欢简单」时，问清简单落在哪：使用者的操作、维护者要记住的规则，
  还是某一段实现？代价是否被转移到别处？只有具体答案才值得进入文章。
- 作者说「没必要」时，追问当时的任务与规模，以及什么变化会让它变得必要。
  个人偏好可以公开表达，别把它包装成无条件的技术定论。
- 保留犹豫、有限信息和合理失误。一次失败如果没有改变决定或帮助读者理解问题，
  就不必为了故事性加入；没有发生过失败也不需要编出曲折。
- 第一人称承载作者真实立场，技术因果仍需解释。
  将现在补做的分析写成回看，避免把 agent 的推导冒充作者当年的思路。
