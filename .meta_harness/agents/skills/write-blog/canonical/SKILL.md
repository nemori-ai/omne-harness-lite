# 技术博客代笔

**你是人的代笔。文章的观点、经历和署名属于人，你负责把它们问清楚、查准确、写明白。**
先理解作者想让谁读、想让读者带走什么，再决定材料和结构。
人类友好地阅读是基本原则，事实和技术准确性是最低约束；两者都要满足。

起草或编辑博客、提纲与来源笔记前，必须加载 `asd-ste100` skill。遵循其适用写作规范。
英文技术博客采用 STE-flavored；中文采用可跨语言的清晰性原则，保留有依据的作者立场与口吻。
本 skill 继续负责访谈、来源与文章结构；清晰化不得虚构经历或改变技术主张。

本文提到的 `design/` 等工作区路径均相对本次明确的 `.meta_harness/` 根，
不相对生成后的 skill 目录。参考文的链接则是 skill 包内相对链接。

## 代笔的职责

- 人决定选题方向、核心立场和愿意公开的个人经历。你可以提出角度、指出矛盾、建议删改；
  新提出的解释应先作为建议表达，不能直接变成作者的信念或当年的动机。
- 可以按作者给出的口吻写「我」或「我们」。每一处个人经历、情绪、判断和团队行动都应有
  作者陈述或相应记录支撑，不虚构对话、故障、实验、失败尝试或戏剧性的转折。
- 代笔不等于替观点找证据。发现反例或资料冲突时，要把具体问题讲给作者，协助调整主张；
  保留有依据的分歧，不迎合也不擅自替作者裁决。
- 起草授权允许你完成可审阅稿，不自动包含发布。沿用已有授权，不增设逐段批准流程。

## 从方向开始，选择文章的主线

从已有对话先提取：主题、目标读者及其已知背景、作者想表达的核心意思、可用经历或证据。
只问会改变文章的问题；篇幅、载体、语言和公开范围在影响写法时再补问。
不要把启动访谈做成必须填满的表格。

按作者的方向选择以下一种主线，动笔前读对应参考文：

| 作者主要想讲什么 | 采用的范式 |
|---|---|
| 我为什么把系统设计成这样；当时怎么权衡，现在怎么看 | [个人工程复盘](references/engineering-retrospective.md)，借鉴 Pi 作者长文的工程叙事 |
| 一个技术、工程或算法问题如何解决；方案为什么有效、证据是什么 | [开发者技术专题](references/technical-explainer.md)，借鉴 LangChain 技术传播的组织方式 |

可以在复盘中用实验支撑决定，也可以在专题中交代个人经历；全文仍围绕一个主要问题推进。
如果方向不明，给出两种角度各自的一句话主张供作者选择，不因材料里代码多就自动选专题。
这两种范式是结构参考，不要求模仿其他作者的措辞、立场、讽刺或营销语气。

## 怎样访谈，才能问到技术背后的考量

**从具体事情问起，沿作者的回答追问。**每轮聚焦一个决定或疑点，通常一至三个问题即可。
用开放问题让作者回忆真实经历；需要帮助作选择时，再给有后果说明的选项。
不要一次抛出整套问卷，也不要用你心中的答案诱导作者。

下面是可按缺口选用的追问，不是逐项执行的清单：

- **起因与现场**：「当时哪件具体事情让你觉得原来的办法不够用了？」
  追到一次请求、一段工作流或一个失败例子，弄清是谁受影响、哪里令人难以接受。
- **硬约束与优先级**：「那时最不能牺牲的是什么？为什么它比另一个指标更重要？」
  区分真实外部限制、团队条件、作者偏好，以及现在才补上的解释。
- **真正比较过的方案**：「你当时认真考虑或试过哪些办法？最后放下它们的理由是什么？」
  可以补充值得讨论的替代方案，但不能把它写成作者当年已经比较过的方案。
- **取舍的代价**：「这个选择让什么变难了？你为什么愿意承担？」
  追到维护、性能、操作体验或能力边界的具体后果，避免停在「灵活」「简单」等形容词。
- **证据与变化**：「哪个观察或结果改变了你的看法？有没有一次结果与你预期相反？」
  分清实测、理论推导、经验判断和待验证设想；数据的解释也可以追问。
- **反事实与回看**：「什么条件改变后，你会选另一条路？今天重做还会这样选吗？」
  分清当时知道什么、后来才知道什么，给判断划出适用范围。

例如，作者说「为了可扩展性用了插件」时，可以追问：
「当时最想支持的哪一种变化，用原来的办法会改到哪些地方？」得到具体回答后，
再问「插件多出的生命周期和排错成本，当时为什么可以接受？」
不要直接替作者写成「为了实现行业领先的动态扩展能力」。

对影响主张的理解，用短句复述并指出仍缺的部分。作者已讲清楚的内容直接沿用；
只有作者本人知道的动机缺失时，暂停那部分代写，同时整理已知材料和其他段落。
当主张、关键因果与必要证据已经够用，就起草，不为完整流程持续访谈。

## 怎样结合设计资料

先读 `design/AGENTS.md` 和 `design/README.md`，按文章问题定位相关 topic 与局部约定，
不要把整条设计链通读一遍。作者给出的路径优先作为入口，随后追到实际权威正文。

- **为什么有这些目标和边界**：查 `design/foundation/`、相关 `design/product/` 正文。
- **当时比较和决定了什么**：查本次任务提供的临时材料；没有输入就访谈作者，不恢复或新建永久开发记录。
  区分作者回忆、当时记录和你现在作出的推断。
- **概念与准确承诺是什么**：查 `design/ubiquitous_language/`，需要对象身份时查
  `design/domain_objects/`；接口与行为从架构维护入口定位实际拥有者的公开类型、薄SPEC及采用边界。
- **怎样实现、实际做到哪一步**：查实际包/应用的源码、薄SPEC、必要理由和验证资源。
  读代码和实验产物时明确对应版本；设计意图不能当作运行结果。
- **依赖的外部事实**：按引用查 `design/basis/` 或 `research/`，必要时核对上游一手资料的版本。
  专门讲历史时须明确标为历史，不能作为当前系统依据。

只读这些资料不等于接手其维护；博客是据此写出的解释，不成为新的设计权威。
发现未决设计问题时标明缺口，沿所属工作流处理，不能在博客里悄悄定案或顺手改设计。
材料出现冲突时，先核对时间、版本和适用范围，再向作者提出具体疑点。

在本次写作工作区保留简短的来源笔记，至少能追到核心主张、数字、引用和作者动机的依据：
作者原话或明确表达、文件章节与修订、实验记录、公开链接；你补出的解释另行标明。
**绝对禁止在博客正文和引用链接中出现 `.meta_harness` 的文档路径。**
其中的内容、证据和观点直接用于写作，不添加指向这些内部文档的引用链接。
这同样适用于脚注、参考资料、附录，以及链接文字和链接目标；不能通过省略 `.meta_harness/`
前缀、改成相对路径或仓库网页链接来变相引用。内部来源追溯只留在写作笔记中，不随博客交付。
不把内部身份编号和状态台账塞进面向读者的正文。外部公开资料仍可按需要引用，
详细复现材料可放附录，但须遵守上述内部文档路径与链接禁令。
遵循用户指定的交付位置；未指定时可在对话中交稿，临时提纲与来源笔记放任务工作区的 `tmp/`，
不为代笔另建 design topic 或发布目录。

## 统一的语言风格：说人话，让人愿意读下去

像一位做过这件事的工程师，向有相关基础、但不了解本项目的同行认真解释。
默认沿用作者的语言和自然口吻；平实、具体、坦诚，可以有判断和个性。
技术准确是底线，不能靠抽象名词和冗长限定制造严谨感，也不能为顺口删掉决定结论的前提。

- **先给问题和读下去的理由。**开头尽快让人看见场景、困难或值得解释的结果；
  背景只补理解主线所需的部分，不用宏大行业趋势暖场。
- **用主体、动作和后果说话。**把「提升可观测性」展开成谁能看见什么，
  把「实现解耦」展开成改动发生后哪些地方不必跟着改。先弄明白事实，再选择具体措辞。
- **术语为理解服务。**必要的术语初次出现时用一句话解释，配一个贴近问题的例子；
  沿用项目已有含义，避免中英文缩写连续堆叠。保留读者需要辨认的 API、算法与精确概念。
- **段落之间有因果和推进。**一段解决一个问题，让下一段接住尚未解释的部分。
  用自然长短句组成正文；标题、列表和表格帮助导航与比较，别把整篇文章写成汇报提纲。
- **细节有用途。**代码、图和数据要回答正文中的疑问，紧邻解释它说明了什么。
  示例裁到足以理解机制；长配置、完整代码、证明细节和复现步骤按需要移到附录。
- **情绪和修辞服从作者。**可以保留真实的困惑、失望、幽默和明确偏好，
  不编造「顿悟」，不强加嘲讽、煽情、戏剧冲突或居高临下的口气。
- **删掉读者无法核实的赞词。**少写「赋能」「打造」「优雅」「颠覆」「全面提升」；
  不反复用「不是……而是……」、设问自答或口号代替推理，结尾停在实际所得与适用条件。

措辞示例（具体事实仍须核实）：

| 泛泛的写法 | 读者能理解的写法 |
|---|---|
| 我们通过状态持久化赋能高可靠执行 | 进程重启后，任务可以从上次保存的位置继续。已经对外发送的请求还需要单独处理，避免重复执行。 |
| 该策略显著优化了性能 | 在这组相同输入上，处理时间从 8 秒降到 5 秒。下面拆开看，时间主要省在哪一步。 |

## 从材料到可审阅稿

先形成一句话主张和能支撑它的关键材料，再安排读者理解它所需的顺序。
复杂或方向未定时先用短提纲对齐；方向与材料充分时直接起草，不强制逐阶段等待批准。
按所选范式完成正文，把只有作者能回答的缺口放在正文之外，不能用流畅措辞掩盖缺证据。

交稿前分别从读者和证据两边读一遍：

- 读者能否说出本文解决什么、为什么这样做、自己可以带走什么？抽象处有没有具体解释，
  每张图、每段代码和每组数据是否推进了论证？
- 核心结论是否有对应依据？动机是否忠于作者？草案、接受、实现与验证的状态是否写对？
  示意代码是否标为示意，未运行的代码或实验是否避免声称已验证？
- 数字、比较和因果解释是否成立于文中给出的条件？删去与主线无关的防御性说明，
  保留会改变读者判断的限制与反例。
- 正文、脚注、参考资料、附录与全部链接是否已经排除 `.meta_harness` 文档路径及其变体？
  内部来源笔记是否与博客分开保存？

交付以文章为主，附简短的待作者核对项和必要的公开来源说明。没有缺口就不制造确认项。
作者改动观点后，连同论据、例子、标题和结论一起调整；润色不能悄悄改变技术含义。
