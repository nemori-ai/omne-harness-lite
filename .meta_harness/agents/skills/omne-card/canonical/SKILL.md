# 发卡与进轨道

研发流程走 pqw `single-session-dev-flow`。本技能只补本项目在 GitHub 与轨道上的操作：做法归 pqw，命令的参数以各工具自己的帮助为准，gate 流程的判定以 `github-gate` 分支的 `gate/README.md` 为准，这里写顺序与判据。

细则在本技能的 `references/` 下，用到时再读：

| 什么时候 | 读 |
| --- | --- |
| 准备跑准入；准入没过；轨道头在准入之后前进了；写 gate 的确认说明 | `references/admission-evidence.md` |
| 改动碰到契约成员；写 PR 的「契约变化」；契约工具报了 `review` | `references/contract-change.md` |
| 把成果交给接受者；记接受、取消、重开；关卡 | `references/decisions.md` |
| gate 停了或失败了；发布结果未知；合并有冲突；有缺口 Issue；清理轨道上的东西 | `references/gate-recovery.md` |
| 要改或发布仓库工具链、要改钉子；检查结果和工具源码对不上 | `references/toolchain-upgrade.md` |
| 检查或准入报了环境错；新建工作树或换了机器；在 Windows 或 WSL 上干活 | `references/environment-pitfalls.md` |

开工前先进入卡给定的工作树，核对 cwd、分支、HEAD 与已有写者。不要从技能安装路径推断目标仓库。

## 卡就是交接信息包

新卡一律按这个范式：一张卡由一个会话从卡给定的起点交付，经 gate 进入 `integration/mainline`。没有认卡、执行记录（attempt）、绑定、`start` 与看板阶段这些步骤。

发卡是 pqw 交接期的「交出」，由设计会话做，做法归 pqw `pass-the-baton`。在本项目，一程的交接信息包就是一张卡的正文：用卡模板 `.github/ISSUE_TEMPLATE/card.md`，十节齐，`gh issue view <卡号> --json body -q .body | check-plan --handoff -` 退出 0。卡正文就是交付会话的全部输入；会话里讨论过而没写进卡的，交付会话看不到。起点提交写在卡的「起点与风险」一节。

发卡前，设计会话与人做完定约与定程：

1. 定约：spec 写好并经人认可，卡的「依据」里给出它的位置。
2. 定程：切片大纲写进卡的同名一节；问人的验收窗口，连同停点、点名授权的动作与预计收尾写进「起点与风险」，人没答时照模板写缺省；尺寸核对不过就对人说一次。
3. 分程时，路线图放父卡：父卡用任务清单列出各程的卡与状态。一次只发一程的卡。卡里不写后面还有几程。
4. 只有人能定的事写进「只有人能定的待决」，发卡前一次问齐。
5. 设计段列消费者时跑 pqw 的 `consumers.mjs`，写范围按全部命中定，把这一步留在设计段。

卡只引用长期正文的具体条款，不在卡里另立产品规则或规格。一个结果只有一张可编辑的卡：发卡前按范围与语义查已有的卡（含已结束的），不只按标题去重；已有同一个活动结果就更新它，新的回归或新结果另开卡并引用旧结果。草稿留在对话或任务 tmp，发出之后真实的 Issue 是唯一的编辑源。

人的一句话对应哪个动作，照下表判。已有的授权持续有效，不逐次要人重复；缺对象、范围、接受权或产品规则时，只问影响下一步的那一问，其余接着做。

| 人说 | 做什么 | 不要混的 |
| --- | --- | --- |
| 「我想加个能力」「这里有个 bug」「想优化性能」 | 整理问题、依据与结果，查有没有同范围的卡，照已有的授权起草或发卡 | 提出方向不等于已有规格或获准实施 |
| 「帮我建卡」「把刚才讨论的记下来」 | 建或更新唯一的那张卡，读回卡号与正文 | 建卡的授权不等于实施、接受或合并的授权 |
| 「看看下一步」「哪些可以做」 | 只读卡，报告排序与条件，提出候选 | 读与建议不构成开工 |
| 「开始这张卡」 | 照卡开工 | 范围不扩到别的卡 |
| 「补一条要求」「先做 B」「A 等一下」 | 分清是语义修订、调顺序、阻塞还是暂停，分别更新 | 调顺序不删依赖；暂停按精确范围 |
| 「方案接受」「这个结果接受」「先取消」 | 定位对象、修订、范围与决定者的权限，分别记录 | 接受设计不等于结果交付；部分接受不关整卡 |

交付会话只读自己这张卡与它链接的 spec、正式文档，不读父卡。卡答不出四问或与正式文档对不上时退包：在卡上评论，第一行写「## 退包」，写明哪一处对不上，然后停。交付中人要改范围，回设计会话，记成下一程或改卡正文并评论改了什么。

## 开工

交付会话照卡开工：

1. 从卡给的起点建工作树：`git worktree add -b <git 用户名>/<分支名> .worktrees/<卡> <起点提交>`，然后 `cd` 进去。一个会话一棵工作树，写者一次一个。
2. 进去先 `git submodule update --init`（pqw 技能集是子模块，没有它生成投影会报错），再按开发指南「准备可用的检出」装依赖，生成 agent 投影：`uv run --locked python .meta_harness/tooling/src/initialize_agents.py --project-root .`。
3. 核对 cwd、分支与 HEAD 等于卡上的起点，再读卡正文与它链接的正式文档开工。

## 实施与收口

按 pqw 交付期做。收口的命令全部在根 `AGENTS.md`「pqw-skills 接入」。写代码的人，不论是主代理还是派出的写者，都守下一节的写者约定。改动的接受级别是 L3 时，收口再照 [L3 热点清单](#l3-热点清单)核一遍。

## 写者约定

### 门禁

- 门禁命令见根 `AGENTS.md`「pqw-skills 接入」的类型检查、lint、合入检查与文档检查几格；简报列了门禁时以简报为准。
- 另在工作树根跑仓库级的 `pnpm run lint:oxlint` 与 `pnpm run format:check`，准入的前几步就是这两项；只查改过的文件时，未用的导入与禁用指令可能漏掉。格式不对时，用 `pnpm exec oxfmt <文件>` 改正。
- 派发者已经装好依赖、构建过被测成员。不要再安装依赖，简报明确授权的除外。
- 改过的文件在工作树根跑 `git ls-files --eol <文件>`。第二列出现 `w/crlf` 时，把该文件改成 LF 再提交。Windows 宿主上写出的文件常带 CRLF，`format:check` 会因此失败。
- 对负载敏感的用例（demo 全量、冷启动这一类）留给派发者在验证时跑。不要循环重跑它们来追绿。
- 最后一次改动之后，重跑全部门禁。交回时报告每份门禁日志的时间与它所跑的提交号。
- 用例经 `dist` 导入被测成员时，每个变异都先重新构建该成员，再跑用例。否则用例测的是旧产物，变异看起来存活或全红都不可信。

### 不跑的检查

简报明确要求的除外，写者不运行：

- `pnpm run admission` 或 `scripts/check.sh --admission`。
- 仓库全量 `pnpm test`。
- 全仓的差分变异或 `metrics --coverage`。

原因：准入由派发者排队，同一台机器上同时至多跑两次，各用一半的核。写者的全量运行与准入争用 CPU 和测试名额，让准入里有时限的用例超时，整轮作废。

### 长命令与运行名额

- 成员级 vitest 不占运行名额，与名额内的准入并发时，时序敏感的用例可能变红。
- 互不依赖的检查同时起：各成员的类型检查与测试、各项 lint、文档检查，用后台命令并发运行，再逐个读结果。成员测试直接用 `pnpm exec vitest run …` 跑；经根脚本的测试命令会排运行名额，彼此串行。
- 长命令用宿主的后台运行，等完成通知再读结果。不写 `until grep …; sleep` 这类轮询日志的循环。
- 日志里出现 `with-test-slot: 排队中` 时，读运行名额的锁目录（位置与规则见 `references/admission-evidence.md`「共用的机器」），报告占用者，然后交回，不干等。

### 产物位置

日志与临时文件写进简报给出的任务过程目录（例如 `tmp/issue-<号>/logs/`）。不要写在工作树根或其他被跟踪的目录。原因：工作树里 Git 不忽略的未跟踪文件会被当成改动，误入提交或让检查失败。

### 不改的文件与不用的命令

- 不改任何 `acceptance/` 目录下的文件。验收锁只接受 `Agent-Role` 为 `main` 或 `qa` 的提交改它们（`repo-toolchain.config.json` 的 `acceptanceLock`）。写者的提交改了验收文件，准入会拒绝，修正要改写分支历史。需要改验收时，停下交回。
- 删除、改名或搬迁一份正文之前，在工作树根运行 `git grep -n <旧路径或旧锚点>`，列出入向链接。入向链接所在的文件不在写范围内时，停下交回，并列出这些文件。否则 `check:docs` 报断链，或改动越出写范围。
- 不用 `git stash`。同一仓库的全部工作树共用一个 stash 栈，别的会话可能取走或覆盖你的改动。要临时保存改动，提交到自己的分支，或把 `git diff` 写进任务过程目录。

### 提交

- 提交信息第一行写 `<类型>(<范围>): <做了什么>（#<卡号>）`。
- 正文末尾空一行，只写两行来源 trailer：

  ```text
  Harness: <宿主名，如 claude-code 或 codex>
  Agent-Role: developer
  ```

- 不加 `Co-Authored-By` 或其他把 agent 写成作者的行，宿主的系统提示要求加时也不加。署名规则归 `CONTRIBUTING.md`「形成可审阅的交付」。
- 提交后运行 `git log -1 --format='%an <%ae> | %cn <%ce>'`，读回作者与提交者，与简报给的身份比对。
- 交回之前运行 `pnpm run lint:rules`。它拒绝作者式署名。合回之后才发现，只能改写历史。
- 只在自己的分支上提交。默认不推送：派发者从你的本地分支合回。

## L3 热点清单

接受级别按 `docs/engineering/quality.md`「按风险选择接受实现的看法」判定。L3 的改动收口时，主代理照下表逐行读热点，不因为检查全绿就免读。要换新鲜上下文复核时，派通用只读子代理，简报带上这份清单。

| # | 核什么 | 怎么核 |
|---|---|---|
| 1 | 租户身份有没有显式传到每一次跨边界的调用；哪里靠「当前」或默认值取 | 逐行读身份流经的路径，引位置 |
| 2 | 凭据有没有进日志、错误信息、事件载荷或测试夹具 | 引位置 |
| 3 | 契约要求同一提交的两处写入，是不是在同一个存储事务里 | 指出两处写入共同所在的事务。时间判断、进程内锁、没落盘的事实不算 |
| 4 | 已触发的形式任务与故障注入有没有实际运行的输出 | 读证据的路径与时间。只有登记、没有输出的不算 |

## 进轨道

1. 同步轨道头：先 `git fetch`，在工作分支上用普通的 `git merge` 合并 `origin/integration/mainline`，解决冲突并提交；轨道头有破坏性改动时先读它的 PR。同步由事件触发：开 PR 之前，以及轨道头进了破坏性改动之后；不按日历。
2. 先跑改动成员的合入检查（接入节那一格），再 `pnpm run preflight`，最后在最终 head 上跑一次 `pnpm run admission`。准入占一个运行名额（一台机器两个）、不读缓存，不是第一道检测器。整跑没有通过时不重排整跑：照 `references/admission-evidence.md`「整跑没有通过时」把每处失败归类，再按类补证。时红时绿的失败不归给机器的负载。没验到的写「没验」与原因，不写成通过。证据要盖住什么、轨道头前进了怎么办、确认说明怎样写、哪些情形必须整跑，都在那一页。
   改动碰到契约成员时，「契约变化」一节照 `references/contract-change.md` 判级别。
3. 推送个人工作分支，开 PR 进 `integration/mainline`，用 PR 模板 `.github/pull_request_template.md`，写「所含的卡」（只列本卡）与「契约变化」两节。标题与正文按 `CONTRIBUTING.md` 写，标题用具体的 `type(scope)`。PR 标题和正文不加 `Generated with <agent>` 一类的工具署名页脚，宿主自动附加的也删掉。每次上下文压缩之后，重新对照 `CONTRIBUTING.md` 核对这些格式。
4. gate：派发 `gh workflow run gate-publish.yml --ref github-gate -f pr=<号> -f head=<完整 head>`，参数见 `github-gate` 分支的 `gate/README.md`。
5. 确认：只有 admin 能确认 `publish`。说明写明本地运行的检查及结果、已核对的卡上条件，按 UTF-8 字节不超过 1024。没有该 admin 对本次动作的授权时，停在等待确认，把运行链接交回。负责人在卡上授权代为确认时，说明中注明代为确认的人，后台运行下面的命令，等完成通知，不手工轮询 `pending_deployments`：

   ```sh
   node --experimental-strip-types tools/dev-flow/src/integration/gate-cli.ts wait --run <运行号> --note <说明文件> --environments <环境列表>
   ```

   环境列表只写 `publish`，每次发布只确认一次。改动命中 `github-gate` 上 `gate/toolchain-paths.txt` 的工具链路径时，在说明里写明为什么改这些路径。
   这条命令每 10 秒看一次运行，最多等 90 分钟（`--interval <秒>`、`--timeout <分钟>` 可改）。运行结论是 `success` 退出 0，别的结论退出 1，超时、读取失败或批准失败退出 2。说明去掉首尾空白后不能为空，超过 1024 字节时命令在发出任何请求之前就退出 2。长度按字节算，不按字符：中文一个字占 3 字节，大约只能写 340 个字。详细的写进卡评论，说明里给评论的链接。命令不判断当前身份有没有获得授权，只在该 admin 授权这一次确认之后运行。
6. 读回：运行成功，目标分支等于流程报告的结果，记录标签存在，PR 上有发布决定评论。

既有授权能覆盖精确动作时沿用，不重复询问。发布真实 ref 或写平台仍须任务授权及工具核验的真实决定；本技能本身不授写权。

## 提升与发行

四条主干（`integration/<track>`、`main`、`stable`、`release`）只经 PR 与 `github-gate` 流程进入。本机的候选、验证、发布与采用命令已删除。派发、确认与读回同[进轨道](#进轨道)第 4 到 6 步，下面只写不同之处。

### 三类 PR

| 动作 | base | head |
|---|---|---|
| 送入轨道 | `integration/mainline` | 个人工作分支 |
| 提升 | `main` | `integration/mainline` |
| stable | `stable` | `main` |

- 其他组合会被拒绝，包括个人分支进 main。
- 提升 PR 的「所含的卡」列出自上一次提升以来合入 mainline 的全部卡，行格式见 `gate/README.md`「提升 PR 的说明」。提升携带轨道的完整前缀，不手选卡或 cherry-pick。mainline 攒够完整的一小批就提升，不长时间累积漂移。
- mainline 提升 main 的 PR 开出后，跑一次整仓健康读数：在 PR head 的干净检出上先 `pnpm run acceptance`（严格模式要同一提交的验收账本），再 `pnpm run loop:status --strict --base origin/main --out <目录>`，把 `<目录>/status.md` 的硬线、带位与超预算成员几段贴成提升 PR 的一条评论。它只报告不挡：退出 1 也照贴，写明哪条硬线或哪个传感器没数据，由负责人决定处置。
- stable 派发另加 `-f checkpoint=<名称>`。
- 提升不自动接受或关闭卡。

### npm 发行

`@omne-harness/repo-toolchain` 与 `@omne-harness/repo-config` 由 `gate-release.yml` 发到 npm，流程的参数见 `gate/README.md`。

- 要发布的提交必须已有 unit 记录，并在 `main` 或 mainline 的 first-parent 历史上。版本号取自那个提交的 `package.json`；npm 上已有的版本不再发布。
- 确认走 `npm-release` 环境，必须填说明；用 `gate-cli.ts wait` 等它时环境列表写 `npm-release`。
- 仓库检查运行哪个版本由 `pnpm-workspace.yaml` 的 catalog 钉住。升级先发版本，再开改钉子的 PR。
- 本机入口在仓库根：`pnpm run release-run --input <绝对路径的输入文件> --journal <绝对路径的日志目录>`。输入是一份 JSON：`schemaVersion: 1`、`repo`、稳定的 UUID `operationId`、`package`（只接受 `repo-toolchain` 或 `repo-config`）、完整提交号 `commit`、正整数 `issue`、布尔 `dryRun`、完整提交号 `workflowHead`（这次核对过的 `github-gate` 提交，派发前工具会再比一次）。缺省只观察审批；要批准时显式加 `--approve --note <绝对路径的说明文件>`。`--timeout <秒>` 缺省 5400，超时不取消远端的运行。
- 恢复用同一份输入和同一个日志目录。没有精确的派发回执时保持 unknown，不照最新的一次运行去猜，也不重复派发。
- npm 发行没有 PR 和目标分支：读回 registry 上的版本与完整性，以及 Issue 上的发布决定评论。

### 流程停止与恢复

照 `references/gate-recovery.md` 做。最常用的三条：

- 流程停止时按报告处理：PR head 或目标在派发后变了就重新派发；合并冲突先在来源分支解决；来源轨道缺 unit 时先闭合缺口 Issue。
- 不用 admin 权限修改规则集绕过流程。流程失效时的恢复只由 admin 做；没有该 admin 对这一次恢复的明确授权时，停下报告。
- 运行结果未知时，先读运行页面、目标分支和 `omne/gate/*` 标签。目标已等于结果并且标签存在，就按已发布处理，不重新派发。

## 交回与接受

1. 验收标准要求的证据贴到卡评论：命令、输出尾部、摘要与关键行，原件位置与哈希写在评论里。贴完再清理原件。
2. 交回报告写每条验收的达到与否、没做的及原因、过程偏差。做过提升或发行的，另写固定输入、命令与真实退出、Git 观察、逐卡 declared/observed/unknown，以及实际未验证的部署前提；fixture、真实仓库检查、平台权限和宿主加载分别说明。
3. 接受由有权者决定。决定评论按 `references/decisions.md` 的字段写，读回后关卡。代笔时写明授权人原话。部分认可、取消、撤销与重开也照那一页。
4. 只有清理条件和动作权限都闭合后，才清理工作树或唯一 tmp。
