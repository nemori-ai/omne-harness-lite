# 契约变更

什么时候读：改动碰到契约成员的公开面；要写 PR 的「契约变化」一节；`omne-contract-api` 报了 `review`；开发中发现必须做破坏性改动。

路径都从执行仓库的根算起。

## 契约成员是哪些

契约成员是 `docs/engineering/delivery-lines.json` 各组 `contracts` 列出的成员。这张表只回答哪些成员是契约成员。分组只为好读，不划归属。文件名与 `lines` 键沿用原名：契约检查按同一路径读历史提交上的这张表。

## 三个级别

PR 的「契约变化」逐个列出改动过的契约成员与它的级别。没有改动契约成员时只写一行「无」。

| 级别 | 含义 | 那一行还要写什么 |
| --- | --- | --- |
| `none` | 不改这个成员的公开面 | 不用写 |
| `additive` | 只做可加改动 | 新增的导出或字段 |
| `breaking` | 做了破坏性改动 | 承接它的卡 |

卡级按本卡起点到候选 head 的改动判断。

## 可加改动怎样判

构造一个值的一方是写方，读取它的一方是读方。一个契约类型的写方包括它的每个提供者与替身。消费者传入的回调，参数由提供者写、消费者读，返回值由消费者写、提供者读。

可加改动是不破坏任何已有写方或读方的改动。下表列常见形状，不穷举；没列出的改动也按「破不破坏任一已有写方或读方」判断。

| 改动 | 对写方 | 对读方 |
| --- | --- | --- |
| 加可选字段 | 不破坏 | 不破坏 |
| 加必填字段 | 破坏 | 不破坏 |
| 必填改为可选 | 不破坏 | 破坏 |
| 可选改为必填 | 破坏 | 不破坏 |
| 删除字段 | 破坏 | 破坏 |
| 给联合加成员 | 不破坏 | 破坏；契约事先声明这个联合开放时不破坏 |
| 从联合删成员 | 破坏 | 不破坏 |
| 给由别人实现的接口加必填方法 | 破坏 | 不破坏 |

这张表的由来与设计方法在 `.meta_harness/human/stable-contracts.md`。它是说明材料，规则以本页为准。

## 破坏性改动

1. 卡没有把破坏性改动写进验收标准，而开发中发现必须对契约成员做破坏性改动：停下依赖这项改动的工作，在卡评论里写明改动与受影响的契约成员，由人拍板。不依赖它的工作照常做。
2. 人同意之后，破坏性切换一次完成：切换提供者，同步全部真实消费者，删除旧形状。不留兼容的旧形状。
3. 破坏性改动按 L3 合入，收口时照 `SKILL.md`「L3 热点清单」核。

## 工具报 `review` 时

`omne-contract-api` 把它证明不了可加的改动分为 `review`。`review` 不是契约级别，它要人判断这个改动可不可加：

1. 卡的接受者在卡评论里写结论。
2. PR 的「契约变化」按结论申报 `additive` 或 `breaking`，并链接那条评论。

负责人已经对这张卡授权过破坏性改动时，按 `breaking` 申报，写明授权的原话与时刻。
