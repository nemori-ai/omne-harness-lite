# 准入证据怎样取得

什么时候读：准备跑准入；准入没有通过；轨道头在准入之后前进了；要写 gate 的确认说明；要做提升 `main` 或进 `stable` 的全量准入。

路径都从执行仓库的根算起。

## 准入回答什么

准入回答一个问题：这次改动合进目标之后，它影响得到的每一项检查通过了没有。回答它的是证据。一次整跑通过是最省的一份证据。整跑没有通过时，按失败的原因补证，不为了得到一次全绿的整跑反复排队：构建与类型检查每一次都从头跑，一次准入占着这台机器两个运行名额里的一个。

## 先便宜后贵

前一步没过不做后一步：

1. 改动成员的类型检查、快层、慢层，有验收的跑验收。
2. `pnpm run preflight`。它只跑轻步骤，不占运行名额。
3. 一次准入：`BASELINE=<目标分支> pnpm run admission`。不给基线时取 `origin/main`。

准入不是第一道检测器。类型错、格式、写范围、改动成员自己的用例，都该在前两步里发现。

## 准入是怎样的一次运行

- 进入任何一条主干之前的检查都是准入检查。`pnpm run admission` 带着 `OMNE_ADMISSION=1` 运行，不读 turbo 的任务缓存，只写本地缓存。原因：缓存命中时任务不会真正运行，检查显示通过而实际没有跑。没有带这个变量的运行不作为准入结论。
- 成员测试的结果记录是另一条规则：准入只认准入模式下真跑出来的记录。输入没变的成员不重跑，输出里逐个写明取自哪个提交、哪个时刻的运行。
- 提升 `main`、进入 `stable` 的全量准入是 `OMNE_ADMISSION=1 FULL=1 pnpm run check`。带 `FULL=1` 的准入不认任何记录，全部重跑。

## 整跑没有通过时

先把每一处失败归到下表的一类，再照那一类补证。同一个头上不排第二次整跑。

| 失败是哪一类 | 怎样判 | 怎样补证 |
| --- | --- | --- |
| 本次改动带来的 | 在基线上单独跑同一个用例文件是通过的，或者它测的就是这次改的东西 | 修。修完按「增量准入」接续 |
| 起点上本来就失败 | 在基线上单独跑同一个用例文件，同样失败 | 不在这次修。确认说明里列出它，附基线上的命令与输出。没有登记过的开一张 issue，说明里带上链接。它不挡这次合入 |
| 时序上的竞争 | 整层一起跑时红、单独跑时绿；失败是超时、等待没等到，或某一步的先后变了 | 把失败的用例文件逐个单独跑，或用 `pnpm run test:triage --run <那次运行的目录>`。单独跑稳定通过可以作这一次合入的证据，但要同时做下面一段说的两件事 |
| 环境 | 缺工具、缺离线缓存、工具版本不对 | 修环境，只重跑受影响的那一步。修不了的在说明里写「没验」与原因 |
| 说不清 | 单独跑时过时不过 | 当成本次改动带来的去查。查清之前不合入 |

失败让后面的层或步骤没有跑时，补跑没跑到的那一部分：改动成员逐个跑慢层；计划判了全量的，用 `pnpm run test:tier slow`。

单独跑通过只说明那个用例自己没有逻辑错误。时红时绿不归给机器的负载：负载只改变两件事谁先到，会因此变红，说明代码或用例里有一个竞争，或把一个上限当成了答案。归到「时序上的竞争」的每一处，做两件事：

1. 在基线（目标分支的头）上照同样的条件跑两三遍，分清它是这次带来的还是原来就有的。照同样的条件，指整层一起跑，不是单跑。这次带来的，按第一行处理。
2. 原来就有的，在确认说明里写它的机制，不写「负载」两个字：哪一步偶尔失败，谁凭哪份滞后的事实做了决定。机制没查清时写取到了哪一步，并开一张 issue 记下复现条件与已有的事实。

## 证据要盖住什么

计划选中的每一步、每个成员的每一层，都至少有一条通过的记录。记录可以来自三处：整跑里通过的；接续里通过的；单独跑通过的。哪一处都没有的，在确认说明里写「没验」与原因，由确认者决定接不接受。不把没验的写成通过。

## 轨道头在准入之后前进了

不为它重排整跑。看新进轨道的提交改了什么：`git diff --name-only <旧轨道头> <新轨道头>`。

- 它们和这个 PR 影响到的成员没有交集：原来的证据照用。确认说明里写明两个轨道头。
- 有交集：只补跑交集里的成员的快层与慢层。
- 合并有冲突：先在来源分支解决，再补跑冲突涉及的成员。各源单独通过不能代替合并之后的结果。

## 共用的机器

- 重的入口经运行名额排队：根 `pnpm run check`（整套占一个名额）、`pnpm run admission`、`pnpm run test`、`pnpm run test:affected`、`pnpm run test:tier`、`pnpm run acceptance`、`pnpm run closeout:mutation` 等。带 `--plan-only` 时不占名额。同一台机器同时至多两个名额，每个名额拿到的进程预算是（核数 − 2）÷ 2，两次同时跑不互相挤。
- 两个名额都占着时排队等它，不另起一次。日志里出现 `with-test-slot: 排队中` 时，占用者记在锁目录里（缺省是系统临时目录下的 `omne-test-slots-<用户>`，`OMNE_TEST_SLOT_DIR` 可以改）。
- 名额随持有它的包装进程退出而释放。要中止一次占着名额的运行，杀整棵进程树（`kill -- -<进程组>`）；只杀包装进程，被包装的命令会成孤儿接着跑，名额却已经放了。
- 准入在跑时，同一个会话不起别的测试、构建或变异，也不派子代理去读写同一棵工作树。
- 成员级的测试（在成员目录里 `pnpm exec vitest run …`）不占名额，别的会话可能同时在跑。出现一批超时类的失败时，记下当时机器上还在跑什么，这是复现条件的一部分，不是原因。

## 确认说明怎样写

说明要让确认者看得出证据盖住了什么：

- 对象：哪个头，和哪个轨道头的合并结果。
- 哪些是整跑里通过的。
- 哪些是补证的：归到了哪一类，单独跑的命令与结果。
- 哪些没验，为什么。
- 没有整跑通过，就写没有整跑通过。

说明按 UTF-8 不超过 1024 字节。写不下的细节放进卡上的评论，说明里给出评论链接。

## 必须整跑通过的情形

下面两种不按上面的办法组合证据：

- mainline 提升 `main`、`main` 进入 `stable` 的全量准入。它可以按「树相同时复用准入」。
- 卡或负责人点名要求整跑的。

## 增量准入

准入只有一步失败时，修复后做增量准入，不整次重跑。三项前提都成立才适用：

1. 头 H1 上整次运行了一次准入（一次 `pnpm run admission` 或带 `OMNE_ADMISSION=1` 的 `pnpm run check`，不是逐步组合），范围按本次要求。它在步骤 X 快速失败，其他跑完的步骤都通过。
2. 修复后得到最终头 H2，H1 是 H2 的祖先。
3. H1..H2 的差异不碰全局路径。全局路径以 `tools/test-runner/test-runs.config.json` 的 `affected.globalPaths` 为准，例如锁文件与工具链配置。碰到时在 H2 上整次重跑。

命令：`pnpm run admission --resume-from <H1>`。它读 H1 那次准入写下的运行记录，自己核对前提，不满足就以 2 退出并写明原因；碰到全局路径时自己改成整次重跑。它在 H2 上跑的是：

1. 失败步 X。
2. H1 上因快速失败没有跑完的全部步骤。
3. 全部轻步骤。
4. 在 H1 上已通过的重步骤（构建、类型检查、成员测试与验收），只对 H1..H2 的差异影响到的成员跑。

前三项的范围与 H2 上整次运行相同，只有第 4 项以 H1 为基线收窄。接续运行的记录不能再当 H1。

证据写成「H1 上的整次准入（失败于步骤 X）加 H2 上的增量准入（基线 H1）」，并附 H1..H2 的差异。

H1 上的准入没有留下记录时，用 `node --experimental-strip-types tools/test-runner/src/testing/cli.ts` 的三个子命令手工组合，运行时带 `OMNE_ADMISSION=1`：`check --list` 打印步骤表（步骤名、前置、轻重、命令）；`plan --json <路径>` 写出计划文件，第 4 项用 `plan --base <H1> --json <路径>`；`step <步骤> --plan <计划文件>` 按计划执行 `python`、`build`、`typecheck`、`test`、`acceptance` 中的一步，其余步骤按步骤表里的命令跑。

## 树相同时复用准入

要在一个提交 F 上做全量准入时（例如 mainline 提升 `main`），F 的树与一个已通过全量准入的头的树相同，那次准入就是 F 上的全量准入，不重跑。

- 核对：`node --experimental-strip-types tools/test-runner/src/testing/cli.ts admission-evidence --for <F>`。它在本树 `tmp/admission/*.json` 里找树与 F 相同、干净、每步都通过的全量准入记录。接受时写明两个提交与树哈希并退出 0，否则逐项列出拒绝原因并退出 1。手工比对用 `git rev-parse <提交>^{tree}`。
- 准入证据写明两个提交与同一个树哈希。
- 那次准入可以是按「增量准入」组成的证据，但 H1 上的整次运行必须带 `FULL=1`。只按影响面运行过的，组不成全量准入。
- 这一条只替代全量准入。联调验收的命令照常在 F 上跑。
