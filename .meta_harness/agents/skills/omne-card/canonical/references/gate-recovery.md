# gate 停下、结果未知与恢复

什么时候读：gate 的运行停了或失败了；不知道一次发布成没成；合并有冲突；`gate-reconcile` 开了缺口 Issue；要清理轨道上的分支、工作树或临时材料。

gate 流程怎样判定、命令与参数，以 `github-gate` 分支的 `gate/README.md` 为准。这一页只写代理与管理员要照做、而流程自己不替你做的事。

## 先分清是哪一种

| 看到的 | 是什么 | 做什么 |
| --- | --- | --- |
| 运行报告 PR head 或目标在派发之后变了 | 派发时的输入过期 | 重新派发，传现在的 head |
| 运行报告合并冲突 | 来源与目标改了同一处 | 见「冲突」 |
| 运行报告来源轨道缺 unit | 有主干提交没有记录 | 见「缺口」。先闭合缺口，再提升 |
| 不知道运行成没成（超时、断线、页面读不到） | 结果未知 | 见「结果未知」 |
| 流程本身出错，或 Actions、发布身份用不了 | 流程失效 | 见「流程失效」。只有 admin 能做 |

不用 admin 权限改规则集来绕过一次正常的停止。

## 结果未知

1. 读运行页面、目标分支和 `omne/gate/*` 标签。
2. 目标分支已经等于这次的结果，记录标签也在：按已发布处理，不重新派发。剩下的接受与卡上的记录交回各自的拥有者。
3. 目标没动、标签不在：这次没有发布。核对 PR head 与目标之后重新派发。流程每次都重新核对目标与 PR，重复启动不会重复发布。
4. 目标与标签对不上（一个在、一个不在）：保留证据，停下报告，不重建、不重试。

Git 已经发布而卡上的记录没写上时，由那条记录原来的写入者补记录，不重放 Git。

## 冲突

- `gate-publish` 遇到冲突就停。冲突在来源分支上解决：在工作分支合并目标的头，解决，提交，推送，再派发。
- 不直接改共享的目标分支来解决冲突。
- 冲突涉及含义上的取舍时，交那段语义的拥有者定。
- 解决冲突之后的合并结果要实际组合验证一遍。各个来源单独通过不能代替它。

## 流程失效

只有 admin 做。没有该 admin 对这一次恢复的明确授权时，停下报告。

- `github-gate` 上的流程出错：admin 修正 `github-gate`，再启动流程。
- Actions 或发布身份不可用：
  1. admin 在一张 Issue 里写明原因。
  2. 临时把自己加入相应规则集的例外，用普通的 Git 命令完成合并并推送。
  3. 恢复规则集，读回确认。
  4. 这样推上去的提交没有 unit 记录，`gate-reconcile` 会把它报成缺口 Issue。照「缺口」闭合。

admin 改规则集属于管理权限；定时核对与记录核对照常适用。

## 缺口

`gate-reconcile` 每小时核对一次，只开缺口 Issue，不创建标签。缺口在，相应主干的提升被拦住。缺口不设处理时限。

没有 unit 记录的主干提交，两步都做完才算闭合：

1. mainline 的 owner 或任一 admin 在缺口 Issue 里写具名决定：缺口提交的来源、处置，以及它带来的卡（Issue 编号）。
2. admin 在 `github-gate` 的 `gate/cutover.json` 里，把这条分支的切换点改成缺口中最后一个没有 unit 的 first-parent 提交，并在缺口 Issue 里注明这次修改的提交。

只移动切换点不算闭合：它只改变核对范围。

stable 的尖端没有记录：admin 在缺口 Issue 里写具名决定，stable 下一次经流程发布之后闭合。

## 清理之前

清理轨道上的分支、工作树或唯一的临时材料之前，先核三件事：Git 已经发布；各卡剩下的接受与记录责任已经交接；唯一的临时材料有去向。然后按已有的权限清理。

ref 的状态未知或分裂时保留证据，不重建、不重试。`git revert` 不撤销外部的副作用。

## 已知的限制

- admin 停用规则集之后直接推送主干，平台拦不住，只能事后从组织审计日志与定时核对里发现。
- 有一种情形流程分辨不出：admin 在流程最后一次读取目标与推送之间，把 stable 直接推到这次要发布的同一个提交。这时流程仍会写入记录。
- 流程不运行测试。确认暂代轨道的自动检查，所以确认说明里要写明本地实际跑了哪些检查与结果。确认不等于交付接受。
