# 产品正文结构与支持状态

起草完整产品正文或重组其阅读方式时采用本结构。局部修订只处理受影响内容。
产品负责人指定分步交付时先完成已授权块，其余显式留空；不能为结构齐全擅自选择版本范围。

完整的 design.md 设以下四个主块，可在块内按阅读需要分节。范围、非目标及已确定职责
放在产品需求描述中，实现缺项及证据放在能力状态中，已确认的版本范围放在阶段承诺中。
最后一块为“未决问题与待定事项”，维护仍有效的缺项及其责任，不收录修订沿革或已答问答。
任务 notes、评审与过程报告不使用此结构限制。

## 四块内容

| 块 | 为读者回答什么 | 必要内容 |
| --- | --- | --- |
| 产品需求描述 | 谁为什么需要它，怎样完成关键目标，选择和限制有什么后果 | 连贯需求叙述、关键用户路径、必要概念、规则及边界；框架契约、可定制范围和默认方案分别表达 |
| 能力定义与实现状态记录表 | 产品要求哪些可辨能力，系统是否实际支持 | 独立提炼的能力定义、稳定编号、需求定位、实现支持及限制、验证事实、接受状态、证据版本与适用装配 |
| 阶段与版本支持承诺 | 哪个明确阶段或版本承诺支持哪些能力 | 能力编号、支持程度、适用装配、必要前提及负责人已确认的范围 |
| 未决问题与待定事项 | 哪些仍有效的问题影响产品、阶段或后续技术，谁决定或维护 | 原问题标识、类别、影响、决定或维护责任及唯一现行位置 |

## 需求叙述与能力定义的分工

需求按用户的问题和关键路径组织。先让读者理解目标，再说明成立条件、选择、参与者及可观察结果。
例如，带一份个人资产进入团队是用户路径，复制、持有和组织接收是它所需的不同能力，
不必将这条路径拆成三个互不相接的需求小节。未设计的界面和交互不当作既定路径。

说明文以连贯段落承载意思。标题按读者问题分节，不固定小节数量，不把每段压成规则卡。
跨路径的共同约束只在需求拥有的位置完整说明，具体路径说明该约束造成的后果。
选择对比可用表，操作先后确有要求时可用步骤，散文形式不能省略资格、条件、例外或失败后果。

第二块从需求中提炼能力。每项说明提供什么、适用范围及需求位置，使读者能够判断完整或有限支持。
能力定义可以先分节说明，再集中记录状态，也可以与状态表合并；不强制把长定义挤进宽表。
需求与能力不是一一对应关系，不要求每条局部规则都有编号。按可判断支持程度的功能粒度编组，
能力编号保持稳定，状态和阶段继续引用它；不能因为调整需求标题而重发编号或复制规则。

## 同页记录，含义各有拥有者

产品维护者拥有能力定义。实现拥有者提供并维护支持事实及验证证据，负责人决定产品和交付接受。
产品读者在同页查到这些事实，证据或聚合视图可以链接出去。不得要求读者跳到另一份总表才能知道基本支持情况。

状态表至少使读者能区分目标、基础实现、完整支持、已知偏离和未核实，并分别识别验证与接受。
字段可按内容组织，不能用一个“完成”状态遮掉其中差异。只有现有类型或局部实现时写具体覆盖，
不能称整个能力完整支持。源码未读到不表示能力未实现，测试文件存在不表示已经运行通过。

每份观察说明日期、版本或具体检出、装配适用范围和证据位置。源码观察、行为验证和发布支持分别陈述。
未核实的维度标为未核实。长技术机制不进入表中，由拥有者正文承载。

没有另建权威映射源时，在产品页维护状态。已有实现拥有者维护的权威记录时，产品页引用或生成同页投影，
不再手写第二份状态。更新后核对真实阅读页面及证据是否对应，不把散列一致当作符合性证明。

## 版本承诺与阶段边界

用明确版本区间或发布版本表达阶段，不能写“本期”“下版”代替边界。
例如 `0.0.0 -> 0.1.0` 描述研发阶段，不表示本页全部能力已经进入 0.1.0 的交付范围。
产品目标、当前实现状态及已承诺的版本范围分别有依据。

负责人未决定支持清单时留空并说明缺项。用户要求先阅读能力再选择范围时，完成前两块即可，
不通过建议选项或“默认采用”替负责人作决定。

承诺采用后按能力编号明确完整或有限支持及必要前提。未经接受的预计发布日期、推测版本和代码仓版本号
不能代替产品承诺。失去有效依据的旧支持记录须重新核对，不沿用已过时结论。

## 未决问题与待定事项

先核对有效正文与已有决定，再筛选问题。产品政策与阶段能力选择在第四块完整说明，
阶段承诺块链接相应缺项。既定CAP和已确认阶段范围保持原意，未选择范围仍待负责人决定。
正式目录中的draft仍是待审正文，其位置不表示规则全部接受，也不表示阶段能力已被选择。

精确技术问题及后续设计义务由对应能力组、成员或协调者的工程设计、长期规格维护唯一正文。
产品第四块说明问题对产品或阶段的影响，并链接该正文及维护责任，不复制字段、机制或协议。
尚未具名的成员保留技术拥有者、承接入口及缺项，不另造组根统一SPEC。

来源缺证项写清缺少的依据、受影响判断和核对责任。没有新依据时保留缺口，不补造决定。
其他领域拥有的问题只链接其唯一现行位置，明确排除的范围继续作为非目标。

已回答项先核对答案已经落实到有效正文，再从现行未决中移除。原问答、来源快照和处理过程留任务tmp。
从questions及其JSON承接时保留原问题标识，正式消费者改指第四块或技术拥有者，历史快照不继续作为现行问题源。

## 精确措辞

| 容易失去含义的说法 | 可维护的表达方式 |
| --- | --- |
| 本期不做某能力 | 写明确阶段及已确认的不支持范围 |
| 当前支持登录 | 写观察日期、检出或发布版本，以及实际支持的登录方式和限制 |
| 最新版本支持定制 | 指定版本及定制能力，说明验证与装配范围 |
| 登录八小时失效 | 产品说明存在可配置最长有效期，具体部署参数归对应说明 |
| 管理员可以处理 | 指定哪个组织、管理资格、对象、动作及适用条件 |
| 它随后恢复 | 指明恢复对象、触发条件及允许恢复的状态 |

信息密度来自必要事实与条件，不来自压缩句子。保留不确定性和例外，避免泛化为“完全支持”“任意定制”。
词条精确定义仍归统一语言，产品用必要解释让读者理解，不另造同名概念。
