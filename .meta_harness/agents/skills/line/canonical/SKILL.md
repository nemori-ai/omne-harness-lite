# 线

本技能是 `docs/engineering/integration.md`「集成节点的清单」里「线怎样工作」一节的可执行版。批次、波、收口点、不变量、提前开工、失败处理的规则都归那一节；卡、修订、条件与接受归 `docs/engineering/delivery.md`；认领、派发与看板归 `docs/engineering/agent-delivery.md`。本技能只给顺序、产物与停止点，不另立规则。

## 工作前提：自驱，不提问

从认领线父卡到里程碑结束，没有人或别的 agent 会在波内给你发消息。你的全部输入是线包、线父卡上的 `line-delta`、各卡正文与评论、仓库里的正文。所以：

- 不用 AskUserQuestion，不用任何等待回复的方式提问。等不到回复。
- 写范围之内的实现与设计选择自己定，依据写进本卡的 `spec.md` 和交接报告。
- 写范围之外、需要人拍板、或与拥有者正文冲突的事，按线包第 9 节的停止条件处理：写进线父卡的线状态注，暂停依赖它的卡，继续不受影响的卡，波末照常交批次。调度者在下一波的 `line-delta` 里答复。
- 停下不是失败。停下而不写明，才是失败。

## 术语

线、线父卡、线包、批次、批次 PR、波、收口点、收口卡、`line-delta` 都按 `integration.md`「集成节点的清单」的定义。本技能里「收口卡」指代表一个收口点的交付卡：它关闭，就是下一波开工的事件。

## 流程总览

| 阶段 | 什么时候做 | 产物 | 出口 |
| --- | --- | --- | --- |
| [1 线级准备](#1-线级准备) | 里程碑里本线第一次开工，做一次 | 认卡评论、线级上下文地图主体、线级工程约束、环境就绪 | 自包含检查四问都能答 |
| [2 开波](#2-开波) | 每波开始 | 批次分支、本波队列 | 批次分支指向本波收口点 |
| [3 波内逐卡](#3-波内逐卡) | 每张卡 | 卡的 PR 合入批次分支、交接报告、线状态注 | 本波队列做完 |
| [4 波末](#4-波末) | 本波最后一张卡合入后 | 批次 PR、批次报告、线状态注 | 进入等待 |

## 1 线级准备

本线第一次开工做一次。之后每张卡只做[卡级增量](#3-波内逐卡)，不重做这里的事。

1. 认领线父卡：按 `agent-delivery.md` 写认卡评论（负责的人、宿主与会话、授权依据是线包里的登记授权、现存执行核对）。记下线父卡当前最新评论号，这是读 `line-delta` 的起点。
2. 读线包。从中取得并写进 `tmp/line-<线>/line.md`：本线 ID、线父卡、队列与每张卡所在的波、每波的收口卡、写范围、收口点、线内登记 attempt 的授权依据、准入锁路径、停止条件。线包里标「未核」的事实，开工前自己核一遍。
3. 准备环境：`pnpm install --frozen-lockfile --prefer-offline`，生成 agent 投影，`pnpm run check:agents` 退出 0，记录 Node、pnpm、git 版本。
4. 按 claim 技能「线级一次性准备」写线级上下文地图主体与线级工程约束：本线各卡共用的拥有者正文、禁止的依赖方向、适用的研发品味与防御指导条目、验证级别、要加载的 pstack 与 Matt 技能、执行角色。每张卡之后只补差额。
5. 做自包含检查：只看线包与第 2、4 步的产物，答得出从哪个提交开工、能改哪些文件、做到什么程度算完成、每条事实出处在哪、等哪张收口卡、拿不准时写到哪。答不出的项按停止条件写到线父卡，不猜。

## 2 开波

1. 取本波收口点：首波来自线包，之后来自 `line-delta`。核对它是联调轨道 `integration/legacy-refactor` 的祖先或等于轨道头。
2. 从收口点切批次分支 `<用户名>/w<波号>-<线>`，推到远端。它是个人分支，不经 gate。
3. 本波队列来自线包，`line-delta` 有调整时以 `line-delta` 为准。上一波停下的卡在队列里的位置也由 `line-delta` 给出。
4. 本波第一张卡从这里进入第 3 阶段。波内不合并联调轨道，规则见 `integration.md`「线轨道的同步与提升」。

## 3 波内逐卡

每张卡按 claim 技能走：卡级增量准备 → 按 `plan.md` 推进 → 交回。本技能只定线内的几件事：

1. 登记 attempt 由你以受托调度写者身份做：按 dispatch 技能第 5 至 8 节写 spec、`post`、`bind`、建分支、写本卡的任务信息包。分支从批次分支头切出，taskBase 取批次分支头。登记评论引用线包的授权。
2. 实施与评审各派新上下文的子代理。修复第 1 轮续用实施子代理，第 2 轮换新的。两轮未闭合就停下：这张卡不进批次，批次报告写明，卡进入下一波队列。
3. 每张卡在最后一次改动后自准入：`OMNE_ADMISSION=1 pnpm run check`，按线包的准入锁路径排队。
4. 卡的 PR 以批次分支为 base。核对卡的 integration 阶段条件，自己合入，把 Stage 改为 delivered（`board-cli.ts delivered`）。卡的 PR 与交接报告保留。
5. 每张卡交回后，以及任何一次压缩上下文之前，在线父卡发一条线状态注（模板在 `.meta_harness/human/map-reduce-delivery/templates/line-state.md`）。压缩后从状态注重建，不从记忆重建。
6. 同一条线里后一张卡从前一张合入后的批次头开工，所以同线依赖不写成开工条件，队列顺序就是保证。

## 4 波末

本波最后一张卡合入批次分支后：

1. 开批次 PR：base `integration/legacy-refactor`，head 批次分支。它由线父卡本波的 attempt 承载：binding 的分支是批次分支，taskBase 是收口点，写范围是各卡写范围之并。正文按 `integration.md`「进轨道 PR 的说明」写「所含的卡」与「契约变化」。
2. 在线父卡发批次报告：卡号、每卡的 PR、批次头、每卡的自准入证据、未进批次的卡及原因。
3. 写一条线状态注，然后进入第 5 阶段。
4. 提前开工：下一波队列里开工条件已被本波收口点满足的卡，可以从本波收口点再切一条批次分支先做。下一个收口点出现后，先把它合进这条分支，再登记后面的卡。提前开工的卡在下一波波准入时一并核对。

## 5 等收口

要等的事件是本波收口卡关闭（GitHub `issues` 事件的 `closed`）。收口卡的编号在线包第 1 节。

- 等待必须阻塞在事件上，不轮询 GitHub：运行 `node --experimental-strip-types tools/dev-flow/src/delivery/wait-cli.ts issue-closed --issue <收口卡>`。命令阻塞到本机事件文件里出现该卡的关闭事件才返回；接收器与 `gh webhook forward` 的启动方法见 `tools/dev-flow/src/delivery/README.md`「事件等待」。
- 在 Claude Code 里用 `Monitor` 工具运行这条命令，会话在返回前不消耗推理。其他宿主用各自的阻塞运行机制；没有的宿主在线状态注里写明怎样等。
- 返回后读线父卡上起点之后的新评论，只认 `<!-- line-delta -->` 标记，按序号去重。`line-delta` 给出新收口点、本线下一波队列与写范围、被退回的批次。
- 批次被退回时，`line-delta` 写明原因。在本波内修复后重新开批次 PR，沿用线父卡的同一个 attempt，head 前进。然后回到本阶段。
- 收口卡关闭了却没有 `line-delta`：等下一条。它由调度者写，不会被别的评论替代。

然后回到[2 开波](#2-开波)。

## 6 里程碑收尾

最后一波收口后，在线父卡发线交接报告（模板在 `.meta_harness/human/map-reduce-delivery/templates/handoff-report.md`）：每波的批次与结果、停下过的事与答复、未进批次的卡、剩余责任。线父卡的接受归调度者。

## 已知的坑

- 批次分支在波内不合并联调轨道。合了就破坏「波内独立」，批次会被退回。
- `start` 写的 targetBase 是远端联调轨道头，与批次分支分叉是预期结果。影响面以批次分支头为准。
- 两张卡同时在跑准入会互相拖慢。按准入锁排队。
- 压缩上下文前没写线状态注，压缩后就找不回进度。
