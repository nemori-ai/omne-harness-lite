# 线会话的工作范式

本页给出常驻线会话在多波之间反复复用的做法。目标有两个：每次被派发都能快速进入状态；每个闭包不重复做重的上下文收集。

本页只组织做法，不另立规则。规则仍归各拥有者：协作规则归 `docs/engineering/integration.md`「集成节点的清单」，线父分支与闭包门槛归同页「线父分支」，切闭包与派子代理归 `delegate` 技能，本波有几张卡时的一次认领归同页「本波有几张卡」与 `claim` 技能，常见失误归 `.meta_harness/human/delivery-pitfalls.md` 的 P1–P29，方法采用归 `docs/engineering/skills.md`。

## Reduce 与你的分工

Reduce 是项目总负责人，你是本线的 dev team lead。Reduce 每波只给你三样：线包、线父卡上本波的一个 attempt、首次消息或 delta。

- **Reduce 定目标、边界与验收。** 线包写本线里程碑的目标与验收，以及本波的交付边界：成果、判据、明确不做、跨线契约与冻结输入、需 Reduce 批复的设计点、停止条件。理由：这些决定牵动别的线和整个里程碑，只有 Reduce 看得到全局。
- **你定拆分与调度。** 怎样拆闭包、排顺序、派子代理、并行，以及线内的合并与联调，都由你决定。理由：离代码最近的人最清楚怎样切得干净。Reduce 替你切，只能凭更少的信息。
- **少建卡。** 线内工作不需要 Issue。确有独立跟踪价值时，你才自建子卡，挂在线父卡下。理由：卡越多，派发、交接与等待的无效时间越多。闭包表与 `tmp/line-<线>/` 足以记录线内进度。
- **本波有几张卡时一次认领。** 线包可能列出载体卡，你也可能自建子卡。你一次认领本波全部的卡，在同一条父分支上推进，最后只开一个集成 PR。理由：几张卡各走一遍认领、准入和 PR，等待时间成倍增加，而它们本来就在同一条线、同一波里联调。
- **边界外的事交回。** 想做线包没写的事，或想越过停止条件，先交回，不自行扩大。理由：扩大范围会推迟本波交付，也会改变别的线的冻结输入。

线包的附录「建议闭包与依赖」只作参考。你按实际代码重新切，不必照抄。

## 线负责人的思维模型

本节是品味与方法，不是条款。规则仍归下面点名的拥有者。

1. **你是派发者和判断者，不是主写者。** 你的产出是闭包切分、规格、验收和取舍。实施交给子代理，你读 diff 并判断。理由：一个会话只有一份注意力，花在写代码上，就没有人看全局。拥有者：`delegate` 技能。
2. **并行靠切得干净的闭包。** 写范围不相交，依赖写明。两个闭包点不出争用的文件、类型或资源，就并行。理由：并行度由切分质量决定，不由派发的勇气决定。拥有者：`delegate`「切闭包」；只读的扇出与汇总用 pstack `swarm`，写者仍按 `delegate` 隔离。
3. **规格与验收写死边界，子代理只在边界内发挥。** 闭包规格给出写范围、判据、命令和停止条件。子代理的交回是证据，不是接受。理由：边界不清时，子代理会自由发挥或过度设计，返工比多写一段规格贵。拥有者：`delegate`「写规格」「独立验收」「评审派发」。
4. **模型按活定档，从经济档起步。** 先用够用的档位。跑偏时追加纠偏，并计入追加次数。追加不行再升档。理由：多数活不需要顶档，升档的依据是实际证据。拥有者：`delegate`「选模型」与派发台账。
5. **以线包的本波交付边界为边界。** 先让它工作，够了就收口。核心保证守住后，剩余边角写成已知限制。不追加机制，不提前优化，不做「明确不做」里的事。理由：每个多出的机制都要有人维护和验证，也推迟本波交付。拥有者：`docs/engineering/quality.md`「够了就收口」；品味见 `.meta_harness/agents/roles/engineering-taste.md`。

## 决策权：三层，默认自己推进

每个决定先归层，再动手。归层理由写进决策记录；判不准时按第二层处理，写明「归层不确定，按第二层处理」，并告知一次。

- **第一层，自定，不记录，也不告知。** 排期、闭包怎么切、子代理的角色与档位、测试接缝放在哪、目录内怎么组织、先做哪个切片。这些都在线包给的范围之内，是 team lead 的本职。
- **第二层，自定，留一句决策记录，波内告知一次。** 三条同时成立：改动在本线写范围内；不改任何已接受的正文（SPEC、产品规则、契约成员的公开形状）；可撤回，且没有第二个消费者现在就要依赖它。典型：线内成员的位置与内部形状、线内新增依赖与锁文件条目、守卫表这类实施输入、线自己成员的设计候选结论。做法：结论贴在线父卡上并带 `<!-- line-decision-record -->`，写回本线成员的正文，波内告知 Reduce 一次，然后继续，不等批复。Reduce 在 RI 时核对，核对出问题直接找你，不推翻已做完的工作。
- **第三层，等 Reduce。** 只有五种：改已接受的正文；改本线写范围之外的路径，或别的线、联调轨道要消费的文件；跨线交接内容变了而对方已按旧约定在消费；不可撤回的动作（关别人的卡、删分支、发版、动平台设置）；产品负责人才能拍的新规则。交上去写三行：改哪份正文、为什么必须改、不改的后果。

**为什么：** 线负责人把本该自己拍的设计点与批次事项交上来等批复，时间会花在排队而不是推进；线包把范围写得太紧、把线内依赖条目当成集成节点单写，也会让线在加依赖时停下来问。两种情况都让一个本来能自己走完的决定停在等待上。**默认可推进，不默认停下。**

**依据：** Reduce 与线的分工归 `docs/engineering/integration.md`「线父分支」。带标记的评论按非交付决定读，不写「决定」列表字段，见 `.meta_harness/human/delivery-pitfalls.md` P24。

## 核心想法：按存续期分三层准备，每层只做差额

| 层 | 什么时候做 | 产物（放 `tmp/line-<线>/`） | 什么时候刷新 |
| --- | --- | --- | --- |
| 会话级 | 线会话第一次开工，做一次 | 身份与长程目标、方法地图、环境记录、线级上下文地图主体、线级约束 | 换会话接续时读回，不重做；delta 写明拥有者正文变了才改对应条目 |
| 波级 | 每次读到 delta | 本波变化摘要：新 F、reduce 做过的消费者迁移、外域变化。active 时另有本波的 `spec.md` 与 `plan.md`（闭包表） | 每个 delta 一次，只写变化 |
| 闭包级 | 每个闭包派出前 | 闭包规格 | 只写本闭包相对本波计划的差额 |

判断一项内容放哪一层，只问一句：**它在下一个闭包、下一波还成立吗？** 成立就上移一层，只写一次。

反面做法：每个闭包重读整套设计正文、重写完整上下文地图、重新选技能、重新整理线级约束。这些都属于会话级，做一次就够。

## 会话级：开工时一次做好

1. **身份与长程目标。** 写下：本线是谁、线父卡、线包里本线里程碑的目标与验收、里程碑卡的关闭门、本线结果服务哪道门。以后每个局部决定都回到这里核对。
2. **加载技能。** 先加载 `line`、`pstack:poteto-mode`、`asd-ste100`，读取实际工作树的 `AGENTS.md`、`docs/orientation.md`、线级上下文地图与拥有者入口；实施前读 `ub-mode`，并按本线工作类型加载专项技能。本波有几张卡时按 `claim` 一次认领；评审用 `review-code`、`review-docs`、`review-delivery`；派子代理时加载 `delegate`。改文档前加载 `asd-ste100`。
3. **方法地图。** 按下一节写一份本线版本：本线的主工作类型对应哪个 playbook，三层各用哪些技能，哪些项目规矩最常碰到。
4. **环境。** 依赖安装、生成 agent 投影（`node --experimental-strip-types tools/dev-flow/src/integration/worktree-cli.ts projections --tree <树>`，它最后运行 `check:agents`）、`check:agents` 通过；记下 Node、pnpm、git 版本。
5. **线级上下文地图主体。** 本线各波共用的拥有者正文、系统图景入口（`docs/orientation.md`）、最容易踩的耦合与禁止的依赖方向、相邻线的接口、读者角色。reduce 已给出时只核对。
6. **线级约束 `constraints.md`。** 借用 `claim` 技能 spec 模板「原则与约束」的格式，写本线适用条目（ub-mode 加项目独有判断），只写一次。

出口：自包含四问能答：从哪个提交开工、能改哪些文件、做到什么程度算完成、每条事实的出处在哪。

## 波级：读 delta，只记变化

1. 读 delta：新 F、本波 assignment（active、idle、redo、terminal）、reduce 做过的修改与消费者迁移、外域变化。
2. 写本波变化摘要。delta 提到的拥有者正文若在线级地图里，只更新那一条。
3. active：核对从新 F 到线轨道的 FI 结果，读回 Reduce 已从本波 attempt 的 taskBase 建好的父分支，在父分支工作树上运行 `start`，用 `status` 读回。不重放上一波的补丁。然后写本波计划，见下一节。
4. idle：只做第 1、2 步，然后继续等。这一步让下一次开工几乎零成本。
5. redo：按线父卡上的新 attempt 重开，波号不变。
6. terminal：交最终报告，结束。

### 绑定在 `start` 之后不变，换树是一次全新准备

**什么时候适用：** 波中发现自己需要扩写范围，或线包、裁定要求在派发之后加路径。

**怎么做：** 先判断能不能留到下一波。确实必须在本波扩，就在扩之前告诉线负责人「波末要换树」，不要等波末才发现。`start` 之后 binding 与写范围都不再改：手改卡正文不算，只改派发行而不重发评论也不算，给同一个 attempt 起新 attempt 号也不算。已经在 `start` 过的树上重跑 `start` 会报这棵树已绑定另一个任务。

**为什么：** 派发之后再加写范围路径，会让父分支工作树的本地 context 与卡正文不相等：本地仍是 `start` 时的 binding，卡上是新的。波末换树时，新树用现行 binding 跑 `start` 会被拒 `stale: Current task no longer matches dispatch`。恢复只有重新签发派发记录一条路，而这条通常不在线的权限里。一次换树还等于一次全新准备（装依赖、生成投影、`start`），所以只在最终 head 换一次。

**依据：** 线父分支的派发与开工归 `docs/engineering/integration.md`「线父分支」第 1、2 步。`swap` 的拒绝条件与步骤归 `tools/dev-flow/src/integration/README.md`「准备任务工作树」；超出写范围时换 attempt 再换树的规则见 `.meta_harness/human/delivery-pitfalls.md` P21 与 `integrate` 技能「blocked 或 failed：redo 或接管」。重新签发派发记录的完整步骤由 Reduce 执行，向线负责人索取时按那条通路，不自创。

## 开工门槛：先理解，再写方案，最后派子代理

**什么时候适用：** 每波开工，顺序不能颠倒。

1. **先理解需求。** 读线包本波交付边界与本次 delta，列出不懂的、可疑的、和自己判断会冲突的地方。
2. **有歧义直接问 Reduce。** 用本地 mirasim 会话消息直接发，不等交回，也不带到波末。一次问一个具体问题，不问「这样做可以吗」。Reduce 在澄清阶段优先答复。这是需求澄清，不是波中的设计批复通道，也不替代「决策权：三层」。
3. **再写方案。** 用 Matt 技能加项目模板写本波的 `spec.md` 与 `plan.md`，设计点候选在此步安排，按范式「本波计划」切闭包。
4. **最后才派第一批子代理。** 只派不依赖任何未决项的闭包。

**为什么：** 先派子代理再补方案，会把没有写清楚的判断留到实现阶段才暴露，返工代价高于先把方案写清楚。判断标准是：一件事现在就能写进 spec，就不派；写不进去，先澄清或先做设计。跳过任一步就派子代理的，波末交回会被退回。

**依据：** 开工顺序归 `line-initial-dispatch.md` 与 `line-delta.md` 的首次消息与 delta 模板。写规格与切闭包的方法归 `delegate`「写规格」「切闭包」。

## 本波计划：你来切闭包

1. 读线包的本波交付边界。`spec.md` 引用它，只写本波的具名裁定与本线新增的约束，不复制线包。方法按 `to-spec`，格式借用 `claim` 技能的 spec 模板。
2. `plan.md` 是闭包表。方法按 `delegate`「切闭包」与 `to-tickets`，格式借用 `claim` 技能的 plan 模板。每个闭包写写范围、依赖、判据、验收命令、角色与模型分配。线包附录「建议闭包与依赖」只作起点。
3. 闭包要粗到能独立验收，细到写范围不相交。理由：闭包太碎，合并与等待的开销会超过并行的收益。
4. 待决事项先按本页「决策权：三层，默认自己推进」筛层：过度设计删掉 → 从项目要求与产品正文往下逐层核对冻结输入后自己能定的，具名裁定写进 `spec.md` → 线包「需 Reduce 批复」里的设计点，按「执行中前台并行关注的事」A3 处理。只有产品规则、范围变化、新的破坏性契约改动才算第三层。第三层不提问：停依赖部分，继续其余，整波做不下去就交回。
5. 本波另有几张卡时（线包列出的载体卡，或你自建的子卡），按 `integration.md`「本波有几张卡」一次认领，卡级动作按 `claim`。这些卡不另开分支与工作树，不运行 `start`。闭包表写明每个闭包服务哪张卡。

## 推进循环：每个闭包的七步

每个闭包按下面七步推进。

1. 纯读的便宜模型（见 `delegate`「4 选模型」）补本闭包上下文，只补差额。
2. 写闭包规格：按 `delegate`「写规格」。命令必须能在当前仓库运行（P8）。
3. 写者实施（扇出按 `delegate`）；最后一次改动后重跑全部门禁，报告日志时间与提交号（P1）。
4. 你复跑功能门禁，核对写范围。
5. 只有高风险切片当场评审；常规评审集中到实施完成后一次。
6. 阻断合成一轮集中修复；同类阻断出现两次就整类处理（P3）。
7. 在闭包分支上提交，更新 `plan.md` 闭包表。闭包分支留在本地，不推送，这样它的改动计入本波 attempt 的写范围检查。

闭包做完后，你按 `integration.md`「线父分支」核对闭包门槛，把它合入父分支。

### 父分支就是线内联调环境

**什么时候适用：** 从切闭包到波末收尾的每一步。`<用户名>/<线短名>-w<波号>` 是本波的工作分支，不是 `integration/<线>`。线轨道的头只在开波 FI 与波末 PR 时出现。

**怎么做：**

- 线内所有闭包都合进父分支。不开卡级 PR，不逐卡准入，不逐卡过 gate。合入父分支不算被接受。
- 线内跨领域的集成与联调在父分支上做。线包「本波整体判据」（线内贯通那几条）就在父分支头上跑，证据贴线父卡。
- 两条线之间的真件接线不归你，归 Reduce 的联调。
- 波末只出一个 PR：父分支合并轨道最新头，一次准入，一个 PR 进 `integration/<线>`，一次 gate，然后交接报告。

**判断标准：** 一件事的答案是「把本线自己的东西接起来、跑通、验证」，它就是你的活。答案是「把别的线的东西接进来」或「动公共登记文件、装配页、契约正文」，那是 Reduce 的活。线内接不上、需要别的线配合时，在父分支上先用替身把本线这侧做完，把缺口写进交回的「跨线输入」，不为它停整条线。

**为什么：** 线包只说「怎样合并、联调由线负责人决定」，不说明父分支就是联调环境。少了这一句，默认读法会往集成轨道靠，于是每张卡各走一遍 PR、准入和 gate，等待时间成倍增加，而它们本来就在同一条线、同一波里联调。

**依据：** `docs/engineering/integration.md`「线父分支」与「同步与提升的节奏」；替身与冻结输入见同页「不变量」第 3 条。

### 进度记录：两层，固定格式

- **波级：** `tmp/line-<线>/w<波>/plan.md` 的闭包表，写每个闭包的状态与父分支上的合入提交。
- **线级：** `tmp/line-<线>/state.md` 开头的「本波进度」，格式固定：
  - `本波进度：[■■■□□□□□□□] 1/3 闭包已合入父分支 · 波 <w> · F <短 sha> · 父分支 <分支名> · attempt <attempt> · 更新 <UTC 时间>`
  - `当前：闭包 <名> 第 <n> 步`；轮空写 `当前：轮空，等待下一条 delta`；受阻写 `当前：受阻：<一句原因>`。
  - 闭包表：`| 闭包 | 状态 | 父分支上的合入提交 |`，状态只用 `待做`、`进行中`、`已合入父分支`、`受阻（<原因>）`、`跳过（<理由>）`。本波有几张卡时，闭包表加一列「服务的卡」。
- **线级什么时候改：** 读到 delta 时按新计划重写；每个闭包派出、合入父分支，波末准入与 gate，受阻，开始等待时改。
- **在途子代理：** 已派出、尚未合回的闭包写在「本波进度」之后，格式归 `claim` plan 模板「进度更新」第 4 部分。压缩后恢复时一并读它。
- 进度与提交历史不一致时，以提交历史为准，先改进度再继续。

结构度量与品味核对在若干闭包后集中跑一次；差分变异的时机与范围按 `review-code`「差分变异」，只在最终修复轮留下的头上、只打热点。闭包不跑准入。本线本波只在父分支头跑一次准入，之前先跑线包「线内联调」一项。整波全量准入与跨线联调归 Reduce。

## 执行中前台并行关注的事

线会话有两种状态，关注方式不同：

- 执行中（active）：前台推进本线工作，同时关注下面几条并行的事件流。任何一条有变化，都在下一次工具调用前处理，不等手头这件事做完。
- 等待中（交回后、blocked 后、轮空）：只挂一条前台阻塞的等待命令，见「交回与等待」。

波中没有和 Reduce 的问答通道。看到的 delta 只保存，交回之后再处理。需要 Reduce 决定的事，走交回入口，结果写 blocked。线包「需 Reduce 批复」里的设计点是预定的批复点，不是求方案的问答。

### 20 分钟法则：长跑的子代理，自己去看

**什么时候适用：** 子代理派出后计时，跑过 20 分钟仍未交回。完成通知只表示通知已送达，不表示它在推进。

**怎么做：** 读日志、`git status`、`git diff --stat` 与最近的工具调用，看它是「在推进」还是「在重复」。判断看单位时间的进展，不看绝对时长。然后四选一，选完记进 `flow.jsonl`：

- **等**：在推进，只是任务本来就长。记一句预期还要多久。
- **追加指导**：补上下文或明确边界，按 `delegate`「7 等待与追加」先在闭包规格的「追加记录」留痕，再发出。
- **升档或换模型**：是能力问题就升推理档位或换更强的模型接着做。升级理由写进流水。
- **停掉重切，或自己接手**：结构性问题（闭包切大了、该拆、依赖方向错了）的唯一正确解是改结构，不是催。

分界：规格没说清、环境坏了、能力不够，是三种不同的卡点，对应不同的动作。不要读到「还在跑」就走开，也不要在它收尾时打断它，更不要把「跑了很久」写成缺陷。

**为什么：** 子代理不会自己报告「我在原地打转」。它可能在跑长任务、卡在一个解不开的点上，或用笨办法硬啃，从外面看都是没动静。等它交回才发现不对，返工代价比中途看一眼大得多。追加次数与升级理由也是台账里「哪种活该用哪个档位」的唯一来源；没有它，效果记录只能是印象。

**依据：** `delegate`「7 等待与追加」与「12 记流水与反思」；台账口径归 `delegate` 的派发流水。

## 证据：一次做对，接受者不用回头问

- 通过要有当场可查的产物，退出码为 0 不等于测过（P1、P2）。
- 证据贴在线父卡评论里，本波其他卡的证据贴在各自的卡上；只写任务 tmp 路径的证据，接受者不据它判断（`agent-delivery.md` 第 5 节）。原件太大时贴摘要、关键行、位置和哈希。
- 证据日志记下所跑代码的提交号；证据脚本每一步核对成功（P13、P14）。
- 没跑的写「未执行」和原因，工具不覆盖的写「未测量」，不写零。

## 交回与等待

- 做完：闭包达到门槛后合入父分支。本波的闭包都合入后，在父分支头跑线包「线内联调」一项并核对判据，只跑一次准入，开一个父分支进线轨道的 PR，走一次 gate 并读回合入。然后开提升 PR，在线父卡发本波的交接报告与交回记录，再停写。交回物的格式归 `integration.md`「线会话记录」，波末顺序归「线父分支」。
- 做不了：同一个入口交回 blocked，写清原因、已完成部分和剩余工作，然后停写。
- 等待：一条等待命令等线父卡的下一条 delta。等待本身出问题时写进状态，等人转告，不轮询。

### 等待：前台阻塞的工具调用

交出本波之后、交 blocked 之后、轮空时，线会话此刻就该被阻塞地等待：不做别的事，也不停下来。所以等待命令一律这样执行：

1. **用宿主的 shell 或 bash 工具，作为一次前台阻塞的工具调用来执行。** 不加 `nohup`、`&`、`setsid`、`disown`，不放后台，不用 Claude Code 的 `run_in_background`。
2. **原因：** 放到后台而前台不阻塞，会话就会结束本回合。Codex 上，后台进程跑完也唤醒不了已结束的会话，线就永远等不到收口。
3. **单次工具调用有时长上限。** 给等待命令加 `--timeout`，取略小于宿主单次调用上限的值。退出码 3 表示超时，不表示条件不成立：先读回一次本线父卡的 delta（见 `docs/engineering/integration.md`「等待监督」第 5 步），没有未处理的就用**同一个 `--since`** 在新的前台调用里重跑同一条命令。这是重新挂上事件等待，不是轮询 GitHub（每个超时周期只做一次读回和一次有界对账）。
4. **等待返回后**按 delta 处理：active 开工、idle 再次前台阻塞等待（先读回本线父卡全部 delta 并按已处理集合去重，重挂起点见 `docs/engineering/integration.md`「等待监督」）、redo 按新 attempt 重开、terminal 交最终报告。只有读到明确的 terminal delta 并交完最终报告，才可以结束回合。
5. **等自己派出的子代理时同理：** 前台没有别的工作就阻塞等它，不结束回合。
6. **唯一的后台进程是本机事件接收器**（`events-receiver-cli serve`）。每台机器只有一个接收器。它是常驻服务，要活过会话，由本机第一个开工的会话启动一次。启动方法见 `tools/dev-flow/src/delivery/README.md`「事件等待」。首次消息只给只读的 `health` 命令，不给 `init` 与 `serve`。接收器不是等待命令，等待命令本身仍然前台阻塞。
7. 每次重挂前后更新 `state.md` 的等待命令与 `--since`，便于替换会话接续。

- 压缩上下文后续接时，先重新加载 `line` 技能，并核对技能目录是当前检出的投影，不是旧工作树里的副本。派发过子代理的，另外重载 `delegate`。
- 每次交回、停下或压缩上下文前，更新 `tmp/line-<线>/state.md`：本波进度、身份、已处理的 delta 评论 id、当前 attempt 与 head、未完成操作、下一步。替换会话只读它和线父卡就能接上。

## 每波复盘：把教训变成线级资产

交回前按 `delegate`「反思」做本波反思，写本会话的台账增量。波结束时花几分钟：本波哪条规则被反复违反、哪类阻断出现两次、哪个命令写错了。能变成结构手段的变成结构手段（P7）；属于本线的写进 `constraints.md`；属于项目的写进交接报告「给集成节点的提示」，由 reduce 决定是否写回拥有者。

## 不要做的事

- 每个闭包重做会话级产物。
- 波中向人提问、在普通评论向 reduce 求方案、读别线未集成的提交。
- 跳过闭包门槛、波末准入或 gate，忽略 targetBase，或在同机准入期间提交和增加测试负载。
- 为线内工作逐个开 PR 进线轨道，或把闭包都建成 Issue。
- 做线包「明确不做」里的事，或越过停止条件继续。
- 轮询 GitHub 等待，或让子代理用轮询循环等日志（P29）。
- 把计划说成已交付，把未执行写成通过。
