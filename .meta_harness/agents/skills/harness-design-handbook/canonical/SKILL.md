# Harness 设计手册

**前身识别 → 领域读数（封存）→ 承载读数 → 对账四表 → 按结果展开 → 装配与符合性核对 → 投影视图落盘。**

```text
需求 ─→ A 前身识别
          │
          ├─→ B 领域读数（先做，封存）───┐
          │                              ├─→ D 对账四表 ─→ E 展开 ─→ F 装配与符合性核对 ─→ G 投影视图
          └─→ C 承载读数（分解+落点+六问）┘                                                  （落回需求 topic）
                                          四表全过时，E 退化为「直接落地」

        └────────── A～E：领域与能力，不用内核机制词汇 ──────────┘└── F：Cordis 在这里出场 ──┘
```

多数需求是既有设计的延伸，走到 D 全过就结束；能力推导、完整动作链和形式模型是**重武器**，
只在 D 失败处展开。本 skill 给主线与判据，参考页解决一个判断后回到主线。

**Cordis 在这条主线里的位置**：它是内核，是**装配时必须满足的契约规范**——系统以 fiber、plugin、service、inject 的方式集成装配，
提供者设计要逐行核对自己符合它。**它不是建模的视角**：需求怎样读成性质、能力怎样切、契约承诺什么，都不借它的词汇来想。
所以 A～E 说的是领域与能力，Cordis 到步骤 F 才出场。

撰写或修订设计、规格、计划、评审与研究文档前，必须加载 `asd-ste100` skill。遵循其适用写作规范。
本手册继续负责设计判断与接受流程；清晰化不得改变术语、不变量、条件或承诺强度。

## 先定这次走多深

主线是给**新的能力边界与新的不变量**准备的。先看这次改动属于哪一种，再决定走多深：
把每次改动都拖过完整主线，第一次可运行的反馈来得太晚；该走主线的抄了近路，漏掉的那条性质不会自己冒出来。

| 这次改动 | 走多深 | 设计评审 |
|---|---|---|
| **沿已接受契约的修复**：契约没变，是实现偏了或漏了 | 不走主线，直接修；验证按契约与节点已登记的证据义务 | 不派设计评审；接受实现时看什么，按[接受级别](references/handoff.md#按风险选择接受实现的看法) |
| **已接受边界内加操作或条款**：owner 不变，不新增不变量（落点 #2／#4） | **契约增量**：A 声明基准；只对新增的那部分做 B 的可观察结果与性质、D 的表 A 与表 B；按[规格演进](references/spec-evolution.md)出新版本并迁移消费者；提供者跟着变的，过[步骤 F](#步骤-f装配与符合性核对) 对照表里对应的那一行 | 规格评审：判「表达」一次 |
| **新的能力边界或新的不变量**：落点 #8、性质表出现两个以上责任归属层，或触及证明义务 | 完整主线 A～G；按[触发点](#仍须走完整推导与形式模型的情况)上形式模型 | 「选择」与「表达」各一次 |

拿不准属于哪一行，按更深的那一行走。做到一半发现新增了不变量或动了边界，升到下一行，已做的读数保留。

### 主路径还没跑通过：先做探路件

不知道一条主路径走不走得通——上游接口是否真这样表现、两个包接起来会不会卡住——不必把完整主线走完才发现走不通。
**先写一个探路件把主路径跑通，再回来做设计。**

- **放哪**：执行仓库的示例区或本次任务区，**不进产品包与应用**，产品源码不得导入它。位置见[工作区上下文](references/workspace-context.md#实现设计与交付)。
- **带回什么**：一份**事实清单**——哪条路走通了、上游实际怎样表现、哪里和预想不一样，各带可复核的出处（命令、输出、版本）。
  **代码不带回来**：规格起草拿到的是事实，不是一份等着被合法化的实现。
- **它不是什么**：不是实现的第一版，不提升任何状态。探路件跑通不等于性质成立，契约照样从领域读数长出来。
- **双盲照旧**：探路件给的是实现一侧的事实。领域读数仍先于它完成并封存，或由没看过探路件的人来做；做不到就照实记「双盲未达成」。
- 探路得到的上游事实若要被长期消费，按[来源核对](references/source-check.md)落到它的拥有者；探路件本身用完即弃。

## 三条不可妥协的纪律

- **双盲。** 领域读数在承载读数之前完成并封存；A～E 与契约正文都不使用 fiber/service/effect/inject/label
  这类内核机制词汇，它们只在提供者设计与步骤 F 出现。顺序一旦颠倒，现有结构与机制的形状会反向裁剪性质集合，
  而被裁掉的那条永远不会被写下来。只为划清界线的否定式说明（「这里的服务不是内核里的 service」）不在此列。
- **绑定到语义条目，不是行号。** 每条由机制保护的性质，绑定要有稳定名字和**一个在该语义消失时会失败的测试**；
  行号随上游任何编辑漂移，既误报又漏报。**「相关的 formal task」不是证据**：模型把「再加入」建成复用同一个元素、
  `TypeOK` 只约束模型自己变量的值域——这些被建模方式吸收的语义，模型里没有任何在该条款被违反时会失败的断言，
  不绑，改在 verification 登记真正的证据形式（场景、lint、单元测试）。
- **契约写性质，提供者设计写绑定。**「设置按同字段优先级覆盖求值，优先级链为 X」进契约；
  「该链由哪段代码按什么顺序求值」进提供者设计。把机制写进语言无关契约，等于把上游语义焊进领域承诺。
  **绑定成立要先验证对齐**：`ctx.intercept` 的合并顺序是**装配链**，若领域的优先级链是**数据层次**
  （出厂 < 租户 < 账号 < 会话），两者并不重合，靠 intercept 承载会退化成为每个身份组合开一条 ctx 分支。
  这类「形状相似但语义不同」的绑定是最常见的错误来源，声明前必须逐条核对。
  **第二常见的是「同一提交」跨 owner**：契约要求「另一 owner 的现读与本操作的写入落在同一提交边界」时，
  提供者设计必须指出**两个写入者共同触碰的那个存储对象**——没有共同存储对象的两个事务，可串行化也排不出次序。
  时间谓词（`now > deadline`）不是存储对象；进程内锁随插件实例生灭，不是正确性机制；「单调事实」只有落成存储里的一列才算。
  判据与走查见[提供者与装配投影](references/project.md#由责任推导运行时形状)。

## 步骤 A：前身识别

**输出**：基准声明 + 相关已有需求条款 + 相关领域对象。**不做落点分类。**

**先声明基准**：实现现状 / 目标态设计 / 混合。同一条需求相对现状是「新增」、相对目标态是「延伸」，
不声明就会两个人得出两个都说得通的答案。基准是目标态且该设计未接受时，**本次全部「落地」暂停**。

**再向需求方问清两件到 E／F 才会显形、但那时改起来要整批搬迁的事**：本批节点落在哪个领域名与包布局下
（realization 区 README 的两层布局规则只定形状，领域名要有人拍板；位置见[工作区上下文](references/workspace-context.md#实现设计与交付)）；
**装配节点（存储、时钟、密钥、入口层身份核实的承接者）是否随本批建立**——不建，契约「装配给」那一列的每一行都没有承接者，
投影会挂着一个空步骤。

**相关领域对象不要凭印象列**：工作区若维护着一份跨需求收齐的领域对象条目，从那里取，
并带上它标明的未裁项——位置与用法见[工作区上下文](references/workspace-context.md#需求与系统约束)。
**它是输入，不是依据**，对不上时以它指向的需求正文为准。

**再查反查索引**：`已有对象 → 需求条款` 的索引（视图清单里的 `object-index`）回答「这个对象上已经挂着谁」。
**本工作区尚未建立该索引**（领域对象条目回答的是「有哪些对象」，不是这个问题）；在它建成前，
已有对象由执行者按需求与现有设计人工列举并标注「未经索引核实」，且**不得用「边界连锁」信号触发回询**。
索引由本次任务输入给出位置时以该输入为准。

## 步骤 B：领域读数

| 产出 | 要求 |
|---|---|
| 需求确认状态 | 已确认 / 继承待核对 / 候选假设 / 未知。**未确认的要求不能驱动已接受设计**，也不得进入 E 的落地 |
| 可观察结果 | 观察者 + 触发情形 + 所需或禁止的结果。说不出观察者的是实现偏好，不是需求 |
| 性质 | 不变量 / 安全 / 进展**三类分开**，各带**责任归属层**与证据形式；进展性写明前提 |

责任归属层只回答「哪个领域 owner 负责」；由哪份契约的哪个拥有者承载要等 D 对账通过后才写，
在 B 写承载等于提前看了 C；用哪种机制兑现更晚，归提供者设计。归位方法见[需求归位](references/intake.md)。

**封存**要有痕迹，三选一：B 的产出先落盘再开始 C；B 与 C 由不同执行者完成；
单执行者无法分离时，明确记录「双盲未达成」并在表 B 结果上标注该限制。

## 步骤 C：承载读数

这一步按对象分诊：需求涉及的每样东西，**落在已有结构的哪一层；现有的装不下时，最少要长出什么**。
它只判落点；落到 #8 的那一部分是组合、扩展还是新增，交[能力覆盖与演化](references/decompose.md)判。
全程用领域与能力的语言——对象、能力、契约条款、依赖、生命周期、作用域。内核机制词不在这里出现：
怎样用 Cordis 的原语兑现这份读数，是提供者设计的事，到步骤 F 才核对。

### C1 对象分解（一切计量的基础）

把需求涉及的东西拆成可独立定位的对象，各记名字、领域含义、生命周期特征。
**粒度**：拆到每个对象能独立回答一次落点提问为止。
**可复核**：分解结果决定后面所有计数，两人拆得不同必须记录理由，不能各按各的清单计数。
**共同基线**：步骤 A 取到的领域对象条目就是那份「不各按各的」清单——从它起步；
分解把某个领域对象拆开、合并或改了宿主时，**把差异与理由报给那份条目的维护者**，
不在本次分析里悄悄另立一份对象清单。

### C2 落点分类（每个对象各判一次，0→8 顺序问，第一个「是」就停）

| # | 落点 | 判据 | 典型误判 |
|---|---|---|---|
| 0 | 什么都不改 | 能在已有条款里指出原文 | 把理解问题当成需求 |
| 1 | 数据 | 只有形状没有行为：无新生命周期、无新可见性边界 | 顺手做成一项能力 |
| 2 | 已有能力的新条款 | 新操作的授权前提与失败模式能被现有契约覆盖 | 悄悄扩大这项能力的责任 |
| 3 | 随宿主生灭的附属责任 | 它的生死与某个已有对象一致，撤除时谁释放、谁交接说得清 | 指望撤除按某个先后发生却没写下来——撤除的先后与结算若关系到正确性，它本身是一条性质，要进契约并指定负责方 |
| 4 | 能力之间的通知或控制 | **先分通知还是控制**。通知不等结果、不改变发起方的走向；控制能否决或改写，这时「等不等它、谁的结果算数、它失败了算什么」都是契约的一部分 | 把控制写成通知（结果被丢掉）；该等的判定没等——**授权检查会静默放行** |
| 5 | 新的依赖关系 | 一项能力开始依赖另一项。被依赖方换代或缺席时，依赖方在途的工作与已拿到的结果怎么办，要答得出：沿用旧的做完、下一次才换新的，还是立即作废 | 没说清要哪一种连续性，就给长时操作加上一条依赖 |
| 6 | 按身份并存的多份实现 | 同一项能力要按新身份给出**不同实现**（不是不同数据） | 只因数据不同，就要求并存多份实现 |
| 7 | 独立的生命周期单元 | 生命周期不同 / 失败要隔离 / 有独立资源，三条任一 | 从已有单元分裂出来时，原靠「同生共死」保护的不变式失去依托 |
| 8 | 独立的新责任 | 独立变化原因 **且** 独立消费者 | 把需求名改成能力名 |
| 9 | 非结构性 | 以上全否 | 见下 |

从大往小问，人会倾向答「这是个新能力」；从小往大问，逼你先证明现有的装不下。

**#9 是必须有的出口**：性能调优、可观测性调整、**废弃与下线**都在这里，不走本主线。
废弃类的核心问题不是「不变式是否仍成立」，而是**「谁还依赖它、撤除后这些依赖怎么办」**，
见[装载效应与撤除责任](references/architecture/runtime/lifecycle.md#装载效应与撤除责任)。

### C3 六问

1. **数据还是行为？**有没有需要被别的能力调用的行为。只有形状没有行为的是数据，不做成能力。
2. **生命周期跟谁？**上表 #7 的三条判据任一为是，它就是独立的生命周期单元；全否，它只是某个已有单元的附属责任，或一份数据。
3. **要不要并存多份实现？**判据是**定制实现还是定制数据**——定制数据用优先级覆盖求值，定制实现才需要并存。
4. **谁依赖谁？**每条依赖带上它的连续性要求：被依赖方换代或不可用时，依赖方在途的工作沿用旧的做完、下一次才换新的，还是立即作废。
   要哪一种由需求定，不由装配的方便定。
5. **通知还是控制？**控制还要再问：发起方等不等它的结果，几方都答时谁的算数，它自己失败算放行还是算拒绝。
6. **装载带来什么，撤除时还回什么？**撤除时释放什么、交接什么、什么仍然为真。

**六问的答案合起来是一张承载草图**：谁拥有什么，谁依赖谁（各要哪种连续性），什么与什么同生共死，哪些关系是控制。
它是能力层的图，不是装配图——每一条用内核的哪种原语去兑现，留给提供者设计，在[步骤 F](#步骤-f装配与符合性核对) 逐行核对。

**C 的结论要有长期的家。**对象为什么这样拆、落点为什么是 #1 而不是 #8、哪几个对象为什么同生共死而不拆——
这些会被提供者设计与投影当作依据引用；读数本身可以留在任务区，**但被引用的理由必须在 E 之前落进
`record/proposals/<topic>/` 或最终引用它的节点正文**。设计正文指认任务区（哪怕是纯文本）等于把依据放在一个会被清理的地方。

## 步骤 D：对账四表

前三张判「做不做得到」，第四张判「值不值、要不要送回需求方」。详细判据与走查示例见[对账](references/reconciliation.md)。

**表 A 性质承载**——把 B 的每条性质对到 C 的承载草图上：草图里有没有一个拥有者，它的结构就保得住这条性质。四种结果：

| 结果 | 去向 |
|---|---|
| 能 | 性质写入契约，绑定写入提供者设计 |
| **有前提地能** | 同上，且契约写明**前提**与前提失效时的责任方 |
| 不能，需求正当 | 契约自己写清由谁兑现 |
| 不能，需求过度 | 走表 D 回询，**不得自行削需求** |

第二行不可省：多数生命周期类性质都是「有前提地能」。判「能」会隐藏前提，判「不能」会把整条性质
推给契约。**同生共死只保证撤除被发起**：性质要的若是撤除的结果——释放完成、先后、结算——一律判「有前提地能」，并写出谁负责收尾。第一、二行也必须产生契约条款，否则靠结构承载的性质只活在流程产物里，实现一换就无条款可依。

**表 B 没有谁白给的保证**——**从原始需求陈述提问，不是从 B 的性质表提问**，否则 B 漏掉的性质在这里同样
不出现，清单退化成表 A 的重复登记。逐条问「这条需求需要它吗」：跨拥有者或跨生命周期单元的事务与原子提交、可靠投递、外部效应回滚、
有序的异步清理、权限边界与沙箱、跨进程的身份与可见性、持久化与崩溃恢复、背压流控、时序保证。
这九样没有哪一层会自动给出：需求需要哪一样，就得有一份契约写明由谁兑现。
内核实际给什么、不给什么的事实归[组合性质](references/architecture/assurance/composability.md)指向的证明边界正文，此处只作提问器。
**命中是常态，不是异常信号**——凡涉及持久化、跨进程、授权、投递的需求命中多条属正常。

**表 C 承载复查**——需求关联到已有对象时，复查该对象原有不变式是否仍成立：

- 仍成立 → 落地；
- 不成立但需求可收紧 → **必须走回询格式**，不得以「回到需求谈」名义非格式化沟通；
- 不成立且需求正当 → 对象边界画错，回 C1 重新分解，**B 的性质表原样保留**；
  **这一条优先于表 D**——先重分解再标价，否则报出的是错误结构的价格。

**表 D 代价与回询**——先自证（换一种分解重走 C→D，换不出更便宜的才准回询；**从步骤 F 回来的那一种，自证是换提供者设计，不是换分解**），再看四个结构性信号：
半径异常（落点 #6/#7 但可观察结果只涉数据或权限差异）、组合爆炸（实例数是两个以上身份维度的乘积）、
边界连锁（改动 ≥2 个对象的边界，须索引已建）、动态性代价（**需求未要求、由方案引入的**钉死）。

回询用四段：当前结构与可计数代价 → 具体的替代表述及其代价 → **两者在产品语言上的差别** → 建议与理由
并写明裁决权不在自己。第三段不能省，只报技术复杂度等于把裁决责任推给看不懂代价的人。
**单条** SYS-* 硬约束不回询直接承担，但 **SYS-* 之间冲突或与产品需求冲突必须回询**。
回询期间两种表述分别往下推，**不得自行选便宜的那个继续**。

**这四张表不评判需求的正当性，它们给需求标价。**价标出来之后，谁付得起是需求 owner 的裁决。

## 步骤 F：装配与符合性核对

契约定下之后，才轮到 Cordis。这一步在**提供者设计**（实现映射节点）上做：把承载草图落成内核的原语，
再核对落成的东西**符合 Cordis 的契约规范、且语义与契约重合**。产物是节点设计里的 Cordis 符合性核对表
（模板位置见[工作区上下文](references/workspace-context.md#主题信息包与模板)）与下面四问的结论。展开方法见[提供者与装配投影](references/project.md)。

**承载草图怎样落成原语**——左列来自 C2 的落点，右两列才是内核的词。中间一列是**通常的**落法，不是唯一的；
同一个落点有几种落法时，选哪一种是提供者设计的判断，要在节点正文里写出理由：

| 承载草图里的 | 装配时通常落成 | 核对什么 |
|---|---|---|
| 数据（#1） | 不进 `ctx` | 纯数据与纯计算不制造 fiber |
| 已有能力的新条款（#2） | 既有 service 的一个成员；也可以是一个事件，或向扩展点注册的一项贡献 | 没有借机扩大这个服务面的责任 |
| 随宿主生灭的附属责任（#3） | effect | 效应的生死与宿主 fiber 一致；**内核不保证有序的异步清理**，要次序就在同一个 effect 内自己组合 |
| 通知或控制（#4） | event 的派发模式 | 通知用 `emit`；同步控制用 `bail`；**异步控制必须 `serial`**——`bail` 不 await，Promise 不是 bail 值，授权检查会静默放行；around 拦截用 `waterfall` |
| 新的依赖关系（#5） | 必需 inject，或调用时取用 | 必需 `inject` 的含义是「提供者换代或不可用，我就卸载重跑」，对应「立即作废」那一种连续性；要「沿用旧的做完」或「下一次才换新的」的，改为调用时取用，并写明旧引用按什么政策处置 |
| 按身份并存的多份实现（#6） | isolate label | 要并存两份实现，`isolate()` 是唯一途径；隔的是实例的可见性，不是数据 |
| 独立的生命周期单元（#7） | fiber | 父卸载必然带走子；跨重载要留的事实不能只活在插件体的闭包里 |
| 独立的新责任（#8） | plugin，提供 service 或向有明确契约的扩展点注册贡献 | 由独立的插件承载它的实现、依赖与生命周期；公开函数面不被服务面吞没 |

「核对什么」一列的每一项，在节点的符合性核对表里都有对应的行；表里填「符合」的要指得到兑现它的小节。

**反向核对四问**：dispose 时在途工作归谁（外部效果不回滚，要留墓碑）；依赖消失时谁被卸载、范围对不对；
事件会不会跨边界泄漏；**跨进程后哪些保证失效**。第四问问的是契约里那张「装配给／协议给」的表与实际装配是否一致：
这张表在起草契约时就写下（单机先行，哪些保证此刻靠同进程装配成立，在能力层就判得出），装配给的保证在分布式演化时须由协议重新兑现。
**核出不一致时，这是 F 唯一回写契约的地方**——只改某条保证归哪一类，不写机制，照[规格演进](references/spec-evolution.md)出修订。

**对不上的时候**：某一条用内核原语兑现不了，或兑现出来的语义与契约只是形状相似——**先换提供者设计**。
换不出来，那是一笔代价：回表 D 标价、按格式回询。**不改契约去迁就机制，也不把机制写回契约**；
契约怎么变由回询的裁决定，不由装配的方便定。交付与审阅见[交付](references/handoff.md)。

## 步骤 G：投影视图落盘

**不可省。** 前六步的产物按拥有者散在 registry、spec、realization、basis、record 各处——
这是按失效事件分家的必然代价。但开发者需要的是另一种切法：**这一个需求，现在该怎么实现。**

落点是**需求 topic 下的 `projection/v<N>/`，按版本固化**；
每版一份 `projection.md` 加一份 `provenance.json`，目录自己的 `README.md` 只做版本导航。
**在 realization 节点的独立评审闭合之后再落**——投影是六步产物的派生快照，节点一改它就要跟着改，
而固化版本的规矩是不原地改；评审前非落不可的，版本说明里标 `pre-review`，评审闭合后出下一版。

- **为什么挂在需求上**：设计变更的触发源是需求变更，版本跟着需求走，
  开发者才答得出「我实施的是哪一版需求对应的设计」。契约有自己的版本线，两者不同频。
- **为什么固化而非实时派生**：实时视图只有「当前」。照着它实施到一半上游一改，
  手上那版就找不回来了。固化版本带来源坐标与哈希，可随时核对是否过期，**但它自己不变**。

| `projection.md` 必含 | 取自 |
|---|---|
| 本版对应的需求条款及其确认状态 | B 的确认状态表 |
| 涉及的领域对象 | C1 对象清单 |
| 不变量、安全性质、进展性质（进展带前提） | 表 A 的分配结果 + 契约条款 |
| 每个操作的前置、后置、失败集合、**缺席时的默认答案**、**原子性与提交点** | 契约 |
| 装配与 Cordis 符合性：插件边界、服务面、inject 关系、effect 装卸配对、事件派发模式、装配图 | 提供者设计与它的符合性核对表 |
| 绑定与证据状态 | bindings |
| 未决 gap 与已回询项 | D 的回询记录 |
| **实施顺序及每步的完成判据** | 上面各节；**判据要能被性质表或绑定里的检查验证** |

**取舍判据是「开发者不该自己决定的，这里都能查到」**：判定次序、失败后的收敛状态、
提交点在哪、缺席时拒绝还是放行、控制类事件用哪种派发、身份参数有无默认值。
这些错了都是语义错，且多半测不出来，不能指望实施者自己想到。

未决项以**显式 gap** 出现，**不填一个看起来合理的默认值**——开发者据此知道哪里在等裁决，
而不是照着一个猜测实施。`provenance.json` 记来源的精确坐标与哈希；与上游不一致时以上游为准，
**出新版，不原地改旧版**，旧版保留并标注被谁取代。

> **哈希是给人核对用的，除非工作区已有工具替你核**：设计投影不在
> [工作区上下文](references/workspace-context.md#规格维护与验证)列出的自动检查范围内时，
> 「这一版是否已经过期」要在**每次据它实施之前**人工核一遍来源坐标。
> 未冻结的来源填 `null` 并在正文里标注该节可能漂移——**不要填一个当时算出来的哈希冒充已冻结**。

## 返回边与收敛

四条返回边：表 C 三行 → C1；自证 → C；回询 → B；**F 对不上且换不出提供者设计 → 表 D**（标价、回询，不直接改契约）。

## Cordis 最小内核模型

这一节只在步骤 F 与提供者设计里用：装配之前必须知道内核会兑现什么、不会兑现什么，
否则提供者设计会把内核不给的保证当成已有的。它不是做领域读数与承载读数时的参照。下面是做这类判断的最小事实集，
核对于 `@deepseek-ai/cordis` 4.0.2 源码（行号均指该包 `src/`），辅以 DSH 修订 [`c291e796`][dsh-docs] 的文档；
二者冲突以源码为准。本次实际采用的版本仍从工作区的采用决定读取，与此基线不同就按[来源核对](references/source-check.md)重验。

- **Fiber 是所有权单位，Context 只是解析入口。** `ctx.plugin(plugin, config)` 应用一次插件并返回一条 Fiber
  （`registry.ts:316`）；同一插件可被应用多次，每次一条 fiber（`registry.ts:139-140`）。子 fiber 的 dispose
  注册为父 fiber 的一个 effect（`fiber.ts:265`），父卸载必然带走子。`Fiber.uid` 只是本次 registry 内的实例身份
  （`fiber.ts:185-186`），不能充当持久身份或租户键。
- **加载由依赖声明驱动，重载是常态而非异常。** `inject` 列出必需服务，不齐就停在 `PENDING`；六态为
  `PENDING/LOADING/ACTIVE/FAILED/DISPOSED/UNLOADING`（`fiber.ts:139-153`）。`Fiber.store` 是必需服务实现的快照
  （`fiber.ts:197-198`），其代际由各提供者 fiber 的 uid 拼成，任一必需服务换了提供者就先卸载再重跑插件体
  （`fiber.ts:611-639`；`ctx.inject(deps, cb)` 同义，`registry.ts:167-176`）；`check` 谓词返回假或提供者非
  `ACTIVE` 亦然（`reflect.ts:274`、`reflect.ts:241`）。所以插件体必须可重复执行，
  跨重载要保留的事实不能只活在插件体的闭包里。
- **只有 effect 注册的副作用被纳管。** `ctx.effect(fn, label)` 收集 disposer，接受单个、Promise 与（异步）生成器多个
  （`fiber.ts:403-418`）。同一 effect 内逆序释放（`fiber.ts:431`）；fiber 卸载时各 effect 也按逆注册序取出
  （`utils.ts:27-31`），但随即由 `Promise.all` 并发驱动，异常只写日志不上抛（`fiber.ts:675-686`）。
  逆序只约束启动顺序：要"先排空再关后端"这类次序和结算，必须自己在一个 effect 内组合。fiber 已进入
  `UNLOADING` 或已 dispose 时再建 effect 抛 `CordisError('INACTIVE_EFFECT')`（`fiber.ts:351-353`、`fiber.ts:419-422`）。
- **服务身份是「服务名 + isolate 标签」，同标签下唯一。** 实现登记在按 isolate symbol 索引的扁平 store，
  同标签重复 provide 直接抛错（`reflect.ts:289-290`）——没有"子上下文默认遮蔽父服务"这回事，要并存两份实现
  就得 `ctx.isolate(name, label)`，同 label 的两次调用合流（`context.ts:121-125`）。解析沿 fiber 链向上，
  父的 isolate 标签一旦不同就抛错、不再上溯（`reflect.ts:154-166`）；换实现引起的重载与 `internal/service`
  默认也只在同标签内传播（`reflect.ts:314`）。提供者 fiber 不在 `ACTIVE` 时该服务读不到（`reflect.ts:237-241`）。
- **事件是五种派发，不是一条消息总线。** `emit` 同步派发且不等待返回的 Promise（`events.ts:194-196`），
  `parallel` 并发全等，`serial` 顺序逐个 await，`bail` 同步到首个 bail 值，`waterfall` 是 around 中间件、
  外层先跑、不调 `next()` 即短路（`events.ts:183-243`）。派发模式是事件契约的一部分。过滤器取自派发时的
  `thisArg`：不带 thisArg 的 `ctx.emit(name, ...)` **不过滤**，`on(..., { global: true })` 的监听者一律绕过过滤
  （`events.ts:165-175`）；服务的默认过滤器比较 isolate 标签（`service.ts:61-63`）。
- **配置沿上下文向下注入。** `ctx.intercept(name, config)` 只影响其下装载的插件，祖先在先、近者在后合并
  （`context.ts:128-145`、`service.ts:86-102`）；`fiber.update(config)` 先走 `internal/update` waterfall
  （HMR 可否决或替换）再重启该 fiber（`fiber.ts:736-752`）。

| 原语                                          | 它是什么                                                        | 装配时用它回答                 |
| --------------------------------------------- | --------------------------------------------------------------- | ------------------------------ |
| `Context`                                     | 解析入口；`extend`/`isolate`/`intercept` 派生子上下文           | 谁看得见什么，配置从哪来       |
| `Fiber`                                       | 一次插件应用的运行实例，持有 config、依赖快照、effect 与清理    | 谁拥有资源，何时对外可用       |
| `inject` / `Fiber.store`                      | 必需服务声明与其实现快照                                        | 依赖缺席或更换时谁被卸载重跑   |
| `ctx.provide` / `Service`                     | 在某个 isolate 标签下登记一份实现                               | 能力对消费者的服务面           |
| `ctx.effect`                                  | 纳管的副作用及其 disposer                                       | 撤除时释放什么、交接什么       |
| `ctx.isolate` / `ctx.intercept`               | 服务可见性作用域 / 向下游注入服务配置                           | 作用域实例与政策下发           |
| `emit` `parallel` `serial` `bail` `waterfall` | 五种派发                                                        | 是否等待、谁决定结果、失败去哪 |

`isolate` 隔离的是服务实例的**可见性**，不是数据本身：一个服务实例内部握着跨租户的数据句柄，隔离多少次都无效，
租户判定仍归数据访问层的身份校验。上游 DSH 在 Cordis 之上另有 `dsh-scope` 等包，它自述不是沙箱也不是权限边界，
其 Known Limitations 属于那个以 agent 为键的上层 scope，不能算到 Cordis 原生 `isolate` 头上。
纯数据或纯计算不必制造 Fiber；插件数量和服务键数量都不表示能力维度。

| -------------------------------------------------------------- | ---------------------------------------------------- |
| 精确的重载/卸载时机、并发重入、`await()` 与 `restart()` 的结算 | `src/fiber.ts` + [fiber API][fiber-api]              |
| 某个事件的等待、顺序、返回值或过滤语义                         | `src/events.ts` + [events API][events-api]、[Primer 派发表][primer] |
| config 校验、`internal/update`、HMR 或 loader 的取值时机       | `src/registry.ts` + [registry API][registry-api]、[Primer Loader 段][primer] |

| 复用某个 DSH 上层包（scope、agent 等）或判断跨 realm 与装配    | 该包自己的 README + [DSH 架构][dsh-arch]；上游应用策略不是原语契约 |

上游行为是事实，采用与否仍是本项目的选择。

只分析影响时做到承载关系和关键缺口明确即可；只换提供者时复用现有语义，展开投影与相关符合性。

## 贯穿主线的边界

- 每项性质能追到需求，每次交接有拥有者；候选政策、已接受承诺、实际实现与证据分别陈述。
- 研究可早于完整 spec；未决项只阻止依赖它的定稿或实施，独立分析继续。
- 内核给的是运行时的组合与生命周期；租户授权、状态迁移、可靠投递、事务和外部效应回滚不因采用 Cordis 而获得，契约要求这些时写清由哪个提供者兑现。
- 能力缺席、撤回或替换时，在途工作与保留事实仍有归属；运行时撤除不等于外部效应回滚。
- 提出、评审、接受、发布和实现是不同动作，加载 skill 不增加批准权限。

## Taste

- **先找承载，再长能力。** 新维度来自未覆盖的独立责任，不能只把需求名改成插件名。
- **不变量先于抽象。** 抽象承担契约或隔离真实变化。
- **最小且充分。** 少建概念，把所有权、失败和进展说完整。
- **成熟复用优先。** 用契约核对差距，再决定直接采用、适配、fork 或自建。
- **一个概念一份权威。** 投影保留语义对应，消费者无需了解提供者内部。
- **变化与缺席是正常状态。** 问清谁接手、何时生效、什么仍为真。
- **复杂度要有收益。** 优化有瓶颈证据，不预建想象中的框架。
- **证据限制信心。** 保留前提与覆盖范围；机制判断给出理由，产品取舍按已有授权确定。
