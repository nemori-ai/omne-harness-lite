# Harness 设计手册

**前身识别 → 领域读数（封存）→ 机制读数 → 对账四表 → 按结果展开 → 反向核对 → 投影视图落盘。**

```text
需求 ─→ A 前身识别（领域层，不用机制词汇）
          │
          ├─→ B 领域读数（先做，封存）───┐
          │                              ├─→ D 对账四表 ─→ E 展开 ─→ F 反向核对 ─→ G 投影视图
          └─→ C 机制读数（分解+落点+六问）┘                                          （落回需求 topic）
                                          四表全过时，E 退化为「直接落地」
```

多数需求是既有设计的延伸，走到 D 全过就结束；能力推导、完整动作链和形式模型是**重武器**，
只在 D 失败处展开。本 skill 给主线与判据，参考页解决一个判断后回到主线。

## 三条不可妥协的纪律

- **双盲。** 领域读数在**任何机制视角之前**完成并封存；步骤 A 也不得使用 fiber/service/effect/label
  等机制词汇。顺序一旦颠倒，机制的形状会反向裁剪性质集合，而被裁掉的那条永远不会被写下来。
- **绑定到语义条目，不是行号。** 每条由机制保护的性质，绑定要有稳定名字和**一个在该语义消失时会失败的测试**；
  行号随上游任何编辑漂移，既误报又漏报。
- **契约写性质，提供者设计写绑定。**「设置按同字段优先级覆盖求值，优先级链为 X」进契约；
  「该链由哪段代码按什么顺序求值」进提供者设计。把机制写进语言无关契约，等于把上游语义焊进领域承诺。
  **绑定成立要先验证对齐**：`ctx.intercept` 的合并顺序是**装配链**，若领域的优先级链是**数据层次**
  （出厂 < 租户 < 账号 < 会话），两者并不重合，靠 intercept 承载会退化成为每个身份组合开一条 ctx 分支。
  这类「形状相似但语义不同」的绑定是最常见的错误来源，声明前必须逐条核对。

## 步骤 A：前身识别

**输出**：装配基准声明 + 相关已有需求条款 + 相关领域对象。**不做落点分类。**

**先声明基准**：实现现状 / 目标态设计 / 混合。同一条需求相对现状是「新增」、相对目标态是「延伸」，
不声明就会两个人得出两个都说得通的答案。基准是目标态且该设计未接受时，**本次全部「落地」暂停**。

**再查反查索引**：`装配对象 → 需求条款` 的索引回答「这个对象上已经挂着谁」。
**本工作区尚未建立该索引**；在它建成前，相关对象由执行者按需求与现有设计人工列举并标注
「未经索引核实」，且**不得用「边界连锁」信号触发回询**。索引由本次任务输入给出位置时以该输入为准。

## 步骤 B：领域读数

| 产出 | 要求 |
|---|---|
| 需求确认状态 | 已确认 / 继承待核对 / 候选假设 / 未知。**未确认的要求不能驱动已接受设计**，也不得进入 E 的落地 |
| 可观察结果 | 观察者 + 触发情形 + 所需或禁止的结果。说不出观察者的是实现偏好，不是需求 |
| 性质 | 不变量 / 安全 / 进展**三类分开**，各带**责任归属层**与证据形式；进展性写明前提 |

责任归属层只回答「哪个领域 owner 负责」；精确的机制绑定要等 D 对账通过后才写，
在 B 写绑定等于提前看了 C。归位方法见[需求归位](references/intake.md)。

**封存**要有痕迹，三选一：B 的产出先落盘再开始 C；B 与 C 由不同执行者完成；
单执行者无法分离时，明确记录「双盲未达成」并在表 B 结果上标注该限制。

## 步骤 C：机制读数

### C1 对象分解（一切计量的基础）

把需求涉及的东西拆成可独立定位的对象，各记名字、领域含义、生命周期特征。
**粒度**：拆到每个对象能独立回答一次落点提问为止。
**可复核**：分解结果决定后面所有计数，两人拆得不同必须记录理由，不能各按各的清单计数。

### C2 落点分类（每个对象各判一次，0→8 顺序问，第一个「是」就停）

| # | 落点 | 判据 | 典型误判 |
|---|---|---|---|
| 0 | 什么都不改 | 能在已有条款里指出原文 | 把理解问题当成需求 |
| 1 | 数据 | 无新生命周期、无新可见性边界 | 顺手做成服务 |
| 2 | service 条款 | 新操作的授权前提与失败模式能被现有契约覆盖 | 悄悄扩大服务责任 |
| 3 | effect | 效应生死与宿主 fiber 一致，撤除责任明确 | 依赖清理顺序——内核不保证有序异步清理 |
| 4 | event | **先分通知还是控制**，控制再按同步/异步选派发：通知 `emit`；同步控制 `bail`；**异步控制必须 `serial`**；around 拦截 `waterfall` | 用 `emit` 做控制（返回值被丢弃）；**异步控制误用 `bail`——它不 await，Promise 不是 bail 值，授权检查会静默放行** |
| 5 | inject 边 | 消费者能否承受被卸载重跑 | 给长时操作加 inject |
| 6 | label | 同名服务要按新身份给出**不同实例**（不是不同数据） | 为「数据不同」开隔离维度 |
| 7 | fiber | 生命周期不同 / 失败要隔离 / 有独立资源，三条任一 | 从已有 fiber 分裂时，原靠「同生共死」保护的不变式失去依托 |
| 8 | plugin + service | 独立变化原因 **且** 独立消费者 | 需求名改成插件名 |
| 9 | 非结构性 | 以上全否 | 见下 |

从大往小问，人会倾向答「这是个新能力」；从小往大问，逼你先证明现有的装不下。

**#9 是必须有的出口**：性能调优、可观测性调整、**废弃与下线**都在这里，不走本主线。
废弃类的核心问题不是「不变式是否仍成立」，而是**「谁还依赖它、撤除后这些依赖怎么办」**，
见[装载效应与撤除责任](references/architecture/runtime/lifecycle.md#装载效应与撤除责任)。

### C3 六问

1. **数据还是服务？**有没有需要被别人 `inject` 的行为。只有形状没有行为的是数据，不进 `ctx`。
2. **哪一层 fiber？**三条判据任一为是则独立成 fiber；全否则它只是一个 effect 或一份数据。
3. **要不要 isolate？**判据是**定制实现还是定制数据**——定制数据用优先级覆盖，定制实现才隔离。
   要并存两份实现，`isolate()` 是唯一途径。
4. **谁 inject 谁？**`inject` 的含义是「提供者换代或不可用，我就卸载重跑」。问消费者：能承受被重启吗？
5. **事件是通知还是控制？**派发模式是事件契约的一部分。控制还要再问一次同步还是异步：
   `bail` 不 await（`events.ts`），异步判定必须走 `serial`，否则拦截形同虚设。
6. **装载效应与撤除责任配对了吗？**卸载时释放什么、交接什么、什么仍然为真。

投影的展开与提供者设计见[提供者与装配投影](references/project.md)。

## 步骤 D：对账四表

前三张判「做不做得到」，第四张判「值不值、要不要送回需求方」。详细判据与走查示例见[对账](references/reconciliation.md)。

**表 A 性质承载**——把 B 的每条性质对到 C 的装配草图上，四种结果：

| 结果 | 去向 |
|---|---|
| 能 | 性质写入契约，绑定写入提供者设计 |
| **有前提地能** | 同上，且契约写明**前提**与前提失效时的责任方 |
| 不能，需求正当 | 契约自己写清由谁兑现 |
| 不能，需求过度 | 走表 D 回询，**不得自行削需求** |

第二行不可省：多数生命周期类性质都是「有前提地能」。判「能」会隐藏前提，判「不能」会把整条性质
推给契约。第一、二行也必须产生契约条款，否则机制承载的性质只活在流程产物里，上游一变就无条款可依。

**表 B 内核负面清单**——**从原始需求陈述提问，不是从 B 的性质表提问**，否则 B 漏掉的性质在这里同样
不出现，清单退化成表 A 的重复登记。内核不提供：跨 fiber 事务、可靠投递、外部效应回滚、有序异步清理、
权限边界与沙箱、跨进程身份与可见性、持久化与崩溃恢复、背压流控、时序保证（同 effect 内启动顺序除外）。
条目权威归[组合性质](references/architecture/assurance/composability.md)指向的证明边界正文，此处只作提问器。
**命中是常态，不是异常信号**——凡涉及持久化、跨进程、授权、投递的需求命中多条属正常。

**表 C 承载复查**——需求关联到已有对象时，复查该对象原有不变式是否仍成立：

- 仍成立 → 落地；
- 不成立但需求可收紧 → **必须走回询格式**，不得以「回到需求谈」名义非格式化沟通；
- 不成立且需求正当 → 对象边界画错，回 C1 重新分解，**B 的性质表原样保留**；
  **这一条优先于表 D**——先重分解再标价，否则报出的是错误结构的价格。

**表 D 代价与回询**——先自证（换一种分解重走 C→D，换不出更便宜的才准回询），再看四个结构性信号：
半径异常（落点 #6/#7 但可观察结果只涉数据或权限差异）、组合爆炸（实例数是两个以上身份维度的乘积）、
边界连锁（改动 ≥2 个对象的边界，须索引已建）、动态性代价（**需求未要求、由实现方案引入的**钉死）。

回询用四段：当前结构与可计数代价 → 具体的替代表述及其代价 → **两者在产品语言上的差别** → 建议与理由
并写明裁决权不在自己。第三段不能省，只报技术复杂度等于把裁决责任推给看不懂代价的人。
**单条** SYS-* 硬约束不回询直接承担，但 **SYS-* 之间冲突或与产品需求冲突必须回询**。
回询期间两种表述分别往下推，**不得自行选便宜的那个继续**。

**这四张表不评判需求的正当性，它们给需求标价。**价标出来之后，谁付得起是需求 owner 的裁决。

## 步骤 E 与 F

| 对账结果 | 展开到哪 |
|---|---|
| 四表全过，落点 #0/#1 | 直接落地 |
| 四表全过，落点 **#2/#4** | **不得直接落地**：改变已发布契约公开面，按[规格演进](references/spec-evolution.md)发布新版本 |
| 表 A 一/二行 | 性质入契约、绑定入提供者设计 |
| 表 A 三行 / 表 B 命中 | 在相应契约补写保证，并写明内核不兑现这一点 |
| 表 C 二行 | 回询；表 C 三行 | 回 C1 重新分解 |
| 表 D 触发 | 自证 → 回询 → 继续推进不依赖该裁决的部分 |
| 落点 #8 | [能力覆盖与演化](references/decompose.md) + [契约与完整动作链](references/define.md) |
| 落点 #9 | 出主线，按该类需求自己的方法处理 |

**F 反向核对**四问：dispose 时在途工作归谁（外部效果不回滚，要留墓碑）；依赖消失时谁被卸载、范围对不对；
事件会不会跨边界泄漏；**跨进程后哪些保证失效**。第四问的结论——哪些保证是装配给的、哪些是协议给的——
**写进契约**，不是流程笔记；装配给的保证在分布式演化时须由协议重新兑现。交付与审阅见[交付](references/handoff.md)。

## 步骤 G：投影视图落盘

**不可省。** 前六步的产物按拥有者散在 registry、spec、realization、basis、record 各处——
这是按失效事件分家的必然代价。但开发者需要的是另一种切法：**这一个需求，现在该怎么实现。**

落点是**需求 topic 下的 `projection/v<N>/`，按版本固化**；
每版一份 `projection.md` 加一份 `provenance.json`，目录自己的 `README.md` 只做版本导航。

- **为什么挂在需求上**：设计变更的触发源是需求变更，版本跟着需求走，
  开发者才答得出「我实施的是哪一版需求对应的设计」。契约有自己的版本线，两者不同频。
- **为什么固化而非实时派生**：实时视图只有「当前」。照着它实施到一半上游一改，
  手上那版就找不回来了。固化版本带来源坐标与哈希，可随时核对是否过期，**但它自己不变**。

| `projection.md` 必含 | 取自 |
|---|---|
| 本版对应的需求条款及其确认状态 | B 的确认状态表 |
| 涉及的领域对象 | C1 对象清单 |
| 不变量、安全性质、进展性质（进展带前提） | 表 A 的分配结果 + 契约条款 |
| 每个操作的前置、后置、失败集合、**缺席时的默认答案**、**原子性与提交点** | 契约 |
| Cordis 建模：插件边界、服务面、inject 关系、effect 装卸配对、事件派发模式、装配草图 | 提供者设计 |
| 绑定与证据状态 | bindings |
| 未决 gap 与已回询项 | D 的回询记录 |
| **实施顺序及每步的完成判据** | 上面各节；**判据要能被性质表或绑定里的检查验证** |

**取舍判据是「开发者不该自己决定的，这里都能查到」**：判定次序、失败后的收敛状态、
提交点在哪、缺席时拒绝还是放行、控制类事件用哪种派发、身份参数有无默认值。
这些错了都是语义错，且多半测不出来，不能指望实施者自己想到。

未决项以**显式 gap** 出现，**不填一个看起来合理的默认值**——开发者据此知道哪里在等裁决，
而不是照着一个猜测实施。`provenance.json` 记来源的精确坐标与哈希；与上游不一致时以上游为准，
**出新版，不原地改旧版**，旧版保留并标注被谁取代。

> **哈希是给人核对用的，除非工作区已有工具替你核**：设计投影不在
> [工作区上下文](references/workspace-context.md#规格维护与验证)列出的自动检查范围内时，
> 「这一版是否已经过期」要在**每次据它实施之前**人工核一遍来源坐标。
> 未冻结的来源填 `null` 并在正文里标注该节可能漂移——**不要填一个当时算出来的哈希冒充已冻结**。

|---|---|

## 返回边与收敛

三条返回边：表 C 三行 → C1；自证 → C；回询 → B。重新分解一个对象会触发挂在它上面的其他需求复查，
在核心对象上可能链式展开。**收敛出口沿用[三轮未收敛时升级结构诊断](references/handoff.md#三轮未收敛时升级结构诊断)**：
同一基线第三轮仍未收敛，停止局部修补，升级整体结构诊断。

**双盲是一次性装置**：任何经过回询或重走的需求，第二遍 B 的执行者已看过机制，
产物必须区分「第一遍封存」与「第二遍重写」，第二遍不享有防偏置声明。

## Cordis 最小内核模型

投影之前必须知道内核会兑现什么、不会兑现什么，否则契约会落在错误的边界上。下面是做这类判断的最小事实集，
核对于 `@deepseek-ai/cordis` 4.0.2 源码（行号均指该包 `src/`），辅以 DSH 修订 [`c291e796`][dsh-docs] 的文档；
二者冲突以源码为准。本次实际采用的版本仍从工作区的采用决定读取，与此基线不同就按[来源核对](references/source-check.md)重验。

- **Fiber 是所有权单位，Context 只是解析入口。** `ctx.plugin(plugin, config)` 应用一次插件并返回一条 Fiber
  （`registry.ts:316`）；同一插件可被应用多次，每次一条 fiber（`registry.ts:139-140`）。子 fiber 的 dispose
  注册为父 fiber 的一个 effect（`fiber.ts:265`），父卸载必然带走子。`Fiber.uid` 只是本次 registry 内的实例身份
  （`fiber.ts:185-186`），不能充当持久身份或租户键。
- **加载由依赖声明驱动，重载是常态而非异常。** `inject` 列出必需服务，不齐就停在 `PENDING`；六态为
  `PENDING/LOADING/ACTIVE/FAILED/DISPOSED/UNLOADING`（`fiber.ts:139-153`）。`Fiber.store` 是必需服务实现的快照
  （`fiber.ts:197-198`），其代际由各提供者 fiber 的 uid 拼成，任一必需服务换了提供者就先卸载再重跑插件体
  （`fiber.ts:611-639`；`ctx.inject(deps, cb)` 同义，`registry.ts:167-176`）；`check` 谓词返回假或提供者非
  `ACTIVE` 亦然（`reflect.ts:274`、`reflect.ts:241`）。所以插件体必须可重复执行，
  跨重载要保留的事实不能只活在插件体的闭包里。
- **只有 effect 注册的副作用被纳管。** `ctx.effect(fn, label)` 收集 disposer，接受单个、Promise 与（异步）生成器多个
  （`fiber.ts:403-418`）。同一 effect 内逆序释放（`fiber.ts:431`）；fiber 卸载时各 effect 也按逆注册序取出
  （`utils.ts:27-31`），但随即由 `Promise.all` 并发驱动，异常只写日志不上抛（`fiber.ts:675-686`）。
  逆序只约束启动顺序：要"先排空再关后端"这类次序和结算，必须自己在一个 effect 内组合。fiber 已进入
  `UNLOADING` 或已 dispose 时再建 effect 抛 `CordisError('INACTIVE_EFFECT')`（`fiber.ts:351-353`、`fiber.ts:419-422`）。
- **服务身份是「服务名 + isolate 标签」，同标签下唯一。** 实现登记在按 isolate symbol 索引的扁平 store，
  同标签重复 provide 直接抛错（`reflect.ts:289-290`）——没有"子上下文默认遮蔽父服务"这回事，要并存两份实现
  就得 `ctx.isolate(name, label)`，同 label 的两次调用合流（`context.ts:121-125`）。解析沿 fiber 链向上，
  父的 isolate 标签一旦不同就抛错、不再上溯（`reflect.ts:154-166`）；换实现引起的重载与 `internal/service`
  默认也只在同标签内传播（`reflect.ts:314`）。提供者 fiber 不在 `ACTIVE` 时该服务读不到（`reflect.ts:237-241`）。
- **事件是五种派发，不是一条消息总线。** `emit` 同步派发且不等待返回的 Promise（`events.ts:194-196`），
  `parallel` 并发全等，`serial` 顺序逐个 await，`bail` 同步到首个 bail 值，`waterfall` 是 around 中间件、
  外层先跑、不调 `next()` 即短路（`events.ts:183-243`）。派发模式是事件契约的一部分。过滤器取自派发时的
  `thisArg`：不带 thisArg 的 `ctx.emit(name, ...)` **不过滤**，`on(..., { global: true })` 的监听者一律绕过过滤
  （`events.ts:165-175`）；服务的默认过滤器比较 isolate 标签（`service.ts:61-63`）。
- **配置沿上下文向下注入。** `ctx.intercept(name, config)` 只影响其下装载的插件，祖先在先、近者在后合并
  （`context.ts:128-145`、`service.ts:86-102`）；`fiber.update(config)` 先走 `internal/update` waterfall
  （HMR 可否决或替换）再重启该 fiber（`fiber.ts:736-752`）。

| 原语                                          | 它是什么                                                        | 设计时用它回答                 |
| --------------------------------------------- | --------------------------------------------------------------- | ------------------------------ |
| `Context`                                     | 解析入口；`extend`/`isolate`/`intercept` 派生子上下文           | 谁看得见什么，配置从哪来       |
| `Fiber`                                       | 一次插件应用的运行实例，持有 config、依赖快照、effect 与清理    | 谁拥有资源，何时对外可用       |
| `inject` / `Fiber.store`                      | 必需服务声明与其实现快照                                        | 依赖缺席或更换时谁被卸载重跑   |
| `ctx.provide` / `Service`                     | 在某个 isolate 标签下登记一份实现                               | 能力对消费者的服务面           |
| `ctx.effect`                                  | 纳管的副作用及其 disposer                                       | 撤除时释放什么、交接什么       |
| `ctx.isolate` / `ctx.intercept`               | 服务可见性作用域 / 向下游注入服务配置                           | 作用域实例与政策下发           |
| `emit` `parallel` `serial` `bail` `waterfall` | 五种派发                                                        | 是否等待、谁决定结果、失败去哪 |

`isolate` 隔离的是服务实例的**可见性**，不是数据本身：一个服务实例内部握着跨租户的数据句柄，隔离多少次都无效，
租户判定仍归数据访问层的身份校验。上游 DSH 在 Cordis 之上另有 `dsh-scope` 等包，它自述不是沙箱也不是权限边界，
其 Known Limitations 属于那个以 agent 为键的上层 scope，不能算到 Cordis 原生 `isolate` 头上。
纯数据或纯计算不必制造 Fiber；插件数量和服务键数量都不表示能力维度。

### 什么时候必须去读官方文档

上面足以支撑边界判断。设计一旦依赖下列精确行为，就停下来核对；方法与记录格式归[来源核对](references/source-check.md)，
历史修订的定位线索与来源清单归 [Cordis 映射](references/architecture/reference/cordis-mapping.md)。

| 设计开始依赖                                                   | 去读采用版本的源码，再对照官方页                     |
| -------------------------------------------------------------- | ---------------------------------------------------- |
| 精确的重载/卸载时机、并发重入、`await()` 与 `restart()` 的结算 | `src/fiber.ts` + [fiber API][fiber-api]              |
| 某个事件的等待、顺序、返回值或过滤语义                         | `src/events.ts` + [events API][events-api]、[Primer 派发表][primer] |
| config 校验、`internal/update`、HMR 或 loader 的取值时机       | `src/registry.ts` + [registry API][registry-api]、[Primer Loader 段][primer] |
| 服务解析、`provide`/`set`/`accessor`/`mixin` 与 isolate 的交互 | `src/reflect.ts`、`src/service.ts` + [service API][service-api]、[context API][context-api] |
| 复用某个 DSH 上层包（scope、agent 等）或判断跨 realm 与装配    | 该包自己的 README + [DSH 架构][dsh-arch]；上游应用策略不是原语契约 |

不在上述情况就不要展开整个上游仓库。核对结论按"主张 → 采用对象/版本 → 原始证据位置 → 适用范围"留下；
上游行为是事实，采用与否仍是本项目的选择。

## 贯穿主线的边界

- 每项性质能追到需求，每次交接有拥有者；候选政策、已接受承诺、实际实现与证据分别陈述。
- 研究可早于完整 spec；未决项只阻止依赖它的定稿或实施，独立分析继续。
- 内核给的是运行时的组合与生命周期；租户授权、状态迁移、可靠投递、事务和外部效应回滚不因采用 Cordis 而获得，契约要求这些时写清由哪个提供者兑现。
- 能力缺席、撤回或替换时，在途工作与保留事实仍有归属；运行时撤除不等于外部效应回滚。
- 提出、评审、接受、发布和实现是不同动作，加载 skill 不增加批准权限。

## Taste

- **先找承载，再长能力。** 新维度来自未覆盖的独立责任，不能只把需求名改成插件名。
- **不变量先于抽象。** 抽象承担契约或隔离真实变化。
- **最小且充分。** 少建概念，把所有权、失败和进展说完整。
- **成熟复用优先。** 用契约核对差距，再决定直接采用、适配、fork 或自建。
- **一个概念一份权威。** 投影保留语义对应，消费者无需了解提供者内部。
- **变化与缺席是正常状态。** 问清谁接手、何时生效、什么仍为真。
- **复杂度要有收益。** 优化有瓶颈证据，不预建想象中的框架。
- **证据限制信心。** 保留前提与覆盖范围；机制判断给出理由，产品取舍按已有授权确定。
