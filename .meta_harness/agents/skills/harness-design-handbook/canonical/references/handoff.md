# S7–S8 · 交付与反向核对

**何时读：**设计需要审阅、规格落地、实施交接，或确认本次范围是否完整。
**读后留下：**工件足迹、采用关系、分层状态、双向覆盖与可接续缺口。
**返回：**[入口](../SKILL.md)；发现缺口回到拥有它的阶段，只调整受影响部分。

## S7：把内容放回拥有者

按任务终点选择必要工件，不为每步建一个文件。
方法页不定义本次产品契约；实际路径由[工作区上下文](workspace-context.md)导航。
新建长期主题时从相应家族的[本地模板信息包](workspace-context.md)起步；
topic 入口维护范围与阅读地图，详细判断、规范和实际证据分别归其拥有者。

| 内容 | 拥有者 |
|---|---|
| 要求、范围、确认记录 | 需求正文与消费基线 |
| 事实、来源与局限 | 研究；一次性观察留在当前任务材料 |
| 候选比较与过程 | 工作树tmp；当前性质和验证义务归实际拥有者 |
| 当前选择、采用范围与必要理由 | 实际拥有者的正文，按需简短ADR；形成过程留tmp |
| 精确身份、行为与组合承诺 | 公开类型、模块旁行为契约及验证资源 |
| 当前运行时兑现方式 | 公开接口、实际实现与必要ADR |
| 候选分解、比较与施工读数 | 工作树tmp；终态仅将仍必要理由写回实际拥有者，不把过程材料改名持久化 |
| 交付依赖、负责人、验证步骤 | 施工计划；引用设计快照，不成为另一份契约 |
| 当前系统投影 | 架构/能力地图，引用决定与精确规格 |

共享含义只有一个拥有者。候选、已接受、已发布、已实现和已验证分别陈述，
不能靠放入某个目录或填满模板替代这些事实。
能力演化被接受后，同步能力地图中的身份、精确契约、组合与采用关系，
使新维度能被后续需求发现和复用；候选与已接受分开呈现，地图引用规格，不成为第二份契约。

## 按当前交接问题展开

| 当前还不能回答 | 加载 | 带回什么 |
|---|---|---|
| 为什么选它，哪些内容值得持久化，如何接受或复议？ | [设计选择](design-decisions.md) | 比较依据、消费基线、接受/取代范围及必要证据 |
| 怎样落 spec，哪个变化要升版，影响哪些消费者？ | [规格演进](spec-evolution.md) | 公开接口/行为/验证分工、精确依赖与传播范围 |
| 采用什么表达，模型与实际实现怎样对应？ | [规格与证据](architecture/assurance/specification.md) | 最小工件、抽象映射和结论的适用范围 |
| 本次还要怎样安排实施和验收？ | [交付规划](delivery-planning.md) | 可观察增量、依赖、写入/组合责任和完成判据 |

这些是条件分支。只交付候选不执行发布，纯规格表达不代选产品政策，
只做影响分析不需要细化施工排期；加载手册不增加批准或执行权限。

## 区分四层就绪状态

| 层次 | 能支持的结论 | 不能由此推断 |
|---|---|---|
| 语义接受 | 有明确范围的要求/契约已被有权者接受 | 提供者已有全部实施输入，或必要证明已完成 |
| 提供者可实施 | 被依赖的机制选择、接口、资源/失败责任已明确 | 应用已正确装配 |
| 装配明确 | 实际提供者、配置、消费与跨能力交接可解释 | 真实组合已经运行通过 |
| 实际验证 | 特定版本/环境/范围取得了相应结果 | 未检查范围成立或模型检查等于无条件证明 |

这是报告维度，不是新增的登记状态或四轮审批。
每个缺口说明负责产物/拥有者、受影响消费者、所需决定或证据及闭合条件；
只暂停依赖它的实施，不把不影响公共契约的内部实现选择都当成缺失规格。
语义接受不能绕过具体机制所需的[证明门槛](architecture/assurance/composability.md)。

## 让评审回答具体问题

形成可识别的待审稿后安排独立只读评审。评审回答的是三种不同的问题，**一次派发只问一种，简报里写明是哪一种**：

| 判断 | 待审的是什么 | 它回答 | 判据 |
|---|---|---|---|
| 选择 | 能力边界、作为语义整体的一批契约、实现映射节点、读数 | 性质有没有保护点，边界切得对不对，装配出来的语义与契约是否重合 | [review/choice.md](review/choice.md) |
| 表达 | 一份或一批规格 | 既定选择是否被完整、明确、规范地写出来 | [review/expression.md](review/expression.md) |
| 计划 | 施工计划 | 可行性、依赖、调度与验收责任 | [review/plan.md](review/plan.md) |

已定义并可用时委派 design-reviewer，提供对象/修订、目标、范围、依据与未决项；判「表达」时另附一份
实际相关的机器输出（公开类型、引用、Schema、依赖及模型配置）。已核机械项不重复手算；未覆盖范围如实标明，不要求旧中央报告。
两类意见混在一份报告里会互相淹没，所以要两种判断就派两次；不要求普通局部修改经历全部三种。

角色和行动边界从[工作区定义](workspace-context.md)取得。
宿主没有对应角色或独立评审能力时报告具体缺口，不把自检标成独立评审；
评审结果是证据和意见，仍需按已有授权形成接受或修订。

## 按风险选择接受实现的看法

接受一份实现类交付之前，先定它属于哪一级。级别决定机器先过什么、人看什么；
派发时把级别写进任务，交回时按它备齐证据。

| 级 | 适用 | 机器先过 | 人看什么 | 不做什么 |
|---|---|---|---|---|
| L0 局部修复 | 沿已接受契约的局部修复，文档与工具的小改 | 受影响范围的测试与类型检查 | 交付说明与变更摘要 | 不派评审 |
| L1 常规增量 | 单个成员内的实现，单份契约的提供者 | L0，加结构度量摘要——变更函数里超阈值的逐条有交代 | 该成员在结构图上的边与着色，抽查两三个最热的函数 | 不逐行读 |
| L2 跨成员与装配 | 多个成员、装配节点、迁移 | L1，加待合并提交的影响面所需检查与真实组合的运行证据 | 依赖方向全图与运行证据 | 不得跳过受影响且必需的用例 |
| L3 安全与不变量 | 身份与租户隔离、凭据、内核原语、要求同一提交的状态 | L2，加已触发的形式任务实际运行与故障注入 | 逐行读热点，并安排独立评审 | 不因为绿灯免读 |

级别按改动触及的最高风险定，不按改动大小；拿不准就上调一级。执行仓库没有某项入口
（结构度量、形式任务）时如实写「无此入口」，不以别的证据顶替。绿灯与度量是抽查线索：
级别只规定最低限度的看法，不代替接受者的判断，也不改变接受权归谁。

检查范围归执行仓库。风险级别不把受影响的检查扩大为无条件全仓检查。
计划排除的步骤如实记未执行，不能写成通过。

交付配了可执行验收（本次真实拥有者维护的验收文件，放置约定见[工作区定义](workspace-context.md)）时，
任何级别都多核一件事：**验收自任务基线以来没有被实施提交改动**。执行仓库有验收锁入口就跑它并把输出留作证据；
没有就对着基线提交看那几个文件的差异。验收被实施者改过的交付不接受，无论改得有没有道理——有道理的改动由验收的主人来做。

**什么时候派独立的 agent 来看实现**（角色定义见[工作区定义](workspace-context.md)）：

| 级 | implementation-reviewer（读这次变更的代码与读数） | qa（在干净检出上按验收标准跑） |
|---|---|---|
| L0、L1 | 不派。例外：机器读数里有实施者**没有交代的红项**，可以派它只看那几处 | 不派 |
| L2 | 有未交代的红项，或接受者读完摘要仍说不清某处时派 | 有可运行的交付面、且有写得成「触发 → 可观察结果」的验收标准时派 |
| L3 | 派：它逐行读热点 | 派 |

实现评审的每条发现要么带工具输出、要么带具体反例，它不收品味意见；验收的判决不是接受。
两者的结论都是证据：L3 上人仍然逐行读热点，不因为派了评审就免读。每张卡都派一遍会把迭代拖长，
所以默认不派，按上表在风险高或读数说不清时才派。

## 三轮未收敛时升级结构诊断

按“同一交付对象 + 同一需求/接受基线”计算实质轮次：一份可识别 revision 经相应独立评审后，
仍留下或新出现会改变语义、能力/所有权边界、状态/失败/在途政策、证据义务、
provider/assembly 可实施性，或计划依赖/验收责任的阻断 finding，计一轮。
同一 revision 的 architecture/spec 并行评审合为一轮；diff 很小但改变授权门或终态等承诺，仍是实质变化。
针对阻断做过实质修订后，独立复评确认原阻断仍未闭合，也计一轮，不要求出现新的 finding。

只有未发生实质修订的重复核对、纯机械修改后的核对，或已经没有实质阻断的复查不计轮次。
“机械”服从语义影响判断：标为措辞、格式、链接、生成投影或同步的改动一旦改变承诺，仍按实质轮次计算。
不按改动行数计数，也不为凑轮次重复 review。每轮都固定 revision、阻断 finding、处置和验证，
使重复、转移和真正闭合的问题可以比较。

**修复方的能力也按轮次升级，而不是同一档位反复试。**前两轮修复用常规档位；
第二轮修完、复评仍有阻断，**先质疑 reviewer 的判定本身，再升级修复方**：对每条剩余阻断逐条问
它是否判得对、是否合理、是否当前阶段必须闭合——reviewer 也会误判，也会把不属于本阶段的完善当成阻断报出来；
站不住的 finding 记下处置理由，不计入「未收敛」。剩下站得住的，第三轮修复交给当前可用的
**最高能力档位**（更强的模型，或派发者亲自动手），作为**最后一次局部完善尝试**。
连续两轮同档位修不干净，可能是判定有误、能力不够或问题不在局部三者之一，按成本从低到高依次排除；
跳过第一步，会把 reviewer 的误判当成结构问题去解决。本手册不绑定具体模型，档位由派发者按当时可用的选项定。

同一基线经过最多三轮实质迭代仍有阻断 finding 时，停止同形态的局部补丁与重审，
冻结当前 revision 及三轮记录，暂停接受和依赖该设计的实施；不依赖该缺口的工作可以继续。
从整体设计链诊断以下关系，而不是继续修表面症状：

- 需求与接受基线是否完整、彼此一致；
- 能力责任和语义 owner 是否唯一，跨 owner 的保证是否有明确拥有者；
- 动作链、失败与在途工作在哪里交接，是否存在无人拥有或循环依赖；
- 单一权威是否被 proposal、spec、provider 或 assembly 的副本分裂；
- spec、provider、assembly 的分层是否把政策放错层，消费者依赖和证据/评审边界是否闭合。

跨 owner、finding 互相牵制或根因不明时，若宿主支持，可委派独立、高能力、只读 advisor 提供结构诊断。
至少给它目标与接受基线、完整设计链和精确 revision、三轮 findings/deltas/验证、重复或转移的问题、
根因假设、不可变约束及明确问题。要求输出根因、影响范围、应保留内容、结构修复路径与所需证据；
advisor 不代写设计、不作接受决定、不修改需求，本手册也不绑定具体模型或固定 advisor 角色。

只有根因、语义 owner、结构修复范围和受影响消费者已明确，需求基线保持不变或已由有权者更新，
并形成新的可识别快照且完成自检后，才恢复一次与变化相称的独立评审。
更换 reviewer、branch 或拆分 patch 不重置计数；真实的新接受基线或边界重构开启新链时，
须记录旧链如何收口以及开启新链的理由。

## S8：反向核对可观察结果

| 需求/约束 | 能力承载与精确契约 | 插件投影与组合责任 | 证据及范围 | 缺口与闭合条件 |
|---|---|---|---|---|
| 回到 S1 的陈述 | 不从代码形状反推 | 哪个提供者/装配兑现 | 已有结果或待验证义务 | 谁需要它、何时才能消费 |

双向检查：关键要求都有落点或缺口，新增性质和机制都有依据；
动作链覆盖相关失败与交接，运行时责任没有绕过契约。
对新增维度反问原能力/组合为何不能承担，检查新增插件是否只拥有那部分独立责任；
对声称已由组合覆盖的要求，核对整体保证和所有前提，没有把尚未实现的协调偷偷当作已有能力。
投影会丢失不变量与理由，核对时须回到契约和来源，不能按插件数量验收。

**停止判据：**达到本次约定终点，剩余事项可辨认、可接续。
交付报告说明“设计了什么、依据与取舍、怎样验证、尚缺什么”，
不把提出/评审/接受/实现合成一句完成，也不继续制造不影响当前判断的工件。

执行仓库若采用多层分支集成，交接时沿其 `docs/engineering/integration.md` 读取实际采用状态和运输责任。保留每卡原 revision/attempt/taskBase，候选另带 targetBase 与证据。技术运输、结果接受、平台投影和部署分别交接；本方法页不授予 ref 或平台写权限。
