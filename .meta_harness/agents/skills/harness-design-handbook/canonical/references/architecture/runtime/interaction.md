# 操作、事件与并发协议

**何时读：**操作、事件、拦截、取消或并发的可观察含义未闭合。
**读后决定：**决策与提交阶段、允许顺序、结果及失败归属。
**返回：**[阶段页](../../define.md) · [专题地图](../../topics.md)。

## 交互类型与决策权

命令请求改变，查询读取状态，事实通知描述已经发生的事情；决策扩展点允许参与者在规定边界内改变是否执行或怎样执行。事件名和参数类型不足以确定它属于哪一种，需要在协议中写明。[基础术语](../foundations/concepts.md)给出统一定义。

一个完成通知通常不应撤销已提交结果；执行前的审批则可以拒绝继续。使用相同事件机制实现二者，并不会使它们具有相同权力。

每个交互表面应说明谁发起、谁回应、由谁作最终决定、是否允许多个参与者，以及没有参与者时如何处理。需要确认所有处理者完成的通知，应当具有等待和失败汇总语义。

## 阶段与顺序

为操作区分接纳、开始执行、提交事实、通知和完成响应。只有存在可观察区别时才需要独立阶段，但不能省略对失败判断有影响的边界。

并发协议说明顺序作用在哪个范围：单个对象、单个租户、一次请求还是全系统。确定因果先后时不能依靠未声明的监听注册顺序或跨节点时钟。需要串行化或冲突控制的地方，由拥有状态变化的能力承担。

例如同一次工具执行的开始与结果需要关联同一调用；全局空闲只说明某个观察范围内没有工作，不能直接证明某条消息已完成。消费者需要的归属证据必须由相应协议提供。

## 失败和取消

取消请求、超时、底层退出、部分输出和业务结果是不同事实。超时可能发生在外部操作提交之后；调用方没有收到成功，不足以认定操作没有发生。

失败应能区分非法输入、授权拒绝、提供者故障、扩展代码缺陷和结果未知。只有消费者能够识别这些差异，才可能选择正确的重试、补偿或停止政策。适配器可以统一外部失败词汇，但不能吞掉无关的实现缺陷。

取消说明何时仍可阻止执行、何时只能请求合作停止、最终如何结算。重试说明是否复用同一操作身份、如何发现已提交结果，以及外部效果是否可能重复。具体策略由契约确定，不强制所有操作实现通用重试层。

## 扩展点的约束

扩展点需要声明允许改写的内容、不可削弱的约束、执行次序和最终权威结果。策略可组合，并不意味着任意后续扩展都能推翻前面的授权拒绝。

一种可选的工具协议是：可扩展的预决策、不可被后续改为允许的拒绝约束、执行包装、结果处理、只读结果通知。这里的关键是决策权清楚，不要求所有子系统照搬同一条流水线。

回调失败应由拥有派发边界的一方处理。通知回调可以报告失败并继续其他通知；需要否决操作的决策回调则可能终止当前操作。框架是否自动捕获异常必须核对，不能从“事件总线”名称推断。

要独立核对协议配对、顺序和结果一致性，见[不变量](../assurance/invariants.md)；已经提交的状态怎样通知，见[状态与存储](../modeling/state-and-storage.md)。
