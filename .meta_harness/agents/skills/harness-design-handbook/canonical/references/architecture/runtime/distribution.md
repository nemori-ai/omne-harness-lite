# 部署与分布式边界

**何时读：**检查当前边界将来跨进程或跨节点时能否保留语义。
**读后决定：**身份、权限、未知结果与协调范围的契约要求。
**返回：**[阶段页](../../project.md) · [专题地图](../../topics.md)。

## 单机交付的设计责任

当要求单机首发且未来能够独立部署时，设计应确定受影响能力，并确保其边界具有可保持的领域语义。
能力边界不要求立即成为进程，也不要求每个插件最终成为微服务；实际部署范围从工作区需求取得。

本地实现可以直接调用、共享受控内存和使用成熟库。对可能跨进程的公共契约，需要避免把不可序列化对象、进程内身份或隐藏调用顺序当作不可替代的业务含义。实际网络基础设施按需求引入。

## 跨边界表示

本地服务对象通过协议表面暴露操作，远程调用传输明确的数据与身份，再在接收方解析。映射应说明哪些字段被保留、哪些仅是本地实现细节，以及不能表示的状态如何拒绝。

契约规定的主体身份和授权依据需要跨边界保持，存在租户边界时保持租户归属与隔离；一个 Context 或进程内对象引用不能直接作为可信远程身份。远程故障也不能通过伪造本地对象状态隐藏，见[身份与作用域](../modeling/identity-and-scope.md)。

异构节点还可能在路径、时钟、可用工具、模型能力和资源限制上不同。差异应作为显式能力或配置被消费，或在接纳任务时拒绝；不能通过同名服务假装环境相同。

## 故障与所有权

跨网络后，调用可能未送达、已经执行但响应丢失、仍在远端进行，或重复到达。契约应能表达与操作相关的这些情况，不能把所有断连统一为确定的“未执行”。

写入所有权从单进程扩展到多节点时，应重新验证互斥范围、失效检测和旧拥有者的写入限制。租约、幂等键、去重或其他机制只在相应约束需要时引入，并明确谁拥有其状态。

远程取消需要确认取消请求与实际终止之间的区别。断开连接也不自动意味着撤除远端能力；重连后是查询当前状态、恢复订阅还是重试操作，需要协议说明。

## 验证可独立扩展

验证的对象是可观察语义。分别用本地和候选远程提供者执行同一组契约场景，再加入延迟、响应丢失、重复执行、节点退出和权限变化，检查原有约束如何保持。

可以先用小型模型或受控替身暴露边界缺口，无需为证明“未来可扩展”预建完整集群。结论应说明哪些性质已验证、采用哪些故障假设，以及还有哪些协议尚未定义。

例如，模型请求的路由可以经本地或远程适配能力实现，但仍须保持契约规定的访问通道、租户归属与请求结果语义。部署位置变化不能悄悄改变这些承诺。
