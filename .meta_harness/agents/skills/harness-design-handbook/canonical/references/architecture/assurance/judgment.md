# 判断抽象与复杂度是否值得

**何时读：**对边界、包装、复用或优化的价值有争议。
**读后决定：**哪项责任支持保留机制，什么可以删除，什么证据还会改变判断。
**返回：**[能力拆解](../../decompose.md)或[提供者投影](../../project.md)。

## 对抽象做一次删除推演

说出它拥有的契约、保护的不变量或隔离的真实变化，再问：“移除这层后，哪项保证消失，哪种内部知识会泄露给消费者？”
如果只少了一个转发名字，没有责任损失，直接表达通常更好；明确的外部边界即使只有一个实现也可能值得保留。

看责任数量，不只看文件和调用次数。相同数据含义应复用，但不能因此合并独立生命周期；
消费者若仍需知道提供者内部状态、错误和清理顺序，就要检查接口背后的责任是否兑现。

## 从现象追问原因

| 现象 | 应核对的具体问题 |
|---|---|
| 每条持久记录都是插件，或每项能力都配空状态机 | 真有独立运行行为、状态或资源生命期吗？ |
| 通用管理器接管所有状态 | 哪些独立权威和不变量被混在一起？ |
| 多处相同结构，或层层改名转发 | 语义差异/边界转换是什么，删去后损失什么？ |
| 初始化顺序、自动发现或全局 Context 维持隐含依赖 | 谁声明需要，缺席/失效如何响应，可达性是否超出权限？ |
| 退出后仍有后台写入，超时统一为失败 | 所有权、静止或未知外部效果是否被隐藏？ |
| mock 调用和成功文字是唯一证据 | 实际资源、状态或消费者结果在哪里？ |
| 热替换声称完整回滚 | 观察范围是否包含其他贡献、旧引用和外部效果？ |

这些是调查入口，不能凭外观直接判错。对跨能力保证使用[契约核对](../reference/contract-description.md)，不靠风格偏好替代语义判断。

## 缺口不直接归责

先说清违反的有效承诺，再列出实现、提取器/规则和指导等候选原因；选择能区分解释的最小反例。
分别记录事实、推断与未知，允许多处共同有缺口；修复后核对原反例和相邻路径，不能仅凭读数变绿宣布归因成立。
例如八个管理绑定没有被提取时，既要检查包装是否遵循正式 Service 约定，也要用合法包装反例检查提取器覆盖。
直接认定提取器有错，会遗漏包装违约；直接改包装，也可能掩盖合法结构未被识别的问题。
实现侧通过[工作区上下文](../../workspace-context.md)定位防御指导 DP-10。

## 复杂度与复用

比较必要承诺的符合程度及适配、验证、运行和长期维护的总负担。
具体直接采用、适配、fork 与自建路径由[提供者投影](../../project.md#选择承担责任的实现路径)拥有，不重复维护选型流程。

维护权允许按目标契约演化 fork，但不自动构成重构理由；成熟且有效的机制继续复用。
也不因沿袭上游而保留没有消费者价值的兼容包装；承载授权、生命周期或部署责任的边界仍有独立价值。

缓存、池化、并发、批处理或自定义协议都会带来一致性与失败成本。
优化性复杂度需要可复现负载、瓶颈和比较结果；正确性机制则给出它保护的规则及相称证据，不以尚未测量的性能收益替代理由。

## 判断的停止点

所需行为、状态、所有权与失败已可直接解释，且当前选择有相称依据时，停止增加抽象和调查。
局部修正沿有效契约完成；新的边界或前提变化回到[设计选择](../../design-decisions.md)，不让兼容包装长期掩盖冲突。
