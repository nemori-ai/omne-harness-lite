# 示例：从覆盖缺口长出可靠投递能力

**何时读：**需要辨认“有相关接口”与“已有能力足以承载”的差异，以及新维度怎样投影为插件。
**读后留下：**未覆盖责任、新维度的边界理由、独立插件与既有能力的组合。
**返回：**[能力分解](../../decompose.md)或[插件投影](../../project.md)。以下契约和系统范围均为教学假设。

## 给定需求与能力基

需求：提交一条通知；确认接纳后跨重启保留，按请求中已确认的规则重试，
可查询当前投递状态；允许重复发送，不承诺撤销已经发出的通知。
合法目标持续可用、重试规则仍允许且调度前提成立时，最终至少一次送达。

假设相关能力已完整提供：发送 T v1 负责一次发送，区分成功、确定失败和结果未知；
存储 K v1 负责命名空间内的原子写入、读取与约定的耐久保证。
它们均有已实现的插件提供者；本范围内没有持久工作调度或投递进展能力。
T 的成功表示目标已接收，但当前契约没有给出持续尝试最终成功的条件与保证。

## 先尝试用现有能力解释

| 要求 | 现有承诺能覆盖什么 | 仍缺什么 |
|---|---|---|
| 向目标发送 | T v1 提供一次尝试及其结果 | 哪些已接纳通知还需尝试 |
| 接纳后跨重启保留 | K v1 能耐久保存记录 | 接纳与持久提交的关系、记录代表什么工作 |
| 按规则重试、查询状态 | T 能报告一次结果，K 能读写 | 尝试归属、状态转移、恢复扫描、重试准入与进展责任 |
| 在给定条件下最终送达 | 当前输入只提供单次结果与耐久保证 | T 在何种通信前提下保证持续尝试最终送达 |

把“写记录、发请求”排成两次调用，并未定义失败或重启后谁继续工作。
缺口是一项跨尝试、跨实例保留并推进投递的责任；实际能力基若已有可配置且契约足够的持久工作能力，
应先检验它与 T 的组合，不能仅凭本例另建可靠投递。

## 为什么形成一个新维度

本例中，扩展 T 会把“一次传输”与“跨尝试工作进展”耦合；扩展 K 会让通用存储拥有业务重试政策。
候选可靠投递能力 D 拥有接纳、投递工作状态、尝试关联、重试与恢复，
依赖 T 的单次结果和 K 的耐久操作，从而保留两者的原有责任。

正交性看变化边界：T 的传输实现、K 的保存实现分别替换且契约保持时，
D 的投递语义可保持；D 的重试实现演化也无需改写 T/K 的语义。
依赖与失败交接仍须成立，这不表示三个插件可以按任意顺序无条件装卸。

## 契约与动作链

D 的候选操作是提交与查询；接纳只在工作按 K v1 的耐久承诺保存后确认。
保存失败不伪报已接纳；保存成功但回执丢失时，用约定的工作身份查询/重提语义判断是否重复接纳，相关政策须明确。

已接纳工作 → 按规则取得本次尝试资格 → 调用 T → 记录该次结果 →
成功后报告送达，失败或未知按规则保留或重试。重启从 D 的持久工作状态恢复，
不能从“没有成功记录”推断外部未发送；允许重复是本例明确的产品取舍。

投递状态由 D 解释，K 只保存，T 只提供尝试结果。退避、额度或终止条件来自已确认规则；
任何一方缺席时暂停、拒绝或保留哪些工作，应落入 D 的契约及完整动作链。

## 投影为独立插件并回到需求

为 D 定义独立插件提供投递服务，显式依赖 T/K；由它拥有运行中的恢复扫描、重试任务及尝试关联。
撤除 D 时关闭新准入，按契约收口在途工作并释放运行资源，保留已接纳的耐久记录；
再次装载从记录接续，不能靠卸载回滚外部发送。具体代际/并发/清理政策与证据仍需设计。

原需求拟由 D + T + K 组合承载，其中最终送达仍有覆盖缺口：T 持续返回失败也可能符合当前契约，
D 正确重试不能单独闭合它。需明确 T 的进展承诺与通信环境假设，必要时修订相应契约并取得证据；
新维度的成立不表示所有组合前提已经满足。

验证覆盖接纳提交与回执丢失、发送成功但状态未记下、
恢复与重试、依赖失效及插件撤除；行为模型和所需证据按[规格与证据](../assurance/specification.md)选择。
这份推理支持候选边界，不表示协议、证明或实现已经完成。

D 被接受后，以精确契约、与 T/K 的关系及采用状态进入能力地图；
后续任务完成通知、报告发送等需求先尝试消费 D，只有出现新的未覆盖责任才继续演化能力基。
