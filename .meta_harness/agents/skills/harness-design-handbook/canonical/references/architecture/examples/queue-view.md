# 示例：从队列读面走通设计

**何时读：**需要看 S1–S8 怎样用于一个小需求，尤其何时无需新增能力插件。
**读后决定：**一个需求怎样落到几个既有能力，以及新增读面配置的组合责任。
**返回：**[拆解](../../decompose.md)或[交付](../../handoff.md)。以下输入与版本全为教学假设，不是工作区现状。

## 给定输入

需求：“每次刷新显示我获准查看的待办总数和前三项；前一次刷新晚到的结果不能覆盖后一次刷新。”

假设已提供并接受的队列契约 Q v1：查询按调用主体授权，返回同一观察点的全部可见待办及稳定顺序；
拒绝与提供者不可用显式返回，查询不改变队列。已有提供者和公共查询入口兑现这些保证。
另有已接受且已实现的读面能力 V v1：绑定一个公共查询及显示转换，关联每次刷新请求，
只允许当前请求更新显示，拒绝/失败也按同一请求身份呈现。两项能力均已有插件提供者。
本任务仅交付读面候选设计；未要求实时订阅、持久化视图或在提供者撤回后离线浏览。
本例只覆盖从查询到呈现期间主体与相关授权不变的情形。
主体切换或撤权后的结果丢弃、重验和既有显示处置，需按实际要求回到[身份与作用域](../modeling/identity-and-scope.md#作用域变化)设计，不能从查询授权推断。

## 要求与能力责任：S1–S3

S1 将“总数、前三项、晚到不覆盖”列为可观察结果，引用上述输入和 Q v1。
其中“当时”仅指查询观察点，不能解释成页面始终与队列最新状态一致。

S2 将要求分解到 Q 与 V：授权和有序快照由 Q v1 提供，当前刷新结果的呈现由 V v1 保护；
总数和前三项由同一快照纯派生。将 Q 的读入口与转换配置给 V，可以解释全部给定要求。
S3 选择现有能力组合与读面投影，新增的是消费配置和派生规则，没有新的独立能力责任。
授权/披露、观察点和请求顺序帮助核对这项组合，它们不是这次分解得到的三个能力维度。

## 性质与动作链：S4–S5

同一次成功显示的总数与前三项来自同一获准快照；读面不增加数据权限；
一旦后一次刷新开始，前一次的结果不得再改变当前显示。刷新失败显式显示当前请求失败，不伪称新快照已取得。

动作链：用户刷新 → 读面记录本次请求身份 → 经公共查询入口请求 Q v1 →
结果回到原请求 → 只在仍是当前请求时替换显示。队列负责查询与授权，读面负责请求关联、呈现与失败状态。
旧请求晚到可结束自身，但不写当前显示；不可用或拒绝也按同一请求身份处理，不能覆盖后来的成功结果。

这里只派生总数和有序前三项，不增加跨能力同提交写入或可靠消息层。
若 Q v1 实际没有足够快照或授权保证，先回到其契约/提供者缺口；不能由读面拼装几次查询冒充同一快照。

## Cordis 投影：S6

装配连接 Q 与 V 的既有插件提供者；快照到显示数据的转换可为纯函数，请求关联沿 V v1 实现。
契约已覆盖给定要求，因此本例不新增插件。若缺少 V 的保证，需重新判断是既有读面责任的扩展还是新维度。

提供者撤回时按已给定契约报告不可用；后续刷新重新解析的具体方式需核对实际绑定机制。
这里不虚构 Cordis API 名称，也不把旧引用自动迁移当作框架保证；需要机制证据时沿[来源核对](../../source-check.md)展开。

## 交付与反查：S7–S8

保留 Q v1 / V v1 精确采用关系，读面配置和派生规则归消费者/装配设计。
没有改变两项契约的保证，故不为这次组合给它们升版；修改保证时再按[规格演进](../../spec-evolution.md)处理。

从输入要求反查：快照一致性由 Q v1 与派生映射支持；在本例主体/授权不变的范围内，披露由 Q 的查询授权保护；显示顺序由 V v1 的当前请求守卫保护。
验证应观察获准/拒绝结果、空列表/多项结果、并发刷新反序返回，以及提供者撤回后的实际读面状态；
复用仍适用的 Q v1 / V v1 证据，真实集成未执行就保留为待验证。

候选至此可审阅。若任务扩展到实时更新或重启恢复，重新检查现有能力覆盖与剩余责任；
需要看新增维度的走法时，读[可靠投递示例](delivery-growth.md)。
