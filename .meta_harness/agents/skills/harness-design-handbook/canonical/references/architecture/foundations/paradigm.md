# 对完全动态系统建模

**何时读：**需要理解能力体系怎样承载新需求，并在完全动态运行中演化。
**读后决定：**能力覆盖与增长、合法结构、结构内行为及合法变迁的关系。
**返回：**[拆解](../../decompose.md)；术语不清时查[概念定义](concepts.md)。

## 同时描述结构和变化

完全动态的目标与允许变化范围来自本次需求。针对其中实际允许的定义、能力集合、实现和组合变化，描述三件事：

| 视图 | 需要回答什么 | 一个检查问题 |
|---|---|---|
| 合法结构 | 哪些能力、实例与关系可同时存在？ | 消费者缺少必需提供者时，结构是否允许存在、能否接纳工作？ |
| 结构内行为 | 在这个组合下，哪些操作和状态变化合法？ | 同一请求所用身份、权限和绑定是否一致？ |
| 结构间变迁 | 怎样改变组合，并在过程中保留必要保证？ | 撤除提供者时，谁接管在途工作和跨实例保留的事实？ |

只画当前模块图会漏掉变化过程；只写重载流程会漏掉合法组合与操作承诺。
运行时集合与关系可变，不意味着身份、不变量或业务政策可任意改变。

## 从消费保证组织责任

先用当前能力基解释需求，检查单个能力及其组合所提供的保证，再从未覆盖责任决定能力演化。
新维度封装新增的独立责任，经契约组合，装配时以独立插件实现进入系统；接受后成为后续需求可复用的承载者。
当前尚缺资料或实现时，不能据此断言需要新维度；具体判断沿[能力分解](../../decompose.md)展开。

能力契约定义可观察含义，插件提供者兑现它，实例承担一次运行的资源与生命周期。
记录、参数与内部函数按所属能力管理，不因出现一个新名词就新增维度；正交性按[边界判据](../modeling/capabilities.md#能力维度的正交性)判断。

分别说明机制、策略和证据：机制提供操作，策略选择何时对谁使用，证据支持性质成立。
例如运行时允许撤除，产品契约仍须选择在途政策，并以对应证据说明保留范围。
具体服务、Agent 工具和 skill 的消费边界见[能力消费方式](../modeling/capabilities.md#系统机制与-agent-消费方式)。

## 不把不同关系压成一棵树

所有权决定谁负责释放；依赖决定工作需要谁；作用域决定解析和可见范围；
业务因果关联事实与操作；部署拓扑划分物理故障边界。
同一对组件可以同时具有多种关系，但每种关系的含义、生效点和变化后果应分别解释。

例如子实例由父实例创建，不足以证明继承其全部权限；同进程调用也不足以证明多次写入原子。
需要把关系绑定时给出理由，随后在[能力边界](../modeling/capabilities.md)与[完整动作链](../../define.md#s5从入口走到稳定点)中核对。

## 检验投影是否保留能力边界

Cordis 投影要能从实际插件、服务、依赖与效应反查能力责任，再由能力及组合解释原需求。
插件清单只显示部分实现结构；能力的承诺、组合前提与证据仍需回到契约核对。
研究暴露无法兑现的前提时回到语义拥有者；语言无关设计与实现调查可以互相校准。
具体步骤由[主线入口](../../../SKILL.md)导航，本页不再维护另一套阶段或产品默认政策。
