## 边界的依据

从现有能力契约与组合检查本次要求的覆盖，剩余责任按[能力演化](../../decompose.md)决定归属。
一个能力维度向消费者提供可独立解释的保证，拥有相应责任，并封装真实变化；实现中能放入某项代码不是边界依据。

定义、提供和消费是角色。服务可以直接实现契约，也可接纳注册贡献；仅为同一个操作改名没有形成新能力。
内部计算可以直接写成函数；确为独立可替换的计算能力时，也可由无额外资源的插件提供服务，不必制造耐久状态。

存储需求本身不要求聚合、Repository 或插件实例。需要发布管理的内容定义可以由服务保存为记录；需要独立启动和结束的行为才需要对应运行实例。数据结构复用其权威定义，不能在每个消费者处复制一份。

## 能力维度的正交性

| 判据 | 应能解释什么 |
|---|---|
| 责任可分别定义 | 各自承诺什么、哪些事实由谁拥有；共享词汇引用同一权威，不要求互不借词 |
| 变化可被边界隔离 | 在消费契约保持成立时，更换一方机制无需重写另一方的语义或依赖其内部表示 |
| 交互明确 | 通过公开契约声明需要与提供的保证，组合约束、共同提交和失败交接均有负责者 |
| 独立演化可兑现 | 加入、撤除或替换一方时，受影响消费者按契约响应，其他合法贡献得到保留 |

正交性是有适用范围的设计判断。能力可以依赖其他能力，也可以共享权威数据定义；
只有前提成立的组合才合法，不能从“维度独立”推导任意装卸顺序可交换。
操作层面的可逆、交换或互不干扰主张按[组合性质](../assurance/composability.md)建立所需证据。

## 服务与插件的不同边界

这一节说的是能力边界与装配单元怎样对应，供装配时核对；**划能力边界本身不看插件**，依据仍是上面的责任与变化。
服务或贡献接口是能力对消费者的表面，插件承载该维度的一项具体实现及其资源生命期。
在本方法中，确认新增独立能力维度后，先定下它独立的契约边界；装配时再由独立的插件提供者承载，使这项责任能被装配、替换和撤除。

一个维度可有多个替代提供者，一个提供者可有多个运行实例或内部部件，这些变化不自动新增维度。
同一插件为本能力提供多个操作/贡献也不表示它承担多个独立维度；多个插件可以放在同一代码包。
装配保持各维度的责任可辨认，不为接线方便隐含绑定本应独立的生命周期，亦不将每个函数变成插件。

判断一个能力边界是否充分，观察它独立变化时谁会受影响，以及谁负责让变化合法
结束。语义依赖和撤除政策属于能力契约；具体插件入口、服务键、注入和运行资源
关系属于[提供者设计](../../workspace-context.md#实现设计与交付)。
两者需要对应，不能以包依赖无环代替运行时组合正确。

## 系统机制与 Agent 消费方式

能力是否供 Agent 使用，是消费者与授权的问题；不是在系统机制之外复制一套
能力，也不要求每项服务自动暴露为工具。

| 消费方式 | 设计要回答的问题 |
|---|---|
| 系统机制与服务 | 哪些行为由系统驱动，哪些保证在实际操作边界强制，其他组件依赖什么？ |
| Agent 工具 | Agent 需要主动查询、执行或控制哪些操作，调用如何关联身份、授权、结果与失败？ |
| Agent 技能 | 哪些判断方法和资源能帮助 Agent 正确选择、组合或使用能力，何时需要读取？ |

这些方式可同时存在。技能不是授权执行器或不变量强制位置；工具入口不能绕过
能力的语义与权限边界。工具被发现、定义被装载、实现可用和调用获准是不同事实，
变化与撤权后仍需兑现相应契约。具体要求沿
[工作区的消费需求](../../workspace-context.md#需求与系统约束)
核对，不从方法论直接接受新的工具名称、协议或装载政策。

## 区分组合关系

| 关系 | 需要说明的含义 |
|---|---|
| 代码依赖 | 哪些公共定义和实现被引入，代码从哪里分发？ |
| 运行依赖 | 哪项能力可用时消费者才可以执行？ |
| 所有权 | 谁负责释放实例、注册和任务？ |
| 作用域 | 名称如何解析，贡献和活动对谁可见？ |
| 业务关系 | 哪些身份、事实和操作在业务上关联？ |
| 部署拓扑 | 哪些部分共同部署，哪些通信跨越故障边界？ |

一棵父子树可以承载其中一种关系。需要把两种关系绑定时，必须说明绑定的理由和变化后果。例如创建了一个子 Agent，不足以自动证明它继承父 Agent 的所有权限。

## 依赖与解析

依赖至少需要明确目标契约、解析范围、必需性和有效期。必需依赖缺失时不得继续按“已就绪”执行；等待、拒绝接纳或结束实例，是需要选择的不同政策。可选依赖缺失时也应有解释得通的行为，不应靠吞掉异常形成默认值。

同名提供者冲突应被拒绝或由明确的选择规则处理。依赖环涉及的是能否激活和取得进展：应说明如何打破循环、延迟哪段行为，或拒绝该组合；不能只验证每个服务名最终都出现在配置中。

依赖声明还包括撤除语义。消费者能否继续持有旧绑定、旧提供者何时可以释放、新请求何时选择新提供者，见[动态演化](../runtime/evolution.md)。有多个相互依赖的字段时，不能在一次操作中分别读取可能来自不同代际的配置。

## 注册条目与替换

依赖注册表和依赖其中某个条目不是同一个条件。例如渲染器需要某个变量，注册表仍存活并不能证明该变量的提供者仍可用。条目级依赖可以通过受管绑定、订阅或独立的生命周期能力表达，选择应与撤除和使用边界相匹配。

替换是否成立，要从消费者可以观察的行为判断。相同方法名和数据形状不足以证明相同含义；错误、持久性、取消和授权保证也是契约的一部分。对多个提供者，用共同的契约场景验证它们兑现相同承诺，详见[规格与证据](../assurance/specification.md)。

例如，本地执行和远程执行可以共享命令执行契约，但远端超时后操作是否仍在运行必须有明确表示。若现有契约只接受“成功／失败”，就需要先修正边界表达，而不是让远程实现伪造确定的失败。
