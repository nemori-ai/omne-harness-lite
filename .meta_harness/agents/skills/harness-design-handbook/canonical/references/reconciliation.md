# 对账：四张表的判据与回询格式

[主线](../SKILL.md)的步骤 D。前三张表判「做不做得到」，第四张判「值不值、要不要把代价送回需求方」。
四张表全部走完才进入步骤 E；表 C 第三行与表 D 同时触发时，**表 C 优先**。

## 表 A：性质承载

把[领域读数](../SKILL.md#步骤-b领域读数)的每条性质，逐条对到[机制读数](../SKILL.md#步骤-c机制读数)的装配草图上。

| 结果 | 含义 | 去向 |
|---|---|---|
| 能 | 机制无条件保护该性质 | **性质写契约，绑定写提供者设计** |
| 有前提地能 | 机制保护的是弱化版，或依赖某个前提 | 同上，且契约写明前提与前提失效时的责任方 |
| 不能，需求正当 | 原语不管这件事 | 契约写清由哪个提供者兑现 |
| 不能，需求过度 | 性质本身要重新谈 | 走[表 D](#表-d代价与需求回询)，不得自行削需求 |

**为什么必须有第二行。** 多数生命周期类性质都落在这里。例：「父 Run 终态 ⇒ 子任务终态」由子 fiber 的
dispose 级联保护，但机制侧的「终态」是「disposer 已被调用、异常已吞」，领域侧要的是「资源已释放」，
中间隔着一个前提（有序收尾须自行在单个 effect 内组合）。只有「能／不能」两格时：判「能」把前提藏起来，
判「不能」又把整条性质推给契约，两边都失真。

**为什么第一、二行也要写契约。** 否则由机制承载的性质只活在分析产物里：上游换版本时绑定报失效，
而契约从没承诺过这条性质，消费者无条款可依。反倒是「机制不管」的性质因为进了契约更稳固——
那与「上游变更不等于领域变更」的目标正好相反。

**绑定的形式**：稳定的语义条目名 + **一个在该语义消失时会失败的测试**。不用行号，行号随上游任何编辑漂移。

## 表 B：内核负面清单

**提问来源是原始需求陈述与可观察结果，不是表 A，也不是性质表。**
若拿性质表来问，领域读数漏掉的性质在这里同样不会出现，清单就退化成表 A 的重复登记，
「把想不到变成查得到」的作用完全落空。条件允许时由不同执行者回答。

逐条问「这条需求需要它吗」：

| 内核不提供 | 需要时谁来兑现 |
|---|---|
| 跨 fiber 事务 / 跨边界原子提交 | 相应组合契约；单流内的批次原子与全域顺序提交不是一回事 |
| 可靠投递（至少一次 / 恰好一次） | 消息或记录能力的契约；effect 卸载不保证对端收到 |
| 外部效应回滚 | 契约须区分恢复、补偿、幂等与撤销 |
| 有序的异步清理 | 自行在单个 effect 内组合次序与结算 |
| 权限边界 / 沙箱 | 授权能力；`isolate` 隔离实例可见性，不隔离数据 |
| 跨进程的身份与可见性 | 协议层；fiber 树是进程内的 |
| 持久化与崩溃恢复 | 记录能力；effect 是内存生命周期 |
| 背压与流控 | 相应能力契约 |
| 时序保证（同 effect 内启动顺序除外） | 同上 |

**命中是常态，不是异常信号。**凡涉及持久化、跨进程、授权、投递的业务需求，命中多条属正常，
按步骤 E 写进契约即可，不因命中多而触发回询。条目的权威归[组合性质](architecture/assurance/composability.md)
指向的证明边界正文，本表只作提问器；上游新增原语时须随采用版本复核本表。

## 表 C：承载复查

需求被关联到**已有对象**时，复查该对象原有的不变式是否仍然成立。

| 结果 | 去向 |
|---|---|
| 仍成立 | 落地 |
| 不成立，但需求可以收紧 | **必须走[回询格式](#回询的四段格式)**，不得以「回到需求谈」名义非格式化沟通 |
| 不成立，且需求正当 | 对象边界画错了，回 C1 重新分解；**领域读数的性质表原样保留** |

第二行的护栏不可省：这里是「用削需求掩盖设计缺陷」最容易发生的地方——修边界贵，收紧需求便宜，
而需求方在不知代价的情况下很可能同意收紧。

第三行的返回边范围：只重做 C1 → C2/C3 → D，**不重做领域读数**（领域没变，变的是谁来承载）。
这条要写明，否则「发现边界画错」看起来像推倒重来，人就会倾向选第二行。

**第三行优先于表 D。**边界画错且修起来贵时，先重新分解再标价；反过来先回询，
需求方见高价而收紧需求，第三行随之消失，旧边界错误被永久掩盖。

## 表 D：代价与需求回询

它防的是两种相反的失败：硬着头皮实现一个代价远超收益的表述，以及拿「太复杂」当挡箭牌削掉正当能力。

### D1 先自证

**回询前必须证明代价不来自自己的建模**：至少换一种对象分解重走 C→D。
换不出更便宜的结构才允许进入 D2。跳过这步的回询，是用「需求太复杂」掩盖建模能力不足。

### D2 四个结构性信号

| 信号 | 触发线 | 在暗示什么 |
|---|---|---|
| 半径异常 | 落点到 #6/#7，但可观察结果只涉及数据或权限差异 | 需求表述可能过宽 |
| 组合爆炸 | 实例数 = 两个以上身份维度的**乘积** | 把「优先级覆盖」误读成「叉乘」 |
| 边界连锁 | 改动 ≥2 个对象的边界（**须反查索引已覆盖**，否则此信号不可用） | 与现有结构系统性冲突 |
| 动态性代价 | **需求未要求、由实现方案引入的**钉死：某能力的演化、装卸或替换被固定 | 违背项目第一目标 |

全部依赖 C1 的对象清单——没有显式分解，这些计数都可以被拆分／合并操纵。

「违背设计理念」用四条可检查判据判：**能力独立演化**（要求共用单一顺序通道即违背）、
**装卸对称**（能装不能卸、卸后有残留贡献）、**依赖显式**（要靠隐藏全局状态或隐式顺序）、
**生命周期有主**（造出没有所有者的长命对象）。

**「需求未要求」这个限定不可省**：需求方自己要求的约束不是代价，是规格。
回询它等于让需求方为自己的决定重新表态。

### 回询的四段格式

1. **当前分解的结构与代价**，用可计数的量（实例数、要改动的对象数、命中条目）；
2. **替代表述及其代价**，必须是具体的另一句需求，不是「能不能简化一点」；
3. **两者在产品语言上的差别** —— 用户因此能做什么、不能做什么。**这一段不能省**：
   只报技术复杂度而不翻译成产品后果，等于把裁决责任推给看不懂代价的人；
4. **本次建议与理由**，同时写明**裁决权不在自己**。

### 不回询的情况

- **单条** SYS-* 硬约束：直接承担，没有裁决空间；
- 拿不出更便宜的替代表述：没有可裁决选项，回询只是抱怨；
- 更好的分解能消化：回到 D1。

**但 SYS-* 之间冲突、或 SYS-* 与产品需求冲突时必须回询**：这类冲突最贵、最结构性，
且只能由有权者裁决，吞掉它正是「从不反馈」。

### 回询之后

两种表述分别往下推，只暂停依赖该裁决的定稿，**不得自行选便宜的那个继续**——
那是偷偷削需求，比硬着头皮实现更坏，因为它不留痕迹。
裁决结果是需求变更，**落在需求正文的拥有者处**；对账过程只留过程记录。

## 走查示例

需求：*用户要能看到某次 Run 的实时输出，断线重连后不丢帧、不重复。*

- **C1 对象分解**：输出帧、订阅、客户端连接、游标 —— 四个对象。
- **C2 落点**：帧 #1 数据；订阅 #3 effect；连接 #7 fiber；游标 #1 数据。
- **表 A**：「游标单调」→ 能（单 writer 的数据）；「已确认的帧不重复投递」→ **不能，需求正当**：
  它要求服务端保留已发未确认的帧，而 effect 卸载只释放本地资源，不保证对端收到。
- **表 B**（从原始需求陈述问）：「可靠投递」命中；「持久化与崩溃恢复」命中（重连要读历史）；
  「跨进程身份」命中（客户端是另一进程）。三条都按步骤 E 写进契约，不触发回询。
- **表 C**：消息流对象原有不变式「帧只是提示、权威在日志」仍成立，且正好支撑上面的结论。
- **表 D**：四信号均不触发。
- **步骤 E**：只在「投递保证」一处展开，补写契约条款——帧是提示、权威在日志、
  重连以日志前缀对齐游标，不从帧流恢复状态。其余直接落地。
- **步骤 F**：连接 fiber dispose 时未确认的帧不重发（在途归属明确）；
  「订阅随连接消失」是装配给的保证，分布式时须由协议重新兑现——这一行写进契约。
