# S6 · 提供者与装配投影

**何时读：**能力覆盖与演化已有结论，需要将契约投影到 Cordis 插件；或契约不变而替换提供者。
**读后留下：**能力维度到插件提供者的映射、采用依据、依赖与装卸政策、组合责任及证据缺口。
**下一步：**按[交付与反查](handoff.md)闭合；机制不能兑现语义时回到[契约](define.md)或[边界](decompose.md)。

## 先用契约提出实现问题

设计说明采用哪版契约、给哪些消费者提供什么保证，再调查所需机制。
既定技术边界从工作区内的[系统约束](workspace-context.md#需求与系统约束)读取。
Cordis、DSH 原语、Agent Loop、Harness、工具协议与治理的复用/自有范围由这些输入确定，
不能从手册的研究来源推断某个包、fork 或业务策略已经被采用。
上游应用策略与可修改 fork 的现有 API 都不是不可更改的产品契约。

研究可与候选规格相互校准，无需等全部 spec 完成。
把关键未知写成“候选能否兑现哪项性质，什么观察会改变选择”，优先核对失败、并发和生命周期边界；
涉及 Cordis/DSH 具体行为时用[来源核对](source-check.md)取得采用版本证据。

## 从能力维度确定插件边界

消费 S3 的承载与演化结论，逐项确定运行时应改变什么：

| 能力分析的结果 | 插件设计的落点 |
|---|---|
| 既有能力及组合足够 | 复用其提供者，补必要消费/装配；不把整条新需求再包成同义能力插件 |
| 契约已足够、实现缺失或不符 | 补齐或更换该能力的插件实现，保留语义身份 |
| 扩展已有能力 | 修订其契约与插件提供者，明确既有消费者影响 |
| 新增独立能力维度 | 定义独立插件承载它的实现、依赖与生命周期，再同已有能力组合 |

独立维度的插件可以提供服务，也可向有明确契约的扩展点注册贡献。
同一维度的替代实现、不同作用域实例及内部函数不因此成为新维度；包/进程划分按实际需要组织。
若无法为新维度说清独立插件应承担什么，回到 S3 检查剩余责任，而不是先制造一个转发包装。

## 选择承担责任的实现路径

| 路径 | 适用判断 |
|---|---|
| 直接采用 | 实际版本在配置、所有权、失败和资源边界内兑现契约 |
| 适配组合 | 差异是表示或真实边界转换，适配能闭合责任 |
| fork 演化 | 保留成熟内核，在明确维护边界内修改必要语义并验证 |
| 自建必要部分 | 已调查的成熟实现不能满足必要契约，或适配/fork 总负担更高 |

选择说明关键替代、证据及未决项；形成正式提案 topic 时遵守[候选准入](design-decisions.md#用能改变选择的依据比较)，不要求逐级试遍所有实现路径。
fork 要保留源基线、修改范围、许可条件、上游修复与后续维护责任；
没有独立行为或边界价值的转发包装不增加保障。详细判断按需读[复杂度与复用](architecture/assurance/judgment.md#复杂度与复用)。

文档不足且未知足以改变选择时做最小区分实验，观察实际资源、结果与失败状态。
上游源码实验、发布包验证、项目 fork 和真实组合证据分别记录；必要保证已有适用依据即停止扩展调研。
候选不适用、证据不足和原设计前提被推翻分别处理，不由某个库失败推出降低契约要求。
需要持久化取舍或接受机制时，按[设计选择](design-decisions.md)留下比较、前提和准确的接受范围。

## 由责任推导运行时形状

| 契约责任 | 需要明确的投影 |
|---|---|
| 对消费者的承诺 | 服务/操作、所需版本及消费方式；不按每个类型强设服务 |
| 实现装配与资源所有权 | 插件、实例、配置和作用域；按独立生命周期与演化决定划分 |
| 同提交组合 | 组合逻辑进入能兑现共同提交的写入/协调边界 |
| 只读投影 | 事实读面、依赖、权限、缺席与新鲜度政策；依赖方向不能替代权限保护 |
| 政策/定义变化 | 配置或贡献、解析与绑定的工作边界、生效版本及历史关联 |
| 机制替换 | 准入关闭、在途归属、拒绝/排空/终止/迁移、旧引用与新代际 |
| 受管效应 | Context/Fiber 采用方式、资源取得、清理/交接、静止与完成条件 |
| 事实与后续反应 | 类型化事件或事实流；明确顺序、投递、耐久与恢复的实际承担者 |

插件的内部实现部件、多个操作与运行实例不改变能力维度的语义边界；
实际投影还要保留不同维度各自的演化和资源责任。具体检查见[能力边界](architecture/modeling/capabilities.md)与
[Cordis 映射](architecture/reference/cordis-mapping.md)，具体 API 以实际采用版本核对。

## 装卸必须成对设计

每项装载贡献写清：取得了什么、谁拥有、何时对外可用、部分失败如何收口、
撤除时清理或交接什么、保留什么事实，以及谁观察完成。
停止请求、关闭准入、排空、结算、释放不是天然同一个动作；实际次序和完成条件归契约。

分别处理 required 提供者撤回、条目消失、一次操作返回不可用与结果未知。
运行时失活不会自动选择产品的重试、降级或取消政策。
沿[生命周期](architecture/runtime/lifecycle.md#装载效应与撤除责任)和
[动态演化](architecture/runtime/evolution.md)核对晚到回调、旧清理、外部效果和恢复责任。

工作边界难以把握时选一个相关例子读：
[提示词绑定](architecture/examples/prompt-bindings.md)、
[模型切换](architecture/examples/model-switch.md)或
[存储替换](architecture/examples/storage-replacement.md)。
示例是候选政策演示，不会替本次产品选择排空或迁移方式。

## 落为提供者与应用设计

提供者正文应覆盖实际需要的契约映射、服务/公开操作、依赖与绑定、
作用域/资源/释放、并发和失败路径、采用版本及符合性证据。
已实现的签名引用公开源码；尚未实现的接口可标为候选，不造看似真实的 API。

应用装配说明选择哪些提供者、在哪里实例化和配置、怎样消费，
以及跨能力动作链由哪个真实边界实现。业务政策留在所属能力，
应用接线与工具暴露不能暗中补齐语义缺口。

部署范围由内部要求决定；需要保留未来跨进程边界时，检查身份、序列化、权限、失败与写权的含义；
需要时读[部署边界](architecture/runtime/distribution.md)，不预建远程平台。
长期提供者/装配设计和临时施工计划按[工作区归属](workspace-context.md#实现设计与交付)分开归属。

**完成判据：**能力维度与插件提供者的对应可解释，每项关键语义有运行时责任，装载与撤除可配对，
依赖变化与真实组合有政策，采用机制有证据或清楚的未决项。
仅给插件列表、服务键或上游示例代码，尚不足以交给消费者实施。
