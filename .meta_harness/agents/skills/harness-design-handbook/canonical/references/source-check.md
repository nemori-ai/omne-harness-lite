# 核对 Cordis 与复用原语的实际语义

**何时读：**API、依赖解析、Context/Fiber、事件、注册、句柄或清理行为会改变本次设计。
**读后留下：**主张 → 采用对象/版本 → 原始证据 → 适用范围/未知。
**返回：**[提供者投影](project.md)；纯语言无关设计不要求先做上游全面调查。

## 明确核对的是哪一个对象

从工作区内的采用决定、提供者设计及其明确指向的依赖快照或 fork 记录定位版本。
需要读源码或锁文件时使用该映射给出的代码位置和修订，不默认扫描工作区外的当前检出。
分别记“实际采用版本”与“此次查阅版本”；项目尚未固定依赖时明确为候选，不能拿上游 HEAD 代替。
分别记录官方发布包、可能采用的 fork 和待设计系统组合，三者证据不混用；没有采用记录时只讨论候选。

它不是当前安装版本证明。先复用仍适用的本地研究，再查必要的官方资料。

## 按主张寻找最短证据链

1. 定位官方 [DeepSeek Harness 仓库](https://github.com/deepseek-ai/deepseek-harness)
   中对应修订的文档、源码与测试。具体页面应记录固定提交或发布版本。
   核对复用的 DSH agent 原语时展开该组件自己的说明，不把 Agent Loop 或上游应用策略当作原语契约。
2. 把主张写具体：例如“这个 emit 是否等待监听器返回的 Promise”，
   而非“事件系统是否可靠”。文档未覆盖时查实现与相应测试。
3. 必要时做能区分结论的小型验证，说明执行的是源码、发布包还是项目 fork。
   未执行不能写成通过；实现细节观察也不自动是公开兼容承诺。
4. 将结论映射回待设计系统契约与调用方式，指出仍由提供者、消费者、装配或环境承担的前提。

区分直接事实、根据事实的推断与未知；记录具体页面/源码位置、修订和验证条件。
无法访问所需来源时保留受影响选择与下一项核对，不编造 API 或默认为框架保证。

文档与源码不一致时，先检查是否同一修订、同一发行物及是否经过 fork/适配。
确为同版本差异时保留双方位置、实际观察和受影响主张，暂停依赖未确认行为的定稿或修改，
继续独立工作；不能静默采用更方便的一方，也不能把源码观察自动升级为公开保证。

## 容易越过证据边界的地方

- 核对撤除是否只覆盖受管效应、是否等待异步工作、部分失败与异常如何处理；
  不能从“有 disposer”推断业务撤销或外部输出可逆。
- 核对依赖服务与注册条目的不同寿命、旧引用/句柄的失效方式；
  一次操作不可用不必等同于依赖被撤回。
- 核对事件通知、决策拦截与持久事实流的差异；方法名称不能证明顺序、等待或耐久投递。
- Context 可达性、宿主执行权限与租户授权分别验证；运行时标识不直接充当持久身份。
- 若借上游定理或证明支持组合，核对操作族、表示、观察关系和失败前提；
  按[组合性质](architecture/assurance/composability.md)判断待设计系统新增义务。

**停止判据：**关键主张已有足够版本证据，剩余未知及其消费影响明确。
不因核对一个原语扩大到 DSH 整个应用，也不由上游行为决定待设计系统业务政策。
