# 评审判据：选择

design-reviewer 被派来判**选择**时读这一页，并且只读这一页判据。
待审的是一份架构设计的可识别待审稿——主线或负责人亲写的领域读数与承载读数、一次能力边界的选择、
一批契约的语义整体、或一个 realization 节点的提供者／装配设计。你判的是**选择本身**：
边界画对了没有、每条性质挂在能兑现它的地方没有、没有谁白给的保证有没有写进契约、
装配有没有「形状像、语义不重合」的绑定。

**Cordis 只在审 realization 节点时出场。**它是装配时要满足的契约规范，不是建模的视角：
读数、能力边界与契约批次都用领域与能力的语言来审，里面出现内核机制词本身就是发现（见下面的三条纪律）；
只为划清界线的否定式说明（「这里的服务不是内核里的 service」）不算。

## 判断什么

| 维度 | 你要找什么 |
|---|---|
| **承载与边界** | 要求是否先投影到了现有能力与组合；新维度有没有说清合理组合／扩展为何承担不了；边界有没有「要求跨拥有者同提交」「重复拥有同一事实」「反复同步修改」这三条反查信号 |
| **性质承载** | 领域读数里的每条不变量／安全／进展性质，对到承载草图上是「能」「有前提地能」「不能」中的哪一种；前提写没写进契约；进展性质有没有前提与上界 |
| **没有谁白给的保证** | 从**原始需求陈述**问：跨拥有者或跨生命周期单元的事务、可靠投递、外部效应回滚、有序异步清理、权限边界、跨进程身份、持久化与崩溃恢复、背压、时序——命中的每一条**由谁兑现有没有写进契约** |
| **承载复查** | 需求关联到已有对象时，该对象原有不变式是否仍成立；不成立是收紧需求还是边界画错 |
| **代价** | 半径异常、组合爆炸、边界连锁、需求未要求的钉死——这四个结构性信号有没有出现；出现了有没有自证与回询 |
| **反向核对** | 审契约批次时只问一件：**跨进程后哪些保证失效**，装配给的与协议给的有没有分开写进契约。审 realization 节点时再加三问：dispose 时在途工作归谁；依赖消失时谁被卸载、范围对不对；事件会不会跨边界泄漏 |
| **装配对齐**（只在审 realization 节点时） | 每条绑定是否先验证过「机制语义 = 领域语义」；装载效应与撤除责任是否配对；异步控制事件是否用了 `bail`；**契约要求「跨 owner 同一提交」的每一处，提供者有没有指出两个写入者共同触碰的存储对象**——时间谓词、进程内锁、未落盘的「单调事实」都不算，构造两条交错去反证；绑定是否空洞（模型里没有在该条款被违反时会失败的断言） |

第二到第五行是对账四表，后两行是主线 F 步的四问与符合性核对——**评的判据要和写的判据是同一套**。

## 不归这一种判断

**表达**——同一句话有没有两种读法、九件事齐不齐、条款坐标与 registry 登记对不对、Schema 与正文一不一致、
rev 标注新不新——归「表达」那一种判断。**施工顺序与分工**归「计划」那一种。
产品方向对不对归产品负责人与 product-design-reviewer。算法证明、实现符合性、替代技术栈的选型也不归你。
顺手看到了，在「未覆盖」里点一句转交，**不写成本次的发现**。

**你不替有权者做选择。**需求冲突、政策未决、两种拆法都说得通时，你指出它阻塞什么承诺、
两边各自的代价，**不代选**；「我会这么切」不是发现，「这么切之后 X 性质没有保护点」才是。

| ✗ 不是你的意见 | ✓ 是你的意见 |
|---|---|
| 「这两个能力我会合并」 | 「S-20 ④ 要求把账号侧两条判定拉进治理的提交边界——这是跨拥有者同提交的反查信号，而设计正文没有自证这条边界为什么仍然成立」 |
| 「这个默认值选错了」 | 「进展性质『邀约最终过期』写在性质表里，但前提『时间源不后退』既不在契约也不在装配给列表，落在哪一侧都没人认领」 |
| 「应该用 serial 派发」 | 「S-9 声明这是可否决的异步控制，绑定用 `bail`；`bail` 不 await，这条绑定的语义与契约不重合」 |
| 「这条链太复杂」 | 「组合以『唯一提交点 + 幂等重跑』省略了跨边界原子提交，按组合性质这触发行为模型义务；formal-tasks 只登了一个配置，崩溃交错那一支没有检查」 |
| 「S-7 措辞有歧义」 | （转交「表达」，不写成本次的发现） |

判据：**你的意见指向一个选择的后果——某条性质失去保护点、某个保证没人兑现、某条边界的代价没被标价——而不是指向你自己会怎么设计。**

## 待审对象与特有输入

| 待审对象 | 特有输入 | 你回答的问题 |
|---|---|---|
| **领域读数与承载读数**（主线或负责人亲写，没有起草角色） | 两份读数及各自开头的「读了什么、没读什么」与封存位置；需求 topic 与精确 rev；`domain_objects/objects.md` 相关条目 | 性质表漏了哪条需求推得出的性质；两份读数里有没有混进内核机制词；对象分解有没有另一种站得住的切法；落点分类里「为什么前面几个不是」成不成立 |
| **能力边界的选择**（一次拆分／合并／新增维度） | `record/proposals/<topic>/` 的候选包（**至少三个实质候选**，不足即为发现）；领域读数产物（性质表）与承载读数产物（对象分解、落点、承载草图）；`domain_objects/objects.md` 相关条目 | 边界画在哪最能兑现性质表；反查信号有没有出现；代价有没有被标价；**候选之间比的是不是能力层的后果**——拿「落成几个插件、谁 inject 谁」当论据的，那是装配落位，不是能力边界 |
| **一批契约的语义整体**（同一领域的 data／capability／composition） | 全批清单与坐标；需求确认范围；registry 的 catalog 与 covers（只消费坐标，不核登记本身）；设计评审报告的「依赖图」一节 | 跨契约动作链在每个拒绝／失败／撤除分支上是否有唯一的责任拥有者；性质→保护点→证据这条链闭不闭合；「没有谁白给的保证」命中项是否都写进了契约 |
| **realization 节点**（`packages/<node>` 提供者设计、`apps/<node>` 装配与 `architecture.md`） | 它引用的契约坐标与 PF；`bindings.yaml`；相关 basis 条目；节点的 Cordis 符合性核对表 | 每条绑定的机制语义与契约语义是否重合；装卸是否配对；装配给／协议给拆分是否与契约一致；`architecture.md` 的每条边上的保证有没有落在某份契约里 |

**不要读任务区（`tmp/`）里主线的处置表**：那里有派发者的倾向，会把你的独立判断带偏；
派发者要你参考已裁方向时，会把它写进简报。

## 读的顺序

1. **派发简报**——先确定待审对象是四种形态里的哪一种，本次该兑现什么。
2. **需求与全局约束的确认范围**——产品正文的相关小节、`foundation/cross-system-constraints/`；
   `domain_objects/objects.md` 的相关条目（**它是输入不是依据**，对不上以它指向的产品正文为准）。
3. **共用的 data 契约**，再逐份 capability／composition，再 realization 节点（如有）。
4. **只在某条核对真的需要时**，展开[对账](../reconciliation.md)（四表的判据与走查示例）、[能力覆盖与演化](../decompose.md)（反查边界）、
   [提供者与装配投影](../project.md)（投影与装卸配对）、[性质](../architecture/assurance/invariants.md)（双向核对）、
   [组合性质](../architecture/assurance/composability.md)（证明义务门槛）、[来源核对](../source-check.md)（Cordis 行为取证）。
   **不通读 references。**

区内规矩从 `design/AGENTS.md` 与各 family 的 AGENTS.md 取；**导航到设计材料不授予重新裁决产品政策的权限。**

## 三条纪律，先核有没有被守住

主线有三条不可妥协的纪律，任一条没守住都是**结构性发现**，优先级高于一切局部问题：

| 纪律 | 判失败的样子 |
|---|---|
| **双盲**：领域读数在承载读数之前完成并封存；A～E 不用内核机制词 | 性质表、承载读数或能力拆分提案里出现 fiber／service／effect／inject／label 等机制词；或两份读数出自同一执行者，却给不出领域读数先行封存的位置（哪个提交），也没有标注「双盲未达成」 |
| **绑定到语义条目，不是行号** | `bindings.yaml` 或 basis 条目引用上游源码行号而没有稳定名字和「该语义消失时会失败的探针」 |
| **契约写性质，提供者写绑定** | 契约条款里出现内核机制词——fiber／service／effect／inject／label、`ctx.intercept`、`serial` 这类派发模式、服务键、插件名（否定式的辨义说明除外）；或提供者设计改写了契约语义而不是引用它 |

## 对账四表，逐张扫

**表 A 性质承载**：把性质表的每一条对到承载草图上。四种结果里第二种「有前提地能」不可省——
判「能」会藏前提，判「不能」会把整条推给契约。**第一、二种都必须产生契约条款**，只活在流程产物里的性质是发现。

**表 B 没有谁白给的保证**：**从原始需求陈述提问，不从性质表提问**——否则 B 漏掉的性质这里同样不出现。
命中是常态；**发现是「命中了却没有契约写明由谁兑现」**。契约写的是由谁兑现，不是「内核不管」。

**表 C 承载复查**：需求关联到已有对象时，原有不变式是否仍成立。不成立且需求正当 ⇒ 边界画错，
这一条**优先于代价判断**——先重分解再标价。

**表 D 代价**：四个结构性信号（半径异常、组合爆炸、边界连锁、动态性代价）出现时，
设计有没有先自证（换一种分解重走；从步骤 F 回来的那一种，自证是换提供者设计，**为迁就装配去重分解领域对象是发现**）、有没有按四段格式回询。
**这四张表不评判需求正当性，它们给需求标价**；你也一样——标出价，谁付得起归有权者。

## 整洁方面要问的

这几问都要落到「哪条依赖、哪份契约、改哪个需求时会怎样」，答不出具体后果的不写成发现。
下列涉及依赖图的问法，读数从派发者附的设计评审报告里取（[工作区上下文](../workspace-context.md#规格维护与验证)给出入口），**不自己数**；简报没附就在「未覆盖」里写明这几问未核。

- **被依赖得多的那一份，是不是稳定且简单。**报告里「稳定的依赖不稳定的」每一条：被依赖方为什么会常变，
  依赖它的那一份有没有因此被拖着改；设计有没有解释这条方向。
- **会一起变的东西是不是放在一起，不会一起变的有没有被捆在一起。**一份契约若同时服务两类各自会变的消费者，
  指出哪个消费者的需求变了、另一个要不要跟着改。
- **依赖图上的环。**环上每一份都不能单独演化；设计有没有说清为什么这个环是必要的、由谁一起发布。
- **契约里有没有只为当前实现方便而钉死的东西**（与「代价」一行的「需求未要求的钉死」同一问，这里从依赖方向再问一次）。

- **新依赖接得多紧、隔得多远。**每条新依赖，问它的集成强度——只经契约、共享一份数据模型、依赖对方的功能行为、还是伸进对方内部——
  与距离——同一成员内、同组、跨组。**强而远**的是发现候选：指出哪一方改了另一方要跟着改、跟着改的成本落在谁身上。
  **它会不会常变不由你判**：易变性要问负责人。在「未覆盖」里写成一问，附上若答「会常变」时这条依赖的后果。
- **这个成员藏住了哪项决定。**每个新成员或新边界，说得出它把哪一项可能变的决定藏在里面、不让别处知道；
  说不出的，指出它把哪项决定暴露给了谁、那项决定一变哪个消费者会被拖着改。
- **提案带不带效用树**（只在审能力边界的选择时问）：新能力边界的提案要有一棵质量属性效用树，每个候选对排在前面的场景给出了响应与风险；
  没有，写成发现（它阻塞的是「候选之间比的是不是能力层的后果」那一问）。你对候选给出的风险、敏感点与权衡点标「候选，待负责人裁」，不代裁。
- **装配上的隐性耦合**（只在审 realization 节点时问）：两个插件之间有没有靠撤除先后、调用时序或服务名字符串的约定耦合在一起，
  而这条约定没写进任何一份契约或节点声明。这一问只用在装配与实现评审里；能力边界与契约的评审不拿它当论据。

## 审读数时的额外纪律

读数是写的人自己的判断，你的任务是**反驳**，不是润色：

- **从需求正文正向推一遍**应有的不变量、安全与进展性质，再和性质表对；漏掉的每一条给出需求小节与一个会因此失去保护的场景。
- **对象分解给出至少一种别的切法**，说清它在哪条性质上更好、在哪条上更差；找不出站得住的别的切法，就直说找不出及查过的范围。
- 说不出观察者的「性质」是实现偏好；读数里拿上游或内核的行为当论据的，一是越了位（那属于装配），二是没有引 basis 条目的标为未取证的假设。
- 你不改写读数，也不给出「你会怎么读」的整份替代稿；反驳指向的是读数会导致的后果。

## 审能力边界时的额外纪律

边界是基座级选择，会被后续每一份设计引用。除四表之外：

- **候选空间**：`record/proposals` 要求至少三个实质候选；改名、调参、空占位不算。不足即为阻断。
- **反查信号**：[反查边界是否合理](../decompose.md#反查边界是否合理)的三条——跨拥有者同提交、重复拥有同一事实、反复同步修改——
  逐条问；命中而设计未自证的，写成发现并给反例位置。
- **你自己的结论要带反证**：对推荐的边界写出**落选方最强的论证**（不少于三条，带位置）、**推荐方的已知弱点**与**置信度**。
  一份只有赞成理由的评审不比作者自检多任何信息。

## 审契约批次时的额外纪律

- **性质双向核**：从目标与需求正向推应有的不变量／安全／进展性质，再从契约的性质表反向看每条有没有需求来源、
  保护位置、跨能力责任与证据义务；**遗漏的必要性质要给来源与反例**，不把个人偏好补成要求。
- **一条真实动作链走到底**：入口 → 准入 → 提交 → 交接 → 结算，走到最可能丢责任的拒绝或失败分支——
  每个局部状态都合法，不等于整条链有合法终点。缺口写成「在何种输入或交错下，哪个消费者无法依赖哪项承诺，由谁补齐」。
- **证明义务门槛**：以自定义协议省略或放宽了某种控制（跨边界原子提交、可靠投递、有序清理）时，
  按组合性质核对行为模型、性质与检查配置是否覆盖了被省略的那一条；**有限检查不是无条件证明**，声明范围不得超过实际证据。

## 审 realization 节点时的额外纪律

- **绑定对齐先于一切**：`intercept` 的合并顺序是装配链，领域优先级链是数据层次——形状相似但语义不同的绑定是最常见的错误来源；
  每条绑定先核「机制语义 = 领域语义」再看别的。
- **装卸配对**：每个 effect 释放什么、交接什么、什么仍为真；内核不保证有序异步清理，依赖清理顺序的设计是发现。
- **派发模式**：契约声明的异步控制事件用了 `bail` 直接判失败（依据 `basis/cordis/async-control-not-bail.md`）。
- **装配给 vs 协议给**：节点把哪些保证记为装配给，与契约的同一张表是否一致；跨进程后失效的保证有没有落在契约里而不是节点笔记里。
- **Cordis 符合性核对表**：节点自己填的那张表逐行核——填「符合」的有没有指到 design.md 的具体位置，填「不适用」的理由成不成立；表缺了就是发现。
  表里的行与主线步骤 F 对照表「核对什么」一列是同一套：纯数据没有进 `ctx`、没有借机扩大服务面、公开函数面没有被服务面吞没、跨重载要留的事实不只活在闭包里，都在其中。
- **`architecture.md`**（assembly）：每条边上的保证有没有落在某份契约；引用的 PF 与提案是否闭合；**不代选技术栈**。

## 四层就绪，只作报告维度

语义接受、提供者可实施、装配明确、实际验证互不替代（[交付](../handoff.md#区分四层就绪状态)）。
你核对本次**声称完成的**是哪一层、依据是什么；不把语义审阅扩大为对未受审实现设计的接受，
也不因某层未到就否定已到的那一层。

## 这一种判断的报告

发现的类别：**承载与边界 / 性质承载 / 没有谁白给的保证 / 承载复查 / 代价 / 反向核对 / 装配对齐 / 纪律失守**。
依据指到需求小节、契约坐标、本手册的参考页或 basis 条目。

**每条阻断额外写两句**：「为什么它必须在本阶段闭合」，以及「它是否一处措辞即可闭合」——是就归非阻断。
复评按「同一交付对象 + 同一基线」计轮，第三轮仍有实质阻断会触发[全局结构诊断](../handoff.md#三轮未收敛时升级结构诊断)；
所以要严格区分「结构性不一致」与「表达没落实」，后者转交「表达」。

审读数时另加一节：**漏掉的性质、另一种切法及其得失、未取证的假设**。
审能力边界时另加一节：**推荐方、落选方最强论证、推荐方已知弱点、置信度与改票条件**。

没有阻断发现时说「**本次范围内未发现阻断问题**」。
