# 评审判据：表达

design-reviewer被派来判表达时只读本页判据。以给定的已决定设计为前提，判断承诺是否完整、明确，能否实施而无需开发者补政策。待审对象可以是公开接口、模块薄SPEC及相应Schema/模型，或同批多份承诺。

## 判断范围

| 维度 | 问法 |
|---|---|
| 表达歧义 | 同一条件下是否有两种读法、字面冲突或同名不同义？ |
| 完整性 | 给定设计中的有效承诺是否都有实际拥有者和明确落点？ |
| 可实施性 | 两个实现者是否会因缺决定而做出不同结果？ |
| 引用与归属 | 公开定义、行为条款、词条、采用范围及实际资源能否定位，是否只有一个现行源？ |
| 跨契约一致 | 同一概念、失败和交接两端是否一致？ |
| 形式对应 | 条款→性质→实际配置是否闭合，范围是否超过证据？模型有无违反该条款会失败的断言？建模吸收身份或TypeOK自指不是对应证据。 |
| 归属越界 | 是否复制另一拥有者的承诺，或把具体提供者承载反写为公共业务？ |

不判断业务选择、替代架构、算法证明、实现符合性或施工顺序。发现这些问题时只在未覆盖中转交，不纳入表达阻断。完整性相对给定设计范围，不覆盖所有想象需求。

## 输入与机器检查

简报给出完整待审清单、修订/快照、依据、范围和已决定/未决边界。派发者附实际适用的类型、引用、Schema、依赖、模型配置或资源检查及执行范围。机器已核项目不重复手算；报告一条读数不自动等于缺陷。

逐条判断成立项；工具unknown按其明确范围人工核对。报告未附或没有适用工具时，指出具体未核机械范围并继续语义表达判断，不要求旧中央报告、不凭空声称工具已覆盖。评审者不运行检查。

阅读顺序：简报与设计依据 → 已有机器输出 → 共享公开定义 → 每份薄SPEC → 跨拥有者核对。仅在具体条款需要时展开[完整动作链](../define.md)、[规格演进](../spec-evolution.md)、[规格与验证](../architecture/assurance/specification.md)或[契约描述](../architecture/reference/contract-description.md)。实际归属见[工作区上下文](../workspace-context.md)，不通读手册、不从shell位置猜政策。

## 操作的九个行为问题

对每项公开操作核下面问题。类型和必要校验表达形状，薄SPEC补类型表达不了的行为。无需固定九行表，也不复制已归其他拥有者的定义；不适用项须能解释，不为未承诺行为补政策。

| # | 要辨认什么 | 典型缺法 |
|---|---|---|
| 1 | **输入与授权**：调用主体、作用域、租户身份、使用时判定、非法输入。**身份类参数不得有默认值** | 写「默认当前租户 / 当前账号」——一有默认值，越权路径就从「传错」变成「不传」 |
| 2 | **前置条件**：什么状态下可以调用；不满足时是拒绝、无操作还是别的 | 只写 happy path 的前提，不写不满足时发生什么 |
| 3 | **提交点与原子性**：何时算发生；是**单次提交**还是**跨多次提交** | 写「创建并通知」，却不说通知失败时创建是否已经成立 |
| 4 | **返回与失败集合**：**逐项枚举**，不留「其他错误」「等等」 | 开放式收尾；或正文提到一种拒绝理由，失败集合里没有对应项 |
| 5 | **幂等边界**：以什么为身份判重，重放同一请求得到什么 | 只说「幂等」不说键；或给有不可撤销外部效果的操作声称幂等 |
| 6 | **事件**：是**已提交事实的通知**还是**可改变结果的控制**，以及**派发模式** | 只写「发一个事件」。派发模式缺失，消费者无法知道自己能不能否决 |
| 7 | **缺席时的默认答案**：依赖不可用、记录查不到、超时——**拒绝还是放行** | 完全不写。这是最危险的缺口：不写等于让实现挑一个，挑错的那一侧是静默越权 |
| 8 | **在途操作的归属**：依赖撤除、替换、重启时，已经在跑的那一次归谁，迟到结果怎么解释 | 只描述稳态，不描述演化 |
| 9 | **装配给 vs 协议给**：哪些是装配时确定的，哪些必须写进契约 | 把本该跨节点成立的约束留给「反正是单机装配」 |


跨边界原子性、授权、恢复、迟到责任或外部效果不因第一版单机而省略。身份参数不能默认当前tenant/account。事件区分通知/控制及等待方式；异步控制不能由同步bail静默放行，机制依据归实际提供者及[最小内核模型](../architecture/reference/cordis-kernel.md)。

## 现行维护约定

| 核对 | 反例 |
|---|---|
| 跨拥有者引用可定位到真实公开定义/行为小节，数据身份不因搬动改变 | 裸条款号指另一文档，Schema URI搬动后被改成新身份 |
| 正式概念沿统一语言；新概念和未决政策由真正拥有者决定 | 临时同义名或合理默认值掩盖未定授权 |
| 当前产品依据、采用范围与实现/验证分别陈述 | 文件存在、绿测或候选被说成已接受/兑现 |
| 公共承诺一份现行源，提供者和消费者均可找到 | 两个SPEC复制同一业务，改一个仍有另一份现行权威 |
| 模型/配置及规范场景在所属成员，单次评审和执行输出留tmp | 原始运行报告进入SPEC、ADR或.meta_harness |
| 语义修订有授权，公开接口、模型、Schema和消费者同步 | 改断言、缩scope或放宽失败集合求通过 |

公共业务与具体Cordis承载分清，但不把薄SPEC中说明正式绑定/撤除的机制词一概判错。结合实际拥有者判断是否改变共享领域语义；纯数据/计算不必制造Service或Fiber。

## 跨契约批次核对

单份读得通，一批放一起未必。同一批多份同时受审时，四项各走一遍：

1. **共享公开定义的字段**：各份引用同一字段时，**名字、取值域、含义**是不是同一个。
2. **同一概念被定义两次**：第二处就是问题——指出哪一份是权威，另一份应改为引用。
3. **A 依赖 B 的条款，B 真的承诺了那件事吗**：翻到 B 的那一条读原文，
   **不看依赖表的措辞**——依赖表写的是 A 以为 B 承诺了什么。工具只核那一条存在，不核它说了什么。
4. **交接的两端说的是不是同一句话**：前方**何时释放**、后方**何时接纳**、
   **回执丢失谁收口**。两份各写一遍而不一致，是最常见也最贵的一类。

## 消费者视角走查

先按[契约描述](../architecture/reference/contract-description.md)的「消费者需要知道」表**逐行问一遍**：
对谁承诺什么、如何辨认和访问、谁能观察哪些事实、何时可以使用、何时算发生或结束、谁保留和释放、
什么必须保持或最终发生、改变后怎样继续、额度与时间怎样约束行为、跨边界是否仍成立、凭什么依赖保证。

再**选一条真实的动作链**走一遍：**入口 → 准入 → 提交 → 交接 → 结算**，
一直走到**最可能丢责任的拒绝或失败分支**——
例如前方已经交出工作资格，后方授权直接拒绝，而路径只有「允许」和「待批准」两种：
**谁来结算，谁来接续原工作？**

> **每个局部状态都合法，不等于整条链有合法终点。**

缺口写成这句话的形状：**在何种输入或交错下，哪个消费者无法依赖哪项承诺，由谁补齐。**
交接的落点是所属能力或组合契约，**不能靠补全 Schema 或列齐接口把最后一段行为遮过去**。

## 形式工件对应

- **条款 → 不变式 / 性质名 → 检查配置**，三段映射是否闭合？少一段就是断链。
- 有前提的进展性质，**前提是否同时写在配置与正文两处**？只写在配置里，等于正文在撒谎。
- **有限检查有没有被写成无条件证明**？TLC 在已检查范围未发现反例、
  Alloy 在给定 scope 未发现反例，都不是任意范围的证明。
- 执行配置、原始输出、反例是否在工作树tmp，并绑定实际输入修订？

**没选某个工具不自动是缺陷**；只有**设计已经触发的义务被遗漏**才是。
不要求所有 topic 都有 TLA+ / TLC / Alloy。这里只核对**声明与证据是否对应**，**不裁决算法证明**。

## 这一种判断的报告

发现的类别：**表达歧义 / 完整性 / 可实施性 / 引用与归属 / 跨契约一致 / 形式对应 / 归属越界**。
依据指到权威——公开接口/行为条款、词条ID、实际验证资源、basis条目；出自工具的发现注明核对项标识。
建议写成「必须补足什么」，不要发展成另一份规格。

没有阻断发现时说「**本次表达与规范范围内未发现阻断问题**」。
