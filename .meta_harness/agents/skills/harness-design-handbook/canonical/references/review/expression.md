# 评审判据：表达

design-reviewer 被派来判**表达**时读这一页，并且只读这一页判据。
待审的是一份规格——一份契约，或同一批同时受审的多份。你以**给定的能力设计为前提**，对**规格文本本身**做评审：
这些已经定下来的承诺，有没有被完整、明确、规范地表达出来；另一个人能不能照着它实施，而不必自己替作者补决定。

## 判断什么

| 维度 | 你要找什么 |
|---|---|
| **表达歧义** | 同一句话有没有两种读法？同一条件下有没有字面冲突？有没有同名不同义？ |
| **完整性** | 设计已经定下来的承诺，是否**逐条**在规格里有落点？每项操作的九件事齐不齐、写得够不够实施？ |
| **可实施性** | 两个实现者照这份规格写，会不会做出不同的东西？哪一处**开发者将不得不自己决定**？ |
| **引用与登记** | 条款坐标、词条、rev、`catalog` / `covers` / `formal-tasks` 登记，是否互相对得上、指得到？ |
| **跨契约一致** | 同一批里几份契约，对同一件事说的是不是同一句话？ |
| **形式对应** | 条款 → 性质 → 检查配置这条链闭不闭合？声明的范围有没有超过实际证据？**模型里有没有一条在该条款被违反时会失败的断言**——被建模方式吸收的语义（复用同一元素表达「同一个」、`TypeOK` 自指）不构成对应 |
| **归属越界** | 这份契约里有没有本该归另一份契约、或本该归提供者/装配的内容？ |

前三个是主体，靠判断力。「引用与登记」里能机械算的那部分**已经由工具算过**，见下一节；
工具不算的仍要你**逐项扫完**——漏掉的，下一版还得再扫一遍。

## 先读工具算过的

派发者应当在简报里附一份**设计评审报告**（入口见[工作区上下文](../workspace-context.md#规格维护与验证)）。
它是确定性的机械核对，**报出一条不等于规格有错**，你的事是逐条判断：

| 报告里的一节 | 你怎么用 |
|---|---|
| 成立的问题 | 逐条回到原文看是否成立。成立的写成你的发现（类别多为「引用与登记」「完整性」），标明出自工具；不成立的在报告里说一句为什么，供派发者收紧工具 |
| 未能判定 | 这些是工具认不出写法、没有判的。**由你用眼睛补上**，范围以它列出的为准 |
| 依赖图 | 「表达」这一种不评依赖方向对不对；只在它暴露登记与正文对不上时使用 |
| 未覆盖 | 工具明说不判的，全部归你 |

**工具已经核的，不要再用眼睛重做一遍**：未带坐标的条款引用、分析阶段编号进契约、产品依据的 rev 是否过期、
catalog 依赖声明消费的条款是否存在、covers 是否指得到、版本目录里有没有未登记的文件、
九件事表格是否缺行、失败集合是否开放式收尾。

简报没附这份报告时：**先在返回的开头指出来**，再照下面的硬约定表把上述各项也人工扫一遍，
并在「未覆盖」里写明「机械项未经工具核对」。不因为没有工具输出就跳过。

## 不归这一种判断

**你不判断业务选择是否正确、合理或值得采用。**
「这个能力不该这么切」「这条政策我不同意」「应该再拆一个契约」「这个默认值选错了」——**这些都不是你的意见**。
业务语义由架构设计者选定、由有权者接受；你评的是「选定的那件事有没有被说清楚」，不是「选得对不对」。
把政策分歧写成规格缺陷，会淹没真正的缺陷，也会把评审变成两份设计方案的拉锯。

同样不归这一种：算法正确性证明、实现符合性、替代架构设计（归「选择」）；
施工顺序、人员分工、工作树写入冲突、估时（归「计划」）。顺手看到了，在「未覆盖」里点一句转交。

| ✗ 不是你的意见 | ✓ 是你的意见 |
|---|---|
| 「我会把成员资格判定做成三值」 | 「S-6 说依赖不可用时拒绝，操作表里『查询成员资格』的失败集合却没有『不可用』一项，两处对不上」 |
| 「这个能力不该和那个合在一起」 | 「§目的说 X 的结算归本契约，§交接又说由 `composition.y` 收口——同一件事两个拥有者」 |
| 「租户校验应该放在入口做」 | 「『创建』的输入里租户参数写了默认值『当前租户』；身份参数一旦有默认值，越权路径就从『传错』变成『不传』」 |
| 「这个错误码太多了」 | 「失败集合以『其他错误』收尾，消费者无法穷举分支；哪些情况落进这一项没有定义」 |
| 「这里应该用 serial 派发」 | 「S-9 声明这是可否决的异步控制事件，提供者设计用 `bail` 承载；`bail` 不 await 监听者返回的 Promise，两处声明不能同时成立」 |
| 「这份契约不必建形式模型」 | 「性质表列了一条进展性质并说由 TLC 检查，`formal/README.md` 没有对应条目，`formal-tasks.json` 也没有这项任务」 |
| 「这个字段名起得不好」 | 「`scope` 在 data 契约里是组织标识，在本契约 S-4 里当权限集合用——同名不同义」 |

判据很简单：**你的意见指向规格里的具体位置和具体后果，还是指向你自己会怎么设计。**

## 输入上的两点

同一批多份契约同时受审时，需要知道这一批的完整清单——**跨契约不一致只有放在一起才看得见**。

完整性相对**已给出的设计范围**与**规格自己声称的承诺**判断，不等于覆盖所有想象得到的需求。
架构尚未选定的政策保留为未决项并说明影响，**不把个人偏好补成要求**。

## 读的顺序

1. **派发给你的简报或设计快照**——先确定这批规格该兑现什么，再去看它写了什么。
2. **设计评审报告**——先知道工具已经指出了哪些位置。
3. **共用的 data 契约**——先把共享字段的名字、取值域和含义记住，后面每份都要对照它。
4. **逐份 capability / composition 契约**——一份读完再读下一份，读完再做跨契约核对。
5. **只在某一条核对真的需要时**，展开[契约与完整动作链](../define.md)、[规格演进](../spec-evolution.md)、
   [规格与证据](../architecture/assurance/specification.md)、[契约描述](../architecture/reference/contract-description.md)；
   涉及官方原语的表述确需核对时用[来源核对](../source-check.md)。**不通读 references。**

区内规矩从 `design/spec/README.md` 与适用的 AGENTS.md 取，不从当前 shell、Git 根或承载仓库推断需求与政策。
**导航到架构材料不授予重新判断业务设计的权限。**

## 每个操作的九件事

对规格里**每一项公开操作**，逐项辨认下面九件事。工具只核「这一行在不在、是不是空的」；
**写了但不够实施**要靠你——缺一项或写得让实现者必须自己挑，就是一条可实施性发现，写成「开发者将不得不自己决定 X」。

| # | 要辨认什么 | 典型缺法 |
|---|---|---|
| 1 | **输入与授权**：调用主体、作用域、租户身份、使用时判定、非法输入。**身份类参数不得有默认值** | 写「默认当前租户 / 当前账号」——一有默认值，越权路径就从「传错」变成「不传」 |
| 2 | **前置条件**：什么状态下可以调用；不满足时是拒绝、无操作还是别的 | 只写 happy path 的前提，不写不满足时发生什么 |
| 3 | **提交点与原子性**：何时算发生；是**单次提交**还是**跨多次提交** | 写「创建并通知」，却不说通知失败时创建是否已经成立 |
| 4 | **返回与失败集合**：**逐项枚举**，不留「其他错误」「等等」 | 开放式收尾；或正文提到一种拒绝理由，失败集合里没有对应项 |
| 5 | **幂等边界**：以什么为身份判重，重放同一请求得到什么 | 只说「幂等」不说键；或给有不可撤销外部效果的操作声称幂等 |
| 6 | **事件**：是**已提交事实的通知**还是**可改变结果的控制**，以及**派发模式** | 只写「发一个事件」。派发模式缺失，消费者无法知道自己能不能否决 |
| 7 | **缺席时的默认答案**：依赖不可用、记录查不到、超时——**拒绝还是放行** | 完全不写。这是最危险的缺口：不写等于让实现挑一个，挑错的那一侧是静默越权 |
| 8 | **在途操作的归属**：依赖撤除、替换、重启时，已经在跑的那一次归谁，迟到结果怎么解释 | 只描述稳态，不描述演化 |
| 9 | **装配给 vs 协议给**：哪些是装配时确定的，哪些必须写进契约 | 把本该跨节点成立的约束留给「反正是单机装配」 |

第 9 项的判据来自 `design/foundation/cross-system-constraints/requirements.md` 的 SYS-DEPLOY：
第一版是单机交付，但边界必须清晰到**不改变领域语义就能拆成分布式**。
因此凡是拆开后就不再成立的约束，**必须写进契约**，不能以装配默契承载。

第 6 项还有一条硬结论：契约声明的是**异步控制事件**、提供者设计却用 `bail` 承载的，
**直接判失败**——`bail` 同步派发且不 await 监听者返回的 Promise，
异步判定会被静默跳过，失败形态是**放行**，不抛错也不告警。
依据在 `design/basis/cordis/async-control-not-bail.md`。

## 本工作区的硬约定

每条都能指到权威。「谁核」一列写「工具」的，以设计评审报告为准，报告缺席时由你补；写「你」的**逐条扫完**。

| 核对什么 | 权威 | 判失败的样子 | 谁核 |
|---|---|---|---|
| 条款编号 `S-n` **只在单个契约的单个版本内有效**；跨契约引用必须带坐标，如 `capability.account-identity/v1#S-3` | `design/registry/id-namespaces.json` 的 `S-` 条目 | 正文裸写「见 S-7」，而 S-7 在另一份契约里 | 工具 |
| 分析阶段的 `INV-` / `SAF-` / `LIV-` 编号**只在那次分析产物内有效，不进契约** | 同上 | 契约条款直接沿用分析产物的性质编号 | 工具 |
| 用词必须是统一语言的词条，英文用词条的**正式英文名**（不另译） | `design/ubiquitous_language/index.md`，查重从这一页开始 | 正文造了一个新概念却没有词条——**这就是发现**，不替它想名字，也不静默统一两个说法 | 你 |
| 「产品依据」标的 rev **必须等于该 topic 当前 rev** | `design/product/README.md` 的 topic 一览 | 依据写「PF-001（rev 5）」，表里当前是 rev 8 | 工具 |
| 未决项以**显式 gap** 出现，标明 owner 与闭合条件 | `design/README.md` 的「状态词怎样组合」 | 用一个**看起来合理的默认值**把未决项填掉——这是最难发现、后果最重的一类 | 你 |
| `catalog.json` 登记的 `contract_id` / `version` / `resources` / `dependencies` 与正文一致，且依赖声明消费的 clauses **在目标契约里真的存在** | `design/registry/README.md` | 依赖声明消费 S-5，目标契约只到 S-4 | 工具核条款存在；**正文说依赖了、登记里没有**的由你核 |
| `covers.json` 若已登记，须能定位到条款；`reviewed: false` 是诚实初值 | 同上 | 覆盖指向不存在的坐标；或为让报表好看把未复核标成已复核 | 工具核指得到；`reviewed` 是否诚实由你核 |
| `formal-tasks.json` 的登记与实际工件路径一致；**执行结果不在版本目录内** | 同上，及 `design/spec/README.md` | 把 TLC 输出放进 `v1/formal/` | 工具核「版本目录里有未登记的文件」；登记与工件路径是否一致由工作区的设计检查判，简报说它没跑时由你补 |
| `candidate` / `accepted` / `frozen` / `implemented` / `assembled` 不混用，后面的不倒推前面的 | `design/README.md` 的「状态词怎样组合」 | 「已冻结」被说成「实现已符合」；目录存在被当成已接受 | 你 |
| 已发布版本不可原地改写；**追加一个规范工件也要新版本** | `design/spec/README.md` | 在已冻结的版本目录里新增 `.tla` | 工作区的设计检查（不是评审报告）会判失败；你只在简报说它没跑时提一句 |

## 归属：这句话该由谁说

| 拥有者 | 拥有什么 | 不该出现在这里的 |
|---|---|---|
| data 契约 | 共享身份、值、关系的含义与结构 | 每个消费者各自复制的同义类型 |
| capability 契约 | 单项能力对消费者的操作、权限、状态与失败承诺 | 内部类层次、具体服务键、库调用 |
| composition 契约 | 无法归属单一能力的整体性质与跨能力交接 | 只为联调再抄一遍各方契约 |
| 提供者 / 装配设计 | 具体服务键、插件入口、接线 | ——语言无关的 spec 不必强行收纳它们 |

**不要求每个能力拥有全部机制**，也**不为未承诺的行为补政策、额外抽象或统一文件模板**。
把 topic 当信息包：先从入口确认范围、状态、正文与证据地图，沿实际需要展开；
**不以附属文件数量判完整**，只有 `contract.md` 不自动构成缺陷。

## 跨契约批次核对

单份读得通，一批放一起未必。同一批多份同时受审时，四项各走一遍：

1. **共用 data 契约的字段**：各份引用同一字段时，**名字、取值域、含义**是不是同一个。
2. **同一概念被定义两次**：第二处就是问题——指出哪一份是权威，另一份应改为引用。
3. **A 依赖 B 的条款，B 真的承诺了那件事吗**：翻到 B 的那一条读原文，
   **不看依赖表的措辞**——依赖表写的是 A 以为 B 承诺了什么。工具只核那一条存在，不核它说了什么。
4. **交接的两端说的是不是同一句话**：前方**何时释放**、后方**何时接纳**、
   **回执丢失谁收口**。两份各写一遍而不一致，是最常见也最贵的一类。

## 消费者视角走查

先按[契约描述](../architecture/reference/contract-description.md)的「消费者需要知道」表**逐行问一遍**：
对谁承诺什么、如何辨认和访问、谁能观察哪些事实、何时可以使用、何时算发生或结束、谁保留和释放、
什么必须保持或最终发生、改变后怎样继续、额度与时间怎样约束行为、跨边界是否仍成立、凭什么依赖保证。

再**选一条真实的动作链**走一遍：**入口 → 准入 → 提交 → 交接 → 结算**，
一直走到**最可能丢责任的拒绝或失败分支**——
例如前方已经交出工作资格，后方授权直接拒绝，而路径只有「允许」和「待批准」两种：
**谁来结算，谁来接续原工作？**

> **每个局部状态都合法，不等于整条链有合法终点。**

缺口写成这句话的形状：**在何种输入或交错下，哪个消费者无法依赖哪项承诺，由谁补齐。**
交接的落点是所属能力或组合契约，**不能靠补全 Schema 或列齐接口把最后一段行为遮过去**。

## 形式工件对应

- **条款 → 不变式 / 性质名 → 检查配置**，三段映射是否闭合？少一段就是断链。
- 有前提的进展性质，**前提是否同时写在配置与正文两处**？只写在配置里，等于正文在撒谎。
- **有限检查有没有被写成无条件证明**？TLC 在已检查范围未发现反例、
  Alloy 在给定 scope 未发现反例，都不是任意范围的证明。
- 执行配置、原始输出、反例是否在版本目录**之外**，并绑定实际输入修订？

**没选某个工具不自动是缺陷**；只有**设计已经触发的义务被遗漏**才是。
不要求所有 topic 都有 TLA+ / TLC / Alloy。这里只核对**声明与证据是否对应**，**不裁决算法证明**。

## 这一种判断的报告

发现的类别：**表达歧义 / 完整性 / 可实施性 / 引用与登记 / 跨契约一致 / 形式对应 / 归属越界**。
依据指到权威——契约坐标、词条 ID、清单文件、basis 条目；出自工具的发现注明核对项标识。
建议写成「必须补足什么」，不要发展成另一份规格。

没有阻断发现时说「**本次表达与规范范围内未发现阻断问题**」。
