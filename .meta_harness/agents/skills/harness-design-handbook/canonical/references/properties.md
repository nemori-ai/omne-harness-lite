# 核对性质、前提和动作链

只展开本次变化所需保证。每条性质记录来源、适用身份和修订、观察范围、成立时点、保护操作、前提拥有者及证据义务。检查器观察到规则不等于运行机制保护规则。

## 两次不同的检查

第一次从已列性质核对候选结构，分别判断无条件成立、有前提成立、没有保护责任或需要改变需求。依赖前提时写出提供者和前提失效后的责任。靠结构成立的性质仍须有公开承诺，不能只留在分析草图里。

生命周期关联通常只能证明撤除被发起。要求资源释放完成、有序收尾或结果结算时，需要额外责任及证据。不能把“同生共死”直接写成收尾完成。

第二次从原始要求和可观察结果重新询问下列保证，不能从第一次的性质清单派生这次输入。

- 跨拥有者事务和跨边界原子提交由谁兑现。
- 可靠投递需要哪种保证，受理和确认丢失由谁收口。
- 外部效应的未知结果、幂等、补偿、恢复或业务撤销由谁承担。
- 异步清理的顺序、失败和完成条件由谁负责。
- 权限边界在哪里执行，如何保护实际数据和外部操作。
- 跨进程身份、可见性、持久化及崩溃恢复由哪个协议提供。
- 所需背压、流控和时序保证由哪个接口承诺。

命中多项是正常责任分配，不自动触发削减需求。内核新增能力时按采用版本核对实际承载，不以本清单反向规定内核事实。

## 沿入口到稳定点

沿触发、准入、执行、提交、通知或交接、结算或恢复走实际相关分支。覆盖正常、拒绝、失败、撤除和恢复中的相关场景，不制造不存在的恢复动作。

每次交接说明发送方何时释放责任，接收方何时取得责任，拒收、迟到、重复、回执丢失和进程失败由谁继续拥有工作。

从消费者核对披露范围、内容裁剪、顺序和新鲜度。额度由谁计量，限额或超时改变准入还是结果，已发生效果如何表达。依赖、绑定或旧引用失效后，谁通知、结算或恢复。这些问法沿实际行为选择，不要求每个成员制造全套工件。

分清三种关系。只读派生和守卫要说明读取版本及一致性。同提交共写要指出共同写入或协调边界。提交后反应要说明已成立事实和后续工作之间的受理及恢复责任。跨 owner 的同一函数调用不是原子提交证据。

## 组合声明和证据

区分局部逆、撤除自身贡献、保留他方合法贡献、释放或交接完成、授权撤销、取消和业务补偿。恢复整个旧快照可能抹掉其他实例的合法贡献。外部输出不因 disposer 而可逆。

模型里的理想清理动作须对应真实 disposer、后台任务和后端的证据。保证覆盖清理失败、挂起或残留时，不能在模型中把这些行为隐藏为原子成功。

组合证明门槛由执行仓库 `docs/verification.md` 的“组合性质与证明义务”拥有。核对新增共享操作的形式证明、并发协议行为模型、依赖性质省略控制及关键保证机器检查义务；未完成的前提不能消费为已成立。

一方的前提由另一方提供时，引用其精确保证和适用证据。互相循环假定不能代替证明。受控 API、宿主权限和生产安全边界分别取得证据。

## 输出和停止

带回性质与保护责任、未由结构提供的保证、动作链、实际证据和待兑现前提。缺前提时只停依赖该保证的方案或实施。已接受目标、已完成模型和真实实现结果分别报告。
