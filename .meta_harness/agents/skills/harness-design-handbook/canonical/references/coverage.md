# 判断能力覆盖和剩余责任

从有效要求的可观察结果出发，定位现有能力、公开承诺、真实提供者及合理组合。包、目录、插件、进程和内部函数都不能直接证明独立领域责任。

## 先辨别缺的是什么

| 缺口 | 判断与处置 |
| --- | --- |
| 资料不足 | 获取实际公开定义、必要行为、采用事实或运行证据，不先造同义能力 |
| 实现不足 | 有效承诺已经足够，但提供者缺失或不符合；补齐、修复或替换实现，保持语义身份 |
| 语义不足 | 现有承诺和合理组合不能覆盖新结果；明确剩余责任及消费者，再比较能力演化 |

逐条记录要求、覆盖它的精确承诺、组合前提、实际证据和剩余责任。不能把尚未实现的协调当成已有组合能力。

## 选择演化方式

已有能力及合理组合足够时，直接消费并补必要装配。跨能力整体结果由明确协调拥有者承担，不因为消费多个接口就新增转发能力。

已有能力的同一责任需要增加保证时，比较扩展及其真实消费者影响。现有边界包含独立变化原因时，比较细分。确有不能由原责任承担的独立维度时，提出新增；说明原能力或组合为什么不能承担。身份、作用域实例或替代提供者的差异本身不构成新维度。

旧能力不再符合有效上层设计时，判断取代范围和消费者接续，不把历史接受作为继续保留的理由。具体同步和删除规则引用执行仓库工程拥有者。

## 用反向检查挑战选择

删除候选新能力后，哪项有效结果失去拥有者或哪项变化无法独立发生。如果没有这样的差异，复核它是不是重复包装。通用接口深度和取舍方法按已采用 pstack 或 Matt 使用，本页不复制其流程。

新增责任改变已有对象边界时，复查原不变量。需求正当而边界不成立，先修边界再标价，保留原需求性质。不得先把错误边界的代价交给需求方，让其在不了解用户后果时削减要求。

回询代价前至少比较一个具体不同分解；提供者机制受限时比较不同提供者设计。回询给出当前结构与可计数代价、具体替代表述及代价、用户能做和不能做的差别、建议及有权裁决者。没有更便宜的有效替代就不以“太复杂”回询。硬约束之间冲突须交有权者，不自行选择方便一项。

## 输出和停止

带回覆盖记录、所选或并列候选、被改变的身份与责任、消费者影响、需要的决定及反例。必要政策未定时保留候选，不继续依赖它的正式实施。能力判断完成后，性质和实际承载仍按本次缺口分别核对。
