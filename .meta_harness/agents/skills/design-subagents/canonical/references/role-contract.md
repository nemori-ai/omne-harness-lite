## 职责不是人设

“资深架构师”“严谨工程师”不能说明应当做什么。角色定义要能回答：谁交给它什么
问题，它产出什么结果，这个结果交给谁，什么意味着本次职责完成。

区分三种权限：**建议权**（提出选择）、**执行权**（在边界内产生改变）、
**接受权**（决定候选成为有效承诺）。能写提案不表示能接受提案；能找出缺陷
不表示能修复；能调用工具不表示当前任务允许这个动作。

共享角色正文保留稳定职责、关键禁止事项、澄清与完成规则。任务说明提供本次路径、
版本、具体目标与授权。项目 AGENTS.md / CLAUDE.md 继续拥有项目约定，不复制成
角色内部的第二份规则。若任务无法满足固定角色边界，交回派发者调整任务或角色，
不在执行中自行改写自己的角色。

## 行动边界

描述允许的具体动作和产物，比“谨慎行事”更可判断。例如：可读取实现核对可行性，
可写候选设计，不能修改产品源码、验收结果或已接受决定。

需要精确约束时，任务说明包含仓库、worktree、基线版本以及允许创建/修改/删除的
路径；区分读范围和写范围。“可以写文件”不能默认包含删除、重命名或修改生成器。
对外发送、提交/合并/推送、依赖安装、部署、继续委派分别说明是否属于职责。
明确已有授权，避免每次使用已许可能力重复询问。

边界要覆盖所有可达通道：禁止 Edit 修改源码但开放 Bash，并不形成机器强制的
源码写保护。需要强制隔离时，核对宿主的真实沙箱和权限机制；无法兑现的限制
保留为指令约束并如实报告，不伪造不存在的 `allowedPaths` 一类字段。

精确路径只是本次授权的表达，不应把临时 worktree 绝对路径永久硬编码在可复用角色
中。恢复任务时重新核对实际工作目录，路径失效不能自动回退到主检出。

## 必要输入与停止

明确输入的内容、来源和接受状态；不是只检查“有一份文档”。实施规格应说明要兑现
的行为和验收，实施计划应说明本任务采用的交付安排与边界。链接失效、只给候选、
版本冲突、缺少决策者都可能让输入尚未就绪。

角色至少区分这些退出情形：

| 情形 | 应有行为 |
|---|---|
| 职责完成 | 返回约定成果、证据与仍需下游处理的事项，结束本次工作 |
| 目标/行动边界歧义 | 暂停依赖该解释的动作，提出最小澄清问题 |
| 必需材料缺失 | 先在授权来源查找；仍缺失则指出准确缺口，不补造后实施 |
| 前提被反例推翻或权威冲突 | 标注受影响结论，停止使用失效前提，提交证据 |
| 工具、权限或环境不足 | 报告缺失能力与未完成范围，不假成功或换成越界手段 |
| 真实预算/时限耗尽 | 保存可交接进度，报告部分完成；不把耗尽算成功 |

这些是结果语义，可用自然语言表达；只有消费者确需解析时才固定为枚举或 Schema。
若角色不能向用户提问，指定通过父 agent / 派发者返回澄清。沟通工具不可用时，
在返回消息中留下问题；不能把“无法询问”解释成可以自行决定。

## 不同角色的差异

| 角色 | 必须说清的边界 | 典型停止点 |
|---|---|---|
| 架构设计 | 产出候选和语义说明；自洽检查属于设计，不承担独立评审与批准 | 需求或政策歧义改变核心语义；设计职责完成后交接 |
| 实施 | 按已给定实施规格与计划修改授权路径并验证 | 必需规格/计划缺失或相互矛盾；需要超出写范围 |
| 独立评审 | 对给定对象和范围形成有证据的判断；修复权另授 | 缺少待评对象/基线；评审证据足够后结束 |
| 只读调查 | 回答给定事实问题，区分事实与推断 | 证据不可得；答案已充分且无需继续扫描 |

这是角色区分示例，不创建这些角色，也不要求一项任务派发全部角色。不要把同一
system prompt 写成“负责设计、实施、审查和批准一切”的全能 agent。
