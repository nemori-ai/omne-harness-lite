# 开发者派发说明

向选定开发者提供以下内容；可以引用已有材料，不必新建文档。派发者先按
[共同契约](developer-contract.md)核对输入是否完整。

| 项目 | 本次需要填写的内容 |
|---|---|
| 身份与位置 | 任务 ID、角色、能力纵线与本次交付物、设计工作区与执行仓库/worktree 绝对路径、分支、基线提交 |
| 模型与推理强度 | developer 的模型按本次任务的性质选（选法见 [README 的「模型配置与本次派发」](README.md#模型配置与本次派发)）；Codex 一端的角色文件不钉模型，**必须显式给**。其他角色用角色配置的模型。档位按实际任务规模和复杂度选 medium/high/xhigh，未调整时使用角色默认；顶档模型上 xhigh 只用于 hardest 任务，取值以 `render_pair.py --resolve` 的结果为准（见 README「模型配置与本次派发」）；通过宿主设置应用并核对实际结果 |
| 目标边界 | 要交付什么、不在范围内什么；允许读取以及创建/修改/删除的具体路径，含临时与生成输出；执行仓库有结构度量入口时，它的命令与产物位置；写范围按执行仓库[`docs/engineering/workflow.md` D1](../../../docs/engineering/workflow.md#d1-写范围由调用方与消费方推出)推出；闭包规格的补充节见 `delegate` 的 `references/closure-spec.md` |
| 验收清单 | 每项标准的 ID 或稳定引用、可观察结果、通过条件、证据要求；适用任务卡须给真实Issue身份、交付修订、本次结果及长期依据；可执行验收须给路径、运行命令与任务基线，对实施者只读，交回时由派发者核对未被改动；本次按哪一级接受（L0～L3，见 执行仓库 docs/engineering/quality.md），以及来源 trailer 里 `Harness`、`Agent-Role` 该写的值 |
| 实施规格 | 设计工作区的明确位置；本次采用的公开接口、行为契约和接受依据；对应公开入口、Schema及模型的修订/快照，公开面、依赖接口版本、不可破坏的条款及关键交接责任。无独立契约时给已接受协议/技术设计，不虚构坐标 |
| 性质及证据义务 | 目标/需求导出的不变量及安全/进展约束、保护位置、前提责任与证据引用；本次要生产或消费哪些结果，尚未闭合的必要义务阻止什么 |
| 施工计划 | 给定的实施顺序、前置依赖、交付节点、验证安排、本角色与其他任务的分界；延期映射的负责产物、受影响消费者及闭合时点 |
| 自主范围与动作授权 | 哪些技术栈、算法和复用库已有采用决定，哪些允许自行调研或随任务交付方案；来源/版本/许可/适配证据要求；依赖安装、锁文件、本地提交、真实外部操作的已有授权及写入 owner |
| 工作树与协调 | 每个实施者的隔离工作树、分支与独立写权；共享接口负责人、消费/交付的接口版本与结果、真正阻塞的前置条件、计划允许的替身、发生冲突时的联系人；涉及组合时明确组合交付负责人及真实组合验证的范围与时点 |
| 方法与知识入口 | handbook 实际入口、相关 family/topic 包及本次采用规则；工作区与执行仓库各自的事实/操作来源，不默认继承父仓库 |
| 当前认知 | 已确认事实、已接受决定、假设、未知、尚未答复的问题 |
| 返回与恢复 | 派发者/接收者、澄清通道、成果和证据位置、交接状态位置、实际时限（如有）；有结构度量入口时，交付说明须附的摘要与产物路径；有差分变异入口时，它的命令（只报告，交付说明附存活与无覆盖的变异体） |

角色名不授予任何目录的所有权，也不自动提供输入材料：实现统一派 developer，能写哪里只由本次的目标边界决定。
按能力纵线与交付物划定任务。独立任务可以在隔离工作树并行，耦合任务按依赖串行。
真实检出、宿主 cwd、共享写权和清理保护沿执行仓库 `docs/engineering/workflow.md` 核对。
共享 Schema、公开入口、锁文件、应用装配等文件指定一名写入负责人，其他任务提交
修改需求。能力状态转换和跨能力产品规则交给对应能力/组合任务；应用装配与验证
不能补造未实现的规则。角色不规定五阶段流水线，也不要求每条纵线使用所有角色；
契约确定后，消费方、后端和交互可依计划分别实施，兄弟任务未全部完成不等于被阻塞。

派发者指定组合交付负责人并安排实际集成；负责人核对参与版本及交接结果，完成
其授权范围内的组合验证。该责任不扩大写权限，也不授予继续委派、Git 合并或最终
接受权。不能把各分支分别通过或替身通过当成真实组合通过。

首次消息应先要求进入指定 worktree 并核对分支。材料缺项时开发者先查给定来源，
仍缺失则向派发者返回最小澄清；派发者补齐后再启动依赖实施。用户无需替每个 worker
回答同一个问题，派发者负责归并和仲裁升级。

采用 `.meta_harness` 时给出本次维护依据及实际承诺路径：公开类型、行为契约、必要ADR与验证资源；不只给产品 topic、包名或笼统要求。派发者已读不代表子会话已收到。任务要求实施者实际
读取与核对相关正文，并在交付中对应关键条款、映射和证据。技术栈/第三方库没有
既定决定不算规格缺失，可由开发者调研或由派发者带方案；不能以此替代领域语义、
放宽验收或重新选择已接受边界。

多层集成已采用时，派发补充真实 Issue identity/revision/attempt、route/completionTarget、不可变 taskBase、写范围与真实 dispatch 定位；共享候选交接另带 operation、B/S/C、每卡审计范围和回执。pending 不伪造这些事实。共享 ref 写权与最终接受权分别明确。
