# 清理任务派发说明

专项清理是**把一个超了预算的成员拉回解除线以下**的任务：不加行为、不改契约、不动别人。
它由回路状态入口生成草稿，**负责人批准之后**才派给 developer；没批准的草稿不是任务。

实施者平时只在自己正在改的文件里顺手清理（见[共同契约](developer-contract.md)）；超出那个范围的，都走这里。

## 什么时候不派

- **草稿没有被负责人批准。**主会话可以提议，不能替负责人批。
- **回路把这个成员标成了「结构问题」**——清理过又反复变红。再清一遍只会再红一遍：
  这是拆分或方向的问题，报给负责人，由负责人或主会话重看这个成员的边界，不派清理。
- **这个成员正有别的任务在写。**同一个成员同一时刻只有一名写入者；等那边并入主线再派。
- **超的那一项是「重复」，而重复的另一端在别的成员里。**跨成员的重复要先定这段逻辑归谁，那是设计问题，不是清理。

## 派发时给什么

在[开发者派发说明](developer-task.md)的各项之外，清理任务固定给这六节，章节名与回路生成的草稿一致，
草稿里已经填好的照抄，不重写：

| 章节 | 写什么 |
|---|---|
| **目标成员** | 一个成员的路径；度量所在的提交，它也是这次任务的基线 |
| **要清理的条目** | 逐条带 `路径:行`：超线的函数与它的读数、重复片段的两端、没有断言的测试。**只做列出来的这些**；清理中发现的别的问题记下来报回，不顺手扩大 |
| **行为锁** | 这个成员现有的测试与验收**只读**。清理前先跑一遍受影响范围的测试并留输出，清理后再跑一遍，两次都全过；哪条测试挡住了清理，停下来报，不改测试 |
| **解除条件** | 每一项超预算的指标回到解除线以下，逐项写当前值与解除线。做不到的如实写做到了哪、卡在哪，不为了达标把函数机械地切碎 |
| **不许动的** | 公开入口（`package.json` 的 `exports` 与从入口导出的名字和类型）、别的成员、验收目录、契约与规格、锁文件。要动其中任何一样才能清理下去，就停下来报 |
| **状态** | 谁在什么时候批准的；按哪一级接受（清理通常是 L1，碰到身份、凭据或要求同一提交的状态时上调） |

## 交回时看什么

- 行为锁前后两次测试的输出，都是全过。
- 回路状态入口在交付的提交上重跑的输出：目标成员的各项回到了解除线以下，或如实写明没回到的那几项。
- 变更文件都在目标成员之内；公开入口的导出清单与清理前逐项相同。
- 提交小步、每个只做一种清理（提取、改名、去重各自分开），带来源 trailer。

清理不改变行为，所以**不需要新的验收，也不升任何规格的版本**；如果清理到一半发现非改行为不可，那已经不是清理，停下来报。
