# 研发角色源包

本目录维护起草者（产品设计、规格、实现映射）、独立评审（设计、实现）、开发者、独立验收与 TUI 取证角色的共享正文及两端配置；有哪些以下表为准。
**架构读数与能力拆分提案没有起草角色**：它们由主线或负责人亲自写，agent 只评审与反驳（见[下文](#架构规格与实现映射的起草)）。
实际设计事实来自明确工作区的 design/ 或本次输入，实施位置由任务指定；
不从承载仓库或角色名称推断产品、包结构、能力清单与政策。

| 角色 | 当前职责 | 正文 |
|---|---|---|
| product-design-drafter | 把一个产品需求做成完整、可被评审的产品设计；配备联网**产品调研**能力，学同类产品的边界与取舍，不做技术调研；固定 xhigh | [产品设计起草](product-design-drafter/role.md) |
| product-design-reviewer | 评审起草交付的文档本身：逻辑、完整性、明显漏洞，叠加一层可实施性；**不评判品味与方向**；只读，固定 xhigh | [产品设计评审](product-design-reviewer/role.md) |
| spec-drafter | 按施工简报写一份候选契约包（九件事、Schema、examples、verification、触发的形式工件）并登记 registry；或对整批草稿做独立评审前的对齐；不选政策、不写机制；默认 xhigh，可调 | [规格起草](spec-drafter/role.md) |
| realization-drafter | 按节点划分写一个 provider／assembly 节点四件套；跨 owner「同一提交」必须点名共同存储对象，绑定只绑会失败的证据，正文不指认任务区；不改契约；默认 xhigh，可调 | [实现映射起草](realization-drafter/role.md) |
| design-reviewer | 设计材料的独立只读评审，**一次派发只做一种判断**：选择（读数、能力边界、契约批次的语义整体、realization 节点）、表达（规格文本）或计划（施工计划）；只读本次那一页判据，不混报、不修复、不接受；固定 xhigh | [设计评审](design-reviewer/role.md) |
| implementation-reviewer | 一次实现类交付的独立评审，**只在接受级别 L2／L3 或读数里有未交代的红项时派**；先跑执行仓库声明的检查，再按检查表问；每条发现带工具输出或具体反例，不收品味意见；不改受版本管理的文件、不接受；默认 high | [实现评审](implementation-reviewer/role.md) |
| developer | 按规格与施工计划实现一个限定的切片：内核原语、能力与组合的行为、具体提供者，或应用装配与流程；**写入范围由任务给，不由角色名给**；模型与档位按本次任务选，默认 high | [开发](developer/role.md) |
| verification-developer | 实现跨边界场景、故障注入、测量及形式工具适配；默认 high | [验证开发](verification-developer/role.md) |
| tui-developer | 按已接受契约实现终端交互与呈现、终端生命周期和输出边界；负责修复与自身回归，不代替独立取证或验收；默认 high | [TUI 开发](tui-developer/role.md) |
| tui-debugger | 对终端界面（TUI）应用的异常现象做**取证**：可重跑的复现、分层证据、假设账本、修复建议，先排除终端特有的嫌疑变量；**不修、不判「修好」**，只写证据目录；默认 high | [TUI 取证](tui-debugger/role.md) |
| qa | 对一个可运行的交付增量（命令行、终端界面、服务或包的公开入口）按给定验收标准在真实装配上做**独立验收**：四态判决、机器证据、逐条对照、缺陷清单；交付面是终端界面时另过终端矩阵、宽字符、resize、退出还原几关；**不修、不接受**，只写场景目录与证据目录；默认 high | [独立验收](qa/role.md) |

角色正文拥有职责与边界，`codex.toml`、`claude.yaml` 和可选模型适配段拥有宿主差异。
共享正文由各角色 `assembly.toml` 的 `shared_prompts` 按序内联：开发者（developer、verification-developer、tui-developer）在品味之后内联[共同契约](developer-contract.md)，
固定提示已经包含必要输入、行动授权和停止条件；[派发模板](developer-task.md)提供本次事实，不进入固定提示。
两个技术起草角色（spec-drafter、realization-drafter）在品味之后内联[起草者的共同纪律](drafter-contract.md)；
implementation-reviewer 在品味之后内联[实现评审检查表](implementation-review-checklist.md)——那份文件是这些问法唯一的正文。
design-reviewer 的判据不内联：三种判断各一页，在手册的 `references/review/` 下，评审时只读本次那一页。
生成说明见[工具入口](../../tooling/README.md)，生成物归工作区内
`.codex/agents/` 与 `.claude/agents/`；这些目录由工具生成，未生成时不作为文档链接目标。

## 共享研发品味

[研发品味](engineering-taste.md)是全部设计与研发角色共用的**唯一**品味正文：
技术 drafter、设计与实现评审、开发者、独立验收与 TUI 取证角色都把它列为 `shared_prompts` 的第一项，
拼接顺序为 `role.md` → 研发品味 →（按角色）共同契约、共同纪律或检查表 → 模型适配段。
它的导语写明只在各角色自身的职责、判断对象与授权之内生效：评审与验收角色不把品味当独立发现来源或验收判据。

**两个产品设计角色刻意不挂**：它们站在 product manager 视角、明令不做技术判断，
product-design-reviewer 还明写不评判设计品味；工程品味会把它们往技术设计上拉。
`tooling/tests/test_role_sources.py` 守住这条：新角色忘了挂、或产品角色误挂，`make test` 都会失败。

改品味只改这一个文件，然后按工具入口重编生成物并运行 `make agents-check`；
已开着的 Claude Code 会话在启动时就固化了角色定义，要开新会话才会用上新正文。
根 `AGENTS.md` 的同名一节只是给主会话的简短投影，原则级变化时再同步它。

## 产品设计的起草与评审

这一对角色服务于**产品设计**，与下面的设计评审服务的对象不同——
设计评审判断的是**技术材料**，这一对判断的是**产品文档**。

派发起草者时给出：需求的原始表述、可写的 topic 路径、设计工作区位置，
以及要建立关系的已有 topic。它开始之前必须能回答「解决谁的什么问题、
不做会怎样、边界到哪」，答不上来会停下来问——**这是有意的，不要替它编一个答案**。

**起草者的联网能力用于产品调研，不是技术调研。**它去看同类产品怎么划边界、
刻意不做什么、遇到同样的冲突怎么解；学的是取舍与品味，不是功能清单。
调研所得**不进拍板记录**，只能作为 PM 推导的参照，且必须说明为什么适用于本产品。

**评审者不评判品味。**方向与取舍由产品负责人裁决；起草者的判断即使不够漂亮，
只要自洽、完整、没有漏洞就不是问题。它找的是四类东西：逻辑矛盾、完整性缺口、
具体场景下的漏洞，以及（薄薄一层）这些定义能不能被无歧义地实施。
它若产生品味意见，会单列并标明不作为评审发现——**不要把那一段当成待办**。

两者可以串联使用：起草 → 评审 → 起草者按发现修订 → 必要时复评。
**评审不产生接受**；接受是产品负责人的动作。

## 架构、规格与实现映射的起草

**架构归人。**领域读数、机制读数与能力拆分提案由主线或负责人亲自写，不设起草角色：
这三样是「系统该怎么切」的判断本身，交给 agent 起草，人拿到的就只剩一份要逐字核对的长文。
agent 在这里的位置是评审与反驳——派 design-reviewer 判「选择」，它对读数找遗漏的性质与混进来的机制视角，
对提案写出落选方最强的论证。亲写的人按手册的纪律**先写完领域读数并封存（落盘、提交），再开始机制读数**，
产物开头写明封存在哪个提交。

规格与实现映射仍有 drafter，服务于 `harness-design-handbook` 主线里**能独立成稿的那几段**；哪几段归主线、哪几段派角色，
权威表在手册的[工作区上下文](../skills/harness-design-handbook/canonical/references/workspace-context.md#实现设计与交付)，
这里只写派发时要给什么。两者都不做对账、不选产品政策、不接受，也都不派评审。

**这两个角色不合并**（2026-10-01 定）：一个写「契约承诺什么性质」，一个写「用 Cordis 怎么兑现」，这条分界正是领域建模独立于 Cordis 的落点；
合成一个，写契约时脑子里已经有 fiber 和 service，机制会渗进契约。它们共同的那部分——开工前核对、报回不自行改判、缺口显式、
收尾与交回——抽成[起草者的共同纪律](drafter-contract.md)一份，两边内联。
realization-drafter 另有一项必交产出：节点 `design.md` 里的 **Cordis 符合性核对表**（模板在 `design/realization/.templates/node/`）。
「架构整洁、实现敏捷」不写成起草者的自我要求：产物交回后由设计评审报告与独立评审来量。

| 角色 | 派发时给齐 | 一次派发做什么 |
|---|---|---|
| spec-drafter | 施工简报（含失败值与服务名账本）、对账产物、已定型的共用 data 契约坐标、模板与 registry 口径、形式工具路径 | 一份契约包 + 登记；或草稿到齐后的**整批对齐**（只派一位） |
| realization-drafter | 节点名与 `<group>/<node>` 路径、契约坐标、节点划分与共同约定（Cordis 版本、存储抽象、配置错误收场）、装配草图或提案、basis | 一个节点四件套；assembly 节点另给本批 provider 的「归装配」事项 |

主线亲自写的设计**一律**派 design-reviewer 判「选择」；写的人对自己的置信度自评不代替评审。
基座级选择（拆分、共用契约的形状）用三票独立投票，投票实例用评审角色而不是 drafter。

## 按判断对象选择 reviewer

设计材料只有一个评审角色 design-reviewer，**一次派发只做一种判断，简报里写明是哪一种**。
三种判断原来是三个角色（architecture-、spec-、plan-reviewer），2026-10-01 合成一个：它们共用同一套只读纪律与报告格式，
差别只在判据，判据各一页放在手册里按需读。**不因为合成了一个角色就一次要它做两种**——两类意见混在一份报告里会互相淹没，
要两种判断就派两次。合并前后的对照见[评估记录](../evaluation/design-reviewer-merge-2026-10-01/README.md)。

| 简报里写的判断 | 它回答的问题 | 判据页（相对手册 skill 的根） | 特有输入与返回边界 |
|---|---|---|---|
| **选择** | 现有能力能否承载；剩余责任是否支撑新维度；每条性质有没有保护点；插件与组合能否兑现 | `references/review/choice.md` | 需求确认范围、能力基或其缺口、设计快照；审契约批次时附设计评审报告的依赖图一节。返回语义反例和所需决定或证据，不代写替代设计 |
| **表达** | 既定选择是否被完整、明确、规范地写出来 | `references/review/expression.md` | 规格快照及其落实的设计，**加一份设计评审报告的输出**。返回表达、引用、版本、证据声明的缺口，不重新判断是否应新增能力 |
| **计划** | 依赖这些设计，实施能否安全推进并形成证据 | `references/review/plan.md` | 计划、验收、采用的设计与规格、必要现状。返回受阻任务、写入冲突、证据和组合责任缺口，不逐条重审规格 |

**派发前先跑设计评审报告**（`make design-review CONTRACT="<坐标>"`，只读、只报告）并把输出原样附进简报：
机械核对——条款引用、登记、rev、九件事表格是否缺行——由工具算，评审者逐条判断成立与否，不用眼睛重做。
评审角色自己不运行任何工具：「不能写、不能执行」是它的安全性质，Claude Code 一端不给 shell，Codex 一端是只读沙箱。

先给出明确设计工作区、待审对象与可恢复修订、目标/约束、采用依据及范围；比较修订时再附比较基线。
候选可以受审，设计缺陷本身不是开始评审的前置缺项。不要假设评审者继承了主会话的背景、已读 skill 或当前执行仓库。
不要求每项局部修改依次经过三种判断。product-design-reviewer 同样只读，但判断对象是产品文档，不走这三页。

TLC/Alloy 工件按需选择，不因缺某工具文件就判错，也不以 optional 取消已触发的义务。
目录、审阅或工具通过不产生接受、发布或实际验证状态。返回意见带对象/版本、范围、位置、依据、触发后果及缺口，
分阻断、非阻断、范围外待裁决与未覆盖四组；报告通过返回消息交付，由派发者按已有授权保存。

## 实现评审与独立验收

这两个角色看的是**实现类交付**，默认不派：每个交付单元都派一遍会把迭代拖长。什么级别派谁，权威在手册的
[按风险选择接受实现的看法](../skills/harness-design-handbook/canonical/references/handoff.md#按风险选择接受实现的看法)。

| 角色 | 问的问题 | 怎么取证 | 可写 |
|---|---|---|---|
| implementation-reviewer | 这次变更有没有越出写入范围、动了验收、破了依赖方向、留下没交代的结构问题、违背它声称兑现的契约 | **先跑工具**（变更清单、仓库规则检查、结构度量、受影响范围的测试与失败归因），再按[检查表](implementation-review-checklist.md)问；每条发现带工具输出或具体反例 | 不改任何受版本管理的文件 |
| qa | 交付的东西按验收标准**到底过没过** | 在干净检出的真实装配上跑验收场景，四态判决加机器证据 | 只写验收场景目录与证据目录 |

**派发 implementation-reviewer 时给齐**：执行仓库与检出、任务基线提交与交付提交、接受级别、任务简报里的写入范围与验收清单、
实施规格、实施者的交付说明（它会当作待验证的主张），以及执行仓库声明各检查入口的文档位置。
它不评命名与风格；只有品味、没有证据的话它会放进末尾的「观察」，**那一节不是待办**。

**派发 qa 时给齐**：交付增量的坐标、验收标准（产品验收条目、契约条款坐标或计划里的清单）、
启动方式与环境、干净检出与两个可写目录、可用的验证设施、预算。
**不转发实现者的完成声明**；验收实例不得是实现者，也不得是写了被验代码的任何实例。
流程：QA 实例 A 在实现前或并行写验收场景 → 实现者交付 → 干净上下文的 QA 实例 B 在干净检出上跑
→ Fail 交 developer（终端面的现象交 tui-debugger）→ 修复后新实例复验（只跑 Fail 项加冒烟）→ Pass 由派发者或产品负责人接受。
qa 原来叫 tui-qa，只服务终端界面；2026-10-01 泛化成通用角色，终端那几关改为「交付面是终端界面时才过」，
依据与验证范围见[评估记录](../evaluation/implementation-review-and-qa-2026-10-01/README.md)。

**两端都没有按路径的写保护**：「不改源码」「只写这两个目录」在 Claude Code 与 Codex 里都是指令约束，
派发者收工时用 `git status` 核写入范围，越界即本次结果无效。这两个角色的 `permissionMode` 是 `default`
而不是 design-reviewer 的 `dontAsk`，因为它们要运行检查、被测程序与外部进程；Codex 侧是 `workspace-write`。

## TUI 开发与取证

tui-developer 消费应用契约并实现终端交互；派发时给齐共同开发输入及目标终端矩阵、输出契约和真实组合边界。
终端界面的验收由通用的 qa 做（见上一节），它在交付面是终端界面时另过终端那几关。

tui-debugger 服务于**终端界面（TUI）应用**的运行现象，与评审判文档、developer 改代码都不同：
它**运行被测程序、往指定目录写证据**，但**不改产品源码、不接受结果**。
设计依据与调研在 [`design/record/proposals/cli-tui`](../../design/record/proposals/cli-tui/README.md)
与 [`research/agent-debugger-subagents`](../../research/agent-debugger-subagents/README.md)。

| 角色 | 问的问题 | 可写 | 交给谁 |
|---|---|---|---|
| developer、tui-developer | 怎么把它做出来 | 产品源码、计划划定的测试 | 派发者 |
| verification-developer | 验证**设施**怎么建（无头终端驱动、替身后端、故障注入、证据 hook） | `tools/`、测试基础设施 | 派发者 |
| tui-debugger | 这个异常**怎么发生的** | 只写证据目录；埋点只在显式给定的隔离工作树里且收工前撤净 | 派发者 → developer |
| qa | 交付的东西按标准**到底过没过** | 只写验收场景目录与证据目录 | 派发者／产品负责人接受 |

**派发 tui-debugger 时给齐**：带观察者的现象陈述、构建坐标、启动方式与环境、正确性判据（oracle）、
证据目录、预算（默认三条假设或三次复现失败即停）。**说不清 oracle 就先派一次「提议 oracle」**，认可后再派取证。
候选原因多于一个且互不重叠时，**一实例一假设**、各自独立的证据子目录，最后比对账本。
因果链闭合后，把 `verdict.md` 与 `repro.sh` 直接作为 developer 任务的实施规格与验收判据；
修复后**由派发者重跑复现脚本**判「修好」，不由 debugger 判。

它与 qa 一样只受指令约束、没有按路径的写保护，派发者收工时用 `git status` 核写入范围。
**桌面应用的取证不在这个角色里。**TUI 与桌面应用的取证面（伪终端与写日志 vs 调试协议与无障碍树）、
口味与最佳实践都不同，硬写成一个角色两边都会稀释；桌面应用有了交付面 PF 之后另立取证角色。

## 开发责任与并行

开发任务按能力纵线、产物及允许写入范围划分，不按角色反推模块——实现只有一个 developer 角色，
代码是集体所有的，这次能写哪里只看任务给的范围。
使用 Cordis、拥有 runtime 或被复用不自动归内核；能力拥有行为与产品规则，提供者兑现
实际资源结果，应用负责接线/交互，验证设施不补造尚未实现的能力。
这四类工作各自「不由你补」的东西写在 [developer 的正文](developer/role.md)里，派发时不必复述。

完整目标边界、验收清单、实施规格与施工计划是开发者必需输入，可以直接引用现有材料。
就绪按本任务的语义、提供者、装配与证据分别判断，内部算法和组织在既定契约内自主选择；
不能把尚未决定的公共语义交给 worker 猜测，也不为四项输入复制四套长期文档。

实现的写入默认一次一个可交付单元、同一成员同一时刻一名写入者，做完并入主线再开下一个；
只有写的是互不相交的成员、且不共用尚未定型的接口时才并行写入。评审、研究与验收是只读的，随时可以并行；
不强制按角色排流水线。
每份共享接口/Schema/锁文件/装配资产指定写入负责人，需要组合时指定真实组合交付负责人。
替身和分支单测只支持其范围；组合责任不附带他人的写权、继续委派、Git 合并或接受权。

## 模型配置与本次派发

模型与档位的权威在各角色的 `codex.toml`、`claude.yaml` 与开发者的 `assembly.toml`；
reviewer 与 product-design-drafter 固定档位；开发者、TUI 角色与技术 drafter 默认档位见上表，可按任务选 medium/high/xhigh。
这些钉值来自有日期的支持记录，不是对当前账户或新版本宿主的重新核验。

**developer 的模型按本次任务选**，不由角色固定。选法写在它的 description 里，依据是[角色合一记录](../evaluation/role-merge-2026-10-01.md)：

| 任务 | Claude Code | Codex | 档位 |
|---|---|---|---|
| 能力与组合的行为、具体提供者（默认） | Opus 5.5 | GPT-6.1 Sol | high |
| 单个模块、规格完整的应用切片 | Sonnet 5.5 | GPT-6.1 Sol | high |
| 内核原语与生命周期机制 | Fable 5.1 | GPT-6 Astra | xhigh |
| 安全敏感、跨多个包或整个装配、契约把失败／诊断／顺序留给判断 | Fable 5.1 | GPT-6 Astra | high 起 |

两端换模型的机制不同：Claude Code 的角色文件钉了默认模型，派发时用 Agent 工具的 `model` 参数覆盖；
Codex 里**角色文件钉的模型优先于派发值**，所以 developer 的 `codex.toml` 不钉模型，**Codex 派发必须显式给模型**，
不给就继承父会话的模型。

开发者派发参数从源配置取得。在本工作区根、使用具备 Python 3.12+ 和 PyYAML 的解释器：

```sh
python agents/skills/design-subagents/canonical/scripts/render_pair.py \
  --source agents/roles/developer --dispatch codex --effort high
python agents/skills/design-subagents/canonical/scripts/render_pair.py \
  --source agents/roles/developer --dispatch claude --effort high
```

命令仅打印 JSON。Codex 派发需要显式应用返回的 effort，developer 的输出里 `model` 为空，由派发者按上表填；直接调用角色不保证采用源默认档位。
Claude 会话覆盖需应用完整角色 JSON，不以单个 effort 字段代替整份定义；实际调用面和支持范围
沿 `design-subagents` skill 核对。固定 reviewer 不接受此调档入口。

原生文件存在不说明当前会话已加载。具名角色不可用时，可在已有授权内交接完整生成提示作普通
agent 试用，并说明未经应用的原生沙箱与权限不能算生效；无可用独立评审能力时保留具体缺口。
