# 研发品味与项目规则入口

本提示接在「开工时对齐项目框架」之后。框架负责按需阅读项目目标、架构、领域和工程入口。本提示只接工程判断，不另存那些正文。它只在角色职责、判断对象、写权限和任务授权内生效。
评审和验收仍按各自判据取证。只有规则对应具体后果时才形成发现，品味观察不替代验收判据。
领域性质与责任先于机制选择，复用或新增依赖仍须符合任务授权。

通用工程判断按[技能采用入口](../../../docs/engineering/skills.md)加载已采用的 pstack 方法及 Matt 补充。
按任务选择方法，不把整套流程强加每次交付。项目独有的能力、性质与 Cordis 符合性判断沿 harness-design-handbook 展开。

## 维度分解与正交

每个设计问题落在一条轴上，每条轴只有一个拥有者。回答之前，先找到问题所在的轴。
正交指在一条轴上移动，不迫使另一条轴改变位置。对 A 轴问题的回答若同时定下了 B 轴上的事，这个回答就耦合了架构分开的两样东西。即使它说得通，它也是错的。

问题提出时通常不带轴名，而是带一个机制、症状或里程碑，例如「没有 sandbox 时，文件范围怎么定？」。问题里出现的那个词多半不是问题所在的轴。

### 单个问题怎么走

1. 剥掉表面。问这里真正在变的量是什么，什么必须保持不变。上例中，「没有 sandbox」只改变宿主提供者能满足哪些隔离断言。agent 能读哪里、能在哪里运行，不随它改变。
2. 命名轴。逐项问：谁在做（身份、租户），允不允许（授权、策略），在哪里运行（落点、执行环境），哪份工作要持续（会话、工作），谁执行、活多久（运行时寿命），怎样被看见（观察），怎样接线（装配）。[三条分解轴](../../../docs/architecture/structure.md#三条分解轴)是这一步用在整个系统上的结果。
3. 找到这条轴的拥有者，先读它的现行正文。多数待决事项在这一步消失，因为拥有者已经回答了它。
4. 查耦合。检查答案有没有让一条轴决定另一条轴。常见形式有四种：隔离提供者决定授权范围；一个实例的寿命决定观察挂在哪里；调用方的寿命决定被调用工作的寿命；提交协议的一个细节反过来决定事实归谁。
5. 到这一步才给剩下的事项分类。某条轴上没有拥有者的缺口是新设计。同一条轴上两个都自洽的答案交有权者裁决。其余事项是实现已经设计好的东西。

### 跨领域的设计怎么分解

一个设计横跨几个领域是常态，不违反正交。正交要求把设计拆成若干份，每一份落在一条轴上并有一个拥有者。合起来才成立的部分单独拿出来，交给一个具名承担者。

1. 列出设计触碰的全部事实与决定。列事实，不列模块，例如「谁能读这个文件」「这次调用活多久」「人看到的内容从哪里来」。
2. 为每条事实命名轴并找到拥有者。一条事实只有一个拥有者。找不到拥有者的事实先记下来，不塞给相邻领域。
3. 每个拥有者只用自己的词说明自己提供什么、需要什么。被集成方不认识集成方，规则见[领域语义依赖与模型边界](../../../docs/architecture/layers-and-dependencies.md#领域语义依赖与模型边界)。需求方可以为自己的需求声明端口，由其他领域实现。声明端口不让实现方认识需求方。例如 Session 在会话日志上实现 Agent 的 Journal 端口：Agent 定义条目的含义与形状，Session 定义日志位置、提交方式和准入的条目种类，存储定义怎样持久化。一份日志有三个拥有者。
4. 把集成本身当作有拥有者的对象。集成方认识所有参与方。它是协调者、适配器或装配，不是任何一方的内部。[组合保证由谁承担](../../../docs/architecture/structure.md#组合保证由谁承担)与[关键接缝与组合承担者](../../../docs/domains/boundaries.md#关键接缝与组合承担者)记录这一层。
5. 在接缝上写合成保证：谁参加，成立条件是什么，失败归谁。几个局部成功不等于整体成立。
6. 做三个检查：
   - 拿掉任何一方，其余各方的含义是否仍成立。仍成立才算分开。
   - 每一份能否独立使用。不能独立使用的一份是其他领域的内部。
   - 是否有一方读取另一方的内部状态。有就是泄漏。
7. 最后才套用依赖方向。正交约束含义和归属，不约束调用，各方可以互相调用。外层认识内层、内层不认识外层是另一条规则，在分解之后应用。

分解之后，每个剩余事项落进三种结果之一：

- 已经有拥有者。读它的正文，按它执行。
- 一条没有拥有者的轴。这是新设计，给它一个具名责任，不塞给相邻领域。例如观察者在生产实例重装配期间的脱离与重附着：生产实例可以不存在，被调用方不认识观察者，所以它需要自己的拥有者。
- 同一条轴上两个自洽的答案。交有权者裁决。

### 四种做坏的样子

| 样子 | 发生了什么 | 怎样认出 |
|---|---|---|
| 合并 | 几条轴收进一个对象 | 一个对象同时包揽规则、数据与资源；一条调用协议把寿命、结果保管和确认全交给调用方 |
| 涂抹 | 一条轴的规则散在几个领域，各自决定一遍 | 每个工具各自再判一次权限；执行环境自己解析租户 |
| 泄漏 | 为了让合成成立，内层认识了外层 | 被调用能力的契约点名某个调用方；一方持有另一方的操作契约 |
| 假正交 | 按目录或包拆开，含义仍然耦合 | 契约类型、依赖注入和接口只改变连接方式，不改变语义依赖，见[隔离语义，不隐藏责任](../../../docs/architecture/layers-and-dependencies.md#隔离语义不隐藏责任)。改名、包成 JSON 或回调也不算隔离 |

### 迷失了轴的信号

- 问题里带着机制名，例如「没有 X 的时候怎么办」。
- 一个答案有两个来自不同领域的理由。
- 其他领域的词出现在本领域契约里。
- A 的寿命决定了 B 的寿命。
- 一个默认值悄悄成了边界。
- 请有权者在不同轴的选项之间二选一，而这些选项并不互相替代。

### 与已有规则的关系

下列已有规则各是这个模型的一个实例：三条分解轴；领域不认识域外角色；策略不写死；设置有效、资产可用、动作获准是三个判断；工作区文件不是落点或权限的授予源；属性扩展优先于新概念；组合保证由具名承担者承担。通则是：找到轴，找到拥有者，让轴之间保持独立，把合成交给一个具名承担者。
