# 项目独有的研发判断

本提示接在「开工时对齐项目框架」之后。它只在角色职责、判断对象、写权限和任务授权内生效。评审和验收仍按各自判据取证；只有规则对应具体后果时才形成发现，品味观察不替代验收判据。

研发判断的基础是 ub-mode，按[技能采用入口](../../../docs/engineering/skills.md#ub-mode-研发品味)加载。本页只保留项目独有的方法：维度分解与正交。项目独有的能力、性质与 Cordis 承载判断归 `harness-design-handbook`。

## 维度分解与正交

本节是本页拥有的判断方法，不是别处正文的副本。

本节的「轴」指一个问题所在的维度，粒度比 `structure.md` 的三条分解轴细。每个被命名的问题落在一个拥有者。回答之前，先找到问题所在的轴。
正交指在一条轴上移动，不迫使另一条轴改变位置。对 A 轴问题的回答若同时定下了 B 轴上的事，这个回答就耦合了架构分开的两样东西。即使它说得通，它也是错的。

问题提出时通常不带轴名，而是带一个机制、症状或里程碑，例如「没有 sandbox 时，文件范围怎么定？」。问题里出现的那个词多半不是问题所在的轴。

### 单个问题怎么走

1. 剥掉表面。问这里真正在变的量是什么，什么必须保持不变。上例中，「没有 sandbox」只改变宿主提供者能满足哪些隔离断言。agent 能读哪里、能在哪里运行，不随它改变。
2. 命名轴。逐项问：谁在做（身份、租户），允不允许（授权、策略），在哪里运行（落点、执行环境），哪份工作要持续（会话、工作），谁执行、活多久（运行时寿命），怎样被看见（观察），怎样接线（装配）。[`structure.md` 的三条分解轴](../../../docs/architecture/structure.md#三条分解轴)是系统层面另一种粒度的分解，不与本节的轴一一对应。
3. 找到这条轴的拥有者，先读它的现行正文。从轴查拥有者时，先查执行仓库的开工定向页 `docs/orientation.md`。多数待决事项在这一步消失，因为拥有者已经回答了它。
4. 查耦合。检查答案有没有让一条轴决定另一条轴。常见形式有四种：隔离提供者决定授权范围；一个实例的寿命决定观察挂在哪里；调用方的寿命决定被调用工作的寿命；提交协议的一个细节反过来决定事实归谁。
5. 到这一步才给剩下的事项分类。某条轴上没有拥有者的缺口是新设计。同一条轴上两个都自洽的答案交有权者裁决。其余事项是实现已经设计好的东西。

### 跨领域的设计怎么分解

一个设计横跨几个领域是常态，不违反正交。正交要求把设计拆成若干份，每一份落在一条轴上并有一个拥有者。合起来才成立的部分单独拿出来，交给一个组合承担者。

1. 列出设计触碰的全部事实与决定。列事实，不列模块，例如「谁能读这个文件」「这次调用活多久」「人看到的内容从哪里来」。
2. 为每条事实命名轴并找到拥有者。一条事实只有一个拥有者。找不到拥有者的事实先记下来，不塞给相邻领域。
3. 每个拥有者只用自己的词说明自己提供什么、需要什么。被集成方不认识集成方，规则见[领域语义依赖与模型边界](../../../docs/architecture/layers-and-dependencies.md#领域语义依赖与模型边界)。需求方为自己的需求声明端口，实现方实现它。实现方认识端口契约，需求方不认识实现方。例如 Agent 声明 Journal 端口，Session 在会话日志上实现它，并按 Agent 公开的读取形状读同一日志里的 Agent 条目，见 [Agent 定义与工作推进的拥有者与输入](../../../docs/domains/agent-progression/architecture.md#拥有者与输入)。
4. 把集成本身当作有拥有者的对象。集成方认识所有参与方。它是协调者、适配器或装配，不是任何一方的内部。[组合保证由谁承担](../../../docs/architecture/structure.md#组合保证由谁承担)与[关键接缝与组合承担者](../../../docs/domains/boundaries.md#关键接缝与组合承担者)记录这一层。
5. 在接缝上写组合保证：谁参加，成立条件是什么，失败归谁。几个局部成功不等于整体成立。
6. 做三个检查：
   - 拿掉任何一方，其余各方的含义是否仍成立。仍成立才算分开。
   - 每一份能否独立使用。不能独立使用的一份是其他领域的内部。
   - 是否有一方读取另一方的内部状态。有就是泄漏。
7. 最后才套用依赖方向。正交约束含义和归属，不约束运行时谁调用谁。调用与代码依赖的方向仍受[依赖关系与禁止方向](../../../docs/architecture/layers-and-dependencies.md#依赖关系与禁止方向)约束，回调、事件订阅和双向消息也不引入反向代码依赖。外层认识内层、内层不认识外层是另一条规则，在分解之后应用。

分解之后，每个剩余事项落进三种结果之一：

- 已经有拥有者。读它的正文，按它执行。
- 一条没有拥有者的轴。这是新设计，给它一个具名责任，不塞给相邻领域。例如一项行为跨越两个参与方的寿命，任何一方都可能先结束，另一方又不认识它，这项行为就需要自己的拥有者。
- 同一条轴上两个自洽的答案。交有权者裁决。

### 四种做坏的样子

| 样子 | 发生了什么 | 怎样认出 |
|---|---|---|
| 合并 | 几条轴收进一个对象 | 一个对象替几条轴做决定，任何一条轴的变化都要改这个对象 |
| 涂抹 | 一条轴的规则散在几个领域，各自决定一遍 | 每个工具各自再判一次权限；执行环境自己解析租户 |
| 泄漏 | 为了让组合成立，内层认识了外层 | 被调用能力的契约点名某个调用方；一方的契约写进另一方的内部状态或内部步骤 |
| 假正交 | 按目录或包拆开，含义仍然耦合 | 契约类型、依赖注入和接口只改变连接方式，不改变语义依赖，见[隔离语义，不隐藏责任](../../../docs/architecture/layers-and-dependencies.md#隔离语义不隐藏责任)。改名、包成 JSON 或回调也不算隔离 |

### 迷失了轴的信号

- 问题里带着机制名，例如「没有 X 的时候怎么办」。
- 一个答案有两个来自不同领域的理由。
- 其他领域的词出现在本领域契约里。
- A 的寿命决定了 B 的寿命。
- 一个默认值悄悄成了边界。
- 请有权者在不同轴的选项之间二选一，而这些选项并不互相替代。

### 与已有规则的关系

下列已有规则各是这个方法的一个实例：

- 被集成方只用自己的词声明供什么、要什么，不知道被谁集成，见[外域概念的进入方式](../../../docs/architecture/layers-and-dependencies.md#外域概念的进入方式)。
- 横切策略采用可配置的策略对象，默认值只是配置初值，见[公开能力、策略与观测](../../../docs/engineering/quality.md#公开能力策略与观测)。
- 设置有效、资产可用、操作获准分别判断，见[资产与规则的范围与边界](../../../docs/domains/assets-and-rules/README.md#范围与边界)。
- 工作区参与内容和设置供给，不成为权限授予层，见[配置的来源与生效](../../../docs/architecture/cross-cutting-concepts.md#配置的来源与生效)。
- 组合保证由组合承担者承担，见[组合保证由谁承担](../../../docs/architecture/structure.md#组合保证由谁承担)。

通则是：找到轴，找到拥有者，让轴之间保持独立，把组合交给一个组合承担者。
