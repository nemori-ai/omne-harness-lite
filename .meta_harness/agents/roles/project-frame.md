# 开工时对齐项目框架

先理解本次任务，再按需阅读执行仓库的现行拥有者。之后的工作保持在同一套目标、约束和心智里。本段只规定阅读义务和入口，不复制那些正文。

## 先理解任务

确认这次要解决什么、交付什么、允许写入哪里、何时停止。这四项来自派发和本角色正文。缺一项时，先向派发者提最小问题。不要沿该缺口开始依赖它的工作。

## 再按需阅读

按上面的理解打开需要的拥有者。找到本次承诺的拥有者、适用范围和停止条件就停。不要通读全库。不要把角色提示当成第二份规范。

| 要核对什么 | 入口 |
|---|---|
| 常驻心智、责任和加载触发 | 执行仓库根 `AGENTS.md`，以及任务所在目录的 `AGENTS.md` |
| 系统目标与全局约束 | `docs/requirements.md` |
| 系统怎样协作 | `docs/architecture/README.md` |
| 责任怎样划分 | `docs/domains/README.md` |
| 工程方法、质量、流程与交付 | `docs/engineering/` 里这次用到的拥有者。方法采用归 `docs/engineering/skills.md` |

约束方向是：目标与产品规则，然后系统技术约定，然后领域与成员承诺，然后实现与验证。工程约定横跨这些层。下层不改写上层承诺。

入口缺失、互相冲突，或与本次授权矛盾时，指出条款和受影响的工作。只停止依赖该缺口的部分。

## 岗位仍由本角色决定

本段不授予技术设计、实现、评审、取证、验收或接受权。可写范围、判据和停止条件以本角色正文为准。

产品设计角色用这些入口约束产品判断。不在这里做技术选型，不写机制。

研发角色在本段之后还有研发品味。已采用的 pstack 与 Matt 方法按 `docs/engineering/skills.md` 按任务加载。提示里出现技能名称，不等于已经加载。读取或修改 TypeScript 时的加载义务在研发品味里。

场景 skill、判据页和检查表是本角色的专业模块。它们不代替上面的按需阅读，也不把项目目标抄进角色提示。
