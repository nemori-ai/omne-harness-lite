# 共享研发品味：单源化与分发（2026-09-23）

本记录保存一次把研发品味从根 `AGENTS.md` 解耦为角色共享正文的范围、去向与验证结果。
品味的权威正文是[研发品味](../../roles/engineering-taste.md)；覆盖名单、拼接顺序与产品角色豁免理由归
[角色源包说明](../../roles/README.md#共享研发品味)；`shared_prompts` 字段语义归 design-subagents skill 的
`references/packaging.md`。本记录不拥有其中任何一项。

## 改了什么

| 原来在哪 | 现在在哪 |
|---|---|
| 根 `AGENTS.md`「研发品味」十条通用判断 | 权威文件「通用判断」，逐字迁入（只把观测要求的链接改成纯文本路径）；根 `AGENTS.md` 留标注为投影的五行 |
| 根 `AGENTS.md` 与开发者契约各一份「工具使用」 | 权威文件「工具使用」：去掉角色用不上的「subagent 派发」例子，补上「任务本身就是运行程序、检查器、测试或外部进程时 shell 就是对口工具」 |
| 开发者契约「TS/JS 研发品味」 | 品味部分进权威文件「TS/JS 代码」，带适用条件；「每轮编辑后跑共享格式化、只传本次获准文件」这条执行义务留在契约「格式化」 |
| 开发者契约「可观测性」里与通用条目同句的一句 | 删去；开发者的观测责任留在契约 |
| 六个角色各自的工具段里的通用半句 | 删去，只留角色专门要求（定点编辑省 token、运行被测程序用 shell 等） |
| 根 `AGENTS.md`「每个 subagent 都应明确职责…」 | 原地保留：那是派发者的品味，角色本身不派发 |

13 个设计与研发角色都把品味列为 `shared_prompts` 首项；三个技术 reviewer 为此新建只含该字段的
`assembly.toml`，固定档位不变。两个产品设计角色按豁免理由不挂。生成器把单个 `shared_prompt`
改为有序列表 `shared_prompts`（旧字段拒绝，不留兼容层）。

顺带修正的引用：根 `AGENTS.md` 三处指向 handbook「工程判断」，该节名并不存在，改指 Taste 与
`judgment.md`；PF-012 两处、PF-014 一处引用「外部输出不因被运行时调用就变得可逆」的链接原本指向
不含这句话的文件，改指权威文件（链接修复，不升 rev）。

## 验证

| 层级 | 结果 |
|---|---|
| 生成器纯重构 | 改字段后重编，15 个角色两端 30 个生成物与改动前逐字节一致 |
| 仓库检查 | 工作树内 `make agents-check`（168 个生成物）、`docs-check`（774 份 Markdown）、`design-check`、`test`（174 项，新增 8 项）全部通过；改动前基线同样全绿 |
| 分发覆盖 | 13 个角色 × 两端共 26 个生成物，各含恰好一个与源文件逐字一致的品味章，且紧跟角色正文；开发者的品味在共同契约之前；两个产品角色的 4 个生成物不含 |
| 改一处即分发 | 在源副本里把品味改一个字重编：168 个生成物中恰好这 26 个变化，其余不变 |
| 单一权威 | 13 条标志句在角色源与根 `AGENTS.md` 中只命中权威文件；例外只有根 `AGENTS.md` 的投影句，以及豁免角色 product-design-drafter 自己工具段里的一句 |
| Claude Code 原生加载 | 在工作树里用 `claude -p --model haiku` 开新进程派发：spec-reviewer 的用量记在 `claude-opus-5-5[1m]` 名下，plan-reviewer 记在 `claude-fable-5-1` 名下；两者都原文引出品味首句，并说明它不改变也不扩大判断对象、不作为独立发现来源 |
| Codex 原生加载 | 在工作树里用 `codex exec -m gpt-6-luna` 派出 spec-drafter：子会话日志记录 `agent_role` 为 spec-drafter、模型为 `gpt-6-astra`，指令中含品味首句。它拒绝逐字引述开发者指令；改问内容后，正确答出三个小节标题、「优先复用不是自行引入依赖的授权」以及 shell 何时是对口工具 |
| 未验证 | 其余 10 个角色的实际派发；品味对真实任务产出质量的影响。主检出与其他工作树的生成物在合并后各自重编 |
