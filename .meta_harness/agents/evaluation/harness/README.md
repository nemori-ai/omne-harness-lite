# 角色评估的运行器

一个**流**是一个角色做一种事。流的用例与判定方法放在[常设用例集](../suites/README.md)里，这里只有跑它们的那一套：
建一次性的工作副本、写派发用的简报、收录宿主留下的记录、把判定结果落成统一形状、算带区间的汇总。
代码在 [roleeval/](roleeval/)，测试在 `tooling/tests/test_role_evals.py`，随 `make test` 跑。

**运行器自己不起任何模型。**角色的一次运行、判官的一次答复，都是主会话用 Agent 工具派出去的一个 subagent。
运行器的子命令成对围着那一次派发：前一个写出该交给 subagent 的东西，后一个把宿主留下的那份记录收进来核对、记账。
不用无界面的宿主进程（`claude -p` 之类）跑评估——负责人 2026-10-01 定的，那样做有封号的风险。

入口是 `make role-eval ARGS="<子命令> <用例集目录> …"`：

| 子命令 | 做什么 |
|---|---|
| `verify` | 给每份材料建副本、落种入，核对种入各恰好落一次、工具核得出的那几处在设计评审报告里确实报了 |
| `inputs` | 把全部用例逐字印成一份 markdown，供用例签字时看 |
| `prepare --variant V --material M [--rep K]` | 为一次运行建副本、写简报，印出该怎样派发 |
| `record … --transcript T --dispatch registered\|inline [--tokens N]` | 收录那次运行的记录：核对简报、模型、副本有没有被动过、有没有够到不该看的地方 |
| `judge-brief --variant V --material M [--rep K]` | 为一次已收录的运行写判官的简报，印出指向它的那句提示 |
| `judge-record … --transcript T` | 核对判官的答复，通过则把这次运行判定成逐条结果 |
| `grade --variant V --labels FILE` | 用人工写下的判定给已收录的运行打分 |
| `calibrate-brief [--case ID]`、`calibrate-record --case ID --transcript T`、`calibrate --judge-model M` | 判官校准：写简报、收录答复、印出与人工判定的比对 |
| `import-run` | 把早先实验留下的一次运行接收成一个运行记录 |
| `summary` | 每个指标的均值与区间、失败按类计数、用量 |
| `report` | 用仓库里的[报告页生成器](report/README.md)出 `report.html` |

这些子命令都不调用模型，也都不花钱；花用量的是两个子命令之间主会话派出去的那个 subagent。

## 一次运行怎么跑

1. `prepare` 从 `agents/roles/` 的源现编译角色定义并冻结到变体目录，建好工作副本，把简报写到
   `<变体>/episodes/<材料>_rep<k>/brief.md`，印出派发方式。它在这几种情况下拒绝：用例集当前版本的两次签字不全；
   受保护的路径有未提交改动（`--allow-dirty` 可放行，结果里记 `dirty`）；这份材料 `verify` 不过。
2. 主会话派**一个** subagent。提示必须逐字带上简报（换行与空格有出入不要紧，字不能有出入）。
3. `record` 读宿主留下的记录（`~/.claude/projects/<项目>/<会话>/subagents/agent-<id>.jsonl`），核对后写下
   `episode.json`、`final.md`、`trajectory.jsonl`，删掉工作副本。`--tokens` 填宿主在完成通知里报的用量合计——
   记录里逐条消息的输出用量偏低（宿主在消息刚开始流出时就落盘），合计以通知为准。

派发有两种，一个变体只收一种，`record` 时要说明是哪一种：

- **registered**：派的就是这个角色自己的 subagent 类型，提示是简报本身。这与平时派发角色的方式一致，基线用它。
  角色定义是宿主在**会话开始时**加载的；改了角色的源、重编了生成物之后，要开一个新会话才派得到新的定义。
  这种派发拿不走角色定义里声明的工具：角色若用了流的 `allowed` 之外的工具，`read_only` 记 0 并写明是哪些。
- **inline**：当前会话里没有这个角色的类型时的替代。派一个通用 subagent，提示先让它读 `prepare` 放在副本旁边的角色定义文件、
  当作系统指令照办，再给简报。角色定义因此是作为文件内容而不是系统提示到达的，通用 subagent 自己的系统提示与全部工具也还在——
  它量的不是平时派发的那个角色，结果不与 registered 的放在一起比。

工作副本有两种来源：**待审材料**（设计树）取自用例集钉的那个提交，所以设计树往前走了，用例还是原来那份输入；
**被测的一部分**（skills 与判据页、tooling、根约定）取自工作树，所以运行前这些路径、用例集与本目录必须已提交，
记下的提交才说得清跑的是什么。评估目录不进副本——真值在这里。副本必须放在任何检出之外（`--work` 或 `ROLEEVAL_WORK`）。

**subagent 的工作目录是主会话的检出，不是副本。**简报告诉它副本在哪，但宿主不拦它读别处。所以 `record` 另外核对两件事：
记录里的工具调用或工具返回提到了用例集目录、校准判定或早先的评估结果，这次运行记为 `contaminated`、不计分；
工具调用点名的、副本之外的其余绝对路径，原样记在 `episode.json` 的 `outside_copy` 里供人看。
subagent 还会带着主会话检出的约定文件（`AGENTS.md` 等）启动，而不是副本里的那一份；两者在被测路径已提交时内容相同。

## 留下什么

默认落在主检出 `tmp/role-evals/<流>/`，不入库：

```text
_state.json                         指标定义，报告生成器读它
_calibration/_briefs/<报告>.md       判官校准用的简报
_calibration/<判官>/                 判官校准：每份校准报告的判定与一份比对
<变体>/agents/<角色>.json            本变体冻结的角色定义
<变体>/episodes/<材料>_rep<k>/       一次运行：brief.md、trajectory.jsonl、final.md、episode.json，
                                    以及判官的简报与每次答复的记录
<变体>/results.jsonl                逐条结果
<变体>/traces/<用例>_rep<k>.json     每条结果的完整轨迹
<变体>/errors.jsonl                 没能产出可判定输出的尝试
```

变体目录只能叫 `baseline` 或 `v<N>`，报告生成器不认别的名字。

**没产出可判定输出的尝试不进结果表。**记录没有以一份报告收尾、宿主实际用的模型不是流里钉的那个、够到了不该看的地方、判定器失败，
各记一行到 `errors.jsonl`（带类别、用量与证据路径），那个（材料、次数）的位置空着，可以重新 `prepare` 再跑。
这样管道故障不会被平均成「模型答错了」。答复被截断的照常落行，标 `truncated`，不计入均值。

评审类的流里，一次运行出若干行：每处应当被报出的问题一行（`caught`），整次运行一行（是否只读、首段是否写明判据页、
越出本次判断的意见条数）。

subagent 的运行没有价格。能记下的是：宿主报的用量合计、墙钟时间、工具调用次数、宿主记录的档位。
档位由宿主按角色定义或会话设置定，派发者管不了；流里写的档位是期望值，`episode.json` 的 `efforts_observed` 是实际值。

## 汇总怎么读

均值先在每个用例的各次运行上取、再在用例之间取，与报告页的算法一致。区间按**用例数**算，不按用例数乘次数算：
同一用例的几次运行彼此相关，当成独立观测会把区间算窄。两个变体之间比的是逐用例的差。
`summary` 末尾给出首要指标的噪声范围；比它小的变化，这个评估分辨不出来。
同一份材料里的几处问题出自同一份报告，也不独立——材料少的时候，实际的不确定性比印出来的区间更大。

报告页只画首要指标；其余指标看 `summary`。生成器在 [report/](report/README.md)，随仓库维护，需要 `node`。

## 判官与它的校准

评审类的流用一个模型判官判「这处问题有没有被报出」。判官只读报告与问题清单，不读材料；它判一处「报出了」，
必须逐字引出报告里的原句、并指明那句话属于报告的哪一条阻断或非阻断发现，程序核对这两样都对得上才采信，
对不上就再派一次，再不过记为判定器失败、不计分。规则原文在 `roleeval/judge.py` 的 `SYSTEM`、`OUT_OF_KIND` 与 `ANSWER_FORMAT`。

判官也是一个 subagent。一份报告动辄上万字，由派发者转抄进提示会走样，所以简报写成文件，提示只有一句指向它的话；
`judge-record` 从记录里核对：提示指的是这份简报，判官只调用了读这个文件的工具，读回去的内容就是磁盘上的整份简报，
全程只有一个模型。有一条不符，这份记录就不是这个判官在答这份简报，不收，也不算一次尝试。

判官的名字是 `judge:subagent:<模型> rules <规则哈希>`：规则一改就是另一个判官，要重新校准。
判定方法的签字写明是给哪个判官签的，别的判官的答复 `judge-record` 不收。

校准：`calibrate-brief` 为用例集 `calibration/cases.json` 里的每份报告写一份简报；主会话逐份派判官；
`calibrate-record` 收录答复；`calibrate` 把收录的判定与那里写下的人工判定逐处比对。
报告有两种：真实运行留下的，和为了得到「没报出」的例子而做的反例——一份真实报告删掉或挪走几条发现，
删改写在清单的 `derive` 里，写简报时现场派生，送给判官的那一份留在结果目录里。
校准量的是判官与人工在这些报告上是否一致，说明不了没有校准报告的材料上判得怎样。

## 这套东西不能声称什么

运行器只保证「记下来的就是跑过的、算出来的与记下来的一致」。用例像不像真实工作、判定方法判得对不对，
归各用例集的说明与两次签字；只有 Claude Code 一端，Codex 一端目前不在范围内。
subagent 的隔离弱于单独的宿主进程：它与主会话共用检出与文件权限，`contaminated` 的核对只认得出记录里留了痕迹的越界。
