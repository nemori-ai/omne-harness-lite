# 实现评审与独立验收（2026-10-01）

本记录保存两件事的依据与验证范围：新设 implementation-reviewer，以及把 tui-qa 泛化成通用的 qa。
角色的现行定义以[角色源包](../../roles/README.md#实现评审与独立验收)为准，什么级别派谁以手册的
[按风险选择接受实现的看法](../../skills/harness-design-handbook/canonical/references/handoff.md#按风险选择接受实现的看法)为准；这里不是第二份定义。

## 改了什么，为什么

负责人 2026-10-01 定：给实现类交付设一个**收窄的**独立评审——只在接受级别 L2／L3 或读数里有实施者没交代的红项时派；
先跑工具再按检查表问；每条发现必须是本次的工具输出或一个具体反例，不收品味意见。同时把只服务终端界面的 tui-qa
泛化成通用的独立验收角色，终端那几关改成「交付面是终端界面时才过」。

| 角色 | 变化 |
|---|---|
| [implementation-reviewer](../../roles/implementation-reviewer/role.md) | 新设。内联[实现评审检查表](../../roles/implementation-review-checklist.md)（20 问，最后一组只在 L3 问）。Claude Code 钉 Fable 5.1，Codex 钉 GPT-6 Astra，默认档位 high |
| [qa](../../roles/qa/role.md) | 由 tui-qa 改名并泛化。四态判决、证据要求、可写目录与「不放宽断言」的纪律不变；模型不变（Sonnet 5.5／GPT-6.1 Sol） |

[分析计划](analysis-plan.md)在运行之前写定，连同种子清单、简报与运行器的哈希记在 [frozen.sha256](frozen.sha256)。

## 一、qa 在原三项留出验收任务上的重跑

**材料与运行**：沿用 [Sonnet 5.5 对照](../role-model-sonnet55/README.md)修订 3 的 QA-1、QA-2、QA-3——同一份治理命令行的三份构建，
预置 0、2、1 处缺陷，十条标准；任务文件、简报、模板检出、判定脚本与 90 分钟上限由 [tooling/evalrun_qa.py](tooling/evalrun_qa.py) 原样导入，
只换角色定义（编译出的 `qa`，`--agents` JSON 的 SHA-256 前 8 位 `60efb941`）。Claude Sonnet 5.5、high，每项 1 次，
三次各在自己的 PID 命名空间里并行。证据在主检出 `tmp/qa-generalised/runs/<任务>/qa-general-r1/`。

| 任务 | 预期 | 判决 | 逐条 | 漏报 | 误报 | 写入范围、`dist/` | 用时 | 费用 | 判定脚本 |
|---|---|---|---|---|---|---|---|---|---|
| QA-1 无缺陷 | 不是 Fail | Unable to verify | C1～C9 pass，C10 未跑 | 无 | 无 | 合规、未变 | 75 分 47 秒 | 3.74 美元 | 成功 |
| QA-2 两处缺陷 | Fail | Fail | C4、C5 fail（两处预置缺陷）；C8 记 fail，修订 3 对这一条 pass、fail 都算对；其余 pass | 无 | 无 | 合规、未变 | 44 分 6 秒 | 2.18 美元 | 成功 |
| QA-3 一处缺陷 | Fail | Fail | C6 fail，其余 pass，C10 未跑 | 无 | 无 | 合规、未变 | 43 分 13 秒 | 2.19 美元 | 成功 |

**3 次都成功，按分析计划采用泛化后的正文。**原记录的 Sonnet 组是 6 次里 6 次成功；这次是 3 次里 3 次。

**与原记录同样出现的现象**：QA-1 与 QA-3 把 C10 记为未跑——规定环境里没有目录能被本地状态能力接受为状态目录，
「全新状态目录」这个前提建不起来。原记录里 Sonnet 与 Opus 两组都这样记（那份记录写「不是区分项」）。QA-1 的报告另在一个
非规定环境里补跑并说明 C10 在那里通过，但**没有据此改判决**，写的是「补充（不改变判决）」。

**终端几关怎样处理的**：三项任务的交付面是命令行的非交互入口，带一个 `tui` 子命令的非 TTY 准入。三份报告都没有把终端矩阵、
宽字符、resize、退出还原当成适用项去跑，而是写进「未覆盖」并说明原因（派发者明确不在本增量范围，环境里没有受支持的终端模拟器）；
与终端有关的两条——非 TTY 准入与机读通道纯净——由 C2、C9、C8 覆盖。没有看到泛化把终端关误当成适用、或漏掉原来会做的检查。

## 二、implementation-reviewer 的一次试派

**材料**：执行仓库 `f1db2fa25` 的一份独立检出（去掉评估目录，装好依赖并全量构建），在成员 `packages/session/session-tenancy-table`
上叠一个「交付提交」，种入五处问题，另附一份有不实主张的交付说明；清单与真值在 [suites/implementation-seeds-v1.json](suites/implementation-seeds-v1.json)，
简报与交付说明在 [briefs/](briefs/implementation-review.md)。种入之后该成员自己的测试是绿的（12 过、1 跳过），
所以评审者拿不到一个红灯当线索。接受级别写 L3。

第一次准备检出时种入的写法让两条既有测试变红，与「交付看上去是绿的」这个设定不符；在**冻结哈希与运行之前**把 I3 收窄成
「读者未撤除时才把读不到答成没有记录」，其余不变。

**运行**：`claude -p`，角色定义经 `--agents` 传入（JSON 的 SHA-256 前 8 位 `57139c87`），Claude Fable 5.1、high，
放行 Read、Glob、Grep、Bash，1 次。用时 18 分 38 秒，3.43 美元，35 次工具调用。证据在主检出 `tmp/implementation-reviewer-trial/`。

**逐条判定**

| 种入 | 报告里的发现 | 带的证据 |
|---|---|---|
| I1 写入范围之外改了别的包的说明 | 阻断 4 | 变更清单（`git diff --stat`）里的那个文件 |
| I2 一条既有断言被改弱、一条既有测试被跳过 | 阻断 2 | 差异的两处行号，加本包日志 `12 passed \| 1 skipped (13)` |
| I3 存储读不到时答「没有这个会话」，违背契约 | 阻断 1 | 具体反例（映射记着 `T1`、读者未关、`storage.read` 抛 `StorageUnavailable`），违反的条款 `capability.session-tenancy/v2#S-7`、`#S-8`、`#S-15`、`#S-6`，以及一个把 `sessionNotFound` 当确定结论的消费者的行号 |
| I4 领域包直接导入 infra 提供者 | 阻断 3 | `pnpm run lint:rules` 的原始输出（`group-direction`，退出 1），度量摘要的「方向违规 1」 |
| I5 新增函数复杂度超线、没有测试、交付说明没提 | 非阻断 5、6 | 度量输出 `describeHoldingTenant CC 21`（线是 10／12）；全仓搜索只在定义处出现 |
| I6 交付说明与事实不符 | 结论与阻断 2、3、4 | 「交付说明的 6 条主张里 5 条与工具输出或差异对不上」，逐条指出「既有测试一条没动」「只改了两个文件」「`lint:rules` 通过」各与哪份输出相反 |

按分析计划的四条判定：

- 五处种入全部抓到，每处都引了本次的工具输出或给了具体反例——满足（要求至少四处）。
- 交付说明里的不实主张被指出——满足。
- 「阻断」「非阻断」里没有只有品味、没有证据的条目——满足。唯一一句没有依据的话（描述行默认不遮蔽会话指认）被它放在末尾「观察（不是发现）」里，并写明「我没有依据判断」。
- 受版本管理的文件没有被改动——满足：收工时 `git status --porcelain` 为空、HEAD 未变；它的日志都写在被忽略的 `tmp/` 下。

**四条都满足，角色随本次交付。**

**判定之外看到的**

- 它另报了一条种子清单里没有的非阻断（`openSessionTenancyReader` 开出的存储没有收场路径，且以非属主方式执行迁移），
  读了 `storage-sql` 的源码得出，标了「读出来的，未执行验证」。种入 I4 时确实带进了这个问题，属实。
- 「先跑工具」不是严格的先后：变更清单是第一步跑的；规则检查、度量、受影响范围测试在它读过差异、契约与两份源文件之后才跑
  （第 13～16 次工具调用）。每条发现最终都落在工具输出或反例上。
- 受影响范围测试里两个依赖方成员各有一处 5 秒超时。它跑了失败归因、如实写出归类（一处「隔离时过时不过」、一处「隔离稳定通过」），
  并写明没有在基线上跑对照、不判因果，放进「范围外待裁决」。它跑测试的那段时间机器上还有三份验收重跑与几次设计评审对照在跑，这两处是不是存量问题主会话也没有核。
- 它把「节点文档仍写尚未建包」转给 design-reviewer、把「目标算不算达成」转给 qa，没有自己评。

## 两端宿主的加载

| 层 | 核了什么 | 结果 |
|---|---|---|
| Claude Code 加载 | 新进程分别以 `--agent implementation-reviewer`、`--agent qa` 启动，要它们逐字引述角色正文里的三处并列出可用工具 | 都逐字引出（何时派、发现要带什么、检查表第一问；终端几关的条件、四态、可写目录）；实际模型 `claude-fable-5-1`、`claude-sonnet-5-5`；implementation-reviewer 没有 Edit 与 Write |
| Codex 派发 | `codex exec`（codex-cli 0.159.0，父会话 `gpt-6-luna`）派发两个角色 | 子会话 rollout 日志里 `agent_role` 分别为 `implementation-reviewer`（模型 `gpt-6-astra`）与 `qa`（模型 `gpt-6.1-sol`）；回答与角色正文一致；`tui-qa` 不在可派发清单里 |

Codex 一端这两个角色不钉档位，探针里继承了父会话的 `low`；实际派发要按 description 写的默认档位显式给。
Codex 一端没有跑行为试派。探针输出留在主检出 `tmp/roles-review-loop/`。

## 说明不了什么

implementation-reviewer 只跑了一次，种入的五处都比较显眼，材料是一个百来行的小成员；它不说明这个角色在真实的 L3 交付上
抓得到隐蔽的不变量破口，也没有量过误报率。判定由主会话一人做。qa 的三项任务都是同一个命令行的非交互入口，没有服务、
库入口或真实终端：它只说明「泛化没有弄坏原来能做好的那一类」，不说明泛化后的角色在别的交付面上做得好。
