# 分析计划修订 3：验收任务单路串行重跑

固定于 2026-09-29，早于本修订的任何运行。[原计划](analysis-plan.md)下 tui-qa 的 12 次运行保留原样作为记录，
但**不用于 tui-qa 的结论**；tui-qa 的结论只取本修订的运行。其余三个角色不受影响。

## 为什么重跑

原计划下的验收运行有三处条件问题，使两个模型的结果都不可靠：

1. **并行运行互相干扰。**检出彼此独立，但进程空间是共享的，本机没有沙箱。至少一次运行用按名字匹配的
   方式结束进程，匹配范围覆盖了同时在跑的其他验收运行。
2. **时间上限偏紧。**交出报告的运行用时 21 到 42 分钟，上限是 45 分钟；两个模型都出现了跑满上限、
   没有报告的运行。
3. **判据有一处疏漏。**QA-2 预置的第二处缺陷让 `machine --version` 输出版本说明而不是报告文档，
   这同时违反 C4 与 C8。原判据只把 C4、C5 记为应失败，把 C8 记为应通过，于是正确报出 C8 的运行被记成误报。

## 与原计划相同的部分

模型、提示、档位（high）、工具、权限、设置来源、检出、辅助保持原样、任务与简报、关键约束及其观察方式、
折算成本上限、重试规则，全部沿用[原计划](analysis-plan.md)。协议适配的说明同样适用。

## 不同的部分

| 项 | 取值 |
|---|---|
| 任务 | QA-1、QA-2、QA-3 |
| 并行度 | 1：同一时刻只有一次运行，期间本机不跑其他评测 |
| 墙钟上限 | 90 分钟 |
| 重复 | 每任务每模型 2 次，共 12 次 |
| 次序 | 两个模型交替，相邻两个任务里先后手对调 |
| QA-2 的判据 | C4、C5 应为失败；C8 记为失败或通过都算判对 |

简报里写给验收者的内容一字不改，包括「重试上限 3 次」与探索时间盒；放宽的只是运行脚本的强制终止时间，
验收者并不知道这个数。

## 已知的局限

- **留出集已被用过**：这三个任务在原计划下跑过两个模型。期间没有调整过提示、辅助、档位或简报；
  判据的更正只针对上面第 3 条，依据是缺陷定义本身，不是任何一次运行的输出。
- **上限是看过结果之后放宽的。**这会同时放过两个模型里原本超时的运行，不偏向某一方；但它意味着
  本修订回答的是「给足时间时谁判得对」，用时与成本另行报告。
- 进程空间仍然共享。串行消除了评测运行之间的干扰，不能阻止一次运行影响本机上与评测无关的进程；
  轨迹里出现不限定在自己检出内的结束进程动作，单列报告。

## 可接受的退化

沿用原计划的四条：候选无关键约束违反；任务成功次数不少于基线减一；十条标准判对条数的均值不低于基线
5 个百分点以上；每次运行平均折算成本低于基线。

另记一项不作判据的观察：每次运行的墙钟用时，以及是否超过原来的 45 分钟。
