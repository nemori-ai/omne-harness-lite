# 分析计划修订 3b：验收任务在进程命名空间里并行补跑

固定于 2026-09-30，早于本修订的任何运行。它只改变[修订 3](analysis-plan-r3-qa-serial.md)的**并行度与隔离方式**，
任务、模型、档位、提示、判据、时限与判定规则全部沿用修订 3。

## 为什么再改

修订 3 的串行批次在 2026-09-29 16 时前后遇到本机断网（DNS 解析失败），12 次里 9 次作废，
原记录改名为 `*-apierror` 保留；恢复后又有一次刚开始就被本次改动中止（`*-killed`）。串行补跑这 9 次
需要五到十小时，用户要求压到两小时以内。

串行的理由只有一个：原计划下并行运行互相干扰，起因是共享进程空间里按名字结束进程。
本机没有沙箱，但支持无特权的用户与 PID 命名空间：每次运行放进自己的 PID 命名空间后，
它看不到、也结束不了其他运行的进程，这正好消除那种干扰。已探测：命名空间内文件权限语义、
FIFO、`stat.uid` 与 `geteuid` 的关系以及 `claude` 的运行都正常。

## 不同的部分

| 项 | 取值 |
|---|---|
| 并行度 | 9（补跑的 9 次同时开始） |
| 隔离 | 每次运行由 `unshare -Ur --pid --fork --mount-proc` 启动，进程只见到自己 |
| 有效记录 | 修订 3 已有效完成的 3 次（QA-1 两臂、QA-2 Sonnet）沿用，不重跑 |

## 由此增加的局限

- 命名空间内进程以映射的 uid 0 运行，文件系统上的实际属主不变。被测应用对秘密文件的属主核对
  比较的是同一映射下的值，探测确认为一致；但这与串行批次的运行条件不完全相同。
- 9 路并行下机器负载高于串行，**墙钟用时不与修订 3 的 3 次有效记录直接比较**；判决正确性、
  token 与折算成本仍可比。
- 命名空间只隔离进程可见性，不隔离文件系统与网络；检出各自独立这一点不变。
