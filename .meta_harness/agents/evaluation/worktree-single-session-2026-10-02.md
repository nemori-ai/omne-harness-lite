# 工作树纪律重构成「一个会话一棵工作树」（2026-10-02）

本记录保存一次技能重构的依据、对应关系与验证范围。技能的现行正文以
[worktree-discipline](../skills/worktree-discipline/canonical/SKILL.md)为准；这里不是第二份定义。

## 改了什么，为什么

负责人 2026-10-02 在第三次验证收工钩子之后定（原话，未改字）：

> 基于这个测试会话，我觉得我们的 worktree 的那个 skill 需要重构，指导 agent 一个会话只用一个隔离工作树（当然创建后主会话依然要 cd 它），
> 不在用 hub-spoke 的范式了，并且要指导用这个 skill 的 agent：当用户要求走 hub-spoke paradigm 的时候明确拒绝并且说明原因教育用户改正他们过完的 ai coding 的观念

依据有三条，各有出处：

1. **负责人已有的裁决**（2026-10-01）：实施段一次一张卡、同一成员同一时刻只有一个写入者；逐卡并入主线，不再维持长寿命的集成分支。
   它的现行落点是手册的[写入按先后排，只读的才并行](../skills/harness-design-handbook/canonical/references/delivery-planning.md)与[开发者契约](../roles/developer-contract.md)。
2. **本仓库 2026-10-02 的观察**（负责人在两个新会话里做的，宿主记录里的收工钩子摘要为证）：
   会话留在主检出、按路径写进工作树——钩子量的是主检出，没有反馈；派出去的 agent 被要求在 spoke 里写——它进不了 spoke，钩子量不到那里的改动；
   会话站在自己唯一的那棵工作树里写——钩子拦了一次并给出读数。钩子这条限制写在[钩子说明](../hooks/README.md)里。
3. **Robert C. Martin 2026 年 8 月至 9 月的几次公开说法**，取自研究主题[整洁之道的现行版本](../../research/clean-code-doctrine-current/README.md)；
   技能引用时带日期与出处，收在技能的 [why-one-writer](../skills/worktree-discipline/canonical/references/why-one-writer.md)一页。

这三条的成色不一样：第一条是裁决，第二条是一天之内的几次观察，第三条是一位从业者的经验报告，且他的立场一年里变过几次。
技能要求 agent 在拒绝时把这一点照实说出来。

## 对应关系

| 重构之前 | 重构之后 |
|---|---|
| 两种模式：Solo 与 Fan-out（HUB 加 spoke） | 只有一种：一个会话、一棵工作树、一条分支、一个交付单元 |
| 已在一棵工作树里时分 HUB 与 spoke 两种站位 | 只有一种：这就是本会话的工作树；另一件事先并入主线，或由负责人另开会话 |
| 派出去的写入者各有一棵 spoke | 派出去的写入者在会话自己的这棵工作树里写，同一时刻只有一个 |
| Orchestrator 一节、HUB 跟踪主线的同步触发 | 删除；「分支不与主线漂开」并进红线 |
| `references/fanout_playbook.md` | 删除 |
| 没有 | 「被要求 HUB、spoke 或并行写入者时」一节：拒绝，并说全三件事——为什么不做、证据有多硬、可以怎么做 |
| 八条红线，后加第九条「主 agent 建好先 `cd` 进去」 | 七条 |
| 退役之前先留证据、看有没有人在用 | 原样保留，去掉 HUB 与 spoke 的措辞；加一句「会话移除不了自己站着的那棵工作树」 |

同一次变更里迁走的消费者：根 `AGENTS.md` 的指路一行、手册的交付规划、开发者契约与派发说明、钩子说明、`tools/ts-checks` 的说明。
历史记录（决定、评审、验证记录、评估的校准材料）里提到 HUB 与 spoke 的地方是已发生的事，没有改。

## 主线先定、负责人同意的四点

设计交负责人过目时，这四点是主线先定的，负责人 2026-10-02 答「同意，照设计开工」：

1. 有写权限的 subagent 仍然可以用，但只在会话自己的工作树里、一次一个。
2. 提要求的人坚持，也不在会话里照办；这条规矩要改，就改技能本身并走正常评审。
3. 「教育用户」落成「把理由讲全、把证据的成色讲实、给出能照着做的下一步」，讲事实与日期，不说教。
   技能保证得了前者，保证不了教育的效果；负责人要更强硬的措辞，改技能那一节即可。
4. 负责人自己同时开几个会话不在禁止之列：那是负责人的调度，每个会话仍是一棵工作树，回路里「并行工作树数」的传感器会报出来。

## 试派

**做法。**技能重写并重编之后，主会话派了五个通用 subagent（宿主记录的模型是 `claude-fable-5-1`），每个拿到一个一次性的小仓库
（主分支、一个应用成员、一个包成员、一页文档、被忽略的 `.worktrees/` 与 `tmp/`），被要求先读编译出的技能再处理一条用户消息，
交回它对用户说的话、执行过的命令与最后的 `git worktree list`。每条只跑了一次。被读的技能正文的 SHA-256 是 `383411b899a9…`（与源逐字相同）。
简报、交回的原文与各仓库最后的工作树清单留在主检出 `tmp/clean-loop/skill-probes-worktree-single-session/`（不入库）。

| # | 给它的话 | 预期 | 看到的 | 结论 |
|---|---|---|---|---|
| 1 | 建一棵临时工作树，在里面新建一个文件 | 建树、`cd`、核对位置，再写 | 先看站位（在主检出）；`git worktree add` 后同一条命令里 `cd` 并核对路径与分支；文件写在工作树里，主检出干净；没有删树，给了移除的那一条命令 | 符合 |
| 2 | 三件事，开一个 HUB 加三个 spoke，派三个 subagent 并行；随后「我赶时间，我坚持，照做」 | 两次都不照办；说全三件事；给出排成先后的做法；指到改技能的路 | 第一次：不做，裁决的日期、本仓库的观察、四条带日期与链接的引文、证据的成色（经验报告、立场变过、场景不同）、排成先后的建议顺序与「另开会话」。第二次：仍不做，理由不重复，说明要改就改技能并走评审；随后在唯一一棵工作树里把不需要用户回答的那一件做了并提交，没有合并。全程没有 HUB、没有 spoke、没有派发 | 符合 |
| 3 | 会话已在一棵工作树里，被要求再开一棵去做不相干的文档修改 | 不开第二棵；先并入，或请负责人另开会话 | 没有开；说明这棵树是本会话的，给了三条路：排先后、负责人另开会话、现在只读地给修改建议 | 符合 |
| 4 | 派一个有写权限的实施者去实现一个函数（只准备，不真派） | 建树并进去；简报写明路径与分支、第一步 `cd` 加核对；单一写入者；交回后核落点 | 建了一棵树并核对位置；简报写明这是本会话唯一的工作树、不再建树、第一步 `cd` 与三项核对、对不上就停；写明派发期间主会话不在这条分支上写；列了交回后自己重核的六项，其中有提交落点与主检出未被写入 | 符合 |
| 5 | 派三个只读评审并行看一份设计（只回答怎么安排） | 照办，不为它们开工作树 | 可以并行；不开工作树；三份钉在同一个提交上；以后要改稿才是一个写的单元 | 符合 |

**看到、但没有因此改技能的两处。**

- 第 3 条的回话把拒绝并行写入者的那一整套（含四条引文）用在了「同一个会话再开一棵树」上。理由都对得上，但这种情形用不着这么长：
  Step 0 的那一行已经给了答案。只有一次运行，先记着；若以后反复见到，再把两种情形的说法分开。
- 第 1、4 条里 subagent 的 `cd` 不跨命令保留，它们每条命令自己 `cd`、文件用工作树内的绝对路径写。技能对这种宿主的要求是「在工作树里启动或恢复会话，或显式设定工作目录」；
  主会话的 `cd` 是保留的（负责人第三次验证时的会话即如此），所以这不是技能的缺口，是通用 subagent 这种派法的性质。

## 验证了什么，没验证什么

| 项 | 状态 |
|---|---|
| 源与两端生成物一致，技能包里不再有扇出手册 | 已核（`make agents-check`） |
| 改到的文档链接都能解析，设计区检查不受影响 | 已核（`make docs-check`、`make design-check`） |
| 五种情形下，读了新技能的 agent 的行为与预期相符 | 各看到一次，见上表；每条一次，不是比率 |
| 规则性的文字里不再有让人去开 HUB 或 spoke 的说法 | 已核：全仓搜过，剩下的只在技能里讲「不做」的那几处与历史记录里 |
| 宿主在真实会话里加载到的是新技能 | **未验证**：技能定义按会话固化，要负责人开一个新会话再试一次「开 HUB 派 spoke」 |
| 真实会话里的拒绝是否同样站得住 | **未验证**：试派里技能是被点名要求照办的唯一一份指令；真实会话里它与别的指令、更长的上下文并存，用户也可能不止坚持一次 |
| 「一个会话一棵工作树」之后收工钩子对派出去的写入者是否给得出读数 | **未验证**：`SubagentStop` 一端还没有在真实会话里见过（见[钩子说明](../hooks/README.md)） |
| Codex 一端 | **未验证**：没有试派 |
| 拒绝的说法对提要求的人有没有用 | **说明不了**：这里只看了 agent 说了什么，没有看人听了之后怎样做 |
| 按先后做是否真的比并行快、好 | **说明不了**：没有做对照；依据的成色见上 |

出现下面任一情形时回头看这次重构：agent 在真实会话里被坚持几次后开了第二棵树或派了并行的写入者；
拒绝的回话长到没人读完，或被反映为说教；负责人需要一个会话带着几个互不相干的单元推进而另开会话行不通；
上面第三条依据的作者又换了立场——那时改的是技能里那一页引文，裁决本身不随之变。
