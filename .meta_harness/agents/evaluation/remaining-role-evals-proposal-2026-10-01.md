## 一、五个角色的流

### product-design-reviewer：判一份产品设计稿

- **它像谁**：与 design-reviewer 的三个流同一类（评审类，判官逐条判「这处种入有没有被报出」）。运行器不用改。
- **用例来源**：一份真实的产品 topic 包（钉在历史提交上）加种入——规则与它自己的场景对不上、同一个概念定义了两次、一条场景属于两张卡、
  未决项被填了一个看起来合理的默认值、技术实现混进正文、推测写成了拍板。另加一份不种入的对照。
  真实案例可以从 PF-017、PF-020、PF-021 的 `decisions.md` 里记下的评审发现反推（那三份记着当时评审提了什么、作者怎么处置）。
- **判定**：判官，沿用 design-reviewer 那一套校准办法；这个角色明令「不评设计品味与方向」，所以另数一项「越界的意见条数」。
- **量不出**：产品方向对不对；它在一份真正难的稿子上的表现——种入的缺陷比真实的显眼。
- **要你定**：真实案例取哪几份。

### product-design-drafter：从一条需求写出一份可评审的产品设计

- **用例来源**：三四条小而完整的需求陈述（新写，不取自现有 topic，免得答案就在仓库里），各带一段故意留的东西：
  一处有两个都说得通的选择（应当进「待裁决」）；一处明确排除的范围（应当进「非目标」，不进「待裁决」）；一处只有一个答案成立的推导（应当自己定并写推理链）。
- **判定**分两层。程序：包的文件齐不齐、`make design-check` 里产品区与故事卡两项过不过、五处 rev 一致、写入范围只在指定的 topic 目录。
  判官：一张**逐条可核**的清单——每条规则有没有走过一个场景、三类记录（拍板、推导、待裁决）有没有混、故意留的那三处各落在了该落的地方没有、正文里有没有版本对比与推导过程。
  不设「写得好不好」这一项。
- **量不出**：设计质量本身；调研做得深不深。**这一项只能靠你抽查**，提案是每次基线你读其中一份。
- **要你定**：需求陈述由谁写（我起草、你改）；抽查的份数。

### spec-drafter：按施工简报写一份候选契约包

- **用例来源**：两份施工简报，各配齐对账产物与账本。简报不入库，所以要**新写**；可以拿已接受的小契约倒推出当初该有的简报（钉在契约接受之前的提交上，契约正文从副本里拿掉）。
- **判定**分两层。程序：`make design-check` 过不过；设计评审报告（`make design-review`）在产出上报出的机械项条数；登记落齐没有；写入范围。
  **行为陷阱**（程序判，看它停不停、报不报）：简报故意缺一份「已定型的共用数据契约」→ 应当停下来问；账本里缺一个必须用的名字 → 应当报回、不自造；
  留一条未决项 → 契约里应当是显式缺口，不是一个默认值；简报与对账产物互相矛盾 → 应当报。这四条正是角色正文里写的「停下来问，不猜」。
- **判官**：只判几条可核的——操作的九件事齐不齐、契约里有没有出现内核机制词与服务键（2026-10-01 起的纪律）、失败集合有没有开放式收尾。
- **量不出**：契约在语义上对不对——那是设计评审的事，这个流不替它。
- **要你定**：倒推简报用哪两份契约；陷阱是每份材料种一个，还是另开四份只测陷阱的短材料（后者干净，但多四次运行）。

### realization-drafter：按节点计划写一个实现映射节点

- **用例来源**：与上一条同法——取一个已有节点，从副本里拿掉它，给出它兑现的契约坐标、承载草图与共同约定，要它重写。
- **判定**。程序：节点对账（`make design-check` 里那一项）过不过；Cordis 符合性核对表十行是否逐行填了、「符合」的有没有指到具体小节；`bindings.yaml` 的每条绑定是否指到一个存在的测试或形式任务；写入范围。
  行为陷阱：契约坐标与登记的版本不一致 → 应当先报；契约要求「跨拥有者同一提交」→ 设计里应当指出两个写入者共同触碰的存储对象，指不出就应当记缺口而不是写一个时间谓词。
- **判官**：只判「有没有把机制写回契约」「绑定是不是空洞的」两条。
- **量不出**：这份设计实现出来对不对。
- **要你定**：取哪个节点；这个角色与 spec-drafter 是否共用同一批材料（同一份契约，一个写契约、一个写节点），那样省材料，也看得出两者的交接。

### tui-debugger：给一个现象，交一份可重跑的复现与取证

- **用例来源**：`apps/cli` 的全屏界面历史上只有三次提交，没有足够的真实缺陷可取，**只能种入**：在一份构建里种一处界面缺陷（比如某种终端答复被错误分帧、退出时终端模式没有恢复），
  给角色的只有现象描述与构建。可以与 `qa-acceptance` 共用那三份带预置缺陷的构建，再补两份界面一侧的。
- **判定**。程序：它交的复现脚本在干净副本上重跑，是否真的复现（退出码与它声明的一致）；写入是否只在证据目录；插桩是否已经还原（副本里受版本管理的文件无改动）。
  判官：它的根因假设是否指到了种入的那一处；有没有越界去「修」或去判「修好了」。
- **量不出**：只在真终端里才出现的问题——副本里没有真终端；它在一个没有种入、原因不明的现象上的表现。
- **要你定**：要不要为它搭一个能驱动伪终端的环境。不搭，这个流只能覆盖非交互的那一半，我的建议是先不搭、照实写明。

## 二、加载探针（全部角色）

要量的是另一件事：**宿主加载到的角色定义是不是我们编译出来的那一份**——能逐字引出正文里的句子、工具清单对、实际模型对。

提议做成与评估运行器同样的成对子命令（`make roles-probe ARGS="prepare|record …"`），一张表驱动：每个角色几条逐字引述题、应有的工具清单、应是的模型。
`prepare` 印出该派发的探针，主会话派 subagent（按角色名 registered 派发），`record` 读宿主留下的记录核对引述、工具与模型。

**限制要先说清**：改了角色源并重编之后，**本会话加载的仍是会话开始时的旧定义**，所以探针必须在新开的会话里跑——这一步没法自动化，只能是「你开一个新会话，说一句跑探针」。
在同一个会话里用 inline 派发（把编译出的角色文件当指令交给通用 subagent）只能证明新正文起作用，证明不了宿主加载到了它；两种结果分开记，不混。

**要你定**：这套探针值不值得做成工具。不做的话，现状是每次改角色后手工试派一次，记在各自的评估记录里。

**已定（2026-10-02）：不做。**负责人的理由：各宿主热加载角色定义的机制不一样，做成一套统一的探针没有意义。
现状照旧——改了角色之后在新会话里手工试派一次，记在那次改动自己的评估记录里。

## 三、Codex 一端

无界面的 Codex 进程与无界面的 Claude Code 进程是同一类做法，我按同一条禁令处理，没有用。于是 Codex 一端能自动做的只有静态部分（生成物、配置解析、支持记录）。
行为评估与加载核对要你在交互的 Codex 会话里做。提议是给一张**你照着做的清单**（派哪个角色、给哪份简报、看子会话日志里的哪三样），而不是一个运行器。

**要你定**：Codex 一端是否也禁无界面进程。若不禁，运行器可以加一个 Codex 宿主入口，工作量与 Claude 一端当初相当。

**已定（2026-10-02）：不禁。**负责人答复：禁的只是 `claude -p`（Claude Code 的无界面运行）；`codex exec` 这类直接运行的 Codex 命令不在禁令之内。
所以本节开头「按同一条禁令处理」的做法到此为止，Codex 一端可以给运行器加宿主入口。**入口还没有做**，什么时候做跟着基线的安排走（[#72](https://github.com/nemori-ai/omne-harness-lite/issues/72)）。

## 四、整仓检出的流怎样派发（遗留问题）

`developer-implement`、`qa-acceptance` 以及新迁的两个流，副本是整仓检出，被测角色有 shell，而仓库与模板里就有答案，
所以运行器要求派发它的会话**不在本仓库的任何检出里**，否则把那次运行记为 `contaminated`。
可是按角色名的 registered 派发要求会话开在一个有 `.claude/agents/` 的项目里——两头对不上，这是四个角色的基线至今没法跑的原因之一。

提议：`prepare` 本来就把现编译的角色定义冻结到变体目录；让它再多铺一个**派发用的空项目目录**（仓库之外，里面只有 `.claude/agents/<角色>.md` 这份冻结的定义）。
你在那个目录里开会话跑基线：角色是 registered 的，会话又不在仓库里。运行器在 `record` 时核对会话的项目目录正是它铺的那一个。

**要你定**：这个办法你接不接受（它要你为每一轮基线在一个指定的目录里开一次会话）。
