# 评审意见：`tmp/plan-under-review/plan.md` r1（候选）

**结论：本次计划范围内发现 7 条阻断问题，r1 现状不能形成可信的验收证据。** 这是评审意见，不代表规格正确，也不构成接受或放行。

- **范围**：仅这一份计划，只读，全部任务与三条前提已评完。
- **依据**：契约 `capability.run-attempt-facts/v2`、节点 `run-attempt-facts-derived` 的 `design.md` 与 `verification.md`，另读了相邻节点入口（`session-log-jsonl`、`tool-execution-runtime`、`apps/cli`）和 `session-log/v3/consumer-impact.md`。
- **未能核对的部分**：本检出里没有 `packages/`、`apps/` 源码，也没有 `design/record/evidence/`。所以实现现状只能按设计区的记录判断；HEAD 的 SHA 我无法取得（无 shell）。

## 阻断项

**B1　交付判据与验收边界脱节，V-1～V-9 多数没有任务。**
- 计划开头把验收边界定为 S-14～S-18 与 V-1～V-9，「交付判据」却写「两个包的单元测试全绿即交付完成」。
- 下列义务在 T1～T7 里找不到产出者：
  - V-2、V-3：并发与随机交错的性质测试。
  - V-5：日志换代的 `bootAssembly` 演练。
  - V-8：`tools/ts-checks` 结构规则加据点清单检查，owner 含 ts-checks 与据点装配两方。
  - V-9：与执行宿主 N-17 同一场景的真并发演练。
  - V-4、V-6：只能猜是否含在 T3 的「源码与测试」里。
- T4 改的是执行宿主，它那一侧的证据义务（节点 N-17 ①）不在验收边界内。
- 后果：按现判据，S-14～S-18 一条没跑也能宣布交付。
- 需补：判据改为逐条对到验收边界；每条 V 要么有任务、负责人和完成判据，要么明示本增量不做及理由（例如 N-17 ② 在执行宿主节点登记为受阻）。

**B2　前提 2 把上游未闭合的缺口写成已成立。**
- 计划称终结记录形状「已由 loop 那一程定下」，产品装配可直接认出「已终结」，不再留缺口。
- 已接受的材料全部相反：
  - 契约 G-3 仍开着，owner 是 loop 那一程；第十一节写明产品装配里这一读恒 `unavailable`。
  - 节点 AFD-1、AFD-4：验收里的认法是测试自定形状，「只在验收里存在」。
  - `apps/cli` 关键选择 5 与 A-27：产品清单本版不装本节点，也不得带 `runEndRecognizer`。
  - `session-log/v3/consumer-impact.md`：「生产 Run 终结认法未定；测试驱动不得关闭完整 Agent Loop 缺口」。
- 后果：照此施工会把测试形状带进产品路径，与 V-1、V-8 直接冲突；S-15 的证据也会被记成无前提通过，而节点 verification 要求记「有前提：测试给认法」、不计入实际验证完成数。
- 需补：撤掉前提 2，保留 AFD-1、AFD-4 为显式缺口。若确有新决定闭合了 G-3，那是契约新版本与节点修订的事，回 loop 那一程与主线，施工计划不能代为关闭。

**B3　T7（契约 S-17）没有负责人、开工条件和交付物。**
- S-17 在验收边界内，守的是契约的安全性质「判不出时绝不答未取代、未终结」。「时间允许的话最后统一补」等于没人负责。
- 节点 verification 给的跑法只需一个 `readSince` 恒答 `unavailable` 的日志交给闭包，T3 完成即可做，不依赖 T4、T5。
- 需补：指定负责人，开工条件挂在 T3，写明完成判据。

**B4　T6 把作者自验记为独立验收。**
- A 写了 T1～T3 又自验出报告，这是作者自查，不能记成独立证据。
- T6 也没写原始结果归谁保存，谁回填节点的 `verification.md` 与 `bindings.yaml`。
- 需补：指定非实现者执行或复核。无人可用时保留为「独立验证未完成」，不要改个名字顶上。

**B5　T4 提前消费尚未产出的共享接口。**
- 服务面类型是 T3 的交付物，T4 却在第 1 天开工，B「按自己的理解写一份本地声明」。
- 契约 S-9 只定了语义，不附 Schema；节点导出名全是候选。失败值在 TS 里怎么表示，B 只能猜。
- 「T3 完成后再对齐」没有任务、负责人和重验步骤。T4 的测试跑在 B 自己的声明上，全绿也不说明真实组合成立。
- 需补（二选一）：A 先把服务面类型作为最早的小交付并入主线，B 从那个快照开工；或写明 B 的替身服从 S-9、由谁在何时换成真类型并重验。

```
现状：T1 → T2 → T3（类型产出）
      T4（第1天开工，用自造声明）──┐  对齐：无任务、无负责人
                                   └→ T5（A、B 双写）→ T6
```

**B6　T5 的装配清单两人共写，全部工作只合并一次。**
- `apps/cli` 装配清单是共写资产，却让 A、B「各自按需修改，最后合并时解决冲突」。没有单一写入负责人，冲突的语义裁决也无人负责。
- T1～T4 攒到最后一次合并，期间 B 看不到真实类型，A 看不到宿主调用点，第一次真实组合要到 T5 之后才出现。
- T5 也没写验收装配里由谁提供代 loop 写终结的测试驱动及其认法；缺它 S-15 跑不起来。
- 需补：清单指定一名写入者；按可交付单元逐个并入主线（提供者包 → 宿主改指 → 装配），不靠一条集成分支攒到最后。

**B7　T4、T5 消费的输入无人生产，前提 1 与基线没有落到可核对的修订。**
- T4 要「删掉对替身的引用」，T5 要「删掉替身那一行」，都预设执行宿主包和带替身的验收装配源码已存在。
- 设计区记录相反：`tool-execution-runtime` 的 README 与 verification 写「尚未建包、没有一行源码」；`apps/cli` 现有源码是治理 CLI/TUI，据点形态标为后续候选。计划里没有任务生产这两样。
- 前提 1「`session-log-jsonl` 已交付并在验收装配里可用」：节点入口只记到 SL3 源码已合入 HUB 的有限签收，明说「不是完整提供者验收」，且恢复增补要求必填 `processOwnership`。
- 基线写「`main` 当前提交」，没有 SHA。
- 需补（派发者澄清）：基线 SHA；执行宿主与验收装配的实际源码修订；`session-log-jsonl` 实际可消费的修订与配置。澄清前 T4、T5 及依赖它们的 T6 无法判断可行性；T1～T3 不受影响。
