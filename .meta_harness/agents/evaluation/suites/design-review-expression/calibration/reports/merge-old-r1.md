## 阻断

**B-1 · 引用与登记（状态词与版本血缘）：可能在原地改写一个已接受、已冻结的坐标**

- **依据**：
  - `record/decisions/pr9-pr10-coordinate-reconciliation/decision.md` 第 4 条规定，原 33 份 v1 按原样迁成 v2，「146 项迁移资源发到新坐标并冻结」。
  - 同一决定的 `acceptance.json` 登记本契约 v2 的 S-1..S-18 为已接受。
  - `version-migrations.json` 记录了 v1→v2 的 identity 映射，目标 hash 为 `62ff6354…`。
  - D-061 接受的是 **v1**。
  - topic README 写的是「accepted、资源已冻结」。
  - 同批的 `session-tenancy`、`session-log` 等 v2 都还在 `frozen.json` 里，只有本契约缺席。
  - `design/spec/README.md`：已发布的版本不能原地改写。
- **触发场景**：v2 已被接受且冻结，已接受的消费者 `capability.tool-execution-runtime/v2` 按 S-5、S-6、S-9 钉在它上面。现在 v2 被改回 candidate 并原地修订。
- **后果**：
  - 已冻结消费者依赖的条款在它不知情的情况下变了。
  - 契约页首在说「已接受」，登记在说「candidate」，两处都不能当依据。
  - `verification.md` 的「变化的影响」最后一条停在 2026-09-25，所以 2026-09-26 接受之后的这一轮修订没有留痕。§十三自己要求每次原地修订都记在那里。
- **作者需明确什么**：
  - 如果 v2 确实已接受并冻结，这一轮必须作为 **v3** 发布，同时恢复 v2 在 catalog 和 frozen 中的登记。
  - 如果有权者已经明确撤销了 v2 的接受，要指出那份决定，并把页首、§十三、topic README、verification 都改成同一种说法。
  - **问派发者**：v2 改回 candidate，有没有接受方的授权记录？

**B-2 · 表达歧义 / 完整性：身份参数有默认值**
- **位置**：S-9 ①「`session`（`SessionRef`；缺省时取调用方当前所在的会话）」。
- **依据**：本契约 S-8 写明会话、运行、尝试缺一即 `invalidInput`，「不从进程上下文或『当前那次尝试』补」；`data.identity-values/v1#S-17`、`#S-18` 也是同样要求。
- **触发场景**：调用方漏传 `session`。
- **后果**：
  - 同一份契约里，对同一件事有两种字面相反的说法。
  - 照 S-9 实现的提供者会从上下文补出会话，越权的路径就从「传错」变成了「不传」。
  - S-11 第 3 行已经点明：拿到一个会话指认就能探知别人的运行进度。
- **作者需明确什么**：删掉 ① 的默认值，让 ⑥ 把「`session` 缺席」明确列入 `invalidInput`。

**B-3 · 表达歧义：允许只回答一半**
- **位置**：S-9 ⑤「`runEnded` 认不出时可以省略，只给 `superseded`」。
- **依据**：
  - S-8 写明「两件事实要么一起答出，要么一起不答」，提供者认不出终结记录时答 `unavailable`。
  - G-3、examples §4 最后一行、M74「不给过渡值」都是同一个口径。
- **触发场景**：在产品装配里（G-3 尚未闭合），一个后台工具在运行终结之后收场，读到 `{ superseded: false }`。
- **后果**：消费者 `tool-execution-runtime/v2` 的 S-13 只处理三种情况：两件事实都给出、`attemptNotFound`、`unavailable`。遇到只回一半的答复，它只能把缺的那一项当成假，于是写成「不晚」。这正是 I-11 主路径上**系统性的漏标**，超出了 S-6 第 4 条声称的「只在窗口里漏标」。
- **作者需明确什么**：删掉 ⑤ 的后半句。

**B-4 · 完整性 / 可实施性：失败集合不封闭，判定次序有两种读法**
- **位置**：S-9 ⑥「…；其他错误由提供者自定」。
- **依据**：§四开头要求 ⑥ 是「闭合枚举，按判定次序」；S-8 失败值总表自称「本契约的全部失败值」。
- **触发场景**：提供者自己定义了一个新错误值返回。
- **后果**：消费者在 S-13 和 S-15 里只给 `attemptNotFound` 和 `unavailable` 两个值准备了分支，遇到新值时由实现自行决定放行还是拒绝。
- **作者需明确什么**：
  - 删掉「其他错误」，或者把它要承载的情形逐项列进总表。
  - 同时写明 `unavailable`（认不出终结记录）和 `attemptNotFound` 谁先判，相关处理见 N-2。

**B-5 · 跨契约一致 / 归属越界：在途的读被命令按「仍是当前」处理**
- **位置**：S-12 第 2 条「调用方可能等不到回答，按『仍是当前、尚未终结』处置，以免挡住落账」。
- **依据**：
  - 本契约 S-8、S-9 ⑧「不答『未取代、未终结』」。
  - 安全性质表中「判不出时答『未取代、未终结』」一行，以及 M74「不给过渡值」。
  - 消费者 `tool-execution-runtime/v2` 的 S-13 和 S-15 规定：读不到就 `dependencyUnavailable{runAttemptFacts}`，**不写缺席的 `late`**。
- **触发场景**：提供者在一次读进行到一半时被撤除或重启。
- **后果**：
  - 本契约在规定消费者怎么处置，而这件事归消费者自己的契约，那份契约已经给了相反的规定。
  - 照这一条实现，就会写下缺席的 `late`，也就是一个没判出来的「不晚」。
- **作者需明确什么**：改成「在途的读没有答复，消费者按自己契约中读不到的那一行收场」，并给出坐标，不规定任何过渡值。

**B-6 · 形式对应：声明的形式证据不存在**
- **位置**：§六 进展性质第 1 行「（已由 TLC 在本契约的行为模型上检查）」。
- **依据**：
  - 本契约 S-13 写的是「不建形式模型」。
  - `verification.md` 的「形式工件：无」。
  - topic README 的「formal-tasks 映射：无」。
  - `formal-tasks.json` 中没有本契约的任务。
- **触发场景**：读者或接受方把这一行当成已有的证据。
- **后果**：声明的证据范围超过了实际有的证据，从条款到性质再到配置的那条链是断的。
- **作者需明确什么**：删掉这句括注；或者真的建模型并登记任务，再相应修改 S-13。

**B-7 · 归属越界 / 跨契约一致：规范条款里写了 Cordis 机制，还依赖一个不存在的事件**
- **位置**：S-7 第 2 条「提供者以 `ctx.inject(['sessionLog'])` 取得日志服务，并在每次调用里先 `await ctx.serial('session-log/flush')` 再读」。
- **依据**：
  - 能力契约不应写具体服务键和库调用（归属表）。
  - `capability.session-log/v2#S-20` 写明「不发、也不监听任何事件」。
  - 「读看得见调用开始之前的提交」本来已经由 `session-log/v2#S-13` 第 1、4 条给出。
  - 本契约 S-5 第 4 条还允许提供者用别的存放。
- **触发场景**：有两种实现：一种在会话日志提供者里加一个 `session-log/flush` 监听，这就违反了那份契约；另一种把它当作空操作。
- **后果**：两种实现的行为不同。这条「机制」实际上什么保证也没提供，却被写成了 S-7 的兑现方式，而且和 S-5 第 4 条允许的存放方式冲突。
- **作者需明确什么**：S-7 第 2 条只写性质，依据是 `session-log/v2#S-13`；机制交给提供者节点。

**B-8 · 引用与登记：catalog 依赖一个不存在的条款**
- **位置**：`catalog.json` 中本契约对 `data.messages` v2 的 clauses 写着 `["S-20","S-24","S-97"]`。
- **依据**：
  - `data.messages/v2` 正文里没有 S-97。
  - 本契约 S-4 只列了 S-20 和 S-24。
  - 页首写明「catalog 按它登记」。
  - 判定规则见 `registry/README.md`。
- **后果**：依赖声明指向一个不存在的条款。按 catalog 做的依赖闭包和影响分析会出错。
- **作者需明确什么**：从 catalog 删掉 S-97；如果确实要消费某一条，就在 S-4 补上，而且那一条必须真实存在。

**B-9 · 引用与登记：产品依据的 rev 过期**
- **位置**：第 7 行「设计依据（PF-012 rev 14）」。
- **依据**：`product/README.md` 显示 PF-012 当前是 **rev 21**。changelog 中：
  - rev 15 改了 §4、I-11 和尝试栅栏的范围（「只拒绝推进运行的旧写入」），这几处都被本契约 S-5 和性质表引用。
  - rev 16 允许投影持久化，而 §十一「另存一张表…所以不存」的论证建立在 rev 14 的措辞上。
- **后果**：按规则，依据 rev 和当前 rev 不等即判失败。我没有在被引的正文里发现和 S-5 相矛盾的语义，但被引的小节确实改过，需要作者重新核一遍。
- **作者需明确什么**：逐个核对被引小节在 rev 21 下是否仍然成立，然后把 rev 改到当前值；不成立的地方登记为缺口。

**N-2 · 可实施性：产品装配下的行为在几处说法不一致**
- **位置**：
  - §十一说「产品装配里这一次读恒收 `unavailable`」。
  - S-9 ⑥ 把 `attemptNotFound` 排在「认不出终结记录 ⇒ `unavailable`」之前，存在两种读法：前者是第三步，还是可以随时出现。
  - 规范场景 S-14、S-16、S-18 和 examples §1–§3 都没有写明是哪种装配；在产品装配里，它们要求的 `runEnded: false` 或 `attemptNotFound` 都不可能出现。

- **触发场景**：在产品装配里读 `(s1, R, 7)`。
- **后果**：实现会在 `attemptNotFound` 和 `unavailable` 之间分成两派，场景演练的判定也会分歧。消费者把这两个值合并处理，所以不影响落账。
- **作者需明确什么**：
  - 写明产品装配下的判定次序。
  - 给 S-14、S-16、S-18 和 examples 标上「验收装配」前提。
  - 给进展性质第 1 行补上 G-3 前提。
