# design-reviewer 判「表达」

量的是：给 [design-reviewer](../../../roles/design-reviewer/role.md) 一份候选规格和派发者附上的设计评审报告、
让它判「表达」这一种，它能不能把规格里的已知缺陷报出来，同时保持只读、只做这一种判断。
判据页是手册的 `references/review/expression.md`。被测的是**一整套**：角色正文、判据页与工具输出；分不出各自的贡献。

状态：用例与判定方法已采用；完整基线尚未运行。当前配置和采用范围见 `flow.json`。

模型：Claude Opus 5.5、xhigh。角色文件钉的是 Fable 5.1，判「表达」时派发可换 Opus 5.5
（[角色说明](../../../roles/README.md#按判断对象选择-reviewer)）；本用例集在 Opus 5.5 上量。

## 材料

| 材料 | 是什么 | 应当被报出 | 来源 |
|---|---|---|---|
| `raf-contract` | `capability.run-attempt-facts` v2，改成 candidate 后种入 | 9 处（E1～E9）：3 处工具核得出，6 处靠判断 | 明确种入的案例输入 |
| `raf-contract-clean` | 同一份契约，只改成 candidate、不种入 | 无（对照） | —— |
| `https-json-r1` | 治理中心入口的传输绑定契约 v1 首稿，第一轮评审之前的快照 | 13 处 | 固定缺陷样本；预期问题见 truth.json |
| `entry-r1` | 治理中心入口契约 v1 候选包（含 Schema 与 TLA+ 模型），第一轮评审之前的快照 | 16 处 | 固定缺陷样本；预期问题见 truth.json |
| `account-identity-v2-r1` | `capability.account-identity` v2 候选稿，第一轮评审之前的快照 | 8 处 | 固定缺陷样本；预期问题见 truth.json |

必要输入封装在各材料的本地夹具中；相邻资料不得泄露预期答案。
E3（失败集合开放式收尾）由判断识别：这份契约没有九件事定义表，工具无法判定它。

## 判官校准

[calibration/cases.json](calibration/cases.json) 与 `calibration/reports/` 是判官的已知好/坏输入，
保留人工期望值、逐字引用和运行级判定规则。判官由主会话派 subagent；
每次校准的输入、输出与比对结果放本工作树 tmp，不持久保存运行流水。
已知问题与表外发现分别计数，判据改变后须复核适用范围；未校准材料不能冒充已验证。

## 量不出什么

- 种入的 9 处是主会话写的，比真实待审稿里的问题更显眼，写的人与被测模型同源。
- 同一份材料里的几处问题由同一份报告判，不独立；三份真实材料都出自治理中心那一程、同一天的评审。
- 真实案例当时是由上一代评审角色（spec-reviewer，同一种模型家族）找出来的：它们量的是「现在的角色能不能找回当时找到过的问题」，
  量不出当时也漏掉的问题。
- 判据页的「跨契约批次核对」（同一批多份契约放在一起才看得见的不一致）没有材料覆盖。
