## 阻断

### B-1 T4、T5 的输入无人生产（已证实的矛盾，以实现映射为准）

- **类别**：无人生产的输入。
- **位置**：目标后半句；T4；T5。
- **依据**：
  - 实现映射 README 工具领域一段与 `tool-execution-runtime` README：执行宿主「尚未建包、没有一行源码」。
  - `apps/cli/verification.md` 第 78 行：这条据点义务的闭合条件是「执行宿主建包、验收装配存在」。
  - `apps/cli/README.md`：现有 `apps/cli` 源码是治理 CLI/TUI，据点形态是「后续候选」。
  - 判据页：能力已定义但提供者未完成属于实施工作。
- **触发场景**：B 第 1 天开工 T4，要「改指」并「删掉对替身的引用」，但按映射没有执行宿主源码。T5 要改的验收装配清单同样没有。
- **后果**：T4、T5 无从下手；T6 的装配级演练和 V-5、V-9 随之受阻；目标里「让执行宿主改用它」在本计划内不可达。
- **作者需明确**：二选一写清。要么给出执行宿主与验收装配已存在的精确源码修订（映射随之应有记录）；要么把它们列为前置依赖，写明负责者、依赖任务何时放行、本增量在它们到位前的可验收范围到哪为止。

### B-2 前提 2 把未闭合的上游缺口写成既定事实（已证实的矛盾）

- **类别**：把猜测写成已成立前提；上游依赖条件。
- **位置**：前提 2，波及 T3、T5、T6 的 S-15。
- **依据**：
  - 契约 S-2、G-3：终结记录形状「本版不收」，owner 是 loop 那一程；闭合前提供者答 `unavailable`。
  - 契约第十一节与 D-060 §八 N-37 ④：产品装配里这次读恒 `unavailable`。
  - 节点 design 关键选择二、AFD-1、AFD-4、AFD-7、「归装配的事项」：认法只在验收装配给。
  - 节点 verification V-1、V-8：产品清单配置不带 `runEndRecognizer`。
  - `session-log/v3/consumer-impact.md`：「生产 Run 终结认法未定；测试驱动不得关闭完整 Agent Loop 缺口」。
  - 我在 `record/decisions` 里没有找到闭合 G-3 的决定。
- **触发场景**：实施者照前提 2 把测试驱动自定的记录形状内建为认法，或在产品清单里给出认法。
- **后果**：
  - 产品装配会按一个只在验收里存在的形状答「已终结」，与契约 S-8、G-3 相抵。
  - V-1、V-8 变成不可能通过，或被默默删除。
  - S-15 的证据会被当成实际验证；节点 verification 的共同前提要求它记「有前提：测试给认法」，不计入完成数。
- **作者需明确**：
  - 给出闭合 G-3 的决定坐标；给不出就撤掉前提 2。
  - 撤掉后要补：认法作为仅验收装配的配置由谁提供（代 loop 写终结的测试驱动归谁）、哪个任务交付它、S-15 的结果怎样标注。
  - 计划不能自行关闭 G-3，应回到 loop 那一程或主线。

### B-3 T4 提前消费尚未定型的服务面，且只在最后合并时相遇

- **类别**：提前消费；并行写入共用未定型接口。
- **位置**：T4 开工条件；T3 交付物；「并行与合并」。
- **依据**：
  - 判据页：依赖共享边界的开发须先取得可消费的明确版本或快照。
  - 节点 design「公开面」：名字全部候选、全部尚未实现。
  - 契约 S-3：不附 Schema，所以失败值在代码里怎样表示契约没有定。
- **触发场景**：B 的本地声明与 A 的 T3 导出不一致，例如失败值是抛出还是返回、成员名、同步还是异步。
- **后果**：B 的单元测试对着自己的声明全绿；分歧到最后一次合并才暴露。「T3 完成后再对齐」没有负责人，也没有重验步骤。叠加 B-7 的交付判据，两个包从未真实组合也会被记为交付完成。
- **作者需明确**：
  - 服务面类型的单一写入者是谁，在哪一步作为可消费快照发布。
  - B 在那之前按什么写：应是已接受契约的 S-8、S-9 与执行宿主节点的失败映射，而不是「自己的理解」。
  - 对齐后的重验由谁做。

### B-4 T5 的装配清单两人共写、合并时解冲突，没有单一写入者与集成者

- **类别**：重叠写权；无负责人收尾的交接。
- **位置**：T5「负责」与「开工条件」两列；「并行与合并」。
- **依据**：
  - 判据页：装配等共写资产要有单一写入负责人，工作树隔离与最后统一合并不能代替共享语义收敛。
  - 节点 design「归装配的事项」：只装一份、装在根上，认法只在验收给。
  - 节点 verification 独立评审 B-5：清单检查归 cli 节点认领。
- **触发场景**：A 加插件行和认法配置，B 删替身行并改执行宿主的取用，各在自己的工作树里改同一份清单。
- **后果**：冲突按文本消解。结果可能是替身与新插件同时提供 `runAttemptFacts`，也可能两者都不在。没有人对装出来的清单负责，V-8 的清单检查也无人接。
- **作者需明确**：清单的唯一写入者；谁做集成并对组合结果负责；cli 节点 owner 认领的清单检查由哪个任务交付。

### B-5 T6 把实施者自验记为独立验收

- **类别**：验收独立性。
- **位置**：T6「负责」列。
- **依据**：判据页（不把作者自查记为独立证据；验收与实现出自同一写入者时指出哪条验收失去独立性）；`handoff.md`（不把自检标成独立评审）。

- **后果**：S-14、S-15、S-16、S-18 四条全部失去独立性，报告不能作为验收证据被消费。报告也没有写明原始结果归属哪里。
- **作者需明确**：
  - 独立执行者是谁。
  - 在哪个修订上跑（应是合入后的实际参与版本）。
  - 原始结果落到哪里，谁回填节点 `verification.md` 与 `bindings.yaml`。
  - 没有独立执行者时如实保留「未完成」。

### B-6 验收边界里的 S-17 与多条 V-n 没有任务、负责者或完成判据

- **类别**：证据无负责人；以「最后补测试」代替。
- **位置**：T7；验收边界一行；T2、T3 的交付物。
- **依据**：
  - 计划自己把 S-14～S-18 和 V-1～V-9 列为验收边界。
  - 契约第六节：S-17 守的是安全性质「判不出时答未取代、未终结」。
  - 节点 verification 的 S-17 一行：做法是交给闭包一个 `readSince` 恒答 `unavailable` 的日志，T3 完成即可跑。
  - 节点 verification 的 V-8、V-9 owner 列：分别需要 ts-checks owner 加据点装配、执行宿主节点共同参与。
- **触发场景**：时间不够，T7 不做；T2、T3 的「单元测试」没有对到任何 V-n。
- **后果**：
  - 最重要的那条安全性质没有证据。

  - 计划声明的验收边界没有可执行路径。
- **作者需明确**：
  - S-17 的负责者、开工条件、交付物。
  - V-1～V-9 逐条对到任务、负责者与证据形式。
  - V-8、V-9 涉及的外部 owner 怎样接入。
  - V-9 如实记为「已知缺口的记录」，不作通过判据。

### B-7 交付判据与计划自己的验收边界相抵
