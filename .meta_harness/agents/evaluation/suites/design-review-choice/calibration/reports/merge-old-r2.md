## 阻断

### B-1　以「进程内会话级互斥锁」宣称闭合契约 G-2

- **类别**：投影对齐 / 纪律失守
- **位置**：`design.md`「契约责任到插件、服务与操作」表后一段（L92）首句。
- **依据**：
  - RAF S-3「不与调用方的写同成同败」、S-6 第 4 条、G-2（闭合条件是「落账与两件事实的写入有一个共同存储对象」，owner 是主线与会话日志／loop 那一程）、S-2「本契约不拒任何写」。
  - RAF S-13：G-2 闭合时那个协议才需要行为模型。
  - `session-log/v2#S-14` 第 4 条：「不靠进程内锁、不靠时间谓词：旧实例的锁新实例看不见」。
  - 节点内部：同段末句写「不以时间谓词或进程内锁顶替」；README L18、AFD-2、`verification.md` V-9 都写窗口闭合不了。
  - 旁证：`tool-execution-runtime/design.md` L199「进程内锁挡不住另一个 owner 的提交」；`apps/cli/design.md` A-24「漏标窗口仍在」。
- **触发场景**（三条交错）：
  1. **换代**：锁由本实例持有并导出。`sessionLog` 换代使本插件重跑（关键选择三），产生新实例和新锁。执行宿主「调用时现取、不重跑」，仍握旧锁并读得「仍是当前」；loop 取到新锁，无竞争地落下尝试 2 开始；执行宿主提交，`late` 缺席。窗口原样存在。若把锁改成模块级全局以躲开换代，它就成了任何 fiber 之外的隐藏全局状态，装卸表里也没有它。
  2. **不经锁的写入者**：栅栏在日志提交点上判，`append` 契约不要求取锁。「loop 写尝试开始时取同一把」是加给 loop 的义务，而 loop 那一程的契约尚未起草（G-1）。同一日志根上的第二个进程实例完全看不见这把锁，S-11 表里也没有这一行。
  3. **进展**：锁跨执行宿主的整个存储事务持有。宿主在途被撤或事务挂住时，loop 写不下尝试开始，没有上界。一个只读节点由此成了另一 owner 写路径的闸门。
- **后果**：
  - 消费者若据首句认为窗口已闭合，`data.call-accounts/v2#S-39`「缺席即确定不晚」会被当作已兑现，实际仍会漏标。
  - 这是跨 owner 的协调责任，没有任何契约认领，却写进了提供者。
  - `bindings.yaml` 为空，而 V-9 预期窗口存在，闭合声明没有任何会因它失败的断言。
- **作者需明确**：本节点对 G-2 的立场只能是一个。要么维持「不闭合」并删去锁；要么确要闭合，那是契约新版加行为模型的事，回 `spec/` 与主线，不在节点里做。
- **为什么本阶段必需**：执行宿主 T-4 与 N-17、cli A-24 都按「窗口仍在」设计；这句话被接受，就等于在节点层改写了已冻结契约的 S-3 与 G-2。
- **能否一处措辞闭合**：不能。删句只恢复一致；首句代表的是一个选择（导出锁，并要求两个外部 owner 取锁），需要作者明确撤回。

### B-2　读面被转发成 HTTP 入口，「调用方身份已核实」改写为「不需要核实」

- **类别**：投影对齐（装配给与协议给）/ 纪律失守
- **位置**：`design.md`「装配给与协议给」表第三行（L156）。
- **依据**：
  - RAF S-11 第三行：单机由装配给，即「据点进程内的能力间面」；跨边界要重新验证；「本契约的面不得直接暴露成终端 API」。
  - RAF S-8 末：「不直接暴露给人或 agent」。
  - 节点内部：紧随其后的「归装配的事项」写「不暴露成入口」。
  - `apps/cli/design.md` 里没有任何转发 `attemptFacts` 的 HTTP 入口。
- **触发场景**：外部工具拿到一个 `SessionRef`，经 HTTP 入口调 `attemptFacts`，没有调用方身份和租户判定。
- **后果**：
  - 「拿到会话指认就能探知别人的运行进度」，这正是 S-11「做不到会怎样」列的后果，同时越过跨租户默认拒绝。
  - 入口一旦存在就是跨进程调用，S-11 右列三条「协议给」全部到期，而本节点声明「右列一条都不兑现」。
  - 节点替装配声明了一个装配里不存在的入口；「归谁」列为空，这条保证没人认领。
- **作者需明确**：这一行应回到「装配给：进程内能力间面，不暴露入口」，并说明由谁的哪条检查守住（V-8 目前只守「不 inject storage」与「产品清单不带认法」）。「外部工具查运行进度」若是真需求，列入范围外待裁决。
- **为什么本阶段必需**：装配给与协议给的拆分是本次评审范围本身，而该行与已接受契约直接相反。
- **能否一处措辞闭合**：改动落在一行，但它是撤回一个暴露面的选择，不是改措辞；若保留需求则牵动契约。

### B-3　日志读不到时以缓存作答

- **类别**：性质承载 / 投影对齐
- **位置**：`design.md`「状态、并发与失败映射」表第二行（L130）。
- **依据**：
  - RAF S-7 第 2 条（那一刻不早于调用开始）、S-8（读不到即 `unavailable`）、S-9 ⑥⑧、S-17（「不交回任何真值」）。
  - RAF S-11 第一行的「做不到会怎样：漏标扩大到任意长」。
  - 节点内部：关键选择一写「每次调用仍真读一次日志，S-7 第 2 条不打折扣」；投影表 S-9 行写「读不到 ⇒ `unavailable`」；FR-4；`verification.md` S-17 行。
- **触发场景**：
  1. 缓存停在 tail=20（尝试 1 仍是当前）；位置 21 落下尝试 2 开始并成功返回；此后一次调用的 `readSince` 答 `unavailable`。节点交回 `{superseded:false, …}`，这是调用开始之前的旧事实。
  2. 缓存为空（首次调用或刚被逐出）且读不到：对空状态作答得 `attemptNotFound`，一个「读得到、确实没有」的结论，而实际根本没读到。`verification.md` S-17 那一支按现设计跑会直接失败。
- **后果**：
  - 「缓存是精确的」只说明它等于某个旧前缀，不说明它不早于调用开始。
  - 契约的进展性质（提交返回后的第一次读即答「已被取代」）失去保护点。
  - 日志持续不可用期间，漏标窗口从「读到提交之间」放大到任意长。
- **作者需明确**：读不到时的映射。按契约是 `unavailable`、缓存不动。若认为旧前缀作答有价值，那是对 S-7 的放宽，回契约。
- **为什么本阶段必需**：它违反的是契约安全性质表第一条，也是执行宿主 `late` 判定的直接输入。
- **能否一处措辞闭合**：单元格一处可改，但该行附了理由（「不必失败」），属于一个与 S-7 相反的选择，需作者明确撤回。

### B-4　认法或折叠抛出时以 `runEnded: false` 顶替

- **类别**：投影对齐 / 性质承载
- **位置**：`design.md` 失败映射表「认法抛出、折叠抛出」行（L135）。
- **依据**：
  - RAF S-8：「绝不以 `false` 顶替一件判不出的事实」「两件事实要么一起答出，要么一起不答」。
  - 节点内部：依赖表 L99「认法抛出 ⇒ 缺陷，原样上抛」；`verification.md` V-6「不折成 `unavailable`、不以 `false` 顶替」。
- **触发场景**：终结记录已在日志里，认法在它（或同段另一条）上抛出，节点答 `{superseded, runEnded:false}`，执行宿主据此落一笔不带 `late` 的账。若水位此时已越过那条记录，它再也不会被重认，`runEnded` 永久为假；设计没有写抛出时水位动不动。
- **后果**：运行已终结之后才到的账被当作「不晚」，契约安全性质「判不出时答未终结」被直接违反；同一情形三处写了两种相反处置，实现者无从取舍。
- **作者需明确**：抛出时的唯一处置（上抛或 `unavailable`，都不交布尔值），以及该次折叠的水位与部分折叠结果是否回退。
- **为什么本阶段必需**：这是 S-8 的核心禁令，且节点内部互相矛盾，不能据此实施。
- **能否一处措辞闭合**：统一三处措辞可消矛盾，但水位在抛出时的行为是未写的设计点，不止措辞。

### B-5　撤除路径：在途调用答 `attemptNotFound`，且安全论证依赖内核有序异步清理

- **类别**：投影对齐（装卸配对）/ 反向核对
- **位置**：`design.md`「成对的装载与撤除」表第二行（L143）与表后「`sessionLog` 换代时收掉什么」（L146）。
- **依据**：
  - RAF S-12：撤除时在途的读按 `unavailable` 处置。
  - RAF S-8：`attemptNotFound` 是「读得到、确实没有」的结论。
  - `basis/cordis/effect-disposal-concurrent-not-ordered`：各 effect 按逆注册序取出后由 `Promise.all` 并发驱动，「逆序只约束取出，不约束完成」；该条目把依赖 effect 之间的清理顺序列为已知误用。
  - 节点内部：持有表 L40 与失败映射 L136 写已撤答 `unavailable`；L146 末句写「本节点照答 `unavailable`」。
- **触发场景**：
  1. 换代或撤除时，在途调用被以 `attemptNotFound` 收场，一个没有读出来的结论。
  2. L146 称「内核按登记的逆序逐个 `await` 每个 effect 的异步清理，所以服务一定先撤回、缓存后清空」。这与 basis 读数相反：缓存 effect 与 `provide` 的 effect 是两个 effect，完成次序不受保证。
  3. 与 B-3 叠加：旧日志对象关准入后答 `unavailable`，再对已清空的缓存作答，同样得 `attemptNotFound`。同一条路径上，设计给出了三种不同答案。
- **后果**：
  - 当前唯一消费者把两个值都收成 `dependencyUnavailable`，所以今天没有可观察差异；但公开函数面的其它消费者会把它当结论。
  - 真正的保护点应是「每次 `await` 之后、折叠与作答之前复查撤除标记」，设计没有写；写下的保护点是内核不提供的次序。
  - `verification.md` V-1～V-9 没有一条覆盖撤除或换代时的在途调用。
- **作者需明确**：在途调用的唯一收场值；保护点落在节点自己的哪一步，不依赖 effect 间完成次序；对应的证据义务。
- **为什么本阶段必需**：装卸配对是本次范围；所引的上游行为与已核对的 basis 条目相反，据此实施会把安全性挂在不存在的保证上。
- **能否一处措辞闭合**：收场值一处可改；次序论证需换保护点并补证据义务，不止措辞。
