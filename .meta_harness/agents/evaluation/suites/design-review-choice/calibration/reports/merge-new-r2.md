## 阻断

### 1. 用进程内锁充当共同存储对象，并声称闭合 G-2
- **类别**：投影对齐 / 纪律失守
- **位置**：`design.md`「契约责任到插件、服务与操作」表后一段首句（:92）。同段后半、`README.md` :18、AFD-2、`verification.md` V-9 都写「闭合不了／如实存在」，节点内互斥。
- **依据**：
  - 判据「投影对齐」行：进程内锁不算共同存储对象。
  - 契约 S-3 第 1 条、G-2（闭合须有共同存储对象，并出新版或被取代）、S-13（G-2 闭合时才需要行为模型）。
  - `session-log/v2#S-14` 第 4 条。
  - 执行宿主节点 R-T3「本节点不加进程内锁」，及其「跨 owner 的现读」段「进程内锁挡不住另一个 owner 的提交」。
- **触发场景**（两条交错）：
  - **换代**：执行宿主持旧实例的锁读得「仍是当前」。此时 `sessionLog` 换代，本插件按关键选择三重跑，新实例是一把新锁。loop 取新锁落下尝试 2 开始，执行宿主随后提交，`late` 缺席。
  - **不取锁的写入者**：栅栏只在日志提交点判，不认谁持锁。任何不经这把锁的追加者（另一进程里醒来的旧协程、不 import 本包的 loop 提供者、验收的测试驱动）在读与提交之间落下更大序号，同样漏标。
- **后果**：
  - `data.call-accounts/v2#S-39` 的读者被告知窗口已闭，实际仍漏标。
  - G-2、G-18、C-16 可能据此被误销。
  - 执行宿主与 loop 被加上「取同一把锁」的义务，两边都没认领，执行宿主明文相反。
  - 公开面多出契约外的导出物，与 README「只兑现窄口」相抵。
  - 若保留闭合声明，S-13 的行为模型义务被触发，而 `bindings.yaml` 为空，这条绑定即成空洞。
- **作者需明确**：本节点是否声称闭合 G-2。
  - 不声称：撤回锁与闭合声明，全节点统一到 AFD-2。
  - 声称：指出两个写入者共同触碰的落盘对象，回 `spec/` 出新版，并由执行宿主与 loop 两侧认领。
- **为什么本阶段闭合**：接受后它会成为「G-2 已闭合」的依据。
- **是否一处措辞可闭合**：否。它牵动导出面、两个外部节点的义务和 V-9 的方向。

### 2. 日志读不到时以缓存作答
- **类别**：性质承载 / 投影对齐
- **位置**：`design.md`「状态、并发与失败映射」表第 2 行（:130）。与同文件 S-9 行（:87）、FR-4、关键选择一「每次调用仍真读一次，S-7 第 2 条不打折扣」、`verification.md` S-17 行互斥。
- **依据**：契约 S-8 表第 2 行、S-9 ⑥⑧、S-7 第 2 条、场景 S-17「不交回任何真值」、S-11 第 1 行「做不到会怎样」。
- **触发场景**：缓存水位停在 t0。loop 落下尝试 2 开始并成功返回。之后执行宿主调用，`readSince` 答 `unavailable`，节点按 t0 的前缀答 `{superseded:false, runEnded:false}`。
- **后果**：
  - 答的是早于调用开始的一刻，S-7 第 2 条失守。
  - 漏标从 G-2 的「读后到提交前」扩大到「日志读不到期间任意长」。
  - 消费者拿到成功值而不是 `dependencyUnavailable`，安全性质「判不出时答未取代、未终结」失去保护点。
  - 「缓存精确」只对已折前缀成立，不对「调用开始那一刻」成立。
- **作者需明确**：这一行取哪种映射。若要保留缓存作答，那是 S-7、S-8 的语义变更，回 `spec/`。
- **为什么本阶段闭合**：这是契约的安全性质，S-17 按此设计必然不过。
- **是否一处措辞可闭合**：改一格能消除矛盾，但它是带理由的行为选择（「不必失败」），不是笔误，仍列阻断。

### 3. 认法或折叠抛出时以 `runEnded: false` 作答
- **类别**：性质承载
- **位置**：`design.md` 失败映射表「认法抛出、折叠抛出」行（:135）。与依赖表（:99「缺陷，原样上抛」）、`verification.md` V-6（「不以 `false` 顶替」）互斥。
- **依据**：契约 S-8「绝不以 `false` 顶替一件判不出的事实」「两件事实一起答或一起不答」；六节安全性质第 1 行；进展性质第 2 行。
- **触发场景**：验收装配里，认法在终结记录那条条目上抛出，节点答 `runEnded:false`，而终结记录就在日志里。设计没说这条条目算不算已折：若水位已越过它，此后每次读都答 `false`。
- **后果**：半截答复加漏标；一次缺陷被缓存固化成永久错误答案，「终结记录提交之后开始的读都答已终结」失守。
- **作者需明确**：三处取哪一个；抛出时水位与已折状态如何处置（不前进或丢弃）。
- **为什么本阶段闭合**：安全性质的保护点在两份文件里指向相反，实施者无从选择。
- **是否一处措辞可闭合**：否。还缺「抛出时水位怎样」这一决定。

### 4. 「调用方身份已核实」被判为不需要，并声称 HTTP 入口直接转发
- **类别**：反向核对 / 内核负面清单（权限边界）
- **位置**：`design.md`「装配给与协议给」表第 3 行（:156），「归谁」列为空。与同节末段「不暴露成入口」（:158）互斥。
- **依据**：
  - 契约 S-11 第 3 行（装配给：据点进程内的能力间面；「不得直接暴露成终端 API」）、S-8 末「谁调用」、S-9 ②。
  - basis `inject-has-no-optional-form`：`ctx.get` 看得见整棵树，这不是访问控制，「不得调用」要靠结构检查。
  - SYS-TENANT。
  - `apps/cli/design.md` 里没有这样的 HTTP 入口，唯一一处 HTTP 属于中心传输。
- **触发场景**：外部工具拿任意 `SessionRef`、`RunId`、尝试序号调 `attemptFacts`。该操作不带租户或调用方身份，三种答复本身就泄露别的会话有没有这次尝试及其进度。
- **后果**：左列保证被节点取消，右列又「一条都不兑现」，这条保证两侧都没人认领。「整棵树可见」被当成免核实的理由，方向与 basis 相反。
- **作者需明确**：
  - 单机时这条保证由谁给：装配不暴露，加哪条结构检查认领（V-8 目前不含此项）。
  - HTTP 查询若是真需求，它属于契约右列或新版本以及装配节点，不在提供者笔记里开口子。
- **为什么本阶段闭合**：它是租户隔离的边界，接受即等于批准暴露。
- **是否一处措辞可闭合**：否。要先定这条保证的 owner 与检查。

### 5. 撤除与换代时在途调用的收场三处互斥，论证依赖内核不给的清理次序
- **类别**：投影对齐（装卸配对）/ 反向核对
- **位置**：
  - `design.md`「成对的装载与撤除」表缓存行（:143）：在途调用立即以 `attemptNotFound` 返回。
  - 表后一段（:146）：「内核按登记的逆序逐个 `await`……服务一定先撤回、缓存后清空」，在途调用答 `unavailable`。
  - 失败映射「本实例已撤 ⇒ `unavailable`」（:136），以及 :130 的缓存作答。
  - 「插件边界」段写「登记一个 effect」（:35），装卸表里却有两个受管效应。
- **依据**：
  - 契约 S-12 第 2 条（在途的读按 `unavailable` 处置）、S-8 表第 1 行（`attemptNotFound` 是「读得到、确实没有」的结论）。
  - basis `effect-disposal-concurrent-not-ordered`（probe 在 4.0.4 通过）：各 effect 并发驱动，逆序只约束取出；要次序须并进同一个 effect。
  - `provide` 经 effect 纳管只是「待核对主张」，没有 basis 条目。
  - 模板核对项 4、5：不依赖清理次序；「立即返回 X」要有机制。
- **触发场景**：
  - 尝试在日志里，撤除时调用正在 `await readSince`，收到「日志里没有这次尝试」。
  - 两个 effect 并发释放，缓存清空与服务撤回没有先后保证。在途调用读回后把一段折进已清空的缓存，按残缺状态作答。
- **后果**：
  - 一个假结论。当前唯一消费者把两个值同收成 `dependencyUnavailable`，今天没有行为差别；但契约特意不合并这两个值，G-1 的真承接者原样收进 S-5～S-9 后，区分它们的消费者会被误导。
  - 「不会读到清到一半的缓存」唯一的论据与 basis 相反。真正的保护点（撤除标记）没写在 `await` 之后何处复核。
  - 正在 `await` 的调用靠什么「立即返回」，没有机制。
- **作者需明确**：在途调用的唯一收场值；不依赖清理次序的保护点（标记的复核点，或并入一个 effect 内定序）；撤掉与 basis 相反的上游断言。
- **为什么本阶段闭合**：否则接受的节点里会留下一条与已取证 basis 相反的上游语义，供别的节点引用。
- **是否一处措辞可闭合**：否。要补机制。
