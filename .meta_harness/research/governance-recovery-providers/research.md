# 同步复制接口与应用恢复保证的距离

调查日期为 2026-09-24，对象为 Litestream v0.5.17。消费者为治理生产基线后续机制选择。当前观察：阻塞同步可覆盖已写入 SQLite 的增量并供恢复，但它不认识应用升级是否确认，也不提供中心接管或登录语义。

## 问题与区分条件

需要区分“本地提交”“备份组件确认保存”“业务可对外确认”和“恢复可重新开放”。若组件只异步备份，不能据此承诺最近安全变更不回退；若组件同步成功，仍需核对确认范围及应用自己的提交规则。

## 当前结论

### 阻塞同步有实际恢复证据，但范围止于同机文件副本

官方文档说明 `sync -wait` 等待远端复制。钉版源码依次执行数据库同步与副本同步；文件提供者写临时文件、同步、改名并同步目录。合成探针中，暂停复制后，本地数据已变而恢复仍为旧值；阻塞调用超时。恢复进程后等待同步，恢复得到新值；杀掉复制进程后仍可恢复最后已同步值。

- 来源：[E1 源码](evidence.md#e1-精确源码与官方接口)、[E2 探针](evidence.md#e2-同机文件副本探针)。
- 范围：精确发行物、单写者、小数据库和同机文件副本；没有网络存储、物理断电或产品数据库证据。
- 代价与边界：同步多一道等待；超时后不知是否已保存，不能据非零退出断言回滚。服务不可达时无法取得同步确认。示例延迟不是容量指标。

### 复制会忠实保存回退后的业务值，不判断升级是否确认

探针把合成安全事实由 1 改为 2、同步成功，再写回 1 并同步；恢复得到 1。后者是普通业务值回写，并非执行项目真实升级。源码没有项目 upgrade guard 的确认输入。

- 来源：[E2](evidence.md#e2-同机文件副本探针)。
- 推断及范围：仅挂复制 daemon 或每次调用同步，不能自动获得项目“升级确认前失败恢复旧版、确认后不得回退”的组合保证；应用阶段与复制保存范围仍需另外协调。没有证明所有协调方式均不可行。
- 代价：失败清理、版本选择、独立副本访问和单写者接管仍属于应用/部署责任，不是这次复制 API 取证覆盖的能力。

### 一次返回的位置不是并发期间本地与副本位置永远相等的保证

`Store.SyncDB` 完成同步后另外读取本地 MaxLTX 和副本 Pos。二者不处于调用者业务事务中；源码不能支持“任何并发写入下两个返回值必定相等”的泛化。CLI 文档的相等说明不构成项目事务屏障。

- 来源：[E1](evidence.md#e1-精确源码与官方接口)。
- 状态：源码交错风险读数，尚未用并发探针构造该返回值不等的运行反例。不能写成已复现上游缺陷。
- 代价：需要精确定义调用前已提交批次、同步期间写者协调及返回值核验。组件 TXID 与产品业务命令不是一对一对应。

### VFS 写入模式文档不承诺生产强一致性

同期官方 VFS 文档明确为周期同步、单写者模式，并将生产强一致性工作负载列为不适用。它不是现有 `node:sqlite` 提供者加一项配置就能得到同步远端提交的证据。

- 来源：[E3](evidence.md#e3-文档所声明的边界)。
- 范围：文档声明，未编译或测试 VFS；不能推断所有未来版本均不支持。
- 代价：额外 VFS 运行时、冲突协调、缓冲区与同步窗口都需要独立评估。

## 未知与下一项证据

| 未知 | 所需最小验证 | 影响 |
|---|---|---|
| 独立备份端是否存在、其确认代表何种耐久 | 部署事实与选定后端同步/断电验证 | 整机损坏后安全事实不回退 |
| 升级 staging、确认与副本公开顺序 | 应用状态机与各崩溃切点反例 | 不能据 E2 接受升级恢复 |
| 写者竞争、时钟续约、慢备份 | 真实组合并发与故障探针 | 进展性和实际容量 |
| 所需最晚副本是否存在、旧中心是否仍可写 | 代际/接管契约及故障探针 | 正确选择恢复源、避免双写 |
| 更成熟数据库同步复制的对照 | PostgreSQL 指定版本及本项目提供者符合性读数 | 此包不裁定 SQLite 路线优于数据库复制 |

本轮没有采用决定。版本、后端或应用确认协议变化后须重新核对对应结论。
