## 3. 从用户场景看得到的行为

这些是对已读上游承诺的场景化复述，不是 PF-021 已确认的验收标准。

| 场景 | 上游可观察要求 | 不能偷换成什么 |
|---|---|---|
| 每周五三点提醒交周报 | 一次耐久通知，无 agent 执行和预算；账本可辨“已通知” | 跑一次模型让它发通知 |
| 每周五替我整理周报 | 独立执行；结果回流与用户交付各有结果 | “启动了”就等于“周报到了” |
| 明天下午三点做一次 | once，派发/运行/终态分明，完成后不需手工停用 | count=1 或派发即成功 |
| 每月第一个周一，最多五次，到年底为止 | 有代表性预览；次数与截止同时约束，排除不计数 | 任一引擎默认行为就是产品规则 |
| 周末调休上班，工作日计划要照常运行 | 逐日日历覆盖 weekday 直觉 | 周一至周五就是工作日 |
| 几天的候选都顺延到周一 | 同计划一次 occurrence，保留所有源槽出处 | 不知情地连跑多次 |
| 去东京后仍说每天八点 | follow 使用新生效时区重算，历史保留旧环境 | 所有计划一律固定 UTC，或无痕改已接受工作 |
| agent 夜里提出新计划，用户不在 | 留耐久草稿，零触发；用户以后可确认/丢弃 | 卡着整个会话等确认，或直接视为已获准 |
| 修改重复规则 | 原子切到后继，前驱历史保留，新旧互指 | 先删旧后建新造成空窗，或先建新造成双触发 |
| 设备暂时离线 | 保留 intent，显示可恢复 blocker；同身份恢复重评 | 超时久了就当设备退役 |
| agent 说外部文件永远没了 | 保存呈报与原因，由 owner 决定后果 | 系统凭模型一句话永久停掉工作 |
| 今天没收到昨晚摘要 | 从窗口处置追执行、回流、发布/归档分别判断 | 一项含糊“失败”，或只显示成功过的日程 |
| 查询本周，跨越现在 | 过去显示实际处置，未来显示预计和被抑制/阻塞/暂停的行 | 用当前定义重新算过去并冒充真实历史 |
| 没网安装 | 三本随包日历先可用，刷新失败独立记录 | 必须在线下载日历后才能开始用 |
| 两个用户订阅同一产品 feature | 两份独立 occurrence/结果，去重含订阅者 | 一个用户先到把另一个吞掉 |

## 4. 几组最容易混淆的轴

### 4.1 计划是否继续，与这次到底做没做

上游区分生命周期 intent、依赖 standing、某个 occurrence 的处置、
一次执行的终态、结果发布与归档。暂停并不抹除 blocker，依赖恢复不取消人的暂停；
永久停用不回滚已接受执行。一次性计划多了执行中与终结的可见状态，
重复计划不因一次成功变成终态。

这带来的产品成本是：用户不能只靠一颗总状态灯理解未来工作。
研究仅说明这个成本已经存在于承诺之间，没有在这里决定本项目如何呈现。

### 4.2 几种“错过”不能套同一规则

| 成因/工作类型 | 上游已读处置 | 剩余边界 |
|---|---|---|
| 直接用户暂停后恢复重复计划 | 从当时下一适用窗口继续，不无界补积压 | 不自动定义所有历史窗如何列账 |
| 设备不可用的重复计划 | 默认 skip；显式 opt-in 有界 catch-up 是上游既有选择 | 不等于宿主进程完全关机的完整 missed 产品处置 |
| 一次性到期依赖不可用 | 默认终局 lapse；显式可选 await_recovery | 永久依赖失效仍终局；执行卡死另缺兜底裁决 |
| 日历数据暂缺、后恢复 | 承接原有 bounded catch-up/skip | 当时可定义时刻，但缺数据 |
| 环境自不一致后自愈 | 从现在往未来算，不补停牌段 | 当时“用户的八点”定义不自洽，不能编造过去槽 |
| 纯提醒在宿主关机期间流逝 | missed，不补迟到提醒/批量补发 | 持久 missed 事实完整形成链仍与 G5 相邻缺口有关 |
| 宿主关机期间错过执行型窗口 | intake 显式登记 G5 未接受片段 | 本轮不能用设备恢复或提醒规则代填 |

来源：E02/E03/E06/E08。表中精确语义与上游的 skip/catch_up 字段关系
只在各来源给出的范围内成立，不是给所有计划声明一个统一默认。

### 4.3 三个“日历”的说法不是同一个承诺

本轮主要看到了两类已批准语义：业务日历作为可查询数据，agenda 作为日程窗口读面。
常见个人日历中的手工事件、全天事项、邀请参与者、会议冲突、
CalDAV/Google/Outlook 双向同步没有在本轮核心材料中找到完整获批条款。
“日历”这个主题名本身不能补出第三类产品承诺。

同样，“工作日”依赖所选业务日历的范围。上游明确规定美国联邦日历不等于全国放假，
也没有授权把它直接解释成交易所营业日。日历回答的意义取决于其声明范围和版本。

## 5. 上游相关设计解决了什么

下表记录已有方案及它的限制，不为本项目推荐机制，也不把它的包边界搬过来。

| 上游设计位置 | 它处理的问题 | 已读代价或限制 |
|---|---|---|
| ADR-033 | 定义、tick 权威和入站翻译分工；跨节点不重复发射 | 建立在上游 state/inbound/runtime 与 lease 架构；本项目首版单机、Cordis 模型不同 |
| scheduling-expressiveness / ADR-101/104 | 时间规则与数据分开，DST 同口径，版本确定性、平移合并、覆盖拒绝 | 查表有覆盖边界；有界前瞻有计算成本；once×overlay 未开 |
| ADR-108 | 设置变更的有界、显式、可审计环境采用 | 不是瞬时全体一致；环境不自洽会停牌；固定意图在旧产品首期无入口 |
| business-calendar-data-supply | 周期取数、语义校验、版本发布、出处与待裁候选 | 官方文档会迟到/另发/回改；多源同血统可能一起错；源码方案不是当前数据准确性的证明 |
| ADR-109 | 随包种子和尽力刷新，离线首装可用 | 覆盖按发版年份，不保证旧安装包永远能用；发布新鲜度闸也不等于真实发布流水线已完成 |
| ADR-114 / 跨系统旅程 | 结构依赖与工作内容呈报分开，最终派发前重读 | 首期只有三族；第二道闸执行位点未落；owner 不能由 Schedule authority 代替 |
| schedule-calendar-web-surface | 规划/观测/评估都用同一事实；预览与到期计算同源 | S13 执行关联、S14 去重事实、S15 列表全量扫描仍有登记 |
| ADR-079 | 执行、结果回流、用户交付、归档分开 | 结果链与通知/知识提供者有独立交接；不能把 execution success 当用户价值兑现 |

供应侧所称横向扩展有具体前提：新国家差异能用已有模型与校验机制表达。
新适配器/配置/装配声明的增加不等于自动支持半日、地方制度或新的计算基准；
旧研究与候选 ADR 已把这些问题暴露出来。

## 8. 后续讨论真正缺少的输入

研究已足够支撑产品开题，但不是足够替用户拍板。需明确的主要是：

1. PF-021 的首版范围：自动工作与提醒之外，是否还要个人事件/会议等不同语义。
2. 日程的持有与管理边界：个人、组织、agent 自建、系统 feature 之间如何在本项目表达。
3. 新建、转正、改期、取消分别如何与当前权限与 HITL 规则相接。
4. 旅行跟随和固定时间的产品入口，以及环境不一致的可见后果。
5. 宿主关机、暂停、受阻、错过、一次性执行不终结这些情形各自怎样收场。
6. 会话/工作区与未来日程的关系，以及归档后结果去哪儿。
7. 通知、结果与归档分别由哪块现行产品语义承接。

这些问题不阻止先理解时间表达、数据版本和证据边界；
它们阻止的是把旧系统政策直接写成 PF-021 已确认的产品规则。
