# 两种个人 Agent 产品的比较：可消费的观察与边界

- 调查对象与日期：Meta AI Muse 与 xAI Grok Bot；2026-09-16 的公开资料截面。
- 消费者：个人 agent 的能力覆盖、提供者/装配边界及授权、恢复、观察与治理设计。
- 当前结论：两者均不是一次性聊天 UI：它们有可持续的云端执行环境、跨会话上下文、浏览器/应用
  操作、后台工作和人工介入。不过，它们公开的安全与状态模型明显不同：Muse 把**单个人的专属
  VM、外部 Sentinel 和连接器范围授权**作为控制结构；Grok Bot 把**一个用户拥有、全部 Bot 共用的
  云电脑**作为协作底座，并以用户规则和 Auto Review 在动作前作门控。该结论只比较公开产品陈述，
  不评定实际安全性或完成率。[C1](evidence.md#c1-直接事实输入与范围)

## 问题与比较方法

比较的问题不是“哪个模型更强”，而是：当个人 agent 可在用户离线时拥有外部账户、文件和持续
任务时，哪些对象承载身份、状态、权限、人工介入与证据？只有两个来源都对同一层次作出明确说明
时才作直接比较；一方未公开的部分记为未知，不能以另一方的设计补齐。

产品名称也须先澄清：`Muse` 是 Meta 的个人 agent；`Muse Spark` 是相关模型系列，不能以模型页
自动扩展 Muse 功能。`Grok Bot` 是 `x.ai/bot` 所称的持续工作产品；X 内的 Grok、及 X 帖子里的
`@username` mention，均不是 Grok Bot invocation 的证据。[C1](evidence.md#c1-直接事实输入与范围)

## 关键差异与不可合并之处

### 1. 执行环境的归属决定最小隔离单位

Muse 的公开启动时架构描述为**每人一台隔离 VM**，并在其内外分置 runtime cell、持久状态、凭据
和安全服务；它没有以“多个可命名 Muse”作为共享工作空间的公开对象。Grok Bot 明确相反：一个
用户的各 Bot 共享一台云电脑、文件、浏览器会话和登录，Bot 间独立的只是 role/conversation/
learned context；官方特别说这不是 Bot 间安全边界。[C1](evidence.md#c1-直接事实输入与范围)

因此，不能从“各 Bot 有屏幕/对话”推出每个 Bot 有最小权限或独立凭据，也不能把 Muse 的每用户
隔离自然而然提升为租户隔离、机密计算或对运营方不可见。前者要求显式的用户内资源共享策略；后者
仍须独立定义多租户身份、管理员访问和密钥所有权。Muse Confidential VM 在截点仍是计划功能，
不能计入现有能力。[C2](evidence.md#c2-已知缺口与禁止推论)

### 2. “审批”相同的结果，不同的权威位置

Muse 的资料声称 Sentinel 位于所有连接器行动和网络出口的强制许可边界，且审批不走 agent 对话
通道。Grok Bot 的公开资料称 Auto Review 是在工具/电脑动作前评估的模型化控制，用户可配置规则，
并明确它不能替代 least privilege；用户控制可关闭这一层。两者都提供“需要批准”的产品体验，但
只有前者公开宣称独立许可服务及 scope/expiry 类能力，后者公开的是策略与 review 模型。
[C1](evidence.md#c1-直接事实输入与范围)

这不是安全强弱结论：没有独立审计、策略完整性、故障行为或绕过测试资料。它仅说明后续设计不能用
一个布尔 `approved` 表示全部授权语义；至少须区分提出者、许可权威、被批准的目标/范围/时效、
真正执行者和可审计决定。

### 3. 持久状态与删除的对象不同

Muse 的公开控制面包括 memory file、forget、删除聊天/文件、reset VM 和 connector 断开；其隐私
政策同时指出删除内容可能仍被记住、断连也不必删除既有记忆/对话。Grok Bot 删除 Bot 会删除 active
profile/conversation/routines，却明确不保证删除共享电脑上的文件或登录态；停止不撤回已完成外部
动作。两者都明确否定“删除一个 UI 对象即删除所有相关状态”的假设。[C1](evidence.md#c1-直接事实输入与范围)

由此可消费的设计问题是：运行态、记忆、凭据/会话、文件、例行触发、审计记录和外部效果分别由谁
所有，哪些操作停止未来访问、哪些只是隐藏或删除引用、哪些要清理副本，以及失败时留下何种可追溯
事实。不能把厂商的 UI 名称当作该问题的答案。

### 4. 社交/消息表面不是统一外部事件协议

Muse 公开入口是 app、Web 与 WhatsApp，连接器示例有 email/calendar/Instagram；没有公开完整
connector 或事件投递语义。Grok Bot 可经 X connector 搜索帖子、读时间线和检查 mentions；其产品
内 `@` 是 Bot/group/routine/connector 的寻址。而 X 官方的帖子 mention 只说明通知语义，并无
Grok Bot 被唤醒的证据。[C1](evidence.md#c1-直接事实输入与范围)

故消息入口、连接器读写、外部 webhook/轮询、任务唤醒和 Bot-to-Bot handoff 必须分别建模。尤其
不能把 “X 上 @Grok” 或“接 WhatsApp”写成已证实的端到端触发和授权协议。

### 5. 个人数据控制不能只看“训练 opt-out”

Muse 称对话/VM 数据不进入 Meta 广告系统，并提供模型训练开关、忘记和账户中心选项；但当前 VM
不从密码学上排除为支持/安全/运营所需的 Meta 访问。Grok Bot 要求云端存储，训练/数据分享依
Cursor 账户设置；而 X 上 Grok 的数据开关/删除政策是另一个产品面，不能自动外推到 Bot 的 X
connector。两方都使“训练使用、广告使用、运营访问、connector 第三方处理、共享电脑暴露、删除
保留”成为不同问题。[C1](evidence.md#c1-直接事实输入与范围)

## 对后续 harness 设计的研究输入（推断，不是决策）

1. **最小对象图应先于 agent 名称。** 需要分开描述 user/tenant、agent profile、conversation、run、
   workspace/computer、credential grant、connector、routine/trigger、memory、artifact、approval
   request/decision 与外部 effect。这样才同时表达 Muse 式专属环境和 Grok Bot 式同用户共享环境，
   而不是把任何一个厂商 UI 直接当成领域模型。
2. **授权应当是可验证的动作前门。** 无论采用独立 policy service 还是 review-assisted workflow，
   请求、范围、时效、用户覆写、拒绝、超时和实际 effect 都须有可检验语义。自然语言“帮我做”与
   audit trail 不足以替代这一边界。
3. **连续运行需要显式失败和保留契约。** 后台运行、crons/routines 和多 agent handoff 不证明任务
   在应用退出、撤权、连接器错误或重复事件后仍正确。消费者需另定义 run ownership、取消、迟到
   结果、重试 attempt、观察记录与非可逆外部效果的关系。
4. **隔离键应从租户和资源类型推导。** Grok Bot 提供了“同用户共享”这一可行协作模式，也显露出
   Bot ID 不是安全边界的风险；Muse 的 per-user VM 也不替代项目要求的 tenant identity。工作区、
   credentials、browser session 和 file 的共享/隔离应逐资源、逐授权声明。
5. **可控记忆应是多条生命周期。** 修改/遗忘记忆、删会话、断开 connector、删 artifact、停止
   routine 和撤销凭据各有不同的有效范围；任何“delete agent”动作都不应虚称为全量回收或外部
   回滚。

这些是比较带回的待验证设计问题；尚未进行能力覆盖、提出候选或取得接受，不能升级为 specification。

## 采用与后续核对

截至 2026-09-16，本比较没有被 proposal、decision、spec、provider 或 assembly 采用。若后续设计
消费某一观察，应直接引用本包的比较结论和所链接的产品级证据；若厂商页面更新，则先追加产品级
记录，再检查本比较中的结论是否仍成立，不能静默把新的产品状态倒写到本截面。
