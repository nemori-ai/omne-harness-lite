## 1. Claude Code（Anthropic 官方 CLI）

- 来源：
  - https://code.claude.com/docs/en/sub-agents （原始链接 `docs.claude.com/en/docs/claude-code/sub-agents` 301 重定向到此）——一手原文，WebFetch + curl 双重核验
  - https://code.claude.com/docs/en/agent-sdk/subagents （Claude Agent SDK 子代理页）——一手原文
- 取得方式：curl 抓取该页 Next.js payload 原始 HTML，用正则从 `children:\`...\`` 片段中还原出 markdown 源文本，**逐字**还原（非模型摘要）；SDK 页面用 WebFetch 摘要+大段原文直出。

### 1.1 是否存在 debugger 类角色
**存在一个文档给出的完整示例子代理，名字就叫 `debugger`**，但**不是内置（built-in）子代理**——它出现在 "Example subagents" 这一节，与 Code reviewer / Data scientist / Database query validator 并列，都是"照抄即可用"的**用户可自定义**范例，不随 Claude Code 安装。

内置（真正 built-in、无需用户定义即可被 Claude 调用）子代理只有：`Explore`、`Plan`、`general-purpose`，以及几个功能性的 `claude`、`statusline-setup`、`claude-code-guide`。这几个里没有 debugger。

### 1.2 完整原文逐字引用

**(a) "Example subagents → Debugger" 一节，完整 frontmatter + system prompt**（来自 https://code.claude.com/docs/en/sub-agents ，通过页面 JSON payload 还原）：

> A subagent that can both analyze and fix issues. Unlike the code reviewer, this one includes Edit because fixing bugs requires modifying code. The prompt provides a clear workflow from diagnosis to verification.

```markdown
---
name: debugger
description: Debugging specialist for errors, test failures, and unexpected behavior. Use proactively when encountering any issues.
tools: Read, Edit, Bash, Grep, Glob
---

You are an expert debugger specializing in root cause analysis.

When invoked:
1. Capture error message and stack trace
2. Identify reproduction steps
3. Isolate the failure location
4. Implement minimal fix
5. Verify solution works

Debugging process:
- Analyze error messages and logs
- Check recent code changes
- Form and test hypotheses
- Add strategic debug logging
- Inspect variable states

For each issue, provide:
- Root cause explanation
- Evidence supporting the diagnosis
- Specific code fix
- Testing approach
- Prevention recommendations

Focus on fixing the underlying issue, not the symptoms.
```

**(b) 另一处更简短的 `--agents` CLI flag 示例**（同一页面，"create a custom subagent via CLI flag" 一节）：

```json
{
  "debugger": {
    "description": "Debugging specialist for errors and test failures.",
    "prompt": "You are an expert debugger. Analyze errors, identify root causes, and provide fixes."
  }
}
```

> 备注：用户交代的起步事实是"文档只有一个两句话的 debugger 示例"——本次核查发现，当前线上版本（2026-09-22）除这个两句话的 CLI flag 示例外，**还有一份完整得多的 "Example subagents → Debugger" 范例**（工具清单 + 5 步流程 + 5 项交付物），可能是文档改版后新增的。两处并存，已如实两份都记录。

### 1.3 工具与限制
- 完整版 debugger 示例的工具集：`Read, Edit, Bash, Grep, Glob`（比只读的 code-reviewer 多了 `Edit`，页面原话："Unlike the code reviewer, this one includes Edit because fixing bugs requires modifying code."）。
- 内置 `Explore`／`Plan` 是只读："read-only tools; Write and Edit are denied"。
- 子代理默认在后台运行，工具集被裁剪；后台子代理保留的工具集官方原话列出为：`Read, Grep, Glob, Bash, PowerShell, Edit, Write, NotebookEdit, WebFetch, WebSearch, TodoWrite, Skill, ToolSearch, EnterWorktree, ExitWorktree, Monitor, TaskStop, SendMessage, Artifact`；被移除的工具：`Agent`（达到深度上限时）、`AskUserQuestion`、`EndConversation`、`EnterPlanMode`、`ExitPlanMode`、`ScheduleWakeup`、`WaitForMcpServers`、`Workflow`。
- 上下文隔离（Agent SDK 页原话）："each subagent runs in its own conversation, which starts fresh... intermediate tool calls and results stay inside the subagent; only its final message returns to the parent."
- 深度/并发上限：默认 3 层子代理嵌套，默认 20 个并发子代理；超限报错 `Concurrent subagent limit reached` / `Budget limit reached`。
- **官方承认的局限（与 debugger 场景直接相关）**：v2.1.210 起，Claude Code 对子代理最终消息做"指令注入扫描"——因为子代理常常要读取错误日志、堆栈、外部文件内容，这些内容可能包含伪装成系统指令的文本；扫描只中和三类模式（伪造 `<system-reminder>` 标签、提及权限配置文件如 `.claude/settings.json`/`bypassPermissions`、伪造 `Human:`/`Assistant:` 对话标记），命中时在结果前加 `[harness: ...]` 标记行，不删除也不改写原文。这条明确承认："子代理读取到的外部内容可能包含试图操纵父级 agent 的注入文本"。
- 子代理默认不能看到父会话历史、父系统提示、已加载的 skill（除非 fork 模式或显式在 `skills` 字段列出）。

### 1.4 官方"何时派发"的说法
- 页面原话（sub-agents 页开场）：*"Use one when a side task would flood your main conversation with search results, logs, or file contents you won't reference again: the subagent does that work in its own context and returns only the summary."*
- 何时该用主对话而非子代理："The task needs frequent back-and-forth or iterative refinement" / "Multiple phases share significant context" / "You're making a quick, targeted change" / "Latency matters"。

### 2.3 工具与限制
- 自定义 agent（`~/.codex/agents/*.toml` 或项目级 `.codex/agents/*.toml`）必填字段：`name`、`description`、`developer_instructions`；可选继承 `config.toml` 里受支持的键：`model`、`model_reasoning_effort`、`sandbox_mode`、`mcp_servers`、`skills.config`。
- 子代理继承父级的权限/沙箱模式：*"Subagents inherit the permission mode selected beneath the composer. Choose the permission mode for the parent turn before you ask Codex to delegate work."* ——但单个自定义 agent 也可以显式覆盖沙箱设置（如上面 `browser_debugger` 样例里显式设了 `sandbox_mode = "workspace-write"`，官方文档提到"可以把某个 agent 明确标成只读，其它保留更大权限"）。
- 全局 `[agents]` 配置：`agents.enabled`、`agents.max_concurrent_threads_per_session`、`agents.default_subagent_model`、`agents.default_subagent_reasoning_effort`、`agents.interrupt_message`。
- **官方承认的局限**：子代理工作流消耗更多 token（每个 spawn 出的 agent 都独立做模型和工具调用），跨并发 agent 有 token 预算约束；设计准则原话："The best custom agents are narrow and opinionated. Give each one clear job, a tool surface that matches that job, and instructions that keep it from drifting into adjacent work."

### 2.4 官方"何时派发"的说法
- `explorer` 角色描述原话："Use `explorer` for specific codebase questions. Explorers are fast and authoritative."
- `worker` 角色描述原话："Use for execution and production work." 典型任务包括 "Fix tests or bugs"。
- （已禁用的）`awaiter` 角色原话："Use an `awaiter` agent EVERY TIME you must run a command that will take some very long time."
- 文档给出的调试相关拆分模式（"UI Debugging"）：分成"code mapping"、"browser debugging"、"implementation" 三个独立 agent，而不是单一"debugger"角色。

## 3. Cursor

- 来源：
  - https://cursor.com/docs/subagents （官方，一手，WebFetch）
  - https://cursor.com/docs/agent/debug-mode （官方，一手，WebFetch）
  - https://cursor.com/docs/bugbot （官方，一手，WebFetch）

### 3.1 是否存在 debugger 类角色
Cursor 的**内置**子代理只有三个：`explore`（代码库检索）、`bash`（shell 命令）、`browser`（浏览器自动化），**没有内置 debugger**。

但 Subagents 文档页的"自定义子代理示例"里同样给出一个叫 `debugger` 的示例——文字与 Claude Code 文档的两句话版本高度相似（措辞几乎相同："Debugging specialist for errors and test failures."），判断为文档惯例上的"通用调试示例"，而非 Cursor 独有的功能。

Cursor 另有两个**独立产品/功能**、常被人跟"debugger 子代理"混同，但官方定位都不是"子代理"：
- **Debug Mode**：Agent 的一个"模式"（不是 subagent_type），通过模式选择器或 `Shift+Tab` 切换。
- **Bugbot**：PR 自动审查机器人，是 CI/代码评审集成，不是对话内可派发的子代理。

### 3.2 完整原文逐字引用

**Subagents 文档页的 debugger 示例**（https://cursor.com/docs/subagents）：

```markdown
---
name: debugger
description: Debugging specialist for errors and test failures. Use when encountering issues.
---

You are an expert debugger specializing in root cause analysis.

When invoked:
1. Capture error message and stack trace
2. Identify reproduction steps
3. Isolate the failure location
4. Implement minimal fix
5. Verify solution works
```

**Debug Mode 工作流（五阶段，官方原话转述，非逐字网页文案）**：
1. Exploration — 检查相关文件，提出多个假设
2. Instrumentation — 添加日志语句，"send data to a local debug server running in a Cursor extension"
3. Reproduction — 用户按 agent 给出的步骤复现
4. Analysis — agent 分析收集到的日志，定位真实根因
5. Fixing and Cleanup — 应用针对性修复，然后移除埋点

Debug Mode 推荐使用场景（官方原话转述）：可复现但原因不明的 bug、竞态/时序问题、性能问题和内存泄漏、此前能跑的功能出现回归。

**Bugbot 触发方式**（官方原话）：默认每次 PR 更新自动跑；也可用评论 `cursor review` 或 `bugbot run` 手动触发；可配置成"每个 PR 只跑一次"或"仅手动触发"。

### 3.3 工具与限制
- Subagents 页原话：子代理"inherit all parent agent tools, including MCP tools from configured servers"；`bash` 子代理能跑 shell 命令，`browser` 子代理能做"capturing DOM snapshots and screenshots"。
- 嵌套限制：直接子代理可以再派生子代理，但**嵌套出来的子代理不能再往下派生**（"nested subagents cannot spawn further ones"）。
- **官方承认的局限**（Subagents 页）：启动开销和并行执行时更高的 token 消耗；子代理以干净上下文启动，需要在 prompt 里把相关信息重新给全；云端子代理只能用团队配置的 MCP server，不能用本地会话的 MCP server。
- Debug Mode 没有在文档里给出明确的工具权限声明（是否能跑命令、能不能截图等未见逐条列出）；页面明确的局限性表述只有一句概括："When standard Agent interactions struggle with a bug, Debug Mode provides a different approach using runtime evidence rather than guessing at fixes."（暗示它是给"常规 agent 交互解决不了"的场景用的补充手段，而非默认路径）
- Bugbot 的官方局限（逐条）：单条规则内容上限 30,000 字符，单次评审合并规则上限 100,000 字符；Azure DevOps 不支持 Autofix；GitLab/Bitbucket 不支持 Autofix 的"Create New Branch"模式；速率限制 30 次评审/分钟（常规）、10 次/分钟（dry-run）、60 次/分钟（管理 API）。

### 3.4 官方"何时派发"的说法
- Subagents 页原话（转述）：适合"context isolation for long research tasks"、"running multiple workstreams in parallel"、"specialized expertise across many steps"；单一目的的小任务用 Skills 而非子代理。
- Debug Mode 的适用场景已在 3.2 列出（可复现但原因不明、竞态、性能/内存、回归）。

**"your-stack-your-rules" 官方博客给出的四个示例**（逐字摘录 name + description + tools）：

- Security audit — "Run our standard security checks across repositories and produce a PR-ready checklist grouped by severity." — tools: `gh, git, semgrep, trivy, gitleaks, jq`
- IaC compliance — "Review Terraform plans and Kubernetes manifests against our guardrails, highlight risky changes, and produce an approval-ready summary." — tools: `gh, terraform, conftest, opa, kubeconform, jq`
- Release docs — "Draft release notes from merged PRs since the previous release, update CHANGELOG.md, and output a short release checklist (tests, migrations, rollout/rollback)." — tools: `gh, git`
- Incident response — "Gather first-look incident data (deploys, error rates, top endpoints, logs) for a service and time window, then draft an incident report and next steps." — tools: `gh, git, jq, curl`

### 4.3 工具与限制
- `create-custom-agents` 页 YAML frontmatter schema：`name`（选填，默认取文件名）、`description`（必填）、`tools`（选填，不填则拿到全部可用工具）、`mcp-servers`（选填）、`model`（选填，仅 VS Code/JetBrains/Eclipse/Xcode 可用）、`target`（选填，`vscode` 或 `github-copilot`）。
- 默认权限原话："agents can access all available tools, including built-in tools, and MCP server tools" ——除非在 `tools` 里显式列出限制。
- 内容限制（官方原话）：prompt 最长 30,000 字符；文件名仅允许 `.`、`-`、`_`、`a-z`、`A-Z`、`0-9`。
- **官方承认的局限**：custom agents 功能目前"in public preview for JetBrains IDEs, Eclipse, and Xcode, and subject to change"；部分 agent profile 属性"may function differently or be ignored between environments"（不同宿主环境行为不一致）。

### 4.4 官方"何时派发"的说法
- `about-custom-agents` 原话："tailored teammates that follow your standards, use the right tools, and implement team-specific practices"，用于消除"重复给同样指令"的负担。
- 未见任何针对"调试/定位 bug"场景的专门派发指引。

DeepSeek Harness 的 `packages/subagent/` 是一套**后端无关的委派基础设施**，不是"角色库"：
- `subagent/` 基础包提供"the delegation service: provider registry, one-shot runs, continuable children, and discovery"，挂在 `ctx.subagents` 上；
- 面向模型的能力通过两个工具暴露：`tool-subagent`（"Exposes delegation to the model"）、`tool-subagent-control`（"adjacent-agent messaging, interrupt, and listing"）；
- 子包按**部署形态**（而非角色语义）区分：`subagent-fork-in-process`（进程内、带父级对话历史的子代理）、`subagent-spawn-in-process`（进程内、全新上下文的子代理）、`subagent-in-process-driver`，以及**后端适配**：`subagent-acp`、`subagent-codex`、`subagent-claude-code`、`subagent-dsh-sdk`（即可以把 Codex CLI、Claude Code 本身接成 DeepSeek Harness 的子代理后端）。

### 8.2 完整原文逐字引用
- README 唯一涉及 agent 能力的一句话："The agent can read and edit workspace files, run commands, delegate work, and maintain a plan."
- AGENTS.md 里唯一与"调试"字面相关的是一个**运行时诊断包**而非调试角色："`packages/runtime-diagnostics/` provides 'runtime invariants' monitoring"——这是监控运行时不变量的基础设施包，不是一个可派发的"debugger 子代理"。

### 8.3 工具与限制
未见任何官方文档给某个子代理预设"只读/可写/能跑命令"这类角色级工具矩阵——权限模型停留在"委派服务 + 两个工具（发起委派、控制/通信）"这一层，角色定义完全留给调用方（这与本项目 CLAUDE.md/AGENTS.md 里"内核层复用 Cordis 与 DSH agent 原语；Agent Loop、Harness 层、工具协议…由本项目自行定义"的定位一致——即 DSH 本身不提供 debugger 语义，是留白）。

### 8.4 官方"何时派发"的说法
未检索到。三份文档均未给出"何时该用子代理/委派"的场景化指引，只说明委派基础设施的存在。
