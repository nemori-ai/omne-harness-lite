## A. 自动修复/调试 agent 系统：定位—假设—验证—修复循环

### A1. SWE-agent: Agent-Computer Interfaces Enable Automated Software Engineering
- 版本/年份：arXiv:2405.15793（提交 2024-05；NeurIPS 2024 论文）
- URL：https://arxiv.org/abs/2405.15793 （全文 HTML：https://arxiv.org/html/2405.15793）
- 一手/转述：一手（通过 WebFetch 抓取 HTML 全文相关段落，非二手摘要）
- 成立条件：GPT-4 Turbo 或 Claude 3 Opus 作为底层 LM；任务集为 SWE-bench / SWE-bench test（2942 或 2294 个真实 GitHub issue 任务）；agent 通过其自定义 Agent-Computer Interface（简化的文件导航/编辑/测试命令）与仓库交互，而非原始 Linux shell。
- 报告的失败率/局限（原文）：
  - "Editing remains challenging for agents. A non-trivial minority of edit actions raise a linting error; out of 2942 task instances, 1185 (51.7%) of SWE-agent w/ GPT-4 Turbo trajectories have 1+ failed edits."
  - "Any attempt at editing has a 90.5% chance of eventually being successful. This probability drops off to 57.2% after a single failed edit."（首次编辑失败后，恢复概率显著下降 —— 即"假设—验证—修复"循环存在级联失败）
  - "Cascading failed edits make up another 23.4% of failures"
  - "About half (52.0%) of unresolved instances fall into the Incorrect Implementation or Overly Specific Implementation categories, suggesting that agents' proposed solutions often simply fail to functionally address the issue or are insufficiently general solutions."
  - 解出率：GPT-4 Turbo 12.47%（2942 任务），Claude 3 Opus 10.46%；此前非交互式检索增强系统基线 3.8%。
  - 每实例预算上限 $4，限制探索空间。
- 与「让 agent 看见 TUI/桌面问题」的关系：SWE-agent 的核心论点是——给 agent 的"计算机接口"（工具反馈的即时性、结构化程度）直接决定定位与修复成功率；其失败模式集中在"编辑后不能验证/纠正自己引入的新错误"，即工具反馈回路一旦失真或滞后，级联失败概率骤增。这对设计任何需要向 agent 暴露 TUI/GUI 状态的工具接口是直接可比的证据：反馈粒度与即时性本身就是决定失败率的变量，而非只是锦上添花。

### A2. AutoCodeRover: Autonomous Program Improvement
- 版本/年份：arXiv:2404.05427（v1 2024-04，v3 见 ASE 2024 会议版）
- URL：https://arxiv.org/abs/2404.05427 （全文：https://arxiv.org/html/2404.05427v3）
- 一手/转述：一手（抓取论文 Section 6.3/7/8 原文）
- 成立条件：基于 AST 的程序结构检索 + LLM 驱动的迭代代码搜索；若测试套件存在，可选启用 spectrum-based fault localization (SBFL) 缩小可疑方法范围。SWE-bench-lite（300 个真实 GitHub issue）。
- 报告的失败率/局限（原文）：
  - "In 29.3% of the tasks, AutoCodeRover correctly decided on all patch locations (at the method-level), but did not produce a correct patch."（定位正确但修复仍失败——定位≠修复）
  - "In 20.0% of the tasks, a patch is generated in the correct file, but at wrong methods / classes in the file."
  - "In 18.0% of the tasks a patch is generated in wrong files, and in 6.7% of the tasks there is no applicable patch."
  - "AutoCodeRover failed on 23 unique instances...mainly due to unimplemented search APIs...the LLM may still fail to invoke valid search APIs in later attempts."（工具接口覆盖不全导致的系统性失败，而非模型推理失败）
  - Threats to Validity: "LLM is known for its randomness to generate different results in different runs, which may threaten the validity of AutoCodeRover's performance." 以及 "this patch may be overfitting"（用测试通过判定"已解决"存在过拟合风险，即验证标准本身不可靠）。
  - 解出率 19%（SWE-bench-lite），平均成本 $0.43/issue。
- 与 TUI/桌面关系：其"定位正确但修复仍错"的数据（29.3%）直接说明"定位—假设—验证—修复"循环里，光有准确的根因定位远不足以保证修复正确；对调试 agent 设计而言，这提示"看见问题在哪"与"看懂问题为何"是两个独立且都可能失败的环节，可观测手段解决的是前者，不能默认覆盖后者。

### A3. RepairAgent: An Autonomous, LLM-Based Agent for Program Repair
- 版本/年份：arXiv:2403.17134（v1 2024-03；ICSE 2025 会议版）
- URL：https://arxiv.org/abs/2403.17134 （全文：https://arxiv.org/html/2403.17134v1）
- 一手/转述：一手（抓取论文 "VI Threats to Validity and Limitations" 章节原文）
- 成立条件：ChatGPT (GPT-3.5) + 状态机管理迭代调试动作；Defects4J（Java，835 个真实 bug，每个 bug 至少有一个失败测试用例）。
- 报告的失败率/局限（原文）：
  - "the LLM may have seen parts of the Java projects during training"（数据泄漏风险，可能高估效果）
  - "Defects4J has at least one failing test case for each bug, which may not be the case for real-world usage scenarios"（验证前提——真实场景常无预先标注的失败测试，方法可能不适用）
  - "Inaccurate or imprecise fault localization could lead to suboptimal repair suggestions"
  - "The inherently non-deterministic nature of LLMs may result in different outcomes between two consecutive runs"
  - 实测：835 个 bug 中只修复 164 个（19.6%），671 个未修复；某些项目（如 JxPath）零成功；"The number of tokens consumed by fixed bugs (21,000) is clearly lower than by unfixed bugs (315,000)"——即失败尝试消耗的资源远高于成功尝试，暗示"循环不收敛"是主要失败模式而非单次判断错误。
- 与 TUI/桌面关系：RepairAgent 的前提"至少有一个失败测试用例"对应 CLI/TUI 场景里"有一个可判定成功/失败的 oracle"；当调试对象是 TUI 渲染问题时，往往没有这样一个二元通过/失败的测试，这正是该假设在 TUI 场景下失效的具体条件。

### A4. Agentless: Demystifying LLM-based Software Engineering Agents
- 版本/年份：arXiv:2407.01489（v2；FSE 2025 会议版，标题见 lingming.cs.illinois.edu/publications/fse2025.pdf）
- URL：https://arxiv.org/abs/2407.01489 （全文：https://arxiv.org/html/2407.01489v2）
- 一手/转述：一手（抓取论文 Introduction 与 "7 Threats to Validity" 原文）
- 成立条件：SWE-bench Lite；GPT-4o；不使用自主 agent 规划，改用三阶段固定流水线（定位→修复→验证），无自由工具调用。
- 报告的失败率/局限（原文，对比"agent 式"系统的失败模式）：
  - "Complex tool usage/design... incorrectly or imprecisely defining/using a tool can both reduce performance and incur additional cost in wasted LLM queries."
  - "Lack of control in decision planning... can be extremely easy for autonomous agents to become confused and perform sub-optimal explorations."
  - "Limited ability to self-reflect... they tend to take all information/feedback and do not know how to filter out or correct irrelevant, incorrect, or misleading information."
  - Threats to Validity: "One threat to validity comes from the data leakage of ground truth developer patches in SWE-bench Lite being part of the training data for GPT-4o." 以及外部效度："While the performance of Agentless might not generalize to other datasets..."
  - 解出率：SWE-bench Lite 27.33%（开源方案中最高），成本 $0.34/issue，低于同期 agent 式方案。
- 与 TUI/桌面关系：Agentless 的核心论证——"自由探索式的工具调用循环本身是失败源之一（迷失在长轨迹里、无法自我纠错、误用工具）"——对设计任何要给调试 agent 接入 TUI/截图/无头终端等丰富工具的场景是直接的反例证据：工具越复杂、自主规划空间越大，失败模式（confusion、sub-optimal exploration、无法过滤误导信息）越明显；这与"多给 agent 一种观测手段就默认更好"的直觉相反。

### A5. OpenHands: An Open Platform for AI Software Developers as Generalist Agents
- 版本/年份：arXiv:2407.16741（ICLR 2025 会议论文；原名 OpenDevin）
- URL：https://arxiv.org/abs/2407.16741 （PDF 全文：https://arxiv.org/pdf/2407.16741）
- 一手/转述：一手（抓取论文 PDF 正文相关段落）
- 成立条件：Docker 沙箱隔离执行环境；Event Stream 作为状态载体；工具接口包括 IPythonRunCellAction / CmdRunAction（执行 Python/bash）、BrowserInteractiveAction（浏览器交互）、AgentSkills（Python 工具库，自动导入 Jupyter IPython 环境）。
- 报告的局限（原文）：
  - "A key component of this state is the event stream, which is a chronological collection of past actions and observations"（观测与动作统一记录在同一事件流中，供 agent 和调试者回放）
  - "For each task session, OpenHands spins up a securely isolated docker container sandbox, where all the actions from the event stream are executed."
  - "Most AI agents today are still research artifacts and lack the ability to perform complex, long-horizon tasks in the real world reliably."（论文自陈的整体局限）
  - 风险缓解策略而非解决方案："OpenHands helps mitigate risks by: (1) Enabling systematic evaluation... (2) Facilitating human-agent interaction rather than allowing agents to operate autonomously without oversight."——即论文承认长时程可靠性问题未解决，只能靠评测与人类监督缓解。
- 与 TUI/桌面关系：OpenHands 的 Event Stream 设计（把所有 action/observation 按时间顺序统一记录）是"给 agent 提供可回放执行历史"的一手工程先例，其证据是"结构化事件流"本身被当作可观测性的基础设施，而不是事后加的日志——但论文同时承认这不能解决长时程任务的根本可靠性问题，只是提供了系统性评测和人工介入的抓手。

## B. 假设驱动调试与经典科学式调试方法

### B1. Andreas Zeller, "Yesterday, my program worked. Today, it does not. Why?"
- 版本/年份：ESEC/FSE 1999（Springer LNCS vol. 1687, pp. 253–267），DOI 10.1007/3-540-48166-4_16
- URL：https://www.st.cs.uni-saarland.de/publications/files/zeller-esec-1999.pdf （论文详情页：https://www.st.cs.uni-saarland.de/publications/details/zeller-esec-1999/）
- 一手/转述：转述（原始 PDF 为扫描/二进制流，WebFetch 无法可靠抽取文本；以下内容经 WebSearch 多源交叉确认，包括 Saarland 大学出版页与后续综述引用）
- 成立条件：需要有一个"曾经能工作的版本"和"现在失败的版本"之间的一组变更（deltas），且失败可重复判定（pass/fail 二元）；案例研究对象是 GNU debugger 4.16→4.17 与前端 DDD 的集成回归。
- 报告的局限/案例数据：GDB 两个版本之间发生了 178,000 行代码变更，delta debugging 原型在数小时内自动定位到单一致因变更（"tracked down a single failure-inducing change from 178,000 changed GDB lines within a few hours"，多个二手源交叉确认同一数字，但未能从一手 PDF 中直接取得精确到"最终归约到几行"的原文数字，此处标注为转述层面的局限）。
- 与 TUI/桌面关系：delta debugging 的前提"存在二元可判定的 pass/fail oracle"，是它能自动化二分定位的必要条件；对 TUI/桌面渲染问题（"看起来不对"往往不是布尔判定，而是视觉/语义判断）而言，这个前提本身能否成立是决定该方法能否移植的关键问题，论文本身没有讨论非二元失败判据下的适用性。

### B2. Andreas Zeller, Ralf Hildebrandt, "Simplifying and Isolating Failure-Inducing Input"
- 版本/年份：IEEE Transactions on Software Engineering, vol. 28, no. 2, pp. 183–200, Feb. 2002（DOI 10.1109/32.988498）；另有 2025 年同作者回顾文章 "A Retrospective on Delta Debugging"（IEEE TSE, DOI 10.1109/TSE.2025.3537167）
- URL：https://www.cs.purdue.edu/homes/xyzhang/fall07/Papers/delta-debugging.pdf （原文 PDF，WebFetch 抽取失败，二进制流）；二手转述来源：https://blog.acolyer.org/2015/11/16/simplifying-and-isolating-failure-inducing-input/
- 一手/转述：转述（经 the morning paper 的二手总结间接确认）
- 成立条件：ddmin 算法保证"最终返回一个 1-minimal 的失败诱因输入"，但其效率高度依赖能否把输入切分成能产生"确定性（最好是失败）测试结果"的小块——即：算法收敛速度依赖输入的可分解性与测试结果的确定性，非在所有输入类型上等效高效。
- 报告的局限（转述原文）："Whether this 'best case' efficiency applies depends on our ability to break down the input into smaller chunks that result in determined (or better: failing) test outcomes."（当输入不能被有意义地切分为独立的小块，或测试结果本身不确定/不可重复时，ddmin 的最佳情形效率不成立）
- 与 TUI/桌面关系：这条局限直接映射到"终端输出流/GUI 事件序列能否被切分为独立小块并各自判定 pass/fail"——终端渲染是高度状态相关（前一帧的光标位置、颜色状态会影响后续帧解释）的流，是否满足 ddmin 所需的"可分解性"是一个需要单独验证的前提，论文层面只对独立输入元素的场景给出了保证。

### B3. Wong, Gao, Li, Abreu, Wotawa, "A Survey on Software Fault Localization"
- 版本/年份：IEEE Transactions on Software Engineering, vol. 42, no. 8, pp. 707–740, 2016（DOI 10.1109/TSE.2016.2521368）
- URL：https://doi.org/10.1109/TSE.2016.2521368 （ACM DL 镜像：https://dl.acm.org/doi/10.1109/TSE.2016.2521368）
- 一手/转述：转述（经 WebSearch 获取摘要级原文片段，未能抓取全文限制章节）
- 成立条件：综述覆盖 SBFL（spectrum-based）、slice-based、program-state-based、machine-learning-based 等多类故障定位技术家族，横向比较各自假设（如需要通过/失败测试集、需要程序切片能力等）。
- 报告的局限（原文摘要片段）："Software fault localization... is widely recognized to be one of the most tedious, time consuming, and expensive – yet equally critical – activities in program debugging." 以及 "due to the increasing scale and complexity of software today, manually locating faults when failures occur is rapidly becoming infeasible"——综述本身未在可抓取片段中给出"无单一技术全面占优"的精确措辞，此处如实标注为未核实到一手原文（避免编造引文）。
- 与 TUI/桌面关系：综述确认故障定位技术家族普遍假设"存在可执行、可插桩、可获取覆盖率/状态的程序"，这对 TUI/桌面场景意味着——若要复用 SBFL 类方法定位"渲染错误"，需要先把"渲染是否正确"转成可插桩的程序谓词，这一步在综述覆盖范围之外。

### B4. Pearson, Campos, Just, Fraser, Abreu, Ernst, Pang, Keller, "Evaluating and Improving Fault Localization"
- 版本/年份：ICSE 2017（IEEE/ACM 39th Intl. Conf. on Software Engineering, pp. 609–620）
- URL：https://ieeexplore.ieee.org/document/7985698/ （技术报告版：https://www.cs.washington.edu/tr/2016/08/UW-CSE-16-08-03.pdf）
- 一手/转述：转述（经 WebSearch 交叉多个摘要/引用来源确认，未直接抓取全文）
- 成立条件：复现 10 项此前文献中关于 SBFL 有效性的主张，先在 3,242 个人工注入故障（mutants）上验证，再在同一批 6 个真实程序上的 323 个真实 bug 上重新验证。
- 报告的局限/关键发现（转述）："Of the previous claims, 7 were supported as statistically significant on artificial faults, but only 3 had non-negligible effect sizes. However, when evaluated on real faults, every previous result was refuted or was statistically and practically insignificant." 结论："artificial faults (e.g., mutants) are not an adequate substitute for real faults for the task of evaluating a fault localization technique."
- 与 TUI/桌面关系：这是自动调试研究中最重要的负面结果之一——在人工合成的故障基准上成立的定位技术有效性，几乎全部无法在真实故障上复现。对任何打算用"人工注入 UI 缺陷"的基准来验证调试 agent 有效性的做法，这条证据说明结论外推到真实缺陷的风险是有实证先例的，而不是理论推测。

## C. 可观测性规范：trace/log 关联用于根因分析

### C1. OpenTelemetry Logs (Specification)
- 版本/年份：opentelemetry.io 当前发布规范（页面未标注独立版本号，语义约定总版本参见 semconv 1.44.0，见 C2）
- URL：https://opentelemetry.io/docs/specs/otel/logs/
- 一手/转述：一手（WebFetch 抓取规范原文）
- 成立条件：日志与 trace 的关联依赖 **执行上下文（execution context / trace context）在应用侧被主动传播并写入日志记录**；不是自动发生的。
- 报告的局限（原文）："By the execution context, also known as the trace context. It is a standard practice to record the execution context (trace and span IDs as well as user-defined context) in the spans. OpenTelemetry extends this practice to logs where possible by including TraceId and SpanId in the LogRecords." 以及关键限制："system logs either do not include any data about the trace context or if included it is highly idiosyncratic and thus difficult to identify, parse and use. This makes it nearly impossible to perform trace context correlation for system logs."
- 与 TUI/桌面关系：这条限制直接适用于"用 OTel 思路关联 CLI/TUI 的系统日志（如终端本身、shell、tmux 产生的日志）与 agent 的执行 trace"——规范原文明确承认系统日志普遍不携带 trace context，跨系统边界（例如 agent 进程与它启动的子进程/TUI 应用）做关联在事实上接近不可行，除非应用层显式插桩传播。

### C2. OpenTelemetry Semantic Conventions — General Logs Attributes
- 版本/年份：semconv 文档当前版本 1.44.0（发布页 https://opentelemetry.io/docs/specs/semconv/ 显示的版本号）
- URL：https://opentelemetry.io/docs/specs/semconv/general/logs/
- 一手/转述：一手（WebFetch 抓取）
- 成立条件：适用于已按 OTel SDK/API 插桩的应用日志字段命名。
- 报告的局限（原文）：该页面所有日志相关属性（通用日志标识属性、日志文件属性、I/O 流属性）均标注为 **"Development"** 稳定性等级，而非 "Stable"——即这些字段的命名/语义在规范层面仍可能变化，尚未进入稳定承诺阶段。
- 与 TUI/桌面关系：若把"日志-trace 关联"当作根因分析基础设施来设计调试 agent 的可观测层，需要注意其底层字段规范本身仍处于 Development 阶段，跨版本兼容性未获稳定承诺。

## D. TUI 专项：终端录制回放与无头终端仿真

### D1. asciicast file format, version 2（asciinema 项目规范）
- 版本/年份：asciicast v2（asciinema 当前 CLI 默认输出已切换到 v3，但 v2 是仍被广泛使用、文档化最完整的历史稳定格式）
- URL：https://docs.asciinema.org/manual/asciicast/v2/ （项目主页：https://github.com/asciinema/asciinema）
- 一手/转述：一手（WebFetch 抓取规范原文）
- 成立条件：录制对象是终端的标准输出（stdout）流 + ANSI 转义序列；每帧以 `[time, code, data]` 三元组记录，time 为相对录制起点的秒数；header 中必须含 `width`/`height`（终端尺寸），可选 `duration`。
- 报告的局限（原文）：
  - "asciinema CLI doesn't capture keyboard input by default. All implementations of asciicast-compatible terminal recorder should not capture it either unless explicitly requested by the user."——**默认不录制键盘输入**，只录制输出；若调试目标涉及"agent 敲了什么导致了什么"，默认格式不足以复现完整因果链，需要显式开启输入录制。
  - v2 与 v1 格式不兼容（JSON 数组式改为逐行 JSON），历史录制文件在工具链升级后可能需要转换。
  - 支持 `idle_time_limit` 把终端空闲时间压缩到上限值，这意味着**录制的时序本身可以被人为压缩**，不是绝对忠实的时间线（用于回放时的可观测性分析要注意这一失真）。
- 与 TUI/桌面关系：这是"终端录制回放"最直接的一手工程规范，明确了它能提供什么（输出流 + ANSI 序列 + 终端尺寸 + 可选输入）和不能提供什么（默认无输入、时序可被压缩失真）。用它做 agent 调试的证据链时，"agent 看到的和实际发生的是否一致"取决于是否显式开启了完整的输入录制与未压缩时序。

### D2. ttyrec 格式
- 版本/年份：原始实现无正式版本号（0xcc.net/ttyrec/），多个社区分支（ovh-ttyrec、mjording/ttyrec）延续同一二进制格式
- URL：https://github.com/mjording/ttyrec （社区镜像）；概述性说明：https://handwiki.org/wiki/Ttyrec
- 一手/转述：转述（WebSearch 综合多个 GitHub 仓库描述，未获取到 0xcc.net 原始规范全文）
- 成立条件：录制文本模式程序（如 emacs -nw、vi、lynx）在真实 tty 上的输出，附带微秒级时间戳。
- 报告的局限（转述原文）："The format does not contain any information about the character set used nor about the terminal size needed to play back the file. Additionally, the 32-bit sec range makes the format susceptible to the Year 2038 problem."——**格式本身不记录字符集与终端尺寸**，回放时若终端尺寸不匹配会导致渲染错位；32 位时间戳有 2038 年问题。
- 与 TUI/桌面关系：与 asciicast 相比，ttyrec 是更"轻量但信息量更少"的历史格式——它把"如何正确回放"的责任完全推给外部约定（回放者必须自行知道原始终端尺寸/字符集），是"录制—回放"链路中一个已知的、结构性的信息缺口，而非实现细节问题。

### D3. @xterm/headless（xterm.js 的无头版本）
- 版本/年份：xterm.js 项目当前维护分支（包名从 `xterm-headless` 迁移至 `@xterm/headless`），无单一论文版本号
- URL：https://www.npmjs.com/package/@xterm/headless （直接 WebFetch 该 npm 页面返回 HTTP 403，以下内容转述自 WebSearch 摘要 + 一手抓取的 TypeScript 声明文件头注释）
- 一手/转述：一手（类型声明文件 `xterm-headless.d.ts` 头注释）+ 转述（npm 页面描述，经 WebSearch 汇总）
- 成立条件：在 Node.js 中运行、不依赖 DOM，用于**在没有可视渲染的情况下维护终端状态机（VT100/VT220 解析 + 屏幕缓冲区模型）**；官方原话（转述）："a stripped down version of xterm.js that runs headless in Node.js... useful in combination with the frontend xterm to keep track of a terminal's state on a remote server where the process is hosted."
- 报告的局限（一手，来自类型声明文件头注释）："Note that some interfaces differ between this file and the actual implementation in src/, that's because this file declares the *public* API which is intended to be stable and consumed by external programs."——即公开类型声明与内部实现可能不完全一致，且官方文档强调"部分 API 标注为 experimental，可能不提供正常 semver 保证"（经 WebSearch 摘要确认，未逐字核验该句在当前版本文档中的措辞）。
- 与 TUI/桌面关系：这是"让 agent 以结构化方式断言终端状态"（而非只看原始字节流）的核心一手技术依据——它把 ANSI/VT 转义序列解析为屏幕缓冲区对象，可供程序化查询（某行某列的字符/颜色是什么），是"无头终端仿真断言"这一手段的具体实现基础；局限在于其 API 稳定性声明本身有限定范围（"public API"与"实现细节"分离，experimental 部分不受 semver 保护）。

## E. 桌面专项：Chromium/Electron DevTools Protocol 与 accessibility tree 取证

### E1. Chrome DevTools Protocol — Accessibility Domain
- 版本/年份：CDP "tot"（tip-of-tree，随 Chromium 演进，无独立版本号；`getFullAXTree` 标注为 Experimental）
- URL：https://chromedevtools.github.io/devtools-protocol/tot/Accessibility/
- 一手/转述：转述（直接抓取该页面被重定向拦截，无法取得原文；以下内容转述自 Chrome for Developers 官方博客对同一 API 的说明）
- 成立条件：需先启用 Accessibility domain；`getFullAXTree` 可选 `depth`/`frameId` 参数控制抓取范围；默认按需（lazy）展开子树。
- 报告的局限（转述原文，来自 https://developer.chrome.com/blog/full-accessibility-tree ）："we need to construct yet another tree than what is available on the backend"——因为 Chrome 把跨站文档隔离到不同渲染进程，前端必须对每个 out-of-process 子文档单独发起 CDP 请求获取其 accessibility 子树，再在前端"拼接"成一棵看起来连贯的树，但这些子树实际生活在不同的渲染进程里；树是懒加载构建的（节点展开时才通过 CDP 拉取子节点）；此外，"ignored" 节点和无名字的 "generic" 角色节点默认被隐藏，不出现在树中。
- 与 TUI/桌面关系：这条限制说明 accessibility tree 并非"渲染结果的镜像"，而是**按需拼接、经过语义过滤（隐藏无意义节点）的二次构造产物**——如果调试 agent 依赖 AX tree 断言"页面上有什么"，需要意识到：(1) 跨 frame/跨进程场景下拿到的是拼接结果而非单一权威快照；(2) 部分节点因为"无语义"被主动过滤掉，即便它们在视觉上确实存在渲染差异。

### E2. Electron 官方文档 — Automated Testing
- 版本/年份：Electron 官方文档当前版本（electronjs.org/docs/latest）
- URL：https://www.electronjs.org/docs/latest/tutorial/automated-testing
- 一手/转述：转述（经 WebSearch 摘要；未逐字抓取全文）
- 成立条件：Electron 应用可通过 Playwright 对 Electron 的**实验性支持**（依托 Electron 对 Chrome DevTools Protocol 的支持）进行自动化，或通过已废弃的 Spectron（基于 WebDriverIO + ChromeDriver）。
- 报告的局限（转述）：Spectron 仓库标注为 **DEPRECATED**（"DEPRECATED: Test Electron apps using ChromeDriver"，见 https://github.com/electron-userland/spectron ）；Playwright 对 Electron 的支持被官方文档描述为"experimental"。Spectron 的 `auditAccessibility()` 方法依赖 Google 的 Accessibility Developer Tools 库，该库本身聚焦网页无障碍审计规则，不等同于"渲染正确性"检测。
- 与 TUI/桌面关系：桌面（Electron）取证链路里，曾经的官方推荐方案（Spectron）已废弃，当前依赖的是"实验性"CDP 支持——这意味着"用 CDP 自动化取证 Electron 应用"目前没有一个官方标注为"稳定"的一手工具链，选择这条路径本身要承担实验性 API 的变动风险。

### F2. An Empirical Analysis of UI-based Flaky Tests
- 版本/年份：arXiv:2103.02669（2021）
- URL：https://arxiv.org/abs/2103.02669 （全文渲染：https://ar5iv.labs.arxiv.org/html/2103.02669）
- 一手/转述：一手（WebFetch 抓取 ar5iv 渲染全文相关段落）
- 成立条件：分析 235 个来自 62 个项目（Web 与 Android 环境）的真实 flaky UI 测试样本（Web 152 个，Android 83 个）。
- 报告的失败率/局限（原文数字）：
  - Async Wait Issues 占 45.1%（105/235）——网络资源加载、渲染、动画时序问题导致的不确定性是 UI 测试不稳定的最大来源；
  - Environment Issues 18.7%（跨浏览器/设备的平台特定渲染差异）；
  - Test Runner API Issues 17.0%；Test Script Logic Issues 19.1%。
  - 论文强调 "UI tests introduce new sources of flakiness"，且 "larger input spaces and more diverse running conditions than traditional unit tests"，"more complex and resource-heavy"（导致重跑多次以检测不稳定性的常规做法在 UI 测试上不现实）。
- 与 TUI/桌面关系：这组量化数据（近半数 UI flaky 测试源于异步等待/时序问题）直接适用于给调试 agent 设计"何时截图/何时读取终端缓冲区判定完成"的时机——时序判定不准确是 UI 级观测手段里最大、最普遍的不可靠来源，且不是某个工具的实现缺陷，而是跨 Web/Android/（可推广到 TUI/Electron）环境的共性问题。
