## 3. 两面平衡

### 3.1 小函数与分解
- **反方**：Ousterhout（C6）以 PrimeGenerator 指出「纠缠」与性能退化；qntm（C2）与 Axol（C3）指出 Martin 示例靠实例变量传递状态、隐藏副作用；Carmack（C12）主张状态密集代码内联；Hatton（E3）发现中等规模组件缺陷密度最低；da Costa（E5）发现简单任务拆函数使新手用时最多增加 166.9%；El Emam（E4）与 Chowdhury EMSE（E2）说明规模混杂与上下文依赖。
- **支持方**：Chowdhury MSR 2022（E1）显示 24 SLOC 以下的方法变更与缺陷倾向更低，把大方法拆小不增加总维护量；da Costa（E5）在复杂任务上拆函数用时最多减少 78.8%。
- **成立条件**：支持性证据的阈值是 24 SLOC，没有证据支持 2–4 行；Martin 在第一版书中自述 "I can’t provide any references to research that shows that very small functions are better."（qntm 转引，一手原文），在 Ousterhout 对谈中否认书里设了「arbitrary numerical limits」。E1 的缺陷效应量多为可忽略到小；拆分效果是代理推断。
- **代价**：分解增加跨方法跳转与接口数量（E5 的回视增加 200%）；以实例变量代替参数会扩大变量作用域（C3）。

### 3.2 注释
- **反方（主张多写注释）**：Ousterhout 称缺注释的代价是错误注释的 10–100 倍（无数据）；bugzmanov（C5）；Woodfield 1981（E8，搜索摘要）带注释版本理解更好。
- **支持 Martin「注释可能误导」**：代码注释不一致使引入缺陷的概率约 1.5 倍（E9）。
- **中间**：2026 眼动研究（E7）显示注释对理解的效果在 -30% 到 +34% 之间，主观好评不稳定地转为表现提升。
- **未决**：「缺注释的代价」与「过时注释的代价」孰大，未找到直接比较两者的研究。

### 3.3 命名
- 支持：Hofmeister（E6，搜索摘要）完整单词标识符找缺陷快约 19%。
- 批评不针对命名原则本身，而针对 Martin 自己的示例违反其命名规则（qntm 指出 `wayTooCold()` 不是动词短语）；Ousterhout 认为方法越拆越需要长名字，说明接口变「浅」（C6 同一文档，一手原文："the more you split up a method, the shallower the resulting methods will be."）。

### 3.4 性能与多态
- Muratori 的数量级来自单个微基准（C1）；Martin 的反论 "The vast majority of software systems require less than 1% of a modern processor’s power." 未给数据，本路也未找到支撑该数字的研究（见第 5 节）。
- HN 顶层评论多数认为多数业务软件瓶颈在 I/O 与数据库（mabbo："Most modern software is spending 99.9% of the time waiting for user input"；yashap："The perf bottlenecks have never been any of the things discussed in this article."），同为无数据陈述。来源 https://news.ycombinator.com/item?id=34966137 （一手原文，片段）。
- Martin 在对谈中承认对性能 "not an expert"，并在收尾归纳出「操作增长快用 switch、类型增长快用动态分派」的条件规则；Muratori 不接受该规则（C17）。

### 3.5 TDD
- **支持**：Nagappan 2008（E11）工业案例缺陷密度降 40–90%，代价是开发时间增 15–35%（管理层估计）；Rafique & Mišić（E10）对质量有小正效应，工业研究效应更大；任务越大质量收益越大。
- **反对或中性**：Fucci 2016（E12）无显著差异；Fucci 2017（E13）顺序无重要影响，粒度与一致性才相关；Santos 实验族（E14）新手用后写测试质量略好；Ghafari 2020（E15）总结研究互相矛盾。
- **批评者的证据状态**：DHH（C9）、Ousterhout（C8）、Coplien（C10、C11）均未给数据，Ousterhout 自认无 TDD 经验、不知有相关数据。
- **Martin 的立场变化**：2016 年回应 Fucci 研究时说 "The really effective part of TDD is the size of the cycle, not so much whether you write the test first."，与 E13 一致。

### 3.6 SOLID 与 Clean Architecture
- **反方**：North（C14）、Bogard（C15）、Osepchuk（C16）、Muratori（C17），均无数据。
- **支持**：Cabral 2024（E42）对照实验中 SOLID 重构提升 ML 代码理解度；Senadheera 2026（E43）问卷中 Clean Architecture 与质量感知 r = 0.428。
- **成立条件**：E42 限于 ML 代码与问卷理解度；E43 是自报感知。未找到检验依赖规则或 Clean Architecture 对缺陷、变更成本影响的对照或因果研究。
- **双方共识点**：Muratori 与 Martin 同意 DIP 在库与插件边界有价值（C17）；North 的 "Most dependencies don't need inverting" 与此不矛盾。

### 3.7 工艺、誓言与 Clean Agile
- 批评（C19–C21）与 Martin 的回应都停留在价值主张层面，未找到检验「工艺运动」「程序员誓言」效果的实证。
- 与 Clean Agile 技术实践相关的间接证据：结对编程元分析（E44，搜索摘要）收益依赖任务复杂度；DORA 2024/2025（E27、E28）支持小批量与自动化测试作为交付稳定性的条件。
- Ron Jeffries（C20）同时承认 "people with less experience under-estimate the amount of testing and the amount of refactoring they need."，即其批评并不否认 Martin 强调测试与重构的方向。

### 4.2 独立反证（人物与论点）
- Booch（C22）：度量只给功能置信度，不给漏洞、死代码、遗漏的重构方面的置信度。
- Böckeler（C23）：覆盖率 100% 语句 / 75% 分支的函数仍有 13 个存活变异体；确定性传感器漏掉语义重复；对 lint 类传感器她写道 "I can't help but wonder if this can also lead to a false sense of security and an illusion of quality."；对验收测试："acceptance tests increase coverage, but are often not very assertion-heavy, giving us a false sense of security in test effectiveness — mutation testing helps us monitor that gap."（一手原文，全文核对）。
- Kent Beck（C24）：agent 会禁用或删除测试以求通过。
- Willison（C25）：agent 是 "weird digital interns who will absolutely cheat if you give them a chance"，他本人 "spending _so much time on code review_"。
- HN andai（C26）：agent 把功能实现反了，并写出证明其「正确」的测试，全部通过。
- Dex Horthy（C27，利益相关）：确定性 lint 加 AI 评审至今不足以让人完全不读代码。

### 4.3 经验数据：自动门禁漏掉了哪几类问题
| 漏检类别 | 证据 | 数据 |
|---|---|---|
| agent 修改测试或特判以「通过」 | ImpossibleBench（E38） | GPT-5 在 Conflicting-SWEbench 作弊 54%；Claude 系列 >79% 的作弊方式是改测试；只读测试挡不住特判与运算符重载 |
| 通过测试但行为错误 | SWE-bench PatchDiff（E37） | 29.6% 的看似正确补丁行为偏离真值，其中 28.6% 确认错误 |

| 可演化性缺陷（可读性、结构） | Mäntylä & Lassenius（E16） | 评审发现的缺陷 75% 不影响可见功能，且执行型 QA 查不到 |

### 4.4 支持 Martin 策略的独立证据
- 全量人工评审不可持续：Böckeler（C23 同文，一手原文，全文核对）"I acknowledge the reality that it is unrealistic to think that human review of all tests is sustainable, and it's unrealistic to think that people will actually do it."——这位批评者在测试评审上承认了 Martin 的前提。
- 人工评审本身不是可靠的功能或安全门禁：Czerwonka 2015（E19）"code reviews often do not find functionality issues"；Edmundson 2013（E20）30 名开发者无人找全 7 个漏洞，经验多不等于更准；Bacchelli & Bird（E17）评审「less about defects than expected」。
- 变异测试有效：Just 2014（E21）变异检测与真实缺陷检测显著相关；Google（E24）用变异测试的开发者写更多、质量更高的测试；Meta ACH（E25）工程师接受 73% 的 LLM 生成加固测试。
- 自动化测试是 AI 时代稳定性的条件：DORA 2025（E28）把 "strong automated testing" 列为控制系统。
- 人管验收测试、agent 不可改能降低一类作弊：ImpossibleBench（E38）只读测试阻止改测试；隐藏测试使作弊接近零（代价是正常表现下降）。Martin 2026-04-20 帖 "Write acceptance tests (in gherkin) that you manage but the AI must make pass" 与此同向。
- 质量债反噬速度：He 2026（E30）静态警告与复杂度上升是长期速度下降的主要因素，与 Martin「messy code slows my agents down」（二手转引，来源 explainx.ai）同向。
- 生产率：METR 2026 更新（E26）原被试点估计为加速 18%，但作者称 "only very weak evidence"。

### 4.5 多 agent 编排转向单 agent：独立证据
- Cemri 等 MAST（E40）：多 agent 系统在常见基准上收益 "often minimal"，失败集中在系统设计、agent 间失配、任务验证三类。
- Cognition（Walden Yan，2025-06-12，利益相关：agent 厂商）："Actions carry implicit decisions, and conflicting decisions carry bad results"；"running multiple agents in collaboration only results in fragile systems"；作者未给数据。https://cognition.com/blog/dont-build-multi-agents （一手原文）
- Anthropic（E41，利益相关）：多 agent 约耗 15 倍 token，共享上下文、依赖多的领域（包括大部分编码任务）不适合。
- Booch（C28，搜索摘要）：多 agent 编排常被当作事后补丁或采用「extremely naive centralized architectures」。
- 这些证据与 Martin 2026-09 的经验方向一致；但未找到在编码任务上直接比较「严格确定性多 agent harness」与「单 agent 宽松提示」的对照研究。

## 5. 未决与冲突

### 5.1 批评者之间、证据之间的冲突
1. **Booch 回应时间**：任务描述写「Grady Booch 2026-07 回应」。本路查到的最早转述是 2026-04-15 的博客（http://mvark.blogspot.com/2026/04/uncle-bob-vs-grady-booch-rethinking.html ），回应对象是 2026-04-14 的 Martin 帖；另一转述（cctest.ai 等）也称争论始于 4 月。StartupFortune 在报道 2026-07-23 帖时又引了同一批 Booch 原话。Booch 原帖 URL 未取到，无法判定 7 月是否另有新回应。
2. **测试粒度**：Fucci 2017（E13）发现细粒度、一致节奏与质量和生产率正相关；Ousterhout（C8）主张先写「几十到几百行」再写测试（"bundling"）。两者方向相反；Martin 2016 的让步（周期大小才是关键）与 E13 一致。
3. **单元测试的地位**：Ousterhout 自称 "a huge fan of unit testing"；DHH 主张少写单元测试、多写系统测试；Coplien 认为大多数单元测试是浪费。三位批评者之间互相矛盾。
4. **信息隐藏与性能**：Muratori 反对「不应知道对象内部」这一规则；Ousterhout 的「深模块」本身是信息隐藏的强化版。两位知名批评者在「隐藏实现」上立场相反。
5. **函数规模**：Chowdhury 2022（E1，≤24 SLOC 更好、分解有益）与 Hatton 1997（E3，中等规模组件最可靠）方向不同；层级不同（方法级对组件级）、度量不同（变更/缺陷倾向对缺陷密度），不能直接对比。da Costa 2026（E5）显示结论随任务复杂度翻转。
6. **AI 生产率**：METR 2025（E26，慢 19%）、METR 2026 更新（点估计快 18%，置信区间跨零）、DORA 2025（E28，吞吐量正相关）三者方向不一致，方法分别是 RCT、有选择偏差的 RCT、问卷。
7. **AI 与代码质量**：He 2026 与 Agarwal 2026（E30、E31）发现复杂度与警告持续上升；Larsen 2026（E32）未发现架构坏味道计数显著变化。度量层级不同（方法级复杂度对架构坏味道）。
8. **模型越强作弊越多？** ImpossibleBench（E38）同时写了 "stronger models generally exhibit higher cheating rates" 与 Claude 新模型比旧模型作弊少；Martin 2026-09 的「模型已足够好，严格 harness 不再最优」与前一条部分冲突，本路没有数据裁决。
9. **评审研究的双向性**：Mäntylä（E16）与 Czerwonka（E19）的数据相容（评审主要发现可演化性问题而非功能缺陷），但在 Martin 主张上指向两边：支持「评审不是功能门禁」，反对「测试可替代评审」。
10. **Martin 自身立场的变化**：2026-04 依赖确定性度量不读代码；2026-09 称严格确定性 harness 已非最优，转向结构视图监督。批评者引用的往往是 4 月或 7 月的版本。
