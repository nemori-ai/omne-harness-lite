# Interview core: Matt Pocock × Robert C. Martin

Paraphrased coverage of the 17-turn interview, snapshot SHA-256 `72e04c65ee930ba574a75e79a065a115f8fdf7732c0aff46b56f0f026df01684`. Full 242-item list: `uncle-bob-complete-coverage.md`. Every claim is **Uncle Bob**, **Interviewer/Ousterhout context**, or **Implementation adaptation**. Cite `UB-xx-yy`. Do not treat this file as a restatement of all 242 items.

## 1. Verdict

A harness that takes Bob seriously treats coding Agents as fast probabilistic workers inside a deterministic control system. Keep each worker short-lived and single-purpose, process one User Story at a time, refuse growing prompt rule-books because of Lost in the Middle, and advance only when named tools report PASS. Quality is enforced by CRAP cleanup, Mutation Testing, architecture dependency rules, and black-box UI/interface QA—not by human line review of generated code, not by immortal personas, and not by a grand up-front plan. The human owns peripheral constraints and verification; the code belongs to the Agents. If the pipeline becomes slower than a comparable human, the economic case is gone.

## 2. Operating principles

1. **Prompt prose is not a control plane.** **Uncle Bob:** early prompts packed TDD, Clean Code, and code-shape rules into a 5–10-page rule book (UB-08-01–UB-08-03). Models treat those rules as guidelines, not iron law (UB-08-04, UB-08-05). The technical cause is Lost in the Middle: as Context grows, the start and end of the window receive the highest weight; middle instructions (the 50th, the 80th) drop out, and the Agent cannot hear them (UB-08-06–UB-08-10). Compress the initial Prompt so the highest-priority instructions stay salient; move remaining quality control onto deterministic tools, which do not vanish as Context grows (UB-08-11–UB-08-15). **Implementation adaptation:** a growing `AGENTS.md` is the same failure mode.

2. **PASS is a tool result, not a sentence.** **Uncle Bob:** deterministic tools put the Agent in a self-correction loop: change code until the tool reports PASS (UB-09-04, UB-09-05). The Agent retries by refactoring functions, lowering cyclomatic complexity, and filling tests (UB-09-06). That trades some productivity for high quality (UB-09-07). Natural-language “done” is not evidence. **Implementation adaptation:** the permitted write scope, retry budget, and stop condition are repository policy, not interview numbers.

3. **Spawn for one job, then destroy.** **Uncle Bob:** multi-Agent value is parallelism plus Context control (UB-10-01–UB-10-03). Narrowing each Agent to one responsibility is how Lost in the Middle is removed (UB-10-04). Mechanism: Agent is created, performs one task, is destroyed; the next Agent enters with a clean Context (UB-10-05, UB-10-06). A long-lived coder carrying many Stories is the opposite of this mechanism. **Implementation adaptation:** hand off through repository artifacts and machine-readable reports, not inherited chat history.

4. **Do not carry mess into the next Story.** **Uncle Bob:** leaving Agent mess and starting the next task produces more mess (UB-07-01, UB-07-02). By the third task the Agent slows and struggles (UB-07-03). Agents, like human programmers, have no immunity to disordered code (UB-07-05). Past a point they cannot handle it: they spin, worsen the code, or give up; one Agent said it could not handle the work (UB-07-06–UB-07-08). Clean and harden before the next Story.

5. **CRAP is a risk score, not a coverage score.** **Uncle Bob:** CRAP (Change Risk Anti-Patterns) mixes test coverage and a function’s cyclomatic complexity through a complex formula; the score says how “crappy” the function is (UB-06-20–UB-06-22). In the early 2000s it found bad functions but cost more time than he could afford, so he shelved it (UB-06-23–UB-06-28). Agents are fast, do not care that the work is boring, and follow instructions, so he had them run CRAP on code they had just written and refactor the high-risk functions (UB-06-42–UB-06-48). Cleaner runs CRAP analysis and static refactoring and removes the Coder’s garbage (UB-10-13, UB-10-14). Human-oriented threshold: below 4 (UB-13-04). Agent-oriented: relaxed to 6 (UB-13-05); he was considering 8 (UB-13-06). **Implementation adaptation:** any concrete formula and any `<` versus `≤` reading of 6/8.

6. **Mutation Testing is the test of the tests.** **Uncle Bob:** a program walks source, flips operators (`-`/`+`, `<`/`>`, `=`/`≠`), reruns the full suite after each mutant, and expects the suite to fail; a still-green suite is a surviving mutant that must be killed (UB-06-29–UB-06-35). Early-2000s run: suite 4 minutes, hundreds of mutants, overnight, impractical for daily builds (UB-06-36–UB-06-41). Agent rerun: about 30 minutes, test holes filled (UB-06-49–UB-06-51). Hardener is the harshest stage: Mutation Testing, 100% effective coverage, every equality and greater-than, do not stop while mutants survive (UB-10-15–UB-10-19). **Implementation adaptation:** equivalent-mutant classification, waivers, and any target below “kill all survivors.”

7. **Architecture is an executable dependency policy.** **Uncle Bob:** until about a month before the interview he interrogated Agents about module structure, heard bad answers, designed the structure himself, and handed back a refactoring plan (UB-11-01–UB-11-06). He also had an Agent write an architecture viewer (UML module dependencies, drill into submodules and code) and a deterministic checker (UB-11-07–UB-11-11). He defines which modules may depend on which and which must not; that becomes a strict spec; every Agent submission must not violate it; repair is dependency inversion or Interface extraction (UB-11-12–UB-11-15).

8. **QA is black-box against the running system.** **Uncle Bob:** Specifier emits QA system-test steps; QA Agent turns that document into automatically executable scripts and deterministically verifies the system UI or interface (UB-10-09, UB-10-20, UB-10-21). **Implementation adaptation:** QA must not inspect Implementation or patch product code; product failure routes back to Coder then downstream stages.

9. **Reject grand plans; one Story, then feedback.** **Uncle Bob:** Agents love writing elaborate, detailed plans that collapse on contact with implementation (UB-14-01–UB-14-03). Heavy up-front planning is the 1970s mistake that produced Waterfall; Agile was the correction (UB-14-04–UB-14-06). He tried a large plan again that week; it was still a disaster because you cannot foresee everything, the Agent is not smarter than you, and it will run the wrong plan at speed until you throw the work away (UB-14-07–UB-14-13). Return to Agile: one User Story, inspect architecture, refactor, get feedback, next Story (UB-14-14–UB-14-17). Change cost has fallen near zero; it **might** be one or two dollars of tokens; then expensive up-front planning is the worse buy, and try-adjust-try until satisfied is the loop (UB-14-18–UB-14-21). Preserve **might**.

10. **Task Spec is ephemeral; tests and architecture rules are not the Spec.** **Uncle Bob:** there is no long-lived Spec file; Spec is ephemeral; final code and running result are their own Spec (UB-14-22–UB-14-24). **Implementation adaptation:** durable requirements for regulation, contracts, or governance are an organizational override and must be labeled as such. “Ephemeral” is not a license to discard executable regression tests or architecture checks.

11. **Keep TDD quality values; drop the human keystroke ritual for Agents.** **Uncle Bob:** Agent working memory for complexity is larger than a human’s and is exact, which is why CRAP thresholds can move (UB-13-01–UB-13-03). TDD is a discipline designed for human physiology (limited short-term memory); do not impose that discipline on an Agent (UB-13-07–UB-13-10). Line-of-test / line-of-code / line-of-test is meaningless for Agents (UB-13-11). He allows an Agent to finish a whole function and then test it, which he attributes to John Ousterhout; even under a strict TDD order, Agents slide back to that mode (UB-13-12, UB-13-13). Imposing human behavioral discipline on Agents is a mistake; imposing human quality values is correct (UB-13-14, UB-13-15). **Interviewer/Ousterhout context:** whole-function-then-test is Ousterhout’s sequence inside Bob’s answer, not Bob’s invention. Coder still writes unit tests and business code until Gherkin passes (UB-10-10, UB-10-11). First implementation is usually a mess (UB-10-12).

12. **Small Interfaces hide Implementation so Agents load less.** **Interviewer/Ousterhout context:** Deep Modules and tactical-versus-strategic programming are Matt Pocock / John Ousterhout framing in this exchange. **Uncle Bob:** he agreed (UB-12-01). Models attend closely to Interface names and structure (UB-12-02). A well-designed Interface lets the model skip reading underlying Implementation, which cuts Context cost and confusion (UB-12-03–UB-12-05). He and Ousterhout debated this in the *Clean Code* second-edition appendix (UB-12-06, UB-12-07).

13. **The human owns constraints, not line-by-line authorship.** **Uncle Bob:** Agents leave a lot of mess; deterministic tools can clean it (UB-06-52–UB-06-54). He has Agents do the work and run the tools (UB-06-55). He works extremely hard to build an environment in which he does not need to review the code (UB-06-56). He trusts the result, does not slow them with his review speed, the code is theirs, and he owns only peripheral verification and constraints (UB-06-57–UB-06-60). This interview position is “no line review because external gates exist,” not “no verification.”

14. **Economics are examples, not SLAs.** **Uncle Bob:** there is an upper bound; once the Agent is slower than a human, you have lost (UB-09-01, UB-09-02). If marginal productivity remains above the human—for example 2–4×—you are still ahead (UB-09-03). A single Agent **might** produce a quality-suspect result in 5 minutes; the full pipeline takes 1 hour; comparable human work takes half a day; that example is about 4–5×, and in his assessment the quality is far above the human’s (UB-10-23–UB-10-27). Preserve **might** on the 5-minute figure. **Implementation adaptation:** local wall-clock, retry, token-cost, escaped-defect, CRAP, mutation-survivor, and architecture-violation measurements; optimize flaky or redundant gates before weakening quality.

15. **Junior apprenticeship is not a product feature unless the product trains humans.** **Uncle Bob:** newcomers must still write code by hand long enough to know what an Agent faces; a later stage treats the newcomer as an Agent on tactical work under the same CRAP and Mutation Testing pressure; only then should they independently direct Agents; if you have never written assembly, spend a weekend—two days—doing so; Java-only is a “fantasy world”; you must know what happens below (UB-15-01–UB-15-14). **Interviewer/Ousterhout context:** tactical-versus-strategic is Pocock/Ousterhout vocabulary; Bob answered the learning-path question. Defer this path unless the harness claims to onboard humans.

16. **Stop the A→B→C spin; do not keep feeding the same Context.** **Uncle Bob:** the observed failure is change A, accidentally break B, repair B, accidentally break C, and spin in place (UB-07-04). **Implementation adaptation:** stop the loop, restore last green state, shrink Context, dispatch a fresh diagnostic or architecture pass. “Agents honking at each other” is not in the 17-turn coverage.

## 3. Pipeline contract

One small, independently verifiable User Story. Dependent stages are ordered. **Implementation adaptation:** parallelize only disjoint work; do not let multiple Agents write one worktree.

## 4. What must NOT be built

- Immortal Specifier/Coder/Cleaner/Hardener/QA personas that keep chat history across Stories (contradicts UB-10-05, UB-10-06).
- A 5–10-page Prompt or a monotonically growing `AGENTS.md` that encodes TDD, Clean Code, architecture, and style as prose (UB-08-01–UB-08-15).
- Prompt-enforced line-by-line TDD ritual for Agents (UB-13-10–UB-13-14).
- One long-lived coder for many Stories, or deferred cleanup “until later” (UB-07-02–UB-07-08, UB-10-12–UB-10-14).
- Coverage percentage as a substitute for Mutation Testing (UB-06-29–UB-06-35, UB-10-16–UB-10-19).
- Human line review as the quality bottleneck (UB-06-56–UB-06-58). Absence of line review is not absence of verification (UB-06-54, UB-06-60).
- A six-month Agent implementation plan executed without architecture inspection, refactor, and feedback (UB-14-01–UB-14-17).
- A permanent detailed feature Spec treated as more authoritative than code and running result, unless an explicit organizational override says so (UB-14-22–UB-14-24).
- Multiple Agents writing the same worktree (**Implementation adaptation** of Context control and ordered dependent stages; UB-10-02, UB-10-03). Parallelism is for independent work only.
- The same Agent both creating a quality exception and approving it (**Implementation adaptation**).
- Weakening test scope, coverage collection, mutation configuration, dependency rules, or ignore files to obtain PASS (**Implementation adaptation** of UB-11-14 and UB-09-05).
- A published CRAP formula, a strict/inclusive reading of 6/8, named packages, or equivalent-mutant waivers attributed to Bob.

## 5. Open tensions in the source

- **CRAP formula is missing.** Bob says coverage and cyclomatic complexity enter a complex formula (UB-06-21). He does not state the formula. Any `CRAP(cc, coverage)` implementation is an **Implementation adaptation**.
- **Threshold inclusivity is unspecified.** “Below 4” for humans is explicit (UB-13-04). Agent “relaxed to 6” and “considering 8” (UB-13-05, UB-13-06) do not say strict versus inclusive. A repository must declare the operator.
- **Which Agent threshold to ship.** 6 is current practice in the interview; 8 is something he was considering. Do not collapse those into one number.
- **Equivalent mutants.** The interview target is kill-all / 100% effective coverage (UB-10-17–UB-10-19). Tool limits are not discussed. Disclose any practical deviation; do not rewrite his position.
- **No line review.** In this interview he aims at an environment where he does not review code (UB-06-56–UB-06-59). Later public “watch it like a hawk” remarks are outside this snapshot and must not be mixed in here.
- **Independent rerun and anti-tampering** are not in the 242 items. They operationalize “trust the tools, own constraints.”
- **Specifier blockers, QA-must-not-edit-product, artifact handoff JSON, and worktree isolation** are role-split inferences, not quoted workflow.
- **“Agents honking at each other”** is not in the coverage. The sourced multi-Agent failure is Context pollution, Lost in the Middle, and the A→B→C spin—not inter-Agent argument.
- **Architecture vs Cleaner.** Architecture enforcement is a deterministic checker on every submission (UB-11-11–UB-11-14), not a sixth named pipeline Agent. Do not invent a “Architect Agent” as source.
- **Ephemeral Spec vs durable tests.** Bob’s Spec claim does not enumerate tests or architecture files. Treating executable gates as durable is an **Implementation adaptation** required to keep the rest of his workflow coherent.
