# Experiment policy

Each row compares two test suites for **that row’s** production program.

The product is always Greg Yob’s Hunt the Wumpus (HTW). Every run implements `requirements.md` (Yob’s rules and UI, plus the listed command-line controls). Compliance is `acceptance/htw-console.sh`. Do not substitute another kata or product.

Rows are independent. Eight rows means eight programs written from empty, and eight mutation suites grown from empty. A later row may not start from, copy, or “reinstall” an earlier row’s source or tests.

## Variables

1. **Testing discipline** — a run uses exactly one of:
   - **Three laws of TDD** — no production without a failing test; no more test than needed to fail; no more production than needed to pass.
   - **Test-last** — write the whole working HTW first, then write unit tests against that finished program.
   - **Bundling** — write one function, then test-last that function; repeat for the next function. Do not write the next function until the current one has its tests.
   - **None** — write the working HTW with no automated tests. The discipline suite is empty.
2. **CRAP reduction below 4** — on or off.

Do not change language, stack, Yob fidelity, or mutator.

CRAP is never mixed into the discipline. When the knob is on, it runs only after the discipline has created all production code (and that discipline’s tests). When the knob is off, skip it.

## Step 1 — Produce HTW under the chosen discipline

Write the program using that discipline. Write it for this row only.

Do not copy `src/htw` from another row, from `runs/`, or by reproducing a prior cell from memory. An empty tree means empty. Different disciplines are not expected to emit the same source; byte-identical production across disciplines is evidence the source was carried forward.

That yields:

- the program
- the **discipline suite**: the tests written under that discipline

If **CRAP reduction below 4** is on, run crap4clj now — after all production exists — and continue until every function’s CRAP score is below 4. CRAP(m) = C²(1 − cov)³ + C. At full coverage, CRAP equals cyclomatic complexity, so a cap below 4 requires every function’s complexity to be at most 3. The reduction may add tests, split production functions, or both.

The frozen artifacts are the discipline suite and the program as they stand after this point (after CRAP if the knob was on).

## Step 2 — Sequester the discipline suite and recreate tests by mutation

Set the discipline suite aside so the default test command no longer runs it.

Against **this row’s** frozen program, start from an empty suite. Use mutation testing to grow a second suite. Add a test only to cover an uncovered site or to kill a surviving mutant.

Do not copy another row’s mutation suite. Do not “install the campaign.” Do not skip growth because the program “is the same HTW,” the operators are unchanged, or a prior kill table would be identical. “Same production ⇒ same mutation suite” is a claim the rows may support after the fact. It is not a procedure, and it is not a reason to write a prior row’s counts into this notebook.

A mutation count is valid only for the row that grew it.

That step yields the **mutation suite**.

## Comparison

Compare the discipline suite to the mutation suite.

The comparison is between two ways of specifying the same program, not between two programs:

- the discipline suite records what the discipline asked for while the code was written, plus whatever CRAP reduction added when that knob was on
- the mutation suite records what the mutator’s operators forced afterward

Record counts, size, runtime, coverage, kill results, and — when the CRAP knob was on — CRAP scores before and after reduction. Do not treat one suite as a replacement for the other.

Record checksums of this row’s `src/htw` and of its mutation suite. If they match another row, say so in the notebook. Matching checksums do not justify having copied; they are a finding, and across different disciplines they are a warning.

## End of each row

After both suites exist and the comparison is written, run `acceptance/htw-console.sh` (`bb accept`). Write the result in that row’s notebook (`notebook-<discipline>-crap-<on|off>.md`): passed or failed, and the pass/fail counts. A row is not finished until that note is there.

Do not delete the code. Move this row’s production (`src/htw`), its discipline suite, and its mutation suite into `runs/<discipline>-crap-<on|off>/`. That directory is the implementation. The working tree is empty afterward because the files were moved, not destroyed.

The next row starts from that empty tree. It may read `runs/`; it may not copy from it.

## Write-up

The conclusion and the summary must include statistics of the implementations themselves — not only of the suites. For every row, report at least: production lines (total and per file), function counts, and checksums of `src/htw`.

Do not collapse eight implementations into one line-count if the trees differ. Do not hide it if they do not.
