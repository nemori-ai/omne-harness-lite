# Experiment plan

Execute the design in `experiment-policy.md`. This file is the run schedule.

## Constants

- Product: Greg Yob’s Hunt the Wumpus, as specified in `requirements.md`
- Compliance: `acceptance/htw-console.sh` (tmux console) must pass for a run to count
- Stack: Babashka, Speclj, clj-mutate, crap4clj
- Mutator: do not change operators or tool
- After a discipline finishes, do not reshape production except when the CRAP knob is on
- Rows are independent: write this row’s program and grow this row’s mutation suite. Do not copy from `runs/` or from a prior cell.

## Procedure (every run)

1. Build HTW under the chosen discipline to `requirements.md`. Write it for this row only, from an empty `src/htw`. That produces the program and the discipline suite (empty if discipline is **None**). `bb accept` must pass before the run proceeds.
2. If CRAP is on: run crap4clj only after all production exists; add tests and/or split functions until every function’s CRAP is below 4.
3. Record discipline-suite stats (counts, spec lines, runtime, coverage; CRAP before/after if the knob was on) and implementation stats (production lines total and per file, function counts, checksum of `src/htw`).
4. Sequester the discipline suite so the default test command does not run it.
5. From an empty suite, grow a mutation suite against **this** frozen program: tests only to cover sites or kill survivors. Do not refactor production. Do not install a prior row’s campaign.
6. Record mutation-suite stats (same measures, plus kill results and checksum of the mutation suite). A count is valid only for the row that grew it.
7. Compare the two suites for that cell. Write the notes for that run in the notebook named below. Do not treat one suite as a replacement for the other. If this row’s checksums match another row, say so.
8. Run `bb accept` and record compliance in the notebook. Do not delete the code. Move `src/htw`, the discipline suite, and the mutation suite into `runs/<discipline>-crap-<on|off>/`. The next row starts clean because the files were moved.
9. Reread `experiment-policy.md` and this plan before starting the next row. Do not start the next row from memory of the last one.

## What to write down each cell

- Implementation: production lines (total and per file), function counts, checksum of `src/htw`
- Discipline suite: examples, assertions, spec lines, Speclj time, wall time, form/line coverage
- If CRAP on: scores before and after; whether tests were added, functions split, or both
- Mutation suite: same size/time/coverage numbers; sites, killed, survived, uncovered; checksum of the suite
- A short comparison of the two suites for that cell
- Whether this row’s source or mutation checksums match another row

The conclusion and summary must include those implementation statistics for every row. Do not collapse eight trees into one line-count if they differ; do not hide it if they do not.

## Disciplines (reminder)

- **Three laws of TDD** — write the program by cycling these three, in order, and nothing else:
  1. You may not write production code unless it is to make a failing unit test pass.
  2. You may not write more of a unit test than is sufficient to fail; a compile error is a failure.
  3. You may not write more production code than is sufficient to pass the one failing test.
- **Test-last** — whole working HTW, then unit tests
- **Bundling** — one function, then test-last that function, then the next
- **None** — working HTW, no automated tests; discipline suite is empty; sequester is a no-op
