## Observations

Five complete `stop` SSE originals—Prime control/long/base and FlashX long/mixed—are preserved in the [test fixture](../../../../../packages/model/pi-ai-transport/tests/fixtures/zai/history-complete-streams.json). Each entry records its original evidence filename, original file SHA-256 and unchanged SSE SHA-256. These are arithmetic/tool research responses, not user conversation data. The fixture contains no request headers or credential. The source files remain the paid owner's evidence; copying a response into a TLS fixture does not repeat the live observation.

The [replay tests](../../../../../packages/model/pi-ai-transport/tests/zai-history-replay.spec.ts) pass these SSE strings through local HTTPS, the production transport, `readStream`, and the production stream assembly. All five preserve concatenated plaintext, merge consecutive equal-head details without dropping metadata, and close with the complete same-route opaque value. Planning a subsequent same-route request retains the exact details and refuses the current unsupported history estimate. Planning for the other commercial model carries the complete plaintext with the unbound candidate; it does not carry foreign-route opaque data. This verifies local conversion, not acceptance of a second request by a hosted model.

The [public GLM-5.3 template](https://huggingface.co/zai-org/GLM-5.3/blob/aca966e4e02791568aa6a4ced368624b3d897f42/chat_template.jinja), SHA-256 `3740abcea51c45830cb3ca562084ad5fb2ef53589376f73332e9886f93ade41c`, reads `reasoning_content` and retains it with `clear_thinking=false`. The independent [Jinja oracle](../../../../../packages/model/pi-ai-transport/tests/fixtures/zai/history-template-oracle.py) was run using Python 3.8 and Jinja2 2.10.1. Its five prompt hashes are pinned in [goldens](../../../../../packages/model/pi-ai-transport/tests/fixtures/zai/history-template-goldens.json); the TypeScript candidate matches all five. Both evaluate the public template assumption, not Prime/FlashX's unknown private template.

The [candidate](../../../../../packages/model/pi-ai-transport/src/input-meters/zai-candidate.ts) reuses the existing text/tool renderer and pinned GLM tokenizer. It retains every supported assistant plaintext reasoning field in the local template projection. It introduces no fitted offset, multiplier, model binding, or usage/cost substitution. Opaque details, unknown fields, media, foreign providers and mismatched serialized bytes remain unavailable. The normal production renderer and meters retain their prior restriction. A finite candidate count is not evidence of hosted accuracy.

## Mixed reasoning counterexample

The current shared planner loses a distinct plaintext thinking block B when the same assistant also has same-route opaque thinking A. It accumulates all plaintext, then chooses `reasoning_details` instead of `reasoning`, so the wire contains A but not B. The named expected-failure test records the missing-text assertion; **that expected failure is an open defect, not an acceptance pass**. No shared planner source is changed by this increment.

The adopted transport [message mapping](../../../../design/realization/packages/model/pi-ai-transport/design.md#线上请求怎样组) assigns same-route opaque to details and other thinking to plaintext, while [v10 input measurement](../../../../design/realization/packages/model/pi-ai-transport/v10-token-estimate-design.md) requires complete final input. The current production meter's refusal prevents this particular unsupported input from being sent; that does not make the lossy projection correct.

[OpenRouter reasoning documentation](https://openrouter.ai/docs/guides/best-practices/reasoning-tokens#preserving-reasoning), directly opened on 2026-09-28, describes plaintext and complete structured replay alternatives. Its consecutive-detail rule requires preserving the original sequence. The inspected page does not specify how a message combining additional independent plaintext and structured details is merged by every provider. This is a source gap; it is not proof that no provider can accept that combination. The candidate therefore supplies no blind two-field workaround and makes no mixed-history support claim.
