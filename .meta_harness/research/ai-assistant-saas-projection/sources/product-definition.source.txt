# AI 助理产品定义与功能需求

需求讨论稿 1.0 · 2026 年 9 月 30 日

## 文档用途与范围

本文从产品定义向下拆解能力、模块和功能，回答“用户获得什么样的助理，以及这个产品必须为用户做到什么”。配套《用户故事》从具体生活与工作旅程说明同一组需求。两份文档可以独立阅读。

本文整合当前已有体验、此前讨论的产品目标，以及本轮确认的商业服务方向。所有条目均为需求表达，不据此声明已经实现、上线或达到商业服务标准。模块按产品价值和依赖关系排列，不是技术组件、界面菜单或开发排期。

来源标记：**延续**表示现有体验及其相关要求；**既有目标**表示此前已讨论的需求；**本轮确认**表示本轮明确的定位与能力要求；**建议补充**表示为形成完整商用旅程提出、仍需产品评审的需求。一个模块可以包含多种来源；新增建议在具体条目中标明。

产品名称未定。Relay 保留为候选名称，本文不将其视为已确定品牌。

## 一 产品定义

### 1.1 一个与你共享现实处境的持续协作助理

**这是一个持续与你的目标对齐、与你共享时间语境、理解现实处境的 AI 助理。它能够主动发现值得做的事情，利用获准使用的资源，与人、其他助理及外部服务协作，并根据进展、资源余量和你的反馈调整行动，让整体投入尽可能换来对你更有价值的结果**。

用户可以直接委托工作，也可以让助理在已有目标与授权下自行发现问题、机会和改进空间。用户的新指令、环境的新变化，以及助理在持续工作中形成的新认识，都可以成为行动的理由。助理需要保持行动的连续性，同时接受用户的纠正、干预和终止。

助理的主动性包括发现、调查、准备、执行、观察结果与调整。产品需要表达它“为什么认为值得做、已经做了什么、下一步准备怎样”，而不能只通过定时提醒、未完成任务续跑或频繁发通知来表现主动。

![主动协作概念设计稿：用户与助理共同面对目标、时间、现实变化和可用资源，自主发现并行动，再依据结果调整。](../插图/01-主动协作.png)

*图解 · 主动协作的行动理由来自持续理解与共同处境，结果再进入下一轮判断。图中对象用于解释产品关系，不代表已经确定的界面。*

### 1.2 服务主体明确，协作范围开放

产品始终以“你与你的助理”为起点。你可以独立工作、参与团队、服务客户，也可以同时处理家庭和生活中的事情。协作对象可以来自任何组织，也可以完全不属于组织。

用户无须先建立团队空间、组织层级或成员席位，才能使用完整助理。已有团队关系、责任分工和外部授权仍然需要被尊重；它们是助理理解事情的现实条件，不是产品版本划分的前提。

外部参与者可以继续使用已有的沟通与工作方式。在受支持的渠道内，助理应能帮助用户跨这些边界协作，减少用户手工转述和搬运信息的负担。

### 1.3 对整体收益负责

用户的收益可以包括结果质量、节省时间、减少操心、把握机会、维护关系、控制花费和生活的从容程度。这些取舍由用户的目标与处境决定，不预设所有事情都应追求最快、最便宜或最多产出。

助理应当理解资源的充裕与匮乏：有时缺算力，有时缺可靠信息、生产档期、用户的审核时间或协作对象的注意力。它需要据此决定是否行动、投入多少、让谁参与、在哪里执行、何时收敛和何时停止。没有新的有价值动作可做时，有理由地等待也是一种合适的判断。

这一承诺描述的是助理的判断方向。产品不要求用户把生活目标换算成统一分数，也不承诺能够数学上求得所有情境的最优解。

### 1.4 注册登录即可开始

用户注册账号即可使用平台提供的整套基础服务，下载受支持的客户端后登录即可接入。用户不需要自行部署基础环境、设立主节点、维护注册中心或逐项拼装服务。

AI 与算力使用支持两种来源：用户自行提供兼容服务的 API，或使用平台提供的服务。用户可以按实际需要扩展自己的设备和远程机器；这些扩展是可选能力，不能成为首次使用的前置条件。

登录让用户接入自己的助理；读取私人邮箱、设备文件、日历或外部账户，仍通过清楚、可撤回的范围选择完成。系统代用户处理连接过程中的技术细节，用户保留业务选择与授权决定。

## 二 用户怎样理解整个产品

### 2.1 从目标到结果的连续关系

用户首先拥有的是一个持续协作的助理。助理逐步理解用户的方向与取舍，观察获准感知的现实，形成值得推进的事情；事情调用协同资源，在合适的设备或云端节点上开展工作；结果与变化再反过来影响后续判断。

| 用户关心的层次 | 用户应当理解的内容 | 在产品中可得到的回答 |
|---|---|---|
| 我与助理 | 它理解我的哪些目标、偏好与约束 | “你为什么认为这件事对我重要？” |
| 当前处境 | 现在发生了什么，时间与资源是否充足 | “现在还来得及吗，缺的是哪一项？” |
| 值得推进的事情 | 我委托了什么，它又主动发现了什么 | “你正在做什么，为什么开始做？” |
| 协同资源 | 为这件事接入了谁、哪些材料和能力 | “现在等谁，能从哪里获得下一步进展？” |
| 工作分布 | 哪些设备和远程节点在承担工作 | “为什么交给这台机器，手机关掉后还会继续吗？” |
| 成果与反馈 | 已完成什么，哪些仍待确认 | “东西在哪里，对方收到了吗，下一步怎么办？” |

这些层次可以从对话进入，也应有便于浏览和管理的可视入口。用户不应为了理解状态而阅读技术日志；想进一步追问时，可以看到真实材料、动作与结果的依据。

### 2.2 几个必须保持一致的产品概念

| 概念 | 面向用户的含义 | 重要区别 |
|---|---|---|
| 目标 | 用户希望达到的方向、状态或具体结果 | 可以持续演化，不要求一开始完整填写 |
| 事情 | 一段有语境、参与者和进展的现实事务 | 可以跨多次对话、多个资源和数周时间 |
| 对话 | 用户与助理交换意图、材料、反馈和决定的入口 | 关闭聊天窗口不等于结束事情 |
| 协同资源 | 为某件事接入的往来、参与者、资料范围、能力或工作入口 | 具有用途、范围、实际能力与使命，必要时可以持续关注 |
| 账户或服务连接 | 让一类外部能力对用户可用的长期连接 | 连接邮箱不等于关注其中全部邮件 |
| 材料 | 原文、原件及可追溯的版本与整理结果 | 存下材料不等于形成长期记忆 |
| 记忆 | 助理在持续相处中形成、可追问和纠正的理解 | 已知事实、用户表达和助理推断应有区别 |
| 设备与执行节点 | 用户接入的手机、电脑、服务器及平台可用工作环境 | 可以承载交互，也可以提供算力、材料或特定操作能力 |
| 成果 | 用户能够取得和使用的实际产物或已确认结果 | 开始执行、接受请求和得到成果是不同状态 |

### 2.3 协同资源贯穿产品

一段供应商 Gmail 往来与一位负责设计稿的 AI 助理，都可以是内容生产中的协同资源。用户使用共同的添加、引用、查看、关注、暂停与结束心智，同时能辨认每种资源的真实内容与能力。

![协同资源概念设计稿：供应商往来、设计助理与物料文件夹围绕同一件事接入，持续交流并完成使命，保留成果与历史。](../插图/02-协同资源.png)

*图解 · 邮件、其他助理和生产资料可以共同服务一件事。结束的是这次使命与后续关注，账户连接、原件和历史各自保留其原有边界。*

资源应当回答六个问题：它是什么；为哪件事服务；可以用它做什么；现在处于什么状态；哪些变化值得关注；什么时候完成使命。无需用户手填全部信息，助理可以结合已有语境补全，缺少关键事实时再澄清。

| 使用阶段 | 用户可理解的意义 | 应保留的行为边界 |
|---|---|---|
| 发现与接入 | 找到适合当前目的的人、材料或能力 | 能看到不等于已取得使用权限 |
| 使用与关注 | 读写、交流、委托，或等待相关变化 | 每种资源只提供实际支持的动作；静态材料不强制监听 |
| 变化与继续 | 收到新回复、版本或结果后继续推进 | 回到正确的事情，保持原来的目标和约束 |
| 暂停 | 暂时停止关注或后续动作 | 已经发出的动作及其结果仍需如实交代 |
| 完成使命 | 不再为这件事继续工作或关注变化 | 不自动删除资料、外部邮件或整个账户连接 |
| 再次使用 | 旧资料与经验可以为新事情服务 | 不默默复活旧监听，也不把旧范围套给新任务 |

视觉符号与快捷入口应让这种关系可见。例如用户能自然引用“印刷商打样沟通”、展开内容、补充说明并结束关注。共同外观不应抹掉具体信息：图片显示缩略图，往来显示联系人与最新消息，其他助理显示委托和交付。

### 2.4 主动与被动协作采用同一套行为原则

用户委托与助理主动发现的工作，都需要说明目的、使用获准资源、保留真实进展并接受干预。主动行动应建立在对用户连续目标的理解之上，能够带来实质工作，不止是建议用户再发一个指令。

助理可以根据已有授权直接完成读取与可控、可恢复的动作。需要追问的主要情况是：缺少影响行动的必要信息；具体行动存在尚未明确确认的不可恢复、高风险后果。首次账户连接、扩大数据范围等仍需要用户作出相应授权，但同一授权不应在每段对话重复询问。

用户沉默、没有打开通知或超时，均不构成新的授权。与用户目标的对齐发生变化时，助理应调整后续行动，妥善交代已发生的部分。

## 三 能力与模块总览

以下先描述助理成立的核心能力，再描述工作与交付，最后描述用户入口和商业服务基础。顺序体现产品逻辑，不是功能优先级。

| 层次 | 模块 | 对用户的主要价值 |
|---|---|---|
| 持续理解与判断 | M01 持续目标对齐与记忆 | 长期懂得用户，并能被纠正 |
| 持续理解与判断 | M02 时间感与现实感知 | 理解当下、时效和可见范围 |
| 持续理解与判断 | M03 主动行动与资源权衡 | 自主发现、投入、调整与收敛 |
| 向外协同与行动 | M04 协同资源 | 用共同心智连接外部世界 |
| 向外协同与行动 | M05 多节点分布式协作 | 在拥有合适算力和材料的地方完成工作 |
| 向外协同与行动 | M06 事情与长期推进 | 跨阶段、跨时间把事情做完 |
| 工作与交付 | M07 对话与多模态交付 | 准确承接用户意图、材料与动作 |
| 工作与交付 | M08 资料与个人内容 | 保留原件、版本、关系和使用语境 |
| 工作与交付 | M09 人、往来与外部协作 | 与真实参与者形成持续工作关系 |
| 工作与交付 | M10 日历、日程与持续关注 | 处理约定、执行时机和信息供给 |
| 工作与交付 | M11 调查、委派与成果 | 获得有依据、可使用的交付 |
| 工作与交付 | M12 交互式成果 | 把结果变成可继续使用的页面或工具 |
| 用户掌握与参与 | M13 视角、关注与通知批阅 | 知道轻重，及时参与需要自己的部分 |
| 用户掌握与参与 | M14 跨平台客户端与桌面助理 | 随处接入，低打扰地相处 |

| 商业服务基础 | M17 授权、隐私与行动控制 | 保持自主权，知道并控制助理的边界 |

## 四 核心能力的功能拆解

### M01 持续目标对齐与记忆

**用户结果**。相处越久，助理越能理解用户的方向、背景与取舍。用户无需每次从头解释，也可以知道助理为何这样理解自己。来源：既有目标＋本轮确认。

![几次相处形成对用户的理解，具体来源能够展开；用户指出这次情境不同后，助理调整当前判断和后续工作，原始记录仍被保留。](../插图/05-长期理解与纠正.png)

*图解 · 旧经验提供背景，用户的新反馈可以改变当下判断；记忆、证据和当前取舍各自可辨。*

| 功能 | 需求与可观察结果 |
|---|---|
| M01.1 在相处中理解目标 | 接受明确目标，也从日常协作中形成有依据的理解；首次使用不要求填写完整人生规划。 |
| M01.2 区分目标的依据 | 用户直接表达、已确认决定与助理推断应可区分；推断不能冒充用户授权。 |
| M01.3 跨对话延续 | 新对话与其他客户端可以沿用相关背景、偏好和既往取舍；调用失败不伪装成遗忘。 |
| M01.4 目标变化与重新对齐 | 用户改变方向、优先事项或现实限制后，助理能说明哪些后续工作受到影响，并调整或结束不再合适的工作。 |
| M01.5 记忆可见可检索 | 用户能查看、按主题寻找助理对自己和相关事情的理解。 |
| M01.6 依据可追问 | 每项重要理解可回到具体来源与时间，注明不确定、过时或不足的部分；不展示或编造模型内部思维过程。 |
| M01.7 纠正与生效反馈 | 用户可以指出误解；产品说明修正是否成功及后续如何使用。历史上的原话与当前理解各自保持真实。 |
| M01.8 情境有边界 | 工作项目中的局部偏好不自动成为所有生活场景的规则；外部材料中的观点不自动变成用户立场。 |

**验收场景**。用户曾表达重视交付稳定性；新项目中助理据此准备可用备选方案。用户随后说明本次更重视探索，助理调整本次工作，不把过去偏好删除或强行套用。

### M02 时间感与现实感知

**用户结果**。助理理解用户所处的时间、环境与信息状况，能区分“当时如此”与“现在如此”，以及“没有变化”与“尚不知道”。来源：既有目标＋本轮确认。

![助理把七个月前的约定与今天收到的出差邀请放到同一个时间语境中，核实日期与现实条件，再准备可行选择。](../插图/06-共同时间与现实.png)

*图解 · 时间感让新变化与旧承诺能够相遇；感知范围、来源时点和仍待核实的条件也需要清楚。*

| 功能 | 需求与可观察结果 |
|---|---|
| M02.1 共同时间语境 | 理解当前日期、时区、已经等待的时间和剩余窗口；跨时区约定保留双方可理解的时间。 |
| M02.2 截止与机会窗口 | 截止临近、报价有效期、生产档期或窗口结束，应改变工作判断；不用过期机会驱动后续行动。 |
| M02.3 现实环境可见性 | 在许可范围内感知相关材料、往来、设备及外部进展；用户能知道哪些来源可见、哪些不可见。 |
| M02.4 新鲜度与不确定性 | 状态附有可判断的时点；过时、断连、无更新、读取失败分别表达。 |
| M02.5 人的可参与程度 | 结合用户表达与获准使用的日程理解忙碌、休息、在途等处境；不能把未经证实的心理或身体状态当事实。 |
| M02.6 资源余量感知 | 知道可用预算、算力、节点负载与材料所在位置，以及相关人和生产条件的已知限制。 |
| M02.7 变化影响判断 | 新回复、资料更新或环境变化到达后，能指出影响哪些目标、事情和已有决定。 |
| M02.8 感知缺口处理 | 重要判断所需信息缺失时，先进行获准查证，无法取得再说明限制；不宣称感知用户全部世界。 |

**验收场景**。供应商报价已过有效期，助理主动核实而不继续按旧价格安排；用户在另一个时区，也能看懂下一次联系安排。

### M03 主动行动与资源权衡

**用户结果**。助理能够自主形成行动理由，在用户连续目标下投入资源、获得进展，并随现实变化调整。来源：本轮确认；用量与暂停能力延续既有目标。

![时间与资源取舍概念设计稿：同一交付目标，在还有两周时调查探索，在只剩两小时时收敛补缺，合理使用时间、算力和用户注意力。](../插图/04-时间与取舍.png)

*图解 · 同一目标在不同时间和资源条件下，需要不同的投入方式。是否加大探索或开始收敛，取决于对用户整体价值的判断。*

| 功能 | 需求与可观察结果 |
|---|---|
| M03.1 自主发现值得做的事情 | 从已知目标、现实变化、重复问题或新机会中形成工作意图，不以用户刚发指令或已有未完成任务为前提。 |
| M03.2 行动理由可解释 | 用户可以追问“为何做这件事”；回答指向相关目标与可观察依据，说明推断部分。 |
| M03.3 实质性主动工作 | 在授权范围内完成调查、整理、试做、改进、委派和协同，不把每次发现都退回成需要用户再次启动的建议。 |
| M03.4 投入与收益权衡 | 综合质量、时效、金钱、用户注意力及其他机会，决定投入程度；不用单一省钱或产出数量替代用户取舍。 |
| M03.5 动态改变工作方式 | 资源充裕时适度探索或并行；截止临近时收敛、保留可交付结果，并说明显著的质量或范围变化。 |
| M03.6 主动等待与停止 | 等待有价值的信息、收益已不足或目标已改变时，能够降低投入、暂停或结束，避免无意义循环。 |
| M03.7 有界自主性 | 自主行动遵循与直接委托相同的授权、预算和风险规则；缺少能力时不能自己扩大管理权限。 |
| M03.8 用户调整自主程度 | 用户能针对一件事或整体暂停新的主动行动，改变投入约束；产品交代正在进行的动作及其实际结局。 |
| M03.9 反馈进入后续判断 | 行动有效、无效或被用户纠正后，助理能调整后续策略，避免反复制造同一种低价值工作。 |

**验收场景**。没有新指令时，助理发现重复返工的原因并准备改进材料；交付临近后停止扩展方案，把资源转向已有稿件的验收与交付。用户可查看这次主动工作的理由、结果和投入。

### M04 协同资源

**用户结果**。用户与助理能用共同的快捷方式和视觉心智，将外部往来、材料、其他助理和能力接入具体事情，并管理它们的使命。来源：延续＋本轮确认。

| 功能 | 需求与可观察结果 |
|---|---|
| M04.1 从意图建立资源 | 自然语言与显式添加入口都可建立资源。已有语境足够时由助理补全用途和对象，避免手填技术参数。 |
| M04.2 发现当前可用能力 | 用户与助理能了解平台及已连接服务当前提供什么，哪些已授权、哪些还需连接或暂不支持。 |
| M04.3 引用与创建可区分 | 引用已存在的资源不重复新建；用户明确要求新建时，不擅自复用不合适的旧对象。 |
| M04.4 统一标识与真实预览 | 每种资源有可识别的名称、类型、用途、状态和适合其内容的预览；可以从对话与事情中直达。 |
| M04.5 具体范围可读 | 邮件往来明确参与对象和主题，资料范围明确文件或目录，其他助理明确委托内容；同名对象不混淆。 |
| M04.6 按能力提供动作 | 只展示实际可用的阅读、修改、发送、委派、关注等动作；只读内容不暗示可以编辑。 |
| M04.7 持续关注相关变化 | 对支持持续关注的资源，能够围绕当前目的接住新消息、版本或结果，并继续原事情。 |
| M04.8 关注范围与频度有目的 | 关注与目标、时效和资源代价相联系；不能默认遍历整个邮箱、目录或所有会话。 |
| M04.9 暂停与结束使命 | 用户与助理可以在适当范围内暂停、结束资源的后续协作；已发生动作和成果仍可追溯。 |
| M04.10 连接与资源各自管理 | 结束一段供应商往来不切断整个邮箱；撤销邮箱授权则如实影响依赖它的资源。 |
| M04.11 多资源关系可理解 | 设计结果可以成为印刷沟通的输入；用户能看懂依赖，信息流转遵守各自的可见与分享范围。 |
| M04.12 授权一次，范围内顺畅使用 | 已授权的读取与可恢复操作不因新建会话资源而重复询问；超出原范围时提供清楚的授权入口。 |

**验收场景**。一件活动同时使用供应商邮件资源和设计助理资源。两者有共同的引用与结束入口，却保留不同的内容与操作；活动完成后不再继续监听相关变化，历史仍可阅读。

### M05 多节点分布式协作

**用户结果**。用户从任意客户端与自己的助理交流，助理能够利用其他已接入设备和云端节点的算力、生产资料与特定能力完成工作。来源：既有多机目标＋本轮明确确认。这是核心产品能力。

手机、电脑与云服务器上的助理共同服务于用户的工作连续性。用户可以在手机上表达目标，而某段工作实际发生在远程机器上；不需要手工转发对话、反复交代背景或自行维护节点之间的连接。

![多节点协作概念设计稿：用户在手机上交流，甲节点算力充足，乙节点拥有所需文档，丙节点当前空闲；工作按实际需要选择地点，进展与成果返回手机。](../插图/03-多节点协作.png)

*图解 · 甲体现按算力选择，乙体现按资料所在位置选择，丙体现其他可用条件。两条选择路径表达可能的取舍，不要求每项任务同时使用所有节点；跨节点传递内容仍受授权与资料限制约束。*

| 功能 | 需求与可观察结果 |
|---|---|
| M05.1 登录接入自己的设备 | 通过产品提供的登录和引导接入设备或远程节点，无需用户部署注册中心、指定主节点或手动配置节点间连接。 |
| M05.2 设备与节点概览 | 能查看自己的手机、电脑、云服务器及平台工作环境的在线情况、可提供能力和当前可用状态。 |
| M05.3 感知算力与资料分布 | 助理了解哪些节点拥有合适的算力、软件或生产资料；节点可见不等于其中所有文件都被授权读取。 |
| M05.4 按任务需要分派 | 可以因算力更适合、材料就在当地、所需工具只在那里或成本与时效更合适，把工作交给相应节点。 |
| M05.5 让工作靠近受限材料 | 材料不能离开原节点时，能够在允许的节点上处理并带回获准返回的结果；先说明结果是否仍可能包含敏感内容。 |
| M05.6 跨节点协同完成一件事 | 可以在一个节点整理材料、在另一个节点执行允许的计算，再将成果汇回同一件事；中间交接不要求用户手动搬运。 |
| M05.7 落点与理由可追问 | 用户能知道工作实际在哪里运行、为何选它、是否在等待节点；选择未确定时不提前显示为已执行。 |
| M05.8 用户约束与指定 | 用户可以要求“只在这台机器处理”“不要搬出这些文件”“暂时不用这台服务器”，助理据此重新判断。 |
| M05.9 交互入口独立于执行地点 | 手机锁屏或关闭客户端不应被解释成远程工作停止；仍在运行、受阻或完成的实际情况返回原事情。 |
| M05.10 节点离线与替代 | 节点离线时说明受影响部分；只有材料、能力与授权允许时才换到其他节点，不能把本地资料可用性凭空带走。 |
| M05.11 收回与退出 | 用户能停止节点承接新工作、撤回相应权限；正在执行的任务是否可以停止及已发生结果分别交代。 |
| M05.12 防止重复与分裂体验 | 网络恢复或节点切换后，同一委托仍能核对进展与结果；不能把不明执行自动重做为两个独立的外部动作。 |

**必须覆盖的旅程**。用户在手机上聊天，名下有三台云服务器：甲有较强算力，乙有独有的项目文档，丙正空闲。助理能够因“算力适合”选择甲，也能够因“所需材料只能在乙读取”选择乙；资料允许转移时可协同使用甲与乙，禁止转移时不得为了速度绕过限制。用户始终从手机查看同一件事与最终成果。

**与同步的区别**。在另一台设备看到同一段聊天，仅满足跨端连续性。M05 还要求实际发现远程工作条件、分派工作、在当地使用获准资源，并返回真实进展和成果。

## 五 工作与交付的功能拆解

### M06 事情与长期推进

**用户结果**。用户可以把跨度长、步骤不确定、需要多方配合的一件事交给助理共同推进，随时了解现实进展。来源：延续＋既有目标＋本轮确认。

![办理一件跨周事务，经历准备、提交、等待与领取；不确定窗口中依据实际进展调整跟进，用户需要出面时获得提醒，完成后停止继续检查。](../插图/07-跨周推进.png)

*图解 · 确定步骤与不确定窗口共同属于一件事；助理根据现实进展调整节奏，并在使命完成后收尾。*

| 功能 | 需求与可观察结果 |
|---|---|
| M06.1 事情的整体语境 | 记录目标、材料、人物、承诺、约束、参与资源与结果；用户自己完成的动作和外部进展也能进入记录。 |
| M06.2 阶段与依赖 | 把长事务组织成可理解的阶段，区分确定步骤、待观察窗口和必须等前一步完成的工作。 |
| M06.3 现实进展可追问 | 回答已经完成什么、正在做什么、等谁、缺什么和下一步；每项重要状态有实际依据。 |
| M06.4 在不确定窗口中判断 | 只知道“大概那几周”的事情，可以根据实际结果调整检查与行动节奏，不要求用户替助理规定每一次唤醒。 |
| M06.5 计划随现实调整 | 延期、回复、资源不足或目标改变后调整后续工作；显著改变范围、承诺和成本时向用户说明。 |
| M06.6 连续性与恢复 | 跨天、跨周、跨客户端仍保留事情的背景与进展；中断后先核对状态，不重复启动已发生的动作。 |
| M06.7 需要本人参与的步骤 | 提前提醒用户到场、签字或作出关键决定，保留地点、时间、材料和真实限制。 |
| M06.8 完成与停止 | 完成标准可表达；用户可以暂停或放弃事情，相关后续关注随之妥善处理，历史与成果仍可回看。 |

**验收场景**。办理证件经历准备、提交、等待、查询与领取。助理不会因一次等待跨越会话就遗忘，也不会在窗口结束后无限检查而不给结论。

### M07 对话与多模态交付

**用户结果**。用户可以自然表达目标、提供材料和干预工作，助理准确理解这次交付的内容与行为语境。来源：延续＋既有目标。

![同一张桌面场景中，用户可把材料直接交给助理，也可先暂放并补充用途；新复制的内容只是半透明候选，点击或拖动接受后才交付完整原件。](../插图/10-桌面交付.png)

*图解 · 直接交付、暂放补充说明与剪贴板候选有不同的动作含义；预览不会自行发送，文件类型也不替用户决定用途。*

| 功能 | 需求与可观察结果 |
|---|---|
| M07.1 日常语言委托 | 可以从一个问题、一段目标或一份自我说明的任务材料开始，不强制先创建结构化任务。 |
| M07.2 多种输入与诚实支持 | 文字、链接、图片和文件进入统一交付旅程；语音、音视频等按实际支持范围提供，不能用文件已上传冒充已理解。 |
| M07.3 保留交付动作 | 拖入、粘贴、点击预览、选择引用和补充说明随原文保留；已知来源与未知来源分别表达。 |
| M07.4 内容与用途分开 | 文本可能是任务，也可能是待翻译材料；文件类型不自动决定业务意图。用户附加的用途与原件同时保留。 |
| M07.5 精确引用 | 用户可以引用联系人、材料、事情和协同资源；历史保留当时选中的具体对象，名称相同也不误换。 |
| M07.6 适度澄清 | 缺少必要事实时，问题说明缺什么、为何需要及回答后做什么；允许自然语言补充，复用已明确的回答。 |
| M07.7 忙碌时继续交流 | 用户可以补充、改方向或提出新工作；产品说明新输入如何处理，不吞消息，也不覆盖未发送草稿。 |
| M07.8 历史与阅读连续性 | 查找会话、加载历史、查看资源与返回原文时保留草稿和阅读位置；历史读取失败不能导致当前输入丢失。 |
| M07.9 过程与结果同步 | 用户看到可理解的执行状态、必要的协作进展和最终结果；结束后主界面与桌面助理同步结束处理状态。 |
| M07.10 干预与真实结局 | 改正、暂停或停止请求后，说明实际接受情况、已发生动作和剩余工作；不能仅凭按钮点击显示全部取消。 |

**验收场景**。用户先引用供应商联系人，再输入“问他打样时间”；助理沿用该联系人，缺少联系方式才问，不重新猜测同名人物。

### M08 资料与个人内容

**用户结果**。资料属于用户，可以独立收纳、编辑与使用，同时为助理的理解和行动提供可靠依据。来源：延续＋既有目标。

![同一份原始材料可以产生摘要、译文和后续版本，也可以被事情、联系人与日程引用；原件、加工结果及当前用途分别可追溯。](../插图/11-原件版本与语境.png)

*图解 · 资料可以先保存、之后再使用；摘要不覆盖原件，多个阅读视角仍指向同一份事实。*

| 功能 | 需求与可观察结果 |
|---|---|
| M08.1 直接收纳 | 可以保存无标题原文、图片或文件，无须先创建会话、分类或配置模型。 |
| M08.2 原件与整理结果 | 原文原件保留，提取文本、摘要、翻译和改稿可回到来源；助理加工不覆盖原始证据。 |
| M08.3 读取与保存各自明确 | 文件保存成功、内容可读取、模型已经读取是不同结果；不支持提取时仍清楚说明原件状态。 |
| M08.4 编辑与版本 | 用户能修改、查看历史和辨认谁改了什么；冲突时保留自己的草稿，不静默覆盖他人的新版本。 |
| M08.5 批量材料交付 | 多文件逐项反馈，部分失败不吞掉成功项，也不将不完整材料伪装为完整任务输入。 |
| M08.6 外部来源与快照 | 远程资料保留来源、取得时间和版本；旧快照与当前内容有区别，断开来源不冒充资料不存在。 |
| M08.7 围绕材料继续讨论 | 从资料打开助理时明确附带的范围；切换材料不把旧草稿或附件错误投向新对象。 |
| M08.8 与事情关联 | 资料可以关联事情、联系人、日程与成果，在多个视角中引用同一份事实。 |
| M08.9 可管理的数据生命周期 | 用户能导出、明确删除和恢复支持的内容；退出登录、重装客户端或停止助理不顺带删除资料。 |

**验收场景**。用户导入一批文件，其中一份不能读取。产品保留其余原件、说明缺口，并允许补齐；助理的分析明确指出实际读到哪些内容。

### M09 人、往来与外部协作

**用户结果**。助理理解人与事情的关系，能在获准范围内参与真实往来，持续承接反馈。来源：延续＋本轮确认；完整跨方旅程为目标。

![用户与自己的助理共同处在协作中心，与客户、同事及伙伴分别交换获准材料和反馈；对方可以继续使用原有沟通方式，各方职责和资料范围保持清楚。](../插图/08-多方协同.png)

*图解 · 服务主体始终是你；协作范围可以跨团队与组织，参与某件事并不意味着获得所有人的资料或决策权。*

| 功能 | 需求与可观察结果 |
|---|---|
| M09.1 联系人与关系语境 | 保留可用联系方式、用户注解及与事情的关系；用户判断和外部来源信息分别呈现。 |
| M09.2 准确选择对象 | 复用明确引用的人；多人同名、多个可行渠道或身份不清时进行必要澄清，不凭名字猜地址。 |
| M09.3 围绕目的建立往来 | 以“询价”“修改反馈”“交付确认”等目的组织协作资源，不要求用户先按通信技术选择工具。 |
| M09.4 已有渠道可参与 | 外部伙伴可通过受支持的既有渠道合作；不以注册本产品作为所有协作的前提。 |
| M09.5 发送与交付状态 | 可以准备和在已有授权下发送内容；草稿、发送成功、投递结果和对方回应分别表达，不夸大确认程度。 |
| M09.6 反馈回到正确事情 | 新回复保留参与者、来源和关联材料，推动原事情；不要求用户复制到新的聊天里重新解释。 |
| M09.7 多方信息取舍 | 信息传递符合实际目的与获准范围；用户能了解哪些材料给了谁，私人注解不自动随外发材料传播。 |
| M09.8 承诺与分歧 | 区分自己的计划、助理建议、对方提议与已确认承诺；存在分歧时保留来源并协助解决。 |
| M09.9 跟进与收尾 | 按目标、时机和对方处境决定是否跟进；用户结束协作后不继续催促，对方旧记录仍可查阅。 |

**验收场景**。印刷商提出新尺寸要求，助理把必要信息带给设计资源；品牌方尚未确认的报价不能被写成双方已经接受的合同条件。

### M10 日历、日程与持续关注

**用户结果**。用户的约定、需要本人行动的提醒、助理将做的工作和持续的信息关注，都有清楚的时间语义。来源：延续＋既有目标。

![用户的现实约定、助理的未来工作、来源简报与基于目标的主动调查有不同起因；新信息可以引出调查，但保存约定本身不等于已建立提醒或执行。](../插图/12-时间安排与持续关注.png)

*图解 · 时间相关能力服务于现实目标。固定安排、变化后的继续工作与自主发现相互衔接，同时保留各自的真实状态。*

| 功能 | 需求与可观察结果 |
|---|---|
| M10.1 日历查阅与安排 | 在已授权范围内查询和管理日历，支持日常语言；只缺开始时间等必要事实时才补问。 |
| M10.2 区分约定、提醒与执行 | “下午会面”“提前提醒我”“届时帮我整理材料”分别表达；保存一个约定不能冒充已经建立提醒或助理工作。 |
| M10.3 时间与日历语境 | 跨时区、全天事项、工作日、节假日与相对时间可正确理解和预览。 |
| M10.4 可见的未来安排 | 用户能查看、改期、暂停和撤下助理安排的未来动作，知道关联哪件事及下一次预计发生时间。 |
| M10.5 来源与简报 | 用户能指定关注来源、目的、汇总时间与接收方式，收到带来源和时点的简报。 |
| M10.6 周期、变化与自主发现 | 固定简报、资源变化后的继续工作、基于目标自主发现问题，都有各自的真实起因，不能全部简化成定时扫待办。 |
| M10.7 空、失败和错过 | 无新增、来源不可达、未执行和投递失败分别说明；恢复后不伪造过去已完成的工作。 |
| M10.8 调整与结束 | 目标变化后更新相关安排，避免旧计划继续生效；重复调整不制造多份同一提醒或重复外部行动。 |

**验收场景**。用户要求“每天给我一份相关信息简报”，助理如实标明一个来源今天无法访问；同时，对另外发现的真实机会可以开展获准调查，不必等下一份简报。

### M11 调查、委派与成果

**用户结果**。助理可以组织多种能力共同完成工作，交付有依据、可实际使用的成果。来源：延续＋既有目标＋本轮确认。

![围绕同一个问题，助理把有限的研究任务和材料交给不同参与者，比较证据与分歧，汇回真实文件、结论及未解决的问题。](../插图/09-协作研究与交付.png)

*图解 · 委派要带着清楚的目的和材料边界；最终价值体现在可使用的成果与可追问的依据。*

| 功能 | 需求与可观察结果 |
|---|---|
| M11.1 有目的的调查 | 围绕问题寻找、比较和核实资料；打不开原文时说明实际取得的范围，不以标题或搜索摘要冒充全文。 |
| M11.2 按需要委派 | 能将适合的工作交给其他助理或专业能力，考虑质量、时效、成本和已有资源；无需用户每次手动编排。 |
| M11.3 委托边界清楚 | 被委派者得到明确目的、材料与可用范围；委派不自动放大权限或传递全部历史。 |
| M11.4 协作过程可见 | 用户可查看参与者、正在做什么、已完成什么和失败原因；不能把主助理的自述当作实际委派证据。 |
| M11.5 等待中的工作 | 耗时任务接受后可以继续其他工作，真实结果返回原事情；等待不意味着已经完成，也不要求用户持续保持窗口打开。 |
| M11.6 汇总与分歧处理 | 汇总多个结果并说明重要分歧、证据与不足，不能拼接互相冲突的结论后当作一致答案。 |
| M11.7 多种成果交付 | 文字、图片、文件和受支持的音视频等成果可预览、取得和继续修改；仅说“已生成”不算交付。 |
| M11.8 真实完成与部分结果 | 全部完成、部分完成、失败和结果不明分别报告；保留已获得的可用成果。 |

**验收场景**。一个助理调查资料，另一个制作方案。主助理带回实际文件与来源，明确未核实内容；子任务完成后各入口的处理状态同步收敛。

### M12 交互式成果

**用户结果**。用户可以把结果变成之后仍能打开、操作和协作使用的页面或小工具。来源：延续需求＋既有目标；完整发布与分享体验仍需完善。

![用户表达用途后，助理交付可在手机打开和操作的行程页面；之后可继续修改、保留实际记录，并按清楚范围分享，成果重新参与后续协作。](../插图/13-交互式成果.png)

*图解 · 真实成果应能被打开、使用和继续调整；可用页面、源代码和临时预览不能混为一谈。*

| 功能 | 需求与可观察结果 |
|---|---|
| M12.1 用自然语言表达用途 | 可以说“把行程做成手机上能打卡的页面”“做一个能和朋友下棋的小工具”，助理据此组织可用成果。 |
| M12.2 可打开与可操作 | 交付实际可访问的成果入口，按明确范围支持交互；源代码文字不等同于已建立的可用页面。 |
| M12.3 持续修改同一成果 | 用户能继续提出变化并更新相应成果，保留重要版本；另建新成果与修改旧成果有区别。 |
| M12.4 成为后续协同资源 | 页面或工具可以被引用、回到原事情，也可以承接之后的协作；仅实际支持的变化才可持续关注。 |
| M12.5 受控分享与参与 | 分享给谁、对方能看什么或操作什么应明确；建议补充访问范围调整、停止分享与到期说明。 |
| M12.6 原材料与外部依赖 | 页面使用的资料、实时信息和外部操作能力分别交代；不能因页面存在就取得其他账户或设备的权限。 |
| M12.7 长期可用性与导出 | 说明成果可保留多久、有哪些使用限制及支持的导出方式；不把临时预览承诺为永久服务。 |

**验收场景**。用户在手机打开助理制作的行程页面，能查看资料并记录实际完成情况；后续修改不会把已经记录的结果无声覆盖。

## 六 用户掌握与参与的功能拆解

### M13 视角、关注与通知批阅

**用户结果**。用户能够理解当前值得关注的事情，迅速进入需要自己参与的部分，同时保有安静工作与生活的空间。来源：延续＋既有目标。

![助理直接推进已经授权且可恢复的整理工作，用户稍后集中查看和调整；确有必要信息或尚未确认的高风险后果时，带着对象、材料与后果向用户协商。](../插图/14-自主行动与用户掌握.png)

*图解 · 日常动作不反复询问，重要决定带着完整语境回到用户；关闭、超时或沉默都不构成新的同意。*

| 功能 | 需求与可观察结果 |
|---|---|
| M13.1 多种内容视角 | 从事情、资料、日历、联系人等角度阅读同一组事实，避免相互矛盾的独立副本。 |
| M13.2 自己的视角 | 用户能保存固定范围或有明确条件的阅读视角，并知道当前覆盖什么、未覆盖什么。 |
| M13.3 此刻值得关注 | 结合当前时间、旧承诺、变化和现实限制呈现少量有依据的关注内容；不要求用户给所有事情打重要性分数。 |
| M13.4 旧承诺仍可被理解 | 很久以前的重要约定不能仅因记录不新而被遗忘；频繁出现的消息也不自动压过真实重要的事情。 |
| M13.5 通知可回找 | 重要消息、结果和待决定事项能在通知中心找到，错过弹窗、换设备或某条投递失败不导致事项消失。 |
| M13.6 打扰方式与时机 | 用户能设置安静时段和通知偏好；相同问题合并跟进，助理考虑用户当前可参与程度。 |
| M13.7 需要决定时信息完整 | 展示具体对象、内容、后果和所需判断；用户可以直接作答，也可查看来源或修改条件。 |
| M13.8 可恢复工作先推进 | 对确实适合且已授权的动作，可先产生可恢复结果；需要事后审阅的项目集中可见，不把所有修改都变成待审批。 |
| M13.9 批阅与真实后果 | 支持的暂行结果能单项或成组接受、调整或撤回，说明受影响的后续成果；不支持干净撤回的外部后果不能包装成可恢复。 |
| M13.10 多入口一个决定 | 从会话或通知作答后，其他入口反映同一结果；超时、关闭卡片和未读均不自动代表同意。 |

**验收场景**。助理准备了多份可修改稿件，用户稍后集中审阅；其中一项需要外部不可恢复动作时，单独呈现具体决定，不阻断其余独立工作。

### M14 跨平台客户端与桌面助理

**用户结果**。用户通过适合当下的入口与同一个助理相处，轻量入口与完整工作体验保持连续。来源：延续＋本轮确认。

| 功能 | 需求与可观察结果 |
|---|---|
| M14.1 同账号跨端使用 | 下载受支持的桌面或移动客户端并登录即可接入自己的助理；会话、事情、资源与成果可连续访问。 |
| M14.2 按设备适配 | 手机适合快速交流、查进展和决定，桌面适合材料交付与深度工作；入口简化不能隐藏重要权限或真实失败。 |
| M14.3 桌面助理形态 | 用户可选择低打扰的桌宠入口，与完整客户端共享任务与状态，不形成另一套助理。 |
| M14.4 放置与锁定 | 可拖动、锁定并按屏幕布局记住位置；拔掉屏幕后回到可见位置，恢复原布局时尊重用户偏好。 |
| M14.5 直接交付与补充用途 | 靠近助理直接交付，暂放区域先补充说明；拖动时明确反馈，内容格式不决定用户意图。 |
| M14.6 剪贴板候选预览 | 用户启用后，新复制的支持内容形成约 30 秒的半透明候选预览；未接受前不作为委托上传或发送。 |
| M14.7 有信息的缩略内容 | 图片和截图显示真实缩略图，文件显示类型和名称，文本显示适当截断的原文；实际交付使用完整内容。 |
| M14.8 状态与角色一致 | 处理、等待用户和完成状态与真实任务同步；动画与形象不遮挡材料、操作或用户工作。 |
| M14.9 替代操作路径 | 拖放、点击和键盘方式有等价入口，窄屏、大字体和辅助技术下也能完成主要旅程。 |

**验收场景**。桌面交付一份 PDF，手机继续补充说明并查看结果；桌宠结束处理，主客户端显示同一成果，不生成两个互不相关的任务。

## 七 商业服务基础的功能拆解

### M15 账号与即用服务

**用户结果**。用户只需注册登录即可获得一套可用服务，接入客户端、设备和私人账户的过程都由产品引导。来源：本轮确认；找回、退出等为建议补充。

| 功能 | 需求与可观察结果 |
|---|---|
| M15.1 注册与登录 | 建立并进入自己的账号，不先选择组织版本或部署方式；首次中断后可以继续。 |
| M15.2 默认可用的基础服务 | 登录后能使用平台提供的基础资源与助理能力，不要求用户逐个注册内部组件。 |
| M15.3 新设备接入 | 通过明确的账号验证接入设备，并可在自己的设备列表中识别；登录不默认授予所有本机内容。 |
| M15.4 私人服务连接 | 通过产品引导连接邮箱、日历等账户，看到目的、范围和当前状态；基础连接不要求自行创建开发者应用。 |
| M15.5 能力与服务管理 | 在客户端查看可用能力、补充连接、调整范围、检查问题；相关管理入口与当前事情可以互相到达。 |
| M15.6 身份恢复 | 建议补充账号找回、失去常用设备后的恢复与安全核验，避免所有内容依赖某一台电脑。 |
| M15.7 登录与业务连续性 | 更换客户端或重新登录后仍能核对已有工作；退出某个客户端与停止所有远程工作有清楚区别。 |
| M15.8 退出使用 | 建议补充停止续费、导出资料、关闭账户等完整旅程，明确各自影响与仍需处理的工作。 |

**验收场景**。一位没有部署知识的用户在新电脑上注册，选择平台服务后完成第一次委托；换到手机登录仍能找到事情，不需要手工指定主节点地址。

### M16 模型、算力与用量

**用户结果**。用户可以使用自己的 API 或平台服务，清楚了解可用能力、投入、费用与限制，助理能够据此安排工作。来源：本轮确认＋既有预算目标；具体计价为待定事项。

![注册登录进入同一个助理后，用户可以使用平台服务，也可连接自己的兼容 API；模型用量、执行算力、预算和切换规则需要各自说明。](../插图/15-登录与双来源服务.png)

*图解 · 平台服务与自带 API 都应有清楚的能力和费用说明；自带模型 API 不表示整件事零成本，也不默认允许静默切换收费来源。*

| 功能 | 需求与可观察结果 |
|---|---|
| M16.1 双来源服务 | 支持平台提供的 AI 与算力，也支持用户提供兼容服务的 API；不能只覆盖模型 token 而遗漏其他执行算力的来源与约束。 |
| M16.2 自带 API 验证 | 可添加、检验、更换和撤回自己的服务连接，知道支持哪些模型或工作能力；密钥不回显到对话与分享材料。 |
| M16.3 平台服务即用 | 用户无须购买外部供应商服务即可开始，产品明确可用额度、限制和不足时的选择。 |
| M16.4 能力与来源选择 | 能知道某类任务使用哪种服务；自动选择应遵守用户的质量、成本、隐私和执行地点约束。 |
| M16.5 费用可理解 | 区分模型用量、执行算力和平台服务等实际收费项；用户能按时段与事情查看可取得的用量和费用。 |
| M16.6 预算与自主工作 | 可设定支持的预算范围，助理据此调整投入；接近上限时尽早说明，到顶后的停用或降级规则明确。 |
| M16.7 主动使用有边界 | 在预算范围内不为每次微小调用反复确认；需要扩大预算或改变已约定服务来源时由用户决定。 |
| M16.8 服务不可用与切换 | 自带 API 失效不能静默切到收费的平台服务；平台额度不足也不能悄悄消耗其他凭据。已有允许的切换规则可直接适用。 |
| M16.9 不完整计量诚实 | 外部服务未提供准确费用时显示估计或未知；自带模型 API 不自动表示平台的其他服务免费。 |
| M16.10 待机与持续工作成本 | 用户能理解持续关注、后台调查和远程执行是否产生费用，能够停用不再需要的持续工作。 |

**验收场景**。用户选择自带模型 API、平台执行算力。助理分清两类消耗，预算变化后调整后续工作，不把“自带 API”显示成整件事零成本。

### M17 授权、隐私与行动控制

**用户结果**。用户知道助理能使用什么、已经做了什么，并能有效收回权限和干预工作。来源：延续＋既有目标＋本轮确认。

| 功能 | 需求与可观察结果 |
|---|---|
| M17.1 权限范围可见 | 可查看授予的账户、材料、设备、动作和适用范围，区分申请中、已授权、过期与已撤回。 |
| M17.2 已授权动作顺畅执行 | 在当前目标和授权范围内，读取与可控、可恢复动作直接进行；不重复索要“允许本次会话连接”的同义确认。 |
| M17.3 必要的澄清与确认 | 必要信息缺失时澄清；尚未明确确认的不可恢复、高风险行为展示具体后果并请求决定。相同行为已有明确确认时复用。 |
| M17.4 自主行动遵守同一边界 | 主动发现、委派、跨节点执行和持续关注不豁免权限，外部材料里的指令不扩大用户授权。 |
| M17.5 管理权由用户掌握 | 助理可引导用户配置，但不能自行获得账户管理秘密、扩大资源权限或代表用户完成未授权的管理动作。 |
| M17.6 可追溯的动作 | 用户能查看真实读取、修改、发送、委派与结果，追问具体依据；技术细节可以展开，秘密值始终不泄露。 |
| M17.7 撤权与真实生效 | 撤回后阻止后续未获准的使用，说明在途工作的实际情况；已外发的信息不能声称被追回。 |
| M17.8 停止与取消的区别 | 用户能停止后续关注和分派；外部动作是否支持取消、是否已经停止，需要真实反馈。 |
| M17.9 数据与分享范围 | 不同用户的资料和工作严格分开；外部协作只分享明确范围，其他参与者无权扩大用户的助理权限。 |
| M17.10 临时材料受控 | 剪贴板候选、未发送草稿与暂放材料不因被预览就交给模型；切换账号不误发原账号的草稿。 |

**验收场景**。用户授权读取日历后询问今日安排，助理直接查询；用户撤回相应权限后，新读取被阻止，旧引用说明当前不可读取。

### M18 可靠性、数据与支持

**用户结果**。用户能够长期托付工作，知道服务出了什么问题、哪些结果可信，以及怎样恢复或求助。来源：延续＋既有目标；面向正式服务的细化条目含建议补充。

![工作中出现断线或节点离线时，保留原委托、草稿与已完成部分；恢复后先核对实际发生的动作和结果，再继续未完成部分，避免重复外部行为。](../插图/16-中断恢复与有序收尾.png)

*图解 · 失去连接不等于任务失败，也不等于工作从未发生。恢复应围绕原来的事情核对事实，并把真实结局带回所有入口。*

| 功能 | 需求与可观察结果 |
|---|---|
| M18.1 真实状态 | 区分准备中、工作中、等待外部、等待用户、部分完成、失败和结果不明；不能永久停在没有解释的“连接中”。 |
| M18.2 断线与重启恢复 | 恢复后能核对原请求、真实终态和成果；保留草稿、附件、已确认的决定与阅读位置。 |
| M18.3 不明结果不盲重做 | 邮件、文件修改等操作结果不明时优先核对；重试不能轻易造成重复发送、重复收费或重复外部承诺。 |
| M18.4 局部故障局部说明 | 某个来源、模型或节点不可用时，其他可用资料与工作入口仍可使用，受影响范围明确。 |
| M18.5 数据导出与恢复 | 提供受支持的数据导出、恢复与明确删除入口，说明覆盖范围；普通退出、升级与重新登录保留用户内容。 |
| M18.6 用户理解的服务范围 | 明确支持的平台、输入格式、大小、交互成果保留时间及离线能力；未支持部分有可理解的反馈。 |
| M18.7 版本与更新 | 建议补充清楚的版本更新、兼容性说明和失败恢复路径，更新不打断未完成的用户输入而无从恢复。 |
| M18.8 支持与反馈 | 建议补充可到达的帮助、问题反馈与处理进度；提交诊断前说明携带的信息并排除秘密。 |
| M18.9 服务承诺明确 | 建议在正式发布前确定可用性、响应、数据保留与恢复承诺，公开故障影响；本文不编造尚未确定的数值。 |
| M18.10 可访问与可理解 | 主要旅程支持清楚的语言、键盘和辅助操作；错误先说发生了什么、影响什么、用户能做什么。 |

**验收场景**。用户在发送后遇到断网，重连时找回原委托结果；另一台机器离线只影响需要该机资料的部分，不把所有功能显示成不可用。

## 八 跨模块的完整体验要求

### 8.1 一件事的状态在所有入口一致

对话、事情列表、资源预览、手机通知和桌面助理可以呈现不同层次的信息，但应指向同一份现实结果。结束的工作不应在另一个入口持续显示处理中；已作出的决定不能再次变成待答；等待外部回复不能假装助理正在持续计算。

### 8.2 共同行为可理解，实际能力不混同

协同资源共享识别、引用、查看和使命管理方式。具体动作取决于真实能力：文件夹可以有版本变化，邮件可以有往来，其他助理可以交付结果；一个静态图片不需要凭空出现“等待回复”。选择某个资源本身不增加权限，也不证明助理已经读取过它。

### 8.3 结果的价值高于活动数量

产品应帮助用户辨认事情是否取得实际进展、是否减少负担、是否作出更合适的取舍。更多消息、工具调用、子任务或通知不自动表示更多价值。助理应能结束没有收益的活动，也能在必要时投入较多资源完成真正重要的工作。

### 8.4 需要用户参与时，参与成本应低

用户不需要从完整历史里重新搜集问题背景。助理应携带必要对象、材料、已有选择和真实后果来协商；允许用户用自然语言修正。相同、未改变的决定不被重复询问，一次决定的结果在所有入口一致。

### 8.5 用户离开屏幕后，责任仍然连续

云端能够继续的工作、依赖某台设备在线的工作、尚未发出的工作应分别说明。用户可以关掉手机而让远程工作继续，也能明确暂停后续行动。不能承诺断电设备还在工作，更不能因为用户没有打开应用就把已经发生的事情忘掉。

## 十 尚需在商业发布前确定的产品承诺

下面是明确保留的产品决策空间，不影响前述整体定义，也不替代技术方案讨论。

1. **首发完整旅程与渠道范围**。哪些生活或工作场景先达到可反复依赖的程度，首发接入哪些通信、资料和生产能力；完整资源心智保留，但支持列表必须真实。
2. **客户端与节点支持范围**。首发桌面、手机和远程节点覆盖的平台及差异；具体操作系统和最低版本另行确定。
3. **自主工作默认边界**。默认可进行的探索、投入范围与通知方式，如何让用户在首次使用时以较低成本理解并调整。
4. **服务与用量计价**。平台用量、自带 API、执行算力和其他服务分别如何收费，余额不足和预算耗尽时怎样处理；不预定套餐价格。
5. **数据与交互成果的长期承诺**。资料、历史、记忆、已发布成果及分享内容的保留、导出和删除范围；账号退出后的影响需向用户说明。
6. **可靠性与支持承诺**。正式服务的可用性、恢复能力、支持响应及用户反馈渠道；需要以可兑现的服务结果确定。

当前需求不要求引入企业组织、团队席位、审批层级或专属部署版本。多方协同所需的身份、授权和分享边界已经包含在相应用户能力中，后续扩展应继续从实际用户场景出发。
