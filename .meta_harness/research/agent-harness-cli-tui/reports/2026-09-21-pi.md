## 1. 技术栈

**结论：TypeScript + Node.js（≥22.19），TUI 是完全自建的 retained-mode 差分渲染器，零 TUI 框架依赖——不是 Ink、不是 React、不是 blessed、不是 OpenTUI。整个 TUI 包只有两个运行时依赖，外加三个平台各一个手写的 ~100–270 行 C/Objective-C N-API 模块。分发同时走 npm 包与 bun `--compile` 单文件二进制。**

### 1.1 语言与运行时

- `package.json:engines` = `node >= 22.19.0`（根与各包一致）。
- 源码全部 TypeScript，**限定使用 Node「strip-only」可擦除语法**：`AGENTS.md` 规定 `packages/*/src`、`packages/*/test` 内「no parameter properties, `enum`, `namespace`/`module`, `import =`, `export =`, or other constructs needing JS emit」。这条约束的直接后果是源码可以被 Node 直接以 `--experimental-strip-types` 运行，benchmark 脚本就是这么跑的（`packages/tui/test/alt-screen-large-transcript-bench.ts:18`）。
- 类型检查用 `@typescript/native-preview`（`tsgo`）+ `typescript 5.9.3`；lint/format 用 **Biome 2.3.5**（`biome.json`，根 `package.json:devDependencies`）。没有 ESLint、没有 Prettier。
- 打包用 **esbuild 0.28.2**（`scripts/build-coding-agent-bundle.mjs`），二进制用 **bun `--compile`**（`packages/coding-agent/package.json` 的 `build:binary`：`bun build --compile --no-compile-autoload-bunfig ./src/bun/cli.ts ...`）。

## 2. 交互范式与渲染

**结论：Pi 同时发货两套渲染器——`TuiMainScreen`（inline，写进终端 scrollback，默认）与 `TuiAltScreen`（alt-screen 全屏视口，应用自有滚动，文档标注 experimental）。二者共享同一 `Component` 接口与同一批组件实例，但语义故意不对齐：main-screen 明确拒绝提供 sticky 区、嵌套滚动与鼠标命中测试。流式输出靠 16 ms 节流帧 + 行级差分；键盘输入绕过节流立即重绘。终端能力全部通过环境变量白名单 + 转义序列探询获得，没有 terminfo。**

### 2.1 两套渲染器并存，默认是 inline

- 类型与入口：`packages/tui/src/tui-main-screen.ts`（655 行）与 `packages/tui/src/tui-alt-screen.ts`（1,742 行），共享 `TUI` 接口（`src/tui.ts`）。
- 选择点：`packages/coding-agent/src/modes/interactive/tui-renderer.ts:18-23`，由 `tuiMode: "regular" | "fullscreen"` 决定。
- **默认是 `regular`**：`packages/coding-agent/src/core/settings-manager.ts:1265-1266`
  ```ts
  getTuiMode(): TuiMode {
      return this.settings.tuiMode === "fullscreen" ? "fullscreen" : "regular";
  }
  ```
- 文档把 fullscreen 标为实验性：`packages/coding-agent/docs/settings.md:92` —「Interactive TUI mode: `"regular"` or experimental `"fullscreen"`」。CLI 帮助文本同样写「regular (default) or fullscreen」（`packages/coding-agent/src/cli/args.ts:315`）。
- 可运行时切换：`interactive-mode.ts:854-877` 有换渲染器而不重启会话的交接路径（`/settings` 改 `tuiMode` 立即生效）。

### 2.2 main-screen（inline）渲染：三态差分

`packages/tui/README.md` 的「Rendering modes」一节把算法写死为三条，与作者博客里的描述逐条对应：

1. First Render：全量输出，不清 scrollback。
2. Width Changed 或「变更行在视口之上」：清屏 + 全量重绘。
3. Normal Update：光标移到第一处不同的行，清到屏末，重绘其后。

作者原文（2025-11-30，一手）：

> "The algorithm is simple: 1. First render: Just output all lines to the terminal 2. Width changed: Clear screen completely and re-render everything (soft wrapping changes) 3. Normal update: Find the first line that differs from what's on screen, move the cursor to that line, and re-render from there to the end"

> "There's one catch: if the first changed line is above the visible viewport (the user scrolled up), we have to do a full clear and re-render. The terminal doesn't let you write to the scrollback buffer above the viewport."

**这个「catch」不是理论风险，它后来变成了一个真实缺陷并直接催生了第二套渲染器**——见 §2.3 与 §5.1。

### 2.3 alt-screen 渲染：设计文档、落地版本与来源

- 设计文档在仓库根：`tui-plan.md`（1,000+ 行，含公共 API、布局算法、绘制、事件路由、测试计划）。它自述是 **implementation handoff**：「This document is an implementation handoff. It records the decisions made during design discussion and should be treated as the intended scope unless implementation findings require revisiting a decision.」（`tui-plan.md:7`）。
- **这份 plan 已经落地，不是待办规格**：`VStack`/`HStack`/`ScrollView`/`layout.ts`/`layout-node.ts` 都在 `packages/tui/src` 里，`packages/tui/README.md` 以现在时文档化了它们的行为。判断依据是源码存在 + README 描述 + CHANGELOG 有发布记录，三者一致。
- 落地版本：`packages/tui/CHANGELOG.md` **`## [0.84.0] - 2026-08-06`** 条目「Added interface-compatible main-screen and alternate-screen TUI renderers with application-owned scrolling ([#7304](https://github.com/earendil-works/pi/issues/7304)).」**CHANGELOG 自己把这次新增挂在 issue #7304 上**，而 #7304 正是「滚上去看历史时，流式输出重排视口上方的行导致整屏重绘 + `ESC[3J` 抹掉 scrollback」——即 §2.2 里作者自述的那个 catch。
- main-screen 与 alt-screen 的语义差异是**刻意不对齐**的，`tui-plan.md:26-40` 给出了理由（一手）：

> "The terminal owns scrolling in main-screen mode. The application cannot reliably provide: sticky rows / independently scrollable nested regions / full-height side-by-side panes / reliable mouse hit testing for content moved into terminal scrollback / arbitrary repainting of off-screen regions without replaying or clearing scrollback. Therefore, do not pretend the same constrained viewport semantics exist in `TuiMainScreen`."

- alt-screen 独有能力（`packages/tui/README.md`，与源码一致）：约束布局（`basis`/`grow`/`shrink`/`minSize`/`maxSize`/响应式 `visible`）、嵌套 `ScrollView` 与滚动链（`overscroll: "chain"`）、SGR 鼠标（滚轮/拖拽/点击/hover）、比例滚动条（hover 展开、拖拽、轨道点击）、拖选文本并经 OSC 52 复制（`copyOnSelect`，默认 true）、`Ctrl+Shift+F` 搜索面板、OSC 133 语义提示符跳转、边缘自动滚动。
- **`TuiMainScreen` 不捕获鼠标**（README 原文：「`TuiMainScreen` does not capture mouse input because the terminal owns its scrollback.」）。

### 2.4 流式输出与重绘调度

- **16 ms 帧预算节流**：`packages/tui/src/tui.ts:477` `private static readonly MIN_RENDER_INTERVAL_MS = 16;`；`scheduleRender()`（`tui.ts:986-999`）按 `max(0, 16 - elapsed)` 延后。CHANGELOG（`packages/tui/CHANGELOG.md:511`）记录了这一改动的动机：「Fixed render scheduling under heavy streaming output by coalescing `requestRender()` calls to a 16ms frame budget while preserving immediate `requestRender(true)` behavior.」
- **键盘输入绕过节流**：`tui.ts:1077-1080`（源码注释，一手）
  ```
  // Keyboard input is latency-sensitive. Avoid the throttled timer path,
  // where even setTimeout(0) can take a full 16 ms tick on Windows.
  ```
  对应 `requestImmediateRender()`（`tui.ts:963-978`）会先 `cancelRenderTimer()` 再在 `process.nextTick` 里直接渲染。
- **同步输出**：两套渲染器都把一帧包在 CSI 2026 里（`\x1b[?2026h` … `\x1b[?2026l`），README「Both renderers wrap updates in **synchronized output**」。
- **组件级缓存**：`Component.render(width)` 返回 `string[]`，组件自己缓存；`invalidate()` 清缓存。`Markdown`、`Text`、`Image`、`Box` 都有缓存。`tui-plan.md:7` 决策 7 明确「Rely on existing leaf render caches… Do not introduce a second framework-level render cache initially.」

### 2.5 输入模型

- **原始模式 + 自建序列切分器**：`ProcessTerminal.start()` 进 raw mode，然后把 stdin 喂给 `StdinBuffer`（`src/stdin-buffer.ts`，444 行），由它把一次 `data` 事件里批量到达的字节切成**单个按键序列**再往上抛（`terminal.ts:213-228`）。
- **括号粘贴**：启动时发 `\x1b[?2004h`（`terminal.ts:181`）；`StdinBuffer` 识别 `\x1b[200~`…`\x1b[201~` 并以 `paste` 事件整体抛出（`stdin-buffer.ts:324-372`），`ProcessTerminal` 再把它重新包上标记交给编辑器（`terminal.ts:230-235`）。编辑器对 **>10 行**的粘贴折叠成 `[paste #1 +50 lines]` 标记（`packages/tui/README.md` Editor 一节）。
- **Kitty 键盘协议协商 + modifyOtherKeys 兜底**（`terminal.ts:14, 242-262`）：发 `\x1b[>7u\x1b[?u\x1b[c`——先请求 flags 7（1 消歧义 + 2 报告按下/重复/释放 + 4 报告备用键），再查询，末尾挂一个 DA 查询作哨兵。**不支持 Kitty 协议的终端会先回 DA，此时立刻切到 `\x1b[>4;2m`（xterm modifyOtherKeys），不需要启动超时**（源码注释原文：「receiving DA before a Kitty response enables modifyOtherKeys fallback without a startup timeout」）。
- **ESC 歧义窗口按传输链路自适应**：`terminal.ts:115-131`，默认 10 ms，检测到 `SSH_CONNECTION`/`SSH_TTY` 时 100 ms，可用 `PI_TUI_ESC_TIMEOUT` 覆盖。理由写在源码注释里：「Legacy Alt+key input is ESC plus another byte, so high-latency transports need a longer reassembly window.」
- **退出前排空 stdin**：`Terminal.drainInput(maxMs=1000, idleMs=50)`（`terminal.ts:77-84` 接口注释）——「Drain stdin before exiting to prevent Kitty key release events from leaking to the parent shell over slow SSH connections.」这是 issue #1204 的修复（`packages/tui/CHANGELOG.md:774`）。
- **IME**：`Focusable` 接口 + `CURSOR_MARKER`（零宽 APC 序列）。组件在假光标位置吐出 marker，TUI 扫描渲染结果找到它，把**硬件光标**定位过去；硬件光标默认隐藏（只为追踪 IME 候选窗的终端服务），`PI_HARDWARE_CURSOR=1` 或 `showHardwareCursor` 可以让它可见（`packages/tui/README.md` Focusable 一节 + `packages/coding-agent/docs/terminal-setup.md`）。README 明确警告：容器组件若不把 `focused` 透传给内部 `Input`/`Editor`，**中日韩 IME 候选窗会出现在错误位置**。
- **键位全可配**：`AGENTS.md` 硬性规定「Never hardcode key checks (e.g. `matchesKey(keyData, "ctrl+x")`). Add defaults to `DEFAULT_EDITOR_KEYBINDINGS` or `DEFAULT_APP_KEYBINDINGS` so they stay configurable.」

### 2.6 宽字符与字形

- `src/utils.ts:1-5`：`get-east-asian-width` 的 `eastAsianWidth` + 两个 `Intl.Segmenter`（grapheme 与 word 粒度）。
- `graphemeWidth()`（`utils.ts:182-240`）处理了 `Intl.Segmenter` 把多个「终端会各占一格」的码点合并成一个 grapheme 的情况——源码注释：「Intl.Segmenter can group multiple terminal-spacing code points into one grapheme. Count trailing visible code points that terminals may allocate…」

### 2.8 非 TTY / headless / 管道模式

- **模式判定**（`packages/coding-agent/src/main.ts:111-122`，一手）：
  ```ts
  function resolveAppMode(parsed: Args, stdinIsTTY: boolean, stdoutIsTTY: boolean): AppMode {
      if (parsed.mode === "rpc") return "rpc";
      if (parsed.mode === "json") return "json";
      if (parsed.print || !stdinIsTTY || !stdoutIsTTY) return "print";
      return "interactive";
  }
  ```
  **stdin 或 stdout 任一不是 TTY 就自动降级为 print 模式**，不需要显式加 `-p`。
- **stdout 接管**（`main.ts:639-642` + `packages/coding-agent/src/core/output-guard.ts:45-70`）：非交互模式下调用 `takeOverStdout()`，它把 `process.stdout.write` **整个替换成写 stderr**，把真正的 stdout 句柄藏起来，只有受控的 `writeRawStdout()` 能写到真 stdout。效果是任何第三方库或扩展的杂散 `console.log` 都不会污染机器可读输出流。
- `writeRawStdoutChunk()`（`output-guard.ts:22-42`）对 `ENOBUFS`/`EAGAIN`/`EWOULDBLOCK` 做 10 ms 退避重试循环，并有 `waitForRawStdoutBackpressure()` 背压等待（print-mode 使用）。
- 输出模式：`--mode text`（默认，只输出最终回复）/ `--mode json`（事件流，`modes/json-event.ts`）/ `--mode rpc`（`modes/rpc/`，821 行）。
- **print 模式的信号处理与交互模式不同**：只注册 `SIGTERM`（+ 非 Windows 的 `SIGHUP`），退出码 `SIGHUP→129` / `SIGTERM→143`（`modes/print-mode.ts:50-67`）。

### 2.9 图片与富内容

- Kitty graphics protocol 与 iTerm2 inline images 两套（`src/terminal-image.ts`，696 行），不支持时回落成文字占位。
- **alt-screen 下 iTerm2 图片被强制降级为文字**，README 给了原因（一手）：「iTerm2's inline-image protocol does not provide operations to delete an existing placement or crop its source while scrolling. To prevent stale images from remaining over repainted content, `TuiAltScreen` renders image components as text placeholders in iTerm2.」
- `src/latex.ts` 有 1,506 行，把 LaTeX 数学式渲染成终端 Unicode（分式、上下标、矩阵、cases、对齐方程）。这是自建栈里体量第三大的文件。

## 3. 工程实践与设计品味（含作者自述理由）

**结论：Pi 的「明确拒绝」写得比多数项目直白，而且两条最核心的拒绝——不用 React 式 TUI、不夺走终端 scrollback——一条守住了，另一条在 2026-08 被自己部分推翻。**

### 3.1 为什么自建 TUI（作者原文，一手，2025-11-30）

来源：Mario Zechner, *What I learned building an opinionated and minimal coding agent*, <https://mariozechner.at/posts/2025-11-30-pi-coding-agent/>（全文已本地留存，见 §8）

> "So why build my own TUI framework? I've looked into the alternatives like Ink, Blessed, OpenTUI, and so on. I'm sure they're all fine in their own way, but **I definitely don't want to write my TUI like a React app**. Blessed seems to be mostly unmaintained, and OpenTUI is explicitly not production ready. Also, writing my own TUI framework on top of Node.js seemed like a fun little challenge."

### 3.2 为什么选 inline 而非全屏（作者原文，一手，同上）

> "There's basically two ways to do it. One is to take ownership of the terminal viewport … I call these full screen TUIs. **Amp and opencode use this approach.**"

> "The drawback is that you lose the scrollback buffer, which means you have to implement custom search. You also lose scrolling, which means you have to simulate scrolling within the viewport yourself. While this is not hard to implement, it means you have to re-implement all the functionality your terminal emulator already provides. **Mouse scrolling specifically always feels kind of off in such TUIs.**"

> "The second approach is to just write to the terminal like any CLI program, appending content to the scrollback buffer … **This is what Claude Code, Codex, and Droid do.**"

> "Everything is nicely linear, which lends itself well to working with the 'native' terminal emulator. You get to use all the built-in functionality like natural scrolling and search within the scrollback buffer. **It also limits what your TUI can do to some degree, which I find charming because constraints make for minimal programs** … This is the direction I picked for pi-tui."

**这段自述与当前实现的分叉，必须写明**：博客写于 2025-11-30；到 `890f920`（0.86.1，2026-09），仓库里已经有了 1,742 行的 `TuiAltScreen`，它恰好做了博客里被列为「drawback」的三件事——接管视口、自己实现滚动、自己实现搜索（`src/alt-screen-search.ts`，327 行）。**以实现为准：Pi 现在两条路都走。** 默认仍是博客里那条（§2.1），alt-screen 被文档标为 experimental。作者没有公开撤回博客里的判断，我也没有找到他解释这次扩展的一手文字（§7.2）。

### 3.3 flicker 与成本的自我评估（作者原文，一手）

> "To prevent flicker during updates, pi-tui wraps all rendering in synchronized output escape sequences (`CSI ?2026h` and `CSI ?2026l`). This tells the terminal to buffer all the output and display it atomically. Most modern terminals support this."

> "In any capable terminal like Ghostty or iTerm2, this works brilliantly and you never see any flicker. **In less fortunate terminal implementations like VS Code's built-in terminal, you will get some flicker** depending on the time of day, your display size, your window size, and so on. Given that I'm very accustomed to Claude Code, I haven't spent any more time optimizing this. I'm happy with the little flicker I get in VS Code. I wouldn't feel at home otherwise. **And it still flickers less than Claude Code.**"

> "How wasteful is this approach? We store an entire scrollback buffer worth of previously rendered lines, and we re-render lines every time the TUI is asked to render itself. That's alleviated with the caching I described above… We still have to compare a lot of lines with each other. Realistically, on computers younger than 25 years, this is not a big deal, both in terms of performance and memory use (**a few hundred kilobytes for very large sessions**). Thanks V8."

「a few hundred kilobytes」**没有给测法**，是作者的估计而非测量结果。§5.2 的 issue 数据与这个乐观估计在方向上是冲突的（那些测的是 CPU 与 stdout 字节量，不是保留的行缓冲内存，两者不是同一个量，不能直接对冲——但都指向「重绘成本随会话总量线性增长」这一同一机制）。

### 3.4 明确拒绝做的事（仓库一手）

- **核心极小、其余走扩展**（`CONTRIBUTING.md`）：「First things first: **pi's core is minimal**. If your feature does not belong in the core, it should be an extension. PRs that bloat the core will likely be rejected. … Even hook points for extensions however should be well considered and discussed to avoid adding unmaintainable bloat and complex interactions.」
- **不做权限系统**（`README.md`）：「Pi does not include a built-in permission system for restricting filesystem, process, network, or credential access. By default, it runs with the permissions of the user and process that launched it.」需要边界就自己容器化。
- **不做 plan mode**（作者博客）：「pi does not and will not have a built-in plan mode. Telling the agent to think through a problem together with you, without modifying files or executing commands, is generally sufficient.」
- **不保留向后兼容**（`AGENTS.md`）：「Do not preserve backward compatibility unless the user asks for it.」
- **不允许动态 import**（`AGENTS.md`）：「**No inline imports** (`await import()`, `import("pkg").Type`, dynamic type imports). Top-level imports only.」——这条与 §4.3 的 koffi 历史直接相关。
- **不允许写死键位**（`AGENTS.md`，见 §2.5）。
- **Windows 上不支持挂起**：`interactive-mode.ts:4243-4246`，`Ctrl+Z` 在 Windows 上直接提示「Suspend to background is not supported on Windows」。
- **贡献门禁**（`CONTRIBUTING.md`）：新贡献者的 issue 与 PR **默认自动关闭**；维护者每日回看并重开值得的；`lgtmi` 放行 issue，`lgtm` 放行 issue+PR；「If you ignore this document twice, or if you spam the tracker with agent-generated issues, your GitHub account will be permanently blocked.」——**这条政策对读 issue tracker 的方法有决定性影响，见 §5.0。**
- **文风**（`AGENTS.md`）：「No emojis in commits, issues, PR comments, or code」「No fluff or cheerful filler text」「Explain non-trivial designs and problems as: problem, concrete example or short trace, then solution.」

## 4. 实施取舍与代价

**结论：自建 TUI 换来的是零框架锁定与可直接调试的渲染路径，付出的是 18k 行自有代码里必须自己解决终端兼容、宽字符、IME、鼠标、图片协议全部问题；把终端差异推给用户配置是它的显式策略；Windows 是唯一需要原生二进制才能正确工作的平台，而 CI 从不在 Windows 上跑测试。**

### 4.1 自建栈要自己承担的东西（可枚举，源码可查）

18,267 行 `packages/tui/src` 里，下面这些在用 Ink/React 时至少有一部分是别人维护的：按键序列解析（`keys.ts` 1,401 行）、stdin 分帧与括号粘贴（`stdin-buffer.ts` 444 行）、宽字符/字形测宽与 ANSI 感知截断换行（`utils.ts` 1,345 行）、多行编辑器含 undo/kill-ring/词导航/自动补全（`editor.ts` 2,470 + `undo-stack.ts` + `kill-ring.ts` + `word-navigation.ts`）、Markdown 渲染（1,015 行）、LaTeX 渲染（1,506 行）、图片协议（696 行）、模糊匹配（`fuzzy.ts` 138 行）、alt-screen 布局与事件路由（1,742 + 449 + 51 行）。

**代价的另一面在 CHANGELOG 里是可数的**：`packages/tui/CHANGELOG.md` 有 1,183 行、`packages/coding-agent/CHANGELOG.md` 有 5,810 行，其中终端兼容类条目（某终端的某个键、某个协议、某个转义序列）密集出现。这是自建栈的持续维护税，不是一次性成本。

### 4.2 把终端差异推给用户配置

`packages/coding-agent/docs/terminal-setup.md`（192 行）是这条策略的直接产物。它为 **11 类终端**逐一写了用户要做什么：

- **Ghostty**：要在配置里加 `keybind = alt+backspace=text:\x1b\x7f`；还要注意「Older Claude Code versions may have added this Ghostty mapping: `keybind = shift+enter=text:\n`. That mapping sends a raw linefeed byte. **Inside pi, that is indistinguishable from `Ctrl+J`**, so tmux and pi no longer see a real `shift+enter` key event.」
- **WezTerm**：macOS 上 `Option+Enter` 被占，要写 lua 覆盖发 `\x1b[13;3u`；WSL 上 CJK IME 候选窗不跟随光标时要设 `PI_HARDWARE_CURSOR=1`。
- **Alacritty**：macOS 上 `Option+Enter` 变成普通 `Enter`，要在 toml 里加 binding。
- **VS Code**：1.109.5 以下要自己加 `workbench.action.terminal.sendSequence` keybinding。
- **Zed**：要加三条 `terminal::SendText`。
- **Windows Terminal**：要在 settings.json 里加 `sendInput` action 才能有 `Shift+Enter`；`Alt+Enter` 被 Windows Terminal 占作全屏。
- **tmux**：`docs/tmux.md` 要求 `set -g extended-keys on` + `set -g extended-keys-format csi-u`，且 `extended-keys-format` 需要 tmux ≥ 3.5。
- **xfce4-terminal / terminator**：文档直接承认做不到——「These terminals have limited escape sequence support. Modified Enter keys like `Ctrl+Enter` and `Shift+Enter` cannot be distinguished from plain `Enter`, **preventing custom keybindings such as `submit: ["ctrl+enter"]` from working**.」并建议换终端。
- **IntelliJ IDEA 内置终端**：同样做不到——「Shift+Enter cannot be distinguished from Enter in IntelliJ's terminal.」
- **iTerm2 全屏模式**：滚轮加速度丢失，需要改 iTerm2 全局设置 **Trackpad scrolls fast? → No**，文档自己写明「This is an iTerm2-wide workaround and **may also change native trackpad scrolling**」，并挂了上游 iTerm2 issue 9619。
- **Ghostty 全屏模式**：「links remain clickable, but Ghostty does not show its hover underline or lower-left URL preview while pi captures mouse input.」

**这是一份坦白的能力边界清单**，同时也是这条技术路线的账单：对 Kitty 键盘协议的依赖把一部分兼容成本外部化成了用户的终端配置工作。

### 4.3 原生模块的历史成本（CHANGELOG 可追，一手）

Windows VT 输入这一个功能的实现方式换了三次，每次都有记录的代价：

1. **koffi（FFI）时期**，`packages/tui/CHANGELOG.md:699`：
   > "Changed koffi import from top-level to dynamic require in `enableWindowsVTInput()` **to prevent bun from embedding all 18 platform `.node` files (~74MB) into every compiled binary.** Koffi is only needed on Windows."

   ——一个只在 Windows 用到的 FFI 依赖，会给**每个平台**的编译二进制加约 74 MB。
2. 同期 ESM 兼容问题，`:689`：「Fixed Windows VT input initialization in ESM by loading `koffi` via `createRequire`, restoring VT input mode while keeping `koffi` externalized from compiled binaries（#1627）」。
3. **换成自带原生 helper**，`:337`（对应 issue #4480，2026-05-13）：「Replaced the optional `koffi` dependency for Windows VT input with a tiny vendored native helper, **reducing install size** while preserving Shift+Tab handling.」
4. 剪贴板同样走过外部 napi-rs 依赖并出过事：`packages/coding-agent/CHANGELOG.md:1432`「Fixed Windows startup crashes under MSYS2 ucrt64 Node.js by updating the native clipboard addon to napi-rs 3.x（#5028）」；到 **0.86.0**（`packages/tui/CHANGELOG.md:11`）才「Added bundled asynchronous native clipboard readers for macOS, Windows, and X11 through the exported `getNativeClipboard()` API, **replacing the external native clipboard dependency in consumers**（#9163）」。

**净结果**：三个平台的原生代码总共只有 678 行 C/ObjC/头文件，预编译产物 8.7 KB–67 KB。代价转移到了构建侧——`native/darwin/README.md` 说交叉构建需要「a Darwin toolchain with a macOS SDK and Mach-O linker, such as osxcross… **Plain clang or Zig alone is not sufficient**」，且 SDK 必须按 Apple 许可获取；`native/win32/README.md` 要 Visual Studio「Desktop development with C++」或 MinGW 交叉工具链。

### 4.4 Windows：付出了什么，以及没有付出什么

**付出的（源码可查）**：

- `native/win32/win32-platform.c:33-48`：`enableVirtualTerminalInput()` 对 stdin 控制台句柄补上 `ENABLE_VIRTUAL_TERMINAL_INPUT`。调用点 `terminal.ts:375-384`，注释给出理由（一手）：
  > "On Windows, add ENABLE_VIRTUAL_TERMINAL_INPUT (0x0200) to the stdin console handle so the terminal sends VT sequences for modified keys (e.g. `\x1b[Z` for Shift+Tab). **Without this, libuv's ReadConsoleInputW discards modifier state and Shift+Tab arrives as plain `\t`.**"
  
  调用必须排在 `setRawMode(true)` 之后（`terminal.ts:193-198` 注释：「Must run AFTER setRawMode(true) since that resets console mode flags.」）。
- `isModifierPressed()` 原生查询：用于在 Windows（和 Apple Terminal）上把本应是 `Shift+Enter` 的裸 `\r` 还原成 `\x1b[13;2u`（`terminal.ts:346-356`）。作用范围有限——文档承认这个回落「cannot detect the local keyboard over remote SSH」。
- alt-screen 的 Windows 专属右键粘贴（`tui-alt-screen.ts:1000-1016`），且显式排除 VS Code 终端（因为 #8186 的重复粘贴）。
- Windows 专属键位默认值（`packages/coding-agent/src/core/keybindings.ts:63-97`）：`isWindowsKeybindings()` 同时覆盖原生 Windows **和 WSL**（看 `WSL_DISTRO_NAME`/`WSL_INTEROP`）；`Ctrl+Z` 在原生 Windows 是撤销，在 WSL 改成 `Alt+Z` 以便 `Ctrl+Z` 仍能挂起。
- Windows 上 npm 会抢控制台标题，启动检查结束后要把标题抢回来（`interactive-mode.ts:1105-1109`，含注释）。
- `windows-x64` 与 `windows-arm64` 两个二进制在发布矩阵里。
- `pi-test.ps1` / `pi-test.bat` 让 Windows 上能从源码直接跑 pi。

**没有付出的（这一条是硬性更正）**：派发说明推测 `pi-test.ps1` / `pi-test.bat` 是「Windows 测试脚本」，说明项目认真对待 Windows 终端。**读过后这个推断不成立。** 这两个文件是**开发期的「从源码跑 pi」包装器**——`pi-test.ps1` 只做两件事：可选地清掉一串 API key 环境变量（`--no-env`），然后用 `node_modules/.bin/tsx.cmd` 执行 `packages/coding-agent/src/cli.ts`；`pi-test.bat` 只是转调 `pi-test.ps1`。它们不跑任何断言，与 `pi-test.sh`（POSIX 版）一一对应。

**真正决定 Windows 质量的是 CI**，而 `.github/workflows/ci.yml:15` 只有一个 job，`runs-on: ubuntu-latest`，步骤是 build / check / test。**Windows 只出现在 `build-binaries.yml` 的编译矩阵里（`windows-latest`，只编译不跑测试），以及 `issue-analysis.yml` 里一个需要显式写 `#run-on-windows` 才触发的分析 runner。** 也就是说：**测试套件从不在 Windows 上运行。** §5.3 里三个 Windows 渲染缺陷与这个事实一致。

### 4.5 生态锁定与可移植性

- **锁在 Node ≥22.19 的具体特性上**：`Intl.Segmenter`、`node:inspector/promises`（benchmark）、strip-only TypeScript、`process.stdout.write` 可替换。不是锁在框架上。
- **Bun 是二等但真实的目标**：二进制用 bun 编译；`profile-coding-agent-node.mjs` 支持 `--runtime bun`；CHANGELOG 记录过 bun 专属崩溃（`bunfig.toml` preload，#7685）与 bun 沙箱下 `process.env` 为空要读 `/proc/self/environ`（#3801）。
- **`pi-tui` 是独立可用的 npm 包**（2.73 MiB，188 文件），不绑 coding agent。`docs/tui.md`（961 行）面向扩展作者文档化了组件系统——**扩展可以直接往终端里画自己的 UI**。Armin Ronacher 的博文（二手转述其原文）：「Pi extensions can render custom TUI components directly in the terminal: spinners, progress bars, interactive file pickers, data tables, preview panes. The TUI is flexible enough that Mario proved you can run Doom in it.」（<https://lucumr.pocoo.org/2026/1/31/pi/>；「run Doom」这一句我**没有**找到可核实的原始演示链接，记为待验证命题。）
- **可调试性是这条路线的明显收益**：渲染输出是 `string[]`，`PI_TUI_WRITE_LOG` 能把完整 ANSI 流落盘，`VirtualTerminal` 能在单测里断言屏幕状态。没有 reconciler、没有 fiber、没有 wasm 布局引擎横在中间。

### 4.6 CLI/TUI 层没有规格

派发说明提到仓库里有 `packages/agent/docs/harness.md`（`AgentHarness` 规格，§0.9 自陈 WP08 进行中）。**我核对过：那份 1,000+ 行的规格讲的是持久化会话、operation 状态机、存储与恢复，与 CLI/TUI 渲染层没有交集。** 它的 §0.9 实现状态清单（J1/C1/R12/T1/S3/R11/WP08/H1）没有一条涉及终端界面。

因此在 CLI/TUI 这一层，**不存在「规格 vs 现状」的双轨**，而是另一种形态的双轨：**两套并存的渲染器**（§2.1）。最接近规格的文档是 `tui-plan.md`（已落地的实现交接稿）与 `packages/tui/README.md` + `docs/tui.md`（已发货行为的文档）。**CLI/TUI 层没有形式规格，没有一致性矩阵。**

### 5.0 读这个 tracker 前必须知道的事（方法论，源码验证）

**`.github/workflows/issue-gate.yml` 会在 issue 被创建时自动关闭它。** 关键代码（`issue-gate.yml:99-128`，一手）：

```js
const message = [
  'This issue was auto-closed. All issues from new contributors are auto-closed by default.',
  ...
];
await github.rest.issues.createComment({ ..., body: message });
await github.rest.issues.addLabels({ ..., labels: ['untriaged'] });
await github.rest.issues.update({ ..., state: 'closed', state_reason: 'not_planned' });
```

只有 collaborator（admin/maintain/write）、`.github/APPROVED_CONTRIBUTORS` 名单内的人、以及受信任的 bot 能豁免。

**推论（我的判断，依据是上面的代码 + `CONTRIBUTING.md` 的政策描述）**：在这个仓库里，一个 issue 标着 `untriaged` 且状态是 **closed as not planned**，**默认含义是「开门即被机器关掉」，不是「维护者判定为不修」**。维护者每日回看并重开值得的。因此把「closed」当作「已解决/已拒绝」来读会系统性地误判这个 tracker。

**这条推论的边界**：我无法对每一个具体 issue 断定它是被自动关的还是被人工关的——WebFetch 返回的页面摘要里我没能稳定看到 bot 评论原文。下面凡标「closed as not planned + untriaged」的，我都按「关闭原因未确证」处理。

**另一个后果**：`pkg:tui` 标签只挂在 **20 个 issue** 上，全部 closed，最后一个是 #4480（2026-05-13）。标签在那之后就不再被系统使用了，**按标签检索 TUI 问题会严重漏报**。

### 5.4 源码级交叉验证：#6665 的两条根因，一条已缓解，一条仍在

这是我按「文档/issue 说的 ≠ 实现做的」做的构造性核对，结论以**源码为准**：

- **根因 (a) grapheme 分词无缓存 —— 已缓解。** `890f920` 的 `packages/tui/src/utils.ts:50-52` 有 512 条 LRU（`widthCache`）加纯 ASCII 快速路径。issue 报的是 0.80.7，缓存是之后加的。**我没有测这个缓存对 issue 场景的实际效果**，只能说机制存在了。
- **根因 (b) 每次更新重建 Markdown —— 仍然存在。** `packages/coding-agent/src/modes/interactive/components/assistant-message.ts:91-118`：`updateContent()` 一上来 `this.contentContainer.clear()`，然后对每个 text 内容块 `this.contentContainer.addChild(new Markdown(content.text.trim(), ...))`。**每次流式更新都构造新的 `Markdown` 实例，旧实例的渲染缓存随之丢弃。** 这与 issue #6665 的描述在 0.86.1 上仍然吻合。

这与 §3.3 里作者「这不是大问题，感谢 V8」的判断构成实质分歧：**作者估计的是保留行缓冲的内存开销（几百 KB），而 issue 测的是流式与 resize 时的 CPU 与 stdout 字节量**。两者不是同一个量，但都源自同一机制——整棵组件树每帧参与渲染与比较，开销随会话总量而非可见视口增长。**这个缺陷目前在仓库里没有已落地的解法**：#6665 标着 `inprogress`、#9549 有指派人但无修复记录，两者在 `890f920` 上都还开着。
