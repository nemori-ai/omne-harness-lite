## 1. 技术栈

**结论：Rust 单体静态二进制，TUI = ratatui 0.30.2（开了四个 unstable feature）+ 一个自维护的 crossterm 0.29.0 分叉；ratatui 的 `Terminal` 被整体复制进仓库改造成 `custom_terminal`。整个 `codex-rs` 是 149 个 workspace 成员、1491 个 lock 条目、186 万行 Rust。**

### 1.1 语言与运行时

- Rust，toolchain 固定 `1.95.0`（`codex-rs/rust-toolchain.toml:2`）。
- 发布 target 含 `x86_64-unknown-linux-musl`、`aarch64-unknown-linux-musl`、`{x86_64,aarch64}-apple-darwin`、`{x86_64,aarch64}-pc-windows-msvc`（`codex-cli/bin/codex.js:16-23`）。
- **Linux 版是 musl 静态链接**：`ldd` 报 `statically linked`，ELF 无 `PT_INTERP` 段。`file(1)` 显示 `dynamically linked` 是 static-PIE（`ET_DYN` 且无 interp）的误判，**不要照抄 `file` 的说法**。

- npm 包 `@openai/codex` 本体只有一个 `bin/codex.js` 派发器（`codex-cli/package.json` 的 `files: ["bin/codex.js"]`），真正的二进制走 `@openai/codex-<platform>` 平台包。Node 只在 npm 安装路径上作为启动器出现，`engines.node >= 16`；standalone 安装（`curl … install.sh`）完全不经过 Node。

## 2. 交互范式与渲染

**结论：默认是 inline 模式——底部一个固定高度的 ratatui viewport，已完成的对话通过裸 ANSI escape 直接压进终端原生 scrollback；alternate screen 默认只给 overlay 用，整会话占屏（`fullscreen_transcript`）是 2026-09 才在推进的 opt-in。流式输出被切成"稳定区/尾区"两段，稳定区进 scrollback，尾区留在活动 cell 里可改写。**

### 2.1 alt-screen 到底默认开不开——三层状态，help 文案会误导

三个状态量：

| 量 | 来源 | 默认 |
|---|---|---|
| `alt_screen_enabled` | `--no-alt-screen` / `tui.alternate_screen`（`auto`/`always`/`never`） | `true`（`auto` → `!= Never` → true，`lib.rs:2047-2053`） |
| `tui.fullscreen_transcript` | config | **`false`**（`config/src/types.rs:800-804`：「Own the fullscreen transcript … Defaults to `false`; alternate-screen restrictions take precedence.」） |
| `owned_screen` | `TranscriptMode::resolve(fullscreen_transcript, alt_screen_enabled)` | `false` |

`transcript_mode.rs` 全文只有 20 行，`resolve` 是 `owned_enabled && alternate_screen_enabled`。而 `Tui::draw()` 里进 alt-screen 的唯一条件是：

```rust
if self.owned_screen && !self.is_alt_screen_active() {
    self.enter_alt_screen()?;
```
（`tui.rs:1182`）

`set_alt_screen_enabled` 的 doc 写得更直白（`tui.rs:714`）：

```
/// Set whether overlays switch to the alternate screen or stay inline.
```

**事实**：默认配置下主对话区不进 alt-screen；`tui::init()` 的函数注释就是 `Initialize the terminal (inline viewport; history stays in normal scrollback)`（`tui.rs:428`）。alt-screen 只在 overlay（Ctrl+T transcript、pager、picker）或显式 `fullscreen_transcript = true` 时启用。

**文档与实现分叉**：`--no-alt-screen` 的 help 文案是「Disable alternate screen mode / Runs the TUI in inline mode, preserving terminal scrollback history」（`tui/src/cli.rs:78-81`，本机 0.154.0 `codex --help` 输出逐字一致）。**这句话隐含"默认是 alt-screen 模式"，与源码默认值不符**——它实际关掉的是 overlay 的 alt-screen 与 owned 模式的可能性，主对话本来就是 inline。**以源码为准**；这是本轮发现的第一处文档层与实现层冲突。

**方向性证据（一手）**：`lib.rs:1845-1856` 有一个遥测计数器 `codex.tui.fullscreen_transcript`，按 `enabled` 打标签统计每次启动——他们在度量 owned 模式的采用率。PR #46733「Integrate the interactive transcript into the alternate-screen TUI」于 2026-09-20 合入（HEAD 前一天）。**判断**：owned/alt-screen 路线正在推进，但截至 HEAD 仍不是默认。

### 2.2 历史行怎么进 scrollback

`codex-rs/tui/src/insert_history.rs`（47.9 KB）文件头原文：

```
//! Inserts finalized history rows into terminal scrollback.
//!
//! Codex uses the terminal scrollback itself for finalized chat history, so inserting a history
//! cell is an escape-sequence operation rather than a normal ratatui render. Untrusted content
//! follows ratatui's control-character filtering before semantic hyperlinks add trusted escapes.
```

机制：viewport 要长高时，先把 viewport 上方的区域用 DECSTBM 滚动区往上顶，腾出的行用 `Print("\r\n")` 推进原生 scrollback，然后把 pre-wrap 好的历史行直接 `queue!` 成 SGR + `Print` 写出去。三条折行路径（`insert_history.rs:115-127` 注释原文）：

- 整行像 URL 的：**不插硬换行**，交给终端字符折行，这样终端能把它识别成可点击链接；
- URL 与散文混排的：自适应折行，URL token 不拆；
- 纯散文：自适应折行（等价于标准折行）。

### 2.3 三套 scrollback 策略：终端特判被写死在代码里

`codex-rs/tui/src/tui/scrollback.rs` 全文 105 行，是本轮最能说明"为原生 scrollback 服务要付多少特判成本"的一份材料：

```rust
pub(super) enum ScrollbackStrategy { Standard, Zellij, FullScreen }

pub(super) fn detect(terminal: &TerminalInfo) -> Self {
    if terminal.is_zellij() { Self::Zellij }
    else if terminal.name == TerminalName::WindowsTerminal
        || std::env::var_os("WT_SESSION").is_some() { Self::FullScreen }
    else { Self::Standard }
}
```

`grow_viewport` 里的注释直接点名了三家终端的行为差异（原文）：

- `Standard` 分支：「CSI S can discard departing rows in QTermWidget and xterm.js. Newlines at the bottom of the history region preserve native scrollback while protecting the composer.」
- `FullScreen` 分支：「Partial DEC scroll regions can discard rows instead of moving them into Windows Terminal's scrollback. … Also use this path for a single history row: DECSTBM requires two distinct rows.」
- `Zellij` 分支：直接调 `scroll_region_up`。

**判断**：这三条分支各自对应一类终端的 scroll-region 实现缺陷；每多支持一种宿主，就多一条不可用统一模型覆盖的路径。**代价证据**：issue #42020（open，2026-09-01，labels `bug,windows-os,TUI,CLI`）报告的正是这套 detect 的漏洞——**原生 Windows 下的 VS Code 集成终端既不上报 `TerminalName::WindowsTerminal` 也不设 `WT_SESSION`，于是落到 `Standard`，inline scrollback 丢失**。源码与该 issue 互为佐证。

### 2.4 流式输出：两段模型 + 表格 holdback

`codex-rs/tui/src/streaming/controller.rs` 文件头（原文节选）：

```
//! Each stream partitions rendered markdown into a *stable region* (committed
//! to scrollback via the animation queue in `StreamState`) and a *tail region*
//! (mutable, displayed in the active-cell slot as a transient stream-tail cell).
...
//! ## Table holdback
//!
//! Table rendering is inherently non-incremental: adding a new row can change
//! every column's width and reshape all prior rows.  The holdback mechanism
//! ... keeps content from the table header onward as mutable tail until the stream finalizes.
...
//! ## Resize handling
//!
//! On terminal width change, `StreamCore::set_width` re-renders at the new
//! width and rebuilds the queued stable region from the current emitted line
//! count. This intentionally avoids byte-level remap complexity while the
//! stream is active;
```

三条不变式也写在文件头，其中一条：「committed source is append-only until `reset()`; never modified mid-stream.」

**这一段是他们明确承认的取舍**：流式中 resize 走的是"按新宽度整体重渲 + 按已发行数重建稳定区"，**有意不做字节级 remap**。§5.2 里大量「resize 后整段 transcript 重播 / 丢行」的 open issue 与这条设计选择直接相关。

### 2.5 渲染循环与事件循环

- **帧率钳制**：`tui/frame_rate_limiter.rs`，`MIN_FRAME_INTERVAL = 8_333_334 ns`（120 FPS）。注释原文：「Widgets sometimes call `FrameRequester::schedule_frame()` more frequently than a user can perceive. This limiter clamps draw notifications to a maximum of 120 FPS to avoid wasted work.」——即**请求驱动重绘 + 上限钳制**，不是固定 tick。
- **差分粒度**：viewport 内 cell 级差分（`diff_buffers`）；viewport 外的历史是一次性 escape 写入，不参与差分。
- **同步更新**：每次 `draw` 整体包在 `stdout().sync_update(|_| …)`（crossterm 的 `SynchronizedUpdate`，即 DEC 2026）里（`tui.rs:1170`、`:1251`、`:1270`、`:1317`）。
- **事件与模型流解耦**：`tui/event_stream.rs` 用 `EventBroker` 持有共享的 crossterm `EventStream`，配 `tokio::sync::broadcast` 分发；draw 请求是独立的 subscription。文件头给出了 drop/recreate 的理由（原文）：

  > The motivation for dropping/recreating the crossterm event stream is to enable the TUI to fully relinquish stdin. If the stream is not dropped, it will continue to read from stdin even if it is not actively being polled (due to how crossterm's EventStream is implemented), potentially stealing input from other processes reading stdin, like terminal text editors. This race can cause missed input or capturing terminal query responses (for example, OSC palette/size queries) that the other process expects to read.

  并引用了 `https://ratatui.rs/recipes/apps/spawn-vim/` 与一条 reddit 线索作为出处。

### 2.6 终端能力探测与降级

`codex-rs/tui/src/terminal_probe.rs`（32 KB）文件头原文：

```
//! Crossterm's public helpers wait up to two seconds for terminal responses. That is too long for
//! TUI startup and resume, where unsupported terminals should simply fall back to conservative
//! defaults.
```

- **启动探测预算 250 ms**（`DEFAULT_TIMEOUT`，`terminal_probe.rs:24`），一次性查三项：光标位置（CPR）、默认前景/背景色（OSC 10/11）、键盘增强支持。超时全部退到保守默认（光标退到原点并 `tracing::warn!`）。
- 探测期间会**回放**被吃掉的终端字节给 crossterm 解析器（`startup_replay`），上限 `MAX_STARTUP_PROBE_BYTES = 64 KiB`；超过 1 KiB 的粘贴留给正常读取路径（`MAX_TERMINAL_PROBE_BYTES = 1024`）。
- **Windows 上不做启动色彩探测**，注释原文：「OSC replies can arrive after their deadline. Do not issue terminal queries before directory trust and other protected startup screens have finished accepting their security decisions.」
- **环境变量识别**：`codex-terminal-detection` crate 只读环境变量，从不执行 PATH 上的助手程序（文件头明写）。识别出 AppleTerminal / Ghostty / iTerm2 / Warp / VsCode / WezTerm / Kitty / Alacritty / Konsole / GnomeTerminal / Vte / WindowsTerminal / Dumb / Unknown，外加 multiplexer（Tmux / Zellij）。
- **键盘增强的保守降级**：`tui/keyboard_modes.rs` —— WSL 下若 VS Code 探测「不确定」，就直接**不启用** Kitty keyboard protocol，注释原文：「If the Windows-side probe is inconclusive, avoid enabling the keyboard mode that can break dead-key composition in VS Code on WSL.」可用 `CODEX_TUI_DISABLE_KEYBOARD_ENHANCEMENT` 强制关闭。
- **tmux 专属轮询**：`tui/size_monitor.rs` —— 仅当检测到 tmux 时启动一个 500 ms 轮询线程调 `crossterm::terminal::window_size()`，文件头标题就是「Recovers lost tmux resize notifications without querying geometry on the UI thread」。注释还说明为什么不用 `terminal::size()`：「Unlike terminal::size(), window_size() has no tput subprocess fallback.」**这条对应 PR #43603（2026-09-07 合入，随 0.155.0 发布），本机 0.154.0 没有。**
- **resize 回流行数上限按终端硬编码**（`tui/src/resize_reflow_cap.rs`）：VS Code 1,000 / Windows Terminal 9,001 / WezTerm 3,500 / Alacritty 10,000 / 其它 fallback 1,000。注释原文：「These caps are deliberately conservative: Codex is rebuilding normal terminal scrollback, not an internal virtual transcript. Replaying more rows than the terminal retains wastes work and can make interactive resize feel worse without giving the user more usable history.」

### 2.7 输入：鼠标、粘贴、宽字符

- **bracketed paste**：crossterm feature 显式开启（`bracketed-paste`）。此外还有一套 **paste burst 检测**——对非 bracketed-paste 终端，把快速连续按键识别成粘贴并缓冲，可用 `tui.disable_paste_burst` 关闭（`config/src/types.rs:783-788`，原文：「When true, disables burst-paste detection for typed input entirely. All characters are inserted as they are received, and no buffering or placeholder replacement will occur for fast keypress bursts.」）。
- **鼠标**：只在 alt-screen overlay 里开指针上报，序列写死在 `tui/alternate_screen.rs`：`\x1b[?1000h\x1b[?1002h\x1b[?1006h\x1b[?1003h`（含 1003 全动作上报）。退出路径对部分写失败做了逐条兜底 reset（`?1003l`/`?1002l`/`?1000l`/`?1006l`）。非 owned 模式下则 `EnableAlternateScroll`，把滚轮交还终端。
- **宽度**：`tui/src/width.rs` 用 `unicode-width`，并**显式补正半宽浊点/半浊点**（`U+FF9E`/`U+FF9F` 各按 1 列而非 0），测试里直接断言 `display_width("ｶﾞﾊﾟ") == 4`、`display_width("界ﾞ") == 3`。另有 `usable_content_width` 的严格正宽度契约：保留列吃光宽度时返回 `None`，调用方走「只渲染前缀」的回退路径，注释原文：「Coercing it to `0` and still attempting wrapped rendering often produces empty or unstable output at very narrow terminal widths.」
- **剪贴板图片**：`arboard` → PNG（`clipboard_paste.rs`），Android/Termux 上整个 `arboard` 依赖被排除（`Cargo.toml` 的 `cfg(not(target_os = "android"))`）。

### 2.8 非 TTY / headless

- `tui::init()` 第一件事就是 `stdin().is_terminal()` 与 `stdout().is_terminal()` 双重检查，任一为假直接返回 `Error::other("stdin is not a terminal")`（`tui.rs:430-436`）。**TUI 不做非 TTY 降级，它拒绝启动。**
- headless 是另一条独立实现：`codex exec`（alias `e`）。`codex-rs/exec` 的依赖里**没有 ratatui / crossterm**，只有 `owo-colors` + `supports-color`；输出分成 `event_processor_with_human_output.rs` 与 `event_processor_with_jsonl_output.rs` 两套 processor。
- 另有 `codex review`（非交互 code review）、`codex debug models|prompt-input`（纯 JSON 输出）。
- **stderr 隔离**：`tui/terminal_stderr.rs` 安装 `TerminalStderrGuard`，注释原文「Keeps unmanaged process stderr writes out of the inline viewport.」（`tui.rs:642`）。

### 2.9 主题与可访问性

- 语法高亮主题可配（`tui.theme`，`/theme` 命令，`$CODEX_HOME/themes` 放自定义）；状态行/终端标题都是可排序的 item 列表（`tui.status_line`、`tui.terminal_title`）。
- 颜色纪律写成了文档 + clippy 规则：`codex-rs/tui/styles.md` 明令「Avoid ANSI `black` & `white` as foreground colors」「Avoid ANSI `blue` and `yellow` because for now the style guide doesn't use them」，并注明「There are some rules to try to catch this in `clippy.toml`」。对比度检查走 `style::readable_color_on(color, background)`。
- **屏幕朗读器**：`tui/src/screen_reader.rs` 做一次性探测（`DETECTION_TIMEOUT = 450 ms`），检出则把动画默认关掉并把结果持久化成 `tui.screen_reader_detection_done`。对应 PR #46040「Default TUI animations off when a screen reader is detected」（closed，2026-09-16）。
- **`raw_output_mode`**：config 项原文「Start the TUI in raw scrollback mode for copy-friendly transcript output. Defaults to `false`.」——一个专为「能被复制」让渡渲染效果的模式，可用 slash 命令切换。
- 动画可整体关（`tui.animations`）或逐项关（`tui.effects.{starfield,shimmer,welcome,effort,progress,title}`，全部默认 `true`）；富内容渲染独立开关（`tui.rendering.{mermaid,math,tables}`，全部默认 `true`）。

## 4. 实施取舍与代价

**结论：最贵的一项是体积——262 MB 单二进制里 194.7 MB 是机器码。这不是资源文件问题，是"一个二进制装下 CLI+TUI+app-server+沙箱+AWS SDK+代理栈+语法高亮+图像解码+遥测"的必然结果，而且团队已明确拒绝优化它。第二贵的是终端兼容面：为服务"原生 scrollback"付出的特判路径数量，与 §5 的缺陷长尾是同一枚硬币的两面。**

### 4.2 `codex-code-mode-host`：为什么要单开一个 69 MB 的进程

**结论：因为它嵌了 V8。**

`codex-rs/code-mode-runtime/Cargo.toml` 依赖原文：

```toml
deno_core_icudata = { workspace = true }
v8 = { workspace = true, features = ["v8_enable_sandbox"] }
```

本机二进制交叉验证（带边界特征串）：`codex-code-mode-host` 里 `v8::internal` 命中 **56** 次、`icudt`（ICU data 表名前缀）命中 **2330** 次；主 `codex` 二进制里这两项都是 **0**。反过来 `ratatui-`/`crossterm` 在 host 里是 0。**两个二进制的职责边界是干净的、可构造验证的。**

进程间用 gRPC over tonic/prost 通信（`code-mode` 与 `code-mode-protocol` 都依赖 `tonic`、`prost 0.14.3`，protocol crate 的 build-dependency 里带 `protoc-bin-vendored`）。`codex-rs/v8-poc` 是一个独立的 V8 试验 crate，带 `sandbox` feature。

**判断**：把 V8 放进独立进程同时买到两件事——（a）40 MB `.text` + 14.7 MB ICU 数据不进主二进制，（b）不受信任的模型生成 JS 跑在独立进程 + V8 sandbox 里。**代价**：多一个进程、一套 gRPC 协议、一套 proto 生成链，以及 standalone 包里多 69 MB。**未查证**：我没有找到官方对这个拆分的自述理由，上述是从依赖结构与 sandbox feature 推出的判断，不是作者原话。

### 4.3 standalone 包里还塞了什么

`/data/qiwei/.codex/packages/standalone/current/` 实测：

```
bin/codex                    262,858,016 B
bin/codex-code-mode-host      69,431,360 B
codex-path/rg                  5,408,904 B   # ripgrep
codex-resources/bwrap            529,776 B   # bubblewrap（Linux 沙箱）
codex-resources/zsh/             (目录)

```

`codex-package.json` 内容：`{"layoutVersion":1,"version":"0.154.0","target":"x86_64-unknown-linux-musl","variant":"codex","entrypoint":"bin/codex","resourcesDir":"codex-resources","pathDir":"codex-path"}`。

**判断**：`codex-path/` 是注入到子进程 PATH 前面的自带工具目录——ripgrep 被整个打包进来，`bwrap` 同理（对应 PR #21257「release/npm: bundle standalone bwrap on Linux」）。主二进制里 `bubblewrap` 串命中 49 次、`ripgrep` 7 次，说明主程序确实引用它们。

### 4.4 构建体系：cargo / Bazel / Nix 三套并存，分工是明确的

**结论：Bazel 是发布路径，cargo 是开发路径，Nix 只是 dev shell + 一个社区可用的 nix 包。不是三选一的混乱，是三个用途。**

一手证据，`justfile`：

```make
build-for-release:
    bazel build //codex-rs/cli:release_binaries     # ← 发布

codex *args:
    cargo run --bin codex -- {args}                 # ← 日常开发

test *args:
    ... cargo nextest run --no-fail-fast "$@"        # ← 日常测试
bazel-test:
    bazel test --test_tag_filters=-argument-comment-lint //... --keep_going
```

- **Bazel 承担的是 cargo 做不了的部分**：V8 与 LLVM 的 hermetic 构建、Windows `gnullvm`/`msvc` 双 ABI、远程执行（`rbe.bzl`、`--config=clippy`、`--config=argument-comment-lint`）。根 `BUILD.bazel` 里定义了 `local_linux`/`local_windows`/`local_windows_msvc`/`windows_x86_64_gnullvm`/`windows_x86_64_msvc` 五个 platform，还有一条注释暴露了具体痛点：「We mark the local platform as glibc-compatible because musl-built rust cannot dlopen proc macros.」
- **代价是可观测的**：`patches/` 下 **31 个补丁文件**，全是为了让 V8 / abseil / LLVM / libcxx / rules_rust / rules_foreign_cc / ring / jemalloc-sys / zstd-sys / bzip2 / xz 在 Bazel + 各平台下编得过。仓库 `AGENTS.md:37-43` 明写双份维护负担：改 `Cargo.toml`/`Cargo.lock` 必须跑 `just bazel-lock-update` 并把 `MODULE.bazel.lock` 一起提交；加 `include_str!`/`include_bytes!`/`sqlx::migrate!` 必须同步改 `BUILD.bazel` 的 `compile_data`，否则「Bazel may fail even when Cargo passes」。`MODULE.bazel.lock` 本身 1,656,001 字节。
- `AGENTS.md:20` 还写了 lint 的等待成本：「This is powered by Bazel, so running it the first time can be slow if Bazel is not warmed up, though incremental invocations should take <15s.」
- **Nix 的定位由 `flake.nix` 自己声明**：`description = "Development Nix flake for OpenAI Codex CLI"`，提供 `packages.<system>.codex-rs`（`pkgs.callPackage ./codex-rs`，用 `rust-overlay` 的 stable minimal）与一个 devShell。它**不在发布路径上**。

### 4.5 其它代价

- **上游锁定**：三个 `[patch.crates-io]` 分叉（crossterm、tokio-tungstenite、tungstenite）+ 31 个 Bazel 补丁 = 每次上游升级都要重新对齐。ratatui 用了四个 `unstable-*` feature，意味着升 ratatui 会撞 API 破坏。
- **可调试性**：符号被剥离到 sidecar（linux-musl 236.7 MB / windows 464.4 MB），用户端 crash 要拿到对应版本的 symbols 包才能还原。`.debug_gdb_scripts` 段保留。
- **安装面**：官方推荐 `curl … install.sh`（`chatgpt.com/codex/install.sh`），主源 `releases.openai.com/codex`，GitHub Releases 是 fallback（可用 `CODEX_INSTALLER_USE_RELEASES_OPENAI_COM=false` 强制）。npm 与 Homebrew cask 也在。**判断**：主分发不经过 GitHub，版本可追溯性取决于 OpenAI 自己的 CDN。

### 6.2 仓库内确实有一个基准，但它只测 `--help` 的进程启动

`codex-rs/cli/BUILD.bazel:20-23`：


对应源文件 `codex-rs/cli/e2e_benches/codex_help.rs` 全文很短，核心是：

```rust
#[divan::bench(sample_count = 20, sample_size = 1)]
fn codex_help(bencher: Bencher) {
    let codex = codex_utils_cargo_bin::cargo_bin("codex")…;

    });

```

运行方式（`justfile`）：`bench-e2e: bazel test --compilation_mode=opt --cache_test_results=no --test_output=streamed //codex-rs:e2e-benchmarks`。源文件自己的注释原话：「Exercises the Bazel-backed end-to-end benchmark path with a cheap, deterministic Codex invocation.
