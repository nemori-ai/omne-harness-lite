# 架构与延迟：级联 vs 端到端，以及轮次控制

- 原始出处：AssemblyAI、LiveKit、Picovoice、Inworld、Hamming AI、FutureAGI 等厂商技术博客
  @ 2026-09-19 检索（**仅搜索摘要，未逐篇取原文**）；学术与一手证据见下方各条单独标注。
- 消费对象：`research.md` 的「两条架构路线未收敛」「决定体验的是轮次控制」两条结论。
- 来源立场：本节的延迟数字**绝大多数出自销售链路某一环的厂商**，各有有利口径；
  凡有学术或 GitHub 一手证据的条目已单独标注来源。

## 两条路线（厂商口径，未独立验证）

- 级联 STT → LLM → TTS：逐段累加——STT 首个 partial 100–300ms，LLM 首 token 200–600ms，
  TTS 首音 75–300ms，加网络与编排，首音延迟（TTFA）常落在 600–1200ms；
  生产端到端实测常见 **1.5–3 秒**（自用户话音结束到 agent 出声）。
  注意这两组数字出自不同来源，起止点定义是否同口径未经核对。
- 端到端语音到语音（S2S）：模型直接吃音频、吐音频，保留转录会毁掉的信息——
  语调、犹豫、讽刺、笑声、口音、背景环境。
- **没有一方绝对更快**：工程良好的级联可以快过部分端到端模型（TTS 首音 100–250ms）。
- 2026 年**生产仍以级联为主**；S2S 在"延迟主导、工具面浅"的短对话场景增长快。
- 级联的实际优势在可换模型、可观测、成本可控、各段独立升级；端到端优势在副语言信息与栈简单。
- 常用降延迟手法：把 partial 转录提前喂给 LLM，不等用户说完；LLM 没生成完就开始合成。

**OpenAI 的立场（一手·经代理，见 `gpt-live.md`）**：API 发布稿把级联称为
"chained STT–LLM–TTS architectures" 并指其有 "latency and brittle handoffs"——
这是竞争性表述，不是中立比较。

## 轮次控制：决定体验的那一层

**预算（厂商口径）**：自然的 barge-in 要求自用户开口到 TTS 冲掉已缓冲音频**低于 150ms**；
轮次间隙（agent 说完到下一轮首音）200–450ms。

**这个区间的学术出处与它的边界**（详见 `evaluation.md`）：能追溯到的最权威来源是
Stivers et al. 2009 (PNAS)，10 语言自然对话，**总体众数 0ms、中位数 +100ms、均值 +208ms**，
各语言均值落在总体均值 ±250ms 内。**论文从未出现"200–450ms"这个区间或措辞**，
450ms 这个上限在论文数据里没有直接支撑，也没找到任何中间文献做过这个映射。
引用这个区间时应说明它是工程经验口径，不是学术结论。

**四种失败模式**：过早切断、漏切、双讲、打断处理失败。
表现是两头——切太早就抢话，等太久就冷场，而冷场吃的是本来就紧的延迟预算。

**两条相反的技术路线，本轮同时观察到**：

- 厂商博客侧的说法是"2026 年的栈正在从能量阈值 VAD **迁往专门的轮次模型**"，
  把 backchannel／真打断／仍在停顿当作学习到的分类信号。
- 而 OpenAI 工程稿（一手·经代理）走的是反方向：**移除独立的轮次检测器**，
  由语音模型自身控制对话流，理由是"检测器判断太早，用户会被打断；判断太晚，响应感觉迟缓"。
  代价转移到应用侧——应用服务器要"从重叠、偶尔歧义的对话中分离出离散消息"，
  靠部分转录与时序信号推断说话者。
- 两条路线都还没有跨方案的对照实测。

**打断处理要分两层**：媒体层立刻停播，逻辑层取消在途的推理与合成，然后带状态回到监听。
`gpt-live-1` 的实际行为是**打断不自动取消后端工作**（见 `field-reports.md`：
两名开发者分别实测到 30 秒与 2 分钟的委托延迟）。

## 一手证据：轮次控制在真实电话上怎么坏掉

这两条来自 GitHub 与独立贡献者，是本包证据强度最高的工程细节（详见 `field-reports.md`）：

- **8kHz 静默失效**：Pipecat 的 `LocalSmartTurnAnalyzerV3` 曾在 8kHz 下给出错误预测，
  根因是 5 处硬编码 16kHz 假设。**电话线路的标准采样率正是 8kHz**——
  意味着轮次检测可能在电话 agent 上一直误判且不报错。
- **backchannel 被当成打断，且跨语言复现**：LiveKit issue #6033 报告印地语/泰卢固语的
  "haa"、"hmm"、"yeah" 被 VAD 误判为打断（自托管缺少云端的自适应打断模型，只能退回纯 VAD）；
  中文工程博客独立报告"嗯""对""不是"同样触发误判。
  **两条独立非厂商来源指向同一弱点：VAD-only 的轮次检测对 backchannel 密集的语言系统性不友好。**

## 局限

- 本节的延迟区间全部为厂商自述口径，无独立复现，各家对"延迟"起止点的定义未必一致。
- 学术侧没有一个基准报告延迟长尾（p99），全部只报均值——生产关心的尾部完全没有数据（见 `evaluation.md`）。
- 「迁往轮次模型」与「移除检测器」两条路线孰优，本轮没有任何对照证据。
- 中文场景下的轮次控制只有一条个人博客的定性观察，无量化数据。
