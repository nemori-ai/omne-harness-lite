# 资产持有与分层求值：同行有没有先例与反例

PF-002 把资产、设置、权限的分层求值定成了几条具体规则：身份是「类别 ＋ name」、同标识即替代、
引用指向能力标识；禁用按析取（任一层为真即不可见）；一个 `immutable` 标记同时管设置值、权限取值、资产替换；
权限取交集且工作区那一级一概不参与；工作区配的禁用只管它自己提供的那批资产。
本包**只补一件事**：这几条在同代 harness 里有没有同样的做法、有没有反着做的，以及没有先例的部分要付什么。
**不重做横向调研**——「deny 不可被任何层放宽」「仓库不能给自己提权」这两条的四家证据已在
[四个 agent harness 怎么设计「会话」](../agent-harness-session-design/README.md)，本包只引用不复制。

## 准入核对

四个来源的精确版本、取得方式与各自的局限记在[证据记录](evidence.md)。本轮有三处必须随结论一起传下去的限制：

- **Codex 的配置装载器不在本轮副本里**（`codex_config` crate 未入档），项目层禁用键清单、层间合并规则只有文档证据；
  源码只核到 `core/src/config/mod.rs` 里 requirements 对 MCP 的过滤与 `Constrained<T>` 的使用处。
- **Claude Code 本机没有 managed 层也没有项目 settings 文件**，managed 与项目层的行为全部来自
  changelog 与上一轮调研引用的官方文档，不是实测。
- **四家都不是多租户系统**，没有「组织 / 租户 / 工作区」三级；本包把它们的「托管 / 用户 / 项目」
  对到本系统的层时是类比，每条结论写明对的是哪一层。

本家族不拥有方案选择：结论只写到「这条事实让什么变得不可能、什么要额外付出代价」为止。
