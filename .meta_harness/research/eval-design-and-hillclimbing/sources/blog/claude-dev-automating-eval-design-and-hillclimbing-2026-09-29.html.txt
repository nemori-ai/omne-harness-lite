id="automating-eval-design-and-hillclimbing-s0"><p>Evaluations provide a signal on how your app or skill is performing on specific tasks. But designing evaluations, and improving performance on them without fooling yourself, is hard. We&#x27;ve added guidance for both to the <a href="https://github.com/anthropics/skills/tree/main/skills/claude-api">claude-api skill</a>.</p>
<p>With the skill, you can run <code>/claude-api build-eval</code> to build an evaluation inside your codebase, and run <code>/claude-api hillclimb</code> to improve your application against it, one change at a time, with a held-out set of examples to catch overfitting.</p>
<p>In this article, we highlight the principles of good eval design and hillclimbing first, then show how Claude Code with the <code>claude-api</code> skill applies those principles. We’ll close by showing a few examples of these commands.</p>
</section><section class="art-section" data-reveal="" style="--reveal-delay:.1s" id="automating-eval-design-and-hillclimbing-s1"><h2 id="eval-design">EVAL DESIGN</h2>
<p>Well designed evaluations have a few common elements (Figure 1):</p>
<ol>
<li><strong>Eval tasks mirror production.</strong> Sample tasks that you care about in “production,” or the setting in which the capability or application you are testing will be used. Sometimes tasks are picked because they are easy to generate or they are easy to grade. But it’s important to ensure that the task distribution represents what you <em>actually</em> care about.</li>
<li><strong>Performance improves with stronger models and more thinking</strong>. More capable models and higher effort levels typically should perform better on an evaluation. If they don’t, ambiguous tasks or a miscalibrated grader often are hobbling performance.</li>
<li><strong>There is “passable” headroom at the frontier</strong>. The most capable model at the highest effort should be well below 100% on the evaluation, otherwise you can’t reliably judge how changes impact performance. Importantly, the gap should not be explained by impossible or ambiguous tasks: a common tell is that a task fails every evaluation run, regardless of the number of replicates. A good task is one where two domain experts would reach the same verdict and everything the grader checks is stated in the task.</li>
<li><strong>Low run-to-run variance</strong>. High variance is often due to poorly designed, ambiguous tasks or a grader that produces different verdicts on identical output. Variance can also hide in the configuration. For example, effort may not be applied consistently. Also, the environment can affect the results of the evaluation: leftover state from an earlier trial (a file, a git history) can hand the agent the answer.</li>
</ol>

<h3 id="adversarial-sampling">Adversarial sampling</h3>
<p>Model capability is jagged. If you pick cases because today&#x27;s model fails them, you are sampling the valleys of one model&#x27;s capability surface (Figure 2). The evaluation can end up measuring that model&#x27;s failure fingerprint rather than what is intrinsically hard or valuable for your application to do.</p>
<figure class="art-fig"><img class="fg" src="/media/6a014fa959cbc13b3026ca0f2ac1cb8754d541bd07da79bb4c61d81af428024a.png" alt="Two panels plotting capability across task space, each with today’s model as a jagged curve and the next model as a smoother curve above it. On the left, cases sampled where today’s model fails sit only in its valleys; on the right, cases a person judged hard are spread across peaks and valleys, with a few should-not-fire cases." loading="lazy" decoding="async" width="2400" height="960" style="display:block;width:100%;aspect-ratio:2400 / 960"/><figcaption class="cap"><b>FIG 2</b><span>Adversarial sampling</span></figcaption></figure>
<p>Pick hard cases because a human judged them hard: a useful test is to be able to say why a task is hard before you include it. Include cases that are specific failures in your application derived from production traffic, bug reports, or tickets. However, don’t blindly trust user traffic: users sometimes try what they expect to work, so a task distribution drawn strictly from user traffic may skew easy.</p>
</section><section class="art-section" data-reveal="" style="--reveal-delay:.1s" id="automating-eval-design-and-hillclimbing-s2"><h2 id="claude-api-build-eval">/CLAUDE-API BUILD-EVAL</h2>
<p>The <code>build-eval</code> command in the claude-api skill turns these principles into a guided workflow. When you run <code>/claude-api build-eval</code> in Claude Code, Claude interviews you, builds the eval inside your codebase, and pauses for approval at specific points.</p>
<h3 id="designing-examples">Designing examples</h3>
<p>Claude helps you sample inputs to build evaluations in this order:</p>
<ol>
<li>Production transcripts, after asking about retention and sensitive data.</li>
<li>Bug reports and support tickets.</li>
<li>Five to ten cases you write by hand.</li>
<li>Cases synthesized from your codebase.</li>
</ol>
<p>The skill prioritizes production traffic, but it can also generate synthetic data anchored in a few real examples that you provide. The skill instructs Claude to generate a simple page that shows you every input and waits until you confirm them. As an illustration, below we show an example set of inputs for an e-mail router application that the skill may ask the user to review (Figure 3).</p>
<figure class="art-fig"><img class="fg" src="/media/bccc92050c6361924330ef504796ca2c0ce9208d8837356472373f8957b9fdd5.png" alt="The skill’s review page for an inbox-routing eval with 24 inputs, listing each case’s email text with tags such as billing, easy and ambiguous. Beside it, Claude asks in chat whether the inputs are representative, and the user answers yes." loading="lazy" decoding="async" width="2400" height="1384" style="display:block;width:100%;aspect-ratio:2400 / 1384"/><figcaption class="cap"><b>FIG 3</b><span>Example inputs review generated by the skill</span></figcaption></figure>
<h3 id="validating-the-grader">Validating the grader</h3>
<p>After the inputs, Claude proposes the cheapest grader that fits your application’s output:</p>
<ul>
<li><strong>Programmatic verification</strong>: If the output possibilities are constrained, it uses a code based check (exact match, a label from a fixed set, JSON that matches a schema, tests that pass).</li>
<li><strong>LLM-as-judge</strong>: It will default to this type of check if the output space is open-ended, with many valid answers but clear quality criteria. In this case, a second model reads the input, the output and a rubric written as checkable claims (not a 1-to-5 scale), and returns a score with its reasoning. If you have a baseline to compare against, the judge instead reads both inputs in random order, without being told which is the baseline, and picks the better one. You pick the judge model, and it should not be the model you are testing.</li>
</ul>
<p>Claude grades a handful of cases and asks whether you would have scored any of them differently (Figure 4). In general, it is important to <a href="https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents">read a sample of scored transcripts</a> before believing your evaluator; scoring failures are among the most common ways an evaluation is misconfigured.</p>
<p>When you’ve validated the grader, the skill tells you the size of the evaluation set (cases × repeats × model, and roughly how long it will take), runs the baseline, and prints the score with a confidence interval. What you get back: the cases, the grader, the runner, one JSON line and one full transcript per case, and a plain page that lists each case&#x27;s score with a link to its transcript. If you want more than that page shows (e.g., a chart), just ask and Claude will build it as an extra page next to it. By default, these extra pages are static files that open locally and load nothing from the network.</p>
<figure class="art-fig"><img class="fg" src="/media/9c7c2f00ebdd0f9e6b8ad0d3de8cdcc6ebb162c9d2fa5b4f4950ac36b736aef8.png" alt="The skill’s results page for the inbox-routing eval: a baseline scoring 0.681 mean correct across 24 cases, then a table of per-case scores with a link to each repetition. <h3 id="diagnostic-checks">Diagnostic checks</h3>
<p>During the baseline runs mentioned above, Claude checks a number of things:</p>
<ul>
<li><strong>Grader</strong>: Claude runs the grader twice on the same output, and reports whether the verdict changed.</li>
<li><strong>Plumbing</strong>: Claude checks for timeouts, API errors, and cut-off answers to ensure infrastructure noise doesn&#x27;t pass as model variance.</li>
<li><strong>Headroom</strong>: if the baseline already scores about 95% or higher, the skill warns the user and alerts that the hillclimb should aim to explore cost or latency rather than quality.</li>
</ul>
</section><section class="art-section" data-reveal="" style="--reveal-delay:.1s" id="automating-eval-design-and-hillclimbing-s3"><h2 id="hillclimbing">HILLCLIMBING</h2>
<p>Now that you have a reliable means of grading your application’s performance on a task, you can try to improve it. Hillclimbing is an effective way to tune parameters like effort or prompts, which trade-off cost and performance. Some general tips for choosing where to apply it:</p>
<ul>
<li><strong>Cheap iteration</strong> - It should be inexpensive (in terms of time, cost, and effort) to modify whatever surface you are focused on for hillclimbing. Many internal efforts and customers have focused hillclimbing on text, such as prompts and skills. These are easy to change and revert. In contrast, open-ended modifications to an agent harness during hillclimbing may involve extensive code changes.</li>
<li><strong>Attributable</strong> - Changes in the score on your evaluation should be attributable to the surface you are modifying during hillclimbing. For example, several successful applications of hillclimbing have focused on skill triggering. The evaluation metric (the trigger rate for the skill) is directly coupled to the skill description that is being modified.</li>
<li><strong>Well-scoped objective</strong> - One common failure mode is an open-ended request to improve performance without careful consideration of the headroom available in the evaluation; an evaluation that’s near saturation or a poorly scoped surface (e.g., an open-ended request to update the harness) is more likely to stall. One generally strong objective across various efforts is cost: even if an evaluation is saturated, you can ask Claude to <a href="https://claude.com/blog/reducing-cost-and-improving-performance-with-claude-platform">find ways to reduce cost</a> while keeping performance at parity.</li>
</ul>
<h3 id="overfitting">Overfitting</h3>
<p>Even a well-designed evaluation rarely matches the exact task distribution you care about in production. As a result, &quot;overfitting&quot; to an evaluation is a common problem and results in a system that performs better on an evaluation than on production traffic.</p>
<p>There are many ways an evaluation can &quot;leak&quot; into your harness (the code around the model, including prompts, tools, and loop that calls Claude). For example, consider an evaluation task that benefits from OCR, but OCR is rarely beneficial in your production tasks. The evaluation harness might add an OCR tool to your application, which improves on the benchmark without any impact on production. More broadly, hillclimbing may add features to that harness that address edge cases in the particular evaluation examples you’ve chosen. These harness additions improve your evaluation score, but don’t translate to improvements in production (Figure 5).</p>
<figure class="art-fig"><img class="fg" src="/media/a328a3f4d5bfd0967174ef2ca79bc8f094d8db3c12af71be3189891bf40d0e53.png" alt="The benchmark’s traits on the left, each shaping a matching addition to the harness on the right: a task mix that needs OCR adds an OCR tool, tasks in /app add “always cd /app, run pytest”, distinctive phrasings get a tuned prompt, and failures you’ve read get one patch each. A dashed arrow marks the outright leak: a public repo with answers lets the harness curl the reference solution." loading="lazy" decoding="async" width="2400" height="1080" style="display:block;width:100%;aspect-ratio:2400 / 1080"/><figcaption class="cap"><b>FIG 5</b><span>Common causes of harness overfitting.</span></figcaption></figure>
<p>Three things can help address this:</p>
<ul>
<li><strong>Split the cases</strong>. Use a train set that the hillclimber may read and a test set that is never seen. If the train set scores improve while the test set scores stay flat, then that is a common overfitting warning sign.</li>
<li><strong>Never paste failures into the prompt</strong>. If the hillclimber reads the failing transcripts, it should never paste the failure content into the prompt.</li>
<li><strong>Keep the answers structurally out of the model&#x27;s reach</strong>. Models can sometimes “reward hack” by directly finding answers to evaluations.</li>
</ul>
<p>As discussed below, the claude-api skill applies these principles for you.</p>
</section><section class="art-section" data-reveal="" style="--reveal-delay:.1s" id="automating-eval-design-and-hillclimbing-s4"><h2 id="claude-api-hillclimb">/CLAUDE-API HILLCLIMB</h2>
<p>The hillclimb command in the claude-api skill turns these principles into a guided workflow. When you run <code>/claude-api hillclimb</code> in Claude Code, Claude iterates to improve against a given evaluation. You choose what changes it can make including:</p>
<ul>
<li>Your system prompt</li>
<li>Skills or instruction files</li>
<li>Tool descriptions</li>
<li>Model choice, effort level, and other API parameters</li>
<li>Your harness code</li>
</ul>
<p>Before it starts, Claude asks what you want to optimize (e.g., performance, or cost while performance holds) and then splits the evaluation set at random into test and train. With a cost goal, it considers <a href="https://claude.com/blog/reducing-cost-and-improving-performance-with-claude-platform">a few common cost drivers</a>, including prompt caching, auditing the prompt for compatibility with the selected model, and picking the model and effort setting.</p>
<p>Before the first round, Claude checks that the eval&#x27;s noise (how far the score can move by chance alone) is smaller than the smallest improvement you&#x27;d act on; if it isn&#x27;t, it says so and suggests more repetitions or cases.</p>
<p>Each round, Claude reads the previous round’s train transcripts and proposes one change as a patch. It aims each round at a change whose effect can show above the eval&#x27;s noise: it fixes the failing behavior at its root (e.g., rewrites the section that causes it or adds a missing rule) rather than rewording a line. It then runs evaluation with the patched change. At this point, Claude applies a check: if the <code>train</code> set improves but the <code>test</code> set is flat, Claude suspects overfitting and reverts the patch. If there is a regression, Claude reverts. If train and test sets improve, it keeps the patch (Figure 6).</p>
<figure class="art-fig"><img class="fg" src="/media/dafbc5fb0edf5aeed96af8984ec09f6a0f8ebd753274c305ccf3043e1640d75a.png" alt="The hillclimbing loop: the thing being edited, such as a prompt, feeds a fixed model and harness that is scored on a held-out test split and a train split. An analyzer reads only the train failures and proposes one diff per round; the diff is kept when train and test both rise, and reverted when only train rises or either score drops." loading="lazy" decoding="async" width="2400" height="1320" style="display:block;width:100%;aspect-ratio:2400 / 1320"/><figcaption class="cap"><b>FIG 6</b><span>The process used by the hillclimber.</span></figcaption></figure>
<p>When the score stalls for two or three rounds, Claude reads each remaining train failure and sorts it by cause. It does the same early if no single fix could gain more than the eval&#x27;s noise, and suggests more repetitions or cases, rather than spending rounds on changes too small to measure. This step can catch ambiguous evaluation cases, harness errors, or run-to-run variance.</p>
<p>Only legitimate failures are included in more hillclimbing rounds.</p>
<p>When hillclimbing completes, Claude leaves your code at the version that did best on the test set for your goal. It reports the test result against the baseline with confidence intervals (Figure 7). If the gain is within noise, it says so and recommends against merging.</p>
<figure class="art-fig"><img class="fg" src="/media/8c9b0ffdf9d75df81ec451ccb55feb091693fb7eb88ad9c20f3911387e3ec4e1.png" alt="The inbox-routing results page after hillclimbing, comparing three variants on train and test scores. </section><section class="art-section" data-reveal="" style="--reveal-delay:.1s" id="automating-eval-design-and-hillclimbing-s5"><h2 id="examples">EXAMPLES</h2>
<h3 id="hillclimbing-for-cost-reduction">Hillclimbing for cost reduction</h3>
<p>We ran <code>/claude-api hillclimb</code> on an <a href="https://claude.com/blog/reducing-cost-and-improving-performance-with-claude-platform">internal customer support benchmark</a> with the goal of reducing cost and improving performance. The benchmark included 44 tickets, with 30 used for the search and 14 held out. It started on Opus 4.8 at default (high) effort settings with 74.4% decision accuracy on the search tickets and a token cost of 4.6 cents per ticket.</p>
<p>The hillclimb first audited the prompt, <a href="https://claude.com/blog/reducing-cost-and-improving-performance-with-claude-platform">removing</a> mandatory tool-call rituals, a scratchpad step, and contradictory rules. Then it tried Opus 5.5 on low effort. This cleared the baseline accuracy bar at 87.8% and cut cost to 1.9 cents per ticket, less than half the starting cost.</p>
<p>Part of that saving comes from <a href="https://claude.dev/blog/getting-the-most-out-of-opus-5-5/">Opus 5.5&#x27;s pricing</a>: input and output tokens cost 20% less than on Opus 4.8, and cache reads cost 60% less. Because Opus 5.5 cleared the bar, the hillclimb then stepped down a tier to check whether a cheaper model could clear it too. Sonnet 5 on low effort scored about the same, 88.9%, at about half the cost, 1 cent per ticket (Figure 8).</p>
<figure class="art-fig"><img class="fg" src="/media/30294a004560ab4b287482ef536a7fdacb9af75c3599e2a5174db8522c189f5e.png" alt="Decision accuracy on the train split against cost per ticket, tracing the adopted path: from the Opus 4.8 high-effort baseline at 74.4% and just over 4¢, to Opus 5.5 at low effort, to Sonnet 5 at low effort near 1¢, and finally Sonnet 5 with an improved prompt near 100%." loading="lazy" decoding="async" width="2088" height="1436" style="display:block;width:100%;aspect-ratio:2088 / 1436"/><figcaption class="cap"><b>FIG 8</b><span>Cost-focused hillclimbing.</span></figcaption></figure>
<p>Finally, Claude improved the prompt with routing rules and a refund-cap cross-reference, bringing Sonnet 5 to 98.9% at about the same cost. On the 14 held-out tickets that the search never saw, the final configuration scored 90.5% against the original setup&#x27;s 78.6%, at about one fifth of the cost.</p>
<h3 id="hillclimbing-for-performance-improvement">Hillclimbing for performance improvement</h3>
<p>Another example is our <a href="https://github.com/anthropics/skills/tree/main/skills/claude-api">claude-api</a> skill, which provides guidance on using our APIs and general tips for working with Claude (including the sub-commands discussed in this article). We want to ensure our skill can correctly implement code that uses our APIs, and we built an evaluation set derived from our documentation to test the skill.</p>
<p>On our evaluation, the skill started at 66%. We gave the hillclimber access to documentation and our SDKs, allowing Claude to identify errors and self-correct them (Figure 9). Claude found that the skill was missing coverage of eight features.</p>
<p>Adding sections for them in the skill improved performance to 74%. It then found errors in C# and Java type tables, boosting performance to 77%.</p>
<figure class="art-fig"><img class="fg" src="/media/5a2d1629b9d790991737608384accbb5b175bbb147c569dc26b54fd603ef5ac2.png" alt="Pass rate across hillclimbing rounds on the claude-api skill’s eval, rising from 66.1% at baseline to 87.9% at round 24. Shaded phases mark the work: adding missing sections and type tables, then fixing how the skill tells Claude to write code, then fixing graders plus more skill edits." loading="lazy" decoding="async" width="2400" height="1440" style="display:block;width:100%;aspect-ratio:2400 / 1440"/><figcaption class="cap"><b>FIG 9</b><span>Performance-focused hillclimbing.</span></figcaption></figure>
<p>After the score stalled for two rounds, Claude analyzed the remaining failures and bucketed them by root-cause. A normal round makes one edit for the most common failure. This step makes no edit; it only sorts every remaining failure by cause. This reflection step was useful in a few ways:</p>
<ul>
<li>Reflecting across a collection of failures, the hillclimber found that the skill content was present but Claude was simply writing older API shapes (e.g., from its trained priors). To address, the hillclimber added a table near the top of the skill that guided Claude from the forms it remembered to the current ones: for example, from extended thinking with a fixed token budget, which the API now rejects on recent Opus models, to adaptive thinking, and from older versions of the web search and web fetch tools to the current ones. It also moved the C# and Java warnings against fixed-budget thinking above their adaptive-thinking examples. This improved performance to 80%.</li>
<li>Tasks that never improved in performance despite addressing obvious content gaps are tells that the example or grader is flawed. One task asked for code that catches one error type, while its grader wanted a chain of at least three. Claude reworded the task. Another grader&#x27;s instructions contradicted our docs, and testing the real API showed the docs were right. Addressing these, along with more skill edits, brought performance to ~88%.</li>
</ul>
</section><section class="art-section" data-reveal="" style="--reveal-delay:.1s" id="automating-eval-design-and-hillclimbing-s6"><h2 id="getting-started">GETTING STARTED</h2>
<p>These sub-commands can be used directly in Claude Code via the <a href="https://github.com/anthropics/skills/tree/main/skills/claude-api">claude-api skill</a>:</p>
<p>Run <code>/claude-api build-eval</code> if you want to generate an evaluation set for a particular problem. You can steer it by providing access to examples (e.g., traces). Claude will employ the guidance shared in this article to design the examples and grader, and ensure you approve the examples and the grader.</p>
<p>Run <code>/claude-api hillclimb</code> if you have an evaluation and want Claude to improve on this, guided by your goal (e.g., better performance, or lower cost while performance holds). Claude will employ the guidance shared in this article to check for overfitting while climbing and check for bugs in the eval itself, such as a grader that marks a correct-looking answer wrong or a harness error, both before the first round and whenever the score stalls.</p>
