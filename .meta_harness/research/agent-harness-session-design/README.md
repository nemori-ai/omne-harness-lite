# 四个 agent harness 怎么设计「会话」

同代的四个 agent harness——DeepSeek Harness、Claude Code、Codex、Pi——各自把「一段持续协作」
建模成了什么，在**数据存储、权限治理、上下文感知域、生命周期控制**四个方面做了什么取舍，
以及各自明确声明**不做**什么。

这项调查要区分的是：**哪些做法四家一致**（那是这一代 harness 的事实基线，另做一种选择要额外举证），
**哪些四家分歧**（那才是真的取舍空间），以及**哪些问题四家都没解决**。

- **调查对象与基线**：DSH `c291e796` / `0.1.5-rc.2`；Claude Code `2.1.278`；
  Codex CLI `0.154.0` + 源码 `5c5308fc9a`；Pi `3390bd9`。全部为 2026-09-20 当日取证。
- **消费者**：`design/product` 的 PF-015（会话的生命周期与归属，产品设计进行中）是已知的第一个；
  其中涉及 Cordis 与上游机制形态的事实（DSH 的 session 不是 Service、scope 的注册可见性、
  permission 交集的实现形态）预期会被后续的架构与规格设计继续消费，**那些消费者此刻尚未出现**。
- **最近核对**：2026-09-20（首轮）。

## 准入核对

四家的精确版本、取证方式与各自的局限，全部记在 [证据记录](evidence.md)，**取证条件与结论不写在同一页**。
本轮有三处必须随结论一起传下去的限制：

- **四家都不是多租户系统**，本轮证据**不能支持**任何关于租户隔离下会话该怎么做的结论。
- **DSH 的 `agent-scope` 有一处上游文档自身的口径冲突**（两层扁平 vs 父链继承），
  调研方给的是推断且标注未查证——**自行核对源码之前不要引用那一条**。
- **Pi 仓库里有两套并存的会话模型**，新一代 `AgentHarness` **是规格不是现状**，引用时必须标明。

本家族不拥有方案选择：结论只写到「这条事实让什么变得不可能、什么要额外付出代价」为止。
