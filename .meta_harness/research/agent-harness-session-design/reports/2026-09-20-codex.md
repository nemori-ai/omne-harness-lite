# 0. 对象确认

## 结论

**Codex 有三个不同层次的名字，且当前正处在一次未收口的改名中途：**

| 层 | 名字 | 是什么 | 适用面 |
|---|---|---|---|
| 用户面 | **chat**（旧称 task，更早 thread） | 「一段可保存的协作空间」 | 全 surface |
| 技术对象 | **thread** | 装 turn 和历史的持久对象，有 id、rollout 文件、状态 | **app-server / SDK / 本地存储** |
| **归属边界** | **session** | **一棵活的 thread 树的根** | 本地 |
| 意图 | **task** | 「一个要达成的结果」；在 cloud 侧同时也是 REST/CLI 的对象名 | 全 surface / Cloud |
| 落盘文件 | **rollout** | thread 的 append-only JSONL 日志 | 本地 |

## 承担「一段持续协作的身份与归属边界」的是谁

**是 `session`，但它不是一个存储对象，而是 thread 树的根 id。** 这是本次调研最关键的发现。

【读到的】`docs/app-server.md`「Start or resume a thread」节，**逐字**：

> `thread.sessionId` identifies the current **live session tree root**. Root threads use their own thread id as the session id; forked threads keep the session id of the root they came from. Clients should read the session id from `thread.sessionId` instead of deriving it from the thread id.

【实测的】本机 rollout 的 `session_meta` 完全印证这一点。一个 subagent thread 的头部记录：

```json
{"type":"session_meta","payload":{
  "session_id":"01a0a4f4-7af6-70e1-b2a2-c0ba97937cb5",   // ← 树根
  "id":"01a0a78a-a599-7da0-ada6-b1532b9af501",            // ← 本 thread（= 文件名里的 UUID）
  "forked_from_id":"01a0a4f4-...",
  "parent_thread_id":"01a0a4f4-...",
  "thread_source":"subagent",
  "source":{"subagent":{"thread_spawn":{
     "parent_thread_id":"01a0a4f4-...","depth":1,
     "agent_path":"/root/s_capability_slice",
     "agent_nickname":"Heisenberg","agent_role":"capability-developer"}}},
  "agent_path":"/root/s_capability_slice",
  "history_mode":"paginated",
  "subagent_history_start_ordinal":17,
  "multi_agent_version":"v2",
  "context_window":{"window_id":"01a0a78a-a599-7da0-ada6-b1647a977546"},
  "cli_version":"0.154.0","originator":"codex-tui",
  "cwd":"/data/qiwei/repos/omne-harness-lite",
  "git":{"commit_hash":"55ac071...","branch":"main"},
  "base_instructions":{"text":"<20919 字符的完整 system prompt>",
                       "provenance":{"type":"model","model":"gpt-6-astra"}}
}}
```

一棵树里**所有 subagent thread 共享同一个 `session_id`**，各自有独立 `id` 和独立 rollout 文件。`agent_path` 是树内路径（`/root`、`/root/s_capability_slice`），不是文件路径。

注意这里还有第四个身份对象：**`context_window.window_id`** —— 上下文窗口是与 thread **分开编号**的独立对象。

## glossary 原文（`docs/glossary.md`，2026-09-20 抓取）

| key | appliesTo | description 逐字 |
|---|---|---|
| **Chat** | Desktop app, Web, Mobile, CLI, IDE extension, Cloud | "A saved space for exchanging messages with ChatGPT or Codex, including shared context, results, and actions." |
| **Thread** | **App-server, SDK** | "A technical object in Codex app-server APIs that contains turns and stored conversation history." |
| **Turn** | 全 + SDK | "One exchange in a chat, usually a user prompt plus the agent's response and actions." |
| **Task** | 全 + Cloud | "A defined outcome ChatGPT or Codex works toward, such as fixing a bug, creating a document, or researching a topic." |
| **Thread fork** | App-server, SDK | "New thread branched from the stored history of an existing thread." |
| **Ephemeral session** | **CLI** | "Non-interactive run that skips saving session state after it completes." |
| **Cloud chat** | Cloud | "A Codex chat that runs remotely in a cloud environment." |
| **Subagent** | Desktop app, CLI | "Specialized child agent spawned to work on part of a task." |

**glossary 里没有独立的 "Session" 词条**（只有 "Ephemeral session"，且 `appliesTo` 限定为 CLI），**也没有 "Workspace" 词条**。「session」这个词现在主要活在 CLI 命令参数（`codex resume <SESSION_ID>`）、目录名（`~/.codex/sessions/`）和落盘字段（`session_meta` / `session_id`）里 —— 即**遗留层**。

## 改名的硬证据

【读到的】`.md` 页为防外链断裂保留了旧锚点，这是改名化石：

- `docs/environments/cloud-environment.md:9`：`<a id="how-codex-cloud-tasks-run"></a>` 紧跟 heading `## How Codex cloud chats run` → **tasks → chats**
- `docs/environments/git-worktrees.md`：`<a id="option-2-handing-a-thread-off-to-local">` / `...-a-task-off-...` / `...-a-chat-off-...` **三个锚点并列**，heading 是 chat 版 → **thread → task → chat 两轮改名**
- `docs/automations.md`：`thread-automations` / `scheduled-tasks-in-threads` / `scheduled-tasks-in-chats` / `schedule-a-task-inside-a-chat` 四连锚点
- 反向证据：CLI 全线仍叫 task/session。`codex cloud --help` = "Browse **tasks** from Codex Cloud"；`codex resume [SESSION_ID]`；`codex archive <SESSION>`。

## 本地 vs 云端是否一致

**不一致，而且是两套不相连的对象模型。**

- 本地：`thread`（app-server 一等对象）+ `session`（树根）+ `rollout`（落盘）。
- 云端：对外只有 **`task`**，字段为 `id / url / title / status / updated_at / environment_id / environment_label / summary / is_review / attempt_total`（`codex cloud list --json` schema，子 agent 实测顶层 key 确为 `{"tasks":[...], "cursor":...}`）。
- **`docs/app-server.md` 全文 grep "cloud" 零命中**；glossary 把 `Thread` 的 `appliesTo` 限定为 "App-server, SDK"，不含 Cloud。→【推断】**cloud 侧根本没对外暴露 thread 对象**。
- cloud 独有结构：一个 task 下挂 **1–4 个并列 `attempt`**（best-of-N，`--attempts <1-4>`，`codex cloud apply --attempt <N>` 1-based）。本地没有这个概念。

## 取舍分析

- **选了「thread 是对象、session 是树根」而不是「session 是对象」**。代价：`session` 没有独立持久化实体，没有自己的生命周期、状态、配额；它只是一个在每个 thread 的 meta 里冗余记录的 id。好处：subagent 树天然可归属、可级联归档/删除、可按 `ancestorThreadId` 查询，而不需要额外的聚合根表。
- **代价二：命名债**。同一事物在 UI 叫 chat、在 API 叫 thread、在 CLI 叫 session、在 cloud 叫 task、在磁盘叫 rollout。文档里五个词并存且锚点层层叠加，这是持续快速迭代 + 不愿破坏外链的直接后果。
- **代价三：本地/云端概念分叉**。cloud 没有 thread/turn/item 原语暴露，导致「把云端会话接力回本地」只能搬 diff（见 §4）。

# 1. 数据存储

## 结论

Codex 本地是**「append-only JSONL 为真相源 + SQLite 为只读投影」的双层存储**，且投影严格是日志的前向尾读者。落盘无任何保留期与清理策略。

## 1.1 布局与格式

【实测的】`~/.codex/` 实际结构（v0.154.0）：

```
~/.codex/
├── sessions/YYYY/MM/DD/rollout-<ISO8601>-<thread_uuid>.jsonl   ← 真相源，7.1 GB / 1671 文件
├── archived_sessions/                     ← 归档目标（文档写明；本机无归档故不存在）
├── thread_history_1.sqlite   1.7 GB       ← rollout 的分页投影
├── state_5.sqlite            13 MB        ← thread 元数据 / 树边 / 项目 / 迁移状态
├── logs_2.sqlite             1.9 GB       ← 结构化运行日志（298573 行）
├── goals_1.sqlite            48 KB        ← Goal 模式的目标与预算
├── queue_1.sqlite            28 KB        ← `codex queue` 排队消息
├── memories_1.sqlite         40 KB        ← 跨会话记忆抽取作业
├── history.jsonl             600 KB       ← 跨会话的「用户输入历史」
├── session_index.jsonl       15 KB        ← {id, thread_name, updated_at} 轻索引
├── config.toml / auth.json / rules/ / skills/ / prompts/ / plugins/
├── .tmp/rollout-maintenance.lock          ← 存在 rollout 维护进程
└── app-server-daemon/{app-server.pid, app-server.stderr.log}
```

文件名格式实测：`rollout-2026-09-16T13-03-54-01a0aa51-100b-76f1-951c-ce2b2f0953a2.jsonl`，UUID 是 **UUIDv7**（`01a0aa51-100b-7...`，时间有序，版本位 7）。

## 1.2 记录单位与字段结构

【实测的】对本机 2026-09-16 的 228 个 rollout 全量统计，**顶层行类型共 8 种**：

| `type` | 计数 | 承载什么 |
|---|---|---|
| `event_msg` | 12269 | UI/运行事件（`item_completed` 8411、`token_count` 3495、`task_started` 158、`task_complete` 140、`thread_settings_applied` 64、`turn_aborted` 1） |
| `response_item` | 10989 | 送给模型 / 模型返回的原始 Responses API item |
| `token_usage_record` | 3426 | 三层 token 归属（见 §5） |
| `world_state` | 329 | **感知域快照/增量**（见 §3） |
| `inter_agent_communication_metadata` | 267 | agent 间通信标记 |
| `turn_context` | 220 | **每轮的治理状态快照**（见 §2） |
| `session_meta` | 73 | 会话/线程身份头 |
| `compacted` | 62 | 压缩替换记录 |

每行统一有 `timestamp` + **`ordinal`**（单调递增序号）+ `type` + `payload`。

`response_item.payload.type` 的取值（实测）：`reasoning`(3455) / `custom_tool_call`(2917) / `custom_tool_call_output`(2917) / `message`(711) / `function_call`(361) / `function_call_output`(361) / `agent_message`(267)。

**各类内容怎么表示**：
- **消息**：`{type:"message", id:"msg_<uuidv7>", role, content:[{type:"input_text",text}], internal_chat_message_metadata_passthrough:{turn_id, create_time, content_item_kinds}}`。
- **reasoning**：**`{type:"reasoning", id:"rs_...", summary:[], encrypted_content:"gAAAAAB..."}`** —— 推理内容以**不透明加密串**落盘（Fernet 风格），本地不可读，作用是能原样回传给 API。
- **工具调用**：`custom_tool_call` 的 `input` 是一段 **JS 代码字符串**（Code Mode）：
  `const r = await tools.exec_command({cmd:"...", workdir:"...", yield_time_ms:10000, max_output_tokens:30000}); text(r.output);`
- **工具结果**：`custom_tool_call_output.output` 是 content item 数组，首项是 `"Script completed\nWall time 0.4 seconds\nOutput:\n"`，次项是实际输出。
- **agent 间消息**：`{type:"agent_message", author:"/root", recipient:"/root/s_capability_slice", content:[{type:"input_text",...},{type:"encrypted_content", encrypted_content:"gAAAAAB..."}]}` —— **agent 间的 payload 同样加密**。

## 1.3 什么时候落盘 / 是不是 append-only

【实测的】**这是本次最干净的一条证据。** `thread_history_1.sqlite` 有一张表：

```sql
CREATE TABLE thread_history_projection_state (
    thread_id TEXT PRIMARY KEY,
    next_rollout_byte_offset INTEGER NOT NULL,
    next_rollout_ordinal INTEGER NOT NULL
)
```

我对全部 **1671** 个有 rollout 文件的 thread 做了校验：**`next_rollout_byte_offset == 文件实际字节数` 的有 1671 个，不匹配 0 个。**

→ 这**证明**：(a) JSONL 是**严格 append-only**，只在尾部增长；(b) SQLite 是一个**纯前向的尾读投影器**，靠记录 byte offset + ordinal 增量消费，从不回读或重写；(c) 真相源是 JSONL，SQLite 可以随时从 JSONL 重建。

另一条佐证：`thread_items` 主键是 `(thread_id, turn_id, item_id)`，带 `updated_at_ordinal` 允许 upsert；但实测 **`updated_at_ordinal <> rollout_ordinal` 的行数 = 0 / 301164**，即本机语料里从未发生过投影覆写。

`thread_turns` 则是对 rollout 的**字节区间索引**：

```sql
CREATE TABLE thread_turns (thread_id, turn_id, rollout_ordinal, status, error_json,
  started_at, completed_at, duration_ms, first_user_item_id, final_agent_item_id,
  rollout_byte_offset, rollout_end_ordinal, rollout_end_byte_offset, ...)
```
这就是 `thread/turns/list` 分页的物理基础 —— 按 turn 定位 JSONL 的 `[offset, end_offset)` 区间。

**落盘时机**【推断】：`ordinal` 连续、投影 offset 恰好等于文件尾、且 `thread_turns` 有 `inProgress` 状态残留，说明是**逐条写入并立即 flush**，而非 turn 结束批量写。但我没有通过运行 Codex 直接观测写入时序 —— 这一条是推断。

## 1.4 压缩/截断时对已有记录做什么

【实测的】**压缩不删除任何历史，它追加一条替换指令。**

```json
{"ordinal":2,"type":"compacted","payload":{
   "message":"",
   "replacement_history":[ ...完整的一串 response_item... ]}}
```
本机实测单条 `compacted` 记录最大 **506309 字节**，内含整段被保留的 user 消息序列。语义是：**模型可见历史（in-context）被替换成 `replacement_history`，但磁盘上原始历史仍在前面的行里，一字未动。**

投影侧对应一个极简的 `contextCompaction` 标记：`{"type":"contextCompaction","id":"<uuid>"}` —— 即压缩在索引层只留一个事件点，重建细节要回 JSONL。

相关配置【读到的】：`model_auto_compact_token_limit`（触发阈值）、`model_auto_compact_token_limit_scope`（`total`（默认）/ `body_after_prefix`，控制阈值是算全量上下文还是只算压缩前缀之后的增量）、`compact_prompt` / `experimental_compact_prompt_file`（压缩提示词覆盖）。

**另一条**：`thread/rollback`（已废弃）—— 【读到的】"It removes the last `numTurns` entries from the **in-memory context** and **persists a rollback marker in the rollout log**." 同样是「内存回退 + 日志追加标记」，不改历史。

## 1.5 大对象怎么存

【实测的】**全部内联，没有外部 blob 存储，没有去重。**

| 对象 | 存法 | 实测数据 |
|---|---|---|
| 长命令输出 | **按 token 截断后内联** | 原文里能看到 `"Warning: truncated output (original token count: 28835)\nTotal output lines: 3323"`；调用侧 `max_output_tokens:30000`。**存的是模型看到的截断版，不是原文** |
| 文件改动 diff | **完整 diff 文本内联** | `fileChange.item_json` 最大 **425403** 字节 |
| 图片 | **base64 data URI 内联进 JSONL** | `{"type":"input_image","image_url":"data:image/png;base64,iVBORw0KGgo..."}` |
| 已查看的本地图片 | 只存路径 | `{"type":"imageView","id":"exec-...","path":"/tmp/omne-gateway-preview.../desktop.png"}` |
| reasoning | 加密串内联 | 见上 |

`item_json` 长度极值（实测）：`commandExecution` max **1653330** 字节（1.65 MB 单条）、`mcpToolCall` max 185703、`fileChange` max 425403。

相关配置【读到的】：`tool_output_token_limit`（"Token budget for storing individual tool/function outputs in history"）、`mcp_servers.<id>.tools.<tool>.output_token_limit`（单工具覆盖，"before the standard 20% serialization allowance"）。

## 1.6 会话结束后怎么处理 / 清理策略

**结论：没有清理策略。** 这是 Codex 会话存储最明显的取舍。

【读到的】唯一的容量控制是 `history.max_bytes`，而它**只管 `history.jsonl`**（跨会话的用户输入行，`{session_id, ts, text}`）：
> "By default, Codex saves local session transcripts under `CODEX_HOME` (for example, `~/.codex/history.jsonl`). To disable local history persistence: `[history] persistence = "none"`。To cap the history file size, set `history.max_bytes`."

我在 `config-reference.md` / `config-advanced.md` / 2.34 MB 的 `codex-manual.md` 全文 grep 过 `retention|prune|cleanup|max_age|expire|garbage`，**对 `sessions/` 的 rollout 零命中**。

【实测的】代价的量级：**本机 ~/.codex 总计 12 GB**（约 3 个月使用），其中
- `sessions/` **7.1 GB**（1671 文件），最大单个 rollout **280.8 MB**
- `thread_history_1.sqlite` **1.7 GB**（同一份内容的第二副本）
- `logs_2.sqlite` **1.9 GB**
- 对比 `history.jsonl` 只有 600 KB —— 唯一被限额管着的，恰好是最小的那个。

**手动清理的三个动作**【读到的】：
- `codex archive <SESSION>` / `thread/archive` → 「move the persisted thread log into the **archived sessions directory**」（`$CODEX_HOME/archived_sessions`），**并级联归档 spawned descendant**。`/archive` 在任务运行中不可用。
- `codex delete <SESSION>` / `thread/delete` → 「permanently delete ... **and its spawned descendant threads**」。`--force` 只对 UUID 生效，具名 session 仍需确认。**"Ephemeral root threads can't be deleted."**
- `codex unarchive` / `thread/unarchive` → 把 rollout 移回 active 目录。
- `codex exec --ephemeral` → 「Run without persisting session files to disk」。

## 1.7 云端存储

【读到的】`docs/enterprise/chatgpt-work-cloud-security.md`，**逐字**：

> "Work Cloud runs on **shared, OpenAI-managed infrastructure**. In the current supported execution path, tasks run in **VM-backed sandboxes**, with **execution state associated with the authenticated account user in the workspace**. Work can **reuse an environment across tasks or replace it while preserving eligible state**. This doesn't mean every task receives a new container or that each customer has a dedicated physical host."

保留矩阵（原表，节选逐字）：

| 类别 | 保留行为 |
|---|---|
| Work conversations | "**Deleted chats are generally scheduled for permanent deletion within 30 days**" |
| **Hosted execution state and snapshots** | "**Follow a separate lifecycle from conversations and files.** ... **Ending a task or deleting a chat doesn't immediately purge every related artifact.**" |
| Files saved to Library | "**Deleting a conversation doesn't delete a file saved to Library.**" |
| Saved memories | "Deleting a conversation doesn't necessarily delete an existing saved memory." |
| Transient uploads | "can expire after **48 hours**" |
| Compliance records | "**Compliance Logs Platform records are available for 30 days.**" |

容器状态缓存【读到的】：「Codex caches container state for **up to 12 hours**」；失效条件是改 setup/maintenance script、env vars 或 secrets；**「For Business and Enterprise users, caches are shared across all users who have access to the environment.」**

## 取舍分析

- **选了「append-only 日志 + 可重建投影」**。收益：任何时刻的历史都可复现，压缩/回滚都不破坏证据，崩溃后投影可从 offset 续读。代价：**磁盘无上界**，且同一份内容存两遍（JSONL 7.1 GB + SQLite 1.7 GB）。
- **选了「存模型看到的，而不是存原始的」**（截断后的工具输出落盘）。收益：rollout 能精确重放模型上下文。代价：**日志不能当审计用** —— 被截掉的 28835 token 的原始输出永久丢失，你无法从 rollout 还原命令真正输出了什么。
- **选了「大对象内联」**。收益：单文件自包含、可整体拷贝/归档/上传做 bug report。代价：单个 rollout 280 MB，base64 图片使体积膨胀 33%，无去重。
- **选了「不做保留策略」**。这不像是疏忽 —— `history.max_bytes` 证明他们知道怎么做限额，只是**刻意没给 rollout 上限额**，因为 rollout 现在还兼任 memories 抽取的输入（`memories.max_rollout_age_days` 默认 30、`memories.max_rollouts_per_startup` 默认 16）、auto-review 事后分析的语料（文档原话：「Auto-review session transcripts are retained under `~/.codex/sessions` by default, so you can ask Codex to analyze past traffic there before changing policy」）。**代价直接落在用户磁盘上。**
- **云端选了「执行状态与会话分离生命周期」**，并明说「删 chat 不等于清执行产物」。这是诚实的，但也意味着**没有单一删除入口**。

# 2. 权限治理

## 2.0 结论摘要

1. **审批（approval）与沙箱（sandbox）是两个正交维度**，文档反复明写。近期又加了**第三个正交维度：谁来审批（`approvals_reviewer`）**。
2. 审批策略在 v0.154.0 只剩 **`on-request` / `never` / `{granular = {...}}`** 三种；`untrusted` 已**移除**，`on-failure` 已废弃。老的 suggest/auto-edit/full-auto 三档在 CLI 层已不存在（`--full-auto` 只作为 deprecated 兼容路径保留并打警告）。
3. 沙箱有两套并存且**互斥**的表达：老的 `sandbox_mode`（read-only / workspace-write / danger-full-access）与新的 **permission profiles**（beta）。
4. **网络是独立维度**，而且被拆成「是否有网」与「有网后是否被代理管」两个相互独立的开关。
5. 治理分 7 层，其中 `requirements.toml` 是**用户不可突破的上界**，但它**只管本地，完全管不到 Codex cloud**。

## 2.1 审批模式（approval mode）

【读到的，v0.154.0 `codex --help` 原文】：

```
-a, --ask-for-approval <APPROVAL_POLICY>
      Configure when the model requires human approval before executing a command
      Possible values:
      - on-request: The model decides when to ask the user for approval
      - never:      Never ask for user approval Execution failures are immediately
                    returned to the model
    --approve-for-me
      Route approval requests through automatic review using the workspace-write sandbox
```

【读到的】config reference 原文（`approval_policy` 行）：
> `on-request | never | { granular = { sandbox_approval = bool, rules = bool, mcp_elicitations = bool, request_permissions = bool, skill_approval = bool } }` — "Controls when Codex pauses for approval before executing commands. ... **`untrusted` is unsupported, and `on-failure` is deprecated**; use `on-request` for interactive runs or `never` for non-interactive runs."

**granular 五个类别**（每个 `true` = 允许弹出，`false` = 自动拒绝）：
| 键 | 覆盖什么 |
|---|---|
| `sandbox_approval` | 沙箱越界升权提示 |
| `rules` | execpolicy `prompt` 规则触发的审批 |
| `mcp_elicitations` | MCP elicitation 提示 |
| `request_permissions` | `request_permissions` 工具的提示 |
| `skill_approval` | skill 脚本审批 |

**`untrusted` 的退役与替代路径**【读到的，逐字】：
> "Codex and ChatGPT Work no longer support `approval_policy = "untrusted"`. The retired setting **can prevent either client from starting**."
> 替代：「omit an explicit `approval_policy` and add a project entry to your user-level `~/.codex/config.toml`: `[projects."/path/to/project"] trust_level = "untrusted"`。Commands then require approval unless an execution-policy rule allows them. **This also disables project-local configuration.** Explicitly setting `on-request` overrides the project-derived policy; managed `allowed_approval_policies` **must include `untrusted`** to permit it.」

→ 注意这个巧妙设计：`untrusted` 从**用户可选值**降级为**系统派生值**（由 project trust 推导），但在 admin 白名单 `allowed_approval_policies` 里仍是一个可列举的值。

**切换方式与作用域**：
- CLI 启动时：`-a/--ask-for-approval`、`-s/--sandbox`、`--approve-for-me`、`--dangerously-bypass-approvals-and-sandbox`
- 会话中：**`/permissions`**（TUI 选 preset 或具名 profile）。【读到的】"Future actions respect the updated policy **until you change it again**" → **会话级，不持久化到 config.toml**。
- 持久：`config.toml` 的 `approval_policy` / `sandbox_mode`，或 profile 文件 `~/.codex/<name>.config.toml` + `--profile`
- per-turn：app-server `turn/start` 可覆盖 `approvalPolicy`/`sandboxPolicy`；【读到的】**"When specified, these settings become the defaults for later turns on the same thread."** → **单次覆盖会粘住变成 thread 默认**。

【实测的】落盘证据 —— 每个 turn 都写一条 `turn_context`，把当时生效的完整治理状态快照下来：
```json
{"type":"turn_context","payload":{
  "turn_id":"...","root_turn_id":"...",
  "cwd":"/data/qiwei/repos/omne-harness-lite",
  "workspace_roots":["/data/qiwei/repos/omne-harness-lite"],
  "approval_policy":"never","approvals_reviewer":"user",
  "sandbox_policy":{"type":"danger-full-access"},
  "permission_profile":{"type":"disabled"},
  "model":"gpt-5.6-sol","effort":"medium","personality":"pragmatic",
  "collaboration_mode":{...},"multi_agent_version":"v2","current_date":"2026-09-15"}}
```
另有 `event_msg/thread_settings_applied` 记录会话级设置变更。→ **「这一轮用的是什么策略」是有落盘审计的。**

## 2.2 沙箱策略（sandbox policy）—— 与审批是否正交

### 正交，文档三处明写

【读到的】`docs/agent-approvals-security.md`，**逐字**：
> "Codex security controls come from **two layers that work together**:
> - **Sandbox mode**: **What** Codex can do technically ...
> - **Approval policy**: **When** Codex must ask you before it executes an action ..."

【读到的】`docs/sandboxing.md`：
> "Sandboxing and approvals are **different controls that work together**. The sandbox defines technical boundaries. The approval policy decides when the agent must stop and ask before crossing them."

【读到的】`docs/permission-modes.md`：
> "**Changing who reviews a request doesn't expand the sandbox.** For example, **Approve for me** keeps the same workspace boundary as **Ask for approval**; it sends requests to cross that boundary to automatic review."

**但 UI 层把它们合成了 preset**，这是混淆的来源：

| UI preset | = sandbox × approval × reviewer |
|---|---|
| **Ask for approval**（默认） | `workspace-write` × `on-request` × `user` |
| **Approve for me**（设置里叫 Auto-review） | `workspace-write` × `on-request` × **`auto_review`** |
| **Read Only** | `read-only` × `on-request` × `user` |
| **Full access** | `danger-full-access` × `never` |
| 具名 permission profile | 由 profile 定义 |

→ **两个维度是真的正交，第三个维度（reviewer）也正交；三者在 preset 层被打包。**

### 沙箱级别

【读到的】`-s/--sandbox` 只有三个值：`read-only` / `workspace-write` / `danger-full-access`。

`workspace-write` 的**可写根**包含 cwd + 临时目录，但有**不可写的保护路径**（逐字）：
> - `<writable_root>/.git` is protected as read-only whether it appears as a directory or file.
> - If `<writable_root>/.git` is a pointer file (`gitdir: ...`), **the resolved Git directory path is also protected**.
> - `<writable_root>/.agents` is protected as read-only when it exists as a directory.
> - `<writable_root>/.codex` is protected as read-only when it exists as a directory.
> - Protection is **recursive**.

相关旋钮：`sandbox_workspace_write.{exclude_tmpdir_env_var, exclude_slash_tmp, writable_roots, network_access}`；CLI `--add-dir <DIR>`。

### 新的 permission profiles（beta，Codex ≥ 0.138.0）

【读到的】**与老设置互斥**，逐字：
> "Permission profiles **do not compose with the older sandbox settings**. Configure either `default_permissions` and `[permissions]`, or `sandbox_mode` / `sandbox_workspace_write`, **but not both**. If `sandbox_mode` appears in any loaded config file, you pass `--sandbox`, or the selected config profile sets `sandbox_mode`, Codex uses **those older sandbox settings instead**."
> 例外：「Managed `allowed_permission_profiles` is the exception: it makes Codex use permission profiles.」

内置三个：`:read-only` / `:workspace` / `:danger-full-access`。可 `extends`，但**「It cannot extend `:danger-full-access`; Codex also rejects unknown parents and inheritance cycles.」**

文件系统规则是 **read/write/deny 三值 + 路径特化优先**：
> "More specific entries override broader entries. When two entries target the same path, **`deny` takes precedence over `write`, and `write` takes precedence over `read`**."

路径符号：`:root` / `:minimal` / `:workspace_roots` / `:tmpdir` / `:slash_tmp` / 绝对路径 / `~/path`。支持 deny-glob（`"**/*.env" = "deny"`），但有平台代价：
> "On Linux, WSL, and native Windows, an unbounded `**` deny-read pattern may need **bounded pre-expansion before the sandbox starts**. Set `glob_scan_max_depth` ... Higher values scan deeper before sandbox startup, which can add startup work."
> "`read` or `write` globs are **less portable** on Linux, WSL, and native Windows sandboxing."

【实测的】落盘时 profile 被**解析成结构化策略**存进 `threads.sandbox_policy`：
```json
{"type":"managed",
 "file_system":{"type":"restricted","entries":[
    {"path":{"type":"special","value":{"kind":"root"}},"access":"read"},
    {"path":{"type":"path","path":"/data/qiwei/repos/omne-next"},"access":"write"}]},
 "network":"restricted"}
```
或 `{"type":"disabled"}`（= danger-full-access）。**注意：`file_system` 和 `network` 是同一个 policy 对象的两个并列字段。**

## 2.3 权限分几层 & 怎么合成

### A. 普通配置（`config.toml`）—— 7 层，高覆盖低

【读到的】`docs/config-file/config-basic.md`「Configuration precedence」，**逐字，高→低**：
> 1. CLI flags and `--config` overrides
> 2. Project config files: `.codex/config.toml`, ordered from the project root down to your current working directory (**closest wins; trusted projects only**)
> 3. Profile files selected with `--profile profile-name` (`~/.codex/profile-name.config.toml`)
> 4. User config: `~/.codex/config.toml`
> 5. Cloud-managed `config.toml` defaults, when delivered for the signed-in workspace
> 6. System config (if present): `/etc/codex/config.toml` on Unix
> 7. Built-in defaults

**项目层有硬性禁用清单**（逐字）：
> "Codex ignores the following keys in project-local `.codex/config.toml` and prints a startup warning when it sees them: `openai_base_url`, `chatgpt_base_url`, `apps_mcp_product_sku`, `model_provider`, `model_providers`, `notify`, `profile`, `profiles`, `experimental_realtime_ws_base_url`, and `otel`."

→ **项目不能改凭证路由、模型供应商、通知命令、遥测出口、profile 选择**。这是防「clone 一个仓库就被接管」的 supply-chain 防线。

**项目信任是这一层的开关**：`[projects."<path>"] trust_level = "trusted"|"untrusted"`。不信任 → 跳过全部 `.codex/` 层（config、hooks、rules）；用户层和系统层照常加载。

### B. 管理员强制（`requirements.toml`）—— 4 层，高覆盖低

【读到的】**逐字，低→高**：
> 1. System `requirements.toml`（`/etc/codex/requirements.toml`，Windows 为 `%ProgramData%\OpenAI\Codex\requirements.toml`）
> 2. **Enterprise-managed requirements delivered in the cloud config bundle**
> 3. Legacy `managed_config.toml` fields that the local client reinterprets as requirements
> 4. **macOS managed preferences (MDM)** via `com.openai.codex:requirements_toml_base64`

> "Higher-precedence layers override ordinary scalar and list values from lower layers. **Tables merge by key**, while requirements such as rules, hooks, and filesystem restrictions have **field-specific composition behavior**. Use the reference **instead of assuming that every field merges the same way**."

### C. 不可突破的上界 —— 合成规则原文

【读到的】**这是回答「谁覆盖谁」最关键的一段，逐字**：
> "Requirements constrain security-sensitive settings (approval policy, approvals reviewer, automatic review policy, sandbox mode, permission profiles, web search mode, managed hooks, which MCP servers users can enable, and which plugin marketplace sources they can use). When resolving configuration (for example from `config.toml`, profile files, or CLI config overrides), **if a value conflicts with an enforced rule, the local client falls back to a compatible value and notifies the user.**"

→ **注意这个语义：不是「报错拒绝启动」，而是「降级到一个兼容值并通知用户」。**

关键 requirements 键：
| 键 | 语义 |
|---|---|
| `allowed_approval_policies` | 白名单。含 `untrusted` 才允许那条项目派生的严格策略 |
| `allowed_approvals_reviewers` | 白名单（`user` / `auto_review`）。也用来抑制 auto-review 的额外模型开销 |
| `allowed_sandbox_modes` | 老沙箱白名单 |
| `allowed_permission_profiles` | **表<bool>，缺省即拒**：「Profiles that are **omitted or set to `false` are denied, including profiles added in future versions**」 |
| `guardian_policy_config` | 管理员的 auto-review 策略正文，**覆盖**用户的 `[auto_review].policy` |
| `allow_managed_hooks_only` | **只能写在 `requirements.toml`**；写进 `config.toml` 无效 |
| `[rules] prefix_rules` | 管理员强制的命令前缀规则 |
| `sqlite_home` / `log_dir` / `allow_login_shell` / `check_for_update_on_startup` / `feedback.enabled` / `windows.sandbox_private_desktop` | **不是白名单，是强制值**：「Users can't override an enforced path, update preference, login-shell policy, feedback setting, or Windows private-desktop setting」 |

**云端 requirements fail-closed**【读到的】：
> "If the request fails or times out and no valid cache is available, **the cloud config bundle load returns an error rather than silently starting without the cloud-managed requirements layer.**"
> "A background refresh can update the cache for a later start; **it doesn't replace the requirements already loaded into the current process.**"

**四个字段云端管不了**（逐字）：
> "Set `allowed_login_methods`, `allowed_chatgpt_workspaces`, `cli_auth_credentials_store`, and `chatgpt_base_url` in the local system `requirements.toml` or macOS MDM requirements. **Codex ignores these four fields in cloud-managed requirements.** Local authentication requirements apply **before** credentials load and **before** Codex retrieves cloud policy."
→ 即「谁能登录、凭证存哪、连哪个服务端」必须由**本地/MDM**决定，不能由云端策略自证。这是防「被劫持的云策略把客户端指向别处」。

**Legacy managed defaults 是另一套顺序**（逐字，top overrides bottom）：
> Managed preferences (macOS MDM; highest) > `managed_config.toml` > `config.toml`
> "CLI `--config key=value` overrides apply to the base, **but managed layers override them**. This means each run starts from the managed defaults even if you provide local flags."

### D. 全局合成原则

文档里反复出现的一句：**`deny` 永远赢**。
- 域名规则：「`deny` always wins over `allow`, and global `*` is only valid for allow rules」
- execpolicy：「Codex applies the **most restrictive** decision when more than one rule matches (`forbidden` > `prompt` > `allow`)」
- 浏览器 origin：「A matching **deny** wins」
- requirements vs config：「Where managed requirements and `config.toml` both apply, **a `deny` from either one wins**」
- PermissionRequest hook：「If multiple matching hooks return decisions, **any `deny` wins**」

## 2.4 会话内逐次批准：存哪、活多久、多大范围

**四档作用域，分别落在四个不同的地方：**

| 档 | app-server 决策值 | 存哪 | 活多久 |
|---|---|---|---|
| **单次** | `accept` | 内存（本次调用） | 这一次 |
| **本会话** | `acceptForSession` | **进程内存 + rollout 的 `world_state.permissions.approved_command_prefixes`** | 本 session |
| **本轮 / 本线程**（权限工具） | `request_permissions` 的 `scope` | 内存 | 「Set `scope` to `"session"` to persist the grant for later turns in the same session; **omit it or use `"turn"` for a turn-scoped grant**」 |
| **永久** | `{"acceptWithExecpolicyAmendment": {"execpolicy_amendment": ["cmd","..."]}}` | **写入 `~/.codex/rules/default.rules`** | 永久，跨所有会话 |
| **本目录** | — | `~/.codex/config.toml` 的 `[projects."<path>"] trust_level` | 永久，限该路径 |

【实测的】会话级批准的落盘位置我在 `world_state` 里找到了：
```json
"permissions":{"instructions":"32ca25d6d85edaeb6f1e19b2a5cc4e08d2a631cd",
               "approved_command_prefixes":[]}
```
（本机全为空数组，因为是 `approval_policy=never`。我在 1671 个 rollout 里 grep 过非空的 `approved_command_prefixes`，**0 命中** —— 这一档的实际填充形态我**未实测到**。）

【读到的】永久档的确认：
> "When you add a command to the allow list in the TUI, Codex **writes to the user layer at `~/.codex/rules/default.rules`** so future runs can skip the prompt."
> "When **Smart approvals** are enabled (the default), Codex may **propose a `prefix_rule` for you** during escalation requests. **Review the suggested prefix carefully before accepting it.**"

文件写入的审批还有 `grantRoot`（授予一个可写根）。浏览器侧有独立的三档：`access_approval_lifetime = turn | thread`（产品默认 `thread`）+ `persistent_approval`（"Always allow"），管理员可用 `browser_use.allow_global_persistent_approval = false` 关掉全局持久批准，且**「Existing saved approvals are ignored, not deleted.」**

## 2.5 「这一刻这个命令放不放行」的完整判定链

把所有证据拼起来，**按顺序**：

```
0. 启动期（一次性，会话开始前）
   0a. 本地 system requirements.toml + MDM requirements 加载（先于凭证加载）
   0b. cloud config bundle 拉取 → 失败且无有效缓存 = 报错，不静默降级
   0c. requirements 四层合成 → 得到「允许的策略集合」上界
   0d. config 七层合成 → 得到期望值；与上界冲突 → 回落到兼容值并通知用户
   0e. 项目 trust 判定：untrusted → 丢弃全部 .codex/ 层（config/hooks/rules），
       并派生更严的审批行为
   0f. rules/ 目录扫描（system / team / user ~/.codex/rules/ / 项目 .codex/rules/（仅 trusted））
       .rules 是 Starlark，带 match/not_match 内联单测，加载期校验
   0g. hooks 加载 + 信任校验（按 hook 定义的 hash 记录信任；未信任则跳过）
   0h. 解析出本 thread 的 sandbox_policy（file_system entries + network）与 workspace_roots

1. 模型发起一个命令（或文件改动 / MCP 工具调用 / 网络请求）

2. Shell 包装拆解（仅对 bash/zsh/sh 的 -c / -lc）
   - 若脚本是「纯字面词 + 安全操作符（&& || ; |）」的线性链
       → tree-sitter 解析，拆成多条独立命令，逐条评估，最严者胜
       （`git add . && rm -rf /` 不会因为 allow 了 `git add` 而整体放行）
   - 若含重定向 / $(...) / 变量赋值 / 通配 / 控制流
       → 不拆，整体按 ["bash","-lc","<全文>"] 评估（保守）

3. execpolicy prefix_rule 匹配（多规则取最严：forbidden > prompt > allow）
   - forbidden → 直接拒绝，不提示
   - allow     → 允许「在沙箱外」运行，不提示
   - prompt    → 进入审批流

4. 沙箱内可行性判断
   - 命令若能在当前 sandbox_policy 内完成 → 直接执行，不进审批流
     （auto-review 也不介入：「Actions that stay inside the sandbox continue without an extra review step」）
   - 需要越界（写 writable_roots 外、访问被禁网络、需要 .git/.codex/.agents 写）→ 进审批流

5. approval_policy 闸门
   - never   → 不弹出。「Execution failures are immediately returned to the model」
               （非交互 / subagent 里：「an action that needs new approval fails and
                 Codex surfaces the error back to the parent workflow」）
   - granular→ 按类别（sandbox_approval / rules / mcp_elicitations /
               request_permissions / skill_approval）决定「允许弹出」还是「自动拒绝」
   - on-request → 继续

6. PermissionRequest hook（若配置且已信任）
   - 任一 hook 返回 deny → 拒绝（deny 胜）
   - 有 allow 且无 deny → 放行，且「lets the request proceed without surfacing
     the approval prompt」（跳过 7、8）
   - 无 hook 决策 → 走正常流程
   - 注意：「Don't return `updatedInput`, `updatedPermissions`, or `interrupt`
     for PermissionRequest; those fields ... fail closed today.」

7. approvals_reviewer 路由
   - "user"        → 弹给人（7a）
   - "auto_review" → 交给 guardian reviewer 子 agent（7b）

   7a. 人工决策：accept / acceptForSession / decline / cancel /
       acceptWithExecpolicyAmendment(写 .rules)
       （文件改动另有 grantRoot；网络审批按 host+protocol+port 分组，
         一个提示可解锁同目的地的多个排队请求）

   7b. Auto-review（guardian）：
       - reviewer 看到「compact transcript + 确切的审批请求」，
         不含隐藏推理（「Hidden assistant reasoning is not included」）
       - 风险分级：low/medium 可过；critical 拒；
         high 需要「enough user authorization and no matching deny rule」
       - 「Prompt-build, review-session, and parse failures **fail closed**」
       - 超时单独上报，但「the action still does not run」
       - 熔断：同一 turn 内连续 3 次拒绝，或最近 50 次评审里 10 次拒绝
         → 发警告并 interrupt 整个 turn
       - 人工翻盘：`/approve` 打开 Auto-review Denials 选单，
         对某一条确切动作批准「一次重试」，且重试仍过 auto-review，
         reviewer 仍可再拒。最多记录 10 条近期拒绝。

8. 执行 / 拒绝
   - 拒绝时 Codex 给模型的不是普通错误，而是加强指令：
     「Do not pursue the same outcome via workaround, indirect execution, or
      policy circumvention. Continue only with a materially safer alternative.
      Otherwise, stop and ask the user.」

9. 事后（异步、可滞后）
   - GPT-6 Astra 的 safety monitoring 异步跑，可暂停整个 task；
     「A pause can arrive after the activity that triggered it」
```

**绕过这条链的三个已知口子**（都是刻意留的）：
1. `--dangerously-bypass-approvals-and-sandbox` —— 跳过 4–8 全部。
2. `thread/shellCommand`（app-server）—— 【读到的】**"This API runs outside the sandbox with full access and doesn't inherit the thread sandbox policy. Clients should expose it only for explicit user-initiated commands."**
3. `--dangerously-bypass-hook-trust` —— 跳过 0g。

## 2.6 网络是不是独立维度

**是，而且是被拆成两个独立开关的独立维度。**

【读到的】**核心逻辑表，逐字**：
> - Network off + `network_proxy` on: network stays off, and **the feature does nothing**.
> - Network on + `network_proxy` off: network stays on with **unrestricted direct outbound access**.
> - Network on + `network_proxy` on: network stays on, and outbound traffic is constrained by the configured network policy.

> "The feature changes **how** enabled network access is enforced; **it does not grant network access by itself**."
> "Adding domain rules **does not enable the proxy by itself**."

→ 这是一个容易踩的坑：**光写了 `domains` 白名单而没开 `features.network_proxy`，等于没写**，命令仍有完全直连的出网能力。

控制点：
- 开关：`sandbox_workspace_write.network_access`（bool）或 `permissions.<name>.network.enabled`
- 执行：`features.network_proxy.enabled`（feature 状态 = **experimental，默认 off**，本机实测 `codex features list` 显示 `network_proxy experimental false`）
- 策略：`domains` 表，`allow`/`deny`，模式 `example.com` / `*.example.com`（仅子域）/ `**.example.com`（含 apex）/ `*`（仅 allow）
- 本地/私网守卫：`allow_local_binding = false`（默认）。「hostnames that resolve to local/private IPs **stay blocked even if they match the allowlist**」
- DNS rebinding 防护（逐字）：「Lookups that fail or time out are blocked. Hostnames that resolve to non-public addresses are blocked. **The check reduces DNS rebinding risk, but it does not eliminate it.** Preventing rebinding completely would require pinning resolved IPs through the transport layer.」
- Unix socket 白名单：`unix_sockets`
- 危险开关：`dangerously_allow_non_loopback_proxy`、`dangerously_allow_all_unix_sockets`
- 管理员侧独立通道：`[experimental_network]` requirements，「can configure and start sandboxed networking without `features.network_proxy`, **but they do not turn on network access when the active sandbox keeps it off**」

**代理管不到的东西**（逐字，很重要）：
> "It does not filter **web search, app or connector tool calls, MCP server connections, browser or Computer Use activity, Codex cloud tasks, or the client's model and authentication requests.**"
> "**A command network allowlist is not a global network policy for every action Codex can perform.**"

Web search 是**第四个独立维度**：`web_search = "cached"`（默认）/ `"indexed"` / `"live"` / `"disabled"`；管理员用 `allowed_web_search_modes`。默认 cached 的理由（逐字）：「cached mode returns pre-indexed results instead of fetching live pages. This **reduces exposure to prompt injection** from arbitrary live content, but you should still treat web results as untrusted.」**且：「If you are using `--yolo` or another full access sandbox setting, web search defaults to live results.」**

## 2.7 取舍分析

- **选了「what / when / who 三维正交，UI 打包成 preset」**。收益：策略可组合、可被管理员分别约束（三个独立白名单）、reviewer 可换而边界不变。代价：**心智负担极高** —— 光「有网」就要同时理解 `network_access`、`features.network_proxy`、`domains`、`allow_local_binding`、`allowed_web_search_modes` 五个不同层次的东西，且默认组合会静默地不生效。文档自己不得不写一张三行真值表来解释。
- **选了「approval_policy=never 时执行失败直接回给模型」而不是阻塞**。这让非交互/CI/subagent 路径能跑，代价是**模型会看到大量沙箱拒绝并自己想办法绕**——他们用「拒绝时附加强化指令 + 熔断」来补这个洞，本身就承认了这个问题。
- **选了「auto-review 是 reviewer 替换，不是权限授予」**，并反复强调。这是很克制的设计：模型评审不扩大边界，只是把人从提示里换出来。代价是**多一次模型调用的成本**（文档明说「Automatic review uses extra model calls, so it can add to Codex usage」），且**不是确定性保证**（「it is not a deterministic security guarantee」「It can still make mistakes, especially in adversarial or unusual contexts」）。
- **选了「退役 untrusted 审批策略」**，理由是它会让客户端根本起不来。改用项目 trust 派生 —— 这把「不信任」从一个用户随手能选的开关，变成了一个**需要在用户级 config 里对具体路径声明**的东西，同时顺带关掉项目局部配置。这是把「不信任」和「不加载该项目的配置」绑死了，语义更干净但**粒度更粗**。
- **选了「permission profiles 与 sandbox_mode 互斥而非叠加」**。避免两套语义打架，但代价是**迁移期极痛**：任何一层 config 里出现 `sandbox_mode`，整个 profile 体系就静默失效，且只有管理员的 `allowed_permission_profiles` 能强制切过去。
- **代价：口子是明写的**。`thread/shellCommand` 完全不继承沙箱策略，`--dangerously-bypass-hook-trust` 跳过 hook 信任。他们选择把口子写在文档里而不是假装没有。
- **云端治理与本地完全割裂**（见 §6）。

# 3. 上下文感知域

## 结论

Codex 有一个**显式的、落盘的、带全量快照 + 增量 delta 的「感知域」对象 —— `world_state`**。它不是隐式拼出来的 prompt，是一个有结构、有版本、会重放进上下文的一等公民。

## 3.1 会话开始时决定了什么

【实测的】`world_state` 的 `full: true` 快照，`state` 的**全部 18 个键**：

| 键 | 内容（实测样本） |
|---|---|
| `agents_md` | `{directory: "/data/qiwei/repos/omne-harness-lite", text: "<AGENTS.md 全文>"}` |
| `environments` | `{environments:{local:{cwd, status:"available", shell:"bash"}}, current_date, timezone, filesystem:"<XML>", subagents:"<XML>"}` |
| `permissions` | `{instructions:"<sha1 hash>", approved_command_prefixes:[]}` |
| `host_skills` | `{body: "## Skills\nA skill is ... 技能目录清单"}` |
| `skills` / `orchestrator_skills` | `{includeInstructions: true}` / `{includeInstructions:true, enabled:false}` |
| `collaboration_mode` | `{mode:"default", model:"gpt-5.6-sol", instructions:"<sha1>"}` |
| `multi_agent_mode` | `{mode:"explicitRequestOnly", usage_hint_hash:"<sha1>"}` |
| `model` / `personality` | `"gpt-5.6-sol"` / `{model, personality:"pragmatic"}` |
| `apps_instructions` / `plugins_instructions` / `environments_instructions` / `git_attribution` | bool |
| `managed_developer_instructions` / `persistent_mode` | `{}` |
| `realtime` | `{active:false}` |
| `context_window_guidance` | `""` |

**filesystem 感知域渲染给模型的确切形态**（实测原文）：
```xml
<filesystem>
  <workspace_roots><root>/data/qiwei/repos/omne-harness-lite</root></workspace_roots>
  <permission_profile type="disabled"><file_system type="unrestricted" /></permission_profile>
</filesystem>
```
并作为一条 `role:user` 的 `<environment_context>` 消息进入历史（`content_item_kinds: ["environments.environment_context"]`）。

**AGENTS.md 加载链**【读到的，逐字】：
> "Codex builds an instruction chain **when it starts (once per run; in the TUI this usually means once per launched session)**. Discovery follows this precedence order:
> 1. **Global scope:** In `~/.codex`（或 `CODEX_HOME`），reads `AGENTS.override.md` if it exists. Otherwise `AGENTS.md`. **Uses only the first non-empty file at this level.**
> 2. **Project scope:** Starting at the project root (typically the Git root), walks **down** to your cwd. In each directory checks `AGENTS.override.md`, then `AGENTS.md`, then `project_doc_fallback_filenames`. **At most one file per directory.**
> 3. **Merge order:** concatenates **from the root down**, joined with blank lines. **Files closer to your current directory override earlier guidance because they appear later in the combined prompt.**"
> "Codex skips empty files and **stops adding files once the combined size reaches `project_doc_max_bytes` (32 KiB by default)**."

→ 覆盖靠「后出现」而非结构化合并；**超过 32 KiB 直接截断**（不是报错）。项目根由 `project_root_markers`（默认 `[".git"]`）决定。

**MCP server**【读到的】：`mcp_servers` 配置；「If you mark an enabled MCP server as `required` in config and that server fails to initialize, **`thread/start` and `thread/resume` fail** instead of continuing without it.」→ **必需 MCP 是会话启动的硬前置**。

**app-server 还会返回 `instructionSources`**：「`thread/start`, `thread/resume`, and `thread/fork` return `instructionSources`, an array of loaded instruction-file paths.」→ 感知域来源可被客户端审计。

## 3.2 会话进行中能不能追加

**能，而且是增量 delta 机制。**

【实测的】`world_state` 的 `full: false` 记录，只带变化的子树。同一个 rollout 里实测 8 条 world_state，`full` 标志序列为 `[True, False, False, False, False, False, False, True]`。delta 实例：

```json
// subagent 花名册变化
{"full":false,"state":{"environments":{"subagents":
   "<agent name=\"/root/f_architecture_review\" />\n<agent name=\"/root/f_capability_slice\" />..."}}}
// 跨天
{"full":false,"state":{"environments":{"current_date":"2026-09-16"}}}
```

→ **活体 subagent 花名册和当前日期都是感知域的一部分，会持续重注入。**

追加路径：
- **写路径**：CLI `--add-dir <DIR>`（启动时）；审批里的 `grantRoot`（运行中授予可写根）；`request_permissions` 工具（scope = turn | session）
- **读路径**：Windows 专有 `/sandbox-add-read-dir <绝对路径>`（【读到的】「Codex **refreshes the Windows sandbox policy** and grants read access to that directory for later commands」）
- **文件**：`/mention <path>`
- **IDE 上下文**：`/ide`
- **任意 item**：app-server `thread/inject_items`（「appends prebuilt Responses API items to a loaded thread's prompt history **without starting a user turn**. These items are **persisted to the rollout**」）
- **cwd**：`turn/start` 可带 `cwd`，且会粘成后续默认

## 3.3 会话级还是持久

| 绑定 | 作用域 |
|---|---|
| `workspace_roots` / `cwd` | **thread 级**，per-turn 可覆盖且粘住 |
| AGENTS.md 链 | **启动时一次**（per run / per launched session） |
| `permissions.<name>.workspace_roots` | **持久**（config 里定义，profile 激活时并入本 session 的 runtime roots） |
| MCP servers | config 层（用户 / 项目 / 管理员白名单） |
| 一次性 grantRoot / request_permissions(turn) | turn 级 |
| request_permissions(session) | session 级 |
| `~/.codex/rules/default.rules` 里的 amendment | **永久，跨会话** |
| `[projects."<path>"] trust_level` | **永久，按路径** |

【读到的】`:workspace_roots` 的合成语义：「the **current session's runtime workspace roots** plus the profile-defined roots」；且同名 profile 可被多层 config 各自扩展：「an organization-level config and a user-level config can extend the same profile independently ... **both workspace roots participate in the effective profile**」。

## 3.4 越界时发生什么

**取决于是否在沙箱内可行**：
- 沙箱内 → 直接跑，无感。
- 沙箱外 → 产生一条 **approval request**（= 升权请求），走 §2.5 第 5–8 步。
- `approval_policy = never` → 不弹，**执行失败直接返回模型**。
- 非交互 / subagent 无法弹出 → 【读到的】「an action that needs new approval **fails and Codex surfaces the error back to the parent workflow**」。
- macOS 上策略无法被平台强制时 → 【读到的】**「If the selected policy cannot be enforced by the platform sandbox, Codex refuses to run the command instead of silently running it unsandboxed.」**
- Windows unelevated / Linux 受限容器 → 「unsupported split policies are **refused**」。
- profile 写了运行时无法强制的直接 write 规则 → 「Codex **rejects** direct write rules that the active runtime cannot enforce.」

## 取舍分析

- **选了「感知域是一个显式的、有 full/delta 的落盘对象」**，而不是每轮重新拼 prompt。收益：可审计（你能从 rollout 读出任一时刻模型「以为」自己在哪）、可增量（只重注入变化的子树，省 token 且利于缓存前缀）、可被 hook 注入（`SessionStart` 的 `additionalContext`）。代价：多一层状态机，且 `world_state` 里大量用 **sha1 hash 指代长文本**（`permissions.instructions`、`collaboration_mode.instructions`、`multi_agent_mode.usage_hint_hash`）—— 这意味着**光看 rollout 无法还原那些指令正文**，只能判断「有没有变」。
- **选了「AGENTS.md 只在启动时组装一次 + 32 KiB 硬上限 + 后出现者覆盖」**。收益：简单、确定、无运行时 IO。代价：会话中途改 AGENTS.md 不生效；超限**静默截断**而不是报错（文档只说「Raise the limit or split instructions across nested directories when you hit the cap」）；「覆盖」靠位置而非语义，两处矛盾的指令都会进上下文。
- **选了「必需 MCP 失败 = 会话起不来」**。fail-fast，正确，但代价是外部依赖变成会话可用性的一部分。
- **选了「平台无法强制则拒跑，而非降级静默运行」**。这是整个沙箱设计里最重要的一条正确决定。

**无人值守的两条正式通道**【读到的】：Service accounts（「run and scale **headless** Codex workflows ... Each CI runner, scheduled job, or shared integration gets its own ChatGPT workspace identity」，**仅 pay-as-you-go 计划**）和 Access tokens（「authenticate trusted **non-interactive local workflows**」，文档用例只写 `codex exec`）。

**两个纠偏**（子 agent 查证）：
- **GitHub Action 不进 cloud**：`openai/codex-action@v1`「installs the **Codex CLI** ... and runs **`codex exec`** under the permissions you specify」——跑在 GitHub runner 上的本地 CLI。
- **Scheduled tasks 不在 Codex cloud 跑**：只有桌面 App（local / worktree，且「keep the machine powered on and the ChatGPT desktop app running」）和 ChatGPT Work web 两种执行位置。**「Codex CLI doesn't provide the Scheduled management interface.」**

**身份归属的一个坑**【读到的】：Linear triage rule 自动派发时「**Codex runs chats using the account of the issue creator.**」→ 配额和审计记在 issue 创建者头上。

## 4.2 状态与终态

**三个层次的状态，互不相同：**

**(a) Thread 运行时状态**【读到的，`thread/read` 返回】：
`notLoaded` | `idle` | `systemError` | `active{activeFlags:[...]}`（如 `waitingOnApproval`）。变更通过 `thread/status/changed` 通知。

**(b) Turn 状态**【实测的，`thread_turns.status` 全库分布】：
`completed` 3995 / `interrupted` 71 / `failed` 67 / **`inProgress` 57**
→ **57 个 turn 永久卡在 `inProgress`**。说明**没有崩溃后的 turn 状态收敛/对账机制** —— 进程死掉时正在跑的 turn 就永远停在 inProgress。

**(c) Thread 持久状态**【实测的，`state_5.sqlite:threads` 列】：
`archived` (0/1) + `archived_at` + `is_pinned` + `name` + `thread_section_id` + `project_id`。
→ **没有 "completed" 这种终态列**。thread 的终态只有 archived 和「被删」。

**(d) Goal 状态**【实测的，`goals_1.sqlite`】—— 这是唯一有正经状态机 CHECK 约束的对象：
```sql
CREATE TABLE thread_goals (
    thread_id TEXT PRIMARY KEY, goal_id TEXT, objective TEXT,
    status TEXT NOT NULL CHECK(status IN
      ('active','paused','blocked','usage_limited','budget_limited','complete')),
    token_budget INTEGER, tokens_used INTEGER DEFAULT 0,
    time_used_seconds INTEGER DEFAULT 0, created_at_ms, updated_at_ms)
```
注意 `usage_limited` 和 `budget_limited` 是**两个不同的受限终态**（账户额度 vs 目标预算）。

**(e) 错误分类**【读到的，app-server `codexErrorInfo`】：
`ContextWindowExceeded` / `UsageLimitExceeded` / `HttpConnectionFailed` / `ResponseStreamConnectionFailed` / `ResponseStreamDisconnected` / `ResponseTooManyFailedAttempts` / `BadRequest` / `Unauthorized` / `SandboxError` / `InternalServerError` / `Other`。

## 4.3 `codex resume` 到底恢复什么

**结论：resume 复用同一个 thread id（同一个对象），fork 才是新建。**

【读到的】app-server 原文，`thread/resume` 传 `threadId: "thr_123"`，返回的 `thread.id` 仍是 `"thr_123"`：
> "To continue a stored session, call `thread/resume` with the `thread.id` you recorded earlier. The response shape matches `thread/start`."
> "**Resuming a thread doesn't update `thread.updatedAt` (or the rollout file's modified time) by itself. The timestamp updates when you start a turn.**"

而 fork（逐字）：
> `/fork`："Codex **clones** the current chat into a new chat **with a fresh ID**, leaving the original transcript untouched so you can explore an alternative approach in parallel."
> glossary `Thread fork`："**New thread branched from the stored history of an existing thread.**"
> `thread.sessionId`：「**forked threads keep the session id of the root they came from**」

【实测的】fork 的落盘形态与我在 §0 给的 `session_meta` 一致：新 `id`、`forked_from_id` 指向源、`session_id` 保持树根不变。

**resume 的两个副作用**【读到的】：
- cwd 冲突：「If the current working directory differs from the session's saved directory, **Codex asks which directory to use.**」由 `tui.resume_cwd = "current" | "session"` 固化；`-C/--cd` 优先。
- 换模型：「If you resume with a different model than the one recorded in the rollout, Codex **emits a warning and applies a one-time model-switch instruction on the next turn.**」
- dynamic tools：「Codex persists these dynamic tools in the thread rollout metadata and **restores them on `thread/resume`** when you don't supply new dynamic tools.」

**选择范围**：`codex resume --last` 默认按 cwd 过滤；`--all` 取消过滤；`--include-non-interactive` 才把 `codex exec` 产生的 session 纳入 picker。【实测的】`threads.source` 分布：`JSON(subagent)` 1785 / `exec` 796 / `vscode` 40 / `cli` 34 —— **exec 产生的 thread 占非 subagent 的绝大多数，默认却对 picker 不可见**。

**`/side`**：「an **ephemeral fork** from the current chat without switching away from the main chat ... whose transcript is separate from the parent chat」，且「unavailable inside another side chat and during review mode」。

## 4.4 终止时正在跑的东西

- **turn 中断**：`turn/interrupt` → 「the turn finishes with `status: "interrupted"`」。【实测的】rollout 里有对应的 `event_msg/turn_aborted`，`thread_turns` 里有 71 个 `interrupted`。
- **subagent 中断**：`agents.interrupt_message`（默认 `true`）—— 「**Record a model-visible message when an agent turn is interrupted**」。设 `false` 则模型看不到自己被打断。
- **后台终端**：`/ps` 列出（含最近 3 行非空输出）、`/stop`（别名 `/clean`）停全部；app-server 有 `thread/backgroundTerminals/{list,clean,terminate}`（experimental）。**不会因为 turn 结束就自动停** —— 这是显式的独立生命周期。
- **SessionEnd hook**【读到的】：「It runs for the main thread when you **archive or delete a conversation that's still open**, when Codex **closes normally**, or after a conversation has been **idle and isn't open in any connected client for 30 minutes**. **It won't run for subagents.**」且「`SessionEnd` hooks **always run synchronously, even when `async` is `true`**. They are **advisory**, so their output won't steer Codex or keep the thread open.」
- **handoff 打断**【读到的】：「**If the chat is running, handoff interrupts the current response before transferring it.**」
- 【实测的】**没有崩溃恢复对账**：57 个 turn 卡在 `inProgress`，1184 条 `thread_spawn_edges` 全部是 `status='open'`，**没有一条变成 closed** —— 子线程的关闭状态在这套语料里从未被写回。

## 4.5 父子会话 / 子任务树

**有，而且是一等公民。**

【实测的】`state_5.sqlite`：
```sql
CREATE TABLE thread_spawn_edges (
    parent_thread_id TEXT NOT NULL,
    child_thread_id  TEXT NOT NULL PRIMARY KEY,   -- 每个子只能有一个父
    status TEXT NOT NULL)
```
1184 条边，全部 `open`。`threads` 表另有 `agent_path` / `agent_nickname` / `agent_role` / `thread_source` 列。

【实测的】`agent_role` 分布（本机）：`worker` 222 / `explorer` 166 / `default` 112 / `omne-architect` 97 / `architecture-reviewer` 47 / ... —— 前三个是 Codex 内置角色，后面是本仓库的自定义 agent。

【读到的】内置三角色：「`default`: general-purpose fallback agent. `worker`: execution-focused agent for implementation and fixes. `explorer`: read-heavy codebase exploration agent.」自定义放 `~/.codex/agents/*.toml`（个人）或 `.codex/agents/*.toml`（项目），必须有 `name` / `description` / `developer_instructions`。

**并发与深度约束**：`agents.max_concurrent_threads_per_session`（旧别名 `agents.max_threads`）、`agents.enabled`、`agents.default_subagent_model` / `default_subagent_reasoning_effort`。本机 config 实测 `[agents] max_threads = 12, max_depth = 1`，rollout 里 `thread_spawn.depth = 1`。

**子 agent 的治理继承 —— 关键段落**【读到的，逐字】：
> "Subagents **inherit your current sandbox policy**."
> "Codex also **reapplies the parent turn's live runtime overrides when it spawns a child**. That includes sandbox and approval choices you set interactively during the session, such as `/permissions` changes or `--yolo`, **even if the selected custom agent file sets different defaults**."
> "In interactive CLI sessions, **approval requests can surface from inactive agent threads even while you are looking at the main thread.** The approval overlay shows the source thread label, and you can press `o` to open that thread before you approve."

配置解析顺序（逐字）：「Codex resolves each setting from an **explicit spawn value**, then the corresponding **`[agents]` default**, then the **parent's value**」，但「If a custom agent file sets `model` or `model_reasoning_effort`, **the value in the file takes precedence**」。其余（`sandbox_mode`、`mcp_servers`、`skills.config`）文件省略时继承父。

**级联语义**：archive 和 delete 都级联到 spawned descendants；`thread/list` 有 experimental 的 `parentThreadId` / `ancestorThreadId` 过滤。

## 4.6 云端生命周期 vs 本地

| 维度 | 本地 | 云端 |
|---|---|---|
| 对象 | thread（+ session 树根） | task（`id/url/title/status/environment_id/attempt_total`...） |
| 并行结构 | subagent 树（父子边） | **attempt 扇出（1–4，best-of-N，同一 task 内并列）** |
| 运行模型 | 单阶段 | **两阶段**：setup（有网、有 secret）→ agent（默认无网、secret 已移除） |
| 环境复用 | 无 | **容器缓存 ≤12h**，Business/Enterprise **跨用户共享** |
| 隔离 | OS 沙箱（Seatbelt / bwrap+seccomp / Windows sandbox） | OpenAI 托管容器 / VM-backed sandbox |
| 审批 | 有完整审批链 | **没有审批概念**（整个容器就是边界） |
| 出网 | 代理 + 域名策略 | 环境级 on/off + 域名白名单 + **允许的 HTTP 方法**（可限 GET/HEAD/OPTIONS）；全部出站流量强制过 HTTP/HTTPS proxy |
| 模型 | 可选 | **不可选**：「Currently, **you can't change the default model for Codex cloud chats**」 |
| 状态枚举 | 有（见 4.2） | **文档未枚举**（只知有 `status` 字段） |
| 超时/回收 | 无文档 | **无文档** |
| 父子关系 | 有 | **无**（list schema 里没有 parent 字段） |

**两阶段的三条硬边界**【读到的，逐字】：
> "Secrets ... are only available to setup scripts. For security reasons, **secrets are removed before the agent phase starts**."
> "**Environment variables** are set for the full duration of the chat (including setup scripts and the agent phase)."
> "Setup scripts run in a **separate Bash session** from the agent, so commands like `export` do not persist into the agent phase."

**安全监控可异步暂停**【读到的】：
> "Monitoring runs asynchronously and **can pause a task** if it detects potentially unsafe model behavior. **A pause can arrive after the activity that triggered it**; monitoring doesn't replace sandboxing, permissions, or review of the result."
> CLI 与移动端：「Full findings and resume aren't available. **The task ends.**」ZDR / Modified Abuse Monitoring / 非美国数据驻留：同样「**The task ends.**」

## 4.7 云端 ↔ 本地接力：身份保不保留

| 交接 | 身份 | 依据 |
|---|---|---|
| Local ↔ Worktree（Handoff） | **保留** | 「Each chat keeps the same associated worktree over time」。但「**any files that are part of your `.gitignore` won't move with the chat**」除非 `.worktreeinclude` |
| Local ↔ Remote host（Handoff） | **保留** | 「transfers the chat and Git state, and switches the chat to that host」 |
| 任意 → Cloud（Handoff） | **不支持** | 「**handoff to a Codex cloud environment isn't supported**」「**Codex can't hand off the chat making the request**」 |
| IDE local → Cloud（`/cloud`） | **新对象** | 「Codex creates a **new chat** in the cloud that carries over the existing chat context (including the plan and any local source changes)」 |
| Cloud → Local（`codex apply` / `cloud apply`） | **不保留，只搬 diff** | `codex cloud` 子命令只有 `exec\|status\|list\|apply\|diff\|help`，无 resume/pull/import。`codex apply` 走 `git apply`，「exits non-zero if `git apply` fails」 |
| CLI ↔ 桌面 App（`/app`） | **保留** | 「The desktop app opens the **same saved chat**」 |

## 取舍分析

- **选了「resume = 同一对象、fork = 新对象且保留 sessionId」**。语义干净。代价：resume 没有「新的一段」的边界 —— 一个 thread 可以无限长（实测最大 rollout 280 MB），而唯一的分界只有压缩点。`SessionStart` hook 的 `source` 里有 `compact` 这一档，说明他们**用「压缩」事件来近似「新的一段」**。
- **选了「thread 没有 completed 终态」**。收益：会话本来就可以随时被 resume，强加终态会撒谎。代价：**没有任何东西告诉你一个会话「结束了」**；`SessionEnd` hook 只能靠「30 分钟没有任何客户端打开」这种启发式来推断，而且它是 advisory 的、不对 subagent 触发。
- **代价：没有崩溃对账**。57 个永久 `inProgress` 的 turn + 1184 条永远 `open` 的 spawn edge，是 append-only 日志 + 无收敛任务的直接后果。这些字段存在但没有被维护到底。
- **选了「子 agent 强制继承父的 live 运行时覆盖，凌驾于 agent 定义文件」**。这是正确的安全默认 —— 不能让一个 agent 定义文件把自己提权。代价：你无法定义「这个 reviewer 永远只读」并指望它在父是 yolo 时仍然只读（文档只说可以在 custom agent 里 override sandbox，但又说 live override 会被 reapply —— 这两句在文档里是**并列且未消解的**，见「未能查证」）。
- **选了「云端不提供会话接力，只提供 diff」**。这是整个产品里最明显的功能缺口：cloud 任务的上下文（推理、工具轨迹、决策）**完全无法带回本地**，你只能拿到一个 patch。代价是云端与本地实际上是两个产品。
- **选了「云端不暴露 thread/turn 原语」**。让云端 API 保持窄而稳（10 个字段），代价是上面那一条。

## 5.1 成本 / token 归属 —— 三层记账

【实测的】每次模型响应都落一条 `token_usage_record`：
```json
{"type":"token_usage_record","payload":{
  "thread_id":"01a0a78a-...","turn_id":"01a0a78a-...",
  "session_id":"01a0a4f4-...","root_turn_id":"01a0a789-...",
  "response_id":"resp_072f68ef...",
  "usage":            {input_tokens, cached_input_tokens, cache_write_input_tokens,
                       output_tokens, reasoning_output_tokens, total_tokens},
  "turn_token_usage":  {同上},
  "thread_token_usage":{同上}}}
```
→ **单次响应 / 本轮累计 / 本线程累计，三层同时记**，并带 `session_id` 和 `root_turn_id` 可以回滚到树根。`threads.tokens_used` 是另一份物化（实测某 subagent thread = 825394）。

**但没有 session 级（树）的聚合列** —— 只能靠 `session_id` 自己 join 出来。

# 6. 它刻意不做什么

## 6.1 危险开关的原文警告

【读到的，本机 v0.154.0 `codex --help` 逐字】：
```
--dangerously-bypass-approvals-and-sandbox
      Skip all confirmation prompts and execute commands without sandboxing.
      EXTREMELY DANGEROUS. Intended solely for running in environments that are
      externally sandboxed
--dangerously-bypass-hook-trust
      Run enabled hooks without requiring persisted hook trust for this invocation.
      DANGEROUS. Intended only for automation that already vets hook sources
```
【读到的】文档里的别名与定性：「`--dangerously-bypass-approvals-and-sandbox` (alias: `--yolo`) — **No sandbox; no approvals *(not recommended)*.**」
⚠️ **【实测的】`codex completion bash` 生成的补全脚本里没有 `--yolo`**，只有全名。→ 该别名在 v0.154.0 要么被隐藏要么已移除（文档与二进制不一致）。

【读到的】Dev container 场景下的诚实告警：
> "Devcontainers provide substantial protection, but **they do not prevent every attack**. If you run Codex with `--sandbox danger-full-access` or `--dangerously-bypass-approvals-and-sandbox` inside the container, a malicious project can **exfiltrate anything available inside the devcontainer, including Codex credentials**."

## 6.2 沙箱的已知平台边界（原文）

【读到的】`docs/permissions.md`「How enforcement works」，逐字：
> - "On **macOS**, Codex uses Seatbelt sandbox profiles. **If the selected policy cannot be enforced by the platform sandbox, Codex refuses to run the command instead of silently running it unsandboxed.**"
> - "On **Linux and WSL**, Codex uses bubblewrap and seccomp, **with Landlock available for compatibility fallback paths**. The strongest enforcement path depends on user namespaces and kernel support; **restricted container hosts can force compatibility paths, and unsupported split policies are refused**."
> - "On **native Windows**, `elevated` sandboxing is strongest ... `unelevated` sandboxing is a **fallback with weaker network isolation and cannot enforce every split read/write carveout**, so unsupported policies are refused. **Use WSL when you need the Linux sandbox model.**"

【读到的】WSL1 支持终止：「**WSL1 was supported through Codex `0.114`; starting in `0.115`, the Linux sandbox moved to `bwrap`, so WSL1 is no longer supported.**」

【读到的】Docker 场景：「When you run Linux in a containerized environment such as Docker, **the sandbox may not work** if the host or container configuration blocks the namespace, setuid `bwrap`, or `seccomp` operations that Codex needs.」

【读到的】DNS rebinding：「The check reduces DNS rebinding risk, **but it does not eliminate it. Preventing rebinding completely would require pinning resolved IPs through the transport layer.** If hostile DNS is in scope, enforce egress controls at a lower layer too.」

## 6.3 明确声明的能力边界

**Auto-review 的 Limits 节**【读到的，逐字】：
> "Auto-review improves the default operating point for long-running agentic work, but **it is not a deterministic security guarantee**.
> - It **only evaluates actions that ask to cross a boundary**.
> - It **can still make mistakes**, especially in adversarial or unusual contexts.
> - It should **complement, not replace**, good sandbox design, monitoring, and organization-specific policy."
> "With `approval_policy = "never"`, `:danger-full-access`, or `--yolo`, **an action can avoid creating the boundary-crossing approval request that review requires**."
> "A network destination on the allowlist **doesn't trigger review by itself**."

**权限 profile 管不到的**【读到的】：
> "Permission profiles govern sandboxed commands that run on your machine. **Connectors, MCP servers, browser or computer-use surfaces, Codex cloud environment settings, and approved escalations use their own controls.**"
> "Network domain rules ... **do not determine whether an allowed destination is trustworthy**, and wildcard allow rules stay broad."

**网络代理管不到的**【读到的】：
> "It does not apply the profile's domain allowlist to: **Web search / Apps and connectors / MCP servers / Browser and Computer Use / Codex service traffic / Codex cloud.**"
> "**A command network allowlist is not a global network policy for every action Codex can perform.**"

**managed configuration 管不到 cloud**【读到的，逐字，这是最硬的一条】：
> "Managed configuration controls supported **local runtime behavior** for covered capabilities in the ChatGPT desktop app, Codex CLI, and IDE extension."
> "It doesn't filter web search, apps and connectors, MCP servers, native-app traffic, Codex service requests, **or Codex cloud traffic**. ... **Configure Codex cloud network access in its cloud environment settings.**"
> "These requirements do not route browser traffic through the proxy or control ... **Codex cloud networking**."

→ **`requirements.toml` / permission profiles / rules / hooks / MCP 白名单 / sandbox mode，一条都落不到 cloud 容器里。**

**审计覆盖不完整**【读到的，逐字】：
> "**Don't assume every shell command, browser interaction, app invocation, file operation, or approval appears in a customer-visible compliance export.**"

## 6.5 会话层刻意不做的（我的归纳）

| 不做 | 依据 |
|---|---|
| **rollout 不做保留期 / 配额 / GC** | 全文档无 retention 键；实测 12 GB 无上限 |
| **thread 不做 completed 终态** | schema 只有 archived |
| **不做崩溃后的 turn/spawn 状态对账** | 实测 57 inProgress、1184 全 open |
| **不做云端会话接力** | `codex cloud` 无 resume/pull |
| **rollout 不当审计日志用** | 存的是截断后的模型可见版本 |
| **reasoning 不留明文** | 只存 `encrypted_content` |
| **压缩不删历史** | 追加 `compacted` 替换记录 |
| **`thread/shellCommand` 刻意不继承沙箱** | 「doesn't inherit the thread sandbox policy」 |
| **`thread/rollback` 已废弃** | 「is deprecated and will be removed」 |
| **paginated history 在 app-server 上 fail-closed** | 「Paginated thread creation isn't supported yet and returns JSON-RPC error `-32601`」「full-history reads, turn pagination, and resume **fail closed**」——但**本机 1671 个 thread 已经是 `history_mode='paginated'`**，文档落后于二进制 |

## 取舍分析

Codex 在「刻意不做」这件事上的姿态很一致，可以概括成三条：

1. **宁可拒跑，不可静默降级。** macOS 策略无法强制 → 拒跑；Linux split policy 不支持 → 拒；profile 写了运行时管不了的 write 规则 → 拒；cloud requirements 拉不到且无缓存 → 报错；必需 MCP 起不来 → thread/start 失败；auto-review 的 prompt 构造/解析失败 → fail closed。**这是整个设计里最一致的一条原则。**
2. **边界是明说的，不是暗示的。** 他们花了大量篇幅写「这个东西管不到什么」（代理管不到 6 类流量、profile 管不到 5 类 surface、requirements 管不到 cloud、compliance log 不是完整审计）。代价是文档极其啰嗦，但比「让用户以为全覆盖」诚实得多。
3. **代价被显式推给用户承担。** 磁盘无上限、审计不完整、云端无法接力、模型可能出错（「Always review answers and diffs」）—— 这些都不是被隐藏的缺陷，是被写进文档的已知代价。

}
match approval_policy {
    AskForApproval::Never => Decision::Allow,        // 靠沙箱兜底
    AskForApproval::UnlessTrusted => Decision::Prompt,
    AskForApproval::OnRequest | Granular(_) => match file_system_sandbox_policy.kind {
        Unrestricted | ExternalSandbox => Decision::Allow,
        Restricted => {
            // In restricted sandboxes, do not prompt for non-escalated,
            // non-dangerous commands; let the sandbox enforce restrictions without a user prompt.
            if sandbox_permissions.requests_sandbox_override() { Decision::Prompt } else { Decision::Allow }
        }
    },
}
```

→ **在 `workspace-write` + `on-request` 下，绝大多数未知命令既不弹窗也不被拦，直接在沙箱里跑。**

### ✅ #3：落盘时机

`rollout/src/recorder.rs`：后台 tokio task + `mpsc::channel::<RolloutCmd>(256)`，命令 `AddItems|Persist|Flush|Shutdown|Discard`。每行：

    let mut json = serde_json::to_string(item)?;
    json.push('\n');
    self.file.write_all(json.as_bytes()).await?;
    self.file.flush().await?;

}
```

## 六、一句话总结这份补遗改变了什么

主报告把 Codex 的审批体系写成了「有一套命令安全判断 + 沙箱兜底」。**源码显示它已经放弃了命令安全判断** ——
白名单式的 `is_known_safe_command` 被删了，留下的只是一个仅认 `rm -f` 的黑名单。
**现在 Codex 的全部赌注是「沙箱边界 + 越界才审批 + 越界审批可交给另一个模型」，而不是「识别哪些命令安全」。**
配套的三条硬不变量（deny-read 存在则永不脱沙箱、子 agent 权限取交集、平台管不了就拒跑）是这个赌注成立的前提 ——
它们在代码里都是显式的、带注释说明动机的，这比文档里任何一句话都更能说明这套设计真正在保护什么。
