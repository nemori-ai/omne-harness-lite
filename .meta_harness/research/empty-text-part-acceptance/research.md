# 「图片＋空文本段」的用户消息经 OpenRouter 会不会被拒

- 调查对象与日期：OpenRouter Chat Completions 上本仓库 official 目录里声明图片输入的 31 条路由（各钉一个供应商、不回退），实测窗口 2026-10-02T16:59:56Z–17:09:23Z；
  本仓库 `73fbfd5ff` 的 `pi-ai-transport` 投影与计量器；上游 pi `1b6ddca8`（#9797 的修复）。
- 消费者：本仓库 [issue #50](https://github.com/nemori-ai/omne-harness-lite/issues/50) 的第二项待办——投影要不要升版（窄修复提案、D-115）；
  [pi-ai-transport 实现节点](../../design/realization/packages/model/pi-ai-transport/README.md)。
- 最近核对：2026-10-02 / 上述窗口与版本。
- 当前结论：31 条里只有 Kimi K3、Kimi K2.7 Code、GLM-5.3 Flash 三条拒收，都是流开始前的 HTTP 400，空文本段在图片前后结果一样；
  生产路径上三条里只有两条 Kimi 真能发出这种消息，GLM-5.3 Flash 在本地计量时就因图片被拒。被拒请求不计费（第 3 轮后补读一次余额判定）。
  实测总花费 0.2320266 美元（不是三轮余额差之和 0.2004），远低于负责人定的 5 美元上限。纯文本里的空文本段、历史位置上的空文本段都没有测。

## 问题与区分条件

本仓库 `plan.ts` 的 `parts()` 把可见文本块原样投成 `{type:'text', text}`，不滤空串，而规格允许文本块为空串（[E7](evidence.md#e7-仓库现状投影与-parts-不滤空串)）；
上游 pi 因直连 Z.AI 拒收这种段，在 0.87.1 起滤掉了用户消息里的空串文本段（[E10](evidence.md#e10-上游-pi-9797-与修复提交)）。issue #50 要知道的是：经 OpenRouter、在本仓库已登记的路由上，这样的请求会不会被拒，被拒时是什么样子。

判断一条路由「因为空文本段而拒收」，要同时满足：

1. 同一路由、同一张图、只差一个空文本段的对照请求被接受——否则拒收可能来自图片或路由本身；
2. 路由钉死单一供应商、不回退——否则拒收与接受可能出自不同的上游；
3. 拒收的形态（HTTP 状态、流内还是流前、错误体在哪）要照录，因为生产代码按形态分类处理。

此外还要区分：上游拒收，与生产路径上**真能把这种消息发出去**，是两件事——本地计量器或缓存选靶可能先拦下。

本轮**不**回答：投影该不该升版、怎么滤；纯文本数组里的空文本段、历史位置上的空文本段、字符串形式的空内容会怎样；生产里哪些入口会产出空文本块。

## 当前结论

### C-1 31 条声明图片输入的路由里，只有 Kimi K3、Kimi K2.7 Code 与 GLM-5.3 Flash 拒收「图片＋空文本段」

**事实。**三轮共发 97 个请求，覆盖 31 条路由 × A1 `[image, text:'']`、A2 `[text:'', image]`、B `[image]` 共 93 个格子（[E2](evidence.md#e2-三轮实测的运行参数范围与停机原因)）。
`moonshotai/kimi-k3`（`moonshotai/mxfp4`）、`moonshotai/kimi-k2.7-code`（`moonshotai/int4`）、`z-ai/glm-5.3-flash`（`z-ai/fp8`）三条的 A1、A2 都是 HTTP 400，同路由的 B 都被接受；
其余 28 条——OpenAI 12 条、Anthropic 4 条、DeepSeek V4.1 Flash、Google 2 条、xAI 2 条、Qwen 6 条、GLM-5.3 FlashX——三种请求全部被接受（[E3](evidence.md#e3-逐路由的结果矩阵)）。
同一供应商 Z.AI、同一量化端点 `z-ai/fp8` 下，GLM-5.3 FlashX 接受、GLM-5.3 Flash 拒收。

**推断。**拒收跟着模型（或它背后的服务实现）走，不跟着供应商走：Z.AI 一家里一收一拒。

- 适用范围：E1 的请求形状——恰一条用户消息、一张 99 字节内联 PNG、恰一个空文本段、`max_tokens:64`、流式、无 system 与 tools；每个格子一次样本；只在这 10 分钟窗口内成立。
  「接受」只说明协议层面收下了（HTTP 200、流正常收尾、有 `usage.cost`）：grok 两条路由连对照 B 的输出都在描述图里没有的东西，本轮不支持「grok 看到了图」。
  路由身份只核到响应里的供应商展示名，量化后缀没有回显。
- 代价与不适用：不覆盖纯文本数组里的空文本段、历史位置上的空文本段、多个空文本段、字符串形式的空内容；不覆盖没有登记图片输入的路由。
- 来源：E2、E3。
- 最近核对：2026-10-02 / 实测窗口。

### C-2 三条的拒收都是流开始前的 HTTP 400，上游原文只在 error.metadata.raw 里；Moonshot 点名空文本，Z.AI 只给通用的 1210

**事实。**六个被拒请求都是非 SSE 的 JSON 错误体，`error.code` 400、`error.message` 是「Provider returned error」，上游原文在 `error.metadata.raw`；没有 `usage`、没有生成 id、没有带内错误（[E4](evidence.md#e4-六个被拒请求的原文)）。
Moonshot（Kimi 两条）的原文是 `{"error":{"message":"Invalid request: text content is empty","type":"invalid_request_error"}}`；
Z.AI（GLM-5.3 Flash）的原文是 `{"error":{"code":"1210","message":"Invalid API parameter, please check the documentation."}}`，另有 `metadata.provider_error_code: "1210"`。
pi #9797 报告直连 Z.AI 的 GLM-5.3 Flash 得到的也是 1210（中文消息「API 调用参数有误，请检查文档。」）（[E10](evidence.md#e10-上游-pi-9797-与修复提交)）。
OpenRouter 文档说供应商错误在 `error.metadata` 里带 `error_type`、上游错误码在 `provider_code`；这六个错误体里两样都没有（[E11](evidence.md#e11-openrouter-文档对错误体与余额接口的说法)、[冲突与不一致](evidence.md#冲突与不一致)）。

**推断。**Z.AI 的 1210 是通用参数错误，单看错误体分不出是空文本段引起的；本轮把它归因到空文本段，靠的是对照 B，不靠文字。

- 适用范围：这三条路由、E1 的请求形状、2026-10-02 当天的 OpenRouter 错误体。
- 代价与不适用：本轮没有看 `pi-ai-transport` 怎样把流前 400 映射成运行时的错误分类。
- 撞上这条事实会怎样：按文档读 `error.metadata.error_type` 或 `provider_code` 来分类的代码，在这六种错误上拿不到值；要认出「空文本被拒」，只能读供应商各自的 `metadata.raw`，而 Z.AI 那一条的文字不点名原因。
  文档说流前错误在开了回退时可能被静默改投别的供应商；生产计划体与探针一样钉 `allow_fallbacks:false`（`plan.ts:260`），所以错误会直接回到调用方。
- 来源：E4、E10、E11。
- 最近核对：2026-10-02 / 实测窗口。

### C-4 被拒请求不计费：三轮收尾读数判定不了，第 3 轮后补读一次判定

**事实。**
- 六个被拒请求的响应里没有 `usage`，探针记为「费用未报」（[E4](evidence.md#e4-六个被拒请求的原文)）。
- 被接受的请求最终按流里报的 `usage.cost` 精确入账：第 1、2 轮收尾读数各缺一截，缺的恰是该轮末尾一串请求的流报费用之和；下一轮开跑前的读数把这一截补齐，分毫不差（[E5](evidence.md#e5-余额读数与流里报的费用对账)）。
- 余额接口滞后：三轮收尾读数时，最后约 40–57 秒内结束的请求都还没入账（各轮区间见 E5）。OpenRouter FAQ 说余额接口是「live information」（[E11](evidence.md#e11-openrouter-文档对错误体与余额接口的说法)）。
- 第 3 轮收尾读数时，缺的是 #23 起的整串请求；六个被拒请求（#25–#32 里的六个）全部落在这一串里，所以三轮收尾读数判定不了。
- 2026-10-02T17:40:42Z（第 3 轮结束约 31 分钟后）补读一次：`total_usage` 为 13340.988396359，恰等于「第 3 轮开跑前读数＋第 3 轮全部被接受请求的流报费用」，即被拒请求不计费时的预期值，分毫不差（[E5](evidence.md#e5-余额读数与流里报的费用对账)）。
- pi #9797 的报告人称直连 Z.AI「Nothing is billed」（[E10](evidence.md#e10-上游-pi-9797-与修复提交)）；OpenRouter 文档两页里没有找到「请求被拒是否计费」的明文（E11）。

**推断。**被拒请求不计费。这个判断要求 17:09:23Z 之后账户没有别的用量——若有，读数会高于预期值而不是恰好相等，恰好相等的巧合需要别处用量与被拒请求的费用正好抵消，不成立。

- 适用范围：OpenRouter 账户余额接口在 2026-10-02 的表现；滞后秒数是三次读数推出的区间，不是接口承诺。
- 代价与不适用：「按请求顺序入账」是从三次缺口都恰为末尾一串推出来的，不是接口说明。
- 撞上这条事实会怎样：拿「收尾余额差 − 流报费用」判断有没有隐性计费，在读数滞后时会得到负数或零，读起来像「没有多收」，实际只是还没入账——探针 `summary.md` 自己的提示行也写了要稍后再读。
- 来源：E4、E5、E10、E11。
- 最近核对：2026-10-02T17:40:42Z / 补读余额。

### C-5 生产路径上，三条拒收路由里只有两条 Kimi 能把末条「图片＋空文本」发上线

**事实（仓库 `73fbfd5ff`，静态读）。**
- 投影修订号是 `openrouter-input-projection/3`（`projection.ts:26`）；`parts()` 把可见文本块原样投成 `{type:'text', text}`，不滤空串（`plan.ts:99`）；规格明说文本块可以是空串（[content-blocks v3 S-8](../../design/spec/data/content-blocks/v3/contract.md#s-8-文本块与来路标记)）（[E7](evidence.md#e7-仓库现状投影与-parts-不滤空串)）。
- 发送前的计量器（[E9](evidence.md#e9-仓库现状哪些路由的计量器在发送前拒收图片哪些放行)）：Kimi 两条的计量器收内联图片，也收任意字符串的文本段，空串在内（`moonshot.ts:183-201`）；
  GLM-5.3 Flash 的计量器只收文本段，遇到图片段即 `unavailable`（`zai-glm52.ts:58-68`、`zai-glm53.ts:34-37`，测试 `zai-glm53-meter.spec.ts:178-191`），计划随之以 `invalidInput`／`input_size_unavailable` 在发送前拒绝（`calibration.ts:382-383`、`plan.ts:393-398`）。
- 其余路由：OpenAI 12 条、DeepSeek V4.1 Flash、Qwen3.8-27B 的计量器同样放行图片＋空文本，而这 14 条在实测里都接受；Google 2 条、xAI 2 条、Qwen 商业 5 条、GLM-5.3 FlashX 的计量器在发送前拒收任何图片。
- Anthropic 4 条：缓存只允许 `last_message` 一种断点，末条用户消息既没有非空文本段、又不全是图片时选不到靶，计划在发送前得 `unavailable`（[E8](evidence.md#e8-仓库现状anthropic-末条的缓存选靶)，`plan.ts:344-345`）；
  同样的消息在非末条位置过得了缓存选靶与计量器（`input-meters/anthropic.ts:219-243`）。实测里 Anthropic 4 条三种请求都接受。

**推断。**
- 三条拒收路由里，生产路径能撞上上游 400 的只有 Kimi K3 与 Kimi K2.7 Code：一条末尾用户消息若是「图片＋空文本块」，计划会成立、请求会发出、上游在流开始前回 400。
  GLM-5.3 Flash 在生产路径上发不出带图片的消息，所以撞不上本轮测到的那种拒收。
- 被拒的消息留在会话里时，之后每一次带上它的请求是否也被拒，取决于上游是否校验历史位置——pi #9797 描述直连 Z.AI 正是如此；Kimi 在历史位置的行为本轮没有测。

- 适用范围：仓库 `73fbfd5ff`；只核到计量器与缓存选靶这两关，没有对任何路由实际执行 `planRequest`；输入上限、图片预处理等其它检查未逐条过。
- 代价与不适用：GLM-5.3 Flash 的计量器收纯文本数组（`zai-glm52.ts:58-68` 把各文本段拼起来，空串也收），按计量器代码，`[text:'a', text:'']` 一类的消息能通过计量并发出；Z.AI 对这种不带图片的空文本段收不收，本轮没有测。其它在发送前拒收图片的路由同样如此。
- 撞上这条事实会怎样：把上游拒收清单直接当成生产风险清单，会把 GLM-5.3 Flash 算进去（生产发不出带图片的消息），又看不到它在纯文本路径上的未知；
  反过来，Anthropic 末条被本地拒为 `unavailable`，原因是缓存选不到靶，不是上游会拒——上游三种形状都接受。
- 来源：E7、E8、E9、E10，以及 C-1。
- 最近核对：2026-10-02 / `73fbfd5ff`。

### C-6 本次实测总花费约 0.23 美元，三轮余额差之和 0.2004 漏算了每轮末尾未入账的部分

**事实。**三轮余额差分别为 0.084710000、0.069582100、0.046117490，合计 0.200409590；三轮流报 `usage.cost` 合计 0.2320266；
从第 1 轮开跑前到第 3 轮收尾后，`total_usage` 一共涨了 0.230174090（[E5](evidence.md#e5-余额读数与流里报的费用对账)）。
第 1 轮开跑前到第 3 轮开跑前之间，账户的涨幅与本探针的流报费用逐分对上，没有别的入账。负责人定的上限是 5 美元。
探针的预留上限按轮计（4.5、4.0、4.0 美元），不跨轮累计；三轮实际预留合计 1.780963785 美元（[E2](evidence.md#e2-三轮实测的运行参数范围与停机原因)、三轮 `summary.md`）。

17:40:42Z 补读时 `total_usage` 比第 1 轮开跑前涨了 0.2320266，与三轮流报费用之和相同。

**推断。**本次真实花费 0.2320266 美元，被拒请求不另计（C-4），不到 5 美元上限的 5%。

- 适用范围：本账户在实测窗口内的读数。
- 代价与不适用：三轮余额差之和 0.2004 这个口径，在读数滞后时系统性偏低，偏低的量就是每轮末尾还没入账的那一截。
- 来源：E2、E5。
- 最近核对：2026-10-02 / 实测窗口。

### C-7 两次中途停机都因为计费的输出 token 远超 max_tokens；-pro 单价与登记一致，只有 grok-4.7 单价更高

**事实。**两次停机都是探针的「单个请求实报费用超过它自己的预留」规则触发：第 1 轮 `gpt-6-luna-pro` A2 实报 0.0002768、预留 0.0002755；第 2 轮 `grok-4.7` A2 实报 0.01073、预留 0.0105856（[E2](evidence.md#e2-三轮实测的运行参数范围与停机原因)）。
91 个被接受的请求里，86 个的流报费用精确等于登记单价乘上报 token；不等的 5 个全是 `grok-4.7`，它的输出单价是 6e-6（登记 4.8e-6），输入另有缓存折扣（[E6](evidence.md#e6-两次中途停机的费用构成)）。
`max_tokens` 设为 64，OpenAI `-pro` 路由的 `completion_tokens` 是 143–316、xAI 两条 424–1945、Qwen3.8-27B 526–622，多出的主要是推理 token；其余路由除 `qwen3.7-flash`（65）外都不超过 64。

**推断。**按「输入字节＋固定额度、输出按 `max_tokens`」估的预留，对推理 token 不受 `max_tokens` 约束的路由会偏低；本轮靠「发完超支的那一条就停」把超支限制在单个请求上（两次各超 0.5% 与 1.4%）。

- 适用范围：只观察了 `max_tokens:64` 一种取值。
- 代价与不适用：本会话交给起草的说法是「`-pro` 路由与 grok 的实价高于登记价」；按原记录，`-pro` 不成立，只有 `grok-4.7` 成立（[冲突与不一致](evidence.md#冲突与不一致)）。
- 来源：E2、E6。
- 最近核对：2026-10-02 / 实测窗口。
