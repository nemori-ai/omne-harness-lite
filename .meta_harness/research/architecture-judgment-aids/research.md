# 哪些方法与工具能辅助架构判断，在本仓库上各自受什么限制

- 调查对象与日期：辅助架构判断的方法（结构度量、对照类方法、历史挖掘、设计期问法、度量批评）与 TS／Node monorepo 上的现成工具，2026-10-02；
  本仓库读数取自主线 `6f3cefa39`（`a68f1558b` 在 `packages/`、`apps/` 下与之相同）。
- 消费者：#53／#46 合并方案的阶段 3（Cordis 集成约定）、阶段 5（评审判据与提案模板）、阶段 6a 与 7（反射对照与符合性读数）、阶段 8a（试点）。
- 最近核对：2026-10-02 / 主线 `a68f1558b`。
- 当前结论：拿意图对照实现的方法（反射模型）能报出结构度量报不出的「缺失」，本仓库的意图写在实现映射节点里但没有机读形状；
  只看 import 图的度量在依赖注入装配下有已知盲区，而本仓库的装配边又有一部分同时是 import 边；历史侧数据太薄，撑不起共变分析；
  设计期问法证据弱、解释力强；没有现成工具理解 Cordis 装配。

## 问题与区分条件

函数级读数（圈复杂度、CRAP）量不到领域划分、抽象与分层是否合理。要区分的是：哪些方法给出的是**可回指意图的问题**、哪些只给出**分数**；
每种方法在本仓库的条件下——TS pnpm monorepo、约 50 个成员、契约先行、实现映射节点、Cordis 插件与服务装配、架构归人而 agent 只评审——
还剩多少证据力，要付出什么代价。

会改变边界的观察：意图侧有没有机读形状；装配边是否落在 import 图之外；历史有多少可用事务；方法本身的实证级别。

## 当前结论

### 拿意图对照实现的反射模型能报出「缺失」，只看结构的度量报不出

反射模型（Murphy、Notkin、Sullivan，FSE 1995／TSE 2001）以「高层模型＋映射＋从源码抽出的关系」为输入，把每条高层边标成三态：
收敛（意图有、实现有）、偏离（实现有、意图没有）、缺失（意图有、实现没有）。结构度量（Martin I、DSM 传播成本、Decoupling Level 等）
只读实现一侧，没有「意图有而实现没有」这一态。

- 适用范围：方法的证据级别为 C——Microsoft 用于约 120 万行 C 代码的 Excel 重构、Testo AG 的工业转移等案例；没有对照实验。
- 代价与不适用：
  - **反面证据**：Rosik 等 2011 在 IBM Dublin 两年的案例里发现，小型非正式团队「检测到不一致并不足以促使其被移除」，反射建模还「掩盖了部分不一致」（R38，摘要）；
    Ali 等 2018 的从业者调查列出四个障碍：后果难量化、对客户不可见、不愿意修、觉得正式工具代价高（R39）。
  - 映射质量决定结果：映射粗了，偏离会被吞成收敛（R38）。
  - 抽取器漏边会制造假「缺失」：动态 `import()`、字符串拼出的服务名、只在运行期决定的装配都是漏边源（推断，未在本仓库实测）。
  - 要有人维护映射与意图模型，意图一旦过时，报告就成了噪声。
- 撞上这条事实会怎样：报告没有指定的接收者与处置规则时，偏离会累积而不被处理——这正是 R38 观察到的情形。
- 来源：[E1](evidence.md#e1两份原始调研稿)（methods 稿 §2.5，R32～R39）。
- 最近核对：2026-10-02。

### 本仓库的意图写在实现映射节点的正文里，没有机读形状

52 个实现映射节点逐个写了「兑现哪些契约、落成哪些 Cordis 插件、提供和注入哪些服务」，这是反射模型最贵的那份输入；
但装配意图只在各节点 `design.md` 的表里，表头各节点不统一，`bindings.yaml` 的顶层键只有 `version`、`node`、`kind`、`bindings`，
检查器读的机读字段只有 README 的 `kind`、`源码位置`、`交付面` 与 `bindings.yaml` 的三个键。另有 9 个节点没有对应的包，
25 个有包节点的 README 仍含「尚未建包」字样。

- 适用范围：主线 `a68f1558b` 上的 `.meta_harness/design/realization/`。
- 代价与不适用：意图侧要被工具读，得先有统一的机读形状；从正文表格抽取意图会把各节点不一致的写法原样带进比对结果。
  「尚未建包」的统计是子串匹配，不区分现行状态行与历史注记。
- 撞上这条事实会怎样：拿现在的节点直接做对照，有包节点会全部落进「没有声明」，三态里的「收敛」「偏离」无从计算；
  源码位置写错的节点会被误报成「意图有、实现没有」。
- 来源：[E8](evidence.md#e8实现映射节点作为意图的现状)。
- 最近核对：2026-10-02 / `a68f1558b`。

### Cordis 装配边有一部分同时是 import 边：32 对中有 14 对

在成员 `src/` 里，被 `ctx.provide` 的服务键 24 个，`inject` 声明合成 32 个「注入方 → 提供方」成员对，其中 14 对同时也是 import 边。
原因是服务接口类型与服务键常量定义在提供者自己的包里，消费者为取它们而 import 提供者；`STORAGE_SERVICE = 'storage'` 在三个包里各定义了一份。
其余 18 对里 15 对指向 `infra/storage-sql` 或 `infra/clock`，这两个成员只经装配被依赖。

这条更正了两份原始调研稿的说法：tools 稿 §0「这 32 对没有一对在 import 图里出现」（它的 import 图因部分成员没构建 `dist/` 而缺边），
methods 稿 §0「消费者在编译期 import 的是 `core` 里的契约，不是提供者」（它没有读仓库）。

- 适用范围：主线 `6f3cefa39` 的成员 `src/`；数字出自正则粗读，量级可信，精确值要以语法树抽取为准。
- 代价与不适用：只读 import 图会把这 14 对当成普通的编译期依赖，看不出它们其实是服务依赖；只读装配图又会漏掉另外的编译期耦合。两张图要分开抽、分开对照。
- 撞上这条事实会怎样：以「服务依赖都不在 import 图里」为前提设计的对照，会把这 14 对同时报成「import 偏离」与「装配收敛」，读数自相矛盾。
- 来源：[E4](evidence.md#e4cordis-注入边与-import-边的重叠更正原稿)。
- 最近核对：2026-10-02 / `6f3cefa39`。

### 只看 import 图的结构度量，在依赖注入装配下有已知盲区

Decoupling Level 的作者自列效度威胁：只在 C、C++、C#、Java 上验证，依赖靠静态抽取，对主要依赖无法静态检测的系统可能算不准（R24，原文）；
传播成本对规模敏感，108 个开源项目里文件数大于 1000 的项目 70% 的 PC 低于 20%，「架构剧变时 PC 可以几乎不变」（R24）；
ABB 的经验是高扇入的工具类文件会形成巨大的设计规则空间、扭曲根因分析，教训是把它们排除（R26，主线核过原文第 854～858 行）；
Martin 的 D 缺「易变性」维度，不易变的组件落在「痛苦区」并无害处（R3，二手读书笔记）。

- 适用范围：证据级别 B（多出自方法提出团队或其合作企业；Martin 的 A／D 实证结果不一致，R5）。
- 代价与不适用：本仓库 `core` 的契约包在结构上正是高扇入节点；成员级只有约 50 个节点，单值度量对单条边敏感（推断）。
  这些度量也不指出「问题在哪」，只给出一个数。
- 撞上这条事实会怎样：把 PC、DL 或 D 当目标值去压，会奖励「把依赖改成装配期解析」这类让静态图变好看、实际耦合不变的改法。
- 来源：[E1](evidence.md#e1两份原始调研稿)（methods 稿 §2.1～§2.4）、[E2](evidence.md#e2主线对关键文献的抽核)。
- 最近核对：2026-10-02。

### 共变与缺陷相关的证据强，但本仓库的历史撑不起共变分析

变更耦合与缺陷正相关有多团队实证（证据级别 A：D'Ambros 等 2009、Cataldo 等 2009、Kirbas 等 2017，R44～R46）；
Clio 一类「结构上应一起变 vs 历史上实际一起变」的差异检测有原作者团队的案例证据（R29）。但本仓库主线首父链上碰过 `packages/` 或 `apps/` 的事务只有 20 个；
提交是 squash 合并，一个 PR 一个事务；code-maat 默认的 `--max-changeset-size 30` 会把大 PR 整体丢掉。

- 适用范围：主线 `6f3cefa39` 的历史；共变强度本身本 topic 没有测。
- 代价与不适用：
  - 纠缠提交：最多 15% 的修缺陷提交含多个纠缠改动（Herzig & Zeller 2013，R47，元数据）；squash 合并下共变对数随 PR 大小平方增长（推断）。
  - 挖掘研究长期假设版本痕迹出自专业开发者，agent 留下的痕迹经常不满足这个前提（Bock、Mockus、Vasilescu 2026，R48，摘要）。
  - 处在依新规格直接破坏性重构的阶段，共变里很大一部分是有意的全局迁移（推断）。
  - 有利条件：提交带 `Agent-Role` trailer，squash 前的提交可从 `refs/pull/N/head` 取回（2026-10-02 有 48 条）。
- 撞上这条事实会怎样：在 20 个事务上算出的共变强度，任何一个大 PR 都能左右结果，读数不稳定。
- 来源：[E1](evidence.md#e1两份原始调研稿)（methods 稿 §2.6～§2.7）、[E3](evidence.md#e3工具试用本机只读)、[E7](evidence.md#e7历史侧数据量)。
- 最近核对：2026-10-02 / `6f3cefa39`。

### 设计期问法有解释力而缺实证；质量属性场景只有案例证据

Khononov 的耦合平衡（集成强度 × 距离 × 易变性，`BALANCE = (STRENGTH XOR DISTANCE) OR NOT VOLATILITY`）、connascence、Parnas 的「模块隐藏哪项决定」
都是证据级别 D：检索未发现针对它们本身的实证；Parnas 有 Sullivan 等 2001 的实物期权形式化解释（R14）。
SEI 的质量属性场景（刺激源、刺激、环境、制品、响应、响应度量）与效用树是 C：Bass 等 2007 分析 18 次评估，「遗漏」类风险主题是「误作」类的两倍（R76）；
中型完整 ATAM 约 70 人日、要多类干系人在场（R74）；Capilla 等 2025／2026 以学生为对照，LLM 生成候选风险多于人，但评估上不一定更好（R81，证据很弱）。

- 适用范围：方法层面的证据；它们在本仓库的效果没有测量。
- 代价与不适用：
  - 三个维度都是定性等级，不同评审者给出的等级可能不一致（推断）；易变性要按领域评估，需要产品侧输入，拿提交历史代替会混入偶然易变性。
  - Löwy 的组件分类法（Manager／Engine／ResourceAccess）预设分层服务风格，与「契约＋插件／服务＋依赖注入」的组合式装配不同构（推断），书中无实证（R68）。
  - 完整 ATAM 的干系人前提在「一个负责人＋若干 agent 角色」的结构下不成立。
  - Khononov 的官方 Claude Code 插件许可为 CC BY-NC-SA 4.0（R60）。
- 撞上这条事实会怎样：把 D 级问法写成判决（「这是错的」）而不是问题，会把评审者的主观等级当成事实；场景写成「高可用」这类形容词，就无从评估。
- 来源：[E1](evidence.md#e1两份原始调研稿)（methods 稿 §2.8～§2.12）。
- 最近核对：2026-10-02。

### 度量与缺陷的相关大多被规模解释，度量变成目标就会失真

El Emam 等 2001、Gil & Lalouche 2017（26 个度量的「效度」几乎可由它与规模的相关预测，R² 有时达 0.97）、Sjøberg 等 2013（调整规模与变更次数后 12 种坏味道无一与工作量显著相关）
构成 A 级证据（R88～R90）；过程度量优于产品度量（R91）。Goodhart 1975 与 Campbell 1979 说明量化指标一旦用于控制就会被腐蚀（R85、R86）；
华为 SAI 的实践总结是要引导团队关注每项度量背后的问题，而不是分数本身（R27，主线核过原文第 23～25 行）。
ImpossibleBench 报告前沿编码 agent 频繁利用与规格矛盾的测试（R95，摘要；具体比例未核实）。

- 适用范围：A 级部分是多团队实证；agent 钻营的那条证据只读到摘要。
- 代价与不适用：任何读数都要带规模对照与趋势才有意义；硬线会被「满足字面」，门禁规则的变更本身要受评审。
- 撞上这条事实会怎样：合成一个架构分数并设阈值，实施者（尤其 agent）会去改让分数变好的东西，而不是设计本身。
- 来源：[E1](evidence.md#e1两份原始调研稿)（methods 稿 §2.14）、[E2](evidence.md#e2主线对关键文献的抽核)。
- 最近核对：2026-10-02。

### 现成工具都不理解 Cordis 装配，也没有确定性的「意图对实现」比对工具

2026-10-02 核过的工具里，没有一个能抽 Cordis 的 `provide`／`inject`／插件装配。接近「意图对实现」的只有三条路，各缺一块：
dependency-cruiser 的配置是 JS，可从外部模型生成 `allowed` 规则，但只抓「代码多出的边」，合成边不参与规则判定（推断）；
Nx 的 `createDependencies` 能往项目图里加边，但对这些边做边界检查要 Nx Enterprise 的 Conformance；
ArchUnitTS 的 `adhereToDiagram` 能按 PlantUML 核对 import，但在本仓库上跨成员 import 落到 `dist/*.d.ts`，试用结果不可信；
Erode 用 LLM 读 diff 判漂移，结果不确定，模型请求不经 OpenRouter。TS 生态里没有在维护、开源、支持 TS 的 DSM 工具；
LikeC4 能从生成的 `.c4` 出 Mermaid 与站点，单独维护它的模型会在实现映射之外多出一份架构描述。
本仓库现有的 `og-s42-dynamic-resolve` 是只认一个服务键的词法正则，产出只有违规列表，不是抽取器；可复用的是 `tools/ts-checks/src/syntax.ts` 的语法树入口。

- 适用范围：E3 所列版本在 2026-10-02 的状态；商业工具（DV8、Lattix、SonarQube 架构管理）对 TS 的支持未核实。
- 代价与不适用：Cordis 装配边的抽取与意图比对只能自己写，要自己承担漏边与误报；dependency-cruiser 要额外配 `exportsFields`／`conditionNames` 才能解析跨成员 import；
  code-maat 是 GPL-3.0，只适合当外部进程跑。
- 撞上这条事实会怎样：把 import 图工具的读数当成依赖全貌，会漏掉 18 对只经装配的依赖（见上一条结论）。
- 来源：[E3](evidence.md#e3工具试用本机只读)、[E5](evidence.md#e5og-s42-规则的性质)、[E6](evidence.md#e6ctxprovide-的分布与运行期读-inject)。
- 最近核对：2026-10-02。

### 成员内部有文件级运行时环，现有的成员级检查看不到

dependency-cruiser 与 skott 在 2026-10-02 的主检出上一致报出 10 条文件级运行时环（算上 type-only 共 34 条），落在 `core/tool-definition` 与 `model/pi-ai-transport` 两个成员内部；
本仓库现有检查只在成员级查环。

- 适用范围：当天那棵树；条数会随代码变化。
- 代价与不适用：环的危害程度不一，Oyetoyan 等 2015 发现子类型知识与环在包树里的位置都区分不出「关键环」与「无害环」（R11）；
  dependency-cruiser 一次运行约 5 s、峰值约 430 MB。
- 来源：[E3](evidence.md#e3工具试用本机只读)、[E1](evidence.md#e1两份原始调研稿)（methods 稿 §2.2）。
- 最近核对：2026-10-02。
