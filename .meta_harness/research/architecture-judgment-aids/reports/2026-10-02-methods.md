# 辅助架构判断的方法调研

> **入库说明（2026-10-02）**：这是原始调研稿，原样保留（原件 sha256 `af2162e8…6cde2d31`，全值见 [evidence.md](../evidence.md)）。稿中含方案建议（§0、§4～§6），
> 那是调研者当时的看法，不是本 topic 的结论；关于本仓库的事实以 [research.md](../research.md) 为准——
> 尤其 §0「消费者在编译期 import 的是 `core` 里的契约」一句与本仓库不符，更正见 research.md。

调研日期：2026-10-02 · 性质：只读方法调研，不改仓库文件 · 读者：负责架构判断的人，以及只做评审与反驳的 agent

## 0. 先看结论

**最值得优先引入的四项（外加一项可选）**

1. **反射模型（reflexion model），用「实现映射 + 分组规则」充当意图模型。**同时抽两张图：编译期 import 图，和装配期 `inject`→`provide` 的解析图。逐条报出「收敛／偏离／缺失」。
2. **结构与历史的差异检测。**沿用 Clio 和热点模式（hotspot patterns）里的模块化违例（modularity violation）与不稳定接口（unstable interface），叠加在现有的成员级共变数据上，把「不稳定契约包」单独列出来。
3. **质量属性场景 + 效用树。**采用 mini-QAW 或轻量 ATAM 第 5–8 步。agent 提出候选风险、敏感点和权衡点，由人裁决。
4. **耦合平衡评审问法。**以 Khononov 的三维（集成强度、距离、易变性）为主，加上 Parnas 的「模块隐藏哪项决定」，再加 connascence 词汇。给 reviewer 当问法用，不当度量用。
5. （可选）**文件级热点**：变更频率 × 现有复杂度，只用来排序，不设阈值。

**不值得引入的几项**

- Martin 的抽象度 A 与离主序列距离 D：维持现有判断，见 §1。
- Lakos 的 CCD／ACD／NCCD 单值指标。
- 把 propagation cost 或 Decoupling Level 当 KPI，或者为此采购 DV8。
- 完整 ATAM。
- 按作者统计的知识分布与所有权分析。
- 另立一套 C4／Structurizr／LikeC4 模型。
- Löwy 的组件分类法（Manager／Engine／ResourceAccess）。
- 任何复合架构分数。
- 自动聚类式架构恢复。

理由见 §4、§5。

**最要紧的一条适配发现**

在 Cordis 这类 DI／插件内核里，消费者在编译期 import 的是 `core` 里的契约，不是提供者。消费者实际用了哪个提供者，要到装配期按服务名解析时才确定。因此，所有只看 import 图的度量都会系统性地偏斜，包括 Martin 的 I、propagation cost、Decoupling Level 和 Lakos 的 CCD：

- 它们把「大家都依赖 `core`」看成耦合，而这本来就是意图；
- 它们看不见「谁在运行时依赖哪个提供者」。

DL 论文自己也写明：对主要依赖无法静态检测的系统（作者举的例子是面向服务架构），DL 可能算不准［R24］。所以对本仓库，**比较意图与实现的方法（反射模型）、比较结构与历史的方法（共变差异），比任何单一的结构耦合数都更对路**。

## 1. 读法、证据分级与核实说明

### 证据强度分级

本报告自定，用于横向比较。

| 级别 | 含义                                                                                         |
| ---- | -------------------------------------------------------------------------------------------- |
| A    | 多个独立团队的实证，或工业／大样本实证，指向同一结论                                         |
| B    | 有实证，但主要来自方法提出团队或工具厂商；或只是横截面相关；或样本小、结果不一致             |
| C    | 案例研究、经验报告、问卷                                                                     |
| D    | 理论主张或从业者经验，检索未发现系统实证                                                     |

「检索未发现」不等于「不存在」。D 级的意思是：本次检索没找到可引用的实证。

### 核实方式标记

见文末参考文献。

- 〔原文〕：读了全文或摘要原文。
- 〔元数据〕：只经出版方、数据库、检索摘要核对了题名、作者、年份和主要结论。
- 〔二手〕：经读书笔记或报道转述。
- **未核实**：查不到可靠来源，或只有零星转述。

### 关于仓库的事实

关于仓库的事实只取自任务背景，没有读仓库。少数推断另行标出，例如「提交多为 squash 合并」是根据提交标题带 PR 号推断的。

「适配性」指对这类仓库的适配：TS pnpm monorepo，约 50 个成员，`core`→领域与基础设施→`apps`，契约先行，有实现映射节点，用 Cordis 做插件与服务装配，架构归人、agent 只评审。

## 2. 逐项方法

### 2.1 Robert Martin 的包度量（I、A、D）

**回答什么问题：**包与包之间的依赖方向是否「朝稳定的方向」（稳定依赖原则 SDP）；稳定的包是否足够抽象，以便扩展而不必修改（稳定抽象原则 SAP）。

**输入：**包级依赖图（Ca 传入、Ce 传出），以及包内抽象类型的比例。

**产出：**

- I = Ce/(Ca+Ce)；
- A = 抽象类型数／类型总数；
- D = |A+I−1|；
- 「痛苦区」（稳定且具体）与「无用区」（不稳定且抽象）的落点。

来源：Martin 1994［R1］；2002 年成书［R2］；2017 年《Clean Architecture》再述［R3］。

**证据强度：总体 D，A/D 部分为 B（结果不一致）。**

- Martin 的主张本身是理论性的。
- Hyrynsalmi & Leppänen 2009 指出 Martin 的度量缺少理论与实证评估。他们按评估框架审视其理论基础，在 5 个开源项目上做了实验，发现其内聚定义有缺陷［R4］。
- Petrić、Hall、Bowes 2020 在 4 个开源系统上考察 A、I、D 区分有缺陷与无缺陷组件的能力，摘要结论是「architecture has an inconsistent impact on defect-proneness」：
  - 某些项目里结构复杂的组件几乎不出缺陷；
  - 4 个系统中有 3 个关系很强；
  - 作者自己承认还有测试投入等未控制的因素［R5］。
- 检索没有找到「I 或 SDP 违例与缺陷或成本」的独立大样本实证。

**已知的坑与误报：**

- **纯数据契约包会被 D 判进痛苦区。**Martin 在《Clean Architecture》里自己就承认，不易变的组件落在 (0,0) 区是无害的，例如 String；只有易变的组件在痛苦区才有问题［R3，经二手读书笔记核对，原书页码未核实］。换句话说，**D 缺了「易变性」这个维度**。这和 Khononov 的「OR NOT VOLATILITY」是同一个洞见（§2.8）。
- **TS 里 A 的定义含糊（推断）。**接口和类型在运行时被擦除，只含类型的包 A 可能接近 1；以 JSON Schema、常量或校验器形式导出的契约包 A 可能接近 0。两者语义同样「是契约」，A 却截然相反。
- **I 只看 import 图。**在 DI 装配下系统性偏斜，见 §0。
- I 是比值：小包的少量边就会让它剧烈波动。

**适配性：**

- **SDP／I 为中**：已经在用，作为方向传感器有价值，但要读成「问题」而不是「判决」。
- **A／D 为低**：维持「有意不移植」的判断。

**能否吃进意图模型：**不能。更好的替代是在实现映射里给每个成员**声明预期稳定性或易变性**，用它代替 A：

- 「被很多成员依赖」且「声明稳定」：健康。
- 「被很多成员依赖」但「声明易变」或「实测共变频繁」：这才是要问的问题。后一种情形就是 §2.4 的 Unstable Interface。

### 2.2 John Lakos 的分层化（levelization）与 CCD／ACD／NCCD

**回答什么问题：**物理依赖是否无环、可以分出层级；整体耦合有多大，用「每个组件为了测试或链接要连带多少组件」来衡量。

**输入：**组件级（在 C++ 里是文件对）的 depends-on 关系，取传递闭包。

**产出：**

- 层号（level）；
- CCD：所有组件的 DependsOn 之和；
- ACD：CCD/N，即平均每个组件直接加间接依赖多少组件；
- NCCD：CCD 与同规模平衡二叉树的 CCD 之比。大于 1 偏「纵向」，小于 1 偏「横向」［R6，R8］。
- Lakos 2019 年的新书沿用了 levelization 技术与「Level Numbers」等章节［R7］。

**证据强度：**

- 分层化原则本身是 D（理论与经验）。
- 「环有害」这个子命题有 B 级实证：
  - Melton & Tempero 2007 研究了 78 个 Java 应用。规模够大的应用里约 45% 有涉及至少 100 个类的环，约 10% 有涉及至少 1000 个类的环；作者给出证据说明这些环并不源于领域固有的相互依赖［R9］。
  - Oyetoyan、Cruzes、Conradi 2013 发现，缺陷和有缺陷的组件集中在处于环中、或直接间接依赖环的组件上［R10］。
  - Oyetoyan、Dietrich、Falleri、Jezek 2015 发现，环会显著影响环附近类的变更倾向，但子类型知识和环在包树中的位置都不能区分「关键环」与「无害环」，建议重新审视「环一律有害」的看法［R11］。
- CCD／NCCD 作为度量的效度：**检索未发现实证（D）**。

**已知的坑与误报：**

- CCD 是为 C++「链接期与增量回归测试成本」设计的［R6，二手转述］。TS 没有链接期，增量构建与测试由 pnpm、TypeScript 项目引用决定，二者含义不同。
- 单值掩盖位置：知道 NCCD 变大了，却不知道是哪里变的。
- 成员级只有约 50 个节点，NCCD 对单条边非常敏感（推断）。
- 环的有害程度不一，盲目断环可能引入无意义的抽象层［R11］。

**适配性：低到中。**

- 无环与分层这部分，你们已有硬门禁和分层成员图，Lakos 能补的增量很小。
- CCD／NCCD 不建议引入。
- 唯一值得借的是「层号」这个概念：把**意图层号**（core=0、领域与基础设施=1、apps=2 之类）与**实际层号**对照。这其实是反射模型的一个特例（§2.5）。

**能否吃进意图模型：**度量本身不能；层号对照可以。

### 2.3 设计结构矩阵（DSM）与 MacCormack 等的 propagation cost

**回答什么问题：**

- 元素之间的依赖是否呈分块、分层的模块结构；
- 改一个随机元素平均会波及系统的多大比例（propagation cost，PC）；
- 哪些文件处在「核心」（core），即高可见、高被可见。

**输入：**元素级依赖矩阵，通常是文件级，可以加上传递闭包。

**产出：**

- 排序后的 DSM 视图；
- 可见性矩阵；
- PC，即可见性矩阵的密度；
- core／periphery 分类。

**来源：**

- DSM 源于 Steward 1981 的工程管理方法［R12］；Baldwin & Clark 把它用于模块化与「设计规则」理论［R13］。
- Sangal 等 2005 把 DSM 用在软件架构管理上：在矩阵上声明「设计规则」（允许或禁止的依赖），随演化复查［R15］。
- MacCormack、Rusnak、Baldwin 2006 用 DSM 比较 Linux 与 Mozilla。他们发现 Mozilla 首版不如 Linux 模块化，而 Mozilla 有目的的重设计使其显著更模块化，甚至超过了 Linux［R16］。

**证据强度：B。**

- Baldwin、MacCormack、Rusnak 2014 研究了 1286 个软件版本，归纳出 Core-Periphery、Multi-Core、Hierarchical 三类结构，多数系统是 Core-Periphery［R17］。
- MacCormack & Sturtevant 2016 研究了两个规模相近、结构不同的系统（各 2 万多个组件）。两者中紧耦合的 core 组件维护成本都显著更高，「少数组件产生了大比例的系统成本」［R18，〔原文〕摘要］。
- Sturtevant 2013 的 MIT 博士论文基于一家公司 8 个版本，报告架构复杂度差异可对应约 50% 的生产率下降、约 3 倍的缺陷密度和数量级上升的人员流失［R19，〔元数据〕］。
- 这些研究多出自同一研究脉络（HBS／MIT），样本以 C、C++、Java 文件级为主。

**已知的坑与误报：**

- **PC 对规模敏感**：文件越多 PC 越小。Mo 等统计的 108 个开源项目里，文件数大于 1000 的项目有 70% 的 PC 低于 20%，小于 1000 的只有约 48%；而且「架构剧变时 PC 可以几乎不变」［R24，〔原文〕］。
- 传递闭包把「仅类型引用」与「运行时调用」等量计入。在契约先行的系统里，所有成员都会经由 `core` 互相「可见」，PC 被抬高（推断）。
- DI 装配边不在 import 图里，见 §0。

**适配性：**

- **DSM 作为视图与规则载体为中。**50×50 的成员矩阵按意图分组排序后，可以一眼看出越级和反向依赖；矩阵上的「设计规则」与你们的依赖方向规则同构［R15］。
- **PC 作为指标为低。**

**能否吃进意图模型：**DSM 可以。把分组与允许规则画在矩阵上，就是 Sangal 式的规则 DSM。PC 不能。

### 2.4 Cai、Kazman、Mo、Xiao 等：设计规则空间、Decoupling Level、热点模式与架构债务

**回答什么问题：**

- 架构的哪些「设计规则空间」（DRSpace）集中了缺陷与变更；
- 系统能被拆成多少「小而可独立替换」的模块（DL）；
- 哪些文件组构成了可识别的架构反模式；
- 它们的维护成本是多少，也就是架构债务。

**输入：**文件级结构依赖，加上修订历史中的共变，可选加上问题跟踪数据（区分修缺陷与改功能）。

**产出：**

- DRSpace：以「领导文件」为设计规则、按设计规则层级（DRH）分层的 DSM［R21］。
- 热点模式。WICSA 2015 版提出 Unstable Interface 和 Implicit Cross-module Dependency 等［R22］；TSE 版整理为 6 个反模式：Unstable Interface、Modularity Violation Group、Unhealthy Inheritance、Crossing、Clique、Package Cycle［R28］。
- DL 值［R24］。
- 架构债务的成本估计［R25］。
- 相关前作 Clio：比较「按模块结构应当一起变的」与「历史上实际一起变的」，报出模块化违例［R29］。

**证据强度：B（数量多，但几乎都出自同一研究群体及其商业工具）。**

- DRSpace［R21］：在 JBoss、Hadoop Common、Eclipse JDT 上，5 个易错 DRSpace 覆盖了各项目 52%–89% 的缺陷文件［〔二手〕博客转述］。
- 热点模式与反模式［R22，R28］：卷入反模式的文件更易错、更易变，卷入越多越严重；Unstable Interface 与 Crossing 的贡献最大。研究涉及 100 多个开源与工业项目，其中 19 个做了细致分析［〔二手〕］。
- DL［R24，〔原文〕］：
  - 度量了 108 个开源和 21 个工业项目。
  - 在 41 个项目上做了横截面相关：DL 与 6 个共变或共同提交者重叠类维护度量的 Pearson 相关在 −0.61 到 −0.77 之间，强于 PC（0.53–0.68）和 IL。
  - 作者自列的效度威胁：只覆盖 C、C++、C#、Java，不能声称适用于其他语言；依赖靠 Understand 静态抽取；维护度量是代理；没做「先测 DL 再观察后续成本」的前瞻验证。
- Clio［R29，〔原文〕摘要］：在 Hadoop Common 15 个版本、Eclipse JDT 10 个版本上，「数百个」违例后来被开发者认作设计问题或被重构。
- 工业经验报告（C）：
  - SoftServe 案例：3 个问题 DRSpace 共 291 个文件，每年每文件 0.82 个缺陷，项目均值 0.33；估算重构首年投资回报 295%［R23，SEI 博客〔原文〕］。
  - ABB 8 个项目：DL 与 PC 结合行业基准与实践者直觉一致，多数项目据此启动重构［R26，〔原文〕］。
  - 华为 4 年的 SAI 实践［R27，〔原文〕］。
  - 医疗通信产品的纵向研究［R31］。

**已知的坑与误报（多条直接来自作者的经验报告）：**

- **高扇入的工具类或公共文件会形成巨大的 DRSpace**，把健康与易错文件一起圈进去，扭曲根因分析。ABB 经验的教训是把这类文件排除［R26，〔原文〕］。本仓库 `core` 的契约包在结构上正是这类高扇入节点。
- **历史数据质量。**ABB 提供的「良好分支」大多是合并提交，单文件历史很少，需要跨分支收集［R26］。本仓库若多为 squash 合并（推断），每个 PR 只剩一个提交，共变的「事务」粒度变粗，频次变少。
- DL 与 PC 都只基于语法依赖，**好分数不代表健康**；分数好但团队仍然吃力时，要再看反模式［R26］。
- DL 对静态不可见的依赖无能为力［R24］，DI 装配正是这种情况。
- 工具链：DV8 是 ArchDia 的商业产品，有限制文件数的教育版与 14 天试用［R30］。它是否支持 TS **未核实**。常用的开源抽取器 Depends 已知支持 Java、C++、Ruby、Python 等，**未见 TS**［〔元数据〕］。
- DL 等方法有专利，美国专利号 11422800，题为 *Identifying and quantifying architectural debt and decoupling level*［〔元数据〕，权利范围未核实］。

**适配性：中。**

- **反模式的定义高度可借**，尤其是 Unstable Interface 和 Modularity Violation，可以用你们现有的共变数据加依赖图自己实现（§4 的 P2）。
- **DL、PC 和 DV8 工具链的适配性低**：语言不覆盖、DI 不可见、商业工具，50 个成员也太粗。

**能否吃进意图模型：**部分可以。DRH 是从结构里**推断**设计规则，而本仓库的设计规则（`core` 契约、分组方向）是**显式声明**的，可以直接用声明代替推断：

- 「领导文件」= `core` 契约包；
- 「Unstable Interface」= 被多成员依赖、又频繁与依赖者共变的契约包，即「不稳定契约」；
- 「Modularity Violation」= 无声明依赖、无共享契约却持续共变的两个成员。

### 2.5 Murphy、Notkin、Sullivan 的反射模型（reflexion models）

**回答什么问题：**工程师心中的高层模型与源码实际结构在哪里一致、哪里不一致。

**输入：**

1. 高层模型：节点及期望的边；
2. 映射：哪些源码实体属于哪个高层节点；
3. 从源码抽出的关系。

**产出：**每条高层边被标为三态之一：

- **收敛**（convergence）：意图里有，实现里也有；
- **偏离**（divergence）：实现里有，意图里没有；
- **缺失**（absence）：意图里有，实现里没有。

可以下钻到构成该边的具体源码关系。原始论文：FSE 1995［R32］；TSE 2001 扩展版［R33］。

**证据强度：C（案例与工业转移经验），另有一项反面证据。**

- Microsoft 工程师用它辅助 Excel 实验性重构，约 120 万行 C 代码［R34］。FSE 1995 论文获 2011 年 SIGSOFT 回顾影响力奖［〔元数据〕］。
- 扩展：层次化反射模型，用于大系统［R35］。Knodel & Popescu 2007 在 13 个维度上比较了反射模型、关系一致性规则、组件访问规则三种静态合规检查［R36］。Testo AG 的工业技术转移经验与「实时反馈」实验［R37］。
- **反面证据：**Rosik 等 2011 在 IBM Dublin 做了两年的案例研究。在小型、非正式团队里，「检测到不一致并不足以促使其被移除」，而且反射建模「掩盖了部分不一致」［R38，〔原文〕摘要］。
- 实践调查：Ali 等 2018 发现，从业者多用非正式手段保持架构一致。四个障碍是：
  - 难以量化不一致的后果；
  - 不一致对客户几乎不可见；
  - 不愿意修；
  - 觉得正式工具代价高［R39］。

**已知的坑与误报：**

- **映射的质量决定一切。**映射粗了会把偏离吞成收敛［R38］。
- 只报不改等于没报［R38，R39］：要配接收者与处置规则。
- 抽取器漏边会制造假「缺失」。在 TS 里，动态 `import()`、字符串服务名注入、`declare module` 增补都是漏边源（推断）。

**适配性：高。**这是本调研中与本仓库契合度最高的一项，理由有三：

1. 你们已经有机器可读的意图：实现映射节点声明「哪个包兑现哪份契约、插件与服务怎么装配」，分组规则声明方向。反射模型最贵的输入——高层模型加映射——**已经存在**。自动聚类式的架构恢复准确度有限［R40］，你们不必走那条路。
2. 「缺失」这一态正好对应契约先行最怕的失败：节点声称包 X 兑现契约 C，代码里 X 却不引用、不校验 C；或者节点声称 X 提供服务 S，装配里却从没有 `provide(S)`。import 图度量天生看不见缺失。
3. 可以沿你们的追溯链延伸到更多层：产品条款 → 契约（覆盖清单）→ 实现映射节点 → 包 → 代码。每一层都能报三态。

**能否吃进意图模型：能，而且是原生用途。**建议抽**两张实现图**：

- 编译期 import 图；
- 装配期 `inject`→`provide` 的解析图：从 `apps` 装配入口静态读取，或在装配期自省 Cordis 上下文。

两张图分别对照意图。

### 2.6 演化耦合与共变挖掘（logical coupling／mining version histories）

**回答什么问题：**哪些实体「总是一起改」，即使代码里看不出依赖；下一处该改哪里。

**输入：**版本历史，按提交、PR 或时间窗聚合成「变更事务」。

**产出：**共变对或共变集，附支持度与置信度（关联规则）；耦合强度趋势。

**来源：**

- Gall、Hajek、Jazayeri 1998 基于 20 个发布版本的历史检测「逻辑耦合」［R41］。
- Zimmermann 等 2004／2005 的 ROSE 在首个改动后能正确预测 26% 的后续文件；前 3 个建议中含正确位置的概率为 64%［R42，〔元数据〕］。
- Ying 等 2004 的同类工作［R43］。

**证据强度：A。**

- D'Ambros、Lanza、Robbes 2009 在三个大型系统上发现，变更耦合与缺陷正相关，高严重度缺陷尤甚，加入共变信息能改进缺陷预测［R44］。
- Cataldo、Mockus、Roberts、Herbsleb 2009 在两家公司的两个项目上发现，逻辑依赖对失败倾向的影响「与结构依赖互补且显著更相关」［R45，〔元数据〕］。
- Kirbas 等 2017 研究了两个大型工业系统（金融与电信，7 年，17.6 万文件），演化耦合度量与缺陷总体显著正相关［R46］。

**已知的坑与误报：**

- **纠缠提交（tangled changes）：**Herzig & Zeller 2013 在 5 个 Java 项目中发现最多 15% 的修缺陷提交含多个纠缠的改动，平均至少 16.6% 的源文件被错误关联到缺陷报告［R47，〔元数据〕］。大提交、批量重命名、格式化会制造大量伪共变。
- **squash 合并**把一个 PR 的全部改动压成一个事务，共变对数随 PR 大小平方增长（推断）。要按 PR 事务计数、过滤超大事务，或者用时间窗。
- **agent 产生的历史违背了经典挖掘的前提。**Bock、Mockus、Vasilescu 2026 指出，挖掘研究长期假设版本痕迹出自专业开发者；agent 用同样的工具留下痕迹后，这个前提经常不成立，已有结论需要重验［R48，〔原文〕摘要］。本仓库提交带 `Agent-Role` trailer，可以按角色分层统计，算是罕见的有利条件。
- **处在「依新规格直接破坏性重构」的阶段时，共变很大一部分是有意的全局迁移**，不代表结构问题（推断）。

**适配性：**

- 作为**差异检测的输入为高**（§2.4、§4 的 P2）；
- 单独看「哪些成员常一起改」为中，你们已经有了。

**能否吃进意图模型：**共变本身不能；但「共变 − 声明依赖」的差集正是意图与实际的错位（Clio 思路［R29］）。

### 2.7 Adam Tornhill 的行为式代码分析

**回答什么问题：**有限的整改预算该先花在哪里，即热点；哪些模块在时间上耦合；知识集中在谁身上，即离职与巴士因子风险。

**输入：**版本历史（提交、作者、时间），每个文件的复杂度代理（Tornhill 常用缩进作语言无关代理），可选问题跟踪。

**产出：**

- 热点：变更频率 × 复杂度；
- 复杂度趋势；
- 文件级、函数级、架构组件级的时间耦合；
- 知识地图与「知识孤岛」。

**来源：**

- 书：*Your Code as a Crime Scene*，2015 年首版，2024 年第二版［R49］；*Software Design X-Rays*，2018［R50］。
- 开源工具 code-maat［R57］。
- 商业产品 CodeScene 把架构组件定义为 glob 模式，在组件级算热点与变更耦合［R57］。

**证据强度：**

- **热点背后的过程度量为 A。**Nagappan & Ball 2005 在 Windows Server 2003 上发现，相对代码变动量高度预测缺陷密度，区分易错二进制的准确率为 89%［R53］。Rahman & Devanbu 2013 在 12 个项目、85 个版本上发现过程度量普遍优于代码度量，且代码度量「停滞」，版本间变化很小［R91］。
- **「缩进作复杂度代理」为 B。**Hindle、Godfrey、Holt 2008 在 278 个项目上，发现缩进统计量排序与 McCabe、Halstead 排序高度一致［R56］。
- **CodeScene 的「Code Health」与业务影响为 B，作者即厂商。**Tornhill & Borg 2022 研究了 39 个专有代码库，低质量代码的缺陷是高质量代码的 15 倍，解决时间多 124%［R51］。Borg 等 2024 报告高质量端回报递增［R52］。两篇都附有复现包，但作者来自 CodeScene。
- **知识与所有权为 A，但不适用于本仓库。**Bird 等 2011［R54］；Greiler 等 2015 在微软 4 个产品上复现［R55］。

**已知的坑与误报：**

- 热点会把「本来就该常改」的文件（配置、注册表、装配入口）排在前面，需要人工排除。
- 复杂度代理与规模强相关（§2.14）。
- **知识分布的前提是「作者=写代码的人」。**本仓库的作者栏按约定永远是负责的人，实际产出多来自 agent，按作者统计知识分布没有意义（推断，依据 AGENTS.md 署名约定与［R48］）。

**适配性：**

- **热点为中**：只作排序输入，可与你们已有的函数级复杂度和 CRAP 合并；
- **时间耦合**与 §2.6 重叠；
- **知识分布为低。**

**能否吃进意图模型：**组件级分析可以借你们的分组作为「架构组件」映射，但它分析的仍是历史，不是意图。

### 2.8 Vlad Khononov：《Balancing Coupling in Software Design》的耦合平衡模型

**回答什么问题：**一处耦合是否「平衡」，即它的成本是否与它的价值和风险相称。

**输入：**每条集成关系的三个维度。

- **集成强度**：共享多少知识。从强到弱为 intrusive（侵入，越过公开接口）> functional（功能）> model（模型）> contract（契约）。
- **距离**：协调一次级联改动的社会技术成本，跨方法、类、组件、服务、系统、组织。
- **易变性**：变化的概率。按领域（DDD 子域）评估，「不只看提交历史」。

**产出：**

- `MODULARITY = STRENGTH XOR DISTANCE`；
- `COMPLEXITY = STRENGTH AND DISTANCE`；
- 实用版 `BALANCE = (STRENGTH XOR DISTANCE) OR NOT VOLATILITY`［R59，〔原文〕］。

另外：低强度却低距离（彼此无关的东西放在一起）意味着低内聚，数量多了就滑向「大泥球」［R59］。书于 2024 年由 Addison-Wesley 出版［R58］。作者另有官方的 Claude Code 插件 `vladikk/modularity`，提供 `/modularity:review` 与 `/modularity:design`，许可证为 CC BY-NC-SA 4.0，商用需联系作者［R60，〔原文〕README］。

**证据强度：D。**

- 作者自述它综合了约 50 年的模块化文献［R59］，其中集成强度沿用了 Myers 的耦合层级与 connascence［R61］。
- 检索未发现针对该模型本身的实证。

**已知的坑与误报：**

- 三个维度都是**定性**等级，不同评审者给出的等级可能不一致（推断）。
- 易变性按领域评估，需要产品侧输入；用提交历史代替会混入「偶然易变性」［R60］。
- 它是判断框架，不是检测器。

**适配性：高（作为评审问法）。**它和契约先行几乎同构：

- 跨成员只经 `core` 契约交互，即 contract coupling，强度低，可以远距离。
- 跨成员共享内部领域类型，即 model coupling，或者直接 import 另一个成员的非公开入口，即 intrusive，强度高、距离远，问题就在这里。
- `OR NOT VOLATILITY` 正好解释了「为什么 `core` 被所有人依赖却没问题」：契约包声明为不易变。这同时也是 §2.1 中 D 的缺陷所在。

**能否吃进意图模型：能。**

- 距离可以从分组与成员结构机械地算出；
- 集成强度可以从「是否只经公开入口与 `core` 契约」半机械地判；
- 易变性取自产品与契约侧的声明。

### 2.9 Connascence（共生性）

**回答什么问题：**两处代码「必须一起改才能保持正确」的方式有多强、多远、多广。

**输入：**代码片段之间的关系，人工判别。

**产出：**

- 静态类别：Name、Type、Meaning、Position、Algorithm；
- 动态类别：Execution、Timing、Value、Identity；
- 三个属性：Strength、Locality、Degree［R65］。

来源：术语由 Page-Jones 1992 在 CACM 引入［R62］，1995 年成书［R63］；Weirich 2009 年以「Grand Unified Theory of Software Design」为题的演讲使之流行［R64，〔元数据〕］。

**证据强度：D。**检索未发现把 connascence 作为度量的实证研究。

**已知的坑与误报：**

- 类别判断依赖人；
- 弱类别（Name）跨距离通常可以接受，不能「见 connascence 就报」。

**适配性：中（代码级评审词汇）。**对 Cordis 尤其有用的是动态类别：

- 插件生命周期、fiber、装配顺序上的 **Execution／Timing connascence**；
- 服务名字符串上的 **Name connascence**。只要服务名由契约集中定义就是弱的；散落的魔法字符串就是 Meaning connascence。

**能否吃进意图模型：**不能直接吃进；作为 reviewer 的词汇最合适。

### 2.10 Parnas 的信息隐藏与「按可能变化的决定分解」；Juval Löwy 的按易变性分解

**回答什么问题：**模块边界应该怎么划，使得一项可能的变化只落在一个模块里。

**输入：**一份「可能变化的设计决定」清单。

**产出：**每个模块隐藏的那项决定（它的 secret），以及对外接口。

**来源：**

- Parnas 1972 在 CACM 以 KWIC 为例，对比「按处理流程分解」与「按隐藏的决定分解」［R66］。
- Sullivan、Griswold、Cai、Hallen 2001 用 DSM 加实物期权给 Parnas 的结论做了形式化估值，结果与 Parnas 的结论一致［R14］。
- Löwy 2019 年的《Righting Software》主张按易变性分解，批评功能分解「最大化变化成本」，并给出识别易变性的启发式：沿「时间」与「客户」两轴，「为竞争对手设计」［R67，R68］。他的方法还规定了组件分类（Client、Manager、Engine、ResourceAccess、Resource、Utility）与封闭分层调用规则［〔二手〕，未从原书核实细节］。

**证据强度：**

- Parnas 为 D，但理论传承最强。它有形式化的经济学解释［R14］，并被大量模块化实证间接支持：模块化程度与维护成本相关［R16，R18，R24］。不过这些实证测的是结构，不是「是否按决定分解」。
- Löwy 为 D，书中未提供实证［R68］。

**已知的坑与误报：**

- 「可能的变化」预测错了，边界就跟着错（推断）。
- Löwy 的分类法预设了一种分层服务风格。它与「插件／服务 + 契约 + 依赖注入」的组合式装配不同构，硬套会产生没有边界价值的包装层（推断）。

**适配性：**

- **Parnas 为高**，作为设计前的纪律：每个成员、每份契约写明「隐藏的决定」与「预期的变化」，评审时问「这项变化会落在几个成员里」。
- **Löwy 的分类法为低**；他的「易变性识别启发式」可以借。

**能否吃进意图模型：能。**「隐藏的决定」与「声明易变性」可以作为实现映射或契约的一个属性，同时喂给 §2.8 的易变性与 §2.1 的稳定性声明。

### 2.11 架构适应度函数（Ford、Parsons、Kua）

**回答什么问题：**某项架构特性是否仍然成立，能否被持续、客观地检查。

**输入：**一项架构特性，以及它的可执行检查。

**产出：**通过或失败、趋势、告警。

**定义**：「An architectural fitness function is any mechanism that provides an objective integrity assessment of some architectural characteristic(s)」［R70，〔元数据〕］。

**来源：**首版 2017［R69］；第二版 2022，加入 Sadalage，副题「Automated Software Governance」［R70］。TS 生态里现成的承载工具有 dependency-cruiser 的 `forbidden`／`reachable` 等规则［R71］。Ford 与 Richards 另有《Architecture as Code》，O'Reilly 页面已上架，出版日期各渠道不一，**未核实**［R72］。

**证据强度：**

- 概念本身为 D：从业者著作，检索未发现系统实证。
- 它的子类「架构合规检查」有 C 级证据［R36–R39］。

**已知的坑与误报：**

- 适应度函数一旦变成硬门禁，就会被「满足字面」，见 §2.14 的 Goodhart 与 agent 的奖励钻营。
- 「什么特性值得写成函数」仍然需要人判断：它是承载判断的工具，不能替代判断。

**适配性：高（作为框架）。**你们的依赖方向规则、环检测、SDP 违例、新增跨成员依赖已经是适应度函数。建议把反射模型的三态（§2.5）与差异检测（§2.4／§2.6）也纳入同一框架。分两级处理：

- 起步只报告；
- 收敛后，把「缺失」与「越级偏离」的一个子集升为硬线。

**能否吃进意图模型：能。**每个函数都应该能回指它守护的意图条款，否则就成了「为度量而度量」。

### 2.12 SEI 的 ATAM、质量属性场景与效用树

**回答什么问题：**架构方案在关键质量属性上是否达标；风险点、敏感点、权衡点在哪里。

**输入：**

- 业务驱动；
- 架构描述；
- 质量属性场景：刺激源、刺激、环境、制品、响应、响应度量［R75］；
- 按「重要性 × 难度」排序的效用树。

**产出：**风险、非风险、敏感点、权衡点、风险主题。

**来源：**ATAM 技术报告 2000［R73］；方法书 2002［R74］；《Software Architecture in Practice》第 4 版 2021［R75］。QAW 用于在架构之前引出质量属性［R77］；mini-QAW 是其轻量版［R78］。

**证据强度：C。**

- Bass、Nord、Wood、Zubrow 2007 分析了 18 次架构评估。「遗漏」类风险主题是「误作」类的两倍；评估中的风险主题与系统的业务或使命目标之间未发现关系［R76］。
- Babar & Gorton 2009 访谈了 20 名架构师：实践中多用非正式、经验式评审，很少采用研究推荐的做法，例如项目外评审者［R80］。
- 成本：中型 ATAM 约 70 人日，其中评估组 36、项目决策者 18、其他干系人 16［R74，经出版社节选〔元数据〕］。
- 轻量替代 TARA 面向「场景法被认为复杂昂贵」的工业情境［R79］。
- **LLM 辅助的初步证据：**Capilla 等 2025／2026 以学生评估为对照。MS Copilot 生成的候选风险、敏感点和权衡点更多，「在生成候选风险上胜过人，但评估上不一定」；作者强调需要专家核验［R81，〔原文〕摘要］。证据很弱：对照组是学生，单一工具。

**已知的坑与误报：**

- 完整 ATAM 依赖多类干系人在场，单人加 agent 的组织结构不满足这个前提。
- 场景写成泛泛的形容词（「高可用」），就无法评估。

**适配性：**

- **完整 ATAM 为低**：成本与干系人前提都不满足。
- **质量属性场景 + 效用树 + 敏感点和权衡点的问法为高**：成本低，而且天然契合「agent 生成候选、人裁决」的分工［R81］。适合的场景包括租户隔离、超长期待机、模型请求统一经 OpenRouter、可恢复性等全局约束。

**能否吃进意图模型：能。**场景的「制品」就是契约或实现映射节点；「响应度量」可以落成适应度函数（§2.11）。

### 2.13 C4 模型与「架构即代码」（由模型生成视图）

**回答什么问题：**如何让不同受众在合适的抽象层看到同一个架构；如何让图与代码不漂移。

**输入：**一个模型，包含系统、容器、组件、代码四层，以及关系。

**产出：**

- 多个视图：上下文、容器、组件、代码；
- 辅助视图：全景、动态、部署［R82］。

C4 由 Simon Brown 在 2006–2011 年间形成［R82，〔二手〕维基］，标榜与记法和工具无关［R82］。Structurizr 用 DSL 定义一个模型，再由它生成多个视图［R83］；LikeC4 是 TS 实现的同类开源工具［R84］。

**证据强度：D。**维基条目没有引用实证研究，检索也未发现。

**已知的坑与误报：**

- 「模型即代码」解决的是「图与图之间」的一致性，**不保证模型与源码一致**。要保证后者，仍需反射模型或适应度函数。
- **单独维护一份 C4 DSL 模型，会在实现映射之外造出第二份架构权威。**这与你们「同一概念只有一个权威定义」相冲突。

**适配性：中偏低。**

- C4 的分层词汇可以借来组织视图；
- 视图应该从**现有实现映射与分组规则生成**，不应另建 Structurizr／LikeC4 模型。

**能否吃进意图模型：能**，前提是让 C4 视图成为实现映射的投影，而不是一个新源。

### 2.14 对度量的批评

**度量变成目标就会失真：**

- Goodhart 1975 的原话是：「any observed statistical regularity will tend to collapse once pressure is placed upon it for control purposes」［R85］。
- 流行的说法「When a measure becomes a target, it ceases to be a good measure」出自 Strathern 1997 的转述［R85］。
- Campbell 1979 提出：量化指标越被用于决策，越容易受到腐蚀压力，也越会扭曲它要监测的过程［R86］。
- 软件架构度量里的现身说法：华为 SAI 的经验总结说，关键是「引导团队关注每项度量背后的问题，而不是分数本身」；推行之初遇到的怀疑，根子在绩效考核带来的隐性压力［R27，〔原文〕］。

**度量与缺陷的相关性大多被规模解释：**

- El Emam 等 2001 证明了类规模的强混杂效应，并质疑此前的 OO 度量验证［R88］。
- Gil & Lalouche 2017 研究了 26 个度量（含 CK）：度量的「效度」几乎可以由它与规模的相关预测，R² 有时高达 0.97；控制规模之后，预测力大多消失［R89］。
- Sjøberg 等 2013 雇了 6 名开发者在 4 个功能等价的系统上做维护任务。调整文件规模与变更次数之后，12 种坏味道没有一种与工作量增加显著相关；规模与变更次数几乎解释了全部变异［R90，〔原文〕］。

**过程度量优于产品度量，且研究本身有偏差：**

- 过程度量优于产品度量［R91］。
- 缺陷预测研究里，「谁做的」比「用什么技术」更能解释结果差异［R92］。
- 早期缺陷预测模型有严重的理论与数据问题［R87］。
- 2000–2010 年的 208 篇研究中，只有 36 篇报告了足够的上下文与方法［R93］。
- 旁证：控制测试集规模后，覆盖率与测试有效性只有低到中等相关［R94］。

**对本仓库特别相关的两条：**

1. **agent 会钻度量的空子。**ImpossibleBench 让测试与规格互相矛盾，以此测量 LLM 编码 agent 利用测试的倾向；作者报告前沿模型频繁这样做［R95，〔原文〕摘要；具体比例未从论文正文核实，故不引用数字］。在「agent 实现、门禁验收」的流程里，任何硬门禁都要防「改测试或改规则而不改设计」。
2. **从业者把架构决定视为技术债的最大来源，但认为现有工具帮不上细节**［R96］。这正是本调研的动机，也提醒我们：工具应该产出「问题清单」，不应产出「分数」。

**证据强度：A**（规模混杂、过程优于产品、研究者偏差都有多团队实证）；Goodhart／Campbell 是社会科学的理论概括加大量案例。

**适配性：高。**它约束上面每一项的用法：

- 读数一律带规模对照；
- 看趋势而不看绝对值；
- 不合成复合分数；
- 硬线极少，且每条硬线能回指意图条款；
- 门禁变更本身受评审，防止 agent 钻营。

这和你们「整洁回路：约束结果不约束做法、只有少数硬线拦合并」的原则一致。

### 2.15 补充：评估过、但不建议的方法

- **自动聚类式架构恢复。**Garcia、Ivkovic、Medvidovic 2013 用独立建立的「真值架构」比较了多种恢复技术［R40］，这类技术的准确度普遍有限〔元数据〕。你们已有显式意图，不需要从代码猜架构。适配性：低。
- **镜像假设与 Conway 定律分析。**MacCormack、Baldwin、Rusnak 2012 检验了产品架构与组织结构的镜像关系［R20］。你们只有一个负责人加若干 agent 角色，组织维度退化。适配性：低。
- **ADR（Nygard 2011）**［R97］：你们已经有决定记录家族，不重复引入。

## 4. 最值得优先引入的 4 项，外加 1 项可选

代价均为本报告的**粗估，未核实**，按「一个人加 agent 实施」估。

### P1　反射模型，以实现映射为意图

**理由：**意图模型与映射已经存在，这是反射模型最贵的输入，而你们白拿。它也是唯一能报出「缺失」的方法：节点声称兑现了契约，代码却不引用；节点声称提供了服务，装配里却没有对应的 `provide`。它还能同时覆盖 import 图看不见的 DI 装配边。

**预期代价：中。**需要做三件事：

1. 一个抽取器：TS 编译器 API 读 import；读 `apps` 装配入口或装配期自省，拿到 `inject`→`provide` 的解析；
2. 一份从实现映射节点到包的映射，大部分已有；
3. 一张三态报告。

**起步规则：**只报告，不拦合并。等误报收敛后，再把「越级偏离」与「声明却缺失的契约兑现」升为硬线。

**风险：**Rosik 等的反面证据［R38］说明，报告必须有接收者和处置流程，否则不会被修。

### P2　结构与历史的差异检测，复用现有共变数据

**理由：**它把你们已有的两类读数（依赖图、成员级共变）**交叉**起来，得到两类有实证支撑的信号［R22，R28，R29，R45］：

- 「持续共变却无声明依赖、无共享契约」的成员对，即模块化违例；
- 「被多成员依赖、又频繁与依赖者共变」的 `core` 契约包，即不稳定接口，也就是「不稳定契约」。

这用一个有依据的问题，替换了被有意放弃的 D：问题不是「稳定的契约包为何不抽象」，而是「声明稳定的契约包为何实测易变」。

**预期代价：低到中。**数据已有，只需要做交集与差集，再加上：

- 按 PR 事务计数，过滤超大事务；
- 用 `Agent-Role` trailer 分层；
- 用时间窗消化「破坏性重构期」的噪声［R47，R48，R26］。

**用法：**只报告。

### P3　质量属性场景 + 效用树，写进设计模板

**理由：**这是 SEI 方法里性价比最高、证据也相对最多的部分［R75–R77］。「遗漏型风险是误作型的两倍」［R76］，说明在设计前系统地引出场景是有价值的。「agent 生成候选风险、敏感点和权衡点，人做取舍」与你们「架构归人、agent 只评审与反驳」的分工天然契合［R81］。

**预期代价：低到中。**每个设计 topic 多写若干条六段式场景和一棵效用树，预计数小时人时（粗估）。不需要组织完整 ATAM。

### P4　耦合平衡评审问法

内容：Khononov 三维，加上 Parnas 的「隐藏的决定」，加上 connascence 词汇。

**理由：**这些方法证据都弱（D），但对契约先行与插件装配的解释力很强（§2.8–§2.10）。它们最适合的形态是「reviewer 的问法」而不是「度量」，正好落在 agent 的职责里：

- 这条新依赖的集成强度是 contract 还是 model？
- 距离是成员内、组内还是跨组？
- 依赖对象声明的易变性是什么？
- 这项预期变化会落在几个成员？

**预期代价：低。**主要是写进评审判据。易变性需要在实现映射或契约里加一个属性。按你们「属性扩展优于新概念」的偏好，应挂在已有对象上。作者有现成的 Claude Code 插件可以参考［R60］，但许可证为 CC BY-NC-SA 4.0，是否可用需要另判；参考其判据即可，不必引入插件。

### P5（可选）　文件级热点：变更频率 × 现有复杂度

**理由：**过程度量的证据为 A［R53，R91］，你们已有函数级复杂度与 CRAP，补上变更频率几乎零成本。

**为什么只排第五：**

- 在 agent 主导、squash 合并、主动破坏性重构的阶段，变更频率的信噪比可能很低［R48］；
- 复杂度本身被规模混杂［R89］。

**用法：**只用来给整改排序，不设阈值，不进门禁。

## 6. 给「只做评审与反驳的 agent」的使用提示

以下由上文推出，不是新的事实主张。

1. **agent 拿读数提问，不拿读数下结论。**每个读数都附带它在本报告中的证据级别。对 D 级方法（Khononov、connascence、Parnas、适应度函数），引用时应写成「按某框架，这里值得问……」，不写成「这是错的」。
2. **反驳时优先给反例或意图条款。**例如「实现映射节点 N 声明了 X，但装配图里没有」。不要只说「指标 Y 偏高」。这与反射模型的三态天然对应。
3. **门禁与规则的变更本身要受评审**，防止「改规则或改测试而不改设计」［R95］。
4. **涉及历史的读数（共变、热点）先按 `Agent-Role` 分层，并标注统计窗口。**处于主动重构期时，必须先说明窗口内的主动迁移有哪些。
