## 0. 先看结论

| 类别 | 首选 | 备选 | 一句理由 |
| --- | --- | --- | --- |
| 依赖结构与规则 | **dependency-cruiser** 18.5.0 | eslint-plugin-boundaries 7.2.0 | depcruise 是 MIT 许可，两天前刚发版，周下载约 515 万。规则表达力最强（含 SDP 的 `moreUnstable`、区分 type-only、已知违例基线、`--affected`）；配置本身是 JS，可以直接从意图模型生成；在本仓库跑一遍约 5 s。boundaries 能给编辑器即时反馈，适合成员内部的文件级分层，代价是得先把 ESLint 引进来。 |
| 架构即代码视图 | **LikeC4** 1.59.4 | Structurizr（合并后的新工具链 v2026.09.19） | LikeC4 是 MIT 许可、TS/npm 原生，有 Model Builder API，`.c4` 文本也很容易从 YAML 生成；可以自定义关系种类，所以能直接画出「injects」边。试用时从代码图生成模型、校验、出 Mermaid、建站，各步都在 10 s 以内。Structurizr 是 C4 的参考实现，但跑在 JVM/Docker 上，CLI 和 Lite 今年 2 月刚归档、合并成新工具链。 |
| 演化与热点 | **code-maat** v1.0.4（当算法参照与差分 oracle） | CodeCharta（vis 2.7.0／analysis 2.0.2） | code-maat 的 coupling、soc、age、churn 和按正则分层聚合是这一类分析的「原典」定义。它在本仓库跑一遍约 6 s，输出 CSV，正好拿来核对我们自建的成员共变。缺点是许可证为 GPL-3.0，从 2023 年起不再发版，只适合当外部进程用。CodeCharta 是 BSD-3 许可、维护活跃，带时间耦合边和城市图可视化，但要同时装 Java 和 Node。 |
| DSM | **自建最小 DSM 视图**（复用现有成员图与共变） | DV8（Viewer 免费；导入自产 JSON） | TS 生态里没有在维护、开源、支持 TS 的 DSM 工具。DV8、Lattix 是商业产品，原生语言里没有 TS（未核实）；Structure101 已停售；DsmSuite 只有 C# 桌面原型，也没有 TS 分析器。 |

另有三条事实，影响该怎么借力：

1. **静态 import 工具看不见 Cordis 的 provide/inject 依赖，这是结构性的。**我用粗糙的正则原型在 `src/` 里抽到 24 个被 provide 的服务、38 条「注入方 → 提供方」边，合成 32 个成员对，**这 32 对没有一对在 import 图里出现**（试用；import 图因部分成员没构建 dist 而有少量缺边，见 §1.1）。上面所有工具都不理解 Cordis，这块只能自建，见 §7。
2. **「代码与意图模型比对」没有确定性的现成工具。**能接近的只有三条路：用 dependency-cruiser 或 Nx 标签从模型生成「允许边」，只能抓「代码多出来的边」；ArchUnitTS／tsarch 按 PlantUML 图核对 import；Erode 用 LLM 读 diff。「模型声明了、代码里却没有」这个方向，以及 inject 边，都要自建一个小比对器（§7）。
3. dependency-cruiser 试用时，在文件级查出成员**内部**的运行时环：10 条，分布在 `core/tool-definition`、`model/pi-ai-transport` 两个成员；算上 type-only 是 34 条，分布在 5 个成员。我们的自建检查只做成员级环检测，看不到这一层。这只是工具读数，要不要处理由人判断。

## 1. 试用记录（本仓库，只读）

### 1.1 dependency-cruiser 18.5.0
- 不带配置直接跑时，跨成员 import 和 `kysely` 都 `couldNotResolve`。原因是成员的 `exports` 只有 `types`/`import` 两个条件，必须在 `enhancedResolveOptions` 里给出 `exportsFields: ['exports']` 和含 `import` 的 `conditionNames`（`depcruise --init` 生成的配置一般会带上）。
- 加了解析配置和 4 条示例规则（环、`core` 不依赖非 core、packages 不依赖 apps、`moreUnstable`）之后：cruise 1017 个模块、2978 条依赖，**5.3 s，约 430 MB 峰值内存**。
- 成员的 `exports` 指向 `dist/`，所以跨成员边解析落在 `dist/index.js`。主检出里有些成员没构建 dist，留下 18 个 `@omne-harness-lite/*` import 解析不到。在 CI 上 build 之后跑即可；不想依赖 build，也可以给成员加一个指向 `src` 的自定义 export 条件，或者用 tsconfig `paths`（未试，要改仓库）。
- `--collapse "^(packages/[^/]+/[^/]+|apps/[^/]+)/"` 能折成成员级；`-T metrics` 给出每个模块和文件夹的 Ca/Ce/I；`-T mermaid` 能直接出图。
- 规则读数：`no-circular` 文件级共 34 条违例，去掉 type-only 后剩 10 条（位置见 §0 第 3 条）；`moreUnstable` 警告 113 条（文件级，未折叠，仅示意）。

### 1.2 skott 0.35.12
- `--no-trackTypeOnlyDependencies --showCircularDependencies`：**20.5 s，约 590 MB**。找到的 10 条环和 dependency-cruiser 一致。

### 1.3 ArchUnitTS（npm 包名 `archunit`）2.5.4
- 在 scratchpad 建了一份 tsconfig，`extends` 仓库的 `tsconfig.base.json`，只 include 各成员 `src`。`extractGraph` 用时约 5 s。
- 问题：跨成员 import 经 pnpm 软链解析到 `dist/*.d.ts`，这些 `.d.ts` 自己也成了图里的源，而且全被标成 `external`。所以用 `projectSlices().definedBy('packages/(**)/')` 按成员切片、做 PlantUML 核对时，结果**不可信**（这次 0 违例，可以确定是切片没对上，不是真的没违例）。要可靠使用，得在仓库根放一份 `paths` 指向各成员 `src` 的 tsconfig（未试，要写仓库）。

### 1.4 code-maat v1.0.4（jar，Java 21）
- 日志用 `git log --numstat --pretty=format:'--%h--%ad--%aN' --no-renames -- packages apps`，在 main 上 4433 行。`-a coupling` 用时 **5.9 s**。
- **坑 1**：默认 `--max-changeset-size 30` 会把大提交丢掉。本仓库是 squash 合并，最近 60 个提交改动文件数的中位数是 23，最大 4079，大 PR 的共变信号会被整体丢掉。阈值要显式放大，或者按 PR 而不是按提交统计。
- **坑 2**：分层文件里的正则必须写成 `^...$` 形式。按 core/infra/domain/apps 四层聚合（`--max-changeset-size 2000 --min-revs 3`）的结果：只有 `core ↔ domain` 越过阈值，degree 39，average-revs 38。

### 1.5 LikeC4 1.59.4 ＋ Cordis 边的粗抽取原型
- 安装 15 s（依赖里有 vite、esbuild 和 wasm graphviz；只有导出 PNG 才需要 Playwright 浏览器）。
- 生成脚本约 60 行 Python（`tool-trials/likec4/gen.py`）。import 边来自 dependency-cruiser 的 JSON；provide/inject 边来自正则：`inject: [...]`、`ctx.provide(X`，再在全仓 `src` 里查 `export const X = '...'` 把常量还原成服务名。输出是 182 行的 `.c4`，用两种关系：`imports` 和 `injects { line dotted }`。
- `likec4 validate` 4.7 s，`gen mermaid` 4.3 s（每个 view 一张 `.mmd`），`build` 9.2 s，静态站 5.7 MB。语法踩过一次坑：view 里不能写 `include **`，要写 `include element.kind = member`。
- 这个原型只用来回答「外部模型能不能生成视图」和「inject 边与 import 边重不重叠」，**不是**可交付的抽取器。真抽取器要走 TS AST，见 §7。

### dependency-cruiser
- **做什么／输出**：抽取文件级依赖图，再用规则校验。规则分 `forbidden`／`allowed`／`required` 三类。条件有 `path`/`pathNot`（`$1` 可以捕获分组）、`circular`、`via`／`viaOnly`、`reachable`、`orphan`、`moreUnstable`（SDP）、`dependencyTypes`（含 `type-only`、`npm-no-pkg` 等 40 种）、`numberOfDependentsLessThan`/`MoreThan`、`couldNotResolve`、`ancestor`。报告器有 `err`、`err-long`、`err-html`、`dot`、`ddot`、`archi`、`flat`、`d2`、`mermaid`、`text`、`json`、`csv`、`markdown`、`html`、`teamcity`、`azure-devops`、`metrics`、`baseline`，也能挂插件报告器。还支持 `--baseline`/`--ignore-known`（已知违例只减不增）、`--affected <rev>`、`--cache`、`--focus`/`--reaches`/`--collapse`。
- **外部意图模型**：配置文件就是 JS 模块，加载时可以读设计区的 YAML/JSON，生成 `allowed` 或 `forbidden` 规则；违例就是「代码多出模型没允许的边」。`required` 规则能表达「匹配 X 的模块必须依赖匹配 Y 的模块」，能覆盖一部分「模型有、代码没有」的情形。
- **非 import 依赖**：不支持。规则只对它自己抽到的依赖求值。cruise 结果的 JSON 格式是公开的，可以往里并入合成边，再用 `depcruise-fmt` 出图；但合成边**不会**参与规则判定（推断，未核实）。
- **与自建的关系**：重叠的是成员方向规则、环检测和不稳定度（它的 `metrics` 是模块和文件夹级）。它补上的是：文件级环、type-only 区分、已知违例基线、`--affected`、现成的 mermaid/d2/dot 输出，还有「import 了却没在 package.json 声明」（`npm-no-pkg`）。我们 ts-checks 里那些按调用点、按 Cordis 上下文判的规则（`ops-event-whitelist`、`og-s42-dynamic-resolve` 等）它都做不了，这些保留自建。

### eslint-plugin-boundaries
- **做什么**：用路径模式把文件归类成「元素」，v7 起是元素、文件、模块三个维度的实体模型（v7.0.0 于 2026-07-05 发布）。主要规则：`boundaries/dependencies`、`entry-point`、`external`、`no-private`、`no-unknown`。输出 ESLint 报错，有编辑器内即时反馈。
- **适配**：适合成员内部的分层，比如「`src/ops/**` 只许 import 某几个文件」。我们 ts-checks 里纯按路径判的那部分规则可以迁过去。仓库目前不用 ESLint，引入它就意味着引入 ESLint 本身。
- **意图模型／非 import**：配置是 JS，可以生成元素和规则；不理解 inject。

### Nx project graph 与 module boundaries
- **做什么**：`nx graph` 提供交互式项目图，`--file=graph.json` 导出图。标签写在 `package.json` 的 `nx.tags` 或 `project.json` 里；`@nx/enforce-module-boundaries` 用 `depConstraints` 约束标签之间的依赖，检查对象是 TS import 和 `package.json` 依赖。
- **独有能力**：`createDependencies` 插件 API 可以从任意来源往项目图里加 `static`／`dynamic`／`implicit` 边。设计区 YAML 或者一个 Cordis 抽取器都能接进来，这是唯一能把 inject 边「合法地」放进一张官方图的现成机制。
- **限制**：ESLint 规则只看 import 和 `package.json`。要对图里**所有**边（含插件加的边）做边界检查，得用 `@nx/conformance` 的 `enforce-project-boundaries`，**它需要 Nx Enterprise 许可**，没有许可时命令直接失败。只为一张图引入 Nx，成本偏高。

### Sheriff
- **做什么**：目录模块（barrel `index.ts` 或配置出来的模块）加标签和 `depRules`，规则可以是函数或通配符。CLI 有 `init`/`verify`/`list`/`export`，`export` 导出 JSON 图；也有 ESLint 插件。
- **适配**：它的强项是「单个应用里的目录模块封装」（偏 Angular/Nx 场景）。我们的成员已经靠 `package.json#exports` 加 pnpm 严格依赖做到了公共入口封装，边际价值低。

### ArchUnitTS／tsarch（架构单元测试）
- **ArchUnitTS 做什么**：在测试里写 `projectFiles()`、`projectSlices()` 规则：文件依赖、切片、环、命名，还有 **`adhereToDiagram(plantuml)`**（按 PlantUML 组件图核对代码）。指标有 LCOM96a/b、耦合因子、抽象度、不稳定度、**到主序列的距离**，另有实验性的 HTML 报告和 `nxProjectSlices()`。
- **意图模型**：从 YAML 生成 PlantUML，再用 `adhereToDiagram` 核对，就是一条「代码 ⊆ 图」的确定性漂移检查。前提是先解决 pnpm 跨包解析的问题（§1.3）。
- **与自建的关系**：抽象度、主序列距离可以补我们只有不稳定度的缺口；但它的抽象度按类和接口算，对我们以函数和对象为主的代码意义有限（推断）。
- **tsarch**：思路相同（`slicesOfProject().adhereToDiagramInFile()`），最近一次发版是 2024-12，已停滞，ArchUnitTS 是更活跃的继任者。

### SonarQube 架构管理（原 Structure101 能力）
- 它会逆向出当前架构，在**图形界面**里定义「意图架构」（没写明的关系一律禁止），把偏离作为普通 issue 报出，接入质量门。支持 TS。Cloud 版 2026-03-02 GA；Server 版从 2026.4 起包含此功能，限 Developer 版及以上。
- 意图在 UI 里定义，**没看到文件或 API 的定义方式**（未核实），没法从我们的 YAML 喂进去；Community Build 版没有这个功能。

### LikeC4（首选）
- **CLI**：`serve`/`dev`、`build`（静态站）、`preview`、`export png|jpg|json|drawio`、`gen mermaid|dot|d2|plantuml|react|model`（可写自定义生成器）、`validate`、`format --check`、`lsp`。
- **与我们的契合点**：设计区的「哪个包兑现哪份契约、插件提供和注入哪些服务」可以直接映射成元素种类（layer／member／contract／service）和关系种类（imports／injects／realizes）。生成器可以是 TS 脚本（Builder API），也可以是纯文本模板。`gen mermaid` 的产物能直接嵌进 Markdown，`build` 产物可以和现有的审讯页并列。
- **与自建的关系**：自建的仿 uml-viewer 成员图优势在「按层排、三角标记、审讯视角」；LikeC4 补的是多视图（上下文、容器、组件，带过滤）、模型优先的叙述视图，还有导出到 draw.io、PlantUML、D2。两者不互斥。
- **Erode** 用 LLM 判漂移，结果不确定，又走非 OpenRouter 的提供方（能否接 OpenRouter 的 OpenAI 兼容端点未核实）。在一个要求「所有模型请求统一经 OpenRouter」的项目里拿它当开发工具，**要人裁**；不建议当合并门。

### Structurizr（备选）
- **现状**：CLI 和 Lite 在 2026-02 归档，并入同一个仓库，Lite 由 `local` 命令取代；`export` 支持 PlantUML、C4-PlantUML、Mermaid、WebSequenceDiagrams、静态站、PNG/SVG，另有 `validate`、`inspect`。
- **选它的理由**：要严格遵守 C4 规范，并且要和 Structurizr 生态互通时选它。
- **代价**：JVM／Docker 依赖，工具链刚重组。

## 7. 只能自建的部分与最小范围

没有任何现成工具理解 Cordis 的 plugin/service/provide/inject，也没有确定性工具能把我们的设计区意图模型和 TS 代码对上。下面是最小自建范围，按依赖顺序排；每一项都尽量把重活交给现成工具。

1. **Cordis 装配边抽取器**（必须自建）
   - 输入：各成员 `src/**/*.ts`。
   - 输出：JSON 边 `{from_member, to_member, service, kind: provides | injects | registers, site}`。`registers` 指 `ctx.plugin(X)`，主要出现在 apps 装配。
   - 实现：走 TS AST。ts-checks 已有锁定的 TypeScript 语法视图，`og-s42-dynamic-resolve` 已经在解析 `inject: [...]`、`{...}`、`ctx.inject([...])`，可以复用。字符串常量在全 workspace 范围解析（常量常在别的文件甚至别的包，原型就靠全局常量表还原）；解析不出的服务名要**报出**，不能静默丢掉。
   - 原型读数：24 个服务、38 条边，没有「只有 inject、无人 provide」的服务（正则原型，只作量级参考）。
2. **意图模型对账器**（必须自建，很薄）
   - 只读设计区的 JSON/YAML，不在设计区以外复制意图，符合仓库「外面不留第二个源」的边界。和两份事实做三向集合比对：dependency-cruiser 的成员级 import 边，以及上一步抽出的装配边。
   - 报告三个集合：「代码有、模型无」「模型有、代码无」「一致」。
   - 「代码有、模型无」这一半，也可以交给 dependency-cruiser：配置文件读模型生成 `allowed` 规则即可，还能顺带用上它的基线和 `--affected`。另一半，以及装配边，只能自己比。
3. **DSM 视图**（自建，很小）
   - 成员 × 成员矩阵，行列按层排序、层内按拓扑序；单元格叠加 import 次数、inject 边、共变 degree。
   - 直接加进现有的静态 HTML 审讯页。如需外部查看器，可以另导出一份 DV8 JSON（格式待核实）。
4. **视图生成**（借 LikeC4，自建部分只是生成器）
   - 从设计区意图模型（元素、契约、服务）加上 1、2 两步的事实边生成 `.c4`，用 `likec4 build`/`gen mermaid` 出图。原型约 60 行。
5. **共变对齐**（改造自建，不新增工具）
   - 用 code-maat 的定义和参数对齐现有成员共变，code-maat 的 CSV 当差分 oracle；处理 squash 合并的大提交问题。

不建议自建的：文件级依赖抽取与解析、环检测、规则引擎、已知违例基线、mermaid/dot 出图，这些交给 dependency-cruiser；C4 渲染与站点交给 LikeC4。
