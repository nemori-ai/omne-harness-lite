### 0 判定口径

每一格只取一个判定：

| 判定 | 含义 |
|---|---|
| **可承载** | 源的现有结构原样满足该条款 |
| **需改** | 源有对应结构，但要增改字段或语义；不必推翻它的既有机制 |
| **不可承载** | 源的**既有机制与条款相冲突**，承载该条款要移除或替换那一机制，不只是加字段 |
| **未覆盖** | 源里读遍相关位置没有对应物 |
| **未核对** | 本轮没读到相关部分（只用于 minimal-runtime 的落盘与 loop 行为） |

「需改」与「不可承载」的分界是：源里有没有一个**正在做相反事情**的机制。只缺字段是需改；
有一段代码在做条款禁止的事（例如在参数没收齐时解析它），就是不可承载。

列名：**DSH** = `dsh-llm` + `dsh-session` 格式；**pi** = `pi-ai` + `pi-agent-core`；**MR** = minimal-runtime。

**哪一源最接近 §5.5 的语法（事实计数，不是推荐）**：上表九行里，DSH 可承载五行、需改三行、未覆盖一行、不可承载零行；
pi 可承载两行、需改四行、未覆盖二行、不可承载一行；MR 可承载三行、需改五行、未覆盖一行。
差别集中在三处：DSH 的块级 start/end 对任意块类型开放（pi 只对三种文本类用途）；DSH 有一个把「账只记一次」「必须有结局」写成可执行检查的伴件；
pi 把在途的半条消息表示成完整消息类型。**两源都没有填法声明与整体替换，都没有语音。**

**「半条不是消息」「组装与一次性相同」在哪一源里是不变量、有没有测试**：

- DSH：「半条不是消息」由结构保证（日志事件只有结算，D8、S2），但 `interruptedBlocks()` 在取消时会把**未封口**的文本块装配进 `interrupted` 消息（D5），这是有意的。
  「组装相同」没有被写成不变量：装配器信任 `block-end`，伴件不查内容；测试只有「紧凑喂入 == 逐条展开喂入」（D7）与「`blocks()` 幂等」（D11）。
- pi：两条都不是不变量。帧归约测试断言「以权威 end 内容为准」「拒绝重复 end 与索引空洞」（P8），不断言和。
- MR：继承 DSH 的确定性测试，丢了性质测试（M1）。

**DSH 的 `tool internal / progress` 轨不存在**：执行上下文只多 `deferContext` 与 `concludeTurn`，UI 卡片是由参数与最终结果纯算的（D9）。
pi 是三源里唯一有「工具执行中往外说话」通道的，但它的形状是「结果快照的瞬态广播」，与 PF-009「一条消息的到达增量」不同构。

### 7 落盘与投影（问题五）

| 条款 | DSH | pi | MR |
|---|---|---|---|
| 日志只增不改，消息只是日志的一部分（PF-009 §4、PF-000 §4） | 可承载——事件日志 seq 连续，消息只占四类，未知必需事件拒绝重建（S1） | 可承载——条目 message/compaction/branch_summary/custom，带 `parentId` 树（P10；harness 地位待核） | 未核对 |
| §9.2 不留到达的过程 | **不可承载**——结算里嵌整条带时间的紧凑流，作者明确否决过「只存装配后的消息」（S2） | 可承载——条目在消息收尾时写；帧编码明言终止结算另存（P7、P8） | 未核对（投递面不写事实，M3） |
| PF-000 §5.4「增量先于成品：一串瞬态增量 + 一条成品条目」 | 需改——在途增量是进程内帧（瞬态），成品条目同时装着全部增量（S2） | 可承载——在途是事件（瞬态），成品只有消息（P7） | 可承载（投递面，M3） |
| 格式演进 | 三条相邻迁移 v0→v1→v2→v3，约 4,700 行；v1→v2 改变事件基数，重写全部 seq 与同会话引用（S5） | 未核对 | 未核对 |

**DSH session-format 对「只增不改、消息只是日志一部分」是承载的**；与本项目冲突的只有一点：它把「怎么到的」作为结算的一部分永久保存，
PF-009 §9.2 明确不要（PF-009 自己也引了这一分歧）。其余代价是历史包袱：迁移链、改变基数时的引用重写、恢复后整份常驻内存（S5、S6）。

**minimal-runtime 的 message-stream 是什么、解决了什么**：它是**投递面**，不是消息模型（M3）。它解决的是「一个 Session 的客户端流如何把已提交事实与在途瞬态合成一条、断线重连不错位」：
持久游标带租户、会话、各域位置与可见性版本，并有 HMAC 完整性保护；活动源代际与水位只在进程内，重连必走先订阅重建；
事实队列满不丢，瞬态环满丢最旧并发 gap；单个订阅失败不影响共享源；`ended` 只是引用已提交处置的提示。
**它不定义消息、块、标注或流语法**——载荷是不透明 JSON，由源自带的 codec 解释。对 PF-009 而言它触及的只有 §6.9（用户看见的与日志一致）与 §6.16（砍了要说）两处。

### 8 脱离 loop 的可测性（问题六）

三源已有的零件：

| 链上的一环 | DSH | pi | MR |
|---|---|---|---|
| 脚本化的流事件源 | `tests/mock-adapter.ts` 的 chunk 数组构造器；**要经 Cordis 的 `LlmRuntime` 才能跑**（D11） | `providers/faux.ts` 可注册假 provider（P12） | 无（运行时未导入） |
| 事件 → 完整消息（含中断/截断收场） | `BlockAssembler`，纯（D5） | `reduceAssistantMessageFrames`，纯（P8）；中断/截断收场在 provider 实现与 agent-loop 里 | `BlockAssembler`，纯 |
| 语法校验 | 不变量伴件，要 `dsh-invariants` 服务（D5） | 帧归约内置校验（P8） | 无 |
| 完整消息 → 落盘 | `AssistantStreamAttempt.settle(eventType, append)`，回调式，**住在 agent-loop 包里**（D8） | 条目在 harness 的消息收尾时写（P7） | 未核对 |
| 日志 → 给模型那份 / 给人那份 | `deriveEventMessage` / `isAppendSurfaceEvent`，纯，住在 session 包（S3） | `convertToLlm` + `transformMessages`，纯（P6、P10） | 无 |
| 工具帧 → `ToolInternalMessage` | 无 | 无（只有瞬态事件） | 无 |
| 工具结果 → `ToolMessage` | `createToolResultMessage`，纯（D1） | 在 agent-loop 内构造 | 同 DSH |

**三源都没有一份「给一串流事件 → 得到落盘消息与两份组装输入」的单体测试夹具。**DSH 的零件最全，但这条链跨了三个包
（`dsh-llm` 的装配、`agent-loop` 的结算、`dsh-session` 的派生），其中结算与脚本化输入都绑在 Cordis 服务或 agent-loop 上；
pi 的链在 agent-loop 里闭合，脚本化输入与纯归约都在，但中间有 P7 的「半条消息进上下文」。

从 PF-009 的条款与三源的结构能读出：要让模型请求运行时与工具运行时各自不经 agent loop 就闭环，**链上每一环都得是一个能单独调用的接缝**——
脚本化事件源、语法校验、事件 → 完整消息（含三种收场）、完整消息 → 追加端口、日志 → 两份组装；工具侧再多一环「帧 → 那条消息」。
**上表里「无」与「住在 loop 包里」的格子，就是三源各自断开的位置。**这是对缺口位置的陈述，不是对接口形状的选择。

### 9 短板与代价（问题七）

**DSH**

- 成立条件：伴件装上时，流语法、账只一次、必有结局都有可执行检查；消息身份与不可变在创建时就成立；原始参数串一路保留到派发。
- 不解决什么：没有工具执行帧；没有块标注；没有提醒/压缩的独立类型；不补中断提醒（作者否决过）；语音不在词表里。
- 退化条件：不装伴件时，缺 finish 静默当作 stop、usage 后写覆盖（D5）；走 pi 路由时原始参数串变成重序列化结果（D10）；
  上游自己记下「一条始终不带工具调用身份的流仍会装配出空身份」未处理（dsh-llm 局限段）。
- 代价：类型文件直接扩展 Cordis 事件与 Typert 错误表，块类型依赖 `dsh-attachment`，运行时是 Cordis 服务、读 `fs` 服务（D12）——
  fork 时必须切掉这些，而 minimal-runtime 的切法同时切掉了两层兜底（M1）；session 格式背着三条迁移与「嵌流」的存储决定（S2、S5）；
  图→文本在出门时派生，与本项目「落盘前就地写」方向相反（D3）。

**pi**

- 成立条件：事件词表简洁、终止事件带完整消息；有假 provider 与纯归约，agent-loop 的流函数可注入；工具执行中有更新通道；日志只存成品。
- 不解决什么：没有消息身份、文件块、语音块、块标注、提醒/压缩的独立消息类型（后两者是应用层自定义消息）。
- 退化条件：工具参数在流中与收尾都做残缺解析，截断时「解析成功却缺字段」是作者自己写下的风险（P4）；中止/出错的消息整条对模型不可见（P6）；
  缺终止事件时等待方挂起（P5，推断）；更新监听者失败会拖垮工具结算（P9，推断）。
- 代价：块类型里嵌着供应商专属字段（`textSignature` 注 OpenAI、`thoughtSignature` 注 Google、`namespace` 注 OpenAI Responses，`Usage` 带计价），
  `AssistantMessage` 带 `api/provider`（P1、P2）；解析逻辑在六个 API 实现里各调一次（P4）；图字节内联（P2）；0.85.1 与 0.86.1 的差异未核（README 限制）。

**两源都不带块标注与模态文本字段的后果**：本项目要么在块上新增这两类字段并改写两源的装配、派生与出门投影，
要么在块之外另立一层映射——后者让「块上的标注是中枢机制」（PF-009 §4）与「转换件就地写块」（PF-013）失去字面上的落点。
两源的出门投影（D3、P11）都在做「没有文本那一份的图照样发给纯文本模型」，这正是 PF-013 §5.11 要从合法目标那一刻挡掉的情形。

### 11 产品正文里读出的张力与缺口（只报告，不裁决）

1. **PF-009 §6.6 与 PF-013 转换件的口径不一致。**PF-009 §6.6 的补充说「发给一个不支持图的模型时，adapter 自己去压……那是出门那一刻的事」
   （[§6.6](../../../design/product/PF-009-context-message-types/design.md#66-内容是块不在进日志时压成文本)，decisions.md 第 68 行同句）；
   PF-013 rev 4 的转换件把「转成文本」放在落盘之前、就地写在块上，没有文本那一份的块把收不下它的模型挡在合法目标之外（§4 转换件、§5.11）。
   按后者，adapter 在出门时不会遇到「要替不能看图的模型压图」的情形。两处都已接受，本轮不判哪句为准。
2. **出错断流、而用户已经看到了部分内容时，内容落在哪里没有说清。**§5.6 表第三行「出错断的：同上」（留尝试的账、没有这条消息），
   §6.9 又要求「用户看见了的，日志里必须有」，§9.2 不留到达的过程。三句合起来，「尝试的账」是否装着那段已交付的内容，正文没有说；
   DSH 的答案是把整条流嵌进 `assistant/attempt`（S2），那正是 §9.2 不要的。
3. **块的身份与嵌套块的标注没有定义。**PF-010 §5.7 要「点名一批消息内容块」，这需要块可被稳定寻址；PF-009 §4 定义了块，
   但工具结果「自己又是一串块」——嵌套在里面的块是否各带两个标注、能否被单独点名，正文没涉及。这属于技术设计要回答的问题，产品正文只需指路。
4. **语音的「给模型看」标注与「标注落盘即定」之间有时序张力。**PF-009 §5.7 表要求「用户没听到的那段语音」给模型 ✗，
   而 PF-010 §5.7 说块上的两位由产生者在落盘那一刻写、之后不变。播放进度是落盘之后才知道的（§5.9「进度从消费端流回生产端」），
   正文没有说明这段语音块何时落盘、或是否拆成已播/未播两块。§5.9 明说双工本版不解决，但单工语音同样有播放落差。

## 本轮结论

1. 消息类型层：前四种三源都有；后三种三源都没有独立类型——DSH 靠 `source.kind` 区分注入与工具结果，pi 靠应用层自定义消息。
2. 块层：DSH 的六类块覆盖 PF 七类中的六类（缺语音），参数保持原始串；pi 缺文件与语音，参数是解析对象。
3. 块标注与模态文本字段：三源都没有；两源的出门投影与 PF-013 转换件方向相反。
4. 流语法：DSH 最接近 §5.5（按 §4 计数），两源都缺填法声明与整体替换；只有 DSH 把「账只一次」「必有结局」写成可执行检查，但那是可选伴件。
5. 流断：三源对半截工具调用的处置互不相同，且都不同于 PF-009；pi 的残缺解析与「组装跳过 aborted」与 PF-009 直接冲突。
6. 工具帧：只有 pi 有执行中更新通道，形状是结果快照的瞬态广播；DSH 与 MR 没有。
7. 落盘：DSH 承载「只增不改、消息只是一部分」，但永久保存到达过程；pi 只存成品。
8. 可测性：三源都没有「事件序列 → 落盘消息 → 两份组装」的单体夹具；DSH 零件最全但散在三个包且结算绑在 loop 包。

## 本轮局限

- 全部为只读源码阅读，没有运行测试或构造探针；pi 的两条「挂起」「监听者失败拖垮结算」是推断。
- pi 只逐行读了 `openai-completions` 一个 API 实现；DSH 没读 `dsh-llm-deepseek` 的 SSE 翻译本体；两源的 issue tracker 未检索。
- minimal-runtime 没读 `session/{session, persistence, projection, run}`，落盘与 loop 行为记为「未核对」。
- PF-006 §5.4 `ToolResult` 的三样（进消息内容、要卸载的原始结果、附件地址）与三源工具结果形状的对照本轮没有展开。
