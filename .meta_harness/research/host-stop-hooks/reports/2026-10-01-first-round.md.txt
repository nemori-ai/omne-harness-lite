## 1. 一页结论

对照你要做的四件事（A 子代理收工触发；B 会话收工触发；C 把事实反馈给 agent 并让它继续；D 至多拦一次、钩子出错不拦人）：

| 需要 | Claude Code 2.1.287 | Codex CLI 0.159.0 |
| --- | --- | --- |
| A 子代理收工触发 | **能**。`SubagentStop`，输入带 `agent_id`、`agent_type`、`agent_transcript_path`、`last_assistant_message`；matcher 按 `agent_type` 过滤。也会因内部代理（提示建议、`/btw`）触发，此时 `agent_type` 为空串或会话的 `--agent` 名 | **能**。`SubagentStop`，输入带 `agent_id`、`agent_type`、`agent_transcript_path`、`last_assistant_message`；matcher 按 `agent_type`。只对「thread-spawned」子代理触发，内部合成子代理不触发（源码观察） |
| B 会话收工触发 | **能**。`Stop`：主代理每次答完一轮就触发（不只是任务完成），用户中断不触发，API 错误改触发 `StopFailure`。`SessionEnd` 也存在但不能拦、输出被丢弃 | **能**。`Stop`：根线程每轮收尾触发。`SessionEnd` 存在，但「advisory」、不能左右 Codex，且不对子代理触发 |
| C 反馈事实并让它继续 | **能**。`{"decision":"block","reason":…}` 或退出码 2 + stderr，`reason` 交给 agent 作为继续的依据；子代理上是「delivers `reason` to the subagent as its next instruction」。另有 `hookSpecificOutput.additionalContext`（同样让对话继续，只是标为 feedback 而非 error）。**同步钩子没有「只告知、不续跑」的通道**：`systemMessage` 只给用户看；「告知但不立刻续跑」只能用 `async` 钩子（下一轮才送达）。`SubagentStop` 的反馈只到子代理，不到主会话 | **能**。`{"decision":"block","reason":…}` 或退出码 2 + stderr；`Stop` 上它「creates a new continuation prompt that acts as a new user prompt」，`SubagentStop` 上「continue the subagent flow」。`Stop`/`SubagentStop` **没有** `additionalContext`（输出 schema `additionalProperties: false`）；`systemMessage` 只是 UI/事件流警告 |
| D 至多拦一次 | **有官方机制**：输入字段 `stop_hook_active`（Stop 与 SubagentStop 都有），钩子见 `true` 时放行；另有默认 8 次连续续跑上限（`CLAUDE_CODE_STOP_HOOK_BLOCK_CAP`，对两种事件都生效） | **有**：`stop_hook_active`（Stop 与 SubagentStop 都有）。文档没写次数上限；0.159.0 的 `turn.rs` 里续跑后只把它置 `true`，读到的代码里没有计数上限（源码观察） |
| D 出错不拦 | **基本成立**：除 2 以外的非零退出、启动失败（127）、超时（输出被丢弃）都是 non-blocking，agent 照常收工。**两处例外**：① 退出码 2 不论原因一律视为拦截（GNU make 失败时恰好退出 2）；② 非 0/2 退出但 stdout 是合法的 block JSON 时，「the JSON alone decides the outcome」，仍会拦 | **基本成立**：非 0/2 退出、超时、无效 JSON、退出 2 但 stderr 为空，都记为 Failed，不续跑（源码观察）。同样有「退出码 2 + 非空 stderr 即拦」的问题 |
| 配置源与信任 | 项目级 `.claude/settings.json` 的钩子在交互会话里要先接受目录信任（本机主检出已信任）；改了文件由 file watcher 自动重载，不必重启。`.claude` 为软链接：文档只在 settings.local.json 的信任规则里提到；本机用 `claude doctor` 验证过它会穿过软链接读到 `.claude/settings.json` | 项目 `.codex/` 层要项目受信任才加载；**另外每个非托管钩子都要在 `/hooks` 里按定义哈希逐条审核信任**，定义一改就被跳过直到重新信任（或每次用 `--dangerously-bypass-hook-trust`）。是否需要重启：文档未说明。`.codex` 为软链接：文档未说明，本机未验证 |

由此带来的限制（事实层面）：

1. 两个宿主上，「在收工点把事实送给 agent」都等于「让它继续干」；不存在同步的「只写进上下文、本次照常收工」的选项（Claude Code 的 async 钩子例外，见 Q3）。
2. 子代理收工点的反馈只回到**子代理**。Claude Code 官方给的「子代理返回后给主会话注入上下文」办法是 `PostToolUse` 挂在 `Agent` 工具上，但交互会话默认 fork 模式、子代理默认后台运行，后台子代理的 `PostToolUse` 在**转入后台时**就触发，不在完成时触发。
3. 两个宿主的 Stop/SubagentStop 都接受 `{"decision":"block","reason":"…"}` 这个最小形状；Claude Code 额外接受的 `hookSpecificOutput` 在 Codex 的 Stop/SubagentStop 上会被判为无效输出（不拦）。
4. 本环境的子代理在 auto 模式下用 `SubagentHandback` 交付报告。`SubagentStop` 在交付之后触发；此时拦下是否还能让子代理继续、报告是否已送出：**未知**（见第 5 节）。

### Q1 与「收工」相关的事件、触发时点、子代理识别

事件总表（[hooks] Hook lifecycle）里与收工相关的行，原文：

> | `SubagentStop` | When a subagent finishes |
> | `TaskCompleted` | When a task is being marked as completed |
> | `Stop` | When Claude finishes responding |
> | `StopFailure` | When the turn ends due to an API error |
> | `TeammateIdle` | When an [agent team](/docs/en/agent-teams) teammate is about to go idle |
> | `SessionEnd` | When a session terminates |

另：`Notification` 的 matcher 值里有 `agent_completed`，但该事件「No decision control」，不能反馈给 agent。

**Stop**（[hooks]#stop）：

> Runs when the main Claude Code agent has finished responding. Does not run if
> the stoppage occurred due to a user interrupt. API errors fire
> [StopFailure](#stopfailure) instead.

[guide]#limitations：

> `Stop` hooks fire whenever Claude finishes responding, not only at task completion. They don't fire on user interrupts. API errors fire [StopFailure](/docs/en/hooks#stopfailure) instead.

**SubagentStop**（[hooks]#subagentstop）：

> Runs when a Claude Code subagent has finished responding. Matches on agent type, same values as SubagentStart.

子代理收工触发的是 `SubagentStop`；子代理定义 frontmatter 里写的 `Stop` 会被转换（[hooks]#hooks-in-skills-and-agents）：

> **Subagent hooks**: Claude Code runs them only while that subagent is running and removes them when it finishes. Claude Code converts a `Stop` hook here to `SubagentStop`, the event it fires when a subagent completes.

能否区分是哪个子代理：能。`agent_type` 是 matcher 的依据，自定义子代理取 frontmatter 的 `name`（[hooks]#subagentstart）：

> For [custom subagents](/docs/en/sub-agents), this is the `name` field from the agent's frontmatter, not the filename.

> For subagents shipped by a [plugin](/docs/en/plugins/overview), the agent type is the plugin-scoped identifier such as `my-plugin:reviewer`, not the bare frontmatter name.

但并非每次 SubagentStop 都来自 Claude 派出的子代理（[hooks]#subagentstop-input）：

> Not every SubagentStop event comes from a subagent Claude spawned. Claude Code also runs internal agents for some of its own features, such as [prompt suggestions](/docs/en/interactive-mode#prompt-suggestions) and [`/btw` side questions](/docs/en/interactive-mode#side-questions-with-%2Fbtw), and SubagentStop fires when one of those finishes too. For those events, `agent_type` is the agent name the session itself runs as, such as one set with [`--agent`](/docs/en/cli-reference#cli-flags) or the [`agent` setting](/docs/en/settings-reference#agent), and an empty string when the session runs without one.

> A `matcher` that names agent types doesn't match an empty `agent_type`. A hook whose matcher is omitted, `""`, or `"*"`, or is a regular expression that matches an empty string, runs for events with an empty `agent_type` too.

**TaskCompleted**（[hooks]#taskcompleted）——只在使用 Task 工具或 agent team 时出现：

> Runs when a task is being marked as completed. This fires in two situations: when any agent explicitly marks a task as completed through the TaskUpdate tool, or when an [agent team](/docs/en/agent-teams) teammate finishes its turn with in-progress tasks.

**TeammateIdle**（[hooks]#teammateidle）：

> Runs when an [agent team](/docs/en/agent-teams) teammate is about to go idle after finishing its turn.

**SessionEnd**（[hooks]#sessionend）：

> SessionEnd hooks have no decision control. They can't block session termination but can perform cleanup tasks. Claude Code discards their [JSON output fields](#json-output), such as `systemMessage`.

**StopFailure**（[hooks]#stopfailure）：

> StopFailure hooks have no decision control. They run for notification and logging purposes only.

### Q3 怎样拦下收工并反馈；stdout／stderr 去向；JSON 字段

**退出码**（[hooks]#exit-code-output）：

> Exit 0 means success, and is the intended exit code when you print JSON for structured control.

> For most events, Claude Code writes stdout to the debug log and doesn't show it in the transcript. The exceptions are `UserPromptSubmit`, `UserPromptExpansion`, `SessionStart`, and `PostModelSwitch`, where Claude Code adds plain-text stdout as context that Claude can see and act on.

> Stderr from a hook that exits 0 goes to the debug log only, never the transcript, and Claude never sees it.

> Exit 2 means a blocking error. On [events that can block](#exit-code-2-behavior-per-event), exit 2 blocks whether or not you print JSON: even a JSON `permissionDecision` of `"allow"` can't override it. Claude Code still reads any valid [JSON output](#json-output) on stdout.

> The blocking message is the reason from your JSON's blocking decision when it makes one, and your stderr text otherwise.

> Any other exit code doesn't block on its own for most hook events. What happens depends on your stdout:
>
> * With a parsed object that passes schema validation, for events that use the standard decision model, Claude Code ignores the exit code and the JSON alone decides the outcome:

> * With stdout that Claude Code [treats as plain text](#exit-code-0), or with empty stdout, it's a non-blocking error for most hook events: the action proceeds, and the transcript shows a `<hook name> hook error` notice followed by the first line of stderr, prefixed with `Failed with non-blocking status code:`.

JSON 只在 stdout 以 `{` 开头、`}` 结尾时才解析：

> * **Starts with `{` and ends with `}`**: Claude Code parses it as JSON. …
> * **Starts with `{` but doesn't end with `}`**: Claude Code treats it as plain text.

退出码 2 的逐事件效果（[hooks]#exit-code-2-behavior-per-event）：

> | `Stop` | Yes | Prevents Claude from stopping, continues the conversation |
> | `SubagentStop` | Yes | Prevents the subagent from stopping |
> | `TeammateIdle` | Yes | Prevents the teammate from going idle, so it continues working |
> | `TaskCompleted` | Yes | Prevents the task from being marked as completed |
> | `StopFailure` | No | Output and exit code are ignored, except `terminalSequence` |
> | `SessionEnd` | No | Shows stderr to user only |

**通用 JSON 字段**（[hooks]#json-output）：

> | `continue` | `true` | If `false`, Claude stops processing entirely after the hook runs. Takes precedence over any event-specific decision fields |
> | `stopReason` | none | Message shown to the user when `continue` is `false`. It stays in the conversation, so Claude sees it if the conversation continues |
> | `suppressOutput` | `false` | Has no effect: Claude Code accepts the field but doesn't act on it. A successful hook's stdout is never shown in the transcript and is recorded in the debug log |
> | `systemMessage` | none | Warning message shown to the user. … |

> * **Top-level `decision` and `reason`** are used by some events to block or provide feedback.
> * **`hookSpecificOutput`** is a nested object for events that need richer control. It requires a `hookEventName` field set to the event name.

决策表（[hooks]#decision-control）：

> | UserPromptSubmit, UserPromptExpansion, PostToolUse, PostToolUseFailure, PostToolBatch, Stop, SubagentStop, ConfigChange, PreCompact | Top-level `decision` | `decision: "block"`, `reason`. Stop and SubagentStop also accept `hookSpecificOutput.additionalContext` for [non-error feedback that continues the conversation](#stop-decision-control) |
> | TeammateIdle, TaskCompleted | Exit code or `continue: false` | … |
> | Setup, Notification, SessionEnd, PostCompact, InstructionsLoaded, StopFailure, CwdChanged, DirectoryAdded, FileChanged | None | No decision control. Used for side effects like logging or cleanup |

**Stop／SubagentStop 决策**（[hooks]#stop-decision-control）：

> | `decision` | `"block"` prevents Claude from stopping. Omit to allow Claude to stop |
> | `reason` | Required when `decision` is `"block"`. Tells Claude why it should continue |
> | `hookSpecificOutput.additionalContext` | Non-error feedback for Claude. The conversation continues so Claude can act on it, but unlike `decision: "block"` it is shown in the transcript as hook feedback rather than a hook error |

> A hook that blocks by exiting 2 routes the same way as `reason`: Claude receives the stderr message as the explanation for why it should continue.

> Use `additionalContext` when the hook is working as designed and giving Claude guidance, such as "run the test suite before finishing". It keeps the conversation going through the same loop protections as `decision: "block"`, namely the `stop_hook_active` input and the 8-consecutive-continuation cap, but the transcript labels it `Stop hook feedback` and no hook error notification is shown:

SubagentStop 的反馈去向（[hooks]#subagentstop-input 末段）：

> SubagentStop hooks use the same decision control format as [Stop hooks](#stop-decision-control), including `hookSpecificOutput.additionalContext` with `hookEventName` set to `"SubagentStop"`, for non-error feedback that keeps the subagent running. Returning `decision: "block"` with a `reason` keeps the subagent running and delivers `reason` to the subagent as its next instruction. A hook that blocks by exiting 2 delivers its stderr message the same way. To inject context into the parent session after a subagent returns, use a [`PostToolUse`](#posttooluse) hook on the `Agent` tool instead.

而 `Agent` 工具的 `PostToolUse` 对后台子代理的时点（[hooks]#agent）：

> For background subagents, the tool returns when the task moves to the background, so `tool_response` carries no usage fields: a background launch returns immediately, and a foreground task that Claude Code backgrounds mid-run returns at that transition.

交互会话下子代理默认后台（[sub-agents]#run-subagents-in-foreground-or-background）：

> * Where [fork mode](#turn-fork-mode-on-or-off) is on, as it is by default in an interactive session, Claude Code runs the subagent in the background, forks and non-fork subagents alike, and Claude can't ask for the foreground.

**怎样「只反馈、不拦」**：文档里同步的 Stop/SubagentStop 钩子没有这一档——`additionalContext` 与 `block` 都让对话继续；`systemMessage` 是「Warning message shown to the user」，文档没说 Claude 能看到。可用的只有后台钩子（[hooks]#run-hooks-in-the-background）：

> After the background process exits, Claude Code delivers the `additionalContext` and `systemMessage` fields from the hook's JSON response to Claude on the next conversation turn. Unlike a synchronous hook's `systemMessage`, neither field is shown to you.

> * Hook output is delivered on the next conversation turn. If the session is idle, the response waits until the next user interaction. Exception: an `asyncRewake` hook that exits with code 2 wakes Claude immediately even when the session is idle.

> Async hooks can't block or control Claude's behavior: response fields like `decision`, `permissionDecision`, and `continue` have no effect, because the action they would have controlled has already completed.

字符上限（[hooks]#json-output）：

> A hook's `additionalContext`, `systemMessage`, and `initialUserMessage` strings, and its plain stdout, are capped at 10,000 characters:

文档未说明 `reason` 字段是否受同一上限约束。

### Q4 怎样保证「至多拦一次」

[hooks]#stop-input（见 Q2）：`stop_hook_active` 「is `true` when Claude Code is already continuing as a result of a stop hook」，并要求：

> Check this value or process the transcript to avoid blocking on a condition that will never resolve. Claude Code applies an 8-consecutive-continuation cap: after stop hooks have continued the turn eight times in a row, Claude Code overrides the next block and ends the turn. To raise the cap, set [`CLAUDE_CODE_STOP_HOOK_BLOCK_CAP`](/docs/en/env-vars).

[guide]#stop-hook-hits-the-block-cap 给的做法：

> Claude Code overrides a Stop hook after it blocks eight times in a row without progress. Your hook script needs to check whether it already triggered a continuation. Parse the `stop_hook_active` field from the JSON input and exit early if it's `true`:

子代理事件上同样可用：

- 文档：SubagentStop 输入列有 `stop_hook_active`（Q2 引文）；`additionalContext`「keeps the conversation going through the same loop protections as `decision: "block"`」。
- [env-vars]：

  > | `CLAUDE_CODE_STOP_HOOK_BLOCK_CAP` | Maximum number of consecutive times a [Stop](/docs/en/hooks#stop) or [SubagentStop](/docs/en/hooks#subagentstop) hook may block the turn from ending before Claude Code overrides it and ends the turn anyway (default: 8). Set to `0` to disable the cap. Raise this if your hook legitimately needs more iterations to resolve |

- 本机观察（2.1.287 二进制字符串）：`For Stop/SubagentStop hooks, check stop_hook_active in the input and return success while it's true. Set CLAUDE_CODE_STOP_HOOK_BLOCK_CAP to raise this limit.`

`stop_hook_active` 在什么时候复位为 `false`（例如下一条用户消息时）：文档没有明说。

另：`once: true` 不能用来做「每次收工至多一次」——

> | `once` | no | If `true`, Claude Code removes the hook after its first successful run. … Only honored for hooks declared in [skill frontmatter](#hooks-in-skills-and-agents); ignored in settings files and agent frontmatter |

### Q5 钩子出错、超时

默认超时与可配置（[hooks]#common-fields）：

> | `timeout` | no | Seconds before canceling. Claude Code doesn't enforce it on a command hook you run with [`async: true`](#run-hooks-in-the-background). Defaults: 600 for `command`, `http`, and `mcp_tool`; 30 for `prompt`; 60 for `agent`. … [`SessionEnd`](#sessionend) hooks share a 1.5-second budget; if your settings set a longer per-hook `timeout`, Claude Code raises the budget to match, up to 60 seconds |

超时的效果（[hooks]#timeouts）：

> Apart from a command hook you run with [`async: true`](#run-hooks-in-the-background), Claude Code cancels a `command`, `http`, or `mcp_tool` hook that reaches its [`timeout`](#common-fields), discarding the hook's output, so on most events a timed-out hook renders no decision.

启动失败（[hooks]#other-exit-codes）：

> A hook that can't start lands in the same non-blocking bucket. When the script path doesn't exist or isn't executable, the shell exits with a code like 127 and you see the same notice with the interpreter's message, … For most hook events, the action proceeds.

退出 1 不拦（同节 Warning）：

> Without valid JSON on stdout, Claude Code treats exit code 1 as a non-blocking error and proceeds with the action, even though 1 is the conventional Unix failure code.

两处会让「出错」变成「拦」的情形（都直接由上面的规则推出）：

1. 退出码 2 无论原因都拦。本机 `make -f /dev/null no-such-target; echo $?` 输出 `make: *** No rule to make target 'no-such-target'.  Stop.` 与 `make exit=2`（GNU Make 4.2.1）：钩子若直接把 make 的退出码透传出去，make 失败就会拦，stderr 成为拦截理由。
2. 非 0/2 退出但 stdout 已是合法的 block JSON：按「the JSON alone decides the outcome」仍拦。

### Q6 配置放在哪；优先级与合并；信任；重载；软链接

位置（[hooks]#hook-locations），原文表格：

> | `~/.claude/settings.json` | All your projects | No, local to your machine |
> | `.claude/settings.json` | Single project | Yes, can be committed to the repo |
> | `.claude/settings.local.json` | Single project | No, gitignored when Claude Code saves a setting to it |
> | Managed policy settings | Organization-wide | Yes, admin-controlled |
> | [Plugin](/docs/en/plugins/overview) `hooks/hooks.json` | When plugin is enabled | Yes, bundled with the plugin |
> | [Skill](/docs/en/skills) frontmatter | The rest of the session once the skill is invoked. … | Yes, defined in the skill file |
> | [Subagent](/docs/en/sub-agents) frontmatter | While that subagent is running | Yes, defined in the subagent file |

合并规则（同节）：

> Hook entries merge across settings levels rather than replacing each other: user, project, and local settings add their own hooks without removing managed ones, and the [`disableAllHooks`](#disable-or-remove-hooks) setting can't disable managed hooks from outside managed settings.

（[hooks]#hook-handler-fields）：

> All matching hooks run in parallel. If you define the same handler in more than one settings file, it runs once. A plugin's or skill's copy of the same handler stays separate.

一般设置的优先级（[settings]#settings-precedence）是 Managed > 命令行 > `.claude/settings.local.json` > `.claude/settings.json` > `~/.claude/settings.json`；钩子按上面的规则合并，不互相覆盖。`disableAllHooks` 按优先级取值（[hooks]#disable-or-remove-hooks）：

> Claude Code reads the value left after [settings precedence](/docs/en/settings#settings-precedence) applies, so a `"disableAllHooks": false` in a project's `.claude/settings.json` overrides a `true` in your user settings. … There is no way to disable an individual hook while keeping it in the configuration.

插件子代理不支持 frontmatter 钩子（[sub-agents]）：

> For security reasons, plugin subagents don't support the `hooks`, `mcpServers`, or `permissionMode` frontmatter fields.

**信任**（[hooks]#workspace-trust）：

> * **Interactive session**: Claude Code holds back hooks from every settings file, including your own `~/.claude/settings.json`, until you accept the [workspace trust dialog](/docs/en/permissions#project-allow-rules-and-workspace-trust) for the folder, or for a parent directory whose trust extends to it
> * **`-p` or SDK session**: Claude Code never shows the dialog and treats the folder as trusted, so hooks committed in a repository's `.claude/settings.json` run in a folder you've never trusted

信任的作用范围（[permissions]#project-allow-rules-and-workspace-trust）：

> * In a repository, Claude Code keys the trust on the git repository root, so the trust covers the whole repository apart from any git repository nested inside it, such as a submodule. In a [worktree](/docs/en/worktrees), it uses the main checkout's root, as it does for [saved rules](#permission-system).

子代理 frontmatter 钩子更严（[sub-agents]#hooks-in-subagent-frontmatter）：

> To let a project-level subagent's frontmatter hooks run, accept the [workspace trust dialog](/docs/en/permissions#project-allow-rules-and-workspace-trust) for the folder that contains the agent file. Hooks from user-level subagents in `~/.claude/agents/` and from definitions you pass with `--agents` run without this step.

> Until you trust the folder, the subagent still runs, but Claude Code skips its frontmatter hooks and logs an error to the debug log explaining how to trust the folder. This is a stricter rule than the one for hooks in settings files: trusting a parent folder isn't enough, and a `-p` session doesn't count as trusted.

skill frontmatter 钩子（[hooks]#hooks-in-skills-and-agents）：

> Frontmatter hooks in a project skill follow the same [workspace trust rule as hooks in settings files](#workspace-trust).

本机观察：`~/.claude.json` 里 `/data/qiwei/repos/omne-harness-lite` 的 `hasTrustDialogAccepted` 为 `true`；`~/.claude/settings.json` 没有 `hooks` 与 `disableAllHooks`。

**改了要不要重启**（[settings]#when-edits-take-effect）：

> Claude Code watches your settings files and reloads them when they change, so it applies most edits to the running session without a restart, including edits to `permissions`, `hooks`, and credential helpers such as `apiKeyHelper`. Claude Code also loads a settings file you create mid-session if its folder existed when the session started. For the project's `.claude/` folder, it loads the file even when you create the folder in the same session.

[guide]#hooks-shows-no-hooks-configured：

> * File edits are normally picked up automatically. If they haven't appeared after a few seconds, the file watcher may have missed the change: restart your session to force a reload.

子代理定义文件改动是否热重载：hooks/settings 页未说明。

**`.claude` 是软链接**：文档没有直接说钩子能否从软链接的 `.claude` 读取。唯一提到的地方是 settings.local.json 的信任规则（[permissions]#when-your-local-settings-file-needs-trust）：

> `.claude/settings.local.json` is normally your own file, so Claude Code applies its allow rules and additional directories without the trust step. When the file is tracked in git, or `.claude` is a symlink, Claude Code treats it as repository-supplied instead and holds its rules until you trust the folder.

### Q7 工作目录、环境变量、matcher

工作目录（[hooks]#hook-handler-fields）：

> Handlers run in the current directory with Claude Code's environment. If the current directory no longer exists, … Claude Code runs command hooks from the first of these that still exists: the directory the session started in, the project root, your home directory, or the system temp directory.

`CLAUDE_PROJECT_DIR` 与工作树（[hooks]#reference-scripts-by-path）：

> * `${CLAUDE_PROJECT_DIR}`: the project root where the session started.

> * **`${CLAUDE_PROJECT_DIR}` stays put**: it still points at the project root where the session started, so a command such as `${CLAUDE_PROJECT_DIR}/.claude/hooks/check-style.sh` still runs the script in the main checkout.
> * **`cwd` follows Claude**: the `cwd` field in the hook's [input JSON](#common-input-fields) is the worktree root after Claude enters a worktree, and the new directory after Claude runs `cd`. Read it when a hook needs to know which directory Claude is working in.

占位符同时作为环境变量导出（[hooks]#exec-form-and-shell-form）：

> Both forms support the same [path placeholders](#reference-scripts-by-path), and both export them as the environment variables `CLAUDE_PROJECT_DIR`, `CLAUDE_PLUGIN_ROOT`, and `CLAUDE_PLUGIN_DATA` on the spawned process,

shell 形式与 exec 形式（同节）：

> **Shell form** runs when `args` is absent. The `command` string is passed to a shell: `sh -c` on macOS and Linux, …

其他环境（[hooks]#common-input-fields）：

> A hook process inherits the parent environment, apart from the `OTEL_*` exporter variables that Claude Code [removes from every subprocess it spawns](/docs/en/monitoring-usage#administrator-configuration) …

另有 `CLAUDE_EFFORT`（[env-vars]：「Set automatically in Bash tool subprocesses and hook commands」）、`$CLAUDE_CODE_REMOTE`（远程 web 环境为 `"true"`）。本机观察：Bash 工具子进程里 `CLAUDE_PROJECT_DIR` 未设置（文档只说钩子、stdio MCP 与插件 LSP 进程会设）。

stdout 只能有 JSON（[hooks]#json-output）：

> Your hook's stdout must contain only the JSON object. If your shell profile prints text on startup, it can interfere with JSON parsing.

matcher（[hooks]#matcher-patterns）：

> | `SubagentStop` | agent type | same values as `SubagentStart` |
> | `UserPromptSubmit`, `PostToolBatch`, `Stop`, `TeammateIdle`, `TaskCreated`, `TaskCompleted`, `WorktreeCreate`, `WorktreeRemove`, `MessageDisplay` | no matcher support | always fires on every occurrence |

> If you add a `matcher` field to an event without matcher support, it is silently ignored.

matcher 的写法：只含字母、数字、`_`、`-`、空格、`,`、`|` 时按精确串（或其列表）匹配；含其他字符时按不加锚点的 JavaScript 正则匹配。`if` 字段只在工具事件上生效，「On other events, a hook with `if` set never runs.」

### Q8 prompt 型与 agent 型钩子

存在。处理器有五种（[hooks]#hook-handler-fields）：

> * **[Prompt hooks](#prompt-and-agent-hook-fields)** (`type: "prompt"`): send a prompt to a Claude model for single-turn evaluation. The model returns its decision as JSON. See [Prompt-based hooks](#prompt-based-hooks).
> * **[Agent hooks](#prompt-and-agent-hook-fields)** (`type: "agent"`): spawn a subagent that can use tools like Read, Grep, and Glob to verify conditions before returning a decision. Agent hooks are experimental and may change. See [Agent-based hooks](#agent-based-hooks).

`Stop`、`SubagentStop`、`TaskCompleted`、`TeammateIdle` 支持全部五种类型；`SessionEnd`、`StopFailure` 不支持 prompt/agent（[hooks]#prompt-based-hooks）。与命令型的区别：由模型返回 `{"ok": …, "reason": …}`，在 Stop/SubagentStop 上：

> * `Stop` and `SubagentStop`: the reason is fed back to Claude as its next instruction and the turn continues, unless the response also sets `impossible: true`, in which case Claude Code allows the stop and the turn ends

默认超时 prompt 30 秒、agent 60 秒；agent 型「experimental」。

### Claude Code 最小配置与脚本骨架（示例，未在本机运行）

只为说明字段怎么用，不是方案。`<path>` 是占位。

`settings.json` 片段：

```json
{
  "hooks": {
    "Stop": [
      {
        "hooks": [
          {
            "type": "command",
            "command": "python3",
            "args": ["${CLAUDE_PROJECT_DIR}/<path>/stop_hook.py"],
            "timeout": 60
          }
        ]
      }
    ],
    "SubagentStop": [
      {
        "matcher": "developer|verification-developer",
        "hooks": [
          {
            "type": "command",
            "command": "python3",
            "args": ["${CLAUDE_PROJECT_DIR}/<path>/stop_hook.py"],
            "timeout": 60
          }
        ]
      }
    ]
  }
}
```

要点：`Stop` 上的 `matcher` 会被忽略；`SubagentStop` 的 matcher 按 `agent_type` 精确匹配，写了类型名就不会匹配内部代理的空 `agent_type`；用 `args`（exec 形式）时占位符不需要加引号。

`stop_hook.py` 骨架：

```python
#!/usr/bin/env python3
# 示例，未在本机运行
import json, subprocess, sys

def main() -> int:
    try:
        data = json.load(sys.stdin)
    except Exception:
        return 0                          # 读不了输入：什么都不输出，退出 0 = 不拦
    if data.get("stop_hook_active"):
        return 0                          # 已经因 stop hook 续跑过一次：放行
    event = data.get("hook_event_name")   # "Stop" 或 "SubagentStop"
    workdir = data.get("cwd")             # 跟随 agent 的目录；CLAUDE_PROJECT_DIR 停在会话起点
    try:
        r = subprocess.run(["<度量命令>"], cwd=workdir,
                           capture_output=True, text=True, timeout=30)
    except Exception:
        return 0                          # 度量本身出错或超时：不拦
    facts = "<从 r.stdout 整理出的事实文本，空串表示没有要反馈的>"
    if not facts:
        return 0
    # 两个宿主的 Stop/SubagentStop 都接受这个最小形状
    sys.stdout.write(json.dumps({"decision": "block", "reason": facts}))
    return 0                              # 不透传被包命令的退出码（make 失败是 2）

if __name__ == "__main__":
    try:
        sys.exit(main())
    except Exception:
        sys.exit(0)
```

骨架体现的文档规则：stdout 只放一个 JSON 对象；只在要拦时输出 `decision`；所有失败路径退出 0 且不输出；`reason` 是否有长度上限见 Q3。

**拦下并反馈**：Stop（[cx-hooks]#stop）：

> `Stop` expects JSON on `stdout` when it exits `0`. Plain text output is invalid
> for this event.

> You can also use exit code `2` and write the continuation reason to `stderr`.

> For this event, `decision: "block"` doesn't reject the turn. Instead, it tells
> Codex to continue and automatically creates a new continuation prompt that acts
> as a new user prompt, using your `reason` as that prompt text.

> If any matching `Stop` hook returns `continue: false`, that takes precedence
> over continuation decisions from other matching `Stop` hooks.

SubagentStop（[cx-hooks]#subagentstop）：

> `SubagentStop` expects JSON on `stdout` when it exits `0`. Plain text output is
> invalid for this event.

> JSON on `stdout` supports [Common output fields](#common-output-fields). To ask
> Codex to continue the subagent flow, return:

```json
{
  "decision": "block",
  "reason": "Run one more focused pass inside the subagent."
}
```

通用输出字段（[cx-hooks] Common output fields）：

> | `continue`       | If `false`, marks that hook run as stopped      |
> | `stopReason`     | Recorded as the reason for stopping             |
> | `systemMessage`  | Surfaced as a warning in the UI or event stream |
> | `suppressOutput` | Parsed today but not yet implemented            |

> Exit `0` with no output is treated as success and Codex continues.

Stop/SubagentStop **没有** `additionalContext`：生成的 `stop.command.output.schema.json` 只有 `continue`、`decision`、`reason`、`stopReason`、`suppressOutput`、`systemMessage`，且 `"additionalProperties": false`；`schema.rs` 里 `SubagentStopCommandOutputWire` 带 `#[serde(deny_unknown_fields)]`。源码观察：解析失败时记 `"hook returned invalid stop hook JSON output"`，状态 Failed，不续跑。所以 Claude Code 风格的 `hookSpecificOutput` 在这里会使整条输出无效。

`systemMessage` 会不会进入模型上下文：文档只说「Surfaced as a warning in the UI or event stream」；源码里它变成 `HookOutputEntryKind::Warning`。是否给模型看：未知。后台（`async`）钩子能投递 `additionalContext`，但 [cx-hooks] 说「Background hooks can't block, approve, rewrite, or otherwise control the operation that triggered them」，且 Stop 的输出 schema 没有 `additionalContext` 字段；Stop 上的后台钩子能否投递上下文：未知。

**至多拦一次**：文档给的是 `stop_hook_active`（见上表）。源码观察（`core/src/session/turn.rs`）：每次 turn 开始 `let mut stop_hook_active = false;`，Stop 要求续跑并成功写入续跑提示后 `stop_hook_active = true; continue;`；若块里没有提示则发出警告「Stop hook requested continuation without a prompt; ignoring the block.」。读到的这段代码里没有次数上限；文档也没写。是否在别处另有上限：未知（未穷尽全仓）。

**出错／超时**（源码观察，`hooks/src/events/stop.rs` 的 `parse_completed`）：

- 运行出错（含超时，`command_runner.rs` 记 `"hook timed out after {}s"`）→ `HookRunStatus::Failed`，不拦。
- 退出 0：stdout 为空 → 成功；是合法 JSON → 按字段处理；不是合法 JSON → Failed。
- 退出 2：stderr 非空 → Blocked（续跑，stderr 为续跑提示）；stderr 为空 → Failed，记「Stop hook exited with code 2 but did not write a continuation prompt to stderr」。
- 其他退出码 → Failed（「hook exited with code {exit_code}」），不拦。

默认超时（[cx-hooks] Config shape 的 Notes）：

> - If `timeout` is omitted, Codex uses `600` seconds for most hooks.
>   - `SessionEnd` and `Interrupt` use `1` second by default and support up to `3` seconds.

SessionEnd 的出错（[cx-hooks]#sessionend）：

> They
> are advisory, so their output won't steer Codex or keep the thread open. If a
> command times out or exits with an error, Codex reports it as a hook failure.

**配置位置与合并**（[cx-hooks] Where Codex looks for hooks）：

> - `~/.codex/hooks.json`
> - `~/.codex/config.toml`
> - `<repo>/.codex/hooks.json`
> - `<repo>/.codex/config.toml`

> If more than one hook source exists, Codex loads all matching hooks.
> Higher-precedence config layers don't replace lower-precedence hooks.

> Project-local hooks load only when the project `.codex/` layer is trusted. In
> untrusted projects, Codex still loads user and system hooks from their own
> active config layers.

插件、托管（`requirements.toml`）也能提供钩子，见原页。

**逐条信任**（[cx-hooks]#review-and-trust-hooks）：

> Before a
> non-managed hook can run, Codex requires you to review and trust the exact hook
> definition. Codex records trust against the hook's current hash, so new or
> changed hooks are marked for review and skipped until trusted.

> Use `/hooks` in the CLI to inspect hook sources, review new or changed hooks,
> trust hooks, or disable individual non-managed hooks.

> For one-off automation that already vets hook sources outside Codex, pass
> `--dangerously-bypass-hook-trust` to run enabled hooks without requiring
> persisted hook trust for that invocation.

源码观察（`discovery.rs`）：哈希由 `hook_hash(event_name, matcher, &group, &config)` 计算，即钩子定义本身，不含脚本文件内容；信任状态从配置栈的 hook state 读取（`HookStateToml.trusted_hash`）。本机 `~/.codex/config.toml` 有一个空的 `[hooks.state]` 表；`~/.codex/hooks.json` 不存在；`/data/qiwei/repos/omne-harness-lite` 的 `trust_level = "trusted"`。工作树 `.worktrees/roles-review-loop` 自身是否算受信任项目：未知（项目根默认以 `.git` 判定，工作树里 `.git` 是文件；父路径的信任是否覆盖它，文档未说明）。

**工作目录与环境变量**：

> - Commands run with the session `cwd` as their working directory.
> - For repo-local hooks, prefer resolving from the git root instead of using a
>   relative path such as `.codex/hooks/...`. Codex may be started from a
>   subdirectory, and a git-root-based path keeps the hook location stable.

源码观察：只有插件钩子会额外注入 `PLUGIN_ROOT`、`PLUGIN_DATA`、`CLAUDE_PLUGIN_ROOT`、`CLAUDE_PLUGIN_DATA`；非插件钩子没有 `CLAUDE_PROJECT_DIR` 这类项目根变量。

**matcher**（[cx-hooks]#matcher-patterns）：

> | `SubagentStop`      | subagent type          | Values depend on the subagent that stops                     |
> | `Stop`              | not supported          | Any configured `matcher` is ignored for this event           |

**prompt/agent 型**：

> - `command` and `mcp_tool` handlers are supported. `prompt` and `agent`
>   handlers are parsed but skipped.

**`notify`**（[cx-adv] Notifications）：

> Use `notify` to trigger an external program whenever Codex emits supported events (currently only `agent-turn-complete`).

源码观察（`legacy_notify.rs`）：以 argv 末参传 JSON，stdin/stdout/stderr 都接 `Stdio::null()`，spawn 后不等待；文件里有注释「TODO: Remove this hook and its environment plumbing when legacy `notify` support is removed.」。它**不能**把输出反馈给 agent，也不能拦。另外 [cx-adv]：项目级 `.codex/config.toml` 里的 `notify` 被忽略（「Codex ignores the following keys in project-local `.codex/config.toml` … `notify`」）。

**子代理定义文件里能否写钩子**：[cx-sub] 说「Codex loads these files as configuration layers for spawned sessions, so custom agents can override the same settings as a normal Codex session config.」；这些层上的 `[hooks]` 是否生效，文档未说明，未知。

**改配置要不要重启**：文档未说明，未知。

**`.codex` 是软链接**：文档未说明；本机未验证。

**已知问题**：GitHub issue #17532「codex_hooks do not fire in interactive sessions when configured via repo-local .codex/config.toml」仍为 OPEN（2026-04-12 创建，评论里最后一次复现报告是 0.132.0，2026-05-21）。对 0.159.0 是否仍成立：未知。另有 #38142「[Hooks] interrupt_agent does not dispatch SubagentStop for interrupted child」、#33097（Windows 上自定义子代理不派发 SubagentStart/SubagentStop）均为 OPEN。

### Q10 没有等价能力的部分

Codex 有等价的「拦下收工并把 `reason` 交给 agent」能力，所以不是「没有」。和 Claude Code 相比**没有**的是：

- Stop/SubagentStop 上的 `additionalContext`（非错误反馈），查于 [cx-hooks]#stop、生成的 `stop.command.output.schema.json`；
- prompt/agent 型处理器（「parsed but skipped」）；
- 文档化的连续续跑上限（查于 [cx-hooks] 全页与 `core/src/session/turn.rs`）；
- 项目根环境变量（查于 `discovery.rs` 的 env 注入）；
- `notify` 的反馈能力（查于 [cx-adv] 与 `legacy_notify.rs`）。
