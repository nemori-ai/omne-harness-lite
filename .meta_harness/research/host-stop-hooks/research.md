# 在 agent 收工点把事实反馈给它，会撞上宿主的哪些行为

- 调查对象与日期：Claude Code `2.1.287`、Codex CLI `0.159.0` 的钩子机制，2026-10-01。
- 消费者：[宿主钩子的源](../../agents/hooks/README.md)。
- 最近核对：2026-10-01 / 上述版本。
- 当前结论：两个宿主都能在会话收工与子代理收工时触发命令钩子，并把一段文字交还给 agent；但在两端「交还文字」都等于「让它继续干」，
  退出码 2 一律当拦截，Codex 另要逐条信任。实际执行层面的几件事仍未知。

## 问题与区分条件

想在 agent 收工时把一组读数作为事实告诉它，要先知道四件事各自在两个宿主上成不成立：收工点能否触发；文字能否送达 agent；
能否保证至多拦一次；钩子自己坏了会不会把人拦住。任何一条不成立，这种反馈方式就要换通道。

## 证据入口

文档原句见[证据记录](evidence.md)的 E-1（Claude Code）与 E-2（Codex）；源码与本机二进制的观察见 E-3，那一组主会话没有复核。

## 当前结论

### C-1 两个宿主都有会话收工与子代理收工两个钩子事件，且子代理一侧能按类型过滤

Claude Code 的 `Stop` 在主代理每次答完一轮时触发（不只是任务完成），用户中断不触发；`SubagentStop` 的输入带 `agent_type`，
matcher 按它过滤。Codex 的 `Stop` 与 `SubagentStop` 同名同位，`SubagentStop` 的 matcher 同样是子代理类型。

- 适用范围：上述两个版本的文档。Claude Code 的内部代理（提示建议、旁问）结束时也会触发 `SubagentStop`，此时 `agent_type` 是空串或会话的代理名。
- 代价与不适用：`Stop` 每一轮都触发，钩子的耗时会加在每一轮的收尾上；两端的 `Stop` 都不认 matcher，只能在脚本里自己判断要不要动。
- 来源：E-1、E-2。
- 最近核对：2026-10-01。

### C-2 在收工点把文字交给 agent，就等于让它继续跑；没有「只告知、照常收工」的同步通道

两端都接受向标准输出写 `{"decision":"block","reason":"…"}`：Claude Code 把 `reason` 作为下一条指令交给 agent、这一轮继续；
Codex 的 `Stop` 据此「自动生成一条续跑提示」，`SubagentStop` 让子代理的流程继续。Claude Code 另有 `hookSpecificOutput.additionalContext`，
同样让对话继续，只是在记录里标为反馈而不是错误。

- 适用范围：同步的命令钩子。Claude Code 的异步钩子可以把内容留到下一轮再送达，本次没有展开。
- 代价与不适用：反馈一次就多一轮模型调用；子代理收工点的反馈只回到子代理，到不了派发它的会话。
- 撞上这条事实会怎样：把「提醒」做成收工钩子，就不存在不打断的提醒——每提醒一次，agent 就被叫回来一次。
- 来源：E-1、E-2。
- 最近核对：2026-10-01。

### C-3 两端在这两个事件上共同接受的输出只有最小形状；Codex 上多写字段会让整条输出无效

Claude Code 额外接受的 `hookSpecificOutput`，在 Codex 的 `Stop`、`SubagentStop` 上不在输出 schema 里。
文档一侧：Codex 写明这两个事件在退出 0 时要求标准输出是 JSON、纯文本无效。「未知字段使整条输出作废、因而不拦」来自对 0.159.0 源码的观察。

- 适用范围：文档部分对两个版本成立；「多一个字段即作废」只有源码观察支持，主会话未复核。
- 撞上这条事实会怎样：同一个脚本两端共用时，为 Claude Code 加的字段会让它在 Codex 上悄悄失效——不报错，只是不反馈。
- 来源：E-1、E-2；源码观察 E-3（仅转述）。
- 最近核对：2026-10-01。

### C-4 两端都给了「这次收工已经因钩子续跑过」的输入字段

`stop_hook_active` 在两端的 `Stop` 与 `SubagentStop` 输入里都有：为真表示这次收工已经是钩子续跑之后的。
Claude Code 另有连续续跑 8 次的上限。Codex 文档没有写次数上限。

- 适用范围：上述两个版本的文档。字段何时复位为假，Claude Code 文档没有明说。
- 撞上这条事实会怎样：钩子不看这个字段、又每次都返回拦截时，Claude Code 上最多连拦 8 次；Codex 上文档没有给出会停下来的保证。
- 来源：E-1、E-2。
- 最近核对：2026-10-01。

### C-5 钩子自己出错大多不拦人，但退出码 2 一律是拦截

Claude Code：除 2 以外的非零退出、超时、标准输出解析不了，都是不拦的错误，agent 照常收工；退出 2 不论有没有 JSON 都拦；
而标准输出是一份通过校验的 JSON 时，「JSON alone decides the outcome」，退出码被忽略。Codex 同样把退出码 2 加标准错误当作拦截的另一种写法。

- 适用范围：上述两个版本的文档。
- 撞上这条事实会怎样：GNU make 在目标失败时恰好退出 2。钩子命令经 make 调用、或把子进程的退出码原样透传，工具一出错就会把 agent 拦住。
- 来源：E-1、E-2。
- 最近核对：2026-10-01。

### C-6 Codex 的项目级钩子要过两道信任，定义一改就被跳过

Codex：项目的 `.codex/` 层受信任才加载项目级钩子；此外每条非托管钩子都要先审阅并信任它的定义，信任记在定义的哈希上，
新增或改过的钩子在重新信任之前被跳过。Claude Code 的项目级设置在交互会话里要先接受目录信任，设置文件改动由宿主自动重载。

- 适用范围：上述两个版本的文档。
- 代价与不适用：生成出来的钩子文件不等于生效；每个使用者、每次改定义之后，都要在自己的 Codex 里再信任一次。被跳过时没有报错。
- 来源：E-1、E-2。
- 最近核对：2026-10-01。

### C-7 Claude Code 的项目目录变量停在会话起点，不跟着进工作树

`CLAUDE_PROJECT_DIR` 作为路径占位符与环境变量提供给钩子命令。会话从主检出启动再进入工作树之后它仍指向主检出，这一点来自首轮报告对文档的转述与本机观察，
主会话只核对了变量本身存在；Codex 没有等价的项目根变量。

- 适用范围：变量存在——文档已核；「不跟着进工作树」——仅转述。
- 撞上这条事实会怎样：钩子命令用这个变量去找脚本时，在工作树里跑的是主检出那一份，读数对不上正在改的那棵树。
- 来源：E-1；E-3（仅转述）。
- 最近核对：2026-10-01。

## 支撑假设

| 假设 | 若它不成立，哪条结论垮掉 | 本轮是否核对 |
|---|---|---|
| 文档描述的行为就是这两个版本实际的行为 | 全部 | 未核对：没有注册并触发过钩子 |
| 宿主经软链接读到的 `.claude/settings.json`、`.codex/hooks.json` 会被实际执行 | C-1、C-6 的可用性 | 未核对：首轮只看到 `claude doctor` 能穿过软链接读到设置文件 |
