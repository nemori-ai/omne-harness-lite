## 完整报告正文

### 两份源各是什么

**DSH jobs** 是一个三包能力族。`dsh-jobs` 定义抽象 Cordis 服务 `JobRegistry`（`ctx.jobs`），九个方法：
`start / list / get / read / kill / wait / onJobDone / onJobsChanged / attachController`。长活的工具是 producer：
调 `start({kind, label, owner?, outputLimitBytes?, run})`，运行时做完全部可失败的预检后调一次 `run()`，
拿回 `{cancel, done, readOutput?}` 三个钩子，原子登记，发一个 `<kind>-N` 的 id。`dsh-jobs-local` 是唯一的提供者，
全部状态在进程内存。`dsh-tool-jobs` 给模型三个工具 `job_output / job_list / job_kill`，挂上运行时要求的「控制器」，
并把每次结算变成 agent 会话里的一条提醒（忙则注入下一步、闲则唤醒一轮，唤醒有预算）。

**local-execution** 是本仓库 minimal-runtime 分支里的一个单机执行者。它只做两件文件动作——预登记文件的有界读、
带内容修订校验的原子替换写——但把这两件事做成了「崩溃与停止下都说得清发生了什么」：每一步前后落持久账本、
停止先落墓碑再等真实静止、恢复不重放、效果与物理状态与清理三维分开记。

### 逐行论证

每一行先写两源的**成立条件**（在什么前提下这一格判得出来），再写**不解决什么**与**代价**。

**第 1 行 · 绑会话，不绑 agent runtime 与 run。**
DSH：授权看 `job.owner.id !== caller?.id`（`jobs-local index.ts:356-360`），这是 session id。
但 `ensureOwnerCleanup`（`:448-464`）要求 owner 是 agent 注册表里的当前实例，在 `owner.ctx.effect` 上挂清理；
`disposeOwned`（`:467-475`）在这个作用域撤除时取消、等结算、删记录。注记 `:50` 明写两种身份分工，`:138` 写后果
「Owned background bash now stops with its agent instead of surviving it」。
PF-006 §5.2 要的是后台执行不受发起它的 agent runtime 退役影响；PF-012 允许 agent runtime 随时起灭（I-2、I-6）。
两者放在一起，DSH 的挂法会让每一次 agent runtime 回收都连坐后台任务——判**不可承载**，因为要改的不是参数，
是「清理挂在哪个作用域上」这件事本身，以及随之的送达目标（tool-jobs 给活体 `Agent` 调 `inject/followup`）。
DSH 给的逃生口是不设 owner：`start` 不挂清理，任务对任何调用者开放（`assertAccess` 放行），活到服务撤除——
这换来了「活得比 agent 长」，却丢了会话栅栏，也仍然活不过进程。
local-execution：执行身份 `CallRef{owner: StepRef|WorkRef, callId, attemptId}`，`StepRef → RunRef → SessionRef{tenantId, sessionId}`
（`work-data index.ts:10,16-20,68`），记得下是哪个会话、哪次运行发起的——这正是 PF 表里「记录得下来」那一列。
但生命周期完全由 host 与部署租约决定，没有任何挂钩把执行与会话的存续连起来；判**需改**（身份可承载，寿命未覆盖）。

**第 2 行 · 前台/后台 × 等待态两维。**
DSH：bash 的执行函数在 `:348` 分岔，只有后台才 `jobs.start`（`:364`）；前台是 `await ctx.shell.run(... signal: exec.signal)`（`:379`）。
所以登记表只知道后台；前台执行对 jobs 不可见。等待态：`JobStatus`（`types.ts:17`）没有等待取值；
DSH 的等人 `ask_user_question` 是前台工具体里的 await（`tool-ask-user index.ts:1-5,90`）。「后台、在等应答」这一格 DSH 无法表达。
local-execution：定义直接写 `background: unsupported`（`plugin.ts:15`），也没有等待概念。

**第 3 行 · 后台由定义声明，不声明就不能；前台超时自动转。**
DSH 的「声明」是 producer 的部署配置 `enableRunInBackground`，默认 `true`（`tool-bash index.ts:40`；注记 `:88` 说 terminal、subagent 同此）。
方向与 PF「默认往保守的那一边倒」相反；归属也不同——PF 放在工具定义里，DSH 放在部署配置里。
自动转：无，理由见第 4 行。local-execution 有 `background.mode` 这个声明位，取值只有 `unsupported`。

**第 4 行 · 转后台＝换宿主。**
DSH 的 README Known Limitations 第三条「Foreground work cannot be promoted — producers choose foreground or background before starting」
（`jobs README.md:122`），注记 `:126` 给出理由（缺一个 SDK 没规定的用户交互契约）。技术上，前台执行的取消耦合在调用的 `exec.signal` 上
（注记 `:32`），登记表里没有它，就没有可以「换宿主」的对象。PF 的三个触发源（超时、手动、插队）全部是中途发生的——判**不可承载**。
反面：DSH 注记 `:32` 的一条规则正是换宿主的后半段——「id 一经发布，后续取消产生它的那次工具调用不得杀掉已发布的任务；取消归任务自己的控制器」。
local-execution：`design.md:126` detach 固定 unsupported。

**第 5 行 · 中断≠失败，说清原因，分得出谁掐的。**
DSH：`killed` 与 `failed` 分开（`types.ts:34`），`job_kill` 落 `killed`。原因：`kill(id, caller, reason)` 的 `reason` 只转给 producer，
tool-jobs 描述写「recorded in the log and forwarded to the job」（`tool-jobs index.ts:366`）；快照无原因字段。
agent 主动 `job_kill`、owner 撤除（`'owner disposed'`）、服务撤除（`'jobs service disposed'`）落同一个 `killed`，原因只在日志。
PF-007 §6.10 要求「agent 主动掐掉自己发起的执行，与用户叫停是两回事，要分得出是谁做的」。
另，`tool-bash background.ts:18-22` 的 TODO 承认非沙箱 spawn 失败会被映射成 `killed`——**失败可能以「被中断」出现**，与 PF 要挡的方向正好相反。
前台被取消时 bash 抛 `HarnessError(TOOL_ABORTED)`，经管线规范化为 `isError` 结果（`docs/tool-execution-pipeline.md:6`）——
PF §5.5 要求六种收场都以正常返回、带语义到达，而不是报错。判**需改**。
local-execution：停止栅栏命中时 `outcome: 'interrupted'`（`host.ts:714-717`），与 `failed` 分开；`controlOperation` 记下是哪次控制操作。原因的取值表没有。

**第 6 行 · 六种收场。**
DSH：终态三种；「转后台」由 producer 的正常返回 `{kind:'background', jobId}` 表达（注记 `:32`），渲染成 `started background job <id>`；
「不可用」在 DSH 属工具注册/可见性一侧，不经 jobs；「等不到应答」无。
local-execution：`succeeded / failed / interrupted / unknown / cancelled_before_execution`（`types.ts:57`）。`unknown` 是 PF §6.12 明文拒绝的「第七种」；
`cancelled_before_execution`（墓碑先于接纳）在 PF 词表里最近的是「被中断」。

**第 7 行 · 停机后不重来，算失败。**
DSH：`jobs README.md:53`、`jobs-local README.md:12,131` 三处说任务随进程消亡。重启后，会话日志里那条 `started background job bash-3`
仍在，但 `bash-3` 在新进程里查无此任务（`expect` 抛 `unknown job`，`jobs-local index.ts:345-348`），而且新进程的计数器从 1 重来，
**同一个 id 可能指向一个全新的任务**。没有任何持久事实能让系统在恢复时说出「这次执行失败了」——判**不可承载**（「不重来」这半句是自然成立的）。
注记 `web-background-job-display :108` 显示 DSH 考虑过把 `job/started … job/settled` 做成持久会话事件（带 `session/end-seed` 把未闭合的开头标为死历史），
为了不改持久格式而否决——那个被否决的方案恰好是「停机后落失败」需要的形状。
local-execution：`host.ts:247-265` 对有 `dispatch_intent` 无终态的 attempt 一律追加 `unknown / effect: possible / cleanup: retained`，从不重放；
「不重来」可承载，「算失败」需改。另，`design.md:164-170` 允许「accepted 而无 dispatch_intent」的 attempt 经恢复许可继续——
它的论证是「完整前缀可证明未进入效果位置」；PF §6.12 的理由是「它可能已经在外面做了事」，对这种可证明没动手的情形没有留例外。

**第 8 行 · 会话归档随之收场。**
DSH 有整套「owner 撤除 → 逐个 cancel（抛错则强制 failed 并警告可能孤儿）→ 等结算 → 删记录 → 标 reported 以免对一个正在销毁的收件人发提醒」
（`jobs-local index.ts:467-475,507-531`；`types.ts:120-127`）。这与 PF-015「收件人都没了，跑完也没处送」的理由同构；
差在触发点：DSH 是 Agent 实例撤除，PF 是会话归档（而 agent runtime 撤除按 PF 恰恰**不该**带走后台执行）。判**需改**。
local-execution：`requestStop` 可对任一执行（甚至尚未 start 的）落墓碑，机制可用；没有会话归档的钩子，只有 host `close()` 对全部未终态执行发协作停止。

**第 9 行 · 单独控制。**
DSH 的 `kill` 是逐任务的，但只对后台；前台单独中断依赖 `exec.signal` 的派生关系，本轮没有追到 agent-loop 里确认能否只取消一次调用而不取消整轮，记为未知。
local-execution 逐执行 `requestStop`，协作式；`force` 返回 unsupported（`host.ts:766-778`）。

**第 10 行 · 发帧。**
DSH `readOutput`：消费式增量、每任务一个游标（`types.ts:85-90`），读者是模型（`job_output`）。PF：读者是人，agent 看不到，
汇成一条 `ToolInternalMessage`。二者读者相反，且 DSH 的游标一旦被人读就会从模型那里「偷走」输出（`jobs README.md:121`、注记 `:80`）。
DSH 给浏览器的只有整表快照帧 `{type:'jobs', sessionId, jobs}`，逐任务输出流给人看被列为下一阶段（web 注记 `:21`）。判**不可承载**（作为帧）。
local-execution：`frames: []`、`subscribe` unsupported；`design.md:188-192` 明写将来加帧不得静默降级为内存帧。

**第 11 行 · 等待态原语。** 两源都没有。见第 2 行。

**第 12 行 · 卸载。**
DSH `outputLimitBytes` 是 producer 自选的 UTF-8 字节上限，tool-jobs 用首尾保留的截断实现（`tool-jobs index.ts:110-166`），只作用于后台读与完成提醒；
不存原件、不给分页取回。PF §6.10 把「系统兜底」定义为首尾保留的机械截断，DSH 的截断与之形似，但 PF 要求原始结果存着、能取全文。
按 PF §6.10 卸载的判断与执行归 agent-loop，不在工具执行运行时。local-execution 读超上限直接 `failed{limit_exceeded}`。

**第 13 行 · 后台跑完以提醒到达。**
DSH tool-jobs `onJobDone`：已 `reported` 或无 owner 则不送；闲置且在预算内 `followup` 开一轮，否则 `inject`（`:278-299`）。
与 PF「跑完之后以提醒的形式到达 agent」同向；差在收件人是 `Agent` 实例而不是会话，owner 被撤时挂着的提醒丢失（README `:175`），
以及「驱动退役窗口」内结算的提醒会搁浅（README `:173`，作者说该在 agent-loop 修）。
local-execution 的 `terminals` 端口：只发执行身份铃，消费者按身份重读持久终态，启动后自行扫描补漏（README `:28-33`）——
这是「提醒不丢」的持久半边，但没有「提醒」这种消息。

**第 14 行 · 每次执行一份账。** DSH 只有起止时间且随进程消失；local-execution 有持久账本与零价计费来源（只对文件动作）。

**第 15 行 · 租户。** DSH 无租户维度；local-execution 的引用类型带 `tenantId`，资源注册与授权范围按租户核对（`host.ts:404,471,482`）。

**第 16 行 · 执行落点。** 两源都不管。DSH 的落点在 producer 与沙箱包；local-execution 只有一个部署独占目录，并声明不是沙箱。

### 问题二：in-memory 假设与改动面

**DSH 有，而且在两层。**实现层：`jobs-local` 的 `store`、`counters`、`layers`、`ownerCleanups`、每任务的 `waiters/waitResolvers/settled`
全部是进程内对象（`index.ts:39-63,102-119`）。契约层：`run()` 同步返回闭包、`done` 是 Promise、owner 与完成监听参数是活体 `Agent`、
id 由进程内计数器生成。DSH 两处自承持久后端需重塑 identity、restart、ownership、observation（`jobs README.md:120`、seam 注记 `:22`）。

在 D-026 下，本轮估计的改动面：

| 块 | 现状 | 要动什么 | 量级 |
|---|---|---|---|
| 提供者 `jobs-local` | 534 行，全内存 | 记录与状态迁移改经 `core/storage`；活体钩子表留在进程内 | 重写 |
| 契约 `types.ts` / `index.ts` | owner、listener 以 `Agent` 为类型；无恢复方法 | owner 换成可序列化的会话引用；增加恢复/枚举在途；id 生成跨重启唯一 | 改签名，波及全部 producer 与 tool-jobs |
| `reported` | 内存布尔 | 持久化，否则重启后提醒去重失效 | 小，但语义敏感 |
| 不变式 companion | `ownerSession === owner?.id` | 随 owner 类型改 | 小 |
| 恢复路径 | 不存在 | 恢复时把在途记录落成终态（按 PF 为「失败」）并送达会话 | 新增 |

判断前提（已在 research 标出）：D-026 点名的是存储与消息队列；`cancel` 回调、waiter 这类活体句柄只能在进程内，本表把它们算运行时句柄。

**local-execution 没有内存版记录**——账本是 fsync 的 JSONL，设计正文还专门禁止以内存 Map 代替停止协议（`design.md:50-51`）。
它与本项目约束的冲突在另一处：记录不经 `core/storage` 协议，自带文件格式、单写者租约、64 MiB 上限且不压缩。

### 问题三：运行时与 tool-jobs 的耦合

代码依赖单向（tool-jobs → jobs）。运行时对工具面的唯一硬要求是 `start` 时至少一个控制器服务该 owner，`attachController` 公开，
非模型控制器可以自挂（注记 `:70`）——**只取运行时在代码上可分**。留在工具面一侧、分开后要自己补的：
完成送达（提醒消息的形态、忙注入/闲唤醒、唤醒预算、依赖 `agent/inbox/claimed` 与 `owner.followup/inject`）、
输出上限在工具管线上的落实（`tools/pre-execute` 监听 + `finalizeContent`）、系统提示词片段。
留在运行时契约里、却是为工具面设计的：`reported` 字段与置位规则（`types.ts:120-127`、`jobs-local index.ts:211,219,225,277,422,517`）、
`outputLimitBytes`（运行时只校验并投影，不使用）。只取运行时，这两样在契约里没有消费者，要么删、要么由新的送达方接手。

### 问题四：local-execution 的覆盖、不做与已知问题

覆盖：见 research「只执行预登记文件……」一条。明确不做：shell、子进程、网络、动态回调、后台/detach、帧、限时强停、forced isolation、任意路径、创建目标文件。
已知问题两件：（1）停止与 I/O 交错——rename 前最后放行检查与真实 rename 之间的异步交错点，`e14a34c` 窄修、`245ef05` 推广到 rename 前各步，
实施侧承认仍是局部证据；源码仍有 `await markers.mayContinue()` 的三处调用（`filesystem.ts:313,346,366`），本轮未逐一判它们是否都已在串行门内。
（2）rename 窗口——Node 不能让修订核对到 rename 成为条件操作，靠部署独占租约兜底；租约遗留即拒绝启动，需部署层证明旧 owner 不可能再运行。
与 DSH：互补为主（见 research 对应结论），重叠只在四个动作的形状上，且语义不同。

### 问题五：短板与代价（两源并列）

| | DSH jobs `c291e796` | local-execution `d79484d` |
|---|---|---|

### 问题六：两源都没覆盖的责任

见 research 最后一条结论的九项。本轮额外观察：第 7 项（停机后落失败并送回会话）在两源里各有一半线索——
local-execution 有「持久在途记录 + 恢复折叠」，DSH 否决过的 `job/started … job/settled` + `session/end-seed` 方案有「在会话日志里把未闭合的开头标成死历史」的形状——
但两源都没有把两半接起来。

## 本轮结论

1. DSH jobs 的后台任务寿命挂在活体 Agent 实例上，与 PF「绑会话、不绑 agent runtime」不可调和，改的是契约面。
2. DSH jobs 只登记后台、不能中途转后台；PF 的三个转后台触发源全部落空。
3. DSH jobs 契约与实现两层都是进程内的；满足 D-026 要重写提供者并改契约签名，且需新增恢复路径。
4. DSH jobs 无等待态、无「等不到应答」、不记中断原因与发起者；bash 的失败映射还可能把失败记成中断。
5. DSH 后台默认开启，方向与 PF 相反，且归属在部署配置而非工具定义。
6. DSH 运行时可在代码上脱离 tool-jobs，但完成送达与 `reported` 语义横跨两者。
7. DSH 的流式输出是给模型的单游标拉取，不是给人的帧。
8. local-execution 覆盖两种文件动作的持久执行与协作停止；不做 shell、后台、帧、等待态。
9. local-execution 停机恢复不重放，但落「状态不明」；「accepted 未 dispatch 可继续」与「停了不重来」之间有待裁问题。
10. local-execution 的账本不经存储协议，且有 64 MiB 硬上限。
11. local-execution 的停止协议有过真实竞态，已局部修复，未被规格落条与组合验收覆盖。
12. 两源互补为主；共同空白九项。
