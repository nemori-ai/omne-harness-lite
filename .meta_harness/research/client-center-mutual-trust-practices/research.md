# 客户端与自托管控制面之间怎样互相确认身份

- 调查对象与日期：RFC 6750（Bearer Token Usage）、RFC 8705（OAuth 2.0 Mutual-TLS）、RFC 9449（DPoP）；kubeconfig v1、Vault CLI、OpenSSH `ssh_config`、Syncthing 设备 ID、PostgreSQL 16 libpq；2026-09-23
- 消费者：D-029；`apps/cli` 与 `apps/tenancy-host` 两个节点；账号能力「到期与刷新」的将来提案
- 最近核对：2026-09-23（首轮）
- 当前结论：服务端身份靠证书加客户端主动核对，核对只有「CA 链加主机名」与「记住指纹」两条路，没有产品默认跳过；终端用户认人普遍用持有型令牌加三条缓解；令牌绑客户端密钥是可选加固；双向 TLS 主要用于机器身份。

## 问题与区分条件

要核实的主张有四条：（1）自托管控制面的客户端怎样确认服务端是真的；（2）持有型令牌的风险边界与业界接受它的前提；
（3）「偷了令牌也用不了」的加固手段是否有标准；（4）双向 TLS 在终端用户场景的普及程度。
什么观察会改变边界：若有主流自托管产品默认不核服务端证书，结论一垮；若 RFC 6750 之外没有对持有型令牌的标准缓解，结论二垮。

## 证据入口

[evidence.md](evidence.md) 的 E-1（RFC 6750）、E-2（RFC 9449）、E-3（RFC 8705）、E-4（kubeconfig）、E-5（Vault）、E-6（OpenSSH）、E-7（Syncthing）、E-8（PostgreSQL libpq）。

## 当前结论

### 服务端身份一律靠证书加客户端主动核对，核对只有两条路，没有产品默认跳过

kubeconfig 用 `certificate-authority`／`certificate-authority-data` 带私有 CA，`tls-server-name` 定核哪个主机名，`insecure-skip-tls-verify` 是显式开关且文档写明「会让连接不安全」（E-4）；
Vault 用 `VAULT_CACERT` 与 `VAULT_TLS_SERVER_NAME`，`VAULT_SKIP_VERIFY` 同样是显式开关（E-5）；
PostgreSQL 的 `sslmode` 只有 `verify-full` 同时防窃听与中间人，`require` 明说「我信任网络会把我连到对的服务器」，默认 `prefer` 不防中间人（E-8）。
另一条路是「记住指纹」：OpenSSH 默认 `StrictHostKeyChecking=ask`，新主机要人确认后才记入 `known_hosts`，指纹变了拒绝连接（E-6）；
Syncthing 的设备 ID 就是证书 DER 的 SHA-256，双方在握手时算出对端 ID 与配置比对，不匹配不接（E-7）。

- 适用范围：以上七个对象的所列版本；对「自托管、客户端可配置」这一类成立，不推广到浏览器（浏览器只有公共 CA 一条路）。
- 代价与不适用：CA 链那条路要有人签发与分发根证书，主机名要稳定；记指纹那条路首次连接要人肉比对，服务端换证书就要重新确认，多台客户端各记各的。
  两条路都不解决「客户端机器本身被拿」。
- 撞上这条事实会怎样：把「跳过校验」做成默认或做成静默，TLS 只剩加密没有身份，登录凭证会交给任何在路上的人，且不报错。
- 来源：E-4～E-8。
- 最近核对：2026-09-23

### 持有型令牌是终端用户 API 的通行做法，标准给它三条缓解

RFC 6750 §1.2 明说「任何持有它的一方都能用它访问资源」；§5.2 的缓解是三条「必须」加两条「应当」：必须走提供机密性与完整性的 TLS、客户端必须核 TLS 证书链、客户端必须保证令牌不泄漏给非预期方；令牌服务应当签短寿命（一小时以内）令牌，令牌不应放 URL（E-1）。
kubeconfig 的 `token` 字段与 Vault 的 `VAULT_TOKEN` 都是这类令牌（E-4、E-5）。

- 适用范围：RFC 6750 定义的 Bearer；对任何「凭证本身不证明持有者」的凭证同样成立。
- 代价与不适用：泄漏即冒用，直到过期或撤销；「短寿命」要有刷新机制配合，否则用户频繁重新登录。它不解决客户端机器被拿。
- 撞上这条事实会怎样：不给寿命也不给撤销的持有型凭证，泄漏后永久有效；只给撤销不给寿命，泄漏后能用到有人发现为止。
- 来源：E-1、E-4、E-5。
- 最近核对：2026-09-23

### 「偷了令牌也用不了」有两份标准：绑到客户端密钥（DPoP）或绑到客户端证书（mTLS 绑定令牌）

RFC 9449 的目标是「防止未授权方使用泄漏或被盗的访问令牌，方法是签发时把令牌绑到一个公钥，使用时要求客户端证明持有对应私钥」，并自述为「对不可预见的令牌泄漏的纵深防御」（E-2）。
RFC 8705 用双向 TLS 把令牌绑到客户端证书，「防止被盗令牌被未授权方使用或重放」，并给出 PKI 与自签名两种客户端认证方式（E-3）。

- 适用范围：OAuth 2.0 生态；机制本身（请求附带持有证明）可脱离 OAuth 使用。
- 代价与不适用：客户端要生成并保管一对密钥，每个请求多一段签名；服务端要核签名与防重放（nonce 或时间窗）；令牌与密钥同时被拿仍然失守。
- 撞上这条事实会怎样：把持有证明设计成可选、又不给服务端拒绝无证明请求的规则，加固形同虚设。
- 来源：E-2、E-3。
- 最近核对：2026-09-23

### 双向 TLS 主要用于机器身份，终端用户场景把它当可选项

kubeconfig 的 `client-certificate` 与 `token` 并列为两种认人方式（E-4）；Vault 有 `VAULT_CLIENT_CERT` 但认人主路是 `VAULT_TOKEN`（E-5）；
RFC 8705 把双向 TLS 定位为「OAuth 客户端认证」即程序身份，不是用户身份（E-3）。

- 适用范围：所列对象。
- 代价与不适用：每个客户端要签发、分发、轮换证书；对终端用户来说是「装一张证书」的负担，所以主流产品把它留给自动化与服务间调用。
- 来源：E-3～E-5。
- 最近核对：2026-09-23
- 状态标记：待核实——服务网格（SPIFFE）、WireGuard 与 Tailscale 的静态密钥对、Docker 守护进程 `--tlsverify` 本轮未取原文，只作旁证不入结论。
