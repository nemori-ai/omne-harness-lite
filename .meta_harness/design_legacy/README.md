# 系统设计链

这里维护待设计系统从需求到实现映射的完整设计链。各 family 入口导航实际 topic 与本地模板；
目录内容随采用基线演进，不能用迁移阶段或一次性数量描述长期状态。

| 目录                                    | 归属                                         |
| --------------------------------------- | -------------------------------------------- |
| [requirements/](requirements/README.md) | 产品需求、系统目标、全局约束及可选访谈语境   |
| [research/](research/README.md)         | 可核对的观察、来源与局限                     |
| [proposals/](proposals/README.md)       | 能力覆盖、剩余责任与候选设计取舍             |
| [decisions/](decisions/README.md)       | 已接受选择、理由、范围与取代关系             |
| [architecture/](architecture/README.md) | 当前系统视图、能力基与组合关系               |
| [spec/](spec/README.md)                 | 精确规格及唯一 catalog、冻结与形式任务记录   |
| [providers/](providers/README.md)       | 按实际产品包组织的插件提供者设计与符合性证据 |
| [assemblies/](assemblies/README.md)     | 按实际应用组织的组合、配置与真实集成证据     |
| [migrations/](migrations/README.md)     | 长期迁移约束、来源与实际执行记录             |

## 状态词怎样组合

这些词描述不同维度，不组成一条可以凭较后状态倒推较前状态的流水线：

| 状态词 | 精确含义 | 不能据此声称 |
|---|---|---|
| `candidate` | 内容可被审阅，选择或新谱系采用仍未由有权者闭合 | 已接受、已冻结或可供消费者发布使用 |
| `accepted` | 有权者接受精确对象、修订和范围；接受依据可定位 | 资源已冻结、实现符合或应用已经装配 |
| `frozen` | 已接受版本的精确资源 hash 进入不可原地改写的发布集合 | provider 已实现、模型已运行或消费者已升级 |
| `implemented` | 具名提供者在固定源码修订上声称兑现精确契约，并有相称符合性证据 | 应用选择了该提供者，或完整动作链成立 |
| `assembled` | 具名应用选择精确提供者、配置和版本，并通过真实组合证据 | 所有部署或未覆盖故障条件都成立 |
| `gap` | 某个必要语义、证据、提供者、采用或装配输入仍缺失；必须标明 owner 与闭合条件 | 对象不存在，或可以用相邻状态替代 |

同一对象可以同时是 accepted/frozen 的规格、尚未 implemented 的提供者和尚未 assembled 的应用。
入口只解释词义；实际状态由对应 decision、catalog/frozen、provider verification 和 assembly evidence 拥有。

## 家族准入与停止条件

材料进入本目录，是因为后续设计或维护会持续消费其中的知识。先判断知识的拥有者，
再选择 family 和模板；完成一次任务、写成 Markdown 或已经过评审，都不是准入理由。

| family       | 进入前必须能回答                                                   | 不满足时停止在何处                                                          |
| ------------ | ------------------------------------------------------------------ | --------------------------------------------------------------------------- |
| requirements | 正式结果能否说明观察者、情形、来源与确认范围；或访谈语境是否可恢复且值得持续回顾 | 前者不足时不补造条款；有长期价值的来源语境进 interview，短暂输入留任务区 |
| research     | 哪个持续设计判断会消费这项可复核观察；对象/版本、方法和局限是什么  | 一次检索与原始日志留在 `tmp/`；事实不足时只保留待验证命题                   |
| proposals    | 同一选择对象、现有能力覆盖与剩余责任，以及至少三个实质候选能否比较 | 不足三个真实候选时留在 research/任务探索；已有决定下的普通施工不建 proposal |
| decisions    | 谁在何种权限范围接受了哪个精确修订的哪些内容                       | 没有实际接受就留在 proposal；评审意见和作者推荐不能升级状态                 |
| architecture | 哪个需求/决定/catalog 快照支撑当前能力基、组合与覆盖范围           | 采用关系不明时只记录候选或资料缺口，不建立第二份契约/catalog                |
| spec         | 语义拥有者、稳定身份、适用范围、精确版本、依赖和接受状态是什么     | 语义或接受未定时保留候选；未处理已触发的形式义务时阻止发布/消费             |
| providers    | 哪个精确能力契约由哪个具体插件/服务兑现，源码与符合性状态是什么    | 只有机制设想时回 proposal；找不到实际提供者时记录实现缺口，不虚构交付       |
| assemblies   | 哪个应用实际选择哪些提供者/配置，怎样完成动作链及真实集成验证      | 选择或组合前提未定时保持候选；各模块局部通过不能升级为装配完成              |
| migrations   | 哪些前后身份/采用关系、过渡约束和消费者退出条件会被长期消费        | 计划、派发、文件清单和进度始终留在 `tmp/`；没有持续迁移对象就不建 topic     |

各 family 入口拥有具体准入、停止条件和模板使用要求。一次施工的工作材料放本次明确工作区的 `tmp/`；
任务完成后只将有持续消费价值的结论整理回对应拥有者，不把整份计划和任务日志转为长期主题。
可复用设计方法及其演化归 `harness-design-handbook` skill
与不分发的 `.design/` 维护证据，不冒充待设计系统的知识。

## 主题是信息包

每个 family 的 README 导航实际主题和本地 `.templates/`；每个 topic 子目录的 README
导航本主题的范围、输入、当前状态与按需正文。先读入口，当前问题需要时才展开详细设计、取舍、证据或评审。

例如：

```text
proposals/
├── README.md
├── .templates/topic/
│   ├── README.md          可复制的主题入口
│   ├── design.md          现有能力覆盖、演化与契约/插件设计
│   ├── alternatives.md    候选比较与依据
│   └── review.md          实际评审与处置
└── <topic>/               实际主题，由模板包起步
```

### 建包与维护

1. 先找现有主题；只有形成新的持续消费对象时才复制相应模板包，给子目录取可辨认的主题名。
2. 模板提示和 `{{说明}}` 是填写指导，成稿时替换或移除；不伪造身份、来源、接受或执行记录。
3. 以包为单位起步、按实际问题裁剪正文与附属材料；删除不适用文件时同步入口链接，保留影响结论的未知及闭合条件。
4. 包内链接保持相对路径，复制后仍可导航。跨包引用实际主题及可恢复修订，不引用模板包作为需求、决定或契约依据。
5. 每项含义只有一个拥有者；入口给摘要与路由，正文保存判断，证据保存观察，评审保存意见与处置，不在几个文件中维护同义权威。

这是信息组织单元，不要求每个主题具有相同文件数，也不要求每个需求依次创建所有 family。
研究、候选规格、原型可相互校准；同一主题的输入与结论有明确快照，实际状态逐项记录。
短小局部改动直接修改已有正文；任务级排期与进度仍放工作区 `tmp/`，稳定知识回到其拥有者。

## 知识怎样被下一步消费

- 需求保存可观察结果和确认范围；提案检查现有能力及组合，把未覆盖责任解释为组合、扩展、新增等演化。
- 新独立维度给出独立插件边界；精确承诺归规格，具体兑现归提供者/装配，整体保证仍须检验所有组合前提。
- 决定记录真实接受范围，规格记录精确版本；接受后的变化更新能力地图，使下一项需求能找到新的承载者。
- 验证记录反馈实现违约、语义遗漏、前提变化或新要求；研究/提案/决定按其职责处理，不用新结果暗改旧规范。

`.templates/` 只拥有模板，不是实际知识主题；它不参与能力地图、接受/发布清单或正式规格发现。
各 family 维护自己的模板形状，skill 不维护另一份副本。模板不是登记格式，也不自动创建 catalog。

具体方法继续由 `harness-design-handbook` skill 按需导航。

可复用方法按 `harness-design-handbook` skill 渐进展开；产品事实和接受状态只由本设计链的实际 owner 维护。
