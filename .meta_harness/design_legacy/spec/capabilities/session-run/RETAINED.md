# 为什么把这一份留下来

> **它只是「可能有用」，所以暂时留着。**
> **它不是必须被用到的东西，也不代表它一定就有价值。**
> 将来有人读完判断用不上，**直接删掉是合理的结论**，不需要先证明什么。

## 它是什么

2026-09-20 从承载仓库根 `spec/capabilities/session-run/` 原样取来的留档：
v1 与 v2 的契约正文、v1 的 `QueueControl` 形式模型与配置。

**这是根 `spec/` 相对本目录唯一独有的一份。**其余的形式模型，本目录要么已经有同一份内容，
要么有更新的版本（`ToolCallMC` 多了 `QuiescenceSafe` 断言、`ToolCall.cfg` 多了
`CHECK_DEADLOCK FALSE`，都是本目录这边更新）。

## 为什么可能有用

`QueueControl.tla` 只有五十来行，编码的是队列这一侧的几条性质：

| 模型里的性质 | 说的是 |
|---|---|
| `SingleClaim` / `ExactSlot` | **同一时刻只有一项被取批**，且占用位置与它一致 |
| `TakenInputStable` | 已经取走的输入**不再被改动** |
| `HoldRespected` | 会话级 hold 生效期间**不许再取** |
| `SafeRelease` | 强停之后**确认安全才释放** |
| `CommandHasExecutionRight` | 命令要真的**有执行权**才产生效果 |

[PF-014「输入的受理与排队」](../../../../design/product/README.md#已排定尚未开题的编号)
要回答的正是同一批问题——消息怎么受理、排队、调序、什么时候取一批。
**这一份是同一个主题上已经算过一遍的编码**，真做形式化时可以拿来对照，
看看当年划出的性质今天还成不成立。

## 为什么它没有被继任者接走

本能力已由 D-014 拆成 `capability.session v1` 与 `capability.run v1`，
两者都在本目录下——**但它们只有契约正文，没有形式模型**。
本目录二十八个模型里没有任何一个编码队列取批、hold 与强停，
**这些性质在拆分之后没有被别的模型接手**。这是留下它的直接原因。

## 它不是什么

- **不是当前契约。**它属于已退役的设计链，catalog 里标为 superseded；
  [新的规格容器](../../../../design/spec/README.md)另起一套身份与路径。
- **不是接受依据。**新体系里任何一条性质要成立，得有它自己的接受记录与证据。
- **不是必须继承的语义。**[PF-014](../../../../design/product/README.md#已排定尚未开题的编号)
  从产品问题出发重做，**得出与这里不同的结论是正常的**，不必解释为什么偏离。
- **不保证跑得起来。**它在当年的工具链与配置下跑过，本次迁入**没有重新运行**。

## 原件不改

`README.md` 与两份 `contract.md` 保持取来时的原样，其中指向 `docs/decisions/`、
`docs/proposals/` 和同级 spec 的相对链接，**是按它原来在根 `spec/` 下的位置写的，
在这里不成立**。留档保原件，不为了让链接好看而改写历史正文。

形式模型按本目录的约定放进了 `v1/formal/`（根 `spec/` 是平铺在 `v1/` 下的），
**这是唯一的位置调整，文件内容一字未动**。
