# capability.message-stream v1 的符合性场景

本表是规范场景，不是已执行的实现测试；模型覆盖与有限范围见验证说明。
事实帧写 `s:<seq>`，瞬态帧写 `~<owner>/e<epoch>#<seq>`，控制帧无位置。场景编号用前缀 `MSS`
（MSS-01～MSS-26；MSS-18～26 为本 baseline 新增交接/投影/媒体场景），与契约的条款编号 MS-xx 不共用含义：引用时写
"场景 MSS-xx"或"条款 MS-xx"。"模型动作 / 性质"列指 Cursor.tla 的动作与性质，
"模型外验收"列是提供者、投影或客户端须另行兑现的部分。

| 编号 | 场景与客户端看到的路径 | 条款 | 模型动作 / 性质 | 模型外验收 |
|---|---|---|---|---|
| MSS-01 | 正常流式：一条用户输入、一次 attempt、一条助手消息。`s:n queue.item.enqueued{batch 1/1}` → `s:n+1` 同批三帧（取批、建 Run、开 Step，客户端收到 3/3 后调用 changes，原子安装该批正文及 state updates 才把游标推到 `n+1`）→ `~A/e0#0 started{purpose: reply, historyAnchor: n+1, routeBinding}` → `~A/e0#1…k chunk`（含 `index = 0` 的 `block-start` 与空 `text-delta`；工具调用只有 `tool-call-start / end`）→ `s:n+2` attempt 结算事实 → `~A/e0#k+1 ended{attemptId:A,attemptEpoch:e0,runEpoch:e0,dispositionRef:{attemptId:A,attemptEpoch:e0,revision:r1,commitPosition:n+2},index:k+1}` → 客户端核对内外 identity 后原子替换草稿 | MS-06、MS-08、MS-20、MS-21、MS-22 | CommitFact（一批多条）/ Project / StartAttempt / Chunk / EndCommitted / Deliver；EndedAfterCommit、DraftCurrent、Monotone、BufferOrdered | 派生消息与耐久紧凑流记录一致（投影验收）；`index = 0` 与空 delta 不被序列化丢弃 |
| MSS-02 | 工具帧与结果交错：一次 attempt 提议三个并行调用，一个有耐久帧、一个无帧、一个只有瞬态帧。三条 `tools.call.admitted` 同批 → `s: tools.frame.stdout{call: C1}`（`render: terminal`）与 `~C3/e0#1 tools.frame.progress` 交错 → `s: tools.call.settled{C2}` → … → `s: tools.call.settled{C1}`；`frames(S)` 的帧与调用事实共享域序号 | MS-04、MS-05、MS-06 | CommitFact("s") 与 Broadcast（瞬态）交错；NoForeignDelivery、BufferOrdered、DeliverOnce | 帧的 `render` 来自命令声明；结果消息恰派生一次；客户端按 `(attempt, seq)` 拼接面板，不按流位置比大小 |
| MSS-03 | 后台调用结算：调用转后台，Run 结束后结果到达。`tools.relation.detached` → `run.step.opened{cutpoint: [deferred_receipt]}` → `run.state.changed{completed}` → 后台 `tools.frame.*` 继续 → `tools.call.settled` 与 `inbound.arrival.accepted` 同批 → `inbound.arrival.classified{queue}` → `run.lifecycle.created` + `run.epoch.issued` + `run.step.opened{cutpoint: [system_reminder{late_result}]}` | MS-04、MS-06 | 事实序列（CommitFact）；模型不区分事实种类 | 占位不消失、迟到结果恰呈现一次；结果消息在结算提交处即可读，不等裁决；提醒按模型族投影（投影验收） |
| MSS-04 | 人类请求卡片：`tools.call.proposed{C5}` + `run.wait.claimed{C5}` 同批 → `tools.call.admitted{C5}` + `hd.request.created{Q}` 同批 → Step 收束、`run.state.changed{waiting}` → 客户端向人类决定读面取卡片 → `hd.decision.recorded` + `tools.call.settled{C5}` + `inbound.arrival.accepted` 同批 → `inbound.arrival.classified{continuation}` + `run.wait.released{C5, settled}` 同批 → `run.step.opened` + `run.state.changed{running}` | MS-04、MS-14 | 事实序列 | 卡片内容与可答性来自人类决定读面而不是帧；答复以调用结果派生消息 |
| MSS-05 | 断线四处：(a) chunk 中断线 → 重连 `stream.opened{target, resumable: cursor, resync:none, baseline: {active: [{A, coveredThrough, state, transformVersion}]}}`，客户端沿有效 cursor 调 changes 安装授权增量，安装folded state后接 `index ≥ coveredThrough`；(b) 结算事实已提交但 `ended` 未投递 → 补齐含结算事实、基线无该 attempt，派生消息直接出现；(c) Run 结束后断线 → 补齐只含事实；(d) 收到 `n+1` 的 1/3 后断线 → 游标仍是 `n`，重连后服务端从 `n` 之后重发整批，客户端按 `dedupKey` 丢掉已有的一帧、收齐提示后仍由 changes 安装完整授权批才推进 | MS-06、MS-08、MS-10、MS-11、MS-23 | Disconnect / Subscribe（`cursor ≥ floor` 分支）/ Reconcile / Deliver；CursorComplete、SentComplete、AtMostOnePartial、DeliverOnce；进展 EventuallyDelivered、BuffersDrain | `now` 只是追平目标；耐久基线用 `asOf`，active baseline 按 MS-23 listener/snapshot 交接；`index` 不连续时丢草稿重订阅；重发批的正文安装仍须完成 |
| MSS-06 | 慢客户端与背压：瞬态环满 → `~C3/e0#7` 被丢，`stream.gap{owner: C3, reason: trimmed}`；事实队列满 → 该订阅 sent 水位停在批内（如 `n+1` 的 2/3），腾出空位后下一次广播或对账从 3/3 续推，不丢事实、不关订阅；瞬态再多也挤不掉事实；停住太久被保留期追上 → `stream.closed{resync_required}` → 重订阅走全量重取 | MS-11、MS-13、MS-17 | Chunk 的 `Broadcast`（瞬态环丢最旧、记 `pend`）/ DeliverGap / `Project` 与 `Reconcile` 经 `Push` 的批内部分推送 / ForceResync；GapMarked、CursorComplete、SentWithinProjection、EventuallyDelivered | owner 与 records 不受流影响（负载验收）；长期不消费的断开阈值是装配参数 |
| MSS-07 | 丢铃：一次或连续多次提交广播丢失。客户端察觉不到差别——服务端听到下一次广播时从水位 `sent` 补齐区间；没有后继广播时由周期对账补齐 | MS-11 | `Project(lost)` 的 `lost` 集合、Reconcile；CursorComplete、SentComplete；否定变体 `SpecNoFill` 给出反例 | 对账周期是装配参数；广播丢失由启动扫描兜底 |
| MSS-08 | 多客户端、撤权与获权：同一 Session 两个订阅（不同租户成员）各自游标、各自缓冲；一个被撤权 → `stream.closed{unauthorized}`，另一个照常，工作不受影响。一个成员对某个已关闭请求获得读权 → 可见范围版本变化 → `stream.closed{resync_required}` → 以旧游标重订阅 → 版本不符 → `resync: full`，历史里出现该请求 | MS-09、MS-14、MS-15、MS-16 | 两个 `Clients`（对称约减）；NoForeignDelivery、DeliverOnce 逐订阅成立 | 两处核对用两个不同租户的主体验收，不用同值替身；撤权不停止工作；可见范围版本由 Session 读面给出（授权验收） |
| MSS-09 | 进程重启：attempt 流中崩溃 → 所有订阅断开 → 重连 `stream.opened{baseline: {attempts: []}}`，草稿标 `crash_gap` → 随后由事实收尾（结算记 `unknown \| failed`，或新 attempt 带新 `epoch`） | MS-13、MS-22、MS-23 | Crash / Subscribe；DraftCurrent（旧 epoch 草稿不存活）、GapMarked | 未知结算记录与计费归模型执行；`epoch` 变化时客户端整体重基线 |
| MSS-10 | 游标掉出投影保留期：`subscribe(session, cursor)` 且游标低于 `floor` → `stream.opened{target: now, resumable: null, resync: full}` → 客户端不能以空/旧 cursor 调 changes，先从 `snapshot` 单一读面重取，期间更大序号的帧暂存 → 同水位 CAS 安装完成点：保存游标 `= asOf`，此后才用 changes 从 asOf 补齐并应用暂存帧；中途读取失败或可见范围版本变化则不保存、重开订阅 | MS-10、MS-12 | AdvanceFloor / Subscribe（`cursor < floor` 分支；安装视为原子）；CursorComplete 在全量重取后仍成立；否定变体 `SpecBuffered` 给出反例 | `floor` 由投影保留期与重建状态给出；安装完成点的原子性是客户端义务（客户端验收） |
| MSS-11 | 归档后的订阅：`session.lifecycle.changed{archived}` 只是事实提示；订阅继续存在，后台调用的帧与结算照常到达；删除后 `stream.closed{session_deleted}` | MS-19 | 事实序列；Disconnect 表示服务端关闭 | 归档不停止工作；删除后的读面按数据治理 |
| MSS-12 | 乱序帧（服务端缺陷）：客户端收到 `(seq, index)` 倒退、同批 `index` 跳号，或同批未收齐就收到更大的 `seq` → 视为服务端错误，关流并以游标重订阅；`seq` 跳号（别的 Session 的提交）不算错 | MS-06 | BufferOrdered 保证模型内不发生；场景检验客户端的防御 | 客户端接收规则（客户端验收） |
| MSS-13 | 用户中断与用新输入打断（流的视角）：中断 → `s: run.control.requested{interrupt}` → `s: tools.control.requested`（各在途调用）→ `~A/e#k ended{dispositionRef:{attemptId:A,attemptEpoch:e,revision,commitPosition}}` → `s: tools.call.settled{interrupted}` … → `s: run.state.changed{interrupted}` + 唯一 `run.epoch.closed{interrupt}` 同批 → 客户端标"已中断，可恢复"，未答问题卡片仍可答；resume → `run.epoch.issued` + `run.state.changed{running}`。用新输入打断 → `queue.item.enqueued` + `run.control.requested{interrupt}` 同批 → 转后台的 `tools.relation.detached`、被停的 `tools.control.requested` → 收口完成 `run.state.changed{superseded}` + 若 epoch 仍 open 则唯一 `run.epoch.closed{superseded}` + `run.wait.released{*, superseded}` + `inbound.arrival.accepted{system_notice}` 同批 → `queue.items.taken` + 新 `run.lifecycle.created` + `run.epoch.issued` + `run.step.opened` → 旧调用的结算与答复随后以 `inbound.arrival.classified{context}` 到达，在新 Run 的下一 Step 以系统提醒呈现 | MS-04、MS-06、MS-22 | 事实序列（CommitFact）；已由控制关闭的 epoch 在终态不重复 closed | Run 与调用状态机的级联归各自契约；客户端对"停止未确认"的呈现 |
| MSS-14 | 归档后迟到的后台结算：`session.lifecycle.changed{archived}` → 后台 `s: tools.call.settled{C7}` + `inbound.arrival.accepted` 同批 → `inbound.arrival.closed` → 客户端按位置拉到该结算派生的结果消息，占位标"已结算"；没有新 Run、没有提醒 | MS-19 | 事实序列 | 结算一律派生结果消息（投影验收）；归档不开新 Run |
| MSS-15 | 投影暂不可用：重建中 → 已开订阅收到一次 `stream.gap{owner: session, reason: unavailable}`，此后只有瞬态帧，事实帧停发、游标不动；新订阅同样受理；恢复后从水位对账续推，客户端察觉不到差别只有延迟 | MS-13 | `pv` 停住（`Project` 不发生）时 `SentWithinProjection` 成立、`Reconcile` 无事可做；`Project` 恢复后 EventuallyDelivered | 缺口标记只发一次、恢复后不重复（投递验收）；"只发实时帧"被禁止 |
| MSS-16 | 模型来源失联：活跃 attempt A 已有草稿 → listener/read 面失联 → `stream.source-unavailable{A, gen, source_lost}`，交接关闭但 attempt 与草稿保持 unresolved → full resync 重建 listener/snapshot；来源恢复后真实 chunk/ended 或迟到 settlement 仍能按 generation 与 MS-22 收尾。observer 不发 `ended{abandoned}` | MS-13、MS-23、MS-24 | 当前模型不覆盖 source-lost/subscribe-first 交接 | 验证 source-unavailable 非事实、非结算、可去重；只有 owner/权威事实能声明 abandoned |
| MSS-17 | 流中途中断，唯一文本块尚未 `block-end`：`started{purpose: reply}` → `text-delta` × n → 供应方超时 → `s:` attempt 结算（`partial`，内容保留文本前缀，缺失清单记该块截断）→ `ended{dispositionRef:{attemptId,attemptEpoch,revision,commitPosition}}` → 客户端以派生消息替换草稿：显示前缀并标"未完成" | MS-20、MS-22 | 事实序列 | 缺失标记表示"不完整"而非"缺席"（投影验收）；`purpose ≠ reply` 的 attempt 不产生草稿（同一验收） |

| MSS-18 | active subscribe-first：RegisterListener 返回 effective cut 10；callback 将 pub11 有序入 buffer；MC snapshot cut10 含 A compact state、`coveredThrough=k`（state=fold chunks `[0,k)`）；客户端原子安装 state，chunk index<k 去重，drain pub11。E 在同一队列串行器观察 empty 并切 live，pub12 随后 live。mutation 延迟11而先入12、gap/倒退、overflow、source/transform/visibility变化均必须撤 listener并换 subscriberGeneration完整 resubscribe，不能只清 buffer | MS-10、MS-12、MS-23 | 当前 Cursor 模型不覆盖 | callback/queue线性化与compact-state fold验收；当前有限模型的有界进展只在有限发布、最终公平与 buffer≥`2*(MaxChunks+1)`；该数值不是生产 sizing 契约，持续生产/反复overflow只验 safety |
| MSS-19 | prior unresolved draft A：断线期间A terminal并离开active，ended完全丢失；重连active snapshot为空。若 durable changes 返回 settled_without_message+outcome unknown，客户端首次关闭并呈现“结果未知”，inspect 后新 revision 可补正文但不重复 semantic close；若 M ledger 只有耐久 `attempt.closing.pending`，该 complete batch 的 attemptStateUpdates 即使无 terminal revision 也返回 in_progress+pendingReason=outcome_unresolved，保留草稿并 lookup，active snapshot 不参与该 fold。其它 settled_with_message/settled_without_message 按正文有无安装；abandoned必须带fence。full snapshot 缺少旧本地草稿时只标 local evidence_unavailable，不猜 outcome/存在/retention。fact-before-ended、ended-before-fact、迟到ended、client crash重发均至多close一次 | MS-11、MS-22、MS-24 | 当前模型不覆盖 | M ledger/SessionProjection/client reducer fault-injection；完整commit batch安装后才推进cursor |
| MSS-20 | CT-03 媒体去重：同一 `MediaRef{tenantId=T, mediaId=M}` 同时出现在过程帧和终态结果，媒体对象元数据另存 `producedBy{call: CallRef}`；两处引用都保留，客户端按 M 只呈现一次。未 retain 的媒体只可作瞬态观察，不进入终态结果 | MS-18、MS-22 | 模型外 | M/E 联合场景与客户端呈现验收 |

| MSS-21 | full snapshot 在 asOf=p 同时返回 history、collection coverage 与当前主体获准完整 attemptStates：A settled_with_message 带 contentRef，B settled_without_message，C settled_without_message+outcome unknown（首次 close），D abandoned+fence，F 从耐久 closing observation fold 为 in_progress+pendingReason=outcome_unresolved（保留草稿）。客户端旧草稿 E 不在授权集合时只形成 local evidence_unavailable；请求没有 E identity 参数，隐藏、不存在、已过期均无逐项响应。原子安装全部集合后才保存 cursor=p；缺任一授权 state 或正文则不推进。另一个 cursor-valid changes 场景中，closing.pending 所在 batch 必带 F 的完整 in_progress update | MS-12、MS-22 | 当前模型不覆盖 state payload | projection/client fault-injection；changes batch 对无 revision/有 revision 分支都携完整 update |
| MSS-22 | 新 epoch baseline A/e2 安装时 buffer 含 A/e1 chunk/ended、A/e2 started/chunk；丢弃 e1，全量 dedup started 与 `[0,coveredThrough)` chunk，ended 只按 dispositionRef；L1 overflow 只撤 L1，L2/source 继续。正常 transform 换代在旧代最后发布 `source.generation.changed{g1,g2,t2,transitionId,pub:n}`，E 排完其前缀后发 `stream.source-generation-changed` 并重订阅 g2；marker 后 g1 frame 拒绝，崩溃无 marker 则走 source-unavailable | MS-20、MS-23、MS-24 | 当前模型不覆盖 | identity/clock、listener isolation、generation marker 与 fold decoder 验收 |
| MSS-23 | snapshot t1/p1 捕获 A closing 后延迟；changes p2 先原子安装 A terminal、cursor=p2、semanticClose=1。迟到 snapshot 因 p1 < installedCursor（或 t1 已被新 replacement token 取代）整份丢弃，不能把 A/游标/revision/close bookkeeping 回退；重取仍按 changes 授权投影批的 coveredThrough 跨过 hidden-only 位置 | MS-08、MS-11、MS-12、MS-22 | 当前模型不覆盖 | client install CAS 与 reordered delivery fault injection |

| MSS-24 | 只有 hidden-only commit p11，客户端没有任何事实提示；有界本地对账调用 `changes(after=p10,to=latest)`，调用开始 resolvedTo=p11、projectionBatches 为空或固定空组、coveredThrough=p11。客户端核对 visibility/floor 后原子安装该空授权区间并推进 cursor=p11；不得从缺号分类隐藏对象。若投影尚只 completeTo=p10，本轮 coveredThrough=p10，下一次周期重试后才推进 | MS-04、MS-08、MS-11、MS-22；SE-10 | 旧 Cursor 模型不覆盖授权空组 | 客户端定时器、projection reader、零帧进展与隐私负例 |
| MSS-25 | p11 只有 M `attempt.closing.pending` 折出的 F `in_progress{pendingReason:outcome_unresolved}`，没有可公开事实提示；`changes(p10,p11)` 返回 p11 非空授权组及完整 attemptStateUpdates。客户端原子安装后保留草稿并推进 p11。随后 p12 事实提示末帧先到，但 p12 的正文或 terminal state 暂不可读，cursor 仍 p11；读面恢复后由 changes 完整安装再推进 | MS-04、MS-08、MS-11、MS-22；SE-03/10 | 旧 Cursor 模型不覆盖 state-only | state-only、last-frame-before-body、读取失败的客户端 reducer 故障注入 |
| MSS-26 | 投影全局 completeTo=p12，但客户端请求 `changes(after=p10,to=p11)`；响应 resolvedTo=p11、coveredThrough≤p11，不能把 p12 偷当已安装。history 一批 p11 派生 3 条消息而页大小 2，服务端整批独占一页；不能先安装前两条或推进 cursor。页 token 固定 asOf/visibility/最后完整批，换权或坏页整体 reset | MS-08、MS-11、MS-12；SE-03/10 | 旧 Cursor 模型不覆盖有界 API 与分页 | bounded response、超页批、重建与撤权 fault injection |

MSS-01、MSS-02、MSS-08 的替身要求（`index = 0`、空 delta、两个不同租户的主体）是验收清单，
不是模型性质。
