# 三个真实候选与取舍

选择对象相同：在已接受的 Account/Tenant 独立语义 owner 与统一 Tenant 个人创建前提下，首版单机怎样使凭据绑定、个人租户、失败认回与注册成功闭合。三条路径都不能把密码或凭据摘要写进 Tenant/Records 的通用事实，不能把历史租户结果当当前业务资格。

| 候选 | 怎样兑现必要性质 | 区分性前提与代价 | 证据与判断 |
|---|---|---|---|
| A. 一个本地原子事务 | 认证凭据唯一绑定、Account 身份与状态、Tenant 目标/owner 在同一耐久提交内成立；对外按同一结果认回 | 真正要求认证 provider 的写入与 Tenant/Records 使用同一个事务接口、同一失败结果；同机或同库文件不足以保证。会把两个可独立演化插件的持久化选择紧耦合 | 当前没有选定或验证这样的 provider，也没有可直接承载三方写入的现行装配。若以后成立，可简化为共同提交，但不能靠假设接受 |
| B. 两个本地动作，直接受信读取 F，目标流承担唯一性（推荐） | Account 耐久确认凭据后发无秘密且不可变的 F；Tenant 当前代读取 F，稳定派生 T/C 和按 UserRef 注入的 target，仅向该租户流写个人租户/唯一 owner；pending 与 T 查询恢复 | 需 Account 原操作/provider 认回、不可变 F 读面和恢复推进；容许 Account 已完成而 Tenant pending，不声称跨存储原子 | 符合首版单机、D-016/017 和 PF-026 允许的 pending；独立架构复核未发现需额外 I/index/混合流的反例。精确规格、模型及真实 provider 仍须验证 |
| C. 来源 F 耐久导入 I，再写 global claim 与目标租户 | Account F 经 CC-05 写入目标域 I，Tenant 用 I 的本代资格写 global personal-index 与 tenant 流，init 再写 bootstrap 流；源和目标回执分别认回 | 增加 I/outbox/ack、导入未知、额外 owner 根、共享 CAS 竞争及个人混合流 codec；还需避免无关账号的 durable CAS conflict 永久耗尽合法 T | 适合确需 Account 长时间缺席仍启动未开始的 Tenant 操作等额外目标；当前产品和系统约束没有该要求，D-017 未接受这些精确机制 |

**推荐 B。** A 的原子性前提尚未验证具备，不能作为已经可实施的规格承诺；C 为首版增加未由需求驱动的状态与失败面。B 保留真正存在的两个语义 owner 与 pending 失败事实，删除不承载额外保证的持久导入和 global index。不同账号的唯一性来自不复用 UserRef 的注入式个人目标；同账号不同来源只争其唯一目标，不把另一操作的结果当成功。

选择改变的证据：若具体认证 provider 与 Tenant/Records 确能在一个本地事务中共同提交且独立插件生命周期仍可兑现，可复议 A；若出现被确认的“Account 不可用时仍须推进未开始的 Tenant 创建”要求或直接受信读取无法保证来源真实性，才比较 C 或更小的替代交接。当前既不预选认证库，也不把未来分布式可能性当成 C 的首版需求。
