# 提案框架骨架（前台草案，2026-09-15）

用户要求：提案必须有候选（至少三个）才谈得上决策；先给大框架，派调研，再让 subagent 细化验证。
本稿是"我们想要什么"的锚，供调研对照，不是政策。

## 骨架

1. **提案 = 一组决定点，每个决定点是一条轴。** 第一个决定点永远是"这个需求对能力基是哪种关系"
   （组合 / 投影 / 拓展 / 换提供者 / 细分 / 新增 / 取代，见 [method.md](method.md) S3）；
   可行的关系类型本身就是候选。后续决定点由所选关系派生（拓展哪条契约、新增什么不变量、
   换谁的提供者……）。
2. **每个决定点 ≥ 3 个真候选。** "真"= 形状不同，不是同一形状调参数；必须含一个基线候选
   （最小改动 / 不做 / 延后）。每个候选写：形状、触及的基向量与消费者、新增不变量、证据义务、
   成本（新概念数、契约改动数、迁移量）、失败模式。
3. **比较用同一把尺，尺先于矩阵。** 尺来自已确认需求条款、全局约束、不变量、研发品味
   （最小正确模型、复杂度收益证据）。
4. **决定 = 选择 + 否决理由 + 复议条件。** 否决方公平陈述；写"什么观测会让它重新成立"；
   作者裁决 / 用户裁决分层（筛过度设计 → 顶层建模自定 → 只把产品取舍交用户）。
5. **证据两级。** 候选阶段证"能否成立"（模型、原型、上游先例），只对前一两名做；决定后证
   "实现是否符合"。三个候选 ≠ 三个原型。
6. **评审清单。** 每个决定点 ≥ 3 真候选？有基线？矩阵同尺？否决方公平？证据与主张匹配？
   Cordis 投影是否对每个候选都能画出来？

## 调研要回答的

- 成熟开源流程（RFC / PEP / KEP / ADR / Swift Evolution / TC39 阶段 / Nix RFC / EIP 等）与 agent
  框架（Semantic Kernel ADR、AutoGen/AG2、LangChain、Letta、Dify、Mastra、DSH 等）怎样表达"备选方案"、
  怎样记录决定、有没有阶段门、模板长什么样、评审看什么。
- 哪些做法在"由 AI agent 撰写与维护"的场景下站得住（可核对、可机器检查、不靠隐性共识）。
- 反面：哪些流程有"Alternatives considered"一节但形同虚设，原因是什么。
