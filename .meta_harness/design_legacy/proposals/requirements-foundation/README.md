# 系统目标与产品要求作为设计基础

状态：已接受。下文建议与 design.md、migration.md 保留讨论时的候选身份和措辞；
当前规则沿 [D-004](../../decisions/D-004-requirements-foundation.md) 进入，原目标已迁到
[系统目标与产品要求](../../requirements/README.md)。

## 问题与依据

用户已经明确：

- 系统目标和产品特性是后续一切建模、能力定义、架构、决定与产品化的前提和约束。
- 产品特性按环境、用户、智能体三个维度组织；每项有唯一主维度，副维度引用说明。
- 当前和未来的目标、特性会持续增长，单页不宜承担全部正文。
- 可检索 `omne-next/omne_harness` 与个人版的已存在或已承诺功能，补充并消解歧义。

现有 [D-001](../../decisions/D-001-documentation-system.md) 已确立知识归属和规格组织；
[D-002](../../decisions/D-002-decision-authority.md) 已允许用户新要求作为输入变化。
当前入口已经引用目标，但仍缺少可持续的正文拆分、需求确认范围、消费基线和
需求变化后的适用性处理。这里提出补足方案。

## 核心建议

继续使用现有 `docs/proposals/` → `docs/decisions/` 体系：提案承载候选和取舍，
决定记录已接受选择；新增目标与产品要求作为两者的上游依据。

1. 建立 `docs/requirements/`，分别维护系统目标与跨系统要求、产品特性。
   系统目标按主题拆页；产品特性按主维度放置，一项一个正文，副维度只作引用。
2. 已确认要求约束下游选择；决定 在这些前提内记录已接受方案。研究提供事实，
   规格拥有精确语义，实现与验证说明兑现程度，各自保留原有职责。
3. 每项特性使用不含维度的稳定身份，例如 `PF-001`、`PF-002`。接受设计时记录
   采用的需求身份、确认条款与 Git 基线，避免需求原文变化后旧设计被重新解释。
4. 新要求改变旧决定的前提时，记录影响范围并停止将冲突部分作为新工作的默认依据；
   新方案仍需评审与接受，旧决定和已发布规格保留其历史及适用版本。

详细设计见[组织与权威](design.md)，对现有体系的调整及检验见[迁移与验证](migration.md)。

## 取舍与待讨论

| 选择 | 建议 | 理由与代价 |
|---|---|---|
| 目标与特性是否放在同一上游目录 | `docs/requirements/` 下分 `system/` 与 `product/` | 形成统一入口，两类正文保持不同职责；名称需认可它同时容纳方向性目标与具体要求 |
| 产品特性的物理归属 | 按唯一主维度放文件 | 直接对应三维阅读；调整主维度时要移动文件、修复链接，稳定 ID 保留 |
| 需求历史如何保存 | 当前页 + Git 历史；下游接受记录固定受保留引用保护的 Git 基线 | 持续讨论维护较轻；正式基线需独立于可重写、可清理的开发分支保留 |
| omne-next 继承范围是否随上游变化 | 建议先确认来源基线，后续新增承诺作为变更输入 | 检索授权便于发现，不自动扩大继承范围；是否持续跟随需要用户明确 |
| 用户要求是否必须另发决定才生效 | 用户明确要求直接确认；决定负责设计选择和治理调整 | 延续用户逐步介绍的工作方式，同时保留确认依据与范围 |
| 初期追溯如何实现 | 在下游保存来源关系，使用已有 Markdown/Git 与检查工具 | 避免双份人工登记；自动生成反向索引可在引用规模需要时增加 |

一个替代方案是将所有产品正文放在同一 `features/` 目录，三个维度只做索引；它减少
主维度调整时的路径变化，但物理布局与用户指定的三维阅读分离。另一个替代方案是
像正式规格一样为每次确认复制 `vN/`；它使历史版本直接可浏览，也会增加逐步补充
阶段的文件与接受成本。当前推荐表中的较轻方案。
