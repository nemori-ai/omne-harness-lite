## 整体目录

下面是目标形状。尖括号表示按实际内容创建的目录，不是要求预建占位目录；带“按需”的文件也不要求每项都有。

```text
docs/
  README.md                          # 按问题导航及文档职责
  architecture-guide/                # 保留现有分层设计指南
  architecture/
    README.md                        # 当前系统概览与各视图入口
    constraints.md                   # 已确认的系统级要求及其规格映射
    views/                           # 按需：能力关系、状态权威、部署等视图
  decisions/
    README.md                        # 已接受决定与取代关系索引
    <decision-id>.md                  # 决定、理由、代价、适用范围及关联契约
  proposals/
    README.md
    <topic>/
      README.md                      # 状态、问题、候选方案、待裁决点、接受范围
      ...                            # 设计正文、review 场景与候选规格附件
  research/
    README.md
    <topic>/                         # 按需：固定版本来源、事实、推论与局限
  postmortems/                       # 按需：值得保留的事故机制与改进依据
    README.md
    <incident>.md
  maintenance/
    README.md                        # 文档维护入口
    organization.md                  # 归属、命名、索引与权威关系
    versioning.md                    # 状态、版本、引用与接受规则
    verification.md                  # 一致性检查、工具和证据规则
    knowledge-flow.md                # 研究、提案、决定与规格的联合使用
    defensive-evolution.md           # 经验提炼、适用范围、收益复核与退出
  defensive-patterns.md              # 当前防御指导与按需导航，持续更新

spec/
  README.md                          # 规格地图、检索方法与正式/历史边界
  catalog.json                       # 版本身份、位置、接受状态及接受依据
  capabilities/
    README.md
    <capability>/
      README.md                      # 本能力入口、版本导航与相关组合
      v1/
        contract.md                  # 语言无关的能力契约
        schemas/                     # 按需：该能力独有的边界消息形状
        models/                      # 按需：*.tla、*.cfg、*.als 等
        scenarios.md                 # 按需：消费者可观察的验收场景
        verification.md              # 规则到模型/场景/证据的映射及缺口
  data/
    README.md
    <concept>/
      README.md                      # 数据契约入口与版本导航
      v1/
        contract.md                  # 一个数据概念的身份、含义与约束
        schema.json                  # 按需：该概念的规范 JSON Schema
        ...                          # 按需：示例、结构模型、验证映射
  compositions/
    README.md
    <composition>/
      README.md
      v1/
        contract.md                  # 参与能力、假设、关系与整体性质
        models/                      # 按需：跨能力形式模型
        scenarios.md                 # 按需：集成及动态演化场景
        verification.md
  archive/
    README.md                        # 停止作为当前契约使用的历史材料
    ddd-models/                      # 一次性迁移的旧定义原件及原始登记信息
  tools/                             # 现有工具及必要校验，集中维护
  Makefile
```

保留 `spec/` 名称，取消有效规格中以 `domain/` 为唯一语义入口的规定。顶层 `tla/`、`alloy/`、`schemas/`、`scenarios/`、`traceability/` 的职责下沉至所属契约；共享工具仍集中维护。

已采用新结构发布的旧版本仍留在原契约的 `vN/` 下。`archive/` 用于不属于新契约版本线的旧材料，不把所有被新版本取代的契约反复搬家。

## 文档职责与权威

| 内容 | 权威归属 | 其他地方如何使用 |
|---|---|---|
| 项目方向和红线 | 根 `AGENTS.md` 的简述、架构要求的展开说明 | 链接展开；两者不各自新增不同含义 |
| 如何进行架构设计 | `docs/architecture-guide/` | skill 按问题路由，不复制整套规则 |
| 系统必须满足的顶层要求 | `docs/architecture/constraints.md` | 分解并映射到具体契约；尚未落实的规格明确标缺口 |
| 某操作、数据或组合的精确含义 | 对应的 `spec/**/vN/contract.md` 及其规范附件 | 架构图和说明引用具体版本，不重新定义 |
| 为何选择一个方案 | `docs/decisions/` | 关联契约和原提案，解释理由及后果 |
| 当前系统如何组成 | `docs/architecture/` 的视图 | 对有效契约作投影，标明覆盖范围和未决边界 |
| 尚未接受的具体方案 | `docs/proposals/` | 可引用为候选，不成为正式依赖 |
| 上游行为和其他研究证据 | `docs/research/` | 记录版本及核对范围，区分事实与分析 |
| 值得保留的故障机制及防线失效原因 | 按需建立的 `docs/postmortems/` | 模式和改进决定链接证据，不复制事故故事 |
| 当前有收益的防御指导 | `docs/defensive-patterns.md` 及按需拆出的专题 | 明确范围、依据和退出条件；系统保证链接所属契约 |
| 维护程序与工具规则 | `docs/maintenance/` | AGENTS 与 skill 只保留必要入口 |

权威按职责判断，而不是“所有 spec 都覆盖所有 docs”。例如，操作契约不能以更具体为由违背租户隔离要求；发现冲突必须先解决，不能把冲突版本登记为有效契约。架构决策改变行为时，应同时落实对应规格，不能只改决策文档。

`constraints.md` 保存系统级要求及其落实关系；具体不变量谓词仍由能力或组合契约拥有。实现细节、上游研究和待选方案分别进入对应位置，避免架构主文档继续累积所有材料。

Research、Proposal 和 Decision 按用途关联，可多对多引用，不要求线性搬移。具体转化与 agent 读取机制见[知识流转](knowledge-flow.md)。防御模式不作为永久累加的纪律表，维护与精简依据见[防御模式演化](defensive-evolution.md)。新增专题是维护规则，不扩展具体能力模型范围。

## 三个规格入口

### 能力契约

描述消费者可以依赖的能力：职责、操作、结果、错误、授权、所有权、依赖、生命周期、状态权威及变化规则。使用现有[能力契约描述要点](../../../architecture-guide/reference/contract-description.md)，不再创建一套重复的设计方法论。

是否单独成项，取决于能否独立解释承诺与边界。一个插件可提供多项能力；一项能力可有多个实现；某项服务也可以满足多个契约。目录不是插件树、运行实例树或部署树。

特定提供者的配置、资源释放和失败限制，如果属于本项目需要约束的公开实现边界，可以在所属能力下按需增加实现约束附件；若产生可独立消费的新保证，再判断是否需要新契约。包名本身不足以成为拆分依据。

### 数据契约

集中保存具有独立名称和复用价值的数据定义，不再分别建立 `enums/`、`value-objects/`、`entities/`、`aggregates/` 分类目录。租户身份记录、模型档案、路由约束和声明等级可以在这里各有自己的版本化定义；“记录”“枚举”“引用”等是定义的性质。

一份数据契约说明数据是什么、身份和取值意味着什么、结构关系怎样解释；改变这些数据需要什么权限、哪些操作和状态转移，由拥有行为的能力契约说明。需要区分状态集合与允许迁移关系，两者通过引用相连。

不是每个字段都独立成文件。只在一个契约内部有意义的匿名辅助结构可以内联；有独立身份、持久化解释责任或被其他能力引用的命名概念，需要独立的权威定义。消费者不得因为使用了不同语言、存储或边界，就复制一套同义数据结构。

封闭词表和动态注册的名称空间也要区分。前者由具体版本列出合法值；后者由注册与解析契约定义授权、可见性和撤除语义。不能为了集中管理类型而把动态可用项固化成一份全局 enum。

### 组合契约

当某项保证依赖多项能力协作，且不能由一个既有能力独立承诺时，在这里定义参与契约的精确版本、前提、交互关系、整体性质和失败规则。

例如，某项能力的依赖缺失响应由它自身定义；跨多能力的一次代际切换若要求一致观察或联合就绪，则需要明确组合契约。组合可以嵌套引用，但不能靠互相引用逃避规则归属；必须可解释假设如何被其他参与者兑现。

组合不一定是一个有进程、有状态的子系统。它首先是对共同运行方式的契约描述；是否需要协调服务，是后续独立设计问题。

## 单项契约怎样组织

最小的正式规格由契约入口、版本化 `contract.md` 和目录清单登记组成。其他文件按语义复杂度拆出，不要求一开始建满树。

以一个假设的“模型目录”能力为例，以下只演示组织方式，不批准服务边界：

```text
capabilities/model-catalog/v1/
  contract.md        # 管理行为、权限、状态变化；引用数据契约
  models/           # 如需验证并发更新/撤回语义，则放相关行为模型
  scenarios.md      # 如果已定义，记录消费者观察与不变量
  verification.md   # 已覆盖什么，哪些行为仍只有文字说明

data/llm-profile/v1/
  contract.md        # 档案的数据含义和身份；引用路由等数据契约
  schema.json       # 数据结构的机器约束
```

简单契约可以把场景与验证缺口写在 `contract.md` 内，内容增长后再拆。TLA+ 是行为权威表达；尚未提供 TLA+ 的部分应明确为未形式化，不能暗示 Markdown 已完成同等验证。

一份行为模型覆盖多个能力时，归属相应组合，而不是复制到每个参与能力。能独立复用的公共数学定义，可以在明确契约下共享；仅在确实出现重复定义时才考虑专用的模型公共目录。

## 横向共享与系统视图

跨能力共享不会自动成为 `common/` 子系统。数据定义的归属说明由哪项能力负责变更、或由哪组项目规则约束，并不限制谁可以合法引用。

租户是贯穿系统的要求，不应把所有含 `tenant_id` 的契约放进同一大目录。身份与成员关系定义只保留一份，各能力明确自身的检查点；跨能力的隔离性质在有必要时用组合模型验证。

目录清单支持按身份和版本定位，索引支持按主题阅读。能力依赖、所有权、数据引用和部署关系是不同的关系，按需形成架构视图；不强制一张树同时表示它们。文档中的“当前架构”是已接受设计的视图，实际安装的插件和正在运行的拓扑另属运行状态。

## 提案与最小起步结构

提案可以同时包含多个候选能力、数据和组合定义，并保留互相比较的方案。候选 Schema、形式模型和示例都留在提案目录中，不因扩展名可执行就进入正式目录清单。

提案内不强制 `vN/`；已经采用版本目录的旧提案保留其版本布局。后续重要 review 快照以明确的提案修订号或 Git commit 标识，不把一次草稿编辑误当成正式契约升版。

首次迁移只创建承接真实内容所需的入口。没有已接受组合时，`compositions/README.md` 可以说明职责和当前为空，无需虚构组合契约。已有 24 篇架构指南保留稳定路径，避免为了统一外观重排已经有效的分层导航。
