## 内容状态与接受边界

研究如何支持选择、提案如何形成最终决定，以及 agent 如何联合读取，见[知识流转](knowledge-flow.md)。本页拥有状态、版本与引用规则，避免在各入口重复定义。防御指导的收益复核和退出见[防御模式演化](defensive-evolution.md)。

提案的入口明确当前状态：`draft`、`in-review`、`accepted`、`partially-accepted`、`rejected` 或 `withdrawn`。这些状态表达设计处理结果，不是每次编辑必须依次经过的流程。

接受记录要能回答：谁在什么时间明确接受了哪些结论、对应哪个修订或具体版本、哪些问题仍未决定。当前项目由用户主导设计裁决；已有明确授权和接受依据的内容不重复索取批准，整理文件或检查通过也不能代替接受依据。

提案接受后保留当时讨论正文及必要快照，在入口补充结果和有效契约链接；后续演进从对应契约或新提案展开，不继续改写旧提案来表示“当前设计”。

部分接受时，逐项链接实际接受的契约或决定，其他候选继续留在提案内。不得把整份提案升级成一个模糊的“全部已批准”。正式目录清单只能登记已接受的契约版本；草案和候选附件不混入其中。

正式契约版本的生命周期状态由目录清单维护：

| 状态 | 含义 |
|---|---|
| `accepted` | 已接受，未被标记为取代或撤回 |
| `superseded` | 已有后继版本；旧版本仍可精确引用和复现，默认入口不再推荐它 |
| `withdrawn` | 接受已被撤回，不再作为新设计依赖；保存内容和撤回原因供追溯 |

“当前推荐版本”是独立指针，不能代替接受状态。已接受 v2 不自动切换所有消费者；采用哪个版本由消费者或系统组合明确。撤回某版本时，要标出仍引用它的有效契约和待处理后果，不能让索引变更伪装成全系统已经迁移。

研究材料只有来源、核对范围、日期和局限，不使用“已接受规格”状态。归档表示退出有效规格入口，不推断该内容过去已经被正式接受。

## 身份与版本

建议正式身份使用与 DDD 分类和文件路径无关的限定名，例如：

```text
data.llm-profile@1
data.model-routing@1
capability.model-catalog@1
composition.model-selection@1
```

这些名称只是格式示例。前缀说明契约职责，不编码插件名、包名、租户实例、数据库表或部署位置。目录清单负责将身份和版本映射到文件。

一份有独立引用意义的数据定义单独保存，能力和组合也独立版本化。操作、规则、场景在所属版本内使用稳定的局部 ID，例如 `rule:tenant-access`；引用时同时携带契约身份与版本，不能只写一个全局难以辨认的 `INV-1`。

`vN` 建议表示**已发布契约修订序号**，不暗示只有不兼容变化才能升版。任何改变已发布规范内容的变更都形成新版本，并说明是澄清、兼容扩展、语义改变还是拆分替代。兼容性要相对于具体消费者行为判断，不能只比较 JSON 字段。

| 内容 | 编辑方式 |
|---|---|
| 正在讨论的草案 | 可直接迭代；重要 review 记录绑定修订号或 Git commit |
| 已发布 `vN/` 的规范正文、Schema、模型及规范场景 | 冻结；新内容写入新版本，不覆盖原文 |
| 拼写或链接等已发布内容勘误 | 在可变入口记录勘误；需要改变规范原件时产生新修订 |
| 接受状态、当前指针、取代与撤回说明 | 更新目录清单，保留可追溯的变更依据 |
| 后续运行产生的证据 | 追加运行记录，绑定未变的规格版本与源码提交 |
| 架构视图、导航和设计指南 | 正常修订；改变已接受约束时关联明确决定和受影响规格 |
| 已接受架构决定的实质内容 | 保留原决定，新决定表达修正或取代，状态信息可更新 |

规格修订、运行时定义内容 revision、提供者 API 版本、某次活跃实例的代际、部署组合版本互不等同。运行时发布提示词内容或切换提供者，并不自动要求修改描述这些行为的规格。

## 目录清单与导航

建议将 `spec/domain/registry.json` 替换为一个仓库级 `spec/catalog.json`。这里的 catalog 是**文档和契约目录清单**，不参与 Cordis 运行时注册、服务解析或动态拓扑管理。

清单只负责以下信息：稳定 ID、当前推荐版本、各版本的入口路径、接受状态、接受依据，以及必要的前驱/后继关系。数据字段、不变量、依赖和验证结果不再抄入清单。

例如，一项概念只有一处 `current_version`；不再同时维护各处 `current.json`。新契约暂时没有可用当前版本时应明确为空，不能用“最大版本号”猜测。

这是最小信息设计，本轮不发布 catalog 的 JSON Schema。迁移实现时可以用现有 JSON Schema validator 校验这份小清单，不需要自制规格数据库。

人类索引负责主题解释和入口链接，不手工再维护一份状态与版本全表。需要展示当前版本或反向引用时，从清单和规范引用生成，或者直接指向权威登记项。小规模阶段允许按精确 ID 搜索定位消费者，不预建复杂依赖图服务。

## 引用和数据复用

正式契约将规范性外部依赖集中列在“引用”部分：目标 ID 与精确版本、链接、引用用途。用途应能区分数据类型、行为保证和组合前提；正文的说明性来源另行列出。

- 正式规范依赖必须可定位到已接受的具体版本，不使用 `current`、`latest`、分支头或未接受提案。
- 若引用的后继版本已经出现，旧的精确引用保持原义；需要更新时作为消费者契约变更处理。
- 设计指南、术语说明、上游文档可以作为解释性链接；不能靠一个浮动链接引入新的规范义务。确实依赖的外部行为要记录版本及适用假设。
- 数据 Schema 使用不可变的规范 `$id`，跨文件引用优先使用目标的规范 `$id`；物理文件位置由本地清单和标准解析器关联。
- JSON Schema 的 URI 身份与本地路径不能混用。验证按 Schema 的基 URI 规则解析 `$ref`，不把“路径存在”当作 Schema 引用有效。所需资源应可在本地解析，不依赖临时在线拉取。
- 不同边界的投影要说明与权威数据的字段和语义映射；投影不是复制定义的理由。

能力独有的请求或事件封套可以放在该能力的 `schemas/` 下，通过 `$ref` 复用数据定义。如果它具有独立消费者、独立演进需求或跨能力共享的语义，再提取为 `spec/data/` 的命名契约。辅助 Schema 不自动需要独立版本目录。

规范中的引用描述“依赖什么保证”；运行时依赖还需要说明解析范围、绑定时机、有效期和消失后的行为。静态文档引用本身不代表运行时提供者可用。

正式接受时记录所依据的系统要求和架构决定版本；尚未独立版本化的要求文档可绑定 Git commit。当前要求变更后需要重新评估影响，不能让同一路径上的新文字静默改写已经冻结的契约含义。

## 不变量与验证证据

规则定义跟随其语义归属，不集中到脱离能力的全局大表。每条关键规则需要可引用的 ID，并说明适用对象、前提、需要成立的状态或观察边界。跨能力整体性质属于组合契约，不能在每个参与者处分别改写。

规范文字解释语义和适用范围；TLA+ 表达行为权威，Alloy 检查结构关系，JSON Schema 约束数据形状。它们不是可以任选一份解释的重复定义，出现冲突时必须修正规格，不能以某个工具检查通过覆盖冲突。

每项契约可用简短映射表记录：

```text
规则 ID → 对应模型性质/Schema 约束 → 验收场景 → 验证证据或明确缺口
```

不要求每条规则同时有三类形式工件；未形式化、模型尚未运行、暂不适用及原因分别表达。验收场景应说明初始条件、动作、可观察结果和规则，不能只验证函数被调用。

已发布版本中的 `verification.md` 描述性质映射、验证方法与已知缺口，不反复改写“最近通过”的运行结果。后续证据可以保存在契约根的 `evidence/` 或稳定 CI 工件中，入口引用即可；小型项目无需先创建专用证据平台。

证据至少绑定：契约与模型文件版本、源码 commit、执行工具及版本、命令/配置、检查边界或假设、结果。只有在验证输入完全相同时旧结果才可复用；失败、不确定、未覆盖也保留其含义。测试和有限模型检查不等于无条件证明。

## 变更管理

变更以语义影响为尺度。尚未决定的新能力先放提案；用户已经明确作出的决定直接记录，不补造讨论流程。已存在的同义结构先引用；确需改变规范时产生新版本，并沿精确引用寻找消费者和组合。

正式接受的一次变更应在同一可 review 的变更集中包含必要内容：规范版本、接受依据、目录清单、消费者采用决定、相关架构投影和适当验证。无需为了填写固定清单额外写不相关文档；尚未完成的采用和验证明确保留为缺口。

发布规范版本与宣布实现支持它分开。两个契约各自成立，并不能证明二者组合成立；新的组合约束需要相应模型或场景支撑。跨能力的不一致不能通过给每份文档都改成 `current` 消除。

决策记录只为有长期解释价值的选择服务，例如真实的边界取舍、保证变化、成熟库复用与限制。局部字段澄清可以在提案或契约变更说明中记录，不要求每次编辑一份 ADR。

目录迁移与语义重设计区分记录。没有语义变化的物理移动不改变契约身份，但已发布的规范快照及其可复现引用不能被破坏；能保持路径稳定时优先保持。需要改变旧身份、拆分旧定义时按明确迁移关系记录，不能只做字符串替换。

## 检查与规则的落点

建议区分三类检查，具体命令名在实施时确定：

| 检查 | 应验证什么 | 不应声称什么 |
|---|---|---|
| 文档与目录一致性 | 链接/锚点、入口覆盖、身份唯一、状态与接受依据、引用可解析 | 设计本身正确 |
| 数据与形式规格 | Schema 及示例有效、所声明的 TLC/Alloy 任务得到明确结果 | 没有建模的部分已得到证明 |
| 实现符合性 | 按契约场景检查实际边界和行为，并绑定实现版本 | 所有实现或部署形式天然等价 |

按变更范围运行相应检查。被选择执行的验证所需工具缺失时给出明确失败或未执行结果，不能将其计为通过；尚无某类模型时明确“无此类验证任务”。安装检查与实际验证分开报告。

正式规格检查以目录清单选出的版本及其精确依赖闭包为范围；仍被有效契约引用的旧版本也在范围内。不能直接递归执行整个仓库的所有 Schema，把提案、归档和正式版本混为一组。提案和历史材料可以分别检查，其结果不改变接受状态。版本冻结检查针对已发布基线的规范文件变化，不根据文件修改时间猜测是否发布。

详细规则最终进入 `docs/maintenance/`；`docs/README.md`、`spec/README.md` 是入口。根 AGENTS 保留凝练原则与导航，必要的局部提示放对应目录的 AGENTS；是否需要局部文件由实际遗漏风险决定，不复制维护手册。双端 `architecture-design` skill 只同步信息路径、权威判断和按需读取方式。
