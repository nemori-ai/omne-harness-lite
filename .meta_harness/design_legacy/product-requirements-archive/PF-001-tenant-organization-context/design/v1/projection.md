### T-11 的前提必须写进契约

**前提：组织上下文只以显式参数参与求值，不作为可见性维度。**

若把租户做成服务可见性维度（为每租户提供独立服务实例），会立刻产生**第四类**
随上下文而变的差异——实例本身不同——PF-001 的收窄裁决当场失守，
且失守方式不报错，只是多了一种没人枚举过的差异。

该做法同时不提供隔离（basis `isolate-hides-instances-not-data`）：
可见性隔离实例，不隔离数据。

## 4. 业务规则

```
resolveScopeChain(account, currentContext) -> Layer[]
  返回：本次求值适用的层序列，每层带其标识
  **本操作不求值任何字段**——字段取值由设置(PF-006)、权限(PF-010)、
  工具组装(PF-014)各自按此层次求值
  ⚠ 本版返回层的集合与标识，**不排序**；消费者不得假设返回顺序即优先级（Q1）
  依据：PF-001 求值方式；不变量 T-12

switchContext(account, targetTenant) -> void
  前置：该账号在目标租户有有效成员资格
  后置：后续协作以目标租户为上下文；**账号身份不变**；
        不复制任何账号级事实到租户级，也不把租户级事实带出
  失败集合：{ no-membership, tenant-not-found }
  缺席默认：成员资格查不到 ⇒ 拒绝
  本契约不定义切换由谁在什么时机发起（Q2）
  依据：PF-026.C4；安全性质 T-7、T-9
```

## 5. Cordis 建模

**三项效用如何生效，而不产生第四类差异：**

```text
一次协作的求值输入 = { verifiedAccountRef, currentTenantId }
         │
         ├─→ 设置求值    (PF-006)  ─┐
         ├─→ 权限判定    (PF-010)  ─┼─ 各自按 resolveScopeChain 给出的
         └─→ 工具组装    (PF-014)  ─┘   同一份层次求值
```

三方消费**同一份层次定义**。若各自定义一套，同一字段在三处会得出不同结果而无人能解释——
这正是 T-12 要防的。

**不叉乘**：PF-001 明确不要求为「组织 × 其他身份维度」的组合预留独立集合。
本设计的组合数恒为 1（一次求值一个上下文），因为上下文是求值**输入**而非预存维度。

**为什么不用 `ctx.intercept` 承载优先级覆盖**：`intercept` 的合并顺序是**装配链**
（祖先在先、近者在后），而这里的优先级链是**数据层次**。两者不重合——
要让 intercept 表达数据层次，就得让 ctx 树形状恰好等于身份层次，
于是每个身份组合都要一条 ctx 分支，**正好撞上「不要求叉乘」**。

优先级覆盖由各求值方自己按层次求值，不经 ctx 装配。
