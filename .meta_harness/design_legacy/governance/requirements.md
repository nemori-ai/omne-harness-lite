# 系统目标与产品要求的维护

本规范落实 [D-004](../decisions/D-004-requirements-foundation.md)。正文入口为
[requirements](../requirements/README.md)，它维护所需结果、范围及约束；设计选择
继续由 proposals → decisions 接受，精确承诺由 spec 拥有。

## 身份与归属

系统目标按独立主题维护；产品特性按环境、用户、智能体中的唯一主维度放置。
主条目拥有完整要求，副维度 README 链接主条目并说明关联，不复制正文。
分类不规定能力或部署结构，一项特性与能力之间可以多对多。

PF-NNN 为全局稳定身份，编号沿介绍顺序、独立于维度；已有 SYS-* 保留其含义与
拥有者。移动或更名保持身份；不重用 ID。拆分、合并、撤回或替代保留旧条目身份
和去向，相关正文以链接连接。需要独立确认或引用的条款才增加稳定子身份。
元数据形状归[元数据规范](metadata.md#需求正文)。

每条要求明确适用范围、确认依据及其范围、来源补充或假设、可观察表现和待澄清项。
短主题无需填满模板。问题归其语义拥有者，入口只链接；跨主题共同义务同样只有
一个正文，例如 SYS-TENANT 拥有全局租户隔离，PF-001 引用并维护多组织协作差异。

## 确认与来源

用户明确要求直接确认，不需另造研究或逐条设计决定。记录日期、来源场景、原话
或忠实摘要及确认范围；有可访问会话或材料链接时附上。页内可以并存已确认正文、
来源解释、假设和未知，不能用整页 accepted 标签接受未来新增文字。

要求确认、阶段交付范围和兑现证据分别记录。最终目标已经确认仍可能缺少达成
判断；不能从目标确认推定第一版完整交付全部目标，也不能削弱“从第一天起”等
已明确时限。依赖关键缺失含义的定稿或实施暂停，其余范围可以继续设计和实验。

omne-next 的继承方向具有约束力。来源映射记录源仓库与提交、文件及条款、当时
接受或承诺范围和本项目对应含义。能无歧义映射到已授权继承范围的内容，可据用户
继承授权和来源登记；冲突、对象差异或解释选择列为待澄清。旧系统的实现结构、
部署策略与未接受设计不会随功能自动采用。具体截止范围及未来新增承诺的处理
以 [SYS-CONTINUITY](../requirements/system/omne-next-continuity.md) 为准。

## 下游依据与覆盖

已确认目标、产品特性、交付范围及用户技术约束共同约束设计。冲突须指出不能
同时满足的部分，由有权作该选择的用户解决；不能按目录、抽象程度或文件新旧
自动选择。用户明确取代的要求按其范围生效。决定只在有效需求前提和适用范围内
具有已接受选择的权威，接受设计不能豁免已确认要求。

下游拥有它消费了什么的记录：提案写需求依据、覆盖及缺口；决定接受时固定
需求身份、确认条款、Git commit 与当时路径；规格的背景或接受依据关联要求与
决定，规范契约依赖仍引用精确版本；实现和验证绑定采用的规格与证据范围。
纯技术支撑说明服务的目标或全局约束；纯治理选择说明治理来源，无须强挂产品 ID。

当前在正文使用“需求依据”及覆盖说明，不增加决定 front matter 字段。日常修复
可沿已有规格和决定追到需求，不必在每份文件重抄整条关系。影响查询先使用 ID、
路径及引用检索并人工核对漏项，不维护独立的全局 JSON 需求清单或人工双向关系库。
链接可达不等于满足要求；自动生成反向索引在规模产生实际需要时再增加。

## 基线保留

当前需求页持续演进，Git 保留历史，不为每次讨论复制 vN 目录。初稿可以使用明确
标识的工作区快照；正式设计接受前，其需求基线须形成可读取提交。Git 时间和
提交身份不代替用户确认依据。

正式消费基线使用保留引用，例如 `requirements-baseline/<name>` tag。维护者须将
引用与对象随仓库交付保存；不得改指或删除，也不能依赖可清理开发分支或本机
reflog。squash、rebase 或 GC 不得使已接受决定引用的基线丢失。迁移历史存储前，
先以自包含 Git bundle 等方式保全对象并更新恢复入口。

交付需在不含开发分支的独立检出中，从所交付保留引用恢复原 commit、路径和确认
范围，记录命令与结果。本地 tag 尚未交付不构成长期保留；可交付自包含 bundle
及恢复说明，远端是否保存另行如实说明。没有正式消费的新草稿无需逐次打 tag。

## 变更与适用性

1. 在拥有者处记录新增、修正、撤回或取代的范围与用户/来源依据，保留旧快照。
2. 沿下游引用核对提案、决定、规格和交付承诺，指出冲突或仍相容的具体范围。
3. 冲突部分在变更记录及当前架构中标为待处理，暂停新工作依赖该冲突选择；未受
   影响范围继续成立，旧接受记录仍是历史事实。
4. 形成必要的候选和取代决定。用户输入变化可用来源对比和因果场景复核，不伪造
   性能实验来“证明”用户要求。精确承诺变化发布新规格，消费者不自动升级。
5. 变更记录链接最终处置，当前架构收敛为处置后的投影，不长期重复维护消费关系。

旧规格与旧测试仍可解释旧实现；它们通过不表示满足新需求。新要求也不会自动
选定新机制。规则内文字、链接或实现修复沿相称检查完成，无需重走完整接受流程。
