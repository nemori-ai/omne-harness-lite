# 设计知识的准入与归属

本文件帮助 agent 判断一份材料是否值得进入设计链，以及应由哪个 family 持续维护；
产品心智与通用权威边界沿用父级约定。

## 先判断知识，再选目录

这里保存后续需求分析、设计和维护要继续消费的知识。准入依据是持续的消费对象，
不是任务名称、文件格式或评审状态；先读 [family 准入](README.md#家族准入与停止条件)，再进入相应 family。

一次交付的计划、派发、文件盘点与进度放本次明确工作区的 `tmp/`，不作为 design topic。
尤其不要因任务叫“迁移”就塞进 migrations；其长期边界与实际收口证据按
[迁移准入](migrations/README.md#主题准入)判断。

创建或迁入材料前执行四步：指出任务结束后的持续消费者；定位唯一语义拥有者；核对该 family README 的
最低信息与停止条件；再从本地 `.templates/` 建包并裁剪。任一步无法回答就停止建包，把待核对输入留在
任务区；不要先创建空 topic、`plan.md` 或第二份权威等待以后补齐。

需求交流若具有持续回顾价值但尚不是正式条款，可进入 requirements 的访谈信息包；访谈只保存来源语境，
状态升级仍由正式 requirement、proposal 或 decision owner 显式完成。触发与记录边界见 `harness-design-handbook` skill 的「需求归位」→「何时自主启记访谈」。

## 状态和交接红线

- 观察、推断、候选、评审、接受、发布、实现与验证分别记录；文件存在或 reviewer 无意见不能提升状态。
- 需求先投影到现有能力及组合；只有合理组合或扩展仍不能拥有剩余独立责任时才提出新能力维度及独立插件边界。
- 新建正式 proposal 至少三个实质候选；不足时继续 research/任务探索，不用改名、参数变化或空选项凑数。
- spec 的形式工件按性质需要选用；optional 表示不是每个 topic 都预建，已经触发的证明义务必须闭合或明确阻断。
- 迁移计划、worker DAG、扫描清单和运行日志留在 `tmp/`；migrations 只接纳长期前后对应、过渡约束与收口证据。

## 按当前缺口展开

- 新建或吸纳主题：读所属 family 的 README 与本地 `.templates/`；按[信息包规则](README.md#主题是信息包)裁剪，模板本身不代表知识已准入。
- 比较方案、记录接受或表达精确承诺：分别定位 proposals、decisions、spec，不能通过换目录提升状态；具体入口见 [family 地图](README.md)。
- 现有条款与实现或证据冲突：加载 `harness-design-handbook` skill，读其「规格演进」，定位拥有者和消费者，不能在施工计划里重写契约。

普通局部修订直接接续已有主题；当前准入、拥有者与缺口清楚后停止扩展阅读，不为一次任务补齐所有 family。
