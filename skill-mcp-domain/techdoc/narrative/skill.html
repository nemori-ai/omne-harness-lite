W1 之后源码里有什么（父分支 aafc0cdc9）

Skill 组仍是三个成员，只有 @omne-harness/skill-contract 有实现：22 个源文件、约 2400 个非空行、13 个测试文件 364 例。另外两个成员仍是模板草稿。读这个成员时按三个入口分开读，三者在 package.json 的 exports 里各占一条。

  • 公开根 .（给调用方）：index.ts 只做重导出。值与品牌在 values.ts、names.ts、digest.ts、media.ts；失败联合在 failures.ts；三个应用服务接口在 services.ts；包检查纯函数在 parse/；类别端口在 contract.ts；资产正文投影在 project.ts。
  • ./provider（给端口实现方）：provider.ts 只重导出 ports.ts 的三个端口类型、PackageInspection、SkillRef、PackageLocator，以及唯一的运行时导出 sealSnapshot。公开根拿不到这些名字，所以调用方无法构造快照、也看不到包定位。
  • ./testing（给实现方自测）：testing.ts 聚合三个套件与三个内存替身。套件返回 ConformanceCase[]，用例用 node:assert/strict 失败，与 tool-contract 同形，不依赖测试框架。

依赖方向

模块图是一棵严格的 DAG，根是 values.ts（只有类型，没有导入）。往上一层是品牌授予与纯函数（names、digest、media），再上一层是 snapshot.ts（用这三者算条目事实）和 parse/（shape → declaration/manifest → package）。contract.ts 复用 parse/shape.ts 的读取器，所以资产正文和 .omne/skill.json 对 scripts、settings 的规则只有一份。testing-* 只依赖端口与值，不被任何非测试模块导入——public-entry.spec.ts 沿 src 的导入图核对这一点。

两条真实的调用路径

  1. 检查一个包。来源把文件字节交给 sealSnapshot(rootName, files)：它逐条算编码、大小、媒体类型与条目摘要，按 UTF-16 码元排序，拒绝重复路径与「文件同时是目录」的前缀冲突，再把快照登记进模块私有的 WeakSet 并以断言式守卫收窄成品牌类型。然后 parseSkillPackage({ snapshot, control, expectedName? })：先 assertSealed（伪造快照抛 TypeError，这是调用方的编程错误），再核对两份控制文件字节的摘要（不符答 version-changed，这是竞争，不是错误），然后 readManifest 解析 SKILL.md 头部（frontmatterOf 逐行找定界，yaml-value.ts 把 YAML 节点转成带预算的纯值）、readDeclaration 解析 .omne/skill.json，所有发现攒进一个列表，最后 firstFinding 按封闭次序（INSPECT_REJECTIONS）取第一条拒绝。名字必须逐字等于包根目录名。
  2. 类别端口。skillBodyContract() 返回 assets 的 BodyContract。judge 的次序是：是真实读取 → 有 name → 等于能力名 → 合 SkillName 词法（name-invalid，本波新增）→ 工具引用合法 → 四个可加字段（description、scripts、settings、package.digest）合形。deriveDeclarations 对每项设置声明产出 setting:<类别>:<名字>。

怎样保证「只能由构造器造出」

两层。类型层：SkillPackageSnapshot 的品牌键是 values.ts 里模块私有的 unique symbol，三个入口都不导出它，不写 as 就造不出这个类型；types.spec-d.ts 证明字面量赋不进去。运行时：{ ...snapshot } 能骗过类型检查，所以 parseSkillPackage 再查 WeakSet。代价写在 SPEC：这是进程内凭证，不可序列化，同一成员被加载成两份实例时互不承认。

还没有的东西

三个应用服务只有接口：PackageInspection（在 ./provider，因为它的调用方是来源与资产登记一侧）、SkillCatalog、SkillAccess。它们的实现、读取 11 步、目录来源都在 W2。
