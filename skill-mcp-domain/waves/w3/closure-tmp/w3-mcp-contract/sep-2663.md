## 与 T6 现有读法对照

| T6 条款 | 原文 | 结论 |
| --- | --- | --- |
| `getTask` 发 `tasks/get`，读 `status` 与 `input_required` 时的 `inputRequests` | 一致 | 不冲突 |
| `getTaskResult` 也发 `tasks/get`，`completed` 的 `result`、`failed` 的 `error` 作为 `finished` 交出；`cancelled` 答 `cancelled`；其他 `not-finished` | 一致 | 不冲突 |
| `updateTask` 发 `tasks/update` 交回答复；`cancelTask` 发 `tasks/cancel` | 一致，参数名 `inputResponses`、`taskId` | 不冲突 |
| `-32602` → `expired` | 一致（不存在与已过期同码） | 不冲突 |
| `classify.ts` 的 `task` 分支在结果顶层读 `taskId` | 一致 | 不冲突；W2 spike 的 `task: {...}` 子对象是自拟，不是原文 |
| T7 `result-missing`：`completed` 没有 `result` | 原文要求 `CompletedTask.result` | 不冲突 |

## 本闭包据此采用的点

- `TaskReport` 与 `task` 结局加 `pollIntervalMs?`、`ttlMs?`、`statusMessage?`：从 `tasks/get` 与 `CreateTaskResult` 顶层读。`ttlMs` 为 `null` 时省略（无限）。
- 套件脚本里 `tasks/get` 的应答按 `DetailedTask` 顶层字段写，`resultType: "complete"` 可带可不带：传输读 `status` 等字段，不核 `resultType`。
- `-32021` 原样 `error-answer`（已定事项 12）。
- 停止条件「SEP-2663 原文与 T6 冲突」未触发。
