## 2. 方法（W3 起，写进范式 r3）

1. **应然—实然差距账本**：每个领域一份（`waves/w3/gaps-<领域>.md`）。列：应然条款（组页或 SPEC 原句与位置）→ 实然（源码位置与行为）→ 差距 → 处置（改实现 / 改承诺并给理由 / 登记为已知限制并给退出条件）→ 证据。每个闭包交回时更新账本；波末账本只能剩下有退出条件的项。
2. **性质账本**：每个领域列出系统关键性质（安全、活性、隔离、无披露、资源守恒、性能上界），每条写成定理：状态与参与者、前提（端口失败模型、公平性）、结论。每条配证据：TLA+ 模型与 TLC 结论（行为权威，按 `docs/verification.md`）、对真实实现的有界穷举探索（实现符合性证据）、契约测试（符合性套件条款）。六种状态分开写，不合并。
3. **对真实实现的有界穷举探索**：把模型的动作（端口答复、拒绝、同步抛出、挂起、迟到、并发调用、关停）实现成一个显式状态探索器，驱动真实的连接表（端口用替身），在每个可达状态核对性质。它是 TLA+ 模型的可执行映射，也是 TLC 不可用时的现有证据；范围写明，不推广为无条件证明。
4. **结构化并发**（MCP 连接表的应然设计方向）：每个异步副作用属于一个作用域（条目或表），作用域有错误去向与等待上界；不存在游离的 promise；端口调用只经一个适配器，把同步抛出、拒绝、挂起与正常答复变成一个类型化结局。
5. **条款 × 违约矩阵**：符合性套件的每条条款至少有一个命名的违约实现证明套件会变红（契约闭包第 2、3 轮已按此做，写成规则）。
