### 1.3 两条指示怎样同时成立

需求范围原则收的是功能与形状，不收正确性。SPEC 已承诺的不变式仍按结构修法与形式守护处理。这些不变式是：租户与对端账号隔离、结局如实、关闭不挂起、关停答复一致、资源恰好释放一次。

判断一项工作时，先问它是否兑现一条已要求的需求或已承诺的不变式：

- 是，就做，出了问题按结构诊断、形式守护和偏函数全化来修。
- 否，就停放，写明理由与重开条件。

已要求的需求来自四处：卡判据 C1–C6、两份领域交接（I-02）列出的消费者与服务、生态兼容基线（`compat/README.md`）、成员 SPEC 已承诺的条款。

## 2. 交付边界与目标

### 2.1 卡的总目标

总目标不变：两个领域在 M2 边界前把领域内部做完。契约、通用实现、本地宿主与 Cordis 服务定义在替身端口上完整可用。M2 之后只需接真实提供者，并与消费者联调。

新增一句范围原则：两个领域只交付已要求的需求，超出的记入停放清单，不在本卡做。

**C4（改写）。** MCP 调用口与任务操作在两种真实传输上，对本地真实服务端端到端走通。本地服务端是 server-everything（stdio、Streamable HTTP、旧 HTTP+SSE）、server-filesystem 与 mcp-server-fetch。旅程是协商 → 刷新 → 调用 → 取消：

- 调用覆盖完成与动作错误两种结局。
- 多轮输入与任务在服务端支持的形状上跑。形状不一致的项，由脚本化传输上的契约用例覆盖，并在报告里写明。

另外三条：

- 六个兼容目标上「发现 → 列工具 → 调一个只读工具」的结论与官方 SDK 2.4.0 客户端一致。远程三个目标在有网络时跑，读数写明时刻。GitHub MCP 需要 OAuth，不在范围内。
- 新代码的并发在探索器与 TLA+ 模型的守护之内。
- Skill 目录服务（`summaries`、`search`）可用。

证据是 W3 交接报告与卡评论。

**C5（改写）。** 包括五条：

- 两组 Cordis 服务定义成员由模板生成，`pnpm package:template scan` 为 pass。
- 每个服务键只由一个抽象 Service 的 `static provide` 给出（IC-2）。根入口不导入 Cordis（IC-4）。
- 两个 host-local 的 `./cordis` 插件在真实 Cordis `Context` 上装配后，测试按服务键取到服务，各走通一条旅程：
  - Skill：在目录来源上走描述 → 读。
  - MCP：在脚本化传输上走刷新 → 调用。
- 撤除插件时，MCP 的连接与进程经 `closeAll` 收口，用例断言撤除完成之后才返回。
- 两组组页「完整行为候选的正式承接缺口」表与领域页按实际成员和状态写回，review-docs 无阻断。

证据是 W4 交接报告。负责人的技术接受另记。

## 4. 实施交付方案与规划

### 4.1 评审与修复规则（从 host、call 第 4 轮起生效）

1. 每个闭包在最终 head 上过一次关口：
   - 正确性（A，L3 热点逐行加探针）与交付边界（E）必做。
   - 表达（B）只在 SPEC 或公开文档有改动时做。
   - 设计与实践（C）只在有新公开形状或新生命周期时做。
   - 差分变异（D）在最终 head 上只打热点，跑一次。
2. 阻断只认违反已要求需求或已承诺不变式的问题。简报写明这条判据，以及第 1.3 节的四处来源。超出的建议记「超出已要求的需求」，进停放清单或已知限制，不修。
3. 关口之后最多一轮修复。复审只核阻断是否闭合，不再五面全审。
4. 同一类阻断第二次出现，做结构诊断：
   - 找共同前提。
   - 把规则写成全函数或 TLA+ 不变式。
   - 配有效动作的变异，证明不变式能变红。
5. 核对写者的自裁时，承诺的每一半都要核。
