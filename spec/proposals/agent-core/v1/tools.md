# 工具提案

沿用 `omne-next/omne_harness` 的定义、引用、执行、结果分离，不创建一个同时拥有
Schema、权限、运行实例与结果的 Tool 大聚合。具体证据见 [来源](sources.md)。

## 模型导航

| 模型 | 层次与责任 |
|---|---|
| `ComponentRef@2`（模型定义已撤回） | 值对象；精确引用共享组件定义 |
| `ComponentProfile@1`（模型定义已撤回） | 值对象；定义来源的声明投影，含工具分支 |
| `ToolVariant@2`（模型定义已撤回） | 值对象；输入 Schema、返回约定 |
| `ToolModelRequirements@1`（模型定义已撤回） | 值对象；本项目对模型适配需求的候选表达 |
| `EffectiveToolBinding@1`（模型定义已撤回） | 值对象；一次请求实际暴露的工具、定义与执行代际绑定 |
| `ToolExecutionFact@1`（模型定义已撤回） | 不可变读模型；从事件派生，非新持久聚合 |
| `ToolResultLedger@2`（模型定义已撤回） | 聚合；一条转储结果的保留、读取、墓碑 |
| `DetachedWorkOrder@1`（模型定义已撤回） | 聚合；离场工作所有权与恢复 |

`ToolVariant` 这个原仓符号指 ComponentProfile 的 tool 分支；“同一能力的多个
模型适配形态”用多个组件引用加适配声明表达，不能把两个意思合成一个 variant ID。
工具不是独立顶层资产聚合的事实不意味着定义没主人：定义归来源组件/蓝图的版本化
发布体系；部署插件负责注册执行实现。数据中不放函数、客户端或 Context。

## 声明到执行

定义引用 → 在可信租户上下文解析 Profile → 检查已安装实现与版本 → 检查模态/
能力等级要求 → 权限及资源就绪判定 → 形成 EffectiveToolBinding → 放入
RequestSnapshot → 模型提出调用 → 再次校验授权与实现代际 → 执行 → 留存事实与结果。

快照说明“当时展示了什么”，不赋予永久调用权。快照后权限被撤回，调用必须被拒绝；
实现被卸载不能悄悄绑定到同名新版本。正在执行的旧实现按生命周期约定 drain/cancel，
下一请求再选择新形态。参数中的 tenant、grant 等值不能充当执行凭证。

模型适配声明只做能力过滤，不替代治理。输入/输出要求分别校验；未声明即无模型
要求。多个形态同时匹配且缺乏明确优先规则时给出冲突，不靠注册顺序碰运气。
无匹配时记录原因，若是必需能力则本次装配失败，否则显式排除。

## 结果和失败

原样内联、小结果转储、大结果分片、detached 占位不能混为一次成功 ToolResult。
对模型的消息、持久骨架事实和 UI 投影均引用同一执行 outcome；不同表达不能互相矛盾。
`tool_call_id` 是模型关联键；`tool_execution_id` 是 harness 执行身份；台账 `row_id`
是存储聚合身份。三者不得因为“一次调用一行”而合并。

外部副作用未确认不能当作没发生；只有具备幂等或查询收据条件才可安全自动重试。
插件 dispose 不撤销已发送请求。结果转储须保留取回能力，清理留下墓碑而非假装未发生。

## 从原仓继承与本地选择

ComponentRef / Profile / ToolVariant、执行事实投影、结果台账与离场工作边界沿用原仓。
模型能力自动选工具在原仓是 **accepted / committed-future**；本项目用户已要求该能力，
因此提出数据模型与选择约束，但不声称迁来了一套已有实现。
ToolProgressProfile / 增量块属于后续详细进度协议，不作为本次基本 Tool 模型的先决条件。
