# capability.live-agent v1

## 职责、依赖与观察范围

本能力维护 Session 的活体运行实例：独占激活、装配绑定、受约束访问、工作所有权
和退出。身份依赖 [data.agent-runtime-identity v1](../../../data/agent-runtime-identity/v1/contract.md)。
行为权威由 [Runtime.tla](Runtime.tla) 的动作关系及其明确抽象边界表达；下列编号
给出语言无关语义和模型以外的提供者义务。[场景](scenarios.md)给出符合性要求。

第一版一个应用部署只有一个逻辑运行时协调权威，所有访问同一 Session 的激活
都经过它。可按租户分区实现索引，但不能因创建第二个 Context/Registry 获得另一份
同 Session 执行权。多进程部署前必须实现等价的协调与旧代际隔离；本版未规定
租约、故障接管或共识算法。现有进程已经失去协调权时不得继续接纳或提交。

注册表拥有活体状态；Session 能力拥有会话身份、定义关联、持久历史及业务状态；
驱动能力拥有 Run/Turn、输入、模型请求和控制策略；工具与子任务能力拥有其独立
工作。一个实例 `ready` 只表示运行装配可用，不表示某 Run 已启动、完成或可恢复。

## 执行信任前提

本版的 Registry、同进程 Factory/驱动、访问验证、Session attachment 及资源
提供者属于部署已信任能兑现本契约的实现。租户调用者通过受限入口使用它们；
不能把仅获得有限文件/网络/服务权限的插件直接当作可信内部实现。Context、
作用域过滤、TypeScript 私有字段和 Node VM 本身均不提供恶意代码安全隔离。
有限信任或 Agent 开发的可执行插件接入前，部署能力必须建立与其实际授权相符、
能约束宿主文件/网络/进程/服务访问的执行边界，并验证跨该边界的身份与权限。
当前没有该映射时不得以“已过装载授权”放行。具体沙箱/进程策略留给插件执行
能力，本契约不承诺已实现该隔离，也不取消获准插件在线演化的产品要求。

## 对象与能力表面

| 名称 | 含义与所有权 |
|---|---|
| AgentRegistry | 维护 SessionRef → 当前激活记录，分配实例身份、串行裁决短状态转换，拥有登记撤销；不是 Session store |
| 激活记录 | AgentRef、阶段、原因、实际装配绑定、资源/工作账目；从私有准备到完成释放一直占用 SessionRef |
| AgentFactory | 一个可替换的构造提供者；取得被选定的确切绑定，准备驱动与实例资源，不能绕过 Registry 发布或启动工作 |
| FactoryBinding | 一次贡献的精确注册身份、解析范围、实现内容版本、可用状态及使用关系；不等同于版本字符串 |
| AgentHandle | 精确实例的受约束控制能力；只能使用授予的操作，不暴露原始可变 Agent、无限权限 Context 或注册撤销器 |
| runtime owner | 本实例资源的稳定运行宿主，负责关闭与清理。不是“最初调用 create 的临时 Agent”，也不是业务 parent |
| initiator | 显式因果归因，携带原始 AgentRef；可缺席/清空，不提供租户授权、活性或销毁权 |
| 工作许可 | 一次已准入的受管工作及其全部未移交后代的所有权；不得以返回一个 Promise 但遗留游离任务冒充完成 |
| Session attachment | 提供者取得的当前 Session 能力绑定，确认精确身份、原有定义关联、可激活性及所需恢复前提；不是传入 DTO 的自我声明 |

工作账目可用作用域和结构化任务实现，不要求额外通用调度器。runtime owner 的
关闭权在取得资源前登记；已持有的清理能力只允许本实例收口，不因用户撤权而遗失
资源，也不能用于启动工作。所有创建路径必须有稳定宿主接管，不存在无主激活。

## 授权、查找与旧引用

**AR-1**：租户所属操作显式接收目标 SessionRef/AgentRef 及经可信边界验证的调用
依据。授权门在查询数据或产生效果前核对当前有效权限、租户、对象和操作；缺失、
冲突、未知、跨租户默认拒绝。相同 tenantId 只是一项必要条件，不能代替对象权限。
尚未越过授权门的下一操作使用当前依据；已准入工作由其控制契约处理撤权影响。

**AR-2**：`lookup(SessionRef)` 返回授权可见的状态描述及可另行取得的受限操作，
不返回无限权限活体对象。`resolve(AgentRef)` 只匹配精确生命期，旧引用返回过期，
不能隐式跟随 Session。跨租户/无权与不存在在公开读面采用不泄漏存在性的统一
不可访问响应；可信管理诊断可区分实际拒绝原因。list、事件订阅、反序列化解析、
缓存、后台调用和删除路径执行同一规则。租户事件路由过滤后仍有授权检查。

**AR-3**：owner、initiator、业务 parent、授权委托分别建模。Runtime 不通过
parent 指针自动推导权限或终止产品 child；因果上下文异步隔离且在退出边界后恢复。
显式传播跨线程/网络时重新验证，不能将异步局部变量当凭证。

## 激活与发布

阶段为 `preparing → ready → closing → releasing → disposed`；准备失败可以从
preparing 直接进入 closing。清理失败保留原退出阶段并记录 `blocked` 原因、
未完成对象与最近错误，不把 blocked 混成 ready，也不丢弃关闭请求。

**AR-4**：`activate(SessionRef, selection, owner, access)` 的第一个状态提交点是
在授权通过、owner 未关闭、确切 FactoryBinding 可接纳时，原子地为 SessionRef
预留一个新 AgentRef。已有 preparing/ready/closing/releasing 记录均返回冲突；
两个租户相同 sessionId 互不冲突。资源创建发生在预留及清理责任登记之后。
activate 不创建长期 Session；应用的 create-session 与 resume-session 组合分别
负责取得既有 Session 身份及必要持久事实，然后调用本能力。activate 不代表工作恢复。

**AR-5**：Factory 在私有准备域中取得 Session attachment、确定实际装配、建立
驱动和所需绑定。selection 是明确的选择输入；必须解析出确切实现和内容版本，
非法或缺失不能静默换目标/版本。Session attachment 必须保持原有会话、租户及
定义关联；能读取日志、找到对象或装配成功均不等于恢复到合法 Run 位置。
所有新资源在对外产生作用前登记清理责任；异步准备与关闭竞争时，晚到资源仍由
原激活持有并清理，不能重新开放入口。

**AR-6**：发布是同一协调权威的一次短提交：再次确认 preparing、owner 和每项
必要绑定仍有效，且 Session attachment 仍准许激活，然后原子设置 ready 和
发布后的实际装配描述。上述条件与提交必须受同一串行化/撤销屏障保护；仅在 await
之前检查不足以兑现。attachment 提供者必须提供可撤销、可原子验证的当前绑定，
Session 业务准入还须在实际 Run 准入处重查。不能声称两个独立注册表构成事务。

ready 成立后才发送 `activated` 事实通知，驱动工作必须重新通过工作准入门。
通知按该实例提交顺序分发；调用监听器时可重入关闭，但不能重复发布同一代际。
监听器同步抛错/异步拒绝隔离并报告，不否决已经成立的发布，不把通知失败返回为
“激活没有发生”。与上游可否决 created 的语义差异是本项目的明确选择。
若 activated 监听器立即请求关闭，activate 返回的精确句柄可已 closing；不得
承诺返回时必然仍 ready。状态查询解释当前结果。

**AR-7**：准备/发布前失败产生可查询的激活失败原因，不产生 activated；先关闭
准备入口并等待在途准备归还/登记资源，再走退出清理。只要资源或继续执行权尚未
安全收口，SessionRef 仍被占用。清理完成后释放占位；该次 incarnationId 不复用。
Session 已有持久事实不因准备失败删除。再次激活是新的尝试；本能力没有跨崩溃的
activate 幂等协议，上层不能用盲目重试创建另一份 Session 或工作。

## 工作准入与实际装配

**AR-8**：`admit(AgentRef, operation, access)` 在精确实例 ready、必要绑定有效、
当前授权通过时原子登记工作许可；在 closing/releasing、旧代际或依赖缺失时拒绝。
operation 的业务参数与结果由拥有该能力的契约定义，本能力不新增 send/followup/
steer/inject 的队列政策。已准入许可覆盖其尚未移交的因果子工作，结算前均受管；
关闭后不得以衍生任务为名接纳独立新工作。清理必需动作沿专用清理能力执行。

**AR-9**：每份工作使用同一份实际装配及确切依赖绑定；一次工作中不能逐字段吸收
变更后的配置。它的业务运行边界（例如一个 Run 或一次命令）由驱动指定，不能把
底层单次函数调用冒充该边界。运行时绑定驱动代码/必要服务的变化采用关闭旧实例、
完成释放、再激活新实例的顺序；保留同一 SessionRef，换 incarnationId。
模型选择、提示词、工具集合等能力配置可在各自契约规定的新工作边界重新求值，
无需为每个值变化重建 Agent。定义身份及授权对象不能因重建或换模型偷偷改变。

**AR-10**：`settle(work)` 只结算该许可的真实受管后代，重复结算无额外作用。
允许已准入工作在 closing 期间完成其受限收口，但释放阶段不能再提交新运行结果。
每个可提交结果同时核对实例、工作许可和业务执行权；仅 AgentRef 正确不证明
对应 Run 仍有提交权。业务终态及 force_stop 的隔离由驱动/工作权威实施。
旧实例晚到回调不能改新实例状态；外部已发生/未知效果仍向原工作权威报告，不能
因为本地句柄失效就丢掉外部事实。

## 关闭、排空与释放

**AR-11**：`close(AgentRef, reason)` 通过授权或已登记的清理能力关闭该实例的
新工作/新资源接纳，并登记一次共享退出过程。并发重复调用加入同一过程，后来的
等待者取消等待不撤销关闭。原因至少区分显式退役、装配替换、owner 关闭、依赖
撤除及准备失败；这些原因不能自动改写为用户的 interrupt/cancel/force_stop。
closing 是已接纳关闭意图，不代表运行已停止或物理资源已释放。

**AR-12**：共享退出过程依次完成：

1. 关闭准入，通知驱动进入退役收口。驱动停止发起新 Run/独立任务，处理当前
   工作到允许的停止或移交位置；在途准备也必须结束其资源归属。
2. 等待所有由本实例拥有的工作结算；独立工作只能在其权威已确认接受所有权、
   后续观察/控制关联可追溯且不再依赖旧实例后移交。移交未确认或结果未知仍由
   原账目持有，不能先减计数。v1 不提供任意热迁移或通用移交 API。
3. 没有准备/工作、驱动确认静止后封闭运行提交权，进入 releasing。按真实
   依赖顺序清理实例资源、绑定和 Session attachment；清理成功前保持独占占位。
4. 所有本实例资源已释放，才撤销登记、设置 disposed，并向此前发布过的实例
   分发一次 `disposed` 通知。未发布的失败尝试只有失败/清理诊断。通知失败隔离
   报告；占位释放后旧清理器仍只能指向原代际。

驱动、工具、Session adapter 必须分别兑现真实静止、移交及资源释放条件；Registry
不能把“收到停止请求”“清空 Map”“Cordis fiber 进入 DISPOSED”当成这些证据。
按此顺序解决源基线中 Handle 清理与两注册表删除顺序不一致的问题；没有自动
删除长期 Session 的步骤，也没有未经明确授权的业务后代级联终止。

**AR-13**：挂起的工作或清理不设隐含超时成功。等待超时/取消返回“退出未完成”及
当前阶段；资源泄漏、失败和外部结果未知分别保留。失败后继续不依赖失败项的清理，
保留失败项及依赖它的资源；有权管理者可在提供者声明可安全重试的动作上继续
同一退出过程。不可重试或无法确认安全的项目保持阻塞，不能删除占位强开新实例。
如果外部效果已由独立工作权威持有，效果未知不必阻止本地资源释放；移交必须先成立。

**AR-14**：工作内部请求自己的关闭可以得到关闭已受理的结果，但不得等待包含
自己的完整退出。需要等待的调用明确返回 self-wait 拒绝，调用者先结束工作，外部
宿主继续等待。不能为了避免死锁把仍有执行权的自身工作从排空条件里无声排除。

## 动态提供者、作用域与事件

**AR-15**：Factory 是作用域内的受管贡献；同解析键的重复绑定拒绝。不同键/作用域
可并存，activate 必须解析到一项明确绑定；选择规则由装配给出，不能偷偷挑任意
可用提供者。绑定撤除先关闭其新激活准入，再请求所有使用者退出；在途准备也包括
在内。提供者资源必须活到使用者完成所需收口；清理未完成不得报告撤除成功或复用
同解析键。旧撤除能力只作用于该绑定，不能删除后来同名贡献。其他绑定不受影响。

**AR-16**：装配区分实例存续必需绑定、某操作必需条件与可选贡献。远端连接不可达
只使实际依赖它的操作等待/拒绝；不能把模型网络断开变成全实例不可查询。可选贡献
消失仅改变依赖它的能力，独立操作保持可用。实例存续必需的每项服务/贡献，其
使用关系都要能在撤除前使受影响实例关闭准入。
不能只依赖“大注册表还在”。可计划的撤除先完成 AR-15 的协作收口，再卸载
Cordis 提供者；异常丢失立即标明不可用并阻止后续工作，不能假定丢失的资源仍可排空。
此时保留 blocked/未知情况，由资源权威核实或隔离。依赖重现不复活旧实例；完成
原退出后才能以新代际激活。此规则不要求整个系统停机，也不禁止独立能力并行。

对实例可选的贡献，一旦被某项已准入工作绑定，就成为该项工作的在途依赖。
消费能力负责登记工作到确切贡献的使用关系；贡献 owner 负责兑现撤除门。计划
撤除先停止新使用，按所属能力契约等待既有使用完成、合法终止或确认移交；
最后一个使用满足该条件前不得释放它需要的资源。尚无在途撤除策略时，明确拒绝
有活跃使用的撤除，而非擅自选择中断或卸载。使用关系必须进入同一撤销屏障，
检查“无人使用”与建立新绑定不能竞态穿过。该局部收口不自动关闭整个 Agent。
意外丢失时，消费能力向原工作报告真实失败/未知及影响，不能把稳定绑定写成
服务永远可用，也不能把连接恢复直接当作旧工作成功。

**AR-17**：生命周期通知是有序的进程内观察，载荷包含精确 AgentRef 和阶段。
不是 append-only Session log、耐久提交凭据、RPC 或恰好一次交付协议。异步观察者
不能凭过去事件控制现在的实例；必须重新经过精确引用和授权门。initiator 的同步/
异步归因传播可以沿成熟实现复用，但它不承担整个运行时的工作排空权威。

## 依赖端口义务与当前交付边界

本版本规定上述运行时端口的提供者义务，不将候选 Session/授权/Loop 规格作为
隐含正式依赖。实现者须为下表提供已验证的符合性映射后，才可接入产品运行路径。

| 端口 | 必须兑现的输入、输出与失败含义 |
|---|---|
| 访问验证 | 当前主体/租户、目标、操作的允许或拒绝；不能从标签推导授权；不可用时默认拒绝 |
| Session attachment | 精确 SessionRef/定义关联、激活前提及撤销屏障；释放只解除运行时附着，不结束/删除 Session；恢复内容由其专有契约决定 |
| Factory/驱动 | 私有准备、实际绑定、退役收口、真实静止、工作账目和独立工作移交；失败/未知不得伪造排空 |
| 资源/贡献提供者 | 可用性、确切使用身份、关闭和清理完成；异常丢失、不可安全重试及残留资源可见 |

这是一份内核运行时契约，未实现或完整规定 Session 日志与恢复、Run 状态机、
输入队列、interrupt_then_run、工具/HITL/预算策略、定义发布治理、跨进程接管
或任意异构恢复。它们的产品要求继续成立，不能以本契约验收抵扣后续交付。
