# capability.message-stream v1 的符合性场景

本表是规范场景，不是已执行的实现测试；模型覆盖与有限范围见[验证说明](../verification.md)。
事实帧写 `s:<seq>`，瞬态帧写 `~<owner>/e<epoch>#<seq>`，控制帧无位置。场景编号用前缀 `MSS`
（MSS-01～MSS-17，沿提案的 MS-01～MS-17 顺序），与[契约](contract.md)的条款编号 MS-xx 不共用含义：引用时写
"场景 MSS-xx"或"条款 MS-xx"。"模型动作 / 性质"列指 [Cursor.tla](Cursor.tla) 的动作与性质，
"模型外验收"列是提供者、投影或客户端须另行兑现的部分。

| 编号 | 场景与客户端看到的路径 | 条款 | 模型动作 / 性质 | 模型外验收 |
|---|---|---|---|---|
| MSS-01 | 正常流式：一条用户输入、一次 attempt、一条助手消息。`s:n queue.item.enqueued{batch 1/1}` → `s:n+1` 同批三帧（取批、建 Run、开 Step，客户端收到 3/3 且拉到该批正文才把游标推到 `n+1`）→ `~A/e0#0 started{purpose: reply, startedAfter: n+1}` → `~A/e0#1…k chunk`（含 `index = 0` 的 `block-start` 与空 `text-delta`；工具调用只有 `tool-call-start / end`）→ `s:n+2` attempt 结算事实 → `~A/e0#k+1 ended{committed, position: n+2, index: k+1}` → 客户端原子替换草稿 | MS-06、MS-08、MS-20、MS-21、MS-22 | CommitFact（一批多条）/ Project / StartAttempt / Chunk / EndCommitted / Deliver；EndedAfterCommit、DraftCurrent、Monotone、BufferOrdered | 派生消息与耐久紧凑流记录一致（投影验收）；`index = 0` 与空 delta 不被序列化丢弃 |
| MSS-02 | 工具帧与结果交错：一次 attempt 提议三个并行调用，一个有耐久帧、一个无帧、一个只有瞬态帧。三条 `tools.call.admitted` 同批 → `s: tools.frame.stdout{call: C1}`（`render: terminal`）与 `~C3/e0#1 tools.frame.progress` 交错 → `s: tools.call.settled{C2}` → … → `s: tools.call.settled{C1}`；`frames(S)` 的帧与调用事实共享域序号 | MS-04、MS-05、MS-06 | CommitFact("s") 与 Broadcast（瞬态）交错；NoForeignDelivery、BufferOrdered、DeliverOnce | 帧的 `render` 来自命令声明；结果消息恰派生一次；客户端按 `(attempt, seq)` 拼接面板，不按流位置比大小 |
| MSS-03 | 后台调用结算：调用转后台，Run 结束后结果到达。`tools.relation.detached` → `run.step.opened{cutpoint: [deferred_receipt]}` → `run.state.changed{completed}` → 后台 `tools.frame.*` 继续 → `tools.call.settled` 与 `inbound.arrival.accepted` 同批 → `inbound.arrival.classified{queue}` → `run.lifecycle.created` + `run.step.opened{cutpoint: [system_reminder{late_result}]}` | MS-04、MS-06 | 事实序列（CommitFact）；模型不区分事实种类 | 占位不消失、迟到结果恰呈现一次；结果消息在结算提交处即可读，不等裁决；提醒按模型族投影（投影验收） |
| MSS-04 | 人类请求卡片：`tools.call.proposed{C5}` + `run.wait.claimed{C5}` 同批 → `tools.call.admitted{C5}` + `hd.request.created{Q}` 同批 → Step 收束、`run.state.changed{waiting}` → 客户端向人类决定读面取卡片 → `hd.decision.recorded` + `tools.call.settled{C5}` + `inbound.arrival.accepted` 同批 → `inbound.arrival.classified{continuation}` + `run.wait.released{C5, settled}` 同批 → `run.step.opened` + `run.state.changed{running}` | MS-04、MS-14 | 事实序列 | 卡片内容与可答性来自人类决定读面而不是帧；答复以调用结果派生消息 |
| MSS-05 | 断线四处：(a) chunk 中断线 → 重连 `stream.opened{target, resumable: cursor, baseline: {attempts: [{A, nextIndex, stream}]}}`，客户端展开基线为草稿再接 `index ≥ nextIndex`；(b) 结算事实已提交但 `ended` 未投递 → 补齐含结算事实、基线无该 attempt，派生消息直接出现；(c) Run 结束后断线 → 补齐只含事实；(d) 收到 `n+1` 的 1/3 后断线 → 游标仍是 `n`，重连后服务端从 `n` 之后重发整批，客户端按 `dedupKey` 丢掉已有的一帧、收齐 3/3 才推进 | MS-06、MS-08、MS-10、MS-11、MS-23 | Disconnect / Subscribe（`cursor ≥ floor` 分支）/ Reconcile / Deliver；CursorComplete、SentComplete、AtMostOnePartial、DeliverOnce；进展 EventuallyDelivered、BuffersDrain | 基线与 `now` 取自同一同步切（读面版本）；`index` 不连续时丢草稿重订阅；重发批的正文安装仍须完成 |
| MSS-06 | 慢客户端与背压：瞬态环满 → `~C3/e0#7` 被丢，`stream.gap{owner: C3, reason: trimmed}`；事实队列满 → 该订阅水位停在批内（如 `n+1` 的 2/3），腾出空位后下一次广播或对账从 3/3 续推，不丢事实、不关订阅；瞬态再多也挤不掉事实；停住太久被保留期追上 → `stream.closed{resync_required}` → 重订阅走全量重取 | MS-11、MS-13、MS-17 | Chunk 的 `Broadcast`（瞬态环丢最旧、记 `pend`）/ DeliverGap / `Project` 与 `Reconcile` 经 `Push` 的批内部分推送 / ForceResync；GapMarked、CursorComplete、SentWithinProjection、EventuallyDelivered | owner 与 records 不受流影响（负载验收）；长期不消费的断开阈值是装配参数 |
| MSS-07 | 丢铃：一次或连续多次提交广播丢失。客户端察觉不到差别——服务端听到下一次广播时从水位 `sent` 补齐区间；没有后继广播时由周期对账补齐 | MS-11 | `Project(lost)` 的 `lost` 集合、Reconcile；CursorComplete、SentComplete；否定变体 `SpecNoFill` 给出反例 | 对账周期是装配参数；广播丢失由启动扫描兜底 |
| MSS-08 | 多客户端、撤权与获权：同一 Session 两个订阅（不同租户成员）各自游标、各自缓冲；一个被撤权 → `stream.closed{unauthorized}`，另一个照常，工作不受影响。一个成员对某个已关闭请求获得读权 → 可见范围版本变化 → `stream.closed{resync_required}` → 以旧游标重订阅 → 版本不符 → `resync: full`，历史里出现该请求 | MS-09、MS-14、MS-15、MS-16 | 两个 `Clients`（对称约减）；NoForeignDelivery、DeliverOnce 逐订阅成立 | 两处核对用两个不同租户的主体验收，不用同值替身；撤权不停止工作；可见范围版本由 Session 读面给出（授权验收） |
| MSS-09 | 进程重启：attempt 流中崩溃 → 所有订阅断开 → 重连 `stream.opened{baseline: {attempts: []}}`，草稿标 `crash_gap` → 随后由事实收尾（结算记 `unknown \| failed`，或新 attempt 带新 `epoch`） | MS-13、MS-22、MS-23 | Crash / Subscribe；DraftCurrent（旧 epoch 草稿不存活）、GapMarked | 未知结算记录与计费归模型执行；`epoch` 变化时客户端整体重基线 |
| MSS-10 | 游标掉出投影保留期：`subscribe(session, cursor)` 且游标低于 `floor` → `stream.opened{target: now, resumable: null, resync: full}` → 客户端清空本地、从 `snapshot` 单一读面重取，期间更大序号的帧暂存 → 安装完成点：保存游标 `= asOf` 并应用暂存帧；中途读取失败或可见范围版本变化则不保存、重开订阅 | MS-10、MS-12 | AdvanceFloor / Subscribe（`cursor < floor` 分支；安装视为原子）；CursorComplete 在全量重取后仍成立；否定变体 `SpecBuffered` 给出反例 | `floor` 由投影保留期与重建状态给出；安装完成点的原子性是客户端义务（客户端验收） |
| MSS-11 | 归档后的订阅：`session.lifecycle.changed{archived}` 只是事实提示；订阅继续存在，后台调用的帧与结算照常到达；删除后 `stream.closed{session_deleted}` | MS-19 | 事实序列；Disconnect 表示服务端关闭 | 归档不停止工作；删除后的读面按数据治理 |
| MSS-12 | 乱序帧（服务端缺陷）：客户端收到 `(seq, index)` 倒退、同批 `index` 跳号，或同批未收齐就收到更大的 `seq` → 视为服务端错误，关流并以游标重订阅；`seq` 跳号（别的 Session 的提交）不算错 | MS-06 | BufferOrdered 保证模型内不发生；场景检验客户端的防御 | 客户端接收规则（客户端验收） |
| MSS-13 | 用户中断与用新输入打断（流的视角）：中断 → `s: run.control.requested{interrupt}` → `s: tools.control.requested`（各在途调用）→ `~A/e#k ended{committed, settled: cancelled}` → `s: tools.call.settled{interrupted}` … → `s: run.state.changed{interrupted}` + `run.epoch.closed` 同批 → 客户端标"已中断，可恢复"，未答问题卡片仍可答；resume → `run.epoch.issued` + `run.state.changed{running}`。用新输入打断 → `queue.item.enqueued` + `run.control.requested{interrupt}` 同批 → 转后台的 `tools.relation.detached`、被停的 `tools.control.requested` → 收口完成 `run.state.changed{superseded}` + `run.epoch.closed` + `run.wait.released{*, superseded}` + `inbound.arrival.accepted{system_notice}` 同批 → `queue.items.taken` + 新 `run.lifecycle.created` + `run.step.opened` → 旧调用的结算与答复随后以 `inbound.arrival.classified{context}` 到达，在新 Run 的下一 Step 以系统提醒呈现 | MS-04、MS-06、MS-22 | 事实序列（CommitFact）；`cancelled` 结局的 EndCommitted 与普通结算同型 | Run 与调用状态机的级联归各自契约；客户端对"停止未确认"的呈现 |
| MSS-14 | 归档后迟到的后台结算：`session.lifecycle.changed{archived}` → 后台 `s: tools.call.settled{C7}` + `inbound.arrival.accepted` 同批 → `inbound.arrival.closed` → 客户端按位置拉到该结算派生的结果消息，占位标"已结算"；没有新 Run、没有提醒 | MS-19 | 事实序列 | 结算一律派生结果消息（投影验收）；归档不开新 Run |
| MSS-15 | 投影暂不可用：重建中 → 已开订阅收到一次 `stream.gap{owner: session, reason: unavailable}`，此后只有瞬态帧，事实帧停发、游标不动；新订阅同样受理；恢复后从水位对账续推，客户端察觉不到差别只有延迟 | MS-13 | `pv` 停住（`Project` 不发生）时 `SentWithinProjection` 成立、`Reconcile` 无事可做；`Project` 恢复后 EventuallyDelivered | 缺口标记只发一次、恢复后不重复（投递验收）；"只发实时帧"被禁止 |
| MSS-16 | 模型执行来源消失而进程未崩溃：活跃 attempt `A` 正在流出、消费者已见 k 个 chunk → 读面失联或服务撤回 → 代发 `~A/e0#k ended{abandoned, reason: source_lost, observer: message_stream}` 并在账上关闭 `A` → 客户端草稿标 `unconfirmed` → 来源恢复后 owner 迟到的 `chunk#k+1` 与 owner 的 `ended` 被丢弃 → 随后 `s:` attempt 结算事实（`unknown \| partial`）或 `run.state.changed{failed}` 到达 → 客户端按位置读消息收尾 | MS-13、MS-23、MS-24 | Abandon；DraftCurrent、GapMarked、AttemptsSettle | 谁发现来源消失（读面调用失败或服务撤回通知）；代发后同 attempt 的帧一律丢弃；重装载时读基线并按 `pub` 与 `version` 接帧（同步切验收） |
| MSS-17 | 流中途中断，唯一文本块尚未 `block-end`：`started{purpose: reply}` → `text-delta` × n → 供应方超时 → `s:` attempt 结算（`partial`，内容保留文本前缀，缺失清单记该块截断）→ `ended{committed, settled: partial, position}` → 客户端以派生消息替换草稿：显示前缀并标"未完成" | MS-20、MS-22 | 事实序列 | 缺失标记表示"不完整"而非"缺席"（投影验收）；`purpose ≠ reply` 的 attempt 不产生草稿（同一验收） |

MSS-01、MSS-02、MSS-08 的替身要求（`index = 0`、空 delta、两个不同租户的主体）是验收清单，
不是模型性质。
